Internal (skills/process): a lifecycle coordinator no longer does side work in its own session — including work the user hands it directly mid-run (FIX-1072). The grounding already stopped a coordinator working on a **PR event** (`orchestration.md` → "PR events are wake signals, not work items") but said nothing about the **user** channel, so an `epic-lifecycle` run handled every direct ask itself and reported it had been told to; it had not been told otherwise. New canonical section **"The coordinator dispatches; it never does the work"**, on the framing that a request from the user is an instruction about *what* happens, not about *who* does it: the closed list of what a coordinator touches with its own hands, a routing table for everything else (status answered from the table, a read-only look to `scout`, a change an issue in the set owns dispatched to that row's worker, anything unowned to `issue-manager`, the rest to a bounded `isolation: worktree` sub-agent), and what doing it yourself costs — the severe cost being that it bypasses every gate and lands on a branch no issue tracks. A row-owned request is **dispatched in the wake it arrives**, never parked as a note: `epic-wake`'s `pendingAction()` has no side-request condition, so a settled `PR_FEEDBACK` row would take its merge gate without the change. `epic-lifecycle` and `issue-lifecycle` carry pointer-plus-altitude deltas; `AGENTS.md`'s orchestration note gains it as a third rule.
