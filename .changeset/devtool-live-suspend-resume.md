DevTool now reflects the full suspend/resume/recovery lifecycle live, without manual refreshes:

- The request-stream hook's status handler ignored `request.suspended` (and `interrupted` / `aborted`), so a request that paused at a `ctx.suspend()` gate stayed on the "in progress" badge. It now maps those to the matching status and stops the live spinner.
- The chat view derived a request's status from the session-requests list snapshot (which only refetches on terminal/refresh) for any request already listed, so live transitions on the watched request didn't show. The live stream is now authoritative for the request it's watching — covering every transition (in_progress → suspended, then in_progress → completed across a resume).
- Resolving a suspension (approve/reject) posted the resume but never re-attached the panel's stream. The Suspensions view now hands the resumed request id back to the panel, which re-subscribes to the same-id continuation and follows it to completion.
- The interrupted-request "Resume" button started a fresh request via retry (new id). It now continues the same request under its own id (the FIX-811 crash-recovery path), re-attaching the stream to follow it to terminal.
- A same-request continuation re-enters under its original id, so re-attaching to that id was a no-op — the request-stream hook keys its connect on the id, and an unchanged id never reconnected. The hook now takes a reconnect token the panel bumps on resume/continue, forcing a fresh attach to the same id so the resumed run streams down live.
- The watched request's status was read from the live stream unconditionally, but the stream's state persists after its wire closes (a suspended run freezes at "suspended"). After a resume completed server-side, that stale value masked the store's fresher "completed", so the badge only corrected on a full page reload and clicking refresh appeared to do nothing. The stream is now authoritative only while actively connected; once it settles, the panel shows whichever of stream/store is furthest along the lifecycle, so a refresh reflects the durable truth.
- The Stream view rendered the raw append-only event log, so a resumed/continued request's superseded re-emissions (e.g. a human-in-the-loop gate's approval prompt, re-emitted when the block re-runs) appeared twice. It now collapses to the canonical view (`collapseToCanonicalLog`), matching `useSession` and `GET` history, so each emission shows once. The Trace view still consumes the raw log, so superseded runs stay visible there for forensics.
- A resumed request's post-resume output (e.g. "Approved. Proceeding…") didn't appear until a full page reload. A same-id GET stream can't follow a continuation — attaching while the record is still `suspended` yields a one-shot replay of the pre-suspension run — and the frozen live-item snapshot was masking the fresher store items. The chat now prefers the durable store items once the stream isn't actively streaming, and a bounded poll after a resume/continue brings the settled continuation's items in, so the post-resume output shows without a reload.
