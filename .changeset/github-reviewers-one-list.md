Trusted GitHub reviewers come from one stored list, with `GITHUB_REVIEWERS` as its default (FIX-2873). A coding run acts only on comments from an account on that list: a listed bot, or a listed user who can also push to the repository.

- **workforce:** `githubTrustedReviewers({ operator, judgeModel, holders })` builds the list a host installs. It reads `GITHUB_REVIEWERS` (comma-separated, a bot as `name[bot]`) once, when it is called, as the `github-reviewers` document's default. The default holds only until the list is first saved. After that the saved list wins, an empty one included, so emptying it stops all steering. It returns the `document`, a `read(ctx)` of the listed accounts, the `tool` that is the list's only writer, the same tool as a `capability` (`githubReviewers`, preset `tool`) for a worker that picks it under `capabilities:`, and `follow(github)`, the follower to hand the harness kit's `onPullRequestRecorded`.
- **workforce:** `setGitHubReviewers`, the tool, changes the list only on the operator's own typed message naming each account, in a session of a worker `holders` names (the host's coordinator, read from the session's server-set worker, so a worker hired later that reaches the tool is refused), after an evaluator reads that message, and after the operator approves the exact change in Inbox. No HTTP action writes the list. Given the list as it already reads while nothing is saved, it saves that list as the operator's own, so `GITHUB_REVIEWERS` stops deciding it. It saves exactly the list the operator approved, and saves nothing if the default changed before the approval was answered. Once saved, the same list again is refused as unchanged. Two approved edits answered at once both land. Once the tool has saved, the list is the document's state, which the screen and the tool both read. The document's body is a copy written after it.
- **workforce:** `operatorGitHub` takes `reviewers`, which declares the list's custom screen on the provider, and `interestModel`, the model a routine's `interest` screen is judged on.
- **workforce:** `githubTrustedReviewersScreen` now passes a listed bot (`name[bot]` in the list) without asking GitHub, and still asks GitHub whether a listed user can write. A bot is matched only against listed bots, and anyone else only against listed people, so a user who registers a listed bot's name isn't heard as that bot. `githubLoginsListed` keeps a bot's `[bot]`. `githubReviewersDocument(logins)` builds the body a save stores.
- **workforce:** a listed bot is heard only on the follow the list builds. `followPullRequest` takes `botsScreenedBy`, the custom screen a bot sender is handed on to past the sender screen. It must be one of the follow's `screens`, or the follow is refused. A model's `subscribe` can't set it. A session that rewrites its own follow (a routine on the same pull request) keeps every screen the follow lists and adds its own, and can't take outsiders the follow didn't, so it can narrow what the follow hears but never drop the list screen. The service flow's `trustedBots` is unchanged and stays service-wide.
- **workforce:** every pull-request follow is now written with `followRev: 2`. A coding run's follow saved by the earlier allow-list follower (no `followRev`, an `allow` screen with `bots`, outsiders taken, no custom screen) hears no one: its `allow` screen refuses every event on it, naming why, until the run follows its pull request again. Its fixed list would otherwise keep hearing an account the operator has removed, with no write check. A follow made today with the same screens is heard as it lists.
- **shift-manager:** the trusted reviewers are workforce's list. Set `GITHUB_REVIEWERS` for the default: the folder's `github-reviewers.md` and its seeded login are gone, so with the setting unset, nobody is heard until the list is saved. A list already saved reads as it was. Listed bots are now heard. The public `setGitHubReviewers` action is gone; the Shift Coordinator's tool is the only way to change the list.
