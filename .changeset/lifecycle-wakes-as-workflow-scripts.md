Internal (skills/process): the mechanical half of the two orchestration lifecycles moves from prose into deterministic workflow scripts under a new `.agents/workflows/` directory (`.claude/workflows` symlinked, matching how `.agents/skills` already works).

**`epic-wake` is now one epic-lifecycle wake.** The coordinator's refresh → advance → collect steps were pure procedure it had to re-derive correctly every wake: the objective gate that holds the whole set, a two-round review budget with one conditional third round, a concurrency cap shared between issue workers and POC settlements, and a claim dedupe. Those are now `if` statements in `.agents/workflows/epic-wake.js`, including a single `atReviewBudget()` that covers issue specs and the epic PR alike — previously the same arithmetic was restated three times across the two skills. The epic-PR fold (`epic-agent`) runs under that same budget rather than a separately-tracked counter. `epic-lifecycle`'s loop drops from six steps to five and no longer restates the budget, cap, or dedupe mechanics.

**`issue-multi-pr` is now one step of a multi-PR issue's DAG.** Ready-set derivation, base selection (a sub-PR whose deps are all merged bases on fresh `origin/main`; one whose single dep is merely open stacks on that dep's branch so review can start early; two open deps are waited on rather than stacked arbitrarily), the rebase a merged dependency forces, and the assembled end-to-end goal that the last merge does *not* satisfy — all encoded rather than described. Single-PR issues are a one-node plan and deliberately don't use it.

**The split is fixed by what a workflow script cannot do:** it has no user prompting, cannot receive a PR webhook, cannot sleep or schedule, and has no filesystem. So every gate (spec approval, epic objective, merge), every PR subscription, the `.orchestration/` store, and turn-ending stay with the coordinator, which passes state in via `args` and persists what comes back. Documented once in `docs/contributing/orchestration.md` → "The pieces at a glance" and in `epic-lifecycle` → "Each wake is a workflow".

**Canonical rules stay in `orchestration.md`, which also now documents the workflow-script contract** (the injected `agent`/`parallel`/`pipeline`/`log`/`phase` API, the no-imports/no-filesystem/no-clock limits, and the fact that `verify.mjs` is a local mirror of that contract rather than proof of it). The scripts are an executable second implementation at the epic altitude; standalone `issue-lifecycle` still applies the same rules as written. Both skills say so, so a rule change goes to the doc first and then to both.

To be precise about what the dedup bought: the *arithmetic* consolidated — one `atReviewBudget()` replaces three prose restatements — while the *narration* only partly did. The skills still describe what the scripts decide (a coordinator has to know), and the scripts carry short pointers to the canonical sections rather than restating them. A rule change is now a doc edit plus two implementations, not five prose sites.

Two limits are recorded rather than papered over: a workflow's own concurrency ceiling is `min(16, cores − 2)` — 2 on a 4-vCPU cloud session, below the 3–4 active issues `epic-lifecycle` recommends, so queueing is expected and logged rather than silent; and whether a workflow consumes one of Claude Code's 5 agent-depth levels is untested, with the existing in-context mitigation noted if a real run hits it.

Both scripts **fail closed**, because the coordinator is their only memory and a script that guesses corrupts state it can't re-read. Two invariants carry that, stated in both file headers:

**A null agent result means nothing happened.** `agent()` returns `null` when a sub-agent dies or is skipped — infrastructure failure, not an outcome. So a dead POC agent requeues its claim instead of recording a fabricated `INCONCLUSIVE` (the "false evidence" `orchestration.md` explicitly forbids); a dead assembled-goal agent retries instead of filing a phantom Linear gap and repair PR; a dead folding worker leaves the verdict on the row rather than consuming it; and a rebase returning anything but success keeps both its `open` status and its stack marker so the retry is still scheduled.

**Never advance a cursor past work that didn't happen.** An activity cursor moves only when the wake actually consumed that activity — a worker ran *and* returned. A row the cap deferred keeps its old cursor, or the feedback just logged as "deferred to the next wake" would read as already-handled and vanish. The cursor is a **timestamp**, not just a head SHA, since a comment never moves the SHA.

The assemble phase is an explicit **state machine** (`NEEDS_GOAL → NEEDS_GAP → NEEDS_FIX → AWAITING_FIX`, with a merged repair returning to `NEEDS_GOAL` because a landed fix still has to be proven), and the per-row update in `epic-wake` is a single named `nextRow()`. Both replaced ad-hoc predicates and inline ternaries that produced opposite bugs in successive passes — first re-running work and filing duplicates, then blocking the rerun while dispatching no retry either. Enumerating the states is what makes "resume at the stage you reached" checkable rather than incidental.

**A phase is a program counter, so it is constrained to the states the machine handles.** A worker's `phase` was a free-form string: a typo or a descriptive value like `"blocked"` was schema-valid, got persisted, and then fell through `pendingAction`'s default on every later wake — a row parked forever carrying no gate and no blocker to say why. Both schemas now share one `LIFECYCLE_PHASES` enum, and an invariant asserts the schema and the switch agree in *both* directions, so adding a phase to one side alone fails.

**The conditional third round follows the canonical rule exactly: it depends on what round *two* found.** `specLevelFound` was preserved whenever a worker omitted it, which is right for a non-review worker (an apply-verdict fold isn't a review round and its silence must not revoke an authorization) and wrong for a review round (whose silence means it found nothing). Carrying round one's finding through a quiet round two authorized a third round `orchestration.md` doesn't. The rule now keys on the action, and both halves are asserted, because fixing either one alone reintroduces the other. The epic side had the mirror image: `aboveBar` is *required*, so a verdict-only fold has to report something and reports `false` — revoking a third round a real round had authorized. It now keys on whether that fold actually spent a round.

**A `building` sub-PR status was a permanent stall.** `issue-lifecycle` documented the cached statuses as `building / open / merged`, but a wake is synchronous — a node either has a PR or doesn't — so `classify()` only knows `pending` and `open`. A node carried over as `building` matched no branch, produced no action, and logged as "waiting" every wake with nothing external able to move it. It normalizes to `pending` on the way in (BP-030) and the doc now describes the three statuses that exist. The check that should have caught this instead *encoded* it: it reached for `status: 'building'` as a convenient "not dispatchable" fixture and asserted the resulting silence was correct.

**Both channels of the spec-approval gate work.** Making a live scan the only source of `specApproved` fixed a real bypass (a carried `true` surviving a push) and broke the other documented channel: the user saying "approved" **in-session** leaves no comment or review for a scout to find, so that approval was discarded and the issue waited forever for one that had already happened. The coordinator now records `approvedInSession: <the head they approved>`, and it counts while that head is current — a push after the human spoke invalidates it, which is the same staleness rule the scan channel gets. Both directions are asserted, because satisfying one alone reintroduces the other.

**Returning is not finishing.** A verdict fold that returns a `blocker` escalated rather than completed, so counting it as folded deleted the row's only copy of the claim, evidence and owed thread reply *and* parked the row — leaving nothing to apply once the human answered.

**An unreported review round is charged one.** `specReviewRoundsSpent` is optional, so an omission credited zero would consume each feedback batch, advance the cursor, and never reach the budget: an unbounded review sequence, the exact failure the budget exists to prevent. A worker that genuinely spent none still says `0` explicitly and is believed, so the canonical zero-cost factual batch survives.

**A multi-PR issue survives the epic wake — all of it.** `WORKER_SCHEMA` had one `implPr` and `additionalProperties: false`, so a worker had nowhere to return the DAG `issue-multi-pr` produced. Adding `subPrs` fixed the handles and left the other half broken: `assembledGoal` is the assemble phase's position in its own multi-wake state machine, so losing it re-ran the end-to-end goal and filed a duplicate gap issue every wake. Both are carried now, and the refresh scout is *given* the sub-PRs to read — told only "Impl PR: none", it had nothing to look at, so a subscribed sub-PR event woke the coordinator and the row still reported no activity: stuck in PR_FEEDBACK for good.

**`DONE` requires merge evidence, on both kinds of row.** A single-PR row reporting `phase: 'DONE'` with `merged` false finished the row, so the coordinator would mirror Done in Linear and could wrap the epic before the human merged anything. The multi-PR half had the mirror image: it derived DONE from `assembledGoal.passed` alone, so a worker reporting a pass while a slice was still open finished the issue, stopped all DAG dispatch, and let the epic wrap with PRs unmerged. Each condition is necessary and neither is sufficient — every slice merged *and* the goal proven. Fixing one half and not the other is how this took two rounds.

**A contract the schema refuses is a stall.** `epic-agent`'s documented return format tells it to report open questions when a cross-cutting decision needs a human — and `EPIC_FOLD_SCHEMA`'s `additionalProperties: false` rejected exactly that, so a fold following its own contract produced a response the harness discarded as `null`. The wake read that as a dead agent, retried forever, and the question reached nobody. There is a channel now, carried durably and re-surfaced each wake like `unsettled`, and the subagent's field name matches the schema so the two can't disagree again.

**"Non-empty" is not "complete", and order is not identity.** This one took three passes, each fixing the previous fix's blind spot. The first guard rejected a multi-PR scan that omitted `subPrStates` entirely and passed one reporting a single handle out of three, so if the omitted handle was the one that merged, the merge was lost while the batch was consumed. Requiring one correctly-attributed entry per handle closed that — and left the two readers of the same array disagreeing: the cursor guard checked *set coverage* while the fold bound *positionally*, so a scan answering every requested handle in a different order passed the guard and then had every entry discarded, losing exactly the merge it had reported. A scout that consistently orders that way parked the row for good.

The fix separates the two questions the callers are actually asking. **Attributable** — every entry labelled, no handle twice, no id outside the dispatched set — is what the *fold* needs, and it is a strictly better rule than position: the set of handles a response can touch is still exactly the set that was dispatched, so "identity comes from the dispatch" holds, while a reorder is no longer mistaken for a lie. **Complete** — every handle actually answered — is what the *cursor* needs, since an unanswered handle may be the one that merged. A partial-but-attributable scan is therefore folded (a merge only ever advances, so this can lose nothing) without being allowed to consume the activity. Position was only ever a proxy for attributability, and a worse one.

**An observed merge finishes a single-PR row, in both directions.** `DONE` without merge evidence was corrected to `PR_FEEDBACK`; the inverse was not, and it is the honest report of a scout looking at a row whose PR landed between wakes. `PR_FEEDBACK` with `merged: true` then matched nothing at all — no events, no CI failure, no DAG, so no work; and `readyToMerge` is false on an already-merged PR, so no gate either. The row idled permanently with nothing to explain it and the epic could never satisfy its wrap condition. The rule is "the merge decides", and a rule applied in one direction is a rule half-applied — the fourth instance of that shape in this work.

**A scan that omits `repairMerged` didn't look.** It is the only observation that can set `fixMerged`, and while that stays false the assemble machine waits in `AWAITING_FIX` — so a scan reporting activity while omitting the field consumed the announcement of a merge nobody checked for, and the row waited on an event that had already happened. It goes through the same `cursorUsable` gate as a missing timestamp and an incomplete handle set, and the row records whether the scan *answered* separately from what it answered, because `false` and "didn't look" have opposite meanings here and one boolean can't carry both.

**An epic approval that couldn't be confirmed stays unconfirmed.** A live scan with no head correctly held the current wake — and left `approved: true` persisted beside the old head, so the *next* wake's dead-scout fallback read that durable approval as good and released every child worker against an objective the last real observation could not confirm was current. Holding a wake is only a hold if it survives into the next one. `epic.headUnconfirmed` carries it, and any scan returning a head clears it, so an epic can't be locked out either.

**An implement dispatch keeps the spec PR open while a settlement is live.** Approval chains into implementation and the worker is told to close the spec PR, but a queued POC on a load-bearing claim means a late `REFUTED` verdict has to be folded into that artifact and replied to on its thread. The dispatch now names the in-flight claim and defers only the cleanup.

**Every partial report merges into the durable state — `assembledGoal` as well as `subPrs`.** The schema permits a partial object, so a worker reporting only `{ fixPr: 42 }` dropped the failure, the gap issue, the evidence and the blocker along with it, and the next wake re-ran the goal before an unmerged repair or restarted the gap cycle. Same rule, both fields, found one round apart.

**An incomplete observation consumes nothing.** A multi-PR scan that omits `subPrStates` didn't look at the handles — the prompt asks for one entry each — yet it could still report `newPrEvents` and have the feedback worker eat that activity, so a just-merged slice was never persisted and the dependent parked with no event coming. It now fails closed through the same `cursorUsable` gate as a missing timestamp. Making the field schema-required instead broke 84 fixtures, which was the harness pointing out that the requirement would tax every single-PR scan with a meaningless `[]`.

**A headless scan doesn't erase the last confirmed head.** Refusing the in-session approval on a headless live scan was right, but spreading the scan also persisted the null — so a dead scout on the *next* wake read "no observed head" as compatible with any approved SHA and dispatched implementation anyway. The last head actually observed is better evidence than none.

**A malformed PR plan builds nothing, not merely one node less.** `byId` is the map every node is classified against, so an invalid row poisons its descendants: an invalid prerequisite persisted as `merged` reads as satisfied and its pending dependent gets dispatched from `origin/main` in the very wake the plan is reported broken. Detection that lets the rest of the set run isn't prevention.

**Held work has a continuation channel.** The one-wake fold hold only means "one wake" if something tells the coordinator to run another; without it the turn ended and the next wake depended on unrelated PR activity — a wait with no path out, which is exactly what the hold was introduced to avoid. `heldForFold` comes back in the return and the skill says what it means.

**A worker's sub-PR table is merged into the durable one, never substituted for it.** A worker returns what it changed, and a compact row omitting `dependsOn` left the slice reading as dependency-free — built straight onto `origin/main` while its prerequisite was still unmerged, the DAG violated by a field nobody meant to change. Structural edges come from the carried row; only what the worker actually reported is applied.

**The unreachable owned-goal shortcut is removed rather than wired up.** `assembledGoal.ownedBy` was meant to let a designated integrating slice's recorded verdict stand instead of re-running the goal, and `issue-lifecycle` documented that behaviour — but nothing ever set the field: no coordinator produced it, no contract carried it. The one round it was exercised (in tests only) it turned out to accept a verdict recorded *before* a repair merged. Saving one real-path run is not worth a stale proof, so the branch and the sentence describing it are gone.

**`blockedBy` is schema-required, and the gating invariant now reaches nested schemas.** The code reads a present Linear row as authoritative — deliberately, so a merged prerequisite actually un-blocks its dependent — which meant an omitted `blockedBy` read as "no blockers" and admitted an issue alongside the prerequisite it was waiting on. The field sat inside `issues.items`, where the "every gating field is required" invariant couldn't see it; it scans every `required` list in a schema now, not just the outermost. The fixture that should have caught this asserted the omission *meant* none, in a comment saying so — the third time in this work a fixture encoded the defect it was meant to exclude.

**The next sibling blocker is lifted in the same pass that clears the answered one.** Clearing the named slice and its marker without re-lifting left a window: a wake with no DAG work runs no worker, so nothing surfaced the next sibling, and the following refresh — seeing neither a blocker nor a marker — fell back to "clear the first" and released a decision nobody had answered. Now the invariant "nested blockers imply a row-level marker" holds at every wake boundary rather than only on wakes that happen to run a worker, and the fallback is gone. A row persisted before the marker existed costs one extra ask rather than stalling.

**The assembled goal runs against the merged tree, not an inherited checkout.** A worktree worker starts from the coordinator's checkout, which the branching contract says may lag `origin/main` — so the goal whose entire purpose is proof could run against a tree missing one of the merges it exists to verify, and record a PASS or FAIL about code that isn't there. It fetches and checks out fresh `origin/main` first.

**An `INCONCLUSIVE` verdict keeps its evidence, not just its claim.** The row-level conversion to a blocker kept the claim text and dropped the structured record, while the coordinator is told to put the question to the user *with* what the POC found — and the thread handle is where their answer gets posted. Rows now carry the same `unsettled` shape the epic already did.

**A phase name never carries the spec-approval gate.** `NEEDS_IMPLEMENTATION` asserts "the spec was approved", but only `specApproved` establishes it and the schema validates the two independently — so a mis-derived phase implemented a spec no human approved. Refusing to *dispatch* turned out to be half a fix: the row then sat at a phase whose gate filter didn't match, surfacing nothing — a silent stall in place of the bypass. The phase is corrected instead: with a spec PR it is awaiting approval and gets that gate; without one there is no spec to approve.

**A parked row is never merge-gated.** `pendingAction` parks on an unresolved decision or an open prerequisite, but the merge gate filtered only terminal Linear state, so the human was told to merge work whose blocker they hadn't answered or whose dependency hadn't landed. Parking has to mean parked everywhere.

**Sub-PR feedback is handled before the DAG step.** `issue-multi-pr` builds, rebases and assembles; it has no notion of an ordinary open PR's review comments. A multi-PR row dispatched for `pr-feedback` and pointed straight at the DAG reported "waiting", and the cursor then consumed the batch unfixed.

**An owned assembled goal is re-run once its repair merges.** The "a designated sub-PR already ran it, confirm the record" shortcut stayed selected after a repair landed, so the repaired result was never exercised — an old failure could start a second repair cycle, or an old pass could finish an issue whose goal was never proven against the fix. Both log lines fired together, which is the contradiction made visible.

**Work that authors against the objective is held for one wake while the objective folds** — and this reverses a call made earlier in review. The stronger form (hold child work until the objective is *re-approved*) was declined twice, correctly: folding is how an objective becomes approvable, so gating it on approval deadlocks the gate it waits for. But the narrow version has no such problem. A `spec` or `implement` dispatched in the same wake as a fold starts from direction that wake is revising, so those two actions — and only those — are deferred one wake, with their approvals intact, and the fold takes priority so the wait is short. Everything else still runs. The fold takes its slot *inside* the cap by displacing one advance — an `epic-agent` fold is a full worktree, and the cap is documented as shared across workers, folds and settlements.

**A nested blocker is lifted to the row, so the resolution rule can't destroy it.** Making the nested sub-PR blocker follow the row-level one closed a stall and opened its inverse: `subPrs[].blocker` is the nested workflow's native field, so a worker can report a fresh escalation without also setting the row-level mirror — and the resolution rule reads an absent row-level blocker as "the human answered" and erases it. Deriving the row-level field from the nested ones makes the pair consistent by construction: a fresh escalation always arrives with its mirror, so the resolution rule only ever fires on a decision that was actually surfaced. That fix then over-cleared: two sub-PR workers can escalate different decisions in one wake and the row surfaces the first, so answering it cleared the sibling's unanswered blocker too. The row records **which** slice its answer releases, and the next wake lifts the next one — a queue, which terminates.

**A malformed PR plan comes back as a blocker.** `issue-multi-pr` refuses a duplicate id, a dependency cycle and an unknown dependency — correctly, since only a human can fix the plan — but under an epic that refusal reached the coordinator as neither work, blocker, nor gate, so the row sat in `PR_FEEDBACK` forever. It now returns through the human-decision channel that already exists rather than a new one.

**An open dependency is only a stackable base with BOTH handles.** An `open` dep with no branch produced `base: undefined`, and the build prompt then told its worker to base the slice on nothing — starting from the inherited checkout rather than its prerequisite. Without a PR number it is equally unusable for a different reason: it can never be reviewed or merged, and a stacked dependent only rebases once its deps have *merged*, so stacking on it strands both slices with no remaining action. That is a wrong implementation or a stall, not a delay, which is the same trade the mixed-merged-and-open rule already makes.

**Merge readiness cannot outlive the worker that may have invalidated it.** Per-handle readiness is observed at refresh time; a `pr-feedback` worker on the same row then pushes commits, which invalidates the approval and re-runs the checks that observation rested on. Surfacing it would tell the human to merge a head nobody has verified, so any worker that ran on a row voids it and the next wake's scan re-establishes it. The mirror of that fix was also needed: a repair PR **awaiting its human merge** is a wait, not work — treating it as work spent a worktree worker every wake to be told to wait, *and* voided the readiness the repair's own merge gate depends on, so the human was never asked to merge the thing the DAG was waiting for.

**Work is withheld when the cursor can't move, on rows as well as the epic.** The epic learned to hold a fold when activity arrives with no timestamp; the rows only preserved the cursor while still dispatching and folding, so the same batch was re-applied indefinitely. Both go through one `cursorUsable()` now — and the epic's *converged note routing* needed the same guard, since it advances no cursor of its own and was re-reading and re-routing the same comments every wake. A CI failure is deliberately exempt — it isn't comment activity and needs no timestamp.

**`multiPrPending` is required, because "answer only when it's true" is a field with no clearing path.** Keying it to the `implement` action had two holes at once: an implement worker that *omitted* the field cleared a carried `true`, stranding cap-deferred slices nothing external will wake, and a `pr-feedback` worker that did run the DAG and did report pending work was ignored. Switching to "whoever answers is believed" fixed both and left a third: the prompt asked only for the true case, so nothing ever reported the false. Once set it was set forever, `multiPrHasWork` made the row actionable on every wake, and with a cap of 2 and a stable row order that starves every other issue in the epic indefinitely. Required in the schema there is no omission left to interpret — and the prompt hands each worker the carried value with instructions to echo it when it ran no DAG step, so always-answer costs no information. This one can only be pinned in the contract: once the field is required, the two readings of the fold rule are provably identical, so no behavioural check can tell them apart.

**A resolved blocker's answer travels to the worker that needs it.** The coordinator was told to clear `blocker` once the human decided — and nowhere to record *what* they decided. The next worker is a fresh sub-agent in a fresh worktree that never saw the escalation and cannot read the session, so clearing alone released it to walk back to the identical architectural fork, where its only options were to escalate the same question again (forever) or to invent the answer the gate existed to supply. The decision is recorded as `blockerResolution`, handed to the next dispatch, and consumed there — a one-shot handoff, since a worker told an already-implemented decision is fresh would re-litigate it. A dispatch that *died* consumes nothing, the same rule the cursor gets, so an infrastructure failure can't discard the human's answer.

**A channel wired at one end, three more times — and the fix itself landed one hop short.** Naming the shape did not exhaust it. The very next pass found the resolution reaching only the *outer* issue-worker, which delegates to `issue-multi-pr`, whose build and fix workers are freshly spawned and are the ones that actually escalated — so the answer stopped one agent above the fork it was meant to resolve, which is the same stall as having no channel. It is forwarded through the workflow args now, and aimed at the slice that asked (derived from the lift's `blockerFor`) rather than broadcast to every worker in the ready set, since a worker handed a sibling's decision will reasonably apply it.

At the epic altitude the write end was missing entirely. `openQuestions` and `unsettled` were both durable and re-surfaced every wake, and their **answer** had no field, no prompt carrying it to `epic-agent`, and nothing that triggered a fold — so unless unrelated review activity happened to arrive, the epic-spec was never updated and every child issue kept building against the unresolved version. The coordinator being told to drop the question on the user's answer completed the loss: decision made, spec unchanged, no trace it was ever asked. `epic.answers` is modelled on `verdicts`, which is the same shape one step earlier — it triggers a fold on its own, is exempt from the review budget (an answer to a question we asked is not another opinion), and is consumed only when a fold *returned*. The wake clears the question, not the coordinator, because the coordinator cannot know the fold succeeded.

**The wake decides when to continue and when to wrap — and the first version of those two predicates enumerated state, which is the drift they exist to remove.** That cost six defects in one round: a verdict parked behind a blocker asked for an immediate wake the dispatcher would refuse (a loop with no exit), a verdict on a *cancelled* row that nothing can ever apply held the epic short of wrap permanently, `multiPrPending` and a fold the cap squeezed out were missed, a carried *epic* verdict was invisible to wrap, and reading any dispatchable row as runnable spun on `ciFailed` — which a worker handling it does not clear, because only a fresh scan can.

Both are now derived. `mayWrap` asks whether anything is *dispatchable* (`pendingAction`) and whether anything is *owed to the human* (the surfaced blockers list itself, so "nothing left to show" and "safe to close" cannot disagree), with cancelled rows excluded because no action can ever clear their leftovers. `moreWorkNow` pairs dispatchability with the three triggers that need no external event — DAG work a nested step reported, a verdict still owed a fold, a queued human answer. CI re-running and a new review are external by nature, and waiting for them is the point.

**The cross-spec hold and the cross-spec ask are different conditions.** The first version conflated them, keying the hold on "every spec approved" — so the *first* approved spec was built while its siblings were still being written, and by the time the set could be checked the code already existed. That is the order the gate exists to prevent. The hold is the whole rule (a multi-issue epic parks every approved row until the pass clears); the ask is narrower (the pass only runs once every spec is open and individually approved, because aligning a good spec to an unvalidated one spreads the flaw). "Not askable yet" is not "go ahead".

**`crossSpecCleared` is documented in the args and persistence contract.** A field the script *requires* and cannot itself set, absent from the skill, is a permanent hold for any coordinator following the procedure — the same read-but-cannot-write class the invariant already guards, which is what caught it. Its invalidation is documented too: the set that was checked is not the set you have once a child is discovered or a spec reopens.

**An in-session spec approval fails closed on a dead scout**, matching the epic gate. Comparing against the carried head accepted an approval for a head a push had already superseded. The approval is still persisted — declining to *act* on it for one wake is not losing it.

**The issue scout collapses each human's reviews to their latest state.** The epic gate prompt has carried that rule from the start; the issue scout asked only for a current-head approved review, so a spec could read approved while another human's latest state was `CHANGES_REQUESTED`, or while the same human approved and then requested changes.

**The cross-spec coherence gate is represented in the wake.** An epic's specs are authored in isolation, so each can be locally excellent while the *set* claims the same surface twice or contradicts itself — `epic-lifecycle` runs one coherence pass over the set before any of it is built. Moving the advance decision into the script left that gate behind entirely: every spec chained from approval straight into implementation, so conflicts surfaced (if at all) after the code existed, which is the expensive half of the order the gate exists to prevent. The hold is derived from the refreshed rows (`specApproved` is scan-derived and never carried, so the incoming table cannot answer "is every spec approved"), covers *both* routes to implementation, and is surfaced as a gate because running the pass needs the user's approval first.

**A standalone multi-PR issue re-invokes until the result names an external wait.** Keying on `deferred` alone ended the turn after every internal assembly transition — a failed goal records its failure and filing the gap is immediately runnable, and with every slice PR already merged there is no PR event left to wake the session. The rule now keys on the workflow's own vocabulary for waiting (`done` · `awaitingFix` · `blockedGap` · `blocker`) rather than re-deriving its state machine, because that vocabulary cannot drift from the code that produces it.

**A failed build goes behind its siblings.** Restoring the prior status was right — the slice still needs building — but left it first in a stable order, so under a cap smaller than the ready set (`cap: 1` especially) the same failing node was picked every wake and independent slices never got a turn.

**A dead gate scout holds child work — reversing an earlier decision here.** Carrying the epic approval through a failed scan was sound while that approval was a one-time objective sign-off. Making it head-sensitive (a push invalidates it) left the fallback unsound and nobody revisited it: H1 approved, a push creates H2, the scout dies, and the stale `headUnconfirmed: false` released every child against an objective nobody approved. The approval itself is still kept — the human gave it once — but it no longer *releases* work without a live scan that can confirm the head. One wake of held work per flaky scan, against children authoring specs and PRs against an objective that may have moved.

**A scout cannot regress a row back across the gate either.** The mirror of the forward jump, and it costs duplicate work rather than a bypass: a carried `PR_FEEDBACK` row reported as `NEEDS_SPEC` while its implementation PR is open makes the next wake author a *second* spec PR for work already under review. Re-gating a row is a decision, and a scan reports facts.

**An acknowledgement describes one delivery, not the slice.** `answerApplied` was spread in only when true, so `...node` carried it forward — and a second decision on the same slice inherited the first one's acknowledgement. If that second resume then failed, the stale marker reported the new answer as landed, deleting a one-shot decision while the PR it was meant to change stayed as it was.

**The nested DAG workflow inherits the epic's cap.** Without it the nested step falls back to its own default, so one outer worker can spawn that many sub-PR worktrees beneath itself — and several outer rows multiply it, which leaves the VM-sized cap bounding nothing.

**Cancelling an issue drops its open question, out loud.** `pendingAction` already refuses to dispatch cancelled work, so a blocker left on the row could never be cleared by anything — and it kept the surfaced blockers list non-empty, holding the whole epic short of wrap while a human was asked to answer a question about work that no longer exists. Cleared where cancellation is observed, so the blockers list and `mayWrap` cannot disagree, and logged rather than dropped silently.

**An externally blocked repair gap is a wait.** The worker was told to report pending DAG work for "any remaining assemble step", but a `blockedGap` recheck waits on an open Linear relation — external by definition. Reporting it as internal work asked for an immediate wake that rechecked an unchanged relation and burned a slot in the shared cap, every wake, until someone else moved it.

**Merge gates withhold while a verdict is unfolded.** Settle runs after Advance, so a POC returning REFUTED or INCONCLUSIVE lands in the same wake a refresh may have marked the PR ready — merging then locks in an implementation whose load-bearing premise the evidence has just contradicted.

**An approval batch holds until its cursor is usable.** This is the only pass that reads spec-PR feedback, so dispatching with a cursor that cannot advance carried the batch once and rediscovered it on every later timestamp-less scan.

**A scan-derived blocker is cleared only by an actual scan.** A dead scout leaves the fresh state empty and a partial multi-PR scan can omit a handle, so "no closed handle reported" was indistinguishable from "reopened" — and clearing on that absence released the row on an observation nobody made, dispatching work against a handle that is still dead.

**The scout cannot jump the approval gate either.** The guard was applied to the worker's report, but the refresh is an independent producer of `phase`: a scan claiming `PR_FEEDBACK` with an implementation handle on a row still awaiting approval walked straight past it.

**The epic's own legacy third-round flag is dual-read**, and a CI failure now waits on unreadable *spec* activity as well as implementation activity — that channel started sharing the same cursor when late spec feedback began routing through the same worker.

**Late spec-PR feedback is routed, not merged over.** Comments can land on a retained or closed spec PR after the row has entered implementation review, and that branch reacted only to impl-PR activity and CI: with no CI failure the row could take a merge gate over an unread comment, and with one the feedback worker consumed the shared cursor and cleared *both* activity flags without ever being told to read it. It now dispatches for that feedback and hands the worker instructions to carry it as implementer notes — the same treatment the approval batch gets, since the spec is already approved.

**A reopened PR clears its closed-handle blocker.** The blocker's own text advertises reopening on GitHub as a recovery needing no answer here — and nothing cleared the blocker when the scan stopped reporting the handle closed, so the advertised path parked the row forever. That blocker is a scan *observation*, so it is tagged as one and retires with the observation, while a worker-raised escalation is untouched.

**The rebuild reset lands before dispatch.** Resetting an answered closed slice after the worker returned meant the worker was handed the still-`open` slice, so the nested workflow classified it as a `resume` and was forbidden from opening a replacement — a wasted wake before the rebuild could start. The slice a worker was handed as reset also takes *nothing* back from that worker: anything it echoes about a slice whose PR the scan just saw closed is the dead handle it read in its own input, not an observation.

**Closed-PR handling is detection, not automatic recovery.** A PR closed without merging is reported per handle and parks the row on a human decision, and the dispatched worker is told in its prompt which handle is dead. The automatic rebuild that grew around that — resetting the slice, marking the dead handle, refusing the worker's echo of it — is gone. It needed a distinction the merge boundary does not have (the handle you were *given* versus the handle you just *created*), and every guard for one side broke the other: the last one discarded the replacement PR a rebuild had legitimately opened, orphaning it and rebuilding the slice again on every wake. Detection was the stall fix and it stands; the recovery is the human's.

**A resume says whether it landed.** A resume works on an existing open PR, so success is `open → open` with no blocker — indistinguishable from failure by status alone. Inferring it meant either dropping the human's answer or re-dispatching the same resume every wake while the merge gate stayed withheld, so the slice could neither finish nor stop reapplying the decision. `answerApplied` is the nested workflow saying so, set only when a resume actually landed.

**A cross-cutting answer is queued, not swapped for the deleted question.** The epic skill told the coordinator to drop the matching `epic.unsettled` entry, which contradicted the `epic.answers` contract and removed the only durable record of the claim without triggering a fold — so the epic-spec and every child aligned to it never received the decision. The answer goes to `epic.answers`, the entry stays, and the script retires it once the fold consumes the answer. The invariant that *required* the old wording pinned the defect, and now asserts the script-side retirement instead.

**An untargeted answer reaches only the slice that asked.** A legacy single-slot `blockerResolution` carries no target, and treating it as "aimed at the issue" handed it to every ready node — so an unrelated pending slice dispatched in the same wake was told to implement another slice's architectural decision as given.

**A decision that was applied stops being advertised as unsettled.** The `unsettled` records an INCONCLUSIVE verdict leaves behind were carried unconditionally, so the top-level disclosure kept naming an already-decided claim on every later wake. They clear when an `apply-decision` worker returns — coarsely, because the row's blocker surfaced all of its unsettled claims as one question and the human answered that question, and a later INCONCLUSIVE re-populates the list.

**The closed-handle blocker has to be answerable.** A closed PR stays closed, so every later scan reports it again — and recreating the blocker on the next refresh parked the row before the human's reopen/reimplement/drop answer could reach a worker. The blocker was unresolvable by construction, which is worse than the idling it replaced. It is suppressed while an answer for it is queued.

**An answer is spent only where something observable proves delivery.** "Still pending, or still blockered" was not enough: the epic refresh clears an answered slice's nested blocker *before* dispatch, so a resume that comes back `failed` leaves the slice `open` with nothing left to preserve — each layer expected the other to be holding the blocker, and the answer was dropped with the PR unchanged and merge-eligible. Two things prove delivery: the slice merged (the decision went in with the code), or it moved `pending → open` this wake (the build that opened the PR *is* the delivery). A slice that was already open and is still open proves nothing, so its answer waits for the wake that lands it.

**A standalone multi-PR issue drains its cap-deferred slices.** `epic-lifecycle` got this rule; the standalone integration ended the turn after one step without looking at `deferred`, so with four independent slices and a cap of three the fourth waited for the heartbeat.

**A worker-added slice cannot claim `merged`, and `open` needs handles however the slice got there.** Two holes around the same guard. `merged` was unassertable only for a *carried* slice — a brand-new one had no `prev` for the transition guard to compare against, so a fabricated `merged` immediately satisfied "every slice merged" and the issue could reach DONE with a slice that never had a PR or passed the human merge gate. And the both-handles requirement ran only for new slices, which left the one transition a worker legitimately owns (`pending → open`) able to land a slice with no PR and no branch: nothing for the scout to refresh, no merge gate able to name it, no DAG action for an ordinary open node.

**The repair PR reports closure too.** The other two handles got a closed-unmerged signal a round earlier; without it on the repair handle, a closed repair left the assemble machine at `AWAITING_FIX` with nothing to dispatch and no gate to show, idling the row indefinitely.

**A worker cannot jump a row across the spec-approval gate.** The correction only applied to a row *sitting* at `NEEDS_IMPLEMENTATION` unapproved, so a worker reporting `PR_FEEDBACK` with an `implPr` straight from `NEEDS_SPEC` skipped the gate entirely and reached a merge gate with no human sign-off. It keys on the *transition* rather than on `specApproved`, deliberately: that flag is re-derived from a live scan each wake and the spec PR is closed once implementation starts, so a legitimately implementing row reports `false` forever — gating every post-spec phase on it would strand all real work at `NEEDS_SPEC`. Refusing the phase was not sufficient on its own, either: the merge gate is derived from `readyToMerge && implPr`, so it now also requires a post-spec phase, which is incoherent to lack whatever produced the handles.

**A PR closed without merging is reportable, and parks the row.** The scout reads PR metadata but could only express merged / ready / not-ready, so a closed-unmerged handle left a single-PR row idle in `PR_FEEDBACK` forever — nothing merged, no activity, no action — and a slice durably `open`, which the DAG cannot advance either. Reopening, re-implementing or dropping is a human call, so it surfaces as a blocker with the handle named.

**The Linear refresh covers carried members, not only parent children.** `orchestration.md` keeps an existing functional parent and links such a member to the epic with `relates-to`, so it is *never* in the parent→children set — and its Linear state froze at whatever was last cached. A blocked member never noticed its prerequisite merging; a cancelled one kept being dispatched.

**The repair worker bases its fix on fresh `origin/main`.** A fresh worktree starts on the lifecycle's checkout, which drifts as slices merge, so the repair PR could carry unrelated commits or omit the very merged slices whose interaction the goal is failing on. The build path already carried this instruction.

**A queued settlement drains like a deferred row.** A claim the cap queued comes back only in `settleRequests`, never in `deferred`, so the immediate-continuation rule missed it and a runnable POC waited on unrelated PR activity.

**An INCONCLUSIVE verdict is never folded as resolved.** The wake turns one into a human decision *after* the folding worker returns, but the prompt told that worker to fold every verdict and record each claim as resolved-with-evidence — so the spec and the PR thread could state a claim was settled before the human had answered the question the POC failed to settle. Settled and unsettled verdicts are now rendered separately, with the unsettled ones explicitly marked as the human's call. Both the issue and epic prompts had the same ordering.

**An answered decision outranks completion, exactly as a landed verdict does.** An INCONCLUSIVE late verdict becomes a human blocker and *leaves* `verdicts`, so once the human answered there was no verdict left for the terminal branch to match: the row parked and the epic wrapped without that answer ever reaching the completed spec or its thread. Cancelled work stays the exception — there is no artifact left to record a decision in.

**A worker cannot add a slice that is `open` with no handles.** The status transition guard only runs when there is a carried row, so a worker revising the PR plan could insert `{ id, status: "open" }` with no PR and no branch — schema-valid and permanently stuck: no DAG action for an ordinary open node, no handle for the scout to refresh, no merge gate able to name it. A new slice like that enters as `pending`, which is what the worker meant.

**The one-wake merge trigger is consumed by the worker that ran on it.** Left set, a later wake whose refresh scout died carried it forward and dispatched another worker on a merge already acted on, burning a slot in the shared cap every time the scout failed.

**A repair answer has no sub-PR row, so the per-slice rule discarded it.** Making answer-consumption per-slice meant a resolution with no matching slice was dropped — and a repair answer is aimed at `assembledGoal.fixBlocker`, which by design has no row in the table. The next wake retried the repair at the identical fork with neither the blocker nor the human's answer. A repair answer now survives while the repair is *owed* (a gap issue filed, no fix PR open) and is spent when one opens. It cannot key on comparing the returned question to the carried one: the resolution pass wipes `fixBlocker` before that comparison could run, and that wipe is precisely how the answer's arrival is recorded — so an echoed question is indistinguishable from a new one, and the conservative direction is to keep the answer for the wake that retries the repair.

**An answered decision is work for a single-PR row too.** The dispatch existed only inside the multi-PR work predicate, so a single-PR row — an `INCONCLUSIVE` POC verdict becomes a row blocker, which the human then answers — had its blocker cleared and its answer queued with nothing able to apply it. Added as a *fallback* after the phase switch rather than ahead of it, so a row with real phase work still does that work; the dispatch prompt hands every worker the answers verbatim, so nothing is lost by letting the phase win. The row-level spec-approval and merge gates now withhold while an answer is unapplied, which the per-slice sub-PR gate has done since that guard was introduced.

**The legacy third-round authorization flag is dual-read (BP-030).** `spec_review_rounds` was dual-read while `spec_level_found` — the flag that *authorizes* the conditional third round, documented under that name by the previous lifecycle instructions — was not. An epic resumed from those instructions read two rounds with no authorization, declared convergence, and silently skipped a round the rules allow.

**Cap-deferred rows drain instead of waiting for the heartbeat.** Only `heldForFold` was documented as forcing another wake, but a row the concurrency cap deferred at `NEEDS_SPEC` has no PR at all, so it cannot generate the activity that would wake the session — with a cap of 2 and three specs to write, the third sat until the heartbeat. The cap is a concurrency limit, not a scheduling delay.

**A nested blocker gets its marker whether or not the worker mirrors it to the row.** `blockerFor` — the field that tells the resolution pass which slice an answer releases — was derived only when the row-level mirror was *absent*. The schema invites both channels, and returning both is the natural thing for a worker to do, so the common case produced no marker at all: the answered slice kept its blocker, the refresh re-lifted the identical question, and the row parked with the answer never dispatched.

**Consuming the answers is per-slice, not all-or-nothing.** `issue-multi-pr` serves only its ready set, so its own cap can defer a blocked slice whose answer is already in hand — and because the outer wake clears a nested blocker *before* dispatch, that slice comes back unbuilt and unblocked, indistinguishable from one that was served unless you look at whether a build actually ran for it. Consuming the whole list on "the nested workflow reported back" discarded the deferred slice's answer and re-asked the human a question they had settled. A resolution now survives while its slice is still unbuilt or still blockered, and is spent when the slice reached `open`, when the blocker text *changed* (the answer was applied and proved insufficient, so the question is new), or when the slice is gone from the table entirely — dropped rather than restated at every future worker.

**A CI failure waits when the same scan reports activity it cannot timestamp.** CI is actionable on its own, and the dispatch for it came first — but `pr-feedback` consumes the review cursor, and an unreadable cursor cannot advance, so that dispatch re-delivered the identical comment batch every wake and the worker re-posted its replies each time. Duplicate replies on someone's PR are not recoverable by waiting; a CI fix delayed a wake is. Narrowly scoped to unreadable *comment activity*, not to cursor-usability in general — the same helper also reports unusable for an incomplete per-handle sub-PR scan, and a CI failure with nothing to re-deliver must not be held hostage to that.

**An incomplete build spends nothing either.** The "reported open but returned no PR number or branch" early return sits one branch before the rule that says a delivery which did not land spends nothing, and cleared the answered slice's blocker anyway — while the outer wake, seeing `subPrs` come back, treated that as delivery and consumed the one-shot resolution. The retry then reached the architectural fork with no answer.

**The spec-approval gate needed that same rule.** Adding the unreadable-activity guard to merge gates alone left approval — which chains *straight* into implementation — able to fire while newly reported spec-review feedback sat untriaged, demoting it to implementer notes rather than weighing whether it changes the spec.

**For a multi-PR row, the nested workflow reporting back is the receipt.** An outer worker can satisfy its schema while never successfully running `issue-multi-pr`: required fields present, `subPrs` omitted. Consuming the human's answer there left the decision spent with nothing applied, and the refresh had already cleared the nested blocker, so the unchanged PR became merge-eligible. A single-PR row is unaffected — its worker *is* the delivery, so returning at all is the receipt.

**A rebase that escalated is not a completed rebase.** `open` alone was read as success, so a rebase that stopped on a human decision cleared the stack marker. After the answer, the generic `resume` applies the decision but never retries the rebase — and the still-stacked PR could then be offered for merge and land its dependency's commits, the exact outcome the marker exists to prevent.

**A delivery that did not reach `open` spends nothing, whichever action delivered it.** Preserving the blocker on failure was restricted to `resume`, but an answered *pending* slice is delivered by a `build` — so a schema-valid `failed`/`pending` from that build cleared the blocker while the caller consumed the one-shot answer, and the next build retried the architectural fork blind. Dropping the action distinction closes the sibling case and costs nothing, since an ordinary unblocked build has no blocker to preserve.

**Parking has to mean parked everywhere — including for activity nobody can read.** A scan reporting new PR activity with no timestamp makes the wake refuse the feedback worker, because the cursor cannot advance and handling it would re-handle it every wake. The merge gate was independent of that: the human merged, the row went terminal, and the feedback that scan had just reported was never handled by anyone. All three gate kinds (row, sub-PR, repair) withhold together now, since the same unreadable scan covers every handle on the row, and the next scan with a timestamp releases them together.

**A fresh worktree does not start on the sub-PR.** The build prompt already warned that the inherited checkout drifts behind as siblings merge — but `rebase` and `resume`, the two paths that operate on an *existing* branch, said nothing about re-entering it. For a rebase that is the worse case: a reported success clears the stack marker, so a rebase that moved whatever the worktree happened to be on leaves nothing to retry.

**An answered escalation had no dispatch path.** The merge-gate guards added a round earlier were half a mechanism: the gate correctly withheld while a human decision was unapplied, the worker correctly reported no pending DAG work while waiting for the human, and *nothing dispatched the worker that applies the answer*. The row sat with no action and no gate. The guard for it has to be checked before the assemble phase's waiting states, because a decision escalated from feedback on an open repair PR is exactly the state those park — and it deliberately does not test for a still-blocked slice, since the resolution pass clears the answered slice's nested blocker before this predicate ever runs. It cannot loop: a queued answer buys exactly one dispatch, the one that spends it.

**A scan-derived spec approval needs a head to be an approval of anything.** The in-session channel had enforced head-currency from the start; the scan channel — the one with no human in the loop that wake — accepted `specApproved: true` with `headSha: null` and dispatched implementation against content nobody could show the human had seen. `headSha` is now required on that channel, which is this PR's standing rule for any field an action depends on.

**A goal proof covers the slice set it was run against.** A late verdict can add a slice to a plan whose end-to-end goal already passed, and preserving that proof marked the issue DONE the moment the new slice merged — evidence that never exercised the code it claimed to cover. Only `passed`/`evidence` are dropped; the failure, gap issue and repair handle are still true of the work done so far, and clearing those would restart the repair cycle on top of the re-run.

**Two predicates over the same state have to agree about what is finished.** `multiPrPhase` requires every slice merged *and* the goal passed before a row is DONE, but the "does this row have DAG work" predicate suppressed all work on the goal pass alone. A pass reported while a slice was still pending therefore left the row at `PR_FEEDBACK` with no action and no gate — a pending slice has no PR to generate one — parked indefinitely. The disagreement *was* the stall.

**A durable PR handle is not something a scan can destroy.** `specPr` and `implPr` are declared `['number','null']`, so a scout omitting or nulling one was schema-valid and the refresh spread wiped it: an `AWAITING_SPEC_APPROVAL` row emitting an approval gate with no PR to approve, a `PR_FEEDBACK` row losing the handle its subscription and merge gate derive from, and nothing able to recover either — no action re-derives a PR number from scratch. Null now means "did not observe", not "no longer exists" (BP-030), on both the scan and worker paths; the worker guard checked `=== undefined`, which tolerated the omission and still accepted an explicit null.

**The repair PR needed the same answer guard as the slices.** `assembledGoal.fixPr` lives outside `subPrs`, so the per-slice "is a human decision still unapplied" check never covered it — and a decision escalated from feedback on an open repair PR would clear, leave the assemble machine reporting `AWAITING_FIX` with nothing to dispatch, and invite the human to merge a repair that ignores their own answer.

**A worker that reports failure delivered nothing.** The resume fold cleared a slice's blocker whenever the worker returned without one — but `failed` and `pending` are both legal statuses, so a schema-valid failure lost the human's decision exactly as a dead worker would: the caller spends the one-shot resolution, and the next wake has neither a blocker nor a resume action while the unchanged PR stays merge-eligible. Same rule as a null result, now applied to an explicit failure.

**Never stack on a dependency whose decision is unsettled.** A pending slice whose sole dependency was open would stack on its branch even when that dependency carried a human blocker. Unanswered, the dependent encodes one side of a fork nobody has settled; answered, the dependency's resume and the dependent's build are dispatched in the *same* `parallel()` call, so the dependent bases itself on a branch being pushed to as it reads it. It waits a wake instead — the same trade the two adjacent base-selection rules already make.

**The two DONE predicates have to agree, or the pair loops.** Requiring evidence at the epic boundary without requiring it inside `issue-multi-pr` was worse than either side being wrong alone: the epic refused DONE on `{ passed: true }` and re-dispatched, the inner workflow saw the same state and returned DONE immediately without running the goal, and the two spun forever doing nothing. Both read the same rule now, and falling through to `NEEDS_GOAL` is what produces the evidence both sides are asking for. A cross-script contract is the one kind of defect neither script's own tests can see.

**A fold that returned has written.** Keying "did this wake revise the objective" on `folded` or a non-zero round count left the hole that mattered most: a verdict fold and an answer fold are explicitly *told* to report `roundsSpent: 0`, and `folded` was optional — so the two folds most certain to have edited the epic-spec could report neither signal. Since the fold is only dispatched when there is something to fold, any fold that came back wrote; withholding one wake's child gates on a fold that changed nothing costs a wake, and getting it wrong invites approval of a superseded objective, which is durable. `folded` is required now too, because it is the coordinator's only window into an artifact it deliberately never reads.

**The objective gate holds the merge, not just the ramp.** Only the spec-approval gate was conditioned on `epicApproved`; merge gates were emitted whatever the objective's state. A merge is the *terminal* step of the ramp the gate exists to hold — the one outcome it cannot undo — so it was the more consequential of the two to miss. Not a dead end: the epic-objective gate is surfaced in the same list, and approving it releases the merges on the next wake.

**A verdict that lands after the work finishes is still evidence.** A POC is non-blocking by design, so it can complete after the implementation PR merged and Linear moved to Done — and terminal-state parking came first in `pendingAction`, so that verdict was never applied: not recorded in the spec, no evidence-backed reply on its thread, and the epic wrapped as though the question had never been asked. Carried verdicts now outrank completion. *Cancelled* work is the deliberate exception — there is nothing left to fold a verdict into — and it is dropped out loud rather than silently.

**Status is an observation, and a worker is not the observer.** Workers build and push; they never merge, and only the refresh scout reads PR metadata. An unrestricted spread in `mergeSubPrs` let a worker echoing the durable table promote a slice to `merged` — which unlocks dependents onto `origin/main` and can run the assembled goal while that PR is still open — or demote an open slice to `pending`, which the next wake rebuilds from scratch. The one transition a worker owns is `pending → open`: it just opened the PR.

**A blocker is cleared by the worker that delivered the answer, never before it runs.** Clearing a *pending* slice's blocker up-front looked safe ("the build is the delivery") and lost the decision whenever that build died: the node persisted already-unblocked while the caller consumed the one-shot resolution, so the next worker reached the fork with nothing. The same held for a successful repair, which carried its answered `fixBlocker` forward and re-parked on the next wake. One rule now, for both: an answer *releases* the work, and the returning worker spends it — a dead worker mutates nothing.

**Deduping a claim must not narrow its evidence.** The settlement key is normalized prose on purpose, because independent workers phrase the same claim differently — which means two issues can collide on wording while meaning it about different load-bearing paths. Keeping only the first request's `load`/`falsify` had the POC exercise one path and the verdict fan to both: a verdict presented as evidence for something it never ran. The framings merge, the way the threads and issue targets already did, so one settlement still answers both issues honestly.

**Clearing a blocker is not delivering the answer.** Last round's fix cleared a slice's blocker as soon as the human answered, which worked for a slice still `pending` — its build had not happened, so the build *is* the delivery. For a slice whose PR was already `open` it was worse than the stall it replaced: `classify()` has no action for an ordinary open node, so nothing consumed the answer, while the slice now read as unblocked and became eligible for a merge gate. The human would have been asked to merge an implementation that ignores the decision they were asked for. A stall is recoverable; that is not. An open slice now keeps its blocker until a **`resume` worker** has applied the decision to its existing PR, and the epic withholds that slice's merge gate until then.

**A fold revises the objective the gates were computed against.** The epic gate is scanned at the top of a wake and `fold:epic` pushes to the epic branch later in it, so the approval the wake emits child gates from is already stale — the documented rule is that a push after approval re-opens the gate, and the fold *is* a push. The next wake's scan re-locks correctly, but this wake had already invited a child spec approval or a merge, and those approvals are durable: accepting one releases implementation against an objective nobody signed off. `heldForFold` does not cover it, because that defers *work*, and a wake whose children are all merely awaiting a human gate holds nothing. Child gates are withheld for the wake that revises, and the moved head is marked unconfirmed so the next wake re-scans it.

**A pass without its evidence is not a pass.** The inner `GOAL_SCHEMA` requires `evidence` — the command run and what happened — precisely because a bare boolean is not a proof, but the outer `WORKER_SCHEMA` carries `assembledGoal` as a free-form object, so `{ passed: true }` was schema-valid at the epic boundary and marked the issue DONE without the proof the whole assemble phase exists to produce. Both the DONE derivation and the has-work predicate now read one `goalPassed()`, so an evidence-free pass **re-runs the goal** rather than parking the row between two rules that disagree — the shape of an earlier fix here that turned a bypass into a stall.

**`merged` is required, and the invariant that should have said so was reading too loosely.** Completion is derived from `merged` in both directions, so a scan reporting `DONE` while omitting it was demoted to `PR_FEEDBACK` — correct — into a phase with no action, no events and no merge gate (`readyToMerge` is false on a merged PR): parked indefinitely, and the epic could never wrap. The gating invariant had `merged` in its list and passed anyway, because it joined *every* `required` list in a schema and asked whether the name appeared anywhere — and `merged` is required inside `subPrStates.items`. It evaluates the schema literals now and checks per scope: every object declaring a gating field as a property must require it *there*. Two harness bugs surfaced fixing that (array and scalar declarations swallowing the next one when extracted by brace-matching alone), which is the cost of a check that reads source as text.

**The third copy of a human decision needed the same lift as the second.** A repair worker escalates through `assembledGoal.fixBlocker`; the outer worker has no obligation to also set the row-level `blocker`, and the lift only read `subPrs[]`. So the decision was never surfaced — and the next refresh, reading an absent row blocker as "the human answered", cleared `fixBlocker` and let the repair proceed through a fork nobody decided. Lifted in `nextRow` only: adding the symmetric re-lift in the refresh deadlocked, because it restated the question at the exact moment the clearing rule was reading the answer.

**Three cache fields the prose spelled one way and the scripts read another.** `depends_on` (in `issue-spec`'s PR-plan table and `issue-lifecycle`'s cache row), `spec_review_rounds`, and `epic_review_rounds` all predate these scripts, which introduced camelCase and converted nothing. A coordinator following its own documented cache format was the caller: dependency edges read as **empty**, which `readySet` treats as "all deps merged" and builds a dependent straight onto `origin/main` beside the prerequisite it declared; and a resumed epic read its spent budget as zero and granted a fresh two rounds, the unbounded-review failure the budget exists to prevent. Both spellings are read now (BP-030) and the docs name the field the scripts use.

**A single-slot field for a queued decision drops all but the last — and the queue guarantees it.** The blocker-resolution field was added as one slot, in a file that already carries the reasoning against exactly that ("two distinct claims on one issue can settle in the same wake, and a single-slot field would drop one", on `verdicts`). The sibling-blocker queue makes it certain rather than unlikely: answering slice A clears A's nested blocker and lifts B in the same pass, which parks the row — so A's answer is never dispatched, and when the human answers B it overwrites A's. A's slice then resumes with nothing and re-asks the question the human already decided. It is a list now, each entry aimed at the slice that asked, with the aim read from the carried row *before* the lift moves the marker — after that the target is unrecoverable. The old single-slot shape is tolerated on the way in (BP-030).

**A parked row is offered no gate at all, not just no merge gate.** "Parking has to mean parked everywhere" was applied to merge gates when review found it, and the spec-approval gate kept its own filter — its comment even noted the filter was independent of parking without drawing the conclusion. So a spec-review worker that escalated an architectural fork parked the row and the coordinator still invited approval of that spec, which releases implementation: the human signs off an artifact whose open question is unanswered and whose answer changes it. Both gates go through one `awaitingHumanDecision()` now, and an invariant asserts the *shape* — a parked row emits no gate of any kind — rather than naming the two call sites, because naming call sites is how they diverged. `blockedBy` is deliberately not part of it: an open prerequisite is a sequencing constraint that doesn't change what the spec says, so approving early is harmless, and it still withholds the merge gate where landing order is the point.

**An answer is what clears the blocker it answers — in the script, not in the caller.** Under an epic, `epic-wake`'s refresh cleared the nested `subPrs[].blocker` and `assembledGoal.fixBlocker` before dispatch, so forwarding a resolution worked. Called directly from `issue-lifecycle` there was no equivalent step: `classify()` returns null for a node with a blocker and `assembleState()` returns `REPAIR_BLOCKED` on `fixBlocker`, so the answer could never reach a worker and the slice stayed parked forever — the forwarding path was dead in standalone use the moment it was added. Deriving the clearing from the answer makes it caller-independent and idempotent when the caller already did it. Third instance of "works under an epic, not standalone".

**Two readers of one array is how the scan-binding bug happened; leaving one behind is how it came back.** The durable merge fold was converted to id-binding while merge-*gate* generation stayed positional — so a scan answering every handle in its own order folded correctly and then produced no gate at all: the green slice was never offered for merge, and a scout that consistently orders that way parks the DAG for good. Both readers go through `subPrScanBinding` now.

**`spec-review` authors against the objective too.** The one-wake fold hold covered `spec` and `implement` because the set was built from "creates a spec" rather than "writes against the objective". Folding review feedback into an existing spec is authoring, and it is the expensive one to miss: the worker is aligned to the pre-fold head and **spends a review round** against direction the fold may be replacing, and a round is not refundable. Deferring it is safe in the way the other two are — the epic fold doesn't wait on a child spec review, so nothing deadlocks, and the row keeps its cursor so the batch is re-derived rather than consumed.

That defect has a shape worth naming, because it is the one this work has hit most: **a channel wired at one end only.** `openQuestions` was it (a documented return the schema rejected), the sub-PR merge gate was it (a handle nothing reported), and this was it in the write direction. So the parked-field invariant grew a mirror: every field the script *reads* but cannot itself write must be one the skill tells the coordinator to write. A field with only one end doesn't fail loudly — it silently drops whatever was meant to travel on it.

**A sub-PR's `status` is enum-constrained, and the invariant now covers the class rather than the instance.** A free-form `"done"` was schema-valid, got persisted, and then produced no build, rebase, merge or assemble action — a slice stalled exactly as a free-form `phase` stalled a row. The enum invariant asserts *every* persisted field a state machine switches on, in both scripts, because naming the call sites is how the first version missed this one.

**A nested sub-PR `blocker` follows the row-level resolution too** — the third copy of the same human decision, after the row and `assembledGoal.fixBlocker`. `classify()` refuses to dispatch a slice while its own blocker is set, and the documented resolution path clears only the row-level field, so the slice was parked permanently after the user had already answered.

**A stacked sub-PR is not offered for merge.** A green dependent whose `stackedOn` still names an unmerged prerequisite has that branch as its base, so merging it lands the slice into the prerequisite (or makes the prerequisite's PR carry both), destroying the isolation the DAG exists for and pre-empting the rebase `classify` still has to schedule. The per-sub-PR merge gate was added without this check.

**A worker transition is refused without its durable handle.** `phase` is required but a schema cannot make `specPr`/`implPr` conditionally required, so a spec worker could report `AWAITING_SPEC_APPROVAL` with no spec PR — an approval gate with nothing to open — and an implement could report `PR_FEEDBACK` with no impl PR, leaving every later refresh scanning "Impl PR: none" and that PR's reviews, CI and subscription invisible. Keeping the old phase makes the next wake retry the transition; accepting it strands the issue behind a handle that will never arrive. A multi-PR row is the deliberate exception, since its handles are the sub-PR table.

**Guards that existed on one side of the epic/row split and not the other** (four separate instances across these rounds, each fixed once the sibling was found). A blocked review worker no longer charges its round — the cursor already held for it, and charging anyway turned one round into two so the retained batch read as *converged* once the human answered, silently eating the work the budget exists to protect. A live gate scan with no `headSha` now holds rather than falling back to the carried approval, because workers align to that SHA and a partial observation must not release an epic even though an infrastructure failure must not re-lock one. And epic activity reported with a null timestamp is neither folded nor charged, since the cursor cannot advance past it and the batch would be rediscovered every wake until the budget converged.

**A multi-PR row's phase is derived, never reported.** Both a scout and a worker will reasonably call the last sub-PR merge "done" — and it isn't, because the merges are exactly what the assembled end-to-end goal does *not* satisfy, so accepting either finished the issue without ever proving it. `PR_FEEDBACK` was the opposite failure: with no newer comment nothing dispatched, so the DAG stalled at the moment a merge unblocked its next slice. The phase is now derived from `subPrs` + `assembledGoal` and overrides **both** sources, because deriving it in one of the two places it can be set is deriving it nowhere. A merge and a worker-reported `multiPrPending` (cap-deferred work that no external event will ever wake) are what dispatch the next step; a row whose slices are all open and waiting on a human merge is a genuine wait and dispatches nothing.

**The worker is handed the assemble state, not just asked to return it.** It runs in an isolated worktree with no access to `.orchestration/`, so state it isn't given does not exist for it: given only `subPrs`, a resumed issue re-ran the end-to-end goal and filed a second repair for a gap already tracked.

**The gap re-check has its own schema.** It reused `GAP_SCHEMA`, whose `required` includes `issueFiled`, while its prompt asks for readiness and says to change nothing — so the compliant `{ ready: true }` answer was rejected by the validating hook, came back as `null`, read as "the scout died", and left the repair re-checking `GAP_BLOCKED` forever. A prompt and a schema that disagree is a stall, and the harness fixture had been sharing the filing shape, which is what hid it.

**A merge gate is emitted per HANDLE, not per issue.** A multi-PR row has no single `implPr` — its handles are the sub-PR table — so one aggregate gate per row carried `pr: null`, which the coordinator cannot surface: the DAG stopped dead at its first merge-ready slice. The refresh scout now reports per-sub-PR state, and each green sub-PR gets its own gate naming which slice it is. The assembled-goal **repair PR** gets one too — it lives outside `subPrs`, so it was invisible to both the gate and the refresh, and nothing could ever set `fixMerged`: the DAG sat in `AWAITING_FIX` forever, never re-running the goal it still had to prove. Per-handle readiness is an observation, not durable state, so it never survives a wake — a carried `true` would keep asking for a merge the human already did.

**`assembledGoal.fixBlocker` is derived from the row's `blocker`, not stored twice.** It is duplicated by design (it is `issue-multi-pr`'s own durable field when that script runs standalone, with no epic row to mirror), but the epic coordinator's documented resolution path clears only the row-level copy — so the nested one re-derived `REPAIR_BLOCKED` forever, a stall behind a field nobody was told to clear. Under an epic the row-level blocker is now the single point of human resolution and the nested copy follows it.

**Escalating is not consuming, for review batches as well as verdicts.** A `spec-review` or `pr-feedback` worker that returns a `blocker` didn't finish reading its batch, but the cursor advanced and the flags cleared — so once the human answered and the coordinator cleared the blocker, no pending event remained and the feedback (with the work waiting on that decision) was stranded. Same rule, one predicate, both places.

**An approving review can arrive in the same batch as fresh spec feedback.** Approval still wins — never hold an approved issue — but the row is about to become PR_FEEDBACK, whose machine never looks at spec-PR activity again, so that dispatch is the only pass that can ever see the batch. It now carries the feedback as implementer notes on the way through (what the convergence rule does with remaining open threads anyway) and consumes it. Which actions read a review batch is a single `consumesReviewActivity()` the cursor invariant *loads* rather than restates, because that rule just grew its first exception and an invariant holding a private copy stops testing the code the moment the code moves.

**Child spec gates are withheld while the objective gate is closed.** They were emitted alongside it despite the comment claiming the objective was the only movable gate: a human would be approving specs aligned to an objective mid-revision, and once it was re-approved those stale child approvals released implementation with no second alignment gate. `allocate()` already holds the issues, so a gate the coordinator can't act on was a trap rather than information.

**A duplicate sub-PR id is refused before anything is scheduled**, alongside the unknown-dependency and cycle cases: the id map silently keeps the last of the pair while the loop still visits both rows, so two workers would build and push the same branch concurrently. And a failed assembled goal now keeps its `evidence` — schema-required precisely because it carries the command and the observed result — and hands it to the gap and repair workers, who are the ones that have to reproduce the failure.

**No agent-reported identifier decides which row a result lands on.** `issueId` is a free-form string in every scout and worker schema, so keying a map on the reported value let one agent's response land on a sibling row — carrying an approval that belonged to a different issue, which is the one gate that must never be bypassable. Results are bound by dispatch position instead (`parallel` preserves input order), and a mismatch is discarded rather than reassigned: a result that can't be attributed is a result that didn't happen. Review found this in the refresh scan; the same shape was also in the worker map and in settle-request attribution, where it would fan a POC verdict to an issue that never argued the claim — and, a round later, in `issue-multi-pr`'s build results, where it applied one sub-PR's branch and status to another while the real one stayed pending and got rebuilt. The same rule covers a POC's reported `claim`: a paraphrase would replace the canonical text while the request was consumed, so the verdict got folded onto its threads under a claim nobody argued. An invariant drives a whole wake with every agent lying about its identity and requires that no gating field and no handle can move between rows.

**An `INCONCLUSIVE` verdict is a decision the human owes, so it lives in a field that can't re-dispatch work.** It settles nothing — `orchestration.md` hands the question back — but it also can't stay in `verdicts`, because that list outranks every phase: a verdict no fold can consume dispatched a folding worker every wake, forever. On an issue row it converts to `blocker` (already the durable human-decision field: parks the row, surfaces in `blockers`, cleared by the coordinator); on the epic it becomes `epic.unsettled`, re-surfaced in `blockers` each wake rather than shown once and forgotten. The previous code had both halves of the bug in opposite directions — the epic retained it and looped, the issue path dropped it silently.

**A row or sub-PR carrying an unresolved `blocker` is parked**, in both scripts. A worker that escalated a decision is waiting on a human, so re-dispatching it on the next unrelated event would either retry the dead end or push the worker to invent the answer at the fork it was told to escalate. The coordinator clears the field when it records the resolution — and the skill says so, because a `blocker` left set stalls the issue for good.

**A step with nothing runnable names what it is waiting on.** `issue-lifecycle` re-invokes `issue-multi-pr` until a result names an external wait, and the return covering the state a multi-PR issue spends most of its life in — every slice built, every PR open, nothing left but merges the human owns — named none, so a standalone run re-invoked forever on an identical result. It now returns `awaiting`, separating a merge wait from an escalated decision from a malformed plan (which waits on a human editing the table, not on any event), and only on the path where nothing ran: a step that dispatched must never name a wait, or the slices its cap deferred are stranded with no PR to wake them. An invariant checks both ends of that vocabulary — a wait the skill stops on that the script never emits ends the turn on a condition that cannot arrive.

**The cross-spec coherence pass is handed the same set it was asked about.** The gate's issue list was filtered on an observable spec approval, which a sibling already implementing or done does not have (its spec PR is closed) — so a re-run triggered by a newly discovered child reviewed the newcomer against nothing and reported coherence it never checked. Both the hold and the ask are now derived from one definition of the set, which excludes cancelled work (its spec is dead, not a live conflict) and work that no spec can be written for yet: an issue with an open `blockedBy` is admitted to nothing, so waiting for its spec to be approved was a closed loop — B blocked by A, A held for the pass, the pass waiting on B — that no event could break. A blocked issue that already *has* a spec stays in the set. And a single spec is not a set, so an epic whose siblings are all cancelled or blocked is not held for a pass that could never be asked for. Its clearance is the coordinator's and now documented as landed-and-re-approved: routing an alignment as a PR comment leaves the target spec's existing approval intact, so clearing the hold there builds the conflict it just found.

**An answer whose fork can't be identified is delivered to nobody.** An untargeted resolution — the legacy single-slot shape, or a `{ answer }` with no `for` — was resolved to the sole blocked slice, which fixed the common case and left the ambiguous one delivering to everybody: with two slices blocked, both were resumed to apply one human's choice to two different forks, and with none blocked the answer was pasted into every build in the wake. The repair's own fork counts as a target too, so an answer that could be for either releases neither. The cost is one more ask with its target named; the cost of guessing is an implementation committed to a decision nobody made, on a PR that then becomes merge-eligible.

**A delivery acknowledgement describes one delivery on both return paths.** `answerApplied` was set explicitly where a slice was dispatched, and carried verbatim where it wasn't — so a slice that applied decision A kept reporting `true` on every later pass that didn't dispatch it. When decision B arrived and the cap spent its slot elsewhere, the caller read the stale flag as proof B had landed, dropped B's one-shot resolution, and offered the unchanged PR for merge.

**A rebuild the human authorized is set up where the rebuild actually happens.** Detection of a closed-unmerged handle is all the wake does — the automatic rebuild was removed after four rounds of defects — and the prompt told the worker to open a replacement PR while the same prompt ordered it to advance the DAG with `issue-multi-pr`, which reads the still-`open` dead handle as a slice to *resume* and forbids replacing it. Two contradictory orders, and the reachable outcome was the worse one: the decision spent, nothing rebuilt, the same question put to the human on the next wake. The worker is now told to hand that slice over as `pending` with its dead handles omitted, and for a closed *repair* PR to clear `fixPr` so the repair re-opens against the gap already filed.

Also failing closed: a sub-PR declaring an unknown dependency is refused rather than treated as dependency-free; a node with a mix of merged and open dependencies waits rather than stacking on a base that may predate the merged one; a dead epic-gate scout reads as "not approved"; a carried `blockedBy` survives a failed Linear refresh; and a repair already in flight — by PR *or* by filed issue — blocks re-running a failed assembled goal.

Verification: `node .agents/workflows/verify.mjs` runs both scripts with stubbed `agent`/`parallel`/`pipeline`/`log`/`phase` hooks and asserts 248 behaviours — the budget edge cases (a zero-round batch consuming nothing, the third round authorized once and a fourth refused), the epic gate dispatching nothing, the cap deferring by name, one claim settling once and fanning to both issues, and the DAG's base/rebase/assembled-goal decisions. No agents, network, or git access.

**Every schema field that gates an action is REQUIRED, not optional — and an invariant enforces it.** Six separate defects across three rounds came from the same shape: an optional boolean whose omission was defaulted the permissive way. `specApproved` was the worst — a live scan reporting a pushed head without restating approval let a carried `true` survive, implementing on a head the human never approved, which is the one gate that must never be bypassable. It is now required in the schema *and* taken only from a live scan. Likewise `issue-manager`'s `ready` verdict, and the epic's `aboveBarFound` third-round authorization.

**Eight of those checks assert invariants over the input space rather than sampling it**, because rounds of example-based review kept finding the same shape of defect: a state combination nobody wrote a case for, which stalls the lifecycle or silently consumes work. They assert that no assemble state is a dead end (a waiting state must wait on a handle a human can act on), that a parked row is never dispatched whatever else is true of it, that the activity cursor never advances past unconsumed activity, that a dead worker mutates nothing but its cursor, that no agent-reported id can move a result onto another row, that every phase a row can hold is one the state machine handles, and that every field the epic wake parks on is one the skill tells the coordinator to clear — a field nobody is told to clear is a permanent stall however correct the script reads. The harness loads each script's `Rules (pure …)` region directly, so this needs no test hooks in the scripts. It also **validates every stub response against that agent's schema** — the real hook returns only validated objects, so a fixture the schema would reject describes a branch that cannot happen. Adding that check failed 11 previously-green tests whose fixtures omitted fields made required in later rounds; they assert something real now. Every one was mutation-tested — reintroducing the exact bugs review found makes them fail. Five didn't at first, across the rounds — every one found by mutation-testing the new check rather than by trusting a green count. The id-binding invariant caught the scout instance but not the worker one, because its row shapes parked without dispatching any worker at all. And the satisfiability invariant read each schema through a fixed byte window, so a nested sub-schema pushed a later property past the cut and it reported an unsatisfiable schema that was fine — it brace-matches the declaration now. An invariant that passes for the wrong reason is the same failure as a fixture the schema would reject, so it is now pinned to a distinguishable per-row handle as well as the gates.
