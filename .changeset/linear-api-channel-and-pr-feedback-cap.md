Internal (skills/process): two changes to how the development skills talk to Linear and how long they'll argue with a PR.

**Linear goes through the API when the key is there.** `CLAUDE.md` gains a short "Linear access" section that makes the channel a single decision made once per task: if `LINEAR_API_KEY` is in the env, use the Linear GraphQL API directly and do not use a Linear MCP server even when one is connected; otherwise fall back to MCP as before. It carries the endpoint and the one non-obvious detail (the key goes in a bare `Authorization` header, no `Bearer` prefix) and leaves the operation-by-operation translation to the agent — it's always-loaded context, so it stays short. The skills that previously said "use the Linear MCP tools" now point at that section instead of naming a channel — `issue-spec`, `issue-lifecycle`, `linear-triage`, `plan-day`, `adhoc-quick-fix`, `second-look`, `distill-lessons`. Beyond dropping the MCP round-trips, this is what makes the Linear-touching skills work in headless and cron runs, where an interactively-authenticated MCP server isn't present.

**The PR-feedback loop is capped at twelve rounds.** A spec PR has been bounded by the convergence rule for a while; the implementation PR was the loop still running unbounded. Several reviewers comment on a diff, a worker fixes and replies, the fixes draw fresh comments, and no individual round looks wrong — nothing in the loop notices that round nine is re-litigating round three, or that the approach rather than the lines is the problem. So `orchestration.md` gains "PR feedback: the round cap" as the canonical rule: twelve auto-handled rounds per issue, then stop handling feedback, post one pause comment on the PR saying what's still open, and ask the human what to do. Twelve is deliberately well past a normal review — it's a loop detector, not a convergence budget, since a code PR's threads really do gate its merge and there's no "carry the rest as notes" exit.

The rule lands in three places. `issue-implement` Step 10 counts and reports its rounds and checks the cap at 10.7. `issue-lifecycle` holds `prFeedbackRounds` in the handle cache and owns the ask. `epic-wake`'s `atPrFeedbackCap()` is the executable copy, with the cap's blocker *derived* from the counter rather than stored — so resetting the counter, which is what the coordinator does when it records the human's answer, is the single act that both un-parks the row and clears the question. Because that park writes no `blocker` field, it joins the shared `awaitingHumanDecision()` predicate the gates withhold on: a capped issue is never invited to merge while its question is unanswered, even when everything else about it is green. "Merge as-is" stays available — as the human's answer, which resets the counter and releases the gate. Rounds are counted the way spec rounds are: a batch of pure acknowledgements costs zero, a worker that escalated mid-round costs zero, an unreported round is charged one (a free round makes the cap unreachable). The cap gates feedback handling only — a multi-PR issue's DAG keeps advancing, since building the next slice was never a feedback round. New harness coverage in `verify.mjs` pins the boundary, the counting rules, the DAG exemption, and that a capped issue is surfaced to the human and holds its epic open.
