`defineWorkstreamBlocks({ leadFit: { model } })` now checks a worker's pick of lead with the same fit check a coordinator's `best-fit` routing uses, so the two can't disagree about whether a worker fits some work. The check is asked about the chosen lead with three choices: the lead, *none fits*, or *the work doesn't say its sort*. It refuses the open with `lead-doesnt-fit` only on *none fits*; a bare-name workstream and a lead with a broad description still pass, and a failed check still lets the open through. The model is asked as an evaluation model first and, on a model string, once more as a language model when that fails. A borderline lead may now get a different verdict than before. `leadFit: { model }` and the `leadFit` record on the tool's answer keep their shape; the record's `unanswered:` reason can also name an answer that wasn't one of the choices. Tests that scripted the old check as the generator `workstream-lead-fit` answering `{ says, fits }` now script an evaluator of that name answering a `worker` choice (the lead, `~none-fits` or `~sort-unsaid`), and its language-model ask as `workstream-lead-fit-ask` (FIX-2083).
