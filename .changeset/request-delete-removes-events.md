Deleting a request, including through session retention, now also deletes its stream events and runOnce results, so a later request that reuses the id cannot replay the earlier run; retention also keeps a request until its run has finished, `onFinished` included, and for twice the live-tail liveness timeout (60s by default) after, so a session can briefly exceed its limits (a request it keeps still counts toward `maxItems`, so older history is evicted in its place). Request records gain `finalizedAtMs`, which the run sets as its last write, and `heartbeatsUntilFinalized`; a custom `RequestStore` must persist both. With heartbeats off, a request whose run dies before setting `finalizedAtMs` is kept rather than evicted. `RequestStore.setFieldsIfStatus` gains an optional sixth argument, `expectedIncarnation`, which a custom store must honor: a record whose incarnation differs is reported as absent and left unwritten. Records from versions that never set `finalizedAtMs` are kept for the stale-request threshold or `maxAge`, whichever is larger, so a rolling deploy is safe. The filesystem store names per-key runOnce files `<id>@<key>.runonce`, so deleting one request can no longer remove another's results; files in the older layout are still read (except one that reads back as a request record, which may be one), and on delete one whose name another id could also have written is renamed aside (`.quarantined`) so no later request reads it. `SubscribeToEventsOptions` gains `isStillAuthorized`, which the request stream route passes to fence a live tail on the request's incarnation; a custom store must call it after every read that returned events and before yielding them, ending the stream when it fails (`isBatchStillAuthorized` is exported for this). The in-memory store's `delete` now ends the request's live streams. The filesystem store's `delete` removes the record last, so a failed sidecar cleanup leaves the id taken and the delete retryable, and deleting one request no longer deletes the record of a request whose id is its id plus `.runonce` or `.events`, nor is a `.runonce` record read as runOnce results (FIX-1647).
