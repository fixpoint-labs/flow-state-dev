A user or org resource is read by scope and key with no session, and a client writes it only through the flow it names (FIX-2624).

- **core:** `defineResource` takes `runBy` and `canWrite`. `runBy: "default"` lets a client write the resource through the framework's default write flow, which checks the schema, the owner and `canWrite({ prev, next, userId, orgId })`, and writes at the version the client read. `runBy: { flow }` names a flow of your app that writes it instead. With no `runBy`, a client can't write the resource; server flows still write it from their actions. User or org scope only, and with a `client` config.
- **core:** an org resource with `runBy: "default"` and no `canWrite` is a definition error: your app refuses to start until you declare who may write it, even everyone (`canWrite: () => true`). A user resource needs no rule: it is its owner's. Also refused at definition: `runBy` on a session resource, with `flowIsolation: true` or with no `client` config, `runBy: "default"` with a computed `client.data` or `writable: false`, and `canWrite` without `runBy: "default"`.
- **engine:** three routes. `GET /api/flows/resources/:scope/:key` reads the caller's copy (`{ value, version }`) with no session and no request. `POST /api/flows/resources/:scope/:key/actions/:action` writes through the resource's `runBy` flow, in a session the server keeps per writer; it records a request like any action. `GET /api/flows/:flow/identity` answers the user and org the server acts as under that flow's sign-in. Each resolves the caller through the declaring flows' own sign-in (a send to `runBy: { flow }` through that flow's, as a direct call to its action would), never the body, query or headers. Until a caller is signed in by every flow that declares the key, and admitted by one declaring instance's pin, every answer is the `404` an unknown key gets. A key two flows declare with different sign-ins or client settings is refused per request, naming both. Write sessions are the server's: no route or transport takes one from a client (session create included), the default write flow answers as an unknown flow, and no listing shows a write's session or request.
- **bullmq:** the job processor runs default writes too. Pass `resolvePrincipal` in the worker's deps, the same host-level resolver your web host is given, so the worker decides whether two flows that declare one resource agree exactly as the host does. Default: the development resolver.
- **client:** `client.resource(def)` returns a handle with `read()`, `state()`, `set(value, { version })` and `update(updater)`. `update` reads, applies your updater and writes at that version; when another write landed first it reads again and re-applies, three times at most, then rejects with `ResourceWriteError` (`code: "stale_version"`). `client.flow(kind).identity()` returns `{ userId, orgId }`.
