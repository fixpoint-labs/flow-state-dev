Living design

Drive this project with the thing we're building

Conductor is one effort: automate the SDLC, starting with issues and epics, later the PRD and the roadmap. It is a meta-harness — an orchestration tool that drives other coding harnesses. Its central bet is that the session you talk to stays small on purpose: the work lives in resources and the jobs are split across roles that are blocks, so the coordinator only ever reasons over what is open right now.

01

What Conductor is

A harness that drives harnesses. It opens a coding agent, gives it a job with the context that job needs, watches what comes back, and decides what happens next. Claude Code is the harness on the other end most of the time. Conductor never writes the code.

Now
issues and epics

One tool that takes an objective, breaks it into issues, drives each through spec, implementation and review, and stops where a person has to decide.

Next
prd and roadmap

The same substrate holding why something is being built, not only what. Roadmapping becomes a read of state rather than a document that rots.

Eventually
the oracle

A central place to ask what is being built and why, answered from what the system actually holds instead of from a person's memory of the last six weeks.

Never
the thing writing code

Conductor assembles context, dispatches, watches and routes. Editing files is the harness's job, and holding that line is what lets the harness be swapped.

The coordinator stays small on purpose

The session you talk to about an epic is the epic session, and the role that works it is the coordinator. Its job on any given wake is narrow: it knows which questions are outstanding, it classifies your reply against that set, and it re-queues the parked row that asked so the run picks the answer up. It seeds and reports; it does not proxy answers on a run's behalf, and a run is a top-level session you can address yourself. It does not hold the epic, the specs, the diffs, or any run's transcript — because the outstanding-question set lives in a resource, not in the conversation. The owner's default, not yet a decision (thread 15).

That is the architectural bet, and everything downstream is built to keep it true. A coordinator whose context grows with the run degrades with the run. A coordinator whose context is the currently open questions is the same size on day four as on day one, no matter how much work happened in between. State in a resource, not in context.

Why this is not today's process with extra steps

The epic-em skill already plays the coordinator role — it dispatches workers, surfaces gates, and holds a status table. Two things it cannot do. It cannot stay bounded: everything it learns accumulates in one transcript, so a long epic and a rotting context are the same event. And it cannot separate the jobs: coordinating, talking to you, planning the architecture and managing the runs all happen in that one context. Conductor's coordinator is bounded by construction — section 6 is where that construction lives — and narrow by role, which is the rest of this section.

A session is owned by a workflow, not by an agent

This is the sharpest difference between Conductor and the harnesses it drives, and it needs stating narrowly or it is wrong. Harnesses do have sub-agents, and a sub-agent does get its own context, so the difference is not that isolated context is unavailable. The difference is which layer is allowed to have it. In Claude Code and the harnesses like it, the top layer belongs to one agent: that agent holds the plan, talks to you, and routes your next reply, and its context grows for as long as the run does. A sub-agent can be handed a job and hand back a summary. It cannot take over the conversation, hold the plan, or route your reply — so the one context that must not rot is exactly the one that cannot be split.

FSD sessions are not shaped that way. A session record carries a flowKind — it belongs to the workflow — and a workflow can take on several isolated roles at once, inside the same request. A role is a block, and each role block declares its own context and its own tools. Isolation comes from the block boundary, not from a session boundary, so one request can run three roles without any of them seeing the others' working set — and the coordinator is one of those roles rather than the container the rest hang beneath.

So read the claim above precisely, because the flattering reading is the wrong one. The coordinator is not holding the epic, the specs and the runs and exercising restraint about what it looks at. It delegates to role blocks that each hold their own narrow context, and its own job — classify a reply, route it — stays small because there is nothing else in it.

Three jobs, three roles

The skill-based process we run today puts all of it in one place. One top-level agent coordinates the work, talks to you, keeps the architecture coherent, and manages the runs. Those are separate jobs, and running them in one context is what makes a long epic degrade — so they should be separate roles.

Coordinator
owns the conversation

Works out who needs to be addressed, routes the conversation, and translates work the other roles did back into terms you can act on. Conversation routing, not planning.

Manager
owns the work · same session

Reads the board and pushes. Is anything stalled, is a run not progressing, does the plan still fit. A block in the coordinator's own chain — a different role, not a different session.

Architect
consults · org-scoped

Does not design. Checks that final designs find alignment and cohesion, within an epic and across epics, and raises what it finds. No write authority over anybody's board.

The coordinator owns the conversation; the manager owns the work. Those two sit in the same session because their subject is the same epic, and the manager reaching the board through the coordinator's chain keeps the board single-writer — the contract note below is why that is a choice and not a constraint. Whether the manager may act on what it finds, or only report it, is genuinely open (thread 12).

The architect lands somewhere else, and for a principled reason rather than a taste: the manager's subject is one epic; the architect's spans many. A role whose whole value is seeing across epics cannot have its memory tied to one of them. Which is a claim about scope, and scope turns out to be a separate axis from the one the next heading is about.

A role is always a block. The call site and the scope are what vary

“Is this role a block or a spawned session?” looks like an open question and is not one. Isolation is free in a block. Concurrency is what costs a session. Both a block and a spawned session give a role its own context and its own tools, so isolation cannot be the thing that decides between them. What only a spawned session adds is running concurrently with, or longer than, the coordinator's turn.

So a role is always a block, and the first question left is where it is called: invoked in-turn, or dispatched into a spawned session that runs that same block. The architect is not either a block or a run. A quick cohesion check is in-turn; a sweep across every open spec is dispatched. Same role, same block, two call sites. “A session per role” is a false frame — it is a session per long-running invocation.

The second question is scope, and it is orthogonal to the first. Agents and sessions are not bound together — an agent can be invoked into any session, and what decides what it knows is not where it runs but where its resources live. Put a role's memory in session-scoped resources and it knows this conversation. Put it in org-scoped resources and every session that invokes it gets the same role, seeing across everything. The agent travels; the memory stays put.

The contract, verbatim

startDetached creates a derived child session. Its own documentation: the child session key is derived from [principal, parent session, seed]; the child “inherits tenant, user, org and flow kind from the running request and records it as its parent”; and “there is no flow or action parameter, so flow.actions is not reachable.”

So a spawned run is fixed in its parent's flow kind and cannot dispatch to an action. That much is a fact, and it is fenced. A task dispatch is the shipped route beside it: the seat names flow.task.actions[target] statically, and the gate reads the durable row rather than the payload exists. The conclusion people draw from it — that a manager therefore cannot run in a spawned session — is not, because flow.actions is not the route to the board. A detached manager reaches the board the way any block does, through ctx.cap.<board>.addTask(…). That was run rather than reasoned about: the row landed in the durable store, and the same manager spawned a peer.

That makes the manager being a block in the coordinator's own chain a design choice, not a shape the framework forced. The choice is single-writer: one author per board transition, one place to look when a task is in a state nobody expects. Section 6 makes the same call for spawned runs generally, and thread 5 holds it open rather than closing it.

Where the expensive thinking goes

The call-site question carries a cost position with it, and it is the design's stance rather than a preference. Conductor's own thinking should be cheap and structural — routing, deciding, planning. If a role needs hours of research, that work belongs in a harness run, which is already built for long autonomous work and already manages its own context. Hours of Conductor-side thinking is not a role working hard. It is the coordinator-stays-small principle failing quietly, one long turn at a time.

The architect is an org-scoped agent, not a session of its own

Apply the scope rule to the role that most needs it. The architect's memory goes in org-scoped resources, and then any session that consults it gets an architect that has seen every epic. It needs no session of its own and should not have one: a session is where a conversation lives, and the architect is not in a conversation with anybody. It is consulted.

Most of that is supported today, which is the useful half of the claim.

What the architect is for

It does not design. When a feature is being specced, the harness does that work, at that point in the flow, with the code in front of it. The architect is a consultant and a monitor: it checks that final designs find alignment and cohesion — within an epic, and across epics. That is a narrower job than “owns the architecture,” and it is the job that actually needs cross-epic sight.

It has no write authority over any epic's board. It raises; the coordinator decides. That is the same request-don't-mutate rule section 6 states for runs, applied to a role sitting above the board rather than inside it, and for the same reason: a board with one writer is a board you can reason about.

The architect may hold a task board of its own, org-scoped like the rest of it. proposed Two instances of the architect running in two sessions is not a contention problem to design around — it is a board working exactly as designed, since a board exists to be claimed from by N workers. The argument for giving it one is not concurrency at all. It is deduplication: two sessions consulting the architect about the same epic produce one claimed check, not two. A board at that scope is drained from many sessions, which is where a row's stored session handle can point at another session's child — thread 17.

The agent surface is thin, and this would be its first real use

The shape is right and the machinery is unfinished, so read every role claim above as a design on a young surface rather than as assembly of a working one. Agent (packages/core/src/types/agent.ts) has no resources field and no notion of scope — resources reach an agent only through usesCapabilities. createWorkforceCapability is a stub: a // TODO returning a bare capability. usesSkills is marked RESERVED and nothing resolves it, and contextMode documents that only "inline" is honored.

And almost nothing exercises it. Exactly one place does: examples/guides/research-team staffs a skill seat through defineAgent + createAgentRegistry + materializeAgent, and has a test — with an inline persona, session scope and a single flow, which is none of the three things this design leans on. agentBlock and definePersona are used nowhere outside the workforce package. apps/kitchen-sink declares @flow-state-dev/workforce as a dependency and uses it in zero source files, and no integration test touches it. There is no existing example of an org-scoped agent, of an agent carrying resources, or of one agent used across two flows.

Code and docs also disagree on precisely the point this design leans on. apps/docs/docs/orchestration/agents.md states “There’s no cross-flow assignment.” A probe built two flows off one agent and it compiled — which is a green build, not a green runtime. Recorded here as an unresolved contradiction, not as evidence either way.

02

How we'll know it works

One criterion, three clauses, each falsifiable on its own.

ClauseIt fails if
We drive this project's development through the toolWe reach for a plain Claude session instead, for any real epic
The UX beats juggling Claude mega sessionsAn operator who has both prefers the manual route
It drives multi-day epics without degrading from context rotDay-three output on comparable work is worse than day one

The third clause is the one the design answers directly, and section 1 is the answer. Context rot is not a model problem to wait out; it is a consequence of putting the run's memory in the run's conversation. Conductor moves that memory into collections and leaves the coordinator a classification job whose input size is bounded by the number of open questions — typically one to three, never the whole epic.

The first two clauses are claims about a person's experience of doing real work. They are easy to fail and hard to fake, which is what makes them worth having, and expensive to measure, which is why measuring them is still open (section 12).

03

What a person does

One product owner, one objective, three gates. Everything between the gates is automated; a gate is a person reading a paragraph and replying.

code — deterministic, executes prose — a model reads markdown and follows it human — a person must act

Gates are not the only time a person is needed. A running agent also asks things — a spec decision it cannot derive, a permission, an ambiguity in the issue. Those arrive unpredictably, from any run, and they are the subject of section 6.

Two rules decide which parts of this loop become code. A rule that must not be half-remembered — a review budget, a feedback cap, dependency ordering — belongs in something that executes. A decision priced in customers, promises or timing stays human, and gets somewhere durable to live rather than a message in a chat window.

Who owns what

Product owner
human · all three gates

Objectives, roadmap, and anything priced in customers or promises. Spec approval is theirs alone — the coordinator never grants it.

Coordinator
classifies and routes

Works the inbox, surfaces gates, and translates the other roles' work back to you. Holds no epic in its head, and does no planning.

Architect and manager
two more roles, two placements

Role blocks with their own context and tools (section 1). The manager is a block in the coordinator's own chain — same session, same epic — and pushes on the running work. The architect is org-scoped: invoked into any session, it consults on cohesion and raises what it finds, and writes to nobody's board.

EM / PM postures
absorb decisions, move no gate

EM absorbs engineering forks. PM may cut scope inside an approved objective but never add — additions always go back to the owner.

Runs
bounded, disposable

One harness run per issue-phase, in its own session — a child of the dispatching session, derived per task (section 6) — and its own worktree. Each returns at most a screen; the transcript stays where it ran. Who a person addresses is thread 15.

Where a gate lives

ctx.suspend(options) durably pauses a flow pending external human action: request status becomes "suspended", a SuspensionRecord persists the whole context (suspensionId, requestId, flowKind, actionName, sessionId, userId, reason, message, data, resumeSchema, render, allow, status, blockInstanceId, stepIndex), and an HTTP resume route re-enters the action with completed steps replayed from the durable log rather than re-executed. reason: "human_approval" defaults allow to ["approve","reject"]; "human_input" to ["submit"]. It needs durable: true on the action and on the runtime. Four working shapes live in apps/kitchen-sink/flows/chat-agent/: requestApproval, askQuestion, collectForm, chooseOption.

All of that belongs to the main session, and it stays exactly as described. It is not the mechanism for anything a spawned run is involved in — and today nothing stops one reaching for it anyway. A run that calls ctx.suspend gets a suspension: its request parks, the row reads as a job still going, and nobody upstream is told. A fence making the call an error inside a run is decided and filed. proposed It is not built.

Which reaches further than the detached case. Take the three gates of section 3. Two of them — a spec waiting on approval, a PR waiting on a merge — are raised after the run that did the work has ended, so there is no request left to suspend by the time anyone is asked. The third could suspend and does not, because running one gate on a different mechanism from the other two buys nothing and costs a second thing to reason about. What waits in all three cases is the task row, parked, and answer releases it. Nothing is given up by dropping the suspension: a parked row is durable state, so it survives a restart the same way a suspension record does, and it survives the run that created it too. The next section is that mechanism.

06

Questions, in and out

The load-bearing subsystem. A spawned run cannot stop and ask you something — so a question travels as data, and an answer travels back the same way.

Start with the constraint, because it is why this section exists. ctx.suspend pauses the request that calls it. A detached worker's parent has already returned — the row is in_progress and the parent's terminationReason is "handed-off". If a run suspends, the run pauses and nothing else does. You are never told. The epic keeps running around a run that is quietly waiting for a person who does not know they are needed.

And nothing refuses the call, which is the half worth saying out loud rather than assuming. A fence making ctx.suspend an error inside a run is decided and filed proposed — it is not built, and section 11 is where it sits. Until it lands the wrong mechanism stays reachable and fails quietly, which is an argument for building the right one rather than for waiting on the fence.

Detached closes session state, not resources

detached: true on claudeCodeAgent suppresses three things at once, and the option's own doc explains why they are one decision rather than three: the sessionStateSchema declaration, the reads and writes that go with it, and the SDK resume — “the session provider is not consulted at all.” Every one of those three is ctx.session.state or ctx.session.patchState.

Read why the flag is set, though, because it is easy to mistake for a stance. It is set so the board will construct at all: a detached worker may declare no sessionStateSchema anywhere in its tree, and claudeCodeAgent authors one unless the flag is on. A construction shim. It is not a decision that every run starts fresh, and it is not a bet that runs cannot be resumed.

Resources are a separate channel, and it stays open. The same block declares three session-scoped collections under recordWork and writes them from a detached run. The inbox is how a run asks a question, and it travels a channel detached leaves open, which is why asking needs no guard narrowed. Continuity is not a resource at all — it rides the task, below — and it does not travel that channel either.

Out — the inbox resource

A user-scoped collection, one instance per open question exists · lab. The scope choice is load-bearing: a spawned child inherits tenant, user, org and flow kind from the request that started it, so a user-scoped collection is one instance set shared by the session that answers and every run under it. A session-scoped collection would need sharedToWorkstream: true exists · fenced — renamed sharedToLineage at the endpoint — to reach the lineage at all, and would then be tied to one epic's session — the wrong lifetime for a thing you answer tomorrow morning. The run index further down was designed to make the opposite call, and the lab reversed it.

The board partitions by epic; the inbox does not. A board is a claim pool, and one collection id is one pool — the claim predicate tests status and deps only, so two epics sharing an id claim each other's rows (section 4) exists · lab. An inbox is not a pool: nothing claims a row. The reason is who reads it, not key uniqueness — the lab's inbox says so, and rejects the uniqueness argument this page once made: the key is attempt-keyed from a board's counter, so two epics driving one issue-phase can both produce attempt 1, and what exempts the inbox is that its reader is a person. A key two boards write whose reader is a job needs the board's discriminator; a key whose reader is a person does not. An unfiltered list() spanning every epic is the product rather than a defect — it is your inbox, and everything waiting on you sits in one place.

A run requests a plan change; it does not make one

A run that discovers the plan is wrong — this issue needs splitting, that dependency points the wrong way, this task should not exist — has the board within reach. It should not touch it. It posts a plan-change request the same way it posts a question, and the top session decides what to do with it. proposed

The reason is single-writer. A board only one session writes is a board you can reason about: every transition has one author, and “why is this task pending” has one place to look. Let N runs edit the plan they are being run by and the board stops being a plan and becomes a negotiation, with no one holding the whole of it. The restriction also costs close to nothing once an internal dispatch via a dispatcher exists: the request travels the channel a mutation would have travelled anyway, and it arrives somewhere that can weigh it against the other seven issues rather than only against its own. Whether some runs should be trusted to write directly is carried as thread 5, not settled here.

Signal and content are separate

The question and the wake are two different things, and keeping them apart is what makes the wake cheap to build. The content — what was asked, by which run, against which task — is the inbox/** row. It is durable, it is re-readable, and it is the truth. The signal carries nothing but there is something for you. It is ephemeral, and it is an optimization over polling rather than a delivery guarantee.

The failure mode is the point. If the coordinator is down when the signal fires, the wake is lost — and nothing else is, because the row is still sitting in the collection and the next re-entry finds it. So the signal never has to be durable, and that removes most of what makes an event bus expensive: no persisted queue, no redelivery, no dead-letter, no acknowledgement protocol. A dropped wake costs latency.

How the coordinator wakes

Honestly: not by a resource hook. reactTo is real — a collection can bind a block to created / stateUpdated / deleted / contentUpdated — but the engine runs a reactive block in-session, inline in the mutating turn. A run writing an inbox row fires the hook inside the run's own request. It cannot reach the coordinator's session. Designing around a hook that quietly fires in the wrong place is the class of mistake this document exists to catch.

Two situations wear the same name. Hot is a wake while work is in flight: something is already looping, so the only question is how it notices a new row. Cold is a wake when nothing is running at all — the board drained, every run settled, and the epic waiting on a person who may take until tomorrow. Nothing is looping, so something outside has to re-enter. The useful thing about the split is that one answer covers both, and it is a watch.

Nothing is held open, and nothing polls

The blocking wait is tempting because it costs nothing to build. It is the wrong shape for the workload this project exists to survive. Holding a worker slot and a live loop open for the hours — or days — a person takes to answer means the machinery carrying a multi-day epic is a loop that must not die for a multi-day epic. Anything that restarts, redeploys, or trips a lease inside that window takes the run with it. A design that leans on an idle poll has quietly made the poll interval its liveness guarantee, which is not a guarantee.

So the intended path is quieter than that. A run blocked on a question ends its request, carrying the question out with it. Its task stays on the board, parked. The coordinator is not looping either — it holds a watch, and a watch costs a row. Nothing has to drain to nothing, because the board is the durable state: what wakes it is an internal dispatch, or the person's answer, arriving against a parked row — the next request picks that task back up and continues from there. The exit is shipped, the lab's answer re-queues and drains, and the framework's own verb is specced; the note below separates them. parked stays as the short-horizon convenience for “the operator is right here, answering now” — not as the thing the design depends on. What is left to design carefully is what re-enters, and how it finds the right outstanding row. The rest of this section is the answer; section 12 carries what it leaves to a separate build. Read it as the shape the first real run ships on rather than as a later upgrade to it. The Proof is an internal dispatch — or the person's answer — plus a parked task row, and the short-horizon loop is not a stepping stone toward that — section 11 is why.

The gap the board had, and the three names that come with it

Checked in packages/orchestration/src/task-board/blocks/check-board.ts. parked is the blocking wait, and says so: it “keeps the loop alive in both modes — the worker's preceding .waitForCondition blocks until an external actor transitions the task back to pending.” The request stays open, which is precisely what the cold path is trying not to do. Everything else in the status set is terminal (completed, errored, cancelled) or out of reach from a claimed row: the state machine admits blocked only from pending, and it means a dependency is not met, not a person is. Leaving the row in_progress and ending the request is worse than either — it is indistinguishable from a child still working.

So the cold path needs two things the board did not have: a way for a parked task to let its request end, and then a way for that row to be picked back up. This document proposed the first as a new status, pending feedback. The answer that shipped is a different shape, and a better one. shipped It is an exit predicate rather than a status: onReview: "exit" excuses a parked row from the drain's waitable count, so the drain returns and reports terminationReason: "parked-for-review" while the row stays parked and durable. Same property — whether the request stays open while the wait happens — without a fourth status to teach the state machine. The same change fixed a second thing worth knowing: parked → completed is a legal transition the ticket fence admits, so until then a worker that parked its own row had it completed by the success tap a moment later. The park did not survive the step after it. Now the recorders read the status first, on every board.

Read the two board verbs precisely, though, because the obvious reading is the wrong one. awaitReview and unpark both exist and both work exists — the first moves a row to parked, the second moves it back to pending and clears the lease and the claim. Neither has anything to do with requests, and unpark has no precondition about one. What it does not do is start one. In the board's own words it “re-queues it — it does not start anything, so whatever drains the board next is what picks it up.”

Which is exactly enough on a board that holds, and not enough on one that exits. Hold the drain and the loop is still turning when the row re-pends, so the next iteration picks it up; that case works today and this changes nothing about it. Exit, and the drain has already returned — re-pending produces a pending row with nothing draining it. So the exit did not make unpark the wake. It made the board need one.

That wake is specced in the framework and not built there; the lab ships it as answer. exists · lab proposed Its shape is a verb that unblocks a parked task with an input, so the answer arrives as a new request rather than as a resumption of the old one — the right shape precisely because the old one is gone. The lab's answer composes three shipped calls — a guard, unpark, then a drain it runs itself in the same request — and names the two windows only an atomic framework verb closes: a non-parked row can move between the read and the re-queue, and a second answer arriving mid-flight is dropped rather than refused. Outside the lab, until the framework verb lands, a parked row on an exiting board is a dead letter: correct, durable, and unreachable. The park itself gets a name in the dispatch-protocol design, ctx.task.park() — the one ambient lifecycle verb the substrate owns, and the only member of ctx.task that design keeps proposed. The coordinator never does the work, so it has no business claiming anything. What it wants is to know when a run's task settles, so it can route the result. That is a watch, and today there is no way to say it — which is most of why the wake looked like a hard problem. The only relationship on offer was the wrong one.

A watch is an internal dispatch with a trigger. “When this row goes terminal, send me a dispatch.” That framing is what makes it cheap, because it is not a new subsystem: addressing, delivery and arbitration on the session key all belong to the internal type described next, and a watch adds only the condition that decides when to send. Each watch names one recipient, so a task with three watchers settles into three addressed dispatches — three sends, not one broadcast. Two design points, both settled.

Watches are keyed rows, one per (watcher, task) — not a list on the task row. A list is read-modify-write on one row by many writers, and the losers' writes vanish. That is the same contention this document rules out for the run index further down, for the same reason, and the fix is the same one: let the key carry the identity and let the collection do what a collection is for. “Everyone watching this task” is a list(), not an array anybody rewrites.

The send is best-effort, inside the settle — the fenced recorders, where every settle already goes. Settle-then-send can half-fail: the row goes terminal and the dispatch never leaves. That is acceptable here, and it is acceptable because of the durability split two headings up rather than because of any care taken in the code. The dispatch is ephemeral; the row is the truth. A lost send costs a wake, not a fact — the watcher re-reads the board on its next entry and catches up on everything it missed. So there is nothing here to engineer around. A two-phase commit between a task row and a dispatch would buy latency in exchange for closing a failure mode the design already absorbs.

The wake is an internal dispatch, not a broadcast

The reason no existing package covers the cold-path wake is worth stating precisely rather than filing as a gap. An inbound transport carries external origin into a flow: mcp, chat-sdk, voice-openai and scheduled each translate somebody else's protocol into a dispatch and stamp where it came from. node and bullmq are host and runtime adapters — they serve the process and run the jobs, and receive nothing on their own account. A run announcing a question is neither of those. It is session-to-session, inside one system, under one principal. That is a different seam, and it is empty.

What fills it is the internal dispatch type: a message bus, not an event bus. The epic that files the work keeps the name relay; the mechanism is the internal row of one dispatch-type table rather than a subsystem beside the transports (thread 3, section 11). One dispatch travels from one request to one named recipient — another session, or the same session as a new request — through a dispatcher({ type: "internal", target }) block whose session slot either names an existing session by id or derives a child from a key. Sessions address each other directly, so a run reaches the epic session, the epic session reaches a run, and two top-level sessions reach each other the same way. There is no topic, no subscriber list, and no fan-out. What a sender may legally address is narrower than this page proposed: an id must name a session that exists, belongs to this principal and tenant, and runs this flow — and absent, another owner's and another tenant's all answer the same refusal on purpose, so a dispatcher is not an existence oracle. A session is never created by an id, and there is no discovery. Session ids are not secret — they appear in items and traces — so what scopes a model's reach is a router over declared dispatchers, not a lookup (thread 2).

Fan-out is ruled out, not deferred

A request runs in a session. That is where its items, its state and its continuity live, and nothing is processed without one — a design invariant, not an accident of the current code. The tempting order is to build fan-out first: publish to a topic and let any interested party pick it up. It cannot be built, because an unaddressed dispatch has no session, so there is nothing for it to run in.

Delivering to every interested party would mean inventing a session per subscriber. That is a different feature — spawning work — wearing delivery's name. So fan-out is not a later version of the internal dispatch. It is incoherent with the thing underneath it, and the design is smaller for saying so out loud.

A flow is already a mailroom

Actions are dispatch types, and the flow routes each one to its workflow. That is what defineFlow({ actions }) has always been, and it is why so little has to be added: an internal dispatch is a sixth type arriving at a door that already exists.

Actions are already API-driven — over REST, or programmatically against the flow instance — so the set of things that can put a dispatch through that door is already open. An internal dispatch adds an internal sender to it. It does not add a second way in.

The machinery is small

The process executing the current request sends. The same process, conceptually on another thread, receives the dispatch and handles it as a request on the addressed session. Where a queue adapter is configured — @flow-state-dev/bullmq is the one in the tree — a { key } child's delivery is a job, and that is what makes it survive a process restart. An { id } delivery into a session that already exists gets no job there at all: the host refuses it before anything is enqueued, because the recipient's concurrency policy would not be applied past that boundary exists. For an in-process host, delivery is attached to the process, not to the originating web request, so a sender that has already returned does not take its dispatch with it. Whether that per-adapter split survives the send becoming a block is open — thread 23.

Arbitration is not new either. The concurrency policy is “enforced once at the shared dispatch seam, so every transport … inherits the same behavior” — and an internal dispatch inherits it with everything else. It either waits for the session to finish its in-flight requests (queue, FIFO on the key) or is handled as soon as it arrives (allow). One word on the flow. No new queueing mechanism.

Cron becomes a sender, not a transport of its own

The same door answers a second thing the project has open. A block that wants a later delivery writes an outbox row carrying the whole envelope — type, name, session, payload, delivery time — and a host sweep claims the rows that are due and dispatches each as a schedule dispatch. Cron then inherits addressing, arbitration and durability from the door instead of carrying its own. Static entries keep the path they have; a session-less tick stays session-less.

Two concrete gaps stand between here and there, and both are visible in the tree today.

  • A scheduled tick has no session at all. The scheduled routes pass none, and the code says why in as many words: “scheduled envelopes have no session.” So there is no way to address a specific session from a cron. It also means a tick gets no arbitration under the default policy, whose "session" key “resolves to undefined (no arbitration) when the dispatch has no session”.
  • A dynamic schedule carries a user, not a session. The schedule row's schema is { cron, kind, input, timezone, onOverlap, description, enabled }, and the resolver parses (userId, collectionKey) and synthesizes principal: { userId }. The address cannot even be expressed.

The shape is a row a block writes, not a field on the schedule. The row carries its session: absent means a new session per delivery — today's behaviour for a static entry, preserved exactly; present means the delivery is a new request on that session. The sweep claims with the board's lease so two overlapping ticks deliver once, delivers at-least-once, and runs under the principal the writing request persisted. proposed — deferred, not this cycle; the cron half stays its own issue, and this atlas states the constraint rather than the design. Two things to carry into that build

There is nothing to await, so the self-addressed deadlock is unrepresentable rather than refused. A delivery ack is synchronous and free — the dispatch is discoverable and will not silently not exist. An outcome is a task row somebody watches. A parent that waits on its child is a block call, not a dispatch. So no send mode blocks, and a sender under queue that addresses its own session queues a request behind itself, nothing more (thread 4).

Fan-in collapsing is anticipated, and additive. debounce is already reserved in the policy enum — it parses, and is rejected at definition time in v1 — and it is exactly what “three runs posted questions, wake the coordinator once” wants. The collapse case has a home without changing the shape.

The coordinator's job, and why it stays small

When the coordinator wakes it does one thing: read the open inbox rows, ask about them, take your reply, and route it. That is a classification problem over a set of size one to three. It is not a re-derivation of the epic, and it never needs to be, because everything that would justify a larger context is already in a collection somebody else can read.

Three runs asking at once is the ordinary case, not the edge case. The epic session is the unit a person addresses, and inside it one inbox serializes — one question at a time, and the answer re-queues the row that asked. The coordinator seeds and reports; it does not proxy answers. Runs are top-level sessions a person can address — not hidden behind anything — but the question path runs through the epic session's inbox, which is deliberately the opposite of per-run question threads, where you would address any of three channels in any order: exactly the juggling of parallel Claude sessions this project exists to replace. proposed This is the working default, pending the owner's sign-off (thread 15).

And the classify-and-route step is itself a flow made of blocks, not one large model turn. A small structured generator decides which open rows a reply answers; a router over the declared dispatchers dispatches one answer per answered row. Both primitives ship today: intentClassifier and intentRouter live in @flow-state-dev/core, and router({ routes, execute }) is a first-class block kind.

The honest hard case. A reply that answers one row cleanly is easy. Three cases are not, and the design has to say what happens rather than hope:

  • Ambiguous across two rows. Two open rows about the same file, one reply that fits both. The classifier returns two candidates at similar confidence; below a threshold the coordinator does not guess — it asks back, naming both rows. Guessing routes a decision into the wrong worktree, which is expensive and silent.
  • Answers one row and opens a new topic. "Use the second option — and while you're there, drop the retry wrapper." Only the answer is classifier output — { rowId, answer, conf } has no field for anything else. It settles its row and rides the answer back. The new topic is a request aimed at the epic session, the board's single writer (thread 5), and this path has no route that takes it there. proposed So the reply half-lands: the answer arrives, the topic does not.
  • Answers nothing. A question back at the epic session. It answers from the collections if it can, and otherwise opens nothing and settles nothing — the rows stay open, which is the correct outcome and the one an eager classifier gets wrong.

What a phase actually is

The question worth asking before writing three adapters: what about a phase requires a custom block sequence, rather than a prompt and a pass-off to the harness? Answered honestly, the design gets smaller.

Take each phase and separate what is genuinely specific to it from what is the same harness management wearing a different name.

The verdict

Three phases differ in three values, not in three block sequences. A prompt builder, a done-condition predicate, and a list of readable collections. Sessions know what the others are working on

A planner reasoning alone plans work that collides with a sibling's. So a planning or architect role gets the other epics in flight in its generator context: what each one is doing, how far along it is, when it last moved. Two things follow. It stops proposing work another session already owns — and, better, it can decide to ask before it commits, raising the assumption with the operator through its own session while the plan is still cheap to change. Deconfliction is the floor. Coordination is the point. These rows complement the architect's org-scoped memory (section 1) rather than substituting for it: resources hold what has been decided across epics, this set holds what is moving right now.

This is a collection, not a framework session registry, and that call is the interesting part. A registry answers “session abc123 is alive”. What a planner needs is “this epic is refactoring the store adapters, three issues open, last moved an hour ago”. Each coordinator writes its own row as it works; any role reads the set through a context formatter over a list(). Four reasons it belongs here rather than in the engine:

  • It carries meaning a liveness registry cannot. Engine state is thin on purpose; the thing a planner is asking is a domain question.
  • It is this document's own principle applied again — state in a resource, not in context. The coordinator's memory already lives in rows. So does its picture of its peers.
  • It reaches a generator through the context slot, which is how every other context in this system is delivered. No new delivery path to invent.
  • It survives session death. A registry loses the epic when the process goes. A row persists, and can say “stalled” instead of vanishing.

So the framework piece is close to nothing: coordinators write their own rows, and reading them is a list() a formatter renders. proposed What is left over usually gets filed as one question — staleness — and it is really two. Does this session exist is cheap, and safe to answer: a session id either names a record or it does not, and saying so leaks nothing a peer's own row was not already publishing. Is this request still live is a different question, and the engine guards it deliberately.

The design sidesteps both, which is why neither has to be built. A sender that needs a reply files a task row and watches it — an outcome is a row, never a send mode (section 6) — and gives up on its own clock. That needs no visibility into the other session at all: the sender knows what it asked and when, and a timeout is a fact it already owns. It is the smallest thing that works, and it covers a case a probe cannot even describe — it is not clear what should make a session stale in the first place, since a request can hang for an hour inside a session that is perfectly present. A sender-side timeout answers the question the sender actually has, which is should I still be waiting.

The caveat, verbatim — and it is a trap

livenessOf?(requestIds: readonly string[]): Promise<LivenessAnswers>, where LivenessAnswers = Readonly<Record<string, boolean>>. Its own documentation: “false means ‘no live registration was found’, never ‘definitely dead.’” A request that completed, one never registered, and one whose registration was lost are indistinguishable by construction, because terminal requests are deregistered. “Treat false as permission to stop waiting — never as proof the work did not happen.”

So it is the right instrument for “should I still be waiting on this” and the wrong one for “did that work happen”. Two limits bind this use of it in particular. The verb is optional and absent when the liveness gate refuses (section 9). And identity filters before the answer is built — user, tenant, flow kind, then descendant-session — with the module stating the consequence in as many words: “an id outside the caller's lineage or under a different principal comes back indistinguishable from an unknown id — there is no existence oracle here.” A peer coordinator's session is outside that lineage, since the walk only ever climbs to the caller's own. Which is the argument for the timeout again. The sender's own clock is the answer; the lookup corroborates it — and only for one's own descendants.

The rows are intelligence, not an address book. A planner reads them to see what a peer is holding and how far along it is. Nothing in the set is a way to reach that peer, though a peer's session id is not secret and any session the sender knows under the same user is deliverable; an unknown id rejects, and there is no discovery (thread 2).

Memory — deferred on purpose, not ruled out

We talk to our agent, which fans out to Claude Code most of the time. So it is genuinely unclear whether Conductor needs memory of its own or can let the harness use its. We expect to hold memory eventually, bespoke and tuned to this workflow, not general conversation retention. Note that the bounded-coordinator design lowers the pressure for it: a coordinator that reasons over open rows has less to remember by construction.

Terminality is now the rule rather than one type's special case: every type resolves one own-property lookup on its own map, a type with no such entry refuses by name, and nothing falls through to flow.actions exists. The fenced detached path is unchanged beside it — workstreamRoutingSeed({ boardId, coordinate, topic, topicFallback: claim.taskId }), source: "workstream", terminal on flow.workstream exists · fenced. That terminality is what the call-site rule of section 1 rests on. It does not by itself stop a dispatched role writing to the board, which is reachable as a capability from anywhere — keeping one writer is a choice the design makes, not one the framework makes for it (thread 5).

Topic was the discriminator, and the slice retired it. Deriving identity from the topic is what let a second task on the same topic adopt the same child session, and it is the mechanism this document once leaned on to land an answer in the run that asked. The decision sits on the seat now, and it is three policies rather than the four this page proposed: "per-task" (the task id), "per-worker" (one child per seat, so the worker remembers what it already did), or { key: (task) => string } read off the worker input — one issue across spec, implement and review exists. There is no explicit-session policy on a task seat; naming a session outright is the internal type's { id }, which is a different slot on a different dispatch. The presets frame the board id into the key so two boards' children stay apart; a custom key is used as returned, which is the sharp edge. Under "per-task" a same-session steer is not automatic: every row mints its own session, so an answer that must land in the run's session takes { key } or a "per-worker" seat. And "per-worker" does not hold across parents: the derivation hashes the parent session before the key, so two sessions draining one user-scoped board get two worker sessions from one seed (thread 18).

3 · What this is called

This document says mail, and that name is not settled. The competing shape is not a synonym, it is a different decomposition. Message is already uniform in this system — a user message, a session message — so instead of standing up a parallel noun, extend messages with a sender and a recipient. Cron then falls out as a scheduled message rather than a second concept: one noun, several origins.

If the flow-config group still wants a qualifier, relay is the accurate one — it names routing, which is what this does, rather than storage. exchange is rejected: AMQP-loaded, and an exchange is a fan-out primitive, the one thing this design rules out. intake is rejected too — it implies inbound-only, and this is bidirectional. Mail's virtue is that it reads as internal; its risk is that a mailbox implies polling, which is exactly the model the design rejects.

Contradicted, and the contradiction is instructive. There is no relay config group to name — no parallel binding table was ever built, and what would have been relay's config is one map on the flow, at flow.internal.actions. relay survives as the epic's name only. The competing decomposition in the paragraph above also lost, and for a reason worth keeping: message was rejected as the concept's name precisely because it already names the content item that enters an LLM's history, and the two meanings meet at an internal send. The noun is dispatch. Read mail above as the metaphor, which survives; mailroom and inbox do too.
4 · How many send modes

Fire-and-forget and wait-for-response are genuinely different intents, and both are wanted: a run posting a question does not wait, a planner checking an assumption against a neighbouring epic does. A third mode, delivery receipt, is questionable. It answers did it arrive, which only matters if you cannot otherwise tell — and a durable row already tells you.

The related design move is not open, and belongs on the same page as the modes. Self-addressed plus wait-for-response should be refused at definition or dispatch time. Under queue a sender that awaits its own message never lets it start, so the deadlock should be unrepresentable rather than merely documented.

Contradicted, and the shipped block confirms it. There is one mode, not two, and wait-for-response is not deferred — it does not exist. A dispatcher() returns { sessionId, requestId, adopted } the moment the host accepts, and there is no slot on it for a mode. Every dispatch carries a synchronous delivery ack; an outcome is a task row somebody watches; a parent that waits for its child is a block call rather than a dispatch. So the question “how many send modes” has no second answer to give. The delivery-receipt mode this thread already doubted is subsumed by the ack. And the self-addressed deadlock is better than refused: with nothing to await, it is unrepresentable. The tracker title still says wait-for-response and lags the decision (section 11).
5 · May some runs manage the board directly?

Section 6 states the answer the design runs on: a run requests a plan change, and the top session decides. That keeps the board single-writer, which is what makes it reasonable about — one author per transition, and one place to look when a task is in a state nobody expects.

The doubt is real, though. Some runs sit closer to the plan than the coordinator does: a review run that finds an issue needs splitting knows more about the split than anyone upstream, and routing it through a request adds a hop and a translation. A narrow write grant — this worker may add sub-tasks under its own issue, and nothing else — is a coherent middle rather than a fudge.

Unresolved. The argument for the stated answer is that single-writer is a property you lose all at once and cannot cheaply get back, while the request path costs a hop rather than a capability. What would change it: a plan-change round trip measurably slower than the work it gates.
6 · A detached agent has no way to be handed a resume id

The design's one real dependency on framework code, and it is small. claudeCodeAgent consults its session provider only on the non-detached path, so nothing today carries a prior sdkSessionId into a detached run. Until something does, a steer starts the coding agent from nothing: the spawned session keeps its item history and the model loses its own. The write half already works — the handle is returned regardless of detached — so what is missing is an input and a conditional resume, not a change to what detached means.

Answered — resume, not restart. Restarting is correct and expensive: a re-stated prompt pays again for a diff the agent had already read, and a Proof whose second turn does that is not proving the loop it claims to. So the input is on the Proof's critical path rather than beside it, and shipping the Proof without it is off the table. Two things follow that are not settled by this answer: the shape of the typed handle field on the task (section 6), and what the resume work lands as — thread 14.
7 · A reply the classifier cannot place

The coordinator's whole economy rests on classification being reliable over a small set. Two open rows about the same file and one reply that fits both is not a contrived case — it is Tuesday. The design says ask back below a confidence threshold, which is safe and mildly annoying. It does not yet say what the threshold is, or whether repeated ask-backs are worse than an occasional misroute.

Does a misrouted answer cost more than a re-ask? If a steer into the wrong worktree is cheap to undo, bias toward guessing; if it silently changes the wrong file, bias toward asking. This is a product call about tone as much as correctness. The default in thread 15 narrows what the classifier is up against — one epic session, one inbox, serialized, so the candidate set is that epic's open rows and not every run in flight — but it does not decide this, because two rows about the same file sit in one inbox just as easily.
8 · Steer delivery is bounded, not instant

Under queue, a steer lands at the next turn boundary. A long turn means a long wait, and the only true interrupt is the mid-turn abort — there is no "stop what you are doing and read this" that preserves the run. That is probably right, since interrupting mid-tool-call is how state gets corrupted, but it is a constraint the UX has to be honest about rather than hide.

Do we show that a steer is queued behind an in-flight turn, or let it look instant and absorb the delay? Showing it is more honest and slightly noisier.
9 · Durability over a multi-day run

The success criterion is literally "multi-day without degrading". A multi-day epic is the longest-running, most failure-exposed workload we have, and the board's load-bearing areas are lease, retry and durable resume: a stranded lease can hang a drain for hours, a reclaim can reset every in-flight task, a dead detached child can look stalled for a full lease, and a blind retry re-runs unchanged work. Resting the question channel on the cold path removes one of these — no worker slot and no lease is held across a human's answer, because the run's request ends and its task waits as a durable row — and leaves the rest untouched.

Harden the board first, or find these on the first real epic? These are not adjacent bugs — they are the criterion's failure modes, and the third clause fails on exactly this class.
10 · Nothing measures the criterion

"Better than juggling Claude mega sessions" and "multi-day epics without degrading" are real, checkable claims. There is no baseline for the mega-session route, no working definition of degradation, and no instrument for either. Nor is there a goal check that runs a development process end to end — every green check today certifies a part.

What is the smallest honest measurement? One epic run both ways, recording wall-clock, gate count, rework rounds, questions asked, and a short operator note, would beat nothing — and it is the only proof this design currently has a route to.
11 · Which layer of workforce do Conductor’s roles sit on?

A package in this repo already materializes a role as a block. agentBlock(agent) returns a BlockDefinition — documented as “invoke an Agent as a standalone block in any flow” — and it sits alongside defineAgent, definePersona, createAgentRegistry, materializeAgent and createWorkforceCapability, with a per-agent tool catalog and capability catalog behind each one. That is close to exactly the coordinator / architect / manager shape of section 1.

But @flow-state-dev/workforce is not a settled package. It was intended as a file-conventions system — an opinionated wrapper that takes primitives already sitting underneath it and packages them into something easier to work with. It is not a finished thing to adopt wholesale. So the fork is not reuse it or build our own. It is which layer Conductor actually needs: the wrapper, or the primitives beneath it.

The layering is visible in the source, which is what makes the question answerable rather than a matter of taste. agentBlock is a thin wrapper over materializeAgent; materializeAgent builds on workerInputSchema, buildUserMessage and the task-tools capability, all of which live in @flow-state-dev/orchestration, and it is written to satisfy MaterializeAgentFn so it can be injected rather than depended on. Hence an outcome worth naming now: if the only piece Conductor ever uses is materialize a role as a block, that piece may belong in @flow-state-dev/orchestration rather than Conductor taking a dependency on a wrapper for one function.

Four things checked since, and they point one way. The persona machinery is separable at essentially one line — materialize-agent.ts's call to resolveAgentPersona — and its types, PersonaSource and PersonaInlineConfig, already live in @flow-state-dev/core rather than in workforce. define-persona.ts and resolve-persona.ts import nothing from workforce at all. Orchestration is already the dependency direction: workforce imports workerInputSchema, buildUserMessage and taskTools from orchestration, so moving the useful part down creates no cycle. And createAgentRegistry is fifteen lines around a Map, needed not by agentBlock but only by the agent-ref string-indirection path in orchestration's own delegation — which is, tellingly, the only part of workforce anything in the tree actually uses.

Still unresolved, and the leaning has moved. It was toward building on workforce, on the argument that “different roles within a team” is precisely what workforce was reaching for and a second materializer would be duplicate surface. The evidence now points instead at moving the agent-as-block piece down into orchestration, rather than taking a dependency on a wrapper for one function. Neither is locked.

Not a decision to make now. It is one to make with the first real role block in front of us, because the layer only becomes obvious once something needs it. What to confirm then is the cheap outcome the evidence now favours — one function moving down into orchestration, and neither package adopted at all.
12 · Does the manager decide to re-plan, or only say that re-planning is needed?

The manager reads the board and pushes — something is stalled, a run is not progressing, the plan no longer fits what the work turned out to be. What it may then do is not settled. It could adjust the plan itself, inside the approved objective, and tell you afterwards. Or it could surface that re-planning is needed and let the coordinator put the question to you.

That is the difference between a manager and a reporter, and it is a product call rather than an implementation detail: it sets how much autonomy the system takes on your behalf while you are not watching.

Leaning: surface rather than decide, until the manager has a track record you can read. Deciding is the better product if it is right most of the time and the worse one if a bad re-plan surfaces a day later — and there is no evidence yet about which. What would change it: a run of epics where the re-plans it proposes are approved unchanged.
13 · A workstream shares its parent’s whole flow

There is no separate Workstream flow. A detached child runs the parent’s own FlowInstance, under the parent’s flow.kind, and the kind is not a construction input at all — packages/engine/src/context/detached-start-operation.ts says it “arrives per call, from the seam, as the parent request’s own kind. A child always belongs to its parent’s flow.” The binding is one line, flowKind: flow.kind in packages/engine/src/context/create-request-host.ts. The identifier WorkstreamFlow appears exactly once in the repository, inside a comment, and names nothing; what is shared is flow.workstream, one ActionCore assembled onto that same flow beside flow.actions (packages/core/src/flow/workstream-core.ts) — the comment is what makes people picture a second flow object.

So everything declared on the flow definition is shared by construction: actions, the resources map, session.stateSchema, webhooks?, schedules?. The Relay spec's placement did not hold. It declared “a relay? group, a sibling of webhooks? / schedules?”; the decision of record drops that group entirely and folds it into the flow's typed entry set, where webhooks? and schedules? are heading too. There is no separate group to place.

Two doors lead into a workstream, and only one is narrowed. The seam door, a framework-stamped detached dispatch, routes terminally to flow.workstream and can never reach flow.actions (packages/engine/src/execution/resolve-action-core.ts). The caller door is not. A child session is an ordinary session of the same flowKind owned by the same principal, and no route-level guard excludes it, so the parent’s full action surface is present inside the workstream to anything that can address that session. That inference is answered. Terminality stops being one type's special case and becomes the rule: every type resolves one keyed lookup on (type, name) with no fallback, so the boundary is the map itself rather than a routing choice made for one door. What that does not fix is a session on a shared flow accepting an entry meant for a different role — which is thread 18.

The shared-flow model already costs something, and the code says so out loud. packages/orchestration/src/task-board/detached.ts refuses a detached worker whose descendants declare sessionStateSchema, because “detached workers share one Workstream flow, where two routes choosing the same key with different shapes corrupt each other with no error.” The refusal is defensible; its stated reason names the wrong mechanism. Two detached workers land in two different child sessions with two different state blobs — board, coordinate and topic must all three match before two tasks share a workstream — so there is no shared cell to corrupt. What they share is the flow-level key namespace: one flow.session.stateSchema for the parent and every descendant, with a block’s sessionStateSchema a pure typing overlay that gets no runtime parse. A comment to correct, not a behaviour to fix.

The fork is narrower than the fact makes it look. Per-role divergence costs nothing and is already the shape: “all workstreams get surface X, all top-level sessions get surface Y” fits inside one flat relay? group today, which is the asymmetric door the Relay spec already draws: a sibling resolves flow.actions because it is a caller, a workstream gets “a narrow, author-declared inside-world surface” and never reaches flow.actions at all. Per-instance divergence is what nothing reserves room for: this workstream addressable at A and that one at B, or a child narrower than its parent. That needs the declared surface to gain a keyed or resolver form rather than a flat group, plus a resolution step that does not exist. It needs almost no new persisted rows — SessionRecord already carries parentSessionId, topic and coordinate alongside flowKind (packages/engine/src/stores/types.ts) — but the recipient lookup reads only flowKind, and nothing else reads that row for relay resolution.

Reshaped rather than answered, and it has a new name: per-role divergence is shape A, per-instance is shape B, and the migration between them is thread 18. Leaning here is unchanged: per-role is enough, so do not build the keyed form. Conductor’s workstreams are all one kind of thing, a phase run, and the differences it wants per phase (askPolicy, model, gate) already live in the phase table the manager reads at dispatch, not in the relay door. Say it rather than leave it silent, though: Relay’s first issue is where the seam gets reserved or consciously closed, and its spec is silent on parent-versus-child divergence, which closes it by default. A seam closed by decision and one closed by silence cost the same today and very different amounts later. What being wrong costs: widening a flat relay? group to a keyed or resolver form, pre-1.0, no persisted-row migration implied. Cheap, which is what makes the restrained call a default rather than a gamble.
14 · Does the resume POC land as a path, or as a harness?

The Proof needs resume rather than restart (thread 6), so the work that proves it sits on the critical path rather than beside it. What that work leaves behind is not decided. It could land as a path later work can call — a real seam, carried forward, at the cost of having to get its shape right before anything has resumed once. Or it could land as a throwaway harness that establishes the behaviour and is then deleted, with the seam built afterwards against a known answer.

Not colour to bury at the end of a section. The two produce different plans: one puts the seam's design inside the Proof, the other puts it after — and the typed handle field on the task (section 6) is undesigned either way. It belongs to the parent resume issue, which is where the shape of the resume input is being settled in any case.

Which does the Proof need — a callable path, or a proof and a delete? Both ways of being wrong are the expensive kind. A throwaway that quietly becomes the path is the one this document keeps naming; a permanent seam designed before anything has resumed once is the other. Answered inside the resume issue it costs a paragraph. Answered after the Proof ships it costs a rewrite.
15 · Who a person actually addresses

Two shapes, and the design does not pick between them. The coordinator holds a serialized inbox and a person talks only to it, so there is one place to look and one queue to drain. Or a person addresses the epic session directly, and the coordinator seeds and reports without ever standing between you and the work.

The second has independent support, which is what makes this a real fork rather than a preference. Building the operator UI produced the same finding from the opposite direction: every flow is top-level, you communicate to it and you spawn it, and the old model hid everything behind one session — a run you can start and then cannot point at, which a UI either invents a second navigation concept for or leaves invisible. That is an argument against routing a person's attention through a proxy.

The working default is on the page: the epic session is the unit a person addresses, one inbox inside it, serialized; runs stay top-level and addressable rather than hidden; the coordinator seeds and reports and does not proxy answers (section 6). proposed This is pending the owner's sign-off, because it is a product call about where attention goes and not an implementation detail. What would change it: an epic whose runs ask often enough that one serialized inbox becomes the bottleneck.
16 · What keeps two epic sessions out of one claim pool

The design's worked example says epics partition by session, on one static board. It does not say what enforces that. The lab locks the opposite: each epic gets its own collection identity, derived from the epic, and states in as many words that a distinct boardId alone is not sufficient because it never reaches the ledger (labs/conductor/src/flow.ts). One collection id is one claim pool; the claim predicate tests status and deps and nothing else. Two epic sessions on one static board can therefore claim and settle each other's rows.

Folded in here because it is the same shape: topic or project scope for the collections a set of epics shares. Try it as an org-scoped parameterized collection before adding a storage scope type; whole-scope read cost decides whether that holds.

Does the partition live in the collection id, as the lab has it, or in something the board can enforce on a shared collection? The lab's answer works today and costs a collection per epic. What would change it: a case where epics must share a ledger — a cross-epic dependency, or a person wanting one list across all of them.
17 · Handle reuse on a board that spans sessions

Board rows are not same-parent by construction. A task collection takes session, user or org scope, and at user or org scope the ledger already spans every session the principal touches — which is exactly the scope Conductor's board runs at. So a row's stored session handle can point at a child of a different session, and reusing it grafts work onto a sibling conversation's lineage, where that conversation's shared resources then get written.

Half of this closed on its own. A { key } dispatch cannot land on somebody else's child at all: adoption validates the stored record's whole identity — flow, principal, tenant, org and parent session — and refuses key-occupied when any of them disagrees. What is left is the half this thread is actually about, reusing a handle read off a row: an { id } delivery checks the principal, the tenant, the org and the flow, and does not check whose child the session is.

Check the lineage before reusing a handle, or restrict reuse to session-scoped boards? The check is one comparison and does not restrict a board shape people already use, which is the recommendation on the design side. The restriction is simpler and takes away the scope Conductor picked deliberately, because a parked row has to outlive the session that opened it.
18 · What triggers the move from A to B

Shape A is one flow with sessions differing by role; shape B is a coordinator flow and an epic flow. B is the endpoint on the design's own test — two roles that accept different dispatches are two flows — and A ships first. The trigger is a single item: the child listing conjoins the parent's flow kind into its query as an authentication boundary, so under B a coordinator asking for its epic sessions gets an empty answer and the devtool breadcrumb goes dark. When that route gains per-child authorization, B is close to free here, because the other blocker — lineage-bucket collisions — never applied: the lab uses no lineage sharing at all.

A's weakness, stated rather than glossed: entries belong to the flow, not the session, so an epic session on the shared flow does accept the caller's seed. Under no-fallbacks that is not a routing accident to catch — it is a real entry on that flow. The guard has to be a check inside the entry reading the session's role, which is convention enforced by vigilance, the class of thing this whole design is trying to reduce. It disappears in B, where the split is structural.

Folded in, and now confirmed rather than predicted: the "per-worker" session policy does not hold across parents. It shipped keyed on the board and the seat, and the child derivation then hashes tenant, principal, parent session and lineage in front of that key — so two sessions draining one user-scoped board get two worker sessions from one policy. Narrow the contract to one session per parent, which is what the derivation already gives, or build a derivation that omits the parent — which needs its own owner, adoption rule and authorization check.

Not a decision to make now, and not one to lose either. What to watch for is the listing route gaining per-child authorization, because that is the whole gate. Until then A holds with a guard written by hand in one entry — and the cost of forgetting to write it is a seed accepted on a session that should not take one.
19 · Does a parked row hold its lease or release it

Parking covers two different waits. A row waiting on a person may wait overnight, and holding a lease across that is holding a claim nothing is working on. A row waiting on a child run is different: the work is in flight, and releasing the lease invites a second claimant onto it.

One thing is unverified and decides most of it: whether the substrate can release a lease without settling the row. If it cannot, hold is the only shape available and the question is moot until that changes.

Check the substrate first, then decide — this is a question with a cheap experiment in front of it, and answering it by argument is how a wrong assumption gets built on. If release is possible, the split is probably per-park-reason rather than global.
20 · Max-N of one phase at a time is not expressible

Three limits bound how much runs at once and they are easy to conflate: the board's concurrency is a worker pool across the whole board, maxPending bounds rows added while others are pending, and entry arbitration bounds competing dispatches on one key. None of them says “at most two implement runs”. Setting the board pool to two caps every assignee together; arbitration is a mutex per key, so max-1 falls out of a constant key with queue and max-2 needs a counting semaphore nothing has.

Folded in: notBefore on a task row. Without it, “wake me later and confirm it happened” has nowhere to live — the deferred half is an outbox row, and the confirmed half is a board row, and nothing joins them.

Worth knowing before anything leans on it: a spec that assumes per-phase max-N is proposing a counting semaphore, not using one. Whether that is worth building depends on whether the board pool is a good enough approximation, and for one epic at a time it probably is.
21 · The fifth block kind is deferred, not rejected

dispatcher ships as a handler factory this cycle, so the locked four kinds stand and no unstated exception is left behind. The three arguments for a fifth kind are not withdrawn: no shape-sniffing at the dispatch seam, a roster that shows statically which workers hand off, and a definition-time walk replacing the derived binding check. Two of the three survive the handler form intact, because the seam is reachable from the factory and from nothing an author writes.

The one that does not survive is legibility. The graph no longer says what the block does — devtool, traces and anything else rendering the block graph see handler, so inline-versus-handed-off is legible to the board through metadata and invisible to a reader. That is a real cost paid every time somebody reads a trace, in exchange for not amending a locked contract in a first cut.

Answered as written: dispatcher() shipped as a factory returning a handler, and the four kinds stand. The two arguments that survive survived — the seam is a symbol on the context that only the factory reaches, and defineFlow walks the block graph for addresses at definition time. Legibility is the cost, and it is now paid rather than predicted. Nothing forecloses the promotion: the factory is the same author-facing surface either way, so making it a kind later changes the engine and the graph, not the flows people wrote. What would trigger it: reading enough traces where handler is the wrong word to make the amendment cheaper than the confusion.
22 · Does the action route already deliver send semantics

Executing an action against an existing session id is a route that exists. Whether it already delivers what an internal send needs is not established: the input arriving as an item, arbitration on the session key, and the incarnation check that stops a stale request writing into a session that has moved on. If it does all three, the send verb is thinner than this page assumes — closer to a name for something already reachable.

Answered, and the answer is no. The internal path does not go through the action route at all: a public dispatch reads flow.actions and an internal one reads flow.internal.actions, and with no fallback between them the action route cannot reach an internal entry however it is addressed. Of the three properties, two were already there and are now shared — the dispatched request is an ordinary request, and the arbiter resolves its policy through the same keyed lookup as every other type. The third had to be built: the incarnation guard compares the recipient's lineage at acceptance against its lineage at run, and drops the delivery if the session was deleted and recreated in between. So the send was not thinner than this page assumed; it was one guard thicker.
23 · Per-adapter delivery

Where a dispatch physically travels is unresolved. In a Node host it is in-process — attached to the process rather than the originating web request, so a sender that has already returned does not take its dispatch with it. Under a queue-backed runtime it is a job, which is where surviving a restart comes from, and the two have different failure modes and different latencies.

The design does not address it. That is a deliberate omission rather than an oversight — addressing, arbitration and the entry lookup are all the same whichever way delivery goes — but it means the first real deployment picks the answer by default rather than by decision.

Still open, and narrower by one edge. What shipped refuses rather than guesses: a host that hands work to an external queue rejects a delivery addressed by id outright — external-dispatcher, decided before anything is enqueued — because the recipient's concurrency policy is not applied on the far side. A { key } child is unaffected and works on both. So the question is no longer “what happens on a queue-backed host” but the original one: which path does the first real deployment take, and is in-process allowed to be the only one for a while? In-process is enough for a single host and loses everything in flight on a restart.
The one-sentence version

Conductor is a meta-harness for our own SDLC, built on a substrate that already has the flow, the board, the detached runs and the parked task row — and its bet is that the session you talk to stays small, because the open questions live in an inbox rather than in its head.
