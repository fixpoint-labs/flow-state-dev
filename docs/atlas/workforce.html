Living design

A general harness on the same substrate

Workforce is the other intended FSD harness. Conductor is product-specific to software development. Workforce is general: a conventions layer so people get going on Layer 1 primitives without inventing their own opinions. The roadmap intends both. This cycle ships Conductor. This page exists so we do not over-build Conductor-only.

Sibling atlas: Conductor — this-cycle priority. This page triangulates; it does not ship.

01

What Workforce is

An open-source, vendor-agnostic harness built as opinions on FSD blocks. Not a coding product. Not this cycle. Not a D-n.

Today
a thin package

Named agents, a registry, and materialization into a block. One example uses it. That is the whole of the shipped surface.

Intended
layer 2 conventions

A file layout so people get going: knowledge on one side, workers on the other. Every folder is still a Layer 1 resource, skill, tool, or agent.

Eventually
a grok-bot-like surface

You talk to the engineering manager you already know. That identity lives on Engineering, has memory, and can be reached from more than one channel. It borrows the copy editor rather than owning one.

Not
this-cycle conductor

Does not ride Relay fire-and-forget or the harness-manager proof. Does not rewrite the objective. Conductor stays the priority.

02

Layer 1 vs Layer 2

Layer 1 has substrate opinions only. How you use them is up to you, which is why it is powerful and advanced-user-only. Layer 2 has opinions so people get going. Workforce was conceived as that layer.

A team’s knowledge is a collection with the team as its topic — that already works

The convention needs no new scope to exist. defineResourceCollection already takes a parameterized pattern — [team]/resources, addressed with { team: "engineering" } — or a wildcard prefix like teams/engineering/* (packages/core/src/types/collection-patterns.ts). That is enough to build the whole layout on today.

What an org-scoped collection does not give you is isolation: nothing stops one team’s worker reading another team’s instances. That is a security property, not a modeling blocker. A proper team scope may earn its place as a framework-level item later — section 8 — and nothing waits on it.

03

Persistent Agent

An Agent does not live on a session, a channel, or even a Flow. It is a persistent identity with its own memory, brought into any session. The session is a channel. The agent is who walks into it.

Do not read Conductor’s architect as this already existing

The Conductor atlas already says agents and sessions are not bound together, and that what a role knows is where its resources live. That is a Layer 1 reading, and it is true of scoped resources today. It is not a persistent-identity runtime. Agent still has no resources field and no scope. Org-scoped memory for a role is a design on a young surface, not a Workforce feature that shipped.

04

Teams, borrowing, channels

A team owns a working set, not a headcount. Its roster has a lead that holds the board and doers that claim its tasks. A specialist every team needs has no home team — it is borrowed. Channels are rooms; Relay is the one Layer 1 door between them, status in section 6. Proposed.

05

Eventual surface

Something you can talk to the way you talk to Grok Bot: an agent you already know, reachable from more than one place, remembering what it already knows. Open source. Vendor-agnostic. Built on blocks, so you replace any piece.

The package is Layer 2 sugar, not the harness

@flow-state-dev/workforce is documented as agent registry and materialization. CLAUDE.md still calls it “Layer 2 on orchestration.” That is the original conception. What landed is the first cut of the conventions — name a participant, look it up, turn it into a block — without the identity, the channels, or the surface. Read every “Workforce” claim in a Conductor discussion against this inventory, not against the intended harness.

08

Not this cycle

Held on purpose. The work that would make Workforce real is not on the Conductor spine, and it does not get a design on this page just because the thought exists.

This is not a ship, and it is not a D-n

Conductor is the cycle: Relay fire-and-forget, the harness-manager proof, the parked row. Workforce is a second intended harness so that cycle does not harden a coding-only substrate. Updating this atlas is the work. Implementing the harness is not.

Do not pull Workforce onto Relay + LAB-139

Relay is a Layer 1 door both products will want. Building it as Conductor’s question channel is correct for this cycle. Building Workforce channels on top of that spine this cycle is how a second product lands as a parasite of the first.

Which layer Conductor’s roles sit on stays Conductor’s thread

The Conductor atlas already holds this open (thread 11): adopt the workforce wrapper, or move “materialize a role as a block” down into orchestration. This page does not settle it. The inventory in section 7 is the evidence that thread is weighing — a thin, almost-unexercised wrapper — not a reason to start the harness.

Knowledge Hub stays held

The resources/ and skills/ folders in the section 2 tree are the knowledge-management half of the convention — what Engineering knows, or Marketing, scoped at org or team. That is not Knowledge Hub. Active-memory, process-the-inbox, a product for that knowledge, stays held. Not a section here, not a design for a held issue.

Team scope, if it comes, comes for security

A team topic on a collection is a naming boundary. It holds the layout and it enforces nothing: a worker that can read the org can read every team’s folder. Making that boundary real means a framework-level team scope, and the argument for one is security — not the convention, which has enough to build with now.

Not a blocker and not this cycle. Build on team-topicked collections; let the first case where one team’s knowledge genuinely must be unreadable by another be what buys the scope. Being wrong costs a migration of resource keys, pre-1.0, with no persisted-row change implied.
Named participant versus persistent identity

Today’s Agent is a definition you materialize. The intended Agent is an identity that persists. Growing the type to look like the second, before a product needs it, is how Layer 1 absorbs a Workforce opinion. Leave the type until a build that is actually staffing persistent identities has to say what field is missing.

When that build exists, the first question is still “is this a resource the agent brings, or a new field on Agent?” — and the cheaper answer is usually the resource.
The one-sentence version

Workforce is the general FSD harness: teams that own a working set — their knowledge and their roster — with shared specialists borrowed across them, on Layer 1 blocks. Eventually a surface where you talk to the engineering manager you already know. Today it is a thin registry. This cycle belongs to Conductor. Keep the substrate mute enough that the second harness is still possible.
