## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A support agent clicks "Build report", which calls the `buildReport` action on the `support` flow, then closes the tab right away. Does the report still get built, and what runs it once the request has returned?
   Answer: Yes. Calling the action on a queued app creates a request and a job on the Redis queue. A worker process takes the job and runs the same `buildReport` action against the same stores, writing the request's items there. The browser does not hold the work, so closing the tab changes nothing (facts section 4: bmq/worker.ts:393-420, rd:34).
2. What do you change in the page's code to send `buildReport` to the queue instead of running it in the web process, and what does `session.sendAction("buildReport", input)` resolve with, and when?
   Answer: Nothing changes in the call. The queue is the app's `worker: bullmqWorker({ connection })` setting on `createFlowState`, and actions have no background flag. The route answers 202 with `{ status: "in_progress", request: { id, ... } }` once the request is recorded and the job is on the queue. `sendAction` resolves with that body at that point, not when the report is finished (facts sections 0 item 8, 2, and 5: eng/routes/action-routes.ts:347-369, rx/hooks/useSession.ts:2313-2323).
3. While the worker builds the report, what does the agent's `useSession` page show, and where does that progress come from?
   Answer: `session.isStreaming` is true while the stream is attached, `session.items` fills as the worker's items arrive, `session.latestRequest` carries the request and its `in_progress` status, and `session.statusMessage` shows the latest status the action emitted. The stream is read from the shared stores the worker writes to, not from Redis, so the web process can show it even though another process runs the job (facts section 6: rx/hooks/useSession.ts:339,356-360,367, eng/routes/stream-routes.ts:5-8).
4. The team splits the app into a web container and a worker container. Which `mode` does each one use, and what happens if the worker is accidentally pointed at a different database from the web container? *(edge case)*
   Answer: The web container uses `dispatch-only` (it only enqueues) and the worker uses `worker-only` (it only consumes). The default, `colocated`, does both in one process. Both must reach the same stores, and nothing checks this. If they use different databases, jobs still enqueue and run, but the web process reads a store the worker never wrote to. The request stays `in_progress` with no error, even though the work finished somewhere else (facts section 3: eng/flowstate/types.ts:49-64, rd:60-64).
5. Someone deploys the web app but forgets to start any worker. What happens to the agent's "Build report" request? *(edge case)*
   Answer: The POST still gets its 202, because the job is on the queue. The request then waits as `in_progress` with nobody to take the job. If no worker claims it within `queuedGraceMs`, ten minutes by default, it is treated as lost and marked `interrupted` (facts section 4: eng/routes/createFlowApiRouter.ts:184-198, eng/flowstate/types.ts:270-279).
6. On its first attempt, `buildReport` hits a network error that can be retried, and meanwhile the agent's connection drops and the page reconnects. What does the agent see? *(edge case)*
   Answer: The job is tried again, with three attempts by default counting the first. Each new attempt numbers its events after the last stored one, so the stream reads as one run and does not restart at zero. Reconnecting needs no code: the client picks up after the last event it got (through `Last-Event-ID` or `starting_after`) and replays from the store. The page carries on where it left off (facts sections 4 and 6: bmq/retry.ts:203-211, bmq/worker.ts:341-353, eng/routes/stream-routes.ts:172-175, cl/client.ts:399-405).
