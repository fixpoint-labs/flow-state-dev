## What you hold fixed (answers Q1)

6. **One variable.** The coordination shape. The task suite, the executor model and the judge are the same for every subject (`bm:17`; `packages/fsdev/README.md:349`; `ad:1-14`; `sw:1-10`). **[page]**
7. **The model is forced onto every subject.** The engine replaces each model id a subject's generators name with one id, `subject.model ?? config.model`, so a pattern that names its own model still runs on yours (`run:48-64`, `:104-119`; `ct:65-71`). **[page: one sentence.]**
8. **Same worker in every pattern.** Where a pattern needs a caller-supplied worker, the adapters pass one shared single-shot generator (prompt "You are a capable problem-solver. Complete the assigned task accurately and completely.", output a string). Patterns that build their own agents (round-robin, debate, plan-and-execute) get the same `model` id instead (`sw:1-45`; `ad:1-14`). So the numbers compare coordination, not each pattern's best-tuned roster of specialist models. **[page: the limit, flat.]** `bm:120` agrees.
9. **Fixed shapes inside the shipped adapters.** Round-robin runs a three-worker roster named `alpha`, `beta`, `gamma`; debate runs `pro` ("argue in favor") against `con` ("argue against") plus a judge and synthesizer; routed-specialists runs a `researcher` and a `writer` (`ad:107-191`). **[ref]** A reader who needs a different roster builds a subject by hand (fact 22).
10. **Provider web search can be stripped.** `disableSearch: true` on the definition removes provider-native web search from every subject and the judge; default false. The shipped suite sets it, because its tasks are answerable from model knowledge. `fsdev benchmark --search` forces it back on (`ty:43-56`, `:191-197`; `cli:258`, `:146`; `suite:43-47`). **[page: one sentence, as a thing to hold fixed when your tasks need no live data.]** A subject that pins a concrete model instance instead of an id escapes the fixed model (`ty:49-55`). **[ref]**
11. **The judge sees only the task and the output.** It is handed the task prompt as "Input" and the output as "Output to Evaluate" (`run:150-158`, `:208-212`; `as:100-120`). It is never told which pattern produced the output. The criteria are the task's `rubric`. **[page]** `expected` on a task is passed to the judge too, when set (`as:109-117`; `ct:44-46`). **[ref]**
12. **The judge's score.** The judge scores each rubric criterion 0 to 1 and the cell's score is the mean of those (`as:17-27`, `:59-68`, default mapping `"mean"` `:132`). A cell "passes" at 0.5 or above (`as:49`, `:133`). The scorecard does not print the pass rate; `passRate` is in the JSON report (`ty:71-72`). **[ref]**
13. **The judge model should differ from the executor.** With `judgeModel` unset, or equal to `model`, the report carries a warning: "Judge model equals executor model ... self-preference bias is possible" (`run:96-102`; [test] `benchmark-run.test.ts:198-208`). The CLI writes each warning to stderr as `warning: <text>` (`cli:220-222`). **[page]**
14. **Repetitions.** `runs` defaults to 3 per (subject, task) (`run:86`; `ty:33`). `--runs <n>` overrides and must be a positive integer (`cli:71-77`, `:246`; [test] `packages/fsdev/test/benchmark-command.test.ts:95-98`). `concurrency` defaults to 3 cells at once (`run:87`; `ty:35`). **[page: runs; concurrency [ref].]**

## What the result compares (answers Q2)

15. **Subjects.** The things compared are subjects: each pattern you name, plus a baseline (`ct:51-72`). A baseline subject is `kind: "baseline"`; a pattern is `kind: "pattern"`. **[page: "subject" defined as "a pattern or the baseline", first use.]**
16. **The baseline.** One generator on the run model, with the prompt "You are a capable assistant. Answer the user's task directly, completely, and correctly.", no coordination. It is named `single-generator` and appended automatically unless `baseline: false` / `--no-baseline` (`idx:30-58`, `:96-107`, `:126-139`; `cli:193-203`; [test] `benchmark-run.test.ts:294-340`). **[page]** The shipped suite and the definition field default: `baseline` omitted means true at run time (`ty:176`; `cli:144`; [test] `benchmark-command.test.ts:75-83`). **[ref: the flag precedence.]**
17. **Delta vs baseline.** For each category and for `overall`: `deltaVsBaseline` = the subject's mean minus the primary baseline's mean in that bucket (`rep:174-182`; `ty:91-97`). Positive means the pattern outscored the single call. **[page]** The primary baseline is the baseline whose model equals the run model (`run:142-148`; `ty:114-119`). **[page only if cross-model is mentioned; else [ref].]**
18. **Credible.** `credible` is true only when `|delta| > 2 × the standard error of the difference of means` and both groups have at least 2 runs (`rep:183-195`; `ty:98-101`; [test] `benchmark-report.test.ts:65-98`, `:128-139`). A `no` means the gap may be noise; it does not mean the pattern lost. The kept page puts it as "no measurable difference" (`bm:107`). **[page]** More `runs` narrows the standard error, so a gap that is `no` at 3 runs can become `yes` at 10 (`rep:183-188`). **[page: one sentence.]**
19. **Errors count as zero.** A subject that throws on a cell scores 0 for that cell; the sweep continues (`run:228-231`; `rep:68-73`; [test] `benchmark-run.test.ts:210-233`, `benchmark-report.test.ts:112-126`). The `success` column shows `successful/total` so a low mean caused by failures is visible (`rep:269-271`). **[page: why `success` matters, one sentence.]**
20. **Cost columns.** `$/task` is estimated cost per cell, executor plus judge; `score/$` is mean divided by `$/task`; either prints `—` when no cost was recorded (`rep:259-275`; `ty:77-82`; [test] `benchmark-report.test.ts:170-196`). The estimate comes from a built-in pricing table; a model not in it estimates to $0, and with `--max-cost` set the run warns that the budget will not count it (`run:123-140`; [test] `benchmark-run.test.ts:250-262`). **[page: `$/task` and `score/$` one line each; the pricing-table warning is [ref].]**
21. **Where the result is only evidence.** The numbers apply to this task suite on this model; they do not rank patterns in general (`bm:120-122`; `apps/pattern-benchmark/README.md` "Caveats"). The 12-task shipped suite is a template, not a verdict. **[page: the limit, flat.]**

## Step 1: a task suite

22. **A task.** `{ id, category, prompt, rubric }`, with optional `expected` and `metadata` (`ct:36-49`). `id` is a stable identifier; `category` buckets the scorecard columns; `prompt` is the same text every subject receives (each adapter maps it onto its own input shape: `{ goal }` for most, `{ question }` for debate); `rubric` is a list of criteria the judge scores (`ct:36-49`; `ad:23-35`, `:133-153`). **[page]**
23. **Write rubric criteria one claim each.** The judge scores each criterion separately and averages, so a criterion that bundles two claims gives one blurry number (`as:17-27`, `:59-68`). `gd:61` gives the same advice. **[page]**
24. **Categories are free labels.** Any string is accepted (fact 2). The scorecard grows one column per category present in the tasks, in first-seen order, plus `overall` (`rep:125-134`, `:166`, `:242-244`). **[page]**
25. **`defineBenchmark`.** Returns the definition unchanged and throws `Benchmark "<name>" must define at least one task.` when `tasks` is empty or missing (`idx:109-117`; [test] `benchmark-run.test.ts:354-372`). Fields: `name`, `patterns`, `registry`, `subjects`, `baseline`, `baselineModels`, `tasks`, `model`, `judgeModel`, `scorers`, `runs`, `disableSearch` (`ty:162-198`). **[page: the ones the example sets; the rest [ref].]**
26. **The file contract.** `fsdev benchmark <file>` imports the file, takes its `default` export (or a named `benchmark` export), and requires an object with a `tasks` array. A missing or unloadable file exits `4`; a module with no such definition exits `2` with "Benchmark file must default-export a defineBenchmark(...) definition: <path>" (`cli:153-175`; `packages/fsdev/src/exit-codes.ts:14-20`; [test] `benchmark-command.test.ts:101-125`). A relative path resolves from the current directory (`cli:154-155`). **[page: default export; exit codes [ref].]**
27. **The shipped suite as a template.** `apps/pattern-benchmark/src/tasks.ts` has twelve tasks, three in each of the four categories, every one with a three-criterion rubric (`tasks:28-187`; [test] `suite.test.ts:9-32`). ## Step 3: read the table

39. **Formats.** `--format table | markdown | json`, default `table`; any other value exits `2` (`cli:97-103`, `:266`; [test] `benchmark-command.test.ts:85-93`). `markdown` renders the same two tables as Markdown, for pasting into a pull request; `json` is the whole `BenchmarkReport` (`rep:350-367`). **[page]**
40. **Where output goes.** Stdout by default. `--output <path>` writes the scorecard to a file instead, creating parent directories, and prints `Scorecard written to <path>` to stderr (`cli:224-234`). Warnings go to stderr either way (`cli:220-222`). **[page]**
41. **The grid.** Rows are subjects in the order run (patterns, then baselines); columns are categories in first-seen order, then `overall`; each cell is `mean±stddev` of the judge score, 0 to 1, to three decimals (`rep:229-232`, `:242-244`, `:331-347`). A cell prints `—` where a subject has no result in that category (`rep:229-231`). **[page]**
42. **The ranking.** Subjects sorted by `overall` mean, highest first, with the columns in fact 3 (`rep:165-201`, `:256-289`). **[page]** The rank and `Δ vs baseline` are read together with `credible`: a top rank whose `credible` is `no` is a tie with the baseline within the noise. **[page]**
43. **How to read it, in order.** (a) Look at `success`: a subject with failed cells scores zero on them (fact 19). (b) Look at `Δ vs baseline` and `credible` on the overall row. (c) Look at the category columns to see where the overall result comes from; a pattern can lose overall and win one category (`gd:134-139`). (d) Look at `$/task` against the delta: a gain that costs several times the baseline's `$/task` may not pay (`rep:259-263`). **[page: three or four sentences. (d) is the reader's judgement, not a framework rule.]**
44. **What the page can't promise.** A subject that wins here wins on the reader's tasks, on this model, at this `runs`. Three repetitions smooth some variance, not all (`gd:155-158`). **[page: one flat sentence.]**
45. **Report fields in JSON.** `model`, `judgeModel`, `runs`, `subjects`, `baselineSubjects`, `primaryBaseline`, `categories`, `stats`, `rankings`, `totalCostUsd`, `budgetExceeded`, `warnings`, `timing.totalMs` (`ty:105-134`). Each `stats` row: `mean`, `stddev`, `passRate`, `runs`, `successfulRuns`, `costUsd`, `costPerTaskUsd`, `meanLatencyMs`, `codeScores` (`ty:62-88`). **[ref]** `scorers` on a definition adds deterministic code scorers whose means land in `codeScores` (`ty:31`, `:85-87`; `run:219-226`). **[ref]**
46. **The in-code route.** `comparePatterns(registry, names, config)` resolves the names, appends the baseline and returns a `BenchmarkReport`; `renderScorecard(report, "table" | "markdown" | "json")` renders it (`idx:61-107`; `rep:350-367`). The registry is the first argument so `@flow-state-dev/testing` never imports `@flow-state-dev/patterns` (`idx:10-12`). **[ref: the recipe's example is `fsdev benchmark`.]**

## Revision round 2

- **Unit names.** A run is one subject on one task, once; the page counts 18 runs (3 x 2 x 3, fact 38) and keeps "cell" only for a scorecard table box (fact 41). Facts 34 and 19 say "cell" for the run unit in source terms; the page's word is "run".
- **Provider keys** are named for the task model and the judge model (fact 29).
- **Self-preference** is explained on the page: a judge tends to score its own model's output higher (fact 13).
- **Shared worker** is stated as observable behavior: where a pattern needs a worker, every pattern gets the same one, same model and prompt (fact 8).

## Revision round 3

- **Shared generator.** The page no longer says "worker". It says every pattern that hands the task to an inner generator gets the same one, same model and prompt, so the scorecard compares coordination shapes (fact 8).
- **Run count.** The page defines a run first (one subject on one task, once), then 3 x 2 x 3 = 18 runs, one judge call per run, several model calls per pattern run (fact 38).
- **stddev.** The page says a cell pools different tasks, so a wide stddev can come from uneven task difficulty, not only run-to-run noise (fact 5).
