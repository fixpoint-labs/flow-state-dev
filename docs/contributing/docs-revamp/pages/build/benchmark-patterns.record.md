## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk drafts replies with a single generator call. You want to know if `supervisor` or `debate` would write better replies on your own tickets. You set up a benchmark comparing the two. Across `supervisor`, `debate` and the extra row the run adds, what stays the same, and what is the one thing that varies?
   Answer: Only the coordination shape varies. The task suite, the executor model and the judge are the same for every subject (fact 6). The model is forced onto every subject: each model id a pattern's generators name is replaced with the run's model, so a pattern that names its own model still runs on yours (fact 7). Where a pattern needs a worker you supply, every pattern gets the same shared single-shot worker, so the numbers compare coordination, not each pattern's best-tuned roster (fact 8). Optionally, `disableSearch: true` takes provider web search away from every subject and the judge when your tasks need no live data (fact 10).
2. The ranking comes back with `debate` in first place, `Δ vs baseline` +0.04, and `credible` printed as `no`. What is the extra row it is compared against, what does the `no` tell you, and what could you do to get a firmer answer?
   Answer: The baseline, `single-generator`, is one generator on the run model with no coordination. The run adds it automatically (fact 16). `Δ vs baseline` is the subject's mean minus the baseline's mean, so positive means the pattern outscored the single call (fact 17). `credible: no` means the gap is within about two standard errors of the difference of means, so it may be noise. It does not mean `debate` lost. A top rank with `no` is a tie with the baseline within the noise (facts 18, 42). More `runs` (default 3) narrows the standard error, so a gap that is `no` at 3 runs can become `yes` at 10 (facts 14, 18).
3. You write four support-desk tasks for the suite: a refund dispute, a shipping delay, and two more. What does each task need, and how should you write its rubric so the score means something? Can you use your own category name, such as `refunds`?
   Answer: A task is `{ id, category, prompt, rubric }`. `id` is stable, `category` sets the scorecard column, `prompt` is the same text every subject receives, and `rubric` is the list of criteria the judge scores (fact 22). Write one claim per criterion, because the judge scores each criterion separately and averages them, so a bundled criterion gives one blurry number (facts 12, 23). Any string works as a category. The four built-in labels are only suggestions, and the scorecard grows one column per category it sees, plus `overall` (facts 2, 24). The file must default-export a `defineBenchmark(...)` definition with at least one task (facts 25, 26).
4. Your `supervisor` row has a much lower overall mean than you expected, and its `success` column reads `20/36`. What happened, and why does it matter when you read the mean? *(edge case)*
   Answer: 16 of the 36 cells failed. A subject that throws on a cell scores 0 for that cell, and the run keeps going (fact 19). The `success` column shows successful/total so you can see when a low mean comes from failures and not from bad answers. That is why you check `success` first, before you read the delta (facts 19, 43a). The 36 cells are 3 subjects × 4 tasks × 3 runs (fact 38).
5. You set `--max-cost 2` to cap spend. Halfway through, the running cost estimate reaches $2. What does the command do, and what do you get? *(edge case)*
   Answer: It stops scheduling new cells once the running estimate reaches the ceiling, prints a partial scorecard, and exits with code 1 (fact 34). Cost counts both executor and judge spend (fact 34). Cells already running finish, so the final total can go a little over the ceiling (fact 34, a Reference-level detail).
6. You leave `judgeModel` unset, or set it to the same model as the executor. The run still finishes, but what does it warn you about, where does the warning appear, and what does the judge see when it scores a reply? *(edge case)*
   Answer: The report carries a warning that the judge model equals the executor model, so self-preference bias is possible. The CLI writes it to stderr as `warning: <text>` (fact 13). Warnings go to stderr even when `--output` sends the scorecard to a file (fact 40). The judge sees only the task prompt and the output, scored against the task's rubric. It is never told which pattern wrote the reply (fact 11). The fix is a `judgeModel` that differs from `model`.
