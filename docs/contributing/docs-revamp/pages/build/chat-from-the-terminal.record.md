## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Yesterday you chatted with the support desk's `support` flow from the project directory, with no `fsdev.config.ts`. Today you want to pick that conversation up where it left off. What do you run, and where do you get the id?
   Answer: Run `fsdev chat support reply --session <id>` (or `-s <id>`) from the same directory. The id is on the opening line of every chat (`Chatting with support · reply (session sess_..., resumed).`). You can also get it from `/status` or `/session` with no argument, or from the DevTool's session list. No `fsdev` command lists sessions. Under discovery the session lives in `.fsdev/data/fsdev.db` in the working directory, so you have to resume from that directory (facts 14, 15, 21; cmd:313, cmd:47, ls:26-28).
2. The support desk now has an `fsdev.config.ts` whose `createFlowState` sets `flows` but no `stores`. You resume yesterday's session id with `--session`. The opening line says `resumed`, but the agent remembers nothing. Why? *(edge case)*
   Answer: With a config, chat uses the app's own stores. A `createFlowState` with no `stores` runs in memory, so nothing survived the restart. A missing id also isn't rejected: chat starts a new, empty session under that id and still prints `resumed`. A mistyped id behaves the same way. To resume after a restart you need directory discovery (SQLite in `.fsdev/data/fsdev.db`) or a config that sets a persistent store (Read-this-first 1 and 4; cmd:184-187, types.ts:170-172, cmd:267-268, cmd:310).
3. The project has several flows and no `chat.default`. You run `fsdev chat --session sess_123` without naming a flow. What happens, and what are the two ways to fix it? *(edge case)*
   Answer: It's an error (exit 2): `--session` needs a target bound at startup. One fix is to name the flow: `fsdev chat support reply --session sess_123`. The other is to start the chat, run `/use support`, then `/session sess_123`, which prints `Bound session: sess_123.` (facts 16, 17; cmd:289-295, cct:188-199, reg:149-155).
4. A teammate started a support session as `--user maya`. You resume the same session id while running as `devuser`, the default. What does chat do with your message? *(edge case)*
   Answer: Before the first turn, chat compares who the session belongs to with who this turn runs as. Here they differ, so it refuses. The message says the session belongs to user maya in her organization, and that nothing was written. Chat then rotates to a fresh session (`Rotated to a fresh session (<new id>); resend to continue.`) and that turn fails. A session keeps the user and organization it was created with. To resume it, run as that same user and organization, with the same `--user`/`--org` or the same resolver result (fact 19; pr:188-203, loop:176-184).
5. Halfway through a support chat you want to try the `billing` flow, then come back to the support conversation. How do you switch, and is the support conversation still there when you return?
   Answer: `/targets` lists every `flow · action` and marks the current one with `*`. `/use billing` switches; add the action if the flow has more than one. Each flow has its own session within a run. `/use support` brings you back to the original support session with its history, and the line reads `Now chatting with support · reply (session <id>, resumed).`. In that line, `resumed` means resumed within this run. History from one flow never reaches the other. Switching doesn't change who you are: who each turn runs as is asked again per turn, using the new flow's resolver (facts 25-27, 29; reg:64-105, st:292-298, cct:90-105).
6. You run `/use` on a flow whose action takes `{ ticket }`, not `{ message }`, and type a message. Separately, you try `/session <id>` with an id that belongs to the `support` flow while you're bound to `billing`. What happens in each case, and does the chat stay open? *(edge case)*
   Answer: In the first case the turn fails with the validation error plus `That target isn't chat-shaped (its action rejected { message }). Pick another with /use, or /targets to list them.` The session stays open. In the second case, `/session` prints `Session <id> belongs to flow "support", not "billing".` and leaves the current session unchanged. A session belongs to one flow. The same mismatch passed with `--session` at startup ends the command instead (facts 10, 18; turn:337-343, cct:179-186, reg:151-152, cmd:305-307).
