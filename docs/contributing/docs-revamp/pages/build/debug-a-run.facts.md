## Step 1: Open the DevTool

14. **Install.** `pnpm add -D @flow-state-dev/fsdev @flow-state-dev/devtool --allow-build=better-sqlite3`. The CLI's default store is SQLite and pnpm 10 builds the native module only when allowed; `--allow-build` needs pnpm 10.4 or later, pnpm 9 leaves the flag off, npm, yarn and bun need no flag. `su:12-20`. `@flow-state-dev/devtool` is an optional peer of the CLI that supplies the pre-built UI assets (`fsdr:180`, `fsdr:543`). **[page, one line; flags are `reference/cli`]**
15. **Run it.** `pnpm fsdev dev` from the project root. It starts one HTTP server that routes `/api/flows/*` to the flow API and serves the DevTool UI for everything else, and opens the browser. `ov:21-37`, `su:62-73`; `dev:610-623`. Default port `4200` (`dev:130`, `:169`), `--port` changes it, `--no-open` skips the browser (`dev:140`). **[page]**
16. **What it prints.** Four lines on stderr: `DevTool server running at <url>`, `Flows:  <ids joined by ", ">`, `API:    <url>/api/flows`, `Data:   <path> (SQLite)` (`dev:610-619`; `su:64-70` shows the same shape with `Data:   .fsdev/data/fsdev.db (SQLite)`, and the `dataLine` is `.fsdev/data/fsdev.db (SQLite)` at `packages/fsdev/src/local-store.ts:78`). The `Flows:` line lists flow ids; for a collection kind each copy has its own id (`dev:407`). **[page: the reader's check that step 1 worked is that the flow's name appears on the `Flows:` line.]**
17. **Where it finds flows.** `src/flows/` and `flows/` by convention, same as `fsdev run`; `--flow-dir <path>` (repeatable) replaces that discovery. `ov:23-27`, `su:75-82`; `dev:135`. With none found, it exits with `No flows found. Searched: ...` and names `src/flows/` or `flows/` or `--flow-dir` (`dev:392-397`). **[page, one sentence; ref for the exit code]**
18. **With an `fsdev.config.ts`, the config wins.** The stores and flows come from the app's wiring, not the local default (`su:130`; `dev:396-420`). The tutorial's app has an `fsdev.config.ts` (`user-docs.md` layout). **[open question for the page plan: the layout lists `fsdev.config.ts` as "the app: its kits, flows and stores", so the tutorial's reader probably runs the config path. ## Stored parts: who owns it, who can see it, where it is stored, how many

The DevTool is a viewer. What it stores is small; what it shows is stored by the framework. The four questions, for each part.

88. **Sessions, requests, items and traces the DevTool shows.** *Owns:* the flow instance that ran them, under the user that started them (`ov:85`). *Sees:* only that user's sessions; the DevTool acts as one user, `devuser` unless config or the Settings sheet says otherwise (facts 29). *Stored:* by the app's stores; with no config, `.fsdev/data/fsdev.db` (SQLite) relative to the working directory, shared with `fsdev run` and `fsdev chat` (`su:128`; `local-store.ts:62-78`); `--store filesystem` keeps JSON files under `.fsdev/data` instead and is single-process (`su:130`). *How many:* as many as were made; a session holds many requests; a request holds many items. The trace events of a request are kept for the most recent requests only (fact 3 for the numbers) and are not removed when the request record is (`tc:44-50`, `[ref]`).
89. **Suspension records.** *Owns:* the flow instance and request that suspended (`suspensions-view.tsx:209-216`). *Sees:* the user whose session it is (`ov:85`); a record shows in the Suspensions tab of its session. *Stored:* the `suspensions` store beside the other stores (`packages/engine/src/stores/index.ts:201`, `:256`; SQLite: `packages/store-sqlite/src/registry.ts:21`). *How many:* one per pause; a request can pause more than once. Resolving one does not delete it; it stays, with `approved` or `rejected` (`suspensions-view.tsx:336-340`).
90. **Resource state shown in the Resources panel.** *Owns:* the resource's scope (session, user or org) (`dvc:10-30`). *Sees:* the panel shows the full state; an app's client sees only what the resource's `client` config allows; secret fields never leave the server (fact 60). *Stored:* the app's resource-state store, the same SQLite file in the default setup. *How many:* by scope; a session-scoped resource has one cell per session, a user-scoped one per user, an org-scoped one per org (`dvc:10-30`; not restated by this page). [ref `reference/resources`]
91. **Browser-side settings, kept only in that browser's `localStorage`.** *Owns:* the browser profile. *Sees:* whoever uses that browser; never sent to the server. *Where:* `fsd-devtool-theme` (theme); `fsd.devtool.userId` (the user the DevTool acts as, when config did not set one); `fsd.devtool.activeSession.<base url>|<user>|<flow id>` (the last session per instance); `fsd.devtool.lastAction.<flow id>` (the last action chosen); `fsd.devtool.debugMode`; `fsd.devtool.traceItemsVisible` (`dt/hooks/use-devtool-theme.ts:16`; `dt/config.ts:23-28`, `:63-90`, `:101-130`, `:156-181`; `dt/context/debug-context.tsx:23`). *How many:* one value per key; one session hint per base URL, user and instance. **The bearer token is not stored here:** it is held in memory for the visit and is never written to `localStorage` (`config.ts:12-16`, `:75-77`; `ov:29`, `su:118`). A link you share opens in whatever theme the other person last picked (`ov:31`). [page: two sentences; the key names are not for the page.]
92. **`devtool` in `fsdev.config.ts`.** *Owns:* the app. *Sees:* the config's author. *Where:* the config file; `fsdev dev` injects its `userId` and `bearerToken` into the loopback page it serves as a global; nothing else reads it (`su:100-118`; `dt/config.ts:36-49`; `dev:*` injection). *How many:* one block per app. [ref `reference/configuration`; not on this page.]
