## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support-desk flow's `reply` action failed. You open the Trace tab, find the `handleTicket` request, and click the red `draftReply` row. Where do you see what `draftReply` received and what it returned?
   Answer: In the block detail panel on the right. The `Input` section shows the value the block was invoked with, and it is open by default because the block failed. `Output` is there too, closed by default, and `Connected Input` shows the value a connector handed the block. The row in the Trace tab also has a one-line `in <preview> out <preview>` summary, with the full value on hover. Facts 6, 43, 44; answer key Q1.
2. `draftReply` wrote an odd reply. You want to know exactly what the model was told on that turn: the instructions, the customer's message, and which model and tools it had. Where do you look, and when might that information be missing?
   Answer: Open `draftReply`'s block detail. `Prompt` shows the resolved prompt string ("You answer customer support messages. Be brief and specific."). `User Message` shows what was sent this turn, the string it was handed. `History (n)` shows the earlier conversation sent with it, and `Resolved Config` shows the `Model` and `Tools`. The data is captured unless `FSDEV_TRACE_OBSERVABILITY` is off. It is on by default outside production, so a run in production mode may not carry the prompt. Facts 7, 44, 45; answer key Q2.
3. You wrote `.step(cleanMessage).step(draftReply)` and TypeScript accepted it, but the run fails. Which row is red, what does its Error card tell you, and what do you change? *(edge case)*
   Answer: `clean-message` completed and `draft-reply` failed, so its row is red. The Error card shows a plain input-check message of the form `Block "draft-reply" input validation failed at ...`, with no code line under it. Its Input section, already open, shows that `draftReply` got the object `{ text, truncated }` when its `inputSchema` is `z.string()`. The step is missing its connector. The fix is `.step(cleanMessage).step((cleaned) => cleaned.text, draftReply)`. Then send the same action again from the action bar. Facts 10, 11, 12, 51.
4. You make the failing run from the terminal with `fsdev run` while `fsdev dev` is already open in your browser, but the session isn't in the navigator. A teammate's session doesn't show up either. Why, and how do you get your terminal run to appear? *(edge case)*
   Answer: With no config, `fsdev run` and `fsdev dev` write the same SQLite file as the same user, `devuser`, so your run belongs in the list. A running `fsdev dev` isn't told about writes as they happen, though. Reload the page or click `Refresh sessions` and it appears. The DevTool acts as one user and lists only that user's sessions, so a session another user created is not shown. Facts 29, 30.
5. You add an approval step before the reply is sent. A run is now waiting on approval. Can you resolve it from the DevTool, and what happens to the run once you do?
   Answer: Yes. The request's status is `suspended`, which means it is held, not failed. Open the Suspensions tab, where the pending row is highlighted, and select it. Optionally type resume data as JSON in `Resume data (JSON)`, then click `Approve` or `Reject`. The same request carries on under its own id. The panel re-attaches the live stream, so the rest of its items arrive without a reload, followed by a `suspension_resume` audit item. Facts 64-68, 73; answer key Q3.
6. While approving the paused run, you type resume data that isn't valid JSON. Later you open a suspension that someone already approved. What does the DevTool do in each case? *(edge case)*
   Answer: With invalid JSON, the panel shows `Resume data is not valid JSON.` and sends nothing. A suspension that is already resolved is read-only: it reads `This suspension is already resolved.` and has no Approve or Reject controls. The record stays in the list with its `approved` or `rejected` status, and resolving it does not delete it. A resolve the server rejects shows its error inline under the textarea. Facts 68, 69, 70, 76, 89.

- With `FSDEV_TRACE_OBSERVABILITY` off, "block rows are recorded without a prompt, messages or history." Untrue: With it off, the live block row is not built at all. Rows are not emitted when a block starts, and failed, suspended and transient blocks get no row. The only rows written are lean rows for blocks that completed, holding identity, output, model usage and duration, with no input, prompt, messages or history. So a failed block would have no Trace row to open. - Reference row 1: If it exits with `No flows found`, your flows are not in `src/flows/` or `flows/`, "the two places it looks." Untrue: After those two, discovery also scans monorepo subdirectories (`packages/*`, `examples/*`, `apps/*`, `labs/*`) for `src/flows/` and `flows/`. With `--flow-dir` it searches only the directories given. The `No flows found` message prints the searched directories. (/home/user/flow-state-dev/packages/fsdev/src/resolve-flow.ts:64-71; message at /home/user/flow-state-dev/packages/fsdev/src/commands/dev.ts:393-396) The row is recorded corrected.
- Reference row 2: The DevTool acts as one user, `devuser` unless you configure another, "the same user `fsdev run` writes as." Untrue: `fsdev run` defaults to the user the app's resolver returns, and falls back to `devuser` only if the app has no resolver or `--org` is passed. `--user` overrides it. With a config on a non-loopback host it forces `FSDEV_DEBUG_ENDPOINTS=0`.
