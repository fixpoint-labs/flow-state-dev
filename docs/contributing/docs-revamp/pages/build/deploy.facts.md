## 2. Does serverless change your flows? (answers Q2)

The flow does not change. Five things around it do. Each is a place a first deploy to Vercel or Lambda goes wrong.

1. **The mount file.** A route file (`createVercelNextHandler`, `createNextHandler`) or a handler export (`createLambdaHandler`) takes the place of `serve()` or `fsdev serve`. Section 1. [page]
2. **A POST that returns before the work is done.** The browser path (`useSession.sendAction`) sends every action with `stream: true`, which asks the server to return the event stream from the POST response itself, so the run and its stream stay on one function instance. `rx:2260-2273` (comment: "On serverless (Vercel), this returns the SSE stream directly from the POST response — keeping action execution and event delivery on the same function instance"); `act:346-361`. The server answers the POST with HTTP 202 and the request's id instead when the caller did not ask for a stream, and also when a job queue runs the action (`runsExternally`: no live stream is created); the client then follows the request over `GET .../requests/:id/stream`. `act:366-385`; `host:957-967`; `rx:2315-2323`. **[test]** `packages/engine/test` (read, not run): no single test covers the 202 for a queued run; the claim is from the code comment at `host:957-967`. A plain `fsdev run` or `createClient(...).flow("support").send("reply", input)` without `stream: true` gets the 202: `cl:929-940`. [page: "the browser's send keeps the POST open and streams from it; any other caller gets a 202 and follows the request"; mechanism [ref]]
3. **Work that continues after the response.** On a 202, the run carries on after the response has been sent. A serverless host can freeze the function once the response is out, and the run is lost mid-flight. The fix is a `createFlowState` option, `onBackgroundWork`, given the platform's post-response primitive: on Vercel, `onBackgroundWork: (promise) => after(() => promise)` with `after` from `next/server`. `fst:242-250`; `vc/next.ts:8-12`; `nxs:120`; `oldv:151`. It is a `createFlowState` option, not a handler option, because the router is built inside `createFlowState` (`fst:242-250`). The page states: "on a serverless host, tell the app how to keep the function alive after the reply". No Lambda equivalent exists in the repo (`rec` lambda sheet Q1.14). [page, Vercel only; the Lambda gap is a limit the page does not need to state]
4. **The clock.** On a long-lived process the built-in local cron ticks each minute in any process that builds the router, so schedules run with no extra setup (`fst:420-427`, the `scheduler` option). On Vercel no process stays up, so the app takes `vercelScheduler()` from `@flow-state-dev/vercel`, passed to `createFlowState({ scheduler })` and mounted as the route one Vercel Cron entry calls; it authenticates the call with `Authorization: Bearer <CRON_SECRET>` (`vc/scheduler.ts:1-21,27-31`; **[test]** `vcT/scheduler.test.ts`). `scheduler: false` means nothing fires the tick (`fst:427`). [page: one sentence, "schedules need something to wake a serverless app"; the recipe is B-16 `schedules/vercel-cron` and [ref] `reference/schedules`]
5. **The disk.** A Vercel function's disk does not last between requests. On Vercel (`VERCEL` set by the platform) the adapter tells the router so, and an attachment upload to a blob store that keeps bytes on the host is refused with HTTP 501 `{ error: "attachments_unavailable" }`; a hosted blob store is unaffected, and off Vercel a local blob store takes uploads. `vc/handler.ts:33-45`; **[test]** `vcT/handler.test.ts:25-50`. [ref]: one clause at most; attachments are not on this page's path.
6. **Startup work.** `detectInterruptedOnStartup` (default true) runs a check at start for requests an earlier run left in progress; on serverless it can use up the Postgres connection pool at cold start, and `false` skips it. `fst:253-257`; `oldv:150`. The cost of `false`: a request abandoned by a stopped process is not marked `interrupted` at start, and the timer-based sweeper does not reliably cover a serverless host; the recovery route is `POST /api/flows/users/:userId/check-interrupted`, called from a scheduled route. `oldv:150`; `cr:36-41`; route exists `packages/engine/src/routes/router.ts:112`. [ref]: the Vercel recipe (`rec` vercel sheet Q2.8). The page does not state this one.

- What does not change: the flow's blocks, actions, state, resources and the client code. A client built for a Node server works against a serverless one with the same `apiPath`. `ha:47-57,80`; `ha:9`. [page]
- A serverless host serves no live push socket: `GET /api/flows/capabilities` reports `push: null` and `POST /api/flows/users/:userId/stream` answers 404 `{ error: "This host serves no push" }` on `createServerApp` (so Lambda) by default, and `serve()` sets `servesPush` when it serves push (`node/app.ts:37-43,150-160`). A client reads on its timer instead. **[ref]** `rec` lambda sheet Q1.7; not on this page.
- **[verify]** Whether `createNextHandler` (non-Vercel Next) serves push: `nx` calls `getRouter` and the guard only; no push route is mounted by it. Do not state anything about push on Next.

## 3. Long requests and streaming (step 2) (answers Q1)

- **The wire.** A call to an action answers 202 with `{ status: "in_progress", request: { id, flowKind, flowId, actionName, status }, session? }`, and the client follows the request on a Server-Sent Events stream; or the POST itself carries the stream when the caller sent `Accept: text/event-stream` (section 2, item 2). `act:346-385`; `cl:929-940`. [page]
- **Heartbeats.** The engine writes a `: ping` comment frame on every live and GET-attach SSE stream, default every 15 s (`DEFAULT_SSE_HEARTBEAT_MS = 15_000`, `packages/engine/src/routes/http-handlers.ts:212`). Change it with `createFlowState({ defaultSseHeartbeatMs })` (`fst:298`) or per flow with `defineFlow({ request: { sseHeartbeatMs } })` (`packages/core/src/types/flow.ts`, the "SSE wire-level heartbeat interval" option at `flow.ts:456`; `stream-routes.ts:109-111`); `0` disables. `cr:27` ("NAT and proxy idle timeouts stop closing the connection"). [page: "the server pings every 15 seconds so an idle proxy does not close the stream"; the option is [ref]]
- **Client and run are separate.** A request keeps running on the server when the browser's connection ends; the stream is a view onto it, and a client that reconnects picks up after the last event it saw. The engine deliberately passes no HTTP abort signal into the run, so a closed tab does not cancel it: `act:185-191`; `cr:7-9`; `docs-revamp/pages/concepts/sessions-items-and-streaming.facts.md:157-158` (sequence numbers, `Last-Event-ID`, `starting_after`). Cancelling is an explicit call: `POST /api/flows/:flowKind/requests/:requestId/abort` answers 204 when the run is in this process, 202 when the stop was recorded for the process running it, 409 when the request is already finished. `abr:37-41`; `packages/engine/src/routes/router.ts:205-207`. [page, **answers Q1**: "the run, not the tab, is what a host must keep alive"; the abort codes are [ref]]
- **Buffering is the way a stream fails.** If anything between the server and the client buffers the response, tokens arrive in bursts or all at the end. `old:30-38` lists the usual causes (a reverse proxy, a CDN, a serverless timeout, Next.js caching a route). The layer in front of the server has to be told not to buffer an event stream. [page]
  - The framework sets `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no` on the inline POST stream (`act:351-361`) and, on Vercel, on every event-stream response (`vc/handler.ts:17-26,77-86`; **[test]** `vcT/handler.test.ts:127-145`). `createNextHandler` adds no Vercel headers (`nx:1-9`); the route file for Next has to export `dynamic = "force-dynamic"` or Next may cache the route (`hc` route file, comment). [ref]: the route-segment config is the Vercel recipe (`rec` vercel sheet Q2.2-Q2.3).
  - Behind nginx: `proxy_buffering off`, `proxy_cache off`, `proxy_http_version 1.1`, and a long `proxy_read_timeout`, with `X-Accel-Buffering: no` also added (`oldd:280-324`). Railway's own proxy handles SSE; a custom domain behind another proxy (Cloudflare and the like) must not buffer it (`oldr:293`). [ref]: B-09 and B-10. The page names "a reverse proxy in front: switch buffering off for the API path" and links Docker.
  - Lambda: a Function URL has to use invoke mode `RESPONSE_STREAM`; otherwise the whole response is held and the events arrive together after the run ends (`node/aws-lambda.ts:5-8,33`; `oldl:52-61,123`). An API Gateway stage in front can re-buffer, so call the Function URL directly (`oldl:135`; **[verify]** AWS behaviour). [ref]: B-11.
- **How long a request can run is the host's decision, not the framework's.** No `createFlowState` or flow option caps a run's length that I found (**[verify]**: absence of a setting, from a read of `fst` and `packages/core/src/types/flow.ts`; the one timeout there, `ToolsConfig.defaults.timeoutMs` at `flow.ts:93`, is per tool call). What bounds a run is the platform:
  - A long-lived process (`serve`, `fsdev serve`) holds a run for as long as the process lives. A `SIGTERM` gives in-flight requests the 10 s grace window and then closes the connections; `dispose()` waits up to 30 s for detached work in this process by default (`dispatchDrainTimeoutMs`, `fst:260-270`; `node/serve.ts:93,146`; `old:100,119` for a supervisor's `kill_timeout`). [page]
  - Vercel: the route file sets `export const maxDuration = 300` and the plan's limit wins if lower. A flow that outruns the limit is cut off. `oldv:43,321`; `packages/vercel/README.md:45,125`. The old page's advice for flows that "consistently exceed the timeout" is Railway or Docker (`oldv:326-331`). [page: "a function has a maximum duration; the platform sets it". No plan numbers, section 0 item 7.]
  - Lambda: the function's own timeout bounds the run and bills until the run ends or the timeout fires; a client that disconnects does not stop the function (`oldl:70-72`, platform behaviour, **[verify]**). A reply that outlives the timeout is cut off, so a flow that streams for minutes belongs on a long-lived host (`oldl:139`). [page: the same clause as Vercel; do not name the number]
- **Which host if a request can run ten minutes (the answer to Q1).** Three honest answers, each from the code above:
  1. A long-lived process, because nothing in the framework ends a run and the run does not depend on the connection (`act:185-191`, `serve` above). The recipes are B-09 (Railway), B-10 (Docker). [page]
  2. A queue with its own processing process: the POST returns 202 at once, the run is a job in Redis worked by another process against the same stores, and a closed tab does not stop it. `@flow-state-dev/bullmq` (`bmq/README.md:3`, `bmq/src/flowstate-adapter.ts:76`); `createFlowState({ jobQueue })` (`fst:409-418`); `c16:50-67` ("A ten-minute report is the case for it. The user closes the tab and the job carries on."). The processing process is a long-lived process, so a queue takes the long run off the web host and not off the need for a long-lived host. `fst:55-67` (`enqueue-only` is the web process, `process-only` a dedicated processing container). [page; the setup is B-19 `build/background-jobs-bullmq`, the options are [ref] `reference/background-work`]
  3. A serverless function only if the platform's limit is longer than the run, and, on Vercel, with the keep-alive of section 2, item 3 for a 202. [page: as the exception]
  - **[verify]** Whether `enqueue-only` on a serverless web tier works with a Redis connection per function instance. `bmq/README.md:3` describes the adapter as "for long-lived self-hosted deployments", and no test or recipe runs a serverless web tier with a queue. Do not say a serverless web tier plus a queue works; say the queue's processing process is long-lived.
- A run in a process that stops is not lost silently. After a restart the run shows up as that conversation's interrupted turn; Continue finishes the same request id and Discard ends it. `goals/continue-interrupted-run/after-a-restart/goal.md:3-9` (SQLite store on disk, `SIGKILL`, a fresh host; with the default 60 s stale threshold the turn appears about a minute after the restart, goal line 15). `cr:28,59-62` (the sweeper runs every 30 s, threshold 60 s: `fst:300-304`). [page: one sentence under "what a restart does"; the thresholds and routes are [ref] `reference/runtime`]
- A run that reaches a stop for a user's approval is held across a restart only on a store that persists; on memory it fails at the stop. `fst:340-354`; C-14 draft "A run that is waiting". [ref]: C-15; the page names it under the store section in one clause or not at all.

## 4. Where the store lives (step 3) (answers Q3)

- The store is where the app keeps what it saves: sessions, state, resources, requests, paused runs. `fst:202`; C-14. [page: one sentence; C-14 owns the model]
- `stores` takes three shapes: omitted (memory, the default), one adapter, or named profiles for an app that picks a store per environment (`defaultProfile`, `FSD_ENV`). `fst:202-212`.
