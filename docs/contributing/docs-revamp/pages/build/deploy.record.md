## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's buildReport action takes ten minutes. Where should acme host the app so the report finishes, and why there?
   Answer: On a long-lived process: serve() or fsdev serve on Railway, Docker or a VPS (recipes B-09, B-10). Nothing in the framework caps how long a run lasts; the host decides. A long-lived process keeps a run going for as long as the process lives, and the run does not depend on the browser's connection (act:185-191; facts section 3). The second honest answer is a queue with its own processing process (@flow-state-dev/bullmq, createFlowState({ jobQueue }), B-19). The POST returns 202 at once and the job runs in another process against the same stores. That processing process is itself long-lived, so the queue moves the long run off the web host but does not remove the need for a long-lived host (fst:55-67; c16:50-67). A serverless function fits only if the platform's maximum duration (maxDuration on Vercel, the function timeout on Lambda) is longer than the run. On Vercel a 202 run also needs onBackgroundWork (facts section 3, Q1 answers 1-3).
2. Acme moves the support desk from Railway to Vercel. What changes in the support flow's code, and what changes around it?
   Answer: The flow does not change: its blocks, actions, state, resources and the client code stay the same, and the client keeps the same apiPath (ha:9,47-57,80; facts section 2). The things around it do change. (1) The mount file: a route file with createVercelNextHandler from @flow-state-dev/vercel/next takes the place of serve(). (2) Work after a 202 response: pass onBackgroundWork: (promise) => after(() => promise) to createFlowState, or the platform can freeze the function in the middle of the run (fst:242-250). (3) The store must be a database the function reaches over the network, for example vercelPostgresStores(), because memory and SQLite do not last. (4) Schedules need something to wake the app: vercelScheduler() called by a Vercel Cron entry (vc/scheduler.ts). (5) The function has a maximum duration (maxDuration) that the platform's plan limit caps.
3. What does the support desk have to keep outside its own process, and what happens if it uses the default store on a serverless host?
   Answer: Three things. First, the store: Alice's sessions, state, resources, requests and paused runs. Second, if jobQueue is set, the queued jobs, which live in Redis. Third, the connection secrets and model keys (FSD_DB_URL or DATABASE_URL, REDIS_URL, OPENAI_API_KEY), which live in the host's own environment settings and never in the repo or the image (facts section 4, the four-questions table). If stores is omitted, the app runs in memory, and nothing survives a restart. Startup says so, and under NODE_ENV=production it warns once (createFlowState.ts:1026-1040). On a serverless host every cold start is a restart, and the host decides when those happen, so requests that land on different instances lose data. Serverless needs a network database such as Postgres (facts section 4).
4. On the first deploy to Vercel, every call to the support flow returns HTTP 500 with { "error": "Internal server error" }. Running locally worked. What is wrong, and how is it fixed? *(edge case)*
   Answer: The support flow has no authentication.resolvePrincipal. A network-facing host refuses to trust a userId sent by the caller, so it answers every call with 500 and a generic body. It logs the cause once: 'Refusing to serve: flow "support" has no authentication configured ...' (nauth:41-58,72-86; vcT/network-auth.test.ts). This happens on the Vercel, Next and Lambda handlers whatever NODE_ENV says. The fix is to configure authentication.resolvePrincipal on the flow (C-17). allowUnauthenticated: true overrides the check. On serve() or fsdev serve the same rule applies at startup instead: on any host other than loopback the server refuses to start, and fsdev serve exits 3 (node/bind-guard.ts:84-90).
5. Five minutes into buildReport, Alice closes her tab. Later the Railway container restarts while another report is running. What happens to each run? *(edge case)*
   Answer: Closing the tab does not stop the run. The run continues on the server, because the stream is only a view onto it and no HTTP abort signal reaches the run. When Alice reconnects she picks up after the last event she saw. Cancelling takes an explicit abort call (act:185-191; cr:7-9; abr:37-41). A run whose process stops is not lost silently. After the restart it shows up as that conversation's interrupted turn, about a minute later with the default 60 s stale threshold. Continue finishes the same request and Discard ends it. This needs a store that persists across the restart, such as SQLite on a volume or Postgres (goals/continue-interrupted-run/after-a-restart/goal.md:3-15; cr:28,59-62).
6. The support desk runs on Railway with SQLite. Traffic grows and acme adds a second replica. What breaks, and what should they use instead? *(edge case)*
   Answer: SQLite is for one process on a disk that lasts. Only one process should write the file, so it supports one replica (sq/README.md:81; oldr:275-281; oldd:403). The file also has to sit on a volume, not on the container's own filesystem, and its folder must exist before the store opens. A second replica needs a store that several processes can share: Postgres, through postgresStores({ connectionString }) from @flow-state-dev/store-postgres. It reads the connection string from connectionString, then FSD_DB_URL, then DATABASE_URL (pg/README.md:321-333; pg/src/registry.ts:129-150). Memory would not help either, because each process has its own (stx:271-282).
