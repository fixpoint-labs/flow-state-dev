## Q1: What must the image contain?

4. **Node 22 or later.** `@flow-state-dev/fsdev` and `@flow-state-dev/store-sqlite` declare `engines.node: ">=22"` (`packages/fsdev/package.json:57-59`; `packages/store-sqlite/package.json:59-61`; `packages/node/package.json:70`). The old page uses `node:22-slim` (`old:26`, `old:43`). **[page]**
5. **The app's `fsdev.config.ts` is what `fsdev serve` runs, and it must be committed and in the image.** `fsdev serve` "requires a committed `fsdev.config.*` that default-exports a FlowState; without one it errors (no directory discovery, no `--flow-dir`, no `--no-config`)" (`fr:184`). It searches the working directory only, for `fsdev.config.ts`, `.mts`, `.js`, `.mjs` in that order, or takes `--config <path>` (`packages/fsdev/src/load-config.ts:20-26`, config search is cwd-only at `:32`, `:75`; `fr:194`, `fs:43`). Without a config it exits `requires a committed fsdev.config` with exit code 3 (`fst:73-77`, **[test]**; `EXIT_CONFIG_ERROR`). **[page]**
6. **A `.ts` config loads without a compile step.** The loader tries native `import()` first, then `jiti` for a `.ts` config Node cannot load (`packages/fsdev/src/load-config.ts:6-10`; the code is in `import-config-module.ts`, not re-read). `fsdev` depends on `tsx` (`packages/fsdev/package.json:82`). **[verify: whether a `.ts` config and flow sources import cleanly in a production image with no build step was not run. The page either copies source and runs `fsdev serve`, or states a build step as the reader's choice. Run `fsdev serve` in a clean directory before the page claims "no build".]** Real example configs are `.ts` files that import flows by relative path (`hc:12-25`, `ks:29-35`). **[page example basis]**
7. **`fsdev` must be a runtime dependency to use `fsdev serve`.** It is the `fsdev` bin (`packages/fsdev/package.json:54-56`). `fsdev serve` does not need `@flow-state-dev/devtool`: "it never mounts the UI" (`fr:207`; `fs:5-9`). So the image installs `@flow-state-dev/fsdev` but not `@flow-state-dev/devtool`. The existing pages install the CLI as a dev dependency (`apps/docs/docs/devtool/setup.md:18`), so a `pnpm install --prod` image would lack it. **[page: say the image installs `@flow-state-dev/fsdev` as a dependency, not a dev dependency. Alternative that needs none of this: a three-line `src/server.ts` calling `serve(flowState)` (fact 9), where only `@flow-state-dev/node` is needed.]**
8. **The SQLite store is a native module.** `@flow-state-dev/store-sqlite` depends on `better-sqlite3 ^11` (`packages/store-sqlite/package.json:65-68`). pnpm 10 builds it only when allowed, `--allow-build=better-sqlite3` needs pnpm 10.4 or later, npm, yarn and bun need no flag (`apps/docs/docs/devtool/setup.md:18-21`). The old page's "needs to be compiled for the same platform as the runtime ... don't copy `node_modules` from your host" (`old:390-392`) is the same constraint. **[page: one sentence, install inside the image, not on the host. The pnpm flag is a [verify] in an image: `pnpm install --frozen-lockfile` with a pnpm 10 build-approval step was not run here.]**
9. **The no-CLI alternative is `serve(flowState, options)`.** Signature `serve(app: FlowState | FlowApiRouter, options?: ServeOptions): Promise<ServeHandle>` (`ns:184-187`). Defaults: `port` = `process.env.PORT`, then `3000` (`ns:52`, `ns:166-174`); `host` `"0.0.0.0"` (`ns:54`); `basePath` `"/api/flows"` (`ns:56`); `healthPath` `"/healthz"` (`ns:58`); `shutdownGraceMs` `10000` (`ns:92`); `handleSignals` `true` (`ns:99`). Handle: `{ server, port, close() }` (`ns:130-141`). Documented usage `await serve(flowState)` (`nr:29-42`). **[page example: if the page shows `src/server.ts`, it is `import flowState from "../fsdev.config"; await serve(flowState);`. The default-export shape is `hc:12`; `serve` import is `nr:31`.]**
10. **`fsdev serve` binds `$HOST` then `0.0.0.0`, and `$PORT` then `3000`.** `fr:182-198`, `fs:97-102`, `fs:70-72`; flags `-p, --port`, `--host`, `--config`, `--dotenv`, `--allow-unauthenticated` (`fr:197-203`). `0.0.0.0` is what a container needs (`ns:54` "required for most PaaS"). An invalid port is exit 3 with `Invalid port: <value>` (`fs:76-78`; `fst:20-47`, **[test]**). **[page: default port 3000; `EXPOSE 3000` and `-p 3000:3000` match. Flag table is [ref] `reference/cli`.]**
11. **A network bind needs authentication on every flow, or the server will not start.** Before binding a non-loopback host `fsdev serve` refuses when a served flow has no `authentication.resolvePrincipal` or runs on the framework default (`fr:207`; `fs:104-117`; `bg:99-104`; `fst:81-86`, **[test]**: message contains `Refusing to bind 0.0.0.0`). The container default host is `0.0.0.0`, so this applies to every container on defaults. The refusal text: `Refusing to bind <host>: flow(s) <kinds> has/have no authentication configured, so a network-exposed server would accept a caller-supplied userId. Configure authentication.resolvePrincipal on the flow, bind a loopback host (--host 127.0.0.1) for local-only use, or pass --allow-unauthenticated to override.` (`bg:99-104`). Exit code 3 (`fs:116`). The check is skipped by `--allow-unauthenticated` (`fr:203`). **[page: this is the likeliest "container exits immediately" cause. State it flat, point to authentication (`apps/docs/docs/server/authentication.md`, not re-read) for how to set `resolvePrincipal`. Do not recommend `--allow-unauthenticated` for a deployed container.]** The same check applies when calling `serve()` yourself only if you call `assertNetworkBindIsAuthenticated`: `serve()` does not call it (`nr:121-150`; `ns` has no call). **[page: the `serve()` entry must `await assertNetworkBindIsAuthenticated(flowState, { host })` first to match `fsdev serve`; `nr:134-144`.]**
12. **Model keys come from environment variables at run time.** The provider key variables are read from the environment: `OPENAI_API_KEY` for `openai/...`, `AI_GATEWAY_API_KEY` for the gateway (`packages/core/src/models/providerDetection.ts:10`, `:16`; `hc:5-10` comment). `fsdev serve` also loads `.env.local` from the working directory and parents, and `--dotenv <path>`; a real exported variable always wins (`fr:426-431`). **[page: pass keys with `-e` at `docker run`; do not `COPY` a `.env.local` into the image. The "do not bake keys" advice is `old:377`.]**
13. **Shutdown.** `fsdev serve` stops on `SIGTERM` and `SIGINT`: it stops accepting connections, drains in-flight requests, force-closes after the grace window (default 10 s), then disposes the router and `FlowState`, which closes the SQLite connection (`fr:207`; `ns:92`, `ns:135-141`; `nr:48-50`; `sq:103-105`). Docker sends `SIGTERM` on `docker stop` (`old:375`, Docker behavior, not repo behavior). **[page: one sentence. Because `fsdev serve` is the process that gets the signal, the `CMD` must run it directly, so [verify] `CMD ["pnpm", "exec", "fsdev", "serve"]` versus `CMD ["npx", ...]` versus `CMD ["node", ...]` forwards `SIGTERM`; not run. The exec-form `CMD` is the only advice the sources support, and only for the old page's `CMD ["node", "dist/server.js"]` (`old:73`).]**
14. **Push needs one key when several containers serve one address.** `pushSecret` or `FSD_PUSH_SECRET`, else a random key per process (`ns:114-119`, `ns:413-414`; `nr:61-75`). **[ref: only with more than one container, and a single container is the page's case. Name it in one clause or leave it to the SQLite single-writer limit, fact 20.]**

## Q2: What do you mount?

The page stores data (the SQLite file), so the four questions follow.

15. **What is stored in the file.** One SQLite database holds sessions, users and orgs, request items and stream events, resource state and resource content, sequencer checkpoints, suspensions, leases, traces, and wakes. Everything survives a process restart (`sqr:83-93`; table at `sqr:85-93`). The adapter fills the `primary` slot, the catch-all state store (`sq:90-94`, `sq:98`; `packages/engine/README.md:82`). **[page: one sentence listing sessions, resource state and the run history as what the mount holds. Table of tables is [ref].]**
16. **Who owns it.** The app's operator. The file belongs to the `sqliteStores` adapter in the app's `createFlowState({ stores })`; records inside it belong to the app's users, orgs and sessions, each scoped by the framework (`sqr:85-93` row names `sessions` / `users` / `orgs`). **[page: "the file is the app's whole store". Per-user ownership of rows is a Concepts topic; do not retell.]**
17. **Who can see it.** Anyone who can read the volume, in plain files. The framework does not encrypt it. The file has no access control of its own; users reach their own records through the API, where the principal resolver decides (fact 11, `bg:99-104`). **[page: the mount is as sensitive as the database, because it holds every user's sessions. Plain statement of fact. The "not encrypted" half is absence from the sources: [verify] leave out or say "plain SQLite file".]**
18. **Where it is stored.** At the `filename` the config passes to `sqliteStores({ filename })` (`sq:34-36`, `sq:95-101`). `filename` is "the path to the SQLite database file"; "if the file doesn't exist, it will be created automatically" (`sqr:43`). `better-sqlite3` does not create parent directories: the local CLI makes `.fsdev/data` itself first (`packages/fsdev/src/local-store.ts:67-68`), and the kitchen-sink config does `mkdirSync(path.dirname(file), { recursive: true })` before opening (`ks:66-69`, `ks:46-52`). So the folder the file lives in must exist before the store opens. **[page: the Dockerfile creates `/data` (`old:61-62`, `RUN mkdir -p /data`); the config uses `/data/flowstate.db`. The page's example config: `stores: { default: { primary: sqliteStores({ filename: "/data/flowstate.db" }) } }`; the import is `@flow-state-dev/store-sqlite` (`sqr:25-32`; `packages/store-sqlite/src/index.ts:9`).]**
19. **Mount the directory, not the file.** The store runs in WAL mode (`journal_mode = WAL`, `sch:3-4`, `sqr:47-49`), which keeps companion files beside the database. **[page: the volume maps the directory `/data`. The `-wal`/`-shm` sibling-file names are SQLite behavior, not in the repo's text: [verify] do not name them unless confirmed; say "the database and the files SQLite keeps beside it". Reason to mount the folder follows from fact 18 and WAL, and a single-file bind mount is the reader's risk.]** The old page mounts a named volume `-v flow-data:/data` and says the database "persists across container restarts and image updates" (`old:221`). **[page: `-v flow-data:/data`.]** The named-volume-versus-bind-mount distinction is Docker's, not the repo's. **[page: one choice, the named volume, the same as the old page. The alternative is a host path, a clause at most.]**
20. **How many exist, and how many writers.** One file per `sqliteStores` adapter, and one process should write it. SQLite "supports one writer at a time"; "multiple container replicas pointing at the same database file" make writes fail (`old:401-403`; `dep:52`: SQLite "No (single-writer)", "Single-server production"). The adapter declares `sharedAcrossProcesses: false` (`sqr:81`), so behavior that reads another process's in-flight requests stays off. WAL lets readers run beside the writer, and a busy timeout of 5 s waits on a lock (`sqr:47-56`; `sch:5`). **[page: run one container on one volume. For more than one, use a store whose writers can share, the Postgres adapter (`@flow-state-dev/store-postgres`, in the package map). The sources disagree on Postgres readiness: `dep:53` says "coming soon", and the package exists. [contradiction: leave the multi-instance path as a link to Reference/Persistence, not a claim.]**
21. **What a volume does and does not keep.** A new image reads the same file; deleting the container does not delete a named volume (Docker behavior, [verify] cited only via the old page, `old:221`). A schema upgrade runs on open (`sq:62-66`; `sqr:99`, additive migration applied automatically on open). Without the mount the file lives in the container's own filesystem and is gone with the container (**[verify]**: Docker behavior; the sources say only that persistence needs the mount, `old:376`). **[page: one sentence for why the mount exists.]**
22. **Trace retention is not a page matter.** A SQLite store keeps the last 50 requests' traces unless `NODE_ENV=development` (1000) (`sq:29-32`, `sqr:45`). **[ref/cut]** The image sets `NODE_ENV=production` (`old:64`), which is not `development`, so 50. **[cut]**
