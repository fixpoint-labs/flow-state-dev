## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are writing the Dockerfile for the support-desk app. What has to be in the image for `fsdev serve` to start it, and what should be left out?
   Answer: Node 22 or later (fsdev and store-sqlite declare engines.node >=22; base node:22-slim). The committed fsdev.config.ts at the working directory, default-exporting the FlowState (fsdev serve searches the cwd only, or --config; without one it exits 3 with 'requires a committed fsdev.config') (facts 4, 5). @flow-state-dev/fsdev installed as a runtime dependency, not a dev dependency, or a production install lacks it; @flow-state-dev/devtool is not needed because serve never mounts the UI (fact 7). Dependencies installed inside the image, not copied from the host, because the SQLite store uses the native better-sqlite3 module (fact 8). Left out: the model key and any .env.local, which come in at run time (fact 12).
2. What do you mount into the support-desk container, where does the config point the store, and what is on that mount?
   Answer: A named volume on a directory: -v flow-data:/data, with the Dockerfile creating /data (RUN mkdir -p /data) and the config passing sqliteStores({ filename: "/data/flowstate.db" }) (facts 18, 19). Mount the directory, not the file, because the store runs in WAL mode and SQLite keeps files beside the database; the folder must exist before the store opens, since the file is created but its parent directory is not (facts 18, 19). The one file is the app's whole store: sessions, users, resource state and the run history; without the mount it lives in the container and goes with it (facts 15, 21). Anyone who can read the volume can read every user's sessions (fact 17).
3. You run the image and the container exits straight away. The log says 'Refusing to bind 0.0.0.0: flow(s) support has no authentication configured...'. Why, and what is the fix? *(edge case)*
   Answer: In a container fsdev serve binds 0.0.0.0 (HOST, else 0.0.0.0), and before binding a non-loopback host it refuses when any served flow has no authentication.resolvePrincipal, because a network-exposed server would otherwise accept a caller-supplied userId; it exits with code 3 (facts 10, 11). The fix is to configure authentication.resolvePrincipal on the support flow (see the authentication page). --allow-unauthenticated overrides the check but is not for a deployed container (fact 11).
4. Traffic grows and a second engineer starts a second support-desk container on the same flow-data volume. What happens, and what should they do instead? *(edge case)*
   Answer: SQLite takes one writer at a time; several replicas pointing at the same database file make writes fail, and the adapter declares sharedAcrossProcesses: false (fact 20). Run one container on one volume. For more than one instance, use a store whose writers can share, such as the Postgres adapter, via the Reference/Persistence link (fact 20). Several containers behind one address also need one shared push key, pushSecret or FSD_PUSH_SECRET (fact 14).
5. You change the support flow, rebuild the image and replace the running container. Are the customers' existing sessions still there? *(edge case)*
   Answer: Yes, provided the new container is run with the same -v flow-data:/data. The named volume outlives the container and the new image reads the same file; a schema upgrade, if any, is applied automatically when the store opens (facts 19, 21, 25). A container run without the mount starts with an empty store (fact 21).
6. How do you pass the OpenAI key to the running container, and how do you (or an orchestrator) tell it is up and ready?
   Answer: Pass the key at run time with -e OPENAI_API_KEY=... on docker run, alongside -p 3000:3000 and -v flow-data:/data; do not bake it or a .env.local into the image (facts 12, 23). On success fsdev serve prints 'Server running at http://0.0.0.0:3000', the API line and the Config line (fact 24). Probe /healthz (not /health): 200 {"status":"ok"} when ready, 503 'initializing' while the store is still opening after the port is bound, so a health check should wait through a cold start, and 500 'error' if initialization fails for good (fact 2). On docker stop the SIGTERM drains in-flight requests for up to 10 s and closes the SQLite file (fact 13).
