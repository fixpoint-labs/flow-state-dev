## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You have an app wired in fsdev.config.ts (it default-exports createFlowState with your flows and stores). What starts the server on Railway, and what does it bind to without any configuration from you?
   Answer: serve(flowState) from @flow-state-dev/node, called from an entry file, or `fsdev serve` (e.g. `pnpm fsdev serve`) as the start command, which wraps the same serve() call. It binds process.env.PORT (Railway sets PORT itself, so you do not set it), falling back to 3000, on host 0.0.0.0. It mounts the flow API at /api/flows and serves /healthz. (Facts 2: SERVE:51-57, 184-187; NODE-README:29-42; CLI:183; section 4: OLD:225.)
2. You set the store to sqliteStores({ filename: "/data/flowstate.db" }). Where does that file actually live on Railway, and what has to be true so the sessions and state in it are still there after you redeploy?
   Answer: It lives at whatever path `filename` names, here /data/flowstate.db. SQLite creates the file if it is missing, but the folder must already exist. On Railway the path must be inside a mounted volume (a volume mounted at /data). Without a volume the file sits on the container's own disk, which a redeploy replaces, so sessions, state, items and checkpoints are lost. (Facts 3, four-questions table: SQLITE-README:43; OLD:191, 195-205; section 6.)
3. Which environment variables do you set in the Railway service's Variables for a first deploy, and do you need to set PORT?
   Answer: At least one LLM provider key, such as OPENAI_API_KEY (others: ANTHROPIC_API_KEY, GOOGLE_GENERATIVE_AI_API_KEY, AI_GATEWAY_API_KEY, OPENROUTER_API_KEY); the model resolver picks providers up from env vars at runtime. You do not set PORT: Railway sets it, and serve() and fsdev serve read it. (Facts 4: environment.md:19-23; OLD:218-225; SERVE:166-174.)
4. You deploy with `fsdev serve` as the start command and the process exits at once with "Refusing to bind 0.0.0.0: flow ... has no authentication configured". Why, and what are your ways out? *(edge case)*
   Answer: fsdev serve runs a bind guard before it binds a non-loopback host such as 0.0.0.0 (which a PaaS needs). It refuses because a flow has no authentication.resolvePrincipal, so a network-exposed server would accept a caller-supplied userId. Ways out: configure authentication.resolvePrincipal on the flow, bind 127.0.0.1 (not useful on Railway), or opt out with --allow-unauthenticated (allowUnauthenticated: true in code). A bare serve() call does not run the guard; a hand-written entry calls assertNetworkBindIsAuthenticated itself. (Facts 2 'The guard': GUARD:97-104; CLI:185, 187; section 6.)
5. After the deploy you curl https://<your-app>.up.railway.app/healthz. What should you see, and what do a 503 or a 500 tell you instead? *(edge case)*
   Answer: 200 with {"status":"ok"} once the server is ready. A 503 ({"status":"initializing"}) means the port is bound but the stores are still opening (serve resolves on bind so a cold-start health check passes). A 500 means store initialization failed permanently, so the deploy fails fast; the process is up but requests error, read the logs. (Under fsdev serve an init failure instead exits with code 3.) The path is /healthz, not /health. (Facts 2: SERVE:58, 178-182; APP:86-88; serve.test.ts:165-200; section 7.)
6. Traffic grows and you want to raise the Railway service to two replicas while keeping the SQLite store. Does that work, and what do you use instead? *(edge case)*
   Answer: No. SQLite is single-writer, one file per primary store with one connection per process, and the registry reports it is not shared across processes, so the page's setup is one replica. For more than one replica, use a Postgres adapter (@flow-state-dev/store-postgres); the filesystem store is per-container and does not help either. (Facts 3 'four questions' and 'alternatives': SQLITE-README:71, 81; section 6.)

## Reference rows

- Router contract: one handler per HTTP method, called with a Web Request and { params: { path: segments } }, returning a Web Response; path segments are decoded once; a method with no handler is not served (railway.md lines 26, 91-92, 120-127) → R-13
- createFlowState: getRouter() opens stores lazily and returns the same router on every call; stores profile `default` with slot `primary` as the catch-all state slot (lines 36-47) → R-12
- Stream response: content type text/event-stream, headers must be flushed before the first chunk, a client disconnect ends the stream → R-06
- Store durability table: filesystem store survives a process restart, lost on redeploy or container migration; SQLite on a mounted volume survives both (lines 191-205) → R-16
- @flow-state-dev/store-sqlite: depends on the native module better-sqlite3, which needs build tools at install time; createSQLiteStores takes `filename` → R-16
- Environment variables: OPENAI_API_KEY is read by the model resolver at runtime; PORT is read by the server file, not the framework → R-15
- Store concurrency table: filesystem store is per-process disk, not shared across replicas; SQLite allows one writer at a time (WAL with a 5000 ms busy timeout, so a second writer waits and fails only if the lock is not released in time) and one file cannot be shared across replicas; the PostgreSQL store (`@flow-state-dev/store-postgres`) handles concurrent access → R-16 (corrected by pass 5)
