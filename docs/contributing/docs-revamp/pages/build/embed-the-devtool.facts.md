## What the page is for, and the question it answers

7. **What it is.** `DevToolPanel` is the DevTool's whole UI as a React component, exported from `@flow-state-dev/devtool/react` (`dt/index.ts:7`; `dt/DevToolPanel.tsx:100`). The standalone `fsdev dev` shell mounts the same component (`apps/devtool/src/App.tsx:30-45`). **[page]**
8. **Why you would embed it.** To open the DevTool on a deployed copy of the app (a preview or staging tier) from the app's own origin, where `fsdev dev` is not running. `emb:8`, `emb:12-16`; the kitchen-sink page comment says the route exists "so PR and Vercel previews are observable from the same origin as the main app" (`ks/page.tsx:7-8`). **[page: one sentence in the opening.]** `fsdev dev` stays the lighter local path (`emb:18`). **[page]**
9. **[answers] Who can open it in production?** Whoever your app lets request the route, **and then** whoever the flow API will answer for (facts 22-28). Nothing in the package restricts the route or the panel by environment: `DevToolPanel` has no `NODE_ENV` check and no "enabled" prop (`dt/DevToolPanel.tsx:68-130`, the full prop list, fact 15). So the answer is: nobody is blocked by the panel itself; you block them. **[page: the page's third step and the answer to the question. State it in one sentence.]**

### What the embedded panel reads and writes

27. **It reads the same flow API as your app.** One client, `createClient({ userId, baseUrl, fetcher })`, talks to `/api/flows/*` on `baseUrl` (`dt/context/devtool-context.tsx:86-91`). When `bearerToken` is set, its `fetcher` adds `Authorization: Bearer <token>` to every call and stream (`dt/lib/client.ts:1-12`, `:28-36`). **[page: this is why restriction at the flow API matters.]**
28. **It opts into trace items on the stream.** The stream route returns trace items only when the request carries `?include=trace` (`eng/routes/stream-routes.ts:106`, `:178`, `:247`, `:312`; `tc:9-14`, `:30`). The only check is the request's ownership: `ownsRecord(flow, requestRecord)` at `stream-routes.ts:164` and `:252` runs for the same request whether or not `include=trace` is set, and nothing else gates the parameter (`:106`). A caller who may read a request's stream can also ask for its trace. **[page: one clause, only if the page needs it; the reason the trace is as visible as the stream is the owner check, not the panel.]**
29. **What trace data holds in production.** Trace observability is on by default outside production and off when `NODE_ENV === "production"`, unless `FSDEV_TRACE_OBSERVABILITY` is `true`, `false`, `1` or `0` (`packages/core/src/helpers/trace-observability.ts:1-19`). With it off, only a lean trace row is written for a block that completed: identity, output and the rescued mark, with no input, prompt, messages or history; failed, suspended and transient blocks get no row (`createExecutionContext.ts:3867-3875` comment). The page says "only its identity and output". Block detail on a production embedded panel is therefore thin unless the variable is set (`eng/context/createExecutionContext.ts` at the `lean: true` write; (confirmed: `createExecutionContext.ts:3870-3878` and `:3975` write `lean: true` per completed block when `isTraceObservabilityEnabled()` is false)). **[page: one sentence in "restrict it", naming `FSDEV_TRACE_OBSERVABILITY`: the panel on a production deployment shows less unless you turn it on, and turning it on records prompts. [ref] `reference/environment`.]**
30. **The debug endpoints are separate and off by default.** The panel's Resources view and Suspensions tab read `/api/flows/sessions/:id/debug/resources*`, which are off unless `debugEndpointsEnabled: true` or `FSDEV_DEBUG_ENDPOINTS=1` (`eng/routes/createFlowApiRouter.ts:231-241`; `eng/routes/debug-routes.ts:54-73`; `dvc:116-132`). `fsdev serve` turns on neither; `fsdev dev` turns on both on loopback (`dvc:134`). A deployed host that embeds the panel gets those views only when it sets them (see facts 31-33). **[page: one sentence.]** With them off the Suspensions tab reads "Suspensions are unavailable" and the Resources panel reads "Debug endpoints disabled" (`dt/components/workspace/suspensions-view.tsx:70-76`; `dt/components/detail/resources-panel.tsx:77-96`). **[ref]**

## Step 3: Restrict it

The question: who can open it in production? Answer in layers. Each layer is a separate fact.

31. **The route.** The page is an ordinary route of the host. Whatever the host does for any route (middleware, a route group, an auth check) decides who gets the HTML. 32. **Not rendering it.** The page-level guard (`emb:91-101`) returns `null` in production unless `NEXT_PUBLIC_FSD_DEVTOOL=1`. That hides the UI; it does not remove the route or change who can call the flow API (fact 1). `NEXT_PUBLIC_FSD_DEVTOOL` is an app-defined name in the docs example, not a framework variable; no source under `packages/` reads it (searched `NEXT_PUBLIC_FSD_DEVTOOL` under `packages/`: no hits, only `emb`). **[page: the page may show a guard as an off switch and must call it that. 33. **Build-time exclusion.** `emb:103` says tree-shaking will not strip the panel because of the guard, so the code still ships in the client bundle unless the route is excluded at the framework level. **[page: one sentence. Mechanism is not stated beyond that. [verify: not run; the claim is the existing page's.]]**
34. **The flow API.** Every call the panel makes is a call to the app's own flow API, which decides by the flows' own authentication. The panel's `userId` is the identity it sends, and under the framework default resolver that is read from the request body: `defaultBodyUserIdPrincipalResolver` reads `body.userId` and nothing else (`eng/transports/auth/defaultBodyUserIdPrincipalResolver.ts:31-47`; `rt:67` lists `resolvePrincipal` default as "body `userId`"). [ref] `reference/authentication`.]** **[verify: how `userIdControl="host"` and a server-resolved principal interact (the panel's `userId` is ignored by a resolver that reads a cookie) was not run. The page states only the default-resolver half and says an app with its own resolver is answered by that resolver.]**
35. **A user sees only their own sessions.** The DevTool acts as one user; a session not created by that user is not listed (`ov:85`). 36. **The debug endpoints' own gate.** Fail-closed: enabled only by `debugEndpointsEnabled` or `FSDEV_DEBUG_ENDPOINTS=1`; origin must be loopback or in `debugAllowedOrigins` (matched by prefix); a request with no `Origin` header gets 403 unless `debugAllowAnonymousLocal` or `FSDEV_DEBUG_ALLOW_ANONYMOUS_LOCAL=1` (`eng/routes/debug-routes.ts:54-73`, `:79-98` `assertDebugAllowed`; `eng/routes/createFlowApiRouter.ts:231-262`; `dvc:116-122`). **The origin check does not identify the caller:** "with this on, any client that can reach the port gets in" (`dvc:122`; `createFlowApiRouter.ts:255-261`). ## Stored parts: who owns it, who can see it, where it is stored, how many

The page installs a viewer. The embedded panel stores very little of its own; what it displays is stored by the app's stores. The four questions, for each.

42. **Sessions, requests, items and traces the panel shows.** *Owns:* the flow instance that ran them, under the user that started them. *Sees:* the user whose session it is (fact 35). *Stored:* by the app's stores, not by the panel; which store depends on the app's `fsdev.config.ts`/`createFlowState` stores, and trace events are kept per request in the paired trace store (`tc:44-50`). *How many:* as many as the app made; trace events are kept for the most recent requests only (cap in `eng/stores/index.ts:164-182`, 50 unless `NODE_ENV=development` then 1000, unless `traceStore: { maxRequests }` is set). **[page: not restated; the page names only that traces are kept for recent requests. [ref] retention.]** The cap is `resolveTraceMaxRequests` (`eng/stores/index.ts:163-185`: 1000 when `NODE_ENV === "development"`, otherwise 50, an explicit number wins).
43. **Browser-side panel settings.** *Owns:* the browser profile. *Sees:* whoever uses that browser; never sent to the server. *Where:* `localStorage` keys `fsd-devtool-theme` (theme), `fsd.devtool.userId` (written only when `userIdControl="internal"`, fact 16), `fsd.devtool.activeSession.<base url>|<user>|<flow id>` (last session per instance), `fsd.devtool.lastAction.<flow id>`, `fsd.devtool.debugMode`, `fsd.devtool.traceItemsVisible` (`dt/hooks/use-devtool-theme.ts:16`; `dt/config.ts:23-28`, `:63-90`, `:101-130`, `:156-181`; `dt/context/debug-context.tsx:23`). *How many:* one value per key; one session hint per base URL, user and instance. Readers are SSR-safe and return defaults without `window` (`dt/config.ts:1-5`). **A bearer token is not written to `localStorage`**: "credentials are never written to localStorage" (`dt/config.ts:15`). **[page: one sentence for "the panel stores nothing on the server; its settings stay in that browser." The key names are not for the page.]**
44. **What `bearerToken` does and where it comes from in an embed.** It is a prop (fact 15); it is held in the panel's state for the visit. The Settings sheet can also set one by hand (`settings-sheet.tsx:17-21`, `:59-65`). A page that passes a token it reads on the server into a client component puts that token in the page's HTML; the framework does not prevent that. **[page: one sentence if the page shows `bearerToken`: pass it only to a route already behind your gate. [verify: this last sentence is a consequence of the prop, not a framework statement; keep it off the page unless the writer wants to show `bearerToken`. The sitemap's three steps do not need it.]]**
45. **The `devtool` block of `fsdev.config.ts`** (`userId`, `bearerToken`) is read by `fsdev dev` only and injected into the page it serves; "Production `serve` ignores it" (`rt:69`). ## Answer key, by sitemap question

- **Who can open it in production?** Anyone your app lets request `/devtool`. What they see is whatever the flow API returns for the user the panel acts as. The package restricts nothing by environment: no `NODE_ENV` check, no enabled prop. Gate the route in the host (middleware or a route group), keep the flow API's own authentication on the flows, and leave the debug endpoints off unless the origin is known. An exposed panel can send actions and resolve suspensions. Facts 9, 31-38.
- **A guard in the page component already returns `null` in production. Is the panel restricted?** No. It renders nothing, but the route exists and the flow API answers the same callers. Facts 1, 32.
- **The panel renders but is unstyled / looks wrong.** The host must run Tailwind v4 and import `@flow-state-dev/devtool/react/styles.css` in the route's layout. Facts 13, 14, 22.
- **The Resources view says "Debug endpoints disabled" on the deployed copy.** The debug endpoints are off by default and `fsdev serve` turns on neither; enabling them in production exposes full server state, and the origin gate does not identify the caller. Facts 30, 36, 37.
- **Block detail on the deployed copy shows no prompt.** Trace observability is off by default when `NODE_ENV=production`; `FSDEV_TRACE_OBSERVABILITY=true` turns it on. Fact 29.
- **The panel and the app show different sessions.** They share sessions only when both present the same `userId` to the same flow API; the panel's `userId` is what the host passes. Facts 39, 40.
