## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are adding the DevTool to the support-desk app so the team can inspect runs on the staging deployment, where `fsdev dev` is not running. What do you install, and which two files under `src/app/devtool/` do you write, with what in each?
   Answer: `pnpm add @flow-state-dev/devtool` as a normal dependency, not `-D`, because the host's build imports it (facts 5, 10). `src/app/devtool/layout.tsx` imports `@flow-state-dev/devtool/react/styles.css`, sets `export const dynamic = "force-dynamic"`, and renders `<div className="h-screen w-screen">{children}</div>` (the panel fills its container, so it needs a parent with a set height). The page renders `<DevToolPanel>` from `@flow-state-dev/devtool/react` in a client component (`"use client"`), because the panel is browser-only (facts 11, 21-24, 50). The page needs React 19 (fact 12).
2. The DevTool route is now in the production build of the support desk. Who can open it, and what does the package itself do to stop a stranger?
   Answer: The package stops nobody. `DevToolPanel` has no `NODE_ENV` check and no enabled prop. Anyone your app lets request the route gets the panel, and the panel can then see whatever the app's flow API serves to the identity it presents. You gate it yourself, in two places: the route, in the host's own middleware or route group (preferably on the app's sign-in check, not just an env var), and the flows, through their own authentication. Under the default resolver the identity is read from `body.userId`, which the caller controls (facts 9, 31, 34, 51).
3. A teammate wraps the page in `if (process.env.NEXT_PUBLIC_FSD_DEVTOOL !== "1" && process.env.NODE_ENV === "production") return null;` and says production is now locked down. Is it? *(edge case)*
   Answer: No. The guard only renders nothing. The route still exists and returns a page shell, the panel code still ships in the client bundle (tree-shaking does not strip it because of this guard), and the flow API answers exactly the same callers as before. `NEXT_PUBLIC_FSD_DEVTOOL` is the example's own name, and the framework does not read it. Treat it as an off switch, not as access control (facts 1, 32, 33).
4. A support agent who is not an engineer finds the unguarded `/devtool` URL on the production support desk. Can they only look, or can they change things? *(edge case)*
   Answer: They can change things. An exposed panel is not read-only. Its action bar sends any of the flow's declared actions under the open session, it has a Resolve control on pending suspensions, and it offers Replay and Continue on requests. They act through the same flow API, as whatever identity the panel presents. That is the strongest reason to gate the route (fact 38).
5. On the staging deployment the panel shows the support desk's sessions, but the Resources view says "Debug endpoints disabled" and block detail shows no prompt. Is the embed broken, and should you switch those on in production? *(edge case)*
   Answer: The embed is fine. The debug endpoints are off by default, and `fsdev serve` does not turn them on. They need `debugEndpointsEnabled` or `FSDEV_DEBUG_ENDPOINTS=1`, and a same-origin panel would also need `debugAllowAnonymousLocal`. The origin check does not identify the caller, and the endpoints expose every session's full server state, so do not turn them on in production just to get the Resources view. Prompts are missing because trace observability is off when `NODE_ENV=production`. `FSDEV_TRACE_OBSERVABILITY=true` turns it on, but then prompts get recorded (facts 29, 30, 36, 37).
6. A signed-in agent opens the support desk's DevTool route and sees none of the conversations they just had in the app, or sees a different user's. What decides which sessions the panel lists, and what should you pass? *(edge case)*
   Answer: The panel acts as one user and lists only that user's sessions. The panel and the app share sessions only when both present the same identity to the same flow API. Pass the user the app is already signed in as as `userId` (read on the server and handed to the client panel), not a hard-coded id, and set `userIdControl="host"`. With `"host"` the panel's Settings user-id editor is hidden and the id is not written to `localStorage`. Changing `userId` rebuilds the client and closes the open session (facts 2, 16, 17, 35, 39, 40).
