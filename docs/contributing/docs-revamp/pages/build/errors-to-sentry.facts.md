## Read this first: what the plan asks, and what the code says

They are different things, and a Sentry integration belongs on `errorCapture`: `onErrored` is a block set on an action or on `request`, it receives `{ requestId, actionName, error }` and nothing else (`ra:3298-3308`), and it runs only for a request that ended failed (`ra:3262-3312`; test `packages/engine/test/execution.test.ts:2287-2316`, order `action.errored`, `request.errored`, `request.finished:failed`). It gets no `userId`, no `sessionId`, no block name and no block path. A block run as the hook can read ids from its own context (`ctx.request.identity.id`, `ctx.session.identity.id`, `ctx.session.identity.userId`: `packages/core/src/types/scope.ts:9-13`, `:221`, `:298`; read in tests `packages/core/test/sequencer.test.ts:1216`, `packages/engine/test/bus/scope-notices.test.ts:113`) **[source: `ctx.session.identity` is read in an engine test; its use inside an `onErrored` block was not run]**. **[page, "Which hook?": `errorCapture` is the hook for a tracker. `onErrored` is the in-flow alternative, with the input above. State both in two sentences, build the recipe on `errorCapture`. The page title and example are `errorCapture`; the plan's "Example: `onErrored`" needs a decision from the plan's owner, flagged in the report.]** [answers Which hook?]
2. **The guide's wiring example does not match the surface.** `flows: { myFlow }` is wrong: `flows` is a list of flow instances (`packages/engine/src/flowstate/types.ts:121`; `wsf` uses `flows: [support]`). `stores: { default: { primary: inMemoryStores() } }` is the named-profile shape; with `stores` omitted the app runs in memory as the `default` profile, and one adapter such as `sqliteStores({ filename })` is the same as `{ default: { primary: adapter } }` (`types.ts:152-159`, `packages/store-sqlite/src/registry.ts:95`). **[contradiction: the code wins. The page's example uses `flows: [support]` and a single adapter, as `wsf` does, or omits `stores`.]** The guide's `import { captureToSentry } from "./capture-to-sentry"` points at a file the guide never names; the page names it (see "The example app" below).
3. **`code` is never missing on the event, so `?? "unknown"` on `code` is dead code.** The event's `error` is the normalized error. A thrown value that is not a `FlowError`, or a `FlowError` with no `code`, comes out with `code: "execution_error"` (`ne:18-24`, `:66`; `fe:38-57` shows `code?` optional on a raw `FlowError`). A provider error such as a rate limit is classified into a typed error with its own code before that default (`ne:52-64`; code table `packages/engine/src/errors/flow-error.ts:36-363`). So `event.error.code` is always a string by the time the callback sees it. **[page: write `code: event.error.code`, drop `?? "unknown"`. If the page's example type-checks only with the fallback, keep the fallback and do not claim it is dead.]**
4. **`blockName` is absent on a `final` event for a setup failure.** A request that fails before any block runs (the test makes the resolver construction fail) still sends one `final` event, with `scope: "request"`, the request's ids, and no block (`ra:2263-2279`; test `fin:141-169`). So `event.blockName ?? "unknown"` is live. **[contradiction with `ec:123`, "does not fire for request-level failures that happen before block execution": a failure after the request is accepted and recorded does fire `final`. Whether an input-validation or authentication refusal before the request is recorded fires anything was not run: [verify], the page does not claim either way and says nothing about those refusals. `ec:123` is stale for the narrow case above.]**
5. **`ec:32` says "The runtime awaits it inside a guard", which reads as if the request waits for the callback.** It does not. The runtime starts the guarded call and moves on (`void safeCaptureError(...)`, `cec:3690`, `:3705`; `ra:2266`); the guard awaits the handler only so a throw or rejection is caught and logged at `warn` (`ecs:140-153`, test `packages/engine/test/error-capture.test.ts:79-107`). ## The hook (Step 1: the hook)

6. **The option.** `errorCapture` on `createFlowState`, imported from `@flow-state-dev/engine`. Off by default; no provider SDK is shipped. `packages/engine/src/flowstate/types.ts:196-206`; forwarded into the runtime config at `createFlowState.ts:1060` and `runtime-config.ts:76`, `:233`; the runtime options table lists it (`cfg:48`). **[page]**
7. **Its type.** `ErrorCaptureHandler = (event: ErrorCaptureEvent) => void | Promise<void>` (`ecs:65`). `ErrorCaptureEvent` is exported from `@flow-state-dev/engine` as a type (`packages/engine/src/index.ts:53`); `ErrorCaptureHandler` is not exported from the package index in this checkout (`index.ts:53` is the only `ErrorCapture` export; searched `packages/engine/src/index.ts`). **[page: type the parameter as `ErrorCaptureEvent`, import it as a type. Do not name `ErrorCaptureHandler`.]**
8. **Read-only; the return value is ignored.** `ecs:59-64`, `ec:32`. A throw or an async rejection is logged at `warn` as `[flow-state] errorCapture handler threw; swallowed` and never reaches the request (`ecs:145-152`; tests `cap:237-253`, `error-capture.test.ts:87-107`). **[page: one sentence. The log line text is [ref].]**
9. **When it fires: once per failing block, at the block that threw.** One event for the leaf block, not one per enclosing sequencer or action root (`ecs:8-9`, `cec:3660-3697`; test `cap:81-109`: a failing step inside a sequencer yields exactly one event, `blockName: "failing-step"`). **[page, "Which hook?"]**
10. **A failure a rescue handles still fires it.** The request completes, and the block event is still sent, with the failed block's name (test `cap:139-164`). **[page]**
11. **A block with a retry policy fires once per failed attempt,** each carrying `attempt` counted from 0 (test `cap:211-235`: `maxAttempts: 3`, always failing, events `attempt` `[0, 1, 2]`). A block that fails once and passes on attempt two still sends the first failure (`fin:119-139`: one non-final event, no final). **[page]**
12. **When it does not fire:** on a request that succeeds (`cap:111-122`), and when no `errorCapture` is set (no-op, the failure surfaces as usual; `cap:124-137`). **[page, one clause]**
13. **The `final` event: one more, for a request that ends failed.** `final: true`, `scope: "request"`, the request's ids, and the leaf block's identity when a block threw. It is sent after rescues and retries have run and after the request's record says `failed` (`ecs:47-55`, `ra:3290-3296`; test `fin:40-92`: status read inside the callback is `failed`, `blockName: "leaf-boom"`, `blockPath` set, the per-block event still sent and not final). A request a rescue or a retry saved sends no `final` (`fin:94-139`). A `final` is sent even when writing the failed status event throws (`fin:171-200`). **[page]**
14. **So a failing request reaches the callback at least twice** (the block's event, then the `final`), unless the page's adapter skips one. A sink that forwards every block failure skips `final` with `if (event.final) return`; a sink that wants one report per failed request keeps only `final`. `ec:60-82`; test `cap:166-209` (two events, the second `final: true`, `blockName: "boom"`). **[page, "Which hook?" and the duplicate trap. The existing guide's skip-`final` adapter forwards every block failure, including ones a retry or rescue later fixed. The choice is the reader's; the page recommends one: forward `final` only, for "one Sentry issue per failed request", and shows the other as a one-line change. [decision for the page; both are code-correct]**
15. **Retry-exhausted failures: the guide's "filter the noise" check drops them from `final` too.** The guide filters with `if (event.transient || event.error.retryable) return;` to keep "failures that were not retried" (`guide`, "Filter the noise"). A `final` event's `error` is the normalized error and keeps `retryable` (`ecs:131`, `cec:3702-3715` passes the thrown value through `normalizeError`; `ne:66-78` preserves `retryable` on a `FlowError`; a `NetworkError`, `TimeoutError`, `RateLimitError`, `ModelError`, `ProviderUnavailableError` are `retryable: true` by default: `packages/engine/src/errors/flow-error.ts:47-140`). So a request that fails because retries ran out on a `NetworkError` has `retryable: true` on its `final` and the guide's filter discards it, and the request that really failed is never reported. **[contradiction in the kept page's advice. Not run end to end. [page]: do not repeat that filter as advice on `final` events. If the page shows a filter, it applies to block events only (`!event.final && event.error.retryable`), or it filters nothing and states that `retryable` is a level hint.]**

## What to attach (Step 2: what to attach)

16. **The event's fields.** `ec:38-56` is the table; `ecs:24-56` the type. Carried on every event: `error`, `requestId`, `flowKind`, `actionName`, `userId`, and `orgId` (typed optional, set on every event: `ec:49`; `ecs:33`, `cec:3667-3674`). Present when there is one: `sessionId` (a session-bound request), `blockName`, `blockKind` (`"handler" | "generator" | "evaluator" | "sequencer" | "router"`), `blockInstanceId`, `blockPath`, `attempt` (only under a retry policy, 0-indexed), `scope` (`"block" | "request" | "sideChain" | "resource"`), `transient` (high-frequency poll-loop blocks), `final`. **[page: a short list of the fields the example attaches. The full table is [ref] `reference/errors`.]**
17. **The event carries no provider vocabulary.** No tags, severity or fingerprint: the adapter derives them from `error.code` and `error.retryable` (`ecs:20-23`; `ec:38`). The raw thrown value is `error.cause`; the `FlowError` is a normalized copy with `code`, `retryable`, `details`, `blockName`, `blockInstanceId`, `scope` (`ecs:25`; `fe:38-57`; `ne:81-89`). **[page]**
18. **What identifies the run: `requestId`, `sessionId`, `userId`, `blockInstanceId`.** [answers What identifies the run?]
    - `requestId` is the failing request; one id is shared by every event from it, the block events and the `final` (`ecs:27`, `cec:3667-3674`). It is the id the DevTool and `fsdev run` show for a request (`packages/fsdev/src/commands/run.ts:488-496`, `:683`; `debug-a-run.facts.md` facts 64 and 78 cite the request separator). **[page: this is the tag to search a Sentry issue by, then find the same request in the DevTool.]**
    - `sessionId` is the session the request ran in; absent on a request with no session (`ecs:32`). **[page]**
    - `userId` is the caller (`ecs:31`). **[page: Sentry `user: { id }`. State that the id is whatever the app's auth resolved; do not claim it is an email or a name.]**
    - `blockInstanceId` is `${requestId}:${blockPath}` and excludes the attempt, so every attempt of one block shares it; useful to group retries (`ecs:37`; `ec:51`). `blockPath` is the block's position in the execution tree, such as `root/step[0]` (`ecs:39`). **[page: `blockInstanceId` in `extra`]**
19. **Tags vs extra.** The guide puts low-cardinality values in `tags` (`flow`, `action`, `block`, `code`) and ids in `extra` (`requestId`, `sessionId`, `blockInstanceId`, `attempt`), and says why: tags are searchable and group, `extra` is free-form (`guide`, "Write the adapter"). That is Sentry's scope model, not the framework's; the page says it in one sentence and links to Sentry's docs rather than restating them. **[page; the grouping behaviour of Sentry itself is not verified here. The page does not describe how Sentry groups issues.]**
20. **`level`.** The guide reports `retryable` errors as `"warning"` and the rest as `"error"`, on the reasoning that a retryable failure may still recover (`guide`; `ec:96`). That reasoning holds for a block event and not for a `final` (fact 15). **[page: if the page forwards `final` only, every event is a request that really failed, so `level` is a fixed `"error"` and the retryable split is dropped. If the page forwards block events, keep the split.]**
21. **`error.message` and `details` leave the server in what you send.** `captureException(event.error)` sends the normalized error's message, code and `details`, which a block put there, and `cause`. The caller-facing error item carries message, code and details and no stack (`wsf`, "What the caller sees"; the C-19 facts cite `eng/...` for it). Whether Sentry's SDK serializes `cause` and `details` is Sentry's behaviour, not verified. **[page: one line telling the reader that `details` and `cause` can hold what the block threw, and that Sentry's own scrubbing settings apply. Do not claim the framework scrubs anything: it does not, in `ecs`.]**

## Stored parts: who owns it, who sees it, where, how many

The page wires a callback and stores nothing of its own. Two things hold data around it.

| Part | Owner | Who can see it | Where it is stored | How many |
| --- | --- | --- | --- | --- |
| The capture event | Not stored by the framework. It is built per failure and handed to the callback (`cec:3679-3697`) | Whatever the callback sends it to: here, the Sentry project | Sentry's, not the framework's.
