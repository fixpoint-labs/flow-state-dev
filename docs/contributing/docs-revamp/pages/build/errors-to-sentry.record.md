## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You want every failure in the support app's `reply` action to land in Sentry. Do you wire `errorCapture` or an `onErrored` hook, and why?
   Answer: `errorCapture`, an option on `createFlowState` from `@flow-state-dev/engine`, passed in `fsdev.config.ts` (`errorCapture: captureToSentry`, the adapter in `src/lib/capture-to-sentry.ts`). It is off by default and gets an `ErrorCaptureEvent` carrying the request, session, user and block identity. `onErrored` is the in-flow alternative: a block set on an action or request that runs only when a request ends failed and receives only `{ requestId, actionName, error }`, with no userId, sessionId or block name (facts 1, 6, 7, 22, 32).
2. A teammate sees a Sentry issue for a failed `reply` and wants to open the same run in the DevTool, and to know which customer hit it. Which event fields do you attach, and where do they go?
   Answer: Use `requestId` to find the run. Every event from one request shares it, both the block events and the `final`, and it is the id the DevTool and `fsdev run` show. Use `userId` for the caller, sent as Sentry `user: { id }`. It is whatever the app's auth resolved, not necessarily an email or a name. `sessionId` (missing when the request has no session) and `blockInstanceId` (`${requestId}:${blockPath}`, the same for every attempt of one block) go in `extra`. Low-cardinality values (flow, action, block, `code`) go in `tags`. Sentry's own docs govern how tags and extra behave (facts 18, 19).
3. A customer sends `reply` an unknown `orderId`. `lookUpOrder` throws `order_not_found` and the request ends failed. How many times is your callback called, and what must the adapter do so you get one Sentry issue per failed request, not two? *(edge case)*
   Answer: At least twice: one block event with `blockName: "look-up-order"`, then one `final` event (`final: true`, `scope: "request"`, the same `requestId`), sent after rescues and retries have run and the request is recorded `failed`. For one issue per failed request, forward only the `final` events and return early on the others. The other choice is to forward every block failure and skip `final` with `if (event.final) return`. The issue shows `code: order_not_found`, the thrown FlowError's own code (facts 13, 14, 33).
4. `lookUpOrder` has a retry policy with `maxAttempts: 3`. The order service is down, so every attempt fails with a network error and the request fails. You copied a filter that drops any event whose `error.retryable` is true. What reaches Sentry, and what should you do instead? *(edge case)*
   Answer: Nothing about the failed request reaches Sentry. The callback gets three block events (`attempt` 0, 1, 2) and then a `final`. The `final` carries the normalized error, and a NetworkError stays `retryable: true` on it, so that filter throws away the one report of a request that really failed. Apply a retryable filter only to block events (`!event.final && event.error.retryable`), or filter nothing. If you forward `final` only, every event is a real failure and `level` can just be `"error"` (facts 11, 15, 20).
5. Sentry is unreachable, or `captureToSentry` itself throws. What happens to the customer's `reply` request? *(edge case)*
   Answer: Nothing. The request doesn't wait for your callback and ignores its return value. A throw or rejection inside it is caught and logged at `warn`, and it never reaches the request. The DevTool and the stream still show the failure as usual. One catch: on a host that freezes the function after the response, such as Vercel, a callback still sending at that point is lost, so flush Sentry in your own deploy (facts 5, 8, 25, 27).
6. You run `fsdev dev` in a scratch directory with no `fsdev.config.ts`, trigger the unknown-order failure from the DevTool, and nothing appears in Sentry. Why, and how do you check it properly? Separately, the order step succeeded on its second attempt after one failure. Does anything reach Sentry? *(edge case)*
   Answer: Without an `fsdev.config.*`, `fsdev dev` builds its own runtime and doesn't call your `errorCapture`. The check needs the config path. Run `fsdev dev` or `fsdev run` where `fsdev.config.ts` passes `errorCapture`, run a flow that fails, and look for the issue in Sentry's Issues view. For the step that passed on its second attempt, the first failed attempt still sends a block event but there is no `final`, because the request didn't fail. Only an adapter that forwards block events reports it. A `final`-only adapter sends nothing (facts 11, 13, 23, 24).

## Reference rows

- errorCapture fires by default for every block failure, including ones a rescue or retry later recovers; each retried attempt fires its own event. Event flags: `transient` (the failing block is a high-frequency transient block such as a poll loop, so adapters can down-sample; it does not mean the failure was rescued or retried), `error.retryable` (the failure type may be retried), `attempt` (0-indexed retry attempt of the failing block). The recipe keeps the filter example and links to this row for what each flag means. → R-22 (corrected by pass 5)
- `final` event: a request that settles failed sends one more event with `final: true` and `scope: "request"`, after its failed record is written, in addition to the per-block events. It names the leaf block that threw when one is known. A failure that a retry or rescue healed never gets one, and a setup failure before any block runs does. Only a request that ends failed has one. → R-22 (corrected by pass 5)
- Per-block events and the final summary event both reach the hook, so an adapter that forwards both reports one failure twice. The code comment shrinks to a pointer to the row. → R-22 (corrected by pass 5)
