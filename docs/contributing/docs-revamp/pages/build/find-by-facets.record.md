## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A support agent saves a new ticket through the flow's `write` action, and the body reads "I was charged twice this month." When does the model classify it, and how many model calls does that take for both questions, `topic` and `status`?
   Answer: It runs during that write, once, inside the same flow turn. The classification runs on a side chain that finishes before the turn ends, so the facets are already stored when the write's turn completes. One evaluator call answers every question on the body, so `topic` and `status` together take one call (fc:12, fc:504-505; enx:279-282 shows three questions making one call; ex test/facets.test.ts:23-26). Facts 14, 15, 21.
2. The desk lead wants every open billing ticket. What do they call, what do they get back, and what does that search cost in model calls and tokens?
   Answer: They call the mounted search action (`search: { block: tickets.search }`) with `{ topic: "billing", status: "open" }`. It returns `{ keys: string[] }`, the keys of the tickets whose stored answers match both values. It returns keys, not records, so to show a title they read each ticket by key, and no order is promised. The search makes no model call and spends 0 tokens, because it filters answers stored at write time. What it does cost is a read of every ticket in the caller's scope, filtered in memory, with no index or paging. That suits a bounded set of tickets, not a corpus of millions (fc:85-90, fc:535, fc:540-546; goal Signal e2; enx:336-355). Facts 5, 34, 35, 38, 39, 40.
3. During a provider outage the model call fails while an agent saves a ticket. Does the save fail? Will the ticket turn up in a search for `{ topic: "outage" }`, or in a search that names no values? *(edge case)*
   Answer: The save succeeds: the turn completes and the body is stored, and the failure shows in the trace as a failed `evaluator` row. The ticket has no facets, so it matches no search at all, not even `{}`, which returns every classified ticket. Nothing retries. The ticket stays unclassified until it is written again or `tickets.reindex` runs, and a reindex returns it in `reindexed` or, if it fails again, in `failed` (fc:18-19, fc:367-378; enx:469-485, enx:336-350, enx:619-636). Facts 22, 23, 24, 30, 41.
4. An agent fixes a typo in a ticket's `title` (a state field), and later rewrites the ticket's body to say the issue is now resolved. Which of those edits re-classifies the ticket? *(edge case)*
   Answer: Only the body rewrite does. The collection reacts to body writes alone, so a state-only edit like the title fix runs no model and leaves the facets as they were: they describe the body as it was last written. The body rewrite clears the earlier answers and runs the model again on the new body, with nothing for the app to call. If a rewrite lands while an earlier classification is still running, the earlier answers are dropped and the newer body's answers win (fc:15-17, fc:481, fc:525, fc:20-22; enx:469-485, enx:519-524). Facts 16, 18, 25; corrections 1 and 2.
5. The team adds a third option, `account`, to the `topic` question. Do the existing tickets get re-classified? What do they have to run, and what does it cost? *(edge case)*
   Answer: Nothing is re-classified automatically. Stored facets keep answering the old questions until each ticket is run again. They run `tickets.reindex` with `{ force: true }`, which re-runs every ticket that has a body (a plain reindex only classifies tickets with no facets). It runs the model once per ticket it classifies and returns `{ reindexed, failed }`. Tickets written before the collection had facets also stay out of every search until a reindex classifies them (fc:92-93, fc:551-563, fc:98-101; enx:585-617, enx:619-636). Facts 29, 30, 31, 33, 47.
6. Two support agents each have their own tickets in the user-scoped collection. When one of them runs the search, whose tickets come back, and can they ask for the other agent's? *(edge case)*
   Answer: The search covers the signed-in user's own tickets in the current organization only, because the collection is `scope: "user"` and the search lists it as the run's scope resolves it. The search takes no user argument, so it cannot be pointed at another user's tickets (fc:540; sas:491; col:298-299). Fact 45, marked verify: no test runs a search as a second user, so the page should state it only as "the signed-in user's tickets" and link to the scope rules.

- defineFacetedCollection: fields, what it returns (collection, search block, reindex block), the evaluator's input (the ticket body), and the definition-time refusal when questions are a function. → R-08
- Reserved record fields on a faceted collection: `facets` and `indexedAs`, and the refusal when `stateSchema` declares them (plus the full list of definition-time refusals the page already points at). → R-08
- When classification runs: every body write inside a flow turn, whatever its source (action, tool, agent). The recipe keeps only the writeContent call in the example. → R-08
- Facet search: input (one optional value per choice question), output (`keys`), unfaceted records never match, search used as an agent tool exposes options as allowed values. Link to `minConfidence` and search options already on that page. → R-08
- Classification timing and failure: runs as a side chain after the save; a failed classification leaves the save intact and the record unfaceted until reindexed; answers from a superseded body are discarded (last write wins). The side-chain failure rule itself is also a row on the sequencer page. → R-08
- Reindex block: input (`force`), which records it selects (unfaceted by default, all with force), output (`reindexed`, `failed`). The recipe keeps one sentence and the call. → R-08
- Reindex failure behavior: failed records are listed in `failed` and are never retried automatically. → R-08
