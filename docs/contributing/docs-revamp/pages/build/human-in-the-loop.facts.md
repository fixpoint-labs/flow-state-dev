## 1. The scenario, mapped to what exists

The tutorial builds one flow end to end. Suggested shape (names are the page's):

## 2. The four questions, for each stored part

| Part | Owns it | Who can see it | Where stored | How many |
| --- | --- | --- | --- | --- |
| The paused request (its record and item log, including each finished block's recorded output) | the user who sent it, in one organization and tenant | its owner, through the session routes, the stream and the status call | the request store (the app's `stores`) | one per request; a session holds many |

Facts behind the cells:

- A request is "one run of one action on one session": `apps/docs/docs/glossary.md:71` (from the C-15 sheet; not re-read). Its status reads `suspended` while it waits: `con/types/request-status.ts:11-18`; `sx:31-85`. [page]
- When a block pauses, the runtime saves a suspension record, emits a `suspension` item on the stream and closes the stream cleanly. Nothing blocks a thread; on serverless the function returns. `hitl:24`. [page]
- The suspension item carries `suspensionId`, `suspensionStatus`, `reason`, `kind?`, `expiresAt?`, `title?`, `message`, `data?`, `resumeSchema?`, `allow?`: `con/items/types.ts:712-745`. The resolution arrives as a `suspension_resume` item with `suspensionId`, `resolution`, `resolvedBy?`, `resumeData?`, `resolvedAt`: `con/items/types.ts:769-781`. [page: item names and `message`]
- The record's and item's `userId` is the request's owner, so "who owns it" is the signed-in user the request ran as. `eng/src/routes/resume-routes.ts:218`. [page]
- The DevTool's Suspensions tab "lists suspensions for the current session — pending ones at the top"; it reads through gated debug endpoints that are off by default and loopback-only; it needs durable execution. `dx` "Managing suspensions in the DevTool" (line 395-401 of the file). [page: one clause]
- Checkpoints of an in-progress or suspended run are never pruned by age: "A flow parked on a slow human-approval gate for a week is safe." `dx` (line 359, "The one invariant worth internalizing"). Resolved suspensions are removed only if `durabilityRetention` is set: "Omitting `durabilityRetention` entirely leaves records in place — nothing is deleted without you asking for it." `dx` (line 355). [ref]
- A pause with no `timeoutMs` waits until it is answered, stopped or cancelled. `dx:143` (`timeoutMs` row); `core/src/types/suspend-for-user.ts` header ("A stop with no `deadline` ... else none"). [page: one clause under step 6]

## 3. Step 1 and 2: pause for a decision

- `ctx.suspend!(options)` returns a promise. On the first run it never returns: the framework stops the step, saves the pause, emits the `suspension` item and ends the stream. On the resumed run the same call returns the answer. `core/src/types/block.ts:580-589`; `hitl:24-26`. [page]
- The request's status is `suspended` after the action's first call, and `runAction`'s result carries a `requestId`: `sx:600-625`. For a client, `sendAction` resolves when the stream ends; the `suspension` item is in `session.items`. [page: items; `sendAction` signature `rx/hooks/useSession.ts:441-445`: `(action: string, input: unknown, options?) => Promise<ExecuteActionResponse>`]
- `reason: "user_approval"` defaults `allow` to `["approve", "reject"]`; `reason: "user_input"` defaults to `["submit"]`; add `"skip"` to make a step optional. `se:46-52`; `core/src/errors/resolve-allowed-actions` (named at `se:15`). [page: approve and reject; the rest [ref]]
- It needs durable execution. A host without it refuses at the call, records the request `failed`, holds nothing, and says how to fix it. `eng/src/context/createExecutionContext.ts:221-225` (message: "stopping for a person needs durable execution, which is on by default wherever stores persist ... - `fsdev run` on this flow exits 0 at the pause and prints "waiting for a person" with the suspension, request and session ids and where the store is: `cli:64-76` (the "When a run waits for a person" block); `goals/durable-by-default/a-local-stop-is-held-and-answered/goal.md:12` (leg a). ## 6. Step 5: resume, and what runs again

- **Same request.** Resume continues the same request id; there is no second request. The log reads: the items before the pause, the `suspension` item, a `suspension_resume` item, the items after, on one record with continuous sequence numbers. `dx` (lines 169, 185-205); `hitl:28`; `sx:436-546`. [page]
- **What does not run again.** On resume, every block that already finished is replayed from its recorded output, not run: `sx:599-660` (`preSpy` called once). With the refund flow: `proposeRefund` runs once; `approveRefund` runs again; `sendRefund` runs once, after the answer. [page; answer to cold-read question 3]
- **The block that paused runs again from the top.** On resume `approveRefund` re-executes and its `ctx.suspend!` call now returns the answer: `dx` intro ("runs the suspended step again — this time returning the resume data instead of suspending"); `hitl:26`; `ks:95-110` (`approvalGateStep`'s comment: "On resume the operator's *action* decides the outcome: approve makes ctx.suspend RETURN the resume data; reject makes it THROW"). Any side effect placed before `ctx.suspend!` in that block would run twice: `gen:84-93`; `gsx:878-926` (unguarded counter 2, `runOnce`-guarded 1). The page states the rule once ("pause before the work"). `ctx.runOnce(key, fn)` guards pre-gate work; `core/src/types/block.ts:571-585`. [page: rule in a sentence; `runOnce` [ref]]
- **A generator rebuilds its conversation from the item log**, so a resumed run costs the same model calls as an uninterrupted one from the approval point forward; a tool that finished before the gate is not run again; only the gated tool re-enters. `gen:59-64`; `gsx:134-197`, `gsx:679-745`. [page: section 8]
- **The resume payload is the human's answer, not the block's output.** `approveRefund` returns what it chooses (e.g. `{ approved: true }`); `ctx.suspend!` returns the `data` sent with `approve`/`submit` (`undefined` for a bare approve). `hitl:80` casts `decision as {...}`; `gen:93` ("The resume payload is the human's decision, not the tool's output"); `eng/src/context/createExecutionContext.ts:4419` (`return resumeCtx.data`). [page]
- **A gate's answer when the human sends data.** `approve` with `data` validates against `resumeSchema` when `data` is sent; a bare approve does not; `submit` always validates. `eng/src/routes/resume-routes.ts:198-216`. [page: skip; Reference. The tutorial's gate takes no data]
- **Items the second run emits.** A block that emits a message before `ctx.suspend!` and runs again on resume shows its emit once in the canonical view. `ks` header comment (lines 1-30); `sx:1120-1180`. [ref]
- **Rejection path in the log**: a `suspension_resume` item with `resolution: "rejected"` and then the rescue handler's items. `con/items/types.ts:769-781`. [page]

- Durable execution is on by default over stores that persist (filesystem, SQLite, Postgres), off over in-memory stores. `durable: false` turns it off; `durable: true` turns it on over in-memory stores, "tests only". `eng/src/flowstate/types.ts:307-319`; `eng/src/durability/default-durability.ts:1-31`; `dx` table "`durable` | Persisting stores | In-memory stores". - With no `stores` (the in-memory default) `createFlowState` runs, startup says nothing persists, and a stop fails. `eng/src/flowstate/types.ts:169-173` ("omitted: in memory ... - The pause is not tied to a process: any process on the same store picks it up. `sfu:466-518` (a new engine over the same stores answers the stop; the request completes). `dx:28` ("held until someone answers it, across a restart" per the C-15 sheet; not re-read). [page]
- What a restart does to the pause: nothing. The request stays `suspended`; the page reads it from the store again; an answer continues it. `goals/durable-by-default/a-local-stop-is-held-and-answered/goal.md:7-8`. [page]
- No time limit unless set: a flow "parked on a slow human-approval gate for a week is safe" (`dx` line 359), because its checkpoint is not pruned by age. A pending suspension with no `expiresAt` is never expired by the sweeper. [page: one clause; mechanics [ref]]

- A crash is a different state from a pause: a request that died is `interrupted` and is continued by the user (Continue), not answered; a suspended request is not interrupted. - After a deploy the next resume uses the new code. ## 9. What it gets you (each point observable in the refund flow)

- **A wait costs nothing while it lasts.** The run is a record in the store; the stream closes cleanly; on serverless the function returns. `hitl:24`. [page]
- **The approver's page is a view of a list of items.** `useSuspensions` derives its list from `session.items`, so a page that holds the session's items can show, approve and reject. `us:121-153,226-262`. [page]
- **After the answer, only the paused block runs again.** The order lookup and the proposal are not repeated; the model is not asked again for finished turns. `sx:599-660`; `gsx:134-197`. [page]
- **One log for the whole story.** Items before the pause, the `suspension` item, the `suspension_resume` item (who answered and how) and the items after are one ordered list on one request. `dx` (lines 185-205). [page]
- **The pause survives a restart or a deploy** on a store that persists. `sfu:466-518`; `goals/durable-by-default/a-local-stop-is-held-and-answered/goal.md`. [page]
