## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A customer asks the support desk for a $250 refund. The `refund` action runs `proposeRefund`, then `approveRefund` calls `ctx.suspend!({ reason: "user_approval", message })`. Nobody approves for two days. Where is the run during those two days, and is anything running or holding a thread while it waits?
   Answer: Nothing is running. The request is a record in the store with status `suspended`. When `approveRefund` paused, the runtime saved a suspension record, put a `suspension` item on the stream and closed the stream cleanly. On serverless the function returns. A pause with no `timeoutMs` waits until someone answers, stops or cancels it, and a suspended run's checkpoint is never pruned by age, so a week-long wait is safe (facts section 2: hitl:24, con/types/request-status.ts:11-18, dx line 359; section 3: core/src/types/block.ts:580-589).
2. You build the approver's page with `useSuspensions(session, { reasons: ["user_approval"] })` and show one row per `pending` entry. Where does that list come from: a database query, an API route, or something else? Why would the page miss a refund request that another tab sends while it is open, unless you change one option?
   Answer: The list comes from the session's items. `useSuspensions` reads `session.items`, and any `suspension` item with no `suspension_resume` item for the same `suspensionId` counts as pending. It queries no store or route of its own. Each row's text is `item.message`, the string `approveRefund` passed to `ctx.suspend!`. By default the session view reads on mount and as the page's own actions run. To hear requests it did not send, such as one from another tab, the page opens the session with `useSession(sessionId, { live: true })` (facts section 0 item 5, section 4: us:121-153, us:226-262, rx/hooks/useSession.ts:272-297).
3. The approver clicks Approve on the $250 refund. Of `proposeRefund`, `approveRefund` and `sendRefund`, which ones run again and which run for the first time? If you had put the money transfer inside `approveRefund`, before its `ctx.suspend!` call, what would go wrong?
   Answer: `proposeRefund` already finished, so it does not run again: the resume replays its recorded output. `approveRefund` runs again from the top, and this time its `ctx.suspend!` call returns the answer instead of pausing. `sendRefund` runs once, for the first time, after the answer. It is still the same request id, with one log: the items from before the pause, the `suspension` item, a `suspension_resume` item, then the items from after. Work placed before `ctx.suspend!` inside the paused block runs twice, so the transfer would be sent twice. The rule is to pause before the work, with the send in its own later step (facts section 1: sx:599-660; section 6: dx intro, ks:95-110, gen:84-93, gsx:878-926).
4. Your team deploys while three refund approvals are waiting, and the server process restarts. What must `createFlowState` be configured with for those three requests to still be approvable afterwards? What happens if `stores` was left out, as in the default setup? *(edge case)*
   Answer: `createFlowState` needs a store that persists, for example `createFlowState({ flows: [support], stores: sqliteStores({ filename: "support.db" }) })`, or `postgresStores` from `@flow-state-dev/store-postgres`. Durable execution is on by default over a persisting store, so no `durable` flag is needed. The pause is not tied to a process. After the restart each request is still `suspended`, any process on the same store can pick it up, and an answer continues it. With no `stores`, the app runs in memory and startup says nothing persists. Worse, the pause itself fails: the request is recorded `failed`, nothing is held, and the error says to use durable execution. `fsdev dev` and `fsdev run` with no config use a local SQLite file, so they do hold the pause (facts section 3: createExecutionContext.ts:221-225, sx:358-397; section 7: eng/src/flowstate/types.ts:169-179 and 307-319, sfu:466-518, cli:78-92).
5. The approver rejects the refund instead. What happens inside `approveRefund`, and how does the request end if you wrote nothing extra? What do you add so the customer gets told instead? *(edge case)*
   Answer: Rejecting makes `ctx.suspend!` throw `SuspensionRejectedError` inside `approveRefund`, so its `return` never runs and `sendRefund` never runs. With no rescue handler, the request ends in an error whose message contains "rejected". To tell the customer, add `.rescue([{ when: [SuspensionRejectedError], block: notifyRejected }])` to the `handleRefund` sequencer, importing `SuspensionRejectedError` from `@flow-state-dev/core`. The log then shows a `suspension_resume` item with `resolution: "rejected"`, followed by the rescue handler's items (facts section 3: sx:293-356, dx lines 233 and 263-276; section 6: con/items/types.ts:769-781).
6. On a signed-in app, a support manager logs in as a different user, opens the customer's session and clicks Approve. Does the refund go through? And who does the log record as having answered, if the request body includes a `resumedBy` field? *(edge case)*
   Answer: No. Only the user who owns the request, in the same tenant and organization, can answer it. Any other signed-in caller gets the same answer as for a request that does not exist (404). So in this tutorial the approver's page is a second page of the same user's app, such as another tab, a phone or an admin screen, not a second person. The log records who answered from the signed-in caller, the request's owner, and ignores a `resumedBy` in the body (facts section 0 item 1: route-utils.ts:190-211, request-principal.ts:42-54, resume-routes.ts:101-110; section 5: resume-routes.ts:218).
