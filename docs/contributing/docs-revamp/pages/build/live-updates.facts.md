## Step 1: What changes without a request  **[answers Q1 in part]**

6. **The problem.** A screen that shows data other users or agents change goes stale until it reads again (`g:5`). Another worker answering, a task finishing in the background, another tab: none of them is a request this screen made. **[page: opening]**
7. **A notice says that, not what.** The server tells the screen when something under a topic changed; the screen then makes the read it already makes. Nothing about the data travels with the notice, and every read is checked on the server like any other (`g:7`; `cn:6-9`: "carries no rows"; `ph:3-4`; `ac:470`). **[page, once]**
8. **What a change is.** A change is one of seven kinds (`cn:11-29`): `items` (an item was kept under one of the session's requests), `request` (a request was created, its status moved, or it was deleted), `run` (a session record was written: the topic's own session or a run under it), `state` (a session, user or org patch), `resource` (a resource under the scope was written, created or deleted), `board` (a row on a task board changed), `resync` (the bus may have missed notices). **[ref `reference/client`: the page names at most `items` and `request`; the others are a row.]**
9. **Where it works.** One WebSocket per client on `serve()` from `@flow-state-dev/node`, which includes `fsdev dev` and `fsdev serve` (`g:103-104`; `ac:Which hosts`, `sv:107-112`). Vercel, Next.js and `createServerApp` alone (Lambda, Bun, Deno) have no push: the read runs every `pollIntervalMs` (`g:105`; `packages/node/src/app.ts:36-43` default `servesPush: false`, reports `push: null`). `FlowCapabilities.push` is the advertisement and is `null` on a host with none (`packages/client/src/types/index.ts:115-124`). **[page: two sentences. The reader writes the same code for both: `g:107`, `ph:34-37`.]** **[ref: the per-host table.]**
10. **Timing.** On a push host the read runs within about a second of the change being saved: three replies shown 4, 3, 2 ms after saved in the goal's pass; the goal's bar is under 1000 ms (`wsg` Signal `a:within-1s`; verdict log, the 2026-11-03 PASS rows). On a host with no push, within one poll interval plus the read: the bar is under 3000 ms with a 2 s interval (`wsg` `c:no-push`). **[page: "within about a second" for push; "the next tick" for no push. Do not quote the milliseconds.]**
11. **Idle cost.** With push up and the bus crossing, the screen makes 0 reads over a 10 s idle window, even with a reply in a session it does not watch (`wsg` `a:no-read-between`). **[page: "No timer runs while the socket is up", with the caveat in fact 16.]**

## Step 2: Subscribe on the page  **[answers Q1]**

12. **The hook.** `useSubscription(topics, read, options?)` runs `read` again when something under `topics` changes (`us:2-3`). `topics` is `readonly WireTopic[]`; `read(notice, signal)` may return a promise; `options` is `{ pollIntervalMs?, enabled?, client? }` (`us:25-61`). It returns `void` (`us:62`). **[page]**
13. **The first read is the screen's.** See correction 3. The page shows a `useEffect` that makes the first read, then the subscription. **[page]**
14. **A burst is one read.** One read in flight and at most one waiting: a burst of changes runs the read once more after the one in flight finishes, not once per change (`us:8-10`; `ust:folds a burst of notices into one read in flight and one waiting` **[test]**; `g:42`). **[page, one sentence]**
15. **What `read` receives.** The notice that woke it, `{ topic, kind, origin? }`, or `null` for a connect, a reconnect, a timer tick, a change in whether push reaches every server process, or a waiting read that stands for several different notices (`us:14-18`; `ust:passes the read the notice that woke it, and null for a connect or a tick` **[test]**; `ust:gives a waiting read that stands for different notices null` **[test]**; `ph:44-48`, `ph:172-176`). Several notices from different requests also give `null` (`ust:gives a waiting read null when its notices came from different requests` **[test]**). A reader who ignores the argument and re-reads everything is always right. **[page: say "read everything on `null`"; the rest is Reference.]**
16. **`pollIntervalMs`.** The pace the client calls `read(null)` wherever push can miss a change: the host has no push, the socket is down (from the first failed reconnect), or the server process the socket reached cannot hear the others (`us:25-31`; `ph:19-33`). Omit it and there is no timer: the read then runs on a notice, a connect and a reconnect only (`us:28-30`; `ust:omits the poll interval when the screen does` **[test]**; `g:108`). With it, the timer is off while the socket is up and covers the topic (`ph:166-170` `covered`, `ph:178-190`). **[page: "Set `pollIntervalMs` so a host with no push still stays current; the same code runs on both." The default in `client.live` is 3 s (`lr:34`, `lr:105`), but `useSubscription` passes `null` when you omit it (`us:78`: `pollIntervalMs ?? null`): the hook has no default timer. **[contradiction with a careless reading of `lr:106`: for the hook, omitted means no timer.]**]** **[page: say a host with no push and no `pollIntervalMs` never updates.]** That follows from `ph:172-176` and `ph:332-336`: no push means no connect call, and no timer means no tick.
17. **`enabled: false` subscribes nothing**, as does an empty topic list (`us:38-40`, `us:74`; `ust:subscribes nothing while disabled or with no topics` **[test]**). **[page, one clause or ref]**
18. **Stable subscription.** A new array with the same topics keeps the subscription, and the latest `read` is the one called (`us:56-60`, `us:63-67`; `ust:keeps one subscription across renders with an equal topic list, and calls the latest read` **[test]**). So the reader need not memoize `topics` or `read` for the hook's sake. **[page: one sentence, because a reader will otherwise wrap everything in `useCallback`.]** Changing the topics subscribes the new ones and closes the old (`ust:subscribes again when the topics change, and closes the old one` **[test]**). Unmount closes the subscription (`ust:subscribes its topics through the client...`, **[test]**).
19. **Unmount while a read is out.** `signal` aborts when the subscription ends (unmount, or topics or options change); a read already running still finishes, so a read that awaits checks `signal.aborted` before it sets state (`us:20-26`; `ust:aborts the signal a running read holds when the hook unmounts` **[test]**, `ust:aborts a running read's signal when the topics change` **[test]**). A waiting read is dropped on unmount (`ust:drops a waiting read on unmount` **[test]**). **[page: the example checks `signal.aborted` before `setRequests`.]**
20. **Which client.** Under `FlowProvider`, the hook subscribes through the provider's client; one client means one socket across every hook under one provider (`ust:shares one client, and so one socket, across hooks under one provider` **[test]**); two providers have two clients (`ust:gives each provider its own clients` **[test]**). An app with its own client, its own `fetcher`, passes `client` so the socket signs in the same way (`us:30-34`; `ust:subscribes through a host's own client when it passes one` **[test]**). **[page: one sentence; the credentials detail is fact 25.]**
21. **Outside React.** `fsd.subscribe(topics, { onChange, pollIntervalMs? })` returns `{ close() }`; every `subscribe` on one client shares one connection, and the last `close()` closes the socket (`g:83-97`; `ph:2-10`; `cl:560`; `ac:468-491`). **[page: a link to `reference/client`, not a section.]**

## Step 3: Scope it  **[answers Q1 and Q2]**

22. **Three topics, no others** (`cn:31-32`): `topic.session(id, options?)` (a session, by id), `topic.user(options?)` (the caller's own user scope) and `topic.org(options?)` (the caller's organization) (`cn:50-65`). All three take `{ resource }` to watch one resource under the scope. **[page: a three-row table, which is within the six-row cap.]**
23. **What each covers.** `topic.session(id)`: its requests, their items, runs started under it, and changes to its task boards (`g:46`). `topic.user()`: the user's own scope and their sessions, with a `"run"` notice when one is created, titled or deleted, or a request in one starts or ends (`g:47`; `ac:226`). `topic.org()`: the organization (`g:48`). **[page]** The user topic is how a session list stays current; `useSessionList` does it for the reader (`ac:226`). **[ref/link, not repeated.]**
24. **Narrowing.** A topic with `{ resource }` hears only that resource; a topic without it also hears changes narrowed to a resource under it (`ac:497`; `ph:44-48` "the same resource unless the subscription's topic names none"). So a screen on `topic.session(id, { resource: "plan" })` is not woken by a long reply, whose `items` notices go to the unnarrowed topic (`g:65`; `rd:273-274`). **[page: the recipe's "scope it" step. The reason to narrow: a reply streaming into the session sends many `items` notices.]** **[verify: that `items` notices are not delivered to a resource-narrowed topic follows from the cover rule at `ph:47-48`; it is also what `goals/realtime/app-views-read-on-notice/goal.md` `b:as-short` shows for request views, which use the live read's `hear` filter, not narrowing. For the narrowed-topic claim itself no test in this checkout pins it, so the page states the cover rule, not the measured result.]**
25. **Filter on kind instead.** The read can return early on a notice it does not care about: `if (notice !== null && notice.kind === "items") return;` (`g:57-61`). `null` and `"resync"` must always read everything (`g:63`; `lr:119-120`: a `resync` is always heard). **[page: the example's callback, one line, because the example's read is a request list that does not need item deltas.]**
26. **What the notice names.** `origin.requestId` names the request that made the change, when one did (`g:63`; `ac:499`). **[ref]**
27. **To a session's own items, use `useSession`, not a subscription.** `useSession(sessionId, { live: true })` and `fsd.sessions.stream` send the items themselves (`g:135-137`). `useSession(..., { live: true })` also subscribes the session, user and org topics, so `useClientData`, `useResourceCollectionList` and `useResource` follow a change from any session, and skip a change their own request made (`g:131-133`; `packages/react/src/hooks/useSession.ts:285-298`; `apps/docs/docs/api/react.md:106`). **[page: one "when not to use this" sentence with the links. It is how the reader decides between three tools, and it answers Q1.]**

### Who receives it  **[answers Q2]**

28. **A caller hears only what they may read.** Each topic is checked on the server when the connection opens, with the same check the matching read uses (`g:127`; `pd:140-148`: "The check the session stream answers to"). A topic the caller may not read is left out, as a session that does not exist is, and the screen never hears of it (`g:127`; `pd:145`; `wsg` `b:c-never-hears`: a user subscribed to another user's session has their handler run 0 times). **[page]**
29. **User and org topics name no id.** The server fills them from the signed-in caller, so a screen cannot ask for someone else's (`g:50`; `cn:6-9`; `pd:148-153`). An anonymous caller in an app that authenticates anything gets none (`pd:149-151`). **[page, one sentence]**
30. **The socket signs in through the client's `fetcher`.** A bearer token the fetcher adds proves who the socket is, and so does a cookie (`g:127`; `ph:23-27`; `ac:Which hosts`). **[page: one clause; the detail is Reference.]**
31. **A topic left out is asked for again.** With `pollIntervalMs`, at each tick; without it, on reconnect (`ph:29-32`; `g:127`). So access given back starts working without a reload. **[ref]**
32. **An open socket is not rechecked.** If a user loses access while the tab stays open, their reads are refused at once and the socket may still say that something changed, never what, until it reconnects; the server closes every socket after an hour, and the reconnect checks again (`g:129`; `packages/engine/src/push/socket-session.ts:14`, `:33`, `:104`: `maxAgeMs: 60 * 60_000`). `wsg` `b:revoked`: after a token is revoked and the socket dropped, the handler runs 0 more times. **[ref `reference/server`]**
33. **More than one server process.** The default change bus lives in memory and is for an app that runs as one process; the `bus` slot of the stores profile can hold one that crosses (Postgres stores fill it by default) (`g:112`; `nd:70-75`; `packages/engine/README.md:84`). Several processes behind one address need one shared `pushSecret` (or `FSD_PUSH_SECRET`), or a connection that lands on another process is refused and the screen reads on its timer until a retry lands (`g:113-123`; `sv:54-60`, `sv:413-414`). `push: false` on `serve()` turns push off (`sv:47-52`). **[ref `reference/server`; the page links.]**
34. **A change another process writes, on the in-memory bus, reaches an open view only at its next read** (`g:112`; `nd:70-75`; `wsg` `c:second-process`: with the socket on a second process, the read shows the first process's reply within one poll interval plus a second). **[ref; the page's one-process line is enough: "With several server processes, see [Reference]."]**

## The four questions: stored parts

This page is about a notice and a read; it stores nothing. A notice carries no row (fact 7) and the screen's list is React state in the reader's own component. The framework keeps no per-screen record of what a client heard. The change bus (`bus` slot of the stores profile) holds transient notices and is covered by `reference/server`, not stated here. **[page: no stored part, so the four questions are n/a; the page does not invent an owner.]**

| Part | Who owns it | Who can see it | Where stored | How many |
|------|-------------|----------------|--------------|----------|
| The screen's list | The reader's component (React state) | The user at that screen | Browser memory | One per mounted component |
| The subscription | The client the hook uses | The client | In memory; one socket per client | One socket per client, one handle per `useSubscription` call (`ph:2-10`) |
| The signed-in identity of the socket | The server, from the verified caller | n/a | A signed ticket minted on `POST /users/:userId/stream` (`ph:202`), valid for one connect | One per socket |
