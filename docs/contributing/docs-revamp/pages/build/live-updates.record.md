## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk has a screen that lists the requests in one conversation. While an agent is looking at it, a teammate's worker answers in that same session. Which hook keeps the list current, and how does the screen find out about the new request?
   Answer: `useSubscription(topics, read, options?)` from `@flow-state-dev/react`. It runs `read` again when something under the topics changes (us:2-3). The server sends a notice that something changed under the topic, never what changed or any rows. The screen then makes the read it already makes, here `fsd.sessions.requests(sessionId)`, and that read is checked on the server like any other (fact 7: cn:6-9, g:7; correction 1). The topic is `topic.session(sessionId)`, which covers the session's requests, their items, runs under it and its task boards (facts 22-23, g:46).
2. The agent's reply streams into that conversation and sends a flood of `items` notices. The request list doesn't need item deltas. How do you stop each one from causing a re-read, and which notices must the read never skip?
   Answer: Two ways. Narrow the topic with `{ resource }`: a narrowed topic hears only that resource, so a streaming reply's `items` notices don't reach it (fact 24, ac:497, ph:44-48). Requests are not a resource, so the request list can't narrow (fact list, example notes). It filters on kind in the callback instead: `if (notice !== null && notice.kind === "items") return;` (fact 25, g:57-61). A `null` notice and a `"resync"` notice must always read everything (g:63, lr:119-120). A burst of changes also folds into one read in flight and at most one waiting, not one read per change (fact 14, test `folds a burst of notices...`).
3. Two agents at the desk have the same page open. Agent B subscribes to a session that belongs to agent A, which B may not read. A request in that session changes. What does B's screen receive? And could B's screen watch A's user topic instead? *(edge case)*
   Answer: Nothing. Each topic is checked on the server when the connection opens, with the same check as the matching read. A topic the caller may not read is left out, the same way as a session that doesn't exist, so the screen never hears of it. The goal measured B's handler running 0 times (fact 28: g:127, pd:140-148, wsg b:c-never-hears). User and org topics name no id. The server fills them from the signed-in caller, so B can't ask for A's (fact 29: g:50, pd:148-153). The socket's identity comes from the client's `fetcher`, through a bearer token or a cookie (fact 30).
4. You deploy the same request-list page to Vercel and don't set `pollIntervalMs`. The list never updates. And the first time the screen mounts, nothing shows until you load it yourself. Why, and what do you change? *(edge case)*
   Answer: Vercel and Next.js have no push. Only `serve()` from `@flow-state-dev/node`, which includes `fsdev dev` and `fsdev serve`, opens the WebSocket (fact 9). With no push there's no connect call, and with no `pollIntervalMs` the hook has no timer: it passes `null`, so it never reads (fact 16, us:78, ph:172-176, ph:332-336). Set `pollIntervalMs` and the read runs on each tick. The code is the same on both kinds of host, and the timer stays off while a push socket is up (ph:166-190). The hook never makes the first read for you (`readNow: false`, us:79). Keep that first read in a `useEffect` (correction 3, fact 13).
5. The agent leaves the conversation, so the RequestList unmounts, while a `fsd.sessions.requests(sessionId)` read is still awaiting. What happens to that read, and what should your callback do about it? *(edge case)*
   Answer: The read gets a second argument, an `AbortSignal`. The signal aborts when the subscription ends: on unmount, or when the topics or options change. A read that is already running still finishes, so before it calls `setRequests` it checks `signal.aborted`. A read that was waiting is dropped on unmount (fact 19, us:20-26, tests `aborts the signal a running read holds when the hook unmounts` and `drops a waiting read on unmount`). Unmount also closes the subscription (fact 18).
6. A teammate suggests three changes: wrap `topics` and `read` in `useMemo`/`useCallback`, use `useSubscription` to show the session's own streaming reply, and use it for a list that is already a view. Which of these does the recipe ask for?
   Answer: None of them. Memoizing isn't needed: a new array with the same topics keeps the same subscription, and the hook calls the latest `read` (fact 18, test `keeps one subscription across renders...`). A session's own items come from `useSession(sessionId, { live: true })` or `fsd.sessions.stream`, which send the items themselves (fact 27, g:135-137). A view uses `useView`, which names no topic because each answer carries the topics of what it read (correction 2, uv:3-15). `useSubscription` is for a read that is not a view.
