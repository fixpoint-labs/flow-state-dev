## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's `support` flow has two actions in `actions`, `lookUpOrder` and `refundOrder`. You add the MCP adapter to `createFlowState` in `fsdev.config.ts`, but you change nothing in the flow. A client sends `tools/list` to `/api/flows/support/mcp`. What does it get back, and what do you have to add? *(edge case)*
   Answer: It gets a JSON-RPC `-32601` error (`Flow "support" is not exposed via MCP.`), not a tool list. A flow is exposed only when it sets `mcp: { enabled: true }`. The default is false (`ft:330-342`, `ad:222-229`, test `at:502`). Mounting `createMcpTransportAdapter()` once in `createFlowState({ adapters })` is needed but not enough on its own.
2. With `mcp: { enabled: true }` on the `support` flow, which of its actions become tools, what is each tool called, and what do you write so that `refundOrder` stays off the tool list?
   Answer: Every action in the flow's `actions` becomes a tool unless it opts out with `mcp: { enabled: false }` (`tc:76`, test `at:106`). So add `mcp: { enabled: false }` to `refundOrder`, and `lookUpOrder` becomes the only tool. The tool name is the action key in snake case, so `lookUpOrder` becomes `look_up_order` (`tc:31-40`, test `at:92-103`). `mcp: { name: "..." }` on the action overrides that name (`ft:140-145`). Webhook handlers and internal actions never become tools (test `at:112`).
3. A client that read an old tool list calls `refund_order` by name after you opted `refundOrder` out. What happens? *(edge case)*
   Answer: The call fails with JSON-RPC `-32601` "Unknown MCP tool". An opted-out action is not a tool, so calling it by name is treated the same as calling a tool that doesn't exist (`ad:384-388`, test `at:489`). The action does not run.
4. Later someone adds a second action whose key also turns into `look_up_order` (for example `look_up_Order`), or leaves the description off a new exposed action. What goes wrong in each case, when, and how do you fix it? *(edge case)*
   Answer: Missing description: an exposed action needs a description, either its own or its block's (`ft:279-284`). Without one, flow registration throws and names the action (`df:1357-1370`). Actions with `mcp: { enabled: false }` are not checked. Name collision: two actions that resolve to the same tool name throw an error that names both keys and suggests `mcp.name` (`tc:85-92`, tests `at:155`, `at:175`). This happens on the first `tools/list` or `tools/call`, not when the flow is defined (`ad:339`, `ad:384`). The fix is to rename one action, or give it an `mcp: { name }` override.
5. You connect an MCP client such as Claude Desktop or Cursor to `https://app.example.com/api/flows/support/mcp`. Where does the token go, how does the flow decide who the caller is, and how would you spot those calls in the DevTool?
   Answer: Point the client at the URL and send the token in the `Authorization` header as `Bearer <secret>`. The caller is whoever the flow's `authentication.resolvePrincipal` says it is. The adapter resolves the principal once per request, through the same `host.resolvePrincipal` that HTTP requests use, with `ctx.source === "mcp"` and the native `Request` (`ad:231-246`). In the example, `createBearerSecretPrincipalResolver({ secret, principal: { userId, orgId } })` compares the header in constant time and returns that fixed principal (`bs:47-88`). The resolver must return both `userId` and `orgId` (`at_:89-92`, `at_:126-131`). Each call is recorded with `source: "mcp"` and shows an MCP badge in the DevTool (`ad:413`, test `e2e:87`, `m:144-147`).
6. A second support agent connects a client to the same server with their own token, and a third client sends a wrong token. With the bearer-secret resolver, who is the second agent to the flow, what does the third client see, and what do you do if each agent should be a different user? *(edge case)*
   Answer: With one secret there is one principal. Anyone who sends the matching secret is the same `userId` and `orgId`, which suits a personal server (`kb:168-172`). A second agent with a different token does not match. A wrong token makes the resolver throw `PrincipalResolutionError` with status 401, and the client gets HTTP 401, JSON-RPC `-32001` and `WWW-Authenticate: Bearer realm="MCP"` (`bs:47-88`, `ad:247-259`, test `at:520-540`). To give each client its own user, write your own `resolvePrincipal`: read the token, look up who owns it, and return `{ userId, orgId }`. To refuse a caller, throw `PrincipalResolutionError`. The framework keeps no token table (`m:229-237`). If a call tries to use a session that another user or organization owns, the client gets `-32602 Unknown session` (`ad:467-475`, test `at:409`).
