## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk (flow `support`, organization `acme`) has run on SQLite at `.fsdev/data/fsdev.db` and is moving to Postgres. You look for an `fsdev` command that exports one store and imports into another. What do you run, and what does the move consist of?
   Answer: There is no export or import command, in `fsdev` or anywhere in the exported surface. You write a short script: open the old store with `sqliteStores({ filename })` and the new one with `postgresStores({ connectionString })`, get each registry with `adapter.resolve(["primary"])`, read records from the old store through its store calls and write them to the new one, count both sides, then switch. Release both with `dispose()`. The Postgres target creates its tables when it opens, so an empty database needs no setup (facts §0 item 1, §1).
2. After the copy, which parts of the support desk's data are on Postgres and which are not?
   Answer: Copied: session records (state, journal, tags, metadata), requests with their items and stream events, user records, org records, and resource state and content for each scope, including `lineage` scopes. Not copied: paused runs (suspensions and checkpoints), leases, active-request entries and wakes (the new store starts with none), traces (debugging history, and Postgres keeps them in memory anyway), attachment bytes (copy the blobs folder, for example `.fsdev/blobs/<profile>`, yourself), dynamic schedules, and memoized `ctx.runOnce` results, which cannot be listed. The in-memory store can never be a source because a fresh instance holds nothing (facts §2 table, §3, §5).
3. Your script copied every session from `sessions.list()`. On SQLite `SELECT COUNT(*) FROM sessions;` is higher than the count on Postgres. What went missing, and what is the fix? *(edge case)*
   Answer: The missing ones are child sessions, meaning sessions another session started. `SessionStore.list` with no options returns top-level sessions only. Pass `parentage: "all"` to get every session, and copy each record under the `id` it came with: a tenant-namespaced id such as `t1:s1` is the record's storage key, so don't rebuild it. Then compare counts again with `list({ parentage: "all" })` and the SQL `COUNT(*)` on both ends (facts §3, §6, §8 items 1 and 7).
4. How do you know the move worked before you point the support desk at Postgres?
   Answer: Compare counts on both ends: session `list({ parentage: "all" })`, `UserStore.list()` and `OrgStore.list()` lengths, `countItems(requestId)` for each request (it counts flushed writes only, so call `flushItems` first), and for each scope the keys from `ResourceStateStore.getAll` and `ContentStore.getAll`. Compare state with state and content with content, never one with the other, because content without state never appears in a state listing. A SQL `SELECT COUNT(*) FROM sessions;` on both databases is the cross-check. Last, open one real session through the new store and read its state and resources (facts §6).
5. An agent on the support desk deleted a resource key last week, and a writer in that scope held version 7 of a resource before the move. After the move, what do they each see on Postgres? *(edge case)*
   Answer: Deletion markers do not copy, because `getAll` returns live rows only. The deleted key reads as if it was never written. Every copied resource state starts again at version 1, since `ResourceStateStore.set` takes no version to store. A writer still holding version 7 no longer matches, and it will not collide with a later recreate of the deleted key the way it would have on the old store. Scope records (session, user, org) are different: `set(id, value, "any")` stores them at the version they were read at (facts §4, §8 item 2).
6. Dana works the support desk in two organizations, `acme` and a second one. Your script ran once, failed halfway, and you run it again. Meanwhile one customer's request was waiting on an agent's approval when you copied. What does Postgres hold for Dana and for the waiting request, and how do you back out if the counts are wrong? *(edge case)*
   Answer: Dana has two user records, one per organization, and listing users with `UserStore.list()` copies both. Copy user records by what `list` returns, never by user id. On the rerun, writing with `set(id, value, "absent")` leaves alone any record the new store already holds and returns the stored one on conflict, so the second run does not overwrite anything. A stop still pending at copy time is not on the new store: stop traffic first, and answer or discard every stop (`SuspensionStore.list` shows them) before copying. Until the switch the old SQLite store is untouched, so backing out means leaving `stores` on the old adapter, or pointing it back. The switch itself is changing `stores` on `createFlowState` to `postgresStores(...)` and restarting. Once Postgres has taken new writes, it is the only correct copy (facts §2, §4, §5, §6, §8 items 3 to 6).

- Per record kind: traces, leases and dynamic schedules are not carried by a move (new store starts with no leases; schedules are recreated). Row in what each store persists, with a cross-link to the schedule index on R-33. → R-16
- The in-memory store keeps data for one process only and cannot be the source of a move. Row in what each store persists. → R-16
- Records written before flowId and orgId existed carry no attribution and arrive as stored. Row in who owns a record and what keys it. The recipe already links here. → R-16
- Write modes on a store call: "absent" writes only when the key is missing; resourceState.set honours it, content.set overwrites. A rerun is safe for records and overwrites content. Row in what a custom store must guarantee. → R-16
- session.list: returns top-level sessions by default; parentage: "all" includes child sessions. Row in the store call tables. The recipe keeps one clause because the script depends on it. → R-16
- User record identity: a user in two organizations has two records, so a user is keyed by record, not by user id. Row in who owns a record and what keys it. → R-16
- Postgres adapter creates its tables when it opens (schema initialisation). Row in store profiles or the store tables. → R-16
- A resource's state and its content are stored separately, and a resource can have content with no state. Row in the resources storage kinds table. → R-08
- Resource identity by scope: session, user, org and lineage resources are stored under that scope's own id. Row in the resource identity (path, scope, uri) table. The recipe keeps only the check. → R-08
