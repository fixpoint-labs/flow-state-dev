## Step 1: A prompt file

The page's app is the support desk. The block is `draftReply`, a generator with `model: "openai/gpt-6-luna"`, an inline `prompt: "You answer customer support messages. Be brief and specific."`, `inputSchema: z.string()`, `user: (input) => input`, `itemVisibility: { client: true, history: true }`, in `src/flows/support/blocks/draft-reply.ts` (`blocks:44-55`). **[page example: the recipe moves that inline prompt into a file.]**

9. **When to move a prompt out.** Long prose, shared fragments across generators, a prompt you review on its own. Skip it for short ones: a three-line instruction gains nothing from a file. `guide:12-21`, `gpm:12-16`. Inline prompts keep working unchanged. `gpm:8`. **[page, two sentences]**
10. **A prompt file is a `.md` file with optional YAML frontmatter, then sections.** The sections are `<system>`, `<user>` and `<context>`, each tag at most once, line-anchored. At least `<system>` is required. Text outside the tags is ignored (**[test]** `pft:122-127`); a missing `<system>`, a whitespace-only one, or two of them throws a `PromptFileParseError` (**[test]** `pft:108-120`). `gpm:43-45`, `pf:248-290`. **[page: `<system>` required; `<user>` optional.]**
11. **Naming.** The doc convention is `<name>.prompt.md` beside the generator. `guide:25-27`; `ks` has `run/assistant/prompts/ask.prompt.md` etc.; engine fixtures `packages/engine/test/fixtures/prompts/analyst.prompt.md`. The loader does not require the `.prompt.md` suffix; any path works (`ldr:184-186`). **[page: "conventionally"]**
12. **What `<system>` holds** is the standing instructions, the same text that is today in the `prompt:` slot. **[test]** `gpt:47-64` (a prompt-file `<system>` renders into the system message). **[page]**
13. **`<user>` is the fixed per-turn user message.** When the file has one, it fills the generator's `user` slot, rendered with the same variables. **[test]** `gpt:110-126`. A `user:` written on the generator beside it wins. **[test]** `gpt:128-143` (override after the spread), `gpt:173-186` (the direct form). For the support desk the generator already has `user: (input) => input`, so a file with no `<user>` leaves that line as is. **[page: one sentence; the page's example file has `<system>` only.]**
14. **Frontmatter keys.** `name, description, intent, model, caching, maxTokens, temperature`. `caching` is `true`/`false` or `{ enabled, breakpoints: "auto"|"manual", ttl: "5m"|"1h" }`; `maxTokens` a positive integer; `temperature` 0 to 2; `description` at most 1024 characters. `pf:58-70`, `pf:45-55`. Any other key throws at load (**[test]** `pft:63-70`); a string `caching` throws (`pft:82-90`). `definePromptFile` turns `caching: true` into `{ enabled: true }` (`pf:446-453`). **[ref: the table and the limits. The page names `description` only.]**
15. **A `name` in the frontmatter overwrites the generator's own.** `definePromptFile` returns `name` when the file has one (`pf:443`); it flows into the spread. A generator's name matters to the flow (items carry it), so leave `name` out. `gpm:285`, `guide:85`. Note this applies when the file is spread after the generator's `name`. In the `prompt: pf` form, the generator's own `name` wins because an explicitly set sibling wins (`gen:2876-2886`, `gpt:145-225`). **[ref: the page no longer states it; the recipe uses the `prompt: pf` form, where it does not apply. ## Step 3: Load it on a generator

26. **Install and import paths.** `loadPromptFile` and `createPromptLoader` come from `@flow-state-dev/engine/prompt-file`; `definePromptFile` and `parsePromptFile` from `@flow-state-dev/core/prompt-file`. `packages/engine/package.json:47-49`, `packages/core/package.json:59-61`; `ldr:15-24`. **[page]**
27. **`loadPromptFile(specifier, importerUrl, options?)` reads the file, finds sibling partials, and returns a `PromptFile`.** `ldr:179-206`. A relative specifier is resolved against `importerUrl` (the caller's `import.meta.url`); an absolute path is used as is and `importerUrl` is ignored (`ldr:184-186`; **[test]** `ldt:21-28`, `ldt:44-54`). It never resolves against the working directory (`ldr:162-170` doc comment). **[page]**
28. **Sibling partials.** Every other `.md` file in the prompt's directory is registered as a partial named by its filename without `.md`; the `partialsDir` option points it at another directory. `ldr:141-160`, `ldr:133-138`; **[test]** `ldt:30-36`, `ldt:64-70`. Because any sibling `.md` counts, a second prompt file in the same directory is also available as a partial. **[source]** **[ref]**
29. **A file that cannot be read throws `PromptFileLoadError`** with the specifier in the message (`ldr:191-196`; **[test]** `ldt:38-42`). A file that parses wrongly throws `PromptFileParseError` (above). Both fire when your code loads the file, at import for a module-level load. **[page: one sentence.]**
30. **Two ways to attach it to the generator.** `prompt: pf` passes the whole file: the generator takes the file's `user`, `caching`, `maxTokens`, `temperature`, `name` and `description` too, and a sibling field you set explicitly wins. `gen:595-608` (doc comment), `gen:2870-2886` (expansion), **[test]** `gpt:145-225`. Or `...definePromptFile(pf)` spreads the same fields, and whatever follows the spread overrides (`pf:429-437` doc; **[test]** `gpt:128-143`). **[page: show `prompt: pf` as the example (shortest); one sentence for the spread.]**
31. **The model stays in TypeScript.** `model`, `tools`, `inputSchema`, `outputSchema`, `context`, `history` are generator options and are not read from the file. `pf:58-59` ("no schemas, no tools, no capabilities (those stay in TypeScript)"); `gpm:45`. **[page]**
32. **`createPromptLoader(baseDir, { partialsDir?, filters? })` returns `load(relPath, { filters? })`.** `baseDir` must be absolute (throws `TypeError` otherwise, `ldr:259-264`, **[test]** `ldt:85-89`); per-call filters override the loader's (`ldr:267-270`, **[test]** `ldt:72-83`). `ks` `shared/prompts.ts` builds one for the flow and `mode-prompt.ts` loads four files with it. `resolveBaseDir([moduleDir(import.meta.url, ".."), path.resolve(process.cwd(), "flows/chat-agent")], { expect: "flow.ts" })` is the kitchen-sink's anchor. **[ref: the loader family. The page uses `loadPromptFile` and mentions `createPromptLoader` once for an app with many prompts.]**
33. **Why a second anchor under Next.js.** A bundler rewrites `import.meta.url`; `moduleDir` returns `undefined` for a non-`file:` URL, `resolveBaseDir` skips it and takes the next candidate that exists and contains the `expect` path, and throws listing every candidate tried if none qualifies. `ldr:26-50`, `ldr:64-127`; **[test]** `ldt:91-150`. **[ref; the page may say once: under a bundler such as Next.js, pass an absolute path.]**
34. **A prompt file is not available in the browser.** `@flow-state-dev/engine/prompt-file` imports `node:fs` (`ldr:15`). In a bundle, import the raw text and call `parsePromptFile(text, { sourcePath, partials })` from `@flow-state-dev/core/prompt-file` (browser-safe, `pf:10-13`). `guide:87`, `gpm:235-245`. **[ref]**
35. **`<context>`: adding one switches the template to own where context sits.** With no `<context>` section, the framework appends the generator's context after the rendered `<system>` as XML-tagged blocks. With one, that append is suppressed, the template writes the context it wants, and a key it does not render is dropped; the output is wrapped in `<context>...</context>`. **[test]** `gpt:47-64` (default append), `gpt:66-88` (override, exact output `"S\n\n<context>\n<mem>M</mem><docs>D</docs>\n</context>"`), `gpt:89-107` (a dropped key). **[ref; the page may link it. ## Step 5: A resource template (the same format on a resource)

38. **What it is.** A resource's content can be rendered from a `.md` template instead of written by hand: the template renders against the resource's own state with no model call, and the next read after a state change returns new content. `rtm:8`, `rt:2-12`; **[test]** `packages/engine/test/resource-template-render.test.ts:11-22`. **[page]**
39. **One variable: `state`.** The resource's state object, matching its `stateSchema`. No `ctx`, `input`, session state or other resources. `rtm:47-51`, `rtm:143-149`; `rt:245` (the render call passes only `{ state }`). **[page: the answer to Q2 for a resource.]** **[answers Q2]**
40. **A missing state field throws on read; use `default`.** `renderResourceTemplate` uses `strictVariables: true` and `lenientIf: true` (`rt:230-241`) and throws `ResourceTemplateRenderError` (`rt:244-250`). **[source; `renderContent` test does not cover a miss. [verify]]**
41. **Limits.** Template text over 512 KB throws `ResourceTemplateParseError` at parse (`rt:22`, `rt:129-134`); render limit 5000 ms and memory limit 1e8 (`rt:23-24`, `rt:238-240`). Property access is own-property only (`rt:236`). **[ref]**
42. **Declare it with `contentTemplate`.** `defineResource({ scope, stateSchema, contentTemplate: "./report.prompt.md", writable? })`. A string path, an `{ path, importerUrl }` object, or a parsed `ResourceTemplate`. `res:269-281`; **[test]** `packages/core/test/resource.test.ts:76-95` area (string path accepted). A bare string resolves from the working directory; the object form resolves against the declaring module first and falls back to the working directory, and throws listing every path tried if neither has the file. `packages/engine/src/resources/content-paths.ts:39-59`. **[page: show the object form with `importerUrl: import.meta.url`, one clause why.]**
43. **`readContent()` returns the rendered text; `readContentRaw()` returns the template source.** `reg:2256-2283` (both, for a parsed `contentTemplate` and for a `contentTemplateRef`). **[page]**
44. **Pre-parse with `loadResourceTemplate(specifier, importerUrl, { partials? })`** from `@flow-state-dev/engine/resource-template`; it also registers sibling `.md` files as partials. `rtl:46-86`. **[ref]**
45. **Only one content source.** `content`, `contentFile`, `contentTemplate`, `contentTemplateRef` are exclusive; `render` cannot be combined with either template field. `defineResource` throws at build time with `at most one content source` / `rejects render with contentTemplate`. `res:608-618`; **[test]** `packages/core/test/resource.test.ts:39-75`. **[page: one sentence.]**
46. **`contentTemplateRef: "<resource name>"` makes the template itself live data.** The named resource's content is the template; `readContent()` re-reads it and renders against this resource's state on every read, so a `writeContent()` on the template resource changes the next read. `res:283-287`, `reg:2272-2283` (reads the current raw content through a resolver each call, parses, renders), `rtm:109-139`. Returns `null` when the template resource has no content (**[test]** `resource-template-render.test.ts:39-51`; `reg:2281`). **[page]**
47. **The ref'd template resource's own content is what you edit.** In the guide's example the template resource sets an initial `content` string and `writable: true`. `rtm:117-122`. Edits go through `writeContent(content)` (`reg:2295-2308`), which throws a read-only refusal when `writable === false` (`reg:2296-2298`). The default for `writable` when omitted is not stated at the declaration (`res:310`, `writable?: boolean`); the write check is `=== false`, so an omitted `writable` allows the write. **[source; the page sets `writable: true` explicitly, as the doc does.]**
48. **`writeContent` on a resource with a static `contentTemplate` stores text that `readContent()` never returns.** `readContent` returns the rendered template before it looks at stored content (`reg:2269-2271`); `writeContent` has no template check (`reg:2295-2308`). **[source; page: do not tell the reader to `writeContent` on the file-backed resource. [verify] not run.]**
49. **A `{% render %}` partial inside a live template is not registered.** The `contentTemplateRef` read calls `parseResourceTemplate(rawTemplate)` with no partials (`reg:2283`); the parse check in `rt:186-203` does not look for partials, so a `{% render 'x' %}` fails when it renders. **[source, [verify] not run; keep off the page. ## The four questions for each stored part

The page stores data in two places. Both are answered from source, not from a run.

**A prompt file (`<name>.prompt.md`).**

- **Who owns it?** The app's repository. It is a source file written by the developer who owns the generator; nothing in the framework creates or edits it. `ldr:179-206` (read only).
- **Who can see it?** Anyone with the repo. At run time, a user of the app sees only what the model said. The DevTool shows the file's text in `Template Source` to whoever has the DevTool open on a dev server (`item-detail.tsx:162-170`); in a production-mode run the trace row may not carry it (item 37). **[answers Q1: the person who edits the file, in code review. The model, the user and the generator's own run cannot change it.]**
- **Where is it stored?** On disk next to the code, read with `readFileSync` when `loadPromptFile` runs (`ldr:188-190`). Not copied into the session or the store; the trace row copies the text when observability is on (`gen:3315-3322`).
- **How many exist?** One file per prompt; as many generators as you like. A generator holds one `PromptFile` in `prompt` (an array slot with several branded entries picks the first, `pf:476-488` `getPromptFileBrand`; **[verify]** no test reads an array slot, keep off the page).

**A resource template.**

- **Who owns it?** Depends on the form. A `contentTemplate` file is app code, like a prompt file. A `contentTemplateRef` template is content of another resource, owned by that resource's scope (`session`, `user` or `org`, declared by the developer: `rtm:117-132`). The scope decides whose data it is.
- **Who can see it, and who can edit it?** A file-backed template: only developers. A ref'd template: whoever and whatever may write that resource's content. Block code can call `writeContent()` unless `writable: false` (`reg:2295-2298`). A client can read or write a resource only through the resource's `client` config; one that sets none stays invisible to clients (`res:318`); writing back needs `client` with `expose` or `exclude` and a `runBy` (`res:740-770`). `llmWritable` is a separate switch for the model (`res:288-289`). **[source; [verify] the exact client edit route was not run. The page says: block code can write it; a client can only if the resource declares `client`; links Resources for the rest. [answers Q1]]**
- **Where is it stored?** A file-backed template: on disk, parsed into the resource config once (item 5). A ref'd template: as the template resource's content in the store for its scope; `readContentRaw()` on the ref'd resource resolves it through the scope (`reg:2256-2265`, `packages/engine/src/routes/resource-routes.ts:118-133`).
- **How many exist?** A file-backed template: one per resource declaration, shared by every session.
