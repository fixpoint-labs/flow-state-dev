## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's `draftReply` generator has its instructions inline: `prompt: "You answer customer support messages. Be brief and specific."`. You want that text in its own file. What does the file contain, how do you attach it to `draftReply`, and what stays in TypeScript?
   Answer: A `.md` file, by convention `draft-reply.prompt.md` beside the generator, with optional YAML frontmatter and a required `<system>` section holding the standing instructions, the same text that was in the `prompt:` slot (facts 10, 11, 12). `<user>` and `<context>` are optional. Load it with `loadPromptFile("./draft-reply.prompt.md", import.meta.url)` from `@flow-state-dev/engine/prompt-file`, which resolves a relative path against the calling module and never against the working directory. Then attach it with `prompt: pf`, or spread `...definePromptFile(pf)`, where anything after the spread wins (facts 26, 27, 30). `model`, `inputSchema`, `outputSchema`, `tools`, `context` and `history` stay on the generator in TypeScript; a `model` key in the frontmatter is metadata only and does not pick the model (facts 8, 31). The file has no `<user>`, so `draftReply`'s existing `user: (input) => input` stays as it is (fact 13).
2. You want the prompt to quote the customer's message and a value the flow keeps in session state. Where do those values come from in the template, and how do you write them?
   Answer: In `<system>` and `<user>`, three variables are in scope: `input`, `ctx` and `config` (fact 16). `input` is what the generator was called with, typed by its `inputSchema`. For `draftReply` (`z.string()`) that is the message string, so you write `{{ input }}` (fact 17). Session state is read through `ctx.session.state`, for example `{{ ctx.session.state.x }}` (fact 18). `config` is the generator's resolved config, and it is read-only (fact 19). The syntax is Liquid: `{{ }}` outputs a value, `{% if %}` branches, and `| default: ""` supplies a fallback. A JavaScript-style `${input}` comes out as literal characters, not the value (fact 21).
3. After the move, a teammate wants to soften the reply tone. Who can change the prompt: the teammate, the model, the customer? If they edit the `.md` file while the server is running, do replies change? *(edge case)*
   Answer: Only whoever changes the file in the app's repository, through normal code review. The file is source code next to the generator. Nothing in the framework creates or edits it, and the model, the customer and the generator's own run cannot change it. Users of the app see only what the model said (four-questions block, Q1). The file is read with `readFileSync` when `loadPromptFile` runs, which for a module-level load is when the module is imported. Editing it afterwards changes nothing until the module loads again, and the page promises no hot reload (fact 6). The edit is deployed with the code.
4. You make a typo in `<system>`: `{{ input.customr }}`. In a separate change, you leave `<system>` out entirely. When does each mistake surface, and how do you make a variable optional? *(edge case)*
   Answer: The typo is a render-time error. The file loads fine, and the prompt rejects with an `undefined variable` error when it renders, because `<system>` and `<user>` are strict about missing variables (facts 2, 22). A missing, empty or duplicated `<system>`, bad frontmatter (such as an unknown key), an unknown filter or a missing partial all throw `PromptFileParseError` when the file is loaded, at import for a module-level load. A file that cannot be read throws `PromptFileLoadError` with the path in the message (facts 2, 10, 29). For an optional value, use `| default: ""` (fact 22).
5. A teammate adds `name: reply-drafter` and `model: some-other-model` to the prompt file's frontmatter. What happens to `draftReply`'s name and model? *(edge case)*
   Answer: `model` does nothing: frontmatter `model` is metadata only, and the model stays the one set in TypeScript (fact 8). `name` depends on how the file is attached. With the spread form `...definePromptFile(pf)` placed after the generator's own `name`, the file's `name` overwrites it. A generator's name matters to the flow, because items carry it. With `prompt: pf`, the generator's explicitly set `name` wins (fact 15). The advice is to leave `name` out of the file.
6. The support desk wants a session summary resource whose content is rendered from a Markdown template. What can the template read? What changes if you declare it with `contentTemplate` (a file) versus `contentTemplateRef` (another resource)? And if a second customer's session edits the live template, does the first customer's summary change? *(edge case)*
   Answer: A resource template renders against one variable, `state`, the resource's own state matching its `stateSchema`. It has no `input`, no `ctx`, no session state and no other resources, and it makes no model call. A missing state field throws on read, so use `default` (facts 38, 39, 40). `contentTemplate`, passed as `{ path, importerUrl: import.meta.url }`, renders a file that is app code. Only developers edit it, and one declaration is shared by every session (facts 42, four-questions block). `contentTemplateRef: "<resource name>"` makes another resource's content the template. That template is re-read on every `readContent()`, so a `writeContent()` on the template resource changes the next read. The template resource sets `writable: true`, and block code can write it. A client can write it only if the resource declares `client` access (facts 46, 47, four-questions block). The template resource lives in its declared scope. If that scope is `session`, each session has its own copy, so the second customer's edit does not touch the first customer's summary. This follows from the scope definitions and was not run across two sessions. A resource takes only one content source: `content`, `contentFile`, `contentTemplate` and `contentTemplateRef` are exclusive, and `defineResource` throws at build time otherwise (fact 45). `readContentRaw()` returns the template source (fact 43).
