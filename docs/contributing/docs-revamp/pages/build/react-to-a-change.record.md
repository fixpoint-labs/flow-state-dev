## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. On the support desk, you want a message every time an agent pins a note on a ticket. The notes live in the ticketNotes collection, and addNote creates them with create(key, { author }). What do you declare, and where, so that a block runs when pinned turns true?
   Answer: Put a reactTo field on the ticketNotes collection definition (defineResourceCollection takes reactTo, and so does defineResource). Bind stateUpdated to the block as { block, when }, with when: (change) => change.state?.pinned === true && change.prevState?.pinned !== true. The block gets a ResourceChange carrying state (after the write) and prevState (before it), and it can call ctx.emit.message. If when returns false, the run is skipped. A collection takes four kinds: created, stateUpdated, deleted and contentUpdated. (Fact sheet sections 1, 2 and 11: rc:58-74, rd:240, res:333, col:231.)
2. An agent edits a note's text with writeContent. Does your stateUpdated binding on ticketNotes run? And if you also want a summary of the new text, how does the block get the body?
   Answer: No. State and content are separate axes. writeContent fires only contentUpdated, and patchState fires only stateUpdated. To react to either one, bind the block to both kinds. A contentUpdated reaction receives only { key, ref, kind }, never the body. The block reads the body with readContent(), which returns the new text because the write is stored before the reaction runs. Writing the summary back with patchState does not fire the content reaction again, because patchState fires stateUpdated. That is the pattern that avoids a loop. (Sections 1, 2 and 7: rd:205-210, rc:76-89, rr:1360-1365, it751:315-380.)
3. When addNote calls create or patchState on a note, does addNote wait for the reaction to finish? And how do you make it not wait while the summary is written?
   Answer: By default it waits. The reaction is awaited inside the mutating call, so create, patchState and writeContent return only after the reaction finishes, and its run time is added to the writer's call. The write, its reaction and everything the reaction emits belong to one turn, in order. There is no flag to change this. To not wait, make the reactive block a sequencer that ends in .sideChain(block). The writer's call returns at once, and the request still finishes only after the side-chained work is done. (Section 4: cec:2907-2911, rd:1-12, rc:130-136, blk:458, sequencer.ts:1005-1010.)
4. Your blocking reaction on ticketNotes throws while addNote is saving a new note. Is the note lost, and what happens to the turn? Would it be different if the reaction were side-chained? *(edge case)*
   Answer: The note is not lost. The write is stored before the reaction runs, and a throw does not undo it. The writer's call rejects with the reaction's own error. If addNote does not catch it, the turn fails with that error. If addNote catches it, the turn completes and the note is still there (getOptional finds it). A side-chained reaction that throws fails neither the write nor the turn, and the writer never hears about it. So a reaction that must succeed for the write to be correct should block, and a side effect such as a summary, an index or a notification should side-chain. (Sections 0.1, 4 and 5: rd:302-305, rdt:299-318, it751:142-193.)
5. A teammate changes the ticketNotes state schema (for example, adds a field) but leaves the reaction's inputSchema built with resourceChangeSchema from the old schema. Notes still save, yet the pin message stops appearing. What happened, and where would you see it? *(edge case)*
   Answer: The payload is checked against the block's inputSchema before the block runs. A mismatch skips the block and emits an error item with the code reactive_input_invalid in the turn's stream. The write is unaffected and the turn does not fail. The usual cause is a resourceChangeSchema built from a different state schema than the resource's. Rebuild it from the collection's current state schema. (Section 6: rd:261-280, rdt:362-391.)
6. Two things puzzle you. First, a supervisor pins a note from the browser and no reaction runs. Second, an agent calls patchState({ pinned: true }) on a note that is already pinned and nothing happens. Then you add a reaction that patches the note it is bound to, and it keeps re-running. Explain all three. *(edge case)*
   Answer: A change made from the browser goes through the write flow. That flow writes straight to the store and runs no reactTo binding. Only a write made by a block in a turn starts a reaction. A write whose result equals the stored value is a no-op, and a no-op starts nothing. A reaction that writes the same kind it reacts to must stop on a condition, such as a when gate that compares the state, or it loops. The engine stops cascades at depth 8 or at 1000 dispatches per turn. It then skips the block and emits an error item with the code reactive_cascade_exceeded, and the turn still completes. Also, the reaction block should not declare ticketNotes in its own resources. It reads the collection through ctx.resources, which the flow installs. Declaring it would create a definition cycle with the collection's reactTo. (Sections 1, 3, 7 and 8: dwf:19-27, rr:866-868, rdt:471-509, rd:43-45, rd:244-259, ks:49-64.)
