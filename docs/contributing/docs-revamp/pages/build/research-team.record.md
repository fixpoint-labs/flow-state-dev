## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your board has three analyst tasks (acme, globex, initech) and a compare task assigned to the writer. When the writer block runs, how does it get the three analysts' findings, and could it ever run with only two of them?
   Answer: The board hands them over. The writer declares taskWorkerInputSchema as its input and reads input.deps, an object keyed by dependency task id (acme, globex, initech), each value being that analyst's recorded output ({ findings }), which is just what the analyst block returned (facts 16, 18). input.deps is filled when the task is claimed, and a task is claimed only when every id in its deps is completed, so the writer never sees a partial set (facts 17, 24). The wait comes from deps, not from a claim order (fact 1).
2. You run the four-task board with fsdev run and get a clean result. What runs at the same time, what does the final board report say, and where in the output is the brief?
   Answer: The three research tasks run together (the drain runs up to four ready tasks at once by default), and compare is claimed only after all three complete (fact 24). The final task-board-meta item reports terminationReason "all-completed" with counts.completed equal to counts.total, 4 of 4 (facts 37, 38). The brief is flow_complete.output, but only because the flow adds a read step after board.drain that gets the compare task with getTask and returns its output. board.drain's own output is the worker loops' results, not the writer's brief (facts 2, 31).
3. You swap the hard-coded list of competitors for a planner generator that decides the list per request. What changes in the flow, and what stays the same?
   Answer: Only where the tasks come from. The board drops initialTasks (it defaults to []). The flow becomes .step(planCompetitors).tap(fileTasks).step(board.drain).step(readBrief): a filing handler with uses: [board.capability] calls ctx.cap.research.createTasks with one analyst task per competitor (goal `Research ${name}`) plus compare, whose deps name those analyst ids in the same batch. The drain picks them up on its first pass (facts 41-47, 49). The board, the workers, the deps rule and the failure behaviour are unchanged. The number of analyst tasks follows the planner's output (fact 47).
4. The initech analyst throws (say, a search tool times out). What happens to each of the four tasks and to the request, and what does the user get? *(edge case)*
   Answer: initech's task ends errored with the thrown message and attempts: 1. It is not retried, because maxAttempts is unset (facts 51, 54). acme and globex still complete (fact 55). compare is cancelled and never runs: label skipped, error "dep <initech's id> failed", causedBy naming initech (facts 52, 53). With the default onError "skip" the request does not fail (fact 56). The final task-board-meta item reports terminationReason "blocked-by-failures" with counts completed 2, errored 1, cancelled 1 (fact 57). The read step returns compare's status "cancelled" and no output, so the user gets no comparison. The flow, not the board, decides what to tell them, such as the cause and which analysts did finish (fact 57).
5. Inside the flow, after board.drain, you want to branch on whether the comparison was written. What do you read, and why not the stop reason? *(edge case)*
   Answer: Read the writer task's status through the board capability (getTask("compare")): "completed" with an output, or "cancelled" with error and causedBy (facts 31, 32, 58). The stop reason (terminationReason) is on the task-board-meta stream item, which is for a client or for jq on the NDJSON. It is not returned to the flow, because the drain's output is the worker loops' results (facts 2, 58, 59). The other stop reasons are listed on reference/task-board (fact 60).
6. Two users send research requests at the same moment with different competitor lists, and later you rerun the same request. Do their boards share tasks, does a rerun find the earlier tasks, and what limits how many competitors a planner can file? *(edge case)*
   Answer: No sharing and nothing kept. The board's list lives on the request (the default storage), one list per collection id per request, so each request gets its own tasks and the list ends with the request. A later run starts empty, on a memory or a persistent store alike (facts 35, 63, the stored-parts table). Within one request, task ids must be unique: a batch that repeats an id is refused whole and nothing is filed (fact 42). A planner that names too many competitors hits the board's creation cap: the filing throws and files nothing. The exact numbers are on reference/task-board (fact 48).
