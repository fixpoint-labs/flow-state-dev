## Step 1: get the flow

6. **`runAction` takes a flow instance, the value `defineFlow(...)` returns when called, not the definition.** `defineFlow({...})` returns a factory; calling it makes the instance. `fa` facts line 27 (`core/flow/defineFlow.ts:1623-1712`). The option is typed `flow: TFlow extends FlowInstance` (`eng/execution/types.ts:71-75`). Every runAction test builds `defineFlow({...})()` (`et/run-action-manual.test.ts:20-33`; `et/run-action-edge.test.ts:12-22`). **[run]** passing the un-called definition (cast to `any`) also ran at runtime. **[verify: off the page. The type says an instance; the page shows an instance and does not say what happens otherwise.]**
7. **The app's own flow file already default-exports the instance.** In the C-05 example, `src/flows/support/flow.ts` has `export const supportFlow = defineFlow({ kind: "support", actions: { reply } });` and `export default supportFlow();` (`fa` page, "A flow with one action"). A script imports that default. **[page]** `import support from "../flows/support/flow";`. The page must say what `support` is in a clause: the flow the server registers. Source is a drafted page; the layout is `docs/contributing/user-docs.md:290-300`.
8. **A flow instance has an id, and for a singleton the id is its `kind`.** `FlowInstance` carries `id`: "for a singleton this equals `kind`; for a collection member it is the explicit id the factory was called with" (`core/types/flow.ts:781-784`). A registry indexes each registered instance by that id and `get(address)` returns the instance or `undefined` (`eng/registry/flow-registry.ts:131`, `:308`). **[page: one clause, only if the page fetches a flow from a registry; see fact 9. Several copies of one flow is [ref] `reference/flows`.]**
9. **An app that already calls `createFlowState` can read its stores and runtime config instead of building them.** `FlowState.getRuntime()` resolves `{ registry, stores, runtimeConfig }`: "the same ... instances the router uses", memoized, and it opens the stores on first call (`eng/flowstate/types.ts:454-461`; `FlowStateRuntime` at `:427-433`). The registry holds the registered instances, `registry.get("support")` (`eng/registry/flow-registry.ts:131`). **[run, in tests]** `et/wait-sweeper-fact.test.ts:25-46` runs `runAction({ ..., stores: runtime.stores, runtimeConfig: runtime.runtimeConfig })`, and `et/resource-find-by.test.ts:74-84`. `fsdev.config.ts` default-exports `createFlowState({ flows: [support] })` in the C-05 example (`fa` page). **[page]** this is the answer to "What do you still have to supply?": the stores and the runtime config are the app's, so a script that imports the app's `fsdev.config.ts` takes them from `getRuntime()`, and one that stands alone builds its own. Never call `getRuntime()` in a request handler for every request; it is memoized, so it is cheap, but the page does not need to say so.
10. **The stores a run writes to must be the stores everything else reads.** A run writes a session, a request record and its items into `stores` (see the four questions below). A script that builds a second in-memory registry writes to a registry nobody else sees. **[page: one sentence.]** `mfe:82-83` says "they are the same registry you built to construct your server". **[run]** with `createInMemoryStores()` the request record is readable from the same registry after the run.
11. **Building stores by hand, for a script that is the whole app.** `createInMemoryStores()` (tests and one-shot scripts; nothing outlives the process) and `createFilesystemStores({ rootDir, developmentOnly: true })` (writes under `rootDir`; `developmentOnly: true` silences a console warning that the filesystem store is unsuitable for production load) are the two registry factories (`eng/stores/index.ts:187`, `:213-229`, option at `:161`). **[page: the in-memory one, one line, so the finished code runs as written. The filesystem one and the SQLite and Postgres stores are [ref] `reference/stores`; a link only.]**

## Step 2: call an action without HTTP

12. **The call.** `runAction(options)` resolves with an `ExecutionResult` when the action reaches a terminal state (`eng/execution/runAction.ts:1026-1036`). The options a caller must pass are `flow`, `actionName`, `input`, `userId`, `orgId`, `stores`, `runtimeConfig` (`eng/execution/types.ts:75-78`, `:94`, `:139`, `:230`; the rest are `?`). **[run]** with exactly those seven, `runAction` ran `reply` and returned `{ echoed: "hi", count: 1 }`. **[page]** the finished code passes the seven plus `sessionId`.
13. **`runtimeConfig` is required, and `{}` is enough when no block calls a model.** `runtimeConfig: RuntimeConfig` is not optional (`eng/execution/types.ts:230`). `RuntimeConfig.modelResolver` is optional (`eng/runtime-config.ts:29-30`). A test passes `runtimeConfig: {}` for a handler flow (`et/run-action-manual.test.ts:45`). A flow with a generator block needs a `modelResolver` in it, or the generator fails at run time as it would over HTTP (`mfe:84-87`). **[page: "a flow that calls a model needs the app's model resolver, so pass `runtime.runtimeConfig`"; the options of `RuntimeConfig` are [ref].]** I did not run a generator block with no resolver; the claim is from `mfe:84-87` and `RuntimeConfig` being optional on every field. **[verify: keep the page's wording to "needs one", no error text.]**
14. **`userId` is the caller's to supply and `runAction` does not check it.** The type is `userId: string` (`eng/execution/types.ts:78`). A blank `userId` throws `Flow "<kind>" requires a userId` (`eng/context/createExecutionContext.ts:755-757`). `mfe:42-45` and `auth:92-100`: "Calling the runtime directly, below any transport, means there is no resolver to supply an identity, so you pass one." Authentication is the caller's job. **[page]** "A run is attributed to the `userId` and `orgId` you pass. Nothing checks them. Pass the ones your own code has verified."
15. **`sessionId` is optional; leave it out and the run gets a new session of its own.** When `sessionId` is absent the runtime makes an ephemeral one, `ephemeral_<time>_<random>` (`eng/context/createExecutionContext.ts:760`; persisted, comment at `:1199-1201`). `et/context.test.ts:102-115` pins "creates an ephemeral session when no sessionId is provided". **[run]** two runs with no `sessionId` each started a fresh session: the second `reply` returned `count: 1`.
16. **A `sessionId` you pass is reused on the next call.** **[run]** two runs with `sessionId: "s1"` shared session state: the first `reply` returned `count: 1`, the second `count: 2`. So a job that runs the same flow on a timer picks a `sessionId` on purpose: a fixed one for one running record, a new one per run for separate records. **[page]** This is the one decision in the call. **[answers "What do you still have to supply?"]**
17. **A session belongs to the user who made it.** **[run]** a second `runAction` with `userId: "u2"` on session `s1` (made by `u1`) rejects with `UserBindingMismatchError: Session s1 belongs to another user and cannot be used by this caller.` (`eng/context/binding-errors.ts:19-44`; admission at `eng/execution/runAction.ts:1291-1296`). The session's organization is likewise fixed when it is made (`OrgBindingMismatchError`, `eng/context/binding-errors.ts:46-65`; `auth:108-109`). The session's flow instance is fixed too: a `sessionId` that belongs to another instance is refused before the action starts with nothing written (`et/flow-instance-ownership.test.ts:194-218`). **[page: one sentence, "a session id names one user, one organization and one flow"; the three error classes are [ref] `reference/errors`.]**
18. **What rejects and what returns.** **[run]** each of these on the in-memory stores:
    - An action name the flow does not define **rejects**: `ValidationError: Flow "support" does not define action "nope"` (`eng/execution/runAction.ts:401-403`; `et/run-action-edge.test.ts:11-36`).
    - A missing `orgId` **rejects** with `OrgRequiredError` (fact 1).
    - Another user's session **rejects** with `UserBindingMismatchError` (fact 17).
    - Input the action's schema refuses **returns** a result: `result.error.code === "validation_error"`, message `Action input validation failed at "message": Expected string, received number`, `result.output` is `undefined`, and the request record is `failed` (`eng/execution/runAction.ts:424`; `et/run-action-edge.test.ts:38-66`).
    - A block that throws returns `result.error` as well (`et/run-action-edge.test.ts:105-140`: a failing `onErrored`/`onFinished` observer still returns the failed result; a throw in the request-level `onStarted` hook **rejects**, `:68-103`; a block that throws in its own body was not run here, **[verify]**). **[page: "A run that fails comes back with `result.error`. A call that is wrong before the run starts, an unknown action, no organization, someone else's session, rejects." Two failure shapes, one sentence each.]** Which request-level hooks reject is [ref] `reference/flows` (lifecycle hooks).
19. **`result.error` is a `FlowError`; its `code` is a string.** `ExecutionResult.error?: FlowError` (`eng/execution/types.ts:48`). The page needs only `code` and `message`: `validation_error` is the one **[run]**. The full code list is [ref] `reference/errors`. **[page: `if (result.error) throw result.error;`, as `mfe:73` and `inv:90-95` do.]**
20. **`input` is checked against the action's `inputSchema`, so pass the shape a client would send.** `input: unknown` (`eng/execution/types.ts:77`). **[run]** `{ message: 5 }` for a `z.string()` field returned `validation_error`; `{ message: "hi" }` ran. **[page]**
21. **Ask for the request id before the run ends.** Pass your own `requestId`; it is echoed on the result (`et/run-action-manual.test.ts:53-66`, "echoes a caller-supplied requestId"). Without one, the result carries a generated `req_<time>_<random>` (`et/run-action-manual.test.ts:37-51`; **[run]** `req_1794753677428_9ee890c4bf9e`). **[page: one clause. It is how a script that does not await the run still knows which request to look up.]**
22. **Not awaiting the run.** `runAction` returns a promise, and nothing in it is detached: drop the `await` and the run goes on, items and events persist to `stores` (`mfe:110-115`). An un-awaited rejection is an unhandled promise rejection in the host process, so a `.catch` is the caller's (`mfe:112-115`; standard promise behaviour). **[page: one sentence, if the page shows a queue consumer. It is a JavaScript fact, not a framework fact; keep it to "attach `.catch`".]** The old page's claim that "a separate HTTP server over the same `stores` can stream this run by opening its GET-stream route for `requestId`" (`mfe:117-130`) is **[verify]**: no test I found runs `runAction` in one registry and streams it from a router over the same stores. **[keep off the page; or say only "the run is recorded in `stores`, so anything that reads those stores sees it".]**
23. **The caller does not wait for a person.** A run that suspends on a human gate (`ctx.suspend`) comes back with a result before the person answers; resuming it is a different call. That is C-17 / Pausing and resuming. **[ref]** link only; one clause at most. I did not run a suspension here.

## Step 3: read the items

24. **`result.items` is the run's items, in order.** `ExecutionResult.items: RuntimeItem[]` (`eng/execution/types.ts:46`). **[run]** the `reply` action (a handler that writes session state and calls `ctx.emit.message("Echo hi")`) returned `["block_trace", "state_change", "message"]`. Note `block_trace` is in it: the items the run produced include the trace items. A script that wants what a user would see filters to the types it wants (`item.type === "message"`). **[page]** show the filter. **[contradiction with the old page: `mfe:91-94` says "the `items` it produced" and says nothing of trace items; the page names `block_trace` as one of the types so the reader is not surprised.]**
25. **A message item's text is in `content`.** `MessageItem` has `type: "message"`, `role`, and `content: Content[]` (`packages/contracts/src/items/types.ts:449-469`). **[run]** the message item was `{"type":"message","role":"assistant","status":"completed","content":[{"type":"output_text","text":"Echo hi"}], ...}`. To read the text, join the `output_text` parts' `text`. **[page]** the finished code reads the assistant text this way, narrowing on `item.type === "message"` and `part.type === "output_text"`. **[verify: type-check the narrowing at pass 4; `RuntimeItem` is from `@flow-state-dev/core/internal`, `eng/execution/internal/response.ts:4-6`. If the narrowing does not type against `RuntimeItem`, import `OutputItem` from `@flow-state-dev/core/items` (the type `onItem` is declared with, `eng/execution/types.ts:173`).]** The full item list and each item's fields are [ref] `reference/items`.
26. **Items as they happen: `onItem`.** `onItem?: (item: OutputItem, kind: "added" | "updated" | "done") => void` is called for every item as it is added, updated and done, the same live fan-out SSE clients get, transient items included (`eng/execution/types.ts:162-173`; `et/run-action-manual.test.ts:68-130`). **[run]** for `reply` it fired `block_trace:added, state_change:added, state_change:done, message:added, message:done, block_trace:updated, block_trace:done`. A listener that throws never breaks the run (doc comment, `eng/execution/types.ts:169-172`). **[page]** one short example that logs messages as they finish, and one sentence that `onItem` sees transient items, which `result.items` and the stored record leave out (fact 27).
27. **`onItem` sees more than `result.items`.** **[test]** a transient message is delivered to `onItem` and is absent from the persisted record's items (`et/run-action-manual.test.ts:89-130`). I did not run a comparison of `result.items` against `onItem` for a transient item; whether `result.items` includes transient items is **[verify]**. The old page says "transient ones will be present in the former [onItem] and absent from the latter [the persisted item log]" (`mfe:130-140`), which is what the test pins; it says nothing of `result.items`. **[page: compare `onItem` with "the stored record", never with `result.items`.]**
28. **Reading a finished run later, from the stores.** `stores.request.get(requestId)` returns the request record: `status`, `source`, `items` (the persisted log), and `result` (`et/run-action-manual.test.ts:125-128`; `RequestRecord.result`, `eng/stores/types.ts:262-277`). **[run]** after the reply run: `status: "completed"`, `source: "http"`, `items: ["block_trace","state_change","message"]`, `result: { output: { echoed: "hi", count: 1 } }`. **[page: one example or sentence, for a script that kept only the `requestId`.]**
29. **A client can read the same record without a stream.** `fsd.sessions.requests` with `includeResultOutput: true` returns the stored `output` (`mfe:100-102`; `packages/client/src/types/index.ts:279-283`, `packages/client/src/client.ts:126`). The page links; it does not state the JSON rule.
30. **`output` and `error` can both be set.** When the action returns and a completion hook (`onCompleted`) then throws, the run fails with the hook's error and `output` still holds what the action returned (`mfe:96-98`). **[ref]** an edge case; lifecycle hooks are on `reference/flows`. ## What a run stores (the four questions)

A recipe stores no data itself, but each call writes records into `stores`, and a script author asks where they went. The page answers these in a short table or a sentence, not a section.

| Part | Who owns it | Who can see it | Where it is stored | How many |
| --- | --- | --- | --- | --- |
| The request record (`status`, `source`, `items`, `result`) | The flow instance that ran it (`flowId`) and the `userId` and `orgId` you passed (`eng/stores/types.ts:138-146`; `et/flow-instance-ownership.test.ts:216-230`, record kept on the owning instance) | The same user, through a client call or the DevTool; a different user is refused as an unknown session over HTTP (`eng/context/binding-errors.ts:19-31`) | In the `stores` you passed: `stores.request` (`et/run-action-manual.test.ts:125`) | One per call. A `requestId` you reuse addresses the same record, which is how a queue retry re-runs one request (`eng/execution/types.ts:141-150`) |
| The session (state, history) | The `userId`, `orgId` and flow instance that made it; fixed for the session's life (fact 17) | The same user; no other user | `stores.session`, or the user's own scope for user-level state | One per `sessionId` you pass and reuse. With no `sessionId`, a new `ephemeral_...` session per call (fact 15) |
| The items (messages, state changes, trace items) | The request that emitted them | Whoever can read that request | On the request record (persisted ones only; transient items are live-only, fact 27) | As many as the run emitted; **[run]** three for the example |

- **Who owns it** is answered by the records: `flowId` (the instance), `userId`, `orgId` (`eng/stores/types.ts:138-146`; `SessionRecord` fixes the same three). **[page]**
- **Who can see it** over HTTP is a different question from who can see it in your process. `runAction` runs below principal resolution, so code that holds the `stores` can read everything in them. Anything a user reads goes through the HTTP layer, which checks the principal (`auth:92-100`). **[page: one sentence.]**
- **Where it is stored** is the `stores` you passed. An in-memory registry holds it until the process ends; the filesystem, SQLite and Postgres stores keep it (`eng/stores/index.ts:187-229`; the SQLite and Postgres packages are in the repo's package list). **[page: names in-memory and "a store that persists", links `reference/stores`.]**
- **How many**: one request record per call, one session per `sessionId` (fact 15 and 16). **[page]**
