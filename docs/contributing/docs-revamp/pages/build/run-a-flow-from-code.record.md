## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk app serves the `support` flow over HTTP. You now want a nightly job, with no request behind it, to run the `reply` action. Should the job go through HTTP or call the flow directly, and when would you still send the work through HTTP instead?
   Answer: Call it directly with `runAction` from `@flow-state-dev/engine`. This is for code that is not a request: a nightly digest, a worker that runs one flow per queued message, a script reacting to a webhook your own code already received (fact 31). Anything a user triggers should go through HTTP, because `runAction` does no authentication and builds no HTTP response (fact 33). If you only want the work on a timer or a queue, the scheduled and BullMQ packages already call `runAction` for you (fact 32).
2. Your script imports the app's flow file and the app's `fsdev.config.ts`. What does it pass to `runAction` to run `reply` with the message "hi", and where do the stores and runtime config come from?
   Answer: Seven options are required: `flow` (the `support` instance, the flow file's default export, which is what `defineFlow({...})()` returns, not the definition), `actionName: "reply"`, `input: { message: "hi" }` (the shape the action's input schema expects, as a client would send it), `userId`, `orgId`, `stores` and `runtimeConfig` (facts 6, 7, 12, 20). Take `stores` and `runtimeConfig` from the app's `createFlowState(...).getRuntime()`, which resolves the same registry, stores and runtime config the server uses (fact 9). The run must write to the stores everything else reads (fact 10). A script that is the whole app can build its own with `createInMemoryStores()` from `@flow-state-dev/engine/host`, where nothing outlives the process, and pass `runtimeConfig: {}` if no block calls a model. A flow that calls a model needs the app's model resolver, so pass `runtime.runtimeConfig` (facts 11, 13).
3. You copy an older example that passes `userId` but no `orgId` to the `reply` call. What happens, and what should the script pass for a single-organization app? Does `runAction` check that the `userId` is real? *(edge case)*
   Answer: The call rejects with `OrgRequiredError` before anything is written; `orgId` is required (fact 1). Pass the verified organization for an authenticated caller, or `DEFAULT_ORG_ID` from `@flow-state-dev/core` for single-organization development (a development identity, not a security boundary). `runAction` does not check either id: the run is attributed to the `userId` and `orgId` you pass, so pass ones your own code has verified (facts 1, 14). Only a blank `userId` throws (fact 14).
4. The nightly job runs `reply` every night and should keep adding to one running record. It runs fine the first night, but the next night the reply's count is back at 1. Why, and what decides whether runs share state? *(edge case)*
   Answer: Without a `sessionId`, each call gets a new ephemeral session of its own, so the second run starts fresh (count 1 again) (fact 15). Pass the same `sessionId` on every call and the runs share session state (first count 1, then count 2). Pick it on purpose: a fixed one for one running record, a new one per run for separate records (fact 16). Each call also makes one request record (four-questions table).
5. A second user's job reuses session `s1`, which the first user's job made, to run `reply` under its own `userId`. What happens? *(edge case)*
   Answer: The call rejects before the run starts: a session belongs to the user, organization and flow that made it, so another user's `userId` on `s1` gets `UserBindingMismatchError` (fact 17). That user needs a session of their own. Over HTTP, another user can't see the first user's records either (four-questions table).
6. Someone edits the job so it sends `{ message: 5 }` (a number) to `reply`, and another typo gives the action name as `"nope"`. Which call rejects and which returns? After a good run, how does the script read the assistant's reply, and how does it look the run up later if it kept only the request id? *(edge case)*
   Answer: Two failure shapes. A call that is wrong before the run starts rejects: an unknown action (`"nope"`), no organization, someone else's session (fact 18). Input the schema refuses returns a result with `result.error` set (code `validation_error`, `output` undefined, request record `failed`). So check `if (result.error) throw result.error;` (facts 18, 19, 20). On success, `result.items` holds the run's items in order, including trace items (`block_trace`, `state_change`, `message`). Filter to `item.type === "message"` and join the `text` of its `output_text` content parts ("Echo hi") (facts 24, 25). `onItem` sees items as they happen, transient ones included, which the stored record leaves out (facts 26, 27). Pass your own `requestId` (or read the generated one from the result), then call `stores.request.get(requestId)` for the record's `status`, `items` and `result` (facts 21, 28).

For fire-and-forget, observe a run failure through the request record or `onItem`, not through `.catch`. Use `.catch` only for admission or setup failures. A session owned by another user is refused with `UserBindingMismatchError`, and the refusal names neither the owner nor the flow. A session in a different tenant is skipped at this check. `FlowInstanceBindingMismatchError` is raised only for a same-user, same-tenant session owned by another flow instance. It is also raised when a supplied `requestId` addresses another instance's request record. (packages/engine/src/context/binding-errors.ts:154-183 (`assertSessionAdmitted`); packages/engine/src/execution/runAction.ts:1295-1330) The row is recorded corrected.
