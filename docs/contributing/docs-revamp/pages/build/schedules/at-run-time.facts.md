## Step 1: store a schedule as data

11. **A user-made schedule is a resource in a user-scoped resource collection, made with `defineScheduleCollection({ pattern, index })`** from `@flow-state-dev/scheduled`. `dsc:116-135`; `goal` `app.mts:120`. `pattern` is typically `"schedules/*"` (`dsc:88-90`). The collection is always `scope: "user"` (`dsc:121`). **[page]**
12. **`index` is optional on the collection.** Omitted, it is a plain resource collection with the schedule schema and no hooks (`dsc:134`; `dsct:66-74`, "installs hooks" vs "no hooks"). A collection with no index is stored and resolved but never ticked. **[page: say the index is what lets the tick find it.]**
13. **The row's fields** (`dsc:40-69`, the zod schema): `cron` (string, required), `kind` (string, required), `input` (any, optional), `timezone` (string, optional), `onOverlap` (`"skip" | "allow"`, optional), `description` (string, optional), `enabled` (boolean, default `true`), `orgId` (string, optional, set by the framework), `metadata` (record, optional, "the writer's own fields, kept with the schedule and never read here", `dsc:61-68`). **[page: `cron`, `kind`, `input`, `enabled`; the rest [ref]]**
14. **`kind` names a block, and the block map lives in code.** A block cannot be serialized into a row, so the row stores a string and `createResourceCollectionScheduleResolver({ collection, blocks })` maps it back (`rsr:55-64`). A row whose `kind` is not in `blocks` resolves to `null`, which the endpoint answers `404` (`rsr:148-149`; `rt:145-147`). `blocks` is a `Record<string, BlockDefinition>` (`rsr:64`). **[page]** The same `blocks` map is what the page declares once and uses in the resolver; the block files are one per file in the app layout.
15. **The flow wires three things, all on `schedules`:** `resolve` (the helper above), `index` (the same index object the collection mirrors into), and, on the flow's `resources`, the collection. `goal` `app.mts:144-157`:

## Step 2: one tick that runs what is due

30. **With no `scheduler` option, `createFlowState` runs a local cron that ticks once a minute.** `scheduler?: SchedulerAdapter | false`; "Omitted: the built-in local cron, which ticks each minute in a process that builds the router (`ready()`, `getRouter()`, a server) or starts a job queue's processing, when a registered flow declares static schedules or a schedule index." (`fst:421-428`; `fs:425-431`; `ls:3-5`, `SCHEDULE_TICK_INTERVAL_MS` = 60,000 at `tick:35`). `lst:80-89`. **[page]** **[answers Q2]**
31. **The app fires its own schedules, so no cron job, `setInterval` or external scheduler has to call anything.** `gd` and `sch` say the host does; they are stale (items 4, 7, 8). **[page]**
32. **One tick fires every schedule of every registered flow:** each static schedule whose latest scheduled time falls after the last tick and at or before now, and, for each flow's `schedules.index`, the entries `claimDue` returns, each for its latest due time from the cron and zone it carries (`tick:5-14`, `tick:98-133`). **[page: "one tick runs what is due: static and dynamic."]** The tick calls `claimDue(now, 100)` per index per tick (`tick:112`; `maxPerTick` default 100, `tick:75-76`). A claim past 100 stays due and is claimed next tick, since `claimDue` takes rows in `next_fire_at` order, limit applied (`sq:48-53`). **[ref]**
33. **A schedule fires into the organization that created it.** The row records the organization (item 21); the resolver builds the config's principal as `{ userId, orgId }` from the id and the row, refusing a row whose `orgId` is not the id's (`rsr:155-164`). **[page: the run's user is the schedule's owner and its organization is the one the row was created in; the page's handler logs `ctx.user`.]** **[answers Q1 in part]**
34. **After downtime a schedule fires once, late, for the latest time it missed.** Missed earlier times are dropped (`tick:15-17`; `it:100-128`, "after downtime fires a static and a dynamic schedule once each, for the latest time missed": down 09:00:30 to 09:23:10 on `*/5`, only 09:20 fires; `goal` signal c). **[page: one sentence; the page does not promise catch-up.]**
35. **Each fire is a request to the scheduled dispatch endpoint**, `POST <base>/api/flows/<kind>/schedules/<id>/dispatch`, body `{ nominalFireTime }` (`tick:160-185`). A dynamic schedule's id is `<orgId>/<userId>/<key>`, each part URL-encoded; `formatScheduleId(orgId, userId, key)` builds it and is exported from `@flow-state-dev/core` (`st:269-278`; `packages/core/src/index.ts:317`). **[ref: the page does not build ids. The tick does. One sentence says the id names org, user and key.]** Under the local cron the request goes through the app's own router, not the network (`fs:1363-1367`). **[ref]**
36. **A dispatch that fails is not retried.** A thrown dispatch is logged with the flow and schedule id (`tick:148-153`); a non-2xx answer is recorded in the tick's report and not retried (`tick:154`; `sidx:13-17`, "at-most-once"). The index has already advanced the row before the fire is sent (`sidx:14-17`; `sq:63-93`: `advanceStmt.run(next, ...)` inside the claim transaction). **[page: one sentence, "a fire that fails is dropped, not retried"; link `reference/schedules` for the contract.]**
37. **At most one process ticks across a deployment that shares a store.** A lease in `stores.leases` elects one; it is held for two intervals, renewed every half lease, and released on a clean stop (`ls:3-19`, `ls:56-58`; `lst:163-176`). 38. **A scheduled time fires at most once, however many ticks or processes reach it.** The dispatch endpoint claims each `(schedule, time)` with a compare-and-set record before the handler runs; a second claim answers `200 { status: "duplicate" }` (`stm:1-20`, `stm:178-190`; `rt:223-229`). ## Stored parts (the four questions)

Each answer is the code's, with the line that says it. "Who sees it" means which callers can read it. "How many" is how many exist.

53. **A schedule resource** (the resource instance under `schedules/<key>`). **[stored] [answers Q1]**
    - **Owner:** the user whose run created it, in the organization of that run. The row's `orgId` is stamped from the creating run (`dsc:127`, `dsc:44-55`), and the resolver returns it as the principal `{ userId, orgId }` (`rsr:161-165`). Never the framework's or the developer's.
    - **Who sees it:** the owner's runs, through `ctx.resources.schedules`. No client reads it by default: the collection's `client` option is "Omitted, no client reads the schedules" (`dsc:98-102`). A client can write one only if `runBy` names a flow (`dsc:103-108`). The scheduled endpoint's listing reports static schedules plus `dynamic: { provided: boolean }`, never dynamic rows (`rt:342-346`, `rt:398-403`; `sch` "No cross-tenant enumeration"). The resolver 404s an id naming another user or org (`rsr:116-123`, `rsr:159`).
    - **Where stored:** the app's resource state, in the user's cell. A schedule collection declares no `flowIsolation` unless asked, so it is the non-isolated cell shared across the user's flows (`rsr:127-134`; `dsc:88-96`; `dsc:121-128`). The resource-state store is whatever the app's stores are: memory, filesystem, SQLite, Postgres.
    - **How many:** one per `(cell, key)`; as many keys as the flow writes. No default cap is set by `defineScheduleCollection` (no `maxInstances` in `dsc`). **[verify: `maxInstances` is a general collection option (`resource-collection.ts:334-340` mentions it); `defineScheduleCollection` does not forward it. A page does not promise a cap.]**
54. **The index row** (`schedule_index`). **[stored] [answers Q1]**

    - **Who sees it:** the engine's tick, through `claimDue` (`tick:112`). Nothing user-facing reads it.
    - **Where stored:** a `schedule_index` table in the same SQLite or Postgres database as the stores (`si:150-157`; `sq:25`), with columns `cell, key, user_id, org_id, cron, timezone, next_fire_at` and primary key `(cell, key)` (`si` schema, `packages/store-sqlite/src/schema.ts`). **[verify: the table is in the same database file only because the page passes the same file; `createSQLiteScheduleIndex(db)` takes any better-sqlite3 handle, `sq:23-24`.]**
    - **How many:** one per enabled, parseable, org-consistent schedule (`dsc:142`, `dsc:154-177`, `dsc:270-273`); none for a disabled one.
55. **The last-tick record.** **[stored] [answers Q2]**
