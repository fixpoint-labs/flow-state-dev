## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A support agent calls the scheduleDigest action with { cron: "0 9 * * 1" }. Where is that schedule kept, and what does the app read to find it when it is due?
   Answer: It is a row (key "ticket-digest", with cron, kind "ticketDigest", enabled) in a user-scoped resource collection made with defineScheduleCollection({ pattern, index }), in that agent's own user cell. That row is the source of truth. Writing it also mirrors a row into the schedule index (a schedule_index table in SQLite or Postgres, e.g. createSQLiteScheduleIndex). The index is a read-model, and it is what the tick claims due entries from (facts 11, 20, 23, 53, 54).
2. Nothing in the deployment has a crontab, setInterval or external scheduler. What actually fires the Monday digest, and what if the app runs on three servers sharing one SQLite store?
   Answer: The app fires it itself. With no scheduler option, createFlowState runs a built-in local cron that ticks once a minute in any process that serves the app. One tick fires every due schedule of every registered flow, both static and dynamic (it claims due entries from each flow's schedules.index). Across servers sharing a store, a lease means only one process ticks, and each scheduled time fires at most once. It does not tick in fsdev run, so a schedule created in a one-off run fires only once a server is up (facts 30-32, 37-39).
3. A developer wires schedules: { resolve } on the support flow and writes a row with cron "every monday". The write returns normally, but the digest never fires. Name the two reasons it could stay silent, and what to do about each. *(edge case)*
   Answer: (1) The flow names no index. The tick fires only an index the flow lists under schedules.index, so a flow with resolve and no index is never ticked (and a collection with no index is never mirrored). Fix: add index to schedules, the same index object the collection mirrors into. (2) The cron does not parse. A bad cron saves without error but gets no index row (only a warning), so it never fires. Fix: validate the cron in the handler before writing it (facts 12, 15, 26).
4. The agent changes their digest to Fridays by calling scheduleDigest again, then later calls cancelDigest. What happens at each step, and can a digest still go out after the cancel? *(edge case)*
   Answer: Calling create again on the same key with { replace: true } replaces the row. That counts as an update, so the index row is re-upserted with the new cron (without replace, create throws because the key exists). cancelDigest deletes the row, which removes its index row in the same call, so the next tick does not claim it. A fire that a tick already claimed before the cancel still goes out. Setting enabled: false pauses it the same way without deleting the record (facts 21, 22, 24, 25, 46).
5. The only server is down from 09:00:30 to 09:23:10 while a dynamic schedule runs every five minutes. One digest dispatch also errors, and another server crashes mid-run. What fires, and what is retried? *(edge case)*
   Answer: When the server comes back, the schedule fires once, late, for the latest time it missed (09:20). The earlier missed times are dropped, with no catch-up. A fire that fails is dropped and never retried (the index has already advanced). A dynamic fire runs in the ticking process, so it does not survive a crash mid-run. If you need that, make it a static schedule, which recovers (facts 34, 36, 40, 58, 59).
6. Two support agents in the same organization each set their own ticket digest with the same key "ticket-digest". Do they collide, who does each fire run as, and can one agent see the other's schedule? *(edge case)*
   Answer: No collision. The collection is user-scoped, so each row sits in its own user's cell, addressed by (cell, key). Each fire runs as that schedule's owner: ctx.user in sendTicketDigest is the agent who created it, in the organization where it was created. Only the owner's runs read the row through ctx.resources.schedules. No client reads it by default, the endpoint never lists dynamic rows, and an id that names another user returns 404. Everyone-gets-a-digest means one schedule per user, since there is no fan-out (facts 33, 48, 53, 61).
