## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You want the `billing` flow's `monthly-invoices` schedule to run its `invoices` block at midnight UTC on the 1st of every month, triggered by Google Cloud Scheduler. What do you put on the flow, and what URL and HTTP method does the Cloud Scheduler job call?
   Answer: Declare a static schedule on the flow: `schedules: { static: { "monthly-invoices": { cron: "0 0 1 * *", block: invoices } } }` (the key quoted because of the hyphen; the handler goes in `block`, not an `action` field; no `flow.actions` entry is needed, though `defineFlow` still takes `actions: {}`). The framework does not run the schedule itself; the job POSTs `https://app.example.com/api/flows/billing/schedules/monthly-invoices/dispatch` (`POST {basePath}/:flowKind/schedules/:scheduleId/dispatch`, basePath defaulting to `/api/flows`), with the scheduled adapter mounted via `createScheduledTransportAdapter()` on `createFlowState`. Facts 1, 2, 4, 6, 10, C1, C2.
2. How does the dispatch endpoint know a call really came from your Cloud Scheduler job and not a stranger, and what does the job have to send for that to work?
   Answer: Give the flow `authentication: { resolvePrincipal: createBearerSecretPrincipalResolver({ secret, principal: { userId: "system", orgId: "org_sys" } }), requireUser: true }`, with the secret read from an environment variable such as `FSDEV_SCHEDULER_SECRET`. The job sends the same secret as `Authorization: Bearer <secret>`. The resolver compares it in constant time and returns the fixed principal; every dispatch passes through it before the schedule's record is read. The principal must include a real `orgId` (not the reserved default), or the call is refused with 401. Facts 11, 12, 13, 17, 19, C3.
3. Someone rotates `FSDEV_SCHEDULER_SECRET` on the app but forgets to update the Cloud Scheduler job, so the job keeps sending the old token. What does the endpoint answer, does the invoice run happen, and what does Cloud Scheduler do next? *(edge case)*
   Answer: A mismatched token throws `PrincipalResolutionError` and the endpoint answers `401 { error: "unauthorized", message: "Invalid scheduler secret." }`. Nothing runs. A non-2xx answer makes Cloud Scheduler retry per the job's retry flags [external], and the retries fail the same way until the job carries the new secret. (A missing header gets a 401 too, via `requireUser: true`.) Facts 14, 15, 31, 32.
4. Cloud Scheduler gets a timeout on the 1st-of-the-month call and retries it, but the first call had in fact reached the app and started the invoice run. Are invoices generated twice? And what if the 2xx came back but the invoice block then threw an error? *(edge case)*
   Answer: No double run: each scheduled time fires at most once however many times it is POSTed, so the retry answers `200 { status: "duplicate" }` and runs nothing (this holds across processes on SQLite or Postgres; on the memory or filesystem store only within one process). If the dispatch returned `202 { status: "accepted" }` and the block failed afterwards, the response is unchanged and Cloud Scheduler does not retry, because it saw 2xx [external]; the failure shows on the request's `RequestRecord` (status `errored`) and in DevTool, so alerting on it is up to you. Facts 27, 33, 36, 39, 40.
5. Why does the recommended job send no request body, and what goes wrong if you configure the job with a fixed JSON body containing `nominalFireTime`? *(edge case)*
   Answer: With no body, each fire counts against the latest scheduled time already due (or due within five seconds). Cloud Scheduler sends the same fixed body on every run [external], so a fixed `nominalFireTime` is accepted once, and once it is more than one period behind the latest due time it answers `200 { status: "duplicate", reason: "stale" }`, runs nothing, and logs a warning on the server. Sending no body is the fix. (A body with `idempotencyKey` is refused `400 idempotency_key_removed`.) The block's input comes from the schedule's `input` field, not the body. Facts 21, 22, 24, 25, 50.
6. Your finance team wants invoices at midnight New York time instead of UTC, so you change the Cloud Scheduler job to `--time-zone="America/New_York"`. Is that enough? What else has to change, and what happens to the run that already fired this month? *(edge case)*
   Answer: No. The endpoint evaluates the schedule's `cron` in the schedule's own `timezone` (default `"UTC"`) to decide which scheduled time a fire counts against, so set `timezone: "America/New_York"` on the schedule too and keep the same cron in both places; the code does not compare them, and a mismatch changes which time each fire is counted against. The zone must be IANA, or registration fails. Changing the cron or zone keeps the schedule's single fired record, so a time at or before the one already fired still answers `duplicate`: the month's run is not repeated. Facts 26, 45, 46, 47, 48, C4.

## Reference rows

- Dispatch with no `nominalFireTime`: the fire is attributed to the latest scheduled time already due. Fields: dispatch body, `nominalFireTime`, how a fire maps to a scheduled time. → R-33
- Dispatch responses and retries: a repeated dispatch for a time that already fired returns `200 { status: "duplicate" }` and the action runs once per scheduled time; a retry landing after the next scheduled time counts against that next time. Which responses count as failures. → R-33
- Action failure after a 202 dispatch: the error is recorded on the `RequestRecord` (status `errored`) and the flow's `onErrored` hook runs; the caller is not told and does not retry. → R-22
- Schedule field `timezone`: the IANA zone (default `UTC`) the framework evaluates the schedule's cron in when it works out which scheduled time a fire counts against. It must match the caller's cron zone, or a fire can be refused as `not_a_scheduled_time` or attributed to the wrong time. It surfaces as `metadata.schedule.timezone` on the request. → R-33 (corrected by pass 5)
- Per-fire input: `nominalFireTime` is available on the input function's context, along with `scheduleId`, `cron`, `principal`, `flowKind` and `origin`. A scheduled run's input otherwise comes only from the schedule's `input` (a static value or that function), or `{}` if none is set. The action can read user/org scope state itself. → R-33 (corrected by pass 5)
