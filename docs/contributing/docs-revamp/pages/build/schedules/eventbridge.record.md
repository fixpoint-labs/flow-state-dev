## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The `billing` flow's `monthly-invoices` schedule fires on the 1st of each month. When EventBridge POSTs the dispatch endpoint, which user does the run belong to, and what stops a stranger from POSTing the same URL to trigger invoices?
   Answer: The run belongs to the fixed principal the flow's bearer resolver returns: `createBearerSecretPrincipalResolver({ secret, principal: { userId: "system", orgId: "org_sys" } })`, with `requireUser: true` (facts 3, 19, 37). Every dispatch goes through the flow's `authentication.resolvePrincipal` first (fact 18). A caller must send `Authorization: Bearer <FSDEV_SCHEDULER_SECRET value>`, compared in constant time. A wrong token gets `401 unauthorized` ("Invalid scheduler secret."). A missing header or a non-Bearer scheme resolves to no user, and `requireUser: true` refuses it with 401 (facts 13, 19).
2. What exactly does the EventBridge schedule need to send for `monthly-invoices`: which URL, method, headers and body?
   Answer: `POST https://app.example.com/api/flows/billing/schedules/monthly-invoices/dispatch` (default basePath `/api/flows`; POST only), with headers `Authorization: Bearer <secret>` and `Content-Type: application/json`, and body `{"nominalFireTime":"<aws.scheduler.scheduled-time>"}`. EventBridge fills that in with the time the schedule was due. The endpoint reads only `nominalFireTime` from the body. It refuses `idempotencyKey` and ignores any other field (facts 13, 14). The AWS wrapper around this (target ARN, HttpParameters, the flag that carries the URL) can't be confirmed from the repo (fact 12).
3. A developer copies the EventBridge expression `cron(0 0 1 * ? *)` into the flow, or keeps a framework `cron` that names different times from the AWS one. What happens? *(edge case)*
   Answer: Each side has to be written in its own dialect, naming the same instants: `0 0 1 * *` on the flow and `cron(0 0 1 * ? *)` in AWS (facts 9, 10). The framework accepts exactly five fields. A six-field expression with `?` is refused at registration, so the app fails at boot (facts 4, 8, 11). If the two crons parse but disagree, the endpoint evaluates the flow's `cron` (in `schedule.timezone`). A `nominalFireTime` that isn't within five seconds of one of its scheduled times answers `400 not_a_scheduled_time`, on every fire (facts 5, 7). EventBridge retries non-2xx responses, so these 400s use up the retry budget and end in the dead-letter queue (fact 27).
4. The invoices run is slow and EventBridge times out and retries the same fire. Do customers get invoiced twice? And what if the action itself throws after the endpoint returned 202? *(edge case)*
   Answer: No double run. A retry of a scheduled time that already dispatched answers `200 { status: "duplicate" }` and runs nothing, for any number of POSTs of that time: retries, a second host, a restart (fact 28). On SQLite or Postgres this holds across processes. On the memory or filesystem store it holds only within one process (fact 34). A 202 means the action started, not that it finished (fact 23). If the action errors afterwards, the response doesn't change and the error is on that request's `RequestRecord`. EventBridge doesn't retry a 2xx, so a failed action is never redriven and never reaches the dead-letter queue (fact 31).
5. The team moves the schedule to 09:00 Europe/Berlin on the 1st. What has to change, and where? *(edge case)*
   Answer: Change both places, because the schedule is written twice and the endpoint reads only the flow's copy (facts 9, 46). In AWS, update the schedule expression and `--schedule-expression-timezone` to `Europe/Berlin`. On the flow, set `cron: "0 9 1 * *"` and `timezone: "Europe/Berlin"`, which must be an IANA zone or registration refuses it. The endpoint evaluates the cron in `schedule.timezone` (default UTC), and nothing compares the two ends (facts 40, 41). If they disagree, every fire is a 400 (fact 7). The fired record survives the change, so a time at or before the last one fired still answers `duplicate` (fact 39).
6. The scheduler secret leaked and has to be rotated. What does that involve, and can the app accept both the old and the new secret for a while? *(edge case)*
   Answer: On the app side the secret is an environment variable. In EventBridge it is templated into the schedule's header when the schedule is created, so rotating it means updating the schedule (or putting API Gateway in front and verifying there) (fact 20). The framework has no rotation of its own, and the bearer helper takes one `secret`. To accept two secrets during a rotation, the host writes `resolvePrincipal` by hand. If the flow already has a resolver for user traffic, branch on `ctx.source === "scheduled"` rather than replace it (facts 20, 21). Until the schedule is updated, the old token gets `401` (fact 19), and EventBridge retries the 401 and dead-letters it (fact 27).

- The `cron` field on ScheduleConfig is display-only metadata and does not drive evaluation; treat the AWS expression as the source of truth and the framework expression as documentation. Untrue: The framework evaluates `cron` (with `timezone`, default UTC) at dispatch to resolve which scheduled time a fire counts against. A carried `nominalFireTime` that is not a scheduled time of the cron (within 5s) is refused with 400 `not_a_scheduled_time`, and one not yet due gets 400 `not_yet_due`. With no body it counts against the latest scheduled time already due. The framework cron therefore has to match the EventBridge schedule. The AWS side still decides when the call is made. (packages/scheduled/src/scheduledTime.ts:86-121; packages/scheduled/src/routes.ts:206-210)
- As with Cloud Scheduler, the framework treats `schedule.timezone` as opaque metadata; set both to the same value for consistency. Untrue: `schedule.timezone` (default "UTC") is passed to cron-parser as `tz` to compute scheduled times and validate `nominalFireTime`. It is validated as a known IANA zone at registration. If it differs from `--schedule-expression-timezone`, the carried time will not match a scheduled time and dispatch returns 400 `not_a_scheduled_time`. The two must match, not just be consistent. (packages/scheduled/src/routes.ts:206-207; packages/scheduled/src/scheduledTime.ts:25-47,102-112; packages/core/src/types/schedules.ts:329-334)

(packages/scheduled/src/scheduledTime.ts:86-121; packages/scheduled/src/routes.ts:207-210; packages/core/src/types/schedules.ts:143) The row is recorded corrected.
