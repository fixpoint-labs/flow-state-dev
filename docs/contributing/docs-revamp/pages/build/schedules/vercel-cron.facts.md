## Declare the schedule

9. **A static schedule is a record on the flow's `schedules.static` map**, keyed by schedule id, with `cron` (POSIX five-field) and `block` (the handler). `st:140-150`; `sch` "Static schedules". Optional on each: `input`, `principal`, `timezone` (IANA, default `"UTC"`), `onOverlap` (`"skip"` default, `"allow"`), `description`, `enabled` (`rt:145`). `st:140-200`; `rt:206`, `rt:145`. **[page: `cron`, `block`, `description`; the rest [ref] `reference/schedules`]**
10. **`defineScheduleBinding({...})` is an identity helper that returns its argument typed as `ScheduleConfig`.** Exported from `@flow-state-dev/core` (`packages/core/src/index.ts:317`; `st:413`). A plain object literal works too (`sch` "Static schedules"; kitchen-sink `flow.ts:68-72` uses a plain literal). **[page: use the plain literal; no helper needed.]**
11. **Cron must be exactly five fields.** Six fields (seconds) are refused: `400 invalid_schedule` at dispatch, and an error at registration for a static one (`sch` "At most once per scheduled time", last two paragraphs; `rt:149-161`). A bad cron or input shape in a static entry fails at registration, not at dispatch (`sch` "Static schedules"). **[page: one sentence; ref for codes.]**
12. **The flow does not run the schedule.** The framework validates cron syntax; the host's scheduler decides when to fire (`sch` "Static schedules"; `st:140-150`). Vercel Cron is that scheduler here. **[page]**
13. **Time zone.** `timezone` defaults to `"UTC"` (`rt:206`; `rt:143`). Vercel Cron's own schedule runs in UTC (**[verify: not in repo; keep off the page]**). The cron expression in `vercel.json` and the one on the flow entry are two separate strings the author keeps equal; the framework does not compare them. **[source: nothing reads `vercel.json`.]** **[page: say the two must match, in one sentence.]** The dispatch counts the fire against the latest due time of the cron on the flow entry (`rt:205-207`), so a `vercel.json` cron that fires at times the flow's cron does not name answers `400 not_a_scheduled_time` only when a body time is carried (`sch` "At most once per scheduled time"); with no body (the shim), the latest due time of the flow's cron is claimed, so a mismatched pair does not 400 but fires the flow's cron times at Vercel's cadence, possibly never matching. **[verify: `once:160-170` pins no-body behaviour on a matching cron only. Keep the mismatch case to "keep the two the same".]**
14. **The dispatch URL is** `POST /api/flows/:flowKind/schedules/:scheduleId/dispatch` (`packages/scheduled/src/createScheduledTransportAdapter.ts:42`; `sch` "The dispatch endpoint"). ## The cron entry

16. **`vercel.json`** carries `crons: [{ path, schedule }]` (`vc:24-33`; kitchen-sink `vercel.json`: `{ "path": "/api/cron/static/monday-summary", "schedule": "0 9 * * 1" }`). `path` is a route in the Next.js app, not the dispatch URL. **[page]**
17. **Vercel Cron sends a GET; the dispatch endpoint takes POST only** (`vc:18-20`; `sch` response table, `405 Wrong method (only POST is supported)`). **[page]**
18. **`createGetToPostCronShim({ flowKind, scheduleId, baseUrl?, secret? })`** from `@flow-state-dev/vercel/schedules` returns `(req: Request) => Promise<Response>`, used as the route's `GET` export (`vs:22-62`; `vr:168-177`). **[page]**
19. **What it does, in order** (`vs:48-61`): (1) read the secret, `secret` option or `CRON_SECRET`, (`vs:143-145`); (2) require `Authorization: Bearer <secret>` on the inbound GET, else `401 Unauthorized` and no outbound call (`vs:50`, `vs:158-160`; `vt:39-49`); (3) read the base URL, `baseUrl` option or `NEXT_PUBLIC_BASE_URL`, else `500 "Server misconfigured: missing baseUrl"` (`vs:52-53`, `vs:148-152`); (4) POST to `<base>/api/flows/<flowKind>/schedules/<scheduleId>/dispatch`, both segments URI-encoded, a trailing slash on the base trimmed, with the same bearer and no body (`vs:55-59`; `vt:62-76`); (5) return the dispatch status with an empty body (`vs:60`; `vt:78-88`). **[page: the list in plain words; order of checks [ref]]**

The kept page builds it once at module level (`vc:41`). Either works; the page uses module level.
21. **`CRON_SECRET` is what Vercel sends.** Vercel Cron sends `Authorization: Bearer ${CRON_SECRET}` on each cron request when the project has an env var of that name (`vc:84-85`, `vc:66`). **[verify: Vercel behaviour, not in the repo; the kept page and the shim's doc comment (`vs:10-12`) both rely on it. The page states it as the premise with a link to Vercel's docs, or the writer adds nothing beyond the kept page's wording.]**
22. **`NEXT_PUBLIC_BASE_URL`** is the deployment's origin the shim POSTs to (`vs:28-32`). It is read at request time, not build time, by the shim (`vs:148-152`). An unset or empty value gives `500`. **[page: name the variable, say what it holds.]** **[verify: that the value should be the production URL and not a preview URL is advice, not a code fact; keep off.]**

## Protect the endpoint

24. **The dispatch endpoint authenticates every call before it reads anything.** Order inside `handleDispatch`: schedule-id pattern check, flow lookup, body parse, gateway auth through `host.resolvePrincipal`, then everything else (`rt:56-99`; header comment `rt:1-16`; comment `rt:71-72`: auth runs before the fire record is read "so an unauthenticated caller can't probe dispatch history"). The listing `GET .../schedules` goes through the same resolver (`rt:110-133`; "cron strings and descriptions are operationally sensitive"). **[answers Q2] [page: "every call to the dispatch endpoint is authenticated first, so a stranger learns nothing about whether a time has fired" in plain words; the listing too.]**
25. **Two checks, not one.** (a) The shim checks the inbound GET against `CRON_SECRET` (`vs:50`). (b) The dispatch endpoint checks the forwarded POST through the flow's `authentication.resolvePrincipal` (`rt:75-99`). A stranger calling the cron route directly gets `401` from (a) and no outbound call (`vt:39-49`). A stranger calling the dispatch URL directly needs the flow's resolver to reject them (fact 27). **[answers Q2]**
26. **The route is public to the internet.** Nothing in the repo restricts the cron route or the dispatch URL by network or IP; the only gate is the bearer secret (`vc:117`, "The shared secret is the only auth on this surface"). **[page: one flat sentence.]**
27. **`createBearerSecretPrincipalResolver({ secret, principal, headerName? })`**, from `@flow-state-dev/engine` (`bs:28-56`; `packages/engine/src/index.ts` re-exports it). It throws at construction when `secret` is not a non-empty string or `principal.userId` is not a non-empty string (`bs:57-69`). Reads `Authorization` (default, case-insensitive name; `headerName` overrides, `bs:72`, test `bst` "supports a custom header name"). Accepts a case-insensitive `Bearer` scheme (`bst` "accepts case-insensitive Bearer scheme"). Compares in constant time and rejects a different length (`bs:79-84`; `bst` "rejects mismatched-length tokens"). On a mismatch throws `PrincipalResolutionError("Invalid scheduler secret.", { status: 401 })` (`bs:81-83`; `bst` "throws PrincipalResolutionError(401)"). On a match returns the configured `principal` (`bs:86`). **[page: signature and the two outcomes.]**
28. **A missing or non-Bearer header does not throw; the resolver returns `null`** (`bs:76-77`; `bst` "returns null when the Authorization header is missing" and "... scheme is not Bearer"). The host then applies the flow's `authentication.defaultUserId` if one is set, else, with `requireUser` true (the default, `host:306`: `flow?.requireUser ?? true`), throws `PrincipalResolutionError("Action request requires non-empty userId", { status: 401 })` (`host:327-340`). Pinned: a POST with no Authorization header answers `401` on a flow with `requireUser: true` and no `defaultUserId` (`e2e:228-243`). **[answers Q2] [page: "no header, 401, as long as the flow keeps `requireUser` on and sets no `defaultUserId`." This is the trap: set `defaultUserId` on a flow with a bearer resolver and a request with no header runs as that user.]** **[verify: that case (`defaultUserId` set, no header, scheduled dispatch runs as the default user) is read from `host:327-329`, not run.]**
29. **When the flow serves other callers too, branch on `ctx.source`.** `resolvePrincipal` receives `ctx.source` of `"scheduled"` for dispatch (`vc:96-101`; `auth` line 150 lists `'http' | 'mcp' | 'webhook' | 'scheduled' | 'cli'`; kitchen-sink `flow.ts:121-131`; `e2e:70-83`). A scheduler-only resolver on a flow with HTTP actions breaks those routes (`sch` "Authenticating dispatch", last paragraph). **[page: only if the page's flow has an action for users; the support-desk flow does. Show the branch.]** The branch example in the kept page falls through to `verifyJwtFromHeader(ctx)`, which is not a framework export; the kitchen-sink one falls through to `defaultBodyUserIdPrincipalResolver` (`flow.ts:131`, exported from `@flow-state-dev/engine`). **[page: use a name the reader can import or declare, or say "your existing resolver" in prose.]** A resolver not branching returns `null` for `"scheduled"` requests lacking a header (see 28).
30. **Rotating the secret.** Change `CRON_SECRET` in Vercel's environment and redeploy; the shim and the resolver both read it from the environment (`vs:143-145`; `vc:117-119`). New requests with the old value get `401`. **[page: one sentence; the "in-flight dispatches finish" half is fact 7, cut.]** **[verify: Vercel env changes apply on the next deployment; not in repo. Say "set it in the project's environment variables" only.]**
31. **Related surface, link only.** `createScheduleTickHandler({ flowKind, index, baseUrl?, secret?, maxPerTick? (100), concurrency? (10), onDispatch? })` for dynamic schedules (`vs:64-136`); it authenticates the inbound call and forwards the bearer exactly as the shim does (`vs:108-109`, `vs:125`). **[ref/other page.]**

## Whose run it is (Q1)

32. **A scheduled run executes as a principal: a user id and an organization id.** The action runs as `schedule.principal` when the entry has one, else as the gateway principal, the one the flow's resolver returned for the dispatch call (`rt:181-203`; `sch` "Effective principal": "The runtime uses `schedule.principal ?? gatewayPrincipal`"). **[answers Q1] [page]**
33. **For a static schedule with no `principal`, the run is the resolver's principal**, e.g. `{ userId: "system" }` in `vc:98-101` and `bs:34-37` doc comment, or `{ userId: "system", orgId: "org_sys" }` in `e2e:51-54`. **[page: the support-desk example names the user (`"system"`) and org.]**
34. **A static entry may name a target user in `principal: { userId, orgId? }`**; if `orgId` is left out, the organization falls back to the gateway's (`rt:197-203`; `st` `principal` JSDoc; `sch` "The organization a schedule fires into"). **[page: one sentence; ref.]**
35. **The organization a run lands in** is the resolver's `orgId`, when valid (`host:314-322`, `isValidOrgId`). With a resolver that returns a principal with no `orgId`, `resolveOrgIdentity(context, isDevelopmentDefault, orgId)` decides (`host:347`); not read further. **[verify: what an absent `orgId` becomes when a custom resolver ran. The page's example gives `orgId` explicitly and says so.]**
36. **`ctx.user` inside the handler** is that principal's user: kitchen-sink's `sendWeeklySummary` reads `ctx.user?.identity.userId` (`flow.ts:35-43`). A flow with `requireUser: true` (default) therefore always has a user in a scheduled run. **[page: a handler example may log `ctx.user.identity.userId`.]**
37. **Request record provenance.** The run is recorded with `source: "scheduled"`, the flow kind, and `metadata.schedule` = `{ scheduleId, origin, cron, nominalFireTime, dispatchedAt, timezone }` (`rt:9-27` envelope, `rt:18-27`; `e2e:158-177`: `record.source === "scheduled"`, `metadata.schedule.scheduleId`, `.origin === "static"`). `record.userId` is the principal's user (`e2e:209-222`, dynamic case: `record.userId` is `"u_1"`). **[page, check step: where to see the run; ref for the record shape.]**
38. **Handler's `input`.** `schedule.input` is a value or a function of `{ scheduleId, cron, nominalFireTime, principal, flowKind, origin }`; absent, the handler gets `{}` (`rt:238-250`; `st:107-122`). The kitchen-sink handler's input schema is `z.object({}).passthrough()` (`flow.ts:37`). **[page: the handler's `inputSchema` must accept `{}` if the entry has no `input` (**[verify]**: failure when it does not was not read)].**
39. **What state a run touches.** User-scoped state lands in the principal's user cell (`rt:116`, `rt:223-227`). **[Stored-parts questions: see "Stored parts" below.]**

## Check a run

40. **Dispatch answers** (`rt:76-81`, `rt:146`, `rt:166-178`, `rt:221-230`; `sch` response table): `202 { status: "accepted", scheduleId, origin, requestId }` the action started; `200 { status: "skipped", reason: "in_flight", requestId }` a previous run of this schedule is still going and `onOverlap` is the default `"skip"`; `200 { status: "duplicate", scheduleId, nominalFireTime }` that scheduled time already fired (or a later one did); `401` auth failed; `404 { error: "flow_not_found" | "schedule_not_found" }`; `400` invalid id, invalid schedule, a body time that is not a scheduled time or not yet due; `500` resolver or input function threw; `503` flow unregistered or dispatch failed. **[page: the three a reader meets in a check (202, 200 duplicate, 401); full table [ref].]**
41. **202 is not "finished".** The endpoint is fire-and-forget; action errors land on the request record and show in the DevTool, not in the dispatch response (`sch` "The dispatch endpoint", paragraph after the table). **[page]**
42. **What reaches the cron caller is the status only** (fact 5). So in Vercel's cron log a green run means the dispatch answered 2xx, including `200 duplicate` and `200 skipped`, which ran nothing. **[page: say so; it is the main misreading.]** **[verify: what Vercel's dashboard shows is not in the repo; the page says "the status code the dispatch endpoint returned", no dashboard claims.]**
43. **List a flow's schedules:** `GET /api/flows/:flowKind/schedules` with the same bearer returns `200 { static: [{ id, cron, action, timezone, description?, enabled }], dynamic: { provided: boolean } }` (`rt:84-97`, `rt:135-156`; `e2e:262-`, test "GET /api/flows/:kind/schedules lists static + dynamic.provided"). `action` there is the handler block's name (`rt:142`). Same auth as dispatch (`rt:110-133`). A flow with no entry returns `404 flow_not_found` (`rt:106-108`). **[page: the check that the entry registered; a `curl`.]**
44. **Fire it by hand** to check the handler without waiting for Vercel: `curl -X POST <base>/api/flows/<kind>/schedules/<id>/dispatch -H "Authorization: Bearer $CRON_SECRET"`; with no body the fire counts against the latest scheduled time already due, so a manual POST runs only if that time has not fired yet, else `200 duplicate` (`sch` "At most once per scheduled time", last sentence of the list; `once:160-170` pins the no-body semantics; `vc:236-241` has a curl with a body). **[page: the curl must have no body; the kept page's body `{"nominalFireTime":"2026-06-01T00:00:00Z"}` is a fixed past time and answers `400 not_yet_due`, `duplicate` or `duplicate/stale` depending on the date, so it fails as a "check".]** **[contradiction with `vc:236-241`: the code wins; the page sends no body.]**
45. **Hit the cron route itself locally** with `curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/...` to exercise the shim and the dispatch together (`vs:48-61`). **[page: yes; one command. [verify]: `NEXT_PUBLIC_BASE_URL` must be set to the local origin, or the shim answers `500` (`vs:52-53`).]**
46. **Vercel Cron does not run under `vercel dev`** (`vc:227`). **[verify: Vercel behaviour; the kept page states it. The page may carry it as one sentence with the same wording; or leave it out and give the curl.]**
47. **Where a run shows.** DevTool lists the run's request with `source: "scheduled"` (`sch` "The dispatch endpoint": errors "surface in DevTool"; `e2e:173`). The `fsdev dev` DevTool reads the same store the flow API writes (see B-06's sheet, fact 15-18, for the page that shows it). **[page: one sentence linking `build/debug-a-run`.]** **[verify: a deployed Vercel app's DevTool access is not documented in the cited sources; say "the request record" and name the DevTool for local runs only.]**
48. **A run whose time already fired is a no-op.** Each scheduled time fires at most once per schedule: one record per schedule holds the latest fired time, claimed by compare-and-set in the host's store before the handler runs (`rt:9-15`, `rt:223-230`; `sch` "At most once per scheduled time"; `once:89-130`: two hosts sharing a store fire a time once; a restart still answers duplicate). A Vercel retry or a second invocation for the same time answers `200 duplicate` and runs nothing. **[page: the guarantee in a sentence; the claim rules [ref].]**

50. **Overlap:** with `onOverlap` unset, a second dispatch while the first still runs answers `200 skipped` (`rt:166-178`; `sch` "Overlap policy"). A cron more frequent than the handler's runtime therefore skips. **[page: one line in the check step, because "skipped" is what a slow handler looks like.]**

## Limits the page states flat

51. Vercel Cron fires GET; the dispatch endpoint takes POST only; so the shim (or a hand-written route) is needed (`vc:18-20`). 
52. The shared secret is the only authentication on the cron route and the dispatch URL (`vc:117`). Anyone holding it can fire any schedule of any flow whose resolver accepts it, once per scheduled time (fact 48), including a manual no-body POST that runs the latest due time if it has not fired.
53. `defaultUserId` on the flow turns a missing header into a run as that user (fact 28). **[page: a warning in the protect step.]**
54. The shim is for static schedules (one route per schedule id, or one `[scheduleId]` route); a dynamic schedule per user is `createScheduleTickHandler`'s job (fact 31). `vc:128-131` names the cap on `vercel.json` entries ("Pro: 40 per project at time of writing"): **[verify, Vercel-side and dated: keep off the page.]**
55. Cron uses five fields (fact 11); a timezone other than UTC is flow-entry metadata the dispatch uses when computing due times (`rt:206-207`); `vercel.json` has its own cron string (fact 13).

## Stored parts (the four questions)

The recipe has one stored part: the **fired record**. Static schedule definitions are source code and the secret is an environment variable; neither is stored data.

56. **Fired record: who owns it.** The user cell of the principal the schedule runs as (`firedRecords.ts:1-6` header; `scheduledTime.ts:160-167`: `scopeId: userStorageKey(principal.userId, principal.orgId)`). For a static schedule with no `principal`, that is the gateway principal's user and organization, e.g. the `system` user. Under the recipe's resolver, the owner is the one fixed system principal. **[page: one clause.]**
57. **Who can see it.** Nothing the page's flow exposes reads it by name; it lives under the resource pattern `scheduled-fires/**` at user scope (`firedRecords.ts:9-14`, `FIRED_RECORDS_PATTERN`) in the flow's user-scoped resource state, so it is reachable only through whoever can read that user cell's resources. **[verify: whether the DevTool or a management route lists it was not read. The page says "an internal record" and does not claim visibility.]**
58. **Where it is stored.** The host's store, the `resourceState` store of the `StoreRegistry` (`rt:223-227`: `claimScheduledTime(host.stores.resourceState, ...)`).
