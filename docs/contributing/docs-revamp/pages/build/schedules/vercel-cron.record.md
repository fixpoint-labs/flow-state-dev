## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support-desk app's `support` flow has a `stale-ticket-sweep` schedule with no `principal` on the entry, and its resolver is a `createBearerSecretPrincipalResolver` configured with `principal: { userId: "system", orgId: "org_sys" }`. When Vercel Cron fires the sweep at 08:00, whose run is it, and what does `ctx.user` show inside `sweepStaleTickets`?
   Answer: The run executes as `schedule.principal ?? gatewayPrincipal`; with no `principal` on the entry it is the principal the resolver returned for the dispatch call, the fixed `{ userId: "system", orgId: "org_sys" }` the author configured. So `ctx.user.identity.userId` is `"system"`, the run lands in organization `org_sys`, and its request record carries `source: "scheduled"` and `userId: "system"` (facts 32, 33, 35, 36, 37). An entry could instead name a target user with `principal: { userId, orgId? }`, with the organization falling back to the gateway's when `orgId` is left out (fact 34).
2. Someone who found the URL `https://<app>/api/cron/support/stale-ticket-sweep` calls it with no `Authorization` header, then tries the dispatch URL `POST /api/flows/support/schedules/stale-ticket-sweep/dispatch` directly. What happens each time, and what stops them? *(edge case)*
   Answer: Neither route is restricted by network; the shared bearer secret is the only gate (fact 26, 52), and it is checked twice. The cron route's shim requires `Authorization: Bearer <CRON_SECRET>` on the inbound GET and answers `401 Unauthorized` without making any outbound call (fact 19, 25). On the dispatch URL the flow's `resolvePrincipal` runs before anything else is read, so a stranger learns nothing about whether a time has fired. With no header the bearer resolver returns `null`, and the host answers `401` because the flow keeps `requireUser` on and sets no `defaultUserId` (facts 24, 25, 28). A wrong token is compared in constant time and rejected with `401` too (fact 27).
3. A teammate adds `authentication.defaultUserId: "agent-1"` to the `support` flow so the helpdesk UI can work without login. What does that change for the scheduled dispatch endpoint? *(edge case)*
   Answer: When the `Authorization` header is missing, the bearer resolver returns `null` and does not throw. The host then applies the flow's `defaultUserId` if one is set, so a request with no header is no longer a `401`: it runs the schedule as that default user. A missing header is a `401` only while the flow requires a user and sets no `defaultUserId` (facts 28, 53). The page warns about this in the protect step.
4. The `support` flow also serves helpdesk agents through HTTP actions. How should its `resolvePrincipal` be written so that both the cron dispatch and the agents' requests work?
   Answer: Branch on `ctx.source`. Dispatch calls arrive with `ctx.source === "scheduled"`, so for those use the bearer-secret resolver, built once at the top of the flow file. Any other source falls through to the existing resolver for users, for example `defaultBodyUserIdPrincipalResolver` from `@flow-state-dev/engine`. A resolver that only knows the scheduler secret breaks the flow's HTTP routes (fact 29). Building the bearer resolver once outside the callback means a missing `CRON_SECRET` fails at startup, not on the first scheduled request (correction 2, fact 27).
5. After deploying, Vercel's cron log shows the 08:00 sweep green, but no tickets were swept. Which responses from the dispatch endpoint could still give a green run, and how do you tell them apart? *(edge case)*
   Answer: The shim relays only the dispatch status code with an empty body, so the cron caller never sees the JSON (facts 5, 42). Any 2xx looks green. `202 accepted` means the action started, not that it finished: action errors land on the request record (the DevTool for local runs), not in the response (fact 41). `200 duplicate` means that scheduled time had already fired, and `200 skipped` (`in_flight`) means a previous run was still going under the default `onOverlap: "skip"`. Both ran nothing (facts 40, 48, 50). To tell them apart, call the dispatch endpoint yourself with curl and read the body, or check the run's request record (`source: "scheduled"`, `metadata.schedule`) (facts 37, 44, 47).
6. You want to check the sweep handler now instead of waiting until 08:00. What do you run, what should the request look like, and why might it answer `200 duplicate` or `500` instead of running? *(edge case)*
   Answer: Either POST to `/api/flows/support/schedules/stale-ticket-sweep/dispatch` with `Authorization: Bearer $CRON_SECRET` and no body, or GET the cron route itself locally with the same header to exercise the shim and dispatch together. `GET /api/flows/support/schedules` with the same bearer confirms the entry registered (facts 43, 44, 45). With no body the fire counts against the latest scheduled time already due. If that time already fired, it answers `200 duplicate`, because each scheduled time fires at most once per schedule (facts 44, 48). Through the cron route, an unset `NEXT_PUBLIC_BASE_URL` makes the shim answer `500 "Server misconfigured: missing baseUrl"` (facts 19, 22, 45). Vercel Cron itself does not fire under `vercel dev` (fact 46).
