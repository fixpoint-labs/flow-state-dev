## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your billing flow has two schedules: a weekly invoice digest at `0 9 * * 1` and a nightly cleanup. How many Vercel Cron entries do you add to `vercel.json`, and what does that entry call?
   Answer: One entry, for the whole app. It points at the one cron route (`/api/cron/schedules`, whose file exports `GET = scheduler.route`). Each call runs the app's schedule tick once, and that tick fires every due schedule of every flow, static and dynamic. The tick then POSTs each fire to that schedule's dispatch endpoint on the same deployment (facts 8, 9, 25, 51).
2. The invoice digest runs and its handler reads `ctx.user.identity.userId`. No person clicked anything. Whose run is it, and what goes wrong if the resolver's principal has no `orgId`?
   Answer: The run belongs to the principal the flow's resolver returns for the `scheduled` source. In this recipe that is the principal given to `createBearerSecretPrincipalResolver`, `{ userId: "system", orgId: "..." }`, so `userId` is `"system"`. A schedule can name its own `principal` instead. If the resolver returns no organization, or the reserved default org, the fire is refused with 401 and does not run. That is why the example names an `orgId` (facts 39, 40, 41, 42).
3. A stranger finds your deployment URL and calls `/api/cron/schedules` without the secret. What happens? Then they skip the cron route and POST straight to `/api/flows/billing/schedules/<id>/dispatch`. What stops them there? *(edge case)*
   Answer: The cron route compares `Authorization` against `Bearer <CRON_SECRET>` in constant time. No header, a wrong secret, or a prefix of the secret all get 401 and nothing fires. The cron route's secret protects only the cron route. The dispatch endpoint is protected by the flow's own `authentication.resolvePrincipal` for the `scheduled` source. In the recipe that is `createBearerSecretPrincipalResolver` checking the same secret, which the tick sends on every fire: a wrong token gets 401, and a missing header returns null, which a configured resolver refuses. If no resolver is configured anywhere, the app runs unauthenticated under the development org and the dispatch endpoint accepts any caller. So configure a resolver before you deploy (facts 31, 32, 33, 34, 35).
4. You deploy and forget to set `CRON_SECRET` on the Vercel project. Does the cron route sit open to anyone? What happens to the app? *(edge case)*
   Answer: No. An empty or unset secret makes the route refuse every call with 401, so a missing secret never opens it. The recipe builds the flow's bearer resolver once, at module top level, and the factory throws on an empty secret, so the app refuses to load at start-up rather than failing later (facts 31, 36).
5. You run `curl -H "Authorization: Bearer $CRON_SECRET" https://<deployment>/api/cron/schedules` to check that things work, then run it again. What comes back, does the digest run twice, and does `dispatched: 1` mean it succeeded?
   Answer: Each call answers 200 `{"dispatched": N}`. It runs a real tick, not a dry run. The digest does not run twice: the dispatch endpoint records the latest scheduled time it fired for each schedule, and a second fire of that time answers `duplicate`. `dispatched` counts fires attempted, not accepted. A fire that got 404 or 400, or whose request threw, still counts, so check the function logs to see the run. If the route answers 500 `Server misconfigured`, the scheduler was never passed to `createFlowState({ scheduler })` (facts 21, 22, 44, 45, 46).
6. The cron entry runs every 15 minutes and the digest is `0 9 * * 1`. When does Monday's digest actually fire? If the deployment is down from 08:50 to 09:40, what happens, and does the framework retry a dispatch that failed? *(edge case)*
   Answer: It fires on the first beat after 09:00, somewhere between 09:00 and 09:15, with `nominalFireTime` 09:00. The beat's cadence sets how late a fire can be. After an outage the schedule fires once, late, for the latest time it missed. Earlier missed times are dropped, not backfilled. A dispatch that gets a non-2xx answer is not retried: the contract is at most once (facts 26, 27, 29, 48, 52).

## Reference rows

- Resolver construction: `createBearerSecretPrincipalResolver` reads its secret when built, so a missing `CRON_SECRET` fails at startup, not on the first request; `principal` is who the scheduled run belongs to. → R-20
- Scheduled handlers are reachable only through the dispatch endpoint; `ctx.source === "scheduled"` is the value a resolver branches on to accept the bearer secret for scheduled calls only. → R-20
- 3. Cron route: `vercelScheduler().route`, exported as the GET of one cron route, runs the app's schedule tick; the tick POSTs each due schedule to its dispatch endpoint. The `vercel.json` schedule sets only how often the tick runs; due times come from each flow's `cron`. → R-33 (corrected by pass 5)
- 4. Route options: `vercelScheduler({ secret? })`; `secret` defaults to `CRON_SECRET`, read on each call. The tick's base URL is the cron request's origin. The route answers `500` when the scheduler was not passed to `createFlowState({ scheduler })` or when the tick fails. → R-33 (corrected by pass 5)
- Bearer-secret auth: Vercel sends `Authorization: Bearer ${CRON_SECRET}`; a wrong secret returns `401` from the cron route or the dispatch endpoint. → R-20
- Where the secret is checked: the cron route (401, calls nothing onward) and the dispatch endpoint (resolver runs before anything else is read, so an unauthenticated POST learns nothing about fired times); a holder of the secret can fire any schedule the resolver accepts; rotation is a change to the env var. → R-20
- `defaultUserId` and scheduled calls: a request with no `Authorization` header runs as the default user; a wrong secret is still `401`. → R-20
- Dispatch with no body: stands in for the most recent scheduled time; a repeat for the same time returns `duplicate`. → R-33
- 9. Dispatch responses: `202` started (handler errors not in the response), `200 duplicate` (time already fired), `200 skipped` (previous run unfinished). The cron route does not relay them; it answers `200` with the count of fires the tick sent, `401`, or `500`. → R-33 (corrected by pass 5)
- Schedule list endpoint: `GET /api/flows/<kind>/schedules` with the bearer header lists the flow's registered schedules. → R-33
- 11. Tick: one cron entry on `vercelScheduler().route` fires every due schedule of every flow, static and dynamic; dynamic due times come from each flow's schedule index (options, cadence, delivery guarantee already linked). → R-33 (corrected by pass 5)
- 12. Delivery: one tick per cron beat; each due schedule fires once per tick. A non-2xx dispatch is not retried. After downtime or a missed beat a schedule fires once, late, for the latest time it missed; earlier missed times are dropped (answers "How is a missed tick handled?"). → R-33 (corrected by pass 5)
