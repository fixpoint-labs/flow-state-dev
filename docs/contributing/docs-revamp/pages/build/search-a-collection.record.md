## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk wants `draftReply` to find earlier ticket notes that mention "refund" before it drafts an answer. What do you change on `ticketNotes` and on the generator so the model can do that?
   Answer: Add `llmReadable: true` to the `ticketNotes` collection definition. It is one collection-wide flag, default `false`, and it applies to every note (facts 7, 12). On `draftReply`, declare the collection with `resources: { notes: ticketNotes }`, and put the search blocks from `resourceSearchTools()` (at least `searchResources`) in `tools` together with `readResourceContentTool()` (facts 30, 32). There is no per-field "searchable" marker. The collection opts in as a whole (fact 1).
2. A support lead asks the model to "find every note Priya wrote". `addNote` stores the author in the note's state (`author`) and writes only the note text to the body. What comes back, and why? *(edge case)*
   Answer: Nothing that matches by author. Search and grep read only the rendered content body (`readContent`). They never read state, and results carry no state either (facts 1, 2, 11). A state field is found only if the body renders it, for example through a template, and then the search matches the rendered text, not the template source (fact 2). To make the author findable, the body has to contain it.
3. You mount `searchResources` as a flow action and call it with `{ query: "refund" }`. What do the results look like, in what order do they come, and how does the model get a note's full text?
   Answer: You get `{ results: [{ uri, score, snippet }], nextCursor? }`, at most 10 by default (facts 15, 25). Each `uri` includes the scope, for example `session/ticketNotes/T-1042`, but `prefix` and glob patterns use the path inside the scope (`ticketNotes/**`) (fact 22). The score counts how many times the query terms occur in the note. Highest comes first, ties are broken by uri, and a note with score 0 is dropped (fact 18). Matching is by substring, so `use` matches "user" (fact 19). The snippet is the first line containing a term, cut short (fact 21). For the whole body, pass the uri to `readResourceContentTool()` (facts 24, 32).
4. Alice works for two customers, Acme and Globex, and the notes collection is user-scoped. Bob works for Acme. When Alice searches in Acme, whose notes come back? Can the model ask for Bob's notes? *(edge case)*
   Answer: Only the records for the scope the run resolves to: Alice's notes in Acme. A user's records are keyed by user and organization, so what she saved in Globex never shows up in Acme (facts 35, 36). Bob's user-scoped notes are not hers and are not returned. Search takes no user id argument (`query`, `prefix`, `limit`, `cursor`), and the caller comes from the server, not from the model, so the model cannot pass an id to reach Bob's notes (fact 41). If the collection were org-scoped, Alice and Bob would both get the same Acme records (fact 37). A session-scoped collection returns only the current session's notes (fact 35).
5. The generator has the search tools, but every search comes back empty and nothing throws. What are the two likely causes? *(edge case)*
   Answer: Either `ticketNotes` was never marked `llmReadable: true`, or the collection is not declared on the generator or the flow (`resources: { notes: ticketNotes }`). The tools read only the run's resource registry, and they skip a collection that did not opt in before listing it. Either way, the collection acts as if nothing registered it, and no error is raised (facts 3, 8, 46). A flow's `resourceVisibility` rule that hides the collection has the same effect (fact 33).
6. The notes collection grows to tens of thousands of entries, and someone asks for "notes about being charged twice" when the notes say "duplicate payment". Is this the right tool, and what if the records come from a projected collection backed by the app's own database? *(edge case)*
   Answer: No, on both counts. Search is lexical (no synonyms, no meaning), and every call reads every readable body, so it suits a bounded, curated set, not a large corpus (facts 26, 43, 45). Because each call reads the current bodies, an edited note is searched by its new text on the next call (fact 26). A projected collection is searched through its own `search` hook, and the results come in the hook's order. Glob and grep skip it. The hook receives `userId` and `orgId` and has to scope its own query with them, or a user will see in one organization what they saved in another (facts 28, 40).
