## What loads, and what the panel is a record of

6. **A resource load is one read of a resource's stored data into the request's memory.** A request loads a resource in one of four ways, and a record carries which: `flow-eager` (the resource is declared on the flow, loaded at request start), `action-eager` (declared in the dispatched action's block tree, loaded when the action starts), `block-eager` (loaded when the block that declares it starts), `lazy` (loaded by a read inside a block) (`ct:196-197`; `rl:17`). **[page]**
7. **Which wave loads what [test].**
   - A flow-level resource loads at request start for every action (`pw:128-141`; `rlt:246-283` asserts one `flow-eager` fetch record).
   - A collection declared in the dispatched action's block tree loads when the action starts, and a sibling action's collection is not loaded (`pw:94-126`; `rlt:246-283` asserts one `action-eager` prefix fetch). **[answers Q1: a resource declared only in another action did not load.]**
   - An eager single declared on the action's own block loads at action start as `action-eager` (`rlt:97-125`).
   - A lazy single loads once, when its declaring block starts, as `block-eager` (`rlt:68-95`; `pw:143-178`, "not loaded at context creation", then "loads a lazy single once at block dispatch").
   - A lazy collection loads nothing up front. Each read of a key fetches that key as `lazy` (`rlt:206-244`; `col:315-328`).
   **[page: the four sources in one table or list of four lines; the wave order is `reference/resources`.]**
8. **Where the rows land.** A block's loads are on that block's row. Loads that fire before any block runs (`flow-eager`, `action-eager`) are on the request's entry block, the top-most block, which is the action's block (`ct:289-295`; `rlt:246-283`, "land on the entry block, exactly once"; `cec:1305-1311`). Parallel branches each keep their own reads, with no cross-talk (`rlt:285-325`). A block that throws keeps its loads (`rlt:127-171`). **[page: the entry-block sentence; the other two are [ref].]**
9. **What a lazy single is for.** A lazy single resource is only valid declared on the block that needs it; declared at flow level it throws when the flow is defined (`core/types/resource.ts:316-323`; `col:338`). **[ref, one clause at most.]**
10. **Wave 1 durations are shares.** The flow-level resources load in one parallel burst, so the measured burst time is divided across the flow-level resources and each row shows its share (`cec:1850-1865`, comment: "split the one measured wall time across every flow-level record"). The rows sum to the burst's real time. **[ref; the page does not state it, but the reader will see equal times on flow-eager rows. If the page shows a flow-eager row's time, one clause: "the time for the whole start-up load, shared across the rows".]** **[source]**

## Step 2: Read the Resource Loads section

15. **Open `Resource Loads`.** Two parts, both optional. **Declared** is a row of chips, one per accessor key the block declares in its own `resources` map (`id:929-952`; `ct:296-301`; `rlt:327-349` asserts `declaredResources` contains `"decl"`). It shows only when the block declares at least one. **Loaded** is one line per load record (`id:953-963`). With a declared key and no records, the section reads `No loads fired for this block.` under Declared (`id:962-964`). **[page; answers Q1's first branch.]**
16. **A Loaded row, left to right** (`id:969-990`): the source label (fact 2); the storage key, or for a collection list or count the key prefix such as `ticketNotes/`; `.get()`, `.getOptional()`, `.list()` or `.count()` when the load came from a collection read; `cache hit` (green) or `fetch`; `×N` when N identical records collapsed into one; and, for a fetch only, the time as `12.3ms` to one decimal. A cache hit shows no time. **[page: this row anatomy, with one example row.]**
    - Storage key: `ct:192-194` ("Canonical storage key for a single/instance load, or the prefix for a collection list/count load").
    - `accessor` absent for a wave preload, since it is not a read (`ct:203-205`).
    - `cacheHit: true` is served from the in-memory cache, `false` a real store fetch (`ct:200-202`).
    - `count` is the number of identical records collapsed (`ct:206-207`).
17. **A fetch is a round trip to the store; a cache hit is a read served from memory the request already loaded.** `ct:200-202`; `rl:15-16`. **[page, one sentence each, in the plain words.]**
18. **What collapses.** Cache-hit records with the same source, key and accessor collapse into one row with a count; a loop that reads one key five times is one `cache hit ×5` row (`rlt:173-204`, count 5; `cec:1330-1364`; `ct:187-189`). Fetches never collapse: a lazy collection read for three distinct keys is three fetch rows, and re-reads of one of them are one hit row (`rlt:206-244`). **[page: one sentence and one example row.]**
19. **The scope of a record** (`session`, `user`, `org`) is on the record (`ct:195`) and the row does not show it. **[ref: do not state on the page.]** **[source]**
20. **The section only exists while trace observability is on.** `FSDEV_TRACE_OBSERVABILITY` set to `true`, `false`, `1` or `0` decides; unset, it is on unless `NODE_ENV` is `production` (`packages/core/src/helpers/trace-observability.ts:14-19`; `env:64`: "toggles full `block_trace` capture: inputs, prompts and resource loads. Defaults to on outside production"). With it off, the block's trace row is written without `resourceLoads` or `declaredResources` (`rlt:351-393` asserts both undefined on the one row, which is still recorded). `ct:289-295`: loads are "present only when trace observability is enabled and at least one load was recorded". **[page: one sentence, naming the variable, linking `reference/environment`. Answers Q1's observability branch.]** `fsdev dev` does not set the variable (`grep FSDEV_TRACE_OBSERVABILITY packages/fsdev/src`: no hits), so a `fsdev dev` started with `NODE_ENV=production` in the shell shows no loads. **[source; [verify] with a run before the page says it. The page need only say "outside production".]**
21. **Resource Load Summary** (a second collapsed section) totals the selected block and every block beneath it, so selecting the entry block gives the whole request (`id:253-263`; `id:901-909` `collectSubtreeLoads`). Five rows (`id:992-1030`): `Total loads` (every access, counting each collapsed record by its `count`), `Store fetches` (the count of non-hit accesses), `Total fetch time` (summed, one decimal, `ms`), `Cache-hit rate` (whole percent, rounded), `Slowest fetch` (key and time). `Slowest fetch` is omitted when no fetch took more than 0 ms (`id:1003-1005`, `:1017-1018`: a key is recorded only when `durationMs > slowestMs`, starting at 0). **[page: the five labels; the rounding and omission are [ref].]** **[source]**
22. **The summary needs a selected block with loads somewhere beneath it.** Select a block whose subtree has none and the section is absent (`id:257-263`). **[page: one clause.]**

## Why a resource did not load [answers Q1]

Each cause below is something the reader can see in the panel or the code they wrote.

23. **No Resource Loads section on the block.** The block declares no resources and read none (`id:243-246`); or trace observability is off (fact 20); or you selected a block that did not declare it (declared keys are the block's own, not its descendants' or its parent's; `ct:296-301`, "Accessor/storage keys this block declares at build time (`ownDeclaredResources`)"). **[page]**
24. **The resource is declared in a different action's block tree.** A request loads only the dispatched action's resources; a sibling action's collection is not loaded (`pw:94-126`). In the DevTool, open the request for the action you meant. **[page; [test].]**
25. **A lazy collection nobody read.** Nothing loads up front; the key appears under Declared and has no Loaded row until a `get`, `getOptional`, `list` or `count` runs (`rlt:206-244`; `col:315-328`; `cec:2260`: `if (mode === "lazy") continue;` for collections in the waves). The read may sit behind a branch that did not run. **[page; the usual cause under a Declared chip with no row.]**
26. **A lazy collection read by `list()` or `count()`** fetches the whole prefix in one scan, and the row's key is the prefix, such as `ticketNotes/`, with `.list()` or `.count()` (`rr:2053-2058`, `recordLazyRead("list", \`${collectionKeyPrefix}${prefix ?? ""}\`, ...)` and `("count", collectionKeyPrefix, ...)`; `col:330-332`: "reads the entire collection prefix in one unbounded scan"). A `list(prefix)` row's key is the collection prefix plus the argument. **[page: one sentence. This is the row that explains a slow lazy request.]**
27. **A projected collection never loads from the store.** Its data comes from the app's `read` hook on every access, so it has no fetch or cache-hit rows for the waves (`cec:2008`, `:2217` skip projected collections; `apps/docs/docs/resources/projected-collections.md:9`: "The framework does not store a copy. Each `get`, `list`, or client read calls the `read` or `search` hook you supply"). **[page: one sentence, link to the projected collections page.]** **[source: no engine test over the loads panel for a projected collection. [verify] that a lazy projected collection read records no row; the doc comment at `cec:2217` covers the wave path only.]**
28. **An org-scoped resource with no organisation on the request** is skipped by the load waves (`cec:2220`, `if (scopeId === undefined) continue; // org scope not present this request`). **[ref: omit from the page unless the app example has an org resource and a request without one. The support-desk's `refundPolicy` is org-scoped (`res:30`); a request with no org would drop it. [verify] what a block reading it then sees before the page says more.]** **[source]**
29. **An eager resource that already loaded is not fetched again.** A second wave that finds the key or prefix in the cache records a cache hit with no time instead of a fetch (`cec:2264-2270`, `:2284-2290`; the record's doc, `ct:200-202`). So an eager resource declared on a block under the action shows its one `fetch` on the entry block (source `Action eager`) and `cache hit` rows on the blocks beneath. A reader who looks only at the reading block sees hits and no fetch, and has not found a missing load. **[page: this is the second most common confusion; one sentence. [test] for the reading block's cache-hit rows: `rlt:173-204` (the reader is a step under a sequencer so it differs from the entry block).]**
30. **The key under Loaded is the storage key, the chip under Declared is the accessor.** Declared lists the names in the block's `resources` map (`build-block.ts` stamps `Object.keys(ownDeclaredResources)`: `packages/core/src/blocks/internal/build-block.ts:325-329`). A single resource's row shows its storage key, which can differ from the accessor when the same resource is declared under another name elsewhere in the flow (`cec:2221-2224`, comment: "Key the load by the canonical storage key ... so aliased single resources load under the same slot the registry reads"). A collection's row shows its prefix. **[page: one clause: "match a chip to a row by the resource's key, not always its name". [source]; [verify] with an aliased example or leave it out. Recommend leaving it out of the page and keeping fact 30's first sentence only.]**
31. **A resource that loaded but has no value.** Loads record that a read happened, not what it returned. A `get` of a key that does not exist still shows as a row; to see the stored data open the Resources panel (fact 1) or read the resource in the block. `rr:2038-2042` records the read after the lookup with no value in the record (`ResourceLoadRecord` carries no value field, `ct:191-208`). **[page: one clause, pointing at the Resources panel. [verify] the not-found case; the page may say only "a row records the read, not the value".]**
32. **A request that resumes after a pause.** Not covered by a page fact; do not state. `packages/engine/test/resume-replay-traces-off.test.ts:169-170` asserts the two load fields undefined with observability off on a resumed request, and says nothing about loads on resume with it on. **[left out: no observable surface for loads on a resumed request.]**

## Stored parts: the four questions

The page is about something that stores data: a resource-load record. (The resource it describes is C-08's subject; the questions below are about the load records only.)

37. **A resource-load record.**
    - **Who owns it.** The run. The framework writes it onto the block's trace row as the block runs; no flow or block code creates it (`ct:289-295`; `cec:3947-3958` drains the buffer onto the row at the block's `output` phase, success or error). The user does not edit it.
    - **Who can see it.** The DevTool reader. Trace rows (`block_trace`) are never delivered to an app's client on the normal stream: they resolve to `client: false, history: false` and arrive only when the stream request asks for trace (`packages/contracts/src/items/resolve-visibility.ts:12-20`, `:40`; `packages/engine/src/routes/stream-routes.ts:106`; `dar` fact 39). The Resource Loads section is read from the trace row and needs no debug endpoint (`dvc:142`: "gated by trace observability rather than the debug endpoint"), unlike the Resources panel, which shows "Debug endpoints disabled" without it (`resources-panel.tsx:77-96`). A key's stored data is not on the record, so no secret field can leak through it (`ct:191-208`: the record has `storageKey`, `scope`, `source`, `durationMs`, `cacheHit`, `accessor`, `count`, `templateSource`). **[page: "your app's users never see this", one sentence.]**
    - **Where it is stored.** On the block's `block_trace` item in the trace store: `fsdev dev` with no config writes SQLite at `.fsdev/data/fsdev.db`; with an `fsdev.config.ts` the app's own stores are used (`su:128-132`; `dar` facts 3, 18). A block marked `transient: true` streams its trace live but does not keep it, so its Resource Loads vanish on reload (`ct:176-182`). **[page: "stored with the run's trace"; transient is [ref].]**
    - **How many exist.** One list per block row per execution. A block that runs more than once (a loop) has one row, so one list, per pass (`ov:138`; `dar` fact 47). Identical cache-hit reads collapse into one record with a count (fact 18); every fetch is its own record. A trace store keeps the most recent 50 requests, or 1000 when `NODE_ENV=development` (`packages/engine/src/stores/index.ts:164-182`; `dar` fact 3), so an old run's loads age out with its trace. **[page: "recent requests only"; the numbers are [ref]. Do not state 1000 (`dar` fact 3: a plain `fsdev dev` keeps 50 unless the shell sets `NODE_ENV`).]**
38. **The resource's own data is a separate stored part** and has its own answers on C-08 (`res`). The page does not repeat them. **[page: link to `../concepts/resources.md`.]**

## Revision round 1 (corrections to the facts above)

- **Cache hits on blocks beneath the top block are a collection behaviour.** Only collection reads (`get`, `getOptional`, `list`, `count`) record a cache hit. A single resource declared on the flow gets a Flow eager fetch row on the top block, and a read of it in a block records no load, so no block beneath shows a hit. Fact 29 holds for collections only.
