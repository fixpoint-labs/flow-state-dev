## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You open the DevTool on a support-desk session, expand the latest request in the Trace tab, and click the `draftReply` row. In its detail panel you expand Resource Loads and see a `ticketNotes` chip under Declared, but no row for it under Loaded. The right-hand Resources panel shows ticketNotes data. What most likely happened, and where should you look in your code?
   Answer: The loads are in the block's detail panel (the collapsed Resource Loads section), not the right-rail Resources panel, which shows each resource's stored state now and says nothing about loads (fact 1). A declared key with no Loaded row is a lazy collection that nothing read: a lazy collection loads nothing up front and gets a row only when a get, getOptional, list or count runs (facts 3, 25). Look for the read in draftReply; it may sit behind a branch that did not run this time.
2. `ticketNotes` is an ordinary (eager) collection. On the `draftReply` row you see only `Action eager ... cache hit` rows for ticketNotes, with no time and no `fetch`. A teammate says the resource never loaded from the store. Are they right, and which row shows the real load?
   Answer: No. An eager resource that already loaded is not fetched again. A later read finds it in memory and records a cache hit with no time (facts 17, 29). The single fetch happened when the action started (source Action eager). It sits on the request's entry block, the top block the action runs, because loads that fire before any block runs land there (facts 8, 13). Click that top row to see the `fetch` with its time.
3. A colleague started `fsdev dev` from a shell where `NODE_ENV=production` was set. They run the support desk, click `draftReply`, and the detail panel has no Resource Loads or Resource Load Summary section at all on any block. What is wrong, and how do they fix it? *(edge case)*
   Answer: The sections only exist while trace observability is on. Without it, block trace rows are still recorded but carry no loads and no declared keys (facts 4, 20, 23). It is on by default outside production. Here NODE_ENV=production turned it off. Set `FSDEV_TRACE_OBSERVABILITY` to `true` (or `1`), or drop NODE_ENV=production, then run again. Other reasons the section can be missing: the block declares and reads no resources, or you selected a block that does not itself declare the resource, since Declared lists only the block's own keys (fact 23).
4. You edit `ticketNotes` to add `prefetchMode: "lazy"`. In `draftReply`, a loop calls `await ctx.resources.ticketNotes.get("n-1")` three times, and then the block calls `list()` once. What rows should Resource Loads show for draftReply after the next run? *(edge case)*
   Answer: Nothing loads up front for a lazy collection (fact 7). The first get fetches that one key: a `Lazy` row with key `ticketNotes/n-1`, `.get()`, `fetch` and a time in ms. The two re-reads are served from memory and collapse into one `cache hit ×2` row. Identical cache hits collapse, fetches never do (facts 16, 18, 34). The `list()` reads the whole collection prefix in one scan: a `Lazy` row whose key is the prefix `ticketNotes/`, with `.list()`, `fetch` and a time. That row is the one to check when a lazy request is slow (fact 26).
5. A support agent using your app, a second person and not you, opens a ticket and `draftReply` runs. Can they see the resource-load records for that request, or any ticket-note data through them? And will looking at loads in the DevTool change what the run did? *(edge case)*
   Answer: No. Load records are trace-only. They are stored on the block's trace row with the run's trace and are never delivered to an app's client on the normal stream, so your app's users never see them (facts 37, 39). A record holds the key, source, time and hit/fetch, never the stored data, so no data leaks through it (fact 37). Reading loads never changes the run (fact 39).
6. You want the totals for a whole support-desk request: how many store fetches it made, the total fetch time, the cache-hit rate and the slowest fetch. Which block do you select, which section do you open, and what if a resource you expected appears nowhere because it is declared only in a different action?
   Answer: Select the request's entry block, the top block the action runs, and expand Resource Load Summary. It totals the selected block and every block beneath it. Its rows are Total loads, Store fetches, Total fetch time, Cache-hit rate and Slowest fetch (fact 21). A block with no loads anywhere beneath it shows no summary (fact 22). A request loads only the dispatched action's resources, and a collection declared only in a sibling action's block tree is not loaded, so open the request for the action you meant (facts 7, 24).

## Reference rows

- Load modes: Flow eager, Action eager, Block eager, Lazy: what triggers each, eager as the collection default, and what a store fetch versus a cache hit is (cache hits carry no time; identical repeats collapse into one `×N` row). → R-08
- Load trace record and its roll-up: fields recorded per load (mode, key, call, fetch or cache hit, duration) and the summary totals (loads, fetches, fetch time, cache-hit rate, slowest fetch), which cover the block and everything under it. → R-06
- `FSDEV_TRACE_OBSERVABILITY`: what reads it, default on outside production, and that turning it off removes load records. → R-15
- Lazy collection: a load is triggered by the first read that needs the data. `get`, `getOptional`, `list` and `count` each record a Lazy load row; `findBy` loads through `list`; `create`, `getOrCreate`, `upsert` and `delete` also load the key first but record no row. Nothing loads before one of these runs. → R-08 (corrected by pass 5)
- Which resources load for a request: the flow's, the invoked action's and the running blocks' declarations only; other actions' resources are not loaded. → R-08
- Where a load is recorded: loads before any block runs, and flow-eager and action-eager loads, are recorded on the request's top block (the first block, the action's block). Blocks beneath record cache hits when they read the same collection, tagged with the wave that loaded it. Reads of a single resource record no load. → R-06 (corrected by pass 5)
- Projected collections: read through the `read` hook on every access, never loaded from the store, no load records. → R-08
- Load records hold the key and timing of a read, never the content returned. → R-06
