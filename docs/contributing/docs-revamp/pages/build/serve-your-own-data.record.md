## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support app keeps customer orders in its own Postgres database, and you declare an `orders` collection over them with `defineProjectedResourceCollection`. Where do the orders live now? Has the framework copied them anywhere, and can a block or the browser write to them through the collection?
   Answer: They stay in the app's own database. The framework keeps no copy, and each read calls the `read` or `search` function the app supplies (fact 7; four-questions table, 'Where it is stored'). They are not in the session snapshot either, which lists the collection as `{ prefetched: [] }` with no `count` (fact 30). The collection is read-only by structure: it has no write methods, no `count`, no `maxInstances` and no eviction (fact 14). A client `POST`, `PATCH` or `DELETE` gets `403` naming a read-only projected collection, and setting `client.content.create/update/delete` to `true` throws when the collection is defined (fact 36).
2. In the `lookUpOrder` block, `ctx.resources.orders.get(id)` is called twice for the same order in one run, and then again in the next run. How many times does your `read` function run, and does the framework cache the order between runs?
   Answer: Within one request a key is read once: the second `get` for the same id, or a `get` for a key that an earlier `list` in that request already returned, is answered from an in-memory map for that request, and concurrent reads of one key share a single call (fact 23). The map is never stored and never shared, so the next request calls `read` again (fact 23, fact 34). Each read asks the app, and the framework adds no cache across requests (fact 34).
3. A second customer signs in to the support app and opens their orders panel. What stops them from seeing the first customer's orders? *(edge case)*
   Answer: Your `read` and `search` functions do. The framework does not filter what the app returns by user. It passes the trusted context, `ctx.userId` and `ctx.orgId` (plus `scopeId`), which the server derives from the loaded session, never from the request body. The app's query has to use both ids in its `where`, or a user sees data across owners or across organizations (facts 18, 19, 21). The key is the one value the caller supplies (fact 21). With `scope: "user"`, `ctx.scopeId` is that user's id (fact 11).
4. `lookUpOrder` asks for order `ord_123`, and the app's database has no row for it. What does your `read` return, and what does the block get from `get` and from `getOptional`? What happens if the row exists but is missing a field the `stateSchema` requires? *(edge case)*
   Answer: `read` returns `null` (`undefined` is treated the same). `get` then throws an error saying the record was not found, and `getOptional` returns `undefined`. A record that fails `stateSchema` makes the read throw, with an error naming `stateSchema`. Schema defaults are applied to what the app returns (facts 12, 16, 17). In `search` the rule is different: a hit that fails the schema is dropped and logged, and the rest of the page is still returned (fact 26). A key that does not match the pattern (such as `a/b` against `orders/*`) throws `does not match`, and `read` is never called (fact 13).
5. You build `orders-panel.tsx` with `useResourceCollectionList(session, "orders", { limit: 20 })`. What must the collection declare before the browser can see anything, what does the panel show on first paint, and what happens when the user scrolls for more?
   Answer: The collection needs `client: { state: { read: true } }`. Without it the list and record routes answer `403`. Pair it with `expose: [...]` so the browser gets only the fields the panel uses (facts 27, 28). The `ref` is the accessor name from `resources: { orders }` (facts 15, 29). `items` starts empty and `hasMore` is false until the first page lands. There is no count or total, because the framework never lists the app's rows into the snapshot (fact 30). Each page is one request that runs the app's `search` with the `limit` and the cursor. `loadMore` passes back the app's own `nextCursor` and appends the results, and `hasMore` stays true while a cursor remains (facts 25, 31). Each item's `clientData` may be undefined, so the panel reads `item.clientData?.status` (type-check note).
6. While a customer has the orders panel open, a teammate changes that customer's order status in the app's database. Does the panel update? What makes it show the new status? *(edge case)*
   Answer: No. Nothing tells the framework that the app's own data changed: the collection sends no `resource_change`, and change-awareness is not built. The screen shows what the app returned when it was asked (C1, facts 30, 35). It asks again only on a new query or a new mount, for example a different `limit` or `topicPrefix` (C1, C2). Calling the list hook's `refetch()` does not ask the app again. For a single record, `useCollectionResource(...).refetch()` does re-read it (C2, fact 32).
