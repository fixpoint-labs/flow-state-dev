## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. On the support desk, `ticketNotes` is declared with `client: { state: { read: true }, expose: ["pinned"] }`. An agent opens a note in the DevTool's Resources panel and sees its `author`, but the ticket page never shows who wrote the note. Why, and where is the fix?
   Answer: Open the note's row: the Server tab (the stored state minus `secret` fields) shows `author` and `pinned`, and the Client tab (the same projection the browser's reads use) shows only `pinned` (facts 8, 14). `expose` keeps only the fields it lists, so `author` stays on the server (fact 20; decision-table row "Client tab lacks the field", fact 24). The fix goes in the resource's `client` config: add `author` to `expose`, unless the browser must never see it, in which case it belongs in `secret` and should not be exposed (facts 25, 26).
2. A developer removes the `client` block from `ticketNotes`. The panel now shows one state tree for each note with no Server/Client tabs, so they assume the browser gets the full state. Are they right, and what does the page actually receive?
   Answer: No. The row's summary line reads `no-client`, and that summary is the reliable check, not whether tabs appear (facts 1, 11). With no `client` config the debug view reports `no_client_data` and draws one tree, while the browser's snapshot leaves the collection out entirely, so the page gets nothing for it (fact 1; decision-table row "Row reads `no-client`", fact 24; pinned by `rst:557-566`).
3. The panel shows `ticketNotes` with 47 items, and the page's snapshot reports `count: 47`, yet the ticket page lists no notes. Is the projection wrong?
   Answer: Not necessarily. The Client tab projects the whole stored state and does not apply `prefetchWindow`, so it can list all 47 items while the browser's snapshot carries `count: 47` and an empty window (fact 14). The snapshot's `prefetched` list is empty unless `prefetchWindow` is above 0 and `client.state.read` is true (fact 22). The page has to read the items itself or set a prefetch window. To see exactly what the browser got, look at the browser's Network tab for the session state route (fact 27).
4. Failure: `ticketNotes` uses a `client.data` function. On one note, the Client tab has a dashed notice reading `client.data threw: Cannot read properties of undefined`, and the pane beneath it reads `— no client value —`. What does the page get for that note, and is there a case where this notice is misleading? *(edge case)*
   Answer: The projection raised an error on that record, and the page gets nothing for it. The Client tab stays in place, with the notice shown above it (facts 3, 24; pinned by `drt:904-922`). The misleading case is an `async` `data` function. The debug snapshot is synchronous, so it reports `client.data returned a Promise; async projection not supported in debug snapshot` as "threw", but the production routes await the projection and the browser does get the value (fact 4, marked verify).
5. Second user: two agents add notes on the same ticket session, and some notes are keyed to the other agent. The developer opens the session in the DevTool and the item count is lower than the number of notes in the store. Is the panel broken? *(edge case)*
   Answer: No. The debug tree reads the session as that session's user. A collection's listing and count include only the keys that user may read, so a note keyed to another user is neither listed nor counted (facts 5, 28). The browser's `count` and prefetch window apply the same owner-private fence, so the panel matches what that user's page would get (fact 28).
6. Edit: after seeing `author` missing from the Client tab, the developer adds `author` to `expose` and saves. Do they need to run `addNote` again to check the change, and why might the Client tab still look the same? *(edge case)*
   Answer: They do not need a new run. The Client tab is not a recording of what the page received. It is recomputed on every read from the stored state and the current `client` config, so existing notes show `author` once the server has the new definition (facts 15, 29). Loading the new definition takes a server restart: restart `fsdev dev`, or start it with `--watch`, which restarts on file changes on a loopback bind (fact 15). After that, the refresh button (`Refresh debug resources`) reloads the panel. The panel also refreshes on its own when the stream carries a `state_change` or `resource_change` item (facts 10, 29).
