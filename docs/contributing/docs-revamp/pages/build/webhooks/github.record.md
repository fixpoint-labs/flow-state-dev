## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Someone who doesn't know your secret POSTs a well-formed `pull_request` body with `action: "opened"` to `https://<host>/api/flows/repo/webhooks/github`, putting a made-up value in `x-hub-signature-256`. What refuses it, what do they get back, and does `reviewPullRequest` run or a session get created? *(edge case)*
   Answer: The host's `githubWebhookVerifier(secret)` refuses it. It computes HMAC-SHA256 of the raw body bytes under the secret and compares that, in constant time, with the `sha256=<hex>` value in `X-Hub-Signature-256`. Verification runs first, before the body is parsed or any session exists. A false result (mismatch, missing header, or a header without the `sha256=` prefix) or a throw returns `401 { error: "invalid_signature" }`. Nothing runs and no session is created (facts 18, 20, 21, 36). The flow holds no secret or signature code; the host supplies them (fact 14).
2. Nobody signs in when GitHub calls your server. Which user does a `reviewPullRequest` run belong to, and what in the flow decides that?
   Answer: The run belongs to the principal resolved with `source: "webhook"`. If no resolver is configured, the flow's `authentication: { defaultUserId: "github-bot", requireUser: false }` applies, so the run belongs to `userId: "github-bot"`. A flow's own `authentication.resolvePrincipal` would take precedence over the host's (facts 13, 37). Don't return a `userId` key from `input`: with no resolver, the default resolver reads `userId` from that object, so the sender could pick the user (fact 38). `requireUser: false` also means the flow can't declare `user.stateSchema`, `user.client` or `scope: "user"` resources, and `defineFlow` throws if it does (fact 13).
3. You register the binding under `on: { "pull_request.opened": ... }` because that's how you think of the event. A PR gets opened and nothing happens. Why, and how should the binding be written to run only on newly opened PRs? *(edge case)*
   Answer: GitHub names the event in the `X-GitHub-Event` header (`pull_request`). The sub-event is the body's `action` field (`opened`, `closed`, `synchronize`). The `on` key has to be `pull_request`. A key that includes the action never matches, and because keys aren't checked against any provider vocabulary, a wrong key raises no error. The delivery just comes back 202 ignored. Routing happens in two steps: the host's `eventType: (_p, headers) => headers.get("x-github-event")` reads the header, then the binding's `when: (e) => e.payload.action === "opened"` narrows on the action (facts 2, 5, 9, 22, 30).
4. Two hours after you open PR #42 on `acme/api`, you push new commits, and GitHub sends a `pull_request` delivery with `action: "synchronize"`. You also selected "Send me everything", so `push` deliveries arrive as well. What does the server send back for each, and does any of them start a review? *(edge case)*
   Answer: Neither starts a review. The `synchronize` delivery fails the `when` predicate, so it is answered `202 { status: "ignored", provider, eventType }` and nothing runs. A `push` delivery has no `on` key and gets the same 202 ignored. Ignoring returns a 2xx because providers retry on non-2xx responses, so subscribing to more events than you bind is safe (facts 9, 28, 30, 31). A throwing `when` also counts as a non-match and returns 202 (fact 9).
5. With `sessionId: (e) => `${e.payload.repository.full_name}#${e.payload.number}``, how many sessions do PR #42 and PR #43 on `acme/api` produce across all their deliveries, and what changes if you leave `sessionId` out?
   Answer: One session per pull request: `acme/api#42` and `acme/api#43`. The first delivery for a key creates the session and later deliveries reuse it. If two first deliveries arrive at once, one creates the session and the other adopts it. The session is owned by the resolved principal (`github-bot`) and lives in the session store of the flow's `stores` profile; `inMemoryStores()` doesn't survive a restart. Without `sessionId`, every delivery gets a fresh ephemeral session (facts 12, 39).
6. You've just added the webhook in the repository settings, and the first real delivery comes back 401 `invalid_signature`. Another attempt comes back 400 `invalid_payload`. What's the likely cause of each, and where do you confirm the fix worked? *(edge case)*
   Answer: A 401 means the Secret configured on GitHub doesn't match the value the host's getter returns (`GITHUB_WEBHOOK_SECRET`), or the body was altered. A 400 `invalid_payload` means the body isn't JSON, so set Content type to `application/json`. For completeness, a 404 `flow_not_found` points to the flow id in the URL, and a 404 `webhook_not_found` means the provider segment isn't `github` or isn't on the mount (facts 28, 29, 34). Success is `202 { status: "accepted", provider, eventType, requestId }`, sent before the block finishes. Errors after that point appear in DevTool, not in the response (fact 32). GitHub's "Recent Deliveries" tab shows each request and response and can redeliver a payload (fact 35).

## Reference rows

- Event routing key: a provider's `eventType` extractor yields the key under `on`; GitHub's comes from the `X-GitHub-Event` header, and the sub-event (`action`) is in the body and is narrowed by `when`. One row per binding field (`on` key, `when`, `input`, `sessionId`, `block`). → R-32
- Binding `on` key and `when` predicate: the key is the extractor's event type, never a dotted sub-event. A delivery whose `when` returns false is acknowledged and ignored, not rejected. → R-32
- Verification: `githubWebhookVerifier(secretFn)` checks `X-Hub-Signature-256` (`sha256=<hex>`) over the raw body; a failed signature's response is the lookup for what a sender gets back. → R-32
- Provider option `deliveryId(payload, headers)`: returns the per-delivery id (`string | undefined`; GitHub's is the `X-GitHub-Delivery` header). It is set on `event.deliveryId` and recorded as `metadata.webhook.deliveryId` for provenance, so a handler can deduplicate on it. A throwing extractor is logged and the id omitted. The `on` route does not deduplicate by itself. → R-32 (corrected by pass 5)
- Delivery response: 202 `{status:"accepted", provider, eventType, requestId}` once the dispatch is durably recorded (the handler then runs asynchronously). A delivery matching no binding, or with `when` false, also gets 202 with `{status:"ignored", provider, eventType}`. If the dispatch could not be durably recorded the response is 503 `dispatch_not_durable`, so the sender retries. → R-32 (corrected by pass 5)
