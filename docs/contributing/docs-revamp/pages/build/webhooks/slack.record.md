## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You have the slack flow deployed and paste its address into the Request URL field on your Slack app's Event Subscriptions page. What address do you paste, what does Slack send straight away, and which part of your code answers it?
   Answer: Paste https://<host>/api/flows/slack/webhooks/slack: the adapter's one route is POST <basePath>/:flowKind/webhooks/:provider, basePath defaults to /api/flows, and a singleton flow's id is its kind (row 27). Slack posts { type: 'url_verification', challenge } once and expects the challenge echoed (row 5). The host's provider definition answers it: its acknowledge returns payload.challenge, and when acknowledge returns a non-null body the route responds 200 with that body and dispatches nothing (rows 6-8). The flow never sees this request; its on map and when are not consulted (row 12).
2. Slack will not mark the Request URL as Verified. The provider's acknowledge looks right, but you set the verifier's secret to the bot token you copied from the app's OAuth page. Why does the handshake fail, and what do you change? *(edge case)*
   Answer: verify runs first on the raw bytes, before the body is parsed and before acknowledge, so the handshake must itself pass the signature check; with the wrong secret the route answers 401 { error: 'invalid_signature' } and no challenge is echoed (rows 9, 21). slackWebhookVerifier wants Slack's signing secret, not a bot token (row 20); it checks the v0=<hex> HMAC-SHA256 of v0:<timestamp>:<rawBody> under that secret (row 16). Put the signing secret in the env var the getter reads. The getter is read once on first verification and cached, so restart after changing it (row 19).
3. The URL shows Verified, you subscribed to message.channels and reaction_added, and someone posts in #support, but the ingest block never runs. Your flow's binding is under on: { 'message.channels': ... }. What is wrong, and what happens to the reaction events? *(edge case)*
   Answer: on keys are matched by exact string equality against what the host's eventType returned. For Slack that is payload.event?.type ?? payload.type, so a channel post arrives as 'message'. 'message.channels' is only the subscription's name in Slack's UI (rows 22, 29). With the key mismatched, the URL still verifies and every event is answered 202 { status: 'ignored' } (row 46). Change the key to message. A reaction_added with no binding gets the same 202 ignored: it is acknowledged and dropped. That makes subscribing to more types than the flow binds safe, and the 2xx stops Slack retrying (row 34).
4. Two people post in #support and a third posts in #billing. How many sessions does the flow end up with, who owns them, and can a teammate logged into your app in the browser see them? *(edge case)*
   Answer: sessionId: e => `channel-${e.payload.event.channel}` gives one session per channel. The first delivery for an id creates the session and later ones reuse it, so you get two sessions: both #support posts accumulate in one, and #billing has its own (row 38; row 47 'How many'). Each is owned by the principal resolved at creation, userId 'slack-bot' from authentication: { defaultUserId: 'slack-bot', requireUser: false }, and not by either Slack poster. The input's user field is Slack's user id, not the run's user (rows 35, 47). A browser user sees neither session unless they resolve to slack-bot in the same org. Any other identity gets 'Unknown session' (404) (row 47 'Who can see it').
5. Your ingest handler takes several seconds to process a message. Slack allows three seconds for a response. Will Slack time out, and if the handler throws, where do you find the error? *(edge case)*
   Answer: No. The route answers 202 { status: 'accepted', provider, eventType, requestId } before the block runs, so a slow block does not make Slack time out (rows 41, 42). The 202 is held only until the request is durably recorded; if recording fails it is 503 { error: 'dispatch_not_durable' } so Slack retries (row 42). An error after dispatch is not in the webhook response. It lands on the request record named by the 202's requestId and shows up in DevTool (row 48).
6. Slack sends the same message event twice after a slow response triggers a retry, and your handler writes a row for each message. How do you stop the duplicate write? *(edge case)*
   Answer: The framework surfaces a delivery id and does not de-duplicate. Providers deliver at least once, especially after a slow response triggers a retry, so a block with a side effect keys its write on deliveryId or a natural key and does nothing on a repeat (row 25). Set deliveryId: payload => payload.event_id on the host's provider definition. Slack's event id then appears on event.deliveryId and on metadata.webhook.deliveryId of the request (row 24). Separately, the verifier rejects a signed request whose timestamp is more than 300 seconds from the server clock (row 18).
