## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Someone who knows your endpoint URL, /api/flows/billing/webhooks/stripe, posts a made-up invoice.paid event for customer cus_42 with the header stripe-signature: t=9999999999,v1=deadbeef. What happens, and does the recordPayment block run? *(edge case)*
   Answer: The host's stripeWebhookVerifier refuses it, not the flow. It runs first, on the raw body bytes, before the body is parsed or any session is created. It signs '<timestamp>.<rawBody>' with HMAC-SHA256 under the secret and compares the result to the header's v1 value in constant time. The comparison fails, so the response is 401 { error: "invalid_signature" }. Nothing is dispatched, the block does not run, and no session customer-cus_42 is created. (Facts 22, 25, 26, 27, 58)
2. A real invoice.paid event for customer cus_42 arrives with a valid signature. The billing flow sets authentication { defaultUserId: "system", requireUser: false } and the binding has sessionId: (e) => `customer-${e.payload.data.object.customer}`. Which user does the run belong to, which session does it land in, and what does Stripe get back?
   Answer: The run belongs to userId "system". No resolver is configured, and the mapped input has no userId field, so defaultUserId applies. It lands in the session customer-cus_42, whose metadata records { source: "webhook", provider: "stripe" }. That session is created on the first delivery and reused for every later event from that customer. Stripe gets 202 { status: "accepted", provider, eventType, requestId } as soon as the request is durably recorded. It does not wait for the block, which runs after the response. (Facts 45, 47, 51, 54, 57, 41, 42)
3. A teammate suggests adding userId: e.payload.data.object.customer to what the binding's input returns, so each Stripe customer gets their own user. Why should the page warn against that? *(edge case)*
   Answer: With no resolver configured, the framework's default principal resolver reads userId from the object the binding's input returned. A payload field mapped into userId would let whoever sent the payload name the run's user. Leave userId out of the mapped input and let defaultUserId ("system") apply. Use sessionId to group the events by customer instead. (Fact 47; the 'sender names the user' half is flagged as inference.)
4. Stripe retries a delivery, so the same invoice.paid event (same Stripe event id) arrives twice with valid signatures. Does the framework drop the duplicate? What should recordPayment do about it? *(edge case)*
   Answer: No. The framework does not de-duplicate, and providers deliver at least once. With deliveryId: (payload) => payload.id on the provider definition, Stripe's event id shows up on event.deliveryId and on the request's metadata.webhook.deliveryId. Make the block idempotent by keying the ledger write on deliveryId or on the invoice id, so a second delivery writes nothing new. (Facts 31, 32)
5. You test locally with a hand-signed request, and Stripe also sends you events such as customer.created that have no binding. What response does each of these get: a correct signature with an invoice.paid body, a correct signature with a customer.created body, a signature whose timestamp is ten minutes old, and a request to /api/flows/billing/webhooks/strip (provider name misspelled)? *(edge case)*
   Answer: invoice.paid with a good signature: 202 accepted, and the handler runs. customer.created: 202 { status: "ignored" } with no run. That is deliberate, because providers retry any non-2xx response. Ten-minute-old timestamp: 401 invalid_signature, even though the HMAC matches, because the verifier allows at most 300 seconds of drift in either direction. Misspelled provider: 404 { error: "webhook_not_found" }, returned before verification. (Facts 23, 38, 40, 57, 59)
6. Where do the signing secret and the signature check live: in the billing flow definition or somewhere else? And how does Stripe's event type get matched to the invoice.paid binding?
   Answer: On the host. The flow carries no secret and no signature code, so it stays browser-safe. At mount, createWebhookTransportAdapter({ providers: { stripe: { verify: stripeWebhookVerifier(() => process.env.STRIPE_WEBHOOK_SECRET), eventType: (payload) => payload.type, ... } } }) goes into adapters on createFlowState. The secret getter is read lazily on the first delivery and then cached, so changing the env var later needs a restart. Stripe puts the event type in the body. eventType reads it, and the value is matched by exact string equality against the keys of webhooks.stripe.on. A key with a typo just never matches; it is not an error. The adapter throws at startup if eventType is missing while a flow declares on for that provider. (Facts 6, 14, 17, 20, 21, 29, 30)
