## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support flow's `draftReply` generator should get the `lookUpOrder` tool, the line "Quote the order number whenever you mention an order." and the `orderLog` resource. All three are bundled in the `orders` capability. What do you write on `draftReply` to get all of them, and do you also have to declare `orderLog` on `defineFlow`?
   Answer: One entry: `uses: [orders]` on the generator. In one run the model was offered `lookUpOrder`, got the context line as its own system message after the prompt and before the user message, and the block had `orderLog` (facts 19 and 11). You don't declare it on `defineFlow`. The flow collects a block's declared resources, a capability's included (fact 21).
2. You're writing `orders` and want to put the tool and the context line directly on the capability, as top-level `tools` and `context` fields next to `resources`. Where do they actually go, and what does `default` do there?
   Answer: Inside presets. A capability has no top-level `context` or `tools`; they exist only on a preset (fact 5). For example: `presets: { context: { context: "..." }, tools: { tools: [lookUpOrder] }, default: ["context", "tools"] }`. `default` lists the presets that are on unless a block says otherwise, and with no `default` every preset is on (facts 23 and 24). `resources: { orderLog }` can stay top-level (fact 5).
3. `summarizeOrder` should see the order context but never call a tool. How does it turn the tools off, what does it still get, and does the change affect `draftReply`, which lists plain `orders` in the same flow? *(edge case)*
   Answer: List `orders.with({ tools: false })` (the same switch as `.presets({ tools: false })`). The model is offered no tools but still gets the context message, and the block keeps `orderLog` (fact 25). `.with()` returns a new capability and leaves the original alone, so `draftReply` still gets `lookUpOrder`. Both blocks built in one flow without conflict, sharing the same resource (fact 27).
4. A teammate types `orders.with({ tool: false })`, with "tools" misspelled. What happens: is the preset silently left on, or does something fail, and when? *(edge case)*
   Answer: It's refused, not ignored. `.with()` throws at the call, naming the key that matches neither a preset nor a config field and listing the presets `[context, tools]`. For a capability with no config, it's also a compile error. `.presets({ tool: false })` throws when the block is built with `Unknown preset "tool"` (fact 28).
5. You turn `orders` into `createOrdersCapability({ scope })` so a deployment can pick between `"session"` and `"user"`. Why a factory and not a preset? And if `draftReply` and `summarizeOrder` each call `createOrdersCapability({ scope: "session" })` in their own file, what happens when the flow is built? *(edge case)*
   Answer: A preset can only switch parts the capability already declares. It can't pick a resource's scope, because scope is set on `defineResource`. So the factory builds the resource (and the tool that declares it) from its argument; `{ scope: "user" }` gave a capability named `orders:user` whose `orderLog` was user-scoped (facts 33 and 34). With two separate calls, each makes its own `orderLog` object, and building the flow throws `Resource conflict` (different `defineResource()` references under one key). Call the factory once, `export const orders = createOrdersCapability({ scope: "session" })`, and import that everywhere (fact 36). The name carries the scope (`orders:${scope}`) because two different capability calls with the same name in one block throw `Capability name collision` (fact 35).
6. A customer asks about order A1 in one session, then comes back in a new session the next day. With `scope: "session"`, does the new session's `lastOrderId` still read "A1"? What changes with `scope: "user"`? And where is `orderLog` kept if you set no store? *(edge case)*
   Answer: With `"session"`, no. There is one record per session and each new session starts fresh, with `lastOrderId` reading `null` until the tool writes it (facts 46 and 16). With `"user"`, the order log follows the customer between sessions: one record per user per organization (fact 46). The capability itself stores nothing. The resource lives in the flow's store, which is in memory by default and lost on restart, unless you use a file, SQLite or Postgres store (facts 45 and 43).

## Reference rows

- Context and tools presets are valid only on generators; listing a capability that brings either on any other block kind throws at build. → R-10
- Context slot forms: a string, or a function returning one, in the array form is its own system message, emitted in author order after the combined prompt message and before history and the user message. An object-form context is not a separate message: its keys render as XML tags inside the one combined prompt+context system message, and contributions to the same key from the generator and from capabilities aggregate inside one tag. → R-10 (corrected by pass 5)
- Precedence: a generator's own `tools:` list is not merged with a capability's tools preset; list the wanted tools there. → R-10
- Turning presets off: `.with({ preset: false })` and `.presets({ preset: false })` are equivalent, return a new reference and leave the original unchanged; an unknown preset name throws. → R-10
- Where resource data is kept: the flow's store; default memory, with file, SQLite and Postgres stores that survive a restart. → R-16
- Name collisions: two different capabilities sharing a name in one block throw; two resource definitions of one name in a flow throw a resource conflict, so a factory result is built once and imported. → R-10
- Open config: `.config()` values for non-resource settings, their shape and merge rules. → R-10
