## Step 1: the plan, drain, reduce skeleton

7. **Every board pattern is the same four moves against one list of tasks: plan, seed, drain, reduce.** `pm:3-8` (header comment) lists `plan the work → seed the collection → drain via board.drain → reduce`; the built-in patterns follow it (`pm:3-5`). **[page; answers Q1's context]**
8. **A pattern is a function that returns a block.** `planMapReduce` returns `BlockDefinition` (`pm:45-47`); `parallelTasks` returns `SequencerDefinition<any, any>` (`par:90-92`); `supervisor` the same (`sup:272-274`). The value is built with `sequencer({ name, inputSchema }).step(...)` (`pm:103-107`). The caller mounts it "like any other block", never sees the board (`pm:41-44`). **[page; answers Q1: a pattern returns a block, a sequencer of its steps]**
9. **The returned block mounts as an action, or as a step in another sequencer.** As an action: `defineFlow({ kind, actions: { count: { block: wordCountBlock } }, session: { stateSchema: z.object({}) } })` (`wf:162-169`). As a step: the `parallelTasks` test mounts the returned block as a sequencer named `inner-pt` and asserts `block.kind === "sequencer"` and `block.name === "inner-pt"` (`pat:259-279`) **[test]**. `testBlock` runs the returned block directly with `{ input }` and gives `output`, `error` (`pat:198-230`; `tbk:83-90`). **[page]**
10. **`plan` is a block, not a function, so a model can do the planning.** `pm:9-13`, `pm:30-34` (the `plan` option is a `BlockDefinition`, "usually a generator", whose output must match `planOutputSchema`). A handler works too; the example uses one so the tests need no key (`pm:12-13`, `wf:122-124`). **[page: one sentence on why the config takes a block]**
11. **The plan block's output shape is `{ items: [{ id: string, input: unknown }] }`.** `planOutputSchema` (`pm:21-23`), exported (`pm:21`). The seed block takes it as its `inputSchema` (`pm:63`). **[page]**
12. **Each step's output is the next step's input.** `plan` → `seed` (`{ items }`), `seed` → `drain` (`{ seeded: number }`, `pm:64`), `drain` → `reduce` (ignored, fact 17). `pm:60`, `pm:102-107`. A mismatch is not caught by the types: `step(block)` takes `BlockDefinition<any, ...>` (`packages/core/src/blocks/sequencer-methods.ts:163-166`, cited on `debug-a-run.facts.md` fact 10) and fails when it runs. **[page, in a clause; links to the Blocks concept for connectors]**
13. **The `map` block is the block that does one task.** `workers: { map: config.map }` (`pm:55-56`): one assignee, `"map"`, staffed by the caller's block; seed files each task with `assignee: "map"` (`pm:72-77`). The option is spelled `workers` (`tb:377`); the revamp's wording is "the block that does the task" (`docs/contributing/user-docs.md`, "Words"). **[page; word choice]**
14. **The `map` block's input is the task, not the item.** It receives `taskWorkerInputSchema`'s shape: `taskId`, `goal`, optional `input` (the item's `input`), `deps`, `attempts`, `feedback`, and more (`wt:39-90`, `wt:131-140`). The example extends it with a typed `input` (`wf:137-140`): `taskWorkerInputSchema.extend({ input: z.object({ text: z.string() }).optional() })`, imported from `@flow-state-dev/orchestration/task-board` (`wf:116`). **[page; the full field list is [ref] `reference/task-collections`]**
15. **The seed writes one task per planned item.** `collection.createTask({ id: item.id, goal: item.id, assignee: "map", input: item.input })` for each item, then returns `{ seeded: input.items.length }` (`pm:71-79`). A task needs a `goal` string; the example reuses the id (`pm:74`). **[page]**
16. **The drain is `board.drain`**, the board's composed sequencer, "plug into a parent flow or sequencer" (`tb:584`; `tbd` "Basic usage": "`board.drain` plugs into a parent sequencer as a normal step"). It runs the claimed tasks across a pool of workers and returns when the board stops: every task completed, or nothing left can run (`tb:46-58`, `tbd` intro). Worker count defaults to 4 (`tb:402`, `tb:687`); the example sets `concurrency: 8` (`pm:53`). **[page; stop rules are [ref]]**
17. **`reduce` reads the finished tasks, not its input.** `reduce` takes `z.unknown()`, ignores `_input`, resolves the collection and reads `list({ status: "completed" })`, mapping to `task.output`, then returns `config.reduce(outputs)` (`pm:85-99`). The comment says so: "it reads the collection through `ctx`, so it ignores whatever input it's handed" (`pm:83-84`). A task's `output` is what its block returned **[run]**: `{ count }` objects arrive in `reduce`. **[page]**
18. **A task that fails is left out of the result, and the run still completes.** The board's default `onError` is `"skip"`: the error is recorded on the failing task and siblings continue (`tb:491-503`, `tb:691`). `reduce` lists only `completed` tasks, so a failed one is absent from `outputs` (`pm:95-97`). Observed with a `map` block that throws on one item of three: `testBlock` returns `error: null` and an `outputs` array of length 2 **[scratch]**; `par:113-120` and `pat:198-230` pin the same default for `parallelTasks` (`onSubTaskError: "skip"`, "skips failed sub-tasks", `error` is `null`) **[test]**. `onError: "fail"` makes a failure abort the drain (`tb:497-499`; `pat:232-255`, `error` is not `null`) **[test]**. **[page: one sentence, because a reader's `reduce` silently sees fewer outputs than items. Passing `onError` through is a design option; the example does not.]**
19. **An empty plan is fine.** `{ documents: [] }` gives `{ total: 0 }` (`pt:19-34`) **[test]**.

## Step 2: wrap it in a factory

20. **Why a factory: one config, many instances, and the wiring lives in one place.** `planMapReduce(config)` builds the board and the blocks around it from `name`, `inputSchema`, `plan`, `map`, `reduce` (`pm:25-39`, `pm:45-108`). The `name` is the board's name and the collection's id (`pm:48`, `pm:51-52`) and prefixes the seed and reduce block names (`pm:62`, `pm:86`), so two instances in one flow need different `name`s (`tb:303-306`: "must be globally unique inside a flow if you have multiple boards"). `g:25-31` says the value of writing a pattern is "the wiring lives in one place and every caller gets it right". **[page; answers Q2. The reader-facing reason is: the board, its collection and its helper blocks are built once per call from the config, so each caller gets its own.]**
21. **The config the factory takes.** `PlanMapReduceConfig<TResult>`: `name: string`, `inputSchema: ZodTypeAny` ("schema of the flow input this pattern is mounted against"), `plan: BlockDefinition`, `map: BlockDefinition` ("its output is what `reduce` sees"), `reduce: (outputs: unknown[]) => TResult` ("fold the completed workers' outputs into the final result. Pure.") (`pm:25-39`). **[page]**
22. **The factory builds the board once, then the blocks that use it.** `taskBoard({ name, collection: { collectionId }, concurrency, claimOrder, workers: { map }, initialTasks: [] })` (`pm:50-58`); `initialTasks: []` is the default (`tb:488-489`), so a plan-seeded board can omit it. `taskBoard` is imported from `@flow-state-dev/orchestration/task-board` (`pm:15`). **[page]**
23. **Use the board's capability to write and read its tasks, in place of resolving the collection twice.** `taskBoard` returns `capability` (`tb:606`), "the whole consumer surface for a board's tasks" (`cap:2-4`): add it to a block's `uses` and call `ctx.cap[board.capability.name]` with `createTask`, `createTasks`, `getTask`, `listTasks`, `countTasks` and `tasks()` (`cap:160-175`). The capability's name is the board's name verbatim (`tb:595-600`, `cap:23-26`); hyphenated names need bracket access, which is why the code reads `ctx.cap[board.capability.name]`. The built-in `parallelTasks` does exactly this: `uses: [board.capability]`, `ctx.cap[board.capability.name].listTasks({ status: "completed" })` (`par:157-171`). The example (`pm:66-70`, `pm:90-94`) calls `getOrCreateTaskCollection` with a `collectionId` that must match the board's, which is how the example's two copies can drift; the capability has one config (`cap:13-18`). **[page; this is the shape the page shows. A [scratch] run of the rewritten factory is below.]**
24. **The rewritten factory, run.** In a throwaway file in `ex/src` (deleted afterwards): `taskBoard({ name: \`${config.name}-board\`, workers: { map: config.map } })`; `seed` = `handler({ name, inputSchema: planOutputSchema, outputSchema: z.object({ seeded: z.number() }), uses: [board.capability], execute: async (input, ctx) => { await ctx.cap[board.capability.name].createTasks(input.items.map((item) => ({ id: item.id, goal: item.id, assignee: "map", input: item.input }))); return { seeded: input.items.length }; } })`; `reduce` = `handler({ ..., uses: [board.capability], execute: async (_input, ctx) => { const done = await ctx.cap[board.capability.name].listTasks({ status: "completed" }); return config.reduce(done.map((t) => t.output)); } })`; the sequencer steps are `.step(config.plan).step(seed).step(board.drain).step(reduce)`. **[scratch]** `pnpm tsc --noEmit` passed and a `testBlock` run of two documents returned the two `{ count }` outputs, and with one failing item returned the other two, `error: null`. `createTasks` exists on the accessor (`cap:164`). **[verify: re-run this at pass 4; the page's code is the page's responsibility.]**
25. **The types.** `handler`, `sequencer`, `BlockDefinition` come from `@flow-state-dev/core` (`pm:14`); `UsesSlot` from `@flow-state-dev/core` too (`packages/core/src/index.ts:176`); `z`, `ZodTypeAny` from `zod` (`pm:18`); `ex/package.json` depends on `@flow-state-dev/core`, `engine`, `orchestration` and `zod` (`ex/package.json:13-18`). **[page, via the imports]**
26. **Where the file goes.** The standard's layout puts one block per file under `src/flows/<flow>/blocks/` and helpers under `src/lib/` (`docs/contributing/user-docs.md`, "Code examples"). A pattern factory is neither a block nor flow-only; **[open: the writer picks `src/lib/plan-map-reduce.ts` and says one clause why, or flags the layout for the owner at pass 10.]**

## Step 3: accept `uses`

27. **`uses` is a slot every block accepts.** `handler` (`packages/core/src/blocks/handler.ts:107-109`), `generator` (`packages/core/src/blocks/generator.ts:566-569`) and `sequencer` (`packages/core/src/blocks/sequencer-methods.ts:496-498`, `uses?: readonly UsesEntry[]`) take `uses`, "capabilities to install", which merge a capability's resources, state, tools and context into the block. **[page, one sentence; the concept is its own page]**
28. **A `UsesSlot` is a readonly array of capabilities and functions.** `UsesEntry = CapabilityRef | ((ctx: BlockContext) => readonly CapabilityRef[])`; `UsesSlot = readonly UsesEntry[]` (`uc:601-607`). Dynamic entries contribute context, tools and control tools only; resources must be declared statically (`uc:597-600`). **[page, one clause; the rest is [ref]]**
29. **Built-in patterns forward a `uses` option to the blocks they build.** `uses?: UsesSlot` on the config; the factory spreads it onto each default generator it builds: `...(config.uses ? { uses: config.uses as any } : {})` (`pae:279`, `pae:575`; `sup:163`, `sup:232`), and passes it on where a default is built (`pae:671`, `pae:684`; `sup:326`). `supervisor`'s docs list `uses?: UsesSlot` in its config (`apps/docs/docs/patterns/supervisor.md:239`) and `planAndExecute`'s comment says "Capabilities to install on default blocks" (`pae:237-238`). **[page: this is what "accept `uses`" means for a pattern: it is the way a caller adds tools and context to the blocks the pattern builds for them.]**

## The four questions for what a pattern stores

A pattern that wraps `taskBoard` stores its tasks; the sheet answers for them. The answers hold for the page's example (default request backing). They are the answers C-21 gives for the board; the page states one clause and links.

37. **Who owns it.** The board built inside the factory: its collection id is `config.name` (`pm:48`, `pm:51-52`; `tb:337-345` default `collectionId` is the board `name`). The caller of the pattern never touches it (`pm:41-44`). Each task is created by the running session's user: `createdBy` is `ctx.session?.identity?.userId` (`goc:163`). **[page, only if it says "per call to the pattern"]**
38. **Who can see it.** Every lifecycle change of a task is sent to the client as a `task-change` item that carries the whole task, minus server-only fields (`goc:188-205`, server-only fields omitted at `:194`). So a client that reads the stream sees the tasks, including each task's `input` and `output`. **[page, one sentence: the tasks are visible to the client that started the request, since the progress view reads them. Redaction of server-only fields is [ref].]**
39. **Where it is stored.** On the request, under the board's `collectionId` in the request's state (`tb:247-265`, `goc:60-70`: "tasks live on the request ... at `[stateKey]`, default the `collectionId`"). The list lasts as long as the request and ends with it: "for cross-request boards use `backing: \"resource\"`" (`goc:68-70`). **[page: one clause. Keeping the list across requests means the board takes a `DefinedTaskCollection` (`defineTaskCollection`) as `collection`, which the pattern would have to expose as a config option; the example does not. See C-21's "How long the list lasts".]**
40. **How many exist.** One per item the plan block returns, bounded by the board's creation limits (500 tasks in total, 100 added while others are still pending, by default) when the seed writes through the board's capability (facts 4, 23). The number of workers running at once is `concurrency`, default 4 (`tb:402`, `tb:687`). **[ref for the limits; the page says "one task per item".]**

## Limits and where a reader would assume otherwise

41. **The pattern runs one drain.** The example's pipeline plans once, seeds once, drains once and reduces once (`pm:102-107`). It does not loop, replan, or review. `parallelTasks` is the closest built-in: single pass, "no feedback loop" (`par:5-7`); `supervisor` adds review and retries; `planAndExecute` adds replanning (`po:52-60`; `tbd` "When to use a task board"). Looping the drain is `goalSeekLoop` (`par:9-13`; `tb:198`; `apps/docs/docs/orchestration/goal-seek-loop.md`). **[page: one sentence in a closing "when you want more" pointer; links to K-19.]**
42. **The task limits and the retry budget are the board's, and the page does not pass them through.** The built-in patterns forward `maxTotalTasks`, `maxEnqueuedTasks` and `maxTotalRetries` (`par:36-63`). The example's config has no such options. A reader who needs more than 100 items in one burst must add them to the config and pass them to `taskBoard` (`tb:407-452`). **[page: one clause; the numbers are [ref] `reference/task-board`.]**
43. **Reduce only sees what the block returned.** `outputs` are `task.output` values with no task ids; if the fold needs to know which item a result belongs to, the `map` block returns the id in its output (`pm:95-97`). **[page: only if the example needs it. It does not.]**
