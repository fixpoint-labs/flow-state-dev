## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are writing `planMapReduce` so the support desk can work through a batch of tickets, one task per ticket. What does `planMapReduce(config)` hand back, and how does the support-desk flow put it to use?
   Answer: It returns a block: a sequencer built with `sequencer({ name, inputSchema })` whose steps are the plan block, a seed block that writes one task per planned item, `board.drain`, and a reduce block. Every board pattern makes these same four moves against one list of tasks. The flow mounts that block like any other block, either as an action (`actions: { <action>: { block } }`) or as a step inside another sequencer. The caller never sees the board inside it. (Facts 7, 8, 9, 12, 15, 16)
2. The desk wants two of these in the same flow, one that triages a batch of new tickets and one that summarizes a batch of closed ones. Why is `planMapReduce` a factory and not a single shared block, and what must differ between the two calls?
   Answer: Each call builds its own board, the board's task collection and the helper blocks (seed, reduce) from the config. The wiring lives in one place, and every caller gets its own correctly wired copy. The config's `name` names the board (as `${name}-board`), sets the collection's id and prefixes the helper blocks' names. Names must be unique inside a flow when it has more than one board, so the two calls need different `name`s. (Facts 5, 20, 21, 22)
3. The `map` block that handles one ticket throws on ticket 7 of a batch of 20. Does the run fail? What does `reduce` receive, and how would you make one failure stop the whole batch? *(edge case)*
   Answer: The run still completes. The board's default `onError` is "skip": the error is recorded on the failed task and the other tasks carry on. `reduce` reads only the completed tasks (`listTasks({ status: "completed" })`), so it gets 19 outputs, not 20, and the failed ticket is silently missing from them. `testBlock` reports `error: null`. Setting the board's `onError: "fail"` makes a failure abort the drain, and the error then comes back non-null. The example does not pass `onError` through its config, so offering that option is your design call. (Facts 17, 18)
4. The plan block finds no open tickets this run and returns `{ items: [] }`. What happens? *(edge case)*
   Answer: Nothing breaks. The seed writes no tasks, the drain has nothing to run and stops, and `reduce` folds an empty list of outputs. In the example, an empty input gives `{ total: 0 }`, and a test pins it. (Facts 15, 16, 19)
5. A teammate swaps the deterministic `plan` handler for a generator that needs a ticket-lookup tool. Should `planMapReduce` accept and forward a `uses` option to make that work? Where does the capability go? *(edge case)*
   Answer: No forwarding is needed for that. `plan` and `map` are blocks the caller supplies, so the teammate puts `uses` on the generator they pass as `plan`, as every block accepts a `uses` slot. A pattern accepts `uses?: UsesSlot` for the blocks it builds itself: the built-ins (`supervisor`, `planAndExecute`) spread it onto the default generators they create. In `planMapReduce`, the only blocks the factory builds are the seed and reduce handlers, which already carry `uses: [board.capability]`. A `uses` option there would install extra capabilities on those two handlers, beside the board's capability. (Facts 27, 28, 29, 30, 31)
6. How do you test the pattern without a model API key, and what does a passing result look like?
   Answer: Keep `plan` and `map` deterministic handlers, which need no key, or, with generators, mock them by passing `generators: { "<block name>": { output } }` to `testFlow` (or use `mockGenerator`). Run the flow with `testFlow({ flow, action, userId, input })` from `@flow-state-dev/testing`. A pass has `status` "completed", `error` undefined and `output` equal to the reduced result. To test the block on its own without a flow, use `testBlock(block, { input })`, whose `error` is `null` on success. (Facts 32, 33, 34)
