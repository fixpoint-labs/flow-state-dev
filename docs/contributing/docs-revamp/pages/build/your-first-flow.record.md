## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You want the hello-chat assistant to answer like a pirate instead of 'concise, friendly'. Which file do you open, and what do you change in it?
   Answer: blocks/chat-generator.ts (src/flows/hello-chat/blocks/chat-generator.ts). Change the generator's `prompt`, the system instruction sent first on every model call ("You are a concise, friendly assistant."). Facts section 2 (Q1 line, core/blocks/generator.ts:608) and section 3 (prompt is the system instruction, a string here).
2. You run `pnpm fsdev run hello-chat chat -i '{"message":"Hello"}'` and the reply looks right. What can the terminal output tell you that the chat page in the browser never shows?
   Answer: Stdout is NDJSON events. The generator's trace carries a `generator` patch listing exactly what the model was sent: `model`, `prompt`, `tools`, `user` and `history` as role/content messages. There is a `block_trace` per block (chat-pipeline, clean-message, chat-generator, count-message) with kind, status and input/output; the `state_change` item for the count (scope `session`, operation, delta, version); and `flow_complete` with the output text, `durationMs` and item count. Stderr carries runtime logs, such as the `running as devuser` line. Facts section 4, 'What fsdev run shows that the page does not'.
3. A user sends one message, then a second one a minute later, and the page shows 'Messages sent: 2'. Between those two messages, where was the number 1 kept, and how did the browser get to see it?
   Answer: It is session state: `messageCount` sits on the session record in the app's store. The flow's `session.stateSchema` gives it a default of 0, and `countMessage` updates it on each run. Session state is private unless the flow lists it in `session.client.expose`, so the browser reads it from the session snapshot's `clientData` only because `messageCount` is exposed (read with `useClientData`). Facts section 5 (Q3 line, the storage table, the expose line).
4. Your test calls `testFlow` on the `chat` action and expects the reply 'Hi there!' without any API key or network. What answers in place of the real model, and how does the test tie it to the right block?
   Answer: A scripted generator from `mockGenerator({ name: "chat-generator", script: [{ text: "Hi there!" }] })`. Each call takes the next script entry, and `{ text }` is the reply. It goes into `testFlow` under `generators`, keyed by the generator block's `name`, `"chat-generator"`. `testFlow` runs in-process against in-memory stores, with no server, network or key. Facts section 8 (Q4 line, testFlow line).
5. A teammate edits the test and keys the mock as `generators: { chat: mock }`, after the action name. What happens when the test runs, and how does it show up? *(edge case)*
   Answer: The run fails but `testFlow` does not throw. `result.status` is `"failed"` and `error.message` reads `No mock for generator "chat-generator" / model "openai/gpt-6-luna". Provide generators["chat-generator"] ...`. The key has to be the generator block's name, not the action's. A wrong key produces the same error as having no mock at all. Facts section 8, failure shapes (first bullet) and the result line ('does not throw when the run fails').
6. While the first user's conversation has a count of 2, a second conversation (a new session) sends its first message. What count does that new session show, and does the model see any of the first conversation's messages? *(edge case)*
   Answer: It shows 1. Each session has its own `messageCount`, starting from the schema default of 0. The new session's model call carries none of the first session's turns, because `history: true` reads only that session's items. Observed: two runs on session s1 left `{messageCount: 2}`, and a run on s2 in the same store held `{messageCount: 1}` with no s1 turns in its model call. Facts section 5 (Q3 run note, 'one per session' in the table) and section 3 (`history: true` loads the session's earlier turns).

- What a run streams: per-block trace events, the generator trace update (model, prompt, history, user message), `state_change` items, duration on `flow_complete`. Plus the exit code 1 and the `error` event text when no provider key is set. → R-06
- `fsdev run` flags: the default user is the one the app's resolver returns, or `devuser` when the app has no resolver (or when `--org` is passed); `-u` user, `-s` session id, `-i` input, `--quiet`. → R-35 (corrected by pass 5)
- Default store per entry point: the CLI uses SQLite at `.fsdev/data/fsdev.db` with no config; a served app uses the in-memory profile until a store is configured, and in-memory state is lost on restart. The page keeps a short warning that the count is lost on restart and links to the row. → R-12
