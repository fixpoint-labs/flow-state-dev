## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You install `claudeCode()` in the `acme-shop` app's `kits` so the `engineering.coder` worker can run on `harness: claude-code`. Which credentials can a run use, and how do you find out before any task starts whether this machine has one?
   Answer: A run can use an `ANTHROPIC_API_KEY`, a `CLAUDE_CODE_OAUTH_TOKEN`, or a `claude` sign-in (a file under the home folder, or the keychain on macOS). These two variable names are the only credentials on the run's pass-list (items 22, 25). On the kit path the check is already wired: the `harnesses` kit's flow serves a `readiness` view with one row per harness. The Claude Code row has `harness: "claude-code"`, `label: "Claude Code"`, `ready`, `reason`, `remedy`, `unanswered` and `checkedAt`. `logReadiness: true` checks once at start and logs a table without stopping the app (items 33, 34). The check asks Claude Code itself, with no model turn. It reports where a credential would come from, not whether it works (items 26, 30).
2. Nobody on the server has run `claude` to sign in or set an API key, and someone gives `engineering.coder` a task. What happens to the task? *(edge case)*
   Answer: The task is refused at once with the reason and the remedy. It never moves to another harness. The sentence reads like "Claude Code isn't set up on this machine: <reason>. Sign in with `claude`, or set ANTHROPIC_API_KEY. Then start the task again." A harness that is not ready gets a fresh check at each task start, so signing in and starting the task again works without a restart. The app itself keeps running, because a missing sign-in never stops it (items 25, 31, 34, 35).
3. You run `tidyImports` (`claudeCodeAgent()`, stepped with `{ prompt: "Tidy the imports in src/." }`) in your own flow. How do you check for a credential in code before you run it, and why does it matter which `env` you pass?
   Answer: Build the run's environment with `harnessEnv({ pass: CLAUDE_CODE_PASS })` (imported from `@flow-state-dev/core/harness`) and call `probeClaudeCodeAccount({ env })` from `@flow-state-dev/claude-code`. It never throws. It returns `status: "account"`, `"none"` (with a `reason`) or `"sdk-missing"`. `checkClaudeCodeReadiness({ env })` gives the same answer as `{ ready: true }` or `{ ready: false, reason, remedy }`. Pass the same `env` the run gets, so a credential the run can't see isn't counted. A key that is set but rejected still reads as `account`, and the failure shows up on the run's first turn (items 27, 29-32).
4. Yesterday `engineering.coder` worked a task and asked a question. Today you answer it. And separately, `tidyImports` ran in a user's session yesterday and the user sends another request in that same session today. How does each one continue the earlier Claude Code session?
   Answer: Kit path: you do nothing. The harness manager supplies `resume` and records the session the agent confirmed. An answer, a retry, a steering line or an "ask for changes" each resume the same coding session (item 54). In-session block path (the default): the block saved `sdkSessionId` in session state and hands it to Claude Code as `resume` on the next request in that session. Same session, same id, on any day, for as long as the app's store keeps the session (items 57, 58). If you build the block with `detached: true`, nothing goes into session state. You pass `resume: (ctx) => id` yourself and capture the id with `onSession: (id, ctx) => ...`, which fires during the run (items 59, 60).
5. Today's resume points at a session Claude Code no longer has, or a run is stopped part-way through. What happens in each case, and where do you get the id to continue from? *(edge case)*
   Answer: On the kit path, if the agent can't find the session it was asked to continue, the next run starts a fresh session with the brief, the question and the answer in its prompt. The manager only records sessions the harness confirmed (item 55). The block marks this failure as `harnessFailure: "unknown-conversation"` on `ClaudeCodeAgentRunError`. A stopped run throws `ClaudeCodeAgentAbortedError` and returns no handle. Its `sessionId` names the session to resume, or is `null` if Claude Code hadn't named one yet. With `onSession`, the host already received the id during the run (items 51, 52, 60). On the kit, a line typed into a running task stops the run and resumes its session with that line (item 42).
6. While `tidyImports` or `engineering.coder` works, what shows up in the stream, and how can you tell afterwards whether it finished, hit a limit or failed? *(edge case)*
   Answer: Claude Code's stream is translated into flow items as it runs. Assistant text arrives as a `message` item, streamed token by token. Thinking becomes a `reasoning` item. Each tool call becomes a `tool_output` item, with a transient status while it runs (a `Bash` call's description, otherwise "Using <tool>..."). A sub-agent becomes a `container` item. Errors become an `error` item. Transient statuses also cover the start ("Starting Claude Code..."), API retries and compaction. At the end a kept status says "Claude Code agent run completed in ..." or "... errored (<reason>)." (items 65, 66). The handle's `outcome` is `finished`, `stopped-at-limit` (max turns or budget) or `failed`. A limited or failed run is an outcome with `status: "errored"` and an `error` item, not a throw. The handle also carries `sessionId`, `resultSubtype` and `toolsObserved` (items 46, 48-50). File operations and pull requests go into collections, not items (item 72).
