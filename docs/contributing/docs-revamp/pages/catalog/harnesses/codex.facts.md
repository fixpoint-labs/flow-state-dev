## What it is

7. **`@flow-state-dev/codex` runs OpenAI's Codex agent as a block.** You hand it a prompt, point it at a directory, and get back the framework's neutral harness handle; it is the same shape the Claude Code package returns, so a caller that reads the handle can drive either. `readme:3-6`; `page:7-11`; `cx/index.ts:1-11`. **[page]**
8. **The block spawns the Codex CLI through the Codex SDK and streams its JSONL back.** `cx/agent.ts:2-4` ("spawns `codex exec --experimental-json`"); `page:19-22` ("spawns the Codex CLI in a subprocess"). The block runs one turn per call and returns. `cx/agent.ts:5-9`; `page:341`. **[page: one sentence]**
9. **Codex owns its own loop.** The framework does not drive it step by step or re-implement its tools. `page:19-20`. **[page: one sentence]**
10. **A harness is "a coding agent driven as a block": a prompt in, its own agentic loop in a directory, a handle out.** `ca:8-11`; `cx/index.ts:5-11`. **[page: as the one-line definition, if the page needs one; the concept lives on the coding-agents page]**

## As a step (the block)

35. **`codexAgent(options)` builds the block; it is a handler.** `cx/agent.ts:233`; exported `cx/index.ts:14`. Its input schema is core's `harnessRunInputSchema` and its output is `codexAgentHandleSchema`. `cx/agent.ts:288-289`. **[page]**
36. **A sequencer steps it.** The existing page's example: `sequencer({ name: "do-the-work" }).step(codexAgent({ cwd, resume, onSession, model, thread: { sandboxMode: "workspace-write", approvalPolicy: "never" } }), { abortSignal: () => AbortSignal.timeout(runTimeoutMs) })`. `page:70-86`; `ca:19-27` (swap `claudeCodeAgent` for `codexAgent` and the step is unchanged, `ca:28-29`). 37. **The block's input is the prompt and nothing else.** `harnessRunInputSchema` is the input; the block throws on an empty prompt before anything spawns (`cx/agent.ts:294-296`, `cxt/agent.spec.ts:570`). Where a run writes, which conversation it continues and which model it runs are configuration, because the same block can be handed to a model as a tool, and a field on the input is a field the model could set. `readme:57-61`; `page:90-93`; `cx/agent.ts:2-14`. The resolvers are given the block context and never the prompt. `readme:61-62`; `cx/agent.ts:319-323`. **[page: the rule and the reason in one sentence; "the prompt is the input; everything else is configuration" is the section at `ca:559`]**
38. **`cwd`: where the run works.** A resolver called once per run, before anything spawns; its answer becomes the thread's working directory. `cx/agent.ts:96-104`. **Omit it and the run works in the host process's own directory, which is almost never what a host wants.** `cx/agent.ts:100-104`. It is a working directory, not a fence: the run can still address paths outside it; `sandboxMode` on `thread` is the fence. `page:100-102`; `ca:596-612` (section "A working directory is not a fence"). **[page: first clause on omitting; the fence statement is a limit to keep as one sentence]**
39. **`model`: a fixed id, or a resolver called once per run**, so one block can run a different model per session; a resumed thread is handed it too. `null`, `""` and `undefined` mean no model named, and Codex runs its own default. Setting `model` and `thread.model` together is refused when the block is built (`CodexAgentConfigError`). `cx/agent.ts:134-143`, `cx/agent.ts:325`; `readme:52-56`; `cxt/agent.spec.ts:778-816`. Codex's SDK can't list models, so the ids are the host's to supply (`readme:55-56`); `listCodexModels` (below) gives a list from the signed-in Codex. These are Codex's ids, not framework model ids. `page:60-61` (example comment). **[page: one example line and the "ids are Codex's own" note; [contradiction between `readme:55-56` "can't list models" and `readme:203-217` `listCodexModels`: both are true. The SDK can't list them; Codex's app-server can. State only the second.]]**
