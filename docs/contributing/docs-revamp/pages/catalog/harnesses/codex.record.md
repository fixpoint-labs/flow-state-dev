## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your app already lists workforce and the harness kit, and the desk team has a new worker, coder-codex, that should change the code in the session's project through Codex. What do you install, what do you put in the kit's slot, and what does the worker's WORKER.md say?
   Answer: Install `@flow-state-dev/codex` with the exact-pinned peer `@openai/codex-sdk@0.164.0`; the SDK brings the `codex` binary (facts 12, 14). Codex is a plain value, not a kit: put `codexHarness()` in the harness kit's `harnesses` slot (`fill: { [harnesses.slots.harnesses]: [codexHarness(), ...] }`), beside workforce and the harnesses kit in `kits` (facts 2, 17, 19). The worker's WORKER.md says `flow: coder` and `harness: codex`, since the slot names its harnesses by id and Codex's id is "codex" (facts 6, 21).
2. Once coder-codex picks up a task, what can that Codex run see and change by default: which environment variables does it start with, and how far can it write?
   Answer: A run through `codexHarness()` gets only Codex's own environment (`harnessEnv({ pass: CODEX_PASS })`). A server secret not on that list is left out, and the `client.env` option is always replaced with Codex's own (fact 27). It works in the `workspace-write` sandbox unless your `thread` options set another `sandboxMode` (fact 30). The filter covers what the run starts with, not what it can read.
3. Outside the harness kit, you want one step of a sequencer to hand Codex a prompt and continue the same Codex conversation on every later call for that session. What do you write, and what is the block's input?
   Answer: Step `codexAgent({ cwd, resume, onSession, model, thread: { sandboxMode, approvalPolicy } })` in the sequencer (facts 35, 36). The input is the prompt and nothing else. Directory, model and conversation are configuration, because the block can be handed to a model as a tool, and a field on the input is one the model could set (fact 37). Continuing is two halves you write. `resume` reads the stored thread id (null, "" or undefined starts a fresh thread). `onSession` is called once with the thread id the moment the run names it, and you store it. The handle's `sessionId` is that thread id (facts 60, 61). If you leave out `cwd`, the run works in the host process's own directory (fact 38).
4. The machine the app runs on was never signed in to Codex, and coder-codex is given a task. What happens to the task, and what does the harness's readiness check tell you to do? *(edge case)*
   Answer: The task fails at once, saying why. It never moves to another harness (fact 24). Readiness reads `{ ready: false, reason: "Codex has no credential: ...", remedy: "Run `codex login`, or set CODEX_API_KEY" }`. A missing sign-in never stops the app from starting (facts 25, 26). Readiness only checks where a credential would come from, not whether it works: a rejected key still reads ready (fact 26).
5. A run hits its step deadline halfway through. Then, on a different day, `resume` hands Codex a thread id that Codex no longer has. What does the caller get back in each case, and what happens to the stored thread id? *(edge case)*
   Answer: Deadline: the block throws (`CodexAgentAbortedError`) and returns no handle. `onSession` already fired on `thread.started`, before any work, so the thread id is stored and the run can be continued (facts 53, 62). The deadline bounds Codex, not a command Codex started; the sandbox bounds that (fact 53). Refused resume: the CLI names no thread, so `onSession` never fires and your stored id is left untouched. The run fails with a `CodexAgentRunError` that `harnessFailureKind(error)` reports as "unknown-conversation" (fact 63). In the harness kit, the next attempt after a refusal asks for a fresh thread rather than retrying the same id (fact 65).
6. A teammate edits coder-codex's WORKER.md to say `harness: cursor`, but the app only fills the slot with `codexHarness()`. Separately, the model fails a Codex turn. What does each look like? *(edge case)*
   Answer: A worker that names a harness nobody filled is refused when the app starts, and the error names the harness (fact 23). A turn the model fails is not a throw. It comes back as a handle with `status: "errored"`, `outcome: "failed"` and the message on `failureMessage`. The stream ends with one `error` item, and nothing retries (facts 46, 49). The block throws only when the run ends without a turn result (fact 46).
