## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are about to move the lab's worker `desk.coder-cursor` onto a new server. Which credential does Cursor need there, how can you tell it is signed in without starting a run, and what happens to a coding task if it is not?
   Answer: Cursor needs `CURSOR_API_KEY` in the run's environment (or `agent.apiKey`), or a stored login that `Cursor.auth.login()` saved after a browser sign-in (facts 17, 20). `cursorSignIn(env)` answers with no run: `{ status: "key" }`, `{ status: "login" }` or `{ status: "none", reason }` (fact 18); keep `HOME` the same for the check and the run, since the stored login is looked up under it (fact 20). On the harness path you need not call it yourself: the harness slot runs `checkCursorReadiness` against the environment the run will get before each coding task, and the harness kit's `readiness` view has a row for `cursor`. A worker naming a harness that cannot run fails at once with the reason and the remedy ("Set CURSOR_API_KEY, or sign in to Cursor"), and never falls back to another agent (facts 21-23).
2. Yesterday a step running `cursorAgent` did some work in a repository. Today you want the next prompt to continue that same conversation rather than start fresh. What do you write, and where does the id live?
   Answer: Cursor calls the durable conversation an agent, and each prompt is one run inside it; the handle's `sessionId` is that agent id (fact 55). You write both halves: `onSession(id, ctx)` stores the id when the SDK opens the agent, before the prompt is sent, and `resume(ctx)` returns it next time (returning `null`, `""` or `undefined` opens a fresh agent) (fact 56). The package keeps no session state, so the id lives wherever your app puts it; on the harness path the manager records it (facts 57, 105). `HOME` must be the same for the run that made the agent and the one that resumes it, because Cursor keeps its agents under it (fact 60).
3. While a Cursor run works, what shows up in the session's stream, how do you know whether it succeeded, and where do you find what it cost?
   Answer: Assistant text arrives as `message`, thinking as `reasoning`, each tool call (including a change to Cursor's to-do list) as a `tool_output` that is settled with its result, and lifecycle as `status`. A finished run ends with a kept status like `Cursor run completed in <duration>.` (facts 63, 64). Read success off the returned handle, not off the status items: `outcome` is `"finished"` or `"failed"`, taken from the SDK's terminal record (facts 71, 72). Token counts never reach the stream. They ride the handle, with Cursor's detail on `cursorUsage`. `cost` is an estimate and is `null` for most runs, because Cursor's own model ids (like `composer-2.5`) are not in the price table, so read `cursorUsage` (facts 68, 76, 77).
4. A step's deadline fires while Cursor is still working, and on another day Cursor itself reports the run as failed. What does the step get in each case, and can you still continue the conversation afterwards? *(edge case)*
   Answer: When the deadline or signal fires, the block asks Cursor's runtime to stop, releases it, and throws `CursorAgentAbortedError` with the agent id on `sessionId`. No handle is returned (facts 52, 72). That conversation is still resumable: `onSession` already ran before the prompt was sent, and the error carries the id too (fact 58). A command Cursor started can outlive the release, and only the sandbox setting bounds that (fact 52). When Cursor itself fails the run, nothing is thrown. The step gets a handle with `status: "errored"`, `outcome: "failed"` and Cursor's message on `failureMessage`, and nothing retries (fact 74).
5. The agent id your app saved points at an agent Cursor no longer knows (say it was made under a different `HOME`). What happens on the resumed run, and what happens to the id you hold? *(edge case)*
   Answer: Cursor refuses the resume, and the block throws instead of opening a new agent, so the stored id is left as it was. The error is a `CursorAgentRunError`, and `harnessFailureKind(error)` reads `"unknown-conversation"`. Any other failure reads `null`, including one after Cursor has resumed the agent (fact 59). Keeping `HOME` the same for both runs avoids the case (fact 60).
6. A teammate types a correction into the session while a Cursor turn is still running on a task. Does the running turn see it, and what happens if it doesn't? *(edge case)*
   Answer: It can join the turn while it runs. The block calls `onSteerable` with a `steer` function once the prompt is sent, and calls it with `null` when the turn is over (fact 84). `steer(text)` resolves `"delivered"` when Cursor took the line into the turn, and `"refused"` when Cursor said it should wait, the call failed, or the turn had ended. A refused line was not taken, so send it as the next prompt (fact 85). From a session, hand `harnessSteering().onSteerable` (from `@flow-state-dev/core/harness`) to the block and declare `steering.action()` as `steer` beside a `defer` turn action. The action answers `{ taken, live }` (facts 88, 89). Offers live in the server process, so a line that reaches another process runs as the next turn (fact 90). On a task board the harness manager hands new messages to the running step the same way, with no stop and no new attempt, and a message the run turns away goes to the next step. Cursor is the one harness that takes a line live today (facts 92, 93).

- `cursorAgent` block: input is `{ prompt }` only; `cwd`, resume and model are configuration; `cwd` is called once per run and does not fence the agent in → R-27
