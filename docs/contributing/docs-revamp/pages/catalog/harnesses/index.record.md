## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. An app runs Workforce and wants a coding worker named Codex that runs tasks on OpenAI's Codex. Which slot does the harness kit open, what goes into it for Codex, and what does the worker's WORKER.md have to say?
   Answer: The kit (`harnesses`, from `@flow-state-dev/harness-manager/kit`) opens one keyed slot, `harnesses.slots.harnesses`, filled with Harness values. Codex is a plain value, so the app fills it with `fill: { [harnesses.slots.harnesses]: [codexHarness()] }` (hk:90-95, lt:376-381). Claude Code is different: it is a kit, `claudeCode()`, that fills the slot itself (cck:72-80). The worker's WORKER.md front matter names `flow: coder` and `harness: codex` (labs/teammates/.../codex/WORKER.md:1-6). A worker file with no `harness:` line runs on the kit's `defaultHarness`, and if there is none its task is refused (cf:224-233).
2. A Codex run on the task "fix cart test" finishes and says it fixed the test. The kit has `checks: { commands: ["pnpm test"] }` and `judge` on, and the task has a goal. What has to hold before the task is marked complete?
   Answer: The verdict comes from the harness handle's status, not from what the agent said. In order: (1) the harness terminated normally; (2) the run reports `finished`, since `stopped-at-limit` does not count as done; (3) the run changed files, so `pnpm test` must pass in its worktree (a run that changed nothing skips the checks); (4) goalJudge reads the goal, the answer, the commits and the changed files, and a confident not-done (0.7 or more) fails the attempt; (5) with `review` on and commits on the branch, a user must accept; (6) if the run opened a pull request and `pullRequests` is on (the default), the PR must merge. Anything short of done fails the attempt, and the next brief says why (hm:31-33, cf:117-145, gj:35, cf:205-206).
3. Where does that run's code live, and what is it made from? If the first attempt fails, where does the retry work?
   Answer: Each task gets its own git checkout: a worktree on its own branch, e.g. `conductor/fix-cart-test-3fa9c1` in the folder `<root>/<name>` under the workspace host's `root` (ws:41-47). If the source is a repository listed in `localRepositories`, the checkout is a worktree of that repository. Any other source the host allows (`remotes.allow`) is cloned under `root` (wsp:197-211). The place is worked out from the run's user, the board, the issue and the phase, so a retry lands in the same directory and carries on from the changes left on the branch (hm:9, hm:438). Setup never touches the user's working tree. A fresh checkout has no installed dependencies until the host runs a `setup` command (wsp:248-254).
4. What does the harness kit need from Workforce, and what does it add to Workforce?
   Answer: It declares `requires: [workforce]`, so the app does not start without the workforce kit (hk:98). It fills two of Workforce's slots: `workforce.slots.workerFlows` gets the single `coder` flow, and `workforce.slots.uses` gets the readiness capability, which tells workers which harnesses are ready (hk:105-106). A coding worker is an ordinary Workforce worker: a WORKER.md naming `flow: coder`, hired and listed on the roster like any other. It takes tasks a coordinator files on its conversation's board. A second coding worker is another WORKER.md, never another flow (cf:6-12, cf:252-254). It does not use the `workforce({ agent: { model } })` model, because a coding run uses its harness's own model.
5. Edge case: the Cursor worker gets a task on a machine where Cursor isn't signed in, while Codex is ready. What happens to the task? And what happens to an app whose worker file says `harness: copilot` when nobody filled that harness? *(edge case)*
   Answer: Before each task starts, the flow asks whether that harness can run on this machine. If it cannot, the task fails at once with the reason and what to run to fix it, and it never falls back to another harness such as Codex (cf:12-13, cf:241-246). Readiness is held in memory and not stored. It checks whether a credential is there, not whether the credential works, and the `harnesses` flow's `readiness` view shows it (rd:20-32). A `harness:` line naming a harness nobody filled stops the app at start and names that harness (kt:106-119).
6. Edge case: with `review: true`, a run commits three changes and a user asks for changes: "Keep the old endpoint as a fallback." What does the user see first, what does that answer do, and what happens if nobody ever answers? *(edge case)*
   Answer: The task stays `in_progress` on the same attempt, and its checkout is released. The user's Inbox shows a review titled "Review the run's changes", with the commits, "N files changed (+a −d)", the check results and what the judge said. The judge's verdict is information, not approval (hm:140). Answering `{ verdict: "revise", words }` writes the words on the task as the user's message. One more run starts on the same attempt in the same coding session, and if it commits again it is reviewed again over all the branch's commits (hm:160). Blank words get a 400 and the review stays open. Accepting completes the task with `review: "accepted"`. With no `userDeadlineMs` the review waits indefinitely. With one set, the task completes at the deadline with `review: "deadline"`, shown as not reviewed, never as approved (hm:162). A review survives a host restart. Reviews need a host with durable execution (hm:166).
