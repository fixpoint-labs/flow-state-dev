## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your feedback setup has one actor watching `observation:slack.*`. You add a second actor, an alert actor watching `event:alert.**`. What do you have to change in the slack actor or anywhere else, and what must be true of the new actor?
   Answer: Nothing else changes. Each actor only declares what it watches, and `emit` matches every entry against the whole actor list, so there is no controller to update and no existing actor to edit (facts 2, 5). You add it to the `actors` list passed to `eventActors`. Its `name` must be unique, and its `watch` list must not be empty, or `actor()` throws at construction (facts 5, 7). An entry that matches both actors makes one task for each, and they run in no guaranteed order (facts 27, 66).
2. An entry `{ type: "observation", topic: "slack.message.edit", body: ... }` is emitted. Which of these actors run: one watching `observation:slack.*`, one watching `observation:**`, one watching `*:slack`? And if an actor lists two patterns that both match, how many times does it run?
   Answer: Only the `observation:**` actor runs. Patterns are matched against `type:topic` (here `observation:slack.message.edit`), and the whole key must match. `*` matches one segment and does not cross `.` or `:`, so `observation:slack.*` fails on `message.edit`, and `*:slack` fails because the topic is not `slack`. `**` matches any number of segments (facts 20-25). An actor runs once per matching entry, not once per matching pattern: one task per actor per entry (facts 26, 27).
3. The slack actor and the alert actor both match an entry. The slack actor's block throws. What happens to the alert actor, to `emit`, and to the slack actor's work? *(edge case)*
   Answer: The alert actor is unaffected and keeps running; `emit` finishes. The throwing actor's task is recorded as failed and the other tasks continue (the board's `skip` error policy, which `eventActors` uses and does not let you change) (facts 51, 52). The failed task is not retried, since eventActors tasks have no retries (fact 55), and a failed actor re-emits nothing (fact 54).
4. You want the slack actor, after summarising a message, to wake a second actor that files a report. How does one actor trigger another?
   Answer: Set `reEmit: true` on `eventActors` and have the slack actor's block return an entry, an object with string `type`, string `topic` and a `body` (or an array of them, or `{ entries: [...] }`). Each returned entry is recorded in the log and dispatched to the actors whose patterns match it, e.g. a report actor watching `summary:**` (facts 39-42, 49). With `reEmit` off, the default, the output is ignored (fact 39). Actors never see each other's output directly; the returned entry is the only hand-off (fact 50).
5. With `reEmit: true`, the chain grows: the slack actor emits a summary, the summary actor emits a report, the report actor emits another entry. With the default settings, where does it stop, and what happens to the output at the limit? *(edge case)*
   Answer: It stops at `maxDepth`, default 3. Entries from `emit` make depth-1 tasks; an entry returned by a depth-d task makes depth d+1 tasks, created only while that stays within `maxDepth` (fact 45). At the limit the actor still runs and its output is still recorded in the log, but no further actors are dispatched for it (fact 46). `maxDepth` only matters when `reEmit` is on (fact 47).
6. A busy channel: one emitted entry matches so many actors that creating their tasks would cross the task limit. What runs? *(edge case)*
   Answer: None of that entry's actors run, and `emit` errors. An entry's tasks are created in one batch, so all its matching actors are dispatched or none are (facts 35, 56a). The limits default to 500 tasks created in all and 100 waiting at once; raise them, or pass `null` to remove them, with `maxTotalTasks` and `maxEnqueuedTasks` (fact 17). If instead an actor's re-emitted output would cross the limit, that actor's task errors and nothing from the output is dispatched (fact 56b).
