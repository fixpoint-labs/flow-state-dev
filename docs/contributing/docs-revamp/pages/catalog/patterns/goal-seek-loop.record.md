## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You wrap a `research` board in `goalSeekLoop` with `maxIterations: 3` and a judge that returns `done` once no task has errored. Name the two ways this loop can stop, and what `reason` the termination item carries in each case.
   Answer: The judge returns `{ decision: "done", reason }`, and the loop ends with the judge's own reason string. Or the iteration budget runs out: at the last allowed drain, a verdict other than `done` is turned into `{ decision: "done", reason: "max-iterations" }`. `maxIterations` is required and counts drains, so the loop always ends (gsl:162-167, gsl:499-518, gt:127-153). Only `done` ends the loop on its own. `continue` and `replan` loop back to the drain (gsl:638-641).
2. Your inline judge is `({ collection }) => ...`. What can it look at to decide, and what must it return?
   Answer: It gets `{ collection, drainResult }`. `collection` is the board's live task collection, and `collection.list()` returns tasks with `id`, `goal`, `status` (for example `completed` or `errored`), `output` and an optional `error`. `drainResult` is the drain's raw result. It must return a `Verdict`: `{ decision: "done", reason }`, `{ decision: "continue", reason }` or `{ decision: "replan", reason, tasks? }`. `reason` is required on all three (gsl:79-94, gsl:435-446, gsl:667-685, ts:14-21). A block or sub-sequencer judge gets the drain result as its input instead and reads the board through `ctx.cap.<board name>` (gsl:84-90).
3. After the first drain, your judge sees that two research tasks errored and wants to queue two follow-up tasks before the next pass. Which verdict does it return, and how does that differ from `continue`?
   Answer: It returns `{ decision: "replan", reason, tasks: [...] }` with the new tasks. Those tasks are added to the board and the board is drained again. `continue` drains again with no new tasks. If a `replan` carries no tasks, the optional `replanner` block supplies them (gsl:73-78, gsl:520-525, gsl:608-634, gt:107-125, gt:161-183). A `replan` on the last allowed drain becomes `max-iterations` instead, so no task is added that no drain would run (gsl:499-502).
4. Your judge has a bug. Sometimes it throws, and sometimes it returns `{ decision: "done" }` with no `reason`. What happens to the loop, and does `finalize` still run? How do you make that failure a request error instead? *(edge case)*
   Answer: With the default `onError: "skip"`, a judge that throws or returns a malformed verdict (a missing `reason` counts) ends the loop with reason `"judge-error"`, and `finalize` still runs over the board (gsl:448-497, gt:338-352, gt:390-403). Set `onError: "fail"` and the failure propagates as a request error instead (gsl:173-179, gt:354-368). A failure in `seed` or in the drain propagates either way (gt:370-388).
5. One research task stops to ask a person a question, so it is waiting when the drain ends. Does the judge rule on the board? Is an iteration spent? How does the work carry on once the person answers? *(edge case)*
   Answer: No. The pass ends with reason `"waiting-on-a-user"`, with no judge, no replan, no `finalize` and no iteration spent (the test reports `iterations: 0`). A task waiting on an event outside the board ends the pass the same way, with `"waiting-on-an-event"`. To carry on after the answer, run the loop again, and the drain takes the task's next turn. This needs a board whose tasks outlive the request, a `defineTaskCollection` board (gsl:21-31, gsl:386-398, gt:604-679, it:1-18).
6. Which shipped patterns run on `goalSeekLoop`, and how does each one configure it? Does `supervisor` run on it?
   Answer: Two do. `parallelTasks` is a single pass: its judge always returns `{ decision: "done", reason: "converged" }`, with `maxIterations: 1`, a `seed` that plans and fills the board, and a `finalize` that collects and merges results (pt:174-200). `planAndExecute` re-plans across drains. Its judge runs the pattern's evaluator (and its replanner) and maps `complete` to `done`, `replan` to `replan` with tasks, and anything else to `continue`. Its `finalize` is a synthesizer, and it passes `onError: "fail"` and forwards its own `maxIterations` (pe:747-825). `supervisor` does not use the loop: its reviewer runs inside each task, with a retry budget per task (fact sheet §5).
