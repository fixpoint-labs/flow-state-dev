## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk turns each incoming ticket into a short summary, and no summary should count until it has been checked against a list of criteria (states the customer's problem, names the product, no invented details). A summary that fails should be redone with the feedback. Which pattern do you reach for, and what do you give it?
   Answer: supervisor. Give it a name, a worker (e.g. summarizeTicket) and reviewCriteria, the list the default reviewer checks each result against. Each task goes worker, then reviewer, then approve or reject. A rejected result is re-run with the reviewer's feedback until the retry budget runs out (maxAttemptsPerTask, default 3). Fact sheet 2.2.
2. You are planning a fix for a recurring outage: first gather the affected tickets, then find the common cause, then draft the customer notice. What you learn in the early steps should be able to add or change later steps. Which pattern fits, and do you get the replanning by default?
   Answer: planAndExecute with enableReplanning: true. It plans a dependency-ordered set of tasks and works through them, one at a time by default (maxConcurrency 1). Replanning is off by default (enableReplanning: false): it runs the seeded tasks once and completes. With replanning on, an evaluator reads the results after each pass and can return continue, complete or replan, and on replan new tasks are added. Fact sheet 2.3.
3. You want to know whether supervisor or parallelTasks gives better ticket digests on your own tickets. How do you compare them, and what in the output tells you the difference is real?
   Answer: Write a TypeScript module that does export default defineBenchmark({...}). Import defineBenchmark from @flow-state-dev/testing/benchmark. Put both registry names in patterns ("supervisor", "parallel-tasks"), your own tasks in tasks (each { id, category, prompt, rubric }), and a model. Then run fsdev benchmark <file>. Both patterns run on the same tasks and the same model, next to a single-generator baseline. A separate judge model scores each output against the rubric without knowing which pattern produced it. In the ranking, read Δ vs baseline and credible. Credible is true only when the gap is more than about two standard errors and both groups have at least 2 runs. Fact sheet 5.1-5.5, 5.12, 5.13, 5.17.
4. Your benchmark comes back and supervisor's row shows a higher mean than parallelTasks, but credible is false. A teammate wants to announce that supervisor wins. What do you tell them? *(edge case)*
   Answer: credible: false means the gap could be noise, so don't treat it as a measurable difference. More runs narrows the variance. Even a credible result only describes your tasks on your model, not the patterns in general: every pattern runs on the same shared generator. Fact sheet 5.13, 5.15, section 7.
5. You start a benchmark with --max-cost 0.50 and the spending passes 50 cents partway through the sweep. What happens, and what does a CI job that ran it see? *(edge case)*
   Answer: The sweep stops, prints a partial scorecard and exits non-zero (exit code 1), so the CI job sees a failure. Fact sheet 5.10.
6. After the agent answers a customer, you want the answer checked for tone and policy, without making the customer wait. You import responseAuditor from @flow-state-dev/patterns and then try to add it to your benchmark next to supervisor. Two things go wrong. What are they? *(edge case)*
   Answer: First, the package root doesn't export responseAuditor. Import it from the subpath @flow-state-dev/patterns/response-auditor. Second, it can't be benchmarked with fsdev benchmark. The default registry has only six entries, and eventActors and responseAuditor aren't goal-to-answer shaped. It's attached with .sideChain() after a generator, so the answer streams first and the analyzers score it afterwards. It never changes the answer. Fact sheet flag 5, flag 6, 1.3, 2.8.
