## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your research flow asks parallelTasks to "compare three competitors", which splits into one sub-task per competitor. The worker for the second competitor throws, and you left the error settings at their defaults. What does the block's result hold, and can you tell from it that a competitor is missing? *(edge case)*
   Answer: The default is onSubTaskError: "skip". The failed sub-task is marked errored, the other two keep running, and the synthesizer gets only the two completed outputs. result.error is null and output.combined holds the merged pair (F26; test parallelTasks.test.ts:198-230). Nothing in the result marks the skip: the output is just the synthesizer's output, so a missing competitor leaves no trace (F27). If every sub-task fails, the synthesizer gets an empty list and the default combiner returns combined: [] with a note (F28).
2. For the same comparison you would rather get no answer than a two-out-of-three answer. What do you set, and what does the caller get back when one competitor's worker fails? *(edge case)*
   Answer: Set onSubTaskError: "fail". The first failure fails the whole block: result.error is non-null and carries the worker's own error (F29). There is no partial result. The block errors instead of returning the outputs that did complete (F30).
3. A competitor's worker fails because of a transient network error. Does parallelTasks retry it on its own, and if not, how do you make it retry? *(edge case)*
   Answer: Not by default. Retries come from the board, one sub-task at a time, and only when the planned task carries maxAttempts. The default planner never sets maxAttempts, so a failed sub-task runs once (F32). To get retries, use a custom planner that puts maxAttempts on each task. On the retry the worker gets the failure message as feedback, and attempts counts up (F33). Retries across all sub-tasks are capped by maxTotalRetries, which defaults to 50 (F34).
4. You want each competitor summary checked, and redone if it is thin, before the results are combined. Does Parallel Tasks do that? If it doesn't, what should you use?
   Answer: No. Parallel Tasks makes one pass: split, run side by side, combine. It has no review step, no replanning and no second pass (F2, F35). Supervisor is the pattern that adds a reviewer per task and retries rejected work (F35, F6).
5. The default planner splits "compare three competitors" in a generic way, and you want exactly one sub-task per named competitor. Where do you swap the planner, and what does your planner have to accept and return?
   Answer: Pass your own block as the planner option of parallelTasks({ name, worker, planner }). It can be any block kind, such as a generator or a handler (F36, F37). It receives { goal: string } and must return { tasks: [{ goal: string, ... }] }. Each task can also carry id, title, context, input, priority, maxAttempts and deps (F14). The default is utility.decomposer, a generator on openai/gpt-6-luna (F13). In tests it can be replaced by name as "<name>-planner" (F17).
6. You want the final output to be a comparison table instead of the default merged object. You add a custom synthesizer. What does it receive, what comes back from the block, and what should the worker include if the table needs to name each competitor?
   Answer: The synthesizer receives unknown[]: the output of each completed task, with undefined outputs and failed tasks left out (F21, F26). Its own output becomes the block's output, with no { combined } wrapper (F22). It gets only the outputs. It does not see the goal, the sub-task goals or which tasks failed. So each worker output has to carry the competitor's name itself (F25). The order of the list is not guaranteed (F24), so don't rely on its position. A generator synthesizer reads the list in its user slot, for example JSON.stringify(results) (F23).

- Synthesizer contract: receives `unknown[]` of completed task outputs, default `utility.combiner()` merges with no model call, `outputSchema` goes to the default combiner only → R-41
- `onSubTaskError` values: `skip` (default; failed sub-tasks left out, synthesizer gets an empty array if all fail) and `fail` (any failure throws and aborts) → R-41
- Unsupported `onSubTaskError` value (`"retry"`): warning at construction, falls back to `skip` → R-41
- Retry behaviour: the planner sets a per-task `maxAttempts`; a failed task with attempts left is re-queued and the error arrives as `feedback` on the next attempt. With `onSubTaskError: "skip"` (default) a failure is only left out of synthesis once attempts run out. With `"fail"` the pattern throws and aborts on the first failed attempt, even if attempts remain. → R-23 (corrected by pass 5)
- `maxTotalRetries`: board-wide retry bound, default 50, `null` for no bound, `0` for none; a sub-task retries only when it has `maxAttempts` → R-23
