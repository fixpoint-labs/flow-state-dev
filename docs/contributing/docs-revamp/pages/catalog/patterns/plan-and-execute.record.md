## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You mount `planAndExecute({ name: "research" })` with no other options. The planner breaks the goal into three tasks, all three run, and one result shows the third task missed something important. Does the pattern go back and plan more work before it answers? What would you change so it can?
   Answer: No. With the defaults it never replans: `enableReplanning` defaults to `false` (ix:613), and the default evaluator makes no model call. It counts passes and says complete when nothing is left to run (ev:107-139), so the run plans once, works every task, then synthesizes (ev:10-14, t:102-134). Set `enableReplanning: true` to get a model evaluator. It reads the goal, the iteration count and each task's status, output and error, then answers `continue`, `replan` or `complete` (ev:146-192). On `replan` the replanner adds only new tasks to the same board, and the board is worked again (ix:253-262, ix:782-808, t:562-641).
2. With replanning on, a five-task plan runs with `maxConcurrency: 1`. How many times is the evaluator asked whether to replan: after every task, or at some other point? And what stops it from replanning forever?
   Answer: Once per pass through the board, not once per task. The board runs every task that can run, and only then does the evaluator judge (ix:13-15, ix:714-733, ix:810-826; t:562-641 shows one evaluator call per pass). `maxIterations` (default 3) is a hard cap on passes. At the cap, any verdict other than done is turned into done with reason `max-iterations`, and a replan on that last pass adds no work (ix:612, gl:500-514, ix:796-801).
3. A plan has tasks s1, s2 and s3, where s2 depends on s1 and s3 depends on s2. The executor for s1 throws, or returns `{ success: false, reason: "Information not available" }`. What happens to s2 and s3, and does the action run end with an error? *(edge case)*
   Answer: s1 is marked `failed`, with its `error` set to the thrown message or the `reason` (ix:458-478, t:392-435). Every pending task that depends on it, directly or through the chain, is cancelled and reported as `skipped`, so s2 and s3 never run (t:259-296, ix:714-733 with onError "skip", sy:39-44). The run does not error. It finishes, and the result reports which tasks failed and which were skipped (t:219-257).
4. In the same plan, a fourth task s4 depends on nothing, and s1 is the only task that fails. Does s4 still run? With the default synthesizer, what does the user get back if every task fails? *(edge case)*
   Answer: Yes. Tasks that don't depend on the failed one carry on and can complete (t:219-257: s2 fails while s1 and s3 complete). The default synthesizer runs even when every task failed. It is told the steps did not finish, given the first error, and asked to answer the goal directly from its own knowledge without mentioning the failed plan. The user still gets a text answer (ix:502-512, ix:565). With `synthesizer: false` the output is the plan object, and its overall `status` is `failed` only when every task that was not skipped failed (sy:96-107).
5. In a chat, a user first asks for asset info on a.com, and then sends "now do that for all of them: a.com, b.com, c.com" (or just "now do that for all of them"). Where does the pattern's goal come from, and what will the planner see unless you change a setting? *(edge case)*
   Answer: The goal is the action's `{ goal: string }` input. The caller decides what that string is, for example `userMessage: (input) => input.goal`, and the pattern does not read the chat on its own (sc:81-83, fx:14-35). By default the goal is used word for word, so the planner sees the literal follow-up text (ix:209-216, t:1301-1318). With `synthesizeGoal: true`, a model call first rewrites the request into a self-contained goal. It uses the last 8 history items to resolve "that" and "all of them" and keeps every concrete value, so the goal becomes, e.g., "Research asset info for a.com, b.com, c.com" (pe:267-287, t:1232-1255). The planner, replanner, evaluator and synthesizer all use that rewritten goal (ix:697-771). If the rewrite call fails, planning goes ahead with the original text (pe:289-306, t:1320-1350).
6. You replace the default executor with your own handler as `stepExecutor`. What input does it receive, how does it see what earlier tasks produced, and how does it report that a step could not be done?
   Answer: It receives `{ stepId, goal, context?, dependencyResults? }`. `stepId` is the task id and `goal` is the task's goal. `context` is per-task support text, a copy of the overall goal by default (`taskContext: "goal"`). `dependencyResults` is an object keyed by the ids of the tasks this one depends on, each holding that task's output, and it is present only when the task has dependencies (ix:439-456, ix:347-352, t:1007-1034). Returning an object with `success: false` and a `reason` fails the task, with the reason as its error. The default executor's shape is `{ summary, success, reason?, sources? }` (ix:309-321, ix:458-478, t:392-435). Any block works as the executor, including a handler, generator, sequencer or another pattern (t:30-39, op:344-360).
