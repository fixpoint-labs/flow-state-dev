## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You attach the auditor after your chat generator and write a custom analyzer for it. What must that analyzer take in and hand back, and which way does its score point?
   Answer: It takes { userInput, response } and returns an AnalyzerResult: analyzerId, category, score (a number from 0 to 1), shouldSurface (boolean), annotations (an array, which may be empty) and an optional supplementary record. Each annotation has type, label, description, severity ('info' | 'warning' | 'critical') and optional evidence. A higher score means more concern. (Facts 2.1-2.4, schemas:7-24)
2. Your chat generator streams an answer to the user and the auditor runs after it in a side chain. Where does the audit show up for the user and for your code, and does the auditor change the answer the user sees?
   Answer: It never changes the response; it only analyzes it. The answer streams first and the audit arrives afterwards. When at least one result surfaces, the auditor emits an 'audit-annotation' component item holding { results, surfacedResults, overallScore }. A chat surface built on chatAssistantRenderers from @flow-state-dev/ui draws it as a 'Response Audit' card with no extra code (without those renderers you add the card with fsdev ui add audit-annotation and register it under renderers.component['audit-annotation']). The item is persisted, so the card survives a page refresh. Code reads the same data as the auditor block's output. (Facts 1.3, 1.6, 4.2, 4.5-4.7, 4.10)
3. You add a model-backed tone analyzer next to an existing handler analyzer. How do you build it and wire it in, and how do you get an extra summary line onto the card?
   Answer: Build a sequencer: a generator with a typed outputSchema (for example { tone, confidence, issues }), then a handler step that turns that into an AnalyzerResult. Pass both analyzers in the array: responseAuditor({ analyzers: [existing, toneAnalyzer] }). Give each analyzer a distinct analyzerId, because the card keys its sections by that id. For extra text, set supplementary.summary to a string and the card shows it under that analyzer's header. Only summary and counterArguments are read; other supplementary keys are carried along but not shown. (Facts 5.3-5.5, 4.8)
4. Three analyzers return scores of 0.1, 0.3 and 0.9. One of the 0.1 results has shouldSurface: true. The threshold is the default. What goes into results, what goes into surfacedResults, what is overallScore, and what does the card list? *(edge case)*
   Answer: The default threshold is 0.3, and a result surfaces when shouldSurface is true or its score is at or above the threshold. All three results go into results. surfacedResults gets the 0.3 result (equal counts), the 0.9 result and the 0.1 result marked shouldSurface. overallScore is the plain mean, (0.1+0.3+0.9)/3 ≈ 0.43. The card lists only surfaced results, so here it lists all three. A 0.1 result without shouldSurface would stay in results but not be drawn. (Facts 3.4-3.7, 4.9)
5. Failure: one of your three analyzers throws (its model call times out), and on another run a custom analyzer returns score: 2. What happens to the audit in each case? *(edge case)*
   Answer: A thrown analyzer is skipped: the auditor does not fail, the other results are kept, the failed analyzer has no entry in results, and it does not count toward overallScore. Nothing in the output names the failed analyzer; the failure shows in the DevTool trace. A returned bad shape is different: the results are validated when collected, so score: 2 (or an annotation with no label) fails the whole auditor. Because it runs as a side chain, the main answer still reaches the user. Putting outputSchema: AnalyzerResultSchema on the analyzer catches the mistake at the analyzer. (Facts 3.3, 2.5, 1.7, 5.7)
6. Second turn: the same user asks a follow-up and the auditor runs again in the same request, and nothing crosses the threshold this time. Does the earlier card get replaced, does a new card appear, and does the auditor keep anything from the first turn? *(edge case)*
   Answer: The earlier card stays. The audit-annotation item has no key and is append-only, so a later run never overwrites an earlier one. When nothing surfaces, no card is emitted at all, though results is still full and overallScore is still computed in the output. The audit belongs to the request that produced it. Nothing is written to session, user or org state, and the next run starts from empty defaults. (Facts 4.3, 4.4, 3.7, section 7)
