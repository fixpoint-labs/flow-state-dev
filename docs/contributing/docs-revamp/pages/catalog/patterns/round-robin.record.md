## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your editorial review runs `writer`, `fact-checker` and `copy-editor` with `maxRounds: 3` and no `terminateWhen`. In what order do they speak, how many contributions are in the transcript when the loop ends, and what runs after the last turn?
   Answer: Each round runs every roster entry once, in declared order, and nobody speaks twice in a round: writer, fact-checker, copy-editor, three times over. That is 9 contributions, rounds x roster length (facts 2-4; storage section, 'How many'). With no `terminateWhen`, only `maxRounds` stops the loop (facts 16, 18). The default synthesizer then runs last and merges the contributions into one string, unless you set `synthesizer: false` (facts 6, 42).
2. You add `terminateWhen` so the review stops once the copy-editor's latest contribution says "no further edits". Round 1 is clean, so the condition is true straight after the copy-editor speaks. When does the loop stop, and could it stop earlier, say right after the writer's round-2 turn?
   Answer: It stops after round 1, so `rounds: 1`. The check runs once per round, after every roster agent and after the referee if there is one (facts 17, 19). It cannot stop partway through a round (section 11). `maxRounds` comes first: if `round >= maxRounds` the loop stops without calling `terminateWhen`. Otherwise a true return from `terminateWhen` stops it (fact 18). `terminateWhen` reads `ctx.sequencer.state` (`round`, `refereeCritiques`, `goal`) and `ctx.session.state` (fact 20).
3. You add a referee to the editorial review. What does it change about the run, and can it end the review early, for example when it judges the draft finished?
   Answer: After each round's roster turns the referee runs, and its `{ critique }` is appended to the sequencer state as `refereeCritiques: { round, critique }[]` (facts 27-29). That includes the last round (fact 26). Default roster agents see every critique so far under "Referee critiques so far", so round 2 sees round 1's critique and round 1 sees none (fact 30). The default synthesizer gets every critique, and they all appear in the final shape (fact 32). The referee cannot stop the loop, since its output is only `{ critique }` (fact 24). It does not change who speaks or rewrite, reorder or remove contributions (fact 33; section 11). To stop on its verdict, read `refereeCritiques` in `terminateWhen` (fact 20). No default referee exists: you pass a block, for example one built with `createReferee` (fact 34).
4. You replace `fact-checker` with your own custom `block`, and the review still has a referee. Which earlier contributions and referee critiques does your block see, and do the pattern-level `instructions` and `tools` reach it? *(edge case)*
   Answer: Only what it declares. The pattern passes a custom block its input (the previous step's value) and injects nothing into it. It gets no prior transcript and no critiques (facts 31, 37). To read the transcript it declares the contributions resource. To read critiques it reads `ctx.sequencer.state.refereeCritiques` (facts 31, 35). Pattern-level `instructions`, `uses`, `tools`, `context` and `model` reach only the default blocks (fact 15; section 11). The block must return a string or `{ text: string }`. Any other value is coerced with `String()`, with one warning per agent name (fact 15).
5. Halfway through round 2 the `fact-checker` agent throws, say on a provider error. What happens to the rest of the round and to the run? Is the agent retried, or does the loop go on to the next agent? *(edge case)*
   Answer: The run fails and the result carries an error. The pattern does not retry the agent or skip it (fact 25; section 11). The same goes for a `terminateWhen` that throws: it surfaces as a loop runtime error, so `terminateWhen` should be pure and total (fact 21).
6. A dashboard block elsewhere in the flow reads the editorial transcript. You pass `contributions: createRoundRobinContributions()` and register it on the flow. A second review runs in the same session. What does the dashboard see afterwards: both reviews' contributions, or only the second's? And can the browser client read the resource? *(edge case)*
   Answer: Only the second's. The pattern clears the transcript (`entries: []`) at the start of every run, so a shared resource holds the latest run's transcript and no history across runs (fact 41). The resource is session-scoped, so every request in the session shares one instance (fact 36; storage section). It sets no `client` config, so clients cannot see it. Only blocks that declare it can (storage section). If you need the whole result after the loop, take the final shape `{ rounds, contributions, refereeCritiques }` as the pattern's output with `synthesizer: false` (facts 37-38).
