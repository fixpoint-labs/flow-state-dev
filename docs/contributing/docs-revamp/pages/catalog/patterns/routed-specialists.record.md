## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You build a routedSpecialists pattern with two specialists, `researcher` and `analyst`. After `researcher` has written its findings to the workspace, who decides whether `analyst` runs next, and how does it say so?
   Answer: The controller decides, on every pass. The specialists never choose each other. The controller returns `{ specialist, done, reasoning }`: `specialist: "analyst"` with `done: false` runs analyst next, and `done: true` with `specialist: null` ends the loop. Only one specialist runs per pass and they never run at the same time. By default the controller is an LLM generator that is given the specialist names, the iteration number and the workspace state as JSON. You can swap in any block that returns the same shape through `controller`. (Facts 2-6, 15.)
2. `analyst` needs to read what `researcher` found about the topic. How does it get that data, and what must you do so it can?
   Answer: Both read and write one shared workspace, created with `createWorkspace(schema)`. It is a session-scoped, writable resource whose whole schema you supply. Each specialist must declare `resources: { workspace }` itself, because the pattern does not install it for them. A specialist reads `ctx.resources.workspace.state` and writes with `ctx.resources.workspace.patchState({...})`. The workspace is not passed in as input: a specialist's input is the controller's decision. `initialState` (an object, or a sync or async function of the pattern input) seeds the workspace once at the start. (Facts 11-16.)
3. What ends a run? If the controller sends `researcher` and then `analyst` and then says done, what come back as `iterations` and `history`?
   Answer: The run ends when the controller returns `done: true`, or when it hits the `maxIterations` cap (default 10). In this case `iterations` is 3, because it counts every controller decision including the final done one. `history` has 2 entries, oldest first, each `{ iteration, specialist, reasoning, output }`, where `output` is what that specialist returned. By default a synthesizer (an LLM generator) turns `{ workspace, iterations, history }` into the final output. With `synthesizer: false` you get that raw object back instead. If the controller says done on the first pass, you get `iterations: 1` and an empty history, and no specialist runs. (Facts 18, 28-32.)
4. Edge case: you set `maxIterations: 3` and the controller never says done. Does the run fail, and how many times does a specialist run? *(edge case)*
   Answer: It does not fail. Hitting the cap is not an error: `result.error` is null and the output comes back. The cap counts repeats after the first pass, not total passes. So the run makes 4 controller decisions and 4 specialist runs, and returns `iterations: 4` with four history entries. (Facts 19-21.)
5. Edge case: `researcher` throws partway through a run. What happens to the loop, and what does the controller see next time? *(edge case)*
   Answer: The loop does not stop. That pass is recorded as failed, a status message `specialist failed: <message>` goes out, and the controller picks again. The failed pass does not show up in `history` or in the default controller's "Previous decisions" list, because both read completed passes only. So the default controller doesn't see that researcher was tried. All it has to go on is the workspace. In the tested case (broken, then recovery, then done), `iterations` is 3 and `history` holds only `recovery`. (Facts 24-25.)
6. Edge case: a custom controller returns `specialist: null` with `done: false`, or names `writer`, which is not registered. Does the run end or error? *(edge case)*
   Answer: Neither ends the run. A null specialist without `done: true` makes the dispatch fail with "Controller returned null specialist without done=true". An unregistered name makes the dispatch fail too, with the registered names listed. Both failures are caught the same way a specialist failure is, so the loop carries on and ends at `maxIterations` or at a later done. The top-level `error` stays null. Separately, building the pattern with no specialists at all throws "At least one specialist is required". (Facts 17, 22-23.)

## Reference rows

- `routedSpecialists` internal block sequence, in run order: (1) init, which seeds the workspace from `initialState` if set; (2) controller, which returns `{ specialist, done, reasoning }`; (3) record-iteration, which creates a Task and claims it if `!done`; (4) dispatch, which routes to the specialist by name only if `!done`, and a specialist failure is rescued and marks the Task failed so the loop continues; (5) record-completion, which marks the Task complete with the specialist's output (skipped when rescued); (6) snapshot, which emits the workspace component; (7) loop check, which returns `{ continue: !done }`; (8) loop back to the controller while `continue` is true, up to `maxIterations`; (9) a map to `{ workspace, iterations, history }`, then the optional synthesizer. → R-41 (corrected by pass 5)
- One Task per iteration where the controller picked a specialist, in a TaskCollection. `assignee` is the picked specialist, `output` is the specialist's return value, `goal` and `metadata.reasoning` hold the controller's reasoning, and `metadata.iteration` the iteration number. A specialist that throws leaves its Task failed. The collection is queryable after the run, and the default controller reads its completed Tasks to build its history prompt. → R-41 (corrected by pass 5)
- `routedSpecialists` config table, all 16 fields: `name` (string, required), `workspace` (DefinedResource, required), `specialists` (Record<string, BlockDefinition>, required, at least one), `instructions` (string or (input, ctx) => string, none), `controller` (BlockDefinition, default LLM controller), `maxIterations` (number, 10), `maxHistory` (number, unlimited), `initialState` (object or (input) => object, none), `model` (string, "openai/gpt-6-luna"), `context` (context slot for the default blocks, none), `uses` (capabilities for the default blocks, none), `controllerVisibility` (ItemVisibility, { client: true, history: false }), `synthesizerVisibility` (ItemVisibility, { client: true, history: true }), `synthesizer` (BlockDefinition or false, default LLM synthesizer), `outputSchema` (ZodTypeAny, none), `collectionId` (string, `name`). → R-41 (corrected by pass 5)
- `routedSpecialists` output shapes: raw `{ workspace, iterations, history[] }` when `synthesizer: false`; synthesizer input equals that shape and its result is the final output otherwise → R-41
- Where `routedSpecialists` records live: one Task per iteration in a TaskCollection whose id is `collectionId` (default: `name`). Query it after the run with `collection.list({ status: "completed" })`. The workspace is a separate writable, session-scoped resource created with `createWorkspace(schema)`. → R-24 (corrected by pass 5)
