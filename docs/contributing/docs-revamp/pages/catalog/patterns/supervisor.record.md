## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your `digest` supervisor runs `summarizeTicket` over each support ticket with `reviewCriteria: ["Names the customer's actual problem", "Under 80 words"]`. Who decides whether a ticket summary is good enough, and how do those criteria reach it?
   Answer: The reviewer decides, with one call for each finished attempt of each task. By default it is a generator the pattern builds, named `digest-reviewer`, using `model: "intent/synthesize"`. It returns `approve`, `reject` (redo, with actionable feedback) or `needs-revision` (close, needs targeted fixes, with feedback). `reviewCriteria` is a list of strings. The default reviewer sees it as a numbered "Evaluation criteria" list in its prompt, and any reviewer, the default or your own, gets it as `input.criteria` (facts §3).
2. You leave `maxAttemptsPerTask` at its default. How many times can the summary for one ticket run before the supervisor gives up on it? What if you set it to 1?
   Answer: The default is 3, and it counts the first attempt, so a task can run three times in all: once, then up to two retries. A task retries while `attempts < maxAttempts`. With `maxAttemptsPerTask: 1` there is no retry, and the first rejection settles the task (facts §4).
3. The reviewer rejects the first summary of ticket t2 with feedback "tighten the second paragraph". What is different about the input `summarizeTicket` gets on the retry, and what does it not get?
   Answer: Every attempt gets the same fields. A retry differs only in `attempts`, which goes from 1 to 2, and `feedback`, which is absent on the first attempt and now holds "tighten the second paragraph". `taskId`, `goal` and `context` stay the same because they are fixed when the task is filed. The worker does not get its previous output, so the reviewer's feedback should say what to keep. A declared `inputSchema` acts as a filter, so `summarizeTicket` must declare `feedback` to receive it (facts §5).
4. Ticket t1 is rejected on all three attempts, while t2 is approved. Does the digest run fail? What happens to t1, and what goes to the synthesizer? *(edge case)*
   Answer: The run does not fail. Once its budget is spent, t1 ends `errored` and gets the label `failed-review` because its last verdict was a rejection. The other tasks keep going. The synthesizer gets `results` holding only the output of each `completed` task, so t2's summary is included and t1's is not. The run still returns the synthesizer's output. This is the default `onSubTaskError: "skip"`. With `"fail"`, the first failed task would abort the run with an error (facts §4, §6, §9).
5. Instead of a rejection, the model call inside `summarizeTicket` throws on the first attempt for one ticket. Is that task retried, and what does the retry see? *(edge case)*
   Answer: Yes. A worker that throws is retried on the same `maxAttemptsPerTask` budget, so rejections and the worker's own errors share one counter. The thrown message becomes the next attempt's `feedback`. If the task runs out of attempts without ever reaching review, it ends `errored` with the label `worker-error` instead of `failed-review` (facts §4; the retry path is code-read, not tested).
6. A second request comes in, from the same user or a different one, an hour after a digest finished with one ticket errored. Can the new request pick up that board and retry the failed ticket? And if a ticket is rejected twice, does the third attempt see both rejections? *(edge case)*
   Answer: No to both. The board is kept on the request (`backing: "state"` on `ctx.request`), so it ends with the request and a new request starts with an empty board. Nothing a supervisor plans carries over to a later call, because it is not a background queue. For a board that outlives the request, see the Task board page (`backing: "resource"`). `feedback` holds only the latest failure, so after a second rejection it carries the second verdict's text, not both (facts §8, §5).
