## 4. How a skill activates (question 2, and the figure) (**[page]**)

The figure: a message, the match, the skill's body joining the prompt for that turn.

### 4a. Matched before the generator runs

- `createSkillActivator(options)` builds a sequencer block, named `"skill-activator"` by default, that is added ahead of the generator with `.tap(...)`. It reads `input.message`, decides which skills apply, and records them. The generator then runs once with the skill body already in its prompt. `act:158-246`, `act:1-34`, `ac:27-54`; test `skill-activator.test.ts:29-38`. **[page]**
- It returns its input unchanged, so it can sit anywhere in a chain without changing downstream input shapes. `act:18-21,152-157`. **[page]** (one clause; why `.tap`)
- It needs an object input with a string `message`. `act:60` (`z.object({ message: z.string() }).passthrough()`). **[page]**
- Three steps, in order, each skipped once an earlier one resolved: (1) slash match, (2) keyword scan, (3) classifier. `act:185-240`. **[page]**
  1. **Slash.** The message begins with `/<skill-name>`; the rest of the message is the argument (`$ARGUMENTS`). The pattern is `^\/([a-z0-9][a-z0-9-]{0,63})(?:\s+([\s\S]*))?$`, so the name is lowercase and the slash must be the first character. An unknown, disabled or not-allowed name falls through to the next step. No model call. `sl:50-82`; `packages/core/src/helpers/slash-command.ts:19`; test `skill-activator-allowed.test.ts:51-65`. **[page]**
  2. **Keyword.** Each skill's `keywords` are matched as plain substrings against the lowercased message; every skill with a hit activates, with source `"keyword"`, with no argument. No model call. `kw:36-90`, `ty:90-97`. **[page]** The parser lowercases each keyword when it reads `SKILL.md`, `smd:318-326`, and the message is lowercased at match time, so capitals in a keyword do not stop a match. A keyword matches as a substring: `news` also matches `newsletter`. `kw:51,68`; `au:88`. **[page]**
  3. **Classifier.** Runs only when neither earlier step resolved. The default is a generator on model `"intent/utility"` with structured output that can match several skills and keeps each only above a confidence of 0.65; it describes at most 20 skills to the model. `act:226-240`, `skill-classifier-gen.ts:25,28,47,62-68`; `ac:62`. **[page]** one sentence; `classifierModel`, `confidenceThreshold`, `maxSkillsInClassifier`, `enableLlmClassifier` and `enableKeywordMatch` are **[ref]** (`act:62-97`).
- A turn that matches by slash or keyword makes no model call for matching; a turn that falls through makes one. `ac:64`. **[page]**
- With an `evaluator`, the third step asks an evaluator block (a block that asks an evaluation model a question with known answers) which one skill fits, or none, instead of using the classifier. `act:212-225`, `ac:66-114`. The pick is final; an error fails the activator and does not fall back to the classifier. `act:114-127`. `skillEvaluator(model)` builds one; `skillEvaluator(model, { recentMessages: 3 })` lets it read the last three turns. `ac:70-92`; goals `goals/skill-activator/evaluator-picks-a-skill/goal.md`, `goals/skill-activator/follow-up-uses-recent-turns`. **[ref]** (the sitemap says "Routing with an evaluator → B-23": one sentence and a link)
- Which skills the matcher may pick: pass `allowed: [...]` to limit it to the binding's own set. A slash or keyword hit outside `allowed` falls through. Without it, a hit for any skill in the collection could land in a shared field and render on a generator that was never given that skill. `act:98-103`, `apply-skill-activation.ts:44-50,67-71`; test `skill-activator-allowed.test.ts:51-110`. **[page]**
- The matcher seeds the library before it reads: pass the same `initialSkills` to `createSkillActivator` that you gave the library. The activator runs before the generator, so without it the steps scan an empty collection on a fresh store's first turn. `act:105-113,177-197`; test `skill-activator-allowed.test.ts:66-92`. **[page]** (a reader hits this on turn 1)
- Where the matcher writes. Default `{ scope: "session", field: "activeSkills" }`, replacing the list each turn (not appending). `act:89-97`, `apply-skill-activation.ts:6-9,55-56,88-92`. **[page]** To feed a per-generator binding, point `activeState` at the field the binding reads (section 5). `act:89-96`. **[page]**
- Each activation records `{ name, mode: "inline", input, activatedAt, source }` with source `"slash"`, `"keyword"` or `"classifier"`; `"manual-override"` exists in the type. `apply-skill-activation.ts:81-87`, `ty:193-197`. **[ref]**

### 4b. Loaded by the agent mid-turn

- Two tool names, depending on how the skills were attached. With the session-wide capability the tool is `runSkill`; with a library binding that has `dynamicActivation` on it is `loadSkill`. - The agent reads the list of loadable skills, "- name: description" per line, in its system prompt and calls the tool when one applies. `lt:92-96,203-207`, `rs:97-116`. The body is added to the prompt on the next step of the same turn, not a later turn. `br:116-120`, `ctx:1-16`, `bd:362`; test `library.test.ts:446-466`. **[page]**
- The listing is on by default. Turn it off with `catalogContext: false` on the same `.with()` call and the agent finds skills through discovery instead, and the load tool's description says so. `lib:477-487`, `lt:92-96`; tests `catalog-preset.test.ts:107-146` (BR-13 default on, BR-14 off, and the tool description then names `discover`). `bd:318`. **[page]** (one sentence; this is the cost knob for a long catalog) The discovery feature itself is **[ref]** / its own page.

- Cost shape: the mid-turn path costs one extra provider call on a turn where a skill loads (decide, then run with the skill) and puts the catalog listing in the prompt every turn; the up-front path puts a classifier call in front of turns that match no slash or keyword. `ac:17-25,237-247`. **[page]** one sentence of each; the six-row "when to pick which" table is **[ref]** or cut (a table over six rows is banned by `user-docs.md`).
- Where a mid-turn activation lives. In a library binding, by default in the generator's own block state: private to that generator and request-scoped, so it does not carry to the next turn. `lib:144-148,450-453`, `activation-store.ts:1-27`, goal `goals/skills-scoped-binding/no-cross-generator-bleed/goal.md` ("a runtime activation is request-scoped by default — it does not carry into the next conversation turn"); test `library.test.ts:303-333`. ## 5. Binding skills to one generator (question 3) (**[page]**)

- A library is the shared catalog, installed once. A binding is per generator: which of the library's skills this generator has, and how. Two generators in one flow hold different skills without seeing each other's. `bd:240-242`, `lib:3-13`; goal `no-cross-generator-bleed`; test `library.test.ts:162-190` ("renders the bound skill body — and only that generator's skill"). **[page]**
- The session-wide capability, by contrast, keeps activations in one session-state list that every generator in the conversation reads. `bd:238`, `ov:57`, `cap:19-20`. **[page]**
- `.with({ ... })` and `.config({ ... }) / .presets({ ... })`: `.with` is one call that routes preset-named keys to presets and the rest to config; it is exactly `.config({ allowed }).presets({ dynamicActivation: true })`. ## 7. Change it (**[page]**)

The four questions, for each stored part.

### The skills (the folders, as stored)

- **Who owns it.** The scope the library is installed at: `"org"` (default, shared by everyone in the organization), `"user"` (each user has their own copy), `"session"` (mainly for tests). `lib:94-98,230`, `col:63-68`, `cap:64-69`. With `partitionBy` or `flowIsolation`, one set per party or per registered flow copy. `lib:100-116`, `col:70-95`. **[page]** the three scopes; `partitionBy`/`flowIsolation` **[ref]**.
- **Who can see it.** Whoever can read that scope. The collection exposes create, update, delete and read of the file content to the client, and puts `description`, `disableModelInvocation`, `allowedTools`, `contextMode`, `keywords` and `seededAt` on the client snapshot. `col:126-163`. So any client surface that can write the resource can edit a skill. **[page]** `gd:321-327` names DevTool, the client package and an admin UI as such surfaces; no test. **[gap]** do not claim DevTool has a skills editor beyond "DevTool shows resources and can edit them", `gd:325`.
- **Where it is stored.** In a resource collection with the pattern `skills/**` (the prefix is the collection key, `"skills"` by default, and also the mount path under `/workspace/`). It lives in whatever store the app runs on: it survives a restart on a store that persists, and not on the in-memory store. `col:106-113`, `lib:238-239`, `cap:110-114`; the persistence of resources is the Stores page's claim. **[page]** the first half; for the second, link, cite no test. `SKILL.md` entries carry the parsed frontmatter as state and the body as content; supporting files are plain entries. `col:1-17`.
- **How many exist.** As many skills as you seed or write, up to the collection's `maxInstances`, which counts `SKILL.md` and supporting files together. Unset by default, so no limit: `maxInstances?: number` with no default in `packages/core/src/types/resource-collection.ts:115` and a minimum of 1 at `:467-469`. ### The seed record (`_meta`)

- **Who owns / sees.** The library, internally; a reserved entry `skills/_meta` holding `seededNames`. `sd:1-15,152-161`, `col:167-168`, `ty:177-183`. A skill cannot be named `_meta`. `smd:46,130`. **[ref]** (the page says only "the library remembers which skills it has already copied in")
- **What it does.** `initialSkills` are copied into the store the first time they are read. A name already recorded is not copied again, so (a) an edit made to a stored skill is not overwritten by a redeploy, (b) a skill someone deleted stays deleted, and (c) a new folder added to `initialSkills` is copied in the next time. `sd:1-15,50-80`; tests `seeding.test.ts:32-75` ("is idempotent...", "seeds newly added skills on a later call", "respects user deletions"). **[page]** (this answers "I edited `SKILL.md` and redeployed, why did nothing change?")
- Seeding writes a copy, and a stored skill survives a source change. `rf:1-30`. To pull an edited source onto a store that already has the skill, call `refreshSeededSkills(collection, sources)`: it replaces each touched skill's folder whole, removes files the source no longer has, and drops any local addition inside that folder; a skill that was deleted stays deleted and a name never seeded is skipped. It returns `{ refreshed, skipped, removed, ... }`. `rf:30-60`, tests `refresh.test.ts:28-110,147-162`. **[page]** one short paragraph with the call; **[ref]** the result shape.
- `importSkillsDirectory(collection, root, { overwrite })` writes a directory over a live collection; with `overwrite: true` it does not delete files the source dropped, so it is not the same as a refresh. `import-directory.ts:1-9,18-35`, `packages/orchestration/README.md:1286-1298`. **[ref]**
