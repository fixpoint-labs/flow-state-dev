## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your team wants a release-notes playbook the agent follows when asked to draft notes. You create a skill for it. What goes in its folder, and what decides the skill's name?
   Answer: A folder with a SKILL.md at its root, optionally with supporting files (any layout; scripts/, references/, assets/ are conventions). SKILL.md is YAML frontmatter plus a Markdown body; the body is the playbook and `description` is the only required key. The skill's name is the folder's name, e.g. release-notes/. The description should say when the skill applies, since the matcher and the agent's catalog listing show it. (facts §1: ov:9-25, rd:4-5, ty:112-115, smd:184-192, au:47)
2. A user types "/release-notes v2.3" in one turn; in another turn they write "can you write up what shipped this week?" and the agent decides on its own to use the release-notes skill. Name the two ways a skill activated here, and say when the skill's body reaches the prompt in each.
   Answer: (1) Matched before the generator runs: a createSkillActivator block, added ahead of the generator with .tap(), reads the message and matches by slash ("/release-notes", with "v2.3" as $ARGUMENTS), then keyword, then a classifier; the generator runs once with the body already in its prompt. (2) Loaded by the agent mid-turn: the agent sees the list of skills in its prompt and calls loadSkill (library binding with dynamicActivation) or runSkill (session-wide capability); the body joins the prompt on the next step of the same turn. Naming a skill in `active` is something you set yourself, not a third way it activates. (facts flag 1, §4a, §4b: act:158-246, sl:50-82, lt:108-112, rs:134-137, br:116-120)
3. Your flow's main agent hands work to workers built with the supervisor pattern. You want only the main agent to load the release-notes skill, not the workers. How?
   Answer: Set itemVisibility: { client: true, history: true } on the skills library (or capability). The skills then attach only to generators whose own itemVisibility is { client: true, history: true } or unset. The supervisor pattern tags its workers { client: true, history: false } by default, so they do not get the skills. Without that setting, the skills attach to every generator that lists them. (Binding the library to just the main agent's generator also keeps it per generator.) (facts §5: cap:70-89, lib:117-121, capability-agent-type-filter.test.ts:52-94, supervisor/index.ts:164)
4. A teammate asks whether the release-notes checklist should be a skill or a capability. Which is it, and why?
   Answer: A skill. It is Markdown, it applies to some turns only, and an editor can change it without a deploy. It needs no tool, so there is no reason for a capability, which is code shipped with the app (resources, tools, context formatters) and is on for every generator that lists it. The skills library itself is shipped as a capability; that is how you attach skills, and the skills themselves are Markdown. (facts §2: ov:27-34, lib:469-492)
5. You edit release-notes/SKILL.md in your repo, which you pass to createSkillsLibrary as initialSkills, and redeploy. The agent still follows the old checklist. Why, and how do you get the new version in? *(edge case)*
   Answer: initialSkills are copied into the store the first time they are read, and the library records which names it has copied. A name already recorded is not copied again, so a redeploy does not overwrite the stored skill (that is also why edits made in the store and deletions survive). To pull the edited source onto a store that already has the skill, call refreshSeededSkills(collection, sources): it replaces that skill's folder whole and removes files the source no longer has; a deleted skill stays deleted. An edit made to the stored skill itself shows on the next step, because the body is read from the store each step. (facts §7: sd:1-15,50-80, seeding.test.ts:32-75, rf:30-60, rb:85-96)
6. On a brand-new store, the first user's very first message is "/release-notes v2.3", but the skill does not activate; later turns work. What went wrong, and what is the fix? *(edge case)*
   Answer: The activator runs before the generator, so on a fresh store's first turn it scanned an empty collection: the library had not seeded the skills yet. Pass the same initialSkills to createSkillActivator that you gave the library, so the matcher seeds before it reads. (Also check that `allowed`, if set, includes release-notes: a slash hit outside it falls through.) (facts §4a: act:105-113,177-197, skill-activator-allowed.test.ts:66-92)
