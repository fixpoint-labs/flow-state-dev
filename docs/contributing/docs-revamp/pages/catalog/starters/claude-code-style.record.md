## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You start the lab from inside your repository and ask desk.main to fix a failing test. It hands the change to desk.coder, which runs Claude Code. Where does that run make its edits, and does anything happen to the branch and files you have checked out?
   Answer: The run works in a git worktree of the project's repository, under the lab's data folder at <data>/runs (default .fsdev/claude-code-style/runs), on a branch of its own. You can find that branch in the repository. Your checked-out branch, index and working tree are never touched. A repository that is not on the lab's list (CLAUDE_CODE_STYLE_REPOSITORIES, which defaults to the repository the lab was started in) gets a clone under the data folder instead, each run on its own branch, and the repository itself is only read. If the project names checks, the run counts as done only when they pass in its worktree. A run that changed no files skips them. Facts 26-29, 34, 62.
2. You make a New project in the picker for a second repository, entered as file:///path/to/repo. You have just added .fsdev/ to its .gitignore but not committed it yet. What happens, and what would also be refused? *(edge case)*
   Answer: The picker checks the repository before Create, and the server refuses the same project (repository-unusable). Your case is refused because the rule is written but not committed: a run's checkout is cut from the last commit, so you must commit the .gitignore change. The other two refusals are a path that is not a git repository and a .gitignore that does not ignore .fsdev/. Only file:// repositories are allowed, so a remote address cannot be used either. Once the repository is usable, the picker says its runs work in their own worktrees. Facts 30-32.
3. In your own app built from these pieces, you want a Codex coder beside desk.coder (Claude Code). What do you add?
   Answer: First, fill the harness kit's slot with the Codex harness value: fill: { [harnesses.slots.harnesses]: [codexHarness()] }. Codex is a plain value, not a kit, unlike claudeCode, which fills the slot itself. Second, add a worker such as desk.coder-codex whose WORKER.md has flow: coder and harness: codex. It needs no new flow, because the harnesses kit installs the one coder flow. Third, put it in desk.main's delegates and say in the brief when to use it (for example, on a 'Coder: Codex' line). Fourth, sign Codex in on the machine (CODEX_API_KEY or codex login). In the lab all of this is already done for Codex and Cursor. The Coder chip's choices are a fixed list in the lab's source, so a harness of your own also needs a chip choice added there. Facts 4, 18-19, 46, 48.
4. You add desk.coder-codex with harness: codex but forget to put codexHarness() in fill. Later you fix that, but the machine has no Codex sign-in. What happens in each case? Does the task fall back to Claude Code? *(edge case)*
   Answer: Without the fill, the app refuses at start: a worker that names a harness nobody filled is refused, and the refusal names codex and the harness. With the fill but no sign-in, a task sent to that coder fails at once and says why. It never moves to another harness, so there is no fallback to Claude Code. The harness kit's readiness check, logged as a table at start, shows which harnesses can run on the machine. It never stops the app. Facts 20, 22, 23.
5. You want desk.main to send every code change to desk.coder-plan before desk.coder. Where do you make that change, and what does desk.main run on? *(edge case)*
   Answer: Edit the brief in workforce/teams/desk/workers/main/WORKER.md. A worker is a folder with a WORKER.md: frontmatter (description, delegates, capabilities), then the brief as the body. The workers it may hand work to are its delegates list, which already includes desk.coder-plan. The brief decides routing, including what a 'Coder:' line means. desk.main has no flow: line, so it runs on the built-in agent flow. Its current brief tells it to read the project's files itself and send code changes to desk.coder. It also tells it that a background task sees only its goal, so the goal must name every id, link and what done means. Facts 42-47.
6. A teammate wants to use the lab on your machine with their own sign-in, see a diff of each run, approve each tool call a run makes, and set the project's test command as its checks. Which of these work today? *(edge case)*
   Answer: None of them. The lab takes every request as one user (CLAUDE_CODE_STYLE_USER, default u_lab) in one organization, with no sign-in, so your teammate sees and acts as that same user. There are no file diffs of a run: the review shows the branch, commits, the judge's verdict and the checks. There are no permission prompts: Claude Code runs in acceptEdits, or plan mode for the plan worker, with nobody approving tool calls. Checks cannot be set from the lab, because the New project form has only a name and a repository. Repositories are file:// only. Harness readiness and linked pull requests are wired: a task whose run opened a PR stays open until the PR merges. Facts 2, 41, 60, 69-74.
