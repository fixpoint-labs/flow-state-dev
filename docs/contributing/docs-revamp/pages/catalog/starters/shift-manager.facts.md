## Flags against the page plan (read first)

1. **The keys route is not in the published package, so "Your own keys" has no install path for a reader.** The page behind Settings is `sm/src/surfaces/Settings.tsx`. It reads and writes `/api/flows/mcp-credentials` (`sm/src/lib/mcp-credentials.ts:20`). That route is served by `mcpCredentialsAdapter` (`mcpr:48`), which `openLab({ mcpServers })` installs (`sm/teams/devteam/host.mts:1350`). Both live under `teams/`, and `package.json` `files` ships only `dist`, `dist-client` and `profiles` (`sm/package.json:38-45`). `rd:238` says "A Lab opened with `openLab({ mcpServers })` serves the route" (the user docs `ov` and `st` name no host), and `openLab` is not exported by any published package. Grep of `packages/*/src` finds `mcpCredentialsAdapter` nowhere. What is published: `mcpCredentialsCapability`, `defineMcpCredentialsCollection`, `MCP_CREDENTIALS_PREFIX`, `mcpCredentialProblem` from `@flow-state-dev/workforce` (`mcpw:32-86`; re-exported at `packages/workforce/src/projects/index.ts:77`), and the Claude Code resolver `apps/docs/docs/workforce/projects.md:820`. **A reader with a published install and their own Lab gets a Settings screen that says "No MCP servers" (404 from the route, `sm/src/lib/mcp-credentials.ts:42-43`) unless they write the route themselves.** The page can state what Settings does and the 404 case. It cannot tell a reader how to turn the route on. **[gap]**. The page's third question ("Where do you set a key for a tool a coding run uses?") is answerable ("Settings") but only for a Lab whose host serves the route. **[reconcile]** whether the route moves into a published package or the page says it is a feature of the repository's `devteam` and `fsd` profiles.
2. **No minimal Lab config that works from a published install is citable.** Every Lab config in the repository is a checkout file: `sm/teams/devteam/fsdev.config.mts` (SQLite, host module, `openLab`), `sm/test/fixtures/multi-worker-collab/fsdev.config.mts` (imports `./host.mts`, `./piece.mts`, test helpers). `rd` shows a config as `import { openLab } from "./host.mts"` and `export default lab.state` (`rd:77-83`, quoted as "the Lab's own assembly"). The only whole-config example in a user doc is two excerpts of that shape. A Lab needs, besides the `FlowState` default export, an open inventory (`ov:98`) and `devtool: { userId }` (`ov:99`); the `workforce` kit does not open the inventory (grep of `packages/workforce/src/kit/workforce-kit.ts` for `inventory`: no match). So "a Lab's config" as the page's example must be one of: the `export default lab.state` shape with its host out of view, or the `createFlowState` snippet at `rd:111-118`, which shows only `resolvePrincipal`. **[gap]** for a complete runnable config. The page may show the three-line shape and say what the config must provide (facts 2.1 to 2.5).
3. **"Starter template" has no install line beyond the package.** Shift Manager is `@flow-state-dev/shift-manager`, `"private"` unset, version `0.2.1`, `bin: shift-manager` (`sm/package.json:2-3,34-36`), so it is the one starter published to npm (K-01's flag 2 says labs are private; this one is not). It is not a copy-and-edit app: `main` is `./cli/index.ts`, whose only exports are `getAssetPath()` and `getSourceRoot()` (`sm/cli/index.ts:22,36`), and the pages ship built (`ov:13`). **[page]** "You do not edit it; you point it at your config." There is no documented way to change its screens in an install. **[gap]** for "change it".
4. **"Lab" (the plan's unsettled item).** The word is used by the glossary, the overview, the README, the package description and the UI ("This Lab declares no shift coordinator", `sm/src/gaps.ts:76`). Citable definitions: "The server one `fsdev.config.mts` default-exports, which Shift Manager serves and reads." (`gl:144`); "A team is served as a **Lab**: one `fsdev.config.mts` that default-exports a `FlowState` holding the team's workers" (`ov:9`); "a set of Workforce workers from one `fsdev.config.mts`" (`rd:3`). Dropped, the replacement is "your config's `FlowState`", which is what the UI and the command line also call "the Lab" (`bin:113`: "Pass --config <path to the Lab's fsdev config>"). **[reconcile]** the owner's pick; the sheet supports either.
5. **The Shift Coordinator is not special to the framework.** Nothing in the framework treats `shift-coordinator` as a built-in. `sc:31`: "There's no switch for it: a Shift Coordinator is a worker your files declare, like any other." 9. **Existing page claims the code contradicts or cannot back.** (a) `ov:56` says the Shift Coordinator screen opens at `/`; true (`sm/test/shift-coordinator.test.ts:18`: "opens Shift Coordinator at /, at /shift-coordinator and at any path Shift Manager doesn't know"). 10. **A coding run's own tools: the plan's question 3 asks where to set a key for "a tool a coding run uses".** Only MCP servers a project names are covered, and only Claude Code runs get them (`apps/docs/docs/workforce/projects.md:818`: "Only Claude Code runs get a project's servers. ## 1. What it is, and what you point it at

- 1.2 A team is "served as a **Lab**: one `fsdev.config.mts` that default-exports a `FlowState` holding the team's workers." `ov:9`. Equivalent: `gl:144`, `rd:3`. **[page]** (the one definition; see flag 4)
- 1.3 "It knows nothing about any particular Lab. Every name on screen is read from the Lab while it runs." `ov:11`; same `rd:7`. **[page]**
- 1.4 "It stores nothing of its own: every screen is a read of the Lab it serves." `gl:140`. **[page]**
- 1.5 It is research software; "several screens are placeholders that say what will fill them." `ov:13`, `ov:106-112`. The lists of what is not there yet are task-screen items (Hand off, reassign, Open PR disabled; Diff, Checks, acceptance criteria, reviewer, harness, tokens and cost empty), a workstream's Results tab, and the IN REVIEW column (`ov:110-111`; `columns.ts:7-9`). **[page]** one clause; the list **[ref]**.
- 1.6 Published to npm as `@flow-state-dev/shift-manager`; "The pages ship built, so there is nothing to compile." `ov:13`. Node `>=22`. `sm/package.json:57-59`. **[page]**
- 1.7 Install and run: `npm install @flow-state-dev/shift-manager`, then `npx shift-manager --config ./fsdev.config.mts`. `ov:20-21`; `rd:16-17`. **[page]** (the example)
- 1.8 The command's synopsis: `shift-manager [--config <path>] [--port <n>] [--host <host>] [--shift <day|evening|night>] [--dev] [--assets <dir>] [--no-open]`. `bin:5-6`. Options parsed, strict, no positionals: `bin:91-103`. An unknown flag is refused: `cmd:191-197` (`--team`, `--devtool`, `--devtool-assets` named). **[page]**
- 1.9 What you point it at is a config file. Without `--config`, it looks in the directory you ran it in for `fsdev.config.ts`, `.mts`, `.js` or `.mjs` (`packages/fsdev/src/load-config.ts:23-28`; `ov:24`; `bin:111`). With none: stops with "No fsdev config in <dir>. Pass --config <path to the Lab's fsdev config>." (`bin:113`), exit code 3 (`bin:31`; `cmd:152-162`: "without one refuses, naming --config"). **[page]**
- 1.10 A relative `--config` resolves from the directory you ran the command in; the process runs from that directory, "so a Lab's relative paths, such as a SQLite file, land where they would under `fsdev dev`." `bin:24-27,108,116-117`; `ov:28,36`; `cmd:164-167`. **[page]** (one sentence; this is where a reader's `.fsdev/` file lands)
- 1.11 A config that doesn't load, or doesn't default-export a `FlowState`, "stops the command with the loader's message", exit 3. `ov:36`; `cmd:169-178`. **[ref]**
- 1.12 It prints its address, `http://127.0.0.1:4300` by default, and opens it. `ov:24`; default `"4300"` at `bin:94`. `--port 0` picks a free port (`ov:29`). `--no-open` skips the browser (`bin:99,124`; `ov:34`). **[page]** address and port; the option table **[ref]**.
- 1.13 One process serves three things: the Lab's API under `/api/flows`, Shift Manager's pages, and the DevTool over the same Lab on a port of its own. `ov:24`; `bin:8-11`; `cmd:88-96` (`/api/flows/sessions` answers 200 and the page serves), `cmd:98-122` (the DevTool sees the same sessions as the app). **[page]**
- 1.14 Without the DevTool's pages installed, Shift Manager still starts, says so, and turns *Open trace* off; install `@flow-state-dev/devtool` for them. `ov:38`. In `package.json`, `@flow-state-dev/devtool` is a dependency (`sm/package.json:71`). **[ref]** (the docs say it can be missing; a plain install lists it as a dependency, so a reader rarely meets this) **[gap]** whether a published install can lack it.
- 1.15 Default host `127.0.0.1`. A non-loopback `--host` is refused unless the Lab authenticates requests, and always refused for a Lab that hands its page a bearer token. `ov:30`; `cmd:124-132` ("Refusing to bind 0.0.0.0: this config hands its page a bearer token"), source `packages/fsdev/src/commands/dev.ts:365-368`. **[ref]** (one clause on the page: it serves your machine only, by default)
- 1.16 `--dev` restarts the Lab when you save a file it loaded (a flow module, or a file under the config's folder such as a `WORKER.md`), reloads the page, and does nothing for a file the Lab didn't load or its data file. A restart is a new process: a Lab with in-memory stores starts empty each time, so use SQLite to keep data across edits. `ov:42-44`. Loopback only: refused on a network host, exit 3 (`cmd:213-220`). **[page]** (the one dev loop a reader wants; short) / the rest **[ref]**
- 1.17 `--shift <day|evening|night>` (or `SHIFT_MANAGER_SHIFT`, flag wins) sets the starting theme; an unknown name is refused with "No shift "<name>". Known shifts: ..." and exit 3. `bin:46,78-86`; `cmd:134-150`. **[ref]**
- 1.18 `--assets <dir>` serves a different build of the pages. `bin:16-19,125`; `ov:33`. **[ref]**
- 1.19 What the config has to provide (the page may list the first four): `ov:92-104`.
  - 2.1 **A `FlowState` as the default export, with a store.** `inMemoryStores()` gives an empty Lab on every start; `sqliteStores` or `postgresStores` keep what it holds. `ov:96`; table at `rd:100-106` (adapters and imports: `@flow-state-dev/engine`, `@flow-state-dev/store-sqlite`, `@flow-state-dev/store-postgres`).
  - 2.2 **An organization**, from `resolvePrincipal` on `createFlowState`; without one the Lab runs in the development organization `DEFAULT_ORG_ID`. `ov:97`; `rd` "An organization".
  - 2.3 **An open inventory**, which TEAMS, Roster and Inbox read to find the workers. Without it, TEAMS says there is none and the rest loads. `ov:98`; `rd` ("Without an inventory, TEAMS says there is none to read, and the other sections load"). The inventory is the org's record of the workers your files declare (`apps/docs/docs/workforce/inventory.md:5,12,20`).
  - 2.4 **Who Shift Manager reads as:** `devtool: { userId }` on `createFlowState`, plus `bearerToken` when the resolver checks one; handed to the page only on a loopback host. `ov:99`; `cmd:124-132`.
  - 2.5 Optional: a Shift Coordinator (fact 3), a `harnessUsage` action for Usage, a `workerUsage` action for *Usage by worker* (`ov:100-102`). **[ref]**
- 1.20 The kit-based route is not wired for a Lab: the `workforce` kit reads the app's `workforce/` folder and serves the worker flows and the roster flow (`packages/workforce/src/kit/workforce-kit.ts:1-10,174-184`) but its source has no `openInventory` call. **[gap]** whether a `kits: [workforce(...)]` config is enough for Shift Manager; nothing citable says it is.

## 3. The Shift Coordinator

- 3.1 **How Shift Manager finds it.** It talks to the worker named `shift-coordinator`: an org worker (`org/workers/shift-coordinator/`) or a team's worker (`<team>/shift-coordinator`). `sm/src/lib/shift.ts:158` (`SHIFT_COORDINATOR`), `shift.ts:175` (`shiftCoordinatorOf`); `sm/test/shift-coordinator.test.ts:45-64`. "Declare one on the coordinator flow at org/workers/shift-coordinator/." `sm/src/gaps.ts:76-77`. Wherever Shift Manager names a worker (Roster, Inbox, Jump to) it shows this one as "Shift Coordinator" (`shift.ts:163`, `workerLabel`). **[page]**
- 3.2 **It is optional.** A Lab with no `shift-coordinator` worker still opens on that screen: "You get the summary, and in place of the conversation a line saying how to add one." `ov:56`; `sm/src/gaps.ts:75-78` (title "This Lab declares no shift coordinator"); `rd` "A Lab with no Shift Coordinator needs nothing in its config." That message needs an open inventory; with no inventory the conversation area shows an error about the inventory instead (`rd`, same paragraph). **[page]**
- 3.3 **Two of that name:** "More than one worker is named shift-coordinator, so Shift Manager talks to neither:" and it lists their ids. `sm/src/gaps.ts:79-81`; `sm/test/shift-coordinator.test.ts:51-57`. **[ref]**
- 3.4 **What it is:** "an org-level worker a user talks to about the organization itself and about getting work done." `sc:10`. It is not a framework built-in: "There's no switch for it: a Shift Coordinator is a worker your files declare, like any other." `sc:31`. A Lab that doesn't declare one doesn't have one (`sc:21`). **[page]**
- 3.5 **What it does that an ordinary worker does not, by its declaration.** These are what its file grants, not a built-in:
  - 3.5a **It is the only worker that hires or fires.** A worker holds `hire` or `fire` "only when its own `tools:` names it, so keep those names in the Shift Coordinator's file and no other." `sc:169`. The repository's file: "You are the only worker that hires or fires." `wm:88`. `tools: [hire, fire, listProjects, createProject, setRepository, listLeads, openWorkstream, memory/recall, listRoutines, saveRoutine, pauseRoutine, deleteRoutine]` `wm:10`. **[page]**
  - 3.5b **A hire belongs to the user it is talking to:** "it is on their roster and nobody else's." `sc:21`; `wm:88-90`. **[page]**
  - 3.5c **A fire waits for your approval.** The ask shows in Inbox; "nothing is removed until they approve"; if you deny it, nothing changes. `sc:18,293-314`; `wm:103-107` ("`fire` itself asks the user to approve in their Inbox"). That wrapper is the app's to write: `fire` as shipped "never asks" until wrapped (`sc:281-282,320`). **[page]** (it is why Inbox matters)
  - 3.5d **It can't fire itself or any worker declared in files**; "those change when someone edits their folder." `sc:324`; `wm:108-109`. **[ref]**
  - 3.5e **It starts projects and opens workstreams** (`createProject`, `openWorkstream`, `setRepository`), once given those tools. `sc:19,201-227`; `wm:111-135`. A repository is approved by the user in Inbox before it is written (`wm:133-135`). **[ref]** → K-10.
  - 3.5f **It hands work to delegates:** on the `coordinator` flow, `delegates: [eng.em, eng.coder]` are the workers it hands this conversation's work to; a delegate's answer lands in the conversation under its name; the Shift Coordinator can add a delegate from the user's roster only with `editsOwnDelegates: true`. `sc:10-17,70`; `wm:7-8,28-43`. The ordinary worker on the `agent` flow has no delegates and hands nothing on (`sc:23`). **[page]** one sentence; coordinators → K-06.
  - 3.5g **It keeps standing rules per user:** "Tell the Shift Coordinator how you want it to work ... and it keeps the note as a standing rule for you. Your rules are yours: another user on the same Shift Manager has their own." `sc:275`. The gear in its header opens its settings, where its standing rules are (`ov:56`; `sm/src/surfaces/ShiftCoordinator.tsx:106-116`, `data-testid="shift-coordinator-settings"`). **[ref]**
  - 3.5h **Memory:** none unless added; `memory/recall` and a `<memory>` context. `sc:231`. **[ref]**
- 3.6 **What Shift Manager adds around it, which an ordinary worker's screen lacks.**
  - 3.6a The shift summary above the conversation is "Shift Manager's own", drawn from the Lab's reads, not the worker's words: how many asks wait on you (each with the same Approve and Reject as Inbox) and how many runs are going across how many workstreams. `sm/src/surfaces/ShiftCoordinator.tsx:7-11,133-138`; `rd` "Shift Coordinator". Answering an ask there clears it in Inbox (`ShiftCoordinator.tsx:9-11`). **[page]**
  - 3.6b The DELEGATES panel in the right panel, when the worker runs on the `coordinator` flow: lists who it hands this conversation's work to, add a worker from your roster, or remove one; a refused add shows the reason. `ov:56`; `sm/test/coordinator-view.test.tsx:82-147`. **[ref]**
  - 3.6c TASKS in the right panel: tasks your conversation filed for its delegates. `rd` "Below DELEGATES, TASKS lists...". **[ref]**

## 5. Stored parts (the four questions)

For each: owner, who can see it, where stored, how many.

### 5.1 A user's MCP key
- **Owner:** the user who set it; their user scope. `mcpw:5` ("at user scope: one record per server the user set a key for"); `mcpr:12-13`. The caller is the user the Lab's principal resolver verifies from the request, "never a field of the body or the path". `mcpr:15-16`.
- **Who can see it:** nobody through any screen or route. A browser read of the record returns `setAt` only (`mcpw:11-12`, `mcpw:55` `expose: ["setAt"]`); the value is declared `secret`, "which keeps it out of the engine's debug reads" (`mcpw:13-14,54`); the collection "is not `llmReadable`, so no resource tool lists or reads it" (`mcpw:22-23`). The one reader of the value is the server step that connects a run's servers (`mcpw:17-19`). Anyone who can read the Lab's store can read it: "The value is the key as the user wrote it, unencrypted, in the host's store" (`mcpw:8-9`); same warning for a run that has a shell and no sandbox (`projects.md:816`). **[page]** (state the plain-text limit flat)
- **Where stored:** in the Lab's own store (whatever the config's `stores` picks), as a record `mcp-credentials/<server>` at user scope (`mcpw:34-35`; `mcpr:98,143`). It is not a request, so it is kept on no request record: the route "is a transport adapter's own: no request is dispatched, no record is written" (`mcpr:9-13`). On `inMemoryStores()` it lasts until the process stops (`rd` adapter table); on SQLite or Postgres it survives a restart. **[page]**
- **How many:** one per server per user. `mcpw:5`. `mcpt:179-199`.

### 5.2 The theme pick
- **Owner:** the browser. **Who sees it:** that browser only. **Where:** `localStorage` key `shift-manager:shift` (`sm/src/lib/theme.ts:40,119,152`). **How many:** one. With storage blocked, boots on the served or clock theme and "the pick just isn't kept" (`sm/test/theme.test.ts:229-241`). **[ref]**

### 5.3 Collapsed sidebar and right panel
- **Owner:** the signed-in user, in that browser. **Where:** `localStorage` key `shift-manager:panels:<userId>`, `{ nav, panel }` (`sm/src/lib/panels.ts:26-45`). **Count:** one per user per browser; another user in the same browser has their own (`ov:74`; `rd` "Collapsing..."). **[ref]**

### 5.4 Everything else (asks, tasks, projects, conversations)
- Shift Manager owns none of it. It is the Lab's data, in the Lab's store, read through the Lab's routes: "Shift Manager reads a Lab only through the routes its `FlowState` serves. It builds nothing for the Lab." `ov:94`; `gl:140`. Who sees what is the Lab's rule: the Shift Coordinator conversation is yours ("your newest session ... that names it", `rd`); Inbox lists asks in sessions you started, not another user's (`sm/src/gaps.ts:85-86`); a private project is listed for its owner alone (`projects.test.tsx:218`); a shared project is the organization's (`ov:60`). **[page]** (one sentence: the Lab keeps your data; closing Shift Manager loses nothing)
- Whether a restart loses it is the store's: in-memory stores start empty on each start (and on each `--dev` restart); SQLite or Postgres keep it. `ov:44,96`. **[page]**
