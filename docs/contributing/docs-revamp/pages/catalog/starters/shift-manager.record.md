## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You have a team's workers declared and a fsdev.config.mts in your project folder. What do you point Shift Manager at, and what does that config have to provide for the Inbox and Roster to show your workers?
   Answer: You point it at a Lab: one fsdev.config.mts that default-exports a FlowState holding the team's workers (fact 1.2). Run `npx shift-manager --config ./fsdev.config.mts`, or run it with no flag from the folder that holds the config, since it looks there for fsdev.config.ts/.mts/.js/.mjs (1.7, 1.9). The config must default-export a FlowState with a store, give an organization (from resolvePrincipal, or else the development org), open an inventory, which TEAMS, Roster and Inbox read to find the workers, and set `devtool: { userId }` so Shift Manager knows who it reads as (1.19, 2.1 to 2.4). Shift Manager itself stores nothing and knows no Lab ahead of time. Every name on screen is read from the Lab while it runs (1.3, 1.4).
2. You run `shift-manager` from a folder that has no fsdev config in it. What happens? *(edge case)*
   Answer: It stops with "No fsdev config in <dir>. Pass --config <path to the Lab's fsdev config>." and exit code 3 (fact 1.9). A config that loads but doesn't default-export a FlowState also stops the command with the loader's message, exit 3 (1.11).
3. What does the Shift Coordinator do that an ordinary worker on your roster does not, and what does the framework itself do to make it special?
   Answer: The framework does nothing special. It is a worker your files declare like any other, and there's no switch for it (3.4, flag 5). Shift Manager talks to the worker named `shift-coordinator` and opens on its screen (3.1, 2.1). What sets it apart comes from its own file's `tools:`. It is the only worker that hires or fires. A hire goes on the roster of the user it is talking to and nobody else's. A fire waits for your approval in Inbox, and nothing is removed until you approve (3.5a to 3.5c). On the `coordinator` flow it hands work to delegates, which an ordinary `agent`-flow worker doesn't do (3.5f). Shift Manager also puts its own summary of the asks waiting on you and the runs going above the conversation, and shows your newest conversation with that worker (3.6a, 3.7).
4. Your Lab has no `shift-coordinator` worker. What do you see when Shift Manager opens, and how would you add one? *(edge case)*
   Answer: It still opens on the Shift Coordinator screen. You get the summary, and in place of the conversation a line saying how to add one ("This Lab declares no shift coordinator") (3.2). That line needs an open inventory. Without one, the conversation area shows an error about the inventory instead (3.2). To add one, declare a worker in `workforce/org/workers/shift-coordinator/WORKER.md` with front matter such as `description`, `flow: agent` and a `model`, plus a body. The folder name is the worker's id (3.9, 3.11).
5. Your project's Claude Code runs need to use Linear's MCP server. Where do you set your Linear key, and what will you see in that place later?
   Answer: In Settings, which lists each MCP server the Lab offers and whether you've set a key, with the date you set it (4.1). You type the key into a password field and press Set. After that the row shows `set · <date>`, and you can Replace or Clear the key (4.3). The page never shows a key back, not even its last characters, so keep your own copy (4.4). Both parts are needed: the project has to name the server and you have to set a key. Without the key, each run's session says it goes without the server (4.6). Only Claude Code runs get a project's servers. A Codex or Cursor run works without them and says so (4.8). The coding agent's own sign-in, such as ANTHROPIC_API_KEY, is not set in Settings (flag 10). If the Lab offers no MCP servers, Settings says "No MCP servers" and there is no key to set (4.9).
6. A teammate uses the same Shift Manager and Lab as you. You have set a Linear key and they have not. Does their run use your key, do they see your asks in their Inbox, and does Shift Manager keep a copy of either? *(edge case)*
   Answer: No to the first two. Your keys are yours: a run you ask for uses them and nobody else's run does. Their Settings shows `not set` until they set their own, and setting or clearing theirs leaves yours alone (4.5). Inbox lists asks in sessions you started and the runs those started, and not another user's (2.2). The run itself never gets the key. The Lab connects to the server and hands the run only the server's tools (4.7). Shift Manager keeps no copy. The key is a record in the Lab's own store at your user scope, stored as you typed it without encryption, so anyone who can read the Lab's store can read it (5.1). On in-memory stores it lasts until the process stops. SQLite or Postgres keep it across a restart (5.1, 5.4).
