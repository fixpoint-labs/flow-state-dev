## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You have a chat generator and an `artifacts` collection (pattern `artifacts/**`, session scope). You want the model on that generator to be able to run shell commands. Which line do you add, where, and what do you import?
   Answer: Add `uses: [bashCap]` on the generator, where `bashCap = createBashCapability(...)` imported from `@flow-state-dev/tools/bash`. Bash is a capability in `uses`, not an entry in `tools: [...]`, and it gives the model three tools: `bash`, `bash-read-file`, `bash-write-file` (F1, F3, F4, F6).
2. During a request the model runs `echo '# Plan' > artifacts/plan.md`. The request ends. Where is plan.md now, and will the next request in the same session see it?
   Answer: It is a row in the `artifacts` collection (stored as `plan.md`, prefix removed), saved right after the command finished, because the collection is mounted at `artifacts/` and changed files are flushed after every `bash` command and every `bash-write-file`. The collection is the copy that survives; the sandbox is only working space. Who else sees it depends on the collection's scope, here the session (Files section; F14, F17, F18, F26).
3. The model writes `notes.txt` in the workspace root and also `scratch/out.log` and `tmp/build.log`. Which of these are saved after the run, and is anyone warned? *(edge case)*
   Answer: None of them are saved. `tmp/` is scratch, never saved and no warning. `notes.txt` is an orphan (outside every mount), dropped with a warning naming it. `scratch/out.log`, in an unmounted subdirectory, is dropped with no warning. Only files under a mounted collection's prefix are saved; the model is told this up front in its guidance (F11, F21, F22).
4. You call `createBashCapability()` with no options and the model tries `npm install` and `curl https://example.com`. What can this sandbox reach, and what would you change to get the host's real binaries?
   Answer: The default provider is `just-bash`: an in-process bash emulator with 60+ built-in commands, files in memory, no real processes, it cannot install packages, and it has no network unless you allow `network.allowedUrls` (or full access). For real host binaries use the `local` provider, a real `/bin/bash` on the server host as the server's user, which is not an isolation boundary; a container (`moat`) or remote (`vercel`) sandbox are the other choices (F8, F31, F32, F35, F36, F39).
5. Two requests (two runs) touch the same `artifacts/plan.md`. While the first run held the file, the second saved a new version. The first run then calls `bash-write-file` on plan.md, and later edits it again with an `echo >` command. What happens to each save, and what does the model learn? *(edge case)*
   Answer: Neither overwrites the newer copy: the flush leaves the collection's version, keeps both copies, and warns naming the path (a conflict). `bash-write-file` returns `{ success: false, refused: ... }` saying the write was not applied, so the model is told. The `bash` command reports nothing: it still returns its `stdout`, `stderr`, `exitCode`, and the refusal is only a logged warning (F27, F28, F29).
6. You mount a `skills` collection as `{ key: "skills", writable: false }` beside `artifacts`, and the model edits a file under `skills/` with a command that exits non-zero. What does the command return, and does the edit reach the skills collection? *(edge case)*
   Answer: A non-zero exit does not throw: the tool returns `{ stdout, stderr, exitCode }` with the non-zero code. Edits under a read-only mount stay in the sandbox and never reach the collection (and a `bash-write-file` there is refused as readonly) (F24, F28, F46).
