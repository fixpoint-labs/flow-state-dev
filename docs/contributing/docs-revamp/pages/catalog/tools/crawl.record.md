## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You give a docs assistant `crawl({ includePatterns: ["/docs/**"], excludePatterns: ["/docs/changelog/**"] })` and the model calls it on `https://site.com/docs/start` with `maxDepth: 1`. Which pages can come back, and how many at most if it passes no `maxPages`?
   Answer: The root and the same-origin pages it links to directly (one hop; the root is depth 0, F12), and only those whose path matches `/docs/**` and not `/docs/changelog/**` (exclude wins, F24). Patterns match the URL's path only (F22). With no `maxPages`, at most 20 pages come back (default 20, F7), counted as pages actually returned (F11), and when the limit cuts the crawl short the deepest pages are the ones left out, because the crawl is breadth-first (F13).
2. A page on the same site links to `/docs/api/ref`, `/docs/changelog/v2`, `https://blog.site.com/docs/post`, `mailto:team@site.com` and `/docs#intro`. Which of these does the built-in crawler follow under the pattern above?
   Answer: Only `/docs/api/ref`. `/docs/changelog/v2` matches the exclude pattern, and exclude wins (F24). `blog.site.com` is another origin (a subdomain counts), so it is dropped (F18). `mailto:` is not http(s) and is skipped (F19). `/docs#intro` loses its fragment and becomes `/docs`, which `/docs/**` does not match because the pattern needs the slash after `docs` (F16, F23).
3. You point the same patterned crawl at the site root, `https://site.com/`, and get back `pages: []` and `totalPages: 0`. Nothing threw. What went wrong, and how do you fix it? *(edge case)*
   Answer: The root itself is checked against the patterns before it is fetched. `/` does not match `/docs/**`, so the root is never fetched and none of its links are followed, and the result is empty (F25). A failure on the built-in crawler does not throw; it gives an empty `pages` array (F28). Start the crawl at a URL under the include path, such as `https://site.com/docs/start` (F25).
4. Your app has no `FIRECRAWL_API_KEY`, and a teammate swaps `crawl(...)` for `firecrawlCrawl(...)`. The app starts fine, but the first time the model crawls, the call fails. Why, and what would `crawl(...)` with no `provider` have done instead? *(edge case)*
   Answer: `firecrawlCrawl()` builds without complaint but throws at call time when no key is found: `Crawl provider "firecrawl" requested but no API key found. Set FIRECRAWL_API_KEY or pass it via config.keys.firecrawl` (F34). It also needs `@mendable/firecrawl-js` installed (F35). With no `provider`, `crawl` looks for `config.keys.firecrawl`, then `FIRECRAWL_API_KEY`, and falls back to the built-in crawler when it finds neither, so auto-selection never throws (F32). The provider is chosen on each call, so setting the env var later takes effect without rebuilding the tool (F34).
5. The site you need to crawl is a single-page app that draws its content and links with JavaScript, and it lives on a public host. Should you use the built-in crawler or Firecrawl, and why?
   Answer: Firecrawl. The built-in crawler reads only the HTML the server sends, so links and content a script adds are not seen, and `waitForJS` is ignored by it (F19, F38, F17). With Firecrawl, `waitForJS: true` asks the service to wait 5000 ms per page (F17). The built-in crawler also fetches one page at a time with a fixed 1-second pause, has no cookies or auth, and stays same-origin (F14, F38). The page recommends Firecrawl for production and the built-in crawler for development (F39).
6. During development you point the built-in crawler at `http://localhost:3000/docs` to test your own site. What do you get, and does switching to Firecrawl help? *(edge case)*
   Answer: An empty result, with no error: the built-in crawler refuses `localhost` and any host that resolves to a private address before it connects, so no request is made and `pages` is empty (F26, F28). Firecrawl is not blocked by that check, but it runs on the vendor's service, not on your network, so it cannot reach your localhost either (F37).
