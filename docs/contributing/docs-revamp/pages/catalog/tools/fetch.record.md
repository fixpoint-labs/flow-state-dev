## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You add `tools.fetch()` to a generator's `tools` list and deploy with no FIRECRAWL_API_KEY or JINA_API_KEY set and no `provider` in the config. The model calls fetch on a public article URL. Does the call work, and how can you tell from the result which provider served it?
   Answer: It works: with no provider named and no key, fetch falls back to the built-in provider and never throws a 'no provider available' error (F10; auto-order is Firecrawl if its key exists, else Jina if its key exists, else built-in, F11). The result's `source` field names the provider that served it, here `"builtin"` (F18, F19).
2. A teammate sets `fetch({ provider: "firecrawl" })` but forgets to set FIRECRAWL_API_KEY on the staging host. What happens when the model calls the tool, and is it the same kind of error as a failed page fetch? *(edge case)*
   Answer: The call throws at call time with a plain `Error`: 'Fetch provider "firecrawl" requested but no API key found. Set FIRECRAWL_API_KEY or pass it via config.keys.firecrawl'. It is not a `FlowError` and carries no `details` or `retryable` flag, unlike a failed fetch (F14, F36). Naming a provider skips the fallback; only an unnamed provider falls back to built-in (F10, F11). Separately, Firecrawl also needs the optional peer package `@mendable/firecrawl-js` installed, or the call throws an install message (F16).
3. The model calls fetch on a page that answers 503, and on another that answers 403 with a bot-wall page. What does each call give back, and how does your code tell whether trying again makes sense? *(edge case)*
   Answer: Neither returns a result; each throws a `FlowError` (F34) with code `fetch_http_error` and `details` holding `errorType: "http"`, `httpStatus`, `httpStatusText`, `url`, and `responseBody` when the body is non-empty (F36). The 503 has `retryable: true` (5xx, 429 and 408 are retryable, F37); the 403 has `retryable: false`, and its `responseBody` holds the wall's text, capped at 1000 characters with `…[truncated]` (F38, F39). Read it with `error instanceof FlowError` and `error.details?.httpStatus`, `FlowError` from `@flow-state-dev/core` (F43). The flag is a field to read: the framework does not retry on it unless the flow sets `tools.defaults.retry`, and that filters by error class (F45).
4. Using the built-in provider, the model is handed `http://169.254.169.254/latest/meta-data` (or a public URL that redirects to 127.0.0.1). What happens, and would the same URL be refused on Firecrawl or Jina? *(edge case)*
   Answer: The built-in provider refuses it before any request reaches that address: it throws a `FlowError` with code `fetch_blocked_url`, `retryable: false`, `details.errorType: "blocked"` (F27, F36). Loopback, link-local (including cloud metadata), private and reserved ranges, and `localhost` are refused, and every redirect hop gets the same check, so a public page that redirects to 127.0.0.1 is refused with no request sent to it (F27, F30). Firecrawl and Jina are not subject to this check; the vendor fetches the page (F31). To read an intranet page on purpose, use your own handler (F32).
5. You want a research assistant that finds pages on the web and then reads the most relevant one in full. How do you give the model both abilities, and what keys do you need?
   Answer: Put both blocks in one `tools` array: `tools: [tools.search(), tools.fetch()]`. Search returns titles, URLs and snippets; fetch reads one URL's full page as Markdown. The model decides when to call each, with no wiring between them, and the names `search` and `fetch` do not collide (F46, F47). Keys differ: search throws when it finds no provider key, while fetch works with none, so the pair needs a search key but no fetch key (F48).
6. You only want the model to read pages from your own docs site, but it passes some other URL to fetch. Does fetch stop it, and how do you restrict it? *(edge case)*
   Answer: Fetch does not stop it: it takes whatever string the model gives as `url` and does not check that it came from a search result or an allowed host (F49). To restrict it, wrap the block: the kitchen-sink example routes the call through a host check and returns `{ refused: "..." }` for any other host, so nothing is requested, using `router`, `handler`, `fetchInputSchema` and `fetchResultSchema`, and renames the block with `.as({ name: "fetch-docs-page" })` (F8, F9, F49). The tool also sets no length limit on `markdown`, so each page lands whole in the model's context (F50).
