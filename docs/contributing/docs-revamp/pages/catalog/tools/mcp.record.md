## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support-desk generator has a Linear MCP server attached. For one turn, the model must not be able to call Linear's create-issue tool, but every other Linear tool should stay available. What do you set, what name do you use, and does Linear have to reconnect?
   Answer: Set `disabledTools` in the request's `mcp` state (`ctx.request.state.mcp`, declared by the capability), using the full namespaced name `mcp__linear__create_issue`, not the server's own tool name (F26, F27). The default filter narrows the tool list for that request only. It runs each time the tool list is built, so the connection and the cached tool list are kept and nothing reconnects (F28). To drop every Linear tool instead, put the server's `name` in `disabledServers`. Both arrays together apply as a union (F27). A name that matches nothing is silently ignored, so a typo fails quietly (F29). (The fact sheet flags that it has not settled how a caller's request sets this state, F30. A grader should accept 'a block earlier in the same request writes it' or 'a custom `filterTools`' as the route, but the field names, the namespaced-name rule and 'no reconnect' are required.)
2. Where in your code do you configure the Linear MCP server, and where does its API key go? Do you list it in the generator's `tools`?
   Answer: Pass it in the `servers` array of `createMcpCapability` (from `@flow-state-dev/tools/mcp`), one object per server: `{ name, transport, description?, whenToUse?, examples?, category? }` (F1, F9). `transport` is `{ type: "http" | "sse", url, headers? }`. `"http"` (Streamable HTTP) is the recommended default (F10). The key goes in `transport.headers`. The package supplies no key of its own, and the kitchen-sink reads it from an environment variable, `LINEAR_MCP_API_KEY` (F8, F13). You attach the capability with `uses: [mcpCap]`, not through `tools` (F1, F15). You also need the optional peer `@ai-sdk/mcp` installed (F7). As an alternative to `servers`, you can pass a `manager` from `createMcpManager({ servers })`, but you pass exactly one of the two (F12).
3. You have connected two servers, Linear and a docs-search server, and the model keeps reaching for the wrong one. What can you give it to help it pick the right tool?
   Answer: Each server can take four optional metadata fields, which are rendered into the system-prompt guidance block (F20): - `description` is shown as written. - `whenToUse` appears as "Use when: ...". - `examples` appear verbatim as bullets, for example a call shape like `mcp__linear__list_issues({ ... })`. - `category` groups servers under a heading. Each tool's description is also prefixed with its server name by default (`[linear] ...`). `enrichDescriptions: "category"` adds the category to that prefix, and `false` turns the prefix off (F25). Tool names themselves carry the server name: `mcp__<server>__<tool>` (F2). For full control, `formatGuidance` replaces the guidance block (F26a). The guidance arrives through the `guidance` preset, which is on by default (F5).
4. At startup the docs-search server is down but Linear is up. What does the model get, what do you see in your logs, and does the docs server come back by itself once it recovers? *(edge case)*
   Answer: Connection is lazy. Every server connects in parallel the first time the tool list is needed (F34). One failure does not stop the others: Linear's tools load. The docs server is marked `errored` and logs `[mcp] Failed to connect to "<name>": <message>`, and its error shows in `manager.getCatalog()` with header values (the key) removed (F35, F36). It is also left out of the guidance block (F24). It is not retried: the result is cached for the manager's life, and only `manager.close()` resets servers to `pending` so that the next `getTools()` reconnects (F37). There is no retry or reconnect option on the config (L2).
5. A teammate edits the generator that has `uses: [mcpCap]` and adds `tools: [lookupOrder]` for a new local tool. The Linear tools stop being called, but the model still seems to know Linear exists. Why, and how do you fix it? *(edge case)*
   Answer: A generator that declares a `tools:` list at all, even `tools: []`, receives only the tools that list names. That drops the capability's MCP tools (F16, L3). The guidance block is context, not a tool, so it still reaches the model. That is why the model still 'knows' about Linear (F18). The fixes are to remove the `tools:` list and deliver `lookupOrder` another way, or to name the MCP tools in the list yourself. A tool the block names survives (F17). The only handle for an MCP tool is one taken from `manager.getTools()`, and the fact sheet marks that route as unverified for MCP.
6. Each user should be able to switch Linear off for their whole session, so you write a custom `filterTools` that reads a flag from session state. Afterwards, requests that set `disabledServers` or `disabledTools` no longer narrow anything. What went wrong? *(edge case)*
   Answer: `filterTools: (ctx, tools) => ...` replaces the default filter completely. A custom filter that does not call the exported `defaultMcpFilterTools` no longer honors `disabledTools` or `disabledServers` (F31, F33). The fix is to compose over `defaultMcpFilterTools` inside your filter. `ctx` is a full block context, so `ctx.session.state` is readable. The session flag is your app's own field, though, and you must declare it in session state yourself (F32). `getMcpToolMeta(tool)` tells MCP tools apart from your own, and returns `null` for non-MCP tools (F46).
