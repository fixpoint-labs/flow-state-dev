## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Two runs hydrate the same `artifacts` collection and both edit `spec.md`. Run A flushes first, then run B flushes. What does each flush report, and whose `spec.md` is in the collection afterwards? *(edge case)*
   Answer: A's flush reports `written` for `artifacts/spec.md` (the collection still held what A's projection laid down) and A's content lands. B's flush reports a `conflict` on `artifacts/spec.md`, and the collection keeps A's content. B's flush still succeeds: everything else B changed that nobody contested still lands, and the conflicting path is left as both writers left it (W18, W19, W21).
2. Run B's flush comes back with a conflict on `artifacts/spec.md`. What does the conflict entry give you to work with, and does `flush()` reject?
   Answer: `flush()` resolves, it never rejects on disagreement, with `{ outcomes, conflicts, contested }`; `conflicts` is the filtered subset of `outcomes`. The conflict entry has `path`, `base` (what the projection last committed, or `null` if it never laid the path down), `theirs` (what the collection holds now, or `null`) and `ours` (what the place holds now, or `null` if deleted). All three are SHA-256 hex hashes of the content, not the content itself (W20, W30, C2).
3. Both runs flush `spec.md` at the same moment rather than one after the other. What does the losing run see, how is that different from a conflict, and what should it do? *(edge case)*
   Answer: The loser gets `contested` for that path (an outcome with only `kind` and `path`). A conflict means somebody already wrote, and three hashes describe it. Contested means somebody is writing right now, so there is nothing to compare yet. Nothing is written for the contested path, and the other run's write stands. The loser's edit is still in its own place, so it can retry the flush (W24, W26, C5). Arbitration only works inside one process: two servers writing one collection are not arbitrated (W47).
4. An agent deletes `notes.md` from its working directory before flushing. When does the flush delete the stored entry, and when does it leave it alone? *(edge case)*
   Answer: The flush deletes the collection entry and reports `deleted` only if the projection laid the path down (it is in the baseline), the mount is writable, and the stored content still hashes to the baseline. It also reports `deleted` if the entry is already gone from the collection. If someone else edited `notes.md` in the collection meanwhile, the flush reports a `conflict` with `ours: null`, and the collection keeps their edit. A path the projection never laid down is never deleted, so a projection with no baseline (a resumed session, a fresh object) deletes nothing (W22, W32, section 3).
5. The flush throws `PlaceUnreadableError` ("the workspace could not be listed: ..."). Did anything reach the collection, and is it safe to catch and ignore? What about other rejections? *(edge case)*
   Answer: That is the only error a flush rejects with on purpose. It means the place could not be listed, so nothing was read, written or deleted, and a caller may swallow it. Any other rejection (a failed collection read, write or delete) means work did not reach the store, and it must not be swallowed. This is also why a custom place's `list` has to throw when it can't read: returning `[]` claims the place is readable and empty, and the flush would then delete everything it owns (W16, W37).
6. When do you reach for `@flow-state-dev/workspace` directly instead of giving the model the Bash tool, and when do you use `put` rather than `flush`?
   Answer: Bash is a tool a model calls, and the workspace is the mechanism under it: the bash tool mounts every collection at its pattern prefix and syncs it through a projection for you, finding collections on `ctx.resources`. Use the package directly when the agent is not a model calling a shell tool, for example a coding harness handed a directory with nothing to carry its writes back. You then give the projection its `Mount`s yourself, because it does not discover them. The place only stores files and never runs commands. Use `put(path, content)` for one file you already wrote to the place: it makes the same decision as a flush for that one path and moves the baseline forward. A flush walks the whole place, so a projection with no baseline would report every file already there as new (W39, W43, W44, W45, W46).
