## 1. How you get them

- The library is a shadcn-compatible custom registry. `rj:2-4` (`$schema` shadcn registry, `name: "flow-state-ui"`, `homepage: "https://flow-state.dev/ui"`); `ov:7`; `rd:3`. **[page]**
- Components are copied in, not imported from a package. Each item's `files[]` maps a source in the registry to a `target` inside the user's project, and the build embeds the file's text as `content` in the item's JSON (`br:95-120`). A component's target is `components/flow-state/<name>.tsx` (every component item in `rj`, for example `rj:109-122`). From then on the file is the user's: `ov:11`, `ov:115` ("the source in your repo is the contract"). **[page]** (answers question 1)
- There is no `import ... from "@flow-state-dev/ui"` for components. The only runtime-importable surface is the generative pair (`pk:5-13`; `rd:5`; `ov:88`). **[page]** (one sentence, link)
- Install command: `fsdev ui add <components...>` (`cli:56-85`). Takes one or more names. Option `--registry <url>` defaults to `https://ui.flow-state.dev/r` (`cli:13,59`); `--cwd <dir>` defaults to the current directory (`cli:60`). It builds `<registry>/<name>.json` for each name, or `<path>/<name>.json` for a local path (`cli:62-66`) and runs `npx shadcn@latest add <urls>` once for all of them in `cwd` (`cli:73-77`). On failure it prints `Failed to install <names>.` and sets the execution-error exit code (`cli:78-82`). **[page]** (the command and one sentence: "delegates to the shadcn CLI")
  - The one-call detail: a call per component stopped at an overwrite prompt for a shared dependency file the earlier call had written (`cli:70-72`). **[ref]** (not a reader action; do not state the history)
- Equivalent without the fsdev CLI: `npx shadcn@latest add https://ui.flow-state.dev/r/message.json` (`ov:21`; `rd:17`). **[page]**
- Listing: `fsdev ui list` prints each item's name and description (`cli:87-128`); `--category <cat>` filters (`cli:90,106-110`). Categories used in the manifest: `ai`, `chat`, `tools`, `code`, `framework`, `patterns`, `generative`, `theme` (`rj`, `categories` of each item). **[page]** (one line) · **[ref]** (the full list of 44)
  - `list` needs the manifest `index.json` from the registry; if it can't load it prints "Could not load registry manifest." and sets the config-error exit code (`cli:94-103`). **[ref]** (CLI reference: `apps/docs/docs/api/cli.md:282-291`)
- The registry holds 44 items: one `registry:theme` (`tokens`), one `registry:file` (`workforce-starter`), and 42 `registry:component` items (count from `rj`; `packages/ui/test/registry-build.test.ts:123` asserts only the two allowed types besides the theme). **[page]** if a count is wanted; **[ref]** for the list.
- Dependencies install with a component. An item's `registryDependencies` pull in the items it needs: other items of this registry (written as full registry URLs in the built JSON, `br:8-14,72`) and shadcn's own (`button`, `collapsible`, `tooltip`, ... stay bare names and resolve against shadcn's registry, `br:12-13`). `message` lists `attachments`, `button`, `button-group`, `tooltip`, `message-response` (`rj` message item). The kitchen-sink's `components.json` sets them to `@/components/ui` and `@/lib/utils` (`apps/kitchen-sink/components.json`). **[page]** (one sentence). **[gap]**: whether `shadcn add` fails or prompts to `init` when `components.json` is absent: that is shadcn's behavior, not in this repo.

- Copies made before the status tokens existed: re-add the components you use, then `fsdev ui add tokens` once; a stylesheet without the tokens renders status parts with no colour, not an error (`ov:62`). **[ref]** (an upgrade row, not page prose; the page states only "re-add, then replay local edits". ## 3. Theming

- Components "never name a colour directly": they use tokens, CSS variables named for the role: `background`, `foreground`, `muted-foreground`, `destructive`, and the rest of the shadcn semantic set (`ov:29`; the `tokens` item's `cssVars.theme` lists every one, `rj:17-43`). **[page]** (answers question 2)
- A test enforces it. The palette census walks every registry file and fails on a fixed Tailwind palette class or a colour literal (`packages/ui/test/palette-census.test.ts:1-9`; patterns in `packages/ui/test/colour-rules.ts:21-27`). **[page]** only as the claim "components read tokens only"; the test is **[ref]**.
- Status tokens, each with a `-foreground` partner: `success`, `warning`, `info`, `attention` (`rj:10`; `packages/ui/test/colour-rules.ts:36-37`). Meanings, from the existing page (`ov:33-41`): `success` done, approved, a passing result; `warning` something off but nobody asked (a blocked task, a stuck request); `info` running, in progress; `attention` a user must act (a tool call waiting for approval, a task waiting on a review); `destructive` failed, rejected, an error. Defaults: green, amber, blue, yellow (`ov:43`; values `rj:61-67`: `--success: hsl(142 76% 36%)`, `--warning: hsl(32 95% 44%)`, `--info: hsl(217 91% 60%)`, `--attention: hsl(41 96% 40%)`). **[page]** (the table; `warning` vs `attention` is the one distinction worth a sentence, `ov:41`)
- The `tokens` item is a `registry:theme`: it carries `cssVars` and `css`, no files (`rj:5-8`; `br:13-14,90-91`; `packages/ui/test/registry-build.test.ts:117-120`). Its description: "Added with the first component that needs it" (`rj:10`). A test holds that every file reading a status token ships in an item whose dependency closure includes `tokens` (`packages/ui/test/registry-reachability.test.ts:9-12,83`). Install by hand: `fsdev ui add tokens` (`ov:43`, `rd:30`). **[page]**
- Where the defaults land: `css["@layer base"]` with `:root` and `.dark` blocks (`rj:44-46,75`). The existing page says "the defaults sit in a base layer, so your own values win wherever you declare them" (`ov:49`), and the item's description says "Neutral defaults in a base layer, so an app's own values win" (`rj:10`). **[page]**
- How to restyle: set the tokens in your stylesheet under `:root` and `.dark` (`ov:51-60`). `.dark` is the dark-mode selector (`rj:75`). Changing a token changes every component that reads it, with no edit to the copied files (`ov:29`). **[page]** (one example: restyle `--attention`)
- The dark theme has its own values for every token (`rj:75` onward; `packages/ui/test/token-defaults.test.ts:1-8`, "token by token, light and dark"). **[ref]**
- Contrast: `packages/ui/test/token-contrast.test.ts` exists. **[gap]**: not read; the page states no contrast figure.
- Tailwind: the registry's own preview uses a `@theme` form of the same defaults, `packages/ui/registry/token-defaults.css`, which is for Storybook (`packages/ui/test/token-defaults.test.ts:1-8`). **[ref]** (contributor; not what `fsdev ui add tokens` writes)
- shadcn-style tokens, not a separate theme file: the kitchen-sink's `components.json` points `tailwind.css` at `app/tokens.css` with `cssVariables: true` (`apps/kitchen-sink/components.json`). Where `shadcn add` writes the `tokens` css in a project is shadcn's rule, set by that file's `tailwind.css`. **[page]** only as "your stylesheet". **[gap]**: the exact write location without a `components.json` is not in this repo.

## 7. Direct answers to the plan's questions

1. **After installing a component, where does its code live?** In your project, at `components/flow-state/<name>.tsx` (and any dependency items beside it, such as `message-response.tsx`). It is a plain source file you edit; there is no package import (section 1: `br:112-118`, `rj`, `ov:11`). **[page]**
2. **How do you theme them?** The components paint only through colour tokens (CSS variables). `fsdev ui add tokens`, added automatically with the first component that needs it, writes defaults under `@layer base`; you set the tokens you want under `:root` and `.dark` and every component follows. Status has four tokens: `success`, `warning`, `info`, `attention`, each with `-foreground` (section 3). **[page]**
3. **Which components know about a flow's session?** The ones in section 4: the ones that read `SessionItemsProvider` (`approval`, `task-plan`, `debate`, `evented-actors`, `routed-specialists`), the ones that read `FlowProvider`'s renderer map (`request-group`, `suspension-card`), the ones that call `@flow-state-dev/react` hooks (`approval`, the suspension cards, `review-hold`, `conversation`, `session-overlay`), and `chat-assistant`, which wires standard item types to components. The rest take a typed item or plain props. **[page]**
