## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's coordinator, support.help, routes by best-fit over support.devices, support.accounts, support.fsd and support.general. You want its own turn to read each message and decide who takes it instead. What do you change, and name one other way it could choose a delegate?
   Answer: Set `routing: judgment` in support.help's WORKER.md. `judgment` is the default, so removing the `routing:` line does the same. Under `judgment` the coordinator's own turn reads the message and files a task for one or more delegates, or answers the message itself. The other routings are `best-fit` (one evaluator call picks a delegate by its note, or else its description), `round-robin` (the next delegate in list order after the one that got the user's last message) and `everyone` (every delegate that can be reached). The delegate's answer lands in the conversation under its own worker id. Facts 3.1 and 3.2 (cc:41, cc:69, cf:22-33), and 1 (co:12, cf:62-70).
2. A user asks support.help, still on best-fit, something none of the four delegates covers, and best fit can't place it. Where does the message go? Then say what happens if support.help had no `fallback:`, and what happens if the coordinator's own turn also fails. *(edge case)*
   Answer: Best fit falls back to the `fallback:` delegate, support.general. With no fallback, or one that can't be reached, the coordinator's own turn takes the message, as it would under `judgment`. If that turn fails too, nobody takes the message. The conversation shows `Nobody took this message: best fit couldn't place it, and the coordinator's own turn failed: <error>.` and the route record has `by: "unplaced"`. Fact 3.3 (wf/best-fit.ts:97-133, :129-132; cf:1203-1205; cr:259-268).
3. Another coordinator uses `routing: round-robin`, and none of its delegates in this conversation can be reached (each has been fired, say). A user sends a message. What do they see? Does a model run? *(edge case)*
   Answer: Nobody takes the message. The conversation says `Nobody took this message: no delegate in this conversation can be reached.` and the route record is `unplaced`. Under `round-robin` and `everyone` the coordinator never runs a model of its own, so no turn of its own steps in. Facts 3.3 (wt/coordinator-rounds.test.ts:122-135, cf:1333) and 3.2 (cc:45-54).
4. You have a billing flow of your own and want a worker on it, support.billing, to be one of support.help's delegates. What does the flow need, and where do you register it?
   Answer: The flow must declare the `contributor` role, and its task entry must be `task: { actions: { work: workerTaskEntry({ name, turn }) } }`, where `turn` takes `{ message }` and returns the answer. Register it in the workforce kit's `workerFlows` slot as `{ flow, roles: ["contributor"] }` or `workerFlow(build, { roles: ["contributor"] })`. Then add support.billing to the coordinator's `delegates:`. The app checks both halves at start: a `contributor` without a `workerTaskEntry` work entry is refused, and so is a `workerTaskEntry` on a flow without the role. A worker on the built-in `agent` flow needs none of this. Fact 3.8 (wf/worker-roles.ts:5-20, kit:10-16, task-entry.ts:125-147).
5. In one conversation, a user calls `addDelegate({ worker: "support.billing" })` on support.help. A second conversation with support.help is already open. Does it see support.billing? Is the WORKER.md changed? And if you later edit `delegates:` in the WORKER.md yourself, which conversations pick up the edit? *(edge case)*
   Answer: No and no. A conversation copies `delegates:` and `fallback:` into its own session state the first time its delegates are read or changed. After that, changes stay in that conversation. Other conversations don't see them, and nothing is written back to the file. An edit to `delegates:` in the WORKER.md reaches only conversations that haven't had a message or a delegate action yet. Facts 3.7 and 5 (dl:14-19, wt/coordinator-delegates.test.ts:114-139).
6. A teammate adds a WORKER.md with `flow: coordinator` to an app on the workforce kit, but the kit's config is `workforce({ agent: { model } })`. The coordinator uses round-robin, so it never needs a routing model. What happens, and what is the fix? *(edge case)*
   Answer: The app does not start. Without a `coordinator` key the kit builds no coordinator flow, so the file names a flow the app does not run. Add `coordinator: { routeModel }` to the kit's config, for example `workforce({ agent: { model }, coordinator: { routeModel: model } })`. `routeModel` is required even when no coordinator routes by best fit. Flags 3 and 4, fact 2 (kit:82-83, cf:213-219, wf/workers/installation.ts:392-395).
