## 1. Who a worker can hand a task to

- A worker's delegates are the workers it hands work to; the worker's `WORKER.md` names them with `delegates:`, a list of worker ids. `dw:10`, `dw:20-29`, `wk/delegates/worker-delegates.ts:7-12`. [page]
- A delegate must be on the same user's roster: another user's worker gets exactly the answer a worker that does not exist gets. `dw:29`, `wk/delegates/delegate-check.ts:12-14`, `wt/delegates-as-authority.test.ts:23`, `:59` (`unknown_assignee` for `bobs.tasker`). [page]
- A worker is a delegate only if its flow takes tasks. A worker on a flow that takes none cannot be added and cannot be assigned: the refusal reads `Worker "x" runs on flow "y", which takes no task, so it can't be a delegate.` `wk/delegates/delegate-check.ts:68-75`. `listDelegates` reports each delegate's `takes` as `"tasks"` or `"nothing"`. `wk/delegates/delegate-check.ts:36-46`, `co:438`, `co:444-448`. [page: one sentence, the `takes` value is [ref]]
- A task filed for anyone else is refused with `unknown_assignee`, and nothing is stored: `{ "ok": false, "error": "unknown_assignee: \"helper\" is not on this board's team. Available: …" }`. `co:438-442`, `wk/../orchestration/src/skills/task-tools-capability.ts:350-355`, `wt/delegates-as-authority.test.ts:23`, `wt/split-down-the-chain.test.ts:352-358`. The same answer for another user's worker, a worker off the roster, a roster worker that is not a delegate, and the filing worker itself. `wt/split-down-the-chain.test.ts:350-366`. [page: the refusal; the full wording is [ref]]
- A task filed with no assignee goes to the conversation's only delegate that takes tasks. With several, it waits unassigned until one is named with `updateTask_tasks`. `co:450`, `wk/delegates/worker-delegates.ts:64-71` (`soleTaskDelegate`). [page, one sentence]
- `delegates: all` is every worker on the user's roster, the worker itself included. It is read on every call, so a worker hired mid-conversation can be handed work on the next call and a worker fired drops off. `dw:33-42`, `wk/delegates/delegate-keys.ts:96-100`, `wk/delegates/worker-delegates.ts:143-157` (`withRoster`). [page, one clause; the rest is [ref]]
- A written `delegates:` list holds at most 25 workers; `all` is not bounded by it. `dw:42`, `wk/delegates/delegate-keys.ts:102-103` (`MAX_DELEGATES = 25`), `wk/delegates/delegate-list.ts:234-239`. [ref]
- Each session starts from the file's list. The list is then the session's own: it changes only through the actions `addDelegate`, `removeDelegate`, `setFallback` and, as a model's tools, only for a coordinator whose file sets `editsOwnDelegates: true`. Every worker with a board can read the list with `listDelegates`. `dw:29-31`, `wk/delegates/worker-delegates.ts:20-24`, `:138-141`. [page: "your app changes a session's list with `addDelegate` and `removeDelegate`"; the rest is [ref]]

A task filed before the removal still runs and is heard. `dw:58`, `wt/any-worker-files.test.ts:293-325`. [page, one sentence]
- A worker with no delegate that takes tasks has no one to hand a task to; on a session of one, an app's `createTask_tasks` answers `{ "ok": false, "error": "no_delegation_board" }`. `dw:48-52`, `wt/any-worker-files.test.ts:255-270`, `:297`. [page]
- There is no flag to turn filing on: a worker gets the task tools when at least one of the session's delegates takes a task. `wk/conversation-board/session-board.ts:7-9`, `dw:14`, `dw:44`. [page]

## 2. Where the delegate does the work

- A filed task starts at once. `createTask_tasks` answers `{ ok: true, taskId }` once the task is stored, without waiting for it to run. `co:452`. [page]
- By default the delegate works it in a new session of its own, a **task session**, on whichever flow the delegate runs on; it belongs to the user like every other session the workers run. `co:452`, `dw:181`, `wk/conversation-board/board.ts:28-32`. [page]
- A task can instead run in the delegate's ongoing session for this conversation (`session: "ongoing"`), starting from everything that session already knows; a session works one task at a time, so a second task for the same session waits. `dw:181`. Only code filing through the board's collection chooses this; the coordinator uses it for routed tasks. `dw:179`, `wk/conversation-board/board.ts:28-32`. [page: one sentence; settings are [ref]]
- A worker working a task, in a task session, cannot choose either `session` or `resultTo`: the filing is refused with `setting_not_from_task_session`, naming the setting. `dw:184`, `wk/conversation-board/board.ts:31-32`, `wt/conversation-board-filing-settings.test.ts:75-76`, `:100`. [ref]
- The delegate is checked again when the task is handed over. If it was removed or fired in the meantime, or its flow takes no task, the task fails and the conversation hears that it failed. `co:452`. [ref]
- A task session is born knowing how deep it is and which task is the top of its chain; both come from the server, never from input. `wk/conversation-board/chain.ts:11-17`, `wt/split-down-the-chain.test.ts:460-475`. [ref]
- Every task gets two attempts, a number the app cannot change; a first failure is run again without a word. A task whose result goes to the conversation gets one. `co:480-482`, `wk/conversation-board/board.ts:1324`. [ref]
- A task's brief carries its goal, title and context: that is what the delegate sees. The delegate in a task session sees only the brief; the lab's lead is told so ("A task session sees only its goal, so write each goal so it can be done with nothing else"). `lab:21-26`. [page, one sentence on writing a goal that stands alone]
- A worker working a task also gets `reportProgress` (a status note and a checkpoint of its output on that task), `holdTaskForUser` (asks the user a question the task then waits on) and `suspendForUser`; none is an action. `dw:46`. [ref]

## 3. Splitting a task

- A worker given a task can split it into pieces for its own delegates. A piece for any other worker is refused with `unknown_assignee` and nothing is filed. `dw:215`, `wt/split-down-the-chain.test.ts:341-379`. [page]
- When the task needs a worker that is not a delegate, the worker says so in its answer and whoever filed the task decides. `dw:215`. [page]
- A piece with no assignee goes to the worker's delegate when it has exactly one. `dw:215`, `wk/delegates/worker-delegates.ts:64-71`. [page]
- The pieces go on the task session's own board. The worker either waits on a piece in the same turn with `getTask({ id, wait: true })`, or files them and ends its turn. `dw:217`. [page]
- Waits nest up to five deep. `dw:217`, `orchestration/src/tasks/helpers/wait-on-task.ts:394-397` (`waits nest at most ${MAX_WAIT_DEPTH} deep`). **[verify]** the constant's value was not read; the user doc says five and the depth limit on boards is also five (`wk/conversation-board/chain.ts:40`). Keep the wait nesting out of the page; "five boards deep" below is the stated limit. [ref]
- When the turn ends instead of waiting, nothing runs for the task while the pieces are worked, but the task stays `in_progress`, with `keptOpenBy: "filed"` on its row, and is not handed out again. `dw:217`, `tb:852-863`, `wk/conversation-board/task-entry.ts:45-47`, `wt/split-down-the-chain.test.ts:50` (test name). [page: "it stays in progress while its pieces run"; `keptOpenBy` is [ref]]
- Each piece's ending wakes the worker for a turn in the task session, where it reads the result and decides what it means; a turn can file more pieces and the task waits on those too. `dw:219`, `wt/split-down-the-chain.test.ts:264-285`. [page]
- The task completes once no piece is open and the worker has had a turn on every piece's ending. `dw:221`, `wt/split-down-the-chain.test.ts:304`. [page]
- The task's output is the latest checkpoint the worker reported with `reportProgress`, or, with none, the answer from the last turn a piece's ending woke. A message's answer is never the output. `dw:221`, `wt/split-down-the-chain.test.ts:239-263`. [page, one sentence]
- To carry a piece's result into the output, the worker puts it in its answer, or reads the piece's row: `listTasks({ filedByTask })` lists the pieces one task filed, `getTask` reads one. `dw:228`. [page]
- A piece that fails for good does not fail the task by itself: its ending wakes the worker, whose turn decides (file again to the same delegate or another, or answer with what it has). If that turn throws, the task's attempt fails. A worker that ignores a failed piece completes its task anyway, so tell your workers what to do when a piece fails. `dw:230`, `wt/split-down-the-chain.test.ts:116-190`. [page]
- Only the session that filed the task hears it end; it does not hear each piece. `dw:230`. [page]
- When a task fails, is retried or is cancelled, every piece it filed that is still open is cancelled within seconds; a retry does not wait on the pieces of the attempt before it. `dw:232`, `wt/split-down-the-chain.test.ts:382-431`. [ref]
- A message to the worker in its task session does not hold the task and is not part of it; its turn cannot write to the task, and a failure in it does not fail the task. `dw:219`. [ref]
- If the server stops after a piece ends but before its notice reaches the task session, a durable host delivers the notice once it is running again; a host without durable execution does not, and the split task stays `in_progress` with nothing to wake it. `dw:234`, `wt/split-down-the-chain.test.ts:191-218`. [page, one sentence with a link to `advanced/durable-execution`]
- Every session in the chain belongs to the user, and only the user's own workers appear in it. `dw:236`. [page]

### How far a split goes

- A chain stops at five boards deep, counting the board of the session that filed the first task. `dw:240`, `wk/conversation-board/chain.ts:39-40` (`MAX_TASK_DEPTH = 5`, fixed), `wt/split-down-the-chain.test.ts:433-458` (a sixth board is refused). [page]
- A chain stops at 100 tasks under one top task, counting every depth together, finished tasks included. `dw:240`, `wk/conversation-board/chain.ts:42-43` (`DEFAULT_TASK_CHAIN_LIMIT = 100`), `wt/split-down-the-chain.test.ts:502-534`. [page]
- A filing past either limit is refused and nothing is filed: `{ "ok": false, "error": "total_task_cap_exceeded" }`. `dw:243`, `wt/split-down-the-chain.test.ts:450-454`. [page]
- `taskChainLimit` raises the 100: a whole number of at least 1, set on the workforce kit as `workforce({ taskChainLimit: 250 })`. The depth of five does not change. `wk/kit/workforce-kit.ts:99-100`, `:142`, `:273`, `dw:248-254`, `wt/split-down-the-chain.test.ts:535-550`. The user doc shows `hireWorkforce(installation, { taskChainLimit })` as the way to set it; the kit's config key is the one a kit-built app uses. [page: the kit key, one line]
- Each task is a session and at least one model turn, so a worker that splits at every level gets expensive fast. `dw:246`. [page]

## 4. Seeing what came back (the filer, and your app)

- The session that filed a task hears once when it ends, in a line under the delegate's name: `Task "Audit our dependencies' licenses" (task_…) completed by licenses: All 214 dependencies are MIT or Apache-2.0.` `co:466-471`. [page]
- It hears when a task completes (with what came back), fails for good (with the error), stops on a question (with the question), or is cancelled, unless the coordinator cancelled it itself. A failure or cancel that took dependent tasks names them in the same line. `co:473`. [page, the completed line; the other endings in a clause]
- When the line arrives, a coordinator that routes by `judgment` or `best-fit` takes a turn to read it and decide what is next, such as filing a failed task again. A coordinator routing `round-robin` or `everyone` has no turn and shows the line only. If the worker is mid-reply, the line starts a second turn at once. `co:475`. [page: the first sentence; the routing split is [ref]]
- Each ending is heard once, even if the server stops just after the task ends. On a host with durable execution, an ending whose notice did not go out is heard within about two seconds of the ending, or as soon as the server is running again. `dw:175`, `tb:1211-1213`. [page, one sentence; mechanism is [ref]]
- The notice carries `boardId`, `taskId`, `attempt`, `ending` (`completed`, `errored`, `cancelled`), `output`, `error`, `cancelled`. `tb:1199-1209`. [ref `reference/task-board`]
- A task the filer waited on with `getTask({ id, wait: true })` sends no notice; the `getTask` call gets the result. `tb:1217`. [page, one sentence]
- A worker reads a finished task with `getTask`, which returns the task whole, with its output. `co:473`, `co:490-492`. [page]
- Managing tasks from the app: `listTasks_tasks` lists this conversation's tasks and the steps its worker filed for itself, never another conversation's; `getTask_tasks` returns one whole; `createTask_tasks` files; `updateTask_tasks` changes a task before it starts, sends a running one a `message`, or cancels it. A task that has started cannot be changed, only steered with a message or cancelled: `field_locked_after_start`. A finished task changes no more: `task_finished`. To retry a failed task, file it again. `co:486-496`. [page: `listTasks_tasks` and `getTask_tasks` only; the rest is [ref]]
