## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your lead worker's WORKER.md has `delegates: [desk.thread-coder, desk.thread-coder-codex]`. Its model files a task with `createTask` naming `desk.reviewer`, a worker on the same user's roster that is not in that list. What happens? *(edge case)*
   Answer: The filing is refused with `unknown_assignee` and nothing is stored. A worker can hand a task only to its delegates, the workers its `WORKER.md` names under `delegates:` (dw:10, dw:20-29). A roster worker that is not a delegate gets the same refusal as a worker that does not exist (wt/split-down-the-chain.test.ts:350-366; co:438-442).
2. Two people use the same app. Alice's lead lists `desk.thread-coder` as a delegate. Can Alice's lead file a task for Bob's `desk.thread-coder`, and can Alice see the tasks Bob's conversations filed? *(edge case)*
   Answer: No to both. A delegate must be on the same user's roster: another user's worker gets exactly the answer a worker that does not exist gets, `unknown_assignee` (dw:29, delegate-check.ts:12-14, wt/delegates-as-authority.test.ts:59). The task tools act as the signed-in user and another user's call is refused (dw:44). A browser read of the `tasks` collection never returns another user's rows (ledger.ts:118-122, conversation-board-browser-read.test.ts:31-65).
3. The lead files a task for `desk.thread-coder` with `createTask`, leaving `session` out. Where does the coder do the work, what does it see, and does `createTask` wait for the result?
   Answer: The task starts at once and `createTask` answers `{ ok: true, taskId }` as soon as the task is stored, without waiting for it to run (co:452). By default the coder works it in a new session of its own, a task session, on whichever flow it runs on, owned by the user (co:452, dw:181). The coder sees only the task's brief, its goal, title and context, so the goal must stand on its own (lab:21-26).
4. The coder finishes the task. How does the lead's conversation learn it is done, and what changes if the lead's model had instead called `getTask({ id, wait: true })` on it?
   Answer: The session that filed the task hears once when it ends, in a line under the delegate's name, e.g. `Task "…" (task_…) completed by …: <what came back>` (co:466-471); it also hears a failure for good, a stop on a question, or a cancel (co:473). Each ending is heard once, even if the server stops just after (dw:175). A task the filer waited on with `getTask({ id, wait: true })` sends no notice: the `getTask` call gets the result (tb:1217).
5. The coder, working its task in a task session, splits it into three pieces for its own delegates and ends its turn instead of waiting. One piece fails for good. What happens to the coder's task, and when does it complete? *(edge case)*
   Answer: The task stays in progress while the pieces run and is not handed out again (dw:217). Each piece's ending, the failure included, wakes the coder for a turn in its task session where it decides what it means: file again to the same or another delegate, or answer with what it has. A failed piece does not fail the task by itself; only a turn that throws fails the attempt, and a coder that ignores the failure completes anyway (dw:219, dw:230). The task completes once no piece is open and the coder has had a turn on every piece's ending; its output is the latest `reportProgress` checkpoint or, with none, the answer from the last woken turn (dw:221). Only the lead's session hears the coder's task end, not each piece (dw:230).
6. Partway through a conversation your app calls `removeDelegate` to take the lead's only delegate that takes tasks off its list, while one task for it is already running. What happens to that running task, and what does the app's next `createTask_tasks` answer? *(edge case)*
   Answer: A session's delegate list starts from the file's list and the app changes it with `addDelegate` and `removeDelegate` (dw:29-31). A task filed before the removal still runs and its ending is still heard; with no delegate that takes tasks left, the app's `createTask_tasks` answers `{ "ok": false, "error": "no_delegation_board" }` (dw:58, wt/any-worker-files.test.ts:293-325). Adding a delegate that takes tasks makes it available on the next call.

## 5 · Fact check

Checked against the code: the page as pass 4 read it after the draft, sha256 a4fccf78ad7d, and the 13 Reference row(s) pass 6 moved.

- The session that filed a task hears it end once ... "It hears when a task completes, fails for good, stops on a question, or is cancelled." (a cancel always raises the ending line) Untrue: A cancel does not always raise a notice. It owes none when the filer made the cancel itself in its own request, through a model's task tool inside its own turn, because the call's result already told it. It also owes none for a dependent cancelled by a cascade from a failed or cancelled row that shares its filer, because that row's notice names it. A cancel from a public `_tasks` action, a user's cancel from a screen, or a cascade from above the filer does owe one. A routed task's cancel also says nothing.
