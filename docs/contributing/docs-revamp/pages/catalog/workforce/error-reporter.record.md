## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In the help-desk app, the reply step of a support conversation throws, and the request ends failed after its retries. Separately, a support agent messages the Error Reporter in its own conversation: "the billing worker keeps quoting last month's prices." Which of these starts a bug report, and how does each reach the reporter?
   Answer: Both do. The first is a failure that stayed failed: the engine's error capture (errorCapture: reporter.capture) sends one final event per request that ends failed after rescues and retries, and the reporter takes only final events (rp:140, rp:316-317, ec:62). A task on a conversation board that ends errored is the same kind, and so is a task that gives up without throwing (ts:233-247; goal Leg 7). The second is a problem a user describes: the reporter calls its reportProblem tool with the description, and the report goes through the same intake, preview and filing as a failure (fl:666-698, t:636-649).
2. The help-desk operator turns the reporter on with a tracker set. Before anything reaches the tracker, who sees the report, what do they see, and what can they answer?
   Answer: The operator named at setup (operator: { userId, orgId }) sees it first, as an ordinary question in Inbox. It is headed "Error report: <title>" and says "Seen N time(s). File it?", followed by any questions the draft has. The draft has a summary, steps to reproduce, expected and actual, suspected cause and a Context section of exact ids. The operator can choose File, File with instructions (for example "Label it P1", which is folded into the filed issue), or Don't file. Nothing is filed before they answer unless preview.autoFile or preview.autoFileAfterMs says otherwise, and both are off by default (fl:416-447, fl:103-107, fl:173-188, rp:113-118, t:290-299; goal Leg 1).
3. The operator answers File. Where does the report go, and how does the operator find out it was filed?
   Answer: It is filed as exactly one new issue in the tracker, through the MCP servers of the project named in tracker: { project: "<visibility>/<id>" }. The shipped filing prompt names Linear. The operator's answer is applied, and the Context lines are kept as written. The reporter then writes "Filed <identifier>: <title> <url>" in its own conversation, which in a Lab is the operator's (rp:106-112, fl:500-515, fl:502, fl:549-551, lab:1423-1427). The run that drafted the report had no tracker tools and only read the code; it never fixes the bug or opens a pull request (fl:270-272, fl:357, mw:98).
4. Edge case, failure: the operator answers File, but the tracker call fails and no issue URL comes back. What happens to the report? And what if the app was set up with no tracker at all? *(edge case)*
   Answer: If filing fails, the report stays approved and is tried again. The row records "not filed: <reason>", the report session says "This report was not filed yet; it will be tried again", and the reporter retries later (after five minutes) and again at the next start. Owed work survives a restart (fl:527-537, rp:167-168, rp:333-343, t:485-499; goal Leg 6). With no tracker, reports are still kept and previewed but never filed: after File, the report session says "This Lab names no tracker, so the report is kept here and nothing was filed." (fl:556-567, rp:106).
5. Edge case, repeats: the same failure happens 11 times in an hour, differing only in request ids. How many Inbox cards does the operator get? What happens on later repeats after the issue is filed, and after the operator answers Don't file? *(edge case)*
   Answer: There is one report and one card. Two failures that differ only in ids, numbers and paths share a fingerprint, so repeats raise the count shown as "Seen N times" (goal Leg 2: count 11, no second card; fp:143-169, rs:555-586). After filing, a repeat adds a counted comment to the issue, at most once an hour by default. If the issue is completed or canceled, the reporter does not comment, and the next occurrence starts a new report that links the old issue (rs:532-536, fl:600-651). After Don't file, repeats only count, with no new card, for a day (limits.dismissForMs, 24 hours) (fl:451-462, rs:172). If many different failures arrive, new reports are capped at five an hour, and the overflow goes into one storm report (rs:452-530).
6. Edge case, a second user and a cancel: a help-desk agent who is not the operator reports a problem and names a session that belongs to a colleague. Then someone cancels a task that had gone wrong. What does the reporter read for the first, and does the second produce a report? *(edge case)*
   Answer: The named session is read only if it belongs to the user who named it. Otherwise the dossier says it is not readable because it is not the reporting user's session (rp:389-403, t:415-433). The report is still previewed to the operator, who is the only one who runs a report, and the "Filed ..." line goes to the reporter's own conversation, not to the agent who reported it (fl:318-320, rp:366-369). A cancelled task is not reported: only an errored ending is (ts:229). A Shift Manager Lab's card for a cancelled task invites the user to tell the reporter what happened and to name the task (tb:12-41). The reporter also never reports its own failures (rs:344-346).
