## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In the help-desk app, `workforce/teams/support/workers/triage/WORKER.md` has a `description:` and a body of instructions, and no `flow:` line and no `model:` line. The kit is installed as `workforce({ agent: { model: "openai/gpt-6-luna" } })`. What does the triage worker run on, where do its instructions come from, and which model answers?
   Answer: It runs on the built-in worker flow `agent`, one registered copy that every worker naming no flow shares; each turn runs as the worker its session names. The file's body becomes its instructions. The model is the file's `model:` if it had one, else the kit's `agent.model` (here `openai/gpt-6-luna`); with neither, it would be `intent/chat`, which the app's model resolver turns into a concrete model. (Facts 3.1; section 11 answer 1: `bw:13`, `bw:33`, `aw:473`, `at:60-69`, goal `g1:5-19`.)
2. While the help-desk app is running, Ana hires a worker from the browser: `workforce.hire({ id: "scribe", instructions: "Take short notes." })`. What changes in the app's `workforce/` folder, does anything restart, and when can she talk to `scribe`?
   Answer: Nothing in the app's files changes: no file is added to `workforce/`, no flow is registered, nothing restarts. The one change is one row in Ana's data in the app's configured store, at `workforce/workers/scribe` at user scope, in the organization she is signed in to. `hire` returns `{ id: "scribe", flow: "agent" }` (no `flow` given means `agent`); the worker is on her roster at once and its next turn, on any of the app's processes, runs on that row. (Facts 4.1, 4.3; section 11 answer 2: `hb:1-5`, `wr:3-15`, `wt:22-31`, `cl:204-211`.)
3. Ben, another help-desk user in the same organization, also hires a worker with id `scribe` an hour after Ana did. Is his hire refused because the id is taken? Can either of them see or message the other's `scribe`? *(edge case)*
   Answer: His hire is not refused: the id only has to be unused on his own roster, and each user's workers are their own rows. They are two separate workers. Only the owner can list a worker of their own, open its sessions, message it or start a session with it; asking for another user's worker gets the answer for one that does not exist. (Refusal 'already on your roster' applies only when the same user reuses an id.) (Facts 4.4 table row 'A user's own worker'; section 11 edge cases: `wt:57-67`, `dh:99-104`, `hb:153-163`.)
4. The billing worker is a standard worker defined by `teams/support/workers/billing/WORKER.md`. Ana edits it from the client to change its instructions. What do Ana and Ben each get on their next turn with `billing`, and how does Ana undo her change? *(edge case)*
   Answer: The edit does not change the file and is not refused: it makes Ana's own copy of the worker under the same id `support.billing`, carrying the file's name, settings, skills and team text, and applies her change to it. Ana's turns read her copy (her roster lists it once, still standard, marked edited); Ben and every other user still get the file's version. `reset({ id })` deletes her copy so her next turn reads the file again (reset refuses a worker she has not edited). Hiring, forking onto, or firing a standard worker's id is still refused, with the hint to fork it. (Facts 4.2: `hb:10-14`, `hb:213-247`, `hb:262-277`; tests `wt:286-310`, `wt:371-383`, `wt:34-47`.)
5. Ana fires her `scribe` worker while she still has past conversations with it. What happens to those conversations, and what happens if she sends a new message in one? *(edge case)*
   Answer: `fire` deletes the worker's record. Her past sessions stay readable, but a new turn on one is refused, naming the worker as fired. (Facts 4.2: `hb:249-260`; test `wt:169-181`; section 11 edge cases.)
6. The help-desk team wants two things: a screen showing each user's workers and how many tokens each used, and a new type of worker (say, a coding worker) that a `WORKER.md` can pick with `flow:`. Which views does the kit serve for the screen, and which slot would a kit fill to add the new type of worker?
   Answer: On the roster flow `workforce-roster`, at user scope with no session: `roster` (the user's workers, their own and the standard ones, an edited standard worker listed once as their copy), `workerUsage` (tokens per worker by model and harness over recent days), plus `workstreamReport` and `routines`. On the `agent` flow (and `coordinator` when configured): `listTasks_tasks`, the conversation's task list. The client handles `rosterView` and `workerUsageView` come from `@flow-state-dev/workforce/browser`. To add a kind of worker, a kit fills `workforce.slots.workerFlows`, a keyed slot of worker flows beside `agent`; a worker's file selects one with `flow:` (the harnesses kit adds `coder` this way). (Facts 5, 7; section 11 answers 3 and 4: `rf:69-75`, `aw:1528`, `br:30-31`, `wk:177-181`, `harnesses-kit.ts:105`, `kt:114-140`.)
