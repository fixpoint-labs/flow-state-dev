## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Alice's Chief of Staff calls sendMessage with `to` set to the id of a researcher on Bob's roster, a different user. What happens, and what does the Chief of Staff learn about Bob's workers from the result? *(edge case)*
   Answer: The send is refused: the tool returns { ok: false, error } with `no_worker: no worker "<id>" on your roster.` That is the same text as for an id that does not exist, so the sender learns nothing about Bob's workers. A worker can reach only workers on its own user's roster, meaning the user's hires plus the app's standard workers. A refused send writes no log row and uses none of the budget. (Facts §2: sm:103, sm:318-321, t1:1005-1014, g1:21.)
2. Alice asks her Chief of Staff something it can't answer until the researcher looks up a fact. Should the Chief of Staff send with `replyRequested: true` or with `wait: true`, and what does it get back?
   Answer: It should use `wait: true`, because the question blocks the answer. `replyRequested` is for an answer the sender wants but can go on without. `wait: true` asks for a reply in the same way, so it needs no `replyRequested`, and the sender waits in the same turn. When the researcher answers in time, the call's result is { "status": "answered", "sent": "msg_…", "reply": "…" }. No message lands in the Chief of Staff's conversation, though the answer gets its own row in the log. A wait needs a host that can hold one, which means durable execution; that is on by default on persistent stores and in `fsdev dev` and `fsdev run`. On any other host the wait is refused with `wait_unavailable` and nothing is sent; there, send with `replyRequested`. (Facts §4: mt:59-65, mt:77-86, t3:248-272, wr:39-43, mw:486.)
3. The Chief of Staff waits on the researcher, and the deadline passes before the researcher answers. By default, how long is that? What result does the Chief of Staff get, and should it send the question again? *(edge case)*
   Answer: With no `deadline`, a wait lasts the host's default of five minutes. When the deadline passes first, the result is { "status": "running", "sent": "msg_…" }. Nothing is stopped: the researcher keeps working and the Chief of Staff goes on. The answer arrives later as a message and wakes a new turn in the Chief of Staff's session. It should not ask again, because the answer still comes. A worker's file should tell it what to do with a `running` result: go on, and use the answer when it arrives. (Facts §4: wait-chain.ts:66-77, wr:158-166, t3:425, mt:101-103, mw:157.)
4. The Chief of Staff messages the researcher with `replyRequested: true` and carries on answering Alice. The researcher's turn then fails, or ends with no text. Does the Chief of Staff ever hear back, and how? *(edge case)*
   Answer: Yes. A message that asks for a reply always gets exactly one answer. Normally that is the recipient's final text. When there is none, the framework sends a "no answer" in its place, for example when the turn failed or ended with no text. That answer comes back as a message from the researcher, with `inReplyTo` set to the original message's id. It lands in the Chief of Staff's session and wakes a turn there. Its log row has `noAnswer: true`. The sender is never left without an answer. If the researcher had instead answered during its turn with sendMessage and `inReplyTo`, that would be the only answer, and its final text would not also be sent. (Facts §3: or:57-61, rx:300-311, lr:326, t2:272, t2:389.)
5. The Chief of Staff messages the researcher. Where can Alice see the exchange, and could Bob see it?
   Answer: On the sender's side, the call shows in the Chief of Staff's session as a tool output item for the tool named `sendMessage`, like any other tool call. On the recipient's side, the message lands in the researcher's own conversation with Alice; that conversation is opened if they have never talked. It lands as an item an app draws (the `workforce:received` component, with data such as { id: "msg_…", from, text, budget: 5 }) plus a `From <sender>:` line that only the researcher's model reads. The researcher then takes a turn on it. Both sessions are Alice's own. She can also read a log with one row per message from her browser. In Shift Manager that log is the Messages screen, and a conversation shows lines like *To researcher: …* or *Asked researcher*. Bob never sees it: a read of the log never returns another user's messages. (Facts §5: keys:140, rx:244-258, sm:33-38, mw:63, mw:663, tl:163-199, t1:178-204.)
6. An app's author edits the researcher's WORKER.md and gives it a `tools:` line that doesn't list sendMessage. Can the researcher still message the Chief of Staff? And what is the right edit to change when a worker sends messages? *(edge case)*
   Answer: Yes, it can still send. sendMessage is part of the workforce kit and comes with every worker, and a `tools:` line does not fence it out. No switch allows or blocks messaging. To change what a worker does about messages, edit its instructions in WORKER.md. The Chief of Staff's file says to message researcher with sendMessage, pass `replyRequested: true`, and never pass `wait`. The researcher's file says to answer with sendMessage and `inReplyTo` when the sender didn't ask for a reply. To change how many messages are allowed, set `workforce({ messages: { budget, perTurn } })`, which defaults to 6 and 3. (Facts flag 5; §6-7: mt:121-123, res:6, res:14-16, cos:33-36, lim:11-14.)
