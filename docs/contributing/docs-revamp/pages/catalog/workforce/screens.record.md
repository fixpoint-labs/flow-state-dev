## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are building a support-desk app on the workforce kit and want a sidebar listing every worker the signed-in agent can use: the ones they hired and the standard ones from the app's WORKER.md files. Which read do you make, and what do you pass it?
   Answer: `useView(rosterView)`: `rosterView` comes from `@flow-state-dev/workforce/browser` and `useView` from `@flow-state-dev/react`. The roster view takes no input and no session, because it is answered at user scope, so `useView(rosterView)` is the whole call. It joins the user's own workers and the standard ones from the app's files, listing each one once (facts flag 3, 3.1: rv:15-24, rv:66-67, rr:11-12).
2. A worker on the support desk hands a question back to the user, so that work is now waiting on them. Which part of your screen changes: the roster sidebar, the conversation's task list, or the session list?
   Answer: Not the roster. A roster entry has no status field, and a `Roster` record shows only the worker's id and flow. The conversation's task list, read with `useView(taskListViewRef("coordinator", "tasks"), {}, { sessionId })`, re-renders when a task on the board changes, and a task waiting on a user carries a `holds` entry. A `BoardColumns` or `BoardList` with `live` re-reads too. In the `FlowNavigator` session list, the session's record shows ◆ "Waiting on you" once its latest request is `suspended` (facts 4.2, 4.4; rv:34-44, task-listing.ts:12-17, session-row.ts:36-64).
3. Your design team wants the roster and the board in your own visual style, not the shipped look. Do you have to use `Roster`, `BoardColumns` and `BoardList`?
   Answer: No. `useView(rosterView)` returns plain data you can render yourself, `useView(taskListViewRef(...))` returns a conversation's tasks, and `watchRoster` follows the roster without React. If you do use the components, `slots.card` and `slots.row` take your own body, theming goes through the `--fsd-panel-*` custom properties, the components bring no CSS framework, and `groupIntoColumns` is exported if you want to draw your own columns (facts 4.3; rc/chrome.ts:49-58).
4. Two agents at the same company sign in to the support desk. Alice hires a 'refund-checker' worker. Does it show in Bob's roster? And if Bob has edited a standard worker, how does his roster list it? *(edge case)*
   Answer: Alice's worker does not show in Bob's roster. Worker records are stored at user scope (per organization), so each read returns only the signed-in user's records. The standard workers from the app's files are listed for every user. A standard worker Bob edited is listed once, as his copy, still with `standard: true` and `edited: true` (facts flag 4, 3.1; wf/workers/worker-row.ts:68-69, rv:102-113; dw:188: a read never returns another user's records).
5. Alice has the roster open in one tab and fires a worker from a script in another process. Does the roster in her open tab update, and does the screen have to name a topic to listen to? *(edge case)*
   Answer: It updates. Each answer carries the change topics of what the view's run read, and the live read listens to those topics, so a hire, edit, fork or fire from any tab, script or worker turn triggers a fresh read. The screen names no topic. Where a push can miss a change, a timer re-reads as a fallback. A re-read that fails keeps the roster already on screen and sets `stale` to `true`, and the next read that lands replaces it (facts 3.1; uv:3-14, rv:20-23, wt/watch-roster.test.ts:108-121).
6. You drop `<BoardColumns sessionId={id} boardRef="tasks" />` onto a page and it shows the empty note. What does that note tell you, and what do you get from `BoardList` on the same board instead? *(edge case)*
   Answer: An empty `BoardColumns` says that boards are wired to a worker explicitly and that probably nothing drains this one. `BoardList` only says "This board has no tasks." Both components also have separate states for loading and for a failed read, the failed one with a Retry button. When rows do exist, `BoardColumns` groups them in the order pending, in_progress, held, completed, errored, cancelled, gives a status it doesn't know its own column, and drops no row (facts 3.4; rc/BoardColumns.ts:48-55, :205-233, rc/BoardList.ts:139-159).
