## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. An app installs the workforce kit with an `agent` model, and Alice tells her worker eng-lead: "Always name the project before the status." What did the app have to configure for this to be kept, what does Alice see, and from when does the worker follow it?
   Answer: Nothing beyond installing the kit. A worker on the built-in agent (or coordinator) flow has the rule tools without any further setup, and the kit has no rules option (facts flag 1, kit:138, kit:178-183). The worker saves the note without asking first (sr:19, st/rules-capability.ts:173). The conversation shows a line such as `✎ Rule added (1 of 20): "Name the project before giving a status."`. The tool writes that line, not the model: Alice sees it, and it does not go back to the model as history (st/rules-list.ts:233, st/rules-capability.ts:146-153). The rule counts from her next turn without a new session. It is then in every later turn eng-lead takes for her, including fresh sessions, and on a persistent store it survives a restart (tk:309-321, g1:12).
2. Bob also uses eng-lead. Does his reply follow the rule Alice set? And does Alice's other worker, otto, follow it? *(edge case)*
   Answer: No to both. A rules list belongs to one worker for one user. Bob's turns with eng-lead do not carry Alice's rule, and reading through the client he gets none of her list (tk:367-379). Each of Alice's workers keeps its own list, so otto starts with none and only follows rules she gives otto (tk:368-379). The record is keyed by the worker the session is verified to run as, and a request that names a user is refused (st/rules-record.ts:86-89, tk:410-411). The browser can read the signed-in user's own list but cannot write to the record directly (tk:381-411).
3. Alice no longer wants the rule. How can she remove it, and when does the worker stop following it?
   Answer: She can ask eng-lead in words to drop it. The worker calls `rules/remove` with the rule's number and current text, and the line `✎ Rule 1 removed (0 of 20 left): "…"` shows (st/rules-capability.ts:192-199, tk:269-274). An app can also call `workforce.standingRules("eng-lead", { op: "remove", version, number, current })` (wf/workers/client.ts:182-187), and Shift Manager's worker settings have a Rules section where she can delete one (g2:3). The removal counts from her next turn (tk:309-321). There is no "remove all", and nobody can remove another user's rule (st/rules-action.ts:21-36).
4. Alice has three rules and removes rule 1. Something that read the list before the removal now asks to change "rule 2", quoting the text rule 2 had then. What happens? *(edge case)*
   Answer: The change is refused and nothing changes. A remove renumbers the rules after it, so the old rule 2 is now rule 1 and number 2 names a different rule. Change and remove must quote the rule's current text, and a quote that doesn't match is refused rather than applied to the wrong rule (tl:72-85, st/rules-list.ts:236-243). Through the client, a stale version is refused the same way (tk:432-445).
5. The team wants eng-lead to "always answer in French". Should that be a standing rule or a line in the brief?
   Answer: A brief line if every user of the worker should get French. The `WORKER.md` body is the same for every user, and nobody can change a standard worker while the app runs (durable-hire.md:10-12). A standing rule if only one user wants it: it is that user's note, read only on that user's turns, and it cannot change the worker's instructions or anyone else's turns (tk:323-335, tk:367-379). A rule is text the model reads after the worker's own instructions (tk:309-321). It is not a setting, so the page must not promise that a rule overrides the file.
6. On Alice's next turn the store that holds the rules is down. Later, with 20 rules saved, she asks for one more. What happens each time? *(edge case)*
   Answer: When the rules can't be read, the turn runs without them and posts one status line saying so. The turn does not fail (st/rules-capability.ts:100-113, tk:337-364). If a write can't be stored, no saved line is posted and no existing rule is lost (tk:277-290). With 20 rules the list is full, so the add is refused and nothing is saved. Alice sees `✎ Rule not added: the list is full (20 of 20); merge or drop a rule before adding one.` and the worker asks her which rule to merge or drop (st/rules-list.ts:226-230, st/rules-capability.ts:174-175, tk:292-305).
