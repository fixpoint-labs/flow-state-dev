## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support team has a refund-policy document that every worker on the support team should be able to look up, but that nothing running in the app should be able to change. Where does the file go, and does a worker on another team see it?
   Answer: teams/support/references/refund-policy.md. references/ holds read-only documents: the file is the text, and only editing the file and deploying changes it (dd:15-17). A team's references/ reaches that team's workers only, plus nothing beside them (dd:277-279, wd:144), so a worker on another team does not see it. For every worker in the organization it would go in org/references/ instead, and the only way to widen a reference is to move the file up the tree, since no setting widens it (dd:279). Instructions told to every support worker on every turn belong in teams/support/TEAM.md's body, not in references/.
2. You add a new worker flow file, workforce/flows/workers/triage.ts, and point a WORKER.md's flow: at it. What do you run before the app serves it?
   Answer: Run `pnpm fsdev gen` from the app's folder (it reads workforce/ relative to where it runs; --root overrides) and commit the workforce.gen.ts it writes. The app passes that module whole to the kit as `generated`. Then restart, because nothing regenerates while `next dev` runs and nothing scans the tree while the app runs (cd:18, cd:64-68, gen:162, wd:956). `@flow-state-dev/workforce` must be in the app's dependencies or devDependencies so the command can find its generator (cd:70). The startup code names no worker flows, so adding one is adding a file (cd:12).
3. Someone leaves a notes.txt at the top of workforce/, and puts a tools/ folder inside teams/support/. What happens when the app starts? *(edge case)*
   Answer: The app does not start. The kit reads the whole folder at startup, claims each file it reads, and refuses the app if any file is left over. Every problem is named at once, each with its path, for example `"teams/support/tools" is not used by anything that reads the folder of kit "workforce". Remove it.` (wff:3-12, claim:1-17, claim:114, kits:260-290; run). Under the kit, a stray file is not skipped quietly. Code a model can call goes in blocks/, never tools/ (dwb:56, cd:149). Only .DS_Store and Thumbs.db are passed over, and a symlink anywhere is refused (claim:5-15).
4. A test file, blocks/search-docs.test.ts, sits next to a block. Does startup catch it, and if not, what does? *(edge case)*
   Answer: Startup does not refuse it, because blocks/ is a claimed place. `fsdev gen` does, because a basename with a second dot breaks the name rule (lowercase letters, digits and single hyphens) (disc:262-268; run: `Block file name "x.test" must be lowercase letters, digits, and single hyphens ...`). Every .ts/.tsx file in a code folder counts as a declaration, so a fixture.ts would register a flow or block called fixture. Keep tests and fixtures out of flows/workers/, every blocks/ folder and every resources/ folder (cd:154). A file in the wrong place is caught at startup. A file that is in the right place but wrongly named is caught by gen.
5. An escalation package sits at teams/support/packages/escalation/. Which workers hold it, and can a worker on the billing team or an org worker use it?
   Answer: Only a worker on the support team whose own WORKER.md names it (`packages: [escalation]`) holds it. A package no worker names reaches nobody, so adding one to a shared library changes no worker until one asks for it (pk:43, pk:55). A worker on another team cannot name it, and an org worker has no team, so no team library reaches it (wp:87-91). The team's library is searched before the org's (wp:117-119). A package in a worker's own packages/ folder is held by that worker always, with no line needed, and org/packages/ can be named by any worker (pk:42-44).
6. You edit teams/support/references/refund-policy.md, add a new worker folder with its WORKER.md, and add a block to a package's blocks/, all while the app is running. Which change shows up without a restart? *(edge case)*
   Answer: Only the reference edit. A reference is read from its file whenever an execution context is built, so the edit reaches the next request. A read already in progress keeps the text it started with (dd:253, dd:393). Nothing watches the folder, which is read once at startup (wd:956, dd:388). A new WORKER.md needs a restart. A new or removed block needs `fsdev gen` and a restart, and a PACKAGE.md edit needs a restart (pk:36, pk:145). The same file edit to a resources/ document would not change the row an organization already holds (dd:275).
