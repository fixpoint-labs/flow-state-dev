## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are building the support desk on Flow State. Does the framework log Alice in for you, and if not, what does your app have to hand it on each request?
   Answer: No. Flow State does not store secrets, run OAuth or look up users. Your app checks the credential the request carries (a session cookie, a JWT, a signed header) and returns the caller's identity, a principal of `{ userId, orgId }`, from the flow's `authentication.resolvePrincipal` hook. The framework treats that `userId` and `orgId` as authoritative. It cannot check that `userId: "alice"` really belongs to whoever sent the request; that check is your job. Facts sec. 1 (auth:12-29, 48-50, 564-570; coreAuth:73-77) and sec. 3 (coreAuth:122-145).
2. Bob is signed in, and his client calls the `support` flow with `{ userId: "alice" }` in the request body. The flow has a resolver that reads the session cookie. Whose identity does the request run under? And what changes if the flow has no resolver at all? *(edge case)*
   Answer: With a resolver, the body is ignored. Identity comes from the resolver's verified principal, so the request runs as Bob (creating a session with body `userId: "alice"` gives a session owned by `bob`). An `orgId` in the body is never read either. Without a resolver, the development default takes `userId` from the body, so the body does name the user. What still guards an existing session is its binding: a session created for Alice and then claimed as Bob is refused (`UserBindingMismatchError`), and nothing from that request is written. A body field never sets identity once a resolver is configured. Facts sec. 4 "A body field never sets identity" and "Session binding" (engT/management-route-auth.test.ts:327-355, 623-632; engT/principal-org-spoofing.test.ts:89-130; engT/binding-immutability.test.ts:54-81), flag 1.
3. Alice has Bob's session id, maybe from a shared screenshot, and asks the support flow for that session. What does she get back, and does the app need to keep session ids secret? *(edge case)*
   Answer: She gets `404 Unknown session`, the same answer as for an id nobody has used, so the reply doesn't even show that the id exists. The framework checks that the caller owns what the URL names; you don't write that check. Ids are addresses, not secrets: nothing depends on keeping them private, so they don't need to be unguessable. Facts sec. 4 (auth:356-360, 371-372, 477-480, 490-493; engT/management-route-auth.test.ts:218-232).
4. Alice works for both `acme` and `globex`. She opens a support session while acting for `acme`, then switches to `globex` and asks for that same session with a valid credential. What happens, and can she move the session over to `globex`? *(edge case)*
   Answer: She gets `403`. The session was stored with organization `acme`, and she is now acting for a different organization; acting for `acme` she gets `200`. A session's user and organization are fixed when it is created and can't be changed later. A request that claims a different organization is refused (`OrgBindingMismatchError`) before anything is written. To work under `globex`, she creates a new session. Facts sec. 4 (auth:361-375, 502-524; engT/org-boundary-routes.test.ts:184-216; engT/binding-immutability.test.ts:110-136).
5. Two customers share one support deployment, and both happen to use session id `chat-1`. What keeps their sessions apart? Does that also keep apart a user's saved preferences (user-scope state)?
   Answer: The tenant id, sent as an HTTP header (`x-tenant-id` by default), which you set from a gateway or a client `fetch` wrapper you trust. Under two tenants the same id is two separate session records, each with its own session state, session resources and request history. A read with the wrong tenant header, or none, gets `404`. With no header the deployment is single-tenant. A tenant splits sessions only. User and org records are keyed by user and organization and are shared across tenants, so a user's preferences are not separated by tenant unless you encode the tenant into the id you pass. The framework doesn't check the header against the credential. Facts sec. 5 (sas:509-523; engT/tenant-route-isolation.test.ts:74-104; engT/tenant-store-isolation.test.ts:63-80; pers:260-265), flags 2-3.
6. A teammate writes a resolver that returns `{ userId: "anyone" }` for every caller and points out that the flow has `requireUser: true`. Does that mean every request comes from a verified user? Where does real enforcement go? *(edge case)*
   Answer: No. `requireUser: true` is the default and only checks that some `userId` exists after the resolver and any `defaultUserId` fallback have run; with none, the request is rejected with 401. It is a presence check, not an authentication check, so `"anyone"` passes it. Real enforcement goes in `resolvePrincipal`: return `null` (401 on a `requireUser: true` flow) or throw `PrincipalResolutionError` for a bad credential, or look the user up in your own store before returning them. For server callers, `createBearerSecretPrincipalResolver({ secret, principal })` throws a 401 on a wrong secret and returns `null` when the header is missing. Facts sec. 3 (auth:118-134, 203-207; coreAuth:185-191; engT/transports/createBearerSecretPrincipalResolver.test.ts:48-87).
