## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In the support desk, once draftReply has answered a ticket you want a summarizeTicket block to write a short summary of the conversation. The user should not wait for it, and if the server crashes and the summary is lost, that is fine. Which of the three mechanisms do you use, and how long does that work last?
   Answer: A side chain: add .sideChain(summarizeTicket) after the reply step. The chain moves on at once and the next step still gets the reply's value. The request waits until the side chain settles before it closes, so the user never waits for it. The work outlives the sequencer but not the request, and a crash drops whatever had not finished. Fits use cases like memory writes and auto-titling. Facts 14, 16-18, 23, 72, 82.
2. A buildReport action takes ten minutes, and the user closes the browser tab partway through. Which mechanism keeps the report going, how do you turn it on, and what does the user's client do afterwards?
   Answer: A queued run. This is a host setting, not a setting on the action: pass a worker adapter to createFlowState, e.g. createFlowState({ flows, stores, worker: bullmqWorker({ connection }) }). Every action on that host then goes through the queue. The POST returns a request id, a worker picks the job up from Redis and runs it against the shared stores, so the browser connection is not what keeps it alive. It is the same request with the same id in the same session, not a new session. The client can attach to the same stream again later and pick up from a sequence number. Facts 1, 27, 28, 73, 83.
3. Your team keeps support tickets on a task board. A colleague says the board is the app's background queue, so anything put on it will run by itself. Are they right?
   Answer: No. A board is a stored list, and its tasks stay at their current status until some request drains the board. The drain has no lifetime of its own, so a board alone is not a background queue. Work outlives the request only when a board in delegation mode hands each row to a dispatch run: the drain returns once the rows are handed out, and each run settles its row later. The background work is those dispatch runs. Facts 6, 13, 74, 87.
4. A dailyDigest has to run every morning at 7, with no user signed in. What starts it, and does the framework keep a clock for it?
   Answer: The framework does not run a clock, and a flow cannot start itself. The flow declares a schedule, a named entry with a cron string (defineScheduleBinding under schedules.static). A scheduler outside the flow, on the host, calls that entry's dispatch endpoint when the time comes. Examples are a platform cron, or the repeatable-job scheduler when you use BullMQ. The call is checked like any other request. The result is a fresh run with no caller, not the continuation of an earlier run. Facts 61-63, 68, 69.
5. After draftReply has streamed its answer, summarizeTicket, running as a side chain, throws an error. What does the user see, what is the request's final status, and where would a developer find the failure? *(edge case)*
   Answer: The user sees nothing, because no item reaches their stream. The request still ends completed, since a failed side chain does not fail the request. The failure is logged, and the failed block trace shows up in the DevTool. That is the trade for not making the reply wait. Facts 4, 20, 77.
6. A ticket conversation dispatches an investigate run for the company 'Acme', using session: { key: (input) => input.company }. Later the same conversation dispatches 'Acme' again, and a different conversation also dispatches 'Acme'. How many dispatch runs exist, and what does each dispatcher call return? *(edge case)*
   Answer: Two. A key is scoped to the conversation. The second dispatch from the same conversation goes back into the existing session rather than creating one, so it returns adopted: true. The dispatch from the other conversation is a separate run. Each call returns { sessionId, requestId, adopted } as soon as the runtime accepts it, and none of them returns the investigation's result. To get the findings, have the run write them somewhere both sides can read, such as a user-scoped resource or a task board. Facts 43-45, 59, 75, 79.
