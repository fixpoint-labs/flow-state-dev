## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk's `handleTicket` flow has to call your own order API in the middle, between `cleanMessage` and `draftReply`, to fetch the customer's refund status. Which kind of block do you write, and why that kind and not a generator?
   Answer: A handler. A handler runs your code, and its `execute(input, ctx)` can be any async function, so a `fetch` to your API inside it is plain TypeScript (facts 2, Handler: `core/types/block.ts:1076`; handler is the kind for non-model work, `old:17`). A generator asks a model to write, which is not this job. On the 'who decides' axis, handler is 'your code decides' (facts 3 table).
2. `handleTicket` is `sequencer().step(cleanMessage).step(draftReply)`, running on a SQLite store. The process is killed after `cleanMessage` has finished and while `draftReply` is running. What happens to the run, and when it is continued, what runs again? *(edge case)*
   Answer: Durable execution is on by default on stores that persist (filesystem, SQLite, Postgres), so the run is not lost: it is listed as `interrupted`, and continuing it (a Continue action or the DevTool's per-run Continue) keeps the same request id and does not start over. It does not pick up on its own the moment the process restarts. On continue, `cleanMessage` is not run again: its recorded output is reused and its `execute` is skipped. `draftReply` runs again, because it had no recorded output when the process died. (facts 6, 'A finished block is a checkpoint': `dur:11`, `dur:32-36`, `memo:7-13`, `goals/continue-interrupted-run/*`)
3. Same crash, but the app runs on the default in-memory store. Does the same answer hold? *(edge case)*
   Answer: No. Durable execution is not on for in-memory stores, so there is no checkpoint to continue from and no recorded output to reuse (facts 6: `dur:11`, `dur:32-36` table). The same is true of waiting: `ctx.suspend()` throws on a host without durable execution (`dur:42`).
4. You want the model in `draftReply` to be able to run the whole `handleTicket` pipeline as one tool call. Can a sequencer be given to a generator as a tool, and what does the model see of it?
   Answer: Yes. A generator's `tools` accepts a block of any kind (`GeneratorTool = BlockDefinition<any, any>`), and a sequencer is itself a block. The model sees the same three things it sees for a handler tool such as `lookUpOrder`: the block's `name`, its `description`, and its `inputSchema` as the parameters. It does not see the steps inside. What the sequencer returns (its last step's output) goes back to the model as the tool result. (facts 5: `core/blocks/generator.ts:422`, `:922-952`; `core/blocks/sequencer.ts:1233-1240`; `old:152`)
5. What does `cleanMessage` have to declare so that `draftReply`, the next step, can trust the value it receives? What happens if the two don't match?
   Answer: The producer declares an `outputSchema` and the consumer declares an `inputSchema` (both Zod schemas). In `.step(cleanMessage).step(draftReply)`, the type of `draftReply`'s input comes from `cleanMessage`'s `outputSchema`, so a mismatch is a TypeScript error unless you reshape the value with a connector (`.step(connector, block)`). At run time both sides are checked too: output against the producer's `outputSchema`, input against the consumer's `inputSchema`. (facts 8: `core/blocks/sequencer-methods.ts:163-181`; `core/blocks/internal/build-block.ts:356-364`)
6. Your order API starts sending back a field `lookUpOrder`'s `outputSchema` doesn't allow, and `lookUpOrder` returns it as is. Separately, a teammate deletes `cleanMessage`'s `outputSchema` to quiet a type error. What happens in each case? *(edge case)*
   Answer: The rejected output throws and fails `lookUpOrder`. A block cannot return a value its `outputSchema` rejects, because output is validated after `execute` runs (facts 1, 7: `core/blocks/internal/build-block.ts:152-170`, `:358-364`). The failure shows in that block's trace row (`block_trace.error`, `items:59-112`). When the schema is deleted, it falls back to `z.any()`: nothing is checked at run time, and the next step's input is typed `any`, so the contract is gone and the type error is hidden, not fixed (facts 8: `core/blocks/internal/build-block.ts:210-211`).

## 5 · Fact check

Checked against the code: the page as pass 4 read it after the page as it was kept, sha256 426825a564b5.

- On a store that persists, a run that dies after cleanMessage picks up at draftReply, and the message is not cleaned twice (stated as automatic behaviour of a finished block being a checkpoint). Untrue: A dead run does not resume by itself. The request is marked interrupted and has to be continued (the /continue route or `lost.continue()` on the client). Completed blocks are then replayed from their recorded output instead of re-run. Resuming from the checkpoint also needs a durable host. Sequencers checkpoint at every step boundary, and recovery then runs through the continue route and the sweeper. (docs/architecture/execution-and-errors.md:390 and :418-430 (checkpoints and replay); docs/architecture/server-and-client.md:191 (`for (const lost of await fsd.requests.interrupted()) await lost.continue()`); packages/engine/src/routes/recovery-routes.ts:1 (retry and interrupted-request recovery); page line 122)
- A block can pause the run for a user and carry on when the answer arrives, and the wait survives a restart (stated unconditionally). Untrue: Waiting, via `ctx.suspend` or `ctx.suspendForUser`, only works inside a durable action, and the page never says so. Suspend and the resume and answer endpoints need a `DurabilityProvider` on `RuntimeConfig`. Without one there is no pause that survives a restart. (docs/architecture/execution-and-errors.md:390 ("combine it with a `DurabilityProvider` on `RuntimeConfig` to enable `ctx.suspend()` and the resume endpoint"); docs/architecture/execution-and-errors.md:~418 ("When a block calls `ctx.suspend()` inside a durable action"); page line 123)
