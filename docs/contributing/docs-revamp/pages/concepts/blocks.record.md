## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk's `handleTicket` sequencer needs to fetch the customer's order from your own orders API before `draftReply` writes the answer. Which kind of block do you add, and why that one?
   Answer: A handler. A handler runs your code, and its `execute(input, ctx)` can be any async function, so calling `fetch` inside it is plain TypeScript. Handlers are the kind for work that does not involve a model. On the 'who decides' axis, your code decides. A generator would hand the decision to the model, and an evaluator only asks a model typed questions. Facts: `core/types/block.ts:38-42`, `:1076`; `old:17`; section 3 table.
2. `handleTicket` runs `cleanMessage`, then `draftReply`. The process is killed just after `cleanMessage` finishes, on a store that persists (filesystem, SQLite or Postgres). When the run is continued, what runs again? *(edge case)*
   Answer: Only `draftReply`. `cleanMessage` finished, so its recorded output is reused and its `execute` does not run again. `draftReply` has no recorded output, so it runs. The run does not start over. It picks up at `draftReply` when someone continues it, for example with the DevTool's Continue. It does not resume on its own. Facts: durable execution is on by default for persisting stores (`dur:11`, `dur:32-36`); the runtime checkpoints at every step boundary (`dur:9`); recorded outputs are injected and completed blocks are skipped (`memo:7-13`); the run is continued rather than restarted (`goals/continue-interrupted-run/*`).
3. The same crash happens, but the app is running on the default in-memory store. Can the run be continued? *(edge case)*
   Answer: No. Durable execution is not on for in-memory stores, so no checkpoint exists and a crashed run cannot be continued. To get checkpoints, use a store that persists: filesystem, SQLite or Postgres. Facts: `dur:11`, `dur:32-36`; section 8.
4. Can you hand the whole `handleTicket` sequencer to a generator as a tool, the way you hand it `lookUpOrder`? If so, what does the model see of it?
   Answer: Yes. A generator's `tools` accepts a block of any kind (`GeneratorTool = BlockDefinition<any, any>`), and a sequencer is itself a block. The model sees the same three things it sees for a handler: the block's `name`, its `description`, and its `inputSchema` as the parameters. It does not see the steps. What the sequencer returns (its last step's output) goes back to the model as the tool result. Facts: `core/blocks/generator.ts:422`, `:922-952`; `core/blocks/sequencer.ts:1233-1240`; `old:152`.
5. What does `cleanMessage` declare so that `draftReply` can trust what it receives, and what happens if a value doesn't fit?
   Answer: `cleanMessage` declares an `outputSchema` and `draftReply` declares an `inputSchema`. Both are Zod schemas. Each is checked at run time: the producer's output after its `execute`, and the consumer's input before its `execute`. A value that a schema rejects throws and fails that block, and the error shows in the block's trace row. Facts: `core/blocks/internal/build-block.ts:152-171`, `:356-366`; `items:59-112`.
6. A teammate edits `cleanMessage` so its output is a different shape than `draftReply`'s `inputSchema` expects, and leaves `.step(draftReply)` as it was. Does TypeScript flag it? When is the mismatch caught, and how do you fix it without changing either block? *(edge case)*
   Answer: TypeScript does not flag it. `step(block)` takes `BlockDefinition<any, ...>`, so the next block's input is not compared with the previous step's output. The mismatch is caught at run time: `draftReply`'s input check rejects the value and the block fails. To fix it without editing either block, reshape the value with a connector: `.step(connector, draftReply)`, where the connector maps `cleanMessage`'s output to `draftReply`'s input. If either schema was left off, it defaults to `z.any()`, so nothing is checked on that side. Facts: `core/blocks/sequencer-methods.ts:163-181`; `build-block.ts:210-211`, `:356-366`; `packages/core/test/build-block.test.ts:50-65`.

## Reference rows

- Visibility flags on an item: `client` streams it to the user, `history` keeps it in the conversation, and the default for each block kind (a per-kind default-visibility table). The page keeps one clause saying the example's reply is shown and kept, and links to the row. → R-06
- Schema checks: the output is checked against `outputSchema` after `execute`, the input against `inputSchema` before it, and a connector reshapes between steps (a check-order table with the connector signature). The page keeps only the guarantee that each side declares its half and the framework checks it. → R-01
- Failure and default rows: an output the `outputSchema` rejects fails the block, and the error names the block and field and shows in the trace. A missing `outputSchema` defaults to `z.any()`, so nothing is checked and the next input is untyped. Both are check and default behaviour with a failure shape. → R-01
- Resume behaviour by store: a finished block's output is recorded and a continued run skips finished blocks on a persisting store, and on the in-memory default nothing is checkpointed so a crashed run cannot be continued. The page keeps the first three sentences, which are the model, and drops the store caveat. The page's link to `../reference/blocks.md` for continuing a run should point at the durable-execution page, since that is where the sitemap puts how to continue a run. → R-17
- Pause and resume row: a block can suspend the run for a user answer, and the wait survives a restart only on a persisting store. The restart and store clause is crash behaviour. The page keeps the idea that a block can wait for a user. → R-17
