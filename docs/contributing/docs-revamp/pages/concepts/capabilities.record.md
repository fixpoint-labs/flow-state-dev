## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. `draftReply` needs to look up orders. That takes a `lookUpOrder` tool, a prompt section listing the customer's orders, and an `ordersResource` to hold them. With an `orders` capability, how many places do you edit to give `draftReply` all three? And when a second tool is added to order lookup next month, how many places do you edit then?
   Answer: One each time. `draftReply` gets the tool, the context and the resource from the single line `uses: [orders]` (use:19-27; bi:124-159). A capability is a bundle of resources, context and tools under one name, and the block that lists it in `uses` gets all of it (ty:2-9; use:8). Next month you add the new tool once, to the capability's `tools` preset, and every block that lists `orders` gets it. You don't hunt down each generator's `tools` array (aut:361; fn:225-236).
2. `summarizeOrders` should see the order context in its prompt but must not be able to call `lookUpOrder`. How do you set that up without writing a second capability?
   Answer: List the capability with that preset turned off: `uses: [orders.presets({ tools: false })]` (ct:241-255; bi:161-186). A preset you turn off contributes nothing. The capability's always-on parts, such as its top-level `resources`, still install (bi:161-186). There is a second true answer: give the generator its own `tools:` list, since that is the complete list of tools the model may call and it drops the tools the capability brings. Context, resources and helpers arrive either way (fn:106-118; use:154-172).
3. Support wants a customer's order history to follow them from conversation to conversation, not reset with each one. Where is `ordersResource` declared, and what do you change to get this?
   Answer: Declare it statically on the capability, in its top-level `resources` or in a preset's `resources` (ty:240-245, ty:64-67; bi:141-159). It can't come from a function entry in `uses`, because resources have to exist before the block runs (ty:590-598; aut:274, aut:287). The flow gets the resource from the block (bi:188-216). Scope is set on the resource, not on the capability (ty:65-66). So make a factory, `createOrdersCapability({ scope: "user" })`, that builds `defineResource({ scope: options.scope, ... })` (aut:294-308; kb:80-85). Session scope gives one record per session. User scope gives one record per user per org, which is what follows the customer (state-and-scopes.md:25).
4. You want to ship order support as a whole feature: its own screens, the flows behind them, and a folder in the app. Is that a capability or a kit?
   Answer: A kit. A kit "packages a feature so an app installs it with one config object" through `createFlowState({ kits: [...] })`, and its `install` returns the flows it serves. Resources, views and capabilities ride on those flows (dk:4-11). A capability attaches to one block through `uses`, and its parts land on that block (ty:6-8; use:10). So a kit can contain the `orders` capability, but a capability does not contain a kit. (The fact sheet derives this rule from the two definitions and flags it [verify].)
5. `draftReply` and `escalateTicket` both list `uses: [orders]`. You change `escalateTicket` to `uses: [orders.presets({ tools: false })]`. Does `draftReply` lose `lookUpOrder`? Does `escalateTicket` still have the orders resource? *(edge case)*
   Answer: `draftReply` keeps the tool. `.presets()` returns a new capability and leaves the original unchanged, so other blocks that list `orders` don't see the change (ct:80-93; bi:448-492). `escalateTicket` still has `ordersResource`. Turning off the tools preset removes only what that preset contributes, and the top-level `resources` still install (bi:161-186). The resource is installed once even though two blocks bring it (ct:143-153; bi:218-240).
6. A teammate edits `draftReply` to add its own `tools: [sendEmail]`. Afterwards the model never calls `lookUpOrder`, but the order context still shows up in the prompt. What happened, and how do you get the lookup back? *(edge case)*
   Answer: A generator's own `tools:` is the complete list of tools the model may call. Once it is declared, the tools a capability brings through its `tools` preset are dropped (fn:106-118; use:154-172). Context, resources, state and helpers still arrive, which is why the prompt section is still there (use:170-172). To get the lookup back, remove the block's `tools:` list (a generator with none receives the capability's tools, fn:225-236; use:166) or name `lookUpOrder` in the list too, since a tool the block names itself stays (fn:161-176).

## Reference rows

- Dependencies: a capability's declared dependencies install transitively, and a base capability shared by two is installed once. → R-10
- Refusals: `.with()` throws at the call site for a key that matches no preset when the capability has no config, or when its config is a closed object schema and the key is not one of its fields. For schemaless, scalar or passthrough config, non-preset keys pass through as config. An unknown preset name passed to `.presets()` throws when a block builds with that capability ("Unknown preset"), not at the `.presets()` call. → R-10 (corrected by pass 5)
- `.with()` routing: a key naming a preset toggles it. A key that is a config field is config. A key that is neither throws for a config-less or closed-schema capability, and passes through as config for schemaless, scalar or passthrough config. A non-object bag is treated entirely as config. → R-10 (corrected by pass 5)
- Open config validation: a wrong shape is a build-time error; the same capability used twice with conflicting config throws, identical config is allowed. → R-10
- Primitives: `.presets({ name: boolean })` and `.config(value)` compose in either order; `.with()` is both in one call. → R-10
- Helpers: a capability with no `fns` installs resources and state and exposes nothing on `ctx.cap.{name}`. → R-10
- What each capability field installs and where it lands (resources, state schemas, helpers, context formatters, tools); validation happens at factory time. → R-10
- Generator `tools:` slot: declared slot (even `[]`) drops capability tools; omitted slot lets them through; context, resources, state and helpers always arrive. → R-10
- Control tools: reach the model whatever `tools:` says, because they are built inside the capability and cannot be named in a list. → R-10
- Type inference map: each capability schema field and the `ctx` location it types. → R-10
- Merge and collision rules: a resource accessor, a target state or a `stateSchema` field declared by both the block and a capability (or by two capabilities) must use the same reference or schema, or the build throws. A block's own declaration wins only for singletons such as `model`, `providerOptions` and `caching`. → R-10 (corrected by pass 5)
- Addressing modes: `ctx.parent` cannot be declared by a capability; the other three are. → R-01
- Inference limit: preset-only or open-config schemas merge at runtime but are not reflected in `ctx` types. → R-10
- Limit: inner capability schema contributions do not flow to the block using the outer one. → R-10
- Static versus dynamic `uses`: function entries contribute context, tools and `controlTools` at runtime and nothing to types. → R-10
- Type-only overrides: `sessionStateType`, `resourcesType`, `targetStatesType`, `sequencerStateType`, compile-time only. → R-10
