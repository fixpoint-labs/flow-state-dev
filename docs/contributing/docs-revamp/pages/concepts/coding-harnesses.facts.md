## If you know coding agents

7. A coding agent here is the thing you already use at a terminal: it takes a prompt, works in an agentic loop in a directory, and reports what it did. `ca:8-11`: "a coding agent driven as a block. You hand it a prompt, it works in its own agentic loop in a directory you point it at, and it hands back a handle describing what it did." **[page]**
8. What is the same: the agent is the vendor's own (Claude Code through the Claude Agent SDK, Codex through the Codex CLI in a subprocess, Cursor through Cursor's local runtime via the Cursor SDK). `ca:16-20`. **[page]**
9. What is different: the framework does not run the agent at a prompt; it runs it as a step with a typed input and a typed result, in a directory it prepared, and decides when the work counts. `ca:8-11`, `hm:7-9`. **[page]**
10. What it says, runs and changes arrive in the flow's item stream as it goes. `ca:9-11`. **[page: one clause]**

## A coding agent as a block

11. A harness is a block. `ca:22` ("Either one is a block, so a sequencer can step it"); `ca:24-29`:
    ```ts
    import { claudeCodeAgent } from "@flow-state-dev/claude-code";
    const agent = claudeCodeAgent();
    // seq.step(agent) with input { prompt: "Tidy the imports in src/." }
    ```
    (Import path corrected per item 2.) **[page]**
12. Input is `{ prompt: string, attachments? }`. `core` `harnessRunInputSchema`, `core:135-139` (read region before `:120`: `prompt: z.string()`, `attachments` optional). Where the run works and which conversation it continues are not input: `cwd` and `resume` reach it as resolved configuration (`core:130-134` comment; `ca:31-36`). **[page: prompt only; the rest ref]**
13. The result is a handle. Every harness returns the same shape: `source`, `status` (`running`, `completed`, `errored`, and `dispatched` in the schema), `sessionId`, `url`, `dispatchedAt`, `outcome` (`finished`, `stopped-at-limit`, `failed`, or `null`), `finalMessage`, `usage`, `cost`. `core:201-219`; `ca:44-52`. A field the agent did not report reads `null`. `ca:54-57`. **[page: status and outcome; the rest ref]**
14. A run that fails returns no handle; the block throws. `ca:72`. `harnessFailureKind(error)` from `@flow-state-dev/core` returns `"unknown-conversation"` or `null`. `ca:72-79`. **[ref]**
15. Code that reads the handle works the same whichever agent produced it. `ca:13-14`, `ca:41-42`. **[page; answers Q4]**
16. Each agent adds fields of its own beside the shared ones (Claude Code: the SDK's result code and tool names; Codex and Cursor: token breakdown and failure message). `ca:59-62`. **[ref]**
17. A harness that reports a plan records it in the `observed-plan` collection. Codex records none. `ca:81-119`. **[ref]**

## Its own checkout

18. **Each task gets its own directory, derived from who the run belongs to plus the board, the issue and the phase.** Any later session works out the same path from the same inputs without looking it up. `hm:438`. The path is a pure function of the task, never read back. `packages/harness-manager/src/workspace.ts` header (derivation). **[page; answers Q1]**
19. **The run works on its own git branch in a git worktree.** `wsr:254` ("`checkout/` a git worktree on the run's branch"); `hmr:38` ("every run gets a new branch of `sourceRepo`... the run's checkout sits under `root`"). The branch is `<prefix><name>` (the app's `branchPrefix`, default `fsd/`) and the folder `<root>/<name>`, where the name is a slug of the task's title plus six hex of what keeps one run apart from another (`packages/harness-manager/src/workspace.ts`, "A run's name"). `hm:272` shows the older form `conductor/<scope>/<issue>--<task-id>--<phase>` for a task that names an issue under `harnessFeature`. **[page: "its own branch"; the name pattern is ref]**
20. **A remote repository is cloned once and each run gets a worktree of the clone.** `wsr:259`: "the host keeps one clone of each remote under `root` and gives every run its own branch in `checkout/`." **[page: one clause]**
21. **A repository on the machine can be listed in `localRepositories`; then a run gets a worktree of that repository itself.** `wsr:280`; option docs at `packages/workspace/src/local-host.ts:204-232`. **[page: one clause]**
22. **Can it touch your working tree? Not your working tree, index or branches; it can move refs.** For a listed local repository: "The repository's own branches, index and working tree are never touched." `wsr:291`. But "A run in a listed repository acts with your trust... Git shares branches, tags and remote-tracking refs between worktrees, so a run can create or move them. ... To keep a run apart from a repository's branches, have the host clone the repository instead of listing it." `wsr:307`; `local-host.ts:225-227`. Git refuses a branch already checked out in another worktree, "including your own checkout of a listed repository". `wsr:323`. **[page; answers Q1: runs never touch your working tree or index; they share refs, so a run can create or move branches and tags in a listed repo. Pointer to the workspace options.]** The page does not say a repository left out of `localRepositories` is cloned: a clone happens only for a remote the host may reach (`remotes.allow`, or a `file://` URL), and a bare local path left out of the list is refused (`packages/workspace/src/local-host.ts:229`, `packages/workspace/src/remotes.ts:187`). **[ref]**
23. **The framework refuses to point a run at the host's own repository.** `assertDistinctRepository(variable, repo, dispatcher)` throws when the source repository is the one the host itself lives in: a different path inside it, another of its worktrees, or a symlink to it. `packages/harness-manager/src/guards.ts:102-133`; tests `packages/harness-manager/test/guards.spec.ts:55-96`. The host passes where it lives, or `[]` for none; a location it cannot resolve is refused. `hm:670-683`. Applies to a manager built with `workspace: { root, sourceRepo, baseRef }`; for the kit's workspace host the source is the host's `source`. **[verify: whether the kit path runs this guard. `assertDistinctRepository` is called by the manager's config door; read of `kit/` and `coder-flow.ts` finds no call. Keep off the page, or say only that it is a Reference row.]**
24. **The agent is not confined to the checkout by the framework.** "The sandbox you configure on the harness is the fence for a runaway command, not this deadline." `hm:454`. Neither does the manager bound what the run spawned. `hm:454`. Claude Code's kit harness allows `Read`, `Write`, `Edit`, `Bash` with `acceptEdits`, reads the folder's own settings with every hook off. `cck:10-16`, `cck:48-58`. Codex runs in `workspace-write` sandbox mode unless options say otherwise. `cxh:5-7`, `cxh:38`. Cursor's sandbox is off, "a coding run already works in its own worktree". `cuh:6-7`, `cuh:36`. **[page: one sentence that the checkout is where it is pointed, not a jail; per-agent settings are ref]**
25. **A lease keeps two attempts out of one tree**: a lock file beside the checkout, taken before provisioning and released on every exit. `hm:442`. **[ref; page at most "one run holds a checkout at a time"]**
26. **A retry finds the same checkout with its work.** The path is derived, so a retry, or a run resumed in another session, lands in the same directory. `hm:27`, `hm:438`. Provisioning is idempotent and the second call leaves uncommitted work untouched: `packages/harness-manager/test/workspace.spec.ts:103-117`. Checkouts "stay on disk after `release`, so a retry finds them." `wsr:329`. **[page: one sentence]**
27. **A checkout lives on the machine that made it**, unless the workspace host has a held-work store; then the run's commits and uncommitted changes are saved at the end of each turn and a retry on another machine gets them back, with the coding agent starting a fresh conversation there. `hm:446`; `hmr:75`, `hmr:823`. **[ref]**
28. **A new checkout has no installed dependencies.** A workspace host `setup` command, such as `pnpm install --frozen-lockfile --prefer-offline`, runs once per fresh checkout before the harness starts. `hm:448`; `local-host.ts:248-259`. **[ref; page may name it for the "failing test" example: the fixer needs deps installed]**
29. **A run on a project works in the project's repository**, as a fresh branch, as long as the host allows that remote. A project with no repository starts from empty files and saves to the project's files. `wp:613-615`. **[ref; belongs to Projects]**
30. **Users get different checkouts.** Two users get different checkouts and branches for the same issue-phase; two organizations likewise. `packages/harness-manager/test/workspace.spec.ts:963-1010`. **[page: one clause if the page names the owner]**

### What is stored (the four questions)

31. **The checkout** (a directory and a branch). Owner: the user the run belongs to; on a board kept for a whole organization "a row's run belongs to the user who started it, and another user's drain doesn't run it". `hm:440`. Who can see it: whoever has the host's disk; no framework read path. Where: on the machine that ran it, under the workspace host's `root`, unless a held-work store is configured. `hm:446`. How many: one per task and phase (per run name); retries reuse it. `hm:438`, `wsr:329`. **[page: owner and where; count is ref]**
32. **The run record** (`runs/**`). Owner: the user (scope `user`, the same principal as the board). `packages/harness-manager/src/run-record.ts:22-46`, `:349-355`. Who can see it: the run's user, from any later session. `run-record.ts:30-46`. Where: the app's store, as a resource collection. How many: one row per issue-phase (per run), no pruning: "Nothing prunes these rows". `run-record.ts:46-48`; `hmr:827` ("No retention policy. Run records grow without bound."). It records the checkout path, branch, harness session id, how the last attempt ended, the checks, `place` and `held`. `hm:25`, `hm:446`, `hm:310`. **[ref: what it records; page: one line that a run keeps a record]**
33. **The subscription usage reading** (`harness-usage/**`). Owner: the user (user scope). Who can see it: through the `harnessUsage` query only; "A client can't read the collection directly." `hm:658-660`. Where: the app's store. How many: one current record per user per harness; no history; the account kept only as a hash. `hm:646-654`. **[ref]**
34. **Readiness rows.** Not stored: "The rows describe this machine, so they live in the process and are never stored." `hm:526-527`. **[ref]**
35. **A question or review hold** lives on the task as an open hold; see "Asking you a question". Owner: the board's task. Visible in the user's Inbox and in `getTask`'s open `questions`. `hm:112`, `hm:140`. **[page]**

## A verdict before it counts

36. **"The agent stopped" and "the task is done" are separate.** `hm:9`: "A verdict is read before the row settles, so a run that produced nothing never closes as done." **[page; answers Q2]**
37. **The manager's steps for a claimed row**: open the run row, build the prompt and take the checkout, run the harness, read the verdict, then settle or re-queue. `hm:17-33`. **[page; the figure *A supervised run*]**
38. **The harness step has a deadline.** `runTimeoutMs` bounds the step; the manager fires the step's abort signal when it passes; how promptly the harness returns, and what the run spawned, are not the manager's. `hm:452-454`. The kit's default is 20 minutes (`cf:66`, `cf:88`). **[page: one clause; ref]**
39. **Status decides succeeded or failed.** `handle.status === "completed"` is the manager's succeeded-or-failed read (`packages/harness-manager/src/manager.ts:3054`). `hm:31`: "`status` is whether the run terminated normally, and the manager's succeed-or-fail verdict is read from that alone." **[page]**
40. **`outcome` is the run's own word for how it stopped**: `finished`, `stopped-at-limit`, `failed`, or `null` for no terminal result. It is the framework's spelling, not a vendor's, so two harnesses settle identically. `hm:31`; `core:201-209`. **[page]**
41. **A run can end cleanly and not be finished.** A run that exhausts its turn or spend budget commits what it got through and reports `stopped-at-limit`. `hm:98`. A test shows a handle with `status: "completed"` and `outcome: "stopped-at-limit"`: `packages/harness-manager/test/completion-context.spec.ts:36-52`. **[page]**
42. **What counts as done is the phase's call.** A phase supplies the prompt builder and `isDone`. `isDone` is consulted only after a successful verdict (`status`). `hm:76-90`, `hm:96`. `isDone` gets `run.stopReport`, the handle's `outcome` exactly as reported, `null` included; an unknown value is never read as `finished`. `hm:96`; test `completion-context.spec.ts:60-119`. **[page: one sentence; the phase contract is ref]**
43. **The kit's phase: done when `outcome` is `finished`.** `cf:131` (`isDone: (run) => run.stopReport === "finished"`). So a run that stops at its limit is not done under the kit; the attempt fails and goes back with the reason. `cf:131`, `hm:33` ("Anything else is a failed attempt, re-queued with the reason, until the retry budget runs out"). **[page; answers Q2] [verify the exact "re-queued" wording against the retry path for a clean `isDone: false`: `hm:306-308` says a not-done attempt "fails and goes back to the board", with the next attempt's `run.feedback` naming why. Test: `packages/harness-manager/test/coding-phase.spec.ts:59-65`.]**
44. **The kit's checks.** With `checks: { commands, timeoutMs? }` on the kit, a run that changed files is done only when every command passes in its checkout. A run that changed nothing (a question) skips them. `cf:21-24`, `cf:101-113`, `cf:144-146`. A red command, a non-zero exit, a timeout, a skip, or a command that could not run, makes the attempt not done; the next attempt's brief names the command and the end of its output. `hm:308`; `coding-phase.spec.ts:43-49`, `:59-65`. With no checks named, a run is done on `finished` alone: `coding-phase.spec.ts:54-57`. The default for the checks' total time is 10 minutes. `cf:69`. **[page; answers Q2]**
45. **A command is a program and its arguments, run with no shell.** `&&`, `|`, `;` and similar are refused. **[ref]** `hm:333`.
46. **The commands run the checkout's own scripts, which the agent can edit.** "Treat a green result as evidence for whoever reviews the run, not as proof the agent left the scripts alone." `hm:337`. **[page: one sentence; honest limit]**
47. **A judge reads the run after the phase's check passes.** The kit turns on `goalJudge` by default (`judge` default true, `cf:81`, `cf:207`): an evaluation model reads the task's goal, the run's answer, its commits and the files they changed, and answers done, not done or ask, with a confidence. `goal-judge.ts:1-15`; `hm:278`. *Done* closes the task. *Not done* fails the attempt and the next attempt's prompt carries the judge's reason, except for a run that opened a pull request: that task waits on the pull request, the reason in a status note, and merging completes it (`manager.ts:625-627`). The third verdict puts a question to the user. A verdict below the floor (`GOAL_JUDGE_FLOOR`, 0.7, `goal-judge.ts:35`) counts as done. A judge that fails never fails the task. `hm:278`; tests `packages/harness-manager/test/judge.spec.ts:44-64`, `:101-137`, `:138`, `:166-185`. It only runs for a task that has a goal. `hm:278`. **[page: one sentence; the rest ref]**
48. **Review: a person can look at the commits before the task completes.** Off by default. The kit's `review` key, or a worker's `review:` line, turns it on. A run that committed waits; a run with no commits completes without a review; a failed run fails the attempt without one. `cf:77`, `cf:233`, `hm:132-138`. While it waits the task stays `in_progress` on the same attempt, the checkout is released, and the Inbox lists a review titled "Review the run's changes". `hm:140`. Accepting completes the task. Requesting changes sends the words to the same coding session for one more run on the same attempt. `hm:158-160`; tests `packages/harness-manager/test/review-changes.spec.ts:343-375`, `:426-470`. A review has no deadline unless the host sets `userDeadlineMs`; at the deadline the task completes and its output says `review: "deadline"`, to be read as not reviewed. `hm:162`; test `review-changes.spec.ts:529`. Needs a host with durable execution. `hm:166`; `review-changes.spec.ts:571`. **[page: that review is a gate you can turn on; rest ref]**
49. **Pull requests.** On by default in the kit: a task whose run opened a pull request is done when it merges, and cancelled when it closes unmerged. `cf:19-20`, `cf:79`, `cf:208`. **[page: one clause; ref]**
50. **An accepted run can land two ways in the reviewer's hands: open a pull request, or merge locally**, when the run was cut from a local repository; a run cloned from a remote offers plain Accept. `review-changes.spec.ts:621-710`, `:656`, `:673-684`. **[verify: option names; ref at most. Keep off the page.]**
51. **Before a task starts, the harness must be ready on this machine.** The kit's coding flow asks readiness before each task and a harness that cannot run fails the task at once, saying why; it never moves to another harness. `cf:9-11`, `cf:244-248`. **[ref: moved off the page in revise round 2; a failure detail]**
52. **Readiness answers whether a credential is there, not whether it works.** "A key that is set but rejected reads as ready and fails on the run's first turn." `hm:497-498`. **[ref]**

## Asking you a question

53. **A run that needs a decision writes its question to a path the prompt names, and stops.** Its work is saved, the checkout is let go, and the task waits on the question: it keeps its attempt, has no lease, and nothing settles it or starts another run while the question is open. `hm:112`; test `claim-board-question.spec.ts:30-55`. **[page, with caveat in item 4]**
54. **The question shows in the user's Inbox**, and in the task's open `questions` when read with `getTask`. `hm:112`; test `claim-board-question.spec.ts:44` (`openOwnHolds` → kind `question`). **[page; answers Q3]**
55. **The user answers from the Inbox, or by typing a line in the run's session.** Either goes through the board's `updateTask` action, naming the question. `hm:114-118`. `hm:432`: while a task waits on a question a line in its session answers the oldest open question. **[page: Inbox, and the line in the session]**
56. **The answer continues the same coding session, on the same attempt.** Once the task's last question is answered it takes one more turn on the same attempt, and that turn's run resumes the same coding session, in the same checkout, with the question and its answer in its brief. `hm:120`; test `claim-board-question.spec.ts:44-55` (`resume` is `sess_1`, `cwd` equal, task `completed` with `attempts: 1`); goal `goals/harness-manager/answered-run-continues-its-session/goal.md` (signal 3 is the discriminating one). **[page; answers Q3]**
57. **An answer spends no retry.** `hm:122`; test `claim-board-question.spec.ts:54`. **[page]**
58. **Nothing is spent while the user thinks.** `hm:112`. **[page: may fold into 53]**
59. **A question waits until answered or cancelled** unless the board's host sets a deadline; at the deadline it closes with a "no answer came" message and the next run goes on in the same session. A cancel closes it, starts nothing, and what the run committed stays. `hm:124`. **[ref]**
60. **The run can ask again**, each time at a path of its own. `hm:120`. **[ref]**
61. **A session the agent cannot find is replaced.** The manager records only a session the harness confirmed; if the agent cannot find the session a run asked to continue, the next run starts fresh with the brief, the question and the answer in its prompt. `hm:128`. **[ref]**
62. **Other things that hold a task on a person**: a judge's *ask*, saved work that disagrees with the run's record, a review, a tool approval. `hm:126`, `hm:140`, `hm:198`. **[page: one sentence listing]**
63. **Per-call tool approval is Claude Code only.** With `approveTools: true` a call the harness was not told it may make stops the run; the Inbox lists "Allow Bash?"; three answers (allow once, allow for this run, deny with note). `hm:177-223`. "Only Claude Code asks per call. Codex and Cursor take their sandbox and approval settings for the whole run, so they ignore the feed." `hm:223`. ## The four questions, answered from this sheet

1. **Where does the harness make its changes, and can it touch your working tree?** In its own git worktree on its own branch, in a directory derived from the task (items 18, 19). It does not edit your checkout's working tree, index or branches; with a repository you listed as local, it shares the repository's refs and can create or move them (items 21, 22). The framework does not confine what the agent runs; the sandbox on the harness does (item 24).
2. **The run says it is done. What has to be true before the task is marked complete?** The run's status is `completed` (the run ended normally), and the phase's check says done: under the kit, `outcome` is `finished` and, if the run changed files, every configured check command passes (items 39 to 44). Then the judge, on by default, must not say not done (item 47); a run that committed waits for a person's review when review is on (item 48); a task whose run opened a pull request waits for it to merge (item 49).
3. **The agent needs a decision from you mid-run. How does it reach you?** It writes the question and stops; the task waits on the question with no lease and spends no retry; the question shows in your Inbox and in the task's open `questions`; you answer in the Inbox or by typing a line in the run's session; the answer continues the same coding session on the same attempt (items 53 to 57). Caveat in item 4 for the kit's own worker.
4. **You switch from Claude Code to Codex. What changes in your flow?** The flow does not change. The worker's `harness:` line changes from `claude-code` to `codex`, and the Codex harness value is in the slot (`codexHarness()` in `fill`). The manager never learns which agent it drives; per-agent options, such as Claude Code's `detached: true` and the sandbox settings, stay inside the harness value (items 73, 76, 77). What Codex lacks: per-call tool approval, subscription-usage windows from runs, live steering, a plan (items 63, 83).
