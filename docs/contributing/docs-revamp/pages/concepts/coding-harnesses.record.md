## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. `engineering.coder` picks up the task "fix the failing test in `cart.test.ts`" while you have uncommitted edits open in the same repository. Where does the agent make its changes, and will it touch your edits?
   Answer: In a checkout of its own: a git worktree on its own branch, in a directory worked out from the task (who the run belongs to, plus the board, issue and phase). A remote repository is cloned once and each run gets a worktree of the clone (facts 18, 19, 20). Your working tree, index and branches are never touched. If you listed the repository as local, the run shares its refs, so it can create or move branches and tags. Having the host clone the repository keeps a run away from them (facts 21, 22). The checkout is not a jail, though. The framework does not confine what the agent runs; the sandbox set on the harness does that (fact 24).
2. The coder's run ends normally and reports that it is done. The kit has `checks: { commands: ["pnpm test"] }`. What has to be true before the task is marked complete?
   Answer: The run's `status` must be `completed`, and the phase must say done. Under the kit, that means `outcome` is `finished` and, because the run changed files, `pnpm test` passes in the run's checkout (facts 39, 40, 43, 44). After that, the judge (on by default, for a task with a goal) reads the goal, the answer and the commits, and it must not say "not done" (fact 47). If review is on, a run that committed waits for a person to accept it (fact 48). If the run opened a pull request, the task is done when that pull request merges (fact 49). The agent saying it stopped is not the same as the task being done; a verdict is read before the task settles (fact 36).
3. The coder runs out of its turn budget halfway through the fix. The run ends cleanly with `outcome: "stopped-at-limit"`. Is the task complete? If not, what happens next? *(edge case)*
   Answer: No. A run can end cleanly and still not be finished. `status` is `completed`, but the kit only counts a run as done when `outcome` is `finished` (facts 41, 43). The attempt fails and the task goes back to the board with the reason, which the next attempt's brief names, until the retry budget runs out (fact 43). The same happens if `pnpm test` is still red: the next attempt's brief names the command and the end of its output (fact 44). The retry lands in the same derived checkout, so the work already done is still there (fact 26).
4. Mid-run, the coder finds two ways to fix the test and needs you to choose. How does the question reach you, how do you answer, and what does answering cost?
   Answer: The run writes its question and stops. Its work is saved, the checkout is released, and the task waits on the question: it keeps its attempt, holds no lease, and nothing runs or settles while you think (fact 53). The question appears in your Inbox, and in the task's open `questions` from `getTask` (fact 54). You answer in the Inbox, or by typing a line in the run's session (fact 55). The answer resumes the same coding session, in the same checkout and on the same attempt, with the question and your answer in its brief (fact 56). It costs no retry (fact 57). A judge's "ask" or a review can also hold a task for you the same way (fact 62). Caveat (fact 4): this works when the phase's prompt names the question path. The kit's own coder prompt does not, so under the kit your Inbox receives the judge's "ask" and the review hold.
5. You move `engineering.coder` from Claude Code to Codex. What changes in your flow and your worker, and what stays the same?
   Answer: The flow stays the same. The worker's `WORKER.md` keeps `flow: coder` and its `harness:` line changes from `claude-code` to `codex`. The app fills the harness slot with `codexHarness()` (`fill: { [harnesses.slots.harnesses]: [codexHarness()] }`) instead of installing the `claudeCode()` kit (facts 3, 73, 76). The manager never learns which agent it is driving. Per-agent settings such as Claude Code's `detached: true` and each agent's sandbox stay inside the harness value (facts 76, 77, 81). Code that reads the run handle works the same for either agent (fact 15). Codex does lack some things: per-call tool approval, live steering, usage readings and a plan (facts 63, 83).
6. You switch the worker to `harness: codex`, but this machine has never had Codex signed in. A coding task is filed. What happens? And if a second user files a task for the same issue, do the two runs share a checkout? *(edge case)*
   Answer: The kit's coding flow checks readiness before each task. A harness that cannot run here fails the task straight away and says why, for example that Codex has no credential and you should run `codex login` or set `CODEX_API_KEY`. It never falls back to another harness (facts 51, 79). A coding agent only runs where its SDK is installed and a user is signed in or a key is set (fact 70). Two users get different checkouts and branches for the same issue and phase, and a run belongs to the user who started it (facts 30, 31).
