## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In handleTicket, cleanMessage returns { text, truncated } and draftReply takes a plain string. Where do you put the code that turns one into the other, and does either block have to change?
   Answer: Put it between the two steps, not inside either block. Either use a connector on the step that needs the new shape, `.step((cleaned) => cleaned.text, draftReply)`, or put it on its own line with `.map((cleaned) => cleaned.text)` between `.step(cleanMessage)` and `.step(draftReply)`. Both blocks keep their own schemas. The connector runs before the block, and what it returns becomes the block's input. `.map` is a plain function with no name and no schema, and it does not show as a step of its own in the trace. Fact sheet section 3 (sm:177-181, sm:219-221, ct:18-27, ct:39-43, old-comp:125); answer key Q1.
2. Before drafting a reply, handleTicket should look up the customer's account, their order history and the matching help articles. None of the three lookups depends on the others. How do you run them, and what does the next step receive?
   Answer: Use `.parallel({ account: ..., orders: ..., articles: ... })`. Every branch gets the same incoming value, not a neighbour's output. The next step receives one object keyed by the branch names you chose, and each value is that branch's output. Keys are placed by name, not by which branch finished first. The next step starts only after every branch has finished, so the step lasts as long as its slowest branch. All branches start together unless you cap them. Fact sheet section 5 (sm:223-226, seq:1494-1520, ct:45-59); answer key Q2.
3. After draftReply produces the reply, you want to write the ticket and reply to an analytics log without making the customer wait. Which method do you use, what does the step after it receive, and when does the request actually finish?
   Answer: Use `.sideChain(logBlock)` after draftReply. It starts the log block in the background, and the chain moves on to the next step straight away. The next step receives the same value the sequencer already had, so the reply is not changed. If the log block throws, the chain and the reply carry on. The failure is logged and shows only in DevTool's trace, not in the user's stream. The reply is not delayed, but the request's stream stays open until the side chain settles. Use `.tap` instead only if the work has to finish before the next step, and then a failure fails the chain. Fact sheet section 6 (sm:290-295, old-sc:13, :41, :72, ct:171-185); answer key Q3.
4. Is handleTicket, a sequencer, itself a block? What can you do with it because of that?
   Answer: Yes. A sequencer is a block: SequencerDefinition extends BlockDefinition. It has a name, an input schema and an output, and both are validated like any block's. Its input is its first step's input, and its output is its last step's output. So it can be a flow action's block, a step in another sequencer, a router's route, a parallel branch, or a tool handed to a generator. Callers see only the name, the input and the output. Fact sheet section 1 (sm:156-161, hc:71-83, flow-config.test.ts:766-790, ct:645-657); answer key Q4.
5. One of the three parallel lookups, the order-history lookup, throws because its service is down. What happens to the turn? What would you change so the other two results still reach draftReply? *(edge case)*
   Answer: One failing branch fails the whole parallel step, and so the sequencer fails. A step that throws stops the chain unless something rescues it. Branches already running finish, but their results are dropped. To let that branch fail on its own while the others continue, put a `.rescue()` on that branch's block. Its recovery output then fills that branch's key and the parallel step completes. Fact sheet section 5 (concurrency.ts:10-27, ct:2104-2123) and section 2 (old-comp:211, :248); pass-2 edge case list.
6. A teammate edits cleanMessage so it returns { body, truncated } instead of { text, truncated }. The connector `(cleaned) => cleaned.text` before draftReply is left unchanged. Does TypeScript catch this when you build? If not, when and how does it show up? *(edge case)*
   Answer: Don't rely on a compile-time check. A step's input is not type-checked against the previous step's output when you build. The step and connector signatures leave the block's input untyped (`any`), and tsc reported no error for a mismatched chain. The mistake shows up at run time. When the draftReply step runs, its own inputSchema rejects the value, and the error names the block and the field: `Block "draftReply" input validation failed at "<path>": <message>`. Fact sheet 'Read this first' item 1 (sm:163-180, bb:152-170, :356, build-block.test.ts:64).

## Reference rows

- `.map()`: input, output, no schema or name, not recorded as a trace step; use a handler with `.step()` when the reshaping has side effects or must be traced → R-03
- Connectors and shape checking: shapes checked at run time, not compile time; the failure names the block and the field → R-03
- Router: every route takes the router's input and returns its output; a router can choose only among the routes it lists, and what happens when `execute` returns a block not listed → R-01
- `.stepIf(condition, block)`: conditional variant of `.step()`; a false condition passes the value through unchanged → R-03
- `.parallel()` failure: one failing branch fails the whole step; `.rescue()` on a branch's block contains it → R-03
- Side chains: failure does not reach the chain or the user's stream; it shows in the DevTool trace, is logged on the server, and is handed to request-end hooks as `backgroundFailures`; the turn closes after all side chains finish; `.waitForSideChain()` makes a later step wait, and with `failOnError: true` it re-throws a side chain's failure (for R-03) → R-03 (corrected by pass 5)
- `.tap()` against `.sideChain()`: waits or not, whether a failure fails the chain, both leave the value unchanged → R-03
