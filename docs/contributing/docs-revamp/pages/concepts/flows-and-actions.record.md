## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support app's browser code needs to get a reply from the backend. What does the client name in that call: a block, an action, or a flow?
   Answer: An action, on a flow, both by string: `fsd.flow("support").send("reply", { message: "hi" }, { sessionId })`. The client never names a block. The block is the value of `reply` in the flow's `actions` map and is not on any route. The route a send goes to carries only the flow's id and the action name (fact sheet section 4, "What the client names": `cli/client.ts:857-860`, `core/types/flow.ts:188-201`; section 3: the action's name is its key in `actions`).
2. Two users, u1 and u2, call `reply` on `support` at the same moment, each in their own session. What do they share, what is separate, and what happens if u2 sends to u1's session id? *(edge case)*
   Answer: Shared: the one registered `support` flow, so the same code, the same `reply` action and the same schema. Also any organization-wide state the flow keeps, and the app's stores. Separate: each user's session and its state, so u1's reply count does not move u2's, and a new session counts from 1. Each `send` is also its own request with its own id. If u2 names u1's session, the server refuses it with `404 Unknown session`, the same answer it gives for an id that does not exist (sections 5 and 2: `eng/routes/action-routes.ts:272-281`, `session-owner-admission.test.ts`, [run]).
3. You add a second action, `reset`, next to `reply`. What changes for a client that already calls `reply`? *(edge case)*
   Answer: Only that it can now send one more name. The flow's address, the `createClient` setup, its sessions and their stored state all stay the same. `fsd.flows()` now lists `"actions": ["reply", "reset"]`, and each action has its own input schema, so `reset` can take `{}` while `reply` takes `{ message }`. With a typed client (`flow<typeof supportFlow>("support")`), `send("reset", {})` type-checks once the flow's type has the action, and a name the flow lacks is a type error. A session started through `reply` can be passed to `reset` (section 6: `fsd.flows()` [run], `client.test.ts:162-170`).
4. Can you run the `reply` action with no web server, for example in a test or from a terminal? How?
   Answer: Yes. From a terminal: `fsdev run support reply -i '{"message":"hi"}'` prints NDJSON, and the last line on success is `flow_complete` with the action's output. Adding `--session s1` keeps state across runs. From code: `createClient({ userId, fetcher: createInProcessFetch(flowState) })` sends the same `flow(...).send(...)` to an engine in the same process, with no web server, through the same router and authentication as HTTP. There is also `runAction` from `@flow-state-dev/engine`, covered on the manual-execution page. Each of these runs the same registered action (section 7: `cli/client.ts:70-79`, `in-process-fetch.test.ts:166-188`, `cliDoc:13-24`).
5. A client sends `reply` with `{ message: "" }`, but the action's schema requires at least one character. What does the client see, and does the `reply` block run? *(edge case)*
   Answer: The `send` itself is accepted, not rejected. The input is checked against the action's schema before the block runs, so the block never runs. The request then settles `failed`: `sent.result()` resolves `{ status: "failed", error: { code: "validation_error", message: "Action input validation failed at \"message\": ..." } }`. This happens whether or not the call is typed. It is not a 400 (sections 4 "What happens to bad input" and 10: `eng/execution/runAction.ts:411-428`, [run]).
6. A developer calls `fsd.flow("support").send("reply", { message: "hi" })` twice with no `sessionId`, and gets `count: 1` both times. Then they wonder why `await send(...)` came back before the reply had run. What is going on in each case? *(edge case)*
   Answer: Without a `sessionId`, each call starts a session of its own, and the response does not return that session's id. So the second call cannot see the first one's count. To keep a conversation, create a session first with `flow.createSession()` and pass its `id` as `sessionId` on each send. Then the second call returns `count: 2`. On the timing: `send` resolves as soon as the server accepts the request (`status: "in_progress"`), not when the action finishes. Use `sent.wait()` for the settled status, `sent.result()` for `{ status, output }`, or `sent.stream(...)` to follow it live (section 4: `eng/routes/action-routes.ts:347-368`, `:360-366`, `cli/client.ts:335-362`, [run]).

## 5 · Fact check

Checked against the code: the page as pass 4 read it after the draft, sha256 d891df7b68af, and the 6 Reference row(s) pass 6 moved.

- "The last line is `flow_complete` with the action's `output`. Run it again with `--session s1` and `count` is 2." This follows the `fsdev.config.ts` shown earlier on the page, `createFlowState({ flows: [support] })`. Untrue: That config sets no `stores`, so the app runs in memory. When `fsdev run` loads an app config it uses the config's own stores, `runtime.stores`. It opens the SQLite local store only when there is no config. Each `fsdev run` is a new process, so the in-memory session `s1` is gone on the second run. `s1` is created again and `count` is 1, not 2. The claim holds only if the config passes persistent stores, or if the run uses the no-config local SQLite path. (packages/engine/src/flowstate/createFlowState.ts:234 (no `stores` gives `inMemoryStores()`); packages/fsdev/src/commands/run.ts:297 (`stores = options.stores ?? runtime.stores`) and :327 (local SQLite only on the no-config branch); packages/fsdev/src/commands/run.ts:410 (reads session `s1` from those stores))

## Reference rows

- Action fields: the action is the bare block or `{ block, ... }`; `userMessage` and the other optional action fields, one row each with type and default → R-05
- Action field `inputSchema`: defaults to the block's `inputSchema`; set on the action to override. The page keeps one sentence, that input is checked before the block runs, and links the row → R-05
- Failure shape: input the schema refuses settles the request as `{ status: "failed", error }` naming the first problem, and `send` does not reject. The page keeps `send` returns on accept and `result()` waits → R-22
- Status code: a session id owned by another user returns `404 Unknown session`, identical to an unknown id → R-13
- Send endpoint: with no `sessionId` the request runs in a new session and the response does not carry the id → R-13
- `fsdev run`: arguments (flow id, action), `-i` input, `--session`; output is one JSON line per event, the last being `flow_complete` with the action's `output` → R-35
