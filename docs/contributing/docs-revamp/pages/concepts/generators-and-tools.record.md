## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are building the support desk's refund reply and go looking for the agent loop so you can add a tool to it. Where is the loop, and who wrote it?
   Answer: Inside every generator that has `tools`, and the framework wrote it, so you never write it. There is no `agent()` builder; the block builders are exactly `handler`, `generator`, `evaluator`, `sequencer`, `router` (facts: Things the page cannot state, 1; section 1, `old:159` 'You define the tools. The framework runs the loop'). One step is one model call: if the model asks for tool calls such as `lookUpOrder`, the framework runs them, adds the results to the conversation and calls the model again, stopping on a step with no tool calls (section 3, `gen:2075-2140`, `gol:62-96`).
2. You want `supportAgent` to choose for itself between `lookUpOrder` and `issueRefund`, but `checkRefundPolicy` must never be skipped. How do you build that?
   Answer: Put the generator with `tools: [lookUpOrder, issueRefund]` as a step in a sequencer and the check as the next step: `sequencer(...).step(supportAgent).step(checkRefundPolicy)`. The model chooses freely inside its step, and the step after it always runs, because a sequencer's order is your code and each step's output feeds the next (section 4, Q2 answer build 1; `bsq:163-166`, `old:111`). The other option, putting the check inside a sequencer passed as a tool, rests on a part of the sheet marked unverified, so the dependable answer is the step after the generator.
3. What is the difference between a tool and a block? Could `lookUpOrder` also be used as an ordinary step in `handleTicket`?
   Answer: There is no difference in the block itself: a tool is any block placed in a generator's `tools` (`type GeneratorTool = BlockDefinition<any, any>`, `gen:422`). 'Tool' names the role. The model is given the block's `name`, `description` and `inputSchema`, calls it by name, and the framework runs it as a block with its input checked against `inputSchema` and returns the output to the model (section 2, `gen:922-932`, `exec:130-137`; section 8). So yes, the same block can be an action, a step, a route and a tool. As a tool it needs a `description` so the model knows when to call it. A step does not need one (section 8, `gen:967-983`).
4. The model needs the customer's plan in its prompt so `supportAgent` can tell whether a refund is allowed. Where does that come from?
   Answer: Not from `prompt`, which holds the standing instructions you write. It comes through the `context` slot, which is for what changes per turn. Use a function of `(input, ctx)` that reads the plan from the run's state, for example `ctx.session.state`, with the state's shape declared via `sessionStateSchema`. The typed helper `contextFn({ session: schema }, ({ session }) => string)` builds exactly that function (section 5, `old-ctx:7`, `gen:550`, `ctxfn:1-60`, `context-fn.test.ts:24-35`). Prompt and context go first, then the conversation (section 5, `asm:70-102`).
5. The order service is down, and `lookUpOrder` throws when the model calls it mid-reply. What happens to the customer's request? *(edge case)*
   Answer: The run does not crash. The error text goes back to the model as the tool's result (`Tool "lookUpOrder" failed: <message>`) and the loop continues, so the model can try something else or answer (section 2, `gen:1629-1631`, `llm-messages.ts:98-100`; section 7 'A tool that errors does not crash the run'). The call still shows up as an item you can inspect (section 7, `items:114-145`). The exact rules, including that a tool which suspends stops the loop, are on the Reference page (section 9).
6. `supportAgent` already gets tools from a capability through `uses`. You edit it to add `tools: [lookUpOrder]`. Which tools can the model call now? *(edge case)*
   Answer: Only `lookUpOrder`. Declaring `tools` on a generator fences it: tools a capability would contribute are dropped once the block declares `tools`, even `tools: []`. Declaring nothing leaves the capability's tools in (section 5, `fence:1-30`, `cfg:73`). The model only gets what you hand it, so the list you declare is all it can reach (section 7). To keep the capability's tools, list them yourself.
