## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A worker on your support desk gives a customer a wrong answer. Which layer do you open first, which next, and what do you run to see which part produced the bad text? *(edge case)*
   Answer: Start with the worker's file, WORKER.md. Its Markdown body is the worker's instructions and its frontmatter is its configuration (model, tools). A worker whose file names no `flow:` runs on the built-in `agent` flow with that body as its instructions (packages/workforce/README.md:5-7, :40-43). If the file looks right, or it names `flow: <kind>`, open that flow next, then the blocks inside it (README.md:60-66). To see which block emitted what, run `fsdev run <flow> <action> -i '<json>'`. It prints one JSON event per line (item_added, content_delta, state_change, flow_complete, error), and `--log-level debug` adds the nested-block events inside sequencers and routers (apps/docs/docs/cli/agent-dev-loop.md:13-14, :50). The DevTool (`pnpm fsdev dev`) shows the same thing as block_trace items, each with the block's input, output and error. The file, then flow, then blocks order is the page's advice built from these facts. It is not a documented procedure.
2. In one sentence each, what is a kit, a flow and a block, and which of the three does an app's `createFlowState` config list?
   Answer: Kit: a feature packaged so an app installs it with one config entry. It brings the flows it serves, a folder it reads at start-up, and slots other kits fill (core/kit/define-kit.ts:3-10). Flow: the deployable unit. It bundles actions, state and client visibility into one object you register, and it is served under its id (apps/docs/guides/anatomy-of-a-flow.md:44; engine/flowstate/types.ts:119-123). Block: a typed unit of work with an input and an output schema, of exactly five kinds: handler, generator, evaluator, sequencer, router (apps/docs/docs/glossary.md:41-42). `createFlowState` takes `kits` and `flows` (a list, e.g. `flows: [helloChatFlow]`) plus `stores`. It does not list blocks; blocks reach the app inside a flow's actions (engine/flowstate/types.ts:124, :137, :178; examples/hello-chat/fsdev.config.ts:14-22).
3. In the hello-chat app, a user types a message and presses send. Name the stops the message makes before the reply's text appears on the page.
   Answer: (1) The page calls `session.sendAction("chat", { message })` from `useSession` (hc-app:47-64). With `userMessage` it shows the user's line at once. (2) The client POSTs to `/api/flows/hello-chat/<sessionId>/actions/chat` (client.ts:857-861). (3) The server checks that the session belongs to this caller and validates the input against the action's inputSchema before any block runs (action-routes.ts:272-280; anatomy-of-a-flow.md:72). (4) The `chat` action's root block runs. It is a sequencer: `chatGenerator` makes the model call, then `incrementMessageCount` runs as a tap for its state change only (hc-flow:71-73). (5) Items stream back over SSE as the generator emits them, because its itemVisibility is client: true (hc-flow:42-52). With `Accept: text/event-stream` the stream comes inline on the POST. Otherwise the server answers 202 and the client follows the request on a GET stream (action-routes.ts:327-362). (6) State is committed when the run completes, and the client refetches the snapshot on request.completed. (7) The page re-renders from `session.items` and the exposed state.
4. Which of these outlive the request that produced them: a block's output, the session, a view's answer? Does the answer change if the app's config leaves out `stores` and the server restarts? *(edge case)*
   Answer: The session does. It is stored in the `primary` store and many requests share it, since a session is one conversation (state-and-scopes.md:35; server/setup.md:78). A block's output does too. It is recorded as that block's block_trace.output in the request's item log, up to 256 KiB, with a placeholder and a 512-character preview above that (block-memoization-and-replay.md:7; streaming/items.md:149-155). A view's answer does not. It is computed on each read and nothing is stored; the browser holds only the last answer in `useView`'s value (engine/test/session-views-store-nothing.test.ts:2-7; react/hooks/useView.ts:13). With `stores` omitted, data is kept in memory and nothing persists across a restart, and startup says so. After a restart the session and the recorded outputs are gone too (engine/flowstate/types.ts:169-172).
5. A second user, Ben, gets hold of the session id of Ana's conversation and sends the `chat` action to it from his own browser. What happens, and what of Ana's session state could Ben's page have seen anyway? *(edge case)*
   Answer: The server answers him as if the session did not exist. A request that names a session another user or organisation owns is answered as an unknown session, before any block runs (engine/routes/action-routes.ts:272-280). Ana's session is owned by Ana in one organisation, and only she sees it. Even on her own page, the browser sees only the session-state fields that the flow's `client.expose` lists, not the whole state (state-and-scopes.md:25; core/types/flow.ts:59-66; hc-flow:88-90).
6. Where does each of these live: the WORKER.md for a standard worker, the hello-chat flow's code, the half-typed text in a message box, the conversation's messages? A user then edits a standard worker. Whose copy changes? *(edge case)*
   Answer: WORKER.md and the flow code are files in your repo. A kit's folder, such as the workers folder, is read when the app starts (workforce README.md:13-23; engine/flowstate/types.ts:134). The half-typed text is in the browser: `useDraft` keeps it in localStorage so a reload keeps it, or in memory only if storage throws (react/hooks/useDraft.ts:2-12, :63). The messages are items. They belong to the request that produced them, are collected on the session, and are kept in the `primary` store (streaming/overview.md:9). When a user edits a standard worker, the first edit makes that user's own copy under the same id. The repo's standard worker is unchanged for everyone else (packages/workforce/src/workers/client.ts:218-223). Every user still has each standard worker (glossary.md:116).
