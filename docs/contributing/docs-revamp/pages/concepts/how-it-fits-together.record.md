## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The help desk's refund worker tells a customer the wrong refund window. Which layer do you open first, and where do you go next if that is not it? *(edge case)*
   Answer: The worker's file first: a worker is a configuration plus an owner, and the Markdown body of its WORKER.md is its instructions on the built-in `agent` flow, so that body steers its answers (packages/workforce/README.md:5-7, :40-43). If the file is right, or its frontmatter names its own `flow: <kind>` (:60-62), open that flow, then the blocks inside it. `fsdev run <flow> <action> -i '<json>'` runs the same engine against the same stores and prints one JSON line per event, and each block run is recorded as a `block_trace` item that carries any failure as `block_trace.error` (docs/cli/agent-dev-loop.md:8, :13-14; docs/streaming/items.md:112). The order (file, flow, blocks) is the page's own advice, built from those facts.
2. In one sentence each: what is a kit, a flow and a block in the help desk app?
   Answer: Kit: a feature the app installs with one config object, bringing the flows its install returns, a folder it reads at start-up and slots other kits fill (core/kit/define-kit.ts:3-10). Flow: the deployable unit, with actions, state and client visibility in one registerable object, served under its id (apps/docs/guides/anatomy-of-a-flow.md:44; engine/flowstate/types.ts:119-123). Block: a typed unit of work with an input and an output schema, one of five kinds: handler, generator, evaluator, sequencer or router (docs/glossary.md:41-42). Note that no kit ships yet, so the kit sentence describes the shape and not a kit the reader can install (fact sheet, 'Read this first' 1).
3. A customer types 'Where is my order?' into the help desk chat and presses send. Name the stops the message makes before the answer's text appears on the page.
   Answer: (1) The page calls the action with `session.sendAction("chat", { message })` and shows the user's line at once, which the server's copy later replaces. (2) A POST goes to `/api/flows/<flow>/<sessionId>/actions/chat`. (3) The server checks the session belongs to the caller and validates the input against the action's inputSchema. (4) The action's root block runs; in the example it is a sequencer that runs the generator (the model call) and then a counter as a tap. (5) Items stream back over SSE as the blocks emit them, and state changes are written as `state_change` items. (6) On completion the request is marked complete and the client refetches the snapshot. (7) The page re-renders from `session.items` and the exposed state. Sources: hc-app:47-64; react/hooks/useSession.ts:436-445; client/client.ts:857-861; engine/routes/action-routes.ts:274-279, :327-362; apps/docs/guides/anatomy-of-a-flow.md:73, :77; hc-flow:42-52, :68-73; docs/fundamentals/state-and-scopes.md:461-463.
4. After a help desk request finishes, which of these are still there: the generator block's output, the customer's session, and the answer of a view that counts open tickets?
   Answer: The session, yes: it is stored in the `primary` store and shared by all its requests (docs/server/setup.md:78; docs/fundamentals/state-and-scopes.md:35). The block's output, yes on a store that persists, as that block's `block_trace.output` in the request's item log; on the default in-memory store it goes when the process does (docs/advanced/block-memoization-and-replay.md:7; engine/flowstate/types.ts:169-172). The view's answer, no: it is computed on each read and nothing is stored (engine/test/session-views-store-nothing.test.ts:2-7). The browser holds only the last answer as `useView`'s `value` while the screen is open (react/hooks/useView.ts:13).
5. Two customers use the help desk. One copies the other's session id and sends a chat message to that session. What happens? *(edge case)*
   Answer: The request is refused before any block runs. A session another user or organization owns is answered as an unknown session, so the caller learns neither who owns it nor that it exists (engine/routes/action-routes.ts:274-279). A session belongs to the user who created it, in one organization (docs/fundamentals/state-and-scopes.md:25).
6. The help desk was set up with no `stores` option, and the server restarts overnight. Which of these does a customer find the next morning: their conversation, the support worker's WORKER.md, and the reply they had half-typed but not sent? *(edge case)*
   Answer: The conversation is gone: with `stores` omitted, data is held in memory and nothing persists across a restart, and startup says so (engine/flowstate/types.ts:168-178; docs/persistence/overview.md:25). The WORKER.md is still there, because it is a file in your repo, read at start-up (packages/workforce/README.md:11-23). The half-typed reply is still there if the page uses `useDraft`, which keeps unsent text in the browser's `localStorage` under `<namespace>:<id>`; if storage throws, it was only in memory (react/hooks/useDraft.ts:2-12). To keep conversations, pass a store such as `sqliteStores({ filename })`.
