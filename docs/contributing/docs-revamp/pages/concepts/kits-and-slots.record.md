## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The help-desk app installs `workforce` and `harnesses`. Afterwards the board has a `coder` worker type, yet `workforce` has never heard of the harnesses kit. How did the coder get there?
   Answer: `workforce` declares a slot (`workerFlows`, a keyed slot of flows). The harnesses kit lists `workforce` in its `requires` and returns the `coder` flow from its `contributes`, under the key it reads from the owner's factory, `workforce.slots.workerFlows`, rather than spelling it itself. The engine merges every contribution, and `workforce`'s `install` receives the merged entries in `slots`. Only a kit that requires the owner, directly or through another kit, may fill its slot. Facts: dk:121-137, dk:125-130 (`{ [workforce.slots.workerFlows]: { coder: coderFlow(config) } }`), dk:50-54, kp:292-299, dk:122-123. The kit names are [reconcile]; the mechanism is tested with made-up kits (et:116-145).
2. The help-desk config lists `kits: [claudeCode(), workforce({ model }), harnesses({})]`, dependents first. Does it start? Later someone edits the list and deletes `workforce()` but keeps `harnesses({})`. What happens then? *(edge case)*
   Answer: The first list starts. Kits can be listed in any order and install in `requires` order, each after every kit it requires. A test lists `[d(), b(), c()]` and they install `["b","c","d"]`, and the goal never lists kits in requires order (dk:205-206, ty:127-129, et:81-90, goal:5). After the edit the app refuses to construct. `createFlowState` throws a `FlowStateConfigError` naming the gap, of the form `kit "harnesses" requires kit "workforce", which is not installed.` (kp:59-69, et:289-303). Listing a kit twice is refused too: "a kit installs once per app" (kp:59-61). The app's own `fill` always lands last. The page should not say that list order breaks ties between independent kits ([verify]). Kit names are [reconcile].
3. You want Codex available beside Claude Code. Whose slot do you fill, and where do you write it?
   Answer: It is the harnesses kit's slot, not workforce's. Fill it from the app's own config with `fill` in `createFlowState`, keyed by the owner's factory: `fill: { [harnesses.slots.harnesses]: [codexHarness(), ...] }`. An app may fill any slot by its key without a `requires` check. The app's entries arrive beside the kit-contributed ones (Claude Code's), and in a list slot the app's come last. Another kit could also fill it, but only if it requires the harnesses kit. Facts: ty:140-145, kp:203-205, et:92-106 (`["c","app"]`), dk:121-123, kp:139-142. Names and the key are [reconcile], and so is whether `claudeCode()` already fills Claude Code.
4. Installing a kit is one line in the config. Besides flows, what does that one line bring into the app?
   Answer: Flows: `install` returns `{ flows }`, which are served beside the app's own `flows` and registered at start-up (`ready()`), not at construction (dk:95-98, ty:130-131, et:92-106, et:108-114). Resources, views and capabilities ride on those flows (dk:9-11, ft:619-624). A config is checked against the kit's schema at the app's own call of the factory, so a bad config fails right there (dk:249-256, dt:29-38). The kit may own a folder in the app, `directory: { path, read }`, for example a `workforce/` folder of `WORKER.md` files, read on the server at start-up (dk:138-147). It may also declare slots for others and fill slots of kits it requires (dk:6-9). The kit itself stores nothing; data lives in its flows' scopes (kp:26-34).
5. You are packaging a feature so other apps can reuse it. When do you ship a kit, when a capability, and when a flow?
   Answer: Derived from the definitions; no source states it as a rule. A capability is a bundle of resources, state, helpers and block config that a block pulls in with `uses`, so a capability fits a piece that blocks pull in (cap:6-8). A flow is one self-contained system the server serves, naming its actions, which an app lists in `flows` (hf:42). A kit is the unit an app installs from its config. Its `install` returns flows, and it alone can take a checked config, own a folder in the app, declare slots and fill other kits' slots (dk:4-11, dk:6-9, dk:240-256). Pick a kit when the feature serves its own flows, takes config, reads a folder or leaves openings for others.
6. A teammate leaves `notes.txt` and an `old/` folder in the app's `workforce/` folder beside the worker files the kit reads. What happens at start-up, and does the rest of the app keep running? *(edge case)*
   Answer: The app does not start. A kit's folder reader claims every entry it uses, and anything left unclaimed stops the app, each entry named. `.DS_Store` and `Thumbs.db` are ignored. `ready()` rejects with `createFlowState: the app can't start; a kit's folder was refused:` plus lines naming the kit, the files and the folder. Nothing is installed, so the rest of the app does not keep running: every later entry point, such as `getRuntime()`, rejects the same way. Fix it by removing the stray entries. Facts: dk:70-75, cl:1-8, wk:22, kp:286-289, et:348-364 (`notes.txt` and `old` named), goal:11 (`b:stray`). The detailed folder rules belong on `reference/kits`.
