## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk's `classify` generator reads each ticket and only needs a small, fast model. What do you write on the generator to get one, and what else does the app have to configure before it runs?
   Answer: Write `model: "openai/gpt-6-luna"`: a model string is the provider, a slash, then the model id, and the id goes to the provider exactly as written. Nothing else needs configuring beyond the provider's key. A literal string resolves on its own with no `models` option on `createFlowState` (fact sheet section 1; `examples/hello-chat/fsdev.config.ts:10-12`, `sm:7,39`). You could also write `model: "intent/utility"` and map `utility` to that model (section 2).
2. `classify` and three other blocks all use the cheap model. You want to move every one of them to a new cheap model without opening any block file. How do you set that up, and what is the one edit when the time comes?
   Answer: Each block names the purpose rather than the model, as `model: "intent/utility"`. The app maps purposes to models in the `models` option of `createFlowState`, with `models.default` (one string) and `models.intents` (each name maps to an ordered list of strings). To swap the model, edit the `utility` list in `models.intents`. Every block that names `intent/utility` picks up the new model and no block changes (section 2; `sm:92-93`, `fm:242`). For a dev or CI environment only, `FSDEV_INTENT_UTILITY` can replace the list without a code edit (section 9; `env:41`).
3. The `reply` generator uses `intent/chat`, mapped to `["anthropic/claude-sonnet-5-5", "openai/gpt-6.1-sol"]`. Mid-afternoon Anthropic starts returning rate-limit errors. What happens to the customer's request, and what does the caller see? *(edge case)*
   Answer: A transient failure such as a rate limit, a 5xx or a network error is retried on the same model first. If that still fails, the next model in the list, `openai/gpt-6.1-sol`, answers. The caller gets the second model's answer and never sees the first model's error. The run's items show which model answered: `model.actual` is the OpenAI model and `model.requested` is `intent/chat` (section 3; `fb:158-203`, `ct/fallback-model.test.ts:204-221`; section 2 on `model.actual`/`requested`).
4. Same desk, but both providers in the `chat` list are down at the same time. What happens? *(edge case)*
   Answer: Each model is tried in order and each one fails, so the call throws a single error that lists every model and what it returned (`All models in group "<name>" failed:` followed by one line per model). Fallback only spares the turn while at least one model in the list can answer (section 3; `fb:152-156,199`, `ct/fallback-model.test.ts:263-281`).
5. A new teammate clones the support desk and only has `OPENAI_API_KEY`. The `utility` intent lists `anthropic/claude-haiku-5-5` first and `openai/gpt-6-luna` second. Where do provider keys go, and does `classify` run on their machine? Would it still run if `classify` used the array `["anthropic/claude-haiku-5-5", "openai/gpt-6-luna"]` directly? *(edge case)*
   Answer: Keys are environment variables, one per provider or gateway (for example `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`), set in the shell, a `.env` file or the host's secret store, and the provider's SDK package must be installed. `reference/environment` lists them all, and `models.keys` on `createFlowState` overrides the environment (section 6). With the intent, `classify` runs: the resolver takes the first model in the list whose provider has a key and an installed package, so it skips the Anthropic entry and uses `gpt-6-luna` (section 2; `sm:82`, `res:1182-1196`). The array is different. An array falls back only when a call fails, not when a key is missing, so the missing Anthropic provider throws before the second entry is ever tried (section 3; probe, `gen:748-756`).
6. You let each agent on the desk pick the model that drafts their replies. One agent switches to a different model mid-shift. When does the switch take effect, and does it change the model the other agents get? *(edge case)*
   Answer: The choice lives in user state. An action writes it, and the generator's `model` is a function that reads `ctx.user.state` on each run. The switch takes effect on the next generation, with no restart. User state belongs to that user across their conversations inside one organization, so the other agents keep their own choices and nothing is shared (section 4; `fm:308-342`, `ss:22`; section 7). The UI sees the choice only if the user scope's client config exposes it.

- Reference row 3: An array on a generator "does not skip, and throws when it reaches a provider it cannot use." Untrue: Each string in the array is resolved up front through ctx.resolveModel, and resolveSingleModel throws at once when the provider has no package or key and no gateway serves it. The throw comes when the generator resolves its model, before any model is called, so an unusable provider later in the list fails the call even if the first model would have answered. It is not thrown on reaching that entry during fallback. (packages/core/src/blocks/generator.ts:741-754 (map over ctx.resolveModel); packages/core/src/models/createModelResolver.ts:1029-1120 (throws noProviderError / pinnedProviderError)) The row is recorded corrected.
- The page repeats that an array "throws when it reaches a provider it cannot use." Untrue: It throws when the array is resolved, before any call, not when fallback reaches that entry. (packages/core/src/blocks/generator.ts:741-754; docs/contributing/docs-revamp/pages/concepts/models.md:65)
- "A gateway key covers all three providers." Untrue: The page names only two providers, anthropic and openai. A gateway serves the providers it supports as a fallback when the direct package or key is unavailable (findGatewayForProvider), not a fixed count of three. Say "covers both providers here" or "covers the providers the gateway serves". (packages/core/src/models/createModelResolver.ts:1097-1113; docs/contributing/docs-revamp/pages/concepts/models.md:92)
- Reference row 7: "An evaluator takes one string: no intents, no list." Row 7 says an evaluator accepts "one string only". Untrue: An evaluator's model is `string | EvaluationModel`. It also accepts an evaluation model instance. It refuses intents, arrays and functions (including selectModel), and refuses a generate-only model instance. (packages/core/src/blocks/evaluator.ts:143-165 and :349) The row is recorded corrected.
- "Only generators and evaluators take a model." Untrue: The harness agent blocks (Codex, Cursor and Claude Code) also take a `model` option, though it is a harness-specific id and not a framework model string. Among the block kinds that resolve framework model strings it is true. The sentence should say so. (packages/codex/src/agent.ts:143; packages/cursor/src/agent.ts:205; packages/claude-code/src/sdk/types.ts:408)
- Reference row 2: "When the first model fails the call, for a rate limit or an outage, the next one answers" (Row 2 "what counts as a failure") Untrue: For generate, any error moves on to the next model after retries, though only retryable ones (429/500/502/503, network errors, isRetryable) are retried first. For streaming, a non-retryable error before content is thrown instead of falling through. Provider-load and file-prepare failures do skip to the next model. Row 2's definition of failure should be written to match. (packages/core/src/models/fallbackModel.ts:41-76, 179-203, 255-279) The row is recorded corrected.

## Reference rows

- Intents table: `default` is one model string, required once any intent exists; it answers when a generator names an unconfigured intent (warning logged in development) and when no model in an intent's list can be reached. → R-21
- Fallback and retry table: models are tried in list order, and a model that returns a retryable error (rate limit 429, 500/502/503, a network failure) is retried up to its attempt limit before the next one is tried. When generating, a non-retryable error also moves on to the next model. When streaming, a non-retryable error before the first chunk is thrown to the caller, and an error after content has started is never retried on another model. If every model fails, the error lists each model and its message. The page keeps one sentence of guarantee (the next model answers) and links here. → R-21 (corrected by pass 5)
- Fallback and retry table: an intent's list skips models whose provider has no key or no installed package before any call. An array on the generator does not skip: every string in it is resolved when the generator resolves its model, so one whose provider is unusable throws then, before any model is called, even if an earlier entry would have answered. → R-21 (corrected by pass 5)
- `selectModel` table: `preferProvider` reorders the list before key checks, so a preferred provider with no key is skipped; model functions take input and context. Keep the first sentence (it lasts across conversations) on the page and move the ordering rule. → R-21
- Provider keys and gateways table (which key makes which model usable; a gateway key covers all providers) and an intent-override row: `FSDEV_INTENT_<NAME>` pins one intent per environment. The page keeps one sentence: a key is all a new machine needs. → R-21
- What is recorded about the model that answered: `model.actual` and `model.requested` fields on each generator item, and what `requested` holds when an intent chose the model. → R-21
- Where a model is set: generators take `model` as a string, an intent, an array, a `selectModel` function or a model instance; evaluators take one model, either a plain model string or an evaluation model instance, and refuse intents, lists and functions when the block is built. A capability can contribute `model` only to generator blocks (an evaluator consuming one throws), and where both set it the block's own `model` wins. → R-21 (corrected by pass 5)
