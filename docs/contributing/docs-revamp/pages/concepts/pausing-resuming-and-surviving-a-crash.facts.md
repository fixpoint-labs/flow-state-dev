## 1. The scenario, mapped to what exists

- A generator calls tools; a tool is a block (`gen:17`, `core` `generator`'s `tools`). `lookUpOrder` is the handler tool already on `blocks.md`/`capabilities.md`. `issueRefund` is a handler tool that calls `ctx.suspend()` before it refunds. Both shapes are tested: `gsx:134-197` (a gated tool in a generator), `gsx:679-745` (a sibling tool that finished, and a gate in the same turn).
- A pause inside a tool pauses the whole request: "`ctx.suspend()` inside a tool's `execute` pauses the whole request, and resume continues on the same request id." `dx:223`; `hitl:270`. [page]
- The gate does the work **after** it returns. A refund tool suspends first and refunds second, so the refund runs once and only after the answer. `gsx:134-197` (`sideEffects` 0 at suspend, 1 after approval); `gen:28-39`. [page]
- A run that has two `ctx.suspend()` calls in two later steps pauses twice, one at a time, on one request: `sx:662-727`; `dx:215-219`. [ref]
- No `durable: true` is needed anywhere in the example. A host on persisting stores holds a stop with no setting; sequencers checkpoint unless they set `durable: false`; the action-level `durable` only clears records at completion. `core/src/types/flow.ts:237-243`; `eng/src/flowstate/types.ts:307-319`; `dx:11,40`. [page]

## 2. The four questions, for each stored part

Who owns it, who can see it, where it is stored, how many exist. Observations are from the cited tests and docs; [ran] where marked.

| Part | Owns it | Who can see it | Where stored | How many |
| --- | --- | --- | --- | --- |
| The paused request (its record and its item log, including each finished block's recorded output) | the user who sent it, in one organization and tenant | its owner, through the session routes, the stream and the status call; the browser shows the items | the request store; items one row each on SQLite and Postgres | one per request; one session holds many |
| The suspension (the pause itself) | the request that made it (and the flow instance that runs it) | the request's owner, to answer it; the DevTool's Suspensions tab, when debug routes are on | the suspension store (SQLite: its own table) | one per `ctx.suspend()` call; a request that pauses twice has two |
| The sequencer's checkpoint | the request | nobody directly: there is no public route for checkpoints | the checkpoint store | one per sequencer instance per request, overwritten at each step |
| The resume lease | the request being resumed | nobody | the lease store | at most one per request, held while a resume starts, not while it waits |

Facts behind each cell:

### The paused request

- A request is "one run of one action on one session": `apps/docs/docs/glossary.md:71`. A suspended request has status `suspended`: `con/types/request-status.ts:11-18` (`in_progress`, `completed`, `incomplete`, `failed`, `interrupted`, `aborted`, `suspended`); [ran] `sx:31-85` asserts `suspended` after `ctx.suspend()`. [page]
- When a block pauses, the runtime saves a suspension record, emits a `suspension` item on the stream and closes the stream cleanly. "Nothing blocks a thread, and on serverless the function returns instead of timing out." `hitl:24`; `dx:128-130`. [page]
- The item log is kept across the pause: the items before the pause, the `suspension` item, a `suspension_resume` item, the items after, on one request with continuous sequence numbers. `dx:185-205`; `sx:436-546` (one request id, full ordered log, no orphan request). [page: one sentence]
- Each finished block's output is kept in that log as a `block_trace`; that record is what resume reuses. `memo:7,13`. With observability off (production's default) a finished step still replays from a lean `block_trace`; a generator's step is recorded as a reference to its message: header of `eng/test/resume-replay-traces-off.test.ts:1-12`; `goals/durable-by-default/a-local-stop-is-held-and-answered/goal.md:12` ("Legs a and b run a second time with `FSDEV_TRACE_OBSERVABILITY=0`"). [page: "recorded outputs"; the trace detail [ref]]
- A request's own state is written to the store on every mutation, "so a paused request can restore it on `/continue`": `apps/docs/docs/state/mutation-model.md:51`. [ref: C-07]
- The record has the owner's `userId`, `orgId`, `tenantId` and the flow instance (`flowId`): `eng/src/stores/types.ts:33-55`; `eng/src/context/request-principal.ts:42-54`. [page: "the user it belongs to"]
- Stored where the session's other records are: C-14 (`persistence.facts.md` section 2, "Request"). [page: link]

## 3. Pausing

- A block pauses the run by calling `ctx.suspend({ reason, message, resumeSchema?, timeoutMs?, allow?, ... })` and awaiting it. `core/src/errors/suspension-error.ts:18-59` (`SuspendOptions`); `dx:134-145` (field table). [page: `reason` and `message`; the rest [ref]]
- On the first call it never returns: the framework stops the step, saves the pause, emits the `suspension` item and ends the stream. On the resumed run the same call returns the answer. `core/src/types/block.ts:580-589`; `hitl:24-26`. [page]
- It needs durable execution. A host without it refuses at the call, names the rule and the setting, records the request `failed` and holds nothing. `eng/src/context/createExecutionContext.ts:221-225`; `dbd:97-129`; [ran] for the in-memory default (item 0.2). [page: one sentence; the message text [ref]]
- Durable execution is on by default wherever the stores persist (filesystem, SQLite, Postgres), off by default over in-memory stores, `durable: false` turns it off, `durable: true` turns it on over in-memory stores "(tests only)". `eng/src/flowstate/types.ts:307-319`; `eng/src/durability/default-durability.ts:1-31`; `dbd:54-95`; `dx:11,30-42`. [page: persisting stores on, memory off, one clause; `durable` option [ref]]
- The pause is not tied to a process: the stored record is all that is needed to pick it up, from any process on the same store. [ran, repo test] a new engine (new flow instance, registry and provider) over the same stores answers a stop and the run completes: `sfu:466-518`. `dx:28` ("held until someone answers it, across a restart"). [page]
- The same on a developer machine: `fsdev run` over the default local store exits 0 at a stop and prints the stop's id; `fsdev dev` started afterwards, and restarted, lists the session and one answer completes the same request, with the step before the stop and the step after it each run once. `goals/durable-by-default/a-local-stop-is-held-and-answered/goal.md:3-12`; `cli:70-83`. [page: one sentence, as the "it survives a restart" evidence]
- What the browser sees: a `suspension` item with `message` and the allowed actions, and the stream ends. A client that was at sequence N reconnects with `Last-Event-ID: N` and gets N+1 onward: `dx:205`. [ref]
- While paused the run's status reads `suspended` on the request record and `GET .../requests/:id/status` reports it with no stream attached: `cr:30,149`. [ref]
- A pause can be stopped: `session.abortRequest()` on a suspended request resolves the gate and ends the request `aborted`; a later approve is refused 409. `dx:320`; `cr:147`. [ref]
- Two pause shapes besides an approval: a question (`user_input`, `allow: ["submit"]` by default) and `skip` for an optional step. `dx:145`, `hitl:189-264`. [ref: B-03, R-17]

## 4. Resuming

- The answer comes in one of four actions: `approve`, `reject`, `submit`, `skip`. `eng/src/routes/resume-routes.ts:27`; `con/types/suspension.ts:48-56`. [ref]
- `approve` and `submit` return their `data` from `ctx.suspend()`; `reject` makes it throw `SuspensionRejectedError`; `skip` returns `SUSPENSION_SKIPPED`. `dx:229-251`; `hitl:247-262,398-411`. [ref: "What `suspend` returns" → R-17]
- On approval the run's later code runs. For the support desk: `issueRefund` carries on past `ctx.suspend()`, refunds, returns its result, and the model writes the reply from the tool's real result, not from the approval payload. `gsx:134-197` ([ran] too: section 5); `gen:55,93`; `goals/suspension/generator-resumes-after-tool-approval/goal.md:4-7`. [page]
- The resumed run is the **same request id**: "Resume continues the same request id. There is no new linked request." `dx:169`; `sx:436-546`. A `GET` on the request returns the whole pause-and-continue history. `dx:169`. [page]
- A resume re-enters the flow instance recorded as the request's owner, not whichever copy is registered. `dx:173`; `hitl:30`. [ref]
- **Who answers.** Only the request's own signed-in user (item 0.1). The server records the signed-in caller as who resumed it; a `resumedBy` in the body is ignored; with no authentication it is the request's owner. `dx:165`; `ac:132-134`; `eng/src/routes/resume-routes.ts:218` ("Who resumed is the signed-in caller, never a field of the body"). [page: one sentence]
- The ways to send the answer:

[ran] all four compile (section 11). [page: two short examples]
  - DevTool: the Suspensions tab approves or rejects through the same resume route: `dx:398-402`. [page: one clause]

## 5. What does not run twice

The rule, from the docs and confirmed by tests, then what the reader sees on the support desk.

- **Finished blocks are not run again.** On resume, "every block that already finished is memoized: the runtime reuses that block's recorded output instead of re-executing it." `memo:7-9`; `sx:599-660` (`replays a completed pre-suspension block instead of re-executing it`: `preSpy` called once). [page]
- **A generator's model calls are not repeated.** A generator rebuilds its conversation from the item log, so "a resumed run costs the same model calls as an uninterrupted one." `gen:59-64`; `gsx:134-197` (`seen.length` is 2 after resume: step 0 not re-called). [page]
- **A tool that finished is not run again.** "If a single model turn called three tools and the second one suspended, the first and third already recorded their outputs. On resume those two are injected from the log, and only the gated tool re-enters." `gen:64`; `gsx:679-745`.
- **[ran] the support desk, end to end** (a scratch test, not kept: `generator` `draftReply` with tools `lookUpOrder` (returns `{ total: 250 }`) and `issueRefund` (calls `ctx.suspend!` then counts a refund); the model script calls `lookUpOrder`, then `issueRefund`, then answers; `createDurableStores()`, `runAction`, `continueRequest` as in `gsx:1-131`):
  - After `runAction`: status `suspended`; `lookUpOrder` ran 1 time; the model was called 2 times.

## 6. A crash is the same shape

- A request running when its process dies is left `in_progress` with no heartbeat. A sweep marks a request whose heartbeat is older than the threshold `interrupted`: every 30 seconds, threshold 60 seconds, by default; the same sweep runs once when the server starts. `cr:27-28,57-58,64`; `eng/src/runtime-config.ts:240-243`; `eng/src/flowstate/createFlowState.ts:805-850`; [ran, repo test] `eng/test/request-recovery.test.ts:105-137`. With the defaults an interrupted turn shows up "about a minute after the restart": `goals/continue-interrupted-run/after-a-restart/goal.md:12`. [page: "about a minute" is fine, it is the goal's statement; thresholds [ref]]
- The sweep needs a store that tracks in-flight requests (the active-request registry); SQLite and Postgres do ("fully supports interrupted request recovery"). `sql/README.md:75-77`; `pg/README.md:317`. The in-memory store has one but dies with the process; the filesystem store builds one too (`eng/src/stores/index.ts:244`). [page: "SQLite or Postgres"]
- The user gets the lost turn back and picks: **Continue** carries the same request on to its answer, **Discard** ends it for good. `goals/continue-interrupted-run/after-a-restart/goal.md:3-8`. [page]
- In code: `fsd.requests.interrupted()` lists the user's interrupted requests (each a handle with `sessionId?`, `flowKind`, `actionName`, `interruptedAt`, `continue()`, `retry()`); `fsd.flow("support").request(savedId).continue()` continues by id. `co:105-128`; `ac:166-176`. A request stays listed until continued or removed. `continue()` keeps the id; `retry()` starts a new request in the same session. Only an `interrupted` request can be continued (any other: 409; use `resume` for a `suspended` one); a request with no session cannot be continued. `co:115,126-128`; `eng/src/routes/recovery-routes.ts:241`. [page: one example]
- The DevTool: the request's overflow menu has Continue; it re-enters the same request id. `dtv:223-229`. [page: one clause]
- **What Continue runs.** Continue replays what finished and runs the block that was in flight again. `co:115`; `dtv:229`; `dx:9`, `dx:169`; [ran, repo test] `sx:813-884` (`continues an interrupted request under its own id, replaying completed blocks`: the earlier step's counter stays 1, the gate re-ran and re-suspended, same request id, no `suspension_resume`); `goals/continue-interrupted-run/continues-not-restarts/goal.md:6-7` (counters stay at 1, one `continuation` item with `trigger: "recovery"`, same id reaches `completed`); `ci:107-129`.
- **[ran] Q3, a real mid-run death after `lookUpOrder`.** A scratch test (not kept): generator `draftReply` with the tool `lookUpOrder` (counts its runs); the model's first step calls `lookUpOrder`, its second step never returns (the process "dies" there); with the request stored `in_progress` the record is set `interrupted`, then `continueRequest({ requestId, ... })` runs with no answer and a model that now replies. Result: `lookUpOrder` ran **1** time in total; the model was called 3 times (step 0, the step that hung, the step after Continue), so **step 0 was not re-asked**; status `completed`; output "drafted". So the order is **not** looked up again: its recorded output is reused. The step that was in flight at the death runs again.
  - The same, with a pause after the lookup (the suspended case with the record flipped to `interrupted`): `lookUpOrder` 1, model calls 2 after the continue (step 0 and the gate step not re-asked), still `suspended` on the same gate, then the approval completes it with `lookUpOrder` still 1 and the refund 1. [ran]
  - The caveat that has a test: a tool that was **in flight** at the death (its output item written but never finished) is run again, "exactly like the absent case", not shown to the model as an error: `gr:335-357`; `core/src/blocks/internal/generator-resume.ts:290-300`. A tool whose output was recorded is injected from the log: `generator-resume.ts:268-290`; `gsx:679-745`. The crash window between a side effect finishing and its output being recorded exists: the effect can run again. `memo:74`: "if the process crashes in the window between `fn` completing and that write landing, a later crash recovery ... can re-fire the effect"; pair with a provider idempotency key. [page: one sentence, the rule "at-least-once for the block in flight"; `dtv:235` says the same for background tasks]
- The page's claim is therefore: finished work is reused, the unfinished piece runs again, the same way for a crash and for a pause. [page]
- **[conflict]** `dtv:231` ("the whole generator or router block re-runs on continue"): contradicted for generators by the [ran] result and by `core/src/blocks/internal/generator-resume.ts:230-245` (steps rebuilt from the log "when artifacts exist but no pending gate"). Do not copy `dtv:231`.
- **A pause is not a crash.** A suspended request is waiting for an answer; it is not marked `interrupted`, needs no Continue, and an answer resumes it. An `interrupted` request is one that died; nobody answers it. `co:128`; `eng/src/routes/recovery-routes.ts:241`; `dx:169` (status walks `suspended → in_progress → terminal`, and `interrupted → in_progress → terminal` on crash recovery). [page]
- A crash while a suspended request is being resumed: if the process dies after the answer was recorded and before the request moved on, the sweeper finishes it: "A request still `suspended` (or `interrupted`) behind a gate that was already resolved ... is driven on with the recorded outcome." `dx:352`; `sfu:282-300,377` (`continues a stop already recorded cancelled whose run never resumed (a crash after the write)`), `sfu:691-717`. [ref]
- Without durable execution a crash resume re-runs from the start; with no provider "`/continue` behaves as it did before (re-runs with observability off)": header of `eng/test/resume-replay-traces-off.test.ts:6-12`. [ref]
- `fsdev` has no Continue of its own for a one-shot run; the abandoned record of a router-less topology is reclassified on the next initialization: `eng/src/flowstate/createFlowState.ts:805-850`. [ref]

## 7. Two requests at once

- The scenario: while the refund waits, the same customer sends another message on the same session. [page]
- A suspended request gives up its place on the session, so another request can run while it waits. `cp:164-166`; `rc:1-11`: "A suspended request gives its session's place back, so a new request can run while it waits on a person." [page]
- The default policy is `allow`: requests run at once. `cp:16,58`. With `allow` the new message runs beside the pause, and the answer, when it comes, runs at once. `rc:337-347`; `cp:170`. [page]
- A flow can name a policy per action (`concurrency: "queue" | "reject" | "hold" | "defer" | "allow"`; key `"session"` by default): `cp:14-60`. [ref: reference/concurrency, "Two requests on one session → reference/concurrency"]
- When the answer arrives it takes a new place on the key like a new request: under `queue` it lines up behind a request already running ("never beside it"); under `reject` the **resumed run is not dropped** but a new request is refused while it runs. `cp:166-170`; `rc:244-278`. [page: one sentence; "lines up" one clause]
- The call that sends the answer does not wait for its turn; it replies `202` with `{ requestId }` at once. If the turn does not come within the queue's 30-second limit the answer is kept, the request stays `suspended`, and the sweeper continues it (every ten minutes by default). `cp:172`; `rc:406-439`. [ref]
- `session.abortRequest()` on a resumed request that is still waiting its turn fails with 409; call it again once it runs. `cp:174`. [ref]
- The run that follows the pause is the same request; it is not a second request: `dx:169`. [page]
- Plain concurrent writes to one session's state are not what this section is about: `cp:24-26` (`allow` leaves overwriting to you); C-07 owns state. [page: link]
- What `defer`/`hold` do and the limits: `cp:101-140`. [ref]

Nothing else: no `durable: true` on the action or the sequencer. `eng/src/flowstate/types.ts:169-179,307-319`; `dx:15-28`; C-14 sheet section 9 for the exact `stores` shape (the short form `stores: sqliteStores({ filename })` is valid). - `fsdev dev` / `fsdev run` with no config are already on SQLite, so a pause there survives a restart without setup. `packages/fsdev/src/local-store.ts:1-16`; `cli:70-83`; `goals/durable-by-default/a-local-stop-is-held-and-answered/goal.md:3`. [page]

## 9. What it gets you (each point observable on the support desk)

- **A wait costs nothing while it lasts.** The run is a record in the store, with no process and no open connection; the stream closes cleanly; on serverless the function returns. `hitl:24`; `dx:128-130`. [page]
- **The answer can come days later, after a deploy or a restart.** The same request continues; a pause with no deadline never expires on its own; its checkpoint is not pruned by age. `sfu:466-518`; `dx:359`; `sw:131-139,245-262`. [page]
- **Finished work is not repeated.** After the approval the order is not looked up again and the model is not asked again for finished turns. [ran] section 5. [page]
- **One log for the whole story.** The items before the pause, the `suspension` item, the `suspension_resume` item (who answered, how, with what) and the items after are one ordered list on one request. `dx:185-205`. [page]
- **A crash gets the same treatment as a pause.** A turn killed mid-run comes back as Continue or Discard, and Continue picks up from what finished. `goals/continue-interrupted-run/after-a-restart/goal.md:3-8`; section 6. [page]
- **The screen is a hook.** A `suspension` item arrives in `session.items`; `useSuspensions` and `useApproval` turn it into controls and stream the continuation back into the same list. `rx/hooks/useSuspensions.ts:1-20`; `hitl:176-181`. [page]
- A decision that fails loudly: a flow on a host with no durable execution fails at the stop with a message naming the setting, and holds nothing, rather than appearing to pause. `dbd:97-129`; [ran] item 0.2. [page: one clause under Q4]

## 13. Cold-read answer key (for pass 2, from this sheet)

1. A refund over $100 waits for approval. **Where is the run while it waits?** In the store, not in a process. The request is saved with status `suspended`, with its item log, a pending suspension record and the sequencer's checkpoint. The stream closes cleanly; no thread or connection is held. Sections 2 and 3; `hitl:24`; `sx:31-85`.
2. The approval comes a day later, after a deploy. **What runs?** A new process continues the same request id. `cleanMessage`, the model's finished turns and `lookUpOrder` are not run again (their recorded outputs are reused); `issueRefund` runs again from its top, `ctx.suspend()` returns the answer, and the refund runs once; the model is then called once more to write the reply. Sections 4 and 5; [ran] counts: `lookUpOrder` 1, model calls 3, refund 1.
3. The process dies after `lookUpOrder`. **Is the order looked up again?** No, if its result was recorded: Continue reuses it. The step that was in flight when the process died runs again, and a tool caught mid-run runs again, so a side effect there can fire twice. Section 6 [ran]: `lookUpOrder` 1, the model not re-asked for step 0.
4. **What must be set up for a restart?** A store that persists (`stores: sqliteStores(...)` or `postgresStores(...)`) on `createFlowState`; durable execution is then on with no setting. The in-memory default makes a stop fail. `fsdev dev` with no config is already on SQLite. For a crash, the store must also track in-flight requests (SQLite and Postgres do). Section 8.
5. Edge, a second user: another signed-in user tries to approve the first user's refund. **Result?** Refused as "not found" (404); the pause stays pending. Only the request's own user answers on an app with sign-in. Item 0.1; `sfu:232-241`.
6. Edge, a crash vs a pause: the process is killed while a request is **waiting** for approval. Does anyone need to click Continue? **No.** A suspended request is not interrupted; after the restart the answer resumes it. Continue is for a request that was running when the process died. Section 6; `co:128`.
7. Edge, double side effect: `issueRefund` calls the payment API **before** `ctx.suspend()`. **What happens on approval?** The payment call runs a second time, because the pausing block runs again from its top. Fix: pause first, or guard it with `ctx.runOnce` or a provider idempotency key. Section 5; `gsx:878-926`.
8. Edge, two messages: the customer sends a second message while the refund waits. **Does it run?** Yes, by default (`allow`): a paused request gives up its place on the session. The later answer takes a new place on the key like a fresh request; under `queue` it lines up behind a running request. Section 7.
9. Edge, no store set: a production app on the default `createFlowState` reaches `issueRefund` with a $250 refund. **Result?** The request fails at the stop with a message naming durable execution and the settings; nothing is held. Item 0.2 [ran].
10. Edge, the restart finds a turn that died: what are the two choices? **Continue** (same request id; finished work reused) or **Discard** (ends it for good; it leaves the list). Section 6.
