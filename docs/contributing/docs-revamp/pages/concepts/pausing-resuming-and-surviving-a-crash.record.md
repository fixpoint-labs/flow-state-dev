## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. On the support desk, a customer asks for a $250 refund. `draftReply` has already called `lookUpOrder`, and now `issueRefund` calls `ctx.suspend()` with reason `user_approval` because the amount is over $100. Where is the run while it waits for someone to approve, and what is holding it open?
   Answer: The run is in the store, not in a process, and nothing holds it open. The request is saved with status `suspended`. Its item log is kept, including each finished block's recorded output and the `suspension` item. A pending suspension record and the sequencer's checkpoint are stored with it. The stream closes cleanly. No thread or connection waits, and on serverless the function returns instead of timing out. With no `timeoutMs` the pause waits until someone answers, stops or cancels it, and its checkpoint is not pruned by age. (Fact sheet sections 2, 3 and 9; hitl:24, dx:128-130, sx:31-85, sw:131-139 and 245-262, dx:359.)
2. The approval for that refund comes a day later, after a deploy restarted the server on the same store. What runs, and is it a new request?
   Answer: It is the same request id, not a new or linked request, and a new process picks it up from the stored record. Blocks that already finished are not run again. `cleanMessage`, the model's finished turns and `lookUpOrder` are reused from their recorded outputs. `issueRefund` runs again from its top, `ctx.suspend()` now returns the answer, and the refund runs once. The model is then called once more to write the reply from the tool's real result. In the run on the sheet, `lookUpOrder` ran once, the model was called 3 times in total, and the refund ran once. Leave out any promise that a flow whose code changed will resume: the sheet checked only a new process over the same store. (Sections 4 and 5 [ran]; dx:169, sfu:466-518, memo:7-9, gen:59-64; item 4 [verify].)
3. Mid-reply, the process dies just after `lookUpOrder` returned and while the model's next step was still running. After the restart, is the order looked up again? *(edge case)*
   Answer: No, because its result was recorded. With default settings the run shows up as interrupted about a minute after the restart, as a lost turn the user can Continue or Discard. Continue keeps the same request id. It reuses `lookUpOrder`'s recorded output and does not ask the model again for the step that finished. The step that was in flight when the process died runs again. In the run on the sheet, `lookUpOrder` ran once in total and the request reached `completed`. One caveat: a tool caught mid-run, whose output was never recorded, runs again, so a side effect there can fire twice. (Section 6 [ran]; co:115, goals/continue-interrupted-run/after-a-restart/goal.md:3-12, gr:335-357, memo:74.)
4. The team puts the support desk in production with a plain `createFlowState({ flows: [support] })` and no `stores`. A customer asks for a $250 refund. What happens, and what do they need to set up so a pause or a crash survives a restart? *(edge case)*
   Answer: The request fails when it reaches the pause. The run's status is `failed`, nothing is held, and the error message names durable execution and the setting to change. The in-memory default does not hold a stop, and a crash loses the run along with the process. The fix is a store that persists, set on `createFlowState`, for example `stores: sqliteStores({ filename: "support.db" })` or `postgresStores(...)`. Durable execution is then on with no further setting: no `durable: true` on the action or the sequencer. SQLite and Postgres also keep track of requests in flight, which is how a crash gets found. `fsdev dev` and `fsdev run` with no config already use SQLite, so a pause survives a restart there with no setup. (Item 0.2 [ran]; section 8; dbd:97-129, eng/src/flowstate/types.ts:307-319, packages/fsdev/src/local-store.ts:1-16.)
5. On an app with sign-in, a different signed-in user (say, a manager on another account) tries to approve the customer's pending refund. What happens? *(edge case)*
   Answer: The server refuses it as if the request did not exist (404), and the pause stays pending. Only the user who owns the request, in the same tenant and organization, can answer it. The server records the signed-in caller as the person who resumed it. A `resumedBy` field in the body is ignored. (Item 0.1; sfu:232-241, eng/src/context/request-principal.ts:42-54, dx:165, ac:132-134.)
6. Two variations while the refund waits. (a) The customer sends a second message on the same session: does it run? (b) The process is killed while the request is still waiting for approval: does someone have to click Continue after the restart? *(edge case)*
   Answer: (a) Yes, by default. A paused request gives up its place on the session, and the default policy is `allow`, so the new message runs alongside the pause. When the answer comes, the resumed run takes a new place like a new request would. Under `queue` it lines up behind a request that is already running. (b) No. A paused request is waiting for an answer. It was not running when the process died, so it is not marked interrupted and needs no Continue. After the restart, the approval resumes it as usual. Continue is only for a request that was mid-run when the process died. (Sections 6 and 7; cp:16, 58 and 164-170, rc:1-11 and 337-347; co:128, dx:169.)

## Reference rows

- Request states and what a pause does: status becomes `suspended`, the stream closes, a `suspension` item carrying the message goes to the client, and a pause with no deadline waits until answered (deadline default). → R-17
- Refusals when answering a pause: who may answer, a different signed-in user gets "not found", and the pause stays open. → R-17
- What runs again on resume: the block that paused re-runs from its top, `ctx.suspend` returns the answer, and the generator is called once more; finished blocks and answered model turns are skipped. → R-17
- Interrupted requests: the `interrupted` status, which stores detect it, the detection delay after restart, and the continue-or-discard choice (`requests.interrupted()`). → R-17
- Continue after a crash: the request id is kept, finished outputs are reused, the in-flight step re-runs, and a side effect inside it can fire twice (idempotency keys are the guard). → R-17
- Concurrency policies and a resumed request: a paused request gives up its place, the default policy runs requests at once, and a resumed request re-enters like a new one (queues behind a running request under `queue`). → R-18
- Pause without a persistent store: `ctx.suspend` fails with an error that says stopping for a person needs durable execution and names the `durable` setting (it also mentions in-memory stores); an in-memory run is lost on a crash. → R-17 (corrected by pass 5)
- Default store profile: `fsdev dev` and `fsdev run` with no config use SQLite; `createFlowState` with no `stores` uses memory. → R-12
