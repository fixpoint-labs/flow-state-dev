## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk's server is built with createFlowState({ flows: [support] }) and no stores key. You restart it. What is gone, and what would be different if you had been running the same project with fsdev dev and no fsdev.config.ts?
   Answer: Everything is gone: sessions and their items, session, user and org state (including the customer's plan), and resources. A run paused for a person was never held in the first place, because durable execution is off over the in-memory store. Startup already says so: with stores omitted, the app runs in memory and nothing persists across a restart. fsdev dev with no app config opens a SQLite file at .fsdev/data/fsdev.db, so that setup keeps all of it across a restart. (Facts 0.2, section 3 Memory, section 5 table, answer key 1; fst:169-173, createFlowState.ts:967-976, ls:5-6.)
2. You are moving the support desk onto one small VM. You want one file on disk and data that survives restarts. Which store do you use, and what do you write?
   Answer: SQLite. Install @flow-state-dev/store-sqlite, import sqliteStores from the package root, and set stores: sqliteStores({ filename: "./data/support.db" }) on createFlowState. One file holds everything, and it survives a process restart, resource state and content included. (Section 4 Choosing, section 9 example 2; pe:416, su:94, sql/README.md:83-85, sql/src/index.ts:9.)
3. A support agent's preferences are stored as user state. Which record do they live in, and what is that record keyed by? Org-wide settings for acme are org state: where do those live?
   Answer: User state lives in that user's own record, keyed by the user and the organization together. Org state is a separate record, keyed by the organization alone (acme), and every user's sessions in acme share it. (Section 2 User and org table, answer key 3; uck:36-45, uck:80-88.)
4. Alice works in the acme organization and also in a second organization, globex. In acme she saves a preference to her user state. She then opens the support desk in globex. Does she see it? Does Bob, in acme? *(edge case)*
   Answer: No to both. Alice has two user records, one per organization, so what she saved in acme is not read in globex. Bob has his own record in acme, so he does not see it either. Because the record is per user and per organization, a block never has to filter by organization. (Section 2 User and org; uck:36-45; goals/user-scope/keeps-a-users-data-in-the-org-it-was-saved-in/goal.md:4; answer key 7.)
5. You switch the support desk from SQLite in development to Postgres in production. Which flow, block or action code do you change, and what does change in how the app behaves?
   Answer: No flow code changes. A flow never names a store: stores is set once on createFlowState, as one adapter or as named profiles (for example dev and prod, picked by FSD_ENV, then defaultProfile, then the first one declared). Two things change with the store: what survives a restart, and whether a paused run is held. Moving from SQLite to Postgres changes neither, since both keep everything. Postgres also lets more than one server share the data. (Section 6, section 4 profiles; fst:169-185, kb:36-42, answer key 4.)
6. On SQLite, the support desk pauses a refund until a person approves it. Before anyone answers, the server crashes and restarts. What happens to the paused refund? What would happen if the same app had shipped to production with no stores set? *(edge case)*
   Answer: On SQLite the paused run is still held after the restart. Durable execution is on by default over a persisting store, so you answer it after the restart and the same request completes with the same payload. If production shipped with no stores, the app still runs, but in memory: it prints a one-time warning that sessions and requests are lost on every restart. In that case the pause was never held, because durable execution is off by default over memory. (Section 2 Paused runs; fst:307-313; goals/durable-by-default/a-local-stop-is-held-and-answered and goals/suspension/resumes-after-a-cold-restart; createFlowState.ts:978-985; answer keys 5 and 6.)

## 5 · Fact check

Checked against the code: the page as pass 4 read it after the draft, sha256 e86e4139fdf7, and the 9 Reference row(s) pass 6 moved.

- Reference row 9: Row 9: crash recovery returning an interrupted turn is done by SQLite only ("which stores do this (SQLite only)"); the page repeats it as "On SQLite, a turn that was running when the server was killed comes back as an interrupted turn." Untrue: The interrupted-turn sweep is store-agnostic. It runs at startup (detectInterruptedOnStartup, default true) over the store's active-request registry via listStale, and Postgres implements that registry (createPostgresActiveRequestRegistry, listStale). So a turn running when the server was killed is also marked interrupted on Postgres. Only the in-memory store loses it, because the data is gone. A SQLite-only reading is wrong; the page's "On SQLite" wording misleads in the same way. (packages/engine/src/flowstate/createFlowState.ts:827-835; packages/engine/src/routes/http-handlers.ts:417; packages/store-postgres/src/registry.ts:230; packages/store-postgres/src/active-request-registry.ts:145; page line 81) The row is recorded corrected.
- On SQLite, a turn that was running when the server was killed comes back as an interrupted turn (implying this is SQLite-only). Untrue: Postgres does the same, since the startup interrupted-request sweep runs over any store with an active-request registry, and Postgres has one. (packages/store-postgres/src/active-request-registry.ts:145; packages/engine/src/flowstate/createFlowState.ts:827-835; page line 81)
