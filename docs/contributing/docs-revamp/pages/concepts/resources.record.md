## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's refund policy is one document every reply should respect. Do you keep it in state or in a resource, and at which scope?
   Answer: A resource, because it is a document with its own name and a content body. Use state for flags, counters and small settings (st:23, st:54, ov:57, fig). Scope is org if the policy is the same for everyone in the org: org holds shared knowledge and team documents (st:130-138, ov:380-386). It is defined with defineResource({ scope: "org", stateSchema, content }) (core/types/resource.ts:596).
2. You drop the draftReply block, which declares resources: { refundPolicy }, into a second flow. What comes with it, and does the second flow get its own copy of the policy?
   Answer: The declaration comes with the block. A block's resources map bubbles up through sequencers and routers, and defineFlow merges it into the flow, so the second flow registers refundPolicy with no resources entry of its own (ov:343, ov:360, ct/flow.test.ts:464-481). The stored data is keyed by scope and path, not by flow. At org scope, by default, both flows read the same org-wide document; only flowIsolation: true would narrow it to one flow (st:62-66, core/types/resource.ts:207-234).
3. Ticket notes pile up, one per note, and you can't know how many there will be. What do you define, and how does a block add a note?
   Answer: A collection, the tool for when the number of instances is unknown (co:7, st:82-89): defineResourceCollection({ pattern: "ticketNotes/**", scope, stateSchema }). A block declares it, for example resources: { notes: ticketNotes }, and the property name, not the pattern, is how the block reaches it. It adds a note with await ctx.resources.notes.create("<key>", { ...initial state }). Each instance is a resource with its own state and content, stored under the pattern prefix plus the key (co:9, co:25-33, co:61, co:83, co:389).
4. refundPolicy is stored in the org, but no block in this flow declares it and neither does the flow. Does a request load it?
   Answer: No. A request loads only the resources its flow declares, directly or through its blocks. Data that nothing declares is not loaded, even when it is stored in the same scope. Flow-level resources load on every request; resources declared in an action's block tree load when that action runs, and a sibling action's do not (ov:61-80, ov:362-376, et/prefetch-waves.test.ts:94-141). The stored data still exists; it just isn't loaded (ov:376).
5. Two messages on the same ticket both reach a block that calls ctx.resources.notes.create("T-1042", {...}). The second call fails. Why, and what should the block call instead? *(edge case)*
   Answer: create throws when an instance with that key already exists (core/types/resource-collection.ts:322-347, co:52-81). If the note may already be there, use getOrCreate or upsert (co:120-127). get(key) rejects when the key is missing; getOptional returns undefined.
6. A second support agent in the same org opens a new conversation. Does draftReply see the same refundPolicy there, and can the model or the customer's browser read the policy without extra setup? *(edge case)*
   Answer: Yes, it sees the same document: an org-scoped resource is one per org and, by default, shared by every flow in that org (st:62-66, the how-many table). Neither the model nor the browser can read it by default. The model needs llmReadable: true plus a generator wired with readResourceContentTool(), and both flags default to off (ov:289, ct/resource-content-tools.test.ts:30, 82-83). Without a client property the resource stays on the server, invisible to clients (ca:7, ca:36, core/types/resource.ts:324).

## 5 · Fact check

- At user and org scope a resource is shared by every flow on the server unless it sets `flowIsolation: true`. Untrue: The default is sharing across every flow the same userId or orgId touches, not every flow on the server. `flowIsolation: true` on the resource is not the only way to isolate it. The flow-level `isolateUserState` / `isolateOrgState` options set the default `flowIsolation` for user- and org-scoped resources that don't declare their own, and a resource's own `flowIsolation` wins over them in both directions. An owner-pinned instance also stores a user-scoped resource in a per-(org, user) cell, so it is shared only with that user's other owner-pinned instances in the same org.
