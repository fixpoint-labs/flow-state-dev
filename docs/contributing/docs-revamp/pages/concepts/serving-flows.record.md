## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support desk has three flows: `support` (a `reply` action), `billing` (which Stripe starts) and `digest` (which a schedule starts). What do you pass to serve all three over HTTP, and what URL does a page call to run `reply` on `support`?
   Answer: One config object holding a list of the three flow instances: `createFlowState({ flows: [support, billing, digest] })`, with each flow being the instance its file exports. The host then mounts that handle. Each flow is served under its own id, under the default mount `/api/flows`, so `reply` is `POST /api/flows/support/actions/reply`, or `/api/flows/support/:sessionId/actions/reply` for an existing session. It answers 202 with a `requestId`, and the result streams over SSE. Facts: section 1 (`eng/flowstate/types.ts:116-125`; `hcc:13-18`), section 2 (`setup:194`, `setup:220-254`), section 9 answer 1.
2. A teammate copies an older snippet and writes `flows: { support, billing }`, then gives a second flow the same id as `support`. When do they find out something is wrong: on the first request or earlier? *(edge case)*
   Answer: Earlier, at construction. The keyed-record form throws at once ("`flows` is a list of flows, each served under its own id ... The keyed record form was removed"). Two flows with the same id are also refused when the app starts, not on the first request. The same holds for an empty `stores` and for a webhook provider the host did not set up. Facts: section 1 (`eng/flowstate/createFlowState.ts:360-380`, `:372-376`; `engT/flowstate/createFlowState.test.ts:53-62`), section 6 ("fails when it starts").
3. Stripe needs to start the `billing` flow when an invoice is paid. Is that an action call? Where does Stripe post, and what do the flow and the host each declare?
   Answer: No. Stripe posts to the webhook route `POST /api/flows/billing/webhooks/stripe`, not to an action route. The flow declares routing and no secret: `webhooks: { stripe: { on: { "invoice.paid": defineWebhookBinding({ block, input }) } } }`. The binding has the shape of an action (a block plus run policy), but it lives on `flow.webhooks` and never in `actions`. It is chosen by event type, so a caller cannot name it as an action, and it is never an MCP tool. The host declares how to verify the delivery: `createWebhookTransportAdapter({ providers: { stripe: { verify: stripeWebhookVerifier(...), eventType } } })` in `adapters`. A flow that only receives webhooks still declares `actions: {}`. Facts: section 4a (`core/types/webhooks.ts:3-14`, `:47-60`; `wh:119-130`; `mcpT/adapter.test.ts:112-135`), section 9 answer 2.
4. Someone sends a forged Stripe event to the billing webhook route, without a valid signature. What happens? And when a real `invoice.paid` arrives, has the payment been recorded by the time Stripe gets its response? *(edge case)*
   Answer: The forged delivery is refused with 401 and nothing runs. A verified delivery is answered 202 at once, and the block runs after the response, so the 202 does not mean the work is finished. An event type with no matching binding is also answered 202 and ignored. Facts: section 4a (`engT/transports/webhook-routes.test.ts:103-149`, `:394-460`), section 6, section 3 (post-response work).
5. Two customers' invoices are paid on the same day, and a later invoice arrives from the first customer. Do these Stripe events share a session, and who are they run as? *(edge case)*
   Answer: By default, no: with no `sessionId` on the binding, each event runs in its own fresh session. If the binding derives `sessionId` from the payload (for example `customer-${...}`), one customer's events share one session, while the second customer gets a separate one. No end user is involved, so the run uses the principal the flow's `authentication` names, for example `defaultUserId: "system"` with `requireUser: false`. Facts: section 4a (`core/types/webhooks.ts:70-77`; `wh:84-95`), section 8 table row "A session a webhook or schedule starts".
6. You move the support desk from a Next.js route to a plain Node process. What changes in your flows, and where do the stores and models live? If you never set `stores`, what happens to sessions when the process restarts? *(edge case)*
   Answer: Nothing changes in the flows. Only the mount changes: a Next.js route uses `createNextHandler(flowstate)` (or `createVercelNextHandler`), and a plain Node process uses `await serve(flowstate)` from `@flow-state-dev/node`, which binds `$PORT` (then 3000), serves `/api/flows` and `/healthz`, and shuts down gracefully on SIGTERM. Both hosts take the same `FlowState`. Stores and models are set on that one config object (`stores`, `models` on `createFlowState`), not on the host or the flow. If `models` is omitted, providers are detected from environment variables. If `stores` is omitted, the app runs in memory and says so at start-up, so sessions are lost on restart. Facts: section 3 (`ha:11`; `node/serve.ts:57-72`, `:184-188`; `eng/flowstate/types.ts:154-178`; `goals/first-hour/runs-without-store-ceremony`), section 9 answers 3 and 4.

- Reference row 2: Page: "It answers `202 Accepted` with a request id, runs the action, and streams the result back as server-sent events." (same claim in Row 2: response 202 with request id, result streamed as SSE) Untrue: The POST answers one of two ways. With `Accept: text/event-stream` the POST response is itself the SSE stream (no 202). Otherwise it returns `202` with a JSON body (`status: in_progress`, `request.id`, `x-request-id`), and the caller follows the request through a separate GET stream. The 202 does not carry the result stream. (/home/user/flow-state-dev/packages/engine/src/routes/action-routes.ts:327-345 (inline SSE when Accept includes text/event-stream) and :347-366 (202 JSON accepted body; live stream closed because 'the caller follows the request through its GET stream')) The row is recorded corrected.
