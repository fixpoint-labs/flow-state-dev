## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A customer sends "Where is order 1042?" to the support desk. The draftReply model has called lookUpOrder and is now halfway through a sentence of its reply. What has the browser received so far, and what has it not yet received?
   Answer: Received so far: the customer's own message as a user-role message item, already complete (the action's userMessage runs before any block, status "completed"). Then the tool call as one tool_output item for lookUpOrder, with its arguments and result in that one item, now done. Last, the reply as a single assistant message item that arrived as in_progress with empty text and has grown by content.delta pieces, so its text is the words streamed so far. Not yet received: that item's item.done, which carries the full text with status "completed", and the request's terminal event. Trace items never reach the browser at all. (Facts section 2 and the Q1 answer: runAction.ts:1825-1846, generator.ts:2321-2332, emit-tool-output.ts, ct/events.ts:31-34, :71-76.)
2. While the reply is still streaming, the customer reloads the page. What do they see, and what decides whether the reply keeps growing? *(edge case)*
   Answer: useSession reads the saved session on mount: the user message, the finished lookUpOrder tool call, and the reply as far as it was last saved. The record keeps a partial reply at the store's own pace, not every token, so the text may be a little behind where the screen was. Anything sent with transient: true is gone, such as a live-only status line or a transient card. With autoResume: true the hook finds the request that is still running, attaches to its stream and carries on from there, and nothing appears twice. autoResume is off by default. Without it the page shows that one snapshot and does not follow the running request. (Facts section 8, "Reloading the page mid-answer", useSession.ts:266-271 and :1741-1850, runAction.ts:431-445 and :1744-1755, react.md:240-248, section 5.)
3. The handler that looks up the order wants to show an order-lookup progress card that changes from "searching" to "found". The second time, it sends only { state: "found" }. What does the handler call, what do a live viewer and a viewer who reloads afterwards each see, and what happened to the orderId field? *(edge case)*
   Answer: It calls ctx.emit.component("order-lookup", data, { key: "order-1042" }), then calls it again with the same key. A renderer named order-lookup has to be registered on the client, and the two names must match. A live viewer gets every emission. With the same key the item id stays the same (item_component_keyed:order-1042), so the card is replaced in place and does not stack. The stored record keeps one entry for each request and key, so after a reload the viewer sees only the latest copy. data is replaced whole, not merged: orderId is gone because the second payload left it out. The engine test shows this: { a: 1, b: 2 } followed by { a: 99 } stores { a: 99 }. Without a key, each call would add a separate card. For a single line of text instead of a card, the handler would call ctx.emit.status. (Facts section 7 and the Q3 answer: createExecutionContext.ts:385-411, execution.test.ts:2907-2962 and :3052-3110.)
4. Next turn the customer asks "and when will it arrive?". Which items from the first turn does draftReply's model see, and does it see the order-lookup card?
   Answer: Only if draftReply asks for history (history: true, or an item query). Without that, the model gets no earlier conversation. When it does ask, it sees items that are history: true: the earlier user message, the assistant reply, any reasoning, and the lookUpOrder tool call (sent as a call and then its result), limited to the history window of 50 turns by default. It never sees component, status, error, state_change, resource_change or suspension items, so the order-lookup card does not reach the model. A message or generator output marked history: false is also left out. (Facts section 6 and the Q4 answer: generator.ts:358-368 and :783-795, resolve-visibility.ts:38-49, history.ts:78-168, flows.md:348-358.)
5. The customer's Wi-Fi drops for ten seconds in the middle of the reply. Does the reply stop being written? When the connection comes back, what does the stream send, and does the text pick up word for word? *(edge case)*
   Answer: The request keeps running on the server. A stream is only a view onto it. Every event carries a sequence number. The client reconnects with Last-Event-ID: <requestId>:N or ?starting_after=N, and the server replays every event after N and then continues live. The browser client reconnects by itself when the server ends a stream before the terminal event. A failed connection, such as a network error, goes to onError, and the React hook then reads the request's record. If the stream goes silent for longer than stuckThresholdMs (30 s), session.isStuck turns true, and followRequest(requestId) re-attaches from the last event the view had. Text deltas are not replayed, so the pieces sent during the gap do not come back one by one. The text jumps to the latest saved copy of the item and continues from the next live delta, and item.done carries the full final text. A reply that has already finished always replays exactly. (Facts section 8: cr:7-9, resume.ts:94-163, streams.ts:182-297, useSession.ts:298-305 and :1646-1664, stream-resume.test.ts:379-448.)
6. A second signed-in user gets hold of this customer's session id and opens it with useSession. What do they get, and can they reach the request that is still running? *(edge case)*
   Answer: No. A session belongs to the userId it was created under, and to its orgId if it has one. That owner is fixed when the session is created. Another user who asks for the session gets a 404, the same answer as for an id nobody has used. A user acting for the wrong organization gets a 403. Requests belong to the same user, so status, stream, retry, continue, resume and abort on this customer's request also return 404 for anyone else.
