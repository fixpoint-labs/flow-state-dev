## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. On the support desk, a customer upgrades and the `support` flow records `plan: "pro"`. When Alice starts a new conversation tomorrow, `draftReply` should still know she is on pro. Which scope does `plan` belong in, and how does a block write it?
   Answer: User scope. User state follows a person from conversation to conversation; observed, after `r1` set `plan: "pro"`, a new session `s2` of the same user in the same organization read `{ plan: "pro" }` while its session state was back at `{ s: 0 }`. Declare it as `user: { stateSchema: z.object({ plan: z.string().default("free") }) }` on the flow, read `ctx.user.state.plan`, and write with `await ctx.user.patchState({ plan: "pro" })` (facts section 2 User, section 8 example 3, section 9 [ran]).
2. While handling one ticket, `handleTicket` keeps a retry counter `tries` in request state and sets it to 3. Alice sends her next message in the same conversation. Does the new request see `tries: 3`? *(edge case)*
   Answer: No. Request state belongs to the one request that created it; each request has its own record, and no other request reads it. Observed: after `r1` patched `tries: 3`, `r2` in the same session read `{}`. If the next request might care, the field belongs in session state (facts section 2 Request, section 4 rule of thumb, section 9 [ran]).
3. Alice and Bob both work at Acme. Alice's run sets the org's `licenses` to 9 and her own `plan` to "pro". What does Bob's next run read for `licenses` and for `plan`, and what do the two of them share? *(edge case)*
   Answer: Bob reads `licenses: 9` and `plan: "free"` (the default). They share one org record; each has their own user record and their own sessions. Observed: Bob, a different user in `acme`, read `licenses: 9` and `plan: "free"` after Alice's writes (facts section 2 Org and User, section 9 [ran], answer key 3).
4. Session state on the support flow holds an internal `score` the team uses for routing, next to `ticketCount`, which the browser shows. How do you keep `score` out of the browser while still showing `ticketCount`?
   Answer: Add `client: { expose: ["ticketCount"] }` to the session scope and leave `score` off the list. Raw state never reaches the client; only fields `expose` names cross, a scope with no `client` exposes nothing, and adding a field to the schema does not leak it because exposure is by name. A block on the server still reads and writes `score`; a browser asking for it through `useClientData` gets nothing. (Request state cannot be exposed at all; it has no `client` config.) (facts section 5, section 10).
5. Alice saved `plan: "pro"` while working in Acme. She also belongs to Globex and opens a new conversation there. What does `ctx.user.state.plan` read, and why? *(edge case)*
   Answer: `"free"`, the default, not her Acme plan. User state belongs to a user inside one organization: the same user in two organizations has two user records, so nothing she saves in one shows up in the other, and a block never has to filter by organization. Observed: alice in `globex` read `plan: "free"` and `licenses: 5` (facts section 2 User, section 6, section 9 [ran]).
6. Months after launch, the team adds `language: z.string().default("en")` to the flow's `user.stateSchema`. Alice already has a stored user record without that field. What does her next run read for `language`, and is a migration needed? *(edge case)*
   Answer: She reads `"en"`, and no migration is needed. When a session, user or org record loads, each field of the flow's `stateSchema` the record does not hold reads as its default, so a field added later reads its default on every existing record (for a static default) (facts section 2 Defaults on read, section 6, answer key 6; `eng/test/scope-state-defaults.test.ts:350-368`).
