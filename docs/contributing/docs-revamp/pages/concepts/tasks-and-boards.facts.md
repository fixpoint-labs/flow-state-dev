## Read this first: contradictions and things the page cannot say

1. **The default claim order is `fifo`, not `topological`.** `tb:66` ("`claimOrder: "topological"`") and `tb:148` ("`"topological"` (default)") are wrong. The code defaults to `"fifo"` (`bi:688`), the named orders are `"fifo"` and `"priority"` only, and a test asserts `"topological"` is not accepted (`bt:456-466`; the type error is the assertion). Both orders gate on `deps` the same way (`bt:352-393`). The pilot does not name an order. **The page does not name one.** The ordering detail is [ref], and the Reference page must not copy `tb:148`. [contradiction: code wins]
2. **There are six termination reasons, not five.** `tb:176-191` and the old table list `all-completed`, `blocked-by-failures`, `retry-budget-exhausted`, `dispatched`, `waiting-on-a-user`. The code emits a sixth, `"waiting-on-an-event"`, when the work left waits on something outside the board and none of it on a user. `bm:291-309`, doc comment at `bm:197-216`. The pilot says "a few other reasons, such as a task waiting on a user, and the reference lists them", which stays true. [ref: all six, with the order the code decides them in, `bm:217-234`; the page names only the two it uses]
3. **There are six task statuses, not five.** `ts:14-21`: `pending`, `in_progress`, `held`, `completed`, `errored`, `cancelled`. The pilot's table omits `held`. `held` is a task filed with `held: true`, which does not start until something releases it (`ti:62-69`; transitions `ts:77-84`). A board with a `held` row left reports `blocked-by-failures` (`bm:276-283`). [page: the pilot's five, and only for the path the example follows; `held` is [ref]. The pilot's "`cancelled` when a task it depends on failed" is true but incomplete: a task can also be cancelled directly, `ts:77-84`]
4. **"Who runs pending tasks when the request ends" has two answers by storage.** On the default, request storage, the list ends with the request, so the tasks do not wait: they are gone (`tc:56-58`, doc comment; `tb:313`; pilot table row "The request"). On a resource, the tasks wait, and nobody runs them until some request runs `board.drain` over that collection again (`bl:183-195`, `bl:235-238`). The sitemap's Q2 ("two tasks pending") is only a question on a resource-backed board; on the default board the honest answer is "they end with the request". See the Q2 answer below. [page: both, one clause each]
5. **`initialTasks` is re-applied on every drain, but skips ids that already exist.** `sc:84-98` (a task whose `id` is already in the collection is skipped; duplicates within the list are skipped too); test `bt:1938-2003`. This is why the pilot's example can keep its `initialTasks` once the list moves to a resource: a second request does not duplicate the four tasks. A task given **no** `id` is added again every time (`sc:12-19`, `bi` handle field `hasIdlessInitialTasks`). The pilot's four tasks all carry ids. [page: one sentence under "How long the list lasts"; the id-less case is [ref]]
6. **Mounting `board.drain` directly as an action is shown in shipped code.** `rt:21` (`research: { block: researchBoard.drain }`, comment "mount the static board's block directly. Its tasks are fixed at definition time, so it takes no input"), `rb:12-30`. The pilot's `defineFlow({ kind, actions: { run: { block: board.drain } } })()` matches that shape. `requireUser` defaults to `true` (`packages/core/src/types/flow.ts:575-578`), so the pilot may leave it off. [page]
7. **The pilot's guide-style claim "the drain waits for that session to finish" is the plan-mode default.** `bi:326-329` (a plan board's drain waits on every row, including a row handed to another session, until it ends). A delegation board returns once each row is handed out. `bi:331-335`. Both are in the pilot; both check out. [page]

## Opening and the model (figure 1: a board is a list and a loop)

8. Some work is a list: research three competitors, then write the comparison. The three are independent and the comparison depends on all three. Example `rb:6-30` is the same shape (two analysts in parallel, a synthesizer that `deps` on both). [page]
9. A board is stored data (the tasks) plus a loop that works through them. The code calls the loop the drain, and `taskBoard(config)` gives both. `bl:27`; `bi:584-590` (`drain`: "the block that runs the board's tasks. Plug into a parent flow or sequencer"). [page: "the drain"]
10. You add tasks and say which depend on which; the drain takes what is ready and runs it; it stops when every task is done or nothing left can run. `bl:25`, `bm:197-216`, `tb:5`. [page; the stop rules beyond "done or nothing left can run" are [ref]]
11. The list and the drain have different lifetimes. The tasks last as long as the storage you choose. The drain runs only while a request is executing `board.drain`, and is gone when that block returns. `bl:25`, `bl:27`, `bl:55-60`, `bl:71-75`. Tasks added after the drain returned wait where they are until a drain runs again. `bl:71-75`; example test `lt` ("seedAndInspect: ... with no drain they stay pending"; "seedDrainRead: running board.drain moves the same tasks to completed"). [page; this is the figure's hatching vs dashed outline]
12. What the drain does, in the order a reader sees it: claim a ready task, run its block, record the result, repeat until nothing is ready. `tb:68-88` (the diagram: claimTask, workerBody, checkBoard, loop back). [page; the block names are not on the page]
13. Items a client sees: `task-change` (one per task transition, keyed `${collectionId}/${taskId}`, so the latest replaces the earlier) and `task-board-meta` (board-level, emitted once `active` at start and once `completed` at end with `terminationReason` and `counts`). `tb:1383-1385`, `bm:112-119` (active emit), `bm:312-316` (completed emit). ## What a task carries

26. [page]
27. Status path in the example: `pending` then `in_progress` then `completed` or `errored`; `cancelled` for a task whose dependency failed or was cancelled. [page: the path; the full transition table is [ref]]
28. A task is ready when it is `pending`, has no open hold, and every id in `deps` is `completed` (a dep that does not exist counts as not completed). `ci:1007-1030` (`isReady`), `ci:935-953` (`depsSatisfied`). [page: "ready when every task in `deps` is `completed`"; the holds and lease clauses are [ref]]
29. A task never runs in two places at once: the claim is atomic. Test: eight workers, one hundred tasks, no task processed twice. `bt:780-818`; `tb:88`. [page, the guarantee only]
30. The drain runs up to four ready tasks at a time unless you set `concurrency`. `bi:405`, `bi:687`; `bt:310-331` (12 tasks, concurrency 4); `bi:711-715` (`concurrency` below 1 throws at construction). [page]
31. In the example, the three research tasks are ready at once (no deps) and with concurrency 4 run together; `compare` is claimed only after all three are `completed`. `bt:361-393` (dependency order holds under two concurrent workers: `["upstream","downstream","leaf"]`). [page, the second figure's "ready, running, done"]
32. Dependencies are checked when a task is filed: an id that names no task on the board, a dep that has already failed or been cancelled, or a loop back to the task is refused and files nothing; in `initialTasks` the ids in the same list count. `tb:158` (`TaskFilingRefusedError`). [ref]

### Four questions for the stored parts

The page is about something that stores data. Two parts are stored: the list (a collection of tasks) and each task in it. The drain stores nothing.

| --- | --- | --- |
| Who owns it | On the default, the request that runs the board: `bi:253-264` ("Tasks live on `ctx.request`"). On a resource, the scope named by `scope` on `defineTaskCollection`: `"session"`, `"user"` or `"org"`. `dc:84-89`, `dc:130-136`. | The list that holds it. Each task is one entry in the list. For a resource-backed list, each task is one resource instance of the collection pattern `<id>/**` at the list's scope. `dc:209-221` |
| Who can see it | Any block in the request, by the board's id, on the default; not only blocks under the drain. `bi:262-264`, `bi:1330-1345` (`board.capability`: "`uses: [board.capability]` gets a typed `ctx.cap.<name>` accessor regardless of backing"). On a resource, whoever the scope reaches: a session's requests (`session`), a user's sessions in one organization, across flows by default (`user`), everyone in the organization (`org`). `sas:491-503`; `tb:362` ("A `user`-scoped board does cross flows, but then every session of that user shares one set of rows"). ## When a task fails

35. If a task fails, the board marks it `errored` and keeps going with whatever else is ready; the other tasks are not affected (default `onError: "skip"`). `bi:491-503`; test `bt:868-903`. With `onError: "fail"` the board itself fails instead. `bi:491-503`, `bt:905-928`. [page: the default and one clause for the alternative; `onError` options are [ref]]
36. A task fails with no retry unless it sets `maxAttempts`: unset is single-attempt, so the failure is final. `ti:50-58`, `pilot` ("Retry a failed task, unless the task sets `maxAttempts`"). [page: one clause. The retry budget (`maxTotalRetries`, default 50), `TaskEndsForGoodError` and the abandoned-claim recovery are [ref]]
37. A task that fails for good or is cancelled takes its open dependents with it: every open task that depends on it is cancelled, then every task that depends on those, down the chain. Each carries the label `skipped`, an `error` of `dep <id> failed` (or `was cancelled`) and `causedBy` naming the task that ended. `cd:1-30` (module doc), `cd:60-94` (`cascadeCancelPatch`, `skippedFor`, `SKIPPED_LABEL`); `tb:162`. There is nothing to wire; every board and every backing does it. [page: **answers Q1**]
38. The cascade runs whichever way the dependency ended: error, or cancel. A retried task owes nothing yet, because the retry may still succeed. `cd:6-30`; `tb:164`. [page: the first; the owed-cascade-after-a-crash detail is [ref]]
39. The test pins the example: `u` fails, `d` depends on `u`; `u` ends `errored`, `d` ends `cancelled`, and `d`'s block never runs. `bt:419-454`. [page, in the example's own names: `initech` `errored`, `compare` `cancelled`, `acme` and `globex` `completed`]
40. Independent tasks are unaffected: when `initech` fails, `acme` and `globex` still run and complete, because they do not depend on it. `bt:868-903` (siblings continue). With concurrency 4 all three start together, so by the time `initech` fails the other two may already be running. [page]
41. When nothing else can run, the drain stops, and the request does not fail (under the default `onError`). The request ends normally; the board's last item says why it stopped. `bt:1839-1888` (`result.error` is `null`; the item has `terminationReason: "blocked-by-failures"`, counts `completed: 0, errored: 1, cancelled: 1, pending: 0` for the two-task case). [page: **answers Q1, "what does the flow learn?"**]
42. What the flow learns: the final `task-board-meta` item carries `terminationReason` and `counts`. `bm:197-216`, `bm:312-316`. In the example: `terminationReason: "blocked-by-failures"`, and counts `completed: 2, errored: 1, cancelled: 1`. `bm:276-283` (any remaining `errored`, `cancelled` or `held` row gives `blocked-by-failures`); the counts' fields `bm:257-262` (`total`, `completed`, `errored`, `cancelled`, `held`, `in_progress`, `pending`, `retries`). [page; the figure's "FAILED · CANCELS WHAT WAITS ON IT"]
43. `all-completed` when every task finished (including a board started with no tasks). `bm:197-203`. [page]
44. The tasks themselves are readable after the drain: each task's `status` (`errored`, `cancelled`) and, on a cancelled one, the cause. `lc:63-76` (`collection.list()` returns tasks with `status` and `output`); `cd:92-94`. The flow can read both: the reason from the item, the detail from the list. [page: one clause, "the flow decides what to tell the user"]
45. Reasons beyond the two: `retry-budget-exhausted`, `dispatched`, `waiting-on-a-user`, `waiting-on-an-event` (see item 2). [ref]
46. A result that arrives for a task that has already moved on (cancelled meanwhile, or claimed by another worker) is dropped silently and affects only that task. `tb:261-265`. [ref]
47. If the board cannot record a result it emits `task-board-recorder-failure` and then fails the run. `tb:269-308`. [ref]

## How long the list lasts

48. Two choices the page gives: **the request** (default) and **a resource at session, user or org scope**. `tb:311-317` (four places in all; sequencer and factory are the other two, [ref]); `pilot` table. [page]
49. The default: no `collection` setting needed. "Omit `collection` entirely, or pass `{ collectionId }` to name it (the id defaults to the board name)." `tb:313`, `bi:266-274`. The list survives every block boundary in the request, including a second `board.drain` in the same request and tasks added by a block before the drain. `bi:253-264`; tests `bt:1416-1452` (a sibling step adds a task before the board drains), `bt:1610-1667` (a second drain sees mid-loop additions). [page]
50. The default list ends with the request: a new request starts empty. `tc:56-58`. [page]
51. A resource-backed list: `defineTaskCollection({ id, scope, stateSchema? })`, passed as `collection` to `taskBoard`. `dc:1-27` (the doc example is `defineTaskCollection({ id: "todos", scope: "user", stateSchema: z.object({ topic: z.string() }) })` then `taskBoard({ name: "todos", collection: todos, workers })`), `dc:130-136`, test `bt:1495-1538` (durable board with `scope: "session"`). Import: `defineTaskCollection` from `@flow-state-dev/orchestration/tasks`; `bl:150-156`. [page, **the "Keep the list" example**]
52. `id` names the collection (and forms the resource pattern and the board's `collectionId`); `scope` is `"session"`, `"user"` or `"org"` and sets the lifetime; `stateSchema` types each task's `input` payload and is optional (defaults to `z.unknown()`). `dc:128-137`, `dc:178-185`. [page: `id` and `scope`; `stateSchema` named once because the page's tasks carry no `input`, so it can be left out of the example]
53. The board registers the collection; nothing else needs declaring in the flow. `bi:362-368` ("The board registers and resolves it for you"); `bl:150-156`. [page]
54. The scope belongs to the collection, not the board. `bl:158-160`. [ref]
55. On a resource, tasks persist, but nothing runs them: "The tasks persisting does not mean anything is draining them. There is no worker sitting behind the collection pulling tasks off it." Processing happens only when some request mounts a board over that collection and runs `board.drain`. `bl:183-190`. Pending tasks stay pending between requests. `bl:191-199`. [page; **answers Q2 for a resource**]
56. A later request that runs the drain processes what is pending. `bl:197-199`. Because `initialTasks` skips ids already in the collection (item 5), a board that keeps `initialTasks` and a resource does not re-add them. [page]
57. A running request must not rely on seeing a write another request makes while it runs; a later request reads it. `bl:223-225`; `tb:315`. [ref]
58. The board's `terminationReason` and the drain's life are unchanged by storage: the drain still ends with the request. `bl:71-75`, `bl:227-233`. [page, that is the figure's arrow]
59. The pilot's claim "A board on its own is not a background queue" is true by these sources: `bl:235-243` ("A board is not a background job queue. Nothing wakes a drain when another request inserts a task, and a foreground request appending tasks while a separate background process drains the same board is not supported"). [page: **answers Q4, first half**]
60. Different scopes share differently: a `user`-scoped board is shared by every session of that user and across that user's flows; an `org` one by everyone in the organization. `tb:362`, `sas:491-503`. [page: one clause under the scope choice, "session for one conversation, user for one user's, org for everyone's"; the pilot's table cell "a resource in session, user or org scope" already carries it]
61. Per-conversation boards that another flow works use a `partitionBy` function. `tb:366-396`. [ref]

## Who does the work

62. In the example, two blocks in the same flow do everything: `workers: { analyst, writer }` maps each `assignee` to the block that does that kind of task. `bi:372-377`, `ag` ("`taskBoard` takes a name → block map and routes on `task.assignee`"). [page]
63. A board worker is any block: a generator with a persona and tools, or a plain handler. `ov` ("A board worker is any block you register on the board"), `ag`. [page]
64. A task's `assignee` can name a standard Workforce worker. ## Answer key for the sitemap questions (for pass 2, taken from this sheet)

**Q1. `initech` fails. What happens to `compare`, and what does the flow learn?**
`initech` ends `errored` (default `onError: "skip"`, and no `maxAttempts`, so no retry). `compare` depends on it, so it is cancelled with the label `skipped` and `causedBy: "initech"`; its block never runs. `acme` and `globex` are independent and complete. The drain then has nothing left it can run and stops without failing the request. The final board item carries `terminationReason: "blocked-by-failures"` and counts with `completed: 2`, `errored: 1`, `cancelled: 1`; the flow reads that and decides what to tell the user. Items 35-42.

**Q2. The request ends with two tasks pending. Who runs them, and when?**
Nobody, until a request runs `board.drain` over that list again, and only if the list outlived the request. On the default request storage the list ends with the request, so the two pending tasks do not wait: they are gone. On a resource-backed list they stay `pending` where they are. The next request that runs the drain processes them. No process watches the list in between. Items 4, 11, 50, 55, 56. (A drain that returns with tasks still pending is the case here, not the usual end of a drain: the default drain runs until nothing is left that can run, so two `pending` tasks at the end mean they were added after the drain returned, or the request never ran it.)

**Q3. You want tasks to survive between requests. What do you change?**
Store the list on a resource: declare it with `defineTaskCollection({ id, scope })` (scope `"session"`, `"user"` or `"org"`) and pass it as the board's `collection`. Nothing else changes: same `initialTasks` (stable ids, so a later request does not add them again), same `board.drain`. Items 48-53, 5.

**Q4. Board or background queue: a nightly job?**
A board is a stored list and a loop that runs only while a request executes it; it does not run on its own and nothing wakes it. A nightly job needs something to start it at night: a schedule, or a queue-backed action run. The job's work can still be a board: that trigger runs `board.drain` over a list kept on a resource. Items 55, 59, 83-85 (the board-run-from-a-schedule combination is [verify]).
