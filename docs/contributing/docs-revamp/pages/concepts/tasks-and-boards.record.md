## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your board has three research tasks (`acme`, `globex`, `initech`) run by `analyst`, and a `compare` task run by `writer` that waits on all three. `initech` fails. What happens to `compare` and to the other two, and what does the flow learn? *(edge case)*
   Answer: `initech` ends `errored`. The default `onError` is "skip", and with no `maxAttempts` there is no retry, so the failure is final (items 35, 36). `compare` depends on it, so it is cancelled: label `skipped`, `causedBy` naming `initech`, and its block never runs (items 37, 39). `acme` and `globex` don't depend on `initech`, so they still complete (item 40). Then nothing else can run, so the drain stops and the request does not fail (item 41). The flow learns what happened from the final `task-board-meta` item: `terminationReason: "blocked-by-failures"`, with counts `completed: 2, errored: 1, cancelled: 1`. It can also read each task's status and cause from the list, then decide what to tell the user (items 42, 44).
2. A request ends with two tasks still `pending` on the board. Who runs them, and when? *(edge case)*
   Answer: Nobody runs them until some request runs `board.drain` over that list again, and only if the list outlived the request. On the default storage, the request, the list ends with the request, so the two tasks are simply gone (items 4, 50). On a resource-backed list they stay `pending` where they are, and the next request that runs the drain processes them. Nothing watches the list in between: there is no worker behind the collection (items 11, 55, 56).
3. You want the competitor-research tasks to survive between requests. What do you change in the board?
   Answer: Store the list on a resource. Declare it with `defineTaskCollection({ id, scope })`, imported from `@flow-state-dev/orchestration/tasks`, with `scope` set to "session", "user" or "org". Pass it to `taskBoard` as `collection`. The board registers the collection, so nothing else needs declaring, and `initialTasks` and `board.drain` stay the same (items 48, 51-53).
4. You've moved the list onto a session resource but kept `initialTasks` with the four tasks. The user sends a second request in the same session and it runs `board.drain` again. Do you now have eight tasks? *(edge case)*
   Answer: No. `initialTasks` is applied again on every drain, but any task whose `id` is already in the collection is skipped. The four tasks all carry stable ids, so the second request does not duplicate them. It only processes what is still pending (items 5, 56). A task given no `id` would be added again on every drain (item 5).
5. You store the list at `user` scope rather than `session`, and the same user opens a second conversation. Does the second conversation get its own list? *(edge case)*
   Answer: No. A `user`-scoped list is shared by every session of that user, across flows too, so both conversations see and drain one set of rows. Use `session` for one list per conversation and `org` for one list everyone in the organization shares (items 60, and the 'Who can see it' row of the stored-parts table).
6. You need a comparison rebuilt every night. Do you use a board or a background queue?
   Answer: Both, for different jobs. A board isn't a background queue. Its drain runs only while a request is executing it, and nothing wakes it when tasks are waiting (items 59, 83). Something else has to start the job at night: a scheduled action, or a queue-backed action run (item 84). The work itself can still live on a board. A board is what the nightly job works through, and the trigger runs `board.drain` over a list kept on a resource, since a drain is a block. No example or test shows a board run from a schedule, so the page should state this only that far (items 84, 85).
