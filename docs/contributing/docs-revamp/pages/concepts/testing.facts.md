## 0. Where the existing docs are wrong (the code wins)

## 1. What a test with no model is (opening, the one idea)

- `@flow-state-dev/testing` is a dev dependency (`pnpm add -D @flow-state-dev/testing vitest`). `oldf:11-13`; `packages/testing/package.json` (name `@flow-state-dev/testing`; `vitest` in peer or dev deps, `:14`, `:82`). The package's own tests, and every example's, run on vitest. [page, one clause]
- A block is a function with a typed input and a typed output, so a test calls it with an input and checks what came back. `testBlock(block, { input })` runs one block and returns `{ output, error, items, state, stateChanges, resources, meta }`. `t/test-utilities/types.ts:88-121`; `t/test-utilities/testBlock.ts:83-96`.
- `testFlow({ flow, action, input, userId })` runs one action of a flow through the same `runAction` the server runs. `t/test-utilities/testFlow.ts:1-9` (header), `:182-239`. `userId` is required. `t/test-utilities/types.ts:158`.
- Nothing needs a running server, a network connection or an API key. Both harnesses run in the test process, over in-memory stores, with generators answered by mocks. `t/test-utilities/testFlow.ts:3` ("an isolated in-memory store registry, with mocked generators"), `:185`; `t/runtime/createTestContext.ts:459`; `old:7` ("no real LLM calls, no network"). Example proof: `hc:6-9` (header: "should never require OPENAI_API_KEY or make real network calls") and `hc:63-67` (a `fetch` spy that throws on any request). [page]
- A fresh in-memory store registry is made for each call, so tests share nothing. `t/test-utilities/testFlow.ts:185` (`options.stores ?? createInMemoryStores()`); `t/runtime/createTestContext.ts:459`. [page]
- A test is plain vitest. `describe`, `it`, `expect` come from vitest; the harness adds no matchers. `tt/test-utilities.test.ts:1`. [page]

## 5. What the test does and does not reach

- Harness runs are in-process. They do not exercise HTTP, SSE streaming, a browser, React, or a persistent store. `old:7`, `old:268` ("No HTTP servers, no SSE connections"); `apps/docs/docs/testing/end-to-end-tests.md:1-16` (the browser tier covers SSE to React desync, hydration, DevTool embed). [page: one sentence in "How it fits"]
- The next tier up: flow integration tests, which run several patterns together through the full `runAction` engine with mocked generators (`packages/integration-tests`). `apps/docs/docs/testing/flow-integration-tests.md:9-16`, `:20-27`. [page: link only]
- The tier above that: a Playwright suite against a real production build of the kitchen-sink app. `apps/docs/docs/testing/end-to-end-tests.md:1-16`. That is about the repo's own app, not something an app author gets from the package. [ref or leave out]
- `fsdev run` runs a real flow with a real model and a real stream, for confirming a change works in practice. `apps/docs/docs/testing/flow-integration-tests.md:18` (the "When to reach for which" list). [page: one clause, as the thing a test is not]
- A mock proves the flow is wired right given a model's answer. It does not prove the model answers well. [page: the bridge to evals; stated by `old:5` ("LLMs aren't deterministic. But your tests should be.") and `old:134` ("Unit tests tell you if your code is correct. Evals tell you if your AI is any good.")]
- Mocks are deterministic: the same script gives the same output every run. `old:265`. [page]
- A test exercises the real validation, lifecycle and execution contracts: the harness runs `executeBlock` and `runAction`, the engine's own paths. `t/test-utilities/testBlock.ts:137-141`; `t/test-utilities/testFlow.ts:215-225`. [page: "the same engine code runs"; do not claim "if it passes in tests it behaves the same in production": `old:266` says so, but nothing proves it, and the section above lists what is not exercised]

## 10. Stored parts (the four questions)

The page is about running code, not storing data. A test run does create stored records; the page says only what the reader controls.

## 11. Questions the sitemap asks, and the answers

1. **How do you test `handleTicket` without calling a provider?** Replace the model, not the block. `testBlock(handleTicket, { input, generators: { "draft-reply": mockGenerator({ name: "draft-reply", script: [{ text }] }) } })`, or `testFlow` on the action. Sections 2, 3.
2. **What do you assert on: text, items, or state?** Output for what a block returned; items for what the user would have been shown and which blocks ran (`messages()`, `blockOutputs(name)`); state for what the run changed: `testBlock`'s `result.state` or `stateChanges`, or `stores.session.get(sessionId)` after `testFlow`. Section 4.
3. **You want to know the reply quality did not drop. Test or eval?** Eval. A test with a mocked generator cannot tell, because the mock's answer is fixed. An eval scores outputs over a dataset, with a judge model or code scorers, and needs a real model passed as `modelResolver` on `evalBlock`. Section 6.
4. **Does a flow test need a database?** No. `testFlow` runs over in-memory stores made for the call. Sections 1, 10.
