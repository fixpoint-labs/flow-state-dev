## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You want a test that runs the support flow's `reply` action end to end (`handleTicket`: `clean-message`, then `draft-reply`) without calling OpenAI or needing an API key. What do you write?
   Answer: Call `testFlow({ flow, action: "reply", userId, input: { message }, generators: { "draft-reply": mockGenerator({ name: "draft-reply", script: [{ text: "Your order shipped." }] }) } })`. The mock stands in for the model call only; it is keyed by the block's `name` ("draft-reply"), not the variable name `draftReply`. Everything else (input validation, `clean-message`'s code, the sequencing, state writes, emitted items) runs through the engine's own `runAction`. With that script, `result.status` is "completed" and `result.output` is "Your order shipped." (facts 1, 3, 4, 12.1, 12.3, 13.1)
2. Your `handleTicket` test passes. What should its assertions check: the exact reply text, the items, or the state?
   Answer: The run's `output`, its `items` and its state, not the model's wording, because the script fixed the wording. Items come from `result.items` (what a client would have received) through selectors such as `testItems(result.items).messages()`, `byType` and `blockOutputs`. State is `result.state.<scope>` (and `stateChanges`) in a `testBlock` test; a `testFlow` result carries no state, so after a flow test you pass a `stores` from `createInMemoryStores()` and read `stores.session.get("test-session")`. (facts 5, 13.2)
3. After a prompt change, you want to know the quality of support replies has not dropped. Do you write another test or an eval?
   Answer: An eval. A test runs against a scripted model, so it gives the same answer every run and cannot see quality: it checks that your code does what you wrote. An eval runs a set of cases and scores each one (`evalBlock(draftReply, { dataset, scorers, blockOptions: { modelResolver } })`), with a real model when given a `modelResolver`, and reports `passed` and a per-scorer `summary`. A model-graded scorer (`analyzerScorer`) also needs a `modelResolver`; without one its judge is a no-op model and nothing real grades the output. (facts 7, 10, 13.3)
4. Does a test of the support flow need a database, a running server or a network connection?
   Answer: No. `testFlow` and `testBlock` run in the same process, start no HTTP server and open no SSE connection; `testFlow` calls `runAction` directly. Each call runs on in-memory stores the harness creates (`createInMemoryStores()`) unless you pass `stores`. The limit: because the stores are in memory, what a persistent store such as SQLite or Postgres does on a crash or restart is not tested. (facts 1, 9, 13.4)
5. A teammate adds a test for the `reply` action but forgets to pass a mock for `draft-reply`. What happens when it runs: does it quietly call the real model, throw, or something else? *(edge case)*
   Answer: It never reaches a provider. The run fails, naming the generator: `No mock for generator "draft-reply" / model "openai/gpt-6-luna"...`. `testFlow` does not throw; it returns `status: "failed"` with that message on `error` (in `testBlock` it lands on `result.error`). The default `unmockedGeneratorPolicy` is "error". The same no-throw rule covers a bad input: `testBlock(cleanMessage, { input: { message: 42 } })` returns `output` undefined and an `error` saying input validation failed. (facts 2, 3, 4, 8)
6. You want one test to cover two messages from the same customer in one session, checking the second turn sees what the first turn wrote. How, and what goes wrong if you reuse one `mockGenerator` across tests? *(edge case)*
   Answer: Create one `stores` with `createInMemoryStores()` and pass the same `stores` to both `testFlow` calls; they then share session, user, org and request state, and seeding does not overwrite a record that already exists. Without `stores` each call gets fresh in-memory stores and sees nothing from the other. Give the mock two script steps, since steps are used in order, one per generator call, and a call beyond the last step fails with a script-exhausted error. A mock keeps its position and recorded `calls` for the life of the object, so build a new one per test or call `.reset()`. (facts 4, 5, 6)
