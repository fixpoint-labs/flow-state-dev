## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The Workforce roster sidebar is open in three browser tabs, and each one asks the `roster` view for the user's workers. Where is the list they get back stored?
   Answer: Nowhere. The view computes its answer each time it is asked, by running its one block on the server. The answer comes back in the response and nothing is stored: a session view leaves every store unchanged after ten calls (es:187-196), and a user or org view never calls the session store (ev:237-258). The worker entries the view reads are stored by the flow's resources, in the user's own collection and the standard workers taken from the installation's files. The view owns none of that data (facts section 8; rv:56-70). The three tabs share one live read, because screens watching the same view with the same input share one read (uv:9-11).
2. Alice's sidebar watches the roster with `useView(rosterView)`. She hires a new worker. What makes the new row appear, and what refresh code did the app have to write for it?
   Answer: None. The app names no topic. Each answer from the view carries the change topics of what its run read. The client's live read listens to those topics, and when one changes it asks the view again (uv:5-9, vt:7-9). So there are three steps: the hire is written to Alice's worker data, the roster view is asked again, and the new row appears. The roster's own doc comment says a hire, edit, fork or fire reaches its watchers with no topic named by the app (rv:11-13). On a real host this took well under a second (goal signal b:within-1s). (Rewritten from the plan's 'a worker starts waiting' badge: the roster row has no waiting field, and that badge is driven by the inbox, not a view. Facts flag 1.)
3. Alice and Bob work in the same organization and have each hired workers. The roster is a user-scoped view. Whose rows does it return when Alice asks? When Bob hires someone, does Alice's sidebar refresh? *(edge case)*
   Answer: Alice gets her own workers plus the standard ones and none of Bob's. A user view runs with the caller's user taken from the verified principal (vt:33-36), and with two users' rows in the same flow, each user gets only their own (ev:260-274). The roster lists the standard workers for whoever asks (rv:56-61). Bob's hire wakes none of Alice's view calls (goal signal b:within-1s), so her sidebar does not refresh. Alice also needs no session: a user view answers a user who never had one (vt:33-36; goal signal a:no-session).
4. Alice edits one of the standard workers. How many times does that worker appear in her roster, and how is it marked? What does Bob, who has not edited it, see? *(edge case)*
   Answer: For Alice it appears once, as her copy. It is still marked standard and stays on the standard file's team, with `edited: true` (rv:6-10, rv:92-99). The view joins the user's collection and the standard workers on the server, so the screen never has to remove the duplicate itself. Her edited copy is stored in her own collection (facts section 8), so Bob still sees the unedited standard worker.
5. You are building the sidebar list of a user's workers, combining the workers they hired with the standard ones. Should it be a view or a resource?
   Answer: Both, each doing a different job. The resource stores the data: the worker entries live in the flow's user-scope resource (keys.ts:11-17), and a client can read a resource directly. The view is how a screen asks for an answer computed from that data, here a list joined from two collections. It runs on the server when asked and stores nothing (es:187; rv:6-10, rv:56-70). Choose a resource for what has to be stored. Choose a view for what the screen reads, whenever that answer is computed, joined or counted. (Plan question 4 used a list of open tickets with a count. The fact sheet cites no ticket code, so the question is recast with the roster.)
6. A developer wants the roster view to stamp a 'last viewed' time on each worker as it reads them, and to call a model to write a one-line summary of the team. What happens? *(edge case)*
   Answer: Both are refused. A view's context refuses every write and every model call, so watching a view never changes what it reads and never pays for a model (vt:6-8). A write is refused as read-only and leaves every store unchanged. A generator or a model call is refused too (ev:320-344). Both edits belong elsewhere: the stamp is a write, so it goes in an action, and an action can update a resource that the view then reads. The page links to reference/views for the exact error codes.

- The flow example `defineFlow({ kind: "roster", views: { roster } })()` is a complete flow declaration. Untrue: `actions` is a required field of a flow definition (`actions: TActions;`, not optional, and `defineFlow` infers `TActions extends Record<string, ActionEntry>` from it). A definition with only `kind` and `views` does not match `FlowDefinition`, so the example fails to typecheck. It needs an `actions` map, even if only `actions: {}`. Real flows that install views also pass `actions`, e.g. `defineFlow({ kind: PROJECTS_FLOW, actions: { ...projects.actions }, views: { ...projects.views } })`. ## Reference rows

- Watch sharing and row identity: watches of one view with equal input share a single read; an unchanged row keeps its identity (matched by row key) across answers. Added to the "when a view is read again" table. → R-09
- `useView` result fields: `value` is `undefined` before the first answer, then the typed rows; `stale` is `true` while the last read failed; a failed read is retried automatically. Goes in the "when a view is read again" table (the `viewRef` signature itself stays in the generated react API). → R-09
- Scopes table: `user` (answered from the user's own rows, needs no session, changes by other users do not refresh it), `org` (needs no session), `session` (runs on one session, called with `sessionId`). The Alice/Bob example and the guarantee that a user's view is private stay on the page in one sentence. → R-09
- `defineView` fields: `scope` (which rows answer), `key` (row id function, used to keep rows by key), `block` (the handler that computes the answer; its output schema types the answer). Row keys get their own row. The page keeps only what the example needs to read. → R-09
- What triggers a re-read: a view is read again when anything its last run read changes; for the roster view that is hire, edit, fork and fire. The recording of what a run read is the page's idea and stays; the list of triggering writes is a table row. → R-09
- What a view refuses: a view's block may not write state or call a model, and a view cannot dispatch an action. The definition-time refusals, each with what the error names, become a table; the page keeps the plain guarantee that watching is safe and links to the rows. → R-09
