## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are building the support desk page for the `support` flow. Name the three things the page can do with that flow, and the React hook (or client call) you would reach for to do each one.
   Answer: (1) Call an action: `useAction({ flowKind: "support", action: "reply" })` or `useSession(...).sendAction("reply", { text })`; plain client `fsd.flow("support").send("reply", { text }, { sessionId })`. (2) Follow a session's stream: `useSession(sessionId)` (plain client: `sent.stream(...)` or `fsd.sessions.stream(sessionId)`). (3) Read what the server exposes: `useClientData` over the session snapshot (plain client `fsd.sessions.state`), or a view read with `useView`. Fact sheet items 7-31 and the key's answer 1.
2. You add a `priority` field to the support flow's session state and set it in a block. The agent's page reads it with `useClientData(session, { session: ["priority"] })` and gets `undefined`. A teammate suggests asking for it in the state request from the browser. Why is it missing, will that work, and what actually puts it on the page? *(edge case)*
   Answer: Raw state never reaches the client; only fields named in that scope's `client.expose` are copied into `clientData` (a scope with no `client` block exposes nothing). A name that is not exposed reads back `undefined`, and stream patches to an unexposed key are dropped. Requesting it from the browser does not work: the `clientData` filter only picks among names already exposed, and the browser cannot opt into private state by passing a flag. Fix: add `priority` to the session scope's `client.expose` (it must be a top-level key of the scope's `stateSchema`, or `defineFlow` throws), or compute it in a view. Items 20-25, 33.
3. The support flow starts emitting a `component` item with component key `ticket-card`, and nobody has written a renderer for it. What does a customer see in the conversation where it lands, and where do you add a renderer so it shows properly? *(edge case)*
   Answer: With no registered renderer and no built-in for that type, `ItemRenderer` falls back to a small JSON `<pre>` showing the item's `type`, its `component` key and its `status`, not its content. Add a renderer in `FlowProvider`'s `renderers` prop, keyed by the component name for component items: `renderers={{ component: { "ticket-card": TicketCard } }}`; the renderer receives `{ item }` as its only prop. Items 39, 41, 43.
4. An agent on the support desk has the conversation open with `useSession`. A second agent replies in the same session from another browser tab. The first agent's page does not show the second agent's messages. Why, and what do you change? *(edge case)*
   Answer: By default `useSession` follows only the requests it sent itself. Pass `live: true`: the hook then holds one stream for the whole session, and each finished item from requests it did not send (another tab, person or agent) joins `items` about a second after it is saved, whole rather than token by token. Without React, `fsd.sessions.stream(sessionId)` follows everything in a session. Items 13, 16.
5. A customer's Wi-Fi drops while a reply from the support flow is streaming into their page over a request stream. What do you do when the connection is back so they don't lose or duplicate any of the reply, and does a session stream behave differently? *(edge case)*
   Answer: A request stream does not reconnect on its own: reopen it with `startingAfter` set to the last sequence number seen, and the server replays what was missed and then goes live; duplicate events are dropped by a sliding window. A session stream (`fsd.sessions.stream`) retries with backoff on its own. Items 12, 13, 59.
6. You need a nightly Node script, with no React and no DOM, that sends a `reply` to a support session and waits for it to finish. What do you import and what do you have to pass when you create it?
   Answer: Import `createClient` from `@flow-state-dev/client` (no React dependency; it runs in Node, browser and edge). Create it with `createClient({ userId, baseUrl })`: `userId` is required and it throws without it, and in Node `baseUrl` must be an absolute URL (or pass a `fetcher`, e.g. the engine's in-process fetch). Then `fsd.flow("support").send("reply", { text }, { sessionId })`, which resolves once the server accepts the request, and `sent.wait()` to get the settled status. Items 1-2, 7-8, 53-54.
