## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In the support desk, `handleTicket` runs `lookUpOrder` as a plain step, and `lookUpOrder` throws `new Error("orders DB timed out")`. Does the user see a stack trace? What exactly reaches the caller?
   Answer: No stack trace. The thrown value is normalized into a `FlowError`: a plain `Error` is wrapped, keeping the original as `cause`. The error stops `handleTicket`, travels up to the action, and the request ends `failed`. The stream carries a terminal item with `type: "error"`, `status: "failed"`, `message: "orders DB timed out"` (the thrown message, word for word) and the normalized `code` (`"execution_error"` for a plain throw; a `FlowError` keeps its own code). After it comes `request.failed`, which closes the stream. `details.cause` carries the cause chain only as `{ name, message, code?, cause? }`. The serializer leaves out `stack` on purpose, because it is large and leaks server paths. Since `message` and `details` reach the caller unchanged, write a thrown message as something a user may read. (facts §1 normalize-error.ts:46-92; §2 ErrorItem ct/items/types.ts:575-587, runAction.ts:921-923, serialize-error.ts:10-21)
2. You want the support desk to send a fallback apology (`apologize`) when the model step `draftReply` fails, and the rest of `handleTicket` should still run. Where does the fallback go, and what changes if you put it on `handleTicket` instead?
   Answer: Use `.rescue()`, the flow's one way to handle a failure inside the flow. Put it on the step: `draftReply.rescue([{ block: apologize }])`. That returns a copy of the block that recovers in place. `apologize` receives the error as its input, its output stands in for `draftReply`'s, and the chain goes on to the next step. Called on the sequencer, `handleTicket.rescue([...])` recovers the whole chain instead: the rescue block's output becomes the sequencer's output and the chain stops there. Handlers are checked in order and the first match runs. A handler with no `when` catches anything, `when: [SomeErrorClass]` matches by `instanceof`, and if nothing matches, the original error propagates. A rescued failure is not an error to the caller: the request completes, with no `error` item and no `request.failed`. (facts §3 cb:240-273, core/test/sequencer.test.ts:418-441, :1936-1984, :1329-1341)
3. How do the support desk's failures reach your error tracker, and how do you avoid reporting one failure twice?
   Answer: Pass an `errorCapture: (event) => {...}` callback to `createFlowState` from `@flow-state-dev/engine`. It is off by default, and its event type is `ErrorCaptureEvent`, whose fields include `error` (a `FlowError`), `requestId`, `blockName` and `final`. It fires once per failing block, on the leaf block that threw (for example `lookUpOrder`), and once more, marked `final: true`, when the request settles failed. To get one report per request that really failed, keep only `event.final`; to report every failing block, skip `event.final`. Forwarding both reports the same failure twice. The callback is read-only: its return value is ignored, and if it throws or rejects, the error is logged and swallowed without changing the request. For Sentry in particular, see the Sentry guide (B-20). (facts §4 eng/errors/error-capture.ts:21-76, error-capture-wiring.test.ts:81-110,166-205; ec:64-92)
4. You added `draftReply.rescue([{ block: apologize }])`, and `draftReply` fails on a ticket, but `apologize` recovers it. Does your error tracker hear about it, and does your `onErrored` hook run? *(edge case)*
   Answer: The tracker gets the per-block `errorCapture` event (with `blockName` set to the block that threw), but no `final` event, because the request did not fail. A failure that a rescue or a retry fixed never fires `final`. So a tracker that keeps only `event.final` stays quiet, while one that forwards per-block events still sees it. The `onErrored` hooks run only on the failure path, and the request completed, so they do not run. (facts §4 error-capture-wiring.test.ts:139-164, error-capture-final.test.ts:94-139; hooks on failure path only, runAction.ts:3298-3316)
5. Your action's `onErrored` hook posts each failure to a Slack channel. One day Slack is down and the hook itself throws. Does the support-desk caller see something different, or is the original `lookUpOrder` failure hidden? And can the hook change the reply the caller got? *(edge case)*
   Answer: Neither changes. `onErrored` is a block (for example a `handler(...)`), not a function. Its input is `{ requestId, actionName, error }`, where `error` is the normalized `FlowError`. It runs after the `error` item has been sent, the record has been written as `failed` and the `failed` status event has gone out, so it cannot change what the caller sees; the hooks only observe. A hook that throws is swallowed: it does not change the outcome or mask the original failure. On a failed request the order is the action's `onErrored`, then `request.onErrored`, then `request.onFinished` with `status: "failed"`. (facts §4 core/types/flow.ts:211,419; runAction.ts:860-875, 3124-3316; execution.test.ts:2308-2313)
6. A ticket's request failed halfway: the user's message was recorded, then `lookUpOrder` threw. Is that failed run's history kept? What is stored, and does it survive a server restart? *(edge case)*
   Answer: Yes, it is kept in the request store like a finished run. The request record has `status: "failed"` and `error` (`code`, `message`). Its `items` keep everything emitted before the throw (the user's message, any tool outputs) plus the `error` item, and the block that threw has a `block_trace` row with `status: "failed"`, which the DevTool can show. The caller who owns the session can read these. Whether the run outlives a restart depends on the store: the in-memory store does not persist, but SQLite and Postgres do. Retrying or continuing a failed run is covered in reference/durable-execution. (facts §6 runAction.ts:647-660, 3280-3286; served-setup-failure.test.ts:247-285; durable-execution.md:11,32-36)
