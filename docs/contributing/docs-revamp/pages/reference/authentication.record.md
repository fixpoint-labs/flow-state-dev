## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk sets `createFlowState({ resolvePrincipal: hostResolver })`, and the `support` flow also sets its own `authentication.resolvePrincipal: cookieResolver`. Alice calls `reply`. Which resolver decides who she is? Which one runs when she lists her sessions with `GET /api/flows/sessions`?
   Answer: For `reply`, the flow's own `cookieResolver` wins. The host-level resolver is only a fallback for flows that have none, and the framework default (which reads `body.userId`) runs only when neither is set (Table 2 step 2; lookup table: pk:27, pfr:73-79 [test]). The `requireUser` and `defaultUserId` that apply are the `support` flow's own (ih:304-305). The listing spans flows, so the host resolver runs with `flowKind: ""`. If that resolver refuses her, the whole listing answers `401`. Rows a flow's own resolver governs go only to the caller that resolver names as their owner (lookup table: ra:586-601; listings table: ra:66-90, ra:584-610). A route that names a stored record uses the resolver of the flow instance the record names as its owner, not the flow in the URL (ra:535, ra:314-358).
2. Bob is signed in with a valid cookie. He has Alice's session id `chat-1` from a shared screenshot and sends `GET /api/flows/sessions/chat-1`, then posts to `reply` with `sessionId: "chat-1"`. What does he get each time, and is anything written? *(edge case)*
   Answer: Both answer as if the id had never been used. On the management read, the resolver runs and resolves Bob. The stored session's `userId` is `alice`, so the user check fails with `404 { error: "Unknown session \"chat-1\"" }`, the same words as for an unused id (Table 7 step 3: ra:619-624, mra:218-232 [test]). The action POST is checked at admission and also answers `404 Unknown session "chat-1"`. Nothing is written: the session's snapshot, stream, `latestRequestId` and `updatedAt` do not change, and no block runs (Table 7: ac:278-280, hat:244 [test]; Table 8: bi:300-326 [test]). With no credential at all, the management read answers `401` (Table 7 step 2). The only place an id shows it is in use is creating a session with a taken id, which answers `409` (session-birth.test.ts:259-264).
3. Alice works for `acme` and `globex`. She opened `chat-1` while her resolver returned `orgId: "acme"`. Now it returns `orgId: "globex"` for her, and she reads `chat-1` and then calls `reply` on it. What happens in each case, and can she move the session over to `globex`? *(edge case)*
   Answer: The management read answers `403 { error: "Caller's organization does not own the requested resource" }`. The user check passes because it is her session, and the organization check fails. The user check runs first, so this `403` is reached only by the same user acting for another organization (Table 7 step 4: ra:666-681, obr:181-199 [test]). The `reply` POST answers `404 Unknown session "chat-1"`: the action route maps `OrgBindingMismatchError` to that answer (Table 8: ac:278-280). She cannot move it. A session's `userId` and `orgId` are fixed when it is created, a later request under another organization is refused before any write, and late-binding an organization onto a session that had none is refused too (Table 8: bi:54-81,111-135,138 [test]). To work under `globex` she creates a new session (fp:198-202).
4. A teammate wires a webhook into the support desk. They write a resolver that returns `null` when there is no cookie and set `authentication.defaultUserId: "support-bot"`, expecting the call to run as the bot. A second teammate's resolver returns `{ userId: "anyone" }` for every caller. What does each one get, and what should a resolver for a caller with no end user return? *(edge case)*
   Answer: Both are refused `401` for want of an organization: "Request requires a verified organization: ... returned no usable orgId". `defaultUserId` fills only the user and never supplies an organization, so `null` plus `defaultUserId` does not fall through (Table 1 return shapes: ih:260-265, pfr:84-101 [test]). `{ userId: "anyone" }` passes `requireUser`, which only checks that a user id is present (Table 3). It still has no `orgId`, so it is refused `401`. A machine caller with no end user returns `{ orgId }` alone and lets `defaultUserId` name the system user (au:131-133, pfr:103-111 [test]). A resolver can never return `DEFAULT_ORG_ID`, which also answers `401` (ih:267-274). If neither user nor organization resolves and `requireUser` is true, the refusal names the user, because that check runs first (pfr:113-122). With `requireUser: false` and no user, the answer is `500`, a configuration mistake (ih:337-347).
5. Two customers, `northwind` and `contoso`, share the support desk deployment, and both have a session called `chat-1`. How are the two kept apart? What does a request get that sends the wrong `x-tenant-id` or none? Does the framework check the header against Alice's credential? *(edge case)*
   Answer: The tenant comes from the `x-tenant-id` header. Its name can be changed only on `createFlowApiRouter({ tenantIdHeader })`, and a tenant id containing `:` is refused `400`. With a tenant, the session is stored under `<tenantId>:<sessionId>`, so the two `chat-1`s are two records with separate state and session-scoped resources. The API still returns the bare id. A lookup under the wrong tenant or with no header answers `404`, a `DELETE` under the wrong tenant does nothing, and listings show only that tenant's sessions (Table 9: ru:58, ru:81-85, sk:230-249, trt:74-142 [test]). The header is not compared with the principal: nothing checks it against the user or organization, so it must come from something you trust, such as your gateway or a client `fetch` wrapper (ru:76-90, sdoc:509). User and organization state are not split by tenant. To isolate those, put the tenant in the id (pdoc:258-267).
6. The support desk adds an `escalation` flow that declares the same user-scope resource key as `support`. Each flow is given its own inline resolver, with an identical body. What happens when Alice reads or writes that resource, and how should the two flows share sign-in?
   Answer: The read or write answers `409 declarations_disagree`: "Resource "<key>" at user scope is declared by flows "support" and "escalation" with different sign-in resolvers ... Give both flows one resolver." Resolvers are compared by function identity, so two functions with the same body disagree (Table 10: sa:181-206, rbs:164-177 [test]). The fix is to share one constant, `const sessionResolver: ResolvePrincipalFn = ...`, and pass it as `authentication: { resolvePrincipal: sessionResolver }` in each flow (adoc:308-324). Different `requireUser` or `defaultUserId` settings also answer `409` (sa:207-218). A flow with its own resolver and a flow on the host fallback disagree. One that names the host resolver itself and one that falls back to it agree (rbs:179-212).

- Reference row 18: On action routes the address and the stored owner must agree first; when they differ the answer is `409 wrong-instance-session`, before any resolver runs. Untrue: The action route resolves the principal at the addressed instance before dispatch. (packages/engine/src/routes/action-routes.ts:107-125 (resolver runs), :299-310 (409 mapped at admission); packages/engine/src/context/binding-errors.ts:171-182 (user check before instance check)) The row is recorded corrected.
- Bearer helper row: no header or a non-Bearer scheme returns `null`, "so the request is refused `401` for want of an organization, whatever `defaultUserId` says"; and "A missing secret is `401` because no organization resolves". Untrue: The host checks the user first. With no `defaultUserId` and `requireUser: true`, a `null` result is refused `401 "Action request requires non-empty userId"`. The organization refusal comes only when `defaultUserId` fills the user. (packages/engine/src/transports/host/createInboundTransportHost.ts:327-336 (user refusal), :351 (org resolved only after a user exists))

Untrue: `null` (or any result with no user) with no `defaultUserId` and `requireUser: true` is refused first with `401 "Action request requires non-empty userId"`. (packages/engine/src/transports/host/createInboundTransportHost.ts:317-351)
- Bind guard row: `fsdev serve`, `fsdev dev`, and `serve()` from `@flow-state-dev/node` all "Refuse to bind, exit code `3`".
