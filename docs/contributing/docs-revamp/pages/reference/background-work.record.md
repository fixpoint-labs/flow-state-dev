## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's buildReport action runs on a job queue (createFlowState({ flows, stores, jobQueue: bullmqJobQueue({ connection }) })). Halfway through a report, the worker process running the job dies. What happens to the run, to the user's stream, and to the session's concurrency key? And how is that different from the job simply throwing? *(edge case)*
   Answer: A dead process: the job's BullMQ lock lapses (lockDuration, 300000 ms by default) and the queue picks the job up again. This is BullMQ's own stalled-job handling, and how it counts attempts is not on a framework surface (3.6, 12). Meanwhile the enqueue side checks the job's state every 10 s. A job still waiting, delayed or running keeps the dispatch open. A job that ended with no terminal message settles with its return value, or with an error terminal carrying failedReason (3.6). A place the run held on the session's concurrency key is freed once its lease runs out (leaseMs, 10 s by default) (3.6). If the request's heartbeat goes quiet past staleSweepThresholdMs (60 s, checked every 30 s), the stale sweep marks it interrupted, and a client can continue it from there (3.6, 3.6.1). A throw, or a retryable error, is retried on the backoff schedule (exponential from 1000 ms, jitter 0.5) up to retry.attempts (default 3), keeping the same request id. Its events carry on numbering past the last persisted event, and the terminal event goes out only on the final attempt, so the user's stream stays open across retries. With deadLetter: true, a job that runs out of attempts is also added to fsd-flows-dlq (3.5, 3.5.2). Validation errors, an unknown flow or action, and a lost concurrency place are never retried (3.5.1).
2. The ticket page starts investigate runs through a dispatcher(). How does the page list the runs this conversation started, tell whether one is still going, and show what it did?
   Answer: List them with fsd.sessions.children(sessionId) (GET /api/flows/sessions/:sessionId/children), or useSession(...).childSessions. Rows come newest-created first, 25 per page by default, up to 100. Each entry has id, parentSessionId, createdAt, updatedAt and the optional flowId, topic, coordinate and status (4.10, 4.10.4, 4.10.5). status === "active" means not finished: queued, running, paused for approval, or interrupted and not superseded. It does not mean a worker is alive; a dead worker's run still reads active. Render it as working only with live: true, which makes useSession re-read as runs start and finish (4.12, 4.12.2, 8). Show what a run did with fsd.sessions.requests(runId, { includeItems: true }). The run's id is a session id, so every session read works on it. Watch a request live on GET /api/flows/:kind/requests/:requestId/stream, and resume with Last-Event-ID or starting_after (8). For a task-board job, completed only means nothing is still running. Read the task to see whether the work came out right (4.12.3).
3. After draftReply answers, .sideChain(summarizeTicket) writes a summary. One day summarizeTicket throws. What does the user see, what status does the request end with, is the summary retried, and how would you make the failure fail the request instead? *(edge case)*
   Answer: Nothing reaches the user's stream. The failure is logged, and a failed block_trace goes to the request's DevTool trace (only with trace observability on, which is off by default when NODE_ENV=production). The request still ends completed, and the task is not retried (2.3.1, 2.2.9). Request-end hooks such as onFinished get it as backgroundFailures: [{ step, message }]. They don't get it when the request's cancel fired or when the request ends suspended (2.3.2, 2.3.3). A default .waitForSideChain() does not throw. To fail the request, use .waitForSideChain({ failOnError: true }). It drains first, then throws the first failure. A request that fails this way cannot be continued on the same id; the follow-up is a fresh retry (2.3.4, 2.3.5). One exception: in a request working a dispatched task, a side chain that throws fails the task's attempt (2.3.6).
4. You split the deployment: the web tier runs bullmqJobQueue({ connection, mode: "enqueue-only" }) and a container runs mode "process-only". By mistake, the container points at its own SQLite file instead of the shared Postgres. What breaks, and how loudly? *(edge case)*
   Answer: Nothing fails loudly. The two processes are separate createFlowState instances, and nothing compares their stores. Jobs enqueue and the worker runs them and writes, but the web tier's stream and refresh routes read a store those writes never reach. The client sees the request in progress forever while the work has finished where it cannot see it. Point every process at a backend both reach, such as Postgres (3.4.2). The modes themselves: colocated (the default) enqueues and consumes; enqueue-only only enqueues; process-only only consumes, and starts on ready(). In process-only, an action that reaches a router runs inline, and a dispatch runs in that process and is not durable (3.3, 3.3.1, 3.3.2). Passing the old worker: option, or a mode named dispatch-only or worker-only, throws (0.1).
5. A teammate edits the investigate dispatcher so it runs an hour after the ticket closes. They also change session from { key } to { id: (input) => input.caseSessionId } to reuse an existing case session. What option sets the delay, and what happens when the id names a session that doesn't exist? *(edge case)*
   Answer: dispatcher() has no delay or run-at option. Timed work is a schedule: a static one, or a stored one from schedules.resolve, whose block does the work. A direct runtime.enqueueAction job takes delay, but that is not a dispatcher option (4.1.4, 3.5.4). With { id }, a session that does not exist is refused session-not-found and nothing is created (4.3). The refusal throws DispatchRefusedError (code "dispatch-refused", with blockName, address, refused, detail) before anything starts, so a .rescue() can branch on refused (4.5). An id naming another user's session, or a session on another flow, is refused session-not-addressable. An id function that returns an empty string throws a plain Error naming the block (4.5, 4.3.2).
6. With no job queue configured, the server is redeployed while three investigate runs are in flight. Separately, the user who started buildReport closed their browser tab. What happens to each? *(edge case)*
   Answer: Investigate runs: dispose() waits up to dispatchDrainTimeoutMs (default 30000 ms) for dispatched runs in this process, including work they dispatched, and logs "waiting for N dispatched request(s)". When the time runs out it cancels the rest and prints a report to stderr that --quiet does not hide, naming up to five request and session ids (5.1.1-5.1.5). It writes no terminal status. The run's row reads active with nothing running it, and the stale sweep marks the request interrupted at the next start. Nothing re-runs it: a client continues or retries it (5.1.6, 5.2, 5.2.2). A dispatch that arrives after dispose() has begun is refused dispatch-rejected (5.1.7). Closed tab: over HTTP, a closed connection cancels nothing. The request keeps running until it finishes or hits the host's timeout. Only the abort route stops it (0.8, 9.1).
