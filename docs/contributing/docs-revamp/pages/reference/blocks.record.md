## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are writing `cleanMessage` as a handler and want the fewest fields that will build. What must you set, and what happens if you leave out `inputSchema` and `outputSchema`?
   Answer: Only `name` (a non-empty string) and `execute`. Leaving out either is refused when the block is built: `Cannot build "<kind>" block without a non-empty "name"` or `Cannot build "cleanMessage" (handler) without an execute function`. Both schemas are optional and default to `z.any()`, so nothing is checked on the way in or out and the next step's input is untyped. Facts: section 2 (handler row), section 11 first lookup, `bb:202-211`.
2. `handleTicket` sends each ticket through a router that picks between a refund block and a shipping block. A teammate changes the selector so it builds and returns a new `escalate` block that is not listed in `routes`. What does the router do? *(edge case)*
   Answer: There is no "no match" case: `execute` has to return a block, and that block is accepted only if it is the same object as one of `routes` or has the same `name` as one. `escalate` is neither, so the router fails with a plain error, `Router "<name>" selected invalid route "escalate". Route must be one of declared candidates.`, which the client sees as `execution_error`. A `validateRoute` function, if set, replaces this membership check entirely, and a `false` from it throws the same error. Facts: section 3e (No route matches, `validateRoute`), section 11 second lookup, `rt:277-294`, `rtt:26-44`.
3. `cleanMessage` sometimes fails on a flaky call, so someone adds `retry: { maxAttempts: 3 }` to it. It runs as a step inside `handleTicket`, which is the action's block. When `cleanMessage` throws, how many times does it run? *(edge case)*
   Answer: Once. A block's `retry` is read only when that block is the action's root block. A block used as a step, a route or a tool runs once whatever its `retry` says. To retry, put the policy on `handleTicket` (the root), which retries the whole sequencer, or catch the failure with `rescue`. Facts: section 6 first row (`eb:423-426`, the [ran] probe: 3 runs as the action's block, 1 as a step), section 14 contradiction 1.
4. `draftReply` (a generator) calls the `lookUpOrder` tool several times in one reply. `lookUpOrder` keeps a call count in its own `stateSchema` and writes it through `ctx.self`. After three calls, what does the count read, and how would you make it count across calls?
   Answer: It reads 1 each time: a tool's own `ctx.self` is a new container on every call, because each call is a new scope initialised from its schema. A tool is a child of the generator that calls it, so `ctx.parent` in `lookUpOrder` is `draftReply`; writing the count to `draftReply`'s state through `ctx.parent` accumulates across the tool loop. That needs `draftReply` to declare a `stateSchema`, otherwise `ctx.parent` has no state operations. Facts: section 9c (tool row, `bst:271-326`), section 9a (`ctx.parent`), section 3a and `te:182`.
5. `draftReply` has an `onCompleted` hook that logs the reply. Someone edits the flow to use `draftReply.connectOutput(fn)` to reshape its output for the next step. Does the log still appear, and what output check is left? *(edge case)*
   Answer: No log. `.connectOutput(fn)` returns a new block with no `onCompleted`, no model-output mapper and `outputSchema: z.any()`: the original hook and output schema are dropped. To keep the log, add the hook to the returned block, or reshape with a connector on the next step instead. Facts: section 1c (`.connectOutput` row, `bb:535-557`, [ran]), section 5a (`.connectOutput(fn)` drops it).
6. Two customers send tickets at the same moment, so two requests run `handleTicket`, which declares a `stateSchema`. Do the two runs share that sequencer state, and can one run's writes fail with `ConcurrentModificationError` because of the other? *(edge case)*
   Answer: No to both. A block's or a sequencer's own state lives in an in-memory container created for one execution of that block within one request, so each request gets its own. Writes to it are applied one at a time per container and never raise `ConcurrentModificationError`; only session, user and org state are version-checked and can. Nothing is kept after the request except a durable sequencer's checkpoint and, where stored, the `state_change` items. Facts: section 9c (`cec:4549-4554`, `sc:150-215`), section 9d (versus session, user and org), section 9e, section 12.
