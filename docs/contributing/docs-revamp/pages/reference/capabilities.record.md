## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. `summarizeOrder` should only see order data for some customers, so you write its `uses` as a function: `uses: [(ctx) => ctx.session.state.vip ? [orders] : []]`. When it runs for a VIP, is the `orderLog` resource there, and does `ctx.cap.orders` exist? What do you change?
   Answer: No to both. A dynamic (function) entry is read on every run, but it installs no resources, no state schemas and no `fns`. Resources must exist before the block runs, so `orderLog` is not declared, and `ctx.cap` is built only from the static list. On a generator the function can only add the capability's `context`, `tools`, `controlTools` and `history` presets each run. Its `model`, `providerOptions` and `caching` are not read, and a capability with open `config` throws when the function runs. Fix: list `orders` statically next to the function, or move `orderLog` to a capability listed statically (D-1 and its lookup answer; I-1 limit 4).
2. `draftReply` should get the `orders` context preset but must not be able to call `lookUpOrder`. `summarizeOrder` should keep both. How do you write that, and does `summarizeOrder` change?
   Answer: In `draftReply`, write `uses: [orders.presets({ tools: false })]`, or `orders.with({ tools: false })`. Either call returns a new reference and leaves `orders` as it was, so `summarizeOrder`, which lists plain `orders`, still has every preset. With no `default` list every preset is on, and `default: []` turns them all off. Turning the preset off does not remove `orderLog`, the capability's top-level state or its `ctx.cap.orders` helpers, because presets never control `fns` and top-level fields always install (P-2 rows 1, 2 and 4; B-1).
3. A teammate adds a handler that records each order, and puts plain `orders` in its `uses`. The app crashes on startup, before any request. Why, and what is the smallest fix? *(edge case)*
   Answer: The `context` and `tools` presets are generator-only, and both are on by default. When the handler is built, it throws `Capability "orders" preset "context" declares context, but the consuming block is a handler. context is only valid on generator blocks.` The type system does not catch this: `uses` accepts any capability on every block kind, so the error is a throw at build. Fix: `orders.presets({ context: false, tools: false })` on the handler. The handler still gets `orderLog`, the state and `ctx.cap.orders` (P-1 fact 1; P-2).
4. Someone edits `draftReply` to `orders.presets({ tool: false })`, dropping the 's'. What happens, and when? What if they write `orders.with({ tool: false })` instead? *(edge case)*
   Answer: In TypeScript, both are compile errors, because the override keys must be preset names the capability declares. If it gets past the compiler, `.presets()` itself returns a reference and the error comes when `draftReply` is built: `Unknown preset "tool" on capability "orders"`. `.with()` fails earlier, at the call. `orders` has no `config`, so a key that is not a preset name throws `.with() on capability "orders" received key(s) [tool] that match neither a preset nor a config field ... Presets: [context, tools]. Config fields: [(none — no config)]`. A capability with an open config (passthrough, scalar or schemaless) would quietly treat that key as config (P-2 last row; B-1 `.with()` routing, steps 3-4).
5. A second team copies the `orders` definition into their own module. They call `defineCapability({ name: "orders", ... })` again and list their copy in a block that already lists the original, through a shared dependency. What happens? And what if both lists use the same `orders` object, configured two ways? *(edge case)*
   Answer: Two separate `defineCapability` calls with one name throw at build: `Capability name collision: "orders" is declared by two different defineCapability() calls`. Reuse the one exported object. The same object listed twice installs once. If the two references carry different `.presets()`, the first one reached wins (dependencies are reached first, depth first). If they carry different `.config()` values, the build throws `Conflicting .config() for capability ...`, while identical config is allowed (C-6; P-2 fact 1; O-1 fact 4).
6. `draftReply` declares its own `tools: [sendReply]` and lists `orders`. Does the model get `lookUpOrder`? Do the orders context and `orderLog` still arrive? What if the list is `tools: []`?
   Answer: `lookUpOrder` does not reach the model. When a generator declares `tools:`, even as an empty array or a function, the capability's `tools` preset is dropped, and its tool functions are not even called. To keep the tool, name it in the generator's own list: `tools: [sendReply, lookUpOrder]`. Only `controlTools` get past a declared `tools:`, and they are for tools the block's own configuration already implies. The context preset, `orderLog`, the state and `ctx.cap.orders` always arrive (G-1).

- Line 310: "A resource accessor, a target and an own-state field declared by both a capability and the block must share one reference, or the build throws." Untrue: Only resources and own-state are checked against the block's own declarations (mergeWithBlockResources throws on a different defineResource reference; mergeCapabilityOwnStateWithBlock throws on a different field schema). The throw applies to a target declared twice across capabilities. (packages/core/src/capability/merge.ts:375-395 and 552-556; packages/core/src/blocks/internal/resolve-capabilities.ts:131-140; packages/core/src/capability/types.ts:729-731)
