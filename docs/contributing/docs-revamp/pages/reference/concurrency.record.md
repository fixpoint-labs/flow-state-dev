## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A chat flow's `send` action declares no `concurrency`, and neither does the flow's `request`. A user sends a second message to the same session while the reply to the first is still streaming. What happens to the second message?
   Answer: It runs at once, beside the first. Resolution is `action.concurrency ?? flow.request.concurrency ?? "allow"`, so an action with no policy at either level runs as `allow`, and an `allow` request runs alongside the one in flight (facts 1.2, policy table row `allow`).
2. You want a user's messages to one session to run one after another, in the order they were sent, instead of overlapping. Which policy do you set, and where?
   Answer: `queue`, declared on the action as `concurrency: "queue"`, or flow-wide as `request.concurrency`. `queue` waits its turn and runs after the one ahead finishes, in arrival order (FIFO), one at a time. `defer` also waits, but for the key to go empty rather than for its turn in line (facts 1.1, policy table, lookup "Which policy queues?").
3. The action is set to `queue`. The reply ahead of a waiting message runs long, and the waiting message has been in line for more than 30 seconds. What does the caller get, and is it safe to send again? *(edge case)*
   Answer: The waiting request fails with `ConcurrencyQueueTimeoutError` (status 503) after waiting 30 s. Over MCP it surfaces as a server-busy error with `retryable: true`. It is safe to retry with backoff. The 30 s counts only time spent waiting for the key, not time queued behind unrelated work (policy table `queue`, section 3, 4.2, 3.4).
4. A webhook action is set to `reject`, so a duplicate delivery is dropped. The provider sends a delivery again while the first is still running, and sends it a third time after the first has finished. What does the provider get each time, and what is stored for the dropped one? *(edge case)*
   Answer: While the first is running, the redelivery is refused: the webhook replies `200 { status: "skipped", reason: "in_flight", requestId }`, with `requestId` naming the in-flight request (a 200, so the provider stops retrying). Nothing is created for the dropped request: no request record, no stream. The third delivery, after the first finished, is not caught by `reject` and runs. Catching that needs an idempotency key (policy table `reject`, section 4 webhook row, 4.1, 4.3, 8.1). Over HTTP the same refusal would be `409 { error: "ConcurrencyRejected", message, requestId }`.
5. A client sends `{ "concurrency": "allow" }` in the request body or metadata of an action the flow declares as `reject`, hoping to skip the refusal. Which policy applies? *(edge case)*
   Answer: The flow's declaration, `reject`. A caller cannot choose the policy: a body or metadata naming another policy is ignored (fact 1.13).
6. You declare `concurrency: "debounce"` on an action to collapse a burst of messages. What happens? *(edge case)*
   Answer: The flow fails to build: declaring `debounce` (or `restart`) throws at definition time with a message saying the name is reserved but not implemented. An unknown name, or an unsupported `key` value, throws the same way. The implemented names are `allow`, `queue`, `reject`, `hold` and `defer` (facts 1.4, 1.5, 1.6).
