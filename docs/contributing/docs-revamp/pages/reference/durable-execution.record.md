## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A flow has three steps: a handler that looks up an order, a generator that drafts a refund note, then a handler that calls `ctx.suspend!({ reason: "user_approval", ... })` before issuing the refund. A person approves an hour later. Which of the three steps run again, what does `ctx.suspend` give the third step this time, and are the lookup and the model call repeated?
   Answer: Resume re-enters the action under the same request id in replay mode. The lookup handler and the generator both have a `completed` recorded output, so they are skipped: their outputs are injected, with no `execute`, no model call, no emit and no state write (section 3; lookup in 16). The block that paused is never skipped. It runs again from the top, and this time `ctx.suspend` returns the approve payload (`resumeData`), or `undefined` if none was sent (1.2). Anything that block did before the `suspend` call happens again. A `transient: true` block would also run again, because it leaves no record.
2. The refund step charges a payment provider and then calls `ctx.suspend`, in that order. After the approval the customer is charged twice. Why, and what are the two fixes the page gives? *(edge case)*
   Answer: The paused block re-runs from its top on resume, so a side effect placed before the `suspend` call fires a second time (sections 3 and 5). Fix one: move the side effect after the `suspend` call. Fix two: guard it. `ctx.runOnce(key, fn)` runs `fn` once per `(requestId, key)` and stores the result durably, and resume keeps the request id, so the re-run gets the stored value and does not call `fn`. Or pass `ctx.idempotencyKey` (`${requestId}:${blockPath}`, the same on every retry and resume) to the provider's idempotency header. That also closes the remaining gap, a crash after `fn` finishes but before the `runOnce` write lands. Note that `retry` makes a new request id, so it starts with an empty `runOnce` record and a different key.
3. A pause was opened with no `timeoutMs`, and nobody answers it for three weeks. The host has `durabilityRetention: {}` set. Is the paused run still there, and what happens next?
   Answer: Yes. A pause with no deadline (no `timeoutMs`; for `suspendForUser`, no `deadline` and no host `userDeadlineMs`) stays `pending`, and the request stays `suspended` until someone answers, stops or cancels it. Nothing ages it out. Pruning never touches the checkpoints of a `suspended` or `in_progress` request, and a pending suspension is not terminal, so pruning skips it (11.1; lookup in 16). The 7-day `suspensionTerminalMaxAgeMs` counts from `resolvedAt` and applies only to resolved gates. On a persisting store (SQLite, Postgres, filesystem) the pause also survives a restart. On in-memory stores no pause is allowed by default.
4. Three gates each have a 10-minute deadline and nobody answers: an approval (`suspendForUser` kind `approval`), an input form (`suspendForUser` kind `input`), and a raw `ctx.suspend` with a custom reason and `allow: ["submit"]`. A server is running. What happens to each at the deadline, and what does a resume sent after the deadline get? *(edge case)*
   Answer: A running server's sweeper marks each `pending` gate `expired` at its deadline, within about a second on a long-lived host (11.2). The approval continues as a no: `suspendForUser` returns `{ approved: false, deadline: true }`, and a raw approval throws `SuspensionRejectedError` with `expired: true`. The input form continues with `SuspensionTimeoutError` thrown at the call, and the request fails if that is left uncaught. The custom gate that allows no `reject` is only marked `expired`: the run does not continue. A resume or answer sent after the deadline gets 410 `Suspension "<id>" expired at <ms>`. The routes check `expiresAt` themselves, so this holds between sweeper ticks and with retention off. A one-shot `fsdev run` sweeps nothing; the next server on that store expires the gate as soon as it starts.
5. A router picks a branch with `Math.random()`, and the chosen branch pauses for approval. After the approval, the resume fails. What error does it fail with, and what rule did the router break? *(edge case)*
   Answer: On resume the router's selector (`execute`) runs again and its result is checked against the recorded `router_decision`. A different pick, or a recorded route that is no longer declared, fails the resume with `RouteUnavailableError` (code `route_unavailable`, `retryable: false`), saying the selector must be deterministic for a router whose branch can suspend (7.2). Selectors, and their mapping closures, must be pure over their input. The same pick continues the branch and injects its completed work. Composition callbacks (`.map`, `.stepIf`, connectors) also run again, so a nondeterministic call in them can steer a different branch on resume. Move such a call into a block whose output is recorded, or into `runOnce`.
6. Two people can see a suspended request. Alice owns it. Bob is signed in as another user and sends a correct `{ suspensionId, action: "approve" }` to the resume route. Then Alice approves twice: her second click lands after the first approval was accepted. What does each call get back? *(edge case)*
   Answer: Bob gets 404 `Request "<id>" not found`. That is the same body as for an unknown request or another tenant's request, so he cannot tell them apart, and the pause stays open (6.1, 6.2). Alice's first approve gets 202 `{ requestId }` with the same id, or the live SSE stream if she sent `Accept: text/event-stream`. Her second click gets one of two answers. If it arrives while the first resume still holds the 60 s lease, it gets 409 `Concurrent resume in progress`. Once the request is no longer `suspended`, it gets 409 `Request is "in_progress", not "suspended"`. Through the `answer` route a resolved stop answers 409 `refused: "already-resolved"`. The answer is recorded with `resolvedBy` set to Alice's user id; a `resumedBy` field sent in the body is ignored.

- Waits and wakes. A due wake: the sweeper runs the internal entry the wake names, as the session's owner, and a wake that fell due while the server was down fires once it runs again. A host without wakes (no durable execution, or a store with no `wakes` store) logs once at start: `this host keeps no wakes: debts are paid on their fast paths only`. Nothing can wait there, and a task split into pieces stays `in_progress` when a piece ends as the server stops, because nothing wakes it. A wait's deadline defaults to 5 minutes. `waitDeadlines: { defaultMs, minMs, maxMs }` sets the bounds. `minMs` defaults to 1 second and `maxMs` to 24 hours, and the host refuses to build unless 0 < min <= default <= max. A wait that names a deadline outside [minMs, maxMs] is refused, not clamped. A wake whose run dies fires again 30 seconds later, until a run clears it. Work owed past `maxDebtAgeMs` (default 24 hours from when it fell due) is given up, recorded undeliverable on its task and logged. → R-19 (corrected by pass 5)
