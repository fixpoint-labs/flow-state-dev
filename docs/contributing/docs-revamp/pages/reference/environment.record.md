## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support app's `reply` generator uses `openai/gpt-6-luna`, and you also want an Anthropic model for one step. Which variables do you set, and if you set only `AI_GATEWAY_API_KEY` (no `OPENAI_API_KEY`), can the OpenAI model still be reached?
   Answer: OpenAI reads `OPENAI_API_KEY` (package `@ai-sdk/openai`), Anthropic reads `ANTHROPIC_API_KEY` (`@ai-sdk/anthropic`); Google is `GOOGLE_GENERATIVE_AI_API_KEY`, Vercel AI Gateway `AI_GATEWAY_API_KEY`, OpenRouter `OPENROUTER_API_KEY` (section 2 table, `pd:8-18`). Setting the key is enough; no model config is needed. A gateway key makes every built-in provider (anthropic, openai, google) available through the gateway, so yes, `openai/gpt-6-luna` resolves through the gateway. Where both a direct key and a gateway key exist for one provider, the direct key wins (`pd:6-8,41-50`).
2. In a monorepo you put `OPENAI_API_KEY` in `apps/support/.env.local` and run `fsdev run` from the repository root. The key is not picked up. Why, and what are the two fixes? Would renaming the file to `.env` have helped? *(edge case)*
   Answer: The `.env.local` walk-up only climbs: it checks the working directory and then each parent, never a child folder, so a file in `apps/support` is not found from the root (`le:72-92`). Fix by running `fsdev` from `apps/support`, or passing `--dotenv apps/support/.env.local`. Renaming to `.env` would not help: only the filename `.env.local` is read (`le:17`). The flag is `--dotenv`, not `--env-file`, because Node consumes `--env-file` first.
3. Your shell already exports `OPENAI_API_KEY`, a `--dotenv` file sets a different value, and `.env.local` sets a third. Which value does the support app use? And if you then edit `.env.local` while `fsdev run` is running, when does the change take effect? *(edge case)*
   Answer: The shell wins: precedence is (1) the real shell environment, which no file overwrites, (2) `--dotenv` files in the order given, (3) `.env.local` in the working directory then each parent; the first source to set a key wins (`le:1-14`, tested in `load-env.test.ts`). A key the shell sets to the empty string still counts as set. Files are read once at start, so an edit needs a process restart; only `fsdev dev --watch` restarts its child automatically when an env file it loaded is saved (`dev:283-286`).
4. You set `FSDEV_INTENT_CHAT=openai/gpt-6-luna,anthropic/...` to swap the support app's `chat` intent in staging. What happens? What variable name does an intent named `my-custom` use, and does the override change a block that hardcodes `model: "openai/gpt-6-luna"`? *(edge case)*
   Answer: The value must be one `provider/model` or `name:model` string; a comma-separated list is not a valid model string, so `createModelResolver` throws at construction with a message prefixed `createModelResolver: FSDEV_INTENT_CHAT:` (`cmr:553-577`). The name is the intent uppercased with `-` turned to `_`: `FSDEV_INTENT_MY_CUSTOM`. An override for an intent the resolver does not declare is warned once and ignored. Overrides replace what `models`/`createModelResolver` declare; a hardcoded model string on a block never goes through intent lookup, so it is unchanged. `FSDEV_DEFAULT_MODEL` replaces the default model.
5. Deploying the support app on Postgres, the platform sets `DATABASE_URL` and you also set `FSD_DB_URL` to a different database. Which one do `postgresStores()` and `vercelPostgresStores()` connect to, and what happens if neither is set? *(edge case)*
   Answer: Order is fixed: `options.connectionString` first, then `FSD_DB_URL`, then `DATABASE_URL` (`pg:127-131`, `vst:73-77`), so `FSD_DB_URL` wins. Default is none. With none (and no `poolOptions.host` for postgresStores) they throw, e.g. `createPostgresStores: no connection string provided. Pass { connectionString } or set FSD_DB_URL / DATABASE_URL.`, and the throw happens when the pool is first built, not when the function is called. Separately, `FSD_ENV` picks the stores profile (an undeclared name throws `FlowStateConfigError` at `ready()`); `NODE_ENV` never picks a profile.
6. You scale the support app to two Node processes behind one address with `serve()` from `@flow-state-dev/node`. A second user's push ticket, minted by process A, is rejected by process B. Which variable fixes this, and what do `PORT` and `HOST` default to? *(edge case)*
   Answer: `FSD_PUSH_SECRET`: `serve()` signs push tickets with `pushSecret` if given, else a non-empty `FSD_PUSH_SECRET`, else a random key per process, so each process had its own key. Set the same value on every process behind the address (`nserve:117-118,362-364`). `PORT` defaults to `3000` for both `serve()` and `fsdev serve` (a non-numeric `PORT` falls back to 3000 in `serve()` but stops `fsdev serve` with `Invalid port`, exit 3). `fsdev serve` reads `HOST` (default `0.0.0.0`); `serve()` reads no `HOST` and uses `options.host` or `0.0.0.0`.
