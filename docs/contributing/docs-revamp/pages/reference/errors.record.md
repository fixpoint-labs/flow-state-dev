## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In the support desk flow, a handler step inside `handleTicket` throws a plain `new Error("orders DB down")` while running the `reply` action. What does the client receive on the stream and in the request's result, and what are the error's `code` and `retryable`?
   Answer: The plain throw is wrapped in a FlowError with `code: "execution_error"`, `retryable: false`, the same message, and the original kept as `cause` (A1). The stream carries one `error` item: `type: "error"`, `status: "failed"`, `message: "orders DB down"` verbatim, `code: "execution_error"`. It has no stack, and it has `details` only if the thrower set some or the error has a cause (A2, A3). After that item comes the request's `failed` status event. On the request: `status: "failed"` and `result.error = { code, message }`, read through `handle.result()` or the session's request list. `details` and `cause` are not in `result.error` (A8; answer key section 8). The block name is not on the item. It rides on the FlowError that hooks and errorCapture get (B2).
2. `lookUpOrder`, a tool that the `draftReply` generator calls, throws because the order service timed out. Does the customer's `reply` request fail? *(edge case)*
   Answer: No. An ordinary tool error does not fail the request. The generator hands the model a failed tool result, the text `Tool "lookUpOrder" failed: <message>`, and the run goes on. The failed call is recorded as a `tool_output` item with `status: "failed"` and `error: { message, code?, details? }`. It is replayed on later turns as the same failed text (A11, F). No `error` item is emitted for it. The request can still end failed if something else throws.
3. The `reply` action's input schema expects a numeric `ticketId`, and a client sends `"ticketId": "A-17"`. Does `send` reject? What does the result look like, and does errorCapture hear about it? *(edge case)*
   Answer: The call does not reject. The request is accepted, then settles `failed` with `code: "validation_error"` (`retryable: false`). The message is `Action input validation failed at "ticketId": <message>`, naming the first issue only. The `error` item has no `details`. No block ran, so `handleTicket` has no `block_trace` row (A5). errorCapture, when it is set, gets one `final` event with no `blockName` and no per-block event (D4, D8).
4. The team adds `retry: { maxAttempts: 3 }` to a `handleTicket` step that keeps throwing a plain Error. How many times does it run, and what reaches errorCapture? What changes if the step instead throws `new FlowError("bad ticket", { code: "bad_ticket", retryable: false })`?
   Answer: With no policy a block is not retried (the default is `maxAttempts: 1`). Under this policy a plain throw has no `retryable` flag, so it is retried: the step runs 3 times, doubling the delay from `baseDelayMs` (default 0). The request then fails with the last error (C1). errorCapture gets one event per failed attempt, with `attempt` 0, 1 and 2, then the `final` event (D5). Each attempt's `blockInstanceId` is different, and `blockPath` is the stable key (D2). A FlowError with `retryable: false` runs once, with no retry, and the client sees `code: "bad_ticket"` (C1, A1). A `.rescue()` on the block runs only after the last attempt, or straight away for a non-retryable error (C1).
5. The app wires `createFlowState({ errorCapture })` to forward every event to a tracker, and also puts an `onErrored` block on the `reply` action to log failures. One ticket that failed shows up twice in the tracker. Separately, the `onErrored` block itself throws once. What explains the duplicate, how is it fixed, and does the throwing hook change the request's outcome? *(edge case)*
   Answer: errorCapture is off until it is set (D1). A failed request sends one event for the leaf block that threw and one more `final: true` event (`scope: "request"`), so forwarding both reports the failure twice. To report each failed request once, forward only `event.final`. To report each failing block, skip `event.final` (D7, D10). A failure that a `.rescue()` recovered sends the per-block event but never a `final` one (D3). The action's `onErrored` hook is a block that gets `{ requestId, actionName, error }`. It runs after the failed record, the final event and the `failed` status event (E1). A hook that throws is ignored: the original failure and `result.error` stand. The hook's own throw does send an extra errorCapture event under the hook's block name (E2, D3).
6. A support agent clicks Retry on a customer's failed turn. What happens to the original request? What does a different user who tries to retry that same request get? If the same `reply` action runs as a BullMQ job and throws a plain Error, is the job retried automatically? *(edge case)*
   Answer: The retry route (`handle.retry({ input? })` on the client) re-runs a `failed` or `interrupted` request as a new request with a new id. The response names the old request in `retryOf`, and the original record stays `failed` (A9, F). Retrying a request that is still `in_progress` gets 409. A caller who does not own the request gets 404, the same answer as for a missing id (A9). Only requests that arrived over `http`, `mcp` or `scheduled` (plus a host's named sources) can be re-run, and the request list's `retryable` field follows the same rule (A9). A queued job is retried only when the failed result is not marked `retryable: false`. A plain throw is marked false, so the job fails at once with no retry, whatever `attempts` (default 3) is set to (C4, C8).
