## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You define one flow with kind "review" and cardinality "collection" and register two copies, review-east and review-west. A teammate's script sends POST /api/flows/review/actions/run. What happens, and what should the URL name to reach the east copy?
   Answer: The bare kind of a collection is not an address: with only review-east and review-west registered, POST /api/flows/review/actions/run answers 404 { error: "Unknown flow \"review\"" }, with no fallback to whichever copy registered first. Every entry point (HTTP routes, client.flow(id), fsdev run <id> <action>, a queue job's flowKind) reaches a copy by its instance id, so the URL should be POST /api/flows/review-east/actions/run. A singleton's id is its kind, which is why my-chat is reached as /api/flows/my-chat. (Facts 6c, section 9; test fio:121-141.)
2. A user started session s1 on review-east. A later request for the same session is sent to review-west instead (POST /api/flows/review-west/s1/actions/run). What does the caller get, and is anything written? *(edge case)*
   Answer: The stored session names its owning instance (flowId = review-east), and that instance governs the record, never the one the caller addressed. The action route refuses with 409 { error: "wrong-instance-session", message: "Session \"s1\" is not owned by flow instance \"review-west\"" }. Nothing is written, and the refusal never names the owning instance. Called programmatically, runAction rejects with FlowInstanceBindingMismatchError before anything is touched. (Facts 6d; test fio:159-222.)
3. A second user tries to send an action into s1, a session another user created on review-east. What do they see, and how does that differ from addressing the wrong copy? *(edge case)*
   Answer: Admission checks another user's session first, before checking the instance. Another user's session raises UserBindingMismatchError and answers over HTTP as 404 { error: "Unknown session \"s1\"" }, the same answer as an id with no session, so the session's existence and owner are not disclosed. Addressing the wrong copy as the owning user is a 409 wrong-instance-session instead. (Facts 6d; be:154-183, ar:278-283.)
4. You set request.onFinished to a handler block to log every request's outcome. Which outcomes will it see, when does it run relative to onCompleted and onErrored, and does it run when a request suspends at a gate?
   Answer: onFinished is a block, not a function. It fires once per request run that ends, whatever the ending: completed, incomplete, failed, aborted or interrupted. It runs after the terminal status is recorded and emitted, and after action.onCompleted and request.onCompleted (on success) or action.onErrored and request.onErrored (on failure). Its input is { requestId, actionName, status } plus output (completed/incomplete) or error (failed). It does not fire when a request suspends at a gate; it fires when the resumed run ends. On failed, aborted or interrupted, a throw inside it is swallowed. (Facts 8, section 9; test ex:2207-2315, ab:2412-2468.)
5. The run action declares tokenBudget { maxTotalTokens: 10000, onExceeded: "stop" }, with an action-level onCompleted hook. A run consumes 12000 tokens. What status does the request end with, and which hooks run? *(edge case)*
   Answer: The budget is checked once, after the block returns. With onExceeded "stop", a transient status item reads "Token budget exceeded: consumed 12000 of 10000" and the request ends incomplete. onCompleted hooks do not run; onFinished does, with status incomplete. With the default onExceeded "error", the request would instead fail with validation_error. (Facts 2a, 8; test rae:446-499.)
6. Your review flow declares user.stateSchema with a field "tier" as a string, and another flow on the same server declares "tier" as a number. What happens when both are registered, and what does setting isolateUserState: true on review change? *(edge case)*
   Answer: By default every flow shares one user record per user per organization, so their user schemas are checked against each other when flows are registered. A field with a different type (or a different default) is refused with CrossFlowSchemaConflictError, and the message suggests isolateUserState: true or reconciling the schemas; a failed registration leaves the registry unchanged. With isolateUserState: true, review's user record is keyed to the instance id (review-east and review-west each get their own, separate from each other and from other flows), its schema drops out of the cross-flow check, and user-scoped resources with no flowIsolation of their own default to isolated. It moves no existing data: the flow starts on a fresh record and the shared one stays for the others. (Facts 7, section 9; test fiso:277-345.)
