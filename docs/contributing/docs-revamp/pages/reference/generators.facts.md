## Table G-1: Generator options (`GeneratorConfig`, `gen:487-649`)

`GeneratorConfig` extends `BlockConfig` minus `execute`, `onCompleted`, `stateSchema`, `flowConfigSchema` (`gen:538-541`), and then re-declares `onCompleted`, `stateSchema` and `flowConfigSchema` (`gen:541-558`). Required: `name` (`blk:1055`) and `prompt` (`gen:608`). `model` is required **unless** a capability in `uses` contributes one; a block-level `model` always wins. ## Table G-2: The `context` slot, form by form

`context` is a `GeneratorSlot`: one entry or an array of entries. An entry is a string, a `ContextObject`, an array of `ContextObject`s, or a function `(input, ctx) => unknown` (sync or async) whose return value is then treated as an entry. Functions at the top level are called once per run, and again before every later step of the tool loop when the generator has any function-valued prompt, context or tools (G-5). (`gen:325-362`, `gen:799-818`, `gen:3166-3196`; `tps:85-145`.)

| Form | Written as | What the model receives | Escaped? | Cite |
| --- | --- | --- | --- | --- |
| String | `context: "Plan: pro"` | One extra `system` message of its own, after the prompt message. | No | `asm:206-208`, `agg:172-175`; `toc:181-200`, `tma:69-80` |
| Function returning a string | `context: (input, ctx) => "..."` or `contextFn(...)` | Same as a string: its own `system` message. | No | `agg:176-180`; **[ran]** (`"fn string"` came out as its own system message) |
| Pre-built message | `{ role: "system" \| "user" \| "assistant" \| "tool", content: ... }` | Passed through to the message list unchanged, in author order with the strings. `role` must be one of those four literals and `content` must be present. | No | `agg:95-107`, `agg:227`; `tag:218-266` |
| Object of tagged sections | `context: { documents: [a, b], userPrefs: "x" }` | One XML block per key, appended to the prompt message after a blank line, see G-2a. | Yes, string leaves | `agg:195-226`, `asm:164-210`; `toc:38-56` |
| Array | `context: ["bare", { documents: "d" }, fn]` | Each element handled by its own row above. Arrays flatten; `null`, `undefined` and empty strings are skipped. | per element | `agg:164-190`, `gen:824-837`; `tag:12-28`, `tag:167-175` |
| Capability contribution (`uses`) | a preset's `context` | Appended to the generator's own entries: static capability entries first, then entries from dynamic `uses`. Object contributions to the same key aggregate into one tag. | per form | `gen:2926-2964`; `toc:58-89` |

### G-2a: Object-form rules

- **Tag names.** Authored keys in `camelCase`, `snake_case` or `kebab-case` all normalize to `kebab-case` before aggregation (`userPreferences`, `user_preferences`, `user-preferences` are one tag). `helpers/string-case` is `normalizeTagName`. `@flow-state-dev/contracts/src/helpers/string-case.ts:22-35`; `agg:230-236`; `tag:49-62`; `toc:91-112`. **[read]**
- **Valid names.** After normalization a name must match `/^[a-z][a-z0-9-]*$/`. A name with a leading digit, whitespace or any other character throws at render: `Invalid context tag name "1st": must match /^[a-z][a-z0-9-]*$/ after normalization ...`. `rt:38-70`; `tag:202-206`; **[ran]**.
- **Reserved names.** These throw: `active-skill`, `thinking`, `answer`, `tool-use`, `tool-result`, `function-calls`, `invoke`, `parameter`, `system`, `user`, `assistant`, `role`, `message`. Checked after normalization, so `tool_use` and `tool-use` are both refused. The error: `Reserved context tag name "thinking": this name collides with a framework-emitted tag or a model-conditioned name ... Choose a different key.` `rt:19-35`, `:65-70`; `trt:33-48`; `toc:222-236`; **[ran]**.
- **`role` as a key.** An object that has a `role` key but is not a pre-built message (`role` is not one of the four literals, or `content` is missing) throws a specific error: `Generator context entry has a `role` key whose value is string "analyst" — not a valid AI-SDK message role. If you meant a tag named "role", rename it ...`. `agg:197-222`; `tag:236-266`; **[ran]**.
- **Value types.** `string`: leaf text. `string[]`: each element a line under the tag. Nested object: nested tags, recursively (not JSON). Function: called with `(input, ctx)`, result re-enters these rules. `null` / `undefined`: a placeholder. Any other value (number, boolean) is coerced with `String(value)`. If you want JSON inside a tag, serialize it yourself. `agg:268-340`; `tag:29-47`, `:76-165`.
- **Aggregation.** Contributions to one key, from the generator and from capabilities, collect in author order inside one tag. `agg:268-300`; `toc:58-89`; `p-ctx:105-130`.
- **Placeholders.** A `null` value reserves its position among the top-level keys. A tag nobody fills is omitted from the output entirely. A placeholder stays type-neutral until a contributor gives it a leaf or an object. `agg:240-262`, `xml:58-66`; `toc:138-180`; `tag:93-134`.
- **Type mismatch.** A string and a nested object on the same key throw, in either order: `Context key "a" type mismatch: a nested object was contributed after a string contribution.` (and the reverse, `... a string was contributed after a nested-object contribution.`). `agg:276-343`; `tag:176-195`; `toc:279-end`; **[ran]**.
- **Escaping.** `&`, `<` and `>` in string leaves become `&amp;`, `&lt;`, `&gt;`. Nested-tag structure is not escaped. Strings in the array form, and prompt text, are not escaped. `xml:125-160`, `:161-164`; `toc:203-221`; **[ran]** (`<d1>` came out `&lt;d1&gt;`).
- **Rendering.** Two-space indent per nesting level, one `<tag>` block per top-level key in first-seen order, joined by newlines. `xml:84-160`.
- **Where the XML goes.** After the prompt text and a blank line, in the same `system` message (G-3). `asm:164-210`; `toc:38-56`; **[ran]** (`"PROMPT\n\n<documents>\n  &lt;d1&gt;\n  d2\n</documents>\n<user-prefs>\n  x\n  y\n</user-prefs>"`).

### G-2b: Formatters and helpers

- `contextFn(schemas, fn)` returns a function that fits the `context` slot. `fn` receives `{ session }`, `{ session, user }` or `{ session, user, org }` and the block context, and must return a string. The schemas argument is a type carrier only: it is never run, so a Zod `.default()` is not applied and `session.x` can be `undefined`. The `{ session, user }` overload's callback is typed for `user` as a known type mismatch in the repo's own test, so show the session overload. `ctxfn:1-103`; `T/context-fn.test.ts:24-50`.
  - Used as an array entry it becomes a `system` message of its own; used as an object value it is wrapped in a tag and aggregates with other contributions to that key (doc comment, `ctxfn:14-22`).
- Text formatters from `@flow-state-dev/core/prompt`, each pure; falsy parts are dropped:
  - `section(title | { title, level }, ...content)` → `## title` (level 2 default, clamped 1 to 6) then the non-falsy content lines (`pidx:28-55`).
  - `list(items, { ordered?, bullet? })` → `- item` lines (or `1. item`; `bullet` default `-`), `""` when empty (`pidx:57-90`).
  - `keyValues(record)` → `key: value` per line, `null`/`undefined` values skipped (`pidx:92-117`).
  - `table(rows, { columns? })` → GitHub-style Markdown table; columns default to the union of keys in first-seen order; `|` is escaped and newlines flattened; `""` for no rows or no columns (`pidx:119-157`).
  - `entries(record, (key, value) => MaybeString)` → one line per entry the formatter returns truthy (`pidx:159-180`).
  - `codeBlock(code, language?)` → fenced block (`pidx:182-195`).
  - `join(...parts)` → falsy dropped, joined with a blank line (`pidx:197-207`).
  - `when(condition, content | () => string)` → the content, or `undefined` (`pidx:209-224`).
  - Tests: `T/prompt.test.ts`, `T/prompt-xml.test.ts`.
- XML helpers, same subpath: `xmlTag(name, content)` (`<name>\n  content\n</name>`, `""` when content is empty or null, does not escape; `xml:58-66`), `renderTaggedContext(tagged, order, { indent?, escape? })` (`xml:84-92`), `validateTagName(name, source?)`, `RESERVED_TAG_NAMES` (`pidx:255`).
- Prompt files: when a `.md` prompt's template has a `<context>` block, the default append of the XML block is suppressed and the template renders context itself from `config.context`, a `Record<string, string>` keyed by tag name that holds the resolved result of the `context` slot plus every capability contribution. A key the template does not render is dropped. `asm:164-210`, `asm:140-152`; `tpf:47-108`.

## Table G-3: In what order is context assembled? (lookup)

The model's message list, in order (`asm:70-102`, `gen:3088-3166`; `tma:109-136`; **[ran]** with one prompt, a bare string, object context, a function string, two tools, a three-message history and a `user`):

| # | Part | Role | Notes | Cite |
| --- | --- | --- | --- | --- |
| 1 | `prompt` text, a blank line, then the XML block built from every object-form `context` entry | `system` | One message. Omitted if both are empty. With a `PromptFile` that owns `<context>`, the XML block is replaced by the template's `<context>` render. | `asm:164-210` |
| 2 | Bare-string and function-string `context` entries, and pre-built messages | `system` (or the message's own role) | One message each, in author order across the array, and static capability entries after the generator's own. | `asm:206-209`, `gen:2926-2964` |
| 3 | The `<tools>` list (when `describeTools` is on and any tool has a `description`) | `system` | Last of the system messages, because it is added to the context values after the others. A tool without a description is not listed. | `gen:3088`, `gen:3126-3133`, `gen:975-982` |
| 4 | `history` | as stored | Turns of the session. Includes the in-flight request's own items by default. | `asm:96-101`, `gen:3131-3141` |
| 5 | `user` | `user` | A string becomes `{ role: "user", content }`; any other value is passed through as a message. | `asm:216-221`, `gen:3143-3166` |

- **De-duplication.** If `history` ends with a user message equal to the first `user` value, that first `user` value is dropped, so the model sees the turn once. Equal means same text, or the same multi-part content regardless of key order; a history line of text plus file or image parts also matches a `user` string equal to its text: the `user` value is dropped and the history line with the files is kept. A `user` slot that is a multi-part message with different content is not matched. Only the first `user` value is examined, and only when history is non-empty. A custom `history` slot that ends in a matching user message triggers it too. `asm:84-101`, `asm:229-282`; `tud:34-292`, esp. `:56-77`, `:273-290`; `tma:138-176`.
- **Per step.** `systemPrefixCount` is the number of leading `system` messages. When the prompt, any context entry (including a function nested inside an object) or `tools` is a function, then before each step after the first the system prefix is rebuilt from the current state and tool list; history, the user message and the step's accumulated tool calls and results are kept. A generator with only static slots resolves them once. `gen:3166-3265`, `agg:357-end` (`objectFormHasNestedFunction`); `tps:85-186`. **[read]** + **[test]**
- Message assembly re-runs on resume from a stored copy of the step-0 messages (G-10), not from fresh slot values. `gen:1651-1705`; `tgr:359-372`.

## Table G-4: `history` and `user`

- `history: true` is `ctx.session.items.history()`. `history: { limit: 8 }` (any `ItemQuery`) is `ctx.session.items.history(query)`. An object is read as an `ItemQuery` unless it has a `content` or `role` key, in which case it is a static message. A function or array is a slot and is used as given. `gen:780-800`.
- `ItemQuery` fields: `limit`, `includeTransient`, `itemTypes`, `roles`, `itemVisibility`, `agentName`, `includeInFlight`, `afterRequestId`, `earlierDocuments`. `scp:72-110`.
  - `limit` is `number | { turns: number } | { tokens: number }`. In `history()` a bare number counts conversational turns; in `all()` and `client()` it counts items. `{ turns: N }` is the explicit form. `{ tokens: N }` packs whole turns from the end until the next would not fit and always includes the most recent prior turn even if it alone is over budget. `scp:50-70`; `p-ctx:289-313`.
  - `includeInFlight` defaults to `true`: items the current request has produced so far come after the prior turns. `false` leaves them out. `scp:82-90`; `p-ctx:289-306`.
  - `afterRequestId` (history only): start after that turn, applied before `limit`. `scp:91-102`.
  - `earlierDocuments` (history only): how an earlier turn's documents ride. `"window"` (default) re-sends the newest, up to one message's limits, and names older ones; `"named"` sends none, each becomes one line with its name and id, which a model with the attachments capability's `readAttachment` reads on request. The request's own files and every image are unaffected. `scp:103-107`; `core/src/helpers/attachments-capability.ts:15`, `:180`.
  - `includeTransient`: default off, transient items are left out (`eng/context/history.ts:572`, `:586`). `itemTypes`: filter by item type. `roles`: filter by message `role`. `itemVisibility`: exact match against resolved visibility. `agentName`: scalar or array filter by producing agent. `scp:62-72`.
- **What a session loads.** `defineFlow({ session: { historyWindow: { turns } } })`, default **50**, caps how many prior turns a request loads; a per-call `limit` can only narrow it. `eng/context/createExecutionContext.ts:775`, `:851`, `:3304`; `flw:390`; `p-ctx:273-287`.
- **Which items enter history.** Only items of type `message`, `reasoning`, `tool_output`, and `data` whose emitter set `itemVisibility.history: true`; and only when the item's visibility has `history: true`. Trace types never. `crv:22-55`; `eng/context/history.ts:44-52`, `:91-94`. **[read]**
- **Summaries past the window.** `utility.historySummary({ summarize, name? })` returns `{ capability, fold, resource }`; the capability narrows the generator's history to start after the summary (`history: false` on the capability's preset turns that off). Details live on the existing page; the row links to it. `p-ctx:323-400`.
- `user` is resolved once per run, before the loop. The slot may be a function of `(input, ctx)`, a static value, or an array of those; array returns flatten. A `PromptFile` with a `<user>` block fills it unless the config sets `user` explicitly. `gen:824-837`, `gen:3143-3160`; `tpf:110-143`.
- Relation to `userMessage` on an action: `userMessage` writes the durable user `message` item; `user` resolves the message the model reads this turn. Wiring both to the same text is safe because of the de-duplication above. `p-ctx:190-210`; `tud:34-55`.

## Table G-5: Tool-loop limits (lookup: What ends a tool loop?)

One step is one model call. The loop runs steps; each step may ask for framework tool calls, which run before the next step starts. Facts below are for a model that supports single-step calls (the AI SDK adapter, the normal case). A model without `generateStep` / `streamStep` runs the older SDK-driven loop with `maxSteps` passed through (`gen:3326-3335`, `gen:3387-3433`); the page does not cover it.

| Condition | What happens | Cite |
| --- | --- | --- |
| A step returns no framework tool calls and its `finishReason` is not `"tool-calls"` | The loop ends. A text answer is the text of every step, joined with a blank line; a structured answer comes from the final step alone (see Text across steps below). | `gen:2123-2140`; `tol:62-96` |
| The step cap is reached | The loop stops after `maxSteps` model calls: `loop.maxIterations ?? maxIterations ?? 8`, minimum 1. See "At the cap" below. | `gen:108`, `gen:1223-1226`, `gen:2075`; `tg:448-472` |
| `loop.runTools: false` | The model may name a tool but nothing runs. The loop ends on the first step that returns a tool call (the calls come back on the result), without feeding results to the model. | `gen:2123-2140`, `gen:3249`; `tg:571-613`; `tol:405-440` |
| A tool calls `ctx.suspend()` | The loop stops and the request suspends for approval; a resume continues from the recorded steps. Sibling calls in the same step finish first, and the first suspension in call order is the one surfaced. | `gen:1494-1593`; `tol:229-280`, `tol:328-404` |
| The request is aborted | The signal is checked at the start of every step. An abort-like model error on an aborted run surfaces as the root-cause message. | `gen:2076`, `gen:1287-1296` |
| A provider-executed call (search, code execution) in a step | Not run by the framework, and does not by itself keep the loop going. A step whose only calls are provider-executed ends the loop unless its `finishReason` is `"tool-calls"` (a deferred provider tool), in which case the loop continues. | `gen:1462-1491`, `gen:2109-2140`; `tol:473-560`, `tol:850-890` |

**At the cap.** What comes back depends on whether the run streams. `canStream` is true when the output is plain text (no `outputSchema`, or a bare `z.string()`), the model has `stream`/`streamStep`, and the generator either sets `itemVisibility` or has tools (`gen:3293-3296`).

- **Not streamed** (an object `outputSchema`, or text with neither `itemVisibility` nor tools, or a model that cannot stream): if no step wrote any text, the generator throws `Generator "<name>" did not produce output after N step(s)` (`gen:3557`; `tol:1710-1716`; **[ran]**). If an earlier step wrote text, that text is the answer and nothing throws (**[ran]**: step 0 `"first"` plus a tool call, step 1 a tool call, cap 2, returned `"first"`).
- **Streamed** (a text generator with tools, or with `itemVisibility`): the run does **not** throw. **[ran]** A step script that asked for a tool on every step, `itemVisibility` set, cap 3, ran three steps and returned the empty string `""`. Whatever text streamed before is the answer (`finalizeStreamedMessage` validates the accumulated text, `gen:2431-2500`).
- `loop.answerOnLastStep: true` (with `runTools` not false and a cap above 1): on the last step the model is offered none of the generator's framework tools, so it answers in text. Provider tools stay. Without it, the last step offers every tool, so a model still looking things up at the cap ends on a tool call with nothing said. `gen:402-412`, `gen:3249-3259`; `tol:1675-1717`.
- **Text across steps.** In text output, text from separate steps is joined with one blank line, however many tool-only steps sit between; a structured (object) answer comes from the final step alone. `gen:2103-2105`; `tol:1327-1353`, `:1518-1548`, `:1549-1563`.
- **Several calls in one step** run concurrently and all settle before the next step; the results go back in one assistant turn followed by one tool message per call, in call order. `gen:1494-1593`; `tol:98-150`.

## Table G-6: Tools a generator is given

- **Forms.** `tools: [a, b]` or `tools: (input, ctx) => [a, b]`, resolved on each run (and again before each later step when a function, see G-3). A tool is any block (`GeneratorTool = BlockDefinition<any, any>`): handler, sequencer, router, generator, evaluator. The model sees the block's `name`, `description` and `inputSchema`. `gen:422-425`, `gen:613`, `gen:936-960`; `tg:396-446`.
- **Resources.** Resources a tool declares are installed in the flow only for tools in a **static** `tools` array; tools returned by a function are not collected. `gen:3047` (`staticTools: Array.isArray(authoredTools) ? authoredTools : undefined`); `gen:2968-2970`. **[read]**
- **Names.** Two different blocks with the same `name` in one resolved tool list throw when the generator runs: `Generator "<name>" has two tools named "<tool>". Tool names must be unique within a generator.` The same block value twice is one tool. `gen:3098-3108`, `helpers/tool-name.ts:81-92`; `tol:650-702`. `.as({ name })` renames a copy (`p-blocks:158-198`).
- **Name the model sees.** Every character outside `[a-zA-Z0-9_-]` becomes `_` (`tf.memory/recall` is `tf_memory_recall`), applied for every provider; two names that sanitize alike get the smallest free numeric suffix (`foo_bar`, `foo_bar_2`). `tool_output` items record the real name and the alias. `helpers/tool-name.ts:1-69`; `tol:151-228`; `tg:674-727`, `:851-896`.
- **Capability tools (the page's label for the fence).** A generator that declares `tools:` at all, even `tools: []` or a function, drops every tool a capability would contribute through `tools`, unless the block names that tool itself. A generator that does not mention `tools` keeps them. A capability's `controlTools` are exempt: they reach the generator whatever `tools:` says, static or dynamic capability alike, and `controlTools` is valid only on generator blocks. A capability declares them for tools its own job needs (the doc comment's examples: a skills loader), as opposed to catalog tools it grants through `tools`; the page says "tools it needs for its own job, such as a skills loader". `core/src/capability/types.ts:98-122`. `gen:2971-3036`; `tfn:106-232`; `core/src/capability/merge.ts:279`, `:584-591`; `core/src/capability/types.ts:107-125`; `p-cfg:73`. Capabilities in this repo that contribute controls include the skills runtime and the task tools (`packages/orchestration/src/skills/library.ts:335`, `packages/orchestration/src/skills/task-tools-capability.ts:2324-2330`).
- **A tool that needs a flow config** (`flowConfigSchema`) the flow's bag does not satisfy throws before the model is offered the tool list. `gen:859-896`. **[read]**
- **Memoizing results.** `cacheable` on the tool block, G-1's shared fields; inert without a tool-cache store in scope. `p-cfg:33-45`; `T/tool-cache.test.ts`.
- **`mapModelOutput(mapper)`** on a tool block sets the string the model reads as the result, applied each time the result is built; the structured output still flows to items and the trace. A mapper that throws fails the run (it is not reported to the model as a failed call). `blk:1285-1306`; `gen:1598-1655`; `tol:1069-1105`; `tgr:151-200`.

## Table G-7: A failed tool call, retries, timeouts and observers

- **What the model is told.** A tool call that throws does not end the run. The loop continues, and the model's next step receives a tool result of type `error-text` whose value is the error's message and nothing else, e.g. `kaboom`, with no tool-name prefix. `gen:1618-1640`, `gen:1519-1540`. **[ran]**: a handler throwing `Error("kaboom")` came back as `{"type":"error-text","value":"kaboom"}`. (A different wording, `failedToolResultText`, is used when a stored `tool_output` is replayed as history on a later turn; `gen:1746`, `gen:1825`.)
- **Input that fails the tool's `inputSchema`.** The block runs with the model's arguments; a mismatch throws `Block "<name>" input validation failed at "<path>": <message>` and goes back to the model as the tool result. The tool's `execute` does not run. **[ran]** (`Block "lookup" input validation failed at "q": Expected string, received number`). `bb:152-175`, `bb:356`. There is no separate "retry on invalid calls": the model sees the message and may call again on its next step, which spends a step.
- **A call to a name that is not a tool** (or a tool the current step deactivated) is not run; the result is `Model called unknown tool "<name>"` and the loop continues. `gen:1519-1540`; `tol:612-649`, `tol:703-850`. **[ran]**-adjacent: `tol:612-649` is a test.
- **A tool that suspends** is not a failed call: it stops the loop (G-5). A `tool_output` recorded for it is a failed item with `error.code === "SUSPENSION"` until the answer arrives. `ct:399-413`; `gen:1494-1593`.
- **Tool retry.** `defineFlow({ tools: { defaults: { retry } } })`, or the generator's `flowTools.defaults.retry`: `{ maxAttempts = 1, baseDelayMs = 0, maxDelayMs = unbounded, retryableErrors }`; delay is `min(maxDelayMs, baseDelayMs * 2^(attempt - 1))`. `retryableErrors`, when non-empty, narrows retry to instances of those classes. It does **not** read a `FlowError`'s `retryable` flag (**[ran]**: a `FlowError` with `retryable: false` was run 3 times under `maxAttempts: 3`). `SuspensionError`, `SuspensionRejectedError` and `SuspensionTimeoutError` are never retried. `exec:403-454`; `tte:129-173`; `tsu:18-60`. The tool's input check is inside the retried call, so a bad-input call is checked once per attempt and `execute` never runs (**[ran]**: 3 checks, 0 runs). The generator's own `retry` option is a different thing (G-1).
- **Tool timeout.** `tools.defaults.timeoutMs` bounds each attempt (the timeout wraps one attempt, inside the retry loop). A timeout is a thrown `tool:<name> timed out after <n>ms`, handled like any failed call. **[ran]**: model saw `{"type":"error-text","value":"tool:slow timed out after 20ms"}`. `exec:80-81`, `exec:139`.
- **Observers.** `onToolStarted`, `onToolCompleted`, `onToolErrored` on `defineFlow({ tools })` (or `flowTools`): each is a function `(event, ctx) => void` or a block (`isBlockObserver`, run with the event). The event is `ToolLifecycleEvent`: `{ toolName, input, output?, error?, cached? }`. `onToolStarted` fires once per call, `onToolCompleted` after success with `output`, `onToolErrored` after a failed call with `error`. `onToolErrored` fires **once per failed call, after every retry attempt is used up**, not once per attempt, and **before** the failed `tool_output` item is finished. **[ran]**: `maxAttempts: 3`, a tool that always threw: 3 runs, 1 `onToolErrored`, 1 `onToolStarted`. `exec:128-142`, `exec:188-196`, `exec:375-401`; `flw:74-99`; `tg:728-792`; `tte:79-118`.
  - Served from the tool cache: `onToolStarted` and `onToolCompleted` still fire with `cached: true`; `onToolErrored` never does, since errors are never cached. `exec:300-345`; `flw:77-89`; `p-flow:212`.
- A tool with `cacheable` that is in flight twice with identical arguments runs once when a cache store is in scope; see the shared-fields table.

## Table G-8: Output schemas

- **Default.** No `outputSchema`: the output is `z.string()`, and the generator returns text (`gen:2865`; `tg:12-29`). For a text schema the request to the model carries no structured-output schema (`tg:30-54`, `tg:981-1013`); an object schema is sent as the structured-output schema (`tg:55-78`).
- **What counts as text.** A bare `z.string()` only. `z.string().nullable()`, `.optional()` or `.refine()` is a structured root, not text. `core/src/models/output-root.ts:15-40`; **[read]**. A `.min()` or similar check on a bare string stays text. **[ran]**
- **Strict-schema guard at definition.** A declared `outputSchema` is checked when `generator()` is called, and the call throws `StrictSchemaError` (`code: "strict_schema_error"`, `retryable: false`, `details.violations[]` with `path`, `typeName`, `reason`) if, after optional/default/nullable wrappers are stripped, it still contains a `z.record` anywhere, or a `z.union` / `z.discriminatedUnion` whose variants are not all literals. The message starts `Generator "<name>" output schema is not OpenAI strict-mode compatible:` and lists `path: type: reason` lines (paths like `$.metrics`, `$.items[]`, `$.result|0`). `z.string()` and enums and literals are always fine. `gen:2859-2863`, `core/src/models/makeSchemaStrict.ts:120-300`, `core/src/errors/strict-schema-error.ts:1-50`; `tso:11-60`; `core/test/models/make-schema-strict.test.ts`. The original schema, with its `.default()` and `.optional()`, is still what validates the reply.
- **Repair, in order, on a failed parse** (`gen:1073-1150`):
  1. The reply is validated against `outputSchema`. A pass returns the parsed value (`.default()` applied).
  2. `repair.mode: "fail"` or `"rescue"`: stop here and throw `OutputValidationError` at once. (`p-api:65` says `rescue` defers to a `.rescue()` handler; in this code `rescue` and `fail` behave the same inside the generator: both throw the validation error. A `.rescue()` on the block or sequencer is what catches a thrown error, in any mode.) `gen:1093-1096`; `tg:152-181`.
  3. Mode `auto`, up to `repair.maxAttempts` (default 1; `0` skips this step) deterministic passes: if `repairOutput` is set it is called, else the built-in pass: parse a string as JSON, else repair it with `jsonrepair` (trailing commas, unclosed braces, code fences) and parse, else leave it; unwrap `{ output: ... }`. Each pass is followed by a new validation. `gen:1048-1070`, `gen:1126-1131`; `trp:72-92`; `tg:127-150`.
  4. Still failing in `auto` and `repair.coerce` is not `false`: **one** model call asks a model to rewrite the reply to match the JSON Schema, keeping content, mapping renamed fields. The model is `repair.coerce.model` (any model value, resolved with the block's input) or, by default, `intent/utility`. The call asks for plain JSON text, passes the request's abort signal, and its usage is reported like the main call's. A failure of this call, other than an abort, is written with `console.warn` (`gen:1206`) and swallowed, and the original validation error is thrown. The result goes through the deterministic pass and one more validation. `gen:1152-1233`; `trp:45-70`, `trp:94-162`, `trp:213-end`.
  5. Otherwise the generator throws `OutputValidationError`, and writes the candidate (truncated to 2,000 characters) with `console.warn` (`gen:1042`). Both go to the server's console. `gen:1020-1046`; `tg:183-216`.
- **Repair applies to** a reply that is not streamed (an object schema, or text without streaming). A streamed text reply is validated once, without repair (`gen:2495-2500`). **[ran]**
- **`OutputValidationError`** (`core/src/errors/output-validation-error.ts:1-31`): `name "OutputValidationError"`, `code "output_validation_error"`, `retryable: false`, message `Generator "<name>" output validation failed at "<path>": <message>` (the first Zod issue; ` at "<path>"` only when the path is not empty). `details`: `rawOutput` (the string, or the candidate as pretty JSON), `issues` (all Zod issues), `phase`: `"final"` for a reply checked after generation, `"stream"` for a streamed text reply. **[ran]**: `z.string().min(50)` with a short reply gave `phase: "stream"` when it streamed and `phase: "final"` when it did not. `tg:218-256`; `gen:986-1012`, `gen:2495-2500`. On a failed block the same `details` appear on the block's trace `error.details` (`ct:325-335`).
- **A generator's output is recorded.** A streamed text reply's `block_trace.output` is a reference to the `message` item rather than a copy of the text, unless a transform changed the text. `gen:2519-2535`, `gen:3610-3616`; `T/generator-block-output-ref.test.ts:45-72`.

The same applies to a `block_trace` `input`/`output`. `eng/streaming/recorded-value.ts:8-21`, `eng/streaming/response-emitter.ts:76`, `:256`; `ct:107-151`. **[read]**
- **Context ends up in storage.** Everything the model was sent, including `context` contents, is in the `block_trace.generator` capture and, on a run with tool calls, in the step-0 `generator_step.prelude`. Keep secrets out of `context`.  (A direct consequence of `gen:3300-3326` and `gen:1651-1705`; the page may state it as the guarantee "what you put in `context` is recorded".)
- Visibility rules: `message`, `reasoning`, `tool_output` use their `itemVisibility`, defaulting to `{ client: true, history: true }`; trace types are never client-visible or in history; `source` and `tool_call_progress` (and any other structural type) resolve to `{ client: true, history: false }` whatever is stamped; `data` also reads the stamp. `crv:22-55`. History only reads `message`, `reasoning`, `tool_output` (and `data` that opted in). `eng/context/history.ts:44-52`.
- Model identity (`{ actual, requested?, gateway? }`) is stamped on a generator's `message`, `reasoning`, `source`, `tool_output` and `tool_call_progress`, and on the trace row. `tg:1342-1468`; `ct:226-236`.

## Where an existing page or sheet says something the code does not

The page states the code. Fix or leave out, in this order of importance.

1. **At the step cap a streamed text generator does not throw.** The C-03 sheet's row 3 and `p-cfg` say or imply `did not produce output after N step(s)` at the cap. That is true only when the run is not streamed and no step wrote text. Streamed, it returns what was written, possibly `""`. **[ran]** G-5. The page must not say "the run throws at the cap" without the condition.
2. **The error text a model gets for a failed tool is the bare message.** The C-03 sheet wrote `Tool "<name>" failed: <message>`. That wording is only used when stored history is replayed on a later turn. In the loop it is the message alone. **[ran]** G-7.
3. **`retry` on a generator re-runs the whole block**, not "the model call" (`p-cfg:88`). G-1.
4. **`maxIterations` has a default (8)** and is not only a "legacy" spelling; `loop.maxIterations` wins when both are set. `repair.mode` and `repair.maxAttempts` have defaults (`"auto"`, `1`). G-1.
5. **`repair.mode: "rescue"`** (`p-api:65`, `p-blocks:339`): inside the generator it throws exactly as `"fail"` does. Whether a `.rescue()` catches it is the sequencer's behaviour, not the generator's. G-8 step 2.
6. **Streamed vs not.** `p-blocks:39` lists "streaming" as something the framework handles; it applies to text output with `itemVisibility` or tools only. G-5, G-1 (`itemVisibility` row).
7. **Capability `context` and the C-03 phrase "a bare string or function in `context` is added to the instructions".** A bare string or function result is a separate `system` message after the one that holds the prompt, not part of it, and it is not escaped. A named section is inside the prompt message and is escaped. G-2, G-3. (The C-03 page text at `concepts/generators-and-tools.md:158` should be checked against this on its own pass.)
