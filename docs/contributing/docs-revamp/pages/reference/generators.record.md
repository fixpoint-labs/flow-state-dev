## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. `supportAgent` is a text generator (no `outputSchema`) with `tools: [lookUpOrder, issueRefund]` and `itemVisibility` set. On a hard ticket the model keeps calling `lookUpOrder` on every step. What ends the loop, after how many model calls, what comes back, and how do you make sure it ends with a written answer instead of a tool call? *(edge case)*
   Answer: The loop ends on its own when a step returns no framework tool calls and its `finishReason` is not "tool-calls" (G-5, gen:2123-2140). Otherwise it stops at the step cap: `loop.maxIterations ?? maxIterations ?? 8` model calls, minimum 1 (gen:108, gen:1223-1226). Because this run streams (plain text, with tools and `itemVisibility`), it does not throw at the cap. It returns whatever text streamed so far, which can be the empty string "" (G-5 'At the cap', [ran]). Set `loop: { answerOnLastStep: true }` (with `runTools` not false and a cap above 1). Then the last step offers none of the generator's framework tools, so the model answers in text. Provider tools stay offered (gen:3249-3259; tol:1675-1717).
2. `supportAgent` has a `prompt`, `context: ["Answer in under 100 words.", { customerPlan: "pro" }]`, a `description` on `lookUpOrder`, `history: true` and a `user` slot. In what order does the model receive these, and which of them sit in the same message?
   Answer: From G-3 (asm:70-102, gen:3088-3166, [ran]): (1) one `system` message holding the prompt text, a blank line, then the XML built from every object-form entry, here `<customer-plan>` with the key normalized to kebab-case; (2) the bare string "Answer in under 100 words." as its own separate `system` message, unescaped, in author order; (3) the `<tools>` list, last of the system messages, with one `- name: description` line for each tool that has a description; (4) the session's history turns, including the in-flight request's own items by default; (5) the `user` message. If history ends with a user message equal to the first `user` value, that `user` value is dropped so the turn is seen once.
3. Mid-loop, `issueRefund` throws `Error("payment service down")`. The flow sets `defineFlow({ tools: { defaults: { retry: { maxAttempts: 3 } }, onToolErrored } })`. Does the run end? How many times does the tool run, how many times does `onToolErrored` fire, and what does the model see? *(edge case)*
   Answer: The run does not end. Retry is per tool call: the tool runs up to 3 times. The default `retryableErrors` is empty, so any error retries, and a `FlowError`'s `retryable` flag is not read (G-7, exec:403-454, [ran]). `onToolErrored` fires once for the failed call, after every attempt is used up and before the failed `tool_output` item is finished. `onToolStarted` fires once ([ran]: 3 runs, 1 onToolErrored, 1 onToolStarted). The model's next step gets a tool result `{ type: "error-text", value: "payment service down" }`, the bare message with no tool-name prefix. It may call again or answer, and each new call spends a step (gen:1618-1640, [ran]). Exceptions: a tool that calls `ctx.suspend()` stops the loop instead, and a throwing `mapModelOutput` fails the run.
4. You change `supportAgent` to return `outputSchema: z.object({ reply: z.string(), refundAmount: z.number() })`. One day the model replies with that JSON inside a code fence and with a trailing comma. What does the generator do, step by step, and what happens if nothing fixes it? Would a `retry` on the generator help? *(edge case)*
   Answer: From G-8 (gen:1073-1150): the reply is validated and fails. In the default `repair.mode: "auto"` with `maxAttempts: 1`, one deterministic pass runs: parse as JSON, else fix it with `jsonrepair` (code fences, trailing commas, unclosed braces) and parse, unwrap `{ output: ... }`, then validate again. That likely fixes this reply. If it still fails and `repair.coerce` is not false, one model call (default `intent/utility`) rewrites the reply to the JSON Schema, then it is passed and validated once more. If that fails, the generator throws `OutputValidationError` (`code: "output_validation_error"`, `details.rawOutput`, `issues`, `phase: "final"`) and logs the candidate. It has `retryable: false`, so the generator's `retry` does not re-run it. With `repair.mode: "fail"` or `"rescue"` it throws at the first failed validation. Separately, a schema containing `z.record` or a non-literal union throws `StrictSchemaError` when `generator()` is called.
5. A capability in `supportAgent`'s `uses` contributes a `searchKnowledgeBase` tool, and the model has been using it. A teammate edits the generator to add `tools: [lookUpOrder]`. Afterwards the model never calls `searchKnowledgeBase`. Why, and how do you get it back? *(edge case)*
   Answer: Declaring `tools:` at all, even `tools: []` or a function, fences out every tool a capability contributes through `tools`, unless the generator names that tool itself. A generator that does not mention `tools` keeps them (G-6 'The fence', gen:2971-3036, tfn:106-232). Fix: list it, `tools: [lookUpOrder, searchKnowledgeBase]`, or drop the `tools` key. A capability's `controlTools` are exempt and reach the generator whatever `tools:` says. Also, two different blocks with the same `name` in one tool list throw when the generator runs. `.as({ name })` renames a copy.
6. `supportAgent` runs with `itemVisibility: { client: true, history: false }`, calls `lookUpOrder` once and then writes its reply. Its `context` carries the customer's account notes. What is recorded for that run, who can see each part, and does the next turn's `history: true` read the reply back? *(edge case)*
   Answer: Everything is stored on the request that ran it; the generator holds no data of its own (G-10). Recorded: one assistant `message` item, which the client sees and later history does not (history: false); one `tool_output` for the lookUpOrder call, with toolCall {callId, name, arguments, ...}, output and status; `tool_call_progress` items, which are transient and never persisted; one `generator_step` per step that called tools, which nobody sees in a UI, and whose step 0 carries `prelude`, the full assembled message list; one `block_trace` with the prompt, user, history, model, `modelUsage` and output, for developers in the DevTool; and spend, reported to the request's ledger per step. So the account notes in `context` are recorded in the trace capture and in the step-0 prelude: keep secrets out of `context`. Next turn, `history: true` does not include the reply, because history only reads items whose visibility has `history: true`. It loads at most `session.historyWindow.turns` (default 50) prior turns. Values over 256 KiB are stored as an `outputOmitted` placeholder.

Untrue: Two attempts per model happen only for non-streamed calls and only for retryable errors; a non-retryable or provider-load error skips to the next model at once.
