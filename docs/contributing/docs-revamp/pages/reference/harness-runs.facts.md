### 1a. What the kit contributes

- The kit requires `workforce` and has one slot, `harnesses`, a keyed slot of harness values (`hk:119-121`). An app fills it with `fill: { [harnesses.slots.harnesses]: [codexHarness(), cursorHarness()] }` (`hk:111-116`); Claude Code fills it itself through `claudeCode()` (`cck:76-81`).
- To workforce's `workerFlows` slot it adds `coder`, the one coding worker flow. To `uses` it adds the harness-readiness capability, which puts the readiness rows in a coordinator's context (`hk:126-127`, `rd:275-300`). To `flows` it adds one flow, `harnesses`, with two views, `readiness` and `codingBoard` (`hk:130-139`).
- **[test]** `hkt:78-91`: with codex ready and cursor not, the app's flows are `agent`, `coder`, `harnesses`, `workforce-roster`, and the readiness view returns `[codex, CODEX, true]` and `[cursor, CURSOR, false]`.
- `harnesses(...).without(workforce.slots.workerFlows, "coder")` switches the flow off; an app with a coding worker that names it then fails at start, naming the harness and the flow **[test]** `hkt:93-104`, `cf:7-9`.
- A worker file that names a harness nobody filled stops the app starting, naming the harness **[test]** `hkt:106-119`. **[ran]** the same refusal for the plan harness: a `WORKER.md` with `flow: coder` and `harness: claude-code-plan`, with `claudeCode({})` (no `plan`), fails start with `hireWorkforce: 1 standard worker problem(s); nothing was registered:` then `worker "core.planner" — Flow "coder" instance "core.planner" has an invalid config bag: "harness": Invalid enum value. Expected 'claude-code', received 'claude-code-plan'.` **[test]** `packages/claude-code/test/sdk/kit.spec.ts:60-74`.
- The `coder` flow takes two lines in a worker's `WORKER.md` beyond workforce's own: `harness:` (one of the filled ids, else refused as above) and `review:` (boolean). `harness` is shown in the roster as a worker setting. `cf:287-290`, `cf:337` (`roles: ["contributor"]`, `showSettings: ["harness"]`).
- The coder flow answers a task through one manager per harness, plus one that waits for review, routed by the session's worker (`cf:221-264`).
- A line typed in a task's session is handled by the session door; a message delivered by another worker is handled by a talk turn (`cf:247-248`, `cf:310-318`, `sd:1-24`).
- `harnesses` flow views: `readiness` and `codingBoard` (`hk:135-136`). `codingBoard` answers the conversation's coding tasks with a state of `queued`, `held`, `running`, `waiting`, `failed`, `done` or `cancelled`, the harness, review result, where work landed, the error and the numbers of pull requests the task waits on (`cbv:53-80`).
- The `coder` flow serves one view, `recordedWork`, in a run's own session (`cf:293`, `rw:1-17`).

Behaviour of the options (all **[doc]** `wsr:236-345` unless a line says otherwise):

- A repository the host clones: one clone per remote under `<root>/.clones/<clone key>.git` (clone key: slug of the remote's host and path, non-alphanumerics `-`, at most 80 characters, then `-` and 12 hex digits of a hash; `remotes.ts:205-210`, `local-host.ts:986`), shared by every run, and each run's own branch in `<place>/checkout/`. Three spellings of one GitHub repository share one clone (`wsr:259-264`).
- A repository listed in `localRepositories`: the run's branch is cut from `baseRef` (or `HEAD`) and stays in that repository. When the source names no kept files the place directory is the checkout itself; with kept files the worktree is `checkout/` and the files are in `project/` (`wsr:291`, `lh:204-212`).
- A bare local path not listed is refused `invalid-remote`, before git runs (`wsr:291`, `rem:185-188`). A repository left out of `localRepositories` is cloned by the host only when it is a remote that `remotes.allow` admits.
- What a run in a listed repository may do to it: its working tree, index and branches are not touched, but git shares branches, tags and remote-tracking refs between worktrees, so the run can create or move refs there. To keep a run apart from a repository's refs, the host clones instead of listing it (`lh:225-228`, `wsr:307`).
- The run's branch cannot be one already checked out in another worktree, including the user's own checkout of a listed repository (`checkout-moved`, `wsr:323`; refusal reasons `refused.ts:12-18`).
- Before cutting a new branch whose base tracks an upstream, the host fetches that one upstream branch and cuts from the newer of the two; local and upstream both moved is refused `base-diverged`; a failed fetch starts from the local base with a warning (`lh:212-223`, `wsr:293-303`).
- Every repository must ignore the question-marker directory, `**/.fsdev/`. A checkout whose repository tracks files there or does not ignore it is refused before the agent runs, with `Add \`**/.fsdev/\` to that repository's .gitignore`. The manager passes this on every provision (`mg:2505`, `wsm:841-850`, `hm-ask:90`). **[test]** `packages/harness-manager/test/workspace.spec.ts:1253`, `:1269`.
- The host runs none of the repository's git hooks while it makes or hands back a checkout (`wsr:272`, `lh:687-689`).
- Where a refused run's failure goes: a source or host refusal ends the task and is not retried. On a task a conversation filed (the kit's boards) the task ends `errored`; on a fixed board it is cancelled (`mg:1305-1311`, `mg:1470-1477`).

### 2a. The branch and the folder

- A run's name is a slug of the task's title (at most 32 characters) plus 6 hex digits of what keeps one run apart from another (principal, board, issue, phase; the page says user or organization, board, issue, phase). The branch is `<branchPrefix><name>` and the folder is `<root>/<name>`; a new run takes the first spelling that no other run holds and no worktree or branch already has (`-2`, `-3`, ...). A run whose record names a branch is found from that branch (`wsm:36-54`, `wsm:808-827`, `wsm:526-552`).
- Two users, or two organizations, never share a folder or branch for the same issue-phase (`wsm:343`; **[test]** `packages/harness-manager/test/workspace.spec.ts:956-1010`).
- A task in the kit has one run identity: its task id as the issue, and the phase `code` (`cf:218`, `cf:141`).

## 3. What happens to the checkout after a run

- Nothing removes it. The manager releases its lease and leaves the checkout, branch and commits on disk, so a retry, an answered question, a typed line or a change request picks up in the same place. No call in the manager, workspace or checkout modules removes a checkout (grep of `mg`, `wsm`, `checkout.ts` for `remove`/`rm`: none) **[source]**. `wsr:329`: "A host's checkouts stay on disk after `release`, so a retry finds them." **[doc]**
- `release` lets the place go: "The directory is kept; the live link to its kept files is dropped" (`lh:507-514`; the manager calls it after saving kept files, `mg:2387`). The one checkout the host removes by itself is one it made in a provision it then refused, such as a repository that does not ignore `**/.fsdev/`: "one this call made is removed again" (`lh:293-302`).
- The lease is the worktree's in-use lock `<cwd>.lock`; the host's `remove` refuses while a run holds it (`wsm:829-833`, `wsr:349`).
- Remove one by hand with `fsdev worktrees <root> --remove <dir>`; add `--delete-branch` to drop the branch too, `--force` with it to drop a branch holding the only copy of some commits. List with `fsdev worktrees <root>` (`--json`, `--repo <path...>`). Source `packages/fsdev/src/commands/worktrees.ts:95`, `:106-110`; **[doc]** `apps/docs/docs/api/cli.md:293-314`.
- The host's `remove` refuses (`WorkspaceRefusedError`) with: `uncommitted-work` (uncommitted or untracked changes), `place-busy` (a provision of the place is running), `in-use` (a run is working in it), `unique-commits` (with `deleteBranch`, the branch holds commits no other branch or remote holds; or a detached HEAD holds commits nothing else holds; `force: true` removes it anyway). A refusal removes nothing; kept files and held work stay where they are. The CLI prints `Refused (<reason>): <message>` and exits 1 (`wsr:345-353`).
- The user's list of worktrees: collection `worktrees/**`, user scope, readable by the user's sessions and by a model (`llmReadable`), readable by clients, written only by the host. One row per worktree: name, path, branch, repository, base commit, owner (`session` or `run`), attached sessions, `state`, pull requests. State is one of `provisioning`, `ready`, `removed`, `lost`. A removed worktree's row stays, marked `removed`. Rows are never deleted (`wtr:1-26`, `wtr:30-35`, `wtr:136-147`; **[doc]** `apps/docs/docs/workforce/projects.md:973`). Whether the kit's coder flow writes a row per run is not shown by a test; the manager writes one when its workspace host is handed the collection (`hmr:287`). Keep this row about the collection, not about the kit.
- On a host with a held-work store, the run's commits and uncommitted changes are saved at the end of each turn and a retry on another machine gets them back, in a fresh conversation with a note that the checkout was rebuilt. Without a store the checkout lives only on the machine that made it, and a retry elsewhere starts from the base branch (`hmr:823`, `packages/harness-manager/src/held.ts:117-125`, `rr:101-122`).
- A new checkout has no installed dependencies unless the host's `setup` command ran (`lh:247-259`).
- A checkout whose creation was interrupted is rebuilt only when the tree shows files missing and nothing else changed; any other change is refused and kept (`wsr:270`, `packages/harness-manager/test/workspace.spec.ts:461-700`).

### 3a. The checkout is not a fence

- The framework prepares the checkout and hands its path to the agent as `cwd`. It does not confine what the agent runs. Each harness's sandbox option sets that (section 11). The run deadline bounds the harness step, not what the run started: "A command the agent's process started can outlive the kill" (`hmr:721-725`, `cxa:106-111`).
- No agent is put in a sandbox by the Claude Code kit harness: the kit passes no `sandbox` option, and an unset `sandbox` hands the SDK no sandbox (`cck:48-58`, `cca:394-400`).

## 4. Run states

Three layers carry state; the figure draws the first.

**Task status** (orchestration): `pending`, `in_progress`, `held`, `completed`, `errored`, `cancelled`. Allowed moves: `pending → in_progress | held | cancelled`; `in_progress → completed | errored | pending | cancelled`; `held → pending | cancelled`; the last three are terminal. `held` sits before any start (`packages/orchestration/src/tasks/schema/task-status.ts:13-61`).

**What a user sees** (`taskView`, and the kit's `codingBoard` rows): stored status maps to `queued` (`pending`), `held`, `running` (`in_progress`), `done` (`completed`), `failed` (`errored`), `cancelled`; `waiting` overrides `running` for a non-terminal task with an open hold for the user (`packages/orchestration/src/inbox/task-view.ts:17-28`, `:84-92`).

**Holds on an `in_progress` task** (the run's waits, each with `ask.kind`):

| Wait | `ask.kind` | Shown as | Ends when |
| --- | --- | --- | --- |
| A question (the judge's *ask*, saved work that does not match the record, a question the run wrote) | `question` | `waiting`, in the Inbox and in the task's open `questions` | Answered, or the task is cancelled |
| A review of the run's commits (`review` on) | `review`, title "Review the run's changes" ("The accepted changes didn't land" on a re-ask after a failed landing; `mg:4142`) | `waiting` | Accepted, changes asked for, host deadline, or cancel |
| A tool approval, title `Allow <tool>?` (`approveTools`, not set by the kit) | `approval` | `waiting` | Allowed, denied, or cancel |
| Waiting on the run's pull requests | external (system-owned, `source.closedBy` one per pull request, event `pull-request`) | `running`: an external wait is never a user's to answer | A pull request merges, all close, or a message wakes it to check |

Sources: `mg:3312-3320`, `mg:4141-4152`, `td:186-195`, `pull-request-wait.ts:22`, `packages/orchestration/src/inbox/holds.ts:63-79`.

While any of these waits, the task keeps its attempt and its claim, has no lease, and nothing settles it or starts another run (`mg:3313-3320`; **[test]** `packages/harness-manager/test/claim-board-question.spec.ts:30-55`: status `in_progress`, `attempts: 1`, no `leaseUntil`).

**Attempts** (board rules): a failed attempt re-pends the task with the failure as `feedback` only while `attempts < maxAttempts`; a task with no `maxAttempts` has one attempt, so `fail` ends it `errored` (`packages/orchestration/src/tasks/schema/task-init.ts:41-47`, `task.ts:50-55`). A task whose result goes to the conversation has one attempt and refuses any other `maxAttempts` (`task-init.ts:86-89`). An answered question, a steer and a review's change request each take another turn on the same attempt and spend none (section 7).

**The run record's own `outcome`** is `running`, `succeeded` or `failed` (`rr:90`, `rr:288`). It stays `running` while the task waits on a question: "the board row is the authority on the job's state" (`mg:3171` comment). A refused or superseded attempt writes nothing (`mg:1313-1331`).

**Place state** on the run record, only where the workspace host holds a run's work: `provisioning`, `ready`, `refused`, `lost`, `restoring` (`rr:96`, `rr:262-285`).

Figure facts for pass 3 (nodes the page may draw, all verified above): queued → running; running → done; running → failed (attempt fails and `maxAttempts` spent) or back to queued (retry with feedback); running → waiting on a question | review | approval; waiting → running (answered, same attempt); running → waiting on pull request(s) → done (merged) or cancelled (closed unmerged); any open state → cancelled. A task that never starts because its harness is not ready or its workspace refused goes straight to failed.

## 5. The verdict contract: what marks a run's task complete

Order, for a task run through the kit's `coder` flow. A step that fails fails the attempt; the reason becomes the next attempt's brief (`feedback`, `cbf:108`).

1. **The harness step ended, within its stops.** The manager reads success from the handle's `status` alone: `completed` is success (`mg:3223`). A run the harness stops by itself (limit, error) comes back `errored`, a thrown error is an exception; either way the attempt fails with `the run stopped without finishing: <outcome or "no result reported"> — <final message>` (`mg:3458-3473`). A silence stop (`idleTimeoutMs`) or the cap (`runTimeoutMs`) aborts the step (`rs:99-105`, section 1).
2. **A question marker, if the run wrote one.** If the step succeeded and the run's marker file exists and is non-blank, the task is held on that question and nothing below runs (`mg:3308-3320`, `hm-ask:156-171`). A failed step with a marker is a failed attempt, never a held task (`mg:3161-3175` comment, `mg:3458`).
3. **The phase says done.** The kit's phase is done when `stopReport === "finished"`, the handle's `outcome` exactly as the harness reported it (`cf:151`; `null` is "no terminal result", never read as finished; `mg:3381-3392`). An unfinished outcome fails the attempt with `<ended> and the code phase is still not done`: `the run stopped at its limit` (`stopped-at-limit`), `the run finished cleanly` (`finished` the phase still refuses), or `the run terminated normally reporting <outcome>` (`no terminal result` for `null`); a reason is appended after a colon when the phase gives one (`mg:3490-3500`). This step is bounded to a minute, or to the checks' time plus a minute (`mg:3339`, `ccm` `doneTimeoutMs`).
4. **Checks, if configured and the run changed files.** The kit's checks (or the project's, with `project`) run in the checkout after step 3 says done. They are skipped when the run changed nothing: no uncommitted files and the checkout's tree equals the commit its branch was cut at; trees are compared, so a run that committed and moved its branch back counts as unchanged only when the trees match; no recorded base, or a git error, counts as changed and the checks run (`cf:120-138`, `cf:166-168`). **[test]** `packages/harness-manager/test/coding-phase-changed-files.spec.ts:73-86`: skipped on a run that changed nothing, run on one that moved its branch back and on one with no recorded base. A red command makes the attempt not done: non-zero exit, timeout, skipped (time ran out), or could not run. The next brief names each red command, why, and the end of its output (`ccm:116-135`; **[test]** `coding-phase.spec.ts:43-65`). Every result is kept on the run record whatever the verdict (`rr:339`, `mg:3411-3414`). The brief names the same commands before the run, from the same list (`cf:168` `inBrief: true`; `coding-phase.spec.ts:66-75`).
5. **Files and held work are saved.** A run whose kept files or held work could not be saved is not completed even when done: the attempt fails and the retry becomes the next save point (`mg:3417-3433`).
6. **The judge, when on and the task has a goal.** `goalJudge` reads the goal, the run's answer (cut at 8 000 characters), the commit count and subjects, and the files the commits changed, then answers *done*, *not done* or *ask* with a confidence. Floor 0.7. *Done* closes the task whatever the confidence. *Not done* or *ask* at or over the floor acts; under the floor the run counts as done. *Not done* fails the attempt and the reason is the next attempt's brief (`The judge read the answer against the goal: <reason>`); *ask* holds the task on a question that names the goal and quotes the start of the answer (500 characters). A judge that throws, times out or answers off-shape gives no verdict: the task settles on the checks alone and its output says `judged: false`. The judge runs only for a task that has a non-blank goal on a claim-read board, which is every task the kit runs (`mg:3438-3441`, `mg:3738-3772`, `mg:3963-3977`; `gj:32-35`, `gj:45-110`; `mg:978`). Model default `typesafe-ai/jev` (`gj:32`, `GOAL_JUDGE_MODEL`; also in `packages/harness-manager/README.md:196`), verified in this pass. **[test]** `judge.spec.ts:44-64`, `:101-137`, `:138-163`, `:165-185`; `goal-judge.spec.ts:86-109`. The judge needs a model through the flow's model resolver (`gj:17-18`).
7. **The review, when on.** A run that passed steps 1 to 6 (including one the judge said done, found nothing about, or read under the floor) with commits over its base waits for a review; a verified zero commits skips it; if git could not count the commits the review is asked anyway and says so. A confident *not done* or *ask* from the judge skips it (`mg:4036-4048`). Review answers: section 8.
8. **Pull requests, with `pullRequests` on (default).** A run that opened a pull request settles on it: each is read from GitHub; with any open the task holds (external wait); with none open and at least one merged it completes; with all closed unmerged it is cancelled with `its pull request was closed without merging`; unreadable holds with a status note (`apr:153-156`, `apr:29`, `mg:3963-3985`, `mg:3849-3865`). A confident *not done* from the judge on a run that opened a pull request does not fail the attempt: the task waits on the pull request, the judge's reading shown as a status note (`mg:3963-3972`). A wait is woken by a message in the task's thread, which checks the pull requests (`apr:162`).
9. **Settle.** A task with no pull request completes and the run record's `outcome` becomes `succeeded` (`mg:3982-3986`).

What the completed task's output carries (`mg:1003-1070`): `issue`, `phase`, `sessionId`, `answer` (the run's last message, cut at 8 000 characters, `null` when none), `branch` (`null` for a run with only kept files), `commits` (over the base the branch was cut at) with `commitsVerified`, `baseCommit`, `path`, `judged`, `review` (`accepted`, `deadline` or `null`), `landed` and `pullRequests`.

Statements the page must not make:

- That a run which spent its turns or budget "commits what it got through". No code does that; the kit's brief asks the agent to commit what it changes (`cf:147-149`).
- That `stopped-at-limit` reaches the completion check under Claude Code: its handle returns `status: "errored"` for the SDK's turn and budget limits, so the attempt fails at step 1 with `the run stopped without finishing: stopped-at-limit` (`cca:1613`, `cca:680-682`, `cct:36-60`). Codex and Cursor never produce `stopped-at-limit` (`cxt:71`, `cut:76`). Either way a run that stops at a limit is not done.
- That a green check proves the agent left the scripts alone: the commands run the checkout's own scripts, which the agent can edit (`ccm:15-17`).

### 5a. What the brief tells the run

`codingBrief` builds every run's prompt: the task title, goal and context; what the task's dependencies produced and what earlier tasks on the board found (each cut at 4 000 characters of JSON); the worker's instructions; conventions (default: read the repository's `AGENTS.md` or `CLAUDE.md`); `Task <id>, phase code, attempt <n>`, the directory and branch; the kit's term "Work in this directory only. If the task asks a question, read what you need, answer it in full, and change nothing. If it asks for a change, commit what you change with git."; answers to earlier questions; a report request; why the last attempt stopped (`cbf:74-109`, `cbf:52`, `cf:141-152`). The report asks for three headings, `What changed`, `Checks` (each line led by `passed:`, `failed:`, `pre-existing:` or `not done:`), `Worth knowing` (`rpt:17-39`). The brief does **not** name the question-marker path, so under the kit an agent is not told where to write a question (`cbf:74-109` has no marker; the field exists on the hand-written phase's context, `mg:303`, `mg:3002`).

## 6. The question channel

- **Who can put a question to the user:** the judge (an *ask* verdict, section 5 step 6); held work that does not match the run's record (the place goes `lost`, the task is held on a question that says what could not be brought back, and answering starts the run again from its base) (`mg:2545-2575`, `packages/harness-manager/src/held.ts:104-111`); and the run itself, by writing a non-blank file at its marker path, `<checkout>/.fsdev/ask/<attempt>-<run>.md` (`hm-ask:77-95`, `hm-ask:156-171`). The kit's brief does not tell the agent the path (section 5a), so the kit does not make an agent ask by default; a hand-written phase gets the path as `run.askMarkerPath` (`mg:303`).
- **Why a path with attempt and run:** a retry reuses the checkout, so a fixed path would read an earlier run's question. The attempt number is the board's, the run number is a count on the run record that is never reset (`hm-ask:22-40`, `rr:160-170`). A blank marker is not a question; an unreadable one fails the attempt (`hm-ask:143-171`).
- **What the task's state is while waiting:** `in_progress` on the same attempt, a hold with `ask.kind: "question"`, no lease, no deadline unless the host sets one; the checkout is let go; the run's work is saved first (`mg:3312-3320`, `mg:2537-2541`; **[test]** `claim-board-question.spec.ts:30-55`; **[doc]** `hm:112`).
- **Where it shows:** the user's Inbox, the task's open `questions` from `getTask`, and the kit's `codingBoard` rows as `waiting` with `asks` (`cbv:56-80`; **[doc]** `hm:112`).
- **How to answer:** (a) the Inbox; (b) `updateTask` with `answers: <hold id>` and `message`; (c) a line typed in the run's own session, which answers the oldest open question or external wait and never a confirm (`packages/orchestration/src/tasks/steers.ts:152-206`, `sd:1-24`). A line that arrives when no question is open is a steer (section 7). Only the run's own user can send one; anyone else is refused before the line is written (**[doc]** `hm:434`).
- **What an answer does:** the task takes one more turn on the same attempt; that turn resumes the same coding session in the same checkout, with the question and its answer in the brief under `Answers to your questions` (`cbf:99-106`). **[test]** `claim-board-question.spec.ts:44-55`: second run's `resume` is the first run's session, `cwd` equal, task `completed` with `attempts: 1`, the answer appears once as an answer and not as feedback, and the marker path differs. A second question holds the task again the same way (`claim-board-question.spec.ts:58-70`).
- **An answer spends no retry** (`claim-board-question.spec.ts:54`; **[doc]** `hm:122`). Nothing is spent while the user thinks (**[doc]** `hm:112`).
- **Cancel:** closes the question, starts no run; the commits and kept files stay (**[doc]** `hm:124`).
- **A deadline** on the question exists only if the host sets `userDeadlineMs` (`apps/docs/docs/configuration/runtime.md:62`); at it the question closes with a "no answer came" message and the next run goes on in the same session (**[doc]** `hm:124`). An approval reads as a no at its deadline, a review ends with `review: "deadline"`.
- **A session the agent cannot find is replaced.** The run record keeps only a session the harness confirmed (`onSession` is the sole writer; each attempt's opening write clears it). If the agent cannot find the session a run asked to continue, the next run starts a fresh one with the brief, the question and the answer (`rr:57-82`, `rr:413-420`, `cca` `resume`; **[doc]** `hm:128`).
- **Per-call tool approval (`approveTools`) is not set by the kit** (`cf:223-239` has no `approveTools`). When you build `harnessManager` or `harnessSessionFlow` yourself with `approveTools: true`: a call the harness has not been told it may make stops the run before it runs; the Inbox shows an approval titled `Allow <tool>?` with `{ tool, touches, cwd, approveOptions }`; answers are allow once, `ALLOW_FOR_RUN` (`{ label: "Allow for this run", data: { scope: "run" } }`; covers the same tool on the same command or file for the attempt) and deny with an optional note; more than 25 approvals in one attempt fails the attempt (`td:97-105`, `td:186-195`, `td:205`; **[doc]** `hm:177-223`). Only Claude Code asks per call: its `onToolApproval` hook returns `{ decision: "allow", updatedInput? }`, `{ decision: "deny", message? }` or `{ decision: "held", message? }` (`cct:541-544`, `cca:245-253`); a call in `allowedTools` never reaches it. Needs durable execution (`mg:2682-2700`). Codex and Cursor take their sandbox and approval settings for the whole run and ignore the feed (**[doc]** `hm:223`, `hmr:833`).

## 7. Talking to a run, and steering

- A line in a task's session: while the task is open it is a steer (kept on the task as the user's message, taken at the run's next step, same coding session, no attempt used); once the task and its follow-ups finished it is talk (one harness run resumes the task's coding session and the reply stays in the session; the task, output and attempts do not change) (`sd:1-24`). Refusals: `not-started`, `cannot-continue` (finished and its harness confirmed no session), `task-running` (a message, not a line, about an open task), plus `steer-limit`, `finished`, `not-supported` (`sd:61-66`). A task takes at most 20 steers (`packages/orchestration/src/tasks/schema/steer.ts:10`).
- A message from another worker: a coding worker named by a message is refused with `task_sessions_only` ("answers only from its tasks' sessions, so it can't be messaged by name. File it a task instead."); a finished task's session can be messaged and answers by resuming its coding session; an open task refuses (`packages/workforce/src/messages/send-message.ts:107-110`, `cf:310-318`, `sd:23-24`; **[doc]** `apps/docs/docs/workforce/messaging-workers.md:28`, `:215-220`).
- A running step is stopped for a steer only when its harness declares `stopsOnAbort` (the block's own word that its process has exited when its signal fires). Claude Code's block declares it (`cca:1679`); Codex and Cursor do not. Otherwise the step finishes first and the next step takes the message (**[doc]** `hm:361`; `core:239-246`).
- A harness that takes a line mid-turn offers a `steer` through `onSteerable` once the prompt is sent and withdraws it (`null`) when the turn ends. Cursor does; Claude Code and Codex do not. `steer(text)` answers `"delivered"` or `"refused"`; a refused line is not taken and is sent as the next prompt (`cua:168-183`, `cua:183`; **[doc]** `hm:365`).
- `harnessSteering()` (from `@flow-state-dev/core/harness`) builds `{ onSteerable, steer, action(options?) }` for a flow that runs a harness turn without a board; `action()` takes `{ prompt }` and answers `{ taken, live }`; offers live in the server process, so a line that reaches another process answers `{ live: false, taken: false }` and runs as the next turn; the action is declared `concurrency: "allow"` and the turn action beside it should declare `concurrency: "defer"` (`packages/core/src/helpers/harness-steering.ts:1-12`, `:81-118`, example `:73-80`).
- A running task's progress note: `statusNote` is set from the harness's `onActivity` feed, first note at once then at most one every 30 seconds (`PROGRESS_NOTE_MS`), cut at 280 characters; Claude Code and Codex report messages and tool calls, Cursor tool calls only (`packages/harness-manager/src/progress-note.ts`, `cua:189-196`; **[doc]** `hm:371-377`). A worker's message to a running coding task is refused until it finishes (**[doc]** `hm:371`).

## 8. Review

Only when `review` is on (kit key, or the worker's `review:` line).

- The reviewed manager is a second manager per harness built with `reviewChanges: true` (`cf:221-246`). A run is reviewed only when it would otherwise complete and has commits (section 5 step 7). The hold is `ask.kind: "review"`, title "Review the run's changes" ("The accepted changes didn't land" when asked again after a failed landing, `mg:4142`). Its prompt gives the commit count and up to 20 subjects, "N files changed (+a −d).", "Checks n/m passed." when checks ran, the judge's verdict, confidence and reason ("No judge read this run." without one), and "The judge's verdict is information, not approval." (`mg:1486-1530`, `mg:4141-4175`, **[doc]** `hm:140`).
- Hold data: `{ branch, commits, subjects, files, fileCount, added, removed, judge, checks, lands, landFailed, landAttempts, goal, answer, pullRequests, round }` (`mg:4153-4174`; `review-detail.ts:17-` `reviewDetail` reads it; **[doc]** `hm:140` lists the first nine only, the rest are code-only). `files` lists up to 200 changed files `{ path, added, removed }` (`added`/`removed` `null` for a binary file); `fileCount`, `added`, `removed` count every file; all four are `null` when git could not read the diff. Only committed changes count; a rename is the old path removed and the new path added (`commits.ts:109`, **[doc]** `hm:140`).
- **Answers** (`harnessReviewAnswerSchema`, `mg:1077-1083`): `{ verdict: "accepted", land?: "pull-request" | "merge", words?: string }` and `{ verdict: "revise", words: string }` with non-blank `words` (a blank revision is refused with a 400 and the review stays open). 
  - `accepted` completes the task with no further run; the output says `review: "accepted"` (`mg:3952-3981`). With `land`, the work is landed first: `pull-request` pushes the run's branch and opens a pull request (recorded in `observed-pull-requests`), `merge` merges the run's branch into the base branch of the user's checkout. `lands` in the hold data lists the ways this host offers: for a run cut from a repository listed in `localRepositories`, `merge` always and `pull-request` too only when the run's base has a pinned remote naming a GitHub repository (`land.ts:151-165` `landWays`); none for a run cloned from a remote (the review keeps a plain Accept). A landing that fails (refused push, merge conflict, never resolved) asks the review again with the error in `landFailed` and the tries in `landAttempts`; the branch and checkout are kept (`mg:4062-4070`, `packages/workspace/src/land.ts:1-30`; **[test]** `review-changes.spec.ts:689-860`: `lands`, `landed: { kind: "pull-request", url, number, branch, base }`, `landed: { kind: "merge", branch, commit, checkout }`, conflict asks again).
  - `revise` writes the words as the user's steer and starts one more run on the same attempt, resuming the same coding session with the words in the brief; if it commits again it is reviewed again over all the branch's commits. Each request counts toward the 20-steer limit; past it the attempt fails. A harness that confirmed no session cannot take a revision: the attempt fails and the next brief carries the words (**[test]** `review-changes.spec.ts:343-375`, `:426-470`; **[doc]** `hm:158-160`).
- A branch with a pull request open from it, opened by this task's own accepted landing, lands there unasked: no review is asked, its commits are pushed to that pull request (`mg:3993-4010`, `mg:4069-4098`). A pull request seen on the branch that this task did not land on is never pushed to unasked (`mg:4069-4075`).
- No deadline unless the host sets `userDeadlineMs`; at it the task completes and the output says `review: "deadline"` (never read as accepted). A cancel while the review waits closes it and starts nothing; commits and kept files stay (**[doc]** `hm:162-164`; **[test]** `review-changes.spec.ts:529`).
- Needs durable execution: on a host without it a reviewed manager is refused before any harness step; on a claim board the task ends `errored` with a message naming durable execution (`mg:2682-2700`, `mg:1470-1477`; `hmr:832` says "cancelled", which is the fixed-board ending). **[test]** `review-changes.spec.ts:571`.
- The kit declares no per-file patch view. A coding flow you build declares `views: { changes: harnessRunChangesView({ board }) }` (input `{ taskId?, path? }`; without `path` `{ diff }`, with it `{ patch }` cut at 64 000 characters, `verified: false` when git could not read it; refused with `HarnessRunChangesRefused` for a session that ran no task or a `taskId` of another session) (`packages/harness-manager/src/run-changes.ts:27-111`, `commits.ts:112`). The kit's `coder` flow declares only `recordedWork` (`cf:293`).
- `workPlace(output)` returns where a run's work went: the branch, the commit count (`null` when unknown, never a guessed zero) and the shell commands that reach it, or `null` for a run with no branch; it is browser-safe and imports nothing (`hmr:338`; **[doc]** `apps/docs/docs/ui/flow-aware-components.md:159`).

## 9. What a run records

All of these are written by the run's harness or by the manager and only read by a user; a client writes none.

**Plan.** `observed-plan/**` rows (one per to-do item, key `conversation/<id>/<item>` where `<id>` is the harness's conversation id) and `observed-plan-list/**` markers (one per conversation, with `status` `writing`, `complete` or `incomplete`, `count`, `reason`, and on a run's marker `conversation`, the pointer to the conversation namespace). Row fields: `title`, `status` (the harness's own word), `previousStatus`, `lastOutcome`, `lastTouchedAt`, `requestId`; every field may be `null`. Session scope, lazy prefetch, client-readable and live. A plan belongs to the conversation, not one run; a new conversation starts with none. Written by Claude Code (with `recordWork: true`, which the kit sets) and by Cursor (only with `recordPlan: true`, default `false`; the kit does not set it). Codex records none (`core` `packages/core/src/types/harness-plan.ts:44`, `:90-160`, `:420-460`; `cck:53`; `cua:236-251`; `cxt:71`; **[doc]** `ca:81-119`). A harness that records no plan does not declare the collection, so a reader checks the session's resource manifest before showing an empty plan (**[doc]** `ca:109-119`).

**Files the run touched** (`recordWork`, Claude Code only). `observed-file-ops/**`, key `<run id>/<path>`: `lastKind` (`created` or `edited`), `outcome`, `lastTouchedAt`, `appliedCount` (operations the harness confirmed applied; `0` means the run touched the path and nothing applied; `null` is a row from before the count). Never contents. Only the file tools' calls are recorded: an edit made through the shell (`sed -i`, a redirect, `mv`) is not. `observed-gaps/**` holds one row per mutation the recorder recognised and could not record, keyed by run and ordinal. Session scope (`packages/claude-code/src/sdk/work-collections.ts:37-60`, `:88-130`, `cca:316-323`).

**Pull requests** (`observed-pull-requests/**`). Row fields, all nullable: `host` (lower-cased), `repository` (`owner/name`), `number`, `url`, `title`, `state` (`open`, `closed`, `merged`, `draft`), `branch`, `requestId`, `source` (`tool` or `branch`), `firstSeenAt` (epoch ms). Key from host, owner, repository and number (`pullRequestKey`), so a pull request seen twice is one row. Session scope, client-readable, no client write (`packages/core/src/types/pull-requests.ts:38-110`; **[doc]** `ca:188-225`). A row comes from a tool call that creates one and whose output names a `https://<host>/<owner>/<repo>/pull/<n>` link: a shell call running `gh pr create` or `gh pr new`, or a tool named `create_pull_request` under any MCP prefix; `gh pr view`, `gh pr list`, a search, a link only in arguments and git's `/pull/new/<branch>` hint are not (**[doc]** `ca:224-262`). The three agent blocks record by default (`recordPullRequests`, default `true`; `false` records nothing and does not declare the collection): `cca:324`, `cxa:181`, `cua:260`.
- Row merge rules (`writePullRequests`, `core pull-requests.ts:443-493`): a new key is written whole with `firstSeenAt`; an existing row keeps `requestId` and `firstSeenAt` once set; a later sighting fills only a `null` `url`, `title`, `branch` or `requestId`; **`state` is replaced by any later sighting that names a different one**; a `tool` sighting upgrades a `branch` row's `source`. [stale] `ca` says state "isn't kept current afterwards".
- The branch check, `recordBranchPullRequests(ctx, options)` from `@flow-state-dev/workspace` (the manager runs it before its verdict and when a run fails): asks GitHub through the host's signed-in `gh` for pull requests whose head is the checkout's current branch (unless detached) plus `branches`, open, closed and merged, same repository only (not forks), at most 20 per branch, and writes those the record lacks with `source: "branch"`. It waits for the request's in-turn recorder first, so a row the tool sighting wrote keeps `source: "tool"` (`bpr:1-30`, `bpr:110-205`). Options: `cwd` (the checkout, required), `branches?` (more branches), `requestId?` (stamp for new rows, default the context's), `openedSince?` (epoch ms; only pull requests GitHub says were created at or after it, with 60 s of clock slack, are written; unset writes every one), `timeoutMs?` (one wall clock for every command, default `BRANCH_PULL_REQUESTS_TIMEOUT_MS` = 30 000), `gh?` (program, default `gh`), `worktree?` (`{ collection, key, startedOn? }`: what is found is also added to the user's worktree row; `startedOn` is a pull request the session started on, added whatever `openedSince` says) (`bpr:50-80`, `bpr:174-200`). Result: `{ status: "recorded", branches, pullRequests }` (every pull request found, including ones already recorded, after the `openedSince` filter) or `{ status: "unavailable", reason }`; it never throws and never fails the turn: a missing or signed-out `gh`, a checkout with no GitHub remote, an undeclared collection, a timeout or a failed write is `unavailable` (`bpr:83-95`, `bpr:135-170`). State mapping: `merged` when GitHub's `merged_at` is set, `draft` when open and a draft, else GitHub's `state` (`bpr:107-120`). Only GitHub is supported.
- The manager's pull-request wait reads each task pull request from GitHub (`readPullRequest`) and writes the state it read back to the record with `source: "branch"` (`apr:134-142`). The task's pull-request verdict: any open holds; none open and one merged completes (a closed one beside it noted on the output); all closed unmerged cancels (`apr:146-156`).
- The kit's `recordedWork` view, input `{ requestId }` (a run of the session), answers `plan` (at most 200 steps, `truncated`; `null` while none) and `pullRequests` (that run's, oldest first, at most 200, `truncated`); `readRecordedWork` from `@flow-state-dev/harness-manager/browser` reads the same rows for a page, plus the files (`rw:30-83`, `packages/harness-manager/src/recorded-work.ts:1-60`). The coding board shows only each task's pull request numbers (`cbv:72`).

**Usage and cost.**
- The handle's `usage` is `{ inputTokens, outputTokens }` or `null`; `cost` is `{ usd, basis: "reported" | "estimated" }` or `null`; values are never invented (`core:201-217`, `core:188-199`). Claude Code reports a cost (`basis: "reported"`); Codex and Cursor estimate one from the model price table, `null` when no model was named or the table has no row (**[doc]** `ca:54-57`, `cx:244-256`, `cu:367-386`; `cca:1620`).
- The run record keeps the last attempt's `usage` and `costUsd` and clears them when the next attempt opens; no decision reads them (`rr:321-331`, `rr:413-420`).
- Subscription windows (how much of a plan is used): `harness-usage/**`, one record per user and harness, window by window; `status` `windows`, `api-key`, `signed-out`, `unavailable`; `plan`; `windows` (with `origin` `read` or `run`); the account kept only as a hash, no email; no history. User scope, `flowIsolation: false`, lazy, `llmWritable: false`. Clients may read the rows but the hashed account and the server's clocks (`account`, `accountAt`, `noSubscriptionAt`, `lastAttemptAt`) are `secret`, so every client read drops them (`packages/harness-manager/src/harness-usage.ts:100-157`). [stale] `hm` and `hmr` say a client cannot read the collection directly.
- A run adds a window when its harness is handed the manager's `onUsage` feed and reports one. Under the kit that is Claude Code only: its harness value spreads `...feeds`, so `onUsage` reaches it, and it reports a window from the SDK's `rate_limit_event` (`cck:48-52`, `cca:652`, `cca:1368-1382`, `packages/claude-code/src/sdk/usage.ts:1-30`). ## 10. Harness values and the handle

A `Harness` value (`hv:20-35`): `id` (what a worker's `harness:` names and readiness rows are keyed by), `label`, `agent(feeds)` (the block one run runs), `readiness(check?)`, `pass` (environment variable names the run is given beside the base ones), optional `usage` and `models`. The slot refuses an entry missing `id`, `agent`, `readiness` or `pass` (`hv:40-49`).

Feeds the manager hands `agent`: `cwd`, `resume`, `onSession`, `onUsage`, optional `onSteerable`, `onActivity`, `onEvent`, `onToolApproval` (`mg:809-885`). `onEvent` marks each event so a working run is not stopped for silence; a harness not handed it is stopped at the idle window however busy it is, and the manager warns once (`rs:80-83`, `rs:114-120`).

The handle (`core:139-217`; **[doc]** `ca:39-80`), the same for every harness:

| Field | Values |
| --- | --- |
| `source` | `<package>/<door>`: `claude-code/sdk`, `codex/sdk`, `cursor/sdk` |
| `status` | `running`, `completed`, `errored`; the schema also admits `dispatched`, which none of the three returns (`core:167`) |
| `sessionId` | the harness's conversation id (Claude Code and Codex: the conversation; Cursor: the agent, each prompt being one run in it); `null` when unknown. A resumed run's id starts as the one asked for, so `onSession` firing is what confirms it |
| `url` | link to the run, or `null` |
| `dispatchedAt` | epoch ms |
| `outcome` | `finished`, `stopped-at-limit`, `failed`, or `null` for no terminal result (`core:202`) |
| `finalMessage` | the last assistant message or `null` |
| `usage` | `{ inputTokens, outputTokens }` or `null` |
| `cost` | `{ usd, basis }` or `null` |

Input is `{ prompt, attachments? }` only; `cwd`, `resume` and `model` are configuration, never input, so a model cannot choose where a run works or which conversation it resumes (`core:139-143`, `cxa:106-122`, `cua:148-165`). Unknown input keys are stripped. A block that conforms is a `HarnessBlock`; it may declare `stopsOnAbort` and `accepts` (`core:228-250`).

Per-agent fields beside the shared ones: Claude Code `resultSubtype` (`success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, `error_max_structured_output_retries`, or `null`) and `toolsObserved` (distinct tool names, first-seen order) (`cct:89-120`); Codex `codexUsage` and `failureMessage` (`cxt:79-81`); Cursor `cursorUsage` and `failureMessage` (`cut:87-89`).

How `outcome` is set: Claude Code `success` is `finished` unless `is_error` is set (then `failed`); `error_max_turns` and `error_max_budget_usd` are `stopped-at-limit`; anything else `failed`; `null` when no terminal result arrived (`cct:36-50`). Codex and Cursor give `finished` or `failed`; a Cursor run reported cancelled reads `failed` with the reason on `failureMessage`; a Cursor handle is always terminal (`cxt:71-75`, `cut:76-80`; **[doc]** `cu:352-366`).

Failure shapes: a run the agent itself fails comes back as a handle with `status: "errored"` and no throw (Claude Code: `outcome` `stopped-at-limit` or `failed` with `resultSubtype`; a turn ending on an API error is `success` with `is_error`, so `failed` with `resultSubtype: "success"`; Codex and Cursor: `outcome: "failed"` with `failureMessage`); nothing retries. A thrown run returns no handle: Claude Code `ClaudeCodeAgentRunError` (SDK threw mid-stream), `ClaudeCodeSdkNotInstalledError`, `ClaudeCodeAgentAbortedError` (carries `sessionId`); Codex `CodexAgentRunError`, `CodexAgentConfigError`, `CodexSdkNotInstalledError`, `CodexAgentAbortedError`; Cursor `CursorAgentRunError`, `CursorAgentConfigError`, `CursorSdkNotInstalledError`, `CursorAgentAbortedError` (carries the agent id on `sessionId`) (`cce:12-72`, `packages/codex/src/errors.ts:18-110`, `packages/cursor/src/errors.ts:18-115`). A stopped run (deadline, cancel) is a throw and never a handle; the session id has already reached `onSession` by then, so the run can be continued. `harnessFailureKind(error)` from `@flow-state-dev/core` reads through wrapped errors and returns `"unknown-conversation"` when the agent does not know the conversation `resume` named, else `null`; the run throws and the stored id is untouched (`cce:34-43`; **[doc]** `ca:72-79`, `cx:324-340`, `cu:388-410`; error table lines `cc:926-936`).
- Version mismatch: the three blocks refuse to build against an installed SDK outside the tested range with one error, `HarnessSdkVersionMismatchError` (code `HARNESS_SDK_VERSION_MISMATCH`), whose message names the SDK, the harness, the installed version (or that it cannot be read) and the range, and gives the install command; absent SDK is not refused at build and surfaces on the first run as the `...SdkNotInstalledError` (`csv:58-85`, `csv:136-145`). [stale] `cu` names a `CursorSdkVersionMismatchError`, which does not exist; `cc` names `ClaudeAgentSdkNotInstalledError` and `ClaudeAgentRunError`, the classes are `ClaudeCode...`.

## 12. Readiness

- One row per harness filled, kept in memory in the process (never stored); the first read runs every check, later reads return the kept rows, `refresh: true` checks every harness again, `refresh: "<id>"` one; concurrent checks of one harness share one call; nothing polls (`rd:20-31`, `rd:105-150`; **[test]** `packages/harness-manager/test/readiness.spec.ts:48-95`).
- Row fields: `harness`, `label`, `ready`, `reason` (`null` when ready), `remedy` (`null` when ready or when the check named nothing), `unanswered` (the check got no answer), `checkedAt` (epoch ms) (`rd:50-67`).
- Never throws: a check that throws, rejects or passes the 30 s timeout is a not-ready row with a plain reason and `unanswered: true` (`rd:39`, `rd:173-214`; **[test]** `readiness.spec.ts:84-93`).
- The view `readiness` on the kit's `harnesses` flow: user scope, read with no session, input `{ refresh?: boolean }` (Re-check is `{ refresh: true }`), one row per harness, no model call; every user of the machine gets the same rows (`rd:258-275`; **[test]** `readiness.spec.ts:198-237`, `hkt:78-91`).
- Before each coding task the coder flow asks `refusal(id)` for the worker's harness: a ready row answers with no check; a not-ready or missing one gets one fresh check so a sign-in made since the last read counts. A harness that cannot run fails the task at once with a sentence that names the harness, says why, and says what to run: `<Label> isn't set up on this machine: <reason>. <remedy>. Then start the task again.`; a check that got no answer says `Couldn't tell whether <Label> is set up on this machine: <reason> Try starting the task again in a moment.` The task is never moved to another harness (`rd:144-165`, `cf:272-277`; **[test]** `readiness.spec.ts:99-141`, **[doc]** `hmr` readiness section). The start is a failed attempt; with no `maxAttempts` the task ends `errored`.
- Start log with `logReadiness`: `Coding harnesses on this machine:` then one line per harness, `✓ <Label>`, `✗ <Label>: <reason>. <remedy>.` or `? <Label>: <reason>.` for no answer (`rd:227-235`; **[test]** `hkt:121-136`).
- The capability puts the same rows in a coordinator's context, followed by guidance: file coding work only on a ready harness; say what to run for one that is not; start the task when the user says they have just signed in, since a start checks again (`rd:275-300`, `hk:127`).
