## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A user files a coding task, "Fix the login redirect", for a worker on Codex. The app uses the harnesses kit with `checks: { commands: ["pnpm test"] }` and leaves `pullRequests`, `judge` and `review` at their defaults. The run commits, the tests pass, and the agent opens a pull request. When is the task marked complete?
   Answer: Not when the run ends. The kit goes through its verdict in order: the harness step comes back `completed`; the phase is done (`outcome` is exactly `finished`); the checks run because the run changed files, and every command passes; the files and held work are saved; the judge (`judge` defaults to true) does not give a confident *not done* or *ask* (confidence 0.7 or more); review is off by default. Because `pullRequests` defaults to true and the run opened a pull request, the task then waits on that pull request, which counts as an external wait and shows as `running`. It completes when the pull request merges, and it is cancelled with "its pull request was closed without merging" if every pull request closes unmerged. A run that opened no pull request completes at the settle step, and its run record's `outcome` becomes `succeeded` (facts §5 steps 1-9, §1 `pullRequests`/`judge`/`review` defaults).
2. The task completed a day ago. What has happened to its checkout and branch, and how does the user clean them up?
   Answer: Nothing removes them. The manager releases its lease and leaves the checkout, the branch (`fsd/<name>` by default, under `<root>/<name>`) and the commits on disk, so a retry, an answer or a typed line can pick up in the same place. To remove one by hand, run `fsdev worktrees <root> --remove <dir>`. Add `--delete-branch` to drop the branch too, and `--force` as well if the branch holds the only copy of some commits. The removal is refused, and nothing is deleted, if there is `uncommitted-work`, if the place is `place-busy` or `in-use`, or if there are `unique-commits` without `--force`. The CLI prints `Refused (<reason>): <message>` and exits 1. The user's `worktrees` list keeps the row and marks it `removed` (facts §3, §2a).
3. A Claude Code run runs out of turns (the SDK's `error_max_turns`) partway through the change. The task has no `maxAttempts`. What state does the task end in, and is the partial work committed for the user? *(edge case)*
   Answer: The task fails. For the SDK's turn and budget limits, Claude Code's handle returns `status: "errored"` with `outcome: "stopped-at-limit"`, so the attempt fails at the first step with `the run stopped without finishing: stopped-at-limit — <final message>`. A task with no `maxAttempts` gets one attempt, so it ends `errored`, which the user sees as `failed`. No code commits what the run got through. Only what the agent itself committed is on the branch, and the checkout stays on disk (facts §5 step 1 and "Statements the page must not make", §4 Attempts, §10 outcome mapping).
4. The judge answers *ask* about a run, with confidence 0.8. What does the user see, how do they answer, and does answering use up the task's retry? *(edge case)*
   Answer: The task is held on a question. It stays `in_progress` on the same attempt, with a hold of `ask.kind: "question"` and no lease, and the question names the goal and quotes the first 500 characters of the answer. It shows as `waiting` in the Inbox, in the task's open `questions` from `getTask`, and on the kit's `codingBoard` rows. The user can answer in three ways: in the Inbox, with `updateTask` (`answers: <hold id>` and `message`), or by typing a line in the run's own session, which answers the oldest open question. The answer gets one more turn on the same attempt. That turn resumes the same coding session in the same checkout, with the question and answer in the brief under "Answers to your questions". It spends no retry. If the user cancels instead, the question closes, no run starts, and the commits stay (facts §5 step 6, §6).
5. While Ana's task is running, a colleague opens the same task's session and types "also update the README". Separately, the colleague files the same issue as their own task. What happens in each case? *(edge case)*
   Answer: Only the run's own user can send a line to its session. The colleague's line is refused before it is written. Runs never share a place between users: two users, or two organizations, never share a folder or branch for the same issue and phase, so the colleague's own task gets its own checkout and branch. If Ana had typed the line herself, it would be a steer. It is kept on the task, taken at the run's next step in the same coding session, and uses no attempt, up to 20 steers (facts §6 "How to answer", §2a, §7).
6. An app fills the kit with `cursorHarness()`. After a Cursor run, the user's page wants to show the run's to-do plan, its pull requests and its cost. Which of these will it have?
   Answer: Pull requests, yes: Cursor records them by default (`recordPullRequests` defaults to true) into `observed-pull-requests/**`, one row per pull request. The plan, no: Cursor records one only with `recordPlan: true`, which defaults to false and which the kit does not set. A harness that records no plan does not declare the collection, so a reader should check the session's resource manifest before showing an empty plan. Cost is usually `null`, because Cursor's model ids are not in the price table, so the page should read `cursorUsage` for the counters. By comparison, Claude Code records a plan under the kit (`recordWork: true`) and reports its cost with `basis: "reported"`, and Codex records no plan (facts §9 Plan, Pull requests, Usage and cost; §11d).
