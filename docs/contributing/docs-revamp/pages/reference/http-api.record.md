## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your front end wants the reply to show up as it is written, so it posts a user's message to an action. Which endpoint starts the action, what goes in the body, and what comes back depending on the Accept header?
   Answer: POST /api/flows/:flowId/actions/:action, or POST /api/flows/:flowId/:sessionId/actions/:action to run in a named session. The body is { input, userId?, requestId?, metadata?, attachments? }. userId goes in the body only on an app with no sign-in. With Accept: text/event-stream the response is the live SSE stream: status 200, content-type text/event-stream; charset=utf-8, plus x-request-id and x-session-id headers. With any other Accept it is 202 { status: "in_progress", request: { id, flowKind, flowId, actionName, status }, session?: { id } }, and you follow it through GET .../requests/:requestId/stream or poll GET .../status. Facts 2.2, 4.8, 4.9, 1.9.
2. You send three messages to the same action with no sessionId, expecting one conversation. What happens, and how do you keep them together?
   Answer: Each send runs in a new session, and the response does not give you its id: the 202 has no session field and the inline stream's x-session-id header is empty. Create the session first with POST /api/flows/:flowId/sessions, which answers 201 { session }. Then pass its id in the path (/:flowId/:sessionId/actions/:action) on every send. The client's send does this through its sessionId option. Facts 4.10, 2.2.
3. A second user, Bob, gets hold of Alice's session id and posts an action into it, then tries to read its state. What does he get back, and can he tell that the session exists? *(edge case)*
   Answer: Both calls answer 404 { error: 'Unknown session "<id>"' }, the same status and the same words, byte for byte, as an id nobody has used. The body names neither the owner nor the organization. On the action route the 404 comes before the request is acknowledged and before the session changes, so nothing is written. Requests work the same way: another user's or tenant's request id gets 404 'Request "<id>" not found' (the stream route says 'Unknown request "<id>"'). So Bob cannot tell the session exists. Facts 5.1 not-found table, 4.6, 2.3h.
4. Your flow is a collection with two copies registered, review-east and review-west. A caller posts to /api/flows/review/actions/run, and later sends a session created under review-east through review-west. What does each call return? *(edge case)*
   Answer: The kind is not an address. POST /api/flows/review/actions/run answers 404 Unknown flow "review", and no copy is picked; each copy is reached only by its own id, which GET /api/flows lists with id, kind and cardinality. A session records the copy that created it, so naming it through review-west answers 409 { error: "wrong-instance-session", message } and nothing is written. Routes that read a request (stream, status, resume, answer) through the wrong copy answer the unknown-request 404 instead. Facts 3.1 to 3.4.
5. The user's connection drops in the middle of a long streamed run. Does the run stop, and how does the client pick the stream back up without missing or repeating events? *(edge case)*
   Answer: The run does not depend on the connection. A disconnect ends only that client's tail, and the request keeps running until it finishes or the host's timeout. Only POST .../requests/:requestId/abort stops it. To pick up again, GET /api/flows/:flowId/requests/:requestId/stream with starting_after=<last sequence_number> or the header Last-Event-ID: <requestId>:<n>; if both are sent, starting_after wins. Each frame's id is <requestId>:<sequence_number>. An in-flight request is followed live from the cursor; a finished one is answered with the saved events past the cursor. Replay never includes content.delta, because item.done carries the whole text. Facts 4.11, 6.1a, 6.2b, 6.2c, 6.2e.
6. A run is waiting for a user's approval. Two people click Approve at the same moment on the answer route, and one of them clicks after the deadline has passed. Which status codes can come back? *(edge case)*
   Answer: Approving goes through POST /api/flows/:flowId/requests/:requestId/answer with { suspensionId, action, data? }. The accepted answer gets 202 { requestId }, or the continuation's stream with Accept: text/event-stream. If another resume holds the request, the second call waits up to 2 seconds, then gets 409 { error: "Another resume of this request is in progress. Try again shortly.", refused: "busy" }. Once the stop is resolved, a later answer gets 409 'Suspension "<id>" has already been resolved (status: ...)' with refused: "already-resolved". An answer past the deadline gets 410 'Suspension "<id>" expired at <ms>'. A request that is not the caller's, or a stop that is not a user's, gets 404 'Suspension "<id>" not found'. Facts 2.3, 5.3a, 5.3c, 5.3d, 5.3f, 5.3i.
