## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A customer is waiting on the support flow. The drafting generator is halfway through its reply when the customer's wifi drops, then comes back. What does the client send to pick the stream up again, and does the reader get back the words that streamed while it was gone? *(edge case)*
   Answer: It sends the last sequence_number it applied, either as `starting_after=<n>` on the request stream URL or as the header `Last-Event-ID: <requestId>:<n>`, which is the id of the last frame it received. Every event numbered above n comes back. If it sends both, `starting_after` wins. A bare number such as `Last-Event-ID: 42`, or another request's id, is ignored and the stream replays from the start (8.1 to 8.3). Replay never includes `content.delta`, so the missed tokens are not played again one by one. The saved copy of the in-progress message holds the text so far, and the finished `item.done` carries the whole text (8.6, 5.2). The JS client does all of this itself: `request(id).stream({ reconnect: true })` resumes after the last event, with backoff from 1 s doubling to 30 s, and drops events it has already seen by requestId and sequence_number (8.7, 8.8, 8.10).
2. While the order is looked up, the support handler shows the line "Looking up your order…" with `ctx.emit.status`, and the lookup tool streams its progress. Then the customer reloads the page. Which of the items they saw are gone, and which item types are never stored at all?
   Answer: After a reload the page reads the saved session snapshot, which holds only client-visible, non-transient items, collapsed to their canonical log (8.16). The status line is gone, because `status` is live-only by default and is stored only when emitted with `{ transient: false }`. The tool's `tool_call_progress` items are gone too, since they are always transient. The `tool_output` itself and the reply `message` remain. Never stored: `resource_change`, `state_snapshot` and `tool_call_progress` (always transient), `status` unless asked, `state_change` in production unless the flow sets `persistStateChanges: true`, any emission with `transient: true`, and ephemeral audio content. A `transient: true` block keeps no trace (5.1, 5.3, lookup in §15).
3. The customer sends a follow-up message: "Can you change the delivery address?" Which of the first turn's items does the drafting generator's model see this time?
   Answer: None at all, unless that generator sets `history` (`true`, an `ItemQuery`, or a slot function). With no `history`, no earlier turns are put together for it (6.1). When it does set `history`, only `message`, `reasoning` and `tool_output` items whose resolved visibility has `history: true` are included. With no `itemVisibility` set, those three default to included. A `data` item (the order card, say) is included only if its emitter set `itemVisibility.history: true`, and it appears as one line, `[<dataType>] <value as JSON>`. `status`, `error`, state and resource records and trace items are never included, and neither are transient items (6.3 to 6.7). The order lookup is replayed as an assistant tool call plus a tool result. Earlier turns are read oldest first, up to `historyWindow.turns`, which defaults to 50 (6.5, 6.8).
4. The support handler shows an order card with `ctx.emit.data("order-card", order, { key: orderId })`. A moment later the order status changes and it emits the card again with the same key and a new value. What ends up stored, and what does the browser show? *(edge case)*
   Answer: The second emission keeps the same item id. That item goes back to in progress, then is done again. The stored record keeps one entry per `(requestId, key)`, and the latest `value` replaces the earlier one completely, with no merge. The event log still records an `item.added` and an `item.done` for each emission (2.25, 3.9, 5.6). In React, `<ItemsRenderer>` uses `deduplicateByKey`, which is on by default, so the browser shows only the latest card, in that card's position. This holds within one request only: the same key in a later request is a separate item (4.16, 1.9). A client that does not use the React hooks has to overwrite by item id rather than append (5.6). The card is drawn only if a renderer is registered under `renderers.data["order-card"]`. Without one it is in the stream and the session but draws nothing (2.23, 4.14).
5. The order-lookup tool throws because the order service is down. What does the browser receive, what does the model see on its next call, and what happens if the whole request then fails? *(edge case)*
   Answer: The lookup's `tool_output` item starts with `item.added`, carrying `toolCall` and `status: "in_progress"`. Once the call settles it ends `failed`, carrying `error { message, code?, details? }` (3.4, 2.3). The lookup block's `block_trace` also ends `failed` with the same error shape, but trace items always resolve to `{ client: false, history: false }`. The browser gets that trace only if the client asks with `?include=trace`, as the DevTool does (4.3, 11.2, 11.5). When history replays it, the model gets the failed call as a tool result whose text is `failedToolResultText(name, error.message)` (6.5, 6.6). If the request itself fails, the runtime emits an `error` item. The error item is client-visible, never in history, and the stream ends with the terminal event `request.failed` (2.8, 4.6, 7.7).
6. A second support agent opens the same customer session in another tab while the reply is still being written. What does their tab show, and how can it follow the reply as it arrives? What happens if a different user opens that request's stream? *(edge case)*
   Answer: With `useSession`'s default `autoResume: false`, the tab loads one snapshot of the saved conversation and opens no stream. The in-progress message in that snapshot holds the text saved so far (8.15, 5.2). With `autoResume: true`, if the session's latest request is still `in_progress`, the hook attaches to that request's stream with no cursor: it replays from the start and merges items by id (8.15). With `live: true`, it opens one session stream, so the tab also hears requests it did not send. Each finished item joins `items` about a second later. That stream has no sequence numbers, and a reconnect can deliver an item twice, which the client resolves by `requestId` plus `item.id` (8.18, 10.3). A user who does not own the request gets `404`, exactly as for an unknown request id (7.13, §14).
