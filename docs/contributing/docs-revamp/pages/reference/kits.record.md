## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. An app lists its kits as `[claudeCode(), harnesses({ workspace }), workforce({ agent: { model } })]`, the reverse of the order they depend on each other. Does it start, and in what order do the kits install?
   Answer: It starts. Kits install in dependency order, each after every kit it requires, whatever order the app listed them in: workforce, then harnesses (requires workforce), then claudeCode (requires harnesses). Only kits where neither requires the other keep the listed order. Facts section 3 (kp:55-85; test et:81-90, where [d(), b(), c()] installs b, c, d; goal g1).
2. The app keeps harnesses but leaves `workforce(...)` out of its `kits` list. What happens, when, and what does the error name? *(edge case)*
   Answer: createFlowState(...) throws synchronously at construction, before ready() runs, with a FlowStateConfigError: `kit "harnesses" requires kit "workforce", which is not installed.` A required kit has to be in the app's own kits list. The error names both kits. If construction finds several problems, they all appear together under `createFlowState: the kits can't be installed:`, one ` - ` line each. Facts 3 and 7.2 (kp:63-69, kp:47-53; tests et:291, et:261-276).
3. An app wants Claude Code installed but doesn't want it offered as a coding harness. How does it drop that one entry from the harnesses slot, and what happens to the rest?
   Answer: It lists `claudeCode().without(harnesses.slots.harnesses, "claude-code")` in kits. without(slotKey, key) returns a new kit instance with only that entry of its contribution dropped, and the original is unchanged. With no key, the kit's whole contribution to that slot is dropped. Other kits' entries and the app's fill entries for the slot stay. Facts 6 (dk:164-171, kp:223-228, cc:17-18; tests et:200-206, et:226-233, ht:93-104).
4. Edit: a teammate removes `cursorHarness()` from the app's `fill` for the harnesses slot and keeps `codexHarness()`. One WORKER.md still says `harness: cursor`. When does the app fail, and what does the message name? *(edge case)*
   Answer: Construction succeeds, but ready() rejects at start-up, and so does every request after it. The worker's `harness:` value is checked against an enum built from the ids the slot holds. The message is `hireWorkforce: 1 standard worker problem(s); nothing was registered:` with a line naming the worker, the id it gave and the ids that are filled (e.g. `Expected 'codex', received 'cursor'`). No worker is registered. A worker file with no `harness:` line would use the kit's defaultHarness instead. Facts 7.3 (cd:288-291; test ht:106-119; message captured by running the code).
5. Failure: someone leaves a stray `workforce/flows/notes.mts` (or an old `drafts/` directory) in the workforce kit's folder. What stops, at which moment, and what does it name? Does anything install? *(edge case)*
   Answer: ready() rejects at start-up. Folders are read after the kits are planned and before any install, so nothing installs. The error is `createFlowState: the app can't start; a kit's folder was refused:` with one line per refused entry, across every kit, all in one error: `kit "workforce": "flows" is not used by anything that reads the folder of kit "workforce". Remove it. (<folder>)`. It names the topmost entry nothing was claimed from, so a stray directory gives one line. Only .DS_Store and Thumbs.db are ignored, and a symlink is refused even if something claimed it. Facts 4 and 7.6 (cl:90-115, kp:268-290; test et:348-364; goal g2 b:stray).
6. Second contributor: two kits, or a kit and the app's own `fill`, each give the keyed `harnesses` slot an entry with id `codex`. And a new kit that doesn't require harnesses tries to fill that slot. What happens in each case? *(edge case)*
   Answer: Both cases throw from createFlowState at construction. A duplicate key: `slot "harnesses.harnesses": the key "codex" is filled by <first> and by <second>.` Each contributor appears as `kit "<name>"` or `the app`, the earlier in install order first, and the app's fill counts as a contributor. (A list slot has no conflict: every entry is kept, with the app's fill last.) A filler that doesn't require the owner, directly or through another kit: `kit "<filler>" fills slot "harnesses.harnesses", but does not require kit "harnesses", which declares it.` The app's own fill may fill any declared slot without a requires check. Facts 2, 5 and 7.2 (kp:135-142, kp:169-199; tests et:236-247, et:249-259).
