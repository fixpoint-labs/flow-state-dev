## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your `support` flow sets `mcp: { enabled: true }` and has two caller-facing actions, `lookUpOrder` and `exportTickets`, plus a scheduled cleanup job and an internal action. With no other settings, which tools does Claude Desktop see in `tools/list`, under what names, and at what URL does it connect?
   Answer: Every entry of `flow.actions` is exposed unless it sets `mcp: { enabled: false }`; internal, task, webhook and schedule entries are never exposed (C; `tc:275-303`, `ft:263-270`). So the tools are `look_up_order` and `export_tickets` (names decamelized with `_`; D, `tc:244-246`), listed in declaration order with `{ name, description, inputSchema }`. Default endpoint is `POST /api/flows/support/mcp`, e.g. `http://localhost:3000/api/flows/support/mcp` (B, L).
2. You want `exportTickets` kept off MCP, because it takes server-side file paths, and you want the endpoint at `/mcp/support` rather than under `/api/flows`. What do you set, and does the old `/api/flows/support/mcp` URL still work afterwards? *(edge case)*
   Answer: Set `mcp: { enabled: false }` on the `exportTickets` action (B, C). Pass `dedicatedBasePath: true` to `createMcpTransportAdapter`; `basePath` then defaults to `/mcp`, so the endpoint is `POST /mcp/support` (B, `ad:139-155`). `dedicatedBasePath` is a boolean, default `false`. The old URL is not served: one adapter mounts one layout, and the route table holds only the dedicated path (`ad:153-173`, `at:248-258`). A call to `export_tickets` now returns `-32601` `Unknown MCP tool "export_tickets".`
3. A teammate adds a new action `look_up_order` next to the existing `lookUpOrder`. The flow registers without complaint. What happens, when, and how do they fix it? *(edge case)*
   Answer: Both resolve to the tool name `look_up_order`. The collision is not caught at registration: the first `tools/list` or `tools/call` that reaches the adapter throws `Flow "support" exposes actions "lookUpOrder" and "look_up_order" which both resolve to the MCP tool name "look_up_order". Rename one of them or set a distinct mcp.name override.` (D, `tc:291-298`, probe; README's "at registration" is wrong). Fix by renaming one or setting a distinct `mcp.name` on one, which goes through the same collision and charset (`[A-Za-z0-9_.-]{1,128}`) checks.
4. Claude Desktop calls `tools/list` on your `support` flow, which has no `authentication.resolvePrincipal` and no `defaultUserId`. What does it get back, and how should you make the endpoint answer as a real user? *(edge case)*
   Answer: HTTP 401 with header `WWW-Authenticate: Bearer realm="MCP"` and body `{"jsonrpc":"2.0","id":<id>,"error":{"code":-32001,"message":"Action request requires non-empty userId"}}` (E, probe, `at:520-540`). (`initialize`, `ping` and `notifications/initialized` still answer before authentication.) Configure `authentication.resolvePrincipal`: it runs once per request with `ctx.source === "mcp"` and the raw `Request`, so it can read the `Authorization` header (e.g. with `extractBearerToken` or `createBearerSecretPrincipalResolver`). The adapter reads no credential itself, and `forwardQueryParams` never touches authentication.
5. You want two `lookUpOrder` calls in one Claude conversation to share flow session state. What do you set, and what happens when a second user, Bob, sends the same `conversationId` as Alice? *(edge case)*
   Answer: By default each `tools/call` gets a fresh flow session and no `Mcp-Session-Id` is ever issued (H). Set `actions.lookUpOrder.mcp.session: { fromInput: "conversationId" }`: calls sharing that string value share one session; a missing, empty or non-string value falls back to a fresh session. The session belongs to the resolved principal, so Bob sending Alice's id is refused before anything runs with `-32602` `Unknown session "<id>"`, naming neither owner (`at:409-435`, probe). Prefix the id with the principal for users who do not trust each other, and bound the field's length in the input schema, since the session record is created before the schema runs.
6. Claude calls `look_up_order` with `orderId` as a number when the schema wants a string. Does it get a JSON-RPC error? And what does a successful call return? *(edge case)*
   Answer: No JSON-RPC error: a failed run is a tool result with HTTP 200, `{ content: [{ type: "text", text: <error message> }], isError: true }`, e.g. `Action input validation failed at "orderId": ...` (J, probe). A success returns one `{ type: "text", text }` block: the action's output as-is if a string, else `JSON.stringify` (e.g. `{"ok":true,"amount":3}`); with no output, the latest `message` item or `block_trace` output; else empty. There is no `structuredContent`, `outputSchema`, progress or streaming (`rf:96-143`, K).
