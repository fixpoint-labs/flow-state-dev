## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's app declares `intents: { chat: ["anthropic/claude-sonnet-5-5", "openai/gpt-6.1-sol"] }` and the reply generator uses `model: "intent/chat"` (not streamed). Anthropic answers with a 429 rate limit every time. Which models are tried, in what order, with what waits, and what does the caller get if OpenAI also fails? *(edge case)*
   Answer: Candidates are tried in list order (5.1). A 429 is retryable (5.4: statusCode 429, 500, 502, 503), so with the default retryPolicy (2 attempts, baseDelayMs 1000, maxDelayMs 10000) Anthropic is tried, the call waits min(10000, 1000 * 2^0) = 1,000 ms, and Anthropic is tried once more; then it moves to OpenAI with the same rule (5.2). A non-retryable or provider-load error would have moved on at once (5.3). If OpenAI also fails, the call throws one Error, `All models in group "intent/chat" failed:`, with one line ` <modelId>: <message>` per failed attempt, so a model tried twice appears twice (5.5). defaultModel does not answer here: it is used only when no candidate could be resolved, not when resolved candidates all fail on the call (3.3).
2. In staging the support desk should run `intent/chat` on `openai/gpt-6.1-sol` instead of the in-code list, with no code change. What do you set, what form must it take, when does it take effect, and which generators does it not change?
   Answer: Set `FSDEV_INTENT_CHAT=openai/gpt-6.1-sol` in that environment (name uppercased, `-` to `_`, 7.1). It replaces the intent's list with a one-element list; the value must be one `provider/model` or `name:model` string, never `intent/*` (7.2). It is read from process.env once, when the resolver is built, so the server must be restarted; setting it later has no effect (7.3). The intent must be declared in `intents` (7.5). `FSDEV_DEFAULT_MODEL` does the same for the default (7.1). A generator with a literal string such as `model: "openai/gpt-6.1-sol"` is not changed by either variable (7.6). In development it logs once `Intent "chat" overridden by FSDEV_INTENT_CHAT; resolves to ...`, silenced by NODE_ENV=production or FSD_QUIET_WARNINGS=1 (7.6). For one command, `fsdev run --model <id>` forces every generator in that process, but not evaluators and not queued background work (7.6).
3. A teammate deploys the support desk to a host that has only ANTHROPIC_API_KEY, no OpenAI package or key, and no gateway key. The triage generator has `model: ["openai/gpt-6-luna", "anthropic/claude-sonnet-5-5"]`; the reply generator uses `intent/chat` whose list is the same two strings. What happens to each? *(edge case)*
   Answer: The intent drops a candidate that does not resolve, silently, and keeps the rest in order, so the reply runs on Anthropic (3.4). The array skips nothing: each string is resolved up front, in order, when the generator resolves its model, so `openai/gpt-6-luna` throws `No provider available for "openai". Tried: direct package (not installed), gateways (none configured for this provider). ...` before any model is called, even though the Anthropic entry would have answered (4.4, 6.3). With a gateway key (AI_GATEWAY_API_KEY or OPENROUTER_API_KEY) the OpenAI string would run through the gateway instead (6.4).
4. Someone sets `FSDEV_INTENT_CHATT=openai/gpt-6.1-sol` (a typo) on one host and `FSDEV_INTENT_CHAT=anthropic/claude-sonnet-5-5,openai/gpt-6.1-sol` on another. What happens on each host? *(edge case)*
   Answer: The typo names an intent the app does not declare: a development warning once, `FSDEV_INTENT_CHATT does not match any declared intent (declared: ...); ignoring the override.`, and the in-code list is used (7.5). The comma-separated value is not one valid model string, so the resolver throws when it is built, with the variable's name in the message, e.g. `createModelResolver: FSDEV_INTENT_CHAT: Invalid model format: ...` (7.2). The variable takes one model string, not a list.
5. The support desk streams its reply. The first model in `intent/chat` has already sent a few chunks when it throws a retryable network error. What does a client rendering chunks as they arrive see, and how is a non-retryable error different? *(edge case)*
   Answer: A stream is tried once per model, with no retry and no wait (5.6). A retryable error moves to the next model whether or not chunks were already yielded, so the client sees the first model's chunks followed by the next model's (5.6, run: `a`, `b`, finish). A non-retryable error is thrown to the caller at once, before or after chunks. If every model fails, the error is `All streaming models in group "intent/chat" failed:` with one line per attempt (5.6).
6. A support agent wants to know which model actually wrote a reply that went through `intent/chat` after the first candidate failed, and what that record says when no candidate had a key and the default model answered. Where do they look and what do the fields hold?
   Answer: The `message` (and `reasoning`, `source`, `tool_output`) items the generator emits carry a ModelIdentity, as does the generator's `block_trace` row (seen in the DevTool, on a stream opened with `?include=trace`) and `meta.model` in `onCompleted` (9.3). `actual` is the provider-reported model id, else the winning candidate string; `requested` is what was asked for, set only when it differs; `gateway` is set when a gateway routed the call (9, 9.1). Through an intent, `requested` is `intent/chat` even when a later candidate won. When the intent fell through to defaultModel, `requested` is the default model's own string, not the intent name (9.2).
