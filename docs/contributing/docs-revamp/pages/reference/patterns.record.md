## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You build a debate with two debaters, one arguing for a four-day week and one against, and you set no round limit. How many rounds run? You then set maxRounds to 6 to get a fuller argument. What happens when the debate is built?
   Answer: Two rounds. `debate`'s `maxRounds` defaults to 2 (db:212). With 6 the debate still builds, but it logs a warning, because any value above 4 counts as unusually high, with diminishing returns (db:247-257). Only a value that is not above 0 throws.
2. You give `routedSpecialists` a `maxIterations` of 3, and its controller never returns `done: true`. How many specialist iterations run, and how many entries does `history` hold when `synthesizer: false`? Does `roundRobin` with `maxRounds: 3` stop in the same place? *(edge case)*
   Answer: Four iterations run, and `history` has four entries. `maxIterations` caps loop-backs, so the controller runs once and then at most `maxIterations` more times (rs:626-629; rst:245-274, finding 0.2). The default is 10. `roundRobin` and `debate` are different: they run at most `maxRounds` rounds, so `roundRobin` with `maxRounds: 3` runs exactly 3 when `terminateWhen` never fires (rr:306-318).
3. A supervisor's default reviewer returns `{ decision: "reject" }` with no `feedback` on a task's first attempt, and `maxAttemptsPerTask` is left at its default. What does the worker receive on the retry? If every attempt is rejected, what label does the task end with? *(edge case)*
   Answer: `feedback` is optional in the verdict schema. With none given, the retry's feedback is the text `Reviewer reject the task output` (svs:58; svr:167-170). The worker's input carries it in `feedback`, which is absent on a first attempt (svt:527-570). `reject` and `needs-revision` both retry, and the default is 3 attempts (sv:280). Once every attempt is used the task settles `errored`. After the drain it is labelled `failed-review`, because the last verdict was a rejection (svl:5-12). With `onSubTaskError` at its default `"skip"`, its siblings carry on and its output is left out of the synthesizer's `results`. Its pending dependents are cancelled and labelled `skipped`.
4. You add a moderator to a debate by passing `debate({ model: "openai/gpt-6-luna", tools: [webSearch] })` and expect it to get that model and those tools automatically. Does it? What do you have to do to get an LLM moderator that can search? *(edge case)*
   Answer: No. `debate()` never builds a moderator, and without one every debater speaks every round. The pattern-level `model`, `tools`, `uses`, `context` and `instructions` do not reach a moderator you pass in (finding 0.6). Call `createModerator({ name, rosterNames, transcript, tools })` from `@flow-state-dev/patterns/debate`, since it is subpath-only. Pass the same `createDebateTranscript()` result to it and to `debate({ transcript })`, then pass the moderator as `moderator`. Its default model is `intent/synthesize` (dbm:40-62). Search results reach the debaters only through the moderator's `briefing`. Passing `moderator: false` throws.
5. You use `planAndExecute` with `synthesizer: false`. Two of its three tasks fail, and the third is cancelled because it depended on one of the failed tasks. What are the output's overall `status`, each task's `status`, and `completedSteps` / `totalSteps`? *(edge case)*
   Answer: The two failed tasks read `failed`, because board `errored` maps to `failed`. The cancelled task reads `skipped`, since every `cancelled` task maps to `skipped` (paey:39-45). The overall `status` is `failed`, because every non-skipped task failed (paey:100-107). `completedSteps` is 0 and `totalSteps` is 3 (paey:92-95). The shape is `{ goal, status, tasks: [{ id, goal, status, result?, error? }], completedSteps, totalSteps }`, and each failed task's `error` is its error, or its feedback when it has no error.
6. You write your own `goalSeekLoop` with `maxIterations: 5` over a task board. Your judge throws on the second pass, and you left `onError` at its default. What happens, and what does the termination item report? What if the judge never says `done` at all?
   Answer: `onError` defaults to `"skip"`. A judge that throws ends the loop with reason `judge-error`, and `finalize` still runs. `"fail"` would propagate a request error instead. `seed` and drain failures always propagate (gsl:321,480). The termination item has type `goal-seek-loop-termination` and payload `{ collectionId, reason, iterations }`, where `iterations` counts the drains that ran (gsl:186). If the judge never says `done`, the loop stops after 5 drains with reason `max-iterations`, runs `finalize` over what has settled, and does not throw (gsl:505-512). That cap is separate from the board's own per-drain `maxIterations` (default 10,000). `maxIterations` has no default on `goalSeekLoop` and must be a finite positive integer.
