## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A notes resource is declared with `defineResource({ scope: "user", ... })` under the accessor `notes`, with no `ref` and `flowIsolation` left off. A user who belongs to two organizations writes to it while signed in to org A, then reads it while signed in to org B. Where is the row stored, does the second read see the first write, and what does `ref.uri` look like?
   Answer: The row lives at (scope type, scope id, resource key). The key is `path`, which is the accessor `notes` because no `ref` is set. The user-scope id is `<userId>:~org:<orgId>`, one cell per (user, organization), so the read in org B hits a different row and does not see the write from org A. `uri` is `${scope}/${path}` = `user/notes`. It leaves out the scope id, so both organizations show the same uri for two different rows. Only with `flowIsolation: true` would `:<flowInstanceId>` be added. (Fact sheet 5.1, 5.2, 17, 20.1)
2. A flow has two actions, `chat` and `export`. The flow declares `settings` in `defineFlow({ resources })`. A block used only in `export` declares an `archive` collection. Another block in `chat` declares `drafts` with `prefetchMode: "lazy"`. Which of these load when a request dispatches `chat`, and when?
   Answer: `settings` loads at the start of every request, before any action runs. `archive` belongs to the `export` action's block tree, so it stays untouched when `chat` runs. `drafts` is lazy, so it loads only when it is used: a lazy single resource loads when the block that declares it dispatches, and a lazy collection loads one key per access (`list(prefix)` loads that sub-tree). Undeclared resources never load, and projected collections never load a copy. Lazy changes when the data loads, not how you call it: reads are async in both modes. (Fact sheet 16, 20.2)
3. Two resources are declared. One is a single resource with `client: { content: { read: true } }` and no `expose`. The other is an `artifacts` collection with `client: { state: { read: true } }` and no projection. Both have a `secret: ["apiKey"]` field. A third resource has no `client` block at all. What can the browser read from each?
   Answer: No `client` block: nothing. The resource is left out of the session snapshot and the manifest, and its routes answer `403 … not permitted` (a `404` means the flow does not declare that ref). The single resource with no projection: no `clientData`, so its state stays private. Its content can be read through the content route because `content.read` is set. The collection with `state.read` and no projection: each item's `clientData` is the full stored state, minus `apiKey`, because a `secret` field is never sent. A collection that has `client` but no `state.read` would send only `count` and the `topic` of each item. (Fact sheet 12.1, 12.2, 20.3)
4. A handler calls `ctx.resources.files.create("readme.md", {...})` on a `files/*` collection, but another branch already created `files/readme.md` earlier in the run. Later it calls `files.get("src/utils.ts")`. What happens in each case, and how do you overwrite the existing file instead? *(edge case)*
   Answer: The `create` call throws a `FlowError` with code `resource_already_exists` (`Resource instance "readme.md" already exists`, `retryable: false`). To overwrite, pass `{ replace: true }`. That uses `setState` semantics, so schema defaults fill any fields you leave out, and it also creates the instance when it is missing. `upsert` and `getOrCreate` are the other choices for this case. The `get` call rejects with `Key "src/utils.ts" does not match collection pattern "files/*"`, because `*` matches one segment only. `getOptional` would return `undefined` instead. You need `files/**` to match nested keys. (Fact sheet 4.3, 8.1)
5. A browser user edits a shared org-scoped `teamSettings` resource while a teammate edits it at the same moment. Both read version 3. What must the resource declare before any browser write is allowed, and what happens to the two edits? *(edge case)*
   Answer: With no `runBy`, a client cannot write the resource at all. It needs `runBy: "default"` (or `{ flow: "<kind>" }`) and a `client` block that projects state (`expose`, `exclude` or `data`). An org resource on the default write flow must also declare `canWrite`, otherwise `defineResource` throws. `canWrite` gets `userId` and `orgId` from the verified sign-in, and a `userId` in the request body is ignored. When the two writes race, the loser's write is refused with `stale_version`. `update` then re-reads and re-applies it, up to three attempts. So both changes are stored. Each writer gets one write session. (Fact sheet 12.5, 12.4)
6. A handler calls `ctx.resources.usage.incState({ tokens: 500 })`, but the stored `tokens` field holds the string "n/a". A second resource is declared `writable: false` and a handler calls `patchState` on it. What does each call do, and is anything written? *(edge case)*
   Answer: The `incState` call is refused with a `FlowError` of code `resource_delta_refused`, `retryable: false`, and the message `Resource "usage" incState target "tokens" is not a number (got string)`. Nothing is written, even for the other fields of a multi-field call. A missing or `null` field would have started from 0. The `patchState` call on the read-only resource throws `resource_read_only`, also with `retryable: false`, and nothing is stored. Under concurrency, delta calls are single guarded writes: memory, SQLite and Postgres compare-and-swap in the store, but the filesystem store guards per key in-process only, so two processes can lose an increment. (Fact sheet 4.1, 4.2, 2)
