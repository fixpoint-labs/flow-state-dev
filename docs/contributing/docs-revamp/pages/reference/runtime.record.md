## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are writing your first `createFlowState({ ... })` call for a new app and want to know the least you must pass. Which fields are required, and what do you get for each one you leave out?
   Answer: None of them. Every field of `CreateFlowStateOptions` is optional; only the options object itself is required, and `createFlowState({})` builds and serves an empty app. If you leave out `flows`, the list registers no flows, though kits listed in `kits` still register theirs at start. If you leave out `stores`, the app runs in memory as the `default` profile. Start says so on stderr, and in production it warns once that sessions and requests are lost on every restart. If you leave out both `models` and `modelResolver`, a `createModelResolver()` is built from the environment at start. (Fact sheet sections 1 and 2.1-2.3; `fst:149-447`; `cfs:247-251`, `:1009-1011`, `:1024-1046`; [run] `createFlowState({})`.)
2. Your config declares `stores: { local: sqliteStores(...), production: postgresStores(...) }` and sets no `defaultProfile`. You deploy with `NODE_ENV=production` and forget to set `FSD_ENV`. Which profile does the server use, and how would you check?
   Answer: It uses `local`. The first rule that matches wins: `FSD_ENV` when it is set and not empty, then `defaultProfile`, then the first declared profile (the first key of `stores`). `NODE_ENV` is never read, so `production` is not picked. You can check two ways. Start prints `[flowstate] active profile: "local"` on stderr once per process, and `FSD_QUIET_WARNINGS` does not hide that line. The handle's `activeProfile` returns the name. To get Postgres, set `FSD_ENV=production` or `defaultProfile: "production"`. (Sections 5.2 and 18; `cfs:973-996`, `:1024-1032`; `t/createFlowState.test.ts:100-148`.)
3. A teammate sets `FSD_ENV=staging` on a server whose `stores` declares only `local` and `production`. When does this fail, what does the error say, and is a deploy with `FSD_ENV=""` affected the same way? *(edge case)*
   Answer: Importing the module and the synchronous `createFlowState(...)` call both succeed. The failure comes at start: the first `ready()`, `getRouter()` or `getRuntime()` rejects, and reading `activeProfile` throws. The error is a `FlowStateConfigError` (`code` `flowstate_config_error`), and its message reads `FSD_ENV="staging" but no profile "staging" is declared. Declared profiles: ...`. The class is not exported, so you identify it by `name` or `code`. An empty `FSD_ENV` counts as unset, so it does not fail: selection falls through to `defaultProfile`, then to the first profile. (Sections 3 and 5.2; `cfs:973-986`; [run] `ready()` and `activeProfile`.)
4. You mount Flow State in a Next.js route handler on Vercel. What do you pass to `createVercelNextHandler`, when do the database pools open, and where does a bad Postgres connection string show up?
   Answer: Pass the handle that `createFlowState` returns, not `getRouter()`. The handlers take the `FlowState` object and resolve the router on the first request. Construction is synchronous and uses no top-level await. Stores, kit folders and the router are built lazily, once, on the first `ready()`, `getRouter()` or `getRuntime()`, so database adapters open their pools at start and not at import. A bad connection string therefore surfaces at the first `ready()` or the first request. A failed start returns the same rejection on every later call, because the promise is memoized. To move that cost off the first request, call `ready()` early, for example in `instrumentation.ts`. (Sections 7.1 and 13; `cfs:1-12`, `:945-971`, `:506-516`; `vn:18-22`; `nx:43-60`.)
5. Locally, with `createFlowState` and no `stores`, an approval step calls `ctx.suspend()` and fails, although the same flow pauses fine under `fsdev dev` with no config. Why, and what are your two ways to fix it? *(edge case)*
   Answer: The `durable` option is unset, which means durable execution is on only where the stores persist. With no `stores`, `createFlowState` runs in memory, and in-memory stores declare `persists = false`. So durable execution is off, `ctx.suspend()` fails with an error that names the setting, and nothing is held. With no config, `fsdev dev` defaults to SQLite at `.fsdev/data/fsdev.db`, so durable execution is on there. The fixes: give `stores` a persisting adapter (SQLite, Postgres, filesystem), or set `durable: true` to hold pauses in memory. That second option is for tests only, and the held requests are lost when the process ends. (Sections 2.7, 5.3 and 11.1; `dd:21-31`; `createExecutionContext.ts:222-230`; `fsd:local-store.ts:3-28`.)
6. You register two copies of the same flow, one for each customer, and each copy needs a different sandbox type. Do you put that in `settings`? And how does a block read `settings` at all? *(edge case)*
   Answer: No. `settings` applies to the whole process: one shape for every flow, passed to every block as `ctx.settings`. Its type comes from declaration-merging into `FlowStateSettings` from `@flow-state-dev/core`. It cannot differ between two registered copies of one flow. For a value that differs per copy, use the flow's `config`, which a block reads as `ctx.flow.config`. The handle's `settings` returns the object you passed, or `{}`, and is read-only. A script that calls `runAction` passes settings as `runtimeConfig.settings`. (Section 6; `packages/core/src/types/block.ts:228-247`; `cfs:441-443`; `flow:798-801`.)
