## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support desk's `support` flow declares a static schedule `nightly-digest` (cron `0 2 * * *`) and runs on one long-lived Node server whose `createFlowState` call passes no `scheduler` option. Nobody has set up an outside cron. Does the schedule fire, what calls the tick, and what would change if the app passed `scheduler: false`?
   Answer: It fires. With `scheduler` omitted, the built-in local cron runs the tick every minute in a process that serves requests. It starts once a router is built (or a job queue starts processing) and a registered flow declares a static schedule or a `schedules.index`. It POSTs each due fire through the app's own router to `POST /api/flows/support/schedules/nightly-digest/dispatch`, which every app mounts with no adapter line. With `scheduler: false` nothing ticks, and an outside caller has to POST that endpoint itself. A `SchedulerAdapter` such as `vercelScheduler()` replaces the local cron (fact sheet: 'What calls the tick?' table, `fst:419-428`, `cfs:1343-1380`, `lst:73/85/146`, `bi:66`).
2. The desk has an `sla-check` schedule on `*/5 * * * *`. The server goes down at 09:02 and comes back at 09:25. What fires when it comes back: 09:05, 09:10, 09:15 and 09:20, or something else? And if the tick runs twice in the same minute, does it fire again? *(edge case)*
   Answer: It fires once, for the latest time it missed: 09:20. Earlier missed times are dropped, so there is no burst after an outage and no backfill (`sct:99`, `tick:15-17`). A second tick within the same minute sends nothing new, because the tick keeps one app-wide last-tick record and only fires times after it (`sct:88`). On a first tick with no record, it looks back only one minute (`sct:111`).
3. `nightly-digest` has no `principal` field. Whose run is it, and how would you make it run as a specific support agent instead?
   Answer: With no `principal`, the run belongs to the principal the endpoint's authentication resolved for the fire. That is the flow's `authentication.resolvePrincipal` called with `source: "scheduled"`, usually a system or gateway user (`rt:178-200`, `adt:464`). Set `principal: { userId, orgId? }` on the schedule to run as that user. If `orgId` is left out, the gateway's organization is used (`st:155-177`, `adt:431`). The run's `source` is `"scheduled"`, and its request metadata carries `schedule: { scheduleId, origin, cron, nominalFireTime, dispatchedAt, timezone }`.
4. Agent Dana belongs to two organizations, `acme` and `globex`. Working in `acme`, she creates a stored follow-up reminder through the flow's `defineScheduleCollection`. Which organization does it fire into? Can a run of hers in `globex` reach or retarget it? *(edge case)*
   Answer: It fires into `acme`. `create` records the creating run's organization in the row's `orgId`, which the caller does not set. The schedule fires into that organization, not into whichever one ticks. The run belongs to the user and organization in the dispatch id (`<orgId>/<userId>/<key>`), and the resolver reads the row from Dana's cell in `acme`. A run of hers in `globex` cannot reach it. A write that names another organization throws, and an update that moves a row to another organization takes it out of the index. A row with no organization, or one whose organization differs from the id's, does not fire (`404 schedule_not_found`; the tick skips entries with no organization) (`dsct:168/192/228`, `cell:238/314/333/357`, `rsr:151-165`, `sct:153`).
5. Dana edits her stored reminder three times. First she sets `enabled: false`. Then she turns it back on with cron `not a cron`. Then she sets `0 9 * * * *`. What happens to firing after each edit? *(edge case)*
   Answer: Edits take effect on the next tick. With `enabled: false` the row is taken out of the schedule index: it stops firing but is not deleted (`dsc:284-287`, `dsct:111`). The collection does not validate cron on write. `not a cron` is saved with a warning, and no index row is written, so the tick never fires it (`dsct:436`). `0 9 * * * *` has six fields but still parses (the sixth is read as seconds), so it is indexed and the tick sends it. The endpoint refuses each fire with `400 invalid_schedule` and the tick logs it, so it never runs. To prevent both, check the cron first with `isFiveFieldCron` and `isKnownTimeZone` from `@flow-state-dev/core/types`.
6. On Vercel, the cron route fires `sla-check` for 09:20. The dispatch fails with a 503, and a little later an outside scheduler POSTs the same 09:20 time again. Two hosts also POST the 09:25 time at the same moment. What does each call get, and does the tick retry the failed fire itself? *(edge case)*
   Answer: The tick does not retry. Delivery is at most once, and a refused or thrown fire is logged with the flow, schedule and status (`ftp:87/101`, `tick:25-26`). A fire that was not admitted, such as a 503, gives its time back, so the outside retry of 09:20 still runs, as long as no later time has fired in between (`rt:228-233`, `adt:675`, `opt:114/123`). Each scheduled time fires at most once across retries, hosts and restarts. Of the two simultaneous 09:25 calls, one gets `202 { status: "accepted" }`, which means started, not finished. The other gets `200 { status: "duplicate" }` (`opt:88`). Across processes this needs a store with cross-process compare-and-set (SQLite, Postgres). On the memory or filesystem store it holds only within one process. The Vercel route does not pass these answers back. It answers `200 { dispatched: <count> }`.

- Local scheduler: runs in any serving process every minute, fires every due static and dynamic schedule; across servers sharing a store one process ticks and each scheduled time fires once; does not run under `fsdev run`; the tick route always exists → R-33
- `schedules` flow fields: `resolve`, `index`, `static`; the clock fires only an index the flow names, so `resolve` without `index` never fires → R-05
- Who a scheduled run belongs to: a dynamic row is per user, fires as its owner in the organization it was made in, is read only through `ctx.resources.schedules`, and no client reads it by default → R-33
- Schedule collection writes: `create` with `replace` moves the next fire; `delete` removes the row and its index entry in one call; a fire claimed just before the delete runs only if its dispatch reads the row before the delete lands, otherwise it answers `404 schedule_not_found` and is dropped; `enabled: false` pauses (for R-33) → R-33 (corrected by pass 5)
- Silent-schedule causes: no `index` named under `schedules`; a cron that does not parse is saved with no index entry and a logged warning; `parseNextFireAt` returns null for it → R-33
- Missed ticks: one late fire for the latest missed time, earlier times dropped; a failed fire is dropped, not retried; a dynamic fire runs in the ticking process and is lost if that process crashes mid-run → R-33
- Scheduled caller identity: the principal must name an organization or the call is refused; resolvers branch on `ctx.source === "scheduled"`; a scheduled handler is not in `actions`, so the dispatch endpoint is the only way to run it → R-33
- Tick cadence on Vercel Cron: the cron entry sets tick frequency only; a schedule fires on the first beat after its time (`0 8 * * *` on a 15-minute beat runs 08:00 to 08:15) → R-33
- Cron and dispatch authentication: bearer `CRON_SECRET` sent by Vercel and by the tick on each dispatch; wrong or missing secret returns `401` from both; an unset secret makes the cron route refuse every call and `createBearerSecretPrincipalResolver` throw at load; rotating means changing the variable and redeploying → R-20
- Tick endpoint response: `200` with `dispatched` counting fires sent, not fires that succeeded; `0` is normal between beats; each scheduled time fires at most once → R-33
