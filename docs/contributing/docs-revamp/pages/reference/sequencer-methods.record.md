## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. In the support desk, `handleTicket` has `.parallel({ order: lookUpOrder, tone: classifyTone })` followed by `.step(draftReply)`. What value does `draftReply` receive, and what would you write instead if you wanted the two results as an ordered list?
   Answer: An object with one key per branch, in the order written: `{ order: <lookUpOrder's output>, tone: <classifyTone's output> }` (a key is `undefined` if that branch's block returns nothing). Both branches got the same input, the previous step's value, because neither has a `{ connector, block }` form. It is not an array; `.stepAll([lookUpOrder, classifyTone])` gives an array, one entry per block, in the order given. (Fact sheet section 2 `parallel` and `stepAll` rows; section 9, first lookup.)
2. Same `.parallel()` step: the order service is down and `lookUpOrder` throws. What happens to the step and to `classifyTone`, and how do you let `draftReply` still run with a fallback for the order? *(edge case)*
   Answer: The whole step throws `lookUpOrder`'s error, so the chain fails there. `classifyTone` is not cancelled: it runs to the end in the background and its result is dropped. To contain the failure, put a per-branch rescue on the branch's block, `lookUpOrder.rescue([{ block: orderFallback }])`. The failure becomes that branch's recovery value and the step succeeds, e.g. `{ order: <fallback>, tone: ... }`. A sequencer-level `.rescue()` would not do this: it ends the chain at the failure and its output becomes the sequencer's output. (Section 2 `parallel` and `rescue` rows; section 1 row 6.)
3. After `draftReply`, `handleTicket` calls `.sideChain(logTicketAnalytics)`. The analytics service rejects the write and `logTicketAnalytics` throws. Does the customer's request fail? Where does the failure show up, and what would make it fail the chain? *(edge case)*
   Answer: No. The request ends `completed`, the next step got the same value `sideChain` was given, and nothing reaches the customer's stream (no `error` item). The failure shows as a failed `block_trace` row (status `failed`, with the error message), marked `provenance.phase: "sideChain"`, and a server log line `[runAction] Background work "<name>" failed: <message>`; request-end hooks get `backgroundFailures` (see the background-work reference). To turn it into a chain error, add `.waitForSideChain({ failOnError: true })`: it waits for every side chain this sequencer queued to settle, then throws the first failure, which a `.rescue()` can catch. Exception: in a request working a dispatched task, the failed background step fails that task's attempt. (Section 5 D3, D4, D1; section 9, second lookup.)
4. `handleTicket` pauses before sending with `.waitForCondition(whenResourceChanged({ scope: 'session', path: 'approval' }), { timeoutMs: 60000 })` until a human agent approves the draft. What does the wait resume on, and what does the step after it receive?
   Answer: It checks the predicate once on entry against the items already on the request; if true it continues at once. Otherwise it re-runs the predicate on every item event (`added`, `updated`, `done`), narrowed by `wakeOn` if given, and resumes on the first of: the predicate returning true; 60 seconds elapsing; the request being aborted. The next step receives `{ timedOut: boolean }`, not the draft: `true` on timeout, `false` when the condition was met and also when the request was aborted (check `ctx.signal.aborted` to tell those apart). It never throws on timeout; a predicate that throws ends the wait and the error propagates out of the step. It only sees this one request's items. (Section 4; section 9, third lookup.)
5. You edit `handleTicket`, changing `.tap(saveDraft)` to `.sideChain(saveDraft)` so the reply is not held up by the save. What changes for the next step, and what if a later step must read what `saveDraft` wrote? *(edge case)*
   Answer: With `tap`, the next step starts only after `saveDraft` finishes and a throw fails the chain. With `sideChain`, the next step starts at once and a throw fails neither the chain nor the request. In both cases the next step gets the previous value unchanged, whatever `saveDraft` returns. The next step does not wait for the side chain implicitly; to order a later step after its side effects, put `.waitForSideChain()` before it (optionally with `timeoutMs`, which rejects the wait with `waitForSideChain timed out after <n>ms` while the task keeps running). (Section 5 D2, D1, D3 'May not'.)
6. `cleanMessage` is a handler with `retry: { maxAttempts: 3 }`, used as `.step(cleanMessage.rescue([...]))` inside `handleTicket`, and it throws on a flaky call. How many times does it run before the rescue takes over? *(edge case)*
   Answer: Once. A step's `retry` setting does nothing inside a sequencer: the engine applies `retry` only to the block an action runs. The step's `.rescue()` runs on its first failure, and the chain continues with the rescue handler's output as that step's output. Only if the sequencer (or block) the action points at retries does a whole run repeat; on that root block a `.rescue()` runs after the last attempt, or at once for a non-retryable error. (Section 6 E3; section 1 row 13.)
