## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A support-desk block calls `ctx.session.patchState({ status: "open" })` while the session already holds `status: "open"`. What does the call return, and does anything else happen (a stored write, a version bump, a `state_change` item)?
   Answer: It returns `false`: the proposed state is structurally equal to the current state, so it is a no-op. Nothing is written, the version does not advance, and no `state_change` item is emitted. `true` would mean the write was sent, the version went up by one and one `state_change` item was emitted. Fact sheet sections 2 and 3: `sco` no-op guard, `emit` returns `false` before emitting, `t/state-container.test.ts:124-175`.
2. Two requests in the same support session handle tickets at the same moment. Each runs `ctx.session.incState({ replyCount: 1 })` on a stored `replyCount` of 0. Then the same two requests each run `ctx.session.patchState({ assignee: ... })`, one with "ana" and one with "ben". What does the session hold afterwards for each field, and what did each call return? *(edge case)*
   Answer: `replyCount` is 2. A single-field `incState` goes to the store as one add, so both deltas land and both calls return `true`. `assignee` holds whichever value reached the store second, and the first is gone. A single-field plain-value `patchState` is last-write-wins: both calls return `true` and nothing is raised. Fact sheet section 6 table ([ran] rows) and the last-write-wins lookup.
3. A block counts replies by reading `ctx.session.state.replyCount` and then calling `patchState({ replyCount: count + 1 })`. Under concurrent requests, why does this lose updates, and what should it call instead?
   Answer: A single-field `patchState` is a blind write of the value the block computed, with no version. When two requests read the same count, both write count + 1, the last write wins, and one increment is lost. `incState({ replyCount: 1 })` adds in the store and both increments land. A read-then-write that has to be safe can also use `atomicState` or `patchState(key, updater)`. Those are version-checked and re-run against the winning value. Fact sheet sections 5, 6 and 16 row 5.
4. A block assigns a ticket with `ctx.session.patchState("assignee", (c) => c ?? "ben")`, but another request has just stored `assignee: "ana"` and this context's copy still shows nothing. What happens, what is stored, and what does the call return? What must the updater be careful not to do? *(edge case)*
   Answer: The write is version-checked. It loses the race, re-reads the record and runs the updater again against the stored "ana". The updater returns "ana" unchanged, so the call is a no-op: it returns `false`, and "ana" stays stored. Because the updater can run more than once, it should be a pure function of the state it receives and write nothing outside it. Fact sheet section 6 ([ran] updater row) and the "Facts behind the table" retry bullet (`cas:164-222`, `mm:218-264`).
5. A burst of conflicting `atomicState` writes on session state keeps losing the version race. When does the call give up, what does it throw, and how would you identify the error in a catch? Is request state configured the same way? *(edge case)*
   Answer: It retries up to `cas.maxRetries` times, 3 by default, with waits of 10, 20 and 40 ms (`baseDelayMs` 10, doubling). When the retries run out it throws `ConcurrentModificationError`, exported from `@flow-state-dev/engine`, with `code` "concurrent_modification" (lowercase), `retryable: true` and `attempts` equal to retries + 1. You set `cas: { maxRetries, baseDelayMs }` per scope on the flow's `session`, `user` and `org` config. Request scope has no `cas` option. Single-field `incState`, `pushState` and the other writes that carry no version never raise this error. Fact sheet section 6.
6. A block calls `ctx.session.incState({ replyCount: 1, escalations: 1 })`, but `escalations` holds the string "none". What happens to `replyCount`? Separately, what if the block assigns `ctx.session.state.replyCount = 5` directly? *(edge case)*
   Answer: `incState` throws a plain `Error` with the message `incState target "escalations" is not a number (got string)`. The whole call is refused, so `replyCount` is not incremented either and nothing is persisted. Assigning to `ctx.session.state` does not throw: the state is read-only only as a type. The assignment changes this context's copy, so a later read in the same context gives 5, but it is never stored. State changes only through the seven operations. Fact sheet sections 1 (what throws) and 8.

- Case 'The record is gone': "A write to a session, user or organization record that has been deleted is not recreated." Untrue: Only the single-operation writes (incState/pushState/single-field patchState/setStateRecord/deleteStateRecord) fail on a missing record: the store's delta verb reports a conflict with no current value, and runCommutative returns false. setState, atomicState, patchState(key, updater) and multi-field patchState/incState go through runWithCAS. A set against a missing record conflicts with currentVersion 0, the container is committed to version 0, and the retry's set with expectedVersion 0 is admitted, because an absent record reads as version 0. - Block state lives for one execution of its block and is gone when that execution finishes. It is never persisted, and no other request can see it. (Ordering-by-scope section, applied to ctx.sequencer and ctx.self.) Untrue: Sequencer state is written into durable sequencer checkpoints. A resumed continuation restores it from the checkpoint, and only fields marked transientSlot() are left out of the checkpoint and reset to their defaults. So ctx.sequencer state is persisted across a suspension and resume, and it is not gone when the first execution stops. The 'never persisted' claim holds for transientSlot fields and for a handler's own ctx.self, which is not in the checkpoint. It does not hold for all block state. The never-persisted claim is untrue for non-transient sequencer fields.
