## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Alice works in two organizations, acme and globex. In acme she saves a preference to her user state. Does a flow run for her in globex read it, and where is each record stored?
   Answer: No. The user record key is `<user>:~org:<org>`, so Alice has two cells: `alice:~org:acme` and `alice:~org:globex`. Each is a separate row in `stores.user` (table `users`), and user-scoped resources are keyed under the same cell. The same user id in two orgs reads and writes different user records (sections 0 and 4, `user-cell-keys.test.ts:47-52`).
2. Alice and Bob both work in acme, under one tenant. The app builds session ids from the ticket number only. Both open ticket 42 and the app creates session `ticket-42` for each. What happens to Bob's create? *(edge case)*
   Answer: Only the session id is in the session's key (plus the tenant prefix when there is one). User and flow are not part of it. Alice's create gets `201`. Bob's gets `409`, and reading the id returns Alice's record, or `403` when authentication is on. Two concurrent creates at `"absent"` let exactly one win. The fix is to derive the id from everything that tells sessions apart, such as user, org, flow and ticket (sections 4, 7.2 and 8).
3. A support app wants to find Alice's existing session for ticket 42 without listing every session and filtering on the client. Can it filter on session `metadata` on the server? If not, what lookup does exist?
   Answer: No route, client option or `SessionListOptions` filters on `metadata`. A caller has to list sessions and filter `metadata` in memory. The server-side lookup is readonly session state. Declare the key as a `.readonly()` field of the flow's session `stateSchema`, set it at create, and call `sessions.list({ flowKind, state: { ticket } })`. The store filters on it in its query. A filter with no `flowKind`/`flowId`, or on a field that is not readonly on that flow, is refused with `400` and is never silently ignored. The other option is a derived session id with create-if-absent, where `409` means it already exists (section 9).
4. You are writing a custom Postgres-like store. Two requests from different tabs create the same session id at the same moment, and two processes try to resume the same paused request. What must your store do atomically for each? *(edge case)*
   Answer: Session create: scope `set(id, value, "absent")` must compare and write in one step. Exactly one create wins, the loser gets back the winner's record as `{ ok: false, conflict: { currentValue, currentVersion } }` rather than an error, and the route answers `201` to one and `409` to the other. Resume: lease `acquire` must grant at most one active lease per request. Of two concurrent first acquires, exactly one succeeds. An expired lease can be taken over, and a stale holder's release must not free a newer holder's lease. Other atomic steps are `setFieldsIfStatus`/`deleteIfStatus` (check status and write), resource-state version check plus write with its index entries, a settling `set` that lands items with the status, and wake `move`/`clear` at the version read (section 7.2).
5. An auditor asks which stored records carry acme's organization id, and how a suspension (Alice's pending refund approval) is tied to acme.
   Answer: Session, request and active-request entry each have `orgId`/`org_id`, stamped on every new record (legacy rows may have none). A wake's `org_id` is required, NOT NULL. A schedule-index row stamps `org_id`, and a row with none is quarantined. The org record uses the org id as its key. User records and user- and org-scoped resources carry the org inside their key or `scope_id`. Suspensions, checkpoints, leases, runOnce results, items, events and traces have no org column. They reach the org through their request, so a suspension is tied to acme by joining to its request (section 5, 14a).
6. Alice's refund approval run is paused on the default in-memory store, and the server restarts. Then the team moves to the filesystem store and runs `fsdev run` while `fsdev dev` is open on the same folder. What survives, and what breaks? *(edge case)*
   Answer: With no `stores` set, the app runs on `inMemoryStores()`. Durable execution is off by default there, and the checkpoint and suspension die with the process, so the run cannot continue after the restart and nothing is left to mark `interrupted`. A production app that never set `stores` also logs a warning. The filesystem store survives a restart, but it is single-process. Its locks live on one store instance, and two instances over one directory are not coordinated. Both create-if-absent calls can succeed, or one record can overwrite another, so `run` and `dev` cannot share it. SQLite allows one writer at a time: a second writer waits up to 5000 ms, then fails with `SQLITE_BUSY`. Postgres is shared across processes (sections 1.1, 2.1, 8, 14).
