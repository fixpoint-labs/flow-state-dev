## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You build a board named "research" and set neither `concurrency` nor `claimOrder`. You file three tasks: "fetch-a", "fetch-b", and "summarize", which lists both fetches in its `deps`. How many tasks can run at once, which one is picked first, and when can "summarize" start? Would `claimOrder: "topological"` change the answer?
   Answer: `concurrency` defaults to 4, so the board starts four workers and each one claims, runs and checks in its own loop (fact sheet 1.2, 4). `claimOrder` defaults to `"fifo"`: the ready task created earliest goes first, and ties break on id (4.3.2). A task can be claimed only when it is `pending`, is not `held`, has no open hold, and every id in its `deps` is a task on the board with status `completed`. So "summarize" waits until both fetches are `completed` (4, Readiness). There are only two claim order names, `"fifo"` and `"priority"`, or a `ClaimOrder` object of your own. `"topological"` is not one of them, and `taskBoard()` throws `unknown claim order name` (0.1, 4.3.1).
2. On the same board, the worker for "fetch-a" throws. The task has no `maxAttempts` and `onError` is left at its default. What happens to "fetch-a" and to "summarize", does the run fail, and what stop reason does the drain report? *(edge case)*
   Answer: With `maxAttempts` unset, a failure is final, so "fetch-a" goes to `errored` (5.1.1). The default `onError: "skip"` writes the failure to that task and the other tasks carry on (1.2). The cascade cancels "summarize": it becomes `cancelled`, labelled `"skipped"`, with `causedBy` set to "fetch-a" and `error` reading `dep fetch-a failed` (2.3.1). The drain ends normally. The run fails only under `onError: "fail"`, which rethrows (2.3.8, 1.2). The final `task-board-meta` item reports `terminationReason: "blocked-by-failures"` (3.1, 2.3.8).
3. You file "fetch-a" with `maxAttempts: 3` and its worker throws on the first try. What does `maxAttempts` change, what does the next attempt see, and what happens if the board has already used up its `maxTotalRetries`? *(edge case)*
   Answer: While a task has attempts left, a failure sends it back from `in_progress` to `pending` and clears its `error`. The error text is kept as `feedback`, and the next attempt receives it as `TaskWorkerInput.feedback` (5.1.2). Each such retry spends one grant of the board's `maxTotalRetries`, which defaults to 50 across every task. Setting it to `0` means nothing is ever retried, and `null` removes the limit (5.2). When the attempts run out, the task goes to `errored` (11). If the budget is already spent, the next failing task goes to `errored` with `not retried: ... has spent its retry budget of <n> (maxTotalRetries)` and `retryLedger.deniedByBudget: true`. The drain then ends normally with `terminationReason: "retry-budget-exhausted"` (5.2, 3.1 order 1). On a durable `defineTaskCollection` board, retries are counted but the budget is not enforced (5.2).
4. The worker for "summarize" asks the user a question partway through its run, and nothing else on the board is left to do. What status does the task show, which stop reason does the drain report, and how does the work continue once the user answers? Does the answer change if "fetch-b" has failed? *(edge case)*
   Answer: Waiting on a user is not a separate status. The task keeps its status, here `in_progress` with no lease, and gains a hold with `actor: "user"`, which `getTask` and `listTasks` show as `holds` (2.1.1, 2.1.2). The drain stops and the final `task-board-meta` reports `terminationReason: "waiting-on-a-user"`. Nothing went wrong and nothing is finished, and the next drain after the answer picks the task up (3.1, 3.1.2). For that next drain to find the task, the list has to outlive the request, so use a resource-backed `defineTaskCollection` board. A request-backed list ends with the request (3.4.2, 6). If "fetch-b" failed, or any task is `errored`, `cancelled` or `held`, that check comes first and the drain reports `blocked-by-failures` instead (3.1.1).
5. After "fetch-a" has started, you call `updateTask` to raise its `maxAttempts`. Later, once "fetch-b" has `completed`, you call `updateTask({ id: "fetch-b", status: "cancelled" })`. What happens to each edit? Apart from `updateTask`, what else can cancel a task? *(edge case)*
   Answer: `maxAttempts` can be edited only before the task first starts, so the first edit is refused (5.1.4). A terminal task cannot be cancelled. The cancel is advisory and returns `task_finished` (2.2). A cancel is sent with no other field, and it is allowed until the task finishes (2.2). Other things that cancel a task: a confirm answered No when its `onNo` is `"cancel"`, which is the default; a worker throwing `TaskEndsForGoodError` with `ending: "cancelled"`; a cascade from a task it depends on that failed for good or was cancelled; stopping the run of a task that waits on a user; and stopping a conversation whose turn is waiting on the task (2.2, 11). To bring back an `errored` or `cancelled` task, use the `retryTask` action, which returns it to `pending` (2.1, 5.1.7).
6. You want the task list to last beyond one request, so a user can come back to it later, and a second user of the same app should have a list of their own. Which `collection` choice does this, how long does each choice last, and what do you give up? *(edge case)*
   Answer: The default request-backed list lasts for the request, and a new request starts empty. `{ backing: "sequencer" }` lasts for one `board.drain` call. A factory lasts as long as your own store keeps it (6). `defineTaskCollection({ id, scope: "user" })` stores the tasks as resources, so they outlive the request. The scope is one user within one organization, across every flow of that user unless isolated, so a second user gets a separate list. `"session"` scope would limit it to one session, and `"org"` would share it across the whole organization (6). The trade-off is that a resource-backed board enforces none of `maxTotalTasks`, `maxEnqueuedTasks` or `maxTotalRetries`. Passing them beside a supplied `defineTaskCollection` throws, and the meta item reports `maxTotalRetries: null`. `maxInstances` caps how many tasks exist at once instead (6, 5.3.5, 1.2).
