## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. A worker claims the task "summarize-sources" on a board and then its process crashes mid-run. No one calls fail or reclaim. What happens to the task, and does the crash count against its maxAttempts: 3? *(edge case)*
   Answer: The task stays in_progress; it does not move back to pending. Once its lease lapses (default 120,000 ms, about 2 minutes), the next claim takes it in place as a new attempt: attempts goes up by 1 and abandonments goes up by 1. The abandonment allowance is separate from maxAttempts, because fail retries only while attempts - abandonments < maxAttempts. So the crash leaves all three failure retries. The allowance is 3 recoveries (DEFAULT_MAX_ABANDONMENTS). The next claim that finds the task lapsed after that settles it errored with "was abandoned by its worker 3 times", so it runs at most four times. Facts 0.5, 6.4.1, 6.4.2, 6.2.1.
2. Two drains working the same board race to claim "summarize-sources". Can both run it, and what does the losing claim see? *(edge case)*
   Answer: Only one gets it: the claim is a single conditional write, and the losing claim returns null, which is not an error. Two concurrent claims over two tasks return different tasks. That is a limit of one holder at a time, not exactly-once dispatch. If the holder's lease runs out (a crash or a stall), the task goes to the next claim and the work can run twice. Only the attempt that holds the claim can record a result: a ticketed write from a worker that lost the task declines lost-claim. Side effects the losing worker already caused still stand. Within one process this holds. For a board shared by two OS processes, use SQLite or Postgres, not a filesystem store. Facts 6.1.2, 6.1.6, 6.3.1, 6.3.2, 6.2.4, 6.3.4.
3. "write-report" was filed with deps: ["gather-sources", "check-facts"]. When it starts, what does its worker get from those two tasks, and does it see the tool calls they made?
   Answer: It cannot be claimed until both dependencies are completed (a dependency that is missing counts as unmet). The worker input carries deps as a Record keyed by dependency task id, holding each dependency's output. The key is present only when at least one dependency has an output that is not undefined. When none does, the key is absent rather than {}. Whether it sees earlier tool calls depends on the board's flow policy. The board's default, flowPolicy.declaredDepsOnly(), selects the observations made by the tasks in deps and puts them on priorWork. priorWork is absent when nothing is selected. The board never injects prior work into a prompt; surfacing it is the worker's job (formatPriorWork can render it). Facts 8.1, 10.1 (deps and priorWork rows), 10.2.2, 10.2.4, 10.2.7.
4. "gather-sources" fails for good. What happens to "check-facts" and "write-report", which depend on it, and what does retrying "gather-sources" do to them? *(edge case)*
   Answer: A task that fails for good (or is cancelled) cancels every open task that depends on it, and then their dependents, down the chain. Each one becomes cancelled, gets the label skipped, gets error "dep gather-sources failed" and gets causedBy set to the failed task. A retry of "gather-sources" (retry(id), which sets it back to pending) cancels no dependents and does not bring back the ones already cancelled. They stay cancelled until each is retried too, and retry on a task undoes its skipped label and causedBy. A dependent's retry is declined dependency-ended while its dependency is still failed. Facts 8.3, 8.7, 3.6, 3.7.
5. After "write-report" has been claimed once, the filer wants to change its goal and its deps. Then, after it completes, the filer wants to add a label. Which of these go through? *(edge case)*
   Answer: goal and deps can change only until the task first starts. A task has started once it has been claimed (startedAt set or attempts > 0), and a retry back to pending does not reopen those fields. Through the task tools the edit is refused field_locked_after_start, and patchSettings declines started. Once a task has finished, every field the filer can edit is refused (task_finished or terminal). Labels are the exception: addLabel, removeLabel, setPriority and patchMetadata are collection methods outside those rules. They write to a finished task and answer only recorded or unchanged. Facts 2.4, 4.1 (patchSettings, setPriority row), 7.2.1, 13.3.
6. A seed handler files "gather-sources", "check-facts" (deps: gather-sources) and "write-report" (deps: both) in one createTasks call, but check-facts names a dependency id that does not exist. What gets filed? *(edge case)*
   Answer: Nothing. createTasks checks every row before writing any. Ids in the same batch count as on the board, so the chain itself is fine. The dependency on an unknown id breaks the rule, and the call throws TaskFilingRefusedError with rule dependency_not_on_board and the taskId, filing none of the batch. Other rule codes include dependency_ended and dependency_loop. On the resource backing, a store failure partway through the insert (not a rule refusal) can leave the earlier rows in place. On the state backing the insert is one write. Facts 4.2.1, 4.2.2, 4.2.4.
