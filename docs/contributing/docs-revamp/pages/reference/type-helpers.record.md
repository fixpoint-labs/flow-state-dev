## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support app's browser code lives in src/lib/support-client.ts. You want a TypeScript type for the input of supportFlow's "reply" action, without pulling server code into the browser bundle. What do you write, and where do you import each piece from?
   Answer: `type ReplyInput = ActionInputOf<typeof supportFlow, "reply">`, with `ActionInputOf` imported from `@flow-state-dev/client` and `supportFlow` imported as a type only (`import type { supportFlow } from "../flows/support/flow"`), so no server code reaches the browser bundle. Facts section 3 lookup (cl:300-306, cl-rd:70-82) and section 10.
2. A server-side test needs the same "reply" action input type, and also the input type of the draftReply block directly. Which helpers give you each, and from which import paths? Does `BlockInput<typeof draftReply>` include `tone`, which has `.default("friendly")`?
   Answer: For the action: `FlowActionInput<typeof supportFlow.actions.reply>`, imported from `@flow-state-dev/core/types` (the subpath, not the core root). For the block: `BlockInput<typeof draftReply>` from `@flow-state-dev/core`. It gives `{ ticketId: string; tone: "formal" | "friendly" }`. `tone` is present and non-optional, because the helper reads the schema's output side (`_output`), where defaults are filled in. Facts sections 0, 1, 3 and 10 (ft:949, blk:1448, aet:21-27).
3. A teammate calls `createClient({ userId }).flow<typeof supportFlow>("support").send("replly", input)`, misspelling the action name. Another passes `{ ticket: "t-1" }` as the input. What happens to each? And what if they had written `.flow("support")` with no type argument? *(edge case)*
   Answer: With the type argument, both fail to compile. `send` takes the action as `ActionNameOf<TFlow>` and the input as `ActionInputOf<TFlow, TAction>`, so an unknown action name or a wrong input shape is a compile error. Without the type argument the handle is untyped (`UntypedFlow`): any action name is accepted and the input is `unknown`, so neither mistake is caught. Facts section 3 (clt:161-170, cl:292-293, cl:431-445, cl-rd:78-82).
4. You write a shared helper, `logTicket(ctx)`, that several different blocks call with their own `ctx`. Those blocks declare different session state, resources and capabilities. An older doc says to type the parameter as `LooseBlockContext`. What type should the parameter have, and will each block's ctx be accepted without a cast? *(edge case)*
   Answer: `LooseBlockContext` does not exist; no package defines or exports it. Type the parameter as plain `BlockContext` from `@flow-state-dev/core`. Every parameter of `BlockContext` defaults to an open record or map, so every typed ctx a block factory produces is assignable to it. That holds whatever the block declared (request, session, user or own state, capabilities in `uses`, resources, targets), so no cast is needed. Facts sections 1 and 7 (bca:1-50, blk:326-345).
5. A tickets resource collection is declared with `client: { expose: ["title"] }`. In React you read one item with `useResourceCollectionItem(session, "tickets", id)`. What type is `clientData`, how do you make it typed, and what happens if you then read a field like `secret` that was not exposed? *(edge case)*
   Answer: Without a type parameter, `clientData` is `unknown`. Pass the projection: `useResourceCollectionItem<ClientDataOf<typeof tickets>>(...)`. `ClientDataOf` gives `{ title: string }`, which is `Pick` of the state by the `expose` list. Reading `secret`, which was not exposed, is a compile error. `ClientDataOf` is compile-time only and changes no data; the runtime payload stays `JsonValue`. Facts section 2 (fct:76-87, res:413-441, re-rd:194-197).
6. Inside a block you call `ctx.session.patchState({ status: "open" })`, but the session's status is already "open". What does the call return, and is a `state_change` event emitted? Which type describes these methods? *(edge case)*
   Answer: It returns `false`. Every `ScopeStateOps` method resolves to a boolean: `true` when the write changed state, `false` when the new value is structurally equal to the current one. In that case the write and its `state_change` event are skipped. `ScopeStateOps<TState>` describes the methods: `patchState` (two forms), `setState`, `incState`, `pushState`, `setStateRecord`, `deleteStateRecord` and `atomicState`. Facts section 2 (st:25-48).

- Block definition: schema parameter defaults, no `run` method (a handler cannot call a block), and a sequencer's builder extends it so it is accepted wherever a definition is → R-01
- Block context type: parameter order (request, session, user, org, resources, sequencer state, parent input, targets, capabilities, own state); each defaults to an open record, so any block's ctx is accepted → R-01
- Block result: the four `status` values and the fields each carries (`output`, `error`) → R-01
- Return value of every state operation: true on change, false on an equal value, and a false write emits no `state_change` event → R-07
- State operations: the full method list with call signatures (the type-helper page keeps only the type name) → R-07
- Scope handle members per scope: which of identity, lineage, metadata, items, window, journal, incarnation, attachments, token usage and cost each scope exposes → R-07
- Resource handle members: read-only `state`, the write operations, and `edges` only when the resource declares edges → R-08
- Client projection typing: expose gives Pick, exclude gives Omit, `client.data` gives the function's return type, a projected collection with `expose` is not exact; a key not exposed does not compile → R-08
