## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Your support-desk flow has a web search step and a knowledge-base step, and each returns a list of articles. You want one deduplicated list and you don't want to write a handler or call a model for it. Which utility block do you use, and what if the thing you need is a reshape rather than a merge?
   Answer: Use `utility.combiner`. It is a handler with no model. It takes an array of artifacts, or `{ artifacts: [...] }`, and returns `{ combined, mergeNotes? }`. When every artifact is an array, it concatenates them and then deduplicates by value. Object keys are sorted before comparison, so two equal objects count as one. For any other reshape, no utility block does it without a model. Use a sequencer's `.map()` instead. (Facts 0.11, 3.8)
2. You route support tickets with `utility.intentRouter` into `billing` and `technical`, with `confidenceThreshold: 0.7` and no `fallback`. A ticket comes back classified `billing` at confidence 0.62. What happens, and what does the `billing` handler receive when the router does choose it? *(edge case)*
   Answer: 0.62 is below the threshold. The check is a strict `<`, so a confidence exactly equal to the threshold passes. With no fallback, the router throws when the request runs, not at construction: `intentRouter "<name>" classified "billing" with confidence 0.62, below threshold 0.7, and no fallback handler was provided`. When a handler is chosen, it receives the original input, not the classification. Its own `connectInput` still applies to that original input. With no threshold set, the top category always wins. (Fact 3.11)
3. You dispatch to per-team blocks with `utility.keyedRouter`, and `select` returns `"toString"` for a malformed ticket. There is no `fallback`. What happens? And does keyedRouter call a model, or reshape the input for the team block? *(edge case)*
   Answer: Only own properties of `blocks` count, so `toString` is an unregistered key. With no fallback it throws `[keyedRouter] no block registered under key "toString" in router "<name>". Available: <keys>`. With a `fallback` set, the fallback runs. keyedRouter calls no model and does no input adaptation. To give a block a different shape, call `block.connectInput(...)` on that block first. An error thrown by `select` itself propagates unwrapped. (Fact 3.10)
4. You add `utility.sessionTitleGenerator` to the chat sequencer so each support conversation gets a title. How do you wire it so the reply isn't delayed? What does `messageLimit` count? And what happens on a later run when the title is already good, or the model returns an empty string? *(edge case)*
   Answer: Wire it with `.sideChain(block)`, so it runs after the answer without delaying it. `messageLimit` (default 4) counts conversational turns, not messages. The model's title is trimmed and is written with `ctx.session.setMetadata({ title })` only when it is non-empty and differs from the current title. A title that is the same or empty writes nothing. When a title is written, a `session.metadata.changed` event goes out and `useSession` refreshes it live. The default model is `openai/gpt-6-luna`, and the block takes no `outputSchema` or `itemVisibility`. (Facts 0.4, 3.13, section 4)
5. An agent tool lets one user's assistant answer from another of their conversations, using `utility.consultSessionHistoryTool()`. The model passes the id of a session that belongs to a different user. What comes back, does a model run, and is anything written to that other conversation? *(edge case)*
   Answer: It returns the refusal `{ ok: false, error: "no_session: no conversation \"<id>\" of yours." }`. A missing session and another user's, org's or tenant's session read the same way, so the tool never reveals whether someone else's session exists. No model runs for a refusal. The tool never writes to, runs or wakes the other conversation. Passing the asking conversation's own id is refused with `self: ...` instead. A session with no finished turns returns a reading with `turnsRead: 0` and no model run. (Fact 3.14)
6. A ticket triage block uses `utility.cascadingRouter` with root level `{ ask: teamEvaluator, on: "team", branches: { billing: { minConfidence: 0.8, block: billingDesk } } }`. The evaluator answers `billing` with confidence exactly 0.8, then on another ticket answers `billing` with no confidence at all. What runs each time, and how does the second case show up in the trace? *(edge case)*
   Answer: The floor is inclusive, so 0.8 opens the `billing` edge and `billingDesk` runs with the router's original input. When no usable confidence is reported, the result is `ambiguous`, with or without a `minConfidence`, so the required `ambiguous` block runs. A choice's `probabilities` is never read as confidence. The gate records the verdict `{ level: "root", on: "team", ambiguous: "no-confidence", choice: "billing" }`. A provider error does not go to `ambiguous`. It fails the router. (Fact 3.12)
