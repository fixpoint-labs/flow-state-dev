## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are adding a `roster` view to the `workforce-roster` flow, and you want it to list each user's workers whether or not that user has a session. Which scope values can you give it? Which one fits here, and what does a caller leave out of the call?
   Answer: A view has exactly three scopes: "session", "user" and "org" (vt:19, dv:39-41). The roster is `scope: "user"` (rr:49-60, dv:25-31). A user view runs at the caller's user scope with no session, so the call carries no session id. It goes to `POST /api/flows/<flow>/views/<view>`, and the caller's user and org come from the verified principal, never from the body (vt:30-35, vr:3-6, vr:17-19).
2. A teammate declares `defineView({ scope: "team", block: notesBlock })`, and `notesBlock` has no `outputSchema`. What happens, when does it happen, and which problem does the error name? *(edge case)*
   Answer: `defineView` throws a plain `Error` right at the call, before any screen asks. It checks in a fixed order: config object, scope, block, output schema, key. The scope comes first, so the error names the scope: `defineView: scope "\"team\"" is not "session", "user" or "org".` The missing output schema is never reported, because the scope check fails before it (dv:36-54, dv:39-44, dvt:44-48).
3. Which mistakes in a view declaration does `defineView` refuse at definition time? And which of these does it NOT catch then: a block that writes a resource, a block that calls a model, an `inputSchema` that is wrong, a `key` that returns duplicate ids?
   Answer: It refuses a config that is not an object, a scope other than session/user/org, a `block` that is not a block, a block with no `outputSchema` (or one that is `z.any()`/`z.unknown()`), and a `key` that is not a function (dv:36-54, dvt:32-48). `defineFlow` also refuses a `views` entry that `defineView` did not return (df:862-885). None of the four listed cases is caught at definition time. A write fails with 409 `read_only` and a model call with 422 `view_model_call`, both when the view runs (ev:330-352). `inputSchema` is never checked when the view is declared. Duplicate keys are checked on each answer and fail with `view_answer_not_keyed` (rv:248-266).
4. The roster declares `key: (entry) => entry.id`. One day the block returns two workers that share the id "w1". What does the screen's call get back? And what happens if the block returns a single object instead of a list? *(edge case)*
   Answer: Both cases fail with 422 `{ error: "view_answer_not_keyed" }`. The error is not retryable. A view that declares a `key` must answer with an array whose rows have distinct string keys. The repeat gives `View "roster"'s rows must have distinct string keys; "w1" repeats`. The non-list gives `View "roster" declares a \`key\`, so its answer must be a list` (rv:248-266, vr:258-260, ev:355-362).
5. Alice has never had a session. Bob wrote an org note. Alice calls the org notes view. What does she get, and does the call create a session for her? What if she calls it with a session id in the path? *(edge case)*
   Answer: She gets Bob's note. An org view answers a user with no session, never creates one and never calls the session store: `calls` stays `[]` (ev:237-262). Called with a session id, a user or org view is refused with 400 `view_takes_no_session` (vr:121-126). A user in a different org would get an empty answer, because a second org reads none of the first org's user or org rows (er:173-182).
6. Alice's screen is watching the user-scoped `roster` view. Bob hires a worker in another tab, then Alice edits one of her own workers from a different client. Which of these makes her screen read the view again? And what does the screen show if that read fails? *(edge case)*
   Answer: Only Alice's edit does. A user view answers each user their own rows, and another user's change does not wake it: a second user's hire wakes none of the first user's view calls (goal:13, ev:264-278). A write from any client or request to something the last run read reaches the view, and the roster is read again on a hire, edit, fork or fire (rr:10-12, em:501-538). If the read fails, `useView` reports `stale: true` with a `failure` giving the reason, and tries again on its own: after 1 s, doubling up to 30 s. A read that lands clears `stale` (lr:14-16, bo:8-15, uv:40-44).

## 5 · Fact check

Checked against the code: the page as pass 4 read it after the draft, sha256 413a88a4ec81, and the 21 Reference row(s) pass 6 moved.

- Reference row 3: Scopes table, Caller identity row: the caller's user and org come from the verified principal, never from the request body, query or headers. Untrue: The user can come from the body. The HTTP view route passes the body to the host's principal resolver, and the framework default resolver reads `body.userId` and takes the user from it. A host or flow resolver can verify the user another way. The org never comes from the body: the default resolver deliberately returns no `orgId`. The route also turns a missing `body.userId` into a 400. (packages/engine/src/routes/view-routes.ts:83-99; packages/engine/src/transports/auth/defaultBodyUserIdPrincipalResolver.ts:26-47) The row is recorded corrected.

Final fact check of the page as it closed, sha256 5744c254a312: 3 untrue, fixed in a last round.

- useView option `changed`: "A notice to pass as the `changed` hint." Untrue: useView accepts `changed` in its type (UseViewOptions extends ViewCallOptions) but never forwards it. The watchView call passes only `sessionId` and `pollIntervalMs`, and watchView builds its call options from `sessionId` alone. The hint on a watched view comes only from the notice that woke the read, so setting `changed` on `useView` does nothing. It is honoured only by `client.view(ref, input, { changed })`. (packages/react/src/hooks/useView.ts:103-106; packages/client/src/view/view.ts:277,286)
- A request's `changed` hint "is honoured when `topic` is one of the topics a view answer can return in `topics`". Untrue: `changeOf` checks only that `topic` is a well-formed wire topic (`isWireTopic`: scope `session` with a non-empty string id, or `user` or `org`, with an optional string `resource`). It is not checked against the topics this view's answer returns. It also requires `kind` to be one of the eight listed kinds and 1 to 100 string ids, and those parts of the claim are correct. (packages/engine/src/routes/view-routes.ts:223-229; packages/engine/src/push/socket-session.ts:228-240)
- `view_answer_not_keyed` message: `View "<name>" declares a key, so its answer must be a list` Untrue: The message has the word key in literal backticks: View "<name>" declares a `key`, so its answer must be a list. A non-string key produces a different message, `View "<name>"'s rows must have distinct string keys; a key is not a string`. The page gives only the repeated-key form for both cases. (packages/engine/src/execution/runView.ts:251,261)
