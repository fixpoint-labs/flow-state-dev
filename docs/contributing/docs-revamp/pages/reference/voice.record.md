## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support chat flow speaks each reply sentence. How long does the framework wait on one sentence before giving up on it, what exactly does that limit cover with a provider that streams audio, and what does it cover with `OpenAIVoiceProvider`?
   Answer: 15 seconds (`SYNTHESIS_TIMEOUT_MS = 15_000`). With a streaming provider it bounds only the time to the first audio chunk of each sentence. The timer is dropped once that chunk arrives, so a long sentence is not cut off, and a stream that stalls after its first chunk is stopped only by the request abort (client disconnect). `OpenAIVoiceProvider` has `speakStream: false`, so TTS always takes the batch path and the 15 s bounds the whole `speak()` call. A sentence that times out is abandoned and reported as a non-fatal `tts.synthesis.error`; the text keeps streaming (fact sheet 2.7, 2.6, 4.4; tts-pipeline.ts:22-28,213-227,277-305; openai-voice-provider.ts:60-65).
2. You set the support flow to `voice: { tts: { voice: "nova", speed: 1.2 } }` and give no `model`. The server's provider is `new OpenAIVoiceProvider({ apiKey })` with no other options. Which speak model and audio format does the customer get, and what would they hear if you dropped `voice` from `tts`? Does a plain `sendAction` from a typed message get audio?
   Answer: The framework has no default for `model`, `voice` or `speed`; the provider's defaults apply. OpenAI's speak model defaults to `gpt-4o-mini-tts` (its `ttsModel`, which becomes `defaultModels.speak`). The pipeline never sets `outputFormat`, so OpenAI's default `mp3` (`audio/mpeg`) is used. With no `voice` the OpenAI default voice `alloy` is used. `speed` 1.2 is a multiplier on 1.0 = normal, which the provider may clamp. A typed `sendAction` gets no audio unless it passes `metadata: { voice: { ttsEnabled: true } }`: TTS needs `voice.tts` on the flow, a provider that can speak, and the request opt-in (fact sheet 1.2, 1.3, 4.4; speech.ts:430-435; runAction.ts:1255-1267,1895-1897; output-format.ts:32-35).
3. A customer records a long complaint and a mobile client posts it to `POST /api/flows/transcribe` as raw audio. The first attempt is 30 MB; the retry is small but the client forgets the `userId` query parameter. What status and error does each get, and how would the JSON form of the same request differ? *(edge case)*
   Answer: The 30 MB upload gets 413 with `Audio payload exceeds maximum size of 26214400 bytes` (the cap is 25 MiB; the raw form checks `Content-Length` first). The retry with no `userId` gets 400 (`Transcription requires non-empty userId query parameter`). In the raw form the body is the audio, `userId`, `language` and `model` go in the query, and `mediaType` is the `Content-Type` without parameters (default `audio/webm`). In the JSON form (`Content-Type: application/json`) the body carries `userId` (required), `audio` (required, base64), and optional `mediaType` (default `audio/webm`), `language` and `model`. A success is 200 `{ text, language }` (fact sheet 3; stream-routes.ts:392-462,483-486).
4. Your server's provider is a custom in-house `VoiceProvider` with no `defaultModels.transcribe`, and the support flow additionally sets its own `voice.provider` that can transcribe. The browser posts a recording to the transcribe endpoint without a `model`. What comes back? And what comes back on a deploy where the server has no provider at all? *(edge case)*
   Answer: `400` with `error: "no_model"` (and a `message`): the endpoint resolves the model from the request's `model`, then the server provider's `defaultModels.transcribe`, and there is no framework default (an empty string counts as none). The flow's own provider does not help: the endpoint belongs to no flow and always uses the server-level provider, and a flow's `voice.provider` applies to TTS only. With no server provider the endpoint returns `501 transcription_not_configured`; with a provider whose `abilities.transcribe` is false it returns `501 provider_does_not_support_transcription` (fact sheet 3, rows 3-4, 13; stream-routes.ts:382-389,464-473; http-handlers.ts:747-752).
5. OpenAI starts rate-limiting the support desk. One reply sentence fails to synthesize, and a moment later a customer's recording fails to transcribe for the same reason. What does each failure look like to the app, and what does the customer end up with in each case if they use `useVoice`? *(edge case)*
   Answer: OpenAI's rate-limit error maps to `VoiceError` kind `rate_limit` (retryable by default). The failed sentence is skipped and the text keeps streaming; it is reported as a debug stream event `tts.synthesis.error` with `{ itemId, text (first 100 chars), kind, retryable, level, message }`, and since the kind is retryable its `level` is `info`. Debug events are not replayed on reconnect. The transcription failure returns `429` with `{ error: "rate_limit", message }`. `useVoice` then sends the interim browser transcript as the action input if it is non-blank; if there is none, nothing is sent and no error surfaces (fact sheet 2.6, 3, 4.2, 4.4, 6; tts-pipeline.ts:143-182; stream-routes.ts:486-523; useVoice.ts:268-278).
6. A customer's connection drops halfway through a spoken reply and reconnects. Later a teammate opens the same conversation from its stored record. What audio, transcript and text does each of them get? *(edge case)*
   Answer: Audio is never stored: every audio part is marked `ephemeral: true` and removed (not blanked) from the items written to the request record, and `content.audio.delta` events are never in the event log. So the reconnecting customer hears no more of a sentence that was streaming when they dropped, since its deltas are not replayed; the replayed `content.added`/`content.done` events carry the sentence's `transcript` with empty audio for a streamed part (full audio for a batch part, as with OpenAI). `useVoice` skips parts whose `audio` is empty. The teammate reading the stored record gets no audio parts and no per-sentence transcripts, only the reply's text, which is the ordinary assistant message and is stored as usual (fact sheet 2.9, 5.3, 7; runAction.ts:430-466,661-690; resume.ts:143-150; response-emitter.ts:775-800).

- Page: "Audio is not kept... so neither batch nor streamed audio can be read back later. The deltas are also absent from the replayable event log: a client that reconnects mid-sentence hears no more of that sentence, and the `transcript` is not recovered from storage either." Untrue: Only the stored request record's items drop ephemeral parts. The event log does not: `content.added` and `content.done` are replayable (only ping, debug, `content.delta` and `content.audio.delta` are filtered) and they are persisted with the part unfiltered. A batch sentence's `content.added`/`content.done` carry the full base64 audio plus `transcript`, so a reconnect replays that audio. A streamed sentence's replayed `content.added`/`content.done` carry the `transcript` with empty `audio`, so the transcript is recovered and only the audio bytes (the deltas) are lost. `useVoice` relies on this: it skips replayed empty-audio parts.
