## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Someone posts a forged Stripe event to your billing flow's webhook URL, and the Stripe-Signature header does not verify against your secret. What does the sender get back, and does anything run or get stored? *(edge case)*
   Answer: 401 with the JSON body { "error": "invalid_signature" }. Verification runs over the raw request bytes before any parsing, so nothing is parsed, routed or dispatched, and no session is created. A verify function that throws is treated the same as one that returns false. (Lookup; 4.5, 4.6, 5.3; wrt:127-137, wrt:435-458, goal 'forged POST returns 401 and creates no session')
2. Your billing flow is registered with kind "billing" and declares webhooks.stripe.on["invoice.paid"]. The host mounts createWebhookTransportAdapter with the default basePath. What URL do you point Stripe's dashboard at, and what two names have to agree for the delivery to be found?
   Answer: POST <host>/api/flows/billing/webhooks/stripe. The route is POST <basePath>/:flowKind/webhooks/:provider, with basePath defaulting to /api/flows. :flowKind is the flow instance's id, and :provider must be the same key in the flow's webhooks map and in the adapter's providers map. If the flow is unknown the answer is 404 flow_not_found; if the provider is not declared on the flow or not configured on the mount, it is 404 webhook_not_found. (1.3, 1.5, 1.6, 5.1, 5.2, 8.4)
3. Stripe sends a customer.subscription.updated event to the billing flow, which only binds invoice.paid. What does Stripe get back, and why is that status chosen? And what changes if the invoice.paid binding has a when predicate that throws? *(edge case)*
   Answer: 202 { status: "ignored", provider, eventType }, and nothing runs. A delivery with no match gets a 2xx so the provider does not keep retrying an event the flow does not handle. The on key must equal the extracted eventType exactly. A when predicate that returns false gives the same 202 ignored, and so does one that throws: the error is logged as a warning and counted as no match, never a 5xx. (2.1, 2.5, 5.7; wrt:139-180)
4. Your invoice.paid handler takes about 20 seconds to record a payment. When does Stripe get its response, what is in it, and if the handler then fails, where does that failure show up?
   Answer: The route waits only until the request is durably recorded (handle.accepted), never for the run to finish, then answers 202 { status: "accepted", provider, eventType, requestId }. The block's output is not returned. The block runs after the response, so an error after dispatch lands on the request record, not in the webhook response. That keeps the answer inside provider time budgets. If the request could not be recorded, the answer is 503 dispatch_not_durable, and the provider retries. (5.13, 5.14, 5.16)
5. Stripe redelivers the same invoice.paid event (same payload.id) after a timeout. Does Flow State drop the duplicate for you? What should you do so the customer isn't credited twice, and what does Stripe get if the first delivery is still running and the flow's concurrency policy is reject? *(edge case)*
   Answer: No. The route does not deduplicate redeliveries, and each accepted delivery makes its own request record. The provider's deliveryId extractor (Stripe: payload.id) sets event.deliveryId and records metadata.webhook.deliveryId. Pass event.deliveryId into the block's input from the binding's input function, and make the block idempotent. If the policy is reject and another request already holds the key (by default the session), the duplicate is answered 200 { status: "skipped", reason: "in_flight", requestId }, so the provider stops redelivering. (3.4, 3.6, 3.7; wrt:461-595)
6. No user is logged in when Stripe calls your webhook. Which userId does the run use, what do you set on the flow so deliveries are accepted, and how do two invoices for the same customer end up in one session? *(edge case)*
   Answer: The route never reads a userId from the body, headers or query. The sender is trusted because of the signature. The userId comes from host.resolvePrincipal (the flow's resolver, else the host's), then authentication.defaultUserId if the resolver gave none. The documented webhook-only setup is authentication: { defaultUserId: "system", requireUser: false }, so the session's userId is "system". An organization is still required: with no resolver configured anywhere, the development org is used; a configured resolver must return a valid orgId, or the answer is 401 unauthorized. For continuity, set sessionId: (event) => `customer-${...}`. The session is found or created, so events with the same id share it. Without sessionId, each delivery gets a fresh session. A later delivery to that session must resolve to the same principal. (2.4, 5.11, 6.1-6.6, 6.8, 5.17)

## Reference rows

- A flow with only webhooks writes `actions: {}` because `defineFlow` requires the map; Next.js serves the route with `createVercelNextHandler(flowstate)` from `@flow-state-dev/vercel/next`. → R-05
- Refusals table: router build throws for a provider with no mount definition and for an `on` map whose provider has no `eventType`; `defineFlow` throws a plain `Error` for each malformed `webhooks` shape (empty provider name, empty `on` key, binding without `block`, non-function `input`/`sessionId`/`when`, `on` and `service` together); event keys are opaque, so a typo never matches. → R-32
- `defineWebhookBinding<TPayload>()`: returns its argument unchanged; a binding carries the block and action policy directly and has no `actions` entry. → R-32
- Binding reachability: no action endpoint, not listed, never an MCP tool; a webhook-sourced request cannot be re-run via `retry`, `continue` or `resume`; `webhook`, `internal` and `task` cannot be added as re-entry sources (throws at router build); a refused re-run answers not-found. → R-32
- `publicReentrySources` option on `createFlowApiRouter` / `createFlowState`: default sources and the sources that are refused. → R-12
- Redelivery: the route does not deduplicate; each redelivery is another request record; use `event.deliveryId` to make the block idempotent. → R-32
- Request record fields for a webhook delivery: `source`, `metadata.webhook`, the record's `action` equal to the block's `name` (display only, not reachable on the public action endpoint), and that a block reads the delivery through `input`, not `metadata.webhook`. → R-32
- Methods: only `POST` is served on the webhook path. → R-32
- Service routes: `service` entry fields, `normalize(event, { received })`, routing through the internal action named by `entry` as user `service:<provider>`, provider service-flow factories such as `githubServiceFlow`, and that verification and handshake run first. → R-32
- Adapter call order: resolvePrincipal, build envelope, validateDispatch, dispatch. → R-32
- `ConcurrencyRejectedError`: status 409, `key`, `inFlightRequestId`. Under a `reject` policy it rejects the handle's `accepted` and `finished`, not a throw from `dispatch`. It is applied once whatever the transport, and a fire-and-forget adapter answers it as a skip. → R-18 (corrected by pass 5)
- `publicReentrySources` on `createFlowApiRouter` or `createFlowState`: how a custom transport source is allowed onto the public re-entry routes. → R-12
