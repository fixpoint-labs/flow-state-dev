## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Alice adds a folder at workforce/teams/support/workers/triage/ holding a WORKER.md. What id does that worker get, and what id would it get if she had put it at workforce/org/workers/triage/ instead?
   Answer: Under the team it is `support.triage`: a team worker's id is `<team>.<name>`. Under org/workers it is the bare folder name `triage`, with no dot. A team worker's id always has a dot, so the two never collide and both can exist as separate workers (facts section 1, rwd:364-376; rwdt:83,89).
2. Which setting must every WORKER.md declare, and what happens to a worker file that leaves out `flow:`?
   Answer: `description`, a non-empty string, is the only setting the file loader requires; a missing, non-string or blank one is refused with `must declare a non-empty description`. With no `flow` key the worker runs on the built-in `agent` flow. One clause: a flow can need more, e.g. a `coder` worker with no `harness` and no kit `defaultHarness` has its task refused (sections 3 row 3, 4, 10).
3. The lead's file, teams/engineering/workers/lead/WORKER.md, sets `name`, `description`, `model` and `delegates: [engineering.coder, engineering.reviewer]`. What does each do, and what are the defaults of `model` and `delegates` if they are left out?
   Answer: `name` is the display name people see in place of the id (the id `engineering.lead` stays the address); `description` is the one line saying what the worker is for; `model` is the model its turn runs on, default the flow's `model` option, else `intent/chat`; `delegates` lists the worker ids it can hand work to (at most 25, or `all`), default `[]`. The body below the frontmatter is its instructions (settings table, section 4).
4. Bob writes `instructions:` in the lead's frontmatter and also leaves the body text below it. He also adds `workerId: engineering.boss` to rename it. What happens? *(edge case)*
   Answer: Both are refused. `workerId` is one of the six keys the framework sets (`persona`, `workerSkills`, `teamInstructions`, `workerTools`, `workerPackages`, `workerId`); the loader reports it as kind `refused-declaration` and leaves the worker out; the id comes only from the folder. Setting `instructions:` while also writing a body is refused at hire as two sources for one setting; remove one. A whitespace-only body counts as no body (section 3 rows 8-9).
5. Alice creates teams/engineering/workers/reviewer/ but puts only a notes.txt in it, and adds another folder named `Code_Review`. What happens when the app starts? *(edge case)*
   Answer: Neither loads. A worker folder with no WORKER.md is reported as `Worker folder "reviewer" has no WORKER.md...`, and `Code_Review` breaks the naming rule (lowercase letters and digits joined by single hyphens, at most 64 characters, not `_meta` or a Windows device name). Each problem lands in `errors` as `{ path, error, kind }` (kind `worker-load-failed`), and the other workers still load. But the workforce kit stops the app at start, naming every problem at once: `the workforce folder did not load:` followed by a `- <layer> <path>: <message>` line for each (sections 2, 3 rows 1, 7, 11).
6. While the app runs, Alice edits engineering.lead's WORKER.md, and Bob edits that same standard worker from the app. When does each change take effect, and does Bob's edit reach Alice? *(edge case)*
   Answer: The file is read only when the app starts, and nobody edits it while the app runs; under `fsdev dev`, saving a file under the config's directory restarts the app, so Alice's edit takes effect after the restart. Bob's edit never writes the file: it writes his own copy under the same id, which is read before the file, only he can see it, and reset deletes it. Alice keeps seeing the standard worker (sections 0, 6).
