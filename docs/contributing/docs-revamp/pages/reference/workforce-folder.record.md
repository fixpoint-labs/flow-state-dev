## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. The support team gets a new worker. You create `workforce/teams/support/workers/billing/WORKER.md` with a `description` in its frontmatter and nothing else. What does the kit make of it, what is the worker's id, and what else do you have to write or wire before it shows up?
   Answer: It becomes the standard worker `support.billing`. A team worker's id is the team folder and the worker folder joined with a dot, and `teams/<team>/workers/<worker>/WORKER.md` with a `description` is the smallest tree that holds a worker (facts s.1 and s.2: `wff:53`, `rwd:372-376`, run: `teams/core/workers/lead/WORKER.md` alone starts as `core.lead`). You wire nothing. The kit reads the folder once when the app starts, so you restart the app and it is there (s.1 `kit:185`, `dk:136-143`; s.10). A worker flow, block or capability file would also need `fsdev gen`, but a `WORKER.md` does not (s.10).
2. A teammate sets up a regional team as `workforce/teams/Support-EU/workers/lead/WORKER.md` and starts the app. What happens? Which names in the folder does that rule cover, and what else does it refuse? *(edge case)*
   Answer: The app does not start. The worker line names the folder and says `Team folder name "Support-EU" must be lowercase letters, digits, and single hyphens (not at the start or end) — it becomes part of the worker's identity, which is joined with a "."` (s.3 lookup table, `seg:64-78`, run; it shows as `- worker teams/Support-EU/workers/lead: ...`, s.3 "Where a refusal shows"). The rule is the same for team, worker, document, skill, package, worker-flow and block names: lowercase letters and digits joined by single hyphens, with no leading or trailing hyphen and no dots, underscores, spaces or capitals. A name may be at most 64 characters. `_meta` is reserved, and Windows device names (`con`, `prn`, `aux`, `nul`, `com1`-`com9`, `lpt1`-`lpt9`) are refused whatever the extension. They are checked in that order: length, reserved, pattern, device name (s.3, `sn:21-54`, `wrn:9-22`). Renaming the folder `support-eu` fixes it, and the id becomes `support-eu.lead`.
3. Two files land in one PR. One is `workforce/teams/support/tools/lookup.ts`. The other is `workforce/teams/support/workers/fsd/blocks/search-docs.test.ts`, next to the existing `search-docs.ts`. Which one stops the app at startup, which one only `fsdev gen` refuses, and what does each message tell you to do? *(edge case)*
   Answer: The `tools/` folder is in a place the kit does not read, so the app refuses it at startup and names the folder once at its top: `"teams/support/tools" is not used by anything that reads the folder of kit "workforce". Remove it.` (s.1 and s.2, `claim:98-114`, run). `fsdev gen` refuses it too, with its own sentence: a tools/ folder is not read, a tool is an ordinary block, so put the file in a `blocks/` folder and name it in a worker's `tools:` (s.2, `dwb:209-228`). The test file sits in the right place with the wrong name. The app starts, and `fsdev gen` refuses it as a block named `search-docs.test` (a dot is not allowed). It writes nothing: `Refused 1 entry under the workforce code folders; nothing was generated:` (flag 2, s.3, s.6 `disc:125-145`, run). Wrong place is caught at startup. Wrong name in a code folder is caught by `fsdev gen`.
4. You write an escalation playbook as a package with tools at `workforce/teams/support/packages/escalation/` (a `PACKAGE.md` plus `blocks/page-oncall.ts`). Which support workers hold it, and how? What changes if you move it to `teams/support/workers/fsd/packages/escalation/` or to `org/packages/escalation/`? Under what key does `workforce.gen.ts` list its tools?
   Answer: In the team's `packages/`, it is held by a worker on the support team only once that worker's `packages:` line names it. A package no worker names reaches nobody. In `fsd`'s own `packages/`, only `fsd` holds it, always, with no line in its file. In `org/packages/`, any worker holds it once its `packages:` names it. A name is looked up in the team library first, then the org's (s.8 table, `pk:40-57`, `wp:104-142`, run). The package's address is its folder path, `teams/support/packages/escalation`. That is its key in the generated `packageBlocks` export, which holds `page-oncall`. Run `fsdev gen` after you add or remove a package block. Leave `packageBlocks` out and a held package brings its instructions and no tools (s.6 generated-exports table, s.8 `man:225-232`, `pk:90`). A package may hold only `PACKAGE.md` and `blocks/`. Any other key in the `PACKAGE.md` frontmatter beyond `description`, or a `README.md` in the folder, stops the app (s.8).
5. The app is running. You edit three things: the body of `teams/support/references/handbook.md`, the body of `teams/support/TEAM.md`, and a new block `teams/support/workers/fsd/blocks/lookup.ts`. When does each change reach the support workers, and what do you have to run? *(edge case)*
   Answer: The reference body reaches the next request, because a reference is read from its file each time a request is handled. A read already in flight keeps the body it started with (s.10, `rfr:12-13`, `rr:567-590`). `TEAM.md` needs a restart, because the folder is read once at startup and nothing watches it (s.10, `dk:136-143`, `dd:388`). The new block needs `fsdev gen`, so that `workforce.gen.ts` lists it under `fsd`'s `workerBlocks`, and then a restart. Nothing regenerates while the app runs, and `fsd` calls the block only if its `tools:` names it, or with no `tools:` line through a preset or package (s.6, s.10, `cd:18`, `cd:160`). Under `fsdev dev --watch` a save restarts the dev server for you (s.10; read from code, not run).
6. The `fsd` worker keeps a private note at `teams/support/workers/fsd/references/known-bugs.md`. Later the `devices` worker on the same team needs to read it too, so a block on `devices` reads `ctx.resources.get("teams/support/workers/fsd/known-bugs")`. What happens, and how do you give `devices` access? And what if someone also adds `teams/support/workers/fsd/resources/known-bugs.md`? *(edge case)*
   Answer: A worker reaches the references of the org, of its own team and of its own folder, and no others. `devices` cannot see a file in `fsd`'s folder. The accessor is absent, so the read throws `is not registered` rather than coming back empty (s.4 "Who reaches a reference", `wr:1-37`, `dd:279`). No setting widens this, and a worker's `references:` line only narrows within that limit. Move the file up to `teams/support/references/known-bugs.md`, where its ref becomes `teams/support/known-bugs` and every worker on the team reaches it (s.4, `wr:35-37`, `rc:100-152`). A `resources/` file and a `references/` file of one name at one level claim the same ref, so the app does not start. Both paths are named: `... both claim the ref "teams/support/workers/fsd/known-bugs". ... Keep one.` (s.4, `rdr:199-227`, run).
