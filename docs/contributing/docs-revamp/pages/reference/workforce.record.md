## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. An app ships a standard worker `support` (a WORKER.md). Ana calls `edit` on `support` to change its name and instructions. What changed, for whom, when does it take effect, how does her roster show it, and how does she undo it? *(edge case)*
   Answer: The first `edit` of a standard worker's id writes Ana's own copy under the same id: the file's configuration (flow, description, instructions, team instructions, skills, settings, name) with her edited fields replacing it. The file is never written, and other users' copies and the file are unaffected. The copy is read before the file, so it takes effect on her next turn, in every session of that worker, on any process; nothing is registered and nothing restarts. Her roster lists it once, as the copy, with `standard: true` and `edited: true`, still on its file's team. `reset("support")` deletes the copy so the file is read again (facts 3.1, 3.2, 1.5).
2. Ana then tries two more writes: `edit` on `support` naming `flow: "coordinator"`, and `hire` with `id: "support"` to make a worker of her own from scratch. What does each do? *(edge case)*
   Answer: Both are refused and nothing is written; the request ends `failed` with the reason. The edit: `"support" runs on "agent", as its file declares, so its flow can't be changed. Nothing was written.` (a standard worker stays on its file's flow). The hire: `"support" is a standard worker, which nobody can hire over. Fork it to get a worker of your own.` To get her own worker under a new id she forks it, which copies the configuration (from her edited copy, without its name) and gives `standard: false`, `forkedFrom: "support"` (facts 3.1, 3.2, 4.1).
3. Ana hired her own worker `ana-researcher`. Ben, in the same organization, knows the id and tries to open a session with it, and to add it as a delegate in his own conversation. What does he get? *(edge case)*
   Answer: Only the owner reaches a user's own worker. Ben's session create gets `No worker "ana-researcher".` with status 404, the same answer as for a worker that does not exist. `addDelegate` gets `No worker "ana-researcher" on your roster.` A delegate must be on the filing user's own roster (their own workers or standard ones), and a message cannot cross users. A user's own worker record is stored at user scope, per organization, and a browser sees only its owner's (facts: stored parts table, 3.4, 4.3, 5.4, 5.5).
4. A coordinator worker's file says `delegates: [billing, triage]`. During a conversation its model tries to file a task for `research`, a standard worker not on that list. What happens, and what would have to be true for `research` to receive the work?
   Answer: A worker hands work only to its conversation's delegate list; the task is refused `unknown_assignee: "research" is not on this board's team. Available: ...` and nothing is stored. To receive it, `research` must be in the conversation's list (the user adds it with `addDelegate`, or the model does if the file sets `editsOwnDelegates: true`; that changes only this conversation's copy, never the file), be on the filing user's roster, have a readable row, and run on a flow declaring the `contributor` role (`agent` and `coordinator` do). The list holds at most 25; `delegates: all` means the whole roster, read on every call (facts 5.4, 5.5).
5. A coordinator uses `routing: best-fit` with `fallback: triage` and `minConfidence: 0.7`. A new user message arrives that no delegate is holding, and the evaluation returns a pick with confidence 0.4. Where does the message go, and what does the user see if everything after that fails too? *(edge case)*
   Answer: Best fit's ladder: held (no delegate holds the last message here), then one `routeModel` evaluation; a pick below `minConfidence` is not used. So it falls to the fallback: `triage` takes it if it can be reached. If no fallback were set or reachable, the message goes to the coordinator's own judgment turn. Only if that turn itself fails is the message unplaced, and the conversation says `Nobody took this message: best fit couldn't place it, and the coordinator's own turn failed: <message>.` The route record's `by` shows `fallback` (or `unplaced`), with `fit.reason: below-floor` (facts 5.2, 5.7).
6. Ben fires his own worker `drafter`, which he used heavily this week. What happens to his old sessions with it, and what does the `workerUsage` view (default period) show for it afterwards? *(edge case)*
   Answer: `fire` deletes his own row; every process sees it on the next turn. His past sessions stay readable, but a new turn in one is refused `Worker "drafter" was fired. This session stays readable; a new turn can't run as it.` Usage records are kept: `workerUsage` (default `days: 7`, UTC, answering only for the caller) still lists `drafter` with `gone: true`, its summed `tokens`, and `bySource` entries. Its `costUsd` is `null` (shown as "not reported", never $0) unless a harness on an `api-key` reported a cost; model sources always carry `null` (facts 3.3, 9).
