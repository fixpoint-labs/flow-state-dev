## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You are adding the `support` flow to a Next.js App Router app you already have. Which file serves it over HTTP, and what must that file export?
   Answer: One route file, `app/api/flows/[[...path]]/route.ts` (or under `src/app/`). It exports all four verbs, `export const { GET, POST, PATCH, DELETE } = createNextHandler(flowstate)` from `@flow-state-dev/next`, plus `export const dynamic = "force-dynamic"`. `createNextHandler` takes the `FlowState` handle from `createFlowState({ flows: [support] })`, which lives in its own module (`fsdev.config.ts`), and not `flowstate.getRouter()`. Facts sec. 4b, sec. 9 Q1; `nextP/src/createNextHandler.ts:40-52`; `hc/app/api/flows/[[...path]]/route.ts`.
2. Your page sends `reply` to the `support` flow. What does every call have to say about who is calling, and what happens to a call that leaves it out?
   Answer: Every call carries a `userId`. On the page it comes from `<FlowProvider flowKind="support" userId="u1">`. The client throws `userId is required` if the value is empty, and with the default resolver the server answers 400 to an action call that names no user. The default trusts whatever `userId` the caller writes, so it identifies the caller but proves nothing. A real check is a `resolvePrincipal`, which the auth page covers. A hook with no `userId` falls back to the development identity `"devuser"`, so pass the value explicitly. Facts sec. 5, sec. 9 Q2; `cli/client.ts:57-62`; `engT/transports/http-adapter.test.ts:226-240`; `react/internal/useClient.ts:15`.
3. You type a message and press Send. The model runs, but the page shows no reply. Which pitfall is it, and what is the fix? *(edge case)*
   Answer: Either answer earns credit if it names the matching symptom. (a) The page stays empty and no reply ever appears: the action's generator has no `itemVisibility`, so it emits no items. Fix: `itemVisibility: { client: true, history: true }`. In development, `defineFlow` warns about this once when the flow is built. (b) Nothing shows until the reply is finished, then it all arrives at once: Next.js is buffering the stream. Fix: `export const dynamic = "force-dynamic"` on the route. Facts sec. 7a, 7b and the Q3 flag; `core/blocks/generator.ts:575-587`; `core/flow/defineFlow.ts:548-573`; `hc/app/api/flows/[[...path]]/route.ts:3-6`.
4. Your app has no Next.js. It is a plain Node project. How do you serve the same `support` flow, and what should you set while developing?
   Answer: Use `@flow-state-dev/node`: `import { serve } from "@flow-state-dev/node"` and `await serve(flowstate)`, where `flowstate` is the same handle the config file default-exports. The flow does not change. Only the file that mounts it does. By default it binds `PORT` (or 3000) on `0.0.0.0` and mounts `/api/flows`. `serve()` does not check authentication, so pass `host: "127.0.0.1"` while developing. Otherwise anyone who can reach the port can name any `userId`. Facts sec. 8, sec. 9 Q4; `node/serve.ts:143-190`; `node/README.md:29-42`.
5. You wrote the route as `app/api/flows/[...path]/route.ts`, exported only `POST`, and set `baseUrl="/api"` on `FlowProvider`. The page fails. What are the three fixes? *(edge case)*
   Answer: (1) Use the optional catch-all `[[...path]]`, so the bare `/api/flows` is served. The page's first call, `useFlow` listing flows, goes to that bare URL. (2) Export all four verbs, `GET, POST, PATCH, DELETE`. The reply stream and state fetches are `GET` requests, so a route with only `POST` breaks streaming. (3) Drop `baseUrl` on the same origin (set it only for a Next.js `basePath`, for example `"/portal"`). The client adds `/api/flows` itself, so `"/api"` produces `/api/api/flows/...` and a 404. Facts sec. 7c, 7d, 7e; `nextP/test/createNextHandler.test.ts:83-91`; `nextP/src/createNextHandler.ts:40-52`; `cli/client.ts:63-72`.
6. Later you add a second flow next to `support`, and you restart the dev server. What do you change to serve the new flow, and what happens to the conversation the user had before the restart? *(edge case)*
   Answer: Add one entry to the list, `createFlowState({ flows: [support, other] })`. You do not add a second route, because one route file serves every flow. Write `flows` as a list: the keyed form `flows: { support }` throws when the server is built. With `stores` omitted, sessions live in memory, so the restart loses the earlier conversation. To keep sessions across restarts, pass a store adapter such as `sqliteStores({ filename })`; the persistence page covers this. Facts sec. 4a, sec. 10, sec. 12; `eng/flowstate/types.ts:119-124`, `:168-178`; `eng/flowstate/createFlowState.ts:365-377`.
