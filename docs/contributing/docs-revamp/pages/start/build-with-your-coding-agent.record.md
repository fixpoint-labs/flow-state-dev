## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You asked your coding agent to add a step to the research flow. How does it check its own change, and what does it read back to decide it worked?
   Answer: It runs the action in-process from the app's directory with `fsdev run <flow> <action> -i '<json>'` (e.g. `fsdev run research <action> -i '{...}'`), and reads the NDJSON on stdout, one JSON event per line, and the `[flow-state]` runtime logs on stderr. The run ends with exactly one terminal event: `flow_complete` `{ output, durationMs, items }` on success, `error` `{ message }` on failure, or `suspended` when held for a person. Exit code 0 means success, 1 an execution error. (Facts 1.1, 1.6, 2.3, 2.18, 4.1)
2. Before you ask the agent for its first change to the research flow, which two things do you give it, and where does each come from?
   Answer: The docs: point it at `https://flow-state.dev/llms.txt`, which lists every docs page, each served as Markdown at its URL plus `.md`. And the skills: `debug-flow` (the fsdev-run toolkit: NDJSON traces, stderr logs, `fsdev block` isolation, a failure-pattern table) and `diagnose` (the bug loop that calls it), plus `install-fsd`, which writes the FSD section of `AGENTS.md`. A skills pack bundled in the starters is not there yet. (Facts 5.1, 5.3, 6.2, 6.4, 6.8)
3. The agent's run of the research flow exits 1 and the last stdout line is `{"type":"error","message":"..."}`. That line doesn't say which block failed. Where does the agent look to find the step, say `runSearches`, that broke? *(edge case)*
   Answer: In the stdout `block_trace` items. Every block that runs emits one. The failed block's trace ends (on `item_done`) with `status: "failed"`, its `blockName` and `blockKind`, and `error: { message, code }`. The terminal `error` event carries only `message`. On stderr, a `[flow-state] block execution failed {...}` line also names `blockName` and the error. If the run used `--quiet`, the stderr line is gone and the stdout `block_trace` is the place to read it. (Facts 2.4, 2.8, 2.11, 2.13, 2.17)
4. Does the agent need a browser or a running dev server to check its change to the research flow? Does it need anything else to reach the outside world?
   Answer: Neither a browser nor a server for the flow's logic. `fsdev run` and `fsdev block` call the engine in-process, with no HTTP server and no SSE, through the same `runAction` the production server uses. A browser is needed only to check how a UI renders. The `assistant` generator still calls its model provider over the network and needs that provider's key, which the CLI loads from `.env.local`. (Facts 1.2, 1.3, 1.4, 1.5, 4.5, 4.6)
5. The agent changed only `planQueries` and wants to try that one block without running the whole research flow. What does it run, and what must be true of the block's file? *(edge case)*
   Answer: `fsdev block src/flows/research/blocks/plan-queries.ts -i '<json>'`. The block runs alone, with no flow context and no session, and prints one JSON document: `success`, `output`, `schemaValidation` for input and output, and `error` on failure. It exits 0 on success and 1 on failure. The file must default-export the block (`export default planQueries;`). Without that it exits 4. (Facts 3.1, 3.2, 3.4, 3.5, 3.6)
6. The agent's run prints `flow_complete`, or a `suspended` event, and exits 0. Does that mean the agent's job is done? *(edge case)*
   Answer: Not always. `suspended` means the run stopped to wait for a person. It exits 0 but is not done, and someone answers it through `fsdev dev` on the same store. This is the one case where the loop needs a person. Separately, `flow_complete` can be printed while background work the flow started is still running. The process stays up until that work ends, bounded by a 30 s default, so a run that printed `flow_complete` and hasn't returned is usually waiting on that work. (Facts 2.21, 2.22, 4.7)
