## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. You add the line "Always begin your answer with the word AHOY." to the bottom of the researcher's WORKER.md, below the second `---`, and save it. What do you do to see the researcher follow it, and does it matter whether you are using `fsdev run` or a running `fsdev dev`?
   Answer: Run it again. Everything below the second `---` is the worker's instructions, and a turn reads its worker by loading it, so the next turn after a restart uses the new file. Each `fsdev run` is a new process, so the next run reads the saved file: in the fact sheet's run, the reply started `AHOY`, in an existing session and in a new one. A running `fsdev dev` reads the tree once, at startup, so restart it, or start it with `fsdev dev --watch`, which restarts when you save. (Facts §2: wd:59, wd:358, wd:956, api:133-145; flag 6.)
2. You want a proofreader on the Teammates team. What do you create, what is the new worker's id, and what is the least the file must contain?
   Answer: Create a folder with a WORKER.md under the team: `workforce/teams/teammates/workers/proofreader/WORKER.md`. The id is the team folder and the worker's folder joined by a dot: `teammates.proofreader`. `description` is the only key the file needs, plus a body of instructions below the front matter. A worker with no `flow:` runs on the built-in `agent` flow. Restart the app, or use `fsdev dev --watch`, which also restarts when a new WORKER.md appears. Every user of the app then has the worker, as a standard worker. (Facts §3: wd:17-35, wd:148-152, wd:76, api:141, wd:271-273.)
3. From the app's folder you want to send the researcher one message without a browser. What command do you type, and what does it print?
   Answer: `pnpm fsdev run agent respond --session make-it-yours --seed-session '{"workerId":"teammates.researcher"}' -i '{"message":"Say hello in one short sentence."}'`. Workers run on the built-in flow `agent`, whose message action is `respond`, and the input is `{ "message": ... }`. It runs in-process, with no HTTP server and no browser, and uses the app's fsdev.config for flows, models and stores, which is why it runs from the app's folder. On stdout it prints NDJSON, one JSON object per line, each with a `type`. The run ends with `flow_complete`, which carries `output` (the reply), `durationMs` and `items`. Stderr says which user the run was made as. (Facts §4: cli:15, cli:26, cli:54, run:574-578, run:413; flag 1.)
4. You leave out `--seed-session` and run `pnpm fsdev run agent respond -i '{"message":"hi"}'`. What happens, and what about the second message in the same conversation? *(edge case)*
   Answer: The run is refused and nothing is stored. A session of `agent` must name its worker when it is created, so the error says the session's initial state doesn't fit at "workerId" (Required) and tells you to pass it with --seed-session. The exit code is 2. The seed is read only when the session is born. For later messages, pass `--session <id>` with the same id to continue that conversation. A second call with the same seed also ran cleanly. Leaving the seed off later calls should work but was not run. (Facts flag 1, flag 2: run:462-464, installation.ts:621-629, cli:42.)
5. You start a proofreader session with `--seed-session '{"workerId":"teammates.proofreeder"}'`, misspelling the folder name. What happens? *(edge case)*
   Answer: No worker has that id, so the run is refused: `No worker "teammates.proofreeder". Nothing was written`, exit code 2, and nothing is stored. The id must match the folder path exactly, team folder dot worker folder. (Facts §3 and §7: installation.ts:687; the fact sheet's bad-id example with `teammates.nobody`.) The exact error text is Reference material, so a reader only needs to know the run is refused and nothing is written.
6. You ran the researcher from the terminal with `--session make-it-yours`. Where do you look to see every step that run took, and what could stop it from showing up there? *(edge case)*
   Answer: In the DevTool. Run `pnpm fsdev dev` (the `@flow-state-dev/devtool` package must be installed, or it stops with `DevTool assets not found`) and open the address it prints. `fsdev run` writes the session and request to the app's own store, the one the DevTool reads. Work down the navigator, flow `agent`, then the session, then the request, or add `?session=make-it-yours` to the address. The Stream tab lists every item of the request in order. The trace view lays them out as a timeline by block, with each block's input and output, and a generator's panel shows the system prompt the model saw. A run made while the page is open appears when you reload. The DevTool acts as one user, the config's `devtool.userId`, so a run made as a different user does not show. (Facts §5: ds:73, dt:91-93, dt:126-140, ds:100-115, ds:128, dev:717; flag 3.)
