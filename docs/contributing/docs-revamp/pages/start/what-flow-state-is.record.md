## 2 · Cold-read questions

1. In the Teammates starter, you want the researcher to say where each fact came from in a different way, for example a link after every claim. What do you edit, in which language, and when does the researcher start following it?
   Answer: The body of the researcher's WORKER.md (workforce/teams/teammates/workers/researcher/WORKER.md). It is plain-language Markdown instructions, not TypeScript. The frontmatter says who the worker is and what it can use, and the body is its brief. Edit the body and restart the app: the workforce kit reads the workforce/ folder at start-up, so the instructions change on the next start. (README.md:65,82; researcher WORKER.md:9-12; packages/workforce/src/kit/workforce-kit.ts:1-9,168-181)
2. Your app already has a team of workers, and you want it to hand coding tasks to Claude Code, a feature somebody else packaged. What do you add, and where? Does it matter where in the list you put it?
   Answer: Add the kits: one line per kit, each kit's factory called with its config, in the kits list of createFlowState({ kits }) (createFlowState comes from @flow-state-dev/engine). Here that means harnesses(...) from @flow-state-dev/harness-manager/kit and claudeCode() from @flow-state-dev/claude-code, next to workforce(...) from @flow-state-dev/workforce/kit. harnesses requires workforce and fills its slots, and claudeCode fills the slot that harnesses opens for coding agents. The order in the list does not matter: kits install in requires order. A missing required kit is refused when the app is built. (packages/core/src/kit/define-kit.ts:1-5; packages/engine/src/flowstate/types.ts:124-137; packages/engine/src/flowstate/kits.ts:1-20; harnesses-kit.ts:96-108; claude-code kit.ts:72-80)
3. Name the layers of a Flow State app from the top down, with what you do at each. You only want to try the Teammates starter today. Which layers do you need to understand?
   Answer: Starter (you run it), kits (you install them), flows (you call them), blocks (you write them), and the engine (it runs them). To run a starter you need none of the four below the top: you run it with pnpm --filter @flow-state-dev/teammates dev, with Node.js 22.18+, pnpm and one model key, and you go down a layer only when you need to. (README.md:21,30-59; the layers table in the fact sheet)
4. Two people use your deployed Teammates app. Alice edits the researcher's instructions inside the app. Where is her edit stored, does the WORKER.md file in your repo change, and what does Bob see? *(edge case)*
   Answer: Her edit is her own copy of the worker under the same id. It is stored as one row in her user scope, at workforce/workers/<id>, in the app's store, which is a SQLite file under .fsdev/ in the starters. The WORKER.md in the repo is never written while the app runs. Bob still gets the standard worker from the file: a worker in Alice's roster is visible only to her, in the organization she is signed in to. In general, code (worker files, flows, the kits in the config, React pages) lives in your repo, and data (conversations, tasks, state, memory, a user's own workers) lives in your database. (packages/workforce/test/worker-roster.test.ts:259-296; apps/docs/docs/workforce/durable-hire.md 'What is stored', 'Who can reach a worker'; README.md:11,59)
5. You add a second researcher to the team by creating a new folder under workers/. The folder holds the new WORKER.md and a notes.txt file of your own, and you mistype a line in the WORKER.md frontmatter. What happens when you start the app? *(edge case)*
   Answer: The app refuses to start, and the error names each problem. Every file in the kit's folder must be used, so the stray notes.txt stops the start and is named. A WORKER.md that does not parse also stops the start, naming that worker. Once both are fixed, the folder with a valid WORKER.md is served as a new worker: adding a folder adds a worker. (packages/core/src/kit/define-kit.ts:68-75; packages/workforce/test/workforce-kit.test.ts:75-121; README.md:82)
6. The server crashes while the researcher is partway through a long piece of work. When the app comes back, what happens to that work? Would the answer be the same if the app ran on in-memory stores? *(edge case)*
   Answer: On the starters' SQLite store the run picks back up where it stopped. Durable execution is on by default when the stores persist (filesystem, SQLite, Postgres), so the continued request replays the completed work from the durable log, under the same request id, instead of running it again. Over in-memory stores durable execution is off unless you force it on, so the resume does not hold there. (packages/engine/src/flowstate/types.ts:319-333; goals/continue-interrupted-run/continues-not-restarts/goal.md:4-6; labs/teammates/host.mts:400,403)

- CLI output formats: `fsdev run` writes NDJSON, one event per line, to stdout as the run proceeds. The sentence after it (a coding agent writes, runs, reads and fixes a flow) is the model and stays, with the link to Build with your coding agent. → R-35
