Internal (skills/process): two changes to the epic and issue lifecycles — a published-POC practice on never-merged spec PRs, and per-PR reviewer guidance written for two audiences.

**Spec PRs can now carry a POC, so a direction is validated before it's implemented (new `spec-poc` skill).** A spec PR never merges, which makes it the cheapest place in the process to put throwaway code: it can't rot into the codebase, can't accrete public surface, and doesn't have to be good. `spec-poc` turns that from a one-line aside in `spec-template.md` §7 into a practice with four kinds — a **characterization** test pinning how the system already behaves (the cheapest and most under-used, since a spec resting on an unchecked premise is the expensive failure), a **shape** POC writing the composition out in real files, a **visual** POC as a self-contained HTML file for anything with a look, and, at epic altitude, an **end-state** POC showing what the whole set looks like once every issue has landed. That last one answers the question only an epic can ask — *does the division into issues hold?* — at the objective gate, which is the last moment changing it is cheap. Where a fork is genuinely contested a POC carries 2–3 radically different variants at **equal effort** (a strawman manufactures consent for the option the author already preferred) and the pick becomes a numbered Decision. Triggered, never default; costs **zero** review rounds; non-blocking but **disclosed**, so nobody approves a gate on a premise nobody said was unchecked. It never merges: the implementation branch is cut from fresh `origin/main`, so only the spec *document* lands, and anything worth keeping is graduated under `tdd` as a real CI spec or a `goals/` entry rather than copied.

The skill sits beside the two throwaway-code skills we already had, split by **who reads the result**: `prototype` answers *what should we do* for you privately, `settle-claim` answers *who is right* for a review thread that stopped converging, and `spec-poc` answers *is this direction right* for reviewers and the human at the gate. A spec POC is proactive and stops the loop forming; a settlement is reactive and fires only after prose has already failed twice.

POCs live in `spec-poc/<ISSUE-ID>-<slug>/`, which is deliberately **not** a pnpm workspace package — so `turbo`-driven `pnpm typecheck` and `pnpm test` never see it, and `spec-poc/**` is added to `knip.json`'s root ignore. This matters because CI runs on every PR into `main`, spec PRs included, and the orchestrators read that signal: quick-and-dirty code anywhere inside a package would turn a spec PR red and break the gate. Verified by committing a POC with an unresolved import, an undeclared dependency, a type error and a failing spec, and confirming all three CI gates stay green and the spec is never collected.

**Every PR description now carries reviewer guidance for two audiences (new `pr-reviewer-guidance.md`).** A human has scarce attention and is the only reviewer who can judge direction and scope; an automated reviewer has unlimited attention and no sense of altitude. A description written for one fails the other, so PRs carry two blocks: the **reviewer contract** (static per PR kind — what this artifact is and at what altitude to review it) and **"Parts worth reviewing closely"** (authored fresh — 1–3 items, each naming *where* · *the question to answer* · *what a wrong answer costs*, plus where the author is genuinely unsure and what is deliberately absent). The new doc is canonical for both and defines the three altitudes: a spec PR asks reviewers to aim *higher* than their default, an epic PR raises that to the set, and an implementation PR is the one place a bot's exhaustiveness is actively **wanted** — there the guidance points at where risk is concentrated (BP-035 second paths, BP-031 caller-controllable input, BP-030 legacy shapes) and names what was already settled upstream so an approved Decision isn't re-argued inline. Implementation PRs had no reviewer guidance at all before this.

The implementation-PR contract comes in **two variants, picked by route**, because the two routes need opposite things said. On the spec route the approach is human-approved, so review is aimed at the code against that direction. On the **direct route** (a bug, or a one-screen agent-brief change) there is no spec, no §6 and no spec PR — the PR *is* the only gate, so the approach itself is in scope and the diagnosis chain (does the repro reproduce, is the named cause real, does the fix address the cause, does the regression test fail without it) is what a reviewer checks hardest. Using the spec-route text on a bug would dangle a link to a spec nobody wrote and suppress exactly the review that route depends on.

Supporting changes: the epic-spec template gains **§3 Shape of the whole** for the end-state POC (running index and open questions shift to §4/§5); both spec templates exclude POC files from line-level review the way the solution sketch already was; `issue-spec` Step 4 routes between the published and private POC routes and Step 6 requires both reviewer blocks; `issue-implement` Step 9 gains the implementation-PR contract; `epic-lifecycle` and the `epic-agent` gain the end-state POC step before the objective gate; and BP-037/BP-040 record both practices. Deliberately unchanged: `epic-wake.js`, because a POC's *trigger* is judgment rather than mechanism — once the practice has run a few times, the parts that turn out to be mechanism (dedupe, the cap, disclosure at the gate) are candidates for the script the way settlement already is.
