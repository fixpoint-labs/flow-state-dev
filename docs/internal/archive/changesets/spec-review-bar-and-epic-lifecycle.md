Internal (skills/process): two changes to how specs get reviewed and how multi-issue runs are framed.

**Spec review is now an explicit direction check with a convergence budget (new BP-040).** Spec-PR feedback is triaged against one test — *does acting on this change the approach?* Above the line it's folded into the spec; below it, it's recorded verbatim in the spec's new §13 "Review notes for the implementer" and answered once, never rewritten into the design prose. The default disposition is *note*, and the burden of proof is on folding. Spec review is budgeted at **two rounds**, after which the spec is declared converged and goes to the approval gate with remaining threads carried as implementer notes; a third round requires a genuine spec-level finding. Open spec-PR threads gate nothing (the spec PR is never merged) and a bot `CHANGES_REQUESTED` neither trips the approval gate nor extends the budget. Below-the-bar spec comments no longer block implementation. Spec PR descriptions now lead with a reviewer contract — what's in scope to challenge, what's deliberately unsettled — the one lever available on automated reviewers we can't instruct. Canonical rule lives in `docs/contributing/orchestration.md` → "Spec review: the bar and the convergence rule".

**`issue-fleet` is renamed `epic-lifecycle`, and a multi-issue run now always happens under an epic.** It sits alongside `issue-lifecycle` as the second of exactly two lifecycles — an issue has one, a set of related issues has one — with explicit phases (EPIC_SETUP → AWAITING_OBJECTIVE → RUNNING → EPIC_WRAP). The epic was previously an optional coordination layer; it is now the unit of work, so parallelism is a property of an epic rather than a mode of its own. A batch of unrelated issues is not an epic and should run as independent `issue-lifecycle` sessions rather than be wrapped in a fabricated one. The "fleet" role noun is retired in favour of "the coordinator" throughout the orchestration skills and worker agents.
