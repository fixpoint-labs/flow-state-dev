# Workforce Coordination: Gaps to Today

This is the refactor material for
[Workforce Coordination: How It Should Work](workforce-coordination-concept.md). The concept doc is
the model; this file is the backlog that feeds FIX-2056's sub-issues: what the model replaces, the
terms it retires, and where today's code differs, phase by phase. It is kept apart from the model on
purpose, so the model stays readable.

## What changes

| | |
| -- | -- |
| Lost | Settling any task by hand. The blocked status. Suspending for a person on a host without durable execution. Reporting every failure automatically |
| Narrowed | Tasks only to delegates (or `delegates: all`). Workers changing their own delegates. A split's `{ answer, pieces }` result |
| Changed | Listed below, each by the concept rule that says it |
| Kept | Patterns, which are plan boards already. Who settles a row: the drain for an inline row (`orchestration/src/task-board/index.ts`, header), the claim gate for a dispatched one (`orchestration/src/task-board/blocks/dispatch-row.ts`, header), never the worker block. Pluggable claim orders. A delegate's memory across routed tasks. Routing, rounds and records. A coding run resuming its coding session, after a question or a steer (`harness-manager/src/door.ts:15-20`). A retry re-entering the session its task ran in (`workforce/src/conversation-board/board.ts:184-189`). The agent flow, the built-in worker flow for a worker that names none (`workforce/src/agent-worker-flow.ts`, header). The Shift Coordinator, Shift Manager's coordinator worker, still `chief-of-staff` (`shift-manager/teams/devteam/workforce/org/workers/chief-of-staff/WORKER.md`, `shift-manager/README.md:3`). Changed, by rule:

- Rule 6: when a task is done; only `suspendForUser` makes it waiting on a person.
- Rule 7: every ending, a failure included, reaches the filer.
- Rule 8: the durability sweeper pays what a board owes.
- Rule 9: waiting on a task with `getTask`; a deadline doesn't cancel the task.
- Rule 10: calls, with their own `deadline`; no automatic reply; sends and calls queue.
- Rules 11 and 12: one Inbox item per stop; a question holds its task, before it starts or midway,
  and code-consumed answers suspend; an answer resumes or releases; the filer hears its task's questions.
- Rule 14: board mode; a worker's plan is a plan board; a dispatcher can wait.
- Rules 15 to 17: roles checked at hire; dependencies within one board; one `dispatch` at a time.
- Rule 19: a goal-seek loop needs a plan board.
- Rule 20: four filer task tools, also public actions; one `updateTask` rule per field; fixed output.
- Rule 22: the worker reports progress with `reportProgress({ statusNote, output })`, claim-bound.
- Rule 21: a message reaches any task of its user's, or one of its user's own conversations by `{ session }`, and never steers.
- No rule: recurring work is a schedule (Tasks); every coordinator can be messaged (Routing).

Counted per mechanism, the model takes 109 to 56: the
[reduction check](https://claude.ai/artifact/QNetb3YFwTCAypMm1EkE4M) lists each one and what it becomes.
