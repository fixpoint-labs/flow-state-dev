## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

**In plain terms.** `.work()` lets a step run in the background — capturing memory after a
chat turn, generating a session title. We tell users the request waits for those tasks:
*"The request executor drains the pool exactly once before the SSE stream closes — your
stream stays open until every queued task settles"*
(`apps/docs/docs/advanced/sequencer-side-chains.md:68`).

That is true on one path out of four. When a request succeeds, `runAction` waits for the
background pool and then writes `completed` (`runAction.ts:1409` → `:1425`). When it fails,
is aborted, or the client disconnects, it writes `failed` / `aborted` / `interrupted` with
no wait at all (`:1584`, `:1616`, `:1658`). The helper's own docstring says so out loud:
*"Skipped entirely on the abort/disconnect/error paths"* (`:88-97`).

So on three of four paths the record says the request is over while the request's own
background work is still running and still writing.

### 1a. Blast radius — who is affected, how badly, how often

Stated deliberately, because its absence on the sibling issue FIX-1000 cost months. The
honest answer here is narrower than "P0" suggests in one direction and worse in another.

**Who.** Only a request that queues background work *and* ends on a non-success path.
Nothing else in the system is touched. There is **no cross-user or cross-tenant exposure**
— the writer, the record, and the session all belong to the same request. This is a
request lying about itself.

**How often.** More often than "error path" implies. The three exposed paths include
`interrupted`, which is what a user closing the tab mid-stream produces, and `aborted`,
which is the stop button. In this repo's own reference app, every chat turn queues three
background tasks — `biasCheck`, `mem.captureFromItems`, `autoTitle`
(`apps/kitchen-sink/flows/chat-agent/run/run.ts:43-55`). A user who stops a long answer, or
navigates away from one, hits this on a normal turn.

**How badly — and this splits hard by host:**

| Host | What actually happens | Severity |
|---|---|---|
| **Ephemeral** (Vercel `waitUntil`, Next `after()`, Lambda) | `onBackgroundWork(finished)` is the only thing keeping the sandbox alive (`createInboundTransportHost.ts:347-349`), and `finished` resolves the moment `runAction` returns. On a catch path that is *before* the pool settles, so the platform is free to freeze or kill the container with a memory write in flight | **Real. Lost or half-applied writes during normal operation** |
| **Long-lived** (`@flow-state-dev/node`, BullMQ) | The process survives, the task finishes, the write lands. What remains is a window where the record says "over" and a write is still coming | **A correctness wart with no consumer today** |

**Nothing reads request status as a liveness signal today.** `isTerminalRequestStatus` has
three consumers and none of them is a reclaimer: stream teardown
(`stream-routes.ts:126`), a dispatch-failure guard (`createInboundTransportHost.ts:79`), and
item-map cleanup in the Postgres/SQLite request stores. The tombstone sweep that would have
read it was designed and retired by FIX-992. FIX-1000, which the earlier version of this
spec named as a downstream consumer, is now in Backlog, unmerged.

**So the case for fixing this is the ephemeral one, not the reclaimer one** — and that is
what sets the scope. Anything in this design whose only justification was "a future
reclaimer needs the guarantee to be total" is cut (§12).

**Why now.** Ephemeral deployment is the default target, and the failure is silent: no
error, no warning, a memory write that just didn't happen.

### 2. Solution in plain terms

**Give the three catch paths what the success path already has.**

The success path already does the right thing, in the right order: wait for background
work, then stop the heartbeat, then flush, then write the record, then tell subscribers.
The catch paths do the last four and skip the first. The fix is to put the wait in, and to
keep the other four in the same relative order once it is there — because inserting a wait
that can last thirty seconds into a sequence that was previously instantaneous breaks two
things that were fine when the gap was microseconds:

- **The heartbeat is cleared first on the catch paths** (`:1559`), so during a long drain
  another process's recovery sweep sees a stale entry and writes `interrupted` over a live
  request (`request-recovery.ts:42-61`). The same false terminal, written by someone else.
- **The terminal status event is published before the record is patched.** A client that
  receives it closes its stream and re-reads the record (`useSession.ts:841-857`), so it
  would cache `in_progress` permanently with nothing left to re-fetch.

Both are fixed by adopting the success path's order, not by inventing one.

**Tenets this leans on.** *Tenet 1 — coherence*: a record that says "finished" while
execution continues is the incoherence the epic exists to remove. *Tenet 3 — subtract*: the
deliverable is a reordering plus one loop, and it deletes three comments that document the
bug.

### 3. Tradeoffs & alternatives

**The decision criterion: the failure direction must be conservative.** Over-reporting
liveness leaks. Under-reporting corrupts.

| Candidate | Failure direction | Verdict |
|---|---|---|
| **Drain with a timeout** | The bound expires → terminal written with a task still running → **under-reports**. The bound *is* the hole, and it opens exactly under load | **Rejected** |
| **Cancel the pool on teardown** | Cancellation is cooperative, so a task that never checks its signal keeps running → **under-reports**. On disconnect it also reverses FIX-663, killing the fire-and-forget work that feature exists to protect | **Rejected** |
| **Hold the record non-terminal until the pool settles** | Over-reports. Conservative | **Rejected on cost:** it makes the client-facing status carry a second meaning, so a failed request reads non-terminal to every client until unrelated background work finishes |
| **Drain unbounded, matching the success path** *(chosen)* | Process dies mid-drain → record stays `in_progress` → **over-reports**, and `request-recovery.ts:56` already sweeps that to `interrupted` on restart | **Chosen** |

**Why unbounded is defensible.** The success path is already an unbounded drain (`:1409`,
deliberately passed no signal per FIX-663). Extending it adds **no new risk class**. If an
unbounded drain were unacceptable it would already be unacceptable on the most common path
in the system.

**The honest cost.** A caller that `await`s a failing request now waits for its background
work. The streaming client does not — the error item is emitted before the drain — but a
non-streaming caller does. That is the same bill the success path already pays.

### 4. Focus practices (1–5)

- **BP-035 (second-path checklist)** — the whole issue is a second path nobody walked. It
  applies again *inside* the fix: inserting a long wait into a short sequence is what
  exposes the heartbeat and publish-order problems in §2.
- **BP-003 (verification evidence)** — each path gets a test asserting the *ordering*
  (`runAction` has not returned while a task is parked), not merely that a drain happened.
- **BP-030 (tolerate the old shape)** — background tasks may emit after the emitter has
  begun teardown. The `safeEmit` swallow in `drainRequestWorkPool` (`:108-114`) is
  load-bearing on these paths and must not be tightened.

### 5. What using it looks like

**No public API changes.** No flow, block, capability, or client signature changes shape; a
user writes the same code before and after. What changes is that the documented `.work()`
guarantee becomes true on every outcome instead of one.

### 6. Decisions & rules — the sign-off surface

1. **Drain on all four terminal paths, not just the error path.**
   *Rejected:* fixing only the error path, as the issue's framing implies.
   *Locks in:* disconnect is treated as an exposed path — a POC on the real path (§7) shows
   its background signal is clean, so it behaves like error, not like abort.
   *Cost of getting it wrong:* the most common non-success path in production stays broken.

2. **The drain is unbounded.**
   *Rejected:* a bounded drain with a timeout.
   *Locks in:* a request holds its runtime handle until its background work settles, on
   failure as well as success.
   *Cost of getting it wrong:* a bound fails in the corrupting direction, and does so
   exactly when tasks are slow.

3. **Do not cancel background work on the disconnect or error paths.**
   *Rejected:* firing the background signal on every terminal path.
   *Locks in:* FIX-663's guarantee that fire-and-forget work survives transport teardown.
   *Cost of getting it wrong:* a silent reversal of a shipped feature, and it would not even
   be sound — cancellation is cooperative.

4. **The drain runs to quiescence, not one snapshot.**
   *Rejected:* a single `drainAll()` call. `drainAll` splices one snapshot of `entries`
   (`request-work-pool.ts:98`), so a nested `.work()` queued by a draining task lands after
   the splice and is never awaited.
   *Locks in:* a background task may itself queue background work and the request still
   waits for it. This changes the **success** path too, which today has the same hole.
   *Cost of getting it wrong:* the headline guarantee is false in a reachable case, and
   silently — a single-writer test still passes.

5. **Fix the ordering in place. No new finalize seam.**
   *Rejected:* routing all four terminal writes through one `finalizeRequest` helper.
   *Locks in:* a fifth terminal path added later must re-derive the ordering rather than
   inherit it — the recurrence risk this spec accepts in exchange for a one-file change.
   *Cost of getting it wrong:* we pay a second, larger PR later if a fifth path appears, or
   this issue recurs.
   **This reverses the earlier scope, and the reason is in §7:** the seam only pays for
   itself if it owns *every* writer, and Decision 6 says it doesn't. A seam that unifies
   three of five writers is a name over a partial ordering, which reads as a guarantee it
   doesn't give.

6. **The invariant covers the background work pool. Lifecycle observers and TTS are named
   carve-outs, not silent ones.**
   *Rejected:* moving `onFinished` / `onErrored` above the record write, and folding TTS
   settlement into the wait.
   *Locks in:* after this change, a terminal status means **"no background task from this
   request can still write."** It does **not** mean "nothing at all can write" — a lifecycle
   observer still runs after the record write on all four paths and can mutate resources,
   and a cancelled TTS chain still emits during teardown.
   *Cost of getting it wrong:* a consumer that reads the narrow guarantee as the broad one
   builds on a promise we didn't make. §11 documents the carve-out; §12 files it.
   *Why cut:* both are **different writers**, not the one in the problem statement. Moving
   observers is a user-visible semantics change on every path (a hook reading its own
   request would see `in_progress`), and neither is made worse by this change. There is no
   consumer today that needs the total guarantee (§1a).

**Non-goals.** The other end of the window — a context reading resource state *before* its
`in_progress` record exists — is FIX-1002 and is untouched. Making
`isTerminalRequestStatus` a sound liveness predicate is not attempted; it returns true for
`suspended`, which deliberately never drains (§12).

**Size: one file of logic (`packages/engine/src/execution/runAction.ts`) plus a two-comment
correction in `packages/core/src/execution/request-work-pool.ts`. One PR.** Derived against
the call graph in §7, not asserted — including why the multi-file problem the previous
scope hit does not arise here.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

#### The ordering, before and after

Success path today, which is the reference:

```
observers (:1379-1389) → TTS finalize (:1393) → DRAIN (:1409) →
clear heartbeat (:1412) → flushes (:1418-1421) → patch record (:1425) →
publish status event (:1434) → … → onFinished (:1532) → deregister (:1541)
```

Catch paths today — the prologue clears the heartbeat for all three, then each branch runs
its own copy:

```
clear heartbeat (:1559) → [error item] → publish status event → flushes →
patch record → TTS cancel → observers → deregister (:1697)
      ▲ no drain anywhere
```

Catch paths after:

```
[error/abort item] → TTS cancel → DRAIN to quiescence → clear heartbeat →
flushes → patch record → publish status event → observers → deregister
```

Four moves per branch, and every one of them makes the branch match the success path:

| Move | Why it is in scope |
|---|---|
| Insert the drain before the flushes | The fix |
| Move the heartbeat clear out of the prologue (`:1559`) to just after the drain | Without it the drain window lets `detectInterruptedRequests` write `interrupted` over a live request (`request-recovery.ts:42-61`, `set(…, "any")` — no version guard). **The change creates this exposure; today the gap is microseconds** |
| Move the status event below the patch | A client closes its stream on the terminal event and re-reads the record (`useSession.ts:841-857` → `:454-466`). **The change grows this window from microseconds to the length of the drain** |
| Move `ttsHook.cancel()` above the drain (from below the patch) | Otherwise a failing request keeps synthesizing through an unbounded drain — new provider `speak()` calls it will never deliver. **A cost regression the change would introduce** |

**The test applied to every candidate change was: is the fix incomplete without it, or does
the change newly break it?** Everything above fails that test one way or the other.
Everything in §12 passes it and is cut.

The client-visible error/abort *item* stays at the top of the branch, so a caller still
hears the failure immediately. It is already a separate call that precedes the status emit
(`:1648` before `:1649`, `:1574` before `:1575`).

#### Quiescence needs no new pool API

`drainAll` already returns `{ completed, failed }` and returns empty when `entries` is
empty (`request-work-pool.ts:88-103`). So "repeat until a pass consumes nothing" is
expressible today, inside `drainRequestWorkPool`:

```
// Illustrative — a sketch, not the contract.
// Unconditional FIRST pass, then repeat. A `while (pendingCount() > 0)` guard
// would skip the drain entirely when every task settled early, losing their
// failure logging and leaving entries unconsumed — the exact case
// drainRequestWorkPool's own comment at :106-110 says it deliberately avoids.
let consumed;
do {
  const r = await pool.drainAll({ onPendingChange: safeEmit });
  consumed = r.completed.length + r.failed.length;
  logFailures(r.failed);
} while (consumed > 0);
```

#### Why this stays one file — the part the previous scope got wrong

Four facts, each checked against the tree at `26664927`:

1. **Pool submission already converges.** Exactly one production call site:
   `packages/core/src/blocks/sequencer.ts:728`, inside `dispatchWorkTask`, fed by
   `.work()` / `.workIf()` / `.forEachBackground()`. Everything else a `addTask(` grep
   returns is the task board's unrelated `collection.addTask` — a name collision, not a
   second submitter. Nothing upstream of `runAction` needs to change.
2. **`drainRequestWorkPool` cannot reject.** With no signal, `drainAll` resolves through
   `Promise.all` over per-task-caught settlements (`request-work-pool.ts:119-136`);
   `notifyDrainListener` and `safeEmit` both swallow. So the heartbeat clear needs no
   `finally` and the catch block's cleanup structure is untouched.
3. **The heartbeat clear lands immediately after the drain — never below the patch.** That
   is exactly where the success path already puts it (`:1412`). Its position *relative to
   `patchRequestRecord`* is unchanged from today on every path.
4. **Therefore the two outer safety nets stay out of the diff.**
   `createInboundTransportHost.ts:339-345` and `request-continuation.ts:165-176` both
   deregister unconditionally in a `finished.finally(...)`. Review correctly established
   that this makes a *failed terminal patch* unrecoverable and that no one-file change can
   fix it. **That is true and it is not this issue.** A rejecting `patchRequestRecord`
   strands the record identically today, on all four paths; fact 3 is what guarantees this
   change neither creates nor worsens it. It goes to §12.

#### External terminal writers — verdicts, not silent skips

| Site | What it is | Verdict |
|---|---|---|
| `createInboundTransportHost.ts:83` | `markRequestFailed` on a **dispatch** failure — the run never started | **No drain.** No execution context, no pool |
| `execution/request-recovery.ts:56` | Crash-recovery sweep in a *different* process | **No drain.** The owning process is gone. This is also the safety net for a process that died mid-drain (§3) |
| `runAction.ts:1288` | The `suspended` patch | **No drain, deliberately.** Suspend is a pause, not an end, and the docs already say so (`sequencer-side-chains.md:397`). See §12 |
| `context/reactive-dispatch.ts:161`, `runAction.ts:384`, `:1535` | `ErrorItem` / observer payloads, not record writes | **Not terminal writers.** Ignore |

#### POC on this branch (throwaway, never merged)

`spec-poc/FIX-1001-drain-terminal-paths/` — a characterization test driving the real
`runAction` against `createInMemoryStores`, nothing mocked. It **refuted the issue's
premise** that the exposure is "largely closed by the signal" for both abort and disconnect:

| Case | final record | background signal aborted | acted *after* `runAction` returned |
|---|---|---|---|
| **A · error** | `failed` | false | **true** |
| **B · disconnect** | `interrupted` | false | **true** |
| **C · abort** | `aborted` | **true** | false |
| **D · success** *(control)* | `completed` | false | false |

Error and disconnect are the same exposure. Only explicit `/abort` is closed by the signal
— and even that only locally: `wasIntentionalAbort` reads the record flag `abortRequested`,
so the **multi-instance abort** path (`abort.test.ts:137`) takes the `aborted` branch with
the local background signal never firing. §10 owes that variant a real test.

### 8. Implementation sequence

Single PR; no DAG.

1. **Pin current behaviour.** Port the POC's four cases into `packages/engine/test/` as
   characterization tests that pass on unmodified `main`. This is the feedback loop.
2. **Make the drain loop to quiescence** inside `drainRequestWorkPool`, and correct its
   docstring (`:88-97`). Verify the success path with the nested-work case from §10.
3. **Reorder the three catch branches** — the four moves in §7, all in one step. Splitting
   them leaves an intermediate commit that hands the bug to the recovery sweep.
   The characterization tests from step 1 now fail, and are inverted.
4. **Delete the comments that document the bug** (tenet 3): the docstring claim at
   `:88-97`, the inline note at `:1399-1408`, and `RequestWorkPool.drainAll`'s interface
   docstring in `packages/core/src/execution/request-work-pool.ts:74` (*"Skipped on
   abort/disconnect/error paths"*) plus the "drains it exactly once" claim at `:6-7`.
5. **Re-run the §7 greps** and reconcile the tables before opening the PR.

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| No background work queued | `drainAll` is a cheap no-op; no spurious `backgroundTasks: 0` item (the guard at `:129-134` handles this and must survive) |
| A background task **throws** during the drain | Already handled: failures are logged (`:121-127`). The terminal status is **not** downgraded — a failed side task doesn't change the request's outcome |
| A task **settled before** the drain runs | Its entry is still in the pool and its failure still needs logging. This is why the first pass is unconditional (§7) |
| A task emits after emitter teardown | `safeEmit`'s swallow (`:112-118`) is load-bearing here. Do not tighten it |
| Explicit `/abort` arrives **mid-drain** | Tasks self-cancel via the background signal and settle as rejections; the drain resolves. Do **not** pass a signal to `drainAll` |
| A background task never settles | The record stays `in_progress` — the conservative direction (§3). Recovered by `request-recovery.ts:56` on restart |
| Multi-instance abort (202 path) | `abortRequested` is set remotely, so the record takes the `aborted` branch while the local background signal never fires. The drain is what makes this path honest |
| A draining task queues a **nested** `.work()` | The loop re-enters until a pass consumes nothing (Decision 4) |
| The drain outlasts the **stale threshold** (30s default) | The heartbeat is still running, so the `activeRequests` entry stays fresh and `detectInterruptedRequests` skips it |
| An **observer** queues `.work()` | **Not awaited — the named carve-out** (Decision 6). Observers run after the record write, so their pool entries land after the drain. Documented, and filed as a follow-up (§12) |
| The record patch **fails** | The status event has not been published yet, so no subscriber has been told the request ended. Unchanged from today: the record stays `in_progress` and the outer `finished.finally` deregisters it, which is the follow-up in §12 |
| `incomplete` (token-budget stop) | Rides the success branch (`:1368`, `:1426`), so it inherits the fix with no extra work. It belongs in the terminal set wherever this guarantee is cited |
| Suspension | Patches `suspended` with no drain, deliberately (`:1288`, and `sequencer-side-chains.md:397` documents it). Out of scope — §12 |

### 10. Testing strategy

This is a Bug (`diagnose`), so the feedback loop comes first. The tier is vitest against
`createInMemoryStores` driving the real `runAction`, in `packages/engine/test/` alongside
`abort.test.ts`, which already has drivers for each terminal path.

**Goal check.** For each terminal path: a `.work()` task parked on a gate, the path driven
to its terminal status, and the assertion that **`runAction` has not returned** while the
task is still parked. That single assertion is the whole contract — false today on three
paths, true on all four after.

**Behaviours (each must fail before the fix on the paths it covers):**

1. `failed` — the record is not terminal until the pool settles.
2. `interrupted` — same. **The regression the issue's own framing would have missed.**
3. `aborted` — same, **including the multi-instance variant** where `abortRequested` is set
   on the record but the local background signal never fires. That variant is the one the
   signal never covered, so it is what justifies draining the abort branch at all. Extend
   the existing 202 case at `abort.test.ts:137` with a parked `.work()`.
4. `completed` — unchanged (guards the refactor).
5. **Nested work** (Decision 4): a `.work()` task that queues another when it runs. Fails
   against a single `drainAll()`, passes against the loop — the only test that separates them.
6. **Settled-before-drain**: a task that already failed before the drain runs still gets its
   failure logged and its entry consumed. The case a `pendingCount()` guard would skip.
7. **Heartbeat survives the drain**: a catch-path request whose work outlasts the stale
   threshold is **not** picked up by `detectInterruptedRequests`. Drive it with a short
   `staleThresholdMs`, not a long task.
8. **Record before news**: at the moment a subscriber observes the terminal status event, a
   read of the record already returns the terminal status. Assert **from the subscriber's
   side** — the defect is a client caching `in_progress` off a closed stream, which an
   internal call-order assertion cannot see.

**Plus one `packages/integration-tests` scenario — required, not optional.** AGENTS.md:
*"You change the request lifecycle (`runAction`, scope seeding, session journal, store
contracts, resume) — add a scenario that exercises the new contract."* A `testFlow` scenario
pinning terminal record/event ordering on a **non-success** path.

**Reuse the harnesses already in the repo — do not port the POC's stack.** It used a
separate vitest config and timing-based sampling (`settle(120)`), which is flaky under load
and was throwaway scaffolding:

| Need | Use |
|---|---|
| Deterministic park/release, and "has the run settled?" | `deferred()` and the `runSettled` pattern (`background-work-recovery.test.ts:65`, `:587-612`) |
| Drivers for each terminal path | `abort.test.ts` |
| `drainAll` / quiescence-loop unit semantics | `request-work-pool.test.ts` |

**Leave `packages/integration-tests/src/scenarios/work-pool-signal-isolation.test.ts`
alone.** It is the FIX-663 guard on Decision 3 and must stay green. Do not duplicate it.

## Spec evolution *(the change story, not an audit log)*

**Re-scoped after six review rounds against a two-round budget.** The direction was right
from the first draft and never contested: drain the pool before the terminal record write.
What kept growing was the *settle set* — each round found another writer that outlives the
record (observers, then TTS, then the heartbeat, then the registry entry), and each round's
fix introduced the next round's defect. By round six the change had stopped being one file:
review established that `createInboundTransportHost.ts:339-345` and
`request-continuation.ts:165-176` deregister unconditionally, so the recovery behaviour the
spec had come to promise was undeliverable in one PR while the spec still claimed
*"Size: Small — one file."*

Two things reset the scope.

**The blast radius was never stated, and stating it changes the answer.** §1a is new. The
case for this fix is ephemeral hosts losing background writes, not a future reclaimer
reading request status — and no such reclaimer exists: FIX-992's tombstone sweep was
retired, and FIX-1000, the consumer the earlier version cited, is in Backlog unmerged. Every
piece of scope whose only justification was "the guarantee must be total for a downstream
consumer" lost its justification with it.

**One test replaced the growing invariant list:** *is the fix incomplete without this, or
does the change newly break it?* That keeps the drain, the quiescence loop, the heartbeat
move, the publish/patch order, and the TTS cancel — all of which the change itself breaks
or leaves broken. It cuts observers, TTS settlement, the `suspended` predicate, and the
failed-patch recovery path, each of which is a real defect that this change does not touch.
They are filed as follow-ups in §12 rather than absorbed.

The result is smaller than v1, not larger: no convergence seam (Decision 5 reverses it), a
narrower guarantee stated out loud (Decision 6), and a size claim derived against the call
graph rather than asserted.
