# FIX-1001: Background work outlives its terminal request record — Implementation Spec

> **Linear issue:** FIX-1001 · **Epic:** FIX-980 — Honest task substrate · **Priority:** P0 · **Blocks:** nothing today; **informs** FIX-1000 (see §12)

## Spec evolution *(the change story, not an audit log)*

- **Spec drafted.** Framed as *one convergence point missing on three of four paths*, not as three candidate mechanisms to choose between. A POC on the real path (§7) **corrected the issue's central premise**: the asymmetry is three-way, not two-way — disconnect is in the same exposed class as error, not the closed class with abort. That correction is what settles the scope: the fix cannot be "special-case the error path," because the error path is not special. Small / 1 PR.

- **v2 — the drain alone does not buy the invariant.** Round 1 confirmed the direction and then found three mechanism gaps that a drain-before-record-write does not close, each verified against the tree (§7). **The success path is not the correct reference it was drafted as**: `onFinished` runs *after* both the drain and the record write there too, with a live context. So v2 changes three things — the drain runs **to quiescence** rather than one snapshot, **lifecycle observers move above** the drain, and the stream-terminating **status event moves below** it (the client-visible error item stays early). The chosen mechanism (one seam, unbounded, no cancel) is unchanged; what changed is that the seam now orders four things instead of two, on **four** paths rather than three.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

**In plain terms.** When a request finishes, the runtime writes a final status onto its
record — `completed`, `failed`, `aborted`, `interrupted`. That status is supposed to mean
*this request is over*. On three of the four paths it doesn't. Background tasks the request
queued are still running, and they can still write.

`runAction` drains its background work pool exactly once, on the success path
(`runAction.ts:1409`). The helper's own docstring says it is *"skipped entirely on the
abort/disconnect/error paths"* (`:88-97`), and the catch block bears that out: three terminal
record writes (`:1584` aborted, `:1616` interrupted, `:1658` failed), none preceded by a
drain.

**Why it is P0 rather than a tidy-up.** Anything that reasons about liveness from request
status is reasoning from a record that **under-reports what is still running**. That premise
was load-bearing for a tombstone sweep FIX-992 designed and then retired — its §12 names this
issue as *"the record goes terminal **too early**"*, the mirror of FIX-1002's *"the record
appears **too late**"*. A sweep or reclaimer built on request-record liveness would be wrong
today, in the corrupting direction: it would conclude "no live observer" for a scope that
still has one, and purge under a live writer.

**What the issue got wrong, and why it changes the fix.** The issue states the exposure is
"largely closed by the signal" for **both** abort and disconnect, leaving error as the lone
open path. That is a two-way split, and it is wrong. A POC on the real path (§7) shows a
**three-way** split:

| Terminal path | background task's own `ctx.signal` | drained? | still able to write after terminal? |
|---|---|---|---|
| `completed` (success) | clean | **yes** | **yes** — via `onFinished` (`:1532`), below |
| `aborted` (explicit `/abort`) | **fired** | no | largely no — the signal stops it |
| `interrupted` (disconnect) | **clean** | no | **yes** |
| `failed` (error) | **clean** | no | **yes** |

**Round 1 widened the last column.** The drain is not the only way a request keeps writing
after its record goes terminal. Lifecycle observers run *after* the record write on every
path — including success — against a live context that can mutate resources and queue more
background work (§7, Decision 5). And a single `drainAll()` never awaited work queued while
it was draining (§7, Decision 2). So the success path is the reference for the *drain* and
for nothing else; all four paths need the fix.

The reason is deliberate and load-bearing: the signal a `.work()` task sees is a **separate
controller** that listens only on the `/abort` registry (`runAction.ts:889-902`). Transport
teardown never reaches it — FIX-663 made that so on purpose, precisely so a client disconnect
does not kill legitimate fire-and-forget work. So disconnect leaves the task running for
exactly the reason abort does not.

This matters for scope: **the error path is not special**, so the fix cannot be a special
case for it. Two of the three broken paths are broken, and one is half-closed by an
unrelated mechanism we do not want to extend.

### 2. Solution in plain terms

**Drain the pool on every terminal path, and route all four paths through one place that
cannot be added to without draining.**

The fix is to stop having four hand-written copies of "write the terminal record" that each
had to remember the drain, and instead have **one seam** that settles everything and then
writes. A fifth terminal path added next year inherits the ordering rather than re-deriving
it.

The ordering is the design, and each step earns its place by closing a specific gap (§7):

- **Observers run first.** They execute arbitrary blocks against the live context, so running
  them after the drain — or after the record write, as all four paths do today — means the
  request can still write once it claims to be finished.
- **The drain runs to quiescence, unbounded.** One `drainAll()` awaits a snapshot; work
  queued while it drains is missed. A *bound* is the one thing that would reintroduce the
  unsafe failure direction (§3).
- **The stream-terminating status event comes after the drain, the client-visible error item
  before it.** The caller still learns its request failed immediately. But the status event
  ends every subscriber's stream, so emitting it first makes anything the drain produces
  undeliverable.
- **The record write is last**, so it is the only thing that claims "terminal," and it claims
  it only once true.

**Tenets this leans on.** *Tenet 5 — one convergence point*: an invariant enumerated at one
entry point is the expensive kind; this one is currently enforced at one of four, which is
the defect itself. *Tenet 1 — coherence*: a record that says "finished" while execution
continues is the incoherence the epic exists to remove. *Tenet 3 — subtract*: the fix removes
a duplicated terminal-write shape rather than adding a mechanism beside it.

### 3. Tradeoffs & alternatives

**The decision criterion, from the issue: the failure direction must be conservative —
over-reporting liveness leaks, under-reporting corrupts.** Saying "still live" when nothing
is running costs disk and a deferred reclaim. Saying "not live" when something is still
writing corrupts. Every candidate below is judged on where it fails, not on how well it works.

| Candidate | Failure direction when it fails | Verdict |
|---|---|---|
| **Drain with a bound** | The bound expires → terminal is written with a task still running → **under-reports**. The bound *is* the hole | **Rejected.** It fails in the corrupting direction by construction, and it does so exactly under load — when tasks are slow and reclaimers are most active |
| **Cancel the pool's tasks** | Cancellation is cooperative; a task that never checks its signal keeps running → **under-reports**. And on disconnect it *reverses FIX-663*, killing the fire-and-forget work that feature exists to protect | **Rejected.** Wrong failure direction *and* it destroys a deliberate behaviour |
| **Mark the request non-terminal until the pool settles** | The record lags → **over-reports**. Conservative | **Rejected on cost, not direction.** It makes the client-facing status field carry a second meaning ("can anything still write") on top of the one it has ("is my turn over"), so a failed request would read non-terminal to every client and route until unrelated background work finished |
| **Drain unbounded, through one seam** *(chosen)* | Process dies mid-drain → record stays `in_progress` → **over-reports**. Conservative, and already recoverable: `request-recovery.ts:56` sweeps orphaned `in_progress` records to `interrupted` on restart | **Chosen** |

**Why unbounded is defensible rather than reckless.** The success path is already an
unbounded drain (`:1409`, deliberately passed no signal per FIX-663). Extending it to the
other three adds **no new risk class** — it makes three paths consistent with the one that is
already correct. If an unbounded drain were unacceptable, it would already be unacceptable
today on the most common path in the system.

**The honest cost.** A failing request now holds its runtime handle until background work
settles. The client is not made to wait (the error emit precedes the drain), but the process
is. That is the price of the record telling the truth, and it is the same price the success
path already pays.

**What we are deliberately not fixing.** This makes `terminal` honest. It does **not** make
`absent` or `in_progress` honest — a context captures resource state *before* its
`in_progress` record exists, which is FIX-1002 and is confirmed by a POC on FIX-992. See §6
Decision 5 and §12: this issue closes one end of the window, not both.

### 4. Focus practices (1–5)

- **BP-035 (second-path checklist)** — the whole issue is a second path that was never
  walked. The implementer must walk *every* terminal path, including ones added since this
  spec was written, via the §7 command rather than by reading the catch block.
- **Tenet 5 / convergence** — the deliverable is not "add three `await drain()` calls." Three
  calls is the same defect with a longer fuse. It is one seam every terminal write passes
  through.
- **BP-003 (verification evidence)** — each of the four paths gets a regression test that
  asserts the *ordering* (drain before record write), not merely that a drain happened.
- **BP-030 (tolerate the old shape)** — background tasks may emit items after the response
  emitter has begun teardown; the existing `safeEmit` swallow in `drainRequestWorkPool`
  (`:108-114`) is load-bearing on these paths and must not be tightened.

### 5. What using it looks like

**No public API changes, so no usage examples.** This is a runtime-internal ordering fix
inside `runAction`. No flow, block, capability, or client-facing signature changes shape; a
user writes exactly the same code before and after. What changes is what the persisted record
means, and that is covered by §6 Decision 5 and the docs plan in §11.

### 6. Decisions & rules — the sign-off surface

1. **Drain on all four terminal paths, not just the error path.** *Rejected:* fixing only the
   error path, as the issue's framing implies. *Locks in:* disconnect is treated as an exposed
   path, because the POC shows its background signal is clean (§7). *Cost of getting it wrong:*
   the most common non-success terminal path in production stays broken.

2. **The drain is unbounded, and it drains to quiescence — not one snapshot.** *Rejected:* a
   bounded drain with a timeout; and a single `drainAll()` call. `drainAll` splices **one
   snapshot** of `entries` (`request-work-pool.ts:98`), so a task queued *while* the pool is
   draining — a nested `.work()` from a draining task, or one queued by an observer under
   Decision 5 — is appended after the splice and is never awaited by that call. One call
   therefore does not establish the invariant this issue exists to establish. *Locks in:*
   finalize loops until the pool reports no pending work. *Cost of getting it wrong:* the
   headline guarantee is false in exactly the case that motivates it, and silently so — the
   single-writer test still passes. *Note:* this makes the pool's own API unchanged; the loop
   lives in the seam. Closing the pool to new submissions was rejected — observers are allowed
   to queue work (Decision 5), and a closed pool would drop it rather than wait for it.

3. **Do not cancel background work on the disconnect or error paths.** *Rejected:* firing the
   background signal on every terminal path. *Locks in:* FIX-663's guarantee that
   fire-and-forget work survives transport teardown. *Cost of getting it wrong:* a silent
   behavioural reversal of a shipped feature, and it would not even be sound (cancellation is
   cooperative).

4. **One convergence point.** Every terminal record write in `runAction` goes through a single
   finalize seam. *Rejected:* three added `await drainRequestWorkPool(ctx)` calls — round 1's
   proposed simplification. *Locks in:* a fifth path cannot be added without inheriting the
   whole ordering. *Cost of getting it wrong:* this exact issue recurs.

   **Round 1 argued this was over-specified for a one-file change, and the verification in §7
   settles it the other way.** Three bare awaits were a fair simplification of what v1
   described — insert a drain, keep everything else. They cannot express what v2 actually
   requires: *observers → drain to quiescence → terminal status event → flush → record write*,
   a four-way ordering where two of the four steps move **past** the record write and one
   moves **below** an emit that currently precedes it. That is not a line you can forget to
   add; it is a sequence you can get wrong in five places. The grep audit in §7 also cannot
   check it — greps find terminal *writes*, not whether an observer ran before or after one.

5. **Lifecycle observers run above the finalize seam, on all four paths.** *Rejected:*
   leaving them where they are and narrowing the invariant to exclude them. Today
   `onErrored` / `onFinished` run **after** the terminal record write on every path —
   `:1583→:1595`, `:1615→:1625`, `:1657→:1668/:1674/:1681`, and on success `:1425→:1532` —
   and `runObserver` executes an arbitrary block against the same live `ExecutionContext`
   (`:296-323`), so an observer can mutate resources and can itself queue `.work()`. *Locks
   in:* the record write is genuinely the last thing the request does. *Cost of getting it
   wrong:* Decision 6's guarantee is false by construction, and an `onFinished` that queues
   background work reintroduces the whole bug through the front door. *Consequence worth
   naming:* observers no longer observe a terminal record. Any observer reading its own
   request's status mid-observation sees `in_progress` — that is the honest state, since the
   request is not over, but it is a behaviour change and §11 documents it.

6. **Request status becomes a sound liveness proxy at the terminal end only — and the spec
   says so out loud.** After this change, `status ∈ {completed, failed, aborted, interrupted}`
   genuinely implies no execution context from that request can still write. It does **not**
   follow that a *missing* or `in_progress` record implies no observer — FIX-1002's window is
   untouched. *Locks in:* anyone building reclamation on request-record liveness needs
   **both** issues, and this spec must not be cited as delivering the whole guarantee.

7. **Split the catch-path emit: the client-visible error/abort *item* stays above the drain;
   the stream-terminating *status event* moves below it.** *Rejected:* v1's "emit, then
   drain," which emitted `request.failed` / `request.aborted` / `request.interrupted` before
   the drain. Those three event types are terminal to every subscriber:
   `isTerminalRequestStreamEvent` (`subscribe-helpers.ts:34-49`) returns true for them, the
   store iterators `yield` then `return` (`pollEvents:141,:156`), and the SSE pump `break`s
   (`stream-routes.ts:285-299`). So anything a background task emitted *during* the drain
   carried a higher sequence number than an event that had already ended the stream —
   unreachable to live subscribers **and** to a reconnecting one, whose catch-up read hits the
   same terminal and returns. v1's §7 claimed those items were preserved by moving the
   flushes; they were persisted but never deliverable. *Locks in:* the latency intent of v1's
   Decision 6 survives — `emitTerminalError` / `emitAbortedMessage` are separate calls that
   already precede the status emit (`:1648` before `:1649`, `:1574` before `:1575`), so the
   caller still hears the failure immediately. *Cost of getting it wrong:* items emitted
   during the drain are silently undeliverable, which is the same class of dishonesty this
   issue is closing, one layer out.

**Size: Small — one file (`runAction.ts`), single PR — but it is a reordering, not an
insertion.** The terminal block on all four paths is resequenced; no new module, no store,
adapter, schema, or pool-API change. Round 1 read v1 as "add three awaits to a four-branch
function"; the honest description is "resequence one function's terminal block, four ways."

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

**POC on the spec branch (throwaway, never merged) — what it showed.**
`spec-poc/FIX-1001-drain-terminal-paths/`, a characterization test driving the real
`runAction` against `createInMemoryStores` with nothing mocked. Full writeup in that
directory's `RESULT.md`.

```bash
pnpm exec vitest run --root . --config spec-poc/FIX-1001-drain-terminal-paths/vitest.config.ts
```

| Case | final record | background `ctx.signal` aborted | acted *after* `runAction` returned | record status it observed |
|---|---|---|---|---|
| **A · error** | `failed` | **false** | **true** | **`failed`** |
| **B · disconnect** | `interrupted` | **false** | **true** | **`interrupted`** |
| **C · abort** | `aborted` | **true** | false | `in_progress` |
| **D · success** *(discrimination)* | `completed` | false | false | `in_progress` |

**It refuted the issue's premise.** Error and disconnect are the *same* exposure: the task's
own signal is clean, it is still parked when the record goes terminal, and when it wakes it
observes a terminal record through the same live stores handle. Only explicit `/abort` is
closed by the signal. That is why Decision 1 covers all four paths.

**Two things it also surfaced.** (a) The signal half is already pinned by a passing test on
`main` — `packages/integration-tests/src/scenarios/work-pool-signal-isolation.test.ts`
(*"transport-level abort does NOT abort background `.work()`"*); the POC adds only the
record-is-already-terminal half. (b) `wasIntentionalAbort` is read from the record flag
`abortRequested`, not from which controller fired, so the **multi-instance abort** path
(`handleAbortRequest`'s 202 branch, `abort.test.ts:137`) takes the `aborted` branch with the
local background signal never firing — a fourth variant that behaves like disconnect. §9
carries it.

**A method note, because it nearly produced a false green.** The POC's first cut fired the
signal from a `.tap()` and ended the chain. Firing a signal does not enter `runAction`'s
catch block — something must *throw* — so cases B and C ran to completion and reported
`completed` while their assertions still passed. Each case now asserts the terminal status it
was named for. **A case that passes without reaching the path it tests is the same failure as
a grep that silently matches nothing**, which is the discipline the next section applies.

**Enumerate by command, not by inspection.** The epic's writer table shipped wrong three
times because it was hand-maintained. Run these before trusting anything below, and again
before opening the PR. Use `grep -a`: `packages/engine/src/context/resource-registry.ts`
carries a NUL byte at line 619, and a bare `grep` reports *nothing* on such a file — a clean
grep and a skipped grep are indistinguishable.

**Result of (1), verified on the same commit.** Terminal record writes inside `runAction`:

| Claim | Verdict | Evidence |
|---|---|---|
| A single `drainAll()` does not await work queued *during* the drain | **CONFIRMED** | `request-work-pool.ts:98` splices one snapshot of `entries`; `addTask` (`:31-52`) appends to the live array afterwards. The nested task is still pending when the outer one settles |
| Lifecycle observers run after the terminal record write, with a live context that can write and can queue | **CONFIRMED — and broader than reported.** Reported for the catch paths; it is true on the **success** path too | `:1583→:1595`, `:1615→:1625`, `:1657→:1668/:1674/:1681`, and `:1425→:1532`. `runObserver` (`:296-323`) runs an arbitrary block against the same `ctx` |
| Emitting the terminal status event before the drain makes anything emitted during the drain undeliverable | **CONFIRMED at both layers** | `isTerminalRequestStreamEvent` (`subscribe-helpers.ts:34-49`); `pollEvents` yields then returns (`:141`, `:156`); `pumpSubscription` breaks (`stream-routes.ts:285-299`). A reconnecting subscriber re-reads the terminal and returns again |

**What this does to v1's premise.** v1 said *"the success path already does the right thing;
the fix is to give the other three what it has."* That is now only true of the drain itself.
The success path drains before its record write (`:1409` → `:1425`) and then runs
`onFinished` at `:1532` — after both. So the success path carries gap 2 as well, and it is
**being changed, not merely named.** One path was already correct on one of three axes.

**The seam.** Sketch — pseudocode, naming roles not functions; the real names are the
implementer's. Deliberately partial: see the scope note below it.

```
// ONE finalize path. Every terminal record write in runAction goes through it.
// Ordering is the deliverable; each step is here because a specific gap needs it.
async function finalizeRequest(ctx, stores, requestId, terminal, observers) {
  // 1. Observers FIRST (Decision 5). They run against the live ctx and may
  //    mutate resources or queue more .work() — so they must run before the
  //    drain that is supposed to settle everything, not after the record write.
  await runObservers(observers);

  // 2. Drain to quiescence (Decision 2), not one snapshot: an observer above,
  //    or a nested .work() from a draining task, lands in the pool AFTER
  //    drainAll's splice. Unbounded, and deliberately passed NO signal —
  //    FIX-663's note at :1400: an explicit /abort mid-drain must not
  //    early-abort the wait; tasks self-cancel via their own background signal.
  while (pool.pendingCount() > 0) await drainRequestWorkPool(ctx);

  // 3. Only now the stream-terminating status event (Decision 7). Emitting it
  //    earlier ends every subscriber's iterator, so items emitted during the
  //    drain become undeliverable. The client already heard the failure: the
  //    error/abort ITEM was emitted by the caller, above this seam.
  await response.emitRequestStatus(terminal.status);

  // 4. Flush below the drain and below the emit, so drain-emitted items and
  //    the status event itself are persisted.
  await flushItemsEventsCheckpointsTraces();

  // 5. The single record write — genuinely the last thing the request does.
  await patchRequestRecord(stores, requestId, terminal);
}
```

**Scope the seam narrowly — it is `drainFlushAndPatch`, not "the terminal block."** Round 1
flagged that the sketch elides real per-path work and that a helper this centrally placed
becomes a magnet for unrelated consolidation. Explicitly **outside** it, staying per-path:
`ttsHook.finalize()` (success) vs `ttsHook.cancel()` (catch); `ctx.requestRuntime.status`
assignment; `emitActionLifecycleSeam`; retention eviction; the per-path log line; deregister.
Only steps 1–5 above converge. The implementer should not treat the sketch as the whole
terminal sequence — it is the part that must be identical everywhere, and nothing more.

**Call order on a catch path becomes:** error/abort *item* emit → `finalizeRequest(...)` →
per-path TTS/status/seam/log → deregister. The item emit staying on top is what preserves the
latency intent (Decision 7).

**What this does not touch.** The background signal's wiring (`:889-902`) is unchanged —
Decision 3. `dispatchBackgroundWork` is unchanged. No store, adapter, or schema changes.

### 8. Implementation sequence

Single PR; no DAG.

1. **Pin current behaviour first.** Port the POC's four cases (§7, `spec-poc/`) into a real
   test file as *characterization* tests asserting today's behaviour. They must pass on
   unmodified `main`. This is the feedback loop.
2. **Introduce the finalize seam** and route the success path through it. **This is a
   behaviour change, not a rename** — `onFinished` moves above the drain and the record write
   (Decision 5), and the drain becomes a loop (Decision 2). v1 had this step as a no-op; it
   is not. Cover it with the success-path cases from step 1 before moving on.
3. **Route the three catch paths through it**, moving the flushes below the drain and the
   status emit below the drain while leaving the error/abort item above it (Decision 7). The
   characterization tests from step 1 now **fail**, and are inverted to assert the fixed
   behaviour. This is the tracer bullet.
4. **Remove** the stale docstring claims that the drain is skipped on these paths
   (`runAction.ts:88-97`) and the inline comment at `:1399-1408`. **Removal is part of the
   deliverable** (tenet 3) — a comment that documents the bug is worse than no comment.
   Also correct `RequestWorkPool.drainAll`'s interface docstring in
   `packages/core/src/execution/request-work-pool.ts:74` (*"Skipped on abort/disconnect/error
   paths"*).
5. **Re-run the §7 greps** and reconcile the tables above before opening the PR.

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| No background work queued | `drainAll` is a cheap no-op; no spurious `backgroundTasks: 0` status item (the existing guard at `:120-124` already handles this and must survive) |
| A background task **throws** during the drain | Already handled: `drainAll` returns settled results and failures are logged (`:116-119`). The terminal status is **not** downgraded — a failed side task does not change the request's outcome |
| A background task emits after emitter teardown | `safeEmit`'s swallow (`:108-114`) is load-bearing on these paths. Do not tighten it |
| Explicit `/abort` arrives **mid-drain** | Tasks self-cancel via the background signal and settle as rejections; the drain resolves. Do **not** pass a signal to `drainAll` |
| A background task never settles | The record stays `in_progress` — the conservative direction (§3). Recovered by `request-recovery.ts:56` on restart |
| Multi-instance abort (202 path) | `abortRequested` is set remotely, so the record takes the `aborted` branch while the local background signal never fired. The drain is what makes this path honest — the one variant the signal never covered (POC §4, RESULT.md) |
| Suspension / replay paths | `SuspensionError` exits before the terminal block; confirm the suspend path at `:1288` is unaffected — it is a non-terminal `patchRequestRecord` and out of scope |
| An **observer** queues `.work()` | Must be awaited. This is why observers run above the drain (Decision 5) and why the drain loops (Decision 2) — an observer's task is queued after any single `drainAll` snapshot would have been taken |
| A draining task queues a **nested** `.work()` | Same: the loop re-enters until the pool is quiet. A single pass misses it (`request-work-pool.ts:98`) |
| An observer **throws** | Unchanged: `runObserverSafely` already swallows on the catch paths, and the success path's `runObserver` already propagates. Moving them earlier must not change which of the two is used on which path |
| A background task emits **during** the drain | Its item is persisted *and* deliverable, because the stream-terminating status event has not been emitted yet (Decision 7). v1 achieved only the first half |
| An observer reads its own request's status | Sees `in_progress`, not the terminal status — the request genuinely is not over. Behaviour change; §11 documents it |

### 10. Testing strategy

**Discipline: this is a Bug (`diagnose`), so the feedback loop comes first.** The seam is
vitest against `createInMemoryStores` driving the real `runAction` — the POC in `spec-poc/`
already establishes it works and is the template.

**Goal check.** For each of the four terminal paths: a `.work()` task parked on a gate, the
path driven to its terminal status, and the assertion that **`runAction` has not returned**
while the task is still parked. That single assertion is the whole contract — it is false
today on three paths and true on all four after.

**Behaviours to test (each must fail before the fix on the paths it covers):**

1. `failed` — record write happens after pool settles.
2. `interrupted` — same. **The regression the issue's own framing would have missed.**
3. `aborted` — same, including the multi-instance variant where `abortRequested` is set on
   the record but the local background signal never fires.
4. `completed` — unchanged (guards against a regression in the refactor).
5. Ordering: an item emitted by a background task *during* the drain is present in the
   persisted item list on a `failed` request **and is still deliverable** — assert it is
   yielded by a subscriber, not merely persisted. Persisted-but-undeliverable is exactly what
   v1 shipped (Decision 7), and an assertion on the item list alone cannot tell the two apart.
6. FIX-663 preservation: a transport-level abort still does **not** abort a background task's
   own signal. `packages/integration-tests/src/scenarios/work-pool-signal-isolation.test.ts`
   already covers this and must stay green — it is the guard on Decision 3. Leave it alone;
   do not duplicate it.
7. **Nested work** (Decision 2): a `.work()` task that queues another `.work()` when it runs.
   The record must not go terminal until the nested one settles. Fails against a single
   `drainAll()`, passes against the loop — this is the only test that distinguishes them.
8. **Observer-queued work** (Decision 5): an `onFinished` / `onErrored` that queues `.work()`
   or mutates a resource. Assert the write lands before the terminal record write. Run it on
   the **success** path too — that path has the same gap and v1 treated it as the reference.
9. **Emit split** (Decision 7): on a `failed` request, the error *item* is observable before
   the drain completes, and the `request.failed` *status event* is not emitted until after.
   Both halves matter — asserting only the second would pass a version that made the client
   wait for the drain, which is the latency regression Decision 7 exists to avoid.

**Where the tests live.** All of these in `packages/engine/test/` alongside `abort.test.ts`,
which already has the harness for driving each terminal path. Item 6 exists.

**Reuse the harnesses already in the repo — do not port the POC's stack.** The POC used a
separate vitest config and timing-based sampling (`settle(120)`), which is flaky under load
and was throwaway scaffolding, not a proposal:

| Need | Use |
|---|---|
| Deterministic park/release + "has the run settled?" | `deferred()` (`background-work-recovery.test.ts:65`) and the `runSettled` pattern (`:587-612`) — both verified present |
| Drivers for each terminal path | `abort.test.ts` |
| The multi-instance abort variant (item 3) | `abort.test.ts:137` — the existing 202 "in-progress on a different instance, no controller" case, extended with a parked `.work()`. This variant is **absent from the POC**, so it is owed a real test rather than left to implementation discovery |
| `drainAll` / quiescence-loop unit semantics | `request-work-pool.test.ts` |

### 12. Dependencies, open questions & follow-ups

**Nothing blocks this issue.** It is one file's control flow. FIX-992 has merged
(#1035/#1039/#1036) and this builds on that `main`; nothing here depends on its CAS work
beyond sharing the epic's framing.

**The cross-issue fact FIX-1000 needs, stated plainly.** After this change:

- **`terminal` becomes sound.** A record in `completed` / `failed` / `aborted` /
  `interrupted` genuinely implies no execution context from that request can still write.
- **`absent` / `in_progress` do not.** A context captures resource state *before* its
  `in_progress` record is persisted (`createExecutionContext.ts:986` vs `:1041`, and the
  default path writes no stub in front — FIX-992 §12, **POC CONFIRMED**). That is FIX-1002
  and this issue does not touch it.

So **request status is a sound liveness proxy only in conjunction with FIX-1002.** Anything
that reclaims on "no live observer" needs both. Per FIX-992 §12, FIX-1000's per-session
storage nonce reclaims by **unreachability** and needs no observer question at all — if that
is still FIX-1000's direction, it does not need this issue and this issue does not gate it.
FIX-1000 is being specced concurrently; **that reconciliation is the owner's, not resolved
here.**

**Open question for the gate.** Decision 2's *unbounded* half was challenged in round 1 and
upheld by both reviewers, so it is settled. What replaces it as the judgment worth a second
opinion is **Decision 5** — moving observers above the terminal record write is the one
change here with a user-visible consequence (a hook reading its own request now sees
`in_progress`). The alternative was to leave observers where they are and narrow the
invariant instead, which is cheaper but hands FIX-1000/FIX-1002 a guarantee with a carve-out
in it. See "Parts worth reviewing closely" on the PR.

**Follow-up, not in scope.** `runAction`'s catch block is ~140 lines of three near-duplicate
terminal sequences (`:1568-1690`). This spec unifies the *record write*; the emit / observer /
log sequences stay triplicated. That is a deepening opportunity for
`improve-codebase-architecture`, not this PR.
