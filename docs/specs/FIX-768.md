# FIX-768: Expose the trading desk as an MCP server — Claude as the chat/control surface — Implementation Spec

## 1. TLDR

**Plain-language summary.** The trading desk is a real app that today you can only drive from its web UI on a dev box: open it, click Run, watch a 10–20 minute analysis. This change lets you drive the desk straight from a Claude conversation — desktop or phone — the same way you'd talk to any connected tool. Ask Claude to start a report on a ticker and it hands back a handle and returns immediately; come back later and ask for the decision, read your holdings, or record a buy you just made. It's secured for real money by a personal token, not an open endpoint. Under the hood we reuse the framework's already-shipped ability to expose a flow as an MCP server; the desk is the first real app to use it.

**Technical statement.** Add an authenticated MCP tool surface to the trading desk's two flows using the shipped `@flow-state-dev/mcp` adapter, with a job-shaped analysis lifecycle (start → poll → fetch) that never blocks a `tools/call`, a personal-bearer-token principal resolver, and a minimal long-lived Node deployment.

**Deliverables** (grouped to mirror the Implementation Sequence in §5):

- **Server wiring:**
  - Add `createMcpTransportAdapter()` to `adapters` and a bearer-token `resolvePrincipal` to `createFlowState()` in `labs/trading-desk/fsdev.config.ts`.
  - Opt both flows into MCP: `mcp: { enabled: true }` on `flows/analysis/flow.ts` and `flows/portfolio/flow.ts`, with per-action `mcp.enabled: false` on the actions that must not be exposed (`analyze`, `runSummary`, `runArtifacts`, `extractHoldingsFromPdf`) and a `description` on every exposed action.
- **Analysis lifecycle actions (job-shaped):**
  - Add `startReport` action in `flows/analysis/orchestration/` that mints a session, launches `analyze` as a detached background run via `runAction`, and returns the `reportId` handle in seconds.
  - Add `getReport` action that reads a report's status and (when complete) renders the FIX-727 at-a-glance summary as markdown, bound via `mcp.session: { fromInput: "reportId" }`.
  - Add `listReports` action projecting recent sessions to `{ reportId, ticker, status, decision }`.
- **Portfolio actions (new thin flow actions over the repository):**
  - Add `getPortfolio` read action (accounts + holdings + household health) in `flows/portfolio/`.
  - Add `recordTransaction` write action over `ingestLedgerEvents` in `flows/portfolio/`.
- **Deployment:** a committed `Dockerfile` + host config and a personal-token env contract so the desk runs on a long-lived host (Railway as the exemplar) with `DATABASE_URL` Postgres.
- **Docs:** new `labs/trading-desk/docs/mcp-server.md`, plus README + CLAUDE.md sections and one "Driving the desk from Claude" section in the `apps/docs` walkthrough.

**Size estimate.** **Large** — multi-file, multi-package-adjacent, >500 LOC across new actions + deploy + docs. Split as: (PR-1) server wiring + auth + analysis lifecycle actions; (PR-2) portfolio read/write actions; (PR-3) deploy artifact + docs. PR-1 is the load-bearing slice (it proves the job-shaped MCP loop end-to-end).

## 2. Overview

Linear issue: [FIX-768](https://linear.app/fixpoint-labs/issue/FIX-768).

The desk's analysis pipeline and portfolio are locked behind a local web UI. This spec exposes them as authenticated MCP tools so the desk can be driven from Claude (including mobile): kick off a report and get a handle without blocking, poll/fetch the decision later, read the portfolio, and record a position change. It reuses the framework's shipped MCP support (FIX-22, `@flow-state-dev/mcp`) — making the desk the **first production consumer** of that surface — plus the principal-resolver auth seam (FIX-23) and a long-lived Node deployment (FIX-712).

## 3. Background & Research

### 3.1 Findings from framework research (what already exists)

- **`@flow-state-dev/mcp` is shipped and mounted as an inbound-transport adapter.** A flow opts in with `mcp: { enabled: true }` on `defineFlow`; the adapter is passed to `createFlowState({ adapters: [createMcpTransportAdapter()] })`. Route shape is `POST /api/flows/:kind/mcp`, served by the desk's existing `app/api/flows/[...path]/` catch-all with **no new route file** (the adapter's default `basePath` is `/api/flows`).
- **The `mcp` config surface is narrower than the issue assumed.** Flow-level `McpConfig` (`packages/core/src/types/flow.ts:275`) has only `enabled` and `exposeResources`. There is **no `exposeActions`, `stateless`, or `serverInfo`.** Action-level control is `action.mcp = { enabled?, name?, session? }` and a required `action.description`. Every non-opted-out action on an MCP-enabled flow **must** have a non-empty `description` or `defineFlow` throws at registration.
- **`tools/call` is strictly synchronous** (`packages/mcp/src/createMcpTransportAdapter.ts` — `await handle.finished`). It ignores the host's fire-and-forget/202 semantics. A 10–20 min action would hold the JSON-RPC connection for the whole run.
- **MCP resources are stubbed in v1** — `resources/read` for flow-bound resources always denies. Everything the desk exposes must be a **tool**, not an MCP resource. (This matches the issue's own tilt toward tools.)
- **Result content is text only** — the adapter returns `{ content: [{ type: "text", text }] }` from `result.output` (stringified) or the terminal message. No structured/JSON channel. So a tool returns markdown/plain text Claude formats.
- **Auth seam exists and takes `source: "mcp"`.** `resolvePrincipal(ctx)` receives the raw `request` (Authorization header, query token reachable). Shipped helper `createBearerSecretPrincipalResolver({ secret, principal })` constant-time-compares `Authorization: Bearer <secret>` and returns a fixed principal. Configurable host-level on `createFlowState` and per-flow via `defineFlow({ authentication })`.
- **Off-transport execution entry exists.** `runAction(options)` (`packages/engine/src/execution/runAction.ts:491`) executes an action against a sessionId without a transport. This is the mechanism a fast `startReport` uses to launch `analyze` in the background and return.
- **Session correlation over MCP is manual.** No `Mcp-Session-Id` binding; the only cross-call handle is `action.mcp.session: { fromInput: "field" }`, which uses `input.field` as the dispatch sessionId. So a `start` tool must return the sessionId in its text output, and poll/fetch tools take it back as an input argument.

### 3.2 Findings from the desk (current state)

- **Deployment posture is closer than the issue thought.** The desk already moved to Postgres-backed stores (FIX-772): embedded PGlite in dev, real Postgres via `DATABASE_URL` in deploy (`db/portfolio-db.ts`, `fsdev.config.ts`). The issue's "`createFilesystemStores({ developmentOnly })`" premise is stale. What's genuinely missing: a deploy artifact, real auth, and a reachable endpoint.
- **Auth today is a hardcoded client-asserted `userId: "devuser"`** (`app/page.tsx:40`), trusted verbatim by the default `defaultBodyUserIdPrincipalResolver`. No principal resolver is configured. Both flows set `requireUser: true` only. This is a documented dev-only IDOR.
- **`analyze` runs inline in the request, SSE-streamed. No worker, no BullMQ, no `@flow-state-dev/node` dependency.** Not durable.
- **A report *is* a session**, keyed by the `{ ticker, date, costPreset, dataSource }` metadata tuple; the PM commit merges `decision` + `reportStatus: "complete"` into metadata. `runSummary`/`runArtifacts` are existing zero-model read-back actions (compact JSON) invoked `-i '{}'` against a bound session.
- **The FIX-727 at-a-glance Summary is UI-layer.** `buildReportSummary(memosByKey, spine)` (`components/summary/aggregate.ts`) is pure but returns a view model and its inputs are assembled in the browser. There is **no server-side markdown rendering** of it today — this spec adds one (zero model spend; reads stored memos + valuationSpine).
- **Portfolio account/holdings/ledger CRUD are REST routes over `getRepository()`, not flow actions** (a deliberate boundary: `app/api/portfolio/*`). MCP tools map to flow actions only, so portfolio reads/writes over MCP need **new thin flow actions** wrapping the repository (userId from `ctx`, never client-trusted). The existing `thesis-actions.ts` is the precedent shape.

### 3.3 Findings from industry research (MCP long-running work)

- **Claude Desktop's remote-connector tool-call timeout is a hard, non-configurable ~4 minutes.** A 10–20 min blocking `tools/call` is a non-starter across all current Claude clients.
- **The accepted pattern for long work is return-a-handle-and-poll** (start → `get_status` → `get_result`). The MCP spec added a native async **Tasks** primitive (2025-11-25 revision) but **no shipping Claude client supports it yet**, so it must be built by hand out of ordinary tools today and layered later.
- **Small, well-described tool sets beat wide 1:1 API wrappers** for Claude-class clients; return rich results as markdown text; make handles semantic and bind them to the authenticated caller (so a guessed id can't read another principal's data).
- **Static personal bearer token in the `Authorization` header (TLS, Streamable HTTP) is a defensible single-user posture**; Claude's custom remote connector supports a fixed request header (rolling out in beta). Token-in-URL is discouraged (leaks to logs).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Decision: keep this desk-side; do NOT expose `analyze` directly — add a `startReport` action that launches `analyze` as a detached background `runAction` and returns a handle in seconds.**
   Alternative rejected: expose `analyze` as a tool (blocks 15 min → dies at Claude's 4-min ceiling); or graduate a framework "async MCP Tasks" issue and block on it.
   Ramification: locks in the start→poll→fetch shape and a v1 in-process (not restart-durable) background run. Rules out, for v1, a crash surviving mid-run (user re-runs). Carries the load-bearing implementation risk that a detached `runAction` on the long-lived host must actually outlive the `startReport` request — this is the one thing to prove first (§7 goal check). Opens a clean upgrade path to BullMQ durability (FIX-711) and native MCP Tasks without changing tool names.

2. **Decision: expose portfolio reads plus one write (`recordTransaction`) as new thin flow actions over `getRepository()` / `ingestLedgerEvents`; keep the rest of portfolio CRUD REST-only.**
   Alternative rejected: full write parity via flow-action wrappers over every REST route (duplicates domain logic, broadly reopens the deliberate CRUD-stays-REST boundary); or reads-only (drops issue outcome 4).
   Ramification: covers the headline conversational write (record a buy/sell) at minimal surface. Locks in a small tool set. Rules out, for v1, conversational account creation / holdings edits / imports over MCP (still REST). Carries a small duplication cost (one write action alongside the REST `recordManualEvent`), both funneling the same idempotent `ingestLedgerEvents` contract, so they can't diverge in behavior.

3. **Decision: authenticate with a single personal bearer token via `createBearerSecretPrincipalResolver`, returning the fixed household `userId` ("devuser"), wired host-level on `createFlowState` and dropping the client-asserted-`userId` fallback.**
   Alternative rejected: per-user token store / OAuth (out of scope — single user); token-in-URL (leaks).
   Ramification: locks the deployed desk to one principal, matching the existing household key so imported data stays owned. Rules out multi-user. Carries a **companion requirement**: the REST portfolio routes and the web UI bypass the flow router, so a publicly-reachable deployment must gate them too (or keep them network-private) — otherwise the client-asserted-`userId` IDOR remains open on the same host. This is called out as an in-scope risk with a minimal mitigation, not full REST/UI auth hardening.

4. **Decision: render the FIX-727 summary as markdown server-side in a new zero-model `getReport` action, reusing the pure `buildReportSummary`.**
   Alternative rejected: return raw `runSummary` JSON and let Claude format (loses the curated at-a-glance shape); or expose the report as an MCP resource (stubbed in v1).
   Ramification: locks the report's Claude-facing shape to a markdown projection of already-stored state (zero model spend, real-money-gated — never fabricates missing figures). Rules out reusing the React view model directly. Carries a small maintenance coupling: the markdown renderer and the React Summary read the same stored fields, so both must stay honest about gaps.

5. **Decision: reuse the shipped `@flow-state-dev/mcp` adapter as-is; do not modify the framework.**
   Alternative rejected: extend the adapter for async/202 `tools/call` (that's a framework issue, graduates out per the issue's own guidance).
   Ramification: the desk is the first production consumer and validates the shipped surface (the MCP project's "v2 — production tested" milestone). Locks the desk to v1 adapter limits (synchronous `tools/call`, no resources, text-only results) — which is exactly why the design routes long work through `startReport` + detached `runAction` rather than through the adapter's blocking path. Any adapter gap the desk hits becomes a separate framework issue, not scope creep here.

## 4. Technical Design

### 4.1 Architecture

Packages/files involved (all under `labs/trading-desk/` unless noted):

- `flows/analysis/orchestration/list-reports-action.ts` (new) — recent-reports projection.
- `flows/analysis/report-summary-markdown.ts` (new) — pure `buildReportSummaryMarkdown(summary: ReportSummary): string` (reuses `components/summary/aggregate.ts` `buildReportSummary`, moved/shared into a server-safe module if needed).
- `flows/portfolio/flow.ts` — add `mcp: { enabled: true }`; add `getPortfolio`, `recordTransaction` actions; descriptions + opt-outs.

- Docs (see §9).

Framework files referenced (not modified): `packages/mcp/src/createMcpTransportAdapter.ts`, `packages/core/src/types/flow.ts`, `packages/core/src/types/auth.ts`, `packages/engine/src/execution/runAction.ts`, `packages/engine/src/transports/auth/createBearerSecretPrincipalResolver.ts`.

### 4.2 The job-shaped analysis lifecycle (data flow)

```
Claude → tools/call start_report { ticker, costPreset?, dataSource?, userThesis?, riskMandate? }
  startReport action (own throwaway session):
    1. mint reportId (sessionId) + write session metadata { ...tuple, reportStatus: "in-progress" }
    2. runAction({ flow: analysis, actionName: "analyze", sessionId: reportId, input, source: "mcp" })
       — invoked WITHOUT await (detached, top-level execution, not a child of this request)
    3. return { reportId, ticker, status: "started", pollWith: "get_report" }   ← resolves in ~1s
  MCP adapter awaits startReport.finished (fast) → single JSON-RPC text result

... analyze runs 10–20 min in the background, persisting memos + decision snapshot to Postgres ...

Claude → tools/call get_report { reportId }
  mcp.session: { fromInput: "reportId" } binds dispatch to that session
  getReport action (zero model):
    - read session state / metadata → status ∈ in-progress | complete | stopped | error
    - if complete: assemble memos + valuationSpine server-side, buildReportSummary → markdown
    - return status + (progress note | markdown summary | stop banner)
```

Handle binding to caller (security): `getReport`/`listReports` read only sessions owned by the resolved `userId`; a `reportId` for another principal returns not-found, never another user's data.

### 4.3 API surface (exact shapes)

**`startReport`** — input `startReportInputSchema`:
```ts
{ ticker: string;                                  // required
  costPreset?: "fast" | "full";                    // default "fast"
  dataSource?: "fixture" | "live" | "record";      // default "live" on deploy
  userThesis?: string | null;
  riskMandate?: RiskMandateId | null }
```
output: `{ reportId: string; ticker: string; status: "started"; pollWith: "get_report" }`.
MCP: tool `start_report`; `description` explains it kicks off a 10–20 min job and to poll `get_report`.

**`getReport`** — input `{ reportId: string }`; `mcp.session: { fromInput: "reportId" }`.
output (text/markdown): a status line plus, when complete, the at-a-glance summary (decision, conviction, target weight + gates, key risks, trade levels, thesis alignment) rendered from stored state; when in-progress, a progress note (memos completed / pending); when stopped, only the stop banner.

**`listReports`** — input `{ limit?: number }` (default 10); output: markdown table of `{ reportId, ticker, status, decision, when }` for the caller's recent sessions.

**`getPortfolio`** — input `{ }`; output: markdown of accounts + holdings + household health (from `getRepository().getPortfolio(userId)` + `domain/portfolio/math/portfolio-health.ts`), real-money-gated (missing prices → `—`).

**`recordTransaction`** — input over the existing `recordEventSchema` / `LedgerEventInput` shape (account, tradeDate, type ∈ buy|sell|dividend|interest|…, ticker?, quantity?, amount, currency?); output: the ingest report `{ inserted, deduplicated }`. Writes via `getRepository().recordManualEvent(...)` (fixes `source: "manual"`), userId from `ctx`.

**Already-actions, cheap to expose** (set `description`, keep enabled): `adoptThesis` → `adopt_thesis`, `saveThesis` → `save_thesis`, `deleteThesis` → `delete_thesis`, `savePortfolioMandate` → `save_portfolio_mandate`, `clearPortfolioMandate` → `clear_portfolio_mandate`, `setInstructions` → `set_instructions`. Include only those that read cleanly conversationally; opt the rest out.

### 4.4 Auth / principal resolution

```ts
// fsdev.config.ts
resolvePrincipal: createBearerSecretPrincipalResolver({
  secret: requireEnv("TRADING_DESK_MCP_TOKEN"),
  principal: { userId: "devuser" },   // the existing household key
})
```
`requireUser: true` stays on both flows; drop reliance on `defaultBodyUserIdPrincipalResolver` for the deployed config so a client can no longer assert an arbitrary `userId`. The MCP adapter calls `resolvePrincipal` once per request with `source: "mcp"` and the raw `Authorization` header.

### 4.5 State management

No new persistent state schema. `startReport` writes the same session metadata the web "Run" writes (tuple + `reportStatus`). Reads reuse the existing decision snapshot, memos collection, and `valuationSpine` resource. `recordTransaction` writes through the existing `ingestLedgerEvents` transaction (positions + realized gains materialized as today).

### 4.6 Error handling

| Case | Behavior |
|---|---|
| `start_report` for a ticker already running (same tuple) | Return the existing `reportId` with `status: "already-running"` (idempotent-ish; reuse `findSessionForTuple`). |
| `get_report` unknown/foreign `reportId` | Not-found tool result (never another principal's data). |
| `get_report` while in-progress | `status: "in-progress"` + progress note, `isError: false`. |
| `analyze` background run throws/stops | Persisted stop/error state; `get_report` surfaces the stop banner / error, never a half-built decision. |
| Detached run fails to outlive the request (host misconfig) | Detectable via goal check (§7); mitigation is BullMQ durability (upgrade path). |
| Missing bearer / bad token | `resolvePrincipal` throws `PrincipalResolutionError({status:401})` → JSON-RPC `-32001` + `WWW-Authenticate`. |
| `record_transaction` foreign account | `ingestLedgerEvents` ownership guard throws, batch rolls back. |

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|---|---|
| Claude calls `get_report` before `analyze` writes anything | `in-progress`, empty progress note, no error. |
| Two `start_report` calls for the same tuple | Second returns the existing handle (`findSessionForTuple`), no duplicate run. |
| `analyze` stops at a guard (unresolvable ticker, unsupported asset) | `get_report` returns the stop reason/banner; `status: "stopped"`. |
| Report completes between two polls | Next `get_report` flips to `complete` + summary. |
| `reportId` from another principal | not-found. |
| `record_transaction` with an identical fingerprint | dedups to one (documented idempotency); response notes `deduplicated`. |
| Bearer token rotated | old token 401s; no partial access. |
| `dataSource: "live"` provider miss | analyst treats as missing signal (`UNAVAILABLE`), never fabricated — unchanged desk behavior; summary shows `—`. |

Error taxonomy: 401 (auth) fatal; `-32000` server-busy retryable (concurrency); tool-level not-found/in-progress are non-error results; background `analyze` errors are persisted and surfaced on fetch, not thrown at the caller.

## 8. Non-Goals

- **Native MCP async/Tasks semantics in the framework.** The shipped adapter's synchronous `tools/call` is worked around desk-side (start→poll→fetch). First-class async `tools/call` (202/Tasks) is a **separate framework issue** if/when a desk gap forces it — do not modify `@flow-state-dev/mcp` here.
- **BullMQ durability for the background run.** v1 uses an in-process detached run (not restart-durable). Adopting `@flow-state-dev/bullmq` + `@flow-state-dev/node` for durable/retryable runs is the explicit upgrade path (FIX-711), out of scope here.
- **Full portfolio write parity over MCP.** Account creation, holdings edits, CSV/PDF/OFX imports stay REST-only; only reads + `recordTransaction` are exposed.
- **Multi-user / OAuth / per-user token store.** Single personal bearer token only (issue out-of-scope).
- **MCP prompts and MCP resources.** Resources are stubbed in the framework v1; everything is a tool.
- **Full REST/UI auth hardening for public exposure.** This spec authenticates the MCP surface and calls out that a public deployment must also gate the client-asserted-`userId` REST routes + web UI (mitigation noted); comprehensive REST/UI auth is a separate hardening concern.
- **A general-purpose "personal Claude hub" MCP service** spanning beyond the desk (issue out-of-scope; the desk is the wedge). Compare the sibling knowledge-base lab MCP (FIX-855).
- **M2 "chat with the team" (FIX-565/566) changes.** Recommended posture: keep M2 as a distinct in-app UI showcase; MCP is the external control surface. Recorded here as a deliberate note, not a roadmap change (Open Question §11).
- **Deepening opportunity flagged during analysis:** the desk has two parallel read-back surfaces (the browser-assembled FIX-727 Summary and the server `runSummary`/`runArtifacts` JSON). This spec adds a third (markdown). If a fourth consumer appears, consolidating the summary projection into one shared server-safe module is a follow-up via `fsd:improve-codebase-architecture` — not in scope here.
