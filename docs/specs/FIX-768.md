# FIX-768: Expose the trading desk as an MCP server — Claude as the chat/control surface — Implementation Spec

> **STATUS: ON HOLD — superseded pending framework work (2026-07-19).** Spec-PR review surfaced that the desk was being asked to hand-roll around real gaps in the MCP surface. Rather than ship a desk-side workaround (bespoke BullMQ launcher, per-app route gating, two connectors), the gaps are graduated to four framework issues that block this one:
> - **FIX-903** — detached/async `tools/call` (return a handle instead of blocking on completion) — the leverage point; lets `analyze` be exposed directly, no bespoke launcher, BullMQ back to optional.
> - **FIX-904** — lookup-only session binding (find-or-404, not find-or-create) — the read-back half of start→poll→fetch.
> - **FIX-905** — one MCP server spanning multiple flows (product-surface façade) — one desk connector instead of two.
> - **FIX-906** — enforce the principal resolver across all inbound flow routes — a real auth boundary without per-app middleware.
>
> FIX-768 is back in **Todo**, blocked by those four. When they land, this spec is **reshaped to a thin desk consumer** of the improved surface (expose `analyze` detached; `get_report`/`list_reports` as lookup-bound reads; portfolio tools on one façade; no queue/worker required). The §0–§11 body below is retained as the analysis that motivated the split — treat its desk-side mechanisms (BullMQ launcher, Next middleware gate, two-endpoint surface) as **the workarounds we chose NOT to ship**, not as the plan of record.

## 0. v1 Reconciliation (post spec-PR review — AUTHORITATIVE)

> This section governs. It folds the spec-PR review (Codex P1×2/P2, the second-look, Cursor `/simplify`) into a locked v1. Where a statement below conflicts with a later section, this note wins.

- **R1 — Background launch is BullMQ, not a detached `runAction`.** The original "block calls `runAction` un-awaited" mechanism is not viable: a `BlockContext` cannot reach the `FlowStateRuntime`, and importing `fsdev.config.ts` into the action would cycle. v1 adopts the shipped `@flow-state-dev/bullmq`: `start_report` enqueues an `analyze` job on a desk-owned queue and returns the handle; a separate **worker process** holds the runtime and runs `analyze`. Durable across restarts, retry/DLQ for free, precedented. Cost (Redis + a worker process) is real and now in the estimate. (Resolves Codex P1 "launcher seam" + second-look #1.)
- **R2 — The bearer token gates ALL `/api/flows/*` and `/api/portfolio/*` routes via Next middleware, not just MCP action dispatch.** The built-in session/resource routes and the portfolio REST routes read `userId` from query/body and never call `resolvePrincipal`; without a middleware gate, an unauthenticated caller could list/read the household's sessions/resources on a public host. (Resolves Codex P1 "gate all flow routes".)
- **R3 — `get_report` does an ownership/existence lookup and never binds-to-create.** `mcp.session: { fromInput }` auto-creates an empty session on a typo/guess, polluting recent reports. `get_report` reads the session store for a report owned by the caller and returns not-found otherwise. (Resolves Codex P2.)
- **R4 — Cut the 6 "cheap to expose" existing actions.** `adopt_thesis` / `save_thesis` / `delete_thesis` / `save_portfolio_mandate` / `clear_portfolio_mandate` / `set_instructions` have no named consumer, several are session-bound (would throw `no-decision` on an ephemeral MCP session), and they cut against the §3.3 "small tool set" finding. v1 is exactly the 5 tools the issue asks for. (Resolves second-look #2 + Cursor.)
- **R5 — Same-tuple dedup is a non-goal for v1.** `findSessionForTuple` is a client/test mirror, not a server API; a conversational double-start is rare and produces two reports, not corruption. (Resolves Cursor.)
- **R6 — Deploy entrypoint is `fsdev serve` (web) + a worker process; cite `examples/knowledge-base` (FIX-855)** as the shipped MCP-consumer template. No custom Node entrypoint reinventing bind-guard / health / SIGTERM.

## 1. TLDR

**Plain-language summary.** The trading desk is a real app you can only drive today from its web UI on a dev box: open it, click Run, watch a 10–20 minute analysis. This change lets you drive it from a Claude conversation — desktop or phone — the way you'd talk to any connected tool. Ask Claude to start a report on a ticker and it hands back a handle immediately; come back later and ask for the decision, read your holdings, or record a buy. It's secured for real money by a personal token. Under the hood we reuse the framework's already-shipped ability to expose a flow as an MCP server, run the long analysis on a durable background worker, and gate everything behind the token; the desk is the first real app to use this.

**Technical statement.** Add an authenticated MCP tool surface (5 tools) to the desk's two flows using the shipped `@flow-state-dev/mcp` adapter, a job-shaped analysis lifecycle where `start_report` enqueues a durable BullMQ job and returns a handle in seconds, a personal-bearer-token principal resolver plus a Next middleware gate over all flow/portfolio routes, and a long-lived web + worker deployment.

**Deliverables** (grouped to mirror §5):

- **Server wiring & auth:** add `createMcpTransportAdapter()` + a bearer-token `resolvePrincipal` to `createFlowState()` in `fsdev.config.ts`; add a Next `middleware.ts` bearer-gating `/api/flows/*` and `/api/portfolio/*` (R2); opt both flows into `mcp: { enabled: true }` with per-action `mcp.enabled: false` on non-exposed actions (`analyze`, `runSummary`, `runArtifacts`, `extractHoldingsFromPdf`, and the six cut per R4) and a `description` on every exposed action.
- **Durable analysis lifecycle (5 tools):** a desk-owned BullMQ queue (`lib/analysis-queue.ts`) + `worker.ts`; `start_report` (enqueues an `analyze` job, returns the `reportId` handle in seconds); `get_report` (ownership lookup + status + FIX-727 summary as markdown, no bind-to-create); `list_reports`; `get_portfolio` (read); `record_transaction` (write over `ingestLedgerEvents`).
- **Deployment:** `fsdev serve` web process + a worker process + Redis + `DATABASE_URL` Postgres, on a long-lived host (Railway exemplar); personal-token env contract (R6).
- **Docs:** new `labs/trading-desk/docs/mcp-server.md` + README/CLAUDE.md sections; one optional "Driving the desk from Claude" section in the `apps/docs` walkthrough.

**Size estimate.** **Large** — multi-file + new worker process + Redis + >500 LOC. Split: (PR-1) MCP wiring + auth/middleware + BullMQ queue/worker + `start_report`/`get_report`/`list_reports` (the load-bearing async proof); (PR-2) `get_portfolio` + `record_transaction`; (PR-3) deploy + docs.

## 3. Background & Research

### 3.1 Framework constraints that force the design

Shipped and reused as-is; only the design-forcing facts (full inventory in the framework MCP reference `apps/docs/docs/server/mcp.md` and the shipped consumer template `examples/knowledge-base`, FIX-855):

- Opt in with `mcp: { enabled: true }`; pass `adapters: [createMcpTransportAdapter()]` to `createFlowState`. Route `POST /api/flows/:kind/mcp` is served by the desk's existing `app/api/flows/[...path]/` catch-all — no new route file.
- `mcp` config is narrow: flow-level `enabled` + `exposeResources` only (no `exposeActions`/`stateless`/`serverInfo`); per-action `mcp = { enabled?, name?, session? }` and a **required** `description` (registration throws without it).
- **`tools/call` is strictly synchronous** (`await handle.finished`) and **text-only**; MCP **resources are stubbed** in v1. So long work must be started fast and read back via tools, never streamed or blocked on.
- `action.mcp.session: { fromInput: "field" }` uses `input.field` as the dispatch sessionId (the only cross-call handle) — and **auto-creates a session if absent** (the R3 hazard).
- Auth seam takes `source: "mcp"`; `createBearerSecretPrincipalResolver({ secret, principal })` compares `Authorization: Bearer <secret>`. But it only runs on the **transport dispatch path** — the built-in session/resource routes and REST routes don't call it (the R2 hazard). `examples/knowledge-base` is the reference for adapter wiring + a prod fail-closed secret guard + per-action opt-out.
- `@flow-state-dev/bullmq` is shipped (worker, dispatcher, flowstate-adapter, retry, stream-bridge, tests) — the precedented seam for durable background flow execution and the R1 launcher.

### 3.2 Desk (current state)

- Already on Postgres stores (FIX-772) — the issue's "filesystem developmentOnly" premise is stale. Missing: deploy artifact, real auth, reachable endpoint, a worker.
- Auth today is a hardcoded client-asserted `userId: "devuser"`, no principal resolver (documented dev IDOR on both flow routes and `/api/portfolio/*`).
- `analyze` runs inline, SSE-streamed; not durable.
- A report **is** a session keyed by the `{ticker,date,costPreset,dataSource}` tuple; `runSummary`/`runArtifacts` are existing zero-model read-backs (`buildRunSummary` + `readAllMemos`).
- The FIX-727 at-a-glance summary is UI-layer (`buildReportSummary`, pure but browser-assembled) — no server markdown rendering today (this spec adds one under `flows/analysis/lib/`).
- Portfolio account/holdings/ledger CRUD are REST routes over `getRepository()`, not flow actions — MCP reads/writes need new thin flow actions (userId from `ctx`; `thesis-actions.ts` precedent).

### 3.3 Industry research (MCP long-running work)

- Claude Desktop's remote-connector tool-call timeout is a **hard, non-configurable ~4 minutes** — a blocking 10–20 min `tools/call` is impossible.
- Accepted pattern: **return a handle, poll** (start → get_status → get_result). Native MCP **Tasks** (2025-11-25) exist but no shipping Claude client supports them yet — build by hand, layer later.
- **Small, well-described tool sets beat wide wrappers** (the R4 basis); return markdown; bind handles to the authenticated caller (the R3 basis).
- Static personal bearer token in the `Authorization` header (TLS, Streamable HTTP) is a defensible single-user posture; Claude's custom remote connector supports a fixed request header (beta).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Durable background launch via BullMQ (R1).** `start_report` enqueues an `analyze` job on a desk-owned queue and returns the handle; a worker process runs it. Rejected: detached `runAction` from a block (can't reach the runtime, import cycle, zero precedent — Codex P1); in-process desk launcher with `.catch` (viable-but-lighter, unprecedented, non-durable, needs app-code safety nets — kept as the documented lighter alternative). Ramification: durable/retryable runs on real infra (Redis + worker); the deploy is now two processes, not one; the goal check proves the enqueue→worker→fetch loop rather than a fragile survival property.
2. **Reuse the shipped MCP adapter as-is; no framework change.** The desk validates the surface (first production consumer). Locks the desk to v1 adapter limits (sync `tools/call`, no resources, text results) — which is exactly why long work goes through the queue, not the adapter's blocking path. Any adapter gap becomes a separate framework issue.
3. **Personal bearer token gates every route via middleware (R2).** `createBearerSecretPrincipalResolver` → fixed household `userId` for MCP dispatch, plus a Next `middleware.ts` bearer-gating `/api/flows/*` and `/api/portfolio/*`. Rejected: relying on `resolvePrincipal` alone (leaves the session/resource + REST routes as an IDOR on a public host); per-user token store / OAuth (out of scope). Ramification: single principal; the token is the whole-surface gate; full REST/UI auth hardening (rate limits, rotation, CSRF for the web UI) stays a separate concern.
4. **Render the FIX-727 summary as markdown server-side in a zero-model `get_report`, reusing pure `buildReportSummary`.** Rejected: build markdown from `buildRunSummary` + `readAllMemos` and extend `RunSummary` with the risk/scenario fields Claude needs (server-native, avoids a third projection — considered, deferred to keep FIX-727 visual parity without extending the RunSummary schema). Ramification: a third read-back projection (browser Summary, `runSummary` JSON, new markdown); §8 fixes the consolidation trigger so it doesn't drift.
5. **Portfolio reads + one `record_transaction` write as new thin flow actions; rest of CRUD stays REST.** Rejected: full write parity (duplicates domain logic, reopens the CRUD-stays-REST boundary) or reads-only (drops outcome 4). Ramification: headline conversational write at minimal surface; both the action and REST `recordManualEvent` funnel the same idempotent `ingestLedgerEvents`.

## 4. Technical Design

### 4.1 Architecture

Files (all under `labs/trading-desk/` unless noted):
- `fsdev.config.ts` — adapter + `resolvePrincipal` + BullMQ worker/dispatcher wiring; new deps `@flow-state-dev/mcp`, `@flow-state-dev/bullmq`, `@flow-state-dev/node`.
- `middleware.ts` (new) — bearer-gate `/api/flows/*` + `/api/portfolio/*` (R2).
- `lib/analysis-queue.ts` (new) — the desk-owned analysis job queue (enqueue side; imported by the action, no runtime import → no cycle).
- `worker.ts` (new) — the worker entrypoint: constructs the runtime and runs `analyze` jobs.
- `flows/analysis/flow.ts` — `+mcp`, `+startReport/getReport/listReports`, opt-outs.
- `flows/analysis/orchestration/{start-report,get-report,list-reports}-action.ts` (new).
- `flows/analysis/lib/report-summary-markdown.ts` (new) — pure `buildReportSummaryMarkdown(summary): string` reusing `buildReportSummary` (under `lib/` per desk convention).
- `flows/portfolio/flow.ts` — `+mcp`, `+getPortfolio/recordTransaction`.
- `flows/portfolio/{get-portfolio,record-transaction}-action.ts` (new).
- `Dockerfile` + host config (web = `fsdev serve`, worker = `node worker.js`); docs (§9).

### 4.2 Durable analysis lifecycle (data flow)

```
start_report { ticker, costPreset?, dataSource?, userThesis?, riskMandate? }
  startReport action (fast):
    1. mint reportId (sessionId) + write metadata { ...tuple, reportStatus: "queued" }
    2. analysisQueue.add({ sessionId: reportId, input, userId })   ← enqueue, returns fast
    3. return { reportId, ticker, status: "queued", pollWith: "get_report" }
  adapter awaits startReport.finished (fast) → single JSON-RPC text result

worker (separate process): consumes job → runAction({ analyze, sessionId, input }) → persists to Postgres
  (BullMQ retry/backoff/DLQ on failure; report status reflects queued → running → complete/stopped/error)

get_report { reportId }
  ownership lookup: find a session owned by caller.userId with id == reportId (else not-found; NEVER bind-to-create)
  zero-model: status from metadata (+ memo counts from RunSummary while in-progress);
              complete → buildReportSummary → markdown; stopped → stop banner only
```

Handles are bound to the caller: `get_report`/`list_reports` only read the resolved `userId`'s sessions.

### 4.3 API surface (5 tools)

- **`startReport`** input `{ ticker: string; costPreset?: "fast"|"full"=fast; dataSource?: "fixture"|"live"|"record"=live-on-deploy; userThesis?: string|null; riskMandate?: RiskMandateId|null }`; output `{ reportId, ticker, status:"queued", pollWith:"get_report" }`. Tool `start_report`; description says it starts a 10–20 min job and to poll `get_report`.
- **`getReport`** input `{ reportId: string }`; ownership-checked read (no session binding-to-create). Output text/markdown: status line + (complete → at-a-glance summary | queued/running → progress note with memo counts | stopped → stop banner).
- **`listReports`** input `{ limit?: number=10 }`; output markdown table `{ reportId, ticker, status, decision, when }` for the caller's sessions.
- **`getPortfolio`** input `{}`; output markdown accounts + holdings + household health (`getRepository().getPortfolio` + `portfolio-health.ts`), `—` on missing price.
- **`recordTransaction`** input over `recordEventSchema`/`LedgerEventInput`; output `{ inserted, deduplicated }` via `recordManualEvent` (source fixed `manual`), userId from `ctx`.

No other actions are MCP-exposed (R4).

### 4.4 Auth
```ts
// fsdev.config.ts
resolvePrincipal: createBearerSecretPrincipalResolver({
  secret: requireEnv("TRADING_DESK_MCP_TOKEN"),
  principal: { userId: "devuser" },
})
```
Plus `middleware.ts` bearer-checks `Authorization` on `/api/flows/*` and `/api/portfolio/*` (R2), returning 401 before the route reads any client `userId`. `requireUser: true` stays; drop the client-asserted fallback on deploy.

### 4.5 State
No new persistent schema. `startReport` writes session metadata + a `reportStatus` the worker advances; reads reuse the decision snapshot + memos + `valuationSpine`; `recordTransaction` writes through `ingestLedgerEvents` (positions + realized gains materialized as today). The BullMQ job payload carries `{ sessionId, input, userId }` only.

### 4.6 Error taxonomy
401 (auth, from middleware or `resolvePrincipal`) fatal; `-32000` server-busy retryable; tool-level not-found / queued / running are non-error results. Worker job failures are handled by BullMQ retry/backoff/DLQ and surfaced as `reportStatus: "error"` on fetch — never thrown at the MCP caller. The enqueue in `start_report` is awaited (a Redis-down enqueue fails the tool call loudly, not silently). See §6 for the case table.

## 6. Edge Cases

| Edge case | Expected behavior |
|---|---|
| `get_report` before the worker writes anything | `queued`/`running`, empty progress note, no error |
| Two concurrent `start_report` for the same tuple (TOCTOU) | Both enqueue → two reports (dedup is a v1 non-goal, R5); no corruption |
| Worker job fails / throws | BullMQ retry/backoff, then DLQ; `reportStatus: "error"` surfaced on fetch |
| Redis unavailable at enqueue | `start_report` fails loudly (tool error), not a silent lost run |
| Guard stop (unresolvable ticker, unsupported asset) | `get_report` returns stop reason/banner, `status:"stopped"` |
| `get_report` foreign/typo `reportId` | not-found; NO empty session created (R3) |
| completes between polls | next `get_report` flips to complete + summary |
| identical-fingerprint transaction | dedups to one; response notes `deduplicated` |
| token rotated / missing | 401 at middleware; no partial access |
| live provider miss | `UNAVAILABLE`, `—` in summary, never fabricated |

## 8. Non-Goals

- **Native MCP async/Tasks in the framework** (separate issue if a desk gap forces it).
- **In-process detached-run launcher** — rejected for v1 in favor of BullMQ (R1); documented as the lighter alternative if Redis/worker infra is later deemed too heavy for a personal desk (would then need `.catch` + a `stalled` report status + the goal check as app-code safety nets).
- **Full portfolio write parity over MCP** (account/holdings edits, imports stay REST).
- **Multi-user / OAuth / per-user token store.**
- **MCP prompts and MCP resources** (stubbed in framework v1).
- **Full REST/UI auth hardening** — the middleware bearer gate (R2) closes the IDOR; rate-limiting, token rotation, and web-UI session auth are a separate concern.
- **Same-tuple report dedup** (R5) — a double-start makes two reports, not corruption; a server `listSessions`+metadata helper can add it later if double-starts prove common.
- **A general-purpose "personal Claude hub"** beyond the desk (cf. FIX-855).
- **M2 "chat with the team" (FIX-565/566) changes** — recommended: keep as an in-app showcase (Open Question §11).
- **Read-back projection consolidation.** This adds a third summary projection (browser FIX-727, `runSummary` JSON, new markdown). **Consolidate before the next trigger** — a REST summary export or a fourth tool consumer — into one shared server-safe module via `fsd:improve-codebase-architecture`. Not now, but not "indefinitely."
