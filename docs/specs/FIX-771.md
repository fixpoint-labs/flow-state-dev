> This section governs. Where a statement below conflicts with it, this note
> wins. It folds the spec-PR review (Cursor "best approach", Greptile P1, Codex
> P2, and the maintainer's `second-look` pass) into a simpler v1 that

> patching them. The load-bearing architecture — mandate-as-sleeve-container,

- **D1 — Routing is computed at PM commit, not in a post-stage tap.**
  `computeSleeveRouting` runs inside `commitPortfolioManagerMemo` (`writer.ts`),
  exactly like `policyDecision`/`mandateDecision`, and echoes onto the PM memo +
  decision snapshot + `RunSummary` (+ `runArtifacts` for eval parity). **No
  `.tap`, no `sleeveRoutingResource`** — routing is a PM *output* projection, not
  a PM *input* (the `lensConvergence` resource exists only because convergence is
  an input). This removes a resource, a tap file, an ordering contradiction, and
  a double-write hazard.
- **D2 — Explicit non-actionable verdicts.** `SleeveFit.verdict` includes
  `capital-unknown` (unpriced sleeve holdings, or a `pct` cap on an incompletely-priced
  whole book) and `posture-blocked` (a hard capacity veto clamps the target to ≤ 0), so
  §4.7's degradation promises have real places in the contract — unknown valuation is
  never coerced into `fits-*`, and a vetoed/$0-target sleeve is never `recommendedSleeveId`.
- **D3 — Per-sleeve posture reuses the *existing* gate helper, with the reward figure
  recomputed per sleeve.** `flows/analysis/lib/mandate-gates.ts` exports the extracted
  clamp (`clampTargetWeight`/`computeMandateGates`, FIX-790). Routing calls it with
  `resolveMandate(sleeve.riskAppetite)`, `decisionConfidence`, and override. It does **not**
  reuse the stored `rewardToRisk` figure — that `lossAdjustedGlr` baked in the active-run
  mandate's λ; routing recomputes it per sleeve via `computeRewardToRisk({ scenarios:
  rewardBuckets, lossAversion: sleeve.mandate.lossAversion })` (L483). Each sleeve clamps from
  the **raw pre-gate PM target** (`pmRawTargetWeightPct`), not the household-clamped committed
  value, so an aggressive sleeve isn't capped at a conservative run's reduced target (L501). A
  `null rewardBuckets` run (thin/errored forecast) gates **reward-blind** — the reward-floor /
  capacity-veto checks are skipped, never fed a synthesized null figure (L530/L536). Nothing
  re-extracted from `writer.ts`.
- **D4 — Unknown sleeve `riskAppetite` is a SAVE-ONLY guard.** It lives in the
  `savePortfolioMandate` action, NOT in `validatePortfolioMandate` — `seedSession`
  re-runs the validator and nulls the *whole* mandate on any issue, so a stale
  persisted sleeve id must degrade only that sleeve's posture, never blank the
  household IPS (the existing `riskAppetite` precedent).
- **D5 — Utilization is never frozen; the mandate is the single source of
  sleeves.** `summarizeSleeveUtilization` is a pure function of the frozen
  `portfolioMandate.sleeves` + the portfolio snapshot seed already materializes,
  recomputed at routing time and in the Health `useMemo` (the `summarizePortfolioHealth`
  precedent — never frozen). No `state.sleeveUtilization`, no separate
  `state.sleeves`.
- **D6 — Availability is cap-room only; cash is shown separately.**
  `availableToDeploy = max(0, capValue − deployedValue)`. Account cash is surfaced
  as an informational figure, not min-folded into availability (which reintroduced
  a soft cash-attribution rule the no-sub-ledger model rejects).
- **D7 — Eligibility is slimmed to `assetClasses` + `excludeTickers`.** It is modeled at
  the **asset-class** grain (the mandate's `equity|fixed_income|cash|crypto|alternative`),
  not asset *type* — the defensive core is a `fixed_income`+`cash` concept, and class
  avoids the bond-ETF / mixed-fund gap a type list would create. `excludeTickers` are
  UPPER-canonicalized at the **write path** (`savePortfolioMandate`), not the validator
  (which can't mutate and is re-run at seed), so an exclusion never silently fails on case.
  `sectors` and `includeOnlyTickers` are dropped from v1 (they duplicate the household mandate's
  exclusions at sleeve scope). Eligibility stays because a *candidate is not yet held in
  any account*, so account membership alone cannot answer "eligible for the
  aggressive sleeve, not the core" — but asset-class + posture carry the motivating
  core-vs-satellite split.
- **D8 — Slice C ships the narrower "list incumbents, no score" v1.** When the
  fitting sleeve is at cap, list its incumbents ordered by thesis-present-vs-absent
  then staleness — no numeric `convictionProxy`, no `marginPp` hysteresis constant,
  no `cleared` boolean. Same user-facing outcome the issue asks for (name the
  funding candidates, or "none" when the sleeve is empty) without a blind-tuned
  score that FIX-763 would redo wholesale. The scored/ranked displacement is the
  **FIX-763 upgrade**. `funding-source` merges into `sleeve-routing.ts` (two
  exports, one module).
- **D9 — Bundle a `mirrorNullable` helper.** Slice B step 6 touches `writer.ts`'s
  `decisionSnapshot` flatten anyway; the `sleeveRouting` mirror would be a *third*
  hand-copy of the `spread ?? {}`-with-typed-defaults pattern
  (`mandateDecision`/`policyDecision`). Fold a tiny shared `mirrorNullable(obj,
  keys)` so all three gates use it — a few lines, no behavior change, stops a
  fourth future copy.
- **D10 — Routing is proven by deterministic vitest + a fixture `fsdev run`
  smoke, not a real-model goal.** Routing is pure projection math; a mandate-swap
  fixture anti-games it. Real-model goals are reserved for end-to-end smoke
  (the `phase-5-policy.spec.ts` discipline).
- **D11 — Routing carries the inputs its dollar math needs, frozen from the WHOLE book.**
  `computeSleeveRouting` takes a **seed-frozen whole-book snapshot** (`state.sleeveBook`:
  all accounts + holdings + quotes + `householdNav`) and a seed-frozen
  `thesisPresenceIndex` (held ticker → thesis `updatedAt` | null). It does **not** reuse
  `state.portfolioContext` — on a scoped run that snapshot is the *selected* accounts only,
  so a sleeve owning accounts outside `selectedAccountIds` would read empty. The whole-book
  snapshot comes from the pre-scoping account read `seedSession` already does for
  `householdTickerWeightPct` (today discarded after that computation). The capital check
  converts the posture size to dollars against **`pmTargetNav`** (the NAV the PM target is a
  fraction of — the *scoped* NAV on a scoped run, not `householdNav`, L516) and subtracts the
  analyzed ticker's **current value in that sleeve** so it gauges the *incremental* buy, not
  the full target; `householdNav` is used only to resolve `pct` caps. The funding list reads
  incumbents + thesis presence/staleness from these inputs and echoes structured
  `FundingEntry` records (L469), so no commit-time collection fan-out is needed (the
  snapshot-freeze precedent avoids the N+1). These are genuine new frozen fields (whole-book), distinct from the scoped
  `portfolioContext`, and the one exception to "no new frozen state."
- **D12 — v1 sleeve eligibility routes only analysis-reachable candidates.** The analysis
  flow is equity-gated (`checkAssetTypeSupported`, FIX-773) — a bond/option/crypto symbol
  stops before PM commit, so routing never runs for it. `assetClasses` eligibility therefore
  functions in v1 as an **exclusion** axis (a `[fixed_income, cash]` core marks an analyzed
  equity `not-eligible`), not as a way to route a bond/crypto *candidate* into a
  sleeve — those verdicts become reachable only when FIX-777 lifts the non-equity stop.
  Documented in §4.2 and §8 so a user configuring an options sleeve isn't surprised it
  never returns `fits` for an option symbol.

**Unchanged and in force:** mandate-as-container (`sleeves[]` on
`portfolioMandateResource`); account-anchored whole-account sleeves + optional hard
cap; run-once-route-deterministically (no per-sleeve LLM, no wider PM schema);
downward-only sizing that never touches `finalRating`; three independently-shippable
slices.

## 1. TLDR

**Plain-language summary.** A real investor rarely runs their whole book with one
risk setting. They keep a defensive core (bonds, money-market, cash earning 4%+)
and, alongside it, a small pool of money earmarked for something more aggressive
(say $20k for short-term options). Today the desk only understands one book with
one risk posture, so it can't say "this trade is wrong for my safe money but right
for my play money," and it can't tell you whether the pool it fits even has cash
left to deploy. This work lets the user declare named **strategies (sleeves)** —
each a set of accounts with its own risk posture, a spending cap, and rules for
what it's allowed to hold — and then, for any name the desk analyzes, answers per
sleeve: *does this fit, and is there money to buy it.* When the fitting sleeve is
tapped out, the desk lists what's already in it as the things you'd sell to make
room (or says the sleeve is empty).

**Technical statement.** Extend the durable `portfolioMandate` resource with an
optional `sleeves[]` container (each sleeve = accounts + a FIX-752 posture + a hard
capital cap + eligibility rules), compute per-sleeve utilization deterministically
from the `app.*` tables, and compute a **deterministic per-sleeve routing
projection at PM commit** (eligible? posture-sized? capital available?) — echoed
onto the PM memo, decision snapshot, RunSummary, and the PmHero + Health UI.

**Deliverables** (grouped by slice; order mirrors §5):

*Slice A — declare sleeves + see utilization:*
- Add `sleeveSchema` + `sleeves[]` to `portfolioMandateSchema` in `domain/portfolio/schema/portfolio-mandate-schema.ts`; extend `validatePortfolioMandate` with structural sleeve invariants (single-owner, cap bounds)
- Add pure leaf `domain/portfolio/math/sleeve-utilization.ts` (`summarizeSleeveUtilization`)
- Add a sleeve editor to `components/portfolio/mandate-dialog.tsx` and a per-sleeve utilization panel to `components/portfolio/health-section.tsx`

*Slice B — per-sleeve routing in analysis:*
- Freeze the validated mandate (with `sleeves`) at `seedSession` (`orchestration/guards.ts`); render `<sleeves>` via a `portfolioMandate`-preset extension
- Add `computeSleeveRouting` (pure) in `domain/portfolio/math/sleeve-routing.ts`, computed inside `commitPortfolioManagerMemo` (`agents/portfolio-manager/writer.ts`) using `mandate-gates.ts`; mirror onto PM memo + decision snapshot + `RunSummary` via a shared `mirrorNullable` helper
- Render the per-sleeve fit table in `components/theses/pm-hero.tsx`

*Slice C — funding-source (narrow):*
- When the routed sleeve is at cap, list its incumbents (thesis-present + staleness order) on the routing projection + PmHero; no numeric scoring (that is the FIX-763 upgrade)

*Docs & tests:* app docs (`labs/trading-desk/docs/sleeves.md` + `CLAUDE.md` section + README criterion note), `apps/docs` walkthrough cross-link, vitest specs per slice, one fixture `fsdev run` smoke.

**Size.** Large — multi-file, multi-PR (Slice A → Slice B → Slice C). No new
Postgres table, no new framework API, no new resource — additive to one resource
schema + two pure leaves + the existing deterministic-gate commit path.

## 2. Overview

**Linear issue:** [FIX-771](https://linear.app/fixpoint-labs/issue/FIX-771) —
*Trading-desk: one book, one posture — multi-strategy capital sleeves with
trade-to-sleeve routing, capital availability, and funding-source analysis.*

The desk models one portfolio with one risk posture. This adds **capital sleeves**:
named strategies (a defensive core, a capped opportunistic pool) each with its own
posture, capital cap, and eligibility rules. Analysis gains a per-sleeve routing
answer — *fits sleeve B not A*, *fits but no free capital* — and, when a fitting
sleeve is at cap, the incumbents you'd sell to fund the trade. It builds directly on
the shipped mandate (FIX-761), risk posture (FIX-752), portfolio-fit verdict
(FIX-728), thesis records (FIX-760), household health view (FIX-762), and the
relational model layer (FIX-772), all of which are Done.

## 3. Background & Research

### 3.1 What already shipped (the surface this extends)

Every dependency this issue was written against is now **Done**. The issue's
central worry — *"reconcile before FIX-761 is specced"* — is moot: FIX-761 shipped
a flat household mandate **deliberately coordinated with this work**. From the
FIX-761 spec, verbatim:

> "Flat household mandate now; a clean seam for FIX-771 sleeves, no container built."
> … "a future `sleeves: Mandate[]` wraps today's object, which becomes the
> household/default policy."

So the reconciliation is already decided in principle: **the mandate is the sleeve
container.** No container structure was pre-built (BP-038/YAGNI); this issue builds it.

Load-bearing shipped facts (all verified in-code):

- **The mandate is a user-scoped resource, not a table.** `portfolioMandateResource`
  (`flows/portfolio/portfolio-resources.ts`, `scope: "user"`, `flowIsolation: false`,
  one document per household). Schema `portfolioMandateSchema`
  (`domain/portfolio/schema/portfolio-mandate-schema.ts`). Chosen as a resource
  because it is a flat household document (no FK/join/aggregation) and agent-facing
  state read at seed — the documented **resource-vs-table criterion** (FIX-772).
- **The decision spine is "LLM decides once; deterministic gates clamp/route."** The
  PM (`agents/portfolio-manager/`) is the sole arbiter. It emits a single
  `portfolioFit` (`action`, `targetWeightPct`, …). At commit, pure functions derive
  the gates from **frozen state, never the LLM**: `computePolicyGate`
  (`lib/policy-gate.ts`, FIX-761 mandate) and the FIX-752 posture clamp
  (`lib/mandate-gates.ts`, from the resolved `MANDATE_PACK` dial). All clamps are
  downward-only and never touch `finalRating`. Verdicts echo onto the PM memo, the
  decision snapshot, and the `RunSummary` (the goal-check read path).
- **Posture is config-as-data, reusable per account-set.** `lib/risk-mandate.ts`:
  `MANDATE_PACK` (`conservative-income`/`balanced`/`aggressive-growth`),
  `resolveMandate(id)`, `mostConservativeMandate(ids)`. The clamp itself is extracted
  in `lib/mandate-gates.ts` (`clampTargetWeight`/`computeMandateGates`, FIX-790).
  Appetite resolves at seed: `run override → account default → IPS household → null`.
- **Accounts/holdings/ledger are relational `app.*` tables** via the typed repository
  (`db/repository.ts`, `getRepository()`). `app.accounts` carries `cash_balance` and
  an opaque `risk_mandate`; `app.holdings` is one row per `(account_id, ticker)`. The
  repository interface reserves *"per-sleeve cash"* aggregates for this issue,
  verbatim.
- **The household Health view is a deterministic pure leaf.**
  `domain/portfolio/math/portfolio-health.ts` (`summarizePortfolioHealth`), rendered
  in `components/portfolio/health-section.tsx` and injected into the PM context at
  seed. It is **never frozen** — recomputed client-side. Per-sleeve utilization is
  its named FIX-771 follow-up.
- **Thesis records** (`thesesCollection`, household × ticker resource) carry entry
  rationale + structured **tripwires** — the "why + invalidation" data the funding
  list orders on. The **re-validation loop that scores thesis health is FIX-763
  (Todo)** — which is why v1 lists incumbents without a numeric score.

### 3.2 Industry practice (how sleeves are really run)

- **Sleeve accounting (UMA/SMA).** A custodial account is subdivided into sleeves,
  each a strategy with its own holdings and — in true sub-accounting — its own cash.
  The hard, drift-prone part is per-sleeve cash: nothing about a deposit, dividend, or
  sale tells you which strategy owns it, so platforms maintain a shadow ledger and
  reconcile. A weaker "tagging" model keeps one cash pool and *"you can't really tell"*
  how much belongs to each strategy. ([Smartleaf](https://www.smartleaf.com/our-thinking/smartleaf-blog/a-guide-to-smas-and-umas), [Vestmark](https://www.vestmark.com/resources/blog/sleeves-tagging-and-the-pathway-to-improved-accounting))
- **Core–satellite.** A large defensive core + capped opportunistic satellites; caps
  expressed as % of book or fixed dollar; hard caps vs. tolerance bands. ([Saxo](https://www.home.saxo/learn/guides/diversification/core-satellite-approach-a-smarter-way-to-diversify-your-investments))
- **Capital vs. risk budgeting.** Risk budgeting (size by risk contribution) is more
  truthful for a small options sleeve but needs a covariance model. **Capital
  budgeting (a dollar/percent cap) is the honest v1** — directly observable from
  positions, no risk model — as long as you don't pretend the dollar cap is a risk
  limit. ([AnalystPrep CFA L3](https://analystprep.com/study-notes/cfa-level-iii/risk-budgeting/))
- **Funding-source / sell discipline.** "Every position must continually earn its
  place." When a candidate fits but there's no dry powder, the funding source is one of
  the sleeve's incumbents — real desks rank by conviction/thesis health and displace
  the weakest. v1 lists the incumbents (the FIX-763 upgrade adds the ranking).
  ([JAG Capital](https://www.jagcap.com/articles/articles-v2/investment-sell-discipline/))
- **Pitfalls.** Shadow-accounting reconciliation drift, cash leakage between sleeves,
  double-counting a name held in two sleeves, over-constraining. The single rule that
  kills most of these at once: **one owning sleeve per position.** ([Smartleaf — The Case Against Sleeves](https://www.smartleaf.com/our-thinking/smartleaf-blog/the-case-against-sleeves))

**The pragmatic v1 the research points to:** a sleeve is a lightweight declaration
`{ id, name, posture, capital cap, eligibility, accounts }`; the cap is a **hard
ceiling on deployed capital**; availability is computed **arithmetically each run**
(`available = cap − Σ market value of the sleeve's positions`) with **no sub-ledger**;
**one owning sleeve per account** removes double-counting and cash-attribution
entirely.

### 3.3 Why this approach (fit to the codebase)

The desk's existing spine — *one LLM decision, deterministic gates clamp size and
emit verdicts from frozen state* — already contains everything sleeve routing needs.
A name's quality/edge (Buy/Hold/Sell + conviction) is **sleeve-independent**; only
*fit* (eligibility rules), *size* (posture math), and *capital* (arithmetic) vary by
sleeve, and all three are deterministic. So routing is a **projection of the single
decision**, not a re-judgment — computed exactly the way `computePolicyGate` and the
posture clamp already are, in the same commit handler. This is why the issue's "run
once and route, or run per-sleeve?" resolves to **run once, route deterministically**,
and why the PM's LLM output does *not* grow a per-sleeve array (which would be an
unfillable strict schema).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Per-sleeve routing is deterministic, computed at PM commit — not an LLM
   fan-out, not a wider PM output, not a post-stage tap/resource.**
   *Alternative rejected:* re-run the pipeline per sleeve (cost × N); widen
   `portfolioDecisionOutputSchema` to an array of verdicts; or persist routing in a
   `sleeveRoutingResource` behind a tap. *Ramification:* fit/size/capital are derived
   projections computed in `commitPortfolioManagerMemo` (the `policyDecision`/
   `mandateDecision` precedent), so a sleeve differs on *eligibility and capital* but
   never on the name-level quality verdict. Cost stays flat, the strict PM schema is
   untouched, and there is no resource/tap to keep coherent (D1).

2. **The mandate becomes the sleeve container: `sleeves[]` on
   `portfolioMandateResource`, not a new table or separate resource.**
   *Alternative rejected:* an `app.sleeves` + `app.sleeve_accounts` table pair.
   *Ramification:* one policy object (resolves the issue's central reconciliation
   exactly as FIX-761 designed), backward compatible (no `sleeves` = today's flat
   mandate = the implicit "core"), inherits the live client read + streaming for free.
   The cost: the resource can't join, so **utilization is computed** from the `app.*`
   tables by a pure leaf at read time — the same pattern Health already uses.

3. **Account-anchored sleeves with an optional hard capital cap; arithmetic
   availability (cap-room only); no cash sub-ledger.**
   *Alternative rejected:* per-holding sleeve tags + a per-sleeve cash sub-ledger.
   *Ramification:* one account → at most one sleeve kills double-counting and
   cash-attribution; `available = max(0, cap − deployedValue)` re-derived each run;
   cash shown separately as informational (D6). The cost: an **intra-account virtual
   partition** (an options pool inside a mixed account) is out of scope — a sleeve
   claims whole accounts. The "$20k options pool" is a sleeve over the options account
   with `cap = $20k`.

4. **Funding-source is a listed set of incumbents in v1, not a scored ranking.**
   *Alternative rejected:* a `convictionProxy` composite + `marginPp` hysteresis built
   now. *Ramification:* v1 lists the at-cap sleeve's incumbents (thesis-present +
   staleness order) — the legible "here's what you'd sell" outcome — without a
   blind-tuned constant that FIX-763's real thesis-health scoring would redo wholesale.
   The scored/ranked displacement is the FIX-763 upgrade (D8).

5. **Ship as three independently-shippable slices** (declare + utilization → routing →
   funding list), not one PR. *Ramification:* Slice A is visible and valuable on its
   own (define sleeves, see utilization) with zero analysis-pipeline change; Slice C
   (the FIX-763-adjacent one) is last and can be re-scoped without blocking A/B.

### 4.2 Data model — the sleeve schema (Slice A)

A sleeve is a **lean policy document**, not a full sub-mandate. It reuses the posture
pack id; it does **not** carry its own `targetAllocation` (that is a household
asset-mix concept, and the mandate's `targetAllocation.max(5)` "one per asset class"
assumption does not transfer to a capital pool). New leaf in
`portfolio-mandate-schema.ts` (browser-safe, zod-only — a resource/input shape, **not**
a generator output, so `.nullable()`/`.default()` are correct; do **not** add to
`output-schemas-strict.spec.ts`):

```ts
export const sleeveCapSchema = z.object({
  // Hard ceiling on DEPLOYED capital. Absent cap → the sleeve's accounts' NAV.
  type: z.enum(["dollar", "pct"]),          // pct = % of household NAV
  value: z.number().positive().finite(),
});

export const sleeveEligibilitySchema = z.object({
  // Deterministic allow/deny predicates over a candidate's classified attributes.
  // v1: asset-CLASS + name exclusion only (D7). sectors / includeOnly are a later add.
  // Asset CLASS (not asset type): the defensive core is "fixed_income + cash", which is a
  // class concept — a bond ETF and a bond both belong to the fixed_income class, so class
  // avoids the bond-ETF / mixed-fund gap that an asset-type list would create.
  assetClasses: z.array(mandateAssetClassSchema).default([]),  // [] = any class; reuses the mandate's
                                                     //   equity | fixed_income | cash | crypto | alternative enum
  excludeTickers: z.array(z.string()).default([]),   // canonical UPPER; never eligible
});

export const sleeveSchema = z.object({
  id: z.string().min(1),                    // stable slug, unique within the mandate
  label: z.string().min(1).max(120),
  objective: z.string().max(400).default(""),         // free-text intent (agent-facing)
  riskAppetite: z.string(),                 // FIX-752 MANDATE_PACK id (the sleeve's posture)
  accountIds: z.array(z.string()).min(1),   // the accounts this sleeve owns (whole-account)
  cap: sleeveCapSchema.nullable().default(null),
  eligibility: sleeveEligibilitySchema.default(() => sleeveEligibilitySchema.parse({})),
});

// Additive to portfolioMandateSchema:
//   sleeves: z.array(sleeveSchema).max(12).default([]),
```

The flat household mandate remains the **default/core policy**; any account not
claimed by a sleeve belongs to the implicit **unsleeved pool** (governed by the
household mandate + posture exactly as today). `sleeves: []` ⇒ current behavior,
unchanged.

**Why eligibility stays (even for whole-account sleeves).** A *candidate being
analyzed is not yet held in any account*, so account membership tells you where
*existing* holdings sit, not which sleeve a *new* name may enter. Without an
eligibility predicate every capitalized sleeve would "fit" every analyzed name and
routing degenerates to "cheapest sleeve with room," losing the issue's "fits B not A"
outcome. Asset-class eligibility + posture carries the motivating split (a speculative
equity is not eligible for a `fixed_income`+`cash` / `conservative-income` core). **In v1,
`assetClasses` works as an exclusion axis only (D12):** the analysis flow is equity-gated
(`checkAssetTypeSupported`, FIX-773), so a bond/crypto symbol never reaches PM commit — a
sleeve whose eligibility *targets* those classes can mark an analyzed equity
`not-eligible`, but it will not return `fits` for a non-equity candidate until FIX-777
lifts the stop. The analyzed name's class is the **resolved** `asset_class` (after ticker
resolution), **not** provider-blind `classify-instrument` — that classifier's import
placeholder rules label the real tickers `CASH`/`USD` as cash/money_market before resolution,
which would mis-route them (L500); resolution is the arbiter (the `checkAssetTypeSupported`
precedent).

**Validation — structural only (`validatePortfolioMandate`, non-throwing):**

- each `sleeve.id` unique; each `accountId` referenced by **at most one sleeve**
  (single-owner invariant — the double-counting killer);
- `cap.value` positive; a `pct` cap ≤ 100.

**`excludeTickers` are canonicalized to UPPER at the WRITE path**, in
`savePortfolioMandate` (the household-exclusion precedent), **not** in
`validatePortfolioMandate` — the validator only returns issue strings and is re-run at seed,
so it cannot mutate the record; a lowercase `nvda` left un-canonicalized would silently fail
the exclusion against the UPPER analyzed ticker (L389).

**Unknown `riskAppetite` is a SAVE-ONLY guard (D4)** — enforced in the
`savePortfolioMandate` action, NOT in `validatePortfolioMandate`. `seedSession`
re-runs the validator and nulls the whole mandate on any issue, so a stale sleeve id
must degrade only that sleeve's posture (posture-blind), never blank the household IPS
— exactly how the mandate's own `riskAppetite` is handled. Account existence is not
validated in the leaf (browser-safe, account-blind); the editor checks the live
account list, and routing tolerates a sleeve naming a since-deleted account (it
contributes zero utilization).

### 4.3 Utilization (Slice A) — the pure leaf

`domain/portfolio/math/sleeve-utilization.ts`, modeled on `summarizePortfolioHealth`
(pure; never frozen — D5):

```ts
export interface SleeveUtilization {
  sleeveId: string;
  label: string;
  accountIds: string[];
  deployedValue: number;                    // Σ market value of the sleeve's accounts' priced holdings
  cash: number;                             // Σ cash_balance of the sleeve's accounts (informational)
  capValue: number | null;                  // pct → % of household NAV; null = accounts' NAV (capless)
  capitalKnown: boolean;                    // false → unpriced holdings or unresolvable pct cap
  availableToDeploy: number;                // max(0, capValue − deployedValue); capless → accounts' NAV − deployed
  utilizationPct: number | null;            // deployedValue / capValue (null when capless/unknown)
  pricedCoverage: { priced: number; total: number };
}

export function summarizeSleeveUtilization(
  sleeves: Sleeve[],
  accounts: AccountState[],                 // from toAccountStates(getPortfolio(userId))
  quotes: QuoteMap,                         // UPPER ticker → last-known price (app.quotes)
  householdNav: number,                     // pct-cap denominator
  navComplete: boolean,                     // every whole-book holding priced — a pct cap
                                            //   resolves only when true, else capitalKnown:false
): SleeveUtilization[];
```

Market value reuses `domain/portfolio/math/value-holding.ts` (`holdingMarketValue`,
FIX-773 per-type valuation) so bonds/MMF/options value correctly. `capitalKnown` is
`false` when a sleeve holding is unpriced **or** the sleeve has a `pct` cap and the
**whole book** isn't fully priced (the leaf takes a `navComplete` flag — a `pct` cap is a
fraction of household NAV, so a missing quote *anywhere in the book* makes that NAV, and
the cap, unresolvable; never a fabricated price or a partial-denominator number — BP-020).
Cash is a separate informational figure, not folded into `availableToDeploy` (D6).
Consumed in two places (one copy of the math): the Health panel (`useMemo`) and routing.

### 4.4 Per-sleeve routing (Slice B) — deterministic projection at PM commit

**Seed.** `seedSession` (`orchestration/guards.ts`) already reads the mandate,
re-validates it, and freezes `state.portfolioMandate` (which now carries `sleeves` — the
single source of sleeve *definitions*, D5) + `state.householdTickerWeightPct`. Two new
frozen fields carry the whole-book data routing needs (D11 — see below). The
`portfolioMandate` capability preset
gains a `<sleeves>` block (frozen-state read, suppressed to null when `sleeves` is
empty — the `<portfolioMandate>` precedent), giving the trader + PM awareness of the
sleeve structure. **No new LLM output.** Seed also freezes, from the **pre-scoping
whole-book account read** it already performs for `householdTickerWeightPct` (today
discarded), a compact `state.sleeveBook` (all accounts + holdings + quotes +
`householdNav` + a `navComplete` flag = every whole-book holding priced) and a
`state.thesisPresenceIndex` (held ticker → thesis `updatedAt` |
null). Routing uses `sleeveBook`, **not** the scoped `state.portfolioContext` — a sleeve
can own accounts outside `selectedAccountIds`, which the scoped snapshot cannot see (D11).
These two whole-book fields are the deliberate new frozen state (distinct from the scoped
`portfolioContext`); both ride the pre-scoping read, so the Slice C funding list needs no
commit-time collection fan-out.

**Routing leaf.** `domain/portfolio/math/sleeve-routing.ts` — pure, called **inside
`commitPortfolioManagerMemo`** (`agents/portfolio-manager/writer.ts`), alongside the
existing `policyDecision`/`mandateDecision` derivations (D1). It recomputes utilization
from the frozen mandate + `book` (passing `book.navComplete`), then for each sleeve:

```ts
export interface SleeveFit {
  sleeveId: string; label: string;
  verdict: "fits-with-capital" | "fits-no-capital" | "capital-unknown"
         | "posture-blocked" | "not-eligible";
  postureTargetPct: number | null;          // PM target re-clamped under the sleeve's MANDATE_PACK (null if not eligible)
  availableToDeploy: number | null;         // null when capital-unknown
  blockers: string[];                        // deterministic reasons: failed predicate, at-cap, unpriced, capacity-veto
  funding: FundingEntry[];                   // Slice C: incumbents to consider selling (only when fits-no-capital)
}

export interface FundingEntry {              // structured so PmHero/RunSummary render + audit the order (D8)
  ticker: string;                            // UPPER
  marketValue: number;                       // its value in the sleeve (how much it would free)
  hasThesis: boolean;                        // false → "no thesis on file"
  thesisUpdatedAt: string | null;            // staleness — the sort key after thesis presence
}

export interface SleeveRouting {
  fits: SleeveFit[];                         // one per sleeve
  recommendedSleeveId: string | null;       // first (mandate-order) sleeve with fits-with-capital
  routableToUnsleeved: boolean;
}

export function computeSleeveRouting(args: {
  ticker: string;                           // analyzed symbol (UPPER)
  assetClass: AssetClass;                   // the RESOLVED candidate's asset_class (post ticker-resolution),
                                            //   NOT provider-blind classify-instrument — which mislabels real
                                            //   tickers CASH/USD as cash/money_market before resolution (L500)
  pmRawTargetWeightPct: number;             // the PM's AS-EMITTED portfolioFit.targetWeightPct, BEFORE the run's
                                            //   FIX-752 + policy clamps — each sleeve clamps from the raw target
                                            //   under its own posture, else a conservative run zeros every sleeve (L501 P1)
  pmTargetNav: number;                       // the NAV that the target is a % of — the SCOPED
                                            //   NAV on a scoped run, else householdNav (D11; L516 fix)
  finalRating: Rating;
  rewardBuckets: ScenarioBucket[] | null;   // RAW scenario terms (λ-independent), so each sleeve's λ
                                            //   re-derives lossAdjustedGlr via computeRewardToRisk (D3; L483 fix) —
                                            //   NOT the active-run rewardToRisk figure, whose λ is already baked in
  decisionConfidence: number;               // threaded for the FIX-752 gate (D3)
  mandateOverrideReason: string;            // threaded for the soft worth-it cap (D3)
  householdExclusions: string[];            // UPPER, from the frozen mandate — for routableToUnsleeved (L554)
  sleeves: Sleeve[];
  book: SleeveBook;                         // seed-frozen WHOLE-BOOK snapshot (all accounts + holdings +
                                            //   quotes + navComplete) — utilization, exposure, incumbents derive from this (D11)
  householdNav: number;                     // whole-book NAV — used ONLY to resolve `pct` caps (D11)
  thesisPresenceIndex: Record<string, string | null>;  // UPPER ticker → thesis updatedAt (null = none),
                                            //   frozen at seed for held tickers; orders the funding list (D11)
}): SleeveRouting;
```

Utilization is recomputed from `book` inside the leaf (D5) — it is not passed in.
Per sleeve, deterministically, in order (first matching verdict wins):
1. **Eligibility** — run the sleeve's `assetClasses`/`excludeTickers` predicates against
   the analyzed name's class + ticker. Fail → `not-eligible`, reasons in `blockers`.
2. **Posture** — every sleeve clamps from `pmRawTargetWeightPct` (the pre-gate PM target,
   L501). Resolve `resolveMandate(sleeve.riskAppetite)`. If it returns `null` (a stale/unknown
   id survived the save-only guard), the sleeve is **posture-blind** (D4): skip the gate, set
   `postureTargetPct = pmRawTargetWeightPct`, add `posture-unknown` to `blockers` — routes on
   eligibility + capital, no other sleeve affected. **If `rewardBuckets == null`** (a thin or
   errored forecast where `computeAndStoreRewardToRisk` cleared the figure), run the gate
   **reward-blind** — apply only its reward-*independent* clamps and **skip the reward-floor /
   capacity-veto checks entirely** (do NOT synthesize a null `RewardToRiskFigure` and pass it
   in — `computeMandateGates` dereferences fields like `rr.noDownside` and would fail closed;
   the helper takes the figure as optional / the reward checks are gated on its presence).
   This matches today's mandate-blind-on-reward run (L530/L536). Otherwise **recompute the
   reward figure with the sleeve's own `lossAversion`** — `computeRewardToRisk({ scenarios:
   rewardBuckets, lossAversion: mandate.lossAversion })` (the stored `lossAdjustedGlr` baked
   the active-run λ, L483) — and call `computeMandateGates`/`clampTargetWeight`
   (`lib/mandate-gates.ts`, D3) with the resolved mandate, that per-sleeve reward figure, and
   the confidence / override inputs → `postureTargetPct`. **A hard capacity veto (target
   clamped to ≤ 0) → `verdict: "posture-blocked"`** (`capacity-veto` in `blockers`); the sleeve
   is not recommendable and the capital step is skipped — a $0 target must never read as "has
   capital."
3. **Capital** — `capitalKnown === false` → `capital-unknown` (unpriced sleeve holdings,
   **or a `pct` cap on an incompletely-priced whole book** — a `pct` cap resolves against
   `householdNav` only when `book.navComplete`, so a missing quote *anywhere in the book*
   makes a pct-capped sleeve `capital-unknown`, never a partial-denominator number).
   Otherwise convert `postureTargetPct` to dollars against **`pmTargetNav`** — the NAV the
   PM target is a fraction of (the scoped NAV on a scoped run, **not** `householdNav`, else
   the dollars are overstated by the household/scoped ratio and the sleeve is wrongly
   `fits-no-capital`, L516) — subtract the analyzed ticker's **current value in this sleeve**
   (from `book`) so the check is the **incremental** buy (D11), and compare to
   `availableToDeploy` → `fits-with-capital` / `fits-no-capital` (`at-cap` in `blockers`).

`recommendedSleeveId` = the first (mandate-order) sleeve with `verdict ===
"fits-with-capital"` (posture-blocked / capital-unknown / not-eligible sleeves are never
recommendable).

**`routableToUnsleeved`** = `true` when the **unsleeved pool** can hold the name:
at least one account is unclaimed by any sleeve **and** the name is not in the threaded
`householdExclusions` (the frozen household mandate's exclusion list — passed in, since the
leaf is otherwise mandate-blind). The unsleeved pool is **not** re-gated per-sleeve — it is governed
by the household mandate + posture that already produced the committed PM decision, so its
"outcome" *is* the household `portfolioFit`/`policyDecision`/`mandateDecision` the run
already emits (no sleeve eligibility, cap, or capital check applies to it). The flag is the
honest fallback signal PmHero uses when no declared sleeve is `fits-with-capital` (e.g. all
`not-eligible`): "fits the general book" vs. "fits no declared sleeve and there is no
unsleeved room." With no sleeves defined at all, every account is unclaimed, so
`routableToUnsleeved` is the pre-FIX-771 behavior.

**Surfacing (no resource, no tap — D1).** The derived `sleeveRouting` mirrors onto the
PM memo (`policyDecision`/`mandateDecision` precedent — PmHero reads one place), the
decision snapshot, and `RunSummary` (+ `runArtifacts` for eval). The three
`decisionSnapshot` mirrors (`mandateDecision`, `policyDecision`, `sleeveRouting`) go
through a shared `mirrorNullable(obj, keys)` helper (D9) rather than a third
field-by-field `?? null` hand-copy.

### 4.5 Funding list (Slice C) — narrow

When a sleeve is `fits-no-capital`, `computeSleeveRouting` fills that `SleeveFit.funding`
with **structured `FundingEntry` records** — the sleeve's incumbents from the frozen `book`
(the sleeve's accounts' held positions), each carrying `{ ticker, marketValue, hasThesis,
thesisUpdatedAt }` from `book` + `thesisPresenceIndex`, ordered **thesis-present-first, then
by staleness** (oldest `thesisUpdatedAt` first — the most-likely-stale candidates surface);
an empty sleeve yields `[]` ("nothing to trim"). The entries are echoed onto the memo /
RunSummary (not reduced to bare tickers) so PmHero can render "no thesis on file" / the
staleness context and a reader can audit why the order was chosen (L469).
**No numeric `convictionProxy`, no `marginPp`, no `cleared` boolean** (D8). The PmHero
renders it as "to fund this, consider trimming: X, Y (Z has no thesis on file)" — a
legible funding list, or "this sleeve holds nothing to trim" when empty. It is a
**suggestion list, never an auto-executed trade or a scored recommendation** (the
desk's real-money honesty gate). The scored/ranked displacement — which incumbent's
edge is actually weakest — is the **FIX-763 upgrade**, when real thesis-health data
exists to rank on.

### 4.6 Household Health view (Slice A)

`health-section.tsx` gains a **Sleeves panel** reading `summarizeSleeveUtilization`
client-side (`useMemo` + pure leaf, BP-010): per-sleeve label, deployed / cap /
available, a utilization bar, cash (informational), and a coverage/`capitalKnown` note.
Zero new route. Capless sleeves show "no cap (accounts' NAV)". The unsleeved pool is a
residual row so the panel reconciles to household NAV.

### 4.7 Error handling & real-money discipline

- **Unpriced holdings / unresolvable pct cap** → `capitalKnown: false` →
  `verdict: "capital-unknown"` (never coerced to buyable or capped — D2/BP-020).
- **Stale/unknown `riskAppetite` on a sleeve** → posture-blind for that sleeve
  (save-only guard, D4); other sleeves + the IPS unaffected.
- **A sleeve naming a deleted account** → zero utilization; not an error.
- **No sleeves** → `sleeveRouting` null on memo/snapshot/RunSummary; `<sleeves>`
  suppressed; the run behaves exactly as pre-FIX-771.
- **Routing never touches `finalRating`** and never inflates size — downward-only,
  the FIX-715/752/761 orthogonality invariant.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| No sleeves defined | Unchanged pre-FIX-771 run; `sleeveRouting` null, `<sleeves>` suppressed |
| Account claimed by two sleeves | Rejected at save (single-owner invariant); editor blocks it |
| Sleeve cap < current deployed value | `utilizationPct > 100`, `availableToDeploy = 0`, `fits-no-capital`; UI over-cap flag (never force-trims) |
| Analyzed name eligible for no sleeve | All `not-eligible`; `routableToUnsleeved` decides; PmHero "fits no declared sleeve" |
| Fitting sleeve has capital | `fits-with-capital`; `recommendedSleeveId` set; no funding list |
| Fitting sleeve at cap | `fits-no-capital`; funding = incumbent list (or "nothing to trim") |
| Unpriced sleeve holding | `capital-unknown`; never buyable/funding-needed |
| `pct` cap + a missing quote anywhere in the whole book | `capital-unknown` (cap can't resolve against a partial NAV), even if the missing name is in another sleeve |
| Hard capacity veto (posture clamps target ≤ 0) | `posture-blocked`; not recommendable; capital step skipped (a $0 target never reads as "has capital") |
| Sleeve names a deleted account | Zero utilization contribution; not an error |
| Unknown / stale `riskAppetite` id on a sleeve | Posture-blind for that sleeve (`posture-unknown` blocker; routes on eligibility + capital); others + IPS unaffected |
| Scoped run (`selectedAccountIds`) | Utilization + routing computed from the pre-scoping whole-book read |

**Error taxonomy:** all sleeve routing is deterministic and non-throwing at read/seed
(business-invalid → degrade, never throw — the mandate precedent); the only throwing
boundary is `savePortfolioMandate` re-validating sleeves + the appetite guard at the
trust boundary.

## 8. Non-Goals

- **Intra-account virtual partitions** — a sleeve owning *part* of a mixed account.
  Needs per-holding tagging + cash attribution; deferred (§3.4-3). v1 sleeves own whole
  accounts.
- **Per-sleeve cash sub-ledger / shadow accounting** — availability is arithmetic
  cap-room, not a running per-sleeve balance (the Smartleaf pitfall).
- **Scored / ranked displacement** — v1 lists incumbents; the numeric conviction score
  + hysteresis is the **FIX-763** upgrade (D8).
- **Per-sleeve theses** — thesis records stay household × ticker (FIX-760's deferral to
  this issue is satisfied by routing + the funding list, not per-sleeve theses).
- **Sleeve eligibility beyond asset-class + exclusions** — `sectors` /
  `includeOnlyTickers` deferred (D7).
- **Routing a non-equity candidate into a sleeve** — the analysis flow is equity-gated
  (FIX-773), so a bond/crypto sleeve's `assetClasses` eligibility is an exclusion
  axis only in v1; `fits` for those candidate classes waits on FIX-777 (D12).
- **Risk-budget caps** — v1 caps capital (dollars/percent), not risk contribution. The
  honesty caveat: a dollar cap understates a small options sleeve's risk; the v2 upgrade
  is a max-loss/notional cap.
- **Rebalancing execution / sell-to-rebalance** — the desk analyzes one name at a time.
- **Options-trade translation** for an aggressive options sleeve — that is **FIX-706**;
  sleeves route and size, they don't translate to a contract.
- **Soft/tolerance-band caps** — v1 caps are hard.
- **Deepening opportunity (accurate scope, per maintainer review):** the FIX-752 and
  FIX-761 clamps are **already extracted** into unit-tested `lib/mandate-gates.ts` and
  `lib/policy-gate.ts`; only the FIX-728 echo (`currentWeightPct`/`weightDeltaPct`,
  ~20 lines at `writer.ts:176–197`) is inline, and it is an echo, not a clamp. This
  spec extracts nothing further there; the one duplication it *does* remove is the
  `decisionSnapshot` field-by-field mirror (via `mirrorNullable`, D9). A fuller
  echo/clamp consolidation is a separate `fsd:improve-codebase-architecture` follow-up,
  correctly *not* bundled here.
