# FIX-771: One book, one posture — multi-strategy capital sleeves — Implementation Spec

## 1. TLDR

**Plain-language summary.** A real investor rarely runs their whole book with one
risk setting. They keep a defensive core (bonds, money-market, cash earning 4%+)
and, alongside it, a small pool of money earmarked for something more aggressive
(say $20k for short-term options). Today the desk only understands one book with
one risk posture, so it can't say "this trade is wrong for my safe money but right
for my play money," and it can't tell you whether the pool it fits even has cash
left to deploy. This work lets the user declare named **strategies (sleeves)** —
each a set of accounts with its own risk posture, a spending cap, and rules for
what it's allowed to hold — and then, for any name the desk analyzes, answers per
sleeve: *does this fit, and is there money to buy it.* When the fitting sleeve is
tapped out, the desk points at the weakest thing already in it as a candidate to
sell to make room (or says nothing clears the bar).

**Technical statement.** Extend the durable `portfolioMandate` resource with an
optional `sleeves[]` container (each sleeve = accounts + a FIX-752 posture + a hard
capital cap + eligibility rules), compute per-sleeve utilization deterministically
from the `app.*` tables, and add a **deterministic post-decision routing step** that
projects the single PM decision onto every sleeve (eligible? posture-sized? capital
available?) plus a heuristic funding-source suggestion — surfaced on the PM memo,
the RunSummary, the PmHero panel, and the household Health view.

**Deliverables** (grouped by slice; order mirrors §5):

*Slice A — declare sleeves + see utilization:*
- Add `sleeveSchema` + `sleeves[]` to `portfolioMandateSchema` in `domain/portfolio/schema/portfolio-mandate-schema.ts`, and extend `validatePortfolioMandate` with sleeve invariants
- Add pure leaf `domain/portfolio/math/sleeve-utilization.ts` (`summarizeSleeveUtilization`) computing per-sleeve deployed/available/cap from accounts + holdings + quotes
- Add a sleeve editor to `components/portfolio/mandate-dialog.tsx` and a per-sleeve utilization panel to `components/portfolio/health-section.tsx`

*Slice B — per-sleeve routing in analysis:*
- Freeze `sleeves` + household snapshot at `seedSession` (`orchestration/guards.ts`); render `<sleeves>` via a `portfolioMandate`-preset extension
- Add pure leaf `domain/portfolio/math/sleeve-routing.ts` (`computeSleeveRouting`) + a post-`portfolioStage` `.tap` writing a nullable `sleeveRoutingResource`; mirror onto the PM memo, decision snapshot, and `RunSummary`
- Render the per-sleeve fit table in `components/theses/pm-hero.tsx`

*Slice C — funding-source / displacement:*
- Add pure leaf `domain/portfolio/math/funding-source.ts` (`computeFundingSources`) invoked when the routed sleeve is at cap; surface "sell X to fund Y" / "none clears the bar" on the routing artifact + PmHero

*Docs & tests:* app docs (`labs/trading-desk/docs/sleeves.md` + `CLAUDE.md` section + README criterion note), `apps/docs` walkthrough cross-link, vitest specs per slice, one real-model goal check.

**Size.** Large — multi-file, multi-PR (split as Slice A → Slice B → Slice C). No new
Postgres table, no new framework API — additive to one resource schema + three pure
leaves + the existing deterministic-gate commit path.

## 2. Overview

**Linear issue:** [FIX-771](https://linear.app/fixpoint-labs/issue/FIX-771) —
*Trading-desk: one book, one posture — multi-strategy capital sleeves with
trade-to-sleeve routing, capital availability, and funding-source analysis.*

The desk models one portfolio with one risk posture. This adds **capital sleeves**:
named strategies (a defensive core, a capped opportunistic pool) each with its own
posture, capital cap, and eligibility rules. Analysis gains a per-sleeve routing
answer — *fits sleeve B not A*, *fits but no free capital* — and a funding-source
heuristic that names what to sell when the fitting sleeve is at its cap. It builds
directly on the shipped mandate (FIX-761), risk posture (FIX-752), portfolio-fit
verdict (FIX-728), thesis records (FIX-760), household health view (FIX-762), and
the relational model layer (FIX-772), all of which are Done.

## 3. Background & Research

### 3.1 What already shipped (the surface this extends)

Every dependency this issue was written against is now **Done**. The issue's
central worry — *"reconcile before FIX-761 is specced"* — is moot: FIX-761 shipped
a flat household mandate **deliberately coordinated with this work**. From the
FIX-761 spec, verbatim:

> "Flat household mandate now; a clean seam for FIX-771 sleeves, no container built."
> … "a future `sleeves: Mandate[]` wraps today's object, which becomes the
> household/default policy."

So the reconciliation is already decided in principle: **the mandate is the sleeve
container.** No container structure was pre-built (BP-038/YAGNI); this issue builds it.

Load-bearing shipped facts (all verified in-code):

- **The mandate is a user-scoped resource, not a table.** `portfolioMandateResource`
  (`flows/portfolio/portfolio-resources.ts`, `scope: "user"`, `flowIsolation: false`,
  one document per household). Schema `portfolioMandateSchema`
  (`domain/portfolio/schema/portfolio-mandate-schema.ts`). Chosen as a resource
  because it is a flat household document (no FK/join/aggregation) and agent-facing
  state read at seed — the documented **resource-vs-table criterion** (FIX-772).
- **The decision spine is "LLM decides once; deterministic gates clamp/route."** The
  PM (`agents/portfolio-manager/`) is the sole arbiter. It emits a single
  `portfolioFit` (`action`, `targetWeightPct`, …). At commit, pure functions derive
  the gates from **frozen state, never the LLM**: `computePolicyGate`
  (`lib/policy-gate.ts`, FIX-761 mandate) and the FIX-752 posture clamp
  (`writer.ts`, from the resolved `MANDATE_PACK` dial). All clamps are downward-only
  and never touch `finalRating`. Verdicts echo onto the PM memo, the decision
  snapshot, and the `RunSummary` (the goal-check read path).
- **Posture is config-as-data, reusable per account-set.** `lib/risk-mandate.ts`:
  `MANDATE_PACK` (`conservative-income`/`balanced`/`aggressive-growth`),
  `resolveMandate(id)`, `mostConservativeMandate(ids)`. Appetite resolves at seed:
  `run override → account default → IPS household → null`. **`mostConservativeMandate`
  is already the "reused per-sleeve" primitive** — today across selected accounts.
- **Accounts/holdings/ledger are relational `app.*` tables** via the typed repository
  (`db/repository.ts`, `getRepository()`). `app.accounts` carries `cash_balance` and
  an opaque `risk_mandate`; `app.holdings` is one row per `(account_id, ticker)`. The
  repository interface reserves *"per-sleeve cash"* aggregates for this issue,
  verbatim.
- **The household Health view is a deterministic pure leaf.**
  `domain/portfolio/math/portfolio-health.ts` (`summarizePortfolioHealth`), rendered
  in `components/portfolio/health-section.tsx` and injected into the PM context at
  seed. Per-sleeve utilization is its named FIX-771 follow-up.
- **Thesis records** (`thesesCollection`, household × ticker resource) carry entry
  rationale + structured **tripwires** — the "why + invalidation" data displacement
  reads. The **re-validation loop that scores thesis health is FIX-763 (Todo)**.

### 3.2 Industry practice (how sleeves are really run)

- **Sleeve accounting (UMA/SMA).** A custodial account is subdivided into sleeves,
  each a strategy with its own holdings and — in true sub-accounting — its own cash.
  The hard, drift-prone part is per-sleeve cash: nothing about a deposit, dividend, or
  sale tells you which strategy owns it, so platforms maintain a shadow ledger and
  reconcile. A weaker "tagging" model keeps one cash pool and *"you can't really tell"*
  how much belongs to each strategy. ([Smartleaf](https://www.smartleaf.com/our-thinking/smartleaf-blog/a-guide-to-smas-and-umas), [Vestmark](https://www.vestmark.com/resources/blog/sleeves-tagging-and-the-pathway-to-improved-accounting))
- **Core–satellite.** A large defensive core + capped opportunistic satellites; caps
  expressed as % of book or fixed dollar; hard caps vs. tolerance bands. ([Saxo](https://www.home.saxo/learn/guides/diversification/core-satellite-approach-a-smarter-way-to-diversify-your-investments))
- **Capital vs. risk budgeting.** Risk budgeting (size by risk contribution) is more
  truthful for a small options sleeve but needs a covariance model. **Capital
  budgeting (a dollar/percent cap) is the honest v1** — directly observable from
  positions, no risk model — as long as you don't pretend the dollar cap is a risk
  limit. ([AnalystPrep CFA L3](https://analystprep.com/study-notes/cfa-level-iii/risk-budgeting/))
- **Funding-source / sell discipline.** "Every position must continually earn its
  place." When a candidate fits but there's no dry powder, rank its edge against the
  **weakest incumbent** and displace only if the margin clears a threshold — a
  counterfactual "would I buy this incumbent again today vs. the new name," with a
  hysteresis band to prevent churn. ([JAG Capital](https://www.jagcap.com/articles/articles-v2/investment-sell-discipline/), [Goodreid](https://www.goodreid.com/investment-sell-discipline-exploring-the-counterfactual-%E2%80%9Cwhat-if%E2%80%9D-scenarios.html))
- **Pitfalls.** Shadow-accounting reconciliation drift, cash leakage between sleeves,
  double-counting a name held in two sleeves, over-constraining. The single rule that
  kills most of these at once: **one owning sleeve per position.** ([Smartleaf — The Case Against Sleeves](https://www.smartleaf.com/our-thinking/smartleaf-blog/the-case-against-sleeves))

**The pragmatic v1 the research points to:** a sleeve is a lightweight declaration
`{ id, name, posture, capital cap, eligibility, accounts }`; the cap is a **hard
ceiling on deployed capital**; availability is computed **arithmetically each run**
(`available = cap − Σ market value of the sleeve's positions`) with **no sub-ledger**;
**one owning sleeve per account** removes double-counting and cash-attribution
entirely; displacement is a **conviction-ranked heuristic with a hysteresis margin**.

### 3.3 Why this approach (fit to the codebase)

The desk's existing spine — *one LLM decision, deterministic gates clamp size and
emit verdicts from frozen state* — already contains everything sleeve routing needs.
A name's quality/edge (Buy/Hold/Sell + conviction) is **sleeve-independent**; only
*fit* (eligibility rules), *size* (posture math), and *capital* (arithmetic) vary by
sleeve, and all three are deterministic. So routing is a **projection of the single
decision**, not a re-judgment — computed exactly the way `computePolicyGate` and the
posture clamp already are. This is why the issue's "run once and route, or run
per-sleeve?" resolves to **run once, route deterministically**, and why the PM's LLM
output does *not* grow a per-sleeve array (which would be an unfillable strict schema).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Per-sleeve routing is deterministic over one LLM decision — not an LLM
   fan-out, not a wider PM output.**
   *Alternative rejected:* re-run the decision pipeline per sleeve (cost × N sleeves),
   or widen `portfolioDecisionOutputSchema` to an array of `portfolioFit` verdicts.
   *Ramification:* fit/size/capital become derived projections (the `computePolicyGate`
   precedent), so a sleeve can differ on *eligibility and capital* but never on the
   name-level quality verdict. That is the honest model of how sleeves work (they carry
   eligibility rules, not separate opinions of a name's merit) — but "per-sleeve
   re-judgment of a name's merit" is out of scope by construction. Cost stays flat
   (one run), and the strict PM schema is untouched.

2. **The mandate becomes the sleeve container: `sleeves[]` on
   `portfolioMandateResource`, not a new table or separate resource.**
   *Alternative rejected:* an `app.sleeves` + `app.sleeve_accounts` table pair.
   *Ramification:* one policy object (resolves the issue's central reconciliation
   exactly as FIX-761 designed), backward compatible (no `sleeves` = today's flat
   mandate = the implicit "core"), and it inherits the live client read +
   `resource_change` streaming for free. The cost: the resource can't join, so
   **utilization must be computed** from the `app.*` tables by a pure leaf at read
   time — which is already how Health works, so it's a consistent pattern, not a new one.

3. **Account-anchored sleeves with an optional hard capital cap; arithmetic
   availability; no cash sub-ledger.**
   *Alternative rejected:* per-holding sleeve tags + a per-sleeve cash sub-ledger (the
   UMA sub-accounting model). *Ramification:* one account belongs to at most one sleeve
   → double-counting and cash-attribution vanish; `available = min(cap − deployedValue,
   sleeveFreeCash)` is re-derived each run from live positions (no stored balance to
   drift). The cost: an **intra-account virtual partition** (an options pool *inside* a
   mixed margin account) is out of scope for v1 — a sleeve claims whole accounts. The
   motivating "$20k options pool" is modeled as a sleeve over the options account with
   `cap = $20k`.

4. **Displacement/funding-source is a conviction-ranked heuristic over stored data,
   not incumbent re-analysis.**
   *Alternative rejected:* re-run the full analysis pipeline on each incumbent to score
   it fresh. *Ramification:* buildable now without FIX-763 — it ranks the at-cap
   sleeve's incumbents by a coarse stored-conviction proxy (thesis presence + last
   decision rating + target/stop proximity) and surfaces the weakest as a funding
   candidate above a hysteresis margin, honestly labeled a heuristic. Real thesis-health
   scoring and full comparative displacement defer to FIX-763.

5. **Ship as three independently-shippable slices** (declare + utilization → routing →
   displacement), not one PR. *Alternative rejected:* one mega-PR touching schema, seed,
   commit, two UIs, docs. *Ramification:* Slice A is visible and valuable on its own
   (define sleeves, see utilization) with zero analysis-pipeline change; Slice C (the
   riskiest, FIX-763-adjacent) is last and can be re-scoped or deferred without blocking
   A/B.

### 4.2 Data model — the sleeve schema (Slice A)

A sleeve is a **lean policy document**, not a full sub-mandate. It reuses the posture
pack id and a constraints subset; it does **not** carry its own `targetAllocation`
(that is a household asset-mix concept, and the mandate's `targetAllocation.max(5)`
"one per asset class" assumption does not transfer to a capital pool). New leaf in
`portfolio-mandate-schema.ts` (browser-safe, zod-only — a resource/input shape, **not**
a generator output, so `.nullable()`/`.default()` are correct; do **not** add to
`output-schemas-strict.spec.ts`):

```ts
export const sleeveCapSchema = z.object({
  // Hard ceiling on DEPLOYED capital. Absent cap → the sleeve's accounts' NAV.
  type: z.enum(["dollar", "pct"]),          // pct = % of household NAV
  value: z.number().positive().finite(),
});

export const sleeveEligibilitySchema = z.object({
  // Deterministic allow/deny predicates over a candidate's classified attributes.
  assetTypes: z.array(assetTypeSchema).default([]),   // [] = any type (reuses FIX-773 asset_type enum)
  sectors: z.array(z.string()).default([]),           // [] = any sector; else canonical sector names
  excludeTickers: z.array(z.string()).default([]),    // canonical UPPER; never eligible
  includeOnlyTickers: z.array(z.string()).default([]),// [] = no allow-list; else the sleeve's universe
});

export const sleeveSchema = z.object({
  id: z.string().min(1),                    // stable slug, unique within the mandate
  label: z.string().min(1).max(120),
  objective: z.string().max(400).default(""),         // free-text intent (agent-facing)
  riskAppetite: z.string(),                 // FIX-752 MANDATE_PACK id (the sleeve's posture)
  accountIds: z.array(z.string()).min(1),   // the accounts this sleeve owns (whole-account)
  cap: sleeveCapSchema.nullable().default(null),
  eligibility: sleeveEligibilitySchema.default(() => sleeveEligibilitySchema.parse({})),
});

// Additive to portfolioMandateSchema:
//   sleeves: z.array(sleeveSchema).max(12).default([]),
```

The flat household mandate remains the **default/core policy**; any account not
claimed by a sleeve belongs to the implicit **unsleeved pool** (governed by the
household mandate + posture exactly as today). `sleeves: []` ⇒ current behavior,
unchanged.

**Validation** — extend `validatePortfolioMandate` (non-throwing; the `savePortfolioMandate`
action re-runs it as a throwing trust boundary):

- each `sleeve.id` unique; each `accountId` referenced by **at most one sleeve**
  (single-owner invariant — the double-counting killer);
- `riskAppetite` is a known `MANDATE_PACK` id (unknown id → a **save-only** guard,
  mirroring the mandate's `riskAppetite` handling, so a legacy stale id degrades only
  that sleeve's posture at seed, never the whole IPS);
- `cap.value` positive; a `pct` cap ≤ 100;
- eligibility lists canonicalized to UPPER; `includeOnlyTickers` and `excludeTickers`
  disjoint.

Account existence is **not** validated in the leaf (the leaf is browser-safe and
account-blind); the editor validates against the live account list, and routing
tolerates a sleeve naming a since-deleted account (it contributes zero utilization).

### 4.3 Utilization (Slice A) — the pure leaf

`domain/portfolio/math/sleeve-utilization.ts`, modeled on `summarizePortfolioHealth`:

```ts
export interface SleeveUtilization {
  sleeveId: string;
  label: string;
  accountIds: string[];
  deployedValue: number;                    // Σ market value of the sleeve's accounts' priced holdings
  cash: number;                             // Σ cash_balance of the sleeve's accounts
  capValue: number | null;                  // resolved to dollars (pct → % of household NAV); null = accounts' NAV
  availableToDeploy: number;                // max(0, min(capValue − deployedValue, cash)); capless → cash
  utilizationPct: number | null;            // deployedValue / capValue (null when capless)
  pricedCoverage: { priced: number; total: number };  // honesty: unpriced positions can't be valued
}

export function summarizeSleeveUtilization(
  sleeves: Sleeve[],
  accounts: AccountState[],                 // from toAccountStates(getPortfolio(userId))
  quotes: QuoteMap,                         // UPPER ticker → last-known price (app.quotes)
  householdNav: number,                     // for pct-cap resolution
): SleeveUtilization[];
```

Market value reuses `domain/portfolio/math/value-holding.ts` (`holdingMarketValue`,
FIX-773 per-type valuation) so bonds/MMF/options value correctly. An unpriced holding
degrades `deployedValue` coverage honestly (never a fabricated price — BP-020); a
sleeve with unpriced positions carries `pricedCoverage.priced < total` and its
`availableToDeploy` is a **conservative over-estimate** flagged in the UI.

Consumed in three places (one copy of the math): the Health view panel (client-side),
the seed injection (`<sleeves>` context), and routing.

### 4.4 Per-sleeve routing (Slice B) — deterministic projection

**Seed.** `seedSession` (`orchestration/guards.ts`) already reads the mandate,
re-validates it, and freezes `state.portfolioMandate` + `state.householdTickerWeightPct`.
Extend it to freeze `state.sleeves` (the validated `sleeves[]`) and, for routing,
`state.sleeveUtilization` (computed from the pre-scoping whole-book read, so a scoped
run still measures sleeve caps against the real accounts). The `portfolioMandate`
capability preset gains a `<sleeves>` block (frozen-state read, suppressed to null when
`sleeves` is empty — the `<portfolioMandate>` precedent), giving the trader + PM
awareness of the sleeve structure. **No new LLM output.**

**Routing leaf.** `domain/portfolio/math/sleeve-routing.ts` — pure, invoked in a
post-`portfolioStage` `.tap` (`compute-sleeve-routing.ts`, mirroring
`compute-reward-to-risk.ts`) that reads the committed PM memo + frozen sleeves +
utilization:

```ts
export interface SleeveFit {
  sleeveId: string; label: string;
  eligible: boolean;
  eligibilityReasons: string[];             // deterministic: which predicate passed/failed
  postureVerdict: "clears" | "soft-capped" | "capacity-vetoed" | "no-posture";
  postureTargetPct: number | null;          // PM target re-clamped under the sleeve's MANDATE_PACK
  availableToDeploy: number;                // from utilization
  capitalStatus: "has-capital" | "at-cap";
  verdict: "fits-with-capital" | "fits-no-capital" | "not-eligible";
}

export interface SleeveRouting {
  fits: SleeveFit[];                         // one per sleeve
  recommendedSleeveId: string | null;       // highest-priority fits-with-capital (order = mandate order)
  routableToUnsleeved: boolean;             // eligible under the household default pool
}

export function computeSleeveRouting(args: {
  ticker: string;
  assetType: AssetType;                     // classify-instrument on the analyzed symbol
  sector: string | null;
  pmTargetWeightPct: number;                // the committed portfolioFit.targetWeightPct
  finalRating: Rating;
  sleeves: Sleeve[];
  utilization: SleeveUtilization[];
  householdNav: number;
}): SleeveRouting;
```

For each sleeve, deterministically:
1. **Eligibility** — run the sleeve's `eligibility` predicates against the analyzed
   name's `assetType`/`sector`/ticker. All pass → eligible; record per-predicate reasons.
2. **Posture** — re-apply the FIX-752 gate math with `resolveMandate(sleeve.riskAppetite)`:
   the same soft worth-it cap + hard capacity veto already in `writer.ts`, but against
   the sleeve's pack and the sleeve's capital base. Reuse the existing clamp helper
   (extracted pure — see the consolidation note in §8). Produces `postureTargetPct`.
3. **Capital** — `availableToDeploy` from utilization; `at-cap` when the posture-sized
   dollar amount exceeds it.

`recommendedSleeveId` = the first (mandate-order) sleeve with
`verdict === "fits-with-capital"`. `"fits-no-capital"` is a first-class outcome that
triggers Slice C.

**Persistence & surfacing.** A nullable `sleeveRoutingResource` (surface-owned,
`.patchState` the full object; null when `sleeves` empty — the `lensConvergence`/
`rewardToRisk` resource precedent) holds the live artifact for the UI. The PM `writer.ts`
mirrors a compact `sleeveRouting` onto the PM memo (PmHero reads one place, the
`policyDecision`/`mandateDecision` precedent). `RunSummary` and the decision snapshot
gain a compact `sleeveRouting` echo (per-sleeve `{ sleeveId, verdict }` +
`recommendedSleeveId`) — the deterministic read path the goal check asserts on.

### 4.5 Funding-source / displacement (Slice C)

`domain/portfolio/math/funding-source.ts`, invoked by the routing tap **only when**
`recommendedSleeveId` is null *and* at least one sleeve is `"fits-no-capital"`:

```ts
export interface FundingCandidate {
  ticker: string; sleeveId: string;
  marketValue: number;
  convictionProxy: number;                  // 0..1 coarse score from stored data
  hasThesis: boolean;
  rationale: string;                        // why this is (or isn't) a displacement candidate
}
export interface FundingSourceResult {
  sleeveId: string;                         // the at-cap sleeve we're funding into
  candidateConviction: number;              // this run's conviction (convergence/rating derived)
  displacement: FundingCandidate | null;    // the weakest incumbent that clears the margin, or null
  cleared: boolean;                         // true → "sell X to fund Y"; false → "none clears the bar"
  marginPp: number;                         // hysteresis threshold used
}
```

`convictionProxy` is a **coarse, honest** composite over already-stored data: thesis
presence (`thesesCollection`), the incumbent's stored target/stop proximity to its last
price, and — where available — its last decision-snapshot rating. It is explicitly a
heuristic; no incumbent is re-analyzed. Displacement is suggested only when
`candidateConviction − weakestIncumbentConviction ≥ marginPp` (a fixed hysteresis
constant, e.g. `0.15`, to prevent churn). The result surfaces on the routing artifact
and PmHero as a **suggestion, never an auto-executed trade** (the desk's real-money
honesty gate). When no incumbent clears, the desk states *"no displacement clears the
bar"* — a first-class, legible output the issue explicitly asks for.

### 4.6 Household Health view (Slice A)

`health-section.tsx` gains a **Sleeves panel** reading `summarizeSleeveUtilization`
client-side (the `useMemo` + pure-leaf idiom, BP-010): per-sleeve label, deployed /
cap / available, utilization bar, coverage note. Zero new route (computed from the
already-fetched accounts + quotes + mandate). Capless sleeves show "no cap (accounts'
NAV)". The unsleeved pool is shown as a residual row so the panel always reconciles to
household NAV.

### 4.7 Error handling & real-money discipline

- **Unpriced holdings** → utilization coverage is honest; `availableToDeploy` flagged
  as an over-estimate; routing's capital check degrades to "capital unknown" rather
  than fabricating room (never coerce an unpriced position to $0 — the BP-020 /
  `computePolicyGate` precedent).
- **Stale/unknown `riskAppetite` on a sleeve** → that sleeve's posture degrades to
  posture-blind at seed (save-only guard), never blanks the mandate.
- **A sleeve naming a deleted account** → contributes zero utilization; not an error.
- **No sleeves** → `sleeveRoutingResource` null, `<sleeves>` suppressed, RunSummary
  `sleeveRouting` null; the run behaves exactly as pre-FIX-771.
- **Sleeve routing never touches `finalRating`** and never inflates size — downward-only,
  the FIX-715/752/761 orthogonality invariant.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| No sleeves defined | Unchanged pre-FIX-771 run; routing null, `<sleeves>` suppressed |
| Account claimed by two sleeves | Rejected at save (single-owner invariant); editor blocks it |
| Sleeve cap < current deployed value | `utilizationPct > 100`, `availableToDeploy = 0`, `at-cap`; UI shows over-cap flag (never force-trims — the at-purchase-cap precedent) |
| Analyzed name eligible for no sleeve | All `not-eligible`; `routableToUnsleeved` decides; PmHero says "fits no declared sleeve" |
| Fitting sleeve has capital | `fits-with-capital`; `recommendedSleeveId` set; no funding-source step |
| Fitting sleeve at cap | `fits-no-capital`; Slice C runs → "sell X to fund Y" or "none clears the bar" |
| Unpriced incumbent in the at-cap sleeve | Excluded from ranking with an honest note; not treated as $0 |
| Sleeve names a deleted account | Zero utilization contribution; not an error |
| Unknown `riskAppetite` id on a sleeve | Posture-blind for that sleeve; other sleeves + IPS unaffected |
| pct cap on a portfolio-blind run (no NAV) | Cap unresolvable → treated as capless with an honest "capital unknown" note |
| Scoped run (`selectedAccountIds`) | Utilization + routing computed from the pre-scoping whole-book read, so caps measure against real accounts |

**Error taxonomy:** all sleeve routing is deterministic and non-throwing at read/seed
(business-invalid → degrade, never throw — the mandate precedent); the only throwing
boundary is `savePortfolioMandate` re-validating sleeves at the trust boundary.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (Feature label) — tracer-bullet cycles per behavior.

**Goal (observable outcome):** With two sleeves declared — a defensive core and a
capped opportunistic sleeve — analyzing a name the core excludes but the opportunistic
sleeve permits produces a decision whose per-sleeve routing reports **"fits the
opportunistic sleeve, not the core"**, with a real capital-availability answer, and —
when that sleeve is at its cap — names a funding source or states none clears the bar.

**Goal check (real model, non-CI):** A `run.mts` under
`goals/trading-desk-sleeves/routes-candidate-to-eligible-sleeve/` that seeds a fixture
household with two sleeves (core = a low-risk account with a `dollar` cap already
near-deployed; opportunistic = an account with room and an `aggressive-growth`
posture), runs `analysis analyze` on a held-out speculative equity via `fsdev run`
against a real model, then reads `analysis runSummary` (zero-model) and asserts on the
`sleeveRouting` echo: the candidate is `not-eligible` for the core, `fits-with-capital`
(or `fits-no-capital` on the near-cap variant) for the opportunistic sleeve, and
`recommendedSleeveId` matches. **Anti-game:** the check must swap the two sleeves'
eligibility in a second fixture and require the recommendation to follow the rules, not
a fixed sleeve id — a hollow pass that always returns the same sleeve fails. Pass/fail
is the deterministic `sleeveRouting` fields, not model prose.

**Behaviours to test (vitest, mocked/deterministic — one per tracer cycle):**
- Sleeve validation: single-owner rejection; unknown-appetite save guard degrades one
  sleeve; cap bounds; eligibility canonicalization/disjointness.
- `summarizeSleeveUtilization`: deployed = Σ priced market value; `available = min(cap −
  deployed, cash)`; `pct` cap resolves against household NAV; capless → cash; unpriced
  coverage honest; deleted-account tolerance.
- `computeSleeveRouting`: eligibility pass/fail per predicate; posture re-clamp differs
  by pack (`conservative-income` vs `aggressive-growth`); `at-cap` vs `has-capital`;
  `recommendedSleeveId` follows mandate order; `not-eligible` for all → `routableToUnsleeved`.
- Pipeline E2E (`phase-5-sleeve-routing.spec.ts`): commit with a frozen multi-sleeve
  mandate emits the per-sleeve table + `recommendedSleeveId` on the memo + snapshot +
  RunSummary; **null when no sleeves**; `finalRating` unchanged; downward-only sizing.
- `computeFundingSources`: weakest-incumbent ranking; hysteresis margin gates the
  suggestion; unpriced incumbent excluded; "none clears the bar" when nothing clears.
- Seed: `state.sleeves`/`state.sleeveUtilization` frozen from the pre-scoping read;
  `<sleeves>` suppressed when empty.

**Reference specs for patterns:** `test/phase-5-policy.spec.ts` (frozen-state commit +
gate assertion off the streamed memo), `test/portfolio-health.spec.ts` (pure-leaf
aggregation), `test/portfolio-mandate-schema.spec.ts` (validation), and the
`fsd:write-block-tests` mock-context idiom.

## 8. Non-Goals

- **Intra-account virtual partitions** — a sleeve that owns *part* of a mixed account
  (options pool inside a margin account also holding equities). Needs per-holding
  tagging + a cash-attribution rule; deferred (§3.4-3). v1 sleeves own whole accounts.
- **Per-sleeve cash sub-ledger / shadow accounting** — availability is arithmetic, not
  a running per-sleeve balance (the Smartleaf pitfall). Deposits/dividends/proceeds are
  not attributed to sleeves.
- **Full comparative displacement** — re-analyzing each incumbent for a fresh conviction
  score. v1 is a stored-data heuristic; the real thesis-health input is **FIX-763**.
- **Per-sleeve theses** — thesis records stay household × ticker (FIX-760's own deferral
  to this issue is satisfied by routing, not by per-sleeve thesis records).
- **Risk-budget caps** — v1 caps capital (dollars/percent), not risk contribution. The
  documented honesty caveat: a dollar cap understates a small options sleeve's risk; the
  v2 upgrade is a max-loss/notional cap, not premium outlay.
- **Rebalancing execution / sell-to-rebalance** — the desk analyzes one name at a time.
- **Options-trade translation** for an aggressive options sleeve — that is **FIX-706**
  (Options Trader); sleeves route and size, they don't translate to a specific contract.
- **Soft/tolerance-band caps** — v1 caps are hard; tolerance bands govern rebalancing,
  which is out of scope.
- **Deepening opportunities flagged during research (follow-ups, not this spec):**
  - The PM commit runs three parallel size-clamp derivations (FIX-728 echo, FIX-752
    posture, FIX-761 policy) as implicit prose in `writer.ts`; per-sleeve routing
    multiplies the posture clamp. **Extract a single composed clamp function** (Slice B
    step 5 extracts the posture clamp; a fuller consolidation is a
    `fsd:improve-codebase-architecture` follow-up).
  - `portfolioDecisionOutputSchema` is very wide (~20 fields); this spec deliberately
    does **not** add to it (routing is derived), but the width itself is a standing
    deepening candidate.
