- **D1 — Routing is computed at PM commit, not in a post-stage tap.**
  `computeSleeveRouting` runs inside `commitPortfolioManagerMemo` (`writer.ts`),
  exactly like `policyDecision`/`mandateDecision`, and echoes onto the PM memo +
  decision snapshot + `RunSummary` (+ `runArtifacts` for eval parity). **No
  `.tap`, no `sleeveRoutingResource`** — routing is a PM *output* projection, not
  a PM *input* (the `lensConvergence` resource exists only because convergence is
  an input). This removes a resource, a tap file, an ordering contradiction, and
  a double-write hazard.
- **D2 — Explicit non-actionable verdicts.** `SleeveFit.verdict` includes
  `capital-unknown` (unpriced sleeve holdings, or a `pct` cap on an incompletely-priced
  whole book), `posture-blocked` (the posture clamp yields `postureTargetPct ≤ 0` — e.g. a
  `conservative-income` capacity veto to 0; a veto that clamps to a *positive* cap is a permitted
  small add, not blocked, L686), and
  `already-at-target` (an eligible sleeve already holds the ticker at/above its sleeve target
  → a non-positive incremental buy, even on a routed Buy). Unknown valuation / a vetoed / an
  already-satisfied sleeve is never coerced into `fits-*` or `recommendedSleeveId`.
- **D3 — Per-sleeve posture reuses the *existing* gate helper, with the reward figure
  recomputed per sleeve.** `flows/analysis/lib/mandate-gates.ts` exports the extracted
  clamp (`clampTargetWeight`/`computeMandateGates`, FIX-790). Routing **first resolves**
  `const m = resolveMandate(sleeve.riskAppetite)`; **if `m` is null** (a stale/removed pack
  survived the save guard) the sleeve is **posture-blind** (D4) — skip the gate entirely, never
  dereference `m` (L33). Otherwise it calls the clamp with `m`, `decisionConfidence`, and
  override. It does **not** reuse the stored `rewardToRisk` figure — that `lossAdjustedGlr` baked
  in the active-run mandate's λ; routing recomputes it per sleeve via `computeRewardToRisk({
  scenarios: rewardBuckets, lossAversion: m.lossAversion })` — the **resolved** pack's λ, since
  the sleeve schema carries only `riskAppetite`, not a `mandate` object (L483). Each sleeve clamps from
  the **raw pre-gate PM target** (`pmRawTargetWeightPct`), not the household-clamped committed
  value, so the deterministic FIX-752 + policy clamps don't **compound** across sleeves — a
  conservative *household* clamp on the committed value doesn't also cap an aggressive sleeve (L501).
  **This does NOT make per-sleeve posture an independent re-sizing.** `pmRawTargetWeightPct` is
  already the LLM's mandate-shaped *size*: the PM prompt (rules 11–12) sizes
  `portfolioFit.targetWeightPct` toward the **active run**'s `<riskMandate>` appetite, and every
  sleeve clamp is **downward-only**, so a more-aggressive sleeve can never *exceed* the
  run-mandate-sized target — it can only be re-clamped further down under a more-conservative
  sleeve. Per-sleeve posture is a downward-only **re-clamp of the run's target**, not a re-sizing to
  the sleeve's own appetite (D3a, §8, §3.3) — a deliberate v1 limitation with an escape: to size a
  name to an aggressive sleeve's appetite, re-run under that appetite via the FIX-752 run-override
  precedence; the fit / capital / funding answers are posture-independent, so a single run still
  routes correctly across every sleeve. A
  `null rewardBuckets` run (thin/errored forecast) gates **reward-blind** — the reward-floor /
  capacity-veto checks are skipped, never fed a synthesized null figure (L530/L536). Nothing
  re-extracted from `writer.ts`.
- **D4 — Unknown sleeve `riskAppetite` is a SAVE-ONLY guard.** It lives in the
  `savePortfolioMandate` action, NOT in `validatePortfolioMandate` — `seedSession`
  re-runs the validator and nulls the *whole* mandate on any issue, so a stale
  persisted sleeve id must degrade only that sleeve's posture, never blank the
  household IPS (the existing `riskAppetite` precedent).
- **D5 — Utilization is never frozen; the mandate is the single source of
  sleeves.** `summarizeSleeveUtilization` is a pure function of the frozen
  `portfolioMandate.sleeves` + the portfolio snapshot seed already materializes,
  recomputed at routing time and in the Health `useMemo` (the `summarizePortfolioHealth`
  precedent — never frozen). No `state.sleeveUtilization`, no separate
  `state.sleeves`.
- **D6 — Availability is cap-room only; cash is shown separately.**
  `availableToDeploy = max(0, capValue − deployedValue)`. Account cash is surfaced
  as an informational figure, not min-folded into availability (which reintroduced
  a soft cash-attribution rule the no-sub-ledger model rejects).
- **D7 — Eligibility is slimmed to `assetClasses` + `excludeTickers`.** It is modeled at
  the **asset-class** grain (the mandate's `equity|fixed_income|cash|crypto|alternative`),
  not asset *type* — the defensive core is a `fixed_income`+`cash` concept, and class
  avoids the bond-ETF / mixed-fund gap a type list would create. `excludeTickers` are
  UPPER-canonicalized at the **write path** (`savePortfolioMandate`), not the validator
  (which can't mutate and is re-run at seed), so an exclusion never silently fails on case.
  `sectors` and `includeOnlyTickers` are dropped from v1 (they duplicate the household mandate's
  exclusions at sleeve scope). Eligibility stays because a *candidate is not yet held in
  any account*, so account membership alone cannot answer "eligible for the
  aggressive sleeve, not the core" — but asset-class + posture carry the motivating
  core-vs-satellite split.
- **D8 — Slice C ships the narrower "list incumbents, no score" v1.** When the
  fitting sleeve is at cap, list its incumbents **no-thesis-first, then oldest-thesis**
  (the weakest — undocumented — incumbent surfaces first as a trim candidate, never
  biasing toward selling thesis-backed names, L594) — no numeric `convictionProxy`, no
  `marginPp` hysteresis constant, no `cleared` boolean. Same user-facing outcome the issue asks for (name the
  funding candidates, or "none" when the sleeve is empty) without a blind-tuned
  score that FIX-763 would redo wholesale. The scored/ranked displacement is the
  **FIX-763 upgrade**. `funding-source` merges into `sleeve-routing.ts` (two
  exports, one module).
- **D9 — Bundle a `mirrorNullable` helper.** Slice B step 6 touches `writer.ts`'s
  `decisionSnapshot` flatten anyway; the `sleeveRouting` mirror would be a *third*
  hand-copy of the `spread ?? {}`-with-typed-defaults pattern
  (`mandateDecision`/`policyDecision`). Fold a tiny shared `mirrorNullable(obj,
  keys)` so all three gates use it — a few lines, no behavior change, stops a
  fourth future copy.
- **D10 — Routing is proven by deterministic vitest + a fixture `fsdev run`
  smoke, not a real-model goal.** Routing is pure projection math; a mandate-swap
  fixture anti-games it. Real-model goals are reserved for end-to-end smoke
  (the `phase-5-policy.spec.ts` discipline).
- **D11 — Routing carries the inputs its dollar math needs, frozen from the WHOLE book.**
  `computeSleeveRouting` takes a **seed-frozen whole-book snapshot** (`state.sleeveBook`:
  all accounts + holdings + quotes + `householdNav`) and a seed-frozen
  `thesisPresenceIndex` (held ticker → thesis `updatedAt` | null). It does **not** reuse
  `state.portfolioContext` — on a scoped run that snapshot is the *selected* accounts only,
  so a sleeve owning accounts outside `selectedAccountIds` would read empty. The whole-book
  snapshot comes from the pre-scoping account read `seedSession` already does for
  `householdTickerWeightPct` (today discarded after that computation). The capital check
  converts the posture size to dollars against **`pmTargetNav`** (the NAV the PM target is a
  fraction of — the *scoped* NAV on a scoped run, not `householdNav`, L516) and subtracts the
  analyzed ticker's current exposure **on that same scope** — the PM's own whole-position
  `pmCurrentTickerWeightPct` (the FIX-728 echo the writer computes from the snapshot the target
  is measured against) — so it gauges the *incremental* buy, not the full target. This is
  cross-sleeve aware (a name already at target in sleeve A doesn't read as a fresh buy in sleeve
  B, L593) yet scope-consistent (a holding in an *unselected* account can't wrongly mark a
  scoped add `already-at-target`, L612). When the ticker is **held but unpriced**, that echo is an
  understated 0, so a `pmCurrentTickerExposureKnown` flag degrades the capital step to
  `capital-unknown` rather than green-lighting a fabricated fit (L571); likewise a
  `pmTargetNavComplete` flag degrades when the target scope has any *other* unpriced holding, since
  `buildPortfolioContext`'s `totalNav` would understate `pmTargetNav` and shrink the dollar add (L679).
  `householdNav` is used
  only to resolve `pct` caps. The frozen snapshot is **JSON-shaped** — quotes are a
  `Record<UPPER, {price,asOf}>`, not the portfolio-math `QuoteMap` `Map` (session state is JSON;
  a Map raises on write), and the leaf rebuilds the Map (L512). The funding list reads
  incumbents + thesis presence/staleness from these inputs and echoes structured
  `FundingEntry` records (L469), so no commit-time collection fan-out is needed (the
  snapshot-freeze precedent avoids the N+1). These are genuine new frozen fields (whole-book), distinct from the scoped
  `portfolioContext`, and the one exception to "no new frozen state."
- **D12 — the candidate's class is `classifyInstrument(ticker).assetClass`, captured at the
  equity-gate step (NOT a constant, NOT seed-frozen).** The analysis flow is equity-*type*-gated
  (`checkAssetTypeSupported`, FIX-773) — but that gate only stops `assetType` ∈
  {bond, option, crypto}. A **bond ETF** (`BND`/`AGG`/`TLT`) has `assetType: "etf"` and reaches
  PM commit, yet `classifyInstrument` already classes it `assetClass: "fixed_income"`
  (`classify-instrument.ts`, `KNOWN_BOND_ETFS`). So a hard-coded `equity` constant would
  mis-route every bond ETF — a `fixed_income` core would wrongly mark it `not-eligible`, an
  equity sleeve could wrongly recommend it (L543). The candidate class is derived at that gate step
  (which runs *after* `seedSession`, so the earlier seed-ordering problem is moot) with a
  **held-book-first** rule (L542): if the analyzed ticker is **already held**, use the *authoritative*
  `assetClass` the book records on its holding rows (frozen in `state.sleeveBook`,
  `portfolio-schema.ts`) — that already knows an off-list bond ETF / MMF as `fixed_income`/`cash`.
  A ticker held in **multiple accounts** can carry the **same class on every row** (the common
  case) or, rarely, **disagreeing** rows (a mis-imported holding); the book class is honored only
  when **every held row agrees** — a `distinct(assetClass)` of size 1. If the held rows **conflict**,
  the book is not authoritative, so it falls back to `classifyInstrument(ticker).assetClass` (the
  unheld path below) rather than arbitrarily picking one row's class (I3/L560). Only for an
  **unheld/new** candidate — or a conflicted held name — fall back to **`classifyInstrument(ticker).assetClass`**
  (the same classifier `checkAssetTypeSupported` computes). Either way it's captured onto
  `state.candidateAssetClass`. `assetClasses` eligibility then works for equities, curated bond
  ETFs, **and any already-held off-list instrument** (a `[fixed_income, cash]` core admits a held
  bond ETF, excludes a growth equity). **Known v1 limitation —
  symbol-only classification is best-effort, not authoritative (L124):** for an **unheld** candidate
  (no book row to consult), `classifyInstrument` has no price/provider hint pre-resolution, so it is
  exact only for plain equities and its **curated** `KNOWN_BOND_ETFS` set; an *unlisted, unheld*
  bond ETF falls through to `equity`, and an unheld money-market fund (recognized by a ~$1 price it
  doesn't have here) is missed. So for a **first-time** off-list candidate a `fixed_income`/`cash`
  sleeve may mis-admit/mis-exclude it until the **provider-resolved** `asset_class` lands (already-held
  off-list instruments are covered by the held-book class above). That resolved class (superseding `classify-instrument`
  entirely, and lifting the bond/crypto *analysis* stop so those candidates route rather than
  exclusion-only — plus the `CASH`/`USD` placeholder quirk) is the **FIX-777** upgrade;
  `resolveTicker` today returns only `{ resolved, reason }`. v1 does **not** add a bespoke stop for
  off-list ETFs (BP-038) — the pipeline already analyzes them as equity-shaped names, and the
  resolved-class upgrade is the right layer to fix it.
- **D13 — Routing gates on the sleeve-independent BUY RATING, not the mandate-shaped
  action.** `computeSleeveRouting` produces a projection when the name is a **buy candidate at all** —
  `finalRating` is a **Buy-family** rating (`Overweight`/`Buy`, the top two of the 5-tier
  `Sell/Underweight/Hold/Overweight/Buy` ladder, tier ≥ 3, `rating-engine.ts`). **It does NOT gate on
  `portfolioFit.action`** (raw *or* committed). The earlier "gate on the raw pre-policy action" design
  was wrong (Codex P1, L166): the PM prompt (rules 11–12) instructs the PM to emit
  `action: "hold"` **directly** for a name that fails the run's `<riskMandate>` bar or sits on the
  household exclusion list — so the AS-EMITTED (`pmRawAction`) action is *already* `hold`, and the
  writer's `add→hold` downgrade (`writer.ts:286`) only fires on the rare non-compliant run where the
  LLM emits `add` for an excluded name. Keying on the action therefore **suppressed routing for the
  exact motivating case**: a name that is a Buy on its merits but held-to-token by *this run's*
  posture — which a different sleeve's posture should still see. `finalRating` is the right signal
  because rules 11–12 keep it **mandate-orthogonal** (the mandate moves size + the worth-it verdict,
  never the rating — the FIX-715/FIX-752 orthogonality). So routing runs on the rating; a genuine
  **Hold / Underweight / Sell** (the name is not a buy candidate on its own merits, tier ≤ 2) →
  `sleeveRouting` + `recommendedSleeveId` null. **A household exclusion binds EVERY sleeve** (D13a,
  Codex P1/L644): a name on the mandate's `exclusions` list is `not-eligible` on every sleeve
  (blocker `household-excluded`) **and** blocks `routableToUnsleeved`. Two reasons this is the correct
  reading, not the earlier "exclusion scoped to the unsleeved remainder": (1) **coherence** — FIX-761
  treats a household exclusion as a **hard no-add**, and the same run's committed decision is a no-add,
  so surfacing "add it to your aggressive sleeve" would contradict the PM's own committed household
  call; (2) **deliverability** — the PM prompt (rule 12) already sizes an excluded name's
  `targetWeightPct` to ≤ the current household weight (0 for an unheld name), so `pmRawTargetWeightPct`
  is 0 and a downward-only per-sleeve clamp can only yield `already-at-target`, never the promised
  sleeve fit — routing a household-excluded name to a sleeve is not achievable without a
  pre-policy base size (the deferred D3a decision-tier change, §8). A sleeve still carries its **own**
  `excludeTickers` (D7) on top of the household floor. **Composes with the downward-only sizing limit (D3a):** the per-sleeve *size* is
  still the downward-only clamp of `pmRawTargetWeightPct`, so when the run's own posture already held
  the name to a token, a hotter sleeve routes as `already-at-target`/token — honest, with the FIX-752
  re-run as the escape for a posture-appropriate size (J3); the *eligibility / capital / fit-direction*
  answers routing surfaces are posture-independent and correct regardless. The per-sleeve
  `already-at-target` (a sleeve whose posture-clamped target ≤ current exposure, D2) replaces the old
  whole-run "non-positive incremental → null" gate — it was the same action/target contamination at
  the run grain. Documented in §4.2 and §8 so a user configuring an options sleeve isn't surprised it
  never returns `fits` for an option symbol (that stop is `checkAssetTypeSupported`, not the rating gate).

**Unchanged and in force:** mandate-as-container (`sleeves[]` on
`portfolioMandateResource`); account-anchored whole-account sleeves + optional hard
cap; run-once-route-deterministically (no per-sleeve LLM, no wider PM schema);
downward-only sizing that never touches `finalRating`; three independently-shippable
slices.

## 1. TLDR

**Plain-language summary.** A real investor rarely runs their whole book with one
risk setting. They keep a defensive core (bonds, money-market, cash earning 4%+)
and, alongside it, a small pool of money earmarked for something more aggressive
(say $20k for short-term options). Today the desk only understands one book with
one risk posture, so it can't say "this trade is wrong for my safe money but right
for my play money," and it can't tell you whether the pool it fits even has cash
left to deploy. This work lets the user declare named **strategies (sleeves)** —
each a set of accounts with its own risk posture, a spending cap, and rules for
what it's allowed to hold — and then, for any name the desk analyzes, answers per
sleeve: *does this fit, and is there money to buy it.* When the fitting sleeve is
tapped out, the desk lists what's already in it as the things you'd sell to make
room (or says the sleeve is empty).

**Technical statement.** Extend the durable `portfolioMandate` resource with an
optional `sleeves[]` container (each sleeve = accounts + a FIX-752 posture + a hard
capital cap + eligibility rules), compute per-sleeve utilization deterministically
from the `app.*` tables, and compute a **deterministic per-sleeve routing
projection at PM commit** (eligible? posture-sized? capital available?) — echoed
onto the PM memo, decision snapshot, RunSummary, and the PmHero + Health UI.

**Deliverables** (grouped by slice; order mirrors §5):

*Slice A — declare sleeves + see utilization:*
- Add `sleeveSchema` + `sleeves[]` to `portfolioMandateSchema` in `domain/portfolio/schema/portfolio-mandate-schema.ts`; extend `validatePortfolioMandate` with structural sleeve invariants (single-owner, cap bounds)
- Add pure leaf `domain/portfolio/math/sleeve-utilization.ts` (`summarizeSleeveUtilization`)
- Add a sleeve editor to `components/portfolio/mandate-dialog.tsx` and a per-sleeve utilization panel to `components/portfolio/health-section.tsx`

*Slice B — per-sleeve routing in analysis:*
- Freeze the validated mandate (with `sleeves`) at `seedSession` (`orchestration/guards.ts`); render `<sleeves>` via a `portfolioMandate`-preset extension
- Add `computeSleeveRouting` (pure) in `domain/portfolio/math/sleeve-routing.ts`, computed inside `commitPortfolioManagerMemo` (`agents/portfolio-manager/writer.ts`) using `mandate-gates.ts`; mirror onto PM memo + decision snapshot + `RunSummary` via a shared `mirrorNullable` helper
- Render the per-sleeve fit table in `components/theses/pm-hero.tsx`

*Slice C — funding-source (narrow):*
- When the routed sleeve is at cap, list its incumbents (no-thesis-first, then oldest-thesis) on the routing projection + PmHero; no numeric scoring (that is the FIX-763 upgrade)

## 2. Overview

**Linear issue:** [FIX-771](https://linear.app/fixpoint-labs/issue/FIX-771) —
*Trading-desk: one book, one posture — multi-strategy capital sleeves with
trade-to-sleeve routing, capital availability, and funding-source analysis.*

The desk models one portfolio with one risk posture. This adds **capital sleeves**:
named strategies (a defensive core, a capped opportunistic pool) each with its own
posture, capital cap, and eligibility rules. Analysis gains a per-sleeve routing
answer — *fits sleeve B not A*, *fits but no free capital* — and, when a fitting
sleeve is at cap, the incumbents you'd sell to fund the trade. It builds directly on
the shipped mandate (FIX-761), risk posture (FIX-752), portfolio-fit verdict
(FIX-728), thesis records (FIX-760), household health view (FIX-762), and the
relational model layer (FIX-772), all of which are Done.

## 3. Background & Research

### 3.1 What already shipped (the surface this extends)

Every dependency this issue was written against is now **Done**. The issue's
central worry — *"reconcile before FIX-761 is specced"* — is moot: FIX-761 shipped
a flat household mandate **deliberately coordinated with this work**. From the
FIX-761 spec, verbatim:

> "Flat household mandate now; a clean seam for FIX-771 sleeves, no container built."
> … "a future `sleeves: Mandate[]` wraps today's object, which becomes the
> household/default policy."

So the reconciliation is already decided in principle: **the mandate is the sleeve
container.** No container structure was pre-built (BP-038/YAGNI); this issue builds it.

Load-bearing shipped facts (all verified in-code):

- **The mandate is a user-scoped resource, not a table.** `portfolioMandateResource`
  (`flows/portfolio/portfolio-resources.ts`, `scope: "user"`, `flowIsolation: false`,
  one document per household). Schema `portfolioMandateSchema`
  (`domain/portfolio/schema/portfolio-mandate-schema.ts`). Chosen as a resource
  because it is a flat household document (no FK/join/aggregation) and agent-facing
  state read at seed — the documented **resource-vs-table criterion** (FIX-772).
- **The decision spine is "LLM decides once; deterministic gates clamp/route."** The
  PM (`agents/portfolio-manager/`) is the sole arbiter. It emits a single
  `portfolioFit` (`action`, `targetWeightPct`, …). At commit, pure functions derive
  the gates from **frozen state, never the LLM**: `computePolicyGate`
  (`lib/policy-gate.ts`, FIX-761 mandate) and the FIX-752 posture clamp
  (`lib/mandate-gates.ts`, from the resolved `MANDATE_PACK` dial). All clamps are
  downward-only and never touch `finalRating`. Verdicts echo onto the PM memo, the
  decision snapshot, and the `RunSummary` (the goal-check read path).
- **Posture is config-as-data, reusable per account-set.** `lib/risk-mandate.ts`:
  `MANDATE_PACK` (`conservative-income`/`balanced`/`aggressive-growth`),
  `resolveMandate(id)`, `mostConservativeMandate(ids)`. The clamp itself is extracted
  in `lib/mandate-gates.ts` (`clampTargetWeight`/`computeMandateGates`, FIX-790).
  Appetite resolves at seed: `run override → account default → IPS household → null`.
- **Accounts/holdings/ledger are relational `app.*` tables** via the typed repository
  (`db/repository.ts`, `getRepository()`). `app.accounts` carries `cash_balance` and
  an opaque `risk_mandate`; `app.holdings` is one row per `(account_id, ticker)`. The
  repository interface reserves *"per-sleeve cash"* aggregates for this issue,
  verbatim.
- **The household Health view is a deterministic pure leaf.**
  `domain/portfolio/math/portfolio-health.ts` (`summarizePortfolioHealth`), rendered
  in `components/portfolio/health-section.tsx` and injected into the PM context at
  seed. It is **never frozen** — recomputed client-side. Per-sleeve utilization is
  its named FIX-771 follow-up.
- **Thesis records** (`thesesCollection`, household × ticker resource) carry entry
  rationale + structured **tripwires** — the "why + invalidation" data the funding
  list orders on. The **re-validation loop that scores thesis health is FIX-763
  (Todo)** — which is why v1 lists incumbents without a numeric score.

### 3.2 Industry practice (how sleeves are really run)

- **Sleeve accounting (UMA/SMA).** A custodial account is subdivided into sleeves,
  each a strategy with its own holdings and — in true sub-accounting — its own cash.
  The hard, drift-prone part is per-sleeve cash: nothing about a deposit, dividend, or
  sale tells you which strategy owns it, so platforms maintain a shadow ledger and
  reconcile. A weaker "tagging" model keeps one cash pool and *"you can't really tell"*
  how much belongs to each strategy. ([Smartleaf](https://www.smartleaf.com/our-thinking/smartleaf-blog/a-guide-to-smas-and-umas), [Vestmark](https://www.vestmark.com/resources/blog/sleeves-tagging-and-the-pathway-to-improved-accounting))
- **Core–satellite.** A large defensive core + capped opportunistic satellites; caps
  expressed as % of book or fixed dollar; hard caps vs. tolerance bands. ([Saxo](https://www.home.saxo/learn/guides/diversification/core-satellite-approach-a-smarter-way-to-diversify-your-investments))
- **Capital vs. risk budgeting.** Risk budgeting (size by risk contribution) is more
  truthful for a small options sleeve but needs a covariance model. **Capital
  budgeting (a dollar/percent cap) is the honest v1** — directly observable from
  positions, no risk model — as long as you don't pretend the dollar cap is a risk
  limit. ([AnalystPrep CFA L3](https://analystprep.com/study-notes/cfa-level-iii/risk-budgeting/))
- **Funding-source / sell discipline.** "Every position must continually earn its
  place." When a candidate fits but there's no dry powder, the funding source is one of
  the sleeve's incumbents — real desks rank by conviction/thesis health and displace
  the weakest. v1 lists the incumbents (the FIX-763 upgrade adds the ranking).
  ([JAG Capital](https://www.jagcap.com/articles/articles-v2/investment-sell-discipline/))
- **Pitfalls.** Shadow-accounting reconciliation drift, cash leakage between sleeves,
  double-counting a name held in two sleeves, over-constraining. The single rule that
  kills most of these at once: **one owning sleeve per position.** ([Smartleaf — The Case Against Sleeves](https://www.smartleaf.com/our-thinking/smartleaf-blog/the-case-against-sleeves))

**The pragmatic v1 the research points to:** a sleeve is a lightweight declaration
`{ id, name, posture, capital cap, eligibility, accounts }`; the cap is a **hard
ceiling on deployed capital**; availability is computed **arithmetically each run**
(`available = cap − Σ market value of the sleeve's positions`) with **no sub-ledger**;
**one owning sleeve per account** removes double-counting and cash-attribution
entirely.

### 3.3 Why this approach (fit to the codebase)

The desk's existing spine — *one LLM decision, deterministic gates clamp size and
emit verdicts from frozen state* — already contains everything sleeve routing needs.
A name's quality/edge (Buy/Hold/Sell + conviction) is **sleeve-independent**; only
*fit* (eligibility rules), *size* (posture math), and *capital* (arithmetic) vary by
sleeve, and all three are deterministic. So routing is a **projection of the single
decision**, not a re-judgment — computed exactly the way `computePolicyGate` and the
posture clamp already are, in the same commit handler. This is why the issue's "run
once and route, or run per-sleeve?" resolves to **run once, route deterministically**,
and why the PM's LLM output does *not* grow a per-sleeve array (which would be an
unfillable strict schema). The one honest seam in "size varies by sleeve": the per-sleeve
posture math is a **downward-only re-clamp** of the run's PM target, not an independent
re-size to each sleeve's appetite. The LLM sized `pmRawTargetWeightPct` toward the **active
run**'s mandate (prompt rules 11–12) and every clamp is downward-only, so a more-aggressive
sleeve can't be sized *above* the run target inside one run — sizing a name to an aggressive
sleeve's appetite is the FIX-752 run-override re-run (D3a, §8). Fit / capital / funding stay
posture-independent, so a single run still routes correctly across every sleeve; only the
in-sleeve *size* under a hotter appetite needs the re-run.

### 3.4 Key Decisions & Ramifications (top 5)

1. **Per-sleeve routing is deterministic, computed at PM commit — not an LLM
   fan-out, not a wider PM output, not a post-stage tap/resource.**
   *Alternative rejected:* re-run the pipeline per sleeve (cost × N); widen
   `portfolioDecisionOutputSchema` to an array of verdicts; or persist routing in a
   `sleeveRoutingResource` behind a tap. *Ramification:* fit/size/capital are derived
   projections computed in `commitPortfolioManagerMemo` (the `policyDecision`/
   `mandateDecision` precedent), so a sleeve differs on *eligibility and capital* but
   never on the name-level quality verdict. Cost stays flat, the strict PM schema is
   untouched, and there is no resource/tap to keep coherent (D1).

2. **The mandate becomes the sleeve container: `sleeves[]` on
   `portfolioMandateResource`, not a new table or separate resource.**
   *Alternative rejected:* an `app.sleeves` + `app.sleeve_accounts` table pair.
   *Ramification:* one policy object (resolves the issue's central reconciliation
   exactly as FIX-761 designed), backward compatible (no `sleeves` = today's flat
   mandate = the implicit "core"), inherits the live client read + streaming for free.
   The cost: the resource can't join, so **utilization is computed** from the `app.*`
   tables by a pure leaf at read time — the same pattern Health already uses.

3. **Account-anchored sleeves with an optional hard capital cap; arithmetic
   availability (cap-room only); no cash sub-ledger.**
   *Alternative rejected:* per-holding sleeve tags + a per-sleeve cash sub-ledger.
   *Ramification:* one account → at most one sleeve kills double-counting and
   cash-attribution; `available = max(0, cap − deployedValue)` re-derived each run;
   cash shown separately as informational (D6). The cost: an **intra-account virtual
   partition** (an options pool inside a mixed account) is out of scope — a sleeve
   claims whole accounts. The "$20k options pool" is a sleeve over the options account
   with `cap = $20k`.

4. **Funding-source is a listed set of incumbents in v1, not a scored ranking.**
   *Alternative rejected:* a `convictionProxy` composite + `marginPp` hysteresis built
   now. *Ramification:* v1 lists the at-cap sleeve's incumbents (no-thesis-first, then
   oldest-thesis — the weakest surfaces first, D8) — the legible "here's what you'd sell"
   outcome — without a blind-tuned constant that FIX-763's real thesis-health scoring would redo wholesale.
   The scored/ranked displacement is the FIX-763 upgrade (D8).

5. **Ship as three independently-shippable slices** (declare + utilization → routing →
   funding list), not one PR. *Ramification:* Slice A is visible and valuable on its
   own (define sleeves, see utilization) with zero analysis-pipeline change; Slice C
   (the FIX-763-adjacent one) is last and can be re-scoped without blocking A/B.

### 4.2 Data model — the sleeve schema (Slice A)

A sleeve is a **lean policy document**, not a full sub-mandate. It reuses the posture
pack id; it does **not** carry its own `targetAllocation` (that is a household
asset-mix concept, and the mandate's `targetAllocation.max(5)` "one per asset class"
assumption does not transfer to a capital pool). New leaf in
`portfolio-mandate-schema.ts` (browser-safe, zod-only — a resource/input shape, **not**
a generator output, so `.nullable()`/`.default()` are correct; do **not** add to
`output-schemas-strict.spec.ts`):

```ts
export const sleeveCapSchema = z.object({
  // Hard ceiling on DEPLOYED capital. Absent cap → the sleeve's accounts' NAV.
  type: z.enum(["dollar", "pct"]),          // pct = % of household NAV
  value: z.number().positive().finite(),
});

export const sleeveEligibilitySchema = z.object({
  // Deterministic allow/deny predicates over a candidate's classified attributes.
  // v1: asset-CLASS + name exclusion only (D7). sectors / includeOnly are a later add.
  // Asset CLASS (not asset type): the defensive core is "fixed_income + cash", which is a
  // class concept — a bond ETF and a bond both belong to the fixed_income class, so class
  // avoids the bond-ETF / mixed-fund gap that an asset-type list would create.
  assetClasses: z.array(mandateAssetClassSchema).default([]),  // [] = any class; reuses the mandate's
                                                     //   equity | fixed_income | cash | crypto | alternative enum
  excludeTickers: z.array(z.string()).default([]),   // canonical UPPER; never eligible
});

export const sleeveSchema = z.object({
  id: z.string().min(1),                    // stable slug, unique within the mandate
  label: z.string().min(1).max(120),
  objective: z.string().max(400).default(""),         // free-text intent (agent-facing)
  riskAppetite: z.string(),                 // FIX-752 MANDATE_PACK id (the sleeve's posture)
  accountIds: z.array(z.string()).min(1),   // the accounts this sleeve owns (whole-account)
  cap: sleeveCapSchema.nullable().default(null),
  eligibility: sleeveEligibilitySchema.default(() => sleeveEligibilitySchema.parse({})),
});

// Additive to portfolioMandateSchema:
//   sleeves: z.array(sleeveSchema).max(12).default([]),
```

The flat household mandate remains the **default/core policy**; any account not
claimed by a sleeve belongs to the implicit **unsleeved pool** (governed by the
household mandate + posture exactly as today). `sleeves: []` ⇒ current behavior,
unchanged.

**Why eligibility stays (even for whole-account sleeves).** A *candidate being
analyzed is not yet held in any account*, so account membership tells you where
*existing* holdings sit, not which sleeve a *new* name may enter. Without an
eligibility predicate every capitalized sleeve would "fit" every analyzed name and
routing degenerates to "cheapest sleeve with room," losing the issue's "fits B not A"
outcome. Asset-class eligibility + posture carries the motivating split (a speculative
equity is not eligible for a `fixed_income`+`cash` / `conservative-income` core). **The
analyzed name's class is `classifyInstrument(ticker).assetClass`, captured at the
`checkAssetTypeSupported` step (D12).** That gate already computes the classification and runs
*after* seed, so it — not seed — freezes `state.candidateAssetClass`. It is **not** a hard-coded
`equity` constant: the gate only stops `assetType` {bond, option, crypto}, so a **bond ETF**
(`BND`/`AGG`/`TLT`, `assetType: "etf"`, `assetClass: "fixed_income"`) reaches commit and must
route as `fixed_income` — a `[fixed_income, cash]` core admits it, an equity sleeve excludes it
(L543). For a non-equity *candidate class* that the analysis pipeline can't yet analyze
(a bond/crypto symbol), `checkAssetTypeSupported` stops the run before commit, so in v1
`assetClasses` mostly acts as an exclusion axis; `fits` for those classes arrives when FIX-777
lifts the analysis stop. Known v1 wart: the placeholder tickers `CASH`/`USD` classify as
cash/money_market though they are real instruments of other kinds (a pre-existing
`classifyInstrument` quirk); a provider-resolved class supersedes it under FIX-777.

**Validation — structural only (`validatePortfolioMandate`, non-throwing):**

- each `sleeve.id` unique; each `accountId` referenced by **at most one sleeve**
  (single-owner invariant — the double-counting killer);
- `cap.value` positive; a `pct` cap ≤ 100.

Intra-sleeve duplicate `accountIds` are **not** a validation issue — `["A","A"]` is
**normalized (deduped) at the `savePortfolioMandate` write path** (the `excludeTickers`
canonicalization precedent), not rejected, so A's holdings/cash count once without failing the
save on a harmless typo (L440/L452).

**`excludeTickers` are canonicalized to UPPER at the WRITE path**, in
`savePortfolioMandate` (the household-exclusion precedent), **not** in
`validatePortfolioMandate` — the validator only returns issue strings and is re-run at seed,
so it cannot mutate the record; a lowercase `nvda` left un-canonicalized would silently fail
the exclusion against the UPPER analyzed ticker (L389).

**Unknown `riskAppetite` is a SAVE-ONLY guard (D4)** — enforced in the
`savePortfolioMandate` action, NOT in `validatePortfolioMandate`. `seedSession`
re-runs the validator and nulls the whole mandate on any issue, so a stale sleeve id
must degrade only that sleeve's posture (posture-blind), never blank the household IPS
— exactly how the mandate's own `riskAppetite` is handled. Account existence is not
validated in the leaf (browser-safe, account-blind); the editor checks the live
account list, and routing tolerates a sleeve naming a since-deleted account (it
contributes zero utilization).

### 4.3 Utilization (Slice A) — the pure leaf

`domain/portfolio/math/sleeve-utilization.ts`, modeled on `summarizePortfolioHealth`
(pure; never frozen — D5):

```ts
export interface SleeveUtilization {
  sleeveId: string;
  label: string;
  accountIds: string[];
  liveAccountCount: number;                 // sleeve accountIds that resolve to a live account; 0 → non-routable
  deployedValue: number;                    // Σ market value of the sleeve's accounts' priced holdings
  cash: number;                             // Σ cash_balance of the sleeve's accounts (informational)
  capValue: number | null;                  // pct → % of household NAV; null = accounts' NAV (capless)
  capitalKnown: boolean;                    // false → unpriced holdings or unresolvable pct cap
  availableToDeploy: number;                // max(0, capValue − deployedValue); capless → accounts' NAV − deployed;
                                            //   FORCED to 0 when liveAccountCount === 0 (no destination for a buy)
  utilizationPct: number | null;            // deployedValue / capValue — null when capless/unknown OR
                                            //   capValue <= 0 (a pct cap on a zero-NAV book; never NaN/Infinity, L487)
  pricedCoverage: { priced: number; total: number };
}

export function summarizeSleeveUtilization(
  sleeves: Sleeve[],
  accounts: AccountState[],                 // from toAccountStates(getPortfolio(userId))
  quotes: QuoteMap,                         // UPPER ticker → last-known price (app.quotes)
  householdNav: number,                     // pct-cap denominator
  navComplete: boolean,                     // every whole-book holding priced — a pct cap
                                            //   resolves only when true, else capitalKnown:false
): SleeveUtilization[];
```

Market value reuses `domain/portfolio/math/value-holding.ts` (`holdingMarketValue`,
FIX-773 per-type valuation) so bonds/MMF/options value correctly. `capitalKnown` is
`false` when a sleeve holding is unpriced **or** the sleeve has a `pct` cap and the
**whole book** isn't fully priced (the leaf takes a `navComplete` flag — a `pct` cap is a
fraction of household NAV, so a missing quote *anywhere in the book* makes that NAV, and
the cap, unresolvable; never a fabricated price or a partial-denominator number — BP-020).
Cash is a separate informational figure, not folded into `availableToDeploy` (D6).
`utilizationPct` guards a **zero denominator**: a `pct` cap on a zero-NAV book resolves
`capValue` to 0, so `utilizationPct` is `null` (not `NaN`/`Infinity`) when `capValue <= 0` — the
Health bar renders "no cap basis" rather than a broken value (L487).
A sleeve whose accounts are **all deleted** has `liveAccountCount === 0`; `availableToDeploy`
is forced to `0` so neither the Health panel nor routing shows deployable capital for a sleeve
with no destination account (a dollar cap would otherwise report the full cap free — L464).
This lives in the leaf (not just routing) because Slice A ships the Health panel independently
of Slice B's routing. Consumed in two places (one copy of the math): the Health panel
(`useMemo`) and routing (which additionally maps `liveAccountCount === 0` → the
`no-live-account` `not-eligible` verdict).

### 4.4 Per-sleeve routing (Slice B) — deterministic projection at PM commit

**Seed.** `seedSession` (`orchestration/guards.ts`) already reads the mandate,
re-validates it, and freezes `state.portfolioMandate` (which now carries `sleeves` — the
single source of sleeve *definitions*, D5) + `state.householdTickerWeightPct`. Two new
frozen fields carry the whole-book data routing needs (D11 — see below). The
`portfolioMandate` capability preset
gains a `<sleeves>` block (frozen-state read, suppressed to null when `sleeves` is
empty — the `<portfolioMandate>` precedent), giving the trader + PM awareness of the
sleeve structure. **No new LLM output.** Seed also freezes, from the **pre-scoping
whole-book account read** it already performs for `householdTickerWeightPct` (today
discarded), a compact `state.sleeveBook` (all accounts + holdings + quotes +
`householdNav` + a `navComplete` flag = every whole-book holding priced) and a
`state.thesisPresenceIndex` (held ticker → thesis `updatedAt` | null). Routing's
`candidateAssetClass` input is **held-book-first** (D12/L542): the authoritative `assetClass` the
book records for the ticker when it is **already held** *and* every held row agrees on the class
(so a held off-list bond ETF routes as `fixed_income`, not `equity`), else
**`classifyInstrument(ticker).assetClass`** for an unheld candidate — or for a held name whose rows
**conflict** on class (I3/L560), where the book isn't authoritative. Frozen onto
`state.candidateAssetClass` at the **`checkAssetTypeSupported`** step (which
runs after seed), so it's never a hard-coded `equity` (L543).
Routing uses `sleeveBook`, **not** the scoped `state.portfolioContext` — a sleeve
can own accounts outside `selectedAccountIds`, which the scoped snapshot cannot see (D11).
These two whole-book fields are the deliberate new frozen state (distinct from the scoped
`portfolioContext`); both ride the pre-scoping read, so the Slice C funding list needs no
commit-time collection fan-out.

**Routing leaf.** `domain/portfolio/math/sleeve-routing.ts` — pure, called **inside
`commitPortfolioManagerMemo`** (`agents/portfolio-manager/writer.ts`), alongside the
existing `policyDecision`/`mandateDecision` derivations (D1). It recomputes utilization
from the frozen mandate + `book` (passing `book.navComplete`), then for each sleeve:

```ts
export interface SleeveFit {
  sleeveId: string; label: string;
  accountIds: string[];                      // the sleeve's owned account IDS — the writer maps the LLM's
                                            //   suggestedAccount LABEL to its id (via the account list) before the
                                            //   membership check, then reconciles the destination (L558/L749)
  verdict: "fits-with-capital" | "fits-no-capital" | "capital-unknown"
         | "posture-blocked" | "already-at-target" | "not-eligible";
  postureTargetPct: number | null;          // PM target re-clamped under the sleeve's MANDATE_PACK (null if not eligible)
  availableToDeploy: number | null;         // null when capital-unknown
  blockers: string[];                        // deterministic reasons: failed predicate, at-cap, unpriced, capacity-veto
  funding: FundingEntry[];                   // Slice C: incumbents to consider selling (only when fits-no-capital)
}

export interface FundingEntry {              // structured so PmHero/RunSummary render + audit the order (D8)
  ticker: string;                            // UPPER
  marketValue: number;                       // its value in the sleeve (how much it would free)
  hasThesis: boolean;                        // false → "no thesis on file"
  thesisUpdatedAt: string | null;            // staleness — the sort key after thesis presence
}

export interface SleeveRouting {
  fits: SleeveFit[];                         // one per sleeve
  recommendedSleeveId: string | null;       // first (mandate-order) sleeve with fits-with-capital
  routableToUnsleeved: boolean;
  unsleevedAccountIds: string[];             // unclaimed in-scope account ids — lets PmHero reconcile
                                            //   suggestedAccount in the unsleeved fallback (L754)
}

export function computeSleeveRouting(args: {
  ticker: string;                           // analyzed symbol (UPPER)
  candidateAssetClass: AssetClass;          // held-book-first (D12/L542): the book's authoritative assetClass
                                            //   when the ticker is already held AND all held rows agree (a held bond
                                            //   ETF → fixed_income); else classifyInstrument(ticker).assetClass for an
                                            //   unheld candidate OR a held name whose rows conflict on class (I3).
                                            //   Frozen at the checkAssetTypeSupported step (post-seed); NOT a
                                            //   hard-coded equity (L543). Provider-resolved class supersedes under FIX-777
  pmRawAction: "initiate" | "add" | "trim" | "exit" | "hold";  // the PM's AS-EMITTED action — RENDER-ONLY
                                            //   context (shows the committed direction beside the routing). NOT the
                                            //   routing gate: rules 11-12 make the PM emit `hold` directly for a
                                            //   mandate-failing / excluded name, so the action is posture-contaminated
                                            //   (D13/L166). The gate is finalRating (below); per-sleeve add-vs-at-target
                                            //   is the sleeve's own posture-clamped target vs current exposure (D2)
  pmRawTargetWeightPct: number;             // the PM's AS-EMITTED portfolioFit.targetWeightPct, BEFORE the run's
                                            //   FIX-752 + policy clamps — each sleeve clamps from the raw target
                                            //   under its own posture, else a conservative run zeros every sleeve (L501 P1)
  pmTargetNav: number;                       // the NAV that the target is a % of — the SCOPED
                                            //   NAV on a scoped run, else householdNav (D11; L516 fix)
  pmTargetNavComplete: boolean;             // is the pmTargetNav SCOPE fully priced? buildPortfolioContext's totalNav
                                            //   omits unpriced holdings, so a partial scope UNDERSTATES pmTargetNav and
                                            //   the %→$ target undershoots — false → capital-unknown, never a fabricated
                                            //   dollar fit against cap room (L679; same discipline as navComplete)
  pmCurrentTickerWeightPct: number;          // the analyzed ticker's CURRENT whole-position weight on the
                                            //   pmTargetNav scope (the FIX-728 echo writer.ts already computes) —
                                            //   the incremental buy subtracts this, so target + exposure share one
                                            //   scope: cross-sleeve aware yet not tricked by unselected accounts (L612)
  pmCurrentTickerExposureKnown: boolean;     // false when the ticker is HELD but unpriced — writer's currentWeightPct
                                            //   sums only priced rows (→ understated 0), so an unknown exposure must
                                            //   degrade the capital step to capital-unknown, never a fabricated fit (L571)
  finalRating: Rating;                       // THE ROUTING GATE (D13): a Buy-family rating (Overweight/Buy,
                                            //   tier >= 3 on the Sell/Underweight/Hold/Overweight/Buy ladder) means
                                            //   the name is a buy candidate at all. Mandate-orthogonal (rules 11-12
                                            //   never let the mandate touch the rating), so it survives a run whose
                                            //   posture shaped `action` to hold. Hold/Underweight/Sell → null routing
  rewardBuckets: ScenarioBucket[] | null;   // RAW scenario terms (λ-independent), so each sleeve's λ
                                            //   re-derives lossAdjustedGlr via computeRewardToRisk (D3; L483 fix) —
                                            //   NOT the active-run rewardToRisk figure, whose λ is already baked in
  decisionConfidence: number;               // threaded for the FIX-752 gate (D3)
  mandateOverrideReason: string;            // threaded for the soft worth-it cap (D3)
  householdExclusions: string[];            // UPPER, from the frozen mandate — a hard household no-add: marks the
                                            //   name not-eligible on EVERY sleeve (household-excluded blocker, D13a)
                                            //   AND blocks routableToUnsleeved (L554/L644)
  householdHasAddRoom: boolean;             // did the COMMITTED household decision leave positive add room? EXACT
                                            //   derivation from the FULL computePolicyGate RESULT (the `policyVerdict`
                                            //   enum ALONE is insufficient — `capped` collapses a cap>household add
                                            //   with room AND a cap<=household clamp-to-current with NONE, Greptile
                                            //   P1/L676): the writer computes it as
                                            //     gate.householdWeightKnown && !gate.excluded
                                            //       && gate.targetWeightPct > state.householdTickerWeightPct
                                            //   i.e. the POST-policy committed target exceeds the current household
                                            //   weight, with the cap actually EVALUATED. This is false for `excluded`
                                            //   (no-add), `unenforced` (householdWeightKnown false — an unpriced held
                                            //   ticker leaves the cap unevaluated, so a positive target is NOT proof of
                                            //   room), a within-policy HOLD-at-current (target <= household), and a
                                            //   cap-full clamp (target clamped down to household). True only for a
                                            //   within-policy or capped add that clears the current household weight.
                                            //   The gate uses household-NAV units; on a scoped run it inherits the SAME
                                            //   documented safe-direction imprecision as the gate's own cap clamp
                                            //   (over-restricts → suppresses the fallback, never fabricates room,
                                            //   writer.ts:263). The unsleeved pool IS the household decision, so
                                            //   routableToUnsleeved requires this (L694/L716)
  selectedAccountIds: string[];             // the run's account scope ([] = unscoped/whole-book). On a scoped
                                            //   run a sleeve owning NONE of these → out-of-scope not-eligible, and
                                            //   routableToUnsleeved counts only unclaimed selected accounts (L616)
  sleeves: Sleeve[];
  book: SleeveBook;                         // seed-frozen WHOLE-BOOK snapshot (all accounts + holdings +
                                            //   quotes + navComplete) — utilization, exposure, incumbents derive from this (D11).
                                            //   JSON-shaped: quotes are a Record<UPPER, {price,asOf}>, NOT a QuoteMap `Map`
                                            //   (session state is JSON; a Map raises on write) — the leaf rebuilds the Map (L512)
  householdNav: number;                     // whole-book NAV — used ONLY to resolve `pct` caps (D11)
  thesisPresenceIndex: Record<string, string | null>;  // UPPER ticker → thesis updatedAt (null = none),
                                            //   frozen at seed for held tickers; orders the funding list (D11)
}): SleeveRouting | null;                   // NULL for the whole-run skip: no sleeves defined, or a non-Buy-family
                                            //   finalRating (Hold/Underweight/Sell — not a buy candidate, D13/L166) —
                                            //   the caller mirrors nothing, preserving the pre-FIX-771 shape
```

**Routing applies to a BUY CANDIDATE — gated on the sleeve-independent `finalRating`.** If
`finalRating` is not Buy-family (`Overweight`/`Buy`, tier ≥ 3) — i.e. a `Hold`, `Underweight`, or
`Sell` on the name's own merits — there is no buy to route: `sleeveRouting` is `null` and
`recommendedSleeveId` stays null. **The gate is the rating, NOT `portfolioFit.action`** (Codex P1,
L166): the PM prompt (rules 11–12) makes the PM emit `action: "hold"` *directly* for a Buy-rated name
that fails the run's `<riskMandate>` bar or the household exclusion, so the AS-EMITTED action is
already `hold` — keying on it (raw or committed) suppresses routing for the exact "Buy on merits, held
by *this run's* posture, right for another sleeve" case the feature exists to surface. `finalRating`
is mandate-orthogonal (rules 11–12 never let the mandate move the rating), so it survives the
posture-shaped `hold`. **A household exclusion, though, binds every sleeve** (D13a) — an excluded
name is `not-eligible` on all sleeves (blocker `household-excluded`) and blocks
`routableToUnsleeved`; it is NOT routed around to an eligible sleeve, both because that would
contradict the run's own committed household no-add and because rule 12 sizes the excluded target to
≤ the current household weight (0 when unheld), so the downward-only per-sleeve clamp could only yield
`already-at-target` anyway (Codex P1/L644). The per-sleeve
`already-at-target` verdict (a sleeve whose posture-clamped target ≤ its current exposure, D2)
replaces the old whole-run "non-positive incremental → null" filter — a Buy the run's posture held to
a token routes per-sleeve as `already-at-target`/token (downward-only size, D3a/J3), with the FIX-752
re-run as the escape for a hotter-posture size; the eligibility / capital answers are
posture-independent and correct regardless.

**Scoped runs route only in-scope sleeves.** On a scoped run (the threaded `selectedAccountIds`
is non-empty) the PM target + `pmCurrentTickerWeightPct` are on the *selected*-account NAV, so a
sleeve owning **none of `selectedAccountIds`** is **not a routing candidate** → `not-eligible`
with an `out-of-scope` blocker (never recommended against the wrong account set's NAV, L575);
`routableToUnsleeved` likewise counts only unclaimed accounts **that are in `selectedAccountIds`**.
The leaf needs the scope explicitly because `book` is the whole book (L616). A sleeve's utilization/cap-room still spans
all its accounts (whole-book `sleeveBook`), so a partial-overlap sleeve routes with the same
documented scoped-cap over-restriction FIX-761 already carries (portfolio-mandate.md) — the safe
direction. An unscoped run (no selection) has one NAV and every sleeve is in scope.

For an add, per sleeve, deterministically, in order (first matching verdict wins) — utilization
recomputed from `book` inside the leaf (D5):
1. **Eligibility** — first, a name on the **household `exclusions`** list → `not-eligible` on
   **every** sleeve with a `household-excluded` blocker (D13a: a hard household no-add binds all
   sleeves, and its emitted target is 0 anyway). Then a sleeve whose `accountIds` resolve to **no live
   account** in `book` (all deleted) → `not-eligible` with a `no-live-account` blocker (a dollar cap
   would otherwise report the full cap deployable with nowhere to place the buy, L445). Then run the
   sleeve's OWN `assetClasses`/`excludeTickers` predicates against the frozen `candidateAssetClass`
   (`classifyInstrument(ticker).assetClass` — `equity` for a plain equity, `fixed_income` for a
   bond ETF, D12) + ticker. Fail → `not-eligible`, reasons in `blockers`.
2. **Posture** — every sleeve clamps from `pmRawTargetWeightPct` (the pre-gate PM target,
   L501). Resolve `resolveMandate(sleeve.riskAppetite)`. If it returns `null` (a stale/unknown
   id survived the save-only guard), the sleeve is **posture-blind** (D4): skip the gate, set
   `postureTargetPct = pmRawTargetWeightPct`, add `posture-unknown` to `blockers` — routes on
   eligibility + capital, no other sleeve affected. **If `rewardBuckets == null`** (a thin or
   errored forecast where `computeAndStoreRewardToRisk` cleared the figure), run the gate
   **reward-blind** — apply only its reward-*independent* clamps and **skip the reward-floor /
   capacity-veto checks entirely** (do NOT synthesize a null `RewardToRiskFigure` and pass it
   in — `computeMandateGates` dereferences fields like `rr.noDownside` and would fail closed;
   the helper takes the figure as optional / the reward checks are gated on its presence).
   This matches today's mandate-blind-on-reward run (L530/L536). Otherwise **recompute the
   reward figure with the sleeve's own `lossAversion`** — `computeRewardToRisk({ scenarios:
   rewardBuckets, lossAversion: mandate.lossAversion })` (the stored `lossAdjustedGlr` baked
   the active-run λ, L483) — and call `computeMandateGates`/`clampTargetWeight`
   (`lib/mandate-gates.ts`, D3) with the resolved mandate, that per-sleeve reward figure, and
   the confidence / override inputs → `postureTargetPct`. **`posture-blocked` is keyed on the
   *clamped result*, not on "a veto fired":** only a `postureTargetPct ≤ 0` → `verdict:
   "posture-blocked"` (`capacity-veto` in `blockers`), not recommendable, capital step skipped — a
   $0 target must never read as "has capital." A capacity veto that clamps to a **positive** cap
   (the FIX-752 packs use `capacityVetoCapPct` `0` for `conservative-income` but `0.5` / `1.0` for
   `balanced` / `aggressive-growth`, `risk-mandate.ts`) is the gate *intentionally permitting a
   small capped add — that sleeve continues to the capital step with the clamped size, NOT
   `posture-blocked` (L686). Suppressing it would drop a buy FIX-752 allows.
3. **Capital** — `capitalKnown === false` → `capital-unknown` (unpriced sleeve holdings,
   **or a `pct` cap on an incompletely-priced whole book** — a `pct` cap resolves against
   `householdNav` only when `book.navComplete`, so a missing quote *anywhere in the book*
   makes a pct-capped sleeve `capital-unknown`, never a partial-denominator number).
   **Also `capital-unknown` when `pmCurrentTickerExposureKnown === false`** — the analyzed
   ticker is held but unpriced, so the writer's priced-only `currentWeightPct` understates
   current exposure to 0 (L571); the incremental buy is then unknowable, and a $0-subtracted
   full target must never green-light a `fits-with-capital` (the "never fabricate from an
   unpriced holding" discipline — this affects every sleeve, since current exposure is a
   whole-position quantity). **And `capital-unknown` when `pmTargetNavComplete === false`** — the
   target scope has an unpriced holding, so `buildPortfolioContext`'s `totalNav` understates
   `pmTargetNav` and the `%→$` conversion undershoots the buy; a dollar-capped sleeve could then
   fabricate a `fits-with-capital` (e.g. a 5% target on a partial $100k scope reads as $5k when the
   real scoped NAV is $200k / $10k, L679) — degrade rather than dollar-compare an understated add.
   Otherwise convert `postureTargetPct` to dollars against
   **`pmTargetNav`** — the NAV the
   PM target is a fraction of (the scoped NAV on a scoped run, **not** `householdNav`, else
   the dollars are overstated by the household/scoped ratio and the sleeve is wrongly
   `fits-no-capital`, L516) — subtract the analyzed ticker's current exposure **on that same
   scope**: the PM's own whole-position `pmCurrentTickerWeightPct` (the FIX-728 echo the writer
   already computes from the same snapshot the target is measured against, `writer.ts:176–197`)
   converted against `pmTargetNav`, so the check is the **incremental** buy (D11). Two failure
   modes this avoids: subtracting only *this sleeve's* slice overstates the buy when the name is
   already held in another in-scope sleeve — `portfolioFit.targetWeightPct` is a whole-position
   target against total current weight, so a book already at a 5% target in sleeve A must not
   read as a full fresh 5% buy in sleeve B (L593); and subtracting **whole-book** exposure
   against a **scoped** target lets a holding in an *unselected* account wrongly mark a scoped
   add `already-at-target` (L612). Using the PM's own scoped current weight keeps target and
   exposure on one NAV scope (on an unscoped run that scope *is* the whole book). Compare the
   incremental to `availableToDeploy` → `fits-with-capital` / `fits-no-capital` (`at-cap` in
   `blockers`). A **non-positive incremental buy** (≤ 0 — the position's current exposure already
   meets *this sleeve's* posture-clamped target, even though the run itself is an add) →
   `verdict: "already-at-target"` (non-actionable, not recommendable), never coerced to `fits-*`
   (L595). The verdict stays per-sleeve because `postureTargetPct` differs by pack — a conservative
   sleeve can be `already-at-target` on exposure an aggressive sleeve would still add to. This
   per-sleeve `already-at-target` **replaces** the old whole-run "non-positive incremental → null"
   filter (D13): the whole-run add gate is now just `finalRating` being Buy-family, and whether a
   given sleeve actually adds is its own posture target vs current exposure.

`recommendedSleeveId` = the first (mandate-order) sleeve with `verdict ===
"fits-with-capital"` (posture-blocked / capital-unknown / not-eligible sleeves are never
recommendable).

**`routableToUnsleeved`** = `true` when the **unsleeved pool** can hold the name:
at least one account is unclaimed by any sleeve, **and** the name is not in the threaded
`householdExclusions`, **and the committed household add is provably a known, sizeable amount** —
i.e. **none of the capital-unknown degradation conditions that block a sleeve also apply to the
unsleeved pool.** The invariant (rather than an enumerated flag list): the unsleeved pool *is* the
household decision, so it can only "fit the general book" when that decision provably adds. In
practice that means `householdHasAddRoom` — derived EXACTLY as `gate.householdWeightKnown &&
!gate.excluded && gate.targetWeightPct > householdWeightPct` (the post-policy committed target
clears the current household weight with the cap evaluated), NOT read off the `policyVerdict` enum,
since `capped` alone can't tell a cap>household add-with-room from a cap≤household clamp-to-current
(Greptile P1/L676) — **and** the add is sizeable — no `pmCurrentTickerExposureKnown === false`
(unpriced held ticker, L722) and no `pmTargetNavComplete === false` (partially-priced target scope
understates `pmTargetNav`, L733). Any of those → `routableToUnsleeved: false`, since a positive
committed target is not proof of a knowable add. This deliberately mirrors the per-sleeve
`capital-unknown` degradation so the fallback is never *more* optimistic than the sleeves it backs. The unsleeved pool is **not** re-gated per-sleeve — it is governed
by the household mandate + posture that already produced the committed PM decision, so its
"outcome" *is* the household `portfolioFit`/`policyDecision`/`mandateDecision` the run
already emits (no sleeve eligibility, cap, or capital check applies to it). The flag is the
honest fallback signal PmHero uses when no declared sleeve is `fits-with-capital` (e.g. all
`not-eligible`): "fits the general book" vs. "fits no declared sleeve and there is no
unsleeved room." `routableToUnsleeved` is therefore only meaningful when at least one sleeve is
defined. **With no sleeves defined at all, `computeSleeveRouting` returns `null` outright** (the
whole-run skip below) — *not* a `{ fits: [], routableToUnsleeved: true }` object — so the
default-mandate run keeps its exact pre-FIX-771 memo/snapshot/RunSummary shape (L681).

**Surfacing (no resource, no tap — D1).** The derived `sleeveRouting` mirrors onto the
PM memo (`policyDecision`/`mandateDecision` precedent — PmHero reads one place), the
decision snapshot, and `RunSummary` (+ `runArtifacts` for eval). The three
`decisionSnapshot` mirrors (`mandateDecision`, `policyDecision`, `sleeveRouting`) go
through a shared `mirrorNullable(obj, keys)` helper (D9) rather than a third
field-by-field `?? null` hand-copy.

**Destination reconciliation — the recommended sleeve wins over the LLM's `suggestedAccount`.**
The PM LLM already emits `portfolioFit.suggestedAccount` (an account *label*, validated by the
writer against real accounts, rendered by PmHero + the summary block). When
`recommendedSleeveId` is non-null it is the **authoritative destination** (the deterministic-gate-
over-LLM spine). Because `suggestedAccount` is an account **label** while `SleeveFit.accountIds`
are **ids**, the writer first **maps the label to its id** via the same account list it already
validates against (a raw `label ∈ accountIds` check would never match — `Roth IRA` vs `acc-roth`,
L749). Account labels are **not unique** (`accountStateSchema.name` / `app.accounts.name` have no
unique index), so a label matching **more than one** live account id is **ambiguous** — the writer
does not guess; it falls back to the sleeve/pool destination (the deterministic anchor) rather than
picking an arbitrary id (L765). It then reconciles: if the (unique) mapped id is one of the recommended sleeve's `accountIds`,
`suggestedAccount` stands as the specific destination within the sleeve; if it is **not** owned by
the recommended sleeve, the sleeve wins and PmHero shows the sleeve destination (its `label`),
**not** two conflicting accounts (L558).

The **unsleeved fallback** reconciles too (L754): when no sleeve is recommended but
`routableToUnsleeved` is true, the destination is the *unsleeved pool*, so `suggestedAccount` may
only stand if its mapped id is an **unclaimed** account (owned by no sleeve); if it maps to an
account owned by a (rejected) sleeve, the unsleeved pool wins and PmHero does not render that
sleeve-owned account beside "fits the general book." The `SleeveRouting` echo therefore also
carries the **unclaimed in-scope account ids** the writer already computes, so PmHero has one
coherent destination in the fallback. With **no sleeves at all** / null routing, `suggestedAccount`
renders exactly as today.

### 4.5 Funding list (Slice C) — narrow

When a sleeve is `fits-no-capital`, `computeSleeveRouting` fills that `SleeveFit.funding`
with **structured `FundingEntry` records** — the sleeve's incumbents from the frozen `book`
(the sleeve's accounts' held positions, **excluding the analyzed ticker itself** — you don't
trim `NVDA` to fund an `NVDA` add, L625), each carrying `{ ticker, marketValue, hasThesis,
thesisUpdatedAt }` from `book` + `thesisPresenceIndex`, ordered **no-thesis-first, then
oldest-thesis** (the list is "weakest incumbents to consider trimming", and an undocumented
holding — `hasThesis: false` — is the weakest, so it surfaces before any thesis-backed name;
within thesis-backed names, oldest `thesisUpdatedAt` first — L594); an empty sleeve yields
`[]` ("nothing to trim"). The entries are echoed onto the memo /
RunSummary (not reduced to bare tickers) so PmHero can render "no thesis on file" / the
staleness context and a reader can audit why the order was chosen (L469).
**No numeric `convictionProxy`, no `marginPp`, no `cleared` boolean** (D8). The PmHero
renders it as "to fund this, consider trimming: X, Y (Z has no thesis on file)" — a
legible funding list, or "this sleeve holds nothing to trim" when empty. It is a
**suggestion list, never an auto-executed trade or a scored recommendation** (the
desk's real-money honesty gate). The scored/ranked displacement — which incumbent's
edge is actually weakest — is the **FIX-763 upgrade**, when real thesis-health data
exists to rank on.

### 4.6 Household Health view (Slice A)

`health-section.tsx` gains a **Sleeves panel** reading `summarizeSleeveUtilization`
client-side (`useMemo` + pure leaf, BP-010): per-sleeve label, deployed / cap /
available, a utilization bar, cash (informational), and a coverage/`capitalKnown` note.
Zero new route. Capless sleeves show "no cap (accounts' NAV)". A sleeve with
`liveAccountCount === 0` renders as "no live account" with `availableToDeploy` 0 — never
"full cap free" (L464). The unsleeved pool is a residual row so the panel reconciles to
household NAV.

### 4.7 Error handling & real-money discipline

- **Unpriced holdings / unresolvable pct cap / held-but-unpriced analyzed ticker** →
  `verdict: "capital-unknown"` (never coerced to buyable or capped — D2/BP-020). The last case
  (`pmCurrentTickerExposureKnown === false`) is whole-position, so it degrades *every* sleeve.
- **Stale/unknown `riskAppetite` on a sleeve** → posture-blind for that sleeve
  (save-only guard, D4); other sleeves + the IPS unaffected.
- **A sleeve naming a *since-deleted* account** → that account contributes zero utilization;
  not an error. But a sleeve whose accounts are **all** deleted (no live destination) is
  **non-routable** → `verdict: "not-eligible"` with a `no-live-account` blocker, never
  recommendable: a dollar cap would otherwise show the full cap as `availableToDeploy`
  (`deployedValue = 0`) and route a buy to a sleeve with nowhere to place it (L445).
- **No sleeves** → `sleeveRouting` null on memo/snapshot/RunSummary; `<sleeves>`
  suppressed; the run behaves exactly as pre-FIX-771.
- **Not a buy candidate** (`finalRating` is `Hold` / `Underweight` / `Sell` — tier ≤ 2) →
  `sleeveRouting` and `recommendedSleeveId` null; nothing is surfaced for a name the desk doesn't
  rate a buy (D13). The gate is the **rating**, not the mandate-shaped `action`: a Buy-rated name the
  run's own posture held to `action: "hold"` (rules 11–12) still routes, so a different sleeve's
  posture can see it (Codex P1, L166). A partially-priced target scope (`pmTargetNavComplete ===
  false`) never *drops* the table on a Buy — every sleeve degrades to `capital-unknown` instead
  (L146). Whether a given sleeve adds is its own concern: on a routed Buy, a single sleeve whose
  posture-clamped target ≤ the position's current exposure emits that sleeve's `already-at-target`
  verdict while **other** sleeves with a higher posture target still route — the fit table is not
  dropped (L687).
- **Routing never touches `finalRating`** and never inflates size — downward-only,
  the FIX-715/752/761 orthogonality invariant.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| No sleeves defined | Unchanged pre-FIX-771 run; `sleeveRouting` null, `<sleeves>` suppressed |
| Account claimed by two sleeves | Rejected at save (single-owner invariant); editor blocks it |
| Sleeve cap < current deployed value | `utilizationPct > 100`, `availableToDeploy = 0`, `fits-no-capital`; UI over-cap flag (never force-trims) |
| Analyzed name eligible for no sleeve | All `not-eligible`; `routableToUnsleeved` decides; PmHero "fits no declared sleeve" |
| No sleeve fits + household cap `unenforced` (unpriced held ticker) | `routableToUnsleeved: false` — the cap couldn't be evaluated, so "fits the general book" isn't provable (L716) |
| Analyzed bond ETF (`BND`/`AGG`/`TLT`) | `candidateAssetClass = fixed_income` (curated `classifyInstrument`, or the book's class if held); eligible for a `fixed_income` sleeve, `not-eligible` for an equity-only sleeve (D12) |
| Add to an already-held **off-list** bond ETF / MMF | Uses the book's authoritative `assetClass` (`fixed_income`/`cash`), not symbol inference — a matching sleeve isn't wrongly `not-eligible` (L542) |
| LLM `suggestedAccount` label matches two live accounts | Ambiguous → writer falls back to the sleeve/pool destination, doesn't guess an id (L765) |
| Fitting sleeve has capital | `fits-with-capital`; `recommendedSleeveId` set; no funding list |
| Fitting sleeve at cap | `fits-no-capital`; funding = incumbent list, no-thesis-first (or "nothing to trim") |
| `finalRating` is Hold / Underweight / Sell (not a buy candidate) | `sleeveRouting` + `recommendedSleeveId` null — the gate is the rating, not `action` (D13) |
| Buy-rated name the run's posture held to `action: "hold"` (rules 11–12) | still routes — `finalRating` is mandate-orthogonal, so other-posture sleeves are evaluated; size is downward-only from the token (D3a/J3) (D13/L166) |
| Buy-rated name on the **household exclusion** list (even if asset-class-eligible for a sleeve) | `not-eligible` on **every** sleeve (`household-excluded` blocker), `routableToUnsleeved` false, no recommendation — a hard household no-add binds all sleeves; not routed around (D13a, Codex P1/L644) |
| Routed Buy, but the ticker's current exposure (on the PM-target scope) already meets a sleeve's posture target | that sleeve → `already-at-target` (incremental buy ≤ 0 vs the PM's `pmCurrentTickerWeightPct`; non-actionable, not recommendable); other sleeves with a higher posture target still route |
| Adding to a held name in an at-cap sleeve | funding list excludes the analyzed ticker itself (no "trim NVDA to fund NVDA") |
| Unpriced sleeve holding | `capital-unknown`; never buyable/funding-needed |
| Analyzed ticker held but unpriced | `pmCurrentTickerExposureKnown false` → `capital-unknown` for every sleeve (priced-only `currentWeightPct` would understate the incremental to a full buy) |
| Another holding in the target scope is unpriced | `pmTargetNavComplete false` → routing still runs (a Buy-rated name isn't nulled on an overstated current weight, L146); every sleeve → `capital-unknown` (understated `pmTargetNav` would shrink the `%→$` add and fabricate a dollar-cap fit, L679) |
| Unsleeved fallback + LLM `suggestedAccount` owned by a rejected sleeve | Unsleeved pool wins; PmHero shows the unclaimed-account destination, not the rejected sleeve's account (L754) |
| `pct` cap + a missing quote anywhere in the whole book | `capital-unknown` (cap can't resolve against a partial NAV), even if the missing name is in another sleeve |
| Posture clamp to ≤ 0 (e.g. `conservative-income` capacity veto to 0) | `posture-blocked`; not recommendable; capital step skipped (a $0 target never reads as "has capital") |
| Capacity veto that clamps to a positive cap (`balanced` 0.5% / `aggressive-growth` 1.0%) | NOT blocked — continues to capital with the clamped small size (the add FIX-752 permits, L686) |
| Sleeve names a since-deleted account (some live) | That account contributes zero utilization; not an error |
| Sleeve's accounts are all deleted (no live destination) | `not-eligible` + `no-live-account` blocker; never recommendable (a dollar cap would otherwise show full room) |
| Unknown / stale `riskAppetite` id on a sleeve | Posture-blind for that sleeve (`posture-unknown` blocker; routes on eligibility + capital); others + IPS unaffected |
| Scoped run (`selectedAccountIds`) | Utilization/cap-room from the whole-book read; incremental subtracts the scoped `pmCurrentTickerWeightPct` (one scope, no unselected-account `already-at-target` fake); a sleeve owning **no selected account** → `not-eligible` (`out-of-scope`), never recommended against the wrong NAV (L575) |
| Sleeve with `accountIds: ["A","A"]` | Normalized (deduped) at the save write path — not rejected; A's holdings/cash counted once (L440/L452) |
| LLM `suggestedAccount` not owned by the recommended sleeve | Recommended sleeve is authoritative; PmHero shows the sleeve destination, not two conflicting accounts (L558). Compared by mapping the label → id first (L749) |

**Error taxonomy:** all sleeve routing is deterministic and non-throwing at read/seed
(business-invalid → degrade, never throw — the mandate precedent); the only throwing
boundary is `savePortfolioMandate` re-validating sleeves + the appetite guard at the
trust boundary.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (Feature label) — tracer-bullet cycles per behavior.

**Goal (observable outcome):** With two sleeves declared — a defensive core and a
capped opportunistic sleeve — analyzing a name the core excludes but the opportunistic
sleeve permits produces a decision whose per-sleeve routing reports **"fits the
opportunistic sleeve, not the core"**, with a real capital-availability answer, and —
when that sleeve is at its cap — lists the incumbents to consider selling.

**Goal check (deterministic + fixture smoke, non-CI — D10):** Routing is pure
projection math, so its correctness is proven by the `computeSleeveRouting` vitest
suite **with a mandate-swap fixture** (swap the two sleeves' eligibility and require
the recommendation to follow the rules, not a fixed sleeve id — a hollow pass that
always returns the same sleeve fails). The end-to-end proof is a **fixture-mode `fsdev
run`** of `analysis analyze` on a held-out ticker followed by `analysis runSummary`,
asserting the `sleeveRouting` echo is populated and internally consistent (the
`goals/trading-desk-headless/fixture-run-clean` two-step). **No real-model goal check
applies** — there is no non-deterministic outcome for a real model to exercise beyond
the decision the existing goal checks already cover.

**Behaviours to test (vitest, mocked/deterministic — one per tracer cycle):**
- Sleeve validation: single-owner rejection; cap bounds; intra-sleeve `accountIds` are

  `savePortfolioMandate` **rejects** a save whose sleeve `riskAppetite` is an unknown pack id

- `computeSleeveRouting`: **gated on `finalRating`, not the action** — a non-Buy-family rating
  (Hold/Underweight/Sell) → null routing (D13); a **Buy-family rating (Overweight/Buy) whose
  `action` the run's mandate/policy shaped to `hold`** still routes (the Codex-P1 case, L166: rules
  11–12 emit `hold` directly, so the action can't be the gate); a **per-sleeve** non-positive
  incremental is NOT a whole-run skip — it yields that one sleeve's `already-at-target` while other
  sleeves still route (L918). A name on the **household `exclusions`** list is `not-eligible` on
  **every** sleeve (`household-excluded` blocker) AND blocks `routableToUnsleeved` — an unheld
  excluded Buy that would be asset-class-eligible for a declared sleeve is NOT routed there (D13a: the
  hard household no-add binds all sleeves, and rule 12 sizes its target to 0 so a fit isn't
  deliverable, Codex P1/L644); a sleeve's OWN `excludeTickers` still apply on top;
  eligibility otherwise runs on the frozen `candidateAssetClass` — **held-book-first**
  (D12/L542): an **already-held** bond ETF classes `fixed_income` from the book row (eligible for a
  `[fixed_income, cash]` core, excluded from an equity sleeve), an unheld candidate falls back to
  `classifyInstrument`, and a name **held in two accounts with disagreeing `assetClass`** falls back
  to `classifyInstrument` (the conflicted book isn't authoritative — never arbitrarily picks one
  row, I3/L560); agreeing multi-account rows honor the book class;
  posture re-clamp differs by pack (`conservative-income` vs `aggressive-growth`) and clamps
  from the **raw pre-gate target**; the **reward figure is recomputed per sleeve λ**; a stale
  appetite → `posture-unknown` (routes, doesn't crash); a posture clamp to **≤ 0** → `posture-blocked`
  **but a veto that clamps to a positive cap** (`balanced` 0.5 / `aggressive-growth` 1.0) continues
  to capital with the clamped size (L686);
  a **scoped run sizes against `pmTargetNav`** and marks a sleeve owning **no selected account**
  `not-eligible` (`out-of-scope`, never recommended against the wrong NAV, L575); a **null `rewardBuckets`** run gates reward-blind
  (no fabricated veto, no crash); `pct` cap + incomplete NAV → `capital-unknown`; a **held-but-unpriced
  analyzed ticker** (`pmCurrentTickerExposureKnown false`) → `capital-unknown` for every sleeve, never
  a fabricated `fits-with-capital` from an understated-0 exposure (L571); a **partially-priced target
  scope** (`pmTargetNavComplete false`) → `capital-unknown` (understated `pmTargetNav` would shrink the
  dollar add, L679); an **all-deleted
  sleeve** → `not-eligible` (`no-live-account`, never recommended even with a dollar cap, L445);
  the **incremental buy subtracts the PM's scoped current weight** (`pmCurrentTickerWeightPct`) —
  a name already at target in sleeve A does not read as a full fresh buy in sleeve B (L593), **and
  on a scoped run a holding in an unselected account does not fake `already-at-target`** (L612);
  when the position's current exposure already meets a sleeve's posture target that sleeve →
  `already-at-target` (per-sleeve; other sleeves still route; not coerced to `fits-*`, L595);
  `fits-*`; `recommendedSleeveId` order (skips posture-blocked/already-at-target/unknown/not-eligible);
  `routableToUnsleeved` (false when the name is in `householdExclusions`, **or** any capital-unknown
  degradation applies to the household add — cap full/`unenforced` (`householdHasAddRoom` false),
  unpriced held ticker (`pmCurrentTickerExposureKnown` false), **or** partially-priced target scope
  (`pmTargetNavComplete` false, L733)); **`householdHasAddRoom` derivation** distinguishes a
  `capped` cap>household add (target clamped to cap **above** the current weight → **true**) from a
  `capped` cap≤household clamp-to-current (target clamped down to the household weight → **false**),
  and a within-policy hold-at-current (target ≤ household → false) from a within-policy add
  (target > household → true) — the `policyVerdict` enum alone cannot (Greptile P1/L676); so the
  fallback is never more optimistic than the sleeves,
  L694/L716/L722; true only when an unclaimed in-scope account exists, the name isn't excluded, and
  the household decision provably adds a **known**-size amount).
- PM commit (`phase-5-sleeve-routing.spec.ts`): per-sleeve table + `recommendedSleeveId`
  on memo + snapshot + RunSummary; null when no sleeves; `finalRating` unchanged;
  `mirrorNullable` parity with the prior hand-copy; **destination reconciliation** — the LLM's
  `suggestedAccount` LABEL is mapped to its id before the membership check (a `Roth IRA`
  suggestion matches sleeve id `acc-roth`, L749); when it isn't owned by the recommended sleeve
  the sleeve wins (L558); **in the unsleeved fallback** it stands only if it maps to an
  **unclaimed** account, else the unsleeved pool wins (no rejected-sleeve account beside "fits the
  general book", L754).
- Funding list: structured `FundingEntry` records (ticker + marketValue + hasThesis +
  thesisUpdatedAt); **excludes the analyzed ticker** (no self-trim, L625); **no-thesis-first,
  then oldest-thesis** (a no-thesis holding precedes a dated-thesis one); empty sleeve → `[]`;
  no numeric score.
- Seed + gate: sleeves ride the frozen mandate; the whole-book `state.sleeveBook` + presence
  index are frozen at seed; `state.candidateAssetClass` is frozen at the `checkAssetTypeSupported`
  step from `classifyInstrument(ticker).assetClass` (a bond ETF → `fixed_income`, D12);
  `<sleeves>` suppressed when empty.

## 8. Non-Goals

- **Intra-account virtual partitions** — a sleeve owning *part* of a mixed account.
  Needs per-holding tagging + cash attribution; deferred (§3.4-3). v1 sleeves own whole
  accounts.
- **Per-sleeve cash sub-ledger / shadow accounting** — availability is arithmetic
  cap-room, not a running per-sleeve balance (the Smartleaf pitfall).
- **Scored / ranked displacement** — v1 lists incumbents; the numeric conviction score
  + hysteresis is the **FIX-763** upgrade (D8).
- **Per-sleeve theses** — thesis records stay household × ticker (FIX-760's deferral to
  this issue is satisfied by routing + the funding list, not per-sleeve theses).
- **Per-sleeve appetite *re-sizing* (D3a)** — a sleeve's posture **re-clamps the run's PM
  target downward**, it does not size the name UP to a more-aggressive sleeve's own appetite.
  The PM already sizes `pmRawTargetWeightPct` toward the **active run**'s mandate (prompt rules
  11–12), and all sleeve clamps are downward-only, so an aggressive sleeve cannot exceed the
  run-mandate-sized target within a single run. The escape is the existing FIX-752 run-override:
  re-run under the aggressive sleeve's appetite to size to it. Fit / capital / funding are
  posture-independent, so one run still routes correctly across every sleeve; only the *size*
  a name would take **in** an aggressive sleeve needs the re-run. Collapsing posture into a
  per-sleeve re-size (one run, N appetite-shaped targets) needs the PM to emit an appetite-neutral
  base size the router re-shapes per sleeve — a decision-tier change deferred past v1.
- **Sleeve eligibility beyond asset-class + exclusions** — `sectors` /
  `includeOnlyTickers` deferred (D7).
- **Per-sleeve override of a household exclusion (true multi-strategy)** — v1 treats a household
  `exclusions` entry as a hard floor that binds every sleeve (D13a): a name the household excludes is
  `not-eligible` everywhere, never routed around to an "allowed" sleeve. Letting a specialized sleeve
  hold a household-default-excluded name would need both a per-sleeve override flag AND a **pre-policy
  base size** for the router to re-shape (the same decision-tier change D3a defers) — since the PM
  already sizes an excluded name's target to 0, there is no base size to route on today. Deferred.
- **Routing a candidate the analysis pipeline can't yet analyze** — a bare bond, an OCC
  option, or a crypto pair is stopped by `checkAssetTypeSupported` (FIX-773) before commit, so
  a sleeve targeting those classes acts as an exclusion axis only until FIX-777 lifts the stop.
  (A bond *ETF* like `BND` is an exception: it passes the gate and routes correctly as
  `fixed_income` today — D12.)
- **Risk-budget caps** — v1 caps capital (dollars/percent), not risk contribution. The
  honesty caveat: a dollar cap understates a small options sleeve's risk; the v2 upgrade
  is a max-loss/notional cap.
- **Rebalancing execution / sell-to-rebalance** — the desk analyzes one name at a time.
- **Options-trade translation** for an aggressive options sleeve — that is **FIX-706**;
  sleeves route and size, they don't translate to a contract.
- **Soft/tolerance-band caps** — v1 caps are hard.
- **Deepening opportunity (accurate scope, per maintainer review):** the FIX-752 and
  FIX-761 clamps are **already extracted** into unit-tested `lib/mandate-gates.ts` and
  `lib/policy-gate.ts`; only the FIX-728 echo (`currentWeightPct`/`weightDeltaPct`,
  ~20 lines at `writer.ts:176–197`) is inline, and it is an echo, not a clamp. This
  spec extracts nothing further there; the one duplication it *does* remove is the
  `decisionSnapshot` field-by-field mirror (via `mirrorNullable`, D9). A fuller
  echo/clamp consolidation is a separate `fsd:improve-codebase-architecture` follow-up,
  correctly *not* bundled here.
