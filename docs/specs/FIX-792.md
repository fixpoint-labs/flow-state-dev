# FIX-792: Trading-desk per-run cost and token accounting + batch budget caps — Implementation Spec

> **Epic:** [FIX-938 — AI evaluation & self-improvement loop](https://linear.app/fixpoint-labs/issue/FIX-938) · epic PR [#898](https://github.com/fixpoint-labs/flow-state-dev/pull/898). This issue is the **loop spine's** first buildable step (FIX-791 in review → **FIX-792** → FIX-794). Per the epic §2c, FIX-792 landing whole-command accounting is a **hard prerequisite** for FIX-794's unattended spend.

## Part I — The Case

### 1. Problem — why it matters, why now

A full analysis run fires 20-plus model calls — nine analysts, a bull/bear debate, four lenses, three risk personas, a scenario forecaster, the PM, a thesis validator, plus each agent's "approach" preamble — and nobody can say what it cost. Today only the LLM-**judge** calls (the scoring layer) are metered and budgeted; the analysis pipeline itself runs unmetered. For an unattended improvement loop that is disqualifying in both directions: a batch can silently overspend, and a prompt change that doubles token use is invisible to the regression scorecard.

**Why now.** This is the prerequisite the epic named for FIX-794: an autonomous campaign that "spends at most $15 or eight experiments" cannot exist until the whole command is accounted and capped. There is no workaround — the shipped `--max-cost-usd` flag bounds judge calls only; the expensive part (the `analyze` fan-out) is uncapped.

### 2. Solution in plain terms

The framework already records token usage for every generator call (each one emits a `block_trace.modelUsage` with input/output/total and cache tokens) and already ships a model-pricing table. So we don't build a metering system — we **consume what exists**: sum the usage across a run's calls, price it against the existing table, and write one whole-run cost figure onto the same JSONL scoreboard line FIX-791 and FIX-794 already read. Then we make `--max-cost-usd` a **whole-command** ceiling that also covers the analysis calls, checked *between* runs so the batch stops cleanly and marks the rest `skipped-for-budget` rather than aborting mid-run. When usage is genuinely missing, the run says "cost unavailable" — never a misleading $0.

**The philosophy that led here.** Tenet 2 (*refine the substrate, don't grow it*): the usage seam, the pricing table, and a `block_trace.modelUsage` reducer already exist — the right move is to consume and **consolidate** them, not add a parallel path. Tenet 3 (*subtraction is part of the change*): fold the judge-only budget into one whole-command budget instead of standing up a second budget system, and collapse the duplicate pricing tables toward one. BP-030 governs the record change (additive, nullable, old readers still parse).

### 3. Tradeoffs & alternatives

- **Where cost is computed — the main fork.** Option A: wire a `costEstimator` into the desk flow and read the framework's live `ctx.request.costEstimate` rollup. Option B: sum `block_trace.modelUsage` off the `analyze` execution `items` the eval runner **already preserves** (`runtime.ts` literally carries them with the comment *"Preserved for whole-run cost accounting in FIX-792"*). **We take B.** It reuses the exact read pattern the judge-cost path already uses, keeps cost in the eval layer where FIX-791 consumes it, and adds no flow-level surface; A is heavier and still depends on the same underlying (observability-gated) usage.
- **The simpler approach considered.** Just call the existing `estimateJudgeCost` / `sumCostFromItems` reducers as-is. Insufficient alone: they're judge-/testing-scoped, there are already 3-4 near-duplicate copies, and neither touches the batch budget rework. The 80/20 win is *one* shared reducer + the *core* pricing table, then the budget gate — not a fifth copy.
- **Where the genuine complexity is.** Not the summation (a fold over items). It's two things: (1) the **batch budget gate** — `sweep`'s Phase A runs tuples through a parallel `mapLimit` fan-out with no budget check, so a clean "stop before the next run" gate means reworking that control flow and accepting bounded (≤ one concurrency-wave) overshoot; and (2) **fail-closed honesty** — provider `usage` is `undefined`-typed and missing in practice (Gateway bugs, provider gaps), and the whole `block_trace` stream is gated behind trace-observability which is **off in production by default**, so "unknown cost" must never render as "$0/free".

### 4. Focus practices (1–5)

1. **Tenet 2 — reuse, don't fork.** One shared cost reducer over `block_trace.modelUsage`, priced by the core `DEFAULT_MODEL_LOOKUP` / `modelPricingEstimator` — *not* a fifth desk-local pricing table. This change should shrink the four-tables/two-reducers surface, not grow it.
2. **BP-030 — additive, nullable record evolution.** New cost fields land nullable on `qualityRecordSchema` so `evalVersion: 1` readers keep parsing; dual-read the AI SDK v4/v5 usage names (`promptTokens`↔`inputTokens`).
3. **BP-035 — the null/second path is the main path.** `undefined` usage and unknown-model aren't edge cases here: unpriced calls are excluded from the total and *counted*, never coerced to 0; the budget's "unknown" state fails *toward* the cap.
4. **BP-020 — degrade honestly.** With trace-observability off (prod default) and no usage present, surface "cost unavailable", not $0.
5. **BP-003 — evidence.** A real `sweep` goal check: a completed run yields a non-null `runCost`, and a low `--max-cost-usd` stops the batch with remaining runs marked skipped.

### 5. What using it looks like

No API is added for end users — this is CLI + scoreboard-record surface. The observable change:

```bash
# Before: cost on the scoreboard reflects judge calls only; analyze is unmetered.
pnpm eval sweep --manifest manifest.json

# After: each scoreboard line carries whole-run cost; the cap covers analyze + judges.
pnpm eval sweep --manifest manifest.json --max-cost-usd 5
```

```jsonc
// scoreboard.jsonl — completed run (AFTER): new nullable `runCost`, additive to evalVersion 1
{ "evalVersion": 1, "sessionId": "sweep_NVDA_0_…", "runStatus": "completed",
  "finalRating": "overweight", "judges": [ /* … unchanged … */ ],
  "runCost": {
    "totalUsd": 0.42,
    "tokens": { "input": 91240, "output": 8130, "total": 99370 },
    "byModel": { "anthropic/claude-…": 0.42 },
    "unpricedCalls": 0, "missingUsageCalls": 0
  } }
```

```jsonc
// scoreboard.jsonl — a run the budget stopped before it started
{ "evalVersion": 1, "sessionId": "sweep_TSLA_7_…", "runStatus": "skipped_budget",
  "runCost": null,
  "warnings": ["skipped: --max-cost-usd $5.00 exhausted (spent $5.13 after 7 runs)"] }
```

```jsonc
// a completed run where a provider returned no usage — honest, not $0
{ "evalVersion": 1, "sessionId": "sweep_AMD_3_…", "runStatus": "completed",
  "runCost": { "totalUsd": null, "tokens": { "input": null, "output": null, "total": null },

```

### 6. Decisions & rules — the sign-off surface

1. **Cost is computed in the eval runner by summing `block_trace.modelUsage` off the preserved `analyze` items.** *Rejected:* wiring a flow `costEstimator` to read `ctx.request.costEstimate`. *Locks in:* cost lives in the eval layer where FIX-791/794 consume it; the runner stays the single funnel; no new flow surface. No framework change is required (the usage seam already exists).
2. **v1 scope = cost on the eval scoreboard record (`QualityRecord`) only.** *Rejected for v1:* persisting cost onto the stored session / `RunSummary` / in-app Past Reports. *Locks in:* the loop and FIX-791 get everything they need now; surfacing cost on the in-app report is a follow-up (§12) gated on the prod trace-observability question, because `buildRunSummary` reads persisted session state and usage is execution-trace, not persisted state. **← the one deliberate scope cut vs. the issue's wording; sign off or push back here.**
3. **Reuse the core pricing table + one shared item-reducer; re-point the desk judge-cost path at it.** *Rejected:* a fifth desk pricing table / a third `sumCostFromItems` copy. *Locks in:* consolidation of four tables / two reducers toward one shared surface (tenet 2/3).
4. **New record fields are additive + nullable; `evalVersion` stays `1`.** *Rejected:* bumping to `2`. *Locks in:* old readers keep parsing (BP-030); error/skipped records carry `runCost: null`.
5. **Fail closed on missing usage / unknown model.** Unpriced calls are excluded from the numeric total and counted; a run with any unpriced/missing call reports honestly (partial or null), never $0. Budget "unknown" charges a worst-case estimate toward the cap or halts — never treated as free. *Rejected:* coercing missing usage to 0.
6. **`--max-cost-usd` becomes a whole-command budget covering analyze + judges**, via one shared budget object generalizing `JudgeBudget` / `createJudgeBudget`. *Rejected:* a second analyze-only budget. *Locks in:* one number, debited across the whole command.
7. **The batch cap is checked between runs in `sweep` Phase A; over-budget tuples are emitted as `skipped_budget` records, never a mid-run abort.** *Rejected:* mid-call cancellation. *Locks in:* bounded (≤ one concurrency-wave) overshoot, documented; a complete, auditable scoreboard.

**Non-goals:** data-provider (non-LLM) rate-limit budgeting (FIX-675); org-level billing/quota; persisting cost to the session / in-app report (v2 — §12); revising the pricing numbers themselves.

**Size estimate:** **Medium** — single package (`labs/trading-desk`) plus consolidation onto a shared reducer; the `sweep` budget-gate control-flow rework is the one non-mechanical part. Single PR, no sub-PR DAG.
