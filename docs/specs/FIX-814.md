# FIX-814: Resume for generator and router primitives — continuation beyond the sequencer — Implementation Spec

## 1. TLDR

Extend durable suspend/resume from the sequencer to the **generator** (suspend mid tool-loop, canonically for tool-call approval) and **router** (resume post-decision) primitives, reusing FIX-811's `ReplayLog` / single-request continuation rather than a bespoke path per kind.

**Router:**
- **Route the router's selected child through the replay seam.** Today the router runs its chosen branch via `asRuntime(selected).run(...)` directly (`packages/core/src/blocks/router.ts:237`), bypassing the `_replayLog` check that lives only in `sequencer.ts`'s `executeBlock`. So a suspension *inside a chosen branch* does not memoize completed descendants on resume — they re-run. Route the selected child through `executeBlock` (or an equivalent replay check at the dispatch site) so the branch participates in FIX-811 memoization.
- **Re-run `execute` and validate against the recorded `router_decision`** on resume (not skip `execute`): re-running preserves the per-call route wrapper a router may return (`route.connectInput(...)`), while validating the selection against the recorded `selectedRoute` keeps the branch stable — a mismatch is fatal. The decision is already persisted (a non-transient `router_decision` trace item via `onRouteSelected`, `createExecutionContext.ts:2163`). Suspendable routers must have unique route names (or a persisted index) since `router_decision` records a bare name.

**Generator:**
- **Invert tool-loop ownership** across `packages/core/src/blocks/generator.ts` **and the `GeneratorModel` contract** (`packages/core/src/types/model.ts:204`, today exposing only `maxSteps`): FSD drives the multi-step loop one model step at a time, reading each step's assistant turn from `GeneratorStepResult` (`text`/`toolCalls`/`toolResults`), instead of delegating multi-step iteration to the SDK via `maxSteps`. Behavior-preserving refactor first. This widens an architecture-doc contract, not just one file.
- **Propagate `ctx.suspend()` from inside a generator tool** (today the SDK swallows tool `execute` throws): with FSD owning the loop, a tool's `SuspensionError` reaches the loop and re-throws to `runAction`. Also make the tool-executor's own `runWithRetry` (`tool-executor.ts:345`) bail on `SuspensionError` — it currently retries any error when `retryableErrors` is undefined, which would retry the suspension before it surfaces.
- **Reconstruct the conversation from the *persistent* item-log on resume** via a **shared, visibility-agnostic** item/step→message conversion factored into `core`/`contracts` (the same low-level mapping `engine`'s `itemToLLMMessages` wraps with a history gate — which the resume path must NOT use, or `history:false` generators lose their turns). Source is the persistent `tool_output` item; `tool_call_progress` is transient and must not be the source. The suspended tool's `tool_output{status:"failed"}` marks the pending gate: on resume the tool **re-enters**, `ctx.suspend()` returns the human payload, and the tool runs to emit its **real** result (the payload is not the tool output).

**Docs:** one new Advanced page (`generator-and-router-suspend-resume`), plus extensions to `durable-execution`, `block-memoization-and-replay`, the `human-in-the-loop` guide, and the generator/router algorithm descriptions in `docs/architecture/execution-and-errors.md`.

**Size: Large** — split as: (PR1) router replay-seam routing + decision-replay; (PR2) generator loop-ownership refactor (incl. `GeneratorModel` widening), behavior-preserving; (PR3) generator turn-boundary suspension + log-based resume. Docs ship **with** the behavior PR that introduces each change (no standalone docs PR — the repo's doc-maintenance protocol requires same-change-set docs).

## 2. Overview

Linear issue: [FIX-814](https://linear.app/fixpoint-labs/issue/FIX-814) — "Resume for generator and router primitives — continuation beyond the sequencer."

FIX-811 (Done) shipped the log-as-source-of-truth resume primitive: a uniform per-block replay check in core `executeBlock` that, on re-entry of a request, injects a block's recorded **completed** output instead of re-running it — keyed off the block's logical path (`${requestId}:${path}`), reading the durable item log via `ReplayLog`. That seam already covers generators and routers that *completed before* a suspension: their `block_trace.output` is replayed, the model is never re-called, the decision is never re-made.

What FIX-811 deliberately left to FIX-814 is the **continuation semantics for a primitive that is itself the locus of the suspension**: a generator that needs to pause *inside* its tool-calling loop (the highest-value HITL case — "approve this tool call before it fires"), and a router that must keep its branch decision stable when the suspension lives *inside the chosen branch*.

Two facts grounded in code shape the work (both surfaced in technical review):
- The per-block replay seam reaches sequencer steps but **not router children** — a router runs its chosen branch via `selected.run(...)` directly, bypassing the `executeBlock` seam where `_replayLog` is consulted. So the router half is not free: completed descendants inside a chosen branch re-run on resume today. The router work is to route the branch through the seam *and* replay the recorded decision for stability.
- The generator half is the larger work: own the tool loop so a tool suspension can propagate, widen the model contract for single-step driving, and reconstruct the conversation from the durable item-log (via a shared visibility-agnostic conversion factored out of the `itemToLLMMessages` path) on resume.

## 3. Background & Research

### 3.1 What FIX-811 already gives us (merged, on `main`)

- **`ReplayLog`** (`packages/core/src/blocks/internal/replay-log.ts`) — `getCompletedOutput(blockLogicalId)`, `pendingSuspension()`, and (added by #610) `resolvedResumes(blockLogicalId)`. Keyed on the **logical** id (path, attempt stripped).
- **Per-block replay seam** in core `executeBlock` (`packages/core/src/blocks/sequencer.ts:407`) and server `executeBlock` (`packages/engine/src/execution/executeBlock.ts`): a block whose logical path holds a committed `completed` output is injected — body not run, no model call, no duplicate trace. Every sequencer step, parallel branch, and forEach iteration dispatches through this seam. **Router-selected children do NOT** — the router calls `selected.run(...)` directly (`router.ts:237`), which is exactly the gap §4.1 closes.
- **`ctx.suspend()` with logical-path matching** (`packages/engine/src/context/createExecutionContext.ts`): on re-entry, a gate whose `blockLogicalId` matches `pendingSuspension()` returns the resume payload; other gates re-suspend; gates already resolved on a prior cycle replay `resolvedResumes(...)` in order (the `resolvedResumeCursor`). This makes a re-running suspend block idempotent — **direct prior art for generator/router resume memoization**.
- **`continueRequest()`** (`packages/engine/src/execution/request-continuation.ts`) — same-request continuation, `suspended → in_progress → terminal`, emits the `suspension_resume` audit item, merges prior ∪ post-resume items.
- **`collapseToCanonicalLog`** (`packages/core/src/items/canonical-log.ts`) — drops superseded run-1 items when a suspending block re-runs from the top.
- **FIX-839 (#626, merged)** — fixed content-vs-reference diffing so a `block_trace` mutated `in_progress → completed` actually persists as `completed`; without it, memoization re-executed blocks on every resume. Generator/router replay depends on this being correct.

### 3.2 What the FIX-275 spike (PR #578, closed/unmerged) proved

Reference-only, but empirically grounded (see the issue comment "Lessons from the FIX-275 spike"):

1. **The AI SDK owns the generator tool loop and *swallows* tool `execute` throws.** Verified against real `generateText`: a tool that calls `ctx.suspend()` does not suspend — the `SuspensionError` is caught, turned into a model-visible `tool-error`, and the loop runs to completion. **To make `ctx.suspend()` work inside a generator tool, FSD must own enough of the loop that the suspension propagates.**
2. **The SDK's only pre-execute interpose (`needsApproval`) is binary** (approve/reject + free-text reason). It cannot carry typed resume data (`resumeSchema`). Structurally unfit as the long-term HITL shape.
3. **You can persist the compiled turn and continue without replaying the model call** — proven by a model-call-count assertion. This is exactly what generator continuation needs.
4. **Don't key continuation off an ad-hoc blob / positional index.** FIX-275 stored an AI-SDK-internal message blob on the SuspensionRecord and matched by `blockPath` (with a known bug when `blockPath` was undefined). FIX-811's log-as-source-of-truth replaces this: reconstruct from the **durable item log**, not a serialized SDK blob.
5. **Topology guard** restricting gating generators to direct steps of the root durable sequencer was a workaround for positional resume; FIX-811's log-replay removes the need.

### 3.3 Industry research

How durable engines resume an in-flight LLM tool loop (full comparison in research notes):

- **Vercel AI SDK** (`ai` v5/v6): `generateText`/`streamText` run the multi-step loop internally driven by `stopWhen`/`maxSteps`. `needsApproval` ends the turn cleanly with a `tool-approval-request` (binary, two-call, no typed resume). Crucially, the SDK **exposes the primitives to own the loop one step at a time**: `response.messages` returns the step's `ModelMessage[]`, and a tool defined **without** `execute` surfaces its call without running it — letting FSD execute tools itself and inject arbitrary typed tool-result messages.
- **LangGraph** `interrupt()` + checkpointer: structured `Command(resume=...)`, but **re-runs the interrupting node from the top** (the documented "double-execution" gotcha) and reconstructs from its own checkpoint blob, not a neutral log.
- **Temporal / Restate / Inngest**: event-sourced — **record each step's output once and replay from the journal; never re-call the model**; Temporal *fails hard* (non-determinism error) if an LLM call sits in replayable code. Idempotency keys on side-effecting steps; per-step memoization (`step.run`), structured resume via signals/awakeables/`waitForEvent`.

**Convergent lesson:** only ecosystems that **own the loop** support typed resume; everyone disciplined records step outputs and replays them rather than re-calling the model. FSD already records each LLM turn's assistant message + tool outputs as durable items — that *is* the journal. So the leverage is to own the per-step loop and treat the item-log as the source of truth, reconstructing `ModelMessage[]` on resume (Approach D in the research notes — the recommended approach).

### 3.4 Why this approach over alternatives

- **Own the loop, key resume off the durable item-log** (chosen). Native fit: the item-log is the journal; no model replay, no side-effect replay, typed resume falls out, resists SDK message-format drift, handles partial multi-tool-call turns by per-`toolCallId` memoization. Cost: FSD reimplements the per-step orchestration `maxSteps` would otherwise do, plus a versioned item-log → `ModelMessage[]` adapter.
- **Use the SDK's native `toolApproval`/`needsApproval` seam as the suspend point instead of owning the loop** (rejected — evaluated in detail, not overlooked). Verified directly against the AI SDK docs: `toolApproval` rules resolve to `'not-applicable' | 'approved' | 'denied' | 'user-approval'`; on `'user-approval'` the SDK stops **before** `execute` runs and returns a `tool-approval-request`; resume is two full `agent.generate()`/`model.generate()` calls with a `tool-approval-response:{approvalId, approved: boolean, reason?: string}` message injected between them — structurally the same "reconstruct messages, inject the decision, call again" shape this spec already uses, just at whole-call (not single-step) granularity. Using it *would* avoid PR2's loop-inversion cost entirely (no re-implementing concurrency, provider-tool passthrough, `runTools:false`, usage aggregation, mappers, or `prepareStep`/`stepNumber` threading — the SDK still drives all of that internally). Rejected for two structural reasons that hold regardless of implementation effort: (1) the approval payload is **boolean + optional string only** — no typed `resumeSchema`, so it can't carry the structured resume data `ctx.suspend()` promises; (2) the gate is a **predicate over the tool call's declared args, evaluated before `execute` runs** — it cannot express "compute a preview inside the tool, then suspend showing that preview," which requires suspension to be callable from *anywhere* in a block's body, matching sequencer/handler/router semantics. `WorkflowAgent`+`needsApproval` (a separate, more durable variant) was also checked: its durability comes from the external Vercel Workflow DevKit runtime, not the `ai` package — adopting it would couple FSD's durability model to Vercel's workflow product specifically, and its approval payload is confirmed boolean-only too, so it doesn't resolve reason (1) either. Decision: FSD wants `ctx.suspend()` to be one uniform, typed, anywhere-callable primitive across all four block kinds (the "unified HITL primitive" goal from the issue) and control over that surface long-term, not two suspend mechanisms (SDK-native for generators, `ctx.suspend()` for everything else) or a narrower generator-only capability. See Key Decision #1.
- **Persist an AI-SDK message blob** (rejected — this was FIX-275): version-drift fragility; re-introduces the blob/positional matching FIX-811 replaced.
- **External durable engine (Temporal/Restate/Inngest)** (rejected): a second source of truth alongside the item-log; heavy infra for one feature.

### 3.5 Key Decisions & Ramifications (top 5)

1. **Invert generator tool-loop ownership: FSD drives the multi-step loop; the AI SDK becomes a stateless per-step model caller.**
   - *Alternative rejected (evaluated in detail during review, deliberately declined):* use the SDK's own `toolApproval`/`needsApproval` seam as the suspend point — verified to work via two full `generate()` calls with the decision injected between them (structurally similar to this spec's approach, just at whole-call granularity), and it would avoid PR2's loop-inversion cost entirely. Declined because (a) its approval payload is boolean + string only — no typed `resumeSchema` — and (b) its gate is a predicate over the tool call's args evaluated *before* `execute` runs, so a tool can't compute something and *then* suspend on it; `ctx.suspend()` must remain callable from anywhere in a block's body to match sequencer/handler/router semantics. The project's explicit call: owning the loop trades more up-front implementation cost for long-term control over the suspend surface — one uniform, typed, anywhere-callable `ctx.suspend()` across all four block kinds, not two suspend mechanisms or a narrower SDK-shaped one. See §3.4 for the full evaluation (including the separate `WorkflowAgent`+`needsApproval` durable variant, which doesn't resolve the typed-resume gap either).
   - *Ramification:* unlocks typed `ctx.suspend()` inside tools and per-step durability, and is the substrate FIX-275 (which this blocks) needs. Requires widening the `GeneratorModel` interface (`packages/core/src/types/model.ts:204`, today exposing only `maxSteps`) and the AI-SDK adapter to drive single steps and return each step's assistant turn — a contract change under `docs/architecture`, not a `generator.ts`-only edit. Locks FSD into owning per-step orchestration (stop-condition checks, message assembly, structured-output/repair re-threading, per-step identity stamping) that the SDK previously hid — the largest risk and LOC in this spec. The behavior-preserving refactor (PR2) lands before any suspension behavior so the inversion is de-risked against the existing generator test suite.

2. **Reconstruct the generator conversation from the *persistent* item-log on resume by reusing the existing `itemToLLMMessages` mapping; never persist an AI-SDK message blob and never re-call the model for recorded turns.**
   - *Alternative rejected:* serialize `ModelMessage[]` onto the SuspensionRecord (FIX-275); or write a new `core` adapter sourced from `tool_call_progress`.
   - *Ramification:* immune to SDK message-schema drift; matches the Temporal/Inngest "replay recorded output, not the model" discipline; reuses the same log FIX-811 made canonical. The source must be the **persistent `tool_output`** item (which carries `callId`/`name`/`alias`/`arguments`/`output`), **not** the transient `tool_call_progress` (stripped before the record is written). `packages/engine/src/context/history.ts:itemToLLMMessages` already builds both the assistant tool-call message and the tool-result message from one `tool_output` (including the `alias`-vs-`name` subtlety and orphan-pair trimming) — but it first applies a **history-visibility gate** and lives in `engine`, which `core`'s `generator.ts` cannot import. So the low-level mapping is **factored into `core`/`contracts`** (mandatory, per review), with `itemToLLMMessages` wrapping it for the history path and the resume adapter using it **visibility-agnostically** (CLAUDE.md "no duplicate copies across packages"). The approved tool re-enters to produce its real result; the payload is not the tool output.

3. **Suspension granularity: suspend at the *turn* boundary; memoize completed sibling tool calls per `toolCallId` via their `tool_output` items.**
   - *Alternative rejected:* per-tool-call suspension that re-runs the whole turn (re-calling the model) on resume.
   - *Ramification:* resolves the issue's open question. A multi-tool turn where tool #2 suspends resumes by injecting #1/#3's recorded `tool_output`s + the resolved result for #2, then continues — no model re-call, no double-fired side effects. Requires the loop to track per-`toolCallId` completion within a turn.

4. **Router resume = route the chosen branch through the replay seam, and re-run `execute` then *validate* it against the recorded `router_decision` (NOT skip `execute` and re-dispatch by name).**
   - *Alternative rejected (revised in review):* the first draft said "replay the recorded `selectedRoute` and skip `execute`." That breaks per-call route wrappers — a router `execute` can return `route.connectInput(...)` (the kitchen-sink thinking-style router does this), and the input mapping lives on the *returned* `BlockDefinition`, not the static route named by `selectedRoute` (`router.ts:56`, `:198-216`). Re-dispatching the base route by name would run it with the router's raw input and fail schemas.
   - *Ramification:* two coupled pieces. (a) Routing the selected child through `executeBlock` makes completed descendants inside a suspended branch memoize on resume instead of re-executing — without this the branch silently re-runs its completed sub-blocks. (b) On resume, **re-run `execute`** (deterministic code; preserves the returned wrapper) and assert the selection's identity matches the recorded `router_decision`; a mismatch is fatal (`RouteUnavailableError`), never a silent branch switch. Because the decision is validated by name, **routers that can suspend must have unique route names** (validated at build) or persist a route index — `router_decision.selectedRoute` is a bare `string` and same-named routes are otherwise ambiguous. `router_decision` stays the durable anchor; the change vs. the draft is *validate, don't replace*. Changes the documented router algorithm (`execution-and-errors.md:57`).

5. **Build on FIX-849's (#645, open) widened `ctx.suspend` surface (`allow`, `submit`/`skip`, `SUSPENSION_SKIPPED`, `resumeSchema` validation) rather than re-deriving a generator-specific suspend API.**
   - *Alternative rejected:* ship generator suspension against today's narrower `ctx.suspend` and reconcile later.
   - *Ramification:* generator tool suspensions inherit typed resume / submit-skip for free and there is one suspend semantics across all kinds. Creates a **sequencing dependency**: FIX-814 should land after #645 merges (they edit the same files — `createExecutionContext.ts`, `runAction.ts`, `ReplayLog`/`ResolvedResume`). See §10 / §11.

## 4. Technical Design

> Package note: the former `@flow-state-dev/server` is now `@flow-state-dev/engine` (`packages/engine/`). FIX-811's spec cites `packages/server/...`; current paths are `packages/engine/...`.

### 4.1 Router post-decision resume

**Current state (corrected against code).** The router block lives at `packages/core/src/blocks/router.ts`: the user `execute(input, ctx)` selects a route (`:100-117`), a `router_decision` item is emitted via the `onRouteSelected` runtime hook (`packages/engine/src/context/createExecutionContext.ts:2163-2180`, fired from core `router.ts:220`), and the chosen branch runs via **`asRuntime(selected).run(input, scopedCtx)` directly** (`router.ts:237`). `RouterDecisionItem` (`packages/contracts/src/items/types.ts:331` — `{ type, routerName, selectedRoute, ... }`, `status:"completed"`) is a `TRACE_TYPE` (`resolve-visibility.ts:27-31`) → `{ client:false, history:false }` and is **already persisted** (non-transient). Note: `packages/engine/src/routes/router.ts` is an unrelated HTTP route table — not the dispatch path.

**Two gaps.**
1. **Router children bypass the replay seam.** The `_replayLog` consultation exists **only** in `sequencer.ts`'s `executeBlock`; `router.ts:237` calls `.run()` directly, so a completed descendant inside a chosen branch is **not** memoized on resume — it re-executes. (Documented router contract: `execution-and-errors.md:57` "Execute selected block via `selected.run(input, ctx)`.")
2. **The decision can be re-derived non-deterministically** if `execute` reads state that changed across the suspend boundary, orphaning the in-flight suspension.

**Design.** On re-entry, when the router itself is *not* completed (the suspension lives inside its chosen branch):

1. Route the selected child through the replay seam — call `executeBlock` (or add the equivalent `_replayLog` check at the router dispatch site) instead of `.run()` directly, so the branch's completed descendants inject their recorded output and the suspending descendant re-runs and resolves via `ctx.suspend()` logical-path match. This also updates the documented algorithm at `execution-and-errors.md:57`.
   **Preserve input provenance through the seam swap (round-4 finding).** Today the router copies its own `_blockInputHint` directly onto the scoped child ctx before calling `.run()` (`router.ts:224-233`), so the routed child's `block_trace.input.source` points at the router's upstream ref rather than an inline copy (FIX-573 provenance). Core `executeBlock`'s seam does not read `_blockInputHint` directly — it forwards a hint only via the one-shot `_pendingChildInputHint` stash pattern (`sequencer.ts:180-181/423-475`, set with `stashInputHint(ctx, hint)` immediately before invoking `executeBlock`). Swapping the router's dispatch to `executeBlock` without also switching to `stashInputHint(ctx, routerInputHint)` silently regresses provenance to inline raw input — replay memoization still works (it doesn't depend on this hint), but the input source shown in traces/DevTool for the routed child would be wrong. PR1 must replace the direct `_blockInputHint` assignment with the `stashInputHint` call `executeBlock` expects.
2. **Re-run `execute`, then validate against the recorded decision (finding #3).** Re-running `execute` is deterministic and preserves the per-call wrapper it returns (e.g. `route.connectInput(...)`), which a name-based re-dispatch would drop. Compare the re-selected route's identity to `router_decision.selectedRoute`: on match, dispatch the (wrapped) block through the seam; on mismatch (non-deterministic drift, or the recorded route no longer exists) → fatal `RouteUnavailableError`, never a silent branch switch. If no `router_decision` is recorded (router never decided before interruption), `execute` runs normally.
3. **Unambiguous decisions (finding #7).** `router_decision.selectedRoute` is a bare `string` and `router.ts:56` matches candidates by object identity *or* `route.name` without rejecting duplicates. Routers that can suspend must therefore **enforce unique route names** (validate at build/registration) or persist a stable route index; otherwise two same-named routes make the validation in step 2 ambiguous.
4. **Router-selector purity for suspendable routers (round-3 finding; widened round-5).** Re-running `execute` on resume (step 2) assumes selection is side-effect-free — but `RouterConfig.execute` receives the full `BlockContext` and no purity contract is declared or enforced anywhere (`execution-and-errors.md` and `router.ts` are silent on this). If a selector emits telemetry, mutates state, or has any other side effect, re-running it on resume duplicates that effect, mirroring the tool pre-gate-side-effect problem in §4.3. PR1 must add an explicit contract: **`execute` on a router that may suspend inside its chosen branch must be pure** (read-only over input/state, no side effects) — documented and, where feasible, checked (e.g. warn/error if `execute` calls a known-mutating context method). This is a new constraint on suspendable routers, not previously part of the router contract. **The purity contract covers the returned wrapper too, split by which value each mapper actually closes over (round-5 finding, corrected round-6).** `execute` doesn't just select a route name — for a `route.connectInput(fn)`/`route.connectOutput(fn)` wrapper, `execute` constructs the mapping closure(s) that later run when `.run()` is invoked at dispatch (`router.ts:231-244` calls `asRuntime(selected).run(input, scopedCtx)` with the router's own `input`; the wrapper applies its own mapping internally). Route-name validation (step 2) only confirms the *same named route* was re-selected — it says nothing about whether the wrapper's mapping produces the *same result* on resume as it did on the original run. The round-5 draft required both `connectInput` and `connectOutput` to be pure over "the router's own `input`" — wrong for `connectOutput`: per its signature (`connectOutput<TTo>(mapper: (output: TOutput, ctx: BlockContext) => TTo | Promise<TTo>)`, `packages/core/src/types/block.ts:897-899`), the mapper receives the **selected child's output**, not the router's input, so requiring it to depend only on router input would forbid legitimate output mapping. The rule is split by what each closure legitimately depends on: **`connectInput`'s mapper** (`ConnectorFn<TFrom, TInput>`, `(input, ctx) => ...`, `block.ts:706-709`) must be pure over the router's own `input` (the value replayed on resume) — no ambient state reads. **`connectOutput`'s mapper** must be pure over the selected child's `output` (which is itself deterministic/memoized through the replay seam) plus anything closed over from the router's own `input` — also no ambient state reads at invocation time. Either closure reading ambient state (not its declared parameter, or a value captured from the router's `input`) breaks resume determinism; document this as part of the same contract, not a separate mechanism.
5. **Make the `router_decision` anchor durable before dispatch (round-5 finding).** `onRouteSelected` writes the `router_decision` trace item **fire-and-forget** — `buildTraceEmitters`'s `recordTrace` does `void traces.appendEvent(...).catch(...)` (`createExecutionContext.ts:340-353/2165-2182`, doc comment: "best-effort... errors are swallowed"). If the chosen branch suspends and the `SuspensionRecord` is persisted before this async write lands, `recordedRouterDecision()` finds nothing and step 2 falls back to "no decision recorded → `execute` runs normally" — which is safe on the *next* resume only because `execute` is now required to be pure (point 4), but leaves a **stale in-flight `router_decision` write racing with the resume path**: if it lands *after* resume has already re-run `execute` and produced its own (equivalent, by purity) decision, a later `recordedRouterDecision()` read could be ambiguous about which write is canonical. PR1 must make this specific write **durable before the router dispatches the selected child** — widen `onRouteSelected` to optionally return a `Promise<void>` and have `router.ts` `await` it (or an equivalent durability signal) before calling into the replay seam, rather than firing it alongside dispatch. This is scoped to the router-decision call site only; the general trace-emitter fire-and-forget behavior for `block_trace`/`state_snapshot` is unchanged.

**Surface for the decision lookup.** Add a read accessor to `ReplayLog` — `recordedRouterDecision(blockLogicalId): { selectedRoute: string } | undefined` — mirroring `getCompletedOutput`. The router dispatch consults `ctx._replayLog?.recordedRouterDecision(routerLogicalId)` **after** re-running `execute`, to validate the selection (not to skip `execute`).

### 4.2 Generator loop ownership inversion (behavior-preserving)

**Current state.** `generator.ts` has two model paths, both of which **delegate multi-step iteration to the AI SDK**:
- Non-streaming (`generator.ts:1820-1844`): `model.generate({ messages, maxSteps, prepareStep, ... })` — comment at `:1820` reads "single call, model handles multi-step loop via maxSteps."
- Streaming (`runStreamingGeneration`, `:1067-1398`): `model.streamText({ ..., maxSteps, prepareStepFn })`.
- `maxSteps` resolved by `resolveMaxIterations` (`:1729`, default 8 at `:72`); `prepareStep` rebuilt per-step at `:1683`. Tools execute inside the SDK loop via `buildToolExecutor` (`:723-770`) → `callTool` (`packages/core/src/blocks/internal/tool-executor.ts:93-130`) → `asRuntime(tool).run(args, scopedCtx)`. Tool outputs emitted via `emitToolOutputAround` (`packages/core/src/blocks/internal/emit-tool-output.ts`).
- There is already a framework-level `GeneratorLoopState<TInput>` and a config `stopWhen?(state, ctx)` (`:276`) used for the generator's higher-level repair loop — a useful hook for the FSD-driven loop, not a replacement for SDK multi-step today.

**Contract change.** `GeneratorModel` (`packages/core/src/types/model.ts:204-242`) today exposes only `maxSteps?: number` and a `GeneratorModelResult` (`:124-141`) that does **not** surface the AI SDK's `response.messages`. Single-step driving therefore requires widening the model contract + AI-SDK adapter to: (a) run one model step per call, and (b) return that step's assistant turn. The per-step turn is already representable as `GeneratorStepResult` (`model.ts:116-122` — `text`/`toolCalls`/`toolResults`); the loop assembles the next `messages` from these (the `history.ts` helpers already build `ModelMessage`s from these shapes), **not** from a raw `response.messages` array.

**Design.** Replace SDK-driven multi-step with an **FSD-driven step loop**:

```
messages = assembleMessages(input, context)          // unchanged initial assembly
steps = []                                            // GeneratorStepResult[] — loop metadata for callbacks
loop:
  step = await model.generateStep({ messages, tools: toolsWithoutExecute,
                                    stepNumber: steps.length, steps })   // single model step
  accumulate step.usage into blockUsage               // aggregate; do NOT emit per-step usage
  buffer step text/reasoning IN MEMORY                // NOT emitted as items here (see PR2 note)
  if step has no tool calls: break (final output)     // provider-native tools already ran provider-side (see note)
  if not runTools: return finalize(step, blockUsage) with surfaced tool-calls as terminal output  // runTools:false — TERMINATE, don't loop
  settled = await settleAll(step.toolCalls, executeTool)  // concurrent, like the SDK; settle ALL siblings
  append ONE assistant message built from ALL of step.toolCalls (+ step text) to messages   // round-6 finding — one turn, not one per call
  for each (toolCall, outcome) in settled:
    if outcome is ordinary error: emit tool_output(failed); modelResult = tool-error result   // model-visible, recoverable
    else: emit tool_output(completed, outcome); modelResult = applyToModelOutput(tool, outcome)  // mapModelOutput applied
    append tool result(modelResult) to messages   // one result message per call, in call order — no separate assistant message per call
  if any settled outcome is SuspensionError: surface ONE gate (see arbitration); throw   // after siblings settle
  steps.push(step)
  // turn complete; continue loop
return finalize(step, blockUsage)                      // structured-output parse + repair + aggregate usage on the final step
```

Key points:
- The model is called for a **single step** per iteration; tools are passed **without** `execute` so the adapter never runs them — FSD executes them via the existing `callTool` path.
- **Emissions stay byte-identical to today (finding #10).** The current non-streaming path emits the persisted assistant `message` **once**, after the final candidate passes repair/validation (`generator.ts:1980-1997`); intermediate steps are represented only by tool items. The FSD loop must preserve that — buffer per-step text in memory for the next model call, do **not** emit an assistant `message`/`reasoning` item per step. Any new replay-only artifact is introduced deliberately in PR3, not here.
- **Buffered pre-tool text must become durable when a turn suspends (finding #1).** The in-memory buffering above means that if a step emits assistant text *before* a tool call and then that tool suspends, the text is lost on `continueRequest()` re-entry — the log walk can't reconstruct it (no `message` item was persisted), so the post-approval model call loses that turn's context. PR3 must persist the suspending turn's buffered text/reasoning as a **replay-only durable artifact** (client-invisible, history-excluded, keyed to the generator path) so reconstruction is complete. This is the deliberate PR3 replay-only artifact referenced above.
- **Persist the step's tool-call metadata before launching tools, not just on suspend (round-4 finding — widens the artifact above).** `tool_output` is the only *persistent* record of a tool call's id/name/args (`tool_call_progress` is transient; the assistant tool-call step is buffered only in memory per the byte-identical-emissions rule). `emitToolOutputAround`'s `item.added` (with the call's `toolCall` metadata) is only durable once the loop has actually started dispatching that specific call. If the process dies in the gap between "the model step returned `step.toolCalls`" and "the loop begins calling `executeTool`/`emitToolOutputAround` for each call," **no durable record of that step's tool calls exists at all** — not even to identify which tool/args were about to run — so recovery would require re-calling the model, contradicting the no-model-replay goal. The loop must persist the step's full tool-call array (ids/names/args) as the **same replay-only durable artifact** described above, written **before** entering `settleAll`/dispatching any tool — not lazily only when a suspension occurs. This turns the "no `tool_output` at all" crash-recovery case (§4.6, §6) into a recoverable one (rerun the specific call from the persisted metadata) rather than an unrecoverable gap.
- **Tool result mappers (finding #6) — persist the mapped value, don't recompute it on replay (round-5 finding); the persisted field lands in PR3, not PR2 (round-6 correction).** Tools that define `mapModelOutput` currently pass it to the SDK as `toModelOutput` (`generator.ts:719`), so the model sees the mapped/redacted string while `tool_output` keeps the structured value. The owned loop must apply the same mapper when building the model-facing tool-result message — but the mapper receives `ctx` and may close over state/code, so recomputing it fresh **during resume reconstruction** (potentially after state changed across the suspend window, or the tool definition itself changed) can hand the resumed model a different tool result than the one the original model step actually saw, breaking the no-model-replay contract's intent one layer down. The live loop applies the mapper in memory the same as today either way — persisting **`tool_output.modelOutput`** (computed once when the tool settles) is needed only so resume can read it back without recomputing. Since PR2 is behavior-preserving and asserts a byte-identical persisted log against pre-refactor `tool_output` records, adding this field (and the round-3 disambiguated-alias fix, below) belongs in **PR3**, where suspension/resume support — and the byte-identical constraint — actually apply. For tools without a mapper, `modelOutput` is the raw `output`.
- **Group all of a step's tool calls into one assistant message, live and on replay (round-6 finding).** The pseudocode above appends one assistant tool-call-plus-result pair per settled call, inside the per-call loop — the same defect round-5 caught and fixed for *resume reconstruction* (§4.3) but left uncorrected here in the *live* loop. A model step with multiple parallel tool calls produced **one** assistant turn containing all of `step.toolCalls`; splitting that into N separate assistant/tool-result pairs when building the next `messages` changes the conversation shape most provider APIs validate against, in the live path just as much as on replay. Fix: build the step's assistant message **once**, from the full `step.toolCalls` (+ buffered step text), before iterating `settled` results; the per-call loop appends only the tool-result message for each call. This also means live and resume message construction now share the same shape, which the shared conversion module (§4.5) can lean on.
- **Same-turn tool concurrency (finding #9).** The SDK runs same-step tool calls concurrently. The owned loop must launch same-turn calls concurrently and **settle all siblings before surfacing a suspension**, so completed siblings are memoized (the `#1/#3`-injected multi-tool contract in §6 depends on this). Sequential execution would both change latency behavior and starve later siblings. **Accepted v1 latency tradeoff (round-5 finding).** Settling all siblings before surfacing means a fast approval-gated tool waits on a slow or hung sibling before the human ever sees the gate. Surfacing the gate early while letting siblings keep running in the background would require a durable background-execution primitive — that's `waitForEvent`/durable background sub-requests, already out of scope (§8, FIX-816/FIX-815). v1 accepts the tradeoff explicitly: siblings are expected to be ordinary framework tool calls, not long-running operations; document this so it's a deliberate scope boundary, not a silent latency bug.
- **PR2 must still swallow `SuspensionError`/`SuspensionRejectedError` as an ordinary tool error, not propagate it (round-6 finding).** PR2 already moves framework-tool execution out of the AI SDK's internal tool loop and into FSD's own `callTool`/`executeTool` path — so the SDK is no longer the thing invoking the tool, and can no longer be the one swallowing a `ctx.suspend()` throw the way it does today (§3.2 finding 1). Suspension *propagation* is explicitly PR3's job (the `if any settled outcome is SuspensionError: surface ONE gate; throw` line above does not exist yet in PR2). Until then, a generator tool that calls `ctx.suspend()` on a PR2-only checkout must still behave exactly as it does pre-refactor: `settleAll`'s "ordinary error" branch catches `SuspensionError`/`SuspensionRejectedError` like any other thrown error and converts it to a model-visible failed-tool result — PR2 does not special-case these error types at all. State this explicitly (not by omission) and add a PR2 regression test: a tool that calls `ctx.suspend()` produces the same model-visible tool-error result pre- and post-PR2-refactor, not a suspended request.
- **Cacheable tools must not also suspend (round-5 finding).** `tool-executor.ts`'s cache lookup runs **before** the tool body/scope executes (`:64-77` — `if (cacheResult.kind === "hit") return cacheResult.output`), so a cached tool with a `ctx.suspend()` gate inside its body never reaches that gate on a cache hit — the approval is silently bypassed. `cacheable` and a suspending gate are **mutually exclusive on the same tool** in v1: document the constraint, and since suspension is a runtime behavior (not statically detectable from a tool's declaration), this is a documented developer contract rather than a build-time check. Test that a cache-warmed suspending tool is not exercised in the suspension test suite (i.e., suspension tests use non-cacheable tools), and call this out explicitly in the HITL docs (§9).
- **Provider-native tools pass through (finding #5).** Generators support `search` / `providerTools` (`generator.ts:459/1606-1608/1836`): raw AI-SDK tools executed **provider-side**, not by `callTool`. The single-step contract must keep a **pass-through path** — provider tools stay attached to the model call and their results/`sources`/provider metadata flow through untouched; only framework tools go through FSD's `executeTool`. Dropping this silently breaks web-search-style generators.
- **Honor `loop.runTools: false` (finding #6, corrected in round-3 review).** When `runTools` is false (`generator.ts:275/686/1728`), the model may *suggest* tool calls but framework tools are **not** invoked — and, per the existing `packages/core/test/generator.test.ts` "skips tool invocation when loop.runTools is false" test, the generator returns the candidate **without producing tool-result messages and without looping further**. The initial pseudocode's "surface calls then continue the loop" was wrong: with no tool-result messages ever produced, continuing would either feed the model an orphaned tool-call turn or spin toward `maxSteps`. The no-execute branch must **terminate the loop on that step**, returning the surfaced tool calls as terminal output/metadata — the same behavior the SDK-driven path has today, not a new loop state.
- **Ordinary tool failures stay model-visible (finding #4).** Today a tool that throws after retries yields a `failed` `tool_output` and a tool-error result the model can react to. The owned loop must **not** let `settleAll` turn a non-suspension tool error into a terminal generator failure — convert it to the same failed-tool result message (only `SuspensionError` propagates as a suspension).
- **One approval gate per turn — arbitration for concurrent suspensions (finding #2).** Because siblings run concurrently, two tools in one turn can both call `ctx.suspend()`. The request layer persists a single pending gate, and resume can't tell a second pending approval from a genuinely failed tool. v1 contract: **first-suspension-wins** — surface exactly one gate per turn; other concurrently-suspending tools are treated as not-yet-run and re-reach their gate on the next loop iteration after the first resolves. Multiple approval gates *within a single model turn* is a **non-goal** (follow-up); document it so the arbitration is deterministic, not incidental.
- **Tag the losing tool's `tool_output` so it isn't replayed as an ordinary failure (round-4 finding).** `emitToolOutputAround`'s catch treats every thrown error identically — `status:"failed"` with `error: item.error` — whether the throw was `SuspensionError` (winning), `SuspensionError` (losing, arbitrated away), `SuspensionRejectedError`, or an ordinary tool exception. Without a discriminator, resume's "identify the pending tool precisely" logic (§4.3) has no way to tell a **losing concurrent suspension** apart from a genuinely failed tool — and the round-3 fix's fallback ("every other failed `tool_output` stays an ordinary model-visible error") is wrong for the loser: it should re-enter and re-attempt `ctx.suspend()` on resume, not be reported to the model as a failure. `emitToolOutputAround` must stamp a discriminator on the emitted `tool_output` (e.g. `error.code`/a dedicated field) when the caught error is `instanceof SuspensionError` or `instanceof SuspensionRejectedError`, distinct from an ordinary thrown error, so reconstruction can classify each failed `tool_output` as: the pending gate / a losing concurrent suspension (re-enter, no payload yet) / an ordinary failure (stays model-visible).
- **Usage aggregation (finding #7).** Once the model is called per step, usage is per-step; the loop must **sum per-step usage** and emit the same aggregate `usage`/cost metadata the current SDK-driven path reports (`:962/:1395/:1856`), or multi-step runs undercount.
- **Loop metadata for `prepareStep`/`stopWhen` (finding #8).** These callbacks depend on `stepNumber`/`steps`; the loop must thread the accumulated `GeneratorStepResult[]` and step count, not just `messages` — and on resume (§4.3) reconstruct that step count from the log so the post-approval step selects the right tools/model/stop condition.
- The streaming path keeps streaming **within** a single step (deltas still flow), but the loop boundary between steps is owned by FSD. Per-step identity stamping (`_currentModelIdentity`, `resolvedIdentity`, `generator.ts:1101/1126`) must be preserved per step.
- Structured-output validation and `applyRepairPolicy` (today run post-loop on the terminal candidate, `:1351/:1976`) must be re-threaded to fire on the final (no-tool-call) step; "final step" is defined by the break condition above.
- **No suspension behavior in this PR** — same items emitted, same persisted outputs (byte-identical), same aggregate usage, existing generator tests green. This isolates the risky inversion.

### 4.3 Generator turn-boundary suspension + log-based resume

**Suspension (first run).** With FSD owning the loop, a tool's `ctx.suspend()` throws a `SuspensionError` that propagates out of `executeTool` into the loop (no longer swallowed by the SDK). The loop:
1. Lets any **already-completed sibling tool calls in the current turn** stay recorded as their (persistent) `tool_output` items.
2. Re-throws the `SuspensionError` up to `runAction`, which (per FIX-811) writes the `SuspensionRecord`, emits the `suspension` item, and sets the request `suspended`. Note: `emitToolOutputAround` (`emit-tool-output.ts:126-147`) catches the propagating error and emits the suspended tool's `tool_output` with **`status:"failed"`** — so the durable log holds a *failed* `tool_output` for the pending tool, distinct from "absent." The log also holds completed siblings' `tool_output`s and the assistant text/reasoning items.
3. **Identity:** the suspending gate's logical path is the **tool's** scope path (`tool-executor.ts:135` extends the path with `blockPathTool(tool.name, toolCallId)`), not the generator's leaf `blockInstanceId`. `ctx.suspend()` matches on the caller's path (`createExecutionContext.ts:2620`), so `pendingSuspension()`/`resolvedResumes()` must key off this tool path consistently on both suspend and resume. (This is exactly the class of bug FIX-275 hit with an undefined `blockPath`; pin it down in PR3.)
4. **Pre-gate side effects re-run — require gate-first or idempotency (finding #8).** Because the pending tool re-enters *from the top* on resume, any side effect the tool runs **before** its `ctx.suspend()` (e.g. writing an audit row or a resource draft) executes once on the first attempt and **again** on approval — contradicting "the approved tool executes exactly once." The contract: a suspending tool should call `ctx.suspend()` **before** any side effect, or guard pre-gate work with `runOnce`/idempotency. PR3 tests that pre-suspend effects are not duplicated. (This is the LangGraph "node re-runs from the top" gotcha, scoped to the tool body.)

**Resume (re-entry).** `continueRequest()` rebuilds `ctx._replayLog` and re-enters. The generator block re-runs from the top of its body (like a sequencer suspend block), but instead of re-calling the model for every prior step, it **reconstructs the conversation from the persistent item-log**:

- **Build the messages from a shared, visibility-agnostic conversion — NOT the history-gated `itemToLLMMessages` (finding #1).** `itemToLLMMessages` (`packages/engine/src/context/history.ts:69-72`) first checks `resolveItemVisibility(item).history` and returns `[]` for `history:false` items. A generator configured `itemVisibility: { history: false }` (observability-only / private) would therefore resume with its tool-call/result turns dropped, feeding the next model step an incomplete conversation. The resume adapter must use a **visibility-bypassing** conversion path (the raw item→message mapping without the history gate), not the session-history helper. This reinforces finding #5: since the mapping is needed by `generator.ts` (in `@flow-state-dev/core`) and `history.ts` lives in `@flow-state-dev/engine` (which core cannot import), the low-level item/step→message conversion must be **factored into `core`/`contracts`** and both the history helper and the resume adapter built on it — see §4.5.
  - Re-assembles initial system/user messages via the same `assembleMessages` path (input + context are stable on resume).
  - **Reconstruct one assistant message per step, not one per `tool_output` (round-5 finding).** A model turn with text plus **multiple parallel tool calls** produced **one** assistant message containing the text and all tool-call parts together — not N separate assistant/tool-result pairs. Walking each completed `tool_output` independently into its own assistant-tool-call-plus-result pair (as originally written here) reconstructs a different conversation shape than the model actually produced, which most provider APIs don't tolerate cleanly. Since §4.2 already requires persisting each step's full tool-call array (ids/names/args) as a replay-only artifact **before** dispatch (round-4 finding), reconstruction has exactly what it needs: group by step using that persisted array — build **one** assistant message per step from its tool-call parts (plus that step's buffered text, from the same artifact), followed by that step's tool-result messages, one per completed `tool_output`, in call order (using the persisted `modelOutput`, round-5 finding above — not a freshly recomputed mapper). This is a refinement of the walk, not a new artifact.
  - The **replay-only text artifact** for the suspending turn (finding #1) supplies the pre-tool assistant text of that turn so it is not lost; it is now folded into the per-step grouping above rather than reconstructed separately.
  - **Provider-native tool calls are not reconstructable — known v1 limitation, not just a fidelity nuance (round-5 finding, sharpens open question §11.3).** The walk above sources exclusively from `message`/`reasoning`/`tool_output` items. Provider-native tools (`search`/`providerTools`, §4.2) execute **provider-side** and, by design, never produce a framework `tool_output` — only `source` items (citation metadata) are persisted, not the provider tool's call/result content itself. So a generator that uses a provider-native tool in an earlier step and *later* suspends via a framework-tool approval gate resumes with that earlier turn's provider-tool call/result **entirely absent** from the reconstructed conversation, not merely degraded. This is a step further than "reconstruction fidelity for opaque provider parts" (§11.3) — it's a full turn's content gone. See §8 for the v1 scope boundary and §6 for the edge case.
- **The approved tool re-enters and runs; the resume payload is NOT the tool result (finding #3).** `resumeContext.data` is the human's approval / typed-resume payload, not the tool's output. Rather than injecting the payload as the tool result, resume lets the pending tool **re-enter**: its `ctx.suspend()` returns `resumeContext.data`, the tool body then runs its real logic and produces its **actual return value**, which is emitted as the completed `tool_output` and is what the next model step sees. This is what satisfies the goal "the approved tool executes exactly once and the final answer incorporates its result." A reject makes `ctx.suspend()` throw `SuspensionRejectedError`, surfaced to the model as a denial result (mirrors FIX-275's "denials are model-facing results, not hard failures"). The pending tool's run-1 `tool_output{status:"failed"}` artifact is superseded by this completed run (canonical-collapse handles the shadowing).
- **Identify the pending tool precisely, not "the failed one" (round-3 finding, widened in round-4).** A resumed turn can hold **multiple** `failed` `tool_output`s, in up to three distinct categories: (a) **the pending gate** — the winning suspension; (b) **a losing concurrent suspension** (round-4 finding) — a sibling that also called `ctx.suspend()` in the same turn but lost arbitration; identified by the `SuspensionError`/`SuspensionRejectedError` discriminator `emitToolOutputAround` now stamps on the item (§4.2), *not* by status; this call must **re-enter and re-attempt `ctx.suspend()`** on resume (it may resolve immediately via `resolvedResumes`, or become the new pending gate for a further resume cycle) — it must **not** be surfaced to the model as a failure; (c) **an ordinary tool failure** — everything else with `status:"failed"` — stays a model-visible tool-error message. Conflating (b) with (c) would tell the model a still-pending approval "failed."
  - **Match the pending gate by forward construction, not by parsing the logical path (round-5 finding).** The original design derived category (a)'s `toolCallId` by parsing `pendingSuspension()`'s `blockLogicalId` string. That's brittle: `blockPathTool(toolName, callId)` (`packages/contracts/src/block-instance-id.ts:100`) formats as `tool[${toolName}][${callId}]` with **no escaping**, and the module's own doc comment notes tool names/call ids aren't guaranteed to avoid `/`, `[`, `]`. Parsing that string back into `(toolName, callId)` components can misidentify the call for names/ids containing those characters. Fix: don't parse backward — **construct forward and compare by equality**, the same way live suspend-matching already works (`createExecutionContext.ts:2620` matches on exact path equality, not parsed components). For each tool call in the step's persisted tool-call array (§4.2, known ids/names), compute its candidate logical path via the same `extendBlockPath(generatorToolPath, blockPathTool(name, callId))` construction used at suspend time, and compare each candidate against `pendingSuspension().blockLogicalId` by string equality. The first match is the pending gate. No new persisted field, no parser — reuse of the existing deterministic construction, applied to already-known candidates instead of decoded from an opaque string.
- The loop then **continues from the step after the suspension**. No model call is re-issued for recorded turns; completed *siblings* are not re-run (their `tool_output`s are injected from the log); the pending gated tool re-enters to produce its real result; any losing concurrent suspension (category b) also re-enters to re-attempt its own gate.
- **Re-emit replayed generator-owned turns, or adjust the collapse/provenance rule (finding #4).** When the suspending generator re-runs, `collapseToCanonicalLog()` treats the new generator `block_trace` as the surviving run and drops earlier items owned by that generator path. If run-1 emitted assistant text or completed sibling `tool_output`s before the suspension and those are only *read* from the old log (not re-emitted), the canonical `GET`/history loses the very prior turns that were replayed internally. PR3 must either re-emit the replayed generator-owned items after resume, or refine the canonicalization/provenance rule so generator continuation preserves them.

**Multi-cycle.** Because resume reconstructs from the log and `resolvedResumes`/`resolvedResumeCursor` replays already-resolved gates in order, a generator with N approval gates suspends and resumes N times correctly (the N-cycle property FIX-811 designed for).

### 4.4 Data flow (generator approval, one cycle)

```
run 1:  block_trace(generator, in_progress)
        step 0: model.generate(stepCountIs(1)) -> assistant text + tool_call(approve_me)
                tool_call_progress(approve_me, in_progress)
                executeTool(approve_me): ctx.suspend({reason:"approval", resumeSchema})  -> SuspensionError
        suspension(item)                                  [record -> suspended]
resume: continueRequest(requestId, resumeContext{data})   [record -> in_progress]
        ctx._replayLog = buildReplayLog(prior items); suspension_resume(item)
        re-enter generator body:
          messages = rebuild from persistent tool_output items (shared visibility-agnostic conversion)  // no model re-call
          executeTool(approve_me): ctx.suspend(...) returns resumeContext.data  // logical-path match
                                   tool body runs its real logic with the payload
                tool_output(approve_me, completed) = tool's ACTUAL return value  // not the payload
          step 1: model.generate(stepCountIs(1)) -> final assistant text       // continues past the call
        block_trace(generator, completed)                 [canonical output]
GET (canonical): prior items + suspension + suspension_resume + tool_output + final text
```

### 4.5 API surface (new / changed)

- `ReplayLog` (`packages/core/src/blocks/internal/replay-log.ts`): add `recordedRouterDecision(blockLogicalId): { selectedRoute: string } | undefined`. (`getCompletedOutput`, `pendingSuspension`, `resolvedResumes` unchanged.)
- `GeneratorModel` (`packages/core/src/types/model.ts:204`): widen to support single-step driving and return each step's assistant turn (e.g. `generateStep(...)` returning `GeneratorStepResult`), plus the AI-SDK adapter implementation. The loop caller aggregates per-step `usage` (finding #7) and threads `steps`/`stepNumber` into `prepareStep`/`stopWhen` (finding #8).
- **Shared item/step → LLM-message conversion factored into `core`/`contracts` (findings #1, #5).** `generator.ts` is in `@flow-state-dev/core`; `history.ts:itemToLLMMessages` is in `@flow-state-dev/engine`, which core cannot import. Extract the low-level, **visibility-agnostic** conversion (assistant text + tool-call/result from a persistent `tool_output`, using the persisted `modelOutput` — round-5 finding, below) into `core`/`contracts`; then (a) the engine `itemToLLMMessages` history helper wraps it with the `resolveItemVisibility().history` gate as today, and (b) the generator resume adapter uses the raw conversion **without** the history gate, grouping by the persisted per-step tool-call array (round-5 finding) and identifying the pending gate by forward-constructed path equality (round-5 finding), not status or path-parsing. Do not import engine from core; do not duplicate the mapping.
- **Carry the adapter-chosen tool alias, not just `sanitizeToolName` (round-3 finding; lands in PR3, not PR2 — round-6 correction).** The tool-compilation adapter can assign a per-request **unique** alias via `ensureUniqueAlias(...)` when two framework tool names sanitize to the same value (e.g. `foo_bar` and `foo_bar_2`) — but `emitToolOutputAround` records only `alias: sanitizeToolName(blockName)` on the `tool_output` (`emit-tool-output.ts:107`), the unsuffixed form. If the resume conversion reconstructs tool-call messages from `tool_output.toolCall.alias` alone, a generator with colliding tool names would rebuild **both** prior calls under the same unsuffixed alias, producing a tool dictionary that no longer matches what the model actually saw pre-suspension. The shared conversion (and `emitToolOutputAround`) must carry the adapter's actual disambiguated alias — either record it directly on `tool_output`, or persist an equivalent `toolCallId → alias` map alongside the item-log — so reconstruction is exact. Only needed for resume, so it ships in PR3: PR2's `tool_output` alias stays exactly as today (unsuffixed), preserving PR2's byte-identical persisted-log guarantee.
- **`tool_output.modelOutput` (round-5 finding; lands in PR3, not PR2 — round-6 correction).** New field on the `tool_output` item, computed once via `mapModelOutput(output)` (or `output` itself, when no mapper is declared) at the moment the tool settles during the live run. Both the live loop's model-facing message and the resume reconstruction's tool-result message read this persisted value — neither recomputes the mapper. Extends `EmitToolOutputAttribution`/the item shape in `emit-tool-output.ts`. Since PR2 asserts a byte-identical persisted `tool_output` log against pre-refactor records, this field is added in **PR3** alongside suspension support, where it's actually needed.
- `generator.ts`: internal FSD-driven step loop replacing the `maxSteps`-delegated calls; no change to the public `generator()` builder signature.
- `packages/core/src/blocks/router.ts` (+ its `executeBlock` routing): re-run `execute`, validate the selection against `ctx._replayLog?.recordedRouterDecision(...)` (preserving the returned wrapper — and, per round-5/round-6, only if `connectInput` is pure over the router's `input` and `connectOutput` is pure over the selected child's `output`, with no ambient reads in either), and dispatch the chosen child through the replay seam.
- **`_runtimeHooks.onRouteSelected` widened to optionally return `Promise<void>` (round-5 finding).** `packages/core/src/types/block.ts:442` and its `createExecutionContext.ts:2156` implementation change from fire-and-forget to awaitable, so `router.ts` can `await` the `router_decision` trace write landing durably before dispatching the selected child through the replay seam — closing the race where a suspension inside the branch persists before the decision anchor does.
- `tool-executor.ts:runWithRetry` (`:345`): bail on `SuspensionError` **and `SuspensionRejectedError`** (do not retry either).
- No new public block-builder API. `ctx.suspend()` semantics are inherited from FIX-849 (#645); this spec makes them *reachable inside generator tools and stable across router branches*.

### 4.6 State & error handling

- **State:** no new checkpoint channel. The generator's durable state on resume is the **item-log** (reconstructed), not a `state_snapshot`. The sequencer accumulator restore path is untouched. (This answers the issue's open question "shares the sequencer's checkpoint channel vs. generator-specific record": **neither — the item-log is the state**.)
- **Errors:**
  - Tool `SuspensionError` **and `SuspensionRejectedError`** → both are control-flow, not tool failures. Must remain non-retryable at **two** layers: the engine `isRetryableError` (`retry.ts:72`) already excludes `SuspensionError`, but the tool-executor's own `runWithRetry` (`tool-executor.ts:345-384`) retries any error when `retry.retryableErrors` is undefined (`:369`) — it must explicitly bail on **both** `SuspensionError` and `SuspensionRejectedError`, or (per round-3 review) a rejected approval re-enters the tool/gate repeatedly under `flowTools.defaults.retry` before the generator loop ever converts the rejection into the intended denial result. Regression test at the tool-executor layer for both error types.
  - Tool reject (`SuspensionRejectedError`) → injected as a model-facing denial tool-result; the model adapts (not a hard generator failure unless the tool body re-throws).
  - **Suspended tool leaves a `tool_output{status:"failed"}`** (emitted by `emit-tool-output.ts` as the suspension propagates through its catch). `emitToolOutputAround` must stamp a discriminator on this item when the caught error is `SuspensionError`/`SuspensionRejectedError` (round-4 finding), distinct from an ordinary thrown error. Reconstruction classifies each failed `tool_output` into one of three categories, not two: the **pending gate** (identified by the suspension's logical path, not status) re-enters and produces its real result (the failed run-1 artifact is shadowed by canonical collapse); a **losing concurrent suspension** (identified by the discriminator, round-4 finding) also re-enters to re-attempt `ctx.suspend()` — it must **not** be surfaced to the model as a failure; everything else (**ordinary failure**) stays a model-visible tool-error message. *Distinct* from the crash-mid-tool case, where `emit-tool-output.ts` may have persisted **either no `tool_output` at all, or one with `status:"in_progress"`** (`item.added` is emitted before `completed`/`failed` — a crash between them persists an in-progress record) — both treated identically as incomplete → tool re-runs (idempotency is the tool's responsibility; document `runOnce` guidance). **If no `tool_output` was ever persisted for a step's tool call at all** (round-4 finding — the process died before the loop even reached `emitToolOutputAround` for that call, and the step's own tool-call metadata was only buffered in memory, not durably recorded), reconstruction has no durable record of that call's id/name/args and cannot recover it without re-calling the model. See §4.2's replay-only step artifact.
  - Router decision present but its recorded `selectedRoute` no longer exists in the route table (flow changed between suspend and resume) → fatal `RouteUnavailableError`; do not silently re-decide.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| Tool `ctx.suspend()` inside generator | Propagates (loop-owned); request suspends; on resume the tool re-enters, `ctx.suspend()` returns the payload, the tool runs and emits its real `tool_output`; loop continues past the call. |
| Tool rejected on resume | `ctx.suspend()` throws `SuspensionRejectedError`; surfaced to the model as a denial `tool-result`; model adapts; not a hard failure unless tool body re-throws. |
| Multi-tool turn, one tool suspends | Same-turn tools run concurrently; all siblings settle before the suspension surfaces; settled siblings memoized via `tool_output`; resume injects those siblings and re-enters only the gated tool. |
| `history:false` (observability-only) generator resumes | Reconstruction uses the visibility-agnostic conversion, not the history-gated helper — recorded turns are NOT dropped. |
| Suspended tool's `tool_output{status:"failed"}` present | Reconstruction treats it as the pending gate → tool re-enters and produces the real result; the failed run-1 artifact is shadowed by canonical collapse. Distinct from the absent case. |
| Replayed pre-suspension turns (text / sibling `tool_output`s) | Survive canonical collapse — re-emitted (or provenance-preserved) so `GET`/history retains them after resume. |
| Crash mid-tool: no `tool_output` at all, OR a persisted `tool_output{status:"in_progress"}` (round-3 finding — `emit-tool-output.ts` emits `item.added` with `status:"in_progress"` before `completed`/`failed`, so a crash between those two emits persists an in-progress record, not an absent one) | Both treated identically as incomplete → tool re-runs on resume (tool must be idempotent / use `runOnce`). Fixture test: crash immediately after `item.added`. |
| Crash before ANY `tool_output.item.added` for a step's tool calls (round-4 finding — the gap between the model step returning `step.toolCalls` and the loop dispatching them) | Recoverable via the persisted step-level replay-only tool-call artifact (§4.2, round-4) — not an unrecoverable "must re-call the model" gap. Fixture test: crash immediately after the model step returns, before `settleAll` starts. |
| Object-schema (structured-output) generator suspends mid-loop | Repair/parse path differs from text output; reconstruction + final-step parse must still fire on the resumed final step. |
| Provider-native tool (`search`/`providerTools`) in the owned loop | Passes through to the model call, executes provider-side; results/`sources` preserved — not routed through `executeTool`. |
| `loop.runTools: false` generator | Tool calls surfaced but not executed; no-execute branch preserves opt-out behavior. |
| Ordinary tool throws after retries | Emits failed `tool_output` + a model-visible tool-error result the model reacts to — NOT a terminal generator failure. Only `SuspensionError` propagates as a suspension. |
| Two same-turn tools both call `ctx.suspend()` | First-suspension-wins: one gate surfaced; the losing tool's `tool_output` is tagged with a `SuspensionError` discriminator (round-4 finding) so resume re-enters it to re-attempt its gate, rather than replaying it as a model-visible failure. Multi-gate-per-turn is a non-goal. |
| Step emits assistant text, then suspends in a tool | The turn's buffered text is persisted as a replay-only artifact so resume reconstructs the full turn (no model replay, no lost context). |
| Tool runs a side effect before `ctx.suspend()` | Re-runs on resume (tool re-enters from the top) → require gate-first or `runOnce`/idempotency; tested. |
| Router `execute` returns a wrapped route (`connectInput`) | Resume re-runs `execute` (preserves the wrapper) and validates against the recorded decision; never re-dispatches the bare route by name. |
| Routed child's `block_trace.input.source` after the `executeBlock` seam swap (round-4 finding) | Router uses `stashInputHint(ctx, routerInputHint)`, not a direct `_blockInputHint` assignment, so the child's traced input still points at the router's upstream ref — FIX-573 provenance is preserved through the seam swap. |
| Suspendable router's `execute` has a side effect (telemetry, mutation) | Contract violation — `execute` on a suspendable router must be pure, since resume re-runs it; documented and checked where feasible. |
| Same turn has an ordinary tool failure AND the pending approval gate | Resume derives the pending `toolCallId` from `pendingSuspension()`'s logical path, not from `status:"failed"` alone — the ordinary failure stays a model-visible error; only the gated call re-enters. |
| Two framework tools sanitize to the same alias (`ensureUniqueAlias` disambiguates) | Resume conversion uses the adapter's actual disambiguated alias, not `sanitizeToolName(blockName)` alone — reconstructed tool dictionary matches what the model originally saw. |
| Router with duplicate route names, suspendable | Rejected at build (unique names required) or disambiguated by persisted index; prevents replaying the wrong same-named branch. |
| Completed descendant inside a router's chosen branch, branch suspends | Memoized on resume (PR1 routes the branch through the replay seam); not re-executed. |
| N approval gates in one generator | N suspend/resume cycles; `resolvedResumes`/cursor replays prior gates; only the pending gate consumes payload. |
| Router branch suspends inside chosen child | Resume re-runs `execute` (preserving the wrapper), validates the selection against recorded `router_decision.selectedRoute`, and continues the same branch. |
| Router route table changed between suspend & resume (recorded route gone) | Fatal `RouteUnavailableError`; never silently re-decide. |
| Generator completed before a later suspension elsewhere | Unchanged FIX-811 behavior: `block_trace.output` injected; model not re-called. |
| `SuspensionError` wrapped by retry | Must remain non-retryable; regression test (FIX-275 caught this). |
| Streaming generator suspends | Stream within a step; suspension at step boundary; resume reconstructs and resumes streaming from next step. |
| A step has text + multiple parallel tool calls, one later suspends (round-5 finding) | Resume rebuilds **one** assistant message for that step (text + all tool-call parts, from the persisted step artifact) followed by per-call tool-result messages — not isolated per-`tool_output` assistant/result pairs. |
| Tool with `mapModelOutput` settles, generator later suspends elsewhere (round-5 finding) | Resume reads the **persisted** `tool_output.modelOutput` (computed once at settle time) — never recomputes the mapper during reconstruction, so state/code drift across the suspend window can't change what the resumed model sees. |
| Cacheable tool also has a `ctx.suspend()` gate (round-5 finding) | Unsupported combination in v1 — the cache lookup runs before the tool body, so a cache hit bypasses the gate entirely. Documented constraint; suspending tools must not be `cacheable`. |
| Router branch suspends immediately after selection, before the `router_decision` trace write lands (round-5 finding) | PR1 awaits the `router_decision` write (widened `onRouteSelected` return) before dispatching the selected child, closing the race between the fire-and-forget trace append and the suspension record. |
| Router returns a `connectInput`/`connectOutput` wrapper whose mapping closure reads ambient state (round-5 finding, corrected round-6) | Contract violation — `connectInput` must be pure over the router's own `input`; `connectOutput` must be pure over the selected child's `output` (plus anything closed over from the router's `input`) — neither reads ambient state (part of the router-selector-purity contract). Otherwise the resume-reconstructed value can differ from the original run even though the route name validates. |
| Generator uses a provider-native tool (`search`/`providerTools`), later suspends via a framework tool (round-5 finding) | Documented v1 limitation (§8, §11.3): the earlier provider-tool turn's call/result is not persisted as a replayable item and is absent from the reconstructed conversation on resume — not just degraded fidelity. |
| A model step returns multiple parallel tool calls, live (not resumed) (round-6 finding) | The live loop builds **one** assistant message from the full `step.toolCalls` array before appending per-call tool-result messages — matching the grouping resume reconstruction uses, not a separate assistant/result pair per call. |
| A generator tool calls `ctx.suspend()` on a PR2-only checkout, before PR3 lands (round-6 finding) | Behaves exactly as today's SDK-swallowing path: `settleAll`'s ordinary-error handling catches `SuspensionError`/`SuspensionRejectedError` like any other thrown error and converts it to a model-visible failed-tool result — not a suspended request. Explicit PR2 requirement + regression test, not an assumption. |
| PR2's persisted `tool_output` log vs. pre-refactor (round-6 finding) | Byte-identical, including for mapper tools and colliding-alias tools: no `modelOutput` field yet, alias still `sanitizeToolName(blockName)` (unsuffixed) even when it collides. Both fixes are deferred to PR3, where the byte-identical constraint no longer applies. |

**Error taxonomy:** `SuspensionError` / `SuspensionRejectedError` = control-flow, non-retryable. `RouteUnavailableError` = fatal. Reconstruction-incomplete tool = retry that single tool (idempotency-guarded). Model/tool transient errors = existing retry/rescue semantics, unchanged.

## 7. Testing Strategy

Discipline: **`fsd:tdd`** (features/enhancement — Linear labels Reliability/Design). Each behavior below is a tracer-bullet cycle. CI specs are mocked/deterministic (mock model resolver, in-memory + sqlite stores); the goal check uses a real model.

**Goal & goal check (required).**
- **Goal (observable):** a human can approve (or reject) a tool call *inside a running agent/generator*, and the agent continues past that call to a final answer — on the same request — **without** the model being re-called for the turns before the approval and **without** the approved tool running twice.
- **Goal check:** a real-LLM script in `goals/resume-generator-tool-approval/approves-and-continues/run.mts` (per `goals/README.md`). **Not `fsdev run` alone (round-3 correction):** the CLI's `run` command mints a fresh `req_${Date.now()}...` request id per invocation (`packages/cli/src/commands/run.ts:432`) and has no resume/request-id flag, so it structurally cannot exercise `continueRequest()` or assert the same request id across suspend→resume — the exact properties this goal check exists to prove. The script must drive the **engine/HTTP resume API directly** (the same path `resume-routes.ts` / `continueRequest()` serve) against a real model: dispatch the initial run, capture the `requestId` + `suspensionId` from the suspension, POST the resume/approval, and assert on the *same* `requestId` throughout. If a CLI resume surface is added before this ships, the goal check can move to it — but it does not exist today, so the spec must not assume it. It builds a generator with one tool gated by `ctx.suspend({ reason:"approval", resumeSchema })`, runs until suspension, resumes with approval, and asserts/prints PASS/FAIL on: (a) model-call count for pre-suspension turns is unchanged across the boundary (no replay), (b) the approved tool executed exactly once, (c) final output incorporates the tool result, (d) the requestId is identical across suspend→resume. A sibling `rejects-and-continues/` exercises the denial path. **PASS/FAIL printed to stdout.**
- Router has no separate real-model goal check (its decision is deterministic code, not a model call) — covered by deterministic integration tests; stated here as the justified exception.

**Behaviours to test (TDD tracer bullets):**
- Router: chosen branch suspends → resume continues the same branch (`execute` re-run + validated against the recorded decision; wrapper preserved); a non-deterministic `execute` that re-selects a different route → `RouteUnavailableError`; recorded-route-removed → `RouteUnavailableError`; a completed descendant inside the branch is not re-executed; a branch that suspends immediately after selection resumes correctly (`onRouteSelected` awaited before dispatch, round-5); a `connectInput` wrapper whose mapping closure is (correctly) pure resumes with identical dispatched input.
- Generator loop refactor (PR2): identical items + outputs vs. pre-refactor; one model call per step.
- Generator suspension: tool `ctx.suspend()` propagates (request enters `suspended`, `suspension` item emitted); resume returns payload and produces final output; rejection injects denial; model-call-count unchanged across boundary; approved tool runs once.
- Multi-tool turn: sibling `tool_output`s memoized; only pending tool re-resolved; a step with text + N parallel tool calls reconstructs as one assistant message, not N assistant/tool-result pairs (round-5).
- N-cycle: two gates in one generator resume in order.
- Canonical log: `GET` after resume returns ordered prior + `suspension` + `suspension_resume` + post-resume items (no duplicate turns).
- Tool result mapper: `tool_output.modelOutput` persisted at settle time (PR3) and read verbatim on resume, not recomputed (round-5, PR-placement corrected round-6).
- PR2 regression: a step with multiple parallel tool calls builds one assistant message live, not N assistant/tool-result pairs (round-6); a tool calling `ctx.suspend()` still yields a model-visible tool-error result, not a suspension, on a PR2-only checkout (round-6); the persisted `tool_output` log is byte-identical to pre-refactor for mapper and colliding-alias tools specifically, not just the common case (round-6).

## 8. Non-Goals

- **The single-request continuation primitive and durable log** — owned by FIX-811 (Done). This spec consumes it.
- **Resume-vs-retry naming/affordance contract** — FIX-637.
- **The HITL approval *middleware/preset* and per-tool gating ergonomics on generators** — FIX-275 (which this **blocks**). This spec delivers the *mechanism* (suspension propagates and resumes inside generators); FIX-275 delivers the `approval: true`-style preset on top.
- **The widened `ctx.suspend` surface** (`allow`, `submit`/`skip`, `SUSPENSION_SKIPPED`, `resumeSchema` validation) — FIX-849 (#645, open). This spec builds **on** it.
- **Client/React HITL hooks/components** (`useSuspensions`, `ApprovalRenderer`) — FIX-276 (#613 merged; #645 extends). Generator/router suspensions reuse the same `suspension` item, so no React change is required here.
- **`waitForEvent`** (FIX-816), **durable background sub-requests** (FIX-815), **detached/serverless suspension surfacing** (FIX-765).
- **Resuming a generator that mixed provider-native tools (`search`/`providerTools`) with a later framework-tool suspension in the same run (round-5 finding).** Provider-tool calls/results aren't persisted as replayable items (only `source`/citation metadata is), so reconstruction cannot restore that turn's content on resume — see §4.3. v1 does not solve this (it would require persisting raw provider-specific SDK response parts, a materially larger mechanism); it's a documented limitation, not silently unsupported. Revisit if a real use case needs both in the same run.
- **Surfacing an approval gate before slower same-turn sibling tool calls finish (round-5 finding).** v1 settles all siblings before surfacing any suspension (§4.2), so a fast approval gate can be delayed behind a slow or hung sibling. Solving this would need a durable background-execution primitive, which is the `waitForEvent`/durable-background-sub-requests scope above. Accepted v1 tradeoff; siblings are expected to be ordinary framework tool calls, not long-running operations.
- **Log compaction / Continue-As-New** for very long generator loops — deferred (perf), tracked under FIX-816.
- **Deepening flag (follow-up, not in scope):** the FIX-811 **nested-durable-sequencer accumulator-restore gap** (a durable sequencer nested inside another is not state-restored on resume) is scope-adjacent if generator/router resume composes nested durable sequencers. Flag for follow-up via `fsd:improve-codebase-architecture`; do not fix here.

## 11. Open Questions

1. **Sequencing vs #645.** Confirm FIX-814 PR3 should land after #645 (FIX-849) merges, inheriting its widened `ctx.suspend`. Alternative: design PR3 against #645's branch surface and merge in either order with a planned rebase. *Recommendation: wait for #645; start PR1/PR2 now.*
2. **Streaming-path suspension in PR3 scope, or follow-up?** Owning the loop covers both paths, but suspending mid-stream-step adds complexity. *Recommendation: include streaming in PR3 (the loop boundary is between steps, so streaming-within-a-step is unaffected); flag as the first cut to revisit if it balloons.*
3. **Known limitation (not open) — reconstruction fidelity for provider-specific message parts, including a full-turn case (sharpened round-5).** The item-log records normalized text/args/result, not opaque provider parts (reasoning-signature blobs, provider-tool parts). For providers that require round-tripping those, reconstruction is lossy. The provider-native-tools case (`search`/`providerTools`, §4.3, §8) is the sharpest instance of this: it isn't partial fidelity loss, it's the entire turn's provider-tool call/result being absent from the reconstructed conversation, since only `source` items are persisted. Treat both as a documented limitation of log-based resume; if a target provider/use-case needs full round-tripping, add a per-provider escape or persist raw response parts (out of scope for the first cut). The goal check should probe basic reconstruction fidelity against the real model; the provider-native-tools case is covered by the §8 non-goal, not the goal check.
