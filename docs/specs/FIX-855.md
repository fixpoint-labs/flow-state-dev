# FIX-855: Knowledge-base lab as a secured personal MCP server — Implementation Spec

## 1. TLDR

Today the knowledge-base experiment can only be driven from the command line: you can't reach it from an AI chat like Claude, it forgets everything between requests, and there's no way to edit a single page without rewriting the whole collection. This work turns it into a small, always-on personal wiki that Claude (or any compatible AI client) can read from and write to over a secured connection — creating, editing, and deleting individual pages, with everything saved to a real database and locked to you by a secret key. It's designed to stand up as a plain server in a couple of lines, so you just run it and point your AI client at it.

**Technical statement:** Harden the incubated `labs/knowledge-base` lab into a hosted, user-scoped, bearer-secured MCP server: add concept-level CRUD to the `knowledgeBase` capability, expose the read/search/write surface as flow actions over MCP, flip the corpus to `scope: "user"`, back it with Postgres, and stand it up as a standalone server via `@flow-state-dev/node`'s `serve()` (no app wrapper), with the Vercel/Next.js route handler documented as the alternative posture.

This is **wiring over landed, tested primitives**, not new framework. Everything it leans on already exists and is documented: the MCP transport (FIX-22, `createMcpTransportAdapter`), the bearer-secret principal resolver (FIX-23, `createBearerSecretPrincipalResolver`), the Postgres store (`@flow-state-dev/store-postgres`), the standalone Node host (`@flow-state-dev/node` `serve()`, shipped in FIX-712), and the `knowledgeBase` capability + OKF adapter (FIX-813). The lab is the **second consumer** of both the MCP transport and the KB capability. The one genuinely missing piece is single-concept write: today the only write path is whole-bundle `importOkf`, which *prunes* anything not in the incoming bundle — the wrong primitive for editing one page.

**No new package is required.** An earlier framing treated a "standalone server package" as a prerequisite; `@flow-state-dev/node` already provides it (`serve(flowState, { port, host })` → a production Node HTTP server with store init, `/healthz`, graceful shutdown, and unbuffered SSE — the same `serve()` that backs `fsdev dev`). This spec *consumes* it.

**Deliverables (lab-local; no public package surface):**

- **Capability:** add `createConcept` / `updateConcept` / `deleteConcept` `fns` to `createKnowledgeBaseCapability()` in `labs/knowledge-base/src/capability.ts`.
- **Storage:** flip the concept collection to `scope: "user"` in `labs/knowledge-base/src/concepts.ts`.
- **Flow:** in `labs/knowledge-base/src/flow.ts`, expose 8 MCP tools (list / read / search / grep / create / update / delete / relate); keep OKF import/export **CLI-only** (they take host filesystem paths). Set `mcp: { enabled: true }`, wire `authentication.resolvePrincipal` to a bearer-secret resolver (constructed only when the secret is set) with no `defaultUserId` fallback, and mark any retained demo action `mcp: { enabled: false }` or move it to a separate flow.
- **Config:** in `labs/knowledge-base/fsdev.config.ts`, register `createMcpTransportAdapter()` via `adapters`, add a Postgres store profile, and select it by env.
- **Serving (primary):** add a tiny standalone entry (`labs/knowledge-base/server.ts`) calling `serve(flowstate, { port, host })` from `@flow-state-dev/node` — no Next.js, no `app/`, no React.
- **Serving (alternative, documented):** the Vercel/Next.js route handler (`app/api/flows/[...path]/route.ts` via `@flow-state-dev/vercel/next`) for anyone deploying to Vercel serverless.
- **Verification:** an end-to-end MCP JSON-RPC round-trip check (`goals/personal-knowledge-mcp/persists-a-concept-across-stateless-calls/`) proving cross-call, user-scoped persistence and 401 on a missing/wrong key.
- **Docs:** extend `labs/knowledge-base/README.md` (MCP-server section, CRUD fns, both deploy postures + auth steps, resolved limitations). No `apps/docs` changes (incubated lab, no published API).

**Size: Medium–Large — single PR (all lab-local).** Optionally split: PR 1 = capability CRUD + user scope + flow actions + auth + `serve()` standalone surface + goal check; PR 2 = Postgres profile + the optional Vercel/Next.js surface + README deploy steps.

## 2. Overview

**Linear issue:** [FIX-855](https://linear.app/fixpoint-labs/issue/FIX-855) — knowledge-base lab: expose the OKF wiki as a secured personal MCP server.

This makes the OKF-backed wiki usable from where the owner actually works — a Claude (or other MCP client) conversation — instead of only via `fsdev run`. It adds the missing incremental-write primitives (single-concept create/update/delete), exposes the full read/search/write surface as MCP tools, binds the corpus to the authenticated principal so it survives the stateless fresh-session-per-call model, persists it in Postgres for durability, and gates the endpoint behind an env-supplied bearer secret. The flows are stood up as a standalone Node server (`@flow-state-dev/node`) so "just run the flows" needs no app wrapper; Vercel serverless remains a documented alternative. OKF import/export stays as the portability/backup path.

**Necessity verdict: Build as scoped.** The lab is the second consumer of both the MCP transport (FIX-22) and the KB capability (FIX-813) — the project's "two consumers before a primitive hardens" trigger. The concept-level CRUD is real missing functionality (no 1–3-line escape-hatch equivalent exists; `importOkf` prunes). Everything else composes landed primitives that a user-space wrapper could not (stateless MCP transport, principal-resolver auth, user-scope partitioning, Postgres store, the standalone Node host). No single-vendor leakage, no public-config grab-bag, no provider guard. The CRUD lives on the incubated capability, so it adds no public API churn.

## 3. Background & Research

### 3.1 The three gaps, and why they map to three landed primitives

The issue names three missing things; each closes against an existing primitive:

| Gap (issue) | Cause today | Fix |
| -- | -- | -- |
| **No external surface** — runs only via `fsdev run knowledge ...` | flow declares no `mcp`; no adapter registered; no standalone server | `mcp: { enabled: true }` on the flow + `createMcpTransportAdapter()` in `adapters` (FIX-22) + `serve()` (FIX-712) |
| **No incremental writes** — only `importOkf` (whole-bundle sync that prunes) | capability `fns` expose list/read/relate/import/export, no single-concept write | add `createConcept` / `updateConcept` / `deleteConcept` `fns` over `collection.create` / `ref.patchState` / `ref.writeContent` / `collection.delete` |
| **Nothing persists across calls** — `scope: "session"` + in-memory stores + stateless MCP (fresh session per `tools/call`) | session-scoped state is gone the moment the ephemeral session ends | flip to `scope: "user"` (binds the corpus to the principal, not the session) + Postgres store (survives restarts/cold starts) |

The load-bearing insight on the third gap: MCP v1 is **stateless** — every `tools/call` runs in a fresh flow session (`sessionId: undefined`). A `scope: "session"` collection is therefore invisible to the next call by construction. `scope: "user"` resolves the resource's storage key by principal (`scope_id` derives from `userId`, not session — see §4.5), so call N+1 for the same bearer principal reads call N's write. In-memory stores already share state across sessions *within one process*; Postgres adds durability *across restarts*. Both changes are needed: user scope for cross-call visibility, Postgres for cross-restart durability.

### 3.2 The standalone server already exists (FIX-712)

`@flow-state-dev/node` (shipped via FIX-712, "Turnkey self-host deploy for long-lived PaaS," Done) exports `serve(flowState | router, options): Promise<ServeHandle>` — a production Node HTTP server that bridges the framework's Web-Fetch router (`{ GET, POST, PATCH, DELETE }`) to `node:http`, streams SSE unbuffered, exposes `/healthz` (503 during store init → 200 ready → 500 on permanent init failure), and shuts down gracefully on `SIGTERM`/`SIGINT`. It is the same `serve()` that backs `fsdev dev`, so it is exercised continuously. Standing up just the flows is therefore:

```ts
import { serve } from "@flow-state-dev/node";
import flowstate from "./fsdev.config";
await serve(flowstate, { port: Number(process.env.PORT ?? 3000), host: "0.0.0.0" });
```

No Next.js, no `app/`, no React. This is the natural home for an always-on personal wiki (always warm, no cold-start durability gymnastics) and the path that matches "stand up the flows without embedding them in an app." It targets long-lived hosts (Railway — which FIX-712 made turnkey — Render, Fly, a container, a VPS). **Vercel serverless is the one posture that still needs the thin Next.js handler** (`serve()` is for long-lived processes, not Vercel functions); it is retained as a documented alternative (§4.6), since stateless MCP runs on either.

### 3.3 Prior art — the LLM-wiki / MCP pattern

Karpathy's "LLM Wiki": a persistent, compounding knowledge base an LLM reads and writes over MCP across sessions, vs. one-shot retrieve-and-discard RAG. The reference implementation (lucasastorian/llmwiki) uses a storage seam where the same wiki tools run against SQLite+filesystem locally or **Postgres in hosted mode**, with the MCP server as Claude's surface. That seam maps directly onto FSD's host-owns-storage principle: the same flow actions run against in-memory stores locally (`fsdev dev`) or Postgres in hosted mode, with the framework MCP transport as Claude's surface, served by the same standalone `serve()` host. OKF export is the portability/backup analog of the prior art's local file mode.

### 3.4 Sibling precedent — trading-desk as MCP server (FIX-768)

FIX-768 (Todo, not yet built) is the parallel "lab as MCP server" effort, and its candidate solution already names this exact posture: `mcp: { enabled: true, exposeActions: [...] }` on the flows, Postgres stores, a personal bearer token through `resolvePrincipal`, and **Railway self-host** (the FIX-711/FIX-712 long-lived track) rather than Vercel. The one framework-gap risk it flags — **long-running work over MCP** (a 10–20-minute analysis run exceeds any client's tool-call patience, forcing a job-shaped start/poll/fetch surface) — **does not apply here**: knowledge-base operations are fast synchronous CRUD that return well inside a tool-call window. This lab is therefore the lower-risk second consumer; it validates the MCP transport's synchronous action→tool mapping without needing async/job semantics.

### 3.5 The nav tools are reusable as actions (resolves the one design question)

`resourceSearchTools()` (`packages/core/src/tools/resource-search-tools.ts`, shipped in FIX-813 PR 1) returns three `handler` blocks — `globResources`, `grepResourceContent`, `searchResources` — each with a `description`, `inputSchema`, and `outputSchema`, operating over `ctx`-enumerated resources (`collectAllResources` / `collectReadableResources`). Because a flow action's `block` can be any handler, these blocks can be **exposed directly as MCP-tool actions** over the user-scoped concept collection — zero new code, zero duplication, and literally the same blocks the generator uses (honoring FIX-813 decision #4: one KB tool surface, not a divergent second one). They emit scope-qualified `uri`s (`user/concepts/<id>`); the id-based tools (read/create/update/delete) take bare concept ids — a small seam handled in §4.3.

### 3.6 Why this shape over alternatives

- **vs. building a new "standalone server" package:** unnecessary — `@flow-state-dev/node` already is one (§3.2). The work is to *use* it.
- **vs. flow-local CRUD handlers** that call `collection.*` directly: keeping create/update/delete in the capability's `fns` holds the KB vocabulary in one place (FIX-813 decision #4) and lets a future consumer reuse them. The flow actions stay thin handlers over `fns`.
- **vs. a file-backed / local mode now:** OKF export already covers portability; a single-file collection variant is a deliberate non-goal (§8).
- **vs. graduating the capability to a public package:** OKF is still v0.1 and the capability is still incubated; graduation waits for Storyteller (FIX-759) + OKF past v0.1. This lab strengthens that case without forcing it.

### 3.7 Key Decisions & Ramifications (top 5)

1. **Concept CRUD lives in the capability `fns`, not flow-local handlers.** Rejected: flow-local `collection.*` calls. *Ramification:* holds the KB vocabulary in one place (FIX-813 decision #4), reusable by a future consumer; couples the lab flow's thin actions to the capability fn surface.
2. **Flip the corpus to `scope: "user"` (+ Postgres) instead of session scope.** Rejected: keep session scope / add an explicit tenant key. *Ramification:* per-principal isolation becomes native (`scope_id` derives from `userId`) and multi-user is a later config flip, not a redesign; persistence now requires an authenticated principal on every stateless call — which is exactly what makes a write visible to the next `tools/call`.
3. **Expose the existing nav blocks directly as the search/grep actions.** Rejected: id-returning wrapper handlers. *Ramification:* zero duplication and one tool surface (decision #4), but introduces a uri-vs-id seam a shared `conceptIdFromUri` normalizer must absorb on every id-taking action (§4.3).
4. **Standalone `serve()` primary, Vercel/Next.js alternative.** Rejected: Vercel-only (the issue's earlier settled direction) / build a new server package. *Ramification:* "stand up just the flows" needs no app wrapper and no new package; an always-on wiki fits a long-lived host; Vercel stays valid but is no longer the default, and the deploy target is now a documented choice rather than assumed.
5. **Static bearer secret, no `defaultUserId` fallback, as the auth floor.** Rejected: rotation / per-client keys now. *Ramification:* simplest secure personal floor over the host's TLS; a leaked key exposes the whole corpus until manually rotated; multi-user/rotation deferred.

## 4. Technical Design

### 4.1 Architecture & placement

All changes are inside `labs/knowledge-base/` (the only other lab is `labs/trading-desk`). No `packages/*` edits — every primitive is landed. New runtime dependencies on the lab: `@flow-state-dev/mcp`, `@flow-state-dev/store-postgres`, and `@flow-state-dev/node` (the standalone host). The optional Vercel path additionally needs `@flow-state-dev/vercel` + `next` + `react`/`react-dom`, isolated to that posture.

### 4.2 Capability — concept-level CRUD `fns`

Add three `fns` to `createKnowledgeBaseCapability()` (`labs/knowledge-base/src/capability.ts`), alongside the existing `listConcepts` / `readConcept` / `relate` / `importBundle` / `exportBundle`. Primitives confirmed on `ResourceCollectionRef<ConceptState>` / `ResourceRef<ConceptState>`: `create(key, initial?, { replace? })`, `delete(key)`, `getOptional(key)`, `get(key)`, `writeContent(body)`, `patchState(updates)`.

```ts
/** Create a NEW concept (frontmatter state + body). Rejects if the id already exists. */
createConcept: async (
  id: string,
  state: ConceptState,        // `type` is required by the schema
  body: string,
): Promise<void> => {
  assertSafeConceptId(id);   // reject absolute paths, `..` segments, empty, and reserved index/log
  const c = ref();
  if (await c.getOptional(id)) {
    throw new Error(`knowledgeBase: concept "${id}" already exists; use updateConcept`);
  }
  const r = await c.create(id, state);     // touches only this key — corpus untouched
  try {
    await r.writeContent(body);
  } catch (err) {
    await c.delete(id);                     // roll back the state row so a retry isn't blocked by "already exists"
    throw err;
  }
},

/** Update an existing concept's state and/or body (partial; last-write-wins). */
updateConcept: async (
  id: string,
  patch: { state?: Partial<ConceptState>; body?: string },
): Promise<void> => {
  const r = await ref().getOptional(id);
  if (!r) throw new Error(`knowledgeBase: concept "${id}" not found`);
  if (patch.state !== undefined) {
    // Validate the MERGED state before persisting. patchState can persist `{}` when the post-patch
    // state fails the collection schema, silently erasing required frontmatter; merge + parse first.
    await r.setState(conceptStateSchema.parse({ ...r.state, ...patch.state }));
  }
  if (patch.body !== undefined) await r.writeContent(patch.body);
},

/** Delete one concept. Dangling inbound edges are tolerated (see §6). */
deleteConcept: async (id: string): Promise<void> => {
  await ref().delete(id);
},
```

Design points:

- **Incremental & idempotent at the concept level (issue outcome #2):** `create` / `delete` / `patchState` / `writeContent` all touch exactly one key. The rest of the corpus is never read, rewritten, or pruned — unlike `importOkf`.
- **create vs. update split:** `createConcept` throws on an existing id; `updateConcept` throws on a missing one. This gives the MCP tool surface clean, predictable semantics and surfaces a usable error to the agent ("already exists; use updateConcept") rather than silently clobbering.
- **`type` is required** (the schema's only required field, `z.string()` with no default), so `createConcept`'s `state` must carry it; the flow action's `inputSchema` enforces this.
- **Concurrency = naive last-write-wins** (resolves issue open-question on concurrency): no optimistic locking. Acceptable for a personal wiki; flagged in §6 and as a non-goal.
- **Failed body write rolls back the state row.** `createConcept` deletes the just-created instance if `writeContent` throws, so a transient store error doesn't strand a state-only concept that a retry would then reject as "already exists."
- **`readConcept` returns `{ state, body }`, not just the body.** The existing fn returns only the content body; extend it to return frontmatter state too, so an edit flow (read → change metadata → `updateConcept`) can see the current `type`/`title`/`description`/`tags` — which `read_concept`'s description promises.
- **Write-path input validation (hardening).** These are the first *remote* write surface for arbitrary ids and frontmatter: (a) `createConcept` calls `assertSafeConceptId(id)` — rejecting absolute paths, `..` segments, empty ids, and the reserved `index`/`log` basenames — because a traversal id (`../outside`) would otherwise escape the export directory on the owner's next CLI `exportOkf` (which writes `path.join(dir, "<id>.md")`), even though export isn't an MCP tool; (b) `updateConcept` validates the merged state against `conceptStateSchema` before persisting (above); (c) `relate` validates that **both** endpoints exist (the existing fn only checks the source), so a mistyped `to` can't create a dangling edge that later exports as a broken `# Related` link.

### 4.3 Flow — actions, MCP, auth

Rewrite `labs/knowledge-base/src/flow.ts` to expose one action per operation and opt into MCP. Each action is a thin handler over a capability `fn` (uniform surface), except the two search actions (`searchConcepts`/`grepConcepts`), which reuse the nav blocks directly.

MCP requirements confirmed: when `mcp.enabled`, **every non-excluded action must have a non-empty `description`** (`validateMcpConfig` throws at registration otherwise). Tool names derive from the action key (`createConcept` → `create_concept`).

Recommended action set (8 tools — small, which Claude-class clients handle best):

| Action key → MCP tool | Block source | Input (sketch) | Notes |
| -- | -- | -- | -- |
| `listConcepts` → `list_concepts` | handler → `fns.listConcepts` | `{}` | clean bare ids |
| `readConcept` → `read_concept` | handler → `fns.readConcept` | `{ id }` | tolerate id **or** `user/concepts/<id>` uri (§ below) |
| `searchConcepts` → `search_concepts` | `nav.searchResources` (direct) | `{ query, prefix?, limit? }` | ranked; returns uris |
| `grepConcepts` → `grep_concepts` | `nav.grepResourceContent` (direct) | `{ pattern, prefix?, maxResults? }` | returns uris+lines |
| `createConcept` → `create_concept` | handler → `fns.createConcept` | `{ id, type, title?, description?, tags?, body }` | rejects existing |
| `updateConcept` → `update_concept` | handler → `fns.updateConcept` | `{ id, state?, body? }` | partial |
| `deleteConcept` → `delete_concept` | handler → `fns.deleteConcept` | `{ id }` | |
| `relateConcepts` → `relate_concepts` | handler → `fns.relate` | `{ from, to, type? }` | typed edge |

OKF `importBundle`/`exportBundle` are **excluded from the MCP surface** — they take server-side filesystem paths, and over a hosted endpoint that would let a remote LLM read from / write to / prune arbitrary host paths. They stay CLI-only (the `fns` remain for `fsdev`-driven use; see §8). If ever exposed, constrain them to a fixed, configured backup directory.

`globResources` is intentionally dropped from the MCP surface (`list_concepts` covers structural discovery; `search`/`grep` cover content). Keep `mcp` exposure tight; the generator path (`research`/`ask`) keeps the full glob/grep/search trio via the capability's `search` preset.

**id vs. uri seam:** `searchConcepts`/`grepConcepts` (the nav blocks) return scope-qualified `uri`s (`user/concepts/<id>`), while the id-based tools take bare ids. Resolution: a shared `conceptIdFromUri(x)` helper (strips a leading `${scope}/${prefix}/`, passes a bare id through) is applied by **every** id-taking action — `read_concept`, `update_concept`, `delete_concept`, and `relate_concepts` — not just read. Otherwise a client pasting a search-result uri into update/delete/relate would silently hit not-found/no-op instead of the intended concept. Document the accepted forms in the action descriptions. (Alternative considered and rejected: wrap the nav blocks in id-returning handlers — more code, and it forks the tool surface FIX-813 decision #4 says to keep single.)

Each thin action handler follows the existing `explore` handler's shape — `uses: [kb.presets({ index: false, search: false })]` (handlers don't need the generator-only presets), `execute` calls `ctx.cap.knowledgeBase.<fn>(...)`, returns a small result (BP-014: never `return input`; these return real results, not echoes).

Flow definition:

```ts
const knowledgeFlow = defineFlow({
  kind: "knowledge",
  authentication: {
    requireUser: true,
    // No defaultUserId: a missing/invalid key denies rather than serving an anon principal.
    // Construct the resolver only when the secret is set — createBearerSecretPrincipalResolver
    // THROWS on an empty secret, so importing this config in local dev / CI (no KB_MCP_SECRET)
    // must not pass "". The hosted entry (server.ts, §4.6) refuses to start without the secret,
    // so a deployed server is never left unauthenticated.
    resolvePrincipal: process.env.KB_MCP_SECRET
      ? createBearerSecretPrincipalResolver({
          secret: process.env.KB_MCP_SECRET,
          principal: { userId: "owner" },   // the single personal user the corpus binds to
        })
      : undefined,
  },
  mcp: { enabled: true },
  actions: {
    listConcepts:  { block: listConceptsHandler,  description: "List all concept ids in the knowledge base." },
    readConcept:   { block: readConceptHandler,   description: "Read one concept's body and frontmatter by id." },
    searchConcepts:{ block: nav.searchResources,  description: "Rank concepts by lexical relevance to a query." },
    grepConcepts:  { block: nav.grepResourceContent, description: "Find concept lines matching a regex/substring." },
    createConcept: { block: createConceptHandler, description: "Create a new concept (frontmatter + body)." },
    updateConcept: { block: updateConceptHandler, description: "Update an existing concept's frontmatter and/or body." },
    deleteConcept: { block: deleteConceptHandler, description: "Delete one concept by id." },
    relateConcepts:{ block: relateHandler,        description: "Add a typed link edge between two concepts." },
    // OKF import/export are NOT MCP tools: they take server-side filesystem paths, so over a hosted
    // endpoint they would let a remote client read/write/prune arbitrary host paths. Kept CLI-only via
    // `fns.importBundle`/`exportBundle` (e.g. a non-MCP `explore` action or a separate flow).
  },
  resources: { concepts: kb.collection },
});
```

**The existing `research`/`ask` demo path must NOT stay on this flow as-is** — two reasons. (1) Its `seedSample` step calls `importBundle(SAMPLE_BUNDLE)`, whose whole-bundle *sync* prunes anything not in the sample; under `scope: "user"` a demo run would wipe the owner's durable corpus (session scope made this harmless before). (2) With `mcp.enabled`, every non-excluded action becomes an MCP tool and needs a description, so a retained `research`/`ask` action would either fail registration or add a model-dependent action to the advertised surface. Resolution: drop the demo from the hosted flow, or move it to a **separate session-scoped flow** (its own `kind`, not `mcp`-enabled). Any CLI/demo action left on this flow must set `mcp: { enabled: false }` so clients see exactly the 8 CRUD tools.

**Auth contract (confirmed):** `createBearerSecretPrincipalResolver(...)` returns a `PrincipalResolver`, which is a type alias of `ResolvePrincipalFn` — the exact type of `authentication.resolvePrincipal`, so it assigns directly. It compares the bearer token in constant time (`node:crypto.timingSafeEqual`), returns the fixed `principal` on match, returns `null` when the header is absent (→ with no `defaultUserId` and `requireUser: true`, the framework rejects 401), and throws `PrincipalResolutionError({ status: 401 })` on a present-but-wrong key. The per-flow `resolvePrincipal` takes precedence over any host-level resolver. **Because the resolver throws on an empty secret** (a build-time guard in the helper), `fsdev.config.ts` constructs it **only when `KB_MCP_SECRET` is set** — so importing the config in local dev / CI never throws — and a **shared config-load guard (§4.4) throws when the hosted (Postgres) profile is selected without the secret**, covering both the standalone `serve()` and the Vercel entries, so a deployment is never left falling back to the body-userId resolver.

### 4.4 Config — adapter + Postgres profile

`labs/knowledge-base/fsdev.config.ts` (`createFlowState` accepts `adapters`, forwarded to `createFlowApiRouter`):

```ts
import { createMcpTransportAdapter } from "@flow-state-dev/mcp";
import { postgresStores } from "@flow-state-dev/store-postgres";

// Select prod when either Postgres URL the adapter honors is set — not just DATABASE_URL —
// else a FSD_DB_URL-only deploy silently picks in-memory dev and loses the corpus on restart.
const profile = (process.env.FSD_DB_URL ?? process.env.DATABASE_URL) ? "prod" : "dev";

// Fail closed at config load: a hosted deploy (prod profile) MUST carry the bearer secret. This guard
// lives in the SHARED config — not just server.ts — so BOTH entries (standalone serve() and the Vercel
// route handler, which import this same flowstate) are covered. Without it, an absent secret leaves
// resolvePrincipal undefined and the host falls back to the body-userId resolver, so a crafted
// tools/call body with a top-level userId could satisfy requireUser without the bearer and read the
// corpus. Dev (no Postgres URL) needs no secret, so importing the config in local dev / CI still
// never throws.
if (profile === "prod" && !process.env.KB_MCP_SECRET) {
  throw new Error("KB_MCP_SECRET must be set for the hosted (Postgres) profile");
}

export default createFlowState({
  flows: { knowledge: knowledgeFlow },
  modelResolver,
  adapters: [createMcpTransportAdapter()],     // mounts POST /api/flows/:kind/mcp
  stores: {
    dev:  { primary: inMemoryStores() },
    // Empty options object is required by the signature; the adapter then reads FSD_DB_URL → DATABASE_URL.
    prod: { primary: postgresStores({}) },
  },
  defaultProfile: profile,
  onError: (error, context) => {
    console.error(`[flow-api] ${context.method} ${context.path}:`, error.message);
  },
});
```

This keeps local development on in-memory stores and selects Postgres automatically when a Postgres URL (`FSD_DB_URL` or `DATABASE_URL`) is set. The same `flowstate` export feeds both the standalone `serve()` entry and (optionally) the Vercel handler — one config, one MCP adapter, two possible hosts. **On Vercel, use a Vercel-tuned `prod` profile — `vercelPostgresStores()` (Neon pooling; avoids per-cold-start schema init and stale pooled TCP connections) — rather than reusing the long-lived-host `postgresStores()` adapter unchanged.**

### 4.5 User-scope isolation (resolves issue open-question)

For a `scope: "user"` resource, the storage `scope_id` derives from the principal: `resolveResourceScopeId(userId, flowKind, isolated)` returns `userId` (or `${userId}:${flowKind}` when `isolateUserState: true`). The content/state/edge rows are keyed by `(scope_type="user", scope_id, resourceKey)`. **Per-principal isolation is therefore native to user scope** — two bearer keys mapping to two principals (`owner`, `owner2`) get `scope_id` `owner` vs. `owner2` and never read each other's rows. No explicit tenant key is needed. `isolateUserState` only affects whether *different flow kinds* share one user's state; with a single flow it is irrelevant — leave it at the default (`false`). This is what makes "more keys → more principals" a later config flip rather than a redesign.

### 4.6 Serving

**Primary — standalone Node server (`@flow-state-dev/node`).** Add a tiny entry that stands up just the flows, no app wrapper:

```ts

import { serve } from "@flow-state-dev/node";
import flowstate from "../fsdev.config";  // config lives at the lab root; importing it triggers the §4.4 fail-closed guard

await serve(flowstate, {
  port: Number(process.env.PORT ?? 3000),
  host: "0.0.0.0",
  basePath: "/api/flows",
});
// POST /api/flows/knowledge/mcp is served by the registered MCP adapter.
// GET/DELETE on that path return 405 (MCP v1). /healthz is exposed for the host's probe.
```

Place the entry where the lab's `tsconfig` `include` already covers it (e.g. `src/server.ts`, or add the root file to `include`) so `pnpm typecheck` catches broken imports / `serve()` options, and add an `fsdev`-adjacent script (e.g. `"serve": "tsx src/server.ts"`). Deploy to a long-lived host (Railway is turnkey via FIX-712; Render/Fly/container/VPS work from the same artifact) with a Postgres URL (`FSD_DB_URL`/`DATABASE_URL`) and `KB_MCP_SECRET` set. This is the always-warm posture and needs no React/Next dependency.

**Alternative — Vercel serverless (Next.js handler), documented.** For anyone targeting Vercel, add the App Router surface mirroring `examples/hello-chat`:

```ts
// labs/knowledge-base/app/api/flows/[...path]/route.ts
import { createVercelNextHandler } from "@flow-state-dev/vercel/next";
import flowstate from "../../../../fsdev.config";

export const { GET, POST, PATCH, DELETE } = createVercelNextHandler(flowstate);

```

This pulls in `@flow-state-dev/vercel` + `next` + `react`/`react-dom` (isolated to this posture) and a `next.config` + `vercel.json`. Stateless MCP fits serverless cleanly, but the corpus's cross-call persistence relies on the external Postgres store either way. Use the Vercel-tuned `vercelPostgresStores()` profile — note it sets `skipSchemaInit: true`, so a fresh Neon/Postgres database needs a **one-shot schema migration** (run `createPostgresStores({ connectionString })` once, or a deploy/build migration step) before the first CRUD call; otherwise `next build` + `tools/list` pass while the first write fails on missing tables. **Auth is covered by the shared config-load guard (§4.4): because this handler imports the same `flowstate`, a Postgres-profile deploy missing `KB_MCP_SECRET` fails closed here too — no separate Vercel guard needed, so the endpoint can't fall back to the body-userId resolver.**

**Provisioning the Postgres database (Neon or a host-managed instance) and the chosen host's project/secrets is a manual operator step** documented in the README — the spec ships the deployable code, not a live deployment.

### 4.7 Data flow (hosted, per `tools/call`)

`MCP client → POST /api/flows/knowledge/mcp (Authorization: Bearer <secret>) → MCP adapter resolves principal (owner) → fresh ephemeral session → runAction(<tool>, args) → capability fn over the user-scoped Postgres-backed collection → terminal output → single JSON tool result`. The next `tools/call` repeats with a new session but the same principal, so it reads the prior call's writes. The path is host-agnostic — identical whether `serve()` or the Vercel handler fronts the router.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| -- | -- |
| `create_concept` with an existing id | Throw `concept "<id>" already exists; use updateConcept`; corpus untouched |
| `update_concept` / `read_concept` / `delete_concept` on a missing id | `update` throws "not found"; `read` returns null/empty; `delete` is a no-op (idempotent) |
| `create_concept` missing `type` | Rejected by the action `inputSchema` (`type` required) before reaching the fn |
| `create_concept` with an unsafe id (`../x`, `/abs`, `index`/`log`) | `assertSafeConceptId` rejects before persisting — blocks path traversal that would escape the export dir on a later CLI `exportOkf` |
| `update_concept` with invalid frontmatter (`type: null`, non-array `tags`) | Merged state is parsed by `conceptStateSchema` before `setState`; a malformed update is rejected loudly, not silently persisted as `{}` |
| `relate_concepts` with a non-existent `to` id | Rejected — both endpoints validated; no dangling edge that would export as a broken `# Related` link |
| `writeContent` fails after `create` persisted state | `createConcept` rolls back (deletes the state row) and rethrows, so a retry isn't blocked by a stranded "already exists" state-only concept |
| Search/grep `uri` pasted into `update`/`delete`/`relate` | Normalized by the shared `conceptIdFromUri` helper (§4.3), same as `read` — resolves to the concept rather than a no-op |
| Missing `Authorization` header | Resolver returns null → no `defaultUserId` + `requireUser` → **401** |
| Present but wrong bearer secret | Resolver throws `PrincipalResolutionError({ status: 401 })` (constant-time compare) |
| Config imported with `KB_MCP_SECRET` unset | **Dev profile** (no Postgres URL): resolver not constructed; the default body-userId resolver applies for `fsdev dev`/`fsdev run` (local only). **Prod profile** (Postgres URL set): the shared config-load guard (§4.4) **throws**, so both the standalone and Vercel entries fail closed rather than falling back to the body-userId resolver and serving the corpus unauthenticated |
| `tools/call` for a different principal (future 2nd key) | Reads/writes a different `scope_id`; cannot see `owner`'s corpus (§4.5) |
| Two `tools/call`s racing on the same concept | Last-write-wins (no optimistic lock); acceptable for a personal wiki |
| `delete_concept` leaves dangling inbound edges from other concepts | Tolerated; traversal/import already treat dangling links as warnings. Inbound-edge cleanup is a non-goal (§8) |
| Search/grep result uri pasted into `read_concept` | Handler strips the `${scope}/${prefix}/` lead so the uri resolves to the id |
| CLI `importBundle` over an existing corpus | Whole-bundle sync **prunes** concepts not in the bundle — OKF mount semantics, not a CRUD edit. Not an MCP tool (§4.3), so a remote client can't trigger it |
| `GET`/`DELETE` on `/api/flows/knowledge/mcp` | 405 (MCP v1 is POST-only) |
| Streaming / large result | v1 returns a single JSON text result; no progress notifications. Fine for CRUD |
| Restart / cold start with in-memory profile | Corpus lost — which is why `prod` uses Postgres; in-memory is `dev`-only. The standalone `serve()` host is long-lived (always warm), so within a deployment the in-process store would also persist, but Postgres remains the durable source of truth |

**Error taxonomy:** auth failures are 401 (non-retryable — fix the key). CRUD precondition failures (already-exists / not-found) are deterministic 4xx-class application errors surfaced as MCP `isError` tool results, not retryable. Store/IO failures are fatal for that call. None are transient-retryable in the framework sense.

## 7. Testing Strategy

**Discipline:** `fsd:tdd`. CI specs (mocked/deterministic) and the goal check (real path) do different jobs; both required.

**Goal & goal check (required).** **Goal:** from an MCP client, a concept created in one stateless `tools/call` is readable in a *separate* `tools/call` for the same bearer principal, and an unauthenticated call is refused — i.e. a durable, user-scoped, secured personal wiki over MCP. **Goal check:** `goals/personal-knowledge-mcp/persists-a-concept-across-stateless-calls/run.mts` stands up the lab via `serve()` (or assembles the router directly) with `createMcpTransportAdapter()` and the **Postgres path** — a PGlite executor via `postgresStores({ executor })`, **required, not in-memory**: the goal is *durable* persistence, so the check must exercise the Postgres profile + schema init, or CI could pass while the production persistence wiring is broken. Then:
1. `POST tools/call create_concept { id, type, title, body }` (request A) → expect success.
2. `POST tools/call read_concept { id }` and `list_concepts` (request B, **separate** request = fresh ephemeral session) → expect the body + id back. **Signal:** the body string from A appears in B's tool result.
3. `POST tools/call` with **no** `Authorization` header → expect HTTP 401. **Signal:** status 401, no tool result.
**Anti-game:** the body asserted in B must come from request B's response, not a variable in the test; swap the fixture id/body and it must still pass. Asserting on A's own echo, or reading the store directly instead of through a second `tools/call`, would be a hollow pass.

This goal check is **model-free** (CRUD needs no LLM) and so can run in CI as a true end-to-end integration test — stronger than a mocked unit test because it drives the real transport + auth + store + CRUD, and (via `serve()`) the real HTTP host. The pattern model is `packages/mcp/test/end-to-end.test.ts` (`postMcp` helper; `tools/list` and `tools/call` JSON-RPC bodies; `source: "mcp"` assertion). A `goal.md` records outcome/signal/anti-game/verdict-log per `goals/README.md`.

**Manual acceptance (real client):** point Claude Desktop (or any MCP client) at the deployed `/api/flows/knowledge/mcp` with the bearer secret; create a page, start a new conversation, read it back. Documented in the README; not automatable.

**CI specs (mocked, every push):**
- *Capability (`test/capability.spec.ts`):* the Step 1 behaviors — create/read (read returns `{ state, body }`), create-on-existing throws, create rolls back on a body-write failure, update partials, update/read/delete on missing, delete isolates (siblings survive).
- *User scope (`test/`):* two `userId`s see isolated corpora.
- *Flow/MCP (`test/`):* registration passes with `mcp.enabled` (all actions described); importing the flow without `KB_MCP_SECRET` does not throw; `tools/list` exposes the 8 tools with derived names (import/export absent); a `uri` from `search_concepts` normalizes correctly into `update`/`delete`/`relate`; a `tools/call create_concept` round-trips through the router.
- *Existing OKF import/export/round-trip specs* continue to pass under user scope.

**Seams:** vitest for capability + flow/MCP unit behavior; the goals `run.mts` for the end-to-end MCP round-trip over `serve()`; `fsdev dev` / `pnpm serve` for manual local serving. Block/handler tests follow `fsd:write-block-tests` mock-context idiom; `test/helpers.ts`'s `makeConceptCollection` is the collection-ref mock.

## 8. Non-Goals

Out of scope (separate issues if pursued):

- **File-backed / local mode** — Postgres-backed; OKF export is the portability path.
- **Semantic / embedding search within the corpus** (FIX-833) — navigation stays lexical (glob/grep/ranked-keyword).
- **A new standalone-server package** — `@flow-state-dev/node` already provides `serve()` (FIX-712); this lab consumes it, it does not build a host.
- **Durable background work / cron / job-shaped MCP tools** — KB ops are fast CRUD; the FIX-711/FIX-768 async concerns do not apply here.
- **Promoting the `knowledgeBase` capability / OKF adapter to a published package** — graduation waits for a second *capability* consumer (Storyteller, FIX-759) + OKF past v0.1. This lab advances but does not complete that case.
- **Full multi-tenant auth** — per-client keys, sign-up, secret rotation, OAuth. v0 is a single static bearer over the host's TLS (the personal-use floor). The user-scope design makes multi-user a later config flip, not a redesign.
- **MCP streaming / resources** — v1 is single-JSON tool results; concepts surface as MCP *tools*, not MCP *resources* (`resources/list` empty). Accepted for v0 CRUD.
- **Inbound-edge cleanup on `deleteConcept`** — dangling edges from other concepts are tolerated (consistent with import's best-effort link handling); a `pruneDangling` sweep is a follow-up.
- **`importBundle` becoming a merge instead of a sync** — it remains whole-bundle sync (prunes); incremental edits go through CRUD.
- **A one-click Railway template / Deploy button** — FIX-712's turnkey template is the general mechanism; this spec ships the `serve()` entry + deploy docs, not a bespoke template.
- **OKF import/export as MCP tools** — `import_bundle`/`export_bundle` take server-side filesystem paths, so over a hosted endpoint they'd let a remote client read/write/prune arbitrary host paths. CLI-only in v0 (§4.3); a path-constrained, backup-dir-scoped MCP export is a possible follow-up.
- **Retaining the `research`/`ask` demo on the hosted flow** — its sample seeding would prune the user-scoped corpus and it adds a model-dependent action to the surface; the demo moves to a separate session-scoped flow or is dropped (§4.3).

**Deepening opportunities** (follow-ups via `fsd:improve-codebase-architecture`, not this spec): none new in the lab. The FIX-813 spec already flagged `resource-tools.ts` `tryMatchPath` duplication and the `CLAUDE.md` `ref.name`→`ref.path` doc bug; not restated here.

No matching entry in `docs/internal/out-of-scope/`; nothing here re-litigates a prior rejection.

## 11. Open Questions & Decision Records

### Decisions recorded by this spec

- **Deployment posture: standalone `serve()` primary, Vercel alternative.** The "standalone server" the issue's prerequisite gestured at already exists as `@flow-state-dev/node` `serve()` (FIX-712), so no package is built. Because the appeal is "stand up the flows without an app wrapper," `serve()` on a long-lived host (Railway/Render/Fly/container) is the primary path — no Next.js/React, always-warm, the natural home for an always-on personal wiki. The Vercel serverless posture (thin Next.js handler) is retained as a documented alternative; stateless MCP and the external Postgres store work on either. This reframes the issue's earlier "Vercel" settled direction. (§3.2, §4.6)
- **Per-user isolation (issue open-question): resolved — user scope is sufficient.** `scope: "user"` partitions content/state/edges by principal (`scope_id` derives from `userId`); a second key → a second principal → an isolated corpus. No explicit tenant key. `isolateUserState` left at default (single flow). (§4.5)
- **MCP v1 limits (issue open-question): accepted for v0.** Tools-only (no MCP resources), single-JSON results (no streaming), POST-only (GET/DELETE 405). Fine for synchronous CRUD. (§6, §8)
- **Auth hardening (issue open-question): static bearer is the v0 floor.** A constant-time bearer-secret compare with no `defaultUserId` fallback over the host's TLS. Rotation / per-client keys are deferred to the multi-user follow-up (§8).
- **Concurrency (issue open-question): naive last-write-wins.** No optimistic locking in v0; acceptable for a single-owner wiki. (§4.2, §6)
- **Graduation signal (issue open-question): strengthens, does not trigger.** This is a second consumer of the MCP transport and the KB capability, but OKF is still v0.1 and the capability is still incubated, so FIX-813 graduation (Storyteller + OKF past v0.1) is not yet met. Surfaced for the owner.

1. **Search/grep action wiring.** Expose `nav.searchResources` / `nav.grepResourceContent` **directly as actions** (returns scope-qualified uris; zero duplication; honors decision #4) vs. wrap them in id-returning handlers. *Recommendation:* direct reuse; normalize uri→id on all id-taking actions via a shared `conceptIdFromUri` helper (§4.3).
