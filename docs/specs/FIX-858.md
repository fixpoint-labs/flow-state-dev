# FIX-858: App-owned data on the resource surface — read/search projection (external/DB-backed collections) — Implementation Spec

> **Linear issue:** [FIX-858](https://linear.app/fixpoint-labs/issue/FIX-858/app-owned-data-cant-appear-on-the-resource-surface-without-being)
> **Status:** In Spec Review · **Category:** Design / Enhancement · **Size:** Large (multi-PR)

## 1. TLDR

**Plain-language summary.** Today, for an AI agent or a live screen to see an app's own data — a portfolio, a task list, customer records — that data has to be *copied* into the framework's storage first, which then drifts out of date. This change lets an app point the framework at a table or API it already owns. The agent can read and search it, and the screen can show it, all from one definition, while the app's database stays the single source of truth. The framework never holds a copy; it re-asks the app for the truth each time it reads. When the app's data changes, the app can tell the framework so an open screen refreshes and any follow-on processing runs.

**Technical statement.** Add a dedicated `defineExternalResourceCollection` definer whose instances' reads and searches delegate to app-supplied `read` / `search` functions (querying the app's own engine) instead of the framework's `ResourceStateStore`. It shares the collection runtime core (`ResourceCollectionRef` addressing, agent tools, client projection, `reactTo`) but is **read-only and lazy by type** — the caveats are structural, not build-time guards. Add a change-signal path so an app event refreshes an active projection and/or dispatches a flow.

**Why a new definer (not a `backing?` flag).** An app-owned source of truth is always a *set* (a table, an endpoint returning rows) under one schema — i.e. a collection, never a single resource. A purpose-built definer types the read-only / lazy / search-required constraints into the surface (no `writable`/`edges`/`prefetchMode`/`maxInstances` fields to reject), instead of bolting an optional `backing?` onto `defineResource` / `defineResourceCollection` and policing ~6 invalid combinations. The general resource types stay untouched.

**Deliverables**

- **Core (`@flow-state-dev/core`):**
  - Add `defineExternalResourceCollection(config)` and the `ExternalResourceCollectionConfig`, `ExternalResourceContext`, `ResourceQuery`, `ResourceSearchResult`, `ExternalRecordHit` types in `packages/core/src/types/` (new `external-resource-collection.ts`, sharing the collection core in `resource-collection.ts`).
  - Emit a `DefinedResourceCollection` variant branded `external` (with a read-only `ExternalResourceCollectionRef`), so the existing flow-merge / addressing / tool / projection machinery treats it as a collection.
  - Route the agent search tools (`searchResources`, `grepResourceContent`, `globResources`) to the external collection's `search` (via an engine-wired ref method); skip external collections in the CRUD `resourceTools()`.
- **Engine (`@flow-state-dev/engine`):**
  - Virtualize the read path in `createScopeResourceRegistry` and the client-route read helpers (`buildResourceSnapshot`, content-endpoint `getPersistedData`) so external-collection `get` / `list` resolve through `read` / `search`.
  - Add a `notifyResourceChanged(...)` host helper + a `resource-change` inbound entry that re-reads and fires the existing `onResourceChanged` seam with a real delta for a target active session.
- **Docs:** new `apps/docs/docs/resources/external-collections.md`; extend `resources/overview.md`, `resources/storage.md`, `resources/collections.md`, `packages/core/README.md`, `packages/engine/README.md`, the two resource architecture docs; one `sidebars.ts` insertion.

**Size: Large.** Split as three PRs in order: **PR1** the definer + read projection, **PR2** search/list pushdown, **PR3** change-awareness. Docs ship with the PR that introduces the surface they document.

## 2. Overview

A *resource* is the framework's uniform interface over a piece of state: agent-facing (auto-derived read/search tools) and client-facing (projected `clientData`, live `resource_change` streaming, generative-UI binding, `reactTo`) at once. But a resource's state/content are bound to scope storage (`ResourceStateStore` / `ContentStore`), so app-owned data only reaches that surface by being **copied into the store** — which FIX-772 deliberately moved away from for relational domain data (trading-desk positions now live in Postgres, read via a bespoke repository + a parallel HTTP route, invisible to the resource pipeline).

This spec adds **external resource collections**: a collection whose instances' reads and searches delegate to app-provided `read` / `search` functions over the app's own query engine. The app's store stays the source of truth; the framework re-queries on read (read-through), so there is no copy and no staleness. An external collection inherits the whole collection surface — agent tools, client projection, template-rendered MD, `reactTo` — from one definition, as a read-through view. Scope is **read/search projection + change-awareness**; agent-initiated create/update/delete is structurally excluded (the type has no mutators).

## 3. Background & Research

### 3.1 How the codebase solves adjacent problems today

- **The registry already injects its read seams.** `createScopeResourceRegistry` (`packages/engine/src/context/resource-registry.ts`) is constructed with `readResources`, `readResourceContent`, `persistResourceKey`, `persistResourceContentKey`, `onResourceChanged`, and a `lazyLoad` accessor (`getInstance(key)`, `getByPrefix(prefix)`). The store is reached *only* through these injected functions — the virtualization point.
- **Lazy collections already read through on access.** `prefetchMode: 'lazy'` collections defer loading to `lazyLoad.getInstance` / `getByPrefix`, share the single-flight map, and never bulk-load. An external collection is the same access shape with the loader pointed at the app's `read` / `search` — so the async-accessor / sync-`.state` contract already holds (instances resolve through `await get(key)`; there is no eager-single special case to invent).
- **Content rendering and client projection are state-driven.** `readContent()` renders the template against `state`; `resolveClientProjection` (`expose`/`exclude`/`data`) projects it; `onResourceChanged` drives the `resource_change` SSE delta + the in-session reactive dispatcher (FIX-739/751/843). If the hook produces `state`, both surfaces work unchanged.
- **Inbound transports already turn an external event into a dispatch.** `InboundTransportAdapter` → `InboundRequestEnvelope` carries a trusted `source` and namespaced `metadata`; `resolveActionCore` reads an event-addressed coordinate gated on `source`. An app change event can already dispatch a flow directly.
- **Definer-per-shape is the established convention.** `defineResource` vs `defineResourceCollection` are already distinct definers that share a runtime core (`ResourceRef` / collection accessors, the same `ResourceStateStore`). Adding `defineExternalResourceCollection` as a third definer over the same collection core matches that convention rather than overloading an existing config with a mode flag.

### 3.2 Industry research

- **MCP Resources (closest analog).** MCP exposes server-owned data with `resources/read { uri }`, `resources/templates/list` (RFC 6570 URI templates for dynamic addressing), and a change channel: `resources/subscribe { uri }` → `notifications/resources/updated { uri }` (URI only; the client re-reads) plus `notifications/resources/list_changed` (membership). Adopted: notification-carries-identity-not-content forces read-through; "content updated" vs "set changed" are distinct; templated addressing avoids enumerating rows (our `pattern`). ([MCP Resources spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/resources), [RFC 6570](https://datatracker.ietf.org/doc/html/rfc6570))
- **Apollo `RESTDataSource` (the hook contract).** A stateless framework delegates fetching to per-request data sources with lifecycle hooks (`willSendRequest` to inject trusted identity, `cacheKeyFor` on the query, `cacheOptionsFor` for TTL). Informs `ExternalResourceContext` (trusted `userId`/scope/tenant passed in — BP-031) and the read-through dedup we already get from the single-flight map. ([Apollo data sources](https://www.apollographql.com/docs/apollo-server/data/fetching-data), [datasource-rest](https://github.com/apollographql/datasource-rest))
- **Read-through cache + CDC invalidation.** Because we read-through rather than materialize, we need only the invalidation/notification half. "Row X changed" distills to `{ op, key→uri, ts, before?, after? }` — `op=u` ≈ `updated`, `op=c|d` ≈ `list_changed`. ([Debezium: cache invalidation via CDC](https://debezium.io/blog/2018/12/05/automating-cache-invalidation-with-change-data-capture/))
- **Portable query pushdown.** PostgREST flat params → OData `$filter`/`$search` → normalized JSON `where` AST (Prisma/Drizzle). `$search` (free text) separate from `$filter` (structured) matches our READ/SEARCH split. Minimal closed shape now; richer AST + semantic search deferred to FIX-833/142. ([OData query options](https://learn.microsoft.com/en-us/odata/concepts/queryoptions-overview), [PostgREST](https://docs.postgrest.org/en/v12/references/api/tables_views.html))

### 3.3 Why this approach (over alternatives)

- **A dedicated definer over the collection core, not a `backing?` field, not a store adapter.** A `backing?` flag on the general configs only makes sense in one narrow combination and needs ~6 "build error if combined with `writable`/`edges`/eager/`llmWritable`/no-`search`" guards — a smell that the field is on the wrong type. A store adapter is global and owns writes. A purpose-built definer types the constraints (no mutator/eager/edges fields exist) and keeps the general resource types untouched. Rejected both.
- **Collection-only (no single-resource backing).** An app source of truth is a set. A lone app-owned object is a degenerate 1-row case, served by a 1-instance external collection or a plain handler/`contextFn` — not worth a parallel single-resource surface. Cutting it is a scope reduction (BP-038).
- **Read-through, not a materialized mirror.** The mirror-into-resources hack (dual-write + staleness + invalidation fight) is what the issue removes. Read-through re-queries the truth — no copy, no FIX-772 regression.
- **Reuse the collection runtime core.** Addressing, tools, projection, and `reactTo` are identical to a normal collection; only the read seam differs. Honors BP-028 (fix at the owning layer) and BP-038 (build the least).

### 3.4 Key Decisions & Ramifications (top 5)

1. **A dedicated `defineExternalResourceCollection` definer that shares the collection runtime core — not a `backing?` field on the general definers, not a virtual store adapter.** *Ramification:* the read-only / lazy / search-required constraints are typed into the config (the fields that would be invalid simply don't exist), so the validation table collapses and `ResourceConfig`/`ResourceCollectionConfig` stay untouched. Locks in "external collections are read-only this slice"; a future write-through would be a deliberate addition to *this* definer.
2. **Collection-only; no single-resource backing.** *Alternative rejected:* a parallel `defineExternalResource`. *Ramification:* one app-owned object is modeled as a 1-instance external collection (or a handler/`contextFn`). Removes the entire async-`read`-vs-sync-`.state` problem for singles — instances always resolve through the already-async `get`/`list`.
3. **Read-through; external collections are lazy by construction.** *Alternative rejected:* a materialized mirror in `ResourceStateStore`. *Ramification:* no staleness within reads, no FIX-772 regression, at the cost of a hook call per read (deduped per request via the single-flight map; per-request memoization allowed, cross-request caching/TTL deferred). No `maxInstances`/`eviction`/`prefetchMode` knobs — the source is unbounded and always read-through.
4. **Minimal portable `ResourceQuery` pushed to `search`; the agent search tools route to it via an engine-wired ref method.** *Alternative rejected:* a full OData/AST grammar now, and core reaching into engine context. *Ramification:* no in-memory enumeration (BP-033). The richer filter AST + semantic search land with FIX-833/FIX-142, which extend this type.
5. **Change-awareness leans on the existing inbound-transport dispatch.** *Alternative rejected:* a new sessionless reactive subsystem. *Ramification:* path A (app event → dispatch an action) is the only path for idle sessions; path B (`resource-change` → re-read + real delta → `onResourceChanged`) refreshes a session only while it has an active live stream. Sessionless `reactTo` and an idle-session push channel are deferred.

## 4. Technical Design

### 4.1 Architecture

| Layer | Package | Change |
| -- | -- | -- |
| New definer + types | `@flow-state-dev/core` | `defineExternalResourceCollection`, `ExternalResourceCollectionConfig`, read-only `ExternalResourceCollectionRef`, the query/hit/context types; shares the collection core |
| Read virtualization + change signal | `@flow-state-dev/engine` | registry + client-route read redirect for external collections, `notifyResourceChanged`, `resource-change` inbound entry |
| Consumers (unchanged contracts) | tools / client / react | content rendering, `clientData` snapshot, `resource_change` SSE, `reactTo` all reused; CRUD tools skip external collections |

### 4.2 API surface

New definer + config (core), `read` / `search` are first-class required members — the config *is* the backing:

```ts
/** Define a read-only collection whose instances are resolved from an app-owned store
 *  (SQL table, API). Shares the collection runtime core; read-only and lazy by type. */
export function defineExternalResourceCollection<TStateSchema extends ZodTypeAny>(
  config: ExternalResourceCollectionConfig<TStateSchema>,
): DefinedResourceCollection</* external */ z.infer<TStateSchema>>;

export type ExternalResourceCollectionConfig<TStateSchema extends ZodTypeAny> = {
  pattern: string;            // maps app rows → instance keys/URIs, e.g. "positions/*" or "[symbol]/position"
  scope: ResourceScope;       // session | user | org — routes scopeId into the read/search context
  stateSchema: TStateSchema;  // the shape of one record (all instances share it)

  /** Resolve one record by its within-scope key. `null` = no such record. REQUIRED. */
  read(args: { key: string; ctx: ExternalResourceContext }): Promise<z.infer<TStateSchema> | null>;
  /** Resolve a filtered/searched page, pushing the query DOWN to the app engine
   *  (never enumerate-in-memory). REQUIRED — list/glob/grep/search all route here. */
  search(args: { query: ResourceQuery; ctx: ExternalResourceContext }): Promise<ResourceSearchResult<z.infer<TStateSchema>>>;

  // Same opt-in surfaces as a normal collection — content rendering, client projection, reactivity:
  contentTemplate?: ResourceTemplate | string | AnchoredPath;
  render?: (content: string, state: JsonObject) => string | Promise<string>;
  llmReadable?: boolean;      // gate the read/search tools (default off)
  client?: ResourceCollectionClientConfig<z.infer<TStateSchema>>; // the COLLECTION client config (item-state + content),
                             // NOT the single-resource one — but its `content.create/update/delete` flags are rejected (read-only)
  reactTo?: ReactiveBindings<z.infer<TStateSchema>>; // created / stateUpdated / deleted / contentUpdated
  metadata?: Record<string, unknown>;

  // NOTE: no `writable` / `llmWritable` / `edges` / `prefetchMode` / `maxInstances` / `eviction` —
  // read-only, lazy, and unbounded are structural, not flags.
};

/** Page of hits + the app's opaque cursor for the next page (echoed into ResourceQuery.cursor). */
export type ResourceSearchResult<TState extends JsonObject = JsonObject> = {
  hits: ExternalRecordHit<TState>[];
  nextCursor?: string;        // omit when exhausted
};

/** Minimal portable query. Richer filter AST + semantic search deferred (FIX-833/FIX-142). */
export type ResourceQuery = {
  search?: string;                    // free-text relevance (lexical now; semantic later) — maps to the tools' query/grep pattern
  prefix?: string;                    // path-boundary prefix — same semantics as the existing search tools
  filter?: Record<string, JsonValue>; // equality map — the only structured predicate this slice
  limit?: number;
  cursor?: string;                    // opaque pagination cursor echoed back by the app
};

export type ExternalRecordHit<TState extends JsonObject = JsonObject> = {
  key: string;   // within-scope key/path; becomes the instance path/uri
  state: TState;
};

/** Trusted, server-derived context handed to read/search (BP-031: never caller-controllable). */
export type ExternalResourceContext = {
  scope: ResourceScope;  // session | user | org (never the transient "request" scope)
  scopeId: string;       // the resolved sessionId / userId / orgId
  userId: string;        // always populated — the server-derived owner; never caller input
  orgId?: string;
  tenantId?: string;     // trusted tenant coordinate (ScopeIdentity) for multi-tenant — so the hook
                         // scopes its own query to the same tenant namespace the framework uses
  flowKind: string;
  signal?: AbortSignal;  // request abort propagation
};
```

**Runtime ref is read-only by type.** `defineExternalResourceCollection` returns a `DefinedResourceCollection` branded `external`, accessed at runtime as an `ExternalResourceCollectionRef<TState>` — the read subset of the collection API only:

```ts
interface ExternalResourceCollectionRef<TState> {
  get(key: string | Record<string, string>): Promise<ExternalResourceRef<TState>>;        // throws if absent
  getOptional(key: string | Record<string, string>): Promise<ExternalResourceRef<TState> | undefined>;
  // Paged result — the source is unbounded, so list returns a page + cursor, NOT a bare array.
  list(query?: string | ResourceQuery): Promise<ExternalResourcePage<TState>>;             // string = prefix; object = pushdown
  count(): Promise<number>;                                                                 // best-effort (see edge cases)
  // No create / getOrCreate / upsert / delete — mutators don't exist on the type.
}

/** A page of resolved instances plus the cursor to fetch the next one. */
export type ExternalResourcePage<TState extends JsonObject = JsonObject> = {
  items: ExternalResourceRef<TState>[];
  nextCursor?: string;   // pass back as ResourceQuery.cursor; omit when exhausted
};
```

Each `ExternalResourceRef<TState>` is a read-only `ResourceRef` (`path`, `uri`, sync `state`, `readContent()`, `readContentRaw()`) — no `patchState`/`setState`/`updateState`/`writeContent`. `list` returns a **paged** `{ items, nextCursor? }` (not a bare array) because the backing source is unbounded and the cursor must have somewhere to live.

**Read-only across every surface, not just the ref.** Three write paths must all be closed for an external collection, or the mirror the feature avoids creeps back in:
- *Block/ref mutators* — don't exist on the type.
- *Agent tools* — the CRUD `resourceTools()` skip external collections, and the content-write tool is gated by `llmWritable`, which external collections never declare.
- *Client HTTP routes* — `client.content.create` / `update` / `delete` are a **build-time error** on an external collection's `client` config, and the `POST`/`PATCH`/`DELETE` resource routes throw for an external collection (defense in depth) — otherwise a client could still write state/content rows into FSD storage.

**Change-signal helper (engine).**

```ts
/** Notify the framework that an app-owned record behind an external collection changed. */
export type ResourceChangeNotice = {
  flowKind: string;
  scope: ResourceScope;   // session | user | org — never the transient "request" scope
  scopeId: string;
  tenantId?: string;      // trusted tenant coordinate; disambiguates a shared sessionId/scopeId
  accessor: string;       // the collection ACCESSOR name (key in flow.resources[...]), NOT the storage ref —
                          // resolution is by accessor (`findResourceConfig`); accessor ≠ storage ref by design
  key?: string;           // changed instance key; omit to signal a set-level (membership) change
  op: "created" | "updated" | "deleted";
  sessionId: string;      // REQUIRED — path B refreshes ONE named live session. A user/org scopeId maps to many
                          // live sessions, so the caller names the session to refresh; multi-session fan-out is out of scope.
};
```

> **Why `sessionId` is required (not optional).** Path B refreshes a single live session's view. For `scope: "user"` / `"org"`, `scopeId` identifies the user/org, which can have many concurrent sessions — there is no unambiguous stream to update without naming one. So `sessionId` is required on the notice; fanning a user/org change out to every live session is a deliberate non-goal (an app that wants that loops over its own session list, or uses path A per session).

### 4.3 Data flow

**Read (agent or client).**
1. A block reads `await ctx.resources.coll.get(key)` / `.list(query)` (external collections are always accessed through the async collection API — there is no sync single-resource path).
2. The registry sees the `external` brand and calls `read({ key, ctx })` / `search({ query, ctx })` (deduped per request via the single-flight map) instead of `ResourceStateStore` / `lazyLoad`. The result is parsed through `stateSchema` and cached, so the returned instance ref's **synchronous** `state` getter resolves against a filled cache.
3. The resolved `state` feeds the ref: `readContent()` renders the template (agent MD); `client.data`/`expose`/`exclude` project it (client snapshot).

**Search (agent tool).**
1. `searchResources({ query, prefix })` / `grepResourceContent({ pattern, prefix })` / `globResources({ pattern })` run.
2. For external collections the tool calls an **engine-wired `search` method on the ref** (which closes over the resolved `ExternalResourceContext`) instead of enumerating content; store-backed resources enumerate as today. The hook returns `{ hits, nextCursor? }`; `nextCursor` is surfaced (and echoed back as `ResourceQuery.cursor`) so pagination advances — a bare-array return would let a query *consume* a cursor but never *advance*. Results merge into one URI/snippet list.
3. Each `ExternalRecordHit.key` becomes a `uri` (`${scope}/${path}`); the agent can `read` it through the same surface.

**Glob/grep have degraded (not exact) semantics over an external collection.** The closed `ResourceQuery` expresses free-text `search`, a path `prefix`, equality `filter`, and pagination — it cannot represent an arbitrary picomatch glob (`**/react*`) or a content regex (`error\d+`). For store-backed resources `globResources`/`grepResourceContent` keep their exact picomatch/regex semantics. For an external collection they are **best-effort**: the tool passes the raw pattern through as the `search` string (a `prefix` when the glob is a clean path prefix) and the app's `search` interprets it as it sees fit; exact glob/regex matching is not guaranteed (it would require enumerate-then-filter, which the unbounded source forbids). `searchResources` and `list({ filter })` are the precise paths over an external collection; this degradation is documented on the tool and the page, not silent.

**Change (app → framework).**
- *Path A (dispatch a flow directly):* the app posts an event through an inbound transport; an event-addressed action runs and reads the collection fresh. No new runtime. **Only path that works for an idle session.**
- *Path B (refresh an active live session):* the app calls `notifyResourceChanged(notice)`; the host resolves the target session by `accessor`(+`key`,`tenantId`), **re-reads** the affected record via `read`, and fires `onResourceChanged` with a real `ResourceChangeDelta` — `{ state, prevState? }` for `created`/`updated`, a tombstone (`state: null`) for `deleted` — so the reactive dispatcher (which returns early on an absent descriptor) actually runs a declared `reactTo`, and a `resource_change` item streams so a connected client refetches.

**Three hard constraints PR3 must honor (all surfaced in spec review):**
1. **`reactTo` needs a real `ResourceChangeDelta`, not an empty signal** — the dispatcher returns early when the change descriptor is absent, so `notifyResourceChanged` must re-read and pass a real delta (with a tombstone for deletes).
2. **The `resource_change` SSE only exists during an active request** (`createExecutionContext` pulls `emitResourceChange` from the request `response`). Path B refreshes a session **only while it has an active request/live stream**; an idle session being merely viewed uses path A. A session-level pub/sub push channel for idle sessions is out of scope.
3. **An app event can't reach the live request context by session lookup alone.** `ActiveRequestEntry` stores only serializable metadata, not the live `ResponseEmitter` / reactive-dispatch context — so `notifyResourceChanged` cannot fire `onResourceChanged` just by finding an active session. PR3 adds a small **in-process active-context registry** (`sessionId → { emitter, dispatch }`) that the engine populates when a request goes live and clears when it settles; the helper looks the target session up there and no-ops (warn) when absent. This is in-process / single-instance (matching the FIX-837 concurrency v1 note); cross-worker delivery is out of scope.

### 4.4 State management

No new persisted state. External collections hold no `ResourceStateStore` / `ContentStore` state — instance state is transient per-request (hook result). The ref type has no mutators, so there is no write path through the resource surface. `edges` are unsupported (they require persisted graph state and the field doesn't exist on the config).

### 4.5 Error handling

| Case | Behavior |
| -- | -- |
| `read` throws | Propagates as the read's rejection (same as a store read failure). `signal` abort → reject with the abort reason. |
| `read` returns `null` | `get` throws not-found; `getOptional` returns `undefined`. |
| `read` / `search` returns a record failing `stateSchema` | Validated through `stateSchema` before any consumer (template `render`, `client.data`, `reactTo`) sees it — same normalization store-backed reads get. A `get`/`read` failure **throws** (fatal to the read); a `search` hit is **dropped + logged** (don't poison the page). Never feed unvalidated app data into projection/render. |
| Mutation attempted (ref / agent tool / client route) | Closed on all three surfaces: the ref type has no mutators; the config has no `writable`/`llmWritable` and rejects `client.content.create/update/delete` at build time; the CRUD `resourceTools()` skip external collections; and the `POST`/`PATCH`/`DELETE` HTTP resource routes throw for an external collection (defense in depth). No write reaches FSD storage. |
| Invalid `pattern`, or missing `read`/`search` | `read`/`search` are required config members (compile error if omitted). Pattern validity reuses the collection pattern rules (build-time error). |
| `notifyResourceChanged` for an unknown/idle/closed session | No-op with a logged warning (best-effort, like other transient client signals). |

**Error taxonomy.** Hook exceptions are *fatal to the read* (no framework retry — retry/caching is the app's concern). Schema-invalid search hits are *non-fatal* (dropped + logged). Unknown/idle-session notifications are *non-fatal* (no-op + warn).

## 5. Implementation Sequence

> Discipline: Enhancement → **`fsd:tdd`** (red-green-refactor, tracer-bullet slices). Each PR is independently shippable.

### PR1 — Definer + read projection
1. **Definer + types.** Add `defineExternalResourceCollection`, `ExternalResourceCollectionConfig`, `ExternalResourceContext`, `ResourceQuery`, `ResourceSearchResult`, `ExternalRecordHit` and the read-only `ExternalResourceCollectionRef` in a new `packages/core/src/types/external-resource-collection.ts`, sharing the collection core (pattern resolution, declaration/merge metadata) from `resource-collection.ts`. The definer emits a `DefinedResourceCollection` branded `external`. *Test:* a flow accepts an external collection; flow-merge and collision detection treat it as a collection.
2. **Validation (minimal — most is structural).** Reuse collection pattern validation; `read`/`search` required by the type. Confirm the brand carries through flow-merge. *Test:* a missing `search` is a compile error (typed) / a malformed pattern throws at build.
3. **Registry options + read redirect.** Extend `createScopeResourceRegistry`'s options to carry `userId`, `orgId`, `tenantId`, `flowKind`, and the request `signal` (thread from `createExecutionContext`) to build `ExternalResourceContext`. For an `external` collection, resolve `get`/`getInstance` through `read` and `list` through `search` (schema-validated, single-flight-deduped); expose the read-only ref. *Test:* `get(key)`/`list()` on an external collection reflect the hook; `getOptional` returns `undefined` on `null`; the ref has no mutators.
4. **Wire backing into *every* store-reading client route (real code, not verify-only).** The public client surfaces read the stores directly, not via the registry — so a single shared backing resolver must feed all of them, or they project defaults/null/empty for an external collection. The full set:
   - `/state` resource snapshot — `buildResourceSnapshot` (`route-utils.ts`).
   - **Scope-level `clientData`** — `createScopeResources()` / `computeClientData` in `state-routes.ts`, since a `session/user/org` `client.data` function may read `resources.<external>.state`.
   - **Collection list / item-state routes** — `handleListCollectionState` / `handleGetCollectionItemState` (`resource-routes.ts`); a client `list` of an external collection must page through `search`, not return empty.
   - **Content endpoints** — `getPersistedData` (`resource-routes.ts`).
   Also reject `client.content.create/update/delete` on an external collection at build time and make the `POST`/`PATCH`/`DELETE` routes throw for one. *Test:* snapshot, scope `clientData`, client `list`, and the content endpoint all project hook state (not defaults) for an external collection; client create/update/delete are rejected.

### PR2 — Search / list pushdown (depends on PR1)
5. **`list(query)` pushdown — paged result.** `ExternalResourceCollectionRef.list(query?: string | ResourceQuery)` returns a paged `{ items, nextCursor? }` (not a bare array), routing object queries to `search` and mapping `hits` → refs. *Test:* `list({ filter })` returns only hook-matched instances; no in-memory enumeration (assert the hook received the query); the returned `nextCursor` round-trips into `list({ cursor })`.
6. **Agent tool routing — engine-wired search, no enumeration leak.** `resourceSearchTools()` lives in `core`, but `ExternalResourceContext` needs `flowKind`/`tenantId`, which exist only on the engine's `ExecutionContext`. Expose the search behind an **engine-wired `search` method on the ref** (closing over the resolved context); the core tools call it when present, with the glob/grep degradation from §4.3. Crucially, **every tool path that would otherwise enumerate must route through `search` or skip external collections** — including `readResourceContentTool()`'s no-`uri` discovery mode, which today calls `collectReadableResources()` → `list()` over every `llmReadable` collection (it must page through `search` with a default limit, not bulk-list). *Test:* `searchResources`/`grepResourceContent`/`globResources` and the read tool's discovery mode over an external collection never enumerate; results carry correct URIs; store-backed resources coexist; `core` builds without importing engine context types.

### PR3 — Change-awareness (depends on PR1; PR2 optional)
7. **In-process active-context registry + `notifyResourceChanged` helper + `resource-change` entry.** First add the in-process registry (`sessionId → { emitter, dispatch }`) the engine fills when a request goes live and clears when it settles (per §4.3 constraint 3) — `ActiveRequestEntry` holds only serializable metadata, so the live emitter/dispatch can't be reached by session lookup alone. Then the helper: take the (required) `sessionId`, look up the live context, **re-read** the record via `read`, and fire `onResourceChanged` with a real `ResourceChangeDelta` (tombstone for `deleted`) so the dispatcher runs `reactTo` and a `resource_change` streams. No live context (idle / settled / cross-worker) → no-op + warn. *Test:* with an active session it streams a `resource_change` and fires a declared `reactTo`; a `deleted` notice streams a tombstone and fires `reactTo.deleted`; an idle/unknown session no-ops; a user/org notice without `sessionId` is rejected.
8. **Document path A.** The "inbound event → dispatch a flow directly" recipe (no new code; uses the inbound-transport contract). *Test (goal check):* see §7.

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
| -- | -- |
| Two reads of the same instance key in one request | Single-flight dedupe → one `read`; both see the same result. |
| `count()` on an external collection | Best-effort: derived from the last `search`/`list` page, or a `search` round-trip; documented as not exact (mirrors lazy-collection `count`). |
| External collection in the client snapshot | The snapshot does **not** enumerate the app source; it contributes only instances already loaded this request (typically none). Clients discover instances via the search tools / a `list` call, then fetch content per URI. Documented explicitly. |
| `prefix` on `search` | Passed through verbatim; the app interprets it (path-boundary semantics recommended to match store-backed tools). |
| Change signal arrives mid-request | Read-through means the next read re-queries; per-request memoization may serve a slightly stale value for the rest of that request (read-your-request-start consistency). |
| `op: "deleted"` on path B | Re-read yields absent → streams a tombstone `resource_change` so a live client drops the instance; fires `reactTo.deleted`. |
| Abort during a hook call | `ctx.signal` aborts; the hook should honor it; the read rejects with the abort reason. |

## 8. Non-Goals

- **Agent-initiated create/update/delete.** Structurally excluded (the ref has no mutators). The agent still mutates app data via handlers; the app's *own* writes are observed (change-awareness), the agent's writes through the resource surface are not. Re-opening it would touch FIX-772 invalidation + FIX-854 atomicity.
- **A single-resource external variant (`defineExternalResource`).** Dropped — an app source of truth is a set; a lone object is a 1-instance external collection or a handler/`contextFn`.
- **Semantic / vector search and a rich filter AST.** `ResourceQuery` is intentionally minimal; semantic retrieval and a full predicate grammar land with **FIX-142** and **FIX-833**, which extend this type.
- **FSD owning an ORM or being the app's data store.** This is a projection/view seam; the host owns storage (FIX-772, host-owns-storage). See `docs/internal/out-of-scope/` (add an entry if not present).
- **Cross-request caching / TTL of the projection.** Per-request memoization only; a `cacheable`/TTL policy is a fast-follow.
- **Sessionless `reactTo` and an idle-session pub/sub push channel.** Path B is active-session only; idle sessions use path A.
- **Cross-worker / multi-instance change delivery, and multi-session fan-out.** The active-context registry is in-process / single-instance (matching the FIX-837 concurrency v1 note); a notice for a session on another worker no-ops. Fanning a user/org change out to every live session is also out of scope — `notifyResourceChanged` names one `sessionId`.
- *Deepening flag:* the trading-desk currently exposes app data through a parallel HTTP route (`labs/trading-desk/app/api/portfolio/accounts/route.ts`) **and** the repository pattern, bypassing the resource surface — once this lands, that parallel read path is a consolidation candidate; follow up via `fsd:improve-codebase-architecture`.
