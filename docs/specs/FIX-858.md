# FIX-858: App-owned data on the resource surface — read/search projection (API/DB-backed resources) — Implementation Spec

> **Linear issue:** [FIX-858](https://linear.app/fixpoint-labs/issue/FIX-858/app-owned-data-cant-appear-on-the-resource-surface-without-being)
> **Status:** In Spec Review · **Category:** Design / Enhancement · **Size:** Large (multi-PR)

## 1. TLDR

**Plain-language summary.** Today, for an AI agent or a live screen to see an app's own data — a portfolio, a task list, customer records — that data has to be *copied* into the framework's storage first, which then drifts out of date. This change lets an app point the framework at data it already owns (a database table, an internal API). The agent can read and search it, and the screen can show it, all from one definition, while the app's database stays the single source of truth. The framework never holds a copy; it re-asks the app for the truth each time it reads. When the app's data changes, the app can tell the framework so an open screen refreshes and any follow-on processing runs.

**Technical statement.** Add a `backing` hook to `defineResource` / `defineResourceCollection` that delegates a resource's *reads and searches* to an app-supplied function (querying the app's own engine), instead of the framework's `ResourceStateStore` — virtualizing the existing scope-resource-registry read seam — and add a change-signal path so an app event refreshes the projection and/or dispatches a flow.

**Deliverables**

- **Core (`@flow-state-dev/core`):**
  - Add `backing?: ResourceBacking<TState>` to `ResourceConfig` and `ResourceCollectionConfig`, plus the `ResourceBacking`, `ResourceQuery`, `ResourceBackingHit`, `ResourceBackingContext` types, in `packages/core/src/types/resource.ts` and `resource-collection.ts`.
  - Add build-time validation for `backing` (read-only; backed collections are lazy and must declare `backing.search`) in the two definers.
  - Route the agent search tools (`searchResources`, `grepResourceContent`, `globResources`) to `backing.search` for backed resources in `packages/core/src/tools/resource-search-tools.ts`.
- **Engine (`@flow-state-dev/engine`):**
  - Virtualize the read path in `createScopeResourceRegistry` so backed resources resolve `state` / `get` / `list` through the hook (`packages/engine/src/context/resource-registry.ts`).
  - Add a `notifyResourceChanged(...)` host helper + a `resource-change` inbound entry that fires the existing `onResourceChanged` seam for a target session (`packages/engine/src/context/` + inbound-transport surface).
- **Docs:** new `apps/docs/docs/resources/api-backed.md`; extend `resources/overview.md`, `resources/storage.md`, `packages/core/README.md`, `packages/engine/README.md`; one `sidebars.ts` insertion.

**Size: Large.** Split as three PRs in order: **PR1** read projection (single + collection, read-through, client/agent surfaces), **PR2** search/list pushdown, **PR3** change-awareness. Docs ship with the PR that introduces the surface they document.

## 2. Overview

A *resource* is the framework's uniform interface over a piece of state: it is agent-facing (auto-derived, flag-gated read/search tools) and client-facing (projected `clientData`, live `resource_change` streaming, generative-UI binding, `reactTo`) at once. But a resource's state and content are bound to scope storage (`ResourceStateStore` / `ContentStore`). App-owned/domain data therefore only reaches that surface by being **copied into the store**, which FIX-772 deliberately moved *away from* for relational domain data (trading-desk positions now live in Postgres, read via a bespoke repository + a parallel HTTP route, invisible to the resource pipeline).

This spec adds a **backing hook**: a resource whose reads and searches delegate to an app-provided function over the app's own query engine. The app's store stays the source of truth; the framework re-queries the truth on read (read-through), so there is no copy and no staleness. Being a resource then buys app data the whole surface — agent tools, client projection, template-rendered MD, `reactTo` — from one definition. Scope is **read/search projection + change-awareness**; agent-initiated create/update/delete *through* the resource is explicitly deferred (Non-Goals).

## 3. Background & Research

### 3.1 How the codebase solves adjacent problems today

- **The registry already injects its read/write seams.** `createScopeResourceRegistry` (`packages/engine/src/context/resource-registry.ts`) is constructed with `readResources`, `readResourceContent`, `persistResourceKey`, `persistResourceContentKey`, `onResourceChanged`, and a `lazyLoad` accessor (`getInstance(key)`, `getByPrefix(prefix)`). The store is reached *only* through these injected functions. This is the virtualization point: a backed resource overrides its read path to call the hook rather than `ResourceStateStore`.
- **Lazy collections already read through on access.** `prefetchMode: 'lazy'` collections defer loading to `lazyLoad.getInstance` / `getByPrefix`, share the single-flight map, and never bulk-load. An API-backed collection is the same shape with the loader pointed at the app hook.
- **Content rendering is read-time and state-driven.** `readContent()` renders `contentTemplate` / `render` against live `state` on every read (FIX-669, deterministic LiquidJS). If the hook produces `state`, MD content for the agent works unchanged.
- **Client projection is state-driven.** `resolveClientProjection` (`expose` / `exclude` / `data`) projects `state` into the snapshot; `onResourceChanged` drives the `resource_change` SSE delta and the in-session reactive dispatcher (FIX-739/751/843). If the hook produces `state`, the client surface works unchanged.
- **Inbound transports already turn an external event into a dispatch.** The `InboundTransportAdapter` contract (HTTP/MCP/webhook/scheduled) lands every entry point as an `InboundRequestEnvelope` carrying a `source` (trusted, server-set) and namespaced `metadata`; `resolveActionCore` reads an event-addressed coordinate gated on `source`. An app change event can already dispatch a flow directly through this contract.
- **Capability-factory injection is the established "app supplies a function" shape.** `defineCapability` / `createXCapability`, store-adapter factories, and tool `execute` functions all follow "factory accepts options, app supplies behavior, framework calls it at runtime." The backing hook mirrors this at the resource-definition level (per-resource), *not* as a store adapter (global).

### 3.2 Industry research

- **MCP Resources (closest analog).** MCP exposes server-owned data to an agent host with `resources/read { uri }`, `resources/templates/list` (RFC 6570 URI templates for dynamic/parameterized addressing), and a change channel: `resources/subscribe { uri }` → `notifications/resources/updated { uri }` (carries *only* the URI; the client re-reads) plus `notifications/resources/list_changed` (membership change). Capability negotiation makes `subscribe` and `listChanged` independently optional. Takeaways adopted here: notification-carries-identity-not-content forces read-through and avoids pushing stale snapshots; "content updated" vs "set changed" are distinct; templated addressing avoids enumerating rows. ([MCP Resources spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/resources), [RFC 6570](https://datatracker.ietf.org/doc/html/rfc6570))
- **Apollo `RESTDataSource` (the hook contract).** A stateless framework delegates fetching to per-request data-source objects with lifecycle hooks (`willSendRequest` to inject trusted identity/scope, `cacheKeyFor` keyed on the *query*, `cacheOptionsFor` for TTL, `didEncounterError`). Policy (cache/dedup) lives in the framework; the app implements only `fetch`. Informs the `ResourceBackingContext` (trusted `userId`/scope passed in — BP-031) and the read-through/dedup behavior we already get from the registry's single-flight map. ([Apollo data sources](https://www.apollographql.com/docs/apollo-server/data/fetching-data), [datasource-rest](https://github.com/apollographql/datasource-rest))
- **Read-through cache + CDC invalidation.** A view over a source of truth is invalidated by change events (push) with TTL as a backstop. Because we read-through (re-query per read) rather than materialize, we need only the *invalidation/notification* half, not a stored view. The distilled "row X changed" event is `{ op: c|u|d, key→uri, ts, before?, after? }` — `op=u` ≈ `updated`, `op=c|d` ≈ `list_changed`; `before/after` optional for the push-projection optimization. ([Debezium: cache invalidation via CDC](https://debezium.io/blog/2018/12/05/automating-cache-invalidation-with-change-data-capture/))
- **Portable query pushdown.** A spectrum from PostgREST-style flat params, to OData `$filter`/`$search`, to a normalized JSON `where` AST (Prisma/Drizzle). `$search` (free text) is deliberately separate from `$filter` (structured predicate) — directly matching our "READ and SEARCH" split, with `search` as the SQL-lexical-now / vector-later channel (FIX-833/142). We adopt a **minimal closed shape** for the first slice and defer a richer filter AST. ([OData query options](https://learn.microsoft.com/en-us/odata/concepts/queryoptions-overview), [PostgREST](https://docs.postgrest.org/en/v12/references/api/tables_views.html))

### 3.3 Why this approach (over alternatives)

- **Per-resource backing hook, not a virtual store adapter.** Store adapters are global (all resources in a scope) and own the write path; backing is per-resource and read-only in this slice. Modeling it as a store would force every resource through the app engine and entangle writes. Rejected.
- **Read-through, not materialized mirror.** The mirror-into-resources hack (dual-write + staleness + invalidation fight) is exactly what the issue removes. Read-through re-queries the truth, so there is no second home for the data and no copy to invalidate (no regression to FIX-772).
- **Reuse the existing registry/tool/reactive seams, add the least surface.** Content rendering, client projection, `onResourceChanged`, and reactive dispatch are untouched; we only redirect the read path and route search to the hook. This honors BP-028 (fix at the owning layer — the registry read seam) and BP-038 (build the least).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Backing is a per-resource hook on the definition (capability-factory style), not a store adapter.** *Alternative rejected:* virtual `ResourceStateStore`. *Ramification:* keeps the write path on the framework store and the read path per-resource; an app can mix store-backed and API-backed resources in one scope. Locks in "backing is read-only" for this slice; a future write-through would extend the same hook, not a store.
2. **Read-through (re-query on read), backed resources are lazy by construction.** *Alternative rejected:* cache the projection in `ResourceStateStore` (a materialized mirror). *Ramification:* no staleness within reads and no FIX-772 regression, at the cost of a hook call per read (mitigated by the registry's per-request single-flight dedupe; per-request memoization is allowed, cross-request caching/TTL is deferred). Forces `prefetchMode: 'lazy'` for backed collections (can't bulk-load an unbounded source) — eager backed collections are a build error.
3. **Search/list pushes a minimal portable `ResourceQuery` to `backing.search`; the agent search tools route to it instead of enumerating.** *Alternative rejected:* a full OData/AST filter grammar now. *Ramification:* backed collections never enumerate-in-memory (BP-033); the closed query shape (`search`, `prefix`, `filter` equality map, `limit`, `cursor`) is easy for apps to map and reject unknowns loudly. The richer filter AST and semantic search land with FIX-833/FIX-142 — this query type is the seam they extend.
4. **Change-awareness has two first-class paths; the first slice leans on the existing inbound-transport dispatch.** *Alternative rejected:* a brand-new sessionless reactive subsystem. *Ramification:* path (A) — app event dispatches an event-addressed action that reads the projection fresh — needs no new runtime (it already works via the inbound contract). Path (B) — a `resource-change` signal that fires `onResourceChanged` for a *target live session* (client `resource_change` + in-session `reactTo`) — is added as a thin helper. Firing `reactTo` with no live session is deferred and flagged (Open Questions): without a session there is no turn to run the reaction in, so that case collapses into path (A).
5. **Backed resources are read-only through the resource surface in this slice (`writable: true` + `backing` is a build error).** *Alternative rejected:* agent CRUD through the resource. *Ramification:* avoids re-opening the FIX-772 view-vs-truth invalidation problem and the FIX-854 cross-record atomicity question; the agent still mutates app data through ordinary handlers. The app's *own* writes are **observed** (change-awareness, in scope); the *agent's* writes through resource CRUD are **deferred**.

## 4. Technical Design

### 4.1 Architecture

| Layer | Package | Change |
| -- | -- | -- |
| Definition + types + validation | `@flow-state-dev/core` | `backing` field, the backing types, definer validation, search-tool routing |
| Read virtualization + change signal | `@flow-state-dev/engine` | registry read-path redirect, `notifyResourceChanged`, `resource-change` inbound entry |
| Consumers (unchanged contracts) | tools / client / react | content rendering, `clientData` snapshot, `resource_change` SSE, `reactTo` all reused as-is |

### 4.2 API surface

Added to `packages/core/src/types/resource.ts` (and re-used by `resource-collection.ts`):

```ts
/** App-supplied read/search delegation for a resource. Read-only in this slice. */
export type ResourceBacking<TState extends JsonObject = JsonObject> = {
  /**
   * Resolve the projected state for one addressed record. `key` is the
   * within-scope path/key (single resource: the canonical key; collection
   * instance: the resolved storage key). Return `null` for "no such record".
   */
  read(args: { key: string; ctx: ResourceBackingContext }): Promise<TState | null>;
  /**
   * Resolve a filtered/searched set, pushing the query DOWN to the app engine
   * (never enumerate-in-memory). REQUIRED for every backed collection (a
   * collection is inherently unbounded, so `list` / glob / grep / search all
   * need a pushdown path). Omit only for a single record-only backing.
   */
  search?(args: { query: ResourceQuery; ctx: ResourceBackingContext }): Promise<ResourceSearchResult<TState>>;
};

/** Page of search hits plus the app's opaque cursor for the next page (echoed back into `ResourceQuery.cursor`). */
export type ResourceSearchResult<TState extends JsonObject = JsonObject> = {
  hits: ResourceBackingHit<TState>[];
  /** Opaque cursor to fetch the next page; omit/undefined when the result set is exhausted. */
  nextCursor?: string;
};

/** Minimal portable query handed to `backing.search`. Richer filter AST + semantic search are deferred (FIX-833/FIX-142). */
export type ResourceQuery = {
  /** Free-text relevance query (lexical now; semantic later). Maps to the search tools' `query` and grep `pattern`. */
  search?: string;
  /** Path-boundary prefix — same semantics as the existing search tools' `prefix`. */
  prefix?: string;
  /** Equality filter map (field → value). The only structured predicate in the first slice. */
  filter?: Record<string, JsonValue>;
  /** Max hits to return. */
  limit?: number;
  /** Opaque pagination cursor echoed back by the app. */
  cursor?: string;
};

export type ResourceBackingHit<TState extends JsonObject = JsonObject> = {
  /** Within-scope key/path identifying the record; becomes the instance `path`/`uri`. */
  key: string;
  state: TState;
};

/** Trusted, server-derived context the framework hands the hook (BP-031: never caller-controllable). */
export type ResourceBackingContext = {
  scope: ResourceScope;      // "session" | "user" | "org" (backed resources never use the transient "request" scope)
  scopeId: string;           // the resolved sessionId / userId / orgId
  userId: string;            // always populated — the session/request owner (server-derived); never caller input
  orgId?: string;
  tenantId?: string;         // the request's trusted tenant coordinate (from ScopeIdentity), when multi-tenant —
                             // so the hook queries its own store with the same tenant namespace the framework uses
  flowKind: string;
  signal?: AbortSignal;      // request abort propagation
};
```

> **Why `tenantId` is in the trusted context.** `ScopeIdentity` tenant-namespaces session/user records and resource state; in a multi-tenant deployment two tenants can share a `sessionId`/`userId`. Passing the framework-resolved `tenantId` lets the hook scope its own query to the same tenant without trusting caller input (BP-031) and without leaking/colliding across tenants.

> **`ResourceScope` vs `ScopeType`.** Resources carry the three-value `ResourceScope` (`session` / `user` / `org`); the engine's broader `ScopeType` also includes a transient `"request"` value that backed resources do not use. The hook context is always one of the three persisted scopes.

> **Registry-wiring task (PR1).** `createScopeResourceRegistry` today receives only `scope` + `scopeId` in its options. Building `ResourceBackingContext` requires threading `userId`, `orgId`, `flowKind`, and the request `signal` into the registry options from the construction site (`createExecutionContext`, where all four are already in scope). Adding those option fields is an explicit PR1 step (see §5 step 3), not assumed pre-existing.

`ResourceConfig` and `ResourceCollectionConfig` each gain:

```ts
  /** Delegate reads/searches to an app store instead of FSD storage (read-only projection). */
  backing?: ResourceBacking<TState>;
```

**Read-only enforcement differs by definer.** A single `ResourceConfig` has a `writable` field — `backing` + `writable: true` is a build error. `ResourceCollectionConfig` has **no** `writable` field; collections express write-ability through `llmWritable` and the mutation methods (`create` / `getOrCreate` / `upsert` / `delete`). For a backed collection the definer rejects `llmWritable: true` and the mutation methods reject at runtime with a clear "backed collections are read-only in this slice" error. The intent is identical (no writes through the resource surface); the gated field is just per-definer.

**`list` signature (collection).** `ResourceCollectionRef.list` today is `list(prefix?: string): Promise<ResourceRef<TState>[]>`. PR2 widens it to `list(query?: string | ResourceQuery)` — a bare string keeps today's prefix behavior (store-backed and backed alike); a `ResourceQuery` is the pushdown path (backed collections call `backing.search`; store-backed collections may interpret `prefix`/`filter` over the loaded set). The string form is retained for source-compat.

Change-signal host helper (engine):

```ts
/** Notify the framework that an app-owned record behind a projected resource changed. */
export type ResourceChangeNotice = {
  flowKind: string;
  scope: ResourceScope;   // session | user | org — never the transient "request" scope
  scopeId: string;
  tenantId?: string;      // trusted tenant coordinate (multi-tenant); disambiguates a shared sessionId/scopeId
  accessor: string;       // the resource ACCESSOR name (the key in `flow.resources[...]`), NOT the storage ref —
                          // resolution is by accessor (`findResourceConfig`), and accessor ≠ storage ref by design
  key?: string;           // collection instance key; omit for a single resource
  op: "created" | "updated" | "deleted";
  sessionId?: string;     // target live session for client refresh + in-session reactTo (path B)
};
```

> **Accessor, not storage ref.** Resource lookup indexes `flow.resources[accessor]` (`findResourceConfig`), and the architecture separates the accessor key from the storage `ref` (a definition registered under accessor `portfolio` may carry `ref: "accounts"`). The notice must carry the **accessor** (plus the collection `key`) so resolution is unambiguous; passing a storage ref would miss or hit the wrong alias.

### 4.3 Data flow

**Read (agent or client).**
1. A block reads `ctx.resources.x` (single) or `await ctx.resources.coll.get(key)` (collection instance).
2. The registry sees `backing` on the config and, instead of reading the per-scope cache/`ResourceStateStore`, calls `backing.read({ key, ctx })` (deduped per request via the existing single-flight map). The result is parsed through `stateSchema` and written into the per-scope cache, so the existing **synchronous** `ResourceRef.state` getter resolves against a filled cache.
3. **Async hook vs sync `.state` getter.** `ResourceRef.state` is `Readonly<TState>` (sync) and the collection instance `state` getter is documented synchronous, but `backing.read` is async — so the value must be resolved *before* a ref's sync `.state` is read. A backed **single** resource therefore loads eagerly: its `backing.read` is awaited during context creation (the resource wave), exactly where store-backed single state is loaded, and the ref is exposed only after. A backed **collection** instance is reached through the already-async `get`/`getInstance`/`list` accessors, which await `backing.read`/`backing.search` and fill the cache before returning the resolved ref — so the instance's sync `.state` is safe. No new awaited read API is introduced.
4. The resolved `state` feeds the normal ref: `readContent()` renders the template against it (agent MD); `client.data`/`expose`/`exclude` project it (client snapshot).

**Search (agent tool).**
1. `searchResources({ query, prefix })` / `grepResourceContent({ pattern, prefix })` / `globResources({ pattern })` run.
2. For backed resources, the tool builds a `ResourceQuery` and calls `backing.search`; for store-backed resources it enumerates as today. Results merge into one URI/snippet list. The hook returns `{ hits, nextCursor? }`; `nextCursor` is surfaced to the caller (and echoed back as `ResourceQuery.cursor` on the next page) so pagination can advance — a bare-array return would let a query *consume* a cursor but never *advance*.
3. Each `ResourceBackingHit.key` becomes a `uri` (`${scope}/${path}`); the agent can then `read` it through the same surface.

**Change (app → framework).**
- *Path A (dispatch a flow directly):* the app posts an event through an inbound transport; an event-addressed action runs and reads the backed resource fresh. No new runtime. **This is the only path that works for an idle session** (see the constraint below).
- *Path B (refresh an active live session):* the app calls `notifyResourceChanged(notice)`; the host resolves the target session and fires `onResourceChanged` with a **re-read delta** (see below), which (i) streams a `resource_change` item so a connected client refetches and (ii) runs the resource's `reactTo` bindings in that session.

**Two hard constraints PR3 must honor (both surfaced in spec review):**

1. **`reactTo` needs a real `ResourceChangeDelta`, not an empty signal.** The reactive dispatcher returns early when the change descriptor is absent — firing `onResourceChanged` with "no payload" would stream the client item but never run a declared `reactTo` block. So `notifyResourceChanged` must **re-read** the projection through `backing.read` and pass a real `ResourceChangeDelta` (`{ state, prevState? }` for `created`/`updated`; a tombstone — `state: null` — for `deleted`) so the dispatcher actually fires the binding.
2. **The `resource_change` SSE only exists during an active request.** `createExecutionContext` pulls `emitResourceChange` from the request `response`; an **idle** session being merely *viewed* has no open request stream to write to. Path B therefore refreshes a session **only while it has an active request/live stream**; for an idle session the app uses path A (dispatch an action, which opens a request and reads fresh). A general session-level pub/sub push channel for idle sessions is **out of scope** (Open Questions / Non-Goals) — calling out the limitation rather than silently assuming a channel that does not exist.

### 4.4 State management

No new persisted state. Backed resources hold *no* state in `ResourceStateStore` / `ContentStore` — their state is transient per-request (hook result). Writes through a backed ref are rejected at build time. Edges (`edges`) are unsupported on backed resources in this slice (they require persisted graph state) — build error if combined.

### 4.5 Error handling

| Case | Behavior |
| -- | -- |
| `backing.read` throws | Propagates as the read's rejection (same as a store read failure); the block/tool sees the error. `signal` abort → reject with the abort reason. |
| `backing.read` returns `null` | Single resource: `state` is the schema default / `read` is treated as "absent". Collection: `get` throws not-found; `getOptional` returns `undefined`. |
| `backing.read` returns a value that fails the resource `stateSchema` | Validated through `stateSchema` before any consumer (template `render`, `client.data`, `reactTo`) sees it — same normalization store-backed reads get. On failure: single resource **throws** (fatal to the read); a collection hit from `search` is **dropped + logged** (don't poison the set). Never feed unvalidated app data into projection/render. |
| `backing.search` returns a key/state that fails schema validation | The hit is dropped and a diagnostic is logged (do not poison the whole result set). |
| Mutation attempted on a backed resource/collection | Single resource: `backing` + `writable: true` is a build-time error. Collection (no `writable` field): `backing` + `llmWritable: true` is a build-time error, **and** every mutator path throws at runtime — the `create` / `getOrCreate` / `upsert` / `delete` methods *and* the CRUD resource tools (`resourceTools()`), which invoke those methods, both reject backed collections with "backed collections are read-only in this slice". The read-only guarantee cannot be bypassed through app code or agent CRUD tools. |
| `backing` + `prefetchMode: 'eager'` on a collection | Build-time error (force `'lazy'`). |
| **Backed collection without `backing.search`** | Build-time error — a collection is unbounded, so `list` and the ungated path-only `globResources` tool have no way to enumerate. (`backing.search` is required for *every* backed collection, regardless of `llmReadable`; a backed *single* resource needs only `read`, since glob matches its one known path without enumeration.) |
| `backing` + `edges` | Build-time error (edges need persisted state). |
| `notifyResourceChanged` for an unknown/closed session | No-op with a logged warning (best-effort, like other transient client signals). |

## 5. Implementation Sequence

> Disciplines: this is an Enhancement → **`fsd:tdd`** (red-green-refactor, tracer-bullet slices). Each PR is independently shippable and testable.

### PR1 — Read projection (single + collection)
1. **Types + field.** Add `ResourceBacking`, `ResourceQuery`, `ResourceBackingHit`, `ResourceBackingContext` and the `backing?` field to `ResourceConfig` (`packages/core/src/types/resource.ts`) and `ResourceCollectionConfig` (`resource-collection.ts`). *Test:* types compile; definitions accept `backing`.
2. **Definer validation.** In `defineResource`: reject `backing` with `writable: true`, with `edges`. In `defineResourceCollection`: reject `backing` with `llmWritable: true`, with `edges`, with `prefetchMode: 'eager'`, and **without `backing.search`** (every backed collection needs a pushdown path for `list`/glob/grep/search). *Test:* each invalid combo throws with a clear message; valid combos pass.
3. **Registry options + read redirect.** First extend `createScopeResourceRegistry`'s options to carry `userId`, `orgId`, `flowKind`, and the request `signal` (thread them from `createExecutionContext`, where they are already in scope) so a `ResourceBackingContext` can be built. Then, when a config has `backing`, resolve the single resource `state` getter and the collection `get`/`getInstance` loader through `backing.read({ key, ctx })`; skip the store read and skip persistence. *Test:* a flow with a backed single resource exposes hook-resolved `state`; a backed collection `get(key)` returns a ref whose `state`/`readContent()` reflect the hook.
4. **Wire backing into the client routes (real code, not verify-only).** The public client surfaces do **not** all go through `createScopeResourceRegistry`: the `/state` snapshot reads `ResourceStateStore`/`ContentStore` directly via `buildResourceSnapshot` (`packages/engine/src/routes/state-routes.ts`, `route-utils.ts`) and the content endpoints call `getPersistedData` (`packages/engine/src/routes/resource-routes.ts`). For a backed resource these must resolve through `backing.read` instead of the store, or the routes would project schema defaults / `null`. Route the snapshot + content-endpoint reads of backed resources through the same backing resolver (factored as a shared helper so the route path and the registry path agree). *Test:* `/state` snapshot returns hook-projected `clientData` for a backed single resource (not defaults); the content endpoint renders MD from hook state.

### PR2 — Search / list pushdown (depends on PR1)
5. **`list(query)` on backed collections.** Widen `ResourceCollectionRef.list` to `list(query?: string | ResourceQuery)` (string = today's prefix; object = pushdown). For backed collections route to `backing.search`, map `hits` → refs, and surface `nextCursor` for pagination. *Test:* `list({ filter })` returns only hook-matched instances; no in-memory enumeration occurs (assert hook receives the query); a returned `nextCursor` round-trips into the next `list({ cursor })` call.
6. **Agent tool routing — engine-provided search adapter.** `resourceSearchTools()` lives in `@flow-state-dev/core`, but `ResourceBackingContext` needs `flowKind`/`tenantId`, which exist only on the engine's `ExecutionContext`, not on the public `BlockContext` core tools receive. Do **not** have core reach into engine internals: expose the backing search behind an **engine-wired ref method** (e.g. a `search(query)` the engine attaches to the backed collection ref, which closes over the resolved `ResourceBackingContext`), and have the core tools call that method when present. This keeps the `core` → `engine` boundary intact (no transport/engine-context leakage into core). The tools detect a backed resource via that method and call it (building a `ResourceQuery` from the tool input) instead of reading content in memory; results merge with store-backed. *Test:* `searchResources`/`grepResourceContent`/`globResources` over a backed collection return hook hits with correct URIs; store-backed resources in the same scope still work; `core` builds without importing engine context types.

### PR3 — Change-awareness (depends on PR1; PR2 optional)
7. **`notifyResourceChanged` helper + `resource-change` entry.** Add the host helper and a thin inbound path (`source: "resource-change"`) that resolves the target session by `accessor` (+ `key`, `tenantId`). It **re-reads** the projection through `backing.read` and fires `onResourceChanged` with a real `ResourceChangeDelta` — `{ state, prevState? }` for `created`/`updated`, a tombstone (`state: null`) for `deleted` — so the reactive dispatcher (which returns early on an absent descriptor) actually runs a declared `reactTo`. Fires only when the target session has an active request/live stream (idle sessions use path A). *Test:* with an active session it streams a `resource_change` item and fires a declared `reactTo` binding; a `deleted` notice streams a tombstone and fires `reactTo.deleted`; unknown/idle session no-ops with a warning.
8. **Document path A.** Add the "inbound event → dispatch a flow directly" recipe (no new code; uses the inbound-transport contract). *Test (goal check):* see §7.

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
| -- | -- |
| Two reads of the same backed key in one request | Single-flight dedupe → one `backing.read`; both see the same result. |
| Backed collection `count()` | Best-effort: returns the count of hits from the last `search`/`list`, or requires a `search` round-trip; documented as not exact (mirrors lazy-collection `count` semantics). |
| Backed collection in the client snapshot | The snapshot does **not** enumerate the app source; a backed collection contributes only instances already loaded this request (typically none). Clients discover instances via the search tools / a `list` call, then fetch content per URI. Documented explicitly. |
| `prefix` on `backing.search` | Passed through verbatim; the app decides how to interpret it (path-boundary semantics recommended to match store-backed tools). |
| Change signal arrives mid-request | Read-through means the next read re-queries; per-request memoization may serve a slightly stale value for the remainder of that request. Documented as the freshness contract (read-your-request-start consistency). |
| `op: "deleted"` on path B | Streams a `null`/tombstone `resource_change` so a live client drops the instance; fires `reactTo.deleted` for backed collections. |
| Abort during a hook call | `ctx.signal` aborts; the hook should honor it; the read rejects with the abort reason. |

**Error taxonomy.** Hook exceptions are *fatal to the read* (not retried by the framework — retry/caching is the app's concern). Schema-invalid search hits are *non-fatal* (dropped + logged). Unknown-session notifications are *non-fatal* (no-op + warn).

## 7. Testing Strategy

**Goal & goal check (required).** *Goal:* an agent can read and search an app's own database through the resource tool surface, and a live client sees the projected data, with the app's store remaining the source of truth (no copy in FSD). *Goal check:* a real-model `goals/` script (`goals/api-backed-resources/agent-reads-app-data/run.mts`) that (a) stands up an in-process app store (a small array/SQLite acting as the source of truth), (b) defines a backed collection over it, (c) runs a real generator turn asking the agent to find and summarize a record, and (d) asserts PASS when the agent's answer reflects a value that exists *only* in the app store (never written to FSD). The script prints `PASS`/`FAIL` on whether the agent retrieved the app-owned value via the resource tools. This is the out-of-CI confirmation that the projection actually serves a real model.

**Discipline:** `fsd:tdd`. Behaviours to test (each a tracer-bullet cycle):
- A backed single resource's `state` reflects `backing.read`; `readContent()` renders MD from it. (PR1)
- A backed collection `get(key)` resolves through the hook; `getOptional` returns `undefined` on `null`. (PR1)
- Build-time validation rejects `writable`/eager/`edges`/llm-without-search combos. (PR1)
- Snapshot route returns projected `clientData` for a backed single resource. (PR1)
- `searchResources`/`grepResourceContent`/`globResources` route to `backing.search` and return correct URIs; store-backed resources coexist. (PR2)
- `list({ filter })` pushes the query to the hook and does not enumerate. (PR2)
- `notifyResourceChanged` streams a `resource_change` item and fires a `reactTo` binding for the target session; unknown session no-ops. (PR3)

**Seams / patterns to reuse:**
- Unit/route: `createInMemoryStores()` + `createFlowRegistry()` (see `packages/engine/test/resource-state-routes.test.ts`).

## 8. Non-Goals

- **Agent-initiated create/update/delete *through* the resource.** Deferred — marginal value (the agent already mutates app data via handlers) and re-opens FIX-772 view-vs-truth invalidation + overlaps FIX-854 (transactional sequencer). The app's own writes are observed (in scope); the agent's resource-CRUD writes are not.
- **Semantic / vector search and a rich filter AST.** The `ResourceQuery` is intentionally minimal; semantic retrieval and a full predicate grammar land with **FIX-142** (embedding/vector foundation) and **FIX-833** (search over large/unbounded collections), which extend this query type.
- **FSD owning an ORM or being the app's data store.** This is a projection/view seam; the host owns storage (FIX-772, host-owns-storage). See `docs/internal/out-of-scope/` (add an entry if not present).
- **Cross-request caching / TTL of the projection.** Per-request memoization only in this slice; a `cacheable`/TTL policy (Apollo `cacheOptionsFor` shape) is a fast-follow.
- **Sessionless / cross-session `reactTo` on an external change.** Without a live session there is no turn to run the reaction in; that case is served by path A (dispatch an action). See Open Questions.
- **A session-level pub/sub push channel for idle sessions.** The `resource_change` SSE only exists during an active request, so path B refreshes a session only while it has a live stream. Pushing a refresh to a session that is merely being *viewed* (no active request) would need a new session-scoped pub/sub transport — out of scope here; path A covers the idle case.
- **`edges` on backed resources.** Typed-edge graphs require persisted state; out of scope here.
- *Deepening opportunities flagged during research:* the trading-desk currently exposes app data through a parallel HTTP route (`labs/trading-desk/app/api/portfolio/accounts/route.ts`) **and** the repository pattern, bypassing the resource surface — once this lands, that parallel read path is a consolidation candidate; follow up via `fsd:improve-codebase-architecture` (not in scope here).

## 11. Open Questions

1. **Sessionless / cross-session `reactTo` on an external change.** Path B fires `reactTo` for a *target live session*. Should an app change with no live session be able to trigger a resource's reactive bindings, or is "dispatch an event-addressed action" (path A) the intended answer for that case? *Recommendation:* path A for sessionless; keep path B scoped to a target session in the first slice. **Needs product sign-off.**
2. **Depth of the portable query in the first slice.** Ship the minimal `ResourceQuery` (`search`/`prefix`/`filter` equality/`limit`/`cursor`) and let FIX-833 richen it, or include `orderBy` and range operators now? *Recommendation:* minimal now; richen with FIX-833. **Confirm.**
3. **Backed collections in the client snapshot.** Confirm the documented behavior (snapshot does not enumerate; clients discover via search/`list`) is acceptable for the two consumers (trading-desk portfolio list, `current` ADHD task list), or whether a bounded "initial page" in the snapshot is wanted. **Two-consumer check before PR2 hardens.**
4. **Per-request memoization vs always-fresh reads.** Is read-your-request-start consistency (memoize per request) acceptable, or must every read within a request re-query? *Recommendation:* memoize per request (matches the existing cache + single-flight). **Confirm.**
