## 1. TLDR

**Plain-language summary.** The framework talks to AI models through a third-party library that just shipped a new major version. This work moves the framework onto that new version without changing how anything behaves: streaming answers, tool use, structured output, caching, and model fallback must all work exactly as before. It has to land first because every other item in this project builds on the new version.

**Technical statement:** Bump `ai` from `^6.0.93` to `^7`, plus the paired `@ai-sdk/*` provider and MCP package majors, across the whole workspace; re-align the model adapter (`createAiSdkModelResolver`) and its satellites to v7's surface; and prove behavioral parity with the existing mocked suites plus real-LLM goal checks.

**Deliverables:**

- Core: migrate `createAiSdkModelResolver.ts` to the v7 surface — `result.fullStream` → `result.stream`; stream-part mapping verified against the part-type union pinned from the installed `ai@7.0.15` types (§3.2 — v6 part names largely survive; `tool-call`/`tool-result` payload fields are `input`/`output`), one mocked assertion per mapped category; final-step values read via `await result.finalStep` in `normalizeFinishChunk`; `stepCountIs` → `isStepCount`; system prefix kept in `messages` with `allowSystemInMessages: true` (Key Decision 6); `createModelResolver.ts` moves from `createRequire` to dynamic `import()` behind a lazy `GeneratorModel` so the public synchronous `ModelResolver` contract is preserved (§4), with a runtime provider-resolution smoke; Google provider table entry `createGoogleGenerativeAI` → `createGoogle`
- Tools: bump `@ai-sdk/mcp`, re-verify `tool()` usage in `create-bash-tool.ts` and the MCP manager path (`packages/tools/src/mcp/manager.ts` — `createMCPClient`, `client.tools()`, tool execution over MCP transports)
- Engine: verify duck-typed error classification; resolve the vestigial `ai` dependency pin
- Tests: `MockLanguageModelV3` usages stay as-is — resolved at install: `ai/test` on v7.0.15 still exports `MockLanguageModelV3` and V3-spec mocks remain valid (v7's `LanguageModel` union accepts `LanguageModelV4 | LanguageModelV3 | LanguageModelV2`)
- Workspace: bump `ai` / `@ai-sdk/*` pins in apps, labs, examples to keep one SDK major per graph; raise the `zod` floor to `^3.25.76` in `packages/core` and `packages/tools` (currently `^3.24.1`, below `ai@7`'s peer range `^3.25.76 || ^4.1.8`; engine is already at `^3.25.76`)
- Docs: migration note + version references (per §9)
- Changesets (`minor`) for core, engine, tools — plus `cli` if the §7 capture fix (include `item.updated`/`item.done` in `--capture`) ships, **and one for every other publishable package whose manifest changes in this PR** (the `engines.node >= 22` bump touches client/react/testing/vercel/store-sqlite/etc. — a changed install constraint is user-facing; BP-022)

**Size:** Large — multi-package, but a single PR (the workspace must move atomically; a split would leave mixed SDK majors mid-stream).

## 2. Overview

[FIX-859](https://linear.app/fixpoint-labs/issue/FIX-859/upgrade-fsd-from-ai-sdk-6-to-ai-sdk-7-core-engine-tools) upgrades the framework's generator provider layer from Vercel AI SDK 6 to AI SDK 7. ### 3.2 AI SDK 7 breaking changes relevant to this surface

Adjudicated against the [official v7 migration guide](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0) and the [v7 `streamText` reference](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text). Verdicts on the review-cycle claims below; the confirmed items are binding on §4.

**CONFIRMED (migration guide):**

- Node.js 22+ required → `engines` bump to `>=22` for the published packages + CI matrix/docs (was a verify-item; now a hard deliverable).
- All packages ESM-only; `require()` unsupported → `createModelResolver`'s `createRequire` loading becomes dynamic `import()` with the async ripple, plus the runtime provider-resolution smoke (typecheck/mocked suites never execute the loader).
- `StreamTextResult.fullStream` renamed to `stream`.
- System messages in `messages` rejected by default → opt-in via `allowSystemInMessages: true` (Key Decision 6 picks this over `instructions`).
- Top-level result properties (`content`, `toolCalls`, …) now accumulate across steps → final-step-only values via `finalStep`; `normalizeFinishChunk` must read from the right object.
- Google provider rename (official codemod `rename-google-generative-ai-to-google`) → provider table entry becomes `createGoogle`.
- `prepareStep` returned `instructions` carry forward into later steps until overridden → generator's message-rewriting `prepareStep` needs the idempotent-rebuild treatment + dynamic multi-step regression test.
- Tool-result content parts canonicalized (single `file` variant replaces `image-*`/legacy `file-*`) → re-verify the `toModelOutput` bridge and recall-tool path.
- `stepCountIs` → `isStepCount` (direct resolver import).
- `onFinish` → `onEnd`, `onStepFinish` → `onStepEnd`; `system` option → `instructions`; telemetry renames (not on our surface, but check no stragglers).
- Usage: `cachedInputTokens` → `inputTokenDetails.cacheReadTokens` — `normalizeUsage` **already reads that nested shape**, so the earlier top-level-keys claim is refuted; add a mocked v7-usage regression to pin it.

**PINNED (installed `ai@7.0.15` type declarations, `TextStreamPart` — §5 step 1 executed 2026-07-04):**

The installed union is the authority; it supersedes both earlier docs readings, refuting two claims that had been promoted to CONFIRMED in review:

- `text-delta` and `reasoning-delta` carry `.text` (no `type: "text"` rename happened).

### 3.3 Key Decisions & Ramifications

1. **Codemod the renames, hand-migrate the seams.** Run the official v7 codemods for mechanical renames (`rename-google-generative-ai-to-google`, `stepCountIs`→`isStepCount`, callback renames), then hand-migrate the resolver's stream/finish/request mapping with the mocked contract suite as the safety net. Alternative rejected: pure codemod (cannot see the duck-typed satellites — caching, fallback, classifier — or the framework chunk mapping) and pure hand-migration (wastes review attention on renames a codemod does deterministically). Ramification: the diff has two visibly different textures; reviewers should read the codemod commits as mechanical and spend attention on the resolver commit.
2. **Bump the entire workspace atomically, not just core/engine/tools.** Alternative rejected: bump only the three named packages. Apps/labs construct provider models (`openai(...)`, gateway models) and hand them to core; a v6 provider model implementing an older LanguageModel spec version handed to a v7 `streamText` is exactly the interop failure a major exists to prevent. Ramification: the PR touches every workspace `package.json` that pins `ai`/`@ai-sdk/*`, and downstream consumers of published FSD packages must bump their own `ai` when they use the escape hatches (`wrapAiSdkModel`, `providerTools`, raw provider models) — this is the content of the migration note.
3. **Behavioral parity is the gate; no new v7 capability adoption.** Alternative rejected: adopt v7 features opportunistically while in the file. Ramification: sibling issues stay unblocked and reviewable; some code may look v6-idiomatic on v7 until siblings land.
4. **Drop engine's vestigial `ai` dependency rather than bump it.** Alternative rejected: bump the unused pin. Engine's only AI SDK contact is structural (symbol/name/statusCode). Ramification: engine no longer expresses a version constraint on `ai`; the classifier's structural detection must be re-verified against v7 error shapes (it was built for realm-safety, which also buys version tolerance). BP-038: subtract before you add.
5. **Mock strategy decided at install, contract suite stays authoritative.** The `MockLanguageModelV3` instantiations update to whatever `ai/test` actually exports on v7 — inspected at §5 step 1, not guessed now. Alternative rejected: pre-writing a compatibility shim over the mocks (speculative surface, BP-038). **Resolved at install:** `ai/test` on v7.0.15 still exports `MockLanguageModelV3` and V3-spec mocks pass unchanged — no rename, no shim; assertions untouched. Ramification: the streaming suites pass partly via ai@7's V3-mock adaptation layer, so suite-green does not by itself prove the §4 migration (see §3.2 install-time note).
6. **Keep the system prefix in `messages` via `allowSystemInMessages: true`, not `instructions`.** v7 rejects system messages in `messages` by default; the opt-in preserves the v6 shape exactly. Alternative rejected: migrating to `instructions` — it moves the system prefix out of `messages`, which silently breaks `applyCaching`'s `role: "system"` cache anchor and the `prepareStep` slice logic, for zero parity benefit. Ramification: FSD stays on an opt-in flag a future major could remove; the `instructions` migration becomes an explicit sibling-issue candidate, and `applyCaching` gains a resolver-level assertion now so any later move cannot silently disable cache markers.

## 4. Technical Design

Per-file plan, ordered by risk. Everything here traces to a CONFIRMED item in §3.2 or a verified in-repo seam in §3.1.

**`packages/core/src/models/createAiSdkModelResolver.ts` (the migration target):**
- Imports: `stepCountIs` → `isStepCount`; verify `generateText`/`streamText`/`Output` names unchanged.
- Request build: add `allowSystemInMessages: true` (Key Decision 6); verify `prepareStep`, `providerOptions`, `abortSignal`, `maxOutputTokens`, `onError` option names against v7 (guide renames `onFinish`-family callbacks; we use `onError` — confirm it survived).
- Stream consumption: iterate `result.stream` (codemod applied); the part-mapping table is **finalized from the installed `TextStreamPart` union (§3.2 PINNED)** — v6 part names largely survive. Verify each mapped category against the pinned shapes: `text-delta`/`reasoning-delta` (`.text`), `tool-input-start`, `tool-input-delta` (`.delta` → framework `argsDelta`; the part carries only `id`/`delta` — **no `toolName`** — so the resolver records the `tool-input-start.id → toolName` mapping and deltas inherit it; the current code falls back to `""`, a gap the migration closes at this layer with an assertion that progress chunks carry the non-empty tool name), `tool-call` (payload field `input`), `tool-result` (`input`/`output`), `source` (**flat**, `sourceType: "url"` variant — existing read stays; `document` variant out of scope) → `source_url`, `finish-step`/`finish` (`totalUsage`, nested `inputTokenDetails`), `error`/`abort`. One mocked resolver assertion per mapped category.
- Finish normalization: on the installed v7 `StreamTextResult`, **every accumulated top-level property is `PromiseLike`** — `content`, `text`, `sources`, `toolCalls`, `toolResults`, `finishReason`, `usage`, `totalUsage`, `steps`, and `finalStep` itself. Final-step-only values come from `await result.finalStep`; every *other* top-level property the finish path consumes must also be awaited before it reaches a normalizer (`normalizeUsage`/source handling receiving a Promise object would silently drop usage/source metadata). `normalizeUsage` keeps its `inputTokenDetails.*` reads (already v7-shaped) and gains the mocked v7-usage regression.
- Error wrapping and provider search tools: re-verify `AI_NoObjectGeneratedError`/`AI_NoOutputGeneratedError` names and the real Anthropic/OpenAI/Google search-tool factory names against installed v7 packages (mocked factories can't catch renames — §7 seam caveat).
- `toModelOutput` bridge: emit the canonical `file` content variant where the old `image-*`/`file-*` parts were produced; recall-tool path re-verified.

**`packages/core/src/models/createModelResolver.ts`:** replace `createRequire` module **execution** with dynamic `import()` (ESM-only) **without breaking the public synchronous `ModelResolver` contract** — `createModelResolver()`, `ctx.resolveModel(...)`, and `resolver.resolveId(...)` stay synchronous. Split the two things `createRequire` does today: **availability checking stays synchronous** via module *resolution* (`createRequire(...).resolve` / `import.meta.resolve` — path lookup works for ESM-only packages; only execution needs `import()`), because three sync decision points depend on it: the intent candidate filter (`resolveIntent` → `tryResolveSingleModel` drops unavailable candidates), the failed-direct-load → configured-gateway fall-through (FIX-609), and public `resolveId` (which probes candidates with `resolveSingleModel` and returns the first *available* one — deferring the check would make it report a candidate that won't actually run). Module **execution** moves into the lazy `GeneratorModel`, awaiting the (cached, single-flight) provider import inside `generate`/`stream`. Both loader fallbacks preserved and regression-tested: (a) `process.cwd()` resolution for pnpm-strict app installs, and (b) the gateway fall-through before throwing — plus a `resolveId` regression: with an unavailable first intent candidate, `resolveId("intent/…")` still returns the same candidate the executing path would use. Google entry → `createGoogle`; gateway import path unchanged (§3.2 RESOLVED). Failure-mode parity: a missing provider package (with no gateway configured) still produces the same actionable "provider package is not installed" error — not an opaque ESM resolution error.

**`packages/core/src/blocks/generator.ts`:** `prepareStep` rebuilds the full message array idempotently each step (carry-forward semantics make a partial return sticky); dynamic multi-step regression test asserting no duplicated/stale context across ≥2 tool-loop steps.

**`packages/core/src/models/caching.ts`:** unchanged by design (Key Decision 6 preserves the `role: "system"` anchor); gains a resolver-level assertion that a resolver-built request carries the cache markers.

**`packages/core/src/models/fallbackModel.ts` + `packages/engine/src/errors/classify-provider-error.ts`:** re-verify constructor names / `statusCode` / `Symbol.for("vercel.ai.error")` against v7 error instances; engine drops its vestigial `ai` dependency (Key Decision 4); classifier test gate in §7.

**`packages/tools`:** bump `@ai-sdk/mcp` (done); re-verify `tool()`; MCP redirect decision made at install (§3.2 RESOLVED): keep v7's reject-by-default, no knob, migration-note callout only; add the un-injected `createMCPClient` smoke and the `tool()`-through-`providerTools` generator test (§7 seam gaps).

## 6. Edge Cases & Error Handling

- **Missing provider package (dynamic import):** the async import failure must surface the same actionable "install @ai-sdk/x" error as the v6 `createRequire` path — not an opaque ESM resolution error.
- **Models that report no usage:** `normalizeUsage` null-guards stay intact (`== null` guards, BP-030-style); the v7-usage regression covers the absent-usage case too.
- **Single-iteration generators:** the generator builds `prepareStep` whenever dynamic slots exist (regardless of `maxIterations`); it is a no-op at step 0, so single-call behavior is the assembly-time prompt sent as-is with dynamic context resolved exactly once — the carry-forward change must not alter that observable contract (regression asserts it). *(Corrected during implementation: an earlier revision claimed no `prepareStep` is built for `maxIterations === 1`, which was wrong about the code.)*
- **Multiple/empty system prefixes:** `allowSystemInMessages: true` with zero system messages and with multi-part prefixes both behave as on v6; `applyCaching` anchor assertion covers the present-prefix case.
- **Stream `error` parts and aborts:** v7 `error` parts route through the same wrapping as v6; `abortSignal` cancellation still yields the framework's cancel path, not an unhandled rejection.
- **Mixed-major graphs:** after the bump, assert the lockfile resolves exactly one `ai` major (guards Key Decision 2 against a stray transitive pin).

## 7. Testing Strategy

**Goal & goal check (required).** Goal: a user's flows behave identically on v7 — streaming text/reasoning/tool deltas render live, structured output validates, multi-step tool loops terminate, caching markers still hit, fallback still falls back. Goal check (real model, out of CI):

1. `KITCHEN_SINK_TEST_MODE= pnpm tsx goals/structured-output/recovers-off-schema-output/run.mts` — exercises real structured output + coercion repair on GLM 5.2 (PASS/FAIL printed by the script). The env clear matters here too: the runner shells out from `apps/kitchen-sink`, and with `KITCHEN_SINK_TEST_MODE=1` inherited from an E2E shell the config installs the mock resolver — `--model`/forced ids only wrap the *active* resolver, so the gate would "pass" without touching the AI SDK. Prerequisite: `AI_GATEWAY_API_KEY` — the runner pins `vercel/zai/glm-5.2`, a gateway id, and fails at model resolution without it.
2. `cd apps/kitchen-sink && KITCHEN_SINK_TEST_MODE= pnpm fsdev run chat-agent run -i '{"message":"…","mode":"ask"}'` — real streaming + tool loop over the default model group, using the app's `fsdev.config.ts` wiring (the command is `fsdev run <flowKind> <action>`; see `apps/kitchen-sink/CLAUDE.md`). **Every goal-check command (1–4) must explicitly clear `KITCHEN_SINK_TEST_MODE` in its literal command line** — `fsdev.config.ts` swaps in the deterministic mock resolver whenever it is `"1"` (Playwright/E2E shells set it), which would bypass the AI SDK entirely while looking like real-model evidence. Prerequisite: `AI_GATEWAY_API_KEY` must be set — the default groups are `vercel/...` gateway ids and the config only wires the gateway when that key is present; without it the run fails before the smoke. The message must be one that deterministically requires a tool (ask the agent to use one of its installed tools on concrete input — a plain-text answer must not be able to satisfy it); pass = the NDJSON contains a `tool_call_progress` item reaching `status: "completed"`, a durable `tool_output` item, **and non-empty assistant text streamed via `content_delta` events** (an empty assistant envelope is a FAIL — it would mean live text streaming broke while items still completed), with **no `type: "error"` events** (that is the CLI's actual failure shape — there is no `execution_error` item type in the NDJSON union; with `--capture`, additionally assert `result.success === true`). A text-only completion is a FAIL for this check even with exit code 0.
3. A reasoning parity check: rerun 2 with thinking enabled — kitchen-sink gates Anthropic thinking on `ctx.user.state.thinkingEnabled` (see `flows/chat-agent/run/assistant/assistant.ts`), which is **user-level** state. Set it by running the flow's own action first, and run **both** commands with `STORE_TYPE=filesystem` so the user-state write survives across the two CLI processes (the local profile defaults to `inMemoryStores()`, which would discard the toggle when the setup command exits): `KITCHEN_SINK_TEST_MODE= STORE_TYPE=filesystem BASH_PROVIDER=just-bash pnpm fsdev run chat-agent setThinkingEnabled -i '{"thinkingEnabled":true}'`, then rerun the smoke the same way as the same user; pass = reasoning items stream live before the assistant message. `BASH_PROVIDER=just-bash` is required because kitchen-sink's `selectBashProvider()` couples sandbox selection to the store type — `STORE_TYPE=filesystem` alone would switch the bash capability to the host `local` shell, executing tool calls on the reviewer's machine and exercising a different tool-loop path than the step-2 smoke. Thinking is Anthropic-only and the assistant honors a persisted `ctx.user.state.selectedModel` before the Anthropic default, so with a persistent store also pin the model first (`... setSelectedModel -i '{"selectedModel":"vercel/anthropic/claude-sonnet-4.6"}'`) or run against a fresh `.fsdev/data` directory — a stale non-Anthropic selection would make this gate pass with no reasoning stream. Do **not** use the CLI seed flags for this: `--seed-session` writes the wrong tier, and `--seed-user` is currently parsed and echoed into capture metadata but never applied (`run.ts` only applies `seedSession` — a pre-existing CLI bug, log separately). The default `mode: "ask"` run never exercises the reasoning stream, so without this the goal's "reasoning deltas render live" clause is unverified.
4. A caching spot-check: run 2 twice with `AI_GATEWAY_API_KEY` set (kitchen-sink's default groups resolve `vercel/...` gateway ids, exercising gateway `caching: "auto"`), adding `--capture <path>` and `FSDEV_TRACE_OBSERVABILITY=true`. **The prompt must actually be cacheable:** pin an Anthropic route first (`setSelectedModel` → `vercel/anthropic/claude-sonnet-4.6`, as in check 3) and include a deterministic static context block large enough to clear the provider's minimum cache-segment threshold (Anthropic-style caching ignores prefixes below ~1024 tokens) — the short tool-forcing message from check 2 alone can legitimately produce zero cache reads on a correct migration, which would make this gate flaky on prompt shape rather than SDK behavior. Reuse the identical message verbatim on both runs — the live stdout stream does not surface cache counters; they are normalized onto the generator `block_trace.modelUsage`. Known gap: `mapStreamEventToNdjson` captures `item.added`/`content.delta`/resource changes/the terminal result but drops `item.updated`/`item.done`, and `modelUsage` is patched onto the trace item *after* it is added — so today the counters never reach the captured payload either. The migration must close this before the gate is runnable: extend the CLI capture to include `item.updated`/`item.done` (preferred — it is verification enablement for this issue) or have the gate read the final trace item from the session store. Pass = `modelUsage.cacheReadTokens` / cache-read provider metadata is non-zero on the second run's final trace (parity for FIX-423). The direct Anthropic `cacheControl` marker shape stays pinned by the mocked suite (`packages/core/test/models/caching.test.ts`) — a live check of that path would require adding `@ai-sdk/anthropic`, which no workspace package installs today, so it is deliberately not part of this gate.

**Discipline:** `fsd:tdd` is the routed discipline (Improvement label), but the work is migration-shaped: the "red" is the existing suites failing on the bumped dependency; "green" is restoring them without weakening assertions. Install-time reality (§3.2 note): the bumped baseline landed near-green because v7.0.15 ships deprecated aliases — the true red is the two `allowSystemInMessages` failures. Suite-green via alias/mock-adaptation is not the gate; the binding gates are the §4 migration off deprecated surface, the new regressions, and the goal checks. New tracer tests are only added where v7 introduces a behavior the suite didn't pin (each such case gets a regression test in `packages/core/test/models/`).
