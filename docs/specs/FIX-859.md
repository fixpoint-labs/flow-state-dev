## 1. TLDR

**Plain-language summary.** The framework talks to AI models through a third-party library that just shipped a new major version. This work moves the framework onto that new version without changing how anything behaves: streaming answers, tool use, structured output, caching, and model fallback must all work exactly as before. It has to land first because every other item in this project builds on the new version.

**Technical statement:** Bump `ai` from `^6.0.93` to `^7`, plus the paired `@ai-sdk/*` provider and MCP package majors, across the whole workspace; re-align the model adapter (`createAiSdkModelResolver`) and its satellites to v7's surface; and prove behavioral parity with the existing mocked suites plus real-LLM goal checks.

## 2. Overview

## 3. Background & Research

### 3.1 Where FSD touches the AI SDK (complete inventory)

The v6 contact surface is narrower than it first appears. One file is the real migration target; everything else is satellites.

**Direct imports of `ai`:**

| File | Imports | Role |
| --- | --- | --- |
| `packages/core/src/models/createAiSdkModelResolver.ts` (~1,073 LOC) | `generateText`, `streamText`, `Output`, `stepCountIs` | **The adapter.** Builds requests (tools, `prepareStep`, `stopWhen`, `providerOptions`, `abortSignal`, `maxOutputTokens`, `onError`), consumes `fullStream` parts and normalizes them to framework `GeneratorModelStreamChunk`s, maps finish metadata/usage, wraps `AI_NoObjectGeneratedError`/`AI_NoOutputGeneratedError`, resolves provider search tools (`webSearch_20250305`, `webSearch`, `googleSearch`), and wraps `GeneratorModelTool.toModelOutput` (set by `compileToolsWithExecute` in `generator.ts`) into the AI SDK tool-result content envelope — `packages/memory/src/tools/recall-tool.ts` (`mapModelOutput`) depends on this bridge to feed compact recall summaries to the next model step. Publicly exported as `createAiSdkModelResolver` and `wrapAiSdkModel`. |
| `packages/core/src/blocks/generator.ts` | `jsonSchema` | `normalizeToolSchema` wraps raw JSON Schema objects; detects AI SDK schema wrappers via `Symbol.for("vercel.ai.schema")`. Otherwise consumes only framework-normalized chunks (`text_delta`, `reasoning_delta`, `tool_call_delta`, `tool_result`, `source_url`, `finish`) — insulated from the SDK taxonomy by the resolver boundary. |
| `packages/tools/src/bash/create-bash-tool.ts` | `tool` | Defines the bash/readFile/writeFile AI SDK tools. |
| `packages/tools/src/mcp/manager.ts` | dynamic `import("@ai-sdk/mcp")` | `createMCPClient` for MCP transports. |

| File | Shape depended on |

| `packages/core/src/models/fallbackModel.ts` | `error.isRetryable`, `LoadAPIKeyError` / `AI_LoadAPIKeyError` constructor names, `statusCode` |

**Tests:** 7 files under `packages/core/test/models/` construct `MockLanguageModelV3` from `ai/test` (48 instantiations). The integration-tests package uses framework-level generator mocks and is insulated from SDK internals.

**Notable finding — engine's pin is vestigial.** `packages/engine` declares `ai@^6.0.93` in `dependencies` but has zero compile-time imports of it (`classify-provider-error.ts` is deliberately structural). See Key Decision 4.

**Workspace dependents outside the issue's named packages:** `apps/kitchen-sink` (`ai@^6.0.97`, `@ai-sdk/openai`, `@ai-sdk/gateway@^3.0.51`, `@ai-sdk/mcp@^1.0.36`), `examples/hello-chat`, `labs/trading-desk` (`ai`, `@ai-sdk/gateway`, `@ai-sdk/xai`), `labs/knowledge-base` (`@ai-sdk/gateway`). These pass provider `LanguageModel` instances into core; mixed SDK majors in one dependency graph risks LanguageModel spec-version interop failures. See Key Decision 2. Trading-desk additionally consumes a version-sensitive hosted-tool surface beyond model construction: `src/flows/analysis/tools/data/get_social_sentiment.ts` imports `xai` from `@ai-sdk/xai` and installs `xai.tools.xSearch()` via `providerTools` — re-verify after the bump (live path is optional/keyed; see `labs/trading-desk/README.md`).

### 3.2 AI SDK 7 breaking changes relevant to this surface

(TO FILL — from industry research agent, with links)

Claims raised in automated PR review, to confirm or refute against the official migration guide before this section is final (unverified — do not implement from this list):

- v7 requires Node 22 → if true, `engines` bumps for the published packages + CI matrix/docs.
- v7 packages are ESM-only → if true, `createModelResolver`'s `createRequire`-based dynamic provider loading needs an explicit migration action (dynamic `import()`), not just a version bump.
- `result.fullStream` renamed to `result.stream` → resolver consumption + stream-chunk parity test.
- System messages inside `messages` need an explicit opt-in (`allowSystemInMessages` or move to `instructions`) → affects how `generator.ts` builds system-prefix messages. Ramification if the `instructions` path is chosen: `applyCaching` (`caching.ts`) finds its direct Anthropic/OpenRouter cache anchor by searching `request.messages` for `role: "system"`, and `caching.test.ts` fabricates that shape directly — moving the system prefix out of `messages` would silently disable direct cache markers while the mocked suite passes, so `applyCaching` must handle the chosen shape and gain a resolver-level assertion.
- `generateText`/`streamText` result properties changed; final-step-only values move behind `await result.finalStep` → affects the resolver's finish normalization (`normalizeFinishChunk` reads final `text`, `toolCalls`, `finishReason`, `usage`, provider metadata, sources from the awaited result) — renaming the stream iterable alone is not sufficient.
- Tool-result content shapes changed → affects the resolver's `toModelOutput` bridge (see §3.1).
- Google provider factory renamed `createGoogleGenerativeAI` → `createGoogle` → `createModelResolver` loads providers by string factory name (`createModelResolver.ts` provider table), so direct `google/...` resolution would hit the "provider package is not installed" path even with `@ai-sdk/google` present; not covered by typecheck or the mocked suites.
- `prepareStep` return semantics changed (returned `messages`/`instructions` carry forward into later steps; `initialMessages`/`responseMessages` exposed for rebuilding) → `generator.ts` builds a `prepareStep` that rewrites `messages` by slicing the initial system-prefix for dynamic prompt/context/tools with `maxIterations > 1`; if confirmed, this needs an explicit adapter change plus a dynamic multi-step regression test.
- `@ai-sdk/mcp` transport redirects flipped from follow-by-default to reject-by-default → the manager forwards only `type`/`url`/`headers` from `MCPTransportConfig`; if confirmed, decide whether to expose a redirect-policy knob (new surface — weigh against BP-038) and test the redirecting-server case.
- Gateway provider moved into the `ai` package (`createGateway` imported from `ai`; separate `@ai-sdk/gateway` possibly stale on v7) → `createModelResolver` dynamically loads `@ai-sdk/gateway`, and kitchen-sink / knowledge-base / trading-desk import it statically; if confirmed, the migration is an import-path move across all of those, not a version bump of the standalone package.
- Usage cache counters moved to top-level `usage.cacheReadTokens` / `usage.cacheWriteTokens` → `normalizeUsage` in the resolver maps `cacheReadInputTokens`/`cachedInputTokens` and nested `inputTokenDetails.*` but not those top-level keys; if confirmed, add mapper coverage plus a mocked v7-usage regression test (otherwise `modelUsage.cacheReadTokens` reads zero and cost accounting + the cache parity gate silently miss cache hits).
- Tool-argument streaming part renamed/reshaped (`tool-input-delta` with `delta` → `tool-call-delta` with `argsTextDelta`) → the resolver only handles the v6 `tool-input-delta` shape; if confirmed, update the stream mapping and add a resolver test asserting an in-progress `tool_call_progress` chunk with non-empty `argsDelta` — the tool-loop smoke alone proves completion, not live argument deltas.

### 3.3 Key Decisions & Ramifications (top 5)

1. **(TO FILL after research)** — codemod-first vs hand-migration of the resolver.
2. **Bump the entire workspace atomically, not just core/engine/tools.** Alternative rejected: bump only the three named packages. Apps/labs construct provider models (`openai(...)`, gateway models) and hand them to core; a v6 provider model implementing an older LanguageModel spec version handed to a v7 `streamText` is exactly the interop failure a major exists to prevent. Ramification: the PR touches every workspace `package.json` that pins `ai`/`@ai-sdk/*`, and downstream consumers of published FSD packages must bump their own `ai` when they use the escape hatches (`wrapAiSdkModel`, `providerTools`, raw provider models) — this is the content of the migration note.
3. **Behavioral parity is the gate; no new v7 capability adoption.** Alternative rejected: adopt v7 features opportunistically while in the file. Ramification: sibling issues stay unblocked and reviewable; some code may look v6-idiomatic on v7 until siblings land.

Ramification: engine no longer expresses a version constraint on `ai`; the classifier's structural detection must be re-verified against v7 error shapes (it was built for realm-safety, which also buys version tolerance). ## 7. Testing Strategy

**Goal & goal check (required).** Goal: a user's flows behave identically on v7 — streaming text/reasoning/tool deltas render live, structured output validates, multi-step tool loops terminate, caching markers still hit, fallback still falls back. Goal check (real model, out of CI):

1. `pnpm tsx goals/structured-output/recovers-off-schema-output/run.mts` — exercises real structured output + coercion repair on GLM 5.2 (PASS/FAIL printed by the script). Prerequisite: `AI_GATEWAY_API_KEY` — the runner pins `vercel/zai/glm-5.2`, a gateway id, and fails at model resolution without it.
2. `cd apps/kitchen-sink && pnpm fsdev run chat-agent run -i '{"message":"…","mode":"ask"}'` — real streaming + tool loop over the default model group, using the app's `fsdev.config.ts` wiring (the command is `fsdev run <flowKind> <action>`; see `apps/kitchen-sink/CLAUDE.md`). Prerequisite: `AI_GATEWAY_API_KEY` must be set — the default groups are `vercel/...` gateway ids and the config only wires the gateway when that key is present; without it the run fails before the smoke. The message must be one that deterministically requires a tool (ask the agent to use one of its installed tools on concrete input — a plain-text answer must not be able to satisfy it); pass = the NDJSON contains a `tool_call_progress` item reaching `status: "completed"` **and** a durable `tool_output` item, followed by assistant message items, with **no `type: "error"` events** (that is the CLI's actual failure shape — there is no `execution_error` item type in the NDJSON union; with `--capture`, additionally assert `result.success === true`). A text-only completion is a FAIL for this check even with exit code 0.
3. A reasoning parity check: rerun 2 with thinking enabled — kitchen-sink gates Anthropic thinking on `ctx.user.state.thinkingEnabled` (see `flows/chat-agent/run/assistant/assistant.ts`), which is **user-level** state. Set it by running the flow's own action first, and run **both** commands with `STORE_TYPE=filesystem` so the user-state write survives across the two CLI processes (the local profile defaults to `inMemoryStores()`, which would discard the toggle when the setup command exits): `STORE_TYPE=filesystem pnpm fsdev run chat-agent setThinkingEnabled -i '{"thinkingEnabled":true}'`, then rerun the smoke the same way as the same user; pass = reasoning items stream live before the assistant message. Thinking is Anthropic-only and the assistant honors a persisted `ctx.user.state.selectedModel` before the Anthropic default, so with a persistent store also pin the model first (`... setSelectedModel -i '{"selectedModel":"vercel/anthropic/claude-sonnet-4.6"}'`) or run against a fresh `.fsdev/data` directory — a stale non-Anthropic selection would make this gate pass with no reasoning stream. Do **not** use the CLI seed flags for this: `--seed-session` writes the wrong tier, and `--seed-user` is currently parsed and echoed into capture metadata but never applied (`run.ts` only applies `seedSession` — a pre-existing CLI bug, log separately). The default `mode: "ask"` run never exercises the reasoning stream, so without this the goal's "reasoning deltas render live" clause is unverified.
4. A caching spot-check: run 2 twice with `AI_GATEWAY_API_KEY` set (kitchen-sink's default groups resolve `vercel/...` gateway ids, exercising gateway `caching: "auto"`), adding `--capture <path>` and `FSDEV_TRACE_OBSERVABILITY=true` — the live stdout stream does not surface cache counters; they are normalized onto the generator `block_trace.modelUsage`. Known gap: `mapStreamEventToNdjson` captures `item.added`/`content.delta`/resource changes/the terminal result but drops `item.updated`/`item.done`, and `modelUsage` is patched onto the trace item *after* it is added — so today the counters never reach the captured payload either. The migration must close this before the gate is runnable: extend the CLI capture to include `item.updated`/`item.done` (preferred — it is verification enablement for this issue) or have the gate read the final trace item from the session store. Pass = `modelUsage.cacheReadTokens` / cache-read provider metadata is non-zero on the second run's final trace (parity for FIX-423). The direct Anthropic `cacheControl` marker shape stays pinned by the mocked suite (`packages/core/test/models/caching.test.ts`) — a live check of that path would require adding `@ai-sdk/anthropic`, which no workspace package installs today, so it is deliberately not part of this gate.

**Discipline:** `fsd:tdd` is the routed discipline (Improvement label), but the work is migration-shaped: the "red" is the existing suites failing on the bumped dependency; "green" is restoring them without weakening assertions. New tracer tests are only added where v7 introduces a behavior the suite didn't pin (each such case gets a regression test in `packages/core/test/models/`).

**CI seams:**

- `packages/core/test/models/*.test.ts` — the resolver contract suite (mock spec-version update per §research).
- `packages/core/test/generator-repair.test.ts`, structured-output/coercion tests — strict-schema parity (FIX-279, FIX-841).
- `pnpm --filter @flow-state-dev/tools test` — bash tool + MCP manager runtime behavior (`packages/tools/test/mcp/manager.test.ts` et al.); typecheck alone does not exercise the dynamic `import("@ai-sdk/mcp")` / `createMCPClient` / `client.tools()` path. **Known seam gaps to close in this migration:** (a) every `getTools()` test injects `_createClient`, so the default `createMCPClient` path is never executed — add an un-injected smoke against a local mock MCP server; (b) the bash tests call `tools.bash.execute(...)` directly — add a generator-level test passing the returned `tool()` objects through `providerTools`/`streamText` so v7 auto-execute/streaming changes can't pass silently.
- `packages/core/test/models/provider-search-tools.test.ts` — caveat: it uses hand-written mock `.tools.webSearch_20250305`/`.webSearch` factories, not the real provider packages, and `mapToProviderSearchTool` string-indexes those names. The migration must re-verify the real Anthropic/OpenAI/Google search-tool factory names against the v7 provider packages (documented inventory or a real-factory smoke) — a rename would silently disable `search: true` while this mocked seam passes.
- `packages/integration-tests` — full composition on mocked generators (unchanged by design; a failure here means the resolver boundary leaked).
- `pnpm typecheck` across the workspace — catches removed/renamed SDK types in apps/labs. Caveat: Turbo only runs workspaces that define a `typecheck` script, and `apps/kitchen-sink` and `examples/hello-chat` define none despite being in the bump scope (kitchen-sink imports `@ai-sdk/gateway` in `fsdev.config.ts`) — add the missing `typecheck` scripts to both as part of this change, or gate them via their build.
