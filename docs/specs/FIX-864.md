# FIX-864: Harness Layer — Evaluate Adopting v7 `HarnessAgent` vs. Maintaining Bespoke Claude Code / Codex Adapters — Implementation Spec

## 1. TLDR

**Plain-language summary.** We hand-built the plumbing that lets FSD drive external coding agents like Claude Code — code that turns each agent's output into our format, keeps its session alive between requests, and wires up tool approvals. AI SDK 7 now ships a "harness layer" that claims to do most of that plumbing for any coding agent behind one interface. Before we build a *second* hand-built adapter for OpenAI Codex (FIX-797), we should actually try the upstream one on a real run and decide, with evidence, how much of ours to keep. This spec doesn't build the migration — it defines a small throwaway prototype (Claude Code behind the harness layer, side-by-side with our existing adapter), a fixed scorecard to compare them on, and a written recommendation that also tells the Codex work whether to change course. It leads with a provisional answer (adopt the harness layer as a thin engine *under* our glue, not as a replacement for it), and names exactly what evidence would flip that answer.

**Technical statement.** Produce an evidence-backed build-vs-adopt decision on AI SDK 7's experimental `HarnessAgent`, via a throwaway prototype that maps one harness's `Agent`-interface stream into canonical FSD items once and is scored against the bespoke `@flow-state-dev/claude-code/sdk` path on fidelity, session continuity, and HITL — then a recommendation that gates FIX-797 (Codex).

**Deliverables:**

- **Prototype (throwaway):** a Claude Code run driven through `HarnessAgent` in `apps/kitchen-sink/flows/_prototypes/harness-agent/`, with a single stream→FSD-item adapter, run side-by-side against the bespoke `/sdk` block.
- **Scorecard:** a filled comparison matrix (`docs/internal/spikes/FIX-864-harness-layer.md`) across the four issue axes — item-stream fidelity, session park/resume vs `sdkSessionId`+`BindingProvider`, HITL/approval, and DevTool/item-log surfacing — plus the structured-output and stability findings.
- **Subsume-vs-irreducible ledger:** explicit list of what `HarnessAgent` subsumes (process/session lifecycle, sandbox, interrupt/resume, raw-message translate) vs. what stays FSD glue (item mapping + provenance/`ownedBy`, envelope, session-state persistence, capability declaration, resolver seams, suspension-based HITL).
- **Recommendation + FIX-797 decision:** a written verdict (adopt-as-thin-seam / keep-bespoke / wait), with the Codex retarget decision gated on named prototype findings.
- **No production code, no public API, no `apps/docs` changes.** The output is a prototype and a decision record.

**Size:** Medium (one throwaway prototype flow + one real-run comparison + a decision record; the code is disposable, the analysis is the deliverable). **This is a Prototype/Design/Decision issue, not a feature or a migration.**

## 2. Overview

Linear issue: [FIX-864](https://linear.app/fixpoint-labs/issue/FIX-864). FSD integrates external agent harnesses by hand: `@flow-state-dev/claude-code/sdk` (FIX-671, Done) carries its own `translate` / `emit` / `session` machinery to turn Claude Code SDK messages into canonical FSD items, resume by persisted `sdkSessionId`, and adapt HITL onto the SDK's `canUseTool`. FIX-797 plans a parallel *bespoke* Codex adapter. AI SDK 7 now ships an experimental harness layer whose `HarnessAgent` implements the AI SDK `Agent` interface and claims to subsume much of that per-harness plumbing.

This issue is the **decision gate**, not the migration: prototype one harness behind `HarnessAgent`, score it against the bespoke path, and recommend whether FSD's harness integration should sit *on top of* `HarnessAgent` (map its `Agent` stream to FSD items once, for all harnesses) or stay bespoke where our model needs more than the abstraction exposes. The output explicitly informs FIX-797 before it is built.

**This issue is now unblocked.** FIX-859 (the AI SDK 6→7 upgrade) landed, so `ai@7` is in the workspace and the prototype can be built hands-on rather than reasoned about on paper.

## 3. Background & Research

### 3.1 The bespoke path today (verified in code)

The in-process adapter (`packages/claude-code/src/sdk/`) is a "Level 2" adapter: the external SDK owns its agentic loop and built-in tools; FSD only observes, translates, and persists.

| Concern | Where | What it does |
|---|---|---|
| **Envelope** | `shared/handle.ts` | `RemoteAgentSource = "cli-remote" \| "sdk"`; `RemoteAgentStatus = "dispatched" \| "running" \| "completed" \| "errored"`; `RemoteAgentTaskHandle { source, status, sessionId, url, dispatchedAt }`. Note: "widening it is a coordinated change." |
| **Translate (pure)** | `sdk/translate.ts` | SDK message → `TranslatedEvent[]`. Handles `system`/`assistant`/`user`/`stream_event`/`result`; tracks open tools + sub-agents (`Agent`/`Task`); distinguishes whole-message vs partial-delta paths. No `ctx`, no I/O — fully unit-testable. |
| **Emit (ctx-driven)** | `sdk/emit.ts` (627 LOC) | Turns events into canonical items: `message`, `reasoning`, `tool_output`, `container` (sub-agents, via synthetic `blockInstanceId` + `ownedBy`), `status`, `error`. Hand-mirrors `packages/core/src/blocks/generator.ts`'s item lifecycle. |
| **Session** | `sdk/session.ts` + `agent.ts` | `ClaudeAgentSession { sdkSessionId }`; `createClaudeAgentSessionProvider()` satisfies `BindingProvider`; persists `sdkSessionId` + appends run handles to `sdkAgentRuns` in session state; resumes via SDK `options.resume`. Host may wrap in `createBindingCache` (`packages/core/src/bindings/createBindingCache.ts`). |
| **HITL** | `agent.ts` `buildCanUseTool` | Optional `onToolApproval` seam adapted onto SDK `canUseTool`; each decision dropped as a **durable audit `status` item**; deny continues the run. Degrades to the SDK's `permissionMode` when unset. |
| **Resolver** | `sdk/sdk-client.ts` (`ResolveClaudeAgent`) | Host supplies the SDK `query` entry point; trivially mockable; SDK is an optional peer dep. |

**Item taxonomy is a fixed, closed set** (`docs/architecture/items.md`): conversational (`message`, `reasoning`, `tool_output`), structural (`container`, `status`, `error`, `component`, `source`, …), trace (`block_trace`, …). Any harness mapping must land in this set. Sub-agent nesting is *only* expressible via `container` + `ownedBy`.

**No DevTool-specific code path exists** for external-agent runs (grep of `packages/devtool` for claude-code symbols: zero hits). Runs surface entirely through the generic canonical-item pipeline plus the handler's auto-emitted `block_trace`. The `SdkAgentHandle` (with `toolsObserved`/`usage`/`costUsd`/`resultSubtype`) is returned as block output and persisted; nothing renders it specially.

**Contrast with FSD generators:** `createAiSdkModelResolver.ts` gives FSD a `GeneratorModel` (`generate`/`stream`) where **FSD owns the agentic loop** over an AI-SDK *model*. The claude-code adapter is the opposite: the *external SDK owns the loop*. `HarnessAgent` sits between these — an external loop exposed behind the AI-SDK `Agent` interface.

### 3.2 AI SDK 7 harness layer (verified via ai-sdk.dev docs + Vercel changelog + GitHub issues, mid-2026)

- **`HarnessAgent` implements the AI SDK `Agent` interface** — `generate()` / `stream()` are shape-compatible with existing AI-SDK integrations. Official adapters: **Claude Code, Codex, Pi, OpenCode, Deep Agents**.
- **Provides:** sandbox configuration, custom instructions / skills / tools injection, session **park/resume**, mid-turn **interrupt/resume**. Stream surfaces text + reasoning + tool parts; file-changes/compaction are reported as provider-executed dynamic tool parts (this last mapping is from a search summary, not a primary line read — flagged below).
- **`experimental` status.** Marked unstable; breaking-change churn is expected.
- **Blocker #16120 (open): no structured output.** `HarnessAgent`'s `OUTPUT` type parameter is pinned to `never`; `generate`/`stream` resolve to text only, even though Claude Code (`outputFormat: json_schema`) and Codex (`outputSchema`) both support it natively. Consumers must hand-parse JSON from `result.text`. **For a workflow framework running a staged spec→implement→review pipeline (FIX-832), this is the single most consequential gap.**
- **HITL is uneven.** A uniform `toolApproval` callback covers *host* tools; *built-in* tools are gated per-harness via `permissionMode` (Claude Code: `allow-reads`/`allow-edits`; **Codex: none, needs `allow-all`**; OpenCode: documented headless auto-rejection bug #16380). There is **no single unified approval path across harnesses for built-in tools.**
- **Codex transport is unconfirmed.** Docs describe a "WebSocket bridge over thread events"; whether the adapter rides `codex exec --json` (the JSONL surface FIX-797 depends on) and preserves `resume <id>` / `--output-schema` is **not verified** from a primary source.

### 3.3 Why a prototype, not a paper decision

The four Open Questions on the issue (item-stream fidelity, park/resume vs `sdkSessionId`, `experimental` stability, DevTool surfacing) all turn on behavior the docs don't pin down, and agent C's research left the exact `Agent` stream-part enumeration, the v1 adapter interface, and per-harness Claude Code fidelity **unverified**. Those are precisely the questions a one-run side-by-side answers definitively and a doc read cannot. `fsd:prototype` (logic prototype) is the right instrument.

### 3.4 Necessity verdict

**Build as scoped.** This is not a wrapper-over-primitive feature request — it is an architecture decision that (a) prevents a wasted *second* bespoke adapter (FIX-797), (b) de-risks the dev-orchestration bet (FIX-832) against the #16120 blocker, and (c) is the first real test of whether the "source-agnostic envelope" generalizes. The gate's don't-build signals (boolean toggle, single-vendor leakage, 1–3 line user-space equivalent) do not apply; design/decision issues are explicitly in-scope for a spec. The deliverable is a prototype + decision record, and the spec scopes it tightly to avoid it sprawling into the migration itself.

### Key Decisions & Ramifications (top 5)

1. **Scope = prototype + decision record, explicitly NOT the migration.** Alt: fold the rework of `@flow-state-dev/claude-code` / retarget of FIX-797 into this issue. Rejected — the issue names itself an evaluation and defers the rework. Locks in: no production code, no envelope widening, no public API change here. Ramification: a follow-up implementation issue carries the actual adoption (and its user-facing docs) if the recommendation says "adopt."
2. **Prototype Claude Code (not Codex) as the control.** Alt: prototype Codex first (the undecided one). Rejected — FIX-671 is Done and its fidelity bar is *known*, so Claude Code is the apples-to-apples baseline; Codex adds an unknown-adapter variable on top of an unknown-abstraction variable. Ramification: Codex fidelity is *inferred* from the Claude Code result + a short targeted spike, not measured end-to-end here (named as an Open Question).
3. **Provisional recommendation: adopt `HarnessAgent` as a thin engine *under* FSD glue, not a replacement for it.** Alt A: rip-and-replace bespoke with `HarnessAgent`. Alt B: reject and stay fully bespoke. The research shows `HarnessAgent` cleanly subsumes process/session lifecycle + raw translate, but item-mapping/provenance/session-persistence/HITL are irreducibly FSD. Ramification: FSD maps the `Agent` stream *once* for all harnesses (retiring per-harness translate), while the envelope, capability, session-state, and suspension-HITL stay FSD-owned. This is provisional — the prototype can refute it.
4. **Do NOT block FIX-797 on adoption; gate it on a named finding.** The #16120 structured-output blocker plus unverified Codex transport fidelity put FIX-797's machine-readable / `--output-schema` / `resume` advantages *at risk* under `HarnessAgent`. Ramification: retarget FIX-797 onto the shared seam *iff* the prototype (+ Codex spike) shows the Codex adapter preserves `exec --json`-grade observability and resume; otherwise keep it bespoke. The decision is deferred to evidence, not made blind — and either way FIX-797 stops waiting on this issue once the finding lands.
5. **Treat #16120 (no structured output) as a gating risk for FIX-832, not a footnote.** Alt: note it and move on. Rejected — a staged spec→implement→review loop needs *validated* structured decisions; `HarnessAgent` forces hand-parsing `result.text`. Ramification: the recommendation must either keep structured-output-critical stages on FSD generators (not `HarnessAgent`) or make adoption contingent on #16120 closing. This shapes whether `HarnessAgent` can underpin the orchestrator at all.

## 4. Technical Design

The "implementation" here is a throwaway measurement rig, not a shipped feature. Its job is to make the four issue axes observable on one real Claude Code run.

### 4.1 Prototype architecture

Location: `apps/kitchen-sink/flows/_prototypes/harness-agent/` (throwaway; deleted after the decision lands, per `fsd:prototype`).

Two runnable paths over the **same prompt + same real Claude Code auth**:

- **Path A (baseline):** the existing `claudeCodeAgent` block (`@flow-state-dev/claude-code/sdk`), unchanged.
- **Path B (candidate):** a `HarnessAgent` (Claude Code adapter, `ai@7`) wrapped in a **single FSD adapter block** that consumes `harness.stream()` (the `Agent` interface) and maps each stream part to canonical FSD items — reusing the *emit* item-lifecycle idiom but driven by the `Agent` part vocabulary instead of `SdkMessageLike`.

The adapter block is deliberately minimal: prompt in → `harness.stream()` → map parts → FSD items → return a `RemoteAgentTaskHandle`-shaped result. It reuses the existing envelope and session-state shape so the comparison isolates *the mapping*, not the surrounding glue.

### 4.2 The comparison scorecard (the actual deliverable shape)

Filled in `docs/internal/spikes/FIX-864-harness-layer.md`:

| Axis | Baseline (bespoke) | Candidate (`HarnessAgent`) | Verdict |
|---|---|---|---|
| **Item-stream fidelity** | assistant text, reasoning/thinking, tool_call+result, sub-agent `container`/`ownedBy`, status, error | which of these does the `Agent` stream expose? what is lost/merged? are sub-agents distinguishable? | parity / gap list |
| **Session continuity** | `sdkSessionId` + `BindingProvider` resume-by-id; `sdkAgentRuns` handle log | does harness park/resume map onto persisted-id resume? one turn, then resume next request | parity / gap |
| **HITL / approval** | `onToolApproval` → `canUseTool`, durable audit status items, deny-continues | `toolApproval` (host tools) + `permissionMode` (built-ins); can a per-tool decision be observed + audited? | parity / gap / *replace-with-suspension* |
| **DevTool / item-log** | generic canonical pipeline + `block_trace` | same, if mapping lands in the fixed taxonomy | parity expected |
| **Structured output** | handler returns typed handle; generator stages use `Output.object` | #16120: text-only, hand-parse `result.text` | **gap (gating)** |
| **Stability** | our code, our churn | `experimental`; #16120/#16380 open | risk note |

### 4.3 Subsume-vs-irreducible ledger (provisional, prototype confirms)

- **`HarnessAgent` subsumes:** subprocess/session lifecycle, sandbox config, interrupt/resume, and the *raw-message translate* layer (`translate.ts` + the `SdkMessageLike` structural types) and the generic streaming-coalescence parts of `emit.ts`.
- **Irreducible FSD glue:** the `RemoteAgentTaskHandle`/`SdkAgentHandle` envelope; provenance/`itemIndex`/`ownedBy` stamping tied to `ctx`; `BindingProvider`-based `sdkSessionId` persistence + `sdkAgentRuns`; the capability + session-state declaration; the resolver seams; and item classification into the fixed taxonomy.
- **Should be *replaced*, not subsumed:** the HITL seam. FSD has first-class durable suspension (`ctx.suspend()` + `suspension`/`suspension_resume` items + `ResumeAction[]`, `packages/core/src/types/suspension.ts`); the `buildCanUseTool` audit-status approach is a shallower reinvention. The recommendation should route harness approvals through suspensions regardless of the adopt/keep verdict.

### 4.4 Data flow (candidate path)

`prompt` → adapter block resolves harness (host-supplied, mockable like `ResolveClaudeAgent`) → `harness.stream({ prompt, resume? })` → for each part: classify → `ctx.emit.*` canonical item (nesting sub-agent parts under a `container` via `ownedBy`) → on finish, persist session id + append handle → return handle. Identical envelope/session shape to Path A by construction.

### 4.5 Error handling

Prototype-grade: surface adapter/stream errors as an `error` item + rethrow (mirrors `agent.ts`). No new error taxonomy — this is a spike. The *analysis* records any harness failure modes (e.g., #16380-style spawn failures) as stability findings, not as code to harden.

## 5. Implementation Sequence

1. **Scaffold the prototype flow** in `apps/kitchen-sink/flows/_prototypes/harness-agent/` with Path A (existing block) wired to a real Claude Code run. Verify: baseline emits the expected item stream via `fsdev run`.
2. **Add the candidate adapter block** consuming `HarnessAgent` (Claude Code adapter) `.stream()`, mapping parts → FSD items. Verify: Path B produces *some* item stream on the same prompt.
3. **Run side-by-side** on a fixed prompt that exercises text + reasoning + a tool call + a sub-agent spawn. Capture both item streams (NDJSON). Verify: both complete; diff the streams.
4. **Fill the scorecard** (§4.2) axis by axis from the captured runs. Verify: every axis has a parity/gap verdict backed by an observed run, not an assumption.
5. **Probe session resume** — one turn, then a second request that resumes — on both paths. Verify: resume continues the same conversation (or document the gap).
6. **Codex spike (targeted, time-boxed):** confirm whether the `HarnessAgent` Codex adapter rides `codex exec --json` and preserves `resume` + `--output-schema`, or degrades them. Verify: a one-paragraph finding with the FIX-797-gating answer.
7. **Write the decision record** (`docs/internal/spikes/FIX-864-harness-layer.md`): scorecard + ledger + recommendation + FIX-797 verdict + FIX-832 risk note.
8. **Tear down the prototype** (delete the `_prototypes/harness-agent/` flow); the decision record is the durable artifact. Verify: no throwaway code left in the tree.

Steps 1→2→3→4 are strictly ordered (each needs the prior). 5 and 6 can run after 3. 7 needs 4–6.

## 6. Edge Cases & Error Handling

| Case | Expected handling in the prototype |
|---|---|
| Harness stream omits reasoning parts | record as a **fidelity gap** in the scorecard; do not synthesize |
| Sub-agent parts not distinguishable in `Agent` stream | record gap; note that FSD `container`/`ownedBy` nesting cannot be reconstructed → a real fidelity loss |
| `#16120` blocks a structured stage | expected; the scorecard's structured-output row captures it; not "fixed" here |
| Codex adapter is WebSocket-bridge, not `exec --json` | record as the FIX-797-gating finding; do not force it |
| Harness `experimental` API differs from docs | the prototype *is* the source of truth; update the ledger to match observed behavior |
| Real auth/model unavailable in the run env | the goal check is out-of-CI and manual (real Claude Code); document if it couldn't run rather than faking parity |

No error *taxonomy* is in scope — this is a measurement rig, and failures are data, not defects to harden.

## 8. Non-Goals

- **The migration itself** — reworking `@flow-state-dev/claude-code` onto `HarnessAgent`, or retargeting FIX-797, is follow-on work gated on this recommendation.
- **Widening the `RemoteAgentSource` / `RemoteAgentStatus` envelope** — a coordinated change owned by whichever adoption issue follows.
- **Building the Codex adapter** — FIX-797; this issue only decides *bespoke vs. ride-the-seam* for it.
- **Fixing #16120 / #16380** — upstream AI SDK issues; we observe and route around them, we don't patch them.
- **Productionizing the prototype** — it is deleted after the decision record lands.
- **Deepening opportunities flagged during research (follow-ups, not this issue):**
  - *HITL bypasses FSD's first-class suspension.* `buildCanUseTool` drops audit `status` items instead of using `ctx.suspend()` + `suspension`/`suspension_resume`. The single biggest conceptual duplication and directly relevant to any harness HITL story — follow up via `fsd:improve-codebase-architecture`. **Note for the follow-up:** routing approvals through `ctx.suspend()` is a *behavioral* change, not a pure refactor — today a deny fire-and-continues (the SDK surfaces the denial to the model mid-run); a real suspension *blocks* execution until a `ResumeAction` arrives. The "replace, not subsume" phrasing above is therefore a semantics change worth scoping deliberately, not a like-for-like swap.
  - *Hand-built item lifecycle duplicated from `generator.ts`.* `emit.ts` re-implements provenance/`itemIndex`/id-minting and four near-identical message/reasoning open/close helpers. A shared core item-lifecycle helper would collapse these (plausibly ~150–250 of `emit.ts`'s 627 lines) and is exactly the surface a harness adapter would standardize on.
  - *`deriveProvenance` reads `ctx._blockIdentity` via an inline cast* (`emit.ts`) — private-context coupling; a supported accessor would be cleaner. **Scope the follow-up repo-wide, not `emit.ts`-local:** the same unsafe `_blockIdentity` cast recurs at 5+ call sites (`patterns/task-board/index.ts`, `engine/createExecutionContext.ts`, `engine/runAction.ts`, `engine/executeBlock.ts`, `emit.ts`), so the fix is a shared supported accessor across the repo, not a one-off here.
- **Doc-drift fix (mention, don't fix here):** the FIX-125 design doc places `createBindingCache` in `@flow-state-dev/engine`; it actually lives in `@flow-state-dev/core` (`packages/core/src/bindings/createBindingCache.ts`). Worth a one-line correction in a later pass.
