# FIX-865: DevTool — continue interrupted runs and verify they resume (not restart), across concurrent flows and background work — Implementation Spec

> **Linear issue:** [FIX-865](https://linear.app/fixpoint-labs/issue/FIX-865/devtool-continue-interrupted-runs-and-verify-they-resume-not-restart)
> **Necessity verdict:** Build as scoped. The background-work outcome is satisfied by honest display (the issue explicitly allows "see honestly that it did not"), not by new durability machinery — durable background work (FIX-815) was canceled.

## 1. TLDR

**Plain-language summary.** The framework can already pick an interrupted run back up where it stopped, but our developer tool can only do that for the single most recent run, and even then it secretly starts the run over instead of continuing it. This change lets a developer see *every* interrupted run in the tool, continue any of them with one click, and actually *watch* it resume — a clear marker in the trace shows which work was replayed from the durable log and which ran fresh. It also tells the honest truth about background (fire-and-forget) work: that work re-runs from scratch on continue today, it does not resume, so the tool labels it that way rather than pretending.

**Technical statement.** Add a per-run "Continue" affordance to the DevTool wired to the existing `/continue` route, and emit a new `continuation` boundary item from the engine on crash-recovery re-entry so the replay/live boundary is visible; display background (`phase: "work"`) re-execution honestly.

**Deliverables (grouped by area, mirroring §5):**

- **Engine:** Emit a `continuation` boundary item in `continueRequest`/`runAction` at the interrupted→in_progress point-of-no-return in `packages/engine/src/execution/`, carrying the replayed-item count and the resume path.
- **Contracts:** Add `ContinuationItem` (`type: "continuation"`) to the item taxonomy in `packages/contracts/src/items/types.ts` and the `OutputItem` union (visibility falls through to the structural default `{ client: true, history: false }` automatically — no visibility-map edit).
- **DevTool:** Add a per-run **Continue** action (gated on `status === "interrupted"`) to `RequestSeparator` in `packages/devtool/src/react/.../request-separator.tsx`, wired to `recoveryClient.continue()`; surface all interrupted runs in the session, and render the `continuation` item as a replay-boundary divider in stream + trace views.
- **Client:** (parity) add `continueStream()` to `createRecoveryClient` in `packages/client/src/recovery-client/recovery.ts` mirroring `resumeSuspensionStream()`.
- **Docs:** Extend the DevTool overview "Replay" section; add `continuation` to `docs/architecture/items.md`; cross-link the durability advanced pages.

**Size estimate:** Medium (multi-file, single PR, ~250–400 LOC across engine/contracts/devtool/client + docs). No multi-PR split required; the engine item and the DevTool surface are small and land together so the marker has a renderer.

## 2. Overview

The durability substrate (single-request continuation via `continueRequest`, FIX-811) is shipped and exercised by the engine, but it cannot be *trusted through the DevTool* in the cases that matter: several runs interrupted at once, and background sidechains. Today the DevTool only offers to recover the latest request on a session, and that affordance actually performs a `/retry` (a fresh run under a new id) — a restart presented as a resume.

This spec makes interruption-recovery legible and per-run: every interrupted run in the session is individually continuable from the tool via the real `/continue` verb, and a new `continuation` boundary item makes "resumed from here" visible in the trace so a continue is distinguishable from a restart by eye. Background work is shown honestly — it re-runs fresh on continue (it does not resume), which is the true current behavior after FIX-815 was canceled.

## 3. Background & Research

### 3.1 How the codebase solves this today

The continue path already exists **end-to-end at per-request granularity** — only the DevTool surface is latest-only:

- **Engine route (per-request, any id).** `POST /:flowKind/sessions/:sessionId/requests/:requestId/continue` is registered in `packages/engine/src/routes/router.ts:150-161` (`continue_request`) and handled by `handleContinueRequest()` in `packages/engine/src/routes/recovery-routes.ts:142-224`. It requires `status === "interrupted"` (L177-181), acquires an exclusive-continuation lease (L188-196), and calls `ctx.host.continueRequest({ requestId })` (L201) — same id, no `resumeContext`. Returns 202 JSON or an SSE stream when `Accept: text/event-stream` (L203-216).
- **Three distinct verbs.** `/retry` mints a **new** request id; `/resume` re-enters the same id for a **suspended** HITL gate (body `{ suspensionId, action, data? }`); `/continue` re-enters the same id for an **interrupted** crash record. `continueRequest` is the shared re-entry (`packages/engine/src/execution/request-continuation.ts:57-173`; host type `packages/engine/src/transports/types.ts:243-245`).
- **Discovery is already multi-request.** `detectInterruptedRequests()` (`packages/engine/src/execution/request-recovery.ts:30-76`) sweeps **all** stale `in_progress` records to `interrupted`; `handleCheckInterruptedRequests()` (`recovery-routes.ts:262-302`) exposes `POST /api/flows/users/:userId/check-interrupted` returning the swept list. The DevTool already calls the sweep on mount/refresh (FIX-467).
- **Client already has `continue`.** `createRecoveryClient()` (`packages/client/src/recovery-client/recovery.ts:150`) exposes `continue({ flowKind, sessionId, requestId })` (L202-217) and `checkInterrupted({ userId, staleThresholdMs })` (L154-171). The per-request continue plumbing is present and unused by the UI.
- **Replay log replays main-chain block outputs.** `ReplayLog` (`packages/core/src/blocks/internal/replay-log.ts:48-184`) injects the canonical completed `block_trace.output` (highest-`itemIndex` `status === "completed"` record) for each logical block path and resolves pending suspensions. Completed blocks are not re-executed; the in-flight block re-runs.
- **HITL resume already has a boundary item.** `suspension_resume` (`SuspensionResumeItem`, `packages/contracts/src/items/types.ts:572-584`) is emitted at re-entry (`runAction.ts:1100-1121`) right after the matching `suspension` item. **Crash-recovery `/continue` emits no equivalent marker** — items simply continue; the boundary is only implicit in `itemIndex` ranges.
- **Background phase is already tagged.** Every item carries `provenance.phase: "main" | "work"` (`packages/contracts/src/items/types.ts:25-34`); the DevTool renders a "BG" badge from it (`packages/devtool/src/react/lib/trace-tree.ts:44-51`). Nested blocks under a `.work()` dispatch inherit `phase: "work"`.

### 3.2 The background-work reality (the load-bearing finding)

Background work **does not survive or resume** a continue today. On re-entry, `continueRequest` builds a new execution context with a **fresh, empty** request-scoped work pool (`createRequestWorkPool()` in `packages/engine/src/context/createExecutionContext.ts:2017`; pool impl `packages/engine/src/execution/request-work-pool.ts`). `ReplayLog` only replays completed main-chain block outputs; there is no replay mechanism for background tasks. So a block that called `.work()` re-executes on continue and dispatches **fresh** `.work()` tasks to the new pool. Any side effects that completed before interruption persist (and may therefore double-fire); in-flight background work from the dead process is gone. The pool is drained exactly once before terminal status (`runAction.ts:1356-1368`).

This is the framework reality after **FIX-815 (durable detached `spawn`) was canceled**. The issue anticipates it ("it may surface a framework gap … see honestly that it did not"). The spec therefore *displays* this honestly rather than trying to fix durability — that fix is a separate, much larger effort and is a non-goal (§8).

### 3.3 Industry framing

Durable-execution systems (Temporal, Inngest, Restate, DBOS) all separate "continue the same run from its journal" from "start a new run," and all provide *replay visibility* — a UI that shows which steps were replayed from history vs newly executed (Temporal's "event history" with replay markers is the canonical example). The `continuation` boundary item is the minimal version of that idea: one audit record at the replay/live seam, mirroring the `suspension_resume` precedent we already ship. No external dependency is warranted; this is small, framework-native instrumentation.

### 3.4 Why a new engine item (not DevTool-only computation)

A boundary that lives only in DevTool-private logic can't be consumed by other clients, the kitchen-sink, or tests, and is fragile against item-log merge ordering. A persisted `continuation` item mirrors the existing `suspension_resume` design exactly (same visibility shape, same renderer pattern), is reusable beyond the DevTool, and makes the boundary part of the durable record — so a `GET` on the request shows the seam, and the goal check can assert on it without scraping the UI.

### 3.5 Key Decisions & Ramifications (top 5)

1. **Emit a new `continuation` item from the engine at the continue boundary** (rejected: compute the boundary in DevTool only). Locks the replay/live seam into the durable log as a first-class, client-visible audit record reusable by any consumer and assertable in tests. Ramification: adds one entry to the locked item taxonomy (`items.md`) and a renderer everywhere items render; a permanent, small piece of public item surface. Rules out a zero-framework-change DevTool-only hack.
2. **Display background work honestly as "re-runs fresh on continue," do not make it durable** (rejected: fix durability here). Keeps scope to a DevTool enabler and tells the truth about current behavior. Ramification: a stated issue outcome ("background work survived") is answered in the negative-but-honest direction; developers see (and the docs warn about) possible double-fired side effects. Durable background remains future work (canceled FIX-815 would need re-opening).
3. **Per-run Continue on every interrupted run in the session, wired to the existing `/continue` route** (rejected: batch "continue all"; project-wide multi-app). Smallest surface that satisfies the concurrent-runs ask, and the route + client method already exist. Ramification: multi-app/project-wide continue (FIX-821) and batch continue are deferred; the tool operates within one inspected app/session at a time.
4. **DevTool-only via `recoveryClient.continue()`; do not add per-request continue to public `useSession`** (rejected: extend `SessionView`). Minimizes public React surface (BP-038); `useSession`'s latest-only resume is untouched. Ramification: host apps (kitchen-sink) don't gain per-request continue from this issue; if they need it later it's an additive `useSession` method. The existing `resumeLatestRequest`-does-retry mislabel is left to FIX-637.
5. **`continuation` marks only the crash-recovery `/continue` boundary; `/resume` keeps `suspension_resume`** (rejected: one unified marker on both paths). Avoids double-marking the HITL case and keeps each audit record semantically precise. Ramification: the DevTool divider logic must treat *either* item as a boundary; two item types express "execution re-entered here" for two triggers.

## 4. Technical Design

### 4.1 Architecture / packages touched

- `@flow-state-dev/contracts` — new `ContinuationItem` type + union/visibility wiring (item taxonomy is here; re-exported by `core`).
- `@flow-state-dev/engine` — emit the item at the continue point-of-no-return; ensure it merges into the persisted log.
- `@flow-state-dev/devtool` — per-run Continue action, interrupted-run surfacing, boundary divider renderer.
- `@flow-state-dev/client` — optional `continueStream()` parity method.
- Docs — `docs/architecture/items.md`, `apps/docs/docs/devtool/overview.md`, cross-links.

### 4.2 New item: `ContinuationItem`

In `packages/contracts/src/items/types.ts`, mirroring `SuspensionResumeItem`:

```ts
export type ContinuationItem = OutputItemBase & {
  type: "continuation";
  /** Why re-entry happened. Crash-recovery /continue today; reserved for future triggers. */
  trigger: "recovery";
  /** Number of items replayed from the durable log before this boundary (the seam position). */
  replayedItemCount: number;
  /** Logical block path where live execution resumed (the in-flight block re-run). */
  resumedAtPath?: string;
  continuedAt: number;
};
```

- Add `ContinuationItem` to the `OutputItem` union (`types.ts:586-598`).
- Visibility resolves **automatically** to the structural default `{ client: true, history: false }` (non-transient). `resolveItemVisibility` (`packages/contracts/src/items/resolve-visibility.ts:37-45`) keys off type-set membership — a type in neither `TRACE_TYPES` nor `CONVERSATIONAL_TYPES` falls through to the structural default, exactly as `suspension_resume` does. So the only requirement is to **not** add `continuation` to those sets; there is no explicit visibility-map entry to add.
- Update `docs/architecture/items.md` taxonomy (locked-contract doc) with the new type and its classification.

### 4.3 Engine: emit the boundary

In the crash-recovery re-entry path (`continueRequest` / `runAction`), at the point-of-no-return where status transitions `interrupted → in_progress` after the `ReplayLog` is built but before any block executes (`runAction.ts:1091-1093` is the analogous seam where `suspension_resume` is emitted at L1100-1121):

- Emit one `ContinuationItem` **only** when re-entry is crash-recovery (replay mode, no pending suspension / no `resumeContext`). The `/resume` path keeps emitting `suspension_resume` and must **not** also emit `continuation`.
- `replayedItemCount` = number of items in the prior persisted log being replayed (the seam index; derivable from the prior log length / completed-trace count). `resumedAtPath` (optional) = the logical path of the in-flight block about to re-run. **Note:** `ReplayLog` does not expose this for crash recovery — its `pendingSuspension()` is suspension-keyed and returns `undefined` here — so the implementer derives it (e.g. the highest non-`completed` block path) or leaves it `undefined`. The field is optional precisely so the divider works without it.
- The item is appended at re-entry, so in the merged log (`mergeItemsById`, `runAction.ts:256-271`) it lands after replayed items (lower `itemIndex`) and before freshly executed items. No change to merge semantics needed.

### 4.4 Client (parity, optional)

Add `continueStream(flowKind, sessionId, requestId): Promise<Response>` to `RecoveryClient` (`packages/client/src/recovery-client/recovery.ts`), mirroring `resumeSuspensionStream()` (L239-266) — same `/continue` URL with `Accept: text/event-stream`. The existing `continue()` (202 JSON) remains; the DevTool's stateful local server can also just call `continue()` and rely on its existing per-request SSE subscription to receive new events. Parity method exists for inline-streaming (serverless) parity with resume.

### 4.5 DevTool: surface + render

- **Surface all interrupted runs.** `useSessionRequests` already fetches all requests in the active session with status; the sweep on mount (FIX-467) keeps `interrupted` fresh. No new query needed — filter/annotate `status === "interrupted"`.
- **Per-run Continue action.** In `RequestSeparator` (`packages/devtool/src/react/.../workspace/request-separator.tsx:68-207`), add a `Continue` entry to the overflow menu / a prominent inline button, gated on `status === "interrupted"` (the existing Replay/Reconnect entries gate on completed/failed, L84). Wire to a new `onContinueInterrupted(requestId)` handler in the panel that calls `recoveryClient.continue({ flowKind, sessionId, requestId })` and ensures the panel is subscribed to that request's stream (reuse `useRequestStream`/reconnect) so the continuation streams live. Each interrupted run has its own separator, so concurrent runs are individually continuable.
- **Boundary divider.** Register a renderer for `type: "continuation"` (and treat `suspension_resume` likewise) in the DevTool item renderer, drawing a labeled divider ("Continued from here — N items replayed") in both stream view (`workspace/stream-view.tsx`) and the trace tree. Items above the divider are replayed; items below ran fresh. Background re-runs appear below the divider with their existing BG badge — making "background re-ran fresh" visually self-evident.

### 4.6 Data flow (continue)

1. DevTool lists session requests; one or more show `interrupted`.
2. Developer clicks **Continue** on a specific interrupted run → `recoveryClient.continue({ flowKind, sessionId, requestId })`.
3. Engine `handleContinueRequest` validates (`interrupted`, session scope, non-webhook), takes the lease, calls `continueRequest({ requestId })`.
4. Re-entry builds `ReplayLog`, transitions `interrupted → in_progress`, emits the `continuation` item, replays completed blocks (no re-execution), re-runs the in-flight block; `.work()` calls re-dispatch fresh.
5. Items merge into the same request's log; DevTool's subscription receives them and renders the divider + fresh (incl. BG) items below it.

### 4.7 Error handling

| Case | Behavior |
| --- | --- |
| Continue a non-`interrupted` request | Route already rejects (status guard, `recovery-routes.ts:177-181`); DevTool only shows the action for `interrupted`. |
| Concurrent double-continue of one run | Exclusive-continuation lease (`recovery-routes.ts:188-196`) → second attempt conflicts; DevTool surfaces the error, leaves status unchanged. |
| Webhook-source request | Route rejects (`recovery-routes.ts:160-162`); no Continue action shown. |
| Wrong session/flow scoping | Route validation 404/400; DevTool only issues ids it listed. |
| Continue fails mid-stream | Request stays `interrupted` (or transitions per engine); DevTool shows error, Continue remains available to retry. |

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
| --- | --- |
| No interrupted runs in session | List shows none with Continue; no error. |
| Interruption inside a **generator/router** (not sequencer) | Sequencer-level continue only (FIX-814 not landed): the in-flight generator/router re-runs from its block boundary; completed sibling blocks still replay. Divider still renders. Document this as the current ceiling. |
| Background block with external side effects (email, payment) ran before interruption | On continue it **re-runs fresh** → side effect may double-fire. Display honestly (BG badge below divider) and warn in docs. Not fixed here. |
| `replayedItemCount === 0` (interrupted before any block completed) | Divider renders at the top ("0 items replayed"); effectively a cold continue — honest. |
| Multiple suspend/continue cycles on one request | Each crash-recovery re-entry appends its own `continuation`; dividers stack in order. (HITL cycles use `suspension_resume`.) |
| Stale list (request completed elsewhere since sweep) | Continue → route rejects non-`interrupted`; DevTool refreshes the list. |

**Error taxonomy.** Lease conflict and status-guard rejections are non-retryable as-is (state changed) — surface and refresh. Network/stream failures are retryable — Continue stays available. No new error codes; reuse the route's existing responses.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (feature). Behaviours below each become a tracer-bullet cycle.

**Goal & goal check (required — applies).** *Goal:* a developer can continue an interrupted run and the run **continues, not restarts** — completed work is replayed (not re-executed) and the boundary is visible. *Goal check (real path, out of CI):* a `goals/continue-interrupted-run/` script (or `fsdev run`) that: starts a flow with a side-effect counter in an early handler, forces the request to `interrupted` after that handler completes (kill/sweep), calls `/continue`, then asserts on the real durable log: (a) exactly one `continuation` item with `replayedItemCount > 0`, (b) the early handler's side-effect counter did **not** increment again (replayed, not re-run), (c) the request reaches a terminal status under the **same** id. Prints PASS/FAIL. A second scenario starts two flows, interrupts both, continues each by id, and asserts both terminate independently. (No real LLM required — handler/sequencer flow suffices to prove continue-not-restart; richer generator validation is bounded by FIX-814.)

**CI specs (mocked, deterministic):**
- Engine: `continuation` emitted on crash-recovery continue only; correct `replayedItemCount`/`resumedAtPath`; not emitted on retry/fresh/resume. Completed blocks not re-executed on continue (existing replay test patterns).
- Engine: two interrupted requests in a session are each continuable by id (no latest-only coupling).
- Engine: a `.work()` block re-dispatches fresh on continue (item with `phase: "work"` appears after the boundary) — encodes the honest background behavior so a future durability change must consciously update it.
- Client: `continue()`/`continueStream()` target a non-latest request by id; correct route + headers.
- DevTool (component): Continue action renders iff `status === "interrupted"`; handler calls `recoveryClient.continue` with the row's id; `continuation` renders as a divider; background re-run renders below it with BG badge.

**Seams / references.** Engine item-log + replay tests under `packages/engine` (continue/replay specs from FIX-811); contracts item tests; DevTool component tests; `packages/integration-tests` for the cross-package continue-not-restart flow. Use `fsd:write-block-tests` mock-context idiom for any block-level specs.

## 8. Non-Goals

- **Tool-driven interrupt button.** The issue marks it optional; killing the server starts the test. Out.
- **Durable / recoverable background work.** Background work staying alive across a crash is the canceled **FIX-815** (`spawn` detached child). This spec displays current behavior honestly; it does not make background work durable.
- **resume-vs-retry contract & relabeling.** `resumeLatestRequest()` currently calls `/retry` (a restart mislabeled "resume"). Correcting the contract/affordance is **FIX-637**; this spec deliberately uses the true `/continue` verb for the new action and leaves `resumeLatestRequest` untouched.
- **Generator/router resume mechanism.** **FIX-814** (in spec review) owns mid-generator/mid-router continuation; until it lands, richer flows validate only to the sequencer ceiling (§6).
- **Project-wide / multi-app continue.** Continuing across apps/ports is **FIX-821** (backlog, unspecced). This spec stays within one inspected app/session.
- **Batch "continue all interrupted."** Per-run only; batch is a later convenience if it earns its place.
- **Per-block replayed/fresh shading.** The divider (replayed-above / fresh-below) is sufficient; per-block tagging of every `block_trace` is deferred.
- **Deepening opportunity (flag, not in scope):** `resumeLatestRequest()` conflating "resume" with a `/retry` restart is a latent correctness-of-label smell in `packages/react/src/hooks/useSession.ts`; fold into FIX-637 rather than this issue. Follow up via `fsd:improve-codebase-architecture` if it persists after FIX-637.
