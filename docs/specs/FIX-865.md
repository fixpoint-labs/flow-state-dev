# FIX-865: DevTool — continue interrupted runs and verify they resume (not restart), across concurrent flows and background work — Implementation Spec

> **Linear issue:** [FIX-865](https://linear.app/fixpoint-labs/issue/FIX-865/devtool-continue-interrupted-runs-and-verify-they-resume-not-restart)
> **Necessity verdict:** Build as scoped. Legitimate Enabler tooling that needs framework-side data (a new taxonomy item + DevTool/client/react integration), not wrapper-over-primitive. Completed background work already restores via the existing phase-agnostic replay; the crash-boundary edge cases are owned by a separate branch.

## 1. TLDR

**Plain-language summary.** The framework can already pick an interrupted run back up where it stopped, but our developer tool can only do that for the single most recent run. This change lets a developer see *every* interrupted run in the tool, continue any of them with one click, and actually *watch* it pick up where it left off — a clear marker in the trace shows where the prior, already-recorded work ends and the freshly-continued work begins. Background (fire-and-forget) work is accounted for too: completed background work is restored along with everything else; a couple of crash-timing edge cases are being handled on a separate branch.

**Technical statement.** Add a per-run "Continue" affordance to the DevTool (and a public `useSession.continueRequest`) wired to the existing `/continue` route via a new inline-streaming `continueStream()`, and emit a new `continuation` boundary item from the engine on crash-recovery re-entry so the prior-log / live-continuation boundary is visible.

**Deliverables (grouped by area, mirroring §5):**

- **Engine:** Emit a `continuation` boundary item in `continueRequest`/`runAction` at the interrupted→in_progress point-of-no-return in `packages/engine/src/execution/`, carrying the prior-log item count and the resume path.
- **Contracts:** Add `ContinuationItem` (`type: "continuation"`) to the item taxonomy in `packages/contracts/src/items/types.ts` and the `OutputItem` union (visibility falls through to the structural default `{ client: true, history: false }` automatically — no visibility-map edit).
- **Client:** Add `continueStream()` (inline-SSE POST) to `createRecoveryClient` in `packages/client/src/recovery-client/recovery.ts`, mirroring `resumeSuspensionStream()`; the existing JSON `continue()` stays as the non-streaming fallback.
- **React:** Add `continueRequest(requestId)` to the public `useSession` `SessionView` in `packages/react/src/hooks/useSession.ts`, using `continueStream()`.
- **DevTool:** Add a per-run **Continue** action (gated on `status === "interrupted"` and non-webhook source) to `RequestSeparator` in `packages/devtool/src/react/.../request-separator.tsx`; sweep stale requests as part of the row refresh; surface all interrupted runs in the session, and render the `continuation` item as a prior-log/live divider in stream + trace views.
- **Docs:** Extend the DevTool overview "Replay" section; add `continuation` to `docs/architecture/items.md` and the streaming item table; document `continueStream()`/`continueRequest()` in the client + react READMEs; cross-link the durability advanced pages.

**Size estimate:** Medium (multi-file, single PR, ~300–450 LOC across engine/contracts/client/react/devtool + docs). No multi-PR split required; the engine item and its renderer land together.

## 2. Overview

The durability substrate (single-request continuation via `continueRequest`, FIX-811) is shipped and exercised by the engine, but it cannot be *trusted through the DevTool* in the cases that matter: several runs interrupted at once, and reading the resume boundary. Today the DevTool's Resume button already uses the real `/continue` verb (`DevToolPanel.handleResume` → `recoveryClient.continue()`), but it is **latest-only** (`canResume = latestRequest?.status === "interrupted"`) — a run that isn't the most recent on the session has no continue affordance. (The separate `/retry`-mislabelled-as-resume problem lives in React's `resumeLatestRequest`, not the DevTool, and is FIX-637's to fix — see §8.)

This spec makes interruption-recovery legible and per-run: every interrupted run in the session is individually continuable from the tool, and a new `continuation` boundary item makes the prior-log / live-continuation seam visible in the trace so a continue reads as a continue, not a restart. Background work is accounted for: completed background work is restored on continue like the rest of the log (the replay model is phase-agnostic); the crash-timing edge cases (in-flight work at the crash, work still draining after the root completed) are being handled on a separate branch and are out of scope here (§8).

## 3. Background & Research

### 3.1 How the codebase solves this today

The continue path already exists **end-to-end at per-request granularity** — only the DevTool surface is latest-only:

- **Engine route (per-request, any id).** `POST /:flowKind/sessions/:sessionId/requests/:requestId/continue` is registered in `packages/engine/src/routes/router.ts:150-161` (`continue_request`) and handled by `handleContinueRequest()` in `packages/engine/src/routes/recovery-routes.ts:142-224`. It requires `status === "interrupted"` (L177-181), acquires an exclusive-continuation lease (L188-196), and calls `ctx.host.continueRequest({ requestId })` (L201) — same id, no `resumeContext`. Returns 202 JSON or an SSE stream when `Accept: text/event-stream` (L203-216).
- **Three distinct verbs.** `/retry` mints a **new** request id; `/resume` re-enters the same id for a **suspended** HITL gate (body `{ suspensionId, action, data? }`); `/continue` re-enters the same id for an **interrupted** crash record. `continueRequest` is the shared re-entry (`packages/engine/src/execution/request-continuation.ts:57-173`; host type `packages/engine/src/transports/types.ts:243-245`).
- **Discovery is already multi-request.** `detectInterruptedRequests()` (`packages/engine/src/execution/request-recovery.ts:30-76`) sweeps **all** stale `in_progress` records to `interrupted`; `handleCheckInterruptedRequests()` (`recovery-routes.ts:262-302`) exposes `POST /api/flows/users/:userId/check-interrupted` returning the swept list. The DevTool already calls the sweep on mount/refresh (FIX-467).
- **Client already has `continue`.** `createRecoveryClient()` (`packages/client/src/recovery-client/recovery.ts:150`) exposes `continue({ flowKind, sessionId, requestId })` (L202-217) and `checkInterrupted({ userId, staleThresholdMs })` (L154-171). The per-request continue plumbing is present and unused by the UI.
- **Replay log replays main-chain block outputs.** `ReplayLog` (`packages/core/src/blocks/internal/replay-log.ts:48-184`) injects the canonical completed `block_trace.output` (highest-`itemIndex` `status === "completed"` record) for each logical block path and resolves pending suspensions. Completed blocks are not re-executed; the in-flight block re-runs.
- **HITL resume already has a boundary item.** `suspension_resume` (`SuspensionResumeItem`, `packages/contracts/src/items/types.ts:572-584`) is emitted at re-entry (`runAction.ts:1100-1121`) right after the matching `suspension` item. **Crash-recovery `/continue` emits no equivalent marker** — items simply continue; the boundary is only implicit in `itemIndex` ranges.
- **Background phase is already tagged.** Every item carries `provenance.phase: "main" | "work"` (`packages/contracts/src/items/types.ts:25-34`); the DevTool renders a "BG" badge from it (`packages/devtool/src/react/lib/trace-tree.ts:44-51`). Nested blocks under a `.work()` dispatch inherit `phase: "work"`.

### 3.2 The background-work contract on continue

Background work is handled by the **same replay model as the main chain**, with edge cases only at the crash boundary. `buildReplayLog` (`packages/core/src/blocks/internal/replay-log.ts:93-184`) indexes **every** completed `block_trace` by logical path — it does **not** filter `provenance.phase` (L106-108). So a background (`phase: "work"`) block that **completed** before interruption is restored on continue via the same `executeBlock` replay short-circuit as a main-chain block: its output is injected and it is **not** re-executed (its side effect does not double-fire). This is the common case, and it works.

Two edge cases exist at the crash boundary and are **being handled on a separate branch** (out of scope here, §8):

- **In-flight background work at the crash.** A work-phase block that had not committed a completed trace when the process died has no output to inject; on continue the parent re-executes and re-dispatches it fresh into a new pool (`createRequestWorkPool()` in `packages/engine/src/context/createExecutionContext.ts:2017`; pool impl `packages/engine/src/execution/request-work-pool.ts`, drained once before terminal status at `runAction.ts:1356-1368`).
- **Drain-time loss.** If the crash lands after the root/parent completed but while the pool is still draining, the parent's completed trace is replayed (so its `.work()` call is not re-executed) and the still-draining child is not re-dispatched — the work can be silently dropped.

For this spec, that means the DevTool shows background work restored on continue in the common (completed) case, and the boundary marker (§4.2) makes the restored-vs-live seam legible. The two edge cases belong to the separate branch; this spec neither fixes nor pretends to fix them.

### 3.3 Industry framing

Durable-execution systems (Temporal, Inngest, Restate, DBOS) all separate "continue the same run from its journal" from "start a new run," and all provide *replay visibility* — a UI that shows which steps were replayed from history vs newly executed (Temporal's "event history" with replay markers is the canonical example). The `continuation` boundary item is the minimal version of that idea: one audit record at the replay/live seam, mirroring the `suspension_resume` precedent we already ship. No external dependency is warranted; this is small, framework-native instrumentation.

### 3.4 Why a new engine item (not DevTool-only computation)

A boundary that lives only in DevTool-private logic can't be consumed by other clients, the kitchen-sink, or tests, and is fragile against item-log merge ordering. A persisted `continuation` item mirrors the existing `suspension_resume` design exactly (same visibility shape, same renderer pattern), is reusable beyond the DevTool, and makes the boundary part of the durable record — so a `GET` on the request shows the seam, and the goal check can assert on it without scraping the UI.

### 3.5 Key Decisions & Ramifications (top 5)

1. **Emit a new `continuation` item from the engine at the continue boundary** (rejected: compute the boundary in DevTool only; deferred: per-block replayed-vs-fresh tagging). Locks the prior-log / live-continuation seam into the durable log as a first-class, client-visible audit record reusable by any consumer and assertable in tests. The divider marks *where re-entry happened*, not a per-item "replayed" claim — the prior log legitimately holds the interrupted block's partial/in-progress rows (retained for forensics, not injected as completed output), so truly distinguishing injected-completed outputs from retained partials would need per-block tagging, deferred (§8). Ramification: adds one entry to the locked item taxonomy (`items.md`) and a renderer everywhere items render; a permanent, small piece of public item surface.
2. **Treat background work as restored by the existing phase-agnostic replay; add no background-specific machinery here** (rejected: fix the crash-boundary edge cases in this issue). Completed background work already replays via `buildReplayLog` (§3.2), so the DevTool shows it restored on continue; the in-flight and drain-time edge cases are owned by a separate branch. Ramification: the background story is correct for the common (completed) case and defers the two edge cases; the DevTool must not over-claim. If the separate branch changes background semantics, only the divider copy and the §7 background test need revisiting.
3. **Per-run Continue on every interrupted run in the session, wired to the existing `/continue` route** (rejected: batch "continue all"; project-wide multi-app). Smallest surface that satisfies the concurrent-runs ask, and the route + client method already exist. Ramification: multi-app/project-wide continue (FIX-821) and batch continue are deferred; the tool operates within one inspected app/session at a time.
4. **Add a public `useSession.continueRequest(requestId)` and route the DevTool action through the inline-streaming `continueStream()`** (rejected: DevTool-only via JSON `continue()` + GET reconnect). Host apps (kitchen-sink) get per-request continue, and the streaming path works in serverless/embedded DevTool where a separate GET can miss the live continuation (the same reason `resumeSuspension` streams inline). Ramification: expands the public React surface by one method and adds `continueStream()` to the client's public API — both must be documented (§9). `useSession`'s existing latest-only `resumeLatestRequest` (which calls `/retry`) is untouched and left to FIX-637.
5. **`continuation` marks only the crash-recovery `/continue` boundary; `/resume` keeps `suspension_resume`** (rejected: one unified marker on both paths). Avoids double-marking the HITL case and keeps each audit record semantically precise. Ramification: the DevTool divider logic must treat *either* item as a boundary; two item types express "execution re-entered here" for two triggers.

## 4. Technical Design

### 4.1 Architecture / packages touched

- `@flow-state-dev/contracts` — new `ContinuationItem` type + `OutputItem` union membership (item taxonomy is here; re-exported by `core`).
- `@flow-state-dev/engine` — emit the item at the continue point-of-no-return; ensure it merges into the persisted log.
- `@flow-state-dev/client` — `continueStream()` (inline-SSE POST) alongside the existing JSON `continue()`.
- `@flow-state-dev/react` — `continueRequest(requestId)` on `useSession`'s `SessionView`.
- `@flow-state-dev/devtool` — per-run Continue action (via `continueRequest`/`continueStream()`), interrupted-run surfacing + sweep, boundary divider renderer.
- Docs — `docs/architecture/items.md`, `apps/docs/docs/devtool/overview.md`, the streaming item table, client + react READMEs, cross-links.

### 4.2 New item: `ContinuationItem`

In `packages/contracts/src/items/types.ts`, mirroring `SuspensionResumeItem`:

```ts
export type ContinuationItem = OutputItemBase & {
  type: "continuation";
  /** Why re-entry happened. Crash-recovery /continue today; reserved for future triggers. */
  trigger: "recovery";
  /** Count of items already in the durable log at re-entry (the seam position). Named
   *  "prior", not "replayed": the prior log may include retained partial/in-progress rows,
   *  not only injected completed outputs. */
  priorItemCount: number;
  /** Logical block path where live execution resumed (the in-flight block re-run). */
  resumedAtPath?: string;
  continuedAt: number;
};
```

- Add `ContinuationItem` to the `OutputItem` union (`types.ts:586-598`).
- Visibility resolves **automatically** to the structural default `{ client: true, history: false }` (non-transient). `resolveItemVisibility` (`packages/contracts/src/items/resolve-visibility.ts:37-45`) keys off type-set membership — a type in neither `TRACE_TYPES` nor `CONVERSATIONAL_TYPES` falls through to the structural default, exactly as `suspension_resume` does. So the only requirement is to **not** add `continuation` to those sets; there is no explicit visibility-map entry to add.
- Update `docs/architecture/items.md` taxonomy (locked-contract doc) with the new type and its classification.

### 4.3 Engine: emit the boundary

In the crash-recovery re-entry path (`continueRequest` / `runAction`), at the point-of-no-return where status transitions `interrupted → in_progress` after the `ReplayLog` is built but before any block executes (`runAction.ts:1091-1093` is the analogous seam where `suspension_resume` is emitted at L1100-1121):

- Emit one `ContinuationItem` **only** when re-entry is crash-recovery (replay mode, no pending suspension / no `resumeContext`). The `/resume` path keeps emitting `suspension_resume` and must **not** also emit `continuation`.
- `priorItemCount` = number of items already in the durable log at re-entry (the seam index; the prior-log length). `resumedAtPath` (optional) = the logical path of the in-flight block about to re-run. **Note:** `ReplayLog` does not expose this for crash recovery — its `pendingSuspension()` is suspension-keyed and returns `undefined` here — so the implementer derives it (e.g. the highest non-`completed` block path) or leaves it `undefined`. The field is optional precisely so the divider works without it.
- The item is appended at re-entry, so in the merged log (`mergeItemsById`, `runAction.ts:256-271`) it lands after replayed items (lower `itemIndex`) and before freshly executed items. No change to merge semantics needed.

### 4.4 Client + React

**Client.** Add `continueStream(flowKind, sessionId, requestId): Promise<Response>` to `RecoveryClient` (`packages/client/src/recovery-client/recovery.ts`), mirroring `resumeSuspensionStream()` (L239-266) — same `/continue` URL with `Accept: text/event-stream`, returning the raw `Response` so the caller reads the continuation inline from the POST body. The existing JSON `continue()` (202) stays as the non-streaming fallback. Inline streaming is required, not optional: in a serverless/embedded deployment the continuation runs on the POST handler's instance, and a separate GET reconnect can miss the live continuation (this is exactly why `resumeSuspension` streams inline).

**React.** Add `continueRequest(requestId: string): Promise<void>` to the public `SessionView` in `packages/react/src/hooks/useSession.ts`. It looks up the request by id in the session's requests, calls `recoveryClient.continueStream()`, and attaches to the resulting stream inline (mirroring `resumeSuspension`'s inline-stream handling at `useSession.ts:1305-1377`), with a JSON `continue()` + GET-reconnect fallback when SSE is unavailable. Unlike `resumeLatestRequest` (latest-only, `/retry`), this targets any interrupted request by id via the true `/continue` verb, and does not replace it.

### 4.5 DevTool: surface + render

- **Surface all interrupted runs, sweeping first.** `useSessionRequests` fetches all requests in the active session with status. The stale-request sweep currently runs on mount and in the session-list hook (FIX-467), *not* on a request-row refresh — so a run that dies while the panel is already open can keep showing `in_progress` and never expose a Continue action. This spec makes the DevTool call `checkInterrupted` (the sweep) as part of / immediately before the request-row refresh, then filter/annotate `status === "interrupted"`. Each interrupted run has its own separator, so concurrent runs are individually continuable.
- **Per-run Continue action.** In `RequestSeparator` (`packages/devtool/src/react/.../workspace/request-separator.tsx:68-207`), add a `Continue` entry to the overflow menu / a prominent inline button, gated on `status === "interrupted"` **and** a non-webhook `source` (the `/continue` route rejects webhook-sourced requests, so a webhook Continue could only 404 — §4.7). Wire to a new `onContinueInterrupted(requestId)` handler that calls the React `continueRequest(requestId)` path (→ `continueStream()`, inline SSE) so the continuation streams live even in serverless/embedded mode. The existing Replay/Reconnect entries gate on completed/failed (L84); the Continue entry is the interrupted-status sibling.
- **Boundary divider.** Register a renderer for `type: "continuation"` (and treat `suspension_resume` likewise — note it is currently not rendered in the DevTool, so this is intentional new behavior) in the DevTool item renderer, drawing a labeled divider ("Continued here — N prior items") in both stream view (`workspace/stream-view.tsx`) and the trace tree. The divider separates the **prior log** (everything persisted before this continuation) from the **live continuation** (everything produced on re-entry); it does **not** assert every prior item was replayed, because the prior log can include the interrupted block's retained partial/in-progress rows. Restored background work sits in the prior region with its BG badge; freshly-run work (including re-dispatched in-flight background work) sits below with its BG badge. Truly distinguishing injected-completed outputs from retained partials is the deferred per-block tagging (§8).

### 4.6 Data flow (continue)

1. DevTool sweeps stale requests, then lists session requests; one or more show `interrupted`.
2. Developer clicks **Continue** on a specific interrupted run → `useSession.continueRequest(requestId)` → `recoveryClient.continueStream({ flowKind, sessionId, requestId })` (inline SSE; JSON `continue()` + GET fallback).
3. Engine `handleContinueRequest` validates (`interrupted`, session scope, non-webhook), takes the lease, calls `continueRequest({ requestId })`.
4. Re-entry builds `ReplayLog`, transitions `interrupted → in_progress`, emits the `continuation` item, injects completed blocks (main-chain and completed background alike — no re-execution), and re-runs the in-flight block; any `.work()` re-reached whose child had a completed trace is injected, otherwise re-dispatched.
5. Items merge into the same request's log; the inline stream delivers them and the DevTool renders the divider with the prior log above and the live continuation (incl. BG) below.

### 4.7 Error handling

| Case | Behavior |
| --- | --- |
| Continue a non-`interrupted` request | Route already rejects (status guard, `recovery-routes.ts:177-181`); DevTool only shows the action for `interrupted`. |
| Concurrent double-continue of one run | Exclusive-continuation lease (`recovery-routes.ts:188-196`) → second attempt conflicts; DevTool surfaces the error, leaves status unchanged. |
| Webhook-source request | Route rejects (`recovery-routes.ts:160-162`); no Continue action shown. |
| Wrong session/flow scoping | Route validation 404/400; DevTool only issues ids it listed. |
| Continue fails mid-stream | Request stays `interrupted` (or transitions per engine); DevTool shows error, Continue remains available to retry. |

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
| --- | --- |
| No interrupted runs in session | List shows none with Continue; no error. |
| Interruption inside a **generator/router** (not sequencer) | Sequencer-level continue only (FIX-814 not landed): the in-flight generator/router re-runs from its block boundary; completed sibling blocks still replay. Divider still renders. Document this as the current ceiling. |
| **Completed** background block ran before interruption | Injected from the log on continue (phase-agnostic replay) → **not** re-executed, side effect does not double-fire. Renders above the divider with its BG badge. |
| **In-flight** background block at the crash (no completed trace) | Re-dispatched fresh on continue (renders below the divider, BG badge); an external side effect that partially ran may repeat. Edge case owned by the separate branch (§8); this spec surfaces it, does not fix it. |
| Work still **draining** after the root completed | May be silently dropped (parent's completed trace replays, child not re-dispatched). Separate branch (§8). |
| `priorItemCount === 0` (interrupted before anything was persisted) | Divider renders at the top ("0 prior items"); effectively a cold continue — honest. |
| Multiple suspend/continue cycles on one request | Each crash-recovery re-entry appends its own `continuation`; dividers stack in order. (HITL cycles use `suspension_resume`.) |
| Stale list (request completed elsewhere since sweep) | Continue → route rejects non-`interrupted`; DevTool refreshes the list. |

**Error taxonomy.** Lease conflict and status-guard rejections are non-retryable as-is (state changed) — surface and refresh. Network/stream failures are retryable — Continue stays available. No new error codes; reuse the route's existing responses.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (feature). Behaviours below each become a tracer-bullet cycle.

**Goal & goal check (required — applies).** *Goal:* a developer can continue an interrupted run and the run **continues, not restarts** — completed work (main-chain and completed background alike) is restored rather than re-executed, and the boundary is visible. *Goal check (real path, out of CI):* a `goals/continue-interrupted-run/` script (or `fsdev run`) that: starts a flow with a side-effect counter in an early handler **and** a completed `.work()` sidechain, forces the request to `interrupted` after both complete (kill/sweep), calls `/continue`, then asserts on the real durable log: (a) exactly one `continuation` item with `priorItemCount > 0`, (b) the early handler's *and* the completed background block's side-effect counters did **not** increment again (both restored, not re-run), (c) the request reaches a terminal status under the **same** id. Prints PASS/FAIL. A second scenario starts two flows, interrupts both, continues each by id, and asserts both terminate independently. (No real LLM required — handler/sequencer flow suffices to prove continue-not-restart; richer generator validation is bounded by FIX-814. The in-flight/drain-time background edge cases are the separate branch's goal check, not this one's.)

**CI specs (mocked, deterministic):**
- Engine: `continuation` emitted on crash-recovery continue only; correct `priorItemCount`/`resumedAtPath`; not emitted on retry/fresh/resume. Completed blocks (any phase) not re-executed on continue (existing replay test patterns).
- Engine: a **completed** `phase: "work"` block is injected on continue (not re-executed) — pins the phase-agnostic replay so a change to that behavior is caught. (In-flight/drain-time edge cases are the separate branch's tests, referenced not duplicated here.)
- Engine: two interrupted requests in a session are each continuable by id (no latest-only coupling).
- Client: `continueStream()` targets a non-latest request by id with `Accept: text/event-stream`; JSON `continue()` fallback path returns `{ requestId }`.
- React: `useSession.continueRequest(id)` resolves the request, calls `continueStream`, and attaches to the stream; does not touch `resumeLatestRequest`.
- DevTool (component): Continue action renders iff `status === "interrupted"` **and** non-webhook source; handler calls `continueRequest` with the row's id; `continuation` renders as a divider; restored background renders above with BG badge, re-dispatched below.

**Seams / references.** Engine item-log + replay tests under `packages/engine` (continue/replay specs from FIX-811); contracts item tests; React hook tests; DevTool component tests; `packages/integration-tests` for the cross-package continue-not-restart flow. Use `fsd:write-block-tests` mock-context idiom for any block-level specs.

## 8. Non-Goals

- **Tool-driven interrupt button.** The issue marks it optional; killing the server starts the test. Out.
- **Background crash-boundary edge cases.** Completed background work already restores via the phase-agnostic replay (§3.2), which this spec relies on. The two edge cases — in-flight background work lost at the crash, and work still draining after the root completed — are **being handled on a separate branch** and are not owned here. This spec surfaces those cases in the trace (below the divider) but does not fix them, and adds no background-specific durability machinery.
- **resume-vs-retry contract & relabeling.** `resumeLatestRequest()` currently calls `/retry` (a restart mislabeled "resume"). Correcting the contract/affordance is **FIX-637**; this spec deliberately uses the true `/continue` verb for the new action and leaves `resumeLatestRequest` untouched.
- **Generator/router resume mechanism.** **FIX-814** (in spec review) owns mid-generator/mid-router continuation; until it lands, richer flows validate only to the sequencer ceiling (§6).
- **Project-wide / multi-app continue.** Continuing across apps/ports is **FIX-821** (backlog, unspecced). This spec stays within one inspected app/session.
- **Batch "continue all interrupted."** Per-run only; batch is a later convenience if it earns its place.
- **Per-block replayed/fresh shading.** The divider (prior-log-above / live-below) is sufficient for this issue; per-block tagging of every `block_trace` to distinguish injected-completed outputs from retained partials is deferred (would let the trace prove replayed-vs-fresh at block granularity).
- **Deepening opportunity (flag, not in scope):** `resumeLatestRequest()` conflating "resume" with a `/retry` restart is a latent correctness-of-label smell in `packages/react/src/hooks/useSession.ts`; fold into FIX-637 rather than this issue. Follow up via `fsd:improve-codebase-architecture` if it persists after FIX-637.

## 11. Resolved Design Decisions

The four design forks were confirmed by the project owner (and refined by spec-PR review):

1. **Replay boundary → new engine `continuation` item**, with a divider that honestly marks *prior log vs live continuation* (not a per-item "replayed" claim). Per-block replayed/fresh tagging is deferred (§8).
2. **Background work → rely on the existing phase-agnostic replay** (completed background work restores on continue); the in-flight/drain-time edge cases are owned by a separate branch, surfaced-but-not-fixed here (§3.2, §8).
3. **Continue scope → per-run, all interrupted runs in the session** (source-gated to non-webhook); batch and project-wide (FIX-821) deferred.
4. **React API → public `useSession.continueRequest(requestId)`** routed through the inline-streaming `continueStream()` (with JSON+GET fallback), so host apps get it and serverless/embedded continuation streams correctly.

No open questions remain that block implementation.
