# FIX-866: Attached durable background work — verify and harden `.work()` / `.forEachBackground()` recovery — Implementation Spec

## 1. TLDR

**Plain-language summary.** When a long-running flow crashes partway through and the system brings it back to life, it has to know which steps already ran so it doesn't run them twice. We already know this works for the *foreground* steps. This issue is about the *background* steps — fire-and-forget side work like analytics, cache warming, or notifications that a flow kicks off without waiting for. We proved the easy case (background work that finished before the crash comes back correctly). This work nails down and tests the hard edges: background work that was still running when the crash hit, background work that failed and left nobody to catch it, and whether any of this holds up on a real database (not just the in-memory test store). Most of this is writing tests and writing down the rules; we only change runtime code if a test catches a real drop or double-run.

**Technical statement.** Verify and harden crash-recovery (`continueRequest`) of in-process background work (`.work()`, `.workIf()`, `.forEachBackground()`) under a `durable: true` parent: pin the contract for in-flight tasks (retry-from-scratch), for a failed task under a completed parent (drop-and-log, terminal), and confirm completed-background-trace replay survives across persistent stores — adding regression coverage for each and fixing only what the coverage surfaces.

**Deliverables.**

- *Tests (engine):* Add a partial `.forEachBackground` fan-out interrupted genuinely mid-drain (no `.waitForWork()` barrier) to `packages/engine/test/background-work-recovery.test.ts` — completed iterations injected, in-flight iterations re-run from scratch.
- *Tests (engine):* Add a `.work()` failure-under-completed-parent case asserting drop-and-log (no recovery path) and the `.waitForWork({ failOnError: true })` escalation that folds the failure into the parent.
- *Tests (cross-store):* Add background-work replay recovery tests to `packages/store-sqlite/test/` and `packages/store-postgres/test/`, mirroring `completed-trace-persistence.test.ts` + `multigate-cold-restart.test.ts`.
- *Runtime (conditional):* Fix at the owning layer only if a test surfaces a dropped completed-trace or a double-run (expected layer: the store item-persistence diff — FIX-839 family — not the sequencer).
- *Docs:* Add a "Durability of background work" section to `apps/docs/docs/advanced/sequencer-side-chains.md`; one cross-link note in `block-memoization-and-replay.md`.

**Size estimate.** **Medium** — multi-file, 1 PR, ~100–400 LOC (mostly tests + docs). Escalates toward the top of that range only if the cross-store tests surface a real persistence drop requiring a runtime fix.

## 2. Overview

Linear issue: [FIX-866](https://linear.app/fixpoint-labs/issue/FIX-866). This spec covers the **verify-and-harden** work that the FIX-866 investigation (merged PR [#674](https://github.com/fixpoint-labs/flow-state-dev/pull/674), test-only) deliberately deferred. That PR proved the happy path — background work that *completed before* a crash is replayed, not re-run, in-memory — and explicitly left four edges open. This spec pins those edges down with a defined contract and regression coverage, and fixes only what the coverage surfaces. It unblocks [FIX-865](https://linear.app/fixpoint-labs/issue/FIX-865) (DevTool can't honestly display background resume until the framework contract is settled).

## 3. Background & Research

### 3.1 How the machinery works today (verified against source)

**Dispatch.** `.work()` / `.workIf()` route through the `runBackground` kernel (`packages/core/src/blocks/internal/sequencer-kernel.ts:87`); `.forEachBackground()` fans out inline (`packages/core/src/blocks/sequencer.ts:1357`). Each child runs through the same `executeBlock` (`packages/core/src/blocks/sequencer.ts:411`) as a foreground step, but with `{ phase: "work", signalOverride }` and at a deterministic logical path: `childBlockPath(ctx, runtime, "work" | "forEachBackground", stepIndex[, index])` → e.g. `…:seq:work:3` or `…:seq:forEachBackground:2:[1]`. The in-flight promise is registered with the per-request work pool via `dispatchWorkTask` (`packages/engine/src/execution/request-work-pool.ts`).

**Journaling.** Background blocks emit non-transient `block_trace` items stamped `provenance.phase = "work"` (`packages/contracts/src/items/types.ts`). These land in the **request record's `items`** (the `RequestStore`), which is the replay source — distinct from the devtool `TraceStore` channel.

**Replay (FIX-811).** On continuation, the server builds a `ReplayLog` from the request's item log (`packages/core/src/blocks/internal/replay-log.ts:93`) and assigns it to `ctx._replayLog`. `executeBlock` consults it *uniformly* for every block, foreground or background (`packages/core/src/blocks/sequencer.ts:443–471`): if a `completed` `block_trace` exists at the block's logical path, its recorded output is injected and the body is skipped; otherwise the block runs. `ReplayLog.getCompletedOutput` keys on `status === "completed"` only (`replay-log.ts:108`).

**The drain asymmetry (the crux).** The request executor drains the work pool **only on the terminal/success path** (`packages/engine/src/execution/runAction.ts:1356`, `drainRequestWorkPool` at `:99`). The **suspension path does not drain** — it persists the `SuspensionRecord`, flushes items/traces, transitions the record to `suspended`, and returns (`runAction.ts:1166–1296`), leaving any in-flight background promises un-awaited. Therefore in-flight background work at suspension time is a *reachable, supported state* whenever a `.work()` / `.forEachBackground()` dispatch is not covered by a preceding `.waitForWork()` barrier in the same scope. (The existing tests use `.waitForWork()` precisely to drain before the gate, which is why every iteration is complete at crash time — masking the mid-drain case.)

**Failure isolation.** Per-task failures are caught and isolated (`request-work-pool.ts:119–178`; `forEachBackground` catches per-iteration at `sequencer.ts:1401`). Failures are logged (`runAction.ts` drain, `waitForWork` at `sequencer.ts:1658`) but do **not** drive request terminal status — the foreground `result.error` does. A failed background task emits an `errored` `block_trace`, never `completed`, so the ReplayLog never injects it.

### 3.2 Industry precedent

This is the classic durable-workflow distinction between *workflow* state (deterministic, replayed from an event log) and *activity* execution (side-effecting, at-least-once). Temporal and comparable engines replay completed activity results from history and **re-run** any activity with no recorded completion — non-idempotent activities must guard their own side effects (idempotency keys), exactly mirroring FSD's "inject-if-completed, re-run-if-not" gate. The framework already encodes this for foreground blocks via `ctx.runOnce` + provider idempotency keys (`apps/docs/docs/advanced/block-memoization-and-replay.md`, `idempotency.md`). The defensible move is to extend the *same* contract to background work, not to invent intra-task checkpointing (which has no analog: a handler is an opaque unit of work with no sub-block boundaries to checkpoint).

### 3.3 Necessity verdict

**Build as scoped.** This is a correctness/reliability change plus contract definition for crash recovery — not a wrapper over an existing primitive and not single-vendor leakage, so it doesn't trip the push-back gate. The one place "build smaller" applies is the *failed-task-under-completed-parent* contract: this spec resolves it in the **minimal** direction (document the existing drop-and-log behavior; lean on the existing `.waitForWork({ failOnError: true })` for correctness-critical work) rather than building a new recoverable-record / dead-letter subsystem, which would be speculative surface nothing consumes (BP-038, YAGNI). The substrate already works for the common case, so the deliverable is *coverage + documented contract*, with runtime fixes gated on what the tests surface.

### 3.4 Key Decisions & Ramifications (top 5)

1. **In-flight background task = retry-from-scratch.** A background block with no `completed` trace re-runs from the top on continuation; only completed ones inject. *Rejected:* intra-task continue-from-log (checkpoint inside a single handler). *Ramification:* locks in at-least-once execution for background side effects; non-idempotent partial side effects can re-fire; the guard is the existing `ctx.runOnce` (keyed on the stable `requestId`, available in the background task ctx) + provider idempotency key. Matches the foreground memoization contract — one rule, not two.

2. **Suspension does not drain the pool (no drain-on-suspend added).** *Rejected:* draining the pool before persisting the suspension, for symmetry with the terminal path. *Ramification:* "in-flight at crash" stays a supported state handled by recovery's re-run; suspension latency is unchanged (a human-approval gate doesn't block on fire-and-forget work); the kill-9-during-drain window can't be closed anyway, so the recovery contract must exist regardless. Authors who need background work finished before a gate use `.waitForWork()` (BP-038).

3. **Failed background task under a completed parent = drop-and-log, terminal, no recovery path.** *Rejected:* a durable failed-task record with its own retry path. *Ramification:* best-effort work stays best-effort; correctness-critical background work opts into `.waitForWork({ failOnError: true })`, which folds the failure into the parent (making it fail and thus recoverable). This is a document+test deliverable, not new machinery; a future dead-letter need is a separate, larger design (flagged in Non-Goals).

4. **Cross-store conformance lives in the persistent-store packages, against the real `continueRequest` path.** *Rejected:* a new abstract recovery-conformance suite in `engine/testing`. *Ramification:* mirrors the established per-store integration pattern (`completed-trace-persistence.test.ts`, `multigate-cold-restart.test.ts`); confirms FIX-839's content-diff fix covers `phase:"work"` traces; the seam is the request record's items (durable on SQLite + Postgres), not the Postgres-in-memory `TraceStore`.

5. **Discipline = `fsd:diagnose`, test-first; fixes gated on findings.** *Rejected:* a speculative refactor of the background dispatch path. *Ramification:* scope stays narrow and proportionate to a verify-and-harden issue; if the partial-fan-out or cross-store test surfaces a dropped completed-trace or a double-run, the fix lands at the owning layer (the store item-persistence diff, FIX-839 family) — not the sequencer.

### 4.2 The three contracts being pinned

**Contract A — in-flight background task (retry-from-scratch).** On `continueRequest`, the `.work` / `.forEachBackground` step re-executes its `run` callback. Each child `executeBlock` consults `ctx._replayLog`: an iteration with a `completed` trace at its logical path is injected; an iteration that was in-flight (or never started) at crash time has no `completed` trace and **re-runs from the top**. There is no intra-handler continuation. *Observable contract:* completed iterations leave their handler at exactly one execution; in-flight iterations may execute their handler more than once across the crash, so non-idempotent side effects must be guarded with `ctx.runOnce` + provider idempotency key. No runtime change expected — this is the existing uniform replay gate; the deliverable is the test + the documented rule.

**Contract B — failed background task under a completed parent (drop-and-log).** A `.work()` / iteration that throws is isolated, logged, and emits an `errored` `block_trace`. If the parent reaches `completed` (foreground finished), the request is terminal — there is no `interrupted` record to continue, so the failed task is never retried. *Observable contract:* the request completes; the failed task is visible only as an `errored` trace in the log + a `console.error`; nothing retries it. Correctness-critical background work must use `.waitForWork({ failOnError: true })` so the failure throws into the parent (parent fails → becomes recoverable / surfaces to the caller). No runtime change expected.

**Contract C — completed-background-trace replay across stores.** The ReplayLog reads `block_trace` items from the persisted request record. FIX-839 showed a persistent store could leave a `completed` trace persisted as `in_progress` (reference-equality persistence diff), which `getCompletedOutput` then skips → re-execution. Background traces ride the same request-store persistence path, so the FIX-839 content-diff fix (`packages/store-sqlite/src/request-store.ts`, `packages/store-postgres/src/request-store.ts`) must also cover `phase:"work"` traces. *Observable contract:* a `.work()` block completed before a crash, on `continueRequest` against SQLite and Postgres, is injected (handler runs once total). Runtime change only if a store drops the background completed-trace.

### 4.3 Data flow (mid-drain interruption)

1. Durable sequencer dispatches `.forEachBackground(items, elem)` (N iterations), **no** `.waitForWork()`, then `.step(gate)`.
2. Some iterations complete (write `completed` traces to the request items); the gate calls `ctx.suspend()` while others are still in-flight.
3. Suspend path persists the suspension and `suspended` status **without draining** the pool; in-flight iterations are abandoned (their late writes may or may not land — pinned by the test).
4. Crash is simulated by flipping the record to `interrupted` (as the existing tests + the stale-request sweeper do).
5. `continueRequest` (no `resumeContext`) re-enters in replay mode, rebuilds the `ReplayLog`, restores root sequencer state from the checkpoint, and re-runs the `forEachBackground` step: completed iterations inject; the rest re-run from scratch.

### 4.4 Error handling

No new error taxonomy. The relevant behaviors are existing: `errored` `block_trace` for failed background tasks; `waitForWork({ failOnError: true })` re-throws the first failure into the parent; foreground `SuspensionError` drives the suspend path. The spec asserts these, it does not add codes.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| Iteration completed before crash | Injected from log; handler runs once total. |
| Iteration in-flight at crash | Re-runs from scratch on continuation (Contract A). Counter > 1 is correct, not a bug. |
| Iteration never started (past concurrency window) at crash | Re-runs from scratch (same as in-flight — no completed trace). |
| `.work()` task fails, parent completes | Drop-and-log; `errored` trace; no retry (Contract B). |
| `.work()` task fails, `.waitForWork({ failOnError: true })` present | First failure re-thrown into parent; parent fails (recoverable). |
| `.work()` task fails, parent *suspends* (gate after, no waitForWork) | On continuation the step re-dispatches; the failed iteration re-runs from scratch (it has no completed trace). This is the recoverable variant of B. |
| Completed background trace persisted as `in_progress` (FIX-839 class) on SQLite/Postgres | Must NOT happen — content-diff persistence covers it; the cross-store test is the regression lock. If it does, step 4 fix. |
| Late trace write after suspension flush | Pinned by step 1: if dropped, the iteration re-runs on continuation (consistent with Contract A); only a *pre-flush completed* trace being dropped is a bug. |
| Postgres `TraceStore` is in-memory | Irrelevant to replay — replay reads the request record's items (durable), not the trace channel. Documented so the test doesn't assert against the wrong store. |

**Error taxonomy:** background failures are non-fatal to the request (logged); `failOnError` promotes them to fatal-for-the-parent. No retryable/fatal classification is added.

## 7. Testing Strategy

**Goal & goal check.** The goal is the real-world outcome: *a durable flow whose background work is interrupted by a crash comes back without silently dropping completed work or double-charging for in-flight work, on a real database.* **No real-LLM goal check applies** — this is deterministic crash-recovery and persistence semantics with no model-exercised behavior. Per `fsd:diagnose`, the real-path confirmation is the **cross-store recovery tests** in step 3, which exercise the real `continueRequest` path against real SQLite and Postgres (PGlite) stores — that is the "did the goal actually hold" signal, run by the suite, not a separate `goals/` script.

**Discipline:** `fsd:diagnose` (verify-and-harden / regression), with the three contracts above as the decided behaviors each regression test encodes.

**Feedback-loop seams:**
- Engine-level (Contracts A & B): vitest in `packages/engine/test/background-work-recovery.test.ts`, driving `runAction` → `continueRequest` against in-memory durable stores. This is the fast loop for shaping the mid-drain harness (the controllable deferred-promise gate).
- Cross-store (Contract C): vitest in `packages/store-sqlite/test/` and `packages/store-postgres/test/`, driving the real `continueRequest` against persistent stores. This is the regression seam for the FIX-839-family persistence drop.

**Behaviors to assert (observable terms):**
- Completed `.forEachBackground` iteration → handler invocation count stays 1 across the crash; output observable via `ctx.getBlockOutput` after continuation.
- In-flight iteration → handler invocation count increments after continuation (re-run).
- Failed `.work()` under completed parent → request status `completed`; one `errored` `block_trace`; no retry.
- Failed `.work()` with `failOnError` → request status `failed`/`errored`; parent throws.
- Completed `.work()` before crash on SQLite **and** Postgres → persisted trace `status: "completed"`; injected on continuation (handler count 1).

**Patterns to reference:** `packages/engine/test/background-work-recovery.test.ts` (existing harness — durable stores, simulated crash via `interrupted`, dual-assert run-count + observed-output); `packages/store-sqlite/test/completed-trace-persistence.test.ts` (FIX-839 persisted-trace assertion); `packages/store-sqlite/test/multigate-cold-restart.test.ts` (cross-store `continueRequest` cycle). The `fsd:write-block-tests` mock-context idiom applies for any block-level isolation.

## 8. Non-Goals

- **Detached / spawned background as its own request** — was FIX-815 (cancelled); the reactive variant is FIX-825 / FIX-441. Out of scope.
- **The `.work` / `.forEachBackground` API surface** — unchanged. No new options, no `durable:` flag on side chains.
- **Generator / router continuation** — FIX-814.
- **A durable dead-letter / recoverable-record subsystem for failed background tasks.** Contract B resolves the failed-task case as drop-and-log + `failOnError` escalation. A first-class "retry this failed background task later" mechanism is a separate, larger design; flag it for follow-up only if a concrete consumer appears. (Before adding it later, check `docs/internal/out-of-scope/` for a prior rejection.)
- **Drain-on-suspend symmetry** — deliberately not added (Decision 2).
- **Deepening opportunity (flag, not in scope):** the drain asymmetry between the suspend path and the terminal path in `runAction.ts` is implicit and only discoverable by reading both paths. If it proves a recurring source of confusion, consider extracting a single named "settle background work for this lifecycle transition" seam — follow up via `fsd:improve-codebase-architecture`, not here.

## 11. Open Questions

1. **Late trace-write durability after suspension.** Step 1 will reveal whether a background task that completes *after* the suspend-path flush still persists its `completed` trace, or whether the write is dropped (record already flushed to `suspended`). Both outcomes are contract-consistent (a dropped late write just means the iteration re-runs, which is Contract A), but if a task that completed *before* the flush has its trace dropped, that is a real bug to fix in step 4. The test pins which it is; no decision needed up front.
2. **Postgres test runner availability.** Confirm the store-postgres suite's PGlite harness is exercised in the same CI lane as store-sqlite (the existing `pglite-*.test.ts` files suggest yes). If Postgres tests are gated behind an env flag, the cross-store assertion for Postgres runs behind that same gate — note it in the PR rather than weakening the SQLite assertion.
