# FIX-866: Attached durable background work — verify and harden `.work()` / `.forEachBackground()` recovery — Implementation Spec

## 1. TLDR

**Plain-language summary.** When a long-running task crashes partway through and gets restarted, it must not redo work it already finished or skip work it didn't. That recovery is already proven for a task's main steps; this issue is about the side jobs a task fires off without waiting for them (analytics, notifications, cache warming). We've confirmed the easy case and now need to settle the harder ones: a side job still running when the crash hit, one that failed with nobody watching, and whether all of it holds up on a real database. The work is mostly tests and writing down the rules, with code changes only where a test catches a real problem.

**Technical statement.** Verify and harden crash-recovery (`continueRequest`) of in-process background work (`.work()`, `.workIf()`, `.forEachBackground()`) under a `durable: true` parent: pin the contract for in-flight tasks (at-least-once / retry-from-scratch), for a failed task under a completed parent (drop-and-log, terminal), and confirm completed-background-trace replay survives across persistent stores — adding regression coverage for each, naming the trace-retention precondition the contract depends on, and fixing only what the coverage surfaces.

**Deliverables.**

- *Tests (engine):* Add a partial `.forEachBackground` fan-out interrupted genuinely mid-drain (no `.waitForWork()` barrier) to `packages/engine/test/background-work-recovery.test.ts` — completed iterations injected, in-flight iterations re-run from scratch. The crash must be simulated so first-run background promises cannot advance after the cutover (cold restart or cancel/settle the first-run deferreds).
- *Tests (engine):* Add a `.work()` failure-under-completed-parent case asserting drop-and-log (no recovery path) and the `.waitForWork({ failOnError: true })` fail-fast escalation that surfaces the failure into the parent (parent → `failed`; not continuable, only `/retry`).
- *Tests (cross-store):* Add background-work replay recovery tests to `packages/store-sqlite/test/` and `packages/store-postgres/test/`, mirroring `completed-trace-persistence.test.ts` + `multigate-cold-restart.test.ts` — including the intervening in-progress-trace flush that actually exercises the FIX-839 content-diff path, and forcing `FSDEV_TRACE_OBSERVABILITY=true`.
- *Runtime (conditional):* Fix at the owning layer only if a test surfaces a dropped completed-trace or a double-run (expected layer: the store item-persistence diff — FIX-839 family — not the sequencer).
- *Docs:* Add a "Durability of background work" section to `apps/docs/docs/advanced/sequencer-side-chains.md` (incl. per-item `runOnce` keys for fan-out + the trace-retention precondition); a cross-link note in `block-memoization-and-replay.md`; and update the relevant `docs/architecture/*` reference(s) so the execution contract stays authoritative.

**Size estimate.** **Medium** — multi-file, 1 PR, ~100–400 LOC (mostly tests + docs). Escalates toward the top of that range only if the cross-store tests surface a real persistence drop requiring a runtime fix.

## 2. Overview

Linear issue: [FIX-866](https://linear.app/fixpoint-labs/issue/FIX-866). This spec covers the **verify-and-harden** work that the FIX-866 investigation (merged PR [#674](https://github.com/fixpoint-labs/flow-state-dev/pull/674), test-only) deliberately deferred. That PR proved the happy path — background work that *completed before* a crash is replayed, not re-run, in-memory — and left four edges open. This spec pins those edges down with a defined contract and regression coverage, and fixes only what the coverage surfaces. It unblocks [FIX-865](https://linear.app/fixpoint-labs/issue/FIX-865) (the DevTool can't honestly display background resume until the contract is settled).

## 3. Background & Research

### 3.1 How the machinery works today (verified against source)

**Dispatch.** `.work()` / `.workIf()` route through the `runBackground` kernel (`packages/core/src/blocks/internal/sequencer-kernel.ts:87`); `.forEachBackground()` fans out inline (`packages/core/src/blocks/sequencer.ts:1357`). Each child runs through the same `executeBlock` (`packages/core/src/blocks/sequencer.ts:411`) as a foreground step, but with `{ phase: "work", signalOverride }` and at a deterministic logical path: `childBlockPath(ctx, runtime, "work" | "forEachBackground", stepIndex[, index])` → e.g. `…:seq:work:3` or `…:seq:forEachBackground:2:[1]`. The in-flight promise is registered with the per-request work pool via `dispatchWorkTask` (`packages/engine/src/execution/request-work-pool.ts`).

**Journaling — and its precondition.** Background blocks emit non-transient `block_trace` items stamped `provenance.phase = "work"` (`packages/contracts/src/items/types.ts`), which land in the **request record's `items`** (the `RequestStore`) — the replay source, distinct from the devtool `TraceStore` channel. **Crucially, `block_trace` capture is gated.** `onBlockTraceCapture` is wired only when `isTraceObservabilityEnabled()` is true (`packages/engine/src/context/createExecutionContext.ts:2189`), which **defaults off when `NODE_ENV === "production"`** (`packages/core/src/helpers/trace-observability.ts:38`), and a block marked `transient: true` records no trace. When no `block_trace` is retained for a logical path, `ReplayLog.getCompletedOutput` returns `undefined` and the block **re-executes** on continuation — foreground *and* background alike. So the entire FIX-811 replay/memoization contract (not just background) presupposes retained traces. This spec inherits that precondition; it does not change it (see Open Question 1).

**Replay (FIX-811).** On continuation the server builds a `ReplayLog` from the request's item log (`packages/core/src/blocks/internal/replay-log.ts:93`) and assigns it to `ctx._replayLog`. `executeBlock` consults it *uniformly* for every block, foreground or background (`packages/core/src/blocks/sequencer.ts:443–471`): if a `completed` `block_trace` exists at the block's logical path, its recorded output is injected and the body is skipped; otherwise the block runs. `ReplayLog.getCompletedOutput` keys on `status === "completed"` only (`replay-log.ts:108`).

**The drain asymmetry (the crux).** The request executor drains the work pool **only on the terminal/success path** (`packages/engine/src/execution/runAction.ts:1356`, `drainRequestWorkPool` at `:99`). The **suspension path does not drain** — it persists the `SuspensionRecord`, flushes items/traces, transitions the record to `suspended`, and returns (`runAction.ts:1166–1296`), leaving any in-flight background promises un-awaited and un-aborted. Therefore in-flight background work at suspension time is a *reachable, supported state* whenever a `.work()` / `.forEachBackground()` dispatch is not covered by a preceding `.waitForWork()` barrier in the same scope. (The existing tests use `.waitForWork()`, which drains before the gate, so every iteration is complete at crash time — masking the mid-drain case.)

**Failure isolation.** Per-task failures are caught and isolated (`request-work-pool.ts:119–178`; `forEachBackground` catches per-iteration at `sequencer.ts:1401`). Failures are logged (`runAction.ts` drain, `waitForWork` at `sequencer.ts:1658`) but do **not** drive request terminal status — the foreground `result.error` does. A failed background task emits an `errored` `block_trace`, never `completed`, so the ReplayLog never injects it.

### 3.2 Industry precedent

This is the classic durable-workflow distinction between *workflow* state (deterministic, replayed from an event log) and *activity* execution (side-effecting, at-least-once). Temporal and comparable engines replay completed activity results from history and **re-run** any activity with no recorded completion; non-idempotent activities must guard their own side effects (idempotency keys), exactly mirroring FSD's "inject-if-completed, re-run-if-not" gate. The framework already encodes this for foreground blocks via `ctx.runOnce` + provider idempotency keys (`apps/docs/docs/advanced/block-memoization-and-replay.md`, `idempotency.md`). The defensible move is to extend the *same* contract to background work, not to invent intra-task checkpointing (which has no analog: a handler is an opaque unit of work with no sub-block boundaries to checkpoint).

### 3.3 Necessity verdict

**Build as scoped.** This is a correctness/reliability change plus contract definition for crash recovery — not a wrapper over an existing primitive and not single-vendor leakage, so it doesn't trip the push-back gate. The one place "build smaller" applies is the *failed-task-under-completed-parent* contract: this spec resolves it in the **minimal** direction (document the existing drop-and-log behavior; lean on the existing `.waitForWork({ failOnError: true })` for correctness-critical work) rather than building a new recoverable-record / dead-letter subsystem, which would be speculative surface nothing consumes (BP-038, YAGNI). The substrate already works for the common case, so the deliverable is *coverage + documented contract*, with runtime fixes gated on what the tests surface.

### 3.4 Key Decisions & Ramifications (top 5)

1. **In-flight background task = at-least-once / retry-from-scratch.** A background block with no `completed` trace re-runs from the top on continuation; only completed ones inject. *Rejected:* intra-task continue-from-log (checkpoint inside a single handler). *Ramification:* the framework guarantees *replay of completed work*, not exactly-once for in-flight work — in-flight side effects are at-least-once; the guard is the existing `ctx.runOnce` + provider idempotency key. For `.forEachBackground()` the `runOnce` key must be per-item/per-index (it dedupes by `(requestId, key)`, so a literal key in a reused handler would collapse the whole fan-out to one effect). Matches the foreground memoization contract — one rule, not two.

2. **Suspension does not drain the pool (no drain-on-suspend added).** *Rejected:* draining the pool before persisting the suspension, for symmetry with the terminal path. *Ramification:* "in-flight at crash" stays a supported state handled by recovery's re-run; suspension latency is unchanged (a human-approval gate doesn't block on fire-and-forget work); the kill-9-during-drain window can't be closed anyway, so the recovery contract must exist regardless. Authors who need background work finished before a gate use `.waitForWork()` (BP-038).

3. **Failed background task under a completed parent = drop-and-log, terminal, no recovery path.** *Rejected:* a durable failed-task record with its own retry path. *Ramification:* best-effort work stays best-effort; correctness-critical background work opts into `.waitForWork({ failOnError: true })`, which is **fail-fast surfacing** — it promotes the failure into the parent, which becomes `failed`. A `failed` request is **not** continuable on the same id (the `continue` path accepts only `interrupted`); the only follow-up is `/retry` as a fresh request. This is a document+test deliverable, not new machinery; a future dead-letter need is a separate, larger design (flagged in Non-Goals).

4. **Cross-store conformance lives in the persistent-store packages, against the real `continueRequest` path, and actually exercises the FIX-839 bug shape.** *Rejected:* a new abstract recovery-conformance suite in `engine/testing`. *Ramification:* mirrors the established per-store integration pattern (`completed-trace-persistence.test.ts`, `multigate-cold-restart.test.ts`); confirms FIX-839's content-diff fix covers `phase:"work"` traces. The work block must emit an intervening non-transient `item.done` while its own trace is still `in_progress` (as the FIX-839 regression does) or the test can pass without ever hitting the content-diff path. The seam is the request record's items (durable on SQLite + Postgres), not the Postgres-in-memory `TraceStore`.

5. **Discipline = `fsd:diagnose` (verify-and-harden), test-first; fixes gated on findings.** *Rejected:* a speculative refactor of the background dispatch path. *Ramification:* scope stays narrow and proportionate to a verify-and-harden issue; if the partial-fan-out or cross-store test surfaces a dropped completed-trace or a double-run, the fix lands at the owning layer (the store item-persistence diff, FIX-839 family) — not the sequencer.

### 4.2 The three contracts being pinned

**Contract A — in-flight background task (at-least-once / retry-from-scratch).** On `continueRequest`, the `.work` / `.forEachBackground` step re-executes its `run` callback. Each child `executeBlock` consults `ctx._replayLog`: an iteration with a retained `completed` trace at its logical path is injected; an iteration that was in-flight (or never started) at crash time has no `completed` trace and **re-runs from the top**. There is no intra-handler continuation. *Observable contract:* completed-and-retained iterations leave their handler at exactly one execution; in-flight iterations execute their handler at least once *more* across the crash, so non-idempotent side effects must be guarded with `ctx.runOnce` (per-item key for fan-out) + provider idempotency key. No runtime change expected — this is the existing uniform replay gate; the deliverable is the test + the documented rule (including the trace-retention precondition).

**Contract B — failed background task under a completed parent (drop-and-log).** A `.work()` / iteration that throws is isolated, logged, and emits an `errored` `block_trace`. If the parent reaches `completed` (foreground finished), the request is terminal — there is no `interrupted` record to continue, so the failed task is never retried. *Observable contract:* the request completes; the failed task is visible only as an `errored` trace in the log + a `console.error`; nothing retries it. Correctness-critical background work uses `.waitForWork({ failOnError: true })`, which **surfaces the failure fail-fast** into the parent (parent → `failed`). A `failed` request is not continuable on the same id; only `/retry` (a fresh request) re-runs it. No runtime change expected.

**Contract C — completed-background-trace replay across stores.** The ReplayLog reads `block_trace` items from the persisted request record. FIX-839 showed a persistent store could leave a `completed` trace persisted as `in_progress` (reference-equality persistence diff), which `getCompletedOutput` then skips → re-execution. Background traces ride the same request-store persistence path, so the FIX-839 content-diff fix (`packages/store-sqlite/src/request-store.ts`, `packages/store-postgres/src/request-store.ts`) must also cover `phase:"work"` traces. *Observable contract:* a `.work()` block that completed before a crash, with trace observability on, on `continueRequest` against SQLite and Postgres, is injected (handler runs once total). The test must force an in-progress flush inside the work block (intervening non-transient `item.done`) so it exercises the content-diff path. Runtime change only if a store drops the background completed-trace.

### 4.3 Data flow (mid-drain interruption)

1. Durable sequencer dispatches `.forEachBackground(items, elem)` (N iterations), **no** `.waitForWork()`, then `.step(gate)`. Trace observability is on (test forces it).
2. Some iterations complete (write `completed` traces to the request items); the gate calls `ctx.suspend()` while others are still in flight.
3. Suspend path persists the suspension and `suspended` status **without draining** the pool; in-flight iterations are abandoned (their late writes may or may not land — pinned by the test).
4. Crash is simulated **so the first-run in-flight tasks cannot advance after the cutover** — a cold restart (fresh store registry + no live promises, as `multigate-cold-restart.test.ts` does) or by cancelling/settling the first-run deferreds before flipping to `interrupted`. (A naive same-process flip leaves first-run promises alive; since the suspend path neither drains nor aborts the pool, they could still bump counters or emit traces after the simulated crash and contaminate the assertions.)
5. `continueRequest` (no `resumeContext`) re-enters in replay mode, rebuilds the `ReplayLog`, restores root sequencer state from the checkpoint, and re-runs the `forEachBackground` step: completed iterations inject; the rest re-run from scratch.

### 4.4 Error handling

No new error taxonomy. The relevant behaviors are existing: `errored` `block_trace` for failed background tasks; `waitForWork({ failOnError: true })` re-throws the first failure into the parent (→ `failed` request, fail-fast, not continuable); foreground `SuspensionError` drives the suspend path. The spec asserts these, it does not add codes.

## 5. Implementation Sequence

Test-first (`fsd:diagnose`): each step adds a failing-or-uncovered scenario, then fixes only if it reveals a real drop/double-run. All tests force `FSDEV_TRACE_OBSERVABILITY=true` so the replay-source traces exist deterministically (as the FIX-839 regression does).

1. **Mid-drain partial fan-out (engine).** Extend `packages/engine/test/background-work-recovery.test.ts`: a durable sequencer with `.forEachBackground` over several items where some iterations block on a controllable deferred, **no** `.waitForWork()` before the suspending `gate`. Drive: let K of N complete, suspend, then simulate the crash so first-run tasks cannot advance (cold restart, or cancel/settle the first-run deferreds), then `continueRequest`. Assert completed iterations' handlers stay at 1 execution (injected) and in-flight ones re-run (counter increments on the continued run only). *Depends on:* nothing. *Verify:* `pnpm --filter @flow-state-dev/engine test`. If completed iterations re-run → bug in trace persistence/replay → go to step 4.

2. **Failure-under-completed-parent (engine).** Add a case: durable sequencer with `.work(failing)` where the parent reaches `completed`; assert the request completes, an `errored` trace exists, and the handler is not retried. Add a sibling case with `.waitForWork({ failOnError: true })` asserting the parent reaches `failed` (fail-fast) and is not continuable on the same id. *Depends on:* nothing. *Verify:* same engine suite.

3. **Cross-store background replay (store-sqlite, store-postgres).** Add `background-work-recovery.test.ts` (or extend `completed-trace-persistence.test.ts`) in `packages/store-sqlite/test/` and `packages/store-postgres/test/`: the completed-`.work()`-before-crash scenario, run against `createSQLiteStores` and the PGlite-backed Postgres stores, with the work block emitting an **intervening non-transient `item.done` while its trace is still `in_progress`** (so the FIX-839 content-diff path is actually exercised), asserting the persisted background trace is `completed` and `continueRequest` injects it. *Depends on:* step 1's shape. *Verify:* `pnpm --filter @flow-state-dev/store-sqlite test`, `pnpm --filter @flow-state-dev/store-postgres test`.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| Iteration completed before crash (trace retained) | Injected from log; handler runs once total. |
| Iteration in-flight at crash | Re-runs from scratch on continuation (Contract A). Counter > 1 is correct, not a bug. At-least-once, not exactly-once. |
| Iteration never started (past concurrency window) at crash | Re-runs from scratch (same as in-flight — no completed trace). |
| Trace observability off / `transient: true` work block | No `block_trace` retained ⇒ ReplayLog has nothing to inject ⇒ the block re-runs on continuation, even if it completed. Same as foreground; this is the precondition, not a background-specific bug (Open Question 1). |
| `.forEachBackground` + `runOnce` with a literal key | All iterations share one `(requestId, key)` memo ⇒ only the first side effect runs. Docs must require a per-item/per-index key (or provider idempotency key). |
| `.work()` task fails, parent completes | Drop-and-log; `errored` trace; no retry (Contract B). |
| `.work()` task fails, `.waitForWork({ failOnError: true })` present | First failure re-thrown into parent; parent → `failed` (fail-fast). Not continuable on the same id; only `/retry`. |
| `.work()` task fails, parent *suspends* (gate after, no waitForWork) | On continuation the step re-dispatches; the failed iteration re-runs from scratch (it has no completed trace). This is the recoverable variant of B. |
| Completed background trace persisted as `in_progress` (FIX-839 class) on SQLite/Postgres | Must NOT happen — content-diff persistence covers it; the cross-store test (with an in-progress flush) is the regression lock. If it does, step 4 fix. |
| Late trace write after suspension flush | Pinned by step 1: if dropped, the iteration re-runs on continuation (consistent with Contract A); only a *pre-flush completed* trace being dropped is a bug. |
| Postgres `TraceStore` is in-memory | Irrelevant to replay — replay reads the request record's items (durable), not the trace channel. Documented so the test doesn't assert against the wrong store. |

**Error taxonomy:** background failures are non-fatal to the request (logged); `failOnError` promotes them to fatal-for-the-parent (fail-fast, fresh-retry only). No retryable/fatal classification is added.

## 7. Testing Strategy

**Goal & goal check.** The goal is the real-world outcome: *a durable flow whose background work is interrupted by a crash comes back without silently dropping or re-running work that already completed, and re-runs still-in-flight work at-least-once (so non-idempotent effects must be guarded) — on a real database.* Note the deliberate asymmetry: the framework guarantees replay of *completed* work, not exactly-once for *in-flight* work. **No real-LLM goal check applies** — this is deterministic crash-recovery and persistence semantics with no model-exercised behavior. Per `fsd:diagnose`, the real-path confirmation is the **cross-store recovery tests** in step 3, which exercise the real `continueRequest` path against real SQLite and Postgres (PGlite) stores.

**Discipline:** `fsd:diagnose` (verify-and-harden / regression), with the three contracts above as the decided behaviors each regression test encodes.

**Feedback-loop seams:**
- Engine-level (Contracts A & B): vitest in `packages/engine/test/background-work-recovery.test.ts`, driving `runAction` → `continueRequest` against in-memory durable stores. The mid-drain harness must prevent first-run tasks from advancing after the simulated crash (cold restart or cancel/settle the deferreds) — otherwise live first-run promises contaminate the counters/traces the assertions read.
- Cross-store (Contract C): vitest in `packages/store-sqlite/test/` and `packages/store-postgres/test/`, driving the real `continueRequest` against persistent stores, with an intervening in-progress-trace flush so the FIX-839 content-diff path is actually exercised.

**Trace-retention in tests.** Every test forces `FSDEV_TRACE_OBSERVABILITY=true` (the FIX-839 regression's pattern). A test that relies on the production default (observability off) would see no retained traces and prove nothing about replay.

**Behaviors to assert (observable terms):**
- Completed `.forEachBackground` iteration → handler invocation count stays 1 across the crash; output observable via `ctx.getBlockOutput` after continuation.
- In-flight iteration → handler invocation count increments on the continued run (re-run); at-least-once, not exactly-once.
- Failed `.work()` under completed parent → request status `completed`; one `errored` `block_trace`; no retry.
- Failed `.work()` with `failOnError` → request status `failed`; parent throws; not continuable on the same id.
- Completed `.work()` before crash on SQLite **and** Postgres (with an in-progress flush) → persisted trace `status: "completed"`; injected on continuation (handler count 1).

**Patterns to reference:** `packages/engine/test/background-work-recovery.test.ts` (existing harness — durable stores, simulated crash via `interrupted`, dual-assert run-count + observed-output); `packages/store-sqlite/test/completed-trace-persistence.test.ts` (FIX-839 persisted-trace assertion + the in-progress-flush trigger); `packages/store-sqlite/test/multigate-cold-restart.test.ts` (cross-store `continueRequest` cycle via a cold restart). The `fsd:write-block-tests` mock-context idiom applies for any block-level isolation.

## 8. Non-Goals

- **Detached / spawned background as its own request** — was FIX-815 (cancelled); the reactive variant is FIX-825 / FIX-441. Out of scope.
- **The `.work` / `.forEachBackground` API surface** — unchanged. No new options, no `durable:` flag on side chains.
- **Generator / router continuation** — FIX-814.
- **Changing the trace-retention precondition.** This spec *names* the precondition (replay needs retained `block_trace`, which is gated by observability / `transient`) but does not change it. Whether durable resume should force trace retention independent of devtool observability is a framework question larger than FIX-866 (Open Question 1 / Non-Goal here).
- **A durable dead-letter / recoverable-record subsystem for failed background tasks.** Contract B resolves the failed-task case as drop-and-log + `failOnError` fail-fast. A first-class "retry this failed background task later" mechanism is a separate, larger design; flag it for follow-up only if a concrete consumer appears. (Before adding it later, check `docs/internal/out-of-scope/` for a prior rejection.)
- **Drain-on-suspend symmetry** — deliberately not added (Decision 2).
- **Deepening opportunity (flag, not in scope):** the drain asymmetry between the suspend path and the terminal path in `runAction.ts` is implicit and only discoverable by reading both paths. If it proves a recurring source of confusion, consider extracting a single named "settle background work for this lifecycle transition" seam — follow up via `fsd:improve-codebase-architecture`, not here.

## 11. Open Questions

1. **Does durable resume memoization depend on trace observability in production?** `block_trace` capture is gated by `isTraceObservabilityEnabled()` (off when `NODE_ENV === "production"`), and the ReplayLog's only source is retained `block_trace` items. Taken literally, a production deployment without `FSDEV_TRACE_OBSERVABILITY=true` retains no traces, so *every* block (foreground and background) re-runs on continuation — memoization becomes a no-op. Either (a) production crash-recovery deployments are expected to enable trace observability (then document it loudly as a durability requirement), or (b) replay should retain `block_trace` independent of the devtool observability flag (then that's a framework gap larger than FIX-866). FIX-866 names the precondition and tests with observability forced on; **the production-default question should be routed to the FIX-811 owner** rather than silently decided here. Flag for the issue owner.
2. **Late trace-write durability after suspension.** Step 1 will reveal whether a background task that completes *after* the suspend-path flush still persists its `completed` trace, or whether the write is dropped (record already flushed to `suspended`). A dropped *late* write is contract-consistent (the iteration re-runs, Contract A); a dropped *pre-flush completed* trace is a real bug to fix in step 4.
3. **Postgres test runner availability.** Confirm the store-postgres PGlite harness runs in the same CI lane as store-sqlite. If Postgres tests are gated behind an env flag, the cross-store assertion for Postgres runs behind that same gate — note it in the PR rather than weakening the SQLite assertion.
