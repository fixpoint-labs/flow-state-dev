# FIX-875: Interactive chat harness (`fsdev chat`) — loop, routing, and target-resolver foundation — Implementation Spec

## 1. TLDR

**Plain-language summary.** Today you can only talk to a flow-state project one command at a time: run a flow, read the output, run it again. This change adds a live conversation mode to the `fsdev` terminal tool. You start it with `fsdev chat`, type messages that go to whichever flow is currently "driving," and use slash commands (like `/use` or `/targets`) to switch flows, see what's available, or check your session. The same loop is designed so that later it can front more advanced setups — a dev agent, a self-managing operator, a workstream driver — just by pointing it at different flows.

**Technical statement.** Add an interactive REPL command `fsdev chat` to `packages/cli` that holds a persistent engine session, routes free text to a switchable default `(flow, action)` target via in-process `runAction`, and dispatches `/`-prefixed built-in commands through a pure, transport-agnostic parse→resolve→execute pipeline with a `Target` seam that later admits skills and workstreams as target kinds.

**Deliverables:**

- **Harness core (pure, transport-agnostic):** Add `packages/cli/src/chat/` — `parse.ts` (input → chat text | command), `targets.ts` (`Target`/`Dispatch` types + resolver), `registry.ts` (built-in command registry: `/help`, `/targets`, `/use`, `/status`, `/session`, `/exit`), `state.ts` (harness state: default target, session id).
- **Shared grammar + runtime prelude:** Export the slash-command pattern (`SLASH_COMMAND_PATTERN`) from `@flow-state-dev/core` and import it in both `packages/skills/src/skill-slash-match.ts` and the harness parser (one grammar, structurally enforced). Extract the ~30-line runtime *prelude* that is copy-paste-identical between `run.ts` and `dev.ts` (env load → `loadFsdevConfig` → `--flow-dir`-with-config guard → `discoverFlows` + import-failure warnings) into `packages/cli/src/resolve-runtime.ts` and migrate `run.ts`, `dev.ts`, and the new `chat.ts` onto it — stores, `--model` handling, and dispose ownership stay per-command (they genuinely diverge; a broad helper would be a shallow module, BP-024).
- **Loop + rendering:** Add `packages/cli/src/chat/loop.ts` (readline-based REPL, TTY and piped-stdin modes, Ctrl-C turn-abort / double-Ctrl-C exit) and `packages/cli/src/chat/render.ts` (`ChatRenderer` interface + plain-text implementation over the engine's item stream).
- **Command wiring:** Add `packages/cli/src/commands/chat.ts` (`fsdev chat [flow] [action]` with `--config`, `--session`, `--user`, `--model`, `--flow-dir`, `--dotenv`), registered in `packages/cli/src/cli.ts`.
- **Execution:** per-turn in-process `runAction` with per-flow persistent sessions, an explicitly threaded `requestId`, interrupt via the engine's exported `abortRequest` (true `aborted` semantics, not `interrupted`), and the emitter-event mapping already proven by `fsdev run`.
- **Tests:** vitest specs for parse/resolve/registry + a piped-stdin integration test following `packages/cli/test/run-command.integration.test.ts`; goal check under `goals/chat-harness/`.
- **Docs:** new `apps/docs/docs/cli/interactive-chat.md` page, `fsdev chat` sections in `apps/docs/docs/api/cli.md` and `packages/cli/README.md`, cross-link edits, changeset.

**Size estimate.** **Large** — primarily `packages/cli`, plus a one-line pattern export in `core`, an import swap in `skills`, and the ~30-line prelude refactor touching `run.ts`/`dev.ts`; one implementation PR (harness core + loop + command + tests) with docs riding the same PR (project convention: docs ship in the same change set). ~700–1000 LOC including tests.

## 2. Overview

Linear issue: [FIX-875](https://linear.app/fixpoint-labs/issue/FIX-875/design-interactive-chat-harness-fsdev-chat-loop-routing-and-target) (project: [Interactive Shell Harness](https://linear.app/fixpoint-labs/project/interactive-shell-harness-e41da8ee4f31)).

Every interaction surface today is one-shot (`fsdev run`, `fsdev block`) or browser-bound (`fsdev dev` + DevTool, web chat UIs). This spec designs the persistent interactive operator surface: a terminal loop that holds a session, routes free text to a chosen flow/action, and dispatches explicit commands. The organizing constraint from the issue holds throughout: **the harness is the invariant; the persona is a flow-level concern.** Nothing in this design hardcodes a dev agent, operator, or workstream — those arrive later as activated flows.

## 3. Background & Research

### 3.1 Codebase findings (verified in source)

- **In-process execution is fully served by existing seams.** `runAction` (`packages/engine/src/execution/runAction.ts:461`) accepts `requestId` (`execution/types.ts:83`), `signal?: AbortSignal`, and `onItem?: (item, kind) => void` (live fan-out identical to what feeds SSE clients — `execution/types.ts:133`). **Abort semantics matter:** a bare caller-signal abort takes the *disconnect* branch (`runAction.ts:1565`) — record status `"interrupted"`, no user-visible item. The true abort path (`"aborted"` status + the "Request was stopped." status item, `emitAbortedMessage`, `runAction.ts:425`) requires `abortRequested: true` on the request record plus the abort registry — the same sequence the HTTP abort route performs (`routes/abort-routes.ts:53`), available in-process via the exported `abortRequest(requestId)` (`execution/index.ts:19`). The harness uses the true abort path (§4.6). Multi-turn memory is an engine concern: `hello-chat`'s generator sets `history: true` (window: last 50 completed requests by default, `core/src/types/flow.ts:293`); the CLI's only job is to hold a stable `sessionId` (what `fsdev run --session` proves today).
- **Runtime resolution is an established two-path pattern.** Both `run.ts` (`executeRunCommand`, steps 0–1) and `dev.ts` (`executeDevCommand`) resolve: `.env` loading → `loadFsdevConfig` (app's `FlowState` wiring: registry, stores, model resolver) → fall back to `discoverFlows` + CLI-owned stores. `fsdev chat` composes the same building blocks.
- **The slash grammar already exists in the framework.** `packages/skills/src/skill-slash-match.ts:23` anchors `/^\/([a-z0-9][a-z0-9-]{0,63})(?:\s+([\s\S]*))?$/` as tier 1 of `skillActivator` — a leading `/skill-name` in the *user message* resolves a skill inside the flow. This is load-bearing for the harness grammar decision (§3.3, decision 3).
- **The cited sibling issues are all unbuilt.** No Ink integration exists in `packages/cli` (FIX-217/FIX-186 not started; `format-output.ts` is JSON-only). No `packages/flows` (FIX-130's PR #141 is closed-unmerged). No dev-agent flow or eject workflow (FIX-18 in Backlog). No open PRs touch `packages/cli`. **The spec therefore treats all four as non-dependencies** and designs seams they can slot into.
- **CLI package boundary:** `cli` depends on `core`, `engine`, `testing` — *not* `client` (`docs/architecture/overview.md` dependency graph). An in-process harness adds no edge; an attach-over-HTTP mode would add `client` and is deferred (§8).

### 3.2 Industry research (summarized; sources linked inline)

- **Command prefix:** every mainstream free-text-first AI CLI (Claude Code, aider, Gemini CLI, Codex CLI) uses `/`; `:` belongs to *modal* tools (vim, ghci) where the input line is not normally free text. The standard collision fix is **resolve-or-send**: input is a command only if the first token resolves in the registry; otherwise it is chat. ([aider commands](https://aider.chat/docs/usage/commands.html), [Claude Code commands](https://code.claude.com/docs/en/commands), [Gemini CLI](https://google-gemini.github.io/gemini-cli/docs/cli/commands.html))
- **Loop construction:** Ink solves streamed-output/prompt interleaving declaratively and is what Gemini CLI uses; raw `node:readline` requires manual cursor discipline but is dependency-free and adequate when the prompt is hidden while a turn streams. Cancellation convention: model the **turn** as the unit of interruption, wired to an `AbortController`. ([Ink](https://github.com/vadimdemedes/ink), [Codex architecture](https://codex.danielvaughan.com/2026/03/28/codex-rs-rust-rewrite-architecture/))
- **Dispatch:** the convergent shape is a **command registry with a default chat target** — parse → resolve → execute → render, with the resolver a pure function so it tests without I/O. ([atmos command-registry PRD](https://github.com/cloudposse/atmos/blob/main/docs/prd/command-registry-pattern.md))
- **Runtime placement:** local dev CLIs default to in-process; the transferable lesson from Codex's app-server is *decouple the UI from the runtime behind an event stream*, which the engine's emitter already provides — not "put a socket in the middle."

### 3.3 Key Decisions & Ramifications (top 5)

1. **In-process runtime via `runAction`; attach mode deferred.** *Alt rejected:* build on `@flow-state-dev/client` with an in-process transport so `--attach <url>` is a flag-swap. That would require inventing an in-process client transport today (speculative surface, BP-038) and add a `cli → client` package edge for a second consumer that doesn't exist yet. *Ramification:* the harness cannot join a session being served by a running `fsdev dev`/production server in v1; the decoupling that makes attach cheap later is preserved at a different altitude — the harness core is pure and the renderer consumes engine emitter events, the same events SSE carries.
2. **`/` prefix with resolve-or-send; unknown `/name` falls through to the flow as chat text.** *Alt rejected:* terminal-native `:` prefix. `/` is the muscle memory of every comparable tool *and* — decisive, beyond the industry default — the fall-through composes with the framework's own skills tier: `/skill-name args` that no built-in claims reaches the flow intact (the raw line, slash included), where `skill-slash-match` resolves it. To make "one grammar" a structural invariant rather than a convention, the pattern is exported from `@flow-state-dev/core` as `SLASH_COMMAND_PATTERN` and imported by both `skills` and the harness parser (both packages already depend on `core` — no new edge). *Ramification:* built-ins shadow same-named skills; the built-in namespace must stay small and stable (six verbs in v1), and the precedence rule (registry first, flow second) is a documented contract.
3. **Built-in commands are plain in-CLI handlers, not a built-in flow bundle.** *Alt rejected:* the issue's candidate framing — ship the help/list/switch/status surface as flows using FIX-18's built-in/eject pattern. That pattern is unbuilt; making `/help` a flow would put a design-blocking dependency on FIX-18 and route trivial metadata reads through the engine. *Ramification:* v1 built-ins are not user-extensible or ejectable; the registry entry shape (§4.3) is written so a later `flow-backed` command kind slots in without changing dispatch — that upgrade is Phase 2, alongside FIX-18.
4. **Rendering is a `ChatRenderer` seam with a plain-text implementation; Ink is not adopted here.** *Alt rejected:* integrate Ink now (the research recommendation in isolation). Ink is FIX-217's whole scope; absorbing it would triple this spec and duplicate a tracked issue. Plain text is sufficient because the loop hides the prompt while a turn streams (the interleaving problem readline actually has only exists when prompt and stream fight for the cursor). *Ramification:* no fancy in-place UI in v1 (no spinners/redraw); FIX-217 lands as a second `ChatRenderer` implementation, not a rewrite — the seam is the contract.
5. **Sessions persist in the same stores the engine already uses — SQLite at `.fsdev/data/fsdev.db` in the discovery path, the app's own stores in the config path.** *Alt rejected:* a harness-private JSONL transcript directory (the Claude Code convention). The engine *is* the session store (request items, session state, history reload all live there), and reusing `fsdev dev`'s database means a chat session is inspectable in the DevTool (with identities aligned — chat defaults to `cli-user`, the DevTool to `devuser`; §4.5). *Ramification:* no human-greppable transcript file in v1 (NDJSON capture stays a `fsdev run` feature); resume is `--session <id>`, and cross-surface inspection comes free.

## 4. Technical Design

### 4.1 Architecture

Nearly all new code lives in `packages/cli`; two sibling packages get one-line-scale changes for the shared grammar.

```
packages/cli/src/
  commands/chat.ts        NEW  commander registration + runtime resolution + wiring
  chat/
    parse.ts              NEW  pure: line → ParsedInput (chat | command | noop)
    targets.ts            NEW  pure: Target/Dispatch types, target enumeration + resolution
    registry.ts           NEW  built-in command definitions
    state.ts              NEW  HarnessState (default target, per-flow session ids, turn counter)
    loop.ts               NEW  readline loop, signal handling, turn lifecycle
    render.ts             NEW  ChatRenderer interface + createPlainTextRenderer()
  resolve-runtime.ts      NEW  shared ~30-line runtime prelude (env → config → guard → discovery)
                               extracted from run.ts/dev.ts; all three commands migrate onto it
  cli.ts                  MODIFIED  register chat command
  index.ts                MODIFIED  export registerChatCommand/executeChatCommand + public chat
                                    types (Target, ParsedInput, ChatRenderer), matching the
                                    existing dev/ui export pattern
  commands/run.ts         MODIFIED  consume resolve-runtime prelude (behavior unchanged)
  commands/dev.ts         MODIFIED  consume resolve-runtime prelude (behavior unchanged)

packages/core             MODIFIED  export SLASH_COMMAND_PATTERN (the skills tier-1 regex, verbatim)
packages/skills/src/skill-slash-match.ts  MODIFIED  import the pattern from core (no behavior change)
```

Scope boundary for the prelude: only the copy-paste-identical lines (env load → `loadFsdevConfig` → `--flow-dir`-with-config guard → `discoverFlows` + import-failure warnings). Store backend, `--model` handling, and dispose ownership genuinely diverge per command and stay per-command — a broad helper would be a shallow module (BP-024: helpers when the body varies). Command-specific *pre-config* env defaults also stay per-command: `dev.ts` sets `FSDEV_DEBUG_ENDPOINTS`/`FSDEV_TRACING_LEVEL` before config import (`dev.ts:112`) so a config-backed DevTool keeps debug endpoints and verbose tracing — those lines run before `dev.ts` invokes the prelude and are **not** absorbed into it (the prelude's contract: callers set command-specific env defaults first).

The `chat/` modules other than `loop.ts` are **pure** (no I/O, no readline, no process): this is the transport-agnostic dispatch core the issue asks for, sited in `packages/cli` per the two-consumer discipline — it is promoted to a shared package only when a second consumer (web surface / workforce) actually materializes.

### 4.2 Data flow (one turn)

```
stdin line
  → parseInput(line)                             parse.ts (pure)
  → resolveDispatch(parsed, state, targets)      targets.ts (pure)
      ├─ { kind: "builtin", command, args }      → registry handler (mutates HarnessState / prints)
      ├─ { kind: "flow-action", target, text }   → executeTurn()
      └─ { kind: "noop" | "unbound" }            → hint / re-prompt
executeTurn:
  runAction({ flow, actionName, input: { message: text }, userId: "cli-user",
              sessionId: state.sessions.get(target.flowKind),   // seeded at bind time (§4.3);
              requestId,                                        // never undefined here
              stores, responseEmitter, signal, runtimeConfig })
  → responseEmitter events → ChatRenderer (streamed assistant text, item one-liners)
  → turn settles → re-prompt
```

### 4.3 API surface (exact shapes)

```ts
// chat/parse.ts
export type ParsedInput =
  | { kind: "empty" }
  | { kind: "chat"; text: string }
  | { kind: "command"; name: string; args: string; raw: string };
/** Any line whose first non-space-escaped character is "/" parses as
 *  `command`, using SLASH_COMMAND_PATTERN (exported from @flow-state-dev/core;
 *  the same pattern skills' tier-1 slash match imports). A lone "/" parses as
 *  `command` with `name: ""` — dispatch maps it to a noop + help hint. A
 *  leading space escapes: " /etc..." is always chat. */
export function parseInput(line: string): ParsedInput;

// chat/targets.ts
export interface FlowActionTarget {
  kind: "flow-action";
  flowKind: string;
  actionName: string;
}
/** Future kinds ("skill", "workstream") extend this union; dispatch is
 *  exhaustive over Target["kind"] so additions are compile-checked. */
export type Target = FlowActionTarget;

export type Dispatch =
  | { kind: "builtin"; command: BuiltinCommand; args: string }
  | { kind: "turn"; target: FlowActionTarget; text: string }
  | { kind: "fallthrough"; text: string }   // unknown /name → the RAW line (slash included) to the
                                            // default target, so in-flow skill-slash-match still fires
  | { kind: "unbound" }                     // free text but no default target set
  | { kind: "noop"; hint?: string };        // empty name (lone "/") → help hint

/** One target per flow kind × action, taken from the registry's DEFAULT
 *  instance per kind (the same `registry.get(kind)` resolution `fsdev run`
 *  uses, `run.ts:337`). The registry can hold multiple instances of one kind
 *  (distinct ids); non-default instances are deliberately not enumerated —
 *  no CLI surface can address an instance by id today, so listing them would
 *  advertise indistinguishable, unselectable duplicates and collapse under
 *  the per-flowKind session map. Instance-id addressing is deferred (§8).
 *  Enumeration derives the distinct kinds from `list()` but reads each
 *  kind's actions from `registry.get(kind)` — the same call turn execution
 *  uses — because the two orderings differ (`get()` prefers a kind-matching
 *  id then first-registered, `flow-registry.ts:124`; `list()` sorts ids
 *  lexicographically, `:143`): enumerating actions from `list()` could
 *  advertise an instance that never executes. */
export function listTargets(registry: {
  list(): FlowInstance[];
  get(kind: string, id?: string): FlowInstance | undefined;
}): FlowActionTarget[];
export function resolveDispatch(
  parsed: ParsedInput,
  state: HarnessState,
  builtins: ReadonlyMap<string, BuiltinCommand>
): Dispatch;

// chat/registry.ts
export interface BuiltinCommand {
  name: string;                 // "help" | "targets" | "use" | "status" | "session" | "exit"
  summary: string;              // one line for /help
  usage: string;                // e.g. "/use <flow> [action]"
  run(args: string, ctx: BuiltinContext): Promise<BuiltinResult>;
}
export interface BuiltinContext {
  state: HarnessState;
  targets: FlowActionTarget[];
  write(line: string): void;
}
export type BuiltinResult = { ok: true; exit?: boolean } | { ok: false; message: string };
export function createBuiltinRegistry(): ReadonlyMap<string, BuiltinCommand>;

// chat/state.ts
export interface HarnessState {
  defaultTarget: FlowActionTarget | undefined;
  /** One session per flowKind within a harness run. Session records are not
   *  flowKind-bound in the engine (history loads by sessionId alone), so
   *  sharing one id across `/use` switches would bleed flow A's history and
   *  state into flow B's context. Switching targets switches to (or creates)
   *  that flow's session; switching back resumes where that flow left off. */
  sessions: Map<string, string>;            // flowKind → sessionId
  turns: number;
}
/** The active session id: `sessions.get(defaultTarget.flowKind)`. Binding a
 *  target — at startup (positional or auto-bind) or via `/use` — seeds this
 *  map with a stable `sess_…` id BEFORE any turn runs: turn execution never
 *  passes `sessionId: undefined` to `runAction`, because
 *  `createExecutionContext` would silently substitute a per-run `ephemeral_…`
 *  id (`createExecutionContext.ts:516`) and no history would persist across
 *  turns. */

// chat/render.ts
export interface ChatRenderer {
  onEvent(event: RequestStreamEventWithId): void;  // same event type run.ts maps
  onTurnStart(target: FlowActionTarget): void;
  onTurnEnd(result: { success: boolean; durationMs: number; aborted: boolean }): void;
  onSystem(line: string): void;                    // harness messages (hints, errors)
}
export function createPlainTextRenderer(out: NodeJS.WritableStream): ChatRenderer;

// commands/chat.ts
export interface ChatCommandOptions {
  session?: string;
  user?: string;                // engine identity; default "cli-user" (§4.5)
  model?: string;
  flowDir?: string[];
  dotenv?: string[];
  config?: string | boolean;
  quiet?: boolean;
  logLevel?: RuntimeLoggerLevel;
}
export function registerChatCommand(program: Command): void;
export async function executeChatCommand(
  flowKind: string | undefined,
  actionName: string | undefined,
  options: ChatCommandInternalOptions   // + cwd?, stores?, modelResolver? (test override for
                                        // generator fixtures via createMockModelResolver from
                                        // @flow-state-dev/testing), input?/output? streams
): Promise<void>;
```

### 4.4 Command surface

```
fsdev chat [flow] [action]
  -s, --session <id>       resume an engine session for the initially bound flow
                           (default: fresh sess_… id per flow as targets are used;
                           requires an initially bound target — see startup binding)
  -m, --model <model>      model override (wraps resolver exactly as run.ts step 5)
  -u, --user <id>          engine identity for sessions and turns (default: "cli-user",
                           as fsdev run; the DevTool defaults to "devuser" — align the
                           two to inspect or resume across surfaces, §4.5)
  --flow-dir <path>        discovery override (repeatable; rejected with config, as run.ts)
  --dotenv <path>          explicit env file(s) (as run.ts step 0)
  --config <path> / --no-config    fsdev.config selection (as run.ts step 1)
  --quiet / --log-level    stderr runtime-log discipline (as run.ts; default log level "warn"
                           so the transcript isn't drowned by info-level engine logs)
```

**Startup target binding:** positional `[flow] [action]` binds the default target (action defaults to the flow's sole action; ambiguous → error listing actions, `EXIT_INVALID_ARGS`). With no positionals: **zero available targets is fatal** — `CliError(EXIT_DISCOVERY_ERROR)` listing searched dirs, exactly like `fsdev run`; never an unbound loop in an empty project. If exactly one discovered flow has exactly one action, auto-bind it and announce. Otherwise (targets exist but none is auto-bindable) start **unbound** — the banner lists targets and free text prompts "No default target — pick one with `/use <flow> [action]`." **`--session` requires an initially bound target:** when startup would begin unbound, passing `--session` is an error (`CliError(EXIT_INVALID_ARGS)`) rather than a silent drop — sessions bind per flow as targets are used, so an id supplied with no flow to bind it to would never take effect. The error message points at the two working paths: bind positionally (`fsdev chat <flow> --session <id>`) or start without the flag and run `/session <id>` after `/use`. **`--session` is also guarded:** an existing session must pass the session guard (see below the built-ins table — record `flowKind` match *and* no cross-flow request history) or startup fails with `EXIT_INVALID_ARGS`. Binding — positional, auto-bind, or `/use` — always seeds the per-flow session map with a stable `sess_…` id before the first turn (§4.3).

**Free-text input contract:** a turn sends `input: { message: text }`. This matches the ecosystem's chat actions (`hello-chat chat`, kitchen-sink `chat-agent`). An action whose input schema rejects `{ message }` fails that turn with the engine's validation error rendered and a hint that the target isn't chat-shaped; the session continues. (A per-target input template is deliberately not designed here — §8.)

**Built-ins (v1, complete list):**

| Command | Behavior |
|---|---|
| `/help` | List built-ins with usage; note the fall-through rule ("anything else after `/` goes to the flow — that's how skills are invoked"). |
| `/targets` | Enumerate `flowKind · action` pairs from the registry/discovery set; mark the current default. |
| `/use <flow> [action]` | Rebind the default target (validated against `listTargets`; unknown → `ok: false` with suggestions). Switches to that flow's session (creating one on first use); announces whether the session is fresh or resumed. |
| `/status` | Current target, active session id, turn count, runtime source (config path vs discovery), store line. |
| `/session [new\|<id>]` | No arg: print the active session id. `new`: rotate the *current flow's* session to a fresh id (state continuity intentionally broken). `<id>`: bind the current flow to that id, subject to the **session guard** (below). Nonexistent ids are allowed (the engine creates the record on first turn). |
| `/exit` | Leave the loop (also Ctrl-D, and double-Ctrl-C). |

**Session guard** (applies to `--session` at startup, to `/session <id>`, and re-checked before every turn): an *existing* session is rejected when (a) its record's `flowKind` differs from the bound flow — the engine's state/resource routes resolve the flow from the session record (`state-routes.ts:54`, `resource-routes.ts:80`), so a cross-flow bind would run turns against one flow while the DevTool and session APIs resolve another — or (b) at bind time, its completed request history contains a different `flowKind`: history is loaded by `sessionId`/tenant/status alone with **no flow filter** (`createExecutionContext.ts:557`), so a session id reused across flows by today's `fsdev run --session` can pass the record check yet still import cross-flow history into the next turn's context. Request records carry `flowKind`, so (b) is one windowed `stores.request.list` read at bind time. Rejection surfaces as `CliError(EXIT_INVALID_ARGS)` at startup and `ok: false` from the builtin; at turn time a record-check mismatch fails that turn, clears the flow's session-map entry, and hints `/session new`. The per-turn re-check (record only — cheap `stores.session.get`) closes the bind-while-nonexistent hole: bind `shared` under flow A, `/use` flow B, run a turn on `shared` there (the engine creates the record with `flowKind: B`), switch back to A — A's stale map entry must not silently execute against B's session.

### 4.5 Runtime resolution & lifecycle

`executeChatCommand` composes the same building blocks as `run.ts`/`dev.ts`, in the same order — env load, config-vs-discovery, stores, model resolver:

- **Config path:** `loadFsdevConfig` → `flowState.getRuntime()` → registry/stores/runtimeConfig; `--flow-dir` rejected; `--model` wraps the config's resolver via `forceModelResolver` (identical to `run.ts` step 5). Dispose the `FlowState` on loop exit (single teardown path, as `dev.ts`).
- **Discovery path:** `discoverFlows` with import-failure warnings on stderr; stores = `createSQLiteStores({ filename: ".fsdev/data/fsdev.db" })` after `mkdir -p .fsdev/data` — the `dev.ts` choice, not `run.ts`'s filesystem store, because an interactive session is long-lived, multi-turn, and this makes it DevTool-inspectable. `stores.close()` on exit.
- **Per turn:** fresh `requestId` — **passed into `runAction`** (unlike `run.ts`, which mints one for the emitter but lets `runAction` mint its own; chat needs one agreed id for the abort registry, `/status`, and item correlation) — and a **fresh `ResponseEmitter` per turn** (`runAction` rebinds item/event hooks per run and sequence numbers are per-emitter; reuse would corrupt both). `runtimeConfig = { ...base, modelResolver, logger }` with the CLI stderr logger (`createCliLogger` pattern from `run.ts:211` — currently private, so hoist it into the shared prelude module rather than copying it a third time; default level `warn`).
- **`--model` with a config** follows `run.ts` (wrap the config's resolver via `forceModelResolver`), deliberately diverging from `dev.ts`, which rejects the combination — the in-process one-shot runner is the right analog for per-turn execution, and the divergence is called out here so it reads as chosen, not accidental.
- **`userId`:** `"cli-user"` by default (the established CLI identity, `run.ts:473`), overridable with `--user`. **Identity matters for cross-surface interop:** sessions are user-bound in the engine (`UserBindingMismatchError` when a session's `userId` doesn't match the caller, `createExecutionContext.ts:634`), and the DevTool's default identity is `"devuser"` (`devtool/src/react/config.ts:8`) with its session list filtered by user — so chat sessions don't appear in a default DevTool, and resuming a DevTool-created session as `cli-user` is rejected by the engine. To get the DevTool-inspectability benefit of the shared SQLite store (§3.3 decision 5), align the identities from either side: `fsdev chat --user devuser`, or point the DevTool's user setting at `cli-user`. The docs page calls this out explicitly (§9).
- **Concurrency policies (`action.concurrency` / `flow.request.concurrency`) are knowingly not arbitrated on this path.** The arbiter lives in the inbound transport host and is in-memory, per-process (v1 enforces the in-process dispatcher only — `transports/concurrency/arbiter.ts`). Chat inherits `fsdev run`'s direct-`runAction` semantics and holds **at most one turn in flight** (readline is paused while a turn streams; piped mode is strictly sequential), so its own dispatches can never contend — routing through a host seam would gate nothing. Cross-*process* contention (a chat process plus a `fsdev dev` server on the same SQLite store) is not arbitrated by any existing seam either — in-process gates don't coordinate across processes, and durable-substrate enforcement is FIX-830's scope — so it surfaces as the store-contention row in §4.8, same as two `fsdev run` invocations today.
- **SQLite path is cwd-relative** (`".fsdev/data/fsdev.db"` resolves against `process.cwd()`): the test seam injects `stores` (as `run.ts` tests do) rather than relying on the `cwd` option to redirect the file.

### 4.6 Loop, signals, and modes

`loop.ts` uses `node:readline` (`createInterface({ input, output, terminal })`):

- **TTY mode:** prompt `❯ ` shown only when idle. While a turn is in flight the readline interface is paused and the renderer owns stdout — this sidesteps readline's cursor-interleaving problem without Ink.
- **Interrupt:** readline's `SIGINT` event. In-flight turn → the **true abort path**, not a bare signal abort: patch the request record with `abortRequested: true` (the CLI owns `stores`) and call the engine's exported `abortRequest(requestId)` — the same sequence the HTTP abort route performs. The request settles with status `"aborted"` and the engine emits its "Request was stopped." status item; renderer prints `(interrupted)`; re-prompt. (A bare `controller.abort()` would instead leave an `"interrupted"` record — the state crash-recovery and the DevTool treat as *resumable*, turning every Ctrl-C into phantom recoverable requests in the shared database.) **The sequence is retried, not one-shot:** `runAction` registers the abort controller and writes the initial request record *after* the harness calls it (`runAction.ts:824` registration precedes the record write inside `createExecutionContext`), so a fast Ctrl-C during slow setup can land before the record exists — a single patch would no-op, the catch path would see `abortRequested !== true`, and the turn would settle `"interrupted"` after all. The interrupt handler therefore treats Ctrl-C as durable intent: it re-attempts the patch + `abortRequest(requestId)` on a short interval (~25 ms) until the patch has landed on an existing record or the turn settles, whichever is first. At idle prompt → first Ctrl-C prints `(press Ctrl-C again or /exit to quit)`, second within the same idle period exits. Ctrl-D (readline `close`) exits.
- **Piped-stdin mode (non-TTY):** no prompt, lines consumed sequentially, each turn runs to completion before the next line is read, EOF exits cleanly. This mode is the test/goal-check seam and mirrors `fsdev run`'s scriptability.
- **Exit codes:** `EXIT_SUCCESS` on `/exit`/EOF in TTY mode; startup failures reuse the taxonomy (`EXIT_CONFIG_ERROR`, `EXIT_DISCOVERY_ERROR`, `EXIT_INVALID_ARGS`); a failed *turn* never exits the loop. **Piped mode is scriptable, so failures must reach the exit code:** the loop tracks whether any turn failed (execution error, validation rejection, unbound input) **or any built-in returned `ok: false`** (a scripted `/use missing` or rejected `/session <id>` must not exit 0 just because no turn ran), and EOF then exits `EXIT_EXECUTION_ERROR` — the same code `fsdev run` uses for a failed run — instead of `EXIT_SUCCESS`. Later lines still process (partial transcripts stay useful); TTY sessions still exit 0 on `/exit`/Ctrl-D because the user saw the errors interactively.

### 4.7 Rendering (plain text, v1)

`createPlainTextRenderer`: `content.delta` for assistant message items → streamed verbatim; `item.added`/`item.done` for non-message items → single dim one-liner (`· tool call: search-web`, `· status: Request was stopped.`); user-message echo suppressed (the user just typed it); turn end → blank line. Deliberately minimal — richness is FIX-217's scope, arriving as a second `ChatRenderer`.

### 4.8 Error handling

| Error | Layer | Handling |
|---|---|---|
| Config load failure | startup | `CliError(EXIT_CONFIG_ERROR)`, exit (as `run.ts`) |
| No flows discovered | startup | `CliError(EXIT_DISCOVERY_ERROR)` listing searched dirs |
| Ambiguous positional action | startup | `CliError(EXIT_INVALID_ARGS)` listing actions |
| Turn execution error (`result.error` or throw) | turn | render error line, keep session, re-prompt |
| Action input validation rejects `{ message }` | turn | render engine error + "target isn't chat-shaped; `/use` another target" |
| `/use` unknown flow/action | builtin | `ok: false` + nearest-match suggestions from `listTargets` |
| Abort mid-turn | turn | engine emits aborted status; renderer `(interrupted)`; re-prompt |
| Store contention with a running `fsdev dev` (same SQLite file) | turn | surfaced as turn error (better-sqlite3 busy); message names the dev server as the likely writer |

## 6. Edge Cases & Error Handling

| # | Case | Expected behavior |
|---|---|---|
| 1 | Empty line / whitespace | `{kind:"empty"}` → re-prompt, no turn |
| 2 | Lone `/` | parses as `command` with empty name; dispatch → `noop` with hint "type /help for commands" (consistent with §4.3's parse contract) |
| 3 | `/help extra args` | args ignored by `/help`; builtins define their own arg handling |
| 4 | `/unknowncmd do thing` | fall-through: sent as chat text to default target (skills path); if unbound → unbound hint |
| 5 | Leading space ` /etc/hosts is weird` | always chat (escape hatch) |
| 6 | `/use` with zero args | `ok:false` + usage line |
| 7 | `/use flow` where flow has multiple actions | `ok:false` listing that flow's actions |
| 8 | Free text while unbound | unbound hint + `/targets` suggestion; input not silently dropped |
| 9 | `--session` id that doesn't exist yet | engine creates it on first turn (existing `runAction` semantics) |
| 10 | `/session new` mid-conversation | fresh id; next turn has no history; `/status` reflects it |
| 11 | Ctrl-C at idle, then a line typed | abort-armed state resets; single Ctrl-C warning re-arms |
| 12 | Ctrl-C during turn, twice rapidly | first aborts turn; second during teardown does not kill the process (turn abort must settle; only idle double-Ctrl-C exits) |
| 13 | Turn in flight, stdin line arrives (piped mode) | strictly sequential: next line waits for turn settle |
| 14 | Flow's action requires fields beyond `message` | validation error rendered; session continues (no crash, no exit) |
| 15 | Config `FlowState` dispose fails on exit | warn to stderr, still exit with the loop's code (pattern: `run.ts` `disposeConfig`) |
| 16 | Same flow kind in config and `--flow-dir` | impossible: flags are mutually exclusive (as `run.ts`) |
| 17 | Zero flows discovered, no config | fatal at startup: `CliError(EXIT_DISCOVERY_ERROR)` listing searched dirs — never an unbound loop |
| 18 | Turn aborted, then next message sent | the aborted turn's partial output is **not** in the next turn's model context (history loads `status: "completed"` requests only) — documented behavior, and `/status` turn count still increments |
| 19 | `/use` to flow B, then back to flow A | flow A's session resumes where it left off (per-flow session map); no cross-flow history bleed |
| 20 | `--session` passed but startup is unbound | fatal: `CliError(EXIT_INVALID_ARGS)` — never silently dropped; message points at positional binding or `/session <id>` after `/use` (§4.4) |
| 21 | Ctrl-C lands before the request record exists (fast interrupt, slow setup) | abort intent is retried until the record materializes; turn still settles `"aborted"`, not `"interrupted"` (§4.6) |
| 22 | Registry holds two instances of one flow kind | `/targets` lists the kind once — the registry-default instance via `registry.get(kind)`, the same instance turns execute (§4.3); instance addressing deferred (§8) |
| 23 | `/session <id>` or `--session` names an existing session of a *different* flow — or one whose completed request history spans flows (legacy `fsdev run --session` reuse) | rejected by the session guard (builtin `ok: false` / startup `EXIT_INVALID_ARGS`) — the engine routes state/resources by the session record's `flowKind` and loads history with no flow filter (§4.4) |
| 24 | First message right after startup binding (no `/use` ever run) | executes under the stable `sess_…` id seeded at bind time — never an engine-minted `ephemeral_…` id (§4.3) |
| 25 | Piped input where one turn fails mid-stream, or a built-in returns `ok: false` | later lines still process; EOF exits `EXIT_EXECUTION_ERROR`, not `EXIT_SUCCESS` (§4.6) |
| 26 | Id bound while nonexistent under flow A, later materialized under flow B (`/use` B + turn), then `/use` back to A | the per-turn session-guard re-check fails A's next turn, clears A's map entry, hints `/session new` — never silently executes against B's session (§4.4) |
| 27 | Chat session not visible in the DevTool session list | identity mismatch, not data loss: chat defaults to `cli-user`, the DevTool to `devuser` — align with `--user devuser` or the DevTool user setting (§4.5) |

**Error taxonomy:** startup errors are fatal (exit-code table §4.6); turn errors and builtin errors are never fatal; the only retryable surface is "type it again" — no automatic retry in the harness (the engine's own `retry` policies still apply inside a turn).

## 7. Testing Strategy

**Goal.** A developer can hold a multi-turn conversation with a real flow from the terminal — messages stream back live, state persists across turns, and they can switch which flow is driving without restarting.

**Goal check (required, real model, out-of-CI).** `goals/chat-harness/holds-a-conversation/{goal.md, run.mts}` (per `goals/README.md` conventions — `goal.md` carries the Outcome/Signal/**Anti-game**/Model/Run/Verdict-log contract): `run.mts` spawns `fsdev chat hello-chat chat` with piped stdin feeding two related messages (`"My name is Ada."`, `"What is my name?"`) then `/status` and `/exit`, against the real `openai/gpt-5-mini` wiring of `examples/hello-chat` (needs `OPENAI_API_KEY`). **PASS:** exit 0, both assistant replies non-empty, second reply contains "Ada" (history actually threaded through the persistent session), `/status` output names the session id and target. **FAIL** otherwise. A short manual TTY checklist (prompt discipline, Ctrl-C abort, double-Ctrl-C exit) lives in `goal.md`, since raw-TTY signal behavior can't be exercised through pipes.

**Discipline:** `fsd:tdd` (feature — red-green-refactor, tracer-bullet slices). Behaviors to test, in observable terms:

1. `parseInput` classifies: chat / command+args / empty / lone-slash / leading-space escape (table-driven; mirrors `SLASH_PATTERN` cases).
2. `resolveDispatch` routes: known builtin → builtin; unknown `/name` → fallthrough; chat with target → turn; chat unbound → unbound.
3. `/use` rebinds and validates; `/targets` enumerates from a stub registry; `/session new` rotates state.
4. A turn against a fixture flow (in-memory stores) streams deltas through the renderer in order and increments session state across two turns under one `sessionId`. Generator-streaming coverage uses `createMockModelResolver`/`mockGenerator` from `@flow-state-dev/testing` injected via the `modelResolver` test override (existing CLI fixtures are handler-only).
5. An aborted turn settles as `"aborted"` (not `"interrupted"`): record patched + `abortRequest(requestId)` called, renderer received the "Request was stopped." status item, loop re-prompts, next turn succeeds. Includes the early-interrupt race: abort intent recorded *before* the request record exists still settles `"aborted"` via the retry loop (§4.6).
6. Piped-stdin end-to-end transcript (step-4 spec in §5), including the failure paths: a turn that fails mid-stream doesn't stop later lines, a failed built-in (`/use missing` then `/exit`) counts as failure even with zero turns run, and the process exits `EXIT_EXECUTION_ERROR` in both cases.
7. Startup binding matrix: positional, sole-flow auto-bind, unbound start (targets exist), zero-targets fatal error, ambiguous action error, `--session`-with-unbound-startup rejection.
8. `/use` across two fixture flows: each flow's session state advances independently; switching back resumes flow A's counter where it left off.
9. Session guards: startup binding and `/use` seed a stable `sess_…` id before the first turn (the store holds no `ephemeral_…` session records afterwards); `/session <id>` and `--session <id>` reject an existing session whose record `flowKind` mismatches the bound flow *and* one whose completed request history contains a foreign `flowKind` (seeded fixture: same session id with completed requests from two flows); the per-turn re-check catches the bind-while-nonexistent → materialized-under-another-flow sequence (edge case 26) by failing the turn and clearing the map entry.
10. `--user` threads through to `runAction` and session records; resuming a session created under a different user surfaces the engine's user-binding error as a startup/turn error, not a crash.

**CI seams and patterns:** vitest in `packages/cli/test/` — `chat-parse.test.ts`, `chat-dispatch.test.ts`, `chat-command.integration.test.ts` following `run-command.integration.test.ts` (fixture flows + injected `stores`/`cwd`/streams via `ChatCommandInternalOptions`). Block-level mock idioms per `fsd:write-block-tests` are not needed — no new blocks ship here.

## 8. Non-Goals

- **Attach mode (`--attach <url>` / joining a running server's session).** Deferred until a second surface demands it — and verified cheap when it comes: `@flow-state-dev/client` already ships the primitives (SSE reattach with `Last-Event-ID`/`starting_after` cursor resume in `createSSEClient`, transcript rehydration via `getSessionState(sessionId, { includeItems })`, out-of-band `abortRequest`). The pure core + renderer seam keep it a bounded addition. Follow-up issue when scheduled.
- **Ink/TUI rendering.** FIX-217/FIX-186 own it; lands as a second `ChatRenderer`.
- **Built-in flow bundle with eject/local-override.** FIX-18's pattern; the registry's command shape admits a `flow-backed` kind later (§3.3 decision 3). When that upgrade happens, the implemented precedent to model is the **skills seeding** semantics (`packages/skills/src/seeding.ts` — seed bundled defaults once, track seeded names, never clobber user edits), the only built-in/override pattern that exists in code today.
- **Skill/workstream target kinds.** The `Target` union is designed for them; `skill` waits on a CLI-side skill enumeration story (enumeration is feasible today via `listEnabledSkills(collection)` against the store, but *invocation* is flow-bound — the fall-through rule covers it); `workstream` waits on the workforce layer (`fsdev workstream` per the project doc).
- **Per-target input templates** (mapping free text into non-`{message}` schemas). Revisit with real demand; the failure mode is a clean rendered error.
- **Flow instance-id addressing** (e.g. `/use <flow>@<id>`). The registry admits multiple instances per kind, but every CLI surface today resolves by kind to the default instance (`registry.get(kind)`, `run.ts:337`) — chat matches that reachability, and `listTargets` enumerates one target per kind so `/targets` never advertises unselectable duplicates (§4.3). Revisit when any CLI surface gains instance addressing.
- **Config-declared default target** (e.g. `chat: { default: … }` in `createFlowState`). Startup positionals + auto-bind cover v1; adding config surface is a one-way door left closed (raised in Open Questions).
- **Autocomplete/hinting** for `/` commands (FIX-417's UX, terminal edition) — needs Ink; Phase 2.
- **Persona tunings** (dev agent, operator, cron/self-settings — FIX-18, FIX-440): flow-level work, explicitly out of scope per the issue.
- **Broad runtime-resolution consolidation.** The ~30-line identical *prelude* is extracted and shared in this change (§4.1, sequence step 2 — rule-of-three, per spec review). Going further — unifying store backends, `--model` handling, and dispose ownership across `run`/`dev`/`chat` — is deliberately out: those genuinely diverge per command, and a helper absorbing them would be a shallow module with a conditional per divergence (BP-024). Revisit via `fsd:improve-codebase-architecture` only if a fourth command changes the calculus.
