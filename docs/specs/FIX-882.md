# FIX-882: Knowledge Hub — `logActivity` capture + inbox staging with fast initial triage — Implementation Spec

> **Linear issue:** [FIX-882](https://linear.app/fixpoint-labs/issue/FIX-882/knowledge-hub-typed-ingestion-verbs-working-memory-staging-with-fast)
> **Project:** Knowledge Hub Lab · **Blocked by:** FIX-881 (Done) · **Blocks:** FIX-883 (cron sweeper)

## 1. TLDR

**Plain-language summary.** This gives the owner a single, natural way to hand off whatever's on their mind — a thought, a task, a memory, a goal, a decision — from any conversation with Claude. Each capture lands in an inbox right away, stamped with when it was said and the situation it came up in, and gets a quick automatic once-over (is this an exact repeat? does it look like something already in the inbox?) without any slow or costly processing at capture time. A later, separate process (the sweeper, FIX-883) reviews the inbox in batches and files things into long-term memory. The system acts as a second brain: it tracks the owner's mental activity, not just isolated notes.

**Technical statement.** Add a `logActivity` MCP tool and an `inbox` user-scoped resource collection to `labs/knowledge-hub`, with a deterministic (non-LLM) "mailroom" pass at capture time (normalization, wall-clock stamping, sha256 idempotency, token-overlap duplicate flagging) and a `listInbox` read-back action for inspection.

**Deliverables:**

- Add `inbox` resource collection (`inbox/**`, `scope: "user"`, `flowIsolation: false`) with kind-tagged record schema in `labs/knowledge-hub/src/inbox.ts`
- Add pure mailroom helpers (normalize, fingerprint, duplicate-overlap scan) in `labs/knowledge-hub/src/mailroom.ts`
- Add `logActivity` and `listInbox` typed handler actions in `labs/knowledge-hub/src/flow.ts`, replacing the scaffold `ping`; flow becomes `requireUser: true`, `mcp: { enabled: true }`
- Wire `createMcpTransportAdapter()` + optional bearer-secret principal resolver (`KH_MCP_SECRET`) in `labs/knowledge-hub/fsdev.config.ts`
- Tests: per-behaviour `testFlow` specs, pure mailroom unit specs, user-scope isolation spec (modeled on `examples/knowledge-base/test/user-scope.spec.ts`)
- Docs: extend `labs/knowledge-hub/README.md` and the `labs/README.md` index line; internal-only changeset

**Size estimate:** Medium — multi-file, 1 PR, ~300–450 LOC, all inside `labs/knowledge-hub`.

## 2. Overview

FIX-882 is the front door of the Knowledge Hub lab: today knowledge can only enter the corpus as a whole OKF bundle import or a direct `create_concept` write into the long-term graph — capture and durable placement are the same moment, and there is no notion of "arrived but not yet organized." This spec adds that missing stage: a single capture verb that any MCP client (primarily Claude mid-conversation) can call, an inbox where captures accumulate with enough metadata for the FIX-883 sweeper to batch-review, and a fast, deterministic triage pass at capture time. Owner direction during spec research (recorded here because it shapes the whole surface): the capture verb is **`logActivity`** — the domain being logged is *mental activity* ("something was decided or came to mind"; the system is a second brain) — and every capture must record not just the content but the **context** in which it arose. The staging area is named the **inbox** (owner direction), which also avoids colliding with the framework's session-scoped "working memory" tier. The capture-time triage pass is the **mailroom** (owner direction, replacing the issue's "receptionist" candidate): a receptionist implies front-desk interaction with the caller, which this pass by design never does — it stamps, sorts, and flags behind the scenes, and it composes with FIX-883's cast (manager, librarian).

## 3. Background & Research

### Codebase findings

- **`labs/knowledge-hub` scaffold (FIX-881, merged as PR #720)** is deliberately empty: one `ping` echo handler, `requireUser: false`, no MCP adapter, no resources, filesystem `dev` profile with a throwing `modelResolver` (`labs/knowledge-hub/src/flow.ts`, `fsdev.config.ts`). Its README states FIX-882 replaces `ping` with the capture surface.
- **`examples/knowledge-base` is the sole in-repo precedent for MCP tools on a flow**: `handler` blocks with `.describe()`d zod schemas, `defineFlow({ mcp: { enabled: true }, authentication: { requireUser: true, resolvePrincipal: createBearerSecretPrincipalResolver(...) }, actions, resources })`, per-action MCP `description` (required by the adapter), per-action `mcp: { enabled: false }` opt-out, `createMcpTransportAdapter()` in `fsdev.config.ts`, and a fail-closed prod secret guard (`examples/knowledge-base/src/flow.ts:63-207`, `fsdev.config.ts:46-53`).
- **`labs/trading-desk` is the record-store and typed-handler precedent**: `thesesCollection = defineResourceCollection({ pattern: "theses/*", scope: "user", flowIsolation: false, stateSchema })` with bare-key helpers (framework auto-prepends the pattern prefix), and handlers declaring `resources: { theses: thesesCollection }` for a **typed** `ctx` (`labs/trading-desk/src/flows/portfolio/portfolio-resources.ts:125-166`, `thesis-actions.ts:37-61`). This typed form is newer than knowledge-base's `ctx: any` + capability indirection and is what FIX-882 copies.
- **`@flow-state-dev/memory` is NOT a fit for the inbox** and this is a deliberate rejection, not an oversight: its working-memory tier is `scope: 'session'` (invisible to a cron sweeper in another process; lost across stateless MCP calls), retention is salience-decay + capacity-7 eviction over a *turn counter* (pending items must never silently drop, and age must be wall-clock), and its capture path is an LLM generator (`packages/memory/src/working-memory.ts:53-58`, `working-memory-blocks.ts:26-80`). No lab or example imports the package today.
- **Cheap dedup primitives already exist in core**: `tokenize`, `tokenOverlap`, `findBestOverlap`, `shortId` in `packages/core/src/helpers/text-match.ts` (hoisted out of the memory package by FIX-836 as the blessed shared home). Exact-idempotency hashing has a precedent in trading-desk's `computeFingerprint` (sha256 over normalized load-bearing fields, `labs/trading-desk/src/db/repository.ts:445-469`). These are two different jobs — exact idempotency vs. fuzzy "roughly the same" — and both are used, per-purpose, not averaged.
- **FIX-858 landed a revised resource-surface contract on main** (scoped `searchResources` pagination, limit contract, multi-collection cursor, external collections). The inbox is a plain internal collection, but any search exposure must target the current contract.

### Industry research

The two-phase split this issue proposes (cheap synchronous capture → batched asynchronous consolidation) is the unanimous pattern across serious agent-memory systems:

- **Letta/MemGPT** moves all memory reorganization to an async "sleep-time" agent; the primary agent deliberately lacks memory-editing tools ([Letta: Sleep-time Compute](https://www.letta.com/blog/sleep-time-compute/)).
- **LangMem/LangGraph** names the tradeoff directly: "hot path" (synchronous, adds latency) vs. "background" memory formation; background is the default for anything expensive ([LangMem hot-path quickstart](https://langchain-ai.github.io/langmem/hot_path_quickstart/)).
- **Mem0** runs cheap capture, then async LLM consolidation (ADD/UPDATE/DELETE/NOOP against top-k similar memories); dedup runs at consolidation, not capture. Stored records carry id, content hash, timestamps, user id, metadata — a good checklist for the inbox schema ([Mem0: Add Memory](https://docs.mem0.ai/core-concepts/memory-operations/add)).
- **GTD / Zettelkasten / PARA** independently validate capture ≠ placement: capture must be near-zero friction; clarify/organize are later steps; fleeting notes should be processed within ~24–72h before converting context fades — an input for FIX-883's cadence, and the source of the "inbox" vocabulary ([GTD inbox capture](https://super-productivity.com/blog/gtd-inbox-capture-system/), [zettelkasten.de on Ahrens](https://zettelkasten.de/posts/concepts-sohnke-ahrens-explained/)).
- **Tool-surface shape**: Anthropic's tool-design guidance says to consolidate related operations behind enum parameters rather than multiplying tools; MCP telemetry shows tool-selection accuracy degrading past ~10–15 tools, and `logThought` vs. `logMemory` for a stray remark is exactly the "ambiguous decision point" to avoid — a wrong `kind` guess is cheap because the sweeper re-classifies anyway ([Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents), [MCP tool-count telemetry](https://medium.com/@meshuggah22/91-at-10-tools-87-at-15-the-five-architecture-patterns-behind-reliable-mcp-servers-11fef1bbe401)).
- **Dedup at personal scale (hundreds–low thousands of items)**: brute-force normalized-hash + token-overlap scans are sub-millisecond; MinHash/SimHash solve a scale problem this system doesn't have and are noisy on one-line captures; embedding similarity catches paraphrases but has known false positives (negation, near-miss entities), so duplicate detection must **flag, never block** ([nelhage: fuzzy dedup](https://blog.nelhage.com/post/fuzzy-dedup/), [semantic dedup thresholds](https://www.cleansmartlabs.com/blog/semantic-duplicate-detection-a-gentle-intro-to-embeddings)).
- **Known pitfalls**: inbox bankruptcy (capture without processing — mitigated by FIX-883's cadence and by making backlog size/age visible now); over-triage at capture (keep the mailroom to stamps and flags, never interrogate the caller); losing raw input (always preserve verbatim text so re-classification can't destroy information).

### Why this approach

The chosen shape is "rules-only mailroom, all intelligence in the sweeper" (the MemGPT/GTD-orthodox pattern), with exact-hash idempotency plus advisory token-overlap flags. A single cheap embedding call at capture (the hybrid pattern) was considered and deferred: it adds a network dependency and latency to the capture hot path for paraphrase detection the sweeper will redo with full context anyway, and the lab currently has zero model/provider dependencies (`neverResolvesAModel`) — keeping capture fully deterministic preserves that. A small-LLM mailroom was rejected outright: it is the pattern the industry moved away from, and the caller here *is already an LLM* that chose the `kind` — paying for classification twice.

### Key Decisions & Ramifications (top 5)

1. **One `logActivity` tool with a `kind` enum, not a verb family** (owner-directed; independently backed by Anthropic tool-design guidance and MCP tool-count telemetry). *Rejected alternative:* `logThought`/`logJournalFragment`/`logTask`/`logMemory`/`logGoal` as separate MCP tools (the issue's candidate direction). *Ramification:* spends one slot of the hub's tool budget (leaving room for FIX-883/884 tools) and moves kind ambiguity into a cheap enum guess; locks all kinds to one input schema — if kinds later need genuinely divergent required fields (e.g. `task.dueDate`), that's the trigger to split, and splitting later is additive, not breaking.
2. **`context` is a required input field** (owner-directed): every capture records the situation in which the mental activity arose, not just the content. *Rejected alternative:* optional context. *Ramification:* the calling LLM (which is the only party that has the conversational context) is contractually the context source — the tool description must instruct it to summarize the situation; risk is terse/low-effort context strings, mitigated by description guidance, not validation (capture must never interrogate the caller).
3. **The inbox is a new lab-local, user-scoped resource collection — not `@flow-state-dev/memory`.** *Rejected alternative:* reuse the framework working-memory tier. *Ramification:* the memory package's session scope, decay/eviction, and LLM capture path are each disqualifying for a durable sweep-later inbox; naming the collection "inbox" (owner-directed) removes the "working memory" term collision entirely. The memory package remains the right tool later for in-agent recall, and the inbox schema deliberately includes a `status` field so FIX-883 can transition records without a schema migration (BP-030).
4. **The mailroom is deterministic and non-LLM: sha256 fingerprint idempotency + token-overlap advisory duplicate flags, no embedding in v1.** *Rejected alternatives:* small-LLM triage at capture (industry anti-pattern, double-pays for classification); one cheap embedding call (better paraphrase recall, but adds a provider dependency and latency to the hot path for work the sweeper redoes). *Ramification:* capture is ~0ms/$0/offline; paraphrase duplicates slip through to the sweeper — acceptable because duplicate flags are advisory everywhere and FIX-883 does semantic work batched. Embedding-at-capture is a documented upgrade path (Non-Goals).
5. **Copy `examples/knowledge-base`'s MCP/auth/config shape with `labs/trading-desk`'s typed-handler form; no capability layer.** *Rejected alternative:* mirror knowledge-base's `createKnowledgeBaseCapability` indirection. *Ramification:* handlers declare `resources: { inbox }` directly (typed ctx, FIX-435 form) — less surface, but if a second consumer of inbox logic appears (plausibly FIX-883's sweeper flow), that's the trigger to hoist helpers into a capability; OKF extraction stays deferred to FIX-883 per PR #720's recorded decision, since FIX-882 never touches the concept graph.

### Inbox collection (`src/inbox.ts`)

```ts
import { z } from "zod";
import { defineResourceCollection, getPatternPrefix, shortId } from "@flow-state-dev/core";

/** What sort of mental activity was captured. Caller-supplied hint; the
 * FIX-883 sweeper re-classifies, so a wrong guess is cheap. */
export const activityKindSchema = z.enum([
  "thought",   // something came to mind
  "journal",   // a journal fragment / diary-style entry
  "task",      // something to do
  "memory",    // something to remember (happened in the past)
  "goal",      // an aspiration / outcome to work toward
  "decision",  // something was decided
]);
export type ActivityKind = z.infer<typeof activityKindSchema>;

export const inboxRecordSchema = z.object({
  kind: activityKindSchema,
  /** Verbatim capture — never mutated, so sweeper re-classification cannot
   * destroy information. */
  content: z.string(),
  /** Required: the situation in which the activity arose (what conversation,
   * task, or trigger). The calling LLM is the context source. */
  context: z.string(),
  /** Server-stamped ISO wall-clock capture time (mailroom). */
  capturedAt: z.string(),
  /** Caller-supplied time the activity refers to (e.g. a memory of last
   * Tuesday), if different from capture time. */
  occurredAt: z.string().nullable().default(null),
  /** Free-form origin hint (client name, conversation title). */
  source: z.string().nullable().default(null),
  /** Sweep lifecycle. FIX-882 only ever writes "pending"; "swept" is
   * declared now so FIX-883 needs no schema migration (BP-030). */
  status: z.enum(["pending", "swept"]).default("pending"),
  /** sha256 over normalize(kind + content) — exact idempotency key. */
  fingerprint: z.string(),
  /** Advisory near-duplicate flags (inbox record ids). Never blocks capture. */
  possibleDuplicateOf: z.array(z.string()).default([]),
});
export type InboxRecord = z.infer<typeof inboxRecordSchema>;

/** User-scoped so captures survive stateless MCP calls and are visible to the
 * FIX-883 cron sweeper in another process (same rationale as the knowledge-base
 * concept corpus). flowIsolation: false per BP-027. No eviction: pending items
 * must never silently drop. */
export const inboxCollection = defineResourceCollection({
  pattern: "inbox/**",
  scope: "user",
  flowIsolation: false,
  stateSchema: inboxRecordSchema,
  llmReadable: true,
  llmWritable: false, // writes go through logActivity, not generic resource tools
});

export const INBOX_PREFIX = getPatternPrefix(inboxCollection.pattern);

/** Bare key (framework auto-prepends the pattern prefix): `<kind>/<ISO-compact>-<shortId>`.
 * Kind-first so list("<kind>/") filters at the source (BP-033); timestamp next
 * so listings sort chronologically within a kind. */
export function inboxKey(kind: ActivityKind, capturedAt: string): string {
  return `${kind}/${capturedAt.replace(/[:.]/g, "")}-${shortId()}`;
}

/** Strip the injected `inbox/` prefix from a stored path to recover the id
 * (mirrors conceptIdFromPath in examples/knowledge-base/src/concepts.ts). */
export function inboxIdFromPath(path: string): string { /* ... */ }
```

Notes:
- Exact zod shapes follow BP-016/BP-023 conventions already used in `examples/knowledge-base/src/concepts.ts:27-37` (no `z.record`; nullable fields `.nullable().default(null)`).
- `llmWritable: false` keeps the generic resource write tools from bypassing the mailroom; `llmReadable: true` lets existing nav/search read the inbox for free. There are no generators in this flow today, so these flags only matter if/when a generator gets `uses` access — set them deliberately now (BP-021 spirit).
- The record `id` used in outputs and `possibleDuplicateOf` is the bare key (prefix-stripped), consistent with knowledge-base's id convention.

### Mailroom helpers (`src/mailroom.ts`)

Pure functions, no ctx, no I/O — the handler owns all store access (keeps these trivially unit-testable):

```ts
import { createHash } from "node:crypto";
import { tokenOverlap } from "@flow-state-dev/core";

/** Lowercase, collapse whitespace, strip leading/trailing space. */
export function normalizeContent(text: string): string;

/** sha256 hex over `${kind}\n${normalizeContent(content)}` — exact-resubmit
 * identity (same recipe philosophy as trading-desk computeFingerprint). */
export function computeFingerprint(kind: string, content: string): string;

/** Advisory near-duplicate scan: token-overlap (packages/core text-match)
 * of the new content against pending records, threshold 0.6 (the
 * findBestOverlap default). Returns matching record ids, capped at 3. */
export function findNearDuplicates(
  content: string,
  pending: Array<{ id: string; content: string }>,
): string[];
```

`kind` is part of the fingerprint deliberately: the same sentence captured as a `task` and as a `memory` is two different mental events, not a duplicate. The fuzzy scan intentionally ignores `kind` (a near-duplicate across kinds is exactly what the sweeper should see flagged).

### Idempotency & dedup semantics

- **Exact resubmit** (same `kind` + normalized `content`, an existing **pending** record): no new record; return the existing record's id with `deduplicated: true`. This makes MCP client retries safe (trading-desk's idempotent-ingest philosophy). Swept records don't participate — re-capturing something previously swept is a new mental event.
- **Near duplicate** (token overlap ≥ 0.6 against pending): record IS created, with `possibleDuplicateOf` set. Advisory only — the sweeper (or owner) decides about merging. Never block or drop on similarity (industry false-positive guidance).
- **Race window**: two concurrent identical captures can both pass the scan and create two records with equal fingerprints. Accepted: dedup here is advisory convenience, the sweeper merges; no locking added (BP-038).
- The pending scan is `list()` + in-memory compare. This is a documented BP-033 tension: the collection API offers only `list(prefix?)`, and the inbox is swept wholesale at personal scale (hundreds of items), so load-then-scan is proportionate. Kind lives first in the key so `listInbox(kind)` narrows at the source.

### Error handling

Namespaced plain `Error` throws surface through the MCP adapter (knowledge-base precedent, `capability.ts:117`):

| Case | Behavior |
| --- | --- |
| Missing/empty `content` or `context`, unknown `kind`, invalid `occurredAt`, over-length input | zod schema rejection → MCP tool error (message names the field) |
| Store write failure | Error propagates; no partial record (single `create` call, no multi-step rollback needed) |
| Unauthenticated/wrong-key MCP request when `KH_MCP_SECRET` set | Rejected by the bearer resolver (FIX-23 machinery), never served |
| `listInbox` on empty inbox | Normal result: `items: [], totalPending: 0, oldestPendingCapturedAt: null` — absence is data, not an error |

## 6. Edge Cases & Error Handling

| # | Edge case | Expected behavior |
| --- | --- | --- |
| 1 | Exact resubmit (same kind + normalized content, pending record exists) | No new record; `{ id: existing, deduplicated: true }` |
| 2 | Same content, different `kind` | New record (fingerprint includes kind); fuzzy flag may still point at the other record |
| 3 | Near-duplicate (overlap ≥ 0.6) | Record created; `possibleDuplicateOf: [ids]` (≤ 3) |
| 4 | Same content as a **swept** record | New record, not deduplicated (only pending participates) |
| 5 | Missing `context` | Schema rejection — capture contract requires it |
| 6 | Whitespace-only `content` | Rejected (`min(1)` after mailroom trim semantics — validate on raw, normalize for fingerprint) |
| 7 | `content`/`context` > 20k chars | Schema rejection with clear message (guard against runaway captures) |
| 8 | Invalid `occurredAt` | Schema rejection; `occurredAt` never defaults to `capturedAt` (absence means "refers to now") |
| 9 | Concurrent identical captures | Both may land (race accepted); sweeper merges; documented above |
| 10 | Large pending backlog (1000s) | O(n) overlap scan still sub-ms at this scale; `listInbox` caps at `limit` but `totalPending` reports the real count |
| 11 | Unknown `kind` value | Enum rejection (adding kinds later = additive enum change, schema-versioned by BP-030 dual-read if ever removed) |
| 12 | MCP call with wrong/missing bearer token (secret set) | Rejected by principal resolver; nothing written |

Error taxonomy: all capture-path errors are **caller errors (non-retryable as-is)** except store write failure (retryable — and safe to retry thanks to fingerprint idempotency). Nothing in this surface has a partial-success state.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (Feature) — red-green-refactor with tracer bullets; each behaviour below is one cycle.

**Goal & goal check.** Goal (observable outcome): *an MCP client can hand off a piece of mental activity mid-conversation and it lands durably in the owner's inbox, typed, dated, context-tagged, and visible to inspection — without any model call at capture time.* **No real-LLM goal check applies**: the flow contains zero generators (`neverResolvesAModel` stands), so there is no model in the loop for a `goals/` run to exercise — mirroring the FIX-885 precedent. The real-path evidence is instead:

- **Evidence path (BP-003):** from `labs/knowledge-hub/`:
  `pnpm fsdev run knowledge-hub logActivity -i '{"kind":"task","content":"Book dentist appointment","context":"Mentioned while planning the week in a Claude conversation"}'`
  then `pnpm fsdev run knowledge-hub listInbox -i '{}'`.
  **Pass criteria:** first command returns `{ id, capturedAt, deduplicated: false }`; second shows the item with `status: "pending"`, correct kind/content/context, `totalPending: 1`; re-running the first command returns the same id with `deduplicated: true` and `totalPending` stays 1. (Read-back action pattern per AGENTS "when the result lives in a resource, not the stream".)
- The full end-to-end MCP-client goal (Claude calling `log_activity` over the network against a hosted endpoint) becomes meaningful once FIX-883 hosts the flow durably; noted in Non-Goals.

**Behaviours to test (tracer bullets, via `testFlow`):**

1. `logActivity` creates a pending inbox record carrying kind, verbatim content, context, server-stamped `capturedAt`, fingerprint.
2. Missing `context` → rejected; error names the field.
3. Exact resubmit → `deduplicated: true`, same id, record count unchanged.
4. Near-duplicate → new record with `possibleDuplicateOf` populated; original untouched.
5. Same content different kind → two records, no exact dedup.
6. `listInbox` → newest-first items, `totalPending`, `oldestPendingCapturedAt`; `kind` filter narrows via key prefix; `limit` respected while `totalPending` reports full count.
7. User isolation: userA's captures invisible to userB; same user shares across separate `testFlow` calls over shared stores (copy `examples/knowledge-base/test/user-scope.spec.ts`).
8. Mailroom pure-function specs (normalize/fingerprint/overlap) in `test/mailroom.spec.ts`.

**Test templates:** `examples/knowledge-base/test/capability.spec.ts` (CRUD + error cases over a real in-memory collection), `test/user-scope.spec.ts` (BP-027), `test/helpers.ts` (`makeConceptCollection` harness shape), `labs/knowledge-hub/test/flow.spec.ts` (`testFlow` idiom). Node env, no model mocking needed (no generators).

- **`@flow-state-dev/memory` integration** — deliberately rejected for the inbox (see Key Decision 3); remains available for future in-agent recall inside hub generators.

## 11. Open Questions

1. **Kind enum membership.** The spec includes `decision` (from the owner's "something was decided" framing) alongside the issue's minimum five (`thought`, `journal`, `task`, `memory`, `goal`). Adding later is additive/cheap; removing later is a BP-030 event. Confirm the v1 list.

3. **Fuzzy-dedup threshold.** 0.6 token overlap (the core `findBestOverlap` default) is a starting point, not tuned. Recommendation: ship at 0.6, revisit with real capture data during FIX-883 — not worth a prototype now since flags are advisory.
