# FIX-882: Knowledge Hub — `logActivity` capture + inbox staging with fast initial triage — Implementation Spec

> **Linear issue:** [FIX-882](https://linear.app/fixpoint-labs/issue/FIX-882/knowledge-hub-typed-ingestion-verbs-working-memory-staging-with-fast)
> **Project:** Knowledge Hub Lab · **Blocked by:** FIX-881 (Done) · **Blocks:** FIX-883 (cron sweeper)

## 1. TLDR

**Plain-language summary.** This gives the owner a single, natural way to hand off whatever's on their mind — a thought, a task, a memory, a goal, a decision — from any conversation with Claude. Each capture lands in an inbox right away, stamped with when it was said and the situation it came up in, and an accidental double-submit of the same capture is recognized rather than filed twice — all without any slow or costly processing at capture time. A later, separate process (the sweeper, FIX-883) reviews the inbox in batches and files things into long-term memory. The system acts as a second brain: it tracks the owner's mental activity, not just isolated notes.

**Technical statement.** Add a `logActivity` MCP tool and an `inbox` user-scoped resource collection to `labs/knowledge-hub`, with a deterministic (non-LLM) "mailroom" pass at capture time (normalization, wall-clock stamping, sha256 fingerprint idempotency for safe retries) and a `listInbox` read-back action for inspection.

**Deliverables:**

- Add `inbox` resource collection (`inbox/**`, `scope: "user"`, `flowIsolation: false`) with kind-tagged record schema and fingerprint-derived keys in `labs/knowledge-hub/src/inbox.ts`
- Add pure mailroom helpers (normalize, fingerprint over the full capture tuple) in `labs/knowledge-hub/src/mailroom.ts`
- Add `logActivity` and `listInbox` typed handler actions in `labs/knowledge-hub/src/flow.ts` (with an always-defined fail-closed resolver in the flow's `authentication`: bearer-secret when `KH_MCP_SECRET` is set, throwing otherwise), replacing the scaffold `ping`; flow becomes `requireUser: true`, `mcp: { enabled: true }`
- Wire `createMcpTransportAdapter()` in `labs/knowledge-hub/fsdev.config.ts` (mounted only when `KH_MCP_SECRET` is set — fail closed) and add the `@flow-state-dev/mcp` workspace dependency to `labs/knowledge-hub/package.json`
- Tests: per-behaviour `testFlow` specs, pure mailroom unit specs, user-scope isolation spec (modeled on `examples/knowledge-base/test/user-scope.spec.ts`)
- Docs: extend `labs/knowledge-hub/README.md` and the `labs/README.md` index line; internal-only changeset

**Size estimate:** Medium — multi-file, 1 PR, ~250–400 LOC, all inside `labs/knowledge-hub`.

## 2. Overview

FIX-882 is the front door of the Knowledge Hub lab: today knowledge can only enter the corpus as a whole OKF bundle import or a direct `create_concept` write into the long-term graph — capture and durable placement are the same moment, and there is no notion of "arrived but not yet organized." This spec adds that missing stage: a single capture verb that any MCP client (primarily Claude mid-conversation) can call, an inbox where captures accumulate with enough metadata for the FIX-883 sweeper to batch-review, and a fast, deterministic triage pass at capture time. Owner direction during spec research (recorded here because it shapes the whole surface): the capture verb is **`logActivity`** — the domain being logged is *mental activity* ("something was decided or came to mind"; the system is a second brain) — and every capture must record not just the content but the **context** in which it arose. The staging area is named the **inbox** (owner direction), which also avoids colliding with the framework's session-scoped "working memory" tier. The capture-time triage pass is the **mailroom** (owner direction, replacing the issue's "receptionist" candidate): a receptionist implies front-desk interaction with the caller, which this pass by design never does — it stamps, sorts, and flags behind the scenes, and it composes with FIX-883's cast (manager, librarian).

- **`labs/trading-desk` is the record-store and typed-handler precedent**: `thesesCollection = defineResourceCollection({ pattern: "theses/*", scope: "user", flowIsolation: false, stateSchema })` with bare-key helpers (framework auto-prepends the pattern prefix), and handlers declaring `resources: { theses: thesesCollection }` for a **typed** `ctx` (`labs/trading-desk/src/flows/portfolio/portfolio-resources.ts:125-166`, `thesis-actions.ts:37-61`). This typed form is newer than knowledge-base's `ctx: any` + capability indirection and is what FIX-882 copies.
- **`@flow-state-dev/memory` is NOT a fit for the inbox** and this is a deliberate rejection, not an oversight: its working-memory tier is `scope: 'session'` (invisible to a cron sweeper in another process; lost across stateless MCP calls), retention is salience-decay + capacity-7 eviction over a *turn counter* (pending items must never silently drop, and age must be wall-clock), and its capture path is an LLM generator (`packages/memory/src/working-memory.ts:53-58`, `working-memory-blocks.ts:26-80`). No lab or example imports the package today.
- **Idempotency-hash precedent**: trading-desk's `computeFingerprint` (sha256 over normalized load-bearing fields, `labs/trading-desk/src/db/repository.ts:453-469`) with its "one idempotent ingestion contract" philosophy. Core also ships fuzzy text-match helpers (`packages/core/src/helpers/text-match.ts`, exported via `@flow-state-dev/core/helpers`) — available to FIX-883, deliberately unused here (see Key Decision 4).
- **FIX-858 landed a revised resource-surface contract on main** (scoped `searchResources` pagination, limit contract, multi-collection cursor, external collections). The inbox is a plain internal collection, but any search exposure must target the current contract.

### Industry research

The two-phase split this issue proposes (cheap synchronous capture → batched asynchronous consolidation) is the unanimous pattern across serious agent-memory systems:

- **Letta/MemGPT** moves all memory reorganization to an async "sleep-time" agent; the primary agent deliberately lacks memory-editing tools ([Letta: Sleep-time Compute](https://www.letta.com/blog/sleep-time-compute/)).
- **LangMem/LangGraph** names the tradeoff directly: "hot path" (synchronous, adds latency) vs. "background" memory formation; background is the default for anything expensive ([LangMem hot-path quickstart](https://langchain-ai.github.io/langmem/hot_path_quickstart/)).
- **Mem0** runs cheap capture, then async LLM consolidation (ADD/UPDATE/DELETE/NOOP against top-k similar memories); **dedup runs at consolidation, not capture**. Stored records carry id, content hash, timestamps, user id, metadata — a good checklist for the inbox schema ([Mem0: Add Memory](https://docs.mem0.ai/core-concepts/memory-operations/add)).
- **GTD / Zettelkasten / PARA** independently validate capture ≠ placement: capture must be near-zero friction; clarify/organize are later steps; fleeting notes should be processed within ~24–72h before converting context fades — an input for FIX-883's cadence, and the source of the "inbox" vocabulary ([GTD inbox capture](https://super-productivity.com/blog/gtd-inbox-capture-system/), [zettelkasten.de on Ahrens](https://zettelkasten.de/posts/concepts-sohnke-ahrens-explained/)).
- **Tool-surface shape**: Anthropic's tool-design guidance says to consolidate related operations behind enum parameters rather than multiplying tools; MCP telemetry shows tool-selection accuracy degrading past ~10–15 tools, and `logThought` vs. `logMemory` for a stray remark is exactly the "ambiguous decision point" to avoid — a wrong `kind` guess is cheap because the sweeper re-classifies anyway ([Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents), [MCP tool-count telemetry](https://medium.com/@meshuggah22/91-at-10-tools-87-at-15-the-five-architecture-patterns-behind-reliable-mcp-servers-11fef1bbe401)).
- **Similarity dedup findings (inform FIX-883, not v1 capture)**: at personal scale, brute-force normalized-hash + token-overlap scans are sub-millisecond; MinHash/SimHash solve a scale problem this system doesn't have; embedding similarity catches paraphrases but has known false positives (negation, near-miss entities), so similarity-based duplicate handling must **flag, never block/drop** ([nelhage: fuzzy dedup](https://blog.nelhage.com/post/fuzzy-dedup/), [semantic dedup thresholds](https://www.cleansmartlabs.com/blog/semantic-duplicate-detection-a-gentle-intro-to-embeddings)).
- **Known pitfalls**: inbox bankruptcy (capture without processing — mitigated by FIX-883's cadence and by making backlog size/age visible now); over-triage at capture (keep the mailroom to stamps and idempotency, never interrogate the caller); losing raw input (always preserve verbatim text so re-classification can't destroy information).

### Why this approach

The chosen shape keeps capture strictly mechanical: normalization, stamping, and an exact-fingerprint idempotency check — **no similarity detection of any kind at capture time**. A small-LLM mailroom was rejected outright (the pattern the industry moved away from, and the caller is already an LLM that chose the `kind` — paying for classification twice). A single cheap embedding call was rejected for adding a provider/network dependency to the hot path for paraphrase work the sweeper redoes with batch context. An earlier draft kept a free token-overlap advisory flag at capture; spec review (second-look pass on PR #726) correctly flagged that as contradicting the same principle — Mem0's validated pattern puts *all* near-duplicate detection at consolidation, and BP-028 says to fix it at the layer that owns it. All similarity work is therefore FIX-883's. What remains at capture is exact-fingerprint idempotency, which is a genuinely different need: making MCP transport retries safe, not judging "roughly the same."

### Key Decisions & Ramifications (top 5)

1. **One `logActivity` tool with a `kind` enum, not a verb family** (owner-directed; independently backed by Anthropic tool-design guidance and MCP tool-count telemetry). *Rejected alternative:* `logThought`/`logJournalFragment`/`logTask`/`logMemory`/`logGoal` as separate MCP tools (the issue's candidate direction). *Ramification:* spends one slot of the hub's tool budget (leaving room for FIX-883/884 tools) and moves kind ambiguity into a cheap enum guess; locks all kinds to one input schema — if kinds later need genuinely divergent required fields (e.g. `task.dueDate`), that's the trigger to split, and splitting later is additive, not breaking.
2. **`context` is a required input field** (owner-directed): every capture records the situation in which the mental activity arose, not just the content. *Rejected alternative:* optional context. *Ramification:* the calling LLM (which is the only party that has the conversational context) is contractually the context source — the tool description must instruct it to summarize the situation; risk is terse/low-effort context strings, mitigated by description guidance, not validation (capture must never interrogate the caller). Context is also part of the idempotency fingerprint (Decision 4), so a re-capture with new context is never silently swallowed.
3. **The inbox is a new lab-local, user-scoped resource collection — not `@flow-state-dev/memory`.** *Rejected alternative:* reuse the framework working-memory tier. *Ramification:* the memory package's session scope, decay/eviction, and LLM capture path are each disqualifying for a durable sweep-later inbox; naming the collection "inbox" (owner-directed) removes the "working memory" term collision entirely. The memory package remains the right tool later for in-agent recall, and the inbox schema deliberately includes a `status` field so FIX-883 can transition records without a schema migration (BP-030).
4. **The mailroom is deterministic and minimal: normalize, stamp, and sha256-fingerprint the full capture tuple (kind, content, context, occurredAt, source) — no similarity detection at capture; records are keyed by the fingerprint.** *Rejected alternatives:* small-LLM triage at capture (industry anti-pattern, double-pays for classification); one cheap embedding call (provider dependency on the hot path); the draft's own token-overlap advisory flags (dropped in spec-PR review — Mem0 puts all near-dup detection at consolidation, the sweeper redoes it with batch context, BP-028). *Ramification:* capture is a pure hash + point lookup (`getOptional` on the derived key — no O(n) collection scan, resolving the draft's self-flagged BP-033 tension); the fingerprint covers the full tuple, so it is strictly a transport-retry key — the same sentence captured with different context is a new record by design, and paraphrase/cross-context duplicates reach the sweeper unflagged, also by design. If capture-time advisory flags ever prove needed, that's a FIX-883-informed follow-up, not a v1 default.
5. **Copy `examples/knowledge-base`'s MCP/auth/config shape with `labs/trading-desk`'s typed-handler form; no capability layer.** *Rejected alternative:* mirror knowledge-base's `createKnowledgeBaseCapability` indirection. *Ramification:* handlers declare `resources: { inbox }` directly (typed ctx, FIX-435 form) — less surface, but if a second consumer of inbox logic appears (plausibly FIX-883's sweeper flow), that's the trigger to hoist helpers into a capability; OKF extraction stays deferred to FIX-883 per PR #720's recorded decision, since FIX-882 never touches the concept graph.

### Inbox collection (`src/inbox.ts`)

```ts
import { z } from "zod";
import { defineResourceCollection } from "@flow-state-dev/core";
import { getPatternPrefix } from "@flow-state-dev/core/types";

/** What sort of mental activity was captured. Caller-supplied hint; the
 * FIX-883 sweeper re-classifies, so a wrong guess is cheap. */
export const activityKindSchema = z.enum([
  "thought",   // something came to mind
  "journal",   // a journal fragment / diary-style entry
  "task",      // something to do
  "memory",    // something to remember (happened in the past)
  "goal",      // an aspiration / outcome to work toward
  "decision",  // something was decided
]);
export type ActivityKind = z.infer<typeof activityKindSchema>;

export const inboxRecordSchema = z.object({
  kind: activityKindSchema,
  /** Verbatim capture — never mutated, so sweeper re-classification cannot
   * destroy information. Normalization exists only inside the fingerprint. */
  content: z.string(),
  /** Required: the situation in which the activity arose (what conversation,
   * task, or trigger). The calling LLM is the context source. */
  context: z.string(),
  /** Server-stamped ISO wall-clock capture time (mailroom). */
  capturedAt: z.string(),
  /** Caller-supplied time the activity refers to (e.g. a memory of last
   * Tuesday), if different from capture time. */
  occurredAt: z.string().nullable().default(null),
  /** Free-form origin hint (client name, conversation title). */
  source: z.string().nullable().default(null),
  /** Sweep lifecycle. FIX-882 only ever writes "pending"; "swept" is
   * declared now so FIX-883 needs no schema migration (BP-030). */
  status: z.enum(["pending", "swept"]).default("pending"),
  /** sha256 over the normalized capture tuple (kind, content, context,
   * occurredAt, source) — transport-retry identity; also the key suffix. */
  fingerprint: z.string(),
});
export type InboxRecord = z.infer<typeof inboxRecordSchema>;

/** User-scoped so captures survive stateless MCP calls and are visible to the
 * FIX-883 cron sweeper in another process (same rationale as the knowledge-base
 * concept corpus). flowIsolation: false per BP-027. No eviction: pending items
 * must never silently drop. */
export const inboxCollection = defineResourceCollection({
  pattern: "inbox/**",
  scope: "user",
  flowIsolation: false,
  stateSchema: inboxRecordSchema,
  /** Lazy is load-bearing: the default eager mode hydrates the entire inbox/
   * prefix into the execution context before execute runs, which would make
   * the capture path O(n) and defeat the fingerprint point lookup. */
  prefetchMode: "lazy",
  llmReadable: true,
  llmWritable: false, // writes go through logActivity, not generic resource tools
});

export const INBOX_PREFIX = getPatternPrefix(inboxCollection.pattern);

/** Bare key (framework auto-prepends the pattern prefix): `<kind>/<fingerprint>`.
 * Kind-first so list("<kind>/") filters at the source (BP-033); fingerprint-keyed
 * so exact-retry dedup is a single point lookup, not a collection scan.
 * capturedAt stays a state field — listInbox sorts on it in memory (a full
 * enumeration of the inbox is legitimate there, not list-then-discard). */
export function inboxKey(kind: ActivityKind, fingerprint: string): string {
  return `${kind}/${fingerprint}`;
}

/** Strip the injected `inbox/` prefix from a stored path to recover the id
 * (mirrors conceptIdFromPath in examples/knowledge-base/src/concepts.ts). */
export function inboxIdFromPath(path: string): string { /* ... */ }
```

Notes:
- Exact zod shapes follow BP-016/BP-023 conventions already used in `examples/knowledge-base/src/concepts.ts:27-37` (no `z.record`; nullable fields `.nullable().default(null)`).
- Import paths matter: the root `@flow-state-dev/core` barrel exports `defineResourceCollection` but **not** `getPatternPrefix` (that lives on `@flow-state-dev/core/types`, as `examples/knowledge-base/src/concepts.ts:16` imports it). Following the wrong path fails typecheck.
- `llmWritable: false` keeps the generic resource write tools from bypassing the mailroom. Note these flags gate instance *content* for the content/search/grep tools, not state (`packages/core/src/types/resource-collection.ts:83-96`) — inbox records are state-only, and there are no generators in this flow today, so the flags only matter if/when a generator gets `uses` access. Set them deliberately now (BP-021 spirit).
- The record `id` used in outputs is the bare key (prefix-stripped), consistent with knowledge-base's id convention.

### Idempotency semantics

Capture-time dedup exists for exactly one reason: **transport-retry safety** (an MCP client resubmitting the same call must not double-file). It is not similarity judgment — that's FIX-883's.

- The fingerprint covers the full capture tuple (kind, content, context, occurredAt, source), so only a true resubmit collides. Same content from a different conversation (different context) is a new record — the sweeper decides whether they merge.
- Records are keyed `<kind>/<fingerprint>`, so the check is a point `getOptional(inboxKey(kind, fp))`:
  - existing record with `status: "pending"` → return its id with `deduplicated: true`, write nothing;
  - existing record with `status: "swept"` → the earlier capture was already placed by the sweeper; create a fresh `pending` record at the same key (`create(key, record, { replace: true })`) — re-capturing after a sweep is a new mental event;
  - absent → `create(key, record)`.
- **The retry guarantee is bounded to the pending window.** If an identical retry arrives *after* the sweeper has already swept the record, it is treated as a fresh capture (the swept branch above), not deduplicated. Accepted deliberately: the window is small (transport retries are seconds; the sweep cadence is ~10 min), the degradation is benign (the sweeper sees the re-capture with batch context and reconciles), and a retry-tombstone mechanism is complexity v1 doesn't need (BP-038). If FIX-883 telemetry shows this firing in practice, a tombstone is the follow-up.
- **Race window**: there is no store-level insert-conflict to catch — `create()` checks the request-local cache and the state store upserts. The fingerprint-derived key is what makes the race benign: two concurrent identical captures converge on the *same* key, last write wins, and the end state is exactly one record. Both callers may report `deduplicated: false`; that inaccuracy is accepted — no locking or CAS (BP-038). No O(n) scan anywhere on the capture path.

### Config & auth (`fsdev.config.ts`, `package.json`)

Mirror `examples/knowledge-base/fsdev.config.ts` with two deliberate tightenings, because the fail-closed contract has to hold on **every** HTTP transport, not just MCP:

1. **The per-flow resolver is always defined** (see the flow sketch above): bearer resolver when `KH_MCP_SECRET` is set, otherwise a resolver that throws. Leaving it `undefined` is not safe — serving `createFlowState` installs the generic HTTP action routes in addition to any MCP endpoint, and hosts fall back to `defaultBodyUserIdPrincipalResolver` (host-level fallback in `createFlowApiRouter`), which derives the principal from caller-supplied `body.userId` — exactly what BP-031 forbids as an auth source. With the throwing resolver, `logActivity`/`listInbox` are unreachable over HTTP (MCP *and* action routes, including under `fsdev dev`) until the secret is provided. The CLI is unaffected: `fsdev run` invokes `runAction` in-process as its built-in `cli-user` principal (`packages/cli/src/commands/run.ts:473`) and never goes through a transport resolver. Constructing (not invoking) the throwing resolver at import time keeps local dev/CI import safe.
2. **Mount the MCP adapter only when `KH_MCP_SECRET` is set** — `adapters: process.env.KH_MCP_SECRET ? [createMcpTransportAdapter()] : []` (imported from `@flow-state-dev/mcp`; mounts `POST /api/flows/knowledge-hub/mcp`). Belt-and-suspenders on top of (1): no secret ⇒ no MCP endpoint at all.

Adding the adapter requires `"@flow-state-dev/mcp": "workspace:*"` in the lab's `package.json` (currently core/engine/zod only). Keep the `dev` filesystem profile and throwing `modelResolver` (still zero generators). **Without the secret the flow is CLI-only**; the README documents this. No Postgres/prod profile in this issue — deployment and durable hosting land with FIX-883, which is when a second process (the cron sweeper) actually needs shared storage; the filesystem store already persists across local runs.

### Error handling

Namespaced plain `Error` throws surface through the MCP adapter (knowledge-base precedent, `capability.ts:117`):

| Case | Behavior |
| --- | --- |
| Missing/blank `content` or `context`, unknown `kind`, invalid `occurredAt`, over-length input | zod schema rejection → MCP tool error (message names the field) |
| Store write failure | Error propagates; no partial record (single `create` call, no multi-step rollback needed); safe to retry (fingerprint idempotency) |
| Concurrent identical captures | Both converge on the same fingerprint-derived key; last write wins, end state is one record (see Idempotency semantics) |
| Unauthenticated/wrong-key MCP request when `KH_MCP_SECRET` set | Rejected by the bearer resolver (FIX-23 machinery), never served |
| `listInbox` on empty inbox | Normal result: `items: [], totalPending: 0, oldestPendingCapturedAt: null` — absence is data, not an error |

## 6. Edge Cases & Error Handling

| # | Edge case | Expected behavior |
| --- | --- | --- |
| 1 | Exact retry (identical kind + content + context + occurredAt + source; pending record exists) | No new record; `{ id: existing, deduplicated: true }` |
| 2 | Same content, different `context` (e.g. same task raised in two conversations) | New record — the fingerprint covers the full tuple; whether they merge is the sweeper's call |
| 3 | Same content + context, different `kind` | New record (kind is in the fingerprint and the key) |
| 4 | Retry of a capture whose record was already **swept** | Fresh `pending` record replaces the swept copy at the same key — the retry guarantee is bounded to the pending window (deliberate; see Idempotency semantics); the sweeper reconciles |
| 5 | Missing `context` | Schema rejection — capture contract requires it |
| 6 | Whitespace-only `content` or `context` | Rejected via non-mutating `.refine(s => s.trim().length > 0)`; valid values are stored verbatim |
| 7 | `content`/`context` > 20k chars, or `source` > 500 chars | Schema rejection with clear message (every caller-controlled field is bounded — `source` is a label, not a transcript) |
| 8 | Invalid `occurredAt` | Schema rejection; `occurredAt` never defaults to `capturedAt` (absence means "refers to now") |
| 9 | Concurrent identical captures | Same derived key → last write wins, end state is one record; callers may both report `deduplicated: false` (accepted; no store-level insert conflict exists to catch) |
| 10 | Large pending backlog (1000s) | Capture path unaffected (point lookup); `listInbox` caps at `limit` but `totalPending` reports the real count |
| 11 | Unknown `kind` value | Enum rejection (adding kinds later = additive enum change; removal would be a BP-030 dual-read event) |
| 12 | MCP call with wrong/missing bearer token (secret set) | Rejected by principal resolver; nothing written |

Error taxonomy: all capture-path errors are **caller errors (non-retryable as-is)** except store write failure and create-conflict (retryable — and safe to retry thanks to fingerprint idempotency). Nothing in this surface has a partial-success state.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (Feature) — red-green-refactor with tracer bullets; each behaviour below is one cycle.

**Goal & goal check.** Goal (observable outcome): *an MCP client can hand off a piece of mental activity mid-conversation and it lands durably in the owner's inbox, typed, dated, context-tagged, and visible to inspection — without any model call at capture time.* **No real-LLM goal check applies**: the flow contains zero generators (`neverResolvesAModel` stands), so there is no model in the loop for a `goals/` run to exercise — mirroring the FIX-885 precedent. The real-path evidence is instead:

- **Evidence path (BP-003):** from `labs/knowledge-hub/`:
  `pnpm fsdev run knowledge-hub logActivity -i '{"kind":"task","content":"Book dentist appointment","context":"Mentioned while planning the week in a Claude conversation"}'`
  then `pnpm fsdev run knowledge-hub listInbox -i '{}'`.
  **Pass criteria** (run against a fresh `.fsdev/data` dir, since the filesystem store persists across local runs): first command returns `{ id, capturedAt, deduplicated: false }`; second shows the item with `status: "pending"`, correct kind/content/context, and `totalPending` incremented by 1; re-running the first command (identical tuple) returns the same id with `deduplicated: true` and `totalPending` unchanged. Captures land under the CLI's built-in `cli-user` principal. (Read-back action pattern per AGENTS "when the result lives in a resource, not the stream".)
- The full end-to-end MCP-client goal (Claude calling `log_activity` over the network against a hosted endpoint) becomes meaningful once FIX-883 hosts the flow durably; noted in Non-Goals.

**Behaviours to test (tracer bullets, via `testFlow`):**

1. `logActivity` creates a pending inbox record carrying kind, verbatim content, context, server-stamped `capturedAt`, fingerprint.
2. Missing `context` → rejected; error names the field.
3. Whitespace-only `content` or `context` → rejected; a valid capture with leading/trailing whitespace is stored verbatim (not trimmed).
4. Exact retry (identical tuple) → `deduplicated: true`, same id, record count unchanged.
5. Same content, different `context` → two records.
6. Same content + context, different `kind` → two records.
7. `listInbox` → pending records only (a record with `status: "swept"` is excluded from `items` and never consumes `limit`), newest-first by `capturedAt`, `totalPending`, `oldestPendingCapturedAt`; `kind` filter narrows via key prefix; `limit` respected while `totalPending` reports full count.
8. User isolation: userA's captures invisible to userB; same user shares across separate `testFlow` calls over shared stores. Same two behaviours as `examples/knowledge-base/test/user-scope.spec.ts`, but expressed via `testFlow` with a shared `stores` registry and two `userId`s — the source spec uses the capability harness, which the hub deliberately doesn't have (Key Decision 5); don't reintroduce a capability just to copy the test. **Give each simulated user a distinct `sessionId`** — `testFlow` defaults every call to `sessionId: "test-session"`, and reusing userA's session for userB fails with a user-binding mismatch before it exercises resource isolation.
9. Mailroom pure-function specs (normalize idempotence; fingerprint sensitivity to every tuple element) in `test/mailroom.spec.ts`.
10. Fail-closed auth: with `KH_MCP_SECRET` unset, the flow's `resolvePrincipal` throws (unit-assert on the flow definition's resolver — HTTP transports are closed); `testFlow`/CLI paths are unaffected since they supply the principal in-process.

**Test templates:** `examples/knowledge-base/test/capability.spec.ts` (CRUD + error cases over a real in-memory collection), `test/user-scope.spec.ts` (BP-027), `test/helpers.ts` (`makeConceptCollection` harness shape), `labs/knowledge-hub/test/flow.spec.ts` (`testFlow` idiom). Node env, no model mocking needed (no generators).
