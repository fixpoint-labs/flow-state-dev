# FIX-885: Trading-desk portfolio pane sidebar — split into Gains & Taxes and Accounts perspectives — Implementation Spec

> Linear: [FIX-885](https://linear.app/fixpoint-labs/issue/FIX-885/trading-desk-portfolio-pane-sidebar-split-into-gains-and-taxes-and)

## 1. TLDR

The trading desk's portfolio page currently piles everything onto one screen: totals, the tax-estimate card, and the grid of accounts, with more surfaces on the way. We're adding a small sidebar so you can flip between two views of the same data — one for your accounts, one for realized gains and taxes — and creating the slot where the upcoming household health view (FIX-762) will live. As a bonus, gains-and-taxes information that today is buried inside each individual account gets a household-wide, year-by-year home.

**Technical statement:** Restructure `labs/trading-desk/components/portfolio/portfolio-pane.tsx` from a single stacked scroll region into a perspective-switched layout — a desktop left rail / mobile horizontal strip selecting between an `accounts` section (existing grid + drill-in, unchanged) and a new `gains` section (household year-by-year realized gains + current-year stats + the relocated tax-estimate card) — using only existing data hooks and row-model primitives.

**Deliverables:**

- Add `portfolio-section-nav.tsx` in `labs/trading-desk/components/portfolio/` — `PortfolioSection` union type, desktop `PortfolioSectionRail`, mobile `PortfolioSectionStrip`
- Add `gains-taxes-section.tsx` in `labs/trading-desk/components/portfolio/` — household summary stats (lifetime + current-year realized), relocated `TaxEstimateCard`, household-wide `RealizedGainsTable`
- Modify `portfolio-pane.tsx` — add `section` state, wrap the scroll region in a rail + content flex row, move `TaxEstimateCard` out of the Accounts content into the Gains section
- Docs: update the "Portfolio view" section of `labs/trading-desk/README.md`; empty changeset (internal lab app)

**Size estimate:** Medium — multi-file, 1 PR, ~200–400 LOC.

## 2. Overview

Issue: [FIX-885](https://linear.app/fixpoint-labs/issue/FIX-885/trading-desk-portfolio-pane-sidebar-split-into-gains-and-taxes-and).

The portfolio pane renders totals, the household tax-estimate card, and the account grid in one scroll region, with per-account detail swapped in via `openAccountId`. Year-by-year realized gains exist only inside each account's detail tab even though the data is fetched household-wide. This spec adds a sidebar that splits the pane into two perspectives — **Accounts** and **Gains & Taxes** — and establishes the extension point FIX-762 (household health) needs for a third.

## 3. Background & Research

### Codebase findings

- **The household year rollup already exists and is discarded.** `portfolio-pane.tsx:241-244` computes `computeRealizedGainTotals(buildRealizedGainsRowModel(realizedGains), "USD")` — which includes a per-year `byYear: Map<number, RealizedGainTotal>` — but only reads `.grandTotal` (the toolbar's lifetime realized stat). The Gains & Taxes section's current-year and per-year figures are nearly free.
- **`RealizedGainsTable` is already household-capable.** It renders a year-grouped table (per-year subtotals + grand total, table/card dual layout via `@3xl` container query) from raw `RealizedGainRow[]` + a display currency, and deliberately filters nothing (`realized-gains-table.tsx:29`). Passing the unfiltered household rows + `"USD"` yields the household year-by-year view with zero new table code.
- **Realized gains are fetched household-wide.** `useTax()` → `GET /api/portfolio/tax` returns all accounts, all years (`app/api/portfolio/tax/route.ts:49,87`); the `year` param scopes only the estimate. Account filtering happens at render time in `AccountDetail` (`account-detail.tsx:120-123`). No API change is needed.
- **The in-app idioms to follow:** the theses pane's `MemoSidebar` (`components/theses/memo-sidebar.tsx` — `w-[200px] shrink-0 overflow-y-auto border-r`, `px-2 py-1.5 text-[12px]` item buttons, selected `bg-[color:var(--c-surface-2)]`) for the desktop rail, and the `TopBar` segmented nav (`components/topbar.tsx:73-92` — `aria-current`, `NAV_ITEMS` const array) for the mobile strip. The `TradingDeskView` union (`topbar.tsx:25`) is the precedent for the section type.
- **Layout constraint:** the pane is a full-height flex column (`portfolio-pane.tsx:589`) whose toolbar and provenance line are pinned; only the middle region scrolls (`overflow-y-auto` at line 768). The app shells (`app/page.tsx:388-436` desktop grid, `443-482` mobile) never scroll the main cell. The sidebar must live inside the pane, below the pinned rows.

### Industry research

- For a secondary nav of 3–7 growing destinations, a persistent left sidebar on desktop degrading to a **horizontal tab strip** on mobile is the recommended shape ([NN/g vertical nav](https://www.nngroup.com/articles/vertical-nav/), [Material 3 navigation rail](https://m3.material.io/components/navigation-rail/guidelines)). Plain tabs cap out around 5–6 items; icon-only rails and desktop hamburgers are explicitly discouraged.
- **Do not add a second drawer on mobile.** The app already has a bottom nav; hidden nested nav kills discoverability ([NN/g mobile nav patterns](https://www.nngroup.com/articles/mobile-navigation-patterns/)). This overrides the theses-pane drawer precedent — that sidebar holds a long content list; this one holds 2–3 perspectives.
- Finance products (Empower, IBKR Client Portal, Monarch) keep the **portfolio total persistent across perspectives**; switching a perspective must not change content above the switcher ([Polaris tabs](https://polaris-react.shopify.com/components/navigation/tabs)).
- Accessibility: page-level section nav uses `<nav aria-label>` + `aria-current`, not `role="tablist"`.

### Why this approach

Tabs-everywhere would be simpler today but caps out exactly when FIX-762/771/763 land; a collapsible icon rail is over-engineered for 3 items. The rail + strip shape matches both the growth plan and existing app idioms, and the entire Gains & Taxes data story reuses tested pure primitives (`realized-gains-row-model.ts` is node-spec-covered).

### Key Decisions & Ramifications (top 5)

1. **Desktop left rail + mobile horizontal strip; no mobile drawer.** *Rejected:* tabs-everywhere; a `<dialog>` drawer mirroring the theses pane. *Ramification:* nav scales to ~6 sections and stays visible on all viewports; costs ~180px of desktop width for what is initially 2 items, and the strip row costs ~32px of mobile height. FIX-762 adds a section by appending one entry to a const array.
2. **Section selection is local React state (`PortfolioSection` union), not URL-addressable.** *Rejected:* Next.js shallow-routing query param. *Ramification:* no deep links or refresh persistence — but consistent with the whole app (top-level view and mobile tab are already local state); making one nav level URL-addressable while its parent isn't would be misleading. Revisit app-wide if deep-linking becomes a need.
3. **Toolbar, totals row, and provenance line stay pinned and unchanged across perspectives; only the content region swaps.** *Rejected:* per-perspective toolbars; moving the lifetime-realized stat out of the totals row. *Ramification:* account-entry actions (imports, add transaction) remain visible on the Gains view and the lifetime realized stat appears both in the toolbar and the Gains section — mild redundancy accepted to avoid layout shift and keep the diff small. Splitting the totals row is deferred to FIX-762, which will have opinions about where portfolio-wide figures live.
4. **Gains & Taxes reuses existing primitives with USD as the household display currency; zero API/wire changes.** *Rejected:* new server-side aggregation; putting `incomeByYear` back on the wire (BP-038 — no consumer yet). *Ramification:* rows in non-USD currencies render "—" via the existing currency gate in `computeRealizedGainTotals` — correct but blunt for mixed-currency households; a currency-aware household view is future work.
5. **Minimal decomposition: two new leaf components; the Accounts content stays inline in `portfolio-pane.tsx`.** *Rejected:* extracting a full `AccountsSection` (would thread ~30 props and balloon the diff). *Ramification:* the 923-line god component persists (flagged in Non-Goals as a deepening follow-up); the perspective seam this spec creates is the natural boundary for that later extraction.

## 4. Technical Design

All paths under `labs/trading-desk/`.

### 4.1 New: `components/portfolio/portfolio-section-nav.tsx`

Pure presentational module; no data hooks.

```ts
export type PortfolioSection = "accounts" | "gains";

const SECTIONS: ReadonlyArray<{ value: PortfolioSection; label: string }> = [
  { value: "accounts", label: "Accounts" },
  { value: "gains", label: "Gains & Taxes" },
];

type SectionNavProps = {
  value: PortfolioSection;
  onChange: (section: PortfolioSection) => void;
};

/** Desktop left rail (hidden below lg). */
export function PortfolioSectionRail({ value, onChange }: SectionNavProps): JSX.Element;

/** Mobile horizontal strip (hidden at lg and above). */
export function PortfolioSectionStrip({ value, onChange }: SectionNavProps): JSX.Element;
```

- **Rail markup:** `<nav aria-label="Portfolio sections" className="hidden w-[180px] shrink-0 overflow-y-auto border-r border-[color:var(--c-border)] bg-[color:var(--c-surface)] lg:block">`, items in a `px-2 pt-3` group. Item buttons follow the `MemoSidebar` idiom (`memo-sidebar.tsx:77-89`): `flex w-full items-center rounded-md px-2 py-1.5 text-left text-[12px]`; selected → `bg-[color:var(--c-surface-2)] text-[color:var(--c-fg)]`; unselected → `text-[color:var(--c-fg-muted)] hover:bg-[color:var(--c-surface-2)]/60`. `aria-current={selected ? "page" : undefined}`.
- **Strip markup:** `<nav aria-label="Portfolio sections" className="flex items-center gap-0.5 border-b border-[color:var(--c-border)] px-4 py-1.5 lg:hidden">` with segmented buttons following the `TopBar` idiom (`topbar.tsx:87-92`): `h-6 rounded px-2.5 text-[11.5px] font-medium`, same active/inactive tokens, inside the `rounded-md border bg-[color:var(--c-surface-2)] p-0.5` pill container.
- FIX-762 extends this by adding `{ value: "health", label: "Health" }` to `SECTIONS` and one union member.

### 4.2 New: `components/portfolio/gains-taxes-section.tsx`

```ts
import type { RealizedGainRow, TaxProfileRow } from "@/src/db/repository";
import type { TaxEstimate } from "@/src/flows/portfolio/tax-estimate";

type GainsTaxesSectionProps = {
  realizedGains: RealizedGainRow[];   // household-wide, unfiltered (from useTax)
  estimate: TaxEstimate | null;
  profile: TaxProfileRow | null;
  onEditProfile: () => void;
};

export function GainsTaxesSection(props: GainsTaxesSectionProps): JSX.Element;
```

Renders, top to bottom, inside the scrollable content column:

1. **Summary stat row** — a small flex row of labeled stats using the existing `RealizedStat` component (`realized-stat.tsx`) and its signed/colored/"excl. N" conventions:
   - *Realized (current year)* — from `computeRealizedGainTotals(models, "USD").byYear.get(currentYear)` where `currentYear = estimate?.year ?? new Date().getFullYear()`. Missing year → render the zero/em-dash state.
   - *Realized (lifetime)* — `.grandTotal` (same figure as the toolbar stat).
   - Both derived in a single `useMemo` (BP-010) over `buildRealizedGainsRowModel(realizedGains)` → `computeRealizedGainTotals(models, "USD")`.
2. **`<TaxEstimateCard estimate profile onEditProfile>`** — moved verbatim from `portfolio-pane.tsx:771-775`. The component is unchanged.
3. **Household realized-gains table** — `<RealizedGainsTable rows={realizedGains} currency="USD" />` (exact props per the component's current signature). Unfiltered rows give the year-grouped, all-accounts view with existing per-year subtotals and grand total. Section header above it follows the app's `font-mono text-[10.5px] uppercase tracking-wider text-[color:var(--c-fg-faint)]` label idiom.

No new server code, routes, or row-model functions. If implementation finds it needs a helper (e.g., a `currentYearTotal(rows, year)` selector), extract it as a pure browser-safe function in `realized-gains-row-model.ts` with a node spec — do not inline non-trivial aggregation in the component.

### 4.3 Modified: `components/portfolio/portfolio-pane.tsx`

- **State:** add `const [section, setSection] = useState<PortfolioSection>("accounts");` alongside `openAccountId` (line ~150). `openAccountId` is *not* reset on section change — returning to Accounts restores the open drill-in.
- **Layout:** regions 1–2 (toolbar lines 591-753, provenance line 758-762) are untouched. Region 3 changes from a single scroll div to:

```tsx
<PortfolioSectionStrip value={section} onChange={setSection} />   {/* pinned, lg:hidden */}
<div className="flex min-h-0 flex-1 overflow-hidden">
  <PortfolioSectionRail value={section} onChange={setSection} />   {/* hidden lg:block */}
  <div className="@container flex-1 space-y-4 overflow-y-auto p-4">
    {section === "gains" ? (
      <GainsTaxesSection realizedGains={realizedGains} estimate={taxEstimate}
                         profile={taxProfile} onEditProfile={() => setTaxProfileOpen(true)} />
    ) : (
      /* existing three-way branch, minus the TaxEstimateCard: empty-state | AccountDetail | card grid */
    )}
  </div>
</div>
```

  The `@container` class moves onto the content column so the account-grid container queries (`@3xl:grid-cols-2 @6xl:grid-cols-3`) keep working; the column is ~180px narrower at `lg`+, which only shifts where those breakpoints trip — acceptable.
- **Removal:** delete the `TaxEstimateCard` render from the top of the (former) scroll region (lines 771-775). It now lives only in `GainsTaxesSection` (BP-038: move, don't duplicate).
- **Dialogs:** all dialogs, including `TaxProfileDialog`, stay mounted at pane level (lines 847-920) — they are section-independent overlays and `taxProfileOpen` is pane state.
- **Memos:** unchanged. `householdRealized` (line 241-244) stays for the toolbar stat; `GainsTaxesSection` computes its own totals internally from the raw rows it receives (keeps the section self-contained for the FIX-762-era decomposition).

### 4.4 Data flow

No changes. `useTax()` already delivers household-wide `realizedGains`, `estimate`, `profile` to the pane; the pane passes them down. No new fetches, no session/resource changes, no engine or flow involvement.

### 4.5 Error handling

Inherited from existing components: `TaxEstimateCard` handles `estimate === null` (no tax profile yet); `RealizedGainsTable` handles empty rows; `RealizedStat` handles `null` gains and `excludedCount`. The section adds no new failure modes because it adds no new IO.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| No accounts yet | Accounts section shows the existing empty state; Gains section still renders (tax card prompts for profile, table shows its empty message) |
| `realizedGains` empty | Table renders its existing empty state; both summary stats render the null/em-dash state |
| `estimate === null` (no tax profile) | `TaxEstimateCard`'s existing "set profile" affordance; current-year stat falls back to `new Date().getFullYear()` |
| Mixed-currency household | Non-USD rows gate to "—" via `computeRealizedGainTotals`'s existing currency guard; USD is the declared household display currency |
| Rows with `basisUnknown` | Existing "excl. N" convention via `RealizedStat` / table totals — unchanged |
| Switch section while account detail open | `openAccountId` preserved; returning to Accounts restores the drill-in |
| Viewport crosses `lg` while on Gains | Rail/strip swap is pure CSS; `section` state unaffected; no modal/top-layer involvement (deliberately no drawer) |
| Dialog open during section switch | Dialogs are pane-level overlays; they stay open and functional regardless of section |

No retryable/fatal error taxonomy applies — the change introduces no new IO.

## 7. Testing Strategy

**Goal:** a user opening the Portfolio view can switch between an Accounts perspective (everything they have today) and a Gains & Taxes perspective showing household-wide year-by-year realized gains, current-year gains, and the tax estimate — on both desktop and mobile widths — without losing any existing capability.

**Goal check:** no real-LLM goal check applies — this is a pure UI-layer change with no model in the loop (per AGENTS.md's verification table, component rendering is verified in a browser, not via `fsdev run`). The observable-outcome check is a browser pass against the dev server (`pnpm --filter @flow-state-dev/trading-desk dev`) with seeded portfolio data, at a `lg`+ viewport and a phone viewport (Playwright/Chromium screenshots are the evidence artifact). PASS = the four verification bullets in §5 steps 2–3 all hold; FAIL = any regression in the Accounts flow or a household figure that doesn't reconcile with the per-account tabs.

**Discipline:** `fsd:tdd` (Feature). Tracer-bullet behaviors, in observable terms:

1. Selecting "Gains & Taxes" swaps the content region to the gains section; selecting "Accounts" restores the grid (and any open drill-in).
2. The gains section's year subtotals equal the sum of the corresponding per-account Realized Gains tabs (same rows, same rollup).
3. The current-year stat equals the table's current-year subtotal; the lifetime stat equals the toolbar's realized stat.
4. The tax-estimate card renders in the gains section and no longer above the account grid.

**Test harness reality:** the trading-desk vitest config is node-env, pure view-model specs only — no jsdom/RTL, and none should be added for this. Automated coverage applies only if a pure helper is extracted into `realized-gains-row-model.ts` (then: node spec beside `test/realized-gains-row-model.spec.ts`, following its existing fixture style). Behaviors 1–4 are verified in the browser pass above. Existing suites (`realized-gains-row-model.spec.ts`, `tax-estimate.spec.ts`, etc.) must stay green — this spec must not change any pure-model behavior.

## 8. Non-Goals

- **The household health section itself** — FIX-762 (this spec only guarantees `SECTIONS` extensibility).
- **URL-addressable section selection / deep-linking** — deliberately local state (Key Decision 2); revisit app-wide if needed.
- **An account filter control on the Gains & Taxes view** — the household cut is the point; per-account gains remain in account detail.
- **Currency-aware multi-currency household totals** — non-USD rows keep the "—" gate.
- **Returning `incomeByYear` on the tax wire** — still no consumer (BP-038); an income-by-year view would be its own issue.
- **Splitting the toolbar totals row by perspective** — deferred to FIX-762 (Key Decision 3).
- **Mobile drawer for the section nav** — rejected by design, not deferred.

**Deepening opportunities flagged (follow up via `fsd:improve-codebase-architecture`, not in scope):**

- `portfolio-pane.tsx` is a 923-line god component (10 state pieces, 6 data hooks, ~11 memos, ~9 write handlers, 8 dialogs). The perspective seam introduced here is the natural boundary for a later `AccountsSection` extraction.
- `AccountDetail` prop-drilling (~30 props) and repeated render-time re-filtering of `realizedGains` by account (`account-detail.tsx:120-123` vs `realizedTotalsByAccount`).
- `realized-gains-table.tsx:46-51` re-implements `directionColor` instead of reusing `RealizedStat`'s convention — a Gains section touching all three is a chance to converge later.
