# FIX-890: Filesystem content/state stores flatten resource keys into unusable, extensionless files — Implementation Spec

## 1. TLDR

**Plain-language summary.** When you point flow-state-dev at a folder on disk to store its "resources" (the docs, notes, and state a flow reads and writes), it doesn't actually give you usable files. A resource named like `concepts/flow-state-dev/overview` gets crammed into a single file whose name is the whole path with the slashes mangled into `%2F`, and with no `.md`/`.json` on the end. So you can't open the folder in Obsidian or VS Code, you can't get a meaningful git diff, and you can't point knowledge-base tooling at it. This change makes the store write real nested folders with real file extensions, so the folder on disk is a browsable vault — while keeping the storage API behaving exactly as before.

**One-sentence technical statement.** Rework `FilesystemContentStore` and `FilesystemResourceStateStore` so a resource key is mapped to a nested on-disk path (one directory per `/`-segment, per-segment character escaping) with a leaf file extension (`.md` for content, `.json` for state), replacing the current single flat `encodeURIComponent(wholeKey)` filename, behind a shared, injective, path-traversal-safe key↔path mapping.

**Deliverables:**

- **Add** a shared key↔path mapping module `packages/engine/src/stores/filesystem/resource-path.ts` — `keyToRelativePath`, `relativePathToKey`, `collectRecords` (recursive walk), and a dot-segment / path-traversal guard. One implementation, consumed by both stores (no duplicated logic).
- **Rewrite** path construction in `packages/engine/src/stores/filesystem/content-store.ts` to nest segments and append `.md`; make `getAll`/`getByPrefix` walk the tree recursively and reconstruct keys.
- **Rewrite** path construction in `packages/engine/src/stores/filesystem/resource-state-store.ts` identically, appending `.json`; preserve its existing atomic-write + ENOENT-retry behavior.
- **Add** a loud collision guard so a write that would require a path to be both a file and a directory fails with a clear error instead of corrupting silently (and prune empty ancestor directories on `delete`).
- **Add** on-disk-layout assertions to `packages/engine/test/content-store.test.ts` and `packages/engine/test/resource-state-store.test.ts`, plus a focused unit test for `resource-path.ts` (round-trip, collision, traversal, prefix reconstruction).
- **Docs:** update the filesystem-store layout description (README/persistence page — see §9).

**Size:** **Medium** (single package `@flow-state-dev/engine`, single PR, ~250–350 LOC incl. tests). No public API-surface change — the `ContentStore` / `ResourceStateStore` interfaces are untouched; only the on-disk representation changes.

## 2. Overview

Linear issue: [FIX-890](https://linear.app/fixpoint-labs/issue/FIX-890).

The two filesystem-backed keyed-resource stores build every on-disk path as `rootDir/{content|state}/{scopeType}/{encodeURIComponent(scopeId)}/{encodeURIComponent(resourceKey)}`, applying `encodeURIComponent` to the **whole** resource key. Any key containing `/` (every collection item, every namespaced doc) collapses to one flat file named `concepts%2Fflow-state-dev%2Foverview` with no extension. The result is a directory that is not browsable, not diffable, doesn't nest, and can't be opened by an editor's language mode — the opposite of what a file-based store is for.

This spec changes the on-disk representation (not the store contract) so that a resource key becomes a nested path with a meaningful extension, making the store's `rootDir` a real vault that Obsidian / VS Code / OKF tooling can read directly, while every existing store behavior (`get`/`set`/`getByPrefix`/`getAll`/`delete`/`deleteAll`, scope isolation, atomic writes) is preserved and re-verified against the shared conformance suite.

## 3. Background & Research

### 3.1 What the code actually does today (verified)

- `content-store.ts` `filePath()` = `join(scopeDir, encodeURIComponent(resourceKey))`. **No extension.** `getByPrefix` does a single-level `readdir`, `decodeURIComponent`s each filename, and filters with `resourceKey.startsWith(keyPrefix)`.
- `resource-state-store.ts` is structurally identical (single-level `readdir`, whole-key encode) and **also writes no extension** — its `filePath()` is `encodeURIComponent(resourceKey)`, not `…json`. **The issue's claim that "state files get a blanket `.json`" is inaccurate**; today neither store adds any extension. (The `.json` pattern lives only in `shared.ts` `toFileName`, used by the opaque-id scope stores, which are out of scope here.) The state store additionally carries an atomic-write loop with a one-shot ENOENT retry (concurrent scope-tree create/teardown) that must be preserved.
- The behavioral contract both stores must keep is the shared **conformance suite** (`packages/engine/src/stores/testing/resource-store-conformance.ts`), which exercises `docs/one`, `docs/two`, `todos/a`, `k/1`, `50%_off` vs `5000_off`, `files/src/utils.ts`, empty prefix, and scope isolation. The in-memory store is the semantic reference: `getByPrefix` is a **plain string `startsWith`** on the reconstructed key, *not* a path-segment-boundary match (`getByPrefix("50%_")` matches `50%_off` but not `5000_off`).

### 3.2 The industry pattern the fix follows

Mapping a hierarchical key to a real file tree where a node can be *both* a leaf and a parent is a solved problem — Hugo's leaf/branch bundles, Obsidian "folder notes," and static-site content trees all coexist a file and a same-named directory. The disambiguator is the **file extension**: a leaf always carries one, a directory segment never does. So `concepts/flow-state-dev` → `concepts/flow-state-dev.md` (a file) sits happily beside `concepts/flow-state-dev/` (a directory holding `overview.md`) because the two names differ by the extension. This dissolves the "leaf-vs-directory collision" open question **by construction** — no reserved `_index.md` sentinel is needed, and no constraint on which keys may share a prefix. (The `_index.md` approach was considered and rejected: it forces every leaf into its own directory, uglifying the common flat case and complicating the tree walk.)

### 3.3 Why per-segment encoding needs a traversal guard

`encodeURIComponent` escapes `/` (→`%2F`) and spaces, but leaves `.`, `..`, and the empty string **unchanged** (verified: `encodeURIComponent("..") === ".."`). The current whole-key encoding *accidentally* neutralizes traversal (`../secret` → `..%2Fsecret`, a flat safe name). Splitting on `/` and encoding per segment **reintroduces a path-traversal vector**: a key `../../etc/passwd` would produce real parent-directory hops. The mapping module must therefore special-case `.`, `..`, and empty segments (percent-escape the dots so they round-trip and never traverse), and assert the resolved path stays under the scope directory.

### 3.4 Key Decisions & Ramifications (top 5)

1. **Extension as the leaf/branch disambiguator (leaf gets `.md`/`.json`, directory segments raw).** Rejected: reserved `_index.md` sentinel per leaf; rejected: forbidding leaf/dir prefix overlap. *Ramification:* the key→path map stays injective and the flat common case stays clean (`overview.md`, not `overview/_index.md`); a leaf and a same-named branch coexist as `X.md` + `X/`. Locks in "one trailing extension is structural, not part of the key" — content whose key ends in a real extension becomes double-suffixed on disk (`files/a.ts` → `files/a.ts.md`), the accepted cost of determinism.
2. **`.md` for all content, `.json` for all state — no content-type inference.** Rejected: a content-type hint / opt-in per resource (defer to FIX-367 binary work). *Ramification:* the vault is markdown-by-default (matches the stated knowledge-base use case) and the mapping is deterministic and reversible; the price is the double-extension case above and that genuinely non-markdown opaque content is still labeled `.md`. Revisit only when binary content (FIX-367) lands.
3. **Clean break on existing on-disk data (no legacy dual-read / migration).** Rejected: read-time fallback to the old flat filename; rejected: one-shot migration on open. *Ramification:* any pre-existing filesystem-store directory stops resolving after upgrade (data re-imported, not silently lost — it's still on disk under the old names). Justified by pre-1.0 status and that nested keys — the whole point of the fix — were never usably stored before, so real persisted nested data is ~nil. **This is the one decision most worth a human sign-off (see §11).**
4. **Extract the mapping into a shared module, don't inline in each store.** Rejected: copy the split/encode/walk logic into both store files. *Ramification:* satisfies the repo's "common helpers belong in a shared utils file — no duplicate copies" rule, and makes the risky part (encoding, traversal, round-trip, prefix reconstruction) unit-testable in isolation. Locks both stores to identical layout semantics by shared code, not by parallel edits.
5. **Scope strictly to the two resource-keyed stores; opaque-id stores untouched.** Rejected: also de-flatten session/user/org/request/checkpoint/trace stores in `shared.ts`. *Ramification:* keeps the change surgical and low-risk; those stores key on opaque framework ids (`req_*`, session ids) that carry no "should be human-browsable" requirement, so flat `encodeURIComponent(id).json` stays correct there. A follow-up issue can revisit if ever wanted.

## 4. Technical Design

### 4.1 Architecture

All changes live in `packages/engine/src/stores/filesystem/`:

- **New:** `resource-path.ts` — the shared, dependency-free mapping used by both stores.
- **Modified:** `content-store.ts`, `resource-state-store.ts` — replace `encodePath(resourceKey)` path construction and the single-level `readdir` in `getByPrefix` with calls into `resource-path.ts`.

No change to `packages/engine/src/stores/types.ts` (interfaces unchanged), to the memory stores, to the SQLite adapter (DB-backed; unaffected), or to `shared.ts`.

**Wiring / blast radius (verified).** Both stores are constructed together by `createFilesystemStores()` (`packages/engine/src/stores/index.ts:225-226`), each handed the same bare `rootDir` and self-appending `content`/`state`. The factories are public (`@flow-state-dev/engine` root exports at `index.ts:10-11`); the classes are **not** exported, so internal restructuring is free. Real consumers (`examples/knowledge-base`, `apps/kitchen-sink`) go through `filesystemStores({ rootDir })` and touch only the method API. **No code anywhere reads the store's on-disk files directly** — no tooling globs `rootDir` — so the layout change has no non-store caller to break.

### 4.2 The mapping module (`resource-path.ts`)

```ts
/** Segments that must never reach the filesystem as-is (traversal / empty). */
// "." "" -> escaped so they round-trip and cannot traverse; ".." likewise.

/** Escape one key segment for filesystem safety. Injective and reversible. */
function encodeSegment(segment: string): string;   // encodeURIComponent + dot/empty special-case
function decodeSegment(segment: string): string;   // exact inverse

/** Map a resource key to a path RELATIVE to the scope dir, incl. leaf extension. */
export function keyToRelativePath(resourceKey: string, ext: string): string;
//   "concepts/flow-state-dev/overview", ".md"
//     -> "concepts/flow-state-dev/overview.md"

/** Inverse: reconstruct the resource key from a relative on-disk path. */
export function relativePathToKey(relPath: string, ext: string): string;

/**
 * Recursively walk `scopeDir`, yielding { resourceKey, absolutePath } for every
 * file whose name ends in `ext`. Skips temp files (`*.tmp-*`) and any entry not
 * ending in `ext`. Reconstructs each key via relativePathToKey. This is the
 * single source of truth for getAll/getByPrefix enumeration.
 */
export async function collectRecords(scopeDir: string, ext: string):
  Promise<Array<{ resourceKey: string; absolutePath: string }>>;
```

**Encoding rule (per segment):**
- Split `resourceKey` on `/`.
- For each segment: if it is `""`, `"."`, or `".."`, replace with a reserved escaped form that `decodeSegment` reverses and that contains no path meaning (e.g. percent-encode the dots: `.` → `%2E`, `..` → `%2E%2E`, `""` → a sentinel like `%2E` is not enough for empty — reject empty interior/leaf segments loudly instead, since a resource key with an empty segment is malformed). Otherwise `encodeURIComponent(segment)`.
- Join with `path.sep` via `path.join`; append `ext` to the **leaf** only.

> Note: `encodeURIComponent` does not escape `.`, so the reserved escaped form must itself be chosen so it decodes back exactly (percent-decoding `%2E` → `.`). The unit test pins every one of these round-trips.

**Injectivity / collision:** because `/` is the only separator, each segment is escaped injectively, and exactly one extension is appended to the leaf, the key→path map is injective; distinct keys never collide. A leaf `X` (`X.md`) and a branch `X` (`X/…`) differ by the extension and coexist. `relativePathToKey` strips exactly one trailing `ext` from the leaf and decodes each segment.

**Traversal safety:** after building the absolute path, assert `path.resolve(abs)` starts with `path.resolve(scopeDir) + path.sep`; throw otherwise. Belt-and-suspenders on top of dot-segment escaping.

### 4.3 Data flow

- **`set(scopeType, scopeId, key, value)`**: `target = join(scopeDir, keyToRelativePath(key, ext))`; `mkdir(dirname(target), { recursive: true })`; atomic temp-write + rename (state store keeps its one-shot ENOENT retry loop, now mkdir-ing the leaf's nested parent, not just `scopeDir`).
- **`get`**: `readFile(join(scopeDir, keyToRelativePath(key, ext)))`; `ENOENT → undefined`.
- **`getAll` / `getByPrefix`**: `collectRecords(scopeDir, ext)` → for each `{resourceKey}` keep when `resourceKey.startsWith(keyPrefix)` (empty prefix = all); read + (state: `JSON.parse`) into the result record. Matches memory-store semantics exactly.
- **`delete`**: `rm(target)`; on success, prune now-empty ancestor directories up to (not including) `scopeDir` so the vault doesn't accumulate ghost folders. `ENOENT` on the file is a no-op.
- **`deleteAll`**: unchanged — `rm(scopeDir, { recursive: true, force: true })`.

### 4.4 Collision guard

A write can hit a genuine filesystem conflict only against pre-existing/foreign data (our own map can't produce one): e.g. a directory already exists where a file must be written, or vice versa. Node surfaces these as `EEXIST` / `ENOTDIR` / `EISDIR`. Wrap `mkdir`/`writeFile`/`rename` so these codes throw a clear `Error` naming the scope, key, and conflicting path ("refusing to write <key>: <path> is a directory") instead of propagating a bare errno or corrupting. This is the "fail loudly" guard the issue asks for.

### 4.5 Error handling summary

| Case | Behavior |
|---|---|
| `get` missing file | `undefined` (ENOENT swallowed) — unchanged |
| `getByPrefix` missing scope dir | `{}` (ENOENT swallowed) — unchanged |
| `set` transient ENOENT (state store) | one-shot mkdir + retry, then propagate — preserved |
| file/dir type conflict on write | throw clear collision error (EEXIST/ENOTDIR/EISDIR) |
| key with `.`/`..`/empty segment | escaped or rejected loudly; never traverses |
| `delete` missing file | no-op; prune empty parents best-effort |

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|---|---|
| Nested key `a/b/c` | dirs `a/b/`, file `c.md`/`c.json` |
| Leaf `a/b` **and** child `a/b/c` both set | `a/b.md` (file) + `a/b/c.md` (file in `a/b/` dir) coexist; no collision |
| Key `50%_off` vs `5000_off`, prefix `50%_` | only `50%_off` matches (string `startsWith`, not path boundary) |
| Key with real extension `files/a.ts` (content) | `files/a.ts.md` on disk; round-trips to `files/a.ts` |
| Key segment `..` / `.` | escaped, never traverses out of scope dir |
| Key with empty interior/leaf segment (`a//b`, `a/`) | rejected loudly (malformed key) |
| Concurrent scope create/teardown (state store) | existing one-shot ENOENT retry preserved |
| Pre-existing dir where file must go (foreign data) | throws clear collision error, no corruption |
| Temp file left by a crashed write (`*.tmp-*`) | skipped by `collectRecords` (doesn't end in `ext`) |
| `delete` empties a directory | empty ancestor dirs pruned up to scope dir |
| Legacy flat file from before this change | not resolved (clean break, §3.4 #3) |

**Retryable vs fatal:** transient ENOENT on the state store's write → retry once (existing). Collision (EEXIST/ENOTDIR/EISDIR) and malformed-key → fatal, thrown. Missing file on read/delete → benign, swallowed.

## 7. Testing Strategy

**Discipline:** `fsd:diagnose` (Bug/correctness). Build the feedback loop first, reproduce the flat-file defect, fix at the mapping layer, add regression tests.

**Goal & goal check.** The goal is observable: *a resource stored through the filesystem store lands on disk as a browsable, nested, extensioned file tree*. This is a filesystem outcome, not a real-LLM outcome, so **no real-model goal check applies** — the "real path" here is the store's own `set`→disk, which is exercised directly by the on-disk-assertion tests (they inspect the actual temp directory, not a mock). That is the goal check: a Vitest that writes `concepts/flow-state-dev/overview` and asserts the real file at `…/concepts/flow-state-dev/overview.md`. No `goals/` script and no `fsdev run` are warranted (there is no model behavior to prove).

**Feedback-loop seam:** Vitest at the adapter level (`packages/engine/test/content-store.test.ts`, `resource-state-store.test.ts`) plus a focused unit seam for the mapping (`packages/engine/test/stores/filesystem/resource-path.test.ts`). The mapping unit test is where reproduction and regression live — it fails today's flat behavior would-be and pins every round-trip.

**Regression-test seam:** the two adapter test files (contract + on-disk layout) and the mapping unit test. The shared conformance suite (`resource-store-conformance.ts`) already runs against both filesystem stores via `@flow-state-dev/engine/testing` — confirm it stays green unchanged (it asserts only the layout-agnostic contract). The **highest-value existing regression gate** is `resource-state-store.test.ts` "many concurrent writes to a fresh scope" (~lines 184-201), which writes real slash-bearing keys (`holdings/acct__T0`) and asserts round-trip through `getAll` — exactly the case this spec reworks (today those become flat `holdings%2Facct__T0`); it must stay green and now proves nested writes survive the concurrent scope-create race.

**Behaviors to pin (regression):**
- Contract preserved: full conformance suite passes on the nested layout.
- On-disk layout: nested dirs + correct extension for content and state.
- Leaf/branch coexistence at the same key prefix.
- `getByPrefix` string-prefix semantics (the `50%_` case) survive the tree walk.
- Path-traversal segments neutralized.
- Collision guard throws, doesn't corrupt.

Reference patterns: `packages/engine/test/content-store.test.ts` (adapter setup with `mkdtemp`), `resource-store-conformance.ts` (contract).

## 8. Non-Goals

- **Opaque-id filesystem stores** (session/user/org/request/checkpoint/trace via `shared.ts` `toFileName`) — stay flat `encodeURIComponent(id).json`; they key on non-browsable ids (§3.4 #5).
- **Binary content extension handling** — deferred to [FIX-367](https://linear.app/fixpoint-labs/issue/FIX-367); content stays `string` and `.md`-labeled here.
- **OKF adapter reconciliation / frontmatter / schema.** Confirmed independent: the OKF export (`examples/knowledge-base/src/okf/export.ts`) writes YAML-frontmatter `.md` bundles to a **caller-supplied interchange `dir`** over the resource-collection abstraction — it never touches the store's `content/`/`state/` trees. This spec makes the live store *resemble* the OKF layout but there is **no path overlap and no duplication**; whether the export later collapses into "point OKF at `rootDir`" is [FIX-813](https://linear.app/fixpoint-labs/issue/FIX-813) follow-up, out of scope here.
- **Legacy migration tooling** — clean break (§3.4 #3); no dual-read, no migration script.
- **Content-type inference / per-resource extension opt-in** — not built; `.md` uniform.

*Deepening opportunities:* none surfaced beyond the existing intentional duplication between the two stores, which this spec actually reduces by extracting the shared mapping module.

## 11. Open Questions

1. **Existing on-disk data (the one real decision).** Spec recommends a **clean break** (no legacy read / migration), justified by pre-1.0 status and that nested keys were never usably stored. If any real deployment has a populated filesystem-store `rootDir`, we'd instead add a cheap read-time fallback to the old flat name. **Needs owner confirmation** that clean break is acceptable.
2. **Double extension for extensioned keys** (`files/a.ts` → `files/a.ts.md`). Accepted as the deterministic default. Confirm no one relies on the store holding non-markdown content that must open in its native language mode. (If they do → FIX-367 territory.)
3. **OKF adapter overlap — resolved.** The export writes to a separate interchange dir over the collection abstraction, not the store tree; no overlap or duplication. Any consolidation is FIX-813 follow-up, not this issue.
