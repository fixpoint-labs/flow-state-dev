# FIX-890: Filesystem content/state stores flatten resource keys into unusable, extensionless files — Implementation Spec

## 1. TLDR

**Plain-language summary.** When you point flow-state-dev at a folder on disk to store its "resources" (the docs, notes, and state a flow reads and writes), it doesn't actually give you usable files. A resource named like `concepts/flow-state-dev/overview` gets crammed into a single file whose name is the whole path with the slashes mangled into `%2F`, and with no `.md`/`.json` on the end. So you can't open the folder in Obsidian or VS Code, you can't get a meaningful git diff, and you can't point knowledge-base tooling at it. This change makes the store write real nested folders with real file extensions, so the folder on disk is a browsable vault — while keeping the storage API behaving exactly as before.

**One-sentence technical statement.** Rework `FilesystemContentStore` and `FilesystemResourceStateStore` so a resource key is mapped to a nested on-disk path (one directory per `/`-segment, per-segment character escaping) with a leaf file extension (`.md` for content, `.json` for state), replacing the current single flat `encodeURIComponent(wholeKey)` filename, behind a shared, injective, path-traversal-safe key↔path mapping.

**Deliverables:**

- **Add** a shared key↔path mapping module `packages/engine/src/stores/filesystem/resource-path.ts` — `keyToRelativePath`, `relativePathToKey`, `collectRecords` (recursive walk), and a dot-segment / path-traversal guard. One implementation, consumed by both stores (no duplicated logic).
- **Rewrite** path construction in `packages/engine/src/stores/filesystem/content-store.ts` to nest segments and append `.md`; make `getAll`/`getByPrefix` walk the tree recursively and reconstruct keys.
- **Rewrite** path construction in `packages/engine/src/stores/filesystem/resource-state-store.ts` identically, appending `.json`; preserve its existing atomic-write + ENOENT-retry behavior.
- **Add** a loud collision guard so a write that would require a path to be both a file and a directory fails with a clear error instead of corrupting silently.
- **Add** a clean-break legacy guard (BP-030): a durable per-subtree `content/.fsdev-store-layout` / `state/.fsdev-store-layout` marker written **by the first `set`** (never at construction or on a read); on first touch a store whose own subtree holds legacy data with no valid marker `throw`s a clear "legacy layout, will not read — move aside or delete" error rather than silently mis-serving. `deleteAll` and construction bypass the guard. No conversion, no hot-path cost.
- **Wire** the shared conformance suite (`createContentStoreConformanceTests` / `createResourceStateStoreConformanceTests`) into `content-store.test.ts` and `resource-state-store.test.ts` (they run an inline suite today, not the shared one), and **add** on-disk-layout assertions to both, plus a focused unit test for `resource-path.ts` (round-trip, collision, traversal, prefix reconstruction).
- **Docs:** update the filesystem-store layout description (README/persistence page — see §9).

**Size:** **Medium** (single package `@flow-state-dev/engine`, single PR, ~250–300 LOC incl. the legacy-detection guard and tests). No public API-surface change — the `ContentStore` / `ResourceStateStore` interfaces are untouched; only the on-disk representation changes.

## 2. Overview

Linear issue: [FIX-890](https://linear.app/fixpoint-labs/issue/FIX-890).

The two filesystem-backed keyed-resource stores build every on-disk path as `rootDir/{content|state}/{scopeType}/{encodeURIComponent(scopeId)}/{encodeURIComponent(resourceKey)}`, applying `encodeURIComponent` to the **whole** resource key. Any key containing `/` (every collection item, every namespaced doc) collapses to one flat file named `concepts%2Fflow-state-dev%2Foverview` with no extension. The result is a directory that is not browsable, not diffable, doesn't nest, and can't be opened by an editor's language mode — the opposite of what a file-based store is for.

This spec changes the on-disk representation (not the store contract) so that a resource key becomes a nested path with a meaningful extension, making the store's `rootDir` a real vault that Obsidian / VS Code / OKF tooling can read directly, while every existing store behavior (`get`/`set`/`getByPrefix`/`getAll`/`delete`/`deleteAll`, scope isolation, atomic writes) is preserved and re-verified against the shared conformance suite.

## 3. Background & Research

### 3.1 What the code actually does today (verified)

- `content-store.ts` `filePath()` = `join(scopeDir, encodeURIComponent(resourceKey))`. **No extension.** `getByPrefix` does a single-level `readdir`, `decodeURIComponent`s each filename, and filters with `resourceKey.startsWith(keyPrefix)`.
- `resource-state-store.ts` is structurally identical (single-level `readdir`, whole-key encode) and **also writes no extension** — its `filePath()` is `encodeURIComponent(resourceKey)`, not `…json`. **The issue's claim that "state files get a blanket `.json`" is inaccurate**; today neither store adds any extension. (The `.json` pattern lives only in `shared.ts` `toFileName`, used by the opaque-id scope stores, which are out of scope here.) The state store additionally carries an atomic-write loop with a one-shot ENOENT retry (concurrent scope-tree create/teardown) that must be preserved.
- The behavioral contract both stores must keep is the shared **conformance suite** (`packages/engine/src/stores/testing/resource-store-conformance.ts`), which today exercises `docs/one`, `docs/two`, `k/1`, `50%_off` vs `5000_off` (the literal-wildcard prefix), empty prefix, and scope isolation. **It does NOT currently cover a dotted-extension nested key like `files/src/utils.ts`** (verified) — the exact case that becomes `files/src/utils%2Ets.md`; this spec **adds that case to the shared suite** (§5) so both filesystem adapters get store-level coverage for it. The in-memory store is the semantic reference: `getByPrefix` is a **plain string `startsWith`** on the reconstructed key, *not* a path-segment-boundary match (`getByPrefix("50%_")` matches `50%_off` but not `5000_off`).

### 3.2 The industry pattern the fix follows

Mapping a hierarchical key to a real file tree where a node can be *both* a leaf and a parent is a solved problem — Hugo's leaf/branch bundles, Obsidian "folder notes," and static-site content trees all coexist a file and a same-named directory. The disambiguator is the **file extension**: a leaf always carries one, a directory segment never does. So `concepts/flow-state-dev` → `concepts/flow-state-dev.md` (a file) sits happily beside `concepts/flow-state-dev/` (a directory holding `overview.md`) because the two names differ by the extension. This dissolves the "leaf-vs-directory collision" open question **by construction** — no reserved `_index.md` sentinel is needed, and no constraint on which keys may share a prefix. (The `_index.md` approach was considered and rejected: it forces every leaf into its own directory, uglifying the common flat case and complicating the tree walk.)

### 3.3 Why per-segment encoding needs a traversal guard

`encodeURIComponent` escapes `/` (→`%2F`) and spaces, but leaves `.`, `..`, and the empty string **unchanged** (verified: `encodeURIComponent("..") === ".."`). The current whole-key encoding *accidentally* neutralizes traversal (`../secret` → `..%2Fsecret`, a flat safe name). Splitting on `/` and encoding per segment **reintroduces a path-traversal vector**: a key `../../etc/passwd` would produce real parent-directory hops. The mapping module must therefore special-case `.`, `..`, and empty segments (percent-escape the dots so they round-trip and never traverse), and assert the resolved path stays under the scope directory.

### 3.4 Key Decisions & Ramifications (top 5)

1. **Extension as the leaf/branch disambiguator (leaf gets `.md`/`.json`, directory segments dot-escaped).** Rejected: reserved `_index.md` sentinel per leaf; rejected: forbidding leaf/dir prefix overlap. *Ramification:* the key→path map stays injective and the flat common case stays clean (`overview.md`, not `overview/_index.md`); a leaf and a same-named branch coexist as `X.md` + `X/`. Because every `.` inside a segment is escaped to `%2E` (§4.2), the appended extension is the only literal dot in any path component, so the extension-named-segment collision (`a` vs `a.md/b`) cannot occur. Cost: a key whose leaf already looks like a filename is double-suffixed and dot-escaped on disk (`files/a.ts` → `files/a%2Ets.md`), the accepted price of a provably injective, deterministic map.
2. **`.md` for all content, `.json` for all state — no content-type inference.** Rejected: a content-type hint / opt-in per resource (defer to FIX-367 binary work). *Ramification:* the vault is markdown-by-default (matches the stated knowledge-base use case) and the mapping is deterministic and reversible; the price is the double-extension case above and that genuinely non-markdown opaque content is still labeled `.md`. Revisit only when binary content (FIX-367) lands.
3. **Clean break on legacy data, with a loud detection guard (owner-confirmed).** The approach converged over several review rounds: clean-break → dual-read fallback → lazy per-scope migration → **back to clean break**. Dual-read and lazy migration each proved bug-prone under review (stale read-back on delete, `set` prefix-collisions, enumeration dedup, ambiguous legacy-vs-new detection, stage-before-unlink ordering, per-scope migration locking, case/Unicode-fold aliasing) — a genuine mini-project serving pre-1.0 data that likely doesn't exist. *Decision (owner-confirmed):* clean break — the new layout does not read old flat files. Each store distinguishes new-layout from legacy by a **durable per-subtree layout marker** (`content/.fsdev-store-layout`, `state/.fsdev-store-layout`, §4.6 — per-subtree, *not* a shared `rootDir` marker, so an empty `content` store can't mask a legacy `state` subtree): own-subtree marker absent/invalid while that subtree holds real data → `throw` a clear, actionable error instead of silently mis-serving, satisfying BP-030's "reject removed keys loudly." (A marker, not filename heuristics — heuristics silently mis-key a legacy scope whose keys all end in the extension.) Rejected: dual-read and lazy migration (four rounds of correctness traps); a deliberate one-time migration tool is a documented follow-up (§8) if a real deployment ever needs it. *Ramification:* the store stays a pure new-layout implementation and the entire migration bug-class disappears; the only cost is a memoized first-touch scan per store for the guard.
4. **Extract the mapping into a shared module, don't inline in each store.** Rejected: copy the split/encode/walk logic into both store files. *Ramification:* satisfies the repo's "common helpers belong in a shared utils file — no duplicate copies" rule, and makes the risky part (encoding, traversal, round-trip, prefix reconstruction) unit-testable in isolation. Locks both stores to identical layout semantics by shared code, not by parallel edits.
5. **Scope strictly to the two resource-keyed stores; opaque-id stores untouched.** Rejected: also de-flatten session/user/org/request/checkpoint/trace stores in `shared.ts`. *Ramification:* keeps the change surgical and low-risk; those stores key on opaque framework ids (`req_*`, session ids) that carry no "should be human-browsable" requirement, so flat `encodeURIComponent(id).json` stays correct there. A follow-up issue can revisit if ever wanted.

## 4. Technical Design

### 4.1 Architecture

All changes live in `packages/engine/src/stores/filesystem/`:

- **New:** `resource-path.ts` — the shared, dependency-free mapping used by both stores.
- **Modified:** `content-store.ts`, `resource-state-store.ts` — replace `encodePath(resourceKey)` path construction and the single-level `readdir` in `getByPrefix` with calls into `resource-path.ts`.

No change to `packages/engine/src/stores/types.ts` (interfaces unchanged), to the memory stores, to the SQLite adapter (DB-backed; unaffected), or to `shared.ts`.

**Wiring / blast radius (verified).** Both stores are constructed together by `createFilesystemStores()` (`packages/engine/src/stores/index.ts:225-226`), each handed the same bare `rootDir` and self-appending `content`/`state`. The factories are public (`@flow-state-dev/engine` root exports at `index.ts:10-11`); the classes are **not** exported, so internal restructuring is free. Real consumers (`examples/knowledge-base`, `apps/kitchen-sink`) go through `filesystemStores({ rootDir })` and touch only the method API. **No code anywhere reads the store's on-disk files directly** — no tooling globs `rootDir` — so the layout change has no non-store caller to break.

### 4.2 The mapping module (`resource-path.ts`)

```ts
/**
 * Escape one key segment for filesystem safety. Injective and reversible.
 * `encodeURIComponent` (escapes `/`, space, control chars, and Windows-invalid
 * `< > : " \ | ?`) THEN `.` -> `%2E` and `*` -> `%2A`. Escaping every `.` is
 * load-bearing: it guarantees the ONLY literal `.` in any path component is the
 * structural extension appended to the leaf, so a directory segment can never
 * equal `<base>.md`/`<base>.json`. It also neutralizes `.`/`..` for free
 * (non-traversing, reversible). `*` is the one Windows-invalid char
 * `encodeURIComponent` leaves through, so it is escaped too.
 */
function encodeSegment(segment: string): string;
function decodeSegment(segment: string): string;   // exact inverse: %2E -> ".", then decodeURIComponent

/** Map a resource key to a path RELATIVE to the scope dir, incl. leaf extension. */
export function keyToRelativePath(resourceKey: string, ext: string): string;
//   "concepts/flow-state-dev/overview", ".md"  ->  "concepts/flow-state-dev/overview.md"
//   "a.md/b", ".md"                             ->  "a%2Emd/b.md"  (no collision with "a" -> "a.md")

/** Inverse: reconstruct the resource key from a relative on-disk path. Splits on
 *  `path.sep`, decodes each segment, and rejoins with a literal "/" so a key is
 *  byte-identical across OSes — Windows `\` never leaks into a key, or the
 *  `startsWith(keyPrefix)` filter would diverge from the in-memory store. */
export function relativePathToKey(relPath: string, ext: string): string;

/**
 * Recursively walk `scopeDir`, yielding { resourceKey, absolutePath } for every
 * file whose name ends in `ext`. A record is identified SOLELY by the `ext`
 * suffix — this already excludes crash-orphaned temp files (`<leaf>.md.tmp-<rand>`
 * ends in `.tmp-<rand>`, not `ext`), so no separate `.tmp-` substring match is
 * used (a real key like `build.tmp-1` must not be dropped). Dot-prefixed entries
 * are skipped — both dot-files AND dot-directories — so editor/VCS metadata a
 * vault accumulates (`.obsidian/workspace.json`, `.git/…`) is never descended
 * into and mis-ingested. Reconstructs each key via relativePathToKey, then
 * **canonicalizes defensively** (the vault is user-editable): a filename that
 * does not round-trip — `keyToRelativePath(relativePathToKey(p)) !== p` — is a
 * non-canonical, hand-created path (`a%2Fb.md` decodes to the same key as
 * canonical `a/b.md` and would last-write-win nondeterministically; `100%.md`
 * makes `decodeURIComponent` THROW and would break listing the whole scope). Such
 * entries are skipped with a `console.warn`, never yielded — one stray editor file
 * can't corrupt or crash enumeration. `decodeSegment` is wrapped so a malformed
 * `%`-sequence is caught and treated as non-canonical, not propagated.
 *
 * Legacy flat files are NOT handled here: the clean-break guard (§4.6) runs on
 * first scope access and throws if it detects them, so a walked scope only ever
 * holds new-layout files. This keeps the walk pure. Single source of truth for
 * getAll/getByPrefix.
 *
 * `keyPrefix` (optional) filters at the source (BP-033): the walk STARTS at the
 * deepest directory the prefix's complete leading segments determine (see §4.3),
 * not always `scopeDir` — so a prefixed query never traverses sibling collections.
 * Omitted / empty → walk the whole scope.
 *
 * Symlink-safe: `lstat` the start directory and every directory before descending;
 * a symlinked directory is skipped (not followed). Enumeration must not escape the
 * scope through a symlinked prefix start dir (`scopeDir/files` -> elsewhere) any
 * more than a direct `get`/`set`/`delete` may (§4.2 traversal safety).
 */
export async function collectRecords(scopeDir: string, ext: string, keyPrefix?: string):
  Promise<Array<{ resourceKey: string; absolutePath: string }>>;
```

**Encoding rule (per segment):**
- Split `resourceKey` on `/`.
- `encodeSegment` each: `encodeURIComponent(segment)`, then replace every remaining `.` with `%2E` **and `*` with `%2A`**. `encodeURIComponent` already escapes `/`, whitespace, control chars, and the Windows-invalid `< > : " \ | ?`; the post-pass adds every dot (so `.`/`..`/dotted names are neutralized — non-traversing, reversible, and no encoded name contains a literal `.`) and `*` — the one remaining Windows-invalid character `encodeURIComponent` leaves through (it's in the "unreserved" set). So `files/*/notes` → `files/%2A/notes` and round-trips, rather than surfacing a Windows backend error.
- Join with `path.join`; append the literal-`.` `ext` to the **leaf** only. That appended extension is therefore the sole literal `.` in every path component.
- **Reject-loudly segments (validation, applied to every segment — leaf and directory alike):** an **empty segment** (`a//b`, leading/trailing `/`) and — on Windows — a **reserved device basename** (`con`/`aux`/`nul`/`com1`–`com9`/`lpt1`–`lpt9`, which Windows reserves for directories *and* files, so `con/notes` fails at `mkdir(con/)` too). These are documented unsupported key shapes on the filesystem backend (§11 #4); framework-generated keys never contain them, so `encodeSegment` throws a clear error rather than letting the write surface a bare backend errno. The `resource-path` unit test pins each rejection.
  - **Leading-`.` segments are NOT rejected** — dot-escaping already makes them safe and reversible: a key segment `.env` encodes to `%2Eenv`, `.` to `%2E`, `..` to `%2E%2E`, none of which is dot-prefixed *on disk*. So the store never creates a `.`-prefixed on-disk name, such keys round-trip cleanly, and `collectRecords`'s dot-prefixed skip (which filters *foreign* metadata like `.git`/`.DS_Store`) never drops a real record. (An earlier draft rejected leading-`.` segments, which contradicted the `.`/`..`→`%2E`/`%2E%2E` round-trip requirement; the rejection is removed.)

> The unit test pins every round-trip, including the `%2E` cases (`.`, `..`, `a.md`, `résumé`).

**Injectivity / collision (closes the extension-named-segment hole):** `/` is the only separator; each segment is escaped injectively; every encoded directory name is dot-free; exactly one literal-`.` extension is appended to the leaf. So a directory name can never equal a leaf filename, and distinct keys never collide. The `a` vs `a.md/b` case that a naive scheme would collide (`a` → file `a.md`, `a.md/` needed as a directory) is closed: `a` → `a.md` (file) sits beside `a.md/b` → `a%2Emd/b.md` (directory `a%2Emd`). A leaf `X` (`X.md`) and a branch `X` (`X/…`) still coexist via the extension. `relativePathToKey` strips one trailing `ext` from the leaf and `decodeSegment`s each component.

**Traversal safety:** after building the absolute path, assert `path.resolve(abs)` starts with `path.resolve(scopeDir) + path.sep`; throw otherwise. That is a *string* check and is belt-and-suspenders on top of dot-segment escaping — but it does **not** stop a pre-existing **symlinked directory** inside the (browsable, user-editable) vault from redirecting a nested write outside the scope: if `scopeDir/docs` is a symlink, `set("docs/secret")` would `mkdir`/write through it while the resolved string still begins with `scopeDir`. This is a traversal class the *nested* layout introduces (the old flat layout had no intermediate directories). Guard it on **every** path operation — not just the final write: before `mkdir`/`writeFile` in `set`, and before `readFile` in `get`, and before `rm` in `delete` (a symlinked parent would otherwise let `mkdir` create through it, and let `get`/`delete` read or remove a file outside the scope). Verify no parent segment of the target is a symlink — `lstat` each ancestor, or compare `fs.realpath(dirname(target))` against `realpath(scopeDir)` — and reject if a segment escapes. (`deleteAll` operates on `scopeDir` itself with `rm -rf`, so it needs no per-segment check.) Pin a symlinked-parent case in the store tests.

**Separator normalization.** `keyToRelativePath` builds with `path.join` (OS separator) but `relativePathToKey` rejoins segments with a literal `/`, so a reconstructed key always uses `/` and `startsWith(keyPrefix)` matches the in-memory store on every OS — Windows `\` never enters a key. The segment-as-directory scheme's documented backend key constraints (empty segment, case-folding, Windows device names) are enumerated in **§11 #4**; empty-segment and Windows-device are rejected loudly, and case-folding is a deliberate accepted limitation there. (Leading-`.` segments are supported via dot-escaping, not a constraint — §4.2.)

### 4.3 Data flow

On first access to a scope, the store runs the cheap legacy-detection guard (§4.6); after that every method operates on a pure new-layout tree.

- **`set(scopeType, scopeId, key, value)`**: `target = join(scopeDir, keyToRelativePath(key, ext))`; `mkdir(dirname(target), { recursive: true })`; atomic temp-write + rename (state store keeps its one-shot ENOENT retry loop, now mkdir-ing the leaf's nested parent).
- **`get`**: `readFile(join(scopeDir, keyToRelativePath(key, ext)))`; `ENOENT → undefined`.
- **`getAll` / `getByPrefix`**: `collectRecords(scopeDir, ext, keyPrefix)` → keep each `{resourceKey}` when `resourceKey.startsWith(keyPrefix)` (empty prefix = all); read + (state: `JSON.parse`). **Filter at the source (BP-033):** `collectRecords` does **not** walk the whole scope and then discard — it starts the walk at the deepest directory the prefix's *complete* segments determine. Split `keyPrefix` on `/`; the leading complete segments (all but the last, partial, piece) encode to a start directory `join(scopeDir, ...encodeSegment(seg))`, and the trailing partial piece is matched within it. So `getByPrefix("files/")` walks only `scopeDir/files/`, and `getByPrefix("files/src")` walks `scopeDir/files/` filtering leaves/branches whose name starts with `encodeSegment("src")` — never touching a sibling `notes/` collection. A prefix with no complete leading segment (e.g. `50%_`, matching `50%_off` and `50%_offers` at the top level) falls back to walking the scope root. The final `startsWith(keyPrefix)` still runs on reconstructed keys for exactness (it's the memory-store contract, incl. the partial-segment `50%_` case); the start-directory narrowing is a pure traversal optimization on top. `getAll` (empty prefix) walks the whole scope as before.
- **`delete`**: `rm(target)`; `ENOENT` no-op. **Empty ancestor directories are left in place** — pruning is deliberately *not* done (a non-goal, §8): cosmetic, and reintroduces the concurrent-`mkdir`/write race the state store already fixed.
- **`deleteAll`**: `rm(scopeDir, { recursive: true, force: true })` — **bypasses the legacy guard** (§4.6). `handleDeleteSession` calls `deleteAll` before removing the session record, so a legacy scope must remain *deletable* via the API; running the throw-guard here would strand it (the operator would have to `rm` the path by hand). `deleteAll` removes the directory regardless of layout and clears any per-store guard cache.

### 4.6 Legacy on-disk data — clean break with a loud guard

A store directory written before this change holds flat `encodeURIComponent(wholeKey)` files. This change makes a **clean break**: the new layout does not read them (see §11 #1 for why — pre-1.0, and preserving them robustly proved to be a bug-prone mini-project across several review rounds). But a clean break must not **silently** mis-serve a populated old store (that would violate BP-030's "reject removed keys loudly"), so the store distinguishes a new-layout store from a legacy one by **provenance** and refuses on the legacy one:

- **Durable layout marker — one per store subtree, NOT one shared at `rootDir`.** `createFilesystemStores({ rootDir })` builds a content store rooted at `rootDir/content` and a state store at `rootDir/state`; these two subtrees are populated independently. So the marker lives at **each store's own subtree root** — `rootDir/content/.fsdev-store-layout` and `rootDir/state/.fsdev-store-layout` (JSON `{ "layout": "nested-v1" }`) — and every store checks *only its own* marker against *its own* subtree. A single shared `rootDir/.fsdev-store-layout` would be **wrong**: an empty `content` store could write it while a legacy `state/` subtree still holds old flat files, and the state store would then see a valid marker and skip its rejection — silently hiding the legacy state data. Each marker is written **the first time that store writes data** (see the guard's `set` branch) — never on a read.
- **Guard runs lazily and once per store — never at construction, never mutating on a read.** `createFilesystemStores()` must **not** throw (an upgraded install with legacy data must still construct so the API can call `deleteAll`). The first `get`/`set`/`getAll`/`getByPrefix`/`delete` on a store triggers a **single memoized resolution** — a shared in-flight promise so concurrent first calls all await the *same* result; `deleteAll` and construction skip it. The resolution checks **that store's whole subtree** (`content/` or `state/` in full — see the scope note below):
  - **subtree marker present and valid** (readable JSON, `layout === "nested-v1"`) → new-layout, proceed. **Validate the payload, not just presence:** a stale/corrupt/hand-created marker atop legacy files would otherwise be trusted and silently mis-key; unreadable/wrong-version → `throw` the layout error.
  - **marker absent but the subtree holds legacy data** — a recursive scan (short-circuits on the first hit) finds a **regular file** that is legacy data → `throw` a clear `Error`: *"Filesystem store subtree at `<storeRoot>` predates the nested-layout change; will not read its flat files — move it aside or delete it."* **Scan the *entire* subtree, not just the scope being touched:** a first write to a fresh `content/session/new` must still detect legacy files under `content/session/old`, or it would stamp the marker and later silently miss `old`. **`lstat` each directory before descending and never follow a symlinked directory** (same rule as §4.2) — a user-editable-vault symlink like `content/session/s1/docs` → elsewhere must not let the scan inspect files outside the store or throw based on outside data. **"Legacy data" counts dot-prefixed files** (the old whole-key encode left leading dots, so a legacy `.env` is a flat file named `.env`; skipping it would silently drop data). The scan counts any regular file *except* the marker and a **minimal denylist** of ubiquitous OS/editor/VCS metadata (`.DS_Store`, `Thumbs.db`, `.gitignore`, `.gitkeep`), and it **descends every directory except a denylist of metadata dirs** (`.git/`, `.obsidian/`, `.svn/`, `.hg/`) — it does **not** blanket-skip dot-directories, because a **scope id can legitimately start with a dot** (`userId=".alice"` → legacy data under `content/user/.alice/…`); skipping that would strand it. The denylist can't fully avoid one ambiguity by name: a legacy store whose *only* data lives under a key or scope-id byte-identical to a denylisted name (a resource literally keyed `.gitignore`, say) is the one legacy shape not auto-detected — a documented, accepted micro-limitation (§11 #4; the framework never generates such keys, and `.DS_Store`-as-metadata is vastly more common than `.DS_Store`-as-a-key, so the denylist errs toward the app functioning on macOS). Otherwise the bias is loud: an unknown foreign dotfile throws (recoverable), never silently missed. **Empty directory scaffolding does not count** — `deleteAll` leaves an empty `content/session/` parent, and counting that would keep the guard throwing forever; only files count, so the store unblocks once its data is gone, **with no ancestor pruning**.
  - **marker absent, no legacy data files** (empty, or only empty dirs / denylisted metadata) → the subtree is fresh: **reads return the normal miss** (`undefined`/`{}`/no-op) **without writing anything** (non-mutating read contract preserved — read-only deployments and fresh-root probes behave as before). Writing the marker is a **`set` responsibility, not the resolution's**: every `set` on a not-yet-marked subtree **ensures the marker exists first — atomically (`writeFile` `wx` / ignore-EEXIST) and before its data file** — even if an earlier *read* already cached the "fresh" scan result. This closes the read-then-set gap: a read caches "fresh, unmarked"; a later/concurrent `set` still stamps the marker before any data file lands, so no process (or a restart with a cold cache) ever sees a data file with no marker and misclassifies the fresh store as legacy. Concurrent first `set`s await the shared resolution promise, and the marker write's idempotency makes the race safe.
- **Why a marker, not filename heuristics:** an earlier draft sniffed for `%2F`-containing or extensionless filenames, but that misses a legacy scope whose keys *all* end in the structural extension — a flat `notes.md` for key `notes.md` is byte-identical to a new-layout leaf for key `notes`. The marker keys on *provenance*, not filename shape, so it is unambiguous for every key set.
- **Cost:** one memoized subtree scan per store on first touch (short-circuits on the first legacy file); nothing on the data is written or renamed by the guard itself. The scan is O(files) only for a genuinely fresh or fully-migrated store; a legacy store trips on the first file.
- **If a deployment genuinely needs old data preserved,** that is an explicit, deliberate one-time migration tool (a documented follow-up, §8), designed and tested on its own — not woven into the hot path.

This satisfies BP-030 (old data is never silently mishandled — the store refuses loudly and tells the operator what to do) while keeping the store code a pure new-layout implementation.

### 4.4 Collision guard

A write can hit a genuine filesystem conflict only against pre-existing/foreign data (our own map can't produce one): e.g. a directory already exists where a file must be written, or vice versa. Node surfaces these as `EEXIST` / `ENOTDIR` / `EISDIR`. Wrap `mkdir`/`writeFile`/`rename` so these codes throw a clear `Error` naming the scope, key, and conflicting path ("refusing to write <key>: <path> is a directory") instead of propagating a bare errno or corrupting. This is the "fail loudly" guard the issue asks for.

### 4.5 Error handling summary

| Case | Behavior |
|---|---|
| `get` missing file | `undefined` (ENOENT swallowed) — unchanged |
| `getByPrefix` missing scope dir | `{}` (ENOENT swallowed) — unchanged |
| `set` transient ENOENT (state store) | one-shot mkdir + retry, then propagate — preserved |
| file/dir type conflict on write | throw clear collision error (EEXIST/ENOTDIR/EISDIR) |
| key with `.`/`..` segment | escaped to `%2E`/`%2E%2E`; never traverses |
| segment that is empty / Windows reserved device name (any segment) | rejected loudly in `encodeSegment` (documented backend constraint, §11 #4) |
| leading-`.` segment (`.env`, `.`, `..`) | supported — escaped to `%2Eenv`/`%2E`/`%2E%2E`, round-trips (§4.2); not a constraint |
| populated store with no layout marker (any legacy key shape) | first access `throw`s "legacy layout, will not read — move aside or delete" (§4.6); `deleteAll` bypasses |
| symlinked parent directory in the vault (`scopeDir/docs` → elsewhere) | rejected before write via `lstat`/`realpath` parent check (§4.2), not just the string `startsWith` |
| `delete` missing file | no-op — no pruning (empty dirs left in place; see §8) |

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|---|---|
| Nested key `a/b/c` | dirs `a/b/`, file `c.md`/`c.json` |
| Leaf `a/b` **and** child `a/b/c` both set | `a/b.md` (file) + `a/b/c.md` (file in `a/b/` dir) coexist; no collision |
| Key `50%_off` vs `5000_off`, prefix `50%_` | only `50%_off` matches (string `startsWith`, not path boundary) |
| Key with real extension `files/a.ts` (content) | `files/a%2Ets.md` on disk; round-trips to `files/a.ts` |
| Extension-named directory segment (`a` leaf **and** `a.md/b`) | no collision: `a.md` (file) beside `a%2Emd/` (dir) — every `.` in a segment is escaped |
| Key segment `..` / `.` | escaped to `%2E%2E` / `%2E`, never traverses out of scope dir |
| Key segment containing `*` (`files/*/notes`) | escaped to `%2A` (`files/%2A/notes`); round-trips, Windows-safe |
| Key with empty interior/leaf segment (`a//b`, `a/`) | rejected loudly (documented unsupported shape, §11 #4; framework keys never produce it) |
| Read (`get`/`getAll`) on a fresh/empty markerless subtree | returns miss (`undefined`/`{}`); writes nothing — marker created only on first `set` (§4.6) |
| Legacy store whose only data is a dot-prefixed key (flat `.env`) | counted as legacy data → guard throws (not silently skipped); `.DS_Store` etc. denylisted (§4.6) |
| Concurrent scope create/teardown (state store) | existing one-shot ENOENT retry preserved |
| Pre-existing dir where file must go (foreign data) | throws clear collision error, no corruption |
| Temp file left by a crashed write (`<leaf>.md.tmp-…`) | skipped by `collectRecords` (doesn't end in `ext`); no `.tmp-` substring match, so a real key `build.tmp-1` still resolves |
| Dot-prefixed entry (`.obsidian/`, `.git/`, `.env.md`) | skipped, not descended into (editor/VCS metadata never ingested as a resource) |
| Windows filesystem (`\` separator) | keys reconstructed with `/`, never `\` — cross-OS prefix parity |
| Case-insensitive volume, keys differ only in case | collide (documented limitation, §11) |
| `delete` empties a directory | empty dir left in place (no pruning — harmless, git-invisible; avoids the prune/write race, §8) |
| Legacy store from before this change (any key shape, incl. an all-`notes.md` scope) | no layout marker present + populated `content/`/`state/` → first access `throw`s a clear "legacy layout, will not read" error; clean break, no silent mis-serve (§4.6, §11 #1) |
| Fresh empty store | no marker, no data → marker written, proceeds |
| New-layout store (marker present) | proceeds normally |

**Retryable vs fatal:** transient ENOENT on the state store's write → retry once (existing). Collision (EEXIST/ENOTDIR/EISDIR) and malformed-key → fatal, thrown. Missing file on read/delete → benign, swallowed.

**Discipline:** `fsd:diagnose` (Bug/correctness). Build the feedback loop first, reproduce the flat-file defect, fix at the mapping layer, add regression tests.

**Goal & goal check.** The goal is observable: *a resource stored through the filesystem store lands on disk as a browsable, nested, extensioned file tree*. This is a filesystem outcome, not a real-LLM outcome, so **no real-model goal check applies** — the "real path" here is the store's own `set`→disk, which is exercised directly by the on-disk-assertion tests (they inspect the actual temp directory, not a mock). That is the goal check: a Vitest that writes `concepts/flow-state-dev/overview` and asserts the real file at `…/concepts/flow-state-dev/overview.md`. No `goals/` script and no `fsdev run` are warranted (there is no model behavior to prove).

**Feedback-loop seam:** Vitest at the adapter level (`packages/engine/test/content-store.test.ts`, `resource-state-store.test.ts`) plus a focused unit seam for the mapping (`packages/engine/test/stores/filesystem/resource-path.test.ts`). The mapping unit test is where reproduction and regression live — it fails today's flat behavior would-be and pins every round-trip.

**Regression-test seam:** the two adapter test files (contract + on-disk layout) and the mapping unit test. **Correction / required work:** the engine's own `content-store.test.ts` and `resource-state-store.test.ts` currently run a *separate, inline* suite (`runContentStoreTests`) — they do **not** register the shared `createContentStoreConformanceTests` / `createResourceStateStoreConformanceTests` (only the SQLite and Postgres packages do). So "confirm it stays green" is not enough: this spec **requires wiring the shared conformance suite into both engine filesystem test files** (via `@flow-state-dev/engine/testing`) so the filesystem adapter actually runs the contract cases named in §3.1 — the literal-wildcard prefix (`50%_`), `docs/` nesting, scope isolation — against the reworked layout. The **highest-value existing regression gate** is `resource-state-store.test.ts` "many concurrent writes to a fresh scope" (~lines 184-201), which writes real slash-bearing keys (`holdings/acct__T0`) and asserts round-trip through `getAll` — exactly the case this spec reworks (today those become flat `holdings%2Facct__T0`); it must stay green and now proves nested writes survive the concurrent scope-create race.

**Behaviors to pin (regression):**
- Contract preserved: full conformance suite passes on the nested layout.
- On-disk layout: nested dirs + correct extension for content and state.
- Leaf/branch coexistence at the same key prefix.
- `getByPrefix` string-prefix semantics (the `50%_` case) survive the tree walk, **and** a segment-aligned prefix (`files/`) narrows the walk to that subtree without touching siblings (BP-033).
- Path-traversal segments neutralized.
- Collision guard throws, doesn't corrupt.
- Legacy guard: a populated subtree with no valid marker (incl. all-extension keys, a dot-prefixed scope id, and legacy files under a *sibling* scope of the one being written) makes first touch `throw`; a fresh subtree writes the marker only on first `set` (reads don't); a valid-marker subtree proceeds; concurrent first `set`s resolve once with the marker landing before any data file; the prefix walk doesn't follow a symlinked start dir.

- **OKF adapter reconciliation / frontmatter / schema.** Confirmed independent: the OKF export (`examples/knowledge-base/src/okf/export.ts`) writes YAML-frontmatter `.md` bundles to a **caller-supplied interchange `dir`** over the resource-collection abstraction — it never touches the store's `content/`/`state/` trees. - **Legacy data migration (any form)** — not built. This change is a clean break: old flat files are detected and refused loudly (§4.6), not converted. A deliberate one-time `migrateFilesystemStore(rootDir)` tool — with its own durable manifest, staging, and quarantine design — is a **documented follow-up** if a real deployment ever needs old data preserved; it is intentionally out of scope here (see §11 #1 for why: preserving pre-1.0 data robustly proved to be a bug-prone mini-project across several review rounds, serving data that likely doesn't exist).
- **Content-type inference / per-resource extension opt-in** — not built; `.md` uniform.
- **Empty-ancestor-directory pruning on `delete`** — deliberately not done. It's cosmetic (git doesn't track empty dirs; Obsidian/VS Code render them fine) and reintroduces the concurrent-`mkdir`/write race the state store already fixed once (`resource-state-store.test.ts:184`), now recursively at every nested level; the content store has no retry guard at all. If tidy directories are ever wanted, that's a separate follow-up with an explicit lock/retry design.

*Deepening opportunity — considered, pending owner decision (see §11 #5):* `content-store.ts` and `resource-state-store.ts` are ~90% identical CRUD scaffolding beyond the path math, differing only in (a) serialize/deserialize, (b) leaf extension, (c) the state store's ENOENT-retry loop. Since this spec already rewrites the read/write/enumerate bodies of both, a sibling `createFilesystemResourceStore<T>({ rootDir, ext, serialize, deserialize })` factory — mirroring `shared.ts`'s existing `createFilesystemRecordStore<TRecord, TListOptions>()` — could back both classes from one implementation and, as a bonus, give the content store the same concurrent-scope-creation resilience the state store earned in production. Folding this in vs. deferring is §11 #5.

## 11. Open Questions

1. **Existing on-disk data — RESOLVED: clean break with a loud guard (owner-confirmed).** The approach converged across four review rounds: clean-break → dual-read fallback → lazy per-scope migration → **back to clean break**. Each data-preserving variant proved to be a bug-prone mini-project — the reviewers surfaced stale-read-on-delete, `set` prefix-collisions, enumeration dedup, ambiguous legacy-vs-new detection, stage-before-unlink ordering, per-scope migration locking, and case/Unicode-fold aliasing — all to preserve pre-1.0 filesystem-store data that most likely doesn't exist. **Decision (owner-confirmed):** clean break. The new layout does not read old flat files; instead each store keys on a **durable per-subtree layout marker** (`content/.fsdev-store-layout`, `state/.fsdev-store-layout`, §4.6 — per-subtree, not a shared `rootDir` marker, so an empty `content` store can't mask legacy `state` data) — own-subtree marker absent/invalid on a populated subtree → `throw` a clear, actionable error rather than silently mis-serving. A marker (provenance), not filename heuristics: heuristics silently mis-key a legacy scope whose keys all end in the extension (`notes.md`) or in a non-structural extension (`readme.txt`). This satisfies BP-030's "reject removed keys loudly." A deliberate one-time migration tool is a documented follow-up (§8) if a real deployment ever needs it. **Result:** the entire migration bug-class is gone; the store is a pure new-layout implementation.
2. **Double extension + dot-escaping for extensioned keys** (`files/a.ts` → `files/a%2Ets.md`). Accepted as the deterministic default. **Known, accepted gap vs. the §1 pitch:** a key that already looks like a source file — `files/src/utils.ts` (one of §3.1's own conformance keys) — lands as `utils%2Ets.md` and so will *not* get TypeScript syntax highlighting / native language mode in Obsidian or VS Code (the dot-escaping makes it read even less like a native `.ts` file, in exchange for provable injectivity). The "browsable, opens in an editor's language mode" promise holds for the markdown resources the vault is built around, not for source-file-shaped keys. Content-type inference to fix this is rightly deferred to FIX-367 (inferring a type from a key that may not resemble a filename is its own problem). Flagged as an explicit tradeoff, not a surprise.
3. **OKF adapter overlap — resolved.** The export writes to a separate interchange dir over the collection abstraction, not the store tree; no overlap or duplication. Any consolidation is FIX-813 follow-up, not this issue.
4. **Documented filesystem-backend key constraints (not blockers, from spec-PR review).** The filesystem backend's accepted key set is slightly narrower than the pure in-memory/DB backends, in three documented ways: (a) keys with an **empty segment** (`a//b`, leading/trailing `/`) are rejected loudly rather than silently mis-stored; (b) the layout assumes a **case-sensitive** filesystem; (c) on **Windows**, a reserved device basename (`con`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`) in **any** segment — leaf *or* directory (`con/notes` fails at `mkdir(con/)`, not just `con` as a leaf) — is rejected loudly on write, applied uniformly in `encodeSegment` validation and pinned in the `resource-path` tests. (Leading-`.` segments like `.env` are **not** a constraint — dot-escaping renders them `%2Eenv` on disk, so they round-trip and are never confused with foreign `.git`/`.DS_Store` metadata; §4.2. Likewise `*` is **escaped** to `%2A`, not rejected — the one Windows-invalid char `encodeURIComponent` leaves through; all other Windows-invalid chars `< > : " \ | ?` are already escaped by `encodeURIComponent`.) Constraints (a) and (c) are enforced (rejected loudly), so they never silently mis-store. **Constraint (b) — case-folding — is the one that folds silently, and is a deliberate accepted tradeoff:** on a case-insensitive/normalization-folding volume (default macOS APFS, Windows), keys differing only in case or Unicode form (`Foo`/`foo`, NFC/NFD) map to distinct on-disk names that the OS aliases, so a later `set` overwrites the earlier and enumeration returns one — diverging from the case-sensitive in-memory contract without an error. Failing loudly here would require a case-insensitive `readdir` scan before every write (hot-path cost + TOCTOU-racy), to guard against keys the framework never generates; every file-per-record store (git, Hugo, Obsidian) has the same property. So it stays a **documented limitation**, not a per-write guard. All three are fine for the intended vault use case and for framework-generated keys (which never hit them); the implementer documents them in the store header. With the clean break these are purely *new-write* constraints — no migration path to strand old records; a pre-existing store is caught wholesale by the §4.6 marker guard — **with one narrow legacy-detection carve-out:** a legacy store whose data lives *only* under a key or scope-id byte-identical to a denylisted metadata name (`.DS_Store`, `Thumbs.db`, `.gitignore`, `.gitkeep`, or a `.git`/`.obsidian`/`.svn`/`.hg` directory) is the one legacy shape the guard cannot distinguish from real OS/VCS metadata, so it isn't auto-detected. The denylist deliberately errs this way — `.DS_Store`-as-metadata is vastly more common than `.DS_Store`-as-a-resource-key, and the framework never generates such keys — accepting an astronomically-unlikely un-detected legacy case to keep the store functioning on macOS/VCS-tracked vaults.
5. **Unify the two stores behind one factory? (scope decision).** Beyond the shared path-mapping module, the two store classes are ~90% duplicated CRUD scaffolding. A `createFilesystemResourceStore<T>({ rootDir, ext, serialize, deserialize })` factory (precedent: `shared.ts`'s `createFilesystemRecordStore`) would collapse them to one implementation and give the content store the state store's concurrent-scope-creation resilience. Since this PR already rewrites both bodies, it's the natural moment — but it expands scope from "fix the path layout" to "restructure both store classes." **Owner decision:** fold into this spec (bumps size toward the top of Medium), or note as considered-and-deferred (§8) and keep this spec surgical.
