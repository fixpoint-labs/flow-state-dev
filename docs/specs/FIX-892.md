# FIX-892: MCP transport: support a dedicated single-segment mount path (e.g. `/mcp/:kind`) — Implementation Spec

## 1. TLDR

**Plain-language summary.** Operators should be able to give an MCP client a clean URL such as `/mcp/knowledge-hub` without also moving the application's ordinary flow API. This change adds an opt-in dedicated mounting style while leaving every existing endpoint unchanged. Enabling the style by itself uses the safe, expected `/mcp` prefix, and operators can still choose another prefix.

**One-sentence technical statement.** Add `dedicatedBasePath?: boolean` to `CreateMcpTransportAdapterOptions`; resolve the MCP route as `${basePath}/:kind` in dedicated mode and `${basePath}/:kind/mcp` otherwise, with mode-specific defaults of `/mcp` and `/api/flows` respectively.

**Deliverables:**

- **Add** `dedicatedBasePath` route-layout configuration to `packages/mcp/src/createMcpTransportAdapter.ts`, with `/mcp` as the dedicated-mode default and the current `/api/flows/:kind/mcp` route unchanged by default.
- **Pin** default, explicit dedicated, implicit dedicated-default, trailing-slash, POST, GET, and DELETE behavior in `packages/mcp/test/adapter.test.ts` and `packages/mcp/test/end-to-end.test.ts`.
- **Adopt** the dedicated layout in Knowledge Hub while preserving its secret gate and installation-source forwarding.
- **Extend** the mounting contract and examples in `docs/architecture/mcp-server.md`, `apps/docs/docs/server/mcp.md`, and `packages/mcp/README.md`.
- **Add** a pre-1.0 `patch` changeset for `@flow-state-dev/mcp` under `.changeset/`.

**Size:** **Small** (one package plus the motivating lab config, one PR, with focused tests and docs).

## 2. Overview

Linear issue: [FIX-892](https://linear.app/fixpoint-labs/issue/FIX-892).

`createMcpTransportAdapter` currently owns one hard-coded route layout: a configurable `basePath` followed by `/:kind/mcp`. Changing `basePath` can move the prefix, but it cannot produce the operator-facing `/mcp/:kind` layout because the adapter always adds the final `/mcp` segment.

This spec adds a second, opt-in layout at the adapter boundary. It does not change the built-in HTTP transport, per-flow MCP opt-in, authentication, dispatch, or protocol behavior. Existing callers that omit the new option retain `/api/flows/:kind/mcp` byte-for-byte.

## 3. Background & Research

### 3.1 Current code path

- `packages/mcp/src/createMcpTransportAdapter.ts` normalizes one trailing slash from `basePath`, then constructs the same `${basePath}/:kind/mcp` pattern for POST, GET, and DELETE.
- The adapter returns ordinary `TransportRoute` values. `createFlowApiRouter` compiles non-HTTP adapter patterns at host construction and gives them first-match priority before falling through to the built-in HTTP catch-all.
- The MCP adapter's `basePath` and the built-in HTTP adapter's `basePath` are independent. `createFlowApiRouter` constructs the HTTP adapter on its canonical `/api/flows` prefix, so changing only the MCP adapter does not move ordinary action/session/resource routes.
- `packages/mcp/test/adapter.test.ts` directly exercises adapter bindings and method behavior. `packages/mcp/test/end-to-end.test.ts` wires the adapter through the real router and is the correct seam for proving a URL pattern actually matches before the HTTP catch-all.

### 3.2 Protocol and ecosystem findings

The MCP Streamable HTTP specification requires one HTTP endpoint path for POST and GET, but it does not prescribe that path; its canonical example is `https://example.com/mcp`. The official TypeScript SDK likewise leaves routing to the host framework and shows mounting a handler with `app.all('/mcp', ...)`. Sources: [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#streamable-http) and [official TypeScript SDK server guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/server.md#streamable-http).

That leaves three viable FSD shapes:

1. **Keep the current adapter and require a reverse-proxy or custom-adapter wrapper.** No framework change, but the wrapper must rewrite all three route patterns returned by `createBindings`; it is brittle deployment plumbing for a route the MCP adapter already owns.
2. **Add a free-form route-template option such as `endpointPath: "/mcp/:kind"`.** Most flexible, but it creates validation and precedence rules with `basePath`, permits unsupported dynamic params, and adds configurability beyond the two demonstrated layouts.
3. **Add a dedicated-layout boolean that reuses `basePath`.** Smallest public surface, preserves the established prefix option, and expresses the actual distinction: the prefix is either shared (`/:kind/mcp`) or MCP-exclusive (`/:kind`). This is the selected approach.

### 3.3 Necessity verdict

**Build as scoped.** A caller can technically wrap the public `InboundTransportAdapter` and rewrite the returned route patterns today, but that is not a stable five-line recipe: it must preserve the bindings object, rewrite POST/GET/DELETE together, and track any future MCP routes. The new option adds framework-owned composition at the route-registration boundary, where collision handling and HTTP fallthrough already live. It is not vendor-specific protocol knowledge, and it does not create a grab-bag of MCP method options.

### 3.4 Key Decisions & Ramifications (top 5)

1. **Use `dedicatedBasePath?: boolean`, not a free-form path template.** *Rejected:* `endpointPath: string` / a callback returning arbitrary patterns. *Ramification:* the public surface supports exactly the two evidenced layouts and keeps `:kind` mandatory; a future third layout would require a deliberate API addition rather than being expressible today.
2. **Dedicated mode defaults `basePath` to `/mcp`; shared mode continues to default it to `/api/flows`.** *Rejected:* keeping `/api/flows` as the implicit base in both modes; requiring callers to pair `dedicatedBasePath: true` with `basePath: "/mcp"`. *Ramification:* `createMcpTransportAdapter({ dedicatedBasePath: true })` produces the useful `/mcp/:kind` route instead of unexpectedly claiming `/api/flows/:kind`; documentation must describe the mode-specific default clearly.
3. **Mount one layout per adapter instance, with no compatibility alias or redirect.** *Rejected:* serving both `/api/flows/:kind/mcp` and `/mcp/:kind` when dedicated mode is enabled. *Ramification:* route ownership stays unambiguous and no extra public endpoint appears; adopting dedicated mode is an endpoint migration, so operators must update MCP client URLs when they change the config.
4. **Change only route registration; reuse the same handlers and `:kind` extraction.** *Rejected:* a second dedicated adapter implementation or changes to MCP protocol dispatch. *Ramification:* authentication, origin checks, query forwarding, JSON-RPC handling, action dispatch, and observability cannot diverge between layouts; every future handler change applies to both automatically.
5. **Verify matching through the real router, not only by inspecting route strings.** *Rejected:* unit assertions alone. *Ramification:* the regression suite proves POST reaches MCP and GET/DELETE return 405 at the dedicated URL while the default-route tests remain green; no engine matcher change or new integration-test fixture is needed.

## 4. Technical Design

### 4.1 Public API

Extend the existing exported interface in `packages/mcp/src/createMcpTransportAdapter.ts`:

```ts
export interface CreateMcpTransportAdapterOptions {
  /**
   * Endpoint base path. Defaults to `/api/flows` in shared mode and `/mcp`
   * when `dedicatedBasePath` is true.
   */
  basePath?: string;

  /**
   * Treat `basePath` as MCP-exclusive and mount at `<basePath>/:kind`
   * instead of `<basePath>/:kind/mcp`. Requires a non-root prefix. Defaults to
   * false.
   */
  dedicatedBasePath?: boolean;

  // allowedOrigins and forwardQueryParams unchanged
}
```

No new export is required: `CreateMcpTransportAdapterOptions` is already re-exported from `packages/mcp/src/index.ts`.

### 4.2 Route resolution

Resolve layout once in the factory and continue constructing one shared path for all three methods:

```ts
const dedicatedBasePath = options.dedicatedBasePath ?? false;
const configuredBasePath =
  options.basePath ?? (dedicatedBasePath ? "/mcp" : "/api/flows");
if (dedicatedBasePath && /^\/*$/.test(configuredBasePath.trim())) {
  throw new TypeError("...dedicated basePath must include a non-root prefix.");
}
const basePath = configuredBasePath.replace(/\/$/, "");

// inside createBindings
const path = dedicatedBasePath
  ? `${basePath}/:kind`
  : `${basePath}/:kind/mcp`;
```

The existing one-trailing-slash normalization remains unchanged. Dedicated mode rejects empty or slash-only bases because the resulting `/:kind` route would claim unrelated single-segment paths before the built-in HTTP adapter. Other custom-base behavior remains unchanged.

### 4.3 Route table and data flow

Both layouts feed the exact same path params and handlers:

```text
POST /mcp/knowledge-hub
  → createFlowApiRouter custom-route matcher
  → MCP POST handler, ctx.params.kind = "knowledge-hub"
  → host.resolvePrincipal
  → JSON-RPC dispatch
  → host.dispatch for tools/call
```

GET and DELETE use the same resolved path and retain the existing `405 Method Not Allowed` response. The default layout follows the identical flow at `/api/flows/knowledge-hub/mcp`.

The built-in HTTP adapter is untouched. With the recommended dedicated base (`/mcp`), its `/api/flows/*` route space does not overlap at all. If a caller deliberately supplies an overlapping custom base, existing first-match behavior and non-HTTP exact-route collision checks continue to apply; this feature adds no special collision policy.

The adapter controls routes inside `createFlowApiRouter`; an outer host must
also forward the dedicated prefix to that router. Next.js filesystem routing
requires a sibling `/mcp/[...path]` route, and a Node host mounted only beneath
`/api/flows` requires an additional mount or rewrite. Automatically expanding
host mounts is separate host-integration work and is not part of this adapter
option.

### 4.4 State and errors

No state is created or changed. Route layout is fixed synchronously when the adapter is constructed.

No new runtime error type is introduced. A request to the inactive layout falls through exactly as any unregistered path does today. Missing/unknown flow handling, authorization failures, origin rejection, malformed JSON-RPC, and concurrency errors are unchanged because both layouts reuse the same handlers.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| No options | POST/GET/DELETE stay at `/api/flows/:kind/mcp`; no compatibility break |
| `basePath: "/custom"`, dedicated omitted/false | Existing custom behavior stays `/custom/:kind/mcp` |
| `dedicatedBasePath: true`, base omitted | Uses safe dedicated default `/mcp/:kind` |
| `basePath: "/mcp"`, `dedicatedBasePath: true` | Uses `/mcp/:kind` |
| Dedicated base has one trailing slash | Slash is removed; no double slash in the route |
| Dedicated base is empty or slash-only | Factory throws before registering a broad `/:kind` route |
| POST at dedicated URL | Same JSON-RPC handler and `ctx.params.kind` behavior as default URL |
| GET or DELETE at dedicated URL | 405 with existing `Allow: POST` behavior; no stateful session support added |
| Request sent to the inactive/default URL after dedicated mode is selected | No alias/redirect; route is unregistered and normal router fallthrough applies |
| Unknown or MCP-disabled flow at dedicated URL | Same JSON-RPC method-not-found behavior as the default layout |
| Dedicated prefix overlaps another non-HTTP adapter's exact route | Existing `TransportRouteCollisionError` at router construction |
| Dedicated prefix overlaps the HTTP catch-all | Existing custom-adapter first-match behavior; no new collision rule |

**Retryability:** unchanged. Route selection itself cannot fail. Protocol/dispatch errors retain their existing retryability and response mappings.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (Feature), using red-green-refactor tracer bullets.

**Goal:** an operator can mount each flow's MCP server at `/mcp/<flow-kind>` without moving ordinary `/api/flows` endpoints, while every existing MCP consumer retains the canonical `/api/flows/<flow-kind>/mcp` URL unless it opts in.

**Goal check:** no separate real-model goal script applies. This is route/config plumbing; MCP `initialize` requires no model, and a model run would add no evidence about URL matching. The real-path proof is the end-to-end router test in `packages/mcp/test/end-to-end.test.ts`, which mounts the production adapter in `createFlowApiRouter` and sends synthetic Web `Request` objects through the production method dispatcher. PASS = POST `initialize` returns the MCP server info at `/mcp/billing`, GET/DELETE return 405 there, and the existing default-route tests remain green. FAIL = the request falls into the HTTP catch-all, method behavior differs, or the default path changes.

**Observable behaviors to pin:**

1. With no new option, every generated route path is unchanged.
2. Dedicated mode with no explicit base generates `/mcp/:kind` for POST, GET, and DELETE.
3. Dedicated mode honors an explicit, trailing-slash-normalized base without appending `/mcp`.
4. Existing custom-base shared mode still appends `/:kind/mcp`.
5. Through `createFlowApiRouter`, POST at the dedicated URL reaches MCP and extracts the flow kind.
6. Through `createFlowApiRouter`, GET and DELETE at the dedicated URL preserve the 405 contract.
7. Knowledge Hub exposes its authenticated MCP tools at `/mcp/knowledge-hub`, retains fail-closed mounting, and still forwards the installation `source` query value.
8. Dedicated mode rejects root-only base values before they can shadow unrelated routes.

**Regression seam:** `packages/mcp/test/adapter.test.ts` for pure binding shape; `packages/mcp/test/end-to-end.test.ts` for actual route matching and HTTP fallthrough; `labs/knowledge-hub/test/config.spec.ts` for motivating-app adoption, auth gating, and source forwarding. No `packages/integration-tests/` scenario is warranted because the change does not involve `runAction` composition, store lifecycle, or cross-package flow behavior.

## 8. Non-Goals

- Changing the built-in HTTP adapter's `/api/flows` prefix, route table, or construction in `createFlowApiRouter`.
- Changing the canonical default MCP URL. `/api/flows/:kind/mcp` remains the default and primary backward-compatible form.
- Serving both route layouts simultaneously from one MCP adapter, redirecting between them, or adding endpoint discovery.
- Free-form route templates, callbacks, per-flow path overrides, aliases, hostnames, or subdomain routing.
- Changing MCP protocol behavior: stateful sessions, GET streaming, DELETE termination, OAuth, resources, progress, or JSON-RPC handling.
- Refactoring base-path normalization across MCP, HTTP, and webhook adapters. Their normalization behavior differs today, but this issue adds only a layout choice and does not need a cross-transport abstraction.

No matching rejected direction exists in `docs/internal/out-of-scope/`. No separate architecture-deepening candidate is warranted for this small branch; cross-transport path normalization can be evaluated only if another real inconsistency requires it.
