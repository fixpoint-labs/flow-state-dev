# FIX-893: `fsdev serve` — standalone production server command (no DevTool, no per-app entrypoint script) — Implementation Spec

> Linear: [FIX-893](https://linear.app/fixpoint-labs/issue/FIX-893/fsdev-serve-standalone-production-server-command-no-devtool-no-per-app)

## 1. TLDR

Today, running a flow app in production without the built-in developer UI means hand-writing a little startup script for every app, and copy-pasting a safety check that refuses to expose an unprotected server to the network. We're adding one command, `fsdev serve`, that starts the app's API (and any MCP endpoints) for production with no developer UI, and we're moving that safety check into the framework so it works for any app automatically — no per-app copy-paste, no app-specific secret name baked in. The existing `fsdev dev` stays the local-development command (with the UI); `fsdev serve` is its production counterpart.

**Technical statement:** Add a `fsdev serve` CLI command that loads the app's committed `fsdev.config.*` via `resolveRuntimeSource`, calls `@flow-state-dev/node`'s `serve()` with **no** `staticDir` (defaults `host: $HOST ?? 0.0.0.0`, `port: $PORT ?? 3000`), and gates a non-loopback bind behind a new shared, app-agnostic bind guard in `@flow-state-dev/node` that refuses to expose the network when any served flow's effective principal resolver is the framework default (`defaultBodyUserIdPrincipalResolver`).

**Deliverables:**

- **Server helper:** Add `isLoopbackHost()` and `assertNetworkBindIsAuthenticated()` in `packages/node/src/bind-guard.ts`, exported from `packages/node/src/index.ts`
- **CLI:** Add `registerServeCommand` / `executeServeCommand` in `packages/cli/src/commands/serve.ts`; register in `packages/cli/src/cli.ts`; re-export from `packages/cli/src/index.ts`. Add a `requireConfig?: boolean` mode to `resolveRuntimeSource` (`resolve-runtime.ts`) that errors before discovery. Extract the duplicated `collectValues` helper into a shared `packages/cli/src/cli-options.ts` (imported by `serve`/`dev`/`run`/`chat`)
- **Consumers:** Migrate `examples/knowledge-base` to `fsdev serve` (delete `src/server.ts`, repoint the `serve` script); add a `serve` script to `labs/knowledge-hub/package.json`
- **Docs:** Extend `apps/docs/docs/api/cli.md`, `apps/docs/docs/cli/overview.md`, `apps/docs/docs/devtool/overview.md`, `apps/docs/guides/deployment.md`, and `packages/cli/README.md`; cross-link `cli/configuration.md`, `server/host-adapters.md`, `server/mcp.md`
- **Changesets:** `minor` for `@flow-state-dev/cli` and `@flow-state-dev/node`

**Size estimate:** Medium — multi-file, 1 PR, ~250–450 LOC across two source packages plus docs and two consumer apps.

## 2. Overview

Issue: [FIX-893](https://linear.app/fixpoint-labs/issue/FIX-893/fsdev-serve-standalone-production-server-command-no-devtool-no-per-app).

`fsdev dev` always bundles the DevTool SPA alongside the flow API (`packages/cli/src/commands/dev.ts:203` passes `staticDir`), so there is no CLI path to run a devtools-free production server. The only way to get one today is a hand-written entrypoint that imports the app's config and calls `serve()` directly (`examples/knowledge-base/src/server.ts`), which every production app must duplicate — including a loopback-bind safety guard keyed on that app's own secret env var. This spec adds `fsdev serve` as the production counterpart to `fsdev dev`, and lifts the bind guard into `@flow-state-dev/node` as an app-agnostic primitive.

## 3. Background & Research

### Codebase findings

- **`serve()` already supports the pure-API shape.** `packages/node/src/serve.ts` makes `staticDir` optional (`ServeOptions`, `serve.ts:27-47`); when omitted, `createServerApp` registers only `/healthz` and the API catch-all under `basePath`, and non-API GETs fall through to a `{ error: "Not found" }` 404 (`packages/node/src/app.ts:110-155`). No DevTool is served. Defaults are already production-shaped: `host: "0.0.0.0"` (`serve.ts:108`), `port` via `resolvePort` → `options.port ?? process.env.PORT ?? 3000` (`serve.ts:85-93`). The command is the missing piece, not the server capability.
- **`fsdev dev` is the exact precedent.** It calls `serve(serveApp, { port, host, basePath, staticDir, handleSignals: false })` after `resolveRuntimeSource` (`dev.ts:95-214`), owns its own SIGINT/SIGTERM teardown, and validates `--port`. `serve` is the same path minus `staticDir`, with production bind defaults, and requiring a committed config.
- **`resolveRuntimeSource` is the shared config prelude.** It returns a discriminated union `{ source: "config", flowState, configPath }` | `{ source: "discovery", flows, ... }` (`packages/cli/src/resolve-runtime.ts:54-134`). Config discovery is cwd-only, precedence `fsdev.config.{ts,mts,js,mjs}` (`load-config.ts:27-32`). An explicit `--config <missing>` throws `CliError` (`load-config.ts:76-85`); an absent config with `config !== false` **silently falls back to discovery, which imports and executes any conventional flow modules (side effects, warnings) before returning** — so `serve` must not merely reject `source === "discovery"` after the fact (that runs discovery first). There is **no** "require committed config, no discovery" mode today — `serve` adds one: a new `requireConfig?: boolean` param on `resolveRuntimeSource` that throws a `CliError` when no config is located, *before* `discoverFlows` is ever called (BP-028 — the fix lives in the config prelude that owns discovery, not in each caller).
- **The bind guard is hand-rolled and app-specific.** `examples/knowledge-base/src/server.ts:31-45` defines `isLoopbackHost` (via `node:net`'s `isIP`) and throws when binding a non-loopback host without `KB_MCP_SECRET`. `labs/knowledge-hub` has no entrypoint at all — it overloads `KH_MCP_SECRET=... pnpm fsdev dev` (which also serves the DevTool). No shared helper exists anywhere in `@flow-state-dev/node` (exports are `serve`, `createServerApp` only, `packages/node/src/index.ts:14-17`).
- **Auth is detectable app-agnostically.** Auth is per-flow: `FlowInstance.authentication?.resolvePrincipal` is a public field (`packages/core/src/types/flow.ts:531`; `AuthenticationConfig.resolvePrincipal` at `auth.ts:109`), enumerable via `registry.list(): FlowInstance[]` (`flow-registry.ts:131`) after `await app.getRuntime()`. When a flow supplies no resolver, the framework falls back to `defaultBodyUserIdPrincipalResolver` — which reads `body.userId` verbatim, i.e. the caller names their own principal (`packages/engine/src/transports/auth/defaultBodyUserIdPrincipalResolver.ts:30-40`). That resolver is exported from `@flow-state-dev/engine` (`transports/index.ts:41`, re-exported via `engine/src/index.ts:89`), and `@flow-state-dev/node` already depends on `@flow-state-dev/engine`. So a generic guard can compute `effective = flow.authentication?.resolvePrincipal ?? defaultBodyUserIdPrincipalResolver` and flag `effective === defaultBodyUserIdPrincipalResolver` as unauthenticated — no app secret name required.
- **The guard is a best-effort safety rail, not a security boundary — and its detection is deliberately narrow.** It answers exactly one question: *"is this flow running on the framework's default `defaultBodyUserIdPrincipalResolver`?"* (the common production accident: a secret env var was forgotten, so `resolvePrincipal` stayed `undefined` and fell through to the default that trusts `body.userId`). The real security boundary is `resolvePrincipal` itself; the rail catches the forgot-to-configure case, nothing more. Two known limits of the identity check follow directly from that narrow scope (both raised in spec-PR review), and both are acceptable given the issue's "not a new auth stack" non-goal:
  - **False-positive — host-level auth.** An app that authenticates via the host-level `createFlowState({ resolvePrincipal })` fallback (consumed internally, never surfaced on the `FlowState` handle, `flowstate/types.ts:252-286`) while leaving per-flow `resolvePrincipal` unset is flagged as unauthenticated. Neither in-repo app does this. Escape: `--allow-unauthenticated`. A precise fix (surface `unauthenticatedFlowKeys` on `FlowState.meta`, computed framework-side where the host fallback is visible) is a follow-up (Non-Goals §8).
  - **False-negative — deliberately-wrapped default.** A flow that sets `resolvePrincipal: (ctx) => defaultBodyUserIdPrincipalResolver(ctx)` is equally insecure but has a distinct function identity, so the guard treats it as authenticated. This is out of the rail's intended scope: a hand-written resolver is a deliberate choice the author owns, not the forgot-the-secret accident. Closing it would require an explicit "this flow is authenticated" marker/contract on `AuthenticationConfig` — precisely the "new auth machinery" the issue's non-goals exclude (Non-Goals §8). The docs (§9) and the guard's own error message frame it as a rail, not a guarantee, so operators don't over-trust it.

### Industry research

Not applicable — this is a framework-internal CLI/host-binding change, not a problem with an external best-practice answer. The relevant precedents are all in-repo (`fsdev dev`, `serve()`, the knowledge-base guard). The bind-guard behavior (refuse to expose an unauthenticated server; loopback is the safe default) mirrors the conventional "secure by default, explicit opt-out" posture and matches the existing knowledge-base guard's intent.

### Why this approach

The command wraps the existing `serve()` primitive rather than reimplementing a server (BP-029), mirrors `fsdev dev`'s proven structure (BP-008/conformance), and puts the bind guard in `@flow-state-dev/node` — the layer that owns host binding (BP-028) — so it is reusable by both the command and any future hand-written entrypoint with custom middleware. The generic auth detection is what makes the guard genuinely "shared" (the issue's explicit goal); a literal extraction of the `KB_MCP_SECRET` check could not be reused across apps.

### Key Decisions & Ramifications (top 5)

1. **The bind guard detects unauthenticated flows generically (`resolvePrincipal === defaultBodyUserIdPrincipalResolver`), not via an app secret env var.** *Rejected:* a literal `assertSafeBind({ host, isAuthenticated })` where each caller computes the boolean (knowledge-base passes `!!KB_MCP_SECRET`); the CLI cannot compute that without introspection anyway. *Ramification:* the guard is truly app-agnostic and reusable, and knowledge-base can drop its custom check entirely. It locks the guard to the framework's principal-resolution contract — if that default resolver changes identity or a new "insecure default" is added, the guard must track it. Apps using the host-level `createFlowState({ resolvePrincipal })` fallback are false-positives until that signal is surfaced (escape: `--allow-unauthenticated`).
2. **The guard lives in `@flow-state-dev/node`, not the CLI, and `serve()` stays unchanged.** *Rejected:* baking the guard into `serve()`'s default path (would break existing intentional `0.0.0.0` deployments behind a trusted proxy, and `fsdev dev` / Vercel reuse `serve()`); putting it in the CLI (unreachable by hand-written entrypoints). *Ramification:* the guard is opt-in at the call site, `serve()` is untouched (surgical), and custom-middleware entrypoints can import it. Adds a `@flow-state-dev/node` `minor` changeset (a second package in the PR).
3. **`fsdev serve` requires a committed config; no `--flow-dir` / `--no-config` discovery.** *Rejected:* mirroring `dev`'s discovery fallback. *Ramification:* production runs from a committed, reviewable config — the intended posture — and the implementation reduces to "reject `resolved.source === "discovery"`". It rules out ad-hoc `fsdev serve` in a bare directory; those users get a clear error pointing at `fsdev.config.*`.
4. **`--port` is unset by default so `$PORT` flows through `serve()`'s `resolvePort`; host defaults to `0.0.0.0`.** *Rejected:* a hardcoded default like `dev`'s `"4200"`, which would shadow `$PORT`. *Ramification:* PaaS `$PORT` injection works out of the box (the whole point). A user passing `--port` overrides env, matching `serve()` precedence. This is the inverse of `dev` (loopback, fixed 4200) and must be called out in docs to avoid confusion.
5. **`serve` owns graceful shutdown (`handleSignals: false`); `handle.close()` disposes the config's `FlowState`.** *Rejected:* `handleSignals: true` (serve installs its own handlers but the command still needs to own teardown ordering; splitting signal handling across two owners is what `dev.ts` explicitly avoids). *Ramification:* SIGTERM/SIGINT call `handle.close()` (which disposes the `FlowState` via `createServerApp`, `app.ts:159-167`) then exit 0, mirroring `dev.ts`. No leaked stores on redeploy; shutdown lives in one path. The command additionally disposes on the pre-`serve()` error paths, where `serve()` never took ownership of the `FlowState`.

## 4. Technical Design

### 4.1 New: `packages/node/src/bind-guard.ts`

```ts
import { isIP } from "node:net";
import { defaultBodyUserIdPrincipalResolver } from "@flow-state-dev/engine";
import type { FlowState } from "@flow-state-dev/engine";

/**
 * Loopback binds (127.0.0.0/8, ::1, localhost) are reachable only from the same
 * host and are safe to serve without authentication; any other host is
 * network-exposed.
 */
export function isLoopbackHost(host: string): boolean {
  if (host === "localhost") return true;
  if (isIP(host) === 4) return host === "127.0.0.1" || host.startsWith("127.");
  if (isIP(host) === 6) return host === "::1";
  return false;
}

/**
 * Refuse to bind a network-exposed host when any served flow would run
 * unauthenticated. A flow is unauthenticated when its effective principal
 * resolver is the framework default `defaultBodyUserIdPrincipalResolver` — the
 * caller names their own `userId` in the request body, so a crafted body could
 * act as any principal. Loopback binds and `allowUnauthenticated` are exempt.
 *
 * @throws Error naming the unauthenticated flow kinds when `host` is non-loopback
 *   and at least one served flow is unauthenticated and `allowUnauthenticated`
 *   is not set.
 */
export async function assertNetworkBindIsAuthenticated(
  app: FlowState,
  opts: { host: string; allowUnauthenticated?: boolean },
): Promise<void> {
  if (opts.allowUnauthenticated || isLoopbackHost(opts.host)) return;
  const runtime = await app.getRuntime();
  const unauthenticated = [
    ...new Set(
      runtime.registry
        .list()
        .filter(
          (flow) =>
            (flow.authentication?.resolvePrincipal ?? defaultBodyUserIdPrincipalResolver) ===
            defaultBodyUserIdPrincipalResolver,
        )
        .map((flow) => flow.kind),
    ),
  ]; // registry.list() is per (kind, id); de-dupe kinds as dev.ts:141 does for its banner
  if (unauthenticated.length === 0) return;
  throw new Error(
    `Refusing to bind ${opts.host}: ${unauthenticated.length === 1 ? "flow" : "flows"} ` +
      `${unauthenticated.map((k) => `"${k}"`).join(", ")} ${unauthenticated.length === 1 ? "has" : "have"} ` +
      `no authentication configured, so a network-exposed server would accept a caller-supplied userId. ` +
      `Configure authentication.resolvePrincipal on the flow, bind a loopback host (--host 127.0.0.1) ` +
      `for local-only use, or pass --allow-unauthenticated to override.`,
  );
}
```

Exported from `packages/node/src/index.ts`:

```ts
export { isLoopbackHost, assertNetworkBindIsAuthenticated } from "./bind-guard";
```

Notes: `FlowState` and `defaultBodyUserIdPrincipalResolver` both come from `@flow-state-dev/engine` (already a dependency). `getRuntime()` is memoized (`dev.ts` already calls it), so resolving the runtime here does not double-initialize stores when the command later hands the same `app` to `serve()`.

### 4.2 New: `packages/cli/src/commands/serve.ts`

Follows the `dev.ts` / `run.ts` structure: a `register…` function attaching the subcommand and a testable `execute…` function.

```ts
interface ServeCommandOptions {
  port?: string;
  host?: string;
  config?: string;            // explicit path only; no --no-config
  dotenv?: string[];
  allowUnauthenticated?: boolean;
  cwd?: string;               // test seam, as in dev.ts
}

export function registerServeCommand(program: Command): void {
  program
    .command("serve")
    .description("Start a production server for the flow API and MCP endpoints (no DevTool UI)")
    .option("-p, --port <port>", "Port to listen on (default: $PORT, then 3000)")
    .option("--host <host>", "Host to bind (default: $HOST, then 0.0.0.0)")
    .option("--config <path>", "Path to an fsdev config file (default: fsdev.config.{ts,mts,js,mjs} in cwd)")
    .option("--dotenv <path>", "Load a specific .env file (repeatable, resolved from cwd)", collectValues, undefined)
    .option("--allow-unauthenticated", "Bind a network host even if a flow has no authentication configured")
    .action(async (options: ServeCommandOptions) => {
      try {
        await executeServeCommand(options);
      } catch (err) {
        if (err instanceof CliError) {
          process.stderr.write(err.message + "\n");
          process.exitCode = err.exitCode;
          return;
        }
        process.stderr.write(`Unexpected error: ${err instanceof Error ? err.message : String(err)}\n`);
        process.exitCode = EXIT_INTERNAL_ERROR;
      }
    });
}
```

`executeServeCommand`:

1. **Validate `--port` if provided** (mirror `dev.ts:81-84`): `parseInt(options.port, 10)`, reject `NaN`/out-of-range with `CliError(..., EXIT_CONFIG_ERROR)`. If omitted, leave `port` `undefined` so `serve()` applies `$PORT ?? 3000`.
2. **Resolve config, config-only** — `resolveRuntimeSource({ cwd: options.cwd, config: options.config ?? true, dotenv: options.dotenv, requireConfig: true })`. This new `requireConfig` param (added to `ResolveRuntimeParams` in `resolve-runtime.ts`) short-circuits **before** the discovery fallback: after `loadFsdevConfig` returns `undefined`, `resolveRuntimeSource` throws a `CliError(EXIT_CONFIG_ERROR)` instead of calling `discoverFlows`. This matters — the current post-hoc "reject `source === "discovery"`" approach would first run discovery, importing/executing conventional flow modules (side effects, warnings) in a repo that has them, contradicting the no-discovery production path (raised in spec-PR review). The thrown message:
   ```
   fsdev serve requires a committed fsdev.config.{ts,mts,js,mjs} in <cwd>. Production
   servers must run from a committed config, not directory discovery. Create one, or
   pass --config <path>.
   ```
   `requireConfig` is additive and inert for `dev`/`run`/`chat` (they don't pass it). An explicit `--config <missing>` already throws inside `loadFsdevConfig` before this. With `requireConfig`, a successful return is always `source: "config"`, so no `source` re-check is needed in the command.
3. **Resolve host + bind guard** — `host = options.host ?? process.env.HOST ?? "0.0.0.0"`. The `$HOST` fallback is symmetric with `$PORT` and **preserves the knowledge-base entrypoint's behavior** (its `src/server.ts` reads `process.env.HOST ?? "0.0.0.0"` and documents `HOST=127.0.0.1` for local-only use, raised in review) — without it, migrating that app to `fsdev serve` would silently bind `0.0.0.0` under `HOST=127.0.0.1`. Then `await assertNetworkBindIsAuthenticated(resolved.flowState, { host, allowUnauthenticated: options.allowUnauthenticated })`. On throw, `await resolved.flowState.dispose().catch(() => {})` then rethrow as `CliError(err.message, EXIT_CONFIG_ERROR)`.
4. **Serve** — `const handle = await serve(resolved.flowState, { host, port, basePath: "/api/flows", handleSignals: false })` (no `staticDir`). On `serve()` rejection, dispose the flowState and rethrow **as `CliError(EXIT_CONFIG_ERROR)`** — a listen failure (`EADDRINUSE`, `EACCES`) is an operational misconfiguration a deployment script should see as exit 3, not the `EXIT_INTERNAL_ERROR` (10) a raw rethrow would produce (raised in review; keeps §4.4 and the §9.3 exit-code note consistent). This differs from `dev.ts`, which rethrows raw — acceptable, since `serve` is the production surface where a clean, script-actionable exit code matters.
5. **Banner + shutdown** — write a startup banner to **stderr** (host, port, base path, MCP note); register SIGINT/SIGTERM handlers (with a re-entry guard, as `dev.ts:232-242`) that `await handle.close()` then `process.exit(EXIT_SUCCESS)`. Do **not** call `flowState.dispose()` here: `handle.close()` already disposes the `FlowState` passed to `serve()` (via `createServerApp`'s dispose, `packages/node/src/app.ts:159-167`) — `dev.ts` relies on the same and does not dispose separately. The explicit `flowState.dispose()` belongs only on the **pre-`serve()` error paths** (guard failure in step 3 and `serve()` rejection in step 4), where `serve()` never took ownership — matching `dev.ts:207-214`.

`collectValues` (the repeatable-option accumulator) is currently a **per-file private helper** copied identically into `dev.ts:46`, `run.ts:84`, and `chat.ts:30`. Rather than add a **fourth** copy to `serve.ts` — which would compound a standing violation of CLAUDE.md's "common helpers belong in a shared utils file — no duplicate copies" rule (raised in spec-PR review) — **extract it once** into a new flat module `packages/cli/src/cli-options.ts` (alongside the package's other flat shared modules, `exit-codes.ts` / `load-config.ts`) and have all four commands import it. This is a small, behavior-preserving refactor folded into this PR: remove the three existing inline copies, `serve.ts` imports the shared one from the start. No changeset of its own (internal refactor, no user-facing change; the command's `@flow-state-dev/cli` changeset covers the PR).

Registration (`packages/cli/src/cli.ts`): add `import { registerServeCommand } from "./commands/serve";` and `registerServeCommand(program);`. Re-export (`packages/cli/src/index.ts`): `export { registerServeCommand, executeServeCommand } from "./commands/serve";`.

### 4.3 Data flow

`fsdev serve` → `resolveRuntimeSource` loads `.env`, then the committed `fsdev.config.*` (default export `FlowState`) → command inspects the resolved runtime's flow registry for unauthenticated flows → hands the same `FlowState` to `serve()` → `serve()` builds the Hono app via `createServerApp` (API + `/healthz`, no static) → binds `host:port`. No new stores, no new engine path. The config's own adapters (e.g. `createMcpTransportAdapter`) mount as they do under `fsdev dev`, just without the DevTool assets.

### 4.4 Error handling

| Case | Handling |
|---|---|
| Invalid `--port` | `CliError(EXIT_CONFIG_ERROR)` before any config load |
| No committed config found | `CliError(EXIT_CONFIG_ERROR)` — clear "requires committed config" message; no discovery |
| `--config <missing path>` | `CliError` from `loadFsdevConfig`/`locateConfig` (existing) |
| Non-loopback bind, ≥1 unauthenticated flow, no override | `assertNetworkBindIsAuthenticated` throws → `CliError(EXIT_CONFIG_ERROR)`; flowState disposed |
| `serve()` fails to bind (port in use, EACCES) | flowState disposed; rethrown as `CliError(EXIT_CONFIG_ERROR)` (exit 3) — an operational misconfiguration, not an internal bug |
| SIGTERM/SIGINT | Graceful: `handle.close()` (disposes the `FlowState` via `createServerApp`) → exit 0 |

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| `--host 127.0.0.1` (loopback), unauthenticated flow | Allowed — loopback is exempt; server starts |
| `--host 0.0.0.0`, all flows authenticated | Allowed — guard passes |
| `--host 0.0.0.0`, unauthenticated flow, `--allow-unauthenticated` | Allowed — explicit override; server starts |
| `--host ::1` | Treated as loopback (`isLoopbackHost`) |
| App uses host-level `createFlowState({ resolvePrincipal })` only | **False-positive**: guard flags flows as unauthenticated (host fallback is not observable). Escape: `--allow-unauthenticated`. Documented limitation; follow-up in §8 |
| Flow wraps the default: `resolvePrincipal: (ctx) => defaultBodyUserIdPrincipalResolver(ctx)` | **False-negative**: distinct function identity, so the guard treats it as authenticated and permits the bind. Out of scope for a best-effort rail (a hand-written resolver is deliberate, not the forgot-the-secret accident); closing it needs an explicit auth marker — the "new auth machinery" the issue excludes (§8) |
| `$PORT` set, no `--port` | `serve()` binds `$PORT` |
| Neither `$PORT` nor `--port` | `serve()` binds `3000` |
| `$HOST=127.0.0.1` set, no `--host` | Binds loopback (guard exempt) — preserves the knowledge-base entrypoint behavior after migration |
| `--host` given and `$HOST` set | `--host` wins (explicit flag over env) |
| `serve()` listen failure (`EADDRINUSE`/`EACCES`) | `CliError(EXIT_CONFIG_ERROR)` (exit 3) |
| `--port 70000` | `CliError(EXIT_CONFIG_ERROR)` — out of range |
| Config present but exports a non-`FlowState` | Existing `loadFsdevConfig` validation error (`isFlowState`) |
| Multiple flows, mixed auth | Guard fails if *any* served flow is unauthenticated; message lists the offending kinds |

Error taxonomy: config/validation/guard failures are **fatal** (`CliError`, non-zero exit, no retry). A failed bind is fatal. There are no retryable errors in this command.

## 7. Testing Strategy

**Goal:** an operator can run `fsdev serve` from an app with a committed config and get a long-lived production server exposing the flow API and MCP endpoints with no DevTool UI, PaaS-friendly bind defaults, and a refusal to expose an unauthenticated flow to the network.

**Goal check:** no real-LLM goal check applies — the command has no model in the loop; its observable outcome is server behavior, not generation (per AGENTS.md, server/CLI behavior is verified by driving the process, not `fsdev run` against a model). The out-of-CI check is a **manual/scripted server probe**, run by hand from `labs/knowledge-hub`:

1. `KH_MCP_SECRET=test pnpm fsdev serve` → server logs a startup banner; `curl -s -o /dev/null -w '%{http_code}' localhost:3000/healthz` → `200`.
2. `curl -s -o /dev/null -w '%{http_code}' localhost:3000/index.html` → `404` (no DevTool SPA fallback — the discriminator vs `fsdev dev`).
3. `curl -sX POST localhost:3000/api/flows/knowledge-hub/mcp` with a valid bearer → MCP responds; `GET`/`DELETE` → `405`.
4. Guard: with a flow whose `resolvePrincipal` is unset, `pnpm fsdev serve --host 0.0.0.0` → exits non-zero with the "Refusing to bind" message; `--host 127.0.0.1` → starts; `--allow-unauthenticated` → starts.

PASS = all four hold. FAIL = a DevTool asset is served, `$PORT`/`3000` defaults are wrong, or the guard fires/omits incorrectly.

**Discipline:** `fsd:tdd` (Feature). Tracer-bullet behaviors (CI, deterministic, following `packages/cli/test/dev-command.test.ts` — assert on decisions that resolve **before** `serve()` binds a port, since binding starts a long-lived process whose shutdown calls `process.exit`):

- **`bind-guard` unit specs** (`packages/node/test/bind-guard.test.ts`):
  1. `isLoopbackHost` — `true` for `localhost`, `127.0.0.1`, `127.5.6.7`, `::1`; `false` for `0.0.0.0`, a public IPv4, a hostname.
  2. `assertNetworkBindIsAuthenticated` resolves (no throw) for a loopback host regardless of auth.
  3. Throws for a non-loopback host when a flow's `resolvePrincipal` is undefined (falls to default); message names the flow kind.
  4. Resolves for a non-loopback host when every flow has a non-default `resolvePrincipal`.
  5. Resolves when `allowUnauthenticated: true`, even with an unauthenticated flow on a non-loopback host.
  Build the `FlowState` fixtures with the testing harness / a minimal `createFlowState` over one or two `defineFlow`s (one with `authentication.resolvePrincipal`, one without), mirroring existing node/engine test setup.
- **`serve` command specs** (`packages/cli/test/serve-command.test.ts`), driven by `cwd` pointing at `test/fixtures-config/*` and never reaching `serve()`:
  6. Invalid `--port` → `CliError`, `EXIT_CONFIG_ERROR`.
  7. `cwd` with no `fsdev.config.*` (a discovery-only fixture) → `CliError` with the "requires committed config" message, `EXIT_CONFIG_ERROR`.
  8. `cwd` with a config whose flow is unauthenticated + default `--host 0.0.0.0` → `CliError` from the guard (flowState disposed).
  9. Same config with `--host 127.0.0.1` → passes the guard (stub/spy `serve` or assert the code path reaches the bind — see note).

  Note for specs 8–9: unlike `dev-command.test.ts`, these need to exercise the guard, which runs *before* `serve()`. Keep them pre-bind by asserting on the guard outcome; for the "passes guard" case, either (a) inject a fixture whose flow is authenticated so the guard passes and then stub `@flow-state-dev/node`'s `serve` to a no-op via `vi.mock` (the one place this package should mock `serve`, justified because the assertion is specifically that the guard let control through), or (b) split the guard call into a unit already covered by specs 2–5 and keep the command spec to the config/validation branches only. Prefer (b) to stay consistent with the package's "assert pre-`serve` decisions, don't mock `serve`" convention; use (a) only if coverage of the command's own guard wiring is deemed necessary.

**Reference test files:** `packages/cli/test/dev-command.test.ts` (validation/config branches, `process.env` save/restore), `packages/cli/test/run-command.integration.test.ts` (stdout/stderr capture, store injection). `packages/cli/test/fixtures-config/<name>/` for config fixtures.

## 8. Non-Goals

- **Not replacing `@flow-state-dev/vercel`'s serverless handlers.** `fsdev serve` is the long-lived-process target; Vercel is a separate deployment path with its own command surface.
- **No new auth machinery.** The bind guard is a best-effort safety rail over whatever `authentication.resolvePrincipal` already implements — it does not add authentication, only detects the framework's *default* (unconfigured) resolver. It deliberately does **not** introduce an explicit "this flow is authenticated" marker/contract on `AuthenticationConfig`: that is new auth surface, out of scope here, and would be the path to closing the wrapped-default false-negative (§3) if the project later decides the rail should be exact rather than best-effort.
- **No `--flow-dir` / `--no-config` discovery mode** for `serve` (Key Decision 3).
- **No `-m/--model` override on `serve`.** `dev` rejects `--model` when a config is loaded; since `serve` *requires* a config, the flag would always error — omit it (BP-038).
- **Not baking the guard into `serve()`'s default path** (Key Decision 2) — it stays an opt-in helper.
- **Not adopting FIX-892's `dedicatedBasePath`.** `serve` mounts at the config's existing paths. When FIX-892 lands, a config can adopt `createMcpTransportAdapter({ basePath: "/mcp", dedicatedBasePath: true })` independently; `serve` needs no change.

**Deepening opportunity flagged (follow up via `fsd:improve-codebase-architecture`, not in scope):**

- **Host-level auth fallback is not observable on the `FlowState` handle** (`createFlowState({ resolvePrincipal })` is consumed internally, `flowstate/types.ts:252-286`). This forces the `--allow-unauthenticated` escape for apps that authenticate at the host level. The clean fix is to surface a derived signal on `FlowState.meta` (e.g. `unauthenticatedFlowKeys: string[]`, computed by the same `=== defaultBodyUserIdPrincipalResolver` test), letting the guard be exact with zero false-positives. Small engine change; deferred to keep this issue scoped.
