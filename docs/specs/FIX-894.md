# FIX-894: DevTool transport auth for bearer-gated flows — Implementation Spec

> **Linear:** [FIX-894](https://linear.app/fixpoint-labs/issue/FIX-894/devtool-bearer-auth-for-secured-flows-dispatch-error-surfacing). Motivated by knowledge-hub ([FIX-882](https://linear.app/fixpoint-labs/issue/FIX-882)) DevTool failures; generalizes to any flow using `createBearerSecretPrincipalResolver`.

## 1. TLDR

**Plain-language summary.** When you run DevTool against a flow that requires a bearer token (like knowledge-hub with `KH_MCP_SECRET` set), creating a session works but sending an action appears to do nothing. The request fails on auth before execution starts, and DevTool never shows the error. This spec adds an optional, clearable bearer-token field to DevTool settings (token set → send `Authorization`; token cleared → no header), threads it through every HTTP call the panel makes, surfaces dispatch failures in the UI, and relaxes knowledge-hub's HTTP auth so local DevTool works without a secret while production keeps bearer required when `KH_MCP_SECRET` is set.

**One-sentence technical statement.** Extend `@flow-state-dev/devtool` and `@flow-state-dev/client` transport wiring so DevTool injects `Authorization: Bearer <token>` only when a non-empty token is configured (clearable in Settings), surface `useActionDispatch` errors in the action bar, expose optional `authentication.principalUserId` / `requiresBearer` hints on `GET /api/flows`, and change knowledge-hub to use bearer auth only when `KH_MCP_SECRET` is set (otherwise HTTP falls back to body `userId` for local DevTool).

**Deliverables:**

- **DevTool:** add clearable `bearerToken` to `DevToolConfig`, persist it in standalone mode (`readBearerToken` / `writeBearerToken` in `packages/devtool/src/react/config.ts`), expose it in `SettingsSheet` (empty = no auth header), build a shared `createAuthFetcher(token)` wrapper, thread `fetcher` through `buildClients`, `dispatchDevToolAction`, and `connectRequestStream`.
- **DevTool:** render `useActionDispatch().error` in `ActionBar` via `ErrorAlert` (dismiss on next send).
- **Core + engine:** add optional `authentication.principalUserId?: string` and `authentication.requiresBearer?: boolean` on `defineFlow` auth config; include both on `GET /api/flows` list entries.
- **Client:** extend `FlowListEntry` with `principalUserId?: string` and `requiresBearer?: boolean`.
- **knowledge-hub:** when `KH_MCP_SECRET` is set → bearer resolver + `principalUserId: "owner"` + `requiresBearer: true`; when unset → `resolvePrincipal: undefined` (body `userId` HTTP, local DevTool without token). MCP adapter mount stays gated on secret. Update README + tests.
- **Docs:** new `apps/docs/docs/devtool/authentication.md`; cross-links from `devtool/setup.md` and `server/authentication.md`.
- **Changesets:** `patch` on `@flow-state-dev/devtool`, `@flow-state-dev/core`, `@flow-state-dev/client`, `@flow-state-dev/engine` (list-flows shape only).

**Size estimate:** **Medium** — multi-package, 1 PR, ~300–450 LOC. Includes knowledge-hub auth resolver change (HTTP only; MCP mount still secret-gated).

## 2. Overview

**Problem:** DevTool sends flow actions with `userId` in the JSON body only. Flows that use `createBearerSecretPrincipalResolver` (knowledge-hub, knowledge-base prod, scheduled-dispatch patterns) require `Authorization: Bearer <secret>`. Without the header, `resolvePrincipal` returns `null` and the host rejects with `Action request requires non-empty userId` (HTTP 400). DevTool catches the error in `useActionDispatch` but `DevToolPanel` never renders it, so the UI looks idle.

**Secondary problem:** Bearer-gated flows often resolve to a **fixed** principal (`{ userId: "owner" }`) while DevTool defaults to `devuser`. Session creation trusts body `userId` (no bearer), so sessions are created as `devuser`. Action dispatch resolves to `owner`, triggering `UserBindingMismatchError` even after bearer is fixed.

**Outcome:** Two local-dev paths both work:
1. **No secret** — `pnpm fsdev dev` in knowledge-hub without `KH_MCP_SECRET`; DevTool with bearer token cleared, normal `devuser` (or any body userId).
2. **Secret set** — `KH_MCP_SECRET=test pnpm fsdev dev`; DevTool Settings → bearer token `test`, user id `owner` (or sync from `principalUserId` hint); actions require matching bearer on both sides.

## 3. Background & Research

### 3.1 Reproduced failure (2026-07-13)

| Step | Result |
|------|--------|
| `POST .../actions/logActivity` without `Authorization` | `400 {"error":"Action request requires non-empty userId"}` |
| Same with `Authorization: Bearer test` + session `userId: devuser` | `202` accepted, then `UserBindingMismatchError` at execution |
| Same with bearer + session created as `owner` | `202`, request `completed`, inbox write succeeds |

Session file evidence: `labs/knowledge-hub/.fsdev/data/sessions/sess_*.json` shows `"userId": "devuser"` from DevTool defaults.

### 3.2 Current DevTool request path

1. `ActionBar` → `DevToolPanel.handleSendAction` → `useActionDispatch.sendAction`
2. `dispatchDevToolAction` → `createClient({ flowKind, userId, baseUrl })` — **no `fetcher`**
3. `client.sendAction` → `requestJson` with headers `{ "content-type": "application/json" }` only
4. Parallel paths (sessions, recovery, debug, SSE) also omit auth

`ClientTransportOptions.fetcher` already exists (`packages/client/src/types/index.ts`) and is the established extension point — no app in the monorepo uses it for bearer auth today.

### 3.3 Analogous patterns

| Pattern | Location | Relevance |
|---------|----------|-----------|
| `createBearerSecretPrincipalResolver` | `packages/engine/src/transports/auth/createBearerSecretPrincipalResolver.ts` | Server-side; returns `null` when header absent |
| MCP tests with `Authorization: Bearer test-secret` | `labs/knowledge-hub/test/config.spec.ts` | Proves authenticated HTTP works |
| `ErrorAlert` in flow list / session context | `packages/devtool/src/react/components/shared/error-alert.tsx` | Existing UI for surfacing errors |
| `readUserId` / `writeUserId` localStorage | `packages/devtool/src/react/config.ts` | Pattern for persisting standalone settings |
| knowledge-hub env-gated auth | `labs/knowledge-hub/src/flow.ts`, README | Motivating flow; secret set → bearer, unset → open HTTP |

### 3.4 Industry / ecosystem

DevTools and API consoles (Postman, Insomnia, OpenAPI explorers) universally support per-environment auth headers. Bearer token in settings is the minimal viable shape; generic header maps are more flexible but heavier to build and validate. Start with bearer — covers knowledge-hub, knowledge-base, and scheduled-dispatch flows without inventing a DevTool-specific auth protocol.

### 3.5 Necessity verdict

**Build as scoped.**

- **Existing primitive:** `createClient({ fetcher })` can wrap `fetch`, but DevTool never exposes it; an operator cannot configure auth without forking DevTool or embedding a custom panel.
- **What the spec adds:** First-class DevTool settings + threading across all panel HTTP paths + user-visible errors + flow metadata for principal alignment. Not a one-line wrapper — six call sites in DevTool must share the same fetcher.
- **Not building:** A DevTool-specific auth protocol, JWT parsing, or changes to `resolvePrincipal` semantics beyond knowledge-hub's env-gated HTTP branch.

### 3.6 Key Decisions & Ramifications (top 6)

1. **Symmetric optional bearer (client + server).** Token/secret present → require bearer on HTTP; absent → no bearer required. *Rejected:* always fail-closed HTTP when secret env exists anywhere in the deployment; DevTool always sending a header slot. *Ramification:* local `pnpm fsdev dev` without `KH_MCP_SECRET` works with DevTool bearer cleared; production sets secret on both server and client. MCP endpoint mount stays secret-gated (unchanged).

2. **Use `fetcher` wrapper, not `SendActionOptions.headers`.** *Rejected:* per-request headers on `sendAction` only. *Ramification:* one `createAuthFetcher(bearerToken)` covers actions, sessions, recovery, debug, and SSE; empty/cleared token → passthrough fetch with no `Authorization` header.

3. **Bearer-only setting in DevTool v1 (`bearerToken: string`, clearable).** *Rejected:* arbitrary header map in settings UI. *Ramification:* operator clears the field (or saves empty) to opt out of client-side auth; covers bearer-gated flows when needed. HMAC/JWT flows still use embedded `fetcher`.

4. **Add `authentication.principalUserId` + `requiresBearer` on flows (opt-in metadata).** *Rejected:* hard-coding `owner` in DevTool; silently overriding userId from env. *Ramification:* knowledge-hub sets both only when `KH_MCP_SECRET` is set at import time; DevTool shows bearer/userId hints only when `requiresBearer` is true on the active flow.

5. **Do not run session creation through `resolvePrincipal`.** *Rejected:* changing `handleCreateSession` to require bearer. *Ramification:* session routes stay simple; alignment is client-side when bearer mode is active.

6. **Surface dispatch errors inline in ActionBar, not a toast system.** *Rejected:* global notification layer. *Ramification:* matches existing `ErrorAlert` usage; HTTP errors visible when auth fails.

## 4. Technical Design

### 4.1 `createAuthFetcher` (devtool internal)

New file: `packages/devtool/src/react/lib/auth-fetcher.ts`

```ts
import type { ClientFetch } from "@flow-state-dev/client";

/** Wrap the global fetch to inject Authorization when a non-empty token is set. */
export function createAuthFetcher(
  bearerToken: string | undefined,
  baseFetcher: ClientFetch = fetch
): ClientFetch {
  const token = bearerToken?.trim();
  if (!token) return baseFetcher;
  return (input, init) =>
    baseFetcher(input, {
      ...init,
      headers: {
        ...(init?.headers ?? {}),
        authorization: `Bearer ${token}`,
      },
    });
}
```

Use lowercase `authorization` — `Headers` normalizes; matches `createBearerSecretPrincipalResolver` default `headerName`.

### 4.2 DevTool config surface

Extend `DevToolConfig` (`packages/devtool/src/react/lib/client.ts`):

```ts
export type DevToolConfig = {
  userId: string;
  bearerToken?: string;
};
```

Extend `DevToolProvider` props:

```ts
export type DevToolProviderProps = {
  // existing...
  /** Initial bearer token. Standalone shell persists via localStorage; embedded hosts supply from server. */
  initialBearerToken?: string;
  /** When "internal", SettingsSheet edits bearer token. When "host", host owns it. Default "internal". */
  bearerTokenControl?: "internal" | "host"; // parallel to userIdControl
};
```

`packages/devtool/src/react/config.ts`:

```ts
const BEARER_TOKEN_KEY = "fsdev.devtool.bearerToken";

export function readBearerToken(): string;
export function writeBearerToken(token: string): void;
```

Persist on `setConfig` when `bearerTokenControl === "internal"` (mirror `userId`).

### 4.3 Thread fetcher through all DevTool clients

`buildClients` in `devtool-context.tsx`:

```ts
function buildClients(config: DevToolConfig, baseUrl: string | undefined) {
  const fetcher = createAuthFetcher(config.bearerToken);
  return {
    client: createDevToolClient(config, baseUrl, fetcher),
    sessionClient: createDevToolSessionClient(baseUrl, fetcher),
    recoveryClient: createDevToolRecoveryClient(baseUrl, fetcher),
  };
}
```

Update factories to accept optional `fetcher` as third arg (or fold into a small options bag — match existing `ClientTransportOptions`).

`dispatchDevToolAction`:

```ts
export function dispatchDevToolAction(..., options: { userId: string; baseUrl?: string; bearerToken?: string }) {
  const fetcher = createAuthFetcher(options.bearerToken);
  const client = createClient({ flowKind, userId: options.userId, baseUrl: options.baseUrl, fetcher });
  ...
}
```

`connectRequestStream` — add `fetcher?: ClientFetch` and pass to `createSSEClient`.

`useActionDispatch` — pass `config.bearerToken` into `dispatchDevToolAction`.

### 4.4 Settings UI

`SettingsSheet` additions (when `bearerTokenControl === "internal"`):

- Label: **Bearer token**
- `<Input type="password" autoComplete="off">` — masks token in UI; **clearable** (save empty string to remove)
- Helper text: *Leave blank for no auth header. When the server requires bearer (e.g. `KH_MCP_SECRET` is set), enter the matching secret.*
- **Clear** affordance: saving with an empty field calls `writeBearerToken("")` and removes persisted token from localStorage
- Save alongside `userId`

When `bearerTokenControl === "host"`: same copy as userId — "owned by host application."

**Client rule:** `createAuthFetcher` treats whitespace-only the same as empty — no `Authorization` header is sent.

### 4.5 Principal userId hint and DevTool sync

**Core** — extend auth config type (`packages/core/src/types/flow.ts`):

```ts
authentication?: {
  resolvePrincipal?: PrincipalResolver;
  defaultUserId?: string;
  requireUser?: boolean;
  requireOrg?: boolean;
  /**
   * When resolvePrincipal always yields the same userId (e.g. bearer-secret
   * flows), declare it here so clients (DevTool) can align session userId.
   * Informational only — not used by the runtime resolver.
   */
  principalUserId?: string;
  /**
   * When true, HTTP clients (DevTool) should send bearer auth and align
   * session userId with principalUserId. Set at flow import time when the
   * bearer secret env is present. Informational only.
   */
  requiresBearer?: boolean;
};
```

**Engine** — include on list flows (`packages/engine/src/routes/http-handlers.ts`):

```ts
flows: registry.list().map((flow) => ({
  // existing fields...
  principalUserId: flow.authentication?.principalUserId,
  requiresBearer: flow.authentication?.requiresBearer,
}))
```

**Client** — `FlowListEntry.principalUserId?: string` and `requiresBearer?: boolean`.

**DevTool** — in `DevToolPanel` or a small `usePrincipalUserIdHint(activeFlowKind, flows, config)` hook:

- Hints render **only when** `activeFlow.requiresBearer === true`
- When `principalUserId` is set and `config.userId !== activeFlow.principalUserId`:
  - Show compact banner above ActionBar: *This flow expects user id `{principalUserId}` for bearer auth. Current: `{config.userId}`.*
  - Button: **Use {principalUserId}** → `setConfig({ userId: principalUserId })`
- When `requiresBearer` and `!config.bearerToken?.trim()`:
  - Banner: *Bearer token required for this flow — add it in Settings, or clear server secret for local open access.*

Do **not** auto-sync without user action (BP-038 — no silent identity changes).

### 4.6 Dispatch error surfacing

`DevToolPanel`:

```ts
const { sendAction, isSending, lastResponse, error: dispatchError } = useActionDispatch();
```

Pass `dispatchError` to `ActionBar`. Render above send row:

```tsx
{dispatchError && <ErrorAlert message={dispatchError} />}
```

Clear `dispatchError` on successful send (already cleared at start of `sendAction`).

Improve error message for `ClientHttpError` — include status and server `error` body field when present (`packages/devtool/src/react/hooks/use-action-dispatch.ts`):

```ts
if (err instanceof ClientHttpError) {
  const bodyMsg = typeof err.body === "object" && err.body && "error" in err.body
    ? String((err.body as { error: unknown }).error)
    : undefined;
  message = bodyMsg ?? `HTTP ${err.status}: ${err.message}`;
}
```

### 4.7 knowledge-hub flow change

`labs/knowledge-hub/src/flow.ts` — env-gated auth (symmetric with DevTool token):

```ts
const bearerSecret = process.env.KH_MCP_SECRET;

const knowledgeHubFlow = defineFlow({
  kind: "knowledge-hub",
  authentication: {
    requireUser: true,
    // Secret set → bearer required on HTTP (production / secured local).
    // Secret unset → no per-flow resolver; host falls back to body userId
    // so DevTool works locally without a bearer token (BP-031: dev-only).
    ...(bearerSecret
      ? {
          requiresBearer: true,
          principalUserId: "owner",
          resolvePrincipal: createBearerSecretPrincipalResolver({
            secret: bearerSecret,
            principal: { userId: "owner" },
          }),
        }
      : {}),
  },
  // ...
});
```

`fsdev.config.ts` — **unchanged:** MCP adapter still mounts only when `KH_MCP_SECRET` is set. HTTP action routes are always available via `fsdev dev`; auth mode follows the flow branch above.

`labs/knowledge-hub/README.md` — document both paths:

```bash
# Local DevTool (no bearer): omit KH_MCP_SECRET, clear bearer in DevTool Settings
pnpm fsdev dev

# Secured local / production-shaped: secret on server + matching token in DevTool
KH_MCP_SECRET=test pnpm fsdev dev
# DevTool: bearer token `test`, user id `owner`
```

**Tests** — replace `flow.spec.ts` behaviour 10 ("throws when secret unset") with:
- Secret unset → `resolvePrincipal` is undefined (no throw on HTTP context)
- Secret set → bearer resolver defined; wrong/missing bearer still 401

### 4.8 Standalone `fsdev dev` shell (optional convenience)

`apps/devtool/src/App.tsx` — read `readBearerToken()` on mount (same as userId). No auto-fill from `KH_MCP_SECRET` in v1 (too implicit; see Open Questions).

### 4.9 Embedded hosts

`DevToolPanel` gains optional `bearerToken?: string` and `bearerTokenControl?: "host" | "internal"` props (parallel to `userId`). kitchen-sink embedding unchanged — open flows without bearer keep working.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|------|-------------------|
| Empty/cleared bearer token in DevTool | No `Authorization` header; works against flows with `requiresBearer: false` |
| Bearer token set in DevTool, server `requiresBearer: false` | Header sent but server ignores it; body `userId` used |
| Bearer token set, server `requiresBearer: true`, token matches | Auth succeeds |
| Wrong bearer token | `401 Invalid scheduler secret.` surfaced in ActionBar |
| Bearer correct, userId mismatch (bearer mode) | `UserBindingMismatchError` in ActionBar; hint banner visible |
| Flow `requiresBearer: false` | No bearer/userId hint banners |
| `KH_MCP_SECRET` unset | knowledge-hub HTTP uses body `userId`; DevTool works with bearer cleared |
| `KH_MCP_SECRET` set, DevTool bearer cleared | Auth failure surfaced in ActionBar |
| MCP endpoint | Still unmounted without server secret (unchanged) |

## 8. Non-Goals

- **Arbitrary custom headers UI** (API keys, tenant headers) — hosts pass `fetcher` when embedding; follow-up if needed.
- **Auto-reading `KH_MCP_SECRET` into DevTool** — convenient but implicit; open for v2.
- **Session creation through `resolvePrincipal`** — server change with broader blast radius.
- **DevTool auth for debug endpoints** — separate from flow `resolvePrincipal`; debug routes keep origin/loopback gating (`debug-vs-client-state.md`).
- **Changing knowledge-hub MCP fail-closed mount** — MCP adapter still requires `KH_MCP_SECRET`; only HTTP action routes relax when secret is absent.
- **OAuth / JWT login UI in DevTool** — use embedded host + custom `fetcher` with `createHs256JwtVerifier` flows.

**Follow-up (deepening):** `dispatchDevToolAction` creates a fresh `createClient` per dispatch — consider a per-flow client cache keyed by `(flowKind, bearerToken)` if profiling shows churn.
