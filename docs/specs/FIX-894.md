# FIX-894: Development auth for DevTool against secured flows — Implementation Spec

> **Linear:** [FIX-894](https://linear.app/fixpoint-labs/issue/FIX-894/devtool-bearer-auth-for-secured-flows-dispatch-error-surfacing). Motivated by knowledge-hub ([FIX-882](https://linear.app/fixpoint-labs/issue/FIX-882)) DevTool failures; generalizes to any flow using `createBearerSecretPrincipalResolver`.

> **Approach history (why this spec looks nothing like v1–v3).** v1 relaxed knowledge-hub so an unset `KH_MCP_SECRET` trusted body `userId` — rejected (two P1 reviews: an accidentally-unset production secret becomes an open identity path). v2/v3 put a clearable bearer token *in DevTool* and threaded it through the client. That worked, but the review rounds ([PR #757](https://github.com/fixpoint-labs/flow-state-dev/pull/757)) showed it dragged a long tail of complexity — not from sending a header, but from the **identity divergence** it created: a bearer flow resolves to a fixed principal (`owner`) while DevTool's session is `devuser`, so surfacing the resulting `UserBindingMismatchError` needed stream-item extraction, error latching, an engine terminal-error path, session resets, and config-sync gating. **v4/v5 (this spec) removes the divergence at its root:** `fsdev dev --dev-auth` runs the local server in a development-auth mode that trusts body `userId` for the HTTP action requests DevTool sends. One identity source, locally, behind an explicit opt-in flag. Production is untouched and stays fail-closed.

> **v5 changes (post-implementation review of PR #757).** Four corrections from the design review, all reflected below: (1) `devAuth` is a **named host option** threaded like `dispatcher`/`resolvePrincipal`, **not** a `RuntimeConfig` field — it is *consumed* at the host's resolver-selection seam, so per BP-026 it stays a named parameter. (2) The HTTP source constant is `HTTP_TRANSPORT_SOURCE = "http"`, read from `context.source` (top-level), not `context.envelope.source`. (3) The config-path seam is the **`FSDEV_DEV_AUTH=1` env fallback** (mirroring `FSDEV_DEBUG_ENDPOINTS`), never a router rebuild from `getRuntime()` (which would drop custom adapters/dispatcher). (4) `--dev-auth` **hard-refuses** when `FSD_DB_URL`/`DATABASE_URL` is set — the only reliable production-backend signal — instead of promising a store-adapter name the CLI cannot introspect. Org and `defaultUserId` behavior under dev-auth is now stated accurately (see §4.2/§6) and tested.

## 1. TLDR

**Plain-language summary.** When you run `fsdev dev` against a flow that authenticates with a bearer secret (like knowledge-hub with `KH_MCP_SECRET` set), creating a session works but sending an action silently fails on auth. The fix: **`fsdev dev --dev-auth`** (an explicit opt-in) authenticates **HTTP action requests** — the traffic DevTool sends — from the request-body `userId`, so secured flows are debuggable through DevTool without a token. It's a local-only development opt-in: **off by default**, the dev server binds `127.0.0.1`, only HTTP action requests are affected (MCP and scheduled transports keep their real auth), and production deployments never enable it. A loud warning prints whenever it's active, naming the local store target, and `--dev-auth` **refuses to start** when a database URL is set — because a config-based `fsdev dev` can serve production-backed stores.

**One-sentence technical statement.** Add a named `devAuth?: boolean` option on the transport host (threaded through `createFlowApiRouter` → `createFlowRouteHandlers` → `createInboundTransportHost`, with an `FSDEV_DEV_AUTH=1` env fallback); when set, the host resolves the principal via `defaultBodyUserIdPrincipalResolver` **only for HTTP-action-sourced requests** (`context.source === "http"`) — overriding the per-flow resolver for that source while MCP/scheduled/webhook keep theirs; the CLI's `fsdev dev --dev-auth` opts in (explicit option on the discovery path, `FSDEV_DEV_AUTH` env on the config path), prints a loud warning **directly**, and hard-refuses against a database URL.

**Deliverables:**

- **Engine:** add `devAuth?: boolean` as a named option on `CreateInboundTransportHostOptions`, `CreateFlowRouteHandlersOptions`, and `CreateFlowApiRouterOptions` (NOT `RuntimeConfig` — BP-026: the flag is consumed at the host, not forwarded verbatim). In `createInboundTransportHost`'s resolver-selection seam, when `devAuth === true` **and `context.source === HTTP_TRANSPORT_SOURCE`** (`"http"`), select `defaultBodyUserIdPrincipalResolver` instead of `flowAuth?.resolvePrincipal ?? resolvePrincipal`; every other transport source keeps the flow resolver. `createFlowRouteHandlers` resolves the effective value as `options.devAuth ?? (process.env.FSDEV_DEV_AUTH === "1")`.
- **CLI:** add an opt-in `--dev-auth` flag to `fsdev dev` (**off by default**). Discovery path: pass `devAuth: options.devAuth` into `createFlowApiRouter`. Config path (pre-built `FlowState`): set `process.env.FSDEV_DEV_AUTH ??= "1"` in `beforeConfigLoad` so the app's router picks it up via the env fallback. Hard-refuse (CliError, `EXIT_INVALID_ARGS`) when `--dev-auth` is combined with `FSD_DB_URL`/`DATABASE_URL`. Print a loud warning **directly from the CLI** (`process.stderr`) naming the resolved store target.
- **knowledge-hub:** unchanged (stays fail-closed). README documents debugging it locally with `fsdev dev --dev-auth`.
- **Docs:** update the **authoritative architecture docs** (`docs/architecture/authentication.md`, `docs/architecture/inbound-transports.md`) to document the scoped dev-auth exception — they currently state per-flow `resolvePrincipal` always wins, and per AGENTS.md they must be updated and outrank this spec; plus user-facing `apps/docs/docs/devtool/setup.md` and `apps/docs/docs/server/authentication.md`, and package READMEs `packages/cli/README.md` (the `fsdev dev` options table) and `packages/engine/README.md` (the authentication contract).
- **Changesets:** `minor` on `@flow-state-dev/engine` and `@flow-state-dev/cli`.
- **Deferred (follow-up, not in this PR):** DevTool inline dispatch-error surfacing in `ActionBar`. With dev-auth there is no auth failure to surface, so it is no longer load-bearing; it ships as its own small robustness improvement later.

**Size estimate:** **Small** — ~60–90 LOC across engine + cli + docs. No DevTool auth surface, no per-flow changes, no client/core changes.

## 2. Overview

**Problem.** DevTool sends flow actions with `userId` in the JSON body only. Flows using `createBearerSecretPrincipalResolver` (knowledge-hub, knowledge-base prod, scheduled-dispatch patterns) require `Authorization: Bearer <secret>`; without it the flow's resolver returns `null` (or throws, for knowledge-hub's fail-closed stub) and the host rejects with `Action request requires non-empty userId` (HTTP 400/401). The panel doesn't render the error, so it looks idle. A secondary failure follows even if you fix auth: a bearer flow resolves to a *fixed* principal (`owner`) while DevTool's session was created as `devuser`, so execution rejects with `UserBindingMismatchError`.

**Root cause.** Both symptoms come from DevTool driving a flow whose transport auth expects an identity DevTool can't easily supply, and from that identity diverging from the session's. For **local development**, the value of real transport auth is near zero — the operator is on `127.0.0.1` debugging their own flow — while the cost (token plumbing, identity alignment, error surfacing) is high.

**Outcome.** `fsdev dev --dev-auth` trusts body `userId` for the HTTP action requests DevTool sends. There is one identity source end-to-end, so a session created as `devuser` and an action dispatched as `devuser` agree — no bearer needed, no mismatch, nothing to surface. Secured flows behave like open flows over HTTP actions, *locally only*. Production, MCP mounts, and any non-dev server path are unaffected and remain fail-closed.

## 3. Background & Research

### 3.1 Reproduced failure (2026-07-13)

| Step | Result |
|------|--------|
| `POST .../actions/logActivity` without `Authorization` | `400 {"error":"Action request requires non-empty userId"}` |
| Same with `Authorization: Bearer test` + session `userId: devuser` | `202` accepted, then `UserBindingMismatchError` at execution |
| Same with bearer + session created as `owner` | `202`, request `completed`, inbox write succeeds |

### 3.2 How principal resolution works

The HTTP action route calls `host.resolvePrincipal(...)` (`action-routes.ts:77`) with a context whose top-level `source` is `"http"`. The host picks the resolver in `createInboundTransportHost`'s `resolve()` (the seam near line 434):

```ts
const flow = registry.get(context.envelope.flowKind);
const flowAuth = flow?.authentication;
const resolver = flowAuth?.resolvePrincipal ?? resolvePrincipal; // per-flow wins over host default
```

The host-level default is `defaultBodyUserIdPrincipalResolver` (`http-handlers.ts:240`), which reads `body.userId` and returns `{ userId }` (plus `orgId` if the body carries one) — exactly the identity DevTool already sends. Per-flow auth (knowledge-hub's bearer/throwing resolver) overrides it. **Dev-auth mode is a one-line override of this selection: use the body-userId resolver for HTTP-action-sourced requests, overriding even the per-flow resolver.**

### 3.3 Analogous patterns

| Pattern | Location | Relevance |
|---------|----------|-----------|
| `defaultBodyUserIdPrincipalResolver` | `packages/engine/src/transports/auth/defaultBodyUserIdPrincipalResolver.ts` | The exact "trust body userId" primitive dev-auth reuses — no new resolver to write |
| `dispatcher` named option | `createInboundTransportHost` / `createFlowRouteHandlers` / `createFlowApiRouter` | The precedent for a per-host option threaded through the chain **without** `RuntimeConfig`; `devAuth` follows the same path (BP-026) |
| `debugEndpointsEnabled` + `FSDEV_DEBUG_ENDPOINTS` env fallback | `debug-routes.ts:62-65`, `dev.ts:98` | Exact precedent for a dev-only host option with a CLI-set env fallback for the config-based serve path |
| Dev server binds loopback | `packages/cli/src/commands/dev.ts` (`host: "127.0.0.1"`) | dev-auth is only ever reachable locally, via the dev command |

### 3.4 Security: why this is not v1's identity hole

v1 was rejected because it relaxed auth **on secret absence**, per-flow, affecting *any* deployment — so an accidentally-unset production `KH_MCP_SECRET` silently became an open identity path (BP-031). Dev-auth is structurally different:

- **Explicit opt-in** (`fsdev dev --dev-auth`), off by default — never triggered by a missing secret or inferred from config state.
- Set only by the CLI dev command; production entry points (`serve`/deploy adapters, Vercel, MCP mounts) never set the flag or the env var.
- **Scoped to HTTP action requests** (`context.source === "http"`) — MCP, scheduled, and webhook transports keep their real per-flow resolvers even when dev-auth is on.
- The dev server binds `127.0.0.1`, and a **loud warning prints directly from the CLI** whenever dev-auth is active.
- **Hard-refuses against a database URL.** A config-based `fsdev dev` serves the app's own stores, and some configs select a **production backend** when `DATABASE_URL`/`FSD_DB_URL` is present (e.g. `examples/knowledge-base/fsdev.config.ts`). Bypassing auth while pointed at prod-backed data is the real risk. The `StoreRegistry` is opaque (no adapter name/connection descriptor), so the CLI can't introspect "local vs remote" — but the DB-URL env vars *are* a reliable signal, and they are exactly what those configs branch on. So `--dev-auth` refuses to start when either is set. Unset the DB URL to debug locally, or drop `--dev-auth`.

### 3.5 Necessity verdict

**Build as scoped.** DevTool cannot drive a bearer-gated flow today without either forking DevTool or standing up real bearer credentials in the browser. Dev-auth is the minimal framework-level switch that makes local debugging work, and it's the same "gate the open path on an explicit dev-only flag" that both P1 reviewers recommended as the correct alternative to v1. Not building: a DevTool auth UI, real bearer handshake in DevTool, or any change to `resolvePrincipal` semantics.

### 3.6 Key Decisions & Ramifications

1. **Framework dev-auth mode, not client-side auth.** The lever is one server-side option, not token plumbing in DevTool. *Rejected:* v2/v3 bearer-token-in-DevTool (works, but drags identity-divergence complexity). *Ramification:* DevTool needs no auth surface; the client-side approach and its escape hatches are dropped.

2. **`devAuth` is a named host option, not a `RuntimeConfig` field (BP-026).** It is *consumed* at the host's resolver-selection seam, not forwarded verbatim to `runAction`, so it stays a named parameter threaded like `dispatcher`. *Rejected:* a `RuntimeConfig.devAuth` field (would drill a security-sensitive switch through dispatchers, workers, recovery, and `runAction` that never read it). *Ramification:* the flag lives on exactly the three option types between the public boundary and the host, plus an env fallback.

3. **Reuse `defaultBodyUserIdPrincipalResolver`; override per-flow resolvers when `devAuth` and source is HTTP.** *Rejected:* a bespoke permissive resolver; wrapping each flow's resolver. *Ramification:* every flow resolves identity the same way locally (body `userId`); knowledge-hub's throwing stub is never invoked in dev, so it stays fail-closed and unchanged.

4. **Config-path opt-in via the `FSDEV_DEV_AUTH` env fallback, not a router rebuild.** A config-based `fsdev dev` serves a pre-built `FlowState` the CLI can't pass options into; `getRuntime()` exposes only `{ registry, stores, runtimeConfig }`, so rebuilding a router from it would drop custom adapters, the host resolver, error handling, and the dispatcher. *Ramification:* the CLI sets `FSDEV_DEV_AUTH=1` before the config loads (mirroring `FSDEV_DEBUG_ENDPOINTS`), and `createFlowRouteHandlers` reads it as the fallback — no router reconstruction, config-mounted MCP adapters preserved.

5. **Explicit opt-in flag, off by default; scoped to HTTP; hard-refuse on a DB URL.** *Rejected:* default-on for `fsdev dev` (unsafe when a config-based dev server points at a production backend — §3.4); auto-relaxing on loopback (too implicit) or on secret absence (v1's hole); a host-wide resolver swap (breaks MCP/scheduled transports, which carry no body `userId`); a warning-only prod guard (leaves the prod-data footgun open). *Ramification:* dev-auth is predictable, greppable, never on unless asked for, and cannot start against a detected production backend; the real handshake is `fsdev dev` with no flag.

6. **Loud startup warning whenever dev-auth is active.** *Ramification:* no silent bypass; an operator always knows the local server is trusting body identity, and the warning names the local store target.

## 4. Technical Design

### 4.1 `devAuth` named option (not `RuntimeConfig`)

`devAuth?: boolean` is added to three option types, following the `dispatcher` precedent:

- `CreateInboundTransportHostOptions` (`createInboundTransportHost.ts`) — the consuming layer.
- `CreateFlowRouteHandlersOptions` (`http-handlers.ts`) — forwards to the host, resolving the env fallback.
- `CreateFlowApiRouterOptions` (`createFlowApiRouter.ts`) — the public boundary; flows through via `...options`.

It is deliberately **not** a `RuntimeConfig` field: BP-026 reserves `RuntimeConfig` for forward-only values, and `devAuth` is read at the host to pick the resolver.

### 4.2 Resolver selection in the host

`createInboundTransportHost.ts`, in `resolve()`. The override is gated on both `devAuth` **and** the request coming from the HTTP source (`context.source === HTTP_TRANSPORT_SOURCE`, the `"http"` constant from `createHttpTransportAdapter.ts`), so MCP / scheduled / webhook sources (which carry no body `userId`) keep their real resolver:

```ts
const flow = registry.get(context.envelope.flowKind);
const flowAuth = flow?.authentication;
const devAuthActive =
  devAuth === true && context.source === HTTP_TRANSPORT_SOURCE;
const resolver = devAuthActive
  ? defaultBodyUserIdPrincipalResolver          // dev: trust body userId for DevTool's HTTP actions
  : (flowAuth?.resolvePrincipal ?? resolvePrincipal);
```

Post-resolution enforcement is unchanged — dev-auth only changes *which* resolver runs:

- **`requireUser`:** a request that omits `userId` still fails 401, exactly as an open flow does.
- **`defaultUserId`:** if the flow configures `authentication.defaultUserId`, it still applies after the resolver returns null (dev-auth swaps the resolver, not the fallback). So a no-`userId` request against a flow with a `defaultUserId` executes as that default — documented, not a rejection.
- **`orgId` / `requireOrg`:** `defaultBodyUserIdPrincipalResolver` yields `{ userId }` plus `orgId` **when the body carries one**, and the action route independently prefers `body.orgId`. So under dev-auth a `requireOrg` flow is satisfied by a body `orgId`; there is **no org entitlement check** — a local caller can name any org. This is acceptable only under the local-only, opt-in, single-operator model (the operator already fully controls the local server), and is the same trust decision as trusting body `userId`. Dev-auth does **not** build a dev-org UI (§8); it just doesn't pretend org flows reject.

### 4.3 Env fallback (config-path seam)

`createFlowRouteHandlers` resolves the effective flag, mirroring `resolveDebugConfig`'s `FSDEV_DEBUG_ENDPOINTS` handling:

```ts
const devAuth =
  options.devAuth === undefined
    ? process.env.FSDEV_DEV_AUTH === "1"
    : options.devAuth;
```

Because `createFlowState.#doInit()` builds its router via `createFlowApiRouter`, a config-based app picks up `FSDEV_DEV_AUTH=1` automatically — no `FlowState` API change and no router rebuild.

### 4.4 Startup warning

The warning must not depend on `RuntimeConfig.logger` (unset on the default `fsdev dev` paths). Emit it **directly from the CLI** (`process.stderr`) when `--dev-auth` is passed, and name the resolved store target (`dataLine`: `.fsdev/data/fsdev.db (SQLite)` on the discovery path, `config: <path>` on the config path — the truthful, available signals; the store adapter itself is opaque):

```
  ⚠  DEVELOPMENT AUTH ENABLED (--dev-auth)
     HTTP action requests are trusted as their body `userId`; per-flow
     transport auth is bypassed for DevTool traffic (MCP/scheduled untouched).
     Store target: <dataLine>. Never use against production data.
```

### 4.5 CLI wiring

Add an opt-in `--dev-auth` flag to `fsdev dev`, **off by default**.

- **Discovery path** — the `createFlowApiRouter({ ... })` call: pass `devAuth: options.devAuth`. Discovery always serves local SQLite, so it's inherently safe.
- **Config path** — the app's own `FlowState`. Set `process.env.FSDEV_DEV_AUTH ??= "1"` in `beforeConfigLoad` (only when `--dev-auth`) so the app's router opts in via the env fallback. **Hard-refuse before opening any pool:** if `FSD_DB_URL`/`DATABASE_URL` is set, dispose the FlowState and throw `CliError(EXIT_INVALID_ARGS)` naming the risk.

```
fsdev dev             # real transport auth — bearer/secret required, as in production
fsdev dev --dev-auth  # HTTP action requests trusted as body userId (DevTool debugging)
```

### 4.6 knowledge-hub

**Unchanged.** The flow stays fail-closed (`KH_MCP_SECRET` set → bearer resolver + `{ userId: "owner" }`; unset → throwing stub). `fsdev dev --dev-auth` debugs it locally with no token because dev-auth bypasses the flow resolver entirely for HTTP actions; the throwing stub is never invoked. `fsdev.config.ts` (MCP mount) unchanged. README documents:

```bash
# Debug knowledge-hub locally in DevTool — no secret, no token needed:
pnpm fsdev dev --dev-auth
# Create a session, send logActivity/listInbox as any userId.

# Exercise the real bearer handshake locally instead (default, no flag):
KH_MCP_SECRET=test pnpm fsdev dev   # then send Authorization: Bearer test via an MCP/HTTP client
```

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|------|-------------------|
| `fsdev dev --dev-auth`, bearer-gated flow, HTTP action | Body `userId` trusted; session + action agree; no mismatch |
| `fsdev dev` (no flag), bearer-gated flow | Real transport auth enforced; missing/invalid bearer rejected as in production |
| `--dev-auth` request with no `userId` in body | Rejects 401 (`requireUser`) — dev-auth changes the resolver, not post-resolution checks — **unless** the flow sets `authentication.defaultUserId`, which still applies |
| `--dev-auth` flow with `requireOrg: true` | Satisfied by a body `orgId` (no entitlement check); acceptable under local-only trust. Org-scoped dev UX is out of scope (§8) |
| `--dev-auth` **MCP or scheduled** request | Unaffected — override is scoped to `context.source === "http"`; those transports keep the flow resolver |
| `--dev-auth` with `FSD_DB_URL`/`DATABASE_URL` set | **Hard-refused** — `CliError(EXIT_INVALID_ARGS)` before any pool opens |
| knowledge-hub `KH_MCP_SECRET` unset, `fsdev dev --dev-auth` | Works (bypass skips the throwing stub for HTTP actions) |
| Production server / deploy adapter / Vercel | `devAuth` never set, `FSDEV_DEV_AUTH` never set; fail-closed unchanged |
| MCP endpoint | Still mounted only when `KH_MCP_SECRET` is set (unchanged) |
| Non-dev embedded host (kitchen-sink) | Unaffected — those routers never set `devAuth` |

## 8. Non-Goals

- **A bearer token / auth UI in DevTool** — dev-auth removes the need locally; embedded hosts that must send real credentials use the client `fetcher` when a consumer appears (none today).
- **Debugging a remote, already-secured server from DevTool** — dev-auth is local-only; a remote secured server needs real credentials, out of scope for this issue's local-`fsdev dev` motivation.
- **`principalUserId` / `requiresBearer` flow metadata, hint banners, session-reset, config-sync gating** — all were scaffolding for the identity divergence that dev-auth eliminates.
- **Relaxing knowledge-hub or any flow's auth** — flow auth is unchanged; only the local dev server's resolver selection changes, behind an explicit flag.
- **Auto-enabling dev-auth on loopback or on secret absence** — too implicit / v1's hole; the flag is explicit.
- **Org entitlement enforcement / a dev-org UI under dev-auth** — dev-auth trusts the body-supplied identity (`userId`, and `orgId` if present) without an entitlement check, locally only. A first-class dev-org coordinate is not built here.
- **Introspecting the store adapter to name the backend** — `StoreRegistry` is opaque; the warning names the truthful available signal (config path / local SQLite), and the DB-URL env vars drive the hard-refuse instead.
- **DevTool inline dispatch-error surfacing** — deferred to a follow-up; dev-auth removes the auth failure that made DevTool look idle, so it is no longer load-bearing.

1. **~~Default-on vs. opt-in~~ — resolved: opt-in.** Explicit `--dev-auth`, off by default: a config-based `fsdev dev` can serve a production backend, and default-on would bypass auth against prod data (§3.4).
2. **~~Flag / config naming~~ — resolved: `--dev-auth`** at the CLI and a named `devAuth` option internally, paired with the loud warning.
3. **~~App-FlowState override seam~~ — resolved: `FSDEV_DEV_AUTH` env fallback**, not a router rebuild from `getRuntime()` (which would drop custom adapters/dispatcher).
4. **~~Hard-refuse against a production backend?~~ — resolved: yes.** `--dev-auth` errors out when `FSD_DB_URL`/`DATABASE_URL` is set (the only reliable production-backend signal, since `StoreRegistry` is opaque).

## 12. Acceptance Criteria (for issue description)

- [ ] `fsdev dev --dev-auth` trusts body `userId` for HTTP action requests, so a bearer-gated flow (knowledge-hub with or without `KH_MCP_SECRET`) is debuggable in DevTool with no token, and a `devuser` session runs `devuser` actions with no binding mismatch.
- [ ] `fsdev dev` (no flag) enforces real transport auth (the bearer handshake) locally.
- [ ] Dev-auth is scoped to the HTTP source — MCP / scheduled / webhook transports keep their per-flow resolver even when it's active.
- [ ] A loud warning prints directly from the CLI whenever `--dev-auth` is active, naming the resolved store target; `--dev-auth` hard-refuses when a database URL is set.
- [ ] `devAuth` is a named host option (not `RuntimeConfig`); no production/deploy/MCP path enables it; the architecture auth docs and package READMEs are updated; flow auth and the knowledge-hub flow are unchanged.
