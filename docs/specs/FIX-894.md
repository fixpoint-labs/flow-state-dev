# FIX-894: Development auth for DevTool against secured flows — Implementation Spec

> **Linear:** [FIX-894](https://linear.app/fixpoint-labs/issue/FIX-894/devtool-bearer-auth-for-secured-flows-dispatch-error-surfacing). Motivated by knowledge-hub ([FIX-882](https://linear.app/fixpoint-labs/issue/FIX-882)) DevTool failures; generalizes to any flow using `createBearerSecretPrincipalResolver`.

> **Approach history (why this spec looks nothing like v1–v3).** v1 relaxed knowledge-hub so an unset `KH_MCP_SECRET` trusted body `userId` — rejected (two P1 reviews: an accidentally-unset production secret becomes an open identity path). v2/v3 put a clearable bearer token *in DevTool* and threaded it through the client. That worked, but the review rounds ([PR #757](https://github.com/fixpoint-labs/flow-state-dev/pull/757)) showed it dragged a long tail of complexity — not from sending a header, but from the **identity divergence** it created: a bearer flow resolves to a fixed principal (`owner`) while DevTool's session is `devuser`, so surfacing the resulting `UserBindingMismatchError` needed stream-item extraction, error latching, an engine terminal-error path, session resets, and config-sync gating. **v4 (this spec) removes the divergence at its root:** `fsdev dev --dev-auth` runs the local server in a development-auth mode that trusts body `userId` for the HTTP action requests DevTool sends. One identity source, locally, behind an explicit opt-in flag. Production is untouched and stays fail-closed.

## 1. TLDR

**Plain-language summary.** When you run `fsdev dev` against a flow that authenticates with a bearer secret (like knowledge-hub with `KH_MCP_SECRET` set), creating a session works but sending an action silently fails on auth. The fix: **`fsdev dev --dev-auth`** (an explicit opt-in) authenticates **HTTP action requests** — the traffic DevTool sends — from the request-body `userId`, so secured flows are debuggable through DevTool without a token. It's a local-only development opt-in: **off by default**, the dev server binds `127.0.0.1`, only HTTP action requests are affected (MCP and scheduled transports keep their real auth), and production deployments never enable it. A loud warning prints whenever it's active, naming the store/backend it points at — because a config-based `fsdev dev` can serve production-backed stores.

**One-sentence technical statement.** Add an internal `RuntimeConfig.devAuth` flag; when set, `createInboundTransportHost` resolves the principal via the existing `defaultBodyUserIdPrincipalResolver` **only for HTTP-action-sourced requests** (per-flow `resolvePrincipal` still runs for MCP, scheduled, and webhook transports); the CLI's `fsdev dev --dev-auth` sets it and prints a loud warning **directly** (not via the optional `RuntimeConfig.logger`); no other server path sets it, so production auth is unchanged.

**Deliverables:**

- **Engine:** add `devAuth?: boolean` to `RuntimeConfig` (`packages/engine/src/runtime-config.ts`). In `createInboundTransportHost`, when `runtimeConfig.devAuth` is set **and the request `source` is the HTTP action adapter** (`envelope.source`), select `defaultBodyUserIdPrincipalResolver` instead of `flowAuth?.resolvePrincipal ?? resolvePrincipal` (the seam at `createInboundTransportHost.ts:434`); every other transport source keeps the flow resolver.
- **CLI:** add an opt-in `--dev-auth` flag to `fsdev dev` (**off by default**). When passed, set `devAuth: true` on the effective runtime config for both serve paths (discovered-flows router and the app's own `FlowState`), and print a loud warning **directly from the CLI** (`console` / `DEFAULT_RUNTIME_LOGGER`, not the optional `RuntimeConfig.logger`) naming the flag and the resolved store/backend target.
- **DevTool (optional, separable):** surface a failed action dispatch inline in `ActionBar` via `ErrorAlert` (the `useActionDispatch().error` rejection, with HTTP status). Small general robustness improvement — no longer required to fix the motivating bug. Can ship here or as its own follow-up.
- **knowledge-hub:** unchanged (stays fail-closed). README documents debugging it locally with `fsdev dev --dev-auth`.
- **Docs:** update the **authoritative architecture docs** (`docs/architecture/authentication.md`, `docs/architecture/inbound-transports.md`) to document the scoped dev-auth exception — they currently state per-flow `resolvePrincipal` always wins, and per AGENTS.md they must be updated and outrank this spec; plus user-facing `apps/docs/docs/devtool/setup.md` and `apps/docs/docs/server/authentication.md`.
- **Changesets:** `patch` on `@flow-state-dev/engine` and `@flow-state-dev/cli` (+ `@flow-state-dev/devtool` if the optional error surfacing lands here).

**Size estimate:** **Small** — ~40–80 LOC across engine + cli + docs (plus ~15 LOC if the optional DevTool error surfacing is included). No DevTool auth surface, no per-flow changes, no client/core changes.

## 2. Overview

**Problem.** DevTool sends flow actions with `userId` in the JSON body only. Flows using `createBearerSecretPrincipalResolver` (knowledge-hub, knowledge-base prod, scheduled-dispatch patterns) require `Authorization: Bearer <secret>`; without it the flow's resolver returns `null` (or throws, for knowledge-hub's fail-closed stub) and the host rejects with `Action request requires non-empty userId` (HTTP 400). The panel doesn't render the error, so it looks idle. A secondary failure follows even if you fix auth: a bearer flow resolves to a *fixed* principal (`owner`) while DevTool's session was created as `devuser`, so execution rejects with `UserBindingMismatchError`.

**Root cause.** Both symptoms come from DevTool driving a flow whose transport auth expects an identity DevTool can't easily supply, and from that identity diverging from the session's. For **local development**, the value of real transport auth is near zero — the operator is on `127.0.0.1` debugging their own flow — while the cost (token plumbing, identity alignment, error surfacing) is high.

**Outcome.** `fsdev dev --dev-auth` trusts body `userId` for the HTTP action requests DevTool sends. There is one identity source end-to-end, so a session created as `devuser` and an action dispatched as `devuser` agree — no bearer needed, no mismatch, nothing to surface. Secured flows behave like open flows over HTTP actions, *locally only*. Production, MCP mounts, and any non-dev server path are unaffected and remain fail-closed.

## 3. Background & Research

### 3.1 Reproduced failure (2026-07-13)

| Step | Result |
|------|--------|
| `POST .../actions/logActivity` without `Authorization` | `400 {"error":"Action request requires non-empty userId"}` |
| Same with `Authorization: Bearer test` + session `userId: devuser` | `202` accepted, then `UserBindingMismatchError` at execution |
| Same with bearer + session created as `owner` | `202`, request `completed`, inbox write succeeds |

### 3.2 How principal resolution works

The HTTP action route calls `host.resolvePrincipal(...)` (`action-routes.ts:77`). The host picks the resolver at `createInboundTransportHost.ts:434`:

```ts
const flowAuth = flow?.authentication;
const resolver = flowAuth?.resolvePrincipal ?? resolvePrincipal; // per-flow wins over host default
```

The host-level default is `defaultBodyUserIdPrincipalResolver` (`http-handlers.ts:240`), which reads `body.userId` and returns `{ userId }` — exactly the identity DevTool already sends. Per-flow auth (knowledge-hub's bearer/throwing resolver) overrides it. **Dev-auth mode is a one-line override of this selection: use the body-userId resolver for HTTP-action-sourced requests.**

### 3.3 Analogous patterns

| Pattern | Location | Relevance |
|---------|----------|-----------|
| `defaultBodyUserIdPrincipalResolver` | `packages/engine/src/transports/auth/defaultBodyUserIdPrincipalResolver.ts` | The exact "trust body userId" primitive dev-auth reuses — no new resolver to write |
| `RuntimeConfig` forwarded bundle | `packages/engine/src/runtime-config.ts` | Internal pass-through config; "adding a forwarded field is a one-line change here plus one assignment at the public boundary" — where `devAuth` lives |
| Dev server binds loopback | `packages/cli/src/commands/dev.ts:201` (`host: "127.0.0.1"`) | dev-auth is only ever reachable locally, via the dev command |
| Debug routes gated to local origin | `docs/architecture/debug-vs-client-state.md` | Established precedent: the dev/debug surface is already treated as local-only and more permissive than production |

### 3.4 Security: why this is not v1's identity hole

v1 was rejected because it relaxed auth **on secret absence**, per-flow, affecting *any* deployment — so an accidentally-unset production `KH_MCP_SECRET` silently became an open identity path (BP-031). Dev-auth is structurally different:

- **Explicit opt-in** (`fsdev dev --dev-auth`), off by default — never triggered by a missing secret or inferred from config state.
- Set only by the CLI dev command; production entry points (`serve`/deploy adapters, Vercel, MCP mounts) never set the flag.
- **Scoped to HTTP action requests** (`envelope.source`) — MCP, scheduled, and webhook transports keep their real per-flow resolvers even when dev-auth is on.
- The dev server binds `127.0.0.1`, and a **loud warning prints directly from the CLI** whenever dev-auth is active.

**One residual hazard, handled explicitly:** the config-based `fsdev dev` serves the app's *own* `FlowState` and stores, and some configs select a **production backend** when `DATABASE_URL` / `FSD_DB_URL` is present (e.g. `examples/knowledge-base/fsdev.config.ts`). Bypassing auth while pointed at prod-backed data is the real risk, and it's exactly why dev-auth is opt-in rather than default-on: the operator must ask for it, and the warning names the resolved store/backend so an accidental `--dev-auth` against a production profile is loud, not silent. (Open Question 4: additionally hard-refuse `--dev-auth` when a remote/prod backend is detected.)

### 3.5 Necessity verdict

**Build as scoped.** DevTool cannot drive a bearer-gated flow today without either forking DevTool or standing up real bearer credentials in the browser. Dev-auth is the minimal framework-level switch that makes local debugging work, and it's the same "gate the open path on an explicit dev-only flag" that both P1 reviewers recommended as the correct alternative to v1. Not building: a DevTool auth UI, real bearer handshake in DevTool, or any change to `resolvePrincipal` semantics.

### 3.6 Key Decisions & Ramifications

1. **Framework dev-auth mode, not client-side auth.** The lever is one server-side flag, not token plumbing in DevTool. *Rejected:* v2/v3 bearer-token-in-DevTool (works, but drags identity-divergence complexity). *Ramification:* DevTool needs no auth surface; the client-side approach and its escape hatches are dropped.

2. **Reuse `defaultBodyUserIdPrincipalResolver`; bypass per-flow resolvers when `devAuth`.** *Rejected:* a bespoke permissive resolver; wrapping each flow's resolver. *Ramification:* every flow resolves identity the same way locally (body `userId`); knowledge-hub's throwing stub is never invoked in dev, so it stays fail-closed and unchanged.

3. **Explicit opt-in flag (`fsdev dev --dev-auth`), off by default; scoped to HTTP action requests.** *Rejected:* default-on for `fsdev dev` (unsafe when a config-based dev server points at a production backend — §3.4); auto-relaxing on loopback (too implicit; SSRF/proxy surface) or on secret absence (v1's hole); a host-wide resolver swap (breaks MCP/scheduled transports, which carry no body `userId`). *Ramification:* dev-auth is predictable, greppable, and never on unless asked for; the real handshake is `fsdev dev` with no flag.

4. **Loud startup warning whenever dev-auth is active.** *Ramification:* no silent bypass; an operator always knows the local server is trusting body identity.

5. **Dispatch error surfacing is separable.** With dev-auth there is no auth failure to surface, so the original "DevTool looks idle" symptom is fixed at the source. Surfacing a failed dispatch in `ActionBar` is still a small general good; it ships as an optional, self-contained addition (or a follow-up), not the load-bearing fix.

## 4. Technical Design

### 4.1 `RuntimeConfig.devAuth`

`packages/engine/src/runtime-config.ts`:

```ts
export interface RuntimeConfig {
  // ...existing forwarded fields...
  /**
   * Development-only transport auth bypass. When true, every flow's principal
   * is resolved from the request body `userId` (via
   * `defaultBodyUserIdPrincipalResolver`), ignoring per-flow
   * `authentication.resolvePrincipal`. Set ONLY by `fsdev dev`; never in
   * production. A misconfiguration cannot enable it because no production
   * entry point constructs it.
   */
  devAuth?: boolean;
}
```

`RuntimeConfig` forwards verbatim to `createInboundTransportHost`, which already destructures it (`createInboundTransportHost.ts:101`).

### 4.2 Resolver selection in the host

`createInboundTransportHost.ts` (the seam at line 434). The override is gated on both `devAuth` **and** the request coming from the HTTP action adapter, so MCP / scheduled / webhook sources (which carry no body `userId`) keep their real resolver:

```ts
const flowAuth = flow?.authentication;
const isHttpAction = context.envelope.source === HTTP_ACTION_SOURCE; // confirm the exact InboundSource value
const resolver = runtimeConfig.devAuth && isHttpAction
  ? defaultBodyUserIdPrincipalResolver          // dev: trust body userId for DevTool's HTTP actions
  : (flowAuth?.resolvePrincipal ?? resolvePrincipal);
```

`requireUser` / `defaultUserId` / `requireOrg` enforcement downstream is unchanged — dev-auth only changes *which* resolver runs, not the post-resolution checks. A request that omits `userId` still fails the same way an open flow does. **`requireOrg` caveat:** `defaultBodyUserIdPrincipalResolver` yields `{ userId }` (plus `orgId` only if the body carries one); DevTool sends only `userId`, so a flow whose action declares `requireOrg: true` (or whose bearer principal supplied a fixed `orgId`) still rejects under dev-auth. Dev-auth covers **userId-scoped** flows; org-scoped flows need the caller to supply an `orgId` (not built here — see §8).

### 4.3 Startup warning

The warning must not depend on `RuntimeConfig.logger` — the default `fsdev dev` paths don't populate it (`dev.ts:169`, the `createFlowState` config bundle), and the logging helpers optional-chain an absent logger, so the warning would silently vanish exactly when auth is being bypassed. Emit it **directly from the CLI** (`console` / `DEFAULT_RUNTIME_LOGGER`) when `--dev-auth` is passed, and name the resolved store/backend:

```
[flow-state] ⚠ DEVELOPMENT AUTH ENABLED (--dev-auth) — HTTP action requests are trusted as
their body `userId`; per-flow auth is bypassed for DevTool traffic. Store target: <backend>.
Never use against production data.
```

### 4.4 CLI wiring

Add an opt-in `--dev-auth` flag to `fsdev dev` (`dev.ts:54`), **off by default**. Only when it is passed does the command set `devAuth: true` on the effective `RuntimeConfig` for **both** serve paths:

- **Discovered-flows path** — the `createFlowApiRouter({ ... })` call (`dev.ts:169`): pass `devAuth: true` through to `RuntimeConfig`.
- **App-FlowState path** — when serving the app's own `FlowState` (`dev.ts:114–125`), the runtime config is the app's. `fsdev dev --dev-auth` must override `devAuth` on the effective config so a config-based app is debuggable too. (Confirm the override seam: a `FlowState` dev-serve option or reconstructing the router with the app's stores + `devAuth`.) **This path can point at a production backend** (§3.4) — the CLI prints the resolved store target in the warning, and Open Question 4 asks whether to hard-refuse in that case.

```
fsdev dev             # real transport auth — bearer/secret required, as in production
fsdev dev --dev-auth  # HTTP action requests trusted as body userId (DevTool debugging)
```

### 4.5 Dispatch error surfacing (optional, separable)

Independent of dev-auth. In `packages/devtool/src/react/hooks/use-action-dispatch.ts`, keep the HTTP status on the message:

```ts
if (err instanceof ClientHttpError) {
  const bodyMsg = typeof err.body === "object" && err.body && "error" in err.body
    ? String((err.body as { error: unknown }).error)
    : undefined;
  message = `HTTP ${err.status}: ${bodyMsg ?? err.message}`;
}
```

`DevToolPanel` passes `useActionDispatch().error` to `ActionBar`, rendered above the send row via the existing `ErrorAlert` (wrapping/non-truncated so a long message is readable), cleared at the start of the next `sendAction`. This covers pre-execution HTTP rejections only — no request-stream/latching machinery, since dev-auth removes the post-202 binding-mismatch case locally.

### 4.6 knowledge-hub

**Unchanged.** The flow stays fail-closed (`KH_MCP_SECRET` set → bearer resolver + `{ userId: "owner" }`; unset → throwing stub). `fsdev dev` debugs it locally with no token because dev-auth bypasses the flow resolver entirely; the throwing stub is never invoked. `fsdev.config.ts` (MCP mount) unchanged. README documents:

```bash
# Debug knowledge-hub locally in DevTool — no secret, no token needed:
pnpm fsdev dev --dev-auth
# Create a session, send logActivity/listInbox as any userId.

# Exercise the real bearer handshake locally instead (default, no flag):
KH_MCP_SECRET=test pnpm fsdev dev   # then send Authorization: Bearer test via an MCP/HTTP client
```

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|------|-------------------|
| `fsdev dev --dev-auth`, bearer-gated flow, HTTP action | Body `userId` trusted; session + action agree; no mismatch |
| `fsdev dev` (no flag), bearer-gated flow | Real transport auth enforced; missing/invalid bearer rejected as in production |
| `--dev-auth` request with no `userId` in body | Same as an open flow: `requireUser` enforcement rejects (dev-auth changes the resolver, not the post-resolution checks) |
| `--dev-auth` flow with `requireOrg: true` | Still rejects — dev-auth yields `{ userId }` only; org-scoped flows out of scope (§8) |
| `--dev-auth` **MCP or scheduled** request | Unaffected — override is scoped to the HTTP action source; those transports keep the flow resolver |
| `--dev-auth` against a config resolving a **production backend** | Warning names the backend; (Open Q4) optionally hard-refused |
| knowledge-hub `KH_MCP_SECRET` unset, `fsdev dev --dev-auth` | Works (bypass skips the throwing stub for HTTP actions) |
| Production server / deploy adapter / Vercel | `devAuth` never set; fail-closed unchanged |
| MCP endpoint | Still mounted only when `KH_MCP_SECRET` is set (unchanged) |
| Non-dev embedded host (kitchen-sink) | Unaffected — those routers never set `devAuth` |

## 8. Non-Goals

- **A bearer token / auth UI in DevTool** — dev-auth removes the need locally; embedded hosts that must send real credentials use the client `fetcher` when a consumer appears (none today).
- **Debugging a remote, already-secured server from DevTool** — dev-auth is local-only; a remote secured server needs real credentials, out of scope for this issue's local-`fsdev dev` motivation.
- **`principalUserId` / `requiresBearer` flow metadata, hint banners, session-reset, config-sync gating** — all were scaffolding for the identity divergence that dev-auth eliminates.
- **Relaxing knowledge-hub or any flow's auth** — flow auth is unchanged; only the local dev server's resolver selection changes, behind an explicit flag.
- **Auto-enabling dev-auth on loopback or on secret absence** — too implicit / v1's hole; the flag is explicit.
- **Org-scoped (`requireOrg`) flows through DevTool under dev-auth** — dev-auth trusts only body `userId`; a dev `orgId` coordinate is not built here. Such flows still need a real principal (or a follow-up dev-org field).
- **Post-202 execution-failure surfacing in DevTool** — not needed once dev-auth removes the binding mismatch; genuine block-failure surfacing can be a separate improvement.

## 11. Open Questions

1. **~~Default-on vs. opt-in~~ — resolved: opt-in.** Changed to explicit `--dev-auth` (off by default) after review: a config-based `fsdev dev` can serve a production backend, and default-on would bypass auth against prod data (§3.4). Flagged as a reversal of an earlier deliberate call.
2. **Flag / config naming** — `--dev-auth` at the CLI and `RuntimeConfig.devAuth` internally; a more alarming `--insecure-auth` / `insecureTrustBodyUserId` is more self-documenting. Recommend `--dev-auth` + the loud warning; confirm.
3. **App-FlowState override seam** — the cleanest way for `fsdev dev --dev-auth` to force `devAuth` onto an app that constructs its own `FlowState` (a dev-serve option vs. rebuilding the router with the app's stores). Resolve during step 2.
4. **Hard-refuse against a production backend?** — should `--dev-auth` *error out* (not just warn) when the resolved config points at a remote/prod store (`DATABASE_URL` / `FSD_DB_URL` present)? Recommend yes — the strongest guard against bypassing auth on prod data; confirm the detection signal.
