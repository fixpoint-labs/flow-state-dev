# FIX-894: DevTool transport auth for bearer-gated flows — Implementation Spec

> **Linear:** [FIX-894](https://linear.app/fixpoint-labs/issue/FIX-894/devtool-bearer-auth-for-secured-flows-dispatch-error-surfacing). Motivated by knowledge-hub ([FIX-882](https://linear.app/fixpoint-labs/issue/FIX-882)) DevTool failures; generalizes to any flow using `createBearerSecretPrincipalResolver`.

> **Revision (v2, review response to [PR #749](https://github.com/fixpoint-labs/flow-state-dev/pull/749)).** Two changes from v1, both narrowing scope:
> 1. **Dropped the `principalUserId` / `requiresBearer` flow-metadata channel and the DevTool hint banner** (was §4.5). Once dispatch errors render (§4.5), the surfaced `UserBindingMismatchError` already names the required userId — the metadata carried the same fact one layer up, across four packages, for a convenience banner the goal-check never relied on. YAGNI (BP-038); ~120–150 LOC and three package changesets avoided. If a one-click "use this id" affordance is wanted later, it can parse the userId out of that same error string with no new flow-level channel.
> 2. **knowledge-hub stays fail-closed** — v1 relaxed it so an unset `KH_MCP_SECRET` fell back to caller-controlled body `userId`. Two P1 reviews flagged this: it derives identity for a user-scoped inbox from caller-controllable input (BP-031), and an accidentally-unset production secret silently becomes an open identity path. The "no-secret open HTTP" path also never exercises the new bearer feature — the path that validates it is *secret set + token in DevTool*. So knowledge-hub is unchanged; local DevTool uses `KH_MCP_SECRET=test`.

## 1. TLDR

**Plain-language summary.** When you run DevTool against a flow that requires a bearer token (like knowledge-hub with `KH_MCP_SECRET` set), creating a session works but sending an action appears to do nothing. The request fails on auth before execution starts, and DevTool never shows the error. This spec adds an optional, clearable bearer-token field to DevTool settings (token set → send `Authorization`; token cleared → no header), threads it through every HTTP/SSE call the panel makes, and surfaces dispatch failures in the UI — both the pre-execution HTTP rejection and the post-acceptance execution failure (e.g. a userId that doesn't match the session).

**One-sentence technical statement.** Extend `@flow-state-dev/devtool` transport wiring so DevTool injects `Authorization: Bearer <token>` only when a non-empty token is configured (clearable in Settings), threaded through the four client factories via the existing `ClientTransportOptions.fetcher`, and surface both `useActionDispatch` rejections and terminal request-stream failures in the action bar.

**Deliverables:**

- **DevTool:** add clearable `bearerToken` to `DevToolConfig`, persist it in standalone mode (`readBearerToken` / `writeBearerToken` in `packages/devtool/src/react/config.ts`), expose it in `SettingsSheet` (empty = no auth header), build a shared `createAuthFetcher(token)` wrapper, thread `fetcher` (via `ClientTransportOptions`) through `buildClients`, `dispatchDevToolAction`, and `connectRequestStream`.
- **DevTool:** surface action failures in `ActionBar` via `ErrorAlert` — the `useActionDispatch().error` rejection **and** the active request stream's terminal `failed` status/`error` (dismissed on next send).
- **DevTool:** embedded-host `bearerToken` / `bearerTokenControl` props, with provider re-sync on host token rotation.
- **knowledge-hub:** unchanged flow auth (stays fail-closed). README documents the `KH_MCP_SECRET=test` local-DevTool path. Tests unchanged.
- **Docs:** new `apps/docs/docs/devtool/authentication.md`; cross-links from `devtool/setup.md`.
- **Changesets:** `patch` on `@flow-state-dev/devtool` only. No public API change to core/engine/client (the transport uses `ClientTransportOptions.fetcher`, which already exists).

**Size estimate:** **Small–Medium** — single package (devtool), 1 PR, ~180–260 LOC. No cross-package type changes; no knowledge-hub flow change.

## 2. Overview

**Problem:** DevTool sends flow actions with `userId` in the JSON body only. Flows that use `createBearerSecretPrincipalResolver` (knowledge-hub, knowledge-base prod, scheduled-dispatch patterns) require `Authorization: Bearer <secret>`. Without the header, `resolvePrincipal` returns `null` and the host rejects with `Action request requires non-empty userId` (HTTP 400). DevTool catches the error in `useActionDispatch` but `DevToolPanel` never renders it, so the UI looks idle.

**Secondary problem:** Bearer-gated flows often resolve to a **fixed** principal (`{ userId: "owner" }`) while DevTool defaults to `devuser`. Session creation trusts body `userId` (no bearer), so sessions are created as `devuser`. Action dispatch then resolves to `owner`, and execution rejects with `UserBindingMismatchError` — **after** a 202 accept, inside execution, not on the dispatch promise. The error message names the required userId; the fix is to surface it (§4.5) so the operator can set `userId` to match, not to add a metadata channel that restates it.

**Outcome:** An operator can drive a bearer-gated flow through DevTool against a local `fsdev dev` server: set the matching bearer token and userId in Settings, and every failure mode (missing/wrong token, mismatched userId) is visible in the action bar instead of a silent no-op.

## 3. Background & Research

### 3.1 Reproduced failure (2026-07-13)

| Step | Result |
|------|--------|
| `POST .../actions/logActivity` without `Authorization` | `400 {"error":"Action request requires non-empty userId"}` |
| Same with `Authorization: Bearer test` + session `userId: devuser` | `202` accepted, then `UserBindingMismatchError` at execution |
| Same with bearer + session created as `owner` | `202`, request `completed`, inbox write succeeds |

Session file evidence: `labs/knowledge-hub/.fsdev/data/sessions/sess_*.json` shows `"userId": "devuser"` from DevTool defaults.

### 3.2 Current DevTool request path

1. `ActionBar` → `DevToolPanel.handleSendAction` → `useActionDispatch.sendAction`
2. `dispatchDevToolAction` → `createClient({ flowKind, userId, baseUrl })` — **no `fetcher`**
3. `client.sendAction` → `requestJson` with headers `{ "content-type": "application/json" }` only
4. Parallel paths (sessions, recovery, debug, SSE) also omit auth

`ClientTransportOptions` (`packages/client/src/types/index.ts`) already models exactly what's needed — `{ baseUrl?: string; fetcher?: ClientFetch }` — and `fetcher` is the established extension point. No app in the monorepo uses it for bearer auth today.

### 3.3 Analogous patterns

| Pattern | Location | Relevance |
|---------|----------|-----------|
| `createBearerSecretPrincipalResolver` | `packages/engine/src/transports/auth/createBearerSecretPrincipalResolver.ts` | Server-side; returns `null` when header **absent** (→ 400 missing-user), throws **401** only on present-but-wrong token |
| MCP tests with `Authorization: Bearer test-secret` | `labs/knowledge-hub/test/config.spec.ts` | Proves authenticated HTTP works |
| `ErrorAlert` in flow list / session context | `packages/devtool/src/react/components/shared/error-alert.tsx` | Existing UI for surfacing errors |
| `use-request-stream` terminal state | `packages/devtool/src/react/hooks/use-request-stream.ts` | Exposes `status` (incl. terminal `failed`) + `error` string — the channel for post-202 failures |
| `readUserId` / `writeUserId` localStorage | `packages/devtool/src/react/config.ts` | Pattern for persisting standalone settings |
| knowledge-hub bearer auth | `labs/knowledge-hub/src/flow.ts`, README | Motivating flow; fail-closed, bearer required over HTTP |

### 3.4 Industry / ecosystem

DevTools and API consoles (Postman, Insomnia, OpenAPI explorers) universally support per-environment auth headers. Bearer token in settings is the minimal viable shape; generic header maps are more flexible but heavier to build and validate. Start with bearer — covers knowledge-hub, knowledge-base, and scheduled-dispatch flows without inventing a DevTool-specific auth protocol.

### 3.5 Necessity verdict

**Build as scoped.**

- **Existing primitive:** `createClient({ fetcher })` can wrap `fetch`, but DevTool never exposes it; an operator cannot configure auth without forking DevTool or embedding a custom panel.
- **What the spec adds:** First-class DevTool settings + threading across all panel HTTP/SSE paths + user-visible errors. Not a one-line wrapper — six call sites in DevTool must share the same fetcher.
- **Not building:** A DevTool-specific auth protocol, JWT parsing, changes to `resolvePrincipal` semantics, flow-level auth metadata, or any relaxation of knowledge-hub's fail-closed HTTP auth.

### 3.6 Key Decisions & Ramifications

1. **Client-side optional bearer only.** DevTool sends `Authorization` when a non-empty token is set and omits it when cleared. *Rejected:* relaxing servers to accept caller-chosen identity when a secret is absent (v1's symmetric-optional design — see Revision note; BP-031). *Ramification:* the server side is unchanged; knowledge-hub stays fail-closed and local dev sets `KH_MCP_SECRET=test`. The client half is the whole feature.

2. **Use the `fetcher` wrapper, threaded via `ClientTransportOptions`.** One `createAuthFetcher(bearerToken)` covers actions, sessions, recovery, debug, and SSE. *Rejected:* per-request `SendActionOptions.headers`. *Ramification:* empty/cleared token → passthrough fetch with no `Authorization` header. All four DevTool factories take a single `options: ClientTransportOptions` trailing param (see §4.3), composing the existing shape rather than adding a bespoke positional convention (BP-029).

3. **Bearer-only setting in DevTool v1 (`bearerToken: string`, clearable).** *Rejected:* arbitrary header map in settings UI. *Ramification:* operator clears the field (or saves empty) to opt out of client-side auth. HMAC/JWT flows still use the embedded `fetcher` escape hatch.

4. **Do not run session creation through `resolvePrincipal`.** *Rejected:* changing `handleCreateSession` to require bearer. *Ramification:* session routes stay simple; userId alignment is the operator's, guided by the surfaced error.

5. **Surface dispatch failures inline in ActionBar — both dispatch-promise rejections and terminal request-stream failures.** *Rejected:* a global toast layer; surfacing only the dispatch promise (misses the 202-then-`UserBindingMismatchError` path). *Ramification:* matches existing `ErrorAlert` usage; every failure mode in §3.1 becomes visible.

## 4. Technical Design

### 4.1 `createAuthFetcher` (devtool internal)

New file: `packages/devtool/src/react/lib/auth-fetcher.ts`

```ts
import type { ClientFetch } from "@flow-state-dev/client";

/** Wrap the global fetch to inject Authorization when a non-empty token is set. */
export function createAuthFetcher(
  bearerToken: string | undefined,
  baseFetcher: ClientFetch = fetch
): ClientFetch {
  const token = bearerToken?.trim();
  if (!token) return baseFetcher;
  return (input, init) => {
    // `new Headers(init?.headers)` preserves entries whether the caller passed a
    // Headers instance, a record, or an array — object spread drops a Headers
    // object's entries and would strip content-type / accept from real requests.
    const headers = new Headers(init?.headers);
    headers.set("authorization", `Bearer ${token}`);
    return baseFetcher(input, { ...init, headers });
  };
}
```

Use lowercase `authorization` — `Headers` normalizes; matches `createBearerSecretPrincipalResolver` default `headerName`.

### 4.2 DevTool config surface

Extend `DevToolConfig` (`packages/devtool/src/react/lib/client.ts`):

```ts
export type DevToolConfig = {
  userId: string;
  bearerToken?: string;
};
```

Extend `DevToolProvider` props:

```ts
export type DevToolProviderProps = {
  // existing...
  /** Initial bearer token. Standalone shell persists via localStorage; embedded hosts supply from server. */
  initialBearerToken?: string;
  /** When "internal", SettingsSheet edits bearer token. When "host", host owns it. Default "internal". */
  bearerTokenControl?: "internal" | "host"; // parallel to userIdControl
};
```

`packages/devtool/src/react/config.ts`:

```ts
const BEARER_TOKEN_KEY = "fsdev.devtool.bearerToken";

export function readBearerToken(): string;
export function writeBearerToken(token: string): void;
```

Persist on `setConfig` when `bearerTokenControl === "internal"` (mirror `userId`).

### 4.3 Thread fetcher through all DevTool clients

Commit the four client factories in `packages/devtool/src/react/lib/client.ts` to a single trailing `options: ClientTransportOptions` param (from `@flow-state-dev/client`), replacing the current bare `baseUrl?` positional. Same LOC, composes the existing shape (BP-029), and no factory ends up with a hand-rolled two-positional signature:

```ts
import type { ClientTransportOptions } from "@flow-state-dev/client";

export function createDevToolClient(config: DevToolConfig, options?: ClientTransportOptions): Client {
  return createClient({ flowKind: "__devtool__", userId: config.userId, ...options });
}
export function createDevToolSessionClient(options?: ClientTransportOptions): SessionClient {
  return createSessionClient(options);
}
export function createDevToolRecoveryClient(options?: ClientTransportOptions): RecoveryClient { ... }
export function connectRequestStream(
  flowKind: string,
  requestId: string,
  callbacks: Omit<CreateSSEClientOptions, "url" | "baseUrl">,
  options?: ClientTransportOptions,
): RequestStreamHandle {
  return createSSEClient({ ...callbacks, ...options, url: `/api/flows/.../stream?include=trace` });
}
```

`buildClients` in `devtool-context.tsx` builds one fetcher and passes it as `options`:

```ts
function buildClients(config: DevToolConfig, baseUrl: string | undefined) {
  const options = { baseUrl, fetcher: createAuthFetcher(config.bearerToken) };
  return {
    client: createDevToolClient(config, options),
    sessionClient: createDevToolSessionClient(options),
    recoveryClient: createDevToolRecoveryClient(options),
  };
}
```

`dispatchDevToolAction` accepts `bearerToken` and builds the fetcher the same way:

```ts
export function dispatchDevToolAction(..., options: { userId: string; baseUrl?: string; bearerToken?: string }) {
  const client = createClient({
    flowKind,
    userId: options.userId,
    baseUrl: options.baseUrl,
    fetcher: createAuthFetcher(options.bearerToken),
  });
  ...
}
```

`useActionDispatch` — pass `config.bearerToken` into `dispatchDevToolAction`. `connectRequestStream` call sites in `use-request-stream` / `use-continue-request` — pass `{ baseUrl, fetcher }`.

### 4.4 Settings UI

`SettingsSheet` additions (when `bearerTokenControl === "internal"`):

- Label: **Bearer token**
- `<Input type="password" autoComplete="off">` — masks token in UI; **clearable** (save empty string to remove)
- Helper text: *Leave blank for no auth header. When the server requires bearer (e.g. `KH_MCP_SECRET` is set), enter the matching secret.*
- **Clear** affordance: saving with an empty field calls `writeBearerToken("")` and removes persisted token from localStorage
- Save alongside `userId`

When `bearerTokenControl === "host"`: same copy as userId — "owned by host application."

**Client rule:** `createAuthFetcher` treats whitespace-only the same as empty — no `Authorization` header is sent.

### 4.5 Dispatch error surfacing

Two distinct failure surfaces, both must reach `ActionBar`:

**(a) Pre-execution HTTP rejection** — `useActionDispatch().error`. The dispatch promise rejects (e.g. 400 missing-user, 401 wrong token) before a request is accepted.

`DevToolPanel`:

```ts
const { sendAction, isSending, lastResponse, error: dispatchError } = useActionDispatch();
```

Improve the message for `ClientHttpError` — include status and the server `error` body field (`packages/devtool/src/react/hooks/use-action-dispatch.ts`):

```ts
if (err instanceof ClientHttpError) {
  const bodyMsg = typeof err.body === "object" && err.body && "error" in err.body
    ? String((err.body as { error: unknown }).error)
    : undefined;
  message = bodyMsg ?? `HTTP ${err.status}: ${err.message}`;
}
```

**(b) Post-acceptance execution failure** — the 202-then-fail path (`UserBindingMismatchError`). This never rejects the dispatch promise; it surfaces as the request stream's terminal `failed` status with an `error` string, which `use-request-stream` already exposes (`StreamStatus === "failed"`, `error`). `DevToolPanel` already consumes the request stream for the active request — surface its `error` when `status` is terminal-failed.

Render both above the send row via the existing `ErrorAlert`:

```tsx
{(dispatchError ?? requestStreamError) && <ErrorAlert message={dispatchError ?? requestStreamError} />}
```

`dispatchError` clears at the start of `sendAction` (already); `requestStreamError` is tied to the active request and is replaced when a new request starts. Without (b), a bearer-correct/userId-mismatch send stays silent — the exact "looks idle" symptom this issue targets.

### 4.6 knowledge-hub (unchanged flow; docs + local path only)

`labs/knowledge-hub/src/flow.ts` — **no change.** The flow stays fail-closed: `KH_MCP_SECRET` set → bearer resolver + `{ userId: "owner" }`; unset → the throwing resolver (HTTP unreachable). `fsdev.config.ts` — unchanged (MCP adapter still mounts only when the secret is set). `fsdev run` is unaffected (in-process `cli-user` principal, never through a transport resolver).

`labs/knowledge-hub/README.md` — document the local DevTool path:

```bash
# Local DevTool against knowledge-hub (bearer required — the path that exercises the feature):
KH_MCP_SECRET=test pnpm fsdev dev
# DevTool Settings: bearer token = test, user id = owner
# Create session (as owner) → logActivity → PASS
# Clear the bearer in Settings → send again → FAIL with a visible auth error in the action bar
```

**Tests** — `flow.spec.ts` is unchanged: secret unset → resolver throws on HTTP (existing behaviour 10); secret set → bearer resolver defined, wrong/absent bearer rejected. No new no-secret-open behaviour to add.

### 4.7 Embedded hosts

`DevToolPanel` / `DevToolProvider` gain optional `bearerToken?: string` and `bearerTokenControl?: "host" | "internal"` props (parallel to `userId`). When `bearerTokenControl === "host"`, the token can rotate on the host (login refresh, logout); the provider's external-config sync must include `bearerToken` in its comparison and effect deps — today it only re-syncs on `userId` change, which would leave the clients closed over a stale fetcher until remount. Rebuild clients (`buildClients`) whenever the effective `bearerToken` changes.

kitchen-sink embedding is unchanged — open flows without a bearer keep working (cleared token → passthrough fetch).

### 4.8 Standalone `fsdev dev` shell

`apps/devtool/src/App.tsx` — read `readBearerToken()` on mount (same as userId). No auto-fill from `KH_MCP_SECRET` in v1 (too implicit; see Open Questions).

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|------|-------------------|
| Empty/cleared bearer token in DevTool | No `Authorization` header; works against open flows |
| Bearer token set, server doesn't require it | Header sent but server ignores it; body `userId` used |
| Bearer token set, server requires it, token matches | Auth succeeds |
| Wrong bearer token | `401 Invalid scheduler secret.` surfaced in ActionBar (present-but-wrong → resolver throws 401) |
| Missing bearer against a bearer-gated flow | `400 {"error":"..."}` (absent header → resolver returns `null` → missing-user 400, **not** 401) surfaced in ActionBar |
| Bearer correct, userId mismatch | 202 accept, then `UserBindingMismatchError` — surfaced via the request stream's terminal `failed` error (§4.5b), naming the required userId |
| Init headers passed as a `Headers` object | `content-type`/`accept` preserved (via `new Headers(init?.headers)`) |
| Host rotates `bearerToken` (embedded, control=host) | Clients rebuild with the new fetcher on the next render; no stale credentials |
| `KH_MCP_SECRET` unset | knowledge-hub HTTP unreachable (fail-closed, unchanged) — set the secret for local DevTool |
| `KH_MCP_SECRET` set, DevTool bearer cleared | Auth failure surfaced in ActionBar |
| MCP endpoint | Still unmounted without server secret (unchanged) |

## 8. Non-Goals

- **Arbitrary custom headers UI** (API keys, tenant headers) — hosts pass `fetcher` when embedding; follow-up if needed.
- **`principalUserId` / `requiresBearer` flow metadata + DevTool hint banner** — cut from v1 (Revision note): the surfaced `UserBindingMismatchError` already names the required userId. Reconsider only if a metadata-driven affordance proves needed beyond the error message.
- **Relaxing knowledge-hub HTTP auth when the secret is unset** — rejected (BP-031, fail-closed). Local DevTool uses `KH_MCP_SECRET=test`.
- **Auto-reading `KH_MCP_SECRET` into DevTool** — convenient but implicit; open for v2.
- **Session creation through `resolvePrincipal`** — server change with broader blast radius.
- **DevTool auth for debug endpoints** — separate from flow `resolvePrincipal`; debug routes keep origin/loopback gating (`debug-vs-client-state.md`).
- **Changing knowledge-hub MCP fail-closed mount** — MCP adapter still requires `KH_MCP_SECRET`.
- **OAuth / JWT login UI in DevTool** — use embedded host + custom `fetcher` with `createHs256JwtVerifier` flows.

**Follow-up (deepening):** `dispatchDevToolAction` creates a fresh `createClient` per dispatch — consider a per-flow client cache keyed by `(flowKind, bearerToken)` if profiling shows churn.
