# FIX-895: Import tax-lot CSVs into the transaction ledger — Implementation Spec

## 1. TLDR

Brokerages export tax-lot CSVs (open lots and closed lots) that are not holdings snapshots and are not OFX. Today those files either corrupt basis if forced through Holdings CSV, or fail entirely on transaction import. This work adds a tax-lot CSV parser on the existing transaction-import path so both files feed the ledger as synthetic buys (and buy+sell pairs for realized lots).

**Technical statement:** Extend `detectAndParseTransactionFile` with a pure `parseTaxLotCsv` adapter that emits `FileLedgerEvent`s into the existing `importTransactionFile` → `ingestLedgerEvents` pipe.

**Deliverables:**

- Add `portfolio-tax-lot-csv.ts` under `labs/trading-desk/src/domain/portfolio/parsers/`
- Wire tax-lot sniff + parse into `transaction-file.ts` after OFX fails
- Accept `.csv` in `ImportTransactionsDialog` and update format labels/copy
- Soft-warn when a tax-lot unrealized file is opened on Holdings CSV import
- Extend `docs/transaction-import-formats.md` + brief `CLAUDE.md` note
- Vitest coverage for unrealized / realized / skips / warnings / dispatcher routing

**Size:** Medium (multi-file / 1 PR / ~200–400 LOC in trading-desk)

## 2. Overview

Linear: [FIX-895](https://linear.app/fixpoint-labs/issue/FIX-895)

Implements the broker-CSV follow-up (PR2) left open by FIX-775. Unrealized tax-lot rows become ledger buys; realized rows become buy+sell pairs keyed by open/close dates. Positions and realized gains continue to derive from FIFO (`deriveLots` / `materializePositions` / `materializeRealizedGains`) — no new ingestion path.

## 3. Background & Research

### Findings

- Holdings CSV (`portfolio-csv.ts`) maps `costBasis` as **average cost per share** and merges duplicate tickers. Tax-lot exports use `costBasis` as **lot total** and `unitCost` as per-share. Mapping the lot total into holdings cost would inflate basis by roughly quantity.
- Transaction import (`transaction-file.ts`) is OFX-only today; non-OFX returns a clear "broker CSV is a follow-up" error — this issue is that follow-up for one concrete header family.
- Ledger contract (`ingestLedgerEvents`, FIX-774): buy `+qty` / `−amount`; sell `−qty` / `+amount`. OFX already models this via `FileLedgerEvent`.

### Why this approach

| Approach | Verdict |
| --- | --- |
| Extend Import Transactions (detect + parse → same REST) | **Chosen** — reuses preview, append/replace, report, ingest |
| Separate tax-lot dialog/route | Rejected — duplicates plumbing |
| Generic multi-broker CSV mapper UI first | Rejected — YAGNI for one header shape |

### Key Decisions & Ramifications (top 5)

1. **Ledger reconstruction, not holdings snapshot.** Both files go through transaction import. *Rejected:* treating unrealized as Holdings CSV. *Locks in:* lot totals become cash amounts on buy events; positions derive from FIFO. *Rules out:* preserving broker lot identity in `app.holdings`.
2. **Single parser family for unrealized + realized.** Detect by headers (`closeDate`+`proceeds` ⇒ realized). *Rejected:* two unrelated importers. *Locks in:* one synonym table and shared externalId recipe. *Risk:* other brokers with different headers need later adapters in the same CSV branch.
3. **Synthetic events with stable `externalId`.** Format `taxlot:{kind}:{symbol}:{openDate}:{closeOrOpen}:{qty}:{costBasis}:{side}`. *Rejected:* null externalId (fingerprint-only). *Locks in:* safe re-import; *rules out:* collapsing distinct lots that collide on those fields.
4. **FIFO remains authority.** Broker `gainLoss` / specific-lot pairing are not stored as law. *Rejected:* writing realized gains from the CSV column. *Locks in:* honesty when interleaved lots differ from CSV; *ramification:* document that **account totals** match with complete history, per-lot attribution may not.
5. **Holdings path warns, does not auto-redirect.** Soft warning only. *Rejected:* silently reinterpret holdings upload as ledger. *Locks in:* surface boundaries stay clear for real-money trust.

## 4. Technical Design

### Architecture

```
CSV (unrealized|realized)
  → detectAndParseTransactionFile (sniff headers after OFX miss)
  → parseTaxLotCsv → FileLedgerEvent[]
  → importTransactionFile (inject accountId, source:"file")
  → ingestLedgerEvents
  → deriveLots → materializePositions + materializeRealizedGains
```

### Event synthesis

**Unrealized** (headers include `openDate`, `symbol`, `quantity`, `costBasis`, `unitCost`; no `closeDate`):

- One `buy` per row: `quantity > 0`, `amount = −|costBasis|` (lot **total**), `unitPrice = unitCost` (or `|amount|/qty` if unitCost blank), `tradeDate = openDate`

**Realized** (headers include `closeDate` + `proceeds`):

- `buy` on `openDate` as above
- `sell` on `closeDate`: `quantity = −|qty|`, `amount = +|proceeds|`, `unitPrice = pricePerUnit` when present

### Shared rules

- Prefer `symbol`; strip trailing `-BOND` (e.g. `71654QBR2-BOND` → CUSIP-shaped symbol); fall back to `cusip` when symbol fails `isImportableSymbol`, else `unresolvedSecurities` / skip
- `qty <= 0` → row skip with parse error (shorts out of scope, same as OFX)
- `washSale=true` → ingest + warning (no wash-sale basis math)
- Bad required fields → per-row `parseErrors`, never abort sibling rows
- Format labels: `tax-lot-unrealized` / `tax-lot-realized`

### Detection

After `looksLikeOfx` is false: normalize header cells (same strip/lower as holdings CSV). Match tax-lot if `symbol` (or synonym) + `quantity` + `costBasis` + `openDate` (+ `unitCost` preferred). Presence of `closeDate` and `proceeds` selects realized mode. Otherwise keep unrecognized error mentioning OFX **or** tax-lot CSV.

### API / UI

No new REST route. Existing `POST /api/portfolio/transactions/import` re-parses server-side. Dialog preview already surfaces format + counts.

## 5. Implementation Sequence

1. **Parser + unit tests** — `portfolio-tax-lot-csv.ts` with synthetic fixtures matching Schwab-style headers (trim of real files OK). Verify signs, amounts, externalIds, skips, wash-sale warning, `-BOND` strip.
2. **Dispatcher** — `transaction-file.ts` routes CSV; vitest for OFX unchanged + CSV branch.
3. **Dialog** — accept `.csv`, copy update.
4. **Holdings soft gate** — warning when tax-lot headers detected on holdings parse / dialog.
5. **Docs** — `transaction-import-formats.md` + `CLAUDE.md`.
6. **Manual goal check** — import both sample CSVs into a throwaway account via UI or curl; confirm holdings + realized gains tabs populate; re-import dedups.

## 6. Edge Cases & Error Handling

| Case | Behavior |
| --- | --- |
| Empty / header-only | warning; 0 events |
| Negative unrealized qty | skip + row error |
| Missing openDate / symbol / qty / cost | skip + row error |
| Realized missing closeDate or proceeds | skip + row error |
| Wash sale true | ingest + warning |
| Bond `CUSIP-BOND` | strip suffix; classify as bond when applicable |
| Duplicate re-import | `(source, externalId)` dedup |
| Tax-lot on Holdings CSV | top-level warning → use Import transactions |
| Mixed OFX+CSV same account | append OK; replace wipes |

## 7. Testing Strategy

**Goal:** A user can import paired unrealized + realized tax-lot CSVs into an account and see derived open positions plus realized disposals without hand-entering trades.

**Goal check (manual / non-CI):** Using the sample files (`*_tax_lot_unrealized.csv`, `*_tax_lot_realized.csv`) against a fresh account via Import transactions (append): holdings reflect open lots; Realized Gains tab shows closed sales; second identical import reports deduplicated counts. Pass/fail is visual + import report — no LLM required.

**Discipline:** `fsd:tdd` (Feature label).

**Behaviours to test (vitest):**

- Unrealized row → one buy with `−costBasis` amount and `+qty`
- Realized row → buy then sell with correct dates/signs/proceeds
- Negative qty skipped
- Wash-sale warning emitted
- `-BOND` symbol stripped
- Dispatcher: content with tax-lot headers → format `tax-lot-*`; OFX still works
- Holdings parser: tax-lot headers produce warning mentioning transaction import

## 8. Non-Goals

- Specific-lot identification / wash-sale adjustment
- Generic column-mapping UI for arbitrary broker CSVs
- Dividends, interest, deposits, transfers (absent from these files)
- Options tax-lot CSVs
- Changing Holdings CSV into a ledger writer
- Writing `gainLoss` / `term` from the file into `app.realized_gains` (derive instead)
