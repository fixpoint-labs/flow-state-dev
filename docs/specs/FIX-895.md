**D1 — No whole-account `replace` rebuild, no whole-account dedication.** Those
existed only to make destructive whole-account replace safe. v1 is **append-only**
into an account that has no *conflicting per-ticker* history. The single enforced
structural rule is the **per-`(account, ticker)` symmetric one-source seam
invariant** (§ "One-source-per-ticker invariant"): a ticker's share-moving events
are all keyed or all unkeyed, both import orders refused. `replaceLedgerFromFile`
is **not** used by this feature. This dissolves the Greptile "rebuild drops
unrestored tax years" P1 (no destructive replace exists) and the Codex "enforce
dedication on subsequent writes" P1 (a later dividend/cash event cannot corrupt
lots when there is no replace — `deriveLots` ignores cash events; the per-ticker
invariant is all that guards lot derivation). A dedicated account remains a
*documented recommendation*, not an enforced whole-account precondition. The
pre-existing cross-feed CUSIP↔ticker limitation is accepted as-is (already
documented), not guarded by bespoke code.

**D2 — No in-place refresh of an existing tax-lot account's unrealized snapshot in
v1.** A fresher unrealized snapshot (lots that closed since the last import) →
**fresh account** (re-import the current files clean). Adding a *new disjoint*
realized tax-year file to an existing tax-lot account still works (append; disjoint
by `closeDate`). This is the one capability reduction; it matches the approved
fresh-start posture. In-place account update is future work.

**D3 — Reject rows whose currency ≠ the target account's currency.** Holdings
derivation is currency-blind (`deriveLots` sums open lots into one numeric
`avgCost`; `Holding` stores no currency; the UI formats basis in the account
currency), so *preserving* a foreign currency on the ledger event would still
mislabel a EUR lot as USD in holdings and sum it with USD lots. Accounts are
single-currency in v1, so the parser/import **skips a row whose currency differs
from the target account** with a per-row parse error (never the silent USD
default). (Resolves Codex P1 "keep foreign lots out of holding totals".)

**D4 — `seq` preserves row multiplicity; identical lots both land.** `seq` is the
1-based index within the content-sorted `(symbol, openDate[, closeDate])` group,
assigned to **every** row in the group **including exact duplicates** — two
genuinely identical broker lots get `seq` 1 and 2 and **both persist**. Idempotency
does NOT come from collapsing identical rows; it comes from re-importing the *same
file* re-deriving the *same* `seq`/`lotKey` and deduping on the
`(accountId, source, externalId)` index. (Resolves Codex P1 "preserve multiplicity"
and the §4 #4 self-contradiction that called identical rows "genuine duplicates
[that] dedup".)

**D5 — Null the aggregate holding basis when ANY open keyed lot lacks basis.**
`materializePositions` must persist a null/flagged cost basis for a ticker whenever
any of its open keyed lots has `basisUnknown`, instead of presenting a partial
average (basis of only the known lots) as the whole position's cost. (Resolves
Codex P1 "null aggregate basis when any imported lot lacks basis".)

**D6 — Fresh-start wipe is an unambiguous prerequisite; the fingerprint recipe is
gated on the wipe sentinel.** The unconditional `|lk|ck|` fingerprint change is only
safe on a cleared ledger, so Impl step 0's destructive wipe runs first and the new
`computeFingerprint` recipe activates **only** behind a sentinel proving the wipe
ran. Any "no marker gating needed" phrasing below is superseded. (Resolves Codex P1
"keep the fingerprint rollout gate in the technical contract".)

**Unchanged and still in force:** the specific-lot `deriveLots` change (keyed
disposal splices its own lot, never FIFO-falls-back — unmatched → `lot-not-found`);
lot-identity fields additive/nullable on the ledger; `recordManualEvent` nulls the
lot fields; split branch skips keyed lots; per-row honesty markers
(`basisUnknown`/`proceedsUnknown`); OCC-option skip; `-BOND` strip; ticker
upper-canonicalization before ticker AND `lotKey`; `closeDate >= openDate`
cross-check; holdings-snapshot discrimination; the seam invariant's
`voided_at IS NULL` predicate and lock-before-read serialization.

## 1. TLDR

Brokerages export **tax-lot CSVs** — an *unrealized* file (every currently-open
lot) and a *realized* file (every closed lot, with the exact acquisition it was
matched against). These are not holdings snapshots and are not OFX. Today they
either corrupt basis if forced through the Holdings CSV path, or fail entirely on
transaction import. This work adds a tax-lot CSV parser on the existing
transaction-import path so both files feed the ledger and reconstruct **both open
positions and realized gains accurately**.

The load-bearing design choice: a realized tax-lot row is a **specific-lot
disposal** — the broker already told us *which* lot closed, its basis, and its
holding period. FIFO (`deriveLots` consuming the oldest open lot first) cannot
honor that when a ticker has more than one lot, so it would silently close the
wrong lot and mis-report basis/term/gain. Rather than accept that inaccuracy (or
cut realized from scope), this spec carries **lot identity** through the ledger so
a tax-lot disposal consumes *its own* paired lot. FIFO stays the default for feeds
that carry no lot identity (OFX, Plaid, manual) — unchanged.

**Technical statement:** Extend `detectAndParseTransactionFile` with a pure
`parseTaxLotCsv` adapter that emits lot-identity-bearing `FileLedgerEvent`s into
the existing `importTransactionFile` → `ingestLedgerEvents` pipe, and extend
`deriveLots` to consume a specifically-referenced lot when a disposal carries one
(FIFO fallback preserved).

**Deliverables:**

- Add `portfolio-tax-lot-csv.ts` under `labs/trading-desk/domain/portfolio/parsers/`
- Add optional lot-linkage fields (`lotKey` / `closesLotKey`) to the ledger event
  contract + `app.ledger_events` columns; teach `deriveLots` specific-lot
  consumption (FIFO fallback when absent)
- Wire tax-lot sniff + parse into `transaction-file.ts` after OFX fails
- Enforce a symmetric one-source-per-ticker invariant at the shared ingest seam:
  keyed and non-keyed share history for a ticker never mix, in either import
  order (tax-lot-after-OFX AND OFX-after-tax-lot both refuse)
- Accept `.csv` in `ImportTransactionsDialog` and update format labels/copy
- Soft-warn when a tax-lot unrealized file is opened on Holdings CSV import
- Extend `docs/transaction-import-formats.md` + brief `CLAUDE.md` note
- Vitest coverage: unrealized / realized / specific-lot matching / skips / warnings
  / dispatcher routing / mixed-source refusal

**Size:** Medium–large (multi-file / 1 PR; parser + a bounded, additive extension
to the lot engine and ledger schema — no change to existing FIFO behavior for
existing feeds).

## 2. Overview

Linear: [FIX-895](https://linear.app/fixpoint-labs/issue/FIX-895)

Implements the broker-CSV follow-up (PR2) left open by FIX-775. Unrealized tax-lot
rows become ledger buys; realized rows become **linked buy+sell pairs** that
reconstruct the exact disposal the broker reported. Open positions and realized
gains still DERIVE from the ledger (`deriveLots` / `materializePositions` /
`materializeRealizedGains`) — no new ingestion path, no stored broker `gainLoss`
as law — but derivation now honors the lot identity the file carries, so the
derived result matches the broker's specific-lot attribution instead of a FIFO
guess.

## 3. Background & Research

### Findings

- Holdings CSV (`portfolio-csv.ts`) maps `costBasis` as **average cost per share**
  and merges duplicate tickers. Tax-lot exports use `costBasis` as **lot total**
  and `unitCost` as per-share. Mapping the lot total into holdings cost would
  inflate basis by roughly quantity.
- Transaction import (`transaction-file.ts`) is OFX-only today; non-OFX returns a
  clear "broker CSV is a follow-up" error — this issue is that follow-up for one
  concrete header family.
- Ledger contract (`ingestLedgerEvents`, FIX-774): buy `+qty` / `−amount`; sell
  `−qty` / `+amount`. OFX already models this via `FileLedgerEvent`.
- **`deriveLots` is FIFO-only (`math/lots.ts`).** A disposal consumes `lots[0]`
  (oldest open lot) — `lots.ts` sorts by `tradeDate` then shifts from the front.
  A realized tax-lot row names a *specific* lot (open date + basis) that is often
  not the oldest (specific-ID / average-cost / LIFO brokers). Feeding it through
  FIFO can consume a lot that is still open in the unrealized file, corrupting
  both open holdings and the realized gain/term. **This is the core problem this
  spec must solve, not document around.**
- **The ledger already has precedent this design reuses:** `attributes` (jsonb)
  carries corporate-action payload on `split` events (FIX-876) — additive,
  type-gated per-event data. The lot-linkage fields follow the same additive
  shape.
- **Fresh start (no backfill / no back-compat contortion).** The desk's ledger is
  still early; the user has approved a one-time **wipe of existing accounts** to
  land this feature cleanly. So we do NOT preserve byte-identical fingerprints on
  existing rows or add dual-read/backfill paths: `computeFingerprint` simply gains
  the linkage fields, and the new `lot_key` / `closes_lot_key` columns are a plain
  additive migration with no data backfill. Ongoing, incremental use is fully
  supported (append more files, add transactions, update accounts over time) — it
  is only the *one-time* back-compat with already-persisted rows that we drop.
- **The ingest seam facts that constrain the design** (`db/repository.ts`):
  the `(account_id, fingerprint)` unique index is **unconditional** and inserts
  run `ON CONFLICT DO NOTHING` — so distinct `externalId`s alone canNOT make two
  content-identical rows both land; the fingerprint itself must carry the linkage
  fields (added unconditionally — fresh start, no marker needed). And the file
  importer
  **bypasses the zod schema** — `ingestEventsInTx` runs only
  `assertShareEventInvariant` on every writer's rows — so any new cross-field
  invariant must ALSO live in that shared assert, not just in the zod refine.
- **A synthesized field-derived `externalId` adds no dedup power.** The
  original spec's `taxlot:{kind}:{symbol}:{openDate}:{closeOrOpen}:{qty}:{costBasis}:{side}`
  encodes exactly the fields `computeFingerprint` already hashes
  (`accountId|tradeDate|type|ticker|quantity|amount`, `db/repository.ts`). Ticker
  = symbol, tradeDate = openDate, type = side, quantity = qty, amount = ±costBasis
  — identical collision profile as plain fingerprint dedup. It is a redundant
  second design surface, dropped here. What genuinely distinguishes two otherwise-
  identical lots is a **within-file row discriminator** — new information the
  fingerprint does not carry — which this spec introduces as *lot identity* (it is
  also what the realized-disposal linkage needs), not as a dedup trick.

### Why this approach

| Approach | Verdict |
| --- | --- |
| Extend Import Transactions (detect + parse → same REST) | **Chosen** — reuses preview, append/replace, report, ingest |
| Carry lot identity so realized disposals consume the specific broker-matched lot | **Chosen** — the only way FIFO-derived storage can reproduce a specific-lot file accurately |
| Ship unrealized-only, defer realized | Rejected — realized is half the value (paired export), and lot identity makes it correct rather than "documented as maybe-wrong" |
| Store the broker `gainLoss` column as authority | Rejected — derivation stays the authority; lot identity just makes the derivation consume the right lot |
| Separate tax-lot dialog/route | Rejected — duplicates plumbing |
| Generic multi-broker CSV mapper UI first | Rejected — YAGNI for one header shape |

### Key Decisions & Ramifications

1. **Ledger reconstruction, not holdings snapshot.** Both files go through
   transaction import. *Rejected:* treating unrealized as Holdings CSV. *Locks in:*
   lot totals become cash amounts on buy events; positions derive from the ledger.
   *Rules out:* preserving broker lot identity in `app.holdings` (it lives on the
   ledger events instead — see #3).

2. **One parser family for unrealized + realized.** Detect by headers
   (`closeDate` + `proceeds` ⇒ realized). *Rejected:* two unrelated importers.
   *Locks in:* one synonym table, one synthesis path. *Risk:* other brokers with
   different headers need later adapters in the same CSV branch.

3. **Lot identity travels on the event; FIFO is the fallback, not the law.** Each
   tax-lot buy carries a stable `lotKey`; each realized sell carries a
   `closesLotKey` pointing at its paired buy. `deriveLots` consumes the referenced
   lot specifically when a disposal names one, and falls back to oldest-first FIFO
   when it does not (OFX / Plaid / manual — bit-for-bit unchanged, BP-030).
   *Rejected:* synthesizing a field-derived `externalId` (adds no disambiguating
   power, §3 Findings) and *rejected:* FIFO-only (structurally wrong for
   specific-lot files). *Locks in:* a realized disposal reproduces the broker's
   exact lot basis, holding period, and gain. *Ramification:* a ticker's lots must
   come from ONE lot-identity-carrying source — enforced by the symmetric
   one-source invariant (#5).

4. **The lot key is genuine identity, and it doubles as the dedup key.** The key
   carries the dates that identify a lot's life:
   - unrealized: `lotKey = taxlot:u:{symbol}:{openDate}:{seq}`
   - realized: `lotKey = taxlot:r:{symbol}:{openDate}:{closeDate}:{seq}`

   `seq` is the 1-based rank *among rows sharing the key's date tuple*, assigned
   in a **canonical content order** — sort the group by `(quantity, costBasis,
   proceeds)` and number from 1 — **NOT raw file order**. Content-ordering makes
   the key a deterministic function of the row set, not its arrangement: a broker
   re-export that lists the same lots in a different order yields identical
   `seq`/`lotKey`/fingerprint, so a re-import still dedups instead of doubling the
   position. (Two rows fully identical on `(symbol, openDate, closeDate, quantity,
   costBasis, proceeds)` sort adjacent and receive **distinct** `seq` values (1, 2,
   …) — a broker can legitimately hold two identical lots, so **both persist**;
   idempotency comes from re-importing the *same file* re-deriving the *same* keys
   and deduping on `(source, externalId)`, per §0 D4, NOT from collapsing identical
   rows.) Scoping the *key text* to the dates (not qty/basis) keeps it compact
   while the canonical sort supplies the tie-break. **`kind` namespaces the paired files** (the partial-close case:
   an open remainder in the unrealized file and a closed portion in the realized
   file share `(symbol, openDate)` but never collide). **`closeDate` namespaces
   *same-kind* realized files**, which are additive across tax years (a 2024
   realized export and a 2025 one, unlike unrealized snapshots that rebuild via
   whole-account `replace` #5): two partial disposals of the same acquisition-date lot
   in different years would otherwise both be `taxlot:r:{symbol}:{openDate}:1` and
   the later buy+sell would drop on the external-id index. With `closeDate` in the
   key, each disposal — and its synthesized acquisition leg — is distinct across
   files (rebuild overlapping exports via `replace`, #5). *Residual constraint:* `seq` is still per-file, so two realized exports
   that both contain a row with the identical `(symbol, openDate, closeDate)`
   would restart `seq=1` and collide. That is only possible for **overlapping**
   realized exports (the normal multi-year case is disjoint by close date);
   overlapping/re-cut realized files must be rebuilt via whole-account `replace`
   (safe in a dedicated account, #5), never appended — the same posture as the
   evolved-export recovery. Disjoint realized files append safely. The buy's
   `externalId` is set to `lotKey`, the sell's to
   `{lotKey}#d`, so the existing `(accountId, source, externalId)` unique index
   makes re-importing the same file idempotent. **Identical lots also need the
   fingerprint to distinguish them**: the `(account_id, fingerprint)` index is
   unconditional with `ON CONFLICT DO NOTHING`, so `computeFingerprint` gains the
   linkage fields **directly** — `…|lk:{lotKey ?? ""}|ck:{closesLotKey ?? ""}` —
   which separates two content-identical keyed lots (and two same-date/qty/proceeds
   sells of *different* lots), while unkeyed rows (both fields empty) keep hashing
   as before. We take a **one-time fresh start** for the desk's ledger (§3 →
   Fresh start), so this is a plain unconditional recipe change — no
   conditional-marker/no-migration contortion. *Rejected:* null
   `externalId` + accept the identical-lot collapse — acceptable for FIFO-only
   manual entry, but here it would break disposal linkage (a sell could not name
   its lot unambiguously). *Ramification:* `seq` is stable across re-imports of
   the same file; an *evolved* export (a lot moved from open to closed between
   exports) is rebuilt via the paired replace workflow (#5), never by appending
   evolving files.

5. **One source per ticker — tax-lot imports require a clean account for their
   tickers; the design keeps sources apart rather than reconciling a mix.** The
   invariant: within an account, a ticker's share-moving events (`quantity IS NOT
   NULL` — buy, sell, AND transfer, since `deriveLots` is sign-driven and
   transfers open/consume lots too) are either all lot-keyed or all non-lot-keyed,
   never mixed. Two layers enforce this so the "dedicated account" is a real
   invariant, not just advice:
   - **Per-`(account, ticker)` at the shared seam** (`assertShareEventInvariant`
     + an `ingestLedgerEvents` check): a batch that would put keyed and unkeyed
     share events under the same ticker is rejected. Binds every writer,
     symmetrically (a tax-lot CSV onto unkeyed history AND an OFX/manual share
     event onto keyed history both refuse).
   - **Whole-account dedication at the tax-lot import**
     (`importTransactionFile`): a tax-lot file lands **only into a tax-lot-
     dedicated account** — one whose ledger holds *nothing but* tax-lot keyed
     share events (an empty account qualifies). If the account has ANY other
     history — unkeyed share events, OR cash/dividend/interest/transfer events
     (even for tickers the file doesn't cover) — the file is **refused whole**
     (0 events) with guidance to use a **fresh account**. This is what makes the
     escape hatch coherent: once an account is provably tax-lot-only, whole-
     account `replace` has nothing else to destroy. *Accepted limitation:* a
     tax-lot-dedicated account tracks positions + realized gains only; dividends/
     interest for those securities live in the feed-based (OFX/Plaid) account,
     consistent with the Non-Goals (the tax-lot files carry no income rows).
   The manual route surfaces its seam rejection to the dialog. *Rejected:* the per-ticker **clear-and-merge**
   alternative (a targeted-clear primitive + orphan reconciliation + partial-file
   ingest + union rebuilds) — real machinery and a recurring correctness-edge
   source, to support mixing feeds in one account that the app doesn't need. A
   dedicated account is the honest, simple boundary (BP-038). *Resolving a
   conflict* (an existing account already holds OFX/manual/dividend history for
   the ticker): the answer is a **fresh/dedicated account** for the tax-lot
   import — NOT whole-account `replace`, which clears the entire account ledger
   and would destroy that account's dividends, interest, cash events, manual
   corrections, and other tickers. `replace` is reserved for **rebuilding within
   an already tax-lot-dedicated account** (an evolved/overlapping export, #4/#7),
   where by construction there is no non-tax-lot history to lose; the pre-check
   never points a mixed account at `replace`. *Keyedness* is
   `lotKey ?? closesLotKey` (a sell carries only `closesLotKey`). *Idempotency-
   safe:* re-importing the same tax-lot CSV, or importing the paired realized
   file after the unrealized one, is same-kind (keyed) onto keyed history — never
   a conflict; it dedups/coexists.

6. **FIFO gain math is unchanged; only the consumed lot changes.** Realized gain is
   still derived as `proceeds − costBasis` over consumed lots
   (`materializeRealizedGains`), never read from the broker `gainLoss` column
   (Non-Goals). Because the sell now consumes its *paired* lot, the derived basis,
   term, and gain equal the broker's specific-lot figures (up to rounding). Where
   the file is internally inconsistent (proceeds/qty missing, currency mismatch),
   the existing honesty rules still null the affected side rather than fabricate.

7. **Splits never rebase lot-keyed lots.** A broker's tax-lot export reports
   quantities and basis **already adjusted** for every split up to the export
   date, so a `split` event (manual, OFX, or the provider backfill — which writes
   splits dated on/after the account's first trade in the ticker) rebasing a
   synthetic lot would double-adjust it: phantom open remainder or a spurious
   over-sell on a lot that spans the split date. `deriveLots`' split branch skips
   lots carrying a `lotKey`, and `backfillSplits` skips **`(account, ticker)`
   pairs** whose **non-voided** share history is entirely lot-keyed (the
   one-source policy is account-local, and the backfill is already keyed by
   `earliestByAcctTicker` — a household-wide ticker skip would suppress a split
   another account's unkeyed OFX history still needs; voided rows are excluded so
   a tombstone can't misclassify the ticker). *Accepted
   limitation:* a REAL split occurring **after** the export date will not rebase
   the keyed lots either — the recovery is re-export fresh files (the broker will
   have adjusted them) and rebuild via whole-account `replace` (safe in a
   tax-lot-dedicated account, #5) with the unrealized file then `append` **every**
   realized slice, documented in the import-formats doc. Tested with an
   acquisition/disposal pair spanning a split.

8. **Holdings path warns, does not auto-redirect.** Soft warning only when tax-lot
   headers land on the Holdings CSV importer. *Rejected:* silently reinterpret a
   holdings upload as a ledger import. *Locks in:* surface boundaries stay clear.

### Lot identity (the ledger extension)

Two nullable fields, added additively to `LedgerEventInput` / `LedgerRow` and the
`app.ledger_events` table:

- `lotKey: string | null` — on an **acquisition** (buy/transfer-in), the stable
  identity of the lot it opens. Null for every feed that carries no lot identity.
- `closesLotKey: string | null` — on a **disposal** (sell/transfer-out), the
  `lotKey` of the lot it closes. Null ⇒ FIFO.

Boundary rules (mirroring the split invariant's discipline): `closesLotKey` is
valid only on a share-removing event; `lotKey` only on a share-adding event; both
null on cash events and splits. Enforced in **two places**, because the file
importer bypasses zod: (1) `refineLedgerEvent` for the zod-validated routes, and
(2) the repository's shared `assertShareEventInvariant` — the one assert every
writer funnels through (`ingestEventsInTx`) — so a parser regression cannot
persist a malformed pairing either.

The fields are **feed-owned, like `proceedsUnknown`**: `recordEventSchema` (the
manual-entry omit) excludes both, and `recordManualEvent` forces them null at the
service boundary — a manual API caller cannot assign or close keyed lots.

Dedup, two tiers as today: `externalId = lotKey` (buy) / `${lotKey}#d` (sell) on
the `(accountId, source, externalId)` index for same-file re-import idempotency;
and `computeFingerprint` gains both linkage fields **unconditionally** —
`…|lk:{lotKey ?? ""}|ck:{closesLotKey ?? ""}`. Both fields (not just `lotKey`)
matter because a sell's `lotKey` is null: a lotKey-only term would leave two
same-date/qty/proceeds sells of different lots with identical fingerprints, and
the unconditional `(account_id, fingerprint)` index with `ON CONFLICT DO NOTHING`
would silently drop one. Unkeyed rows (both empty) hash exactly as before; the
one-time fresh start (§3) means the recipe change needs no marker gating or
migration.

### `deriveLots` change (bounded, additive)

Today: a disposal consumes `lots[0]` repeatedly (oldest-first). Change: when the
disposal's `closesLotKey` is set, find the open lot for the ticker whose `lotKey`
matches and consume *that* lot (splice, not shift). **A keyed disposal never
falls back to FIFO**: if the referenced lot is not open (evolved/partial file,
or already consumed), the sell emits an unmatched disposal — real proceeds,
unknown acquisition/basis/term, a `lot-not-found` reason (the
`makeUnmatchedDisposal` honesty path) — and consumes nothing. Silently switching
to FIFO would consume an unrelated lot *without* tripping the over-sell signal,
fabricating a plausible-but-wrong basis/term/gain — the exact corruption lot
identity exists to prevent. When `closesLotKey` is null, the loop is
byte-for-byte the current FIFO behavior. `OpenLot` gains an optional `lotKey`
carried from the acquiring buy; the `split` branch **skips keyed lots** (Key
Decision #7 — broker tax-lot files are already split-adjusted as of export).
Everything downstream (`makeDisposal`, term classification, over-sell nulling,
`materializePositions`, `materializeRealizedGains`) is unchanged — it operates on
the consumed lot, which is now the *correct* lot.

### Event synthesis

**Unrealized** (headers include `openDate`, `symbol`, `quantity`, `costBasis`,
`unitCost`; no `closeDate`):

- One `buy` per row: `quantity = +|qty|`, `amount = −|costBasis|` (the lot
  **total** is authoritative), `tradeDate = openDate`, `lotKey` assigned,
  `currency` from the file/account (never the USD default — Shared rules).
- `unitPrice = |costBasis| / qty` (derived from the authoritative total), **not**
  the broker's `unitCost` — `deriveLots` prefers `unitPrice` over `amount/qty`, so
  a rounded/adjusted `unitCost` would drive holdings/basis away from the lot total
  this spec treats as truth. (Equivalently, leave `unitPrice` null and let `amount`
  drive basis; setting it from `costBasis/qty` keeps a sensible per-share display.)
- **Missing basis:** if `costBasis` is blank, the buy still lands with
  `amount = 0`, `unitPrice = null`, `basisUnknown` set (see Shared rules) — the
  position is preserved, the basis honestly unknown.

**Realized** (headers include `closeDate` + `proceeds`):

- `buy` on `openDate` exactly as above, with the realized `lotKey`
  (`taxlot:r:{symbol}:{openDate}:{closeDate}:{seq}` — the `closeDate` ties this
  synthesized acquisition leg to *its* disposal, so two partial closes of the
  same acquisition-date lot across tax-year files stay distinct).
- `sell` on `closeDate`: `quantity = −|qty|`, `amount = +|proceeds|`,
  `unitPrice = pricePerUnit` when present, `closesLotKey = lotKey`. A blank
  `proceeds` records the sell with the `proceedsUnknown` marker (Shared rules)
  rather than dropping it — the disposal, its basis, and its term still land.

The buy+sell are synthesized together from one row, so the pairing is exact and
local. Because a closed lot is never in the unrealized file (disjoint sets),
importing both files reconstructs the full history with no overlap: `Σ` open lots
(unrealized) + the buy legs of closed lots (realized) = every acquisition; the
sell legs = every disposal.

### Shared rules

- **Canonicalize the ticker to upper-case FIRST** (`canonicalTickerKey`, the same
  helper manual entry / holdings import / quote lookup use), before it becomes the
  event `ticker` AND before it is interpolated into the `lotKey`. `isImportableSymbol`
  only upper-cases its *local* validation copy, so a broker's `aapl` would
  otherwise persist as `aapl` and build a lowercase `lotKey` — a holdings /
  source-isolation group distinct from the canonical `AAPL`. Parser tests cover
  mixed-case input.
- Prefer `symbol`; strip trailing `-BOND` (e.g. `71654QBR2-BOND` → CUSIP-shaped
  symbol); fall back to `cusip` when symbol fails `isImportableSymbol`, else
  `unresolvedSecurities` / skip. A CUSIP-keyed row inherits the pre-existing
  cross-feed CUSIP↔ticker limitation (`transaction-import-formats.md` — a CUSIP
  and a ticker for the same security don't match across feeds); the
  dedicated-account rule (Key Decision #5) is what keeps that from double-counting
  in practice, so no bespoke alias guard is added here.
- **Reject OCC option symbols.** `isImportableSymbol` deliberately *accepts*
  OCC/OSI option symbols, but option tax-lot CSVs are a Non-Goal (contract
  multipliers + open/close semantics unmodeled — the OFX importer skips options
  for the same reason). A row whose symbol classifies as an option is skipped
  with a parse error, never fed to the share-lot engine.
- **Currency comes from the file or the target account, never the USD default.**
  A synthesized event's `currency` is read from a file currency column when the
  format supplies one, else injected from the target account's `currency` at the
  server boundary (`importTransactionFile`, alongside `accountId`/`source`).
  Falling through to the ledger's `"USD"` default would label a foreign lot's
  basis/proceeds as USD, and the tax estimator counts only `currency === "USD"`
  rows — so foreign gains would be silently taxed. (Multi-currency remains
  excluded from the *estimate* as today; the point is honest labeling, not
  estimation.)
- `qty <= 0` → row skip with parse error (shorts out of scope, same as OFX).
- `washSale=true` → ingest + warning (no wash-sale basis math).
- **Represent, don't drop, on a missing MONEY field** (the existing
  honest-basis machinery, not a skip):
  - **Blank/unavailable `costBasis`** (a noncovered or transferred lot) → still
    import the buy with `amount = 0`, `unitPrice = null`, and `basisUnknown` set
    (an `"import-missing-basis"` reason). `deriveLots` already nulls
    `costPerShare` when `basisUnknown !== null`, so the shares land and the gain
    is honestly excluded — dropping the row would lose the position entirely.
  - **Blank/unavailable `proceeds`** on a realized row → record the sell with the
    import-only `proceedsUnknown` marker (FIX-874), which nulls proceeds/gain in
    derivation while keeping the disposal, its basis, and its holding period.
- **Truly unrepresentable rows skip** — only a missing `symbol`, `qty`, or the
  event's own DATE (`openDate` for a buy, `closeDate` for a sell) makes a row
  unrepresentable → per-row `parseError`, never abort sibling rows.
- **`closeDate >= openDate` cross-check** on realized rows: a close-before-open
  row would sort the synthetic sell *ahead* of its paired buy in `deriveLots`,
  leaving the sell unmatched and the buy a phantom open holding. Reject the row
  with a parse error (same-day acquire+sell is allowed).
- Format labels: `tax-lot-unrealized` / `tax-lot-realized`.

### Detection

After `looksLikeOfx` is false: normalize header cells (same strip/lower as
holdings CSV). Match tax-lot if `symbol` (or synonym) + `quantity` + `costBasis` +
`openDate` + **`unitCost` (required, not preferred)**. Presence of `closeDate`
AND `proceeds` selects realized mode. Two hard gates keep the signature honest:

- **Incomplete realized headers → reject the file.** `closeDate` without
  `proceeds` (or vice versa) is evidence of an intended realized export with an
  unrecognized counterpart column — rejecting beats parsing it as unrealized and
  synthesizing phantom open buys for already-closed lots.
- **Holdings-snapshot discrimination.** A holdings snapshot (symbol / quantity /
  per-share avg `costBasis` / acquired date) can satisfy the loose signature, and
  misreading its per-share basis as a lot total is exactly the corruption in the
  TLDR. Beyond requiring `unitCost`, the parser cross-checks each multi-share row:
  a tax-lot file satisfies `costBasis ≈ unitCost × quantity` (lot total); a
  holdings file reads `costBasis ≈ unitCost` (per-share). When the majority of
  multi-share rows look per-share, **refuse the file** with a message directing
  the user to the Holdings CSV import — never synthesize events from an
  ambiguous basis convention.

Otherwise keep the unrecognized-format error mentioning OFX **or** tax-lot CSV.

### One-source-per-ticker invariant + clean-account rule

The invariant (Key Decision #5): within an account, a ticker's **share-moving**
events (`quantity IS NOT NULL` — buy, sell, and transfer; `deriveLots` is
sign-driven, so transfers open/consume lots too) are all **keyed** or all
**unkeyed**. *Keyed* means `lot_key IS NOT NULL OR closes_lot_key IS NOT NULL` —
a realized **sell** carries only `closesLotKey` (its `lotKey` is null), so a bare
`lot_key IS NULL` test would misclassify every disposal as unkeyed and refuse the
unrealized half of the very same paired import. Keyedness is therefore
`lot_key IS NOT NULL OR closes_lot_key IS NOT NULL`. The design **keeps sources
apart** rather than reconciling a mix, so enforcement is a plain refusal — no
clear/merge machinery:

- **Shared seam.** `ingestLedgerEvents` checks each incoming share event's
  `(accountId, ticker)` group against (1) the rest of the batch and (2) the
  ticker's existing **non-voided** history: if either would put a keyed and an
  unkeyed share event under the same ticker, the batch is **rejected and rolled
  back**. The history predicate requires `voided_at IS NULL` — a voided tombstone
  keeps its quantity/linkage fields but is excluded from `deriveLots`, so counting
  it would permanently block a legitimate void-then-reimport of the other source.
  Binds every writer (import, manual, future Plaid) symmetrically — a tax-lot CSV
  onto unkeyed history AND an OFX/manual share event onto keyed history both
  refuse. `assertShareEventInvariant` carries the field-level rule (lot fields
  only on the right event kind), so the file path (which bypasses zod) is covered
  too. **Serialization:** the existing per-account advisory lock is acquired
  **before** the history read (today it's taken after insertion), so two
  concurrent imports of the same empty ticker can't both pass the check and land
  a keyed + an unkeyed batch.
- **Whole-account dedication pre-check.** `importTransactionFile` (tax-lot
  formats) additionally requires the target account to be **tax-lot-dedicated**:
  a single query rejects the file (0 events, friendly report → use a fresh
  account) if the account holds ANY event that is not a tax-lot keyed share event
  — an unkeyed share event, or any cash/dividend/interest/transfer row, for any
  ticker. This is stricter than the per-ticker seam check (which only sees the
  covered tickers) and is what guarantees the `replace` rebuild path has no
  unrelated history to erase. An empty account passes.
- **Escape hatch — no new primitive, and never `replace` on a mixed account.**
  Two distinct cases, kept separate:
  - **A source conflict** (an existing account already has OFX/manual/dividend
    history for the ticker) → use a **fresh/dedicated account** for the tax-lot
    import. The pre-check's guidance points here. It does **not** offer
    whole-account `replace`, which clears the entire account ledger —
    dividends, interest, cash, manual corrections, and other tickers included —
    and would silently destroy that non-tax-lot history.
  - **A rebuild inside an already tax-lot-dedicated account** (an evolved or
    overlapping export) → the existing whole-account `replace` mode (FIX-876,
    `replaceLedgerFromFile`, which already carries orphan-holdings reconciliation)
    is safe *here only*, because such an account holds nothing but tax-lot share
    events — there is no cash/income to lose. Rebuild is `replace` with the
    unrealized file, then `append` **every** realized file the account was built
    from (each disjoint tax-year slice), since `replace` wipes the account ledger
    — appending only one realized file would silently drop the other years'
    realized gains. All appends are keyed, same-kind, no conflict.
- **Refusals are rendered, not just returned.** The conflict is DB-dependent, so
  the client-side preview can't show it. Today `portfolio-pane.tsx`'s
  `handleImportTransactions` discards the returned `FileImportReport` and the
  dialogs close before the request settles — a 200 with 0 inserts + a warning
  would be invisible. The import dialog stays open (or reopens) to render the
  report (the refusal + dedicated-account guidance); the manual add-transaction
  path surfaces its seam rejection as a visible error instead of a console log.

The check ignores same-kind history (keyed onto keyed), so re-importing the same
tax-lot CSV never self-conflicts.

### API / UI

No new REST route. Existing `POST /api/portfolio/transactions/import` re-parses
server-side. Dialog preview already surfaces format + counts. A one-source
conflict is a normal `FileImportReport` (0 inserts + the conflicting-ticker
warning + dedicated-account guidance) — but it must be **rendered**: the pane
currently discards the report and the dialogs close before the request settles,
so the import dialog gains post-submit report display and the manual path a
visible rejection (see the invariant section).

## 5. Implementation Sequence

0. **Fresh-start wipe (rollout gate, runs BEFORE the new fingerprint recipe is
   enabled).** The unconditional `lk`/`ck` fingerprint change and the no-backfill
   migration are only safe on a cleared ledger — old unkeyed rows carry
   pre-`lk|ck` fingerprints, so a re-submit of the same unkeyed event would hash
   differently and bypass the unique index (duplicate), and retained unkeyed
   share rows would refuse tax-lot imports. So a one-time destructive wipe of the
   desk's ledger-derived tables (`ledger_events`, and the tables it
   materializes: `holdings`, `realized_gains`) runs as a deploy step (a guarded
   script, e.g. `pnpm --filter @flow-state-dev/trading-desk ledger-reset`,
   idempotent), and the new `computeFingerprint` recipe ships **gated on a
   marker proving the wipe ran** (a schema/migration sentinel row), so the recipe
   never activates against un-wiped data. Snapshot-only holdings (CSV/PDF, no
   ledger history) are re-imported by the user afterward; this is the accepted
   one-time cost of the fresh start (§3). Dev (PGlite) resets by deleting
   `.fsdev/pglite`; deploy runs the script under the migrator.
1. **Ledger lot-identity fields** — add `lotKey` / `closesLotKey` to
   `ledger-schema.ts` (+ refine), `db/schema.ts` (+ migration), the repository
   mapping, the lot-aware fingerprint marker, AND the shared
   `assertShareEventInvariant` (the file path bypasses zod). Omit both fields
   from `recordEventSchema`; `recordManualEvent` forces them null (the
   `proceedsUnknown` idiom). Unit-test the boundary rules at both layers.
2. **`deriveLots` specific-lot consumption** — keyed consumption (splice by key);
   unmatched key → unmatched disposal (`lot-not-found`), never FIFO; split branch
   skips keyed lots. Regression-test that every existing FIFO test is unchanged,
   then add specific-lot tests (multi-lot ticker, non-oldest lot closed; keyed
   pair spanning a split; missing referenced lot).
3. **Parser + unit tests** — `portfolio-tax-lot-csv.ts` with synthetic fixtures
   matching Schwab-style headers. Canonicalize ticker to upper-case before the
   event ticker + `lotKey` (cover mixed-case input). Assign `seq` by canonical
   content sort `(quantity, costBasis, proceeds)`, NOT file order (cover a
   reordered re-export → identical keys). Verify signs, amounts, `unitPrice` from
   `costBasis/qty`, lot keys + `seq` (incl. same-symbol-same-date rows with
   different qty/basis getting distinct keys), buy/sell pairing, skips, wash-sale
   warning, `-BOND` strip.
4. **Dispatcher** — `transaction-file.ts` routes CSV; vitest for OFX unchanged +
   CSV branch.
5. **One-source invariant + dedicated-account enforcement** — the ingest-seam
   check (in-batch + vs `voided_at IS NULL` history, keyedness = `lotKey ??
   closesLotKey`, reject-and-rollback on conflict) + the `importTransactionFile`
   **whole-account dedication pre-check** (refuse a tax-lot file unless the target
   account holds nothing but tax-lot keyed share events) returning a clean refusal
   report with fresh-account guidance; `backfillSplits` skips `(account, ticker)`
   pairs whose non-voided history is entirely keyed. Test: a tax-lot file into an
   account holding an unrelated MSFT position OR any dividend/cash row → refused,
   0 events; conflict in BOTH directions (tax-lot onto OFX history, OFX/manual
   onto keyed history) → refused; realized-after-unrealized into a dedicated
   account → NOT a conflict (both keyed); an in-batch mixed-linkage group rejected
   on an empty ticker; a voided-then-reimport of the opposite source allowed
   (voided rows excluded); idempotent re-import; the `replace`+`append`-**all**-
   realized rebuild in a dedicated account restores every tax-year slice.
6. **Dialog + refusal surfacing** — accept `.csv`, copy update (incl. the
   dedicated-account guidance for tax-lot imports); render the post-submit
   `FileImportReport` in the import dialog (today the pane discards it) and
   surface manual-write seam rejections visibly.
7. **Holdings soft gate** — warning when tax-lot headers detected on holdings
   parse / dialog.
8. **Docs** — `transaction-import-formats.md` + `CLAUDE.md`.
9. **Goal check (manual / non-CI)** — import both sample CSVs into a throwaway
   account; confirm open holdings match the unrealized file, the Realized Gains tab
   matches the realized file's per-lot basis/term (not a FIFO re-derivation), and a
   second identical import dedups.

## 6. Edge Cases & Error Handling

| Case | Behavior |
| --- | --- |
| Empty / header-only | warning; 0 events |
| Negative unrealized qty | skip + row error |
| OCC option symbol | skip + row error — options are a Non-Goal (unmodeled multipliers/semantics), never fed to the lot engine |
| Foreign-currency lot | `currency` read from file/account, never USD default — foreign gains aren't mislabeled as taxable USD |
| CUSIP fallback + possibly-aliased existing history | inherits the pre-existing cross-feed CUSIP↔ticker limitation; the dedicated-account rule keeps it from double-counting |
| Missing openDate / symbol / qty | skip + row error (unrepresentable) |
| Blank `costBasis` on a valid lot | buy lands with `amount=0` + `basisUnknown` — position kept, basis honestly unknown (never dropped) |
| Realized row: missing `closeDate` | skip + row error (no disposal date) |
| Realized row: blank `proceeds` | sell recorded with `proceedsUnknown` marker — disposal + basis + term kept, gain nulled |
| Realized row: `closeDate < openDate` | reject + row error (would sort the sell ahead of its buy); same-day allowed |
| `closeDate` header without `proceeds` header (or vice versa) | **file rejected** — an intended realized export with an unrecognized column, never parsed as unrealized (phantom open buys) |
| Holdings snapshot fed to the transactions dialog | **file refused** — per-share vs lot-total cross-check (`costBasis ≈ unitCost` on multi-share rows) detects it; message points to Holdings CSV import |
| Partial close across the paired files (same symbol + openDate in both) | `kind` (`u`/`r`) namespaces the keys — no cross-file collision |
| Two same-date sells of different lots, equal qty/proceeds | distinct `closesLotKey` → distinct fingerprint fields → both land |
| Batch itself mixes keyed + unkeyed rows for one ticker (empty ticker) | rejected — the in-batch group check catches it even with no existing history |
| Concurrent keyed + unkeyed imports of an empty ticker | per-account advisory lock precedes the history check — one wins, the other refuses |
| Tax-lot CSV into an account that already holds ANY non-tax-lot history (unrelated ticker, dividend, cash, manual row) | **whole file refused** (0 events) → use a fresh account; the whole-account dedication check, not just per-covered-ticker isolation |
| Tax-lot CSV covers a ticker that already has OFX/Plaid/manual share history | refused by both the dedication check and the per-ticker seam check |
| Mixed-case broker symbol (`aapl`) | canonicalized to `AAPL` before the event ticker AND the `lotKey`, so it shares the canonical holdings/source group |
| Reordered re-export (same rows, different file order) | identical `seq`/`lotKey`/fingerprint (content-sorted `seq`), so re-import dedups — no double-count |
| Voided-then-reimport of the opposite source | allowed — the history check requires `voided_at IS NULL`, so a tombstone doesn't permanently block the switch |
| Evolved / overlapping export rebuild (account built from 2024 + 2025 realized slices) | whole-account `replace` (safe — the account is tax-lot-only) with the unrealized file, then `append` **every** realized slice — appending only one would drop the other years' gains |
| Two genuinely-identical lots (same symbol/open/qty/basis) | distinct `seq` → distinct `lotKey` → distinct lot-aware fingerprint → both land; re-import dedups |
| Same symbol + openDate, different qty/basis | distinct `seq` by construction (scope is `(symbol, openDate)`) — e.g. a purchase split into realized + open portions |
| Realized sell references a lot not open (evolved/partial file) | unmatched disposal (`lot-not-found`: real proceeds, null basis/term) — **never** FIFO fallback onto an unrelated lot |
| Keyed lot spans a split date | split branch skips keyed lots (file already split-adjusted); post-export real split → re-export + `replace` rebuild |
| Partial close of a lot across tax years | closed portion (realized file) + open remainder (unrealized file) are separate rows, each self-contained; Σ = original purchase |
| Same acquisition-date lot partially disposed in TWO realized files (different years) | `closeDate` in the realized key keeps both disposals (+ their acquisition legs) distinct — the later file isn't dropped on the external-id index |
| Wash sale true | ingest + warning (no basis adjustment) |
| Bond `CUSIP-BOND` | strip suffix; classify as bond when applicable |
| Duplicate re-import | `(source, externalId)` dedup on the lot key; fingerprint keeps it consistent |
| Tax-lot on Holdings CSV | top-level warning → use Import transactions |
| Realized file imported first, then its paired unrealized file (clean account) | NOT a conflict — the disposal counts as keyed (`closesLotKey`), so the unrealized buys are same-kind |
| OFX/manual share event onto a keyed ticker (reverse order) | whole batch refused at the shared seam — the invariant is symmetric |
| Overlapping realized exports (same `(symbol, openDate, closeDate)` across two files) | rebuild via `replace`, not append — `seq` is per-file so an identical tuple would collide |
| Manual API supplies `lotKey`/`closesLotKey` | fields absent from `recordEventSchema`; forced null at the service boundary |

## 7. Testing Strategy

**Goal:** A user imports paired unrealized + realized tax-lot CSVs into an account
and sees derived open positions plus realized disposals **whose basis, term, and
gain match the broker's specific-lot file**, without hand-entering trades.

**Goal check (manual / non-CI):** Using the sample files
(`*_tax_lot_unrealized.csv`, `*_tax_lot_realized.csv`) against a fresh account via
Import transactions (append): open holdings reflect the unrealized lots; the
Realized Gains tab shows each closed lot with the file's own basis/term/gain (not
FIFO's); a second identical import reports deduplicated counts. Pass/fail is visual
+ import report — no LLM required.

**Discipline:** `tdd` (Feature label).

**Behaviours to test (vitest):**

- Unrealized row → one buy with `−costBasis` amount, `+qty`, `unitPrice =
  costBasis/qty`, and a `lotKey`.
- Realized row → buy then sell with correct dates/signs/proceeds; sell's
  `closesLotKey` equals the buy's `lotKey`.
- Paired-file partial close: same `(symbol, openDate)` in both files → distinct
  keys via `kind`; both buys land; the realized sell closes ITS lot.
- Two realized files (different tax years), same symbol + openDate, different
  closeDates → distinct realized keys via `closeDate`; both disposals + both
  acquisition legs persist (neither dropped on the external-id index).
- Two same-date sells of different lots (equal qty/proceeds) → distinct
  fingerprints (`lk`/`ck` fields); both persist.
- Detection: `closeDate` header without `proceeds` → file rejected; a
  per-share-basis holdings snapshot → file refused with the Holdings-CSV
  pointer; a genuine lot-total file passes the cross-check.
- **Specific-lot matching (the crux):** a ticker with two open lots where the
  realized row closes the *newer* lot → the older lot stays open, and the disposal
  reports the newer lot's basis/term. FIFO would fail this.
- Existing FIFO derivation tests unchanged (no `closesLotKey` → oldest-first).
- Two identical lots → both land (distinct `seq` → distinct key → distinct
  lot-aware fingerprint, verified against the real unique indexes).
- Same symbol + openDate, different qty/basis → distinct keys (no collapse).
- Keyed disposal whose referenced lot is missing → unmatched `lot-not-found`
  disposal; no other lot consumed.
- A split between a keyed lot's open and close dates → lot NOT rebased; derived
  disposal matches the file. `backfillSplits` skips a fully-keyed
  `(account, ticker)` pair but still backfills another account's unkeyed history
  in the same ticker.
- Negative qty skipped; wash-sale warning emitted; `-BOND` symbol stripped;
  **OCC option symbol skipped** (Non-Goal); **foreign-currency lot keeps its
  currency** (file/account, not USD).
- Dispatcher: content with tax-lot headers → format `tax-lot-*`; OFX still works.
- Blank `costBasis` → buy lands with `basisUnknown` (position kept, gain
  excluded); blank `proceeds` → sell recorded with `proceedsUnknown`; only a
  missing symbol/qty/openDate (buy) or closeDate (sell) skips the row.
- `closeDate < openDate` → row rejected; same-day acquire+sell allowed.
- Ticker canonicalization: a mixed-case `aapl` row persists as `AAPL` on both the
  event ticker and the `lotKey`.
- Content-sorted `seq`: a reordered re-export of the same rows yields identical
  `seq`/`lotKey`/fingerprint → re-import dedups (no double-count).
- Whole-account dedication: a tax-lot file into an account holding an unrelated
  MSFT position OR a dividend/cash row → **refused, 0 events** (fresh-account
  guidance), even though MSFT isn't in the file.
- One-source invariant, both directions: OFX/transfer-in history for a ticker
  then a tax-lot CSV covering it → refused; tax-lot history then an OFX/manual
  share event for that ticker → refused; realized-first-then-unrealized pair into
  a dedicated account → NOT a conflict (both keyed); an in-batch group mixing
  keyed+unkeyed for an empty ticker → rejected; a voided-then-reimport of the
  opposite source → allowed (voided rows excluded); re-importing the same tax-lot
  CSV → no conflict, deduped.
- Rebuild: `replace` (unrealized) then `append` **every** realized slice into a
  dedicated account restores all tax-year gains (appending only one slice drops
  the others); manual `lotKey` injection is stripped/rejected at the manual
  boundary.
- Fresh-start gate: the new `lk`/`ck` fingerprint recipe activates only behind the
  wipe sentinel; an un-wiped ledger does not enable it (rollout safety).
- The import dialog renders the refusal report (0 inserts + dedicated-account
  guidance, not silently closed); a manual seam rejection surfaces as a visible
  error.
- Holdings parser: tax-lot headers produce a warning mentioning transaction import.

## 8. Non-Goals

- Wash-sale basis adjustment (recorded + warned, not computed).
- Average-cost / LIFO *method reconstruction* beyond what the file's per-lot rows
  state (we honor the file's lot pairing; we do not re-derive an alternate method).
- Generic column-mapping UI for arbitrary broker CSVs.
- Dividends, interest, deposits, transfers (absent from these files).
- Options tax-lot CSVs.
- Changing Holdings CSV into a ledger writer.
- Storing the broker `gainLoss` / `term` columns as authority — derivation stays
  the authority; lot identity only makes it consume the right lot.
- Cross-source reconciliation (OFX ⇄ tax-lot CSV for the same ticker) — refused,
  not merged; tax-lot imports use a dedicated account.

## 11. Open Questions

None blocking. Defaults locked in this spec:

- Neg qty / shorts → skip.
- Wash sale → warn only.
- Realized accuracy → specific-lot via carried lot identity (not FIFO, not stored
  broker gain).
- Tax-lot imports require a **tax-lot-dedicated account** (enforced whole-account,
  not just per-ticker); a conflict → use a fresh account. Whole-account `replace`
  is a rebuild path *within* a dedicated account only (never to convert a mixed
  account).
- Identical distinct lots → content-sorted `seq` discriminator on the lot key
  (order-independent, so a reordered re-export still dedups).
- Fresh start: a one-time ledger wipe precedes the unconditional-fingerprint
  rollout (gated on a sentinel).
