# FIX-897: Knowledge Hub caller-supplied context (session) for the sessionless MCP capture surface — Implementation Spec

## 1. TLDR

**Plain-language summary.** Today every MCP capture into the Knowledge Hub lands in its own throwaway runtime session, so related notes from one conversation do not group together and the sweeper cannot see which captures belonged to the same topic. This change adds a `create_context` tool the client calls once per conversation (with a short topic description), returns a reusable context id, and requires that id on every `log_activity` call. Captures under the same id are grouped in storage and share one framework session across MCP calls. If the model logs activity with an id that was never opened, the capture still succeeds and a minimal context record is created on the fly — nothing is rejected for missing setup. The framework also gains a small, optional hook so an MCP `tools/call` can map tool input to a stable session id (the enabler for this lab, shaped so it can graduate later).

**Technical statement.** Add `McpConfig.resolveSessionId` in `@flow-state-dev/mcp`, a user-scoped `contexts` collection plus `createContext` / `logActivity.contextId` in `labs/knowledge-hub`, and wire the hub flow so MCP `log_activity` runs with `sessionId = contextId`.

**Deliverables.**

- **Framework:** Add `resolveSessionId` to `McpConfig` in `packages/core/src/types/flow.ts` and invoke it from `handleToolsCall` in `packages/mcp/src/createMcpTransportAdapter.ts` before `host.dispatch`, passing the resolved value as `sessionId` (unchanged when the hook returns `undefined`).
- **Framework:** Export the hook context type from `packages/mcp` (and re-export from `packages/core` if needed for flow authors typing the callback).
- **Framework:** Unit + end-to-end tests in `packages/mcp/test/` proving a flow-configured hook groups consecutive `tools/call` invocations under one `RequestRecord.sessionId`.
- **Lab:** Add `contexts` user-scoped collection (`labs/knowledge-hub/src/contexts.ts`) and `createContext` handler (`labs/knowledge-hub/src/flow.ts`).
- **Lab:** Extend `logActivity` with required `contextId`, persist `contextId` on inbox records, lazy-open missing contexts, include `contextId` in the mailroom fingerprint tuple.
- **Lab:** Configure `knowledgeHubFlow` `mcp.resolveSessionId` to map `logActivity` input `contextId` → session id; update MCP tool descriptions and `labs/knowledge-hub/README.md`.
- **Docs:** Extend `apps/docs/docs/server/mcp.md` (stateless v1 + caller-derived session POC); update `packages/mcp/README.md` v1 limitations blurb.

**Size estimate.** **Medium** — multi-package (core types, mcp adapter, knowledge-hub lab, docs), one PR, ~250–400 LOC including tests.

## 2. Overview

- **Linear:** [FIX-897](https://linear.app/fixpoint-labs/issue/FIX-897/knowledge-hub-caller-supplied-context-session-for-the-sessionless-mcp)
- **Depends on:** FIX-882 (capture inbox + `logActivity` MCP surface) — shipped.
- **Problem:** MCP is sessionless at the transport layer; each `tools/call` currently passes `sessionId: undefined`, so the runtime mints a fresh ephemeral session per capture. The Knowledge Hub inbox is user-scoped and durable, but request/session grouping (DevTool, session request lists, future session-scoped features) and explicit conversational metadata for FIX-883 are missing.
- **Solution:** Introduce an application-level **context** (topic + id) stored in user-scoped resources, require `contextId` on capture, and use the new MCP hook to align framework `sessionId` with `contextId` for `log_activity` calls.

## 3. Background & Research

### Industry / MCP

- [Sessionless MCP SEP](https://modelcontextprotocol.io/seps/2567-sessionless-mcp) treats each `tools/call` as stateless and recommends that servers which need continuity expose **session (or context) creation as its own tool** rather than relying on transport session headers.
- This spec follows that pattern: `create_context` is the explicit open; `log_activity` carries the returned id.

### In-repo patterns

| Area | Pattern to follow |
|------|-------------------|
| User-scoped durable staging | `inboxCollection` in `labs/knowledge-hub/src/inbox.ts` (`scope: "user"`, `flowIsolation: false`, lazy prefetch) |
| Installation-level MCP input | `forwardQueryParams: ["source"]` in `labs/knowledge-hub/fsdev.config.ts` — authoritative merge in adapter (BP-031: provenance from URL, not model) |
| HTTP session continuity | `POST /:flowKind/:sessionId/actions/:actionName` passes `sessionId` on the envelope (`packages/engine/src/routes/action-routes.ts`) |
| MCP dispatch today | `handleToolsCall` hard-codes `sessionId: undefined` (`packages/mcp/src/createMcpTransportAdapter.ts` ~414–415) |
| Session auto-create | `createExecutionContext` creates a session record when `sessionId` is provided but missing (`packages/engine/src/context/createExecutionContext.ts` ~581–596), binding `userId` from the authenticated principal |
| Mailroom fingerprint | Fixed field order in `computeFingerprint` (`labs/knowledge-hub/src/mailroom.ts`) — extend with `contextId` so the same verbatim capture in two contexts stays two records |

### Why this approach

| Alternative | Rejected because |
|-------------|------------------|
| Only store `contextId` on inbox rows (no framework session hook) | Satisfies sweeper grouping but leaves MCP/DevTool request history fragmented; issue explicitly asks for minimal framework enabler |
| Full MCP `Mcp-Session-Id` transport statefulness | Out of scope; serverless/host complexity; SEP points to app-level tools instead |
| Enforce `create_context` before capture (hard gate) | Violates desired outcome #4 — captures must never be lost to ordering mistakes |
| Promote hook to first-class `capability` now | Issue scope: POC in lab; keep surface on `McpConfig` until a second consumer exists (BP-038) |

### Key Decisions & Ramifications (top 5)

1. **Decision:** Add `mcp.resolveSessionId` on the flow's `McpConfig`, called from the MCP adapter after input merge (including `forwardQueryParams`) and before `host.dispatch`.  
   **Alternative rejected:** Per-action hook on `ActionMcpConfig` — more granular but redundant until a second action needs a different mapping.  
   **Ramification:** Flow authors own session derivation in one function; action key is available in the callback for branching. Future transport statefulness remains separate.

2. **Decision:** Use **`contextId` as the framework `sessionId`** for MCP `log_activity` only (via the hook).  
   **Alternative rejected:** Separate internal session id + `contextId` on records only — duplicates identifiers and confuses DevTool.  
   **Ramification:** Session request lists and DevTool group captures per context; session ids are caller/model-supplied strings (hardening deferred per issue). `UserBindingMismatchError` still prevents cross-user reuse of the same id.

3. **Decision:** Persist contexts in a **user-scoped resource collection** `contexts/{id}` with `description` + `openedAt`.  
   **Alternative rejected:** Session `metadata` only — harder for sweeper/cron to query without session API; inbox pattern already established.  
   **Ramification:** FIX-883 can list contexts and join inbox rows on `contextId` without loading framework session state.

4. **Decision:** **Lazy-open** on `logActivity` when `contextId` is unknown: upsert `{ description: null, openedAt: capturedAt, lazyOpened: true }` (exact field names in schema below).  
   **Alternative rejected:** Reject or no-op — violates outcome #4.  
   **Ramification:** Sweeper must treat `lazyOpened` / null description as "topic unknown"; optional later `create_context` can enrich the same id.

5. **Decision:** Include **`contextId` in the mailroom fingerprint** tuple (after normalization).  
   **Alternative rejected:** Fingerprint without `contextId` — would dedupe the same content across two conversations sharing no other discriminator.  
   **Ramification:** Intentional re-capture of identical text in another context creates a second inbox row (desired).

## 4. Technical Design

### Architecture

```
MCP client
  tools/call create_context ──► MCP adapter ──► dispatch(sessionId: undefined)
                                      │
                                      ▼
                              createContext handler
                                      │
                                      ▼
                         contexts/{id} user resource

MCP client
  tools/call log_activity { contextId, ... } ──► MCP adapter
                                      │
                         mcp.resolveSessionId → contextId
                                      │
                                      ▼
                         dispatch(sessionId: contextId)
                                      │
                                      ▼
                              logActivity handler
                                      │
                         lazy-open context if missing
                                      │
                                      ▼
                         inbox/{kind}/{fingerprint} user resource
```

**Packages:** `@flow-state-dev/core` (types), `@flow-state-dev/mcp` (adapter), `@flow-state-dev/knowledge-hub` (lab).

### Framework API

**`McpConfig`** (`packages/core/src/types/flow.ts`):

```ts
/** Context passed to {@link McpConfig.resolveSessionId} after tools/call input is merged. */
export interface McpResolveSessionIdContext {
  readonly flowKind: string;
  /** Internal action key (camelCase), not the MCP tool name. */
  readonly actionKey: string;
  readonly toolName: string;
  /** Parsed + merged tool arguments (plain object). */
  readonly input: Record<string, unknown>;
  readonly principal: ResolvedPrincipal;
  readonly tenantId?: string;
}

export interface McpConfig {
  enabled?: boolean;
  exposeResources?: boolean;
  /**
   * Optional MCP-only hook: derive the framework session id for this tools/call.
   * Return `undefined` to keep today's stateless behavior (fresh ephemeral session).
   * The returned id is passed to `host.dispatch` as `sessionId` — not read from the
   * request body on the HTTP action path (BP-031).
   */
  resolveSessionId?: (ctx: McpResolveSessionIdContext) => string | undefined;
}
```

**Adapter behavior** (`createMcpTransportAdapter.ts`):

1. After building `input` (model args + forwarded query params), if `flow.mcp?.resolveSessionId` is defined, call it with `{ flowKind, actionKey: target.actionKey, toolName: name, input: input as Record<string, unknown>, principal, tenantId }` (tenant from host if available on the call path; if not threaded today, omit until host exposes it — hook still works for single-tenant hub).
2. Pass `sessionId: resolved ?? undefined` to `host.dispatch`.
3. Do **not** invoke the hook for `tools/list`, `initialize`, or `resources/*`.

**Validation:** No define-time validation of the hook body. Runtime: if the hook throws, map to JSON-RPC `-32603` or `-32000` with a clear message (same family as other adapter failures).

### Knowledge Hub — context collection

**File:** `labs/knowledge-hub/src/contexts.ts`

```ts
export const contextRecordSchema = z.object({
  /** Short topic label from create_context; null when lazy-opened at capture time. */
  description: z.string().nullable().default(null),
  openedAt: z.string(), // ISO-8601
  lazyOpened: z.boolean().default(false),
});

export const contextsCollection = defineResourceCollection({
  pattern: "contexts/**",
  scope: "user",
  flowIsolation: false,
  stateSchema: contextRecordSchema,
  prefetchMode: "lazy",
  llmReadable: true,
  llmWritable: false,
});
```

**Id format:** `generateId("kctx")` from engine/core id helper (or `kctx_` + uuid — match existing `generateId` usage in session routes). Returned bare id; storage key `contexts/{id}`.

### `createContext` action

- **MCP tool name:** `create_context`
- **Input:** `{ description: string }` — min 1, max 500, non-blank (same `nonBlank` refine as inbox).
- **Output:** `{ contextId: string, openedAt: string }`
- **Behavior:** Generate id, `contexts.create(id, { description, openedAt: now, lazyOpened: false })`, return ids. Idempotent re-call with same description is **not** required to dedupe (each call opens a new context) — clients should call once per conversation.

### `logActivity` changes

- **New required field:** `contextId` — string, min 1, max 128, describe as "Context id from `create_context` for this conversation."
- **Keep** existing `context` string field (situational snippet) unchanged in meaning.
- **On execute:**
  1. `const ctxRecord = await ctx.resources.contexts.getOptional(contextKey(contextId))`
  2. If missing: `contexts.create(contextId, { description: null, openedAt: capturedAt, lazyOpened: true }, { replace: true })` — use caller-supplied id as key (lazy open).
  3. If present and `lazyOpened` and later `create_context` runs with same id — **out of scope** for v1 (create always mints new ids). Optional follow-up: `create_context` could accept optional id — **not in this spec**.
  4. Write inbox record including `contextId` field on `InboxRecord`.
- **Fingerprint:** extend `computeFingerprint` input with `contextId: string` as first line of tuple (before `kind`) so grouping and dedup semantics stay coherent.

### `listInbox` summary

Add `contextId: z.string()` to `inboxItemSummarySchema` and map from record state.

### Flow MCP wiring

```ts
mcp: {
  enabled: true,
  resolveSessionId({ actionKey, input }) {
    if (actionKey !== "logActivity") return undefined;
    const contextId = input.contextId;
    return typeof contextId === "string" && contextId.length > 0 ? contextId : undefined;
  },
},
```

When `contextId` is missing/invalid, zod fails before dispatch — hook not reached. CLI `fsdev run` callers pass `--session <contextId>` manually for grouped testing (document in README).

### Error handling

| Case | Behavior |
|------|----------|
| Missing `contextId` on `logActivity` | Zod validation error; no inbox write |
| Unknown `contextId` | Lazy-open context + capture succeeds |
| `resolveSessionId` throws | MCP JSON-RPC error; no dispatch |
| Session exists for different `userId` | `UserBindingMismatchError` at runtime (existing engine guard) |
| Duplicate fingerprint same context | Existing pending dedup behavior unchanged |

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|-----------|-------------------|
| Two captures, same context, identical tuple | Second returns `deduplicated: true` (pending window) |
| Same tuple, different `contextId` | Two records (fingerprint differs) |
| `log_activity` without prior `create_context` | Lazy context + success |
| `create_context` then many captures | Same `sessionId` on MCP requests when hook wired |
| Concurrent lazy-open + create same id | `replace: true` on context write; last write wins (acceptable POC) |
| Model supplies another user's `contextId` | Fails `UserBindingMismatchError` when session exists under owner |
| Empty `contextId` after trim | Zod reject |

**Retryable:** Concurrency / server-busy unchanged. **Fatal:** Auth, validation, user binding mismatch.

## 8. Non-Goals

- Promoting `resolveSessionId` to a built-in "MCP sessions" capability package.
- Hard requirement that `create_context` run before capture.
- Per-tenant namespacing / cryptographic context id binding (issue follow-up).
- FIX-883 sweeper batching logic (consumer only).
- `list_contexts` MCP tool (add when sweeper/UI needs it).
- Enriching lazy-opened context when `create_context` is called later with matching id.
- **Deepening note:** MCP README still defers "stateful mode" globally; this hook is intentionally narrow (caller-derived id per call, not transport `Mcp-Session-Id`).

## Necessity verdict (Step 3.5)

**Build as scoped.** The inbox alone cannot group MCP request history or align with framework session primitives; the hook adds composition with `runAction` / `RequestRecord` that user-space inbox fields alone do not provide, and FIX-897 is the explicit consumer called out in `@flow-state-dev/mcp` README ("deferred until a real consumer asks").
