# FIX-897: Knowledge Hub — caller-supplied context (session) for the sessionless MCP capture surface — Implementation Spec

## 1. TLDR

**Plain-language summary.** MCP (the protocol Claude and other clients use to call our tools) has no built-in idea of a "session" — every tool call is a blank slate. That means every Knowledge Hub capture today lands in its own throwaway session, with no way to say "these five things I just logged are all from the same conversation about X." This spec adds a small tool, `createContext`, that a client calls once to open a context (handing us a short description of the topic) and gets back a context id. Every later `logActivity` call passes that id, and under the hood the framework routes all of them into the same session. The only framework-level addition is a tiny hook that lets an MCP tool call decide its own session id instead of always getting a fresh one.

**Technical statement.** Add an optional `session` directive to `ActionMcpConfig` that lets the MCP transport adapter derive a request's `sessionId` from a tool call (either mint a fresh id from a template, or read it from a named input field), and use it in the Knowledge Hub lab to add a `createContext` tool plus a required `contextId` on `logActivity`.

**Deliverables.**

- **Framework (core):** Add `session?: string | { fromInput: string }` to `ActionMcpConfig` in `packages/core/src/types/flow.ts`.
- **Framework (mcp):** Derive `sessionId` from `target.action.mcp?.session` at the `tools/call` dispatch site in `packages/mcp/src/createMcpTransportAdapter.ts` (replacing the hardcoded `sessionId: undefined`); add a `deriveSessionId` helper + unit tests.
- **Lab (knowledge-hub):** Add a `createContext` handler + session `stateSchema` (holds `description`) and register it as an MCP action with `mcp: { session: "ctx_*" }` in `labs/knowledge-hub/src/flow.ts`.
- **Lab (knowledge-hub):** Add a required `contextId` to `logActivity`'s input schema; set `mcp: { session: { fromInput: "contextId" } }` on its action config; store `contextId` on the `InboxRecord` and include it in the mailroom fingerprint and the `listInbox` summary.
- **Tests:** mcp adapter unit tests (directive → sessionId); knowledge-hub tests (createContext returns/stores; shared contextId groups captures; auto-vivify).
- **Docs:** see section 9 (mcp docs page + `packages/mcp/README.md` + `labs/knowledge-hub/README.md`; changeset).

**Size.** Medium (multi-file, single PR, ~150–250 LOC incl. tests). Two packages + one lab, but each change is small and the framework surface is one field.

## 2. Overview

Linear issue: [FIX-897](https://linear.app/fixpoint-labs/issue/FIX-897/knowledge-hub-caller-supplied-context-session-for-the-sessionless-mcp)

MCP is sessionless — the [sessionless-MCP SEP](https://modelcontextprotocol.io/seps/2567-sessionless-mcp) makes this explicit and recommends that a server wanting session semantics expose session creation as its own tool. Our MCP adapter honors that today by hardcoding `sessionId: undefined` on every `tools/call`, so every call gets a fresh ephemeral session. This spec gives an MCP tool call the ability to determine its own session, and uses it to let a Knowledge Hub client open a named **context** and group multiple captures under it. "Context" here is exactly a session: the context id *is* the session id.

## 3. Background & Research

### The mechanism gap

A request's `sessionId` is fixed at dispatch time and drives which session record and session-scoped state get loaded ([`createExecutionContext.ts:485`](../../packages/engine/src/context/createExecutionContext.ts#L485): `options.sessionId ?? ephemeral_…`). A handler therefore cannot choose its own session — the id must be supplied to `host.dispatch(...)`, which happens inside each transport adapter. The MCP adapter currently always passes `sessionId: undefined` ([`createMcpTransportAdapter.ts:415`](../../packages/mcp/src/createMcpTransportAdapter.ts#L415)). So "derive a sessionId from the tool call" is only expressible at the adapter layer — this is the single real capability gap.

### "Ephemeral" is cosmetic

The `ephemeral_` prefix is just the naming for an auto-generated id (`ephemeral_${Date.now()}_${Math.random()…}`). Those sessions persist to the store identically to any other — there is no GC, no special-casing anywhere in the engine (a repo-wide grep for `ephemeral` finds only the one generation site plus unrelated item-content usage). So the real distinction the feature needs is not "a different kind of session" but "an id the caller learns and can reuse." Reusing the ephemeral scheme is functionally sufficient; the only reason to mint a purpose-prefixed id (`ctx_…`) is so the value we hand an external MCP client as a "contextId" doesn't read as `ephemeral_…`.

### Existing precedents this mirrors

- **`forwardQueryParams`** (already used by knowledge-hub) merges an installation-set value into a tool call's input before dispatch — the same "adapter shapes the dispatch envelope from request context" shape this extends, one field over (`sessionId` instead of `input`).
- **Per-action `ActionMcpConfig`** already carries `enabled` and `name`; `session` is a natural third member. `enabled`/`name` are read inside `resolveExposedActions`; `session` is read one step later at the `handleToolsCall` dispatch site, off the `target.action.mcp` object that function already returns — same data, adjacent site.
- **`computeFingerprint`** reads *named* fields and `InboxRecord` is built field-by-field, so extending both with `contextId` is a localized, explicit change — the mailroom's existing "same content captured in a different context is a different event" philosophy extends cleanly to the conversation `contextId`.

### Why this approach over alternatives

The chosen mechanism is a **declarative per-action directive** interpreted by the adapter. A flow-level *function hook* (`mcp.resolveSessionId(tool, input)`) was considered and rejected for the POC: it is logic-in-config (it has to branch on `actionKey`), a larger public surface, and harder to lift into a reusable capability. The declarative union keeps the surface minimal and leaves an obvious door for a future `{ resolve: fn }` arm without reworking the two existing arms. A *reserved-arg convention* (auto-map a magic `contextId` field) was rejected as implicit and unable to express "mint a fresh id."

**A separate `contexts` resource collection was also considered and rejected.** Because the context id *is* the session id and sessions already persist state, the session record already **is** the context record — its state holds the description. A parallel user-scoped `contexts/{id}` collection would be a second source of truth for the same thing. Instead, `contextId` is stored on each inbox row: the downstream sweeper (FIX-883), which reads the user-scoped inbox, groups captures by that field directly, and can load the session's state by the same id when it wants the topic description. One identifier, two lookups, no duplication.

### Necessity verdict: **Build as scoped**

No existing primitive lets a user do this in their own code — the sessionId is set inside the adapter before dispatch and is unreachable from a handler. The addition composes with the framework's session-scope resolution path (a capability user space cannot replicate) and is provider-agnostic (aligned to the MCP SEP, not a single vendor). The precedent (`forwardQueryParams`, `ActionMcpConfig`) transfers with matching semantics. Scope was already trimmed during design: enforcement of "context must exist before capture" was dropped in favor of auto-vivify, and no `"open"`-vs-`"use"` mode split is needed because the string template covers minting.

### Key Decisions & Ramifications (top 5)

1. **Decision:** Session derivation lives as a declarative directive on `ActionMcpConfig` (`session?: string | { fromInput: string }`), interpreted by the MCP adapter.
   **Alternative rejected:** A flow-level `resolveSessionId` function hook.
   **Ramification:** Minimal, typed, self-documenting surface that reads cleanly as a future built-in. Locks the mechanism to MCP for now (other transports keep their own session handling). The union shape reserves room for a `{ resolve: fn }` arm later without breaking callers.

2. **Decision:** A `string` value is a **template** — `*` is replaced by a fresh random token (`"ctx_*"` → `ctx_1784…_a1b2`); a `{ fromInput }` object reads an existing id.
   **Alternative rejected:** A separate `"open"` enum mode, or reusing the `ephemeral_` id verbatim.
   **Ramification:** Clients receive a purpose-named context id, not an `ephemeral_…` string. Discriminating by `typeof` keeps the two arms unambiguous. If a template omits `*`, the token is appended (guards against a constant id that would collide every context).

3. **Decision:** `logActivity` auto-vivifies — an unknown `contextId` still succeeds (a fresh session with a null description). `contextId` is stored on the `InboxRecord` and included in `computeFingerprint`, but the adapter never inspects session state.
   **Alternative rejected:** Rejecting captures whose context was never opened; or keeping `contextId` off the record ("inert routing key").
   **Ramification:** No capture is lost to a missing precondition, and the sweeper can group inbox rows by `contextId` without loading session records. Because `contextId` is in the fingerprint, the same tuple captured under two contexts yields two rows (no cross-context dedup collision). "Call `createContext` first" is a documented convention, not an enforced gate.

4. **Decision:** The context description is the **session's state** (`stateSchema` `{ description }`), written by `createContext` with `ctx.session.setState`. No separate `contexts` collection — the session record *is* the context record.
   **Alternative rejected:** A dedicated user-scoped `contexts/{id}` collection (Cursor's approach); or `ctx.session.setMetadata({ description })`.
   **Ramification:** One source of truth for the topic. The sweeper reaches the description by loading session state for the `contextId`; grouping needs only the `contextId` field on the record, so the description read is optional. Typed and exposable later via `client.expose`. Trivial to switch to metadata if we ever prefer zero schema.

5. **Decision:** `fromInput` reads caller-controlled input as the session id, under a server-set `userId` (bearer principal `owner`).
   **Alternative rejected:** Requiring a server-minted id even for `logActivity`.
   **Ramification:** A caller can name any session id — safe here because everything runs under a single server-set `userId` and BP-031 is preserved (the id is used only as a session key, never for auth/routing). A general framework version must confirm per-user/tenant session-key namespacing before promoting this (flagged in Non-Goals).

## 4. Technical Design

### 4.1 Framework — `packages/core/src/types/flow.ts`

Extend `ActionMcpConfig` (currently `enabled?`, `name?`, around line 154):

```ts
export interface ActionMcpConfig {
  enabled?: boolean;
  name?: string;
  /**
   * How the MCP adapter derives the dispatch sessionId for this action.
   *
   * - Omitted (default): stateless — every tools/call mints a fresh
   *   ephemeral session (v1 behavior).
   * - `string`: a template for a freshly minted id. The first `*` is
   *   replaced by a random token (`"ctx_*"` → `"ctx_1784…_a1b2"`); with no
   *   `*` the token is appended. Use to hand the caller a reusable id whose
   *   prefix names the concept (e.g. a "context").
   * - `{ fromInput: <field> }`: use the string value at `input.<field>` as
   *   the sessionId, so a caller-supplied id groups calls into one session.
   *
   * (A future `{ resolve: (input) => string | undefined }` arm can add a
   * custom resolver without changing the two arms above.)
   */
  session?: string | { fromInput: string };
}
```

### 4.2 Framework — `packages/mcp/src/createMcpTransportAdapter.ts`

At the `handleToolsCall` dispatch site (`sessionId: undefined` is on line 415), replace it with a derived value. `target.action` (the full `ActionConfig`) is already in scope from `resolveExposedActions`, and `input` (merged args + `forwardedInput`) is already computed above (lines 399–404).

```ts
const sessionId = deriveSessionId(target.action.mcp?.session, input);
// ...
handle = host.dispatch({
  source: MCP_TRANSPORT_SOURCE,
  flowKind: flow.kind,
  action: target.actionKey,
  input,
  principal,
  sessionId,            // was: undefined
  responseEmitter: null,
  metadata: { mcpMethod: "tools/call", mcpToolName: name }
});
```

New module-local helper (co-located in the adapter file, near the other tools/call helpers):

```ts
/**
 * Derive the dispatch sessionId for a tools/call from the action's
 * `mcp.session` directive. Returns undefined (→ fresh ephemeral session, the
 * v1 default) when no directive is set or a `fromInput` field is
 * missing/blank. `input` is the pre-validation merged arguments; a
 * missing/malformed field falls through to undefined and the action's own
 * zod schema rejects the call downstream.
 */
function deriveSessionId(
  directive: ActionMcpConfig["session"],
  input: unknown
): string | undefined {
  if (directive === undefined) return undefined;
  if (typeof directive === "string") {
    const token = `${Date.now()}_${Math.random().toString(16).slice(2)}`;
    return directive.includes("*") ? directive.replace("*", token) : `${directive}${token}`;
  }
  if (input !== null && typeof input === "object" && !Array.isArray(input)) {
    const value = (input as Record<string, unknown>)[directive.fromInput];
    if (typeof value === "string" && value.length > 0) return value;
  }
  return undefined;
}
```

Import `ActionMcpConfig` as a type from the `@flow-state-dev/core/types` subpath — matching the adapter's existing sibling import (`import type { ActionConfig, McpConfig } from "@flow-state-dev/core/types";`), not the bare package root.

### 4.3 Lab — `labs/knowledge-hub/src/flow.ts`

**Session state schema** (BP-023 nullable + default) on the flow:

```ts
session: {
  stateSchema: z.object({
    description: z.string().nullable().default(null),
  }),
},
```

**`createContext` handler** (no resources; runs in a freshly-minted `ctx_…` session):

```ts
const createContext = handler({
  name: "createContext",
  inputSchema: z.object({
    description: z
      .string()
      .min(1)
      .max(2_000)
      .refine(nonBlank, "description must not be blank")
      .describe(
        "A short description or topic for this context — what this conversation is about. Stored on the context and reused by later review passes."
      ),
  }),
  outputSchema: z.object({ contextId: z.string() }),
  execute: async (input, ctx) => {
    await ctx.session.setState({ description: input.description });
    return { contextId: ctx.session.identity.id };
  },
});
```

**`logActivity` input** gains a required `contextId` (placed first for prominence):

```ts
contextId: z
  .string()
  .min(1)
  .max(200)  // a fromInput value becomes a literal session storage key — bound it (every sibling field is bounded)
  .describe(
    "The context id returned by createContext. Groups this capture into that conversation. Call createContext first to open a context."
  ),
```

The `.max(200)` is load-bearing, not cosmetic: a `fromInput` value becomes the literal `sessionId` and thus a storage key, and a session record is persisted even when the surrounding call later fails validation (see §4.6). An unbounded `contextId` would let a client write oversized session records, one per call. 200 comfortably fits a minted `ctx_…` id (~35 chars) with headroom.

**The `logActivity` handler stores `contextId` on the record and includes it in the fingerprint** (three small edits across the lab):

- `labs/knowledge-hub/src/inbox.ts` — add `contextId: z.string()` to `inboxRecordSchema` (and note it in the schema's field docs).
- `labs/knowledge-hub/src/mailroom.ts` — add `contextId` as the first field of the `computeFingerprint` tuple and its input type. This makes the same tuple under two contexts two distinct rows (no cross-context dedup collision), consistent with the mailroom's existing per-`context` philosophy.
- `labs/knowledge-hub/src/flow.ts` — set `contextId: input.contextId` when building the `InboxRecord`; add `contextId` to `inboxItemSummarySchema` and the `listInbox` mapping so inspectors (and the sweeper) see the grouping key.

`contextId` still doubles as the routing key the adapter consumes to pick the session, before the handler runs.

**Action registrations** on the flow:

```ts
createContext: {
  block: createContext,
  mcp: { session: "ctx_*" },
  description:
    "Open a context (a conversation/topic) for capturing activity. Supply a short description of what this conversation is about; returns a contextId to pass to every subsequent logActivity call. Call this once at the start of a session before logging activity.",
},
logActivity: {
  block: logActivity,
  mcp: { session: { fromInput: "contextId" } },
  description: /* existing description + note that contextId is required and comes from createContext */,
},
```

### 4.4 Data flow

1. Client → `tools/call createContext { description }`. Adapter reads `mcp.session = "ctx_*"`, mints `ctx_<token>`, dispatches with that `sessionId`. Handler writes `{ description }` to session state, returns `{ contextId: ctx.session.identity.id }` (= `ctx_<token>`).
2. Client → `tools/call logActivity { contextId: "ctx_<token>", kind, content, context, … }`. Adapter reads `mcp.session = { fromInput: "contextId" }`, dispatches with `sessionId = "ctx_<token>"`. The capture is written to the user-scoped inbox **with `contextId` on the row**; the *request* also runs inside session `ctx_<token>`. Grouping is therefore visible two ways: on the inbox rows (what the sweeper reads) and in the session's request history (DevTool).
3. A second `logActivity` with the same `contextId` lands in the same session → grouped.

### 4.5 State

- New session-scoped state field `description: string | null` on the knowledge-hub flow — the session record doubles as the context record. Written by `createContext`; defaulted to `null` for any session that was never opened via `createContext` (auto-vivify).
- `InboxRecord` gains a `contextId: string` field (the grouping key); `computeFingerprint` gains `contextId`. No new collection.

### 4.6 Error handling

- **No directive / blank `fromInput` value** → `deriveSessionId` returns `undefined` → fresh ephemeral session (unchanged v1 behavior).
- **`logActivity` with missing/blank `contextId`** → `deriveSessionId` returns `undefined`; a fresh ephemeral session is created and the action's zod schema then rejects the call for the missing required `contextId`. **Note:** the session record *is* persisted before the validation error throws — `runAction` defers the parse-error throw until after `createExecutionContext` (which persists a new session record) runs. This is not new behavior (every MCP call already writes a session record on a validation failure, since `sessionId: undefined` is minted into an id before dispatch validates), and it is why `contextId` must be bounded (`.max(200)` in §4.3) so a client can't write oversized records on the failure path.
- **Template with no `*`** → token appended, never a constant id.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| Action has no `mcp.session` | `sessionId: undefined` → fresh ephemeral session (v1 default, unchanged) |
| `session: "ctx_*"` | Mint `ctx_<Date.now()>_<rand>`; handler returns it as `contextId` |
| `session: "ctx"` (no `*`) | Token appended → `ctx<token>` (never a constant/colliding id) |
| `session: { fromInput: "contextId" }`, value present | `sessionId = input.contextId` |
| `fromInput` field missing / empty / non-string | `undefined` → ephemeral session (record persisted); required zod field then rejects `logActivity` downstream. `.max(200)` bounds the record on this path |
| `input` not a plain object (array/primitive) | `undefined` → ephemeral; zod rejects (matches existing malformed-args handling) |
| Oversized `contextId` (> 200 chars) | Rejected by zod `.max(200)` before it can become a session key |
| `logActivity` with a never-opened `contextId` | Succeeds; session auto-vivifies with `description: null`; row still carries the `contextId` |
| Two `logActivity` calls, same `contextId` | Both run in the same session and both rows carry the `contextId` → grouped |
| Same capture tuple, different `contextId` | Two records — `contextId` is in the fingerprint, so no cross-context dedup collision |
| CLI `fsdev run … logActivity` | `contextId` is still stored on the record and in the fingerprint (handler runs identically), but the `mcp.session` directive is not consulted, so it does not set the session id (CLI routes session via `--session`) |

No new error taxonomy. All existing tools/call error mapping (`ConcurrencyRejectedError`, capacity, queue timeout) is untouched.

## 8. Non-Goals

- **Promoting the hook to a first-class framework capability.** This is a POC in the knowledge-hub lab. A general "sessions for MCP" capability (built-in tool + declarative wiring across flows) is a follow-up.
- **Enforcing "context must exist before capture."** Auto-vivify is deliberate; a hard gate is out of scope.
- **Per-user/tenant namespacing hardening for caller-supplied session ids.** Safe here under a single server-set `userId`; a general version must confirm session-key namespacing before exposing `fromInput` broadly. Flag for the capability follow-up.
- **The `{ resolve: fn }` arm** of the directive — reserved in the type's intent but not implemented now.
- **Other transports** (HTTP action routes, webhooks) deriving session from input — MCP only.
- **A separate `contexts` resource collection.** Rejected as a redundant second source of truth — the session record already is the context record (its state holds the description); `contextId` on the inbox row carries the grouping. Revisit only if a consumer needs to enumerate/query contexts independently of the inbox and session stores.
- **Sweeper consumption of the description / grouping** — owned by FIX-883.
