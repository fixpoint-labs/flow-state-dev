# FIX-907: Rename `board.block` → `board.drain` — Implementation Spec

## 1. TLDR

**Plain-language summary.** A task board is two things: durable task *state*, and the
*thing that runs those tasks* — the "drain." Today the handle you get back from
`taskBoard({...})` exposes that runner as `board.block`, an opaque name that says
nothing about what it does. This renames it to `board.drain` everywhere, so the
name matches the concept the docs already teach. Nothing about how the board runs
changes — it's a vocabulary fix that makes the board-lifecycle mental model land.

**Technical statement.** Rename the `TaskBoardHandle.block` field to `drain` (a
one-pass rename that drops the old name — no alias), and update every in-repo
consumer, test, example, and doc page to match.

**Deliverables.**

- **Orchestration:** Rename `TaskBoardHandle.block` → `drain` and its construction in `packages/orchestration/src/task-board/index.ts`; update the handle/collection-spec JSDoc that references `board.block`.
- **Patterns:** Update the four internal drain mounts (`supervisor`, `plan-and-execute`, `parallelTasks`, `eventActors`) and the `taskBoard`→`MaterializedPattern` adapter in `packages/patterns/src/skill-registry.ts`.
- **Apps / integration-tests:** Update `apps/kitchen-sink/flows/chat-agent/task-queue-demo.ts` and the two integration-test fixtures/scenarios that mount `board.block`.
- **Tests:** Update `packages/orchestration/test/task-board/*` and any `packages/patterns/test/*` that access `.block`.
- **Examples:** Update `examples/guides/{board-lifecycle,custom-pattern,research-team}` source, tests, and READMEs.
- **Docs:** Update the `board-lifecycle` and `create-your-own-pattern` guides, the `orchestration/task-board` reference page, the four pattern pages, `packages/orchestration/README.md`, and the `create-pattern` skill doc.
- **Changeset:** Add `.changeset/fix-907-board-drain-rename.md` bumping `@flow-state-dev/orchestration` + `@flow-state-dev/patterns` (minor).

**Size estimate.** **Medium** — multi-file / 1 PR / <100 net LOC, but the rename
touches ~9 code files, ~9 doc pages, and 3 example dirs. Mechanical, type-enforced,
single PR.

## 2. Overview

Linear issue: [FIX-907](https://linear.app/fixpoint-labs/issue/FIX-907/task-board-rename-boardblock-boarddrain-and-make-the-drain-a)

`taskBoard({...})` returns `{ block, collectionId, capability }`. The `block` field
holds the composed sequencer that *drains* the board — it claims pending tasks, runs
workers, and loops until idle. The name `block` is generic (every mountable thing in
the framework is a "block") and carries none of that meaning. The new
`board-lifecycle` guide is built entirely around the identity "`board.block` = the
drain," teaching the split between durable task *state* and the *drain* that runs it
— and the field name works against the very distinction the guide exists to make.

This spec renames the field to `board.drain` in one pass, dropping `board.block`
(no deprecated alias). All consumers are first-party and in-repo, and the framework
is pre-1.0, so a clean break is safe and the compiler enumerates every stale call
site for us.

The issue's Phase 2 (a configurable drain factory) is **out of scope here** and
moves to FIX-910 — see §8 and §10.

## 3. Background & Research

### How the drain works today

`taskBoard()` (`packages/orchestration/src/task-board/index.ts:408`) builds a
composed outer `sequencer` (lines 641–662): `installFlowState → boardMetaActive →
seed → forEach(worker) → boardMetaCompleted → teardown`. Each worker is its own
sequencer that claims a task, runs the worker body, checks the board, and loops back.
That composed sequencer is returned as `TaskBoardHandle.block` (line 691) and mounted
by consumers via `.step(board.block)`.

The behavior is unchanged by this spec. The rename touches exactly one public field
name and its references.

### Why the rename is separable from the factory

The issue bundles two things: (1) the rename, and (2) making the drain a configurable
`board.drain(options)` factory with candidate knobs `max` / `snapshot` / `filter`. A
necessity check (documented on the issue) found the factory's knobs have no cited
consumer today, and turning `.drain` from a property into a callable is itself a
breaking change that should be pinned by a real use case rather than guessed.

FIX-910 ("Rethink patterns as config-driven strategies") surfaces that use case: a
`converge` primitive parameterized by `(produceNextTasks, drain, judge, terminate)`.
But converge needs the drain as a **first-class, named, mountable block it can pass
as a parameter** — which *this rename delivers* (`drain: board.drain` composes exactly
like plan-and-execute's `.step(board.block).loopBack(...)` does today). The
*configurable* factory (and any `createDrain` extraction) should be shaped by
converge's concrete config schema, so it is owned by FIX-910. This spec unblocks that
work by landing the `board.drain` name.

### Precedent for the rename mechanics

The `MaterializedPattern` contract (`packages/orchestration/src/skills/pattern-registry.ts:75`)
has its own `block` field, populated by the `taskBoard`→`MaterializedPattern` adapter
in `packages/patterns/src/skill-registry.ts:143`. That contract is **not** part of
this rename — only the adapter's read of the handle changes
(`handle.block` → `handle.drain`). This keeps the skills/pattern-run materialization
path untouched.

### Key Decisions & Ramifications (top 5)

1. **Scope = rename only; the configurable drain factory moves to FIX-910.**
   Alternative rejected: design `board.drain(options)` here. Ramification: FIX-907
   stays a mechanical, type-enforced vocabulary change with no design risk; the
   factory's shape is pinned by converge's real needs in FIX-910 instead of guessed.
   Risk it carries: FIX-910 must actually build the seam — tracked via the
   FIX-907↔FIX-910 relation and called out in §8/§10.

2. **One-pass rename that drops `board.block` (no deprecated alias).**
   Alternative rejected: keep `.block` as a delegating alias for one release.
   Ramification: a single public name (BP-038, no dual surface); dropping the field
   turns every stale consumer into a compile error, so the rename cannot silently
   miss a site. Locks out any external caller still on `.block` — acceptable because
   all consumers are in-repo and the framework is pre-1.0.

3. **`MaterializedPattern.block` is a separate contract and is NOT renamed.**
   Alternative rejected: rename every `.block` the grep surfaces. Ramification: the
   ripple stays bounded to the `taskBoard` handle and its direct mounts; the
   pattern-registry / runSkill materialization path (which keys on its own `block`
   field) is untouched.

4. **Verification is typecheck-driven; no goal check applies.**
   Alternative rejected: author a real-model goal check. Ramification: because the
   drain's runtime behavior is byte-for-byte unchanged, a real-LLM run would prove
   nothing the existing suite doesn't. `pnpm typecheck` (red→green as consumers are
   updated) plus the existing task-board/pattern/integration suites are the correct
   and sufficient evidence. The one non-type-enforced site (an `as unknown` cast,
   §6) is called out for manual check.

5. **Changeset bumps `@flow-state-dev/orchestration` + `@flow-state-dev/patterns` (minor).**
   Alternative rejected: patch, or orchestration-only. Ramification: a public API
   rename is a breaking change shipped as `minor` per BP-022 pre-1.0 rules; patterns
   bumps because it mounts the drain internally and its adapter changes. Workforce is
   excluded (no `board.block` usage found).

## 4. Technical Design

### Architecture

The public field lives in `@flow-state-dev/orchestration`; the internal consumers
live in `@flow-state-dev/patterns`, `apps/kitchen-sink`, and
`packages/integration-tests`. No new modules, types, or exports — this is a rename
of one field plus its references.

### API surface change

`packages/orchestration/src/task-board/index.ts`:

```ts
// Before
export interface TaskBoardHandle {
  block: SequencerDefinition<any, any>;
  collectionId: string;
  capability: DefinedCapability<string, TaskBoardCapabilityAccessor>;
}
// ...
return { block, collectionId, capability };

// After
export interface TaskBoardHandle {
  /** The composed drain sequencer. Mount it in a parent flow or sequencer. */
  drain: SequencerDefinition<any, any>;
  collectionId: string;
  capability: DefinedCapability<string, TaskBoardCapabilityAccessor>;
}
// ...
return { drain: block, collectionId, capability };
```

The local variable `block` (the composed sequencer) may stay named `block`
internally; only the returned field key changes. The JSDoc on the `TaskBoardHandle`
field (index.ts:367–397) and the collection-spec doc comments that mention
`board.block` (index.ts:196, 217, 669, 673) are updated to say `board.drain`.

   `skill-registry.ts:143` adapter + JSDoc.

4. **Update `apps/kitchen-sink` + `packages/integration-tests`.**

5. **Update `examples/guides/{board-lifecycle,custom-pattern,research-team}`** source,

   → verify: each example's `pnpm test` (where present) passes; grep the example dirs
   for residual `board.block`.

6. **Update docs** (§9) and the `create-pattern` skill doc.

independent of each other once step 1 lands.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| A consumer reads `.block` after the rename | Compile error (`Property 'block' does not exist on type 'TaskBoardHandle'`). Intended — this is the migration checklist. |
| `plan-and-execute/index.ts:757` `.loopBack(board.block.name, …)` | Becomes `board.drain.name`. The block's `.name` is unaffected by the field rename; only the accessor path changes. |
| `skill-registry.ts:143` `handle.block as unknown as BlockDefinition` | The `as unknown` cast applies to the *result* of the property access, so `handle.block` still errors when the field is gone — typecheck catches it. **Still verify manually** — it is the one site where a cast is adjacent to the renamed access. |
| `MaterializedPattern.block` and `PatternFactory` return shape | Unchanged. Not part of this rename. |
| Unrelated `.block` reads (`RosterEntry.block` in round-robin/debate, actor `a.block` in eventActors:357, flow-action `.block`) | Untouched — these are different contracts. Do not rename. |
| Internal worker/sequencer block *names* (`${name}-worker-…`) | Independent of the handle field name; no runtime name collision from the rename. |
| Prose-only "drain" references already correct (`orchestration/overview.md`, `task-substrate.md`, `agents.md`) | No field-name edit needed; leave conceptually valid prose as-is. |

No retryable vs. fatal taxonomy applies — there is no runtime error surface.

## 7. Testing Strategy

**Goal & goal check.** No goal check applies. This is a pure symbol rename with **no
observable runtime behavior change** — the drain claims, runs, and terminates
identically before and after. A real-model `fsdev run` would prove nothing the
existing deterministic suite doesn't. (Escape hatch justified per the skill: "no
observable behaviour to prove," not "a real run is inconvenient.")

**Discipline.** Enhancement/refactor. Not a red-green TDD cycle (no new behavior) and
not a bug diagnose loop. The feedback loop is the **compiler**: dropping `.block`
makes `pnpm typecheck` red, and it goes green exactly when every consumer is migrated.
Then the existing suites confirm behavior is preserved.

**Verification evidence (BP-003).**

- `pnpm typecheck` — workspace-clean. Pass criteria: zero errors; the transient
  red→green trace during implementation is the migration checklist.
- `pnpm --filter @flow-state-dev/orchestration test` — the task-board suite
  (`test/task-board/task-board.test.ts` + research-demo, tool-cache,
  flow-policy-backcompat) green. These drive the board via
  `testBlock(board.drain, …)` and assert terminal task states from emitted
  `task-change` items — behavior preservation is exactly what they check.
- `pnpm --filter @flow-state-dev/patterns test` — supervisor / plan-and-execute /
  parallelTasks suites green (they exercise the drain mounts).
- `packages/integration-tests` task-board scenarios green.
- Repo-wide grep for residual `board.block` / `taskBoard.block` returns nothing
  (outside this spec and changelog history).

**Reference test files for patterns:** `packages/orchestration/test/task-board/task-board.test.ts`
(mock-context + `testBlock` idiom, `lastTaskState` helper) and
`packages/orchestration/test/helpers.ts`.

## 8. Non-Goals

- **The configurable drain factory** (`board.drain(options)` / a standalone
  `createDrain(...)`), and the candidate knobs `max` / `snapshot` / `filter`. This is
  the issue's Phase 2. It is **owned by FIX-910**, where the `converge` primitive is
  the concrete consumer that pins the factory's config shape. This spec deliberately
  keeps `board.drain` a plain mountable block so `converge({ …, drain: board.drain, … })`
  composes today; FIX-910 adds configurability against its real schema.
- **Any change to drain runtime behavior** — termination modes, dispatcher,
  concurrency, live-vs-snapshot semantics, flow policy, tool cache. Untouched.
- **Renaming `MaterializedPattern.block`** or the pattern-registry / runSkill
  materialization contract.
- **The `pattern` → `strategy` naming** (FIX-910) and the **board capability-surface
  redesign** (FIX-908). Coordinated siblings, not this spec.
- **Deepening opportunity flagged during analysis (follow-up, not this spec):** the
  drain construction is currently inlined inside `taskBoard()` (index.ts ~468–662).
  Extracting it into a standalone drain builder is the natural home for FIX-910's
  factory work; flagged here so it is visible without expanding this scope. Follow up
  via FIX-910 / `fsd:improve-codebase-architecture`.
