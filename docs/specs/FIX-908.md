# FIX-908: Task board — make backing an internal detail (one capability surface, addTask sugar, request-default) — Implementation Spec

## 1. TLDR

**Plain-language summary.** When you build a "task board" (a to-do list that AI
workers pull from), you currently have to keep repeating *how* the board stores
its tasks every time you touch it — and the storage choice you almost never want
is the one you get by default. That is fiddly and error-prone, and it makes some
natural compositions blow up. This change lets you pick the storage once when you
create the board, gives you short, direct methods to add and read tasks
(`board.addTask(...)` instead of `(await board.tasks()).addTask(...)`), flips the
default to the storage everyone actually reaches for, and adds a clean way to
declare a durable board that survives across turns.

**Technical statement.** Make `backing` a once-chosen internal detail of
`taskBoard({...})`, expose `addTask`/`addTasks`/`getTask`/`listTasks`/`countTasks`
sugar (plus the existing `tasks()` escape hatch) directly on the capability
accessor, shorten the accessor key from `ctx.cap.taskBoard_<name>` to
`ctx.cap.<name>`, flip the default backing from `sequencer` to `request`, and add
a first-class `defineTaskCollection({ scope, stateSchema, ... })` for the
resource-backed (durable) case.

**Deliverables:**

- **Orchestration (core surface):**
  - Add sugar methods (`addTask`, `addTasks`, `getTask`, `listTasks`, `countTasks`)
    to the capability accessor built in
    `packages/orchestration/src/task-board/capability.ts`, delegating to the
    resolved `TaskCollectionRef`; keep `tasks()` as the full-ref escape hatch.
  - Shorten the accessor key from `taskBoard_<name>` to the board name verbatim
    (`<name>`) in `capability.ts` (no new identifier throw; same-name collisions
    ride the existing `flattenCapabilities` merge check).
  - Flip the default backing to `request` in `taskBoard()`
    (`packages/orchestration/src/task-board/index.ts`); accept an omitted
    `collection` (defaults to `{ backing: "request", collectionId: name }`).
  - Accept a resource-backed board by passing a `DefinedTaskCollection` as
    `collection` (closes the resource/sequencer/request config asymmetry).
  - Add `defineTaskCollection({ scope, stateSchema, ... })` in a new
    `packages/orchestration/src/tasks/collection/define-task-collection.ts`,
    wrapping `defineResourceCollection` (mirrors `defineSkillsCollection` /
    `defineScheduleCollection`).
- **Patterns:** drop the now-redundant explicit `backing: "request"` overrides in
  supervisor, plan-and-execute, eventActors, parallelTasks, and the shared
  planning entry (default now covers them).
- **Docs:** rewrite the backing model across
  `apps/docs/docs/orchestration/{overview,task-substrate,task-board,flow-policy}.md`
  and the four `apps/docs/guides/*` orchestration guides; update
  `packages/orchestration/README.md` and `packages/patterns/README.md`; add a
  `.changeset/*.md`.

**Size:** **Large** — multi-package (orchestration + patterns + docs), >500 LOC
across source, tests, and doc rewrites, but a single PR (no runtime data
migration). Splittable if needed as: (1) capability accessor sugar + accessor
rename, (2) request-default + `defineTaskCollection` + pattern cleanup, (3) docs.

## 2. Overview

Linear: [FIX-908](https://linear.app/fixpoint-labs/issue/FIX-908)

A composer should never have to know or restate how a task board stores its tasks.
Today the `backing` choice (`sequencer` / `request` / `resource`) leaks into every
call site, the capability that is supposed to hide it exposes only `tasks()`, the
accessor key is long and awkward, resource backing has no config-object form, and
the default (`sequencer`) is a composition footgun that nobody reaches for. This
spec makes backing a once-chosen internal detail, completes the capability surface
with direct sugar methods, flips the default to `request`, and adds a first-class
`defineTaskCollection` for the durable (resource) case. Surfaced during the #798
orchestration-consolidation review.

## 3. Background & Research

### How the code is shaped today

- **`taskBoard(config)`** (`packages/orchestration/src/task-board/index.ts:408`)
  returns `{ block, collectionId, capability }`
  (`TaskBoardHandle`, `index.ts:367`). `config.collection` is a union
  (`index.ts:198–233`): `TaskBoardSequencerCollectionSpec` (backing optional,
  **defaults to `"sequencer"`** at `index.ts:685`),
  `TaskBoardRequestCollectionSpec` (`backing: "request"`), or a
  `TaskBoardCollectionFactory` `(ctx) => TaskCollectionRef` — the **only** way to
  reach resource backing. There is no `{ backing: "resource", collection,
  collectionId }` object form.
- **`getOrCreateTaskCollection(options)`**
  (`packages/orchestration/src/tasks/collection/get-or-create.ts:107`) is the
  substrate factory. It takes one of three backing specs, each requiring the
  caller to restate `backing` + `collectionId` (+ `stateKey` / `sequencer` /
  `collection`). It is uniformly `async` (FIX-700). Board consumers reach it either
  through the capability's `tasks()` or by calling it directly with
  `ctx.getTarget(boardName)`/`ctx.sequencer` (sequencer backing) — which only
  resolves inside the board's own subtree, the root cause of the sibling-add
  footgun.
- **The capability** (`packages/orchestration/src/task-board/capability.ts:158`)
  builds a `DefinedCapability` named `taskBoard_<boardName>` (`capability.ts:162`;
  underscore keeps a valid JS identifier, `capability.ts:28–34`). Its `fns(ctx)`
  returns `{ tasks: () => Promise<TaskCollectionRef> }` — **`tasks()` is the only
  method** (`TaskBoardCapabilityAccessor`, `capability.ts:139`). The framework maps
  a capability's `name` verbatim to its `ctx.cap` key
  (`packages/engine/src/execution/executeBlock.ts:175`:
  `capObj[base.name] = base.fns(ctx)`).
- **`TaskCollectionRef`** (`packages/orchestration/src/tasks/collection/types.ts:78`)
  exposes `addTask`, `addTasks`, `get`, `list`, `count`, plus worker-lifecycle
  methods (`claim`, `complete`, `fail`, `block`, …). The resolved ref's `get`/
  `list`/`count` are **synchronous**; only the resolution (`tasks()`) is async.
- **`defineResourceCollection`**
  (`packages/core/src/types/resource-collection.ts:259`) already takes `scope`
  (required `"session" | "user" | "org"`), `pattern`, `stateSchema`, etc. Two
  in-repo precedents wrap it into an opinionated `defineXCollection`:
  `defineSkillsCollection`
  (`packages/orchestration/src/skills/collection.ts:75`) and
  `defineScheduleCollection`
  (`packages/scheduled/src/defineScheduleCollection.ts:70`) — both fix a `pattern`,
  forward/default `scope`, fix a `stateSchema`, return the branded collection, and
  are declared on a capability's `resources:` map so a consumer reaches the ref via
  `ctx.resources.<key>`.

### Precedent that decides the design

- **Multi-method sugar accessors are the norm, not a novelty.**
  `ctx.cap.workingMemory` exposes 8 methods (`packages/memory/src/capabilities.ts:64`);
  `semanticMemory` exposes `addFact`/`removeFact`/`allFacts`/`query`
  (`capabilities.ts:171`); `ctx.cap.perspective` exposes ~10
  (`packages/thought-fabric-core/src/identity/perspective-capability.ts:147`). Each
  resolves its ref(s) once at the top of `fns` and returns named closures. Adding
  `addTask`/`listTasks`/… to the board accessor **matches the framework's own
  capability design** — it is not a wrapper-over-primitive.
- **Every other capability uses a bare singleton name** (`workingMemory`,
  `perspective`, `mcp`, `skills`, `taskTools`, `memory`). The task board's
  `taskBoard_<name>` prefix is the lone exception. Shortening to `<name>` aligns it
  with the convention.
- **Changing a default while keeping the old option is a blessed move.** FIX-626
  changed the board's `onIdle` default and kept the superseded value as an explicit
  opt-in with a pinned regression test
  (`packages/orchestration/test/task-board/task-board.test.ts:536`). The backing
  flip follows exactly this template.
- **Pre-1.0 posture.** `packages/orchestration/package.json` is `0.0.0`; BP-022
  allows breaking changes as `minor`. BP-030 mandates dual-read only for
  *persisted/in-flight data* — not source-level API aliases — and BP-038 says a
  superseded internal path is deleted in the same PR. So the accessor rename and
  the `collection`-shape change are clean breaks (no deprecated alias), while the
  one persisted concern (request namespacing by `collectionId`) is preserved by
  keeping `collectionId` defaulting to `name`.

### Why this approach over alternatives

| Question | Chosen | Rejected |
|---|---|---|
| How to hide backing? | Choose once on `taskBoard`; omitted `collection` ⇒ request; capability accessor is the only thing consumers touch | Keep restating `{ backing, collectionId }` at every `getOrCreateTaskCollection` call (status quo — drift-prone) |
| Sugar shape? | Named delegating closures on the accessor (`addTask`/`listTasks`/…), uniformly async, over the resolved ref; `tasks()` retained | Spread the full ref onto the accessor (20+ methods, mixes worker-lifecycle verbs into the composer surface) |
| Accessor key? | Bare `ctx.cap.<name>` (board name verbatim); collisions ride the existing merge check, no new throw | Keep `taskBoard_<name>` (inconsistent, verbose); a hard identifier throw (breaks hyphenated names) |
| Default backing? | `request` (composition-safe, re-enterable) | `sequencer` (footgun) — kept only as explicit opt-in |
| Resource case? | `defineTaskCollection({ scope, stateSchema })` passed as `collection` | Keep the `(ctx) => getOrCreateTaskCollection({ backing: "resource" })` factory asymmetry |

### Key Decisions & Ramifications (top 5)

1. **Default backing flips `sequencer` → `request`; `sequencer` survives as an
   explicit opt-in.** *Rejected:* removing sequencer backing entirely (see Open
   Questions). *Locks in:* board tasks live on `ctx.request` by default, so
   sibling/outer steps can `addTask` before/after/between drains and re-entry
   (replan loops) accumulates by `collectionId`. *Ramification / risk:* request
   namespaces by `collectionId`, so invoking the same board id twice in one request
   **shares** state — desirable for replan, but independent boards must use distinct
   ids. `collectionId` defaults to `name` (flow-unique), so this is safe by default;
   documented explicitly. A pinned regression test keeps sequencer backing's
   isolated/auto-cleaned semantics working.

2. **The capability accessor is the whole consumer surface; `getOrCreateTaskCollection`
   stays a substrate primitive, not a board-consumer API.** *Rejected:* making
   `getOrCreateTaskCollection` fully private (breaks round-robin/debate/
   routedSpecialists, which call it directly with `ctx.sequencer!` and have no
   board). *Locks in:* board consumers use `ctx.cap.<name>.addTask/…`; the raw
   factory remains public in `@flow-state-dev/orchestration/tasks` for the rare
   no-board direct-substrate composition. *Ramification:* the "backing chosen once,
   never restated" guarantee holds for anything with a board; the non-board
   substrate users are a documented follow-up (Non-Goals), not a break.

3. **Accessor key shortens to bare `ctx.cap.<name>`, using the board name
   verbatim.** *Rejected:* `board_<name>` (safer against collisions but still
   verbose), keeping `taskBoard_<name>`, and adding a hard "valid JS identifier"
   throw. *Locks in:* alignment with every other capability's bare-name convention;
   hyphenated names stay bracket-accessible exactly as today (`ctx.cap["plan-board"]`).
   *Ramification / risk:* a board named `memory` alongside the memory capability
   would collide on `ctx.cap.memory` — but this is **already caught** by the
   existing `flattenCapabilities` merge check (`merge.ts:92`), so no new code and
   no change to the capability-merge contract. A hard identifier throw was rejected
   because the board `name` doubles as the sequencer/block-name prefix and
   hyphenated names (`${config}-board`) are common and currently work; forcing an
   identifier would newly break them.

4. **`defineTaskCollection({ scope, stateSchema, ... })` is the resource-backed
   entry, and a `DefinedTaskCollection` is accepted directly as `collection`.**
   *Rejected:* keeping the resolve-inside-a-factory asymmetry. *Locks in:* the
   three backings become symmetric at the `taskBoard` level (`{ backing: "request"
   }` | `{ backing: "sequencer" }` | a `DefinedTaskCollection`), and durable boards
   are declared with one call that mirrors `defineSkillsCollection`/
   `defineScheduleCollection`. *Ramification:* the board capability declares the
   collection on its `resources:` map so the sugar can resolve it via
   `ctx.resources`; the pre-existing sync-mirror snapshot caveat (a resolved
   resource handle knows a fixed task set at resolution time) is inherited and must
   be documented, not silently changed.

5. **Clean break, no deprecated aliases (pre-1.0, BP-038).** *Rejected:* keeping
   `taskBoard_<name>` and the per-call `collection: { backing }` object as
   deprecated aliases for a release. *Locks in:* one surface, no dead paths; every
   in-repo consumer (patterns, kitchen-sink, examples, tests) is migrated in the
   same PR. *Ramification:* a `minor` changeset with a short migration note; no
   external users to break at 0.0.0, and BP-030's dual-read obligation does not
   apply (no persisted shape changes — request state keying is preserved).

## 4. Technical Design

> **Post-validation note (authoritative).** Three-agent validation corrected the
> resource-backing wiring, the `fns` typing, and the accessor-collision story. The
> load-bearing corrections, folded into the sections below:
> (1) `defineTaskCollection`'s pattern must be a **single-wildcard** `"<id>/*"` (curly
> `{taskId}` fails `validatePattern`; a parameterized `[taskId]` breaks the
> string-key `create(task.id)` call in `resource-backed.ts`).
> (2) The board must declare the resource collection on the **outer board sequencer
> `block`** (which bubbles to the flow-global `ctx.resources`) — capability-`uses`
> registration alone does not feed the board's *own* drain blocks.
> (3) `TaskBoardCapabilityAccessor` stays a `type` with the
> `& Record<string, (...args)=>any>` intersection (an `interface` fails
> `defineCapability`'s `TFns` constraint).
> (4) Accessor-key collisions are already caught by the existing
> `flattenCapabilities` merge check — no new task-board-specific merge check, and
> **no hard "valid JS identifier" throw** (that would newly reject today-working
> hyphenated names like `${config}-board`); the board name is used verbatim as the
> key, bracket-accessible for non-identifier names exactly as today.

### 4.1 `taskBoard()` config — backing chosen once

`packages/orchestration/src/task-board/index.ts`. Widen `collection` to accept a
`DefinedTaskCollection` and make it optional:

```ts
type TaskBoardCollection<TInput, TOutput> =
  | { backing?: "request"; collectionId?: string; stateKey?: string }   // default
  | { backing: "sequencer"; collectionId: string; stateKey?: string }   // opt-in
  | DefinedTaskCollection<TInput>;                                       // resource

interface TaskBoardConfig<TInput, TOutput> {
  name: string;
  collection?: TaskBoardCollection<TInput, TOutput>;  // omitted ⇒ request, id = name
  workers: TaskWorker<TInput, TOutput> | TaskWorkerRegistry<TInput, TOutput>;
  // ...unchanged: concurrency, dispatcher, onIdle, initialTasks, onError,
  //    maxIterations, shouldExit, idlePollMs, toolCache, flowPolicy
}
```

Resolution (`resolveCollectionId` / `buildCollectionFactory`, `index.ts:721–771`):

- `collection` omitted → `{ backing: "request", collectionId: name }`.
- `{ backing: "request", collectionId? }` → `collectionId ?? name`.
- `{ backing: "sequencer", collectionId }` → unchanged sequencer path.
- `DefinedTaskCollection` → the board declares the collection on its **outer
  sequencer `block`'s** `resources: { [key]: def }` slot (scope from the
  definition). Declaring it on `block` is required, not optional: `ctx.resources`
  is a flat, flow-global registry built from all bubbled-up declarations, and the
  board's own drain blocks (seed, workers, meta) resolve the collection through
  `collectionFactory(ctx)` → `ctx.resources[key]` (the `getCollection` idiom in
  `active-pattern-collection.ts:71`) — they never list `board.capability` in
  `uses`, so a capability-`uses`-only registration would leave the storage
  unregistered and the drain would resolve `undefined` and throw. Declaring on
  `block` makes the ref resolvable both for the drain and for external
  `uses: [board.capability]` consumers. The board's `collectionId` is the
  collection's stable id.

The bridge from the branded `DefinedTaskCollection` (a definition) to the resolved
`ResourceCollectionRef` (what `getOrCreateTaskCollection({ backing: "resource",
collection })` needs) is exactly this `ctx.resources[key]` lookup at runtime,
resolved inside `buildCollectionFactory` (`index.ts:721`).

### 4.2 `defineTaskCollection`

New file `packages/orchestration/src/tasks/collection/define-task-collection.ts`,
exported from `packages/orchestration/src/index.ts` and the
`@flow-state-dev/orchestration/tasks` subpath. Mirrors `defineScheduleCollection`:

```ts
export interface DefineTaskCollectionOptions<TInput> {
  scope: ScopeType;                                  // "session" | "user" | "org"
  /** Per-task input payload schema (task envelope is fixed). */
  stateSchema?: ZodType<TInput>;
  id?: string;                                       // storage-key namespace; default derived
  maxInstances?: number;
  eviction?: "none" | "lru" | "oldest";
  prefetchMode?: "eager" | "lazy";
}

export function defineTaskCollection<TInput = unknown>(
  options: DefineTaskCollectionOptions<TInput>,
): DefinedTaskCollection<TInput>;
```

Internally: `defineResourceCollection({ pattern: "<id>/*", scope, stateSchema:
taskEnvelopeSchema(stateSchema), maxInstances, eviction, prefetchMode })`, branded
as `DefinedTaskCollection` so `taskBoard` and the capability can recognize it.

Two correctness constraints (from validation):

- **Pattern is single-wildcard `"<id>/*"`, not `{taskId}` or `[taskId]`.** The
  collection-pattern validator (`packages/core/src/types/collection-patterns.ts:22`)
  requires `*`, `**`, or `[param]`; curly braces are not a pattern token. And
  `createResourceBackedTaskCollection` calls `collection.create(task.id, …)` with a
  **string** key (`packages/orchestration/src/tasks/collection/resource-backed.ts:204,217`),
  which a parameterized `[taskId]` pattern would reject
  (`collection-patterns.ts:162` requires an object key for parameterized patterns).
  A single `*` resolves the string id as `<id>/<taskId>`.
- **`taskEnvelopeSchema(stateSchema)` must validate the whole `Task` envelope
  permissively**, not just the per-task `input`. Resource backing stores the full
  `Task` as instance state (`resource-backed.ts:204`), and a schema-reject wipes the
  record via `normalizeResourceState` (see the warning at
  `packages/orchestration/src/skills/collection.ts:24–35`). So the envelope schema
  wraps the fixed `taskSchema` (`packages/orchestration/src/tasks/schema/task.ts` —
  `status`/`attempts`/`leaseUntil`/…) and substitutes the caller's `stateSchema`
  only for the `input` field. The caller's `stateSchema` types only the per-task
  `input`; the envelope is otherwise fixed.

### 4.3 Capability accessor — sugar + rename

`packages/orchestration/src/task-board/capability.ts`.

- **Name:** `const capabilityName = boardName` (drop the `taskBoard_` prefix,
  `capability.ts:162`). Use the board name **verbatim** as the key — no new
  identifier throw. This matches today's behavior exactly minus the prefix: an
  identifier-valid name is dot-accessible (`ctx.cap.research`), a hyphenated name
  (`ctx.cap["plan-board"]`) is bracket-accessible, just as `taskBoard_plan-board`
  is today. A hard "valid JS identifier" throw is **rejected** — the board `name`
  doubles as the sequencer/block-name prefix and hyphenated names
  (`${config}-board`, `my-plan`) are common and currently work. Collisions with
  another capability of the same name are already caught by the existing
  `flattenCapabilities` merge check
  (`packages/core/src/capability/merge.ts:92`, throws "Capability name
  collision: …") — no new task-board-specific check is added, so the
  capability-merge contract is reused as-is (§9.2).
- **Accessor shape:** widen `TaskBoardCapabilityAccessor`, kept a `type` with the
  `& Record<...>` intersection (a plain `interface` lacks the implicit index
  signature `defineCapability`'s `TFns extends Record<string, (...args:any[]) =>
  any>` constraint requires — the reason the current alias is a `type`,
  `capability.ts:135–141`):

```ts
export type TaskBoardCapabilityAccessor<TInput = unknown, TOutput = unknown> = {
  /** Escape hatch: the full resolved TaskCollectionRef. */
  tasks(): Promise<TaskCollectionRef<TInput, TOutput>>;
  addTask(init: TaskInit<TInput>): Promise<Task<TInput, TOutput>>;
  addTasks(inits: readonly TaskInit<TInput>[]): Promise<Task<TInput, TOutput>[]>;
  getTask(id: string): Promise<TaskHandle<TInput, TOutput> | undefined>;
  listTasks(filter?: TaskFilter): Promise<TaskHandle<TInput, TOutput>[]>;
  countTasks(filter?: TaskFilter): Promise<number>;
} & Record<string, (...args: any[]) => any>;
```

Each backing branch builds the accessor by closing over a **local** `resolve`
(the branch's backing-aware `tasks()` logic), not `this` — so a destructured
`const { addTask } = ctx.cap.research` still works:

```ts
const resolve = () => getOrCreateTaskCollection({ ctx, backing, collectionId, ... });
return {
  tasks: resolve,
  addTask: async (init) => (await resolve()).addTask(init),
  addTasks: async (inits) => (await resolve()).addTasks(inits),
  getTask: async (id) => (await resolve()).get(id),
  listTasks: async (f) => (await resolve()).list(f),
  countTasks: async (f) => (await resolve()).count(f),
};
```

All sugar is **uniformly async** across all three backings (resolution is async
even though the resolved ref's reads are sync) — one shape regardless of backing.
The three backing branches (`capability.ts:170/195/228`) each build this same
accessor object; only `resolve` differs per backing. The sequencer branch keeps
its `targetStateSchemas: { [boardName]: taskBoardStateSchema }` and its
throw-when-resolved-outside-subtree behavior. The resource branch resolves the
`DefinedTaskCollection` ref from `ctx.resources.<key>`.

**Sugar naming:** the query methods are task-suffixed (`getTask`/`listTasks`/
`countTasks`) rather than the ref's bare `get`/`list`/`count`, because at the
board-accessor altitude (`ctx.cap.research.get(id)`) the bare verbs are ambiguous.
`addTask`/`addTasks` already match the ref. `tasks()` remains for full-ref access
(lifecycle verbs, `items()` windows).

### 4.4 Data flow

```
taskBoard({ name, collection?, workers })
  → resolve backing once (request default | sequencer opt-in | DefinedTaskCollection)
  → handle { drain (was block, FIX-907), collectionId, capability }
  → uses: [board.capability] on any block
      → ctx.cap.<name>.addTask({...})       // sibling/outer step, before/after drain
      → ctx.cap.<name>.listTasks({ status })
  → board.drain processes tasks; request backing lifts state to ctx.request,
    so adds from outside the board subtree resolve (no getTarget throw)
```

### 4.5 Pattern cleanup

**Remove the redundant `taskBoard({ collection: { backing: "request" } })`
overrides** (default now covers them) at the four board-construction sites:
`supervisor/index.ts:339`, `plan-and-execute/index.ts:690`, `eventActors/index.ts:363`,
`parallelTasks/index.ts:93`.

**Migrate the board-scoped `getOrCreateTaskCollection({ backing: "request" })`
resolution calls to `ctx.cap.<name>` sugar.** Enumerated so an implementer need not
rediscover them: `shared/planning-entry.ts:110`,
`supervisor/blocks/{reviewer-check.ts:188, label-failed-reviews.ts:36, synthesize.ts:49}`,
`plan-and-execute/blocks/{evaluate-progress.ts:126, evaluate-progress.ts:168,
synthesize.ts:76, apply-replan.ts:83}`. For each: if the block already
`uses: [board.capability]`, replace resolve-then-call with the sugar; if not,
adding the capability to `uses` is the smaller change, but leaving the direct
substrate call is acceptable (it still works — the substrate stays public).
**`skills/skill-registry.ts:134` and `skills/active-pattern-collection.ts` are NOT
board-scoped** (the skills runtime resolves a pattern collection with no
`taskBoard`) — leave them on the substrate call. Sequencer-backed patterns
(round-robin, debate, routedSpecialists) are unchanged.

### 4.6 Error handling

| Condition | Handling |
|---|---|
| Board name is a hyphenated / non-identifier string | No error — used verbatim as the `ctx.cap` key, reachable via bracket access (`ctx.cap["plan-board"]`), unchanged from today's `taskBoard_plan-board` |
| Board name collides with another capability of the same name | Existing `flattenCapabilities` merge throw (`merge.ts:92`) — no new task-board code |
| Sugar method called where sequencer-backed collection can't resolve (outside board subtree) | Same throw the current `tasks()` raises (`capability.ts:239–251`), surfaced through the sugar method |
| `DefinedTaskCollection` passed but its scope resource not registered on `block` | Build-time resource-merge error (existing `defineResourceCollection` wiring); §4.1 requires declaring it on the outer board `block` |
| Same `collectionId` reused for two logically-independent request-backed boards | Not an error — documented shared-accumulation semantic; distinct ids required for independence |

## 5. Implementation Sequence

Discipline: **`fsd:tdd`** (Enhancement). Each step is independently testable.

1. **`defineTaskCollection` + `DefinedTaskCollection` brand.** New file + export.
   Unit-test: it produces a `defineResourceCollection` with the task pattern, the
   given scope, and a task envelope schema; the brand is recognized by a type
   guard. (Mirror `defineScheduleCollection` tests.)
2. **Capability accessor sugar.** Add `addTask`/`addTasks`/`getTask`/`listTasks`/
   `countTasks` delegating to the resolved ref across all three backing branches;
   keep `tasks()`. Test each sugar method against a `testBlock`-driven board for
   each backing (request, sequencer, resource-via-`defineTaskCollection`), asserting
   delegation parity with the ref.
3. **Accessor rename.** `taskBoard_<name>` → `<name>` (verbatim; no identifier
   throw, no new collision check — collisions ride the existing
   `flattenCapabilities` throw). Update the naming test
   (`task-board.test.ts:947–1005`) to assert `board.capability.name === "research"`
   and, for the existing `factory-board` fixture, `=== "factory-board"` (bracket
   access), not a throw. Add a test that two boards named the same as a sibling
   capability collide via the existing merge check.
4. **Request default + resource config form.** Make `collection` optional (⇒
   request, id = `name`); accept a `DefinedTaskCollection` as `collection`. Test:
   omitted collection drains correctly; a sibling step `addTask`-ing **before** the
   drain is processed (the footgun regression — this is the composition proof); the
   `DefinedTaskCollection` path drains a resource-backed board.
5. **Sequencer opt-in regression.** Pin sequencer backing's isolated/per-invocation
   behavior with an explicit `collection: { backing: "sequencer", collectionId }`
   test (mirror the FIX-626 legacy-pinning pattern).
6. **Pattern cleanup.** Remove redundant `backing: "request"` overrides; migrate
   board-scoped `getOrCreateTaskCollection` calls to sugar. Run the patterns test
   suites + integration-tests (`packages/integration-tests/src/scenarios/task-board-*`,
   `pattern-skill-*`) green.
7. **Migrate examples/kitchen-sink** (`apps/kitchen-sink/flows/chat-agent/task-queue-demo.ts`,

8. **Docs + changeset** (section 9).

Dependencies between steps: 1 precedes 4 (resource form needs the definer); 2
precedes 6 (sugar must exist before patterns adopt it); 3 is independent but should
land with 2 to avoid a churny second rename.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| `collection` omitted | Request-backed, `collectionId = name` |
| Same board id invoked twice in one request (request backing) | Shared/accumulated task state — intended for replan loops; documented |
| Two independent boards, same request | Must use distinct `collectionId`s (default = distinct `name`s, so safe) |
| Sibling step adds a task before the drain | Works under request default (was a throw under sequencer default) — the core footgun fix |
| Board name `factory-board` (hyphen) | No throw — `ctx.cap["factory-board"]` via bracket access, unchanged from today's `taskBoard_factory-board`. The existing `factory-board` naming fixture (`task-board.test.ts:947–1005`) keeps its name; only the expected key string updates (`"factory-board"`, not `"taskBoard_factory-board"`) |
| Board name equals another capability name (`memory`) | Existing `flattenCapabilities` collision throw (`merge.ts:92`) |
| `getTask`/`listTasks` on empty board | Resolves to `undefined` / `[]` / `0` (ref semantics) |
| Sequencer-backed sugar resolved outside the board subtree | Throws (unchanged `getTarget` semantics) — opt-in backing keeps its constraint |
| `defineTaskCollection` scope not registered on the flow | Build-time resource-merge error |
| Resource-backed handle read after mid-drain adds | Sync-mirror snapshot caveat: the resolved handle reflects the task set at resolution time — documented, not changed here |

Error taxonomy: the only new failure surface is **build-time** and reuses existing
machinery — a same-name capability collision (existing `flattenCapabilities`
throw) and a missing scope-resource registration (existing resource-merge error).
No new task-board-specific error code, no new retryable runtime error. Runtime
resolution failures reuse the existing `getTarget` throw.

## 7. Testing Strategy

concrete: this change is API ergonomics (sugar, accessor name), a composition fix
(request default), and a durable-declaration helper — none of it is a new
model-graded outcome. The one genuinely new *runtime* behavior — a sibling/outer
step can `addTask` before the drain and the drain processes it — is fully
deterministic and is proven by an integration test (step 4), not a real model. The
real-model regression for this change rests on the **existing vitest + integration

of scope. If it is authored, it becomes the standing regression that the
request-default flip and pattern edits didn't change observable end-to-end
behavior.

**Discipline:** `fsd:tdd` — each behavior below is a tracer-bullet cycle.

**Behaviours to test (vitest, `testBlock` + `lastTaskState` idiom,
`packages/orchestration/test/task-board/task-board.test.ts`):**

- Omitted `collection` → board drains; tasks live on `ctx.request`.

## 11. Open Questions

1. **Does sequencer backing still earn its keep at the `taskBoard` level?** No
   first-party `taskBoard` caller uses it (all four patterns override to request;
   the direct-sequencer users bypass `taskBoard` entirely). This spec **keeps** it
   as an explicit opt-in for the strictly-isolated, auto-cleaned, fresh-per-invocation
   black-box case. *Decision needed:* keep as opt-in (recommended — low cost, real
   isolation semantics, pinned by a regression test) vs. remove entirely (bigger
   break; the substrate sequencer backing stays regardless for round-robin/debate).
2. **Accessor key: bare `<name>` vs `board_<name>`.** Bare aligns with every other
   capability and matches the issue's stated target. The two risks the draft raised
   are resolved: collisions ride the **existing** `flattenCapabilities` throw (no new
   code), and hyphenated names stay bracket-accessible verbatim (no identifier throw,
   nothing that currently works breaks). *Recommendation:* bare `<name>`, verbatim.
   `board_<name>` (collision-safer but verbose) remains the fallback if the owner
   prefers a namespace prefix. Flagged only because it is a public-surface naming
   call.
3. **Sugar query naming: `getTask`/`listTasks`/`countTasks` vs mirroring the ref's
   `get`/`list`/`count`.** Recommendation: task-suffixed (clearer at the board
   altitude; `addTask` already matches the ref). Cheap to flip if the owner prefers
   mirroring.
