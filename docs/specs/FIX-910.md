# FIX-910: The converge primitive — a config-driven judge-gated loop over the task board — Implementation Spec

## 1. TLDR

**Plain-language summary.** Several of our built-in orchestration recipes are the
same underlying loop: hand out some work, run it to completion, ask "are we done
yet?", and if not, hand out more and repeat. Right now each recipe hand-wires that
loop its own way, so the same idea is spelled three different ways across the
codebase. This spec introduces one named building block — `converge` — that
captures the loop once, and then rebuilds the recipes that fit on top of it so the
duplication goes away. We keep every recipe's current behavior; we just stop
writing the loop five times.

**Technical statement.** Add a `converge` primitive to
`@flow-state-dev/orchestration/task-board` that composes an outer, judge-gated
`sequencer.loopBack` around a task board's drain block (`board.drain` — FIX-907's
spec, PR #819, renames `board.block` → `board.drain` and drops `board.block`; this
spec targets the new name and falls back to `board.block` only if it lands first),
parameterized by `(seed, board, judge, maxIterations, finalize)`, with a single
`Verdict` contract that subsumes the three termination dialects in the suite today;
then re-express
`planAndExecute`, `routedSpecialists`, and `parallelTasks` on it, prove behavior is
unchanged via the existing integration suite, and delete only `parallelTasks`'
bespoke body once it is a trivial config.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*

- **What we gain.** One named loop instead of three hand-wired ones. New looping
  behavior becomes config rather than a fresh sequencer, and the recipe that's pure
  boilerplate (`parallelTasks`) collapses to a few lines. Nothing changes for anyone
  using the recipes today.
- **How big.** Large, but mostly rewiring, not new logic. The loop itself is small. The
  bulk is (a) moving a few shared helpers down into orchestration so the primitive can
  reach them, and (b) proving each rebuilt recipe behaves identically to the original.
- **Where the complexity actually is.** Not the happy path — the edges where the three
  recipes quietly differ. Their stop conditions disagree (board-empty vs. an LLM "are we
  done?" vs. a fixed count), and unifying them into one `Verdict` without shifting any
  recipe's observable behavior is the delicate work. `routedSpecialists` is the outlier
  (it sidesteps the task board entirely), which is why it's an optional, parity-gated PR3.
- **The risk.** Almost entirely "did we preserve behavior?" — caught by re-expressing
  each recipe against its existing tests before deleting the old body. Little new surface
  area; the danger is a subtle parity slip, not a new feature going wrong.

**Deliverables:**

- **Orchestration (the primitive):**
  - Add `converge()` factory + `ConvergeConfig`/`Verdict` types + a small
    `mapToVerdict` helper in `packages/orchestration/src/task-board/converge.ts`;
    export from `task-board/index.ts`. (Judges are bring-your-own via the `judge`
    slot + `mapToVerdict`; converge does NOT ship per-dialect judge factories.)
  - **Move** (BP-034, not reimplement) `createApplyReplan` /
    `createCascadeSkipDependents` / the `planning-entry` factories from
    `@flow-state-dev/patterns` into orchestration, since orchestration can't import
    patterns and `converge` needs them for the `afterDrain`/`replanner` slots.
  - Emit a typed `converge` termination item via a **distinct component type**
    `<TaskPlan/>` doesn't consume (or one that merges the completed board-meta
    `counts`/`status`) — NOT the plain `task-board-meta` the renderer scans by
    `collectionId`, which it would clobber (§4.3).
- **Patterns (re-expression, behavior-preserving) — PR2:**
  - Re-express `parallelTasks` (`packages/patterns/src/parallelTasks/index.ts`) as a
    single-pass `converge` (inline always-done judge), then **delete** the loop body
    (~20–28 lines) once tests pass; `collectResults` stays as the `finalize`.
  - Re-express `planAndExecute` (`packages/patterns/src/plan-and-execute/index.ts`)
    as `converge`, passing its existing `createEvaluateProgress` as the `judge`
    (mapped via `mapToVerdict`) and wiring the `afterDrain` (cascade-skip) + `replanner`
    slots. Keep the public factory.
  - **(PR3, optional)** Re-express `routedSpecialists`
    (`packages/patterns/src/routedSpecialists/index.ts`) — **parity-gated stretch**: it
    bypasses `taskBoard` entirely, so folding it on requires a specialist-input
    adapter, re-homed snapshot/container emission, metadata threading, and a
    sequencer→request backing switch (see §5 step 7). Deferrable.
- **Docs:** new `apps/docs/docs/orchestration/converge.md` reference page + sidebar
  entry; cross-link and "re-expressed on converge" notes on the pattern pages
  and orchestration overview.
- **Tests:** integration parity scenarios in `packages/integration-tests/` proving each
  re-expressed pattern is behavior-identical; unit tests for `converge` (incl. the
  `maxIterations` drain-count and judge-error cases); a real-model goal check.

**Size:** **Large** — multi-package (orchestration + patterns + docs + integration
tests), >500 LOC. **FIX-910 "done" = PR1 + PR2**; PR3 is an optional follow-up unless
parity is cheap. Split: **PR1** the `converge` primitive + the lifted helpers + unit
tests + docs page; **PR2** re-express `parallelTasks` (delete the loop body) and
`planAndExecute` (keep factory) + parity scenarios (both clean); **PR3** re-express
`routedSpecialists` (the fiddly one — parity-gated, adapter work, deferrable).

## 2. Overview

Linear: [FIX-910](https://linear.app/fixpoint-labs/issue/FIX-910/rethink-patterns-as-config-driven-strategies-converge-primitive)

Most bespoke patterns encode the same shape — produce tasks, drain the board, ask a
judge whether we've reached the endstate, repeat. That shape is currently
hand-wired three incompatible ways. This spec names it once as `converge`, a
substrate primitive on the task board, and re-expresses the patterns that genuinely
fit it — keeping tested behavior by having the replacement in hand before deleting
anything (BP-038). Scope was deliberately narrowed (see §8): this spec builds the
primitive and the re-expression only. The `pattern:` → `strategy:` skill-frontmatter
rename and the crosswalk collapse are a **separate** follow-up.

## 3. Background & Research

### 3.1 How this problem is solved today (in this codebase)

The orchestration suite has **three parallel termination dialects** with no shared
contract (codebase map, `packages/orchestration` + `packages/patterns`):

| Dialect | Signal | Patterns using it |
| --- | --- | --- |
| **drain-to-empty** | `checkBoard` returns `{ shouldContinue, reason }` from the board's `onIdle` mode (`task-board/blocks/check-board.ts`, `createCheckBoard`) | `taskBoard`, `parallelTasks`, `eventActors`, `supervisor` (per-task) |
| **LLM-verdict** | outer `.loopBack(when: decision !== "complete")` over a generator's `{ decision }` | `planAndExecute` (`plan-and-execute/index.ts:757`), `routedSpecialists` (`{ done }` check `:517`, `loopBack` `:521`) |
| **fixed-count** | `.loopBack(when: round < max && !terminateWhen(ctx))` | `debate`, `round-robin` |

There is already a half-step toward unification: `taskLoopBack`
(`packages/orchestration/src/tasks/helpers/task-loop-back.ts`) packages the
canonical "drain until all tasks settled" predicate for `sequencer.loopBack`. Its
own module doc states the current stance this spec reverses: *"Loop shapes are
sequencer compositions, not codified primitives. This helper packages the canonical
… exit condition so patterns don't reinvent it."* Only `planAndExecute`'s outer
loop and the board's inner worker loop consume `.loopBack`; `routedSpecialists`,
`debate`, and `round-robin` each re-hand-roll it. Note `taskLoopBack` /
`defaultTaskLoopUntil` is itself currently **unused by any live call site** (only
re-exported and unit-tested) — so `converge` *promotes* a dead-ish helper into a
real primitive rather than consolidating existing call sites. The consolidation
value comes from the re-expression (§5), not from `taskLoopBack` today.

The canonical outer loop, verbatim, is `planAndExecute`
(`plan-and-execute/index.ts:735`):

```ts
.tap(stampOuterGoal)
.step(captureAndPlan)               // produce (initial plan)
.step(board.block)                  // drain            ← loopBack target
.tap(cascadeSkipDependents)
.step(evaluator)                    // judge → { decision }
.stepIf(d => d.decision === "replan" && !Array.isArray(d.tasks), replanner)
.stepIf(d => Array.isArray(d.tasks), applyReplan)   // produce-more (replan)
.map(d => ({ decision: d.decision ?? "continue" }))
.loopBack(board.block.name, { when: r => r.decision !== "complete", maxIterations })
.step(synthesize);                  // finalize
```

`routedSpecialists` is the same shape hand-rolled over a sequencer-backed
`TaskCollection` **without using `taskBoard` at all**
(`routedSpecialists/index.ts:509`): `.step(controller).stepIf(!done,
dispatch).step(checkLoop).loopBack(controller.name, { when: continue,
maxIterations })`.

Two judge schemas are already near-isomorphic —
`evaluatorVerdictSchema { decision: continue|replan|complete }` (plan-and-execute)
and `controllerOutputSchema { specialist, done, reasoning }` (routedSpecialists) —
plus supervisor's per-task `reviewerVerdictSchema { decision: approve|reject|…,
feedback }`. A single `Verdict` abstraction subsumes the first two (the third is a
different axis; see §3.4).

### 3.2 Industry practice (what to borrow)

Mature agent frameworks separate two orthogonal concerns and never conflate them:
the **"keep going?" decision** and the **guardrail**.

- **LangGraph** — `add_conditional_edges(node, should_continue)` (soft decision over
  accumulated state) + a separate hard `recursion_limit` that *throws*.
- **OpenAI Agents SDK** — terminates on typed final output, handoff, or `max_turns`
  (raises `MaxTurnsExceeded`). Termination is *typed*: a well-formed output of the
  expected schema is itself the exit signal.
- **AutoGen** — termination as first-class composable objects
  (`MaxMessageTermination(10) | TextMentionTermination("APPROVE")`), each carrying a
  reason. The cleanest precedent for config-driven stop-logic.
- **Anthropic, *Building Effective Agents*** — *evaluator-optimizer* (generate →
  evaluate against criteria → loop; "terminates when criteria met or iterations
  exhausted") and *orchestrator-workers* (dynamic subtask count). Our `converge`
  is the framework realization of evaluator-optimizer over a task board.

The 2026 "loop engineering" writeups rank exit conditions by strength —
**test-defined > diff/fixed-point > count-defined (drain-empty) > judge-defined
(LLM-as-judge, the *weakest*)** — and insist a loop that hits budget should **land,
not die**. Two facts we adopt directly: (a) at least one hard budget must be
non-optional so no config can hang; (b) termination should emit a *typed reason*,
not a bare boolean, to guard the judge-flapping / hallucinated-success failure
modes.

### 3.3 Why this approach (design chosen)

`converge` is an **outer sequencer loop around `board.block`**, exactly mirroring
the `planAndExecute` shape that already works — not a new execution engine. It lives
in `@flow-state-dev/orchestration` (below `patterns` in the layering `core →
orchestration → patterns`) so patterns can re-express onto it. It generalizes the
existing `taskLoopBack` helper rather than inventing a parallel mechanism — the
plain "compose/generalize, don't reinvent" instinct (not BP-029, which is
specifically about glue around *external* tools).

The termination surface takes the **unified `Verdict`** middle path between "keep
three dialects" and "full AutoGen condition algebra": one judge slot returning
`{ decision: "done" | "continue" | "replan"; reason; tasks? }`, plus a **mandatory
`maxIterations`** budget and a **typed termination item**. The composable
`.or()/.and()` condition algebra and cost/stall budgets are attractive but
speculative for v1 (BP-038) — deferred to §8 with the precedent recorded.

Alternatives considered:

| Approach | Verdict |
| --- | --- |
| `converge` as an outer `.loopBack` over `board.block`, unified `Verdict`, mandatory budget | **Chosen** — mirrors the proven `planAndExecute` shape; re-expresses cleanly; no new engine |
| New pattern in `@flow-state-dev/patterns` | Rejected — layering: patterns must re-express *onto* it, so it must live below them in orchestration |
| Full AutoGen-style composable termination-condition algebra (`.or()/.and()`, cost/stall budgets) in v1 | Rejected for v1 — speculative surface (BP-038); deferred as a follow-up with precedent noted |
| Keep the three dialects; just document the crosswalk | Rejected — the duplication (and the crosswalk it forces) is the problem, not the docs |
| Delete patterns first, rebuild on the primitive | Rejected — BP-038 requires the replacement in hand; re-express then delete only what becomes trivial |

### 3.4 Key Decisions & Ramifications (top 5)

1. **`converge` is a substrate primitive in orchestration, wrapping `board.block`
   as an outer loop — not a new pattern and not a new engine.** *Rejected:* adding
   it to `@flow-state-dev/patterns`. *Locks in:* the layering (`core → orchestration
   → patterns`) so patterns re-express onto it; reuse of the sequencer DSL's
   `.loopBack` (no bespoke loop runtime). *Rules out:* patterns importing it
   circularly — they can't, orchestration is below them, which is exactly why it has
   to live here.

2. **One `Verdict` contract subsumes the drain-empty and LLM-verdict dialects; the
   judge is a single seam.** `Verdict = { decision: "done" | "continue" | "replan";
   reason: string; tasks?: TaskInit[] }` (three-way — `replan`≠`continue`), plus a
   small `mapToVerdict` helper; judges are
   **bring-your-own** (a pattern passes its own evaluator/controller, mapped to a
   `Verdict`), NOT a per-dialect factory library on orchestration. *Rejected:* three
   separate dialects; shipping `drained()`/`evaluatorJudge()`/`controllerJudge()` as
   public API; and (for v1) a full condition algebra. *Ramification:*
   **supervisor is deliberately NOT re-expressed** — its judge is *per-task* inside
   each worker (a retry budget via `reviewer-check.ts` + `maxAttemptsPerTask`), a
   different axis than a board-level converge loop. The issue's thesis over-reaches
   in lumping supervisor with plan-and-execute; the code disproves it. supervisor
   stays as-is.

3. **`maxIterations` is mandatory and the loop emits a typed termination reason.**
   No `converge` config can produce a non-terminating loop (industry: budgets
   non-optional); the terminal board-meta item records which condition fired and the
   iteration count. *Rejected:* an optional cap and a bare boolean exit. *Locks in:*
   a safety default and a small, renderer-compatible observability surface (reuses
   the board-meta channel, no new item taxonomy). *Carries:* judges that hit the cap
   without a `"done"` verdict *land* (emit `reason: "max-iterations"`) rather than
   throw.

4. **Re-express, then delete only what becomes trivial (BP-038 with the replacement
   in hand).** `parallelTasks` → single-pass `converge` (`maxIterations: 1`, inline
   always-done judge); the board-wiring + terminal drain-loop portion it supersedes
   is **~20–28 lines** (not the whole file — `collectResults` stays as the `finalize`,
   and the config destructure/defaults/warning plumbing remains). `planAndExecute`
   and `routedSpecialists` → re-expressed internally but keep their public factories
   (rich config, defaults, docs). *Rejected:* deleting patterns before the primitive
   exists, or re-expressing all patterns (debate/round-robin don't use `taskBoard`).
   *Ramification:* `routedSpecialists` stops hand-rolling a loop and bypassing
   `taskBoard` — a deepening win, but the highest-risk re-expression: it passes
   `{specialist,done,reasoning}` as the specialist's input via a `keyedRouter` and
   emits its own snapshot/container items, none of which the board provides. It is
   parity-gated and deferrable (PR3, §5 step 7), not assumed free.

5. **Coordinate with FIX-907 / FIX-908; no hard blocker, but the drain-factory
   boundary needs a decision.** `converge` mounts the board's drain block via its
   `board` slot. *FIX-907 (spec PR #819 — now **closed unmerged**, i.e. its spec is
   settled and implementation may be underway; `board.block` is still the live name on
   `main`, so re-verify FIX-907's implementation status before PR1)* renames
   `board.block` → `board.drain` and **explicitly hands the *configurable* drain
   factory (`max`/`snapshot`/`filter`) to FIX-910**, on the reasoning that converge's
   config schema should shape it. This spec **declines that expansion** (per the
   "primitive only" scope + BP-038): converge is the *outer* loop and does not need
   *inner*-drain knobs; it mounts `board.drain` as-is. The inner-drain factory stays
   a separate follow-up, forward-compatible because converge's `board` slot already
   accepts whatever drain the board exposes (see §8, §10). *FIX-908 (PR #817)* flips
   the default backing to `request`, which **satisfies converge's request-backing
   precondition by default** — a converge board is request-backed unless a caller
   explicitly opts into `sequencer`. *Rejected:* blocking 910 until 907/908 land, and
   absorbing the drain factory. *Locks in:* 910 proceeds against current `main`, with
   a one-line mount-name reconciliation depending on merge order.

## 4. Technical Design

### 4.1 Architecture

```
@flow-state-dev/orchestration/task-board
  converge.ts   ← NEW: converge() factory + ConvergeConfig + Verdict + mapToVerdict
  index.ts      ← export converge, Verdict, mapToVerdict
  apply-replan.ts, cascade-skip-dependents.ts, planning-entry.ts
                ← MOVED here from @flow-state-dev/patterns (orchestration can't import patterns)
  (generalizes tasks/helpers/task-loop-back.ts)

@flow-state-dev/patterns   (re-express onto converge; re-import the moved helpers)
  parallelTasks/index.ts      → converge({ maxIterations: 1, judge: () => ({decision:"done", reason:"converged"}),
                                  finalize: <collectResults → configured combiner> }); delete loop body
  plan-and-execute/index.ts   → converge({ afterDrain: cascadeSkipDependents,
                                  judge: createEvaluateProgress (→ mapToVerdict), replanner, ... })
  routedSpecialists/index.ts  → converge({ judge: controller (→ mapToVerdict) })   // PR3, optional
```

`converge` sits at the same altitude as `taskBoard` (both in
`@flow-state-dev/orchestration/task-board`) and consumes a `TaskBoardHandle`.

### 4.2 API surface

```ts
// packages/orchestration/src/task-board/converge.ts

/** A judge's verdict after one drain. Three-way (mirrors P&E's evaluator), because
 *  `replan` and `continue` must NOT collapse: `continue` re-drains existing in-flight
 *  work with no new tasks; `replan` adds work (inline `tasks`, or via the `replanner`
 *  slot when absent). Collapsing them would either fire the replanner on ordinary
 *  continues or skip it on replans. */
export type Verdict =
  | { decision: "done"; reason: string }
  | { decision: "continue"; reason: string }
  | { decision: "replan"; reason: string; tasks?: TaskInit[] };

/** Judge slot. Crucially this is NOT just a generator wrapper — the real
 *  plan-and-execute evaluator (`createEvaluateProgress`) is a *sub-sequencer*
 *  (iteration preflight, optional LLM, `emitReplanningMeta`). So the slot accepts a
 *  full block or sub-sequencer whose output maps to a `Verdict`, or an inline fn.
 *  Patterns bring their own judge; converge does not ship per-dialect factories
 *  (see the `mapToVerdict` note below). */
/** Normalized judge input — the SAME shape whether the judge is a block,
 *  sub-sequencer, or inline fn (so a judge is expressible either way and the
 *  "identical input" parity test holds). converge builds it before `judgeStep`. */
export interface JudgeInput { collection: TaskCollectionRef; drainResult: unknown }
export type JudgeSlot =
  | BlockDefinition
  | SequencerDefinition<any, any>
  | ((input: JudgeInput, ctx: BlockContext) => Verdict | Promise<Verdict>);

export interface ConvergeConfig {
  name: string;
  /** Input schema for converge's **outer** sequencer — forwarded verbatim so the
   *  re-expressed patterns keep their PUBLIC block metadata. `parallelTasks` /
   *  `planAndExecute` are top-level sequencers today declaring
   *  `parallelTasksInputSchema` / `planAndExecuteInputSchema`; a bare `converge(...)`
   *  with no schema would silently swap that to `z.unknown()` and change any
   *  action/tool schema generated from the pattern (valid-input tests still pass
   *  because a child seed block validates later — so the drift is invisible to them).
   *  Omit for `z.unknown()`. */
  inputSchema?: ZodTypeAny;
  /** The drain substrate. converge mounts the board's drain block —
   *  `board.drain` after FIX-907 (PR #819) lands, `board.block` if converge lands
   *  first (the FIX-907 rename then sweeps this mount). */
  board: TaskBoardHandle;
  /** Extra state fields merged into converge's own sequencer state. **Required for
   *  P&E parity**: the re-expressed seed/evaluator/finalize blocks read and patch
   *  `ctx.sequencer!.state.goal` / `.status` (`stampOuterGoal`, `createBuildPlanOutput`,
   *  the evaluator), but converge's internal state only carries `iteration` /
   *  `lastVerdict` / collection id. Without this hook the nearest `ctx.sequencer`
   *  inside those blocks is converge's and lacks `goal`/`status`, so P&E would
   *  synthesize empty-goal outputs and lose replan context. P&E passes
   *  `planAndExecuteStateSchema`; converge merges it. converge's OWN fields are
   *  `__`-namespaced (`__convergeDrains`/`__convergeVerdict`), so a caller schema that
   *  declares `iteration` (as P&E's does) never collides — no caller burden. */
  stateSchema?: ZodTypeAny;
  /** Produces the initial tasks (the "plan"). Optional if tasks are pre-seeded.
   *  Accepts a SequencerDefinition too, because the patterns' seeds are multi-step —
   *  parallelTasks (planner + seedTasks), and plan-and-execute (its **optional
   *  `synthesizeGoalStep`** for `synthesizeGoal: true`, then `stampOuterGoal`, then
   *  `captureAndPlan`). Goal synthesis MUST run inside the seed, before stamp/capture,
   *  or the planner plans against the un-rewritten goal. A single-block slot would
   *  force every caller to pre-wrap.
   *  **The seed writes tasks via the board accessor** (`ctx.cap.<board>.addTask`), so it
   *  runs before `.step(board.block)` (§4.3) and — like the other helpers — **declares
   *  `uses: [board.capability]` itself**. That write only lands if the collection exists
   *  before the drain, i.e. **`seed` REQUIRES request/resource backing**: a
   *  `sequencer`-backed board's collection is created *by* the drain, so a pre-drain seed
   *  can't populate it — this holds even for `maxIterations: 1` (the single-pass case is
   *  otherwise fine only when tasks are pre-seeded into a request-backed collection). */
  seed?: BlockDefinition | SequencerDefinition<any, any>;
  /** Runs as a `.tap` immediately AFTER each drain, before the judge — the seam
   *  plan-and-execute uses for `cascadeSkipDependents` (a pending task whose dep
   *  errored is cascade-skipped so the judge sees settled state). Without this slot,
   *  P&E parity is impossible. Lifted into orchestration (see §4.3 layering note). */
  afterDrain?: BlockDefinition;
  /** Evaluated after `afterDrain` → `Verdict` (see JudgeSlot). MANDATORY. */
  judge: JudgeSlot;
  /** Runs on a `replan` verdict with no pre-baked `tasks` (mirrors P&E's `replanner`
   *  stepIf, `index.ts:744-749`); its emitted `tasks` then flow through the add step. */
  replanner?: BlockDefinition;
  /** Forwarded to the lifted `createApplyReplan` so a replan task that omits its own
   *  value inherits the caller's defaults — WITHOUT these, P&E's custom
   *  `maxAttemptsPerTask` / `taskContext` are lost after re-expression (the board
   *  handle exposes neither). P&E populates them from its own config. */
  maxAttemptsPerTask?: number;
  taskContext?: TaskContextSlot;
  /** MANDATORY hard backstop (a **positive integer**, validated at construction — a
   *  `0`/negative value throws, since passing `maxIterations - 1 = -1` to `loopBack`
   *  would make its jump counter never reach the cap and leave an always-continue loop
   *  unbounded). Threaded to `loopBack` as `maxIterations - 1` jumps → N drains. A judge
   *  that self-caps (P&E's evaluator preflight skips its own LLM at
   *  `iteration >= maxIterations`) KEEPS that preflight and is constructed with the SAME
   *  N, so its cap and the loopBack backstop terminate on the same drain — no divergence,
   *  and the LLM-call pattern is identical to today's P&E. Judges with no self-cap rely
   *  on the loopBack backstop plus the post-judge cap coercion. */
  maxIterations: number;
  /** Synthesizer over the settled board — converge **projects the board before invoking
   *  it**, so `finalize`'s input is the settled-board projection (tasks/results), NOT the
   *  exit verdict. Omit to return that raw projection.
   *  NOTE this is NOT the same as plan-and-execute's `synthesizer: false`, which
   *  still runs `createBuildPlanOutput` and returns the legacy
   *  `{ goal, status, tasks, completedSteps, totalSteps }` shape — that maps onto a
   *  build-output `finalize` block, not an omitted `finalize`. Omitting `finalize`
   *  is the genuinely-no-synthesis case (raw projection). */
  finalize?: BlockDefinition;
  /** Forwarded to the outer sequencer's error posture. Default "skip". */
  onError?: "skip" | "fail";
}

export function converge(config: ConvergeConfig): SequencerDefinition<any, any>;
```

**Judges are bring-your-own, not a per-dialect factory library.** Orchestration ships
the `Verdict` type and one small pure helper, `mapToVerdict(output, mapping)`, that
adapts an existing decision shape to a `Verdict`. **It injects a default `reason`**
(`converged`/`continue`/`replan`) when the source omits one — the real P&E evaluator
returns decision-only objects like `{ decision: "complete" }`, and the parallelTasks
inline judge is `() => ({ decision: "done", reason: "converged" })`; without a default
reason, `Verdict`'s required `reason` would make every normal verdict "malformed" and
terminate as `judge-error` (or fail under `onError: "fail"`). It does **not** ship
`drained()`/`evaluatorJudge()`/`controllerJudge()` as public API — those were thin
schema-mappers that would grow orchestration one entry per pattern dialect (and
`drained()` is near-tautological as an outer judge, since the board's inner loop
already drains to empty before the drain block returns). Instead each pattern maps
its own verdict:

- **parallelTasks** — a one-line inline judge returning `{ decision: "done" }` after
  the single drain (with `maxIterations: 1`). No `drained()` needed.
- **plan-and-execute** — passes its existing `createEvaluateProgress` sub-sequencer as
  the `judge`, mapping `{ decision: continue|replan|complete }` → `Verdict` via
  `mapToVerdict` 1:1 (`complete`→done; `replan`+tasks→`replan`-with-tasks; `replan`
  without tasks→`replan` (the `replanner` slot then runs); `continue`→`continue`).
  **The reason must distinguish the self-cap, keyed on the iteration count** (not a
  reasoning string): **both** evaluator variants force-`complete` at
  `iteration >= maxIterations` — the replanning preflight skips the LLM
  (`evaluate-progress.ts:250-257`), and the non-replanning `createTaskEvaluator` returns a
  **bare** `{ complete }` before even checking for work (`:122-123`). So the adapter maps
  a `complete` produced **at** `iteration >= maxIterations` → `{ done, "max-iterations" }`
  and a `complete` **before** the cap → `{ done, "converged" }`, reading `iteration` from
  state (both evaluators patch it). Keying only on the LLM preflight's `reasoning` string
  would mislabel the no-LLM path's budget-fired `complete` (which carries no reasoning) as
  `converged` — converge keeps every `done` verdict's reason and cannot tell a cap-origin
  `done` from a genuine one (§4.3).
- **routedSpecialists** — maps its controller `{ done, specialist }` → `Verdict`
  (done→done; else `replan` with the picked specialist as one task).

### 4.3 Data flow (how `converge` assembles)

```ts
sequencer({ name, stateSchema: mergedStateSchema, uses: [board.capability] })  // state: convergeStateSchema (namespaced) ⊕ config.stateSchema. NOTE ctx.cap is per-block: each helper that reads ctx.cap.<board> declares uses:[board.capability] ITSELF (see note) — the sequencer's uses does NOT flow to sibling steps
  .step(seed ?? noopSeed)                         // produce initial tasks (block or sub-sequencer)
  .step(board.block)                              // drain              ← loopBack target
  .tap(incrementDrainCount)                       // ++state.__convergeDrains ON EVERY drain (see note) — the count source of truth
  .tapIf(afterDrain !== undefined, afterDrain)    // post-drain hook (e.g. cascadeSkipDependents) — MUTATES the collection, BEFORE the judge
  .tap(stashDrainProjection)                      // state.__convergeDrainResult = collection projection AFTER afterDrain (in-subtree read → post-cascade), for projectBoard (see note)
  .step(judgeStep)                                // sub-sequencer: adapts drain output → JudgeInput{collection,drainResult}, runs the JudgeSlot (rescue-wrapped) → Verdict. ALWAYS runs, INCLUDING the final allowed drain — converge adds NO outer cap skip (see note)
  .map(v => atCap() && v.decision !== "done" ? { decision: "done", reason: "max-iterations" } : v)  // CAP COERCION: at the last allowed drain (drainCount() >= maxIterations) coerce ONLY a NON-done verdict → {done,"max-iterations"} (drops the un-drainable replan). A `done` on the final drain is KEPT → "converged". Runs BEFORE replan/apply.
  .map(rejectTasklessReplanWithoutReplanner)      // replan with no tasks array AND no replanner configured → onError (config/judge bug), not a silent re-drain
  .stepIf(v => v.decision === "replan" && !Array.isArray(v.tasks) && replanner, replanner) // replan with NO tasks ARRAY → replanner emits {tasks}
  .stepIf(v => Array.isArray(v.tasks), applyReplanTasks)  // add — keyed on ARRAY PRESENCE (incl. []), matching P&E's `Array.isArray` idiom; empty = no-op
  .map(v => ({ decision: v.decision ?? "continue", reason: v.reason }))  // continue AND replan both re-drain; only "done" exits
  .loopBack(board.block.name, {
    when: v => v.decision !== "done",             // done exits; continue AND replan both loop
    maxIterations: maxIterations - 1,             // loopBack counts JUMPS; drain runs once before the 1st jump.
  })                                              //   config maxIterations = total drains → jumps = N-1 (see note)
  .tap(emitFromDrainCount)                        // terminal reason + iteration read from state.__convergeDrains
  .tap(emitConvergeTermination)                   // typed board-meta item: reason + iteration count
  .map(projectBoard)                              // verdict → settled-board projection (carried drain output; see note): finalize's INPUT is the BOARD, not the verdict
  .step(finalize ?? passThrough);                 // provided finalize synthesizes OVER the projection; omitted → passThrough returns it
```

**Rescue scope (correctness).** A chain-level `.rescue()` after `judgeStep` would
catch failures from *every prior step* — a real `seed`/`board.block` failure (e.g. a
worker board with `onError: "fail"`) would be silently converted into a successful
`judge-error` termination. So the judge-error rescue is **internal to `judgeStep`**:
`judgeStep` is itself a small sub-sequencer wrapping the `JudgeSlot` with a
block-level `.rescue` that maps a *judge* throw to `Verdict{ done, reason:
"judge-error" }` under `onError: "skip"` (omitted under `"fail"`). Seed and board
failures propagate as before.

The terminal `reason` at `emitConvergeTermination` **preserves the exit verdict's own
`reason`** rather than flattening every `done` to `"converged"`: a normal judge `done`
carries `"converged"`, but a rescued judge failure is a `done` carrying
`"judge-error"` — so the emitted item must report `"judge-error"`, not `"converged"`
(otherwise the typed taxonomy and the `judge-throws→judge-error` test are defeated). A
cap exit also arrives as a `done` verdict, but one the cap guards stamped
`"max-iterations"` (see the cap-handling note below). So every exit is a `done` verdict
and `emitConvergeTermination` uniformly reports `verdict.reason` — `"converged"`,
`"judge-error"`, or `"max-iterations"`.

- **A `replan` that produces no work is a bug, not a re-drain.** If a judge returns
  `{ decision: "replan" }` with no `tasks` array and **no `replanner` is configured**,
  both conditional steps skip and the loop would just re-drain the settled board until
  the cap — hiding a bad judge/config. `rejectTasklessReplanWithoutReplanner` routes it
  through the `onError` path instead (invalid verdict). (A `replan` with `tasks: []`
  and no replanner is a caller-intended no-op and is allowed; the guard fires only when
  there is neither a tasks array nor a replanner to produce one.)
- **The judge always runs; the cap only coerces a non-`done` verdict.** Converge adds
  **no outer pre-judge skip**. Judges that must stop making LLM calls at the cap own
  that themselves: P&E passes its full `createEvaluateProgress`, whose preflight
  increments `iteration` and **skips the LLM** at `iteration >= maxIterations`
  (`evaluate-progress.ts:250-258`) *inside* the judge — so calling that judge on the
  final drain makes no extra model call and emits no `replanning` meta (decision is
  `complete`, not `replan`). An earlier revision wrapped an outer pre-judge skip around
  the judge to "preserve call-count parity," but that was solving a non-problem (the
  judge self-caps) and it broke the boundary case: a legitimate `done` on the Nth
  allowed drain was reported as `max-iterations` because the judge never ran. So the
  only cap handling is a single post-judge coercion:
  - `atCap() && decision !== "done" → { done, "max-iterations" }` (`atCap()` is
    `drainCount() >= maxIterations`). It runs **before** the replan/apply steps, so a
    `replan`/`continue` on the final drain terminates cleanly and the un-drainable tasks
    are dropped (no orphaned `pending` in the projection).
  - A `done` on the final drain is **kept** — `parallelTasks` (`maxIterations: 1`, judge
    on drain 1) reports `converged`, and `continue×2 → done` on drain N reports
    `converged`, not `max-iterations`.
  - A `done` verdict's **reason is authoritative**: converge keeps it and **cannot tell a
    cap-origin `done`** (a self-capping judge whose budget fired) **from a genuine one**.
    So a self-capping judge must emit `reason: "max-iterations"` itself when its budget
    fires (P&E's mapping does — §4.2); converge only *standardizes* the reason for the
    non-`done` verdicts it coerces.
  The loopBack (`maxIterations: maxIterations - 1` jumps → N drains) is the hard
  backstop for judges with no self-cap; the coercion stamps the terminal reason and
  prevents the final-drain replan from adding work that can never drain.
- **Declare the board capability on each helper block that reads it — not just the outer
  sequencer.** `ctx.cap.<board>` is populated **per block** from *that block's own*
  declared capabilities: `executeBlock` sets `ctx.cap = buildCapObject(theBlock, …)` from
  the block's `__resolvedCapabilities` (`executeBlock.ts:272-279`), and the core path
  builds accessors only for "the capabilities THIS block declares"
  (`build-block.ts:201-217`). Declaring `uses: [board.capability]` on the converge
  sequencer alone does **not** flow the accessor into sibling helper blocks
  (`applyReplanTasks`, `cascadeSkipDependents`, `stashDrainProjection`, and `afterDrain`
  if it reads the board) — each sees a fresh `cap: {}` otherwise. So converge passes
  `config.board.capability` into the lifted helper factories and each helper declares it
  in its own `uses`. (Keep it on the sequencer too where the sequencer body reads it; the
  build is skip-by-name/idempotent.)
- **`replan` vs `continue` are distinct (must not collapse).** `Verdict` is three-way
  (`done`/`continue`/`replan`). `continue` re-drains existing in-flight work with no
  new tasks; `replan` produces new work — inline `tasks`, or via the `replanner` slot
  when absent. The replanner emits `{ tasks }` (carrying `decision`/`reason` through),
  and the **add step is keyed on task PRESENCE** (`Array.isArray(v.tasks)`, P&E's
  `applyReplan` idiom) so it catches both the inline and replanner-produced cases.
  Keying the replanner or the add on `continue` would fire it for ordinary continues;
  keying only on inline `tasks` would drop the replan-without-tasks path (re-drain to
  the cap). This is the exact P&E `stepIf(replan && !tasks, replanner).stepIf(tasks,
  applyReplan)` shape (`index.ts:739-749`).
- **`finalize` receives the settled-board projection, not the verdict.** After the loop
  the chain value is `{ decision, reason }` (the exit verdict), NOT tasks — so converge
  inserts a `.map(projectBoard)` that turns it into the board's task/result projection
  **before** `finalize` runs. A provided `finalize` then synthesizes over the projection
  (honoring its "synthesizer over the settled board" contract); an omitted `finalize`
  returns that projection directly (`passThrough`). The built-in finalizers (`synthesize`,
  `collectResults`) ignore their input and re-read the collection, so feeding them the
  projection instead of the verdict is behavior-neutral — parity holds. `projectBoard`
  reads the settled board from **`state.__convergeDrainResult`** (§4.4 — the
  `stashDrainProjection` tap captures it **after `afterDrain`** each iteration, so the
  projection reflects the post-cascade board the judge saw, not the pre-mutation drain
  output; by finalize the chain value is the `Verdict`) rather than re-resolving the board
  capability from a sibling step —
  `ctx.getTarget(boardName)` is undefined there and a **sequencer-backed** board's
  capability throws (`capability.ts:238-243`). Where the carried output isn't sufficient,
  the projection step **requires request/resource backing** (the re-enterable case already
  does). Documented as a precondition until the handle exposes a parent-safe accessor (§11).
- **Post-drain hook is a real slot.** `planAndExecute` runs
  `.tap(cascadeSkipDependents)` after every drain (`index.ts:739`); the `afterDrain`
  slot carries it. Without it a failed-prerequisite plan leaves dependents pending.
- **Layering: LIFT, don't reimplement.** `applyReplanTasks`, the `afterDrain`
  cascade, and the seed/replan helpers currently live in
  `packages/patterns/.../{apply-replan,cascade-skip-dependents,planning-entry}.ts`.
  Orchestration **cannot import patterns**, so PR1 **moves** `createApplyReplan` /
  `createCascadeSkipDependents` (and the `planning-entry` factories they need) into
  `@flow-state-dev/orchestration/task-board`; patterns re-import them from there. This
  is a move refactor (BP-034), not a duplicate implementation.
- **Drain count is converge's OWN state, incremented per drain (not read from
  loopBack).** `sequencer.loopBack` keeps its jump count in internal runtime, not on
  `BlockContext`, so a post-loop tap cannot read it — and an inline judge that patches
  no state wouldn't record anything either. So converge increments
  `state.__convergeDrains` in an `incrementDrainCount` tap right after **every** drain;
  the terminal item and the drain-count tests read that field. The `maxIterations`
  off-by-one is handled at the loop cap: `loopBack` counts *jumps* and the drain runs
  once before the first jump, so converge passes `maxIterations - 1` to `loopBack`
  while its own per-drain counter records the true total. Unit-tested: `maxIterations:
  2` performs exactly 2 drains and reports `2`.
- **converge's internal state fields are namespaced** (`__convergeDrains`,
  `__convergeVerdict`, `__convergeDrainResult`) so merging **any** caller `stateSchema` — including P&E's, which
  already declares its own `iteration` that `createEvaluateProgress` patches — never
  collides. converge does NOT reuse the bare name `iteration`; the caller keeps sole
  ownership of its fields.
- **converge requires re-enterable backing (request / resource-factory); sequencer
  backing is unsupported for the loop.** `TaskBoardSequencerCollectionSpec` is
  *single-invocation* — a sequencer-backed board loses its `tasks` slot between
  `board.block` calls, so replanned tasks can't survive to the next drain. converge
  therefore **requires request- (or resource-factory-) backed storage** whenever
  `maxIterations > 1`. **It needs an explicit detection mechanism** — relying on "the
  second drain throws" does NOT work: a sequencer-backed collection whose slot is
  absent returns `{}` from `readTasks()` (`sequencer-backed.ts:71-76`), so a re-entry
  just silently drains an empty board and lands at the cap. Two options, decided in
  §11: (a) **construction-time assert** once FIX-908 exposes `backing`/`stateKey` on
  the handle (preferred); (b) a **converge sentinel** — seed writes a marker the drain
  shouldn't consume, and converge throws before the second drain if the marker didn't
  survive. The spec requires one of these, not silent no-progress. Single-pass
  (`maxIterations: 1`, parallelTasks) has no re-entry and is unaffected.
- **Both lifted helpers use the board's OWN backing-aware accessor — never a
  reconstructed request ref.** `createApplyReplan` AND `createCascadeSkipDependents`
  currently reconstruct a request-backed collection from `name`; lifted as-is they'd
  read/write the wrong collection under a resource-factory-backed board (cascade would
  leave failed-dep dependents pending; replans would land in the wrong place). The
  lift must route both through the **board handle's own accessor** (post-FIX-908
  `board.capability` / `ctx.cap.<name>`; today the board's resolved `collectionId`), so
  the hook, the add, and the drain all touch one collection.
- **`applyReplanTasks` is the *full* lifted `createApplyReplan`, not a bare add**, and
  needs its inputs: it preserves **id deconfliction** (a repeated evaluator task id
  must not reject/overwrite existing work) and stamps **`maxAttemptsPerTask` /
  `taskContext`** on tasks that omit them. Those defaults have no source on the board
  handle, so they are **forwarded via `ConvergeConfig.maxAttemptsPerTask` /
  `taskContext`** (§4.2); P&E populates them from its own config so retry behavior is
  unchanged after re-expression.
- **Judge input is normalized across forms.** An inline `JudgeSlot` fn receives the
  `TaskCollectionRef`; a block/sub-sequencer judge mounted with `.step()` would
  otherwise receive the *drain output* (a board projection), not the ref — different
  contract. converge inserts a `.map` before `judgeStep` that resolves and passes the
  collection ref (plus the drain result) uniformly, so both judge forms see the same
  documented input. P&E passes its `createEvaluateProgress` sub-sequencer here, its
  output mapped by `mapToVerdict`; its inner iteration preflight cap is **kept** and
  constructed with the same `maxIterations` converge uses, so the self-cap and the
  loopBack backstop terminate on the same drain and the LLM-call pattern is unchanged
  (§4.2). (BP-011: an inline fn is lifted into a `handler`, no `block.run()`.)
- `emitConvergeTermination` emits via `ctx.emit.component(...)` **directly** (the
  mechanism `evaluate-progress.ts` / `planning-entry.ts` use) — NOT
  `createBoardMetaActive/Completed`. **It must NOT reuse the `task-board-meta`
  component for this collection.** `extractTaskPlanState` reverse-scans for the latest
  `task-board-meta` whose `data.collectionId` matches and **ignores the item key**
  (`task-plan-state.ts:423-429`), so a *distinct key* alone doesn't help — a terminal
  `task-board-meta` for the same `collectionId` still becomes the renderer's latest
  board snapshot and drops the completed `counts`/`status`. Two acceptable options:
  (a) emit a **distinct component type** that `<TaskPlan/>` does not consume, or
  (b) **merge the full completed board-meta fields** (`counts`/`status`) onto the
  terminal item so it doesn't lose the snapshot. Only then is it genuinely additive
  (§7 asserts the pre-existing item stream plus this one non-clobbering item).

### 4.4 State

`convergeStateSchema` carries **namespaced** internal fields — `__convergeDrains`
(`z.number().default(0)`, the per-drain counter), `__convergeVerdict`
(`.nullable().default(null)`), and `__convergeDrainResult`
(`.nullable().default(null)`, the latest drain's settled output) — plus the collection
id, then **merges `config.stateSchema`** so a caller's fields join the same sequencer
state. `__convergeDrainResult` is stashed by a `stashDrainProjection` tap that runs
**after `afterDrain`** — so it captures the board *post*-cascade (the same state the judge
sees), not the pre-mutation drain output — and is what `projectBoard` reads at finalize
time: by then the chain value is the exit `Verdict`, and a sequencer-backed board's
capability can't be re-resolved from a sibling step (§4.3), so the carried post-cascade
projection, not a re-read, is the projection source. The stash reads the collection
in-subtree (where the board capability *does* resolve), unlike the sibling finalize step. The `__`
prefix means converge never claims a bare name like `iteration`, so merging P&E's
schema (which already owns `iteration`, patched by `createEvaluateProgress`) can't
collide — the caller keeps sole ownership of its fields, and this is what lets P&E's
re-expressed blocks read/patch `goal`/`status` on the nearest `ctx.sequencer`. It does
**not** own task state — that lives in the board's request-backed `TaskCollection`
(`ctx.request` namespaced by `collectionId`), which is why tasks added by
`applyReplanTasks` persist across the `loopBack`.

### 4.5 Error handling

| Case | Behavior |
| --- | --- |
| Judge throws | `onError: "skip"` (default): the **judgeStep-internal** rescue maps it to `Verdict{ done, reason: "judge-error" }`; `"fail"` propagates. The rescue is scoped to the judge only, so a `seed`/`board.block` failure is NOT swallowed as a judge-error. |
| `maxIterations` reached without `"done"` | Loop **lands** (does not throw): emits terminal item `reason: "max-iterations"`; `finalize` runs over whatever settled. |
| `seed` produces no tasks (parallelTasks empty plan) | First drain is a no-op; the inline `{ decision: "done" }` judge terminates immediately; `finalize` runs on an empty board (matches `parallelTasks` empty-plan behavior today). |
| Inline judge returns a malformed `Verdict` | Zod-validated at the `judgeStep` boundary; invalid → treated as `onError`. |
| `finalize` omitted | converge's `.map(projectBoard)` turns the exit verdict into the board's task/result projection and `passThrough` returns it (a provided `finalize` synthesizes over that same projection — §4.3). This is NOT `planAndExecute({ synthesizer: false })`, which returns the legacy `{ goal, status, tasks, … }` build-output shape — that re-expresses as a `createBuildPlanOutput` `finalize` block. |
| Sequencer-backed board with `maxIterations > 1` | **Unsupported — rejected via an explicit check** (construction-time backing assert once FIX-908 exposes it, or a converge sentinel). NOT left to "the 2nd drain throws" — a lost sequencer slot returns `{}` and would silently spin to the cap (§4.3, §11). |
| Sequencer-backed board, single-pass, **any `finalize`** | The pre-`finalize` `.map(projectBoard)` runs for both provided and omitted `finalize`, and can't resolve a sequencer board's capability from a sibling step (`capability.ts:238-243`). Works only via the carried drain output; otherwise requires request/resource backing (§4.3). A `finalize` that re-reads the board itself (like the built-ins) is unaffected. |
| Sequencer-backed board **with a `seed`** (even `maxIterations: 1`) | **Unsupported** — the seed writes via `ctx.cap.<board>.addTask` before the drain, but a sequencer-backed collection is created *by* the drain, so the pre-drain write has nowhere to land. `seed` requires request/resource backing (§4.2). A single-pass sequencer board is fine only with tasks pre-seeded into a request-backed collection (no `seed` slot). |
| Custom `evaluator` (no built-in iteration cap), P&E budget | **Deliberate normalization** (not a bug): today a custom evaluator gets `maxIterations + 1` drains (loopBack's jump cap binds) while the default evaluator gets exactly `maxIterations` (its preflight binds first). Re-expressed on converge, `maxIterations` means *total drains* uniformly, so the custom-evaluator path is `maxIterations` drains — one fewer. Documented as the single intentional behavior delta (§8), with a parity test asserting the new count. |
| `maxIterations: 0` or negative | **Rejected at construction** (throws) — a non-positive budget would pass `-1` to `loopBack` and leave an always-continue loop unbounded. Must be a positive integer. |
| Board configured with idless `initialTasks`, `maxIterations > 1` | The board's own seed step re-runs on every re-entry, and `createSeedCollection` only dedups `initialTasks` with **stable ids** — idless ones get re-added each drain, inflating counts/results. converge forbids this — but the current `TaskBoardHandle` (`{ block, collectionId, capability }`) exposes no seed metadata, so the guard needs the **same handle-metadata path as the backing check**: expose seed info on the handle (FIX-908-adjacent), or move the validation into `taskBoard`. Until then it is a **documented caller precondition** (use stable ids or an external one-time `seed`). See §11. |

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| Judge says `done` on iteration 1 | Single drain, `finalize` runs, terminal `reason: "converged"`. |
| Judge never says `done` | Lands at `maxIterations`, `reason: "max-iterations"`, `finalize` over settled board (land-not-die). |
| `continue` verdict | Re-drain the existing board (no new tasks) — a "wait for in-flight" loop; still bounded by `maxIterations`. |
| `replan` verdict (inline `tasks` or via `replanner`) | Tasks added via the board's own collection accessor (lifted `createApplyReplan`, with id-deconfliction / forwarded `taskContext` / `maxAttemptsPerTask` preserved) before re-drain. |
| A task added mid-drain by a worker | Next drain picks it up (live board semantics preserved — the board's default live behavior; snapshot is FIX-907's opt-in). |
| Board configured `sequencer`-backed, `maxIterations > 1` | **Unsupported, fails loudly** — sequencer collections are single-invocation and don't survive re-entry (§4.3). Single-pass (`maxIterations: 1`) sequencer boards are fine **only without a `seed`** (a `seed` needs request/resource backing — §4.2/§6). |
| Evaluator repeats an existing task id on replan | Deconflicted by the lifted `createApplyReplan` (not rejected/overwritten) — parity with today's `applyReplan`. |
| `maxIterations: N` with a judge that always continues | Exactly `N` drains (converge passes `N-1` to `loopBack`, whose cap counts jumps) — the terminal iteration count is the true drain count. |
| Inline judge vs block judge | Both supported; inline lifted into a `handler` (BP-011: no `block.run()` inside `execute`). |
| `finalize` omitted | converge's `.map(projectBoard)` yields the board's projection and `passThrough` returns it (provided `finalize` synthesizes over the same projection). This is NOT `synthesizer: false` — that case re-expresses as a `createBuildPlanOutput` `finalize` block (legacy `{ goal, status, tasks, … }` shape). |
| Multi-step seed (planner + seedTasks) | `seed` accepts a `SequencerDefinition`, so no caller pre-wrapping needed. |
| Re-expressed pattern changes item order | Caught by PR2/PR3 parity scenarios — this is the acceptance gate for "behavior preserved". |

**Error taxonomy:** `judge-error` (retryable per `onError`), `max-iterations`
(non-error terminal — lands), malformed-verdict (validation, treated as
`onError`). None of these throw under the default `onError: "skip"`.

## 7. Testing Strategy

**Goal.** A user can express a judge-gated "keep working until done" loop over a
task board with one primitive, and the built-in patterns re-expressed on it behave
exactly as before. The observable outcome: `planAndExecute`, `routedSpecialists`,
and `parallelTasks` produce the same items, final outputs, and iteration behavior
after the refactor as before it.

**Goal check (real model, non-CI).** A `goals/converge/replans-until-done/run.mts`
(per `goals/README.md`) that runs a real `converge` with an LLM evaluator judge
(mapped to a `Verdict`) against a real model on a task that requires one replan (e.g.
"research X, then — if the
first pass missed a sub-topic — research that too"), and prints PASS when the loop
does ≥2 iterations and terminates with `reason: "converged"` (not
`"max-iterations"`), FAIL otherwise. Also drive the re-expressed `planAndExecute`
via `fsdev run` against a real model and confirm a multi-step plan still completes
and synthesizes. Pass/fail signal: the printed reason + iteration count.

**Discipline:** `fsd:tdd` (this is a Feature/Enhancement — red-green-refactor with
tracer-bullet slices per behavior). The re-expression steps (§5 steps 4, 5, 7) are
*characterization* refactors: the parity scenarios are written/greened against the
**current** pattern first, then must stay green after the swap.

**Behaviours to test (CI, mocked generators):**

- `converge` with a stub board + inline judge: done-on-1 → single drain; continue×2
  then done → 3 drains; replan judge adds tasks → board grows between drains; judge
  never done → lands at `maxIterations` with `reason: "max-iterations"` (does not
  throw).
- **`maxIterations: N` performs exactly N drains** (not N+1) and the terminal
  `iteration` equals the true drain count (the loopBack jump-count off-by-one).
- **Replan on the final drain adds no un-drained tasks:** a judge that returns
  `replan` on drain N terminates `max-iterations` with the board unchanged (the
  cap-coercion `.map` runs before apply), so `finalize` never sees pending replans that
  never ran. Conversely, a judge that returns **`done` on drain N** terminates
  `converged` (the coercion touches only non-`done` verdicts) — `continue×2 → done`
  at `maxIterations: 3` lands `converged`, not `max-iterations`.
- **A self-capping judge's budget-fired `done` is reported as `max-iterations`:** a
  judge that force-`complete`s at `iteration >= maxIterations` maps to
  `{ done, "max-iterations" }`, so the terminal item reads `max-iterations` — NOT
  `converged` — while a goal-met `complete` on an earlier drain reads `converged`. Cover
  **both** P&E evaluator variants: the replanning preflight (skips the LLM) **and** the
  non-replanning `createTaskEvaluator` (returns a bare `{ complete }` at the cap), keyed on
  the iteration count (§4.2).
- **P&E evaluator throw propagates** (`onError: "fail"`), not swallowed as judge-error.
- **Judge-scoped rescue:** a *judge* throw → `judge-error` `done`; a *seed* or
  *board.block* throw **propagates** (is NOT swallowed as a judge-error).
- Terminal converge item carries `reason` and the drain count, emitted with a
  **distinct component type** (or a full merged board-meta payload) — assert it does
  NOT clobber the completed `task-board-meta` snapshot `<TaskPlan/>` reads by
  `collectionId` (test both the kitchen-sink and `packages/ui` `task-plan-state`).
- `mapToVerdict` mappings (three-way, no collapse of replan/continue): `complete`→done,
  `replan`(+tasks array)→add tasks, `replan`(no tasks array)→`replanner` runs,
  `continue`→`continue`; controller `done`→done else `replan`-with-specialist.
  Test that a plain `continue` does NOT fire the replanner, that a **`replan` with
  `tasks: []`** (empty array present) runs the add step as a no-op and does NOT fire
  the replanner (matches P&E), and that **reasonless source verdicts** (`{ decision:
  "complete" }`, the inline `done` judge) get a default `reason` and are NOT treated as
  malformed.
- Judge input is identical for inline-fn and block/sub-sequencer judges (the
  normalization `.map`); malformed verdict → `onError` path.
- Replan through the lifted `createApplyReplan` deconflicts a repeated task id and
  preserves forwarded `taskContext`/`maxAttemptsPerTask` (not a bare add).
- **Backing:** a `sequencer`-backed board with `maxIterations > 1` **fails loudly**
  (unsupported re-entry, §4.3/§6); a single-pass (`maxIterations: 1`) board is fine
  **without a `seed`**, and a `sequencer`-backed board **with a `seed`** is rejected/needs
  request backing (the pre-drain seed write can't land — §4.2/§6).
- **Custom-evaluator budget (deliberate delta):** a `planAndExecute` with a custom
  `evaluator` lacking its own cap runs **exactly `maxIterations` drains** after
  re-expression (not `maxIterations + 1`); assert the drain count so the normalization is
  explicit (§8).
- **State merge:** with `config.stateSchema` merged, the re-expressed P&E blocks read
  and patch `goal`/`status` on `ctx.sequencer` — a `synthesizeGoal: true` run has the
  planner receive the rewritten goal, and `createBuildPlanOutput` reads the real goal
  (not an empty one).
- **Parity (the acceptance gate):** `planAndExecute`, `parallelTasks` (and
  `routedSpecialists` in PR3) scenarios in `packages/integration-tests/` pass
  identically before and after re-expression — **final output identical; item stream
  identical modulo the one additive converge-termination meta item; drain count and
  iteration count identical** (PR3 also asserts specialist-selection order and
  judge-call count).

**Reference test patterns:** `packages/integration-tests/src/scenarios/*` (the
supervisor + task-board claim-system scenario is the canonical multi-block example);
`fsd:write-block-tests` for the mock-context idiom on the `converge`/judge units.

  Touches the skills runtime (`skill-md.ts`, `pattern-run.ts`, `pattern-registry.ts`),
  every `pattern:` skill file, and the skills docs — an independent, breaking change
  that should not gate the primitive. Note FIX-911's spec (PR #818) also defers this
  reshape to FIX-910, so it currently sits in nobody's active scope — it needs a
  tracked home (re-scoped under FIX-910 or a fresh issue).
- **The pattern-config crosswalk collapse** (issue §4). It is coupled to the rename
  (the crosswalk lives in `apps/docs/docs/skills/pattern-skills.md`, which the rename
  turns into `strategy-skills.md`) and is an *output* of re-expression. Follows the
  rename, not the primitive. A partial simplification naturally falls out of PR2/PR3
  but the doc-table rewrite is deferred.
- **Re-expressing `supervisor`.** Its judge is per-task (worker-level retry budget),
  not a board-level converge loop — a different axis. Stays as-is (§3.4 #2).
- **Re-expressing `debate` / `round-robin`.** They are round-count loops that don't
  use `taskBoard`; folding them onto `converge` would need a `roundsJudge` and is
  optional future work, not v1.
- **`eventActors`.** Stigmergic recursion via `reEmit`, no judge; not a converge
  shape.
- **The full composable termination-condition algebra** (AutoGen-style `.or()/.and()`,
  cost/wall-clock budgets, built-in stall/no-progress detection). Attractive
  (industry precedent) but speculative for v1 (BP-038). Follow-up: extend `judge` /
  add a `Termination` combinator once a second real budget need appears.
- **The configurable *inner*-drain factory** (`board.drain({ max, snapshot, filter })`).
  FIX-907's spec (PR #819) descopes this and assigns it to FIX-910, but it is
  orthogonal to the converge *outer* loop: converge mounts the drain as-is and needs
  no inner-drain knobs. Declining it here (BP-038 — no speculative surface, no
  consumer whose config shape is known). converge stays forward-compatible: its
  `board` slot accepts whatever drain block the board exposes, configured or not. If
  the project wants the factory, it warrants its own issue/spec shaped by a real use
  case — not a rider on this one.
- **Deleting `planAndExecute` / `routedSpecialists` factories.** Only `parallelTasks`'
  *body* is deleted (it becomes trivial config); the named factories stay.

**One deliberate behavior delta (not preserved).** Re-expressed `planAndExecute` unifies
the iteration budget: `maxIterations` becomes *total drains* for every judge. Today a
caller-supplied **custom `evaluator` with no built-in cap** gets `maxIterations + 1`
drains (loopBack's jump cap binds after the first drain), whereas the default evaluator
gets exactly `maxIterations` (its preflight binds first). After re-expression the
custom-evaluator path is `maxIterations` drains — **one fewer**. This is an accepted
normalization (uniform "total drains" semantics beat preserving an incidental off-by-one
on a niche path); a parity test asserts the new count so the change is explicit, not
silent. All other `planAndExecute` behavior is preserved.

**Deepening opportunities flagged during analysis** (follow up via
`fsd:improve-codebase-architecture`, not in scope here):

- The three near-isomorphic judge schemas (`evaluatorVerdictSchema`,
  `controllerOutputSchema`, `reviewerVerdictSchema`) — this spec unifies the first
  two under `Verdict`; the per-task reviewer verdict remains separate.
- `routedSpecialists` bypassing `taskBoard` — this spec folds it back on, removing
  a hand-rolled loop and manual `collection.claim/complete/fail`.

- **Contract name for the follow-up:** `strategy` (confirmed).
- **Primitive name:** `converge` (signals termination intent; `iterate`/`loop`

### Implementation choices (decide during PR1/PR2; none blocks starting)

- **Handle-metadata guards (backing + idless `initialTasks`) — which mechanism.** Two
  multi-iteration preconditions can't be checked from today's thin `TaskBoardHandle`
  (`{ block, collectionId, capability }`): (1) **re-enterable backing** — a
  sequencer-backed board can't survive re-entry, and a lost slot returns `{}` rather
  than throwing (§4.3), so "2nd drain throws" is NOT viable; (2) **no idless board
  `initialTasks`** — the board seed re-runs each drain and re-adds them (§6). Both want
  the same fix: **expose the needed metadata on the handle** (backing/stateKey + seed
  info — FIX-908-adjacent) for a construction-time assert (preferred), or move the
  validation into `taskBoard`. Fallback for the backing case only: a **converge
  sentinel** (seed writes a marker; converge throws before the 2nd drain if it didn't
  survive). Until the handle exposes them, both are **documented caller preconditions**.
