# FIX-911: Skills v2 — per-generator skill binding via capability config — Implementation Spec

> **Status: design settled, implementation gated.** This spec was reshaped after a
> long design discussion (see the issue thread). The earlier "structural per-generator
> keying" design (a request slot keyed by a `ownerGeneratorKey` stamped into the tool
> executor) is **superseded** — it was faking a per-generator state scope, and spec-PR
> review surfaced ~a dozen edge cases confirming that was the wrong foundation. The
> settled model below binds skills through **capability config** and stores dynamic
> activation in an **author-named state field or the generator's own block state**.
> It depends on two primitives, now **specced and in implementation**:
> **[FIX-915](https://linear.app/fixpoint-labs/issue/FIX-915)** (capability config
> factories, #828) and **[FIX-914](https://linear.app/fixpoint-labs/issue/FIX-914)**
> (block-level state, #827). Their contracts are **settled**, and this spec is reconciled
> to what they actually deliver (§10): the tool→generator write is **`ctx.parent`** (not a
> nearest-ancestor resolver), the badge is **FIX-911's own per-activation client item**
> (FIX-914 declined a client-visible block-state projection), and the block-state default is
> **in-memory** (durability ⇒ a session-scoped `activeState`). FIX-911 is fully blocked on
> **FIX-915** and on **FIX-914 PR1+PR2** landing; it is *only partially* blocked on FIX-914
> — a FIX-915-only first slice (dynamic activation requires an explicit `activeState`) can
> land before FIX-914's block-state default (§10).

## 1. TLDR

**Plain-language summary.** Today, when an agent "activates" a skill, that activation
goes into one shared bag every agent in the conversation reads from — so in a
multi-agent flow one agent's skill leaks into another's instructions. The new model:
there's a shared **skills library**, and each generator **configures** which skills it
has and how. Skills you want on from the start are preloaded. Skills the agent may pick
up mid-task live in a named piece of state (by default, the generator's own private
state), and a small opt-in installs the tool that lets the model load one. No shared
bag, no framework guessing which generator is which.

**Technical statement.** Replace session-global `activeSkills` with (a) a shared skills
**library** capability and (b) a per-generator binding configured via
`library.config({ active, allowed, activeState }).presets({ dynamicActivation })`,
built on the capability-config primitive (FIX-915). Dynamic activation is stored in the
author-named `activeState` field, defaulting to the generator's **block state**
(FIX-914) when `dynamicActivation` is on and no field is named. The `/skill` + keyword
matcher stays an upstream block that writes the same `activeState`.

**Deliverables (blocked on FIX-914 + FIX-915):**
- **Library:** factor the writable skills collection + catalog + seeding into a shared
  library capability (installed once), separate from the per-generator binding.
- **Binding via config (FIX-915):** `config({ active, allowed, activeState })` — `active`
  preloads bodies statically (+ the skills' declared `allowed-tools`; no runtime state, no
  activation tool); `allowed` is the catalog the load tool
  may pull from; `activeState: { scope, field }` names where dynamic activations live.
- **Dynamic-activation preset:** `presets({ dynamicActivation })` installs the tool that
  lets the model load a skill (writes `activeState`); defaults its storage to the
  generator's block state (FIX-914) when no `activeState` is named.
- **Reader:** the generator's context formatter renders `active` (static) + whatever is
  in `activeState` (dynamic), memoized per execution.
- **Upstream matcher:** `createSkillActivator` (`/skill`, keyword) stays a configured
  upstream block; it writes the same `activeState` field. Not built into generators.
- **Docs:** CREATE `apps/docs/docs/skills/binding.md`; correct `overview`/`activation`/
  `authoring` + the guide + README off the session-global model.

**Size: Large; blocked.** Design is settled; implementation is gated on FIX-914 and
FIX-915. Once those land, FIX-911 is a focused consumer.

## 2. Overview

Linear issue: [FIX-911](https://linear.app/fixpoint-labs/issue/FIX-911). Skills are
reusable instruction playbooks (a Markdown body + optional tool allow-list) injected as
context into an LLM generation. Today they activate into a **session-global** registry
(`activeSkills` in `session.state`) shared by every generator, causing cross-generator
bleed and cross-turn persistence. This moves binding to be **configured per generator**:
what a generator knows about, what's preloaded, and where dynamic activations live are
all declared where the generator is defined. Nothing lives in a shared bag; isolation is
by configuration and by block-namespaced state, not by framework-derived identity.

## 3. Background & Key Decisions

### 3.1 Two needs, not one

A generator relates to skills along two independent axes (owner framing):
- **What's available** — skills the generator knows about and *may* load on demand.
- **What's active** — skills whose bodies are currently in context.

And "active" splits by *who decides*: config-time (static), code/an upstream block at
runtime, or the LLM mid-loop. These are orthogonal — "state-driven" does not imply
"LLM-driven."

### 3.2 Why the structural-keying design was abandoned

The prior design stored dynamic activation in request state keyed by a per-generator
structural id, because **generator-scoped state isn't a first-class scope** — so it
synthesized one via a `ownerGeneratorKey` stamped into the tool-executor scope. Spec-PR
review (Codex, Greptile/T-Rex, the owner) surfaced that this foundation leaks at every
seam: `agentName`/`ownedBy` don't reliably carry the generator id in a tool scope; a
per-attempt `blockInstanceId` re-keys on retry and drops the activation; request state
is lost on durable resume; the up-front activator (upstream) can't see the generator's
id at all; the replacement UI badge (a transient item) is dropped by the client's
transient filter; ownerless v1 legacy entries can't be routed on resume. Every one of
those is "I'm trying to derive per-generator identity at runtime." The fix is to stop
deriving it: **the author names where active state lives (config), and un-configured
dynamic activation gets a real home via block state.**

### 3.3 The settled model

- **Library vs binding.** One shared **library** (collection/catalog/seeding), installed
  once; a per-generator **binding** via `config({...})` returns the CapabilityRef.
- **`active: [...]`** — static preload: bodies + the skills' declared `allowed-tools` from
  the catalog. No runtime state, no activation tool. (This is what
  the abandoned `.bind()` was reaching for.)
- **`activeState: { scope, field }`** — where dynamic activations live. A named state
  field at a chosen scope. Whoever writes it — code, an upstream block, or the LLM tool —
  the formatter renders whatever's there. Isolation is by field/scope (author-chosen);
  durability is by scope (session survives durable resume; request/block-state resets per
  turn). No framework-derived key, so retry/resume/identity all stop being problems.
- **`presets({ dynamicActivation })`** — installs the tool that lets the *model* load a
  skill (writes `activeState`). Separate from `activeState` (state-driven ≠ LLM-driven).
  When on and no `activeState` is named, it **defaults storage to the generator's block
  state** (FIX-914) — the natural per-generator home, so `dynamicActivation: true` "just
  works" with no author boilerplate and no bleed.
- **Upstream matcher unchanged.** `/skill` + keyword detection stays a configured block
  ahead of the generator (today's `createSkillActivator`). Because it runs upstream, it
  writes an **explicit shared `activeState` field** (required for this path — it can't
  reach a generator's block-state default; §4.3). The right place for explicit-request
  detection is the configured sequence, not inside generators.
- **Pattern/fork untouched**, deferred to FIX-910 (the pattern→strategy binding becomes a
  config dimension later; see FIX-915).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Bind skills through capability config, not session-global state or structural
   keying.** *Rejected:* the request-slot-keyed-by-structural-id design. *Ramification:*
   dissolves the cross-generator bleed and the entire keying/retry/resume/identity class
   of bugs; makes FIX-911 a consumer of the FIX-915 config primitive (hard dependency).
2. **`activeState` names where dynamic activations live; `dynamicActivation` installs the
   LLM tool — kept separate.** *Rejected:* folding the tool into `activeState` (my
   over-collapse). *Ramification:* preserves the code-drives-active-state case (a matcher
   or flag sets skills, the LLM never gets a tool); the resolver decides how config
   composes.
3. **Un-configured `dynamicActivation` defaults to the generator's block state.**
   *Rejected:* "no default" (too much boilerplate for the lone-generator case) and an
   auto-named request field (a framework-derived key — the thing we're escaping).
   *Ramification:* the clean `dynamicActivation: true`-just-works experience — but makes
   FIX-911 depend on FIX-914 (block state).
4. **One shared library + per-generator config binding; presets ride alongside config.**
   *Rejected:* one muddled `createSkillsCapability` conflating library and binding, and a
   presets-only surface (can't carry values). *Ramification:* the writable-store concerns
   (collection/seed/catalog) separate from per-generator binding; `config().presets()`
   compose.
5. **Pattern/fork and the pattern→strategy rename stay deferred (FIX-910).**
   *Ramification:* FIX-911 stays scoped to binding; the strategy binding later expresses
   through this same config surface (FIX-915), not `runSkill` `pattern` mode.

## 4. Technical Design

### 4.1 Surface

```ts
// Installed once — the shared library (writable collection + catalog + seeding).
const skills = createSkillsLibrary({ catalog, initialSkills /* , scope, collection */ });

// Per generator — configure the binding (built on the FIX-915 config primitive):
const researcher = generator({
  name: "researcher",
  model: "openai/gpt-5.4-mini",
  uses: [skills.config({ active: ["detailed-analysis"] })],          // static preload only
});

const assistant = generator({
  name: "assistant",
  model: "openai/gpt-5.4-mini",
  uses: [
    skills
      .config({ allowed: ["deep-research", "auto-learn"] })          // catalog the tool may load
      .presets({ dynamicActivation: true }),                         // + the load tool; storage → block state
  ],
});

// Explicit code/state binding — no LLM tool, code decides. `allowed` is still required
// (it bounds the reader and installs the activatable skills' tools):
skills.config({ allowed: ["deep-research"], activeState: { scope: "session", field: "activeAnalystSkills" } });
```

- `active: string[]` — statically render these bodies **and contribute the catalog tools
  those skills declare via `allowed-tools`**, so a statically-active skill can actually call
  the tools its body references. No runtime state and no *activation* tool — but the skills'
  own declared tools are installed (or the resolver rejects a skill whose tools aren't in the
  catalog). **Omitted `allowed-tools` = unrestricted** — mirror the `allowed` path and
  contribute the full catalog (or reject), so a preloaded skill that declares no list still
  reaches the tools its body references. **Inline-mode skills only** — a `fork`/`pattern`
  skill is rejected here, since those are dispatch routes (subagent / task-board strategy),
  not static context.
- `allowed: string[]` — the set the load tool may pull from (a catalog). Meaningful with
  dynamic activation. The binding **also contributes the catalog tools those `allowed` skills
  declare via `allowed-tools`** (same as static `active`), so a skill loaded at runtime can
  actually call the tools its body references — a body rendered on the next step without its
  tools present is the failure this avoids. Preserve the existing omitted-`allowed-tools`
  semantics (no declared list = unrestricted); the resolver rejects a skill whose declared
  tools aren't in the catalog. Like `active`, `allowed` is **author config and fails loud**:
  resolve it **after seeding** and reject a name not present (a typo / deleted skill would
  otherwise build a catalog that silently can't load the skill the author declared).
- `activeState: { scope, field }` — where dynamic activations are stored/read. Written by
  code, an upstream block, or (with `dynamicActivation`) the LLM tool. **An `activeState`
  binding must pair with an `allowed` catalog** (which contributes the possible skills'
  declared catalog tools, §4.1 `allowed`) — otherwise code or the matcher can write an inline
  skill whose body references tools the generator was never given. The `allowed` set both
  bounds what the reader renders (§4.2) and installs the tools those skills need.
- `presets({ dynamicActivation })` — installs the model-facing load/activate tool; storage
  defaults to the generator's block state (FIX-914) when `activeState` is omitted. The tool
  accepts **inline-mode skills only** — a `fork`/`pattern` skill in `allowed` is rejected by
  the tool (not routed here). Otherwise the tool could write a mode-bearing `activeState`
  entry that §4.2 then filters out of context, appearing to succeed while injecting nothing
  and dispatching nothing. Fork/pattern dispatch stays on the existing `runSkill` router
  surface (reshape deferred to FIX-910). **`dynamicActivation` requires `allowed`** — the tool
  loads only from the binding's `allowed` catalog. Defaulting to the whole shared library would
  recreate the global-availability bleed this issue removes; defaulting to none makes the tool
  useless. So a `dynamicActivation` preset without `allowed` is a config error (rejected), not
  a silent "load anything."

Two primitives split this work. The skills capability defines a **config resolver** (FIX-915)
that maps these settings onto **context / tool / resource** contributions at build time and
owns their compose semantics — e.g. an explicit `activeState` overrides the `dynamicActivation`
default target (singleton-like), while contributed `context` adds. **Configure the binding in
one `.config().presets()` chain per generator, not two `uses` entries.** The FIX-915 flattener
dedups configured refs **by base capability** and keeps only one, throwing on a **diamond
conflict** (same base, non-identical config) — so two separate `skills.config({...})` refs on
one generator (e.g. `{active}` from one wrapper and `{allowed}.presets({dynamicActivation})`
from another) do **not** silently merge: they either dedup-drop one or throw. The single-binding
rule (one chained ref) is the contract; the diamond-throw is the backstop against an accidental
second ref. Separately, the
`dynamicActivation` block-state **default cell** (the generator's own `activeSkills` state) is
contributed through **FIX-914 PR2's capability own-state seam**, not the FIX-915 resolver —
the resolver produces context/tools; FIX-914 PR2 gives the generator the `stateSchema` those
tools read via `ctx.self` and write via `ctx.parent`.

### 4.2 Reader

The generator's context formatter renders: the `active` bodies (static, resolved once and
memoized per execution — cache scoped to the execution or keyed by skill revision, never
to the library ref) **plus the `inline`-mode entries in `activeState`** (dynamic). Both
come from the library collection. **The reader gates `activeState` entries by this binding's
own set** (`active` ∪ `allowed`): an entry naming a skill outside the binding is **skipped +
warned**, not rendered. A persisted/shared `activeState` field can hold entries written by a
sibling generator, arbitrary code, or a stale older config; without this gate a foreign skill
would inject and reintroduce the cross-generator bleed this issue removes. (An explicit
unbounded-mode opt-out could exist later; the default is gated.) **Memoization covers only the static `active` bodies** —
`activeState` must be **re-read on every tool-loop step** (the generator re-resolves dynamic
context in `prepareStep`), so a skill the load tool writes mid-loop injects on the *next*
step of the same execution, not a later turn. Memoizing the combined `active + activeState`
result would defeat dynamic activation entirely. The formatter reads `activeState` at its
configured scope/field (or the generator's block state when defaulted).

**`activeState` entries carry a mode *and* the activation input.** Only `inline` activations
render as context; `fork`/`pattern` are *dispatch* concerns (subagent / task-board strategy),
not context, and must **not** be inline-rendered. Those stay on the existing shared dispatch
surface, untouched here (reshape deferred to FIX-910). So the `activeState` schema is
mode-bearing and the formatter filters to `inline` — writing a fork/pattern skill into
`activeState` without that filter would wrongly inline its body and bypass its dispatch path.
The schema must also **preserve each activation's input argument and `source` tier** (today's
`ActiveSkillEntry.input` / `.source`, captured by `/skill topic`, the keyword/classifier
tiers, and the load tool). The formatter substitutes the input into the skill body's
`$ARGUMENTS` — dropping it silently breaks argument-dependent skills; and the badge displays
the `source` tier (slash / keyword / classifier) — dropping it regresses matcher-driven
skills to a generic tool/default label.

### 4.3 Writers

- **LLM (with `dynamicActivation`):** the load/activate tool runs inside the generator's
  loop **as a child scope node** of the generator — its *own* block state is **not** the
  generator's. To land where the formatter reads, the tool writes the **parent generator's**
  block state via **`ctx.parent`** (FIX-914's settled handle; the tool declares a
  `parentStateSchema`), or the configured explicit `activeState`, atomically. FIX-914
  confirmed this is `ctx.parent` — a tool's immediate parent *is* its generator, so **no
  "nearest-ancestor-of-type" resolver is needed** (FIX-914 §8 rejected one). Without a
  container on the generator, `dynamicActivation: true` would write tool-local state the
  formatter never reads — so this needs **FIX-914 PR1 (`ctx.self`/`ctx.parent`) *and* PR2**
  (the capability own-state seam that lets the skills capability contribute the generator's
  `stateSchema`; §10). The tool rejects invalid loads (§6), so a bad activation surfaces to
  the model rather than silently no-op'ing.
- **Upstream matcher (`createSkillActivator`) / arbitrary code:** runs **before** (or
  outside) the generator, so it **cannot** write the generator's block state — block state
  is created when the block runs and a not-yet-dispatched downstream generator isn't
  addressable pre-dispatch (surfaced in spec-PR review). Therefore **the code/upstream path
  requires an explicit shared `activeState: { scope, field }`** at any persisted, writable
  scope — request, session, user, or org (`ctx.user`/`ctx.org` are normal writable handles;
  user/org are what §4.4's badge path needs) — referenced by both the writer and the generator. The block-state default applies to the
  in-generator LLM path only; a flow that uses the upstream matcher must configure an
  explicit field. The matcher must also be **scoped to the field's consumers' catalogs**: its
  tiers enumerate the whole skills collection today, so it has to receive/enforce an `allowed`
  bound before writing — otherwise a `/skill` (or keyword) for a skill no consumer permits
  would land in `activeState` and render, bypassing the availability contract. For a field
  used by **one** generator that bound is the generator's `allowed`. For a **shared** field
  used by two generators with **different** catalogs, the matcher must be given the **union**
  of the consumers' `allowed` sets (scoping it to a single generator's catalog would drop a
  `/skill` that's valid for the *other* generator before the per-binding reader gate, §4.2,
  can filter it). The matcher writes the union; **each generator's reader gate then filters to
  its own catalog** — that division keeps the shared-field case working for non-identical
  catalogs. (Alternatively, reject a shared field + single-catalog matcher; the union is
  preferred.) **The matcher owns replace/clear semantics for a persisted field:** on a turn
  with **no** slash/keyword/classifier match it must **clear (or replace) its own entries**
  (as v1's apply step writes `activeSkills = []`), not leave them. On a persisted
  session/user/org field the reader (§4.2) renders whatever is there, so a stale entry left by
  a prior turn would re-inject and reintroduce the cross-turn persistence this issue removes.
  (Request-scoped `activeState` and the block-state default reset per turn, so this bites only
  the persisted-field path.) **Scope choice for per-turn activation is a request-isolation
  question, and only request scope is isolated by construction.** `session` is
  conversation-scoped but **not** request-isolated — under the default `allow` concurrency two
  requests in one session overlap, so a session-field match/clear from one request can interleave
  with another request's matcher→generator read (dropped or bled skill). `user` spans a user's
  sessions; `org` spans users — wider still. So: the **per-turn default is request scope** (the
  block-state default), naturally isolated, with the **badge coming from the per-activation
  client item** (§4.4), not a projected field. A **persisted** field (session/user/org) is an
  opt-in for **sticky activation that outlives the request**, and per-turn use of one requires
  either **session-queued/rejected concurrency** or a **request discriminator inside the field**
  (plus, for user/org, the identity-breadth caveat above). Don't reach for a persisted scope
  just to get a badge — the client item covers that.

This split is the concrete form of "state-driven ≠ LLM-driven": the LLM tool writes its
owning generator's block state (ancestor-addressed); anything writing from outside the
generator coordinates through a shared, addressable field.

### 4.4 UI

When `activeState` is at a **persisted, client-visible scope** (session/user/org), the badge
reads it from real state — but **not** via a `client.derived` projection for *live* updates.
The React reducer merges raw `state_change` deltas into already-**exposed** keys and leaves
derived projections stale until the terminal snapshot refresh — so a mid-loop or upfront
activation routed through `client.derived` would not move the badge while the generator is
still using the skill. The live path is an **exposed/defaulted state field** (raw deltas merge
live) or a **dedicated per-activation item/channel** — not a derived projection. An exposed
field must also be **declared on that identity scope's own `stateSchema`** — and it must be
**the flow that declares it, not the skills capability**. `defineFlow` normalizes
`session/user/org.client.expose` against the flow scope's *own* `stateSchema` before/without
aggregating block or capability state schemas, and the FIX-914 capability own-state seam
contributes **request-scoped block state**, not an identity-scope schema. So a capability-
contributed field does **not** satisfy the flow-scope `client.expose` validator: a badge-backed
session/user/org `activeState` field must be **declared by the flow author on that scope's
`stateSchema`** (or await a flow-level schema-aggregation primitive). Naming a field to expose
without a flow-scope declaration fails at flow-definition time.

**Identity-scope tenancy (org only).** An `activeState` at **`org`** scope requires the
consuming action (and the writer) to be **org-bound** — `ctx.org` is optional and absent
unless the action opts in (`requireOrg`), and capability presets can't contribute that flag
today, so org-scoped `activeState` is a **config error unless the action is org-bound**;
the author sets `requireOrg` explicitly. **`user` scope needs no extra opt-in** — `ctx.user`
is a required block-context handle and `defineFlow` already rejects `requireUser: false` when
user state/client/resources are declared, so a user-scoped `activeState` field is bound
automatically. So the rule is org-only; session/user are fine as-is.

The **block-state default is request-scoped, block-local, and in-memory** — FIX-914 emits
block-instance `state_change` as **transient in production** and **explicitly declines** a
client-visible projection of block state, handing the skills badge back to **FIX-911** (FIX-914
§8/§10). So a flow relying on `dynamicActivation: true` with no explicit field has **no live
badge source from FIX-914**, and **FIX-911 owns the badge via a per-activation client item**
(a real, non-transient item the reader/tool emits on each activation) — not a block-state
projection. The default path's badge is FIX-911's to emit, not "just read the field."
**But a non-transient item persists in the item log**, while the underlying activation is
request-local (block-state / request scope) and gone next turn — so the badge item **must
define its own clearing**: either the UI scopes the badge to the **current in-flight request**
(ignore activation items from prior requests), or the run emits a **clear/deactivate item** at
request end. Without one, the badge lingers showing a skill the formatter no longer reads.

The same gap applies to an **explicit `activeState: { scope: "request" }`**: request state
has no flow-level `client.derived` projection (the client reducer folds `state_change` only
for session/user/org), so a request-scoped field loses the badge just like the block-state
default. Rule for badge-backed activations: **per-turn activation stores in request scope (the
block-state default) and badges via the per-activation client item** — request-isolated by
construction, no projected field needed. Reach for a **persisted** `activeState`
(session/user/org) only for activation that should **outlive the request** (sticky), accepting
the §4.3 concurrency/tenancy caveats (session isn't request-isolated; user/org span
sessions/users). Don't pick a persisted scope merely to get a badge — the client item covers
the per-turn badge without the isolation hazards.

### 4.5 Migration off v1

v1 `activeSkills` is session-global and **ownerless by design** — no migration can
reconstruct which generator an entry belonged to. Policy: a cross-deploy resume of an
in-flight v1 request **continues v1 (session-global) semantics for the remainder of that
one suspended request**; new (post-deploy) requests use the config model. **How the runtime
picks the v1 reader:** by an **explicit request-level v1-resume marker** stamped on the
suspension by v1 — **not** by mere presence of a config-model field. A badge-backed flow
**declares/defaults** its `activeState` field, so that field is *present but empty* on a
resumed v1 request before any v2 activation; a "config-state present → use v2" rule would then
wrongly ignore the legacy `activeSkills` and drop the skill. So the reader keys the branch off
the request-level marker (or, equivalently, a **nonempty v2-write marker** — the field was
actually written by a v2 activation), and only then **dual-reads** config-model state, else
legacy `activeSkills` (BP-030).

**Rollout ordering — the marker can't be retroactive, and session-state presence isn't the
discriminator.** Requests already suspended under the *current* v1 runtime carry **no**
request-level marker (nothing stamped it), so the branch can't rely on the marker alone. And
mere presence of `session.state.activeSkills` can't be the discriminator either: v1
`activeSkills` is **session-global and persistent**, so a genuinely *new* post-deploy request
in an upgraded session may still see leftover v1 entries — routing it through legacy would be
wrong. The real discriminator is **"is this the continuation of a pre-v2 suspension record"**,
which **already exists on old records** (a resumed request carries a suspension/continuation
record; a new request does not). So: **legacy semantics apply only when resuming a pre-v2
suspension record** (identified by that record + no v2-write on the field); a **new request
uses the config model and ignores leftover session `activeSkills`** (BP-031 — don't derive
behavior from session leftovers). This needs no pre-stamping and no new discriminator. The
pattern board pointer (`ActivePatternMeta`) is a separate, cross-generator concern and is
untouched here (stays shared; reshaped by FIX-910).

## 5. Implementation Sequence

**Gated on FIX-914 (block state) and FIX-915 (capability config) landing.** Once both are
in, FIX-911 is a focused consumer; discipline `fsd:tdd`.

1. **Library extraction** — factor the collection/catalog/seeding into
   `createSkillsLibrary` (shared, installed once), separate from the per-generator binding.
   The library **owns seeding**: it must seed `initialSkills` on install (or the matcher
   must seed before its first tier runs), not lazily inside `runSkill`/the catalog formatter
   as today. Otherwise a flow that uses static binding or disables the catalog/`runSkill`
   preset leaves the collection empty on turn 1, and the upstream matcher's slash/keyword/
   classifier tiers scan an empty catalog — `/skill` and keyword matches against bundled
   skills silently miss until something else seeds.
2. **Config binding (consumes FIX-915)** — `skills.config({ active, allowed, activeState })`
   with the skills config resolver; `active` → static context; `allowed` → catalog;
   `activeState` → wire read/write to the named scope/field.
3. **`dynamicActivation` preset** — install the load/activate tool (writing `activeState`);
   default its storage to the generator's block state (consumes FIX-914) when no
   `activeState` is configured.
4. **Reader** — formatter renders `active` + `activeState`, memoized per execution.
5. **Upstream matcher** — repoint `createSkillActivator` to write the configured
   `activeState` field.
6. **Caller + fixture migration** — kitchen-sink, research-team, integration fixtures off
   session-global `activeSkills`; add a no-cross-generator-bleed integration scenario.
7. **Docs** (§9).

## 6. Edge Cases

| Case | Expected |
| --- | --- |
| Two generators, each `config({ active: [...] })` different skills | Each renders only its own; no bleed (separate config). |
| `dynamicActivation` on, no `activeState` | Storage = the generator's block state; per-generator, no bleed, no author field. |
| `dynamicActivation` on, explicit `activeState` | Uses the named field/scope; config overrides the block-state default (resolver). |
| Upstream `createSkillActivator` with only the block-state default (no `activeState`) | **Rejected/required-config:** upstream can't write a downstream generator's block state; the matcher path requires an explicit shared `activeState` field. |
| Two generators share the same `activeState` field+scope | They share active skills — an explicit, visible author choice (e.g. a coordinating team), not framework magic. |
| Whole-generator retry after a mid-loop activation | Block state keys by the **retry-stable logical path** (path minus `attempt`) → the activation survives the retry. |
| Same generator dispatched twice (two sequencer steps / concurrent `forEach`) | Must stay isolated — the key is the **logical path** (which includes step/iter segments), not bare `block.name`; FIX-914 owns this fan-out contract. |
| Durable resume after an activation | Survives **only** with an explicit durable identity scope (session/user/org `activeState`). The **block-state default is in-memory** (FIX-914 PR1) and is **lost on suspend/resume** — durable non-sequencer block state is a deferred FIX-914 follow-up, so `dynamicActivation` needing durability must configure a session-scoped `activeState`, not rely on the default. Request-scoped resets per turn (intended default). |
| `active` names an unseeded bundled skill | Rendered (formatter seeds first). |
| `active` **or `allowed`** names a missing / disabled / typo'd skill | **Fails loud** (build-time or first resolution after seeding) — both are author config, not a stale read. |
| Badge-backed `activeState` at session/user/org, field declared only by the capability | **Fails at flow-definition** — `client.expose` validates against the flow scope's own `stateSchema`; the flow author must declare the field. |
| `activeState` at **`org`** scope on a non-org-bound action | **Config error** — `ctx.org` absent unless the action sets `requireOrg`. (`user` needs no opt-in — `ctx.user` is auto-required.) |
| Per-turn activation, scope choice | **Request scope (block-state default) + per-activation client item for the badge** — request-isolated. Persisted scopes are sticky-only: `session` isn't request-isolated (concurrent same-session requests interleave → needs queued concurrency or a request discriminator); `user`/`org` also span sessions/users. |
| Two `skills.config({...})` refs of the same library on one generator | **Dedup-drop-one or diamond-throw** (FIX-915), never silent merge — use one `.config().presets()` chain per generator. |
| v1 request already suspended before the marker-writing deploy | Legacy branch keyed to the **pre-v2 suspension/continuation record** (present on old records; absent on new requests), not state presence — no retroactive marker needed. |
| Leftover session `activeSkills` on a genuinely new post-deploy request | **Config model; ignore the leftover** — v1 `activeSkills` is session-global/persistent, so state presence must **not** select v1 (only a suspension record does). |
| Legacy v1 `session.state.activeSkills` at deploy | In-flight suspended request (identified by its record) continues v1 semantics; new requests use the config model. Pattern pointer untouched. |
| Pattern/fork invoked | Works as today; reshape deferred to FIX-910. |

**Failure taxonomy.** Three cases, not one. (1) *Static `active` resolution* is an author
**declaration** — a missing/disabled/typo'd bundled skill is a config error and **fails
loud** (build-time, or first runtime resolution after seeding), because silently skipping it
would run the generator without instructions the author explicitly requested. (2) *Passive
reads of persisted `activeState`* are non-fatal (skip + warn) — an entry that's since gone
missing shouldn't crash the turn, since that state accumulated at runtime and may legitimately
outlive a skill. (3) The *model-facing activation tool* **rejects** an unknown / disabled /
disallowed load (throws, as `runSkill` does today) — a silent skip would let the model proceed
believing it loaded instructions it didn't. So: static config fails loud; stale runtime reads
skip+warn; the tool is fatal on invalid loads.

## 7. Testing Strategy

**Goal.** In a two-generator flow, a skill configured on / activated by one generator
never appears in the other's context, and an activation does not persist into the next
turn (unless the author chose a durable scope).

**Goal check (real-model, out-of-CI):** `goals/skills-scoped-binding/no-cross-generator-bleed/run.mts`
— generator A configures/activates a distinctive skill, B does not; drive a real turn;
assert B shows no trace and a second turn on A starts clean.

**Discipline `fsd:tdd` — behaviours:** `config({ active })` renders statically with zero
writes; `dynamicActivation` installs the tool and its default storage is the generator's
block state; `dynamicActivation` without `allowed` is a config error; an exposed `activeState`
field undeclared on the scope `stateSchema` fails at flow-definition time; the upstream matcher
can target a user/org-scoped `activeState`; an explicit `activeState` is used and overrides the default; the upstream
matcher writing `activeState` is rendered by the generator; two generators with distinct
configs are isolated; the reader **skips+warns an `activeState` entry outside this binding's
`active`∪`allowed` set** (shared/stale-field bleed guard); an `activeState` binding without
`allowed` is a config error; two generators sharing a field share only entries within each's
catalog (documented); block-state retry keeps the activation; an activation with an input argument round-trips through `activeState` and
substitutes into the body's `$ARGUMENTS`; the activation `source` tier round-trips so the
badge keeps its slash/keyword/classifier label; a skill the load tool writes mid-loop is injected
on the next step of the *same* execution (memoization doesn't stale out dynamic activeState);
a static `active` skill that omits `allowed-tools` still reaches the catalog tools; a missing
static `active` **or `allowed`** skill fails loud while a stale persisted `activeState` entry
skips+warns; a badge-backed session/user/org `activeState` field declared only by the capability
(not the flow scope) fails at flow-definition; an `org`-scoped `activeState` on a
non-org-bound action is a config error (user needs no opt-in); a v1 request suspended before the
marker deploy gets v1 semantics **because it carries a pre-v2 suspension record** (a *new*
request with leftover session `activeSkills` but no such record uses the config model — state
presence must not select v1); the upstream matcher clears its persisted-field entries on a
no-match turn; the badge updates live from an exposed field (not a
stale `client.derived` projection); `dynamicActivation` rejects a `fork`/`pattern`
skill in `allowed` and contributes the `allowed` skills' catalog tools (a runtime-loaded
skill can call its declared tools); the upstream matcher finds a bundled skill on turn 1 with
the catalog preset disabled (seed-before-scan); existing `pattern-skill-*` scenarios pass.

Seams: `packages/orchestration/test/skills/*` (unit), `packages/integration-tests/src/scenarios/*`
(flow-level), plus the goal check.

## 10. Dependencies

Both blockers are now **specced and in implementation** (FIX-914 #827, FIX-915 #828). Their
contracts are settled; this section is reconciled to what they actually deliver.

- **FIX-915 (capability config factories)** — hard blocker; provides the `.config()` /
  `.presets()` builder + the author-defined **resolver** (`resolve(config, ctx) →
  Partial<PresetDef>`) that maps `{ active, allowed, activeState }` to the binding's
  **context/tools/resource** contributions at *build time*. Notes reconciled from FIX-915:
  the resolver runs at merge time (no runtime channel); `.config().presets()` chains in
  **either order**; the skills schema is `z.object({ active?, allowed?, activeState? }).default({})`
  so `.config()` stays optional; a configured ref through a **dynamic `uses`** function is
  rejected at runtime, so the skills binding must be a **static `uses`** entry. FIX-915's
  resolver does **not** create the block-state container — that is FIX-914's job (below).
- **FIX-914 (block-level state)** — hard blocker; needs **PR1 *and* PR2**. PR1 gives the
  generator its own request-scoped state read via **`ctx.self`** and written by its child
  activation tool via **`ctx.parent`** (the settled handle — a tool's immediate parent *is*
  its generator, so there is **no** nearest-ancestor-of-type resolver; the tool declares a
  `parentStateSchema`). PR2 is the **capability own-state seam** that lets the skills
  capability contribute the generator's `stateSchema` (the `activeSkills` cell), with
  duplicate-field collision detection. Reconciled facts: (a) block state is **retry-stable by
  path** and **fan-out-isolated per scope node** automatically — no work for FIX-911; (b)
  FIX-914 emits block-instance `state_change` as **transient** and **explicitly declines a
  client-visible projection** — so the **badge is FIX-911's own** per-activation client item
  (§4.4), not FIX-914's; (c) the child→ancestor write is **`ctx.parent`** (settled); (d)
  pre-dispatch writes to a not-yet-run generator's block state are **unsupported** (confirmed)
  — hence the upstream matcher needs an explicit shared `activeState` (§4.3); (e) durable /
  suspend-resume block state is a **deferred FIX-914 follow-up**, so the block-state default
  is in-memory and durability requires a session-scoped `activeState` (§6).
- **Partial-block insight (scheduling):** only the **block-state default** for
  `dynamicActivation` (no explicit field) needs FIX-914. The library, `config({ active,
  allowed, activeState })`, an explicit session/user/org `activeState`, and the upstream
  matcher need only **FIX-915** + existing identity scopes. So FIX-911 can land in two slices
  — a FIX-915-only slice (dynamic activation requires an explicit `activeState`), then the
  block-state-default ergonomics once FIX-914 PR1+PR2 land.
- **FIX-910 (converge / pattern→strategy)** — related; pattern/fork stay deferred there,
  and the strategy binding later expresses through this config surface. Not a blocker.
- **FIX-908 (board capability surface)** — related; a confirmed sibling consumer of FIX-915.
