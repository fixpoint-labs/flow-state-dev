# FIX-911: Skills v2 — per-generator skill binding via capability config — Implementation Spec

> **Repo copy (canonical).** Mirrors the Linear document; kept in sync (BP-037).
> The Linear issue states *what* and *why*; this states *how*.

> **Status: implemented (additive).** The settled model binds skills through
> **capability config** (FIX-915) and stores dynamic activation in an
> author-named state field or the generator's own **block state** (FIX-914).
> Both primitives landed, so FIX-911 is unblocked. This change is **additive**:
> the new `createSkillsLibrary` + `.config()` surface lands alongside the
> existing session-global `createSkillsCapability`, which is unchanged (the
> migration keeps v1 working for in-flight requests and existing consumers).

## 1. TLDR

**Plain-language.** Today skill activation goes into one shared bag every agent
reads → cross-generator bleed. New model: a shared skills **library**, and each
generator **configures** which skills it has and how. Preloaded skills are on
from the start; skills the agent may load mid-task live in a named piece of
state (default: the generator's own block state); a small opt-in installs the
load tool. No shared bag, no framework guessing which generator is which.

**Technical.** Add a shared skills **library** (`createSkillsLibrary`) and a
per-generator binding via `library.config({ active, allowed, activeState })` +
`library.presets({ dynamicActivation })`, built on the capability-config
primitive (FIX-915). Dynamic activation is stored in the author-named
`activeState` field, defaulting to the generator's **block state** (FIX-914).
The `/skill` + keyword matcher stays an upstream block writing an **explicit
shared** `activeState`.

## 2. Overview

Skills are reusable instruction playbooks injected as context into an LLM
generation. The legacy path activates into a **session-global** registry shared
by every generator → cross-generator bleed + cross-turn persistence. This moves
binding to be **configured per generator**; isolation is by configuration and
block-namespaced state, not framework-derived identity.

## 3. Key decisions

- **Bind through capability config, not session-global/structural keying**
  (depends on FIX-915). An earlier "structural per-generator keying" design (a
  request slot keyed by an `ownerGeneratorKey` stamped into the tool executor)
  was superseded — it faked a per-generator state scope and leaked in many
  places (unreliable `ownedBy`, per-attempt re-keying, request state lost on
  resume, upstream activator can't see the id).
- **`activeState` (where) is separate from `dynamicActivation` (the LLM tool)** —
  preserves the code-drives-state and upstream-matcher cases.
- **Un-configured `dynamicActivation` defaults to block state** (FIX-914). The
  load tool runs as a child of the generator and writes the parent's block
  state via `ctx.parent`; the reader runs in the generator's scope and reads
  `ctx.self`.
- **Shared library + per-generator config; presets ride alongside config.**
- **Pattern/fork untouched** (FIX-910). Fork/pattern dispatch stays on the
  `runSkill` router; the inline binding is inline-only.

## 4. Technical design

**Surface.**

```ts
const skills = createSkillsLibrary({ catalog, initialSkills });                 // installed once
generator({ uses: [ skills.config({ active: ["detailed-analysis"] }) ] });      // static only
generator({ uses: [ skills.config({ allowed: ["deep-research"] }).presets({ dynamicActivation: true }) ] });
skills.config({ activeState: { scope: "session", field: "activeAnalystSkills" } }); // code / upstream-driven
```

- `active` — render bodies **+ contribute the skills' declared `allowed-tools`**
  (omitted = full catalog). **Inline-mode skills only.** No runtime state, no
  activation tool. Resolution **fails loud** on a missing/typo'd skill.
- `allowed` — the catalog the load tool may pull from. Also contributes those
  skills' declared catalog tools. Omitted = full catalog.
- `activeState: { scope, field }` — where dynamic activations live; mode + input
  + source-bearing.
- `presets({ dynamicActivation })` — installs the load tool (**inline-mode only**;
  a fork/pattern skill in `allowed` is rejected). Storage → block state when
  `activeState` omitted.

The skills capability defines a **config resolver** (FIX-915) mapping settings →
contributions and owning compose semantics (explicit `activeState` overrides the
block-state default; contributed `context` / tools add).

**Reader.** Renders `active` bodies + the `inline`-mode entries in `activeState`.
`activeState` is re-read on every tool-loop step (the generator re-resolves
dynamic context in `prepareStep`), so a skill the load tool writes mid-loop
injects on the *next* step of the same execution, not a later turn. Entries
carry **mode, input, and source**: only `inline` renders; the input arg is
substituted into `$ARGUMENTS`; the source tier drives the badge label.

**Writers.** *LLM (with `dynamicActivation`)*: the tool runs as a child block, so
it writes the parent generator's block state via `ctx.parent` (FIX-914) or the
configured `activeState`. *Upstream matcher / code*: runs before/outside the
generator, so it **cannot** write the generator's block state — it **requires an
explicit shared `activeState`** and must be **scoped to the binding's `allowed`
set**.

**Delivered-primitive gaps.** (1, FIX-914 PR1) A capability cannot yet
contribute an own-block `stateSchema` to its host generator, so the block-state
default requires the author to declare `stateSchema: z.object({ activeSkills:
activeSkillsArraySchema })` on the generator (documented). (2, FIX-915) A config
resolver's returned surface reaches only the generator's context/tools — the
framework does not apply a merged-surface `sessionStateSchema` to the block
state contract — so the explicit `activeState` binding does **not** turnkey a
scope state schema. The field is declared where it's written: the upstream
matcher declares its scope schema on its own block; a code/generator writer
declares it on the flow/generator's own `sessionStateSchema`. The reader
tolerates an absent field. **Live mode is enforced at render:** a skill edited
to fork/pattern after binding renders `null` (not `<active_skill>` context),
keeping the inline-only contract against the live manifest.

**Migration.** Legacy `activeSkills` (session-global) is unchanged; new bindings
use the config model. The pattern board pointer is untouched (FIX-910).

## 5. What shipped

New `@flow-state-dev/orchestration` surface:

- `createSkillsLibrary(options)` → a `DefinedCapability` with a config resolver
  and a `dynamicActivation` preset. Library owns seeding (`initialSkills` seeded
  on a binding's first render).
- `skills.config({ active, allowed, activeState })` resolver — `active` → static
  reader + declared tools + fail-loud; `allowed` → load-tool catalog + declared
  tools; `activeState` → `<scope>StateSchema` contribution + read/write wiring.
- `createLoadSkillTool` (the inline `loadSkill` tool, distinct from the v1
  `runSkill` router), `buildSkillBindingReader`
  (static + dynamic reader), `activation-store` (`readActivations` /
  `appendActivation` / `replaceActivations` over block vs explicit locations).
- `createSkillActivator({ activeState, allowed })` — the up-front matcher can
  write an explicit shared field scoped to the binding's allowed set.
- Shared `renderActiveSkillBody` (the legacy formatter now reuses it).

## 6. Edge cases

Two generators, different `active` → each only its own. `dynamicActivation` + no
`activeState` → block state (author declares `stateSchema`). + explicit
`activeState` → uses it. Upstream matcher → requires an explicit shared field +
`allowed` scoping. Activation input arg → round-trips into `$ARGUMENTS`; source
tier round-trips for the badge. Mid-loop load → injected on the next step of the
same execution. A missing/typo'd static `active` skill → fails loud. A fork/
pattern skill in `active`/`allowed` → rejected.

session-global path and its consumers (staged follow-up).
