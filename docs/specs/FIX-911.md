# FIX-911: Skills v2 — move off session-global activeSkills to per-generator scoped binding — Implementation Spec

## 1. TLDR

**Plain-language summary.** Today, when an agent "activates" a skill (a reusable
instruction playbook), that activation is written into one shared bag that every
agent in the conversation reads from. So in a multi-agent setup, one agent's
skill leaks into another agent's instructions, and the activation sticks around
for the rest of the conversation whether you want it or not. This change makes a
skill bind to a single agent by construction: you declare which skills an agent
can use where you define that agent, and each agent carries only its own. There's
still a path for an agent to pick up a skill mid-task, but the pickup now stays
local to that agent and that turn instead of going into the shared bag.

**Technical statement.** Replace the session-global `activeSkills` state slice
with per-generator-scoped skill binding: a declarative construction-time path
(`uses: [skills.bind(["name"])]`) that injects skill bodies as static context
with no runtime state, and a re-scoped agent-driven path that writes to
request-state keyed by the generator's block-instance id rather than session
state.

**Deliverables (grouped by area, mirrors §5):**

- **Core (`@flow-state-dev/core`):**
  - Promote a stable per-block-instance identity onto the public `BlockContext`
    surface (`ctx.self.instanceId`) so capability context formatters can read a
    generator-scoped key without touching `@internal` `_blockIdentity`.
- **Orchestration (`@flow-state-dev/orchestration`) — skills:**
  - Move the **inline** skill-body binding slot to `requestStateSchema` keyed by
    block-instance id, in
    `packages/orchestration/src/skills/active-skill-state.ts` and `capability.ts`
    (the session `activeSkills` schema is retained for the shared pattern pointer).
  - Rewrite `context-fn.ts`'s active-body formatter to read the per-instance slot.
  - Route the two **inline** writers (`inline-activate.ts`,
    `apply-skill-activation.ts`) through one per-instance scoped-write helper;
    `pattern-run.ts` is left unchanged (its board pointer is cross-generator).
  - Add `createSkillsCapability(...).bind(names, opts?)` — a base-identity-preserving
    configured ref (single-ref, `staticBind` preset) that seeds then renders the
    named skills' bodies as static context (the declarative 90% path).
  - Rename the mid-loop `runSkill` inline path off the "run" misnomer
    (recommended `activateSkill`; **naming open**, see §11).
- **Docs:**
  - CREATE `apps/docs/docs/skills/binding.md` (the deferred "how skills bind" page).
  - EXTEND `skills/overview.md`, `skills/activation.md`, `skills/authoring.md`,
    `guides/adding-skills-to-your-app.md`, `packages/orchestration/README.md` to
    the scoped model.

**Size: Large** — multi-package (core + orchestration + docs), heavy test
churn. Suggested PR split: (PR1) scoped-slot substrate + `ctx.self.instanceId` +
agent-driven path migration + writer consolidation; (PR2) declarative `.bind()`
90% path; (PR3) docs. PR1 and PR2 can also land together if kept under ~500 LOC.
**PR1 alone fixes the cross-generator bleed** — `.bind()` (PR2) is the ergonomic
90% path and could be split to a sibling issue if the owner wants the smallest
epic (open question §11.2).

## 2. Overview

Linear issue: [FIX-911](https://linear.app/fixpoint-labs/issue/FIX-911/skills-v2-move-off-session-global-activeskills-to-per-generator-scoped)
(Orchestration Primitives project).

Skills are reusable instruction playbooks (a Markdown body plus an optional tool
allow-list) that get injected as context into an LLM generation. Today they are
"activated" into a **session-global** mutable registry (`activeSkills`, stored in
`session.state`) that every generator in the conversation shares and reads on
every step. This spec moves skill binding to be **per-generator, scoped by
construction**: the declarative path carries no runtime state at all, and the
minimal agent-driven "model picks a skill mid-loop" path writes to a
generator-scoped slot that resets each turn. This fixes cross-generator context
bleed in multi-agent flows and removes the activate/deactivate lifecycle the
session-global model forced.

## 3. Background & Research

### 3.1 How the current model works (and where it hurts)

- `active-skill-state.ts` stores `activeSkills` in **session state** — the header
  comment explicitly argues this is correct "so a multi-step request shares the
  activation set across iterations." That reasoning conflates two things:
  *survives the tool loop* (request scope also does this) with *session-global*
  (which additionally bleeds into sibling generators and persists across turns).
- `createSkillsCapability()` (`capability.ts:204`) declares
  `sessionStateSchema: activeSkillStateSchema`. The dynamic context formatter
  (`context-fn.ts:80-116`, `buildActiveSkillsContext`) reads
  `ctx.session.state.activeSkills` fresh on every generator step, so a mid-loop
  activation shows up on the next step's system prefix. This re-run happens via
  the generator's `prepareStep` machinery (`generator.ts:2804-2871`), which
  re-resolves function-form context slots each step > 0.
- **Three writers** touch the slot with subtly different semantics:
  `inline-activate.ts:41` (append-dedup), `pattern-run.ts:213` (append-dedup for
  pattern metadata), `apply-skill-activation.ts:76` (up-front router, replace).
  One reader: `context-fn.ts:84`.
- `runSkill` conflates three behaviours: `inline` (an *activation* — patches the
  slot, persistent, doesn't "run"), `fork` (subagent generator — self-contained,
  writes no state), `pattern` (task-board strategy — writes `ActivePatternMeta`).

### 3.2 The extension seam already exists (`uses` capabilities)

Orchestration extends the core `generator` block **through a capability listed in
`uses`** — core's config schema is never touched. `defineCapability` can already
contribute request-scoped state (`requestStateSchema`) and sequencer-scoped state
(`sequencerStateSchema`), not just session state (`packages/core/src/capability/types.ts:64-99`).
There is **no per-block-instance state scope**, and adding one (a new scope across
stores/CAS/SSE) is explicitly out of scope. The realistic finer-grained slot is
**request state keyed by block-instance id**: request scope spans one action
execution (so it survives a generator's whole tool loop), and keying by the
generator's own instance id isolates siblings and auto-resets each turn.
Precedent for request-state-keyed-by-activation already exists in
`pattern-run.ts:169-183` (`nextSkillCollectionId` reaches into `ctx.request.state`
+ `request.identity.id`).

### 3.3 Industry validation

The target design is where the ecosystem has converged:

- **Anthropic Claude Agent SDK** (whose `SKILL.md` format this framework mirrors):
  skills are controlled by a `skills` option **per `query()`** — "a context
  filter" on that call — and **subagents do not inherit the parent's skills**
  unless explicitly listed. Skill invocation is temporary and scoped to the agent
  loop, with "no residual behavioral modifications" afterward. This is
  per-generator declarative binding, from the closest analog.
  ([engineering blog](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills),
  [SDK skills docs](https://code.claude.com/docs/en/agent-sdk/skills))
- **OpenAI Agents SDK / Mastra**: tools and instructions are owned per-agent at
  construction; guidance explicitly warns against sharing a tool across agents in
  different domains (data-exfiltration risk). Per-request variation flows through
  an explicit injected context object, never a mutable global.
- **Shared-mutable-state pitfalls**: multi-agent concurrency studies attribute a
  large share of failures to shared-state consistency errors (silent
  last-write-wins overwrites with concurrent writers). The recommended fix is
  exactly this direction: eliminate the shared cell, partition per-execution.
- **Mid-loop model selection stays local**: Claude's Skill tool injects the body
  into the *invoking agent's* context window only; the effect falls away when the
  loop moves on. Per-loop injection also shrinks the prompt-injection blast radius
  versus a global bag.
- **Enforce scope at execution, not just prompt assembly**: the Vercel AI SDK
  `activeTools` bug (a filter that trims the offered set but still executes the
  full tool object) is a cautionary note — a skill's tool allow-list must gate the
  actual execution path, not only the prompt.

### 3.4 Why this approach over alternatives

- **Static context for the declarative path (no state)** over request-state for
  everything: the 90% case binds a known skill at construction, so its body is a
  pure static context contribution — sibling isolation is automatic and there is
  nothing to reset. Reserve mutable (request) state for the genuinely dynamic
  "model picks mid-loop" path only.
- **Request-state-keyed-by-instance-id** over a new per-block scope: reuses the
  existing request scope + the existing `prepareStep` re-run; a new scope is a
  large cross-cutting change (BP-029 compose existing primitives).
- **`uses: [skills.bind([...])]`** over a first-class `generator({ skills })` key
  on core: a bare `skills:` key on `GeneratorConfig` either needs a global skills
  registry or a general "capability contributes typed config keys to blocks" seam.
  Both are heavier, and a plugin-owned key on core's generator type directly
  contradicts the issue's own constraint ("no new keys get bolted onto core's
  generator type by a plugin"). `.bind()` needs zero core change and is nearly as
  ergonomic (BP-038 build the least).

### 3.5 Key Decisions & Ramifications (top 5)

1. **Binding slot moves session → request-state keyed by block-instance id (for
   the dynamic path); the declarative path carries no state.**
   *Alternative rejected:* add a new per-block state scope.
   *Ramification:* fixes cross-generator bleed and cross-turn persistence; the
   dynamic activation now **resets every turn** (a deliberate behaviour change —
   see edge cases). Locks in a dependency on a stable per-instance id being
   available to capability formatters (Decision 2). Does not require store/CAS/SSE
   changes.

2. **Promote a public `ctx.self.instanceId` on `BlockContext`**, sourced from the
   existing `@internal` `_blockIdentity.blockInstanceId`.
   *Alternative rejected:* have the skills capability reach into `_blockIdentity`
   directly.
   *Ramification:* a small, permanent addition to core's public context surface
   (mirrors the already-public `StateRef.instanceId` for sequencers). Any future
   capability that wants per-generator-instance state reuses it. Underscore-prefixed
   internal stays internal.

3. **Declarative 90% path is `uses: [skills.bind(["name"])]`; the first-class
   `generator({ skills: [...] })` key is deferred** to a separate "capability
   contributes typed config keys to blocks" primitive.
   *Alternative rejected:* ship the bare `skills:` key now.
   *Ramification:* keeps core's generator type free of plugin-owned keys (honours
   the issue's constraint) and avoids building a general seam speculatively. Costs
   a slightly longer call site than the issue's stated ideal. **This is the main
   open question (§11) — flagged for the issue owner.**

4. **`.bind(names)` is a preset-configured variant of the *single* skills ref
   (via `Object.create`, like `.presets()`) — not a second capability, and not a
   union across multiple `.bind()` refs.**
   *Alternative rejected:* return a fresh `defineCapability({ name: "skills", … })`
   per call, or rely on two `skills.bind([...])` refs on one block merging to a
   union.
   *Ramification:* capability merge dedups by base reference and, on re-seeing the
   same base, **early-returns without merging the second ref**
   (`merge.ts:92-95`) — so `[skills.bind(["a"]), skills.bind(["b"])]` is
   *first-wins*, never a union, and `[skills.bind(["a"]), skills]` silently drops
   one ref. Therefore: **bind all names in one call** (`skills.bind(["a","b"])`),
   and express "statically bind X *and* let the model pick more" as an **option on
   the same ref** (`skills.bind(["a"], { modelPick: true })`), not two refs. Base
   identity is preserved so a single bind avoids the same-name-different-reference
   error and its names reach the formatter via a function-form preset override.
   Two `.bind()` refs on one block is a **documented first-wins / lint-worthy
   mistake**, not a supported union.

5. **Fork and pattern modes keep working, untouched. Only the *inline
   context-injection* binding moves to the per-instance slot; the shared pattern
   *board pointer* stays in its current shared slot.**
   *Alternative rejected:* fold all three writers behind one per-instance helper.
   *Ramification:* `ActivePatternMeta` is a **cross-generator** pointer — a task
   board is shared by construction, and `getActivePatternMeta`
   (`active-pattern-collection.ts:45-55`) reads it *globally* for every `taskTools`
   mutator (`task-tools-capability.ts:37-41`), including worker generators on a
   different instance id and cross-turn reconnection of a resource-backed board.
   Keying it per-instance would break exactly that. So `pattern-run.ts`'s writer is
   **excluded** from the per-instance helper and its reader is left on the shared
   slot. FIX-911 relocates only the skill-body binding (`inline-activate.ts`,
   `apply-skill-activation.ts`); the pattern semantic reshape stays with FIX-910.

### 4.2 Data flow

**Declarative path (90%, no state):**

```
build time:  generator({ uses: [skills.bind(["research"])] })
             → skills.bind renders a static `context` entry (base ref "skills")
runtime:     each step → the static context entry emits the "research" body
             under the <skills> tag. No read/write of any mutable slot.
             Sibling generators each carry their own bound context.
```

**Agent-driven path (dynamic, request-scoped):**

```
step N:   model calls activateSkill({ name })
          → scoped-write helper appends an ActiveSkillEntry under
            [SLOT][ctx.self.instanceId] via ctx.request.patchState
            (CAS-safe, task-board style — not a raw request.state mutation)
step N+1: prepareStep re-runs buildActiveSkillsContext, which reads
          ctx.request.state[SLOT][ctx.self.instanceId] → renders the body.
          A sibling generator (different instanceId) sees nothing.
end of turn (request ends): the slot is gone. Next turn starts clean.
```

### 4.3 API surface

```ts
// capability.ts — the configured capability gains a per-generator binder.
export interface DefinedSkillsCapability extends DefinedCapability {
  /**
   * Bind an explicit set of skills to one generator, by construction.
   * Returns a base-identity-preserving *configured* ref (same base as the
   * capability) whose `staticBind` preset renders exactly these skills'
   * bodies as static context. No runtime state.
   *
   * Bind ALL names in one call — two `skills.bind([...])` refs on one block
   * do not union (merge keeps the first, drops the rest). By default the
   * mid-loop `activateSkill` tool + catalog are turned OFF for a bound
   * generator (pure declarative). Pass `{ modelPick: true }` to keep them on
   * so the model may additionally pick skills mid-loop.
   */
  bind(
    names: readonly string[],
    opts?: { modelPick?: boolean },
  ): ConfiguredCapability;
}
// The `staticBind` preset MUST be pre-declared in the base capability's
// presets map (even as an empty shape), or resolveActivePresets throws
// "Unknown preset" (merge.ts:158-164). `.bind()` enables `staticBind` and,
// unless modelPick, disables the default `runSkill` preset.

const skills = createSkillsCapability({ catalog, initialSkills /* … */ });

// 90% path — declarative, per generator:
const researcher = generator({
  name: "researcher",
  model: "openai/gpt-5.4-mini",
  uses: [skills.bind(["research"])],
});

// Mid-loop path — model may pick a skill during its own loop; scoped to
// this generator, resets next turn:
const assistant = generator({
  name: "assistant",
  model: "openai/gpt-5.4-mini",
  uses: [skills], // full capability incl. activateSkill tool + catalog
});
```

Request-state schema for the **inline binding** (the session `activeSkills`
schema is retained for the shared pattern pointer, unchanged):

```ts
// keyed by block-instance id; value is the per-generator activation list.
export const inlineBindingRequestStateSchema = z.object({
  activeSkillsByInstance: z
    .record(z.string(), z.array(activeSkillEntrySchema))
    .optional()
    .default({}),
});
```

A new `readInlineBindings(state, instanceId)` + per-instance scoped-write helper
serve the inline binding; `unionAllowedTools` narrows to the calling generator's
entries. The existing `readActiveSkills(state)` (single-arg, session) stays for
`getActivePatternMeta` — do **not** change its signature.

*Typing note:* capability state type-forwarding covers `sessionStateSchema` but
**not** `requestStateSchema` (`capabilities.md:84-89`). The inline slot therefore
won't reflect into consumer `ctx` types — the formatter/helpers read it via an
inline cast (as `pattern-run.ts:170-174` already does). Functionally fine;
acknowledged asymmetry, not a blocker.

### 4.4 State management

- **Declarative path:** no mutable state. The static formatter still performs an
  **async collection read** (and `ensureSeeded`) to fetch bodies — "no state" ≠
  "no async read." **Perf:** the "no per-step cost" win only holds if `.bind()`
  contributes bound bodies as a **non-function** context value (resolved once at
  assembly / first step). A function-form formatter like today's
  `buildActiveSkillsContext` keeps `hasDynamicContext` true, so `prepareStep`
  rebuilds the system prefix every tool-loop step — the implementer should resolve
  bound bodies eagerly (names are fixed at bind time) and reserve the function form
  for the dynamic mid-loop path.
- **Dynamic path:** `request` scope (ephemeral, one action execution), keyed by
  `ctx.self.instanceId`. No session, user, or org writes for skill binding. The
  slot is persisted to the request store, so an activation survives not just steps
  but a tool-approval suspension/resume.
- **`ctx.self.instanceId`:** deterministic per `(generator instance, attempt)`
  within a request (`${requestId}:${path}:${attempt}`; already computed for
  `_blockIdentity`). Read-only for consumers. A whole-generator **retry**
  re-enters with a new instance id, orphaning the pre-retry slot — self-heals (the
  model re-activates on the re-run) and the orphan is inert.

### 4.5 Error handling

- **`ctx.self.instanceId` absent** (older host / non-generator context): to keep
  the scoped invariant the *default*, **fail closed in production** — throw a clear
  "skills binding requires a stamped block identity" error rather than silently
  sharing a slot (a shared `"_"` key would reintroduce the very bleed this fixes
  when two unstamped siblings collide). The shared-key fallback is **test-only**
  (mock contexts that don't stamp identity). In well-formed flows identity is
  always stamped, so production never hits the throw.
- **`.bind()` names a not-yet-seeded bundled skill:** the static formatter
  `ensureSeeded`s first, so bundled `initialSkills` render on turn 1. (Without
  seeding, the declarative-only path — no `runSkill`/catalog present — would render
  empty until some other path seeded the collection.)
- **`.bind()` with a genuinely unknown skill name** (not in `initialSkills`, not
  seeded): the formatter skips it and logs a dev warning (matches the `getOptional`
  skip in `context-fn.ts:92`); no build-time throw.
- **Two `.bind()` refs on one block:** merge keeps the first, drops the rest
  (first-wins, **not** a union) — a documented mistake; bind all names in one call.
  A lint/dev-warning on duplicate base refs is a nice-to-have.
- **Skill tool allow-list vs generator tools:** unchanged from today —
  `unionAllowedTools` computes the restriction from the calling generator's
  entries only. (Enforcement-at-execution is noted as a follow-up, §8.)

## 6. Edge Cases & Error Handling

| Case | Expected behaviour |
| --- | --- |
| Two sibling generators, each `.bind()` different skills | Each renders only its own; no bleed. |
| Sibling generators sharing the full `skills` cap; one activates mid-loop | Only the activating generator's next step renders it; sibling unaffected (distinct instance id). |
| Same generator activates a skill, then a new turn begins | Inline activation is gone (request-scoped). Re-activation required. **Behaviour change from v1** (was persistent) — intended, matches "mid-loop" framing. |
| Whole-generator retry after an activation | New instance id; pre-retry slot orphaned (inert). Model re-activates on the re-run — self-heals. |
| `.bind()` names a bundled-but-unseeded skill | Rendered (formatter seeds first). |
| `.bind()` names a genuinely unknown skill | Formatter skips it, dev warning; no throw. |
| Two `.bind()` refs on one block | First-wins (merge drops the rest) — a documented mistake, not a union. Bind all names in one call. |
| `skills.bind([...], { modelPick: true })` | Static bodies **and** the `activateSkill` tool; bare `.bind()` is static-only. |
| Host context without `ctx.self.instanceId` | Production: fail closed (throw) — never silently share a slot. Test-only: shared key `"_"` for mock contexts. |
| In-flight session with a v1 `session.state.activeSkills` inline value at deploy | Ignored by the new inline reader; the stale slice is inert. No persisted-data migration needed (activations are ephemeral). Documented. |
| Pattern/fork mode invoked | Works exactly as today — pattern pointer stays on its shared slot; fork is self-contained. Semantic reshape deferred (FIX-910). |

**Error taxonomy:** all skill-binding failures are non-fatal to the turn
(skip + warn); binding is additive context, never a hard precondition. No
retryable/fatal distinction is introduced.

## 7. Testing Strategy

**Goal.** In a flow with two generators, a skill bound to (or activated by) one
generator must never appear in the other's context, and an activation must not
persist into the next conversation turn.

**Goal check (required, real-model, out-of-CI).** A `goals/` script
(`goals/skills-scoped-binding/no-cross-generator-bleed/run.mts`, per
`goals/README.md`) that runs a real two-generator flow: generator A binds/activates
a distinctive skill (e.g. one whose body instructs a recognizable output token),
generator B does not. Drive a real turn and assert generator B's output shows
**no** trace of A's skill instruction, and that a second turn on A starts without
the prior activation. Prints PASS/FAIL on the bleed check. This is the observable
outcome mocked specs cannot prove.

**Discipline: `fsd:tdd`.** Behaviours to test (each a tracer-bullet cycle):

## 11. Open Questions

1. **First-class `generator({ skills: [...] })` sugar — ship now or defer?**
   (Main question for the issue owner.) The issue names `generator({ skills })` as
   the 90% path *and* says "no new keys get bolted onto core's generator type by a
   plugin." Those conflict unless we build a general "capability contributes typed
   config keys to blocks" seam. This spec recommends **`uses: [skills.bind([...])]`
   now** (zero core change, honours the no-plugin-keys constraint) and **defers the
   bare `skills:` key** to that general primitive as its own issue.
   - *Option A (recommended):* ship `.bind()`, open a follow-up for the general seam.
   - *Option B:* build the general typed-config-key seam in this issue so bare
     `skills:` lands now (larger; touches core generator + merge).
   - *Option C:* thin skills-specific `skills:` key on `GeneratorConfig` that
     desugars against a `skills` cap already in `uses` (rejected — a plugin concept
     leaking a key onto core, against the issue's constraint).

2. **Is the declarative `.bind()` path (PR2) in scope for FIX-911, or a sibling
   issue?** **PR1 alone fixes the cross-generator bleed** (scoped dynamic slot +
   writer migration + rename); apps keep working with `uses: [skills]` + the
   up-front activator. `.bind()` + the `staticBind` preset is a second binding
   pipeline that buys the ergonomic 90% path but is *not required for the defect*.
   - *Option A (spec default):* ship `.bind()` in PR2 within this issue (owner gets
     the ergonomic path in the same epic).
   - *Option B:* land PR1 only here; move `.bind()` to a follow-up issue for the
     smallest epic.

3. **Naming.** The issue says don't lock a specific decomposition prematurely.
   Recommended: rename the mid-loop inline tool `runSkill` → `activateSkill`;
   binder method `skills.bind(names)`. Alternatives considered: `useSkill` /
   `skills.only(names)` / `skills.for(names)`. Decide before docs.

**Closed decision (was open):** *Dynamic activation resets each turn.* Consumer
audit done — the only writer of inline activations besides the mid-loop tool is the
up-front `createSkillActivator`, which re-runs per turn and re-populates; no
consumer relies on a skill staying active across turns. Request-scoping is the
decided behaviour (see §4.2, §6), not an open question.
