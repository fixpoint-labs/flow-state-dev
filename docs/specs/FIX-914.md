## 1. TLDR

**Plain-language summary.** Today only one kind of building block — a "sequencer" (a block that runs other blocks in sequence) — gets a private scratchpad it can keep notes in while a request runs. Every other kind of block has nowhere clean to keep its own notes, so authors borrow the enclosing sequencer's scratchpad and hand-label fields to avoid clashes. This change gives *every* block its own scratchpad, and gives it two obvious handles: a block reads and writes its own notes through `ctx.self`, and a block reads or writes its immediate parent's notes through `ctx.parent`. Those two are the same scratchpad seen from either side — a router writes `ctx.self`, and the block it routes to reads the same thing as `ctx.parent`.

**One-sentence technical statement.** Generalize the per-execution-scope state container — today gated to `kind === "sequencer"` — to any block that declares an own-state schema, and expose that container through two new handles, `ctx.self` (own) and `ctx.parent` (immediate parent, gaining state ops), alongside the existing `ctx.sequencer` (nearest sequencer) and `ctx.targets`/`getTarget` (by name), which already resolve over the same container mechanism.

**Deliverables.**

- *Core (types):* Add `ctx.self: StateRef<TSelf>` (own state, from the block's `stateSchema`) and give `ctx.parent` state ops `ctx.parent: { name; kind; input } & StateRef<TParent>` (from a new `parentStateSchema`) to `BlockContext` in `packages/core/src/types/block.ts`; thread the generics through the `handler` / `generator` / `router` / `sequencer` factories (DSL callbacks inherit them).
- *Engine (runtime):* Lift the four container-creation gates (`createExecutionContext.ts:2773-2778`, `sequencer.ts:614`, `executeBlock.ts:301`, `tool-executor.ts:165`) from `kind === "sequencer"` to "any block whose *effective* (config + capability-merged) `stateSchema` is present"; bind `ctx.self` directly to that scope node's container and `ctx.parent` to the immediate parent scope node's container.
- *Engine (live emit):* Reuse the already-generic `state_change` path (`scope-emit.ts`, `scope: "block_instance"`) + transient stripping for non-sequencer containers. **Note:** these items are transient-by-default in production (`shouldPersistScopeChange`), so they are *not* a client-visible projection — client visibility of block state is a non-goal here (see §8 / §10).
- *Core (capability seam — PR2):* Add a new own-state `stateSchema` field to the capability/preset surface + a `mergeSurfaceInto` rule + **explicit duplicate-field collision detection** (today `.extend()` silently last-wins) + wire `mergedSurface` into the block's effective schema (today the merged surface is unconsumed except for the generator's context/tool entries). **This is FIX-911's actual dependency** — the skills capability contributes the generator's `stateSchema`.
- *Contract:* State the **fan-out / loop contract** — a loop-owner accumulates in `ctx.self`; a loop-body / fan-out iteration gets a fresh isolated cell per pass — with a regression test.
- *Docs:* CREATE `apps/docs/docs/advanced/block-state.md`; EXTEND the two specialization pages + overview + core/orchestration READMEs + `docs/architecture/state-and-scopes.md`.

**Size: Large** — concentrated in load-bearing engine state plumbing, but mostly *generalizing three gates + adding two handles*, not new subsystems. Split: **(PR1)** the primitive — three gates + `ctx.self` + `ctx.parent`-state + in-memory live emit + fan-out/loop contract + tests; **(PR2)** the capability own-state seam (contributes a generator's `stateSchema` via `uses`, with collision detection) — **FIX-911 needs PR1 *and* PR2**, since its skills capability, not the generator author, declares the state. **(Follow-up, not PR1)** durable checkpoint + suspension-boundary persistence for non-sequencer block state (no PR1 goal needs it; see §5). **(PR3)** docs.

## 2. Overview

Flow State Dev has four identity scopes (`request` / `session` / `user` / `org`) plus an execution-lifetime state container that today only sequencers get. Blocks that want their own private state — a generator tracking what it has loaded across its tool loop, a converge-style sequencer counting its own drain passes, a router recording where it routed, a fan-out body needing scratch that never leaks to a sibling — have no clean home, so they borrow the enclosing sequencer's state and hand-namespace fields.

This spec makes the execution-lifetime container a property of *any* block that declares an own-state schema, and gives it a symmetric pair of local handles: `ctx.self` reads/writes a block's own container; `ctx.parent` reads/writes the immediate parent's. They are the same container seen from either side. `ctx.sequencer` (nearest sequencer) and `ctx.targets`/`getTarget` (by name) are the longer-range addressing sugars, already implemented as `getTarget(...)` over this exact mechanism. So the change is **one runtime primitive with four addressing modes** — the resolution layer is already unified; this completes it at the container-gate and the local (`self`/`parent`) handles. It unblocks FIX-911 (a generator holds its own `activeSkills`; its activation tool writes them via `ctx.parent`) and simplifies FIX-910 (a converge sequencer's drain counter is its own `ctx.self` state).

**Honest scope note (net-shrink is runtime-only for now).** The *runtime* collapses onto one container mechanism, but the *config surface* does not shrink in this spec — it grows by `parentStateSchema`, and `sequencerStateSchema` / `targetStateSchemas` stay. Consolidating those four declaration keys into one addressing surface is the deferred "audit-then-remove" follow-up (§8), done only once consumers are re-expressed and proven.

## 3. Background & Research

### 3.1 How this works in the codebase today

- **The container gate is sequencer-only.** A `MemoryStateContainer` is created only when a scope's block `kind === "sequencer"` and it has `config.stateSchema` (`createExecutionContext.ts:2773-2778`, threaded through `sequencer.ts:614` and `executeBlock.ts:301`). Handlers/generators/routers never get one. **This gate is the primary thing FIX-914 generalizes.**
- **Resolution is already unified.** `ctx.sequencer` is literally `getTarget(nearestSequencerName)` (`createExecutionContext.ts:3174-3191`); `ctx.targets.<name>` is a `Proxy` forwarding to `getTarget` (`:2443-2457`). `getTarget` resolves siblings-first then ancestors and throws `AmbiguousBlockNameError` on duplicate names (`:2509-2541`). So "unify sequencer/parent/target" is *already done at the resolution layer* — the fragmentation is only in the container gate and the declaration keys.
- **`ctx.parent` exists but is stateless.** `ctx.parent` today carries only `{ name, kind, input }` (`block.ts:238-242`; getter at `createExecutionContext.ts:3193-3203`). FIX-914 gives it state ops over the immediate parent's container.
- **The container is per-execution-scope-node.** It hangs on `ExecutionParentNode.parentStateContainer` (`createExecutionContext.ts:2000, 2773-2778`), one per block invocation, surfaced by name through `getTarget`. In-memory only (`MemoryStateContainer`, `state-container.ts:52-81`; the no-CAS FIFO-lock mutation path lives in `createScopeStateOps`, `state-container.ts:219-416` — never `ConcurrentModificationError`); durability rides a separate `state_snapshot` checkpoint (`emitStateSnapshot`, `sequencer.ts:257-356`).
- **`config.stateSchema` already means "this block's own state."** It exists on every `BlockConfig` (`block.ts:728`) but is honored only for sequencers. `sequencerStateSchema` (`handler.ts:63`) and `targetStateSchemas` (`handler.ts:73`) are **type-only** read-declarations; they create no container.
- **Tool calls are child scope nodes of their generator.** `tool-executor.ts:150-168` gives each tool `extendBlockPath(parentPath, blockPathTool(...))` — a genuine child scope node. So an in-generator activation tool's *immediate parent* is the generator: once the generator has a container, `ctx.parent` (or `ctx.targets.<generatorName>`) reaches it. No "nearest-ancestor-of-type" resolver is needed.
- **Identity is retry-stable via the path.** `blockInstanceId = ${requestId}:${path}:${attempt}` (`contracts/block-instance-id.ts:50-56`); `path` excludes `attempt`. In-flow child instanceIds are built with `attempt: 0` (`sequencer.ts:420`); only the engine root dispatch carries an incrementing `attempt` (`executeBlock.ts:206-214`). `ctx.idempotencyKey` (public) = `${requestId}:${blockPath}` is a ready-made retry-stable key. Fan-out copies already get distinct scope nodes (`forEach[i]/iter[j]`, `parallel[i]/branch[j]`); `loopBack` re-runs get a `loop[N]` prefix while the loop-owner's own container is untouched (`sequencer.ts:382-398`).
- **The checkpoint STORE keys on provenance, not `item.key`.** The durability hook writes/deletes checkpoints under `item.provenance.blockInstanceId` (`runAction.ts:718`, `.write({ blockInstanceId })` / `.delete(requestId, blockInstanceId)`), *not* the streamed `item.key` (which is the client dedupe key). Restore loads `stores.checkpoints.latest(..., suspension.blockInstanceId)`, and `blockInstanceId` is stamped from the sequencer instance id today. This is why non-sequencer durable/suspend-resume state is a **new, larger piece of work**, deferred (§5).
- **Capability state schemas are type-only.** `defineCapability` copies `sequencerStateSchema`/`requestStateSchema`/`targetStateSchemas` (`define-capability.ts:74-84`) and `mergeCapabilities` merges them (`capability/merge.ts:316-417` via `extendSchema`, `:271-284`), but **no factory consumes the merged state schemas at runtime** — only the generator reads context/tool entries (`generator.ts:2581-2602`). And `extendSchema` uses Zod `.extend()`, which **silently last-wins on duplicate fields** — it does not throw on conflict. FIX-911's skills capability needs a container created from a capability-contributed schema, with real collision detection.

### 3.2 Industry research

Comparable systems key per-node private state and handle fan-out consistently:

- **LangGraph** keys checkpoints by a `|`-joined node **path** (`checkpoint_ns`), disambiguates fan-out (`Send`) by **index within a superstep**; per-branch state is **private by default**, merged only through explicit reducers.
- **Inngest** keys each step by a **string id** plus a **per-id occurrence counter** — name + occurrence, retry-stable.
- **React hooks** = identity-by-position within a stable fiber; the **`key` prop** is the explicit fan-out disambiguator. Lesson: *position/path for the common case, an explicit stable discriminator for fan-out.*
- **XState / AWS Step Functions Map** — isolate-per-instance on fan-out, aggregate at fan-in.

The universal rule: **isolate per instance on fan-out; merge explicitly at fan-in.** FSD's per-scope-node container model already realizes this — each fan-out iteration is a fresh scope node, so its container is private by construction. FIX-914 uses **path/scope-node identity** (not a bolt-on name+index) because block state is **request-scoped** — there is no cross-run/cross-code-version replay window where path fragility bites.

### 3.3 Why this approach over alternatives

Generalize the existing per-scope-node container and its gate (BP-029: compose the existing primitive), rather than (a) a fifth `ScopeType` (heavyweight new store/keys/persist for a *partition of one request*, not a new identity axis) or (b) a name→cell request sub-namespace (re-implements the scope-node container + `getTarget`). The `ctx.self` / `ctx.parent` duality reuses the container both directions with no new resolver. Defer removing the legacy declaration keys to a later audit-then-remove issue (the issue's explicit discipline).

### 3.4 Key Decisions & Ramifications (top 5)

1. **Generalize the per-scope-node container gate; do NOT add a fifth scope.** Block state is a `MemoryStateContainer` on any stateful block's scope node, exactly as sequencer state is today. *Locks in:* in-memory FIFO-lock (no `ConcurrentModificationError`) + `state_snapshot` model inherited for free. *Ramification:* the three sequencer-hardcoded gate sites must be lifted together.
2. **Two local handles, `ctx.self` (own) + `ctx.parent` (immediate parent, gains state), as duals over one container.** A block writes its own state via `ctx.self` (handler/router `execute`, sequencer callbacks; generators read-only in config fns); a child reaches that same container upward via `ctx.parent`. *Rejected:* `ctx.self` alone with the child→parent write forced through `getTarget(name)` (works, but names the parent needlessly; the user's call is that `ctx.parent` is the ergonomic dual). *Ramification:* adds `parentStateSchema` — a new declaration key — so the config surface grows now; consolidation is deferred (§8). `ctx.self` is the public self handle FIX-911 was told to wait for. **`ctx.self` name is locked** (Decision, not an open question).
3. **Fan-out contract = private per iteration; loop/sequencer owner accumulates.** Emergent from per-scope-node containers: each `forEach`/`parallel` iteration and each `loop[N]` re-executed body is a fresh scope node (fresh container); a loop-owner keeps its single container across passes. *Rules out:* shared-across-siblings block state by default (the universal footgun). *Ramification:* a regression-test addition, not new complexity.
4. **The checkpoint STORE key is `provenance.blockInstanceId`, not `item.key` — so durable/suspend-resume for non-sequencer state is a distinct, deferred piece.** Retry-stable durability needs the durability hook (`runAction.ts:718`) to key on the path (a new storage-key field), the `state_snapshot` emit to carry a non-sequencer ref, *and* the suspension record + restore lookup to stamp the block's own path (today `blockInstanceId` is sequencer-stamped). None of PR1's goals need this. *Decision:* **PR1 ships in-memory only; sequencer checkpoints are unchanged; the non-sequencer durable+suspension story is an explicit follow-up** (§5). *Ramification:* a root-level non-sequencer stateful block does not reclaim state across a retry/resume until the follow-up — acceptable, no named consumer needs it (FIX-911's durable path is the session-scoped `activeState`, not block state).
5. **A capability-contributed `stateSchema` creates a container, with explicit collision detection; do NOT delete the legacy surface.** The capability surface has **no own-state field today**, the merged surface is unconsumed except for the generator, and `extendSchema` silently last-wins. So the FIX-911 seam (PR2) requires a new own-state field on `CapabilityConfig`/`PresetDef`, a merge rule that **detects duplicate-field conflicts instead of overwriting**, and wiring `mergedSurface` into the block's effective `stateSchema`. Removing `targetStateSchemas`/parent-state is **out** — later audit-then-remove. *Ramification:* the runtime unifies now; the config-surface shrink is deferred.

### 4.2 API surface

```ts
interface BlockContext</* ... */ TSelf extends object = ..., TParent extends object = ...> {
  /** This block's own request-scoped state, if it declared `stateSchema`.
   *  Undefined when the block declares no own state. Read/write (write is
   *  meaningful for blocks with an `execute`; generators read it in config fns). */
  self?: StateRef<TSelf>;

  /** Immediate parent block: identity + its state, if the parent has a
   *  `stateSchema` and this block declared `parentStateSchema`. A child writes
   *  its owner's state here (e.g. an activation tool → its generator). */
  parent?: { name: string; kind: BlockKind; input: TParentInput } & Partial<StateRef<TParent>>;

  sequencer?: StateRef<TSequencerState>;            // unchanged: nearest enclosing sequencer
  targets: InferTargetStatesFromSchemas<TTargets>;  // unchanged: by-name
  getTarget<T extends object>(name: string): StateRef<T> | undefined; // unchanged
}
```

`StateRef` is unchanged (`{ name, instanceId, state, input } & ScopeStateOps`).

```ts
// A router writes its own routing state; the block it routes to reads it as ctx.parent.
const route = router({
  name: "route-next",
  stateSchema: z.object({ lastRoute: z.string().nullable().default(null) }),
  routes: [alpha, beta],
  execute: async (input, ctx) => {
    const next = pick(input);
    await ctx.self!.setState({ lastRoute: next.name });   // writes own container
    return next;
  },
});

// The routed-to block reads the router's state via ctx.parent.
const alpha = handler({
  name: "alpha",
  parentStateSchema: z.object({ lastRoute: z.string().nullable() }),
  execute: async (input, ctx) => `came from ${ctx.parent?.state?.lastRoute}`,
});
```

**Router `ctx.self` writes must be idempotent under the resume contract.** A durable router **re-runs `execute` on resume** (it is not skipped — the re-run preserves the per-call route wrapper and is validated against the recorded `router_decision`; `execution-and-errors.md:57`). So a router's own-state write must be **deterministic/idempotent** — `setState` of a value derived from the (replay-stable) routing decision is safe, as above; `incState`/`pushState` in a router are **not** (they double-apply on re-run). The docs page and tests must carry this caveat, not bless arbitrary router self-writes.

// FIX-911: a generator reads its own skills state; its activation tool writes upward.
const researcher = generator({
  name: "researcher",
  stateSchema: z.object({ activeSkills: z.array(z.string()).default([]) }),  // (contributed by the skills capability in PR2)
  context: (_input, ctx) => `Active skills: ${(ctx.self?.state.activeSkills ?? []).join(", ")}`,
  // activation tool (a child block) declares parentStateSchema and writes ctx.parent.pushState("activeSkills", id)
});
```

### 4.3 Addressing modes (all resolve over the same per-scope-node container)

- **`ctx.self`** — the current block's own container (NEW). Read by any block; written by blocks with an `execute` (handler, router) and sequencer callbacks. Bound directly to the current scope node.
- **`ctx.parent`** — the immediate parent's container (NEW state). A child reads/writes its owner's state without naming it. The FIX-911 tool→generator write; the router→routed-child read.
- **`ctx.sequencer`** — nearest sequencer ancestor (unchanged; = `getTarget(nearestSequencerName)`).
- **`ctx.targets.<name>` / `getTarget(name)`** — a named ancestor (unchanged). A named non-sequencer target now *has* state if it declared `stateSchema`.

### 4.4 Fan-out & loop semantics (the contract)

- **`forEach` / `parallel` fan-out:** each iteration/branch runs in its own scope node → its own container → **private per iteration**.
- **`loopBack` loop:** the loop-owning sequencer keeps one container across passes → its own `ctx.self` **accumulates**. Re-executed *bodies* get `loop[N]` scope nodes → their `ctx.self` is **fresh per pass** (isolation). A loop body needing cross-pass memory writes it on the loop-owner via `ctx.parent` / `ctx.sequencer`.
- **Generator tool loop:** a generator enters its scope once and iterates the model/tool loop *inside* its config-driven execution, so its `ctx.self` persists across tool-loop steps. Its tools (child scopes) write upward via `ctx.parent`.
- **Self / parent are duals:** the router's `ctx.self` is the routed-child's `ctx.parent`; the generator's `ctx.self` is the tool's `ctx.parent`. Same container, two sides.

### 4.5 State / durability / emit

- **In-memory (PR1):** FIFO-lock container (`createScopeStateOps` no-persist path), deep-equal no-op suppression, `version+1`, never `ConcurrentModificationError` — identical to sequencer state today. Serves every PR1 goal (generator tool-loop accumulation, loop-owner accumulation, fan-out isolation, self/parent duality).
- **Live streaming (PR1):** `state_change` items carry `scope: "block_instance"` + `blockInstanceId` and reuse the existing path. They are **transient in production** (`shouldPersistScopeChange`), so they are a debug/devtool signal, not a client-visible projection.
- **Durable checkpoint + suspend/resume (FOLLOW-UP):** making a non-sequencer block's state survive a suspension/retry requires a new `emitStateSnapshot` call site, a path-based **storage key** in the durability hook (`runAction.ts:718` keys on `provenance.blockInstanceId`, not `item.key`), and suspension-record stamping + restore keyed on the block's own path. Out of PR1; sequencer checkpoints unchanged in PR1.

### 4.6 Error handling

| Case | Behavior |
|---|---|
| Block declares no `stateSchema` | `ctx.self` is `undefined`; guard with `?.`. |
| Child declares `parentStateSchema` but parent has no container | `ctx.parent.state`/ops absent (`Partial<StateRef>`); guard with `?.`. |
| Capability + block both declare own `stateSchema` | **Collision detection required (PR2)** — duplicate fields with incompatible types throw at build time; `.extend()` last-win is a bug to fix, not the contract. |
| Two ancestors share a target name | `AmbiguousBlockNameError` (unchanged). |
| Fan-out sibling reads another iteration's `self` | Not possible — distinct scope nodes. |
| Non-sequencer block suspends mid-execution (PR1) | State is lost on resume (in-memory only). Documented limitation until the durable follow-up; no PR1 consumer relies on it. |

## 6. Edge Cases

The fan-out / loop contract (§4.4), the self/parent duality (§4.3), and the durability boundary (§4.5) cover the behavioral cases; §4.6 covers the error cases. ## 7. Testing Strategy

**Goal (observable):** an author declares `stateSchema` on a non-sequencer block and it carries its own private state across its re-runs within one request — a generator remembers what it loaded across tool-loop steps (writes arriving from its tools via `ctx.parent`, reads via `ctx.self`), a sequencer counts its own `loopBack` passes, a router records its route and the routed-to block reads it via `ctx.parent` — while a fan-out / loop-body block gets a private cell that never leaks to a sibling or the next pass.

**Goal check (out-of-CI):** `goals/block-state/generator-remembers-across-tool-loop/run.mts` — a real-model generator whose activation tool writes `ctx.parent.pushState("loaded", id)` and whose `context` reflects prior loads via `ctx.self`; PASS = later steps see earlier loads. A second, mock-model assertion drives (a) a sequencer counting its own `.loopBack` drains in `ctx.self`, and (b) a `forEach` per-iteration isolation check. (Real model only for the generator variant.)
