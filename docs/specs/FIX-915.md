# FIX-915: Capability config factories — capabilities expose typed config with a custom resolver (`.config()` / `.with()`) — Implementation Spec

> **Linear issue:** [FIX-915](https://linear.app/fixpoint-labs/issue/FIX-915/capability-config-factories-capabilities-expose-typed-config-with-a)
> **Repo copy (canonical):** `docs/specs/FIX-915.md` — kept in sync with the Linear document.

## 1. TLDR

**Plain-language summary.** Today the only way to tune a capability from the outside is with **presets** — named on/off switches the capability author defined ahead of time. You can flip a switch, but you can't hand the capability a *value* (a list, a limit, a field name). Anyone who needs real per-use configuration has to abandon the shared capability machinery and write a one-off factory function instead, which then can't cleanly combine with the switch-based presets. This change gives a capability a second, open door: the author declares what typed configuration the capability accepts and writes a small function — a **resolver** — that turns that configuration into the capability's actual behavior. A user tunes it by calling `.config({ ... })`, and it still combines with presets exactly like before.

**One-sentence technical statement.** Add a build-time, typed **config-resolver** primitive to `defineCapability` plus a `.config(value)` / `.with({ config, presets })` builder surface that mirrors the existing `.presets()` builder (base-identity preserving, diamond-dedup safe), where the capability author's resolver maps validated config → a `Partial<PresetDef>` surface merged through the existing capability pipeline.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*
- **What we gain.** Capability authors get a first-class way to accept typed values and own how those values map onto a block, instead of a bespoke `createXCapability(options)` factory per capability. Users get one consistent `.config()` surface that composes with presets. FIX-911 (Skills v2) and FIX-908 (board) get the primitive they are blocked on.
- **Where the work sits.** Almost entirely inside one small directory (`packages/core/src/capability/*`) plus its tests and docs. It is mostly *new* plumbing bolted onto an existing merge pipeline, not a rewrite — the resolver's output reuses the same code path presets already use.
- **Where the complexity actually is.** Not the happy path. It's the identity/composition machinery: making `.config()` and `.presets()` chain in either order while a configured capability still deduplicates against its base by identity, and letting the resolver reconcile a config value against an active preset default (the "explicit value wins over the preset's default" case) without inventing a fixed framework rule.
- **The risk.** A wrong move on the base-identity trick silently breaks diamond deduplication (spurious "name collision" errors, or lost config). Caught by mirroring the proven `.presets()` `Object.create` mechanics, keeping every configured ref exactly one hop from its base, and a type-test + runtime-test matrix that pins chaining, dedup, and validation.

**Deliverables.**

Core (`packages/core/src/capability/`):
- Add a `config` declaration field (`{ schema?, resolve }`) to `CapabilityConfig` / `defineCapability`, carrying a `TConfig` const generic, in `types.ts` + `define-capability.ts`.
- Add `.config(value)` and `.with({ config, presets })` builder methods to `DefinedCapability`, both producing a single-hop, base-identity-preserving configured ref that carries `__config` (and copies forward `__presetOverrides`), in `define-capability.ts` + `types.ts`; thread the escape-hatch carriers through the `.config()`/`.with()`/`.presets()` return types so chaining preserves `sessionStateType`-style overrides (also repairs the latent `.presets()` drop).
- Extend `getBaseCapability()` to recover the base through a `__config`-bearing ref, and add `resolveConfigSurface()`, wired into `mergeCapabilities()` after presets, in `merge.ts`.
- Export the new types from `capability/index.ts`.

Tests:
- Add runtime tests to `packages/core/test/capability.test.ts` (builder identity, chaining, dedup, resolver merge, validation errors).
- Add type-tests to `packages/core/src/types/tests/capability-inference.type-test.ts` and `capability-schema-forwarding.type-test.ts`.
- Add a real-path goal check at `goals/capability-config/resolver-reaches-generator/run.mts`.

Docs:
- Extend `apps/docs/docs/advanced/capabilities-authoring.md`, `apps/docs/docs/fundamentals/capabilities.md`, `packages/core/README.md`, and `docs/architecture/capabilities.md`.
- Add a `.changeset/*.md` (minor).

**Size estimate. Medium** (multi-file, single PR, ~300–450 LOC; self-contained in `packages/core/src/capability/*` + tests + docs).

## 2. Overview

A **capability** is a named, reusable bundle of block wiring (resources, state-schema fragments, generator context and tools, helper functions) that a block opts into via `uses: [cap]`. The framework merges every declared capability's contributions into the block's effective config. Today a capability can be tuned from the outside in exactly one way: **presets** — predefined, named on/off bundles the author declared up front (`cap.presets({ verbose: true })`). Presets can flip a predefined surface on or off; they cannot carry a *value*.

This spec adds the missing door: a capability author declares a **typed config input** and a **resolver** (`resolve(config, ctx) => Partial<PresetDef>`) that maps that config to the same block-contribution surface presets already produce. Consumers pass config with `.config({ ... })`, and `.with({ config, presets })` sets config and presets together. Config and presets stay distinct and compose; existing preset behavior is unchanged.

The resolver runs at capability-merge (block build) time and reuses the existing merge pipeline, so no runtime or generator code changes. FIX-915 is a foundational primitive: it is a **hard blocker for FIX-911** (Skills v2) and a likely consumer of **FIX-908** (task-board capability surface).

## 3. Background & Research

### How the capability system works today

`defineCapability(config)` (`packages/core/src/capability/define-capability.ts:18`) returns a branded object. The only post-definition tuning surface is `.presets(overrides)` (`define-capability.ts:88-94`): it does `Object.create(capability)` (base becomes the prototype), stamps `__presetOverrides` as an own property, and returns the clone. `getBaseCapability(ref)` (`merge.ts:35-40`) recovers the base with a **single** `Object.getPrototypeOf` hop, gated on `"__presetOverrides" in ref`. Diamond dedup in `flattenCapabilities` (`merge.ts:82-120`) keys on base identity + name, so two `.presets()` clones of the same base dedup correctly, and two *different* capabilities sharing a name throw a collision error.

At block build time, `resolveCapabilities` (`resolve-capabilities.ts:68`) flattens `uses` and calls `mergeCapabilities(scoped, blockKind)` (`merge.ts:427-447`). For each capability it merges the always-on **required** surface, then `resolveActivePresets(cap)` (`merge.ts:141-193`) and merges each active preset. All merging funnels through **one choke point**, `mergeSurfaceInto(acc, surface, blockKind, ...)` (`merge.ts:316-417`), which accepts a `Partial<PresetDef>` and routes each field into the accumulator (resources, state schemas via `extendSchema`, targets, and the generator-only `context`/`tools`/singletons with block-kind guards). The accumulator's `contextEntries`/`toolEntries` are consumed by `generator.ts` (`:2581-2674`) at runtime; static preset tool/context factories run there against the raw `BlockContext`.

**Two findings shape the design:**

1. **A resolver that returns `Partial<PresetDef>` reuses the entire pipeline with zero downstream changes.** It plugs into the `mergeCapabilities` loop next to `resolveActivePresets` and funnels through `mergeSurfaceInto`. (`merge.ts:433-444`.)
2. **There is no runtime channel for per-capability config.** `CapabilityPresetCtx` (`types.ts:50-58`) is a phantom type; at runtime the generator passes the raw `BlockContext`, which carries `session.state`, `resources`, `identity` — nothing capability-config-specific (`generator.ts:2656`). So a config value a preset tool must read (e.g. skills' `activeState`) has to be **captured in the tool factory's closure at build time**, exactly how `createSkillsCapability(options)` bakes options into its tool factory today (`orchestration/src/skills/capability.ts:163-174`). Config is therefore a **build-time transform**, not a runtime injection.

### How similar problems are solved in the codebase already

Seven capabilities are configured today via a bespoke `createXCapability(options)` factory (memory, bash, mcp, workforce, task-board, perspective, and the memory sub-tiers). In every case the factory does **structural** build-time work — creating `defineResource` instances, sub-capabilities, tool blocks, or choosing a schema-declaration branch — that a post-construction override ref *cannot* do, because resources and schemas must exist statically at build time. The parts these factories express as presets are already `.presets()`-toggleable. So `.config()` is a **complement** to these factories (a typed-override surface that composes with `uses`/presets), not a replacement; adoption is opt-in.

The typing precedent to mirror is the framework's `Resolvable<TInput, TCtx>` pattern (`generator.ts:171` for `ResolvableModel`, etc.) — a `Value | ((input, ctx) => MaybePromise<Value>)` with the input type threaded through a `const` generic, and the type-only escape-hatch carrier fields (`types.ts:165-171`) for types a schema can't infer. `.presets()` is the sole `Object.create` identity-preserving builder; `.config()` and `.with()` are green-field names (zero existing matches).

### Industry research (scoped)

This is a framework-internal builder primitive, not a domain problem with external libraries to evaluate. The relevant prior art — immutable fluent builders that return new instances, config-normalizer/resolver hooks (Vite/webpack plugin config functions), and strategy objects that own their own merge policy — is idiom applied directly; it does not change an FSD-internal API decision that must mirror the existing `.presets()` mechanics and the `mergeSurfaceInto` choke point. Deep external research was judged not warranted here; the design is anchored to the in-repo precedents above.

### Why this approach over alternatives

- **Build-time resolver returning `Partial<PresetDef>`** over a new runtime `ctx.capConfig[name]` channel: reuses the merge pipeline with no generator changes and matches how config is baked today; the runtime channel is a larger ctx-contract change deferred as a follow-up (F3).
- **One configured object carrying both `__config` and `__presetOverrides`** over nested `Object.create` layers: keeps `getBaseCapability` single-hop, preserving the load-bearing invariant that flatten/merge/build-block depend on.
- **Resolver sees active preset names** over a fixed "config overrides preset" framework rule: the issue explicitly wants the *resolver* to own merge-vs-add semantics, not the framework.

### Key Decisions & Ramifications (top 5)

1. **Config is a build-time transform that returns `Partial<PresetDef>` and reuses `mergeSurfaceInto`; not a runtime ctx channel.**
   Alternative rejected: inject per-capability config into a new runtime `ctx.capConfig[name]` slot. Ramification: **zero** changes to `generator.ts` and the runtime ctx contract; resolver-emitted tools/context must close over config at build time (which is how config is baked today). Locks config to build-time semantics — a capability whose config must vary per runtime invocation is not served (flagged F3, future). This is the single biggest architectural commitment.

2. **A configured capability is one `Object.create(base)` clone carrying both `__config` and `__presetOverrides`; `getBaseCapability` stays single-hop.**
   Alternative rejected: nested `Object.create` (config-clone then preset-clone), or a looping `getBaseCapability`. Ramification: `.config().presets()` and `.presets().config()` chain in either order and still diamond-dedup by base identity; preserves the single-hop invariant relied on by `flattenCapabilities`, `mergeCapabilities`, `resolveActivePresets`, and `build-block`. Cost: both builders must copy-forward the sibling field, and today's `.presets()` closure (which captures the base and would drop chained config) must be reworked.

3. **The resolver receives the set of active preset names (`ctx.presets`), so the resolver owns override-vs-add semantics per setting.**
   Alternative rejected: a blind resolver (forcing every knob to be config, so a preset like `dynamicActivation` couldn't exist), or a fixed framework "config overrides preset" rule (the issue explicitly rejects this). Ramification: enables the canonical skills example — an explicit config field *overrides* a preset default while a context contribution *adds* — because the resolver computes the final surface itself. A preset may be a pure flag (`{}`) whose entire effect lives in the resolver. Couples the resolver to the author's own preset names (acceptable — same author). Presets' own direct-contribution behavior is unchanged.

4. **`.config()` complements the bespoke `createXCapability(options)` factories; no capability is re-authored.**
   Alternative rejected: migrate existing factories onto config. Ramification: factories keep doing the structural build-time work (creating resources/sub-capabilities/blocks/schema branches) that a post-construction override can't; adoption is opt-in and the two coexist; avoids a large, churny, higher-risk migration for no new capability.

5. **Ship `.with({ config, presets })` sugar alongside `.config()` + `.presets()` chaining (the one optional piece of public surface).**
   Alternative rejected: chaining-only. Ramification: `.with()` is near-free once the one-object copy-forward machinery exists and gives one obvious "set both at once" call the issue requested; but **no current consumer uses it** (FIX-911's surface is `config().presets()`), so per BP-038 it is the one droppable bit of surface. Flagged for owner sign-off (Open Questions §11).

## 4. Technical Design

### Architecture

All changes are inside `packages/core/src/capability/` (four files) plus tests and docs. No changes to `generator.ts`, `build-block.ts`, or the runtime ctx contract.

| File | Change |
| --- | --- |
| `capability/types.ts` | `TConfig` const generic; `CapabilityConfigDef<TConfig, TSessionState>`; `CapabilityConfigResolveCtx`; `.config()` / `.with()` method signatures on `DefinedCapability`; `__config` on `ConfiguredCapability`. |
| `capability/define-capability.ts` | Build the `.config()` and `.with()` builders; rework `.presets()` to copy-forward `__config`; move `config` def onto the runtime object (e.g. `__configDef`). |
| `capability/merge.ts` | Extend `getBaseCapability`; add `resolveConfigSurface(cap, resolveCtx)`; wire it into `mergeCapabilities` after presets; document the single-hop invariant. |
| `capability/index.ts` | Export new public types. |

### API surface

**Author side — declaring config on a capability:**

```ts
// New field on the defineCapability() config object.
interface CapabilityConfigDef<TConfig, TSessionState> {
  /** Optional Zod schema — validates the config value at build time and
   *  types the `.config()` argument (via z.input). Omit to type off TConfig. */
  schema?: ZodTypeAny;
  /** Maps validated config → a partial block-contribution surface. Runs at
   *  block build time; emitted tools/context factories run at runtime. */
  resolve: (
    config: TConfig,
    ctx: CapabilityConfigResolveCtx,
  ) => Partial<PresetDef<TSessionState>>;
}

interface CapabilityConfigResolveCtx {
  /** Names of the presets active on this consuming ref. Lets the resolver
   *  reconcile config against a preset default (override vs add). */
  presets: ReadonlySet<string>;
  /** The consuming block's kind — resolver may branch on it. */
  blockKind: BlockKind;
}
```

**`TConfig` inference contract.** `TConfig` is *computed*, not inferred from the resolver's own parameter (which is itself typed `TConfig` — inferring from it would be self-referential). The rule: `TConfig = TSchema extends ZodTypeAny ? z.input<TSchema> : TExplicit`, where `TSchema` is `config.schema` and `TExplicit` is an optional type-only carrier for the schemaless case. The `resolve` parameter is *constrained to* that computed `TConfig`, not an inference source for it. A capability that declares **no** `config` def resolves `TConfig` to `never`, so `.config(...)` on it is a compile error (the runtime backstop in §4 error handling is the second line of defence).

**Consumer side — the builder methods on a `DefinedCapability`:**

```ts
// TConfig is `never` when the capability declares no config def → compile error at the call.
config(value: TConfig): ConfiguredCapability</* … */>;
with(opts: { config?: TConfig; presets?: PresetOverrides<…> }): ConfiguredCapability</* … */>;
```

`ConfiguredCapability` gains `readonly __config?: unknown` (parallel to `__presetOverrides`).

**Escape-hatch carriers must thread through the configured-ref return types.** `defineCapability`'s return type intersects the concrete escape-hatch carriers (`& { readonly sessionStateType?: TSessionStateType; … }`, `define-capability.ts:58-62`), but `.presets()`'s declared return is a plain `ConfiguredCapability<…>` whose carriers are `readonly …Type?: unknown` (`types.ts:250`). Consequence today: a capability that uses the `sessionStateType` escape hatch **loses that override the moment it is `.presets()`'d** — `InferCapabilitySessionStateEntry` sees `unknown` and falls back to raw-schema inference (`types.ts:403-410`). `.config()` would inherit this latent `.presets()` bug, and FIX-911 (the primary consumer, and the likeliest escape-hatch user, since `z.input` of a skills config is often too loose) chaining `.config().presets()` would silently get raw-schema `ctx` types. **In scope for this spec:** thread the escape-hatch generics through the `.config()`, `.with()`, and `.presets()` return types so chaining preserves the overrides. Since the one-object rework already rewrites these return types, fixing `.presets()`'s latent drop here is the layer that owns the bug (BP-028). A negative type-test with the escape hatch pins it.

### Usage examples

**Generic author + consumer (the minimal shape of the primitive):**

```ts
const banner = defineCapability({
  name: "banner",
  config: {
    schema: z.object({ note: z.string(), loud: z.boolean().default(false) }),
    resolve: (cfg) => ({
      context: [cfg.loud ? cfg.note.toUpperCase() : cfg.note],
    }),
  },
});

// Consumer: typed config reaches the generator's context.
generator({ uses: [banner.config({ note: "ship it", loud: true })] });
```

**Config + presets composing (the skills shape FIX-911 will build on — illustrative; FIX-911 owns the exact skills surface):**

```ts
// dynamicActivation is a pure-flag preset; its effect lives in the resolver.
const skills = defineCapability({
  name: "skills",
  resources: { skills: skillsCollection },      // static, always-on
  sessionStateSchema: activeSkillStateSchema,    // static base schema
  presets: { dynamicActivation: {} },
  config: {
    schema: skillsConfigSchema,                  // { active?, allowed?, activeState? }
    resolve: (cfg, ctx) => {
      const surface: Partial<PresetDef> = {};
      if (cfg.active) surface.context = [renderActiveSkills(cfg.active)];
      if (ctx.presets.has("dynamicActivation")) {
        // explicit activeState OVERRIDES the block-state default (resolver-owned);
        // the load tool closes over the resolved target at build time.
        const target = cfg.activeState ?? blockStateDefault;
        surface.tools = [makeLoadSkillTool({ target, allowed: cfg.allowed })];
      }
      return surface;
    },
  },
});

// Chain in either order; or set both at once with .with().
generator({ uses: [skills.config({ active: ["deep-analysis"] })] });
generator({ uses: [skills.config({ allowed: ["research"] }).presets({ dynamicActivation: true })] });
generator({ uses: [skills.with({ config: { active: ["deep-analysis"] }, presets: { dynamicActivation: true } })] });
```

### Data flow

1. Consumer calls `cap.config(v)` / `.with({...})` → a single `Object.create(base)` clone carrying `__config` (and `__presetOverrides` when chained/`.with()`'d), one hop from base.
2. Block build: `resolveCapabilities` → `flattenCapabilities` (diamond-dedup by base identity, unchanged) → `mergeCapabilities`.
3. Per capability in `mergeCapabilities`: (a) merge required surface, (b) `resolveActivePresets` + merge each active preset (unchanged), (c) **new:** if the base declares a `config` def, run `resolveConfigSurface(cap, { presets, blockKind })` and merge its `Partial<PresetDef>` via `mergeSurfaceInto`.
4. `mergeSurfaceInto` routes the resolver's fields into the accumulator exactly as it does preset fields (block-kind guards reused).
5. Runtime: emitted context/tool factories run against `BlockContext` in `generator.ts` (unchanged), reading whatever config the resolver closed over.

`mergeCapabilities` already computes the active preset names (`resolveActivePresets`, `merge.ts:440`); it passes those names into `resolveConfigSurface` rather than recomputing them. `resolveConfigSurface` validates the config value against `config.schema` if present (throwing a clear, capability-named error on failure), then calls `resolve`. It runs **after** presets so config-contributed singletons win over *that same capability's* presets and required surface, and config context/tools append after that capability's preset context/tools. (Cross-capability ordering is unchanged: singletons remain global last-wins across capabilities, so a later capability's required `model` still wins over an earlier capability's config `model`.)

**When the resolver runs (the config-is-opt-in contract).** The resolver runs whenever a *used* capability declares a `config` def. The value handed to it is `schema.parse(__config)`, where `__config` is `undefined` when the consumer never called `.config()`. This means: **a capability meant to be usable without `.config()` must declare an all-optional / fully-defaulted config schema** (so `schema.parse(undefined)` succeeds and yields defaults). If the author makes any config field required, omitting `.config()` is — by design — a build-time validation error telling the consumer that `.config()` is mandatory for that capability. This contract is what lets a pure-flag preset like skills' `dynamicActivation` still install its tool when only `.presets({ dynamicActivation: true })` is set and no config is passed: the skills config schema is all-optional (`{ active?, allowed?, activeState? }`), so `schema.parse(undefined)` yields `{}`, the resolver runs, sees `ctx.presets.has("dynamicActivation")`, and installs the load tool with the block-state default.

**Error message source label.** `mergeSurfaceInto`'s block-kind guards currently interpolate `preset "${presetName}"` (`merge.ts:349,367,381,393,405,411`). A resolver emitting a generator-only field for a handler would otherwise throw a misleading "preset" error. Parameterize the source label so a config-sourced surface reports `config` (e.g. pass `source: "<config>"`).

### State management

The resolver may contribute state-schema fragments (merged/validated at runtime via `extendSchema`, same as presets). Consistent with presets today, **resolver-contributed schemas do not forward their types to the static `ctx` types** — only a capability's base `sessionStateSchema` forwards via `InferCapabilitySessionState`. Consumers of resolver-declared state read it by name through a state ref (matching FIX-911's author-names-the-field model). No new state scope is introduced; FIX-915 is pure capability-layer plumbing and does **not** depend on FIX-914 (block-level state).

### Error handling

| Case | Handling |
| --- | --- |
| `.config(v)` with a `schema`, `v` invalid | Build-time throw: `Capability "<name>" config failed validation: <zod message>`. Fatal. |
| Consumer calls `.config()` on a capability that declares no `config` def | Type error at the call site; runtime backstop throw `Capability "<name>" does not accept config`. Fatal. |
| Resolver emits `tools`/`context`/singletons for a non-generator block | Existing `mergeSurfaceInto` block-kind guard throws (reused, unchanged). Fatal. |
| Resolver throws | Wrapped with the capability name and rethrown at build time. Fatal. |
| Same base capability reached twice with different config in one block (diamond) | First-wins, matching current `.presets()` dedup behavior; documented sharp edge (§6, §11). |

All config errors are **build-time and fatal** (mirroring the existing unknown-preset error). None are retryable.

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
| --- | --- |
| Capability declares an **all-optional** `config` schema, consumer never calls `.config()` | Resolver runs with `schema.parse(undefined)` → defaults; emits its default surface (this is the path that lets a pure-flag preset install its tool without a config call). |
| Capability declares a `config` schema with a **required** field, consumer never calls `.config()` | Build-time validation error: `.config()` is mandatory for this capability (by design — see the opt-in contract in §4). |
| `.config().presets()` chain | One configured object carries both `__config` + `__presetOverrides`; base recovered single-hop; both applied. |
| `.presets().config()` chain | Same one-object result; order-independent. |
| `.with({ config, presets })` | Equivalent to `.config(config).presets(presets)`; both applied on one object. |
| Resolver reads `ctx.presets` to override a preset default | Supported (skills `activeState` case) — resolver owns the semantics. |
| Resolver emits `resources` | Merged, but a fresh `defineResource` per call breaks cross-block reference dedup. **Guidance:** declare resources on the base required surface; keep the resolver to context/tools/state schemas. |
| Resolver-contributed session schema | Validated/merged at runtime via `extendSchema`; **not** forwarded to static `ctx` types (consistent with presets). |
| Same base, different config, one block (diamond) | First-wins (matches `.presets()`); documented sharp edge. |
| `.config()` on a config-less capability | Type error + runtime backstop throw. |
| Invalid config against `schema` | Build-time throw, capability-named. |
| Resolver emits generator-only field for a handler/router/sequencer | `mergeSurfaceInto` block-kind guard throws (reused). |

**Error taxonomy:** all config-resolution failures are **build-time / fatal**. There are no retryable config errors. Fallback: a capability with no `config` def behaves exactly as today.

## 7. Testing Strategy

**Discipline:** `fsd:tdd` (feature). Each behavior below is a tracer-bullet cycle.

**Goal & goal check.** *Goal (observable outcome):* a capability author can hand a capability typed configuration and the resolver's output reaches the consuming block's real, assembled generation surface — composing correctly with presets. *Goal check (real path, out-of-CI):* `goals/capability-config/resolver-reaches-generator/run.mts` — a real `fsdev run` of a tiny flow whose generator uses `banner.config({ note: "hello-915", loud: true })`. **Capture point:** `fsdev run --capture` surfaces the model's *output/items*, not the outbound request, so the goal script wires the generator to an **echo stub model** (a deterministic model provider whose response echoes the assembled context back into the run output — the goal harness already runs real flows against a configured model per `goals/README.md`; here the configured model is the echo stub). The script then asserts the run output contains `HELLO-915` for the `loud: true` generator and `hello-915` for a second generator using `.config({ loud: false })`. **PASS/FAIL** printed on that assertion. *Why no real **LLM** is required:* the primitive's outcome is deterministic (config → build-time surface merge → request assembly → echoed into output); a real model's judgment adds nothing, but the **real path** (builder → flatten/dedup → `mergeCapabilities` → generator request assembly → dispatch) is exercised end-to-end, which the mocked CI specs do not fully assemble. This is the honest classification per the two-kinds-of-test rule: deterministic outcome, real path, no model judgment. *(If wiring an echo stub through `fsdev run` proves impractical, the fallback is a `goals/`-style `run.mts` that calls the block factory / `mergeCapabilities` directly and asserts on `mergedSurface.contextEntries` — a real-path assertion without a flow; the CI spec already covers the accumulator, so the echo-stub flow is preferred for genuine end-to-end coverage.)*

**CI specs (mocked, deterministic) — behaviors to test (tracer bullets):**
- `.config(v)` returns a base-identity-preserving ref: `Object.getPrototypeOf(ref) === base`, `__config` own prop, original not mutated.
- Resolver output merges into `mergedSurface.contextEntries` / `toolEntries` for a generator.
- Resolver receives active preset names in `ctx.presets`; the override example produces the config-targeted tool, the add example appends context.
- `.config().presets()` and `.presets().config()` both carry both fields; diamond dedup by base yields no spurious collision.
- `.with({ config, presets })` applies both.
- Invalid config against `schema` throws a capability-named build-time error.
- `.config()` on a config-less capability throws the backstop error.
- Resolver emitting `tools` for a non-generator block throws the block-kind guard.
- Resolver-contributed `sessionStateSchema` is merged/validated at runtime.

**Type-tests (mirror the existing idiom):**
- `capability-inference.type-test.ts`: `.config(v)` accepts a well-typed value and rejects a mistyped one (`@ts-expect-error`); `.with(...)` typed likewise.
- `capability-schema-forwarding.type-test.ts`: `ReturnType<typeof cap.config>` / `.with(...)` preserve the inferred **schema-derived** capability shape (`ctx.cap`, resources, targets, session state) across chaining. **Escape-hatch axis:** a capability using the `sessionStateType` escape hatch, chained through `.config().presets()`, still exposes the *override* type (not the raw-schema fallback) — this is the negative test that pins the carrier-threading fix (§4); it must fail before the fix and pass after.
- `.config()` on a capability with no `config` def is a compile error (`@ts-expect-error`), confirming `TConfig` resolves to `never`.

Mock-context idiom per `fsd:write-block-tests`.

## 8. Non-Goals

- **Re-authoring existing capabilities onto `.config()`.** Adoption is opt-in; the seven `createXCapability` factories keep their structural build-time work.
- **A general "config overrides everything" framework rule.** The resolver owns merge-vs-add semantics, deliberately.
- **A runtime per-capability config channel** (`ctx.capConfig[name]`). Config is a build-time transform; runtime-varying config is out of scope (see F3 below).
- **FIX-914 (block-level state).** FIX-915 is self-contained in the capability layer and does not need it; FIX-911 consumes both independently.
- **FIX-911 / FIX-908 consumer work.** This spec ships the primitive; the skills and board surfaces are their own issues (the skills surface in §4 is illustrative).

**Deepening opportunities flagged during analysis (follow-ups via `fsd:improve-codebase-architecture`, not in scope):**
- **F1** — `.presets()`'s closure captures the base and would silently drop chained config; this spec fixes it for the config path via the one-object design, but the broader "double-configuration silently drops a layer" hazard deserves a guard.
- **F2** — `getBaseCapability`'s single-hop assumption is an unstated, load-bearing invariant; this spec adds a comment, but it is worth a dedicated note in `docs/architecture/capabilities.md`.
- **F3** — no runtime channel for per-capability config (`CapabilityPresetCtx` has no `capConfig` slot); a capability genuinely needing runtime-varying config is a deliberate ctx-contract change to design later, at the layer that owns it (BP-028).
- **F4** — `CapabilityPresetCtx` is a phantom type never constructed; a future config that adds preset-ctx fields has no construction site to update. Type-drift risk to watch.
- **F5** — the escape-hatch-carrier drop through `.presets()` (a latent bug where `.presets()` widens a `sessionStateType` override back to raw-schema inference) is *fixed for the config path in this spec* by threading carriers through the configured-ref return types. That fix also repairs `.presets()`. If the owner prefers to keep this spec's diff minimal, the `.presets()` fix can be split out — but shipping it here is cheaper (the return types are already being rewritten) and directly protects the FIX-911 consumer.

## 11. Open Questions

1. **Naming (non-blocking, resolve before docs).** Author declaration field `config` vs `configResolver` / `params` (the `.config()` method reuses the word `config`, which is mildly overloaded against the `CapabilityConfig` type name). Resolver-ctx field `presets`. Recommendation: `config: { schema, resolve }` + `.config()` for symmetry; open to `configResolver` if the overload reads badly.
2. **Ship `.with()` now, or defer? (BP-038, owner call).** No current consumer uses `.with()` (FIX-911 uses `config().presets()`); it is near-free sugar but the one droppable piece of public surface. Recommendation: ship it (the composition machinery is the hard part and `.with()` gives one obvious "set both" call the issue requested), but happy to defer until a consumer needs it.
3. **Same-base/different-config in one block (diamond): first-wins or throw?** First-wins matches current `.presets()` behavior (consistency); a throw is safer but stricter than the sibling. Recommendation: match `.presets()` (first-wins) and document the sharp edge; revisit if it bites.
4. **Fix `.presets()`'s latent escape-hatch drop now, or split it out? (F5).** The carrier-threading fix this spec needs for `.config()` also repairs `.presets()`. Recommendation: ship it here (cheaper, and it protects the FIX-911 consumer directly), but happy to split into a tiny standalone PR if the owner wants this diff minimal.
