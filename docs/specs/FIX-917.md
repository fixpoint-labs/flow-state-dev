## Part I — The Case

### 1. Problem — why it matters, why now

FIX-914 gave any block its own request-scoped state and unified the *runtime*
onto one container. But two rough edges surfaced in that PR's review and were
deferred as non-blocking follow-ups:

1. **The declaration surface is still fragmented.** A block declares state-schema
   intent through **four separate top-level config keys** — `stateSchema`,
   `parentStateSchema`, `sequencerStateSchema`, `targetStateSchemas` — even though
   the runtime now resolves all four over one container mechanism. Four keys for
   one concept is the main remaining complexity after the runtime unification, and
   leaving it un-consolidated risks the fragmentation ossifying as more code is
   written against it.

2. **State loss on suspend is silent.** A non-sequencer block (handler / generator
   / router) that writes its own `stateSchema` state and then calls `ctx.suspend()`
   loses that state on resume — the container is re-created from schema defaults
   with **no error, no warning, no log line**. For the FIX-911 use case this
   unblocks (a generator accumulating loaded skills across a tool loop), that reads
   as "it silently forgot everything."

**Why now.** The keys and the suspend behaviour are days old (FIX-914 just landed),
so the config surface has almost no external consumers yet — the cheapest moment to
consolidate it is before more code depends on the four-key shape. The silent reset
is a correctness/observability gap that will mislead the first author who hits it;
a warning is a small, self-contained guard until the durable-checkpoint follow-up
(explicitly out of scope, see §12) lands.

### 2. Solution in plain terms

**Part 1 — one `state` config key.** Collapse the four top-level keys into a single
`state` object whose sub-keys name the context accessor each one types:

| Today (top-level key) | Becomes (`state.` sub-key) | Types the accessor |
| --- | --- | --- |
| `stateSchema` | `state.own` | `ctx.self` |
| `parentStateSchema` | `state.parent` | `ctx.parent` |
| `sequencerStateSchema` | `state.sequencer` | `ctx.sequencer` |
| `targetStateSchemas` | `state.targets` | `ctx.targets` / `ctx.getTarget()` |

The mapping becomes 1:1 and self-documenting: each declaration sub-key is named for
the accessor it enables. Only `state.own` declares a *store this block owns*; the
other three declare the *expected shape of state owned elsewhere* that this block
reads/writes through a typed accessor. The `state.own` naming makes that ownership
distinction legible where four flat keys hid it.

**Part 2 — warn on silent suspend-reset.** When a non-sequencer block whose own
(`state.own`) container has been written to calls `ctx.suspend()` on a path where
that container will not be checkpointed, emit a dev-mode `console.warn` (and a trace
note) naming the block and the state that will be lost on resume. Turn the silent
reset into an observable one until durable block-state checkpointing lands.

**The philosophy that led here.** Tenet 2 (*the framework gets more impactful
without getting bigger*): Part 1 removes surface — four keys become one — while the
runtime stays exactly as unified as FIX-914 made it; the config now reflects the
container it already resolves to. Tenet 1 (*coherence*): a config surface that
fragments a concept the runtime unified is incoherent; this realigns them. Tenet 3
(*subtraction is part of the change*): the deliverable is a net removal of public
keys, not an addition. Part 2 leans on tenet 1 too — silent divergence between what
an author wrote and what survives resume is the exact incoherence the warning makes
visible.

### 3. Tradeoffs & alternatives

- **Alternative for Part 1 — a two-key split** (`stateSchema` for own state +
  `readsState: { parent, sequencer, targets }` for the foreign-shape declarations).
  Semantically honest about ownership, but keeps two top-level keys and doesn't map
  as cleanly to the four accessors. `state.own` already signals ownership by name
  while giving one entry point. Rejected in favour of the single `state` key.
- **Alternative for Part 1 — do nothing / just document.** The runtime already
  works; the four keys are "only" ergonomics. Rejected because the review explicitly
  flagged ossification risk, and the window where there are near-zero consumers is
  closing. This is refinement of a just-shipped surface, not speculative churn.
- **Simpler approach for Part 2 — throw on suspend-with-dirty-own-state.** Louder,
  but it breaks a legitimate pattern (a block may not care that its own state
  resets) and would be a behaviour regression on a path that "works" today. A warning
  is the right altitude until durable checkpointing makes the reset unnecessary.
- **Where the genuine complexity is.** Not the rename (mechanical). It's (a)
  backward-compatibility policy for the four legacy keys — clean rename vs. dual-read
  (Decision 2), and (b) Part 2's *dirty own-state* detection at suspend time (deep-equal
  against schema defaults). The predicate deliberately does **not** try to model checkpoint
  coverage — that path produced a false negative on the HITL suspend (see §7, Decision 4),
  so we warn on any dirty own-state suspend from a non-sequencer caller and accept a rare
  harmless false positive rather than risk silent state loss.

### 4. Focus practices

- **BP-030 (tolerate the old shape) governs Decision 2.** If we dual-read the legacy
  keys, new code must accept both shapes and reject nothing silently; if we hard-rename,
  we must prove there are no external consumers first. Either way the choice is explicit.
- **BP-035 (second-path checklist).** Part 2 *is* a second-path fix (the suspend/resume
  path). Walk cancel/error and the "off state" of the new warning (production-gated) as
  part of the change.
- **BP-007 (document exported APIs).** The four keys are documented public config; the
  consolidation must update every doc/README/JSDoc that names them, not just the types
  (BP-034 finish the rename).
- **Change-specific rule: the warning is dev-only and side-effect-free.** It must never
  fire in production builds and must never alter control flow — it is observability, not
  a guard.

### 5. What using it looks like

**Part 1 — before / after (a generator that owns state and reads its sequencer's):**

```ts
// BEFORE (FIX-914 four-key surface)
generator({
  name: "loader",
  stateSchema: z.object({ loaded: z.array(z.string()).default([]) }),
  sequencerStateSchema: z.object({ turn: z.number() }),
  // ...
});

// AFTER (FIX-917 consolidated surface)
generator({
  name: "loader",
  state: {
    own: z.object({ loaded: z.array(z.string()).default([]) }),
    sequencer: z.object({ turn: z.number() }),
  },
  // ...
});
```

Accessors are unchanged: `ctx.self`, `ctx.parent`, `ctx.sequencer`, `ctx.targets`
read exactly as before. Only the declaration shape moves.

**Part 2 — the observable result when the reset would happen:**

```ts
const h = handler({
  name: "accumulate",
  state: { own: z.object({ items: z.array(z.string()).default([]) }) },
  execute: async (input, ctx) => {
    ctx.self?.push("items", input.value);   // own state now dirty
    await ctx.suspend({ reason: "await-approval" });
    // ^ dev console.warn: [flow-state] block "accumulate" suspended with
    //   non-empty own state ({items}) that will NOT survive resume — its
    //   container re-initializes to schema defaults. (durable block-state
    //   checkpointing: not yet implemented.)
    return ctx.self?.get("items");           // after resume: [] (reset), now visible
  },
});
```

### 6. Decisions & rules — the sign-off surface

1. **One `state` config key with sub-keys `own` / `parent` / `sequencer` / `targets`.**
   - *Alternative rejected:* two-key split (`stateSchema` + `readsState`); keep four keys.
   - *Ramification:* the public config surface for block state is a single key; sub-keys
     are named for the accessors they type, locking a 1:1 declaration→accessor mapping.
2. **Hard rename, no dual-read — contingent on confirming zero external consumers.**
   Because the four keys shipped days ago (FIX-914) and are used only inside this repo,
   migrate all call sites to `state.*` and remove the old keys outright.
   - *Alternative rejected:* BP-030 dual-read (accept both shapes with a deprecation
     warning).
   - *Ramification:* no legacy-shape debt carried forward, but any out-of-repo consumer
     of the four keys breaks. **This is the primary decision needing human sign-off** —
     if any published/external consumer exists, fall back to dual-read + deprecation.
   - **Even the hard-rename path must reject the removed keys loudly at runtime, not only
     at the type level (BP-030 "reject removed keys loudly").** Removing the four keys from
     the config *types* stops TypeScript callers, but JS callers, stale compiled consumers,
     and TS excess-property escapes can still pass `stateSchema` / `parentStateSchema` /
     `sequencerStateSchema` / `targetStateSchemas`. Since `buildBlock` normalizes only
     `config.state.*`, a stray legacy key would otherwise be **silently ignored** — the
     block's declared state vanishes with no error, no warning. So `buildBlock` must throw
     a clear replacement error (e.g. `"stateSchema" was renamed to "state.own"`) whenever
     any of the four removed keys is present on a block config. This runtime dead-key
     rejection is required regardless of the dual-read/hard-rename choice; hard-rename is
     "no dual-read," not "no runtime guard."
3. **Part 2 is a dev-mode `console.warn` + trace note, not a throw and not a persist.**
   - *Alternative rejected:* throw on suspend-with-dirty-own-state; silently persist.
   - *Ramification:* zero behaviour change on the happy path; the reset still happens,
     it's just observable. Persistence is the separate durable-checkpoint follow-up (§12).
4. **The warning fires when own-state is dirty AND the caller is a non-sequencer block —
   no checkpoint-coverage predicate.**
   - *Alternative rejected:* the earlier "dirty AND uncovered by a checkpoint" rule, which
     walked the ancestor chain and suppressed the warning under an enclosing sequencer
     checkpoint. Two independent reviewers converged that this is a false negative: a
     sequencer checkpoint persists only `ctx.sequencer.state`, not a child block's own
     `state.own` container, so the common HITL path (dirty non-sequencer suspending inside
     a durable sequencer) would silently lose state while the warning stayed quiet.
   - *Ramification:* accepts a rare, harmless false positive (an extra dev-warning inside a
     genuinely-checkpointed path) to guarantee it **never** produces a false negative. It
     still won't warn for a block that declared own state but never wrote it (not dirty).
     False positive = harmless dev noise; false negative = defeats the feature.
5. **Warning is production-gated and side-effect-free.**
   - *Alternative rejected:* always-on log.
   - *Ramification:* no production log noise; the guard is an observability aid in dev.

**Non-goals.** Durable checkpoint/persistence for non-sequencer block state (the real
fix for #2). Capability-contributed own-state `stateSchema` merging (FIX-911's PR2 seam
— needs `extendSchema` duplicate-field collision detection first). Any change to the
four context accessors themselves.

**Size estimate.** Medium (multi-file, one PR, ~150–350 LOC). Splittable into two PRs
along the two parts if review prefers; Part 1 is the larger, Part 2 is self-contained.

## Part II — The Build Plan

### 7. Technical design

**Part 1 — config surface (package `@flow-state-dev/core`).**

The four keys live on the config interfaces of the four block factories plus the
`BlockConfig`/`BlockDefinition` runtime shape:

- `packages/core/src/blocks/handler.ts` — `HandlerConfig` declares `stateSchema`,
  `parentStateSchema`, `sequencerStateSchema`, `targetStateSchemas` (lines ~63–86);
  `HandlerDefaults` mirrors `sequencerStateSchema` (line ~170).
- `packages/core/src/blocks/generator.ts` — `sequencerStateSchema` (~423),
  `targetStateSchemas` (~427), plus own/parent.
- `packages/core/src/blocks/router.ts` — `sequencerStateSchema` (~91),
  `targetStateSchemas` (~95), plus own/parent.
- `packages/core/src/blocks/sequencer-methods.ts` — sequencer's own `stateSchema`
  (~406). NOTE: a sequencer *owns* state via `stateSchema`; it does not read a parent
  the same way. Decide whether the sequencer surface also moves to `state.own` for
  consistency (recommended) — this is the "3 of 4 factories" the issue references
  (the sequencer already has a distinct declaration path).

Introduce a single `state` config field, typed so each sub-key carries its own
generic (preserving the existing per-schema `z.infer` inference that types
`ctx.self` / `ctx.parent` / `ctx.sequencer` / `ctx.targets`):

```ts
interface BlockStateConfig<
  TOwn   extends ZodTypeAny | undefined = undefined,
  TParent extends ZodTypeAny | undefined = undefined,
  TSeq   extends ZodTypeAny | undefined = undefined,
  TTargets extends Record<string, ZodTypeAny> | undefined = undefined,
> {
  own?: TOwn;
  parent?: TParent;
  sequencer?: TSeq;
  targets?: TTargets;
}
```

The factory generics (`TStateSchema`, `TParentStateSchema`, `TSequencerStateSchema`,
`TTargetSchemas`) are retained internally but now sourced from `config.state.*` rather
than four top-level keys. The `resolveCapabilities(config, kind)` call (handler.ts
~136) returns `stateSchema` — it must read from `config.state?.own` and still merge
capability-contributed own-state (`InferCapabilityOwnState<TUses>` is unchanged; the
capability *contribution* path is untouched, only the author-declared key moves).

`buildBlock` normalizes `config.state` back into the flat runtime fields the engine
already consumes (`BlockDefinition.config.stateSchema`, etc.) so **no engine change is
required for Part 1** — the runtime container mechanism in
`createExecutionContext.ts` (`_withExecutionScope`, ~2782) keeps reading
`resolvedParent.stateSchema`. The consolidation is a config-layer remap; the runtime
contract is unchanged.

**Part 2 — suspend warning (package `@flow-state-dev/engine`).**

Seam: the per-scope `suspend` closure in
`packages/engine/src/context/createExecutionContext.ts` (~2636). At suspend time the
calling scope node is available as `parentChain?.parent` (the block that called
`ctx.suspend()`), and its state container as `parentChain?.parentStateContainer` (the
container created in `_withExecutionScope` at ~2782, named `parentStateContainer` for
legacy reasons — it is the *calling block's own* container from the perspective of this
closure).

The predicate for warning:

1. `parentChain.parent.stateSchema !== undefined` (block declared own state).
2. `parentChain?.parent.kind !== "sequencer"` (the caller is a non-sequencer block).
3. The container is **dirty** — its current value differs from
   `normalizeStateDefault(stateSchema)` (deep-equal against defaults; reuse the shared
   `deepEqual` util per CLAUDE.md coding conventions).

**No ancestor/checkpoint-coverage walk.** An earlier draft added a fourth condition —
suppress the warning when an enclosing sequencer on the `parentChain` checkpoints — but
two independent reviewers converged that this produces a **false negative** on the common
HITL path: a sequencer checkpoint persists only `ctx.sequencer.state` (via
`state_snapshot`), **not** a child block's own `state.own` container. A dirty
handler/generator/router that suspends inside a durable sequencer still gets its own
container rebuilt from schema defaults on resume, yet the coverage walk would treat it as
"covered" and stay silent — exactly the silent state loss the warning exists to catch.
The predicate therefore drops the coverage walk entirely and depends on no checkpoint
semantics. The tradeoff is deliberate: a block whose state is genuinely checkpointed may
draw one extra dev-warning (a harmless false positive / bit of dev noise), which we accept
in exchange for **never** producing a false negative (silent state loss defeats the
feature). Dirty-detection and the dev-gate/side-effect-free properties are unchanged.

When all hold, and `process.env.NODE_ENV !== "production"`, `console.warn(...)` with a
message naming the block, the dirty top-level keys, and a pointer that durable
block-state checkpointing is not yet implemented. Optionally emit a trace note adjacent
to the existing suspend trace (a `state_change`-adjacent annotation) so it is visible in
DevTool, not just stdout — keep this behind the same dev gate.

### 8. Implementation sequence

1. **Add `BlockStateConfig` type + `state` field to the four factory config
   interfaces** (`handler.ts`, `generator.ts`, `router.ts`, `sequencer-methods.ts`).
   Wire the internal generics to source from `config.state.*`. *Test:* type-tests in
   `packages/core/src/types/tests/` (extend `sequencer-state-schema-bubbling`,
   `targets`, `flow-state-inference`) compile with the new shape and infer the same
   `ctx.*` types. *Modify;* no new files.
2. **Normalize `config.state` → flat runtime fields in `buildBlock`** (or the shared
   config-resolution path), and **add a runtime dead-key guard**: if any of the four
   removed keys is present on the config, throw a loud error naming the key and its
   `state.*` replacement (BP-030 — see Decision 2). *Test:* a built block's
   `config.stateSchema` etc. equal the `state.*` inputs; passing a legacy key (cast through
   `any` to bypass types) throws the dead-key error. *Remove:* the four top-level keys from
   the config interfaces (subtraction — tenet 3).
3. **Migrate all in-repo call sites** from the four keys to `state.*`. Grep surface is
   wide (patterns, orchestration, memory, kitchen-sink, tests, labs). *Test:* `pnpm
   typecheck` clean; `pnpm test` green. Depends on 1–2.
4. **Confirm zero external consumers** (Decision 2). Check package READMEs, published
   examples, changelog. If any exist, STOP and escalate — fall back to dual-read.
5. **Part 2: add the suspend-warning predicate + `console.warn`** in the suspend closure
   (`createExecutionContext.ts` ~2636). Predicate = dirty own-state + non-sequencer caller
   (no checkpoint-coverage walk — see §7). *Test:* engine test — a non-sequencer handler
   with dirty own state that suspends triggers the warn (spy on `console.warn`); one with
   clean state does not; a sequencer caller does not. Independent of 1–4.
6. **Docs + changeset** (§11, BP-022).

### 9. Edge cases & error handling

| Case | Expected behavior |
| --- | --- |
| Block declares `state.own` but never writes it, then suspends | No warning (container equals defaults — not dirty). |
| Sequencer suspends with its own state | No warning (sequencer state is checkpointed). |
| Non-sequencer with dirty own state inside a checkpointed sequencer | **Warns.** A sequencer checkpoint persists only `ctx.sequencer.state`, not the child's `state.own` container, so the container still resets on resume. Predicate does not model coverage (§7). |
| Production build | Never warns (NODE_ENV gate). |
| Legacy four-key config passed after rename | **`buildBlock` throws a loud runtime dead-key error** naming the removed key and its `state.*` replacement (BP-030 "reject removed keys loudly") — in addition to the compile-time TypeScript rejection. The runtime guard is mandatory because JS callers, stale compiled consumers, and TS excess-property escapes bypass the type removal, and `buildBlock` normalizes only `config.state.*`, so an unguarded legacy key would be silently ignored (silent state loss). If dual-read is chosen instead (Decision 2 fallback), accept both and deprecation-warn on the old shape (BP-030). |
| `state: {}` or `state` omitted | Identical to declaring no state today (all accessors undefined). |
| Capability-contributed own-state + author `state.own` | Merge unchanged from FIX-914 (`InferCapabilityOwnState` intersect); only the author key moved. |

Error taxonomy: Part 2 introduces no errors — warning only, non-throwing, no control-flow
change. Part 1 surfaces mistakes primarily at compile time (type errors), plus one
deliberate runtime error: `buildBlock` throws a loud dead-key error when a removed legacy
key (`stateSchema` / `parentStateSchema` / `sequencerStateSchema` / `targetStateSchemas`)
is present, so non-TypeScript callers fail loudly rather than losing state silently (BP-030).

### 10. Testing strategy

- **Goal & goal check.** Part 1 is a pure config/type refactor → no runtime goal check;
  the goal check is `pnpm typecheck` + full `pnpm test` staying green after the migration
  (the observable outcome is "same behaviour, one key"). Part 2 has a real observable: run
  a flow with a suspending stateful handler under `fsdev run` (or the engine suspend test
  harness) and confirm the warn fires on the reset path — this is the `fsd:diagnose` seam
  (the suspend/resume path is where the feedback loop lives).
- **CI specs (mocked, deterministic):** (a) type-tests proving `state.*` infers the same
  `ctx.*` types as the four keys did; (b) engine test asserting `console.warn` is called
  exactly when the predicate holds and not otherwise (dirty vs. clean vs. sequencer vs.
  production-gate).
- **Discipline:** Part 1 → `fsd:tdd` (type-tests first, red-green). Part 2 → `fsd:diagnose`
  (reproduce the silent reset, then make it observable, then regression-test).
