## 1. TLDR

**Plain-language summary.** A skill today can run in one of three modes.
"Inline" just adds instructions to the agent. The other two — "pattern" and
"fork" — are really hidden ways of launching separate work: pattern hands
control to a rigid, hard-coded dispatcher that builds a fixed task board and
workers from a YAML-like config; fork spins up a throwaway sub-agent. Both are
awkward, and having three modes for what is really "instructions plus optional
extra machinery" has been more confusing than useful. We're removing pattern
and fork entirely, leaving a skill as just instructions plus, optionally, the
ability to delegate. Delegation works by giving the agent a private worklist
and a set of callable helper tools, and letting the agent's own normal
decision-making loop decide when to use them — no separate rigid engine
underneath. Separately, existing multi-step recipes (like the "keep working
until a goal is met" loop already shipped, and the plain task-board runner)
become things an agent can call directly as a single action, the same way it
calls any other tool. Three real example skills use the old pattern system
today, so this isn't just a framework change on paper — the same change has to
keep those three working, which is also the proof the replacement holds up.
(Fork, by contrast, has no real users to migrate — it's a clean delete.)

**One-sentence technical statement.** Remove both non-inline skill context
modes — pattern (`PatternRegistry`, the `pattern-run` router,
`worker-materializer`'s pattern coupling, `pattern:`/`pattern-config:`/
`initial-tasks:` frontmatter) and fork (`fork-generator.ts`, the `runSkill`
fork route, `context: fork` parsing) — collapsing `SkillContextMode` to
`"inline"`; replace pattern-style delegation with a new `delegation` preset on
`createSkillsLibrary` (own-state task board + `taskTools` + per-worker callable
tools, executive-orchestrated, no drain loop); verify/harden `goalSeekLoop` and
`taskBoard().drain` (and any block) as directly tool-callable primitives; and
migrate the three real pattern-mode skills (`apps/kitchen-sink` ×3,
`examples/guides/research-team` ×2) onto the two replacements. Fork has no
consumers to migrate. Supersedes FIX-919.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*
- **What we gain.** A skill stops being a three-mode concept and becomes one
  thing: instructions, optionally plus delegation. One coherent way to
  delegate (a private ledger + named worker tools the executive calls itself)
  instead of a rigid, session-global, YAML-driven dispatcher; deterministic
  multi-step flows (`goalSeekLoop` and friends) become ordinary callable tools
  any agent can reach for. The `SkillContextMode` enum collapses from three
  values to one, and an entire dispatch surface (fork generator, pattern
  registry, the `runSkill` router's non-inline branches) is deleted.
- **Where the work sits.** Mostly rewiring existing primitives (capability
  own-state, the task board, worker materialization, the generic
  block-as-tool mechanism that already exists) into a new capability preset;
  the genuinely new code is small — one new task-board backing, one new
  capability file, one decoupled frontmatter parser.
- **Where the complexity actually is.** Proving that a deterministic flow's
  *internal* steps stay invisible to the calling agent's history when it runs
  as a single tool call — the mechanism looks sound by construction but has
  zero test coverage today, so this is a verify-then-patch-if-needed problem,
  not a code-review problem.
- **The risk.** Two risks. (1) Deleting the pattern dispatcher before the new
  path is proven would break real skills — three in this repo
  (`apps/kitchen-sink`) plus a full example package
  (`examples/guides/research-team`) hard-import `defaultPatternRegistry` and
  break at build time the moment it's deleted; mitigated by migrating all of
  them in this same change (§4.10) and using two as the actual goal checks.
  (2) Removing fork drops one capability outright — a sub-agent that
  *inherits the conversation so far* — which no other current surface
  reproduces (a delegation worker gets its task input, not the full prior
  conversation). This is a knowing deferral to FIX-920, not an oversight;
  the isolation half of fork's value (sub-agent work hidden from parent
  history) is already covered by delegation + the task board. Fork itself has
  zero SKILL.md consumers, so the deletion breaks no shipping code.

## 2. Overview

Linear issue: [FIX-918](https://linear.app/fixpoint-labs/issue/FIX-918/remove-skill-pattern-mode-deliver-delegation-via-a-capability-blocks).

Skills today carry a `context:` mode — `inline | fork | pattern`. `inline`
injects instructions into the host generator (kept). The other two are
disguised dispatch mechanisms: `pattern` hands execution to `PatternRegistry`,
a session-global dispatcher that materializes a task board and named workers
from YAML-shaped config and runs them through a fixed pattern factory
(`taskBoard`, `planAndExecute`, `supervisor`, etc.); `fork` spins up an
isolated sub-agent via `createSkillForkGenerator`. This spec removes **both**
non-inline modes, collapsing `SkillContextMode` to `"inline"`, and replaces
pattern-style delegation with a `delegation` preset on the already-shipped
`createSkillsLibrary` (FIX-911) — the executive generator's own tool-calling
loop becomes the orchestrator, with a private task board and named
worker-tools as its building blocks. It also verifies that the already-shipped
`goalSeekLoop` primitive (FIX-910) and a plain `taskBoard().drain` can be
called directly as tools by any generator, closing the loop on "deterministic
recipes as blocks-as-tools." Fork is removed outright, not relocated; its
"sub-agent that inherits the conversation so far" capability is deferred to
FIX-920 (delivered through task management). This supersedes FIX-919.

## 3. Background & Research

### 3.1 Why this is being done (condensed design history)

This issue was filed at the end of a long design thread captured in
`docs/internal/design/skills-goalseek-design-notes.md` (branch
`claude/skills-system-architecture-kw77zs`, not yet on `main` — this spec
inlines everything load-bearing from it since the branch itself is
undiscoverable from `main`). The thread's conclusion, in brief:

The skills system overloaded one concept (`context: inline | fork | pattern`)
across three unrelated execution shapes. Only `inline` is actually "context injection";
`fork` and `pattern` are *dispatches* that happen to be triggered via a
`runSkill` tool call. FIX-911 fixed the real session-global bleed problem for
`inline` (per-generator capability-config binding) but explicitly left
`fork`/`pattern` on the legacy session-global `runSkill` router — sharpening
the fragmentation rather than reducing it (`docs/specs/FIX-911.md` §8: "Full
migration/removal of the session-global path... (staged follow-up)").

**On fork specifically (the post-filing scope expansion).** The original
skills redesign kept fork as a real mode and even had a dedicated rework in
flight (FIX-919 / PR #844: make the fork child inherit history to the fork
point, deliver it as a capability-installed tool). The project owner has since
decided fork is not worth its complication: it adds a whole dispatch shape and
a second "spawn a child like the parent" resolution problem, for a capability
whose *isolation* half (a sub-agent whose work is hidden from the parent's
history) delegation + the task board already provide — tasks already emit at
`itemVisibility: { client: true, history: false }`, so a task's work is
fork-like sub-agent behavior without a fork mode. The remaining half —
*inheriting the prior conversation into the child* — is deferred to **FIX-920**,
which will deliver it through task management rather than a bespoke `context:`
mode. So fork is removed here (not relocated), FIX-919 is superseded, and its
PR #844 should be closed unmerged. This is the same "split the taxonomy by
what a skill *is*, not how it runs" principle from the design notes, taken to
its conclusion: after this change, a skill *is* inline instructions, plus
(optionally) a delegation capability. There is no "how it runs" axis left.

Removing fork is a deliberate, owner-made call, not a research conclusion of
this spec. The one honest ramification (recorded in §5 Key Decision 1): between
this landing and FIX-920, there is no way to spawn a sub-agent that sees the
full prior conversation. No shipping skill relies on that today (zero
`context: fork` SKILL.md consumers), so nothing breaks — but the capability
gap is real and named.

Two competing designs were weighed for what replaces `pattern` mode:

- **Direction A — a `skillHarness` block wraps the generator**, owns an outer
  GoalSeek loop, and enforces whole-turn convergence across every active
  skill's goals. Needs a new top-level "harness" block type and loop-around-a-
  loop context re-threading.
- **Direction B — the generator stays the executive; deterministic recipes are
  tools it calls.** No wrapping, no new block type. A skill that needs to
  delegate gets a capability-installed task board + worker-tools; the
  executive's own ReAct loop decides when to use them. A skill that needs a
  rigorous, autonomous multi-step recipe (e.g., `goalSeekLoop`) calls that
  recipe *as a tool* and gets back only the finalized result.

**Direction B was chosen** (see §5 for the rejected alternative's ramifications).
The reasoning: whole-turn enforced convergence — the only thing Direction A
buys that B doesn't — decomposes into two things the framework already has:
rigorous delegation (enforcement lives inside the called flow, i.e.
`goalSeekLoop`) and enforced output gating (the existing `response-auditor`
pattern, an action/flow-level guard). No concrete case requiring a harness was
identified. Building the harness would mean a third top-level concept trying
to do both delegation and output-gating from inside the skill layer — the
opposite of BP-038 (subtract before you add).

### 3.2 Industry precedent

The chosen shape — an orchestrating agent calling worker sub-agents as
ordinary tools, with only the finalized result flowing back — matches how
established frameworks solve the same problem:

- **Anthropic's "Building Effective Agents"** describes the orchestrator-
  workers pattern directly: a central LLM decomposes a task and delegates
  pieces to worker LLMs, synthesizing their outputs itself, with no fixed
  subtask list decided in advance — this validates "the executive's own loop
  is the orchestrator, no separate drain loop."
- **OpenAI's Agents SDK** implements almost exactly Shape 1: `agent.as_tool()`
  exposes a sub-agent as a callable tool; the sub-agent runs its own loop
  internally and only its result re-enters the caller's context via a
  `custom_output_extractor`. This is the concrete precedent for "return only
  the finalized result, not the trace" (relevant to Replacement B).
- **LangGraph's supervisor pattern** uses non-overlapping state-schema keys
  between a subgraph and its parent so subgraph-internal state never leaks
  back — the same isolation property this spec needs from `itemVisibility`
  when a `goalSeekLoop` runs as a tool (§4.6).
- **CrewAI's hierarchical-delegation mode** is a cautionary case: multiple
  reports describe delegation silently degrading into the manager doing the
  work itself when the worker's input schema isn't strict. This is the
  concrete argument for keeping worker-tool `inputSchema`s exactly as strict
  as any other tool (no special-casing "delegation tools").
- **OWASP guidance on eval/deserialization** directly supports "assignment by
  key, resolved against a closed registry, never by embedded/dynamic code
  reference" — exactly the existing `task.assignee` → `TaskWorkerRegistry[assignee]`
  convention this spec reuses (§4.5), and the reason `blockRef`/`agentRef`
  workers must stay app-code references, never embedded in a skill folder.

(reference-equality collision detection on duplicate field names, not
last-wins). `ctx.self` is typed `StateRef<TSelfState>` — the **same** interface
`ctx.sequencer` and `ctx.request` already implement (`packages/core/src/types/block.ts`

comment written for this exact ticket:

> "Input schema forwarded to the OUTER sequencer verbatim, so a re-expressed
> pattern keeps its public block metadata (and survives `GeneratorTool`
> wrapping — FIX-918 forward-compat)."

And the mechanism it's forward-compatible with already exists generically:
`GeneratorTool = BlockDefinition<any, any>` (`packages/core/src/blocks/generator.ts`),

branching. **So "any block, including a whole `goalSeekLoop`, can already go
in a `tools:` array" is true today, with zero new framework code required.**
What's unverified: no test or production code has ever exercised this (zero
grep hits for a `SequencerDefinition` inside a `tools:` array), and the
composite item-visibility case (a multi-step sequencer, with mixed internal
visibility, running as one tool call) has no coverage — see §4.6.

Deleting `defaultPatternRegistry` without migrating these breaks the
monorepo build, not just a stale doc. `research-company` and
`competitor-analysis` (both copies) are genuinely **Shape 2** — a fixed or
dynamically-grown task graph run to completion under explicit
concurrency/dependency dispatch — which Shape 1's executive-serialized tool
calls cannot reproduce without changing their observable behavior (parallel
analyst dispatch would become however the model happens to sequence tool
calls, which is not equivalent). `tech-brief` is the one skill simple enough
to become a genuine Shape 1 delegation-preset example. See §4.10 for the
concrete per-skill migration plan.

**Existing "assignment by key" precedent** (not new — reused directly):
`Task.assignee: z.string().optional()`; `packages/orchestration/src/task-board/blocks/worker-step.ts`
already dispatches a `TaskWorkerRegistry` by `task.assignee` through
`keyedRouter({ blocks, select: (task) => task.assignee })`
(`packages/core/src/utility/keyed-router.ts`, "promoted from three hand-rolled
routers across the patterns package"). Replacement A's "assignment by key,
never by block reference" is this exact convention, just exposed as
individually-named tools instead of routed through a `keyedRouter` sequencer
step (there's no drain loop to route inside — the executive calls the named
tool directly).

### 3.4 Necessity check — the six questions

1. **What existing primitive could a user adopt today?** Pattern mode itself
   already delivers *a* form of delegation. But it's not a primitive a user
   composes — it's a closed, session-global dispatcher requiring `pattern:`
   frontmatter, mutually exclusive with `inline`/`fork`, with no way to give
   one generator its own private board without going through the pattern
   route. There's no way today to say "let this ReAct loop delegate, but stay
   the orchestrator itself."
2. **What does this add that pattern-mode doesn't?** (a) **Composition with
   existing framework features that wouldn't work outside the framework's
   resolution path** — own-state (`ctx.self`), capability merge, and
   `atomicState` are all framework-internal machinery; a user can't replicate
   "a private, collision-free board namespaced by the block itself" in
   userland. Strongest case. (b) **New vocabulary that shapes reasoning** — "a
   skill can delegate" becomes a capability preset instead of a whole
   execution mode; "a deterministic flow is just a tool" is a real mental
   model shift. (c) Removes ~900 lines of bespoke session-global dispatch
   machinery in exchange for composing primitives that already exist for
   other reasons (BP-029).
3. **Does the cited precedent transfer?** Yes — FIX-911's own-state
   contribution (`library.ts`'s conditional `stateSchema` for `activeSkills`)
   is the *same* mechanism this spec reuses for the task board, not a
   syntax-alike. Confirmed by reading the actual merge code (`merge.ts`), not
   assumed.
4. **Single-vendor knowledge?** None — this is pure internal framework
   architecture. No provider-specific identifiers anywhere in this design.
5. **Does an error path hide the real problem?** No new "wrong provider/context"
   guard is introduced. The one error condition that does change
   (`no_active_pattern` → a new sentinel) is a resolution-failure UX contract
   already present today, preserved, not newly invented to compensate for a
   bad abstraction.
6. **Path-of-least-resistance test.** Shipping this establishes "a capability
   composes task-board + tool infrastructure onto a generator" as the general
   pattern for delegation. That's a generalizable direction (matches how
   `taskBoard()`'s own capability accessor and `taskTools` already work
   standalone in `packages/integration-tests/src/scenarios/fixtures/pattern-skill-task-board-flow.ts`,
   bypassing the pattern route entirely) — not a special-case dead end.

None of the "push back" signals fire: this isn't a `boolean | Config` toggle
resolving to one factory call with no other delta; it isn't single-vendor;
existing primitives don't already give a 1–3 line escape hatch for
"delegate but stay the orchestrator"; the precedent (own-state) genuinely
transfers; there's no provider/platform guard error in the design.

**On the fork removal specifically** (a pure subtraction, not a build): the
necessity question inverts — the burden is on *keeping* fork, not removing it.
Fork is a whole dispatch shape and a second "spawn a child like the parent"
resolution problem (FIX-919's central design difficulty) serving a capability
whose isolation half delegation + the task board already deliver, and whose
inheritance half is deferred to FIX-920. It has zero consumers. Removing it is
textbook BP-038 (subtract before you add; delete the path you supersede). The
one thing to be honest about — the temporary loss of "sub-agent inherits the
prior conversation" — is a product call the owner has made explicitly, not a
gap this spec is glossing over (recorded in §5 KD1 and §8).

**Verdict: Build as scoped** (pattern replacement + fork deletion).

## 4. Technical Design

### 4.1 Where delegation lives: a preset on `createSkillsLibrary`, not a standalone capability

**Decision:** delegation ships as a `delegation` preset on the existing
`createSkillsLibrary` capability (`library.ts`), consumed the same way
`dynamicActivation` is today:

```ts
const skills = createSkillsLibrary({ catalog, initialSkills });
generator({
  uses: [
    skills.with({
      active: ["research-lead"],
      presets: { delegation: true },        // private own-state board (default)
      // or: presets: { delegation: { board: mySharedBoard } }
    }),
  ],
});
```

This is a deliberate rejection of a fully standalone `createDelegationCapability`
composed via its own `uses` entry (the design notes' phrasing — "a capability
installs..." — didn't specify placement). The reason: delegation needs to read
the *active skill's* declared workers (§4.4), and `createSkillsLibrary` is
already the thing that resolves "which skill is bound to this generator and
what does its body/frontmatter say" (it does the same for `dynamicActivation`
today). A standalone capability would need its own parallel "which skill is
active" resolution, duplicating what the library already does. See Key
Decision 3 (§5) for the full ramification.

### 4.2 New task-board backing: `"own-state"`

`getOrCreateTaskCollection` (`packages/orchestration/src/tasks/collection/get-or-create.ts`,
198 lines) currently supports three backings: `"sequencer"`, `"resource"`,
`"request"`. None is block-scoped/collision-free by construction — `"request"`
is the closest, but it lives on the *whole request's* state namespaced only
by a hand-chosen `stateKey`, which is exactly the kind of hand-namespacing
FIX-914 was built to eliminate elsewhere. Add a fourth:

```ts
export interface OwnStateBackingSpec extends CommonOptions {
  backing: "own-state";
  /** The block's own state ref (`ctx.self`), contributed via the
   * delegation preset's `stateSchema`. Already `StateRef`-shaped —
   * no adapter needed, unlike `requestStateRef()`. */
  self: StateRef<Record<string, unknown>>;
  stateKey?: string;
}
```

Implementation: add a fourth branch to `getOrCreateTaskCollection` that calls
`createSequencerBackedTaskCollection({ sequencer: options.self, ... })` —
identical to the existing `"request"` branch's call, just passing `ctx.self`
directly instead of adapting `ctx.request` through `requestStateRef()` (no
adapter needed: `ctx.self` already satisfies `StateRef<Record<string, unknown>>`
per `packages/core/src/types/block.ts` line 232). This is a ~20-line addition
to a well-understood factory, not a new collection implementation.

The delegation preset's config resolver contributes
`stateSchema: z.object({ [TASK_BOARD_FIELD]: z.record(z.string(), taskSchema) })`
conditionally (mirroring `library.ts`'s existing `activeSkills` contribution
exactly), and its tools call `getOrCreateTaskCollection({ backing: "own-state", self: ctx.self, ... })`
to get a working `TaskCollectionRef` scoped to that generator alone.

### 4.3 `taskTools`, decoupled from the pattern-activation lookup

`createTaskToolsCapability()` (`task-tools-capability.ts`, 241 lines) keeps
its eight handler bodies (`addTask`/`assignTask`/`completeTask`/`failTask`/
`blockTask`/`cancelTask`/`updateTask`/`listTasks`) verbatim — only the board
resolution changes. Today:

```ts
async function getCollection(ctx: BlockContext): Promise<TaskCollectionRef | undefined> {
  return getActivePatternCollection(ctx);   // walks activeSkills for mode: "pattern"
}
```

Becomes a parameterized factory:

```ts
export function createTaskToolsCapability(
  resolveCollection: (ctx: BlockContext) => Promise<TaskCollectionRef | undefined>,
): DefinedCapability { /* same 8 tools, getCollection = resolveCollection */ }
```

The delegation preset supplies a resolver that either (a) resolves the
own-state board via `getOrCreateTaskCollection({ backing: "own-state", ... })`
(default), or (b) returns the passed-in shared board's collection when
`presets: { delegation: { board } }` supplies one. `active-pattern-collection.ts`
is deleted outright — nothing calls it once pattern mode is gone. The
`{ ok: false, error: "no_active_pattern" }` UX contract (recover gracefully,
never throw) is **preserved** under a renamed sentinel (`"no_delegation_board"`
or similar) — this is a UX guarantee worth keeping even though its cause
changes.

### 4.4 Worker declaration: a decoupled `workers:` frontmatter field

**Decision:** workers stay declared in the skill's own SKILL.md, via a new
`workers:` frontmatter field parsed independent of `pattern:` — not moved to
app-level TypeScript config. This is the single most consequential
interpretive call in this spec; see the Open Questions (§11) for the
alternative and why it's flagged for explicit sign-off despite the
recommendation below.

The issue's "Remove" list includes "frontmatter parsing of `pattern:` /
`workers:` / `initial-tasks:`" — read together with its "Keep" list ("Workers:
prompt/promptRef are portable data... **safe to define inside a (portable)
skill**"), the removal is of the *old*, `PatternBinding`-coupled `workers:`
parser (which required `pattern:` to also be present and fed a rigid
`pattern-config:` crosswalk) — not of the ability to declare workers in a
skill file at all. If `prompt`/`promptRef` workers must remain "portable data
inside a skill," they need a place to live in the skill file, since moving
them to app TypeScript config would mean a portable skill folder can no
longer ship its own delegation behavior — a real regression against the
design notes' explicit intent.

So: `skill-md.ts` keeps a `workers:` field, but its parser (`parseWorkersField`/
`parseWorkerSpec`, kept structurally) drops every `PatternBinding`-specific
dependency: no `pattern:` requirement, no `pattern-config:` crosswalk, no
mutual-exclusivity check against `context`. A skill declares `workers:`
alongside `context: inline` — the only remaining mode after fork and pattern
are gone (§4.11). `initial-tasks:` is **not** re-added — Shape 1 delegation
has no seed/drain step (the executive adds its own tasks via `addTask`), so
there's nothing for a seed list to feed.

`blockRef`/`agentRef` workers still require an app-supplied registry
(`blocks`/`agentRegistry` passed to the delegation preset's config) to
resolve the string key — unchanged from today; only `prompt`/`promptRef`
workers are "fully portable."

### 4.5 Worker materialization: reuse `materializeWorker`, trim its dependencies

`materializeWorker(workerKey, spec: WorkerSpec, deps)` already returns a plain
`BlockDefinition` — type-identical to `GeneratorTool`, so **no new wrapping is
needed** to make a materialized worker callable as a tool; it's dropped
straight into the executive's `tools:` array, named by its worker key. Trim
`PatternRegistryDeps` (currently: `catalog, blocks?, agentRegistry?,
capabilityCatalog?, materializeAgent?, skillName, skillCollection,
defaultModelId?, input?, collectionId`) to a smaller `WorkerMaterializationDeps`
dropping only the fields that were pattern-specific (`collectionId` — no
board-scoped collection id needed per worker; the board itself is resolved
separately per §4.3). Everything else — `blocks`/`agentRegistry`/
`materializeAgent`/`capabilityCatalog`/`skillName`/`skillCollection`/
`defaultModelId` — is reused verbatim; this is the exact taxonomy dispatch
(`blockRef → agentRef → promptRef → prompt`) the delegation preset needs.

The delegation preset's `tools` contribution becomes: for each worker key in
the active skill's parsed `workers:` map, call `materializeWorker(key, spec, deps)`
and install the resulting `BlockDefinition` under that key's name in the
executive's tool list. Task `assignee` strings match these keys directly —
no `keyedRouter` needed, since the executive's own tool-loop already
dispatches by tool name.

### 4.6 Blocks-as-tools: verify, don't invent

Per §3.3, the general mechanism (`GeneratorTool = BlockDefinition`) already
exists, applies equally to `goalSeekLoop` **and** a plain `taskBoard().drain`
sequencer (both are `SequencerDefinition`s), and `goalSeekLoop` was already
built anticipating it. **This spec does not add a new wrapper primitive up
front.** Instead:

1. Write the first-ever test placing a `goalSeekLoop`-based block inside a
   generator's `tools:` array (`packages/orchestration/test/task-board/goal-seek-loop-as-tool.test.ts`),
   using `mockGenerator` (`packages/testing/src/mocks/mockGenerator.ts`) to
   script the tool call.
2. Assert: the tool call's result is the `finalize` step's projected output
   (not the raw trace); internal per-iteration items (worker generator
   outputs, judge verdicts, replan steps) resolve to non-history visibility
   in the calling generator's assembled history.
3. **If** the test finds a real leak — e.g., `goalSeekLoop`'s internal
   `judgeStep`/replanner-invocation/`coerceAtCap` steps emit bare
   `ctx.emit.component`/message calls without explicit `itemVisibility`, so
   they default to `{client:true, history:true}` and leak into the caller's
   history — patch those specific emit call sites in `goal-seek-loop.ts` to
   declare `itemVisibility: { client: true, history: false }` explicitly.
   This is a targeted fix to existing emit calls, not a new framework
   primitive (Key Decision 6, §5).

### 4.7 Usage example (before/after)

**Before** (pattern-mode SKILL.md, removed by this spec):

```yaml
---
description: Research a topic using a lead + two specialists.
context: pattern
pattern: task-board
workers:
  researcher: { prompt: "You research assigned subtopics." }
  writer: { prompt: "You synthesize findings into a report." }
pattern-config:
  max-iterations: 4
---
```

**After** (app code composes the delegation preset; the skill body stays
plain instructions + a decoupled `workers:` field):

```yaml
---
description: Research a topic using a lead + two specialists.
context: inline
workers:
  researcher: { prompt: "You research assigned subtopics." }
  writer: { prompt: "You synthesize findings into a report." }
---
You are the research lead. Use `addTask` to hand out subtopics to `researcher`
and `writer` via their tools, and `listTasks`/`completeTask` to track progress.
```

```ts
const skills = createSkillsLibrary({ catalog, initialSkills });
const researchLead = generator({
  uses: [skills.with({ active: ["research-lead"], presets: { delegation: true } })],
});
// researchLead now has: addTask/assignTask/completeTask/... (taskTools),
// plus a `researcher` tool and a `writer` tool, each a materialized worker.
```

**Blocks-as-tools (new, no "before" — this capability didn't exist)**:

```ts
const deepResearch = goalSeekLoop({
  name: "deep-research",
  inputSchema: z.object({ question: z.string() }),
  board, seed: planQuestions, judge: assessCoverage,
  replanner: proposeFollowups, maxIterations: 4, finalize: synthesizeAnswer,
});
const chatAgent = generator({
  tools: [deepResearch],   // callable directly — no wrapper needed
});
```

### 4.8 State management

- **New:** own-state task board (`ctx.self`), contributed by the delegation
  preset's `stateSchema`, scoped to the one generator that installed it —
  never visible to or namespaced against any other block.
- **Modified:** `activeSkillsArraySchema`'s `mode` enum shrinks from
  `"inline" | "fork" | "pattern"` all the way to `"inline"` (both non-inline
  modes removed — pattern here, fork in §4.11). This schema is shared by both
  the legacy v1 (`active-skill-state.ts`) and v2 (`library.ts`/`load-tool.ts`)
  surfaces — both need the change together, and both must tolerate a stale
  persisted `"fork"`/`"pattern"` entry on resume (§6, the enum-shrink
  edge-case row; BP-030).
- **Unchanged:** `taskTools`'s eight tools' input/output shapes; `TaskInit`,
  `Task`, `TaskCollectionRef` (all in `packages/orchestration/src/tasks/`).

### 4.9 Error handling

- Delegation preset installed, active skill has no `workers:` block: board +
  `taskTools` still install; zero worker-tools; assigning to an unknown key
  fails at the point of use (no static workers to validate against bind
  time), not silently.
- Unknown/missing `blockRef`/`agentRef`: same fail-loud error
  `materializeWorker` already raises today — unchanged, not weakened.
- Board resolution failure (no active delegation, e.g. a stray `taskTools`-only
  consumer with no delegation preset): the renamed `{ ok: false, error: "no_delegation_board" }`
  sentinel — recover gracefully, never throw, matching today's `no_active_pattern` contract.
- Legacy `pattern:` frontmatter found post-removal: `skill-md.ts`'s parser
  fails loud with an explicit "pattern mode removed; see the `delegation`
  preset" message — never silently reinterprets the file as `inline`.
- Legacy `context: fork` found post-removal: parser fails loud with a
  "fork mode removed" message (§4.11, §6) — never silently downgrades to
  `inline`.

### 4.10 Migrating the real pattern-mode consumers

Not a synthetic exercise — these are the actual skills that break without a
migration plan (§3.3), and using them as goal checks (§7) is stronger proof
than a hand-built test fixture.

**`tech-brief` → `delegation` preset (Shape 1).** One worker, no
concurrency/dependency config, `visibility: primary` (its output is already
meant to surface directly). Rewrite frontmatter to drop `pattern:`/`pattern-config:`,
keep a decoupled `workers: { briefer: { agent-ref: tech-briefer } }`. The
skill body's instructions change from "call `runSkill`" to "call the
`briefer` tool, then return its result" — the executive generator now
dispatches directly instead of going through the pattern router.

**`research-company` / `competitor-analysis` (and their `examples/guides/research-team`
mirrors) → task-board-drain-as-tool (Shape 2 / Replacement B).** These keep
their existing worker prompts, `initial-tasks:` graph (or runtime fan-out via
`taskTools`, for `competitor-analysis`'s discoverer), and `pattern-config:`
concurrency/dispatcher values — but re-expressed as a plain code-defined
block (`taskBoard({...}).drain`, composed with a `finalize` step projecting
the settled board into a synthesized report, mirroring `goalSeekLoop`'s own
`projectBoard`/`finalize` shape but without a judge/replan loop, since these
skills don't need one). That block is referenced by the skill (`blockRef`,
per the existing app-code-reference taxonomy — these are app-specific
blocks, not portable skill-folder data) and the executive generator calls it
**as a single tool**. The board's own concurrency/dependency dispatch
(already proven, unchanged from `worker-step.ts`'s `keyedRouter`-based
assignee dispatch) does the parallel/topological work exactly as it does
today; only the *invocation path* changes (pattern-router dispatch → direct
tool call), not the dispatch semantics.

`examples/guides/research-team/src/skills.ts` drops its `defaultPatternRegistry`
import and `patternRegistry:` option entirely; its two `SKILL.md` files and
`test/board.test.ts`/`test/research-router.test.ts`/`test/flow.test.ts` update
to match. The kitchen-sink equivalents migrate the same way — `apps/kitchen-sink/flows/chat-agent/shared/capabilities/features.ts`
drops its `defaultPatternRegistry` import.

### 4.11 Removing fork mode and collapsing `SkillContextMode`

Fork is a straight deletion (§3.3 fork inventory) — no replacement, no
migration, because nothing declares `context: fork`. The care needed is
entirely in *not over-removing* shared surface and in landing the
taxonomy-collapse edits cleanly.

**The mode enum collapse.** `SkillContextMode` (`packages/core/src/types/skill.ts:36`)
and `activeSkillsArraySchema.mode` (`active-skill-state.ts:70`) both currently
enumerate `"inline" | "fork" | "pattern"`. Removing fork here and pattern in
§3.3's pattern removal leaves a single-value enum, `"inline"`. Two choices,
flagged as an open question (§11):

- **Keep `SkillContextMode = "inline"` as a one-value type.** Minimal churn;
  the field and its readers (`SkillState.contextMode`, `Skill.contextMode`,
  `RunSkillOutput.mode`, `unionAllowedTools`'s `mode === "inline"` filter) all
  keep compiling; leaves a forward-compat seam if a future mode is ever added.
- **Retire the concept entirely.** Remove `contextMode` from the skill types
  and every reader, on the argument that a one-value discriminator is dead
  weight (BP-038). Larger diff, touches more files, but arguably the honest
  end state of "a skill is inline instructions."

Recommendation: **keep the one-value enum for this PR** (smaller, safer,
reversible), and flag full retirement as a follow-up — the enum being
single-valued is not itself a bug, and collapsing it to nothing is a
separable cleanup that shouldn't gate the fork/pattern removal. This is the
conservative BP-035 call (test the off/new state of the change without also
taking on an adjacent refactor).

**`RunSkillOutput.mode`.** Collapses to `z.literal("inline")` (or the
one-value enum). Any caller matching on `"fork"`/`"pattern"` is dead code to
remove; grep confirms the only branches are inside the router being gutted.

**The shared `forkModelId` option.** Named for fork but also threaded into the
pattern route as `defaultModelId` (`run-skill-tool.ts:191`) and exposed on
`createSkillsCapability`/`createRunSkillTool`. Since both fork and pattern
consumers of it are being removed, the option has no remaining consumer inside
the skills runtime — **remove it** rather than rename it, unless the
delegation preset's materialized workers need a model override, in which case
the delegation preset should carry its own explicitly-named option
(`workerModelId` or similar), not inherit `forkModelId`'s misleading name.
Flagged in §11.

**`SkillState.outputSchema`.** Its JSDoc says it held "the fork-mode subagent's
structured output"; grep shows it's populated by the `output-schema`
frontmatter parse (`skill-md.ts:1094-1096`) and consumed by fork. If nothing
else reads it after fork is gone, remove the field and its parse; verify
during implementation (a `fsdev block`/grep check, not a guess).

**Agent-level fork stays.** `AgentOverrides.contextMode` (`agent.ts:89`) is a
separate inline `"fork" | "inline"` literal, not `SkillContextMode`; its only
consumer (`materialize-agent.ts`) already warns-and-composes-inline for
`"fork"`. This spec does not touch it. (If the project later wants to remove
the agent-level fork affordance too, that's its own change against the
workforce package — out of scope here, noted in §8.)

## 5. Key Decisions & Ramifications (top 6)

1. **Remove fork mode outright (not relocate it), superseding FIX-919 and its
   in-review PR #844.** Rejected alternatives: (a) land FIX-919 as designed —
   keep fork, fix it to inherit history, move it to a `fork` preset; (b) leave
   fork on the legacy `runSkill` router untouched while only pattern is
   removed. **Ramification:** the load-bearing one in this spec.
   `SkillContextMode` collapses to a single `"inline"` value and an entire
   dispatch shape is deleted — the cleanest possible end state for "a skill is
   inline instructions plus optional delegation." The cost is real and named:
   between this landing and **FIX-920** there is **no** way to spawn a
   sub-agent that inherits the full prior conversation (fork's distinctive
   property; a delegation worker gets its task input, not the conversation).
   The *isolation* half of fork (a sub-agent whose work is hidden from the
   parent's history) is already covered by delegation + the task board
   (`itemVisibility: { client: true, history: false }`), so what's deferred is
   specifically history-inheritance-into-a-child, which FIX-920 will deliver
   through task management. This is an owner decision, made with the tradeoff
   in view — not a research finding of this spec. Concrete waste incurred:
   PR #844's ~1000 lines of working fork-rework are thrown away (closed
   unmerged). Zero `context: fork` SKILL.md consumers exist, so no shipping
   skill breaks. If FIX-920 slips, the gap persists — acceptable per the owner,
   flagged here so it's a conscious risk.
2. **Direction B (no harness) over Direction A (`skillHarness` owns the
   loop).** Rejected alternative: a block wrapping the generator that owns an
   outer GoalSeek loop and enforces whole-turn convergence across every
   active skill's goals. **Ramification:** whole-turn enforced convergence is
   deliberately *not* a framework primitive — it decomposes into rigorous
   delegation (enforcement inside the called flow) plus enforced output
   gating (`response-auditor`). If a genuine "must enforce the whole turn on
   the generator's own top-level output, and neither of those two covers it"
   case appears later, this decision needs revisiting — none has been
   identified to date (design notes §5, "Still open").
3. **Delegation ships as a preset on `createSkillsLibrary`, not a standalone
   capability.** Rejected alternative: a fully independent
   `createDelegationCapability` composed via its own `uses` entry.
   **Ramification:** ties delegation's lifecycle to the skills-library
   binding surface — a generator can only get delegation through a bound
   skill, not independently of the skills system. `library.ts` grows a
   `delegation` preset alongside its catalog/context surface, a cohesion
   cost, but avoids building a second "which skill/body is active" resolution
   path that would duplicate what the library already does. (With fork
   removed, `delegation` is the *only* execution-shape preset added here — the
   `fork` preset FIX-919 would have added does not land.)
4. **Workers stay skill-declared via a decoupled `workers:` frontmatter
   field, not moved to app-level TypeScript config.** Rejected alternative:
   fully TS-declared workers on the consuming capability's config (cleaner
   separation, type-checked at the call site). **Ramification:** `skill-md.ts`'s
   frontmatter-parsing surface does not shrink as much as "remove pattern
   mode" might suggest — a `workers:` parser survives, just decoupled from
   `PatternBinding`. In exchange, prompt/promptRef delegation stays portable
   inside a shareable skill folder, matching the design notes' explicit
   intent ("safe to define inside a (portable) skill"). This is the single
   biggest interpretive call in this spec — flagged in Open Questions (§11)
   for explicit sign-off before implementation starts.
5. **New task-board backing built by adapting `ctx.self` (already
   `StateRef`-shaped), not a bespoke collection implementation.** Rejected
   alternative: reuse the existing `"request"` backing with a manually
   chosen, hand-namespaced `stateKey`. **Ramification:** preserves the
   collision-free-by-construction property FIX-914's own-state was built to
   deliver; a hand-namespaced request field is exactly the smell FIX-914
   exists to eliminate elsewhere in the codebase, so reintroducing it here
   for the one new backing this spec needs would be a regression against the
   framework's own stated direction.
6. **Migrating the three real pattern-mode consumers (`apps/kitchen-sink`'s
   `tech-brief`/`research-company`/`competitor-analysis` and their
   `examples/guides/research-team` mirrors) is in scope, split by shape —
   not deferred or stubbed out.** Rejected alternatives: (a) delete/stub
   these skills instead of migrating them, treating them as disposable demo
   content; (b) force all of them onto the `delegation` preset for
   consistency. **Ramification:** (a) would leave the monorepo build broken
   the moment `defaultPatternRegistry` is deleted — validation research
   confirmed `pnpm test` runs `examples/guides/research-team`'s test suite
   today via the workspace's `turbo run test`, so this isn't cosmetic;
   deleting rather than migrating trades a clean spec boundary for a broken
   build, which this spec rejects. (b) would silently change
   `research-company`/`competitor-analysis`'s observable behavior — their
   `pattern-config: { concurrency, dispatcher: topological }` and
   dependency-gated tasks rely on the task board's own deterministic
   dispatch, which Shape 1's executive-serialized tool calls cannot
   reproduce. The two shapes are kept distinct (§4.10): `tech-brief` →
   `delegation` preset (Shape 1, its one worker has no concurrency needs);
   `research-company`/`competitor-analysis` (both copies) → a
   task-board-drain-as-tool block (Shape 2/Replacement B), which is also
   this spec's strongest goal check — proof against real skills, not a
   synthetic fixture. `goalSeekLoop`-as-tool itself still ships via the
   existing generic `GeneratorTool = BlockDefinition` mechanism, verified
   and patched only if a real item-visibility leak is found (§4.6) — no new
   wrapper primitive is built preemptively.

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|---|---|
| Delegation preset enabled, bound skill has no `workers:` block | Board + `taskTools` install; zero worker-tools; assigning an unknown key fails at first use with a clear error, not at bind time (no static roster to validate against) |
| Two active skills on one generator both declare a worker under the same key (e.g. both have a `researcher` worker) | Fail loud at bind time on key collision — never silently last-wins |
| App passes a shared `board` (`presets: { delegation: { board } }`) instead of using the private own-state default | `taskTools` and worker-tools resolve against the shared board's `capability` accessor; the own-state `stateSchema` contribution is skipped entirely on that branch |
| `blockRef`/`agentRef` worker declared but the app never registered that key | Same fail-loud error `materializeWorker` raises today — preserved, not weakened |
| A `prompt`/`promptRef` worker itself needs `taskTools` (to add sub-tasks back to the same board) | Worker's `uses: [taskTools]` must resolve the *same* board instance the executive's `taskTools` resolves — not a fresh, disconnected one |
| `goalSeekLoop`-based tool call hits `maxIterations` without the judge returning `"done"` | Tool call still returns (existing cap-coercion + `finalize` handle this per FIX-910); the calling agent should be able to tell the result was cap-terminated, not organically completed (surface via the finalize projection, not a thrown error) |
| Old `pattern:` frontmatter present in a skill folder post-removal (unmigrated) | Parser fails loud with an explicit "pattern mode removed, see delegation" message — never silently reinterprets as `inline` |
| Old `context: fork` frontmatter present post-removal (external skill folder, not in this repo) | Parser fails loud with an explicit "fork mode removed" message pointing at delegation / FIX-920 — never silently downgrades to `inline` and runs the body in-context (which would leak the sub-agent's work into the parent, the opposite of what the author asked for) |
| `activeSkillsArraySchema`'s mode enum shrinks (`"pattern"` and `"fork"` removed → `"inline"` only) | A persisted session/request with a stale `mode: "pattern"` or `mode: "fork"` entry from before this ships must not crash on resume — dual-read/tolerate per BP-030, even though the entry is now inert |
| Agent-level fork (`AgentOverrides.contextMode: "fork"`) in an app's agent config | Unchanged — this spec removes only *skill* fork; the agent-level affordance keeps its current warn-and-compose-inline behavior (`materialize-agent.ts`). Not a regression, an unchanged boundary |
| A skill's `pattern-config:` declares `concurrency`/`dispatcher` (dependency-graph dispatch) | This is a Shape 2 signal, not Shape 1 — migrate to a task-board-drain-as-tool block (§4.10), never to the `delegation` preset, or the concurrency/dependency behavior silently changes to whatever the model's own tool-call ordering happens to produce |
| `competitor-analysis`'s discoverer worker fans out new tasks at runtime via `taskTools` mid-drain | The task-board-drain-as-tool block's `taskTools`-equipped worker must resolve the *same* board the drain is iterating, so dynamically queued tasks are picked up by the still-running drain — not a disconnected board instance |

**Error taxonomy:** all `taskTools`/worker-tool failures stay in the existing
`{ ok: false, error: string }` structured-return contract (never thrown) —
this spec renames one sentinel (`no_active_pattern` → `no_delegation_board`)
and adds none. Two new *fatal, load-time* errors, both fail-loud and
non-retryable (the file needs migrating, not retrying): the legacy `pattern:`
frontmatter rejection and the legacy `context: fork` rejection.

## 7. Testing Strategy

**Goal (observable outcome):** an executive generator bound to a delegating
skill can hand sub-work to named workers through ordinary tool calls it
chooses to make itself, and a deterministic multi-step flow (a task-board
drain or `goalSeekLoop`) can be called by any generator as a single tool
without its internal steps leaking into the caller's history — proven
against the real skills this repo already ships, not just a synthetic
fixture.

**Goal check (real path, run by hand, not CI):**

1. `fsdev run` the migrated `apps/kitchen-sink/skills/tech-brief` (now a
   `delegation`-preset skill) end to end. Inspect the NDJSON trace and
   confirm: (a) a private task board was created, (b) the `briefer`
   worker-tool was invoked by name, (c) the final response is the worker's
   briefing. PASS/FAIL on all three — this is the Shape 1 proof.
2. `fsdev run` the migrated `apps/kitchen-sink/skills/research-company` (now
   a task-board-drain-as-tool block) end to end. Confirm via NDJSON: (a) the
   tool call's result is the finalized synthesis, not the raw per-worker
   trace, (b) `market-analyst`/`financial-analyst` ran under the same
   concurrency the old `pattern-config: { concurrency: 2 }` specified, (c)
   `synthesizer` only started after both deps completed, (d) no
   non-`history:false` intermediate items from the nested drain leaked into
   the executive's history. PASS/FAIL on all four — this is the Shape 2 /
   Replacement B proof, and the strongest evidence in this spec that
   removal is safe.
3. `fsdev run` the migrated `competitor-analysis` specifically to confirm
   the discoverer's runtime `taskTools`-driven fan-out (queuing analyzer
   tasks mid-drain) is still picked up by the same drain instance, not lost.

**Discipline:** `fsd:tdd` (feature/enhancement) — red-green-refactor,
vertical tracer-bullet slices. This is new composition of existing
primitives plus one new backing, not a bug fix.

**Behaviors to test (tracer bullets, observable in terms of items/state/
return values):**

1. `getOrCreateTaskCollection({ backing: "own-state", self, ... })` builds a
   working `TaskCollectionRef` (mirrors existing sequencer/request-backing
   tests in the same file's test suite).

   board + `taskTools` + N worker-tools when the bound skill declares

5. Delegation preset with a passed-in shared board skips own-state
   contribution and resolves against the shared board's `capability`.
6. `goalSeekLoop`-based block runs correctly placed inside a generator's

7. Item-visibility: a tool-wrapped `goalSeekLoop`'s internal iterations

## 8. Non-Goals

- **New generic Shape 2 infrastructure beyond what this spec's three real
  migrations need.** This spec proves `taskBoard().drain` and `goalSeekLoop`
  are tool-callable (§4.6) and migrates the three specific skills that
  require it (§4.10) — it does not add a new pattern-recipe registry, a
  generic "board-drain-as-tool" factory function, or any new pattern
  factories beyond what FIX-910 already shipped. If a future skill needs the
  same shape, it follows the same manual `blockRef` wiring this spec
  establishes by example, not a new declarative surface.
- **Cross-skill/team-level shared boards that autonomously dispatch to many
  skills' workers** (the "workstream" tier in the design notes) — explicitly
  deferred, build-time-composed from a shared worker library, later.
- **Renaming/collapsing pattern→strategy terminology.** That was FIX-916,
  canceled and superseded by this issue; not resurrected here.
- **Reintroducing fork-like behavior in any form.** Fork is removed, full
  stop. "Spawn a sub-agent that inherits the conversation so far" is
  **FIX-920's** job (via task management), not this spec's — this spec does
  not build a partial or interim version of it. Callers who need sub-agent
  *isolation* today use delegation + the task board (already history-hiding);
  callers who need *inheritance* wait for FIX-920.
- **The workforce agent-level fork** (`AgentOverrides.contextMode: "fork"`,
  `materialize-agent.ts`) — a separate type and code path (§4.11), left
  exactly as-is. Whether to also remove that affordance is a future workforce
  change, not this spec.
- **Fully retiring `SkillContextMode`** (removing the now-single-value
  discriminator from the type surface and every reader). This spec keeps the
  one-value `"inline"` enum (§4.11, §11) — collapsing it to nothing is a
  separable cleanup that shouldn't gate the fork/pattern removal.
- **Full removal of the session-global `createSkillsCapability`/`runSkill`
  router shell.** This spec removes both the `pattern` and `fork` *routes*
  from the router, leaving it inline-only. Whether the inline-only router
  shell should then be deleted entirely (inline binding already lives on the
  FIX-911 `createSkillsLibrary` path) is a follow-up cleanup, not committed
  to here.
- **A generic `asGeneratorTool()` wrapper primitive** — built only if §4.6's
  verification step proves the existing generic mechanism has a real,
  unfixable item-visibility gap (Key Decision 6, see §5).
- **Deepening opportunities flagged, not fixed here** (from codebase
  research, follow up via `fsd:improve-codebase-architecture`):
  - `skill-md.ts` is a 1326-line single file mixing inline/fork/pattern
    frontmatter parsing. Excising fork- and pattern-specific parsing is in
    scope; splitting the file into per-concern modules is not.
  - `taskTools`'s board-resolution is generalized only as far as this spec's
    delegation-preset use case needs (an injected resolver function); a
    fuller "target a specific board among several" design is a follow-up.
  - No architecture doc names "any `BlockDefinition` can be a `GeneratorTool`"
    as an intentional, documented pattern — this spec adds a docs cross-link
    (§9) but not a fuller architecture-doc treatment.
  - `docs/specs/FIX-911.md`'s own "Pattern/fork untouched (FIX-910)" line is
    a stale cross-reference (FIX-910 shipped as the `goalSeekLoop` primitive,
    not a pattern→strategy rename) — worth a one-line correction when this
    ships; not fixed as part of this scope.
- **Already-rejected directions:** none found in `docs/internal/out-of-scope/`
  for this area (checked; no existing entry references skills/pattern-mode/
  delegation).

## 11. Open Questions

1. **Worker declaration surface (§4.4, Key Decision 4) — needs explicit
   sign-off.** This spec recommends keeping a decoupled `workers:` SKILL.md
   frontmatter field (portable prompt/promptRef workers stay in the skill
   folder). The alternative — moving worker declaration entirely to the
   delegation preset's TypeScript config — is cleaner/more type-safe but
   breaks portability for the common case. Given this shapes the whole
   `skill-md.ts` diff and the delegation preset's config surface, confirm
   before implementation starts.
