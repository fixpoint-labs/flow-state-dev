# FIX-918: Remove skill pattern/fork modes; deliver delegation as a board-commanded agent team — Implementation Spec

## 1. TLDR

**Plain-language summary.** A skill can hand parts of its work to a small team. Today the model running the skill has to call each teammate one by one, like phoning them individually, and a "task board" sits to the side as a to-do list that doesn't actually do anything. This spec flips that: the skill describes its team (each teammate is an *agent* — a prompt, defined right inside the skill so no app code is needed, or borrowed from a shared roster), assigns work as tasks on the board (this depends on that; these two can run at once), then says "go." The board runs the whole plan — parallel where it can, in order where it must — and hands back the results. The board is how work gets done, not a sticky-note list beside it.

**One-sentence technical statement.** Replace the delegation surface's per-agent direct-call "worker tools" with a board-commanded model: a skill declares `agents:` (inline-defined or registry-referenced), populates its own-state task board with `addTask` (assignee + deps + input), and executes the whole dependency graph by draining the board.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*
- **What we gain.** Skills orchestrate real dependency graphs (parallel + gated) instead of a serialized "call one teammate, wait, call the next" loop; teams are code-free and portable (agents live inside the skill folder); one concept — *agent* — replaces the parallel "worker" vocabulary; the board becomes the single, honest execution mechanism.
- **Where the work sits.** Almost entirely *removal and rename*, not new logic: delete the direct-call worker-tool path, rename `workers→agents`, collapse the four worker resolution fields to two agent shapes, and rewrite the two docs that teach the old model. The board drain, own-state board, agent materialization, and `taskTools` ledger already exist (PR #854) and are kept as-is.
- **Where the complexity actually is.** Not the happy path (that already runs). It's the collapse: making the delegation surface build a *board-only* surface (no host-side agent tools), and making inline agents materialize cleanly through one path (persona resolution, cross-skill dedupe) so an inline agent and a registry agent behave identically.
- **The risk.** Behavior change, not new failure modes: a skill that previously "called a worker tool" must now assign a task and drain. Caught by the example board tests (assign→drain) and a real-model goal check that asserts the coordinator's tool surface has no per-agent tool and work only completes via a drain.

**Deliverables** (grouped to mirror the Implementation Sequence):

- *Core (`@flow-state-dev/core`):* Rename `WorkerSpec` → `AgentSpec`; collapse resolution to inline-agent (`prompt`/`prompt-ref` + `tools`/`model`/`visibility`) or `agent-ref` (+ `agent-overrides`); remove `blockRef`. Rename `SkillState.workers` → `SkillState.agents`.
- *Orchestration — parser:* Rename `workers:` → `agents:` frontmatter with inline-agent/`agent-ref` parsing; remove `block-ref`; `workers:`/`block-ref` fail loud with a migration message; rename `serializeWorkers` → `serializeAgents`.
- *Orchestration — skills:* Rewrite the delegation surface to build a board **agent** registry (no per-agent host tools); keep `taskTools` + the board-drain tool; inline agents materialize via orchestration `materializeWorker` (board mode), registry agents via `agentRef`; delete `buildDirectWorkerGenerator` direct mode + the host-tool loop; frame the drain tool honestly (see §Technical Design); rewrite the guidance context to "assign and drain."
- *Examples:* research-team + kitchen-sink skills declare `agents:` (inline `prompt`/`prompt-ref`; research-team registers its handlers as registry agents); bodies assign tasks and drain the board.
- *Docs:* Heavy rewrite of `delegation.md` and `agents-command-the-board.md` (both teach the reversed "ledger + call worker tools" model); targeted fixes to the research-team guide, skills overview/binding/authoring, orchestration `agents.md`, and the orchestration README; changeset update.

**Size estimate.** **Medium** — multi-file across core + orchestration + two example apps + docs, but net predominantly removal + rename on top of PR #854's already-landed board substrate (no task-board substrate change; see §Non-Goals for the deferred tool-assignment work). Single PR (it supersedes PR #854 on the same branch). Docs are a meaningful slice of the diff.

## 2. Overview

Linear issue: [FIX-918](https://linear.app/fixpoint-labs/issue/FIX-918).

This spec supersedes the issue's original **Replacement A** ("one callable worker-tool per skill-defined worker … the board is a ledger; the executive's ReAct loop orchestrates"). Building that model (PR #854) showed it to be the wrong shape: it leaves the task board a passive to-do list beside the real work and forces the host generator to serialize sub-agent calls. The corrected model makes **the board the orchestration mechanism** — a skill assigns work as tasks and drains the board — and unifies "workers" into **agents** (prompt-driven participants defined inline in the skill or referenced from the agent registry).

The pattern/fork removal (the issue's core) already landed on PR #854; this spec keeps it and corrects the delegation surface built on top.

## 3. Background & Research

### Where we are (PR #854, branch `claude/fix-918-83h9lt`)

PR #854 removed `context: pattern`/`fork`, collapsed `SkillContextMode` to `"inline"`, and built a delegation surface that installs, per worker-declaring skill: a private own-state task board, the eight `taskTools`, **one direct-call tool per worker**, a board-drain tool, and a guidance context — workers materializing at runtime through an async tool-resolution seam. The direct-call worker tools are the vestige of Replacement A; they let the host bypass the board.

> **Baseline note.** This spec is authored against the **PR #854 branch** (`claude/fix-918-83h9lt`), and implementation continues on that branch — not from `main`. Two things PR #854 already landed are relied on here and do **not** exist on `main`: (1) the skills doc page was renamed `pattern-skills.md` → `delegation.md` (with a redirect); (2) `taskTools.addTask` gained an `input` field (`goal`/`assignee`/`deps`/`priority`/`input`/`metadata`), forwarded to the worker as `TaskWorkerInput.input`. Line references and "already exists" claims below are relative to the PR #854 branch. An implementer starting from `main` instead would additionally perform PR #854's rename and the `addTask` `input` addition. (Automated review against the `main` base will flag both as "missing" — that is the base-branch delta, not a spec gap.)

### How the substrate works (kept unchanged by this spec)

- **Board dispatch** (`packages/orchestration/src/task-board/blocks/worker-step.ts:178`): `buildWorkerStep` routes by `task.assignee` through a `utility.keyedRouter`; each registry entry is pre-wrapped `Task → TaskWorkerInput` via `packWorkerInput` (`:74`), with dep outputs materialized onto `TaskWorkerInput.deps`. Output records kind-agnostically via `recordSuccess`/`recordError` (`record-result.ts:40`/`:78`). All participants here are **agents** (blocks consuming `TaskWorkerInput`), so the existing registry path is exactly what we need — no substrate change.
- **Agents** (`packages/core/src/types/agent.ts:61`): the `Agent` type carries `persona` (`string | { template, state } | { path }`), `model`, `itemVisibility`, `outputSchema`, `allowedTools`, `usesCapabilities`. `materializeAgent({ shape: "worker", … })` already produces a `workerInputSchema`-consuming, board-ready block. Inline agents are constructed from an `AgentSpec` and materialized through orchestration's `materializeWorker` (board mode), which threads a drain-board-bound `taskTools` (`worker-materializer.ts:239-240`) — so an inline agent that lists `tools: [taskTools]` can enqueue follow-up tasks mid-drain (the runtime-fan-out case).
- **The board-drain tool** (PR #854's `runBoard`): a `sequencer` of `[board.drain, settle]` where `board` is a `taskBoard` whose collection is the executive's own-state board, and `settle` reads the settled collection and returns `{ status, tasks: [{ id, goal, status, assignee, output, error }] }`. See the framing note in §Technical Design.

### Why this approach

The board already *is* a concurrent, dependency-gated execution engine (`taskBoard(...).drain`). The corrected model stops treating it as a ledger and routes all delegated work through it. Unifying participants as agents matches the existing `Agent` type and the forward-compat note in `workers/types.ts:76`. Deferring tool-assignable tasks (FIX-925) keeps this PR to a rename + rewire with no substrate change; a step that needs a tool is assigned to an agent that carries the tool.

### Key Decisions & Ramifications (top 5)

1. **The board is the sole execution mechanism; remove the per-agent direct-call worker tools.** *Alternative rejected:* keep both (direct call for single-shot, board for graphs). *Ramification:* all delegated work is assigned as a task and executed by draining the board. A host "ask an agent a question" affordance (`askAgent`) is explicitly deferred (Non-Goals; overlaps FIX-920). This is the core correction and the reason the spec exists.

2. **Unify participants as agents (inline-defined or registry-referenced); remove `block-ref`.** *Alternative rejected:* keep the `workers` concept with `block-ref` for app code. *Ramification:* skills stay code-free and portable — an inline agent (persona + tools + model) travels inside the skill folder; app-defined participants come in as registry agents (`agent-ref`). We drop "assign an arbitrary app block as a participant"; an arbitrary unit of app logic will become a **tool** (FIX-925), and a prompt-driven participant is an **agent**. No third category.

3. **Defer tasks-assignable-to-a-tool to a follow-up (FIX-925); an agent carries its own tools.** *Alternative rejected:* land the agent-or-tool dispatch in this PR. *Ramification:* this PR needs **no task-board substrate change** (no registry-kind, no `worker-step.ts` adapter branch, no Task-schema question). A step that needs a deterministic tool call is assigned to an agent whose `tools:` include it; the agent calls the tool within its task. Slightly more expensive (an agent turn) but it also lets the agent handle surrounding work, and it keeps this PR to a clean rename + rewire.

4. **An inline agent reuses the existing core `Agent` type**, not a bespoke inline-worker shape. *Alternative rejected:* a new inline-participant type distinct from `Agent`. *Ramification:* the parser maps each `agents:` entry to an `Agent` (persona from `prompt`/`prompt-ref`, `allowedTools` from `tools`, plus `model`/`visibility`); a required `Agent.description` with no `AgentSpec` field is synthesized as a placeholder. Inline and registry agents share one materialization path and inline agents transparently gain persona-template / `usesCapabilities` / resources as those mature (FIX-921). Worker-shape output stays `z.string()` (structured per-task output is a follow-up).

5. **The drain tool is the skill's own board drained — not a second execution primitive; `runBoard` stays the explicit trigger.** *Alternative rejected:* auto-drain at end-of-turn now. *Ramification:* the skill body calls the drain tool once after assigning tasks; deterministic board lifecycle (auto-activation, drain-on-turn, drain guarantees, multi-board ownership) is deferred to a dedicated `skillController` block (new issue). The tool is a thin wrapper over `board.drain` (see §Technical Design) — its only jobs are binding the drain to the own-state board and returning task outputs instead of board-meta.

### The drain tool (framing — answers "runBoard vs drain")

There is **one** execution mechanism: the board's `.drain`. The model-facing tool the skill calls (named `runBoard`) is not a second concept — it is the executive's own-state board's `.drain`, wrapped so it (a) is bound to that own-state board (the raw `taskBoard(...).drain` block is bound to whatever collection its config resolves) and (b) returns the settled tasks' outputs. The raw drain's native output is a `task-board-meta` item (`terminationReason` + counts), which is not what the model needs; a one-line `settle` step re-reads the collection and returns `{ status, tasks: [{ id, goal, status, assignee, output, error }] }`. "Drain" and "run" are the same act — draining the board is running it. (Open question 1 records the alternative: expose the raw `.drain` and extend `listTasks` to include `output`, trading a projection for an extra model round-trip.)

### Data flow (assign → drain → read)

1. A worker-declaring skill is bound (or activated). The delegation surface builds, for that generator: the own-state board, `taskTools`, the drain tool, a guidance context (no per-agent tools). It builds the board's **agent registry**: one materialized worker per declared agent (inline via `materializeWorker` board mode; registry via `agentRef`).
2. The skill body calls `addTask({ goal, assignee, deps?, input? })` N times, then the drain tool once.
3. The drain claims pending tasks (deps-gated), routes each by `assignee` to its agent, dispatches the `TaskWorkerInput` envelope (with materialized dep outputs), and records each agent's output onto its task.
4. The tool returns the settled board; the skill reads the terminal task's output and surfaces it.

### API surface

**Core types** (`packages/core/src/types/skill.ts`):

```ts
// Renamed from WorkerSpec; block-ref removed. Exactly one of the two
// resolution shapes is set: an inline agent, or an agent-ref.
export interface AgentSpec {
  // Inline agent (portable, code-free): persona body + optional tuning.
  prompt?: string;            // inline persona body
  promptRef?: string;         // skill-folder-relative persona file
  // Registry agent:
  agentRef?: string;          // agent registry key
  agentOverrides?: AgentOverrides; // requires agentRef; replace-semantics (tools/model/visibility)
  // Inline-agent tuning (agentRef uses agentOverrides instead):
  tools?: string[];           // catalog keys this agent may call directly (incl. "taskTools")
  model?: string;
  itemVisibility?: ItemVisibility;
}
// SkillState.workers  ->  SkillState.agents: Record<string, AgentSpec>
```

**Skill frontmatter** (`agents:` replaces `workers:`):

```yaml
---
description: Multi-angle company research by a small team of analysts.
agents:
  market-analyst:                 # inline agent — travels with the skill
    prompt-ref: ./reference/market.md
    tools: [search, fetch]        # the agent calls these itself
  synthesizer:
    prompt: You synthesize the analysts' findings into one brief.
  scout:
    agent-ref: scout-agent        # registry agent (app-supplied)
---
Plan the work on your board, then run it:
1. addTask({ goal: "...", assignee: "market-analyst", input: { subject } })
2. addTask({ goal: "...", assignee: "synthesizer", deps: [<ids>] })
3. runBoard()
Surface the synthesizer task's output.
```

### Usage examples

**Before (PR #854 — host calls the worker tool):**
```ts
// model's loop: researcher("subtopic") -> inline result; then writer(...)
```
**After (board-commanded):**
```ts
const a = addTask({ goal: "market analysis", assignee: "market-analyst", input: { subject } });
const b = addTask({ goal: "financials",     assignee: "financial-analyst", input: { subject } });
addTask({ goal: "synthesize", assignee: "synthesizer", deps: [a.taskId, b.taskId], input: { subject } });
const board = runBoard();           // analysts run in parallel; synthesizer gated on both
// read board.tasks.find(t => t.assignee === "synthesizer").output
```

A full worked set across situations (none / one / parallel+gated / runtime fan-out / registry agent / code-defined board) is in the **Appendix**.

### State management

Unchanged from PR #854: the board lives on the host generator's own block state (`delegationBoardSchema.default({})`), resolved via `getOrCreateTaskCollection({ backing: "sequencer", sequencer: ctx.self, … })` with `changeVisibility: { client: true, history: false }`. No new scopes or fields.

### Error handling

- **Unknown assignee** (not in the agent registry): fails that task at dispatch (the existing `keyedRouter` throw → `recordError` → `fail`), unchanged.
- **Inline agent with an unresolvable `prompt-ref`**: fails loud at materialization (build-time for static-active skills; at tool-surface resolution for runtime-activated ones), same as the current prompt-ref path.
- **Legacy `workers:` / `block-ref` frontmatter**: fails loud at parse with a migration message (mirrors the pattern/fork migration-throw).
- **Registry agent using `tools: [taskTools]` for mid-drain fan-out**: resolves to the singleton own-state board, not the drain board (`MaterializeAgentOptions` has no `boardTaskTools` slot). Known limitation — use an **inline** agent for fan-out today (Non-Goals).

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
|---|---|
| Task assigned to a name not in the agent registry | Task fails at dispatch with the registry's "no participant" error; siblings continue under `onError: "skip"`. |
| Inline agent `prompt-ref` file missing | Fail loud at materialization with the file path (build-time for static, resolution-time for runtime activation). |
| Two active skills declare the same agent key with identical specs | Dedupe into one registry entry (as PR #854 already does). Divergent specs under one key → fail loud. |
| Legacy `workers:` or `block-ref` in a SKILL.md | Parse throws a migration message pointing at `agents:` / `agent-ref`. |
| `runBoard` called with an empty board | Returns immediately as `drained` (existing drain-on-empty behavior). |
| A step needs a deterministic tool call | Assign it to an agent whose `tools:` include the tool; the agent calls it. Direct tool-as-assignee is FIX-925. |
| Registry (`agent-ref`) agent lists `tools: [taskTools]` for fan-out | Resolves to the singleton own-state board, not the drain board (known limitation). Use an inline agent for fan-out. |
| Agent task output needs structure (not string) | Out of scope — worker-shape output is `z.string()`; the host reads `task.output`. Follow-up. |

Error taxonomy: dispatch/materialization failures are per-task (retryable per `maxAttempts`, else terminal `errored`); parse-time migration errors are fatal (author must migrate).

## 7. Testing Strategy

**Goal & goal check (required).** *Goal:* a skill that declares a team of agents can research a subject by assigning a dependency-ordered set of tasks and draining its board — parallel agents, gated synthesizer — and surface the synthesized result, without the host ever calling an agent as a direct tool. *Goal check:* `pnpm fsdev run research-team chat -i '{"message":"research ACME Corp"}'` against a real model (gpt-5.4-mini via the gateway). **PASS** = the trace shows the coordinator's tool surface is `[addTask…listTasks, runBoard]` with **no per-agent tool**, `runBoard` drains analysts-in-parallel → gated synthesizer, and the final output is the synthesizer task's report. **FAIL** = any per-agent worker tool present, or work completed without a board drain. (Same harness as PR #854, re-pointed at the corrected surface.)

**Discipline:** `tdd` (Feature/Enhancement) — red-green tracer bullets.

- Inline vs registry agent: an inline `prompt`/`prompt-ref` agent and an `agent-ref` agent both materialize into board workers and drain; an inline agent with `tools: [taskTools]` fans out mid-drain onto the drain board.
- Parser: `agents:` inline + `agent-ref` parse/round-trip; legacy `workers:`/`block-ref` throw the migration error.

## 8. Non-Goals

- **Tasks assignable directly to a tool (dynamic tool-call tasks).** Split to **[FIX-925](https://linear.app/fixpoint-labs/issue/FIX-925)** to keep this PR scoped. Interim: assign the task to an agent that carries the tool. That follow-up owns the task-board substrate work (participant kind, the `worker-step.ts` dispatch adapter, tool-task dep-output semantics).
- **`askAgent` (host asks an agent a question, not assigns work).** Future. The isolation/context-supply direction is tracked by **FIX-920** (fork as a task context-supply `conversation` mode, In Review); a Q&A affordance would build on that, not on a resurrected direct-call tool.
- **Auto-drain / `skillController` block.** Deterministic board lifecycle (auto-activation, drain-on-turn-end, drain guarantees, ownership of one or more boards) is deferred to a dedicated control block — file as a new issue. This spec keeps `runBoard` as the explicit trigger.
- **Structured (non-string) per-task agent output.** Worker-shape agents emit `z.string()`; structured task outputs are a follow-up.
- **Drain-board-bound `taskTools` for registry (`agent-ref`) agents.** Requires a `boardTaskTools` slot on `MaterializeAgentOptions` (a workforce change). Deferred — inline agents cover mid-drain fan-out.
- **Skill-defined resources / task blackboard.** Tracked by **FIX-921** (Backlog); complements inline agents (agent memory/resources) but is out of scope here.
- **Backward compatibility for a stored `workers:` skill (BP-030).** Not provided: `workers:`/`block-ref` fail loud at parse with a migration message, no dual-read/auto-migrate. Acceptable — `workers:` only ever shipped in the paused, unreleased PR #854, so there is no released persisted data to tolerate, and it mirrors the `pattern:`/`fork` migration-throw.

## Appendix — Skill examples across situations

Concrete end-state shapes, to validate the model. All assume `const skills = createSkillsLibrary({ initialSkills, catalog, /* + agentRegistry, materializeAgent for agent-ref */ })` and a generator bound via `skills.with({ active: [...] })` (or dynamic activation).

### A. No delegation — a plain skill

Zero board, zero agents, zero overhead. Just instructions spliced into the prompt.

```yaml
---
description: Rewrite text in the house style.
---
Rewrite the user's text: short sentences, active voice, no filler. Return only the rewrite.
```

### B. One agent — the simplest delegation (the old "fork" one-shot)

A single unit of work handed to one agent. Replaces "call the worker tool once."

```yaml
---
description: Produce a concise technology briefing.
agents:
  briefer:
    prompt: |
      You are a senior technology analyst. Write a concise, opinionated briefing:
      lead with the takeaway, then evidence, then risks. Cite every claim.
    tools: [search, fetch]      # the briefer calls these itself
---
Assign the briefing to your `briefer`, then return its result verbatim:
1. addTask({ goal: "Brief on <topic>", assignee: "briefer", input: { topic } })
2. runBoard()
Surface the briefer task's output.
```

### C. Parallel team + gated synthesizer (research-company)

Independent agents run at once; a synthesizer waits on both via `deps`.

```yaml
---
description: Multi-angle company research.
agents:
  market-analyst:    { prompt-ref: ./reference/market.md,    tools: [search, fetch] }
  financial-analyst: { prompt-ref: ./reference/financials.md, tools: [search, fetch] }
  synthesizer:       { prompt-ref: ./reference/synthesis.md }
---
1. m = addTask({ goal: "market positioning of <subject>",  assignee: "market-analyst",    input: { subject } })
2. f = addTask({ goal: "financial health of <subject>",    assignee: "financial-analyst", input: { subject } })
3. addTask({ goal: "synthesize a brief for <subject>", assignee: "synthesizer", deps: [m, f], input: { subject } })
4. runBoard()   // market + financial run in parallel; synthesizer starts when both complete
Surface the synthesizer task's output.
```

### D. Runtime fan-out — an agent enqueues its own work (competitor-analysis)

A discoverer agent with `taskTools` decides the fan-out mid-drain: it enqueues one analyzer task per competitor plus a gated synthesizer, and the same drain picks them up.

```yaml
---
description: Competitor analysis — the team decides the competitors.
agents:
  discoverer: { prompt-ref: ./reference/discover.md, tools: [search, taskTools] }
  analyzer:   { prompt-ref: ./reference/analyze.md,   tools: [search, fetch] }
  synthesizer:{ prompt-ref: ./reference/synthesize.md }
---
1. addTask({
     goal: "Identify 3-5 competitors for <topic>, then addTask one 'analyzer' task per competitor
            plus a single 'synthesizer' task whose deps cover every analyzer you queued.",
     assignee: "discoverer", input: { topic } })
2. runBoard()   // the drain runs the discoverer, then the analyzers it queued (parallel), then the gated synthesizer
Surface the synthesizer task's output.
```

### E. Registry agent reused across skills (`agent-ref`)

A named agent defined once in app code, referenced by many skills. Needs `createSkillsLibrary({ agentRegistry, materializeAgent })`.

```yaml
---
description: Company research using the shared analyst roster.
agents:
  market-analyst:
    agent-ref: market-analyst           # defined via defineAgent(), in the registry
    agent-overrides: { model: openai/gpt-5.4-mini }
  synthesizer:
    agent-ref: research-synthesizer
---
1. m = addTask({ goal: "...", assignee: "market-analyst", input: { subject } })
2. addTask({ goal: "...", assignee: "synthesizer", deps: [m], input: { subject } })
3. runBoard()
```

### F. Fixed graph as a tool — not delegation

When the graph is fixed in code (seeded `initialTasks`, custom collection, tuned dispatcher), skip agents entirely: register a code-defined `taskBoard(...).drain` in the catalog and list it under `allowed-tools`. The skill just calls it.

```yaml
---
description: Run the standard research board.
allowed-tools: [runResearchBoard]   # a taskBoard(...).drain registered in the skills catalog
---
Call runResearchBoard({ subject }) once and surface its result. It runs the fixed
analyst + synthesizer graph under its own concurrency.
```
