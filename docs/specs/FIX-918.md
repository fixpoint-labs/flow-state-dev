## 1. TLDR

**Plain-language summary.** A skill today can run in one of three modes.
"Inline" just adds instructions to the agent. The other two — "pattern" and
"fork" — are really hidden ways of launching separate work: pattern hands
control to a rigid, hard-coded dispatcher that builds a fixed task board and
workers from a YAML-like config; fork spins up a throwaway sub-agent. Both are
awkward, and having three modes for what is really "instructions plus optional
extra machinery" has been more confusing than useful. We're removing pattern
and fork entirely, leaving a skill as just instructions plus, optionally, the
ability to delegate. Delegation works by giving the agent a private worklist
and a set of callable helper tools, and letting the agent's own normal
decision-making loop decide when to use them — no separate rigid engine
underneath. For the common "just run this one piece of work as a sub-agent and
give me the result" case there's a single one-liner call, so removing fork
doesn't make simple delegation any more work than it is today. Separately,
existing multi-step recipes (like the "keep working until a goal is met" loop
already shipped, and the plain task-board runner) become things an agent can
call directly as a single action, the same way it calls any other tool. Three
real example skills use the old pattern system today, so this isn't just a
framework change on paper — the same change has to keep those three working,
which is also the proof the replacement holds up. (Fork, by contrast, has no
real users to migrate — it's a clean delete, and the everyday version of what
it did comes back as that one-liner; the fancier "sub-agent that remembers the
whole conversation so far" version returns later as separate work.)

**One-sentence technical statement.** Remove both non-inline skill context
modes — pattern (`PatternRegistry`, the `pattern-run` router,
`worker-materializer`'s pattern coupling, `pattern:`/`pattern-config:`/
`initial-tasks:` frontmatter) and fork (`fork-generator.ts`, the `runSkill`
fork route, `context: fork` parsing) — collapsing `SkillContextMode` to
`"inline"`; replace pattern-style delegation with a new `delegation` preset on
`createSkillsLibrary` (own-state task board + `taskTools` + per-worker callable
tools, executive-orchestrated, no drain loop); verify/harden `goalSeekLoop` and
`taskBoard().drain` (and any block) as directly tool-callable primitives; and
migrate the three real pattern-mode skills (`apps/kitchen-sink` ×3,
`examples/guides/research-team` ×2) onto the two replacements. Fork has no
consumers to migrate. Supersedes FIX-919.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*
- **What we gain.** A skill stops being a three-mode concept and becomes one
  thing: instructions, optionally plus delegation. One coherent way to
  delegate (a private ledger + named worker tools the executive calls itself)
  instead of a rigid, session-global, YAML-driven dispatcher; deterministic
  multi-step flows (`goalSeekLoop` and friends) become ordinary callable tools
  any agent can reach for. The `SkillContextMode` enum collapses from three
  values to one, and an entire dispatch surface (fork generator, pattern
  registry, the `runSkill` router's non-inline branches) is deleted.
- **Where the work sits.** Mostly rewiring existing primitives (capability
  own-state, the task board, worker materialization, the generic
  block-as-tool mechanism that already exists) into a new capability preset;
  the genuinely new code is small — one new task-board backing, one new
  capability file, one decoupled frontmatter parser.
- **Where the complexity actually is.** Proving that a deterministic flow's
  *internal* steps stay invisible to the calling agent's history when it runs
  as a single tool call — the mechanism looks sound by construction but has
  zero test coverage today, so this is a verify-then-patch-if-needed problem,
  not a code-review problem.
- **The risk.** Two risks. (1) Deleting the pattern dispatcher before the new
  path is proven would break real skills — three in this repo
  (`apps/kitchen-sink`) plus a full example package
  (`examples/guides/research-team`) hard-import `defaultPatternRegistry` and
  break at build time the moment it's deleted; mitigated by migrating all of
  them in this same change (§4.10) and using two as the actual goal checks.
  (2) Removing fork defers exactly one narrow capability — a sub-agent that
  *inherits the conversation so far* — to FIX-920. The everyday fork shape
  ("run this as a sub-agent, give me the result") is *not* deferred: it
  survives with no new tool, because calling a worker-tool is already one call
  that returns its result (§4.12). So the gap is specifically
  history-inheritance, not delegation in general — a much narrower risk than
  "fork is gone." Fork has zero SKILL.md consumers, so the deletion breaks no
  shipping code, and the issue names FIX-920 as the re-introduction home.

## 2. Overview

Linear issue: [FIX-918](https://linear.app/fixpoint-labs/issue/FIX-918/remove-skill-pattern-mode-deliver-delegation-via-a-capability-blocks).

Skills today carry a `context:` mode — `inline | fork | pattern`. `inline`
injects instructions into the host generator (kept). The other two are
disguised dispatch mechanisms: `pattern` hands execution to `PatternRegistry`,
a session-global dispatcher that materializes a task board and named workers
from YAML-shaped config and runs them through a fixed pattern factory
(`taskBoard`, `planAndExecute`, `supervisor`, etc.); `fork` spins up an
isolated sub-agent via `createSkillForkGenerator`. This spec removes **both**
non-inline modes, collapsing `SkillContextMode` to `"inline"`, and replaces
pattern-style delegation with a `delegation` preset on the already-shipped
`createSkillsLibrary` (FIX-911) — the executive generator's own tool-calling
loop becomes the orchestrator, with a private task board and named
worker-tools as its building blocks — where calling a worker-tool is itself the
single-shot "run one sub-task, get result inline" path, so the everyday fork
ergonomic survives fork's removal with no new tool. It also verifies that the
already-shipped `goalSeekLoop`
primitive (FIX-910) and a plain `taskBoard().drain` can be called directly as
tools by any generator, closing the loop on "deterministic recipes as
blocks-as-tools." Fork is removed outright, not relocated; only its
*context-window-preserving* half — "a sub-agent that inherits the conversation
so far" — is deferred, to FIX-920 (a task context-supply mode). This
supersedes FIX-919 (now deprecated).

## 3. Background & Research

### 3.1 Why this is being done (condensed design history)

This issue was filed at the end of a long design thread captured in
`docs/internal/design/skills-goalseek-design-notes.md` (branch
`claude/skills-system-architecture-kw77zs`, not yet on `main` — this spec
inlines everything load-bearing from it since the branch itself is
undiscoverable from `main`). The thread's conclusion, in brief:

The skills system overloaded one concept (`context: inline | fork | pattern`)
across three unrelated execution shapes. Only `inline` is actually "context injection";
`fork` and `pattern` are *dispatches* that happen to be triggered via a
`runSkill` tool call. FIX-911 fixed the real session-global bleed problem for
`inline` (per-generator capability-config binding) but explicitly left
`fork`/`pattern` on the legacy session-global `runSkill` router — sharpening
the fragmentation rather than reducing it (`docs/specs/FIX-911.md` §8: "Full
migration/removal of the session-global path... (staged follow-up)").

**On fork specifically (the post-filing scope expansion).** The original
skills redesign kept fork as a real mode and even had a dedicated rework in
flight (FIX-919 / PR #844: make the fork child inherit history to the fork
point, deliver it as a capability-installed tool). The project owner has since
decided fork is not worth its complication: it adds a whole dispatch shape and
a second "spawn a child like the parent" resolution problem. Fork's value
decomposes into three parts, and this spec covers or defers each explicitly:
(1) *isolation* — a sub-agent whose work is hidden from the parent's history —
already provided by delegation + the task board (tasks emit at
`itemVisibility: { client: true, history: false }`); (2) *fresh-context
single-shot ergonomics* — "run this as a sub-agent, hand me the result in one
call" — **already satisfied** by worker-tools being directly callable (call a
worker, get its result; §4.12), so no new tool is added for it; (3)
*context-window-preserving inheritance* — a child that sees the prior
conversation — **deferred to FIX-920** ("Re-introduce fork-like sub-execution
via a task context-supply mode"), a task-level mechanism rather than a bespoke
`context:` mode. (The adjacent "should the host also run tasks itself / spin up
ad-hoc undeclared sub-agents" question is **FIX-923**'s manager-vs-IC research,
also out of scope here.) So fork is removed here (not relocated), FIX-919 is
superseded
(the issue now marks it deprecated), and its PR #844 should be closed unmerged.
This is the same "split the taxonomy by what a skill *is*, not how it runs"
principle from the design notes, taken to its conclusion: after this change, a
skill *is* inline instructions, plus (optionally) a delegation capability.
There is no "how it runs" axis left.

Removing fork is a deliberate, owner-made call, not a research conclusion of
this spec. The one honest ramification (recorded in §5 Key Decision 1): between
this landing and FIX-920, there is no *history-inheriting* sub-agent — but the
fresh-context single-shot case (part 2 above) ships here, so the gap is narrow.
No shipping skill relies on any fork behavior today (zero `context: fork`
SKILL.md consumers), so nothing breaks.

Two competing designs were weighed for what replaces `pattern` mode:

- **Direction A — a `skillHarness` block wraps the generator**, owns an outer
  GoalSeek loop, and enforces whole-turn convergence across every active
  skill's goals. Needs a new top-level "harness" block type and loop-around-a-
  loop context re-threading.
- **Direction B — the generator stays the executive; deterministic recipes are
  tools it calls.** No wrapping, no new block type. A skill that needs to
  delegate gets a capability-installed task board + worker-tools; the
  executive's own ReAct loop decides when to use them. A skill that needs a
  rigorous, autonomous multi-step recipe (e.g., `goalSeekLoop`) calls that
  recipe *as a tool* and gets back only the finalized result.

**Direction B was chosen** (see §5 for the rejected alternative's ramifications).
The reasoning: whole-turn enforced convergence — the only thing Direction A
buys that B doesn't — decomposes into two things the framework already has:
rigorous delegation (enforcement lives inside the called flow, i.e.
`goalSeekLoop`) and enforced output gating (the existing `response-auditor`
pattern, an action/flow-level guard). No concrete case requiring a harness was
identified. Building the harness would mean a third top-level concept trying
to do both delegation and output-gating from inside the skill layer — the
opposite of BP-038 (subtract before you add).

### 3.2 Industry precedent

The chosen shape — an orchestrating agent calling worker sub-agents as
ordinary tools, with only the finalized result flowing back — matches how
established frameworks solve the same problem:

- **Anthropic's "Building Effective Agents"** describes the orchestrator-
  workers pattern directly: a central LLM decomposes a task and delegates
  pieces to worker LLMs, synthesizing their outputs itself, with no fixed
  subtask list decided in advance — this validates "the executive's own loop
  is the orchestrator, no separate drain loop."
- **OpenAI's Agents SDK** implements almost exactly Shape 1: `agent.as_tool()`
  exposes a sub-agent as a callable tool; the sub-agent runs its own loop
  internally and only its result re-enters the caller's context via a
  `custom_output_extractor`. This is the concrete precedent for "return only
  the finalized result, not the trace" (relevant to Replacement B).
- **LangGraph's supervisor pattern** uses non-overlapping state-schema keys
  between a subgraph and its parent so subgraph-internal state never leaks
  back — the same isolation property this spec needs from `itemVisibility`
  when a `goalSeekLoop` runs as a tool (§4.6).
- **CrewAI's hierarchical-delegation mode** is a cautionary case: multiple
  reports describe delegation silently degrading into the manager doing the
  work itself when the worker's input schema isn't strict. This is the
  concrete argument for keeping worker-tool `inputSchema`s exactly as strict
  as any other tool (no special-casing "delegation tools").
- **OWASP guidance on eval/deserialization** directly supports "assignment by
  key, resolved against a closed registry, never by embedded/dynamic code
  reference" — exactly the existing `task.assignee` → `TaskWorkerRegistry[assignee]`
  convention this spec reuses (§4.5), and the reason `blockRef`/`agentRef`
  workers must stay app-code references, never embedded in a skill folder.

resolver's returned `PresetDef.stateSchema` contributes to the consuming
block's own `ctx.self` container, merged via `mergeCapabilityOwnStateWithBlock`
(reference-equality collision detection on duplicate field names, not
last-wins). `ctx.self` is typed `StateRef<TSelfState>` — the **same** interface
`ctx.sequencer` and `ctx.request` already implement (`packages/core/src/types/block.ts`
line 232), which is exactly what makes §4.2's new task-board backing cheap.

**FIX-910's `goalSeekLoop`** (`packages/orchestration/src/task-board/goal-seek-loop.ts`,
603 lines, landed via PR #841) already carries an explicit forward-compat
comment written for this exact ticket:

> "Input schema forwarded to the OUTER sequencer verbatim, so a re-expressed
> pattern keeps its public block metadata (and survives `GeneratorTool`
> wrapping — FIX-918 forward-compat)."

And the mechanism it's forward-compatible with already exists generically:
`GeneratorTool = BlockDefinition<any, any>` (`packages/core/src/blocks/generator.ts`),
and `SequencerDefinition` (what `sequencer()`/`goalSeekLoop()` return)
structurally extends `BlockDefinition`. The tool-loop compiler
(`compileToolsWithExecute`, same file) only reads `tool.name`/`description`/
`inputSchema` and calls `asRuntime(tool).run(...)` — no kind-specific
branching. **So "any block, including a whole `goalSeekLoop`, can already go
in a `tools:` array" is true today, with zero new framework code required.**
What's unverified: no test or production code has ever exercised this (zero
grep hits for a `SequencerDefinition` inside a `tools:` array), and the
composite item-visibility case (a multi-step sequencer, with mixed internal
visibility, running as one tool call) has no coverage — see §4.6.

**Real, currently-shipping pattern-mode consumers (must migrate, not just
research context).** Grepping for `pattern:` frontmatter across the repo
turns up three skills in `apps/kitchen-sink/skills/` plus a full mirror
package, none of them hypothetical:

- `apps/kitchen-sink/skills/tech-brief/SKILL.md` — `pattern: plan-and-execute`
  with **one** worker (`briefer: { agent-ref: tech-briefer, visibility: primary }`).
  No concurrency/dependency config. This is the simple case.
- `apps/kitchen-sink/skills/research-company/SKILL.md` — `pattern: task-board`
  with three `prompt-ref` workers, a static `initial-tasks:` graph with a
  `deps: [market, financials]` edge, and `pattern-config: { concurrency: 2,
  dispatcher: topological, on-idle: complete, on-error: skip }`.
- `apps/kitchen-sink/skills/competitor-analysis/SKILL.md` — `pattern: task-board`
  with a `discoverer` worker that **dynamically** fans out via `taskTools`
  (queues one `analyzer` task per discovered competitor at runtime, plus a
  `synthesizer` gated on all of them), and `pattern-config: { concurrency: 4,

- `examples/guides/research-team/src/skills/` — `research-company` and
  `competitor-analysis` are near-identical mirrors of the two above (this

Deleting `defaultPatternRegistry` without migrating these breaks the
monorepo build, not just a stale doc. `research-company` and

dynamically-grown task graph run to completion under explicit
concurrency/dependency dispatch — which Shape 1's executive-serialized tool
calls cannot reproduce without changing their observable behavior (parallel
analyst dispatch would become however the model happens to sequence tool
calls, which is not equivalent). `tech-brief` is the one skill simple enough
to become a genuine Shape 1 delegation-preset example. See §4.10 for the
concrete per-skill migration plan.

**Existing "assignment by key" precedent** (not new — reused directly):
`Task.assignee: z.string().optional()`; `packages/orchestration/src/task-board/blocks/worker-step.ts`
already dispatches a `TaskWorkerRegistry` by `task.assignee` through
`keyedRouter({ blocks, select: (task) => task.assignee })`
(`packages/core/src/utility/keyed-router.ts`, "promoted from three hand-rolled
routers across the patterns package"). Replacement A's "assignment by key,
never by block reference" is this exact convention, just exposed as
individually-named tools instead of routed through a `keyedRouter` sequencer
step (there's no drain loop to route inside — the executive calls the named
tool directly).

### 3.4 Necessity check — the six questions

1. **What existing primitive could a user adopt today?** Pattern mode itself
   already delivers *a* form of delegation. But it's not a primitive a user
   composes — it's a closed, session-global dispatcher requiring `pattern:`
   frontmatter, mutually exclusive with `inline`/`fork`, with no way to give
   one generator its own private board without going through the pattern
   route. There's no way today to say "let this ReAct loop delegate, but stay
   the orchestrator itself."
2. **What does this add that pattern-mode doesn't?** (a) **Composition with
   existing framework features that wouldn't work outside the framework's
   resolution path** — own-state (`ctx.self`), capability merge, and
   `atomicState` are all framework-internal machinery; a user can't replicate
   "a private, collision-free board namespaced by the block itself" in
   userland. Strongest case. (b) **New vocabulary that shapes reasoning** — "a
   skill can delegate" becomes a capability preset instead of a whole
   execution mode; "a deterministic flow is just a tool" is a real mental
   model shift. (c) Removes ~900 lines of bespoke session-global dispatch
   machinery in exchange for composing primitives that already exist for
   other reasons (BP-029).
3. **Does the cited precedent transfer?** Yes — FIX-911's own-state
   contribution (`library.ts`'s conditional `stateSchema` for `activeSkills`)
   is the *same* mechanism this spec reuses for the task board, not a
   syntax-alike. Confirmed by reading the actual merge code (`merge.ts`), not
   assumed.
4. **Single-vendor knowledge?** None — this is pure internal framework
   architecture. No provider-specific identifiers anywhere in this design.
5. **Does an error path hide the real problem?** No new "wrong provider/context"
   guard is introduced. The one error condition that does change
   (`no_active_pattern` → a new sentinel) is a resolution-failure UX contract
   already present today, preserved, not newly invented to compensate for a
   bad abstraction.
6. **Path-of-least-resistance test.** Shipping this establishes "a capability
   composes task-board + tool infrastructure onto a generator" as the general
   pattern for delegation. That's a generalizable direction (matches how
   `taskBoard()`'s own capability accessor and `taskTools` already work
   standalone in `packages/integration-tests/src/scenarios/fixtures/pattern-skill-task-board-flow.ts`,
   bypassing the pattern route entirely) — not a special-case dead end.

None of the "push back" signals fire: this isn't a `boolean | Config` toggle
resolving to one factory call with no other delta; it isn't single-vendor;
existing primitives don't already give a 1–3 line escape hatch for
"delegate but stay the orchestrator"; the precedent (own-state) genuinely
transfers; there's no provider/platform guard error in the design.

**On the fork removal specifically** (a pure subtraction, not a build): the
necessity question inverts — the burden is on *keeping* fork, not removing it.
Fork is a whole dispatch shape and a second "spawn a child like the parent"
resolution problem (FIX-919's central design difficulty) serving a capability
whose isolation half delegation + the task board already deliver, and whose
inheritance half is deferred to FIX-920. It has zero consumers. Removing it is
textbook BP-038 (subtract before you add; delete the path you supersede). The
one thing to be honest about — the temporary loss of "sub-agent inherits the
prior conversation" — is a product call the owner has made explicitly, not a
gap this spec is glossing over (recorded in §5 KD1 and §8).

**Verdict: Build as scoped** (pattern replacement + fork deletion).

## 4. Technical Design

### 4.1 Where delegation lives: derived from `workers:`, inside `createSkillsLibrary`

**Decision:** delegation is **derived** from the bound skills — if any bound
skill declares `workers:` (§4.4), the library installs the delegation surface;
if none do, it installs nothing. There is no `presets: { delegation: true }`
opt-in flag: the `workers:` declaration *is* the signal. This lives inside
`createSkillsLibrary` (`library.ts`), not a standalone capability.

```ts
const skills = createSkillsLibrary({ catalog, initialSkills });
// A bound skill with `workers:` → delegation installs automatically.
generator({ uses: [skills.with({ active: ["research-lead"] })] });

// Optional overrides (not required to turn delegation on):
skills.with({ active: ["research-lead"], delegationBoard: mySharedBoard }); // shared board
skills.with({ active: ["research-lead"], delegation: false });              // force-off
```

Two rejected alternatives: a manual `delegation: true` preset (a second
declaration of intent that can desync with `workers:` — see Key Decision 3),
and a fully standalone `createDelegationCapability` composed via its own `uses`
entry. The reason delegation lives here: it needs to read the *bound skill's*
declared workers (§4.4), and `createSkillsLibrary` is already the thing that
resolves "which skill is bound to this generator and what does its
frontmatter say" — its config resolver inspects each bound skill's parsed
manifest today. Deriving "does any bound skill declare workers?" is a natural
extension of that resolver; a standalone capability would duplicate the whole
"which skill is active" resolution. See Key Decision 3 (§5) and §4.2 for the
static-own-state / dynamic-tools split that makes derivation work for both
statically-`active` and dynamically-loaded skills.

### 4.2 Board backing: reuse the existing `StateRef` path against the host generator state

`getOrCreateTaskCollection` (`packages/orchestration/src/tasks/collection/get-or-create.ts`,
198 lines) supports three backings: `"sequencer"`, `"resource"`, `"request"`.
The delegation board needs to live on the host generator's own block state
(FIX-914 own-state) — collision-free by construction, unlike the `"request"`
backing's hand-namespaced whole-request field.

> **Simplification (from spec-PR review — BP-038).** An earlier cut added a
> fourth `"own-state"` backing discriminant. That is unnecessary surface: the
> existing `createSequencerBackedTaskCollection` already accepts any
> `StateRef<Record<string, unknown>>`, and a generator's own-state ref
> (`ctx.self`) and a child tool's parent ref (`ctx.parent`) both *are*
> `StateRef`s (`packages/core/src/types/block.ts` line 232) — no adapter, unlike
> `requestStateRef()`. So the board is built by passing the host state ref to
> the **existing** StateRef-accepting path (`getOrCreateTaskCollection({ backing:
> "sequencer", sequencer: <hostStateRef>, stateKey: TASK_BOARD_FIELD, ctx })`),
> with **zero new discriminant**. If a named `"own-state"` alias is later wanted
> purely for readability, that's a follow-up, not this change.

> **Correctness — which host state ref (from spec-PR review, P1).** The board
> lives on the *generator*, but the `taskTools` handlers that mutate it run as
> **child blocks**, so a tool's own `ctx.self` is a per-call scope, not the
> generator's. Using `ctx.self` from a tool would build a disconnected per-call
> board and `addTask`/`listTasks` would miss the real ledger. So the host state
> ref is:
> - **`ctx.parent`** from inside a `taskTools`/worker helper (the tool declares
>   `parentStateSchema` for the board field), and
> - **`ctx.self`** only from the generator's own scope (e.g. a context formatter
>   reading the board).
>
> This is exactly FIX-911's load-tool pattern, already documented in §3.3 ("the
> load tool runs as a child and writes the parent's block state via `ctx.parent`;
> the reader runs in the generator's scope and reads `ctx.self`"). See §4.5 for
> the one place this gets subtler — a worker that *itself* declares
> `tools: [taskTools]`, where `ctx.parent` is the *worker*, not the board owner.

This is a small addition (the caller wiring + `parentStateSchema` declarations),
not a new collection implementation.

The library's config resolver contributes
`stateSchema: z.object({ [TASK_BOARD_FIELD]: z.record(z.string(), taskSchema) })`
on the generator **when delegation might occur** (below) — mirroring
`library.ts`'s existing conditional `activeSkills` contribution exactly.
Own-state is a build-time structural thing (you can't add a state field
mid-run), so it must be pre-declared whenever delegation *might* happen; the
cost is one empty `Record<string, Task>` field. Each `taskTools` handler then
declares `parentStateSchema` for that board field and calls
`getOrCreateTaskCollection({ backing: "sequencer", sequencer: ctx.parent, stateKey: TASK_BOARD_FIELD, ctx })`
to reach the generator's ledger; a reader in the generator's own scope passes
`ctx.self`. Worker-tools and the guidance context, by contrast, are *dynamic*
contributions (added per tool-loop step for whichever worker-declaring skills
are active), so they need no static pre-declaration — the same
static-state / dynamic-tools split FIX-911 uses for `activeSkills` + the load
tool.

**"Might occur" — precisely (from spec-PR review, P2, live-catalog case).**
Own-state can't be added after the block is built, so the board field must be
declared for *any* binding that could later resolve a worker-declaring skill:

- **Explicit `active` / `allowed` set:** declare the board iff any *named*
  skill declares `workers:` (build-time inspectable — the library parses those
  manifests). If none do, declare nothing (zero overhead).
- **Whole-catalog dynamic activation** (`dynamicActivation` with no `allowed`):
  the load catalog is the *live* skills resource collection, not just the
  bundled `initialSkills` index, so a user/admin could load a worker-declaring
  skill that wasn't inspectable at build time. Since the board can't be added
  then, **always pre-declare** the board field for this binding shape (one
  empty record; harmless if never used). The alternative — letting a
  runtime-loaded delegating skill activate against a generator with no board
  field — must **not** silently no-op; if the implementation chooses not to
  always-declare, it must fail loud when such a skill activates ("delegation
  requires the board declared at bind time"). Recommendation: always-declare
  for whole-catalog `dynamicActivation`; it's cheaper and can't surprise.

### 4.3 `taskTools`, decoupled from the pattern-activation lookup

`createTaskToolsCapability()` (`task-tools-capability.ts`, 241 lines) keeps
its eight handler bodies (`addTask`/`assignTask`/`completeTask`/`failTask`/
`blockTask`/`cancelTask`/`updateTask`/`listTasks`) verbatim — only the board
resolution changes. Today:

```ts
async function getCollection(ctx: BlockContext): Promise<TaskCollectionRef | undefined> {
  return getActivePatternCollection(ctx);   // walks activeSkills for mode: "pattern"
}
```

Becomes a factory with an **optional** resolver (the resolver param defaults,
so the exported singleton keeps working — see the review note below):

```ts
export function createTaskToolsCapability(
  resolveCollection: (ctx: BlockContext) => Promise<TaskCollectionRef | undefined>
    = defaultOwnStateResolver,   // reads the generator's board via ctx.parent
): DefinedCapability { /* same 8 tools, getCollection = resolveCollection */ }

/** Default instance — unchanged public export; now resolves the own-state
 *  board through `ctx.parent` instead of `getActivePatternCollection`. */
export const taskTools = createTaskToolsCapability();
```

- The **default resolver** (`defaultOwnStateResolver`) reads the host
  generator's own-state board via `ctx.parent` (§4.2). This is what the derived
  delegation surface uses for a private board, and what a standalone `taskTools`
  consumer gets.
- An **injected resolver** overrides it for the **shared-board** case
  (`delegationBoard: myBoard` → a resolver that returns that board's collection).

> **Compatibility note (from spec-PR review, P2).** The resolver must stay
> optional. The package exports `taskTools = createTaskToolsCapability()` and
> real code/tests import that singleton directly. Making the resolver required
> would break the export and every consumer, and would also make the
> "stray `taskTools`-only consumer returns `no_delegation_board`" edge case
> (§6) uncompilable. Keeping a default resolver preserves the export; the
> default returns the renamed sentinel when the parent has no board field.

`active-pattern-collection.ts` (and `getActivePatternCollection`) is deleted
outright — nothing calls it once pattern mode is gone. The
`{ ok: false, error: "no_active_pattern" }` UX contract (recover gracefully,
never throw) is **preserved** under a renamed sentinel (`"no_delegation_board"`
or similar) — this is a UX guarantee worth keeping even though its cause
changes.

### 4.4 Worker declaration: a decoupled `workers:` frontmatter field

**Decision:** workers stay declared in the skill's own SKILL.md, via a new
`workers:` frontmatter field parsed independent of `pattern:` — not moved to
app-level TypeScript config. This is the single most consequential
interpretive call in this spec; see the Open Questions (§11) for the
alternative and why it's flagged for explicit sign-off despite the
recommendation below.

The issue's "Remove" list includes "frontmatter parsing of `pattern:` /
`workers:` / `initial-tasks:`" — read together with its "Keep" list ("Workers:
prompt/promptRef are portable data... **safe to define inside a (portable)
skill**"), the removal is of the *old*, `PatternBinding`-coupled `workers:`
parser (which required `pattern:` to also be present and fed a rigid
`pattern-config:` crosswalk) — not of the ability to declare workers in a
skill file at all. If `prompt`/`promptRef` workers must remain "portable data
inside a skill," they need a place to live in the skill file, since moving
them to app TypeScript config would mean a portable skill folder can no
longer ship its own delegation behavior — a real regression against the
design notes' explicit intent.

So: `skill-md.ts` keeps a `workers:` field, but its parser (`parseWorkersField`/
`parseWorkerSpec`, kept structurally) drops every `PatternBinding`-specific
dependency: no `pattern:` requirement, no `pattern-config:` crosswalk, no
mutual-exclusivity check against `context`. A skill declares `workers:`
alongside `context: inline` — the only remaining mode after fork and pattern
are gone (§4.11). `initial-tasks:` is **not** re-added — Shape 1 delegation
has no seed/drain step (the executive adds its own tasks via `addTask`), so
there's nothing for a seed list to feed.

`blockRef`/`agentRef` workers still require an app-supplied registry
(`blocks`/`agentRegistry` passed to the delegation preset's config) to
resolve the string key — unchanged from today; only `prompt`/`promptRef`
workers are "fully portable."

**Concrete type + parser + index changes (from spec-PR review — don't leave
this for the implementer to discover mid-PR).** Today `workers:` is only
recognized *inside* a `PatternBinding`; a standalone `workers:` without
`pattern:` is treated as an orphan key and warned/ignored (`skill-md.ts`), and
`SkillState` has no top-level `workers` field. The library's resolver (§4.1)
and guidance roster (§4.13) both need the bound skill's worker map at
build/resolve time, so three named changes are required:
1. **`@flow-state-dev/core`** — add `workers?: Record<string, WorkerSpec>` to
   `SkillState` (`packages/core/src/types/skill.ts`), a top-level field, not
   nested under the removed `PatternBinding`.
2. **Parser** — `skill-md.ts` populates `state.workers` **directly** from the
   `workers:` frontmatter (the decoupled `parseWorkersField`), dropping the
   orphan-key warning for `workers:` and its `pattern:`-presence requirement.
3. **Index** — extend `indexInitialSkills` in `library.ts` so each indexed
   skill entry carries its parsed `workers` map, so the resolver can answer
   "does this bound skill declare workers, and which?" without re-parsing.

### 4.5 Worker materialization: a delegation-mode variant of `materializeWorker`

`materializeWorker(workerKey, spec, deps)` reuses the existing four-branch
taxonomy dispatch (`blockRef → agentRef → promptRef → prompt`), and its
`prompt`/`promptRef` branch already builds a `generator()`. But **two things
about its current output make it not directly LLM-tool-callable**, and the spec
must resolve both (raised in spec-PR review — load-bearing for §4.12's
"call `briefer(...)`, get a result" claim):

**(A) Input schema — the worker's schema is board-dispatch-shaped, not
LLM-facing.** `materializeWorker` builds workers with `workerInputSchema`
(`{ taskId, goal, attempts }`, all required — `worker-materializer.ts:30-38`),
which is what the board's `dispatch-and-execute` step feeds. A model calling a
worker-tool can't sensibly supply `taskId`/`attempts` — those are substrate
bookkeeping. **Decision:** the delegation preset materializes worker-tools in a
**direct-call mode** whose tool `inputSchema` is the minimal LLM-facing shape
`{ input: string }` (the task content), substituted into the worker's
prompt/`$ARGUMENTS` exactly as the board path substitutes `goal`; the substrate
fields are supplied internally (a synthesized `taskId`, `attempts: 0`). This is
the `agent.as_tool()` input-shaping precedent (§3.2) applied to *input*, not
just output. Concretely: a `mode: "direct" | "board"` param on
`materializeWorker` (or a thin `materializeWorkerTool` wrapper) — direct mode
for the delegation preset's callable tools, board mode unchanged for the Shape
2 drain path (which *wants* `workerInputSchema`).

**(B) Tool name — must be the worker key, not the internal block name.**
`materializeWorker` names its block `skillWorker_${skillName}_${workerKey}`, and
the generator tool-loop exposes `BlockDefinition.name` as the model-facing tool
name. Dropping the block into `tools:` as-is would show the model
`skillWorker_research_lead_briefer`, breaking both the §4.7 examples and the
`assignee`-key convention. **Decision:** direct-mode materialization sets the
tool name to the bare `workerKey` (`briefer`) — via a name override at
materialization, or `.mapModelOutput`-adjacent renaming — so `assignee` strings,
tool names, and the roster (§4.13) all line up on the same key.

**(C) A worker that itself declares `tools: [taskTools]` (Shape 2 fan-out).**
`competitor-analysis`'s discoverer adds tasks mid-drain via `taskTools`. Those
task tools run as children of the *worker* generator, so their `ctx.parent` is
the worker's state — **not** the executive/drain board. The default resolver
(§4.3, `ctx.parent`) is therefore wrong for worker-embedded `taskTools`.

> **Correction (from spec-PR review, P1 — `board.capability` alone is not
> enough).** An earlier cut said the fan-out worker wires `uses:
> [board.capability]`. That's wrong: `board.capability` exposes
> `ctx.cap.<board>` **code helpers** (`addTask()`, `listTasks()`), it does
> **not** contribute model-facing `tools` — so the discoverer's *model* would
> have no callable `addTask`, and runtime fan-out would never queue tasks. The
> LLM worker needs the actual eight `taskTools` handler tools, resolved against
> the drain board. **Decision:** the fan-out worker uses a **board-bound
> `taskTools`** — `createTaskToolsCapability(resolver)` (the injected-resolver
> path from §4.3) whose `resolver` resolves the *drain's* collection (it can
> reach it through the drain board's `ctx.cap.<board>` accessor, which resolves
> the collection from inside the drain subtree). So `board.capability` is what
> the *resolver* uses in code to find the board; `taskTools` is what contributes
> the model tools. Wire `uses: [taskToolsForDrainBoard]`, not
> `uses: [board.capability]`.

(Shape 1 delegation workers generally don't need `taskTools` at all — they're
leaf tools the executive calls; if one does, it takes the same board-bound
`taskTools` wiring, resolver pointed at the executive's own board.)

**Deps trim:** `PatternRegistryDeps` (`catalog, blocks?, agentRegistry?,
capabilityCatalog?, materializeAgent?, skillName, skillCollection,
defaultModelId?, input?, collectionId`) drops only the pattern-specific
`collectionId`; everything else is reused.

The delegation surface's `tools` contribution becomes: for each worker key in
the active skill's parsed `workers:` map, direct-mode-materialize it (A+B) and
install it under the bare worker key in the executive's tool list — after a
**bind-time reserved-name check** that the key doesn't collide with a
`taskTools` handler name, an allowed catalog tool, or another worker (§6),
since the runtime rejects duplicate model-facing tool names.

### 4.6 Blocks-as-tools: verify, don't invent

Per §3.3, the general mechanism (`GeneratorTool = BlockDefinition`) already
exists, applies equally to `goalSeekLoop` **and** a plain `taskBoard().drain`
sequencer (both are `SequencerDefinition`s), and `goalSeekLoop` was already
built anticipating it. **This spec does not add a new wrapper primitive up
front.** Instead:

1. Write the first-ever test placing a `goalSeekLoop`-based block inside a
   generator's `tools:` array (`packages/orchestration/test/task-board/goal-seek-loop-as-tool.test.ts`),
   using `mockGenerator` (`packages/testing/src/mocks/mockGenerator.ts`) to
   script the tool call.
2. Assert: the tool call's result is the `finalize` step's projected output
   (not the raw trace); internal per-iteration items (worker generator
   outputs, judge verdicts, replan steps) resolve to non-history visibility
   in the calling generator's assembled history.
3. **If** the test finds a real leak — e.g., `goalSeekLoop`'s internal
   `judgeStep`/replanner-invocation/`coerceAtCap` steps emit bare
   `ctx.emit.component`/message calls without explicit `itemVisibility`, so
   they default to `{client:true, history:true}` and leak into the caller's
   history — patch those specific emit call sites in `goal-seek-loop.ts` to
   declare `itemVisibility: { client: true, history: false }` explicitly.
   This is a targeted fix to existing emit calls, not a new framework
   primitive (Key Decision 6, §5).

**Audit scope includes the board's own `onChange` emit (from spec-PR review).**
The leak surface is not only `goal-seek-loop.ts`. `getOrCreateTaskCollection`'s
`onChange` handler (`get-or-create.ts:122-134`) emits a `task-change` component
item on **every** task lifecycle transition with no explicit `itemVisibility`,
so it defaults to `{ client: true, history: true }`. For a Shape 2
drain-as-tool (`research-company`, `competitor-analysis`), that's potentially
O(tasks × transitions) history-visible items per single tool call — a bigger
leak than goalSeekLoop's internal steps. The audit (step 3 above) and behavior
7 (§7) must cover this `onChange` path too: when a board runs *inside* a
tool-wrapped drain, its `task-change` emits should be `history: false` (still
`client: true` so the `<Plan />` UI updates live). The board already threads an
`onChange`; the fix is to pass the tool-nested visibility through it (e.g. the
drain-as-tool wrapper stamps `history: false` on the board's change emits),
not a per-call-site edit in `goal-seek-loop.ts` alone.

### 4.7 Usage example (before/after)

**Before** (pattern-mode SKILL.md, removed by this spec):

```yaml
---
description: Research a topic using a lead + two specialists.
context: pattern
pattern: task-board
workers:
  researcher: { prompt: "You research assigned subtopics." }
  writer: { prompt: "You synthesize findings into a report." }
pattern-config:
  max-iterations: 4
---
```

**After** (app code composes the delegation preset; the skill body stays
plain instructions + a decoupled `workers:` field):

```yaml
---
description: Research a topic using a lead + two specialists.
context: inline
workers:
  researcher: { prompt: "You research assigned subtopics." }
  writer: { prompt: "You synthesize findings into a report." }
---
You are the research lead. Use `addTask` to hand out subtopics to `researcher`
and `writer` via their tools, and `listTasks`/`completeTask` to track progress.
```

```ts
const skills = createSkillsLibrary({ catalog, initialSkills });
const researchLead = generator({
  uses: [skills.with({ active: ["research-lead"] })],
});
// Because "research-lead" declares `workers:`, delegation installs
// automatically — no `presets: { delegation: true }` flag (§4.1). researchLead
// now has: addTask/assignTask/completeTask/... (taskTools), plus a `researcher`
// tool and a `writer` tool, each a materialized worker, plus the guidance
// context. A skill with no `workers:` installs none of this.
```

**Blocks-as-tools (new, no "before" — this capability didn't exist)**:

```ts
const deepResearch = goalSeekLoop({
  name: "deep-research",
  inputSchema: z.object({ question: z.string() }),
  board, seed: planQuestions, judge: assessCoverage,
  replanner: proposeFollowups, maxIterations: 4, finalize: synthesizeAnswer,
});
const chatAgent = generator({
  tools: [deepResearch],   // callable directly — no wrapper needed
});
```

### 4.8 State management

- **New:** own-state task board (`ctx.self`), contributed by the delegation
  preset's `stateSchema`, scoped to the one generator that installed it —
  never visible to or namespaced against any other block.
- **Modified:** `activeSkillsArraySchema`'s `mode` enum shrinks from
  `"inline" | "fork" | "pattern"` all the way to `"inline"` (both non-inline
  modes removed — pattern here, fork in §4.11). This schema is shared by both
  the legacy v1 (`active-skill-state.ts`) and v2 (`library.ts`/`load-tool.ts`)
  surfaces — both need the change together, and both must tolerate a stale
  persisted `"fork"`/`"pattern"` entry on resume (§6, the enum-shrink
  edge-case row; BP-030).
- **Unchanged:** `taskTools`'s eight tools' input/output shapes; `TaskInit`,
  `Task`, `TaskCollectionRef` (all in `packages/orchestration/src/tasks/`).

### 4.9 Error handling

- Bound skill declares no `workers:`: **no delegation surface installs at all**
  — no board, no `taskTools`, no worker-tools, no guidance (§4.1 derivation).
  Ordinary inline skills never get task-board tools. (The one exception is the
  whole-catalog `dynamicActivation` predeclare, §4.2 — an empty board field, but
  still no `taskTools`/worker-tools until a worker-declaring skill activates.)
- Unknown/missing `blockRef`/`agentRef`: same fail-loud error
  `materializeWorker` already raises today — unchanged, not weakened.
- Board resolution failure (no active delegation, e.g. a stray `taskTools`-only
  consumer with no delegation preset): the renamed `{ ok: false, error: "no_delegation_board" }`
  sentinel — recover gracefully, never throw, matching today's `no_active_pattern` contract.
- Legacy `pattern:` frontmatter found post-removal: `skill-md.ts`'s parser
  fails loud with an explicit "pattern mode removed; see the `delegation`
  preset" message — never silently reinterprets the file as `inline`.
- Legacy `context: fork` found post-removal: parser fails loud with a
  "fork mode removed" message (§4.11, §6) — never silently downgrades to
  `inline`.

### 4.10 Migrating the real pattern-mode consumers

Not a synthetic exercise — these are the actual skills that break without a
migration plan (§3.3), and using them as goal checks (§7) is stronger proof
than a hand-built test fixture.

**`tech-brief` → `delegation` preset (Shape 1).** One worker, no
concurrency/dependency config, `visibility: primary` (its output is already
meant to surface directly). Rewrite frontmatter to drop `pattern:`/`pattern-config:`,
keep a decoupled `workers: { briefer: { agent-ref: tech-briefer } }`. The
skill body's instructions change from "call `runSkill`" to "call the
`briefer` tool, then return its result" — the executive generator now
dispatches directly instead of going through the pattern router.

**`research-company` / `competitor-analysis` (and their `examples/guides/research-team`
mirrors) → task-board-drain-as-tool (Shape 2 / Replacement B).** These keep
their existing worker prompts, `initial-tasks:` graph (or runtime fan-out via
`taskTools`, for `competitor-analysis`'s discoverer), and `pattern-config:`
concurrency/dispatcher values — but re-expressed as a plain code-defined
block (`taskBoard({...}).drain`, composed with a `finalize` step projecting
the settled board into a synthesized report, mirroring `goalSeekLoop`'s own
`projectBoard`/`finalize` shape but without a judge/replan loop, since these
skills don't need one). **Wiring (from spec-PR review, P1 — `blockRef` is the
wrong layer):** `blockRef` is a *worker-spec* field consumed by
`materializeWorker` under delegation; it does **not** register a top-level tool
on the executive generator. So a Shape 2 skill exposes its drain block the same
way any app-code tool reaches a generator — the app registers the drain block
(a `GeneratorTool`, per §4.6 blocks-as-tools) in the skills **`catalog`**, and
the skill's frontmatter lists it under **`allowed-tools`** (exactly how these
skills already list `search`/`fetch`). The executive then has the drain in its
`tools:` and calls it **as a single tool** with the drain's own `inputSchema`
(e.g. `{ topic }`). No `blockRef`, no worker materialization for the Shape 2
root. The board's own concurrency/dependency dispatch
(already proven, unchanged from `worker-step.ts`'s `keyedRouter`-based
assignee dispatch) does the parallel/topological work exactly as it does
today; only the *invocation path* changes (pattern-router dispatch → direct
tool call), not the dispatch semantics.

**Both consumers must move from v1 `createSkillsCapability` to v2
`createSkillsLibrary` (from spec-PR review, P1).** Today
`examples/guides/research-team/src/skills.ts` and
`apps/kitchen-sink/flows/chat-agent/shared/capabilities/features.ts` instantiate
the **v1 `createSkillsCapability`**, which only composes `taskTools` when
`patternRegistry` is supplied and does **not** derive worker-tools from
`workers:`. The delegation surface in this spec lives on **`createSkillsLibrary`**
(v2, §4.1). So dropping `defaultPatternRegistry` is not sufficient — following
that alone would leave `tech-brief` an inline skill with no `briefer` tool,
board, or guidance. The migration **replaces the `createSkillsCapability`
usage with a `createSkillsLibrary` binding**: `tech-brief` binds via the derived
delegation surface (Shape 1), and the Shape 2 skills bind inline + list their
drain block in `allowed-tools` (above). `examples/guides/research-team`'s two
`SKILL.md` files and `test/board.test.ts`/`test/research-router.test.ts`/
`test/flow.test.ts` update to match; the kitchen-sink `features.ts` does the same.

### 4.11 Removing fork mode and collapsing `SkillContextMode`

Fork is a straight deletion (§3.3 fork inventory) — no replacement, no
migration, because nothing declares `context: fork`. The care needed is
entirely in *not over-removing* shared surface and in landing the
taxonomy-collapse edits cleanly.

**The mode enum collapse.** `SkillContextMode` (`packages/core/src/types/skill.ts:36`)
and `activeSkillsArraySchema.mode` (`active-skill-state.ts:70`) both currently
enumerate `"inline" | "fork" | "pattern"`. Removing fork here and pattern in
§3.3's pattern removal leaves a single-value enum, `"inline"`. Two choices,
flagged as an open question (§11):

- **Keep `SkillContextMode = "inline"` as a one-value type.** Minimal churn;
  the field and its readers (`SkillState.contextMode`, `Skill.contextMode`,
  `RunSkillOutput.mode`, `unionAllowedTools`'s `mode === "inline"` filter) all
  keep compiling; leaves a forward-compat seam if a future mode is ever added.
- **Retire the concept entirely.** Remove `contextMode` from the skill types
  and every reader, on the argument that a one-value discriminator is dead
  weight (BP-038). Larger diff, touches more files, but arguably the honest
  end state of "a skill is inline instructions."

Recommendation: **keep the one-value enum for this PR** (smaller, safer,
reversible), and flag full retirement as a follow-up — the enum being
single-valued is not itself a bug, and collapsing it to nothing is a
separable cleanup that shouldn't gate the fork/pattern removal. This is the
conservative BP-035 call (test the off/new state of the change without also
taking on an adjacent refactor).

**`RunSkillOutput.mode`.** Collapses to `z.literal("inline")` (or the
one-value enum). Any caller matching on `"fork"`/`"pattern"` is dead code to
remove; grep confirms the only branches are inside the router being gutted.

**The shared `forkModelId` option.** Named for fork but also threaded into the
pattern route as `defaultModelId` (`run-skill-tool.ts:191`) and exposed on
`createSkillsCapability`/`createRunSkillTool`. Since both fork and pattern
consumers of it are being removed, the option has no remaining consumer inside
the skills runtime — **remove it** rather than rename it, unless the
delegation preset's materialized workers need a model override, in which case
the delegation preset should carry its own explicitly-named option
(`workerModelId` or similar), not inherit `forkModelId`'s misleading name.
Flagged in §11.

**`SkillState.outputSchema` — decision: remove it (from spec-PR review).** This
is public `@flow-state-dev/core` surface, so "verify during implementation" is
not good enough — the changeset scope should be known up front. A repo-wide
grep shows it is populated only by the `output-schema` frontmatter parse
(`skill-md.ts:1094-1096`) and read only on the fork path; nothing else consumes
it. So the spec commits to **removing** the field and its parse with the fork
removal, as a **public-API removal → minor changeset** (pre-1.0, so `minor`).
If the implementer's own grep surprisingly finds a non-fork reader, that reader
is migrated in the same PR; the default is removal.

**Agent-level fork stays.** `AgentOverrides.contextMode` (`agent.ts:89`) is a
separate inline `"fork" | "inline"` literal, not `SkillContextMode`; its only
consumer (`materialize-agent.ts`) already warns-and-composes-inline for
`"fork"`. This spec does not touch it. (If the project later wants to remove
the agent-level fork affordance too, that's its own change against the
workforce package — out of scope here, noted in §8.)

### 4.12 The single-shot path is the worker-tool — there is no `delegate` tool

The Linear issue's Replacement A asks for a **lightweight single-shot
delegation path — "run one sub-task, get result" as a one-liner, not manual
board choreography.** An earlier cut of this spec added a dedicated `delegate`
tool for it. That was wrong, and the reasoning matters because it turns on the
one fact that's easy to lose:

**Shape 1 has no drain loop.** The delegation capability installs the board as
a *ledger* — "the executive's own ReAct loop orchestrates; the board is a
ledger, not an execution engine" (design notes). Nothing watches the board. So:

- `taskTools.addTask({ goal, assignee })` writes a **ledger row and nothing
  runs it.** There is no "free concurrency loop" to pick it up — that loop is a
  **Shape 2** property (the `taskBoard().drain` block, §4.6/§4.10), a different
  surface entirely. In Shape 1, `addTask` is note-taking, not execution.
- The way the executive actually *runs* delegated work is by **calling a
  worker-tool** — a materialized sub-generator sitting in its `tools:` array
  (§4.5). `briefer("WebTransport")` runs the worker and returns its result
  inline. **That is the single-shot path**: one call, get a result, no board
  choreography. It already exists once §4.5 installs worker-tools.

So a separate `delegate({ to })` tool would just duplicate the worker-tool call
(BP-038 speculative surface). The only thing a `delegate` tool would add that
worker-tools don't is the **ad-hoc, undeclared** case (`delegate({ instructions })`
— spin up a sub-agent with no pre-declared worker). That is deliberately **out
of scope**: an undeclared sub-agent overlaps the "should the host also execute
tasks itself / manager-vs-IC" question, which is **FIX-923**'s research, and the
history-inheriting variant is **FIX-920**. Until those land, "declare a worker,
even a trivial one" (as `tech-brief`'s single `briefer` worker does) covers the
need. So this spec ships **no `delegate` tool**.

**Net delegation surface (two things, not three):**

- **Worker-tools** (§4.5) — call one to run a unit of work and get its result
  inline. This is the single-shot / everyday-fork-ergonomic path.
- **`taskTools`** (§4.3) — an optional *ledger* for when the executive wants to
  track a multi-step plan across turns (`addTask`/`listTasks`/`completeTask`).
  Nothing auto-runs; the executive still drives execution by calling workers.

### 4.13 Uniform delegation guidance lives in the capability, not the skill body

Pattern-mode skills had to hand-write boilerplate teaching the model *how* to
invoke them — `tech-brief`'s body literally opened with *"This is a pattern
skill — invoke it through `runSkill`: `runSkill({ name: "tech-brief", input })`."*
That mechanics-of-delegation text is uniform across every delegation skill and
should not be re-authored per skill.

**Decision.** The derived delegation surface (§4.1) contributes a **guidance
context** alongside the board and worker-tools — default-on, but toggleable via
a `guidance: false` opt-out (mirroring `createBashCapability`'s `tools` +
`guidance` preset split) — so the "how to orchestrate delegation" playbook is
injected by the capability, not written into each skill. Like the worker-tools,
it's a *dynamic* contribution (§4.2): it appears only when a worker-declaring
skill is active, and enumerates that skill's roster. Two parts:

- **Static playbook** (identical for all delegation skills): a concise fragment —
  "You have a private task board and worker tools. To hand off a unit of work,
  call the matching worker tool and use its result. Nothing runs tasks
  automatically; you drive the work. For a multi-step plan, track it with the
  task tools. Synthesize the workers' results into your answer." Kept short to
  avoid prompt bloat.
- **Dynamic roster** (per bound skill): enumerate the available worker tools by
  name + one-line purpose, resolved from the skill's `workers:` map — the same
  way `buildSkillsCatalogContext` enumerates skills today. This is what makes it
  *this skill's* team, not a generic lecture.

Delivered as **capability context, not a "meta-skill."** A literal meta-skill
(a skill that teaches skills) would have to be remembered and activated — which
just moves the boilerplate up a level — and couldn't enumerate the bound skill's
actual workers. Capability context auto-applies exactly when a worker-declaring
skill is active (§4.1 derivation), and sees the live roster. An author who wants
full manual control can disable the guidance with `skills.with({ ..., guidance: false })`,
same as bash's guidance opt-out.

**Consequence for skill bodies.** A delegation skill's body drops all "how to
delegate" text and carries only skill-specific content: purpose, when to
delegate, and what "done" looks like. `tech-brief`'s body shrinks from the
`runSkill` boilerplate to roughly *"Produce a concise technology briefing on
the requested topic. Hand the research to your `briefer` worker and return its
briefing."* — the mechanics come from the capability (§4.10 reflects this).

This also strengthens the necessity case for the delegation capability (§3.4):
it is not just tool plumbing, it carries the uniform playbook so N skills stop
repeating it (DRY; BP-018 shared prompt formatters; CLAUDE.md "prefer static
capability context entries over manual context functions").

## 5. Key Decisions & Ramifications (most load-bearing)

1. **Remove fork mode outright (not relocate it), superseding FIX-919 and its
   in-review PR #844.** Rejected alternatives: (a) land FIX-919 as designed —
   keep fork, fix it to inherit history, move it to a `fork` preset; (b) leave
   fork on the legacy `runSkill` router untouched while only pattern is
   removed. **Ramification:** the load-bearing decision in this spec.
   `SkillContextMode` collapses to a single `"inline"` value and an entire
   dispatch shape is deleted — the cleanest end state for "a skill is inline
   instructions plus optional delegation." Fork decomposes into two halves,
   and only one is deferred: the *fresh-context* half ("run this as a
   sub-agent, hand me the result") **already works** — calling a worker-tool is
   one call that returns its result (§4.12), so the everyday fork ergonomic
   survives with no new tool. What is deferred to **FIX-920** ("Re-introduce
   fork-like sub-execution via a task context-supply mode") is specifically the
   *context-window-preserving* half: a sub-agent that inherits the prior
   conversation up to the fork point. Between this landing and FIX-920, that
   history-inheriting variant does not exist; the isolation and single-shot
   ergonomics do. This is an owner decision (the issue now names FIX-920 as
   the re-introduction home and marks FIX-919 deprecated), made with the
   tradeoff in view. Concrete waste incurred: PR #844's ~1000 lines of
   fork-rework are thrown away (closed unmerged). Zero `context: fork` SKILL.md
   consumers exist, so no shipping skill breaks. If FIX-920 slips, only the
   history-inheriting case is unavailable — a much narrower gap than "no fork
   at all," and acceptable per the owner.
2. **Direction B (no harness) over Direction A (`skillHarness` owns the
   loop).** Rejected alternative: a block wrapping the generator that owns an
   outer GoalSeek loop and enforces whole-turn convergence across every
   active skill's goals. **Ramification:** whole-turn enforced convergence is
   deliberately *not* a framework primitive — it decomposes into rigorous
   delegation (enforcement inside the called flow) plus enforced output
   gating (`response-auditor`). If a genuine "must enforce the whole turn on
   the generator's own top-level output, and neither of those two covers it"
   case appears later, this decision needs revisiting — none has been
   identified to date (design notes §5, "Still open").
3. **Delegation is derived from the bound skills' `workers:`, on
   `createSkillsLibrary`, not an opt-in preset and not a standalone
   capability.** Rejected alternatives: (a) a manual `presets: { delegation: true }`
   opt-in flag; (b) a fully independent `createDelegationCapability` composed
   via its own `uses` entry. **Ramification:** the app author declares
   delegation *once* — by giving a skill `workers:` — instead of twice (workers
   + a flag that can desync with them). The library's config resolver already
   inspects each bound skill's parsed frontmatter; deriving "does any bound
   skill declare workers?" is a natural extension, and if none do, **nothing**
   installs (no board, no `taskTools`, no worker-tools, no guidance — zero
   overhead). This ties delegation's lifecycle to the skills-library binding
   surface (a generator gets delegation only through a bound skill), and
   `library.ts` owns the derivation, but avoids both a redundant flag and a
   second "which skill/body is active" resolution path. The board's own-state
   is pre-declared statically when the binding's inspectable skill set
   (`active` + `allowed`/catalog) contains any worker-declaring skill (§4.2);
   worker-tools + guidance are added dynamically per active skill — the same
   static-own-state / dynamic-tools split FIX-911 already uses. Board *choice*
   (shared vs. private) and a `delegation: false` force-off remain optional
   config overrides, so derivation doesn't remove control, only the redundant
   opt-in. (With fork removed, no execution-shape preset is added here at all —
   the `fork` preset FIX-919 would have added does not land.)
4. **Workers stay skill-declared via a decoupled `workers:` frontmatter
   field, not moved to app-level TypeScript config.** Rejected alternative:
   fully TS-declared workers on the consuming capability's config (cleaner
   separation, type-checked at the call site). **Ramification:** `skill-md.ts`'s
   frontmatter-parsing surface does not shrink as much as "remove pattern
   mode" might suggest — a `workers:` parser survives, just decoupled from
   `PatternBinding`. In exchange, prompt/promptRef delegation stays portable
   inside a shareable skill folder, matching the design notes' explicit
   intent ("safe to define inside a (portable) skill"). This is the single
   biggest interpretive call in this spec — flagged in Open Questions (§11)
   for explicit sign-off before implementation starts.
5. **New task-board backing built by adapting `ctx.self` (already
   `StateRef`-shaped), not a bespoke collection implementation.** Rejected
   alternative: reuse the existing `"request"` backing with a manually
   chosen, hand-namespaced `stateKey`. **Ramification:** preserves the
   collision-free-by-construction property FIX-914's own-state was built to
   deliver; a hand-namespaced request field is exactly the smell FIX-914
   exists to eliminate elsewhere in the codebase, so reintroducing it here
   for the one new backing this spec needs would be a regression against the
   framework's own stated direction.
6. **Migrating the three real pattern-mode consumers (`apps/kitchen-sink`'s
   `tech-brief`/`research-company`/`competitor-analysis` and their
   `examples/guides/research-team` mirrors) is in scope, split by shape —
   not deferred or stubbed out.** Rejected alternatives: (a) delete/stub
   these skills instead of migrating them, treating them as disposable demo
   content; (b) force all of them onto the `delegation` preset for
   consistency. **Ramification:** (a) would leave the monorepo build broken
   the moment `defaultPatternRegistry` is deleted — validation research
   confirmed `pnpm test` runs `examples/guides/research-team`'s test suite
   today via the workspace's `turbo run test`, so this isn't cosmetic;
   deleting rather than migrating trades a clean spec boundary for a broken
   build, which this spec rejects. (b) would silently change
   `research-company`/`competitor-analysis`'s observable behavior — their
   `pattern-config: { concurrency, dispatcher: topological }` and
   dependency-gated tasks rely on the task board's own deterministic
   dispatch, which Shape 1's executive-serialized tool calls cannot
   reproduce. The two shapes are kept distinct (§4.10): `tech-brief` →
   `delegation` preset (Shape 1, its one worker has no concurrency needs);
   `research-company`/`competitor-analysis` (both copies) → a
   task-board-drain-as-tool block (Shape 2/Replacement B), which is also
   this spec's strongest goal check — proof against real skills, not a
   synthetic fixture. `goalSeekLoop`-as-tool itself still ships via the
   existing generic `GeneratorTool = BlockDefinition` mechanism, verified
   and patched only if a real item-visibility leak is found (§4.6) — no new
   wrapper primitive is built preemptively.
7. **No dedicated `delegate` tool; the uniform "how to delegate" playbook is
   contributed by the capability, not written into each skill (§4.12–4.13).**
   Rejected alternatives: (a) ship a `delegate({ to, instructions })` tool as
   the single-shot surface; (b) leave each skill to hand-write its own
   delegation-mechanics boilerplate (as pattern skills did). **Ramification:**
   (a) is redundant — because Shape 1 has no drain loop, calling a worker-tool
   *is* the single-shot path, so a `delegate` tool would duplicate it (BP-038);
   the ad-hoc/undeclared and host-as-worker variants it would enable are
   deferred to FIX-923 (manager-vs-IC) and FIX-920. (b) fragments a uniform
   playbook across N skill files and re-introduces the `runSkill` boilerplate
   the redesign is trying to kill. So the `delegation` preset carries a
   concise, toggleable guidance context (static playbook + live worker roster);
   the cost is one more thing in the generator's system prompt, bounded by
   keeping the fragment short and opt-out-able. This makes the delegation
   capability carry vocabulary and instruction, not just tools — part of why it
   earns its place over a user-space wrapper (§3.4).

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|---|---|
| No bound skill declares `workers:` | Delegation is not installed at all — no board own-state, no `taskTools`, no worker-tools, no guidance context. Zero overhead (§4.1, derived-not-flagged) |
| A worker-declaring skill is in `allowed` but not yet active | The board own-state is pre-declared statically (delegation *might* happen, §4.2); its worker-tools + guidance appear dynamically only once that skill activates |
| Bound skill declares `workers:` but the executive never uses them | Board own-state + `taskTools` + worker-tools + guidance all install (derivation is per skill, not per use); unused is fine — the surface is available, not forced |
| Two active skills on one generator both declare a worker under the same key (e.g. both have a `researcher` worker) | Fail loud at bind time on key collision — never silently last-wins |
| A worker key collides with an already-installed tool name — `taskTools`' `addTask`/`listTasks`/… or a catalog tool like `search`/`fetch` (from spec-PR review) | Fail loud at **bind time** with a reserved-name check: worker keys are validated against the full installed tool set (taskTools handler names + the skill's allowed catalog tools + other workers), not just worker-vs-worker. Otherwise the generator runtime rejects duplicate tool names and the skill dies on its first step |
| App passes a shared board via `delegationBoard: myBoard` instead of the private own-state default | `taskTools` and worker-tools resolve against the shared board's `capability` accessor; the own-state `stateSchema` contribution is skipped entirely on that branch |
| App sets `delegation: false` on a binding whose skill declares `workers:` | Force-off: delegation surface is suppressed even though workers are declared (the one explicit override of derivation, §4.1) |
| `blockRef`/`agentRef` worker declared but the app never registered that key | Same fail-loud error `materializeWorker` raises today — preserved, not weakened |
| A `prompt`/`promptRef` worker itself needs `taskTools` (to add sub-tasks back to the same board) | The worker wires `uses: [board.capability]` (the drain board's own factory-backed accessor), **not** the generic `taskTools` singleton — its `ctx.parent` is the worker, not the board owner, so the singleton's default resolver would miss the ledger (§4.5 C) |
| Executive calls a worker-tool (the single-shot path) | Runs the materialized worker to completion and returns its result inline in one tool call — no `addTask`/`completeTask` needed; this is the everyday-fork ergonomic (§4.12) |
| Executive `addTask`s but never calls the assignee's worker-tool | The task sits in the ledger, unexecuted — Shape 1 has no drain to run it (§4.12). This is expected: the board is a ledger, not an engine. Guidance context (§4.13) tells the model it must drive execution itself |
| `taskTools.addTask({ assignee })` names an assignee with no matching worker | Today `addTask` accepts it and it only fails if/when dispatched (a fail-late smell FIX-923 flags). This spec keeps that behavior; whether to validate `assignee` against the known worker set at creation is FIX-923's call, not resolved here |
| `goalSeekLoop`-based tool call hits `maxIterations` without the judge returning `"done"` | Tool call still returns (existing cap-coercion + `finalize` handle this per FIX-910); the calling agent should be able to tell the result was cap-terminated, not organically completed (surface via the finalize projection, not a thrown error) |
| Old `pattern:` frontmatter present in a skill folder post-removal (unmigrated) | Parser fails loud with an explicit "pattern mode removed, see delegation" message — never silently reinterprets as `inline` |
| Old `context: fork` frontmatter present post-removal (external skill folder, not in this repo) | Parser fails loud with an explicit "fork mode removed" message pointing at delegation / FIX-920 — never silently downgrades to `inline` and runs the body in-context (which would leak the sub-agent's work into the parent, the opposite of what the author asked for) |
| `activeSkillsArraySchema`'s mode enum shrinks (`"pattern"` and `"fork"` removed → `"inline"` only) | A persisted session/request with a stale `mode: "pattern"` or `mode: "fork"` entry from before this ships must not crash on resume — dual-read/tolerate per BP-030, even though the entry is now inert |
| Agent-level fork (`AgentOverrides.contextMode: "fork"`) in an app's agent config | Unchanged — this spec removes only *skill* fork; the agent-level affordance keeps its current warn-and-compose-inline behavior (`materialize-agent.ts`). Not a regression, an unchanged boundary |
| A skill's `pattern-config:` declares `concurrency`/`dispatcher` (dependency-graph dispatch) | This is a Shape 2 signal, not Shape 1 — migrate to a task-board-drain-as-tool block (§4.10), never to the `delegation` preset, or the concurrency/dependency behavior silently changes to whatever the model's own tool-call ordering happens to produce |
| `competitor-analysis`'s discoverer worker fans out new tasks at runtime via `taskTools` mid-drain | The worker resolves the drain's board via its `board.capability` (which resolves the collection from inside the drain subtree, §4.5 C), so dynamically queued tasks are picked up by the still-running drain — not a disconnected board instance |

**Error taxonomy:** all `taskTools`/worker-tool failures stay in the existing
`{ ok: false, error: string }` structured-return contract (never thrown) —
this spec renames one sentinel (`no_active_pattern` → `no_delegation_board`)
and adds none. Two new *fatal, load-time* errors, both fail-loud and
non-retryable (the file needs migrating, not retrying): the legacy `pattern:`
frontmatter rejection and the legacy `context: fork` rejection.

## 7. Testing Strategy

**Goal (observable outcome):** an executive generator bound to a delegating
skill can hand sub-work to named workers through ordinary tool calls it
chooses to make itself, and a deterministic multi-step flow (a task-board
drain or `goalSeekLoop`) can be called by any generator as a single tool
without its internal steps leaking into the caller's history — proven
against the real skills this repo already ships, not just a synthetic
fixture.

**Goal check (real path, run by hand, not CI):**

1. `fsdev run` the migrated `apps/kitchen-sink/skills/tech-brief` (now a
   `delegation`-preset skill) end to end. This skill's single `briefer` worker
   makes it the natural single-shot proof. Inspect the NDJSON trace and
   confirm: (a) a private task board was created, (b) the sub-work ran as a
   single worker-tool call — one tool invocation, not a manual
   `addTask`→`completeTask` sequence, (c) the final response is the worker's
   briefing, and (d) the skill body carried no delegation-mechanics boilerplate
   (the "how to delegate" guidance came from the capability context, §4.13).
   PASS/FAIL on all four — this is the Shape 1 + single-shot proof, and the
   concrete evidence that fork removal did not regress the everyday "run one
   sub-agent, get result" ergonomic.
2. `fsdev run` the migrated `apps/kitchen-sink/skills/research-company` (now
   a task-board-drain-as-tool block) end to end. Confirm via NDJSON: (a) the
   tool call's result is the finalized synthesis, not the raw per-worker
   trace, (b) `market-analyst`/`financial-analyst` ran under the same
   concurrency the old `pattern-config: { concurrency: 2 }` specified, (c)
   `synthesizer` only started after both deps completed, (d) no
   non-`history:false` intermediate items from the nested drain leaked into
   the executive's history. PASS/FAIL on all four — this is the Shape 2 /
   Replacement B proof, and the strongest evidence in this spec that
   removal is safe.
3. `fsdev run` the migrated `competitor-analysis` specifically to confirm
   the discoverer's runtime `taskTools`-driven fan-out (queuing analyzer
   tasks mid-drain) is still picked up by the same drain instance, not lost.

**Discipline:** `fsd:tdd` (feature/enhancement) — red-green-refactor,
vertical tracer-bullet slices. This is new composition of existing
primitives plus one new backing, not a bug fix.

**Behaviors to test (tracer bullets, observable in terms of items/state/
return values):**

1. `getOrCreateTaskCollection` builds a working `TaskCollectionRef` from a host
   state ref passed to the existing `StateRef` path (mirrors the
   sequencer/request-backing tests in the same suite) — no new backing.
2. **Derivation:** `skills.with({ active: ["research-lead"] })` where the skill
   declares `workers:` installs board + `taskTools` + N worker-tools + guidance
   — with **no** `delegation` flag (§4.1). A bound skill with no `workers:`
   installs none of it. `delegation: false` suppresses it even with workers.
   Whole-catalog `dynamicActivation` pre-declares the board even with no
   statically-named worker skill (§4.2).
3. Calling a worker-tool by name dispatches to the correctly materialized
   worker and returns its result inline in one tool call (the single-shot
   path, §4.12) — matrixed across `prompt`/`promptRef`/`blockRef`/`agentRef`.
2a. **Worker-tool schema + name (§4.5 A/B):** a direct-mode worker-tool exposes
    an LLM-facing `{ input }` schema (not `workerInputSchema`'s
    `taskId`/`attempts`) and is named by the bare worker key (`briefer`, not
    `skillWorker_*`) — assert both, since the single-shot claim depends on them.
2b. **Worker-embedded `taskTools` (§4.5 C):** in a Shape 2 drain, a worker that
    declares `tools: [taskTools]` mutates the *drain's* board via
    `board.capability` (assert its `addTask` is picked up by the running drain),
    not a disconnected board from its own `ctx.parent`.
3a. The derived delegation surface contributes a guidance context that includes
    the static playbook **and** the live worker roster (the bound skill's
    declared worker names) — assert the roster text reflects the actual
    `workers:` map, and that a skill body with no delegation boilerplate still
    yields a generator whose system prompt explains how to delegate (§4.13).
3b. **Board resolution via `ctx.parent` (P1):** a `taskTools` handler invoked as
    a child of the generator mutates the *generator's* board (assert `addTask`

## 8. Non-Goals

- **New generic Shape 2 infrastructure beyond what this spec's three real
  migrations need.** This spec proves `taskBoard().drain` and `goalSeekLoop`
  are tool-callable (§4.6) and migrates the three specific skills that
  require it (§4.10) — it does not add a new pattern-recipe registry, a
  generic "board-drain-as-tool" factory function, or any new pattern
  factories beyond what FIX-910 already shipped. If a future skill needs the
  same shape, it follows the same manual `blockRef` wiring this spec
  establishes by example, not a new declarative surface.
- **Cross-skill/team-level shared boards that autonomously dispatch to many
  skills' workers** (the "workstream" tier in the design notes) — explicitly
  deferred, build-time-composed from a shared worker library, later.
- **Renaming/collapsing pattern→strategy terminology.** That was FIX-916,
  canceled and superseded by this issue; not resurrected here.
- **Reintroducing fork-like behavior in any form.** Fork is removed, full
  stop. "Spawn a sub-agent that inherits the conversation so far" is
  **FIX-920's** job (via a task context-supply mode), not this spec's — this
  spec does not build a partial or interim version of it. Callers who need
  sub-agent *isolation* today use delegation + the task board (already
  history-hiding); callers who need the fresh-context single-shot ergonomic
  call a worker-tool (§4.12); callers who need *inheritance* wait for FIX-920.
- **Ad-hoc / undeclared sub-agents and the host-as-worker question.** A
  `delegate({ instructions })`-style ad-hoc sub-agent, and whether the
  executive host may also *execute* tasks itself (not just coordinate), are
  deferred to **FIX-923** ("should a delegating host also be a worker? —
  manager-vs-IC research"). This spec ships only declared-worker delegation
  and a ledger; it does not add ad-hoc invocation or host self-execution, and
  keeps today's `assignee`-not-validated-at-creation behavior for FIX-923 to
  rule on.
- **The workforce agent-level fork** (`AgentOverrides.contextMode: "fork"`,
  `materialize-agent.ts`) — a separate type and code path (§4.11), left
  exactly as-is. Whether to also remove that affordance is a future workforce
  change, not this spec.
- **Skill-defined resources / a task's resource workspace (blackboard)** —
  the related **FIX-921** ("Skills define resources; assign a task a resource
  workspace"). This spec's delegation task board is a *task ledger*, not a
  shared resource/blackboard workspace; giving a delegated task its own
  resource workspace is FIX-921's job. The worker surface here should not
  preempt that design — it passes task *input*, not a resource workspace
  handle.
- **Focusing / pruning the pattern catalog** — the related **FIX-922** ("what
  does task-board + delegation + goalSeekLoop subsume?"). This spec removes
  the *skill-frontmatter binding* to patterns (`defaultPatternRegistry`) and
  migrates the three real consumers, but it does **not** decide which
  `@flow-state-dev/patterns` factories are now redundant once delegation +
  `goalSeekLoop` exist — that catalog-rationalization is FIX-922's scope. The
  pattern factories themselves (`parallelTasks`, `planAndExecute`,
  `supervisor`, etc.) stay as-is here.
- **Fully retiring `SkillContextMode`** (removing the now-single-value
  discriminator from the type surface and every reader). This spec keeps the
  one-value `"inline"` enum (§4.11, §11) — collapsing it to nothing is a
  separable cleanup that shouldn't gate the fork/pattern removal.
- **Full removal of the session-global `createSkillsCapability`/`runSkill`
  router shell.** This spec removes both the `pattern` and `fork` *routes*
  from the router, leaving it inline-only. Whether the inline-only router
  shell should then be deleted entirely (inline binding already lives on the
  FIX-911 `createSkillsLibrary` path) is a follow-up cleanup, not committed
  to here.
- **A generic `asGeneratorTool()` wrapper primitive** — built only if §4.6's
  verification step proves the existing generic mechanism has a real,
  unfixable item-visibility gap (Key Decision 6, see §5).
- **Deepening opportunities flagged, not fixed here** (from codebase
  research, follow up via `fsd:improve-codebase-architecture`):
  - `skill-md.ts` is a 1326-line single file mixing inline/fork/pattern
    frontmatter parsing. Excising fork- and pattern-specific parsing is in
    scope; splitting the file into per-concern modules is not.
  - `taskTools`'s board-resolution is generalized only as far as this spec's
    delegation-preset use case needs (an injected resolver function); a
    fuller "target a specific board among several" design is a follow-up.
  - No architecture doc names "any `BlockDefinition` can be a `GeneratorTool`"
    as an intentional, documented pattern — this spec adds a docs cross-link
    (§9) but not a fuller architecture-doc treatment.
  - `docs/specs/FIX-911.md`'s own "Pattern/fork untouched (FIX-910)" line is
    a stale cross-reference (FIX-910 shipped as the `goalSeekLoop` primitive,
    not a pattern→strategy rename) — worth a one-line correction when this
    ships; not fixed as part of this scope.
- **Already-rejected directions:** none found in `docs/internal/out-of-scope/`
  for this area (checked; no existing entry references skills/pattern-mode/
  delegation).
