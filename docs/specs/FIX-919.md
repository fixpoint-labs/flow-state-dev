## 1. TLDR

**Plain-language summary.** Today a "fork" skill doesn't really fork. It's meant
to peel off a chunk of work into a child agent so the main chat's context window
stays clean — but the child starts with a blank slate and can't see anything the
conversation already established. This change makes a fork behave like a real
fork in the road: the child picks up the conversation exactly where the parent
was, goes off and does the heavy work on its own, and hands back only its final
answer. The main chat never sees the child's scratch work, so its context stays
small. We also stop routing fork through the old shared, whole-session dispatch
and instead hang it directly off the generator that uses it, as a tool.

**Technical statement.** Rework skill-fork so the child generator seeds its
messages from the engine's already-assembled history view (`ctx.session.items.history()`)
up to the fork point, keeps `itemVisibility: { client: true, history: false }`
so its own work stays out of the parent's future history, and is delivered as a
tool installed by a `createSkillsLibrary` preset (FIX-911) rather than a route on
the session-global `runSkill` router.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*
- **What we gain.** Fork skills become usable for their actual purpose — a child
  that already knows the conversation, does a big investigation, and returns a
  compact result without bloating the parent's context. Fork also stops being a
  special whole-session mode and becomes a normal per-generator tool.
- **Where the work sits.** Mostly rewiring, not new logic: history inheritance is
  a small addition to the existing child generator using a slot the framework
  already supports, and the delivery is a new preset alongside FIX-911's existing
  one. The genuinely new code is the fork tool that reads the binding and spawns
  the child.
- **Where the complexity actually is.** Not the happy path. It's the boundary: not
  copying a half-finished tool call into the child (which a model would reject),
  bounding how much history gets copied so a long conversation doesn't blow up
  cost, and keeping the child's work from leaking back into the parent.
- **The risk.** A subtly wrong inherited-message set (a dangling tool call, the
  child's own work bleeding into the parent). Caught by unit tests on the seeded
  message set and item isolation, plus a real-model goal check that a fork child
  can answer using a fact only the parent's earlier turn established.

**Deliverables.**

Engine:
- Skip `in_progress` `tool_output` items in `itemToLLMMessages` (`packages/engine/src/context/history.ts`) so the triggering fork call (and any in-flight tool result) isn't replayed into inherited history; confirm against the retry/resume path (§ History exclusion).

Orchestration:
- Add a `history` slot (bounded, opt-in window; `!== undefined` guard so an explicit `0` means empty) to the fork child generator in `packages/orchestration/src/skills/fork-generator.ts`, seeding from `ctx.session.items.history()`.
- Extract a **private** `resolveAndDispatchForkSkill(...)` from the existing `run-skill-tool.ts` fork branch (reusing `internal/get-collection`, `stripFrontmatter`/`substitute`/`toSkill`); no new public tool-factory export unless a concrete consumer appears.
- Add a `fork` preset on `createSkillsLibrary` (`library.ts`) that installs the fork tool **and** a catalog context formatter over the `allowed` fork skills (both seed `initialSkills` on first use); add `forkModelId` / `forkHistoryLimit` to `SkillsLibraryOptions` (one naming scheme, threaded straight through); require a non-empty `allowed` statically, and filter to `context: fork` skills when reading each manifest at runtime (mode isn't known at build-time preset resolution).
- Remove the fork route from the session-global `runSkill` router (`run-skill-tool.ts` / `createSkillsCapability`), leaving pattern + the router shell for FIX-918; update the stale FIX-911 `library.ts` comment about fork dispatching through `runSkill`.

Docs:
- Create `apps/docs/docs/skills/fork.md`; extend `skills/overview.md`, `skills/activation.md`, `skills/authoring.md`, `guides/adding-skills-to-your-app.md` (Step 10), and `packages/orchestration/README.md`.

Tests:
- Add `packages/orchestration/test/skills/fork-generator.test.ts` and fork-tool tests; add a real-model goal check `goals/skill-fork/inherits-history-to-fork-point/`.

**Size estimate.** **Medium** — multi-file, one package (`orchestration`) plus docs, ~150–350 LOC. Single PR. (The FIX-911 dependency and FIX-918 coordination are sequencing, not extra code here.)

## 2. Overview

Linear issue: [FIX-919](https://linear.app/fixpoint-labs/issue/FIX-919). Part of
the skills-system redesign (fast-follow to FIX-911).

A "fork" skill is meant to spawn a child agent that does a bounded chunk of work
and returns only its result, so the parent generator's context window is
preserved. Today the child starts empty — it receives only the skill body and a
tool list, with no inherited conversation — so it can't act on anything the
conversation already established, defeating the purpose. This spec makes the
child inherit the conversation history up to the fork point, then diverge in
isolation, and moves fork off the retiring session-global dispatch onto a
per-generator capability tool (the model FIX-911 established for inline skills).

## 3. Background & Research

### Industry framing

The ecosystem splits sub-agents into two shapes: **"subagents"** (Claude Code,
Anthropic Research, Vercel AI SDK) run in an *isolated* context and return only a
result; **"handoffs"** (OpenAI Agents SDK / Swarm) inherit the *full* transcript
and replace the parent. FIX-919's fork is a deliberate hybrid — inherit history
*up to a fork point*, then isolate, then return only the result. There is no
single industry name; "forking subagent" / "scoped handoff" both communicate it.
The return-only-the-result property is the established **context-firewall** /
**context-offloading** benefit: heavy reading happens in the child's window, and
the parent's window stays clean.

Two hard constraints surfaced from prior art and apply directly:

1. **Never inherit a dangling tool call.** Anthropic's Messages API rejects a
   `tool_use` block with no matching `tool_result` (HTTP 400). Forking at a state
   that includes the triggering tool call but not its result reproduces the exact
   "orphaned tool_use after truncation" failure seen across `claude-code`,
   `litellm`, and `openclaw`. The safe fork point is **just before the triggering
   call**. OpenAI's `remove_all_tools` handoff filter and the AI SDK's
   `ignoreIncompleteToolCalls` exist precisely to guard this.
2. **Copying history into a child is uncached and costs real tokens.** A subagent
   builds its own prompt cache from scratch; the copied prefix is billed uncached
   on first use, and front-truncating to bound it both orphans tool pairs and
   kills the cache. So the inherited window must be **bounded by whole turns**, not
   front-trimmed mid-pair. Anthropic's own guidance prefers a scoped brief over a
   full transcript for cost reasons; our default is "inherit to here" with a knob
   to cap it.

### How the codebase already supports this

The engine makes the fork almost free, which reshapes the whole design:

- **A child generator invoked as a tool shares the parent's execution context's
  `session` handle.** `ctx.session.items` (built once at request setup) is passed
  by reference into every scoped child context (`createExecutionContext.ts` —
  `_withExecutionScope` → `createContext`). So `ctx.session.items.history()`
  *inside the child* returns the parent's assembled history with no new plumbing
  (each fork still pays the normal history-expansion cost: item→message, orphan
  trim, optional token counting).
- **The generator `history` slot is the sanctioned seam** for injecting prior
  turns as real role-tagged messages. `assembleMessages` builds `system → history
  → user`; `normalizeHistorySlot` turns `history: true` into `(_i, ctx) =>
  ctx.session.items.history()` and `history: { limit }` into a bounded query
  (`generator.ts:640-657`, `message-assembly.ts:70-101`). Today's fork sets **no**
  `history` slot, which is exactly why it starts empty.
- **`history()` self-excludes the child's own work, but the in-flight fork call
  must be excluded explicitly.** `loadLLMHistory` expands prior completed requests
  + already-emitted live items, dropping anything resolved to `history: false`
  (`history.ts:74-77`, `330-368`). The child's own emissions are `history: false`,
  so they self-exclude. **The triggering fork call does not.** `emitToolOutputAround`
  emits the fork tool's `tool_output` item with `status: "in_progress"` and
  `output: undefined` *before* the tool body runs (`emit-tool-output.ts:146-149`),
  and `itemToLLMMessages` converts any `tool_output` regardless of status
  (`history.ts:105-133`); the item carries the host generator's visibility
  (`history: true` for a normal agent). So a fork child using a plain `history:
  true` would inherit its own triggering call with a garbage/undefined result —
  breaking the "fork just before the call" semantics. This is the P1 gap Codex
  raised on the spec PR (verified against the engine). **The fork child must
  exclude the current fork tool call's `tool_output` from its inherited history**
  — see §4 (History exclusion) for the mechanism. Completed earlier-in-turn tool
  calls still expand as *matched* call+result pairs (`itemToLLMMessages`), and
  `trimOrphanedToolMessages` is a further net.
- **Capabilities are blind to host config.** A capability's config resolver
  receives only `{ presets, blockKind }`; a contributed tool receives a runtime
  `BlockContext` that does **not** expose the host generator's resolved `model`
  or sibling tool set (`capability/types.ts`, `merge.ts`, `resolve-capabilities.ts`).
  So "clone the host generator's model/tools" cannot be discovered through `uses`
  — it must be threaded via the capability factory's closure, exactly as today's
  `createSkillForkGenerator(options)` already takes `catalog` + `forkModelId`.

### Why the chosen approach

The ticket frames a "central design problem": for a capability's fork tool to
spawn "a child just like the parent," it needs the host's resolved config, and
lists three options — (a) give capabilities config-awareness (two-phase
resolution), (b) a narrower clone, (c) a framework "spawn a child of the current
generator" seam. The research resolves this decisively toward **(b), with no
framework change**:

- The one genuinely load-bearing thing "like the parent" needs — the conversation
  so far — is available to the child via the shared session views + the existing
  `history` slot, with no new seam (only the in-flight-fork-call exclusion of
  § History exclusion, and the normal per-fork history-expansion cost).
- Everything else the child needs (its instructions, its tools, its model) is
  already threaded through the capability factory closure. The child's tools come
  from the skill's declared `allowed-tools` against the library `catalog`; its
  model from a configured `forkModelId`.
- Options (a) and (c) buy only the ability to clone the host's *exact* resolved
  model and *every* sibling capability. That is not what a fork skill needs — a
  fork skill declares the tools it wants — and (a) carries a real framework cost
  (two-phase capability resolution, `uses`-resolves-last). Per BP-038, we build
  the least that satisfies the spec and do not add the seam.

Delivery follows FIX-911's established shape: fork installs as a **preset on
`createSkillsLibrary`** (a sibling to `dynamicActivation`), so a generator opts
into fork the same way it opts into any other skills behavior — `uses: [
skills.config({ allowed: [...] }).presets({ fork: true }) ]`.

### Key Decisions & Ramifications (top 5)

1. **Inherit history via the generator `history` slot reading `ctx.session.items.history()`, plus an explicit exclusion of the triggering fork call.**
   *Alternative rejected:* a bespoke "fork-point item index" API on the session
   views. *Ramification:* the child still inherits via the standard `history` slot,
   but the "in-flight fork call is excluded by construction" assumption is **false**
   — `emitToolOutputAround` emits the fork call's `tool_output` (`in_progress`,
   `output: undefined`) before the tool body runs, and `itemToLLMMessages` replays
   it regardless of status (Codex P1, verified). So a small history-exclusion
   mechanism is required (§4 History exclusion): the recommended fix is a
   layer-owning guard in `itemToLLMMessages` that skips `in_progress` `tool_output`
   items (an in-flight, resultless call must never be replayed as a completed
   result), which touches `packages/engine` — revising the earlier "zero engine
   change" framing. Locks us to turn-granular history (no sub-turn cursor) —
   accepted, because sub-turn forking would reintroduce the dangling-tool-call
   hazard.

2. **Resolve the "central design problem" as option (b): a narrower clone, no framework change.**
   *Alternative rejected:* (a) capability config-awareness / two-phase resolution;
   (c) a framework spawn-child seam. *Ramification:* the fork child inherits
   history + skill body + skill-declared tools + a configured model — **not** the
   host's exact resolved model or every sibling capability. A fork skill that needs
   a specific tool must declare it in `allowed-tools`. This keeps the framework
   surface untouched; the cost is that "just like the parent" is a documented
   approximation, not a literal clone.

3. **Bound the inherited history by whole turns; default to a conservative `{ turns: 10 }`, expose `forkHistoryLimit`.**
   *Alternative rejected:* default to full-to-here (unbounded); or summarize the
   prefix. *Ramification:* the default (`DEFAULT_FORK_HISTORY = { turns: 10 }`, §11 Q2)
   protects against the uncached-token blow-up on long conversations out of the box;
   apps that want the full conversation set `forkHistoryLimit: undefined` (or a
   wider `{ turns }` / `{ tokens }` cap). Uses the existing `MessageLimit`
   (`{ turns } | { tokens } | number`) which packs whole turns and never splits a
   tool pair. No summarization primitive is built (YAGNI). This default is stated
   consistently in §4 (API), §5 step 1, §6, and §11.

4. **Deliver fork as a `fork` preset on `createSkillsLibrary`, and remove the fork route from the session-global `runSkill` router.**
   *Alternative rejected:* leave fork on the session-global router (purely
   additive). *Ramification:* fork gets exactly one home, aligned with FIX-911's
   per-generator model, and the session-global `activeSkills` path shrinks toward
   deletion. This couples FIX-919 to editing the retiring router — coordinated with
   FIX-918, which owns the router's *final* deletion (pattern route + shell).

5. **Configure the child's model via `forkModelId` (closure), not the host's resolved model.**
   *Alternative rejected:* read the host's model from `ctx` at fork time.
   *Ramification:* the host's resolved model is provably unreachable from a
   capability tool (Background), so we don't pretend to clone it. The child runs on
   a library-configured model with a sensible default. Documented as a deliberate
   limitation of "like the parent."

### History exclusion (the fork-point boundary)

The fork child must not inherit its own triggering `tool_output`. `emitToolOutputAround`
emits that item (`status: "in_progress"`, `output: undefined`) *before* the fork
tool body runs, and `itemToLLMMessages` currently replays any `tool_output`
regardless of status, so a plain `history: true` child would see a
call-with-garbage-result at the tail of its inherited messages (Codex P1).

**Chosen mechanism — a layer-owning guard (BP-028).** Skip `in_progress`
`tool_output` items in `itemToLLMMessages` (`packages/engine/src/context/history.ts`).
An in-flight, resultless tool call has nothing model-valid to replay in *any*
history assembly, so this is a general correctness fix, not a fork special-case;
it removes the fork call cleanly and needs no callId plumbing into the fork tool.
The implementer **must** confirm against the retry/resume path (BP-035 second-path
checklist) that no consumer relied on an `in_progress` `tool_output` being replayed
— the intentional live-item inclusion in `loadLLMHistory` targets `completed` /
`failed` items (the "try again sees in-flight tool state" guarantee), which this
guard leaves untouched.

*Fallback if the guard proves unsafe for resume:* a fork-local custom `history`
function that reads items via `selectForContext`, drops the current fork call's
`tool_output` (by `callId`), and builds messages — heavier (duplicates
`itemToLLMMessages`) and needs the callId surfaced to the tool body, so preferred
only if the engine guard can't be made safe. Recorded as Open Question 4.

### Data flow

1. A generator binds fork: `uses: [ skills.config({ allowed: ["deep-research"] }).presets({ fork: true }) ]`.
2. The model calls the installed `forkSkill` tool with `{ name, input }` where `name` is a `context: fork` skill in `allowed`.
3. The fork tool (running in the host generator's scope, with `ctx`) resolves the
   manifest from the skills collection, validates it is fork-mode and in `allowed`,
   strips frontmatter, and substitutes `$ARGUMENTS` (`input`) and `${SKILL_DIR}`.
4. It dispatches the fork **child generator** with `{ skillName, body,
   allowedToolNames, modelId }`, adding the inherited-history configuration.
5. The child, sharing the parent's `ctx.session.items`, assembles `system (skill
   body) → history (inherited, bounded, with the in-flight fork call excluded per
   § History exclusion) → user (substituted task)`, runs its tool
   loop with the skill's tools, and streams `{ client: true, history: false }`
   items (visible in DevTool, absent from the parent's future history).
6. The child's final text returns as the fork tool's result item — the only thing
   the parent sees.

### API surface

`SkillsLibraryOptions` (extends the FIX-911 surface):

```ts
export interface SkillsLibraryOptions {
  // ... existing FIX-911 fields (collection, catalog, initialSkills, scope, …) …
  /** Model the fork child runs on. Not the host's resolved model (unreachable
   *  from a capability tool). Default: a sensible chat model. */
  forkModelId?: string;
  /** Bound on the history the fork child inherits. Whole turns, never split.
   *  Omitted = the conservative default `DEFAULT_FORK_HISTORY = { turns: 10 }`.
   *  Set `{ turns: 0 }` for none, or a wider `{ turns }` / `{ tokens }` cap for
   *  more. (Inheriting the *entire* window is the owner-level choice of making
   *  DEFAULT_FORK_HISTORY `undefined` — §11 Q2 — not a per-call sentinel.) */
  forkHistoryLimit?: MessageLimit; // number | { turns: number } | { tokens: number }
}
```

Binding + preset (mirrors `dynamicActivation`):

```ts
const skills = createSkillsLibrary({ catalog, initialSkills, forkModelId: "openai/gpt-5.4-mini" });

generator({
  uses: [ skills.config({ allowed: ["deep-research"] }).presets({ fork: true }) ],
  // …
});
```

Fork tool I/O (unchanged public shape from today's fork result):

```ts
// input
{ name: string; input?: string }
// result item (the only thing the parent sees)
{ skill: string; mode: "fork"; result: string }
```

Fork generator (extended):

```ts
export interface CreateSkillForkGeneratorOptions {

  defaultModelId?: string;

```

### Usage example

Before (today): the fork child starts empty; a research skill can't use anything
the user said earlier in the chat.

After: a fork skill picks up the conversation. In a session where the user
already said "our launch is March 3," the model forks a research skill whose
`input` never mentions the date, and the child still grounds its work on it —
then only the report returns.

```ts
// skills/deep-research/SKILL.md
// ---
// description: Deep research on a topic. Returns a structured report.
// context: fork
// allowed-tools: [search, fetch]
// ---
// Research the topic in light of the conversation so far. Return: background,
// key findings, open questions. Topic: $ARGUMENTS

// flow.ts
export const assistant = generator({
  name: "assistant",
  itemVisibility: { client: true, history: true },
  model: "openai/gpt-5.4-mini",
  uses: [ skills.config({ allowed: ["deep-research"] }).presets({ fork: true }) ],
});
// The model calls forkSkill({ name: "deep-research", input: "competitor pricing" }).
// The child sees the prior turns (incl. "launch is March 3"), runs search/fetch
// in isolation, and returns only its report as the tool result. The parent's
// next turn does NOT contain the child's search/fetch chatter.
```

### State management

None new. The fork tool reads the skills collection and `ctx.session.items`; it
holds no request-scoped own-state. (FIX-914 own-state is available if a future
need arises, but the fork path does not require it — a fork tool's own `ctx.self`
resets per call anyway.)

### Error handling

| Case | Behavior |
|---|---|
| `name` not in the binding's `allowed` set | Throw at call time: `Skill "X" is not in this generator's allowed fork set.` |
| `name` resolves to an inline/pattern skill | Throw: fork tool only accepts `context: fork` skills (mirror of `dynamicActivation`'s inline-only rejection). |
| Unknown/`disable-model-invocation` skill | Throw with the available list (reuse today's `run-skill-tool` messages). |
| Unknown tool key in `allowed-tools` | Warn and skip (unchanged from `resolveForkTools`). |
| Inherited history contains an orphaned tool message (edge data) | `trimOrphanedToolMessages` in `loadLLMHistory` drops it; the child never sees a dangling pair. |
| Empty history (turn 1 fork) | Child runs with just system + user (degrades to today's behavior). |

## 5. Implementation Sequence

Each step is independently testable; TDD tracer-bullet order.

1. **History inheritance on the fork generator.** In `fork-generator.ts`, add
   `historyLimit?: MessageLimit` to options and set the child's slot to
   `history: { limit: historyLimit ?? DEFAULT_FORK_HISTORY }`, where
   `const DEFAULT_FORK_HISTORY: MessageLimit = { turns: 10 }` (§11 Q2). The cap
   lives under `limit` because the `history` object is an `ItemQuery`, not a bare
   `MessageLimit` (Codex P2 — `{ turns: 10 }` at top level would be ignored and fall
   back to the full window). Use `??` (nullish), not truthiness, so an explicit
   `forkHistoryLimit: 0` / `{ turns: 0 }` is preserved as an empty window rather than
   replaced by the default. Keep `itemVisibility` unchanged. *Test:* build the block
   and assert `config.history` is set; run with a seeded session and assert the
   mocked `generate` received prior-turn messages (see §7).

2. **Fork dispatch helper (private).** Extract a private
   `resolveAndDispatchForkSkill({ collectionKey, catalog, forkModelId, historyLimit, allowed, initialSkills })`
   from the existing `run-skill-tool.ts` fork branch (into `fork-generator.ts` or
   `internal/`). It calls `ensureSeeded(collection, initialSkills)` first, resolves
   the manifest (reuse `internal/get-collection`), validates the manifest's mode is
   `fork` and that it's in `allowed`, substitutes the body (reuse
   `substitute` / `stripFrontmatter` / `toSkill`), builds the fork child via
   `createSkillForkGenerator`, and adapts I/O (`connectInput`/`connectOutput`) so
   the child's text is the tool result. **Not exported publicly.** *Test:* call with
   an allowed fork skill → result item shape; with a non-allowed / inline skill →
   throws; a **bundled fork skill on the first turn** (only `initialSkills`, nothing
   pre-seeded) resolves rather than failing as unknown.

3. **Library preset.** In `library.ts`, add a flag-only `fork` preset that, when
   set, contributes the fork tool built from the binding's resolved `allowed` set +
   library `forkModelId`/`forkHistoryLimit`, plus the fork catalog formatter. The
   only static check is that `allowed` is non-empty; mode (accept only
   `context: fork`) is validated when the tool/catalog reads the manifest at runtime,
   because the resolver can't see skill mode at build time. Add the two options to
   `SkillsLibraryOptions`. *Test:* `skills.config({ allowed }).presets({ fork: true })`
   installs the tool + formatter; an empty `allowed` fails at resolution; a non-fork
   manifest is skipped/rejected at read time.

4. **Retire the session-global fork route + stop the runSkill catalog advertising fork skills.**
   Remove the fork branch + fork generator wiring from `run-skill-tool.ts` and the
   fork-related options from `createSkillsCapability` (`capability.ts`). **Also
   filter `context: fork` skills out of the runSkill catalog** — `listEnabledSkills`
   / `buildSkillsCatalogContext` today filter only disabled skills, not
   `contextMode`, so a generator carrying both the default `runSkill` preset and the
   new `fork` preset would still advertise fork skills under `runSkill`, and the
   model would call a route that no longer exists (Codex P2). Add a `contextMode`
   filter (and have the runSkill router reject a fork skill with a clear error as
   defense-in-depth). Leave the inline (legacy) and pattern routes + the router
   shell for FIX-918. *Test:* existing `run-skill-tool.test.ts` fork cases move to
   the new fork-tool test; the router test asserts no fork route and that fork
   skills are absent from the runSkill catalog.

   **Up-front activation stays inline-only; fork is tool-dispatch-only (Codex P2).**
   Removing fork from `runSkill` would otherwise make a fork skill matched by
   `createSkillActivator` (slash/keyword/classifier) inert:
   `createApplySkillActivation` writes a non-inline `activeState` entry and relies
   on `runSkill` for fork dispatch (`apply-skill-activation.ts:15-18`), while the
   active-skill formatter skips non-inline entries (`context-fn.ts:90-91`) — so
   nothing would run it. Fork skills are invoked **only** by the model calling the
   `forkSkill` tool. So: exclude `context: fork` skills from up-front activation
   (scope the activator's `allowed` to inline skills, and have
   `createApplySkillActivation` skip/reject a fork match with a clear error rather
   than writing a dead entry). Drop its now-removed `runSkill`-for-fork reliance.
   *Test:* an activator that matches a fork skill does not produce a dead activeState
   entry; the model still reaches the skill via `forkSkill`.

5. **Exports + docs.** Export only new option types from `index.ts` (the fork
   dispatch helper stays private — no public `createForkSkillTool` factory). Apply
   the Documentation Plan (§9).

*Dependencies between steps:* 1 → 2 → 3 (each builds on the prior). 4 depends on
3 (the replacement must exist before the old route is removed). 5 last.

## 6. Edge Cases & Error Handling

| Edge case | Expected behavior |
|---|---|
| Fork at turn 1 (no prior history) | Child gets system + user only; no error. |
| Very large inherited history | Bounded by `forkHistoryLimit` (whole turns); default `{ turns: 10 }` (DEFAULT_FORK_HISTORY). Document the uncached-token cost and the engine's implicit `historyWindow` cap. |
| The triggering fork tool call | Emitted as an `in_progress` `tool_output` *before* the fork body runs, so it is NOT excluded automatically — the § History exclusion guard removes it. Regression test asserts the child's seeded messages contain no dangling/garbage-result fork call. |
| Prior completed tool calls in the same turn | Expand as matched call+result pairs; never dangling. |
| Child emits many items | All `history: false` → absent from the parent's next-turn `history()`; visible in DevTool (`showSubAgents`). |
| Nested fork (fork skill forks again) | Grandchild inherits history filtered by `history: false`, so it does **not** see the parent-fork's child work — only the shared conversation. Documented; not specially handled. |
| `allowed` omitted / empty with `fork: true` | **Fail at preset resolution** with a clear error. Fork spawns a child with tools + inherited history, so it is security-sensitive; unlike `dynamicActivation` it does not default to the full catalog. Requiring an explicit `allowed` set is the simpler, safer contract (Codex/Cursor review). |
| Same-turn in-flight items and `forkHistoryLimit` | `loadLLMHistory` always appends in-flight items of the current request regardless of `limit`; `forkHistoryLimit` bounds prior *completed* turns, not tool-heavy same-turn context. The cap is not absolute — document this so implementers don't assume it bounds everything. |

**Error taxonomy:** all fork-tool validation errors (not-allowed, wrong mode,
unknown skill) are **fatal** to that tool call (thrown, surfaced as a failed tool
result) — not retryable. Unknown tool keys in `allowed-tools` are **non-fatal**
(warn + skip), preserving today's tolerance.

## 7. Testing Strategy

**Discipline: `fsd:tdd`** (feature/enhancement — new behavior + new delivery
surface, executed red-green-refactor with tracer bullets). The Linear issue
should carry an **Enhancement** category label so `implement-issue` routes to TDD.

**Goal & goal check (required).**
- **Goal (observable outcome):** a fork skill invoked mid-conversation can act on
  a fact only an *earlier* turn established, and returns only its result — the
  parent's later turns never contain the child's intermediate work.
- **Goal check:** `goals/skill-fork/inherits-history-to-fork-point/` — a real-model
  two-turn `fsdev run` (or `run.mts`) modeled on `goals/chat-harness/holds-a-conversation`.
  Turn 1 states a held-out fact (e.g. a codename) that the fork input never
  repeats. Turn 2 the model forks a research/echo skill.
  - **Signal (PASS):** the fork tool's result references the turn-1 fact (proving
    the child inherited history); and the parent's turn-3 **LLM `history()`**
    contains **none** of the child's intermediate items (proving isolation); and
    only the fork result item carries the child's answer to the parent.
  - **Anti-game:** the fork `input` must not contain the fact, so the child can
    only have it from inherited history; grade only the fork result segment, and
    assert the child's item count in the parent's next-turn **`history()`** is zero
    — not mere "something returned." **Assert isolation against `history()` (and the
    default-rendered conversation), NOT the raw `useSession().items`** (Codex P2):
    the fork child is `{ client: true, history: false }`, so its items are
    *deliberately* client-visible and still flow through `useSession().items` (only
    the default renderer hides `history:false` sub-agent items unless
    `showSubAgents`). Asserting their absence from `useSession` would false-fail a
    correct implementation or wrongly push fork output to be client-invisible.

## 8. Non-Goals

- **No harness, no session-global `activeSkills` bag.** Fork stays a per-generator
  tool (design-notes Direction B).
- **Not folding fork into the delegation capability** — that is FIX-918 (Shape-1
  delegation). Fork stays inline-authored via a `context: fork` skill.
- **Not cloning the host's exact resolved model or every sibling capability** —
  option (b) narrower clone (see §3, Decision 2). The host's resolved config is
  unreachable from a capability tool; adding a framework seam for it is explicitly
  out of scope.
- **No history summarization / compaction primitive** — bounding is whole-turn
  windowing via `MessageLimit` only. Prefix summarization (OpenAI's
  `nest_handoff_history` shape) is a possible future enhancement, not built now.
- **No sub-turn / mid-tool-call fork point** — the fork point is turn-granular by
  construction; sub-turn forking would reintroduce the dangling-tool-call hazard.
- **Final deletion of the session-global `runSkill` router** is FIX-918's, not
  this spec's. FIX-919 removes only the fork route.
- **`agent-ref` / workforce fork** — `materializeAgent` does not honor
  `contextMode: "fork"` today (`apps/docs/docs/orchestration/agents.md` documents
  this); extending fork to workforce agents is out of scope, and that page stays
  accurate.
- **Deepening opportunity (flag, not scope):** the fork generator, the fork tool,
  and `worker-materializer` all build near-identical sub-agent generators with
  overlapping option shapes. Once FIX-918 lands, there may be a single
  "sub-agent-generator" factory worth consolidating — follow up via
  `fsd:improve-codebase-architecture`, not here.

## 11. Open Questions

1. **Fork preset name.** `fork` (chosen, symmetric with `dynamicActivation`) vs.
   `forkActivation`. Recommendation: `fork`. Low-stakes; confirm at implementation.
2. **Default `forkHistoryLimit`.** The spec now sets `DEFAULT_FORK_HISTORY = { turns: 10 }`
   (conservative) so the tracer bullet and §11 agree and no expensive default ships
   by accident (Codex P2). Rationale: `undefined` = full visible window is honest
   but expensive per fork on long sessions (uncached prefix), and is itself capped
   by the engine's implicit `historyWindow`. **Owner call to confirm:** keep
   `{ turns: 10 }` (recommended) or use `undefined` (inherit everything to here).
   Reversible, low-stakes to flip.
3. **Child's default model.** The host's resolved model is unreachable; proposal is
   a library `forkModelId` defaulting to a sensible chat preset. Confirm the
   default id against the app's model presets at implementation.
4. **History-exclusion mechanism.** Engine guard (skip `in_progress` `tool_output`
   in `itemToLLMMessages` — chosen, general, no callId plumbing) vs. a fork-local
   custom `history` fn that drops the fork call by `callId`. The guard is preferred
   unless it proves unsafe for the retry/resume replay path (§ History exclusion).

**Resolved during review (Codex/Cursor spec PR #840):** the in-flight fork call is
**not** excluded by construction — an engine-level history-exclusion is required
(Q4, §3/§4). An explicit `0` history limit must be preserved (`!== undefined`
guard). `allowed` is **required** (non-empty) when `fork: true` rather than
defaulting to the full catalog. Fork dispatch is an **extracted private helper**,
not a new public `createForkSkillTool` export. The `fork` preset also installs a
catalog context formatter for model discoverability.
