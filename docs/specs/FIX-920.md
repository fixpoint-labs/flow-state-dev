# FIX-920: Re-introduce fork-like sub-execution via a task context-supply mode — Implementation Spec

> **Repo copy (canonical).** Mirrors the Linear document; kept in sync (BP-037).
> The Linear issue states *what* and *why*; this states *how*.

> **Necessity check (Step 3.5): Build as scoped — with the optional `fork: true`
> sugar deliberately dropped.** The core `conversation` context-supply mode is
> load-bearing: it closes a gap that has no user-space workaround on the
> *delegation* path (a materialized agent cannot inherit conversation history
> today; the mechanism is prototype-only), and it composes with framework
> features — agent materialization, the delegation surface, `itemVisibility`
> — a hand-written generator can't reach. The issue's own open question ("do we
> even need first-class fork ergonomics, or is delegating a task with
> `conversation` context enough on its own?") is answered here: **the mode is
> enough.** A separate `fork: true` boolean is not built (§3.6 KD4, §11 Q1). See
> §3.4 for the full gate reasoning.

## 1. TLDR

**Plain-language summary.** When an agent hands a piece of work to a sub-worker,
that worker normally starts fresh — it sees only the specific task it was given,
not the conversation that led up to it. Sometimes that's wrong: the worker needs
to know what was already discussed, but you still don't want its noisy
back-and-forth cluttering the main agent's memory afterward. That combination —
"remember everything up to now, do a lot of work, hand back only the answer" — is
what people mean by "forking" a conversation. The old skills system had a
special "fork mode" for it; we removed that (it made a skill declare *how* it
runs). This change brings the capability back the right way: as one setting on a
delegated agent that says "inherit the conversation so far." The agent's own
steps still stay out of the main agent's history, so the main context window
stays lean. There's no new tool and no new concept to learn — you mark an agent
as conversation-inheriting, and delegating to it is the same board assignment it
already is.

**One-sentence technical statement.** Add a `conversation` context-supply mode to
delegated agents — a materialized agent declared `contextSupply: "conversation"`
gets the generator `history` slot wired to `ctx.session.items.history()`
(whole-turn bounded) so it inherits the parent conversation up to dispatch, while
its output keeps `itemVisibility: { history: false }` so the sub-execution never
re-enters the host's LLM history — realized as an `AgentSpec` field + decoupled
`context-supply:` sub-key on `agents:` frontmatter honored in `materializeWorker`,
orthogonal to (not folded into) the `TaskFlowPolicy` observation-ledger seam.

**The solution in plain terms.** *(the shape of the change, if you don't want the deep-dive)*
- **What we gain.** Fork-like sub-execution returns without a fork primitive: a
  declared agent can inherit the parent conversation and still hand back only
  its result, keeping the host context window lean. It slots onto the delegation
  surface FIX-918 already ships (board-commanded agents), so it needs no new tool
  and no new skill mode — the thing the wider skills redesign was trying to get
  away from.
- **Where the work sits.** Almost entirely rewiring: every primitive already
  exists on `main` (the generator history slot, whole-turn bounding, output
  isolation). The genuinely new code is one field threaded through a few layers
  (agent spec → frontmatter parser + serializer → materializer) plus the one
  line that actually sets the history slot. No new subsystem.
- **Where the complexity actually is.** Not the happy path. It's the boundary
  question — "up to the dispatch point" has no exact sub-turn cut in the engine
  today; an agent running as a board worker inherits whole completed turns plus
  the in-flight items emitted before it ran. Pinning down that this is correct
  enough (and that output isolation genuinely holds under real runs) is the
  subtle part.
- **The risk.** That the sub-worker's steps leak into host history anyway, or
  that inheriting the whole conversation floods a small agent with irrelevant
  context. Both are caught: the first by an item-visibility assertion in the
  goal check (a real `fsdev run`, inspecting the NDJSON trace), the second by
  making the mode strictly opt-in per agent and documenting when *not* to use
  it.

## 2. Overview

Linear issue: [FIX-920](https://linear.app/fixpoint-labs/issue/FIX-920/re-introduce-fork-like-sub-execution-via-a-task-context-supply-mode).

"Fork" — running a unit of work in isolation so it doesn't bloat the host's
context window — is delegation with a particular context-supply policy, not a
skill mode. FIX-918 removes `context: fork` as a skill mode (and deletes the
`skillFork` generator) and delivers delegation as a **board-commanded** surface:
the executive generator gets the `taskTools` (the board ledger) plus `runBoard`,
and each declared agent materializes into a board worker. This issue
re-introduces the *context-window-preserving* half of fork that FIX-918
explicitly deferred: a delegated agent that **inherits the parent conversation
history up to the dispatch point**, does its work, and returns only its result —
its own steps never re-entering host history. The mechanism (the generator
`history` slot + `itemVisibility: { history: false }` output isolation) already
exists on `main`; this change wires it into the materialized-agent path and gives
it a name.

## 3. Background & Research

### 3.1 What FIX-918 leaves for this issue

FIX-918 (merged, PR #854) collapses `SkillContextMode`, deletes
`fork-generator.ts` (`createSkillForkGenerator`), and ships the **board-commanded
delegation surface** on `createSkillsLibrary` (`delegation-surface.ts`). Its §3.1
decomposes fork's value into three parts and states which land where:

1. **Isolation** (sub-work hidden from parent history) — delivered by FIX-918:
   board workers emit at `itemVisibility: { client: true, history: false }`
   (`worker-materializer.ts:156`).
2. **Fresh-context single-shot ergonomics** ("hand this goal to a sub-agent, get
   the result back") — delivered by FIX-918 as **board-commanded delegation**,
   not a per-agent tool. There is no `delegate` tool and no per-agent
   "worker-tool": the executive gets `taskTools` + `runBoard`
   (`delegation-surface.ts:12-25`), assigns work with `addTask({ assignee: <agent> })`,
   and executes the whole graph with a single `runBoard` call (a real
   `taskBoard(...).drain` over its own-state board). The board returns the
   settled results — that *is* the one-call "run it and hand me the answer" path.
3. **Context-window-preserving inheritance** (a child that sees the prior
   conversation) — **deferred to this issue.**

So the only genuinely-missing capability after FIX-918 is part 3. FIX-920 does
**not** re-add a fork tool, a fork skill mode, or a single-shot delegation path —
those either exist (parts 1–2) or were deliberately removed. It adds the
conversation-inheritance lever on top of FIX-918's board-commanded agent surface.

### 3.2 What exists on `main` today (code-verified)

Every primitive this change needs is already present; only the *wiring* into the
materialized agent is missing.

- **The generator `history` slot** — `packages/core/src/blocks/generator.ts`.
  `history?: GeneratorHistoryConfig` (`generator.ts:500`), where
  `GeneratorHistoryConfig = true | ItemQuery | GeneratorSlot`
  (`generator.ts:269-272`). `history: true` normalizes to `(_i, ctx) =>
  ctx.session.items.history()` (`normalizeHistorySlot`, `generator.ts:640-657`);
  an `ItemQuery` object becomes `ctx.session.items.history(query)`. Resolved once
  at assembly time (`generator.ts:2804`) and placed between the system prefix and
  the user message (`message-assembly.ts:97-101`). `normalizeHistorySlot(undefined)`
  returns `undefined`, so "no slot" is the natural isolated default.
- **`ctx.session.items.history()`** — `packages/core/src/types/scope.ts:75-96`;
  implemented by `loadLLMHistory` (`packages/engine/src/context/history.ts:330-368`).
  Returns `Promise<LLMMessage[]>`, walking prior *completed* turns
  (`RequestRecord`s) plus the live in-flight items of the current request.
- **Whole-turn bounding** — `MessageLimit = number | { tokens } | { turns }`
  (`scope.ts:62`); one `RequestRecord` = one turn; turns are never split
  (`selectRequestsByLimit`, `history.ts:243-301`). The default history window is
  50 turns (`createExecutionContext.ts:513`).
- **Output isolation via `history: false`** — `resolveItemVisibility`
  (`packages/contracts/src/items/resolve-visibility.ts:40-48`); an item resolving
  to `history: false` produces **zero** LLM messages (`itemToLLMMessages`,
  `history.ts:74-77`) — applied on both the completed-turn path *and* the live
  in-flight path (`expandRequestToMessages`, `history.ts:206`). A generator
  declaring `itemVisibility: { client: true, history: false }` stamps that on
  every conversational item it emits, so its output streams to the client but
  never re-enters the parent's LLM history.
- **The worker materializer** — `materializeWorker` (`worker-materializer.ts:94`)
  builds a `generator({ ..., itemVisibility: spec.itemVisibility ?? { client:
  true, history: false }, ... })` for prompt/promptRef agents (the
  `generator({...})` call is `worker-materializer.ts:154-166`; the `itemVisibility`
  default is `:156`). It has **no `history` slot** — this is the exact gap
  FIX-920 fills. (FIX-918 keeps and reuses this function; the authoring entity is
  now an `AgentSpec`, but the runtime it builds is still a board worker.)

**The prototype was never on `main`.** The `skillFork` generator
(`fork-generator.ts`) that PR #844 was to extend also has no `history` slot — it
only isolates its *own* output. PR #844's history-inheriting fork child is
prototype-only; the branch is deleted. So FIX-920 reconstructs the mechanism from
the shipped primitives, not from #844's code, and lands it on the
FIX-918 agent path rather than the deleted fork generator.

### 3.3 The load-bearing correction: `conversation` is NOT a `TaskFlowPolicy` arm

The issue's framing — "the task system already has a context-supply seam
(`TaskFlowPolicy` → `priorWork`)… extend that seam with a conversation-history
source" — rests on an assumption the code contradicts. The observation ledger
that `TaskFlowPolicy` selects from holds **only tool-call tuples**
(`Observation = { toolName, args, result?, error?, cached, ts, … }`,
`flow-policy/index.ts:32-51`) — never conversation messages. Every policy
(`none`/`declaredDepsOnly`/`ancestors`/`recentTrajectory`/`allCompleted`/
`compact`/`custom`, `flow-policy/index.ts:441-449`) filters `Observation[]` and
stamps `TaskPriorWork.observations` onto the worker input. Conversation history
is a different kind of data living in a different place (the session item stream,
reached via the generator `history` slot).

Therefore `conversation` cannot be "just another `flowPolicy.*` arm." It is a
**sibling lever** to flow-policy on the same conceptual context-supply axis:

| Lever | Source | Mechanism | What it supplies |
| --- | --- | --- | --- |
| Flow policy (`priorWork`) | per-run observation ledger | `TaskFlowPolicy.select` → worker input | prior *tool-call observations* |
| **Context supply (`conversation`)** | session item stream | generator `history` slot | prior *conversation messages* |

Modeling `conversation` as a history-slot concern (kept out of `TaskFlowPolicy`)
is the cleanest fit and matches the code reality. The two levers compose in
principle ("inherit conversation **and** get declared-dep observations"), but
note the pre-existing gap in §8 (materialized prompt-agents ignore `priorWork`
today — orthogonal, out of scope).

### 3.4 Necessity check (Step 3.5) — full reasoning

1. **Existing user-space primitive.** A user hand-writing a generator can already
   set `history: true` + `itemVisibility: { history: false }` to get fork
   behavior today (~2 lines). So for *hand-written* generators, nothing new is
   needed.
2. **What the mode adds over that.** The gap is on the *delegation / materialized-
   agent* path: an agent declared as portable skill data (`agents:` frontmatter)
   or installed by the delegation surface is built by `materializeWorker`, which
   exposes **no** history slot. A skill author cannot make a declared agent
   fork-like from user space — the materializer doesn't forward it. FIX-920 wires
   it, so the capability composes with agent materialization, the delegation
   surface, and SKILL.md portability. That is framework-level composition, not a
   wrapper (strong case).
3. **Precedent transfers.** The generator `history` slot is the exact mechanism
   generators already use to inherit conversation; `itemVisibility: { history:
   false }` is the exact isolation FIX-918's board workers already rely on. Same
   semantics, no new primitive.
4. **No single-vendor knowledge.** Conversation history is provider-agnostic
   framework state; no provider guard, no vendor enum.
5. **Path-of-least-resistance destination.** The next similar asks —
   "inherit last N turns," "inherit but strip tool output" — extend the *same*
   `contextSupply` surface (or its history-slot bounding), exactly the
   `input_filter` evolution OpenAI's Agents SDK went through. Designing
   `conversation` as one point on a context-supply continuum (not a bespoke fork
   object) keeps that path clean.
6. **Where the gate cuts scope.** The `fork: true` boolean sugar the issue floats
   is a redundant alias: `contextSupply: "conversation"` on an agent is *already*
   the one-liner (declare it once, assign it a task, drain the board — the
   board-commanded path from FIX-918). A second name for the same thing is
   speculative surface (BP-038). The issue pre-authorizes dropping it ("implement
   only if we decide the ergonomic is worth it"); the decision here is **not
   worth it** (§3.6 KD4).

**Verdict: Build as scoped**, dropping the optional `fork: true` sugar.

### 3.5 Industry precedent

The chosen shape matches how mature frameworks handle sub-agent context, and the
research sharpened three design calls:

- **Inheritance is a point on a context-supply continuum, not a bespoke primitive.**
  OpenAI's Agents SDK models full-history inheritance via a tunable `input_filter`
  on handoffs (and `RunConfig.nest_handoff_history` to collapse the transcript),
  not a boolean mode. LangGraph models it as subgraph state-schema overlap.
  The frameworks that hard-coded inheritance as a *default* (AutoGen inherit-all,
  CrewAI summarize-all) are the ones users complain about, precisely because
  there's no knob. This validates modeling `conversation` as one selectable mode.
- **Opt-in, never default.** Anthropic's multi-agent research system hands
  subagents a *curated brief*, not the transcript, and pays ~15× tokens only when
  the task value justifies it. Claude Code's Task tool defaults to fresh context;
  the community request for a `fork_context: true` flag
  ([anthropics/claude-code#16153](https://github.com/anthropics/claude-code/issues/16153))
  is explicitly argued as *opt-in* to avoid anchoring bias and context rot.
  FIX-920's default is `isolated`; `conversation` is opt-in per agent.
- **Full inheritance has real costs.** Context rot (every one of 18 frontier
  models degrades as input grows), context distraction (~100k tokens, per the
  Gemini team), and context poisoning are documented failure modes of inheriting
  irrelevant history. The docs page (§9) states plainly *when not to* fork.
- **The novel-ish cell.** Every framework couples "context inheritance" with "who
  owns the final answer": full-history inheritance usually rides on a *handoff*
  (child takes over), while delegation where the parent keeps control defaults to
  fresh context. FIX-920 combines *parent-keeps-control* with *full-history
  inheritance* — deliberate, and worth naming in the docs.

### 3.6 Key Decisions & Ramifications (top 5)

1. **`conversation` is a history-slot lever, kept out of `TaskFlowPolicy`.**
   Rejected: adding a `flowPolicy.conversation()` arm or widening `TaskPriorWork`
   with a `messages` field. **Ramification:** `TaskFlowPolicy`/`priorWork` stays
   exactly what it is (observation selection); the change is surgical and touches
   no policy code. Locks in that the two context-supply levers are separate
   surfaces — a future "unified context-supply config" would have to reconcile
   them, which we accept as a later concern. Corrects the issue's original "extend
   the seam" mental model (§3.3).
2. **The mode lives on the *agent* (`AgentSpec`), not the task.** Rejected:
   a per-task/`taskSchema` or per-`addTask`-call field. **Ramification:** an
   agent's context needs are declared once and stable; you don't thread a mode
   through every dispatch, and the calling LLM doesn't decide inheritance per
   `addTask` (which would be an odd task arg). If an agent must sometimes fork and
   sometimes not, you declare two agents (assignment-by-key, the existing FSD
   model). Rules out per-dispatch override without a follow-up.
3. **Wire the history slot in `materializeWorker`; keep output `history: false`.**
   Rejected: a bespoke fork generator (the deleted `skillFork` shape).
   **Ramification:** the mode applies to the agents `materializeWorker` builds a
   generator for — **prompt/promptRef only in v1**; `agentRef` agents own their
   own context (they resolve through the workforce `materialize-agent.ts`) and are
   rejected at parse time (§4.4), with agentRef threading deferred (§8). For the
   in-scope agents the isolation guarantee is preserved by construction (output
   visibility is independent of the inherited history slot). The subtle part is
   proving no leak (§4.4, §7).
4. **No `fork: true` sugar; a distinctly-named `contextSupply: "conversation"`
   is the surface.** Rejected: (a) a boolean `fork` alias flipping a task
   default; (b) reusing the name `contextMode` (which already means the collapsing
   `SkillContextMode` on `Skill`/`SkillState` in the *same file* —
   `skill.ts:87`/`:138` — **and** the workforce agent-level `contextMode: "fork"`
   on `Agent` in `materialize-agent.ts:107` — a three-way collision).
   **Ramification:** one capability, one clearly-named field, no redundant surface
   (BP-038); answers the issue's open question. If real ergonomic pain appears
   later, a thin `fork` alias is trivial to add — but it is not built now.
5. **"Up to the dispatch point" = `history: true` semantics (whole completed
   turns + in-flight items so far), not an exact sub-turn cut.** Rejected:
   engineering a new sub-turn boundary in `loadLLMHistory`. **Ramification:** an
   agent run as a board worker inherits everything up to the moment it runs, which
   *is* the dispatch point for serial assignment; because the board drains at
   `concurrency: 4` (`delegation-surface.ts:71`), concurrent sibling board workers
   in the same turn could have their already-emitted output included. Accepted for
   v1 (bounded, isolated, good-enough); an exact fork-point cut is a documented
   non-goal (§8).

## 4. Technical Design

### 4.1 Architecture

Two packages, one field, one consumption point:

- `@flow-state-dev/core` — `AgentSpec` gains `contextSupply`
  (`packages/core/src/types/skill.ts`).
- `@flow-state-dev/orchestration` — `materializeWorker` honors it
  (`worker-materializer.ts`); the `agents:` frontmatter parser (`parseAgentSpec`)
  **and** serializer (`serializeAgents`) in `skill-md.ts` accept/emit
  `context-supply:` (building on FIX-918's `agents:` parser — see §10).

No change to `TaskFlowPolicy`, the task board, the delegation surface's structure
(it already materializes agents into board workers via `materializeWorker`, so it
inherits the field for free), or `runBoard`.

### 4.2 API surface

**`AgentSpec` (new field):**

```ts
export interface AgentSpec {
  // ...existing fields (prompt / promptRef / agentRef / agentOverrides /
  //    tools / itemVisibility / model)...

  /**
   * How much prior context the materialized agent inherits.
   * - "isolated" (default): the agent sees only its task input — today's
   *   behavior. No conversation history slot.
   * - "conversation": the agent inherits the parent conversation history up
   *   to the point it was dispatched (the fork point), then diverges. Its own
   *   steps still stay out of the host's history (output stays
   *   `itemVisibility.history: false`), so the host context window is preserved.
   *
   * This is an INPUT policy only — it controls what the agent reads (the
   * generator `history` slot). It is unrelated to the output axis
   * (`itemVisibility.history`) and to flow-policy / `priorWork` (tool-call
   * observations). Named `contextSupply` (not `contextMode`) to avoid colliding
   * with the skill-level `SkillContextMode` in this same file and the workforce
   * agent-level `contextMode`.
   */
  contextSupply?: "isolated" | "conversation";
}
```

Note: FIX-918 removed `blockRef` from the agent surface — an `AgentSpec` resolves
via `prompt` / `promptRef` / `agentRef` only ("There is no `blockRef`",
`skill.ts:53`). So `contextSupply` interacts with exactly three resolution shapes,
and the only rejection case is `agentRef` (§4.4).

**SKILL.md `agents:` frontmatter (portable skill data):**

```yaml
agents:
  researcher:
    prompt: "You research the assigned subtopic in depth."
    context-supply: conversation   # inherit the conversation so far; return only the result
```

Parser mechanics (`parseAgentSpec` in `skill-md.ts`): add `context-supply` to
`AGENT_KNOWN_KEYS` (`skill-md.ts:68`; unknown agent keys already fail loud at
`skill-md.ts:184`), then hand-map `context-supply` → `contextSupply` and validate
the value against `isolated | conversation` (mirroring how `prompt-ref` →
`promptRef` and the `model` field are handled). The enum-value guard is the only
genuinely-new parser validation. `serializeAgents` (`skill-md.ts:965`) must emit
`context-supply` so a parsed-then-serialized skill round-trips (the CI test in §7
depends on this).

### 4.3 Data flow

At dispatch (a board task assigned to the agent and drained via `runBoard`):

1. `materializeWorker(agentKey, spec, deps)` builds the agent's board-worker
   generator.
2. If `spec.contextSupply === "conversation"`, the generator is built with
   `history: true` (→ `ctx.session.items.history()` at execution). If `"isolated"`
   or absent, no `history` slot is set (today's behavior — unchanged). Nested
   board workers share the executive's `ctx.request`/`ctx.session`
   (`task-board/index.ts:205`), so `ctx.session.items.history()` reaches the
   parent conversation.
3. Output `itemVisibility` stays `spec.itemVisibility ?? { client: true, history:
   false }` (`worker-materializer.ts:156`) **regardless of `contextSupply`** —
   inheritance (input) and isolation (output) are independent axes.
4. On execution, the generator resolves its history slot once at assembly time
   (`generator.ts:2804`), inheriting whole completed turns + the in-flight items
   emitted before it ran. Its own emitted items carry `history: false`, so they
   never re-enter the host's assembled history.

### 4.4 The `materializeWorker` change (the one consumption point)

`worker-materializer.ts` prompt/promptRef branch (the `generator({...})` call at
`154-166`) gains a conditional `history` slot:

```ts
return generator({
  name: `skillWorker_${deps.skillName}_${agentKey}`,
  itemVisibility: spec.itemVisibility ?? { client: true, history: false },
  ...(spec.contextSupply === "conversation" ? { history: true } : {}),
  agentName: `skill-${deps.skillName}-${agentKey}`,
  inputSchema: workerInputSchema,
  outputSchema: z.string(),
  model: modelId,
  prompt: substituted,
  user: (input: WorkerInput) => buildUserMessage(input),
  tools,
  maxIterations: 12,
  ...(usesTaskTools ? { uses: [taskToolsCap] as const } : {}),
}) as unknown as BlockDefinition;
```

**Isolation is preserved by construction.** The `history` slot governs what the
agent *reads*; `itemVisibility` governs what the agent's output *contributes*.
They never interact — a `conversation` agent reads the parent history and writes
`history: false` output (validator-confirmed: `resolveItemVisibility` keys only on
item type + `itemVisibility`, applied on both the completed-turn and live
in-flight paths). This is the property §7's goal check proves against a real run
rather than assuming.

**agentRef agents — fail loud, don't silently ignore.** `contextSupply` is only
honorable for agents the materializer *builds the generator for*, i.e.
`prompt`/`promptRef`. An `agentRef` agent resolves through the workforce
`materialize-agent.ts` (which has its own currently-no-op agent-level
`contextMode`, `materialize-agent.ts:107`), so `contextSupply` cannot be applied
by `materializeWorker`. Rather than accept-and-ignore (a silent no-op on a field
that reads universal — an author would think they forked when they didn't),
**reject `contextSupply` on an `agentRef` agent with an explicit "context-supply
applies to prompt/promptRef agents; agent-ref agents own their own context"
error.** (`blockRef` needs no handling — it no longer exists on `AgentSpec`;
FIX-918 already fails loud on a `block-ref` frontmatter key at `skill-md.ts:165`.)

**Validate in two places, not just the parser.** `AgentSpec` and
`materializeWorker` are exported, and a persisted `PatternBinding` is only
shallowly revalidated before factories call the materializer — so not every
`AgentSpec` flows through `parseAgentSpec`. A programmatic or persisted
`{ agentRef, contextSupply: "conversation" }` would bypass the frontmatter guard
and hit the early `agentRef` branch in `materializeWorker`, silently dropping the
field. Put the fail-loud check **both** in `parseAgentSpec` (early authoring
feedback) **and** in `materializeWorker` before its branch dispatch (the seam
that actually builds — or declines to build — the generator). The materializer is
the authoritative guard; the parser one is the ergonomic early-warning.

The materializer guard covers **two** failure modes, not just the agentRef one:
(a) `contextSupply` set on an `agentRef` agent → reject; (b) `contextSupply` set
to a value outside `"isolated" | "conversation"` on any agent → reject. Without
(b), a persisted/programmatic typo (`"converstaion"`) would fall through the
`=== "conversation"` check and silently run *isolated* — the exact
silent-wrong-behavior this fail-loud policy exists to prevent. The prompt-branch
mapping is then strictly `contextSupply === "conversation" → history: true`, on
an already-validated value.

Threading `contextSupply` through `materializeAgent` so `agentRef` agents can
fork too is the documented follow-up (§8) — cheap, since the agent-level
`contextMode` already exists (as a no-op) there.

### 4.5 Usage example

**Before** (no way to make a declared agent inherit conversation):

```yaml
agents:
  summarizer: { prompt: "Summarize the discussion into a brief." }
```

The `summarizer` agent only ever saw its task input — it could not reference
what the user and host agent already discussed.

**After** (opt into conversation inheritance):

```yaml
agents:
  summarizer:
    prompt: "Summarize the discussion into a brief."
    context-supply: conversation
```

```ts
// FIX-918's delegation surface gives the executive `taskTools` + `runBoard`.
// The executive assigns the work as a board task and drains once:
//   addTask({ assignee: "summarizer", input: "focus on the API decisions" })
//   runBoard()
// -> the summarizer board worker sees the prior conversation, produces a brief,
//    and only that brief re-enters the host's history. Its own reasoning does not.
```

Hand-written equivalent (already possible today, shown for contrast — this is the
mechanism the mode packages for declared agents):

```ts
const forked = generator({
  model: "openai/gpt-5.4-mini",
  itemVisibility: { client: true, history: false }, // its steps stay out of host history
  history: true,                                     // inherits the conversation so far
  prompt: "…",
});
```

### 4.6 State management

No new state. The mode reads the existing session item stream (via the history
slot) and writes nothing to task/board state. `TaskFlowPolicy`, the observation
ledger, and the task board are untouched.

### 4.7 Error handling

- **`context-supply:` on an `agentRef` agent:** fails loud — in
  `parseAgentSpec` (frontmatter authoring) **and** in `materializeWorker` before
  branch dispatch (the authoritative guard for programmatic/persisted specs that
  bypass the parser; §4.4). `context-supply` applies only to prompt/promptRef
  agents. Never a silent no-op.
- **`contextSupply: "conversation"` + an explicit `itemVisibility: { history:
  true }` on the same agent:** the combination defeats the point (the agent's
  steps would re-enter host history). Allowed, but `materializeWorker` emits a
  one-time warning at build ("contextSupply: conversation with history-visible
  output re-enters host history; the sub-work is no longer isolated"). Not a hard
  error — an author may genuinely want a visible sub-agent — but it should not be
  silent.
- **Unknown `context-supply:` value in frontmatter:** the parser fails loud at
  parse time (consistent with the existing enum-validated frontmatter fields),
  never silently defaulting to `isolated`.
- **`conversation` agent in a context with no prior history** (first turn, empty
  session): `ctx.session.items.history()` returns `[]`; the agent runs with just
  its task input — a graceful no-op, not an error.

## 6. Edge Cases & Error Handling

| Case | Expected behavior |
| --- | --- |
| `contextSupply` absent | `isolated` — today's behavior exactly (no history slot). Backward compatible. |
| `conversation` agent, empty session (first turn) | History resolves to `[]`; agent runs on task input only. No error. |
| `conversation` agent's own steps | Emitted at `itemVisibility.history: false` → excluded from host LLM history (`itemToLLMMessages` returns `[]`, on both completed-turn and live paths). Only the agent's returned result re-enters host history. |
| `conversation` + explicit `itemVisibility: { history: true }` on the spec | Author override wins for output; the agent's steps WOULD re-enter host history. Allowed, but `materializeWorker` emits a one-time build-time warning (§4.7) — not silent. |
| Agent runs as a board worker inside the parent's in-flight turn | Inherits completed turns + live items emitted so far (nested board workers share the executive's `ctx.request`/`ctx.session`, `task-board/index.ts:205`). No self-inclusion — history resolves once before the worker emits, and its own `history:false` items would be filtered anyway. The parent's still-pending assignment is handled by `trimOrphanedToolMessages`. |
| Concurrent sibling board workers in the same in-flight turn | The board drains at `concurrency: 4` (`delegation-surface.ts:71`); live in-flight items are appended whole (`loadLLMHistory` has no dispatch-point cut), so a concurrent sibling's already-emitted output could be inherited. Accepted for v1 (§3.6 KD5); documented. |
| `agentRef` agent + `context-supply` | Rejected fail-loud in both `parseAgentSpec` and `materializeWorker` (§4.4) — workforce agents own their history slot. Covers programmatic/persisted specs that skip the parser. agentRef alignment (threading through `materializeAgent`) is a follow-up (§8). |
| Very long conversation inherited into a small agent | Bounded by the 50-turn default history window; author can narrow later (future `conversation` bounding). Docs warn about context rot / when not to fork. |
| Stale persisted agent specs | `contextSupply` is additive and optional; absence reads as `isolated`. No migration of persisted skill state needed (BP-030). |

## 7. Testing Strategy

**Goal (observable outcome):** a delegated agent declared `context-supply:
conversation`, assigned a board task and drained via `runBoard`, can answer using
a fact that appears **only** in the parent conversation (never in its task input)
— while its own intermediate steps never appear in the host generator's
subsequent LLM history. That is the whole point: inheritance in, isolation out.

**Goal check (real path, run by hand, not CI):** `fsdev run` a small flow (added
under `apps/kitchen-sink` or a `goals/` entry — see `goals/README.md`) with:

1. A host generator bound to a skill declaring one `conversation` agent, with the
   FIX-918 delegation surface (`taskTools` + `runBoard`) active.
2. A scripted parent conversation that establishes a fact (e.g. "the project
   codename is Aurora") in an earlier turn, then asks the host to `addTask({
   assignee: <the conversation agent> })` a task whose input text does **not**
   repeat the fact, followed by a single `runBoard`.
3. Inspect the NDJSON trace and assert PASS/FAIL on: (a) the agent's assembled
   prompt contains the inherited conversation history, and its output references
   the fact — proving it inherited the conversation; (b) the agent's own
   reasoning/message items carry `itemVisibility.history: false` and do **not**
   appear in the host's assembled history on the following step — proving
   isolation (output isolation) held; (c) only the agent's returned result
   re-entered host history.

This is the real-model proof of the *answer quality*; a mocked test can't prove a
model actually used the inherited fact. (No exemption applies — there is an
observable runtime outcome.)

**CI integration test (deterministic, required — not just units).** The unit
behaviors below prove the wiring pieces in isolation, but the load-bearing
invariant spans the whole board-commanded delegation path — host generator
`addTask` → `runBoard` drain → materialized board worker → session-history replay
→ the worker's assembled prompt → the worker's items filtered back out of host
history. Per AGENTS.md, that end-to-end path must be exercised in CI with a
**mocked model** (a `testFlow`/integration scenario using `mockGenerator`), so CI
fails if the delegation wiring stops supplying history — not only when someone
remembers to run `fsdev run`. The scenario: a host generator with one
`conversation` agent, a scripted prior turn carrying a fact, one
`addTask({ assignee: <agent> })` then one `runBoard`; assert (a) the agent's
assembled prompt contains the inherited history messages and (b) the agent's own
emitted items are absent from the host's next-step assembled history (output
isolation). The hand-run `fsdev run` goal check above stays as supplemental
real-model evidence, not the only proof.

**Discipline:** `fsd:tdd` (feature) — red-green-refactor, tracer-bullet slices.

**Behaviors to test (CI, mocked/deterministic):**

1. `materializeWorker` with `contextSupply: "conversation"` builds a generator
   whose config has a `history` slot; with `"isolated"`/absent, it has none.
2. Output `itemVisibility` stays `{ client: true, history: false }` for both
   modes (inheritance doesn't change output isolation).
3. `skill-md.ts` round-trips `context-supply: conversation` (parse → serialize →
   parse) → `AgentSpec.contextSupply`; unknown values fail loud; absent →
   `undefined` (reads as isolated).
4. A `conversation` agent whose history-slot resolves against a stubbed
   `ctx.session.items.history()` receives those messages in its assembled prompt
   (assert via `mockGenerator` / the message-assembly seam).
5. `itemToLLMMessages` on a `history: false` agent item returns `[]` (regression
   guard on the isolation invariant, if not already covered). Where cheap, also
   assert the agent's returned *result* (its `tool_output`) DOES re-enter host
   history while its `agentName`-scoped internal items do not — the one slice of
   "isolation out" the mocked tests can otherwise leave to the real run.
6. `materializeWorker` fails loud on parser-bypassed specs: `contextSupply` on an
   `agentRef` agent throws (agentRef rejection), and an out-of-enum value on a
   prompt agent (`"converstaion"`) throws rather than silently running isolated.

**Existing test patterns to follow:** `worker-materializer` tests in
`packages/orchestration/test/skills/`; history-assembly tests around
`packages/engine/src/context/history.ts`; `fsd:write-block-tests` for the
mock-context idiom.

## 8. Non-Goals

- **A separate `fork: true` boolean / task-default flip.** `contextSupply:
  "conversation"` on an agent is the surface (§3.6 KD4, §11 Q1).
- **Per-task / per-`addTask`-call context-supply override.** The mode is
  agent-level; declare distinct agents if you need both behaviors (§3.6 KD2).
- **Folding `conversation` into `TaskFlowPolicy` / the observation ledger.** Kept
  a separate lever (§3.3, KD1).
- **Exact sub-turn "dispatch-point" cut in `loadLLMHistory`.** v1 uses whole-turn
  + live-items-so-far semantics (§3.6 KD5). An exact fork-point boundary is a
  future refinement.
- **Wiring `priorWork` (observations) into materialized prompt-agents.** Agent
  research surfaced that `materializeWorker`'s `buildUserMessage`/`workerInputSchema`
  ignore `priorWork` today (only custom `blockRef`-style app blocks read it, and
  those are now *tools*, not agents). That is a **pre-existing gap**, orthogonal to
  conversation inheritance, and out of scope here — flagged as a follow-up (below).
- **Honoring the workforce agent-level `contextMode`.** `materialize-agent.ts`
  has a `contextMode: "fork"` on `Agent` that currently warns/no-ops
  (`materialize-agent.ts:107`). FIX-918 leaves agent-level fork untouched;
  FIX-920 scopes to the orchestration agent path. Aligning the workforce agent
  surface to the same mechanism (making its `contextMode` real) is a cheap
  follow-up since the mechanism is identical — but a `contextMode` that silently
  no-ops is a trap worth naming.
- **Deepening opportunities flagged (follow up via `fsd:improve-codebase-architecture`):**
  - The two context-supply levers (flow-policy `priorWork`, history-slot
    `conversation`) are conceptually one axis expressed in two unrelated
    surfaces. A future unified "context-supply config" on the agent/board could
    subsume both; not attempted here.
  - `materializeWorker` prompt-agents ignoring `priorWork` (above) — the
    consumption seam (`buildUserMessage`) is the place to close it.
  - `loadLLMHistory` has no per-request memoization: multiple `conversation`
    agents in one turn each re-expand session history independently (CPU, not a
    store N+1). Harmless at current scale; a memoized per-request history view is
    a cheap future optimization if `conversation` agents become common.
