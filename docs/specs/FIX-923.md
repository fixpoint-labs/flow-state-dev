# FIX-923: Research — delegation host model (manager/IC separation + on-demand vs pre-defined agents) — Research Spec

> **This is a research / decision spec, not a build spec.** FIX-923 is a spike whose
> deliverable is a *recommendation* on the delegation host model. Part I is the human
> decision surface (the recommendation and why). Part II is the grounded analysis and
> the concrete implications the recommendation hands to the issues it feeds
> (FIX-641, FIX-924, FIX-918's surface, FIX-922). No production code ships from this
> spec; a tiny throwaway prototype is optional (see §12).

---

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

When a skill delegates work today, two things are fixed at authoring time: **who can
do work** (a closed roster declared under `agents:`) and **who coordinates vs. who
executes** (the coordinating host generator is *not* itself a worker — coordinator and
worker pool are disjoint). That forces every delegation to pre-declare every agent it
might ever dispatch to, and it makes self-assignment a fail-late error: an undeclared
or self `assignee` is accepted at task creation and then throws at dispatch.

Two linked questions fall out, and they are really one design decision:

1. **Manager vs. IC** — should the coordinating host also execute tasks itself, or stay
   a pure coordinator?
2. **On-demand vs. pre-defined agents** — must every agent be declared up front, or can
   the host dispatch to an agent it *describes at dispatch time* (the way Claude Code
   spins up a general-purpose sub-agent from just a task description), with declared
   agents becoming an optional specialization layer rather than the cost of entry?

Why now: this spike **blocks FIX-641** (Dynamic worker identities), which is the concrete
implementation of Q2's ad-hoc path. FIX-641 can't be shaped until we decide *whether*
and *in what form* on-demand agents exist. It also has to reconcile with **FIX-924**
(roster-aware assignment validation), which currently wants to reject unknown
assignees — the exact opposite of what on-demand delegation needs.

### 2. Solution in plain terms — the recommendation

**Q1 (manager/IC): the host is coordinator *and* synthesizer, and does cheap work
inline — but we do not build a "host-as-worker" routing slot.** The host generator
already owns the final turn: it plans, calls `runBoard`, and then continues its own
generation with the drained results. That *is* the "manager that also produces the
final answer" posture (OpenAI's agents-as-tools shape). Trivial, tightly-coupled,
in-context steps the host just does inline in its own loop; heavy, parallelizable,
context-isolable work it delegates to fresh-context workers. Manager/IC is a **default
posture, not a wired constraint** — and specifically **not** a self-assignment route
back into the host (rejected; see §3).

**Q2 (on-demand): yes to on-demand, delivered in two sequenced layers.**

- **Floor (do first, minimal): a uniform general-purpose fallback worker.** Wire the
  `keyedRouter`'s already-existing-but-unused `fallback` so an unassigned / general
  task runs a single general-purpose worker instead of throwing. This is the smallest
  possible change (the substrate already supports both halves), needs **zero new public
  surface**, and matches Claude Code's built-in general-purpose fallback. It is
  opt-in (delegation is gated on a skill declaring `agents:`; zero-declared-agent
  delegation needs an explicit opt-in — see §6, Decision 4).
- **Specialization layer (FIX-641): a per-task ad-hoc agent/identity spec.**
  `addTask({ goal, assignee?, identity?: { name, role, tools?, model? } })` materializes
  a per-task worker via the *existing* `worker-materializer` machinery. Declared
  `agents:` stay as the reusable, named customization layer. This is exactly FIX-641's
  `runtime-bound personas of a worker class` — this spec confirms that direction and
  the class+identity shape (not pure-ad-hoc, not uniform-only).

**The philosophy that led here.** This leans hardest on **tenet 2 (composition over
features)** and **tenet 3 (earn every addition)**: the floor is a one-argument change
that activates a parameter the substrate already carries, and the specialization layer
reuses `worker-materializer` rather than adding a parallel path. It also leans on
**tenet 5 (fix at the owning layer)**: the "self-assignment fails at dispatch" smell is
cured at the substrate (the router gets a fallback; the host is never a route), not
worked around per skill. The one tension: adding on-demand dispatch sits against
tenet 3's "default answer is no" — resolved because the *floor* costs almost nothing and
the *specialization* is FIX-641's already-planned surface, not new accretion.

### 3. Tradeoffs & alternatives

- **Rejected for Q1 — host-as-worker registered slot (a self-assigned task routes back
  into a fork of the host's own loop).** This is machinery we don't need: the host
  already synthesizes in its own turn, so "IC work" is just work the host does inline,
  not a task it dispatches to itself. A self-route adds a registry entry, a recursion
  boundary, and a new failure mode for no capability we lack. Rejected on tenet 3.
- **The simpler approach for Q2 — uniform-fallback-only, never build the ad-hoc spec.**
  Genuinely sufficient as a *floor*, and we ship it first. Insufficient as the whole
  answer because every ad-hoc task then gets the *same* fixed persona/tools/model — no
  per-task specialization, which is the entire point of FIX-641's dynamic identities.
  So: floor now, specialization via FIX-641.
- **Rejected — pure ad-hoc with no declared roster.** Throws away reproducibility,
  roster validation, and centralized tracing (the documented strengths of the
  pre-defined camp: CrewAI / AG2 / LangGraph / OpenAI-SDK). Declared agents stay; they
  just stop being the *cost of entry*.
- **Where the genuine complexity is.** Not the happy path (the floor is one line). It's
  (a) the **defaults** for an undescribed worker — model, toolset, prompt — and (b) the
  **over-spawning guard**: the documented failure mode of on-demand is token blow-up
  (Anthropic saw a lead spawn 50 subagents for a trivial query; multi-agent ≈ 15× chat
  tokens). Both are called out as decisions/open questions, not hand-waved.

### 4. Focus practices (1–5)

1. **Refine the substrate, don't accrete (tenet 2).** The floor must be the
   `keyedRouter` fallback that already exists — resist adding a second dispatch path.
2. **Subtract as you go (tenet 3 / BP-038).** On-demand delegation supersedes the
   fail-late "unknown assignee throws" behavior — the throw for a *bare general task*
   goes away; it is not left beside the fallback.
3. **Tolerate the old shape at the boundary (BP-030).** `addTask` gains an optional
   `identity`/ad-hoc field; existing declared-roster boards must materialize
   byte-identically (the field is absent → today's path).
4. **Prove the goal, not the mock (tenet 7).** Any prototype validates the *real* drain
   (a board with zero declared agents dispatches an unassigned task to the fallback and
   the host synthesizes the result), not a mocked router.

### 5. What using it looks like

The change is to the *delegation surface*, so this shows the delegating author's calls.

**Floor — zero declared agents, general task runs instead of erroring:**

```ts
// A skill opts into general-purpose delegation (no `agents:` roster required).
// Host plans a general task with no assignee:
addTask({ goal: "Summarize the three uploaded contracts and flag unusual clauses" });
runBoard();
// Today: the router throws (no assignee, registry supplied) → task errored.
// Proposed: routes to the general-purpose fallback worker → completes; host synthesizes.
```

**Specialization (FIX-641) — per-task ad-hoc identity, no pre-declaration:**

```ts
addTask({
  goal: "Draft the migration guide section on the renamed exports",
  identity: { name: "docs-writer", role: "Technical writer", tools: ["readFile"], model: "openai/gpt-5.4-mini" },
});
// Materialized per task via the existing worker-materializer; declared `agents:`
// remain available for reusable named workers.
```

**Reconciled validation (FIX-924) — a typo still fails loudly:**

```ts
addTask({ goal: "…", assignee: "resercher" }); // meant the declared "researcher"
// Rejected at creation: assignee looks like a named-agent reference but matches no
// roster key and carries no inline identity → loud fail (typo), NOT a silent ad-hoc.
```

### 6. Decisions & rules — the sign-off surface

1. **Q1: host is coordinator + synthesizer; no host-as-worker slot.**
   - *Alternative rejected:* register the host as a worker and route self-assigned tasks
     back into a fork of its loop.
   - *Ramification:* "IC work" is work the host does inline in its own turn; the host is
     never a dispatch target. Self-assignment is therefore an *invalid* assignee, not a
     supported route (feeds Decision 5 / FIX-924).
2. **Q2 floor: a uniform general-purpose fallback worker, via the existing `keyedRouter`
   `fallback`.**
   - *Alternative rejected:* keep throwing on unknown/absent assignee.
   - *Ramification:* smallest change, no new public surface; every fallback task shares
     one persona/tools/model until Decision 3 lands. This is the piece FIX-918's
     delegation surface should adopt to stop fail-late erroring.
3. **Q2 specialization: per-task ad-hoc `identity` spec on `addTask`, materialized via
   the existing `worker-materializer`; this is FIX-641's shape (class + runtime
   identity), not pure-ad-hoc and not uniform-only.**
   - *Alternative rejected:* pure ad-hoc with no declared roster; or uniform-only forever.
   - *Ramification:* declared `agents:` become the optional reusable customization layer,
     not the cost of entry. FIX-641 owns the build; its current framing (which references
     the removed pattern-skill surface — `packages/skills`, `WorkerSpec`,
     `agent-ref`/FIX-450 dispatch) must be refreshed onto the `agents:` /
     `@flow-state-dev/orchestration` model before it's actionable.
4. **Zero-declared-agent delegation requires an explicit opt-in.**
   - *Alternative rejected:* auto-install the delegation surface whenever a fallback
     could apply.
   - *Ramification:* delegation stays gated (today: presence of `agents:`); a general-
     purpose-only skill needs a deliberate flag, so no skill silently gains a task board.
5. **FIX-924's validation rule narrows: reject a *typo'd named-agent reference*, allow an
   *explicit ad-hoc / general* dispatch.**
   - *Alternative rejected:* reject every undeclared assignee at creation (FIX-924's
     current wording), which would forbid on-demand entirely.
   - *Ramification:* the rule becomes: a bare `assignee` string that matches no roster key
     and carries no inline `identity` → reject at creation (typo); no assignee / explicit
     general → route to fallback; inline `identity` → materialize per task. FIX-924's
     wording is updated alongside whichever Q2 pieces land.
6. **Defaults and an over-spawning guard are load-bearing, not incidental.**
   - *Alternative rejected:* ship the fallback with an implicit model/toolset and no cap.
   - *Ramification:* the undescribed worker's model follows the materializer's existing
     resolution (`spec.model ?? defaultModelId ?? "intent/chat"`) with a defined default
     toolset; a roster-size / concurrency cap on the drain guards the documented token-
     blow-up failure mode. Exact cap shape is an open question for FIX-641/FIX-924 (§12).

**Non-goals.** No production code in this spec; no change to `runBoard` concurrency here
(only a recommendation that FIX-641 add the cap); no refresh of FIX-641's issue text
here (flagged, owned there); no new pattern in `@flow-state-dev/patterns`.

**Size estimate.** Research doc: Small. Downstream builds it authorizes: the **floor** is
Small (~1 substrate line + gating opt-in + tests); the **specialization** is Medium and
lives in **FIX-641**.

## Part II — The Findings *(grounded analysis + implications for the issues this feeds)*

> This half is dense on purpose: it is the evidence trail behind Part I's decisions and
> the concrete hand-off to FIX-641 / FIX-924 / FIX-918 / FIX-922.

### 7. Current behavior — verified against the code

Every claim below was read in the current tree (not taken from the issue on faith):

- **Closed roster, board-commanded.** A skill declares agents under `agents:`; the host
  plans with `addTask({ goal, assignee, deps, input })` and drains with `runBoard`.
  Delegation surface (own-state `delegationBoard` field, `taskTools`, `runBoard`,
  guidance) is installed **only** when a bound skill declares `agents:`
  (`packages/orchestration/src/skills/library.ts:394-396`, derived from `agents:`
  presence, force-off via `delegation: false`). → confirms Decision 4's gating premise.
- **`addTask` does not validate `assignee`.** `inputSchema` has
  `assignee: z.string().optional()`; the value is passed straight through to
  `collection.addTask` (`packages/orchestration/src/skills/task-tools-capability.ts:120-149`).
  → confirms the fail-late smell and Decision 5.
- **Dispatch is a `keyedRouter` on `task.assignee`; the host is not in the registry.**
  `buildWorkerStep` builds `utility.keyedRouter({ blocks: connectedWorkers, select: task
  => task.assignee })` and **throws** when `assignee` is undefined
  (`packages/orchestration/src/task-board/blocks/worker-step.ts:208-221`). No `fallback`
  is passed. → confirms Decisions 1 and 2.
- **`keyedRouter` already accepts a `fallback` for unknown keys**, and routes to it
  instead of throwing (`packages/core/src/utility/keyed-router.ts:28-71`). The task-board
  simply never passes one. → **this single omission is the floor (Decision 2).**
- **Uniform-worker path already exists.** `isUniformWorker` +
  `worker.connectInput(...)` accept a *single* block that handles every task regardless
  of assignee (`worker-step.ts:54-58, 191-195`). The FIX-918 surface only ever passes the
  registry. → the fallback worker is the uniform block wired as `keyedRouter.fallback`.
- **Materialize-from-spec already exists.** `materializeWorker` builds a board worker from
  exactly `{ prompt, tools?, model? }`, with model resolution
  `spec.model ?? deps.defaultModelId ?? "intent/chat"`
  (`packages/orchestration/src/skills/worker-materializer.ts:94-167`). → an ad-hoc
  per-task worker (Decision 3) is the *same* machinery fed from a per-task spec, and the
  default-model rule in Decision 6 is the one already in this file.

**Net:** the gap is a **delegation-surface choice, not a substrate change.** Both halves
of the recommendation activate machinery that already exists.

### 8. Prior art — what the evidence actually says (cite, don't assume)

**Role separation — dominant convention is "manager coordinates, workers execute in
fresh contexts":**
- **Anthropic, multi-agent research system** — the lead *analyzes, strategizes, spawns
  subagents* and synthesizes; it does not do the subtasks. Rationale: context-window
  compression, parallelism, separation of concerns. Also documents the on-demand side
  (lead spawns 3–5 subagents dynamically from self-contained descriptions, can spawn more
  mid-run). <https://www.anthropic.com/engineering/built-multi-agent-research-system>
- **Anthropic, Building Effective Agents** — orchestrator-workers: *a central LLM
  dynamically breaks down tasks, delegates to workers, synthesizes; subtasks aren't
  pre-defined.* Start simple, add multi-agent only when needed.
  <https://www.anthropic.com/research/building-effective-agents>
- **CrewAI hierarchical / AutoGen-AG2 `GroupChatManager` / LangGraph supervisor** — all
  separate coordinator from workers, all require agents **pre-registered**. (CrewAI's
  separation is documented intent, reportedly unreliable in practice.)

**Deliberate counterexample (manager also does integrative work):**
- **OpenAI Agents SDK, agents-as-tools** — *a manager agent keeps control of the
  conversation and calls specialists*; use when *you want one agent to own the final
  answer, combine outputs.* → separation is a best-practice **default, not a hard
  constraint**. This is the posture FSD's host already occupies (it owns the turn and
  synthesizes), which is why Q1's answer is "coordinator + synthesizer, inline IC work"
  rather than a separation mandate. <https://openai.github.io/openai-agents-python/multi_agent/>

**On-demand vs pre-defined — a genuine fork:**
- **Ad-hoc:** Anthropic research system + **Claude Code sub-agents** — built-in
  general-purpose / Explore / Plan need no definition; a custom `.claude/agents/*.md` is
  *optional* (adds persona, tool constraint, pinned model, description-based
  auto-selection); dispatch falls back to general-purpose when nothing matches; the main
  agent is **both manager and IC**. <https://code.claude.com/docs/en/sub-agents>
- **Pre-defined:** CrewAI / AG2 / LangGraph / OpenAI-SDK — registration buys
  reproducibility, roster validation, centralized tracing.
- **Tradeoff cost of on-demand:** over-spawning / token blow-up (Anthropic: a lead once
  spawned 50 subagents for a simple query; multi-agent ≈ 15× chat tokens). → Decision 6's
  cap.

**"Don't decompose" camp (keep it one agent):**
- **Cognition, Don't Build Multi-Agents** — parallel workers under conflicting, unshared
  assumptions produce fragmented results a coordinator can't repair; prefer a
  single-threaded agent with continuous context. <https://cognition.com/blog/dont-build-multi-agents>
- **Anthropic, when NOT to** — sequential phases of the same work share too much context;
  tightly-coupled components belong in the same agent; splitting by problem-type causes a
  telephone game. <https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them>
- **Cross-camp consensus:** start single-agent; keep tightly-coupled plan→implement→test
  of one unit in **one** context; reserve fresh-context delegation for
  **parallelizable, context-isolable** work; give workers scoped self-contained
  descriptions and let the host synthesize. → this is exactly Q1's "host does trivial
  in-context work inline, delegates isolable work" rule.

### 10. Edge cases the downstream builds must handle

| Case | Expected behavior |
| --- | --- |
| No assignee, no roster, opt-in on | Route to general-purpose fallback worker; complete; host synthesizes. |
| No assignee, no roster, opt-in **off** | Today's behavior preserved (delegation surface not installed / task errors). No silent board. |
| Bare `assignee` matching a roster key | Unchanged: keyed dispatch to the declared worker. |
| Bare `assignee` matching **no** roster key, no `identity` | Reject at creation (typo) — Decision 5. |
| Inline `identity` present (FIX-641) | Materialize a per-task worker from the spec; ignore/override any bare `assignee`. |
| Self-assignment (host names itself) | Invalid assignee — Decision 1; the host is never a route. Rejected like any unknown key (unless it carries an explicit `identity`, which makes it an ordinary ad-hoc worker, not "the host"). |
| Runaway planning (many ad-hoc tasks) | Roster-size / concurrency cap on the drain trips (Decision 6); exact shape is FIX-641/FIX-924's to settle. |
| Existing declared-roster board, new field absent | Materializes byte-identically to today (BP-030). |

### 12. Dependencies, open questions & follow-ups

**Dependencies.** This spike has no hard blockers. It **blocks FIX-641**. Relates to
FIX-918 (Done, PR #854), FIX-922, FIX-924.

**Open questions (for the builds, not blocking this spec's conclusions):**
1. **Fallback worker defaults** — exact default toolset for an undescribed general-purpose
   worker (model default already resolved by the materializer). Owned by the floor PR.
2. **Over-spawning cap shape** — roster-size cap, concurrency cap, or both, and where it
   lives (`runBoard` vs. the delegation surface). Owned by FIX-641/FIX-924.
3. **Opt-in flag shape** — how a skill opts into zero-declared-agent delegation (a
   `delegation: { generalPurpose: true }`-style flag vs. a sentinel agent entry). Owned by
   the floor PR; should reuse the existing `delegation` gating in `library.ts`.

**Optional prototype (welcome, per the issue; not required for the decision).** Wire the
`keyedRouter` fallback in a throwaway board and confirm a zero-declared-agent skill
dispatches an unassigned task to a general-purpose worker and the host synthesizes the
result — a LOGIC prototype under `apps/kitchen-sink/flows/_prototypes/` (fsd:prototype).
The decisions above do not depend on it; it de-risks the floor PR's ergonomics.
