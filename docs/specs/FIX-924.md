# FIX-924: Roster-aware task assignment: manager knows its workers; validate assignment at creation — Implementation Spec

> **Status:** spec for review (not yet implemented).
> **Related:** FIX-918 (Done — delegation via capability + blocks-as-tools; the surface this refines) · FIX-923 (active research — delegation host model; **its Q2 outcome reshapes this spec's validation rule, see §6 Decision 5 and §12**).

---

## Part I — The Case

### 1. Problem — why it matters, why now

When a skill delegates work, the model (the "manager") plans by calling `addTask` with an `assignee` naming which agent should do the work. Today that assignee is an unchecked free-form string. If the model names a worker that does not exist — a typo, a hallucinated name, or an agent from a skill that isn't loaded — nothing complains. The task is happily created, sits on the board, and only blows up much later when the board is drained: the dispatch router can't find the worker, throws, and the task is marked `errored`.

That is a fail-late smell. The error surfaces far from its cause, after the model has moved on, and the model gets a dead task instead of an immediate, correctable "that agent doesn't exist — here are the ones that do." The manager is effectively assigning blind at the moment it matters.

Why now: FIX-918 shipped the board-commanded delegation surface, so this is the surface every delegating skill now uses. Getting assignment validation right here is cheap (it's a young surface) and it's a correctness gap authors will hit as soon as they write a skill with more than one agent.

### 2. Solution in plain terms

Validate the assignee **at the moment a task is created or reassigned**, against the set of workers the board actually has. When the model calls `addTask` / `assignTask` / `updateTask` with an assignee that isn't a real worker, the tool returns immediately with `ok: false` and an error that names the bad assignee and lists the workers that *do* exist. The task is never created against a phantom worker.

The manager already learns its roster: FIX-918's delegation guidance injects a "Your agents:" list into the executive's context. So the "manager knows its workers" half of this issue is **already satisfied in context** — this spec does not add a redundant `listWorkers` tool. It closes the other half: assignment is checked against that same roster, so the two agree.

The model-facing vocabulary follows FIX-918: the guidance presents the roster as "Your agents:", so the `checkAssignee` rejection says the assignee "is not an **agent** on this board" — the error the model reads back matches the word it was given. The internal `WorkerRoster` type name (below) is unchanged; only the model-facing wording is "agent".

**Philosophy that led here:**
- **Tenet 5 (Fix at the owning layer).** The error belongs where the bad assignee *enters* the system — the `addTask` tool surface — not downstream in the dispatch router where the string finally fails to resolve. We move the check to the owning layer.
- **Tenet 1 (Coherence over local cleverness).** The board's worker registry is the single source of truth for valid assignees. Validation reads from that same roster the guidance advertises, so context, validation, and dispatch cannot disagree.
- **Tenet 3 (Earn every addition).** The roster is already in context, so no new `listWorkers` tool is added. The change threads existing information into the existing tools; it does not grow the surface.

### 3. Tradeoffs & alternatives

- **Return `ok: false` vs. throw.** The task tools already speak a `{ ok: false, error }` contract (`no_delegation_board`, `task_not_found`). An unknown assignee joins that contract as `unknown_assignee`. This is the loud-and-immediate rejection the issue asks for *without* crashing the turn — a thrown error would abort the whole executive turn; a structured `ok: false` lets the model read "wrong worker, here are the real ones" and re-issue the call. Same information, recoverable.
- **Simpler approach considered — validate only in dispatch (keep today's behavior) and just improve the error message.** Rejected: it stays fail-late. The model has already planned an entire graph before the error surfaces, and a `blocked`/`errored` task is a worse signal than an inline correction.
- **Simpler approach considered — a `listWorkers` tool.** Rejected as redundant (tenet 3): the roster is already in the executive's context via `buildDelegationGuidance`. Adding a tool to fetch what's already in context is surface for its own sake.
- **Where the genuine complexity is.** Not the happy path. It's the boundary with FIX-923: on-demand agents want to *accept* an assignee that isn't in the declared roster (an ad-hoc worker). "Reject unknown assignee" and "allow ad-hoc dispatch" look contradictory. They reconcile (§6 Decision 5) but the validation must be written as one centralized gate so 923 can widen the definition of "valid" in one place, not scatter it.

### 4. Focus practices

1. **Fail at the owning layer, not downstream (tenet 5).** The whole point: the check lives in the task tools, not the dispatch router.
2. **One source of truth for the roster (tenet 1).** Validation, context guidance, and the board's participant registry all derive from the same worker keys. Do not build a second list.
3. **Graceful degradation preserves the standalone `taskTools` singleton (BP-030).** When no roster is supplied (the singleton used outside delegation), validation is inert — assignee is accepted as today. The new check tolerates the old, roster-less shape.
4. **Centralize the gate for FIX-923's benefit (tenet 1).** One `validateAssignee` function so 923's on-demand rule extends it in one edit.

### 5. What using it looks like

Author's skill declares a two-agent team (unchanged from FIX-918):

```yaml
# researcher.skill.md frontmatter
agents:
  researcher: { prompt-ref: ./researcher.md }
  writer: { prompt-ref: ./writer.md }
```

At runtime the manager plans. **Today** a typo is accepted and dies at drain:

```
addTask({ goal: "Find sources", assignee: "reseacher" })
  → { ok: true, taskId: "t_01" }        // accepted (typo!)
runBoard()
  → task t_01 status "errored"           // fails late, at dispatch
```

**After this change** the typo is rejected at creation, with the real roster in the message:

```
addTask({ goal: "Find sources", assignee: "reseacher" })
  → { ok: false,
      error: 'unknown_assignee: "reseacher" is not an agent on this board. Available: researcher (Researches sources and returns findings), writer (Drafts prose from findings).' }

addTask({ goal: "Find sources", assignee: "researcher" })
  → { ok: true, taskId: "t_01" }         // corrected, accepted
```

Same for `assignTask({ taskId, assignee })` and `updateTask({ taskId, patch: { assignee } })`. The standalone `taskTools` singleton (no board roster) is unaffected — it accepts any assignee as before.

### 6. Decisions & rules — the sign-off surface

1. **Validate assignee at creation/reassignment, in the task tools.** — *Rejected:* validating only at dispatch. — *Locks in:* the error surfaces at `addTask`/`assignTask`/`updateTask`, immediately and correctably.
2. **Return `{ ok: false, error: "unknown_assignee: … Available: …" }`, don't throw.** — *Rejected:* throwing (aborts the turn). — *Locks in:* recoverable, consistent with the existing `no_delegation_board`/`task_not_found` contract; no output-schema change (the roster rides in the `error` string).
3. **Roster is threaded into the task tools from the board's worker registry; no new list is built and no `listWorkers` tool is added.** — *Rejected:* a `listWorkers` tool. — *Locks in:* one source of truth (the `boardWorkers` keys); the manager already sees the roster in context.
4. **When no roster is supplied, validation is inert (accept any assignee).** — *Rejected:* always-on validation. — *Locks in:* the standalone `taskTools` singleton and any roster-less consumer keep today's behavior; only the delegation surface, which knows its workers, validates.
5. **The rule is "reject an assignee that is not a declared worker," implemented as one centralized `validateAssignee` gate — and it is contingent on FIX-923.** — *Rejected:* hardcoding the check inline in each tool. — *Locks in / carries forward:* if FIX-923 adopts on-demand agents, "valid" widens to "a declared worker **or** an explicit ad-hoc dispatch shape" (a bare unknown *string* stays invalid — that's the typo case; an explicit inline `agent` spec or the uniform-fallback path becomes valid). The reviewer must reconcile this at the approval gate; see §12.

**Non-goals:** Does not add on-demand/ad-hoc agents (FIX-923/FIX-641). Does not change dispatch-time behavior for an *unassigned* task (assignee `undefined`) — that fail-late path is left to FIX-923's fallback decision. Does not add a `listWorkers` tool.

**Size estimate:** Small (2 source files + tests, <150 LOC).

## Part II — The Build Plan

### 7. Technical design

**Packages/files involved (all in `@flow-state-dev/orchestration`):**
- `packages/orchestration/src/skills/task-tools-capability.ts` — the eight task tools. Add a roster parameter and the validation gate.
- `packages/orchestration/src/skills/delegation-surface.ts` — builds `boardWorkers`; construct the roster and pass it into the two task-tool constructors.
- Tests: the existing test file for the task-tools module, plus a delegation-surface test.

**New type — the roster contract (in `task-tools-capability.ts`):**

```ts
/**
 * The set of workers a delegation board can assign to, plus a human-readable
 * description for error messages. Passed into the task tools so assignment is
 * validated against the board's real participant registry.
 */
export interface WorkerRoster {
  /** True when `assignee` names a declared worker on this board. */
  has(assignee: string): boolean;
  /** Roster rendered for an error message, e.g. `researcher (…), writer (…)`. */
  describe(): string;
}
```

**Validation helper (module-private in `task-tools-capability.ts`):**

```ts
const unknownAssigneeError = (assignee: string, roster: WorkerRoster) => ({
  ok: false as const,
  error:
    `unknown_assignee: "${assignee}" is not an agent on this board. ` +
    `Available: ${roster.describe()}.`,
});

/** Returns an error object when the assignee is invalid, else undefined. */
function checkAssignee(
  assignee: string | undefined,
  roster: WorkerRoster | undefined,
): { ok: false; error: string } | undefined {
  if (roster === undefined || assignee === undefined) return undefined;
  if (roster.has(assignee)) return undefined;
  return unknownAssigneeError(assignee, roster);
}
```

`checkAssignee` is the **single gate** referenced by Decision 5 — the one place FIX-923 widens.

**Threading the roster in:**
- `buildTaskTools(resolve, roster?)` — closes over the optional roster.
- `buildTaskToolsList(resolveCollection?, roster?)` — new second param, forwarded.
- `createTaskToolsCapability(resolveCollection?, roster?)` — new second param, forwarded.

**Where the gate fires (in `buildTaskTools`):**
- `addTask.execute` — before `collection.addTask(...)`: `const bad = checkAssignee(input.assignee, roster); if (bad) return bad;`
- `assignTask.execute` — before the `withTask` mutation: check `input.assignee`.
- `updateTask.execute` — before the `withTask` mutation: check `input.patch.assignee`.

No output-schema changes: `addTask`'s output union already has `{ ok: false, error: string }`; `assignTask`/`updateTask` use `okOrError` which already carries `{ ok: false, error }`.

**Constructing the roster (in `delegation-surface.ts` `buildDelegationTools`):** the loop over `sources` already builds `boardWorkers[agentKey]`. Alongside it, accumulate `rosterDescriptions[agentKey] = agentPurpose(resolvedSpec, source.files)` (function already exported in this module). After the loop:

```ts
const rosterKeys = new Set(Object.keys(boardWorkers));
const roster: WorkerRoster = {
  has: (a) => rosterKeys.has(a),
  describe: () =>
    Object.entries(rosterDescriptions)
      .map(([k, purpose]) => `${k} (${purpose})`)
      .join(", "),
};
```

Pass it to both constructors:
- `buildTaskToolsList(defaultOwnStateResolver, roster)` at the return (currently `buildTaskToolsList()`).
- `createTaskToolsCapability(() => boardCollection(), roster)` for `boardTaskTools`, so a mid-drain fan-out agent enqueuing follow-up tasks is validated against the same roster.

Note the `defaultOwnStateResolver` is already the default first arg of `buildTaskToolsList`; pass it explicitly to supply the second arg.

### 8. Implementation sequence

1. **Add `WorkerRoster` type + `checkAssignee`/`unknownAssigneeError` helpers to `task-tools-capability.ts`.** Thread an optional `roster` param through `buildTaskTools` → `buildTaskToolsList` → `createTaskToolsCapability`. *Test:* unit — `checkAssignee` returns `undefined` for a known assignee, for `undefined` assignee, and for `undefined` roster; returns the error object (with the assignee and the roster list in the message) for an unknown assignee.
2. **Fire the gate in `addTask`, `assignTask`, `updateTask`.** *Test:* each tool returns `{ ok: false, error }` for an unknown assignee and proceeds normally for a known one; with no roster, all accept any assignee (back-compat).
3. **Build and pass the roster in `delegation-surface.ts`** for both `buildTaskToolsList` and the `boardTaskTools` capability; accumulate `rosterDescriptions` in the existing worker loop. *Test:* a delegation surface built from a two-agent skill rejects `addTask` with a typo'd assignee at creation and never reaches drain; a valid assignee runs.
4. **Changeset.** Not required for the spec PR (docs-only). The *implementation* PR adds a `patch` changeset (BP-022): "delegation: reject an unknown task assignee at creation with the available roster, instead of failing late at dispatch."

### 9. Edge cases & error handling

| Case | Expected |
| --- | --- |
| `addTask` assignee is a declared worker | `{ ok: true, taskId }` (created) |
| `addTask` assignee is not a declared worker | `{ ok: false, error: "unknown_assignee: … Available: …" }`; task **not** created |
| `addTask` with no assignee (`undefined`) | Accepted (created unassigned) — unassigned fail-late is out of scope, see §12 |
| `assignTask` / `updateTask` to an unknown worker | `{ ok: false, error }`; task unchanged |
| Roster-less consumer (standalone `taskTools` singleton) | Any assignee accepted (validation inert) — BP-030 tolerate the old shape |
| Board with zero workers | `buildDelegationTools` already returns `[]` (no tools built); gate never runs |
| Two skills share an agent key (deduped in `boardWorkers`) | Roster has one entry for that key; validation matches it |
| Case/whitespace mismatch (`"Researcher"` vs `researcher`) | Rejected — exact-match only; keys are declared literals |

Error taxonomy: `unknown_assignee` is a **recoverable** tool result (the model re-issues with a valid assignee), never a thrown/fatal error. Second-path checklist (BP-035): legacy/roster-less path tested (inert); no null-boundary beyond the `assignee === undefined` guard; no concurrency/tenancy surface touched.

### 10. Testing strategy

- **Goal check:** No full real-model goal check required — the observable outcome is a deterministic tool return at the `taskTools` boundary, better proven by CI specs than a live model. (Optional manual sanity: `fsdev run` a delegation flow and confirm a bad assignee returns `unknown_assignee`.) Justification: this is a correctness change on a tool return value, deterministic and mockable.
- **CI specs (vitest, deterministic):** the behaviours in §8 steps 1–3 — the gate helper in isolation, each of the three tools with/without a roster, and the delegation-surface integration (typo rejected at creation, valid assignee runs). Assert the error message contains both the bad assignee and the roster keys.
- **Discipline:** `fsd:tdd` (this is an enhancement to a surface, not a bug hunt) — red-green at the tool boundary. Seam: vitest against `buildTaskToolsList(resolver, roster)` and `buildDelegationTools`.

### 12. Dependencies, open questions & follow-ups

**Dependencies:** None blocking. Builds directly on FIX-918 (Done). No open PR touches `task-tools-capability.ts` or `delegation-surface.ts` at spec time (verify at implementation start).

**Open question — the FIX-923 coupling (must be reconciled at the spec-approval gate):**
FIX-923's own description flags this tension explicitly (its "Tension to resolve with FIX-924" section). FIX-924 as specced rejects any assignee not in the declared roster. FIX-923 is researching on-demand agents, where the manager dispatches to a worker it did *not* pre-declare:
- **923 Option 1 (uniform-fallback worker):** unknown/unassigned tasks route to a general-purpose fallback instead of erroring. If adopted, an unknown *string* assignee arguably should still be rejected (it's a typo), but an *unassigned* task becomes valid (the fallback handles it).
- **923 Option 2 (per-task inline `agent` spec):** `addTask({ agent: { prompt, tools? } })` is an explicit ad-hoc dispatch. If adopted, "valid" widens to "a declared worker **or** an explicit `agent` spec"; a bare unknown assignee string stays invalid.

**This spec's stance:** the fail-at-creation *principle* is correct regardless of 923 (the issue was split out precisely because it holds independent of the research). The *definition of a valid assignee* is what 923 may widen. The design isolates that definition in one `checkAssignee` gate (Decision 5) so the 923 outcome is a one-function edit, not a scatter. **Reviewer action at the approval gate:** confirm whether to ship 924's strict "declared-worker-only" rule now (and let 923 relax it later) or hold 924 until 923's Q2 lands. Recommended: ship now — strict validation is the correct default, and relaxing it is a clean follow-up when on-demand agents arrive. FIX-641 (Dynamic worker identities) is the downstream implementation of 923's on-demand path and would consume the widened gate.
