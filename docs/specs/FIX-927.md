# FIX-927: Delegation — agent-ref agents can't carry board-scoped taskTools for mid-drain fan-out — Implementation Spec

> **Epic:** [FIX-930 — Delegation substrate](./_epics/delegation-substrate.md) · epic PR #873 (`epic approved`).
> This issue is one of the epic's "delegation plumbing bugs underneath" and moves **independently** of the keystone work — it is not blocked by FIX-923 and does not touch the host model.

---

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

When a delegation skill lets one of its workers enqueue follow-up work *while the board is draining*, that only works today if the worker is defined **inline** (its prompt written directly in the skill's `agents:` block). If the same worker is instead a **registered agent** the skill points at by name (an `agent-ref`), its attempts to enqueue tasks silently fail — they land on the wrong (empty) board and come back with `no_delegation_board` during the drain.

**Why now.** The board-commanded delegation model shipped in FIX-918, and its worked examples happen to do mid-drain fan-out with an *inline* agent, so the gap is currently invisible. But `agent-ref` is a first-class way to declare a worker (it's how a skill reuses a registered persona), and the moment someone points a fan-out worker at a registered agent it breaks with a confusing error. It's a real asymmetry between two declaration styles that should behave identically. The fix was deliberately deferred out of FIX-918 / PR #854 (it's a small cross-package public-type change) and is tracked here.

### 2. Solution in plain terms

Make the `agent-ref` worker path do what the inline path already does: hand the worker the **board-scoped** `taskTools` (the eight `addTask`/…/`listTasks` tools bound to the *active drain board*) instead of the process-wide singleton that looks at nothing.

Concretely, the board-bound capability already exists — the delegation surface builds `boardTaskTools` and threads it to inline workers today. This change carries that same capability across the one seam it currently stops at: the `materializeAgent` call that turns a registered agent into a worker. We add an optional `boardTaskTools` field to that call's options (defined in `core`), have `workforce` prefer it over the singleton when present, and have the skills materializer pass it through on the `agent-ref` branch — exactly mirroring the inline branch.

A registered agent can declare `taskTools` **two** ways — `allowedTools: ["taskTools"]` (resolved from the tool catalog) or `usesCapabilities: ["taskTools"]` (resolved from the capability catalog). Both are valid, and both are broken today for mid-drain fan-out: the first resolves the non-board singleton, and the second resolves whatever `"taskTools"` is registered in the capability catalog — never `opts.boardTaskTools`. So `workforce` must prefer the board-bound capability **regardless of which declaration path the agent used**, normalizing both to one board-aware seam inside `materializeAgent`. Fixing only the first path would leave `usesCapabilities` agents still hitting `no_delegation_board` — a half-fix for a valid declaration style.

**Philosophy that led here.** This leans on **tenet 1 (coherence)**: two ways of declaring the same worker should resolve `taskTools` the same way; the current split is an incoherence, not a feature. And **tenet 2 (few, flexible primitives)**: we thread one already-existing capability through an existing options object rather than adding any new concept — the board-scoped taskTools primitive already exists, it just wasn't reaching this one caller.

### 3. Tradeoffs & alternatives

- **Main alternative — resolve the board inside the singleton capability** (make `taskToolsCapability` itself find the active board via context). Rejected: the board lives on the host generator's own block state and is reached by *closure*, not by context walking (see `delegation-surface.ts` — `boardTaskTools` closes over `boardCollection()`). Making the singleton context-aware would be a much larger, more speculative change to how the capability resolves its collection, for no benefit over passing the already-built board-bound capability through.
- **Simpler approach considered** — do nothing / document the limitation ("use inline agents for fan-out workers"). Rejected: it bakes a surprising asymmetry into the public surface and turns a one-field threading fix into a permanent footgun with a `no_delegation_board` error as the only signal.
- **Where the genuine complexity is** — mostly threading, with one real care point beyond the boundary. The **package boundary**: `MaterializeAgentOptions` lives in `core` (not `workforce`) precisely so `orchestration` can type the injected `materializeAgent` without importing `workforce`; the new field must be added in `core` and consumed in `workforce`, keeping that boundary intact. The **second care point** (added when scope widened to two declaration paths): the two ways an agent can declare `taskTools` — `allowedTools`/`tools` (tool catalog) and `usesCapabilities` (capability catalog) — resolve through *different* code in `materializeAgent`. The board override must land on both without double-adding the capability, so the `workforce` change is a small normalization of taskTools resolution, not a one-line coalescing expression. That is the one spot in this fix that needs care.

### 4. Focus practices

- **BP-034 (finish move/rename refactors) / coherence (tenet 1).** The inline and `agent-ref` paths are two halves of one behavior. The fix isn't done until both resolve `taskTools` identically — mirror the inline branch exactly, don't invent a parallel mechanism.
- **Package boundary (core ← workforce ← orchestration).** The option type is added in `core`; `workforce` consumes it; `orchestration` passes it. No new cross-package import may be introduced (`orchestration` must still not import `workforce`).
- **BP-003 (verification evidence).** The bug is invisible to today's tests because every fan-out example uses an inline agent. The regression test must use an **`agent-ref`** worker carrying `taskTools` and assert it enqueues onto the *active* board during a drain — the exact shape that's broken today.

### 5. What using it looks like

No public authoring surface changes — a skill author writes their `agents:` roster exactly as before. The change is that an `agent-ref` worker carrying `taskTools` now *works* where it silently failed. Illustratively, given a registered agent used as a fan-out worker:

```ts
// A skill roster that points at a registered agent by name, where that agent
// carries taskTools so it can enqueue follow-up work mid-drain:
agents: {
  discoverer: { agentRef: "competitor-scout" },   // registered agent, tools include "taskTools"
}
// Before: during runBoard drain, discoverer.addTask(...) -> { error: "no_delegation_board" }
// After:  discoverer.addTask(...) lands on the active drain board; the drain picks up the new task.
```

The only *code-level* surface change is one new optional field on an internal materialization options type (`MaterializeAgentOptions.boardTaskTools`), which is framework-internal plumbing, not an end-user API. Fuller worked wiring will live in the spec PR rather than the doc.

### 6. Decisions & rules — the sign-off surface

1. **Thread the existing board-bound capability; do not make the singleton context-aware.**
   - *Alternative rejected:* teaching `taskToolsCapability` to discover the active board from context.
   - *Ramification:* the fix stays a small threading change; board resolution remains closure-based, consistent with how inline workers already get it.

2. **Add `boardTaskTools?: DefinedCapability` to `MaterializeAgentOptions` in `core`.**
   - *Alternative rejected:* defining the field in `workforce` (where it's consumed).
   - *Ramification:* preserves the boundary that lets `orchestration` type `materializeAgent` without importing `workforce`. `core`'s public type surface gains one optional field.

3. **`workforce` prefers `opts.boardTaskTools` over the singleton whenever the agent declares `taskTools` — by *either* declaration path (`allowedTools`/`tools` or `usesCapabilities`) — falling back to the singleton when no override is supplied.**
   - *Alternative rejected:* fixing only the `allowedTools` path and deferring `usesCapabilities` (the original draft's non-goal). Rejected on the scope widen: `usesCapabilities: ["taskTools"]` is a valid declaration style that would still hit `no_delegation_board`, leaving the bug half-fixed.
   - *Ramification:* both declaration paths converge on the board-bound capability through one seam in `materializeAgent`; standalone-shape agents and non-delegation callers keep working unchanged (no override supplied → singleton); the capability must not be double-added when an agent somehow names it on both paths.

4. **The `agent-ref` branch mirrors the inline branch exactly — pass `deps.boardTaskTools` through.**
   - *Alternative rejected:* a bespoke resolution path for agent-ref workers.
   - *Ramification:* the two declaration styles converge on one behavior; future changes to board scoping touch one shared notion.

**Non-goals:** No change to the host model, board modes, on-demand/default-worker floor, or any other epic work. No new authoring surface. No change to how inline workers already resolve taskTools. Not touching the standalone-agent (`shape: "standalone"`) path beyond the shared option default.

**Size estimate:** Small-to-moderate. Still the same three source files (`core` / `workforce` / `orchestration`), but the scope widen to cover both `taskTools` declaration paths grew the change beyond the original 3-file / "one-line coalescing, well under 100 LOC" framing: the `workforce` change now normalizes taskTools resolution across the `allowedTools` and `usesCapabilities` paths (not a single `??`), and the test surface adds a mandatory `usesCapabilities` unit case and a mandatory orchestration agent-ref integration test. Likely ~100–150 LOC including tests. Single PR — no PR-plan DAG.

## Part II — The Build Plan *(for the implementer)*

### 1. Exact files touched

Three source files, two test files. `delegation-surface.ts` is **not** touched — it already builds `boardTaskTools` and forwards it on *every* `materializeWorker` call.

| # | File | Package | Change |
| - | ---- | ------- | ------ |
| 1 | `packages/core/src/types/agent.ts` | `core` | Add one optional field to `MaterializeAgentOptions`. |
| 2 | `packages/workforce/src/materialize-agent.ts` | `workforce` | Prefer `opts.boardTaskTools` over the non-board taskTools capability when the agent declares taskTools by **either** path (`allowedTools`/`tools` **or** `usesCapabilities`), normalizing both to one board-aware seam without double-adding. |
| 3 | `packages/orchestration/src/skills/worker-materializer.ts` | `orchestration` | `agent-ref` branch forwards `deps.boardTaskTools` into the `materializeAgent` call. |
| 4 | `packages/workforce/test/materialize-agent.test.ts` | `workforce` | Unit red-green for both declaration paths + fallback (§4). |
| 5 | `packages/orchestration/test/…` (skills / delegation drain) | `orchestration` | **Mandatory** agent-ref end-to-end regression: an agent declared by ref, delegated via the board, reaches `boardTaskTools` and fans out mid-drain (§4). Not optional — a workforce-unit-only test passes while the agent-ref forwarding bug persists. |

**Why `delegation-surface.ts` needs no change (scope precision).** `delegation-surface.ts:345` already builds `const boardTaskTools = createTaskToolsCapability(() => boardCollection())` and passes `boardTaskTools` into the `materializeWorker` deps **unconditionally** (`:389`, outside any spread guard). Every worker on the drain board already receives the board-bound capability in its deps. The bug is purely that the `agent-ref` branch of `materializeWorker` drops it on the floor instead of forwarding it to `materializeAgent`. So the fix is confined to the three files above; the surface that constructs and hands over `boardTaskTools` is already correct.

### 2. The three code changes (verbatim intent)

**(1) `core` — add the option field.** In `MaterializeAgentOptions` (`packages/core/src/types/agent.ts:110`), add after `skillName?`:

```ts
  /**
   * Board-bound `taskTools` capability for a worker-shaped agent that itself
   * declares `taskTools` (mid-drain fan-out). When set, the agent's `taskTools`
   * resolve against the active drain board rather than the process-wide
   * singleton (which looks at no board). When unset, the singleton is used —
   * standalone agents and non-delegation callers are unaffected.
   */
  boardTaskTools?: DefinedCapability;
```

`DefinedCapability` is already imported in this file (`:15`), so no new import. This is the *only* new public-type surface — one optional field. Boundary intact: the type stays in `core`, so `orchestration` keeps typing the injected `materializeAgent` without importing `workforce` (Decision 2).

**(2) `workforce` — prefer the override on both declaration paths.** In `buildAgentGenerator` (`packages/workforce/src/materialize-agent.ts:86-99`), taskTools can arrive two ways, and today only the tools path is detected while the capability path resolves the non-board catalog entry:

```ts
  const toolKeys = opts.overrides?.tools ?? agent.allowedTools;
  const usesTaskTools = toolKeys?.includes("taskTools") ?? false;      // tools path only
  // …
  const resolvedUses = resolveCapabilities(
    agent.name,
    agent.usesCapabilities,           // resolves catalog["taskTools"] → non-board singleton
    opts.capabilityCatalog,
  );
  const uses = [
    ...resolvedUses,
    ...(usesTaskTools ? [taskToolsCapability] : []),                   // hardcodes the singleton
  ];
```

Normalize both paths to a single board-aware seam. Detect taskTools from `allowedTools`/`tools` **and** from `usesCapabilities`, strip any taskTools entry that `resolveCapabilities` produced (so the non-board catalog entry never slips through and the capability is never double-added), then append the board-aware capability once (Decision 3):

```ts
  const usesTaskToolsViaTools = toolKeys?.includes("taskTools") ?? false;
  const usesTaskToolsViaCaps =
    agent.usesCapabilities?.some(
      (e) =>
        e === "taskTools" ||
        (typeof e !== "string" && e.name === "taskTools"),
    ) ?? false;
  const usesTaskTools = usesTaskToolsViaTools || usesTaskToolsViaCaps;

  // Drop any taskTools capability the catalog resolved — it is re-added below
  // through the single board-aware seam, so the board override reaches the
  // `usesCapabilities` path too and taskTools is never added twice.
  const resolvedUses = resolveCapabilities(
    agent.name,
    agent.usesCapabilities,
    opts.capabilityCatalog,
  ).filter((cap) => cap.name !== "taskTools");

  const taskToolsCap = opts.boardTaskTools ?? taskToolsCapability;
  const uses = [
    ...resolvedUses,
    ...(usesTaskTools ? [taskToolsCap] : []),
  ];
```

The `catalogKeys = toolKeys?.filter((t) => t !== "taskTools")` line (`:88`) already keeps taskTools out of tool resolution, so nothing else in this function double-counts it. The identity check for the capability path uses the capability's `name === "taskTools"` (the value `createTaskToolsCapability` stamps at `task-tools-capability.ts:311`); the implementer should confirm `DefinedCapability` exposes `name` on the resolved type and, if not, match identity against the imported `taskToolsCapability` singleton instead. Both declaration paths now resolve taskTools through the one `opts.boardTaskTools ?? taskToolsCapability` expression.

**(3) `orchestration` — forward on the agent-ref branch.** In `materializeWorker` (`packages/orchestration/src/skills/worker-materializer.ts:125-133`), the `agent-ref` branch calls `deps.materializeAgent(agent, { … })`. Add one line to the options object, mirroring how the inline branch already consumes `deps.boardTaskTools` (`:146`):

```ts
    return deps.materializeAgent(agent, {
      catalog: deps.catalog,
      capabilityCatalog: deps.capabilityCatalog,
      defaultModelId: deps.defaultModelId,
      overrides: spec.agentOverrides,
      shape: "worker",
      workerKey: agentKey,
      skillName: deps.skillName,
      boardTaskTools: deps.boardTaskTools,   // ← the one-field forward (Decision 4)
    });
```

`deps.boardTaskTools` is already on `WorkerMaterializationDeps` (`:72`) and already populated by the surface (§1). This single forward is the behavioral heart of the fix.

### 3. Decisions on the review-surfaced refinements

**(a) `usesCapabilities: ["taskTools"]` secondary path — IN SCOPE (scope widen).** An agent can declare taskTools either as `allowedTools: ["taskTools"]` (tool-catalog path) or as `usesCapabilities: ["taskTools"]`. The latter is resolved by `resolveCapabilities(agent.usesCapabilities, opts.capabilityCatalog)` (`materialize-agent.ts:91-95`) against the **capability catalog** — it produces `catalog["taskTools"]` (the non-board singleton) and never touches `opts.boardTaskTools`. So an agent-ref agent declaring taskTools that way still hits `no_delegation_board` mid-drain: the original single-path fix left it half-fixed for a valid declaration style.

  - **Decision: fold both paths into this fix.** The mid-drain board taskTools must reach the worker regardless of which way it declares taskTools. The mechanism is in change (2) above: detect taskTools from `allowedTools`/`tools` **and** from `usesCapabilities`, strip the catalog-resolved taskTools entry so the non-board one can't slip through, and re-add the board-aware capability through the *one* `opts.boardTaskTools ?? taskToolsCapability` seam. This is the *more* coherent shape (tenet 1): one override point for the concept, not two — the earlier worry about "two override points" applied to the rejected approach of teaching `resolveCapabilities` to special-case the catalog key in a *separate* branch, which we do **not** do. `delegation-surface.ts` still needs no change (it already supplies `boardTaskTools`), and the `capabilityCatalog` construction is untouched — the normalization lives entirely in `materializeAgent`. Both declaration paths get a mandatory red-green test (§4).

**(b) Dev-only warn-guard — INCLUDED (cheap insurance).** `opts.boardTaskTools ?? taskToolsCapability` silently falls back to the no-board singleton. For a worker-shape agent that declares `taskTools` but whose caller forgot to supply the override, that reproduces exactly today's silent `no_delegation_board`-at-runtime failure. Add a dev-only guard in `buildAgentGenerator`, right where `usesTaskTools` is known:

```ts
  if (
    process.env.NODE_ENV !== "production" &&
    opts.shape === "worker" &&
    usesTaskTools &&
    !opts.boardTaskTools
  ) {
    console.warn(
      `[workforce] agent "${agent.name}": worker declares taskTools but no ` +
        `boardTaskTools was supplied — fan-out tools will target the empty ` +
        `singleton board (no_delegation_board at drain).`,
    );
  }
```

  - **Rationale for in:** turns a silent-at-drain failure into a materialization-time signal, at the cost of ~8 lines and zero runtime behavior change. Scoped to `shape: "worker"` so standalone agents (which legitimately have no board) never warn. Gated on `NODE_ENV` so production stays quiet. If review judges it noise, it can be dropped without affecting the fix — but it directly serves BP-035 (test/annotate the off/new state of a new flag).

**(c) `resolveTaskToolsCapability` DRY helper — DEFERRED as optional polish.** Both the inline path (`worker-materializer.ts:146`) and the workforce path (`materialize-agent.ts:98`) now express `boardTaskTools ?? taskToolsCapability`. Extracting a shared `resolveTaskToolsCapability(board?: DefinedCapability)` helper would DRY the two, but they live in different packages (`orchestration` vs `workforce`) and each imports its own `taskTools` singleton — a shared helper would need a home in `core`/`contracts` and both singletons to agree. The duplication is one trivial coalescing expression in two places.

  - **Decision: not in this PR.** The expression is too small to justify a new cross-package export; forcing it into `core` adds more surface than it removes. Left as a one-line note for a future consolidation if a third caller appears (rule of three). Does not block the fix.

### 4. Test plan (red-green)

The bug is invisible to today's suite because every fan-out example uses an inline agent. The load-bearing new test drives the **`agent-ref`** path and asserts the worker resolves the **board-scoped** capability, not the singleton.

**Unit — `workforce` (`packages/workforce/test/materialize-agent.test.ts`), the direct red-green. Tests 1 and 2 cover the two declaration paths and are both mandatory (a `usesCapabilities` agent is broken by a different line than an `allowedTools` agent):**

1. **RED → GREEN: board override reaches `uses` via `allowedTools`.** Materialize a worker-shape agent with `allowedTools: ["taskTools"]`, passing a **distinct sentinel** `boardTaskTools` capability in `opts`. Assert the built block's `uses` contains *that* capability instance, not the singleton `taskToolsCapability`. Before change 2 this fails (uses holds the singleton); after, it passes. Identity is checkable because `createTaskToolsCapability()` returns a fresh object — the sentinel is `!==` the singleton.
2. **RED → GREEN: board override reaches `uses` via `usesCapabilities` (scope widen — mandatory).** Materialize a worker-shape agent with `usesCapabilities: ["taskTools"]` and a `capabilityCatalog` whose `"taskTools"` key is the non-board singleton, passing a **distinct sentinel** `boardTaskTools` in `opts`. Assert `uses` contains the **sentinel** board capability and **not** the catalog's non-board `"taskTools"` entry, and that taskTools appears **exactly once** (no double-add). Before change 2 this fails (uses holds the catalog singleton); after, it passes. This is the path the original single-path fix left broken.
3. **Fallback unchanged (both paths).** Same agents (each declaration path), **no** `boardTaskTools` in `opts` → `uses` contains the singleton `taskToolsCapability` (Decision 3: standalone / non-delegation callers keep working). Guards against regressing the default on either path.
4. **No taskTools → no capability.** Agent without `taskTools` in either `allowedTools` or `usesCapabilities`, with `boardTaskTools` supplied → `uses` contains no taskTools capability (the override only applies when the agent actually declares taskTools).
5. **(If guard (b) included)** worker-shape + `taskTools` + no `boardTaskTools` emits the dev warn; standalone + `taskTools` + no `boardTaskTools` does **not** warn (spy on `console.warn`, assert with `NODE_ENV !== "production"`).

**Integration — `orchestration` (delegation-surface / drain), the behavioral proof the Case demands (BP-003). Mandatory — a workforce-unit-only suite passes green while the agent-ref → `worker-materializer.ts:125-133` forwarding bug persists, because the units never exercise the orchestration forward:**

6. **RED → GREEN: agent-ref worker fans out mid-drain (MANDATORY, end-to-end).** Build a delegation board whose roster points a worker at a **registered agent** by ref (`agentRef`) that carries `taskTools`, with a stub `agentRegistry` + the real `materializeAgent` injected. Run the board drain; have that worker call `addTask(...)`. Assert the new task lands on the **active drain board** and the drain picks it up — no `no_delegation_board`. This drives the full orchestration path (ref resolution → `materializeWorker` agent-ref branch forwarding `deps.boardTaskTools` → `materializeAgent` → board-bound taskTools reaching the worker), which the workforce unit cannot reach. Before changes 2+3 this fails with `no_delegation_board` (the agent-ref branch dropped `boardTaskTools`); after, the follow-up task drains. This is the exact shape broken today. Use an `allowedTools: ["taskTools"]` agent as the load-bearing case; a `usesCapabilities: ["taskTools"]` variant is covered at unit altitude by test 2.
7. **Inline path unchanged.** Existing inline-agent mid-drain fan-out test (from FIX-918) still passes untouched — proves the fix converges the declaration styles rather than perturbing the working one (tenet 1).

**Whole-suite gates:** `pnpm --filter @flow-state-dev/core typecheck` (new optional field compiles, boundary intact), `pnpm --filter @flow-state-dev/workforce test`, `pnpm --filter @flow-state-dev/orchestration test`, and `pnpm typecheck` at the root to confirm no cross-package type breakage from the `core` surface addition.

**Evidence path (BP-003):** the RED→GREEN tests — #1 (unit, `allowedTools` path), #2 (unit, `usesCapabilities` path), and #6 (mandatory integration, agent-ref end-to-end) — each fail on `main`/pre-change and pass after; captured in the PR description as the before/after. Pass criteria: agent-ref worker enqueues onto the active board mid-drain regardless of declaration path; taskTools appears exactly once; inline path and default fallback both unchanged.
