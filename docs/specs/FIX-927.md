# FIX-927: Delegation — agent-ref agents can't carry board-scoped taskTools for mid-drain fan-out — Implementation Spec

> **Epic:** [FIX-930 — Delegation substrate](./_epics/delegation-substrate.md) · epic PR #873 (`epic approved`).
> This issue is one of the epic's "delegation plumbing bugs underneath" and moves **independently** of the keystone work — it is not blocked by FIX-923 and does not touch the host model.

---

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

When a delegation skill lets one of its workers enqueue follow-up work *while the board is draining*, that only works today if the worker is defined **inline** (its prompt written directly in the skill's `agents:` block). If the same worker is instead a **registered agent** the skill points at by name (an `agent-ref`), its attempts to enqueue tasks silently fail — they land on the wrong (empty) board and come back with `no_delegation_board` during the drain.

**Why now.** The board-commanded delegation model shipped in FIX-918, and its worked examples happen to do mid-drain fan-out with an *inline* agent, so the gap is currently invisible. But `agent-ref` is a first-class way to declare a worker (it's how a skill reuses a registered persona), and the moment someone points a fan-out worker at a registered agent it breaks with a confusing error. It's a real asymmetry between two declaration styles that should behave identically. The fix was deliberately deferred out of FIX-918 / PR #854 (it's a small cross-package public-type change) and is tracked here.

### 2. Solution in plain terms

Make the `agent-ref` worker path do what the inline path already does: hand the worker the **board-scoped** `taskTools` (the eight `addTask`/…/`listTasks` tools bound to the *active drain board*) instead of the process-wide singleton that looks at nothing.

Concretely, the board-bound capability already exists — the delegation surface builds `boardTaskTools` and threads it to inline workers today. This change carries that same capability across the one seam it currently stops at: the `materializeAgent` call that turns a registered agent into a worker. We add an optional `boardTaskTools` field to that call's options (defined in `core`), have `workforce` prefer it over the singleton when present, and have the skills materializer pass it through on the `agent-ref` branch — exactly mirroring the inline branch.

**Philosophy that led here.** This leans on **tenet 1 (coherence)**: two ways of declaring the same worker should resolve `taskTools` the same way; the current split is an incoherence, not a feature. And **tenet 2 (few, flexible primitives)**: we thread one already-existing capability through an existing options object rather than adding any new concept — the board-scoped taskTools primitive already exists, it just wasn't reaching this one caller.

### 3. Tradeoffs & alternatives

- **Main alternative — resolve the board inside the singleton capability** (make `taskToolsCapability` itself find the active board via context). Rejected: the board lives on the host generator's own block state and is reached by *closure*, not by context walking (see `delegation-surface.ts` — `boardTaskTools` closes over `boardCollection()`). Making the singleton context-aware would be a much larger, more speculative change to how the capability resolves its collection, for no benefit over passing the already-built board-bound capability through.
- **Simpler approach considered** — do nothing / document the limitation ("use inline agents for fan-out workers"). Rejected: it bakes a surprising asymmetry into the public surface and turns a one-field threading fix into a permanent footgun with a `no_delegation_board` error as the only signal.
- **Where the genuine complexity is** — there isn't much; it's a threading fix. The only care point is the **package boundary**: `MaterializeAgentOptions` lives in `core` (not `workforce`) precisely so `orchestration` can type the injected `materializeAgent` without importing `workforce`. The new field must be added in `core` and consumed in `workforce`, keeping that boundary intact.

### 4. Focus practices

- **BP-034 (finish move/rename refactors) / coherence (tenet 1).** The inline and `agent-ref` paths are two halves of one behavior. The fix isn't done until both resolve `taskTools` identically — mirror the inline branch exactly, don't invent a parallel mechanism.
- **Package boundary (core ← workforce ← orchestration).** The option type is added in `core`; `workforce` consumes it; `orchestration` passes it. No new cross-package import may be introduced (`orchestration` must still not import `workforce`).
- **BP-003 (verification evidence).** The bug is invisible to today's tests because every fan-out example uses an inline agent. The regression test must use an **`agent-ref`** worker carrying `taskTools` and assert it enqueues onto the *active* board during a drain — the exact shape that's broken today.

### 5. What using it looks like

No public authoring surface changes — a skill author writes their `agents:` roster exactly as before. The change is that an `agent-ref` worker carrying `taskTools` now *works* where it silently failed. Illustratively, given a registered agent used as a fan-out worker:

```ts
// A skill roster that points at a registered agent by name, where that agent
// carries taskTools so it can enqueue follow-up work mid-drain:
agents: {
  discoverer: { agentRef: "competitor-scout" },   // registered agent, tools include "taskTools"
}
// Before: during runBoard drain, discoverer.addTask(...) -> { error: "no_delegation_board" }
// After:  discoverer.addTask(...) lands on the active drain board; the drain picks up the new task.
```

The only *code-level* surface change is one new optional field on an internal materialization options type (`MaterializeAgentOptions.boardTaskTools`), which is framework-internal plumbing, not an end-user API. Fuller worked wiring will live in the spec PR rather than the doc.

### 6. Decisions & rules — the sign-off surface

1. **Thread the existing board-bound capability; do not make the singleton context-aware.**
   - *Alternative rejected:* teaching `taskToolsCapability` to discover the active board from context.
   - *Ramification:* the fix stays a small threading change; board resolution remains closure-based, consistent with how inline workers already get it.

2. **Add `boardTaskTools?: DefinedCapability` to `MaterializeAgentOptions` in `core`.**
   - *Alternative rejected:* defining the field in `workforce` (where it's consumed).
   - *Ramification:* preserves the boundary that lets `orchestration` type `materializeAgent` without importing `workforce`. `core`'s public type surface gains one optional field.

3. **`workforce` prefers `opts.boardTaskTools` over the singleton, falling back to it when absent (`opts.boardTaskTools ?? taskToolsCapability`).**
   - *Alternative rejected:* always requiring the board capability.
   - *Ramification:* standalone-shape agents and non-delegation callers keep working unchanged; only the delegation path supplies the override.

4. **The `agent-ref` branch mirrors the inline branch exactly — pass `deps.boardTaskTools` through.**
   - *Alternative rejected:* a bespoke resolution path for agent-ref workers.
   - *Ramification:* the two declaration styles converge on one behavior; future changes to board scoping touch one shared notion.

**Non-goals:** No change to the host model, board modes, on-demand/default-worker floor, or any other epic work. No new authoring surface. No change to how inline workers already resolve taskTools. Not touching the standalone-agent (`shape: "standalone"`) path beyond the shared option default.

**Size estimate:** Small (3 files touched in `core` / `workforce` / `orchestration`, plus one regression test; well under 100 LOC). Single PR — no PR-plan DAG.

## Part II — The Build Plan *(for the implementer)*

### 1. Exact files touched

Three source files, one test file. `delegation-surface.ts` is **not** touched — it already builds `boardTaskTools` and forwards it on *every* `materializeWorker` call.

| # | File | Package | Change |
| - | ---- | ------- | ------ |
| 1 | `packages/core/src/types/agent.ts` | `core` | Add one optional field to `MaterializeAgentOptions`. |
| 2 | `packages/workforce/src/materialize-agent.ts` | `workforce` | Prefer `opts.boardTaskTools` over the singleton when composing `uses`. |
| 3 | `packages/orchestration/src/skills/worker-materializer.ts` | `orchestration` | `agent-ref` branch forwards `deps.boardTaskTools` into the `materializeAgent` call. |
| 4 | `packages/workforce/test/materialize-agent.test.ts` (+ optionally one orchestration test) | `workforce` / `orchestration` | Regression coverage (§4). |

**Why `delegation-surface.ts` needs no change (scope precision).** `delegation-surface.ts:345` already builds `const boardTaskTools = createTaskToolsCapability(() => boardCollection())` and passes `boardTaskTools` into the `materializeWorker` deps **unconditionally** (`:389`, outside any spread guard). Every worker on the drain board already receives the board-bound capability in its deps. The bug is purely that the `agent-ref` branch of `materializeWorker` drops it on the floor instead of forwarding it to `materializeAgent`. So the fix is confined to the three files above; the surface that constructs and hands over `boardTaskTools` is already correct.

### 2. The three code changes (verbatim intent)

**(1) `core` — add the option field.** In `MaterializeAgentOptions` (`packages/core/src/types/agent.ts:110`), add after `skillName?`:

```ts
  /**
   * Board-bound `taskTools` capability for a worker-shaped agent that itself
   * declares `taskTools` (mid-drain fan-out). When set, the agent's `taskTools`
   * resolve against the active drain board rather than the process-wide
   * singleton (which looks at no board). When unset, the singleton is used —
   * standalone agents and non-delegation callers are unaffected.
   */
  boardTaskTools?: DefinedCapability;
```

`DefinedCapability` is already imported in this file (`:15`), so no new import. This is the *only* new public-type surface — one optional field. Boundary intact: the type stays in `core`, so `orchestration` keeps typing the injected `materializeAgent` without importing `workforce` (Decision 2).

**(2) `workforce` — prefer the override.** In `buildAgentGenerator` (`packages/workforce/src/materialize-agent.ts:96-99`), the `uses` array currently hardcodes the singleton:

```ts
  const uses = [
    ...resolvedUses,
    ...(usesTaskTools ? [taskToolsCapability] : []),
  ];
```

Change the taskTools entry to prefer the injected board capability, falling back to the singleton when absent (Decision 3):

```ts
  const uses = [
    ...resolvedUses,
    ...(usesTaskTools ? [opts.boardTaskTools ?? taskToolsCapability] : []),
  ];
```

Note `usesTaskTools` here is derived from `toolKeys` = `opts.overrides?.tools ?? agent.allowedTools` (`:86-87`) — i.e. the **`allowedTools: ["taskTools"]`** path. See §3 for the `usesCapabilities` path.

**(3) `orchestration` — forward on the agent-ref branch.** In `materializeWorker` (`packages/orchestration/src/skills/worker-materializer.ts:125-133`), the `agent-ref` branch calls `deps.materializeAgent(agent, { … })`. Add one line to the options object, mirroring how the inline branch already consumes `deps.boardTaskTools` (`:146`):

```ts
    return deps.materializeAgent(agent, {
      catalog: deps.catalog,
      capabilityCatalog: deps.capabilityCatalog,
      defaultModelId: deps.defaultModelId,
      overrides: spec.agentOverrides,
      shape: "worker",
      workerKey: agentKey,
      skillName: deps.skillName,
      boardTaskTools: deps.boardTaskTools,   // ← the one-field forward (Decision 4)
    });
```

`deps.boardTaskTools` is already on `WorkerMaterializationDeps` (`:72`) and already populated by the surface (§1). This single forward is the behavioral heart of the fix.

### 3. Decisions on the review-surfaced refinements

**(a) `usesCapabilities: ["taskTools"]` secondary path — non-goal, documented.** The fix targets the `allowedTools: ["taskTools"]` → `usesTaskTools` path. An agent that instead declares `usesCapabilities: ["taskTools"]` is resolved by `resolveCapabilities(agent.usesCapabilities, opts.capabilityCatalog)` (`materialize-agent.ts:91-95`) against the **capability catalog**, never touching `opts.boardTaskTools`. Such an agent would still get a non-board-scoped `taskTools` and remain broken for mid-drain fan-out.

  - **Decision: out of scope for FIX-927; recorded as a known residual asymmetry.** Rationale: (i) the delegation materialization path and every worked example declare fan-out tools via `allowedTools`/`tools: ["taskTools"]`, not `usesCapabilities`; (ii) closing it means teaching `resolveCapabilities` to special-case the `"taskTools"` catalog key and swap in the board binding — a second, different mechanism that cuts against tenet-1 coherence (two override points for one concept). If a future caller needs the `usesCapabilities` route, the cleaner fix is to have the delegation surface inject `boardTaskTools` **as** the `"taskTools"` entry of the `capabilityCatalog` it already passes, so both paths resolve through one seam. Noted here so it is a deliberate deferral, not an oversight. Added to Non-goals below.

**(b) Dev-only warn-guard — INCLUDED (cheap insurance).** `opts.boardTaskTools ?? taskToolsCapability` silently falls back to the no-board singleton. For a worker-shape agent that declares `taskTools` but whose caller forgot to supply the override, that reproduces exactly today's silent `no_delegation_board`-at-runtime failure. Add a dev-only guard in `buildAgentGenerator`, right where `usesTaskTools` is known:

```ts
  if (
    process.env.NODE_ENV !== "production" &&
    opts.shape === "worker" &&
    usesTaskTools &&
    !opts.boardTaskTools
  ) {
    console.warn(
      `[workforce] agent "${agent.name}": worker declares taskTools but no ` +
        `boardTaskTools was supplied — fan-out tools will target the empty ` +
        `singleton board (no_delegation_board at drain).`,
    );
  }
```

  - **Rationale for in:** turns a silent-at-drain failure into a materialization-time signal, at the cost of ~8 lines and zero runtime behavior change. Scoped to `shape: "worker"` so standalone agents (which legitimately have no board) never warn. Gated on `NODE_ENV` so production stays quiet. If review judges it noise, it can be dropped without affecting the fix — but it directly serves BP-035 (test/annotate the off/new state of a new flag).

**(c) `resolveTaskToolsCapability` DRY helper — DEFERRED as optional polish.** Both the inline path (`worker-materializer.ts:146`) and the workforce path (`materialize-agent.ts:98`) now express `boardTaskTools ?? taskToolsCapability`. Extracting a shared `resolveTaskToolsCapability(board?: DefinedCapability)` helper would DRY the two, but they live in different packages (`orchestration` vs `workforce`) and each imports its own `taskTools` singleton — a shared helper would need a home in `core`/`contracts` and both singletons to agree. The duplication is one trivial coalescing expression in two places.

  - **Decision: not in this PR.** The expression is too small to justify a new cross-package export; forcing it into `core` adds more surface than it removes. Left as a one-line note for a future consolidation if a third caller appears (rule of three). Does not block the fix.

### 4. Test plan (red-green)

The bug is invisible to today's suite because every fan-out example uses an inline agent. The load-bearing new test drives the **`agent-ref`** path and asserts the worker resolves the **board-scoped** capability, not the singleton.

**Unit — `workforce` (`packages/workforce/test/materialize-agent.test.ts`), the direct red-green:**

1. **RED → GREEN: board override reaches `uses`.** Materialize a worker-shape agent with `allowedTools: ["taskTools"]`, passing a **distinct sentinel** `boardTaskTools` capability in `opts`. Assert the built block's `uses` contains *that* capability instance, not the singleton `taskToolsCapability`. Before change 2 this fails (uses holds the singleton); after, it passes. Identity is checkable because `createTaskToolsCapability()` returns a fresh object — the sentinel is `!==` the singleton.
2. **Fallback unchanged.** Same agent, **no** `boardTaskTools` in `opts` → `uses` contains the singleton `taskToolsCapability` (Decision 3: standalone / non-delegation callers keep working). Guards against regressing the default.
3. **No taskTools → no capability.** Agent without `taskTools` in `allowedTools`, with `boardTaskTools` supplied → `uses` contains neither taskTools capability (the override only applies when the agent actually declares taskTools).
4. **(If guard (b) included)** worker-shape + `taskTools` + no `boardTaskTools` emits the dev warn; standalone + `taskTools` + no `boardTaskTools` does **not** warn (spy on `console.warn`, assert with `NODE_ENV !== "production"`).

**Integration — `orchestration` (delegation-surface / drain), the behavioral proof the Case demands (BP-003):**

5. **RED → GREEN: agent-ref worker fans out mid-drain.** Build a delegation board whose roster points a worker at a **registered agent** (`agentRef`) that carries `taskTools`, with a stub `agentRegistry` + real `materializeAgent` injected. Run the board drain; have that worker call `addTask(...)`. Assert the new task lands on the **active drain board** and the drain picks it up — no `no_delegation_board`. Before changes 2+3 this fails with `no_delegation_board` (worker got the empty singleton); after, the follow-up task drains. This is the exact shape broken today and is the endorsed "ship as written" behavior.
6. **Inline path unchanged.** Existing inline-agent mid-drain fan-out test (from FIX-918) still passes untouched — proves the fix converges the two declaration styles rather than perturbing the working one (tenet 1).

**Whole-suite gates:** `pnpm --filter @flow-state-dev/core typecheck` (new optional field compiles, boundary intact), `pnpm --filter @flow-state-dev/workforce test`, `pnpm --filter @flow-state-dev/orchestration test`, and `pnpm typecheck` at the root to confirm no cross-package type breakage from the `core` surface addition.

**Evidence path (BP-003):** the two RED→GREEN tests (#1 unit, #5 integration) each fail on `main`/pre-change and pass after; captured in the PR description as the before/after. Pass criteria: agent-ref worker enqueues onto the active board mid-drain; inline path and default fallback both unchanged.

## Spec evolution

- **Case drafted** — framed as a coherence/threading bug: the `agent-ref` worker path doesn't hand workers the board-scoped `taskTools` the inline path already does, so mid-drain fan-out fails with `no_delegation_board`. Chosen approach threads the existing `boardTaskTools` capability through `MaterializeAgentOptions` (core → workforce → orchestration), mirroring the inline branch, rather than making the singleton capability context-aware.
- **Case endorsed ("ship as written")** and **Build Plan authored** (Part II) — pinned the exact three-file scope after reading the code: `delegation-surface.ts` needs **no** change (it already builds `boardTaskTools` at `:345` and forwards it unconditionally on every `materializeWorker` call at `:389`); the fix is `core` (add `MaterializeAgentOptions.boardTaskTools`), `workforce` (`opts.boardTaskTools ?? taskToolsCapability` in the `uses` composition), and `orchestration` (agent-ref branch forwards `deps.boardTaskTools` into `materializeAgent`). Folded in four review refinements: (1) scope precision — surface untouched; (2) the `usesCapabilities: ["taskTools"]` path is a **deliberately deferred** residual asymmetry (added to Non-goals) since it resolves via `capabilityCatalog`, not `opts.boardTaskTools`; (3) **included** a dev-only warn-guard for worker-shape agents that declare taskTools without a supplied board; (4) **deferred** the cross-package `resolveTaskToolsCapability` DRY helper as too small to justify a new `core` export. Added a red-green test plan: agent-ref worker fans out mid-drain onto the active board (integration), board override reaches `uses` + fallback unchanged (workforce unit), inline path unchanged.
