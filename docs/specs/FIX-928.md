# FIX-928: Delegation surface — memoize per-step rebuild + dedup build/runtime helpers — Implementation Spec

> **Epic:** [FIX-930 — Delegation substrate](https://linear.app/fixpoint-labs/issue/FIX-930) · epic-spec on `epic/delegation-substrate` (epic PR #873, `epic approved`). This issue is the delegation-surface polish member of that set: "the delegation-surface helpers get a memoize/dedup polish (FIX-928)." It moves independently of the FIX-923 keystone and does not change the delegation *model* — only tightens the surface FIX-918 shipped.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

FIX-918 shipped the board-commanded delegation surface: a skill declares a roster of agents, the host plans work with `addTask`, and drains it with `runBoard`. The `/simplify` review of that PR (#854) flagged a cluster of correctness-neutral rough edges on the surface it left behind — one performance waste and four small duplications. None blocks anything; they were grouped so the surface gets tightened in a single pass rather than trickled out.

The performance one has teeth on the hot path. Because the delegation tools are contributed as an async function (so a skill activated mid-turn can still join the board), the generator treats the whole tool set as *dynamic* and re-resolves it before **every** step of the tool loop. The primary delegation flow is inherently multi-step (`addTask` N times, then `runBoard`), so on each of those steps the framework **re-materializes every agent into a board worker, rebuilds the eight task-tool handlers, and reconstructs the task board and the `runBoard` sequencer from scratch** — even when the roster is unchanged. Materialization is the real cost: `materializeWorker` builds a generator per agent, resolves its persona/capabilities, and for `agent-ref`/non-bundled `prompt-ref` agents hits the agent registry or reads the skill collection (an N+1 over the roster). LLM latency dominates the wall clock, but that rebuild does real per-step allocation, re-parsing, and I/O, and it repeats as delegation adoption grows.

**Why now.** The surface is fresh, the review notes are fresh, and doing this before FIX-641 (the class+identity specialization layer that lands on top of this same surface) means that later work builds on a deduplicated, memoized base instead of forking the drift further.

### 2. Solution in plain terms

Two moves, both on the delegation surface, neither touching the delegation *model*:

- **(C) Stop re-materializing the board every step.** Materialize the delegation tools once per generator turn and reuse that result across steps, rebuilding only when the roster actually changes. What counts as "the roster changed" is the **resolved source list** — the output of the existing `collectAgentSources` pass (which agent-declaring skills are live right now, each with its `$ARGUMENTS` input and agent keys). That pass is *kept per step*: it is where the live-manifest `disable-model-invocation` read happens for every source, so re-running it every step is what keeps a disabled skill from leaking its agents (see §6, decision 2). One precondition rides with this change — FIX-918's collector skipped that disable read on a *single* path (runtime activations resolved from the bundled index), so this issue adds it there too, making "the collector drops every disabled source" true on all three paths before the snapshot relies on it (§7.1). What we cache and skip on an unchanged source list is the **expensive downstream build**: the per-agent `materializeWorker` calls, the eight task-tool handlers, the `taskBoard`, and the `runBoard` sequencer. A model activating (or disabling) a skill mid-turn changes the resolved source list, which busts the cache and triggers exactly one rebuild. The same per-turn cache also holds the guidance (roster) text, which today independently re-walks the same sources and rebuilds the same string every step.

- **(D) Collapse four small duplications into one owner each.** (1) `collectAgentSources` runs twice per step — once for the tools, once for the guidance roster — and each caller then rebuilds its artifact; route both through the shared per-turn cache from (C) so the roster is walked and built once per snapshot. (2) The skills package redefines a worker-input Zod schema (`workerInputSchema` in `worker-materializer.ts`) that is a near-copy of the substrate's `taskWorkerInputSchema` — reuse the substrate's so the two can't drift. (3) The agent-key collision logic (`deepEqual` → dedupe, then throw-or-warn) is written twice — once at build time in `library.ts`, once at runtime in `delegation-surface.ts` — extract one tiny shared **predicate** (`specsCollide`), leaving each site's throw/warn and materialization loop local. (4) Two clarifying comments where the code has a non-obvious shape (the two integration paths for the task tools; the deliberately-broad `dynamicAgentEligible` whole-catalog branch).

**The philosophy that led here.**
- **Tenet 3 (Earn every addition).** This change is mostly *subtraction*: two schema definitions become one, two collision routines share one predicate, two source-collection-and-rebuild passes become one. The surface gets smaller and cheaper without losing behavior.
- **Tenet 1 (Coherence over local cleverness).** Duplicated schema and duplicated collision logic are two truths that will drift; and the memo must return *identical* results to the per-step rebuild, so the win is coherence, not a clever shortcut. Critically, the memo must not narrow the existing safety contract — a skill disabled mid-turn is still dropped from every activation path — so the cache key is the *post-eligibility* source list, not the raw activation reads (§6, decision 2).
- **Tenet 5 (Fix at the owning layer).** The worker-input shape is owned by the task-board substrate; skills should consume it, not re-declare it. The fix moves the definition back to its owner.

### 3. Tradeoffs & alternatives

- **Memoize the build vs. split-static-vs-dynamic.** The issue floated an alternative for (C): contribute the static agent set's tools synchronously and only go async when a runtime activation appears, so the pure-static case never trips `hasDynamicTools` and never re-resolves. It was weighed and **rejected as primary**: `runBoard` and the board-bound task tools need `ctx.self` (the generator's own block state, reachable only at execution), so the tools cannot be fully built at config time — the contribution stays function-typed either way, and `hasDynamicTools` still fires. The split narrows *when* async collection runs but doesn't remove the per-step re-build; memoization removes the waste directly and covers both the static and the mid-turn-activation cases with one mechanism. (The split remains a possible later refinement if the synchronous-static path is ever made reachable; noted as a follow-up in the Non-goals below, not built.)
- **The simpler approach considered.** Do only (C) and leave the duplications. Rejected: the duplications are the cheapest to fix while the surface is already open and the reviewer already located them; deferring them just re-pays the context cost later and lets the schemas drift in the meantime. (D2/D3 are genuine drift hazards, not cosmetics.) The one concession to this instinct is the **PR split** (§6, decision 6): the mechanical dedups ride in a separate PR from the perf change so the risky change lands isolated.
- **Where the genuine complexity is.** Not the happy path — it's the **memo key correctness**, and specifically *what stays outside the cache*. The eligibility walk (`collectAgentSources`, including its live-manifest disable read) must keep running every step, or the cache would let a skill disabled mid-turn keep exposing its agents — a regression of the documented "disabled skills are skipped by every activation path" contract (`apps/docs/docs/skills/authoring.md`). So the cache boundary is drawn *below* eligibility: eligibility is recomputed every step, its resolved output is the snapshot, and only the materialization below it is memoized. That leaves a small, named residue of accepted staleness — a mid-turn edit to an *already-live* non-bundled skill's `agents:` map that changes an existing agent's spec **without** changing which skills/keys/inputs are active — enumerated as a signed-off decision (§6, decision 2), not buried.

### 4. Focus practices (1–5)

- **Coherence of the memo (tenet 1).** The cached result must be *observably identical* to the per-step rebuild for an unchanged source list — same tools, same order, same descriptions, same guidance text. The regression test asserts this, not just "it's faster."
- **Don't cache past the safety boundary (tenet 1 / BP-031-adjacent).** `collectAgentSources` — the live-manifest eligibility read — stays per-step; only the downstream build is memoized. The test proves a mid-turn `disable-model-invocation` still drops the skill's agents **on every collection path**, including a bundled runtime activation — the one path FIX-918's collector left unguarded, closed by this change (§7.1).
- **Second-path checklist (BP-035), concurrency & cache-scope.** The memo is per-generator-*execution* state; it must not leak across executions or across generators. Test the rebuild-on-change path (activation added / skill disabled mid-turn), the reuse path (source list unchanged), the **cross-execution non-leak** path (two runs → two builds), and that the empty-roster and no-own-state early-returns still short-circuit.
- **Tolerate the moved schema (BP-030 / BP-034).** `workerInputSchema` is an existing export of the skills package (consumed by `@flow-state-dev/workforce/materialize-agent.ts`, not only orchestration); folding it onto `taskWorkerInputSchema` must keep a compatible export (alias/re-export) — finish the move, don't half-rename.
- **Evidence for a perf claim (BP-003).** The "materialize once per turn" claim needs a deterministic assertion (spy on `materializeWorker`/`collectAgentSources` call counts across ≥2 steps of a mocked multi-step loop, with an `agent-ref` or non-bundled `prompt-ref` agent in the roster so the spy covers registry/collection I/O, not just inline allocation), since wall-clock is dominated by the LLM and won't show it.

### 5. What using it looks like

**No usage examples — this change does not alter how anyone writes code against the framework.** It is an internal performance + deduplication refactor of the delegation surface. Skill authors still declare `agents:` and call `addTask`/`runBoard` exactly as before; the model still sees the identical tool set and roster. The only observable difference is that the tools are materialized once per turn instead of once per step. (The one touched export, `workerInputSchema`, is an internal orchestration symbol, not part of the authoring surface.)

### 6. Decisions & rules — the sign-off surface

1. **(C) Fix per-step rebuild by memoizing the materialization within the turn, not by splitting static/dynamic.**
   - *Alternative rejected:* contribute static-agent tools synchronously and go async only on runtime activation.
   - *Ramification:* the tool contribution stays a function (it needs `ctx.self`, reachable only at execution), so `hasDynamicTools` stays true; the win comes from the cache returning the already-built tools early, not from dodging `prepareStep`. Keeps one code path for static and dynamic rosters. Split stays available as a future refinement (Non-goals, below).

2. **Memo key = the resolved source list (`collectAgentSources` output), recomputed every step; only the downstream build is cached.**
   - *Alternative rejected:* (a) cache `collectAgentSources` itself / re-derive it globally, or (b) key on the raw activation-store reads. Both would let a mid-turn `disable-model-invocation` keep exposing agents until the activation *set* next changed — a regression of the "disabled skills are skipped by every activation path" contract (`delegation-surface.ts:136-145`, `181-185`; `apps/docs/docs/skills/authoring.md:55`).
   - *Collector precondition (safety, rides in this issue):* the snapshot is only safe if `collectAgentSources` actually drops **every** disabled source. It does so today on the static path (`delegation-surface.ts:144`) and the non-bundled runtime path (`185`), but **not** on the bundled runtime shortcut (`168-176`), which pushes `deps.bundledAgentIndex.get(entry.name)` with no live-manifest disable read. So a bundled skill activated mid-turn — or a static skill also present in `activeState`, which the static loop drops but the bundled branch would otherwise re-add — keeps exposing its agents after gaining `disable-model-invocation`, and the memo would then faithfully cache that leak. This change adds the same `isManifestDisabled` read before the bundled shortcut (§7.1), making the "collector drops every disabled source" premise true on all three paths. Without it the memo would harden an existing FIX-918 gap rather than inherit a safe collector.
   - *Ramification:* `collectAgentSources` (and its live-manifest disable read) runs every step — the same deliberate "re-render every step, never memoize the store" policy `binding-reader.ts` applies to the *same* activation store (its combined `active + activeState` body is never memoized because dynamic activation must not stale out). The two are reconcilable and cited together in Part II §7: the reader must re-render because its text always reflects current state; the delegation memo may cache **below** eligibility because eligibility is what it recomputes. Disabling, enabling, adding, or removing a skill/agent-key, or changing an activation's `$ARGUMENTS` input, all change the resolved source list and bust the cache. **Accepted residual staleness (the same class the FIX-918 code left):** a mid-turn edit to an *already-live* non-bundled skill's `agents:` map that changes an existing agent's spec body under an unchanged key — without changing which skills/keys/inputs are active — is not observed until the source-list identity next changes. Rare, low-impact, signed off here.

3. **The same per-turn cache serves both the tools builder and the guidance roster (D1) — and that is load-bearing perf, not just dedup.**
   - *Alternative rejected:* two independent `collectAgentSources` passes, each rebuilding its own artifact every step.
   - *Ramification:* `buildDelegationGuidance` is a function-form context entry, so `hasDynamicContext` re-runs it every step *independently of tool memoization* — if only the tools resolver were memoized, the guidance path would still re-walk sources and rebuild the roster string every step. Routing both through the shared memo is required for the perf claim; the regression test asserts the **guidance path** hits the shared memo, not only the tools resolver.

4. **(D2) Skills reuse the substrate's `taskWorkerInputSchema` instead of the local `workerInputSchema`.**
   - *Alternative rejected:* keep the near-duplicate copy in `worker-materializer.ts`.
   - *Ramification:* the substrate schema is the single owner of the worker-input shape (it carries a superset — `title`/`context` — and a stricter `attempts: int().nonnegative()`); the board worker's `inputSchema` accepts those harmless extra optionals. **Cross-package second path:** `workerInputSchema` is imported by `@flow-state-dev/workforce/materialize-agent.ts` (`inputSchema: isWorker ? workerInputSchema : …`) as well as by orchestration's `worker-materializer.ts` — the "harmless extra optionals" analysis must hold for the workforce worker path too, and a compatible export must be preserved for both importers (BP-034).

5. **(D3) Extract one tiny pure predicate (`specsCollide`), not a mode-parameterized reconciler.**
   - *Alternative rejected:* a shared `reconcile(specs, mode)` helper that owns the throw/warn branching.
   - *Ramification:* the runtime path decides throw-vs-warn **per agent key** via `staticNames.has(source.skillName)`, not via a call-level `mode` — a merged reconciler risks being the wrong abstraction. Extract only `specsCollide(a, b)` (the `!deepEqual`-under-shared-key check, ~5 lines) into `skills/internal/agent-key-reconcile.ts`; keep the `throw` (build-time in `library.ts` + static runtime path) and `warn+skip` (runtime activation path) and the materialization loops **local** to each call site.

6. **(De-risking split) Ship the perf change and the mechanical dedups as two independent PRs.**
   - *Alternative rejected:* one PR for everything (the FIX-918-review grouping).
   - *Ramification:* D1 is genuinely coupled to (C) and rides with it; D2/D3/D4 are independent convenience cleanups (§3), and D2 is the only piece with a cross-package consumer. Splitting the mechanical dedups (D2/D3/D4) into their own PR keeps the risky perf change (C+D1) isolated for review and rollback. The two are independent — no `depends_on` — so they build in parallel (§8 PR plan). Small enough that this is a de-risking split, not a size necessity.

7. **(D4) Add two clarifying comments; do not refactor the code they describe.**
   - *Alternative rejected:* silently leave the non-obvious shapes, or restructure them.
   - *Ramification:* documents (a) why both `buildTaskToolsList` (flat, model-facing) and `createTaskToolsCapability` (closed-over board, for mid-drain fan-out) exist, and (b) that `dynamicAgentEligible`'s whole-catalog `: true` branch is intentionally broader than strictly needed (own-state can't be added mid-run, so the board field is pre-declared defensively).

**Non-goals.** No change to the delegation model, the board/drain semantics, the tool set the model sees, or any authoring surface. Not the split-static-vs-dynamic rearchitecture (weighed in §3 and left as a possible later refinement, not built). Not dependent on FIX-923/FIX-641. Not a change to the residual accepted-staleness window (§6, decision 2) — closing that would require re-reading and re-materializing every step, which is the cost being removed.

**Size estimate:** **Medium** (multi-file, ~100–250 LOC net — with subtraction offsetting additions), shipped as a **2-PR de-risking split** (§8): perf (C+D1) and dedup (D2/D3/D4), independent.

### 7. Technical design

All changes live in `@flow-state-dev/orchestration` (`packages/orchestration/src/skills/`), with one export-compatibility touch felt by `@flow-state-dev/workforce`.

**7.1 The per-execution memo (C + D1).**

Today `library.ts` builds one `surfaceDeps: DelegationSurfaceDeps` per binding-config resolution and closes it into two per-step resolvers (lines ~493–529):

```ts
contributions.tools = (async (blockCtx) => [
  ...staticTools,
  ...(await buildDelegationTools(blockCtx as never, surfaceDeps)),
]) as PresetDef["tools"];
if (cfg.guidance !== false) {
  contextEntries.push(buildDelegationGuidance(surfaceDeps) as never);
}
```

`surfaceDeps` is built **once per binding config and reused across every execution** of that generator — so it must **not** carry the cache (hanging `{ snapshot, result }` off the closure or off `surfaceDeps` leaks state across executions). The carrier is a **module-level `WeakMap` keyed on a per-execution handle**, precedent `ensureSeeded`'s `const sentinel = new WeakMap<object, Promise<void>>()` in `seeding.ts` (keyed on the collection ref; here keyed on the execution's `ctx`/`ctx.self`).

Add to `delegation-surface.ts`:

```ts
interface DelegationMemoEntry {
  /** Structural snapshot of the resolved source list this build was keyed on. */
  snapshot: SourceSnapshot;
  tools: GeneratorTool[];
  /** Roster text, or null when the roster contributes nothing. */
  guidance: string | null;
}

// Per-execution, module-scoped. The key is an execution-stable handle so the
// entry is naturally GC'd with the execution and never leaks across executions
// (NOT surfaceDeps — that is per-binding-config and shared across executions).
const delegationMemo = new WeakMap<object, DelegationMemoEntry>();

/**
 * Resolve (and memoize) the delegation build for this execution step. Runs the
 * per-step eligibility walk (collectAgentSources — keeps the live-manifest
 * disable read on every step, matching binding-reader.ts's deliberate
 * never-memoize policy on the same activation store), snapshots its OUTPUT, and
 * rebuilds the tools + roster only when that snapshot changes. Both the tools
 * resolver and the guidance resolver call this, so the roster is walked and
 * built once per snapshot per step (D1).
 */
async function resolveDelegationBuild(
  ctx: BlockContext,
  deps: DelegationSurfaceDeps,
): Promise<{ tools: GeneratorTool[]; guidance: string | null }> {
  const sources = await collectAgentSources(ctx, deps); // per-step eligibility (unchanged)
  const snapshot = snapshotSources(sources);
  const key = memoKey(ctx); // ctx if execution-stable across steps, else ctx.self
  const cached = delegationMemo.get(key);
  if (cached && deepEqual(cached.snapshot, snapshot)) { // deepEqual from @flow-state-dev/core/helpers
    return { tools: cached.tools, guidance: cached.guidance };
  }
  const tools = sources.length === 0 ? [] : await buildTools(ctx, deps, sources);
  const guidance = buildGuidance(sources);
  delegationMemo.set(key, { snapshot, tools, guidance });
  return { tools, guidance };
}
```

- **`buildTools(ctx, deps, sources)`** is the current body of `buildDelegationTools` *below* `collectAgentSources` (the `ctx.self` own-state check, `boardCollection`, the `materializeWorker` loop, `buildTaskToolsList()` + `buildRunBoardTool`). It now takes the already-resolved `sources` instead of re-collecting them.
- **`buildGuidance(sources)`** is the current body of the closure returned by `buildDelegationGuidance` *below* `collectAgentSources` (the roster `Map` + `DELEGATION_PLAYBOOK` join).
- `buildDelegationTools(ctx, deps)` becomes a thin wrapper: `return (await resolveDelegationBuild(ctx, deps)).tools`. `buildDelegationGuidance(deps)` returns `async (_input, ctx) => (await resolveDelegationBuild(ctx, deps)).guidance`. Both public signatures are preserved so `library.ts` is unchanged except (optionally) nothing.

**Collector precondition — close the bundled-disable gap (safety, §6 decision 2).** The memo snapshots `collectAgentSources`'s output and trusts it to have dropped disabled skills. That trust holds on the static path (`delegation-surface.ts:144`, `isManifestDisabled`) and the non-bundled runtime path (`185`, `state?.disableModelInvocation === true`), but the **bundled runtime branch** (`168-176`) pushes `deps.bundledAgentIndex.get(entry.name)` with **no live-manifest disable read**. Add that read before the bundled shortcut:

```ts
// delegation-surface.ts, inside collectAgentSources, before the bundled push (~168)
if (collection && (await isManifestDisabled(collection, entry.name))) continue;
const bundled = deps.bundledAgentIndex.get(entry.name);
if (bundled) { /* …existing push… */ }
```

This drops a bundled runtime activation (and a static skill also present in `activeState`, which the static loop drops but the bundled branch would otherwise re-add under the same name) the moment its live manifest gains `disable-model-invocation` mid-turn. With the collector correct on all three paths, the snapshot shrinks and busts the memo naturally — no disable signal in the memo key itself. This is a required prerequisite of the memo, not an optional cleanup: without it the memo would harden a pre-existing FIX-918 leak. It rides in sub-PR **a** (§8), the same PR as the memo it protects.

**Snapshot shape (structural compare, not a hash).** Per the cursor review, this is a single-slot "compare against last" memo, so use structural equality over a canonical projection — no hash, which would need a specified delimiter/ordering to avoid `name+input` collisions:

```ts
type SourceSnapshot = Array<{ skill: string; input: string | undefined; agentKeys: string[] }>;

function snapshotSources(sources: DelegationAgentSource[]): SourceSnapshot {
  return sources
    .map((s) => ({ skill: s.skillName, input: s.input, agentKeys: Object.keys(s.agents).sort() }))
    .sort((a, b) => a.skill.localeCompare(b.skill));
}
// compare with deepEqual(a, b) from @flow-state-dev/core/helpers
```

The snapshot is over the resolved source **identity** — which skills are live (disabled skills are filtered out by `collectAgentSources` on every path once the bundled-runtime disable check below is added, so a disable drops a skill and changes the snapshot), each skill's `$ARGUMENTS` input, and its agent-key set. It deliberately does **not** deep-compare each agent's full spec body; that draws the accepted-staleness line at Part I §6 decision 2 (a mid-turn body edit under an unchanged key on a live skill is not observed until identity changes). `deepEqual` is the existing shared helper — no new comparator.

**`memoKey(ctx)`.** The key must be one object per execution, stable across that execution's steps. Verify (precedent: `ensureSeeded` keys on the collection ref, stable per collection) whether the generator passes the *same* `BlockContext` object to `prepareStep` across steps; if it does, key on `ctx`. If `ctx` is a fresh wrapper per step, key on `ctx.self` (the generator's own-state `StateRef`, which is execution-scoped and already the anchor the board/tools close over). This is the one design point the implementer confirms in-code before wiring (§12).

**7.2 Worker-input schema unification (D2).**

`worker-materializer.ts:76` defines `workerInputSchema` (a near-copy) and re-exports it via `skills/index.ts:90`. `task-board/schemas.ts:112` owns `taskWorkerInputSchema` (superset: adds `title`/`context`, stricter `attempts: z.number().int().nonnegative()`). Replace the local definition with a re-export of the substrate's, keeping the `workerInputSchema` name as a compatible alias so both importers keep working:

```ts
// worker-materializer.ts
import { taskWorkerInputSchema } from "../task-board";
/** @deprecated alias — the worker-input shape is owned by the task-board substrate. */
export const workerInputSchema = taskWorkerInputSchema;
```

Importers unchanged: `worker-materializer.ts:158` (`inputSchema: workerInputSchema`) and `workforce/materialize-agent.ts:134` (`inputSchema: isWorker ? workerInputSchema : …`) both continue to compile — the board dispatch already feeds `taskId`/`goal`/`attempts`/…; the extra optionals (`title`/`context`) are accepted, not required. Confirm the workforce worker generator tolerates the superset (it validates *input*, so extra optional keys are permissive).

**7.3 Agent-key collision predicate (D3).**

Two sites run `deepEqual`→dedupe→throw/warn: `library.ts:432-444` (build-time static, throw) and `delegation-surface.ts` `buildDelegationTools` (runtime, throw for static-named source / warn+skip for runtime activation, decided per-key via `staticNames.has(source.skillName)`). Extract only the shared **predicate** into `skills/internal/agent-key-reconcile.ts`:

```ts
import { deepEqual } from "@flow-state-dev/core/helpers";
import type { AgentSpec } from "@flow-state-dev/core";
/** True when two agent specs share a key but are NOT identical — a real collision
 *  (identical specs dedupe into one board worker; only divergent ones collide). */
export function specsCollide(a: AgentSpec, b: AgentSpec): boolean {
  return !deepEqual(a, b);
}
```

Both sites call `if (prior && specsCollide(prior, spec)) { …throw or warn… }`; the throw/warn wording, the `staticNames` per-key decision, and the `seenSpecs`/`boardWorkers` loops stay local. Net: the collision *judgement* has one owner; the *policy* stays where it belongs.

**7.4 Clarifying comments (D4).** Add two comments — no code movement:
- In `delegation-surface.ts` / `task-tools-capability.ts` where both `buildTaskToolsList` and `createTaskToolsCapability` are used: one exists as the flat model-facing task tools, the other as a board-closed-over capability for an inline agent's mid-drain fan-out.
- In `library.ts` at the `dynamicAgentEligible` whole-catalog `: true` branch: it is intentionally broader than strictly needed because own-state fields can't be added mid-run, so the board field is pre-declared defensively.

### 9. Edge cases & error handling

| Case | Expected behavior |
|---|---|
| Empty roster (no agent-declaring skill live) | `collectAgentSources` → `[]`; `resolveDelegationBuild` returns `{ tools: [], guidance: null }`; snapshot is `[]`, cache stores it — no rebuild while empty. Existing early-returns preserved. |
| Host generator has no own state | `buildTools` hits the existing `ctx.self`/`atomicState` guard, warns, returns `[]`. Cached like any other result for the snapshot. |
| Static skill disabled mid-turn (`disable-model-invocation` added to live manifest) | static loop's `isManifestDisabled` drops it (per-step read, §7.1) → snapshot shrinks → cache busts → rebuild without its agents. **Safety contract preserved.** |
| Non-bundled runtime activation disabled mid-turn | non-bundled branch's `disableModelInvocation` check drops it → snapshot shrinks → cache busts. **Preserved.** |
| Bundled runtime activation disabled mid-turn | the added bundled-branch `isManifestDisabled` check (§7.1) drops it → snapshot shrinks → cache busts. **Gap closed by this change** — was leaking before. |
| Static skill also present in `activeState` (bundled), disabled mid-turn | static loop drops it *and* the bundled-branch check prevents the activation loop re-adding it under the same name → dropped. **Gap closed by this change.** |
| Skill activated mid-turn | new source in the list → snapshot grows → rebuild includes it. |
| Activation `$ARGUMENTS` input changes mid-turn | snapshot's `input` field changes → rebuild with new substitution. |
| Same agent key, identical spec, two skills | `specsCollide` → false → dedupe into one board worker (both sites). |
| Same agent key, divergent spec | static: throw (build-time + runtime static-named); runtime activation: warn+skip. Unchanged. |
| Mid-turn body edit to an existing agent key on a live non-bundled skill, no identity change | **Accepted staleness** (§6 decision 2) — served from cache until identity next changes. |
| Two concurrent executions of the same generator | distinct `memoKey` handles → distinct `WeakMap` entries → two builds, no cross-talk (cross-execution non-leak test). |

Second-path checklist (BP-035): legacy — `workerInputSchema` alias holds for existing importers; null-boundary — `input === undefined` participates in the snapshot and `guidance: null` short-circuits; concurrency/multi-tenant — per-execution WeakMap key; cost-observability — the whole change *is* a cost reduction, asserted by call-count. No new flag.

### 10. Testing strategy

- **No goal check applies** — internal perf + dedup refactor; the model sees an identical tool set and roster, so there is no new user-observable outcome to prove with a real-model run. The perf claim is proven deterministically (below), per BP-003.
- **CI specs (mocked, deterministic):**
  - **Perf / materialize-once** (`integration-tests/`): a mocked multi-step tool loop (≥2 steps: `addTask` then `runBoard`) with an unchanged roster; spy on `materializeWorker` (or `collectAgentSources`-downstream build) and assert **one** materialization across the steps. The roster **must include an `agent-ref` or non-bundled `prompt-ref` agent** so the spy covers registry/collection I/O (the N+1 path), not just inline allocation.
  - **Guidance hits the memo** (`integration-tests/`): across the same ≥2 steps, assert the guidance/roster string is built **once**, not per step (the D1 load-bearing claim — guidance is function-form context and would otherwise re-walk every step).
  - **Disable-safety** (`integration-tests/`): a skill live at step 1, its live manifest gains `disable-model-invocation` before step 2 → assert step 2's tools **and** roster no longer include its agents (proves eligibility is not cached away). **Cover every collection path, not just the static one** — the test matrix must include: (i) a **dynamically-activated bundled skill** (resolved via `bundledAgentIndex`, the path FIX-918 left unguarded) disabled mid-turn, and (ii) a **static skill also present in `activeState`** disabled mid-turn. Both must drop the skill's `addTask`/`runBoard` agents and its roster line at step 2 even under memoization — proving the added bundled-branch disable check (§7.1), not the memo, governs. (The non-bundled runtime path is already covered by the base case.)
  - **Rebuild-on-change** (`integration-tests/`): activate a new skill between steps → assert a second materialization and the new agent present.
  - **Cross-execution non-leak** (`integration-tests/`): two separate executions with the same roster → assert **two** builds (memo keyed per execution, not on the shared closure/deps).
  - **Snapshot compare** (fast unit test, `packages/orchestration`): `snapshotSources` + `deepEqual` — order-independence (sources/keys sorted), input-sensitivity, disable-drop changes the snapshot, identical rosters compare equal.
  - **Dedup** (fast unit tests, `packages/orchestration`): `specsCollide` truth table (identical → false, divergent → true); D2 — a dispatch input with `title`/`context` validates against the aliased schema.
- **Discipline:** `fsd:tdd` (this is enhancement/refactor, not a bug) — the seam for the perf/safety specs is the mocked multi-step loop in `integration-tests/`; the seam for snapshot/predicate specs is vitest in `packages/orchestration`.
