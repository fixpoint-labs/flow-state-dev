# FIX-928: Delegation surface — memoize per-step rebuild + dedup build/runtime helpers — Implementation Spec

> **Epic:** [FIX-930 — Delegation substrate](https://linear.app/fixpoint-labs/issue/FIX-930) · epic-spec on `epic/delegation-substrate` (epic PR #873, `epic approved`). This issue is the delegation-surface polish member of that set: "the delegation-surface helpers get a memoize/dedup polish (FIX-928)." It moves independently of the FIX-923 keystone and does not change the delegation *model* — only tightens the surface FIX-918 shipped.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

FIX-918 shipped the board-commanded delegation surface: a skill declares a roster of agents, the host plans work with `addTask`, and drains it with `runBoard`. The `/simplify` review of that PR (#854) flagged a cluster of correctness-neutral rough edges on the surface it left behind — one performance waste and four small duplications. None blocks anything; they were grouped so the surface gets tightened in a single pass rather than trickled out.

The performance one has teeth on the hot path. Because the delegation tools are contributed as an async function (so a skill activated mid-turn can still join the board), the generator treats the whole tool set as *dynamic* and re-resolves it before **every** step of the tool loop. The primary delegation flow is inherently multi-step (`addTask` N times, then `runBoard`), so on each of those steps the framework re-materializes every agent, rebuilds the eight task-tool handlers, and reconstructs the task board and the `runBoard` sequencer from scratch — even when nothing about the roster changed. That is wasted work (LLM latency dominates, but the rebuild does real allocation and re-parsing per step) and it repeats as delegation adoption grows.

**Why now.** The surface is fresh, the review notes are fresh, and doing this before FIX-641 (the class+identity specialization layer that lands on top of this same surface) means that later work builds on a deduplicated, memoized base instead of forking the drift further.

### 2. Solution in plain terms

Two moves, both on the delegation surface, neither touching the delegation *model*:

- **(C) Stop rebuilding the board every step.** Build the delegation tools once per generator turn and reuse that result across steps, rebuilding only when the roster actually changes. "The roster changed" is captured by a cheap **activation snapshot** — the static agent-skill set (fixed for the turn) plus a hash of the runtime activations read from the binding's activation store. When a step re-resolves the tools and the snapshot matches the last one, hand back the already-built tools instead of re-materializing. The one legitimate reason to rebuild — a model activating a new agent-skill mid-turn — still triggers a rebuild because the snapshot changes. The same per-turn cache also serves the guidance (roster) text, which today independently re-walks the same sources.

- **(D) Collapse four small duplications into one owner each.** (1) `collectAgentSources` runs twice per resolve (once for the tools, once for the guidance roster) — share one pass via the cache from (C). (2) The skills package redefines a worker-input Zod schema (`workerInputSchema`) that is a near-copy of the substrate's `taskWorkerInputSchema` — reuse the substrate's so the two can't drift. (3) The agent-key collision logic (`deepEqual` → dedupe, then throw-or-warn) is written twice — once at build time in `library.ts`, once at runtime in `delegation-surface.ts` — extract one shared helper that keeps the **static-throws / runtime-warns** distinction as a mode. (4) Two clarifying comments where the code has a non-obvious shape (the two integration paths for the task tools; the deliberately-broad `dynamicAgentEligible` whole-catalog branch).

**The philosophy that led here.**
- **Tenet 3 (Earn every addition).** This change is mostly *subtraction*: two schema definitions become one, two collision routines become one, two source-collection passes become one. The surface gets smaller and cheaper without losing behavior.
- **Tenet 1 (Coherence over local cleverness).** Duplicated schema and duplicated collision logic are two truths that will drift; the memo must return *identical* results to the per-step rebuild, so the win is coherence, not a clever shortcut. Where the snapshot deliberately narrows what counts as "changed," that tradeoff is named (§6), not hidden.
- **Tenet 5 (Fix at the owning layer).** The worker-input shape is owned by the task-board substrate; skills should consume it, not re-declare it. The fix moves the definition back to its owner.

### 3. Tradeoffs & alternatives

- **Memoize vs. split-static-vs-dynamic.** The issue floated an alternative for (C): contribute the static agent set's tools synchronously and only go async when a runtime activation appears, so the pure-static case never trips `hasDynamicTools` and never re-resolves. It was weighed and **rejected as primary**: `runBoard` and the board-bound task tools need `ctx.self` (the generator's own block state, only reachable at execution), so the tools cannot be fully built at config time — the contribution stays function-typed either way, and `hasDynamicTools` still fires. The split narrows *when* async collection runs but doesn't remove the per-step re-resolve; memoization removes the waste directly and covers both the static and the mid-turn-activation cases with one mechanism. (The split remains a possible later refinement if the synchronous-static path is ever made reachable; noted as a follow-up, not built.)
- **The simpler approach considered.** Do only (C) and leave the duplications. Rejected: the duplications are the cheapest to fix while the surface is already open and the reviewer already located them; deferring them just re-pays the context cost later and lets the schemas drift in the meantime. (D2/D3 are genuine drift hazards, not cosmetics.)
- **Where the genuine complexity is.** Not the happy path — it's the **memo key correctness**. The snapshot must capture everything that can change the built tool set within a turn (static sources, runtime activations, per-activation `$ARGUMENTS` input) while deliberately *not* re-reading live skill manifests on every step (that live read is exactly the cost we're removing). The consequence — a `disable-model-invocation` toggled on a skill *mid-turn* isn't observed until the activation set next changes — is real, rare, and acceptable; it's called out as a signed-off decision, not buried.

### 4. Focus practices (1–5)

- **Coherence of the memo (tenet 1).** The cached result must be *observably identical* to the per-step rebuild for an unchanged snapshot — same tools, same order, same descriptions, same guidance text. The regression test asserts this, not just "it's faster."
- **Second-path checklist (BP-035), concurrency & cache-scope.** The memo is per-generator-turn state; it must not leak across executions or across generators. Test the rebuild-on-change path (activation added mid-turn) and the reuse path (snapshot unchanged), plus the empty-roster and no-own-state early-returns still short-circuit.
- **Tolerate the moved schema (BP-030 / BP-034).** `workerInputSchema` is an existing export of the skills package; folding it onto `taskWorkerInputSchema` must keep a compatible export (alias/re-export) or update every consumer — finish the move, don't half-rename.
- **Evidence for a perf claim (BP-003).** The "rebuild once per turn" claim needs a deterministic assertion (spy on materialization/`collectAgentSources` call count across ≥2 steps of a mocked multi-step loop), since wall-clock is dominated by the LLM and won't show it.

### 5. What using it looks like

**No usage examples — this change does not alter how anyone writes code against the framework.** It is an internal performance + deduplication refactor of the delegation surface. Skill authors still declare `agents:` and call `addTask`/`runBoard` exactly as before; the model still sees the identical tool set and roster. The only observable difference is that the tools are built once per turn instead of once per step. (The one touched export, `workerInputSchema`, is an internal orchestration symbol, not part of the authoring surface.)

### 6. Decisions & rules — the sign-off surface

1. **(C) Fix per-step rebuild by memoizing within the turn, not by splitting static/dynamic.**
   - *Alternative rejected:* contribute static-agent tools synchronously and go async only on runtime activation.
   - *Ramification:* the tool contribution stays a function (it needs `ctx.self`), so `hasDynamicTools` stays true; the win comes from the cache returning early, not from dodging `prepareStep`. Keeps one code path for static and dynamic rosters. Split stays available as a future refinement (§12).

2. **Memo key = activation snapshot: static source names + a hash of runtime activations (name + input), scoped per generator turn.**
   - *Alternative rejected:* re-derive the full source list (including live manifest reads) every step, or cache globally.
   - *Ramification:* a `disable-model-invocation` toggled on a skill **mid-turn** is not observed until the activation set next changes within that turn — accepted as rare and low-impact. Cache is per-turn/per-ctx and must not persist across executions.

3. **The same per-turn cache serves both the tools builder and the guidance roster (D1).**
   - *Alternative rejected:* two independent `collectAgentSources` passes.
   - *Ramification:* one source-collection per snapshot per turn; the guidance function and the tools function read from the shared memo rather than each re-walking sources.

4. **(D2) Skills reuse the substrate's `taskWorkerInputSchema` instead of the local `workerInputSchema`.**
   - *Alternative rejected:* keep the near-duplicate copy in `worker-materializer.ts`.
   - *Ramification:* the substrate schema is the single owner of the worker-input shape (it carries a superset — `title`/`context` — and a stricter `attempts`); the board worker's `inputSchema` accepts those harmless extra optionals. A compatible export must be preserved for existing importers (BP-034).

5. **(D3) One shared agent-key reconciliation helper, parameterized by outcome mode.**
   - *Alternative rejected:* two hand-written copies of the `deepEqual`→dedupe→throw/warn logic.
   - *Ramification:* the helper keeps the **static ⇒ throw** vs **runtime ⇒ warn+skip** distinction as a mode argument; both `library.ts` build-time validation and `delegation-surface.ts` runtime materialization call it. Identical-spec dedupe and divergent-spec handling live in one place.

6. **(D4) Add two clarifying comments; do not refactor the code they describe.**
   - *Alternative rejected:* silently leave the non-obvious shapes, or restructure them.
   - *Ramification:* documents (a) why both `buildTaskToolsList` (flat, model-facing) and `createTaskToolsCapability` (closed-over board, for mid-drain fan-out) exist, and (b) that `dynamicAgentEligible`'s whole-catalog `: true` branch is intentionally broader than strictly needed (own-state can't be added mid-run, so the board field is pre-declared defensively).

**Non-goals.** No change to the delegation model, the board/drain semantics, the tool set the model sees, or any authoring surface. Not the split-static-vs-dynamic rearchitecture. Not dependent on FIX-923/FIX-641.

**Size estimate:** **Medium** (multi-file, single PR, ~100–250 LOC net — with subtraction offsetting additions). Single-node PR plan; no DAG.
