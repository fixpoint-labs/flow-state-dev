# FIX-929: Design — Agent vs. AgentController (wrap a generator with fuller agent-level capabilities) — Implementation Spec

> **This is a design / decision spike, like FIX-923.** Its deliverable is a decision
> — Agent-vs-AgentController, flat-vs-nested, the relationship to `defineAgent` and to
> capabilities, and the background-execution model — **not** a build. It ships no API.
> Part II below is **The Findings** (the grounded evidence behind Part I's decisions and
> the hand-off to the issues this feeds), not a build sequence.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

A generator today is a model plus a tool loop. When we want an agent to do more than
"reason and call tools in one turn" — coordinate delegated work, auto-load a skill on a
deterministic cue, run work in the background and pick the results back up later, enforce
a lifecycle — the question is *where that machinery lives*. The FIX-918 delegation review
floated a bespoke `skillController` block to own board lifecycle outside the model's loop.
On reflection the real question is broader: **is the managed unit we deploy and delegate
to a new "Agent" primitive, a separate "AgentController" that has a generator, or just a
generator with the right capabilities composed around it?**

Why now: FIX-923 (the keystone host-model spike) has **landed** and decided *what* the
delegation host is (coordinator + synthesizer; on-demand as a default-worker floor). Two
coupled questions about *how the host is packaged and run* were deliberately left to this
spike (epic FIX-930 §2e, Q6): the Agent/AgentController shape, and whether delegated work
can run in the **background** via a controller loop rather than a standalone
event/listener/notification subsystem (FIX-901's current lean). Those calls gate how
FIX-901 is designed and how the host packaging reads, so they are worth settling before
that work proceeds. There is no user-facing gap open today — this decision prevents
building the wrong shape, it does not unblock a broken workflow.

### 2. Solution in plain terms — the recommendation

**There is no new primitive. The "agent controller" is a composition role, not an object
the author constructs.** Keep `defineAgent`'s `Agent` as the *spec* (persona, model,
tools, `uses`, skills). Everything the issue calls an "agent-level capability" —
delegation/board draining, skill install/auto-load, memory, HITL gating — is **already a
capability (`uses`) or the skills binding, composed around the generator by
`materializeAgent`.** The managed unit is *the materialized generator plus the
capabilities bound around it*. We do **not** add an `AgentController` wrapper, and we do
**not** build a tower of nesting decorators. **Flat, not nested.**

The one thing a capability genuinely *cannot* do by itself is **re-invoke the generator
across a gap** — a capability runs *inside* a loop iteration; it can `ctx.suspend()` to
pause, but the thing that *wakes* the generator is the runtime, not the capability. That
is the only "controller" in the picture, and **it already exists as machinery**: a
`runBoard` tool call is one generator loop iteration with the framework's existing
**suspend/resume semantics** (FIX-814), and the wake is the existing `wakeOn` listener
(FIX-660) over a durable, session-scoped task board (`defineTaskCollection`). "Host stays
alive and synthesizes the board inline" and "host ends its turn and is woken when the
board completes" are the *same thing* from the generator's point of view — a tool it
called, returning on its next iteration. So **background execution is a property of the
existing loop, not a new notification subsystem** — which is the direction FIX-901 should
take.

**The philosophy that led here.** This leans hardest on **tenet 2 (composition over
features)** — the controller is a composition of primitives that already exist, and a new
`Agent`/`AgentController` primitive would fracture the model `defineAgent`, capabilities,
and the task board already establish. **Tenet 3 (earn every addition)**: the default
answer to "should an `AgentController` exist?" is no, and nothing here clears that bar
that `uses` + the skills binding + the drain don't already clear. **Tenet 4 (framework
absorbs infrastructure, not knowledge)**: the background loop is infrastructure the
framework already owns (suspend/resume, `wakeOn`, durable collections) — the recommendation
points FIX-901 at that infrastructure instead of a parallel one.

### 3. Tradeoffs & alternatives

- **Rejected — a new `Agent` primitive that owns the generator (generator as an
  implementation detail of an Agent).** This duplicates `defineAgent` (which already *is*
  the agent spec) and demotes the generator from a first-class block to a hidden internal.
  Every flow that composes a generator directly would gain a second, competing "how do I
  run a model" path. Rejected on tenets 2 and 3.
- **Rejected — nesting controllers (composable decorators, one capability each) wrapping a
  generator.** This is the "controller-tower" the issue itself flags as hard to reason
  about. We already have a flat composition surface — `uses: [cap, cap, …]` — that adds
  around-the-loop behavior without nesting. A decorator stack would reinvent `uses` with
  worse ergonomics and unclear ordering semantics. Rejected on tenet 2.
- **The simpler approach — "do nothing; it's all capabilities already."** This is close to
  correct and is most of the recommendation. Where it is *insufficient* is the background
  loop: a capability cannot re-invoke its own generator across a cross-request gap, so
  *true* background drain (FIX-901) needs a durable board plus a drainer that resumes the
  suspended host. That piece is real work — but it is **FIX-901's** work against the
  existing suspend/resume runtime, not a new controller primitive.
- **Where the genuine complexity is** — not the happy path (in-request drain works today).
  It is **state continuity across a cross-request gap.** A *history-driven* host is
  transparent for free (the history *is* the state; reseeding it can't tell it ever
  stopped). A *stateful* host that keeps its own block-state across the gap loses that
  state unless it is durably checkpointed — a real, conditional dependency on FIX-917
  Part-2 (durable block-state, which today only *warns* on silent suspend-reset). Naming
  that boundary correctly is the load-bearing part of this spike.

### 4. Focus practices (1–5)

1. **Compose, don't accrete (tenet 2).** The controller must be expressed as
   `Agent` (spec) + `uses` (capabilities) + the drain, reusing `materializeAgent`. Resist
   any new `AgentController` type or block kind — if a reviewer can point at a capability
   or the skills binding that already covers a concern, that concern is not new surface.
2. **Reuse the existing suspend/resume, don't build a bus (tenet 4).** The background wake
   is `ctx.suspend()` inside `runBoard` + the resume runtime + `wakeOn` over a durable
   collection. A new event/listener/notification subsystem for FIX-901 would duplicate
   machinery that already re-enters the exact suspending tool call by replay-log identity.
3. **Name the durable-state boundary honestly (BP-030 / BP-035).** History-driven host =
   free across the gap; own-block-state host = needs FIX-917 Part-2. State the conditional
   dependency; do not hand-wave it into "not a dependency."
4. **Caps accumulate across wakes, per-run counters reset (BP-035, second-path).** A
   background host that wakes repeatedly must not get a fresh enqueue/spend budget each
   wake (FIX-931/FIX-933); `max-turns`-style per-run counters resetting per wake is fine.

### 5. What using it looks like

This spike ships **no new API**, so there is no new call site to show. The point of the
recommendation is that *the surface a delegating author already writes does not change* —
the "controller" is the composition they already express. Illustrative, to make the
"it's already capabilities" claim concrete (a sketch, not a contract):

```ts
// Today: an "agent controller" is a generator with capabilities composed around it.
// defineAgent is the spec; materializeAgent binds the around-the-loop capabilities.
defineAgent({
  name: "coordinator",
  persona: "…",
  usesCapabilities: [taskTools /* delegation + board drain */, memory /* cross-turn */],
  usesSkills: ["research", "summarize"], // skill install / auto-load (the skills binding)
});
// runBoard() inside its loop IS the drain; ctx.suspend() inside runBoard IS the wake point.
// No AgentController object is constructed — the composition is the controller.
```

The **background** difference is one behavioral choice inside `runBoard` (end-the-turn and
be woken vs. synthesize inline), not a new author-facing type — and that choice, plus the
drainer that wakes a suspended host, is **FIX-901's** to build against this decision.

### 6. Decisions & rules — the sign-off surface

1. **No new primitive: the "agent controller" is `Agent` (spec) + capabilities (`uses`) +
   the skills binding + the drain, materialized by `materializeAgent` — flat, not nested.**
   - *Alternative rejected:* a new `Agent`/`AgentController` type that owns the generator,
     or a stack of nesting per-capability decorators.
   - *Ramification:* around-the-loop concerns are added as capabilities, not wrapper
     layers; `defineAgent` stays the single agent spec. Locks out a second "how to run a
     model" path. *Falsifier:* a concern that genuinely cannot be a capability *and* cannot
     be the runtime loop would justify a thin wrapper — name it then, not now.
2. **The background loop is the framework's existing suspend/resume, not a new execution
   model.** `runBoard` is one loop iteration; `ctx.suspend()` inside it is the wake point;
   the resume runtime (FIX-814/FIX-141) re-enters the exact tool call.
   - *Alternative rejected:* treating "background execution" as a distinct runtime to design.
   - *Ramification:* in-request (synthesize inline) and cross-request (end-and-wake) are the
     same mechanism with different backings. *Falsifier:* if resume cannot re-enter a
     generator tool after a cross-request gap without replaying model turns, end-and-reseed
     needs new machinery (code today says it can — replay-log identity survives).
3. **The real fork is in-request suspend/resume vs. cross-request end-and-reseed — ship
   in-request first; cross-request true-background is FIX-901.** In-request needs nothing
   new. Cross-request needs a durable session-scoped board keyed per agent id (exists:
   `defineTaskCollection`) plus a drainer that wakes the suspended host.
   - *Alternative rejected:* committing the host packaging to cross-request semantics now.
   - *Ramification:* the packaging commits to *nothing that blocks either*; FIX-901 owns the
     cross-request drainer.
4. **Q6 resolved: controller-loop over a standalone event/listener/notification subsystem —
   because the "loop" *is* the existing `wakeOn` listener over a durable collection, not new
   machinery. FIX-901 is reframed accordingly.** The board's workers already wake on
   `task-change` (`wakeOn`, FIX-660); the *host* waking when the board completes is the same
   primitive one scope up.
   - *Alternative rejected:* FIX-901 building a separate notification bus.
   - *Ramification:* FIX-901 becomes "a background drainer that resumes a suspended host when
     its durable board signals completion," not a new subsystem. *Falsifier:* cross-*process*
     / external-drainer deployment may still need a transport signal (a Vercel-adapter
     concern), but that is not a new user primitive.
5. **State continuity: history-driven hosts are transparent across the gap for free;
   own-block-state hosts are a *conditional* dependency on FIX-917 Part-2 (durable
   block-state).** Durable state for a woken host lives at **controller/session scope** (the
   durable board keyed per agent id), **not** block scope — so the common history-driven case
   is **not** blocked on FIX-917.
   - *Alternative rejected:* declaring a hard FIX-917 dependency for all hosts, or claiming
     no dependency at all.
   - *Ramification:* the first background pass targets history-driven hosts; own-block-state
     hosts wait on FIX-917 Part-2. The exact holding mechanism (block-state-at-agent-level
     vs. a session resource) is deferred but must support either.
6. **Skill install/auto-load is the existing skills binding, not new controller machinery.**
   A deterministic `/skill-name` cue is an *activation matcher* on the skills capability
   (whose `active` / `dynamicActivation` / load-tool / upstream-matcher activation paths
   already exist), not a new mechanism the controller owns.
   - *Alternative rejected:* a bespoke skill-install path inside a controller wrapper.
   - *Ramification:* auto-load rides the binding every generator already can carry.
     *Falsifier:* if deterministic pre-generation activation can't hook the existing binding,
     a small activation-matcher addition is warranted (still a capability, not a wrapper).
7. **Caps accumulate across wakes; per-run counters reset per wake.** FIX-931 (enqueue
   count) and FIX-933 (spend) budgets live on the durable session-scoped board and
   accumulate; `max-turns`-style per-run counters resetting per wake is expected.
   - *Alternative rejected:* per-invocation budgets that a repeated wake silently refreshes.
   - *Ramification:* the durable board is the home for cumulative budgets; the cap gates read
     it at session scope.
8. **Sequencing (epic Q6, for the human): land this decision now; FIX-901 builds against it;
   the floor/identity/cap work (FIX-641/924/931) does NOT block on it. Recommend 929 does
   NOT hard-block the dependent build — but the human owns final sequencing.** 929 settles
   the *shape* so FIX-901 isn't designed as a separate notification subsystem; the builds
   that align to 923's decided floor are unaffected by this packaging call.
   - *Alternative rejected:* gating all dependent build work behind this spike.
   - *Ramification:* parallel progress; the only thing that must wait for 929 is FIX-901's
     design commitment.

**Non-goals.** Not building the controller, FIX-901's drainer, or any API (this is a
decision doc). Not a general agent-abstraction redesign — the wider agent-abstraction /
roster-introspection question stays in **FIX-817, out of this epic**. Not deciding the exact
durable-state holding mechanism (deferred; must support either).

**Size estimate.** Design/decision spike — **no code, no PR plan.** Deliverable is this
document (mirrored to Linear), like FIX-923. The *downstream* build it authorizes (chiefly
FIX-901) is separately estimated at its own spec.

## Part II — The Findings *(grounded analysis + hand-off to the issues this feeds)*

> Dense on purpose: the evidence behind Part I's decisions, read against the current tree,
> plus the concrete hand-off to FIX-901 / FIX-641 / FIX-931 / FIX-933 / FIX-817.

### 7. Current behavior — verified against the code

Every claim was read in the current tree, not taken from the issue on faith.

- **`defineAgent` already *is* the agent spec.** `defineAgent(config: Agent)` validates and
  returns an `Agent` (name, `persona`, `model`, `allowedTools`, `usesCapabilities`,
  `usesSkills`, `itemVisibility`, `outputSchema`) — `packages/workforce/src/define-agent.ts`.
  → confirms Decision 1: the "spec" half the issue asks about already exists.
- **`materializeAgent` already composes capabilities *around* a generator.** It builds a
  `generator({ … tools, uses, maxIterations })` from an `Agent`, resolving `usesCapabilities`
  into `uses` and folding in board-scoped `taskTools`
  (`packages/workforce/src/materialize-agent.ts`). `agentBlock` is the standalone wrapper;
  the worker shape is the same machinery with a `workerInputSchema`. → confirms Decision 1:
  around-the-loop capabilities are *already* `uses`, materialized flat. Note two live
  reserved-but-unwired hooks the warnings expose: `usesSkills` ("reserved and not yet
  wired") and `contextMode: "fork"` ("not honored") — the skill-install and fork concerns
  the issue names are *already anticipated slots on the spec*, not missing primitives.
- **`runBoard` is a real drain tool over the generator's own-state board.** The delegation
  surface installs `taskTools` + `runBoard` (a `taskBoard(...).drain`) only when a bound
  skill declares `agents:` (`packages/orchestration/src/skills/delegation-surface.ts`,
  `library.ts:394-408`). → confirms Decision 2: the drain is a tool call inside the loop.
- **Generator suspension already spans a loop iteration and resumes the exact tool call.**
  A tool that calls `ctx.suspend()` throws a `SuspensionError`; siblings settle, one gate is
  surfaced, and on resume the runtime re-enters the *same* tool call — `completed` calls
  inject persisted output, the pending gate's `ctx.suspend()` returns the resume payload
  (FIX-814, `packages/core/src/blocks/generator.ts:1293,1490-1500`; resume runtime FIX-141).
  → confirms Decision 2's falsifier is satisfied: cross-request re-entry preserves tool-call
  identity via the replay log, so "end-and-reseed" needs no new re-entry machinery.
- **`wakeOn` (FIX-660) is the existing event-driven wake primitive.** The board's idle
  workers `.waitForCondition(…, { wakeOn })` filtered by `onTaskChangeFor(collectionId)`,
  waking on `task-change` items rather than polling
  (`packages/orchestration/src/task-board/index.ts:661`). → confirms Decision 4: the "loop"
  is this listener one scope up (host wakes on board-complete), not a new bus.
- **Durable, session-scoped boards already exist.** `defineTaskCollection` yields a durable,
  resource-backed `TaskCollection` whose tasks survive across turns as instances
  (`packages/orchestration/src/tasks/collection/define-task-collection.ts`; resolve via
  `resolve-resource.ts`). → confirms Decision 3/5: the "durable board keyed per agent id" is
  an existing backing, not new substrate.
- **The skills binding already owns install / auto-load.** `.with({ active })` preloads
  skill bodies; `.with({ allowed, dynamicActivation: true })` installs a model-facing load
  tool; activation also flows from an upstream matcher or code
  (`packages/orchestration/src/skills/library.ts:6-29,323-355`). → confirms Decision 6: a
  deterministic `/skill-name` cue is an activation matcher on this binding.
- **The background *drainer* is the genuine gap.** FIX-901 states plainly that persistence
  and scheduled actions exist but "nothing turns 'there is durable work' into 'workers are
  draining it in the background'"; a failed request is only picked up "when a next request
  happens to come." → confirms Decision 3: cross-request true-background is the one real
  build, and it is FIX-901's.

### 8. Prior art — the packaging question, cited

- **Anthropic, "Building Effective Agents"** ([post](https://www.anthropic.com/research/building-effective-agents)):
  the orchestrator-workers shape is a *composition* — "a central LLM dynamically breaks down
  tasks, delegates them to worker LLMs, and synthesizes." The guidance is explicit: *start
  simple, add structure only when it earns its place.* A new controller primitive is exactly
  the structure to defer until composition fails — which it does not here.
- **Claude Code sub-agents** ([docs](https://code.claude.com/docs/en/sub-agents)): the agent
  is a generator whose "around-the-loop" behavior (which sub-agents exist, which skills load)
  is configuration and description-based matching, not a wrapper class the author constructs.
  The deterministic-cue skill auto-load in FIX-929 mirrors this — matcher, not machinery.
- **Durable-execution engines (Temporal-style suspend/resume)**: the transferable pattern is
  that "background work that pauses and continues" is a property of a *durable execution +
  resume* substrate, not a bespoke notification bus. FSD already has that substrate
  (`ctx.suspend()` + resume runtime + durable collection); the Q6 recommendation is to use
  it rather than reintroduce a message-bus layer beside it.
- **The counter-signal (why a wrapper *can* be right)**: OpenAI Agents-SDK and LangGraph both
  ship an explicit orchestrator object. That is justified when the orchestrator owns runtime
  state a plain function can't — which, in FSD, is exactly the *cross-request wake*, and that
  lives in the runtime/drainer (FIX-901), not a user-constructed `AgentController`.

No new bus. Its *shape* is now decided; its viability rests on the suspend/resume re-entry proven in §7. |
| **FIX-641** (class+identity) | Unaffected by this packaging call — it aligns to 923's decided default-worker floor. No dependency on 929. |
| **FIX-924** (validateAssignee) | Unaffected — mode-based rule already decided by 923. |
| **FIX-931** (enqueue cap) / **FIX-933** (spend cap) | **Budgets live on the durable session-scoped board and ACCUMULATE across host wakes**, not per-invocation. Per-run counters (max-turns) reset per wake. |
| **FIX-917** (durable block-state) | **Conditional dependency for own-block-state hosts only.** History-driven hosts don't need it. Part-2 durable block-state (today only warns on silent suspend-reset) is the prerequisite for a host that keeps own block-state across a cross-request wake. |

### 10. Edge cases the downstream builds must handle

| Case | Expected behavior |
| -- | -- |
| History-driven host, cross-request wake | Transparent: reseed history; the host cannot tell it stopped. No FIX-917 dependency. |
| Own-block-state host, cross-request wake | Own block-state is lost unless durably checkpointed → **blocked on FIX-917 Part-2**; until then, warn (today's suspend-reset warning) rather than silently drop. |
| Host wakes repeatedly (runaway) | FIX-931 count + FIX-933 spend budgets accumulate on the durable board and reject past the ceiling; they do **not** refresh per wake. |
| In-request drain (no background) | Today's behavior preserved: `runBoard` synthesizes inline; no suspend, no durable board required. |
| Partial completion / task ordering on wake | The host is woken per-completion or once-all-done per `runBoard` config; the durable board is the source of truth for which tasks settled, so a re-entered host reconciles from board state, not from in-memory turn state. |
| Cross-process / external drainer | Out of scope for the first pass (Decision 4 falsifier): single-node drainer first; multi-process leasing/transport signal is a later deployment concern (Vercel adapter), not a new user primitive. |

### 11. Documentation plan

### 12. Dependencies, open questions & follow-ups

**Dependencies.** This spike has **no hard blockers** (it is a decision). It **informs**
FIX-901 (whose design commitment should wait for it) and reframes the epic's Q6. It does
**not** block FIX-641 / FIX-924 / FIX-931.

**Open questions for the human (do not block the decision):**
- **Sequencing (epic Q6).** Recommended: land 929 now, FIX-901 builds against it, dependent
  build work proceeds in parallel. The human owns whether 929 must precede, run alongside, or
  follow the dependent work — *not pre-decided here* (Decision 8).
- **Durable-state holding mechanism** for a woken host: block-state-at-agent-level vs. a
  session resource. Deferred; whatever FIX-901 lands must support either (Decision 5).

**Follow-ups (flagged, not built):**
- **Deepening opportunity — retire the reserved-but-unwired `Agent` hooks.** `usesSkills`
  ("reserved and not yet wired") and `contextMode: "fork"` ("not honored") in
  `materialize-agent.ts` are warn-only placeholders. When skill auto-load (Decision 6) and
  fork-like context supply (FIX-920) land, these should be *wired or removed*, not left as
  permanent warnings (tenet 3, subtract-as-you-go). Follow up via `improve-codebase-architecture`.
- **Already-rejected direction.** A new `Agent`/`AgentController` primitive and a nesting
  decorator tower are rejected here (Decision 1); record rather than re-litigate if they
  resurface.
