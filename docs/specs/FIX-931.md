# FIX-931: Over-spawning guard — cap total enqueued tasks before on-demand spawning — Implementation Spec

> **Issue:** [FIX-931](https://linear.app/fixpoint-labs/issue/FIX-931/over-spawning-guard-cap-total-enqueued-tasks-before-on-demand) · **Epic:** [FIX-930](https://linear.app/fixpoint-labs/issue/FIX-930/delegation-substrate-host-model-roster-and-identity-and-worker-context) (Delegation substrate) · **Sequences after:** [FIX-940](https://linear.app/fixpoint-labs/issue/FIX-940/on-demand-default-worker-delegation-floor) (on-demand default-worker floor) · **Same seam as:** [FIX-924](https://linear.app/fixpoint-labs/issue/FIX-924/roster-aware-task-assignment-manager-knows-its-workers-validate) (assignee validation)
>
> **Spec PR:** [#909](https://github.com/fixpoint-labs/flow-state-dev/pull/909) · kept in sync with this document.
>
> **Necessity verdict:** Build as scoped (small, but not trivial). No existing `taskBoard` knob bounds enqueue breadth — `concurrency` paces the parallel drain; `maxIterations` is a per-worker loop-back circuit-breaker that trips *during* a drain, after a coordinator's up-front `addTask` breadth is already committed. The real work is making the cap **atomic and intrinsic to the board's collection** (so no creation path bypasses it), not the compare itself.

---

## Part I — The Case

### 1. Problem — why it matters, why now

A coordinating agent plans work by adding tasks to its board, then draining the board to run them. Each task is an agent turn, and each turn costs tokens. Nothing today bounds how many tasks a coordinator can pile on: one off-course planning step can fire a burst of `addTask` calls, and every one eventually runs. The board's `concurrency` only paces how many run at once — it doesn't cap the total.

**Why now:** FIX-940 makes rosterless delegation the cheap default (a coordinator farms work out to a worker that materializes on demand, no roster to wire first), so unbounded `addTask` breadth becomes the easy path. Anthropic's own multi-agent research reported a lead agent spawning ~50 subagents for a trivial query, at ~15× the cost of a single chat. This is the guardrail that catches that before the board drains.

### 2. Solution in plain terms

Give the delegation board a ceiling on how many tasks it will accept, enforced when a task is created. Past that count, creation is refused with a clear message telling the coordinator to work with what it has. Under the ceiling, nothing changes.

The ceiling is **cumulative within one uninterrupted (in-request) execution** — across tool-loop steps and repeated `runBoard` passes, draining tasks to completion does **not** refund the budget, so a runaway that re-triggers inside the request can't silently earn a fresh allowance. It is deliberately **not** durable across a suspend/resume: the delegation board lives on generator own (block) state, which is in-memory only, so a resume rebuilds it empty (see §9, P2). Durable-count-across-resume is FIX-939/FIX-917 territory.

Two properties make it correct rather than leaky:

* **Intrinsic to the collection, not the tool.** The cap lives inside the delegation board's resolved collection, on **both** insertion methods (`addTask` and batch `addTasks`) — not on the model-facing `addTask` tool. A tool-seam guard would leak: the board capability also exposes batch `addTasks` and the whole ref via `tasks()`, and a below-default *override* threaded only into the executive tool would leave worker fan-out on the default. Enforcing in the collection covers every creation path — executive tool, worker fan-out, batch, the `tasks()` escape hatch — and an override applies to executive and worker alike because both resolve the same guarded collection.
* **Atomic.** Same-step framework tool calls run **concurrently** (the generator settles a step's calls with `Promise.all`), so a "read `count()`, then insert" is a time-of-check/time-of-use race. The check runs **inside the collection's existing CAS write** (`sequencer.atomicState`), which serializes concurrent adds — a burst at `cap − 1` yields exactly the cap's worth.

**The philosophy that led here.** Tenet 2 (Composition over features): reuse the collection's existing CAS write to make the cap atomic and universal, rather than a lock, a counter, or a per-call tool guard. Tenet 3 (Earn every addition): one default (100), surfaced as a board knob only because a board options object already exists (FIX-940 is extending the same object).

### 3. Tradeoffs & alternatives

The simple part is the policy — an integer ceiling; the load-bearing part is *where* and *how* it holds. Enforcing at the tool seam (the first draft) is rejected: it misses batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under an override. Enforcing in the collection's CAS `addTask`/`addTasks` closes all of those at once and is atomic for free. The delegation board is always **sequencer-backed** (own-state), whose insertion is a single whole-map CAS — so a total-count cap is atomically enforceable there. The **resource-backed** backing inserts per-task via `collection.create(...)` with no atomic whole-collection count, so it can't back a hard total cap the same way; the knob is scoped to that boundary honestly (§6.5) rather than advertising a guarantee the code can't keep.

### 4. Focus practices

* **Intrinsic + atomic is the correctness core (tenet 1, BP-035).** Cap inside the collection's CAS on `addTask` **and** `addTasks`; prove it with a concurrent-sibling test **and** a worker-fan-out-under-override test.
* **Compose at the existing seam (tenet 2).** Reuse the sequencer CAS write; the value threads via collection construction so executive + worker share one guarded collection.
* **Earn every addition (tenet 3).** Default 100; a `taskBoard({ maxTasks })` knob only because the options object exists. Validate it (finite positive integer) so a bad value can't silently disable the guard.
* **BP-003 / tenet 7 — evidence.** Mocked invariants (concurrent-sibling, batch, override-reaches-worker, validation boundaries) **and** a real-model goal check that a real coordinator's excessive fan-out is bounded and still completes.

### 5. What using it looks like

No new API for the author — the cap is intrinsic to any delegation board; a consumer constructing a board directly can override it (`taskBoard({ maxTasks })`, default 100). The only observable change is that creation is refused once the ceiling is reached, and draining doesn't reset it within the run:

```ts
// A coordinator fans out tasks (declared workers, or the FIX-940 floor).
await addTask({ goal: "part 1" });    // → { ok: true, taskId: "t_1" }
// ... up to the ceiling ...
await addTask({ goal: "part 101" });  // → { ok: false, error: "task_cap_exceeded" }  (message names the ceiling)
await runBoard();                     // the queued tasks settle (completed)
await addTask({ goal: "one more" });  // → { ok: false, error: "task_cap_exceeded" }  (completed tasks still count, in-request)
```

### 6. Decisions & rules — the sign-off surface

1. **The cap is intrinsic to the delegation board's collection — on `addTask` AND batch `addTasks` — not on the model-facing `addTask` tool.** **← core sign-off.**
   * *Rejected:* a per-call guard in the `addTask` tool handler — it misses batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under an override (the override only threads into the executive tool).
   * *Ramification:* every creation path is bounded, and an override applies to executive and worker alike (both resolve the same guarded collection). `runBoard`'s drain logic is untouched.
2. **The check is atomic — one CAS op inside the collection's insertion, checked against the freshest committed map.** **← correctness sign-off.**
   * *Rejected:* a `count()` read before the insert — same-step tool calls run concurrently (`Promise.all`), so a burst at `cap − 1` all pass the read then all insert.
   * *Ramification:* the sequencer-backed collection's `addTask`/`addTasks` reject (no-op) inside the existing `casWrite` when the map already holds `>= maxTasks`; CAS retry serializes concurrent adds, so exactly the cap's worth land. Batch `addTasks` is atomic all-or-nothing: if it would cross the cap it is rejected as a unit.
3. **The cap is cumulative within one uninterrupted (in-request) execution; NOT durable across suspend/resume.** **← scope sign-off.**
   * *Rejected:* a cross-resume guarantee — generator own (block) state is in-memory only, so a resume rebuilds the board empty and the count resets.
   * *Ramification:* "cumulative" = across tool-loop steps and repeated `runBoard` passes within the request, terminal tasks included. Durable-count → FIX-939/FIX-917.
4. **On breach, refuse creation with a soft error (`{ ok: false, error: "task_cap_exceeded" }`, clear message); don't throw, don't silently drop.**
   * *Rejected:* throwing (crashes the turn); halting the whole board (FIX-933's spend-cap shape).
   * *Ramification:* the collection returns a rejection sentinel the `addTask` handler maps to the soft error, matching the `no_delegation_board` contract; the model adapts.
5. **Default cap = 100, surfaced as `taskBoard({ maxTasks?: number })`, validated at construction (finite positive integer) and enforced on the sequencer-backed backing; the value threads via collection construction.** **← default/knob/scope sign-off (decided: 100).**
   * *Rejected:* an unrestricted `number` (`NaN`/`Infinity` make `length >= maxTasks` always false → silently unbounded; zero/negative/fractional are ambiguous) — reject non-finite / non-positive / non-integer at construction, mirroring the existing `concurrency`/`maxIterations` guards. Advertising a board-wide ceiling that resource-backed can't atomically keep — instead the knob is scoped to sequencer-backed (the delegation board always is), and setting it on a non-enforcing backing is rejected at construction rather than silently ignored.
   * *Ramification:* 100 gives headroom for legitimate decomposition/replans while bounding the runaway. The default constant lives at the enforcement layer; the delegation surface threads any override into every collection it creates for the board, so executive and worker share it.

**Non-goals:** the on-demand floor itself (FIX-940); assignee/roster validation (FIX-924); a cost/token **spend** ceiling (FIX-933 — bounds *spend*; this bounds *count*); durable count across suspend/resume (FIX-939/FIX-917); an atomic total-count cap on resource-backed boards; capping non-delegation collections by default.

**Size:** Small — an intrinsic atomic cap on the sequencer-backed collection's `addTask`/`addTasks`, a validated default + knob, guidance/docs, and tests. Single PR, no PR plan.

## Part II — The Build Plan

### 7. Technical design

Two seams: **where the check fires (intrinsic + atomic)** and **where the value comes from (construction)**.

* **Enforcement — intrinsic to the sequencer-backed collection.** `createSequencerBackedTaskCollection` (`sequencer-backed.ts`) gains an optional `maxTasks`. Both `addTask` and `addTasks` already write through `casWrite` → `sequencer.atomicState`, which reads the freshest committed task map inside the CAS; add the guard there — when `maxTasks` is set and the resulting map would hold `> maxTasks` (singular: `length >= maxTasks`; batch: `length + inits.length > maxTasks`), the mutate no-ops and the method returns a rejection sentinel instead of a `Task`/`Task[]`. CAS retry re-evaluates against the winner's committed map, so concurrent adds serialize and a burst at `cap − 1` yields exactly the cap's worth. This one place covers **every** creation path onto the board — the executive `addTask` tool, worker fan-out, the capability's batch `addTasks`, and the `tasks()` escape hatch (it returns this same guarded ref). Unset `maxTasks` = today's behavior.
* **Construction-time validation.** `maxTasks` is validated where it enters (the sequencer-backed constructor and the `taskBoard()` config, mirroring `taskBoard`'s existing `concurrency < 1` / `maxIterations < 1` throws): reject non-finite, non-positive, and non-integer, so a bad value fails loud instead of silently disabling the guard. Resource-backed can't atomically enforce a whole-count cap via per-task `create`, so `maxTasks` on a resource-backed board is rejected at construction (named boundary, not a silent no-op).
* **Value flow (no tool-seam threading).** `taskBoard({ maxTasks?: number })` is added to the board config (beside `concurrency`, `maxIterations`, FIX-940's `defaultWorker`), default 100 at the enforcement layer. `getOrCreateTaskCollection` gains a `maxTasks` common option forwarded to the sequencer-backed constructor. The delegation surface, which constructs the board's collection for **both** the executive task-tools resolver and the worker/drain (`boardCollection()`), threads the same configured value into each — so all refs over the shared own-state `atomicState` carry the cap. No per-factory threading gap; no circular import (a number flows the existing import direction).
* Only creation is guarded; `assignTask`/`updateTask` mutate existing rows and are untouched.

*Illustrative (a sketch, not the contract) — the atomic guard inside the shared CAS, singular and batch:*

```ts
// addTask(init):  reject when full
await casWrite((tasks) => {
  if (maxTasks !== undefined && Object.keys(tasks).length >= maxTasks) { rejected = true; return undefined; }
  return { ...tasks, [task.id]: task };
});
// addTasks(inits): all-or-nothing
await casWrite((tasks) => {
  if (maxTasks !== undefined && Object.keys(tasks).length + inits.length > maxTasks) { rejected = true; return undefined; }
  return { ...tasks, ...byId(built) };
});
// rejected → handler maps to { ok: false, error: "task_cap_exceeded" }
```

### 8. Implementation sequence

All one PR.

1. **Intrinsic atomic cap on the sequencer-backed collection.** Add optional `maxTasks` to `createSequencerBackedTaskCollection`; enforce inside the existing `casWrite` on **both** `addTask` and `addTasks` (batch all-or-nothing); return a rejection sentinel on breach (unset = unbounded). Validate `maxTasks` (finite positive integer) at construction. *Test:* fill to cap → reject; **concurrent-sibling** (N adds at `cap − 1` → exactly the cap's worth land); **batch** `addTasks` crossing the cap rejected as a unit; validation rejects `NaN`/`Infinity`/`0`/`-1`/`1.5`.
2. **Thread the value through construction.** Add `maxTasks` to `getOrCreateTaskCollection` common options → sequencer constructor. Add `maxTasks?: number` to `taskBoard` config (default 100, validated; rejected on resource-backed). The delegation surface threads the configured value into every collection it creates for the board (executive resolver + worker/drain `boardCollection()`). *Test:* default applies unset; an override lowers the effective cap; **worker fan-out under override** (override=5, a worker tries to exceed mid-drain → bounded).
3. **Map the rejection to the soft error.** The `addTask` tool handler maps the collection's rejection sentinel to `{ ok: false, error: "task_cap_exceeded" }` with a message naming the ceiling. *Test:* the tool returns the soft error, not a throw.
4. **Guidance copy + docs + changeset.** One clause in the delegation playbook / `addTask` description; docs per §11; `.changeset/*.md` (minor).

**Removals:** none — additive; the guard removes an unbounded path, no code deleted.

### 9. Edge cases & error handling

| Case | Expected behavior |
| -- | -- |
| `addTask` below the cap | Creates the task — unchanged. |
| `addTask` at the cap | Rejected atomically inside CAS → `task_cap_exceeded`. |
| **Concurrent burst at `cap − 1`** | Exactly `cap` total land; the rest rejected (CAS serializes them). |
| **Batch `addTasks` that would cross the cap** | Rejected all-or-nothing (no partial insert). |
| **`tasks()` escape hatch / worker fan-out** | Guarded — they use the same capped collection; an override reaches workers. |
| Cap reached, tasks then drained to terminal (same request) | Still rejected — terminal tasks count (cumulative in-request). |
| Suspend/resume between adds (P2) | Board rebuilt empty (block state in-memory) → count resets; cap is in-request only. |
| `maxTasks` = `NaN`/`Infinity`/`0`/negative/fractional | Rejected at construction (fail loud). |
| `maxTasks` on a resource-backed board | Rejected at construction (named boundary — not atomically enforceable there). |
| `assignTask`/`updateTask` at/over cap | Allowed — they mutate existing rows, create nothing. |

Error taxonomy: one new soft-error code, `task_cap_exceeded`, in the `{ ok: false, error }` family (like `no_delegation_board`); construction-time validation throws (fail-loud config error, not a soft error). No new fatal runtime path.

Second-path checklist (BP-035): **concurrency** — handled by the CAS-internal check + concurrent-sibling test. **Batch/escape-hatch** — covered because enforcement is on the collection, not the tool. **Resume/legacy** — cap is in-request; a resumed board starts fresh; no persisted field. **Off/new-state** — test unset (unbounded), default (100), override; below/at/over the cap; invalid `maxTasks`.

### 10. Testing strategy

**Discipline:** `tdd`. Both levels required (the concurrent path is real, so AGENTS.md's real-path requirement applies).

* **Mocked seam (deterministic)** — vitest at the sequencer-backed collection and `task-tools-capability.test.ts`, board seeded via `preTasks`:
  * fill to cap → `addTask` rejected (`task_cap_exceeded`); fill with **completed** tasks → still rejected (cumulative in-request).
  * **concurrent-sibling:** N `addTask` at `cap − 1` → exactly the cap's worth succeed (atomicity).
  * **batch:** `addTasks` that would cross the cap rejected as a unit; the `tasks()` escape hatch honors the cap.
  * **worker fan-out under override:** `maxTasks` override = 5, a worker attempts to exceed mid-drain → bounded.
  * **validation boundaries:** `NaN`/`Infinity`/`0`/`-1`/`1.5` rejected at construction; `maxTasks` on resource-backed rejected.
  * `assignTask`/`updateTask` unaffected; message names the ceiling.
* **Real-model goal check (required)** — `goals/` harness (`runAction` + real resolver, `openai/gpt-5.4-mini`, `AI_GATEWAY_API_KEY`), same pattern as `goals/context-supply` / `goals/skills-scoped-binding`. A real coordinator with **declared workers** (so it doesn't depend on unmerged FIX-940) prompted to over-fan-out is bounded by the cap **and** still completes coherently. Seam: a new `goals/delegation-cap` (or an added assertion on the delegation e2e check).

## Spec evolution

* **Spec drafted** — one cumulative count check at the `addTask` enqueue seam (co-located with FIX-924's assignee gate), a constant default mirroring `BOARD_CONCURRENCY`, reject-the-enqueue soft error; single small PR sequenced after FIX-940.
* **After spec review (Cursor + Codex, round 1)** — approach validated; folded: (1) **atomicity** — same-step tool calls run concurrently (`Promise.all`), so a `count()`-then-insert read is racy → moved the check inside the collection's CAS + a concurrent-sibling test; (2) **resume scope** — generator own/block state is in-memory only → scoped the cap to an uninterrupted in-request execution (durable count → FIX-939/FIX-917); (3) **default raised to 100 and made a `taskBoard({ maxTasks })` knob**; kept the real-model goal check with declared workers.
* **After spec review (Codex, round 2 — final tightening)** — made enforcement **intrinsic to the collection** rather than the tool seam: the cap lives on the sequencer-backed collection's `addTask` **and** batch `addTasks` inside the shared CAS, so it also covers the capability's batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under a below-default override (all resolve the same guarded collection); the value threads via collection construction, closing the per-factory gap. Added **construction-time `maxTasks` validation** (reject non-finite / non-positive / non-integer, mirroring `concurrency`/`maxIterations`) with boundary tests, and a worker-fan-out-under-override test. Scoped the knob honestly to the sequencer-backed backing (the delegation board always is) — resource-backed can't atomically enforce a total cap via per-task `create`, so `maxTasks` there is rejected at construction and named as a boundary rather than a silent no-op.
