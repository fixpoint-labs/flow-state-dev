# FIX-931: Over-spawning guard — cap enqueued and total tasks before on-demand spawning — Implementation Spec

> **Necessity verdict:** Build as scoped (Small). No existing `taskBoard` knob bounds enqueue breadth — `concurrency` only paces *in-flight* workers. The board needs two more bounds — how many tasks may wait enqueued at once, and how many may ever exist — and the real work is enforcing them **atomically and intrinsically in the board's collection** so no creation path bypasses them.

---

## Part I — The Case

### 1. Problem — why it matters, why now

A coordinating agent plans work by adding tasks to its board, then draining the board to run them. Each task is an agent turn, and each turn costs tokens. Nothing today bounds how many tasks a coordinator can pile on: one off-course planning step can fire a burst of `addTask` calls, and every one eventually runs. The board's `concurrency` only paces how many run *at once* — it doesn't cap how many wait in line, nor how many are created over the whole run.

**Why now:** FIX-940 makes rosterless delegation the cheap default (a coordinator farms work out to a worker that materializes on demand, no roster to wire first), so unbounded `addTask` breadth becomes the easy path. Anthropic's own multi-agent research reported a lead agent spawning ~50 subagents for a trivial query, at ~15× the cost of a single chat. This is the guardrail that catches that before the board drains.

### 2. Solution in plain terms

Bound the board along two new axes, in addition to the existing one — three limits at three different scopes:

* **`maxTotalTasks`** (default **500**) — the board's **lifetime size**: the count of *all* tasks ever in the ledger, **including terminal** (completed/errored/cancelled) ones. Cumulative within the run, **never refunded on drain**. This is the backstop that catches a drain-then-re-enqueue runaway.
* **`maxEnqueuedTasks`** (default **100**) — the **enqueue-while-outstanding** bound: at creation time, how many tasks may be *added* while others are still waiting in `pending`. It **refreshes** as tasks drain — a task leaving `pending` frees a slot for a later `addTask`. It bounds a single up-front fan-out burst, which is the runaway vector; this is the primary over-spawn guard. It is *not* a hard ceiling on concurrent `pending` (see below).
* **`concurrency`** (existing, **unchanged**) — the **in-flight** bound: max `in_progress` workers draining at once.

Roughly, *in-flight ⊆ enqueued ⊆ total* (4 / 100 / 500 by default) — an approximation that holds **at creation time**, not a hard invariant (see the honest consequence below). A coordinator that bursts past 100 pending is told to drain first, freeing enqueue slots; one that keeps re-enqueuing across drains eventually hits the 500 lifetime ceiling and is stopped for good within the run.

Two properties make the two new caps correct rather than leaky:

* **Intrinsic to the collection, not the tool.** Both caps live inside the board's resolved collection, on **every** insertion path (`addTask`, batch `addTasks`, and the `tasks()` escape-hatch ref) — not on the model-facing `addTask` tool, which the batch and escape-hatch paths bypass.
* **Atomic.** Same-step framework tool calls run **concurrently** (`Promise.all`), so a "read count, then insert" is a time-of-check/time-of-use race. Both checks run **inside the collection's existing CAS write** (`sequencer.atomicState`), evaluated against the *resulting* map, so concurrent adds serialize and a burst at a cap boundary lands exactly the cap's worth.

**The honest consequence: `maxEnqueuedTasks` is enforced only at creation.** Tasks also *re-enter* `pending` through the lifecycle — a failed task retrying under its `maxAttempts` budget, an `unblock`, a `resumeFromReview`, an expired lease `reclaim`ed. Those are **not** capped, so `pending` can transiently exceed `maxEnqueuedTasks`. We say so plainly rather than advertise a ceiling the design doesn't hold. Runaway protection rests on `maxTotalTasks` (500, cumulative, never refunded), which bounds how many tasks can ever *exist*. Note the limit of that: a retry re-pends an existing task and creates none, and `TaskInit.maxAttempts` is copied through `buildInitialTask` without schema parsing and only compared as `attempts < maxAttempts`, so `Infinity` re-pends forever while `maxTotalTasks` never moves. We therefore make **no** claim that these caps bound retry storms — a separate, pre-existing hazard (flagged in §12), not something this issue fixes. Capping re-entry was designed and rejected — see §6, decision 4.

**One resolver per board — not one per writer.** `getOrCreateTaskCollection` does **not** cache despite its name: every call constructs a fresh ref. So "the caps live in the collection" only holds if every writer for a board resolves through the *same* construction. The trace found two writers that build their own ref for the same logical board and would bypass both limits: the executive's `addTask` (the delegation surface calls `buildTaskToolsList()` with **no** resolver, falling back to `defaultOwnStateResolver`, which constructs its own uncapped ref — the primary over-spawn vector), and `ctx.cap.<board>` on a *declarative* board (the capability's request/sequencer branches call `getOrCreateTaskCollection` independently of the one `taskBoard` built). Both are fixed by convergence rather than new machinery: `buildTaskToolsList` **already accepts** a resolver, so the delegation surface passes its single `boardCollection` — the same one the workers' `createTaskToolsCapability` and `runBoard`'s drain already share — and `taskBoard` forwards its cap values into the capability it constructs. See §7's writer-path table.

**Caps are a property of the collection, not the board.** `taskBoard({ maxTotalTasks, maxEnqueuedTasks })` is sugar for the one case where the board builds the collection itself — the declarative sequencer/request-backed form — and there it constructs a capped collection. When you **supply** a collection (a `defineTaskCollection(...)` or a `collection` factory), the board applies **no caps at all**: the collection you supplied carries whatever caps it was built with and remains the sole authority. Supplying both cap options and a collection is a config error, refused at construction with a message pointing you to configure the caps where the collection is created.

**Where the knob lives for the delegation board.** Because the delegation surface constructs its own collection, the configurable knob surfaces there rather than on `taskBoard`: `SkillsLibraryOptions` gains `maxTotalTasks?` / `maxEnqueuedTasks?` beside the existing `workerModelId?` (the same shape and the same forwarding path), and the delegation surface passes them into `boardCollection()`'s `getOrCreateTaskCollection(...)`, where the **500/100 defaults are applied**. So the delegation board — the path this issue exists for — is capped by default and tunable by the app author, with no board-level cap options anywhere.

**Compatibility, stated truthfully.** This is **not** a no-op for every existing call site. Boards where `taskBoard` constructs the collection (declarative sequencer/request) now get 500/100 by default, so a board that legitimately creates more than 500 tasks in a run, or holds more than 100 pending at once, **starts being refused work with no call-site change**. That is a deliberate safety default, not an oversight — but it is a behavior change and is documented as one, with the migration path: raise or disable the caps at the collection's construction site (`taskBoard({ maxTotalTasks, maxEnqueuedTasks })`, or `getOrCreateTaskCollection` when you build the collection yourself; the delegation board via `SkillsLibraryOptions`). What *is* unchanged: any board that **supplies** its collection — durable `defineTaskCollection` boards, factory-supplied boards — and the legacy replan resolver, none of which the board caps.

**The philosophy that led here.** Tenet 2 (Composition over features): reuse the collection's existing CAS write to make both caps atomic and universal, not a lock or a per-call guard. Tenet 3 (Earn every addition): the knob is added at the two points that already construct collections — `taskBoard`'s declarative branch and `SkillsLibraryOptions` (beside `workerModelId`) — rather than inventing a new surface, and nothing is added to the paths that supply their own collection.

### 3. Tradeoffs & alternatives

The simple part is the policy — two integer bounds; the load-bearing part is *where* and *how* they hold. A single cap (an earlier draft) can't express both "one burst too wide" and "too many over the whole run" — hence two. A tool-seam guard is rejected: it misses batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under an override. Enforcing in the collection's CAS closes all of those and is atomic for free. The delegation board is always **sequencer-backed** (own-state, whole-map CAS); request-backed shares that same CAS, so both enforce. The harder question was what to do when the caller supplies the collection. Successive attempts to have the board police a collection it didn't build — reject non-enforcing backings, then brand refs with their effective cap values and match them — each broke a real path (the durable-board form; the delegation drain, itself a factory; a plain `collection: ctx => getOrCreateTaskCollection(...)` whose ref brands unset against the board's defaults) and none could be made coherent, because **a board cannot retrofit limits onto a collection it did not construct**. The rule that dissolves it: caps belong to the collection. The board only applies them when it is the one constructing. See §6, decision 6.

### 4. Focus practices

* **Intrinsic + atomic on both caps (tenet 1, BP-035).** Both checks inside the collection's CAS on `addTask` **and** `addTasks`; prove each with a concurrent-sibling test, plus a pending-refresh test (`maxEnqueuedTasks`) and a no-refund test (`maxTotalTasks`).
* **Typed breach + atomic batches, no silent drop (tenet 1).** Insertion surfaces a *typed* breach every caller must reckon with, and every batch caller inserts through one atomic `addTasks` — the `initialTasks` seed included, so a refused seed leaves the board empty rather than partially committed.
* **Earn every addition (tenet 3).** Two defaults (500/100); knobs only because the options object exists. Validate both (finite positive integer) and their relationship (`maxEnqueuedTasks ≤ maxTotalTasks`).
* **BP-003 / tenet 7 — evidence.** Mocked invariants for both caps **and** a real-model goal check that exercises both a burst hitting `maxEnqueuedTasks` and a longer loop hitting `maxTotalTasks`, bounded while still completing.

### 5. What using it looks like

No new API for the author — both caps are intrinsic to any delegation board; a consumer constructing a board directly can override them (`taskBoard({ maxTotalTasks, maxEnqueuedTasks })`, defaults 500/100). The observable change is which soft error a refused creation returns:

```ts
// Burst past the enqueued-at-once bound → drain to free slots, then continue.
for (…) await addTask({ goal });        // → ok, until 100 pending
await addTask({ goal: "one more" });     // → { ok: false, error: "enqueued_task_cap_exceeded" }  (drain first)
await runBoard();                        // pending tasks drain → enqueue slots free again
await addTask({ goal: "next wave" });    // → ok (pending back below 100)

// Across many drains, the lifetime ceiling still bites (no refund on drain).
// … after 500 tasks have existed on the board this run …
await addTask({ goal: "yet another" });  // → { ok: false, error: "total_task_cap_exceeded" }
```

### 6. Decisions & rules — the sign-off surface

1. **Three named bounds: `maxTotalTasks` (default 500, count of ALL tasks incl. terminal, cumulative-in-request, no refund), `maxEnqueuedTasks` (default 100, checked **at creation** against the `pending` count, refreshes on drain), and the unchanged `concurrency` (in-flight).** **← core sign-off.**
   * *Rejected:* one combined cap (can't express both burst-width and lifetime-size); a pending-only cap (misses the drain-then-re-enqueue runaway); a total-only cap (a single burst could still enqueue the whole 500 at once).
   * *Ramification:* the three approximate *in-flight ⊆ enqueued ⊆ total* **at creation time** — not a hard invariant, since re-entry into `pending` is uncapped (decision 4); `concurrency` is referenced, not touched.
2. **Both new caps are enforced atomically — one CAS op inside the collection's insertion, evaluated against the *resulting* map (`maxEnqueuedTasks` = would-be `pending` count; `maxTotalTasks` = would-be all-count).** **← correctness sign-off.**
   * *Rejected:* a `count()` read before insert — same-step calls run concurrently (`Promise.all`), so a burst at a boundary all pass then all insert.
   * *Ramification:* the check lives in the existing `casWrite`; CAS retry serializes concurrent adds; batch `addTasks` is atomic all-or-nothing against both caps.
3. **Both caps are intrinsic to the collection and hold on every insertion path** — singular `addTask`, batch `addTasks`, and the `tasks()` escape-hatch ref — not on the model-facing tool.
   * *Rejected:* a per-call tool-handler guard (bypassed by batch and `tasks()`, and an override wouldn't reach worker fan-out).
   * *Ramification:* an override applies to executive and worker alike (both resolve the same guarded collection); `runBoard`'s drain is untouched.
4. **`maxEnqueuedTasks` is enforced ONLY at task creation (`addTask` / batch `addTasks`). Re-entry into `pending` — `fail`-retry, `unblock`, `resumeFromReview`, `reclaim` — is NOT capped, so `pending` can transiently exceed it.** **← scope sign-off point (the honest boundary).**
   * *Rejected — designed, then abandoned:* capping re-entry by **parking** the task in `blocked` with a marker and **promoting** it back when a slot frees. Four defects sank it. (a) **Promotion never runs on the drain-exit path**: `inFlightCount` and the `complete-or-blocked` wake predicate both count only `pending`/`in_progress`/`awaiting_review`, so a parked (blocked) task makes the board look drained and it exits before another `claim` — stranding exactly the task the mechanism existed to save. (b) Parking an `in_progress`/`awaiting_review` task into `blocked` isn't in the canonical transition table, so `transitionTo` rejects it unless we silently widen a public lifecycle contract. (c) The marker would live in caller-writable `labels` (`TaskInit`, `updateTask`) — forgeable (promote an ordinary blocked task) and removable (permanently strand parked work). (d) Multi-promotion emits only the single `claim()` task-change, so promoted-but-unclaimed tasks stay rendered as blocked. A guard whose recovery path doesn't run is worse than an honest gap.
   * *Also rejected:* refusing a breaching re-entry (strands a retry / resumed review / reclaimed lease).
   * *Ramification:* no parking, no promotion, no marker, no new events, **no transition-table change** — the lifecycle is untouched. `pending` may transiently exceed `maxEnqueuedTasks` after retries/unblocks/resumes/reclaims; the nested bound is an at-creation approximation, not an invariant, and is documented that way. The hard runaway bound remains `maxTotalTasks` (task *count*, cumulative, no refund); retry storms are explicitly out of its reach (see §2 and the §12 follow-up).
5. **Breach surfaces a TYPED result both insertion methods raise and every caller handles — a `TaskCapExceededError` carrying which cap was hit; the `addTask` tool handler maps it to distinct soft codes (`enqueued_task_cap_exceeded` / `total_task_cap_exceeded`); internal batch callers propagate it (fail loud).** **← contract sign-off.**
   * *Rejected:* a bare sentinel only the tool handler maps — `createSeedCollection` (`initialTasks`) and `createApplyReplan` currently ignore insertion results, so an oversized batch would partial-insert-and-truncate silently, violating no-silent-drop.
   * *Ramification:* the CAS no-ops on breach (nothing inserted) and the method throws the typed error; the tool catches → soft error; seed/replan let it propagate loud. Consistent with the existing throw-on-duplicate-id contract.
6. **Caps are a property of the COLLECTION, not the board. `taskBoard`'s cap options apply only when `taskBoard` itself constructs the collection; a supplied collection is left entirely alone, and supplying both is a config error.** **← backing-scope sign-off.**
   * *Rejected (twice, each time it broke a real path):* having the board police a collection it didn't build. First by **rejecting non-enforcing backings** — but since the defaults are always present that disables `taskBoard({ collection: defineTaskCollection(...) })` universally, a documented and tested durable-board path. Then by **branding refs with their effective cap values and matching them** — but the delegation drain is itself a factory (so a blanket factory rule breaks every agent-declaring skill), while a plain `collection: ctx => getOrCreateTaskCollection(...)` yields a ref branded *unset* against a board holding defaults and would be rejected at runtime — even as the adjacent rule waved through genuinely *opaque* factories. Framework-created refs breaking while opaque ones survive is incoherent. The root cause is structural: **a board cannot retrofit limits onto a collection it did not construct.**
   * *Ramification:* one static rule, no runtime machinery. Declarative sequencer/request form → the board constructs a capped collection (defaults 500/100 apply). Supplied `defineTaskCollection` / factory → **no caps applied, nothing inspected, nothing rejected**; that collection is the sole authority and behaves exactly as today. Cap options + a supplied collection → **rejected at construction** with a clear message (configure the caps where the collection is created, e.g. on `getOrCreateTaskCollection`). This deletes the value-matching brand, the cap metadata on refs, the first-resolution timing caveat, the opaque-vs-branded discrimination, the resource-backed rejection, and the replan cap-provenance problem — none of them exist under this rule.
7. **Validate both caps at construction (finite positive integer) plus the relationship `maxEnqueuedTasks ≤ maxTotalTasks`; the caps are in-request only, not durable across suspend/resume.** **← validation/scope sign-off.**
   * *Rejected:* unrestricted `number` (`NaN`/`Infinity` disable the guard; zero/negative/fractional ambiguous) — reject at construction, mirroring the existing `concurrency`/`maxIterations` throws; an enqueue cap above the total ceiling is meaningless — **reject** it (documented rule, not silent clamp). A cross-resume guarantee — generator own/block state is in-memory only, so a resume rebuilds the board empty.
   * *Ramification:* "cumulative" means within one uninterrupted request; durable count → FIX-939/FIX-917.

**Non-goals:** the on-demand floor (FIX-940); assignee/roster validation (FIX-924); a cost/token **spend** ceiling (FIX-933 — bounds *spend*; these bound *count*); durable count across resume (FIX-939/FIX-917); capping collections the board didn't construct (a supplied collection carries its own caps); capping non-delegation collections by default.

**Size:** Small — two atomic caps inside the sequencer-backed collection's `addTask`/`addTasks` with a typed breach, cap options on the two construction points (`taskBoard`'s declarative branch, `SkillsLibraryOptions`), validation, guidance/docs, and tests. Single PR, no PR plan.

## Part II — The Build Plan

### 7. Technical design

Two seams: **where the checks fire (intrinsic + atomic + typed)** and **where the values come from (construction)**.

* **Enforcement — intrinsic to the sequencer-backed collection.** `createSequencerBackedTaskCollection` (`sequencer-backed.ts`) gains optional `maxTotalTasks` and `maxEnqueuedTasks`. Both `addTask` and `addTasks` already write through `casWrite` → `sequencer.atomicState`, which reads the freshest committed task map inside the CAS. Add the guard there: compute the **resulting** map's all-count and `pending`-count; if either would exceed its cap, the mutate no-ops and the method **throws a typed `TaskCapExceededError`** (`{ cap: "total" | "enqueued", limit, attempted }`) instead of returning a `Task`/`Task[]`. CAS retry re-evaluates against the winner's committed map, so concurrent adds serialize and a burst at a boundary lands exactly the cap's worth. Batch `addTasks` is all-or-nothing: if the batch would cross either cap, it throws and inserts nothing. Unset caps = today's behavior. Because request-backed reuses this same constructor (`get-or-create.ts` adapts `ctx.request` to the sequencer CAS), it inherits both caps for free.
* **Typed breach contract across all callers.** The throw (not a bare sentinel) is the contract every caller must reckon with. The `addTask` **tool handler** catches `TaskCapExceededError` and maps `cap` → `{ ok: false, error: "enqueued_task_cap_exceeded" | "total_task_cap_exceeded" }` (soft, no throw to the model). Internal batch callers must both propagate it **and insert atomically**, or "inserts nothing" is a lie. `createApplyReplan` already submits one `addTasks` call, so it inherits all-or-nothing for free. **`createSeedCollection` does not**: it loops `await collection.addTask(init)` per task, so an oversized `initialTasks` list would commit tasks up to the cap and only then throw — a partial seed. It must instead build the batch once and submit it through **one atomic `addTasks` call**. The rewrite has to preserve an easily-lost behavior: today's loop calls `collection.get(init.id)` *after* each awaited insert, so it also skips **duplicates within the same seed**. A one-time filter against only the already-present collection would let both copies reach `addTasks`, whose duplicate-id guard would then reject the **entire** seed. So build the batch with a **seen-id set seeded from the collection and updated as each init is added**, skipping within-seed duplicates exactly as before.
* **Where the caps come from.** `taskBoard({ maxTotalTasks?, maxEnqueuedTasks? })` sits beside `concurrency`/`maxIterations`/FIX-940's `defaultWorker`, and is consumed in exactly one place: the declarative branch where `taskBoard` builds the collection itself, which forwards them (defaults 500/100) to `getOrCreateTaskCollection` → the sequencer constructor. `getOrCreateTaskCollection` gains the two as common options, so anyone constructing a collection directly can cap it the same way. In the supplied-collection branches (`index.ts` normalizes a function straight into `collectionFactory`; a `DefinedTaskCollection` / ref resolves as given) the board reads no cap options and performs no check — the supplied collection is authoritative. Passing cap options together with a `collection` is a config error thrown at `taskBoard()` construction: static, immediate, no timing subtlety.
* **The delegation knob, at its real call site.** `runBoard` builds `taskBoard({ collection: () => boardCollection() })` — a supplied collection, so it takes no board-level cap options. The caps therefore ride the construction of `boardCollection()` itself (`delegation-surface.ts`), which already calls `getOrCreateTaskCollection({ backing: "sequencer", sequencer: self, … })`; it gains the two cap values, defaulted to **500/100** there. The author-facing knob is `SkillsLibraryOptions.maxTotalTasks?` / `.maxEnqueuedTasks?` — declared beside the existing `workerModelId?` (`library.ts`) and threaded through `DelegationSurfaceDeps` exactly as `workerModelId` → `defaultModelId` already is, so this reuses a live forwarding path rather than inventing one. The executive task-tools resolver and the worker/drain both resolve through `boardCollection()`, so one value covers both. The **legacy `createApplyReplan` resolver** (no `capability`) reconstructs a request-backed ref from `collectionId` alone and is therefore **uncapped by construction, exactly as today** — `ApplyReplanOptions` carries no board handle or cap fields, so it cannot know whether a board was capped, and inventing that plumbing is precisely the retrofitting this decision rejects. A capped replan must go through the `capability` path, which resolves the board's real (capped) collection. That is a documented limitation, not a silent bypass.
* **Creation only — the lifecycle is untouched.** `claim` moves a task `pending → in_progress`, freeing a `maxEnqueuedTasks` slot for a later `addTask`. The transitions that move tasks *back* into `pending` (`fail()` on the retry branch, `unblock()`, `resumeFromReview()`, `reclaim()`) are deliberately **not** capped (decision 4), so no re-pend path, transition-table entry, status marker, or task-change event changes. `assignTask`/`updateTask` mutate existing rows without changing status and are untouched too.

*Illustrative (a sketch, not the contract) — both caps inside the shared CAS:*

```ts
// inside casWrite((tasks) => { ... }) for addTask/addTasks — check the RESULTING map
const next = { ...tasks, ...built };
const total = Object.keys(next).length;
const pending = Object.values(next).filter((t) => t.status === "pending").length;
if (maxTotalTasks    !== undefined && total   > maxTotalTasks)    throw new TaskCapExceededError({ cap: "total" });
if (maxEnqueuedTasks !== undefined && pending > maxEnqueuedTasks) throw new TaskCapExceededError({ cap: "enqueued" });
return next; // tool handler catches the throw → distinct soft codes; seed/replan propagate
```

### 8. Implementation sequence

All one PR.

1. **Typed breach + both caps on the sequencer-backed collection.** Add `TaskCapExceededError` (typed `cap` discriminant) and optional `maxTotalTasks`/`maxEnqueuedTasks` to `createSequencerBackedTaskCollection`; enforce both inside the existing `casWrite` on `addTask` and `addTasks` (batch all-or-nothing), evaluated against the resulting map; validate both caps + `maxEnqueuedTasks ≤ maxTotalTasks` at construction. *Test:* each cap — fill/burst → throw; concurrent-sibling atomicity; pending-refresh frees an enqueued slot; terminal tasks still count toward total (no refund); batch crossing either cap all-or-nothing; validation boundaries.
2. **Make internal callers atomic + loud, without losing idempotency.** Rework `createSeedCollection` from its per-task `addTask` loop to one atomic `addTasks`, building the batch with a **seen-id set seeded from the collection and updated per init** — so already-present IDs *and* within-seed duplicates are both skipped, exactly as the old loop did (it re-read `collection.get` after each awaited insert). `createApplyReplan` already uses a single `addTasks` and needs no change — its legacy resolver stays uncapped by construction (documented, §7). Neither swallows the typed error. *Test:* an oversized `initialTasks` seed throws **and leaves the board empty**; a re-seed with existing stable IDs still skips them; **a duplicate stable ID *within* one `initialTasks` list is skipped, not a whole-seed rejection** (regression guard); an oversized replan batch on a capped (capability-resolved) collection throws and inserts nothing.
3. **Surface the caps where collections are constructed.** Add both caps to `getOrCreateTaskCollection`'s common options → sequencer constructor. Add them to `taskBoard` config, consumed **only** in the declarative branch that builds the collection (defaults 500/100); in the supplied-collection branches read nothing and check nothing, and throw at construction if cap options accompany a `collection`. Add `maxTotalTasks?`/`maxEnqueuedTasks?` to `SkillsLibraryOptions`, threaded through `DelegationSurfaceDeps` into `boardCollection()` (defaults 500/100 applied there) — mirroring the existing `workerModelId` → `defaultModelId` path. *Test:* declarative board applies defaults; an override bites; **cap options + a supplied `collection` → construction error**; each supplied-collection form (`defineTaskCollection`, `ctx => getOrCreateTaskCollection(...)`, a plain ref) constructs and behaves **exactly as today**; **the delegation board still enforces its caps** (default and overridden), including worker fan-out.
4. **Map to soft errors + guidance + docs + changeset.** The `addTask` tool handler catches `TaskCapExceededError` → `enqueued_task_cap_exceeded` / `total_task_cap_exceeded`. One clause in the delegation playbook / `addTask` description (drain to free enqueue slots; lifetime ceiling). Docs per §11; `.changeset/*.md` (minor).

**Removals:** none — additive; the guards remove unbounded paths, no code deleted.

### 9. Edge cases & error handling

| Case | Expected behavior |
| -- | -- |
| `addTask` below both caps | Creates the task — unchanged. |
| `pending` at `maxEnqueuedTasks` | `addTask` throws → `enqueued_task_cap_exceeded`; **drains free slots** (refresh). |
| All-count at `maxTotalTasks` (even after draining) | `addTask` throws → `total_task_cap_exceeded`; terminal tasks count (no refund). |
| **Re-entry into `pending`** (`fail`-retry, `unblock`, `resumeFromReview`, `reclaim`) | Proceeds normally — **not capped**. `pending` may transiently exceed `maxEnqueuedTasks`. `maxTotalTasks` bounds task *count*, not retries (a retry creates no task). |
| **Concurrent burst at either boundary** | Exactly the cap's worth land; the rest rejected (CAS serializes). |
| **Batch `addTasks` crossing either cap** | Rejected all-or-nothing (typed throw; no partial insert). |
| **`initialTasks` seed / replan batch oversized** | Fails loud (propagated typed error) **and inserts nothing** — the seed submits one atomic `addTasks`, so it can't partially commit. |
| **`tasks()` escape hatch / worker fan-out** | Guarded — same capped collection; an override reaches workers. |
| Suspend/resume between adds | Board rebuilt empty (block state in-memory) → counts reset; caps are in-request only. |
| Either cap `NaN`/`Infinity`/`0`/negative/fractional, or `maxEnqueuedTasks > maxTotalTasks` | Rejected at construction (fail loud). |
| **Any supplied collection** — `defineTaskCollection` or a `collection` factory | **Unchanged from today** — no caps applied, nothing inspected, nothing rejected. That collection is the sole authority. |
| Cap options passed **together with** a `collection` | Rejected at `taskBoard()` construction with a clear message: configure the caps where the collection is created. |
| Delegation board (`runBoard`) | Capped — its collection is constructed with the caps by the delegation surface (defaults 500/100, tunable via `SkillsLibraryOptions`). |
| Legacy `createApplyReplan` without `capability` | Uncapped by construction, exactly as today — documented limitation; capped replans use the `capability` resolver. |
| **Duplicate stable ID within one `initialTasks` list** | Skipped (not a whole-seed rejection) — the atomic seed keeps a running seen-id set, matching the old loop. |
| `assignTask`/`updateTask` at/over a cap | Allowed — they mutate existing rows, create nothing. |

Error taxonomy: two new soft-error codes (`enqueued_task_cap_exceeded`, `total_task_cap_exceeded`) in the `{ ok: false, error }` family; one typed `TaskCapExceededError` at the collection boundary (caught by the tool, propagated by internal callers); construction-time validation throws. No new fatal runtime path to the model.

Second-path checklist (BP-035): **concurrency** — both CAS-internal checks + concurrent-sibling tests. **Re-entry** — deliberately uncapped (decision 4); the resulting transient overshoot of `maxEnqueuedTasks` is documented, not silently assumed away. **Batch/escape-hatch/internal-callers** — covered because enforcement is on the collection and the breach is typed (seed/replan propagate). **Resume/legacy** — caps in-request; a resumed board starts fresh; no persisted field. **Off/new-state** — test unset (unbounded), defaults, overrides; below/at/over each cap; the refresh vs no-refund distinction; invalid configs.

## Spec evolution

* **Spec drafted** — one cumulative count check at the `addTask` enqueue seam (co-located with FIX-924's assignee gate), a constant default mirroring `BOARD_CONCURRENCY`, reject-the-enqueue soft error; single small PR sequenced after FIX-940.
* **After spec review (Cursor + Codex, round 1)** — folded: atomicity (same-step calls run concurrently → check inside the collection CAS + concurrent-sibling test); in-request scope (generator own/block state is in-memory only → dropped the cross-resume claim, durable count → FIX-939/FIX-917); default raised and made a `taskBoard` knob; kept the real-model goal check with declared workers.
* **After spec review (Codex, round 2)** — made enforcement **intrinsic to the collection** (not the tool seam), covering batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under an override; added construction-time validation and named the sequencer-backed boundary.
* **After owner re-architecture (round 3)** — replaced the single cap with a **three-bound model**: `maxTotalTasks` (500, all-count incl. terminal, no refund — the lifetime backstop), `maxEnqueuedTasks` (100, `pending`-count, refreshes on drain — the primary burst guard), and the unchanged `concurrency` (in-flight). Both new caps enforced atomically + intrinsically on every insertion path with **distinct** soft codes. Folded the two round-3 Codex P2s: (a) a **typed breach** (`TaskCapExceededError`) both insertion methods raise and every caller handles — `createSeedCollection` and `createApplyReplan` now fail loud instead of partial-insert-and-truncate; (b) reject the caps on **resource-backed AND the custom-factory** collection form (not just resource), since a factory passes its ref through the capped constructor unchanged. Added `maxEnqueuedTasks ≤ maxTotalTasks` sanity validation and a two-cap real-model goal check.
* **After spec review (Codex, round 4)** — tried to close the gap that `maxEnqueuedTasks` refreshes on drain, so tasks re-entering `pending` (`fail`-retry, `unblock`, `resumeFromReview`, `reclaim`) could exceed it: enforced the cap on every transition into `pending` with **queue-behind** (park in `blocked` with a marker, promote back when a slot frees).
* **After spec review (Codex, round 5 — simplify)** — round 4's park-and-promote re-entry cap was **removed, not fixed**: review found four defects, the first fatal. Promotion rode `claim`'s CAS, but `inFlightCount` and the `complete-or-blocked` wake predicate count only `pending`/`in_progress`/`awaiting_review`, so a parked (blocked) task makes the board look drained and it exits before another `claim` — stranding exactly the task the mechanism existed to save. It also required parking `in_progress`/`awaiting_review` into `blocked` (not in the canonical transition table), a marker living in caller-writable `labels` (forgeable, removable), and multi-promotion that emitted no task-change for promoted-but-unclaimed tasks. Four defects in one mechanism is a signal to simplify: **`maxEnqueuedTasks` is now enforced only at creation**, re-entry proceeds normally, and the transient overshoot is **documented honestly** rather than papered over — the nested bound is stated as an at-creation approximation, not an invariant. Runaway protection is unchanged (`maxTotalTasks`, cumulative and never refunded, bounds the run; retry storms bounded by `maxAttempts` × total). Park/promote/per-re-entry-path tests dropped for one test locking in the uncapped-re-entry semantics; size back to Small.
* **After spec review (Codex, round 6 — two corrections)** — fixed a P1 that would have shipped a broken feature and a P2 that made an advertised guarantee false. **(P1)** The backing rule rejected the *factory* collection form outright, but the delegation drain builds itself as `taskBoard({ collection: () => boardCollection() })` — the factory form — while `boardCollection()` returns the sequencer-backed ledger, so the guard would have failed while materializing `runBoard` and broken every agent-declaring skill. The rule now discriminates on **what the factory returns**, and on **whether its caps match**: the capped constructor brands its refs with the effective cap values, and the board compares them to its own — a boolean "is cap-enforcing" brand proved insufficient, since the board passes a factory's ref through unchanged and so would have advertised a ceiling (say 5) that a ref built with 500, or with caps unset, never enforces. Declarative resource-backed is rejected at construction; a factory is checked on first resolution and accepted only on a values match, rejected on mismatch (unset-on-ref included) or when unbranded. **(P2)** `createSeedCollection` loops `await collection.addTask(init)` per task, so an oversized `initialTasks` list would commit up to the cap and only then throw, contradicting the spec's all-or-nothing promise; the seed path now filters already-present stable IDs and submits the remainder through **one atomic `addTasks`** (`createApplyReplan` already did, so it inherits it). Tests updated: the internal delegation board constructs fine with default caps and still enforces them, a branded-but-mismatched factory is rejected, and the oversized-seed test asserts the board is left **empty**, not merely that it threw.
* **After spec review (Codex, round 7 — correctness pass)** — three fixes, two of them consequences of earlier rounds. **(P1, breaking)** Because the 500/100 defaults are always present, "reject a non-enforcing backing when caps apply" would have disabled `taskBoard({ collection: defineTaskCollection(...) })` **universally** — a documented (`task-board.md`), tested (`task-board.test.ts`) durable-board path — making an additive guard a breaking change. Now **defaults apply only where enforceable**: a non-enforcing backing with no explicit caps keeps today's unbounded behavior untouched, and only an *explicit* cap request there is refused. **(P2)** Round 6's atomic-seed instruction would have regressed duplicate-ID idempotency: the old loop re-read `collection.get` after each awaited insert, so it skipped duplicates *within* one `initialTasks` list, whereas a one-time pre-filter lets both copies reach `addTasks` and its duplicate-id guard rejects the entire seed. The batch is now built with a running seen-id set, with a regression test. **(P2)** `createApplyReplan`'s legacy resolver reconstructs a request-backed ref from `collectionId` alone, carrying no cap values, so it could batch past both ceilings into the same board state; a capped replan must now use the board `capability` resolver (chosen over threading cap values through `ApplyReplanOptions` — one construction-time check instead of new public option surface, and the capability path already resolves the board's real capped collection).
* **After spec review (Codex, round 8 — collapse the seam)** — the third failure on the same seam ended the approach rather than patching it. Value-matching would have rejected an existing `collection: ctx => getOrCreateTaskCollection(...)` (branded *unset* against a board holding the 500/100 defaults — `task-board.test.ts:200-207`) while the adjacent rule waved through genuinely *opaque* factories: framework-created refs breaking while opaque ones survive. And `ApplyReplanOptions` carries no board handle or cap fields, so "reject only explicitly-capped legacy replans" was unimplementable without exactly the plumbing the design was trying to avoid. Root cause: **a board cannot retrofit limits onto a collection it did not construct.** New rule — **caps belong to the collection**: `taskBoard`'s cap options apply only when `taskBoard` builds the collection (declarative sequencer/request), a supplied collection is left entirely alone (no defaults, no inspection, no rejection), and passing both is a static config error. This **deleted** the value-matching brand, the cap metadata on refs, the first-resolution timing caveat, the opaque-vs-branded discrimination, the resource-backed rejection, and the replan cap-provenance machinery. The knob for the path that matters moves to its real construction site: `SkillsLibraryOptions.maxTotalTasks?`/`.maxEnqueuedTasks?` (beside the existing `workerModelId?`), threaded into the delegation surface's `boardCollection()` where the 500/100 defaults apply — so the delegation board stays capped-by-default and tunable, while durable boards, factory-supplied boards, and the legacy replan resolver are untouched.
