# FIX-931: Over-spawning guard — cap enqueued and total tasks before on-demand spawning — Implementation Spec

> **Spec PR:** [#909](https://github.com/fixpoint-labs/flow-state-dev/pull/909) · kept in sync with this document.

> **Necessity verdict:** Build as scoped (Medium). No existing `taskBoard` knob bounds enqueue breadth — `concurrency` only paces *in-flight* workers. The board needs two more bounds — how many tasks may wait enqueued at once, and how many may ever exist — and the real work is enforcing them **atomically and intrinsically in the board's collection**, on every path a task enters or re-enters the queue.

---

## Part I — The Case

### 1. Problem — why it matters, why now

A coordinating agent plans work by adding tasks to its board, then draining the board to run them. Each task is an agent turn, and each turn costs tokens. Nothing today bounds how many tasks a coordinator can pile on: one off-course planning step can fire a burst of `addTask` calls, and every one eventually runs. The board's `concurrency` only paces how many run *at once* — it doesn't cap how many wait in line, nor how many are created over the whole run.

**Why now:** FIX-940 makes rosterless delegation the cheap default (a coordinator farms work out to a worker that materializes on demand, no roster to wire first), so unbounded `addTask` breadth becomes the easy path. Anthropic's own multi-agent research reported a lead agent spawning ~50 subagents for a trivial query, at ~15× the cost of a single chat. This is the guardrail that catches that before the board drains.

### 2. Solution in plain terms

Bound the board along two new axes, in addition to the existing one — three limits that read as a nested hierarchy:

* **`maxTotalTasks`** (default **500**) — the board's **lifetime size**: the count of *all* tasks ever in the ledger, **including terminal** (completed/errored/cancelled) ones. Cumulative within the run, **never refunded on drain**. This is the backstop that catches a drain-then-re-enqueue runaway.
* **`maxEnqueuedTasks`** (default **100**) — the **enqueued-at-once** bound: the count of tasks currently in `pending` status (waiting to be claimed). This **refreshes** as tasks drain — a task leaving `pending` frees a slot. It bounds a single fan-out burst; this is the primary over-spawn guard.
* **`concurrency`** (existing, **unchanged**) — the **in-flight** bound: max `in_progress` workers draining at once.

So: *in-flight now ⊆ enqueued now ⊆ total ever* (4 ⊆ 100 ⊆ 500 by default). A coordinator that bursts past 100 pending is told to drain first (freeing enqueue slots); one that keeps re-enqueuing across drains eventually hits the 500 lifetime ceiling and is stopped for good within the run.

Three properties make the two new caps correct rather than leaky:

* **Intrinsic to the collection, not the tool.** Both caps live inside the board's resolved collection, on **every** insertion path (`addTask`, batch `addTasks`, and the `tasks()` escape-hatch ref) — not on the model-facing `addTask` tool, which the batch and escape-hatch paths bypass.
* **Atomic.** Same-step framework tool calls run **concurrently** (`Promise.all`), so a "read count, then insert" is a time-of-check/time-of-use race. Both checks run **inside the collection's existing CAS write** (`sequencer.atomicState`), evaluated against the *resulting* map, so concurrent adds serialize and a burst at a cap boundary lands exactly the cap's worth.
* **`maxEnqueuedTasks` holds on every entry into `pending`, not just creation.** Because it refreshes as tasks drain, tasks that *re-enter* `pending` — a failed task retrying, an unblock, a resume-from-review, an expired lease reclaimed — would otherwise push the queue past the ceiling. (Repro at cap 1: claim A, which frees the slot; add B, which fills it; A fails and re-pends → 2 pending.) Left unguarded the pending queue could grow to `maxTotalTasks`, breaking the nested bound above. So the same CAS-internal check runs on the re-entry transitions too — with different handling, because re-entry is not new work (below).

**New work is refused; existing work is deferred, never lost.** A creation that would breach is rejected outright — that is the over-spawn guard doing its job. A *re-entry* is a task that already exists and is already counted against `maxTotalTasks`; refusing it would strand real work (a retry silently dropped, a resumed review lost). So a re-entry that would breach is **queued behind**: the task parks in the existing `blocked` status carrying a cap marker, and is promoted back to `pending` automatically as soon as a slot frees. Nothing is stranded, and the ceiling stays honest.

**The philosophy that led here.** Tenet 2 (Composition over features): reuse the collection's existing CAS write to make both caps atomic and universal, not a lock or a per-call guard. Tenet 3 (Earn every addition): sensible defaults surfaced as board knobs only because a board options object already exists (FIX-940 is extending the same object).

### 3. Tradeoffs & alternatives

The simple part is the policy — two integer bounds; the load-bearing part is *where* and *how* they hold. A single cap (an earlier draft) can't express both "one burst too wide" and "too many over the whole run" — hence two. A tool-seam guard is rejected: it misses batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under an override. Enforcing in the collection's CAS closes all of those and is atomic for free. The delegation board is always **sequencer-backed** (own-state, whole-map CAS); request-backed shares that same CAS, so both enforce. **Resource-backed** (per-task `create`) and the **custom-factory** collection form can't atomically enforce a whole-count, so the caps are rejected there at construction (§6, decision 6) rather than advertising a guarantee the code can't keep.

### 4. Focus practices

* **Intrinsic + atomic on both caps (tenet 1, BP-035).** Both checks inside the collection's CAS on `addTask` **and** `addTasks`; prove each with a concurrent-sibling test, plus a pending-refresh test (`maxEnqueuedTasks`) and a no-refund test (`maxTotalTasks`).
* **Guard every entry into `pending`, not just creation (tenet 1).** A cap that refreshes is only true if re-entry respects it too. Cover all four re-entry paths (`fail`-retry, `unblock`, `resumeFromReview`, `reclaim`) — with queue-behind, so recovery is never lost.
* **Typed breach, no silent drop (tenet 1).** Insertion surfaces a *typed* breach every caller must reckon with — internal batch callers (`initialTasks` seed, replan) fail loud, they don't partial-insert-and-truncate.
* **Earn every addition (tenet 3).** Two defaults (500/100); knobs only because the options object exists. Validate both (finite positive integer) and their relationship (`maxEnqueuedTasks ≤ maxTotalTasks`).
* **BP-003 / tenet 7 — evidence.** Mocked invariants for both caps **and** a real-model goal check that exercises both a burst hitting `maxEnqueuedTasks` and a longer loop hitting `maxTotalTasks`, bounded while still completing.

### 5. What using it looks like

No new API for the author — both caps are intrinsic to any delegation board; a consumer constructing a board directly can override them (`taskBoard({ maxTotalTasks, maxEnqueuedTasks })`, defaults 500/100). The observable change is which soft error a refused creation returns:

```ts
// Burst past the enqueued-at-once bound → drain to free slots, then continue.
for (…) await addTask({ goal });        // → ok, until 100 pending
await addTask({ goal: "one more" });     // → { ok: false, error: "enqueued_task_cap_exceeded" }  (drain first)
await runBoard();                        // pending tasks drain → enqueue slots free again
await addTask({ goal: "next wave" });    // → ok (pending back below 100)

// Across many drains, the lifetime ceiling still bites (no refund on drain).
// … after 500 tasks have existed on the board this run …
await addTask({ goal: "yet another" });  // → { ok: false, error: "total_task_cap_exceeded" }
```

### 6. Decisions & rules — the sign-off surface

1. **Three named bounds: `maxTotalTasks` (default 500, count of ALL tasks incl. terminal, cumulative-in-request, no refund), `maxEnqueuedTasks` (default 100, count of `pending` tasks, refreshes on drain), and the unchanged `concurrency` (in-flight).** **← core sign-off.**
   * *Rejected:* one combined cap (can't express both burst-width and lifetime-size); a pending-only cap (misses the drain-then-re-enqueue runaway); a total-only cap (a single burst could still enqueue the whole 500 at once).
   * *Ramification:* the three form *in-flight ⊆ enqueued ⊆ total*; `concurrency` is referenced, not touched.
2. **Both new caps are enforced atomically — one CAS op inside the collection's insertion, evaluated against the *resulting* map (`maxEnqueuedTasks` = would-be `pending` count; `maxTotalTasks` = would-be all-count).** **← correctness sign-off.**
   * *Rejected:* a `count()` read before insert — same-step calls run concurrently (`Promise.all`), so a burst at a boundary all pass then all insert.
   * *Ramification:* the check lives in the existing `casWrite`; CAS retry serializes concurrent adds; batch `addTasks` is atomic all-or-nothing against both caps.
3. **Both caps are intrinsic to the collection and hold on every insertion path** — singular `addTask`, batch `addTasks`, and the `tasks()` escape-hatch ref — not on the model-facing tool.
   * *Rejected:* a per-call tool-handler guard (bypassed by batch and `tasks()`, and an override wouldn't reach worker fan-out).
   * *Ramification:* an override applies to executive and worker alike (both resolve the same guarded collection); `runBoard`'s drain is untouched.
4. **`maxEnqueuedTasks` is additionally enforced on every transition INTO `pending` — `fail`-with-retry, `unblock`, `resumeFromReview`, and lease `reclaim` — and a breaching re-entry is QUEUED BEHIND (parks in `blocked` with a cap marker, auto-promoted to `pending` when a slot frees), not refused.** **← re-entry sign-off point.**
   * *Rejected:* **guarding creation only** — the cap refreshes on drain, so re-entry would breach it (at cap 1: claim A → add B → A fails and re-pends → 2 pending), and the pending queue could grow to `maxTotalTasks`, falsifying the nested bound in Decision 1. **Refusing the re-entry loudly** — it strands real work: a retry silently dropped, a resumed review lost, a reclaimed lease never re-run. **Allowing re-entry to exceed** (documented exception) — re-breaks the ceiling.
   * *Why queue-behind for all four rather than a model/framework split:* the split doesn't survive the code. `unblock`/`resumeFromReview` are **not** exposed as model tools at all (the eight are `addTask`/`assignTask`/`completeTask`/`failTask`/`blockTask`/`cancelTask`/`updateTask`/`listTasks`), and `fail` is **both** model-initiated (the `failTask` tool) and framework-initiated (worker rescue in `record-result`, `dispatch-and-execute`, `routedSpecialists`). The rule that does hold: **creation is new breadth (refuse); re-entry is an existing task already counted against `maxTotalTasks` (defer, never lose).** One uniform rule, no caller-origin sniffing.
   * *Ramification:* `blocked` is the substrate's existing "parked pending an external condition" state and `blocked → pending` is already a legal transition, so no new status is introduced; `onIdle: "complete-or-blocked"` already treats blocked as unresolved, so a cap-parked task surfaces rather than vanishing. Promotion happens inside `claim`'s CAS (which already runs every drain poll), so it is atomic and needs no new loop.
5. **Breach surfaces a TYPED result both insertion methods raise and every caller handles — a `TaskCapExceededError` carrying which cap was hit; the `addTask` tool handler maps it to distinct soft codes (`enqueued_task_cap_exceeded` / `total_task_cap_exceeded`); internal batch callers propagate it (fail loud).** **← contract sign-off.**
   * *Rejected:* a bare sentinel only the tool handler maps — `createSeedCollection` (`initialTasks`) and `createApplyReplan` currently ignore insertion results, so an oversized batch would partial-insert-and-truncate silently, violating no-silent-drop.
   * *Ramification:* the CAS no-ops on breach (nothing inserted) and the method throws the typed error; the tool catches → soft error; seed/replan let it propagate loud. Consistent with the existing throw-on-duplicate-id contract.
6. **Both caps are enforced only on the sequencer-CAS backings (sequencer + request, which share `createSequencerBackedTaskCollection`); rejected at construction on resource-backed and the custom-factory collection form.** **← backing-scope sign-off.**
   * *Rejected:* silently ignoring the caps on backings that can't atomically enforce a whole-count (resource-backed's per-task `create`; a factory that passes its ref through unchanged, never hitting the capped constructor).
   * *Ramification:* the delegation board is always sequencer-backed, so this only constrains direct `taskBoard()` consumers; both caps are documented sequencer-backed-only.
7. **Validate both caps at construction (finite positive integer) plus the relationship `maxEnqueuedTasks ≤ maxTotalTasks`; the caps are in-request only, not durable across suspend/resume.** **← validation/scope sign-off.**
   * *Rejected:* unrestricted `number` (`NaN`/`Infinity` disable the guard; zero/negative/fractional ambiguous) — reject at construction, mirroring the existing `concurrency`/`maxIterations` throws; an enqueue cap above the total ceiling is meaningless — **reject** it (documented rule, not silent clamp). A cross-resume guarantee — generator own/block state is in-memory only, so a resume rebuilds the board empty.
   * *Ramification:* "cumulative" means within one uninterrupted request; durable count → FIX-939/FIX-917.

**Non-goals:** the on-demand floor (FIX-940); assignee/roster validation (FIX-924); a cost/token **spend** ceiling (FIX-933 — bounds *spend*; these bound *count*); durable count across resume (FIX-939/FIX-917); atomic caps on resource-backed / factory boards; capping non-delegation collections by default.

**Size:** Medium — two intrinsic atomic caps across the sequencer-backed collection's insertion **and** re-entry transitions (with queue-behind + promotion in `claim`), a typed breach, validated defaults + knobs, guidance/docs, and tests. Single PR, no PR plan.

## Part II — The Build Plan

### 7. Technical design

Two seams: **where the checks fire (intrinsic + atomic + typed)** and **where the values come from (construction)**.

* **Enforcement — intrinsic to the sequencer-backed collection.** `createSequencerBackedTaskCollection` (`sequencer-backed.ts`) gains optional `maxTotalTasks` and `maxEnqueuedTasks`. Both `addTask` and `addTasks` already write through `casWrite` → `sequencer.atomicState`, which reads the freshest committed task map inside the CAS. Add the guard there: compute the **resulting** map's all-count and `pending`-count; if either would exceed its cap, the mutate no-ops and the method **throws a typed `TaskCapExceededError`** (`{ cap: "total" | "enqueued", limit, attempted }`) instead of returning a `Task`/`Task[]`. CAS retry re-evaluates against the winner's committed map, so concurrent adds serialize and a burst at a boundary lands exactly the cap's worth. Batch `addTasks` is all-or-nothing: if the batch would cross either cap, it throws and inserts nothing. Unset caps = today's behavior. Because request-backed reuses this same constructor (`get-or-create.ts` adapts `ctx.request` to the sequencer CAS), it inherits both caps for free.
* **Typed breach contract across all callers.** The throw (not a bare sentinel) is the contract every caller must reckon with. The `addTask` **tool handler** catches `TaskCapExceededError` and maps `cap` → `{ ok: false, error: "enqueued_task_cap_exceeded" | "total_task_cap_exceeded" }` (soft, no throw to the model). Internal batch callers that currently ignore the insertion result — `createSeedCollection` (`initialTasks`) and `createApplyReplan` (`apply-replan.ts` `addTasks`) — let it propagate, so an oversized seed/replan batch fails loud instead of partial-inserting-and-truncating.
* **Construction-time validation.** In the sequencer constructor and the `taskBoard()` config (mirroring `taskBoard`'s existing `concurrency < 1` / `maxIterations < 1` throws): reject non-finite, non-positive, non-integer for each cap, and reject `maxEnqueuedTasks > maxTotalTasks`. Reject either cap on a **resource-backed** or **factory** collection (they can't atomically enforce a whole-count) — a named boundary, not a silent no-op.
* **Value flow (no tool-seam threading).** `taskBoard({ maxTotalTasks?, maxEnqueuedTasks? })` are added to the board config beside `concurrency`/`maxIterations`/FIX-940's `defaultWorker`, defaults 500/100 at the enforcement layer. `getOrCreateTaskCollection` gains the two as common options forwarded to the sequencer constructor. The delegation surface, which constructs the board's collection for **both** the executive task-tools resolver and the worker/drain (`boardCollection()`), threads the same values into each — so all refs over the shared own-state `atomicState` carry both caps, and any override reaches executive and worker alike.
* **Re-entry into `pending` (the refresh's other half).** `claim` moves a task `pending → in_progress`, which is what frees a `maxEnqueuedTasks` slot — so the cap must also hold where tasks move *back*. Four transitions re-pend, all already routed through `transitionTo`/`casWrite` in `sequencer-backed.ts`: `fail()` on the retry branch (`shouldRetryOnFail`), `unblock()`, `resumeFromReview()`, and `reclaim()` (expired lease). Each gains the same CAS-internal `pending`-count check, but with **queue-behind** rather than refusal: if the target would exceed `maxEnqueuedTasks`, the transition instead lands the task in `blocked` with a reserved cap marker (e.g. a `__enqueue_cap__` label) and the existing `error`/`feedback` payload preserved, so the retry's feedback or the review's resolution isn't lost. `reclaim` parks the same way instead of returning the task to `pending`.
* **Promotion (queue-behind's other half).** `claim` already performs a CAS write and already knows the freshest map, and the board polls it every `idlePollMs` while draining. Inside that same CAS, before candidate selection, promote up to `maxEnqueuedTasks − pending` cap-marked `blocked` tasks back to `pending` (oldest first, marker cleared). That makes promotion atomic, ordered, and free of any new loop or timer. A board that terminates with cap-parked tasks still reports them via `onIdle: "complete-or-blocked"` (`terminationReason: blocked-by-failures`), so they are visible, never silently dropped.
* `assignTask`/`updateTask` mutate existing rows without changing status and are untouched.

*Illustrative (a sketch, not the contract) — both caps inside the shared CAS:*

```ts
// inside casWrite((tasks) => { ... }) for addTask/addTasks — check the RESULTING map
const next = { ...tasks, ...built };
const total = Object.keys(next).length;
const pending = Object.values(next).filter((t) => t.status === "pending").length;
if (maxTotalTasks    !== undefined && total   > maxTotalTasks)    throw new TaskCapExceededError({ cap: "total" });
if (maxEnqueuedTasks !== undefined && pending > maxEnqueuedTasks) throw new TaskCapExceededError({ cap: "enqueued" });
return next; // tool handler catches the throw → distinct soft codes; seed/replan propagate
```

### 8. Implementation sequence

All one PR.

1. **Typed breach + both caps on the sequencer-backed collection.** Add `TaskCapExceededError` (typed `cap` discriminant) and optional `maxTotalTasks`/`maxEnqueuedTasks` to `createSequencerBackedTaskCollection`; enforce both inside the existing `casWrite` on `addTask` and `addTasks` (batch all-or-nothing), evaluated against the resulting map; validate both caps + `maxEnqueuedTasks ≤ maxTotalTasks` at construction. *Test:* each cap — fill/burst → throw; concurrent-sibling atomicity; pending-refresh frees an enqueued slot; terminal tasks still count toward total (no refund); batch crossing either cap all-or-nothing; validation boundaries.
2. **Guard re-entry into `pending` + promotion.** Apply the same CAS-internal `pending`-count check to the four re-pend transitions (`fail`-retry, `unblock`, `resumeFromReview`, `reclaim`); on breach, park in `blocked` with the cap marker (preserving `error`/`feedback`) instead of re-pending. Add promotion inside `claim`'s CAS: before candidate selection, promote up to `maxEnqueuedTasks − pending` cap-marked tasks (oldest first, marker cleared). *Test:* the cap-1 repro (claim A → add B → A fails/re-pends → pending never exceeds 1, A parked); one per re-entry path (`unblock`, `resumeFromReview`, `reclaim`); promotion restores a parked task once a slot frees; a parked task is never lost across a drain.
3. **Make internal callers fail loud.** Ensure `createSeedCollection` (`initialTasks`) and `createApplyReplan` propagate the typed error (no swallow, no partial insert). *Test:* an oversized `initialTasks`/replan batch throws at construction/replan, inserts nothing.
4. **Thread values + backing rejection.** Add both caps to `getOrCreateTaskCollection` common options → sequencer constructor, and to `taskBoard` config (defaults 500/100). Reject both on resource-backed and factory forms at `taskBoard()` construction. The delegation surface threads the values into every collection it creates for the board. *Test:* defaults apply unset; overrides bite; worker fan-out under an override bounded; caps on resource/factory backings rejected.
5. **Map to soft errors + guidance + docs + changeset.** The `addTask` tool handler catches `TaskCapExceededError` → `enqueued_task_cap_exceeded` / `total_task_cap_exceeded`. One clause in the delegation playbook / `addTask` description (drain to free enqueue slots; lifetime ceiling). Docs per §11; `.changeset/*.md` (minor).

**Removals:** none — additive; the guards remove unbounded paths, no code deleted.

### 9. Edge cases & error handling

| Case | Expected behavior |
| -- | -- |
| `addTask` below both caps | Creates the task — unchanged. |
| `pending` at `maxEnqueuedTasks` | `addTask` throws → `enqueued_task_cap_exceeded`; **drains free slots** (refresh). |
| All-count at `maxTotalTasks` (even after draining) | `addTask` throws → `total_task_cap_exceeded`; terminal tasks count (no refund). |
| **Re-entry into `pending` that would breach** (`fail`-retry, `unblock`, `resumeFromReview`, `reclaim`) | **Queued behind** — parks in `blocked` with the cap marker (`error`/`feedback` preserved), auto-promoted when a slot frees. Never refused, never lost. |
| **Cap-1 repro:** claim A → add B → A fails and re-pends | Pending never exceeds 1; A parks cap-blocked and re-pends once B drains. The nested bound holds. |
| Board terminates with cap-parked tasks | Reported via `onIdle: "complete-or-blocked"` (unresolved/blocked) — visible, not silently dropped. |
| **Concurrent burst at either boundary** | Exactly the cap's worth land; the rest rejected (CAS serializes). |
| **Batch `addTasks` crossing either cap** | Rejected all-or-nothing (typed throw; no partial insert). |
| **`initialTasks` seed / replan batch oversized** | Fails loud (propagated typed error) — not silently truncated. |
| **`tasks()` escape hatch / worker fan-out** | Guarded — same capped collection; an override reaches workers. |
| Suspend/resume between adds | Board rebuilt empty (block state in-memory) → counts reset; caps are in-request only. |
| Either cap `NaN`/`Infinity`/`0`/negative/fractional, or `maxEnqueuedTasks > maxTotalTasks` | Rejected at construction (fail loud). |
| Either cap on a resource-backed or factory board | Rejected at construction (named boundary). |
| `assignTask`/`updateTask` at/over a cap | Allowed — they mutate existing rows, create nothing. |

Error taxonomy: two new soft-error codes (`enqueued_task_cap_exceeded`, `total_task_cap_exceeded`) in the `{ ok: false, error }` family; one typed `TaskCapExceededError` at the collection boundary (caught by the tool, propagated by internal callers); construction-time validation throws. No new fatal runtime path to the model.

Second-path checklist (BP-035): **concurrency** — both CAS-internal checks + concurrent-sibling tests. **Re-entry** — the cap's other direction (`fail`-retry / `unblock` / `resumeFromReview` / `reclaim`), guarded with queue-behind so the ceiling holds without stranding recovery. **Batch/escape-hatch/internal-callers** — covered because enforcement is on the collection and the breach is typed (seed/replan propagate). **Resume/legacy** — caps in-request; a resumed board starts fresh; no persisted field. **Off/new-state** — test unset (unbounded), defaults, overrides; below/at/over each cap; the refresh vs no-refund distinction; invalid configs.

### 10. Testing strategy

**Discipline:** `tdd`. Both levels required (the concurrent path is real, so AGENTS.md's real-path requirement applies).

* **Mocked seam (deterministic)** — vitest at the sequencer-backed collection and `task-tools-capability.test.ts`, board seeded via `preTasks`:
  * **`maxEnqueuedTasks`:** fill `pending` to the cap → `addTask` → `enqueued_task_cap_exceeded`; claim/drain some → a slot frees → next `addTask` ok (refresh).
  * **`maxTotalTasks`:** fill to the cap with a mix incl. **completed** tasks → `addTask` → `total_task_cap_exceeded`; draining does not refund.
  * **re-entry (the cap-1 repro):** at `maxEnqueuedTasks: 1` — claim A (frees the slot), add B (fills it), A fails with retry budget → assert pending never exceeds 1 and A is cap-parked; then drain B → A is promoted back to `pending` and runs. One test per re-entry path (`unblock`, `resumeFromReview`, `reclaim`-on-expired-lease) asserting the same ceiling + promotion, and that no task is lost across the drain.
  * **concurrent-sibling atomicity** on each cap; **batch** `addTasks` crossing either cap rejected all-or-nothing; the `tasks()` escape hatch honors both.
  * **internal callers:** oversized `initialTasks` seed and replan batch throw loud (no partial insert).
  * **worker fan-out under override** bounded; **backing rejection** (resource + factory) at construction; **validation** (`NaN`/`Infinity`/`0`/`-1`/`1.5`, and `maxEnqueuedTasks > maxTotalTasks`).
* **Real-model goal check (required)** — `goals/` harness (`runAction` + real resolver, `openai/gpt-5.4-mini`, `AI_GATEWAY_API_KEY`), same pattern as `goals/context-supply` / `goals/skills-scoped-binding`, **declared workers** (no FIX-940 dependency). Exercise **both**: a coordinator whose single burst hits `maxEnqueuedTasks` (and recovers by draining), and a longer loop that hits `maxTotalTasks` — both bounded while still completing coherently. Seam: a new `goals/delegation-cap` (or added assertions on the delegation e2e check).

### 12. Dependencies & follow-ups

**Dependencies:**

* **Sequences after FIX-940** (on-demand default worker). ## Spec evolution

* **Spec drafted** — one cumulative count check at the `addTask` enqueue seam (co-located with FIX-924's assignee gate), a constant default mirroring `BOARD_CONCURRENCY`, reject-the-enqueue soft error; single small PR sequenced after FIX-940.
* **After spec review (Cursor + Codex, round 1)** — folded: atomicity (same-step calls run concurrently → check inside the collection CAS + concurrent-sibling test); in-request scope (generator own/block state is in-memory only → dropped the cross-resume claim, durable count → FIX-939/FIX-917); default raised and made a `taskBoard` knob; kept the real-model goal check with declared workers.
* **After spec review (Codex, round 2)** — made enforcement **intrinsic to the collection** (not the tool seam), covering batch `addTasks`, the `tasks()` escape hatch, and worker fan-out under an override; added construction-time validation and named the sequencer-backed boundary.
* **After owner re-architecture (round 3)** — replaced the single cap with a **three-bound model**: `maxTotalTasks` (500, all-count incl. terminal, no refund — the lifetime backstop), `maxEnqueuedTasks` (100, `pending`-count, refreshes on drain — the primary burst guard), and the unchanged `concurrency` (in-flight), forming *in-flight ⊆ enqueued ⊆ total*. Both new caps enforced atomically + intrinsically on every insertion path with **distinct** soft codes. Folded the two round-3 Codex P2s: (a) a **typed breach** (`TaskCapExceededError`) both insertion methods raise and every caller handles — `createSeedCollection` and `createApplyReplan` now fail loud instead of partial-insert-and-truncate; (b) reject the caps on **resource-backed AND the custom-factory** collection form (not just resource), since a factory passes its ref through the capped constructor unchanged. Added `maxEnqueuedTasks ≤ maxTotalTasks` sanity validation and a two-cap real-model goal check.
* **After spec review (Codex, round 4 — final)** — closed a correctness hole the three-cap model itself introduced: because `maxEnqueuedTasks` *refreshes* on drain, guarding only creation let tasks **re-enter** `pending` past the ceiling (`fail`-retry, `unblock`, `resumeFromReview`, lease `reclaim`) — at cap 1: claim A, add B, A fails and re-pends → 2 pending, and the queue could grow to `maxTotalTasks`, falsifying the nested *in-flight ⊆ enqueued ⊆ total* bound. Now enforced atomically on **every transition into `pending`**, with **queue-behind** on breach (park in the existing `blocked` status with a cap marker, auto-promoted inside `claim`'s CAS when a slot frees) rather than refusal. Rule chosen as **creation = new breadth (refuse) vs. re-entry = existing task already counted against `maxTotalTasks` (defer, never lose)** — the suggested model-vs-framework split was checked against the code and dropped: `unblock`/`resumeFromReview` aren't model tools at all, and `fail` is both model-initiated (`failTask`) and framework-initiated (worker rescue). Added the cap-1 repro plus one test per re-entry path; size re-estimated Small → Medium.
