# FIX-931: Over-spawning guard — cap total enqueued tasks before on-demand spawning — Implementation Spec

> **Issue:** [FIX-931](https://linear.app/fixpoint-labs/issue/FIX-931/over-spawning-guard-cap-total-enqueued-tasks-before-on-demand) · **Epic:** [FIX-930](https://linear.app/fixpoint-labs/issue/FIX-930/delegation-substrate-host-model-roster-and-identity-and-worker-context) (Delegation substrate) · **Sequences after:** [FIX-940](https://linear.app/fixpoint-labs/issue/FIX-940/on-demand-default-worker-delegation-floor) (on-demand default-worker floor) · **Same seam as:** [FIX-924](https://linear.app/fixpoint-labs/issue/FIX-924/roster-aware-task-assignment-manager-knows-its-workers-validate) (assignee validation)
>
> **Spec PR:** [#909](https://github.com/fixpoint-labs/flow-state-dev/pull/909) · kept in sync with this document.
>
> **Necessity verdict:** Build as scoped (small, but not trivial). No existing `taskBoard` knob bounds enqueue breadth — `concurrency` paces the parallel drain; `maxIterations` is a per-worker loop-back circuit-breaker that trips *during* a drain, after a coordinator's up-front `addTask` breadth is already committed. The real work is making the cap **atomic under concurrent same-step tool calls**, not the compare itself.

---

## Part I — The Case

### 1. Problem — why it matters, why now

A coordinating agent plans work by adding tasks to its board, then draining the board to run them. Each task is an agent turn, and each turn costs tokens. Nothing today bounds how many tasks a coordinator can pile on: one off-course planning step can fire a burst of `addTask` calls, and every one eventually runs. The board's `concurrency` only paces how many run at once — it doesn't cap the total.

**Why now:** FIX-940 makes rosterless delegation the cheap default (a coordinator farms work out to a worker that materializes on demand, no roster to wire first), so unbounded `addTask` breadth becomes the easy path. Anthropic's own multi-agent research reported a lead agent spawning ~50 subagents for a trivial query, at ~15× the cost of a single chat. This is the guardrail that catches that before the board drains.

### 2. Solution in plain terms

Give the delegation board a ceiling on how many tasks it will accept, enforced when a task is added. Past that count, the next `addTask` is refused with a clear message telling the coordinator to work with what it has. Under the ceiling, nothing changes.

The ceiling is **cumulative within one uninterrupted (in-request) execution** — across tool-loop steps and repeated `runBoard` passes, draining tasks to completion does **not** refund the budget, so a runaway that re-triggers inside the request can't silently earn a fresh allowance. It is deliberately **not** durable across a suspend/resume: the delegation board lives on generator own (block) state, which is in-memory only, so a resume rebuilds it empty (see §9, P2). Durable-count-across-resume is FIX-939/FIX-917 territory, out of scope for this in-request epic.

Because same-step framework tool calls run **concurrently** (the generator settles a step's calls with `Promise.all`), a naive "read `count()`, then insert" is a time-of-check/time-of-use race: at `cap − 1`, a burst of adds can all pass the read and all insert. So the check must be **atomic with the insertion** — one CAS operation — not a read followed by a write.

**The philosophy that led here.** Tenet 3 (Earn every addition): one default (100), surfaced as a board knob only because a board options object already exists to hang it on (FIX-940 is extending the same object). Tenet 2 (Composition over features): reuse the collection's existing CAS write to make the cap atomic, rather than inventing a lock or a counter.

### 3. Tradeoffs & alternatives

The simple part is the policy — an integer ceiling; the load-bearing part is atomicity. We enforce inside the collection's existing `addTask` CAS write (checked against the freshest committed task map on each retry), which serializes concurrent adds for free — rather than serializing the handlers with a mutex, or living with a racy read-then-insert. The rejected policy alternatives (existing knobs; a *pending*-only cap; halting the drain) are recorded in §6. Non-delegation boards (patterns, blackboard) are unaffected: the cap is opt-in (unset = unbounded).

### 4. Focus practices

* **Atomicity is the correctness core (BP-035, tenet 1).** The check-and-insert must be one CAS op; prove it with a concurrent-sibling test (N adds fired at `cap − 1` → exactly the cap's worth succeed).
* **Compose at the existing seam (tenet 2).** Enforce via the collection's CAS `addTask`, applied from the `buildTaskTools` closure so both the executive and worker task-tool factories inherit it; co-locate with FIX-924's assignee check.
* **Earn every addition (tenet 3).** Default 100; a `taskBoard({ maxTasks })` knob only because the options object already exists. No new counter, no lock.
* **BP-003 / tenet 7 — evidence.** Mocked seam tests for the invariants (incl. the concurrent-sibling and cumulative cases) **and** a real-model goal check that a real coordinator's excessive fan-out is bounded and still completes.

### 5. What using it looks like

No new API for the author — the cap is enforced automatically on any delegation board; a consumer constructing a board directly can override it (`taskBoard({ maxTasks })`, default 100). The only observable change is the `addTask` result once the ceiling is reached, and that draining doesn't reset it within the run:

```ts
// A coordinator fans out tasks (declared workers, or the FIX-940 floor).
await addTask({ goal: "part 1" });    // → { ok: true, taskId: "t_1" }
// ... up to the ceiling ...
await addTask({ goal: "part 101" });  // → { ok: false, error: "task_cap_exceeded" }  (message names the ceiling)
await runBoard();                     // the queued tasks settle (completed)
await addTask({ goal: "one more" });  // → { ok: false, error: "task_cap_exceeded" }  (completed tasks still count, in-request)
```

### 6. Decisions & rules — the sign-off surface

1. **Cap the total tasks a delegation board accepts, enforced at the `addTask` seam.** **← core sign-off.**
   * *Rejected:* relying on `concurrency`/`maxIterations` (neither bounds enqueue breadth); enforcing at drain time (breadth is already committed by then).
   * *Ramification:* the guard is applied at the `addTask` handler and executes inside the collection's CAS. `runBoard`'s drain logic is untouched.
2. **The check is atomic with insertion — one CAS op inside the collection's `addTask`, not a `count()` read before it.** **← correctness sign-off (decided).**
   * *Rejected:* a synchronous `count() >= cap` read in the handler ahead of `collection.addTask` — same-step tool calls run concurrently (`Promise.all`), so a burst at `cap − 1` all pass the read then all insert.
   * *Ramification:* the substrate collection's `addTask` gains an optional `maxTasks`; when set, the CAS mutate rejects (no-op) if the freshest map already holds `>= maxTasks`, returning a rejection sentinel the handler maps to the soft error. CAS retry makes concurrent adds serialize, so exactly the cap's worth land.
3. **The cap is cumulative within one uninterrupted (in-request) execution; it is NOT durable across suspend/resume.** **← scope sign-off (decided).**
   * *Rejected:* a cross-resume cumulative guarantee — generator own (block) state is in-memory only (not checkpointed), so a resume rebuilds the board empty and the count resets to 0. Promising otherwise would be unbacked.
   * *Ramification:* "cumulative" means across tool-loop steps and repeated `runBoard` passes within the request, terminal tasks included. Durable-count-across-resume is noted as FIX-939/FIX-917 follow-up territory.
4. **On breach, reject the individual `addTask` with a soft error (`{ ok: false, error: "task_cap_exceeded" }`, clear message); don't throw, don't silently drop.**
   * *Rejected:* throwing (crashes the turn); halting the whole board (that's FIX-933's spend-cap shape).
   * *Ramification:* matches the task tools' existing `no_delegation_board` soft-error contract; the model reads the result and adapts.
5. **Default cap = 100, surfaced as `taskBoard({ maxTasks?: number })`; the default constant lives at the enforcement site (`task-tools-capability.ts`), the override is threaded as a value from the board config.** **← default/knob sign-off (decided: 100).**
   * *Rejected:* a bare no-knob constant (owner wants it configurable now that a board options surface exists — FIX-940 is extending the same object with `defaultWorker`); putting the constant in `delegation-surface.ts` (it already imports `task-tools-capability` → circular-import risk). Threading a *number* the other way is fine.
   * *Ramification:* 100 gives generous headroom for legitimate decomposition and replans while still bounding the runaway. If, on inspection, there is genuinely no viable board options surface, fall back to a plain module default of 100 (invent no new surface).

**Non-goals:** the on-demand floor itself (FIX-940); assignee/roster validation (FIX-924); a cost/token **spend** ceiling (FIX-933 — bounds *spend*; this bounds *count*); durable count across suspend/resume (FIX-939/FIX-917); capping non-delegation task collections by default.

**Size:** Small — an optional atomic cap on the collection's `addTask`, a default + knob, guidance/docs, and tests (incl. concurrent-sibling + real-model). Single PR, no PR plan.

## Part II — The Build Plan

### 7. Technical design

Two seams: **where the value comes from** and **where the check fires atomically**.

* **Enforcement (atomic).** The substrate collection's `addTask` (`sequencer-backed.ts`) gains an optional `maxTasks`. Its existing `casWrite` already reads the freshest committed task map inside `atomicState`; add a guard there — when `maxTasks` is set and `Object.keys(tasks).length >= maxTasks`, the mutate no-ops and `addTask` returns a rejection sentinel instead of a `Task`. Because `atomicState` is CAS-guarded and retries on conflict, concurrent adds serialize: each retry re-evaluates the count against the winner's committed map, so a burst at `cap − 1` yields exactly one success and the rest reject. Unset `maxTasks` = today's behavior (patterns/blackboard unaffected).
* **Application (value + soft error).** The delegation task-tools live in `buildTaskTools(resolve)` (`task-tools-capability.ts`). A module constant `DEFAULT_MAX_TASKS = 100` is the default; `buildTaskTools` closes over an effective cap (`override ?? DEFAULT_MAX_TASKS`). Its `addTask` handler calls `collection.addTask(init, { maxTasks: cap })` and maps a rejection sentinel to `{ ok: false, error: "task_cap_exceeded" }` with a message naming the ceiling. Because `buildTaskTools` backs **both** delegation entry points — the executive surface (`buildTaskToolsList`) and each worker's board-bound fan-out capability (`createTaskToolsCapability(() => boardCollection())`) — this one closure covers both without a second check on the delegation surface.
* **The knob.** `taskBoard({ maxTasks?: number })` is added to the board config (beside `concurrency`, `maxIterations`, and FIX-940's `defaultWorker`), default 100. The delegation surface, which constructs the board, threads the configured value into `buildTaskToolsList(resolver?, { maxTasks })` as a plain number (import direction unchanged → no circular import). Only `addTask` creates tasks; `assignTask`/`updateTask` mutate existing rows and need no guard.

*Illustrative (a sketch, not the contract) — the atomic guard inside the collection's CAS:*

```ts
// collection.addTask(init, { maxTasks })
let rejected = false;
await casWrite((tasks) => {
  if (maxTasks !== undefined && Object.keys(tasks).length >= maxTasks) { rejected = true; return undefined; }
  return { ...tasks, [task.id]: task };
});
return rejected ? null : task; // handler maps null → { ok: false, error: "task_cap_exceeded" }
```

### 8. Implementation sequence

All one PR.

1. **Atomic cap on the collection.** Add optional `maxTasks` to `addTask` on `TaskCollectionRef` + `sequencer-backed.ts`; enforce inside the existing `casWrite`; return a rejection sentinel on breach (unset = unbounded). *Test:* fill to cap → reject; **concurrent-sibling** — N adds fired at `cap − 1` resolve to exactly the cap's worth succeeding, the rest `task_cap_exceeded`.
2. **Default + apply in the shared closure.** Add `DEFAULT_MAX_TASKS = 100` in `task-tools-capability.ts`; `buildTaskTools` closes over the effective cap and its `addTask` handler passes `{ maxTasks }` and maps rejection → soft error. This covers the executive (`buildTaskToolsList`) and worker (`createTaskToolsCapability`) paths at once. *Test:* per §10.
3. **The knob.** Add `maxTasks?: number` to `taskBoard` config (default 100); thread the value from the delegation surface into `buildTaskToolsList`. *Test:* an override lowers the effective cap; default applies when unset.
4. **Guidance copy + docs + changeset.** One clause in the delegation playbook / `addTask` description noting the ceiling; docs per §11; `.changeset/*.md` (minor).

**Removals:** none — additive; the guard removes an unbounded path, no code deleted.

### 9. Edge cases & error handling

| Case | Expected behavior |
| -- | -- |
| `addTask` below the cap | Creates the task — unchanged. |
| `addTask` at the cap | Rejected atomically inside CAS. |
| **Concurrent burst at `cap − 1`** | Exactly `cap` total land; the rest get `task_cap_exceeded` (CAS serializes them). |
| Cap reached, tasks then drained to terminal (same request) | Still rejected — terminal tasks count (cumulative in-request). |
| Suspend/resume between adds (P2) | Board rebuilt empty from schema default (block state in-memory) → count resets; cap is in-request only, by decision §6.3. |
| `assignTask`/`updateTask` at/over cap | Allowed — they mutate existing rows, create nothing. |
| Non-delegation board (pattern, blackboard) | No cap unless `maxTasks` set — opt-in; substrate default unbounded. |

Error taxonomy: one new soft-error code, `task_cap_exceeded`, in the `{ ok: false, error }` family (like `no_delegation_board`). No thrown errors, no new fatal path.

Second-path checklist (BP-035): **concurrency** — the primary risk, handled by the CAS-internal check (decision §6.2) and the concurrent-sibling test. **Resume/legacy** — cap is in-request; a resumed board simply starts fresh; no persisted field, nothing to migrate. **Off/new-state** — test unset (unbounded), default (100), and an override; below/at/over the cap.

### 10. Testing strategy

**Discipline:** `tdd`. Both levels are required (this is not a trivially-deterministic guard — the concurrent path is real, so AGENTS.md's real-path requirement applies).

* **Mocked seam (deterministic invariants)** — vitest at the collection and `task-tools-capability.test.ts`, own-state board seeded via `preTasks`:
  * fill to cap → next `addTask` → `{ ok: false, error: "task_cap_exceeded" }`.
  * fill to cap with **completed** tasks → still rejected (cumulative / no-refund within a run).
  * **concurrent-sibling:** N `addTask` calls fired at `cap − 1` → exactly the cap's worth succeed (proves atomicity).
  * override via `maxTasks` lowers the effective cap; `assignTask`/`updateTask` unaffected; message names the ceiling.
* **Real-model goal check (required)** — `goals/` harness (`runAction` + real resolver, `openai/gpt-5.4-mini`, `AI_GATEWAY_API_KEY`), same pattern as `goals/context-supply` / `goals/skills-scoped-binding`. A real coordinator with **declared workers** (so it does not depend on unmerged FIX-940) prompted to over-fan-out (a burst of `addTask`) is bounded by the cap **and** still completes coherently. Seam: a new `goals/delegation-cap` (or an added assertion on the delegation e2e check).

## Spec evolution

* **Spec drafted** — one cumulative count check at the `addTask` enqueue seam (co-located with FIX-924's assignee gate), a constant default mirroring `BOARD_CONCURRENCY`, reject-the-enqueue soft error; single small PR sequenced after FIX-940.
* **After spec review (Cursor + Codex)** — approach validated; folded in review findings that materially sharpened it: (1) **atomicity** — same-step tool calls run concurrently (`Promise.all`), so a `count()`-then-insert read is racy; moved the check inside the collection's CAS `addTask` (atomic check-and-insert) and added a concurrent-sibling regression test; (2) **resume scope** — generator own (block) state is in-memory only, so the cap is scoped to an uninterrupted in-request execution, dropping the unbacked cross-resume claim (durable count → FIX-939/FIX-917); (3) **default raised to 100 and made a `taskBoard({ maxTasks })` knob** (default constant at the enforcement site, value threaded from the board config — no circular import), per owner direction; (4) constant lives at the enforcement site closed over in `buildTaskTools` (dual-factory coverage: executive + worker), no threading of the constant itself; (5) kept the real-model goal check (real-path required for this concurrent-behavior class) alongside the mocked invariants; (6) §12 open questions closed into §6; prose trimmed and the redundant mermaid dropped.
