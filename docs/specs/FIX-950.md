# Part I — The Case

## 1. Problem — why it matters, why now

A skill that delegates gets a task board and eight tools for driving it. Five of them answer a bad call the same way: they hand the model a small result saying what went wrong, and the model tries again. The other three — the ones that mark a task done, failed, or blocked — answer differently when the task isn't in a state that permits the change. They raise an error, which reaches the model as a bare line of internal text instead of the result shape the other five use.

So the surface speaks two languages. An author who follows our own documentation and writes "if the tool comes back not-ok, do X" has written a rule that silently doesn't cover three of the eight tools.

**Why now.** We are documenting this surface right now. [PR #932](https://github.com/fixpoint-labs/flow-state-dev/pull/932) had to write the split into the reference docs — one paragraph listing the five soft tools, a second naming the three exceptions and telling authors to "sequence these against what the board actually holds rather than issuing them speculatively." That is the cost of the inconsistency, written down as advice. Fixing the behavior collapses those two paragraphs into one instead of teaching the split.

**One correction to how this issue was filed, because it changes the argument.** The issue says these throws "end the turn." **They do not.** The generator catches every tool throw and feeds it back to the model as an error result (`packages/core/src/blocks/generator.ts:1346`, rendered at `:1417`); only a suspension re-throws. So the model already sees *something* and can already recover. What it sees is the raw internal string `[tasks] illegal status transition for task "t-3": pending → completed` — which names the rejected move but not the task's current status, not what the model can do about it, and not that the task simply hasn't been started yet.

That makes this a **coherence and message-quality fix, not a turn-saving fix.** It is smaller than filed. It is still worth doing, for the reason above: one surface, one contract, and an error that tells the model what to do instead of only what it did wrong.

## 2. Solution in plain terms

Give the transition guard its own error type instead of a generic one. At the tool boundary — the single shared helper all six by-id tools already route through — catch exactly that type and return the same not-ok result shape the other tools use, with a message that names the task's current status and **the tool calls actually available from that status**. Everything else that can go wrong keeps propagating, untouched.

The state machine itself does not get more permissive. Code that calls the collection directly still gets an exception. Only the model-facing boundary translates.

**The philosophy that led here.**

- **Tenet 1 (coherence over local cleverness).** Incoherence is the failure we rank first. One tool surface answering the same class of question in two different shapes is exactly that, and it is already leaking into the docs as a split authors must memorize.
- **Tenet 5 (fix at the owning layer — the owning layer is where the paths converge).** Two convergence points, each owning one job. `assertTransitionAllowed` is the single place that decides a transition is illegal, for both collection backings. `withTask` is the single place all six by-id tools pass through. The guard stays where it is; the *translation* goes where the model-facing contract is owned.
- **Tenet 3 (earn every addition).** This adds one error class and one catch, mirroring a precedent already on the same file. It also *subtracts*: the docs split naming three exceptional tools goes away, and so does the advice to sequence calls defensively around it.

## 3. Tradeoffs & alternatives

**The main alternative: catch everything at the tool boundary.** Rejected, and it is the tempting one — a single `catch (err)` at the mutator call is three lines and closes every gap at once. It would also swallow scope-mutation timeouts, concurrent-modification conflicts on store-backed boards, raw storage failures, and ordinary bugs, converting each into a polite "that didn't work" the model reads as *its own mistake* and continues past. That is the "error swallowing" failure class: the model narrates around a real infrastructure failure and nobody finds out for hours. The .NET Try-Parse guideline states the rule we're following — a non-throwing variant must have a strictly enumerated failure set, and anything outside it still throws.

**The simpler approach considered: pre-check the transition in `withTask` before calling the mutator.** Rejected on a concrete blocker, not on taste. `withTask` receives the mutator as an opaque closure and does not know its target status. Each tool would have to declare its target, duplicating state-machine knowledge at the tool layer — and it breaks outright on `failTask`, whose target depends on the task's retry budget at call time. A pre-check would have to re-derive that branch and would drift the moment either side changes.

**Why the throw matrix in §9 was verified by execution rather than derived.** It is *mostly* derivable from `ALLOWED_TRANSITIONS` plus `fail()`'s routing — but derivation is exactly what missed the one non-obvious cell. Both the filed issue and the brief that commissioned this spec derived the matrix by hand, and both missed that `failTask`'s throw set is conditional on the retry budget. Running every tool against every status caught it in one pass. A method that catches what derivation misses has earned its place.

**Where the genuine complexity is.** In the **recovery half of the error message**, and it is a layer trap. The obvious move is to list the statuses reachable from here, straight out of `allowedTransitionsFrom`. That helper is correct about the *collection* and wrong about the *tools*: no task tool can move a task to `awaiting_review` or `in_progress`, and `pending` is reachable only through `failTask` and only with retry budget left. A status-derived list would tell the model it can do things it has no tool for, which is worse than saying nothing — it sends the model at unavailable operations and preserves the retry loop this change exists to break. The recovery list has to be derived from *tool-reachable actions*.

**Honest limits of the evidence.** Vendor guidance is unanimous that tool errors should be results, not exceptions, and that messages should name the next action (MCP's spec puts business-logic errors explicitly in the return-as-result bucket; Anthropic's tool-use docs make the same point about instructive messages). But there is **no controlled study** isolating a bare error code against an action-naming sentence. We are following consistent guidance, not a measured result.

## 4. Focus practices

1. **Ask at which layer each fact is true.** Every significant miss on this issue has been a fact verified one layer away from the reader who needs it — `allowedTransitionsFrom` is true of the collection and wrong of the tools; `cancelTask` looks like its siblings at the `withTask` layer and differs one call deeper. Before citing a helper or a table in model-facing output, confirm it is true at the layer the model is standing on.
2. **Catch by type, never by `catch (err)`.** (Tenet 5, and the Try-Parse rule.) The enumerated soft set is a deliberate list. Anything not on it propagates.
3. **The error message is the deliverable.** (Tenet 7.) The model is the consumer, which is why §10's goal check is a required gate rather than a nice-to-have — a unit test can assert the returned object while the model still fails to act on it.
4. **Preserve the substrate's error message text verbatim.** Two existing tests match on it. Ordinary regression discipline and tenet 1, *not* BP-030 — that practice governs persisted and in-flight data shapes, and an error string is neither.
5. **BP-022 — changeset required.** Observable behavior in a published package.

## 5. What using it looks like

**Before** — the model calls `completeTask` on a task it never drained. The tool raises, and the generator hands the model this:

```
[tasks] illegal status transition for task "t-3": pending → completed
```

No `ok` field, so a SKILL.md rule like "when a tool returns `ok: false`, call `listTasks` and re-plan" does not fire.

**After** — same call, same board state. The recovery half names calls, not statuses:

```js
completeTask({ taskId: "t-3", output: "…" })
// → {
//     ok: false,
//     taskId: "t-3",
//     error: 'illegal_status_transition: task "t-3" is pending, so transitioning to
//              completed is not available. A pending task has not been started yet —
//              call runBoard to have a worker claim and finish it. From here you can
//              also call blockTask or cancelTask.'
//   }
```

**A dead end, stated as one** — a `blocked` task has no unblock tool, and the message must not imply otherwise:

```js
completeTask({ taskId: "t-9", output: "…" })
// → {
//     ok: false,
//     taskId: "t-9",
//     error: 'illegal_status_transition: task "t-9" is blocked, so transitioning to
//              completed is not available. From here you can call cancelTask.'
//   }
```

**And the terminal case**, where nothing meaningful is available:

```js
blockTask({ taskId: "t-7", reason: "waiting on legal" })
// → {
//     ok: false,
//     taskId: "t-7",
//     error: 'illegal_status_transition: task "t-7" is completed, which is terminal.
//              Its status will not change again. Add a new task instead.'
//   }
```

Nothing changes for code that drives a collection directly — `collection.complete(id, output)` still throws.

## 6. Decisions & rules

1. **A dedicated error type carries the illegal transition; the tool boundary catches it by `instanceof`.** *Alternative rejected:* matching on the error message string, or a blanket `catch (err)`. *Ramification:* the soft set becomes an explicit, reviewable list, and infrastructure failures keep propagating. Costs one new class, `IllegalTaskTransitionError`, mirroring `TaskCapExceededError`.

2. **`IllegalTaskTransitionError` is exported and documented, not internal.** *Alternative rejected:* keeping it module-private and discriminating some other way. *Ramification:* Decision 3 preserves the throwing contract for direct collection callers, so a caller catching it is a supported path and BP-007 requires an exported API be documented. This moves `packages/orchestration/README.md` from optional to required in §11. An undocumented package-root export is not an option.

3. **The guard stays in `assertTransitionAllowed`; only its error *type* changes, not its message or its semantics.** *Alternative rejected:* making the state machine lenient, or moving the check into the tools. *Ramification:* non-tool callers still get a throw, and the two existing message assertions keep passing. This is a *default*, not a universal claim — [FIX-951](https://linear.app/fixpoint-labs/issue/FIX-951/task-board-drain-containment-breaks-when-a-worker-fails-after-its-own) is a non-tool caller where the same throw is actively harmful, fixed at that caller rather than here.

4. **The rejected move is described by status; the recovery is derived from tool-reachable actions.** *Alternative rejected:* deriving the recovery list from `allowedTransitionsFrom`. *Ramification:* that helper answers a question about the collection, and the model is standing at the tool layer. It would advertise `awaiting_review` and `in_progress`, which **no task tool can reach** (`awaiting_review` appears in `task-tools-capability.ts` only in `listTasks`'s filter enum; `in_progress` comes only from a worker claim during `runBoard`). The composer instead tests each status-changing tool's own target with `isTransitionAllowed`, honouring `failTask`'s retry-budget branch, and names `runBoard` when the task is merely `pending`. Roughly fifteen lines rather than three — see §12 for the honest re-weigh.

5. **Naming the operation is avoided; the rejected move is named by target status.** *Alternative rejected:* tool-verb copy ("complete is not available"). *Ramification:* `withTask` receives an opaque mutator and cannot know which tool it serves, so verb copy needs a parameter or a target→verb map. **The one case where the attempted target diverges from the model's intent — `failTask` with a retry budget, which targets `pending` — is safe, because all three of its throwing sources are terminal and take the terminal branch, which never names a target.** Non-obvious, so it is written down.

6. **Tool descriptions are not changed.** *Alternative rejected:* stating status preconditions in the three tools' descriptions. *Ramification:* the model cannot know a task's status without calling `listTasks`, so a precondition it cannot check is prompt weight on every turn to prevent a mistake the error already corrects at the moment it happens.

7. **In the docs, the concept is a "recoverable tool result", not a "soft error".** *Alternative rejected:* matching the source vocabulary. *Ramification:* `task-substrate.md:74` already uses "soft fail" for the retry-budget meaning, on the same page as a line this change edits (`:46`).

8. **This change lands after PR #932.** *Alternative rejected:* landing in parallel, or downgrading to a soft note. *Ramification:* #932's doc changes are **379 insertions against 114 deletions, and the two paragraphs this change collapses are pure additions** — merging FIX-950 first would let #932 re-introduce the split with **no merge conflict to catch it**. The guide is restructured hard enough (+416/−114) that the insertion point moves outright. #932 is finished and awaiting merge, so the gate is short-lived.

**Non-goals.** Re-litigating `ALLOWED_TRANSITIONS`. Changing `cancelTask`, which already never throws. Making the collection API non-throwing for direct callers. Renaming existing error codes. [FIX-951](https://linear.app/fixpoint-labs/issue/FIX-951/task-board-drain-containment-breaks-when-a-worker-fails-after-its-own).

**Size: Small.** Two source files plus tests and one required goal check.

# Part II — The Build Plan

## 7. Technical design

The substrate keeps deciding legality and keeps throwing. The tool boundary translates one enumerated error class into the result shape the model already understands.

```mermaid
flowchart TD
    M[Coordinating model] -->|completeTask / failTask / blockTask| WT[withTask<br/>tool boundary]
    WT --> R{board? task? assignee?}
    R -->|no| SOFT[" { ok: false, error, taskId } "]
    R -->|yes| MUT[mutator → collection lifecycle]
    MUT --> TT[transitionTo]
    TT --> AG[assertTransitionAllowed<br/>*the single legality decision*]
    AG -->|legal| W[CAS write + emit] --> OK[" { ok: true } "]
    AG -->|illegal| ERR[IllegalTaskTransitionError]
    ERR --> XL[typed catch + action composer<br/>*in withTask only*]
    XL --> SOFT
    MUT -.->|CAS conflict, storage failure,<br/>scope timeout, bugs| TH[propagates — unchanged]

    DIRECT[Direct collection callers<br/>drain rescue, user code] --> TT
    ERR -.->|not caught here| DIRECT
```

`assertTransitionAllowed` is reached from exactly two call sites — `sequencer-backed.ts:193` and `resource-backed.ts:161` — so typing its error there covers both backings. It is **not** reached by every lifecycle method: `claim`, `reclaim`, and `addTask` write status without it. The convergence claim is about *transition legality*, not all status writes.

**Surface added:** `IllegalTaskTransitionError`, carrying the task id, source status, and attempted target. Extends `Error`, sets `name`, matching `TaskCapExceededError`. Exported from the tasks module (the package root already re-exports it) and documented per Decision 2. The composer, `illegalTransitionToolError`, lives in `task-tools-capability.ts` beside `unknownAssigneeError` and `capError`.

**The action composer.** Given the source status and the task, it derives the available calls rather than hardcoding a table: for each status-changing tool, test `isTransitionAllowed(from, thatTool'sTarget)` — with `failTask`'s target selected by `shouldRetryOnFail` — and drop same-status no-ops. `cancelTask` is always available on a non-terminal task. When the source is `pending`, name `runBoard`, because the task simply has not been claimed yet. Terminal statuses take a separate branch selected by `isTerminalStatus`, not by testing for an empty array.

**Surface unchanged:** the `okOrError` schema (`error` is already `z.string()`, `taskId` already optional), every existing error code, and every tool description.

**Surfaces that change, listed because nothing currently lists them.** Because these calls stop throwing, four observable behaviors move from the error path to the success path:

- the `tool_output` item stops being marked `status: "failed"` with a populated `item.error` (`emit-tool-output.ts:180-199`)
- `flowTools.onToolErrored` stops firing (`tool-executor.ts:174-178`)
- the tool observation is written as a normal result rather than an error (`tool-executor.ts:202-208`)
- **where `flowTools.defaults.retry` is configured, the call is no longer retried** (`tool-executor.ts:123-126`) — today a deterministic model mistake is re-executed N times, which is pure waste

Three of the four are improvements; the DevTool rendering of these calls changes either way.

Discipline is **`diagnose`** (Bug). Feedback loop is vitest against `packages/orchestration/test/skills/task-tools-capability.test.ts`.

2. **Introduce the error type.** Add the class; throw it from `assertTransitionAllowed` in place of the generic `Error`. **Keep the message text byte-identical.** Export from the tasks module index. **The gate for this step is not "green"** — step-1 tests are still red, because a typed throw is still a throw. The gate is `pnpm --filter @flow-state-dev/orchestration test test/schema/task.test.ts test/collection/collection.test.ts` passing unchanged.

3. **Catch and compose, in `withTask` only.** Wrap `await mutator(collection)` with a typed catch that returns the composed result and re-throws everything else. Add `illegalTransitionToolError` beside the other error builders. **`addTask` is not touched** — see §12.

4. **Green + widen.** Tests per §10.

5. **Rename the mis-named existing test.** `it("completeTask transitions a pending task to completed")` at `:183` seeds `in_progress` at `:189`. In scope and flagged, not a silent drive-by.

6. **Goal check** per §10, then docs + changeset per §11, rebased onto #932.

## 9. Edge cases & error handling

Throw matrix, computed from `ALLOWED_TRANSITIONS` and verified by executing every tool against every status. Every `THROW` becomes a recoverable result; no `ok` cell changes.

| tool | throws today from | after |
|---|---|---|
| `completeTask` | `pending`, `blocked`, `errored`, `cancelled` | recoverable result |
| `failTask` *(no retry budget)* | `pending`, `blocked`, `completed`, `cancelled` | recoverable result |
| `failTask` *(retry budget left)* | `completed`, `errored`, `cancelled` | recoverable result |
| `blockTask` | `in_progress`, `awaiting_review`, `completed`, `errored`, `cancelled` | recoverable result |
| `cancelTask` | **never** | unchanged |
| `addTask` / `assignTask` / `updateTask` / `listTasks` | never *(no transition)* | unchanged |

Two corrections to the filed issue: it names only `pending` for complete/fail and `in_progress` for block, missing the **terminal source statuses**; and **`failTask`'s set is conditional on the retry budget**. Note the matrix is not "all terminal sources throw for all three tools" — `completeTask` from `completed` and `failTask`(no budget) from `errored` are same-status no-ops that succeed.

**Tool-reachable actions by source status** — what the composer must produce, and the reason `allowedTransitionsFrom` cannot produce it:

| source | meaningful tool calls available | `allowedTransitionsFrom` would also claim |
|---|---|---|
| `pending` | `runBoard`, `blockTask`, `cancelTask`, `failTask` *(budget only)* | `in_progress` — no tool reaches it |
| `in_progress` | `completeTask`, `failTask`, `cancelTask` | `awaiting_review`, `pending` — no tool reaches either |
| `blocked` | `cancelTask`, `failTask` *(budget only)* | `pending` — reachable only via `failTask` with budget |
| `awaiting_review` | `completeTask`, `failTask`, `cancelTask` | `pending` — same |
| terminal | none meaningful | *(empty)* |

| Edge case | Expected behavior |
|---|---|
| Task already in the target status | Legal same-status no-op, returns ok — **not** an error. |
| Terminal task | Terminal phrasing via `isTerminalStatus`. No empty action list rendered. |
| `cancelTask` on a terminal task | Silent no-op returning ok. So the terminal message must not claim *nothing* can be called — only that the status will not change. |
| `blocked` source | No tool unblocks a task. The message must not imply one exists. |
| CAS conflict / scope timeout / storage failure | **Still throws.** Out of the soft set. |
| `updateTask` partial apply | Its five patches route to `patchOne`, which never transitions. |
| Direct collection callers | Still throw. Decision 3. |

**The model-mistake/infrastructure dichotomy is not clean, and the spec should not pretend it is.** `assertTransitionAllowed` runs *inside* the replayed `casWrite` closure (`sequencer-backed.ts:193`; `resource-backed.ts:156-165` under `ref.updateState`). A model calling `completeTask` on a legitimately `in_progress` task can lose a race to a concurrent drain worker that terminalizes it, and the guard fires on the CAS retry. That is a lost race, not a model mistake — and it now returns a soft result while the sibling task-removed race still throws. The soft result remains right (the message is true and actionable), but the justification is "this failure is *recoverable by the model*", not "this failure is *always the model's fault*." Related: `shouldRetryOnFail`'s input is read outside the CAS (`:317`), so the retry-branch decision can be made on a stale snapshot.

**BP-035 second-path checklist.** *Legacy shape:* message text preserved; step 2 verifies in isolation. *Null boundary:* terminal statuses handled by `isTerminalStatus`, not an empty-array test. *Concurrent/409:* CAS conflicts stay loud; the in-CAS race is documented rather than silently absorbed. *Cancel/error path:* `cancelTask` verified unchanged. *Multi-tenant:* n/a, board is block-scoped. *Cost/observability:* four surfaces flip — §7. *New-flag off-state:* no flag added.

## 10. Testing strategy

**Representative CI specs** (vitest), not a cross-product suite — the matrix is research evidence, not a test mandate. Following `delegation-caps.test.ts`'s two-part shape (assert the result, then assert the board is untouched):

- One illegal case per tool returning not-ok with the `illegal_status_transition` prefix, **and the task's status unchanged**.
- **`blocked` and `awaiting_review` sources specifically** — these are where status-derived and action-derived recovery diverge. Assert the message names only tool-reachable calls, and in particular that the `blocked` case does not imply an unblock exists.
- A terminal-source case: terminal phrasing, no empty action list, and no claim that `cancelTask` is unavailable.
- `failTask` on `pending` **with** a `maxAttempts` budget still succeeds — the retry branch.
- **A non-transition throw from the mutator still propagates.** The most important test here: it is what separates this from the rejected blanket catch.
- Substrate unchanged: `assertTransitionAllowed` still throws, still matches the existing message assertions.

**Goal check — REQUIRED.** Not optional. The deliverable is defined as a change in model behavior, and vitest asserting the returned object can pass while the generator's tool loop presents it in a way the model does not act on. A deliverable defined as model behavior is evidenced only by a model-backed run.

Shape it on `goals/delegation-caps/bounds-a-runaway-coordinator/`. What makes it discriminating, and therefore what must hold:

- **It must fail before the fix.** The pass criterion is not "the board finished" — that can pass pre-fix, since the raw error already reaches the model. It is that after a rejected call the coordinator's **next** task-tool call is one the error named as available, and that it does not re-issue the same rejected call.
- **Anti-game control:** the run must evidence that an illegal transition was actually issued, so a run that never hits the case cannot pass by vacuity.
- Model-backed via `AI_GATEWAY_API_KEY`.

If the check proves too stochastic to gate CI reliably, that is a finding to report, not a licence to drop it — record the observed variance and raise it rather than quietly downgrading.

**Changeset:** required, `@flow-state-dev/orchestration`, `patch` (`release-notes-workflow.md:55`; FIX-924's precedent). FIX-931 shipped `minor` for structurally similar work, but that was for new user-facing cap *options*, not error translation.

## 12. Dependencies, open questions & follow-ups

**Dependencies.**
- **PR #932** (`fix/FIX-932`, docs-only, finished and awaiting merge) — land first, per Decision 8. Verified: no other open PR among the 15 currently open touches `packages/orchestration/src/**` or `packages/orchestration/test/**`.
- No blocking Linear issues. The epic (FIX-930) is approved and in development.

**An honest re-weigh of Decision 4.** The action-derived recovery list is the second correction to this decision's mechanism, and it is no longer "a few lines using an already-exported helper." Whether that changes the verdict: **no, and the correction makes the decision easier to defend, not harder.** The cost is roughly fifteen lines, because the composer derives availability from each tool's own target via `isTransitionAllowed` rather than hardcoding a per-status table — it does not duplicate the state machine, it queries it once per tool. And the alternative got *worse* on inspection: a status-derived list is not merely less helpful, it actively names operations the model cannot perform, which preserves the retry loop this change exists to break. A phased ship that mechanically preserved the `from → to` text would deliver the shape fix while leaving the model no better informed than it is today, for a change whose entire remaining value is the message. If the goal check in §10 cannot demonstrate the behavior delta, *that* is the signal to revisit scope — not the line count.

**Open question.** Should the error carry a structured `code` field alongside the string? Decision 4 puts the code in the message prefix, needing no schema change. A real field would be a shared-schema change across all six tools and shouldn't ride along on a bug fix.
