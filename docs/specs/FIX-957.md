## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

**In plain language.** When a skill delegates work to a team of agents, the framework hands it a *board* — a to-do list its coordinator plans on and then runs. Today that board is erased at the end of every user turn. Ask a follow-up question and the coordinator starts from an empty list, with no way to reach the work it planned a minute ago.

That's a real limit, but it isn't the whole problem. The framework *already knows how* to keep a board alive across turns — `defineTaskCollection({ id, scope })` ships today, is documented for exactly this, and works when you build a board by hand in code. The delegation path just can't reach it: it is hardwired to the disposable option. So this is not a missing capability. It's an existing capability that one caller can't ask for.

**Why now.** Two of the delegation surface's own tool descriptions promise something the disposable board cannot deliver. `blockTask` says "block a task pending an external condition," and the `awaiting_review` status implies a human will look at the task later. The conditions those names evoke — a person answers, a rate limit resets, a fact arrives — all resolve *after* the turn ends, which is precisely when the board no longer exists. We are advertising cross-turn parking on a substrate that erases itself. Anyone building a delegating skill today is being pointed at a dead end.

There is also a live correctness hazard sitting behind the switch. Several things in the current code assume the board is disposable, and each turns into a defect the moment it isn't. Flipping the scope without addressing them first would ship a board that survives *and* misreports *and* is unbounded *and* can run the same task twice. That's why this issue is larger than a config field — and why some of it turns out not to be fixable here at all (Decision 3).

### 2. Solution in plain terms

Let the delegation board be given a durable home, fix what can be fixed, and state plainly what cannot.

The configuration itself is deliberately small. Each *binding* — one generator's use of the skills library — gains **one** option naming how long its board should live: `block` (today's behavior, the default) through `request`, `session`, `user`, `org`, plus an id for every rung above `block`. The storage backing is derived from that answer rather than chosen, and the library builds and registers the collection. It mirrors the binding's existing `activeState` option exactly, which already asks a caller for a scope and a storage field for per-binding state. No new durability machinery is invented anywhere: the durable values resolve to the same `defineTaskCollection` primitive the code-first path already uses.

The three fixes are where the actual work is:

1. **Report on the work this run actually engaged.** `runBoard` currently reports on every task the board has ever held. Once tasks survive, one parked task from last Tuesday makes every future run report "blocked" forever, and the coordinator is handed a growing pile of finished work it didn't ask about.
2. **Be honest about what durable storage cannot give us.** The guards that bound runaway delegation cannot be enforced there, and neither can task claiming be serialized across concurrent requests — one missing cross-execution atomic, two consequences. Turning durability on removes the ceiling *and* admits a task running twice, and both have to be stated trades rather than surprises.
3. **Give a parked task a way out.** A task blocked mid-run has exactly one exit today: cancel it. Cancelling mints a new id if the coordinator re-adds the work, and anything that depended on the original silently becomes unrunnable forever.

**The philosophy that led here.**

- **Tenet 2 (composition over features, refine don't accrete).** The strongest thing about this change is what it *doesn't* add. `defineTaskCollection` already solves durable boards; the delegation surface just couldn't reach it. Wiring the existing primitive in beats inventing board persistence a second time, and it keeps one definition of "a durable board" rather than two that drift.
- **Tenet 5 (fix at the owning layer — find where paths converge).** Applied twice, both times as a negative result worth having: the creation caps have several writers (the coordinator's tools, a fan-out worker's tools, the drain, internal batch callers), and on durable storage there is *no* point where they all converge under one critical section — which is why the honest answer is "unbounded, and claims unserialized" rather than a guard at one entry point.
- **Tenet 3 (earn every addition).** One new option, on a binding surface that already carries its twin; no new field on the shared task schema; and a cap surface that shrinks rather than grows, because the existing type-level ban on caps for durable storage turned out to be right.

### 3. Tradeoffs & alternatives

**The simpler approach considered: just flip the backing and ship it.** Genuinely tempting — the durable primitive exists, and the wiring is a few lines. It's insufficient because each blocker is a defect that only *appears* once the board survives, and most of them are silent. A board that reports "blocked" forever, or that has lost its runaway ceiling, is worse than one that forgets. The config change is the small part; it is not shippable alone.

**Alternative rejected — accepting a `DefinedTaskCollection` as the option (this spec's first two drafts).** The stated reason for preferring it was that a lifetime enum would "invent a parallel scope vocabulary." That reason does not survive inspection, and the option lost on re-examination. The codebase already carries two vocabularies and neither is a lifetime: **backing** (`sequencer` / `request` / `resource`) names storage shape, and `ResourceScope` (`session` / `user` / `org`) names reach. `defineTaskCollection` already collapses both for the durable half. A lifetime axis doesn't add a third vocabulary — it finishes the one that exists, and it is the same insight FIX-960 is acting on internally (renaming `sequencer` → `state` precisely because that name describes storage rather than lifetime). See Decision 1 for the full comparison, including the objection that survives (a durable board still costs an id) and the registration defect the enum dissolves.

**Alternative rejected — scoping the run's report by *which turn created each task*.** This was the first draft's approach and it is wrong. A task created in turn 1, unblocked and completed in turn 2, is neither "created this turn" nor "still unfinished" — so it would be dropped from turn 2's report, silently withholding the worker output for the one task turn 2 actually ran. That is the exact scenario this whole feature exists for. It would also have changed what today's per-turn board returns unless every default board stamped its tasks too. The replacement — report on the tasks *this run engaged* — is both correct and strictly smaller: no new field on the shared task schema, and no migration for already-persisted rows.

**Alternative rejected — adapt the durable collection to look like the disposable one.** This would have let one code path serve both and made the cap work trivial. It is not possible, and the reason is structural rather than effort: the disposable backing is a single atomic value, the durable one is many independently-written keys. Synthesizing the former from the latter needs a multi-key transaction the resource registry has no verb for, and it would regress the per-key write granularity that makes task claiming safe under concurrency. This was verified during the issue's architectural audit and is settled, not open.

**Where the genuine complexity is.** Everything durable storage cannot coordinate, and the honest conclusion is that none of it can be fixed here. On the disposable backing the cap check lives *inside* the atomic write, so a burst of concurrent adds serializes and lands exactly the cap's worth. Durable storage has no such write: it creates one key per task, every count is read from a per-execution cache that is updated only after a store round-trip resolves, and there is no collection-wide critical section to hold across the two. The storage layer's own retention limit fails the same way and with a wider window, so it is not a fallback. The same missing atomic also leaves task claims unserialized across executions, so two concurrent drains of one board can run the same task twice — the sharper edge of one root cause, and the one that produces a wrong answer rather than a large bill.

This spec claimed a workable bound four times before accepting that. Each formulation was weaker than the last and each was still wrong in the same direction; the fourth prescribed a test that would have passed while certifying a false guarantee. Decision 3 now states the unbounded result and deletes the bound rather than producing a fifth number. Closing it for real needs a store-backed count or a multi-key atomic — substrate work, tracked under FIX-939.

The second complexity is that the durable backing's hydration cost makes caching mandatory rather than optional, which in turn interacts with that same staleness. See Decision 3 and §12.

### 4. Focus practices

1. **Enumerate the writers before believing any guard (tenet 5).** The board has several: the coordinator's `addTask`, a fan-out worker's board-bound tools, the drain, internal batch callers (seed, replan), and settle. This is what killed four attempts at a durable cap, and it is what the shared collection memo in sub-PR `d` depends on — if any writer resolves its own reference, the memo only partly binds. Enumerate them; don't assert coverage.
2. **A durable board's rows outlive the deploy that wrote them (BP-030).** Once tasks persist at session/user/org scope, the stored task envelope becomes a real migration surface it never was when the board died every turn. Any change to that envelope must dual-read the old shape and `== null`-guard new optional fields. This spec deliberately adds no new field, which is the cheapest way to honor this — keep it that way unless something forces otherwise.
3. **Test the off state of the new option (BP-035).** The default lifetime (`block`) is the one every existing consumer is on, and it must be bit-for-bit unchanged, **including exactly which tasks `runBoard` returns**. Every behavior added here needs a test proving it is inert at `block` — and note that `request` is *not* the off state, which is the mistake an earlier draft made.
4. **A refusal the model can act on is a result, not a throw.** This surface's established contract is `{ ok: false, error }` with enough detail to recover. The one refusal this spec may add — a guarded unblock, if Decision 4 goes that way — joins that contract; nothing new throws through the tool boundary.
5. **Don't re-derive the audit (tenet 1).** The issue body carries an architectural audit already verified against `main`, including one finding that was wrong, corrected, and re-verified. Treat it as established. In particular: `maxInstances` is a live-capacity limit, not a lifetime ceiling, and `SkillsLibraryOptions.scope` scopes the *skills* collection, not the board. Both have already cost a cycle.

### 5. What using it looks like

**Today — unchanged, and still the default.** A delegating skill gets a private per-turn board with no configuration at all:

```ts
const skills = createSkillsLibrary({ collection: "skills", catalog });
// Coordinator plans with addTask, runs with runBoard. Board is erased at turn end.
```

**New — a board that survives the conversation.** One option on the binding, no second import:

```ts
const skills = createSkillsLibrary({ collection: "skills", catalog });

// Per binding — one generator, one board. Mirrors the existing `activeState` option.
generator({
  uses: [skills.with({ board: { lifetime: "session", id: "researcher" } })],
  //                            ↑ block (default) | request | session | user | org
  //                              `id` namespaces every rung above `block`
});
```

Turn 1 plans three tasks and drains two; turn 2 resumes the third:

```
turn 1:  addTask("research")  → { ok: true, taskId: "t1" }
         addTask("draft")     → { ok: true, taskId: "t2" }
         addTask("review")    → { ok: true, taskId: "t3" }   // blocked on a human
         runBoard()           → { status: "blocked", tasks: [t1 completed, t2 completed, t3 blocked] }

turn 2:  unblockTask("t3")    → { ok: true }
         runBoard()           → { status: "drained", tasks: [t3 completed] }
                                 └─ t3 was unfinished when this run started, so it is
                                    this run's business and its output comes back.
                                    t1/t2 were already finished — not re-reported.
```

The second `runBoard` is the point of the whole change. Today turn 2's board is empty and `t3` is unreachable. With a naive durable board, turn 2 would report `blocked` (poisoned by `t3`) and hand back all three tasks including two the coordinator already consumed.

**New — a parked task's exit.** `unblockTask` returns a task to `pending` without minting a new id, so dependents survive:

```
blockTask("t3", "waiting on the customer's answer")   → { ok: true }
unblockTask("t3")                                      → { ok: true }
// t4 declared deps: ["t3"] — still runnable. Cancel-and-re-add would have
// stranded t4 permanently, with no error surfaced.
```

### 6. Decisions & rules — the sign-off surface

1. **The board is configured per *binding*, by one option naming its lifetime — `block` (default, today's behavior) | `request` | `session` | `user` | `org` — plus a caller-supplied id that namespaces the board at every rung above `block`. The storage backing is derived, not chosen, and the library constructs and registers the collection.**

   The five values are one monotonic ladder of lifetime-and-reach: `block` ⊂ `request` ⊂ `session` ⊂ `user` ⊂ `org`. Each maps to a backing that already exists — `block` to the host generator's own state (exactly today's board), `request` to request state, and the three durable values to a `defineTaskCollection` at that scope. The consumer answers "how long should this board live," which is the question they actually have; nobody picks a storage shape.

   **It lives on the binding, not the library, and that is load-bearing rather than cosmetic.** One library is installed once and bound per generator via `skills.with({ … })`. A board configured library-wide would give every binding of that library the same durable resource, so a task created by one generator could be listed or drained by another using a different roster and different workers — breaking the private-per-generator contract `apps/docs/docs/skills/delegation.md` states today ("scoped to the one generator that installed it, never shared with or namespaced against any other block").

   **This applies to `request`, not only to the durable rungs.** `RequestBackingSpec.stateKey` defaults to the `collectionId`, and the delegation surface passes a constant one — so two bindings at `request` land on the same request-state field and can drain each other's tasks, exactly the durable defect one rung down. The id therefore namespaces every rung above `block`; `block` alone is exempt, because a generator's own state is private by construction. Two earlier drafts each missed one half of this: one derived the id from the library's collection key, the other scoped the fix to durable storage only.

   **And at `user`/`org` it needs a flow namespace too — a third seam.** `defineTaskCollection` leaves `flowIsolation` unset, so `resolveResourceIsolation` falls back to the flow's `isolateUserState`/`isolateOrgState`, which resolve to `false` by default — meaning *shared*, keyed at the bare identity id. Two flows serving the same user that both pick the natural id `"researcher"` land on one `researcher/**` namespace and see each other's tasks. The fix is a **forwarded option on an existing primitive, not a new mechanism**: `defineResourceCollection` already accepts `flowIsolation`, and `defineTaskCollection` simply doesn't pass it through. Forwarding it closes the seam.

   **The `session` rung needs nothing here, and must not be given it.** `defineResourceCollection` rejects `flowIsolation: true` at session scope outright — sessions are intrinsically flow-bound, so a session board is already isolated by construction. So the seam is a `user`/`org` concern only, and whatever carries it has to be scope-aware rather than uniform across the ladder.

   Same private-board rule as the other two seams, one level further out; not a separate concern.

   **Both collision mechanisms are confirmed by execution, not just by reading** (same spike as Decision 3). Two request-backed collections sharing a `collectionId` land on one request-state slot and read each other's tasks, while a control with an explicit distinct `stateKey` stays isolated. At `user` scope, flow B read flow A's task under the same collection id, with the raw row sitting in the bare identity bucket and both flow-namespaced buckets empty; the session-scope guard fires with its exact message, and a user-scope control confirms the rejection is scope-specific.

   **One caveat, stated so it isn't overclaimed:** the `board` option does not exist yet, so the spike exercised the *mechanical basis* of these collisions, not the proposed surface. It also confirmed that today's delegation board **is** private per generator — sequencer backing over the host's own state. The defect this decision fixes therefore arrives only *if* this decision ships. That is a point in its favour rather than evidence of a live bug, and it should be read that way.

   The shape mirrors the binding's existing `activeState?: { scope, field }`, which already asks a caller to name a scope and a storage field for per-binding state — so this introduces no new vocabulary and no new place to look. The id is caller-supplied rather than derived because a derived key (a block path, say) silently changes when a block is renamed, which for a durable board means losing the board.

   *Alternative rejected — accepting a `DefinedTaskCollection`* (this spec's first two drafts). It loses on four counts once examined. **(a)** It cannot register itself: a caller-supplied collection is never declared in the library's capability resources, so `ctx.resources[boardId]` is absent at runtime — a real defect this spec was carrying a fix for. When the library constructs the collection it declares it in the same record it already declares the skills collection in, and **the defect stops existing rather than getting fixed**. **(b)** The board id has to come from somewhere, and on the binding it is one string beside the lifetime rather than a whole collection object — the same thing `activeState` already asks for. (An earlier draft derived it from the library's collection key instead; that was the per-binding defect this decision now fixes.) **(c)** The `stateSchema` objection — that an enum can't express a typed task-input payload — is inert *on this surface*: the only creator of a task on a delegation board is the `addTask` tool, whose `input` is `z.unknown()`, so a typed payload schema buys the delegation path nothing. **(d)** `maxInstances` is *not* an argument for the collection form either, but **not for the reason an earlier draft of this decision gave.** That draft said it was "superseded by the task-layer caps in Decision 3." That was false: it was verified against Decision 3 as written and asserted of Decision 3 as it turned out to be, and those caps do not hold on the durable backing. The true reason is that `maxInstances` does not hold there either — it is checked against the same per-execution cache, and that cache is written only *after* the store round-trip resolves, so a concurrent creator reads a stale count across the widest yield in the path (see Decision 3). Exposing it would buy a ceiling that doesn't bind. **Whether a durable board is bounded at all is Decision 3's problem, and it is currently unresolved — see the consequence stated there.**

   *Alternative rejected — a union accepting either the lifetime enum or a `DefinedTaskCollection`.* Each arm stays simple and it would cover the one case the enum can't (sharing a board with a code-first `taskBoard` over the same collection — the app writes tasks, the agent drains them). Rejected under tenet 3: that case is speculative today, two ways to configure one thing is a permanent cost, and **the enum-only choice is the reversible one** — adding the collection arm later is additive, whereas removing it is not. Enum-only also strictly expands what is possible today, so it regresses nothing.

   *Ramification:* one new option on a surface that already carries its twin, no second import, and the durable values reuse the same primitive as the code-first path. **Only `block` is free.** Every other rung costs an id, because every other rung shares storage with something. That is the honest expression of the point that leaving the default board is a storage commitment rather than a flag — and it is one rung broader than an earlier draft claimed, which said `request` needed nothing. That narrows the enum's margin over accepting a collection, though it still wins on registration, on the absent second import, and on not dragging `stateSchema`/`maxInstances` along. Two things are given up: a caller cannot hand in a pre-existing collection (so a board shared with code-first `taskBoard` is out until the union arm is added), and a caller cannot set a typed task-input schema or `maxInstances` on the delegation board. `request` is the least-motivated rung — a delegation board is already re-enterable within a turn at `block` scope — but it is included because a ladder with a rung missing is harder to reason about than a complete one, and the backing it maps to already exists and is already routed.

2. **The report is filtered for every lifetime except `block`, which is returned unfiltered exactly as today.** On a durable board it reports the tasks this run engaged — those unfinished when the drain started, plus any created during it — from a snapshot taken inside `runBoard` before the drain. The verdict stays "any unfinished task ⇒ blocked."
   *Alternative rejected:* scoping by which turn created each task (drops a carried-over task this run completed). Also rejected: applying the same filter on both branches and *arguing* it comes out equivalent on the per-turn board. Two rounds of review found two different counterexamples to that argument — most recently a task the coordinator adds and cancels before draining, which is terminal at snapshot time and would vanish from a report that today includes it. Branching is what makes BP-035's off-state requirement true by construction instead of by an equivalence proof that keeps failing. Also rejected: exempting everything non-durable. BP-035 only obliges the **default** path to be unchanged, and the default is `block`. A `request` board can outlive an earlier block invocation within the same turn, so a later drain would inherit tasks an earlier one already completed — the same defect as the durable case, and it exists only because the ladder added that rung.
   *Ramification:* the default path is untouched, which is the point. On a durable board, finished work from earlier runs is not re-reported, so the coordinator's context doesn't grow without bound; work this run touched comes back with its output. A still-stuck task reports `blocked` on every later run — correct, and escapable via Decision 5. A task created and cancelled by the coordinator *before* it calls `runBoard` on a durable board is not re-reported; the coordinator cancelled it itself this turn and already has the result. **No new task-schema field and no migration for persisted rows.**

3. **A durable delegation board is UNBOUNDED *and* its task claims are NOT SERIALIZED across concurrent executions. The spec stops claiming otherwise on both counts. The existing type-level ban on cap options for the resource backing was correct and stays, and this issue changes nothing there.**
   **Evidence (BP-003).** Both consequences are reproduced by a spike rather than argued from code reading — `labs/SPIKE-durable-board-claims/` on `spike/durable-board-claims` @ `ebd8f96ad`, real `store-sqlite` on a real file, two concurrent `testFlow` executions sharing one store, each with its own execution context and resource cache, nothing load-bearing stubbed. Re-run with `pnpm --filter @flow-state-dev/spike-durable-board-claims test`. This matters because the reading below changed four times before it settled.

   *Alternative rejected:* every previous formulation of this decision. It has been restated four times — "coherent across backings", then "advisory", then "bounded within an execution", then "bounded by the number of in-flight requests" — and each was wrong in the same direction, claiming more than the substrate delivers. The fourth was the worst, because it prescribed a **test** for its bound, which would have passed and certified a false guarantee. The bound and that test are deleted rather than corrected to a fifth number.

   **One root cause, two consequences.** Durable storage offers no cross-execution atomic. `serializeResourceWrite` chains per storage key inside a *single* registry, and a registry is built per scope per execution; every read goes through the per-execution resource cache; every write is a plain `stores.resourceState.set(...)` with no version or compare. Nothing coordinates two executions over one board.

   *Consequence one — no ceiling, and by a shorter route than earlier drafts took.* The two task-layer caps are not merely unenforced on a durable board: `taskBoard` **refuses them at construction** — *"cannot take maxTotalTasks/maxEnqueuedTasks together with a supplied collection — caps belong to the collection."* So `maxInstances` is the only cap in play at all, and it reads the per-execution cache, which is written only *after* the store round-trip resolves. Measured: **8 rows created against `maxInstances: 4`** — exactly 2×, matching the `(requests − 1) ×` locally-visible-headroom shape. Each execution enforced its own ceiling *correctly*, which is the part that makes this hard to notice: an operator watching one request sees a properly-enforced cap and nothing wrong.

   *Consequence two — overlapping drains double-execute a task **by default**, and the second result wins.* This is the more serious of the two and it is a correctness hazard rather than a capacity one. It is also not a narrow race to be provoked: the spike reproduced it with **zero coordination** — a bare `Promise.all` of two drains over one seeded task, two distinct request ids, both worker bodies entered in the same millisecond. A barrier variant was written to force the interleave and turned out to be unnecessary. The sequential control ran the body exactly once, so the instrument can report "1" when that is the truth.

   Three observed details make it worse than "no error surfaced." **Both drains returned `status: "completed"`.** **`error_or_warning_items_emitted: []`.** And the surviving row carries **`attempts: 1`** — the ledger actively asserts the task ran once, so there is no artifact from which the doubled run could be reconstructed after the fact. `claim` re-checks eligibility *inside* `updateState`'s updater, which makes it race-free between workers in one drain; across executions each reads its own cache, sees `pending`, passes the re-check, and writes `in_progress` through a plain `set`. The `resource-backed.ts` header's "at most one worker claims any given task" is true within an execution and becomes false the moment a board is shared across them — precisely what this spec introduces.

   `maxInstances` was checked on its own terms, since the registry create branch is a different mechanism from the task-layer caps. It fails the same way with a wider window, so it is not a fallback ceiling and Decision 1's enum deliberately does not expose it.

   **A third hazard, different root cause, same silence — a durable board can outlive its roster.** Tasks persist; the roster is rebuilt per execution from the live skill manifest (`collectAgentSources` re-resolves per `resolveBuild` and honours a live `disable-model-invocation`). So a task assigned to `beta` in turn 1 can be drained in turn 2 by a roster that no longer has `beta`. Measured: the drain reported `completed`, `t-beta` ran on **`FLOOR-generalist`**, and the stored row reads `assignee: "beta"`, `output: { persona: "FLOOR-generalist" }`, `attempts: 1`. Nothing records the substitution — the task claims one persona and was answered by another.

   The control is what makes this actionable: with the floor worker removed, the same scenario **fails loudly** — `t-beta` never runs and is stored `errored` with `[keyedRouter] no block registered under key "beta"`. The silence comes entirely from the default worker, and the delegation surface **always wires one** (`materializeFloor`, passed as `defaultWorker`). So the delegation path is on the silent branch by construction the moment its board is durable. Today's board is sequencer-backed and rebuilt per turn, so a stale assignee cannot survive to a later turn: **this is a hazard FIX-957 introduces**, the same shape as the double-claim. FIX-943 does not cover it — `utility.keyedRouter` already has an own-property guard *and* a `fallback` slot that takes precedence over the throw, so a prototype-named assignee lands on the floor rather than resolving to `Object.prototype.constructor` (verified). Sub-PR `d` fixes it rather than documenting it; see §8.

   **And the roster can empty entirely, which takes the whole surface with it.** With the roster emptied at runtime (a manifest flipped to `disable-model-invocation`, which `collectAgentSources` honours), turn 2's tool list is **`[]`** — all nine tools gone, `runBoard` included, and the guidance playbook with them. `resolveBuild` returns `{ tools: [], guidance: null }` as one unit, so there is no partial-surface question, and the turn completes with `error: null`. A control binding carrying `delegation: true` keeps the full surface under identical conditions.

   **Scope the harm correctly: this is availability, not durability.** Nothing is lost. The spike rescued an orphaned task out-of-band with a plain handler holding `board.capability` over the same collection — listed it, cancelled it, `status: "cancelled"` in the durable row, with no library, no roster and no generator involved. So no recovery tooling is warranted and nobody should scope a migration. What is lost is **the coordinator's ability to help itself**: mid-conversation the model cannot see, cancel or reassign work it queued, has no guidance text explaining why, and will keep planning against a board it cannot touch.

   **⚠️ STATED CONSEQUENCE AT SIGN-OFF.** A `session`/`user`/`org` delegation board has no working ceiling of any kind, *and* overlapping requests against it execute the same task twice by default with the later result silently winning, *and* a task whose assignee has left the roster is silently answered by the floor worker under a persona the record does not reflect. **The doubled run leaves no trace at all:** both drains report success, no warning item is emitted, and the surviving row reads `attempts: 1` — so the ledger does not merely fail to flag the duplicate, it asserts the opposite. Nothing downstream can detect or reconstruct it. All three are silent: none emits a warning item, and in two of them the stored row asserts the opposite of what happened. The first is the over-spawning hazard FIX-931 exists to close; the second is worse, because an unbounded board wastes money whereas a double-claimed task produces a wrong answer. The first two are rarer at `session` scope, where concurrent requests in one conversation are uncommon, and ordinary at `user`/`org` — **but the third applies at `session` scope too**, since it needs only a roster edit between two turns of one conversation. `session` is the safer rung for the storage hazards, not a safe rung generally.

   The owner's options, and what each actually buys given both consequences: **(i)** ship durability as-is and document both — cheapest, and defensible if `session` is the realistic use; note it does *not* make double-execution rare at `user`/`org`. **(ii)** add task-layer serialization over the shared memo Decision 1's sub-PR `d` already makes mandatory — an in-process promise chain above the registry, needing no collection-level atomic. **The spike settles this one: near-worthless here.** The double-claim needed no within-execution contention whatsoever — two independent executions, no shared in-process state — so an in-process lock has nothing to serialize. It is listed because it is the owner's to weigh, not because the evidence supports it. **(iii)** hold durability until FIX-939 lands a cross-execution atomic — the only option that closes the *storage* problems outright.

   **(iv)** ship durability and document a required concurrency policy as a deployment constraint. **A correction first, because the conflation is easy and would otherwise propagate: request concurrency is *not* serialized by default.** `normalizeConfig(undefined)` returns `{ policy: "allow", key: "session" }` — `"session"` is the default *key*, not the default *policy*. Nothing serializes unless an author writes it. What is confirmed, measured in one run against a no-policy control: no policy → **2** worker-body invocations; `concurrency: "queue"` (session key) → **1**; `{ policy: "queue", key: "user" }` → **1**; `"reject"` → **1**, with the competing dispatch dropped and a clear message. It gates whole requests at the top of `dispatch`, before any request record exists.

   Its limits all belong in the option, because they decide where it is usable: it is **opt-in** against an `allow` default; it is a **per-host in-process gate** (one arbiter per host over a keyed async gate and a `Map`), so two hosts sharing one SQLite store still produced **2** invocations — sharing the database buys nothing; the host **skips arbitration entirely** for external dispatchers; `key: "user"` puts every dispatch of that action for that user behind one FIFO with a 30s wait budget, and `org` would do that to an organization; `queue` with the default `session` key on a sessionless dispatch resolves to `key: undefined` and **degrades silently to passthrough**; and it closes the double-claim but not the unbounded ceiling, since the queue is per action key rather than per board. **Honest assessment:** (iv) makes `session` scope defensible *with a documented deployment requirement*, and does **not** make `user`/`org` safe, because the multi-instance case defeats it. **This spec picks none.**

   *Ramification:* the cap work disappears from this spec entirely — combined with Decision 6, sub-PR `a` is gone rather than merely smaller. The FIX-931 rationale this spec previously proposed deleting — that a cap on the resource backing should be a compile error rather than a silently ignored ceiling — turns out to have been right, so it stays and the type-level ban stays with it. The state backing is untouched: its caps remain atomic inside the CAS write.

4. **⚠️ OWNER DECISION — whether to guard the `in_progress` / `awaiting_review` → `pending` transition. Not decided here.** Guarding it reverses FIX-953's signed-off Decision 5c ("`unblockTask` is a thin wrapper… no status precondition of its own"), so it needs the same sign-off weight that decision got. Two options:
   - **(A) Re-affirm 5c.** `unblockTask` stays a thin wrapper; the transition stays permissive. Cheapest, consistent with the record.
   - **(B) Guard it.** The unblock path refuses `in_progress` and `awaiting_review` sources.

   *Recommendation: (B).* 5c's stated reasoning was that no coordinator tool reaches `awaiting_review` today. That premise is weaker now: a fan-out worker holding board tools mid-drain is a real, reachable writer, and it can move a running task back to `pending` — manufacturing exactly the drain-containment failure FIX-951 exists to contain.
   *Ramification either way:* (B) closes a model-reachable path to a known drain failure and costs one refusal the coordinator may hit legitimately. (A) leaves it open and keeps the signed-off record intact.

5. **`unblockTask` ships in this issue, re-grounded on the two arguments that survive independent of turns, and is built in parallel rather than gating the durability work.** Those arguments are the mid-drain fan-out exit (a task blocked inside a drain otherwise has only `cancelTask`) and dependency corruption (cancel-and-re-add mints a new id; `deps` resolve by id and require `completed`, so every dependent becomes permanently unrunnable with no error surfaced).
   *Alternative rejected:* implementing FIX-953's spec as written, whose primary argument was a cross-turn case that didn't exist. Also rejected: moving the tool back out to FIX-953 — it landed here only because FIX-953 was closed as a duplicate, and moving it back invites it to be lost a second time, which has already happened once.
   *Ramification:* the coordinator gains a ninth task tool. **The earlier claim that "nothing in the durability path waits on it" was wrong and is withdrawn.** Sub-PR `d`'s refusal needs a tool through which the coordinator acts on a refusal, and the empty-roster gate fix has to carry that tool from the moment the refusal lands rather than retrofitting it — `unblockTask` does not exist today, in any spike arm including the healthy control. So `d` now depends on `c` (§8) — and that edge is **load-bearing on evidence, not caution**: with the refusal parking tasks `blocked`, there is *no* model-facing tool that moves `blocked → pending`, and the spike's own recovery had to call `collection.unblock()` in code. Without `c`, `d` ships a state the coordinator cannot leave. Decision 4 still gates only the *guard*, not the tool, so it does not gate `d` transitively.

6. **DROPPED — the typed capacity error is not this spec's to ship, because nothing in the surface this feature adds can reach it.** The delegation option is `{ lifetime, id }`; Decision 3 leaves durable boards uncapped; and the collection the library constructs never sets `maxInstances`, which the registry checks only when it is defined. So the retention refusal cannot fire through any public path this feature introduces, and its promised test would have needed a hand-wired collection rather than the feature itself.
   *Alternative rejected:* exposing a retention option so the error becomes reachable — new public surface invented to justify a test, which is backwards.
   *Ramification:* the spec sheds a deliverable and a user-facing promise (`board_at_capacity` is no longer offered). **The underlying defect is real but belongs elsewhere:** a code-first `taskBoard({ collection: defineTaskCollection({ maxInstances }) })` still hard-throws a plain `Error` at the model boundary. Recorded as a follow-up in §12; revisit here only if retention config is ever exposed on the delegation surface. The number is kept rather than renumbered so an earlier reading still lines up.

7. **Tool descriptions and delegation docs state the board's real lifetime, and say it depends on how the board was configured. Documentation ships inside the PR that introduces each surface, not as a trailing docs PR.**
   *Alternative rejected:* correcting the descriptions to today's boundary as a separate early fix and again later; also rejected, a trailing docs-only sub-PR, which contradicts the repo's own rule that user-facing changes are documented in the same change set.
   *Ramification:* one description change instead of two, and no window where a shipped surface is undocumented. FIX-958 separately fixes the code comments that wrongly claim the ledger already survives.

8. **⚠️ OWNER DECISION — sequencing FIX-960 (rename the `sequencer` backing to `state`) ahead of this work. Not enacted here.**
   *Recommendation: yes, but the argument has weakened as this spec shrank.* It was originally that FIX-960 rewrites the same files as this spec's cap work; that cap work is now shed (Decisions 3 and 6), so there is no longer a collision to sequence around. What remains is the coherence case on its own terms — the `sequencer` discriminant lies at one of its own call sites, and this spec's lifetime ladder is the same insight applied to the public surface, so landing them near each other keeps one story. *Ramification:* no longer a dependency of any kind; purely an ordering preference. If it is not obviously cheap, drop the sequencing.

**Non-goals.** Not building: durable non-sequencer *block* state (FIX-917's deferred follow-up — a different failure mode); detached/background jobs that run outside any request (FIX-939); a spend/cost ceiling (FIX-933 owns spend, and a row count is the wrong noun for it); a `pending`-subset bound derived from the resource registry (it has no notion of task status); retry-storm accounting (FIX-948 — see §12); FIX-950's soft-error contract.

**Size estimate: Medium–Large** (multi-PR, across `orchestration` and docs). **PR plan shape** (the detail is in §8): three sub-PRs. Two are independent and build in parallel — the run's working set and the `unblockTask` tool. The configurable board depends on **both** *and* is **gated on Decision 3 being answered**, because it is the PR that makes a board durable. Scope was shed twice in review — the cap-enforcement refactor, then the typed capacity error — which is most of why this is no longer Large. Docs ship inside each PR.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

One package (`@flow-state-dev/orchestration`), after this spec shed the capacity error (Decision 6), across two layers. The **delegation surface** (`skills/`) owns the board's construction, the tools, and the drain, and carries nearly all the work. The **task collection** layer (`tasks/collection/`) keeps its caps and backings untouched but is **not** left alone entirely: `defineTaskCollection` has to forward one option it currently drops, for Decision 1's third seam. That forwarding is the only change outside `skills/`.


**The board's home becomes derived, not a constant.** Today the delegation surface builds its collection with a hardcoded state backing against the host generator's own state. It becomes a mapping from the lifetime value: `block` → the host generator's own state (today's path, unchanged), `request` → request state, and `session`/`user`/`org` → a `defineTaskCollection` the library built at that scope.

**The binding id is what keeps rungs above `block` isolated, and it is needed one rung lower than it first appears.** The delegation surface passes a constant `collectionId`, and `RequestBackingSpec.stateKey` defaults to exactly that — so at `request` two bindings share one request-state field unless the id is threaded into the state key. Above that, the id distinguishes the declared collections. `block` needs nothing: a generator's own state is private by construction. Whatever mechanism carries the id, it has to reach the state key on the request rung and the collection identity on the durable ones — one id, three seams.

Three consequences follow, and the third is easy to miss:

- The surface's early bail-out when the host generator has no own state must only fire on the state-backed branch — under a durable board the host's own state is irrelevant.
- The resolver handed to fan-out workers already flows from this one construction site (`boardTaskTools`, threaded through the worker materializers in both `orchestration` and `workforce`), so those call sites need **no change** — they inherit the configured backing for free.
- **The durable board must be declared as a resource, and under Decision 1 the library is what declares it.** This was a live defect while the option accepted a caller-supplied collection: `taskBoard` registers a `DefinedTaskCollection` handed to it *directly* (it builds an internal resource-declaring capability keyed on the collection id), but the delegation surface never takes that path — it passes a *factory*, which routes to `taskBoard`'s factory branch and registers nothing. A caller-supplied collection would therefore have been unresolvable at runtime. Under Decision 1 the library builds the collection from the lifetime value, so it declares it in the same `resources` record it already declares the skills collection in (`DeclaredResourceEntry` accepts a `DefinedResourceCollection`, which is what `defineTaskCollection` returns). **The defect dissolves rather than needing a fix** — the library builds it, so the library declares it. Two durable bindings declaring the same id collide at build time like any two resources claiming one key.

> **Correction to the issue's framing, worth stating because it reduces scope.** The issue lists `defaultOwnStateResolver` returning `undefined` under non-own-state backing as a blocker "also hit via `worker-materializer.ts` and `workforce/src/materialize-agent.ts`." Reading those two sites: both already prefer the injected board capability and fall back to the own-state singleton only when none was supplied — which is correct for a standalone, boardless consumer. So `defaultOwnStateResolver` stays own-state-only and needs no change.

**Caching the resolved collection is mandatory, not an optimization.** `getOrCreateTaskCollection` never caches — every call builds a fresh reference, and on the resource branch each construction awaits a full collection listing to hydrate its mirror. `boardCollection()` is reached from many distinct places per turn: each of the flat task tools, each fan-out worker's board-bound capability, the board capability's accessor, the drain's per-worker resolution, and settle. Without a per-execution memo the durable branch pays a listing at each of them. The memo must be shared by all of those, or it only partly binds.

> One precision, because a reviewer stated the mechanism slightly too strongly: the drain's idle-wait path does *not* re-resolve on every worker-loop iteration — it caches the collection in a per-worker cell after the first resolve. The multiplicity comes from the number of distinct resolve *sites* listed above, not from loop iterations. The conclusion is unchanged.

**The run's working set replaces the turn stamp, and applies at every lifetime except `block`.** `runBoard` is already a sequencer (`drain` → `settle`). Above `block` it gains a step before the drain that records which task ids exist and which of them are unfinished; settle then reports the ids unfinished at that moment plus any id present now that wasn't in the snapshot. At `block` settle returns the full list exactly as it does today — no snapshot, no filter, nothing to prove.

Branching here is deliberate and is the lesson of three review rounds. Two drafts applied one rule everywhere and argued it came out equivalent on the default board; both were wrong, in different ways (the second missed a task the coordinator adds and cancels before draining, which is terminal at snapshot time). A third drew the branch at "durable" and missed that `request` can also outlive an earlier drain. The equivalence isn't worth proving when the branch is one condition — and the condition is `block`, not durability.

This needs no field on the task schema, no stamping, and no migration — the snapshot is taken in-request and consumed in the same run.

> **Illustrative — a sketch, not the contract.**
> ```ts
> // every lifetime except `block`:
> //   before drain: { ids: Set<string>, unfinished: Set<string> }
> //   at settle:    working = snapshot.unfinished ∪ (currentIds − snapshot.ids)
> // block: working = every task, as today
> //   verdict (both): working.some(unfinished) ? "blocked" : "drained"
> ```

**The stale-assignee refusal is a preflight step, not a routing change.** `runBoard` is already a sequencer; it gains a step that walks the ledger before the drain and parks any task whose named assignee is absent from the live roster as `blocked`, with the reason on the task's `error`. It sits **after the board seeds and before the drain** — a board using `initialTasks` seeds inside the drain, so a preflight placed ahead of that sees an empty ledger. Nothing at the worker or router layer changes: `blocked` is already non-terminal, already excluded from `inFlightCount`, already counted unresolved by settle, and `blocked → pending` is already permitted, so recovery is reassign-then-unblock through existing verbs.

**The cap surface does not move.** An earlier plan lifted the check into a shared module and had both backings call it. That is dropped: on durable storage there is nothing a lifted check could enforce (Decision 3), so the state backing keeps its check inside its own CAS write, unchanged and still atomic, and the resource backing keeps its type-level ban on cap options. Deleting a planned refactor is the right outcome here — the existing shape was correct and the spec was wrong about it.

**Sub-PR `d` is additionally gated on Decision 3 being answered, and must not be started while it is open.** `d` is what makes a board durable, so building it against an open Decision 3 ships the unbounded and double-execution paths under a decision the owner has not made — the plan would quietly settle what the spec says it is not settling. Start `d` only once the owner has accepted the documented consequences (option i or ii), adopted the concurrency policy as a documented deployment requirement (option iv), or the cross-execution atomic has landed (option iii).

**Within each sub-PR.**

*b — the working set.* Add the pre-drain snapshot and the settle partition together, behind the not-`block` condition — they're one behavior. Test both branches separately: at `block` the filter must not run at all (including `addTask` → `cancelTask` → `runBoard`); at `request` and above, a carried-over task completed by this run comes back with its output, a task finished before this run does not, a task added mid-drain does, and the verdict reflects only the working set. `request` needs its own case — it is the rung that made "durable-only" wrong.

*c — unblockTask.* The tool, its soft-error contract, and the dependency-preservation behavior (the id is stable, so dependents stay runnable). The guard is gated on Decision 4 — **if the owner picks (A), the guard is not built and this PR is smaller.**

*d — the option.* The per-binding option, the id threaded to all three seams — including the `flowIsolation` forwarding, which is scope-aware because session scope rejects it — construction and declaration of the durable collection, the backing derivation, the conditional guard, the memo.

**The refusal and the empty-roster gate fix must ship in the same PR — this is a constraint, not two bullets.** Landed separately, the refusal makes the empty case *worse than today's behavior*: today a departed agent's task at least completes, wrongly, under the floor; with the refusal in place and no gate fix it fails instead, and there is no tool left through which the coordinator can act on the failure. Neither half is shippable alone.

**The gate fix is two gates and roughly two lines.** There is a **runtime** gate — `resolveBuild` returning `{ tools: [], guidance: null }` when the roster resolves empty — and a **build-time** gate — `delegationPossible = delegationOn && (staticAgentSkills.length > 0 || dynamicAgentEligible || allowEmptyRoster)`, which when false never declares the board field and never attaches the tools function at all. A fix touching only the runtime gate leaves a binding whose roster was *never* non-empty at build time with no board whatsoever. Both need the same disjunct.

`allowEmptyRoster` has exactly one assignment in the package — `allowEmptyRoster = cfg.delegation === true` — and nothing on the delegation path derives it. Decision 1's lifetime option is the signal: a configured durable board should set it, at both gates. No new public option is needed, because `delegation: true` already means precisely "keep the surface installed with an empty roster," which is the property a durable board requires. FIX-940's own comment at that site anticipated this: *"merely deriving delegation from a declared roster does NOT set this — an emptied derived roster tears the surface down as before."* The author described the hole exactly; the durable board is what makes it matter.

**Plus the stale-roster refusal, and the spike settles where it lives: a PRE-CLAIM preflight that parks the task `blocked`.** The distinction is between *no assignee* — use the floor, correct and intended — and *an assignee was explicitly named and is no longer on the roster*, which must not silently substitute. Earlier drafts left the mechanism to the implementer; the evidence closes that, because the two obvious placements both fail.

**Post-claim is rejected — it is strictly worse than today's silent floor.** Once a worker holds the task there is no recoverable outcome: returning marks it `completed`, throwing marks it `errored`, both absorbing, and `settle` reports `drained`. There is no retry budget to fall back on, and `maxAttempts` is not among `addTask`'s six model-facing fields, so a delegation task cannot be given one at all. Worse, two of the three recovery attempts a coordinator would make **report success while doing nothing useful**: `assignTask` returns `{ ok: true }` on a terminal task *and writes the new assignee* (`setAssignee` → `patchOne` changes no status, so the transition guard never runs), and `cancelTask` returns `{ ok: true }` and changes nothing (`collection.cancel()` passes `{ ifAllowed: true }`, so the decline happens silently inside the CAS write). Only `blockTask` refuses loudly. A refusal delivered post-claim therefore leaves the coordinator confidently wrong — today's floor at least produces an answer.

**Leaving the task `pending` is also rejected, on measurement rather than taste.** It spins: `hasClaimableTask` tests only `depsSatisfied` and knows nothing about assignees, so an unclaimable pending task reads as claimable every iteration. The spike hit the iteration ceiling at 6/6; at delegation defaults (`maxIterations` 10,000, `BOARD_CONCURRENCY` 4) that is **40,004 claim attempts against a durable store per orphaned task**. It terminates and reports `blocked` via settle, so it is not a hang — but it is a hot loop over persistent storage, and closing it would mean teaching assignee eligibility to `hasClaimableTask`, a shared predicate the dependency gating also depends on.

**Parking as `blocked` needs no substrate change.** Measured at 13ms: the healthy sibling drains normally, the orphan is never claimed, `settle` reports `blocked` with the reason on the task's `error` field, and reassign-then-unblock returns it to `pending` under the new assignee. Every property already exists — `blocked` is non-terminal, excluded from `inFlightCount`, counted unresolved by settle, and `blocked → pending` is already permitted. The preflight is an ordinary step before the drain, not a framework change.

> **Ordering caveat, and it is not incidental.** The preflight must run **after the board seeds and before the drain**. A board using `initialTasks` seeds its ledger *inside* the drain; the spike's first attempt placed the preflight ahead of that and got the post-claim `errored` outcome instead.

Test the off state hardest (BP-035): at the default `block` lifetime every behavior above must be inert and today's path bit-for-bit unchanged. Test each rung resolves to the backing it should, and — the case that matters — that **two bindings of one library get separate boards, run once per rung above `block`**. That is the same test with a different lifetime value, not a second test design; `request` is included because it is the rung where the default state key would otherwise collide.

**Removals** (tenet 3): the hardcoded own-state backing at the delegation construction site, replaced by the lifetime mapping. Note what is deliberately *not* removed — the FIX-931 comment and the resource backing's type-level cap ban both stay, having turned out to be right (Decision 3).

### 9. Edge cases & error handling

| Case | Expected behavior |
|---|---|
| Default lifetime (`block`) | Identical to today in every respect. The settle filter does not run at all on this branch, so the returned set is today's by construction, not by argument. Includes the sequence `addTask` → `cancelTask` → `runBoard`, where the cancelled task is still reported. |
| Carried-over task unblocked and completed by this run | Returned with its output, and does not set `blocked`. This is the §5 scenario and the goal check. |
| Task finished by an earlier run, untouched by this one | Not returned. Keeps the coordinator's context bounded. |
| Task created mid-drain by a fan-out worker | In the working set (present now, absent from the snapshot), so it is reported and counts toward the verdict. |
| Durable board, earlier run left a task `blocked`, still blocked | In the working set; sets `blocked`. Correct, and escapable via `unblockTask` / `cancelTask`. |
| Any concurrent creation on a durable board | **No cap binds** — not the task-layer caps, not `maxInstances`. Stated consequence (Decision 3), not a bound to test. Do not write a test asserting a maximum overshoot; there is no true number to assert. |
| Two concurrent requests draining one durable board | **Both can claim the same task**, both execute it, and the later result overwrites the earlier with no error surfaced. Stated consequence (Decision 3), not a behavior to guard here — the in-updater eligibility re-check is race-free only within an execution. |
| Durable board, task assigned to an agent the roster no longer has | **Parked `blocked` by the pre-claim preflight**, never claimed, reason on the task's `error`; `settle` reports `blocked`. Recoverable by reassign-then-unblock. Measured today: silent substitution — drain `completed`, `assignee: "beta"`, `output.persona: "FLOOR-generalist"`, `attempts: 1`. |
| Orphaned task left `pending` instead of parked | Rejected shape — spins. `hasClaimableTask` sees only `depsSatisfied`, so it reads as claimable every iteration: 40,004 claim attempts at delegation defaults. Terminates, but hot-loops a durable store. |
| Orphaned task refused after a worker claims it | Rejected shape — unrecoverable, and `assignTask`/`cancelTask` both answer `{ ok: true }` while achieving nothing. |
| Durable board, roster empty, orphaned tasks present | Every task parks `blocked`, nothing runs, no spin, `settle` reports `blocked`. Only actionable if the surface survived — the C7 gate fix, same PR. |
| Durable board, roster empties mid-conversation | The surface survives: tools and guidance still installed, so the coordinator can still see, reassign or cancel queued work. Measured today: tool list `[]`, guidance `null`, turn completes `error: null`. |
| Durable board, task with no assignee at all | Runs on the floor, unchanged. The delegation floor working as designed; must not be caught by the refusal above. |
| Two bindings of one library, any rung above `block` | Separate boards, `request` included. Each binding names its own id, so neither can list or drain the other's tasks. This is the private-per-generator contract; a library-level option broke it for the durable rungs and a durable-only fix broke it for `request`. |
| `board: { lifetime: "request" }`, second drain in the same request | Tasks the earlier drain completed are excluded from the later report — `request` is filtered like the durable rungs, not exempted with `block`. |
| Sequential turns on a durable board | Each execution loads the board from the store at start, so earlier turns' tasks are visible and addressable. No ceiling binds (Decision 3). |
| Batch add crossing a cap, state backing | Nothing inserted — the single CAS write makes it all-or-nothing. Typed cap breach → soft error. Unchanged by this spec. |
| Batch add hitting a store failure mid-batch, resource backing | A prefix may land. Documented residual difference; no rollback machinery. |
| Two durable bindings declaring the same board id | Build-time collision error, like any two resources claiming one key. |
| Own-state guard, durable board configured, host generator has no own state | Surface installs normally — the guard must not fire. This is the bug the conditional fixes. |
| Hand-wired `taskTools` (no skills binding) | Unchanged: own-state, uncapped, no roster. Explicitly out of scope. |

**Second-path checklist (BP-035).** *Legacy:* the persisted task envelope is a migration surface now that rows outlive deploys; this spec adds no field to it, which is the cheapest way to stay safe. *Null boundary:* the board option is optional and absent by default; guard it. *Concurrency:* the unbounded durable board **and its unserialized claims** (Decision 3), plus the memo/staleness interaction in §12 — none closed here, all stated. *Multi-tenant:* a durable board at `user` or `org` scope is shared across sessions by construction — the caller's explicit choice, with `session` documented as the conservative default. *Cost observability:* more surviving tasks means more context replayed, which is exactly what Decision 2's working set bounds. *Flag off-state:* covered above and the hardest test target.

### 10. Testing strategy

**Discipline: `diagnose`** (Linear category: Bug). The feedback loop is vitest at the collection and surface seams — `packages/orchestration/src/tasks/collection/tests/` and the skills/delegation tests already exercise these paths including cap behavior, so the reproduction can be written before the fix in each sub-PR.

**Goal check (real path, real model).** A delegating skill configured with a session-scoped board, run over two turns through `fsdev run`: turn 1 plans three tasks, drains two, leaves one blocked; turn 2 unblocks and drains it. Passes when turn 2's `runBoard` reports `drained`, returns `t3` *with its worker output*, and the task id from turn 1 still resolves.

**Required: a mocked two-turn flow-integration scenario.** The cross-request contract must not rest on a manual real-model run — a unit test at the surface seam cannot catch a missing resource declaration or request-to-request composition, which are exactly the two failure modes sub-PR `d` introduces. Drive two actions against shared stores and one session id: turn 1 blocks a task, turn 2 unblocks and drains the same task, asserting the id resolves across the boundary and the output comes back.

**Required: a hydration call-count assertion.** Assert the number of collection listings per execution on the resource branch. A BP-035 off-state test passes whether or not the memo actually binds on the durable path, so without a call-count assertion the memo is untested — the test would prove it exists, not that it works.

**Required: an empty-roster survival test.** Turn 1 queues work on a durable board; turn 2 runs with the roster emptied at runtime. The tool surface and guidance must both survive, and the coordinator must be able to act on the queued task. A build-time arm belongs beside it — a binding whose roster was never non-empty must still get a board. Both gates, or the test only proves half the fix.

**Required: preflight behavior pinned four ways.** The orphan is parked `blocked` and never claimed; the drain does **not** spin (assert the claim-attempt count, not just termination — the failing shape terminates too); `settle` reports `blocked` and the reason is legible on the task; and reassign-then-unblock returns the task to `pending` and it then runs. A healthy sibling must drain normally in the same run, or the test cannot tell "parked correctly" from "drain broken." Pin the preflight's position relative to seeding, since placing it before the board seeds is what produced the rejected post-claim outcome.

**Required: a two-turn roster-change test.** Turn 1 seeds a task assigned to `beta` into a durable board without draining; turn 2 drains the same board with `beta` removed from the roster. The named-but-absent assignee must refuse visibly, and a companion case with *no* assignee must still run on the floor — the test is only meaningful if it pins both sides of that distinction, since the fix is exactly the boundary between them.

**Deliberately NOT tested: any overshoot bound on a durable board.** There is no true bound to assert (Decision 3), so a test claiming one would pass and certify a false guarantee. If option (ii) is later chosen, the within-execution case becomes testable; nothing about the cross-execution case does.

**Other CI specs, in observable terms.** The `block` default returns the same task set as today, including for `addTask` → `cancelTask` → `runBoard`. The state backing's caps still refuse past both bounds and a cap-crossing batch still inserts nothing there — regression cover, since this spec no longer touches them. Settle: carried-over-and-completed returned with output; finished-before-this-run omitted; added-mid-drain included; verdict from the working set only. `unblockTask` returns a blocked task to `pending` with a stable id and dependents still runnable. The own-state guard does not fire under a durable board. Board-id collision throws at construction. Per Decision 4(B) if chosen: the unblock path refuses `in_progress` / `awaiting_review`.

Tests must encode *why* (tenet 7 / CLAUDE.md §5) — e.g. the carried-over test asserts the output comes back *because* withholding it is what made the first draft's rule wrong, not merely that a filter has a particular shape.

## Spec evolution

- **Spec drafted** — framed the problem as "an existing durability primitive the delegation path can't reach" rather than "build board persistence," so the fix reuses `defineTaskCollection` instead of inventing a second mechanism; settled the four blockers (turn-scoped settle, cross-backing caps, typed capacity error, a parked task's exit), accepted advisory rather than atomic cap enforcement on the durable backing as a deliberate weaker guarantee, and split the work into five sub-PRs with three building in parallel. Left two calls to the owner rather than deciding them: reversing FIX-953's Decision 5c, and sequencing FIX-960 first. Recommended not absorbing FIX-948, with the one sentence this spec owes it.
- **After spec review** — replaced the turn-stamp rule with "the tasks this run engaged," because two reviewers independently showed the stamp dropped a carried-over task the run had just completed (the one scenario the feature exists for) and would have changed the default path's output too; this also removed the task-schema field and its migration. Made the durable cap check re-read authoritatively before deciding, because the mirror-only check let overshoot scale with the number of writers rather than staying within a few tasks, which was the premise Decision 3 rested on. Moved the capacity error type to `core`, because orchestration has engine only as a dev dependency and catching an engine class at runtime would have inverted the layering. Added the resource declaration and id-collision rule to sub-PR `d`, because the supplied collection would otherwise be unresolvable at runtime. Folded docs into each feature PR and ungated `d` from `c`, dropping the plan to four sub-PRs.
- **After spec review (round 2)** — stopped claiming the durable cap check is "authoritative" and replaced it with an explicitly bounded guarantee, because the registry's `list()`/`count()` enumerate a per-execution cache and never reach the store: the cap holds within an execution and across sequential turns, but cannot hold across concurrently in-flight requests without a store-backed count the substrate doesn't have. Added a retention-headroom pre-check, because the task caps could pass and the create loop then trip the storage limit partway, landing a prefix under a whole-batch promise. Made the settle filter apply **only on the durable branch**, because two successive attempts to prove one rule was equivalent to today's behavior on the per-turn board were both wrong — a branch makes it true by construction instead.
- **After spec review (round 3, owner)** — reversed Decision 1 to a lifetime enum (`block` → `org`) with the backing derived, after the owner reopened it and its rejection paragraph failed its own premise: an enum doesn't invent a vocabulary beside `defineTaskCollection`'s, it finishes the one already there, which is the same insight FIX-960 is acting on internally. Three of the objections to the enum turned out not to bind on this surface (`stateSchema` is inert because the model's `addTask` types `input` as unknown; `maxInstances` is superseded by the task-layer caps; the board id derives from the library's collection key). The fourth reversed direction entirely: because the library now constructs the collection, it can declare it in the resources record it already owns, so the unregistered-collection defect and the id-collision case both stop existing instead of needing fixes. A union with the collection form was weighed and rejected under tenet 3 as the non-reversible choice.
- **After spec review (round 4)** — resolved a hazard that lived only in the interaction of Decisions 1 and 3: D1 dropped `maxInstances` as "superseded by D3's task-layer caps," but those caps don't hold on the durable backing, so a durable board had no working ceiling at all — FIX-931's over-spawning hazard reintroduced at the durable tier. Checked whether `maxInstances` is enforceable there and it is not, for the same structural reason and with a wider window: it reads the same per-execution cache, and `persistResourceKey` writes that cache only *after* awaiting the store, so a concurrent creator reads a stale count across a full store round-trip. D1's rationale is corrected and the unbounded result is now a stated consequence in D3 with three options for the owner, rather than something derivable six months later.
- **After spec review (round 5)** — moved the board option from the library to the **binding**, mirroring the existing `activeState?: { scope, field }`, after review found the previous draft's library-derived id gave every binding of one library the same durable resource: one generator could have drained another's tasks with a different roster, breaking the private-per-generator contract the delegation docs state. Extended the settle filter to every lifetime except `block` — the `request` rung this spec's own ladder added can outlive an earlier drain in the same turn, and BP-035 only obliges the *default* to be unchanged. And stopped claiming a cap on the durable backing at all: `maxInstances` was checked on its own terms and fails the same way with a wider window, so the decision now states plainly that a durable board is unbounded, deletes the overshoot bound and the test that would have certified it, and keeps FIX-931's type-level ban — which turns out to have been right all along.
- **After spec review (round 6)** — two fold-ins of existing decisions, no new direction. Extended Decision 1's binding id to namespace **every rung above `block`**, not just the durable ones: `RequestBackingSpec.stateKey` defaults to the `collectionId` and the delegation surface passes a constant, so two bindings at `request` shared one state field — the same private-per-generator break, one rung down. And widened Decision 3 after verifying that durable claims are not serialized across executions either: `updateState` reads a per-execution cache and persists with a plain `set`, and `serializeResourceWrite` chains per key within a single registry, so two concurrent drains of one board can both claim a task, both run it, and the later result silently wins. That is the same missing cross-execution atomic as the unenforceable caps, so it widened the existing decision rather than opening a new one — but it is a correctness hazard where the caps are only a capacity one, and it changes what Decision 3's three options are worth.
- **After spec review (round 7, final)** — three consistency fold-ins, all of which shrank the spec. Extended Decision 1's namespacing to a **third seam**: `defineTaskCollection` leaves `flowIsolation` unset and the flow default resolves to `false` (shared), so two flows serving one user that pick the same natural board id share a storage namespace. Gated sub-PR `d` on Decision 3 being answered, closing a contradiction where the plan scheduled the durable path unconditionally while the decision it depends on was open. And **dropped sub-PR `a` and the `board_at_capacity` promise**: the delegation surface exposes only `{ lifetime, id }`, Decision 3 leaves durable boards uncapped, and the constructed collection never sets `maxInstances` — so the retention refusal is unreachable through anything this feature adds, and its required test would have needed a hand-wired collection. The underlying defect is real for the code-first path and moved to §12. Also repaired three Decision-1 edits from round 6 that a failed edit script had silently dropped.
- **After spec review (round 8)** — fixed two things round 7 left contradictory or stranded. It added Decision 1's third seam while simultaneously declaring the `tasks/collection` layer untouched, and both cannot hold: closing the seam means forwarding `flowIsolation`, an option `defineResourceCollection` already accepts and `defineTaskCollection` simply drops — a forwarded option on an existing primitive, not the collection-level mechanism the review implied. Reading that path also surfaced the session-scope guard (`flowIsolation: true` throws there), which makes the flag scope-aware rather than uniform across the ladder. And deleted the last live capacity promise that round 7's drop of sub-PR `a` had left standing — the second time a shed decision left prose behind, which is why the sweep now greps for what should be *absent* rather than only for what was added.
- **After spec review (round 9)** — recorded two implementer-time notes in §13 rather than folding them, per the rule that spec review is a direction check and below-the-bar feedback reaches the implementer without distorting the design: sub-PR `b`'s changeset altitude (internal until `d` exists, and permanently so if Decision 3 lands on option iii), and the docs obligation `flowIsolation` creates on the exported `DefineTaskCollectionOptions` surface.
- **After the durable-board spike** — replaced read-derived evidence with executed evidence for the four claims Decisions 1 and 3 rest on, using a real SQLite store and two concurrent executions sharing it. Nothing was contradicted, but three things turned out stronger or earlier than the prose: the double-claim needs **no coordination at all** to reproduce, so "can run twice" became "runs twice by default"; the doubled run leaves *no* recoverable trace, because both drains report success and the surviving row reads `attempts: 1`, which the sign-off warning now says outright; and the task-layer caps are **refused at construction** on a durable board rather than merely unenforced, which shortens Decision 3's route to `maxInstances` being the only cap in play (measured: 8 rows against a limit of 4, each execution enforcing its own ceiling correctly). Option (ii) moved from "worth less than it looked" to near-worthless on evidence — the failure involves no within-execution contention, so in-process serialization has nothing to serialize. Decision 1's collision basis is confirmed with the honest caveat that the spike tested the mechanism, not the unbuilt option, and that today's board is genuinely private per generator.
- **After the spike's second batch** — two more executed claims, one correcting an option and one adding a hazard the spec did not have. Decision 3 gains **option (iv)**, request-level concurrency policy as a deployment constraint, which required correcting a conflation worth naming: `concurrency: "queue"` is *not* on by default — `normalizeConfig(undefined)` yields `{ policy: "allow", key: "session" }`, so `session` is the default *key*, not the default *policy*, and nothing serializes unless an author writes it. Measured against a no-policy control the policies do work (2 invocations → 1), but the option carries real limits: opt-in, per-host and in-process (two hosts over one store still double-executed), skipped for external dispatchers, and silently degrading to passthrough on a sessionless dispatch with the default key. That also falsifies the claim that (iii) was the only option touching double-execution. And a **third hazard** landed: a durable board outlives its roster, so a task assigned to a departed agent is answered by the floor worker with the record still reading the original assignee — silent, and unlike the first two it bites at `session` scope, since it needs only a roster edit between turns. The control (floor removed → loud `keyedRouter` failure) shows the silence comes entirely from the default worker, which the delegation surface always wires. Sub-PR `d` now fixes it rather than documenting it: a named-but-absent assignee refuses instead of falling through, while an unassigned task still uses the floor.
- **After the empty-roster spike** — confirmed the hole in `d`'s stale-assignee refusal and changed the fix's shape. An emptied roster does not degrade the surface, it removes it: tools `[]`, guidance `null`, turn completing `error: null`. Two corrections to how the spec would otherwise have handled it. First, there are **two** gates, not the one review named — a runtime gate in `resolveBuild` and a build-time `delegationPossible` gate that never declares the board at all, so a runtime-only fix would leave never-populated rosters boardless. Second, the harm is **availability, not durability**: the spike rescued an orphaned task out-of-band through `board.capability` with no library or roster involved, so nothing is lost and no migration should be scoped — what is lost is the coordinator's ability to help itself mid-conversation. The fix reuses `allowEmptyRoster` rather than adding surface, which FIX-940's own comment at that site had already anticipated. And the refusal and the gate fix are now an explicit **same-PR constraint**, because the refusal alone makes the empty case worse than today's silent-floor behavior: it converts a wrong answer into a failure with no tool left to act on it. That last point also withdrew Decision 5's claim that nothing in the durability path waits on `unblockTask` — the refusal needs a tool to act through, so `d` now depends on `c`.
- **After the refusal-mechanism spike** — settled where `d`'s stale-assignee refusal lives, which earlier drafts had left to the implementer. It is a **pre-claim preflight that parks the task `blocked`**, and both alternatives were tested and rejected on evidence rather than preference. Post-claim is unrecoverable and strictly worse than today's silent floor: a claimed task can only complete or error, there is no retry budget (`maxAttempts` isn't even among `addTask`'s model-facing fields), and two of the three recovery attempts a coordinator would make return `{ ok: true }` while achieving nothing. The review's own suggestion — leave the task `pending` — spins, because `hasClaimableTask` tests only `depsSatisfied`: 40,004 claim attempts against a durable store at delegation defaults, terminating but hot-looping. Parking as `blocked` needs no substrate change, since every property it relies on already exists. One ordering caveat came out of the spike's first failed attempt and is now in the spec: the preflight runs *after* seeding, because an `initialTasks` board seeds inside the drain. This also converted `d`'s dependency on `c` from a judgment call into a measured one — nothing model-facing moves `blocked → pending`, so without `unblockTask` the refusal strands work the coordinator cannot free.
