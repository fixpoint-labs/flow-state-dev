>
> **The durable half of this work moved to [FIX-939](https://linear.app/fixpoint-labs/issue/FIX-939/durable-jobs-and-detached-task-substrate) (durable jobs & detached-task substrate).** This spec now covers **`block` and `request` lifetimes only**. Everything requiring a board that outlives a request — the `session`/`user`/`org` rungs, the whole of the former Decision 3 and its five consequences, the pre-drain `reclaim()`, the unresolved claim-recovery mechanism, and `flowIsolation` forwarding — belongs to FIX-939 and is not decided, designed, or built here.
>
> **The owner's reasoning, recorded verbatim because it is the rationale a future reader will most want:**
>
> > "A board that can delegate across requests or sessions is the same question as the scope it spans. You cannot delegate out of a `block`- or `request`-scoped board, so board lifetime and task detachment are one axis. FIX-939 already names the reclaim/heartbeat gap as its own risk #2 — this work was always its."
>
> **Why the cut lands here and not somewhere else:** every concurrency hazard the old spec carried is a **cross-execution** hazard — cap overshoot, double-claiming, the recovery-write lost-update path, and the stranded `in_progress` claim all need two executions holding two independently-hydrated caches over one board. A request is one execution with **one resource registry and one hydrated cache**, so that whole class genuinely cannot reach `request`, and request-state CAS prevents duplicate claims besides. The line between `request` and `session` is not an arbitrary scope boundary — it is exactly where those hazards become reachable.
>
> **What a request board does share, stated so "one execution" is not over-read.** The request backing is reachable from *any* block in the request — the code says so twice: *"Reachable from any block in the request (sibling adds, outer-loop re-entry)"* and *"reaches the collection from any block in the request, not just blocks under `board.drain`'s subtree."* So concurrent `parallel`/`forEach` invocations of one generator share the static binding id and land on the same request-state slot. That is **contamination, not a concurrency hazard**: each invocation can treat a sibling's unfinished tasks as its own, drain them, and report them. It is exactly what the working-set filter (Decision 2) is for, and it is already in scope — no new hazard class, and no change to the cut.
>
> **Note for the owner on the issue title.** FIX-957's Linear title still says "make the delegation board survive a turn." After this factoring it does not: a `request` board dies with the request. What remains is real but narrower — in-request re-entry, an honest working-set report, roster protections, and a parking exit. The title may want updating, which is the owner's call, not this spec's.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

**In plain language.** When a skill delegates work to a team of agents, the framework hands it a *board* — a to-do list its coordinator plans on and then runs. That board is welded to the block that owns it. It cannot be given any other lifetime, even one that stays inside the same request.

That matters more than it sounds, because a generator can be re-entered inside one request — that is what the `request` backing exists for, and its own documentation says so. When it is, the coordinator comes back to an empty board and to a report that describes a world it no longer recognizes.

The framework already knows how to give a board a different home: `defineTaskCollection` and the `request` backing both ship today and work when you build a board by hand. The delegation path just can't reach them — it is hardwired to the disposable option. This is not a missing capability. It's an existing capability one caller can't ask for.

**Why now.** Three defects sit behind that switch, and each one only *appears* once the board outlives a single block invocation:

- **The report is unfiltered.** `runBoard` reports every task the board has ever held. A board re-entered within a request hands the coordinator back work it already consumed, and one parked task poisons the verdict of every later run.
- **The roster is rebuilt but the tasks are not.** `resolveBuild` re-walks the agent roster on every call and never memoizes it, so a re-entered generator can rebuild a roster that no longer carries an agent an earlier task was assigned to. Today that task is answered silently by the floor worker under a persona the record does not reflect. If the roster empties entirely, the *whole delegation surface* disappears — all nine tools and the guidance with them.
- **A parked task has one exit, and it corrupts dependents.** `blockTask` can park a task; only `cancelTask` gets it out. Cancelling mints a new id if the work is re-added, and anything that declared a dependency on the original becomes permanently unrunnable with no error surfaced.

The first is a reporting defect, the second two are correctness defects, and all three are reachable inside a single request.

### 2. Solution in plain terms

Let the delegation board be given a lifetime, and fix the three things that break when it has one.

The configuration is deliberately small. Each *binding* — one generator's use of the skills library — gains **one** option naming how long its board should live: `block` (today's behavior, the default) or `request`, plus an id that keeps two bindings apart. The storage backing is derived from that answer rather than chosen. It mirrors the binding's existing `activeState` option, which already asks a caller for a scope and a storage field. No new durability machinery is invented: `request` resolves to the request backing that already exists.

The three fixes:

1. **Report on the work this run actually engaged** — the tasks unfinished when the drain started, plus any created during it. Not everything the board has ever held.
2. **Protect the surface against roster drift** — a task naming an assignee who is no longer on the roster is refused rather than silently answered by the floor, and an emptied roster no longer takes the whole delegation surface with it.
3. **Give a parked task a way out** — `unblockTask` returns it to `pending` with a stable id, so dependents survive.

**The philosophy that led here.**

- **Tenet 2 (composition over features, refine don't accrete).** The strongest thing about this change is what it *doesn't* add. The `request` backing already exists; the delegation surface just couldn't reach it.
- **Tenet 3 (earn every addition).** One new option on a surface that already carries its twin, and no new field on the shared task schema.
- **Tenet 5 (fix at the owning layer).** The roster protections go where the roster is resolved, not at the worker or the router.

### 3. Tradeoffs & alternatives

**The simpler approach considered: just flip the backing and ship it.** Genuinely tempting — the wiring is a few lines. It's insufficient because each of the three defects only appears once the board outlives a block, and two of them are silent. The config change is the small part; it is not shippable alone.

**Alternative rejected — accepting a `DefinedTaskCollection` as the option** (this spec's first two drafts). The stated reason for preferring it was that a lifetime enum would "invent a parallel scope vocabulary." That does not survive inspection: the codebase already carries two vocabularies and neither is a lifetime — **backing** names storage shape, `ResourceScope` names reach. A lifetime axis finishes the one that exists, and it is the same insight FIX-960 is acting on internally. See Decision 1.

**Alternative rejected — scoping the run's report by *which turn created each task*.** A task created in one invocation, unblocked and completed in the next, is neither "created this run" nor "still unfinished," so it would be dropped from the report that should carry its output. It would also have needed a new field on the shared task schema. The replacement — report on the tasks *this run engaged* — is both correct and strictly smaller.

**Where the genuine complexity is — and most of it left with the durable scope.** What remains is a narrower question: exactly which tasks a re-entered drain owns, and what a roster that changed underneath a surviving ledger should do. Both are settled here on measured evidence rather than argument (§7).

**What is deliberately not solved here.** A board that survives a request. Everything about it — including whether such a board can be bounded or its claims serialized at all — is FIX-939's, and the answer there is genuinely hard: there is no cross-execution atomic in the substrate today. Nothing in this spec depends on that answer.

### 4. Focus practices

1. **Test the off state of the new option (BP-035).** The default lifetime (`block`) is the one every existing consumer is on, and it must be bit-for-bit unchanged, **including exactly which tasks `runBoard` returns**. Note that `request` is *not* the off state — that mistake has been made once in this spec's history.
2. **`request` is not a safe rung by default.** It is easy to read "in-request" as "nothing can go wrong." The two roster protections exist precisely because a `request` board outlives block boundaries while its roster is rebuilt on every resolve.
3. **A refusal the model can act on is a result, not a throw.** This surface's contract is `{ ok: false, error }` with enough detail to recover. Nothing new throws through the tool boundary.
4. **Don't re-derive the audit (tenet 1).** The issue body carries an architectural audit already verified against `main`. In particular: `SkillsLibraryOptions.scope` scopes the *skills* collection, not the board. That misreading has already cost a cycle.

### 5. What using it looks like

**Today — unchanged, and still the default.** A delegating skill gets a private per-block board with no configuration at all:

```ts
const skills = createSkillsLibrary({ collection: "skills", catalog });
// Coordinator plans with addTask, runs with runBoard. Board dies with the block.
```

**New — a board that survives re-entry within the request:**

```ts
generator({
  uses: [skills.with({ board: { lifetime: "request", id: "researcher" } })],
  //                            ↑ block (default) | request
  //                              `id` keeps two bindings from sharing one board
});
```

A generator re-entered by an outer loop, twice in one request:

```
pass 1:  addTask("research")  → { ok: true, taskId: "t1" }
         addTask("draft")     → { ok: true, taskId: "t2" }   // blocked on a fact
         runBoard()           → { status: "blocked", tasks: [t1 completed, t2 blocked] }

pass 2:  unblockTask("t2")    → { ok: true }
         runBoard()           → { status: "drained", tasks: [t2 completed] }
                                 └─ t2 was unfinished when this run started, so its
                                    output comes back. t1 already finished — not re-reported.
```

The second `runBoard` is the point of the change. Today pass 2's board is empty and `t2` is unreachable. With a naive `request` board, pass 2 would report `blocked` (poisoned by `t2`) and hand back both tasks including one the coordinator already consumed.

**A parked task's exit** — `unblockTask` returns a task to `pending` without minting a new id, so dependents survive:

```
blockTask("t2", "waiting on the lookup")   → { ok: true }
unblockTask("t2")                           → { ok: true }
// t3 declared deps: ["t2"] — still runnable. Cancel-and-re-add would have
// stranded t3 permanently, with no error surfaced.
```

### 6. Decisions & rules — the sign-off surface

> **Numbering is not reflowed.** Decision 3 moved to FIX-939 with the durable scope, and its number is retired rather than reused — the same reason Decision 6's number was kept when it was dropped. An earlier reading of this spec still lines up.

**1. The board is configured per *binding*, by one option naming its lifetime, plus a caller-supplied id that keeps `request` boards apart. The storage backing is derived, not chosen.**

`block` maps to the host generator's own state (exactly today's board); `request` maps to request state. The consumer answers "how long should this board live," which is the question they actually have; nobody picks a storage shape.

**It lives on the binding, not the library, and that is load-bearing.** One library is installed once and bound per generator via `skills.with({ … })`. A board not namespaced per binding gives every binding the same storage slot, so a task created by one generator could be listed or drained by another with a different roster — breaking the private-per-generator contract `delegation.md` states today.

**The id is needed at `request`, which is easy to miss.** `RequestBackingSpec.stateKey` defaults to the `collectionId`, and the delegation surface passes a constant one — so two bindings at `request` land on the same request-state field and can drain each other's tasks. **Confirmed by execution:** two request-backed collections sharing a `collectionId` land on one request-state slot and read each other's tasks, while a control with an explicit distinct `stateKey` stays isolated. `block` alone needs no id, because its board dies with the generator that owns it.

**⚠️ OWNER QUESTION — does the enum still declare `session` / `user` / `org`?** Two options, and this is public surface, so it is put here rather than settled quietly.

- **(A) Declare all five rungs, reject the durable three at build time** until FIX-939 lands them. Documents the intended ladder in the type.
- **(B) Narrow the enum to `block | request` now**, and widen it when FIX-939 ships the durable rungs.

*Recommendation: (B).* Three reasons, in order of weight. **Widening an enum is additive and non-breaking; narrowing one is not** — so (B) is the reversible choice, which is the same argument this spec already used to reject the enum-plus-collection union. **A type that accepts values it refuses at runtime is a worse public boundary than a smaller honest type** (BP-004): (A) obliges us to ship, document, and test a rejection path for three values whose only purpose is to fail. And the ladder can be documented in prose with a pointer to FIX-939, which costs nothing and misleads nobody. The one thing (A) buys — a visible signal of direction — does not need to live in the type to be visible.

*Alternative rejected — accepting a `DefinedTaskCollection`.* **(a)** A caller-supplied collection is never declared in the library's capability resources, so the runtime lookup is absent — a real defect that *dissolves* when the library owns construction rather than needing a fix. **(b)** The id is one string beside the lifetime rather than a whole collection object, mirroring `activeState`. **(c)** The `stateSchema` objection is inert on this surface: the only creator of a task on a delegation board is `addTask`, whose `input` is `z.unknown()`.

*Ramification:* one new option on a surface that already carries its twin, and no second import. **Only `block` is free *of the id*** — `request` costs one, because it shares storage with something. Read that narrowly: `block` is free of the id seam and of the storage hazards, and **not** free of roster drift, which reaches it too (§7). Conflating those two freedoms is a mistake this spec made and carried for several rounds.

**2. The report is filtered at `request`, and returned unfiltered at `block` exactly as today.** At `request` it reports the tasks this run engaged — those unfinished when the drain started, plus any created during it — from a snapshot taken inside `runBoard` before the drain. The verdict stays "any unfinished task ⇒ blocked."

*Alternative rejected:* scoping by which turn created each task (drops a carried-over task this run completed). Also rejected: applying one rule on both branches and *arguing* it comes out equivalent at `block`. Two rounds of review found two different counterexamples to that argument — most recently a task the coordinator adds and cancels before draining, which is terminal at snapshot time and would vanish from a report that today includes it. **Branching is what makes BP-035's off-state requirement true by construction instead of by an equivalence proof that keeps failing.**

*Ramification:* the default path is untouched. On a `request` board, work finished by an earlier pass is not re-reported; work this run touched comes back with its output. **No new task-schema field and no migration.**

**4. ⚠️ OWNER DECISION — whether to guard the `in_progress` / `awaiting_review` → `pending` transition. Not decided here.** Guarding it reverses FIX-953's signed-off Decision 5c ("`unblockTask` is a thin wrapper… no status precondition of its own"), so it needs the same sign-off weight that decision got.

- **(A) Re-affirm 5c.** `unblockTask` stays a thin wrapper; the transition stays permissive. Cheapest, consistent with the record.
- **(B) Guard it.** The unblock path refuses `in_progress` and `awaiting_review` sources.

*Recommendation: (B).* 5c's stated reasoning was that no coordinator tool reaches `awaiting_review` today. That premise is weaker now: a fan-out worker holding board tools mid-drain is a real, reachable writer, and it can move a running task back to `pending` — manufacturing exactly the drain-containment failure FIX-951 exists to contain.

**§13 carries an input that bears directly on this and may open a third position:** `resumeFromReview` is never exposed as a tool, so (B) as written would leave a reviewed task with no model-facing exit — whereas guarding `in_progress` *alone* gets the safety benefit without that cost. The owner should read that note before answering.

*Ramification either way:* (B) closes a model-reachable path to a known drain failure and costs one refusal the coordinator may hit legitimately. (A) leaves it open and keeps the signed-off record intact.

**5. `unblockTask` ships in this issue, re-grounded on the two arguments that survive independent of board lifetime.** Those are the mid-drain fan-out exit (a task blocked inside a drain otherwise has only `cancelTask`) and dependency corruption (cancel-and-re-add mints a new id; `deps` resolve by id and require `completed`, so every dependent becomes permanently unrunnable with no error surfaced).

*Alternative rejected:* implementing FIX-953's spec as written, whose primary argument was a cross-turn case that did not exist. Also rejected: moving the tool back out to FIX-953 — it landed here only because FIX-953 was closed as a duplicate, and moving it back invites it to be lost a second time, which has already happened once.

*Ramification:* the coordinator gains a ninth task tool. **`c` gates `d`, and that edge is load-bearing on evidence:** with `d`'s preflight parking tasks `blocked`, there is *no* model-facing tool that moves `blocked → pending` — the refusal-mechanism spike's own recovery had to call `collection.unblock()` in code. Without `c`, `d` ships a state the coordinator cannot leave. Decision 4 gates only the *guard*, not the tool, so it does not gate `d` transitively.

**6. DROPPED — the typed capacity error is not this spec's to ship.** Nothing in the surface this feature adds can reach it: the option is `{ lifetime, id }`, and the collection the library constructs never sets `maxInstances`, which the registry checks only when it is defined. **The underlying defect is real but belongs elsewhere** — a code-first `taskBoard({ collection: defineTaskCollection({ maxInstances }) })` still hard-throws a plain `Error` at the model boundary where every other refusal is a soft result. Follow-up in §12.

**7. Tool descriptions and delegation docs state the board's real lifetime, and documentation ships inside the PR that introduces each surface.**

**8. ⚠️ OWNER DECISION — sequencing FIX-960 ahead of this work.** *Recommendation: yes, but the argument is weak and should be weighed as such.* It originally rested on FIX-960 rewriting the same files as this spec's cap work; that work is gone, so there is no collision to sequence around. It is now purely a coherence preference: FIX-960 renames the `sequencer` backing to `state` precisely because that name describes storage rather than lifetime, and this spec adds a lifetime axis on top of it. *Ramification:* not a dependency of any kind; nothing here waits on it either way.

**Non-goals.** **Any board outliving its request — FIX-939** (and with it: cap enforcement on durable storage, cross-execution claim serialization, lease reclamation, and `flowIsolation` forwarding). Durable non-sequencer block state (FIX-917); a spend ceiling (FIX-933); retry-storm accounting (FIX-948); FIX-950's soft-error contract.

**Size estimate: Small–Medium** (multi-PR, within `orchestration` plus docs), down from Medium–Large before the factoring. Three sub-PRs: two independent and parallel, the third depending on both. **No sub-PR is gated on an open decision** — the two prerequisites that used to gate `d` left with the durable scope. Docs ship inside each PR.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

All of it lives in one package, and nearly all in one layer: the delegation surface (`packages/orchestration/src/skills/`). The `flowIsolation` forwarding that used to pull in the task-collection layer was a `user`/`org` concern and went to FIX-939. **Whether the collection layer is touched at all now turns on one open question** — the unassign path needs a `clearAssignee` mutation it does not have (see the owner question below). An earlier draft of this section claimed the layer was "genuinely untouched"; that claim was made before the verb was checked and is withdrawn.

**The board's home becomes derived, not a constant.** `block` → the host generator's own state, unchanged. `request` → request state, keyed by the binding id. The hardcoded `backing: "sequencer"` at the delegation construction site is replaced by that mapping.

**The early own-state bail-out must become conditional, and this is not durable-only.** The surface currently refuses to install when the host generator has no own state. That guard is correct for a `block` board and wrong for a `request` one, which does not ride own state either. It must fire only on the state-backed branch.

**The run's working set.** At `request`, `runBoard` gains a step before the drain recording which ids exist and which are unfinished; settle then reports the ids unfinished then, plus any id present now that wasn't in the snapshot. At `block` settle returns the full list as today.

> **Illustrative — a sketch, not the contract.**
>
> ```ts
> // request: before drain: { ids: Set<string>, unfinished: Set<string> }
> //          at settle:    working = snapshot.unfinished ∪ (currentIds − snapshot.ids)
> // block:   working = every task, as today
> ```

**The stale-assignee refusal is a preflight step, not a routing change.** `runBoard` is already a sequencer; it gains a step that walks the ledger before the drain and parks **`pending`** tasks whose named assignee is absent from the live roster as `blocked`, with the reason on the task's `error`.

**The `pending` filter is not an optimization and must not be widened.** Parking *is* the `pending → blocked` transition, and `ALLOWED_TRANSITIONS` makes `blocked` reachable from `pending` and nothing else — so calling `block()` on a task in any other status throws. A surviving ledger routinely carries `completed`, `errored`, `cancelled`, `in_progress` and `awaiting_review` tasks whose assignee has since left.

**Both roster protections apply at `request` — and at `block` too. "Only `block` is free" was true of one kind of freedom and got applied to two, which is worth naming because that line has been load-bearing since the first draft.** `block` is free of the **storage** hazards and of the id seam, because its board dies with the generator that owns it. It is **not** free of **roster drift**, because the board outlives something smaller than a generator execution: the *step*.

*Verified directly, since this is the load-bearing half.* `resolveDelegationBuild` is re-resolved before **every step** of the generator's tool loop, and its memo is keyed on the execution's `BlockContext` — one object reused across every step of one execution. Callers re-walk eligibility (including the live-manifest disable read) on every call, the freshly resolved sources are projected to a `SourceSnapshot`, and the build is re-invoked whenever that snapshot changes: *"A mid-turn skill disable shrinks the snapshot and busts the cache."* Meanwhile the block-backed board is own state, which persists across those steps. **So an agent can disappear between one step's `addTask` and a later step's `runBoard`, inside a single generator execution, with the task still sitting in the same ledger** — silently floor-routed, or, if the roster empties entirely, with the whole tool surface gone.

At `request` the same drift reaches one rung further out: the board survives every block boundary in the request — re-entry from an outer loop is the backing's stated purpose — so a re-entered generator can rebuild a roster missing an earlier assignee and inherit tasks queued against it.

**The consequence for the plan is that the roster protections are not conditioned on lifetime at all.** They run wherever the surface runs, which removes a branch rather than adding one — the preflight and the gate fix are unconditional, and only the *settle filter* and the *id* branch on lifetime. This also means `d` improves today's default board, not just the new rung.

The preflight sits **before `board.drain`**, and that placement is trivially available: `.tap(preflight).tap(board.drain)`. There is no seeding step to order against — `buildRunBoardTool` passes seven keys to the board and `initialTasks` is not among them.

**Nothing at the worker or router layer changes:** `blocked` is already non-terminal, already excluded from `inFlightCount`, already counted unresolved by settle, and `blocked → pending` is already permitted, so recovery runs through existing verbs.

**Recovery needs one more verb than `unblockTask` when the roster has emptied — and the earlier draft of this paragraph got the mechanism backwards.** It claimed `checkAssignee` refuses every absent name including the empty string. **It refuses nothing.** `buildTools` passes `rosterPurposes.size > 0 ? roster : undefined`, so an emptied roster supplies `undefined`, and `checkAssignee` returns early on `roster === undefined` — accepting every assignee by design, to tolerate the legacy rosterless board (BP-030). So `assignTask("placeholder")` **succeeds**, writes the assignee, and the next drain's preflight parks the task again because that name is not on the (empty) roster. The loop is real; the gate is wide open rather than shut.

**Two different meanings share one representation, which is why this was easy to miss.** `undefined` currently signals both *"this board never had a roster — validate nothing"* and *"this board's roster resolved empty"*. The first must keep accepting everything; the second must reject everything. **`d` must pass an explicit empty roster on the protected paths** and keep `undefined` for the intentionally-rosterless case, so the two stop being spelled the same way. Without that the empty-roster gate fix keeps the surface alive while leaving every assignment unvalidated — half a fix that reads like a whole one.

**Then the exit itself.** `unblockTask` alone does not close the loop: it returns the task to `pending` and the preflight re-parks it. **Floor routing already works** — an empty-string assignee falls through to the router's `fallback` — so the destination exists; what is missing is the coordinator's ability to *express* "unassign".

> **⚠️ OWNER QUESTION — the unassign path needs a collection-layer change, which contradicts this spec's new single-layer claim.** `TaskCollectionRef` exposes only `setAssignee(id: string, assignee: string)`; there is no clear/unassign, and `updateTask` omitting `assignee` is a no-op. So `d` cannot implement its own mandatory recovery without reaching into internal state.
>
> - **(a) Add a `clearAssignee` mutation** to `TaskCollectionRef` and both backings, and stop claiming `tasks/collection/` is untouched.
> - **(b) Adopt a sentinel** — define `""` as "unassigned", and teach the preflight and `checkAssignee` to read it that way.
> - **(c) Drop the unassign path** from this spec, accept the in-request dead end, and let FIX-939 own recovery.
>
> *Recommendation: (a).* It is one method that makes the state **representable rather than encoded**. (b) looks cheaper but is not: it needs changes in three places (the preflight, `checkAssignee`, and the docs) to avoid one interface method, and it leaves a sentinel whose meaning must be known everywhere the field is read — the *exact* failure this section just corrected, where one representation carried two meanings. Choosing it to protect a summary sentence would be letting a description drive the design; the single-layer property was a **consequence** of the carve, not a goal of it, so §7's claim is corrected rather than defended.
>
> **The real alternative to (a) is (c), not (b).** If the owner would rather keep this spec single-layer, the honest move is to drop the exit entirely — the preflight and the gate fix still ship, and the coordinator's recovery narrows to "reassign, when an agent remains." That is a defensible trade: a `request` board strands work for one request rather than forever. It should be chosen deliberately, though, because "the coordinator cannot free a task it is being told about" is a dead end inside a single run, which is the failure class this issue is named for.

**Caching the resolved collection is no longer mandatory.** That requirement came entirely from the durable branch, where each construction awaits a full listing against the store. The request backing has no such cost. Resolve sites may still share a reference for clarity, but it is now an ordinary readability question rather than a load-bearing performance constraint — **and it is not a correctness requirement, so no test needs to pin it.**

**Evidence for what stays (BP-003).** The request-state key collision is confirmed by execution (spike, `spike/durable-board-claims`). The roster behaviors are measured: today's silent substitution reports the drain `completed` with `assignee: "beta"` and `output.persona: "FLOOR-generalist"` at `attempts: 1`, and the control with the floor worker removed fails loudly — so the silence comes entirely from the default worker, which the delegation surface always wires. With the roster emptied at runtime the tool list is `[]`, guidance is `null`, and the turn still completes with `error: null`. Parking as `blocked` was measured end-to-end at 13ms, with a healthy sibling draining normally alongside the parked orphan.

**Two alternative refusal mechanisms were tested and rejected on evidence, not preference.** *Post-claim* is unrecoverable and strictly worse than today's silent floor: a claimed task can only complete or error, `maxAttempts` is not among `addTask`'s model-facing fields so there is no retry budget, and two of the three recovery attempts a coordinator would make return `{ ok: true }` while achieving nothing. *Leaving the task `pending`* spins: `hasClaimableTask` tests only `depsSatisfied` and knows nothing about assignees, so an unclaimable pending task reads as claimable every iteration — measured at the iteration ceiling, which is 40,004 claim attempts at delegation defaults. It terminates, so it is not a hang, but it is a hot loop.

### 9. Edge cases & error handling

| Case | Expected behavior |
|---|---|
| Default lifetime (`block`) | Identical to today in every respect. The settle filter does not run at all on this branch, so the returned set is today's by construction, not by argument. Includes the sequence `addTask` → `cancelTask` → `runBoard`, where the cancelled task is still reported. |
| Carried-over task unblocked and completed by this run | Returned with its output, and does not set `blocked`. This is the §5 scenario and the goal check. |
| Task finished by an earlier pass, untouched by this one | Not returned. Keeps the coordinator's context bounded. |
| Task created mid-drain by a fan-out worker | In the working set (present now, absent from the snapshot), so it is reported and counts toward the verdict. |
| Earlier pass left a task `blocked`, still blocked | In the working set; sets `blocked`. Correct, and escapable via `unblockTask` / `cancelTask`. |
| **Two concurrent invocations of one generator (`parallel`/`forEach`) over one `request` board** | Both share the static binding id and the same request-state slot — the backing is reachable from any block in the request by design. **Not a concurrency hazard:** one execution, one registry, one hydrated cache, and request-state CAS still serializes claims, so nothing double-claims or lost-updates. **It is contamination:** each invocation must report only its own working set, or a sibling's unfinished tasks get drained and reported as this run's. This is the settle filter's job, and it is the sharpest case for it. |
| **`block` board, agent disabled between one step's `addTask` and a later step's `runBoard`** | Same two protections as `request`. The board is own state and persists across steps of the tool loop, while `resolveDelegationBuild` re-reads the live roster before every step and busts its memo when a skill is disabled — so the roster can shrink under a surviving ledger inside one execution. **`block` is free of the storage hazards, not of roster drift.** |
| `lifetime: "request"`, generator re-entered mid-request with a rebuilt roster | Both protections apply: the surface survives, and inherited work for a departed assignee parks `blocked` rather than routing to the floor. The board outlives the block boundary and the roster walk is never memoized, so both hazards reach this rung. |
| `request` board, task assigned to an agent the roster no longer has | **Parked `blocked` by the pre-claim preflight**, never claimed, reason on the task's `error`; `settle` reports `blocked`. Measured today: silent substitution — drain `completed`, `assignee: "beta"`, `output.persona: "FLOOR-generalist"`, `attempts: 1`. |
| Terminal task (`completed`/`errored`/`cancelled`) whose assignee has left | **Skipped, not parked.** `blocked` is unreachable from a terminal status, so parking it throws. |
| `awaiting_review` or `in_progress` task whose assignee has left | **Skipped, not parked** — same reason. These are the rows that catch a too-wide filter, since they are non-terminal and so read as "live" to a careless preflight. |
| Roster empties mid-request, orphaned tasks present | The surface survives (both gates), every orphan parks `blocked`, nothing runs, no spin. Recoverable only through the unassign path — `unblockTask` alone re-parks on the next drain. Measured today without the gate fix: tool list `[]`, guidance `null`, turn completes `error: null`. |
| Coordinator assigns a name that is not on the roster, roster **non-empty** | Refused with `unknown_assignee`. |
| Coordinator assigns any name, roster **empty** | **Must be refused — today it is accepted.** `buildTools` passes `undefined` for an empty roster and `checkAssignee` accepts everything when its roster argument is absent, so `assignTask("placeholder")` succeeds and the preflight re-parks the task on the next drain. Fixed by passing an **explicit empty roster** on the protected paths, keeping `undefined` for the intentionally-rosterless board (BP-030) — two meanings that currently share one representation. |
| Task with no assignee at all | Runs on the floor, unchanged. The delegation floor working as designed; must not be caught by the refusal above. |
| Orphaned task left `pending` instead of parked | Rejected shape — spins. 40,004 claim attempts at delegation defaults. Terminates, but hot-loops. |
| Orphaned task refused after a worker claims it | Rejected shape — unrecoverable, and `assignTask`/`cancelTask` both answer `{ ok: true }` while achieving nothing. |
| Two bindings of one library at `request` | Separate boards. Each binding names its own id, so neither can list or drain the other's tasks. Without the id they share one request-state field — confirmed by execution. |
| `board: { lifetime: "request" }`, second drain in the same request | Tasks the earlier drain completed are excluded from the later report. |
| Own-state guard, `request` board, host generator has no own state | Surface installs normally — the guard must not fire. This is the bug the conditional fixes, and it is not durable-only. |
| Hand-wired `taskTools` (no skills binding) | Unchanged: own-state, no roster. Explicitly out of scope. |

**Second-path checklist (BP-035).** *Legacy:* this spec adds no field to the persisted task envelope — and after the factoring the envelope is no longer even a migration surface here, since a `request` board cannot outlive a deploy. *Null boundary:* the board option is optional and absent by default; guard it. *Concurrency:* the **cross-execution** class is out of scope by construction — one request, one registry, one hydrated cache — which is what the factoring was for. What remains is **in-request sharing**: sibling and concurrent invocations reach the same request-state slot, which the working-set filter handles and which the new §9 row pins. *Cancel/error:* a cancelled task at `block` is still reported; a parked task is escapable. *Multi-tenant:* not reached — no shared storage remains here. *Flag off-state:* covered above and the hardest test target.

### 10. Testing strategy

**Discipline: `diagnose`** (Linear category: Bug). The feedback loop is vitest at the surface seam — `packages/orchestration/src/skills/` tests already exercise these paths, so the reproduction can be written before the fix in each sub-PR.

**Goal check (real path, real model).** A delegating skill configured with a `request` board, driven through `fsdev run` with an outer loop that re-enters the generator: pass 1 plans two tasks, drains one, leaves one blocked; pass 2 unblocks and drains it. Passes when pass 2's `runBoard` reports `drained`, returns the task *with its worker output*, and the id from pass 1 still resolves.

**Required: the `block` off-state, tested hardest.** Every behavior added here must be inert at `block`, including exactly which tasks `runBoard` returns.

**Required: the two-binding isolation test.** Two bindings of one library at `request` get separate boards. Without the id they share a request-state field, so this is the test that pins Decision 1's least obvious claim.

**Required, and NOT covered by the test above: two concurrent invocations of *one* binding.** The two-binding test proves distinct ids produce distinct slots; it says nothing about one id reached twice, which is the shape `parallel`/`forEach` produces and which the backing explicitly permits. Drive one generator concurrently over one `request` board and assert each invocation reports **only its own working set** — a sibling's unfinished task must not appear in the other's report or verdict. Assert on the reports, not on the ledger: the ledger is legitimately shared, and the filter is what makes that safe.

**Required: the roster protections tested at `block`, not only at `request`.** Disable an agent between one step's `addTask` and a later step's `runBoard` within a single generator execution. The task must park rather than route to the floor, and the surface must survive an emptied roster. Running these only at `request` would leave the default board — the one every existing consumer is on — untested against the drift that reaches it.

**Required: an assignment-validation test with an empty roster.** `assignTask` must be refused when the roster resolved empty, and must still be accepted on an intentionally-rosterless board. One test per meaning, because the two currently share a representation and a single test would pass on either reading.

**Required: an empty-roster survival test.** The roster empties mid-request; the tool surface and guidance must both survive, and the coordinator must be able to act on a queued task. A build-time arm belongs beside it — a binding whose roster was never non-empty must still get a board. Both gates, or the test only proves half the fix. **And assert that the coordinator can actually *free* a parked task with no valid assignee available** — surviving tools that cannot express any legal move is only half a recovery, and `unblockTask` alone re-parks on the next drain.

**The preflight fixture must carry a mixed-status ledger** — at minimum one `pending` orphan plus a terminal orphan and an `awaiting_review` orphan. A single-pending-task fixture cannot catch the too-wide-filter class at all: it passes whether or not the filter exists, and the throw only appears once the ledger holds a status `blocked` is unreachable from.

**Required: preflight behavior pinned four ways.** The orphan is parked `blocked` and never claimed; the drain does **not** spin — **assert the claim-attempt count, not just termination, because the failing shape terminates too**; `settle` reports `blocked` and the reason is legible on the task; and recovery returns the task to `pending` and it then runs. A healthy sibling must drain normally in the same run, or the test cannot tell "parked correctly" from "drain broken."

> **A lesson this spec paid for twice, worth carrying into every test above.** Two tests were specified here that would have *passed against the defect they were meant to catch* — one asserting that the drain terminates rather than counting claim attempts, one seeding an already-expired lease. Both failed the same way: they asserted the outcome a working system happens to produce, rather than the property that separates it from the broken one. When writing these, name the broken shape first and check the assertion excludes it.

**Other CI specs, in observable terms.** The `block` default returns the same task set as today, including for `addTask` → `cancelTask` → `runBoard`. Settle: carried-over-and-completed returned with output; finished-before-this-run omitted; added-mid-drain included; verdict from the working set only. `unblockTask` returns a blocked task to `pending` with a stable id and dependents still runnable. The own-state guard does not fire under a `request` board. Per Decision 4(B) if chosen: the unblock path refuses the guarded sources.

Tests must encode *why* (tenet 7 / CLAUDE.md §5) — e.g. the carried-over test asserts the output comes back *because* withholding it is what made the first draft's rule wrong, not merely that a filter has a particular shape.

## Spec evolution

**After the FIX-939 factoring (owner scope change, not a review round)** — the durable half of this spec moved to FIX-939 and the document was rewritten for the reduced scope rather than struck through. The owner's reasoning, verbatim: *"a board that can delegate across requests or sessions is the same question as the scope it spans. You cannot delegate out of a `block`- or `request`-scoped board, so board lifetime and task detachment are one axis. FIX-939 already names the reclaim/heartbeat gap as its own risk #2 — this work was always its."* The cut falls exactly where the hazards divide: every concurrency consequence this spec had accumulated needs two executions over one board, and in-request there is only ever one. **What left:** the `session`/`user`/`org` rungs, the whole of Decision 3 and its five consequences, the pre-drain `reclaim()`, the unresolved (a)/(b) claim-recovery mechanism, `flowIsolation` forwarding, the durable collection identity seam, and the mandatory memo. **What stayed, and why it is not merely the leftovers:** the request-state key seam, the working-set filter, both roster protections, the conditional own-state guard, and `unblockTask` — each of which is reachable inside one request and three of which are silent today. **Two re-derivations rather than deletions.** The memo was mandatory only because durable hydration awaits a full store listing; at `request` that cost does not exist, so it drops from a correctness requirement to a readability preference and no test needs to pin it. The unassign path was listed to move, but it is needed exactly where the preflight and empty-roster gate are needed — `unblockTask` alone re-parks on the next drain — so it stays, with the disagreement surfaced in §7 rather than resolved silently. **Consequences for the plan:** sub-PR `d` lost both of its prerequisites, so nothing here is gated on an open fork; the size estimate dropped from Medium–Large to Small–Medium; and the spec is now single-layer, since the one change it needed outside `skills/` was `user`/`org`-only. Decision 3's number is retired rather than reused. A new owner question was added to Decision 1 — whether the enum still declares the durable rungs — with a recommendation to narrow, since widening an enum later is additive and shipping values that throw is a worse public boundary than shipping fewer.

**Prior history** — the full round-by-round log for the pre-factoring spec (twelve review rounds, four spikes, and every falsified premise) is in this file's git history on `spec/FIX-957`, most completely at `bc203df0b`. The material that moved carries its own history into FIX-939. Summary of the arc: the spec began with five sub-PRs and a cap-enforcement refactor; shed the cap work and the typed capacity error after a spike proved durable boards cannot be bounded; moved the board option from the library to the binding; widened the settle filter and the roster protections from "durable only" to "every lifetime above `block`" three times; added the stale-assignee preflight and the recovery path; generalized the lost-update flaw from `block()` to every recovery write; and withdrew every expiry-based recovery mechanism after confirming nothing renews a lease while a worker runs.

**Recurring failure classes worth carrying forward** — these outlived the factoring and are the most transferable thing here. (1) Reporting from what was intended rather than from the committed file; fixed by reading every claim back from `git show HEAD:`, including greping for what should be *absent* after a deletion. (2) Claiming the strongest bound the evidence *permitted* rather than the one it *compelled* — four successive wrong cap readings, the fourth of which prescribed a test that would have certified a false guarantee. (3) Scoping a protection to "durable only" when the correct scope was "everything above `block`" — three times, and it is why the roster protections survived this factoring at all. (4) Asserting a statement that was true when written and not revisiting it when the thing it described moved — four times, including a stale mirror that misled a downstream agent. (5) Mistaking a signal that *correlates* with a failure for one that *identifies* it — twice in tests, once in the lease semantics.

**After the post-carve verification pass** — four corrections, all inside the reduced scope, each verified in code before editing. **(1)** The carve's "one execution, so no second execution exists" **overstated a claim that is still true where it matters.** The request backing is reachable from any block in the request (the code says so twice), so concurrent `parallel`/`forEach` invocations share the binding id and the request-state slot. The cut is unaffected — one request means one registry and one hydrated cache, so the cross-execution lost-update class cannot reach `request`, and request-state CAS prevents duplicate claims — but what *does* reach it is **contamination**, which is the working-set filter's job. Narrowed the claim, added a §9 row, and added a §10 scenario after checking that the existing two-bindings test does **not** cover it: that test proves distinct ids give distinct slots and says nothing about one id reached twice. **(2)** **"Only `block` is free" was true of one freedom and applied to two.** Verified the load-bearing half directly: `resolveDelegationBuild` re-resolves before every step of the tool loop, memoizes on the execution's `BlockContext`, and busts the memo when a live-manifest disable shrinks the source snapshot — while a block-backed board is own state that persists across those steps. So an agent can vanish between one step's `addTask` and a later step's `runBoard` inside one execution. `block` is free of the **storage** hazards and the id seam, **not** of roster drift. Both protections become **unconditional**, which removes a branch rather than adding one and means `d` improves today's default board, not just the new rung. **(3)** The unassign path needs a collection-layer verb that does not exist — `TaskCollectionRef` offers only `setAssignee(id, string)` — which contradicts the carve's fresh single-layer claim. Raised as an owner question with three options and a recommendation of **(a) add `clearAssignee`**: one method that makes the state representable rather than encoded, against a sentinel that would need three call sites to know its meaning — the very failure finding (4) had just exposed. Stated plainly that the single-layer property was a *consequence* of the carve rather than a goal, so the claim is corrected rather than defended, and that **the real alternative is dropping the path (c), not the sentinel (b)**. **(4)** The §7 note claiming `checkAssignee` refuses every absent name on an empty roster was **backwards: it refuses nothing.** `buildTools` passes `undefined` when the roster is empty, and `checkAssignee` accepts every assignee when its roster argument is absent — deliberately, to tolerate the legacy rosterless board. So `assignTask("placeholder")` succeeds and the preflight re-parks on the next drain, with the gate wide open. `d` must pass an **explicit empty roster** on the protected paths while keeping `undefined` for the intentionally-rosterless case. **Two meanings sharing one representation is why this was easy to miss — the same class as failure (5) below, and the second time in this spec that a representation carried more than one meaning.**
