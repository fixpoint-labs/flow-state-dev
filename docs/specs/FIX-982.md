# FIX-982: The task board drain has no out-of-request executor — a leased task can't run outside its request — Implementation Spec

**Linear:** [FIX-982](https://linear.app/fixpoint-labs/issue/FIX-982) · **Epic:** [FIX-939](https://linear.app/fixpoint-labs/issue/FIX-939) (M3) · **Epic spec:** [`docs/specs/_epics/durable-jobs.md`](_epics/durable-jobs.md) on `epic/durable-jobs` · **Epic PR:** [#993](https://github.com/fixpoint-labs/flow-state-dev/pull/993)

## Spec evolution

- **Spec drafted** — framed as *"the spawn is the only unbuilt piece"*: everything downstream of it is measured on the real path, so this issue builds an injected capability that claims a task, derives a routing coordinate, and dispatches a request into a **Workstream** through the shipped `FlowDispatcher` seam. Three departures from the epic-spec's stated requirements are argued from code rather than inherited: the re-dispatch template is **derived, not persisted** (§7.6, dissolving N43/N34), the Workstream **settles its own task** (§7.7, dissolving N26), and the worker registry **bubbles up at flow-definition time** rather than being authored (§7.3, dissolving N9). Build shape is a five-node PR DAG; size is **Large**, not the epic's Medium.
- **After spec review (round 1)** — the dispatch-resolution model is now stated explicitly, because Decision 4 and §7.3 disagreed and one reading silently broke attribution: dispatch resolves to **one fixed internal `WorkstreamFlow` core**, never a per-coordinate binding, so Decision 4's wrapper is unbypassable and the `actionName` type widening disappears (the carried-core alternative is rejected on measurement — BullMQ does not forward `resolvedActionCore`). The registry bubble-up is corrected to the mechanism that actually ships — sequencers accumulate, `defineFlow` reads the union off each action root — rather than a tree walk `defineFlow` does not perform. §7.4's open `sessionStateSchema` fork is settled as a construction-time refusal. §7.7 **drops the canonical result item entirely**, because FIX-1008 settled on the record field and Workstream-side settlement already holds the value; FIX-1008 drops from blocker to consumer. P3 splits into P3a/P3b so FIX-999, the one genuinely unsettled blocker, cannot swallow the tracer bullet. Decision 9 names the reconciler's fleet-scale breakpoint.
- **After the epic's N68 decision (owner, 2026-08-07 — option A)** — settlement's reach is a seam this issue **builds**, not a property of board scope. Review established that a session-scoped parent board is unreachable from its Workstream (`scopeIdentityId` resolves `session` to the current `sessionKey`), and that the obvious workaround — user/org scope with `flowIsolation: false` — silently shares one ledger across every session of that user, since `resolveResourceScopeId` returns the bare `identityId` and task rows carry no parent-session partition. The owner chose to keep isolation and pay for a narrow **settlement-only, server-derived, ownership-fenced** seam instead (the fence is FIX-981's claim ticket — see the entry below). §7.7 carries the contract and its bound (not a general cross-session read — that stays the epic's OQ-F); Decision 11's scope requirement relaxes, since scope no longer decides reachability; §8's P3a gains the seam.
- **After FIX-1008 was cancelled** — the last dependency on a result-read surface is removed rather than narrowed. FIX-1008 existed to carry a worker's return value across the request boundary, which Decision 1 stopped requiring; the owner closed it with nothing built, and its `blocks` edge here is deleted. §7.7 now names `Task.output` (`tasks/schema/task.ts:47`, written by `complete` at `tasks/collection/types.ts:159`) as the sole durable result, records the two findings that outlive the issue — the JSON constraint stands on the board alone, and a result must never be reconstructed from a block trace, whose `structure` shape elides the value — and names the one thing now genuinely uncovered (an observer read path that bypasses the task row), deliberately unfiled. §6's non-goals, §8's P3 rationale, and §11's blocker table follow.

So the Workstream **re-mints** the ticket from the task row its start gate already reads (§7.4), adding no read of its own — which is also how this spec discharges the M3 obligation FIX-981 books onto it: stamp at spawn, or a detached worker's `taskTools` calls silently run unguarded. Two owner answers land with it: the ticket carries **`createdAt`** as a fourth field, closing ABA rather than accepting it; and the epic's filesystem "done" criterion is **this issue's** to satisfy (§12). **The FIX-978 blocker edge is dropped** — FIX-978 ships no recovery path, and `in_progress`-after-process-loss recovery belongs to [FIX-1005](https://linear.app/fixpoint-labs/issue/FIX-1005), which is `Backlog` with no spec, so Decision 1 and §9 now name a backstop that is honestly *not yet built*. Lower-severity folds: the `createExecutionContext` adopt-on-conflict rewire is claimed by P3a, `SessionRecord.topic` / `.coordinate` by P2, FIX-1007's settled sentinel answers by §12.1, and FIX-1000's record-derived scope address as a conditional note. One knock-on the fold surfaced: the parent-board **read** is what the start gate needs, so that half of §7.7's seam moves to P3a and P3b keeps the write verbs.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

A task board is a durable ledger of work. Its drain is not: whatever claims a task runs it **synchronously, inside the request that created the drain** (`task-board/index.ts` — the worker body sequencer, looped by `.loopBack`). When that request returns, anything still running dies with it.

That caps a task's life at one request cycle. The forcing function is Conductor M2 ([FIX-969](https://linear.app/fixpoint-labs/issue/FIX-969)): a phase — authoring a spec, implementing a PR — runs many minutes to an hour. It cannot be bound to a tick. FIX-939 names this its first top risk, and every other milestone in the epic is either blocked on it or dissolved by it.

**Why now, specifically:** the epic's objective gate is approved and the three blocking prerequisites are being specced concurrently. This is the last substrate piece that is genuinely unbuilt. The epic measured everything *downstream* of the spawn on the real `runAction` path — cross-flow execution, history isolation, topic reuse, restart re-resolution — and states the honest boundary plainly: *"the spawn itself is the one unbuilt piece."*

### 2. Solution in plain terms

When a board declares a worker as **detached**, claiming a task no longer runs it inline. Instead the board **spawns a Workstream** — a child session dedicated to one body of work — and starts a request inside it. The originating request returns immediately; the Workstream keeps going.

Four things make that work, and only the first is new machinery:

1. **A spawn capability.** Blocks already hold `ctx.stores` and their own `ctx.flow` at runtime, but a *capability* cannot legally name either — `core` can't depend on `engine`. So the spawn arrives as a capability declared in `core` and implemented in `engine`, over a public injection seam ([FIX-999](https://linear.app/fixpoint-labs/issue/FIX-999)). The board lives in `orchestration`, which has `engine` as a devDependency only, so injection is the only route that keeps the package boundary intact.

2. **A Workstream is just a session.** Its id is **derived** by hashing the routing tuple `(parentSessionId, boardId, coordinate, topic)`, so two racing coordinators aim at one key and create-if-absent ([FIX-1007](https://linear.app/fixpoint-labs/issue/FIX-1007)) makes one of them lose. History isolation then costs nothing — the `sessionId` filter every adapter already implements does all the work.

3. **Execution composes, it does not rebuild.** After the claim, the parent hands the payload to `host.dispatch` → `FlowDispatcher`. In-process that is `runAction`; out-of-process that is BullMQ's shipped worker, which already runs a request in another process from a serializable envelope with sequence-number stream resume. There is no second job queue and no bespoke loop.

4. **The worker is addressed by a coordinate nobody authored.** A task author names a `topic` and an `assignee`; the framework derives everything else. Worker bindings **bubble up into a flow-level registry at flow-definition time**, exactly as resource declarations already do — so the binding is re-resolvable from strings after a restart, and because it lives outside `flow.actions` it is not reachable from any HTTP or MCP caller.

**Philosophy.** **Tenet 2 (composition over features)** carries this: no new primitive: a Workstream is a session, the wake is a request, the ledger is the board, and the transport is the shipped dispatcher. **Tenet 5 (fix at the owning layer)** decides three of the sharper calls — cross-instance abort is fixed on the *request*'s heartbeat, where every clientless request benefits, not on the task; and the binding registry sits where the flow's block tree converges rather than at each board. **Tenet 3 (earn every addition)** is why forking, per-task targeting, and the serialized-continuation guarantee are all explicitly *not* built here.

### 3. Tradeoffs & alternatives

**The alternative that was already rejected upstream, and stays rejected:** a background *sibling request in the parent's session*. The epic built and measured it. Cross-turn history loads by `{sessionId, tenantId, status: "completed"}` with no foreground/background dimension, so a completed background request is indistinguishable from a user turn, and the window counts requests rather than tokens — 50 background turns evict the user's own turn entirely. A child session is excluded by a filter that already exists and is already correct in all four adapters. Isolation becomes a boundary that cannot be forgotten instead of a filter that must be remembered.

**The simpler approach: let the worker keep running and just not await it.** This is what `.work` / `_requestBackgroundSignal` does, and it genuinely is simpler. It is insufficient for one measured reason: the request work pool is **drained before terminal status**, so the request cannot return until the work finishes. It is intra-request concurrency, not detachment. Nothing about it survives the request boundary.

**Where I traded correctness for scope, deliberately, and the owner should see both:**

- **Serialized continuation is dropped, not solved.** Two requests in one Workstream can interleave. The epic proposed and then withdrew three mechanisms for a lane owner (the session record — clobbered by three unconditional writers; a liveness check — a cross-task predicate against a per-task fence; `LeaseStore` — no renewal, so the lock lets go while you hold it). I am not proposing a fourth. §6 decision 8 states the exposure and the app-level discipline that narrows it.
- **The reconciler needs a drain to run.** A board nobody drains never reconciles a lost wake. FSD supplies no scheduler loop, so the honest alternatives were "declare this" or "require the host to wire a cron". I declare it.

**Where the complexity actually is** — and it is not the spawn, which is about thirty lines. It is (a) **the two stamps the drain's leading tap makes and a Workstream must remake** — the one that attributes emitted items marks *sequencer* scopes only and silently does nothing otherwise, and the one that carries the worker's ownership token lives in an `AsyncLocalStorage` that cannot cross a process boundary, so it has to be re-minted rather than forwarded (§7.4); (b) **the failure map**, because "the request ended" is six statuses, two of which are not settlements at all; and (c) **admission**, because two shipped paths reach a board without ever seeing it.

### 4. Focus practices (1–5)

1. **BP-031 (never route or authorize from caller-controllable input)** — this issue adds **four** trust boundaries. The worker coordinate must be *derived* server-side, never authored on a task; the admission gate on worker actions must key on the transport-set `source`, which the HTTP route hard-codes and a caller cannot forge; the claim ticket the Workstream re-mints must come from the durable task row, so the envelope supplies the *target* of the check and never the *authority* for it (§7.4); and the adopt-on-conflict path must re-run the binding validation the load path applies, or a lost race silently skips a tenancy check (§8). Verified: `routes/action-routes.ts` sets `source: "http"` literally, and BullMQ forwards the server-written envelope source.
2. **Tenet 5 / one convergence point** — the invariant "a detached task's items are attributed to it" has to hold at the point every detached worker passes through, which is the WorkstreamFlow's root, not each worker. Same for the durable-backing refusal: it belongs at `taskBoard` construction, where all four backings converge.
3. **BP-030 (tolerate the old shape)** — a bare `TaskWorker` value keeps meaning inline, so no existing board needs editing; pending tasks admitted before a board became detached must still run; and an ordinary session already sitting at a `ws_`-prefixed id keeps working.
4. **BP-035 (second-path checklist)** — the second paths here are load-bearing and named individually in §9: the cancel-in-the-claim-gap window, the reclaim/retry path, the multi-tenant key, and the *off* state of detached mode.
5. **BP-003 (evidence)** — every criterion below names a check that fails against today's code. The ordering ones matter most: a reconciler test that seeds tasks *before* starting the sweep passes under a broken implementation.

### 5. What using it looks like

*(None of this compiles today.)*

**Declaring detached work — the only authored change:**

```ts
const board = taskBoard({
  name: "issue-work",
  boardId: "issue-work",                  // NEW: explicit, stable, required when detached
  collection: workBoardCollection,        // REQUIRED to detach — a durable backing
  workers: {
    summarize: summarizeBlock,            // bare value = inline, exactly as today
    implement: { worker: implementBlock, dispatch: { mode: "detached" } }
  }
});
```

**Filing work at it — unchanged, plus one field:**

```ts
await tasks.addTask({ goal: "Implement FIX-981", assignee: "implement", topic: "FIX-981" });
// The originating request returns here. `implement` is still running.
// A later task with the same topic routes to the SAME Workstream and appends to it.
```

**What the coordinator observes afterwards:**

```ts
const workstreams = await stores.session.list({ tenantId, parentage: { parentOf: sessionId } });
// → [{ id: "ws_9f2c…", parentSessionId: sessionId, topic: "FIX-981", coordinate: {kind:"assignee",name:"implement"} }]

const requests = await stores.request.list({ sessionId: "ws_9f2c…", tenantId, withItems: true });
// → the detached request, source: "taskboard", metadata.taskId set — and NOT in the parent's own request list.
```

`parentSessionId` is [FIX-1009](https://linear.app/fixpoint-labs/issue/FIX-1009)'s field, which this spec writes. **`topic` and `coordinate` are declared by *this* spec** (P2) and written at spawn (P3a), because nothing else adds them and this is the only writer. They are not decoration: a derived id is a hash, so without them a `ws_` record is opaque — and Decision 12's occupied-key case has no way to tell *our* Workstream from a squatter, which is the discriminator the epic's N27 named as the alternative to an HMAC. Both are optional (BP-030): an ordinary session has neither, a legacy record has neither, and a record at a derived key carrying neither is **not** a Workstream, which is exactly the verdict that recovery needs. FIX-1009 drops the `boardId` / `coordinate` / `topic` **predicates** — nothing lists by them — and that is a decision about *filters*, not about these fields; the two do not conflict (§12).

**Cancelling it:**

```ts
await tasks.cancelTask(taskId);
// Board row → cancelled. The Workstream's in-flight request is interrupted
// within one heartbeat interval (default 10s), cross-instance, with no client attached.
```

**What a detached worker must do differently — nothing, and that is the point:**

```ts
const implementBlock = handler({
  name: "implement",
  execute: async (input, ctx) => {
    return { pr: 182 };   // Identical inline or detached. No result obligation.
  }
});
```

An earlier draft of this spec put a result obligation here — a detached worker had to emit its result as a tagged item, because a bare return had nowhere durable to land. That obligation is **gone**, and it takes only one reason: the Workstream settles its own task from a live context (Decision 1), so it already holds the returned value and passes it straight to `complete(taskId, output)`. The value never crosses a request boundary. Its durable home is `Task.output` (`packages/orchestration/src/tasks/schema/task.ts:47`), written by `complete(id, output, options?)` (`tasks/collection/types.ts:159`) — the same row an inline worker's result lands on.

The only constraint on the value is that it be JSON-safe, which a durable board **already** imposes on an inline worker's `task.output` — so it is not a detached-only rule, and it needs nothing built to hold. A block behaves the same inline or detached, results included.

### 6. Decisions & rules — the sign-off surface

1. **The Workstream settles its own task; the assignee owns both.**
   *Rejected:* parent-side settlement driven by observing the Workstream's request status (the epic's Decision 7 body).
   *Locks in:* the hard problem disappears rather than being solved. Parent-side settlement has **no addressable surface** — every `TaskCollectionRef` constructor needs a live `BlockContext`, and once the initiating request ends nothing holds one (N26). Inside the Workstream there *is* a live context. It also collapses the six-terminal-status map to three in-Workstream outcomes (success → `complete`, throw → `fail`, abort → the canceller already settled), because the Workstream knows what happened directly instead of inferring it from a status that is written identically on a retryable and a final attempt (N41). **Cost, stated:** this narrows binding rule 14 — a Workstream now writes to the dispatching board. The rule's *reason* is untouched (the coordinator's outstanding-work list does not grow with entries it never planned; settling a task it *did* plan adds nothing), so the rule holds in spirit and is amended in letter. Every such write is fenced with **FIX-981's claim ticket, re-minted inside the Workstream** (§7.4) rather than carried on the payload — FIX-981 removes `expectAttempt`, and a caller-carried token is the shape its Decision 2 rejects. **Process loss settles nothing, and this spec no longer claims a backstop that exists.** Recovering a task left `in_progress` by a dead process is [FIX-1005](https://linear.app/fixpoint-labs/issue/FIX-1005)'s — the epic's corrected C3 row names it, with FIX-978 as a *prerequisite* rather than the owner — and FIX-1005 is `Backlog` with no spec. Decision 9's reconciler does not cover the gap: it sweeps `pending` only, explicitly not `in_progress`-with-an-expired-lease. So a process lost mid-work strands a claimed task until FIX-1005 ships, and that is stated rather than deferred to a mechanism this spec assumed (§12).

2. **Worker bindings bubble up into a flow-level registry at flow-definition time, outside `flow.actions`. Dispatch resolves to one fixed internal `WorkstreamFlow` core for the transport-set `source: "taskboard"` — never to a per-coordinate binding.**
   *Rejected:* a per-worker hosting coordinate authored on the board (N9's first option); a source *gate* on an ordinary `flow.actions` entry; **a per-coordinate core returned from the registry at dispatch time**; and **a carried core on the envelope** (`resolvedActionCore`).
   *Locks in:* the two halves of N6 at once — the binding is re-resolvable from strings after a restart, **and** the worker is unreachable from HTTP/MCP because it is not in `flow.actions` at all, rather than being in there behind a check. This copies the shipped precedent exactly: `webhook` / `chat` / `scheduled` already resolve from flow-level maps that are not `flow.actions`, reachable only when `source` matches. The registry is produced **by construction** — declarations accumulate on the sequencer as steps are added and `defineFlow` reads the union off each action root (FIX-688), so `taskBoard()` stamps its bindings on the drain sequencer and they arrive at the flow the same way resources do. No author declares a coordinate; N9's "no surface to derive from" dissolves. **Resolving to one fixed core rather than per-coordinate is what makes Decision 4's wrapper unbypassable** — there is no route from dispatch to a bare worker block, so the attribution mark cannot silently no-op. It also means **no type widening**: the envelope carries a fixed internal sentinel exactly as the event transports do, `runAction`'s public `keyof typeof flow.actions & string` constraint is untouched, and the internal dispatch boundary casts as it already does in four shipped call sites. The carried-core variant is rejected on measurement — `resolvedActionCore` is neither serialized nor persisted and the BullMQ dispatcher does not forward it, so under Decision 3's out-of-process scope it would resolve in-process and silently fail out-of-process (§7.3).

3. **Execution composes through `host.dispatch` → `FlowDispatcher`; detached work gets its own dispatcher constructed with `attempts: 1`.**
   *Rejected:* a bespoke `runAction` loop; and a per-dispatch retry override on the envelope.
   *Locks in:* the epic's "no sibling job queue" rule protects the *substrate*, not the *transport* — this is stated so a reviewer does not read reuse as a reversal. The board already owns retries via `maxAttempts` and `fail`'s soft/hard split; BullMQ's default of 3 attempts stacked underneath would triple the real attempt count and make the task row's `attempts` a lie (N41). A dedicated queue is config-only with no new public surface, where a per-dispatch override would be new envelope surface that must be server-derived to stay BP-031-safe (N60).

4. **The detached action is a `WorkstreamFlow`: an internal, non-API-callable flow whose action takes `{boardId, taskId}` and whose root is a sequencer wrapping a router that dispatches to the task's assigned worker. It is assembled once per flow from the bubbled registry, and it is what dispatch resolves to as a whole (Decision 2).**
   *Rejected:* a router at the action root (the shape as measured in `__poc-workstream-schema.test-d.ts`); and pre-wrapping each registry binding as its own sequencer, which would delete this router.
   *Locks in:* `connectInput` erases a route's input schema to `ZodTypeAny`, which is what lets one static flow carry heterogeneous workers with no union and no registry — that half is measured and kept. **The sequencer wrapper is my correction and it is load-bearing:** `_markTaskScope` walks the parent chain and writes only to a node with `kind === "sequencer"`, returning silently when it finds none. With a router root, marking the task scope is a **silent no-op** and every detached worker's items are unattributed — N24 unfixed while looking fixed. The wrapper's first `.tap` mirrors the drain's own leading tap one level up, and that means **all** of it: gate the start, mark the scope (`index.ts:700`), and **re-mint FIX-981's claim ticket** (`:704`'s stamp, which cannot be inherited across a process boundary — §7.4). Adopting only the scope mark is what leaves a detached worker's tool calls unguarded. **The router selects on the task row's `assignee`**, re-read from the durable board by that same gate — a server-derived fact, not envelope metadata (BP-031). Pre-wrapped bindings are rejected because they would enforce the attribution invariant once per binding instead of at one convergence point (focus practice 2), so a binding added without its wrapper regresses in silence.

5. **No re-dispatch template is persisted on the task row. It is derived at claim and at reconcile time.**
   *Rejected:* the epic's Decision 6 requirement (2) — writing a template atomically with admission. **The two documents disagree in letter and the owner has not yet ruled; §12 open question 4 carries it.**
   *Locks in:* three findings dissolve rather than being handled. N43 (two shipped admission paths bypass the board, so a board-minted template is absent from exactly the admissions an agent makes at runtime) stops mattering, because nothing is minted at admission. N34 (rows admitted before a board became detached carry no template) stops mattering for the same reason. And Decision 6's atomic-write requirement drops to zero. **The argument:** the epic assumed the template could not be re-derived, citing that the raw `addTask` path never had the registry. That is true of the *admission* path and false of the *reconciler*, which runs inside a board-aware drain that holds the registry — the routing tuple is fully recoverable from the board plus the task's `assignee` and `topic`. What the task row *does* record is `{sessionId, requestId}` as **fact at claim time**, which is the same field [FIX-1005](https://linear.app/fixpoint-labs/issue/FIX-1005) needs for liveness. **This is an epic-level departure and is being raised on the epic PR.**

6. **No forking. A detached participant declaring `contextSupply: "conversation"` is refused by name at board construction.**
   *Rejected:* REFERENCE forking with an accepted N+1 cursor read.
   *Locks in:* five sub-problems leave this issue with it — N17 (a cursor on a caller-writable surface), N19 and N32 (an awaited content snapshot whose retention contradicts why COPY was rejected), N7 (a history window that does not compose across a chain), and N36 (41 store calls per child turn, with no batch-by-id read on any adapter). None is referenced by any completion criterion. The required condition is the refusal: a worker that has quietly forgotten the conversation it was delegated from is the failure mode hardest to see from outside. The claim-time payload is the deliberate, narrower channel.

7. **Cancellation is delivered by teaching the existing heartbeat to read `abortRequested`.**
   *Rejected:* a new interrupt channel; relying on the shipped abort flag as-is.
   *Locks in:* every request already runs a heartbeat timer at `heartbeatIntervalMs` (default 10s) that *writes* to `ActiveRequestRegistry`. Making the same beat also read the request record and fire the local `AbortController` costs one store read per beat per in-flight request — bounded by deployment concurrency, not by board size. The shipped flag alone cannot do it: its contract is *"treat the next client disconnect as an intentional abort"*, and a detached request has no client to disconnect. **This is tenet 5:** the hole is on clientless requests generally, not on tasks, so it is fixed on the request — which also fixes it for every BullMQ job. Latency is bounded by one heartbeat interval and is stated in the contract.

8. **The serialized-continuation guarantee is dropped, and the criteria say so.**
   *Rejected:* a lane owner on the session record, a board-level liveness claim rule, and a generalized `LeaseStore` key — all three proposed and withdrawn upstream on inspection.
   *Locks in:* two requests in one Workstream may interleave. The epic explicitly permits dropping this and forbids shipping it on an unfenced field, a liveness check, or an expiring lock. **Exposure, honestly:** under claim-before-spawn one *task* produces one request, so a second concurrent request in a Workstream arises only from a second *task* on the same topic. Until a lane owner exists, one in-flight task per topic is an app-level discipline, documented. Filed as a follow-up rather than attempted.

9. **The pending-task reconciler runs as a step in the board's own drain, and it needs a drain to run.**
   *Rejected:* a standalone timer; assuming `reclaim()` covers it.
   *Locks in:* `reclaim()` — which ships today, and which FIX-978 explicitly does **not** give an automatic caller — skips every task that is not `in_progress` with an expired lease, so a task admitted and never claimed is invisible to it permanently, exactly what a dropped wake leaves behind. The two sweeps answer different questions and neither subsumes the other: this reconciler covers `pending`-with-no-live-request; `in_progress`-after-process-loss is FIX-1005's (§12). The sweep is idempotent for free, because re-waking an already-claimed task loses the claim race. Liveness comes from `ActiveRequestRegistry.listAll()` filtered by the derived session id — no new store verb. **Its cost is stated honestly, because the shape is not the one it looks like:** that is O(*global* in-flight requests) per scan, not O(board pending), so it scales with fleet concurrency rather than with the board. Acceptable at M3 and named as a **scale breakpoint**: when a deployment's global in-flight count materially exceeds a board's pending count, the scan is doing work proportional to traffic it has nothing to do with. The narrower shape already has a precedent in the same registry — the stale-request sweeper uses `listStale()` rather than filtering `listAll()` — so the follow-up is either a `listBySessionId` verb or a targeted `request.get(requestId)` per stale `pending` row, bounded by board size (§12). Not built now: it is a store-contract change across four adapters to solve a load profile M3 does not have. **The other cost, stated plainly:** a board nobody drains never reconciles. Each scan must use a freshly resolved ref, because a resource-backed ref hydrates its id mirror once and never observes later inserts — a poller holding a captured ref sees nothing, permanently and silently.

10. **`boardId` is explicitly declared and required when any worker is detached; a task's `assignee` is immutable after admission on a detached board.**
    *Rejected:* deriving `boardId` from `name` (unique per flow, not per session) or `collectionId` (the literal `"factory-supplied"` for every factory board).
    *Locks in:* the value lands in a persisted, derived session id, so it cannot be an incidental string. A rename is a **breaking re-key** that orphans live Workstreams, documented as such. Assignee immutability closes N11 — mutating it after a Workstream is keyed on the old coordinate runs the wrong worker or gets no wake at all. Coordinate with [FIX-976](https://linear.app/fixpoint-labs/issue/FIX-976), same path from the honesty angle.

11. **A detached board is refused at construction unless its backing is durable *and* its store can fence ownership; the filesystem adapter is excluded.**
    *Rejected:* degrading with a warning.
    *Locks in:* the two-part check binding rule 8 requires — `backing: "resource"` is not itself proof of durability. The default backing is `request`, whose lifetime *is* the request, so a detached worker on one runs with nothing able to settle or observe it and the failure appears only after the first restart. Filesystem has the conditional-write verb but guards it with a per-key mutex held on the **store instance**, which does not protect two OS processes over one directory — under Decision 8 that is the exact case a detached board cannot rely on, so it is *silently weaker*, which is the more dangerous shape. `factory` backings stay unsupported for detached work (Decision 3). **This decision is where the epic's filesystem "done" criterion is discharged** — FIX-981's Decision 6 routed it here because detachment does not exist until M3, and the owner confirmed the routing (§12). Two conditions come with it: the refusal is **by name, loudly**, and it must not be counted satisfied merely because `set` now accepts `expectedVersion` — a silent degrade fails the criterion. Testing behaviour 9 asserts it; §11 documents the limit for users.

12. **The `ws_` prefix is reserved at the caller-supplied boundary only, and an occupied derived key is a named terminal failure.**
    *Rejected:* an exemption flag on the envelope; a retroactive rule.
    *Locks in:* a derived id is squattable — a same-tenant caller who guesses the tuple can occupy the key before the task is admitted, and create-if-absent (`expectedVersion: "absent"`, FIX-1007's settled spelling) then conflicts forever against a record that is not a Workstream. **What tells the two apart is the routing tuple stored on the record** (§7.3): a conflicting record whose `parentSessionId` / `coordinate` / `topic` match the tuple just derived is *our* Workstream and is adopted; one that does not — including one carrying none at all — is an occupant. The reservation binds where caller input enters (the action route and `runAction`'s public entry); the framework's own create path is exempt **by construction** — a distinct internal entry point, not a caller-settable flag (BP-031). It is **not retroactive** (BP-030), so an existing session at a `ws_` id keeps working — which means the reservation stops future squats and does nothing for an existing occupant, and an occupied-key recovery is required regardless. That recovery fails the task by name. **Consequence, named:** `fail()` chooses soft-vs-hard from the retry budget alone, so a deterministic failure burns `maxAttempts` proving the same thing N times. This spec takes the epic's documented alternative — deterministic failures consume the budget — rather than inventing a force-terminal seam beside the one [FIX-948](https://linear.app/fixpoint-labs/issue/FIX-948) is already rewriting. If FIX-948 widens to carry N53, this becomes one call.

13. **Size is Large and the build is a five-node PR DAG, not Medium and not one PR.**
    *Rejected:* the epic's Medium sizing.
    *Locks in:* the epic itself says *"the missing-mechanism count is now the argument for splitting it."* Fifty-two findings, three unresolved design gaps, two security boundaries, and four blockers is not one reviewable change. The DAG is §8.

**Non-goals** — claim safety itself (FIX-981); automated reclamation and redelivery of an `in_progress` task after process loss (FIX-1005 — *not* FIX-978, which ships none); create-if-absent at the scope store (FIX-1007); the parentage predicate (FIX-1009); a result-*read* surface that bypasses the task row (unfiled — FIX-1008 cancelled, §7.7); the injection seam (FIX-999); the `TaskHandle.items()` accessor union (FIX-991b); cross-request *waiting* (FIX-983, deferred per N52); in-flight generator **delta** progress across processes (N35 — items are covered, deltas are not); forking; per-task dispatch targeting; a lane owner for serialized continuation; the HTTP route and client/react hops (S1b/S2/S3).

**Size:** Large — five sub-PRs across `core`, `engine`, `orchestration`, plus docs.

#### 7.2 The spawn capability, and where it may live

The board is in `orchestration`, which has `@flow-state-dev/engine` as a **devDependency only** — it cannot reach the seam by import even in principle. So the capability is a **type declared in `core`, implemented in `engine`, injected onto the execution context**, and consumed by the board through `uses`. It needs `stores` (create/resolve the child session) and `flow` (resolve the worker's hosting flow by kind), neither of which is on the public `BlockContext` — that is FIX-999's seam, and this issue is its first consumer.

Scope the seam to what the spawn legitimately needs rather than passing `StoreRegistry` through. A narrow named surface is easier to keep honest.

#### 7.3 The worker registry — derived, not authored

**How the bubble-up works — the rail already exists, but it is not a tree walk.** Stating the mechanism precisely matters, because the wrong description invites the wrong implementation. `defineFlow` does **not** walk the block tree. Declarations accumulate *on the sequencer*: as steps are added, each merges its child's `declaredResources` and ORs its `requiresOrg` into the sequencer's accumulator (`packages/core/src/blocks/sequencer.ts` — `mergeFrom` / `mergeRequiresOrgFrom`), so by definition time an action's **root block already carries the union**. `defineFlow` then reads that property off each action root and merges across actions (`collectBlockResources` / `collectRequiresOrg`, `packages/core/src/flow/defineFlow.ts`).

Detached bindings ride that same rail: `taskBoard()` stamps its `(boardId, coordinateKey) → worker` bindings onto the drain sequencer, they accumulate to the action root exactly as resources do, and `defineFlow` reads them into a flow-level map. **No new tree walker.** The flow's `kind` is known at the same moment, so the durable binding is `(flowKind, boardId, coordinateKey)` and **no author declares anything** — N9's "no surface to derive from" dissolves at the seam FIX-688 already built.

**What dispatch resolves to: one fixed internal action, not a per-coordinate core.** This is the load-bearing half, and it is what keeps Decision 4's wrapper from being bypassable. `resolveActionCore` gains a fourth branch that returns **one pre-assembled `WorkstreamFlow` core** — it does not index the registry by coordinate:

```
if (source === TASKBOARD_SOURCE) {
  if (flow.workstream !== undefined) return flow.workstream;  // ONE pre-assembled core
}
return flow.actions[actionName];                              // unchanged
```

The gate is the transport-set `source`, exactly as the shipped comment requires: *"the source gate is what stops a caller-addressed request from pivoting into an event handler via injected metadata."*

The `WorkstreamFlow` core is assembled once per flow at definition time **from** the bubbled registry: a sequencer root whose first `.tap` marks the task scope and runs the start gate, wrapping a router that carries every detached binding in that flow. Worker selection happens *inside* that router, and it selects on the **task row's** `assignee` — re-read from the durable board by the start gate that already runs there (§7.8) — not on envelope metadata. So the routing decision is server-derived (BP-031), and the coordinate on `metadata` is load-bearing only **upstream**, at spawn time, where it feeds the session-id derivation. Metadata is never itself trusted for routing.

Three consequences, all of them the point:

- **The attribution mark cannot be bypassed.** There is no path from `resolveActionCore` to a bare worker block, so `_markTaskScope` always has the sequencer it requires (§7.4). Under a per-coordinate binding it would be one forgotten wrapper away from the silent no-op Decision 4 exists to fix — the failure reintroduced while looking fixed.
- **The `actionName` type widening drops out entirely.** The envelope carries a fixed internal sentinel, exactly as the event transports do, and the branch never reaches `flow.actions[actionName]`. The public `runAction<TFlow, TActionName>` constraint is untouched; the internal dispatch boundary casts, which is the shipped precedent at `in-process-dispatcher.ts:82`, `request-recovery.ts:158`, `request-continuation.ts:143`, and `bullmq/worker.ts:83`. **No public type escape hatch is opened.**
- **The registry keeps exactly one job:** it is what the router routes over, and what the reconciler reads to re-derive a routing tuple after a restart (§7.6). It is no longer a dispatch-time lookup table.

**The two alternatives, and why they lose.**

*Pre-wrapped bindings* — each registry entry is itself a sequencer (mark + gate + worker), and Decision 4's router goes away. Rejected: it enforces the attribution invariant **N times instead of once**, which is precisely the shape focus practice 2 (tenet 5, one convergence point) rules out. A binding added later without the wrapper regresses silently, and silence is the whole failure class here.

*A carried core on the envelope* (`resolvedActionCore`, the dynamic-schedule precedent) for the hot claim→spawn path, with registry bubble-up serving only restart and reconcile. **Rejected on measurement, not preference.** `resolvedActionCore` is not serialized and not persisted — `docs/architecture/action-forms.md` marks the dynamic schedule as the one form that is **not crash-recoverable** for exactly this reason ("a block can't be serialized anyway") — and the BullMQ dispatcher's `queue.add` payload does not carry the field at all (`packages/bullmq/src/dispatcher.ts`). Decision 3 puts out-of-process dispatch **in scope**, so a carried core would work in-process and silently fail to resolve out-of-process: the same "works until it doesn't" class the sequencer-root correction exists to eliminate.

**Coordinate encoding.** The coordinate is the tagged union `{kind:"assignee",name} | {kind:"uniform"} | {kind:"floor"}` — not a reserved string, because assignees are unrestricted and a board may legally declare one named `__uniform__`. `coordinateKey()` serializes the tag before the tuple is encoded; handing the union to a string encoder directly stringifies every variant identically and merges every worker into one history.

**Derivation.** `ws_${sha256(JSON.stringify([parentSessionId, boardId, coordinateKey(c), topic])).slice(0,32)}`. The array form is what makes it canonical — under a raw join a separator migrates between fields and two different worker/topic pairs collide. `JSON.stringify` escapes lone surrogates that a URI encoder throws on, and hashing bounds the length regardless of a model-authored topic's size. `tenantId` stays *out* of the derivation and does its work through the storage namespace, as every other tenant separation already does — which makes the tenant filter on every read load-bearing rather than belt-and-braces. A blank or whitespace topic normalizes to absent and falls back to `taskId`, so continuity is opted into and never accidental.

**The tuple is also written onto the record, and this spec owns those fields.** `SessionRecord` gains optional `topic` and `coordinate` beside FIX-1009's `parentSessionId`. Nothing else adds them and this is the only writer, so the alternative was to correct §5's listing example instead — rejected, because a *second* consumer makes them load-bearing rather than cosmetic: **Decision 12's occupied-key case cannot otherwise tell our Workstream from a squatter.** A hash collides with a squat identically from the outside; comparing the record's stored tuple against the tuple just derived is what discriminates them, and it is the discriminator-field alternative the epic's N27 named beside an HMAC derivation. The fields are declared in P2 with the other derived-id machinery and written at spawn in P3a. Both optional (BP-030): an ordinary session has neither, a legacy record has neither, and a record sitting at a derived key with neither **is not a Workstream** — which is precisely the verdict occupied-key recovery needs, and it agrees with §9's row that such a session keeps working.

#### 7.4 The leading tap — attribution, and the claim ticket it must re-mint

`_markTaskScope` walks the parent chain and writes `scopeTaskId` onto the first node whose `parent.kind === "sequencer"`. **If there is none, the loop ends and it does nothing — no throw, no warning.** So the WorkstreamFlow's root must be a sequencer, and its first `.tap` marks the scope before any child scope is constructed. Descendant scopes then inherit through the existing walk, and the shared attribution algorithm (`itemsForTask` / `attributeItemsToTasks`) works unchanged — the algorithm was never the gap, the stamping was.

**The tap makes *two* stamps, and an earlier draft adopted only one.** The inline drain makes them as separate calls: `ctx._markTaskScope?.(task.id)` (`task-board/index.ts:700`) marks the item-attribution scope, and `stampCurrentTaskId(task)` (`:704`, defined at `flow-policy-wiring.ts:299-301`) enters the per-worker `AsyncLocalStorage` that carries the worker's **ownership token**. Mirroring only the first leaves the second silently absent inside a Workstream, and "silently absent" is the entire failure class this section exists for.

**Why the token cannot be inherited, and has to be re-minted.** [FIX-981](https://linear.app/fixpoint-labs/issue/FIX-981) (**Spec Approved**, lands first as M1) replaces `expectAttempt` with a bound **claim ticket** — `(collectionId, taskId, attempt, createdAt)` — minted by the board at claim time and read back through `currentClaim()`. Callers do not construct one, and a token handed along on a payload is the shape its Decision 2 explicitly rejects. Its carrier is `workerTaskIdStore`, an `AsyncLocalStorage` (`flow-policy-wiring.ts:106`), which is per-process and per-async-chain: the parent's claim-time stamp **cannot reach the Workstream at all**, and under Decision 3 the Workstream may legitimately be in another OS process. There is no plumbing that fixes this — an ALS value is not serializable, and making it one would recreate the caller-carried token FIX-981 rejected.

**The mint and the start gate are the same read.** §7.8's start gate re-reads the task row from the dispatching board — which is also the read §7.3's router selects on — and that row *is* the ticket: `collectionId` from the resolved parent board, plus `taskId`, `attempts` and `createdAt` (`tasks/schema/task.ts:88`, already persisted, so the fourth field costs no schema change). The gate verifies the envelope's claimed attempt **and** `createdAt` against the row, aborts on a mismatch, and mints the ticket from the row it just verified. **The mint adds no read of its own** (§7.8 counts what that one read now carries). The ticket is therefore **server-derived** (BP-031): the envelope supplies the *target* of the check and never the *authority* for it, which is FIX-981 Decision 2's posture reached from the other side.

**`createdAt` is what closes ABA here, not just there.** The owner's answer on FIX-981 puts `createdAt` in the ticket and closes the ABA case rather than accepting it. That answer earns something in this spec too: the claim→spawn window is exactly long enough for a task to be deleted and recreated under the same id, and an attempt-only gate can pass against the impostor. Comparing `createdAt` at the gate closes that window with the same fact the ticket already carries (§9).

**`collectionId` must be the *parent's*, and this is the trap worth naming.** FIX-981 declines a ticket naming a different collection exactly as it declines one naming a different task — two boards may both hold a task id. A ticket minted against the Workstream's own board would make every settlement `not-my-task`: silently, permanently, and only in the deployments where a Workstream has a board of its own. So the mint takes its `collectionId` from the board resolved through §7.7's seam, which is why that seam's **read** half belongs to P3a beside the start gate rather than to P3b beside the settlement writes (§8).

**Why this is not optional — `taskTools`.** FIX-981 §6.4 fences the model-facing tools by reading the ticket off that same ALS, and its rule is mechanical: no stamp means no guard and no error, because *"no ticket presented"* and *"not a claimed worker"* are the same condition. A detached worker is a model doing long work with tools, so `completeTask` / `failTask` / `cancelTask` / `blockTask` / `updateTask` are its **normal** way of touching the board, not an edge path. Without the re-mint every one of those calls runs unguarded — which is the obligation FIX-981 books onto this issue in as many words: *"FIX-982 must stamp the ticket at spawn for a detached worker, or its tool calls silently return to the unguarded posture."* It says "at spawn"; the only place a stamp survives to reach the worker is the Workstream's own async chain, so that is where this spec discharges it. Because `enterWith` mutates the current async resource, a tool call made inside a generator's tool loop inherits the ticket through the same await chain that already carries the task id — the same mechanism the drain relies on, one level up. Pinned by testing behaviour 12.

**Also refused at construction: `sessionStateSchema` on a detached worker.** Two routes declaring the same `sessionStateSchema` key with different shapes is silent at declaration, at `tsc`, and at write time — measured on `epic/durable-jobs` in `packages/core/test/__poc-workstream-schema.test-d.ts`, because `createScopeStateOps` performs no parse. Since every detached worker in a flow becomes a route on one shared `WorkstreamFlow` router, that collision is not hypothetical here; it is the default outcome of two workers picking the same obvious key name. **The refusal is one construction-time check and it is the whole fix for M3.** Key-shape *compatibility validation* — the richer alternative — is deferred: it is strictly more mechanism, and it buys nothing until a worker genuinely needs session-scoped state, which none of the M3 consumers do. A follow-up if a real use case appears (§12). A silent shape mismatch that ships is corrupted worker state discovered much later, so the failure has to be loud and early rather than clever.

#### 7.5 Payload validation

Two checks, and the second is the load-bearing one:

- **At admission**, on a detached board: `input` and `metadata` must be JSON-safe, so a bad value is a rejected `addTask` rather than a task nothing can dispatch.
- **At claim time**, on the fully materialized `TaskWorkerInput`: `packWorkerInput` adds dependency outputs and flow-policy `priorWork` *after* the claim, both typed `unknown` and authored by a different worker. That is the likelier source of a bad value, and it fails *after* ownership is acquired.

**A round-trip is not the check.** `JSON.parse(JSON.stringify(v))` throws only on `BigInt` and cycles; a `Date` becomes a string, a `Map` or class instance becomes `{}`, and a function disappears — all silently. Use a recursive JSON-value validator (reject non-plain prototypes, `undefined` in object position, functions, symbols) or deep-equivalence against the parsed result.

#### 7.6 Re-dispatch without a stored template

Nothing is written at admission. At reconcile time the sweep holds a board-aware context, so for each stale `pending` row it recovers the routing tuple from `(boardId from the board, coordinate from task.assignee via the board's three-case resolution, topic from the task, parentSessionId from the board's session)` and re-derives the envelope. The task row records only `{sessionId, requestId}` as fact at claim time — **the same field FIX-1005 adds for liveness; coordinate on it rather than adding a second.**

Worker resolution uses the board's **three-case** resolution (assignee → uniform → floor), not `dispatch-and-execute`'s helper, which throws on an unknown assignee and has no floor. Keep the `Object.hasOwn` guard: `assignee` arrives from a model-facing tool, and a bare index resolves inherited `Object.prototype` members, returning a non-worker function while skipping both the floor and the error.

#### 7.7 Settlement, and why no result projection is needed

The Workstream settles its own task, so it holds a live `BlockContext` and resolves the *parent's* board explicitly from the coordinate on its payload — not through `ctx.parent`, which would bind to the Workstream's own board. Both `complete` and `fail` present `currentClaim()` — the ticket the leading `.tap` re-minted from the verified task row (§7.4) — never a token carried on the payload.

**That resolution is a seam this issue must BUILD, and the epic's N68 (decided by the owner, 2026-08-07, option A) is what put it in scope.** An earlier draft assumed the parent's board was reachable through the ordinary resource path; it is not. `scopeIdentityId` resolves `session` to the **current** `sessionKey` (`createExecutionContext.ts:808-809`), so a session-scoped parent board resolved inside a Workstream hydrates a fresh empty board keyed `ws_…` and settles nothing. The alternative — forcing every detached board to user/org scope with `flowIsolation: false` — was **rejected**, because `resolveResourceScopeId` then returns the bare `identityId` and task rows carry no parent-session partition, so two coordinator sessions for one user would share one ledger.

**What to build, and the bound that keeps it small.** A settlement-only surface: resolve the dispatching board from the routing coordinate the Workstream already carries, expose `complete`/`fail` on it, nothing else. The coordinate is **server-derived, never caller-authored** (BP-031), and every write through it is fenced by the re-minted claim ticket (§7.4). It is **not** a general cross-session resource read — that is the epic's OQ-F and stays deferred. The mutation path underneath is unchanged: `getOrCreateTaskCollection` already accepts an already-resolved `ResourceCollectionRef` for `backing: "resource"`, so what the seam adds is resolving that ref against a session other than the current one. **Consequence for §6 Decision 11 and the epic's rule 15: a detached board's scope is now the author's choice** — session, user, or org — because the seam, not the scope, is what makes settlement reachable.

**The seam is read-then-write, and the read lands earlier than settlement.** The start gate re-reads the task row from this same board, before the worker runs (§7.4, §7.8), and §7.3's router selects on what that read returns. So the seam's **read** half is a P3a dependency and only the `complete` / `fail` verbs are P3b's — §8 splits the node that way rather than assigning the whole seam to settlement.

**Conditional on [FIX-1000](https://linear.app/fixpoint-labs/issue/FIX-1000) (#1049, not yet approved).** The seam addresses the parent's board by a session id it carries. FIX-1000 changes what a session-scope resource address is derived *from*: `resolveSessionResourceScopeId(record)` takes the **record**, because the address includes a storage generation minted at session creation, and *"a call site holding only a `sessionId` cannot produce an address without loading the record"* (its Decision 4). If FIX-1000 lands, this seam pays **one extra `stores.session.get` on the parent** before it can resolve the board — cheap, once per settlement, and on a path that already does a durable read. It is not merely a cost: skipping it after FIX-1000 lands would address the *bare* scope id and settle into an address nothing reads, which is the silent-loss failure FIX-1000's own §10 is built to pin. Recorded as conditional because FIX-1000 is unapproved; if it is dropped, nothing here changes.

**No result projection is built here, and none is needed.** The earlier draft specified a canonical tagged result item for the Workstream to decode; a later draft kept a narrowed dependency on FIX-1008's `RequestRecord.output`. Both are gone, and one fact removes them:

**Decision 1 settles inside the Workstream**, which holds a live `BlockContext` and the worker's return value *in hand*. It calls `complete(taskId, output)` with the value directly. There is nothing to write down and read back, so there is no decode rule, no tag convention, and no boxing problem. The durable record of the result is `Task.output` on the durable board (`tasks/schema/task.ts:47`, written by `complete` at `tasks/collection/types.ts:159`) — the same field an inline worker's result lands on, through the same JSON round-trip.

This is a strict simplification: the "one canonical typed projection" requirement N31 imposes is met by *not routing the value through a projection at all*.

**This spec now consumes nothing from FIX-1008, which is cancelled.** It was filed against parent-side settlement, where the worker's return value had to survive the request boundary because `RequestRecord` persists status and items but not `ExecutionResult.output`. Decision 1 removed that boundary crossing, so the issue was closed with nothing built (see the epic's N64). Two things it established survive it:

- **The JSON constraint stands on its own.** A durable board already requires `task.output` to be JSON-round-trippable, for inline and detached workers alike. §7.5's payload validation covers the *input* side; the board's own round-trip covers the output side. Neither needs a request-record preflight.
- **A result must never be reconstructed from a block trace**, and this is a trap worth naming because the shortcut looks correct. Block trace output is one of three shapes (`engine/src/context/createExecutionContext.ts:3006-3012`): `inline` carries the value, `ref` points at another item (resolvable, one hop), and `structure` records **shape only, with the value elided**. A settlement path reading "the last non-tapped block's output" therefore works in every test anyone would think to write and returns a shape-only object wherever `structure` kicks in — silently, with no error. `Task.output` is written explicitly by the settling code with the real value, which is why it is the only durable read path this spec relies on.

**Left uncovered, deliberately unfiled:** an observer that wants a Workstream's result *without* reading the task row. FIX-1008 would have supplied one as a side effect of its real purpose; with that purpose gone, no consumer has asked for the read path on its own. If one appears it should be argued on its own merits rather than inherited from a dissolved premise.

**Consequence for §7.4:** attribution is **no longer a precondition of settlement**. It remains required for testing behaviour 3 (a detached worker's items are attributed to its task) and for FIX-991b, but settlement does not wait on it.

#### 7.8 Cancellation and the claim→spawn window

Task cancellation looks up the task's recorded `{sessionId, requestId}`, sets `abortRequested` on the request record, and the running instance's next heartbeat fires its local controller. Bounded by one heartbeat interval.

Between claim and spawn there is **no request**, so a cancel landing in that gap makes the row terminal while the claimant proceeds from its stale snapshot — a cancelled task runs to completion. The **start gate** closes it: the same `.tap` that marks the task scope re-reads the task and aborts unless the claim is still current — `attempts` matches, `createdAt` matches, and status is `in_progress`. `createdAt` is what makes it an *identity* check rather than a counter check, so a task deleted and recreated under the same id inside the window cannot pass (§7.4). This also covers a crash-then-reclaim interleaving. **That one read does three jobs** — the staleness verdict here, the router's worker selection (§7.3), and the claim ticket the tap mints from the row it just verified (§7.4) — so the cost stays one read per detached request.

**What P3a inherits from [FIX-1007](https://linear.app/fixpoint-labs/issue/FIX-1007), and why it is more than a call-site swap.** FIX-1007 ships `expectedVersion: "absent"` on all four scope adapters and rewires exactly one caller — `handleCreateSession`, which wants create-or-**409**. It deliberately leaves `createExecutionContext:584` (user), `:602` (session) and `:664` (org) on their read-then-`set(…, "any")` shape, and names this issue as the rewire's owner, because *"the two callers need different semantics"*: a Workstream dispatch wants create-or-**adopt**. Failing the request on a lost race would be a regression, so on conflict the loser takes the winner's record and continues — **and the adopted record must then be run through the same binding validation the load path applies**: `ensureJournalDefaults` (`:604`), the userId check (`:609-611`), the tenant check (`:620-626`), and org immutability (`:636`). Three records, three adopt rules, one validation pass each. **The consequence is BP-031, not ergonomics:** the adopt path is the only one that reaches a record it did not write, so skipping that validation means a lost race silently *skips a tenancy check* — a Workstream continuing against another tenant's or another user's scope record, with no error anywhere. Neither spec claimed this until now; it is claimed here. FIX-1007 also notes the ordering against FIX-1000: if FIX-1000 lands first the adopted record carries the winner's storage generation, which is the correct outcome and is why the two are compatible.

**Why P3 splits.** The reviewer's objection was that a tracer bullet and an unsettled blocker fight each other, and it was right on the sequencing even though one half of it has since resolved. FIX-1008 is **cancelled** and gates nothing here (§7.7), so the projection contract is not a gate. **FIX-999 still is** — it is `Backlog`, it is the least-settled blocker, and it is the one that most affects this node's size. Splitting contains that: P3a is the vertical slice that proves detachment and is the piece FIX-999's seam shape can move; P3b is settlement, which depends on nothing external now that the Workstream settles from a live context. **P3a does not ship on its own** — a detached task that runs and never settles is worse than no detachment — so P3b follows immediately; the split buys reviewability and a contained blast radius if FIX-999's surface lands differently than assumed, not two independently shippable increments.

**Removals** (tenet 3 — a change that supersedes a path deletes it in the same change): the epic's POC suites under `packages/engine/test/poc-workstream-*.ts`, `packages/orchestration/test/poc-worker-dispatch-config.test.ts` and `packages/core/test/__poc-workstream-schema.*` are throwaway and currently run on the default vitest path. **Promote the checks that pin *shipped* behaviour into real regression tests — the silent `sessionStateSchema` collision, the absent public `BlockContext` members, the six terminal statuses — and delete the rest, plus the companion `__poc-tsconfig.json`, in the same PR** (P3a). Excluding them from the glob is rejected: an unrun POC rots silently and then misleads.

### 9. Edge cases & error handling

| Case | Behaviour |
|---|---|
| Cancel lands between claim and spawn | Start gate aborts the request before the worker runs; the row is already terminal. |
| Derived key occupied by a non-Workstream | Named terminal failure. Consumes retry budget (decision 12); recovery is not automatic. |
| Existing session already at a `ws_` id | Keeps working (BP-030). The reservation is not retroactive. |
| Two tenants, same parent session id / board / coordinate / topic | Same bare `ws_` id by construction; separated only by the storage namespace. **Every read must pass the tenant filter** — omitting it hands one tenant the other's turns silently, because the tenant matcher short-circuits on an absent key. |
| Board rebound to a different flow while a Workstream is live | Refuse and fail loudly. `flowKind` is deliberately out of the routing key (so a *hosting* rename does not orphan a live Workstream), which is wrong when the *binding* changes underneath (N28). A new topic is the migration. |
| Worker throws | `fail(id, error, { claim: currentClaim() })` — soft while budget remains (back to `pending`, `feedback` captured), hard to `errored` when exhausted. Skipping this leaves the task `in_progress` with nothing to recover it (see the row below), so the retry policy never advances. |
| Request `interrupted` / `suspended` | **Not settlements.** Both continue on the same request id. The Workstream settles nothing and the task stays claimed. **Its lease is not a backstop today:** nothing sweeps expired leases automatically — that is [FIX-1005](https://linear.app/fixpoint-labs/issue/FIX-1005)'s liveness-joined reclamation, which is `Backlog` with no spec, and Decision 9's reconciler covers `pending` only. Until FIX-1005 ships, a lost process leaves a claimed task stranded (§12). |
| Task deleted and recreated under the same id inside the claim→spawn window | Start gate declines: it compares the row's `createdAt`, not only `attempts`, so a recreated impostor at a matching attempt does not pass (§7.4). Same fact the claim ticket carries, checked one step earlier. |
| Claim ticket minted against the wrong collection | Every settlement declines as `not-my-task`, silently and permanently. The mint takes `collectionId` from the **parent** board resolved through §7.7's seam — the reason that seam's read half is a P3a dependency (§7.4, §8). |
| Detached mode **off** (the flag's second state) | A bare `TaskWorker` value and a board with no `dispatch` behave exactly as today — no new code path, asserted. |
| Legacy `pending` rows on a board that just became detached | Run through the ordinary path; the reconciler derives their envelope (no template needed — §7.6). |
| Reconciler scan | Must resolve the collection ref **per scan**. A ref hydrates its id mirror once and never observes later inserts, so a captured ref sees nothing, permanently and silently. |
| Detached worker declares `sessionStateSchema` | Refused at construction, by name (§7.4). Every detached worker in a flow is a route on one shared `WorkstreamFlow`, so two workers choosing the same key with different shapes would corrupt silently — the collision is measured to be invisible at declaration, at `tsc`, and at write time. |
| Uniform-worker board / absent assignee | Route to the `uniform` / `floor` coordinate. Detached mode must not convert a floor-routed task into an error, and must not fabricate an assignee a task never had. |
| Prototype-member assignee (`constructor`, `__proto__`, …) | Rejected by the `Object.hasOwn` guard; routes to the floor, or throws `unknown_assignee` without one. |
| Parent session deleted | Refused while **any** descendant exists — not merely a live one. An idle Workstream still leaves a child pointing at a deleted ancestor and, for a session-scoped board, erases the ledger under a live worker. |

### 10. Testing strategy

Feature → TDD, vertical tracer-bullet slices. P3a is the tracer bullet.

**Behaviours to test** (observable, each failing against today's code):

1. A foreground turn **returns while its detached work is still running**, and the work then completes.
2. The detached request appears in the **Workstream's** request list with `source: "taskboard"` and its `taskId` in metadata, and **not** in the parent's.
3. A detached worker's emitted items are **attributed to the task**. *Falsification:* run the same assertion against a router-rooted WorkstreamFlow and confirm it returns nothing — otherwise the test cannot distinguish a working mark from a silent no-op.
4. Two coordinating requests targeting one topic concurrently produce **exactly one Workstream** (needs FIX-1007).
5. Cancelling a task **terminates the in-flight request**, observably — not merely flipping a flag — within one heartbeat interval, with no client attached.
6. A cancel landing **between claim and spawn** prevents the worker from running.
7. The reconciler re-wakes a `pending` task with no live request. **Ordering is the whole assertion: start the sweep *before* admitting the task.** Seeding first passes under a captured-ref implementation that observes nothing.
8. A worker that throws consumes exactly **one** board attempt — not three (asserts the transport's retries are off).
9. A detached board on a request backing, on a filesystem store, with a `contextSupply: "conversation"` participant, or with a worker declaring `sessionStateSchema`, is **refused at construction, by name**.
10. Two tenants with identical routing tuples do not read each other's Workstream history.
11. A bare `TaskWorker` value still runs inline, and no existing board needs editing.
12. **A detached worker's `taskTools` call naming a task it does not hold is declined `not-my-task`** — the FIX-981 obligation, asserted rather than assumed. *Falsification:* remove the tap's ticket mint and confirm the same call **succeeds**; if it still declines, the test is reading the parent's stamp and proves nothing about a Workstream. Run it out-of-process, where an inherited stamp is impossible by construction.

**Evidence path (BP-003):** `pnpm test` for the unit-level slices; `fsdev run` over a kitchen-sink flow for the end-to-end criteria (1)–(3) and (5). **Pass criteria** are the twelve behaviours above, each failing before its slice and passing after. The epic's harness gap is real but bounded — `integration-tests/src/scenarios/task-board-drain-containment.test.ts` already proves a board property through full `runAction` composition, and `testFlow`'s seeding is deliberately idempotent so several calls share one store registry, which is the two-executions-over-one-board setup. Extend it; do not budget a spike rebuild.

**The reclamation backstop, stated rather than assumed.** Two places leaned on FIX-978 for recovery of a task left `in_progress` by a dead process — Decision 1's *"that is reclaim's job"* and §9's *"its lease is reclaim's backstop"*. Neither is true as written, and both now point at **[FIX-1005](https://linear.app/fixpoint-labs/issue/FIX-1005)**, which owns liveness-joined reclamation and redelivery. **FIX-1005 is `Backlog` with no spec, so the backstop is not built.** Keeping it honest in both directions: Decision 9's reconciler is not a substitute — it sweeps `pending` rows with no live request, explicitly **not** `in_progress`-with-an-expired-lease, and a lease expiring is not evidence of abandonment (the epic's rule 1). Nothing in this spec's build plan depends on FIX-1005 landing: P3a and P3b are complete without it. What is exposed is the epic's clause 3, not this issue's criteria — a lost process strands a claimed task until FIX-1005 exists, and the mechanism that closes it is FIX-1005's to design.

**Where this design depends on a blocker's outcome** *(for `cross-spec-review`)* — items 1 and 2 have settled since the first draft and are kept for the record:

1. **FIX-1007's sentinel — settled, both branches.** This spec assumed `SessionStore.set` could express "must not exist" and flagged two unknowns. Both are now answered by FIX-1007's spec, so they are folded rather than carried. **(a) The spelling is a distinct literal, `expectedVersion: "absent"`** — *not* a reuse of `0`, which is unavailable because scope records are born at version `0` and the first CAS write on every new session passes `0` against a live row. §7's call site takes that spelling. **(b) Version reuse on a recreated id is accepted** (its Decision 2 declines tombstones), which makes the decision-12 interaction **live rather than conditional** — and the resolution is that this spec must never treat a scope-record version as evidence of *identity*. It does not: get-or-create asks `"absent"`, which answers "is there a live row" and is unaffected by what version a recreated row starts at; and what discriminates *our* Workstream from a squatter at the same key is the routing tuple stored on the record (§7.3), not a version. The same lesson arrives from FIX-1000's side, where a recreated session gets a new storage generation for exactly this reason.
2. **FIX-1008's result mechanism — the collision is gone because the issue is.** This was the design's largest dependency on an unsettled blocker, and it resolved by subtraction. FIX-1008 was filed against parent-side settlement, where a worker's return value had to survive the request boundary; Decision 1 removed the crossing, the owner cancelled the issue, and its `blocks` edge here is deleted. **This spec builds no result projection and consumes no result-read surface** (§7.7), so the boundary that was the most likely cross-spec collision does not exist in either direction. One residual note for `cross-spec-review`, non-blocking: attribution (§7.4 / N24) is no longer a settlement precondition, which the epic now states from its side too (N64).
3. **FIX-999's surface shape.** This spec assumes a narrow named seam exposing store access and flow-resolution-by-kind. If FIX-999 exposes something narrower, the spawn capability may need a second seam entry. It is also **`Backlog`** while the other three are in spec — it is the least-settled blocker and the one that most affects P3a's size — which is why P3 is split (§8).
4. **FIX-1005 and the `{sessionId, requestId}` field.** Decision 5 records this at claim time; FIX-1005 (N61) needs the same field for liveness. **Two issues writing one field is a collision unless coordinated** — the recommendation is that FIX-1005 owns the schema change and this issue consumes it.
5. **FIX-948 and N53.** Decision 12 takes the documented alternative (deterministic failures consume the budget) precisely so this is *not* a blocker. If the owner moves N53 into FIX-948's scope, revisit — it becomes one branch in a routing rule FIX-948 is already rewriting.
6. **FIX-1000's record-derived scope address — conditional, and it is unapproved.** FIX-1000 (#1049) makes a session-scope resource address derive from the session *record* rather than its id, because the address carries a storage generation. §7.7's settlement seam holds a parent session **id**, so if FIX-1000 lands the seam gains one `stores.session.get` on the parent before it can resolve the board. The two specs edit the same type, so whichever lands second rebases; they do not conflict.
