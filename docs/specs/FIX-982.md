# FIX-982: The task board drain has no out-of-request executor — a leased task can't run outside its request — Implementation Spec

**Linear:** [FIX-982](https://linear.app/fixpoint-labs/issue/FIX-982) · **Epic:** [FIX-939](https://linear.app/fixpoint-labs/issue/FIX-939) (M3) · **Epic spec:** [`docs/specs/_epics/durable-jobs.md`](_epics/durable-jobs.md) on `epic/durable-jobs` · **Epic PR:** [#993](https://github.com/fixpoint-labs/flow-state-dev/pull/993)

## Spec evolution

- **Spec drafted** — framed as *"the spawn is the only unbuilt piece"*: everything downstream of it is measured on the real path, so this issue builds an injected capability that claims a task, derives a routing coordinate, and dispatches a request into a **Workstream** through the shipped `FlowDispatcher` seam. Three departures from the epic-spec's stated requirements are argued from code rather than inherited: the re-dispatch template is **derived, not persisted** (§7.6, dissolving N43/N34), the Workstream **settles its own task** (§7.7, dissolving N26), and the worker registry **bubbles up at flow-definition time** rather than being authored (§7.3, dissolving N9). Build shape is a five-node PR DAG; size is **Large**, not the epic's Medium.

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

A task board is a durable ledger of work. Its drain is not: whatever claims a task runs it **synchronously, inside the request that created the drain** (`task-board/index.ts` — the worker body sequencer, looped by `.loopBack`). When that request returns, anything still running dies with it.

That caps a task's life at one request cycle. The forcing function is Conductor M2 ([FIX-969](https://linear.app/fixpoint-labs/issue/FIX-969)): a phase — authoring a spec, implementing a PR — runs many minutes to an hour. It cannot be bound to a tick. FIX-939 names this its first top risk, and every other milestone in the epic is either blocked on it or dissolved by it.

**Why now, specifically:** the epic's objective gate is approved and the three blocking prerequisites are being specced concurrently. This is the last substrate piece that is genuinely unbuilt. The epic measured everything *downstream* of the spawn on the real `runAction` path — cross-flow execution, history isolation, topic reuse, restart re-resolution — and states the honest boundary plainly: *"the spawn itself is the one unbuilt piece."*

### 2. Solution in plain terms

When a board declares a worker as **detached**, claiming a task no longer runs it inline. Instead the board **spawns a Workstream** — a child session dedicated to one body of work — and starts a request inside it. The originating request returns immediately; the Workstream keeps going.

Four things make that work, and only the first is new machinery:

1. **A spawn capability.** Blocks already hold `ctx.stores` and their own `ctx.flow` at runtime, but a *capability* cannot legally name either — `core` can't depend on `engine`. So the spawn arrives as a capability declared in `core` and implemented in `engine`, over a public injection seam ([FIX-999](https://linear.app/fixpoint-labs/issue/FIX-999)). The board lives in `orchestration`, which has `engine` as a devDependency only, so injection is the only route that keeps the package boundary intact.

2. **A Workstream is just a session.** Its id is **derived** by hashing the routing tuple `(parentSessionId, boardId, coordinate, topic)`, so two racing coordinators aim at one key and create-if-absent ([FIX-1007](https://linear.app/fixpoint-labs/issue/FIX-1007)) makes one of them lose. History isolation then costs nothing — the `sessionId` filter every adapter already implements does all the work.

3. **Execution composes, it does not rebuild.** After the claim, the parent hands the payload to `host.dispatch` → `FlowDispatcher`. In-process that is `runAction`; out-of-process that is BullMQ's shipped worker, which already runs a request in another process from a serializable envelope with sequence-number stream resume. There is no second job queue and no bespoke loop.

4. **The worker is addressed by a coordinate nobody authored.** A task author names a `topic` and an `assignee`; the framework derives everything else. Worker bindings **bubble up into a flow-level registry at flow-definition time**, exactly as resource declarations already do — so the binding is re-resolvable from strings after a restart, and because it lives outside `flow.actions` it is not reachable from any HTTP or MCP caller.

**Philosophy.** **Tenet 2 (composition over features)** carries this: no new primitive: a Workstream is a session, the wake is a request, the ledger is the board, and the transport is the shipped dispatcher. **Tenet 5 (fix at the owning layer)** decides three of the sharper calls — cross-instance abort is fixed on the *request*'s heartbeat, where every clientless request benefits, not on the task; and the binding registry sits where the flow's block tree converges rather than at each board. **Tenet 3 (earn every addition)** is why forking, per-task targeting, and the serialized-continuation guarantee are all explicitly *not* built here.

### 3. Tradeoffs & alternatives

**The alternative that was already rejected upstream, and stays rejected:** a background *sibling request in the parent's session*. The epic built and measured it. Cross-turn history loads by `{sessionId, tenantId, status: "completed"}` with no foreground/background dimension, so a completed background request is indistinguishable from a user turn, and the window counts requests rather than tokens — 50 background turns evict the user's own turn entirely. A child session is excluded by a filter that already exists and is already correct in all four adapters. Isolation becomes a boundary that cannot be forgotten instead of a filter that must be remembered.

**The simpler approach: let the worker keep running and just not await it.** This is what `.work` / `_requestBackgroundSignal` does, and it genuinely is simpler. It is insufficient for one measured reason: the request work pool is **drained before terminal status**, so the request cannot return until the work finishes. It is intra-request concurrency, not detachment. Nothing about it survives the request boundary.

**Where I traded correctness for scope, deliberately, and the owner should see both:**

- **Serialized continuation is dropped, not solved.** Two requests in one Workstream can interleave. The epic proposed and then withdrew three mechanisms for a lane owner (the session record — clobbered by three unconditional writers; a liveness check — a cross-task predicate against a per-task fence; `LeaseStore` — no renewal, so the lock lets go while you hold it). I am not proposing a fourth. §6 decision 8 states the exposure and the app-level discipline that narrows it.
- **The reconciler needs a drain to run.** A board nobody drains never reconciles a lost wake. FSD supplies no scheduler loop, so the honest alternatives were "declare this" or "require the host to wire a cron". I declare it.

**Where the complexity actually is** — and it is not the spawn, which is about thirty lines. It is (a) **attribution**, because the one mechanism that stamps a task id onto emitted items only marks *sequencer* scopes and silently does nothing otherwise (§7.4); (b) **the failure map**, because "the request ended" is six statuses, two of which are not settlements at all; and (c) **admission**, because two shipped paths reach a board without ever seeing it.

### 4. Focus practices (1–5)

1. **BP-031 (never route or authorize from caller-controllable input)** — this issue adds two trust boundaries. The worker coordinate must be *derived* server-side, never authored on a task; and the admission gate on worker actions must key on the transport-set `source`, which the HTTP route hard-codes and a caller cannot forge. Verified: `routes/action-routes.ts` sets `source: "http"` literally, and BullMQ forwards the server-written envelope source.
2. **Tenet 5 / one convergence point** — the invariant "a detached task's items are attributed to it" has to hold at the point every detached worker passes through, which is the WorkstreamFlow's root, not each worker. Same for the durable-backing refusal: it belongs at `taskBoard` construction, where all four backings converge.
3. **BP-030 (tolerate the old shape)** — a bare `TaskWorker` value keeps meaning inline, so no existing board needs editing; pending tasks admitted before a board became detached must still run; and an ordinary session already sitting at a `ws_`-prefixed id keeps working.
4. **BP-035 (second-path checklist)** — the second paths here are load-bearing and named individually in §9: the cancel-in-the-claim-gap window, the reclaim/retry path, the multi-tenant key, and the *off* state of detached mode.
5. **BP-003 (evidence)** — every criterion below names a check that fails against today's code. The ordering ones matter most: a reconciler test that seeds tasks *before* starting the sweep passes under a broken implementation.

### 5. What using it looks like

*(None of this compiles today.)*

**Declaring detached work — the only authored change:**

```ts
const board = taskBoard({
  name: "issue-work",
  boardId: "issue-work",                  // NEW: explicit, stable, required when detached
  collection: workBoardCollection,        // REQUIRED to detach — a durable backing
  workers: {
    summarize: summarizeBlock,            // bare value = inline, exactly as today
    implement: { worker: implementBlock, dispatch: { mode: "detached" } }
  }
});
```

**Filing work at it — unchanged, plus one field:**

```ts
await tasks.addTask({ goal: "Implement FIX-981", assignee: "implement", topic: "FIX-981" });
// The originating request returns here. `implement` is still running.
// A later task with the same topic routes to the SAME Workstream and appends to it.
```

**What the coordinator observes afterwards:**

```ts
const workstreams = await stores.session.list({ tenantId, parentage: { parentOf: sessionId } });
// → [{ id: "ws_9f2c…", parentSessionId: sessionId, topic: "FIX-981", coordinate: {kind:"assignee",name:"implement"} }]

const requests = await stores.request.list({ sessionId: "ws_9f2c…", tenantId, withItems: true });
// → the detached request, source: "taskboard", metadata.taskId set — and NOT in the parent's own request list.
```

**Cancelling it:**

```ts
await tasks.cancelTask(taskId);
// Board row → cancelled. The Workstream's in-flight request is interrupted
// within one heartbeat interval (default 10s), cross-instance, with no client attached.
```

**What a detached worker must do differently — the one non-orthogonality:**

```ts
const implementBlock = handler({
  name: "implement",
  execute: async (input, ctx) => {
    // Inline, `return { pr: 182 }` is enough. Detached, a bare return is LOST —
    // RequestRecord persists status and items, never ExecutionResult.output.
    return { pr: 182 };   // ...surfaced durably by the result projection (§7.7)
  }
});
```

### 6. Decisions & rules — the sign-off surface

1. **The Workstream settles its own task; the assignee owns both.**
   *Rejected:* parent-side settlement driven by observing the Workstream's request status (the epic's Decision 7 body).
   *Locks in:* the hard problem disappears rather than being solved. Parent-side settlement has **no addressable surface** — every `TaskCollectionRef` constructor needs a live `BlockContext`, and once the initiating request ends nothing holds one (N26). Inside the Workstream there *is* a live context. It also collapses the six-terminal-status map to three in-Workstream outcomes (success → `complete`, throw → `fail`, abort → the canceller already settled), because the Workstream knows what happened directly instead of inferring it from a status that is written identically on a retryable and a final attempt (N41). **Cost, stated:** this narrows binding rule 14 — a Workstream now writes to the dispatching board. The rule's *reason* is untouched (the coordinator's outstanding-work list does not grow with entries it never planned; settling a task it *did* plan adds nothing), so the rule holds in spirit and is amended in letter. Every such write is fenced with `expectAttempt` (Decision 4's token, which the handed payload carries). **Process loss settles nothing** — that is reclaim's job, not this path's.

2. **Worker bindings bubble up into a flow-level registry at flow-definition time, outside `flow.actions`, and are resolved only for the transport-set `source: "taskboard"`.**
   *Rejected:* a per-worker hosting coordinate authored on the board (N9's first option); and a source *gate* on an ordinary `flow.actions` entry.
   *Locks in:* the two halves of N6 at once — the binding is re-resolvable from strings after a restart, **and** the worker is unreachable from HTTP/MCP because it is not in `flow.actions` at all, rather than being in there behind a check. This copies the shipped precedent exactly: `webhook` / `chat` / `scheduled` already resolve from flow-level maps that are not `flow.actions`, reachable only when `source` matches. The registry is produced **by construction** — `defineFlow` already walks the block tree to bubble resource declarations up (FIX-688), so no author declares a coordinate and N9's "no surface to derive from" dissolves. *Consequence named, not hidden:* `runAction`'s `actionName` is typed `keyof typeof flow.actions & string`, which a worker coordinate does not satisfy — the implementer widens that type or introduces a discriminated dispatch target.

3. **Execution composes through `host.dispatch` → `FlowDispatcher`; detached work gets its own dispatcher constructed with `attempts: 1`.**
   *Rejected:* a bespoke `runAction` loop; and a per-dispatch retry override on the envelope.
   *Locks in:* the epic's "no sibling job queue" rule protects the *substrate*, not the *transport* — this is stated so a reviewer does not read reuse as a reversal. The board already owns retries via `maxAttempts` and `fail`'s soft/hard split; BullMQ's default of 3 attempts stacked underneath would triple the real attempt count and make the task row's `attempts` a lie (N41). A dedicated queue is config-only with no new public surface, where a per-dispatch override would be new envelope surface that must be server-derived to stay BP-031-safe (N60).

4. **The detached action is a `WorkstreamFlow`: an internal, non-API-callable flow whose action takes `{boardId, taskId}` and whose root is a sequencer wrapping a router that dispatches to the task's assigned worker.**
   *Rejected:* a router at the action root (the shape as measured in `__poc-workstream-schema.test-d.ts`).
   *Locks in:* `connectInput` erases a route's input schema to `ZodTypeAny`, which is what lets one static flow carry heterogeneous workers with no union and no registry — that half is measured and kept. **The sequencer wrapper is my correction and it is load-bearing:** `_markTaskScope` walks the parent chain and writes only to a node with `kind === "sequencer"`, returning silently when it finds none. With a router root, marking the task scope is a **silent no-op** and every detached worker's items are unattributed — N24 unfixed while looking fixed. The wrapper's first `.tap` marks the scope and gates the start, mirroring `task-board/index.ts` exactly, one level up.

5. **No re-dispatch template is persisted on the task row. It is derived at claim and at reconcile time.**
   *Rejected:* the epic's Decision 6 requirement (2) — writing a template atomically with admission.
   *Locks in:* three findings dissolve rather than being handled. N43 (two shipped admission paths bypass the board, so a board-minted template is absent from exactly the admissions an agent makes at runtime) stops mattering, because nothing is minted at admission. N34 (rows admitted before a board became detached carry no template) stops mattering for the same reason. And Decision 6's atomic-write requirement drops to zero. **The argument:** the epic assumed the template could not be re-derived, citing that the raw `addTask` path never had the registry. That is true of the *admission* path and false of the *reconciler*, which runs inside a board-aware drain that holds the registry — the routing tuple is fully recoverable from the board plus the task's `assignee` and `topic`. What the task row *does* record is `{sessionId, requestId}` as **fact at claim time**, which is the same field [FIX-1005](https://linear.app/fixpoint-labs/issue/FIX-1005) needs for liveness. **This is an epic-level departure and is being raised on the epic PR.**

6. **No forking. A detached participant declaring `contextSupply: "conversation"` is refused by name at board construction.**
   *Rejected:* REFERENCE forking with an accepted N+1 cursor read.
   *Locks in:* five sub-problems leave this issue with it — N17 (a cursor on a caller-writable surface), N19 and N32 (an awaited content snapshot whose retention contradicts why COPY was rejected), N7 (a history window that does not compose across a chain), and N36 (41 store calls per child turn, with no batch-by-id read on any adapter). None is referenced by any completion criterion. The required condition is the refusal: a worker that has quietly forgotten the conversation it was delegated from is the failure mode hardest to see from outside. The claim-time payload is the deliberate, narrower channel.

7. **Cancellation is delivered by teaching the existing heartbeat to read `abortRequested`.**
   *Rejected:* a new interrupt channel; relying on the shipped abort flag as-is.
   *Locks in:* every request already runs a heartbeat timer at `heartbeatIntervalMs` (default 10s) that *writes* to `ActiveRequestRegistry`. Making the same beat also read the request record and fire the local `AbortController` costs one store read per beat per in-flight request — bounded by deployment concurrency, not by board size. The shipped flag alone cannot do it: its contract is *"treat the next client disconnect as an intentional abort"*, and a detached request has no client to disconnect. **This is tenet 5:** the hole is on clientless requests generally, not on tasks, so it is fixed on the request — which also fixes it for every BullMQ job. Latency is bounded by one heartbeat interval and is stated in the contract.

8. **The serialized-continuation guarantee is dropped, and the criteria say so.**
   *Rejected:* a lane owner on the session record, a board-level liveness claim rule, and a generalized `LeaseStore` key — all three proposed and withdrawn upstream on inspection.
   *Locks in:* two requests in one Workstream may interleave. The epic explicitly permits dropping this and forbids shipping it on an unfenced field, a liveness check, or an expiring lock. **Exposure, honestly:** under claim-before-spawn one *task* produces one request, so a second concurrent request in a Workstream arises only from a second *task* on the same topic. Until a lane owner exists, one in-flight task per topic is an app-level discipline, documented. Filed as a follow-up rather than attempted.

9. **The pending-task reconciler runs as a step in the board's own drain, and it needs a drain to run.**
   *Rejected:* a standalone timer; assuming FIX-978's reclaim covers it.
   *Locks in:* FIX-978's `reclaim` skips every task that is not `in_progress` with an expired lease, so a task admitted and never claimed is invisible to it permanently — exactly what a dropped wake leaves behind. The sweep is idempotent for free, because re-waking an already-claimed task loses the claim race. Liveness comes from `ActiveRequestRegistry.listAll()` filtered by the derived session id — no new store verb, O(in-flight requests). **The cost stated plainly:** a board nobody drains never reconciles. Each scan must use a freshly resolved ref, because a resource-backed ref hydrates its id mirror once and never observes later inserts — a poller holding a captured ref sees nothing, permanently and silently.

10. **`boardId` is explicitly declared and required when any worker is detached; a task's `assignee` is immutable after admission on a detached board.**
    *Rejected:* deriving `boardId` from `name` (unique per flow, not per session) or `collectionId` (the literal `"factory-supplied"` for every factory board).
    *Locks in:* the value lands in a persisted, derived session id, so it cannot be an incidental string. A rename is a **breaking re-key** that orphans live Workstreams, documented as such. Assignee immutability closes N11 — mutating it after a Workstream is keyed on the old coordinate runs the wrong worker or gets no wake at all. Coordinate with [FIX-976](https://linear.app/fixpoint-labs/issue/FIX-976), same path from the honesty angle.

11. **A detached board is refused at construction unless its backing is durable *and* its store can fence ownership; the filesystem adapter is excluded.**
    *Rejected:* degrading with a warning.
    *Locks in:* the two-part check binding rule 8 requires — `backing: "resource"` is not itself proof of durability. The default backing is `request`, whose lifetime *is* the request, so a detached worker on one runs with nothing able to settle or observe it and the failure appears only after the first restart. Filesystem has the conditional-write verb but guards it with a per-key mutex held on the **store instance**, which does not protect two OS processes over one directory — under Decision 8 that is the exact case a detached board cannot rely on, so it is *silently weaker*, which is the more dangerous shape. `factory` backings stay unsupported for detached work (Decision 3).

12. **The `ws_` prefix is reserved at the caller-supplied boundary only, and an occupied derived key is a named terminal failure.**
    *Rejected:* an exemption flag on the envelope; a retroactive rule.
    *Locks in:* a derived id is squattable — a same-tenant caller who guesses the tuple can occupy the key before the task is admitted, and create-if-absent then conflicts forever against a record that is not a Workstream. The reservation binds where caller input enters (the action route and `runAction`'s public entry); the framework's own create path is exempt **by construction** — a distinct internal entry point, not a caller-settable flag (BP-031). It is **not retroactive** (BP-030), so an existing session at a `ws_` id keeps working — which means the reservation stops future squats and does nothing for an existing occupant, and an occupied-key recovery is required regardless. That recovery fails the task by name. **Consequence, named:** `fail()` chooses soft-vs-hard from the retry budget alone, so a deterministic failure burns `maxAttempts` proving the same thing N times. This spec takes the epic's documented alternative — deterministic failures consume the budget — rather than inventing a force-terminal seam beside the one [FIX-948](https://linear.app/fixpoint-labs/issue/FIX-948) is already rewriting. If FIX-948 widens to carry N53, this becomes one call.

13. **Size is Large and the build is a five-node PR DAG, not Medium and not one PR.**
    *Rejected:* the epic's Medium sizing.
    *Locks in:* the epic itself says *"the missing-mechanism count is now the argument for splitting it."* Fifty-two findings, three unresolved design gaps, two security boundaries, and four blockers is not one reviewable change. The DAG is §8.

**Non-goals** — claim safety itself (FIX-981); automated reclamation (FIX-978); create-if-absent at the scope store (FIX-1007); the parentage predicate (FIX-1009); the result-*read* surface (FIX-1008); the injection seam (FIX-999); the `TaskHandle.items()` accessor union (FIX-991b); cross-request *waiting* (FIX-983, deferred per N52); in-flight generator **delta** progress across processes (N35 — items are covered, deltas are not); forking; per-task dispatch targeting; a lane owner for serialized continuation; the HTTP route and client/react hops (S1b/S2/S3).

**Size:** Large — five sub-PRs across `core`, `engine`, `orchestration`, plus docs.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

#### 7.1 The shape

```mermaid
sequenceDiagram
  participant C as Coordinator request<br/>(parent session S)
  participant B as Board (durable)
  participant Cap as spawn capability<br/>core type / engine impl
  participant D as FlowDispatcher<br/>in-process | BullMQ
  participant W as Workstream ws_9f2c…<br/>WorkstreamFlow

  C->>B: addTask{goal, assignee, topic}
  Note over C,B: JSON-safety check at admission (loud, early)
  C->>B: claim(taskId) — FIX-981's fenced write
  B-->>C: claimed{attempts: n}
  C->>C: packWorkerInput → payload (deps, feedback, priorWork)
  Note over C: recursive JSON validation of the MATERIALIZED payload
  C->>Cap: spawn{boardId, coordinate, topic, taskId, payload}
  Cap->>Cap: derive ws id = ws_sha256([parentSessionId, boardId, coordKey, topic])
  Cap->>W: get-or-create session (create-if-absent, FIX-1007)
  Note over Cap,W: inherits userId / orgId / tenantId from parent (N29)
  Cap->>D: dispatch envelope{flowKind, workerCoordinate, sessionId: ws_…, source: "taskboard"}
  Note over C: coordinator request RETURNS here
  D->>W: runAction
  W->>W: tap: mark task scope + START GATE (re-read task, abort if attempt stale)
  W->>W: router → worker block (connectInput erases route schemas)
  W->>B: complete / fail with expectAttempt — Workstream settles (decision 1)
```

#### 7.2 The spawn capability, and where it may live

The board is in `orchestration`, which has `@flow-state-dev/engine` as a **devDependency only** — it cannot reach the seam by import even in principle. So the capability is a **type declared in `core`, implemented in `engine`, injected onto the execution context**, and consumed by the board through `uses`. It needs `stores` (create/resolve the child session) and `flow` (resolve the worker's hosting flow by kind), neither of which is on the public `BlockContext` — that is FIX-999's seam, and this issue is its first consumer.

Scope the seam to what the spawn legitimately needs rather than passing `StoreRegistry` through. A narrow named surface is easier to keep honest.

#### 7.3 The worker registry — derived, not authored

`defineFlow` already walks the block tree at definition time to bubble block-declared resources up into the flow (FIX-688, `collectBlockResources`). Extend that walk: every `taskBoard` with a detached worker contributes its `(boardId, coordinateKey) → worker` bindings to a flow-level map. The flow's `kind` is known at the same moment, so the durable binding is `(flowKind, boardId, coordinateKey)` and **no author declares anything**.

`resolveActionCore` gains a fourth branch, structurally identical to the three that ship:

```
if (source === TASKBOARD_SOURCE) {
  const coord = metadata?.taskboard?.coordinate;   // metadata for the coordinate…
  const binding = flow.workstreamWorkers?.[coord]; // …but the SOURCE is the gate
  if (binding !== undefined) return binding;
}
return flow.actions[actionName];                    // unchanged
```

The gate is the transport-set `source`, exactly as the shipped comment requires: *"the source gate is what stops a caller-addressed request from pivoting into an event handler via injected metadata."* `metadata` carries the coordinate and is never itself trusted.

**Coordinate encoding.** The coordinate is the tagged union `{kind:"assignee",name} | {kind:"uniform"} | {kind:"floor"}` — not a reserved string, because assignees are unrestricted and a board may legally declare one named `__uniform__`. `coordinateKey()` serializes the tag before the tuple is encoded; handing the union to a string encoder directly stringifies every variant identically and merges every worker into one history.

**Derivation.** `ws_${sha256(JSON.stringify([parentSessionId, boardId, coordinateKey(c), topic])).slice(0,32)}`. The array form is what makes it canonical — under a raw join a separator migrates between fields and two different worker/topic pairs collide. `JSON.stringify` escapes lone surrogates that a URI encoder throws on, and hashing bounds the length regardless of a model-authored topic's size. `tenantId` stays *out* of the derivation and does its work through the storage namespace, as every other tenant separation already does — which makes the tenant filter on every read load-bearing rather than belt-and-braces. A blank or whitespace topic normalizes to absent and falls back to `taskId`, so continuity is opted into and never accidental.

#### 7.4 Attribution — the correction that matters

`_markTaskScope` walks the parent chain and writes `scopeTaskId` onto the first node whose `parent.kind === "sequencer"`. **If there is none, the loop ends and it does nothing — no throw, no warning.** So the WorkstreamFlow's root must be a sequencer, and its first `.tap` marks the scope before any child scope is constructed. Descendant scopes then inherit through the existing walk, and the shared attribution algorithm (`itemsForTask` / `attributeItemsToTasks`) works unchanged — the algorithm was never the gap, the stamping was.

**Also flag at construction:** two routes declaring the same `sessionStateSchema` key with different shapes is silent at declaration, at `tsc`, and at write time (measured — `createScopeStateOps` performs no parse). Either forbid `sessionStateSchema` on detached workers or validate key-shape compatibility when the WorkstreamFlow is assembled. A silent shape mismatch here surfaces as corrupted worker state much later.

#### 7.5 Payload validation

Two checks, and the second is the load-bearing one:

- **At admission**, on a detached board: `input` and `metadata` must be JSON-safe, so a bad value is a rejected `addTask` rather than a task nothing can dispatch.
- **At claim time**, on the fully materialized `TaskWorkerInput`: `packWorkerInput` adds dependency outputs and flow-policy `priorWork` *after* the claim, both typed `unknown` and authored by a different worker. That is the likelier source of a bad value, and it fails *after* ownership is acquired.

**A round-trip is not the check.** `JSON.parse(JSON.stringify(v))` throws only on `BigInt` and cycles; a `Date` becomes a string, a `Map` or class instance becomes `{}`, and a function disappears — all silently. Use a recursive JSON-value validator (reject non-plain prototypes, `undefined` in object position, functions, symbols) or deep-equivalence against the parsed result.

#### 7.6 Re-dispatch without a stored template

Nothing is written at admission. At reconcile time the sweep holds a board-aware context, so for each stale `pending` row it recovers the routing tuple from `(boardId from the board, coordinate from task.assignee via the board's three-case resolution, topic from the task, parentSessionId from the board's session)` and re-derives the envelope. The task row records only `{sessionId, requestId}` as fact at claim time — **the same field FIX-1005 adds for liveness; coordinate on it rather than adding a second.**

Worker resolution uses the board's **three-case** resolution (assignee → uniform → floor), not `dispatch-and-execute`'s helper, which throws on an unknown assignee and has no floor. Keep the `Object.hasOwn` guard: `assignee` arrives from a model-facing tool, and a bare index resolves inherited `Object.prototype` members, returning a non-worker function while skipping both the floor and the error.

#### 7.7 Settlement and the result projection

The Workstream settles its own task, so it holds a live `BlockContext` and resolves the *parent's* board explicitly from the coordinate on its payload — not through `ctx.parent`, which would bind to the Workstream's own board. Both `complete` and `fail` carry `expectAttempt` from the handed payload.

The worker's result must be represented on a surface that survives a restart, because `RequestRecord` persists status and items but never `ExecutionResult.output`. **This spec's projection is a single canonical, typed result item** — one tagged item carrying `{taskId, attempt, output}` — and settlement decodes exactly that. "Retrieve the items and infer" is rejected: whatever `complete(id, output)` stores is handed verbatim to downstream workers as `deps[depId]`, so a guessed shape does not merely record the wrong thing on one row, it feeds a wrong-shaped value into another worker's typed input where nothing checks it.

> **This is the design's largest dependency on an unsettled blocker.** FIX-1008 owns the result-read *surface* and its stated verification does not name a mechanism. If it lands a task-keyed shared resource instead of an item, §7.7's shape changes (the direction — one canonical typed projection, decoded not inferred — does not). If it takes the item path, the attribution fix in §7.4 is a **precondition of settlement**, not a parallel task. See §12.

#### 7.8 Cancellation and the claim→spawn window

Task cancellation looks up the task's recorded `{sessionId, requestId}`, sets `abortRequested` on the request record, and the running instance's next heartbeat fires its local controller. Bounded by one heartbeat interval.

Between claim and spawn there is **no request**, so a cancel landing in that gap makes the row terminal while the claimant proceeds from its stale snapshot — a cancelled task runs to completion. The **start gate** closes it: the same `.tap` that marks the task scope re-reads the task and aborts unless the claimed attempt is still current (`attempts` matches and status is `in_progress`). This also covers a crash-then-reclaim interleaving, and costs one read per detached request.

### 9. Edge cases & error handling

| Case | Behaviour |
|---|---|
| Cancel lands between claim and spawn | Start gate aborts the request before the worker runs; the row is already terminal. |
| Derived key occupied by a non-Workstream | Named terminal failure. Consumes retry budget (decision 12); recovery is not automatic. |
| Existing session already at a `ws_` id | Keeps working (BP-030). The reservation is not retroactive. |
| Two tenants, same parent session id / board / coordinate / topic | Same bare `ws_` id by construction; separated only by the storage namespace. **Every read must pass the tenant filter** — omitting it hands one tenant the other's turns silently, because the tenant matcher short-circuits on an absent key. |
| Board rebound to a different flow while a Workstream is live | Refuse and fail loudly. `flowKind` is deliberately out of the routing key (so a *hosting* rename does not orphan a live Workstream), which is wrong when the *binding* changes underneath (N28). A new topic is the migration. |
| Worker throws | `fail(id, error, {expectAttempt})` — soft while budget remains (back to `pending`, `feedback` captured), hard to `errored` when exhausted. Skipping this leaves the task `in_progress` until reclaim, which restores it *without* consuming the retry policy — reclaimable forever while the budget never moves. |
| Request `interrupted` / `suspended` | **Not settlements.** Both continue on the same request id. The Workstream settles nothing; the task stays claimed and its lease is reclaim's backstop. |
| Detached mode **off** (the flag's second state) | A bare `TaskWorker` value and a board with no `dispatch` behave exactly as today — no new code path, asserted. |
| Legacy `pending` rows on a board that just became detached | Run through the ordinary path; the reconciler derives their envelope (no template needed — §7.6). |
| Reconciler scan | Must resolve the collection ref **per scan**. A ref hydrates its id mirror once and never observes later inserts, so a captured ref sees nothing, permanently and silently. |
| Uniform-worker board / absent assignee | Route to the `uniform` / `floor` coordinate. Detached mode must not convert a floor-routed task into an error, and must not fabricate an assignee a task never had. |
| Prototype-member assignee (`constructor`, `__proto__`, …) | Rejected by the `Object.hasOwn` guard; routes to the floor, or throws `unknown_assignee` without one. |
| Parent session deleted | Refused while **any** descendant exists — not merely a live one. An idle Workstream still leaves a child pointing at a deleted ancestor and, for a session-scoped board, erases the ledger under a live worker. |

### 10. Testing strategy

Feature → TDD, vertical tracer-bullet slices. P3 is the tracer bullet.

**Behaviours to test** (observable, each failing against today's code):

1. A foreground turn **returns while its detached work is still running**, and the work then completes.
2. The detached request appears in the **Workstream's** request list with `source: "taskboard"` and its `taskId` in metadata, and **not** in the parent's.
3. A detached worker's emitted items are **attributed to the task**. *Falsification:* run the same assertion against a router-rooted WorkstreamFlow and confirm it returns nothing — otherwise the test cannot distinguish a working mark from a silent no-op.
4. Two coordinating requests targeting one topic concurrently produce **exactly one Workstream** (needs FIX-1007).
5. Cancelling a task **terminates the in-flight request**, observably — not merely flipping a flag — within one heartbeat interval, with no client attached.
6. A cancel landing **between claim and spawn** prevents the worker from running.
7. The reconciler re-wakes a `pending` task with no live request. **Ordering is the whole assertion: start the sweep *before* admitting the task.** Seeding first passes under a captured-ref implementation that observes nothing.
8. A worker that throws consumes exactly **one** board attempt — not three (asserts the transport's retries are off).
9. A detached board on a request backing, on a filesystem store, or with a `contextSupply: "conversation"` participant is **refused at construction, by name**.
10. Two tenants with identical routing tuples do not read each other's Workstream history.
11. A bare `TaskWorker` value still runs inline, and no existing board needs editing.

**Evidence path (BP-003):** `pnpm test` for the unit-level slices; `fsdev run` over a kitchen-sink flow for the end-to-end criteria (1)–(3) and (5). **Pass criteria** are the eleven behaviours above, each failing before its slice and passing after. The epic's harness gap is real but bounded — `integration-tests/src/scenarios/task-board-drain-containment.test.ts` already proves a board property through full `runAction` composition, and `testFlow`'s seeding is deliberately idempotent so several calls share one store registry, which is the two-executions-over-one-board setup. Extend it; do not budget a spike rebuild.

**Where this design depends on an outcome a blocker has not settled** *(for `cross-spec-review`)*:

1. **FIX-1007's sentinel spelling.** This spec assumes `SessionStore.set` can express "must not exist". FIX-1007's own main decision is tombstones-vs-version-reuse, and `ExpectedVersion` now carries **two meanings for `0`** in one registry — create-if-absent on `ResourceStateStore`, plain version-equality on the scope stores. If FIX-1007 introduces a distinct literal instead of reusing `0`, §7's call site changes spelling only. **If it accepts version reuse on a recreated id, a deleted-and-recreated Workstream can reuse a version** — which interacts with decision 12's occupied-key recovery. Flagged, not assumed.
2. **FIX-1008's result mechanism.** §7.7 picks a canonical tagged result item. If FIX-1008 lands a task-keyed shared resource, §7.7's shape changes and the item-attribution work in §7.4 stops being a settlement precondition (it is still required for criterion 4b). **The projection contract itself is claimed by this spec and the read surface by FIX-1008 — that boundary is the single most likely cross-spec collision.**
3. **FIX-999's surface shape.** This spec assumes a narrow named seam exposing store access and flow-resolution-by-kind. If FIX-999 exposes something narrower, the spawn capability may need a second seam entry. It is also **`Backlog`** while the other three are in spec — it is the least-settled blocker and the one that most affects P3's size.
4. **FIX-1005 and the `{sessionId, requestId}` field.** Decision 5 records this at claim time; FIX-1005 (N61) needs the same field for liveness. **Two issues writing one field is a collision unless coordinated** — the recommendation is that FIX-1005 owns the schema change and this issue consumes it.
5. **FIX-948 and N53.** Decision 12 takes the documented alternative (deterministic failures consume the budget) precisely so this is *not* a blocker. If the owner moves N53 into FIX-948's scope, revisit — it becomes one branch in a routing rule FIX-948 is already rewriting.
