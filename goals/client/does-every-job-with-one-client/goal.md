# client › it does-every-job-with-one-client

**Issue:** FIX-2162
**Outcome:** An app builds one client, from an address or an in-process fetcher and a user, and does every job with it: it opens a session, sends typed turns, reads the resource they wrote, answers a stop for a person, and, after the host is killed mid-run and restarted, finds the run that was cut off and carries it on under its own id without redoing finished work. The same code runs over HTTP and in the host's own process, with no web server.
**Input:** `fixtures/support.json` (the support desk, a singleton: one turn, an approval) and `fixtures/notes.json` (a notes copy addressed by its instance id: three turns, a line of input as the answer). Held-out: each leg grades the transcript, the answer and the held step's label against the fixture, and the notes copy's id comes from the fixture too. Both must pass.
**Signal:** four legs, each transport with each input. The HTTP host is `fsdev serve --config fixtures/fsdev.config.mts` in its own process. The in-process host is `createInProcessFetch` over the same `fixtures/host.mts`, in the client's own process. Both run on a scratch SQLite file with `staleSweepThresholdMs: 2000`. Process 1 (`client.mts`) creates a session, sends the turns, reads the `transcript` resource, sends `approve` (it stops) and `hold` (it counts a run, then waits on a latch). Once the count is written, the host's process group is SIGKILLed. The latch is released, the host restarts on the same file, and process 2 does the rest.
- **a:** two reads of `fsd.requests.interrupted()` list the held request (`a:listed`); `continue()` carries it on under the same id (`a:same-id`) to `completed` (`a:completed`); each of its two steps ran once in all, by the counter file (`a:ran-once`).
- **b:** `flow(address).request(savedId).resume(...)` answers the stop under its id, and the action's output is the fixture's answer (`b:resumed`); both processes read the resource as the fixture's turns (`b:resource`); the session lists every request (`b:turns`); each process called `createClient` once (`b:one-client`, counted by a load-time patch to the client package, so a client built any way is counted); no call reached global `fetch` around the client's fetcher, and the fetcher was used (`b:through-fetcher`); the continued request's stream reports `completed` (`b:stream`). Phase 1's setup is graded too: each turn completed (`p1:turns`), the approval stopped (`p1:stopped`).
- **c:** `node check.mjs --after` exits 0 (`c:census`), and `node check.mjs --control` names every plant (`c:control`).
- **One transport, structurally:** `packages/client/test/one-transport.test.ts`, beside the client, not here.

**Anti-game:** the in-process leg uses the public `createInProcessFetch`, never engine internals or a mocked fetch. The HTTP host is a separate process, killed with SIGKILL, never stopped cleanly. The held request comes back from `interrupted()`, matched by its action and session, and only then compared with the id process 1 saw; the stop is answered through `request(id)` with the id an app would have saved. "Ran once" is a line in a file, not a status. A wait that read a run's status back before it got its turn would pass `a:same-id` and fail `a:completed`, which is how the in-process legs found that `wait()` must also see no live run. The census skips only retained history and its own two paths.
**Model:** n/a. No generator; the path under test is the client, the routes and crash recovery.
**Run:** `pnpm tsx goals/client/does-every-job-with-one-client/run.mts` (unset `FSDEV_DEFAULT_MODEL` first).
**Controls:** each runs the four legs with process 2 changed; leg c grades the tree, which no control changes, so it is skipped under one.
- `GOAL_CONTROL=retry-instead` calls `retry()` instead of `continue()`: must fail `a:same-id` and `a:ran-once`, nothing else.
- `GOAL_CONTROL=two-clients` builds a second client for the recovery reads: must fail `b:one-client`, nothing else.
- `GOAL_CONTROL=stream-off-fetcher` opens the stream with global `fetch`: must fail `b:through-fetcher`. Also red: `b:stream` on the in-process legs only, since a fetch around the fetcher has no web server to reach.
- `node check.mjs --control` plants a named facade, a hand-built router helper, the goals' retired action helper and each removed method, and requires the census to name every one; it also plants a facade built from neutrally named helpers and requires the census to pass it (that one is the structural test's to catch).
