# continue-interrupted-run › it continues-not-restarts

**Issue:** FIX-865
**Outcome:** A DevTool operator can hit Continue on a run that was interrupted mid-flight (the process/host crashed or was swept as stale while the run was suspended awaiting approval). The continued run **resumes the same request** — already-completed work (an early handler's side effect, and a background `.work()` call that finished before the interruption) is restored from the durable log rather than re-executed — and the SAME request id eventually reaches a terminal status. This is the behavior the engine's crash-recovery `/continue` path (and the DevTool's per-run Continue action) is supposed to guarantee, as distinct from a silent restart that redoes the early work.
**Input:** `fixtures/note.json` — `{ note }`, an approver note carried through the second (resolving) continue call and returned by the final step's output. Held-out: the check reads it from the fixture and grades the terminal output against it; swapping the note must still pass a correct implementation.
**Signal:** in a single process, against `@flow-state-dev/engine`'s real `runAction`/`continueRequest` (no HTTP layer, no mocked blocks): (a) exactly one `continuation` item appears in the request's durable item log, with `trigger: "recovery"` and `priorItemCount > 0`; (b) the early handler's run-counter and the completed `.work()` block's run-counter both stay at `1` across both continue calls — proving they were replayed from the log, not re-executed; (c) the request reaches status `"completed"` under the **same** `requestId` it started with, and the final output contains the held-out `note`.
**Anti-game:** a hollow pass would assert only that the request eventually says `"completed"`, or that *some* `continuation` item exists. Both hold even if the continue silently reran the early handler and the background work (a restart wearing a continue's clothes) — completion doesn't prove non-re-execution, and item presence doesn't prove there's exactly one (a `/retry`-style double-continue would emit two, or the fresh-run path would emit zero on a request that only looks continued). The check MUST assert the run-counters directly (a real side effect, not item de-duplication or a status flag) AND assert `continuationItems.length === 1` AND assert the id is unchanged — dropping any one of the three lets a restart-in-disguise pass.
**Model:** n/a — the flow is handlers + a `.work()` background block + `ctx.suspend()`; no generator, no LLM call. The real path under test is the engine's crash-recovery continuation/replay machinery, not model output.
**Run:** `pnpm tsx goals/continue-interrupted-run/continues-not-restarts/run.mts`

> **Why a manufactured interruption, not a real second-process crash.** The sibling goal `goals/suspension/resumes-after-a-cold-restart` proves a *different* guarantee — that a suspension survives an actual process teardown/rebuild over an on-disk store (cross-process durability, FIX-811's territory). This goal proves *continue-not-restart*: that continuing an interrupted request replays completed work instead of redoing it. Those are separable concerns, and the spec (§7) only asks for the latter here. The engine's own crash-recovery test suite (`packages/engine/test/continuation-item.test.ts`, `packages/engine/test/background-work-recovery.test.ts`) proves this exact contract in-process by directly flipping a suspended request's stored status to `"interrupted"` — the same state the stale-request sweeper produces after a real crash — then calling `continueRequest()` with no `resumeContext` (the crash-recovery re-entry path). This goal check uses the identical technique: no process is killed, because the thing under test (replay-vs-rerun of completed blocks, and the continuation item's shape) does not depend on process boundaries, only on `runAction`'s replay mode reading the persisted item log. Using `createInMemoryStores()` (rather than a filesystem store across two processes) keeps the check to the minimum real path that exercises the actual contract, per BP-038.
>
> **Why two `continueRequest()` calls.** The interruption point is a suspending gate (the same shape the engine's own recovery tests use — there is no other reachable way to produce a genuinely mid-flight `interrupted` record without an async external event). The first `continueRequest()` call (no `resumeContext`) is the crash-recovery re-entry: it emits the single `continuation` item, replays the early handler and the background work, and re-runs the gate — which re-suspends (correctly; nobody has resolved it yet), so the record is `suspended`, not terminal. The second `continueRequest()` call supplies a `resumeContext` approving the new suspension — this is the ordinary post-crash operator approval (the same path `/resume` already takes, and the same one `resumes-and-completes-after-approval` exercises), and it drives the SAME request id to `"completed"`. The `continuation` item count and the run-counters are asserted after the FIRST call (the recovery path itself); the terminal-status and same-id assertions are checked after the second.
