# delegation › it recovers from a refused task transition

**Issue:** FIX-950
**Outcome:** A coordinator that asks its board for a status change the task cannot make is told *what the task's status is* and *which calls are available from there*, as an ordinary tool result — and it acts on that guidance instead of stalling, retrying, or narrating past a raw error. What a user notices: the run keeps going and the board ends up in the state the work actually called for.
**Input:** `fixtures/input.json` — the day's intake (requests that arrived already answered, requests that still need doing) plus a held-out `workerSalt` the declared agent must echo. Held-out: swap in different requests or a different salt and a correct implementation still passes; the check reads all three from the fixture and never a literal. Two setup requirements are asserted before any model call — at least one already-answered request (or nothing would ever ask the board to complete a task that was never started) and at least one request that needs doing (or "the run still completed" is vacuous).
**Signal:** One run through the shipped delegation surface. A bound agent-declaring skill installs the board; the coordinator logs each request with `addTask`, then tries to close out the already-answered ones — on tasks that are still `pending`, because nothing has drained the board. All of the following must hold:
- **The refusal happened, as a result.** Some `taskTools` call returns `{ ok: false, error: "illegal_status_transition: …" }`.
- **The message names the way out.** Its "From here you can call …" clause parses to a non-empty list, and every name in it is a real task tool.
- **Recovery, in a strictly later model step.** The coordinator's first `taskTools` call after the rejecting step is one of the names that clause advertised.
- **Applied to the refused task.** The task named in the rejection is not still `pending` at the end of the run.
- **No retry.** The coordinator does not re-issue `completeTask` on that task and get refused again.
- **It still finished.** Non-empty terminal answer, and at least one `completed` task carries the held-out salt, so the request that genuinely needed doing really ran.

**Anti-game:** Four hollow passes are closed.
1. **A run that never provoked the case.** Every assertion above is about a rejection; if none occurred the run FAILS as `ANTI-GAME VOID` rather than passing with nothing to grade. This is the mandatory control, and it is what the pre-fix arm trips when the coordinator happens not to attempt the close-out at all.
2. **A rejection that arrived as a throw.** A `completeTask` that FAILED carrying the raw `illegal status transition` text is reported as its own distinct failure — "the transition WAS refused, but as a THROW" — not folded into the void case. That is the pre-fix shape, and separating it is what makes this check discriminate rather than merely notice.
3. **A sibling scored as the recovery.** A model step's tool calls settle concurrently, so anything emitted *alongside* the rejected call was chosen before the rejection existed. The recovery is read only from a strictly later step. See "The step boundary" below — this is the part of the check most able to produce a false FAIL, so how the boundary is established is spelled out rather than assumed.
4. **The answer planted in the prompt.** The skill body never names `cancelTask` or `blockTask`, and never mentions this error. It states a general workflow rule — a request that needs no work must not be left outstanding on the board, and must not be handed to a worker to get it moving — and points the model at the board's own refusals. The recovery list the check grades against is PARSED OUT OF THE ACTUAL MESSAGE, so if the composer changes which calls it offers, the check follows it instead of grading a stale literal.

**`runBoard` — scored deliberately:** `runBoard` is not one of the eight `taskTools`, and the refusal message never names it (deliberately — `taskTools` also ships standalone, where no drain tool exists). So it can neither satisfy nor violate a criterion about "the calls the message named"; grading it either way would hold the model to a contract the message does not make. It is **skipped** when looking for the recovery, and reported in the verdict log. It cannot pass silently: a coordinator whose only answer to the rejection is to drain makes no advertised call at all, and the check FAILs with "made NO task-tool call after the rejection". It cannot fail silently either — the count is printed on every run.

## The step boundary

`tool_output.toolCall.stepNumber` is the field that answers "which model step chose this call", and it is what this check wants. **It is not populated on this path.** Verified empirically (every `toolCall` carried `callId`, `name`, `alias`, `arguments`, `generatorBlock`, and no `stepNumber`) and traced to its cause: the field is stamped only by the framework-owned per-step loop, which the generator takes only when the resolved model exposes `streamStep`/`generateStep`. A model served through a lazily loaded gateway package — what a bare `createModelResolver()` plus `AI_GATEWAY_API_KEY` produces — is wrapped by `createLazyGeneratorModel`, which exposes only `generate`/`stream`, so the generator falls to the legacy SDK-owned multi-step path and no step index is ever recorded. Making the model step-capable would mean handing the resolver an explicit gateway instance (`createGateway` from `@ai-sdk/gateway`), which `goals/` cannot resolve — only `apps/kitchen-sink` depends on it, which is why the suspension goal copies its harness there.

Rather than *assume* one tool call per step, the step is **reconstructed from dispatch time**. `emitToolOutputAround` stamps `ts: Date.now()` when it builds the `tool_output` item, BEFORE the tool runs — so the timestamp records when the call was dispatched, not how long it took, and a slow tool (`runBoard` takes seconds) cannot smear it. A step's calls are dispatched together in one synchronous burst; the next step's calls cannot be dispatched until a provider round trip completes. Measured: same-burst spread 0–1ms, between-step gap 970–2174ms. The threshold sits at 100ms, three orders of magnitude of headroom on each side, and the real measured gap is printed in the verdict log so the margin stays visible rather than trusted. If `stepNumber` is ever present on every call — a step-capable model — it wins automatically and the reconstruction is not used; the log says which source was in effect.

**Model:** real — openai/gpt-5.4-mini
**Run:** `pnpm tsx goals/delegation/recovers-from-a-refused-task-transition/run.mts`
