# delegation › it recovers from a refused task transition

**Issue:** FIX-950
**Outcome:** A coordinator that asks its board for a status change the task cannot make is told *what the task's status is* and *which calls are available from there*, as an ordinary tool result — and it acts on that guidance instead of stalling, retrying, or narrating past a raw error. What a user notices: the run keeps going and the board ends up in the state the work actually called for.
**Input:** `fixtures/input.json` — the day's intake (requests that arrived already answered, requests that still need doing) plus a held-out `workerSalt` the declared agent must echo. Held-out: swap in different requests or a different salt and a correct implementation still passes; the check reads all three from the fixture and never a literal. Five setup requirements are asserted at module load, before the probe suite and before anything indexes the fixture — at least one already-answered request (or nothing would ever ask the board to complete a task that was never started); at least one request that needs doing (or "the run still completed" is vacuous); no blank open request (or (E)'s containment is vacuous, since every goal contains the empty string); no already-answered request whose text reads as one of the open ones (or criterion (E) could not tell the real work apart from the work that needed none); and the salt absent from the coordinator's own context. Asserted this early on purpose: an invalid intake makes the probes meaningless, so a bad fixture must report `setup invalid` rather than surfacing as a grader failure or an index error.
**Signal:** One run through the shipped delegation surface. A bound agent-declaring skill installs the board; the coordinator logs each request with `addTask`, then tries to close out the already-answered ones — on tasks that are still `pending`, because nothing has drained the board. All of the following must hold:
- **The refusal happened, as a result.** Some `taskTools` call returns `{ ok: false, error: "illegal_status_transition: …" }`.
- **The message names the way out.** Its "From here you can call …" clause parses to a non-empty list, and every name in it is a real task tool.
- **Recovery, in a strictly later model step.** The coordinator's first `taskTools` call after the rejecting step is one of the names that clause advertised.
- **Aimed at the refused task.** Some advertised call in a later step carries `taskId` equal to the task named in the rejection. Read from the call's own arguments — see "Binding the recovery" below for why the final status cannot stand in for this.
- **And it took.** The task named in the rejection is not still `pending` at the end of the run.
- **No retry.** The coordinator does not re-issue `completeTask` on that task and get refused again.
- **It still finished.** Non-empty terminal answer, and at least one `completed` task carries the held-out salt **on a goal that is one of the fixture's open requests**, so the request that genuinely needed doing is the one that really ran.

**Anti-game:** Six hollow passes are closed.
1. **A run that never provoked the case.** Every assertion above is about a rejection; if none occurred the run FAILS as `ANTI-GAME VOID` rather than passing with nothing to grade. This is the mandatory control, and it is what the pre-fix arm trips when the coordinator happens not to attempt the close-out at all.
2. **A rejection that arrived as a throw.** A `completeTask` that FAILED carrying the raw `illegal status transition` text is reported as its own distinct failure — "the transition WAS refused, but as a THROW" — not folded into the void case. That is the pre-fix shape, and separating it is what makes this check discriminate rather than merely notice.
3. **A sibling scored as the recovery.** A model step's tool calls settle concurrently, so anything emitted *alongside* the rejected call was chosen before the rejection existed. The recovery is read only from a strictly later step. See "The step boundary" below — this is the part of the check most able to produce a false FAIL, so how the boundary is established is spelled out rather than assumed.
4. **A recovery on the wrong task, with the drain covering for it.** The coordinator makes a genuinely advertised call in a later step but aims it at a *different* pending task, then drains; `runBoard` claims and completes the refused task, so it ends non-`pending` on its own. This satisfies every other criterion. Closed by reading the recovery's `taskId` argument rather than inferring it from the final status — see "Binding the recovery".
5. **The work done on the wrong request.** The coordinator recovers from the refusal cleanly but runs an *already-answered* request on a worker — which the skill says must never happen — and cancels the one that actually needed doing. A salted `completed` task exists, so a salt check that only asks "did some worker run" passes it. Closed by requiring the salted completion's `goal` to be one of the fixture's open requests — see "Binding the real work".
6. **The answer planted in the prompt.** The skill body never names `cancelTask` or `blockTask`, and never mentions this error. It states a general workflow rule — a request that needs no work must not be left outstanding on the board, and must not be handed to a worker to get it moving — and points the model at the board's own refusals. The recovery list the check grades against is PARSED OUT OF THE ACTUAL MESSAGE, so if the composer changes which calls it offers, the check follows it instead of grading a stale literal.

**`runBoard` — scored deliberately:** `runBoard` is not one of the eight `taskTools`, and the refusal message never names it (deliberately — `taskTools` also ships standalone, where no drain tool exists). So it can neither satisfy nor violate a criterion about "the calls the message named"; grading it either way would hold the model to a contract the message does not make. It is **skipped** when looking for the recovery, and reported in the verdict log. It cannot pass silently: a coordinator whose only answer to the rejection is to drain makes no advertised call at all, and the check FAILs with "made NO task-tool call after the rejection". It cannot fail silently either — the count is printed on every run.

## Binding the recovery

"The refused task was actually dealt with" is one question that needs **two** assertions, because either alone is satisfiable without it.

- **Aimed (C1)** — an advertised call in a later step carries `taskId` equal to the refused task's. Read from the call's own arguments.
- **Took (C2)** — that task is not still `pending` at the end of the run. Read from the final task state.

The tempting simplification is to keep only C2 and call it "the task was dealt with". That is a **proxy the substrate can satisfy on its own**: `runBoard` claims and completes whatever is still pending, so a drain moves the refused task out of `pending` with no recovery call ever naming it. The fixture deliberately holds several pending tasks, so a coordinator can cancel the *wrong* one and still leave a clean-looking board. C1 is the only thing standing between that run and a false PASS.

C2 is not made redundant by C1 either: an advertised call aimed at the right task can fail to land (a second refusal, a CAS conflict). C1 reads intent from the arguments and cannot see that; the final state can. Both stay.

C1 scans **every** later task-tool call rather than just the first: a coordinator that cancels another task and *then* the refused one has still bound its recovery to it.

This was originally guarded by C2 alone. The hazard had been identified correctly and the code comment named it precisely — the guard chosen for it was simply a property the drain also satisfies. Every advertisable tool (`blockTask`/`cancelTask`/`completeTask`/`failTask`) takes `taskId`, so the binding is readable for any list the composer emits.

## Binding the real work

The salt proves a worker turn happened. It does not say *which* request that turn served, and that is the thing criterion (E) is there to establish — recovering from the refusal is not the outcome if the recovery came at the cost of the work.

The fixture supplies both kinds of request on purpose, and the skill draws a hard line between them: an already-answered one must never be handed to a worker. So the exact inversion of the intended behaviour — work a settled request, drop the open one — still leaves a `completed` task carrying the salt, and a salt-only check PASSES it. The task's `goal` is what tells them apart, and it comes off the change stream the run already reads.

The comparison is against `fx.openRequests`, never a literal, so swapping the intake swaps what counts as real work. Goals are matched lowercased, whitespace-collapsed and with trailing punctuation dropped, and containment runs **one way**: the goal must contain the *whole* open request. The skill has the coordinator log each request's text as the goal, so the two shapes worth tolerating are a goal that quotes the request and adds to it, and one that drops its trailing period — normalization plus that direction cover both.

The reverse direction is deliberately not accepted. `open.includes(goal)` matches any fragment, so a task goal of `"Draft"` satisfies (E) while `"Draft the maintenance window notice for Friday night."` sits cancelled — the same false pass (E) exists to close, put back inside the guard meant to close it. The first cut of this check had that direction, and it took a probe to see it: driving the grader with a fragment-goal run returned **zero** failures. The `goal !== ""` guard that cut also needed is the tell, not a fix — `"anything".includes("")` is true, which is a symptom of matching fragments at all. One-way containment removes both.

A tolerant matcher still depends on the intake's two request kinds being textually distinct, so that distinctness is a setup requirement rather than a hope: an intake where an already-answered request reads as an open one, or where an open request is blank, FAILs as `setup invalid` before any model call.

This is a narrowing, not a hole closed. Unlike the C1 defect below, the substrate could never satisfy the old assertion on its own — a worker still had to run and echo a token the coordinator's context never contains. What it admitted was one specific wrong-routing run, not an arbitrary one.

## The probe suite

`grade` is a pure function of one observed run, and a deterministic probe suite drives it with synthetic runs before any model call — printed as `probes: N/M` on every run. It exists because a criterion that has never been *seen* to fail is not evidence that it works; the C2-only guard passed every real run it was ever shown.

Six probes: a correct run grades clean (the positive control — without it, a C1 or an (E) that rejected everything would look like a working guard); the wrong-task-plus-drain run FAILs on C1; an aimed-but-refused-again run FAILs on C2 (so neither check subsumes the other); a recovery that lands on the refused task only after touching another one still passes C1; the inverted-routing run — salt on an already-answered request, the open one cancelled — FAILs on (E) with **exactly one** failure; and the same inversion with the salted goal cut down to a fragment of the open request also FAILs on (E), which is what holds the matcher's direction in place. A probe failure is reported as `PROBE FAILED (grader bug, not a substrate verdict)`, so a grader regression can never be read as a verdict about the framework.

Exactly one is the load-bearing number in both falsification probes. It says the pre-change grader returned **zero** failures on that run and would have PASSED it, so the false positive is confirmed rather than inferred.

## The step boundary

`tool_output.toolCall.stepNumber` is the field that answers "which model step chose this call", and it is what this check wants. **It is not populated on this path.** Verified empirically (every `toolCall` carried `callId`, `name`, `alias`, `arguments`, `generatorBlock`, and no `stepNumber`) and traced to its cause: the field is stamped only by the framework-owned per-step loop, which the generator takes only when the resolved model exposes `streamStep`/`generateStep`. A model served through a lazily loaded gateway package — what a bare `createModelResolver()` plus `AI_GATEWAY_API_KEY` produces — is wrapped by `createLazyGeneratorModel`, which exposes only `generate`/`stream`, so the generator falls to the legacy SDK-owned multi-step path and no step index is ever recorded. Making the model step-capable would mean handing the resolver an explicit gateway instance (`createGateway` from `@ai-sdk/gateway`), which `goals/` cannot resolve — only `apps/kitchen-sink` depends on it, which is why the suspension goal copies its harness there.

Rather than *assume* one tool call per step, the step is **reconstructed from dispatch time**. `emitToolOutputAround` stamps `ts: Date.now()` when it builds the `tool_output` item, BEFORE the tool runs — so the timestamp records when the call was dispatched, not how long it took, and a slow tool (`runBoard` takes seconds) cannot smear it. A step's calls are dispatched together in one synchronous burst; the next step's calls cannot be dispatched until a provider round trip completes. Measured: same-burst spread 0–1ms, between-step gap 970–2174ms. The threshold sits at 100ms, three orders of magnitude of headroom on each side, and the real measured gap is printed in the verdict log so the margin stays visible rather than trusted. If `stepNumber` is ever present on every call — a step-capable model — it wins automatically and the reconstruction is not used; the log says which source was in effect.
