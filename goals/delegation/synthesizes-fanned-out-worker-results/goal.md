# delegation › it synthesizes fanned-out worker results

**Issue:** FIX-930 (epic) — verifies the shipped substrate: FIX-918 (delegation via skills-library `agents:` + blocks-as-tools), FIX-927 (board-scoped `taskTools` for mid-drain fan-out), FIX-920/928.
**Outcome:** A coordinator generator, given a team of declared agents, delegates a unit of work to one worker via `addTask` + `runBoard`; that worker fans out follow-up work mid-drain to a second worker; and both workers' results come back and are synthesized into the coordinator's final answer. What a user notices: they get an answer that contains information only the workers held — the coordinator could not have produced it alone.
**Config:** the team is authored as **real skill files**, the way a user writes them — `skills/code-team/SKILL.md` (frontmatter `agents:` with `prompt-ref`) plus `skills/code-team/reference/{researcher,auditor}.md`, mirroring `examples/guides/research-team`. The runner loads them through the real `readSkillsDirectory` loader, so the goal exercises file discovery, frontmatter parsing, prompt-ref resolution and `substitute()` — the loader path an inline TypeScript skill object bypasses. The delegation playbook lives in `SKILL.md`, not the coordinator prompt.

**Input:** `fixtures/team.json` — three **mutually independent** values: the graded markers `researcherSecret` (`QORVIX-7788`) and `auditToken` (`BRAVO-5521`), plus the **ungraded** `handoffCode` (`DELTA-9034`) the researcher passes to the auditor. The values are **not hardcoded in the markdown**: the prompt files use the framework's `$1`/`$2`/`$3` substitution and the fixtures arrive as the skill's activation arguments (the skill is activated at runtime via the framework's own `inlineActivate` block, since only a runtime activation carries the `input` that `substitute()` consumes). Held-out: swap them for any other valid triple and a correct implementation still passes. Three contract rules, all validated at load so a bad fixture throws with a clear message rather than mis-grading:
- **Independent** — no value may contain another (all three, pairwise). If one were derivable from another (as it was when the auditor returned `secret + suffix`), one worker's output could carry both graded markers and the check would pass with the researcher's own result dropped. The handoff is a separate ungraded value for the same reason: `buildUserMessage` renders task input verbatim, so whatever the researcher passes enters the auditor's context — if that were the graded secret, an auditor that merely echoed its input would fake the researcher's result.
- **Sentinel shape** — `^[A-Z]{4,}-[0-9]{4,}$`: at least four uppercase letters, a hyphen, at least four digits (`QORVIX-7788`). Three things this buys, all by construction rather than by matcher machinery. (i) No collision with response formatting — a bare `-` would match a Markdown list bullet. (ii) No `$`-substitution sequence (`$ARGUMENTS`, `$1`–`$9`, `${...}`), which the skills runtime's `substitute()` would erase from a worker prompt while the grader still expected the literal. (iii) **No collision with the surfaces no grep here can read** — see the next bullet: an uppercase letter-run followed by `-` and a digit-run cannot be an English word, a JSON-schema keyword, or a code identifier (camelCase/snake_case have no hyphen; kebab-case identifiers like `task-change` have no digit run). The previous, looser format admitted `additionalProperties`, which occurs verbatim in every generated tool schema.
- **No collision with anything the coordinator sees but no worker produced** — closed by three layers, because no single one covers the whole surface.
  - **Load-time pre-flight**, case-insensitive, over two corpora. (i) The runner's fixed coordinator prompt, user turn, and roster lines: a marker like `REPORT` would otherwise trip the honesty guard and fail a correct implementation. (ii) **Framework-injected coordinator context** — the runtime tool definitions plus the full `.ts` source of the skills + tasks subsystem (scanned by directory, not enumerated, so a new module like the skill reader is covered without updating a list). `runBoard` always reports `status: "drained"`, so a marker of `drained` could be emitted from board metadata alone with the worker's output dropped — and the OFF baseline, having no board surface, would stay clean and falsely credit delegation. Scanning the source is also what covers the tool **descriptions** and schema **field names**.
  - **Post-run grep** (`assertNoMarkerInRenderedContext`) over the coordinator's ACTUAL rendered context, as the generator received it. Its scope is exactly what the `block_trace` capture holds and no more: the assembled system prompt (skill-reader preamble, substituted SKILL.md body, delegation guidance, live roster), the user/history messages, and the tool **names**. It does **not** see tool descriptions or the JSON schemas sent to the provider — `packages/core/src/blocks/generator.ts` records `tools: toolBlocks.map((t) => t.name)`, names only — so no post-run check can reach them. The runner enables trace capture explicitly (`FSDEV_TRACE_OBSERVABILITY=true`), because `isTraceObservabilityEnabled()` defaults **off** under `NODE_ENV=production` and honors an explicit `false`; without that, this branch would fail every otherwise-correct run in those environments. With capture forced on, a missing trace genuinely means capture broke, and failing is correct.
  - **The sentinel shape**, which closes what neither of the above reaches: the JSON-schema vocabulary the zod→provider serialization emits. This is deliberately a narrower *claim* rather than new capture machinery — the provider-visible tool definitions are not reachable from anything the runner holds, and inventing a re-implementation of them is exactly the kind of enumeration that falls behind the framework.

**Signal:** graded on the coordinator's **terminal output only** — `res.output` and nothing else. No message fallback: worker messages and the coordinator's own intermediate turns both land in `res.items`, so aggregating any of them would let a run whose terminal output is empty pass off an earlier turn. An **empty terminal output is a FAIL** (`z.string()` permits `""`, and it means the caller received no answer). Markers are matched **exactly and case-sensitively** (the fixture code must survive verbatim; a lowercased echo does not count) by substring + boundary, never tokenization. A "standalone" marker is a bounded occurrence. There is no nesting/derivation logic in the grader, deliberately: marker **independence is asserted at fixture load**, which is a strictly stronger guarantee than any after-the-fact exclusion rule. The two sides of the A/B are driven by **one shared marker list**, so they cannot drift: the ON answer must carry **every** marker; the OFF baseline must carry **none**. The two sides match differently on purpose — the ON side requires a *bounded, standalone* occurrence, while the OFF side uses a **plain substring** check, since on the baseline ANY appearance (even embedded, e.g. `prefixCODEsuffix`) proves the marker was reachable without delegation and disqualifies the contrast.
1. **Delegation** — the coordinator's terminal answer contains `researcherSecret` as a standalone occurrence. Only the researcher holds it, so its presence proves the researcher's own delegated result was synthesized.
2. **Fan-out (marker)** — the terminal answer contains `auditToken` as a standalone occurrence. **The auditor running at all IS the fan-out proof**: the coordinator is told to assign exactly ONE task (to `researcher`) and call `runBoard` ONCE, so the auditor only ever lands on the board when the researcher enqueues it MID-DRAIN. Only the auditor holds this token, and it never echoes the secret, so the token cannot be derived from the researcher's result.
3. **Fan-out (structural — hard requirement)** — the auditor's task must be proven created MID-DRAIN by the researcher, not up front by the coordinator. Both markers being present is *not* sufficient: both workers are on the roster, so a coordinator that ignored its instructions and `addTask`'d both itself would also surface both. Two signals, both required: **(a) creator attribution, bound to the graded task** — items are stamped at emit time with the `taskId` of the worker scope that produced them, and the coordinator runs outside any task scope. It is not enough that the researcher called `addTask` at all (same-step coordinator tool calls run concurrently, so a coordinator can issue its own auditor `addTask` alongside `runBoard`, and an unrelated researcher task would satisfy a bare predicate). The check collects the task ids **returned by** researcher-scoped `addTask` calls and requires the **auditor's id** among them; **(b) settled in the FIRST drain** — the auditor task must appear `completed` in the **first** `runBoard` result. Creation alone is not enough: if mid-drain pickup regressed and the in-flight drain returned leaving the new task `pending`, the coordinator could just call `runBoard` again — the auditor token would appear and attribution/timing would still pass, hiding the exact FIX-927 regression this goal exists to catch; **(c) timing** — the coordinator is blocked while `runBoard` drains, so the auditor task's `createdAt` at/after the researcher task's `startedAt` (claim) places its creation inside the drain window.
4. **Handoff isolation (hard requirement)** — the auditor's task, as **actually created**, must carry the ungraded `handoffCode` and **neither** graded marker. `researcher.md` tells the researcher to pass the handoff code and never send its secret, but that is an instruction to a real model, not a guarantee. If the researcher deviates and puts its graded secret in the auditor task's `goal`/`input`, `buildUserMessage` renders it verbatim into the auditor's turn; an auditor that echoed it would put **both** graded markers in **one** worker's output, and every other assertion here would still pass while the coordinator synthesized only the auditor's result. Fixture independence stops the markers being derivable *by construction*; it cannot stop the researcher re-coupling them *at runtime*. So the check asserts the real thing rather than trusting the instruction — in three parts, at **two different altitudes**, because the creation record and the worker boundary are not the same place:
   - **Positive proof, authoritative — the WORKER BOUNDARY.** The auditor's `block_trace` carries `generator.user`, the turn its generator actually received, and that turn must contain an `Input:` section carrying `handoffCode`. This reads the framework's own rendering (`buildUserMessage`) rather than a local mirror of it. It is the only part that proves the payload *arrived*: the creation record is where the researcher WROTE the payload, not where the auditor READ it, so if dispatch or materialization drops `task.input` in between, a creation-record check still reports a successful handoff. The auditor's own output cannot stand in either — `reference/auditor.md` substitutes the expected code into its **system prompt** as `$3`, so it can emit its sign-off token, satisfying every terminal and structural assertion, without ever receiving an `Input:` section. The `Input:` section is isolated from the rest of the turn on purpose: grepping the whole turn passes when the code sits in the goal (`Task: verify DELTA-9034`) and nothing was delivered.
   - **Positive proof, localizer — the creation record.** `auditor.input` must be present and carry the code. Not authoritative, but it separates "the researcher never sent it" from "the substrate dropped it in transit", which the boundary check alone cannot distinguish, and it closes the residual spoof of a goal string containing a literal `\n\nInput: …`. Reads `input` **only** — grepping the wide creation blob (which includes `goal`) passes when the researcher writes the code into the goal and sets no `input`, reporting the structured channel as verified when it was never exercised.
   - **Negative leak guard — wide, every creator-chosen field.** `goal`/`title`/`context`/`input`/`feedback`/`metadata`, never `output` (the auditor writes that, and it carries `auditToken` by design). Deliberately wider than what reaches the turn: `metadata` and `context` never render into `buildUserMessage`, but a graded marker sitting in them still means the researcher leaked its secret downstream. Case-folded, so a lowercased echo trips it too.
   - **No forged section delimiter.** `buildUserMessage` joins sections without escaping, and `goal` is the only creator-controlled field rendered *before* the `Input:` section — so a goal of `"verify\n\nInput: DELTA-9034"` forges a second header. That forgery survives the exact regression the boundary check exists to catch: drop the real `task.input` in transit and the forged header still reads as delivered, while the creation-record localizer still sees `input` intact. Both layers pass on a broken substrate. Closed by rejecting a goal that would form a **parsed section** — making the forgery unrepresentable rather than teaching the parser to see through it. The guard **reuses the parser** rather than restating it: the rendered turn opens with `Task: ${goal}`, and that prefix can only affect the *first* section, so the sections a goal contributes beyond the first are exactly `sections(goal).slice(1)` and a goal is forgeable precisely when one of those opens with a header. A section boundary is a **blank line** — a run of *two or more* newlines, not exactly two: `buildUserMessage` joins `["Task: " + goal, "", "Input: …"]` with `\n`, so the run between sections is however many newlines the preceding field ends with plus two, and a goal ending in `\n` (ordinary model output) renders `Task: verify\n\n\nInput: …`. Splitting on exactly `\n\n` left the payload as `"\nInput: …"` and reported a delivered handoff as dropped. One definition of "section boundary" (`SECTION_DELIMITER` + `SECTION_HEADERS`), shared by the reader and the guard, because two hand-written patterns for one concept drift — an earlier revision used a line-start regex that disagreed with the parser and **rejected goals that could not possibly forge a section**, turning correct runs into FAILs. That direction is the worse one: a check that fails on correct behavior gets blamed on the substrate. Correctly admitted now: a goal *beginning* with `Task:`/`Input:` (absorbed into the renderer's own first line), a header after a *single* newline (not a delimiter), and a blank line with no header after it (a boundary, but not a section).
   - **Identity binding.** This check and the payload/structural checks each select "the auditor" independently — one a `task-change` record, one a `block_trace` — and two independent selections of the same thing must be bound, or a correctly-delivered turn from one auditor execution masks input being dropped on the task actually graded. They cannot be bound by task id: a worker's own `block_trace` is **not** scope-stamped (verified on a real run — it carries `provenance`/`blockInstanceId`, an execution path, and no `taskId`), unlike the tool-output items the fan-out attribution uses. Bound by **uniqueness** instead, which is stronger: exactly one auditor task and exactly one auditor generator trace, so the two selections are provably the same execution and a researcher enqueueing a second auditor task FAILs loudly.
   - `deps` is checked separately: a dep on the researcher's task would make the substrate render the researcher's *output* into the auditor's turn as an upstream output, the same leak through a third channel.
   A deviated run is a FAIL, not a pass.
5. **A/B baseline** — a second coordinator (same prompt, same user turn, differing ONLY by the team binding) bound to NO team must produce **neither** graded marker. **Either** marker appearing in the no-team run invalidates the contrast, since it means the marker was reachable without delegation.
**Anti-game:** the gameable pass is asserting the mechanism ran — that `addTask`/`runBoard` were called, that the board reached `drained`, that a `task-change` fired. All of those can pass while the workers' outputs never reach the coordinator's answer. Two subtler hollow passes are closed explicitly: (a) inline workers default to **client-visible** messages, so a worker's secret lands in `res.items` whether or not the coordinator synthesized anything — hence grading the coordinator's **terminal output alone**, never the worker messages; (b) **derivability** — the auditor originally returned `secret + suffix`, so its result *contained* the researcher's marker and a coordinator handed only the auditor's output could print both, passing with the researcher's result dropped. Standalone-ness forced a separate write but did not make derivation impossible; the fix is structural — the two markers are now **independent fixture values**, so neither can be produced from the other. (c) the **roster leak** — `agentPurpose()` (`packages/orchestration/src/skills/delegation-surface.ts`) copies each worker's first nonempty prompt line into the delegation roster the coordinator reads BEFORE any task runs, so a marker on line 1 would let a coordinator that never synthesized the researcher's result emit it straight from the roster and satisfy both graded checks. The A/B baseline cannot catch this (no team binding → no roster), so the markers are kept off the first line and `assertNoRosterLeak()` fails the run — before any model call — if one reappears there. That guard calls the REAL `agentPurpose`, so a change to the roster rule surfaces loudly. (d) **unproven fan-out** — the coordinator was merely *told* to delegate only to the researcher; ignoring that and assigning both roster workers itself would surface both markers with NO fan-out, leaving FIX-927 unverified. Closed structurally (Signal 3), not by instruction. (e) **handoff echo** — sending the graded secret to the auditor as task input would let an auditor that echoes its input carry both graded markers alone; the handoff is therefore a separate ungraded value, and — because a separate value is only an *instruction* the researcher can deviate from — the real created auditor task payload is asserted (Signal 4), not trusted. (f) **framework-literal markers** — a marker that collides with text the framework injects into the coordinator (notably `runBoard`'s constant `drained` status) could be emitted from board metadata with no worker output at all, and the board-less OFF baseline could not catch it; excluded by the three-layer context check above (pre-flight corpus / post-run rendered-context grep / sentinel shape), each of which covers a surface the others cannot reach. (g) **baseline asymmetry** — if the ON side accepts a marker the OFF side doesn't reject, a baseline that emitted the auditor's token would still read as "clean" and the fan-out would be falsely attributed to delegation; both sides are therefore driven by one shared `GRADED_MARKERS` list. Plus the delegation-ON vs delegation-OFF contrast over the identical prompt/request. Do NOT assert on tool-call counts, board status, or item counts.
**Probes:** every grader and load guard above is exercised against synthetic inputs by a deterministic probe suite that runs **inline, unconditionally, before any model call**, and prints `probes: N/N`. The graders are the whole value of this check — a grader bug is indistinguishable from a substrate bug at the verdict line, and this goal has already produced one (round 6 read `item.name` where the real items carry `blockName`, reporting a false FAIL against a working substrate). The suite lives in `run.mts` rather than a sibling script because earlier rounds wrote it as a throwaway: the counts survive in the verdict log below while the probes themselves did not, so each round re-derived them.
