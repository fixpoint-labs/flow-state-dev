# devtool-workforce-visibility › it works a task from its row

**Issue:** FIX-1629 (absorbs FIX-1523). The spec's goal check (VG). Converted by FIX-1792 P3: the lab's mailbox and its board are gone, and every row is on the planner's own conversation's board.

**Outcome:** A developer opens any task in the DevTool's Tasks tab, reads its whole record in place, changes its state from the same row through the flow's own actions, and sees the result on the row without a reload. On a laptop-width window a row waiting on a person shows its status and the question it waits on before anything is opened.

**Input:** The `multi-seat-collab` hire (`packages/shift-manager/test/fixtures/multi-worker-collab/`), with no model, and `fixtures/input.json`: a piece of work with a question only a person can settle, the answer, a spare row to file on the planner's conversation, and a cancel reason. Both are **held out**. The desk's owning worker and the planner come off the tree at run time, and every row is found by the id the ledger gave it. A different question, answer, or spare row must pass too.

**Signal:** Chromium on the shipped DevTool bundle, rebuilt at the start of the run, at a **1280×800** window. The lab's driver files the piece on the planner's conversation's board over HTTP, for the delegate the app routes its desk to, so the builder holds it on a question by design. After that, every change this goal grades is made from a row on screen. Every failure line names its leg.

- **read.** First the positive record: the ledger holds the row running with an open question (FIX-2131 retired `parked`), in a known run. The run, the task session the board opened for the row, is opened from the navigator (kind, then the worker copy it is listed under, then the session) and its Tasks tab is read by task id. Collapsed, the row is not open, its status slot reads `in_progress`, and its reason slot reads the question the ledger holds it on, with at least 40px of width and one line of height in view after every clipping ancestor and the window. A clamped reason carries the whole text on its title. Opened in place in that task session, every field the ledger holds is shown and agrees with the ledger: a field the row has a label for under that label, and any other under its own raw key. A carried empty list reads `none`, and `maxAttempts` is the Attempts field's limit. Only the fields the ledger never sends to a client (`SERVER_ONLY_TASK_FIELDS`) are left out, and they are noted. Nothing in the row ends past the pane's right edge, and the pane does not scroll sideways.
- **answer.** On the planner's conversation, the same row, opened, offers the board's `updateTask_tasks` action. Its form carries the row's task id, locked. The check fills the question's id and the answer as its message, and runs it, leaving every other field as the form starts it. The row reports `ok`, the ledger row's question is answered and the row finishes, and the row on screen moves on too. If the row there does not yet show the ledger's final status, the check reopens the task session the row ran in from the navigator and requires its row to show it.
- **tool.** The driver files a spare row for nobody, held, through the planner's conversation's `createTask_tasks`, so the board keeps it waiting and nothing runs it. On the planner's conversation its row, opened, offers the board's `updateTask_tasks` tool. Run from the row with `status: cancelled`, it reports `ok`, the ledger row is `cancelled`, and the row on screen reads `cancelled`.
- **refuse.** The same tool, run again on that now-cancelled row, reports a refusal on the row in the tool's own words, and the ledger row is byte-for-byte unchanged. Graded only when the tool leg's row opened. If it never did, that is the tool leg's failure, and the run notes refuse as ungraded.
- **reload.** The page loads once. Any further main-frame navigation fails.

**Anti-game:** The hollow passes are:

- reading the ledger for what the screen should show;
- finding a row by its text;
- typing a URL, or reloading so a stale screen is replaced;
- a refusal that reads as success;
- an action that ran somewhere other than the row.

So the check never reads the store to decide what is on screen. The ledger is only the thing the screen is graded against. Rows are found by `data-task-id`. The page loads once, and navigation is counted. A refusal must be read as `refused` off the row, with the ledger unchanged. Every action is picked and run from the row's own Actions strip, with the task id already locked in the form. The answer leg's follow-up is the navigator, not a URL.

**Model:** n/a. The worker bodies are deterministic.

**Run:** `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers pnpm tsx goals/devtool-workforce-visibility/works-a-task-from-its-row/run.mts`. The run builds the DevTool bundle first. On a clean checkout, run `pnpm --filter @flow-state-dev/devtool build` once before it.

**Controls:** Each control must FAIL at exactly the legs named.

- `mailbox-actions-off` is retired (below). Its red state is now produced by hand: the planner's flow with `updateTask_tasks` taken out of its task actions. Since FIX-2131 the answer runs through `updateTask_tasks` too, so it must fail **answer, tool and refuse**; read stays green, because the row still opens.
- **Today's `main`** (not a flag): the DevTool source from `origin/main`, with this branch's files under `packages/devtool/src` that main does not have removed, rebuilt, and the same command run. Must fail **read, answer and tool**. The rows are a table with no `data-task-id` and no Actions strip. Refuse reports itself ungraded, because its row never opened. Only the DevTool is taken from `main`: `main`'s mailbox binder refuses the lab's `boardActions` key, so a whole-`main` server would not start and would grade nothing.

## What changed when the lab lost its mailbox, and why (BR-24)

- *The answer is the seat's own `answer` action, on the seat's session.* No worker has an answer action: a person answers a held row's question through the board's `updateTask_tasks`, naming the question, on the conversation that keeps the board (it was `answerTask_tasks` before FIX-2131). The answer leg runs it from the planner's conversation's row.
- *The answer leg follows the row's own dispatch-run link to the run that finished it.* The DevTool links a row to its run by decoding a mailbox board's run session key, and does not decode a conversation board's, so the row shows no link. The answer leg reopens that task session from the navigator; that a row names the run working it is graded by `goals/task-run-link/it-names-the-run-working-each-task` (legs **browser** and **stream**).
- *The open row is read in the run.* A Tasks tab is a fold over its own session's items. Before FIX-2131 a conversation board's last write to a parked row was its notice to the planner, emitted into the planner's conversation, so the open row was read there. A question writes no notice: the row's last write is the ask, made in the task session, so the open row is read in the run again, where it is the ledger's row.
- *The spare row is filed through the mailbox's `fileTask`, and the tool is `cancelTask_<board>` on the mailbox's session.* Both are the planner's conversation's: `createTask_tasks` for a row for nobody, held, and `updateTask_tasks` from its row.
- *`GOAL_CONTROL=mailbox-actions-off`.* It retires with the mailbox's board actions. That a worker has the task actions only while one of its `delegates:` takes tasks is proved by `goals/manager-queue-lab/it-stands-the-team-and-its-board-up-from-files` (its twin arm). This goal's tool and refuse legs are shown able to go red by the hand mutation above.
