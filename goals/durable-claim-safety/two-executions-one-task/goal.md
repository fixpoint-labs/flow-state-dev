# durable-claim-safety › it two-executions-one-task

**Issue:** FIX-981
**Outcome:** Two things running at the same time over one shared, durable to-do list cannot both pick up the same job, and neither can record a result against a job it isn't holding. Before this, a worker that had been handed job A could record a finished result onto job B and the substrate accepted it — so one job got settled by someone who never worked on it, and the job that worker actually held was left running with nobody to finish it. Nothing errored; the only symptom was duplicated model spend and a task that quietly never completed.
**Input:** the four values in `fixtures/input.json` — the two task ids and the two output payloads. Held-out: every assertion is phrased against those values rather than against literals, so renaming the tasks or changing the payloads still grades a correct implementation correctly and still fails a broken one.
**Signal:** three real `runAction` executions over one SQLite file at one session. Two race to claim the contended task; exactly one may win. A third execution then claims the *other* task and presents its own ownership token against the contended one — that write must be **declined**. The database is then **closed and reopened**, and the contended task's durable row must carry the holder's output at status `completed`, while the third execution's own task is untouched at `in_progress`.
**Anti-game:** a hollow pass would (a) assert only that the two settlements don't both land, which is satisfied by fencing settlement while leaving `claim` open — the task still runs twice, so exclusivity is asserted separately at the claim; (b) build the racers lazily so the second claims after the first committed, turning the race into a sequence that last-write-wins also survives — both are launched and both reach a barrier before either claims; (c) read the verdict from a participating execution's `TaskCollectionRef`, whose per-execution cache can look correct while the persisted row disagrees — hence the reopened connection; (d) let the two tasks sit on *different* attempt numbers, which lets today's counter-only guard refuse the cross-task write for a reason unrelated to ownership, so the check asserts the collision as a precondition and reports "cannot discriminate" if it does not hold; or (e) start the third execution *before* the contended task is claimed, in which case its stale view of that task refuses the write as an illegal transition — the right outcome by the wrong route, which would pass without proving anything. The third execution is therefore started only after the claim has been decided.

> One further trap, learned the hard way while writing this: a custom `eligibility` predicate **replaces** the substrate's default rather than narrowing it. Narrowing to a task id alone — without `status === "pending"` — removes the readiness condition the claim's own re-check consults inside the atomic write, and the board then hands the same task to both racers. That is a property of the check's setup, not of the code under test, and getting it wrong makes the exclusivity assertion fail for a reason that has nothing to do with the milestone.

**Model:** n/a — task ownership and durable persistence; no generator anywhere in the flow.
**Run:** `pnpm tsx goals/durable-claim-safety/two-executions-one-task/run.mts`
