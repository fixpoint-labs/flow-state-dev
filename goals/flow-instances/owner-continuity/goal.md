# flow-instances › it keeps saved work with the instance that created it

**Issue:** FIX-1322 (integration owner) and FIX-1321 (registry cardinality), landed together
**Outcome:** An operator runs two copies of one flow definition on one server, each with its own configuration. Work addressed to copy A runs A's configuration, is saved as A's, and is still A's after the server restarts, whichever copies are registered afterwards and in whatever order. Addressing that saved session through copy B refuses before anything runs or changes. A copy's bare kind is not an address. The same holds when the work arrives through the CLI and through a queue worker, not only over HTTP.
**Input:** `fixtures/input.json` — two instance ids and the marker each copy writes into session state. Held-out: the markers are read from the fixture and graded against what the stores hold afterwards; swapping ids or markers must still pass a correct implementation.
**Signal:** against the real HTTP router (`createFlowApiRouter`) over on-disk SQLite stores: (a) `POST /api/flows/<A>/<session>/actions/run` leaves `session.state.marker === A.marker` and stamps `flowId === A.id` on the session and the request; `POST …/<B>/…` likewise for B; `POST /api/flows/review/…` (the bare kind) is `404`. (b) After closing the stores, reopening the same file and building a fresh host with B removed and A registered alone, re-entering A's session through A is `202` and the marker is still A's; a host that knows only B answers `409 wrong-instance-session` for that session, and the session's `flowId` and marker are unchanged. (c) `GET /api/flows/sessions/<A's session>/state` is `200` on the owner's host. (d) Through the real CLI (`fsdev run <id> run --flow-dir …`, the directory-discovery path): both ids run their own marker; the bare kind is not found and the error lists both ids; re-entering A's session through B exits non-zero with no marker change. (e) Through the real BullMQ job processor (`createFlowJobProcessor` over the same registry and stores, the only part of the queue path that resolves a flow): a job addressed to A writes A's marker; a job addressed to B naming A's session fails as `UnrecoverableError` with A's session untouched.
**Anti-game:** a hollow pass would assert only that requests complete, or only that a refusal message appears. Both hold if the bare kind silently picks the first registered copy, or if B's refusal happens *after* B already ran (a refusal that follows an effect). The check MUST read the marker and `flowId` from the stores after every refusal and assert they are unchanged; MUST re-order/remove registrations across the restart so a first-registered fallback cannot pass; and MUST drive the CLI and the queue processor with the same ids, not a mock dispatcher. Grading `flowKind` alone proves nothing, since every copy shares it.
**Model:** n/a — handlers only; the property under test is identity and persistence, not model output.
**Run:** `pnpm tsx goals/flow-instances/owner-continuity/run.mts`

> **What the BullMQ leg covers, and what it does not.** No Redis is assumed, so the queue transport itself is not exercised; the job processor the worker runs is, with a real `Job`-shaped payload carrying the instance address exactly as the dispatcher enqueues it. That is the whole of the worker's flow resolution and admission. A live-Redis round trip adds the transport, which carries the address unchanged.
