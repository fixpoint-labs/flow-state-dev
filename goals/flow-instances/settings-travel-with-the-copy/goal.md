# flow-instances › a copy's settings travel with it, and go nowhere else

**Issue:** FIX-1331 (builds on FIX-1321/1322 cardinality and instance ids, FIX-1323 instance-isolated state)
**Outcome:** An operator runs three copies of one flow definition on one server, differing only in the settings each was created with. Each copy behaves according to its OWN settings — including in blocks nested well below the action root — and can see none of its siblings'. One copy that omitted a defaulted setting reads the default. The settings themselves never leave the process: not on the unauthenticated flow listing, not anywhere in the database. A setting nobody declared, or one a block cannot read, refuses where the copy is created, before any request exists.
**Input:** `fixtures/input.json` — three copy ids with their bags (each carrying a distinct credential-shaped value), the setting the third copy omits and the default it should read, and the key to mistype. Held-out: every id, knob and marker is read from the fixture and graded against what the HTTP routes and the store return afterwards; swapping any of them must still pass a correct implementation.
**Signal:** against the real HTTP router (`createFlowApiRouter`) over on-disk SQLite stores.
(a) Three copies mint from one definition: all three carry the *same* action block object (no per-copy graph was built), all three bags differ, and the copy that omitted `retries` reads the schema's default.
(b) Each copy runs `POST /api/flows/<id>/<session>/actions/run` to completion. After closing the stores, reopening the same file and building a fresh host, `GET /api/flows/sessions/<session>/state` shows each copy the harness and model *it* was created with — written by a tap nested inside the sequencer and by a handler inside a router branch the copy's own knob selected — and none of its siblings' values.
(c) `GET /api/flows` carries no `config` key for any copy, no copy's credential appears anywhere in that payload, and no copy's credential appears anywhere in the SQLite file on disk.
(d) Minting with a mistyped key throws at that line, naming the flow, the instance id and the unknown key. A second definition installing the *same* block under a looser schema (`model` optional where the block requires it) is defined without complaint, refuses at the mint of the copy that omits `model` — naming the flow, the id and a declaring block — and mints normally for the copy that supplies it.

**Anti-game:** a hollow pass would assert only that the requests completed, or read each copy's settings back off the instance object the test itself minted — both hold when all three copies share one bag and one silently wins. So the check MUST close the stores and build a fresh host before reading, so nothing is served from a live context; MUST read the observed behaviour through the public `/state` route rather than off `instance.config`, since the question is whether the value reached the running blocks; MUST read it from a NESTED block (a tap inside a sequencer, and a handler inside a router branch), because a root-only read proves nothing about the context spread that carries the value down; MUST assert each sibling's value is ABSENT as well as that its own is present, since one shared bag is always right for somebody; MUST grep the whole database file rather than checking one endpoint's keys, so "never persisted" cannot be satisfied by a record written under another name; and MUST assert `defineFlow` did NOT throw for the looser pair in (d), because the guarantee is per copy and a test that only checked the refusal would let someone later turn it into a build-time check nobody costed. Grading `flowKind` or `cardinality` proves nothing — all three copies share both.
**Model:** n/a — handlers and a router only; the property under test is which settings reach a block, not model output.
**Run:** `pnpm tsx goals/flow-instances/settings-travel-with-the-copy/run.mts`

> **What the per-copy limit means here.** Leg (d) pins decision 6's stated cost rather than papering over it: the check is a parse of the real bag, so it is exact — refinements, nested objects and defaults included — but it happens once per copy rather than once per definition. "These two can never fit" is not reported where the flow and the block were written; it is reported at each mint that would have run unsatisfied. No block ever executes against a bag it did not accept.
