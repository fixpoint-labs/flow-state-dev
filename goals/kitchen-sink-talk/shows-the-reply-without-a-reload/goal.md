# kitchen-sink-talk › shows the reply without a reload

**Issue:** FIX-1609 (VG of the spec's PLAN; the epic FIX-1592's ER-23); re-pointed by FIX-1611

**Outcome:** With `support.help` open, a person whose post is routed to `support.devices` sees `support.devices is working`, then its line in the mailbox under its own name, with no reload. The same holds in the specialist's own conversation open in another tab.

**Re-pointed (FIX-1611).** The folder name is kept so its verdict history stays in one place. Until FIX-1611 this read `support.desk`, where every member was woken, and `support.otto` answering there. The mailbox is now routed, so each post names its specialist (`[route:support.devices]`), which the scripted route picks. The second post, sent before the first is answered, goes to the same specialist. The legs are unchanged.

**Input:** `fixtures/input.json`: the mailbox, the specialist that answers there (`support.devices`), what a post carries to be routed to it (`[route:support.devices]`), the scenario marker the scripted model keys on (`[scenario:reply-after-a-hold]`, the reply-in-mailbox answer held about three seconds), the marker it writes on the specialist's line (`[reply:in-mailbox]`), how long a line may take (15 s) and how many snapshot reads the page may make meanwhile (2). Held-out: each run posts three lines, each with a fresh `reply-token-…`, and only those tokens are graded, so a line another run or test left in the shared mailbox can never be the one that passes. The second post goes in while the specialist still works on the first. The third is read in a second surface, the specialist's own conversation for the mailbox, open in a second tab.

**Signal:** one real browser against kitchen-sink's **production build** (built by the run, never assumed), served by `next start` on the scripted model, the in-memory store and **no model key**. Everything graded is read off the open page; the page is reloaded once, for the last leg only.

- **working**: for each of the first two posts, the mailbox's panel shows `support.devices is working` in a reading before the one that first shows its line for that post, and before the next post is sent: a Send re-reads the runs even on a page that doesn't follow its session, so a later reading could show the row without the stream. The specialist working on the first post shows the same row, so for the second the reading must also come after its line for the first is in: still working on the second once it has answered the first.
- **line**: for each of the first two posts, within 15 s of Send, the open panel shows the specialist's line carrying the token and `[reply:in-mailbox]`, labelled `support.devices` (a second copy is graded under **once**); once its last line lands, the working row is gone within 5 s. For the third post, the specialist's conversation open in the second tab shows the post heard, and its answer after it, within 15 s.
- **once**: no reading while the page is open shows a post or the specialist's line twice, and after the one reload each post and each reply shows exactly once.
- **no-poll**: between Send and the line, the page reads a session snapshot (`GET …/sessions/<id>/state`) at most twice. The same holds for the second tab and the third post.

**Anti-game:** no reload before **once**. Nothing asserted on the wire, a hook's return, a package test or a CLI run: the page's own requests are only counted, for **no-poll**, and the server's reads behind the stream are not the page's. Before the reload the run reads the mailbox's state until every answer is kept, so the reload grades what was kept and not how fast; that read is not graded. Only this run's tokens count.

**Model:** n/a. kitchen-sink's scripted model routes each post by the specialist it names and answers the seats (epic FIX-1592 D3): after a three-second hold, a step calling `post-to-mailbox` with no text, so the real tool runs, then a text step. Keyless: the server runs with `AI_GATEWAY_API_KEY` empty.

**Run:** `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers pnpm tsx goals/kitchen-sink-talk/shows-the-reply-without-a-reload/run.mts`

**Controls:** on the same command.

- `GOAL_CONTROL=no-live`: the page is opened with `?goalControl=no-live`, which a test-mode build honours (`apps/kitchen-sink/lib/goal-control.ts`, `pageGoalControl`) by leaving the rail's panels without `live`. The page stays silent until the reload. Must FAIL at **working** and **line**, and at nothing else.
- `GOAL_CONTROL=main`: the app before the live view, run from a checkout of it with this directory copied in (for FIX-1609, `main`; for the FIX-1611 re-point, the FIX-1611 branch before FIX-1609 merged into it, since `main` had no `support.help`), and the scripted seat that holds (`apps/kitchen-sink/lib/e2e-mock-script.ts` and `apps/kitchen-sink/test/mock-flowstate.ts`), so the control differs from the change only in the stream and the panels. The app knows no control by that name; it tells the run which legs must fail. Must FAIL at **working** and **line**, and at nothing else.
