# manager-queue-lab › it routes a queue to the seats their files name

**Issue:** FIX-1430 (the goal check — the epic's exit gate, ER-20 and ER-21). Rewritten by FIX-1792 P2: the mailbox is removed, and the manager files on its own conversation's board for its `delegates:`.

**Outcome:** A team declared entirely in files takes in more work than it has workers. The manager, a worker on Workforce's coordinator flow whose `delegates:` names the three builders, files one task per piece on its own conversation's board, each naming the builder it is for. Each task runs on the worker it names and carries that worker's own file, in a task session of its own, and a second task for one worker is neither re-routed nor dropped. Nobody writes a board id, nobody wires a collection between the workers, and nothing is dispatched by hand.

**Input:** `lab/workforce/` (the tree) and `WORK` in `run.mts` (four pieces of work). Both are **held out**: the manager's delegates, each builder's `answersFor:` and which flow each worker runs on come off the tree at run time, and the four pieces are ordinary English sentences the lab knows nothing about. `answersFor:` routes nothing: it is a fact only the right file holds, reported back out of the running work.

**The manager's flow, a call recorded here.** The manager's `WORKER.md` says `flow: coordinator`, unchanged. The lab used to register a flow of its own under that name; it now registers Workforce's coordinator flow (`defineCoordinatorFlow`), and the lab's own `flows/workers/coordinator.mts` is gone. Since FIX-1791 `coordinator` is the framework's name, and a lab flow under it would make this the one tree where the line means something else. The manager's judgment turn carries the task tools through its delegates (FIX-1802), so nothing in the lab composes them. The builders keep the lab's `builder` flow, which takes tasks through `workerTaskEntry`.

**The oracle and the implementation are two different sources, and that is the whole check.** The stored row says which worker it was filed for; the running work reports, from inside its task session, which worker it runs as and what that worker's own file says; the tree says which file declares which worker. Nothing that routes reads `answersFor:`, and the grade never reads the board's own report.

**Signal:** six legs over a real `createFlowState` host, acted on through its HTTP router as the lab's verified user, with the rows read from the store. **Every control also grades itself**: a control that goes red at a leg other than the one it names has demonstrated a different check.

(a) **The rows are filed, on the manager's own board.** On the gate's path the manager's judgment turn decides which builder each piece is for and files with its `createTask` tool: the check sends no `createTask_tasks`, and the turn was handed `createTask`. Every row is stored in the manager's conversation's partition.

(b) **Every piece reaches the board in its own words, one distinct row per piece**, both directions (exactly one row carries each piece, and each row carries exactly one piece), every row naming one of the manager's delegates, and one builder given two pieces, or leg (e) grades nothing.

(c) **Every row runs on the worker it names, carrying that worker's own file.** The work's reported worker must be the row's assignee, and its reported `answersFor:` must be what the tree's file for that assignee says. Proof of execution is a **file on disk** written by the builder's turn, not the board's report.

(d) **Each row runs in its own task session**, a child of the manager's conversation, the lab user's, naming the manager's board as its filer, and holding none of the conversation's other pieces.

(e) **A second row for one worker is not re-routed and not dropped**: every row for that worker ran on it, once each, and every row completed.

(f) **A row for a worker the manager can't hand a task to is refused by name**: a filing for `eng.nobody` answers `unknown_assignee`, naming it, and stores nothing. A row filed for nobody, with three delegates, waits `held` and unassigned (FIX-1794 BR-6; `pending` before FIX-2080) and runs nowhere.

**Retired under FIX-1792's BR-24, with the reason.**

- **Leg (e)'s first half, "the extra row waits for its worker to free".** A conversation board has no drain: each row filed is handed over at once to a task session of its own, so two rows for one worker run at the same time. The lab saw it: with the builder turns held, both rows filed for `eng.builder-a` were `in_progress` at once, in two sessions. The `MANAGER_QUEUE_DRAIN_WIDTH` knob goes with it: nothing reads a width. The surviving half (not re-routed, not dropped) is leg (e).
- **Leg 0, "the minted board id appears in no file".** No file declares a board, so nothing is minted. The sibling check's leg 0 now asserts that no file declares a board or grants the task tools.
- **Old leg (f)'s "errored, naming the row".** With no default worker, a mailbox drain refused a row for nobody where it would have run. A conversation board refuses an unknown assignee at filing and keeps a row for nobody waiting for `updateTask({ assignee })`; leg (f) grades both, as the code does.

**The filer is a slot, and only one of its two values is the gate.**

- `GOAL_FILER=model` (default) — **the gate.** The manager chooses and files with its own tool. Needs a model credential.
- `GOAL_FILER=scripted` — **not the gate.** The same four pieces are filed through the conversation's `createTask_tasks` action, spread across the manager's delegates (two for the first), and legs (b) to (f) run unchanged. The manager's turn, woken by each task's notice, runs on a quiet stub that files nothing. A scripted run says so in its own evidence line.

**Anti-game:** A hollow pass would file four rows and assert the board reported four completions, true even when a task ran as the wrong worker or nothing ran at all. So the check MUST prove execution by a **side effect outside the board** (the outbox file); MUST grade the file a worker ran with against **the tree's file for the row's assignee**, read at run time, never against the session's own label alone, since the board's hand-over agrees with itself; MUST require one builder to get two pieces, or leg (e) grades nothing; MUST match pieces to rows **one to one in both directions**; and MUST read the rows from the store, not from the board's own listing.

**Model:** `openai/gpt-5.4-mini` on the gate's path (`gatewayModel()`, overridable with `GOAL_MODEL`). The model appears at one surface, the manager deciding who gets what, plus the turns each task's notice wakes, which file nothing. Builder turns are deterministic stubs.

**Run:** `cd goals && pnpm exec tsx manager-queue-lab/it-routes-a-queue-to-the-seats-their-files-name/run.mts`

**Controls** (each forces the scripted filer):

- `GOAL_CONTROL=repointed-map` — the host hands the installation two builders' files swapped under their ids; the tree on disk is untouched. Every id is well-formed, the roster hires, every row names a delegate, runs on it and completes. Must FAIL at **leg (c)** once for every row filed for either of the two, and nowhere else; the control derives that set from the stored rows and checks it itself. (Before the conversion this control swapped two entries in the host's worker → desk map. Rows now name their worker, so there is no desk map; the host's id → file records are what it moves now.)
- `GOAL_CONTROL=duplicate-filing` — the filer combines two pieces into one row and files a third twice. Four rows still land, every row names a delegate, one builder still gets two, and every row runs where it names. Must FAIL at **leg (b)**, and nowhere else.
