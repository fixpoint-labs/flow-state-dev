# multi-seat-collab › it hands a row between two seats in view

**Issue:** FIX-1497 — the ER-Collab exit proof of epic FIX-1457 (VG of the spec's Checks table; BR-1 to BR-21)

**Outcome:** Two seats hired from Markdown work one channel's board. The planner files a piece of work for the `build` desk; the seat whose own file answers for that desk takes it, reaches a question only a person can settle, and parks the row saying what it needs. The person answers through that seat's own action; the same seat finishes the row and, in finishing, files the next row for the `review` desk, which the other seat takes and finishes. Nobody claims a row on the person's behalf, and an answer sent as someone else does not land. All of it runs on the shipped `fsdev dev`, and a person who has not read the spec can open the shipped DevTool and say which seat was waiting, what for, what it was told, and which other seat picked the work up.

**Input:** `../lab/workforce/` (one `CHANNEL.md`, three `WORKER.md`) and `fixtures/input.json` (the piece of work, its question, the answer, a second answer, a second person's id, and a piece for nobody). Both are **held out**: the channel, the board's local name, the members, each seat's desk and every seat id come off the tree at run time; the fixture's sentences are ordinary English the lab knows nothing about, and its two desk keys are checked against the desks the tree declares before anything runs. The app's desk → seat map is written in `../lab/fsdev.config.mts`, as an app would write it, and is never read by a check.

**Signal:** one run of the shipped `fsdev dev` over the lab's config, driven over its own HTTP doors, then read in Chromium on the shipped DevTool bundle. Every failure line is tagged with its leg, and every control grades itself against the legs it names.

- **V0 · BR-1.** A `CHANNEL.md` declares the board by name, and no file under `goals/multi-seat-collab/` carries the minted ledger id.
- **V1 · BR-2, BR-5.** Exactly one row lands for the one piece, carrying it verbatim, for a desk the tree declares — not one per channel member. A piece filed for nobody reaches the board, is taken at a drain, and settles `errored` carrying its own id, having run nowhere.
- **V2 · BR-3, BR-4.** Every attempt that ran is graded against the `WORKER.md` of the seat that ran it: the row's desk is the desk that seat's own file answers for. Proved by a line the worker body appends to a file, never by the board's report.
- **V3 · BR-6, BR-7, BR-7a, BR-10.** The owning seat parks the row. The seats hand rows off, so the drain that claimed it returns `handed-off` as soon as the row is running in its child session; the park happens there. A drain run afterwards over the parked row returns promptly with `parked-for-review` and the row is still `parked` when read back. The answer, through the owning seat's `answer` action, completes the row with the answer on it; the finishing attempt runs under a claim made by an `answer` request on the owning seat's own session, not by a later drain; the row parks once and finishes once. A second answer completes, having found the row, and changes nothing on it and runs nothing.
- **V4 · BR-8, BR-9.** Every attempt ran under a claim made from a worker seat's own session, every visible `claimed` change was emitted from one by a `drain` or `answer` request as the one principal, and the row for nobody was taken and refused from one. An answer sent to the owning seat as a second person, while the row is parked, leaves the row byte-for-byte unchanged.
- **V5 · BR-12, BR-13, BR-14.** The seat that finished the first row filed a second row, for the other desk, naming the first; the other seat instance ran it in its own child session under its own session; moving the first row's assignee was declined `immutable-assignee` and the assignee never moved. Graded only when the first row finished — if it did not, that is V3's failure and the run says so.
- **V6 · BR-20.** `TaskStatus` equals the written list of seven.
- **VB · BR-15, BR-16, BR-17.** In Chromium, on the DevTool's own navigation: (1) each seat is a navigator row by its exact id, and the owning seat's session's Tasks tab shows the row with its goal, assignee and a link to the session it ran in; (2) following that link opens the child session the row ran in, whose Tasks tab shows the row `parked` with the reason legible **and nothing expanded** — a clamped reason must carry the whole text on its title — and, after the answer, the row in its current state with the answer in the same place; (3) the Resources panel's ledger collection lists every row with the status, assignee and running seat the ledger holds. Screen 3 grades what a person sees against the ledger; that the ledger holds two rows with two assignees is V5's to grade.
- **V7 · BR-19.** Every path changed against the merge base, committed or not, is under `goals/` or `specs/issues/FIX-1497/`.

**Anti-game:** A hollow pass would file a row, drain it, answer it and read back `completed` — true when every row ran on one seat, true when the check read the routing map on both sides of its own comparison, true when the board reported a completion for work that never ran, and true when the "answer" was simply the next drain picking the row up. So the check MUST prove execution by a file the worker body writes, outside the board; MUST grade each attempt against the `WORKER.md` of the seat that ran it and never against the app's map; MUST read the finishing claim back to the `answer` request rather than accepting that the row got done somehow; MUST assert the second person's delivery reached the server as a request before judging that it did not land; MUST read the reason off the row on screen with nothing expanded, not off the store; and MUST NOT count "two rows exist" as a handoff unless two different seat instances ran them. A pass condition that is an absence is paired with a positive record every time: the second delivery *completed* (so it found the row) before "changed nothing" counts, and the row for nobody *reached the board* before its fate is judged.

**One refusal is silent, and it is a finding rather than a pass condition.** An answer sent as a second person is admitted with a `202` and a request id, and then never advances: no items, no log line, still `in_progress` when the window closes. It does not land, which is what BR-9 asks — but the refusal has the same silent shape as FIX-1511 (a throw on the served path swallowed into a request that never settles), here with a principal mismatch as the trigger rather than the environment. Observed, not diagnosed. The run records it in its notes on every pass.

**Model:** n/a — model-free. Seat bodies are deterministic; a model would add a way to fail that has nothing to do with the claim.

**Run:** `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers pnpm tsx goals/multi-seat-collab/it-hands-a-row-between-two-seats-in-view/run.mts` (builds the DevTool bundle first; on a clean checkout run `pnpm --filter @flow-state-dev/devtool build` once before).

**Controls:** `GOAL_CONTROL=<name>` on the same command. The server's config reads the same variable, so it is one switch end to end. Each must FAIL, at exactly the legs named, and the run checks that itself.

- `swapped-desks` — the app's map trades the two desks' seats; the tree is untouched. Every row still runs, parks, is answered and completes. Must fail **V2** only: each attempt ran on a seat whose own file answers for the other desk.
- `ignore-the-answer` — the worker parks on the question in its input instead of on whether the row carries an answer. Must fail **V3** only: the answered row parks again and never finishes. V5 reports itself ungraded, because the row it grades never finished.
- `second-principal` — the "second person's" delivery is sent as the session's own principal instead. Must fail **V4** only: the delivery lands and moves the row. A driver-side perturbation, because the refusal it grades is the engine's and nothing under `packages/` may change; it proves V4's check sees a landing, not that the engine refuses one — the unperturbed run shows that.
- `silent-park` — the worker parks with no reason. Every headless leg stays green. Must fail **VB** only, at screen 2: the parked row shows no reason.
- `one-seat` — both desks route to the first seat. Must fail **V5 and V2, both**: two rows ran on one seat instance, so nothing changed hands (V5), and the review row ran on a seat whose own file answers for `build` (V2) — widening one seat's eligibility is what puts a review row there. A run that reddens only one of the two is itself a failure.

V0, V6 and V7 have no named control. Their red states were produced once by hand, snapshotted and reverted, and are recorded below.
