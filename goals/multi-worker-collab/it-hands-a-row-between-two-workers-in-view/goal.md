# multi-worker-collab › it hands a row between two seats in view

**Issue:** FIX-1497 — the ER-Collab exit proof of epic FIX-1457 (VG of the spec's Checks table; BR-1 to BR-21). Rewritten by FIX-1792 P3: the mailbox and its board are gone, and the planner files for its `delegates:` on its own conversation's board.

**Outcome:** Two workers hired from Markdown take the work a third files for them. The planner, whose `WORKER.md` names the two as its `delegates:`, files a piece of work for the `build` desk on its own conversation's board, and the work that piece implies for the `review` desk beside it, waiting on the first. The worker whose own file answers for `build` takes the first in a task session of its own, reaches a question only a person can settle, and asks it: the row holds on the question. The person answers through the planner's conversation; the same task session carries on, on the same attempt, and finishes the row. The other worker then takes the second row in its own task session and finishes it. Nobody answers on the person's behalf, an answer sent as someone else does not land, and a held row's worker cannot be swapped. All of it runs on the shipped `fsdev dev`, and a person who has not read the spec can open the shipped DevTool and say which worker was waiting, what for, what it was told, and which other worker picked the work up.

**Input:** `packages/shift-manager/test/fixtures/multi-worker-collab/workforce/` (four `WORKER.md`: the `eng.queue` coordinator, the planner and two workers) and `fixtures/input.json` (the piece of work, its question, the work it implies for the other desk, the answer, a second answer, a second person's id, and a piece for nobody). Both are **held out**: the planner, its delegates, each worker's desk and every worker id come off the tree at run time; the fixture's sentences are ordinary English the lab knows nothing about, and its two desk keys are checked against the desks the tree declares before anything runs. The app's desk → delegate map is `ROUTES` in `packages/shift-manager/test/fixtures/multi-worker-collab/host.mts`, as an app would write it: the filer reads it to name a row's assignee, and no check grades against it.

**Signal:** one run of the shipped `fsdev dev` over the lab's config, driven over its own HTTP doors, then read in Chromium on the shipped DevTool bundle. What the board holds is read off the server's SQLite file, read-only (the browser read carries only a row's board fields, and the checks grade a row's input and answer too). Every failure line is tagged with its leg, and every control grades itself against the legs it names.

- **V0 · BR-1.** No file under `goals/multi-worker-collab/` or the lab declares a board: no `MAILBOX.md`, and no `boards:` line in a `WORKER.md`. The planner's file names the two workers as its `delegates:`. Before any leg, the tree is refused whole unless it holds exactly one coordinator, one planner and two workers — a stray worker would still hire and run, and the proof would be about a different team.
- **V1 · BR-2, BR-5.** Filing two pieces lands exactly two rows — not one per delegate — each carrying its piece verbatim with its desk, for one of the planner's delegates, on the planner's conversation's own board. A piece filed for nobody reaches the board and runs nowhere: after the board has run it is still `pending`, with no attempt, no run, no task session and no work line.
- **V2 · BR-3, BR-4.** Every attempt that ran is graded against the `WORKER.md` of the worker that ran it: the row's desk is the desk that worker's own file answers for. Proved by a line the worker body appends to a file, never by the board's report.
- **V3 · BR-6, BR-7, BR-7a, BR-10.** The worker asks its question and the row holds on it (`in_progress`, an open row hold whose prompt is the question; FIX-2131 retired the `parked` status). A question holds nothing open: the turn that asked ended `completed`, and nothing is running while the row stays held. The answer, through the planner's conversation's `updateTask_tasks` naming the question as the one person, answers it (an `answered` change from that request in that conversation); the row completes with the question answered by that message, on the same attempt; it asked once and finished once, on the same worker, in the same task session as the ask, reading the answer. A second answer completes, having found the row, and its action answers `question_answered`; it changes nothing on the row and runs nothing.
- **V4 · BR-8, BR-9.** Every claim was made by the planner's conversation's own board run (`dispatch` in that conversation) as the one principal, and every attempt ran in the task session that board opened for its row: a child of the planner's conversation, naming the row and its assignee, born for the board the row is on. An answer sent into the planner's conversation as a second person, while the row is held, leaves the row byte-for-byte unchanged; the delivery must first have reached the server as a `202` with a request id, or been refused explicitly: a `401`/`403`, or the engine's answer for another user's session, a `404 Unknown session` naming the planner's conversation, which counts only once the owner's own delivery to that same session is admitted (an unused id gets the same `404`, so the owner's admission is what tells them apart). Any other status, a missing request id or a transport error fails V4.
- **V5 · BR-12, BR-13, BR-14.** Moving the held row to the other delegate (`updateTask_tasks`) is refused `field_locked_after_start` (FIX-2081: a started task keeps one accountable worker), and the first row's assignee never moves. The second row names the first and waits on it (`follows`, `deps`), is for the other delegate, started only once the first completed, and was finished by the other worker in a task session of its own. Graded past the freeze only when the first row finished — if it did not, that is V3's failure and the run says so.
- **V6 · BR-20.** `TaskStatus` equals the written list of six.
- **VB · BR-15, BR-16, BR-17.** In Chromium, on the DevTool's own navigation: (1) each worker's own session is a navigator row under the one copy of the flow it runs on, and the planner's conversation's Tasks tab shows the row with its goal and the assignee the board holds; (2) the task session the row names as its run, opened from the navigator under its worker's flow, has a Tasks tab showing the row `in_progress` with its question legible in the collapsed row's reason slot, read by task id, **and no row open** — a clamped reason must carry the whole text on its title — and, after the answer, the row in its current state with the question gone from that slot; (3) the Resources panel's ledger collection (`tasks`) lists both of the planner's rows, and each expanded row shows the status and assignee the board holds and names the task session it ran in — a listed row whose body shows none of it fails. The body folds after 20 lines behind a "… (N more lines)" button, so the check clicks it, as a person would, before reading.

**Anti-game:** A hollow pass would file a row, answer it and read back `completed` — true when every row ran on one worker, true when the check read the desk → delegate map on both sides of its own comparison, true when the board reported a completion for work that never ran, and true when the "answer" was simply a retry picking the row up. So the check MUST prove execution by a file the worker body writes, outside the board; MUST grade each attempt against the `WORKER.md` of the worker that ran it and never against the app's map; MUST read the answered attempt back to the task session that parked and to the answer request that resumed the row; MUST assert the second person's delivery reached the server as a request before judging that it did not land; MUST read the reason off the row on screen with nothing expanded, not off the store; and MUST NOT count "two rows exist" as a handoff unless two different workers ran them in two sessions. A pass condition that is an absence is paired with a positive record every time: the second delivery *completed* (so it found the row) before "changed nothing" counts, and the row for nobody *reached the board* before its fate is judged.

**What changed in the conversion, and why (BR-24).** The mailbox's board and its drains are gone; each line below names what proves the old step's outcome now.

- *The drain over a parked row returns `parked-for-review`.* No worker drains: the planner's board hands each row to a task session at once. The outcome, a park holds nothing open, is V3's "the parking attempt ended and nothing runs while the row stays parked".
- *The finishing attempt runs under a claim made by the `answer` request.* The answer no longer claims: it puts the row back in the queue, and the board run claims it. V3 grades the answer request's own `resumed` change and the finishing attempt's session, which is the parking one.
- *The minted ledger id appears in no file.* No file declares a board, so there is no mint; V0 grades that no file declares one.
- *A row for nobody is refused by name (`errored`).* A conversation's board keeps a row with no assignee waiting for one and hands it to nobody (FIX-1794). V1 grades exactly that.
- *The finishing worker files the next desk's row, and tries to move its own row's assignee.* A task session files only its own task's pieces, which its task then waits on, so a worker can't file a sibling row on the planner's board. The planner files the second row, waiting on the first, and the freeze is tried by the planner on the parked row (V5).
- *Screen 1's run link.* The DevTool's Tasks tab links a row to its run by decoding the run's session key, and it decodes only a mailbox board's `task|<board>|<task>` key, not a conversation board's task session key, so the planner's row shows no link. The reader now opens the session the row names as its run from the navigator (VB 2); that a row names exactly the run working it is graded by `goals/task-run-link/it-names-the-run-working-each-task` (legs **browser** and **stream**).
- *`mailbox-actions-off`.* That control lived in the lab's config, not this goal, and retires with the mailbox's board actions: a worker has the task actions only while one of its `delegates:` takes a task, which `goals/manager-queue-lab/it-stands-the-team-and-its-board-up-from-files` proves (leg (c), its twin arm: builders that take no task, no task tools, and `addTask_tasks` answers `no_delegation_board`).
- *Controls.* `swapped-desks` and `one-seat` moved the app's desk → worker routing for a drain; the routing is now the filer's assignee, so both are assignee mistakes made by the filer, and `one-seat` is named `one-worker`.

**Model:** n/a — model-free. Worker bodies are deterministic; a model would add a way to fail that has nothing to do with the claim.

**Run:** `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers pnpm tsx goals/multi-worker-collab/it-hands-a-row-between-two-workers-in-view/run.mts` (builds the DevTool bundle first; on a clean checkout run `pnpm --filter @flow-state-dev/devtool build` once before).

**Controls:** `GOAL_CONTROL=<name>` on the same command. The server's config and the filer read the same variable, so it is one switch end to end. Each must FAIL, at exactly the legs named, and the run checks that itself.

- `swapped-desks` — the filer's desk → delegate map trades the two desks' workers; the tree is untouched. Every row still runs, parks, is answered and completes. Must fail **V2** only: each attempt ran on a worker whose own file answers for the other desk.
- `ignore-the-answer` — the worker asks the question its row carries instead of asking only while the row has no answer. Must fail **V3** only: the answered row asks again and never finishes. V5 reports itself ungraded past the freeze, because the row it grades never finished.
- `second-principal` — the "second person's" delivery is sent as the session's own principal instead. Must fail **V4** only: the delivery lands and moves the row. A driver-side perturbation, because the refusal it grades is the engine's and nothing under `packages/` may change; it proves V4's check sees a landing, not that the engine refuses one — the unperturbed run shows that.
- `silent-park` — the worker asks a question that says nothing (`?`). Every headless leg stays green. Must fail **VB** only, at screen 2: the held row shows no reason.
- `one-worker` — the filer sends both desks to the first desk's delegate. Must fail **V5 and V2, both**: two rows ran on one worker, so nothing changed hands (V5), and the review row ran on a worker whose own file answers for `build` (V2). A run that reddens only one of the two is itself a failure.

V0 and V6 have no named control. Their red states are produced by hand, snapshotted and reverted, and recorded below.
