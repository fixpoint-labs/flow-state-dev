# projects › it a shared project has one owner per workstream

**Issue:** FIX-1793 (epic FIX-1786), its goal: `specs/issues/FIX-1793/SPEC.md` → "The goal, and how we'll know it's met"; PLAN VG.

**Outcome:** two users of one org each own a workstream in one shared project. Each reads both workstreams' status, and neither can change the other's, by any path. Each talks to the project through their own project coordinator, which reads every workstream and hands work only to that user's own workstreams. A private project is reachable by nobody else, Alice in her second org included.

**Input:** Shift Manager's DevTeam install as the checkout ships it, served by its own command over a fresh SQLite store. Alice is its owner and Bob its second member, each over HTTP with their own verified bearer; Alice's second org comes from the scratch patch `second-org`. Held out, in `fixtures/inputs.json`: the private and shared projects, each user's workstream (id, title, objectives, due date), Bob's status word, the word Bob's lead is asked to write onto Alice's entry, the work word, and the four asks (status, work, the work re-ask, tool). Each run picks one of each at random and adds a fresh suffix to every id and word, so any other values of the same shape must pass too.

**Signal:** every assertion below, by name.

- **a** (model-free). Alice makes a private and a shared project (`createProject` on the `projects` flow, Bob a member of the shared one). `a:alice-lists-hers`: her private listing holds it and she opens it by its address. `a:bob-cant-list`: neither of Bob's project listings (org and user scope, through his roster session) holds it. `a:bob-cant-open`: the resource route answers Bob no row at its address, in either collection. `a:bob-cant-read`: Bob's `ensureWorkerSession` for a project coordinator linked to it is refused. `a:second-org`: Alice in her second org lists neither project, opens neither, and can't link a coordinator to the private one. `a:both-see-shared`: both list the shared project, and Bob links his own coordinator to it.
- **b**. Each opens a workstream on the shared project over HTTP, naming a lead of their own: the roster flow's `hire` puts a worker on `agent` on the opener's roster at `lead-<project>-<workstream>`, listing `eng.coder` as its delegate and holding `updateWorkstream`, and `openWorkstream` names it as the lead. `b:opened`: the entry is the opener's, led by that worker, with a session. `b:own-roster`: the lead is on its owner's roster as their own worker and not on the other's. `b:session-owner`: the workstream session is in its owner's listing, readable by them, found by `findWorkerSession` with its lead and workstream, and the other user's read of it is refused. `b:bobs-write-refused`: Bob writes Alice's entry three ways, each refused naming the engine's owner rule, and her entry's state and report read back unchanged: the app's `updateWorkstream` naming her as owner; a registered flow's code (`goal-entry-writer`) updating her entry's status and report, deleting a row Alice planted under her own key just before (and graded on that row still being there), and creating a second entry under her key; and a worker's tool, Bob's own lead asked on a real-model turn to set her workstream's status, whose `updateWorkstream` writes only the workstream its session leads (his). `b:tool-reached`: that turn called the tool (asked twice at most), so the tool path ran. `b:owner-writes`: Bob's write of his own status lands and both read it. `b:project-read`: as Alice and as Bob, the project's one-prefix read holds exactly the two entries, with each owner's objectives as opened, and Workforce's `projectProgress` over them counts 2 workstreams and both owners' objectives.
- **c** (real model). Alice opens her project coordinator on the shared project (`ensureWorkerSession` with `projectId`). Asked how the project is going and Bob's workstream's status: `c:read-holds-status`, its `readProject` tool output (the stored `tool_output` item) holds Bob's workstream with his held-out status word; `c:names-status`, its answer names that word. Asked to hand a task to every workstream of hers (and, when that turn completes but calls no `createTask` because the model listed its delegates and asked first, told once more to go ahead and hand it to each delegate it listed, as a user answers that question): `c:delivers-once`, the coordinator's delivery ledger (read from the store row she owns) holds exactly one delivery across the posts those asks made, to her lead and her workstream, delivered into her workstream session, and that session holds exactly one line carrying the work word; `c:never-to-bobs`, no ledger entry and no routing record outcome other than `skipped` names Bob's lead or workstream, and Bob's workstream session holds no line with the word.

**Anti-game:** no project, entry, worker or session is seeded: each user makes each one through the install's routes as themselves. Every grade reads what that user gets back from the routes (listings, rows by address, session reads, stored items), or, for the coordinator's delivery ledger, the server-written session row the user owns in the store file; never a key string, never Shift Manager's own state, never the model's retelling alone (`c:names-status` is graded beside `c:read-holds-status`, which reads the tool's output). A refusal is graded together with what the store holds afterwards, so a write refused at the door but landed anyway still fails. The direct write runs in a flow registered on the served install and reached over HTTP as Bob, not a double: the owner rule must hold at the store, whichever flow writes. "Never to Bob's" is graded on the coordinator's own decision (ledger and routing record), not only on Bob's session, because the engine refuses a dispatch into another user's session as a second layer: under `all-entries-delegate` the coordinator does hand to Bob's, the dispatch fails `session-not-found`, and his session stays empty. A check on his session alone could not see the control.

**Model:** real — openai/gpt-5.4-mini (the DevTeam project coordinator's own `model:`, and the hired leads'), on leg b's one tool turn (Bob's lead) and leg c's two coordinator turns (three when the work ask is re-asked). The delegate's turn after delivery runs too, ungraded.

**Run:** `flock /tmp/fsd-goal.lock pnpm tsx goals/projects/a-shared-project-has-one-owner-per-workstream/run.mts` (`GOAL_LEGS=a` or `a,b` runs fewer legs; each leg needs the ones before it). The run prints every module patch in full, and fails when one never reached the code it served.

**Controls:** each is a module patch on the served process, never written to the checkout.

- `GOAL_CONTROL=no-owner-rule` (runs legs a and b): the engine's owner-writes check (`ownerWriteRefusal` in `packages/engine/src/resources/owner-private.ts`) never refuses. Must FAIL **`b:bobs-write-refused`**, and nothing else. Leg c isn't run: the control has let Bob write Alice's entry, and leg c makes no claim about the owner rule. (Dropping `ownerWrites` from the entries' declaration doesn't isolate the rule: an owner-keyed collection without it reads as owner-private, and Alice's own `openWorkstream` is refused before any write by Bob is tried.)
- `GOAL_CONTROL=all-entries-delegate` (runs legs a to c): a project coordinator takes every open entry in its project as a delegate: its seed keeps every owner's entries, its delivery resolves a workstream under whichever owner holds the id, and its delegate check takes a worker that isn't on the user's roster (Bob's lead is his own hire). Must FAIL **`c:never-to-bobs`**, and nothing else. The re-ask above is what keeps this reliable: a work turn that dispatches nothing hands to nobody, so without it the control can't see what it removes, and fails `c:delivers-once` instead (r6d).

**Not run: legs a to c on the pre-feature `main`.** The spec wants them FAIL on the commit before FIX-1793's P1 merged. This clone is shallow: its oldest commit, `be0443be` (2026-10-07), already carries `ownerWrites`, so the pre-P1 commit isn't here, and serving it would need a deeper fetch plus a full install of that tree. Its `openWorkstream`, `visibility` and project coordinator didn't exist, so leg a's first `createProject` (strict input, `visibility`) would refuse at setup; and the `entry-writer` patch imports this checkout's Workforce, which an older engine wouldn't load. Recorded rather than run.
