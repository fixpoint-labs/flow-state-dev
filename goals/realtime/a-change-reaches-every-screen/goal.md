# realtime › a change reaches every screen

**Issue:** FIX-2368, the closure of epic FIX-2367. Its spec: `specs/issues/FIX-2368/SPEC.md` → "The goal, and how we'll know it's met". The labs' half of j2 (`j2-teammates`, `j2-claude-code-style`) is FIX-2843: `specs/issues/FIX-2843/SPEC.md`.

**Outcome:** On one `main` commit, an app on the Node host, run as two processes over one Postgres on the Postgres bus at the product's defaults, shows a viewer on process 2 another user's org-state patch, org row and plain reply within a second, reading nothing between changes; Shift Manager's board shows a settled task within a second with no read between notices; a user who may not read a session is refused and hears nothing, through a restart; a reply run on a BullMQ worker reaches a third process; and behind `createNextHandler` the same app says it has no push and catches up on its poll. Each lab (Teammates, Claude Code-style), served as two processes over that Postgres, shows on process 2's page a reply, a running turn, the worker's activity and a settled task that process 1 wrote, each within a second, and reads nothing while idle.

**Input:** The fixture app in `app/`: one flow (`flow.ts`: `setPlan` patches `ctx.org`, `addSeat` adds a row to an org collection, `say` writes a reply and nothing else), one page (`Board.tsx`: `useSession(id, { live: true })`, `useClientData`, `useResourceCollectionList`), its `FlowState` (`flowstate.ts`, `postgresStores` from `FSD_DB_URL`, no bus, push or poll option), its Node host (`host.mts`, `serve()`) and its Next route (`next-route.ts`). Sign-in is a cookie naming a token: A and B in org 1, C in org 2. The runner prints `app/`'s sha256 and runs the same bytes on the control commit. Processes are forked (`goals/lib/peers.mts`) over one Postgres (`goals/lib/postgres.mts`: `initdb` + `pg_ctl` with `log_statement = all` and `log_line_prefix = '%n|%a|'`, each process its own `application_name`). Chromium through `goals/lib/playwright.mts`, one browser context per user; the page is built with esbuild from the checkout's packages. Leg b and j2 run Shift Manager's own command over the closure's Lab (D2): the run-lab (`packages/shift-manager/test/fixtures/run-lab`) copied to scratch with its store line swapped to `postgresStores`, its lead flow declaring the board's task-list view as shipped worker flows do, and one file added to its tree, an org `shift-coordinator` on the coordinator flow filing for the run-lab's coder (the panel Shift Manager keeps a board timer on is the Shift Coordinator's; the run-lab declares none). j3 adds a `redis-server` on a free port. The lab scenes serve each lab as it ships, `fsdev dev --config <config> --app <the lab's package>` over its built pages, twice, each its own OS process on its own port; the config is the goal's (`labs/teammates.config.mts`, `labs/claude-code-style.config.mts`): the lab's own open function on its own workers, with only the model scripted (`labs/scripts.mts`, through `labs/test-support`'s `scriptedModels` and the host's `modelResolver`) and every coding worker on harness-manager's scripted coder. Each lab's `host.mts` is the file on `main`, its store line swapped to `postgresStores` as the process loads it (`goals/lib/module-patch.mts`; a host whose line is gone fails setup). The lead's turn is picked by its line: `SAY-<tag>` answers at once, `HOLD-<tag>` answers after 2.5 s, `FILE-<tag>` files a task for the lab's coder (Teammates' `teammates.cursor`, Claude Code-style's `desk.coder`). Another client on process 1 opens the conversation (Teammates: Chief of Staff's; Claude Code-style: a session-mode session on a new project over a scratch checkout) and sends every line. One Chromium context per lab, one page on process 2, fronted: Teammates on Chief of Staff with its panel's Done tab, Claude Code-style on the session. Teammates reviews a coding run that committed, so its task waits for a review: the same client on process 1 accepts it, as a person does. Held out: every value and id is stamped per run.

**Signal:** each "within 1 s" is 5 samples, all under 1000 ms, none retried. A sample starts when A's page sends its action (so it includes the run), or, for Shift Manager, when the store says the task completed or the runner sends the line.
- `a:org-state` — B's page on process 2 shows A's plan patch (A's page on process 1).
- `a:org-row` — B's page shows A's new seat.
- `a:no-timer` — from B's first `crosses: true` frame and its opening reads done, B sends 0 requests over 10 s idle; while A writes, every read B sends follows a notice frame, a socket open or the session stream's connect by less than 1 s.
- `d:plain-reply` — A's session view on process 2 shows A's reply. The viewer is A's second screen: a session is its owner's alone (leg c is refused it), so no other user may watch it.
- `d:no-timed-read` — over the same idle window, Postgres logs 0 statements from process 2 naming a watched session.
- `c:refused` — C asks the mint, from its own page, for A's session topic (the app's page never asks: its session read is refused first) and opens a socket with the ticket: no answer grants the topic, C's socket hears no notice for it, and C's page shows none of A's values.
- `c:other-org-silent` — C's own board (org 2) sends 0 reads and changes 0 times while A writes org 1.
- `c:reconnect-refused` — process 2 is stopped and started again on its port; C's socket reconnects and re-mints, the re-mint grants nothing of A's session, and C hears nothing of A's next reply (which A's view on the restarted process 2 shows).
- `b:settles` — five tasks filed on the Shift Coordinator's conversation, each run by the coder in its own task session: the panel draws each settled (it lists active tasks, so settled reads as gone or `completed`) within 1 s of the store holding it `completed` (polled every 5 ms on the runner's own connection).
- `b:no-read-between` — over 10 s from the panel's first `crosses: true` frame, with a task held running, every read the page sends follows a notice frame by less than 1 s.
- `j2:no-poll` — every scripted run cancelled and no request running anywhere, one task held open on the panel; the lead's conversation (`/s/<id>`), Messages and the panel each send 0 requests over 10 s.
- `j2:message` — a line sent into the lead's conversation from another client (its door, `respond`) is drawn in the conversation within 1 s of being sent. Samples are 1.5 s apart: the session stream reads at most once a second per connection (FIX-2426), and a sample inside that interval would time the cap.
- `j3:worker-reply` — process 1 runs `enqueue-only`, a third process `process-only` (the same host file with `FSD_REDIS_URL`); A's reply, sent from A's page on process 1, shows on A's session view on process 2. The worker's own connection wrote the items; process 1 wrote none.
- `j3:no-timed-read` — 10 s idle after: process 2 logs 0 statements naming the session.
- `j2-<lab>:message` — a `SAY` line sent on process 1 is answered there; process 2's page draws the answer within 1 s of the send.
- `j2-<lab>:turn` — a `HOLD` line's turn on process 1: the conversation draws it running within 1 s of the store holding its request `in_progress`, and ended (no running mark, its answer drawn) within 1 s of the store holding it ended. A sample passes only when both ends do. The store is polled every 5 ms on the runner's own connection.
- `j2-<lab>:activity` — during that turn, the worker list (Teammates' status line under Chief of Staff, `Replying…`; Claude Code-style's sessions list, the session's `running` mark) draws it working within 1 s of the store holding the request `in_progress`.
- `j2-<lab>:task` — a `FILE` line's task runs on the scripted coder on process 1 and completes; the tasks view (Teammates' panel, under Done; Claude Code-style's Background tasks, a card `completed`) draws it settled within 1 s of the store holding it `completed`.
- `j2-<lab>:no-poll` — over 10 s from the page's first `crosses: true` frame and its opening reads quiet, before any line is sent, the page sends 0 requests.
- `j2-<lab>:no-timed-read` — over the same 10 s, process 2 logs 0 statements naming a watched session (one the page named in a request).
- Every graded change is written by process 1: each write the log holds naming a sample's answer, its request or its task is under process 1's `application_name`; one from process 2 is a setup error, never a sample.
- `j4:polls` — two processes of a Node stand-in for Next's server (`next-server.mts`) serving the route file's handlers: `GET /capabilities` reports no push, and B shows A's plan and seat (10 samples) under 4000 ms, the hooks' 3 s poll plus 1 s.

**Anti-game:** Never `publish` calls. Every grade reads what a page drew (a `MutationObserver` stamping each change in the page, or `waitForFunction` on the text), the requests and socket frames Playwright saw the page make, or the statements Postgres logged under a process's `application_name`; no counter inside the framework. Two forked processes, never two registries. The real Postgres bus, never `goals/lib/crossing-bus.mts`. The run sets no poll, timer or timed-read switch: the app names none, so what is off is off by default. `app/` hashes the same in both trees, printed. Each graded list is floored with `tell.over`; the lists whose emptiness is the claim say so. Under a high notice rate the "follows a notice" rule can't tell a timer from a woken read; `main-before` shows what the timer looks like there (reads with no notice at all). The Lab's two additions are named in Input; each is how shipped flows and Labs already are, and each is printed by the run as a scratch edit.

**Model:** n/a (handler actions; the run-lab's scripted runs; the labs' scripted model and scripted coder).

**Run:** `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers pnpm tsx goals/realtime/a-change-reaches-every-screen/run.mts`. `GOAL_SCENES=a,b,c,d,j2,j3,j4,j2-teammates,j2-claude-code-style` runs some (a, c and d always run together); the lab scenes build their lab's pages first. Needs `initdb`/`pg_ctl` (Postgres 16 under `/usr/lib/postgresql`) or `FSD_DB_URL` (the log-read assertions are then CAN'T TELL), and `redis-server` for j3.

**Controls:** each runs this file again; the patches are applied as the processes load (`goals/lib/module-patch.mts`), the lab processes' beside their store swap.
- `GOAL_CONTROL=memory-bus` — FIX-2427's `no-bus`: the Postgres adapter backs no bus, so each process gets the in-memory one. Must FAIL `a:org-state` and `a:org-row`. B never updates: since FIX-2545 the in-memory bus says it crosses, so B keeps no timer (the spec says the same). On both labs, must FAIL `j2-<lab>:message`, `:turn`, `:activity` and `:task`: process 2 never hears.
- `GOAL_CONTROL=no-request-publish` — FIX-2426's `no-publish` on today's module: the request and session store wrappers send no notice (scope-state, resource and board notices share the queue and still go). Must FAIL `d:plain-reply` (and `j3:worker-reply`), with leg a passing. Since FIX-2841 it also fails `j2:message`: Shift Manager's line is a request item, so with request notices cut it never shows. On both labs, must FAIL `j2-<lab>:message`, `:turn` and `:activity` (it also cuts the request's `run` notice on the user topic, which the worker sessions view hears), with `:task` passing.
- `GOAL_CONTROL=never-crosses` — FIX-2427's `no-listen`, its first hunk only (`#start()` returns), without the second that makes `crossesProcesses` say true: the bus never listens and never says it crosses, so the labs' views fall back to their timers. Run it on the lab scenes (`GOAL_SCENES=j2-teammates,j2-claude-code-style`). Its idle window starts once the page has seen `crosses: false` and its opening reads have gone quiet; on both labs it must FAIL `j2-<lab>:no-poll` and `:no-timed-read` on the requests and statements that window counts, each printed. A page that never says `crosses: false` is a setup error.
- `GOAL_CONTROL=skip-check` — FIX-2428's: the mint grants every session topic. Must FAIL `c:refused`.
- `GOAL_CONTROL=main-before` — today's `main`: the parent of FIX-2426's implementation merge (`db498b976`), extracted to scratch and installed, with `app/` copied in unchanged. Must FAIL every `a:` assertion and `b:no-read-between`. It runs neither lab scene, as it runs no j4: the labs' hosts on that commit predate the options the scenes serve them with.
