# realtime › app views read on a notice

**Issue:** FIX-2466, FIX-2545
**Outcome:** On a long-lived host, each app view this change moved shows a change another session made within a second, reads nothing between changes, and reads no more during a long reply than a short one; on a host whose bus doesn't cross, the same views still show the change within their old pace.
**Input:** One `serve()` host on a bound port over Kitchen Sink's workforce (its roster and worker flows declare the message log, the projects and their entries), a `desk` flow (`respond` writes `count` messages one at a time, after an optional hold; `logMessage`, `openProject` and `openEntry` write a message log row, a shared project and one of its workstream entries, as `sendMessage` and the project coordinator's open write them) and the claude-code-style lab's pins user resource (written through the default write flow since FIX-2624), one user behind a bearer token per view, on the default in-memory bus (no bus given: the router fills it), which covers an app that runs as one process (FIX-2545). The views, each on its own real client (Node's `fetch` and `WebSocket`) whose fetcher counts its reads: the claude-code-style lab's `watchThread` (running turn) and `watchPins`, the Teammates lab's `watchConversation` (answering), `watchWindow` and `watchTalk` (the Talk panel), Shift Manager's `followSessionItems`, the follow its conversation hook runs, Shift Manager's `useProjectRead` (a project's entries), and Shift Manager's task screen (`TaskProvider`) waiting on its run's link, each under its real `LabProvider`, rendered by react-dom over happy-dom and counted at the page's `fetch`. The task screen's task is filed through a Kitchen Sink coordinator conversation's `createTask_tasks`, waiting on a held task, and followed as after a board action; `updateTask_tasks` dropping that dependency lets the board dispatch it, and the dispatch writes the run's link to the row, which publishes a `board` notice. Leg c runs the same views on a host whose bus doesn't cross: FIX-2426's crossing double (`goals/lib/crossing-bus.mts`) set to `false`.
**Signal:**
- `a:within-1s` — after another client sends a slow turn into the watched session, the claude-code-style thread and the Teammates conversation report it running, Shift Manager's conversation shows its reply; after a pin the pins view shows it; after a message is logged the Talk panel shows it; and after a workstream entry is written the project view lists it; each less than 1000 ms after the write.
- `a:within-1s` (task screen) — the task screen shows the run the board links less than 1000 ms after the link's write.
- `a:lab-read` — a Lab read (Shift Manager's Refresh) reads the project's entries again within 1000 ms.
- `a:idle-0-reads` — over a 10 s idle window, each of the seven views makes 0 reads; and over 10 s waiting on its run's link, the task screen makes 0 board reads.
- `b:as-short` — during a 200-item reply each request view (thread running turn, Teammates answering, divider) makes the same number of reads as during a 2-item reply that takes as long, and Shift Manager's conversation makes none. The two replies last the same time so they differ only in items: how a request's own notices coalesce depends on how far apart they land.
- `c:within-poll` — with no crossing bus, the pins view shows a pin within 3 s + 1 s, the Teammates conversation a turn and the Talk panel a message within 1.5 s + 1 s, the project view an entry within 5 s + 1 s, and the task screen its run link within 2 s + 1 s.
- `c:fallback-reads` — with no crossing bus and nothing written, the Talk panel, the project view and the waiting task screen each still read over a 6 s window: the old pace runs where push can miss a change. (The in-process double delivers what it hears, so `c:within-poll` alone can't show it.)

**Anti-game:** Every assertion reads what a view reported or the reads its own fetcher made, never `publish` calls or frames sent. Real sockets on a bound port. Each graded list is floored with `tell.over`.
**Model:** n/a
**Run:** `cd goals && pnpm tsx realtime/app-views-read-on-notice/run.mts` (from `goals/`, whose `tsconfig.json` maps Shift Manager's `@/` imports)
**Controls:**
- `GOAL_CONTROL=timer` — each live read keeps a fixed timer beside its subscription (a scratch patch to the client's live read, `packages/client/src/live/live-read.ts`, which the labs' watches and Shift Manager's project entries and task run link are; Shift Manager's conversation follows the session stream). Must FAIL `a:idle-0-reads`.
- `GOAL_CONTROL=every-kind` — the live reads read on every notice on their topic, `items` included (a scratch patch to the live read's filter). Must FAIL `b:as-short`.
