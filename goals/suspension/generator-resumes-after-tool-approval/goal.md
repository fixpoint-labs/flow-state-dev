# suspension › it resumes a generator's tool loop after tool approval

**Issue:** FIX-814 (PR3)
**Outcome:** A tool running inside a live generator's tool loop asks for human approval mid-turn (a "publish" tool that gates before it acts), an operator approves, and on resume the SAME request continues past the approved call: the tool does its real work exactly once and the model writes a final answer that quotes the tool's real result. Not stuck suspended, not re-published on every resume, not answered from the approval payload instead of the tool. This is the end-to-end path a durable HITL agent sits on — proven here through the REAL AI-SDK `generateStep` adapter and its framework-owned tool loop, not a scripted mock.
**Input:** `fixtures/publish.json` — `{ title, confirmationId, approver }`. Held-out: the runner reads all three from the fixture. `title` becomes the user's publish request, `confirmationId` is the token the tool returns AFTER approval (the model never sees it otherwise), and `approver` is the operator payload injected on resume. Swapping them for any other valid triple must still pass a correct implementation (verified: a second run with a different title/token/approver passes with the new values). Nothing in the runner hardcodes the strings.
**Signal:** after resume, ALL of: (1) the final generator answer contains the held-out `confirmationId` — the tool's real, post-approval result; (2) the request reaches status `"completed"`; (3) the tool's side-effect counter is `0` at suspend and exactly `1` after resume; (4) exactly one real model call happened before the suspend (step 0), and the first model call on resume already carried the gated tool's result message (`toolResults ≥ 1`) — i.e. step 0 was replayed from the durable item log, not re-issued to the model.
**Anti-game:** the hollow pass is asserting a suspension was created, or `status === "completed"`, or that the resumed run returned any text. All of those hold even if the flow never re-ran the approved tool, re-ran it twice, or answered from the injected `approver` payload rather than the tool's result. The check MUST grade the final answer's **content** against the held-out `confirmationId` — a token the model can only emit if the gated tool actually executed **after** approval and its real result flowed back into the model on the next step. The `approver` payload is kept deliberately distinct from `confirmationId` so a payload-echo cannot pass (the check fails if `approver` appears but `confirmationId` does not). It also asserts the side-effect fired **exactly once** (a real state counter, not item de-dup) and that **step 0 was not re-called** (per-phase `generateStep` call count, with the first resume call carrying the tool result). It does **not** pass on the completion flag, the suspension's existence, item counts, or block traces.
**Model:** real — `openai/gpt-5.4-mini` (resolved as `vercel/openai/gpt-5.4-mini` through the Vercel AI Gateway, the gateway kitchen-sink is configured for). The whole point is exercising the real adapter's `generateStep` / framework-owned tool-loop suspension path; a mock model is the deterministic sibling in `packages/engine/test/generator-suspension-resume.test.ts`.
**Run:** `pnpm tsx goals/suspension/generator-resumes-after-tool-approval/run.mts`

> **Scope.** This drives the **warm** path: dispatch and resume in one process against the checkpoint durability provider (in-memory). It proves "generator tool suspends → approve → generator resumes past the gate with the tool's real result and no model re-call for step 0" — the FIX-814 PR3 regression. It does **not** cover a cold restart against a persisted store, nor the rejection branch (the deterministic engine suite covers both). Because a real model is nondeterministic, the flow uses a single obvious gated tool and a strong system prompt to reliably induce the tool call; the runner retries up to 3× if the model happens not to call the tool (no suspension induced) rather than reporting a false failure.
