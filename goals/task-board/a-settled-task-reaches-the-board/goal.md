# task-board › a settled task reaches the board

**Issue:** FIX-2429 (epic FIX-2367). Its spec's goal: `specs/issues/FIX-2429/SPEC.md` → "The goal, and how we'll know it's met".

**Outcome:** On a long-lived host, a change to a conversation's task board, written by any session on any process, shows on every open view of that board within a second, and a view reads nothing between changes. Wherever push can miss a change, the same views keep a timer and miss nothing.

**Input:** Real `serve()` hosts on bound ports, behind a bearer-token sign-in, and real WebSocket clients. One user's conversation on a Workforce session board (`desk`, worker `lead`), whose turn runs no model: it files tasks for a handler delegate (`eng.doer`, which takes 1.5 s), files a plan step for itself (a 1.5 s step turn), or streams a 3 s reply that touches no task. Four board views of the conversation, each on its own client: the Teammates lab's own hooks over harness-manager's coding board view, rendered by react-dom over happy-dom (`useTasks`, a task card's read, and `useTaskDetail`, an open popup's read of one task by `taskId`, open on the task the leg grades: FIX-2773), a live read of the merged `listTasks_tasks` view (`merged-view.mts`, as an app's `useView` keeps it, with no session stream beside it; the claude-code-style lab read the board this way until FIX-2628 moved it onto the coding board view), and a live `BoardList`'s read (`client.subscribe` on `topic.session(id, { resource: "tasks" })`, `listCollectionResources` on mount and on each wake, at its 3 s fallback pace). Legs a and c run in memory, leg a on FIX-2426's crossing double (`goals/lib/crossing-bus.mts`); leg b runs two registries over one real Postgres (`goals/lib/postgres.mts`), each with its own Postgres bus. Held out: a second conversation of the same user, whose task settles during leg a's idle window and must not read the first's board; every id is stamped per run.

**Signal:**
- `a:within-1s` — each view shows the delegate's task `completed`, and the Teammates view its run's link, less than 1000 ms after the change can be read from the store (polled every 5 ms). The task settles in its own task session.
- `a:plan-step` — the merged view shows the conversation's plan step `completed` less than 1000 ms after the store.
- `a:0-reads` — over a 10 s window, starting once every view's socket said `crosses: true` and the views have sent no board read for 1 s (the reads their opening owed are done), with a task held open and Teammates' popup open on it, each view makes 0 board reads (`/views/listTasks_tasks`, `/views/codingBoard`, `/resources/tasks`), while a reply streams in the conversation and the second conversation files and settles a task.
- `b:within-1s` — as `a:within-1s`, the task released and settled on process 2 (graded: the delegate ran there and nowhere else); the views are on process 1.
- `b:0-reads` — as `a:0-reads`, over 10 s from each view's first `crosses: true` frame (which on the Postgres bus waits for its first ping) and the views going quiet.
- `c:within-a-poll` — on a host with `push: false`, each view shows the task `completed` within its own poll interval plus 1 s (Teammates' card and popup reads 1.5 s, the merged view 2 s, `BoardList` 3 s).

**Anti-game:** Not `publish` calls and not frames sent: every grade is what a view's own callback or read returned, timed against the store, or how many board reads its client's fetcher sent. The socket taps only time the start of the idle windows. Real sockets against bound ports, not an in-process fetch; two registries for leg b, not two clients of one. Each graded list is floored with `tell.over`. The `BoardList` view drives the call shape `BoardList` makes rather than rendering React in Node; that the component makes exactly that call (the narrowed topic, its pace, a read on mount and on each wake, coalesced) is proven by `packages/react/test/board-list.test.ts`. The plan step is graded on the merged view only: Teammates' coding board view lists the conversation's tasks, not its plan.

**Model:** n/a, model-free (handler turns settle every task).

**Run:** `cd goals && pnpm tsx task-board/a-settled-task-reaches-the-board/run.mts` (from `goals/`, whose `tsconfig.json` maps the `@/` imports the lab's components make). `GOAL_LEGS=a,b,c` runs some legs. Leg b needs `initdb` and `pg_ctl`, or `FSD_DB_URL`.

**Controls:** each runs leg a with a scratch patch applied as the process loads (`goals/lib/module-patch.mts`).
- `GOAL_CONTROL=whole-topic` — the Teammates views (`useView`'s shared watch, `packages/client/src/view/view.ts`) and the merged view drop the board view's `hears`, so they hear every notice under the conversation's whole topic. Must FAIL `a:0-reads`, on Teammates' card read and on its popup's `taskId` read.
- `GOAL_CONTROL=tasks-only` — the merged view drops the plan's topics and hearings from the board view's answer, so it hears `tasks` alone. Must FAIL `a:plan-step` (graded on the merged view only).
- Today's `main` (the parent of this change) has no board notice and no `client.subscribe` in the labs, so this script doesn't load there; on it the claude-code-style list reads every 2 s whatever happens, which is what `a:0-reads` would catch. The three controls stand in for its red state.
