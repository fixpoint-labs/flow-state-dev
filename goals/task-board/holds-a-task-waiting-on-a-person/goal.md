# task-board › it holds a task waiting on a person

**Issue:** FIX-2129 (epic FIX-2058). Its spec's goal: `specs/issues/FIX-2129/SPEC.md` → "The goal, and how we'll know it's met".

**Outcome:** a task whose run suspends for a user shows what it waits for, is answered from the Inbox on the same try by that user only, and ends exactly once, whether it is answered, runs out of time, is cancelled or is stopped, a crash after the cancel included.

**Input:** a real `createFlowState` host on a durable SQLite store, with trace observability off (`FSDEV_TRACE_OBSERVABILITY=0`, production's default), and the Workforce session board on two flows: `desk`, the person's conversation that files tasks for `eng.doer`, and `doer`, whose task sessions do the work and file pieces for `eng.helper`. The doer is a deterministic script driven by marks in the task: its work is one step (the counter), then it asks. `[ask:approval|review|input]` calls `ctx.waitForUser` ("Ship the release?", "Review the draft.", "Which region?"); `[deadline:MS]` gives that call a deadline; `[catch]` goes ahead at an input's deadline; `[raw:REASON]` and `[raw:REASON:MS]` stop with `ctx.suspend` instead; `[file-first]` files a piece before asking; `[then-report]` and `[then-file]` report a checkpoint and file a piece after the wait comes back. Prompts, kinds and deadlines are inputs; others must pass too.

**Signal:** each failure is tagged `<leg>:<assertion>`.

- `a` (answered): past three lease periods and a board pass, `a:shown` `getTask` shows it `in_progress`, held by its run's stop (an open `source: "suspension"` hold in `holds`, FIX-2133) with kind `input` and the prompt, and `a:listed` so does `listTasks`; `a:kept` try 1, no lease, the work run once (no second worker took it); `a:notice-during-stop` the piece it filed before asking ended, and its `onTaskSettled` turn ran, while it waited; `a:message-while-waiting` a message to the session meanwhile ran at once, outside the task (no claim), and the task kept waiting (rule 10's behaviour today, pinned so FIX-2070's change is seen); `a:another-tenant` the same answer from a caller with the stop's user id in another tenant is told the stop doesn't exist (404), and from another org is refused (the host's org guard answers 403 before the route reads anything); `a:answered` the answer through the client call a screen makes is accepted; `a:once` completed on try 1 with the answer, the work run once; `a:item-closed` the item leaves the Inbox's pending read, and a second answer is told the stop is resolved (409).
- `b` (deadlines, each set on the call): `b:input-fails-try` an unhandled input's deadline throws `SuspensionTimeoutError` and fails try 1; `b:input-caught` a caught one completes try 1; `b:approval-no` an approval reads as a no with `deadline: true` on try 1, its work run once (the resume ran no completed step again); `b:item-closed` each item leaves the list.
- `c` (cancelled): `c:runs-on-once` the block resumes `{ cancelled: true }` once; `c:answer-after-cancel` an answer after the cancel is told the stop is resolved; `c:writes-refused` its progress write and its filing are refused; `c:stays-cancelled` the row is `cancelled` with no output and no open child; `c:item-closed`; `c:race-once` an answer and a cancel sent together resume the stop once and the task ends cancelled.
- `cprime` (a cancelled block files on its task session's board): a latch holds the filing right after a piece's add commits, and a claimer in another process, on the same store, touches that board inside the window. `cprime:never-claimable` no piece of the cancelled task is claimed or runs.
- `d` (stopped): the abort route on the run. `d:cancelled-on-try-1` the task is cancelled on try 1; `d:run-ends` the request ends `aborted`, nothing ran past the stop, the work ran once; `d:item-closed`.
- `e` (a crash after the cancel): a host in another process files a task, cancels it, and is killed (SIGKILL) right after the cancel's row write, before the resume. `e:killed-between` the row is cancelled and the block not resumed; after a restart, the dead host's resume lease (60 s) and a board touch, `e:resumed-cancelled` the block resumes cancelled and the item closes.
- `f` (the host's setting, `userDeadlineMs` set to 7,777,000 ms): `f:host-setting` a `waitForUser` with no deadline persists the host's deadline, on the stop and on the row's hold of it (`due`); `f:raw-keeps-its-own` a raw `ctx.suspend` keeps its own `timeoutMs` (5,555,000 ms), none meaning none. A held question (FIX-2133) reads the same setting: that half is `goals/task-board/waits-on-its-questions`, leg f.
- `g` (no deadline, the setting unset): `g:still-suspended` past twice the sweep's interval and a board touch, the request is still suspended, its stop pending with no expiry, the row waiting on the user with no deadline, and its item still listed.

**Anti-game:** no grade reads a store write the code under test made for itself, or the suspension record, to decide an ending: the task is read through the board's `getTask` and `listTasks` actions, the pending list through Shift Manager's own Inbox read (`readPendingSuspensions`, filtered as Inbox filters it), and every answer goes through the request handle's `answer`, the client call a screen makes. The work counter is a proof each worker appends from inside its own run, never an item count. Leg e kills the host process; leg c′'s claimer is a second process on the same SQLite file. The lease is shortened (a scratch patch, printed by the run) so three lease periods are seconds: that fakes time, not behaviour.

**Model:** n/a (model-free).

**Run:** `pnpm tsx goals/task-board/holds-a-task-waiting-on-a-person/run.mts`. `GOAL_LEGS=a,b,c,cprime,d,e,f,g` runs some legs; leg e waits out a 60-second resume lease. On demand only, never a CI gate.

**Controls:** scratch patches to the code under test, applied as it loads (`goals/lib/module-patch.mts`), printed by the run, and refused when they never reached the code.

- `GOAL_CONTROL=stop-fails-attempt`: a stop of a task waiting on a user fails its try (`task-entry.ts`, `cancelForStop` fails instead). Runs leg d. Must fail **`d:cancelled-on-try-1`**.
- `GOAL_CONTROL=public-resume`: the screen's answer goes through the public resume route (`client`'s `answer` posts to `/resume`). Runs leg a. Must fail **`a:answered`**.
- `GOAL_CONTROL=stored-user-only`: the answer route checks only the stored stop's user, not the resume path's tenant and org checks. Runs leg a. Must fail **`a:another-tenant`**.
- `GOAL_CONTROL=cancel-after-add`: today's order, the piece added and only then cancelled for its cancelled task (the refusal before the add removed). Runs leg c′. Must fail **`cprime:never-claimable`**: the latch forces the claimer into the window, and it claims the piece.
- `GOAL_CONTROL=default-deadline`: a stop with no deadline gets 1.5 s anyway. Runs leg g. Must fail **`g:still-suspended`**.

Today's `main` has no `waitForUser`: every leg but d fails at its first wait, and leg d's stop leaves the task `in_progress`, `keptOpenBy: "person"`, with no lease and no payer, for good.

FIX-2133's `reconcileInbox` (#3854) checks this kind's Inbox items; `goals/task-board/waits-on-its-questions` runs it with a task run's stop and row holds present (t9).
