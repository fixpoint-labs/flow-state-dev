# webhook-routing › it polls each event once without a webhook

**Issue:** FIX-2536 (epic FIX-2471); (m) to (o) FIX-2886
**Outcome:** With no webhook, a session subscribed to a thread hears each event on it once, within one poll period, through the same screens and delivery as push; nothing polls more often than every 5 minutes, one user's sessions on a thread share one fetch, and no user's poll reaches another user. A restart adds no poll, and a declared routine whose entry left config stops at its next poll.
**Input:** FIX-2534's fixture (`../delivers-each-event-once-to-its-subscribers/fixtures/`: 24 subscriptions over `alice` and `bob`, 300 normalized events) replayed as a provider's timeline, one event every 10 seconds from 10:00 (50 minutes), then a 30-minute tail. A fake GitHub provider answers each poll with the thread's events at or after the cursor's `since`, as the polling user, with an ETag per thread (`304` when nothing new is visible). The run's clock is moved (`clock.mts`), one minute a beat; each beat runs the app's own schedule tick (`createFlowState`'s `ScheduleTicker`) over a SQLite schedule index and the real dispatch endpoint (the router's built-in), over `sqliteStores`. Four legs, each on its own file:
- **leg 1** polled only, webhook off.
- **leg 2** polled, with each of 15 sessions' last expected delivery lost: 10 dispatches the store never records once, 4 takes that fail once (accepted, never taken), 1 dispatch lost every time. Each is a session's last event on its thread, so no later event on that thread can carry its retry.
- **leg 3** pushed (every event routed through `routeServiceEvent` at its time) and polled.
- **leg 4** alice follows the repository every 15 minutes and a PR at the default; the app declares an event routine on that PR, which the routines' own seed writes (`cfg_…`) on a roster run; a restart over the same file, with config that no longer declares it.

Leg 1 also runs (n) and (o), on two of alice's polls, each on a thread only one of her subscriptions follows, with no screen (the first such, and the busiest of the rest): from 10 minutes in, the provider fails the first fetch of the first that has something new, once; from 20 minutes in, it holds the first answer of the second that an event follows within a cadence, as it stood when asked, until the beat after its next fire came due. Before leg 1, a probe over its own file subscribes alice to the first poll's thread and reads the session id from her first fire's request record, so the run never derives it. `bob` is the second user.

Held-out: the expected set per session is the oracle FIX-2534's run restates, written again here and importing no screen or delivery code. For a subscription that unsubscribes (b7, at event 150), polled legs expect only what its user's poll had fetched by then: polling hears an event within one period, so a subscription that ends inside the period misses the rest of it, as the goal allows.
**Signal:** All of them, on one run:
- **(a)** each session's delivered service messages equal the oracle exactly, every leg (leg 2 less the never-taken one; leg 3 the push oracle, and no message twice);
- **(b)** no poll fires within 5 minutes of its last fire;
- **(c)** every poll's fires are exactly its cadence apart, every fire accepted (`202`): fires are the due entries;
- **(d)** reported: the polls answered `304` (unchanged), which deliver nothing;
- **(e)** each lost or never-taken-once delivery lands exactly once, on a later poll;
- **(f)** no poll ran as a user who can't read its thread;
- **(i)** the delivery lost every time is given up after three polls: nothing owed at the end, the mark past it;
- **(j)** a restart adds no poll and the polls keep firing; the removed declared entry's subscription ends `config_removed` at its next fire, with no roster run in between, while the session's own subscription on that thread stays on;
- **(k)** the 15-minute poll fires 15 minutes apart, and a cadence of 3 is refused;
- **(l)** no user fetches a thread twice within a cadence, alice's two sessions on #412 included;
- **(m)** every leg: each poll's accepted fires name one session in their request records; it carries the schedule session prefix, its row belongs to the poll's user on the service flow, and its request listing (`GET /api/flows/sessions/:id/requests`, as the DevTool reads it, as that user) returns every accepted fire; no two polls share one, and across leg 4's restart each poll keeps its one; the service flow holds no `ephemeral_` session on any leg: leg 3's pushed deliveries run in the service's routing session (`service-route:…`) and each owner's run session (`owner-run:…`), not one-off ones, so the spec's "one per pushed event" reads zero here;
- **(n)** leg 1, before alice's first fire: bob's `POST /api/flows/github-service/sessions` at her poll's session id is refused; his creates on his own flow (`follower`) with the id split across `x-tenant-id` (the part before its first `:`, or after the prefix for a colon-free id) and the rest as `sessionId`, and with the two joined as `"<tenant>:<id>"` and no header, leave no session at that id. After: the probed id is the session her poll ran in, bob's action to it and read of its state are refused, it is alice's, and her poll delivers as the oracle says. The fire whose fetch the provider failed ended `failed`; alice's `POST …/requests/:id/retry` of it is refused, her session's listing marks it `retryable: false`, and each event the failed fetch missed lands once;
- **(o)** leg 1: the fire due while the held one runs is answered `skipped` (the one fire (c) lets answer other than `202`); no poll's session ever has two requests whose runs overlap (each request's `startedAtMs` to `finalizedAtMs`, from the store); the two events after the held answer's time land once each, fetched by a fire after the skipped one.

**Anti-game:** assertions read stored message-log entries, schedule resources and subscriptions, and the provider's own record of who fetched what; nothing counts a function call in the code under test. Each graded list is floored with `tell.over`, so an instrument that saw nothing reads CAN'T TELL. Losses are chosen by rule (each session's last expected delivery, in fixture order), not by seed, and the lossy leg's planned losses must all happen or the run fails. (m) to (o) read request records and session rows from the store, listings and refusals from the owner HTTP routes, and the dispatch endpoint's own answer to each fire; the run recognises a schedule session by its prefix and never imports the id's derivation. The probed id is graded as the one alice's poll runs in, so (n)'s attacks can't aim at a different id and pass.
**Model:** n/a (model-free: no generator or evaluator is on this path)
**Run:** `pnpm tsx goals/webhook-routing/polls-each-event-once-without-a-webhook/run.mts` (about ten minutes)
**Controls:**
- `GOAL_CONTROL=poll-per-subscription` keys a poll by subscription, not by user and thread. Must FAIL **(l)**.
- `GOAL_CONTROL=mark-moves` moves the mark to the poll's end whatever is owed. Must FAIL **(e)**.
- `GOAL_CONTROL=walk-all` claims every poll each beat, due or not. Must FAIL **(b)**/**(c)**.
- `GOAL_CONTROL=under-floor` fires every poll each minute. Must FAIL **(b)**.
- `GOAL_CONTROL=hold-forever` never gives a delivery up. Must FAIL **(i)**.
- `GOAL_CONTROL=etag-while-held` sends validators while a delivery is owed. Must FAIL **(e)**.
- `GOAL_CONTROL=keep-removed` ignores the declared list at a fire. Must FAIL **(j)**.
- `GOAL_CONTROL=ignore-cadence` polls every subscription at the default. Must FAIL **(k)**: leg 4's 15-minute poll fires 5 minutes apart (reported as leg 4 · c, the cadence check).
- `GOAL_CONTROL=session-per-fire` the service flow's poll resolver names no session. Must FAIL **(m)**; today's `main` behaves this way.
- `GOAL_CONTROL=no-reserve` the create route takes a schedule session id from a client. Must FAIL **(n)**, on bob's create.
- `GOAL_CONTROL=colon-id` the schedule session id joins its parts with `:`. Must FAIL **(n)**, on the split create.
- `GOAL_CONTROL=reentry-open` retry, continue and resume skip their schedule-session check. Must FAIL **(n)**, on the retry and the listing's `retryable`.
- `GOAL_CONTROL=overlap-allow` the poll schedule is written with `onOverlap: "allow"`. Must FAIL **(o)**.
- (n)'s refusal of bob's action to alice's poll session has no isolating red state: the action route's reserved check, the host's reserved-address refusal and the session's owner and flow each refuse it, and with every reserved check off (`isScheduleSessionId` returning `false`) it is still refused. The probed-id check and the state read went red only under a mutation of this run (the probe reads the other troubled poll; the read goes as alice).
- Today's `main` has none of the API this run imports, so it stops before grading; not run as a control.

Not in this run: the spec's (g)/`no-screened` (a refused version judged once) and (h)/`outage-screened` (a screen down, then up) need a screen that can be down, which FIX-2537's evaluator screen brings; unit tests cover `screened` (`packages/workforce/test/subscriptions-poll.test.ts`). Leg 3's count of push refusals a poll judges again is not reported.
