# workforce-conventions › its code comes from files alone

**Issue:** FIX-1357; re-pointed by FIX-1611
**Outcome:** Someone adds workforce code to their app by writing one file — a tool block in `workforce/blocks/`, or a worker kind in `workforce/flows/workers/` named from a `WORKER.md` — and it registers and runs. Nothing is written anywhere in the app's source to wire it — not on a `hireWorkforce` call, not in a barrel, not in a registry line — and the app behaves the same deployed as it does locally, because what registers the code is a committed module of static imports rather than a scan that happens while the app runs.
**Re-pointed (FIX-1611).** Until FIX-1611 the whole check ran on kitchen-sink's `desk-clerk` kind and `desk-note` block, with `support.ada` and `support.grace` answering from their desks. The app now carries one piece of workforce code, the `escalate` tool block, and no custom kind. So the Next-built half rides `escalate`, through the same generated module, and the kind half moved to a fixture host in this folder: two seats on one custom kind, differing by a setting. Nothing the check proves was dropped; the build leg no longer counts a kind, because the app has none to count.
**Input:** Two subjects. **The app:** `apps/kitchen-sink/workforce/`, whose `blocks/escalate.ts` is on the committed `workforce.gen.ts` and named in each specialist's `tools:`. **The fixture host:** `fixtures/workforce/`, one team (`support`), two seats (`ada`, `grace`) whose files both name `flow: desk-clerk` and declare different `desk:` values, one custom kind at `flows/workers/desk-clerk.ts`, and its committed `workforce.gen.ts`. Held out: each run's filing carries a fresh `case-token-…`, and `desk` is declared only in the two `WORKER.md` files and read only by the kind's own schema — nothing in the runner supplies it.
**Signal:** Four legs. **(a)** After a real `pnpm build`, a name only the block's module carries (`escalate-file`) appears in the compiled chunks under `.next`, with the three hand-wired flows as the positive control on the same probe. **(b)** Over the real HTTP route **against the app as built for Next**, a person's post routed to `support.devices` with `[scenario:needs-a-person]` leaves a row carrying the run's token on `support.help`'s `escalations` board, read back over the route the team panel reads. **(c)** A scan of `apps/kitchen-sink/**` outside `workforce.gen.ts` finds nothing that names the block or imports its module. **(d)** On the fixture host, `fsdev gen --check` agrees the generated module is the tree's, both seats hire from that module's `kinds` map onto `desk-clerk`, and each one's `answer` names the desk *its own file* declared (`front` for ada, `back` for grace). PASS prints the chunk counts, the filed token, the scanned file count and both answers; any mismatch is a FAIL.
**Anti-game:** A hollow pass would assert that the tool call returned, or that two seats came back — both survive an implementation that wired the block by hand, or hired every seat onto one shared configuration. So (b) grades a row only the block can write, read back from the board rather than from the model's claim, and (d) grades a value only the discovered kind declares and only each seat's own file supplies: the two seats sit on **one** kind and differ only in `desk`, so anything keyed by kind rather than by seat gives both the same answer and fails. The runner reaches the fixture's kind only through the generated module, and says so by checking its own imports. The source scan is the inverse probe — it fails if the block reaches the catalog by any route other than the generated module. It scans **registration routes**: every source file under the app except `test/` and `e2e/`, the scripted model (`lib/e2e-mock-script.ts`, which names the tool to call it) and the `no-filing` control (`lib/escalate-control.ts`, which imports the block's input schema to build a test-mode stand-in, held inert outside test mode by `test/goal-control.test.ts`). None is served as the block; a hand registration anywhere else still fails the leg. Running (a) to (c) against the **Next-built** app rather than the source tree is what makes them a check of the decision: a design that scanned the tree at run time passes on plain Node and returns an empty map here. Leg (d) runs on plain Node by design: the Next-built half is (a) to (c)'s, through the same generated module.
**Model:** scripted for the app; none for the fixture host. `next start` runs with `KITCHEN_SINK_TEST_MODE=1`, keyless: the scripted route picks `support.devices` and the scripted model calls `escalate`. The fixture's kind answers with a handler.
**Run:** `pnpm tsx goals/workforce-conventions/code-comes-from-files-alone/run.mts`
**Controls:** on the same command.
- `GOAL_CONTROL=no-filing` (the app's, test mode only): `escalate` swapped for a stand-in that says it filed and files nothing. Must FAIL at **b**, and at nothing else.
- `GOAL_CONTROL=shared-settings` (this runner's): both fixture seats hired on the first seat's settings. Must FAIL at **d**, and at nothing else.
- **The planted registration** (by hand, recorded below): a file under `lib/` importing the block's module. Must FAIL at **c**.
