# workforce-conventions › a hired team survives a redeploy

**Issue:** FIX-1475
**Outcome:** Someone hires a team into a running app over its ordinary HTTP route, redeploys, and the team is still there — the seats answer at the same addresses, carrying the settings the hire supplied rather than any default. Hiring writes the seat down; the next start reads it back. A stored seat the current code can no longer run costs one seat, not the deployment.
**Input:** `apps/kitchen-sink`, built for Next and served by `next start`, with `STORE_TYPE=filesystem` so one store outlives the process, and `WORKFORCE_ADMIN_TOKENS` configuring an admin credential for two organizations (`acme`, `bravo`). Held out: the settings of the seat leg 3 grades are a **token generated at check time** — nothing in the app, the tree or this file can supply it.
**Signal:** Six legs on one run. (0) the file-declared `support.ada` answers naming its own desk, asserted first and re-asserted after every restart. (1) a hire over `workforce-admin` answers straight away in the hiring process; a hire naming a kind the app does not carry is refused and leaves no address. (2–3) a seat hired with a check-time token answers **after a restart** and its answer carries **that token**. (4) a stored row edited to name a kind the code does not carry leaves the app serving, the other seats answering, that one address 404ing, the boot naming the skip, and the bad row unrepaired. (5) firing the token seat and restarting leaves a 404 that no start brings back. PASS prints the token seat's answer, the degrade evidence and the fire evidence; any mismatch is a FAIL.
**Anti-game:** A hollow pass would assert that the seat answered 200 after a restart — which an app that re-read the same `WORKER.md` files, or hired every seat onto one shared default, passes without storing anything. So leg 3 grades a value **only the stored row can carry**: a token minted by this run, sent in the hire's settings, and read back out of the answer. A seat coming back on a file-declared default or a kind's own default cannot produce it. The store directory is **removed before the run**, so a roster an earlier run left behind cannot be what passes. The file-declared control in leg 0 is the inverse probe: it is asserted before everything and re-asserted after every restart, so a zero on a durability leg is distinguishable from an app that simply is not serving. Leg 4 edits a row **the app itself wrote** rather than fabricating one, because a fabricated row tests the parser while the real failure is a kind deleted from the source after the row was written. Running against the **Next-built** app rather than the source tree is what makes it a check of the decision: a roster read lazily on first request, or held in module memory, behaves differently across a real process boundary.
**Model:** none — the seat's action is a handler that reads its own settings; no model is contacted.
**Run:** `pnpm tsx goals/workforce-conventions/durable-hire-survives-redeploy/run.mts`
