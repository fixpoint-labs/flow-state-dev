# workforce-seats › a non-agent seat receives its skills

**Issue:** FIX-1367 (thin `WorkerConfig` admission for hireable kinds; builds on FIX-1356's skills file convention and FIX-1325's seat factory)
**Outcome:** An app defines a worker flow with **no model and no generator in it**, composes the admission contract into its settings schema, and runs two workers on one registered copy of it, from a workforce tree that declares skills at three levels — an `org/skills/` folder, a team's, and one beside a worker. Each worker runs an action to completion through the real HTTP route, in a session naming it, and a block **nested inside that action** reads the skills its own folders declared off the turn's worker, in level order. Neither worker holds the other's team-level or own-folder skills; both hold the org folder's. With the contract stripped from a flow, the whole installation refuses at boot, the message names the worker, the flow and the missing key, and nothing is registered. Rewritten for FIX-1788: workers are data on one copy of their flow, and a turn reads its worker through the installation.

**Why a non-agent flow.** The claim is about *every worker flow*, not about the built-in `agent`. An end-to-end run of the agent would be green for a mechanism that only ever worked on the one flow that happened to declare the key. The flow here calls no model, so a pass cannot be coming from anything an agent does.

**Input:** `fixtures/input.json` — the two worker ids, each one's own setting, and the skill names each one's folders declare. `fixtures/workforce/**` carries the same thing as files: `org/skills/house-style/`, `teams/support/skills/triage-tone/`, `teams/support/workers/desk/skills/escalation/`, `teams/billing/skills/dunning/`, and a `WORKER.md` per worker. `fixtures/no-contract/` is the control tree. Held-out: every id, setting and skill name is read from the fixture and graded against what the running blocks reported, so swapping any of them still passes a correct implementation. **Each worker's own setting differs from its schema's default on purpose** — a setting dropped on the way to the turn would otherwise read back as the default and pass.
**Signal:** against the real HTTP router (`createFlowApiRouter`) over on-disk SQLite stores, matching its siblings in this family. The records come from the real loader (`readWorkforce`), never hand-built: the folders are half of what is under test.
(a) `readWorkforce` reads the tree with no errors and produces two records; `hireWorkforce` registers one copy of the non-agent flow, at its kind.
(b) Each worker's session is created naming it, and runs `POST /api/flows/<flow>/<session>/actions/run` to completion. After closing the stores, reopening the same file and building a fresh host, `GET /api/flows/sessions/<session>/state` shows what a block **nested inside the action** read from the turn's worker: its own skill names as a **sequence** in level order (org, team, own), and its own desk.
(c) Neither worker's list equals the other's; neither holds a skill from the other's team or worker folder; both hold the org folder's.
(d) A flow whose schema omits only `seatSkills`, with one worker on it: `hireWorkforce` throws, naming the worker, the flow and `seatSkills`, and says nothing was registered. It omits **one** contract key rather than all of them on purpose — a control that drops the helper drops every key with it, and its refusal would then be equally consistent with a check on whether the helper was called. It also runs its **own action set**, requiring no setting: a block that required `seatSkills` would refuse it on its own.
(e) A hand-written schema that never calls `workerConfigSchema()` but takes everything a worker is handed registers, and its worker's turn carries `seatSkills`. It runs the same action set as (d), so the pair differs in exactly one thing: whether its schema declares `seatSkills`. This is what makes (d) mean what it says: admission is decided by what a schema takes, not by which helper built it.

**Anti-game:** a hollow pass would assert the hires returned and the requests completed — true even when every seat holds an empty catalog, or one shared one. So the check MUST read the skills back through `/state` rather than off the returned instance, because the claim is that the bag reached a RUNNING BLOCK; MUST read from a **nested** block rather than the action root, since a root-only read proves nothing about the context spread that carries the value down; MUST close the stores and rebuild the host first, so nothing is served from a live context; MUST compare the names as an ordered **sequence**, since a set check passes for a bag assembled backwards and level order is part of the promise; MUST assert each seat does NOT hold its sibling's folders, since one shared bag is always right for somebody; MUST use a kind with no model, since an agent run cannot distinguish the contract from the agent kind's own path; MUST assert the control refusal registered **nothing**, since a refusal after a partial registration is not a refusal; and MUST keep the control pair off any action set whose blocks require `seatSkills`, since such a block refuses the control on its own and lets the pair pass while hiring imposes nothing. That last property is checked statically by `goals/scripts/validate-control-shape.mts` (rule C4).
**Model:** n/a — handlers only, by construction. The property under test is which settings reach a running block.
**Run:** `pnpm tsx goals/workforce-seats/a-non-agent-seat-receives-its-skills/run.mts`
