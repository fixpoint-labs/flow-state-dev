# workforce-seats › two seats run their own configuration

**Issue:** FIX-1325 (the seat factory; builds on FIX-1321/1322 cardinality and instance ids, FIX-1323 instance-isolated state, FIX-1331 per-copy settings)
**Outcome:** An app defines two worker flow kinds in code and hires two workers — one opinionated, one thin. Each becomes a copy addressable by its own id, behaving according to the settings its own record declared and none of its sibling's, still true after a restart. The opinionated worker's record body reached its flow as `persona` and a block nested inside its action ran on it. The thin worker is a fully addressable seat that runs to completion carrying no persona at all. A record naming a kind the app didn't define, a record declaring a setting its flow never offered, and a body handed to a flow kind that never declared one all refuse at the hire, with nothing hired and nothing registered.

**Where the records come from — stated by the run, not chosen by hand.** The two records are produced by the real loader (`readWorkforceDirectory` over `fixtures/teams/`, one folder per worker) when `@flow-state-dev/workforce/loader` exists, and hand-built exactly as `WorkerManifest` declares them when it does not. The selector is the presence of that export — nothing here is a judgement call — and the run prints which source it used as its **first line of output**, repeated in the verdict log below, so a reader can tell which bar a green run cleared without reading the script. Every clause below binds both paths, refusal cases included: the fixture tree is a stronger source for the same records, not a replacement for the checks.

**Input:** `fixtures/input.json` — the two worker ids with the settings and body each declares, and the three bad records (an unknown kind, an undeclared setting, a body on the thin seat). `fixtures/teams/**/WORKER.md` and the three refusal trees beside it carry the same records as files. Held-out: every id, setting and marker is read from the fixture and graded against what the HTTP routes return afterwards; swapping any of them must still pass a correct implementation. **Each declared setting differs from its flow's schema default on purpose** — a setting that was dropped on the way to the flow would otherwise read back as the default and pass.
(0) Before anything runs, every `WORKER.md` in the fixture trees is compared against `input.json` key by key and body by body — whole values, not substrings. The two roster sources cannot drift apart unnoticed, which is what keeps whichever path is *not* running from quietly weakening.
**Signal:** against the real HTTP router (`createFlowApiRouter`) over on-disk SQLite stores, matching its siblings under `goals/flow-instances/`.
(a) One `hireWorkforce` call turns the two records into two flow copies, ordered by id, each carrying its own record's id as its address — not its flow kind.
(b) Each seat runs `POST /api/flows/<id>/<session>/actions/run` to completion. After closing the stores, reopening the same file and building a fresh host, `GET /api/flows/sessions/<session>/state` shows each seat what a block **nested inside its action** read from `ctx.flow.config`: for the opinionated worker, its record's body as `persona` and its own model; for the thin worker, its own desk, no persona, and no model. Neither shows the other's value.
(c) `POST` against the bare flow kind — `worker-agent`, `intake` — is a 404 for both. The kind is not an address.
(d) Three bad rosters, each hired alongside the good records: an unknown flow kind, a setting the flow never declared, and the thin record with a body added. Each throws, naming the worker and the offending thing (`persona` for the third), returns nothing, and leaves the good worker's address a 404 on a host built from what came back.

**Anti-game:** a hollow pass would assert the hires returned and the requests completed — true even when both seats share one settings bag and one silently wins. So the check MUST read the settings back through `/state` rather than off the returned instance, since the question is whether the value reached the running blocks; MUST read them from a NESTED block rather than the action root, because a root-only read proves nothing about the context spread that carries the value down; MUST close the stores and rebuild the host before reading, so nothing is served from a live context; MUST assert each seat's sibling value is **absent** as well as its own present, since one shared bag is always right for somebody; MUST address each worker by the exact id its record carried, since grading `flowKind` proves nothing — both workers of a kind share it; MUST assert the bare kind 404s, since that is the address the slash-separated identity would have answered on; and MUST assert every refusal left **nothing** registered, since a refusal after a partial hire is not a refusal. Thinness is graded as a **pair**, one half positive and one half a refusal — the thin seat is live and runs, *and* adding a body to that same record refuses by name — because "carries no persona" alone is satisfied by never hiring the worker at all.
**Model:** n/a — handlers only. The property under test is which settings reach a running block, not model output; a generator here would add a model call and prove nothing more.
**Run:** `pnpm tsx goals/workforce-seats/two-seats-run-their-own-configuration/run.mts`

> **On the body's whitespace.** The persona is graded trimmed on both sides. What travels verbatim is the instructions; the newline a Markdown file ends with belongs to the file, and pinning it would make this goal a test of the loader's trailing-whitespace policy rather than of the body's journey.
