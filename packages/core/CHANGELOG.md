- fad96df: Resource and collection handles now infer their state from the schema passed to the definition. A conditionally declared resource remains optional when read by property on `ctx.resources`. - 7ac7f90: A scope is how many copies exist; the owner decides who may look; name a session to reach its copy (FIX-2942).

  - **`ctx.resources.at({ session }).<name>`.** A block reads, lists and writes another session's copy of a session-scoped collection, with its own flow's definition at that session's address: `ctx.resources.at({ session: launchChatId }).notes.list()`. Every verb acts on that one copy. Writes are versioned like a local write; two sessions writing one copy conflict the way two local writers do, with no cross-session lock.
  - **Only the owner's sessions.** The session is reached only when the HTTP routes would admit the run's principal to it. A session of another user, org or tenant, one with no org, one an own-resolver flow refuses, and an id no one holds all answer every verb the same way: rejected with `SessionNotFoundError`. A schedule's or a webhook's machine principal reaches no other session.
  - **The session written hears it.** A write publishes on that session's change-bus topics, as its own write would, never on the caller's. It starts a turn there only when the collection declares `wakeEntry: "<internal entry>"`: the write owes a wake on that session and entry before it is written, and writes under one resolver that land before it runs fold into one turn. That entry reads what changed and settles its wake like any wake entry. If the wake can't be owed, nothing is written and the write rejects; a write that fails after its wake was owed leaves one turn that finds nothing new. A turn that runs before the writing request's lease is up and finds nothing new holds its wake to the lease, so expect one more, empty turn then. A write into a session whose flow doesn't declare the entry is refused, naming the entry. The session's `reactTo` blocks don't run inside the writer's turn.
  - **Webhook turns are fenced.** A turn a webhook delivery started, or a run it fired, can name no session but its own: every verb is refused with `UntrustedReachError`. Both errors are exported from `@flow-state-dev/engine`, so a block can catch them by type.
  - **Single resources and projected collections** can't be reached this way yet; naming one throws, and with declared resources it doesn't compile: `at()` is typed to the session-scoped collections (a collection ref now carries its declared scope, `ResourceCollectionRef<State, "session">`).
  - **Flow construction checks.** `at` is a reserved resource accessor, and two session collections whose patterns overlap can't name different `wakeEntry`s.
  - **Use `ctx.sessions`** for what isn't a resource: another session's flow, readable state, history and turns.
  - **Wakes are kept per resolver.** A wake's key is now (tenant, session, entry, `resolvedBy`), with no resolver a key value of its own: `WakeKey` carries an optional `resolvedBy`, and `get`, `move` and `clear` act on that one wake. A woken run carries its wake's `resolvedBy` for the whole turn and reaches the own-resolver sessions that resolver admits; it reads and settles only its own resolver's wake. The cost: a burst of writes from principals of different resolvers starts one turn per resolver, not one in total. A burst under one resolver is still one turn. A `WakeStore` adapter outside this repo must key its wakes the same way.
  - **Schema migration for `wakes`.** SQLite and Postgres re-key `wakes` on start, adding `resolved_by` (`''` for none) to the primary key; SQLite rebuilds the table in one transaction. A wake stored before names no resolver, keeps coalescing with the other such wakes, and reaches no own-resolver session.
  - **Sessions record a per-birth `incarnationToken`.** It tells a session id deleted and taken again apart from the session it replaced, even within one millisecond. Every session store's `set` writes it once and keeps it, like `principalKind` (the SQL stores through `writeOnceJsonKeys`). A store adapter outside this repo must do the same. A session from before the field has none and is compared by its birth time and lineage.

  - **The two errors, for `packages/engine/README.md`.** `SessionNotFoundError`: a named session this run may not reach, or that no one holds, with one message for both. `UntrustedReachError`: a turn a webhook delivery started named a session other than its own.

  Docs: packages/engine/README.md (`SessionNotFoundError`, `UntrustedReachError`), apps/docs resource guides (a "Another session's copy" section beside `ctx.sessions`, with `wakeEntry` and the webhook fence), and the store adapters' schema notes for the `wakes` key, which now includes `resolved_by`.

- 16e6852: One read of a collection across every session its owner has, in one query a page, heard on one change topic (FIX-2945).

  - **`ctx.resources.acrossSessions().<name>.list({ after, where })`.** A block, a user-scope view's included, reads one session-scoped collection across all of the run's owner's sessions: `const page = await ctx.resources.acrossSessions().notes.list()`. Each entry in `page.entries` is `{ session, key, value }`: the session it belongs to (as `ctx.resources.at({ session })` takes it), its storage path there, and its state. Read-only.
  - **Paging.** A page holds up to 50 entries. Pass `page.next` as `after` for the next one, and stop only when `next` is absent: a page can be short, even empty, while `next` is set. `next` is opaque and names no entry. Any other `after` is refused with `AcrossSessionsCursorError`, which a view call answers as `400 invalid_cursor`: start the listing again.
  - **`sealingSecret` (default `FSD_SEALING_SECRET`).** A new option on `createFlowState` and `createFlowApiRouter`: the host's secret for sealing a read's cursor, from which the cursor key is derived. Every process with the same secret opens a cursor another handed out. Without one, each process uses a key of its own, which is right for one process. **A host that runs more than one process behind one address (a serverless deployment, a cluster) must set the same secret on every process**, or a client's next page fails on another process with `invalid_cursor`.
  - **Filters.** `where: { key }` reads the entry at that path in each session; `where: { index, value }` reads a collection's declared index. A field with no declared index is refused, naming it: declare the index in the collection's `indexes` to filter on it. A session's declared indexes are now built at its first write that carries them; a session written before this release is built by the filtered reads that meet it, a few sessions per request, so the first reads after an upgrade stay quick and stay correct while the rest are built.
  - **Only the owner's sessions.** A session is answered only when `ctx.resources.at` would reach it: the same user, organization and tenant, and the same admission (an own-resolver flow's sessions, a machine's run). Any other session is left out as though it held nothing. A turn a webhook delivery started is refused with `UntrustedReachError`. A collection whose entries are lineage-shared can't be read this way.
  - **Notices.** In a view, the read is heard on one change topic per collection pattern and owner. Every write to any session's resources at a key the pattern covers wakes it, whatever the writing flow declares, so the view wakes for an entry filed in a session made after it ran. A deleted session's entries leave the view too. A client sees it as the user topic narrowed to `/sessions/<view flow>/<collection pattern>`; the same user in another organization never hears it, a write in a session the read would leave out (a flow whose own sign-in didn't sign the caller in for this view, or a pin they fail) wakes nothing, and a notice on it names no session id, no entry key and no request.
  - **Reserved accessor.** `acrossSessions`, like `at`, is a reserved resource accessor: a flow that declares a resource under that key is refused at definition. The registry `ctx.resources.at({ session })` returns has no `acrossSessions`.
  - **For store and bus adapters.** `ResourceStateStore` gains an optional `listAcrossSessions(query)`, one page joined to the session store on the full owner; without it the read is refused. `createInMemoryResourceStateStore` and `createFilesystemResourceStateStore` take `{ sessions }` for it (the registry factories pass it). A change-bus topic's `scope` can now be `"owner"`, the bus's own scope for these change topics; an adapter that treats the scope as an opaque string needs nothing.
  - **Schema.** SQLite adds `idx_sessions_owner`; Postgres adds `idx_sessions_owner` and `idx_sessions_tenant_owner`, built concurrently on start.

  - **The error, for `packages/engine/README.md`.** `AcrossSessionsCursorError`: an `after` that isn't a cursor this read handed back, under this host's sealing secret.

  Docs: packages/engine/README.md (`AcrossSessionsCursorError`, the `sealingSecret` option and `FSD_SEALING_SECRET`), the deployment guides (`FSD_SEALING_SECRET` beside `FSD_PUSH_SECRET`, required on any host with more than one process), apps/docs resource guides (a "Looking across sessions" section beside the one on reaching another session's resources: the call, paging with `next` and restarting on `invalid_cursor`, the two filters, the reserved accessor, and that a view using it hears sessions made later).

- 61efa05: The app fires its own schedules (FIX-2752). One tick in the engine fires every schedule of every flow, static and dynamic, once per scheduled time. A long-lived server or `fsdev dev` needs no outside cron, several servers on one store tick from one process, and a serverless host adds one route. The five old ways to fire a schedule are removed, with no aliases.

  - **engine:** `createFlowState` takes `scheduler`. Omitted, a built-in local cron ticks each minute in a process that serves the app (`ready()`, `getRouter()`, `serve()`, `fsdev dev`) or works a job queue, never in `fsdev run`, `fsdev chat` or `fsdev block`, and only when a flow declares a static schedule or a schedule index. It ticks only while it holds a lease in `stores.leases`, so one process ticks across servers that share a SQLite or Postgres store; if that process dies, another takes over within three minutes. In production on in-memory or filesystem stores it warns at start: run one server, or use SQLite or Postgres. `scheduler: false` fires nothing; a `SchedulerAdapter` (from `@flow-state-dev/engine/host`, with `ScheduleTicker` and `ScheduleTickReport`) decides when the tick runs. After downtime each schedule fires once, late, for the latest time it missed; earlier missed times are dropped. On Vercel with the local default, startup warns to pass `vercelScheduler()`.
  - **vercel:** `vercelScheduler({ secret? })` is the scheduler for Vercel: pass it as `scheduler` and export its `route` as the `GET` of one route that one Vercel Cron entry calls (`CRON_SECRET` by default; an empty secret refuses every call). Each call fires every due schedule of every flow, each as its own request to the deployment the call reached, and answers 500 when a schedule index fails so the next beat retries. `createGetToPostCronShim` and `createScheduleTickHandler` are removed, with the `@flow-state-dev/vercel/schedules` entry: replace each per-schedule cron entry and route, and each per-flow tick route, with the one route. A once-a-minute beat needs Vercel Pro; a daily beat (Hobby) fires each schedule once a day, late.
  - **bullmq:** `registerStaticSchedules`, `createScheduleDispatchProcessor` and `createBullmqScheduleIndex` are removed, with the `@flow-state-dev/bullmq/schedules` entry. A BullMQ deployment wires nothing for schedules: the local cron runs in its job-queue processes too, elected by the shared store's lease. A static schedule's fire is enqueued like any action, with the queue's retries; a dynamic schedule's fire runs in the process that ticked, since its block can't ride a job, so it has no queue retries and a crash mid-run loses it. Dynamic schedules use the SQLite or Postgres schedule index. The pending rename of `createScheduleDispatchWorker` to `createScheduleDispatchProcessor` in this release ends in this removal.
  - **node:** `serveScheduleTicks` is removed. `serve()` no longer ticks schedule indexes itself; the app's local cron fires static and dynamic schedules alike.
  - **scheduled:** `runScheduleTick`, `startScheduleTick` and `scheduleDispatchRequest` are removed from `@flow-state-dev/scheduled/collection` (the tick is the engine's), and `formatScheduleId` from the package root (it is core's). The pending note that added the first three in this release is superseded by this removal.
  - **core:** `formatScheduleId(orgId, userId, key)` is exported from `@flow-state-dev/core`. `ScheduleDueEntry` names `cron` and `timezone`, so a custom schedule index returns the cron and zone each row already carries.

- ec99b11: A file attached to a message is uploaded once and travels by reference. Its bytes stay out of session reads and survive a restart wherever the sessions do (FIX-824).

  - **engine:** `POST /api/flows/blobs` takes one file as the raw request body. `POST /api/flows/<flow>/blobs` does the same under that flow's own sign-in: use it when a flow sets `authentication.resolvePrincipal`, so the file is held for the user its sends resolve. The `content-type` header is the file's type, and the `filename` query parameter is its name. It answers 201 `{ attachment }`, a `FileContent` whose `data` is a reference (`fsd-blob:<id>`), not the bytes. It refuses an unsupported type (415 `attachment_type_refused`), a file over the limit (413 `attachment_too_large`), an empty body (400 `attachment_empty`) and an app with nowhere to keep files (501 `attachments_not_configured`).
  - **engine:** an action request takes `attachments: FileContent[]` beside `input`. Each listed file moves from its uploader to the session the message is sent into. A file that is not the caller's or is gone answers 404 `attachment_not_found`, a file another session already holds answers 409 `attachment_already_sent`, and attachments with no session id answer 400 `attachments_need_session`. A refused send hands its files back to their uploader, except a file another send into the same session still relies on or was admitted with.
  - **engine:** `GET /api/flows/blobs/:blobId` returns the file's bytes to a caller who can read the session that holds it. Anyone else, and a file no session holds yet, gets 404 `attachment_not_found`. Deleting a session deletes its files. A file no message claims is deleted after 24 hours.
  - **engine:** files are kept where the sessions are. When the active profile's stores persist (SQLite, Postgres), files go to `.fsdev/blobs/<profile>` under the working directory. `filesystemStores({ rootDir })` keeps them under `<rootDir>/blobs`. Memory stores keep them in memory. A profile's `blobs` slot overrides this; `localBlobStores({ rootDir })` is a store adapter that keeps files on local disk. A database backup does not include the file bytes, so back up the blob folder too.
  - **vercel:** a function's disk does not last between requests, so an upload to a blob store that keeps files on the local disk is refused with 501 `attachments_unavailable`. Configure a hosted `blobs` slot to accept attachments there.
  - **client:** `client.upload({ data, mediaType?, filename? })` uploads one file and resolves to its `FileContent` reference. `client.flow(address).upload(...)` uploads through that flow's route. Send that reference, not the bytes.
  - **contracts / core:** a new `./attachments` subpath (`@flow-state-dev/core/attachments`) carries `ATTACHMENT_LIMITS` (10 images and 5 documents per message, 20 MB per file), the accepted types (PNG, JPEG, WebP, GIF, PDF), and `toBlobRef` / `parseBlobRef` / `isBlobId` for the reference form.

- aa45e92: A user or org resource is read by scope and key with no session, and a client writes it only through the flow it names (FIX-2624).

  - **core:** `defineResource` takes `runBy` and `canWrite`. `runBy: "default"` lets a client write the resource through the framework's default write flow, which checks the schema, the owner and `canWrite({ prev, next, userId, orgId })`, and writes at the version the client read. `runBy: { flow }` names a flow of your app that writes it instead. With no `runBy`, a client can't write the resource; server flows still write it from their actions. User or org scope only, and with a `client` config.
  - **core:** an org resource with `runBy: "default"` and no `canWrite` is a definition error: your app refuses to start until you declare who may write it, even everyone (`canWrite: () => true`). A user resource needs no rule: it is its owner's. Also refused at definition: `runBy` on a session resource, with `flowIsolation: true` or with no `client` config, `runBy: "default"` with a computed `client.data`, `writable: false`, or (any `runBy`) a `client` config that projects no state, and `canWrite` without `runBy: "default"`.
  - **engine:** three routes. `GET /api/flows/resources/:scope/:key` reads the caller's copy (`{ value, version }`) with no session and no request, projected exactly as the session snapshot projects it: a resource with no `expose`, `exclude` or `data` (content-only) returns no `value`. `POST /api/flows/resources/:scope/:key/actions/:action` writes through the resource's `runBy` flow, in a session the server keeps per writer; it records a request like any action. `GET /api/flows/:flow/identity` answers the user and org the server acts as under that flow's sign-in. Each resolves the caller through the declaring flows' own sign-in (a send to `runBy: { flow }` through that flow's, as a direct call to its action would), never the body, query or headers. Until a caller is signed in by every flow that declares the key, and admitted by one declaring instance's pin, every answer is the `404` an unknown key gets. If the declaring flows' sign-in resolves one request to different users or orgs, the read or write is refused (`500 resolver_disagreement`). A key two flows declare with different sign-ins or client settings is refused per request, naming both. Write sessions are the server's: no route or transport takes one from a client (session create included), the default write flow answers as an unknown flow, and no listing shows a write's session or request.
  - **bullmq:** the job processor runs default writes too. A worker started through `createFlowState({ worker: bullmqWorker(...) })` is given the host's `resolvePrincipal` itself (on `FlowStateRuntime`); one built directly with `createFlowWorker` takes `resolvePrincipal` in its deps, the same host-level resolver your web host is given, so the worker decides whether two flows that declare one resource agree exactly as the host does. Default: the development resolver.
  - **client:** `client.resource(def)` returns a handle with `read()`, `state()`, `set(value, { version })` and `update(updater)`. `update` reads, applies your updater and writes at that version; when another write landed first it reads again and re-applies, three times at most, then rejects with `ResourceWriteError` (`code: "stale_version"`). `client.flow(kind).identity()` returns `{ userId, orgId }`.

  - **core (definition error):** `runBy` of either kind on a single resource whose `client` config projects no state (neither `expose`, `exclude` nor `data`, for example `client: {}`) now throws at definition. With no state projection a client reads none of the resource's state, so it has nothing to write back. To fix it, list the fields the client reads and writes: `client: { expose: ["pinned"] }` (or `exclude: [...]`). A resource with no `runBy` and no state projection (content-only) is not served by the direct read: it answers as an unknown key.

Both comparisons are required: they read separately stamped rows, and a caller whose organization was not forwarded to the read matched only entries carrying no organization at all.

- b48158a: Organization identity is now required on every request (FIX-1442).

  A session, request, dispatched child and scheduled job each carry an
  organization, and the server checks it on reads and execution alongside the
  user. It comes from a configured `resolvePrincipal`, or — when an app
  configures no resolver — from the new reserved `DEFAULT_ORG_ID` exported by
  `@flow-state-dev/core`. A caller-supplied `orgId` is never authoritative.

  **What you need to change**

  - A resolver must return a verified `orgId`. Returning none, a blank one, or
    `DEFAULT_ORG_ID` is refused with 401. A machine transport may return
    `{ orgId }` alone and let `defaultUserId` name its system user.
  - Direct `runAction` calls must pass `orgId` — your verified organization, or
    `DEFAULT_ORG_ID` for single-organization development.
  - `authentication.requireOrg` and a block's `requireOrg` are removed.
    Organization is unconditional, so the declaration had nothing left to say;
    a config that still carries either is rejected at definition time rather
    than ignored.
  - Client and React session APIs no longer take an `orgId` — the server owns
    it. `SessionDetail.orgId` is now required on the way back.
  - `openChannels` no longer takes an `orgId`; the server binds the channel.
  - A queued BullMQ job that carries no organization now fails terminally
    instead of being retried: a worker runs below principal resolution, so no
    later attempt could supply one. Subscribers receive an error terminal rather
    than waiting for a job that never completes.

  **The schedule index stores the organization.** `schedule_index` gains a
  nullable `org_id` column in both the SQLite and PostgreSQL adapters, so the
  organization a schedule fires into survives a round trip through the database.
  The column is added for you on the next schema init — there is no manual DDL
  step. Existing rows read back with no organization and are quarantined rather
  than dispatched, so a schedule written before this upgrade does not fire until
  it is attributed; rewriting it stamps the organization of the execution that
  writes it.

  **Upgrading a store with existing data.** Records written before this carry no
  organization. They are preserved and refused (`409 migration-required`) rather
  than guessed at, and listings and scheduler scans skip them. Attribute them
  offline first — the procedure, including dynamic schedules, index rebuild and
  the reserved-id collision check, is in the persistence guide under "Which
  organization a record belongs to".

- f25f03c: Rename the read-through collection family from `ExternalResource*` to `ProjectedResource*` (FIX-1518). Call `defineProjectedResourceCollection` and the `projected: true` brand; the old `External*` names and `external: true` brand are gone.
- bff5e06: FIX-1393: a generator's declared `tools:` is now a runtime fence over capability-contributed tools, not just a documented one.

  A capability's tools used to be unioned onto whatever the block declared, so a block with `tools: []` could still be handed tools it never named. Declaring the slot now drops a capability's catalog-granted tools — `tools: []` reaches the model with none. Omitting `tools:` entirely is unchanged: it declares no fence, so capability tools still flow.

  Capabilities declare tools through two slots. `tools` is a grant from the app's catalog and is fenced. The new `controlTools` is a framework control the consuming block's own configuration asked for, and the fence never touches it — a control is built inside its capability and never exported, so no `tools:` list could name it back in. One capability may use both: the skills library registers the app catalog through `tools` and its own skill loader through `controlTools`, and `taskTools` contributes the delegation board entirely as controls.

  **Migration.** If you relied on a capability's tools arriving past a narrower `tools:` declaration, name them in `tools:` or drop the declaration. Pattern factories (`planAndExecute`, `supervisor`, `routedSpecialists`) forward both slots, so a call site passing `tools` and `uses` together now gets the fence inside the pattern. Capability authors whose tools are framework controls rather than catalog grants should move them to `controlTools`.

### 2026-05-06 — Generator: log unparseable candidates

### 2026-05-02 — Memory pipeline + naming reliability fixes

`sanitizeToolName` is now exported from `@flow-state-dev/core/utils/tool-name` (and the `@flow-state-dev/core/utils` barrel). `BlockToolOutputItem.toolCall` gains an optional `alias` field so tool-call replay reads the model-facing sanitized name from item metadata rather than re-sanitizing the framework name at replay time. `sideChainIf` predicate signature changed to `(value, ctx)` like `thenIf` and `tapIf`.

### 2026-05-02 — Resource content moved out of scope records (FIX-347)

`SessionRecord`, `UserRecord`, and `OrgRecord` no longer carry a `resourceContent` field. Content lives exclusively in `ContentStore`, keyed by `(scopeType, scopeId, resourceKey)`. Concurrent writes to different resources no longer contend on the scope-record CAS path.

### 2026-05-01 — Per-scope FIFO mutation queue (FIX-492)

In-memory state scopes now serialize mutations through a per-`StateContainer` FIFO queue. `ConcurrentModificationError` is no longer thrown for these scopes. New `flow.request.mutationTimeoutMs` (default 30s) bounds worst-case waits; `ScopeMutationTimeoutError` is thrown on exceedance.

### 2026-04-30 — `emit*` default-transient decouple (FIX-478)

`ctx.emitMessage()` and `ctx.emitComponent()` no longer inherit the producing block's `transient` flag — both default to `transient: false` regardless. `ctx.emitStatus()` continues to default to `transient: true`. All three emitters now accept a per-call `{ transient?: boolean }` override.

### 2026-04-30 — SSE noise reduction (FIX-477)

Framework-level no-op guard in `applyMutation`: when the proposed next state deep-equals current, the persist call is skipped, no `state_change` SSE item is emitted, and the helper returns `false`. New `transientSlot()` helper marks top-level fields on a sequencer's `stateSchema` as in-memory only. Breaking (internal): `runWithCAS` now returns `{ state, committed }`; `applyMutation` and the seven `ScopeStateOps` helpers return `Promise<boolean>`.

### 2026-04-30 — `content.delta` non-replayable (FIX-479)

`content.delta` events are no longer persisted to the events log and no longer await `flushEvents`. Running text is checkpointed via an items snapshot instead; new `ResponseEmitterItemHooks.onItemUpdate` hook fires on each delta. Resume contract change: mid-stream reconnects snap to the latest persisted snapshot rather than replaying the exact token sequence.

### 2026-04-30 — Connection resilience (FIX-476)

`RequestStatus` and `RequestStatusSnapshot` now live in `@flow-state-dev/core/types`.

### 2026-04-29 — Per-flow authentication (FIX-23)

New `authentication` config on `defineFlow`: `{ resolvePrincipal?, defaultUserId?, requireUser?, requireOrg? }`. `requireUser: false` is now a real option; flows that declare user-scoped state, clientData, or resources under `requireUser: false` are rejected at registration with the offending field named.

### 2026-04-28 — Durable sequencer checkpoint schema (FIX-401)

New `SequencerCheckpoint` type and `CheckpointStore` interface. `durable: true` is now the sequencer default. `state_snapshot` items now carry a stable `key` per sequencer instance.

### 2026-04-26 — Org scope rename + immutable session binding (FIX-428) [BREAKING]

`project` scope renamed to `org` across the framework. `ScopeType` is now `'request' | 'session' | 'user' | 'org'`. Block configs use `orgResources` / `orgStateSchema` / `orgClientData`. Session `orgId` and `userId` are now immutable; mismatches throw `OrgBindingMismatchError` / `UserBindingMismatchError`. New `requireOrg: true` block flag.

### 2026-04-24 — Cross-flow schema registry + per-flow isolation (FIX-431)

Added `isolateUserState` and `isolateProjectState` flags to `defineFlow`. Isolated flows get their user/org storage namespaced by `flowKind` and skip cross-flow schema checks. `FlowRegistry.register` throws `CrossFlowSchemaConflictError` on incompatible declarations. New storage-key helpers (`resolveUserStorageKey`, `resolveProjectStorageKey`).

### 2026-04-24 — Prompt caching audit and default-enable (FIX-423)

New `caching` field on `generator()` config, defaulting to `{ enabled: true, breakpoints: 'auto', ttl: '5m' }`. Provider-specific markers applied for Anthropic / OpenRouter / Vercel AI Gateway; OpenAI / Google / DeepSeek cache implicitly. `GeneratorModelUsage` gains `cacheReadInputTokens` and `cacheCreationInputTokens`.

### 2026-04-11 — DevTool: View Sequencer State (FIX-348)

New `SequencerStateSnapshotItem` trace item captures the full state of a sequencer at each step boundary. Sequencers now auto-emit an initial snapshot before execution begins and one after each step completes (including `loopBack` iterations).

### 2026-04-11 — `defineCapability()` (FIX-351)

New `defineCapability()` packages resources, state schemas, targets, helper functions, and presets under a single name. All four block kinds accept `uses: [capability]`. Capabilities compose transitively with cycle detection and diamond dedup. `.presets()` builder ships with boolean toggles and function-form overrides. `ctx.cap.{name}.{fn}` provides memoized helpers.

### 2026-03-20 — Resource Namespaces (FIX-98)

New `defineResourceNamespace()` for typed dynamic resource collections with glob patterns (`files/*`, `files/**`) and parameterized patterns (`[topic]/observations`). `ResourceNamespaceRef` runtime interface with `create`, `get`, `getOrCreate`, `list`, `delete`, `count`. `maxInstances` cap with `none` / `lru` / `oldest` eviction. Per-instance lifecycle hooks. Block-level `sessionResources` / `userResources` / `projectResources` slots accept namespace definitions alongside static resources.

### 2026-03-03 — `contextReducer` utility block (FIX-73)

New `utility.contextReducer(config)` generator factory with three modes: `distill`, `denoise`, `compress`. Mode-specific default output schemas exported with caller override support.

### 2026-03-01 — Sequencer container item emission (FIX-8)

Optional `container` metadata on the shared block config surface so sequencer/router container settings remain attached to built block definitions. Parent metadata extended with `parentInstanceId` and resolved container metadata.

### 2026-03-01 — Block resource declarations (FIX-92)

New `DeclaredResources` type and `declaredResources` field on `BlockDefinition`. Handler, generator, and router blocks accept `sessionResources`, `userResources`, `projectResources`. Sequencers collect declared resources from all child blocks (with build-time conflict detection on same-name/different-reference); `defineFlow` merges them into flow scope configs.
