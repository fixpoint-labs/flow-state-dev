# Scope state and resources split one mutation surface across two APIs

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

FSD stores durable data two ways: the **state bag** on a session (or user, or org), and
**resources**. Developers pick by **which one carries the verb they need** rather than by
where the data belongs. The bag has "add one to this counter" and "append to this list";
resources have neither, and our docs tell people to *prefer* those verbs when several
things write at once. Someone who correctly chose a resource reads that and moves the data
back into a bag it did not belong in.

Underneath, the surfaces differ in **eleven** ways — most written down nowhere, none
collected anywhere a developer would look, and no way to tell which are deliberate.

*Tracked as [FIX-1154](https://linear.app/fixpoint-labs/issue/FIX-1154); an implementation spec,
so it never lands on `main` (BP-037).*

### 2. Solution in plain terms

**Write the eleven differences down once, and ship that map into the docs where the choice
gets made.** Each difference is labelled deliberate, deferred, or a defect. That is the whole
deliverable: **no production code changes.**

The headline nobody has written down: the two surfaces **share verb names without sharing a
guarantee.** A resource write is always version-checked and can be refused; the bag's may skip
that check, depending on the call's shape and the adapter. Published guides state the bag's half
unqualified, and correcting them is the part of this change a user feels.

Writing the map turned up **six defects on `main`**, each a way a write reports success while
losing or corrupting data. All six are filed and tracked independently; this change documents
them and fixes none (§7b).

### 6. Decisions & rules

**All three are closed at D-6 ([#1446](https://github.com/fixpoint-labs/flow-state-dev/issues/1446)).
Nothing here is an open ask.**

1. **Resources do not get `incState` / `pushState` this cycle** — the gap is documented instead.
   *Locks in:* the two surfaces keep different verb lists, and choosing between them rests on
   §11's map rather than on symmetry.
2. **Store-native increment and append for resources is DEFERRED, not dropped.**
   *Locks in:* resource writes keep sending the whole value, and concurrent resource increments
   keep contending, for this cycle.
3. **The map ships as documentation, split by audience** — the whole shipped artifact.
   *Locks in:* the pages §11 lists are now a contract anyone changing either surface keeps true.

What each decision rests on — and the argument one of them got wrong — is §7d.

**Non-goals** — merging or deprecating either primitive; a shared `MutationContract` type;
reconciling the two retry drivers; fixing the bag's own adapter divergences; cross-record
atomicity (FIX-854).

**Size:** Small — documentation only (§11) · 1 PR + an empty changeset.

All six are live on `main` today, reachable through the write methods resources already have
(`updateState` / `patchState` / `setState`). **None is fixed here** — this cycle's deliverable
is documentation. Three share one root, named at the end.

**D1, D2, D3 and D4 share one root:** `normalizeResourceState` stores the **output** of
`safeParse` rather than validating the candidate and storing the candidate. Four different
failures fall out of that one decision — reject-and-replace (D1), swallow-and-replace (D2),
accept-and-alter (D3), accept-and-corrupt-downstream (D4) — and they are worth keeping apart,
because only D1 has a rejection anywhere in it and only D3 and D4 leave a plausible-looking
row behind.

**A fix belongs to the shared normalizer, not to any one verb.** An earlier draft of this spec
proposed a fixed-point guard on two new verbs; that would have put schema safety on the newest
methods while the three shipped ones kept corrupting through the same normalizer, rebuilding
inside one primitive the per-verb asymmetry this epic exists to remove.

### 7c. Round-trip stability — the hazard class behind D4

Values the storage layer cannot round-trip are lost or altered **without anything raising** —
and only *some* of them go on to reach D1's destruction (the prose under the table says which,
and it is the minority). The boundary that holds is **anything a JSON round-trip does not return
unchanged** — not "non-finite", not "JSON-safe". Zod accepts all of these under an ordinary
schema, and the adapters then disagree:

| Value | Zod (`z.number()` / `z.array(z.any())`) | Memory (`structuredClone`) | SQLite / filesystem (`JSON.stringify`) |
|---|---|---|---|
| `Infinity`, `-Infinity`, overflow | accepts | **keeps** | → **`null`** |
| `undefined` in an array | accepts | keeps | → **`null`** |
| function, symbol | accepts | **clone throws** `DataCloneError` | → **`null`** |
| `bigint` | accepts | **keeps** it | **throws** `TypeError` mid-write |
| `Date` | accepts | **keeps** (a live `Date`) | → **a string** |
| `Map`, `Set`, `RegExp` | accepts | **keeps** (contents intact) | → **`{}`**, contents gone |
| `-0` | accepts | **keeps** the sign | → **`0`** |
| a sparse array (a hole) | accepts | **keeps** the hole | → **`[null]`** |
| an array with a custom own property | accepts | **keeps** the property | → **dropped** |

`NaN` is the one exception, caught by `z.number()` itself. Everything else passes the schema
check, is written, and — on the SQL and filesystem adapters — comes back as something else.

**Whether that then lands in D1's replacement depends on the schema, and for most of this table
it does not.** D1 needs the schema to **reject the serialized form**: `Infinity` under
`z.number()` reads back as `null`, fails the parse, and the row is replaced by its default. But
under the permissive `z.array(z.any())` these branded rows actually use, the flattened values
still parse — a `Date` reads back as a string and `Map` / `Set` / `RegExp` as `{}`, all four
accepted on the next read (run) — and `-0` → `0` is still a valid number. So the next read
succeeds and nothing is replaced. **Route a round-trip hazard into D1 only when the schema would
refuse the serialized representation.** The rest are not the milder half: they lose data with no
rejection anywhere, which is the paragraph below.

**The class has three shapes, and the two loud ones are mirrors. Conflating them produces a wrong
fix or a wrong test.** Read off the columns above:

1. **Converts quietly — the majority.** `Date`, `Map`, `Set`, `RegExp`, `Infinity`, `NaN`, `-0`, a
   sparse hole, a non-index array property. The write resolves on both sides, and the two adapters
   end up holding different data.
2. **Loud on the durable side — `bigint` alone.** `structuredClone(1n)` succeeds and preserves the
   value, so the memory store keeps it, while `JSON.stringify` throws
   (`TypeError: Do not know how to serialize a BigInt`) and every JSON-backed adapter — SQLite,
   Postgres, filesystem — **rejects the write outright** at persist time, with a raw error naming
   no field. It **passes in tests and fails in production**: the memory store is what tests and
   local development run against.
3. **Loud on the memory side — function and symbol.** The exact mirror. `structuredClone` throws
   `DataCloneError`, so the write **fails in tests**, while `JSON.stringify` accepts it and the
   durable adapters **corrupt it quietly in production** — `null` in array position, and the key
   **dropped entirely** in object position.

Verified on the repo's Node (v22.22.2): `structuredClone({x:1n}).x` returns `1n` while
`JSON.stringify({x:1n})` throws; `structuredClone` throws `DataCloneError` on both a function and
a symbol while `JSON.stringify([v])` gives `[null]` and `JSON.stringify({x:v})` gives `{}` for
each. Alongside them, `Infinity` →
`{"x":null}`, `NaN` → `{"x":null}`, `undefined` → `{}`, `-0` → `{"x":0}`, `Date` →
`{"x":"1970-01-01T00:00:00.000Z"}`, and `Map` / `Set` → `{"x":{}}`.

**Three shapes, one boundary check — this is not three fixes.** The decidable test is still the
one the table is drawn on: `JSON.parse(JSON.stringify(v))` deep-equals `v`. It selects all three.
The shapes describe what a *caller observes*, which is what the **tests** have to match.

**The trap for a test author, and it is wrong in both directions.** A test asserting "the memory
and JSON sides hold different values" fails on **both** loud shapes for opposite reasons: on
`bigint` there is no JSON value to compare against, and on a function or symbol there is no memory
value. A fix designed only for silent conversion covers neither.

**The branded rows are the ones that force the phrasing.** A `Date` or a `Map` is not
"unsafe" in any sense a type check can see: it serializes without complaint, and it serializes
to something *else*. Nothing throws on either side, so there is no failure to notice — the two
deployments simply hold different data from the same call, and the one that lost its contents
finds out on a later read.

`cloneValue` is what makes the memory column behave differently: it uses `structuredClone`
when available and only falls back to a JSON round-trip otherwise
(`core/src/helpers/clone.ts:15-21`).

*(The last three rows — `-0`, sparse arrays, array custom properties — were added in rounds 15
and 17. They are the same class and the same adapter split; none needs its own defect entry.)*

### 7d. Why this is documentation, and the record on the deferred tier

**The case for adding the verbs, and why it did not carry.** Every increment and append on a
resource in this repository today is **compound** — semantic memory's `addFact` appends a fact
*and* bumps a counter in one write; working memory's `advance` bumps a turn counter *and*
recomputes every entry. None would be rewritten to use a single verb, so two new methods would
have replaced **zero** existing call sites. The remaining case was discoverability plus
**eight files** across `@flow-state-dev/memory` and `@thought-fabric/core` that type their
resource work as `ResourceContext` and hold the narrower handle. D-6 weighed that against
adding public surface we cannot take back and chose the documentation. **This block records
the decision; it does not argue it.**

**Philosophy** — tenet 1 (one true statement replacing the misleading published ones) and tenet 4
(fix or document; do not add unused public surface).

**The store-native tier (the epic's Tier 2) — deferred at D-6, not dropped.** Two things are
worth carrying forward: the reason that turned out to be false, and the reason that stands.

*The falsified reason, kept visible because the epic made the same error.* An earlier draft
deferred this on the grounds that native verbs *remove no conflicts*. That assumed a native
resource delta must carry a held `expectedVersion` — the epic's constraint says never use the
commutative `"any"` downgrade, since `"any"` asserts nothing about the row and can resurrect a
tombstone. But `"any"` is not the only version-free option. **Both SQL resource stores already
predicate every conditional update on `lifecycle = 'live'`**
(`store-postgres/src/resource-state-store.ts`, `store-sqlite/src/resource-state-store.ts`), and
a delta predicated on *liveness rather than version* is tombstone-safe by construction:
concurrent increments all land, and a delete that wins first makes the delta refuse without
resurrecting anything. So a lifecycle-guarded native delta **would** remove contention. Ruling
out one extreme is not establishing the other, and both the epic and this spec made that step
without noticing.

*What the deferral rests on.* Implementation cost, and a design surface nobody has evaluated:
a version-free resource write bypasses `runResourceCAS`, which is where the verified-no-op
check, the `previousState` basis and the `resource_change` gate live. The epic's theme-2 proof
obligation — *every row of the policy table survives* — comes back with it, and harder than
the version-checked form, because the commutative path has no basis to verify against. The
cost half is also where this spec was wrong twice in the other direction: the optional,
feature-detected delta verbs belong to the **scope-record** stores (`SessionStore`,
`RequestStore`, `UserStore`, `OrgStore` each `extends DeltaStoreOps`); resources go through
**none** of them, persisting via `ResourceStateStore`, which extends nothing and whose whole
mutation surface is `set`, `delete` and `deleteAll`. Reason about this from
`ResourceStateStore`, never from the scope-side precedent.

**If a later cycle picks the tier up, it is an epic-theme rewrite, not a child leftover.**
Theme 2 frames the constraint as *held `expectedVersion`, never `"any"`* — and the
liveness-gated option is neither, so the constraint is **incomplete rather than merely
deferred**. A future cycle has to amend theme 2 to name lifecycle-guarded as an allowed
exception, next to FIX-992, rather than inherit "never `any`" and conclude the tier is
unreachable. Cite **D-6 (#1446)**. Epic #1365's "Tier 2 deferred" stays **deferred** — do not
fold it to dropped.

**Where the complexity in this issue is:** not in any code. It is in getting each map row's
*reason* right rather than its existence — six review passes have each corrected a row that
read as true.

**The lesson that shaped the map, and the one the docs depend on:** *don't assert into a
subsystem you aren't changing.* Nearly every correction across those passes landed on a claim
about the **state bag**, which this issue does not touch; the resource column stayed stable
throughout. A comparison is a claim about two systems, and a spec only owns one of them. So
row 10 states the bag side **by reference**, and where a planned doc page genuinely needs a
bag fact, the fact lives in §11 beside the page that publishes it, to be re-verified at
writing time.

### 7e. What the difference looks like when it bites

```
scope bag    await ctx.session.incState({ n: 1 })
             → single field + adapter has a native increment: version check
               skipped, so concurrent state updates cannot refuse it
             → but a concurrent DELETE of the record still refuses it, even
               at "any" — reported as a no-op on the commutative path
             → multi-field, e.g. incState({ a: 1, b: 1 }): version-checked,
               and can raise ConcurrentModificationError on retry exhaustion

resource     await ctx.resources.stats.updateState((s) => ({
               ...s, n: s.n + 1
             }))
             → the only way to increment a resource. Always version-checked:
               normally lands, re-running against the winner on a conflict
             → ConcurrentModificationError if contention outlasts the retries
             → ResourceDeletedError if the resource was deleted underneath,
               PROVIDED this request had observed it live (D5 otherwise)
             → the callback returns the WHOLE next state, which is then
               re-parsed against the schema. A field it forgets to spread
               loses its live value either way, but does NOT simply vanish:
               with a schema default it comes back AT that default (a stored
               ["keep-me"] reads back as []), optional-with-no-default it is
               absent, required-with-no-default the whole write is replaced
               by the default (D1). Never say "gone" — see map row 5

resource     await ctx.resources.log.updateState((s) => ({
               ...s, entries: [...s.entries, e]
             }))                                        // in a loop
             → N whole-state writes. For bulk appends, one compound write
```

### 8. Implementation sequence

**No production code changes.** Two steps.

1. **Ship the map per §11, and correct the concurrency-guidance line** that tells readers to
   prefer increment and append for concurrent writes without saying which primitive, which
   adapter, which arity, or that a deleted record refuses the write anyway.
   **Do not write this prose yourself, and do not hand the writer this document.** §11's target
   list is the entire deliverable — and `AGENTS.md` is explicit that the writer
   "runs in a fresh context on **a surface brief** — the symbols a user touches, what a caller
   sees including failures, and the limits — and derives the rest from the public API", because
   "implementation rationale leaks into published pages in a predictable way (design defense,
   **defect narrative**, before/after framing)".

### 9. What the resource write path does today

The evidence behind §7a and §7b, stated as observed behaviour rather than as a contract. Every
row is reachable through `updateState` / `patchState` / `setState` on `main`. **Rows marked
POC are run** (§10); the rest are read off the code at the citation given.

| Case | Observed today | Evidence |
|---|---|---|
| Two contexts writing one resource | Both land; the loser re-runs against the winner | POC |
| Contention outlasting the retry budget | `ConcurrentModificationError`, after **four** attempts — `resource-cas.ts:62` sets `DEFAULT_MAX_RETRIES = 3` | POC (a store seam whose rival writer wins every race; the row asserts the attempt count, not just the error type) |
| A write racing a delete, **from a context that observed the resource live** | Terminal `ResourceDeletedError`, immediately. **What that buys is precision, not safety** — a positive held version requires a *live* row at that version (`resource-state-predicate.ts:154-156`), so a tombstone refuses it however many times it is retried. The alternative was a retry storm exhausting into a generic error, not a resurrection | POC |
| A write racing a delete, **from a context that never observed it** | **The write succeeds and the resource comes back live** — D5 / FIX-1258. Pinned as current behaviour, so the fix landing shows as that row failing | POC |
| A write producing no change, against a **live** or a **never-stored** resource | A **verified** no-op: no write, no version bump, no change event — and specifically not an error about a deletion | POC |
| A write producing no change, while holding a **stale positive version** of a row since **deleted** | **`ResourceDeletedError`** — terminal, not a quiet no-op. The boundary of the row above; stating that guarantee unqualified was a defect in an earlier draft | POC |
| A write on a resource never yet stored, **whose schema has a valid complete default** | Creates it from that default plus the change | POC |
| A write on a resource never yet stored, whose schema has **no** valid complete default | **Nothing lands, and nothing is reported.** `normalizeResourceState` **does not throw** — it falls back to `normalizeResourceDefault`, which cannot parse `undefined` or `{}` against such a schema either and returns `{}` (`normalize-resource-state.ts:26-36, 44-50`). That deep-equals the `{}` the write started from, so the driver takes it as a **verified no-op**: no row, no version, no error. An updater that *does* supply every required field succeeds normally. *Corrected round 18 — the earlier "throws … landing in D1" was wrong in both halves, and contradicted the D1 row below, which never throws.* | POC |
| A result the schema **rejects** | **The whole state is replaced by the default and the call succeeds** — D1 | POC |
| A result the schema **swallows** via a top-level `.catch()` | **The whole state is replaced by the catch fallback and the call succeeds** — D2 | POC |
| A result a **same-type transform** rewrites | **The stored value drifts and the call succeeds** — D3 / FIX-1260 | POC |
| A transform that yields a round-trip-unstable value | **Stored intact in memory, flattened by JSON adapters, no error** — D4 | POC |
| A value that would not survive a JSON round-trip, written directly | Accepted by the schema, then split by adapter — §7c's three shapes. `bigint` throws mid-write on a JSON adapter; a function or symbol throws on the memory store instead | POC (branded objects, deltas) |
| A **string** where a number belongs, reached untyped | **No error at all.** `0 + "5"` concatenates, the schema rejects the result, and the row is replaced by the default while the call reports success — D1 reached through an argument | POC |
| A `bigint` or symbol where a number belongs | A raw `TypeError` — **not** a `FlowError`, so `isRetryableError` classifies it **retryable**. Whether that becomes a replay depends on the block's policy: unconfigured, `maxAttempts` is 1 and it surfaces once; under a policy with `maxAttempts > 1` that restricts no error types, the block re-runs every side effect it already performed (D6's three conditions) | POC |
| A write on a resource declared `writable: false` | Refused — with a plain `Error`, so it is **classified retryable**, and replayed wherever D6's three conditions hold | read (`resource-registry.ts:659`) |
| A write on a **collection instance** whose collection declared `writable: false` | **Lands.** `persistNamespaceInstanceState` has no `writable` check at all (`resource-registry.ts:669-684`), and `ResourceCollectionConfig` declares no `writable` field, so the declaration type-checks clean and is silently ignored (§12) | read |
| An unknown key returned from an `updateState` callback | Silently **stripped** by an ordinary `z.object`; the result deep-equals current state and the call resolves as a **verified no-op**. A lost write, not lost data | read |

**Second path (BP-035) for anything published from this table:** the **collection-instance**
handle is a separate code path from the single-resource handle, built by separate code in the
same module, and it does not share the `writable` check. A claim checked only against
`ctx.resources.foo` is a claim about half the surface.

  create-if-absent too, via the `"absent"` sentinel. This lands in an **exported** symbol's doc
  comment, so a wrong invariant here is a published one.
- **Map rows 8 and 9** carry their own triggers; neither fires while decision 2 holds.
- **Deepening:** the two ref builders in the resource registry duplicate their write-op bodies
  almost exactly. Follow up via `improve-codebase-architecture`.

## Spec evolution

**Rounds 1–17.** This document was drafted as an implementation spec for two new resource
verbs and was rewritten at round 18 into the gap write-up D-6 asked for. The verb-level
contract it carried — key typing, the runtime unknown-key backstop, availability conditions,
the refusal set, the retry-path and field-survival test predicates, and the twenty-six CI
behaviours — was **cut**, not filed off: it specified methods that are not shipping. It
remains in this branch's history at `edbe3513` if a later cycle wants it, though decision 2's
tier is a different design (store-native, liveness-gated) and would not inherit much.

**What the seventeen rounds actually bought, and what survived the rewrite:**

- **The map's row-by-row reasons.** Six passes produced roughly twenty confirmed factual
  corrections. Nearly every one landed on a claim about the **state bag**, a subsystem this
  issue does not change, while the resource column stayed stable throughout. That is why row 10
  states the bag side by reference and why §11's bag facts sit beside the page that publishes
  them, flagged for re-verification. **A comparison is a claim about two systems, and a spec
  only owns one of them.**
- **Six defects on `main`**, none of which the issue set out to find. Four (D1–D4) trace to one
  decision in `normalizeResourceState` — storing the output of `safeParse` instead of
  validating the candidate and storing the candidate. Three rounds narrowed a rule that was
  quietly compensating for it before anyone checked one layer down. **When a rule needs
  narrowing repeatedly, check whether it is covering for a bug somewhere else.**
- **The POC, which is now the write-up's evidence base.** The refusal hazards were argued in
  prose for three consecutive rounds, each round enumerating the value kinds known at the time
  and each round missing a neighbour. They were then run. **When a rule has been corrected in
  prose twice, the third correction should be a test** — prose can be wrong in a way that reads
  fine; a row asserting `keep: "schema-default"` cannot.
- **Two sweep directions, and both were needed.** *Backwards:* has a neighbour outgrown this
  rule? — which found real defects three rounds running, because a widening has a blast radius
  over every rule that enumerated the old, narrower set. *Forwards:* now that this rule is
  wider, what does it wrongly include? — which found three over-inclusions the backwards sweep
  could not see, since new members satisfy the widened rule by construction. **After widening a
  predicate, walk its new members and ask what each now owes that it cannot pay.**
- **A derivation's published output goes stale even when the derivation is right.** The
  read-only blast radius was stated as a derivation over callers precisely so a list could not
  rot, and its worked output still missed a caller one hop further out. **A derivation stated
  correctly and then enumerated by hand once inherits every weakness of the list it replaced.**
- **Rules get written at the width of the instance that motivated them.** The round-trip rule
  was drawn at non-finite numbers (because `Infinity` prompted it), then at JSON-safety
  (because `undefined` and `bigint` broke it), and neither held — a `Date` is JSON-safe and
  still stores differently on two adapters. The boundary that holds is the property the storage
  layer actually needs.
- **A survey is a claim like any other.** "No in-tree resource uses a passthrough state schema"
  stood for two rounds and was false, and a count reported as "declarations" was actually
  mentions of the word (340 versus 137). BP-003 says to execute the check rather than read it;
  the gap was executing a check aimed at a *neighbour* of the claim, which is the failure tenet
  7 names.
- **Fifteen rounds did not notice the document's own first line.** It led with a ref and an
  artifact label before the problem, which `AGENTS.md` prohibits outright for specs. A rule
  about the top of the file is invisible to every review that starts by looking for the
  interesting part.
- **Three enumerations in this document came up short, and each was extended by hand rather
  than replaced by a rule.** The read-only blast radius, the round-trip value kinds, and now the
  published pages carrying the CAS guarantee — §11 listed three, review named two more, and the
  sweep found two reference pages worse than any of them. Extending a list answers the instance;
  it does not answer the next one. The fix each time was to state the **selection rule** and the
  command that runs it, so the list becomes an output rather than an inventory — which is what
  §11 now carries. *(Round 20 proved the point twice over: the rule's own supporting grep was
  written from memory as "returns nothing" and actually returns one hit. Even the check on the
  check has to be run.)*
  **Round 21 found the half that a selection rule does not fix: the *counts* that summarize the
  list.** Widening §11 left "seven surfaces", "three guides" and "four pages" behind it in four
  other sections — an implementer working to the number would have stopped short and published
  identified contradictions. A rule turns the list into an output; a number written next to it is
  still an inventory, and a stale one. **Where a handoff needs a quantity, define it from the list
  ("one brief per target below"), never by restating the count.**

**Round 17's four findings, and what became of them.** All four specified guards for the verbs
D-6 stopped. Two of them, checked against `main`, turned out to describe live defects reachable
through `updateState` today, and were promoted into §7b as **D2** (`.catch()` swallowing an
invalid candidate) and **D4** (a transform introducing a round-trip-unstable value). One —
non-index properties on an appended array — is a real adapter divergence and a ninth member of
§7c's existing class, so it widened that table rather than earning an entry. The fourth, on
traversing `ZodIntersection` to collect declared keys, was purely about implementing a backstop
for verbs that are not shipping, and is closed with them.

**Round 18 — the rewrite.** D-6 (#1446) settled Ask 1 as B. The deliverable became the gap
write-up: what differs between the two durable-storage surfaces, which differences are
deliberate, and which are defects. Decision 2 stays defer-not-drop in D-6's own words; FIX-1258
and FIX-1260 keep their pinned-not-fixed posture; the POC keeps passing and is now the evidence
base rather than a design validation.

**Round 18's review, and the one pattern in it.** Five findings landed, and four were confirmed
against the code. The `getOrPatchState` "no consumer" claim was **false** — the method has ten
production call sites in `labs/trading-desk` and is public documented API — so row 6 withdraws
the no-demand argument and defers on the narrower ground that only the *handle split* is
unexercised. The other three all corrected an **error path stated from a reading**: an
invalid-default first touch was said to throw (it is a silent no-op), an omitted `updateState`
field was said to be gone (it returns at its schema default), and a JSON-flattened branded value
was said to fail its next read into D1 (it parses). One finding was rejected: nothing here is
evidence of a *systematic* "the normalizer throws" error — §9's invalid-default row was the only
place the spec attributed a throw to that path, and every other throw in the document names a
genuinely different mechanism (the read-only guard, `structuredClone`, `JSON.stringify`, the
bag's own adapters). **The transferable lesson is narrower and sharper than "check the
normalizer":** every one of the three corrections was a row this document had marked *read*
rather than *run*, and the error was always about what happens on the failure path. Success
paths get exercised by ordinary use and read correctly; failure paths are where a plausible
sentence and the code diverge, and where citing a line number gives false confidence. All three
are now run rows (§10).

**Round 19 — three findings, and the P1 is the one worth carrying out of this issue.** §8 step 1
told the implementer to dispatch `docs-writer` with §7a and §11 — **while quoting the isolation
rule that forbids exactly that.** §7a is a defect narrative: verdict labels, internal paths,
review history. The step cited *"the context leaks even when you know the rules"* and then handed
over the context in the same sentence. It now requires the implementer to distill a surface brief
per target first, with §7a and §11 as the material rather than the payload. **A rule quoted in
the same breath as its violation is the strongest evidence that knowing a rule is not a control**
— which is the rule's own claim, demonstrated on itself.

The other two were the same forward blast radius this document keeps catching, now on round 18's
own corrections. §7e still said an omitted field was `GONE` while row 5 had already been fixed —
**a correction that did not reach its neighbour**, and §11 sends writers to that exact example.
And the headline conflated two independent conditions: whether a bag write skips the *version
check* (decided from the hint alone, before any lookup, `scope-persist.ts:60`) and whether a
*missing record* refuses it (a separate predicate that runs regardless, `memory/shared.ts:72-77`).
Split in row 10, and in §11 beside the page that publishes it — round 21 then cut the restatement
out of Part I, so those two are the copies to keep true. **When a fix lands, grep the document for
the phrasing it replaced** — twice now the stale copy sat in the section the docs plan points
writers at.
