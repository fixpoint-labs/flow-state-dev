# Scope state and resources split one mutation surface across two APIs

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

FSD stores durable data two ways: the **state bag** on a session (or user, or org), and
**resources**. Developers pick by **which one carries the verb they need**, not by where the
data belongs. The bag has "add one to this counter" and "append to this list";
resources have neither today, and our docs tell people to *prefer* those verbs under
concurrent writes. Someone who correctly chose a resource reads that and moves the data back
into a bag.

Underneath, the surfaces differ in **eleven** ways — most written down nowhere, and no way to
tell which are deliberate.

*[FIX-1154](https://linear.app/fixpoint-labs/issue/FIX-1154) — an implementation spec, so it
never lands on `main` (BP-037).*

### 2. Solution in plain terms

**Write the eleven differences down once, and ship that map into the docs where the choice
gets made.** Each is labelled deliberate, closing, deferred, or a defect. **No production code
here.**

The headline nobody has written down: the two surfaces **share verb names without sharing a
guarantee.** A resource write **through the shared state mutators** is always version-checked
and can be refused; the bag's may skip that check, depending on the call's shape and the
adapter. Published guides state the bag's half unqualified, and correcting that is what a user
feels.

Writing the map turned up **six write-safety defects on `main`**. Four still report success and
get the data wrong; a fifth was fixed mid-review; the sixth refuses a write correctly, then tells
the runtime that refusal is worth retrying — half-fixed, still live on collections. All are
filed; this change documents them and fixes none (§7b).

### 6. Decisions & rules

**All three are closed at D-6 ([#1446](https://github.com/fixpoint-labs/flow-state-dev/issues/1446)).
Nothing here is an open ask.**

1. **Resources get `incState` / `pushState`** — Ask 1, amended to **A** on 2026-08-26. Ships as
   **[FIX-1269](https://linear.app/fixpoint-labs/issue/FIX-1269)** (symmetry only; no behaviour
   change), not here — and **first**, per §12.
2. **Store-native increment and append is DEFERRED, not dropped** — **FIX-1267**, next to
   FIX-992, untouched by Ask 1.
3. **The map ships as documentation, split by audience**, documenting those verbs as API.

What each rests on, including one argument that was wrong, is §7d.

**Non-goals** — merging or deprecating either primitive; a shared `MutationContract` type;
reconciling the two retry drivers; fixing the bag's adapter divergences; cross-record
atomicity (FIX-854).

**Size:** Medium — **0 production files, 0 test behaviours**; §11's documentation targets,
counted by `check-targets.mjs` · **1 PR** + an empty changeset.

**D1, D2, D3 and D4 share one root:** `normalizeResourceState` stores the **output** of
`safeParse` rather than validating the candidate and storing the candidate. Four different
failures fall out of that one decision — reject-and-replace (D1), swallow-and-replace (D2),
accept-and-alter (D3), accept-and-corrupt-downstream (D4) — and **that four-way split is itself
the argument for keeping them apart.** They differ by where in the parse the failure happens and
what the normalizer then does with it, which is the axis any fix has to handle. Only D1 has a
rejection anywhere in it; the other three never fail a parse at all.

**What does *not* separate them — corrected round 26.** An earlier draft added *"and only D3 and
D4 leave a plausible-looking row behind."* Re-run rather than re-read, and it is false for **all
four**: every one leaves a row a reader would accept. D1 stores the schema default
(`keep: "schema-default"`), D2 stores the catch fallback (`{ n: 0, keep: "schema-default" }` —
demonstrated in D2's own row two paragraphs above, which is where the contradiction was visible
without running anything), D3 stores a drifted number, and D4 stores `null` and then feeds D1 one
read later (`policy-rows.poc.test.ts:702, 771, 811`). **A plausible-looking row is the cluster's
shared symptom, not a discriminator.** Stating it as one implied two of these fail visibly, when
the defining property of the whole cluster is that none of them does.

**A fix belongs to the normalizer, not to any one verb.** An earlier draft of this spec
proposed a fixed-point guard on two new verbs; that would have put schema safety on the newest
methods while the three shipped ones kept corrupting through the same normalizer, rebuilding
inside one primitive the per-verb asymmetry this epic exists to remove.

**But "the normalizer" is two copies, and a one-site fix leaves the other standing.**
`normalizeResourceState` covers **single** resources only. A **collection instance** never
reaches it: `persistNamespaceInstanceState` calls `nsConfig.stateSchema.safeParse(...)` itself
and substitutes `{}` on failure (`resource-registry.ts:669-683`) — the same
store-the-output-of-`safeParse` decision, written a second time. So all four of D1–D4 are
reachable through a collection instance by the same mechanism, D1 explicitly includes
collections, and **a fix landing only in `normalizeResourceState` fixes half the surface while
reporting success.** Whoever takes FIX-1256 owes both paths, and the honest first move is to
consolidate them into one rather than to patch each — two copies is how this got here. This is
the same second-path hazard §9's closing note names for `writable`, on a different field, which
is the argument for consolidating rather than for a third careful edit.

### 7c. Round-trip stability — the hazard class behind D4

Values the storage layer cannot round-trip are lost or altered, and **for the quiet majority
nothing raises** — the two loud members are the exception, not the rule, and shapes 2 and 3
below say which they are and on which adapters they throw. Of the ones that stay quiet, only
*some* go on to reach D1's destruction (the prose under the table says which, and it is the
minority). The boundary that holds is **anything a JSON round-trip does not return unchanged** —
not "non-finite", not "JSON-safe". Zod accepts all of these under an ordinary schema, and the
adapters then disagree:

**The last column is `JSON.stringify`, and that is a claim about SQLite and Postgres — not
about "durable". Run, round 22.** The **filesystem** resource-state adapter calls `cloneValue`
(→ `structuredClone`) on the way in, *before* it serializes
(`filesystem/resource-state-store.ts:166`), so on the clone-refusing kinds it behaves like the
memory column rather than the JSON one. Reason about this table as **clone-first adapters
(memory, filesystem)** versus **stringify-first adapters (SQLite, Postgres)**, never as
"memory versus durable".

| Value | Zod (`z.number()` / `z.array(z.any())`) | Clone-first (memory, filesystem) | Stringify-first (SQLite, Postgres) |
|---|---|---|---|
| `Infinity`, `-Infinity`, overflow | accepts | **keeps** | → **`null`** |
| `undefined` in an array | accepts | keeps | → **`null`** |
| function, symbol | accepts | **clone throws** `DataCloneError` | → **`null`**, and **the row lands before the caller's own error** (below) |
| `bigint` | accepts | memory **keeps** it; filesystem **throws** `TypeError` at its own `JSON.stringify` | **throws** `TypeError` mid-write |
| `Date` | accepts | **keeps** (a live `Date`) | → **a string** |
| `Map`, `Set`, `RegExp` | accepts | **keeps** (contents intact) | → **`{}`**, contents gone |
| `-0` | accepts | **keeps** the sign | → **`0`** |
| a sparse array (a hole) | accepts | **keeps** the hole | → **`[null]`** |
| an array with a custom own property | `z.array(...)` **strips it** (returns a new array, property gone); a passthrough `z.any()` keeps it | **keeps** the property — *only if a schema let it through* | → **dropped** |
| `NaN` | `z.number()` **rejects**; `z.array(z.any())` accepts | **keeps** | → **`null`** |

**Two rows' fate depends on which schema is in play, and both are rows rather than exceptions.**

*`NaN`.* Under a numerically-typed field `z.number()` rejects it before persistence, so nothing
reaches a store and there is no divergence to test. Under the permissive `z.array(z.any())` that
the branded rows actually use (the paragraph below), it parses, persists, and converts exactly
like the rest of the quiet majority. *Round 24 flagged this as an impossible persistence case to
be dropped from shape 1, on the strength of the `z.number()` half alone; run on the repo's Zod
3.25.76, `z.number().safeParse(NaN)` fails and `z.array(z.any()).safeParse([NaN])` succeeds, so
the correct fix was the qualifier, not the deletion.*

*An array's custom own property — and here the schema does not merely decide the outcome, it
decides whether there is a storage question at all.* `z.array(...)` **rebuilds** the array from
its parsed elements, so a non-index own property is gone **before any adapter sees it**: under
the `z.array(z.any())` these rows otherwise assume, every adapter receives the same plain array
and there is **no divergence to observe**. The clone-versus-stringify split in that row is real
only under a passthrough (`z.any()`), which does reach the boundary, where `structuredClone`
keeps the property and `JSON.stringify` drops it. *Run, round 25 — `z.array(z.any()).parse(arr)`
returns a new array with `hasOwnProperty("custom") === false`, while `structuredClone(arr)`
keeps it and `z.any().parse(arr)` keeps it. Round 17 added this row as an adapter divergence and
never checked whether a schema let it through; that framing was wrong for the common case.*
**Consequence for FIX-1266: this row is not evidence for the storage-boundary fix** — under the
ordinary array schema it never gets there.

Everything else passes whichever schema would plausibly hold it — and **what happens after that
is the three shapes below, not one outcome.** Do not compress this table into a sentence. The rows that never reach a
store at all on at least one adapter — `bigint` on every serializing adapter, a function or symbol
on every cloning one — make "is written, and comes back as something else" a description of the
quiet majority that is false for exactly those, and it groups filesystem with SQL, which is the
partition round 22 ran and falsified. *This line said exactly that for a round after the table
above it was corrected; it is the summary-of-a-table case in §10's derived-statement rule.*

**Whether that then lands in D1's replacement depends on the schema, and for most of this table
it does not.** D1 needs the schema to **reject the serialized form**: `Infinity` under
`z.number()` reads back as `null`, fails the parse, and the row is replaced by its default. But
under the permissive `z.array(z.any())` these branded rows actually use, the flattened values
still parse — a `Date` reads back as a string and `Map` / `Set` / `RegExp` as `{}`, all four
accepted on the next read (run) — and `-0` → `0` is still a valid number. So the next read
succeeds and nothing is replaced. **Route a round-trip hazard into D1 only when the schema would
refuse the serialized representation.** The rest are not the milder half: they lose data with no
rejection anywhere, which is the paragraph below.

**The class has three shapes, and the two loud ones are NOT mirrors — they split the adapters
along different lines, and the filesystem adapter changes sides between them.** `bigint` separates
memory from every serializing adapter; a function or symbol separates the clone-first adapters —
memory *and* filesystem — from **both** stringify-first adapters, **SQLite and Postgres**, which
are where the corruption becomes durable. **No two-adapter model describes both, so a test design
built on one will get the other wrong** (D4 says the same thing to FIX-1266: do not restore the
symmetry). Read off the columns above:

1. **Converts quietly — the majority.** `Date`, `Map`, `Set`, `RegExp`, `Infinity`, `undefined` in
   an array, `-0`, a sparse hole, a non-index array property, and `NaN` under a permissive schema.
   The write resolves on both sides, and the two adapters end up holding different data.
2. **Loud on the durable side — `bigint` alone.** `structuredClone(1n)` succeeds and preserves the
   value, so the memory store keeps it, while `JSON.stringify` throws
   (`TypeError: Do not know how to serialize a BigInt`) and every JSON-backed adapter — SQLite,
   Postgres, filesystem — **rejects the write outright** at persist time, with a raw error naming
   no field, and nothing lands. It **passes in tests and fails in production**: the memory store
   is what tests and local development run against. *(Run on all three, round 22: memory holds
   the live `1n`; filesystem and SQLite each throw a `TypeError` naming BigInt and store no row.
   This is the one shape where the filesystem adapter does group with the JSON column, because
   `structuredClone` carries a bigint through to the serializer.)*
3. **Loud on the clone-first side — function and symbol.** Not a mirror of shape 2 in any part,
   and round 22 ran it rather than reading it. `structuredClone` throws `DataCloneError`, so
   the write **fails on memory *and* on the filesystem adapter**, which clones before it
   serializes. On **both SQL adapters** the store takes the value —
   `store-sqlite/src/resource-state-store.ts:212` and
   `store-postgres/src/resource-state-store.ts:147` each call `JSON.stringify(state)` with **no
   clone step anywhere in the package** — and **the row lands corrupted**: `null` in array
   position, the key **dropped entirely** in object position. The call *still* throws
   `DataCloneError`, from the registry's own read-back of the state it just wrote
   (`resource-registry.ts:1588` → `readState`, `:1492`). **So the caller sees an error on every
   adapter, and on the two stringify-first ones the corruption is already durable when it
   does.** An error is not evidence the write was refused, which is the half the earlier
   "corrupts quietly" phrasing hid: it is quiet about the *write*, not about the *call*.
   *Corrected round 25: this said "SQLite alone" for three rounds, which contradicted the table
   directly above it — whose last column has read **"Stringify-first (SQLite, Postgres)"** since
   round 22. The filesystem adapter's own comment (`filesystem/resource-state-store.ts:164`)
   says so too: "**both SQL adapters `JSON.stringify` before their first query**". The run
   reached SQLite and the sentence was written from the run rather than from the partition the
   run established — §10's derived-statement failure, one more time.*

Verified on the repo's Node (v22.22.2): `structuredClone({x:1n}).x` returns `1n` while
`JSON.stringify({x:1n})` throws; `structuredClone` throws `DataCloneError` on both a function and
a symbol while `JSON.stringify([v])` gives `[null]` and `JSON.stringify({x:v})` gives `{}` for
each. Alongside them, `Infinity` →
`{"x":null}`, `NaN` → `{"x":null}`, `undefined` → `{}`, `-0` → `{"x":0}`, `Date` →
`{"x":"1970-01-01T00:00:00.000Z"}`, and `Map` / `Set` → `{"x":{}}`.

**Three shapes, one boundary check — this is not three fixes.** The decidable test is still the
one the table is drawn on: `JSON.parse(JSON.stringify(v))` deep-equals `v`. It selects all three.
The shapes describe what a *caller observes*, which is what the **tests** have to match.

**The trap for a test author, and it is wrong in both directions.** A test asserting "the memory
and JSON sides hold different values" fails on **both** loud shapes for opposite reasons: on
`bigint` there is no JSON value to compare against, and on a function or symbol there is no memory
value. A fix designed only for silent conversion covers neither.

**The branded rows are the ones that force the phrasing.** A `Date` or a `Map` is not
"unsafe" in any sense a type check can see: it serializes without complaint, and it serializes
to something *else*. Nothing throws on either side, so there is no failure to notice — the two
deployments simply hold different data from the same call, and the one that lost its contents
finds out on a later read.

`cloneValue` is what makes the memory column behave differently: it uses `structuredClone`
when available and only falls back to a JSON round-trip otherwise
(`core/src/helpers/clone.ts:15-21`).

*(The last three rows — `-0`, sparse arrays, array custom properties — were added in rounds 15
and 17. They are the same class and the same adapter split; none needs its own defect entry.)*

### 7d. Why this issue is documentation, and the record on the two tiers

**The verbs ship, and they are not this issue.** D-6's Ask 1 was decided **B** (document the
gap) on 2026-08-25 and **amended to A** on 2026-08-26: resource `incState` / `pushState` ship,
at medium priority, as **FIX-1269**. What carried was **API consistency** with the bag, not a
this-cycle consumer need — the usage argument below is unchanged and was reweighted, not
refuted. **This block records the decision; it does not argue it.**

*The usage picture, kept because it sizes the verbs rather than opposing them.* Every increment
and append on a resource in this repository today is **compound** — semantic memory's `addFact`
appends a fact *and* bumps a counter in one write; working memory's `advance` bumps a turn
counter *and* recomputes every entry. None would be rewritten to use a single verb, so the two
new methods replace **zero** existing call sites. That is why they are sized as symmetry, and
why nothing in §11 may present them as a fix for contention.

**The two tiers, which must not be conflated — conflating them is what made D-6 look
expensive the first time it was asked:**

| | What it is | Where |
|---|---|---|
| **Tier 1 — handle surface** | `incState` / `pushState` on the resource handle, read-modify-write over the **existing** `runResourceCAS`. **No contention improvement over `updateState` — same path, same outcome**, the loser re-runs and lands. API symmetry only | **FIX-1269** — this cycle, medium priority |
| **Tier 2 — store interface** | Real store-native deltas, the liveness-gating safety argument, the theme-2 constraint amendment, the transferred proof obligation | **FIX-1267** — deferred, next to FIX-992 |

**FIX-1269 landing does not make FIX-1267 done.** A later Tier 2 re-implements the same two
verbs underneath without changing their signatures. Everything in the rest of this section is
**Tier 2's** record and is untouched by Ask 1.

**Philosophy** — tenet 1 (one true statement replacing the misleading published ones) and tenet 4
(the bag already has these verbs; documenting them as API is the honest form of "fix or
document").

**The store-native tier (the epic's Tier 2) — deferred at D-6, not dropped.** Two things are
worth carrying forward: the reason that turned out to be false, and the reason that stands.

*The falsified reason, kept visible because the epic made the same error.* An earlier draft
deferred this on the grounds that native verbs *remove no conflicts*. That assumed a native
resource delta must carry a held `expectedVersion` — the epic's constraint says never use the
commutative `"any"` downgrade, since `"any"` asserts nothing about the row and can resurrect a
tombstone. But `"any"` is not the only version-free option. **Both SQL resource stores already
predicate every conditional update on `lifecycle = 'live'`**
(`store-postgres/src/resource-state-store.ts`, `store-sqlite/src/resource-state-store.ts`), and
a delta predicated on *liveness rather than version* is tombstone-safe by construction:
concurrent increments all land, and a delete that wins first makes the delta refuse without
resurrecting anything. So a lifecycle-guarded native delta **would** remove contention. Ruling
out one extreme is not establishing the other, and both the epic and this spec made that step
without noticing.

*What the deferral rests on.* Implementation cost, and a design surface nobody has evaluated:
a version-free resource write bypasses `runResourceCAS`, which is where the verified-no-op
check, the `previousState` basis and the `resource_change` gate live. The epic's theme-2 proof
obligation — *every row of the policy table survives* — comes back with it, and harder than
the version-checked form, because the commutative path has no basis to verify against. The
cost half is also where this spec was wrong twice in the other direction: the optional,
feature-detected delta verbs belong to the **scope-record** stores (`SessionStore`,
`RequestStore`, `UserStore`, `OrgStore` each `extends DeltaStoreOps`); resources go through
**none** of them, persisting via `ResourceStateStore`, which extends nothing and whose whole
mutation surface is `set`, `delete` and `deleteAll`. Reason about this from
`ResourceStateStore`, never from the scope-side precedent.

**If a later cycle picks the tier up, it is an epic-theme rewrite, not a child leftover.**
Theme 2 frames the constraint as *held `expectedVersion`, never `"any"`* — and the
liveness-gated option is neither, so the constraint is **incomplete rather than merely
deferred**. A future cycle has to amend theme 2 to name lifecycle-guarded as an allowed
exception, next to FIX-992, rather than inherit "never `any`" and conclude the tier is
unreachable. Cite **D-6 (#1446)**. Epic #1365's "Tier 2 deferred" stays **deferred** — do not
fold it to dropped.

**Where the complexity in this issue is:** not in any code. It is in getting each map row's
*reason* right rather than its existence — six review passes have each corrected a row that
read as true.

**The lesson that shaped the map, and the one the docs depend on:** *don't assert into a
subsystem you aren't changing.* Nearly every correction across those passes landed on a claim
about the **state bag**, which this issue does not touch; the resource column stayed stable
throughout. A comparison is a claim about two systems, and a spec only owns one of them. So
row 10 states the bag side **by reference**, and where a planned doc page genuinely needs a
bag fact, the fact lives in §11 beside the page that publishes it, to be re-verified at
writing time.

**Round 22 showed the limit of that remedy, and it is worth stating plainly: "by reference" is
not a substitute for running it.** Row 10's bag half was deliberately stated by reference for
three rounds — and it was still wrong, because the reference it deferred to was a code comment
(`stores/cas.ts:170`) asserting the very thing the code beneath it does not do. Deferring to the
subsystem's own account of itself inherits that account's errors. **Where a comparison rests on
a load-bearing claim about the subsystem you do not own, the resolution is a run against that
subsystem, not a citation into it** — which is what `spec-poc/FIX-1154-bag-resurrection/` now
is, and why the bag gets a POC of its own rather than a footnote in the resource one.

**Keeping the Linear mirror honest (BP-037) — the normalization recipe, and why a raw compare
must never be the criterion.**

The mirror is the durable copy; this branch never merges. Re-sync it in the same step that
pushes. **Confirm the sync on normalized content, never on bytes** — Linear re-renders markdown
on store, so a byte compare reports drift on a correct mirror every time. At round 25 the branch
and the mirror differed by **872 raw characters and 0 normalized characters**: the mirror was
already correct, and four rounds of "it has drifted again" were partly this check crying wolf.

Apply these in order; **the order is load-bearing in two places**, both of which produced a
false drift report before they were fixed:

1. Strip code fences and inline backticks.
2. Images `![alt](url)` → `alt`.
3. **Markdown links → their link TEXT only, discarding the href.** Linear **auto-linkifies bare
   issue identifiers** on store, so `FIX-1253` in our source becomes a full link in theirs. Worse,
   **the generated label does not always name the same issue as its href** — a bullet rendering as
   `flow-state-dev#1289` was observed pointing at FIX-1154, an identifier appearing nowhere in the
   source. **The href must not participate in the comparison**, or the check can never pass.
4. Autolinks `<https://…>` → the bare URL (Linear adds these brackets around bare URLs).
5. Drop any surviving bare URL entirely, for the same reason as (3).
6. **Bullet markers → one canonical marker. This MUST precede step 7.** Linear stores `-` as `*`.
   Stripping emphasis first erases a `*` bullet on *their* side while leaving our `-` intact, and
   the compare then diverges at the first list in the document, forever. *This exact inversion is
   why the round-22 recipe never converged.*
7. Strip emphasis markers `*` and `_`.
8. Table separator rows → one token: `|---|`, `| -- |`, `|:--|` are all the same row.
9. Collapse table cell padding around `|`.
10. Headings: keep the level, drop the padding.
11. **Strip blockquote markers.** Linear stores a multi-line blockquote as one block and drops
    the `>` on continuation lines; ours keep it on every line.
12. Collapse all whitespace — **last**, so no earlier step depends on layout.

Compare the two normalized strings. On a mismatch, walk to the first differing character and
print both sides with context — a length delta alone cannot tell a real edit from a formatting
artifact.

## Spec evolution

**Rounds 1–17.** This document was drafted as an implementation spec for two new resource
verbs and was rewritten at round 18 into the gap write-up D-6 asked for. The verb-level
contract it carried — key typing, the runtime unknown-key backstop, availability conditions,
the refusal set, the retry-path and field-survival test predicates, and the twenty-six CI
behaviours — was **cut**, not filed off. **Round 25 note: Ask 1 was amended back to A, so
those methods are shipping after all — as FIX-1269.** That cut material is the closest thing
to a starting point for it and remains in this branch's history at `edbe3513`; whoever takes
FIX-1269 should read it before re-deriving the contract. It is Tier 1 only — decision 2's tier
is a different design (store-native, liveness-gated) and would not inherit much.

**What the seventeen rounds actually bought, and what survived the rewrite:**

- **The map's row-by-row reasons.** Six passes produced roughly twenty confirmed factual
  corrections. Nearly every one landed on a claim about the **state bag**, a subsystem this
  issue does not change, while the resource column stayed stable throughout. That is why row 10
  states the bag side by reference and why §11's bag facts sit beside the page that publishes
  them, flagged for re-verification. **A comparison is a claim about two systems, and a spec
  only owns one of them.**
- **Six defects on `main`**, none of which the issue set out to find. Four (D1–D4) trace to one
  decision in `normalizeResourceState` — storing the output of `safeParse` instead of
  validating the candidate and storing the candidate. Three rounds narrowed a rule that was
  quietly compensating for it before anyone checked one layer down. **When a rule needs
  narrowing repeatedly, check whether it is covering for a bug somewhere else.**
- **The POC, which is now the write-up's evidence base.** The refusal hazards were argued in
  prose for three consecutive rounds, each round enumerating the value kinds known at the time
  and each round missing a neighbour. They were then run. **When a rule has been corrected in
  prose twice, the third correction should be a test** — prose can be wrong in a way that reads
  fine; a row asserting `keep: "schema-default"` cannot.
- **Two sweep directions, and both were needed.** *Backwards:* has a neighbour outgrown this
  rule? — which found real defects three rounds running, because a widening has a blast radius
  over every rule that enumerated the old, narrower set. *Forwards:* now that this rule is
  wider, what does it wrongly include? — which found three over-inclusions the backwards sweep
  could not see, since new members satisfy the widened rule by construction. **After widening a
  predicate, walk its new members and ask what each now owes that it cannot pay.**
- **A derivation's published output goes stale even when the derivation is right.** The
  read-only blast radius was stated as a derivation over callers precisely so a list could not
  rot, and its worked output still missed a caller one hop further out. **A derivation stated
  correctly and then enumerated by hand once inherits every weakness of the list it replaced.**
- **Rules get written at the width of the instance that motivated them.** The round-trip rule
  was drawn at non-finite numbers (because `Infinity` prompted it), then at JSON-safety
  (because `undefined` and `bigint` broke it), and neither held — a `Date` is JSON-safe and
  still stores differently on two adapters. The boundary that holds is the property the storage
  layer actually needs.
- **A survey is a claim like any other.** "No in-tree resource uses a passthrough state schema"
  stood for two rounds and was false, and a count reported as "declarations" was actually
  mentions of the word (340 versus 137). BP-003 says to execute the check rather than read it;
  the gap was executing a check aimed at a *neighbour* of the claim, which is the failure tenet
  7 names.
- **Fifteen rounds did not notice the document's own first line.** It led with a ref and an
  artifact label before the problem, which `AGENTS.md` prohibits outright for specs. A rule
  about the top of the file is invisible to every review that starts by looking for the
  interesting part.
- **Three enumerations in this document came up short, and each was extended by hand rather
  than replaced by a rule.** The read-only blast radius, the round-trip value kinds, and now the
  published pages carrying the CAS guarantee — §11 listed three, review named two more, and the
  sweep found two reference pages worse than any of them. Extending a list answers the instance;
  it does not answer the next one. The fix each time was to state the **selection rule** and the
  command that runs it, so the list becomes an output rather than an inventory — which is what
