# FIX-1159: `fsdev init` — wire FSD into an existing project — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

Someone who wants to try FSD in a project they already have has no way in. The only
documented path is cloning our monorepo, so adding FSD to an existing Next.js app or Node
service means copying files out of our repository by hand and guessing at the wiring —
config, the route that serves flows, the keys, the scripts. Most people stop there.

**Why now** — Public Launch points strangers at a front door that does not exist. Everything
else in that project assumes a person can get FSD running in their own code in a few minutes.
There is no workaround worth naming: hand-copying our internal wiring is what we are trying to
stop asking people to do.

### 2. Solution in plain terms

One command, run inside a project that already exists, that sets FSD up without disturbing
anything already there. It works out what kind of project it is, writes the few files FSD
needs, appends to the handful it must touch, installs the dependencies through whatever
package manager the project already uses, and then prints exactly what to run next.

The shape of the answer is mostly **subtraction**. The obvious version of this command
generates a server file for non-Next projects, adds a `fsdev` script to `package.json`, and
hands the developer a hand-written entrypoint to maintain. Each of those three is a place to
get security, environment loading, or naming wrong — and our command-line tool already does
all three correctly today. So init writes **less**: no generated server, no package script.
For a Next.js app it writes a real route, because that is the only way FSD can reach a server
the developer already runs. Everywhere else FSD arrives as a second process that our own CLI
starts.

**Philosophy** — tenet 3 (earn every addition): every file init does not write is a file
nobody has to keep correct. Tenet 5 (fix at the owning layer): loading credentials and
refusing to expose an unauthenticated flow on the network are the CLI's jobs, and it already
does both — a generated entrypoint would re-implement them one layer down and get them wrong.
Tenet 2 (composition over features): init composes commands that already ship rather than
generating new surface beside them.

### 6. Decisions & rules — the sign-off surface

1. **A project that is not Next.js gets no generated server file. FSD runs there as a second
   process started by our own tooling — `fsdev dev` while developing, `fsdev serve` in
   production.**
   *Rejected:* generating a small `src/fsdev-server.ts` for the developer to own, which is
   what the epic's sketch showed.
   *Locks in:* the process model for every non-Next host belongs to us, not to a file sitting
   in the customer's repo. That means we can fix or improve how it starts in a normal release
   and every existing project gets it; it also means a customer who wants to change how the
   server boots has to reach for our flags rather than edit a file. The reason it is worth
   that trade is that the generated file was the only thing in this command that could ship a
   security defect: a hand-written server exposes the demo flow to everyone on the local
   network and never reads the key init just saved, and both failures are silent.

2. **The generated setup keeps a first session on disk, so restarting the server does not
   erase it — using file storage that ships with FSD, not a database.**
   *Rejected:* memory-only (a restart wipes the conversation during the exact hour someone is
   forming an opinion) and SQLite (needs a compiled native component, which fails to install
   on some machines — a first-hour failure we would be choosing on purpose).
   *Locks in:* init creates a data directory in the customer's project and tells their version
   control to ignore it. Cheap to revise later: it only affects projects that run init after
   we change it.

3. **The "what to run next" instructions invoke FSD directly rather than through a shortcut
   added to the project's own scripts, and init adds no such shortcut.**
   *Rejected:* adding an `fsdev` entry to the project's scripts and printing the shorter
   command.
   *Locks in:* init never has to decide what to do when the project already has something
   called `fsdev` — it cannot overwrite what it does not own, and it cannot print a command
   that would run someone else's script. The cost is that the printed commands are slightly
   longer. Securing the short public name (FIX-1162) later becomes a nicer alias on top of
   this, not a change to what init writes.

**Non-goals** — the content of the agent-instructions file (FIX-1160 authors it; init only
places it), the `create-fsd-app` wrapper and its demo content (FIX-548), and any host beyond
Next.js App Router and plain Node. A project init cannot identify is told so and left alone
rather than guessed at.

**Size:** Large — 7 production files · 14 test behaviours · 3 doc surfaces · 3 PRs.

### 3. Tradeoffs & alternatives

**Alternative: generate a server entrypoint for Node projects**, as the epic's illustrative
diff showed. Rejected on evidence rather than taste. The framework's `serve()` binds all
network interfaces by default and applies no authentication guard of its own — the guard
lives one layer up, in the CLI command. It also does not read `.env.local`; only the CLI's
resolution path does. So the natural three-line generated file exposes the demo flow to the
local network *and* fails on the first run with a missing-provider error, having just asked
the developer for their key. Both are silent in the sense that nothing in the generated file
looks wrong.

**The simpler approach: skip detection and just write files.** Genuinely tempting — detection
is the fiddliest part. Insufficient because the Next.js and Node paths differ in the one way
that matters to a developer (a route inside their app vs. a second process on another port),
and a command that guesses wrong leaves them with a route file in a project that has no route
convention, or no way to reach FSD at all.

**Where the complexity is:** not the file writing. It is the **idempotent, additive edits to
files the project already owns** — appending a delimited section to an `AGENTS.md` that
already exists and updating that same section on a second run rather than appending a second
one, ordering the ignore entry before the credential is written, and reporting honestly what
happened to each file. That is where a bug damages someone else's repository, which is the
only kind of bug this command can ship that is not recoverable by deleting a file.

### 4. Focus practices (1–5)

1. **Never write a credential before it is ignored** (tenet 5, BP-031-adjacent) — the
   `.gitignore` entry lands in the same edit pass and strictly before the `.env.local` write.
   A fresh `create-next-app` hides this because its own ignore rules already cover it;
   arbitrary existing projects do not.
2. **BP-035 (second-path checklist)** — the second path here is *the second run*. Every
   in-place edit is exercised twice in tests, and the second run must update its own section
   rather than duplicate it. It is also the path where a project already has each of the four
   files.
3. **One convergence point for the in-place edits** (tenet 5) — all four editable files go
   through one append-or-update mechanism with one delimiter convention, so the
   never-overwrite guarantee is enforced in one place rather than re-argued per file.
4. **Tenet 7 (prove the goal, not the mock)** — the goal check runs init into projects
   created by the real `create-next-app` and a real bare Node project, with a real model, and
   asserts seeded content survives. A unit test over a temp directory cannot show that.

### 5. What using it looks like (1–5 examples)

**Into an existing Next.js app** *(what this spec proposes; today there is no such command):*

```
$ cd my-existing-app
$ npx @flow-state-dev/cli init

  Detected  Next.js (App Router)  ·  package manager: pnpm
? Model provider ›  OpenAI
? OPENAI_API_KEY ›  sk-••••••••

  Created   app/api/flows/[[...path]]/route.ts
            flows/hello.ts
            fsdev.config.ts
  Modified  .gitignore     (FSD ignore entries)
            .env.local     (appended OPENAI_API_KEY)
            AGENTS.md      (appended an FSD section; your existing content is unchanged)
            package.json   (+6 dependencies)
  Installed via pnpm — pnpm-lock.yaml was rewritten by pnpm, not by init

  Nothing was overwritten. Every file above was created or appended to.

  Next steps

    pnpm dev                      your app, now serving /api/flows/*  → http://localhost:3000
    pnpm exec fsdev dev           the FSD DevTool                     → http://localhost:4200
    pnpm exec fsdev run hello send --input '{"userId":"u1","message":"hi"}'
```

**Into an existing plain-Node project** — the same command; the difference the developer sees
is that FSD is a second process rather than a route in their app:

```
  Detected  Node project (no host framework)  ·  package manager: npm
  FSD will run as a second server alongside yours.

  Next steps

    npm exec fsdev dev            FSD API + DevTool  → http://localhost:4200
    npm exec fsdev serve          the same API, for production
```

**Running it twice** — the guarantee that matters:

```
before  AGENTS.md contains the developer's own instructions + one FSD section
after   the same file, same developer content, the FSD section updated in place
        (not appended a second time)
```

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

`fsdev init` is a new command in `@flow-state-dev/cli`. It is a pipeline over the project
directory: detect, author new files, edit existing files additively, install, report. Nothing
it writes imports anything from our monorepo.

```mermaid
flowchart TB
  A[detect host + package manager] --> B[author new files]
  A --> C[edit 4 files in place]
  C -->|ignore entry BEFORE key write| C
  B --> D[install via detected PM]
  C --> D
  D --> E[report all 5 files + next steps]

  B -.Next.js.-> B1["app/api/flows/[[...path]]/route.ts"]
  B -.always.-> B2["fsdev.config.ts · flows/hello.ts"]
```

- **Detection** — host framework from the project's dependencies plus the App Router
  directory convention; package manager from the lockfile present, falling back to the
  `npm_config_user_agent` of the invoking process. No detection logic exists in the CLI
  today; this is new.
- **Authored files** — `fsdev.config.ts` (default-exports `createFlowState({ flows, stores })`
  with the decision-2 store profile), `flows/hello.ts`, and for Next.js an **optional**
  catch-all route. The optional form is load-bearing: the engine registers `list_flows` as
  `GET /` on the mount base, which is the bare `/api/flows` that the client's `listFlows()`
  requests. A required catch-all needs at least one segment, so the bare URL returns a
  framework 404 while every nested route works — presenting as a broken client rather than a
  wrong route file. `apps/kitchen-sink/app/api/admin/queues/[[...path]]` is the in-repo
  precedent for the optional form.
- **In-place edits** — one mechanism, four files, append-or-update against a delimited
  section, never overwrite.
- **Install** — invoke the detected package manager's install; never write a lockfile.
  The provider SDK for the chosen provider (e.g. `@ai-sdk/openai`) is installed as a real
  dependency, and so is `@flow-state-dev/devtool` as a dev dependency: the first is only a
  dev dependency of our `core` package and so never reaches a consumer, and the second is an
  *optional peer* of the CLI, satisfied inside our monorepo and by nothing at all outside it.
  Without both, the two commands the next-steps block prints fail immediately.
- **Next-steps block** — authored here as a reusable module, because FIX-548 reuses it
  verbatim (epic theme 5).
- **Untouched:** the engine, the adapters, every block kind. Init generates configuration and
  wiring; it changes no framework behaviour.

**Sketch — pseudocode. Illustrative, not the contract. React to the shape.**

```
detect(project):
    host ← "next" if a Next dependency and an app-router directory, else "node"
    pm   ← from lockfile, else from the invoking process's user agent

editInPlace(file, section):                      ← the one convergence point
    if file absent:            create with section
    else if section present:   replace between the delimiters   ← the second-run path
    else:                      append section, leave everything above untouched

run:
    detect
    ask provider + key
    author new files (route only when host is next)
    editInPlace(.gitignore, ignore entries)      ← strictly before the next line
    editInPlace(.env.local, provider key)
    editInPlace(AGENTS.md, the FSD section)
    editInPlace(package.json, dependencies only) ← no script; decision 3
    install through pm
    report all five paths, then the next-steps block
```

What this asks a reviewer: *is one append-or-update mechanism across four very different file
formats the right shape, or should `package.json` (structured) be separated from the three
text files?* That is the real question in this sketch.

**No POC.** The premises this design rests on were settled by reading the code rather than
running it, and each is a single unambiguous fact: `serve()`'s default host, where the
authentication guard actually lives, where `.env` loading actually happens, how `list_flows`
is registered, and whether the provider SDK and DevTool packages reach a consumer. §12 records
them.

### 8. Implementation sequence

1. **The in-place edit mechanism** — one module, the four file shapes, delimited
   append-or-update. *Test:* create-when-absent, append-when-present, update-on-second-run,
   and that content the file already had is byte-identical afterwards. *Depends on:* nothing.
2. **Detection** — host framework and package manager, including the "cannot tell" outcome.
   *Test:* a Next App Router project, a bare Node project, each lockfile, and an
   unidentifiable directory. *Depends on:* nothing.
3. **Authored file templates** — config with the decision-2 store profile, hello flow, and the
   optional catch-all route. *Test:* the generated config type-checks and loads; the bare
   `/api/flows` path resolves as well as a nested one. *Depends on:* nothing.
4. **The command** — composes 1–3, prompts for provider and key, orders the ignore entry
   before the key write, installs through the detected manager, reports all five files and
   prints the next-steps block. *Test:* the §5 transcripts, and that a second run is additive.
   *Depends on:* 1, 2, 3.
5. **Register** `init` on the CLI program, and **narrow** the CLI's declared Node range to the
   floor its own config loader already documents (native TypeScript stripping) — otherwise
   init installs cleanly on a runtime where every command it just printed fails at config
   load. *Depends on:* 4.

**PR plan.** Three sub-PRs; the first two are independent.

| sub-PR | deliverables | depends_on |
|---|---|---|
| a | the in-place edit mechanism (step 1) | — |
| b | detection + authored file templates (steps 2–3) | — |
| c | the `init` command, install, next-steps block, registration, engines floor (steps 4–5) | a, b |

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| Host framework cannot be identified | Say so and stop. Do not guess a route location. |
| `AGENTS.md` exists with unrelated content | Append a delimited section; everything above untouched. |
| Second run | Update the existing delimited section in place; never a second one. |
| `.env.local` already holds the provider key | Keep it, say it was found, write nothing. |
| Project already has `fsdev.config.*` | Do not overwrite. Report it and continue with the rest. |
| Project has no `package.json` | Not a Node project; stop with that message. |
| Install fails (offline, registry error) | Files stay; report the failure and the exact command to retry. Do not roll back. |
| `.gitignore` absent | Create it with FSD's entries, before the key write. |
| Node runtime below the config loader's floor | The existing error already prints three remediations; step 5's engines range stops it being reached by install. |

**Taxonomy:** everything before install is recoverable and leaves the project in a state the
developer can inspect. A failed install is non-fatal and retryable. The only refusals are
"this is not a project I can identify" and "this is not a Node project", both stated before
anything is written.

### 10. Testing strategy

**Goal & goal check** (the epic's proof for this issue; real model, real projects — two runs
because they are different shapes, not the same check twice):

- *Mounted-route path* — a fresh `create-next-app`, seed distinctive content into each of the
  four in-place files, run init, then `fsdev run` returns a streamed model response, a route
  that existed before init still responds, **the bare `/api/flows` responds**, and all seeded
  content is intact.
- *Second-process path* — an existing plain-Node project with its own server, seeded the same
  way: the printed command starts FSD, a call to it returns a streamed model response, the
  project's own server still runs, and the seeded content is intact.

Neither run pre-exports the provider key; the key goes in through init's prompt, which is
what a real user does and what makes the credential path actually exercised.

**CI specs** (the behaviours, not the test names):

- one behaviour per decision in §6, in observable terms
- **the second run** (BP-035) — every in-place edit exercised twice, asserting update rather
  than duplicate
- **the additive guarantee** — pre-existing content in all four files is byte-identical after
  init, including the case where the project already has all four
- **ordering** — the ignore entry is present before the credential is written, asserted on the
  sequence of writes rather than only the end state, since the end state looks identical
  either way and the hazard is a crash in between
- **the bare mount path** — `/api/flows` resolves, not only `/api/flows/<something>`. This is
  the one that a naive route test misses.

**Discipline:** `tdd`. The seam is the init pipeline against a temporary project directory —
every behaviour above is reachable from a vitest spec with no network and no real host
framework, except the two goal checks.

### 12. Dependencies, open questions & follow-ups

**Dependencies:** none blocking. FIX-1162 (npm short name) is **not** a blocker for this issue
— decision 3 makes init work under the scoped package name we already own, and the short name
becomes an alias later. FIX-1160 authors the agent-instructions content; init only places the
file, so the two can be built in parallel and this issue does not wait on it.

**Open questions:** none.

**Verified premises** (read from the code, so a reviewer need not re-derive them):

- `serve()` in `@flow-state-dev/node` defaults its host to all interfaces and applies no
  authentication guard itself; the guard is in the CLI's `serve` command. This is what makes
  decision 1 a security decision rather than a style one.
- `.env` loading happens in the CLI's runtime-resolution path, not in `serve()`. A generated
  entrypoint would not load the key init just wrote.
- `list_flows` is registered as `GET /` on the mount base, so the bare `/api/flows` is a real
  endpoint the client requests.
- `@ai-sdk/openai` is a *dev* dependency of our `core` package, so it never reaches a
  consumer; `@flow-state-dev/devtool` is an *optional peer* of the CLI, satisfied only inside
  our monorepo. Both must be installed by init.

**Cross-issue notes (raised on the epic PR, not decided here):** this spec deviates from two
details of the epic's illustrative sketch — it generates no `src/fsdev-server.ts` for Node
(decision 1) and adds no `fsdev` package script (decision 3). Epic theme 6 leaves the
*contents* of each edited file to this issue, so both are within scope, but FIX-548's Node
template inherits the process model and should match.

**Follow-ups (flagged, not built):**

- The two existing in-repo Next.js mounts (`apps/kitchen-sink` and `examples/hello-chat`) use
  the required catch-all and therefore 404 on the bare `/api/flows`. Out of scope here; worth
  its own small fix so our own examples do not model the broken shape.
