# FIX-1159: Adding FSD to a project you already have — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

Someone who wants to try FSD in a project they already have has no way in. The only documented
path is cloning our monorepo, so adding FSD to an existing Next.js app or Node service means
copying files out of our repository by hand and guessing at the wiring — config, the route that
serves flows, the keys, the scripts. Most people stop there.

**Why now** — Public Launch points strangers at a front door that does not exist. Everything
else in that project assumes a person can get FSD running in their own code in a few minutes.
There is no workaround worth naming: hand-copying our internal wiring is what we are trying to
stop asking people to do.

**Why this spec was re-shaped twice.** The approved version answered the whole problem with one
deterministic command. Three rounds of review then grew it a separate branch for each of: four
merge semantics across four files; CommonJS versus ESM config loading; Node 22.0–22.17 versus
22.18+; `packageManager` versus lockfile versus `npm_config_user_agent`; an already-tracked
`.env.local`; an existing `fsdev.config` that orphans the generated flow; an existing
`scripts.fsdev`; npm's option separator; `create-next-app` drift; the network-bind guard; a
two-process store race; provider SDK selection. Every one was found by a reviewer, one at a
time, and no round was the last. That is not a design converging — it is a command trying to
**enumerate** the shapes of repositories it has never seen. So brownfield became something an
agent runs. The second re-shape is this pass: the epic then assigned the set's **one** command,
and every deterministic file-writing path, to FIX-548. What is left here is the knowledge the
brownfield path is made of, and no command at all. §6 decision 1 carries the reasoning.

*Linear **FIX-1159** · Epic **FIX-1161** (`epic/building-with-fsd`, PR
[#1301](https://github.com/fixpoint-labs/flow-state-dev/pull/1301)) · spec PR
[#1310](https://github.com/fixpoint-labs/flow-state-dev/pull/1310) · Project **Public Launch**.*

### 2. Solution in plain terms

Four deliverables, and none of them is something a person types.

**Detection.** Which package manager, which Next version and where its app directory actually
is, which `fsdev.config.*` the CLI would load if several are present, whether `.env.local` is
tracked by git. Cheap, checkable
facts about a repository, and an agent guessing at them is exactly the failure this issue exists
to prevent. They ship as deterministic scripts, and their output — a report — is the contract
everything else reads. **Detection is also where every refusal is decided**, which is what keeps
a run that cannot succeed from writing anything first.

**The install skill's content.** Adding FSD to a repository that already exists is a reading
problem before it is a writing problem: what is already in `AGENTS.md`, whether this project is
CommonJS, whether a config already claims the flow registry. A coding assistant reads all of
that directly, decides each case in context, and leaves the result as a diff the developer
reviews before accepting. This issue authors what that assistant is told to do. FIX-1160
packages and ships it as a Claude skill inside the plugin.

**The next-steps block.** The paragraph a developer reads when the run finishes — which servers
now exist, what each is for, which ports they land on, and the caveats. One authored source,
used by the brownfield skill and by FIX-548's greenfield command, with the commands rendered for
whichever package manager the path is actually using.

**The wiring contract both entry paths satisfy.** What a wired-up FSD project looks like: the
mount pair, the config's shape and store profile, and the dependency set. This issue holds the
knowledge of what wiring FSD into an existing repo requires, so it writes the specification;
FIX-548's template is the deterministic *writer* that conforms to it. Writing the shape and
specifying it are different jobs, and separating them is what lets the skill cite a shared
contract instead of restating a template it can never read.

**Philosophy** — tenet 5 (fix at the owning layer): merging into an unknown repository is a
judgment problem, and putting judgment in a `switch` statement is fixing it at the wrong layer.
Tenet 3 (earn every addition): this issue used to ship a command, then a command plus a library
behind it; it now ships neither, because the epic gave the deterministic writing to the one
issue that has a shape it controls. Tenet 2 (composition over features): the skill composes
commands that already ship, and composes the project's own package manager instead of
re-implementing manifest editing.

### 6. Decisions & rules — the sign-off surface

1. **This issue ships no `fsdev init` — not the command, and not a library entry point behind
   it. The only artifact that crosses to FIX-548 is the next-steps block.**
   *Rejected:* keeping write mode as an in-process library that `create-flow-state` calls with
   the target directory, the declared host, the collected provider and key, and a declaration
   that config and flows are already present — which is the seam FIX-548's spec still describes
   and depends on.
   *Why:* the epic gives FIX-548 "the greenfield command and its template — **it is the only
   command in the set**", and lists this issue's deliverables as detection scripts, the skill's
   content, and the next-steps block. The five jobs FIX-548's spec routes through the library —
   the key, the ignore entry, the agent-instructions section, the install, the printed block —
   are the same five the epic's objective hands FIX-548 when it gives that issue the template
   "end to end … the agent-instructions file", and the same five its greenfield transcript shows
   the command doing with no init step in it. Its sequencing note then says the wrapper
   relationship "is gone, and what remains is the shared next-steps block". So a library here
   would keep the deterministic mutation the epic removed; putting it behind a function instead
   of a command does not change what it is. §12 carries the full citation trail.
   *Locks in:* **FIX-548's spec now has a hole in it** — the decision that made its template
   checked-in files while delegating the rest to init, its hand-off table, its fourth build step,
   four test behaviours and its dependency note all rest on a seam that will not exist, and it
   converged over three review rounds in that shape. Nothing in this document can close that; it
   is the first ask on the PR. What this issue gains is that FIX-548 waits on one small module
   rather than on this issue merging.

2. **Detection ships as scripts the skill runs, not as a subcommand of our CLI.**
   *Rejected:* an `fsdev detect` (or `fsdev init --report`) subcommand, which is how the
   previous draft delivered the same facts.
   *Locks in:* **a developer without a coding assistant has nothing to type.** The previous
   draft gave them a real keystroke — run the command in your own repo, get a report and two
   ways forward. That is gone, and the manual path is now a documentation page reached from the
   README rather than a command that meets them where they are. In exchange there is exactly one
   command in the epic, which is the thing the epic's ownership split is for, and the report
   stops being an artifact that has to be good enough to earn a keystroke from a person who
   wanted files. The scripts are authored here and travel with the skill, so the plugin a
   stranger installs carries both halves and neither can rot without the other.

3. **The config the brownfield path writes is `fsdev.config.mts`. FIX-548's template writes
   `fsdev.config.ts`, and that divergence is required rather than a coordination failure.**
   *Rejected:* one extension across both paths — either `.ts` everywhere, or `.mts` everywhere.
   *Why:* the extension is not a preference, it is a consequence of who controls the manifest.
   FIX-548 created the directory seconds earlier and adds `"type": "module"` to it, so `.ts`
   loads cleanly for both Turbopack and our CLI. The brownfield skill lands in a repository
   whose module system somebody else chose, and adding `"type": "module"` to it would rewrite
   content we did not author and break their code — the one thing the epic's additive guarantee
   forbids outright. Measured, not assumed (§12): under an explicit `"type": "commonjs"` a `.ts`
   config with `export default` fails outright; with no `type` field it loads but prints a Node
   warning on every command a beginner runs; `.mts` is clean in all three settings.
   *Locks in:* the two paths produce files with different names, so the skill's instructions
   cannot point at the template *file* for this one detail — they point at its shape and state
   the extension rule themselves. That is the narrowest possible exception to the drift rule and
   §10 spends a check on it. Aligning the wider corpus on one extension is a follow-up (§12);
   this issue should follow the corpus, not lead it.
   *Also locks in — and this is the part that decides a rule in §7:* **`.mts` is second in the
   CLI's filename precedence, behind `.ts`.** `CONFIG_FILENAMES` in `packages/cli/src/load-config.ts`
   is `["fsdev.config.ts", "fsdev.config.mts", "fsdev.config.js", "fsdev.config.mjs"]` and
   `locateConfig` loads the **first present** one, warning on stderr about each it is ignoring. So
   a `.mts` this path writes is authoritative only while no `.ts` sits beside it, and a developer
   who later adds one — or who runs FIX-548's template in the same directory — silently moves the
   config the CLI actually loads. The skill therefore writes `fsdev.config.mts` **only when no
   config of any extension exists**, and every later rule keys on the precedence *winner* rather
   than on "the config" (§7).

4. **The setup the skill writes keeps a first session on disk, using the development-only file
   store that ships with FSD, marked as such in the generated config and in the next-steps
   block.**
   *Rejected:* memory-only (a restart wipes the conversation during the exact hour someone is
   forming an opinion) and SQLite (a compiled native component that fails to install on some
   machines — a first-hour failure chosen on purpose).
   *Locks in:* the wired-up project is deliberately **not deployable as it stands** — a
   development store and no authentication — and it says so in its own output and in the docs.
   The run creates a data directory and adds it to the project's ignore file. Cheap to revise:
   it only affects projects wired up after we change it. FIX-548's template declares the same
   store profile, citing this decision.

5. **The next-steps block invokes the CLI directly rather than through a script added to the
   project, and no path adds such a script.**
   *Rejected:* adding an `fsdev` entry to `scripts` and printing the shorter command.
   *Locks in:* nothing ever has to decide what to do when a project already has something called
   `fsdev`, and no path prints a command that would run someone else's script. Printed commands
   are longer, and under npm they carry the option separator — `npm exec -- fsdev serve --host
   127.0.0.1` — because without it npm consumes `--host` as its own configuration and the
   command fails.

6. **The next-steps block is one authored source: the steps as content, the commands rendered
   for the package manager in use. It is verified by executing what it printed, never by
   matching a pattern.**
   *Rejected:* a block each path authors separately, and a single literal string shared
   byte-for-byte.
   *Locks in:* a brownfield run against a pnpm repo prints `pnpm dev` and `pnpm exec fsdev dev`
   while greenfield prints `npm run dev` and `npx fsdev dev`, so the rendered text genuinely
   differs and any test asserting the two are identical is wrong. What must not vary is the
   content: which servers exist, what each is for, which ports they land on, and the caveats
   that go with them. The module ships where `create-flow-state` can depend on it — the CLI is
   the obvious home, since both paths already require the CLI to be present — and it carries no
   monorepo reach.

**Non-goals** — the greenfield command and its template in every part (FIX-548); the packaging
and distribution of the install skill and the detection scripts (FIX-1160 — see §12); the
*content* of the agent-instructions file (FIX-1160 authors it, and on this path the skill places
it); and any host beyond Next.js App Router and plain Node. A shape nobody can identify is
reported, never guessed at.

**Size:** Medium — detection scripts · 1 authored Claude skill · 1 next-steps source block (two
conditional branches) + its exported comparison · 1 wiring contract · **34 named CI behaviours**
(≈47 assertions once the per-decision and per-fixture sub-cases are expanded) + the 2 goal checks ·
3 doc surfaces · 3 PRs.

### 3. Tradeoffs & alternatives

**Alternative: keep a deterministic brownfield command and cap its ambition** — handle the three
commonest host shapes properly and refuse everything else. This is the conservative version of
the same lesson and it deserved a real hearing, because it keeps the path testable in CI. It
fails on where the refusals fall. Of §1's thirteen branches, only three are about the *host
framework*; the rest are about the project's module system, its version-control state, its
package manager, and files it already owns — all of which vary independently inside "a Next.js
App Router project". Capping the host list does not cap the branch count, so we would ship the
same enumeration with a narrower door.

**Alternative: keep write mode as a library FIX-548 calls** — decision 1's rejected option, and
the one this pass turned on. Beyond what the epic says, it has exactly one caller: brownfield
cannot use it, because the skill is instructions plus scripts and instructions do not make
in-process function calls. So it would be a single-use abstraction in a package owned by another
issue, adding a build-and-merge edge between two issues the epic wants running in parallel. The
argument *for* it is real and should be said plainly: FIX-548's spec is converged and this breaks
it. That is a sequencing cost rather than a design argument, and §12 carries it rather than
absorbing it.

**Where the complexity is:** the **detection report**. It is what stops the assistant guessing,
and it is the one place a wrong answer is silent — a report that says "npm" about a pnpm project
produces a confidently wrong install and a lockfile the project never wanted. Everything else
here is authored prose.

**What the shape costs, stated plainly:** the brownfield path is not something we can prove in
CI. §10 replaces that check with a recorded run, which is weaker evidence, and §12 carries it as
an open question rather than burying it. **That trade has not been put to the owner, and this
document previously said it had.** What the owner changed was the delivery mechanism — brownfield
became agent work. The proof-strength consequence is a *coordinator* reading of that change,
recommended and never asked, and it is **reversible**: the reversal cost is a maintained fixture
repository per host shape, kept green on machines we do not control, which is the treadmill the
split was made to escape.

### 4. Focus practices (1–5)

1. **The safety properties are stated once and carried as instructions, not as branches.** Each
   was earned by a specific review finding. The epic's additive guarantee binds both entry
   paths now, so these are this issue's half of it rather than the whole rule:
   - Never overwrite a file the run did not author, and never rewrite content outside our own
     delimiters.
   - **Refuse** when `.env.local` is already tracked by git — naming the file and the
     `git rm --cached` the developer must run. Adding a tracked file to `.gitignore` does not
     untrack it, so ordering the ignore entry first is not sufficient on its own.
   - **Never ask for, accept, echo, or repeat a provider key.** The brownfield surface is an
     assistant conversation, so a key typed there is disclosed to a third party before it reaches
     the file. The run writes the empty variable line; the developer supplies the value; the run
     asserts presence and non-emptiness only. **The run handles the variable's *presence*, never
     its *value*** — every rule in this document is written that way, and any sentence implying
     the run receives, holds, or reads back a key is a defect in the document, not a variant.
   - **Never overwrite or duplicate a credential the developer supplied, in any file the loader
     reads.** A populated provider variable means write nothing at all — replacing our own section
     would put the canonical empty value over their key, appending a second assignment masks it at
     load, and writing an empty assignment into a *nearer* `.env.local` masks one held a directory
     up. Last-wins within a file and nearest-wins across files are opposite directions and both
     produce the same silent loss.
   - **Never replace between delimiters that are not exactly one balanced pair.** An unmatched
     start marker turns "replace our section" into "delete to end of file" in a file the developer
     owns. Count them in preflight and refuse anything but a clean pair.
   - **Write only beneath the write root, and resolve the roots before anything else.** The
     directory whose manifest declared the host is the only place the run writes; the package
     manager may be declared above it; git answers repository questions. Pointed at a workspace
     root, refuse rather than choosing an app.
   - **Decide every refusal from state the run has not modified** — including the ignore question,
     which is answered by evaluating the *proposed* file in a scratch location rather than by
     editing the real one and reading it back. Untracked is not the same as ignored, and our own entry is not the
     last word on the answer — a later `!.env.local` re-includes it. The guard has to run against
     the file as it will exist, not against a prediction of it (§7).
   - **Refuse a host the skill has no design for**, rather than reporting it as supported and
     discovering it at install time or at first request. A Next project that is Pages Router, or
     below the adapters' `>=15` peer range, is refused with the failing condition named.
   - **Refuse a package manager that is neither declared nor evidenced** — two lockfiles and no
     `packageManager` field, or no lockfile and no field at all. Name what was found and ask for a
     `packageManager` declaration, rather than picking one and installing through it. There is no
     ambient signal worth trusting: `npm_config_user_agent` describes how our own script was
     launched, not what the project uses, and defaulting to npm writes a lockfile the project
     never asked for.
   - **Refuse when a file the run must create is already there and is not ours** — checked for
     every required path before the first write, so a collision never leaves a half-applied repo.
     *Ours* is decided by the marker, never by the path being occupied: for a mount, the slot is
     the unit scanned and the marker is what classifies what the scan found. A rule that refused
     on occupancy alone would refuse every rerun of a project this skill wired up itself.
   - **Read the config the CLI would actually load, never merely "a config"** — it loads the first
     present of `fsdev.config.{ts,mts,js,mjs}` and ignores the rest, so a fact taken from a
     shadowed file describes nothing that runs. Report every candidate; act on the winner.
   - **Refuse when the next steps cannot be written truthfully** — no identifiable dev script **on
     a host whose next steps print one**, or a `pageExtensions` setting we cannot read — rather
     than printing a command that fails or writing a route the framework will ignore. The scope is
     the topology that spends the fact: a second-process host prints only `fsdev` commands, so a
     project with no dev script is a coherent host rather than an unwritable one.
   - Never print a command the project cannot run.
   - The Node path must not bind `0.0.0.0` with an unauthenticated flow.
   - Name every file the run touched and say what happened to each, the lockfile included.
   - The wired-up project is not deployable as it stands, and says so in its own output.
2. **Tenet 7 (prove the goal, not the mock)** — "never print a command the project cannot run"
   has caught three separate defects and every one of them survived a plausible-looking
   transcript. It is asserted by **executing the printed strings**, never by matching them
   against a pattern. See §10.
3. **BP-035 (second-path checklist)** — the second path is *the second run*. Every delimited
   section the skill writes is exercised twice and must update in place rather than duplicate.
4. **BP-031-adjacent (never make a decision from untrusted input)** — the report is derived from
   the filesystem and from `git`, and its provenance is stated per field. The skill acts on the
   report; it does not re-derive a fact the report already carries, and it does not overrule one.

### 5. What using it looks like (1–5 examples)

**An existing Next.js app — the mounted-route shape** *(what this spec proposes; there is no
such capability today)*:

```
you   add FSD to this project

      ▸ running FSD detection …
        host: next 15.4 (app router)  ·  app root: ./src/app
        package manager: pnpm (pnpm-lock.yaml)  ·  module: commonjs
        route extension: .ts (pageExtensions not set — Next's default)
        dev command: pnpm serve  (next dev -p 4000)
        fsdev.config: absent  ·  AGENTS.md: present, no FSD section
        .env.local: present, untracked
        no collisions on any path I need to create

      I'll create   src/app/api/flows/route.ts   src/app/api/flows/[...path]/route.ts
                    flows/hello/flow.mts         fsdev.config.mts
      and append to .gitignore · AGENTS.md · .env.local   (delimited FSD section)
      and add dependencies with pnpm, which rewrites pnpm-lock.yaml.
      (zod and @ai-sdk/openai included — your flow imports them directly.)

      Nothing already in those files will be changed. Review the diff before you accept it.

      [ diff shown · accepted ]

      Next steps

        pnpm serve           your app, now serving /api/flows/*  → http://localhost:4000
                             (this project sets no basePath; one would prefix that path)
        pnpm exec fsdev dev  the FSD DevTool                     → http://localhost:4200

        pnpm exec fsdev run hello send --input '{"userId":"u1","message":"hi"}'

      (Your dev script is `serve`, on port 4000 — that is what it prints, not `dev` and 3000.)

      Storage is on disk for development. Pick a real store before you deploy.
      AGENTS.md tells your coding assistant how to write FSD flows.
```

**An existing plain-Node service — the second-process shape.** A plain-Node project gives no
derivable mount point, and nothing edits an entrypoint it did not write, so FSD arrives beside
the server that is already there rather than inside it. The run says which shape it gave you:

```
      ▸ running FSD detection …
        host: node  ·  package manager: npm  ·  module: esm  ·  no mount point

      Your project has no convention that tells me where an FSD route would go, so FSD
      will run as its own process alongside your server rather than inside it.

      I'll create   flows/hello/flow.mts   fsdev.config.mts
      and append to .gitignore · AGENTS.md · .env.local
      and add dependencies with npm, which rewrites package-lock.json.

      Next steps

        npm exec fsdev dev              FSD API + DevTool  → http://localhost:4200
        npm exec -- fsdev serve --host 127.0.0.1
                                        the same API, without the DevTool

      Your own server is untouched and still starts the way it did.
      Storage is on disk for development, and the demo flow has no authentication,
      so serve binds to localhost only.
```

Two details in that block are load-bearing rather than cosmetic. The `--` separator is required:
without it npm consumes `--host` as its own configuration and the command fails. And
`--host 127.0.0.1` is required because `fsdev serve` defaults to `0.0.0.0` and the CLI refuses to
bind a network host when a served flow uses the framework's default principal resolver — which
the demo flow does. A bare `fsdev serve` fails on first use. §10 asserts both by running what was
printed.

**A repository that would publish the key — the refusal:**

```
      ▸ running FSD detection …
        .env.local: present, TRACKED BY GIT

      .env.local is committed to this repository, so I am not putting your API key
      in it. Run this first, then ask me again:

          git rm --cached .env.local
```

**A host the skill cannot serve — refused before anything is written:**

```
      ▸ running FSD detection …
        next 14.2.5 detected  ·  Pages Router (./pages)

      I can't add FSD to this project yet, and I've written nothing.

      Two things would need to be true:
        · App Router — the route adapter builds App Router route exports,
          and there is no Pages Router equivalent yet
        · Next 15 or later — the FSD Next adapter requires it, so the
          install would fail partway

      This project is on neither. https://flow-state.dev/docs/getting-started/existing-project
      has the by-hand path if you want to wire it up yourself.
```

**An ambiguous package manager — the same posture, a cheaper answer:**

```
      ▸ running FSD detection …
        lockfiles: pnpm-lock.yaml AND package-lock.json  ·  no packageManager field

      I can't tell which package manager this project actually uses, and installing
      through the wrong one would rewrite the wrong lockfile. Nothing written.

      Either delete the stale lockfile, or declare it — "packageManager": "pnpm@9.x"
      in package.json — and ask me again.
```

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

Three artifacts, no command, and nothing here imports from this monorepo at run time.

```mermaid
flowchart TB
  D["detection scripts<br/>filesystem + git, no writes"] --> R["the report<br/>JSON, one field per fact"]
  R --> S["install skill (SKILL.md)<br/>authored here · packaged by FIX-1160"]
  S -->|"reads the repo, decides each<br/>case, leaves a diff"| P["the developer's project"]
  N["next-steps blocks<br/>canonical text + placeholders"] --> S
  N --> G["create-flow-state (FIX-548)"]
```

**Every field below is relative to a root, and "the project root" is two different directories in
an ordinary monorepo.** This was left undefined and it has to be settled first, because a wrong
answer here is not a bad report — it is writing into the wrong directory. In a pnpm/npm/Yarn
workspace the app's manifest sits at `apps/web/package.json` while the **lockfile and the
`packageManager` field sit at the repository root**, and the two facts detection needs most are
therefore in different places. Run in `apps/web`, a root-only search finds no lockfile and no
declaration and reports the manager `undeclared`; run at the repository root, the search finds no
`next` in the root manifest and no App Router beneath it and reports the host `node` — which would
put a second-process setup, a config and a demo flow at the top of somebody's monorepo. **A pnpm
workspace is not an exotic layout**, so both outcomes are ordinary rather than edge cases.

**That interacts with a rule added one revision ago, and the interaction made it worse.** The
package-manager row now refuses on `undeclared` rather than guessing. Without an ancestor search
that refusal fires on **every app inside every workspace** — a rule intended to stop one
destructive guess, turned into a wall in front of a large share of real projects. Neither half is
wrong on its own; the pair is, which is what a per-edit consistency check is for.

**Every fact in this section is the output of somebody else's resolution algorithm, and writing
it down as a directly-observable property is the defect this document keeps producing.** Ten
findings across four review rounds have been the same mistake: which config the CLI loads (a
precedence list, not a file), which files occupy a route slot (a matcher's extension set, not the
name we picked), what the env chain resolves to (a walk with two different tie-breaks, not a
file), which directory the manager is declared in (a chain, not the app), what URL the mount
answers on (the router's `basePath` handling, not the path on disk). **Each was fixed where it was
found and the next one appeared in the rule written to fix it**, because every new rule was
written in the same idiom.

**So the resolutions are named, ordered, and derived once — and no later rule may re-derive one
from the filesystem.** The order matters because they depend on each other, and every defect above
sat exactly where two dependent resolutions were written in different places:

| # | resolved fact | the system whose behaviour defines it | depends on | ambiguous when |
|---|---|---|---|---|
| 1 | **workspace root** | the package manager's own workspace discovery — `pnpm-workspace.yaml`, a `workspaces` array, else the repository, else the write root | — | never; it is the outermost marker found |
| 2 | **write root** | the host framework, via the manifest that declares it | 1 | the target is a workspace root rather than a host → **refuse** |
| 3 | **package manager** | corepack + the manager's own precedence, across the whole chain 2→1 | 1, 2 | no declaration and disagreeing or absent lockfiles → **refuse** |
| 4 | **app root** | Next's `findDir` — root before `src/` | 2 | — |
| 5 | **route extension** | Next's `createValidFileMatcher`, from `pageExtensions` | 2 | not a plain array of literals → **refuse** |
| 6 | **mount URL** | Next's router, from `basePath` | 2, 4 | `basePath` not a plain string literal → **refuse** |
| 7 | **route slot occupancy** | the same matcher, over the scan set | 4, 5 | — |
| 8 | **loaded config** | the CLI's `locateConfig` — first present of four filenames | 2 | — |
| 9 | **effective credential** | the CLI's `loadEnvFiles` + `parseEnvFile` — nearest file, last line | 2 | — |
| 10 | **the file that will be filled** | resolution 9's answer | 9 | — |

**Two rules make this hold, and they are what the per-case patches could not give:** every
downstream rule **cites a numbered resolution rather than reading the filesystem again**, and a
resolution's *consumers* are checked when it changes. Resolution 10 exists as its own row for
exactly that reason — the tracked-by-git question is asked about **whichever file 9 selected**,
which is not always the write root's own, and writing it as "check `.env.local`" is how a run
came to point a developer's credential at a committed file.

**Three roots, and they genuinely differ:**

| root | what it is | what it decides |
|---|---|---|
| **the write root** | the directory holding the `package.json` that declared the host — the Next app, or the Node service. Detection is pointed at it, and it is reported | **everything the run writes.** The config, the flow, the mount beneath the app root, `.gitignore`, `AGENTS.md`, and the `.env.local` our section would be appended to. Nothing is ever written above it |
| **the workspace root** | the **outermost** ancestor declaring a workspace — `pnpm-workspace.yaml`, or a `workspaces` array in a `package.json` — else the repository root, else the write root. **A lockfile is not a workspace marker and does not bound this search**, because a lockfile is residue that can sit anywhere, including a stale one inside an app | **how far the package-manager search may travel.** It bounds the chain; it does not answer the manager question |
| **the repository** | whatever `git` says, which is already how `git check-ignore` and `git ls-files` behave | the credential questions — tracked, ignored, and the parent `.gitignore` files a scratch copy cannot reproduce |

**Bounding the search on the nearest package-manager signal was wrong, and it installs through the
wrong manager.** An earlier form of this table stopped the workspace search at the nearest
ancestor carrying *a lockfile or* a `packageManager` field. In a pnpm workspace whose root
declares `packageManager: "pnpm@9"` but whose app carries a **stale `package-lock.json`**, that
made the app its own workspace root: the search never travelled far enough to see the root's
declaration, the stale lockfile was the only evidence in range, and the run resolved **npm** — then
installed with it, writing a `package-lock.json` into a pnpm workspace and a `node_modules` the
workspace does not manage. A stale lockfile beside an app is common, which is what makes this
ordinary rather than exotic. **The boundary is a workspace declaration; the manager is decided
separately, across the whole chain.**

**So manager precedence applies once, over the entire write-root→workspace-root chain, and it is
not nearest-first.** Nearest-first is what let the stale lockfile win:

1. **Any `packageManager` field anywhere in the chain beats every lockfile anywhere in the chain.**
   It is the only declaration among these signals and corepack enforces it. Among fields, the
   nearest wins — an app may legitimately override its workspace.
2. **With no field anywhere**, lockfiles across the chain decide: all pointing at one manager →
   that manager; **disagreeing, or two at one level → `ambiguous`, refuse**, naming every lockfile
   found and its directory.
3. **No field and no lockfile anywhere in the chain → `undeclared`, refuse.**

**The install still runs in the write root**, whichever manager was resolved and wherever it was
declared: that is whose `package.json` must gain the dependencies. The lockfile it rewrites is the
workspace root's, and **the report says so by path**, because "your lockfile changed" is materially
different news when the lockfile is two directories above the app the developer was working in.

**Pointed at a workspace root, the run refuses rather than guessing which app was meant.** A
directory carrying `pnpm-workspace.yaml`, or a `workspaces` array, or several package manifests
beneath it, is not a host — it is a container of hosts, and nothing in it says which one the
developer wants FSD in. Treating it as a plain Node host is the false-`node` classification above,
and picking one app for them is the guess this whole issue exists to refuse. **So it refuses,
names what it found, and asks them to run it in the app they mean** — a one-line remediation from
a developer who already knows the answer. This is the same posture as the ambiguous package
manager: refuse the undecidable, and make the remediation cheap.

**Detection (the report).** One module, one shape, two renderers — JSON for the skill, prose for
the transcript the developer reads. Every field carries where it came from **and which root it was
resolved against**, because the skill is instructed not to overrule it:

| field | derived from |
|---|---|
| **the roots** | the write root, the workspace root, and the repository — resolved as above and reported as paths. A directory that is a **workspace root rather than a host** → `workspace-root`, which refuses and names the manifests it found beneath |
| host | read from the **write root's** manifest and directory conventions. `next` **only** when the App Router convention is present **and** the declared `next` satisfies `>=15`. Any other Next shape — Pages Router, or Next below 15 — is `next-unsupported`, which refuses; it must never fall back to `node`. No Next dependency → `node`. Otherwise `unknown` |
| **app root** | `app/` or `src/app/` **beneath the write root**, resolved **the way Next resolves it** — root first, then `src/` — and reported as a path, never assumed. Everything the run writes for a Next host goes beneath this path. A `pages` directory found the same way is reported too, because its parent has to match |
| package manager | **resolution 3.** Precedence applied once over the whole **write-root→workspace-root** chain, never nearest-signal-first: **any `packageManager` field anywhere in the chain beats every lockfile anywhere in it** (nearest field wins among fields); with no field, lockfiles across the chain must agree, and **disagreeing or doubled lockfiles → `ambiguous`, refuse**, naming each and its directory; **nothing anywhere → `undeclared`, refuse** — there is no third source (below). **Whatever the source, the answer is validated against the supported set — npm, pnpm, Yarn — and anything else refuses**, because being certain which manager a project uses is no help when no command forms exist for it. The report names the directory the answer came from |
| **route slot occupancy** | for each slot the run would write — `<appRoot>/api/flows` and `<appRoot>/api/flows/[...path]`, leaf `route` — every file present at the **scan set**: every currently enabled extension, **plus every extension this skill can itself emit (`ts`, `tsx`)**. The unit is the slot, not the filename we picked, and the scan set is wider than the enabled set on purpose (§7) |
| **route extension** | **resolution 5.** Which extension the mount files may use, from `pageExtensions` in `next.config.*`. Absent → Next's default `['tsx','ts','jsx','js']`, so `.ts`. Present as a plain array of string literals → prefer `ts`, else `tsx`, else **refuse**. Present in any form we cannot read statically → **refuse**; see below |
| **mount URL** | **resolution 6.** The path the mount actually answers on, which is **not** derivable from where the files sit: `basePath` in `next.config.*` prefixes every route. Absent, `''` or `'/'` → `/api/flows`. A plain string literal → that literal + `/api/flows`, carried into every place a URL is printed or probed. Present in any form we cannot read statically → **refuse**, exactly as for `pageExtensions` and for the same reason. Read from the same file in the same pass |
| **dev command** | the script that starts the host app, and the port it lands on, read from `scripts` in `package.json`. Reported for every host; **required only where the next-steps block spends it — the `mounted-route` topology.** No usable script on a Next host → **refuse**. On a plain-Node host → report `none` and proceed, because the `second-process` branch prints only `fsdev` commands and never names the host's script or URL |
| module system | nearest `package.json` `type` — `module`, `commonjs`, or absent |
| **existing config** | **every** `fsdev.config.{ts,mts,js,mjs}` present in the **write root**, reported as a list in the CLI's own precedence order with the **winner named** — the CLI searches cwd-only and loads the first present filename, ignoring the rest. A single-fact "config: present/absent" is what lets a run act on a file the CLI is not loading. Cwd-only is also why this one does not search upward: the CLI would not find an ancestor config either |
| **effective credential** | **resolution 9.** Every `.env.local` from the write root upward — the chain `loadEnvFiles` walks — reduced to **one** value and **one** path: first file that assigns the key, last assignment within it |
| **the file that will be filled** | **resolution 10**, and it is a separate row because it is separately dangerous. Whichever file resolution 9 named, or the write root's own when nothing assigns the key. **Tracked by git** (`git ls-files --error-unmatch`) and **would git ignore it** (`git check-ignore -q`) are asked about **that** file — not about the write root's by default. Tracked and ignored are different questions and both have to be asked, of the right file |
| **instructions file** | `AGENTS.md` in the write root; present or absent; and **how many of our delimiters it carries, with their line numbers** — not merely whether it has a section, since an unbalanced or duplicated pair refuses |
| **ignore file** | `.gitignore` in the write root, with the same delimiter accounting, for the same reason |
| declared FSD deps | which of ours are already in the **write root's** `package.json`, at what versions |
| runtime | the Node version running detection |

No detection logic exists in the CLI today; this is new, and it is the bulk of the work.

**Two of those rows refuse rather than report, and both exist because a permissive report defeats
the refusal posture.** Every refusal in this design is stated before anything is written; a
detection rule that admits a host the skill cannot serve moves the failure *after* the writes,
which is the one place the guarantee does not hold.

**Next is narrower than "a Next dependency", measured against the adapters.** Both
`@flow-state-dev/next` and `@flow-state-dev/vercel` declare `next: ">=15.0.0"` as a peer, and
`createNextHandler` is an App Router adapter by construction — it returns the
`{ GET, POST, PATCH, DELETE }` exports a route file needs, and awaits Next 15's `params`
promise. A Pages Router project needs a different handler shape that does not exist, and Next 13
or 14 fails the peer range at install. So a report of plain `next` for either shape hands the
skill a green light for a host it has no design for: it writes four files, then the install
fails or the printed route never answers. `next-unsupported` refuses first, names which of the
two conditions failed, and says what would make the project eligible. **Degrading to `node`
would be worse than guessing** — it would write a second-process setup into a Next app, which is
the one host where theme 8 says FSD arrives as a mounted route.

**Writing into the wrong app root breaks the project silently, which is the worst thing this
issue can do.** Next resolves its app directory with `findDir`, which checks `./app` **before**
`./src/app` and returns the first that exists — read from the published tarballs of `next@16.3.1`
and `next@15.5.23`, both carrying the comment *"prioritize `./${name}` over `./src/${name}`"*. So
creating a root `app/` in a project laid out under `src/app` does not extend their application.
It **changes which directory Next treats as the app**, and every route they had stops being
served. Nothing errors; the developer accepts a diff that added four files and discovers their
site is gone.

**The same mistake fails differently on Next 16, and one of the two failures is loud.** Next
16's `findPagesDir` adds a check `next@15` does not have: if a `pages` directory and an `app`
directory are both found and their parents differ, it throws *"`pages` and `app` directories
should be under the same folder"*. A project migrating incrementally — `src/app` alongside
`src/pages`, which detection accepts because App Router is present — gets a hard build failure
the moment our root `app/` lands, because our parent is the project root and theirs is `src`.
On `next@15` the same project silently shadows instead. **Two versions, two failure modes, one
cause**, and writing beneath the detected root removes both. This is why the app root is a
reported field rather than a constant: a rule that hardcodes `app/` is correct only for the
layout `create-next-app` happens to produce without `--src-dir`.

**A project can configure `route.ts` out of existence, and the run would report success.** Next
builds its App Router file matcher from `pageExtensions`: `createValidFileMatcher` composes
`` `(^route|[\\/]route)\.(?:${exts.join('|')})$` `` and `isAppRouterRoute` tests against it, so in a
project whose config sets `pageExtensions: ['jsx','js']` a `route.ts` file simply is not a route.
Both mount files land, nothing errors, and `/api/flows` does not exist — read from
`next/dist/server/lib/find-page-file.js` in the published tarball, with the default
`['tsx','ts','jsx','js']` read from `dist/server/config-shared.js`. The run must pick an
extension the project actually enables, and say which.

**Reading that value has to stay cheap, which decides the rule's shape.** Detection derives facts
from the filesystem and from `git`; it does not execute the project's code, and `next.config.*`
is a module that can export a function or compute its value. So: **when `pageExtensions` is a
plain array of string literals — the overwhelmingly common form, including the frequent
`[…, 'mdx']` — read it statically and choose.** When it is absent, the documented default
applies and `.ts` is correct. When it is present in any other form, we cannot know what it
evaluates to without running their config, so the run **refuses and says why** rather than
writing files that might be invisible. Refusing on the unreadable case is the conservative half
of a rule whose common case needs no refusal at all.

**The same file decides where the mount answers, and reading only half of it advertises an
endpoint that 404s.** `basePath` prefixes every route in the application, so in a project
configuring `basePath: '/portal'` the mount files land correctly, compile correctly, and serve at
`/portal/api/flows` — while the transcript, the next-steps block and the goal check all name
`/api/flows`. **Verified in the router rather than assumed:** `resolve-routes.js` in the published
`next@16.1.6` tarball tests `pathHasPrefix(curPathname, config.basePath)` and **`return`s
immediately when the prefix is absent — before any route matching happens** — then fetches the
matched page through `addPathPrefix(route.page, config.basePath)`. So the bare path is not merely
unmatched, it is rejected upstream of the matcher, and the endpoint we told the developer to open
does not exist.

**It is carried, not refused, because carrying it costs one substitution.** `basePath` is a plain
string in the overwhelming majority of configs that set it at all, and a project that sets one is
otherwise perfectly serveable — refusing it would reject a working host over a prefix. So the
resolved mount URL becomes a declared substitution like the dev command and its port, filled from
detection and used **everywhere a URL is printed or probed**, and the unreadable case refuses on
exactly the same terms as `pageExtensions`. **This is the third fact read out of `next.config.*`
and the second one whose absence was silent**, which is why the resolution table names the router
as the authority rather than the file: what we need is not the config's text but what Next does
with it.

**Nothing may print a command the project cannot run, and the block had no inputs with which to
keep that promise.** A brownfield host is not `create-next-app` output: a project may have renamed
`scripts.dev`, removed it, or pointed it at another port. A block rendered from the package
manager alone prints `pnpm dev` and advertises `localhost:3000` regardless, so the first thing
the developer types fails, or the URL sends them to the wrong place. **The dev command and its
port therefore become declared substitutions filled from detection, not constants.** The script is chosen by
name where a `dev` script exists, and otherwise by finding the single script that starts the
host; a port stated in that script's own flags is used, and when no port is stated the block
says where the framework's default lands rather than asserting a number as fact.

**The refusal that follows is scoped to the topology that spends the fact, not to the run.** On a
`mounted-route` host the printed command **is** the project's own dev script and the URL **is**
where it serves, so with no identifiable script there is nothing truthful to print and the run
refuses. On a `second-process` host neither placeholder appears at all: that branch prints
`{{exec}} fsdev dev` and `{{exec}} fsdev serve --host 127.0.0.1`, says the developer's own server
is untouched, and never names their script or their port. **A plain-Node project with no
identifiable script is therefore coherent rather than broken** — a library, a service started by
`node server.js`, a container entrypoint — and refusing it rejects a setup that would have
worked, on the strength of a field that setup never reads. The refusal condition is
`host is next AND no identifiable dev script`, which is still decided entirely from unmodified
state, so the write barrier is unaffected.

**Nothing is lost by narrowing it**, and it is worth saying which loss was considered: on a
plain-Node host we no longer learn the port the developer's own server uses, so we cannot warn
that it collides with the DevTool's 4200. That is not a regression — no version of this design
checks port availability for any host — and inventing the check here would be a new feature
smuggled in as a refusal.

**Two lockfiles is a question, not a tiebreak.** A repository carrying a stale
`package-lock.json` beside `pnpm-lock.yaml` has no fact that resolves it, and the skill installs
immediately through whatever the report names — so a wrong pick mutates a manifest state the
project abandoned, or leaves a third lockfile behind. The `packageManager` field is promoted
above lockfiles rather than kept beneath them because it is the only *declaration* among these
signals: a lockfile is residue, and corepack enforces the field. That promotion also makes the
refusal rare, which matters — a repo that migrated managers and left the old lockfile is common,
and it now resolves cleanly on the field instead of refusing. What is left refusing is the
genuinely undecidable case: two lockfiles, nothing declared. There the report names both files
and asks for one of two cheap human answers — delete the stale lockfile, or add a
`packageManager` field.

**`npm_config_user_agent` is gone as a third source, and the reason is that the invocation
changed under it.** An earlier draft fell back to that variable when neither a field nor a
lockfile existed, arguing it would say `npm` because the documented invocation was `npx`. Under
decision 2 detection is not a command anybody types: it ships as scripts the assistant runs
directly from the installed plugin, so **npm is not in the process tree and the variable is
simply absent.** The premise the fallback rested on was deleted by the re-shape, and the
statement outlived it.

**It is worth naming what the fallback would cost if it were kept, because it is worse than an
unhelpful report.** The variable describes *how the script was launched*, never what the project
uses — so on the rare run where it is set it is answering a different question, and on the normal
run it is missing. Either way the tempting default is `npm`, and `npm add` in a lockfile-free
pnpm or Yarn project **creates a `package-lock.json` the project never wanted**: a file outside
the write allowlist, in someone else's repository, from a signal that was never evidence.

**So a project with no declaration and no lockfile refuses, with the same remediation the
ambiguous case already uses.** The rule collapses to one sentence — *the manager must be declared
or evidenced, or the run stops* — and the remediation is the better one to hand a developer
anyway: adding a `packageManager` field settles it for corepack, for CI, and for every future run,
where a one-off answer typed into a chat settles it for exactly this run. This is not a new class
of refusal; it is the `ambiguous` row's sibling, and §10 asserts them as one pair.

**Why `.mts` on this path, measured rather than assumed.** The config is loaded by a plain native
`import()`, so its module format follows the project's `package.json`. Probed on Node 22.22
(§12): with an explicit `"type": "commonjs"` a `.ts` config carrying `export default` fails with
`SyntaxError: Unexpected token 'export'`; with no `type` field at all it *works* but emits a
`MODULE_TYPELESS_PACKAGE_JSON` warning on every command; `.mts` loads clean in all three. Note
the consequence: the CLI's directory discovery looks only for `flow.ts` / `flow.js` / `index.ts`
/ `index.js`, so a `.mts` flow is **not** discoverable — which is fine and deliberate, because
the config the skill writes registers its flows explicitly, and an explicit registry is what the
CLI uses whenever a config exists. §12 carries the follow-up.

**What the skill is instructed to write.** `fsdev.config.mts`, `flows/hello/flow.mts`, and for a
Next.js App Router host the mount. The mount is **two files** — the required catch-all plus a
sibling bare route forwarding an empty path array — because `list_flows` is registered as
`GET /` on the mount base, which is what the client's `listFlows()` requests, and a required
catch-all cannot match zero segments. Both in-repo mounts and the published guides do exactly
this, with a comment saying why; a single optional catch-all would make this a third shape (§12).

**The write allowlist is per host, because the count differs by host. Every path in it is
relative to the write root**, which is what keeps a workspace app's files out of the repository
root above it. Enumerated rather than
counted — a single number is wrong for at least one host and stays wrong as hosts are added:

| host | files the skill may write or append to |
|---|---|
| `next` | `fsdev.config.mts` · `flows/hello/flow.mts` · `<appRoot>/api/flows/route.<ext>` · `<appRoot>/api/flows/[...path]/route.<ext>` · `.gitignore` · `.env.local` · `AGENTS.md` — **seven**, because the mount is two files. Both `<appRoot>` and `<ext>` come from **detection**: the literal `app/` and the literal `.ts` are each wrong for a real project, so the allowlist is parameterized on the same two facts the writing rule uses. A check that hardcoded either would pass on a run that wrote to the wrong place |
| `node` | `fsdev.config.mts` · `flows/hello/flow.mts` · `.gitignore` · `.env.local` · `AGENTS.md` — **five**, no mount |

`package.json` and the lockfile are deliberately **not** on either list: the skill never writes
them, the project's package manager does. They still have to appear in the run's report, so the
report-versus-diff check in §10 counts them as named-and-expected rather than as unlisted
touches. A check that enforced one flat number would have to reject the bare route the client's
`listFlows()` needs, or be loosened until it asserted nothing.

**The unit a mount is checked against is the route *slot*, not the filename we chose.** A slot is
a directory plus the leaf name — `<appRoot>/api/flows` with leaf `route` — and Next will treat
**any** enabled extension there as that route. So a project that already owns
`<appRoot>/api/flows/route.js` occupies the slot our `route.ts` would take, and a preflight that
only asks about the filename it selected sees an absent path and writes into an endpoint the
developer already has. Verified against the matcher rather than reasoned about: with the default
`['tsx','ts','jsx','js']`, `isAppRouterRoute` matches `route.ts` **and** `route.js` **and**
`route.tsx` at the same slot — the pattern is built from the extension list and does not
disambiguate (§12). A local Next 16.1.6 fixture on this PR showed the pair compiling with
`route.ts` selected and `route.js` silently excluded, so the developer's handler stops answering
with nothing reported.

**Which file Next picks does not change the conclusion, which is why the rule does not depend on
it.** If it prefers ours, we have silently replaced a working endpoint. If it prefers theirs, our
mount silently never answers. Both are undetected collisions. **So the preflight tests every slot
the run would occupy across a scan set, not a single filename** — the same generalization already
applied to the app root and the extension, carried one step further to the thing those two facts
are used to build.

**The scan set is wider than the enabled set, and scanning only the enabled set is a check that
cannot fail.** Here is the scenario, and what a scan of enabled extensions alone returns in it:
run one writes `route.ts` under Next's default `['tsx','ts','jsx','js']`; the developer later
narrows `pageExtensions` to `['tsx']`; on the rerun the scan asks about `tsx` only, **finds
nothing, and returns "slot empty → write"** — a pass, on a slot that holds a file we wrote. It
then writes `route.tsx` beside the stale `route.ts`, and the refusal below that exists for exactly
that state can never fire, because nothing ever looks where the stale file is. *This defect was
introduced by the fix in this same section, one revision earlier, which is the shape it warns
about: a refusal added without widening the thing that feeds it.*

**So the scan set is every currently enabled extension, union every extension this skill can ever
emit — `ts` and `tsx`, and only those, because the extension rule prefers `ts`, falls back to
`tsx`, and otherwise refuses.** The two halves answer two different questions and neither covers
the other: the enabled half finds files that are live routes today, ours or theirs; the emitted
half finds files **we** left behind that are dormant today and become live if the setting widens.
A file at a third extension that is neither enabled nor ours — an unmarked `route.js` under
`['tsx']` — is deliberately out of scope: it is not a route, we did not write it, and it is not
ours to have an opinion about.

**What an occupant means is decided by the marker, not by its presence — and stating it any other
way breaks every rerun.** A first run leaves `route.<ext>` in both slots, so on a second run *the
slots are always occupied, by us*. A rule reading "any occupant refuses" therefore refuses every
rerun of an untouched project, which contradicts the ownership rule below (*Rerun semantics for
the files the run authors whole*) and would make the idempotent case — the common one — the only
case that cannot work. **The slot scan
finds occupants; the marker classifies each one**, and the two are separate steps:

| the slot's occupants **across the scan set** | what the run does |
|---|---|
| none | write our file at the selected extension |
| exactly one, carrying our marker, at the extension now selected | **ours.** Rewrite or leave, per the rerun rule below |
| one or more carrying no marker, or a marker that does not match | **refuse the whole run**, naming each occupant. This is the `route.js`-beside-`route.ts` case, and it refuses whether or not one of the occupants is also ours |
| ours, but at an extension the project no longer enables | **refuse**, naming it. `pageExtensions` narrowing between runs strands a file we wrote: it is not a route today and becomes a duplicate handler in the same slot the moment the setting widens again. The run never deletes, so the developer removes it — a one-line remediation on a file we authored, not the deadlock the config case had. **This row is only reachable because the scan set includes the extensions we emit** — under an enabled-only scan it is dead text |

The distinction is the one the classification table already draws for every other authored path.
It is restated here because the slot is the one place where the *unit being checked* (a directory
plus a leaf name, across a scan set wider than the enabled extensions) differs from the *unit
being owned* (a file with a marker in it), and collapsing them is what produced the contradiction.

### The write barrier

**One invariant governs every refusal, and it is stated here once because three separate defects
have been the same violation of it.** Each was found individually — an unsupported host, a
colliding path, an ignore rule read back after we had already edited the file — and each was
fixed individually, which is how the next instance gets written.

> **Every refusal is decided from state the run has not modified.**
> Nothing is written until every refusal condition has been evaluated and none fired.

Two corollaries do the actual work. **No refusal may depend on reading back the effect of our own
write** — that is the shape that keeps recurring, because "write it then verify" reads as
prudence. **A condition that could only be evaluated after a write is evaluated against
*proposed* content instead**, in a scratch location, never in the developer's tree.

Every refusal condition, and what it reads:

| refusal | decided from | modifies anything first? |
|---|---|---|
| host is not a supported Next shape, or below `>=15` | manifest + directory conventions | no |
| host unknown | manifest + directory conventions | no |
| Node below 22.18 | the running runtime | no |
| `pageExtensions` unreadable without executing their config | `next.config.*` bytes | no |
| **`basePath` unreadable without executing their config** | `next.config.*` bytes, same pass | no |
| **package manager outside the supported set** | resolution 3 | no |
| package manager ambiguous (lockfiles disagreeing across the chain, nothing declared) | resolution 3 — the whole write-root→workspace-root chain | no |
| **package manager undeclared and unevidenced** (no field, no lockfile anywhere in the chain) | resolution 3 | no |
| no identifiable dev script **on a `next` host** | `package.json` `scripts` | no |
| **a route slot holds an occupant that is not ours** — no marker, a stale marker, or ours at an extension no longer enabled | the filesystem, across the scan set (enabled extensions ∪ `ts`, `tsx`), plus our markers | no |
| a required path exists and is not ours, with no integration | the filesystem + our markers | no |
| **the file that will be filled is tracked by git** | `git ls-files --error-unmatch` against **resolution 10's** path — not the write root's by default | no |
| **`.env.local` would still be publishable after our ignore entry** — fires only when the run would actually create or add to a `.env.local` | existing `.gitignore` bytes, evaluated as *proposed* content in a scratch location | no |
| **a prose file's delimiters are unbalanced, out of order, or duplicated** | the existing bytes of `.gitignore` / `AGENTS.md` | no |
| **detection was pointed at a workspace root rather than a host** | `pnpm-workspace.yaml` / `workspaces` / manifests beneath | no |
| provider not chosen | the developer's answer — the **provider only**, taken before any write; the key is never part of it | no |

**Four of these rows are newer than the barrier itself, which is the point of writing it as an
enumeration rather than as a property of each case.** §10 asserts the invariant directly rather
than only its instances: for each row, a fixture that trips it must leave the working tree
**byte-identical**. Because that check is a loop over this table, a refusal added here is covered
the moment it is listed — but only if the thing that *feeds* it is widened too. Two rows here have
already failed that way once each: the slot row needed the scan set widened past the enabled
extensions before its stale-file case could fire, and the package-manager row needed the ancestor
search before `undeclared` stopped firing on every workspace app. **When adding a row, check the
input as well as the condition.**

**In-place edits.** One mechanism for the three **prose** files — `.gitignore`, `AGENTS.md`, and
the agent-instructions placeholder: a delimited section, created when the file is absent,
appended when it is present, replaced between our own delimiters on a second run — **and the
replace case is defined only for exactly one balanced pair, which the next paragraph makes a
refusal rather than an assumption.** Nothing outside the delimiters is read or rewritten. `package.json` is not on that list — the project's own
package manager owns the manifest and the lockfile, and the skill installs through it rather than
editing either. That is the epic's rule, not a local call, and delegation is why it holds: the
manager already preserves everything it does not own.

**"Replace between our delimiters" is only defined when there is exactly one balanced pair, and
the undefined cases destroy the file.** The mechanism names three states — absent, present,
present-with-our-section — and a real file can be in a fourth. A start delimiter with **no
matching end** is the dangerous one: the natural implementation finds the start, searches for the
end, does not find it, and replaces **to EOF** — silently deleting everything the developer wrote
below our marker. In a `.gitignore` that is their entire ignore list; in `AGENTS.md` it is their
instructions. **That is a write outside our delimiters, in a file we do not own, and it is the
exact guarantee this whole section exists to make.** Two lockfiles taught the same lesson about
reading; this is it about writing. The other malformed states are less destructive but equally
undefined: two or more of our sections (which one is authoritative — and the loser is then
orphaned content nothing will ever update), an end delimiter before its start, or nested pairs.

**So the preflight requires exactly one balanced, correctly ordered pair per prose file, and
anything else refuses.** Enumerated, because "handle malformed markers carefully" is not a
specification and the careful implementation is the one that deletes to EOF:

| delimiters found in the file | what the run does |
|---|---|
| none | **append** our section. This is the ordinary first run |
| exactly one start and one end, start before end | **replace between them.** The ordinary rerun |
| a start with no end, or an end with no start | **refuse the whole run**, naming the file and the line the stray delimiter sits on. Never replace to EOF, and never append a second section beside a broken one |
| more than one pair, or a pair nested inside another | **refuse the whole run**, naming the file and every delimiter line found |

The refusal is decided from the file's existing bytes with nothing modified, so it belongs to the
write barrier like every other. The remediation is one a developer can act on in seconds — delete
the stray marker, or collapse the duplicate sections — and it is far cheaper than the alternative,
which is discovering afterwards that a file they maintained by hand is now shorter.

**`.env.local` is deliberately not on that list, and a future reader will want to put it there.**
It looks like a fourth prose file and it is not: its content is a live secret the developer
supplied, so "replace between our delimiters" destroys the thing the file exists to hold. On a
rerun the canonical section carries `OPENAI_API_KEY=` with an empty value — that is what the
section says — so replacing the section **overwrites the developer's working key with nothing.**
The append variant is worse because it is quieter: with a pre-existing key above our section and
our empty assignment below it, the file still visibly contains the key while the run silently
fails. Measured, not reasoned — `parseEnvFile` in `packages/cli/src/load-env.ts` iterates lines
and calls `vars.set(key, value)` per line, so **within a single file the last occurrence wins**;
replaying that parser over exactly this layout resolves the key to the empty string (§12). The
file-level "first source wins" guard is about precedence *between* sources and does not reach
duplicates inside one file.

**One file is not the unit either, and the second direction is the opposite of the first.** The
loader walks `.env.local` from the working directory **upward** to the filesystem root, and
`applyEnvFile` assigns only `if (process.env[key] === undefined)` — so **across files the
*nearest* occurrence wins**, while within one file the *last* does. Read from
`loadEnvFiles`/`applyEnvFile` in the same `packages/cli/src/load-env.ts`, whose own header states
the precedence: shell environment, then explicit `--dotenv` paths, then cwd and up.

**Both directions are the same defect and stating only one is how it comes back.** The within-file
half was found first and fixed; the across-file half fails in a shape a monorepo makes ordinary. A
plain-Node service at `services/api` inside a workspace whose **root** `.env.local` already holds
`OPENAI_API_KEY=sk-…` looks, to a rule that reads one file, like a project with no credential. The
run appends `OPENAI_API_KEY=` to `services/api/.env.local`; that file is nearer, it is loaded
first, and an **empty string is a set value** as far as `process.env[key] === undefined` is
concerned — so the parent's working key is never applied. **The developer's credential still sits
in the repository, unchanged and unreachable**, and the failure surfaces as `No provider
available` from a project whose `.env.local` visibly contains the right variable.

**So the rule keys on one resolved value, not on a search of several files — and computing that
value is resolution 9 rather than a condition each row re-asks.** An earlier form of this table
asked three questions of the chain independently ("absent everywhere", "non-empty anywhere",
"present but empty") and a real project matches two of them at once: an empty `KEY=` in the write
root with `KEY=secret` in a parent is simultaneously *empty here* and *non-empty somewhere*. The
"non-empty anywhere" row then reports the credential configured while the loader resolves the
empty one and the model call fails. **Two rows matching is not a wording problem; it is the
symptom of asking the filesystem a question only the loader can answer.**

**Resolution 9 — the effective credential.** Walk the chain from the write root upward. The
**first** `.env.local` that assigns the key at all decides it; within that file the **last**
assignment wins. That is exactly `loadEnvFiles` applying `parseEnvFile` per file and setting each
key only when `process.env[key] === undefined`, and it yields **one** value and **one** path. Both
tie-breaks are in play and they run in opposite directions, which is why neither can be dropped.

| the **effective** value, and where it lives | what the run does |
|---|---|
| no assignment anywhere in the chain | append our delimited section containing `KEY=` with an empty value to the **write root's own** `.env.local`, then ask the developer to fill it |
| non-empty | **write nothing at all.** Do not add our section, do not duplicate the key, do not touch the existing line. Report that the credential is already configured **and name the file that holds it**, since it may not be the one the developer is looking at |
| empty | leave that line exactly where it is and ask the developer to fill **it**, naming its path. **Nothing further up matters** — a populated parent is already masked by this line, and saying "already configured" would be false |

**The tracked-file refusal follows resolution 10, and asking it about the wrong file walks a
credential into version control.** The refusal exists to stop a key landing in a committed file.
It was written as a property of the write root's `.env.local` — but the rule above can point the
developer at an **ancestor** file, and an ancestor `.env.local` at a repository root is exactly the
kind of file a project is more likely to have committed. Composed, the two rules said: *the
effective assignment is the empty `OPENAI_API_KEY=` at the repository root, so fill that line* —
while the tracking question was asked of `apps/web/.env.local`, which does not exist and is
therefore untracked, so **nothing refused.** The developer pastes a live key into a tracked file
because our tooling pointed at the line.

**So tracking and ignoring are asked about whichever file will actually receive the value**, and a
tracked one refuses with the `git rm --cached` remediation naming **that** path. This is the same
class as the key-solicitation clause and it deserves the same weight: the end state is a secret in
version control, in a stranger's repository, arrived at by following our instructions. §10 asserts
it with a fixture rather than trusting the prose, because the two halves are stated in different
places and that is precisely how they came apart.

**The empty case is the one that changed, and it is worth stating why it now looks unhelpful on
purpose.** When the effective value is an empty assignment in the write root and a real key sits
in a parent, the honest report is *"this file has an empty `OPENAI_API_KEY=` that is hiding the
one at `<parent>` — fill it or delete the line"*, not *"you're all set"*. The old table said the
latter. **The run still writes nothing either way**, so this is a reporting defect rather than a
destructive one — but it sends a developer to debug `No provider available` in a project the tool
just told them was configured.

**The rule never writes a second assignment for a key that already appears anywhere the loader
would read it**, which is what makes both masking cases unreachable rather than merely unlikely —
the within-file one, where a later empty line wins, and the across-file one, where a nearer empty
file wins. A key the developer later moves outside our delimiters keeps working, and so does one
that lives a directory up.

**Scanning the loader's own chain is the point, not a wider net for its own sake.** The set of
files that can supply this variable is exactly the set `loadEnvFiles` walks; matching it is the
only way to be sure, and reading anything narrower is the same mistake as reading a config the CLI
is not loading. The scan is a read, it writes nothing, and a missing file at each level costs one
`existsSync`.

**Rerun semantics for the files the run authors whole.** The delimited mechanism above covers the
three text files it appends to. The config, the flow and the mount pair are different: the run
creates them entire, so on a second run they already exist and the question is whether they are
still ours. **Each carries an authorship marker in its header** —
`// fsd:generated sha256:<digest of the body below>` — written on creation, and the rule is three
cases per path.

**This marker is a stored value, and the epic's "no stored values" rule does not reach it** — the
distinction is worth stating because the two look alike. That rule governs *shared artifacts*,
where a canonical text exists in this repository and a shipper's copy can simply be compared
against it. Here there is no canonical: the question is whether a file **in someone else's
repository** is still as this tool left it, months later, with no reference copy anywhere. A
stored fingerprint is the only thing that answers it, and its failure mode is the benign one — a
mismatch means "assume it's theirs and leave it alone", so a stale or wrong marker costs a
skipped rewrite rather than an overwrite.

| state on rerun | what the run does |
|---|---|
| absent | write it, with the marker |
| present, marker matches the body | ours and unedited. Safe to leave, or to rewrite if the content changed — either way, report it as unchanged or updated |
| present, marker missing or not matching | **the developer has edited it, or wrote it themselves. Never overwrite.** Report the path, say it was left alone, and print what would have changed |

This is the same rule the run already applies to everyone else's files — never rewrite content it
did not author — extended to content it *did* author but no longer owns. The marker is what makes
"did we write this?" a fact rather than a guess: comparing against freshly generated content
cannot answer it, because the content legitimately varies with the provider and model the
developer chose.

**Every required path is checked before the first write, and a collision refuses the whole run.**
The three cases above decide *per file*, and applying them file-by-file mid-run is what produces
the failure they were meant to prevent. A first run that meets an unrelated `flows/hello/flow.mts`,
or a `route.ts` already sitting where the mount goes, leaves that file alone under the rule — and
then carries on appending credentials, appending instructions, and installing dependencies. The
developer ends up with a changed repository and **no demo flow or no mount**, and next steps that
tell them to run something that cannot work. That is the same shape as the Next-version gap: a
condition known before any write, discovered after several.

So the rule is a **preflight**: resolve the host's whole allowlist, classify every path in it,
and only then write anything. **Partial application is never a legitimate outcome**, which is
what turns a per-file decision into a whole-run one.

| classification | what it means | what the run does |
|---|---|---|
| absent | nothing there — for a mount, **no occupant in the slot anywhere in the scan set** | write it, with a marker |
| ours | marker present and matching — for a mount, the slot's **only** occupant is ours, at the extension now selected | rewrite or leave, and report which |
| **theirs, with a defined integration** | today this is exactly one path: the `fsdev.config.*` the CLI would actually load — the **precedence winner** — carrying no marker of ours | **proceed.** Do not write a config, keep every other write, and tell them the one line that registers the new flow **in that file** |
| theirs, no integration | a flow file whose name is taken; a mount slot holding any occupant without a matching marker, or one of ours at an extension no longer enabled | **refuse the whole run**, nothing touched, naming every such path |

**An existing FSD config is an integration point, not a collision, and treating it as one
deadlocks the case it was written for.** A project that already uses FSD is the most likely
brownfield caller there is. Classifying its config as a colliding required path stops the run
before the flow is written — while the remediation for that very case tells the developer to
register the flow that was never created, and a rerun hits the identical stop. The run would be
unable to complete on any existing FSD project, forever. So a user-owned config is the one path
with a defined integration behaviour: skip writing it, write everything else, and hand back the
registration line. **The distinguishing question is not "is it ours" but "is there a defined way
to proceed"** — a taken flow name, or a mount slot holding a file that is not ours, has no such
answer, and those still refuse.

**The marker also fixes a rule that misled rather than broke.** §9 says a project with an
existing `fsdev.config.*` is told the demo flow is unregistered, reasoning that a config we did
not write uses its own explicit registry. On a second run that config *is* ours and *does*
register the flow, so the same rule would print a remediation for a problem that does not exist.
A config carrying our marker is ours and the flow is registered; one without belongs to the
project, and the warning — plus the integration path above — is right.

**But "our marker" and "the config that runs" are two different facts, and a project can hold
both files at once.** The CLI loads one filename out of four, first-present wins, `.ts` ahead of
the `.mts` this path writes (decision 3). So the reachable sequence is: run one writes
`fsdev.config.mts` and registers the demo flow in it; the developer later adds an
`fsdev.config.ts` — by hand, or by running FIX-548's template in the same directory; the CLI now
loads the `.ts` and the demo flow is not registered anywhere it reads. **A rerun that classifies
"the config" by looking at our `.mts` finds its own marker, concludes the flow is registered, and
reports a success the CLI cannot deliver** — the check reading a file the loader is not loading.
It is a check that cannot fail, in the class this design keeps producing, and it is silent in
exactly the way §7's other silent failures are.

**So classification is keyed on the precedence winner, and every candidate is reported.**
Detection lists all four filenames it found in the loader's order; the run names which one the
CLI loads and states plainly that the others are ignored — which is also what the CLI itself
prints on stderr, so the developer meets the same fact twice rather than never. Three consequences,
and none of them is a new refusal:

- **winner absent** (no config at all) → write `fsdev.config.mts`. This is the only state in which
  the skill writes a config, so nothing it authors is born shadowed.
- **winner is ours** (marker matches) → the flow *is* registered; rerun normally. Any shadowed
  file is named as ignored.
- **winner is theirs** (no marker), whether or not one of ours sits behind it → the integration
  case above, and the registration line names **the winner**. Where a marker-carrying file of ours
  is among the shadowed, say so and say it is now dead weight the developer can delete.

**Refusing on multiple configs was the alternative and it is worse:** the state is legal, the CLI
merely warns about it, and a project that has just run FIX-548's template beside an earlier
brownfield run would be locked out of ever rerunning. Reporting the winner costs one detection
field and removes the whole class.

**The provider is chosen before anything is written, and one answer settles four things.
The *provider* is what is asked for — never the key.** The run asks which provider before the
first write, not because a prompt is tidy, but because the model the generated flow names, the
dependency that gets installed, the environment variable name and the `.env.local` line all
follow from that one answer. A run that reaches the install step without having asked has already
written files it cannot finish. **The key is not part of this exchange and never becomes part of
it** — the run writes the empty variable line, the developer types the value into that line in
their own editor, and the run afterwards asserts only that the variable is present and non-empty.
That rule is stated in full below and it binds here too; this paragraph is about the provider
question alone. **The mapping is a declared contract, not the implementer's to invent**, because
four artifacts have to agree:

| provider | package installed | statically imported factory | env var | the model string the generated flow names |
|---|---|---|---|---|
| `openai` | `@ai-sdk/openai` | `createOpenAI` | `OPENAI_API_KEY` | **`openai/gpt-5.4-mini`** |
| `anthropic` | `@ai-sdk/anthropic` | `createAnthropic` | `ANTHROPIC_API_KEY` | **`anthropic/claude-haiku-4-5`** |
| `google` | `@ai-sdk/google` | `createGoogle` | `GOOGLE_GENERATIVE_AI_API_KEY` | **`google/gemini-3.1-flash-lite`** |

**The last column is exact because nothing else in the system will make it exact.** The framework
ships **no default model and no built-in intent lists** — `apps/docs/docs/fundamentals/models.md`
says so outright ("Apps configure their own model lists per intent — there are no built-in
defaults"), and `createModelResolver` has no model table in it at all. Nothing validates a model
*id* either: `parseModelString` checks the `provider/model` shape and stops there, and the repo's
`scripts/validate-model-strings.mjs` guards only the removed `preset/*` syntax. So an implementer
handed "an OpenAI chat model" invents a plausible id, construction accepts it, the install
succeeds, every check in §10 that does not call a provider stays green — and the developer's
first request fails with a model-not-found from the provider. **That is the first thing they do
after following our instructions**, which is why the strings are pinned here rather than left as
a description. The three are not picked here: they are the exact `utility` list in
`apps/docs/docs/getting-started/setting-up-models.md` — one small/fast model per supported
provider, in that order — and `openai/gpt-5.4-mini` is the house default `CLAUDE.md` mandates for
examples. So a project this run wires up names the same model the docs page it is sent to teaches,
and updating one place updates the pair.

**The generated config declares no intents, and that is a decision rather than an omission.**
`defaultModel` is *required* the moment `intents` is non-empty — `createModelResolver` throws
`defaultModel is required when intents are configured` at construction, which for a generated
project means `createFlowState` fails and **every** command the next-steps block prints dies
before it runs. A demo flow needs one model, so the config passes one statically imported
provider instance and the flow's generator names the concrete `provider/model` string above:

```ts
const openai = createOpenAI({ apiKey: process.env.OPENAI_API_KEY });
const modelResolver = createModelResolver({ providers: { openai } });
export default createFlowState({ modelResolver, flows: [...], stores: {...} });
```

That is the shape `getting-started/setting-up-models` already documents for a pre-built provider,
and it is why the contract's column is a model string rather than an intent: the earlier phrasing
("model intent `default`") named a resolver option that only exists once intents do, borrowed from
the `models` shorthand the very next sentence forbids. A refusal to answer is a refusal to
proceed: there is no default provider, because guessing one installs the wrong package and writes
the wrong variable name.

**The provider is asked; the key never enters the conversation.** Choosing a provider is not a
secret. An API key is, and on this path the "prompt" is a chat with a coding assistant —
a transcript that is retained, often uploaded, and not the developer's terminal. **A key pasted
there has been disclosed to a third party before it ever reaches `.env.local`,** and no later
handling of the file undoes that. So the run **never asks for, accepts, echoes, or repeats a key
value.** It prepares `.env.local` with the variable name and an empty value, tells the developer
to paste the key into that line themselves, and afterwards asserts only that the variable is
**present and non-empty** — a fact about the file, established without reading the secret back
into the conversation.

**This is the one place the two entry paths legitimately differ on credentials, and the reason is
the surface, not the design.** FIX-548's greenfield command prompts in a terminal, where the
value goes from the developer's keyboard into a local process; the epic's proof describes exactly
that and it is safe there. The same words describing an agent conversation would mean something
else entirely. **A key already present in an untracked `.env.local` is the easy case:** confirm
the variable exists and move on, without printing it.

**The credential guard asks about the file we *would* write, and writes nothing to ask.** The
hazard is real and was measured: a `.gitignore` reading `.env*`, then our delimited section, then
`!.env.local`, leaves the file untracked and **re-included** — the key lands and the next
`git add -A` stages it, which a scratch repository confirmed by actually staging it. Our own
entry does not settle the question, because git's last matching rule wins and a negation can come
after ours.

**But evaluating that by editing `.gitignore` and then asking git violates the write barrier**, and
an earlier draft did exactly that: it wrote, checked, and refused, leaving a modified `.gitignore`
behind on a run that was supposed to touch nothing. *This is the write-then-check shape the
barrier exists to catch, and it reached the spec because "verify against reality" sounds stronger
than evaluating a proposal.* Reality here is a file we have not written yet, so there is nothing
to verify against.

**So the proposed content is evaluated with git's own matcher, in a scratch location.** The run
composes the bytes `.gitignore` *would* have — existing content plus our section at the position
we would insert it — materializes that together with an empty `.env.local` in a temporary
directory, and asks `git check-ignore -q` there. Nothing in the developer's tree is touched, and
we do not reimplement git's precedence rules. The untouched repository is also asked directly,
which is what covers the inputs a scratch copy cannot reproduce — a parent directory's
`.gitignore`, `.git/info/exclude`, a global excludes file. If the proposal does not come out
ignored, the run refuses with nothing written and names the rule that re-includes the file.

**This guard is scoped to runs that would put a credential line on disk, which the chain rule
above makes a real distinction rather than a pedantic one.** When the provider variable already
resolves non-empty from an ancestor `.env.local`, the run writes no `.env.local` at all — so there
is no secret of ours to publish and refusing would reject a workspace app that is already
correctly configured. In that case the guard **reports** rather than refuses, and the ignore entry
is still written, because a `.gitignore` line costs nothing and the developer may add a local key
later. The refusal fires when the run would create the file or add our variable line to it, which
is exactly the case where a value is about to exist that git could take.

**The check is `git check-ignore -q`, and the `-q` is load-bearing:** with `-v` the command exits
0 whenever *any* pattern matches, including the negation that re-included the file, so a `-v`
exit-code test reports "ignored" for a file git will happily commit. Measured both ways (§12).

**Supported package managers are a closed set, checked before any write.** The substitutions
define command forms for **npm, pnpm and Yarn** and nothing else, so a manifest declaring
`"packageManager": "bun@1.2.0"` is authoritative about a manager this run cannot render commands
for. Treating the field as authoritative and proceeding leaves the skill inventing an install
command and a next-steps block, or discovering the gap after the files are on disk — the write
barrier again, reached through the one rule that was supposed to make the manager unambiguous.
**A manager outside the set refuses**, naming it and saying which are supported. Adding one later
is additive: a row of command forms plus its detection, and a fixture.

**Install.** `<pm> add` for the runtime dependencies and `<pm> add -D` for
`@flow-state-dev/devtool`, **invoked in the write root** — that is whose `package.json` the
generated files import from, and in a workspace it is the app rather than the repository root
where the manager was declared. The manager rewrites the workspace root's lockfile as a
consequence, which is correct and which **the report names by path**, since a lockfile changing two
directories above the app is not news a developer should have to discover from `git status`. The
set is the dependency rule from the wiring contract, not a list: every package the generated files
import directly, which is `zod`, the chosen provider's `@ai-sdk/*`, and the `@flow-state-dev/*`
packages — plus the DevTool, an *optional peer* of the CLI satisfied inside our monorepo and by
nothing outside it. Without them the commands the next-steps block prints fail immediately.

**The next-steps block is a source block, and that dissolves the renderer problem rather than
solving it.** Earlier drafts specified a module with a render function, which left the install
skill — Markdown, with no callable interface — unable to reach it. There is nothing to call:
**one canonical block text, carrying declared placeholders, is embedded verbatim in each
shipper's own source and substituted at emit time.** The skill embeds the same text and fills the
placeholders from what detection already told it. `create-flow-state` embeds the same text and
fills them from what it just wrote.

**Declared variation has two forms, and this issue owns both syntaxes.** Everything that varies
is one of these or it is not inside the delimiters.

**Values** — named placeholders replaced with a detected value:

| placeholder | filled with |
|---|---|
| `{{run}}` | the package manager's run form — `npm run`, `pnpm`, `yarn` |
| `{{exec}}` | its exec form — `npx`, `pnpm exec`, **`yarn exec`** |
| `{{execSep}}` | the option separator npm needs and the others do not |
| `{{devScript}}` | the host's own dev script name, from detection or from what the template wrote |
| `{{devUrl}}` | where that script actually serves, not an assumed `localhost:3000` |
| `{{mountPath}}` | **resolution 6** — the path the mount answers on, `basePath` included. Never the literal `/api/flows`, which is right only when no `basePath` is set |

**Conditional sections** — a named region rendered only under one of the two host topologies,
`mounted-route` or `second-process`. **The key set is closed and belongs to the epic**, because
exactly two topologies exist; a block wanting a third has hit a cross-cutting question rather
than a local call. This form exists because the first cannot express what the topologies differ
in: a mounted-route host runs its own dev server with FSD answering inside it, while a
second-process host starts `fsdev serve` alongside the server already there, and no
package-manager substitution turns one process list into the other. Moving the process list
outside the delimiters is not the escape — that hands the block's whole payload back to unowned
per-host prose, which is what a single authored source exists to prevent.

**One block, not two — corrected this pass.** An earlier draft split the shapes into two
canonical texts on the reasoning that they differ in prose rather than in a value. The epic then
provided conditional sections for exactly this, so the two topologies are branches of one block.
That matters beyond tidiness: **every shipper embeds every branch and renders only its own.**
`create-flow-state` ships greenfield Next.js and never renders `second-process`, but that branch
still sits in its source identical to canonical, because that is what the check reads. A shipper
that trims a branch it cannot reach breaks the check — and trimming it looks like tidying, which
is why it is stated rather than assumed.

**The check is normalized text equality, and this issue owns the implementation.** Stored values
are gone: no digest, no hash, no marker line to maintain — the mechanism was wrong five times and
every one of those fixes was defending a stored value. **The author owns the comparison** — the
normalization, the placeholder and conditional syntax, and the equality itself are one
implementation, here, exported. Two shippers cannot drift apart on a normalization neither of
them implements.

**Owning the comparison is not owning its invocation, and that distinction is what makes the
invariant enforceable.** This issue lands *before* FIX-548, so a check run here over a shipper's
copy cannot be written correctly: demanding the copy exist fails while FIX-548 has not landed,
and tolerating its absence passes forever if FIX-548 never ships it. Neither distinguishes *not
yet* from *never*. **So the comparison is exported and each shipper invokes it against its own
embedded copy inside its own test suite** — the assertion lands exactly when the copy does, and a
shipper that never embeds the block has no passing suite to hide behind. The skill's own copy is
checked the same way, by this issue, since it is a shipper too. This adds no dependency between
packages: it is a test-time import inside this monorepo, where every shipper already lives.

**The assertion is equality over the whole block, every branch included — never presence or a
substring.** A dropped `second-process` branch changes the text and fails; a check that only

*Rejected: a CLI subcommand the skill shells out to.* It is the obvious way to give Markdown an
interface, and decision 1 forbids it — this issue ships no command. It is also wrong on its own
terms: it would make printing the next steps depend on our CLI already resolving in a project
that may have just failed to install it, which is exactly the moment the block matters most.
*Also rejected: the skill restating the steps freehand*, which is the drift the equality check
exists to catch.

**Invoking our CLI before the project has been installed into.** Use the scoped
`npx @flow-state-dev/cli …` form — there is no `fsdev` on the path yet. After the install there
is: a scoped package's `bin` key does create `node_modules/.bin/fsdev` (§12, verified by
execution), which is why the next-steps block prints `pnpm exec fsdev …` instead. Decision 1
removed the subcommand the previous draft named here; it did not remove the rule.

**Three shared artifacts touch this issue, and each declares author, kind, carrier and check**
against the epic's one rule rather than inventing a mechanism per artifact — which is what
produced four different seam answers before the rule existed:

| artifact | author | kind | this issue's role | check owner |
|---|---|---|---|---|
| wiring contract | **this issue** | specification | author; the skill is also a shipper | **this issue** — behavioural conformance, both paths, under an isolated install |
| next-steps block | **this issue** | source block (values + conditional sections above) | author; the skill embeds it and is checked like any shipper | **this issue** — exports the comparison; each shipper invokes it |
| agent-instructions block | FIX-1160 | source block | **shipper only, and not even the embedder** — the skill carries a named placeholder that FIX-1160 substitutes with the canonical block when it packages the plugin | FIX-1160 |

**The third row runs against the epic's dependency direction, which is why it is handled
differently.** This issue lands *before* FIX-1160, because FIX-1160 packages this skill — so the
skill cannot embed a canonical block that has not landed. A placeholder filled by the packager
runs along the existing edge instead of against it, and it costs this issue nothing but a named
slot. **Nothing here re-authors that block**, and the skill must not restate its content in
prose: that is the drift the equality check exists to catch, and it would also make this issue a
second author of something it does not own.

**A specification is checked behaviourally, and that is deliberate rather than an omission.** The
wiring contract's shippers produce genuinely different output — the template writes a chat page
and `flows/chat.ts`, a brownfield Next run writes `flows/hello.ts`, a plain-Node run writes no
mount at all — so there is no common text to compare. Conformance is the only honest check: both
paths' proofs have to produce the same observable shape, under an isolated install, with the
dependency rule holding. A text comparison here would either force the outputs to be identical,
which they are not, or compare something so abstract it could not fail.

**The wiring contract — authored here, and it replaces the seam that used to be missing.** The
epic previously made FIX-548's template the reference shape and had the skill point at it; the
skill can never reach it, since nothing may instruct an agent to read our monorepo and a
brownfield developer installs only the plugin. That is now resolved the other way round: **this
issue authors a wiring contract that both entry paths satisfy, and FIX-548's template conforms to
it.** Writing the shape and specifying it are different jobs. The contract is skill content, so
it travels the path skill content already travels — authored here, packaged by FIX-1160, shipped
in the plugin — and needs no new package, artifact, or dependency between packages.

It covers only what both paths genuinely share, which is less than the template carries (that
also has a chat page and a `flows/chat.ts` no brownfield run writes, and a plain-Node run writes
no mount at all): **the Next.js mount pair · the config's shape, including a declared store
profile · how the provider is wired, down to the model string · the dependency set · the runtime
floor.**

**The config must declare a store profile, because `stores` is not optional.** It is a required
option needing at least one named profile — `createFlowState({ flows })` alone neither typechecks
nor initializes, which would break every command the next-steps block prints. Which profile ships
and how it is labelled a development default is decision 4's call; that one exists at all is the
contract's.

**The provider is imported statically and passed as a pre-built `modelResolver`, never through
the `models` shorthand.** `createModelResolver` reaches providers through `createRequire` and a
dynamic `import()`, and **Next bundles server code, which breaks that path** — our own published
Vercel guide already says exactly this and shows the fix. Both entry paths mount into Next, so it
binds both, which is why it sits in the contract rather than in either issue. **The failure it
prevents is the reason it is stated at all:** the dependency rule can be fully satisfied — the
provider package installed, the manifest complete, an isolated install green — and the first
browser request still fails with `No provider available`. Installing a package and being able to
reach it through a bundler are two different claims, and only one of them had a check.

**The contract also fixes the model string, for the same reason it fixes the wiring: nothing
downstream will.** The provider table above is the contract's, not this path's — FIX-548's
template names the same string for the same provider, because a greenfield project and a
brownfield project pointed at the same docs should not run different models, and because the
failure mode is identical on both sides. There are no built-in defaults to fall back on and no
validation of a model id anywhere between the config and the provider's API, so "a chat model for
that provider" is not a specification; it is an instruction to guess. Updating the three strings
when the corpus moves is a follow-up (§12), and it is one edit in one table.

**The dependency set is a rule, not a list: every package the generated files import directly is
a direct dependency.** Stating it as a rule is what closes the class, because two separate review
rounds each found one member missing from a list. **pnpm's strict isolation does not expose a
dependency's own dependencies for direct import**, so "core already depends on it" never
satisfies a consumer's `import`. Under the shape specified here that means:

- **`zod`** — the generated flow needs an input schema and imports `z` directly.
  `@flow-state-dev/core` carries `zod` in its own dependencies, which does nothing for a consumer
  under pnpm. Without it the run fails while *importing* the generated flow, before reaching a
  model at all.
- **The AI SDK package for the provider the developer chose** — `@ai-sdk/openai`,
  `@ai-sdk/anthropic` or `@ai-sdk/google`, never a fixed one. `@flow-state-dev/core` carries
  `@ai-sdk/openai` as a **devDependency only**, and the model resolver loads provider packages
  from the consumer's own `node_modules`, so with it absent the first request throws
  `No provider available`.
- **`@flow-state-dev/devtool`**, an optional peer of the CLI satisfied only inside our monorepo,
  without which `fsdev dev` — a command the next-steps block prints — cannot resolve its assets.

**The manifest is proved by an isolated install, and a static scan may not be substituted** (§10).
npm hoists transitives into a flat `node_modules`, so an npm-only proof passes on an incomplete
`package.json`; and a static import scan cannot see the provider SDK at all, which is resolved at
run time rather than imported. This binds both issues symmetrically — the brownfield manifest and
FIX-548's greenfield manifest each need their own isolated install.

**The runtime floor is 22.18, not 22.** Every FSD package declares `"engines": {"node": ">=22"}`,
and that is the wrong number to check: both paths emit a **TypeScript** config — `.mts` here,
`.ts` on FIX-548's template (decision 3) — and the CLI loads either with a native `import()` that
needs **Node 22.18+** for type stripping. `load-config.ts` names 22.18 in its own error text and
tests both extensions with one `/\.m?ts$/`, so the extension divergence does not move the floor.
Node 22.0–22.17 passes a `>=22` check and then fails every printed command at config load. **Both
entry paths check 22.18 before writing anything, and the guidance names 22.18.** A `.mjs` or `.js`
config is the documented escape, but a path that emits TypeScript does not get to rely on it.

**Untouched:** the engine, the adapters, every block kind, and `.agents/skills/` (our own
development skills). Nothing here changes framework behaviour.

| Case | Expected |
|---|---|
| The `.env.local` **that will be filled** is already tracked by git | Refuse before writing anything, naming that file and `git rm --cached <path>`. The question is asked of **resolution 10's** path, which is the write root's own file only when nothing further up assigns the key. |
| **The line to fill is an empty assignment in a *tracked* ancestor `.env.local`** | Refuse. This is the composition that walks a credential into version control: the effective assignment is the empty `OPENAI_API_KEY=` at the repository root, so the rule says *fill that line*, while a tracking check aimed at `apps/web/.env.local` finds a file that does not exist, reports untracked, and lets the run proceed. **The developer then pastes a live key into a committed file because we pointed at it.** Same weight as soliciting the key in chat — the end state is a secret in version control, reached by following our instructions. |
| Project has an explicit `"type": "commonjs"` | Nothing special — decision 3 makes the written config format-independent. The report still states it, because the *developer's own* later files are affected. |
| Node below the floor | **The floor is 22.18, and the guidance names 22.18** — not the `>=22` our packages declare. Detection reports the host's version and the run refuses before writing. `>=22` is the wrong number twice over: Node 22.0–22.17 passes it and then fails every printed command at config load, because the CLI loads the emitted TypeScript config — `.mts` on this path — with a native `import()` that needs type stripping; and Next 16 accepts Node 20.9+ while npm's engines check only warns, so without this gate a run completes and hands over an app that cannot start. | Host framework cannot be identified | Report `unknown` and stop. Do not guess a mount location. |
| Next.js project on the **Pages Router** | Report `next-unsupported` and refuse before writing. `createNextHandler` returns App Router route exports and there is no Pages handler shape, so the mount could not work even if the install succeeded. | Next.js **below 15** | Report `next-unsupported` and refuse before writing. Both adapters declare `next: ">=15.0.0"` as a peer, so the install would fail after four files were already on disk. Name the installed version and the required range. |
| Two lockfiles, no `packageManager` field | Report `ambiguous` and refuse before writing. Name both lockfiles and offer the two cheap answers: delete the stale one, or declare a `packageManager`. | Two lockfiles **with** a `packageManager` field | Not ambiguous. The field wins and the run proceeds, and the report says which lockfile it is ignoring so the developer sees it in the plan before accepting. |
| `AGENTS.md` exists with unrelated content | Append a delimited section; everything outside the delimiters is untouched. |
| **A prose file carries an FSD start delimiter with no matching end** | Refuse before writing, naming the file and the line. **Never replace to end of file** — that deletes everything the developer wrote below the marker, which in a `.gitignore` is their whole ignore list. This is the destructive case the balance rule exists for, and "search for the end and use EOF if missing" is the implementation that causes it. |
| **A prose file carries more than one FSD section, or a nested or out-of-order pair** | Refuse before writing, naming every delimiter line. There is no defensible pick: replacing one leaves the other as orphaned content nothing will ever update again, and replacing both is a rewrite of a region we did not author. |
| Project uses the `src/` layout | The mount goes under `src/app/`, because that is where detection resolved the app root. **Never create a root `app/`** — Next prefers root over `src/`, so that would shadow every route the project already serves, silently on Next 15 and as a hard build error on Next 16 when a `src/pages` is also present. |
| `next.config.*` sets `pageExtensions` excluding `ts` | Write the mount with an enabled extension — `tsx` where that is allowed. If neither `ts` nor `tsx` is enabled, refuse: a route file we can write would not be a route. Never write `route.ts` into a project that has configured it out, which lands the files and leaves `/api/flows` non-existent with nothing in the output. |
| `pageExtensions` present but not a plain array of literals | Refuse before writing. Reading it would mean executing the project's config, which detection does not do. Name the file and ask the developer to confirm which extensions are enabled. |
| A required path already exists and is not ours | Refuse the **whole run** before the first write, naming every colliding path. Never write the rest and skip the collision — that leaves the repository changed and the promised mount or demo flow absent. |
| The `fsdev.config.*` the CLI loads is the project's own (no marker) | **Not a collision — proceed.** Write no config, write everything else, and hand back the one line that registers the new flow in it. | **More than one `fsdev.config.*` in the root** | Report every candidate in the CLI's precedence order (`.ts`, `.mts`, `.js`, `.mjs`) and act **only on the winner** — the CLI loads the first present and ignores the rest, printing its own stderr warning about them. | The developer declines to choose a provider | Refuse before writing. There is no default: guessing installs the wrong `@ai-sdk/*` package, writes the wrong environment variable name, and wires a provider with no credential behind it. |

| The **effective** value (resolution 9) is non-empty | Write nothing to any `.env.local` — no section, no duplicate assignment. | The **effective** value is empty | Leave that line where it is and ask the developer to fill it, by path. Never add a second assignment for the same key, wherever the first one sits — and check git tracking on **that** file before pointing at it. |
| **The effective value is non-empty and lives in an ancestor `.env.local`** — a workspace root above the app | Write nothing. Report that the credential is already configured **and name the file**, since the developer looking at `apps/web/.env.local` sees an empty directory's worth of nothing. Appending `KEY=` here would be the quietest failure in this document: the nearer file is loaded first, `""` counts as set, and the working parent key is never applied — leaving a project whose own `.env.local` contains the right variable name and which fails with `No provider available`. |

Two rules matching one project is the tell that the filesystem was asked a question only the loader can answer. |
| A route slot holds a file anywhere in the scan set that is **not ours** | Refuse before writing, naming the occupant. `route.js` occupies the slot `route.ts` would take: whichever file Next then prefers, the result is either silently replacing the developer's endpoint or silently failing to serve ours. Refuses even when one of our own files is also in the slot — two live handlers at one slot is the same collision. |

| Our `route` file from a previous run sits at an extension `pageExtensions` no longer enables | Refuse before writing, naming the file. | `packageManager` names a manager outside npm / pnpm / Yarn | Refuse before writing, naming it and listing what is supported. The field being authoritative settles *which* manager, not whether commands exist for it. |
| `scripts.dev` renamed or on another port | Render the script the project actually has, and its port. Never print `pnpm dev` and `localhost:3000` at a project that moved either — that is precisely the command-the-project-cannot-run failure. |
| No identifiable dev script, on a **Next** host | Refuse before writing. The `mounted-route` next steps print the project's own dev command and the URL it serves, so there is nothing truthful to write. |
| No identifiable dev script, on a **plain-Node** host | **Proceed.** The `second-process` branch prints only `fsdev dev` and `fsdev serve --host 127.0.0.1`, says the developer's own server is untouched, and names neither their script nor their port — so the field it would refuse over is one this topology never reads. A library, a `node server.js` service, or a container entrypoint is a coherent host, and refusing it rejects a setup that would have worked. |
| Second run, delimited text files | Replace between our own delimiters, having first confirmed there is exactly one balanced pair. Never a second section. |
| **A Next app inside a workspace — `apps/web`, lockfile and `packageManager` at the repository root** | Proceed. Reporting `undeclared` here would refuse an ordinary pnpm monorepo, and writing at the repository root would put a config and a demo flow above every app in it. |
| **A workspace app carrying a stale `package-lock.json`, with `packageManager: pnpm` at the root** | Resolve **pnpm** and install with it. The workspace boundary is the `pnpm-workspace.yaml`, not the nearest lockfile, so the search reaches the root declaration; and a `packageManager` field anywhere in the chain beats every lockfile in it. **Bounding the search at the stale lockfile makes the app its own workspace root, resolves npm, and installs through the wrong manager** — writing a lockfile the workspace does not manage and a `node_modules` it did not build. A stale lockfile beside an app is common enough that this is an ordinary project, not an exotic one. |
| **`next.config.*` sets a `basePath`** | Carry it. The mount answers at `<basePath>/api/flows`, and every printed or probed URL uses the resolved path. **Never advertise the bare `/api/flows`**: Next's router tests the prefix and returns before route matching, so the endpoint we told the developer to open does not merely miss — it is rejected upstream of the matcher. Unreadable statically → refuse, as for `pageExtensions`. |
| **Detection pointed at a workspace root** | Refuse before writing, naming `pnpm-workspace.yaml` (or the `workspaces` array, or the manifests found beneath) and asking the developer to run it in the app they mean. **Never classify it as a `node` host** — a workspace root has no `next` dependency of its own, so the plain host rule would call it Node and write a second-process setup at the top of the repository. Never pick one of the apps either; nothing in the repository says which one they want. |
| Second run, a file the run authored whole, still unedited | Marker matches the body: ours. Leave it or rewrite it, and report which. |
| Second run, a file the run authored whole, since edited | Marker missing or not matching: **do not overwrite.** Name the path, say it was left alone, and print what would have changed so the developer can merge it themselves. |
| Second run, and the config the CLI loads is ours | The marker says so, so the demo flow *is* registered. Do not print the unregistered-flow remediation — that warning belongs to a config the project wrote, not to one from a previous run. Asserted against the **winner**, never against any config carrying our marker. |
| Project already has an `fsdev.config.*` **it wrote itself** (no marker) and it is the one the CLI loads | Report it and do not overwrite. A present config makes runtime resolution use its explicit registry instead of directory discovery, so a newly written demo flow would be invisible to it — say the flow is unregistered and print the one line that registers it, rather than promising `fsdev run hello send` will work. |
| A dependency is already declared at another version | The package manager decides. The run reports what the install did. |
| Install fails (offline, registry error) | Files stay; report the failure and the exact command to retry. Do not roll back. |
| The demo flow is unauthenticated and `fsdev serve` defaults to `0.0.0.0` | Print the loopback form and say why. Never print `--allow-unauthenticated`: teaching someone to switch off a safety rail in their first hour is the wrong lesson, and the guard is correct. |
| The Next.js next steps run the app and `fsdev dev` over one store directory | Two filesystem-store instances over the same directory can each accept the same write. Tolerable for a development default (decision 4) as long as nothing implies the two should drive the same session concurrently; the block's wording and the docs page owe the caveat beside "replace this before you deploy". |
| The developer has no coding assistant | Not served by anything this issue ships (decision 2). The docs page §11 creates is the whole answer, and the README points at it. |

**Taxonomy:** detection writes nothing, so it cannot fail destructively. **Every refusal is
decided from unmodified state and stated before anything is written** — the write barrier in §7
lists the conditions and what each reads. Three separate defects have been the same violation of
that one rule, which is why it is stated as an invariant with an enumeration rather than as a
property of each case.

**Two stops legitimately happen after writing, and naming them is what keeps the invariant
falsifiable.** A rule with unmarked exceptions cannot be checked, and both of these are
*outcomes* rather than refusals — neither is knowable from any state the run could have read
first:

- **the install fails** (offline, registry error). Files stay, the failure is reported with the
  retry command, and nothing is rolled back. We cannot know the registry is reachable without
  reaching for it.
- **the developer never fills in the credential line.** The run stops before printing next steps
  that promise a model response the project cannot produce. The line has to exist before it can
  be filled, so this cannot precede the write that creates it.

Anything else that stops after a write is a defect in the barrier, not a third exception. **The
skill's own two-phase structure is what enforces this**: every condition that can refuse is
evaluated in phase 1, and phase 2 contains no refusal at all. A failed install is the one non-fatal case, and it is retryable. **A refusal that
fires after a write would be a defect in this table, not a new case for it** — that is the test
to apply when adding a row.

### 10. Testing strategy

**Goal checks** (the epic's proof for this issue; real projects, real model, both brownfield):

- *Mounted-route path* — a fresh `create-next-app` **scaffolded with `--src-dir` and installed
  with pnpm**, with distinctive content seeded into `package.json`, `.gitignore`, `.env.local`
  and `AGENTS.md` and a route that existed before the run. An agent is given the install skill
  and nothing else. Afterwards every seeded string is intact, the pre-existing route still
  responds, the **resolved mount URL** and a nested path beneath it both respond — the probe uses
  resolution 6's path rather than a hardcoded `/api/flows`, so the check still means something in a
  project with a `basePath` — and **a request through the
  mounted HTTP route returns a streamed model response**. **The run's own report is compared
  against the actual diff**, so a file it touched but did not name is a failure.

  **Three of those setup choices are load-bearing rather than incidental.** `--src-dir` is the
  layout that catches a run writing to a root `app/`: the pre-existing route lives under
  `src/app`, so shadowing it makes that assertion fail instead of passing silently. pnpm's
  strict isolation is what catches a missing direct dependency — under npm's flat
  `node_modules` a hoisted `zod` or provider SDK satisfies the import and the whole class hides.
  And **the model request goes through the HTTP route rather than through `fsdev run`**: the CLI
  runs in-process and resolves providers through the dynamic path that works there, so a
  CLI-only check stays green while the product's actual path — a bundled Next server — is broken.
  That is precisely how the static-provider wiring in the contract could go missing with every
  other check passing.
- *Second-process path* — the same skill against an **existing plain-Node project**, seeded and
  checked the same way. The printed command starts FSD, a call to it returns a streamed model
  response, and the project's own server still runs. This is a different host and a different
  shape, not the same check twice, and with the Node template cut it is the epic's only Node
  coverage of any kind.

**These are one recorded observation each, not deterministic checks** — the honest cost of the
brownfield path being an agent, and the same shape as FIX-1160's proof. **Neither run pre-exports
the provider key, and neither supplies it through the conversation**: the run prepares the empty
variable line and the key is pasted into the file directly, which is both what exercises the
credential path and what the path itself requires. A brownfield check that handed the key to the
assistant would be testing a flow the design forbids.

**CI specs** (behaviours, not test names) — all against fixture project trees in a temporary
directory; no `create-next-app`, no network, no install:

- one behaviour per decision in §6, in observable terms
- **the report is right** — one case per host shape, per lockfile, per `type` setting, plus an
  unidentifiable directory
- **package-manager precedence, each rule its own case** — a `packageManager` field beats a
  lockfile that disagrees with it; a single lockfile with no field resolves to that manager; **two
  lockfiles with no field resolve to `ambiguous` and refuse**, naming both files; and **a project
  with neither a field nor any lockfile resolves to `undeclared` and refuses**, asking for a
  `packageManager` declaration. That last case is asserted **with `npm_config_user_agent` unset
  and again with it set to an npm agent** — both must refuse. The second half is the one that
  matters: it is the fixture that fails if an implementer keeps the old fallback, and its failure
  mode in the field is `npm add` fabricating a `package-lock.json` in a pnpm project
- **an unsupported Next shape refuses and does not degrade** — a Pages Router project and a Next
  14 project each resolve to `next-unsupported`, not to `next` and not to `node`, and the refusal
  names which condition failed. The `>=15` bound is asserted against the adapters' declared peer
  range rather than hardcoded twice, so bumping the adapter moves this check with it
- **the report's JSON is a contract** — its shape is asserted directly, because the skill is the
  consumer and there is no compiler between them
- **detection writes nothing** — run against a seeded tree and assert every file is unchanged,
  including mtimes
- **the printed commands actually run** — execute the strings the next-steps block emitted, in a
  wired-up fixture project, and assert the process starts. This is where npm's option separator
  and the network-bind guard are caught; a plausible-looking transcript has hidden a broken
  command three times
- **the block says the same thing across managers** — the same steps in the same order with the
  same caveats, and the commands differing exactly where the manager differs. Asserted on the
  content, not on the rendered string, because requiring the two renderings to match byte-for-byte
  is wrong for at least one supported context
- **the skill's rules are checkable** — its first instruction runs detection; its instruction set
  names no file outside its host's allowlist — seven for `next`, five for `node`, asserted per
  host rather than against one number; it states which shape the host got
- **the app root is detected, never assumed** — a fixture laid out under `src/app` resolves to
  `src/app`, one under root `app/` resolves to root, and a fixture with **both** resolves to root
  the way Next's own `findDir` does. Then the writing rule: given a `src/app` fixture, every path
  the skill would write sits beneath `src/app` and **no root `app/` is proposed** — the assertion
  that would have caught the shadowing bug
- **the route extension follows `pageExtensions`** — a fixture with no `next.config` gets `.ts`;
  one configuring `['jsx','js']` refuses; one configuring `['tsx','ts','jsx','js','mdx']`
  proceeds with `.ts`; one whose `pageExtensions` is a function or a spread refuses rather than
  guessing. The assertion is on the extension chosen, not on the file merely being written,
  because writing a file Next ignores is the bug
- **the write barrier holds on every refusal, asserted as one behaviour over every row of that
  table** — for each refusal condition, a fixture that trips it leaves the working tree
  **byte-identical**, mtimes included. This is the check that would have caught all three
  instances at once, and it is written as a loop over the conditions rather than as one test per
  condition, so a new refusal is covered the moment it is listed
- **the credential guard sees through a negation, and writes nothing to find out** — a fixture
  whose `.gitignore` re-includes `.env.local` after our delimited section must **fail before the
  fix and pass after**: assert the run stopped, **no key was written, and `.gitignore` itself is
  unchanged**. That last clause is the one that fails on a write-then-check implementation, which
  otherwise passes this test. Paired with a fixture using `-v` semantics to show why the check is
  `-q`, since a `-v` exit-code test passes while the credential lands
- **a populated credential survives a rerun** — seed `.env.local` with a real-looking value, run
  twice, and assert the value is unchanged and appears **exactly once** in the file. Then the
  masking variant explicitly: a pre-existing key above our section must never gain a second empty
  assignment below it, asserted by parsing the file the way the CLI does and checking the resolved
  value is non-empty
- **a credential in an ancestor is not masked by one we write** — a fixture with the provider key
  non-empty in a **workspace-root** `.env.local` and the write root two directories down with no
  `.env.local` of its own. Assert the run writes **no** `.env.local` at all, names the ancestor
  path in its report, and that **resolving the variable the way `loadEnvFiles` does — nearest file
  first, first-set-wins — still yields the parent's value**. *Asserted through the loader's own
  walk rather than by reading one file, because reading one file is the bug: an empty `KEY=` in
  the nearer file passes a "the variable is present" check and fails the resolution.* Paired with
  the within-file variant above, since the two directions are opposite (last-wins inside a file,
  nearest-wins across files) and fixing one has twice left the other standing
- **the effective credential is one value, and the masking case is not reported as configured** —
  a fixture with an empty `KEY=` in the write root and `KEY=secret` in the parent. Assert the run
  writes nothing, reports the **write root's line as masking the parent**, and does **not** report
  the credential configured. *Asserted by resolving through `loadEnvFiles` and checking the result
  is empty — a check phrased as "is it non-empty somewhere?" passes here while the product is
  broken, which is the whole defect.*
- **the tracked-file refusal follows the file that will be filled** — a fixture with an empty
  `KEY=` in a **repository-root `.env.local` that is tracked by git**, and a write root at
  `apps/web` with no `.env.local` of its own. Assert the run **refuses**, names the repository-root
  path in the `git rm --cached` remediation, and **writes nothing**. *This is the credential-into-
  git composition: the fill instruction points at the ancestor while a tracking check aimed at the
  write root sees a file that does not exist, reports untracked, and lets the run continue. A
  fixture that asks about the write root's file passes on the broken behaviour, so the assertion is
  on which path the refusal names.*
- **a malformed delimiter block refuses and deletes nothing** — three fixtures, each asserting the
  file is **byte-identical** afterwards, not merely that it still exists:
  - `.gitignore` with an FSD start delimiter and **no end**, followed by 20 lines of the
    developer's own rules → refuses, and every one of those lines is still there. *The
    implementation this catches finds the start, searches for the end, and truncates to EOF; it
    passes a check that only asserts the run stopped.*
  - `AGENTS.md` carrying **two** complete FSD sections → refuses, naming both
  - a file with an end delimiter **before** its start → refuses
  - and the negative control: exactly one balanced pair replaces cleanly, with content above and
    below it untouched
- **the roots are resolved, and nothing is written above the write root** — a workspace fixture:
  `apps/web` holding the Next app, `pnpm-lock.yaml` and `packageManager` at the repository root
  only. Assert the manager resolves to pnpm **from the root declaration** (not `undeclared`), the
  install is invoked in `apps/web`, the report names the root lockfile by path, and **every path
  the run writes is beneath `apps/web`** — asserted as a prefix check over the whole write set,
  since a single wrong path is the whole defect. *Without the ancestor search this fixture refuses;
  without the write-root rule it writes at the repository root.*
- **a stale lockfile inside a workspace app does not decide the manager** — `apps/web` carrying a
  `package-lock.json`, `pnpm-workspace.yaml` and `packageManager: "pnpm@9"` at the repository root.
  Assert the resolved manager is **pnpm** and the install command is a pnpm one. *Under a workspace
  search bounded by the nearest package-manager signal, `apps/web` becomes its own workspace root,
  the root declaration is never seen, and this resolves npm — so the assertion is on the manager
  and the command, not on the search terminating.* Paired with the inverse: an app that declares
  its own `packageManager` **overrides** the root's, since the nearest field wins among fields
- **the mount URL carries `basePath`** — a fixture whose `next.config.ts` sets
  `basePath: '/portal'`. Assert every printed and probed URL is `/portal/api/flows`, and that the
  bare `/api/flows` appears **nowhere** in the rendered next-steps block. *The failure this catches
  is a 404 on the one endpoint we told the developer to open: Next's router tests the prefix and
  returns before route matching, so the files are correct and the advertised path is not.* Plus a
  `basePath` that is a template literal or a computed expression → **refuses**, on the same terms
  as an unreadable `pageExtensions`; and the negative control, no `basePath` → `/api/flows`
- **a workspace root refuses instead of being classified as a Node host** — detection pointed at a
  directory with `pnpm-workspace.yaml` and two apps beneath it resolves to `workspace-root`, not
  to `node`, and writes nothing. *The bug this catches is silent: a workspace root has no `next`
  dependency, so the plain host rule returns `node` and the run scaffolds a second-process setup
  at the top of the repository.* Asserted for a `workspaces` array in `package.json` too, so the
  check does not encode pnpm alone
- **the skill never solicits a key value** — its authored instructions are scanned for any
  instruction to ask for, accept, read, or repeat a key, and the only credential instructions
  present are write-the-empty-line, ask-them-to-fill-it, and assert-non-empty. Cheap and worth
  having: the failure is a live credential in a retained transcript, and it reached this document
  once as a single clause left standing in a paragraph that was otherwise rewritten
- **a route slot is checked across the scan set, and classified by marker** — four fixtures,
  because each of the three fixes in this area was a rule that could not fail on its own:
  - a slot owning `<appRoot>/api/flows/route.js` under default extensions **refuses**, nothing
    written. Asserted per extension in the enabled set rather than for `.js` alone, so the check
    does not encode the one example that was reported
  - a slot holding **only our own marker-matching `route.ts`** — the state every second run is in
    — **completes**, rewriting or leaving it. *Under a presence-only rule this fixture refuses,
    which is why it is written as a positive case: it is the assertion that fails on the
    contradiction rather than reporting it.*
  - a slot holding our marker-matching `route.ts` **and** an unmarked `route.js` **refuses**. Our
    file being present does not make the slot ours
  - **`pageExtensions` narrowed to `['tsx']` with our marker-matching `route.ts` still in the
    slot** — the run **refuses**, naming the stale file, and **writes no `route.tsx`**. *Under a
    scan of enabled extensions only, this fixture reports the slot empty, writes a second handler,
    and **passes** — which is what makes it the load-bearing one. The assertion is on nothing
    being written, not merely on the stale file surviving, since it survives either way.*
- **an unsupported package manager refuses** — a fixture declaring `"packageManager": "bun@1.2.0"`
  stops before writing and names the supported set, rather than proceeding into an install command
  that does not exist
- **provider selection reaches every artifact it decides** — choosing `anthropic` installs
  `@ai-sdk/anthropic`, statically imports `createAnthropic`, writes `ANTHROPIC_API_KEY`, and makes
  the generated flow name the **exact string `anthropic/claude-haiku-4-5`**; declining refuses.
  Asserted across all four together, because the failure is them disagreeing, not any one being
  wrong. **The model string is asserted literally against the contract table**, not as "a string
  starting `anthropic/`" — the defect being guarded is a plausible invented id, which a
  prefix-shaped assertion accepts and a provider rejects on the first request
- **the generated config declares no intents** — asserted directly, because declaring one without
  a `defaultModel` throws at construction and takes every printed command down with it. A fixture
  builds the config the skill would write and calls `createFlowState` on it
- **a user-owned config completes the run** — a fixture with a marker-less `fsdev.config.mts`
  writes the flow and everything else, writes no config, and returns the registration line. The
  regression this guards is the run refusing and the project never being able to finish
- **the config the run acts on is the one the CLI loads** — a fixture holding **both** our
  marker-carrying `fsdev.config.mts` and a marker-less `fsdev.config.ts` must report the `.ts` as
  the winner, write no config, return the registration line **naming the `.ts`**, and must **not**
  report the demo flow as registered. *Under the single-config model this fixture reports "flow
  registered" and passes — the check that cannot fail, on a file the loader is not loading.* Paired
  with a precedence case asserting the order `.ts` → `.mts` → `.js` → `.mjs` against
  `CONFIG_FILENAMES` itself rather than a second copy of the list, so reordering the loader moves
  this check with it
- **preflight refuses as a whole run** — seed one required path (an unrelated
  `flows/hello/flow.mts`, then separately a pre-existing mount file) and assert **nothing at all
  was written or appended** — no credential line, no instructions section, no install invoked.
  Asserting only that the colliding file survived would pass on the broken behaviour
- **the printed command is the project's own, and the refusal is scoped to the topology that
  prints one** — a fixture whose dev script is renamed renders that name; one whose script sets
  another port renders that port; a **Next** fixture with no identifiable script **refuses**; and a
  **plain-Node** fixture with no identifiable script **completes**, emitting a `second-process`
  block that names neither a script nor a host URL. *That last case is the one that fails on an
  over-broad refusal: it rejects a coherent host over a field that topology never reads.* Paired
  with the executed-command check, since a rendered command that is correct but unrunnable is the
  failure this pair exists to catch
- **rerun ownership, three cases per authored path** — absent writes it with a marker; present
  and matching its marker is treated as ours; present with the marker missing or stale is left
  untouched and reported. Asserted for the config, the flow and both route files, since the rule
  has to hold for every path the run authors, not just the config
- **a config carrying our marker does not trigger the unregistered-flow warning**, and one
  without a marker still does — the two halves asserted separately, because the bug was that one
  rule covered both
- **the skill's embedded block equals canonical after normalization** — the skill is a shipper
  like any other, so it invokes the exported comparison against its own copy. **Equality over the
  whole block, every branch included**, never presence or a substring: the regression case is a
  copy with the `second-process` branch trimmed, which a presence check passes and this one fails
- **the comparison is the only implementation** — asserted by the skill's test importing the
  exported one rather than reimplementing normalization, since a second implementation is the
  drift a single owner exists to prevent

**Where the line falls.** The two goal checks are real-machine runs under `goals/fsd-install/`,
one directory per host shape, never part of the vitest suite. Everything above runs in CI with no
network.

**Discipline:** `tdd`. The seam is the report and the block's substitution against a temporary
project directory.

**Verified premises** (measured, so a reviewer need not re-derive them):

- **Module-type loading, probed on Node 22.22** (the run that produced decision 3): a
  `fsdev.config.ts` with `export default` fails under an explicit `"type": "commonjs"`
  (`SyntaxError: Unexpected token 'export'`); under a `package.json` with no `type` field it
  loads but emits `MODULE_TYPELESS_PACKAGE_JSON` and reparses; `fsdev.config.mts` loads cleanly
  in every setting. The earlier claim that "CommonJS projects cannot load an ESM
  `fsdev.config.ts`" is true only of the explicit form, and `.mts` makes the distinction moot.
- **The CLI loads exactly one config, first-present, and `.mts` is second.** `CONFIG_FILENAMES` in
  `packages/cli/src/load-config.ts` is `["fsdev.config.ts", "fsdev.config.mts", "fsdev.config.js",
  "fsdev.config.mjs"]`; `locateConfig` filters that list by existence, takes `present[0]`, and
  writes a stderr warning naming each file it is ignoring. Decision 3 needs no loader change —
  **but "second in precedence" means `.ts` wins, which is the consequence the earlier wording
  conceded and did not draw.** Every rule in §7/§9 that used to say "the config" now says the
  precedence winner, because a marker in a shadowed `.mts` otherwise proves nothing about what
  runs.
- **The framework ships no default model and no built-in intent lists, and validates no model id.**
  `createModelResolver` carries no model table — only `PROVIDER_PACKAGES` mapping
  `openai`/`anthropic`/`google` to `@ai-sdk/*` and their factory names — and
  `apps/docs/docs/fundamentals/models.md` states it in prose ("Apps configure their own model
  lists per intent — there are no built-in defaults"). `defaultModel` is **required** once
  `intents` is non-empty and throws at construction otherwise; `parseModelString` validates the
  `provider/model` *shape* and never the id; `scripts/validate-model-strings.mjs` guards only the
  removed `preset/*` syntax. So an invented model id survives construction, install, and every CI
  check, and fails on the developer's first request. Hence the exact strings in §7's provider
  contract.
- **`createModelResolver({ providers: { <name>: <instance> } })` with no intents is a documented
  shape**, shown in `apps/docs/docs/getting-started/setting-up-models.md` for a pre-built provider,
  and `createFlowState` accepts the built resolver as `modelResolver`. That is what lets the
  generated config avoid intents entirely and name one concrete model on the flow's generator.
- The CLI's flow discovery matches only `flow.ts` / `flow.js` / `index.ts` / `index.js`, so a
  `.mts` flow is registered explicitly in the config rather than discovered — which is what the
  CLI does anyway whenever a config is present.
- **Next resolves its app directory root-first, so writing a root `app/` into a `src/app` project
  shadows it.** `findDir` in `next/dist/lib/find-pages-dir.js` joins `dir` with the name, returns
  it if it exists, and only then tries `dir/src/<name>` — carrying the comment *"prioritize
  `./${name}` over `./src/${name}`"*. Read from the published tarballs of **`next@16.3.1`** and
  **`next@15.5.23`**, fetched from the registry and extracted, since no Next is installed in this
  repo. **The two versions then differ, which is why both were checked:** 16's `findPagesDir` adds
  a guard that throws *"`pages` and `app` directories should be under the same folder"* when a
  found `pages` and a found `app` have different parents; 15 has no such guard. So the same
  mistake is a hard build failure on 16 for a project with `src/pages`, and a silent shadowing
  everywhere else.
- **Across `.env.local` files the *nearest* wins, and an empty value counts as set — so a file we
  write in a child directory masks a working key in the parent.** `loadEnvFiles` in
  `packages/cli/src/load-env.ts` walks from cwd upward to the filesystem root applying each file
  it finds, and `applyEnvFile` assigns only `if (process.env[key] === undefined)` — first-set
  wins, and the cwd's own file is applied first. `""` is not `undefined`, so an empty
  `OPENAI_API_KEY=` in `apps/web/.env.local` is a set value that stops the workspace root's real
  key from ever being applied. The file's own header states the precedence: shell environment,
  then explicit `--dotenv` paths, then cwd and up. **This is the across-file mirror of the
  within-file rule below, and the two run in opposite directions** — nearest-wins between files,
  last-wins inside one — which is why both are written down rather than one being left as an
  instance of the other.
- **A duplicate key inside one `.env.local` resolves to the *last* occurrence, so an appended
  empty assignment masks a working credential.** `parseEnvFile` in `packages/cli/src/load-env.ts`
  iterates `content.split("\n")` and calls `vars.set(key, value)` for every line, with no
  first-wins guard inside the file; replaying that parser over a real key followed by our
  delimited section's `OPENAI_API_KEY=` resolves the variable to the empty string. The
  "first source to set a key wins" comment in that file governs precedence *between* sources —
  process env, then each `.env.local` up the tree — and does not reach duplicates within one file.
- **`route.ts` and `route.js` occupy the same App Router slot.** `createValidFileMatcher` builds
  its leaf pattern from the enabled extension list, so with the default
  `['tsx','ts','jsx','js']` `isAppRouterRoute` returns true for `route.ts`, `route.js` and
  `route.tsx` at the same directory — the matcher does not disambiguate between them. A Next
  16.1.6 fixture built on this PR observed the pair compiling with `route.ts` selected and
  `route.js` silently excluded. The rule this issue adopts does not depend on which one wins,
  because both outcomes are an undetected collision.
- **A `.gitignore` negation re-includes a file our own entry ignored, and `git check-ignore -v`
  will not tell you.** Reproduced in a scratch repository: with `.env*`, then our delimited
  section, then `!.env.local`, the file is **untracked** (`git ls-files --error-unmatch` fails)
  yet **not ignored** — and `git add -A` staged `.env.local`. The exit codes differ by flag:
  `git check-ignore -q` exits **1** (correctly, "not ignored"), while `git check-ignore -v` exits
  **0**, because verbose mode reports that *some* pattern matched and the matching pattern was
  the negation. **A guard written with `-v`'s exit code passes on exactly the case that leaks the
  key.** Hence `-q`, and hence checking after the edit rather than predicting from our own entry.
- **`pageExtensions` decides whether a `route.ts` is a route at all.**
  `createValidFileMatcher` in `next/dist/server/lib/find-page-file.js` composes
  `` `(^route|[\\/]route)\.(?:${pageExtensions.join('|')})$` `` and `isAppRouterRoute` tests
  against it, so a project configuring `['jsx','js']` makes `route.ts` a non-route with no error
  anywhere. The default is `['tsx','ts','jsx','js']`, read from `dist/server/config-shared.js`.
  Both read from the published `next@16.3.1` tarball.
- **`basePath` decides the URL the mount answers on, and a bare path is rejected before route
  matching.** In `next/dist/server/lib/router-utils/resolve-routes.js` from the published
  `next@16.1.6` tarball, the dynamic-route resolver does
  `if (config.basePath) { if (!pathHasPrefix(curPathname, config.basePath)) { return; } … }` —
  an early `return` ahead of any `route.match`, so a request to `/api/flows` in a project with
  `basePath: '/portal'` never reaches the matcher at all. The matched page is then fetched through
  `addPathPrefix(route.page, config.basePath)`, confirming the served path carries the prefix.
  So the mount files are correct and the advertised endpoint is wrong, which is why the URL is a
  resolved fact rather than a constant.
- **Both Next adapters require Next 15 or later, and both are App Router only.**
  `@flow-state-dev/next` and `@flow-state-dev/vercel` each declare `"next": ">=15.0.0"` under
  `peerDependencies`, read from their manifests. `createNextHandler` is documented as the
  "Platform-agnostic Next.js App Router adapter", returns the `{ GET, POST, PATCH, DELETE }`
  exports a catch-all route file needs, and types its route context as
  `{ params: Promise<{ path?: string[] }> }` — Next 15's async `params`. There is no Pages
  Router handler in either package. This is what the host row refuses on, and it is why the
  refusal is a correctness gate rather than a scope preference.
- `serve()` in `@flow-state-dev/node` defaults its host to all interfaces and applies no
  authentication guard itself; the guard is `assertNetworkBindIsAuthenticated` in the CLI's
  `serve` command. This is why the printed command carries `--host 127.0.0.1`, and it is why the
  brownfield Node path starts FSD through our CLI rather than through a generated entrypoint.
- `.env` loading happens in the CLI's runtime-resolution path, not in `serve()`.
- `list_flows` is registered as `GET /` on the mount base, so the bare `/api/flows` is a real
  endpoint the client requests; both in-repo mounts pair the catch-all with a sibling bare route
  deliberately, with a comment saying why.
- `@ai-sdk/openai` is a *dev* dependency of our `core` package, so it never reaches a consumer;
  `@flow-state-dev/devtool` is an *optional peer* of the CLI, satisfied only inside this
  monorepo. Both must be installed.
- The engine's filesystem store warns once per process that it is unsuitable for production
  unless constructed with the flag acknowledging local-only use — which is why decision 4 ships
  it qualified.
- `packages/cli/src/commands/` holds `run`, `dev`, `serve`, `chat`, `block`, `ui` and
  `benchmark`, and has never had an `init`. Decision 1 removes a planned command, not a shipped
  one, so nothing depends on it today.
- A scoped package's `bin` key creates `node_modules/.bin/<name>` in a consumer and `npx <name>`
  runs it, with no unscoped package existing — packed, installed and executed by FIX-1162's
  worker. Only a bare `npx fsdev` typed where nothing is installed needs an unscoped name.
- The repo-wide Node floor is `>=22` (`docs/contributing/RELEASING.md`), which is why §9 gates
  the wired-up project rather than narrowing any package's `engines`.

- **Spec drafted** — framed as the missing front door for Public Launch; chose to compose the
  existing CLI commands rather than generate a server entrypoint, which removed the
  unauthenticated-bind and unloaded-credential hazards outright; settled the store profile on

  and a structured manifest merge, because JSON carries no comment syntax; qualified the store as

- **After spec review (round 2)** — corrected the printed plain-Node next step to
  `fsdev serve --host 127.0.0.1`; made the credential guarantee *"will git publish this file"*
