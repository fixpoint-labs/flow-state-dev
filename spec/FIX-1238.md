# FIX-1238 — The park-exit verdict's carrier depends on step adjacency

> **Status:** spec, awaiting direction approval. Never merges to `main` (BP-037).
> **Issue:** FIX-1238 · P0 · epic FIX-980 (Honest task substrate) · project Orchestration Primitives
> **Predecessor:** FIX-1234 (PR [#1422](https://github.com/fixpoint-labs/flow-state-dev/pull/1422)), where this was raised and deliberately deferred.

---

## Part I — The Case

### 1. Problem — why it matters, why now

A task board runs work until it has nothing left to do, then reports why it stopped. One of
those reasons is special: **"a person owes us an answer."** The board stops on purpose, the
work is fine, and somebody needs to come back and reply. Every other stop reason means
something went wrong.

That "a person owes us an answer" verdict is carried from the worker that decided it to the
message that reports it by nothing more than **two steps sitting next to each other** in the
board's internal pipeline. If a future change slots a step between those two, the verdict is
dropped on the floor and the board reports **"blocked by failures"** instead. An operator
looking at that board would be told their work broke, when in fact it is politely waiting on
them. Nothing warns anyone: the code still compiles.

**How exposed are we, honestly.** Narrowly. The board's own end-to-end tests assert the
reported reason, so the ordinary version of this mistake turns a test red immediately. There
is one version they cannot catch — a step inserted on a *conditional* path, live only on a
board configuration those tests don't exercise. That one ships silently.

**Why now — and the part that argues against itself.** The ticket set its own bar: do this
"only if concurrent drains of one board inside one request become a real product scenario, or
if the drain pipeline grows steps near that seam." **Neither fired literally**, and §3 says so
in full rather than treating the go-ahead as settling it. What is true is that this is a P0
that has stood since 2026-08-23 on an epic whose whole subject is a substrate that reports
honestly, and the pipeline in question has been edited three times in the last week.

### 2. Solution in plain terms

Tell the compiler what the reporting step expects to be handed. Today the pipeline carries a
comment asking future editors to keep the two steps adjacent. We replace the comment's
load-bearing half with a check the compiler performs: the reporting step is wired up with an
explicit statement of the shape it is fed, so wiring anything else in front of it stops the
build at the exact line, with the exact reason.

Nothing about how the board behaves changes. The added code is an identity function — it hands
along precisely what it received. No new option, no new concept, no new surface for anyone
building on the framework. **One changed line and one added import**, both verified against the
real file (§7).

It is an honest **partial** guard, not a proof. It catches an inserted step that declares what
it produces, and it catches the conditional-path insert the tests miss. It does not catch a
step that declares nothing. §3 prices that.

**Philosophy** — tenet 3 (earn every addition): the change adds no mechanism, no state and no
API; it annotates wiring that already exists. Tenet 1 (coherence): the pipeline currently
states a requirement in prose that the type system was capable of holding all along, and the
gap between what a comment claims and what the code enforces is exactly the incoherence the
tenet names. **In tension with tenet 3 in the other direction** — the strictest reading of
"earn every addition" says a defect already covered by tests earns nothing, and §3 takes that
argument seriously rather than waving at it.

### 6. Decisions & rules — the sign-off surface

**Decision 1 — Build the guard now, rather than closing the ticket and re-grading the P0.**

*Rejected alternative:* close FIX-1238, drop the P0, and leave the tests as the only guard —
which is what the ticket's own stated bar implies, since neither of its preconditions fired.

*Locks in:* we accept that a stop-reason a human is meant to act on is worth a compiler-level
guarantee and not just a test, on an epic whose promise is that the substrate reports honestly.
The cost is one small change and one review cycle on a defect nobody has hit. The benefit is
that the one break the tests structurally cannot see stops being possible. If the answer is
"not worth it," the honest consequence is not "do it later" — it is that a P0 was the wrong
grade, and the ticket should close.

**Decision 2 — The verdict keeps riding the pipeline's own dataflow. It does not move to the
board's per-request slot.**

*Rejected alternative:* move it onto the request-scoped slot FIX-1244 introduced — the ticket's
second candidate shape, and the one that only became available last week.

*Locks in:* two runs of the same board can never be handed each other's answer. That guarantee
holds today because the verdict flows through the run itself, and it would be **weakened**, not
strengthened, by the move: the slot is keyed by board name within a request, so two runs of one
board inside one request share it — which is the same class of cross-run leakage FIX-1234
rejected in the first place, merely narrower (§3 carries the evidence). Choosing this also
means the board does not grow a second mechanism for a job the first one already does.

### 3. Tradeoffs & alternatives

#### 3.1 The ticket's own bar did not fire, and it was the wrong bar

Checked on `main` at `5811f4ef`, not assumed:

- **"The drain pipeline grows steps near that seam."** FIX-1244 (PR #1571, merged 09-05) touched
  `task-board/index.ts` in three commits. None of them inserted anything between the worker
  `forEach` and the completion tap — verified by reading each diff. The install/teardown taps
  around the seam predate it (FIX-610). **Did not fire.**
- **"Concurrent drains of one board inside one request."** `board.unparkAndDrain` is
  `.step(unpark).tapIf(recorded, drain)` — it runs the drain in the *answering* request, not
  alongside the parking run inside one request. FIX-1244's own concurrency test
  (`task-board-concurrent-drains.test.ts`) uses two separate `testBlock` calls, i.e. two
  requests. **Did not fire.**

So on its own terms the ticket says wait. But the bar is misattributed. Reading Cursor's
original comment on PR #1422:

> If concurrent drains of one board in one request stay a real product scenario, consider a
> follow-up that makes the carrier structural (typed connector from `forEach` output, or a
> per-invocation slot scoped narrower than the board-definition flow-state bag).

The concurrency condition gates the **carrier** question — should the verdict move to a slot.
It does not gate the **typing** question. Adjacency fragility has nothing to do with
concurrency; it depends only on whether the pipeline gets edited. And it does: three commits in
one week. The ticket copied one precondition onto both candidate shapes, and that is a
transcription error, not a judgement anyone made.

**This does not by itself justify building.** It means the ticket's "no" is not evidence, and
the decision has to be made on merit. §3.2 does that.

#### 3.2 The merit case, and the case against

The honest question is what a compiler guard buys over the tests that already exist. The POC on
this branch (`spec-poc/FIX-1238-typed-tap-connector/`, §7) answers it by experiment rather than
argument:

| Inserted between the `forEach` and the completion tap | Breaks the verdict? | Existing drain tests catch it? | Guard catches it? |
| --- | --- | --- | --- |
| a `.tap(...)` | **no** — `tap` returns the value unchanged | n/a | no error (correct: no false alarm) |
| a `.step(...)` that declares what it produces | yes | yes | **yes** |
| a `.step(...)` that declares nothing | yes | yes | **no** |
| a `.stepIf(cond, ...)` on an untested configuration | yes, on that configuration | **no** | **yes** |

**For:** row four is the whole case. It is the one break the existing tests are structurally
incapable of catching — a conditional step live only on a board configuration the park-exit
suite doesn't exercise — and the guard catches it. Rows one to three show the guard is
complementary to the tests rather than redundant with them, and row one shows it doesn't
misfire on the pipeline's actual growth mode, which is taps.

**Against, stated fairly:**

- Row three is a real hole. A handler with no declared output type slips straight through, and
  handlers like that exist in this very pipeline. The guard is partial and should not be
  described as closing the defect.
- The blast radius if the bug ever lands is one wrong word on a completion message. No data
  loss, no stuck work, nothing unrecoverable — the parked row stays parked and durable either
  way.
- Nobody has hit this. It is a defect found by review, not by a user.

**Where that lands.** The cost side is unusually small and measured, not estimated: one changed
line, one import, zero runtime change, zero public surface. The benefit is narrow but real and
lands exactly where the tests are blind. On a P0 under an epic about honest reporting, spending
one line to make a misreport impossible-at-compile-time in the case tests can't see is worth it.
That is Decision 1, and it is the recommendation — but it is genuinely close, and §3.4 states
what the other answer looks like so it can be chosen cleanly.

#### 3.3 Alternatives rejected

**Move the verdict onto the request-scoped slot (the ticket's second candidate).** FIX-1244 did
create the mechanism, and it is load-bearing — it carries the tool cache, the observation ledger
and the flow policy, on `ctx.request` under a slot keyed by board name
(`flow-policy-wiring.ts`, `boardRunStateSlot(name)`). But it is **not** the "per-invocation slot"
the ticket asks for. Its key is the board's *definition* name scoped to the request, so two runs
of one board inside one request write and delete the same slot — one run's teardown would clear
the other's verdict. That is precisely the failure FIX-1234 rejected the flow-state bag for,
narrowed from per-process to per-request but not eliminated. Today's dataflow carry has no such
failure: it is per-invocation by construction. Adopting the slot would **trade a typed-adjacency
problem for a cross-run correctness problem**, and add a second mechanism for a job the first
one does. Rejected on evidence, not on restraint. (Decision 2.)

**Validate at runtime and throw on a mis-wire.** Loud, but it converts a composition mistake
into a board failure in production, and D5 is explicit that "loud" and "contained" are not
automatically compatible — FIX-951's containment bar is non-negotiable. The compile-time guard
gets the same signal strictly earlier and cannot reach a user. Rejected.

**Tighten `boardMetaCompleted`'s `inputSchema` from `z.unknown()`.** The block is exported and
constructed directly by callers outside the composed pipeline; the `z.unknown()` is deliberate
and documented as such. Narrowing it would reject those callers' inputs at runtime (BP-030) and
break a published boundary (BP-004) to fix an internal wiring concern. The connector reaches the
same place without touching the block at all — it lives at the wiring site, so external callers
are untouched by construction. **Explicitly out of scope, and Part II forbids it.**

**Fix the real root cause in `core`.** The deeper reason the guard is only partial: a `forEach`
over a *sequencer* factory erases the element type to `any[]`, because `SequencerDefinition`
extends `BlockDefinition<any, any>` (POC line 41; the same `forEach` over a plain handler
preserves the type, line 45). Fixing that in core's generics is the correct root-cause repair
and is far outside this ticket — it would change inference for every sequencer in the repo.
Recorded as a follow-up in §12, not attempted here.

**Do nothing; re-grade and close.** See §3.4.

#### 3.4 What "don't build it" looks like, if that is the call

A legitimate outcome, and cheap to take: close FIX-1238, drop the P0 to no-priority or close it
outright, and record on FIX-980 that the park-exit verdict's carrier is guarded by drain-level
tests with a known conditional-path blind spot. The comment at the wiring site already says the
right thing and would stay. Nothing regresses. What we would be accepting is that a board can
one day tell an operator their work failed when it is actually waiting for them, in a
configuration no test covers — and that we found that acceptable knowingly, which is a defensible
position and a materially better outcome than a P0 sitting open indefinitely while the body
argues for deferral.

### 4. Focus practices

- **BP-004 / BP-030 — the public boundary is not the place to fix internal wiring.**
  `boardMetaCompleted`'s permissive `inputSchema` stays exactly as it is.
- **Tenet 3 — earn every addition.** The whole change is an annotation on existing wiring. If
  implementation finds itself adding a helper, a type, or a second mechanism, that is a signal
  the direction was wrong, not a signal to build more.
- **D5 — containment is a non-negotiable regression bar.** The change must be runtime-inert.
  `task-board-drain-containment.test.ts` is the bar and must stay green untouched.
- **D4 — a guarantee is observable at a persisted surface.** This change deliberately does *not*
  add observability. It removes a way for the persisted `terminationReason` to become wrong; it
  does not add a trace item, and a `transient` breadcrumb would not count if it did.
- **BP-003 — verify, don't read.** Every claim in §3 was executed (§7 evidence paths). The
  "before" claim especially: the silent break was reproduced, not assumed.

### 5. What using it looks like

**Nothing about how anyone writes code against the framework changes** — no public API, no
config, no new option. Per the template, that is the one case where usage examples are skipped,
and this is it. The only thing that changes shape is one internal wiring line:

```ts
// before — the requirement lives in a comment
.tap(boardMetaCompleted)

// after — the requirement is what the compiler checks
.tap((exits: readonly CheckBoardOutput[]) => exits, boardMetaCompleted)
```

What a future editor sees when they get it wrong, on the real file, verified:

```
packages/orchestration/src/task-board/index.ts(1192,10): error TS2769: No overload matches this call.
  Types of parameters 'exits' and 'input' are incompatible.
```

Today, that same edit compiles clean and the board silently starts reporting review exits as
failures.

## Part II — The Build Plan

### 7. Technical design

**The one site.** `packages/orchestration/src/task-board/index.ts`, the `.tap(boardMetaCompleted)`
immediately after the worker `forEach` (~line 1190 on `5811f4ef`).

Two edits, both verified to compile on the real file:

1. Add `type CheckBoardOutput` to the existing `import { … } from "./schemas"` block (~line 122).
   The symbol is *re-exported* further down the file but is not in lexical scope — omitting this
   is a `TS2304`, which is how the first attempt failed.
2. Replace `.tap(boardMetaCompleted)` with
   `.tap((exits: readonly CheckBoardOutput[]) => exits, boardMetaCompleted)`.

**Why this is runtime-inert.** `tap(connector, block)` dispatches the child through
`runChild(ctx, { block, connector }, …)` and returns `{ value }` — the sequencer's own output
and chain pointer are untouched (`core/src/blocks/sequencer.ts`, the `tap` implementation). The
connector is identity, so the value `boardMetaCompleted` receives is byte-for-byte what it
receives today.

**Explicitly do not:**

- touch `boardMetaCompleted`'s `inputSchema: z.unknown()`, or `excusedParkedByPool`'s defensive
  shape checks in `blocks/board-meta.ts` — both are deliberate, documented, and load-bearing for
  external callers;
- move the verdict onto the request slot in `flow-policy-wiring.ts` (Decision 2);
- rewrite the comment at the wiring site wholesale. Its first half (why the completion item
  reads the pool's exits at all) is still true and still useful. Only its "Known fragility"
  paragraph is now stale, and it should be **replaced** with a short note saying the connector is
  what holds the requirement, plus the one residual hole from §3.2 row three — a reader who is
  told "the compiler has this" and then hits row three is worse off than before.

**POC on this branch — `spec-poc/FIX-1238-typed-tap-connector/`.** Throwaway; never merges.
Run it with:

```bash
npx tsc --noEmit -p spec-poc/FIX-1238-typed-tap-connector/tsconfig.json
```

Expect exactly five errors, on lines 41, 45, 53, 63, 78 — two of them deliberate type-printers,
three of them the finding. **What it settled**, all of it load-bearing for §3 and §6:

- the guard catches a declared-output insert and a `stepIf` insert; it does **not** catch a
  schema-less insert, and it does **not** misfire on an inserted `.tap`;
- `forEach` over a sequencer factory erases the element type to `any[]`, which is why the guard
  is partial (and why a type-level assertion on the element shape is not available today);
- on the real `index.ts`: with the connector the mis-wire is `TS2769`; without it, the identical
  mis-wire **compiles clean**. The "before" half of §1 is measured, not asserted. `index.ts` on
  this branch is pristine — the experiment was reverted.

### 8. Implementation sequence

1. **Red first.** On a scratch commit, insert a `.step(checkBoard)` above the completion tap and
   confirm `npx tsc --noEmit -p packages/orchestration/tsconfig.json` is **clean**. That pins the
   defect. Revert.
2. Apply the import + connector. Typecheck → clean.
3. Re-apply the inserted step → `TS2769` at the tap. Revert the step, keep the connector.
4. Add the type-level regression test (§10) and confirm it is covered by a check that actually
   runs (see the warning there).
5. Update the wiring comment per §7.
6. Full verification (§10).

### 9. Edge cases & error handling

- **External callers of `boardMetaCompleted`** — unaffected by construction; the connector is at
  the wiring site, not on the block. Verified by the block's schema being untouched.
- **The `.rescue` path.** The drain's `.rescue([{ block: teardownFlowState }])` is unchanged; the
  connector sits on a success-path tap and never runs on the error path.
- **`unparkAndDrain`** composes the same `drain` object, so it inherits the guard with no
  separate wiring.
- **Row three (schema-less insert)** remains possible. This is a known, documented residual, not
  an oversight — it must be named in the wiring comment (§7) and in §12.
- **No persisted or in-flight shape changes**, so BP-030's dual-read obligations do not arise.

### 10. Testing strategy

**Behaviours to pin:**

1. The drain still reports `parked-for-review` on a park exit, and `blocked-by-failures` on the
   mixed state — i.e. the connector changed nothing. Existing:
   `packages/orchestration/test/task-board/task-board-park-exit-drain.test.ts` and
   `-report.test.ts`, unmodified.
2. Containment is unregressed (**D5**):
   `packages/integration-tests/src/scenarios/task-board-drain-containment.test.ts`, unmodified.
3. Cross-run isolation of the verdict is unregressed:
   `packages/orchestration/test/task-board/task-board-concurrent-drains.test.ts` and
   `task-board-unpark-and-drain.test.ts`, unmodified.
4. **New — the guard has teeth.** A type-level test constructing a miniature drain and asserting
   with `@ts-expect-error` that a step inserted before a connector-guarded completion tap fails
   to compile. Without this, someone can later "simplify" the connector to `(exits: any) => exits`
   and silently delete the guard while every runtime test stays green.

> **Warning for the implementer — read before placing test 4.** Put it under `src/`, following
> `packages/orchestration/src/tasks/collection/tests/task-caps.type-test.ts`. **Do not** put it
> beside `packages/orchestration/test/types.type-test.ts`: that file's header claims "vitest's
> typecheck mode covers them," and it does not — `packages/orchestration/vitest.config.ts` sets
> no `typecheck` option and `scripts/typecheck.mjs` runs `tsc -p tsconfig.json`, whose `include`
> is `src/**/*` only. A type test placed there is checked by nothing. Verify placement by
> deliberately breaking the new test and confirming `pnpm --filter @flow-state-dev/orchestration
> typecheck` goes red. (The stale claim in the existing file is pre-existing and out of scope —
> §12.)

**Evidence path and pass criteria:**

| Check | Command | Pass |
| --- | --- | --- |
| Guard compiles | `pnpm --filter @flow-state-dev/orchestration typecheck` | clean |
| Guard has teeth | break test 4 deliberately, re-run the above | goes **red** |
| Runtime inert | `pnpm --filter @flow-state-dev/orchestration test` | 1318/1318 or better, no test file edited |
| D5 containment | the containment scenario in `@flow-state-dev/integration-tests` | green, unmodified |

### 12. Dependencies, open questions & follow-ups

**Dependencies:** none. FIX-1244 is merged and this does not build on it.

**Follow-ups (not in scope, do not fix here):**

1. **`forEach` over a sequencer factory erases the element type to `any[]`** —
   `SequencerDefinition extends BlockDefinition<any, any>` in
   `packages/core/src/blocks/sequencer-methods.ts`. This is the root cause of the guard's
   partiality and it affects every `forEach`-over-sequencer in the repo, not just this one.
   Worth its own ticket; a candidate for `improve-codebase-architecture`.
2. **`packages/orchestration/test/types.type-test.ts` is typechecked by nothing.** Its header
   asserts vitest typecheck mode covers it; no `typecheck` option is configured, and the package
   `typecheck` script only sees `src/**`. Pre-existing, unrelated to this change, flagged rather
   than fixed (CLAUDE.md §3).
3. **The residual hole** — a schema-less inserted step still breaks the carry silently. Closing
   it depends on follow-up 1. Documented at the wiring site, not worked around.
