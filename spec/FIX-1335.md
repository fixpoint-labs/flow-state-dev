# FIX-1335: Convention loader — scan `teams/<id>/workers/<name>/` into the workforce registries — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

Someone building an app with several collaborating AI workers — an engineering manager, an
API designer, a copy editor — has to wire each one in by hand, in code, one at a time. There
is no place to *put* a worker. Every team that has tried has invented its own folder layout
and its own loading code, and none of them agree.

The stakes are the objective this epic serves: nobody has built a real multi-seat
application on FSD yet, and the first thing everyone hits is that the framework has no
opinion about where a worker lives. The workaround is real but bad — you write the wiring
yourself, and it works, so nothing forces the question. What it costs is that no two apps
look alike, no worker can be moved between them, and the layout we eventually want has
no head start.

**Why now:** the file shape was locked this week (the Workforce atlas, merged 2026-09-08).
The shape is decided; nothing reads it.

### 2. Solution in plain terms

Put workers in folders. One folder per worker, grouped under the team it belongs to. Each
folder holds one Markdown file that says who the worker is: a few settings at the top
(which model, which tools) and the worker's instructions as the body. Point the app at the
root of that tree at startup and it comes back with every worker, ready to hand to the
registry the framework already has.

Nothing new gets invented to hold them. The framework already has an agent registry, and
it already reads exactly this kind of folder tree for *skills* — same file format, same
error handling, same "one bad folder doesn't break the rest" behaviour. This is that
reader, pointed at workers.

**Philosophy** — tenet 2 (composition over features): the loader adds no runtime concept,
it fills a registry that already exists. Tenet 3 (earn every addition): one new function,
and it copies an established one rather than inventing a second convention for the same
job. Tenet 5 (one convergence point): a worker's identity is minted in exactly one place,
so the registry key and every future reference to it can never disagree.

### 6. Decisions & rules — the sign-off surface

1. **A worker is a folder with a `WORKER.md` in it: settings at the top, the worker's
   instructions as the body.**
   *Rejected:* a TypeScript file per worker that the loader imports. It reads as tidier and
   it is strictly worse — importing code at startup is the hand-wiring we are replacing,
   just moved to a different line, and it puts every worker behind a build step.
   *Locks in:* the worker file is a document, not code, so a non-engineer can write and
   edit one — which is the whole reason to have a convention. The cost is that a worker
   can only be described by things that can be named in text (a model name, a tool name);
   anything that needs real code stays in the app. **This also corrects the issue as
   written:** there is no "persona registry" in the framework to populate. A worker's
   instructions are a field on the worker, and the file body *is* that field.

2. **A worker's identity is its team and its name together — `engineering/lead`, not
   `lead`.**
   *Rejected:* bare names, with a startup error if two teams collide.
   *Locks in:* every team can have a "lead" and a "reviewer" without coordinating names
   with every other team. The bill for the alternative arrives late and lands on the wrong
   person: adding a second team would break the *first* team's startup, and the fix would
   be renaming workers that were fine. The cost is that the identity has a `/` in it and
   is now the string anything referring to a worker has to use — changing that shape later
   would break every reference in every app that adopted it.

3. **Only worker folders are loaded. The other folders in the locked layout are skipped,
   and the ones that could be mistaken for workers say so out loud.**
   *Rejected:* loading team-level knowledge (resources, skills, tools) and shared
   org-level workers in the same pass.
   *Locks in:* an author who lays out the full tree from the atlas gets part of it read and
   part of it ignored — so the loader reports the shared-workers folder by name instead of
   passing over it silently, and someone reading the report knows which half is live. The
   rest of the tree is a later issue's to claim (team addressability, FIX-1310), and
   claiming it here would ship a partial version of it under this issue's name.

**Non-goals** — binding a worker to a running flow (that is the seat factory, FIX-1325);
making the framework honest about capabilities it cannot supply (FIX-1327); team
addressability and board scoping (FIX-1310); registering a worker at runtime, after
startup (ruled out at epic level, theme 4).

**Size:** Medium — 6 production files · 11 test behaviours · 2 doc surfaces · 1 PR.

### 3. Tradeoffs & alternatives

**Alternative: the loader builds and returns the registry itself.** One call, nothing for
the author to wire. Rejected because it makes the loader the only way in — the registry is
also fed by hand-written definitions today, and a loader that owns construction quietly
turns the TypeScript path into a second-class one. Returning the workers and letting the
author pass them to the registry keeps both paths identical, which is the point of theme 1
("files and hand-written definitions produce the same entries"). It also matches how the
skills reader already works, so an author who has wired skills already knows this shape.

**The simpler approach: no file format at all — a folder per worker whose whole contents
are the instructions.** Genuinely tempting; it removes the settings block and everything
that can go wrong parsing it. Insufficient because a worker that cannot say which model it
runs on or which tools it may call is not a worker, it is a prompt — and the app would be
back to declaring those in code, which is the wiring we are removing.

**Where the complexity is:** not the walk. It is what the loader does with a settings key
it does not recognise. Keys it drops today are keys the next issue in this epic (the seat
factory) needs to add tomorrow, so dropping them silently would make this format
un-extendable and force a second format beside it.

### 4. Focus practices (1–5)

1. **BP-030 (tolerate the shape you don't own yet)** — unrecognised settings keys are
   preserved, not dropped. This is the practice the whole change lives on: it is what lets
   the seat factory add its keys later without a format change, and it is why this issue
   does not have to wait for that contract to settle.
2. **One convergence point for a worker's identity (tenet 5)** — team and name are joined
   in exactly one helper. Two places that build the same id is how the registry key and a
   future reference to it drift apart with nothing failing.
3. **No duplicate parser (CLAUDE.md → Coding Conventions)** — the settings block is the
   same format the skills reader already parses. Share that parser; do not copy it into a
   second package.
4. **Report what you skipped (epic theme 3)** — a folder that looks like a worker and is
   not loaded is named in the result. Silence is the failure mode a convention cannot
   recover from.

### 5. What using it looks like (1–5 examples)

**The tree an author writes** *(what this spec proposes; nothing reads this layout today)*:

```
workforce/
  teams/
    engineering/
      workers/
        lead/WORKER.md
        api-designer/WORKER.md
    marketing/
      workers/
        lead/WORKER.md
```

**One worker file:**

```md
---
description: Holds the engineering board and breaks work into tasks.
model: openai/gpt-5.4-mini
allowed-tools: [search, fetch]
---

You are the engineering lead. You do not write code yourself — you break
the request into tasks, assign them, and report what came back.
```

**Wiring it at startup** *(the whole change at the call site)*:

```ts
import { readWorkforceDirectory } from "@flow-state-dev/workforce/loader";
import { createAgentRegistry } from "@flow-state-dev/workforce";

const { agents, errors } = await readWorkforceDirectory("./workforce");
for (const { name, error } of errors) console.warn(`[workforce] ${name}:`, error.message);

export const agentRegistry = createAgentRegistry(agents);
// agents[0].name === "engineering/lead"
```

**Referring to a worker from a skill** *(before / after)*:

```
before  agent-ref: eng-manager        — the name a hand-written defineAgent chose
after   agent-ref: engineering/lead   — the name its folder gives it
```

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

The loader is a Node-only directory walk that produces plain `Agent` values. It talks to
nothing at runtime: it reads files, validates them, and returns. Everything downstream —
the registry, materialization, the block — is untouched code on `main`.

```mermaid
flowchart LR
  T[teams/&lt;id&gt;/workers/&lt;name&gt;/WORKER.md] --> W[readWorkforceDirectory<br/>workforce/loader]
  F[shared frontmatter parser<br/>orchestration/skills] --> W
  W -->|Agent[] + errors| A[createAgentRegistry<br/>unchanged]
  A --> M[materializeAgent<br/>unchanged]
```

- **`@flow-state-dev/orchestration`** — the SKILL.md frontmatter splitter and its
  YAML-subset parser are internal today. Promote them to a named export so both readers
  share one parser. `parseSkillMd` keeps its current behaviour and its tests.
- **`@flow-state-dev/workforce`** — gains a **`./loader` subpath export** carrying the walk
  and the `WORKER.md` parser. The root export stays free of `node:fs`, so a consumer that
  only wants `defineAgent` is not pulled onto Node. (The skills reader ships from
  orchestration's *root* export; that is the pattern we are deliberately not copying —
  core/engine split node-only code at a boundary and that is the more established rule.
  CLAUDE.md → §6, surface the conflict rather than average it.)
- **What the loader exposes:** one async function taking a root path, returning the loaded
  workers and a per-folder error list. No registry construction, no `loadWorkforce()`.
- **Untouched:** `createAgentRegistry`, `materializeAgent`, `defineAgent`, `definePersona`,
  the core `Agent` type, and every existing caller.

**Identity.** `teams/<teamId>/workers/<workerName>/` yields `Agent.name = "<teamId>/<workerName>"`,
minted by one internal helper. Both segments are validated with the same name rules skills
use. Duplicate identities cannot occur on one filesystem; across two roots merged by a
caller, `createAgentRegistry`'s existing duplicate-name error is the guard — no new
invariant is introduced.

**The `WORKER.md` contract.** Frontmatter maps onto fields that already exist on `Agent`:
`description`, `model`, `allowed-tools`, `uses-capabilities`, `visibility`. The body
becomes the worker's persona in its inline form. **Unrecognised keys are preserved, not
dropped** (decision 1's forward door; see §12). String keys under `allowed-tools` and
`uses-capabilities` are recorded verbatim — the loader resolves nothing against a catalog,
because that resolution happens at materialization and its current dishonesty is FIX-1327's
to fix, not this issue's to work around.

*No solution sketch.* The change extends `readSkillsDirectory` closely enough that pointing
at it (`packages/orchestration/src/skills/read-directory.ts`) says more than re-drawing it.

### 8. Implementation sequence

1. **Extract the frontmatter parser** in orchestration — the `---` splitter and the
   YAML-subset mapping parser out of `skill-md.ts` into their own module, exported from the
   skills index. Pure move. *Test:* the existing `skill-md` suite stays green unchanged.
   *Depends on:* nothing.
2. **`WORKER.md` parse** in workforce: frontmatter → the `Agent` fields decision 1 names,
   body → persona, unknown keys preserved. *Test:* each supported key; a missing
   `description`; unknown keys survive; an empty body. *Depends on:* 1.
3. **Identity minting** — one helper joining team and worker name, with the shared name
   validation on both segments. *Test:* the joined form, and rejection of an illegal
   segment. *Depends on:* nothing.
4. **The walk** — `teams/*/workers/*/`, symlinks rejected as the skills reader rejects
   them, per-folder failures collected rather than thrown. *Test:* a two-team tree; one
   malformed worker does not lose the others; a symlinked folder is refused.
   *Depends on:* 2, 3.
5. **Report the skipped** per decision 3 — an org-level `workers/` and a worker folder with
   no `WORKER.md` land in `errors` by name; a team's `resources/`, `skills/`, `tools/`
   siblings are passed over quietly (they are the locked layout, not a mistake).
   *Test:* both reported cases, and that the atlas siblings produce no noise.
   *Depends on:* 4.
6. **Ship the subpath** — `./loader` in `package.json` exports and `publishConfig`, and the
   goal fixture tree. *Test:* the §10 goal. *Depends on:* 5.

*No removals.* Nothing on `main` does this job today, so there is nothing this subtracts —
the subtraction in this change is the parser that does **not** get written twice (step 1).

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| `teams/` absent under the root | Empty result, no error — an app may have no file-defined workers |
| Root path unreadable | Throw. A configured root that does not exist is a wiring mistake, not a per-worker one (matches the skills reader) |
| Worker folder with no `WORKER.md` | Collected in `errors` by name; the rest still load |
| `WORKER.md` with no frontmatter, or no `description` | Collected in `errors`; the file is unusable, not partially usable |
| Team or worker segment that breaks the name rules | Collected in `errors` — the identity would be unaddressable |
| Symlinked team or worker folder | Refused and reported, exactly as the skills reader refuses one |
| Unrecognised frontmatter key | Preserved, not an error — see §12 |
| `allowed-tools` naming a tool no catalog has | Not this loader's call. It records the key; the drop happens at materialization (FIX-1327) |
| A file, not a folder, under `workers/` | Skipped quietly |

**On the `/` in an identity — checked, not assumed.** A skill's `agents:` map restricts the
*assignee key* to `/^[a-zA-Z0-9][a-zA-Z0-9_-]*$/`, which excludes `/`. It does **not**
restrict the `agent-ref` *value*, which is the registry name this loader mints
(`skill-md.ts` applies `isValidAgentKey` to the key only, in `parseAgentsField`). So
`analyzer: { agent-ref: engineering/lead }` is legal today with no change to that parser.

**Taxonomy:** every per-worker problem is non-fatal and collected, so one bad folder never
costs an app its other workers. The single fatal path is an unreadable root.

### 10. Testing strategy

**Goal:** a `teams/` tree on disk, loaded with no hand-written agent definition anywhere in
the path, produces a registry whose worker materializes and answers — with the answer
carrying a held-out marker that only the folder's own `WORKER.md` body could have supplied.
That last clause is what keeps it from passing on a default persona.
`goals/workforce-conventions/files-alone-produce-a-working-worker/`, real model.

**CI specs** (behaviours, not test names):

- one behaviour per §6 decision, in observable terms — a folder produces a worker; two
  teams' same-named workers both load and are distinct; a shared `workers/` at the root is
  named in the report rather than passed over
- **the second path (BP-035):** every error case in §9 exercised alongside a *good* worker
  in the same tree, proving the good one still loads. A suite that tests failures on their
  own proves nothing about isolation
- **what must not change:** `parseSkillMd` behaves identically after step 1 — the existing
  skills suite runs unmodified
- **the one easy to state wrongly:** an unrecognised frontmatter key must be *retrievable
  after the round trip*, not merely "does not throw". A parser that silently discards it
  also does not throw, and that is the exact failure this decision exists to prevent

**Discipline:** `tdd`. The seam is the loader function itself — it takes a path and returns
data, so every behaviour above is a vitest spec over a fixture tree with no flow, no engine,
and no model.

### 12. Dependencies, open questions & follow-ups

**Dependencies:** none blocking. The epic-spec sequences this behind FIX-1325 ("the loader
has to land against a settled factory contract"), and **the preserved-unknown-keys rule in
§7 dissolves that**: the loader commits to nothing about flow instances, and the factory's
future keys (`flow-kind`, instance config) are additive to a format that already carries
what it does not understand. This issue can land first or in parallel. Raised on the epic
PR rather than decided here.

**Open questions:** none.

**Follow-ups (flagged, not built):**

- **Deepening:** `readSkillsDirectory` ships from orchestration's *root* export while
  importing `node:fs`, which makes the whole package Node-only for anyone importing
  `createSkillsLibrary`. This spec does not copy that; moving the skills reader behind a
  subpath is a separate, breaking-ish change. Follow up via
  `improve-codebase-architecture`.
- **Later consumers:** team-level knowledge folders and org-level shared workers
  (FIX-1310); binding a loaded worker to a flow instance (FIX-1325).

## Spec evolution

- **Spec drafted** — framed as "workers have nowhere to live"; chose a document-per-worker
  folder read by a copy of the established skills-directory reader over a code-per-worker
  import; team-qualified identities so a second team cannot break the first; scope held to
  worker folders with everything else named-and-skipped. Corrected the issue's premise that
  a persona registry exists to populate — the file body is the persona.
