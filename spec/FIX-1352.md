# FIX-1352: W3 — Channels file convention (either-source; declaration-only) — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

An app can describe its workers in files today. Each worker is a folder with a `WORKER.md`
in it, and the app reads that folder at startup to find out who it employs. Nothing else
about a team can be described that way, and the three remaining pieces are in three different
states. A channel has **no declaration surface at all** today, in code or in files. Resources are
declared in code, with `defineResource`. Skills already have a file convention that ships —
`SKILL.md` read by `readSkillsDirectory` — which is why FIX-1356 ratifies one rather than
building one.

This epic adds file conventions for three of those things: channels, resources, and skills.
Channels is first out of the gate, and that is the real stake here. Whatever the channels
convention does becomes the default the other two copy — where the folder sits, what the
file's header may say, what an error looks like. Get it wrong and we pay for it twice more
inside this epic, and then every app author pays for it once per convention they learn.

**Why now** — the other two conventions are queued behind this one and will be written by
different agents in different sessions. Absent a settled shape they will each invent one,
and the epic's back half turns into reconciliation work. Channels is also the *least* useful
of the three to ship alone: what makes a channel do anything is the flow kind it runs — the
default **ChannelFlow**, which is FIX-1311's floor. Decision 1 is where you buy that trade
knowingly.

### 2. Solution in plain terms

Keep the shape that already shipped and extend it. A channel becomes a folder under its team
with a `CHANNEL.md` inside it, exactly as a worker is a folder with a `WORKER.md`. Reading the
tree reports bad folders instead of crashing, so one mistyped channel never costs an app its
other channels. One header key is required (`description`), one is refused by name, and
everything else an author writes is carried through untouched for whoever claims it later.

The FIX-1341 lock says a channel may be declared in a file **or** in code, and that a system
channel must be undeletable. This issue **settles both rules and builds only the half that has
a caller today.** The file reader ships, including its refusal of a `system:` key an author
tries to write. The code-declared source has no caller yet — nothing in the repo declares a
channel in code — so the machinery that merges two sources and stamps provenance lands with the
issue that introduces the first one. Decisions 2 and 3 lock the contract now so that when it
does, it cannot arrive as a precedence rule.

**What a channel is.** Not a roster name over a shared message board. A channel is a
**replaceable L2 flow kind** — batteries-included default **ChannelFlow** — and each declared
channel is **one instance** of that kind, with a session carrying its transcript. Posting is a
dispatch into that instance, not a write into a collection.

A `flow:` key on `CHANNEL.md` names the kind, exactly as it does on `WORKER.md`, and by the
same division of labour: the reader carries `flow:` verbatim, the minter reads it.
`hireWorkforce` already works this way for workers — `manifest.declared.flow` resolved against
the app's `kinds` map, one flow instance minted per record and registered under that record's
id (§10). A channel is the same mechanism, one altitude over. The kind itself, its default,
and the clean transcript projection it owes from day one are **FIX-1311's ChannelFlow floor**,
which this issue sequences behind. Nothing in this issue mints, dispatches, or projects
anything.

**Philosophy** — tenet 2 (composition over features): a channel is a convention over an L2
flow kind and the L1 session that kind runs in — not a new Channel L1 package type beside them.
Tenet 3 (earn every addition): the public surface grows by one reader, and the directory
walk is shared with the worker reader rather than copied. Tenet 5 (one convergence point for
an invariant): the `system:` refusal sits at the reader's door now, and the second source,
when it arrives, must come through a door that refuses the same way.

**In tension with tenet 3, and worth naming:** an addition that nothing consumes has not
obviously earned its place. Decision 1.

### 6. Decisions & rules — the sign-off surface

1. **W3 ships the channel *declaration* — the files that say which ChannelFlow instances an
   app has. It does not ship what mints or runs them.** A `CHANNEL.md` describes an instance to
   mint: its identity, the kind it runs, and whatever settings that kind reads. W3 ships that
   file convention and its reader. Minting the instance, dispatching a post into it, and
   projecting its transcript belong to the ChannelFlow kind, and the kind is FIX-1311's floor.
   *Rejected:* building the channel runtime here. It cannot be built — there is no ChannelFlow
   kind yet to mint an instance of, and no channel surface of any spelling exists in any
   package (§10).
   *Out of scope, and not deferred with a plan:* the Collab roster — seeding, a dynamic lane,
   membership helpers, and enforcing "undeletable". None of it is in the W3 floor, and this
   spec names no phase for it.
   *Locks in:* we accept a convention that does nothing until the kind lands. If
   the lab Proof (FIX-1355) does not end up declaring channels in files, we will have shipped
   layout consistency and nothing else — recoverable, since it is one small reader we would
   delete, but it would mean this issue ran a cycle early and should have been sequenced
   after the lab.

2. **The same channel id declared in a file and in code is refused at startup, naming both
   sources. There is no precedence rule.** The rule is settled here; the code path is built
   by the issue that introduces the first code-declared channel (§12), because today it would
   guard a second source with no caller.
   *Rejected:* code-wins (file is a default) and file-wins (code is an override). Either
   means an app can be running a channel nobody can point to the declaration of, which is the
   failure mode this project has spent an epic removing.
   *Locks in:* when the second source arrives, an app that declares a channel in both places
   stops booting instead of quietly running one of them. It also locks the *direction* of
   any future change: adding an explicit opt-in override later is additive and breaks
   nobody, whereas shipping a precedence rule and tightening it later breaks every app that
   came to depend on it. We are choosing the reversible order.

3. **A channel's `system` status is derived from the declaration path, and a `CHANNEL.md` that
   writes `system:` is refused by name.** The refusal ships in this issue; the derivation —
   stamping the status onto a merged roster — lands with the reconciler (§12).
   *Rejected:* `system: true` as ordinary frontmatter an author writes.
   *Locks in:* when the delete verb exists, there is exactly one place to enforce
   "undeletable" and exactly one way a channel can have become undeletable. No author, and no
   helper that writes a file, can mint an undeletable channel by typing a key.

**Non-goals** — the reconciler and the provenance stamp (deferred, §12); minting a channel's
flow instance, dispatching a post into it, or projecting its transcript; seeding channels into
anything; a delete verb or its enforcement; the Collab roster, its dynamic lane and its
membership helpers; a `teams/<id>/team.md` as a third declaration source; and Channel /
MessageBoard / TeamFlow **L1 package types**, per the epic's invent-kill. That kill is about
package peers: ChannelFlow is **L2 opinion**, the same altitude as the agent kind, not a peer
of Flow or Session. A smart resource with `reactTo` fan-out (#1627) stays valid for
non-conversation shared state and as framework teaching — it is not the author-facing channel
API, and it is not what a `CHANNEL.md` declares.

**Size:** Small — 5 production files · 2 test behaviours · 1 doc surface · 1 PR.

### 3. Tradeoffs & alternatives

**The simpler approach, considered and rejected.** Copy `read-workforce-directory.ts`,
replace "worker" with "channel", ship it. It is faster today and it is what will happen twice
more if this spec does not say otherwise — four near-identical directory walks, each
free to drift in how it refuses a symlink or reports an unreadable folder.

Rejected because the worker reader and the channel reader need the *same* walk, and extracting
it on the second caller is ordinary de-duplication. Waiting until the fourth is how a
convention drifts.

A third reader, `readSkillsDirectory` in `orchestration`, shows the same *pattern* recurring
— a folder per thing, a fixed manifest name, a required `description`, symlinks refused,
failures collected rather than thrown. **It is not a third caller for this extraction, and
should not be cited as one:** it walks a flat tree rather than the `teams/<id>/<slot>/`
nesting, keys its errors by name rather than by path, and collapses every non-`ENOENT`
failure into a silent `continue` instead of keeping *unreadable* distinct from *absent* —
which is precisely the distinction the worker reader is built around. It is evidence the
convention shape is real. It is not shared code, and this issue does not touch it.

**The alternative on scope.** Ship nothing in W3 and fold the channel file convention into the
issue that builds the ChannelFlow kind, so a declaration and the thing that reads it land
together. Coherent, and its argument is Decision 1's risk read back. It
loses because the shape question is real and immediate — three more conventions are queued
behind this one now, not when the kind lands — and because the either-source rule is far
cheaper to settle before anything merges two sources than to retrofit into what already does.

### 5. What using it looks like

An app declares two channels in files and reads them at startup.

```
workforce/teams/engineering/channels/standup/CHANNEL.md
workforce/teams/engineering/channels/incidents/CHANNEL.md
```

```md
---
description: Where the engineering team posts daily status.
flow: channel
members: [engineering.lead, engineering.analyst]
---

Post what you finished, what you're on, and what's blocking you.
```

```ts
import { readChannelsDirectory } from "@flow-state-dev/workforce/loader";

const { channels, errors } = await readChannelsDirectory("./workforce");
if (errors.length) throw new Error(/* same fail-on-errors shape as workers */);
```

```ts
channels; // ChannelManifest[], in walk order
// [ { id: "engineering.standup",   declared: { description: "…", flow: "channel", members: [...] }, body: "Post what…" },
//   { id: "engineering.incidents", declared: { description: "…" },                                 body: "…" } ]
```

A file that tries to declare its own status is refused when the tree is read:

```
errors;
// [{ path: "teams/engineering/channels/standup",
//    error: Error('CHANNEL.md in "standup/" declares `system:`, which is not a setting a
//                  channel declares. A channel is a system channel because it was declared, not
//                  because it said so.') }]
```

Reading the tree mints nothing and merges nothing. `flow: channel` is carried verbatim like
any other key — the reader does not resolve it. As with workers, turning a record into a
running instance is a separate call: `hireWorkforce` for a worker, and for a channel the call
that mints its ChannelFlow instance, which is not in this issue.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

**Where the tree puts a channel.** `teams/<teamId>/channels/<channelName>/CHANNEL.md` — the `channels`
slot sits beside `workers` under the same team folder, and a channel is a folder holding a
fixed-name Markdown file, as a worker and a skill are. The atlas (`docs/atlas/workforce.html`
§06) is canonical for this tree and already draws `resources/` and `skills/` as siblings of
`workers/`; `channels/` joins them at that level.

Folder-per-channel rather than `channels/<name>.md` is the one place this spec sets a precedent
rather than following one. Both existing readers are folder-per-thing with a fixed uppercase
manifest inside, and a channel folder can later hold a sibling file without a second convention
being invented. The cost is one directory level for a folder that will often hold one file;
that cost is real, and consistency across four conventions is worth more than removing it
from one.

**Identity.** `<teamId>.<channelName>`, minted from the two folder names using the *existing*
segment validator, not a restatement of its rules. One honest difference from workers: a
worker id must avoid `/` because it becomes a route segment, and a channel id has no such
proven constraint today — it is adopted for consistency and because a channel id is expected to
become its flow instance id and session key, as a worker id already is. Do not claim the
routing justification for channels.

**The record.** One type, mirroring `WorkerManifest` exactly and deliberately, so an author
and a consumer who know one know the other:

```
ChannelManifest { id, declared, body }
```

It lives beside `WorkerManifest`, node-free. A channel's `flow:` sits inside `declared` like
every other key: the reader neither validates it nor resolves it against a kinds map, exactly
as the worker loader leaves `flow:` to `hireWorkforce`. There is no second record type in this
issue — the reconciler's output shape is deferred along with the reconciler (§12).

**One export.** The package draws a hard line: `./loader` touches `node:fs`, the root stays
isomorphic. Channels adds to the loader side only.

- `readChannelsDirectory(root)` → `{ channels, errors }`, on the `./loader` subpath. Walks the
  tree, mints nothing, decides nothing. Same error contract as the worker reader:
  `errors[]` keyed by a slash-separated path relative to the root, structural folders
  reported under their own path when they cannot be listed, throws only when `root` itself
  is unreadable.

**The shared walk.** Extract what the worker reader and the channel reader both need into one
internal module under `src/loader/` — not a new public export. What moves: `classify` (lstat
without following symlinks, keeping `absent` and `unreadable` distinct),
`openStructuralDirectory`, the symlink and unreadable error wordings, `IGNORED_ENTRIES`, and
the segment validator. What does not move: anything that knows what a worker or a channel is.
Each slot's reader supplies its slot folder name, manifest filename, required key, and
refused key.

Keep it an extraction, not a framework. Do not build a generic convention registry or a
config-driven walker for the other three conventions to plug into — that design should be
made when the third convention exists and its shape is known, not guessed from the second.

**The refused key.** Refusing `system:` in the reader is the channels-specific instance of a
pattern the package already has: `WORKER.md` refuses `persona:` by name, in one shared
message constant. The worker version is checked in *both* the loader and the seat factory,
because a hand-built record never passes the loader. Channels has only the loader door today,
so the constant ships here and the reconciler picks it up when it lands — put the message in
a constant now precisely so the second door cannot spell it differently.

**Where "undeletable" is enforced — and it is not here.** The issue's question is answerable,
and the answer is "none of the three, yet." The loader has no store and no delete verb. The
A helper must not be the enforcement point: a helper is one path to deletion and
anything reaching the store directly goes around it, which is a guard with a door beside it.
Enforcement belongs to whatever owns the delete verb, and nothing in the W3 floor owns one.
What this issue owes it is the narrower thing it can actually deliver: a file convention under
which `system` is never something an author wrote.

**What the other conventions inherit — where to read it, not a copy of it.** The shipped
`WORKER.md` pair (`packages/workforce/src/loader/read-workforce-directory.ts` and
`hire.ts`) plus the atlas §06 tree are canonical for the general shape: path layout, dot-
joined team-qualified identity minted from folder names, the one shared frontmatter dialect
from `orchestration`, `description` required and unknown keys carried verbatim, the
`{ things, errors }` reporting contract, and the node-reader / isomorphic-root package split.
FIX-1354 and FIX-1356 should read those two files and deviate only with a stated reason in
their own spec. This spec does not restate those rules, because a restatement is a copy that
goes stale when the originals move and nothing fails when it does.

**What is channel-specific and should not be copied.** Two things here are *not* the general
shape:

- **The refused `system:` key, and the either-source rule behind it,** exist because channels
  have two declaration sources and a later deletion guarantee. A convention with one source
  needs neither, and adding them for symmetry would be cargo cult.
- **Folder-per-thing is the call most likely not to fit resources** (FIX-1354). If resources
  turn out to be many small declarations, a folder each is heavy, and that spec is entitled
  to argue for `resources/<name>.md` — provided it argues, rather than drifting.

What *should* generalise beyond channels is the pair of rules in Decisions 2 and 3: two sources
for one thing is a refusal rather than a precedence rule, and any status the framework grants
is derived from the declaration path rather than declared in the file.

### 8. Implementation sequence

1. **Extract the shared walk.** Move `classify`, `openStructuralDirectory`, the symlink and
   unreadable wordings, `IGNORED_ENTRIES` and the segment validator into an internal module
   under `src/loader/`. `readWorkforceDirectory` imports them. → *verify:* the 31 existing
   `read-workforce-directory` tests and the 23 `hire` tests pass **with no edits to either
   test file**. A diff touching those tests means the extraction changed behaviour.
2. **Add `ChannelManifest` and the refused-key message constant** beside `WorkerManifest`. →
   *verify:* typecheck; the constant is imported by the reader.
3. **Add `readChannelsDirectory`** on the `./loader` subpath, walking `teams/<id>/channels/`. →
   *verify:* §10 behaviours R1–R2.
4. **Export it** from `loader/index.ts` and document it in the package README. → *verify:*
   an import from the package name resolves.

**Removals** — none; the extraction moves code without deleting a public surface. If step 1
leaves an unreferenced helper behind in `read-workforce-directory.ts`, delete it in that step.

### 9. Edge cases & error handling

**Inherited from the worker reader, and expected to behave identically** — a channel folder with
no `CHANNEL.md`; no frontmatter; a missing, empty, or non-string `description`; a folder name
breaking the segment rules; a symlink anywhere on the path; a directory that exists but
cannot be listed, reported under its own path; a file rather than a folder in the `channels/`
slot, skipped in silence; editor droppings ignored; an absent `channels/` folder, which is not
an error because a team may have no channels; a root with no `teams/`, which is empty; an
unreadable root, which throws. These are the worker reader's contract and are covered by
behaviour R1, not by ten restatements of it.

**New to channels** — a `CHANNEL.md` declaring `system:` lands in `errors` naming the file, not a
silent strip. That is the only new error class this issue adds; the collision cases belong to
the deferred reconciler (§12).

### 12. Dependencies, open questions & follow-ups

**Dependencies.** **Blocked by FIX-1311 / #1565**, recut to the **default ChannelFlow /
channel kind floor**: the replaceable L2 kind a channel is one instance of, post-as-dispatch
into that instance, and minimal clean transcript projection in the default kind. A channel file
names the kind it runs, so the kind is what it names; this issue sequences after that floor
lands. **Not** the message board as a public API — a smart resource with `reactTo` (#1627) is
characterization and framework teaching, not what a `CHANNEL.md` declares. Brief, housekeeper,
retirement and CAS are out of the floor's admission and block nothing here. The Collab roster
(FIX-1341) is not in the W3 floor at all and is not a dependency of this issue.

Otherwise this issue touches `packages/workforce` only, and the two
in-flight W3 issues that also touch it are disjoint: FIX-1342 (kinds map / seat contract)
works on `hire.ts` and the seat teach, and FIX-1357 (kinds + blocks boot scan) designs the
*code* registration door, not the document tree. This spec does not modify `hire.ts`, only
cites its refusal wording as precedent. Sequence this PR after FIX-1342's if both are in
flight, to keep the package's diff readable.

**Deferred to the issue that introduces the first code-declared channel** — the lab Proof, or
whatever first declares one, whichever lands first. Decisions 2 and 3 are the contract that
issue implements; it does not get to re-decide them.

- `reconcileChannels(fileChannels, { declaredInCode })` — the one door both sources pass through,
  collecting every problem and throwing once naming all of them, returning nothing partially
  (`hireWorkforce`'s discipline).
- **`ReconciledChannel`** — the output record, `{ id, declared, body, system, origin }` with
  `origin: "file" | "code"`. **This is the agreed spelling; it is deliberately not declared
  in this issue**, because a named exported type whose only producer is deferred is the same
  inert surface Decision 1 cuts. Use this name when it lands; do not invent a third one.
- The collision behaviours: the same id from both sources refuses naming both; every
  collision in one run is named in a single refusal; the same id twice within the
  code-declared list refuses with `hireWorkforce`'s duplicate-roster wording; and a
  code-declared record carrying `system:` refuses — the second path around the reader, using
  the message constant this issue ships.
- **Segment validation on hand-built records** (raised in review): a `ChannelManifest` handed to
  `declaredInCode` never passes the folder walk, so its `id` never meets the segment
  validator. `Engineering.standup`, or a bare `standup` with no team qualifier, could enter
  the merged set and later alias as a flow instance id or session key. The reconciler must
  validate ids it did not mint. Not solvable here — this issue has no code-declared path to
  validate.

**Settled by the owner, not open — one L2 communication file type.** The epic's product noun
is **channel**, and this convention is it. There is no `ROOM.md`, no parallel `rooms/` tree
and no second reader; "room" survives at most as an optional channel *kind* a later issue may
define, never as a second convention. The file half FIX-1353 was carrying folds in here. Its
composition half — subscribe helpers, DM versus group — belongs to the ChannelFlow kind
(FIX-1311); the Collab roster is out of the W3 floor entirely. The frontmatter shape already
supports that split: `flow:` and every other key are carried verbatim, so each lands with
whatever mints and runs the instance rather than with a second file type.

**Follow-up.** When the third convention (FIX-1354 or FIX-1356) is built, revisit whether the
shared walk should become a parameterised slot reader. Deliberately not done now — §7.

**Open, and deliberately not settled here — is `flow:` required on a `CHANNEL.md`, or
optional?** The lock says `flow:` selects the kind "exactly the way `WORKER.md` does" *and*
that ChannelFlow is the **default** kind. Those two pull apart: `WORKER.md`'s `flow:` is
required — `hireWorkforce` refuses a record that declares none — whereas a default kind implies
a `CHANNEL.md` may omit `flow:` and fall back to ChannelFlow. Either reading leaves this
issue's reader unchanged, because the reader carries `flow:` verbatim either way; the whole
difference is in the minter. Named here rather than guessed, and owned by the issue that mints
a channel's instance.

**Noted for the implementer, not a blocker:** FIX-1341 names three declaration sources —
code, `teams/<id>/channels`, and "team config". There is no team-level config file in the tree
today, so this convention has two. A third source would be exactly the shape Decision 2
refuses; if it is ever wanted, it should replace a source rather than join them.

## Spec evolution *(the change story)*

- **Spec drafted** — framed as the shape-setter for the epic's four file conventions rather
  than as a channels feature, because channels is inert until Collab and its real value now is the
  shape the other three inherit. Approach: extend the shipped `WORKER.md` convention to a
  `channels/` slot, extract the shared directory walk on its second caller, and preserve the
  FIX-1341 lock with a collision refusal plus a derived `system` stamp rather than a
