# FIX-1354: W3 — Resources file convention — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

A team's shared documents — a handbook, a glossary, an escalation procedure — are the
things every worker on that team is supposed to be reading. Today an app declares each one
in TypeScript, one `defineResource` stanza per document, naming the file it loads. The
documents live in files already; the list of them does not.

That leaves the workforce tree with a hole. `workers/` is a convention, `rooms/` and
`skills/` are becoming one, and `resources/` — which the atlas has drawn beside them since
§06 — is still code. An author who has learned to add a worker by adding a folder adds a
document by editing a source file and redeploying.

**Why now** — this is the third of the epic's four conventions, and it is the one the
first spec predicted would not fit. FIX-1352 flagged folder-per-thing as *"the call most
likely not to fit resources"* and invited this spec to argue. Arguing it now, with two
conventions written and two to go, is cheap. Arguing it after all four have shipped is a
migration.

### 2. Solution in plain terms

A document becomes a Markdown file in a `resources/` folder. Drop
`teams/engineering/resources/handbook.md` into the tree and the team has a handbook. Its
frontmatter is settings, its body is the document — the same bargain `WORKER.md` makes,
where frontmatter is settings and the body is instructions.

Two levels are readable: `org/resources/` for documents every team shares, and
`teams/<id>/resources/` for one team's. Where the file sits decides the document's identity
and storage key, so that is not something the file gets to say.

**It does not decide who can read it.** The team level is a *namespace*, not a boundary —
every file-declared document is org-scoped, and anything installed on a flow is reachable
by that flow's resource tools. Partitioning by team is the app's to do, by installing only
that team's documents (§7). A convention that reads as isolation and isn't would be worse
than one that makes no claim.

Reading the tree hands back plain records. A second call turns those records into the
resource map the app already passes to a flow — it calls `defineResource`, the same
function an author calls by hand today, and builds nothing else. There is no resource
registry in this issue, because L1 already has one.

**Philosophy** — tenet 2 (composition over features): the install half composes
`defineResource` rather than standing a second registry beside it. Tenet 3 (earn every
addition): the public surface grows by one reader and one pure function, and the directory
walk is shared with the worker reader rather than copied. Tenet 1 (coherence): the record
is deliberately *not* called `ResourceManifest`, because the framework already uses that
term for something else (§7).

**Named plainly:** this buys layout consistency and a keying rule, not capability. Decision
3 is where that trade is weighed and the counterfactual priced.

### 6. Decisions & rules — the sign-off surface

1. **A resource is a *file*, not a folder — `resources/<name>.md`, with no fixed manifest
   filename.** This breaks the shape FIX-1352 set for workers and rooms
   (`<slot>/<name>/THING.md`), deliberately and as that spec invited.
   *Why:* a worker folder and a room folder are containers — the atlas draws
   `workers/<name>/skills/` and `workers/<name>/resources/` inside a worker. A resource
   folder would contain nothing, because anything you would put beside a document *is
   another document*, which is another entry in the same `resources/` folder. Folder-per-
   thing also costs the name: `resources/incident-response.md` reads as a document, while
   `resources/incident-response/RESOURCE.md` reads as configuration, and a tree of
   identically-named `RESOURCE.md` files is worse to open, grep and diff the more
   documents a team has — which is the direction resources scale in and workers do not.
   *Rejected:* folder-per-resource for uniformity; and accepting **both** forms, which is
   worse than either, because then one document can be declared two ways and the epic's
   own rule (two sources for one thing is a refusal) would have to be enforced over a
   layout choice nobody needed.
   *Locks in:* the epic ships three folder-conventions and one file-convention, and an
   author must be told once that resources differ. Mitigated by §9's loudest error, which
   exists only because of this decision.

2. **A file-declared resource is an org-scoped document, and *every field the convention
   derives* is refused by name — not just `scope:`.** The derived set is `scope`, `ref`,
   `stateSchema`, `default`, and the four content sources (`content`, `contentFile`,
   `contentTemplate`, `contentTemplateRef`). `org/resources/x.md` and
   `teams/<id>/resources/x.md` both produce an org-scoped resource, keyed as the atlas
   keys it (§7). Resources with a state schema, a render function, reactive block bindings
   or an edge graph stay in code.
   *Why:* this is the epic's inherited rule — a status the framework grants is derived from
   the declaration path, never declared in the file. **The rule needs the wider refusal to
   actually hold**, which review found by running it: with only `scope:` refused and the
   rest carried verbatim, a file writing `ref:` silently redirects its storage row, `content:`
   replaces the Markdown body, and a YAML `stateSchema:` string *constructs successfully*
   and only fails later when the engine calls `safeParse` on a string (§10, F1a–F1c). A
   derived field that frontmatter can overwrite was never derived.
   *Rejected:* letting a file declare its own scope; and silently letting derivation win
   over a verbatim key, which fixes the corruption but leaves an author whose `ref:` does
   nothing and says nothing.
   *Locks in:* session- and user-scoped resources are never file-declared, and the
   convention owns its own fields. If a file-declared per-user document is ever wanted, it
   arrives as a new *path* (a level in the tree that means it), not a new key — additive,
   and it breaks nobody.
   *This deviates from inherited rule 4* (at most one key refused by name). Resources
   refuse a set because resources derive a set — §7's table has the full inherited/broken
   ledger, and §12 raises the general form to the epic rather than patching it here.

3. **We ship it knowing it buys consistency, not capability — and we accept it may be
   inert.** The install half composes `defineResource` and adds no registry, so the whole
   change is one reader, one pure function and one record type.
   *Why:* the counterfactual is the epic's stated defect — a tree with three of its four
   slots conventional and the fourth still code. The one thing that is genuinely new is
   the keying rule: nothing today mints a team-qualified ref for a shared org row, so
   every app inventing its own prefix is the status quo we would be preserving.
   *Rejected:* closing the issue and telling authors to write `defineResource({ contentFile })`
   — which works today, verified (§10, E1) — and folding documents into the skills
   convention, which already has folders that hold reference files. Skills lose because a
   skill is an activatable procedure and a resource is stored, mutable state the framework
   reads and writes; they are different things that happen to both be Markdown.
   *Locks in:* if FIX-1355's lab Proof does not declare resources in files, we will have
   shipped layout consistency and nothing else. Recoverable — it is one reader and one
   function we would delete — but it would mean this issue ran a cycle early and should
   have been sequenced after the lab.

**Non-goals** — `workers/<name>/resources/` (the atlas names member scope an open gap and
says prove `flowIsolation` first; §12); session- or user-scoped file-declared resources;
resource *collections* from files; any registry, store or install machinery beyond
returning a map; mutating resources through the convention; and a `teams/<id>/team.md` as
a second declaration source.

**Size:** Small — ~4 production files · 3 test behaviours + 1 goal check · 1 doc surface · 1 PR.

### 3. Tradeoffs & alternatives

**The cost of Decision 1, stated plainly.** The epic loses one-line uniformity. "Everything
is a folder with an uppercase file in it" would have been the shorter teach, and three of
four conventions will still be able to say it. What we get back is that the odd one out is
the one where the folder was doing no work.

**The alternative that nearly won: don't build it.** Weighed and answered in Decision 3 —
the deltas are ergonomic and naming, which is the weak end of the ladder.

**An answer the epic asked for, now that a third convention exists.** FIX-1352 left a
follow-up: when the third convention lands, revisit whether the shared walk should become
a *parameterised slot reader* — one walker configured with a slot name, a manifest
filename and a refused key. The answer is no, and this spec is the evidence. Resources is
not slot-shaped: its leaf is a file, its identity comes from a filename, and it reads two
roots rather than one. What the three readers share is the *primitives* — classify without
following symlinks, open a structural directory, the symlink and unreadable wordings, the
segment validator — and that is the extraction FIX-1352 is already making. Generalising
past it would have been a design guessed from two samples that the third contradicts.

### 4. Focus practices

- **BP-003 (verification evidence).** Every behavioural claim was executed (§10). One was
  deliberately *not* claimed: no measurement of how many documents a team typically has —
  Decision 1's cardinality argument is structural, not measured, and is written that way.
- **Tenet 1 (coherence).** `ResourceManifest` is already the framework's name for the
  client-facing list of a session's public resources over HTTP. The new record takes a
  different name (§7) rather than putting two meanings on one term.
- **BP-030 (tolerate the old shape).** A shipped goal check pins that the worker loader
  stays *silent* on a team's `resources/` folder. That silence is the worker reader's
  contract and is not to be traded away when a second reader starts claiming that folder.
- **BP-007 (concise API docs).** Two new exports get a file header and documented
  signatures at the density the existing loader sets.

### 5. What using it looks like

An org-wide document and a team document, declared as files:

```
workforce/org/resources/code-of-conduct.md
workforce/teams/engineering/resources/handbook.md
```

```md
---
description: How the engineering team works — on-call, review, escalation.
llmReadable: true
---

# Engineering handbook

Escalate anything customer-visible within 15 minutes.
```

```ts
import { readResourcesDirectory } from "@flow-state-dev/workforce/loader";
import { resourcesFromDocs } from "@flow-state-dev/workforce";

const { documents, errors } = await readResourcesDirectory("./workforce");
if (errors.length) throw new Error(/* same fail-on-errors shape as workers */);

const declared = resourcesFromDocs(documents);
// { "code-of-conduct":             DefinedResource, // scope "org", ref "code-of-conduct"
//   "teams/engineering/handbook":  DefinedResource } // scope "org", same as the ref
```

Every team's documents come back in one map. To give a team's seats only its own, filter
the records first — the team folder is a namespace, not a visibility boundary (§7):

```ts
const engineering = resourcesFromDocs(
  documents.filter((d) => d.ref.startsWith("teams/engineering/")),
);
```

The app merges that map into its own, explicitly — the framework will not do it (§7):

```ts
export const supportFlow = defineFlow({
  kind: "support",
  actions: { ... },
  resources: { ...appResources, ...declared },
});
```

A file that tries to declare where it lives is refused when the tree is read:

```ts
errors;
// [{ path: "teams/engineering/resources/handbook.md",
//    error: Error('"handbook.md" declares `scope:`, which is a setting the convention
//                  derives from where the file sits, not one a resource declares.') }]
```

The same refusal covers `ref:`, `stateSchema:`, `default:` and the content-source keys —
everything the convention derives (Decision 2).

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

**What this inherits from FIX-1352, and what it breaks.** The rooms spec set the shape for
the epic's four conventions and named its own most-likely-to-break call. Four of the seven
carry over untouched; three do not, each for a reason found in this issue rather than
imported.

| # | Inherited rule | Here |
| --- | --- | --- |
| 1 | Path `teams/<id>/<slot>/<name>/THING.md` — folder per thing, fixed uppercase manifest | **Broken.** File per document, `<slot>/<name>.md`, no manifest filename — Decision 1. **Also broken:** two roots, not one; the atlas draws `org/resources/` beside `teams/` |
| 2 | Identity `<teamId>.<name>`, dot-joined, minted in one helper via the shared segment validator | **Broken in form, kept in mechanism.** The ref is `teams/<teamId>/<name>` — the atlas fixes this key (§10, F3) — still minted in one helper, still validated segment by segment |
| 3 | One shared frontmatter dialect from `orchestration`; no second dialect | **Inherited**, unchanged |
| 4 | `description` required; unknown keys verbatim; **at most one** key refused by name | **Broken.** The refusal covers every *derived* field, not one key — rule 4 collides with rule 7 wherever a convention derives more than one thing (Decision 2; raised to the epic, §12) |
| 5 | `{ things, errors }`; per-entry problems collected; structural folders under their own path; throw only on an unreadable root | **Inherited**, unchanged |
| 6 | Reader touches `node:fs` behind `./loader`; what turns records into something usable stays isomorphic at the root | **Inherited**, unchanged |
| 7 | Two sources for one thing is a refusal, not precedence; framework-granted status is derived from the path, never declared | **Inherited** — and rule 7 is what *forces* the break in rule 4 |

Rooms' `system:` key and the either-source rule behind it are rooms-specific and are
deliberately not copied: resources have one declaration source.

**Where the tree puts a resource.** Two roots, both locked by the atlas (§06):

| Path | Scope | Ref |
| --- | --- | --- |
| `org/resources/<name>.md` | `"org"` | `<name>` |
| `teams/<teamId>/resources/<name>.md` | `"org"` | `teams/<teamId>/<name>` |

`org/` is a new root for this package — the worker reader walks `teams/` only (verified,
§10) — but it is not a new idea: the atlas has drawn `org/resources/` and `org/skills/`
beside `teams/` since §06, and marks org scope as already existing.
`workers/<name>/resources/` is drawn there too and is a non-goal here; the atlas marks it
a gap pending `flowIsolation` work.

**Identity — the path form, because the atlas already fixed it.** A team document's ref is
`teams/<teamId>/<name>`, **not** the dot-joined `<teamId>.<name>` a worker id uses: the
atlas states that key three separate ways (§10, F3), so a dotted ref would put the same
logical document at a different org storage row from anything else following the atlas.

The `/` is safe here in a way it is not for a worker. The worker reader dot-joins because a
worker id becomes a *flow instance id* and a slashed one 404s on every flow route; a
resource ref is a storage-key namespace and never routes. Do not carry the worker's
justification across — it does not apply. The mechanism does carry across: minted in one
helper, each segment validated by the existing shared validator. The accessor key is the
ref, so a team's handbook is `ctx.resources["teams/engineering/handbook"]`.

**What the record is called, and why not the obvious name.** `ResourceManifest` is taken:
`handleGetResourceManifest` in `@flow-state-dev/engine` returns a session's public resource
list over HTTP. Reusing the word for an on-disk record would put two meanings on one term
in one framework. Name the record for what it is — a document — e.g. `ResourceDoc`,
mirroring `WorkerManifest`'s three fields:

```
ResourceDoc { ref, declared, body }
```

It lives beside `WorkerManifest`, node-free. `body` is the document; `declared` is the
frontmatter verbatim.

**Two exports, on the two sides of the package's existing line.**

- `readResourcesDirectory(root)` → `{ documents: ResourceDoc[], errors }`, on the
  `./loader` subpath (`node:fs`). Walks both roots, decides nothing, installs nothing.
  The field is `documents`, **not** `resources`: this call returns records, and a
  `resources` field here reads as the L1 resource map — which is what the *other* call
  returns, and what it gets merged into at the call site.
  Same error contract as the worker reader — `errors[]` keyed by slash-separated path
  relative to the root, structural folders reported under their own path, throws only when
  `root` itself is unreadable.
- `resourcesFromDocs(documents)` → `DeclaredResources`, at the isomorphic root. Pure. No
  `node:fs`, no store, no registry.

**What `resourcesFromDocs` hands `defineResource`, and the order it does it in.** It
requires a `stateSchema` and refuses an absent scope — both executed (§10, E1/E2). A
document has no state, so the function supplies a permissive empty-object schema and an
empty default, and the body becomes `content`.

**The derived fields are applied *last*, over an allowlisted passthrough — never spread
before it.** Naive `{ ...derived, ...frontmatter }` is the bug review caught by running it
(§10, F1a–F1c), and F1d is the shape that holds:

```
defineResource({ ...allowlistedFrontmatter, ref, scope, stateSchema, default, content })
```

Two guards, deliberately both, for the two-door reason `hire.ts` already has — a hand-built
`ResourceDoc[]` never passed the reader:

1. **Refused by name**, one shared message constant beside `REFUSED_PERSONA_KEY_MESSAGE`,
   checked at *both* entry points: `scope`, `ref`, `stateSchema`, `default`, `content`,
   `contentFile`, `contentTemplate`, `contentTemplateRef`. A file writing one gets told the
   convention owns it, rather than having it quietly ignored.
2. **Ordering**, so that even if a refusal is ever missed the derivation still wins and no
   document can be pointed at another document's storage row.

Everything outside the derived set is still carried verbatim, so the JSON-valued options
(`llmReadable`, `llmWritable`, `writable`, `allowedExtensions`, `metadata`) work by being
written. **`prefetchMode: "lazy"` is the one exception and must be refused too** — verified
(§10, F4): `defineFlow` rejects a lazy *single* resource declared at flow level, because
there is no per-block load trigger, and every document here is flow-level. Refuse it with
the reason rather than letting an app discover it at startup. The function- and
schema-valued options (`render`, `client.data`, `reactTo`, `edges`) cannot be expressed in
YAML at all.

**The team level is a namespace, not a visibility boundary.** Every file-declared document
is org-scoped, and the resource tools enumerate *every* installed entry marked
`llmReadable` with no per-team or per-seat filter (§10, F2) — org scope keys storage, it
does not gate reads. So installing a whole tree on one flow makes every team's documents
reachable from it. An app that wants otherwise **partitions at install** by filtering
`documents` on its path prefix; no API is added for that. A reader who infers isolation
from the folder will be wrong, so the README says this outright (§11).

**Where a file-declared resource meets the existing L1 install — and the sharp edge there.**
It meets it at `defineFlow({ resources })`, or at a flow instance's mint
(`flow({ id, resources })`). Both accept a resource map; the instance door is verified (§10,
E3). **The instance door replaces the definition's own map rather than merging with it** —
also verified (E4), and it is why `resourcesFromDocs` returns a plain map instead of
installing anything. Handing file-declared resources straight to `hireWorkforce`'s mint
would silently delete whatever resources the seat's flow kind declared. The app spreads the
map itself, visibly, at its own call site. That is the whole of the "no second registry"
requirement: there is nothing to register, because L1's resource map is the registry.

**Sharing the walk.** Consume the internal walk primitives FIX-1352 extracts under
`src/loader/` — `classify`, `openStructuralDirectory`, the symlink and unreadable wordings,
`IGNORED_ENTRIES`, the segment validator. Do not build a parameterised slot reader; §3 says
why. If FIX-1352 has not landed when this starts, do the same extraction here on the same
terms.

### 8. Implementation sequence

1. **Add `ResourceDoc`, the derived-field name set, and its shared refusal message** beside
   `WorkerManifest`. → *verify:* typecheck; the set and message are imported by both new
   modules, so neither spells the refusal itself.
2. **Add `readResourcesDirectory`** on `./loader`, walking `org/resources/` and
   `teams/<id>/resources/`. **Gate before writing it:** FIX-1352's extraction must already
   be on `main`, or this step does that extraction first. → *verify:* §10 behaviours R1–R2,
   **and** `grep -c 'function classify' packages/workforce/src` returns `1` — a second
   definition means the walk was copied instead of shared, which is the main way this
   implementation overshoots.
3. **Add `resourcesFromDocs`** at the isomorphic root, with the derived fields applied
   after the allowlisted passthrough. → *verify:* §10 behaviours R3–R4; that the module
   imports nothing from `node:`; and that no `...declared` spread appears *after* the
   derived fields in the `defineResource` call.
4. **Export both** and document them in the package README. → *verify:* an import from the
   package name and from `/loader` each resolve.
5. **Add the goal check** (§10). → *verify:* it PASSes, and fails when controlled.

**Removals** — none. If step 2 consumes FIX-1352's extraction, no code moves here.

### 9. Edge cases & error handling

**The one that exists because of Decision 1, and the most important error in this spec:**
a **directory** inside a `resources/` slot is **reported**, not skipped, with a message
naming the file convention. An author arriving from `workers/` or `rooms/` will create
`resources/handbook/RESOURCE.md`, and silence would leave them with a tree that looks right
and a team with no handbook. Note this inverts the worker reader's rule, where a *file* in
the slot is the thing that is skipped in silence — the inversion is exactly Decision 1 and
should read as deliberate in the code.

**Also new to resources:** a non-`.md` file in the slot is skipped in silence (a stray
`notes.txt` or an image is not a document anyone declared); a `.md` file whose name breaks
the segment rules is reported under its own path; a file declaring any **derived** field —
`scope`, `ref`, `stateSchema`, `default`, or a content source — is reported naming the file
and the field; and `prefetchMode: "lazy"` is refused with its reason, because `defineFlow`
would otherwise reject the whole flow at startup (§10, F4).

**Inherited from the worker reader, and expected to behave identically** — no frontmatter;
a bad `description`; a folder name breaking the segment rules; a symlink anywhere on the
path; a directory that exists and cannot be listed, reported under its own path; editor
droppings ignored; an absent `resources/` folder or `org/` root, neither an error (a team
may have no documents); a root with neither, which is empty; an unreadable root, which
throws. This is the worker reader's contract, covered by R1 rather than restated case by
case.

**At the install half:** a doc whose frontmatter makes `defineResource` throw (two content
sources, a bad client projection) throws from `resourcesFromDocs` naming the ref — this is
startup misconfiguration, and the reader's collect-don't-throw discipline does not extend
to it, exactly as `hireWorkforce` throws where `readWorkforceDirectory` collects.

### 10. Testing strategy

**Evidence run for the claims this spec rests on** — executed at `7aa5ad4b0`, the pin this
spec was written against, with dependencies installed in the authoring worktree.

| **E2** `defineResource` refuses an absent scope — so the convention must supply one | same harness, scope omitted | Threw `requires an explicit scope` |

**Second evidence run — the four findings spec review raised, each executed before being
folded in** (same pin). Findings 1 and 4 changed the design; 2 and 3 changed what the spec
claims.

| Claim | How | Result |
| --- | --- | --- |
| **F1a** Verbatim passthrough lets a file **replace the derived ref** | `{ ...derived, ...frontmatter }` with `ref: "somewhere-else"` | `ref = somewhere-else` — storage row redirected |
| **F1b** …and **replace the Markdown body** | same, with `content: "hijacked"` | `content = hijacked` |
| **F1c** …and a YAML `stateSchema:` string **constructs successfully**, failing only later | same, with `stateSchema` as a string | `typeof === "string"`; throws only when `safeParse` is called on it |
| **F1d** Applying derived fields **after** an allowlisted passthrough holds | `{ ...allowlisted, ref, scope, stateSchema, default, content }` | `ref` and `content` both the derived values |
| **F2** Resource tools enumerate **every** installed `llmReadable` entry, with no per-team filter | `packages/core/src/tools/resource-tools.ts` — "Every `llmReadable` resource"; `ns.ref.config?.llmReadable !== true` is the only gate | No seat/team predicate exists — team folder is not a boundary |
| **F3** The atlas fixes the team resource key as a **path**, not a dotted id | `docs/atlas/workforce.html` — §06 tree, the Team row, and `defineResourceCollection({ pattern: "teams/[teamId]/[doc]" })` | Three independent statements of `teams/[teamId]/[doc]` |
| **F4** `prefetchMode: "lazy"` on a flow-level single **throws at `defineFlow`** | `defineFlow({ resources: { …, prefetchMode: "lazy" } })` | Threw: *"declared at flow level cannot be prefetchMode: 'lazy' — flow-level declarations have no per-block load trigger"* |

**Still not claimed:** that a collection instance under `teams/[teamId]/[doc]` and a single
resource with that `ref` resolve to the same storage row. The ref *form* now matches the
atlas (F3), which is what stops the keys diverging; whether the two install shapes are
row-compatible was not executed and must be settled by whoever moves documents to a
collection (§12).

**Not claimed:** how many documents a team typically has. Decision 1's cardinality argument
is structural — a resource folder has nothing legitimate to hold — and is not supported by
any measurement, deliberately.

**Behaviours to test** (TDD, per the Feature label). The inherited reader contract is
already pinned by the worker reader's 31 tests; this does not re-test it folder by folder.

- **R1.** The reader honours the worker reader's contract on both resource roots: an
  `org/` document and two team documents load with correctly qualified refs, verbatim
  frontmatter and body; and each error class (bad `description`, bad segment name, symlink,
  unreadable structural folder) lands in `errors` under its own path rather than throwing.
  One table-driven test.
- **R2.** The two Decision-1 consequences: a **directory** in a `resources/` slot is
  reported with a message naming the file convention; a non-`.md` file is silently skipped.
- **R3.** `resourcesFromDocs` produces a map keyed by the atlas's ref form
  (`teams/<teamId>/<name>`, and a bare name at org level) whose entries carry the body as
  content at org scope.
- **R4.** The derived-field guard, both doors and both mechanisms — table-driven over the
  refused set (`scope`, `ref`, `stateSchema`, `default`, each content source,
  `prefetchMode: "lazy"`): the reader reports it under the file's path, a hand-built
  `ResourceDoc` is refused by `resourcesFromDocs` with the *same* message, and — the
  regression that matters — a doc that somehow carries one produces a resource whose `ref`
  and `content` are still the derived values, never the declared ones. F1a–F1c are what
  this test exists to keep fixed.

**Goal check** (the project's verification shape for a convention, alongside
`files-alone-produce-the-roster`): *a team's documents come from files alone* — a fixture
tree with an org document and two teams that each have a `handbook`, marker tokens in each
file so a reader that mis-keys puts the wrong body on a team, one directory in a
`resources/` slot that must be reported, and a passing tree that produces a resource map an
L1 flow accepts. Anti-game: assert on the markers and on which slot is reported, never on
counts or on shape the loader itself produced.

**Regression guard:** E7's 137 tests pass unmodified.

### 12. Dependencies, open questions & follow-ups

**Dependencies.** No hard blocker. Sequence after FIX-1352's implementation PR so the
shared walk is extracted once by its owner — enforced as a gate in §8 step 2, not left to
prose here. FIX-1342 (kinds map / seat contract) and FIX-1357 (code registration door) also
touch `packages/workforce` and are disjoint: neither reads the document tree, and this spec
modifies neither `hire.ts` nor the seat contract.

**Open questions.** None. The two calls a reviewer might expect to find open are decided:
worker-level resources are a non-goal on the atlas's authority, and the install door is
chosen on executed evidence (E3/E4) rather than on preference.

**Raised to the epic, not decided here.**

- **The one-refused-key rule has a hole, and it is not only ours.** Inherited rule 4 (unknown
  keys carried verbatim, at most one key refused by name) contradicts inherited rule 7 (a
  status the framework grants is derived, never declared) wherever a convention derives
  *more than one* field. Every convention so far reserves exactly one — `WORKER.md`
  `persona:`, rooms `system:`, this one started at `scope:` — and none reserves the other
  fields it owns, so verbatim passthrough can overwrite them. Executed here (F1a–F1c):
  `ref:` redirects a storage row and a YAML `stateSchema:` constructs fine and fails much
  later. **Resources is fixed by Decision 2. Rooms is specced and skills is drafting, and
  both inherit the hole.** The general form: *a convention refuses the set of fields it
  derives, not one key.* Named for the epic to route; deliberately not patched into their
  specs from here.
- **FIX-1352's parameterised-slot-reader follow-up is answered: no.** §3 carries the
  argument. Worth the epic knowing before FIX-1356 (skills) is written, because skills
  *is* slot-shaped and might otherwise be built to a generalisation this issue disproves.
- **The epic now has two layout shapes.** Three conventions are folder-per-thing, this one
  is file-per-thing. That is a teach the epic's docs pass owes one sentence, and it is
  cheaper to write that sentence than to make resources heavier so the sentence is
  unnecessary.

**Follow-ups.**

- **Member-scoped resources** (`workers/<name>/resources/`) — the atlas's named gap. Needs
  `flowIsolation` proven per kind first, and is explicitly not closed by growing `Agent`.
  Not in scope; the path stays unread, and an author who creates it gets silence rather
  than a wrong answer, which is the correct behaviour for a level that has no meaning yet.
- **Documents as a collection, which is what the atlas actually proposes.** The atlas's
  worked shape for team docs is `defineResourceCollection({ pattern: "teams/[teamId]/[doc]",
  scope: "org" })` — one parameterised collection, not N singles. This spec installs singles
  **at that same ref form** (Decision 2 / §7), so the keys do not diverge, but the install
  shapes differ and row-compatibility between them is explicitly unverified (§10). Whoever
  moves documents onto a collection settles that first. A `resources/<name>/` folder would
  also acquire a meaning under a collection — many instances under one ref — and that is a
  better reason to reintroduce folders later than uniformity ever was.

## Spec evolution *(the change story)*

*Changes since the last review only. The decisions themselves live in §6–§7 and are not
restated here — one copy, so an edit cannot leave two.*

- **Spec drafted** — framed as the epic's first deliberate deviation from the shape
  FIX-1352 set, rather than a fourth copy of the worker convention.
- **After spec review** — compressed throughout (each decision's case appears once, later
  mentions cite it). Two ergonomic changes: the reader's result field is `documents`, not
  `resources`, so it does not read as the L1 map it gets merged into; and the FIX-1352
  sequencing moved from prose in §12 to a gate with a failing check in §8 step 2.
- **After the review's executed findings** — Decision 2 widened from refusing `scope:` to
  refusing **every field the convention derives**, because running it showed verbatim
  passthrough could redirect a document's storage row and smuggle a YAML string in where a
  Zod schema belongs. Team refs changed from the dot-joined `<teamId>.<name>` to the atlas's
  canonical `teams/<teamId>/<name>`, so file-declared documents share a storage key with
  anything else following the atlas. The team folder is now described as a namespace rather
  than a visibility boundary — it never was one, and the earlier wording implied it.
  `prefetchMode: "lazy"` joined the refused set rather than being listed as working.
