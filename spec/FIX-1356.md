# FIX-1356: W3 — Skills file convention — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

W3 is giving four things a file convention — rooms, channels, resources, and skills — so an
app can describe a whole team in files instead of in code. Three of them start from nothing.

Skills do not. A skills file convention already ships: a folder with a `SKILL.md` in it. It is
public API, documented across five pages of our site, used by an app in this repo, and the
file format is not ours — it is the open Agent Skills format, whose portability our docs
promise in both directions.

So the real question is not what convention skills should have. It is: **the one they have
doesn't look like its three new siblings — does that matter?**

**Why now** — the other three are being written this week. Left unscoped, an issue with this
title resolves one of two bad ways: it aligns skills to the sibling shape and breaks a
published format for symmetry, or it adds a second skills reader beside the first, which the
issue's own words forbid. Both are cheap to rule out now and expensive to unpick later.

### 2. Solution in plain terms

**Ratify the convention skills already have, and add only the rule that is genuinely missing.**

Two facts do most of the work, both executed rather than assumed (§10). A seat can already
name its skills in a file: a `WORKER.md` saying `skills: [port-scan, triage]` loads and hires
today. And a skills folder can already sit at any level, because the existing reader takes a
root — which is what our own internal atlas prescribes: the same wiring aimed at a different
level, not a skills package per level.

What is missing is the rule for **the same skill name declared at two levels**. Today the second
one silently overwrites the first and nothing is said.

**The limit that comes with it, because it is user-visible:** skills all land in one catalog
keyed by the bare skill name, so a name is unique across the *whole app*. A team folder says who
owns a skill and lets an app load one team's worth; it does not give that team its own
namespace. Two teams cannot each have a `review`. Decision 3 carries this.

So this ships three things: the levels and the scope each maps to, written down; one thin load
that reads them through the existing reader and refuses a duplicated name; and one defect fix
— a `SKILL.md` that exists but cannot be read is currently reported as *missing*, which sends
an author to the wrong fix.

**Philosophy.** Tenet 2 (composition over features): a skills level is the existing reader
pointed at a folder. Tenet 3 (earn every addition): the only new behaviour is the refusal.
Tenet 5 (one convergence point): it lives at the one door both levels pass through.

**Worth naming, because it cuts against shipping anything:** strip the refusal and what remains
is documentation, and this issue could close instead. Decision 1 is where you buy that.

### 6. Decisions & rules — the sign-off surface

1. **Skills keep the convention they have. It is ratified, not aligned** — so this issue is much
   smaller than its title suggests.
   *Rejected:* bringing the skills reader onto the worker/room shape. It fails on four
   independent counts, each measured in §10: the walk change breaks every existing skills
   folder, including this repo's own 38 and every documented example; re-keying its errors is a
   breaking change to a published package bought for cosmetic symmetry; the dot-joined
   `team.name` identity the siblings mint is refused by the shipped skill-name validator, which
   also gates collection keys, activation and slash matching; and the format is external and we
   advertise its portability.
   *Locks in:* four conventions, three sharing a shape and one not, on the record as deliberate.
   Reversing later costs a migration for every app with a skills folder — so this is the
   reversible order, not merely the cheap one.

2. **A team's skills are the existing reader pointed at that team's folder — no second reader,
   and no `scope: "team"`. The level derives the scope, and a `SKILL.md` that writes `scope:`
   is refused by name.**
   *Rejected:* a `readTeamSkillsDirectory` beside the existing one — it would produce records
   nothing consumes, since a seat already selects its skills by name. Also rejected: letting a
   file declare its own scope. Today `scope:` is not a key the parser knows, so it is silently
   preserved and ignored — an author can write it, be wrong, and never be told.
   *Locks in:* a level is a path and a scope mapping, not a new subsystem. Team-level skills
   store as org-scoped rows keyed by team, because `"team"` is not one of the three scopes the
   framework has, and this issue does not add one. The refusal lands at the **workforce loader's
   door only**, not in `readSkillsDirectory` — that reader also serves roots with no workforce
   tree and no level, where the rule has nothing to say, and Decision 1 keeps it untouched.

   *This is the epic's derived-status rule, on its fourth convention.* `WORKER.md` refuses
   `persona:`, `ROOM.md` refuses `system:`, a resource file refuses `scope:` — same discipline,
   same reason: a status the framework grants is read from where the file sits, never from what
   it says.

3. **One skill name declared twice anywhere in the tree is refused, naming both paths — and
   skill names are therefore globally unique across an app's teams.**
   *This refusal is forced, not chosen, and the spec earlier presented it as a choice.* Skills
   seed into one collection keyed by the bare skill name (`<name>/SKILL.md`), and the record
   that reaches it carries no team. So two same-named skills have nowhere to both exist: run
   (§10, `C1`), the second overwrites the first and nothing reports it. The genuine options are
   refuse loudly or overwrite silently. A precedence rule was never available — it would only be
   choosing which declaration gets clobbered.
   *Rejected:* overwriting silently, which is today's behaviour.
   *Locks in:* **a team cannot name a skill `review` if any other team already has one.** Two
   teams share one skill namespace; the team folder buys ownership that a human can see and a
   level an app can choose to load, not a namespace. If that limit is unacceptable, the fix is
   not a precedence rule — it is per-team identity, which Decision 1 rules out (the shipped name
   validator refuses the dot-joined form) and which would be a much larger issue than this one.

**Non-goals** — a second skills reader; any change to the `SKILL.md` format, the skill-name
rules, or the reader's `{ name, error }` contract; a `scope: "team"`; team-qualified skill
identity; binding a seat's declared `skills:` list to a live skills capability at runtime (the
flow kind's job — §12); and skills declared in code.

**Size:** Small — 2 production files · 3 test behaviours · 2 doc surfaces · 1 PR.

### 3. Tradeoffs & alternatives

**The simpler approach, and it is close to right: close the issue.** Skills have a working
convention, a seat can already declare its skills, and every level already reads. On that
reading, W3's skills row is satisfied by two paragraphs of documentation.

What tips it is the collision rule. It is behaviour that does not exist, it is silent when it
bites, and it is the one part a user cannot cheaply fix: concatenating two reads is four lines,
but noticing that `triage` was declared twice and one copy vanished is not something an author
discovers until a seat behaves like the wrong skill. If review disagrees that this clears the
bar, closing is a coherent outcome and Decision 1 is where to say so.

**Aligning the reader to its siblings** is rejected in Decision 1. The one piece worth keeping
is the defect: the siblings keep *unreadable* and *absent* apart deliberately, the skills reader
collapses them, and that is a bug rather than a difference of taste. It ships here on its own.

**Folding skills into the lab Proof (FIX-1355)** is coherent — the Proof is where a team's skills
first get exercised, and it would prove the convention instead of asserting it. It loses
narrowly: the collision rule is cheaper to settle before two levels exist in a real tree, and
the Proof should be spending its attention on whether three seats fan in.

### 4. Focus practices

- **BP-003 (verification evidence).** Every claim the recommendation rests on is executed, and
  the POC is on this branch so a reviewer can re-run it. That matters more than usual here: the
  case for *not* building the obvious thing is only as good as the measurements under it.
- **BP-030 (tolerate the old shape).** This touches a reader that already ships with documented
  consumers. Its error entries, flat walk and options keep working; its suite is the contract
  and is not rewritten to fit.
- **Tenet 5 (one convergence point).** The refusal gets one door. Do not also enforce it in a
  per-level helper.
- **BP-022 (release notes).** This change straddles **two published packages, so it needs two
  `patch` changeset entries, not one** — the error-message fix is in
  `@flow-state-dev/orchestration`, the new `readWorkforceSkills` export is in
  `@flow-state-dev/workforce`, and they version separately. Attributing both to orchestration
  would ship the fix and leave the export unreleased to installed consumers — a change that
  looks complete and silently does not arrive.

### 5. What using it looks like

An app keeps shared skills at the org level and one team's skills beside that team.

```
workforce/org/skills/triage/SKILL.md
workforce/teams/pentest/skills/port-scan/SKILL.md
workforce/teams/pentest/workers/recon/WORKER.md
```

The seat names the skills it wants, in the file that already carries its settings:

```md
---
description: Recon seat.
flow: seat
skills: [port-scan, triage]
---
Find things and write them down.
```

Loading the conventional levels is one call, handing back what `initialSkills` already takes:

```ts
import { readWorkforceSkills } from "@flow-state-dev/workforce/loader";

const { skills, errors } = await readWorkforceSkills("./workforce");
if (errors.length) throw new Error(/* same fail-on-errors shape as workers */);
```

```ts
skills; // InitialSkill[] — the same records readSkillsDirectory returns
// [ { name: "triage",    skillMd: "---\ndescription: …", files: [] },
//   { name: "port-scan", skillMd: "---\ndescription: …", files: [] } ]
```

Declaring one name at two levels stops the app instead of picking a winner:

```ts
errors;
// [{ path: "teams/pentest/skills/triage",
//    error: Error('Skill "triage" is declared at two levels — org/skills/triage and
//                  teams/pentest/skills/triage. Remove one: there is no precedence rule.') }]
```

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

**The divergence, and the call on each.** Five axes on which the shipped skills reader differs
from the worker/room shape. Middle column is what the siblings do; right column is the call.
**The evidence for every row is §10's table** — it is not repeated here.

| What | Sibling shape | Call |
| --- | --- | --- |
| Walk | `teams/<id>/<slot>/<name>/` | **Keep flat.** The reader takes a root; the level is the caller's choice. Changing it breaks every existing skills folder. |
| Error key | slash-separated `path` | **Keep `name`.** Published API, documented. The new multi-level load reports by `path`, since it is the thing that knows about levels. |
| Unreadable vs absent | kept apart | **Fix.** A present-but-unreadable `SKILL.md` reports as missing today. Genuine defect; the only behaviour change to the existing reader. |
| Identity | dot-joined `<team>.<name>` | **Keep bare.** The shipped name validator refuses dots, and it gates collection keys, the activation store and slash matching. |
| Package split | node reader on `./loader` | **Keep as is.** `orchestration`'s root is deliberately the Node-reaching entry and `./tasks` is the browser-safe one — the inverse of `workforce`'s split, on purpose and documented in its index. |

Two things the conventions **already agree on**, and neither needs work: they share one
frontmatter dialect (both parse through the same `splitFrontmatter` / `parseFrontmatterYaml`
from `orchestration`), and both require a non-empty `description` while carrying unknown keys
through verbatim. The folder is the identity in both; skills enforce it by *agreement* (a
`name:` that disagrees with its folder is refused) rather than by refusing the key, which is a
stricter, better version of the same rule and stays.

**Where the new code goes.** `workforce`, not `orchestration`, and on the `./loader` subpath
beside the worker reader. The reason is ownership: what is being added knows about *the
workforce tree* — that `org/skills` and `teams/<id>/skills` are the levels — and nothing about
how a skill is parsed or stored. `orchestration` owns skills and must not learn the workforce
tree; `workforce` already depends on `orchestration` and already walks this tree.

**The one new export.** `readWorkforceSkills(root)` → `{ skills, errors }`.

- Reads `<root>/org/skills` and each `<root>/teams/<teamId>/skills` by calling
  **`readSkillsDirectory` unchanged**, once per level.
- A level that is absent is not an error (an app may have no org skills, and a team may have
  no skills of its own). A level that exists and cannot be read is, reported under its path —
  the `openStructuralDirectory` discipline the worker reader already has.
- Re-keys each level's `{ name, error }` entries onto `{ path, error }` using that level's
  path, so a caller can tell which level broke. This is the adapter, not a new contract.
- Returns `InitialSkill[]` — the existing record, which is what `initialSkills` takes. **No new
  record type.**

**Why the return carries no team, and what that costs.** `InitialSkill` is `{ name, skillMd,
files? }`, and `createSkillsCapability` seeds the array into one collection keyed by
`<name>/SKILL.md`. There is no team dimension anywhere on that path. Three options were weighed:

- **Carry provenance on the record** (a team field, or grouped-by-team return). Rejected: the
  collection key has no room for it, so nothing downstream could read it. It would be a field
  that exists only to be dropped at the seeding call — surface with no consumer, which is the
  thing this spec spends its Decisions refusing.
- **Defer the aggregate loader** until a consumer can keep the boundary. Coherent, and it is
  effectively Decision 1's close-the-issue alternative; noted there rather than duplicated here.
- **Keep the flat shape and state the limit.** Chosen, and Decision 3 states it: one namespace
  across all teams.

Giving skills a real per-team namespace means per-team *identity*, which the shipped name
validator refuses (§10, `D7`) and which reaches into collection keys, the activation store and
slash matching. That is a different, larger issue; this one must not half-build it.

**The two refusals, both at this one door** (tenet 5) — and nowhere else:

- **A name at two levels.** One pass over the assembled names after every level is read,
  producing one `errors` entry naming both paths. Every collision in a run is reported, not
  just the first, so an author fixes them in one pass.
- **A `SKILL.md` that writes `scope:`.** Refused by name, per Decision 2. Cheap to enforce and
  currently silent: `scope` is not a key the parser knows, so today it is preserved and
  ignored.

Both wordings live as shared message constants beside the workforce package's existing refusal
constants, so a second door — should one ever exist — cannot spell them differently.

**Scope mapping is documentation, not code.** `org/skills` → `scope: "org"`;
`teams/<id>/skills` → org-scoped, keyed by team. The reader does not write resources and must
not learn about scopes — it hands back records, and the app installs them into whichever
collection it defines. Say this in the docs; build nothing for it.

**Do not build a level registry, and do not build a parameterised slot reader.** Two levels are
known and fixed, so level-discovery for a third that does not exist is speculative surface
(tenet 3). The broader generalisation is now settled and should not be reopened here: rooms
left open whether the four conventions would collapse into one reader parameterised over slot
name and manifest filename; **resources (FIX-1354) answered no** — it is a file leaf
(`resources/<name>.md`) taking identity from the filename, with two roots. Skills is the fourth
sample and does not fit that generalisation either, from the opposite direction: it is
folder-per-thing like workers and rooms, but it has **no team nesting and no slot** — its root
is wherever the caller points it. Four samples, no common slot shape. **What is shared is
primitives** — the `classify` / structural-directory / segment-validation helpers rooms is
already extracting — and this issue consumes those, adding no generic walker.

**Leaf shape, for the record:** workers, rooms and skills are folder-per-thing; resources is a
file leaf, a deviation its spec argued and the Architect endorsed. Skills needs no deviation on
this axis and takes none. Per the epic's rule, **only one form is accepted per convention** —
this issue does not teach the skills reader to also accept `skills/<name>.md`.

### 8. Implementation sequence

1. **Fix the unreadable/absent conflation** in `readSkillsDirectory`. A `SKILL.md` that exists
   and fails to read reports what went wrong; only a genuinely missing one reports missing.
   → *verify:* the existing 8 `read-directory` tests pass **unmodified**, plus behaviour S1.
2. **Add the two refusal message constants** — duplicated name, and declared `scope:` — beside
   the workforce package's existing refusal constants. → *verify:* typecheck; both are imported
   by the loader, not re-spelled.
3. **Add `readWorkforceSkills`** on `@flow-state-dev/workforce/loader`, calling the existing
   reader once per level and adapting its errors to paths. Do **not** generalise the walk
   primitives into a slot reader (§7). → *verify:* behaviours S2–S4, **and** that the module
   contains no `readdir` of its own — team enumeration goes through the primitive FIX-1352
   extracts (`grep -c 'readdir' <the new module>` → `0`). A second inlined `teams/` loop is the
   failure this step exists to prevent, so it gets a check rather than a sentence.
4. **Export and document it** — `loader/index.ts`, the package README, and the docs surfaces
   in §11. → *verify:* an import from the package name resolves.
5. **Changesets — two entries, one per package.** `@flow-state-dev/workforce` `patch` for the
   new `readWorkforceSkills` export; `@flow-state-dev/orchestration` `patch` for the changed
   error message. → *verify:* the `.changeset/*.md` frontmatter names **both** package names; one
   entry naming only orchestration means the export never reaches installed consumers.

**Removals** — none. Nothing is superseded; if step 1 leaves a now-unreachable branch in the
skills reader, delete it in that step.

### 9. Edge cases & error handling

**Inherited from `readSkillsDirectory`, unchanged and not re-tested** — a folder with no
`SKILL.md`; a bad or missing `description`; a `name:` disagreeing with its folder; a skill
name breaking the naming rules; a symlink anywhere; editor droppings. These are that reader's
contract, already covered by its 8 tests.

**Inherited from the worker reader's walk** — an absent `teams/` or an absent `skills/` level
is an empty result, not an error; a level that exists and cannot be listed is reported under
its own path; a file where a folder belongs is skipped in silence; an unreadable `root`
throws.

**New to this issue:**

- A `SKILL.md` that exists but cannot be read reports the actual failure rather than "missing".
- A name declared at two levels lands in `errors` naming both paths; several collisions in one
  run all report.
- Two *different* teams declaring the same name — note this is **also** a collision under
  Decision 3, because the assembled set is one flat namespace. This is the case most likely to
  surprise an author, so its message must name both team paths explicitly rather than saying
  "already declared".
- A `SKILL.md` declaring `scope:` lands in `errors` naming the file, not a silent strip — and
  **only** when read through `readWorkforceSkills`. The same file read directly by
  `readSkillsDirectory` is unaffected, which is intended: that reader serves roots with no
  level, where there is no derived scope to contradict.

**One claim was corrected by running it.** An earlier draft said a collision is silent because
seeding *skips* a name already seeded. That was read from the source, and it was wrong. Run
(`C1`), the real behaviour is worse: the "already seeded" guard reads its record once before
the loop, so it never sees a name added during the same pass. Both declarations are written,
**the second overwrites the first**, the surviving row is the last one, and `ensureSeeded`
returns `void` — there is no channel a report could appear on. The seeded-names record even
lists `triage` twice.

The conclusion Decision 3 rests on is therefore confirmed and sharper than drafted: not "one is
skipped" but "the later one wins outright and the earlier is gone without trace." Decision 3 is
settled evidence, not a premise for the implementer to check.

**Behaviours to test** (TDD, per the Feature label):

- **S1.** A `SKILL.md` that exists and cannot be read reports the failure, not "missing"; a
  genuinely absent one still reports missing. (Regression for step 1.)
- **S2.** `readWorkforceSkills` assembles org-level and team-level skills into one
  `InitialSkill[]`; an absent level is empty rather than an error; a level that exists and
  cannot be listed lands in `errors` under its own path; a per-skill error is re-keyed onto
  that skill's full path.
- **S3.** A name declared at two levels lands in `errors` naming both paths and is not
  silently resolved; two collisions in one run both report; two different teams colliding
  reports with both team paths.
- **S4.** A `SKILL.md` declaring `scope:` is refused by name through `readWorkforceSkills`, and
  the same file read through `readSkillsDirectory` still loads — the refusal is at the
  workforce door, not in the shared reader.

**Regression guard:** the existing 8 `read-directory` tests and the workforce loader/hire
suites pass **unmodified**. A diff touching them means step 1 changed more than the defect.

**What happens to the POC — it is deleted, not graduated.** The two `test/_fix1356/`
directories live on this branch only and **must not reach the implementation PR.** They
characterize behaviour this issue *changes* (`D3`, `C1`), so graduating them would pin the bug
as the contract. Their replacements are S1–S4, written fresh against the new behaviour. Step 1
of §8 therefore starts by deleting both directories; if the implementation branch is cut from
this one rather than from `main`, that deletion is the first commit. The only case worth
carrying forward is `R47`'s identity-agreement check, and `read-directory.test.ts` already
covers it — so nothing is actually lost. Their `console.log` output is gated behind
`FIX1356_LOG` so they are silent in an ordinary run.

### 12. Dependencies, open questions & follow-ups

**Dependencies.** None blocking. This touches `packages/workforce/src/loader/` and one function
in `packages/orchestration/src/skills/read-directory.ts`. FIX-1352 (rooms) also adds to
`workforce/src/loader/` and **extracts the shared walk primitives** there; if both are in
flight, sequence this PR after it and consume those primitives rather than re-deriving a walk.
**Primitives only** — not a reader parameterised over slot name and manifest filename (§7).
FIX-1342 works on `hire.ts`, which this does not touch.

**Does "unknown keys verbatim" let a file overwrite something the framework derives? For skills,
no — run, not reasoned.** This is the epic's rule-4-vs-rule-7 hole (raised on FIX-1351 §12 by the
resources spec, where a declared `ref:` redirected a storage row and a YAML `stateSchema:`
constructed and then failed at `safeParse`). Skills is **not** exempt by the easy argument —
it derives **two** fields, not one:

| Derived | From | Can frontmatter displace it? |
| --- | --- | --- |
| `name` | the folder | **No** — a disagreeing `name:` is *refused* (`R47`), not silently obeyed or corrected |
| `files` | the directory walk | **No** — a declared `files:` never becomes a file entry; the walked list stands, and no error is raised because nothing collided (`R47`) |

**The structural reason, which is stronger than either guard.** Frontmatter only ever becomes
*state*. The record's derived fields — `name` and `files` — are built from the folder name and
the walk, on a different data path that frontmatter cannot reach. They do not share a
destination, so there is no ordering slip to get wrong and nothing to allowlist. That is why
skills needs no "refuse the whole derived set" message: the set is two, and both are closed by
construction rather than by enumeration.

**So the hole is two-of-three, not three-of-three** — resources and (per its own spec) rooms are
exposed where a derived field and a declared field share a destination; skills is not. Worth the
epic knowing, since it bears on whether the general rule needs to become a universal one.

The one thing this issue *does* newly derive is the scope, and it has no such separation —
scope would be read from the path while `scope:` sits in frontmatter — which is exactly why
Decision 2 refuses that key by name rather than relying on construction.

**Closed, not deferred — the parameterised slot reader.** Rooms' §12 left a follow-up: revisit
the generalisation when the third convention is built. Resources (FIX-1354) was that sample and
answered no, and skills is the fourth and also does not fit. **This spec closes that follow-up
rather than re-deferring it**; reopening it needs a fifth convention that actually is
slot-shaped, not another round of the same question.

**Deferred, and named so nobody builds it here — binding a seat's `skills:` list at runtime.**
A seat declaring `skills: [port-scan]` gets that list as ordinary settings; nothing turns it
into a live skills binding on the seat's generator. That is deliberate and it is not a file
convention: the flow kind's `configSchema` claims `skills`, and how a kind wires it to
`createSkillsCapability` is the kind's business. It belongs to **FIX-1357** (kinds + blocks
boot scan) or the lab Proof, whichever first hires a seat that must actually *use* a skill.
The atlas reserves `usesSkills` on the worker contract for this; do not spend it here.

**Raised to the epic, not decided here — team skills have no per-team namespace, and the atlas
does not confront it.** The atlas gives `teams/<id>/resources/` an explicit **"org + team key"**
but gives `teams/<id>/skills/` only *"same `SKILL.md` wiring, this team"* — it names a mechanism
rather than a key, and that mechanism (`readSkillsDirectory` → `initialSkills` → a bare-name
collection) has no team dimension at all. So the atlas does not *promise* team-keyed skills, and
this spec does not contradict it; but "this team" reads like ownership-with-isolation and
delivers ownership only. Decision 3 states the consequence plainly so an author does not
discover it when their second team cannot name a skill `review`. **Whether that is good enough
for the lab Proof is the epic's call, not this issue's** — and if the answer is no, the fix is
per-team skill identity, which is a larger issue that Decision 1 deliberately forecloses here.
Noted on FIX-1351.

**Raised to the epic, not decided here — the four conventions will not be symmetrical, and the
epic should say so once.** Rooms, channels and resources are new and share a shape; skills are
older and external and do not. FIX-1352 already anticipated this ("it is evidence the
convention shape is real. It is not shared code"). The epic is the right place to record that
three-of-four is the intended end state, so the next reader does not file it as drift. Noted
on FIX-1351; not settled inside this spec.

**Follow-up, deliberately not done now.** If a third level ever appears (a per-worker
`workers/<name>/skills/`, which the atlas lists as a *named gap* pending member-identity work),
revisit whether the level list should become data. With two fixed levels it should not.

## Spec evolution

- **Spec drafted** — framed as a reconciliation rather than a greenfield convention, because a
  skills file convention already ships as an external open format with live consumers. The
  approach ratifies it and adds only the missing cross-level collision refusal plus one real
  defect fix; the build is one new export in `workforce` that calls the existing skills reader
  once per level.
- **After the epic's rule-4-vs-rule-7 finding** — ran whether frontmatter can displace a derived
  field. It cannot: skills derives two fields (`name`, `files`) and both are built on a data path
  frontmatter never reaches, so the hole resources hit is two-of-three conventions, not three.
  Recorded in §12 with what was run, rather than adopting a refusal skills does not need.
- **After review flagged the flat catalog** — Decision 3 was presented as a design choice
  (*refuse, don't prioritise*) and it is not one: skills seed into a single bare-name-keyed
  collection, so two same-named skills have nowhere to both exist and the only alternative to
  refusing is today's silent overwrite. Re-drafted as forced rather than chosen, and the
  user-visible consequence it had been burying — **skill names are globally unique across an
  app's teams** — is now stated in §2 and carried by the decision. Also corrected the changeset
  plan: the new export and the error fix live in different published packages and need one
  entry each.
- **After running the premise under Decision 3** — the claim that a duplicate skill name is
  resolved silently was drafted from *reading* `seeding.ts` and said the later one is skipped.

  earlier, which disappears without trace. The decision is unchanged and better supported; §10
  now records the correction rather than the original reasoning.
- **After the resources spec (FIX-1354) cleared** — added the derived-scope refusal to Decision
  2, because resources confirmed the derived-status rule for a third time and skills had the
  same silent hole (`scope:` in a `SKILL.md` is preserved and never read). Also closed rooms'
  parameterised-slot-reader follow-up outright instead of re-deferring it: resources is not
  slot-shaped and skills has no slot at all, so four samples produce no common shape, and what
  this issue consumes from the rooms extraction is primitives only.
