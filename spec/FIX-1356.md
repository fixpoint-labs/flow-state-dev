# FIX-1356: W3 — Skills file convention — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

W3 is giving three things a file convention — channels, resources, and skills — so an
app can describe a whole team in files instead of in code. Two of them start from nothing.

Skills do not. A skills file convention already ships: a folder with a `SKILL.md` in it. It is
public API, documented across five pages of our site, used by an app in this repo, and the
file format is not ours — it is the open Agent Skills format, whose portability our docs
promise in both directions.

So the real question is not what convention skills should have. It is: **the one they have
doesn't look like its two new siblings — does that matter?**

**Why now** — the other two are being written this week. Left unscoped, an issue with this
title resolves one of two bad ways: it aligns skills to the sibling shape and breaks a
published format for symmetry, or it adds a second skills reader beside the first, which the
issue's own words forbid. Both are cheap to rule out now and expensive to unpick later.

### 2. Solution in plain terms

**Ratify the convention skills already have, and add only the rule that is genuinely missing.**

Two facts do most of the work, both executed rather than assumed (§10). A seat can already
name its skills in a file: a `WORKER.md` saying `skills: [port-scan, triage]` loads and hires
today. And a skills folder can already sit at any level, because the existing reader takes a
root — which is what our own internal atlas prescribes: the same wiring aimed at a different
level, not a skills package per level.

**Skills are read per seat, not per app.** A seat sees the union of three levels: the org's
skills, its own team's, and any sitting beside the worker itself (`workers/<name>/skills/`),
which are **available without being listed** in `skills:`. That union is what gets registered
when the seat boots.

Reading per seat is what makes teams isolated. Each seat's catalog is its own, so two teams can
both have a `review` and neither can see the other's — run, not reasoned (§10, `I1`). The team
folder is a boundary, not merely a label.

What is missing is the rule for **one name appearing twice in a single seat's own view** — org
and team both declaring `triage`, say. There the union really does hold one name twice, and
today the second silently overwrites the first with nothing said (§10, `I2`).

So this ships three things: the levels a seat draws from, written down; one thin read that
assembles a seat's union and refuses a name appearing in it twice; and one defect fix — a
`SKILL.md` that exists but cannot be read is currently reported as *missing*, which sends an
author to the wrong fix.

**Philosophy.** Tenet 2 (composition over features): a skills level is the existing reader
pointed at a folder. Tenet 3 (earn every addition): the only new behaviour is the refusal.
Tenet 5 (one convergence point): it lives at the one door every level passes through.

**Worth naming, because it cuts against shipping anything:** strip the refusal and what remains
is documentation, and this issue could close instead. Decision 1 is where you buy that.

### 6. Decisions & rules — the sign-off surface

1. **Skills keep the convention they have. It is ratified, not aligned** — so this issue is much
   smaller than its title suggests.
   *Rejected:* bringing the skills reader onto the worker/channel shape. It fails on four
   independent counts, each measured in §10: the walk change breaks every existing skills
   folder, including this repo's own 38 and every documented example; re-keying its errors is a
   breaking change to a published package bought for cosmetic symmetry; the dot-joined
   `team.name` identity the siblings mint is refused by the shipped skill-name validator, which
   also gates collection keys, activation and slash matching; and the format is external and we
   advertise its portability.
   *Locks in:* three conventions, two sharing a shape and one not, on the record as deliberate.
   Reversing later costs a migration for every app with a skills folder — so this is the
   reversible order, not merely the cheap one.

2. **Teams are isolated at registration, not at identity. A seat's skills are the existing
   reader pointed at each level that seat can see — org, its own team, and its own folder —
   assembled into that seat's own catalog. No second reader, no `scope: "team"`, and a
   `SKILL.md` that writes `scope:` is refused by name.**
   *Rejected:* per-team skill *identity* — a dot-joined `<team>.<name>`. The shipped validator
   refuses it (§10, `D7`), and it reaches into collection keys, the activation store and slash
   matching. Isolation does not need it: two catalogs with different prefixes do not share
   storage keys, so two teams' `review` never meet (§10, `I1`). Also rejected: a
   `readTeamSkillsDirectory` beside the existing one — a second reader is what the issue
   forbids. Also rejected: letting a file declare its own scope. Today `scope:` is not a key the
   parser knows, so it is silently preserved and ignored — an author can write it, be wrong, and
   never be told.
   *Locks in:* a level is a path, and isolation is **where a catalog is registered**, not what a
   skill is called. Bare names stay bare; the Agent Skills format is untouched; `"team"` does not
   become a fourth resource scope. The refusal lands at the **workforce loader's door only**, not
   in `readSkillsDirectory` — that reader also serves roots with no workforce tree and no level,
   where the rule has nothing to say, and Decision 1 keeps it untouched.
   *Worker-colocated skills are auto-available.* A skill beside the worker is in that seat's
   union without being listed in `skills:`, because the folder already says whose it is; making
   an author repeat it in frontmatter would be the only place in the convention where sitting
   somewhere is not enough.

   *This is the epic's derived-status rule, on its fourth convention — counting the shipped
   `WORKER.md` alongside the epic's three new ones.* `WORKER.md` refuses `persona:`, `CHANNEL.md`
   refuses `system:`, a resource file refuses its derived set, and a `SKILL.md` now refuses
   `scope:` — same discipline, same reason: a status the framework grants is read from where the
   file sits, never from what it says.

3. **One skill name appearing twice in a single seat's own view is refused, naming both paths.
   Across teams there is no collision at all.**
   *This narrows an earlier refusal, and retracts the argument under it.* The spec previously
   said the refusal was *forced* — that skills seed into one bare-name-keyed collection, so two
   same-named skills have nowhere to both exist. That premise was true only of **one app-wide
   catalog**, which the spec had assumed rather than established. Read per seat, it dissolves:
   each catalog carries its own prefix, and `teams/alpha/skills/review/SKILL.md` and
   `teams/beta/skills/review/SKILL.md` are simply different keys (§10, `I1`). **"Globally unique
   across an app's teams" is withdrawn.**
   What survives is the narrower case: org and team — or team and worker-local — both declaring
   `triage` inside *one* seat's union. That union is one catalog, so the old argument applies
   there, and run (§10, `I2`) the later declaration overwrites the earlier with nothing reported.
   *Rejected:* **a precedence rule** — worker-local beats team beats org. This is now genuinely
   available where the spec previously said it was not: a seat's union is assembled by one
   registrar in a known order, and seeding is last-wins (§10, `I2`), so the order alone would
   implement it. It is rejected on merit, not availability. Precedence resolves the clash
   *silently*, and silent resolution is the exact defect this issue exists to remove — an author
   with `triage` at two levels would still have no idea which one is live. Refusing is also the
   reversible direction: a refusal can be relaxed into an opt-in override later without breaking
   anyone, while a precedence rule cannot be tightened once apps depend on shadowing.
   *Also rejected:* overwriting silently, which is today's behaviour.
   *Locks in:* **a seat cannot see one skill name twice.** Two teams may each have a `review`; one
   seat may not draw `triage` from both org and its team. The fix an author reaches for is a
   rename or a deletion, named for them in the error.

**Non-goals** — a second skills reader; any change to the `SKILL.md` format, the skill-name
rules, or the reader's `{ name, error }` contract; a `scope: "team"`; team-qualified skill
identity; and skills declared in code.

**The registration half is a non-goal too, and this is the load-bearing one.** This issue ships
the **read** side — assembling a seat's union and refusing a name twice inside it. Actually
*creating* each seat's catalog at hire (and binding a seat's `skills:` list, its auto-included
local folder, and any default skill to a live capability) is the flow kind's job and is **not
built here** — see §12, which routes it and names what is not yet settled. The spec states the
boundary; it does not pretend to have wired it.

**Size:** Small — 2 production files · 4 test behaviours · 2 doc surfaces · 1 PR.

### 3. Tradeoffs & alternatives

**The simpler approach, and it is close to right: close the issue.** Skills have a working
convention, a seat can already declare its skills, and every level already reads. On that
reading, W3's skills row is satisfied by two paragraphs of documentation.

What tips it is the collision rule. It is behaviour that does not exist, it is silent when it
bites, and it is the one part a user cannot cheaply fix: concatenating a seat's three reads is a
few lines, but noticing that `triage` came from two of them and one copy vanished is not
something an author discovers until a seat behaves like the wrong skill. If review disagrees
that this clears the bar, closing is a coherent outcome and Decision 1 is where to say so.

**Aligning the reader to its siblings** is rejected in Decision 1. The one piece worth keeping
is the defect: the siblings keep *unreadable* and *absent* apart deliberately, the skills reader
collapses them, and that is a bug rather than a difference of taste. It ships here on its own.

**Folding skills into the lab Proof (FIX-1355)** is coherent — the Proof is where a team's skills
first get exercised, and it would prove the convention instead of asserting it. It loses
narrowly: the collision rule is cheaper to settle before the levels exist in a real tree, and
the Proof should be spending its attention on whether three seats fan in.

**This alternative got stronger with the rewrite, and the spec should say so rather than let it
pass.** Under the old direction the new export was callable the moment it shipped. Under
per-seat registration its only real consumer is the registrar, which is now explicitly out of
scope (§6 non-goals, §12) and is a larger piece of work than it sounds (§10, `L2`). So
`readSeatSkills` would land with **no caller in the tree** until FIX-1357 or the Proof picks it
up. That does not change the recommendation — the defect fix is independent and the collision
rule is still cheapest to settle now — but it moves the close-or-defer option from *close to
right* to *closer still*, and it is the honest reading of what a reviewer is being asked to
approve.

### 4. Focus practices

- **BP-003 (verification evidence).** Every claim the recommendation rests on is executed, and
  the POC is on this branch so a reviewer can re-run it. That matters more than usual here: the
  case for *not* building the obvious thing is only as good as the measurements under it.
- **BP-030 (tolerate the old shape).** This touches a reader that already ships with documented
  consumers. Its error entries, flat walk and options keep working; its suite is the contract
  and is not rewritten to fit.
- **Tenet 5 (one convergence point).** The refusal gets one door. Do not also enforce it in a
  per-level helper.
- **BP-022 (release notes).** This change straddles **two published packages, so it needs two
  `patch` changeset entries, not one** — the error-message fix is in
  `@flow-state-dev/orchestration`, the new `readSeatSkills` export is in
  `@flow-state-dev/workforce`, and they version separately. Attributing both to orchestration
  would ship the fix and leave the export unreleased to installed consumers — a change that
  looks complete and silently does not arrive.

### 5. What using it looks like

An app keeps shared skills at the org level, a team's beside that team, and a seat's own beside
the worker. Two teams can both have a `review`; they are different skills and never meet.

```
workforce/org/skills/triage/SKILL.md
workforce/teams/pentest/skills/port-scan/SKILL.md
workforce/teams/pentest/skills/review/SKILL.md
workforce/teams/audit/skills/review/SKILL.md          # a different `review`. No clash.
workforce/teams/pentest/workers/recon/WORKER.md
workforce/teams/pentest/workers/recon/skills/sweep/SKILL.md   # auto-available to recon
```

The seat names the shared skills it wants. **It does not list `sweep`** — a skill beside the
worker is already the seat's:

```md
---
description: Recon seat.
flow: seat
skills: [port-scan, triage]
---
Find things and write them down.
```

Reading one seat's view is one call, handing back what `initialSkills` already takes:

```ts
import { readSeatSkills } from "@flow-state-dev/workforce/loader";

// org ∪ teams/pentest ∪ workers/recon — the levels this one seat can see.
const { skills, errors } = await readSeatSkills("./workforce", {
  team: "pentest",
  worker: "recon",
});
if (errors.length) throw new Error(/* same fail-on-errors shape as workers */);
```

```ts
skills; // InitialSkill[] — the same records readSkillsDirectory returns
// [ { name: "triage",    skillMd: "---\ndescription: …", files: [] },
//   { name: "port-scan", skillMd: "---\ndescription: …", files: [] },
//   { name: "review",    skillMd: "---\ndescription: …", files: [] },
//   { name: "sweep",     skillMd: "---\ndescription: …", files: [] } ]
```

The `audit` team's `review` is absent, because this seat cannot see it. That is the isolation:
it comes from *what was read*, not from what anything is named.

One name reaching a single seat twice stops the app instead of picking a winner:

```ts
errors;
// [{ path: "teams/pentest/skills/triage",
//    error: Error('Skill "triage" reaches seat "recon" from two levels — org/skills/triage
//                  and teams/pentest/skills/triage. Remove one: there is no precedence
//                  rule.') }]
```

Note what is *not* an error: `pentest/review` and `audit/review` coexist untouched. The refusal
is scoped to one seat's view, so it fires only where a seat would genuinely be ambiguous.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

**The divergence, and the call on each.** Five axes on which the shipped skills reader differs
from the worker/channel shape. Middle column is what the siblings do; right column is the call.
**The evidence for every row is §10's table** — it is not repeated here.

| What | Sibling shape | Call |
| --- | --- | --- |
| Walk | `teams/<id>/<slot>/<name>/` | **Keep flat.** The reader takes a root; the level is the caller's choice. Changing it breaks every existing skills folder. |
| Error key | slash-separated `path` | **Keep `name`.** Published API, documented. The new multi-level load reports by `path`, since it is the thing that knows about levels. |
| Unreadable vs absent | kept apart | **Fix.** A present-but-unreadable `SKILL.md` reports as missing today. Genuine defect; the only behaviour change to the existing reader. |
| Identity | dot-joined `<team>.<name>` | **Keep bare.** The shipped name validator refuses dots, and it gates collection keys, the activation store and slash matching. |
| Package split | node reader on `./loader` | **Keep as is.** `orchestration`'s root is deliberately the Node-reaching entry and `./tasks` is the browser-safe one — the inverse of `workforce`'s split, on purpose and documented in its index. |

Two things the conventions **already agree on**, and neither needs work: they share one
frontmatter dialect (both parse through the same `splitFrontmatter` / `parseFrontmatterYaml`
from `orchestration`), and both require a non-empty `description` while carrying unknown keys
through verbatim. The folder is the identity in both; skills enforce it by *agreement* (a
`name:` that disagrees with its folder is refused) rather than by refusing the key, which is a
stricter, better version of the same rule and stays.

**Where the new code goes.** `workforce`, not `orchestration`, and on the `./loader` subpath
beside the worker reader. The reason is ownership: what is being added knows about *the
workforce tree* — that `org/skills`, `teams/<id>/skills` and `workers/<name>/skills` are the
levels — and nothing about how a skill is parsed or stored. `orchestration` owns skills and must
not learn the workforce tree; `workforce` already depends on `orchestration` and already walks
this tree.

**The one new export.** `readSeatSkills(root, { team, worker })` → `{ skills, errors }`.

- Reads `<root>/org/skills`, `<root>/teams/<team>/skills` and
  `<root>/teams/<team>/workers/<worker>/skills` by calling **`readSkillsDirectory` unchanged**,
  once per level. The worker level needs no opt-in: it is included because it is the seat's.
- A level that is absent is not an error (an app may have no org skills, and a seat may have no
  skills of its own). A level that exists and cannot be read is, reported under its path — the
  `openStructuralDirectory` discipline the worker reader already has.
- Re-keys each level's `{ name, error }` entries onto `{ path, error }` using that level's
  path, so a caller can tell which level broke. This is the adapter, not a new contract.
- Refuses a name that appears in the assembled union more than once, naming both paths.
- Returns `InitialSkill[]` — the existing record, which is what `initialSkills` takes. **No new
  record type.**

**Why the return still carries no team, and why that is now the right shape.** `InitialSkill` is
`{ name, skillMd, files? }` and carries no team dimension. Under the old app-wide reading that
was a *limitation* the spec had to apologise for. Under per-seat reading it is simply correct:
the return is already scoped to one seat, so a team field on the record would restate what the
call arguments already said. Provenance that a caller does need — which level a skill came from
— is on the `errors` entries, where it is actionable.

**Isolation is a property of registration, and this issue does not perform it.** The mechanism
is that each seat's catalog is created with its own collection prefix; two prefixes do not share
storage keys (§10, `I1`). Two things about that are worth stating precisely, because the spec
must not overclaim:

- **The L1 surface already supports it.** `createSkillsLibrary` takes `collection`, `scope` and
  `collectionConfig.prefix` today, and the collection pattern is `${prefix}/**` (§10, `L1`). No
  new identity machinery, no change to the bare-name validator, no dot-joined form.
- **The wiring that gives each seat its own prefix does not exist yet.** A skills library is
  built once per *flow kind*, at module scope, and `hireWorkforce` mints every seat of a kind
  from that one factory (§10, `L2`). Making the catalog per-seat is the runtime-bind work, and
  it is **routed out of this issue** (§12). What FIX-1356 owes that consumer is a read shaped
  per-seat, which is what this export is.

One route is worth ruling out explicitly so the follow-on does not spend a day on it: a
*parameterised* collection pattern (`skills/[seatId]/**`) cannot carry skills, because the
skills code seeds with a string key and a parameterised pattern refuses one (§10, `L3`). The
available route is a distinct prefix per library instance.

Per-seat catalogs do mean a team's skills are stored once per seat rather than once per team.
That is real and accepted: seats per team are small in the lab Proof, and the alternative —
sharing a team catalog while overlaying worker-local skills — needs two collections per seat and
a merge at read time, which is more machinery than the duplication costs.

**The two refusals, both at this one door** (tenet 5) — and nowhere else:

- **A name twice in one seat's union.** One pass over the assembled names after every level is
  read, producing one `errors` entry naming both paths. Every collision in a run is reported,
  not just the first, so an author fixes them in one pass. The pass is per seat, so two teams
  holding the same name is not a collision and must not be reported as one.
- **A `SKILL.md` that writes `scope:`.** Refused by name, per Decision 2. Cheap to enforce and
  currently silent: `scope` is not a key the parser knows, so today it is preserved and
  ignored.

Both wordings live as shared message constants beside the workforce package's existing refusal
constants, so a second door — should one ever exist — cannot spell them differently.

**Scope mapping is documentation, not code.** Every level a seat reads lands in that seat's own
catalog, which the app installs at whatever scope it defines — `"org"` by default. The reader
does not write resources and must not learn about scopes: it hands back records. Say this in the
docs; build nothing for it.

**Do not build a level registry, and do not build a parameterised slot reader.** Three levels
are known and fixed, so level-discovery for a fourth that does not exist is speculative surface
(tenet 3). The broader generalisation is now settled and should not be reopened here: channels
left open whether the conventions would collapse into one reader parameterised over slot
name and manifest filename; **resources (FIX-1354) answered no** — it is a file leaf
(`resources/<name>.md`) taking identity from the filename, with two roots. Skills — the fourth
sample, counting the shipped `WORKER.md` alongside the epic's three new conventions — does not
fit that generalisation either, from the opposite direction: it is folder-per-thing like workers
and channels, but it has **no slot of its own** — its root is wherever the caller points it.
Four samples, no common slot shape. **What is shared is
primitives** — the `classify` / structural-directory / segment-validation helpers channels is
already extracting — and this issue consumes those, adding no generic walker.

**Leaf shape, for the record:** workers, channels and skills are folder-per-thing; resources is a
file leaf, a deviation its spec argued and the Architect endorsed. Skills needs no deviation on
this axis and takes none. Per the epic's rule, **only one form is accepted per convention** —
this issue does not teach the skills reader to also accept `skills/<name>.md`.

### 8. Implementation sequence

1. **Fix the unreadable/absent conflation** in `readSkillsDirectory`. A `SKILL.md` that exists
   and fails to read reports what went wrong; only a genuinely missing one reports missing.
   → *verify:* the existing 8 `read-directory` tests pass **unmodified**, plus behaviour S1.
2. **Add the two refusal message constants** — duplicated name, and declared `scope:` — beside
   the workforce package's existing refusal constants. → *verify:* typecheck; both are imported
   by the loader, not re-spelled.
3. **Add `readSeatSkills`** on `@flow-state-dev/workforce/loader`, calling the existing
   reader once per level for the seat named in the arguments and adapting its errors to paths.
   Do **not** generalise the walk primitives into a slot reader (§7). → *verify:* behaviours
   S2–S5, **and** that the module contains no `readdir` of its own — path enumeration goes
   through the primitive FIX-1352 extracts (`grep -c 'readdir' <the new module>` → `0`). A
   second inlined `teams/` loop is the failure this step exists to prevent, so it gets a check
   rather than a sentence.
4. **Export and document it** — `loader/index.ts`, the package README, and the docs surfaces
   in §11. → *verify:* an import from the package name resolves.
5. **Changesets — two entries, one per package.** `@flow-state-dev/workforce` `patch` for the
   new `readSeatSkills` export; `@flow-state-dev/orchestration` `patch` for the changed
   error message. → *verify:* the `.changeset/*.md` frontmatter names **both** package names; one
   entry naming only orchestration means the export never reaches installed consumers.

**Removals** — none. Nothing is superseded; if step 1 leaves a now-unreachable branch in the
skills reader, delete it in that step.

### 9. Edge cases & error handling

**Inherited from `readSkillsDirectory`, unchanged and not re-tested** — a folder with no
`SKILL.md`; a bad or missing `description`; a `name:` disagreeing with its folder; a skill
name breaking the naming rules; a symlink anywhere; editor droppings. These are that reader's
contract, already covered by its 8 tests.

**Inherited from the worker reader's walk** — an absent `teams/`, an absent `skills/` level, or
a seat with no folder of its own is an empty result, not an error; a level that exists and
cannot be listed is reported under its own path; a file where a folder belongs is skipped in
silence; an unreadable `root` throws.

**New to this issue:**

- A `SKILL.md` that exists but cannot be read reports the actual failure rather than "missing".
- A name reaching one seat from two of its levels lands in `errors` naming both paths; several
  collisions in one run all report.
- Two *different* teams declaring the same name is **not** an error and must not be reported as
  one. Neither seat's union holds it twice, so there is nothing ambiguous to refuse. This is the
  case most likely to be got wrong by an implementer carrying the old flat-catalog reading, so
  it gets an explicit behaviour (S3) rather than a sentence.
- A seat's own folder and its team both declaring a name **is** a collision, and refuses. It is
  the case an author is most likely to have meant as an override — the error therefore names
  both paths and says plainly that there is no precedence rule, so the intent fails loudly
  instead of half-working.
- A `SKILL.md` declaring `scope:` lands in `errors` naming the file, not a silent strip — and
  **only** when read through `readSeatSkills`. The same file read directly by
  `readSkillsDirectory` is unaffected, which is intended: that reader serves roots with no
  level, where there is no derived scope to contradict.

**One claim was corrected by running it.** An earlier draft said a collision is silent because
seeding *skips* a name already seeded. That was read from the source, and it was wrong. Run
(`C1`), the real behaviour is worse: the "already seeded" guard reads its record once before
the loop, so it never sees a name added during the same pass. Both declarations are written,
**the second overwrites the first**, the surviving row is the last one, and `ensureSeeded`
returns `void` — there is no channel a report could appear on. The seeded-names record even
lists `triage` twice.

skipped" but "the later one wins outright and the earlier is gone without trace." What changed
in the rewrite is *where that applies* — `I1` shows it is not the cross-team case, and `I2`
shows it is still the within-one-seat case. Both are settled evidence, not premises for the
implementer to check.

### 12. Dependencies, open questions & follow-ups

**Dependencies.** None blocking. This touches `packages/workforce/src/loader/` and one function
in `packages/orchestration/src/skills/read-directory.ts`. FIX-1352 (channels) also adds to
`workforce/src/loader/` and **extracts the shared walk primitives** there; if both are in
flight, sequence this PR after it and consume those primitives rather than re-deriving a walk.
**Primitives only** — not a reader parameterised over slot name and manifest filename (§7).
FIX-1342 works on `hire.ts`, which this does not touch.

**Does a file get to overwrite something the framework derives? For skills, no — run, not
reasoned.** This is the epic's rule-4-vs-rule-7 hole (raised on FIX-1351 §12 by the resources
spec). The rule as the epic is settling it — **a key the convention *consumes* is stripped; a key
it *derives* is refused** — sorts the skills surface cleanly, and the sort is what shows skills
is exempt. Skills derives more than one field, so the easy argument does not apply; each was run.

| Field | Kind | Shares the passthrough bag? | Result |
| --- | --- | --- | --- |
| `name` | derived (the folder) | **No** — sibling field on the record | A disagreeing `name:` is *refused*, not obeyed (`R47`) |
| `files` | derived (the walk) | **No** — sibling field on the record | A declared `files:` never becomes a file entry; the walked list stands (`R47`) |
| `_seededAt` | derived (framework-written) | **Yes** — skill *state* is flat | Derivation runs **after** the passthrough, so the framework's value wins over a declared one (`R47`) |
| `description`, `allowed-tools`, `agents`, `keywords`, … | **consumed** | yes | The author's own declarations. Nothing to strip or refuse — the convention reads them, it does not grant them |

**The structural reason, which decides it.** The record is `{ name, skillMd, files }` and
frontmatter only ever becomes *state*. The two derived fields live as siblings to the
passthrough, not inside it — the same shape that protects `WorkerManifest`'s minted `id`, and
the opposite of the resources case, where passthrough merged into the same object as the derived
fields. The one derived value that *does* share the flat state bag is protected by ordering
instead. So skills needs no "refuse the derived set" message: nothing of its derived set is
reachable from a file.

**No convention is exempt from the rule; what differs is which mechanism discharges it.** Three,
in order of preference — and the table above is one row of each:

1. **Shape** — the derived field is a *sibling* to the passthrough bag, so a declared key has
   nowhere to land (`name`, `files`; `WorkerManifest`'s minted `id`).
2. **Ordering** — it shares the bag, but derivation runs *after* the passthrough, so the
   framework's value wins (`_seededAt`; resources' apply-after-allowlist).
3. **Explicit refusal** — neither applies, so the key is refused by name (skills' new `scope:`,
   below; channels' `system:`; resources' derived set).

Stated that way it is checkable by the next convention — **for each field you derive, name which
of the three protects it** — rather than a count that goes stale the moment a fifth convention
lands.

**The one thing this issue newly derives lands on mechanism 3.** The scope comes from the level,
and it has neither shape nor ordering protecting it — it would be read from the path while
`scope:` sits in frontmatter, flattened together. That is precisely why Decision 2 refuses the
key by name rather than relying on construction: the rule applied, not an extra.

**Resolved, no longer an epic question — team skills *are* isolated.** An earlier revision raised
to the epic that `teams/<id>/skills/` bought ownership without isolation, and that the atlas's
*"same `SKILL.md` wiring, this team"* therefore over-read. That is withdrawn. Isolation comes
from reading per seat and registering into that seat's own catalog, not from keying a name, so
the atlas's wording turns out to be exactly right and needs no revision. Two teams' `review` are
different skills (§10, `I1`). Nothing is escalated here any more.

**Open question, not settled by this issue — which skill loads by default.** A seat's union may
be large, and *available* is not the same as *on*. Whether a default-skill declaration belongs on
`WORKER.md` (beside `skills:`) or on the flow kind is genuinely open, and it is not this issue's
to answer: this issue reads folders, and default-activation is an activation concern. Routed to
the runtime-bind follow-up below. **Named rather than quietly omitted**, because an author
reading §5 will reasonably ask it.

**The honesty gap, stated plainly: agent flow is not well defined, and this spec does not settle
it.** How an agent flow treats memory, and how it treats skills across turns, is not specified
anywhere today. Per-seat registration touches the edge of that — a seat's catalog is created
*somewhere*, at *some* lifetime — but this issue deliberately stops at reading folders and does
not propose an answer. **Nothing here should be read as defining agent-flow behaviour.** It needs
its own fence rather than being settled as a side effect of a file-convention ticket; raised to
the epic (FIX-1351) to be given one.

**Routed out of this issue — the runtime bind.** Creating each seat's catalog at hire, binding a
seat's explicit `skills:` list, auto-including its worker-local folder, and honouring any default
skill are one piece of work and belong to the seat / flow-kind layer: **FIX-1357, the lab Proof
(FIX-1355), or a dedicated agent-flow ticket**, whichever picks it up first. §10 `L2` records why
it cannot be a footnote here — a skills library is built once per flow kind at module scope, and
every seat of a kind is minted from that one factory, so per-seat catalogs are a real change to
how a seat's flow is constructed. §10 `L3` rules out the parameterised-pattern shortcut. This
issue ships the read side shaped to fit that consumer, and says so rather than implying the
boundary already exists.

**Raised to the epic, not decided here — the epic's three new conventions will not be
symmetrical, and the epic should say so once.** Channels and resources are new and share a
shape; skills are older and external and do not. FIX-1352 already anticipated this ("it is
evidence the convention shape is real. It is not shared code"). The epic is the right place to
record that two of its three new conventions sharing a shape is the intended end state, so the
next reader does not file it as drift. Noted on FIX-1351; not settled inside this spec.

**Follow-up, deliberately not done now.** If a *fourth* level ever appears, revisit whether the
level list should become data. With three fixed levels it should not. (The per-worker level the
atlas listed as a named gap is no longer a gap — this issue reads it.)

## Spec evolution

- **Spec drafted** — framed as a reconciliation rather than a greenfield convention, because a
  skills file convention already ships as an external open format with live consumers. The
  approach ratifies it and adds only the missing cross-level collision refusal plus one real
  defect fix; the build is one new export in `workforce` that calls the existing skills reader
  once per level.
- **After the epic's rule-4-vs-rule-7 finding** — ran whether frontmatter can displace a derived
  field, and re-sorted the surface under the epic's sharper wording (*consumed keys are stripped,
  derived keys are refused*). It cannot: the two record-level derived fields sit outside the
  passthrough bag, and the one that shares it is protected by deriving after it. Stated the
  durable way rather than as a count of exempt conventions — every convention is subject to the
  rule, and what differs is whether **shape**, **ordering**, or an **explicit refusal**
  discharges it per field. Skills uses all three: shape for `name`/`files`, ordering for
  `_seededAt`, and a refusal for the `scope:` key Decision 2 adds. Recorded in §12 with what
  was run.
- **After review flagged the flat catalog** — Decision 3 was presented as a design choice
  (*refuse, don't prioritise*) and it is not one: skills seed into a single bare-name-keyed
  collection, so two same-named skills have nowhere to both exist and the only alternative to
  refusing is today's silent overwrite. Re-drafted as forced rather than chosen, and the
  user-visible consequence it had been burying — **skill names are globally unique across an
  app's teams** — is now stated in §2 and carried by the decision. Also corrected the changeset
  plan: the new export and the error fix live in different published packages and need one
  entry each.
- **After running the premise under Decision 3** — the claim that a duplicate skill name is
  resolved silently was drafted from *reading* `seeding.ts` and said the later one is skipped.
  Running it showed the opposite mechanism and a worse outcome: the later one overwrites the
  earlier, which disappears without trace. The decision is unchanged and better supported; §10
  now records the correction rather than the original reasoning.
- **After the resources spec (FIX-1354) cleared** — added the derived-scope refusal to Decision
  2, because resources confirmed the derived-status rule for a third time and skills had the
  same silent hole (`scope:` in a `SKILL.md` is preserved and never read). Also closed channels'
  parameterised-slot-reader follow-up outright instead of re-deferring it: resources is not
  slot-shaped and skills has no slot at all, so four samples produce no common shape, and what
  this issue consumes from the channels extraction is primitives only.
- **After the Architect withdrew its clear on Decisions 2 and 3 — the direction changed.** The
  earlier clear (PR #1716, comment 5628576237) endorsed a flat app-wide catalog and the global
  name-uniqueness that followed from it. **That clear is withdrawn**, and the product call is
  that team skills are *isolated*: a seat registers the union of what it can see — org, its own
  team, and skills sitting beside the worker, which are auto-available without being listed.
  Decision 1 and the defect fix were untouched by the withdrawal and stand as written.

  **The argument under Decision 3 was wrong in a way the withdrawal did not name, and is
  retracted here.** The spec had claimed the refusal was *forced* — two same-named skills "have
  nowhere to both exist". That was true only if there is one app-wide catalog, which the spec
  assumed rather than established. Read per seat, two teams' `review` are different storage keys
  and the cross-team collision dissolves entirely (§10, `I1`). So Decision 3 **narrows rather
  than disappears**: a name reaching one seat from two of its own levels is still one catalog
  holding one name twice, and still resolves silently (§10, `I2`). Deleting the refusal outright
  would have dropped a real defect.

  Consequently **a precedence rule is now genuinely available where the spec said it never was**
  — a seat's union is assembled by one registrar in a known order and seeding is last-wins — so
  it is now carried as a named rejected alternative argued on merit (silent resolution is the
  defect this issue exists to remove; a refusal relaxes into an override later, an override
  cannot be tightened), not dismissed as impossible.

  Also: `readWorkforceSkills` as one flat merge-for-the-app was the wrong consumer shape and is
  now `readSeatSkills`; §12 stops escalating the no-namespace question (resolved) and instead
  names what this issue does **not** settle — default-skill placement, and agent-flow
  memory/skills, which needs its own fence. The registration half is an explicit non-goal, with
  §10 `L2`/`L3` recording why it cannot be a footnote.
