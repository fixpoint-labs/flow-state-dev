# FIX-1360: Kitchen-sink drift audit (chat-agent + skill activator) — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

Four specs are about to be written against an app nobody has re-read.

FIX-1359 ships an out-of-the-box `agent` flow kind, and the only working example of that shape
we own is `apps/kitchen-sink`'s `chat-agent` flow. Four sibling issues — the contract
(FIX-1361), the kind itself (FIX-1363), per-seat skills (FIX-1362) and memory (FIX-1364) — will
each need to know what that app actually proves. Without one shared answer, each author reads
the app independently, and four readings of a 60-file demo will not agree. Worse, they will
agree on the wrong things: `chat-agent` was built before the `WORKER.md` hire surface existed,
and the parts of it that look most like an agent are exactly the parts that have drifted.

The drift is not hypothetical. The single most load-bearing fact this audit found:
**nothing in `apps/kitchen-sink` hires anybody.** No file imports `hireWorkforce`, and no
`WORKER.md` is read anywhere in the app. So the closest working composition of the agent shape
we have proves a great deal about the *flow* and precisely nothing about the *seat*. An author
who ports from it without being told that will ship a kind that cannot be hired.

Why now: FIX-1360 is first in the epic's chain and FIX-1361 is blocked on it. Every day it is
not written is a day the chain is stopped, and every sibling spec written before it is a spec
that will need reconciling afterwards.

### 2. Solution in plain terms

Produce one short drift note — a characterization of `chat-agent` and its skill activator —
and put it where four agent authors working in four separate checkouts will actually find it.

The note answers three questions and nothing else:

- **What kitchen-sink still proves.** The pipeline shape, the up-front skill activator
  (FIX-421's lineage), per-generator skill scoping (FIX-911's lineage), cross-turn memory, and
  capability bundling. These are real and they work; port the shape.
- **What must be re-homed onto the agent kind.** The things kitchen-sink does by hand that a
  kind has to do from configuration: prompt composition off `instructions`, skill source tiers,
  and the config surface a `WORKER.md` fills in.
- **What is stale and must not be copied.** Two parallel skills entry points and two parallel
  memory entry points, of which kitchen-sink picked the heavy one both times; an app-flat,
  session-global skill catalog that is *not* the per-seat register FIX-1356 is landing; a
  storage layer that does not isolate what the register promises to isolate; and a large tail
  of demo machinery that is not agent-kind material at all.

**This spec is where the audit was done.** The research is in Part II §7 in full — that is the
note's content, and it is on this PR so the people who will consume it can argue with it before
four specs are written against it. Implementation is small: land it at a stable address and
mirror it to Linear.

**What it deliberately does not do.** It does not design the agent kind, choose the kind's id,
decide which package exports it, rewrite kitchen-sink, or invent a new activator. Two of the
audit's findings are recommendations *to* FIX-1361 and FIX-1362, offered with the evidence
behind them, not decisions taken here.

This leans on tenet 7 (*prove the goal, not the mock*) — the note reports what the code does,
verified by reading it, not what the app's own comments claim — and on tenet 3 (*name the
removals*): a drift note whose only content is "here is what works" is the failure mode, because
the expensive mistake downstream is copying, not omitting.

### 6. Decisions & rules — the sign-off surface

1. **The note lands as a repo doc at `docs/internal/design/kitchen-sink-agent-drift.md`,
   mirrored to the FIX-1360 Linear document.**
   *Alternative rejected:* a Linear comment only, which is what the issue originally asked for.
   The four consumers are agent authors working in separate git worktrees; they grep the repo,
   and a repo doc gets diffed, reviewed and updated with the code. `docs/internal/` is the
   established home for process artifacts and is not published to users.
   *What a wrong call costs:* a Linear-only note means four Linear fetches, no diff history, and
   no way for a later change to kitchen-sink to show up as a conflict against the note.

2. **The out-of-the-box agent kind's canonical paths are the light ones: the skills
   *library + binding* for skills, and the *read-side* memory capability for memory. The
   heavy halves — the per-turn LLM classifier tier and the full memory capture pipeline — are
   opt-in config, not defaults.**
   *Alternative rejected:* port kitchen-sink's composition as-is, which is what "port the shape,
   don't redesign" reads like if the note stays silent. Kitchen-sink runs both heavy halves.
   *What a wrong call costs:* two or more extra model calls on **every turn of every seat**, set
   as the default in the one place where a default becomes everybody's bill. Reversing it later
   is a breaking change to hired rosters, not a config edit.

3. **The note characterizes the kitchen-sink *spine* and explicitly rules the rest of
   `chat-agent` out of scope for the agent kind** — thinking-style pipelines, bias check,
   perspective capture, artifacts, the bash sandbox, MCP, the human-in-the-loop actions and
   voice.
   *Alternative rejected:* an exhaustive inventory of the app.
   *What a wrong call costs:* an exhaustive note reads as a porting checklist. The demo is
   roughly ten times the surface the kind needs, and a downstream author who treats "present in
   kitchen-sink" as "belongs in the default" ships an agent kind nobody can afford to hire.

**Size:** Small. One document, one PR, no code.

### 3. Tradeoffs & alternatives

**The honest objection, stated first: this issue's deliverable is a document, and so is a
spec.** The epic's own review raised it — FIX-1360 was challenged as "make it a research section
inside FIX-1363's spec" and kept as an issue because four specs cite it and one shared artifact
beats four independent re-readings. That reasoning holds, but it does mean the spec PR and the
deliverable are unusually close together. Two things keep them distinct and make the round-trip
worth its cost:

- **The audit needs review before it is consumed, not after.** Four specs will be written
  against these findings. Getting them argued with on a spec PR — by the bots and by the people
  who will consume them — is much cheaper than discovering in FIX-1363's implementation that the
  note pointed at the wrong skills entry point.
- **Decision 2 is a real product decision with a recurring cost**, and it is the kind of thing
  that gets made silently inside an implementation PR if nobody puts it up for sign-off.

If the reviewer's read is that this should have collapsed into FIX-1361 — that is a legitimate
call and §12 says what would change it.

**The alternative approach weighed and rejected: audit by characterization test rather than by
prose.** Pin kitchen-sink's behaviour in executable tests and hand those to the sibling specs.
Rejected because the question is not "what does it do" — the code answers that and the reading
took an afternoon — but "which parts of what it does should the default inherit". That is a
judgement, and a test cannot carry one. A test would also have pinned the app, which nothing in
this epic wants to do: kitchen-sink is characterization, not a contract.

**What this trades away.** The note is a point-in-time reading. Kitchen-sink will keep moving,
and nothing enforces that the note stays true. Accepted deliberately: its consumers are the four
specs in this epic, all of which are written within the epic's life. It is not documentation and
should not be maintained as if it were.

### 4. Focus practices (1–5)

- **BP-003 (verification evidence).** Every claim in the note names the file it was read from.
  The specific trap here is kitchen-sink's own comments: they are thorough and some of them
  describe intent rather than behaviour. A drift note that repeats a stale comment is worse than
  no note, because it launders it into four specs.
- **BP-039 (lead with the problem).** The note leads with what must not be copied, not with a
  tour of the app. The tour is the part a reader does not need.
- **Tenet 3 (name the removals).** The note's third section — what is stale — is the one that
  earns it. A note that only lists what works is a porting checklist with the warnings removed.

### 5. What using it looks like (1–5 examples)

No public API changes, so no usage examples in the framework sense. What "using it" means here
is a sibling spec citing it instead of re-reading the app:

> **Skills.** The agent kind binds skills through the library + binding path, not the standalone
> skills capability — see the drift note, *Two parallel skills entry points*. The per-turn LLM
> classifier tier is **not** on by default; kitchen-sink enables it and pays a generator call per
> turn for it.

### 6. (continued) — rules that are not decisions

- The note never uses "thin" or "fat" (epic theme 1). It says *seat*, *kind*, *worker*.
- The note recommends, and does not decide, anything the epic assigned to another issue —
  the kind's id and admission rule (FIX-1361), the skill merge and isolation rule (FIX-1362),
  the memory gap (FIX-1364), which package exports the kind (FIX-1361). Each recommendation
  carries its evidence so the owning issue can act without re-reading the app.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design — **this is the drift note's content**

The audit is done. What follows is the substance the implementation lands; the implementer's job
is to shape it into the document, not to re-derive it. Every claim below was read from the file
named.

#### 7.1 What kitchen-sink still proves

| Proves | Where | Why it matters to the kind |
|---|---|---|
| **The agent pipeline shape** | `apps/kitchen-sink/flows/chat-agent/run/run.ts` | `sequencer(...).tap(…) ×4 → .step(router) → .sideChain(…) ×3 → .tap(terminal)`. Pre-generator taps decide state, one step produces the answer, background side-chains do capture. This is the spine the kind ports. |
| **Up-front skill activation works (FIX-421 lineage)** | `createSkillActivator`, `packages/orchestration/src/skills/skill-activator.ts`; used at `run.ts` via `skillActivatorBlock` in `shared/capabilities/features.ts` | Three tiers — literal `/<skill>` slash prefix, keyword scan over `keywords` frontmatter, then an LLM classifier. Returns a `.tap()`-able sequencer that patches state and passes input through, so it drops into any chain. Tier 3 is opt-out via `enableLlmClassifier: false`. |
| **The activator and the reader agree via one state slot** | `features.ts` — activator `activeState: { scope: "session", field: "activeSkills" }` mirrored on the library binding | Matched skills land in `session.state.activeSkills`; the binding's formatter reads the same slot and injects bodies under `<skills>`. This handshake is the mechanism to re-home, whatever the scope ends up being. |
| **Per-generator skill scoping works (FIX-911 lineage)** | `createSkillsLibrary({ itemVisibility })` in `features.ts` | The library is attached as a **static** `uses` entry because dynamic `uses` callbacks contribute tools and context but **not resources** — the collection must install at build time. Visibility keeps worker generators inside patterns from replicating skill bodies. |
| **Cross-turn memory works** | `run/cognition.ts` (`system()` from `@flow-state-dev/memory`), `flow.ts` (`resources: { ...mem.userResources }`) | Four tiers (working/episodic/semantic/digest), capability on the generators, `captureFromItems` as a background `.sideChain`, resources registered flat on the flow per FIX-435. |
| **Capability bundling** | `featuresCapability` in `features.ts` | One capability composing static `uses`, a dynamic `uses` callback for the optional MCP surface, and a `presets` block for feature-gated tools. This is the shape the kind's default tool/context surface should take. |

#### 7.2 What must be re-homed onto the agent kind

1. **The pipeline becomes the kind's body, parameterized.** Kitchen-sink hand-wires the chain in
   application code. The kind owns the chain and takes its variable parts from configuration.
2. **Prompt composition moves onto `instructions`.** Kitchen-sink assembles its system prompt
   from `shared/prompts.ts` plus per-mode `*.prompt.md` files. The kind consumes
   `prompt: [default, instructions]` (epic theme 2) and **defines no second default-prompt
   config** — FIX-1344 part 2 owns shipping `default`, and until it lands the kind ships against
   `instructions` alone with an explicit seam.
3. **Skill sources become tiered.** Kitchen-sink reads exactly one app-flat directory
   (`apps/kitchen-sink/skills`) via `readSkillsDirectory` at module init. The kind registers
   `org ∪ teams/<thatTeam> ∪ workers/<thatSeat>` (epic theme 7; convention owned by FIX-1356,
   runtime bind by FIX-1362).
4. **Configuration moves into `configSchema`.** Kitchen-sink keeps model choice and feature flags
   in session state, mutated by dedicated `setSelectedModel` / `setThinkingEnabled` actions. The
   kind declares them on `configSchema` so `hireWorkforce` can fill them from `WORKER.md` — the
   shape already demonstrated by `workerAgentFlow` in `packages/workforce/test/hire.test.ts`
   (`configSchema: { instructions, model, tools }`).

#### 7.3 What is stale — do not copy blindly

**a. Kitchen-sink never hires. This is the biggest drift fact and belongs at the top of the
note.** No file under `apps/kitchen-sink` imports `hireWorkforce` or reads a `WORKER.md`. The app
proves the flow shape and proves nothing about the seat shape: no `configSchema`-driven
instantiation, no roster, no `flow:` resolution. Every hire-side claim a sibling spec makes has
to be grounded in `packages/workforce` — `hire.ts`, `manifest.ts`, `test/hire.test.ts` and the
hire README — never in kitchen-sink.

**b. Two parallel skills entry points, and kitchen-sink picked the heavy one.**

| Path | What it is | Kitchen-sink |
|---|---|---|
| `createSkillsLibrary` + `.with(binding)` + a separate `createSkillActivator` | Shared catalog as a resource collection; activation decided up front by the activator and read from a state slot | **Uses this** |
| `createSkillsCapability` + `readSkillsDirectory` | One capability carrying the collection, the `activeSkills` state fragment, the catalog tools, the body formatter, and a default-on `runSkill` preset for mid-flow activation | Not used |

They overlap heavily and their docs cross-reference each other; `createSkillsCapability`'s own
header notes you drop its `runSkill` preset when using up-front activation. **The note recommends
the library + binding path** as the kind's canonical one (Decision 2), because it is the path with
a working activator behind it and the one FIX-1362's per-seat register composes with. The final
call is FIX-1362's; the note gives it the comparison so it need not re-derive it.

**c. Two parallel memory entry points, and kitchen-sink picked the heavy one.**
`createMemoryCapability` is read-side only — tiers, the recall tool, section presets — and its own
header says to reach for it "when a flow only consumes memory", and for `system()` "when the flow
also captures". Kitchen-sink uses `system()` with all four tiers, capture, consolidation, prune
and the hygiene janitor. **The note recommends `createMemoryCapability` as the OOTB default**, with
capture opt-in (Decision 2).

**d. The cost of copying c and b together, stated as a budget.** Tier-3 activation is one extra
structured-output generator call per turn. `system()` capture is a background generator call per
turn plus periodic consolidation/prune/janitor chains. Ported as defaults that is two or more
extra model calls on every turn of every seat. The note states this explicitly — it is the reason
Decision 2 exists, and it is the note's answer to the implementer note routed from the epic PR.

**e. App-flat, session-global activation is not a per-seat register.** Kitchen-sink's active-skill
set lives at `{ scope: "session", field: "activeSkills" }` — one session-wide set shared by every
generator in the turn, over one flat catalog read from one directory. FIX-1356's model is
`org ∪ team ∪ worker-local` per seat. **Name this; do not copy it.**

**f. Registration does not isolate storage, and kitchen-sink's own comment says why it hurts.**
`createSkillsLibrary` defaults its collection key to `"skills"` at **`org`** scope
(`packages/orchestration/src/skills/library.ts`). Kitchen-sink overrides to `scope: "user"` with a
comment recording that org scope "falls through to an ambient org with no persistence identity,
which is why nothing seeds". So two seats in one org registering the same bare `SKILL.md` name
resolve to the same collection entry. A per-seat *register* over one shared collection gives
isolation at the view level and not at the storage level. Per-seat isolation needs a real resource
identity — distinct collection key, prefix or scope. This corroborates epic theme 7 from the
source; the contract is FIX-1361's to state and FIX-1362's to implement.

**g. Memory is per end-user, not per member — name the gap, invent nothing.** Kitchen-sink
registers `mem.userResources` at `user` scope. That is durable per end user; there is no
member/seat identity in it. A multi-seat roster serving one user would share one memory. This is
the honest gap for FIX-1364, which the epic already instructs to name rather than paper over with
seat-local state that looks durable and isn't.

**h. Most of `chat-agent` is not agent-kind material.** Beyond the spine the app carries five
thinking-style pattern pipelines with a classifier and router, a bias check, perspective capture
(`@thought-fabric/core/identity`), an artifacts subsystem, a bash sandbox with
environment-selected providers, optional MCP, four durable human-in-the-loop actions, voice, and
auto-titling. All of it is good demo surface and none of it belongs in an out-of-the-box default.
The note says so by name (Decision 3) so no downstream author treats presence in kitchen-sink as
evidence of belonging in the kind.

**i. The killed agent surface is still taught in twelve places a user can reach.** `defineAgent` /
`materializeAgent` / `AgentRegistry` are FIX-1344's kill targets. Outside
`packages/workforce/src` they are still referenced by:

- **Seven published pages** — `apps/docs/docs/orchestration/{agents,configuration,overview}.md`,
  `apps/docs/docs/skills/delegation.md`,
  `apps/docs/guides/{building-agents,building-a-research-team,agents-command-the-board}.md`.
- **The Atlas itself** — `docs/atlas/README.md`. This is FIX-1366's direct target.
- **Two package READMEs** — `packages/workforce/README.md`, `packages/orchestration/README.md`.
- **The research-team example** — `examples/guides/research-team/` (README, `src/agents.ts`,
  `src/skills.ts`, and a bundled `SKILL.md`), which is runnable code a user copies from.

Internal design docs (`docs/internal/design/agent-primitive-gaps.md`, two trading-desk docs, the
trading-desk-v2 plans, archived changesets) also reference it; those are historical records, not
teach surface, and only `agent-primitive-gaps.md` is a live design doc. The note hands this
catalogue to FIX-1366 rather than making it re-derive one. It is a list, not a work item here.

**j. The skills module couples to the kill-target cluster — by optional injection, and
kitchen-sink does not use it.** This one is easy to get backwards, so the note states it
precisely. `createSkillsLibrary` accepts optional `agentRegistry` and `materializeAgent`
(`packages/orchestration/src/skills/library.ts`), and the delegation surface and worker
materializer thread them through
(`skills/delegation-surface.ts`, `skills/worker-materializer.ts`); a skill whose `agents:` map
names a registry agent throws without them (`library.ts`, the guard around line 488).
Kitchen-sink passes **neither** — its skills resolve their board workers through
`workerModelId: "intent/chat"` instead. So the path the agent kind would inherit from
kitchen-sink is the one that does *not* touch the cluster, and FIX-1344's deletion does not
block FIX-1362 (epic theme 3, corroborated from source). The seam is real and stays optional.

#### 7.4 One narrowed observation for FIX-1361 — not a decision here

The epic does not say which package exports the built-in kind, and the epic PR review asked for
it to be settled in the contract. The audit narrows it without deciding it: the kind must compose
skills (`@flow-state-dev/orchestration`), memory (`@flow-state-dev/memory`) and the hire surface
(`@flow-state-dev/workforce`), and of those only `workforce` already owns the hire path that the
kind has to reach. The note records that as evidence for FIX-1361's call.
