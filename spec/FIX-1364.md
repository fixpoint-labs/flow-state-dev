# FIX-1364: Memory attach + gap honesty for agent kind — Implementation Spec

## Part I — The Case *(for the human)*

*The numbered decisions this asks you to sign off on are in §6.*

### 1. Problem — why it matters, why now

A team can now describe a worker in a file and get a working agent. It talks, and it can
reach the skills the app handed it. It does not remember anything — not within a
conversation, not across them.

The contract already decided that is correct by default: a stock worker carries no memory,
because memory costs tokens and latency on every turn and nobody should pay for it without
asking. It also decided how an app *should* turn memory on — by composing it into its own
copy of the worker kind when it defines it, not by flipping a per-worker switch.

**That path does not exist.** Everything composing memory requires happens inside the
factory we ship, and none of it is reachable from outside. An app that wants a worker who
remembers has exactly one option today: copy our factory and edit the copy. Then every fix
we make to workers is a fix they don't get.

So the promise "memory attaches by composition" is currently a promise with no door behind
it. This issue builds the door, and says accurately what is on the other side of it.

### 2. Solution in plain terms

Open three doors on the worker-kind factory, all deliberately generic: *what capabilities to
attach*, *whether each worker's storage is its own*, and *what runs after the worker answers*.
Memory is then one thing an app can pass through them. The workforce package learns nothing
about memory — no dependency, no memory-shaped option, no tier knowledge.

**The third door is what makes the other two worth having.** Memory has a read side and a
write side, and they are separate entry points in the memory package. Attaching only the
read side produces a worker that can recall facts someone else stored but never records
anything from its own conversations — a worker that looks like it remembers and doesn't.
Remembering needs a step *after* the answer, and the kind's sequence is as closed to an app
as its generator is.

The other half of getting this right is **how a worker reads memory back**, and it interacts
with a rule the contract already set: a worker may call only the tools it names. Memory's
on-demand recall arrives as a tool, so the recipe turns it off — and then surfaces prior
knowledge as injected context instead, which is not a tool and so is not fenced. A worker
ends up reading what it knows every turn rather than searching on request. That trade is the
design, not an accident (Decision 2).

Calling the factory with no arguments still produces exactly what it produces today: a
worker with no memory, and no memory storage declared anywhere in it. That stays provable
rather than promised.

The rest of the work is making what we say about it true — in the docs this issue owns, in
the contract, and in follow-ups for the parts that are still missing. Research improved that
story in one place (Decision 3) and, in another, showed that the rule about tools is currently
upheld by each consumer rather than by the framework; the framework fix is filed as FIX-1393
and this issue is one consumer honouring the rule (Decision 2).

**What this deliberately does not do:** ship a memory helper, add a per-worker memory
setting, change anything inside the memory package, change `@flow-state-dev/core`, or design
a new isolation primitive.

Leans on tenet 2 (the framework absorbs what serves apps broadly — a generic composition
seam serves every capability, not just this one) and tenet 3 (earn every addition — three
options, no helper, no new concept).

### 6. Decisions & rules — the sign-off surface

1. **The seam is generic, and it opens the write side as well as the read side.** The factory
   accepts capabilities, a per-worker-storage flag, and a post-answer step — never a `memory:`
   option. The post-answer step is what lets an app wire memory's capture pipeline, and it
   stays opt-in, matching the contract's rule that the heavy path is never the default.
   *Rejected:* a `memory:` option or a `withMemory()` helper, which would couple the workforce
   package to the memory package. Also rejected: opening only the read side, which ships a
   worker that appears to remember and cannot.
   **Changed under review — this is two doors, not the three the Architect ratified.** A
   separate `resources` option was in the ratified version and has been dropped: a capability
   already contributes its declared resources, and `defineFlow` merges every action block's
   declarations, so `uses:` alone installs memory's stores. Verified by running it (§7). It
   was a second registration route with no consumer.

2. **The recipe closes the tool fence for memory; the general guarantee is enforced by
   FIX-1393, not by anything here.** Memory's recall and connect arrive as tools, so the recipe
   turns them off and surfaces memory through context injection instead — which carries no tool
   and so does not touch the fence. An app that wants on-demand recall puts the recall tool in
   its own catalog, where a worker opts in by naming it.
   **Where the guarantee actually comes from:** the framework currently *unions* capability
   tools onto a block's own list, so today the rule is upheld at each consumer. FIX-1393 moves
   it into `@flow-state-dev/core` as a real intersection — declared `tools:` ∩ capability
   tools, empty stays empty. The fence stays the contract it always was; this issue is one
   consumer honouring it, and the consumer opt-outs remain **necessary** until FIX-1393 lands.
   *Locks in:* a correct recipe, and no pretence that §10's tests prove more than the recipe.

3. **We teach that per-worker memory works, because it does.** The contract records it as an
   unproved gap. A POC on this branch showed it is reachable today with one flag and no new
   primitive (§7). The real remaining limit is narrower and gets filed, not taught as a
   blocker: isolation is chosen per worker *kind*, so a roster is all-shared or all-separate,
   never mixed. A worker rename orphans its isolated memory — documented, not migrated.
   *Locks in:* the teaching surface says "yes, with this flag", not "not yet".

**Size:** Medium. One package touched, three options, a docs pass, follow-ups filed.

### 3. Tradeoffs & alternatives

**The simpler thing, weighed and rejected:** export the factory's internals and let apps
assemble their own kind with `defineFlow`. Composition in its purest form, no options at all
— but it moves the whole flow into every app that wants memory, which is the copy-the-factory
problem with extra steps, and it turns internals into public surface we'd owe compatibility on.

**The real cost, and it is Decision 2's:** a worker built to this recipe cannot *search* its
memory mid-turn. It receives a slice of what it knows as context on every turn instead. For
most workers that is equivalent or better — no tool round-trip, no chance the model forgets to
look. For a worker with a large store and a specific question, injected context is strictly
worse than a query, and the escape hatch (recall via the app catalog) costs the app a
deliberate decision. We are choosing the fence over the faculty, and Decision 2 is where to
disagree.

**What we're accepting:** attaching memory is several lines of app code, and getting a worker
that records takes the write-side entry point plus a post-answer step. Deliberate — it is what
keeps the zero-config worker cheap.

### 4. Focus practices

- **BP-003** — three claims here are load-bearing and all were *run*, not asserted: isolation
  separates workers (with a control case), `uses:` alone installs resources, and the read path
  survives the fence. The first draft's acceptance criteria would have passed on a worker that
  could not remember anything new — that is the failure this practice exists to catch.
- **BP-027** — user-scoped resources default to shared. That default *is* the gap; don't
  describe it as a defect.
- **BP-030** — the default factory call must keep producing a kind with no memory storage.
- **BP-041** — the honesty half is a teaching-surface change; write it as what someone gets.

### 5. What using it looks like

An app that wants workers who remember, each separately. Note `system()`, not
`createMemoryCapability` — the latter is read-only and produces a worker that never records:

```ts
import { AGENT_KIND, defineAgentWorkerFlow, hireWorkforce } from "@flow-state-dev/workforce";
import { system } from "@flow-state-dev/memory";

const mem = system({
  model: "openai/gpt-5.4-mini",
  working: { capacity: 7 },
  episodic: true,
  semantic: true,
});

const rememberingWorker = defineAgentWorkerFlow({
  catalog: appTools,
  uses: [
    mem.capability.presets({
      // Tools — turned off so a worker's `tools:` stays the only door.
      recall: false,
      connect: false,
      // Context injection — not tools, so the fence is untouched. These are
      // OFF by default, and without them the durable stores are written but
      // never read back.
      semantic: true,
      episodic: true,
    }),
  ],
  isolateUserState: true,             // each worker remembers separately
  afterAnswer: mem.captureFromItems,  // the write side — without this, nothing is recorded
});

const workforce = hireWorkforce({
  dir: "./workers",
  kinds: { [AGENT_KIND]: rememberingWorker },
});
```

Observable result: tell a worker something in one conversation and it recalls it in the next.
Drop `afterAnswer` and it recalls only what something else stored. Drop the `semantic` /
`episodic` presets and it writes durably but reads back only the current conversation. Drop
`isolateUserState` and two workers serving one person share a memory. Drop the whole block and
they remember nothing — which is what every roster hired today already does.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

Three additions to `AgentWorkerFlowOptions`, all app-level and build-time. None reaches the
worker settings schema, so no worker file can turn memory on or off — that is what keeps the
contract's C5 split checkable.

- **capabilities to attach** — forwarded to the kind's generator alongside the skills binding
  it already carries. The skills binding must stay first-class; app capabilities compose
  beside it, never replace it.
- **per-worker storage** — forwarded as the flow's user-scope isolation flag.
- **a post-answer step** — run after the generator in the kind's sequence, as a side-chain so
  it cannot alter the answer. Absent, the sequence is exactly today's.

Absent, each resolves to the empty/false case, so the no-argument call produces today's kind
byte-for-byte in behaviour.

**No `resources` option — established by running it.** A capability's declared resources reach
the generator's `declaredResources`, and `defineFlow` merges every action block's declarations
(`collectBlockResources`). A flow declaring `uses: [memoryCapability]` and *no* `resources`
resolved `workingMemory`, `semanticMemory` and `episodicMemory` at runtime
(`spec-poc/.../resources-bubble.ts`). The memory README's spread is redundant, not required.
One nuance worth knowing rather than acting on: flow-level declarations are prefetched while
block-level ones load on the declaring block, so the option would only come back if a concrete
prefetch requirement appeared. None has.

**The read/write split is the thing to get right, and it has two halves.**

*Write:* `createMemoryCapability` builds the read side only — its own docstring says it omits
capture, consolidation, prune and the janitor, and to reach for `system()` when the flow also
captures. So the recipe is `system()` plus its capture block in the post-answer door.

*Read:* memory's default-on presets are `digest`, `working` and `recall` only. `semantic` and
`episodic` are **off by default**. So turning `recall` off to satisfy the fence, without
turning those two on, produces a worker whose durable stores are written and never read —
neither injected nor queryable. The recipe must turn them on explicitly. **This is why the
fence and the faculty do not actually collide:** `recall`/`connect` are the only tool-bearing
presets; `digest`/`working`/`semantic`/`episodic` contribute `context` and no tools. Context
injection is not a tool, so the read path survives the fence intact.

**The tools fence — one mechanism here, with the general fix owned elsewhere.** The supported
recipe turns the tool-bearing presets off and routes on-demand recall through the app catalog,
so the generator's own `tools:` mapping stays the single registration path. §10's fence test is
the guarantee **for that recipe** — say so where it is written, so a passing test is not read
as proving the general case.

Do **not** build a general enforcement mechanism here. The framework's tools resolver ends in
`[...base, ...staticTools, ...dynTools]` — a union, not an intersection — and that is fixed in
`@flow-state-dev/core` by **FIX-1393**, which makes it a real intersection (declared `tools:` ∩
capability tools, empty stays empty). The fence is still the contract it has always been; this
issue is one consumer honouring it. **The recipe's opt-outs stay necessary until FIX-1393
lands**, and are not an alternative fence story.

### 8. Implementation sequence

1. Add the three options, defaulting to the empty case. **Verify:** a no-argument call declares
   no resources, no isolation, and an unchanged sequence.
2. Thread capabilities to the generator beside the skills binding. **Verify:** a memory
   capability's context block reaches the prompt; skills still activate.
3. Thread the isolation flag to `defineFlow`. **Verify:** the POC's two-worker scenario, run
   against the real kind rather than the POC's stand-in flow.
4. Thread the post-answer step into the kind's sequence as a side-chain. **Verify:** §10's
   write-then-read check — the one that fails without this step.
5. Confirm the fence for the supported recipe. **Verify:** §10's fence check.
6. Docs and the gap account (§11).
7. File the follow-ups (§12).

**Removals:** none. Purely additive to a factory that shipped days ago.

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| No-argument factory call | Today's kind exactly: no memory, no resources, no isolation, unchanged sequence |
| Read-side capability attached, no post-answer step | Worker recalls stored facts, records nothing. Legitimate but documented as such, not sold as memory |
| Capture on, but `semantic`/`episodic` presets left off | Durable stores written and never read back. The silent half-failure this spec exists to prevent — the docs must call it out |
| Post-answer step throws | Must not fail the worker's answer — it is a side-chain, and a capture failure is not a conversation failure |
| Worker declares `tools: []`, memory attached per the recipe | Zero tools reach the model |
| Another tool-bearing capability passed through `uses` | Its tools reach the worker. Known limit, recorded in §12, not fixed here |
| App passes a resource key the kind already uses | Merge refuses at build time on conflicting references — do not add a second check |
| `isolateUserState: true`, worker renamed | Memory is orphaned — documented consequence of keying on the worker's id. **No migration invented here** |
| Memory attached, roster already hired without it | Workers start with empty memory; nothing to migrate |

### 10. Testing strategy

Behaviours, as tracer-bullet tests. **The first one is the one that matters**, and it is
written to fail against the read-only recipe — the earlier draft's criteria would all have
passed on a worker that could not remember anything new.

1. **A worker records what it is told and reads it back, with nothing pre-seeded.** Tell a
   worker a fact in one turn; in a later turn it recalls that fact. No seeded storage anywhere
   in the setup. This fails without the post-answer step *and* without the `semantic` /
   `episodic` presets, which is exactly the pair of gaps review found. If it cannot be made to
   pass, that is the real finding and the gap-honesty half must say so plainly.
2. **The default stays empty.** A no-argument kind declares no memory resources and no
   post-answer step. Makes the contract's C5 falsifiable rather than decorative.
3. **The fence holds for the supported recipe.** A worker declaring `tools: []`, on a kind with
   memory attached per §5, sends zero tools to the model. Written to fail against the naive
   attach. **Name it for what it covers** — this proves the memory recipe, not the general
   guarantee, which is FIX-1393's. A test named as though it proved the general case is how a
   green check starts certifying a gap.
4. **Separate workers, separate memories.** Two workers, one end user, isolation on: a fact
   written through one is not visible to the other. **With the control case** — isolation off,
   the fact *is* visible. Without the control this passes on a broken build.
5. **Skills still work alongside memory.** The skills binding is not displaced.

Note: `testFlow` cannot currently drive a collection flow without pre-seeding sessions that
name their owning instance — see §12.

### 12. Dependencies, open questions & follow-ups

**Dependencies:** FIX-1363 (merged — the factory this extends). No dependency on the memory
package changing, and none on FIX-1351, which is the file-convention/channels epic and does
not touch memory's surface. **Nothing here widens another package's API, and nothing here
changes `@flow-state-dev/core`.**

**Resolved by POC — do not reopen.**

- Per-worker durable memory needs no new isolation primitive; `isolateUserState: true` gives
  each worker its own, keyed on the worker's id. Control case included.
- `uses:` alone installs a capability's resources; a separate `resources` option has no
  consumer.

Both under `spec-poc/FIX-1364-seat-memory-isolation/`.

**Confirmed against source during review — do not re-litigate.** `createMemoryCapability`
omits the write-side pipeline; memory's default-on presets are `digest`/`working`/`recall`
only, so `semantic` and `episodic` need turning on explicitly; the framework's tools resolver
returns a union of block and capability tools. All folded into §6 and §7.

**Follow-ups to file, not build here:**

1. **FIX-1393 — capability tools union onto declared `tools:` instead of intersecting.** Filed,
   High, blocking neither this issue nor FIX-1362. It carries the Architect's ruling that the
   intersection is enforced in `@flow-state-dev/core`. Until it lands, consumer opt-outs like
   this spec's recipe are necessary. Fourth time this epic has met that one line.
2. **Memory's resource factories don't forward `flowIsolation`.** So isolation is all-or-nothing
   per kind; a roster cannot mix a shared tier with a per-worker one. Same shape as the
   skills-collection gap the contract found (C3). Belongs to the memory package's owner.
3. **`testFlow` cannot drive a collection flow.** It seeds sessions with no owning instance id,
   so ownership refuses the run as needing migration. Blocks seat-level tests generally.
4. **Renaming a worker orphans its isolated memory.** Inherent to keying on the instance id.
   Document it; do not invent a migration.
5. **The memory README teaches a redundant resource spread.** Harmless but misleading now that
   the bubble-up path is confirmed.

**Open questions:** none blocking.

## Spec evolution

- **Spec drafted** — framed as a missing door rather than a missing feature: the contract
  already decided memory attaches by composition, but nothing in the shipped factory lets an
  app do it without forking our source. Chose a generic three-option seam over a memory-shaped
  option or helper, so the workforce package takes no memory dependency.
- **After POC** — the gap-honesty half changed direction. The contract records per-member
  memory isolation as an unproved L1 gap; a characterization test with a control case showed it
  is reachable today with one flag and no new primitive. The spec now teaches that it works and
  files the narrower real limit (isolation is per kind, not per tier).
- **After spec review** — three changes, all from findings two or three reviewers reached
  independently. Added a post-answer door and switched to the write-side entry point, because
  the original recipe attached read-only memory and would have shipped a worker that recalls but
  never records — and the acceptance criteria would have passed on it. Turned the `semantic` and
  `episodic` context presets on explicitly, because they are off by default and turning `recall`
  off for the fence would otherwise have left the durable stores written but unreadable; this is
  also what shows the fence and the faculty don't collide, since context injection carries no
  tool. Dropped the `resources` option after running it — capability resources already bubble
  up — which narrows Decision 1 from the shape the Architect ratified.
- **After the FIX-1393 ruling** — Decision 2 stops describing the tool rule as a residue this
  issue declines to hold. The rule is unchanged and still the contract; what review established
  is that it is upheld per consumer today, and FIX-1393 moves the intersection into core. This
  spec is one consumer honouring it, and §10's fence test is named for the recipe it covers.
