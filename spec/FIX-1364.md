# FIX-1364: Memory attach + gap honesty for agent kind — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

A team can now describe a worker in a file and get a working agent. It talks, and it can
reach the skills the app handed it. It does not remember anything — not within a
conversation, not across them.

The contract already decided that is correct by default: a stock worker carries no memory,
because memory costs tokens and latency on every turn and nobody should pay for it without
asking. It also decided how an app *should* turn memory on — by composing it into its own
copy of the worker kind when it defines it, not by flipping a per-worker switch.

**That path does not exist.** The three things composing memory requires — attaching the
capability, declaring its storage, and choosing whether seats share it — all happen inside
the factory we ship, and none of them is reachable from outside it. An app that wants a
worker who remembers has exactly one option today: copy our factory and edit the copy. Then
every fix we make to workers is a fix they don't get.

So the promise "memory attaches by composition" is currently a promise with no door behind
it. This issue builds the door.

The second half is what we *say* about it. Everywhere the product implies a worker
remembers, we owe the honest version — including the part that is still missing. A setting
someone can write that quietly does nothing is the failure this epic has already refused
twice.

### 2. Solution in plain terms

Open three doors on the worker-kind factory, and they are deliberately generic: *what
capabilities to attach*, *what storage to declare*, and *whether each worker's storage is
its own*. Memory is then just one thing an app can pass through them. The workforce package
learns nothing about memory — no dependency, no memory-shaped option, no tier knowledge.

Calling the factory with no arguments still produces exactly what it produces today: a
worker with no memory, and no memory storage declared anywhere in it. That stays provable
rather than promised.

Alongside it, the honest account of what an app gets when it does attach memory, and what it
still can't have. Research for this spec turned up something the contract didn't know, so
that account is better news than expected — see Decision 3.

**What this deliberately does not do:** ship a memory helper, add a per-worker memory
setting, change anything inside the memory package, or design a new isolation primitive.

Leans on tenet 2 (the framework absorbs what serves apps broadly — a generic composition
seam serves every capability, not just this one) and tenet 3 (earn every addition — three
options, no helper, no new concept).

### 6. Decisions & rules — the sign-off surface

1. **The seam is generic, not memory-shaped.** The factory accepts capabilities, resources,
   and a per-worker-storage flag — never a `memory:` option. *Rejected:* a `memory:` option
   or a `withMemory()` helper, which would make the workforce package depend on the memory
   package and bake in tier choices we have no basis to make. *Locks in:* memory is attached
   by the app, the same way anything else would be, and the factory stays ignorant of it.

2. **A worker's declared tool list stays the only door to tools, even when a capability
   brings its own.** Memory ships an agent-callable recall tool that is on by default, and
   the framework adds capability tools to a block's own list rather than checking them
   against it. Left alone, attaching memory would hand every worker a tool it never asked
   for — including one declared with no tools at all. The recall tool reaches a worker only
   by going in the app's tool catalog, where a worker opts in by naming it. *Locks in:* one
   registration path, and the existing fence keeps meaning what it says.

3. **We teach that per-worker memory works, because it does.** The contract records it as an
   unproved gap. A POC on this branch showed it is reachable today with one flag and no new
   primitive (§7). The real remaining limit is narrower and gets filed, not taught as a
   blocker: isolation is chosen per worker *kind*, so a roster is all-shared or all-separate,
   never mixed. *Locks in:* the teaching surface says "yes, with this flag", not "not yet".

**Size:** Medium. One package touched, three options, a docs pass, one ticket filed.

### 3. Tradeoffs & alternatives

**The simpler thing, weighed and rejected:** export the factory's internals — its settings
schema, its prompt seam, its skills wiring — and let apps assemble their own kind with
`defineFlow`. That is composition in its purest form and adds no options at all. Rejected
because it moves the whole 277-line flow into every app that wants memory, which is the
copy-the-factory problem with extra steps, and it turns internals into public surface we'd
then owe compatibility on. Three options is the smaller commitment.

**The cost of the generic seam:** `uses` and `resources` are broad doors. An app can pass
anything through them, including something that conflicts with the kind's own skills wiring.
We are trading a narrow, safe, memory-only option for a wider one that serves every future
capability. Given the contract's instruction not to grow memory-specific surface, and that
the alternative forces a package dependency, the wide door is the right trade — but it is a
real one, and Decision 1 is where to disagree.

**What we're accepting:** attaching memory stays a few lines of app code rather than one
flag. That is deliberate per the contract, and it is what keeps the zero-config worker cheap.

### 4. Focus practices

- **BP-003** — the isolation claim is the spec's load-bearing fact and was *run*, with a
  control case proving the check could fail. Don't re-assert it from reading.
- **BP-027** — user-scoped resources default to shared. That default *is* the gap; the spec
  must not describe it as a defect.
- **BP-030** — the default factory call must keep producing a kind with no memory storage,
  for rosters already hired.
- **BP-041** — the honesty half is a teaching-surface change; write it as what someone gets,
  not what we built.

### 5. What using it looks like

An app that wants workers who remember, each separately:

```ts
import { AGENT_KIND, defineAgentWorkerFlow, hireWorkforce } from "@flow-state-dev/workforce";
import { createMemoryCapability } from "@flow-state-dev/memory";

const mem = createMemoryCapability({
  model: "openai/gpt-5.4-mini",
  working: { capacity: 7 },
  episodic: true,
  semantic: true,
});

const rememberingWorker = defineAgentWorkerFlow({
  catalog: appTools,
  // Memory's own recall tool is left off: a worker's `tools:` is the only door.
  // Put it in `catalog` instead if workers should be able to name it.
  uses: [mem.presets({ recall: false, connect: false })],
  resources: { ...mem.sessionResources, ...mem.userResources },
  isolateUserState: true, // each worker remembers separately
});

const workforce = hireWorkforce({
  dir: "./workers",
  kinds: { [AGENT_KIND]: rememberingWorker },
});
```

Observable result: two workers serving the same person keep separate memories. Drop
`isolateUserState` and they share one. Drop the whole block and they remember nothing —
which is what every roster hired today already does.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

Three additions to `AgentWorkerFlowOptions`, all app-level and build-time. None reaches the
worker settings schema, so no worker file can turn memory on or off — that is what keeps the
contract's C5 split checkable.

- **capabilities to attach** — forwarded to the kind's generator alongside the skills binding
  it already carries. The skills binding must stay first-class; app capabilities compose
  beside it, never replace it.
- **resources to declare** — spread onto the kind's `defineFlow` resource map.
- **per-worker storage** — forwarded as the flow's user-scope isolation flag.

Absent, each resolves to the empty/false case, so the no-argument call produces today's kind
byte-for-byte in behaviour: no capability beyond skills, no resources, no isolation.

**The invariant and its convergence point.** Decision 2 tightens the existing rule that a
worker may call exactly the tools it names. The convergence point is the generator's own
`tools:` mapping, which is already the single registration path. The threat is that the
framework *unions* capability-contributed tools onto that list rather than filtering them
(`packages/core/src/blocks/generator.ts`, the tools resolver returns
`[...base, ...staticTools, ...dynTools]`), and memory's `recall` preset declares a tool
default-on (`packages/memory/src/memory-capability.ts`). Every writer that can put a tool on
a stock worker must pass through the seat's list: the generator's mapping does, the skills
library is already held off with `registerCatalogTools: false`, and app capabilities are the
new third writer this spec must close.

Establish first, before building: whether the kind can *refuse* a capability carrying tool
presets at definition time, in the loud-fail style the rest of this kind uses. If it can,
that is the mechanism. If capability tools cannot be inspected before resolution, fall back
to documenting the stripped-preset recipe and prove the fence with the §10 check — which is
the real guarantee either way.

### 8. Implementation sequence

1. Add the three options, defaulting to the empty case. **Verify:** a no-argument call
   declares no resources and no isolation.
2. Thread capabilities to the generator beside the skills binding. **Verify:** a memory
   capability's context block reaches the prompt; skills still activate.
3. Thread resources and the isolation flag to `defineFlow`. **Verify:** the POC's two-seat
   scenario, run against the real kind rather than the POC's stand-in flow.
4. Close the tools fence per §7. **Verify:** §10's fence check.
5. Docs and the gap account (§11).
6. File the residual-gap ticket (§12).

**Removals:** none. This is purely additive to a factory that shipped days ago; nothing it
supersedes.

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| No-argument factory call | Today's kind exactly: no memory, no resources, no isolation |
| Capability passed that carries tool presets | Refused loudly at definition, or stripped — never silently widening a worker (§7) |
| Worker declares `tools: []`, memory attached | Zero tools reach the model |
| App passes a resource key the kind already uses | Refuse by name at definition; do not let an app shadow the skills collection |
| `isolateUserState: true`, worker renamed | Memory is orphaned — a documented consequence of keying on the worker's id, not a bug to fix here |
| Memory attached, roster already hired without it | Workers start with empty memory; nothing to migrate |

### 10. Testing strategy

Behaviours, as tracer-bullet tests:

1. **The default stays empty.** A no-argument kind declares no memory resources. This is the
   check that makes the contract's C5 falsifiable rather than decorative — it must fail if
   someone later adds memory to the default.
2. **The fence holds.** A worker declaring `tools: []`, on a kind with memory attached, sends
   zero tools to the model. Written to fail against the naive attach.
3. **Separate workers, separate memories.** Two workers, one end user, isolation on: a fact
   written through one is not visible to the other. **With the control case** — isolation off,
   the fact *is* visible. Without the control this test passes on a broken build.
4. **Memory reaches the prompt.** A stored fact appears in the worker's context block.
5. **Skills still work alongside memory.** The skills binding is not displaced by app
   capabilities.

Note for whoever writes these: `testFlow` cannot currently drive a collection flow without
pre-seeding sessions that name their owning instance — see §12.

The gap account belongs on the workforce pages, not the memory pages: it is a fact about
workers, and a memory reader not using workforce shouldn't meet it. Voice watch-items:
no "powerful" / "seamless"; introduce *capability* and *worker kind* on first use; no issue
or PR numbers anywhere under `apps/docs/`.

### 12. Dependencies, open questions & follow-ups

**Dependencies:** FIX-1363 (merged — the factory this extends). No dependency on the memory
package changing, and none on FIX-1351, which is the file-convention/channels epic and does
not touch memory's surface. **Nothing here widens another package's API.**

**Resolved by POC — do not reopen.** Per-seat durable memory needs no new isolation
primitive; `isolateUserState: true` gives each worker its own, keyed on the worker's id.
Evidence and the control case: `spec-poc/FIX-1364-seat-memory-isolation/`.

**Follow-ups to file, not build here:**

1. **Memory's resource factories don't forward `flowIsolation`.** So isolation is
   all-or-nothing per kind; a roster cannot mix a shared tier with a per-worker one. Exactly
   the shape of the skills-collection gap the contract found (C3) one level over. Small
   passthrough; belongs to the memory package's owner.
2. **`testFlow` cannot drive a collection flow.** It seeds sessions with no owning instance
   id, so ownership refuses the run as needing migration. Blocks seat-level tests generally.
3. **Renaming a worker orphans its isolated memory.** Inherent to keying on the instance id;
   worth a documented warning and possibly a migration path later.

**Open questions:** none blocking. The one genuine unknown — whether the tools fence can be
enforced by refusal rather than documentation — is an implementation question with a stated
fallback and a test that guarantees the outcome either way (§7, §10).

## Spec evolution

- **Spec drafted** — framed as a missing door rather than a missing feature: the contract
  already decided memory attaches by composition, but nothing in the shipped factory lets an
  app do it without forking our source. Chose a generic three-option seam over a
  memory-shaped option or helper, so the workforce package takes no memory dependency.
- **After POC** — the gap-honesty half changed direction. The contract records per-member
  memory isolation as an unproved L1 gap; a characterization test with a control case showed
  it is reachable today with one flag and no new primitive. The spec now teaches that it
  works and files the narrower real limit (isolation is per kind, not per tier) instead of
  teaching a blocker that isn't one.
