# FIX-1365: Thin Proof — hire the OOTB `agent` kind — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

Epic FIX-1359 shipped a promise: **write a Markdown file describing a worker, point the app at
the folder, and you have a working worker** — no TypeScript, no registration, no flow to define.
Six issues built it and all six have merged.

Nothing anywhere does that and gets an answer back.

Every check we have stops one step short, and each stops short in a different direction:

- **The unit specs mock the model.** `packages/workforce/test/agent-worker-flow.test.ts` proves
  a file with no `flow:` *mints* into the built-in kind and that its body *arrives* as the
  `instructions` setting. It cannot prove the model ever saw it — a mocked generator returns
  whatever the test told it to.
- **The goal checks never hire the built-in.** Every `hireWorkforce` call in `goals/` hands over
  an explicit `kinds` map, so what they exercise is a flow the app wrote, not the one it gets
  for free.
- **No workforce goal declares itself model-backed.** Every one of them carries a model-free
  `Model:` field, deliberately and for good local reasons — but the consequence is that the
  sentence "it talks" has no check standing behind it.

These are counted claims, and this spec was drafted hours after six sibling PRs merged, so they
are re-derived by a script rather than asserted: `spec-poc/FIX-1365-evidence/check.mjs` on this
branch. Its current output:

```
C-A: defineAgentWorkerFlow appears in 0 of 177 files under goals/
C-B: all 4 hireWorkforce call site(s) under goals/ pass a kinds argument
C-C: 0 of 3 workforce goal(s) are model-backed
```

Each claim was watched go red against a planted counter-example before it was believed.

**What C-C does and does not establish.** It reads each goal's `Model:` frontmatter — the field
`goal:all` itself reads to decide what a `--model-free` sweep may run. So it establishes that no
workforce goal *declares* a model, which is what the corpus's own machinery goes on. It does
**not** prove that no `run.mts` anywhere contacts a model; a goal could do so without declaring
it. The narrower claim is the one this spec rests on, and C-A and C-B carry the rest of the
weight: nothing under `goals/` so much as references the built-in kind's factory, and every hire
there passes an explicit `kinds` map.

**Why now:** this is the last issue of the epic. The gap is not that a piece is missing — the
pieces are all built and well tested. It is that the epic's *headline claim* is the one thing
nobody can demonstrate, and a claim nobody can demonstrate is how a framework ships a promise
that quietly stopped being true two refactors later.

### 2. Solution in plain terms

Add **one goal check** — this repo's existing form for "prove the real thing actually works,
on a real model, outside CI" (`goals/README.md`).

It does what a team adopting the framework would do, in that order:

1. Reads a folder of worker Markdown files from disk with the real loader.
2. Calls `hireWorkforce(workers)` — **with no `kinds` argument at all**, so the built-in `agent`
   kind is the only thing that could answer.
3. Registers those seats and asks each one a question over the real HTTP route.
4. Grades the **answers**, and grades them as a pair: each worker's answer must carry the
   instruction written in *its own* file and not its neighbour's.

It also carries the refusal case — a file naming a kind nobody registered is refused by name and
**nothing on the roster hires** — because "it hired" is only trustworthy next to a demonstration
that a bad roster doesn't.

**What it deliberately does not do:** it adds no product surface. No new app, no kitchen-sink
feature, no page, no exported API. The only thing that ships is a check.

**What it deliberately does not claim:** memory, and per-seat skills. Both are covered below and
both are somebody else's — saying so out loud is part of the deliverable, not a caveat on it.

### 6. Decisions & rules — the sign-off surface

1. **The proof ships as one goal check under `goals/`, and adds no product surface.**
   *Rejected:* a demo app, or a feature in `apps/kitchen-sink`. Kitchen-sink is still used — as
   the working directory the check runs in, because it is the only place the AI gateway resolves —
   but nothing is added to it and nothing there changes.
   *Locks in:* the proof is run by hand, not in CI, so it can be wrong for a while before anyone
   notices — that is the deal `goals/` already makes, and it buys a check that runs a real model.
   It also means we are **not** shipping a sample app for this epic; a team looking for something
   to copy still gets the docs FIX-1366 wrote, not a runnable example.

2. **What counts as proved is the model's answer, not the settings bag.**
   The check grades the text each worker replied with. It is forbidden from grading
   `ctx.flow.config.instructions`, which a sibling goal already covers and which stays true even
   if the model never sees the body.
   *Rejected:* a cheaper model-free check asserting the instructions reached the flow.
   *Locks in:* every run costs real model calls — **two on the passing path** (two seats, one
   question each), and roughly **six for a full verification**, which re-runs the answer leg under
   each negative control. Retries on model flakiness add to both. It also inherits real-model
   nondeterminism and can be blocked outright when no inference credential is present. In
   exchange, "an app can hire the out-of-the-box worker and it talks"
   becomes a sentence with evidence under it, and stays one — this is the regression check when
   someone refactors the prompt composition next quarter.

3. **The proof states what it does not prove, in the artifact itself.**
   The worker it hires does **not** remember anything and holds no skills, and `goal.md` says so
   in its own words rather than leaving a green check to imply otherwise.
   *Rejected:* stretching the proof to cover memory attach, which the issue's older text reads as
   in scope.
   *Locks in:* memory stays FIX-1364's and per-seat skills stay FIX-1362's, so anyone wanting
   *that* evidence is sent to where it actually lives. The cost of getting this wrong is the one
   the epic's honesty gate was written against — a reader takes a passing check to mean the
   out-of-the-box worker remembers, which is false, and builds on it.

**Non-goals** — acceptance criteria 4, 5 and 6 (they are assigned to FIX-1363 and FIX-1362 by
the locked contract, and are built); memory of any kind; MCP; Collab; a custom-kind matrix; any
change to `apps/kitchen-sink`'s own flows, routes or pages; any published documentation change.

**Size:** Small — 7 files · 5 behaviours (3 graded legs + 2 negative controls) · 0 doc surfaces · 1 PR.

### 3. Tradeoffs & alternatives

**The simpler thing considered, and rejected: no new check at all.** The mint-level behaviour of
acceptance criteria 1 and 3 genuinely *is* covered by the existing unit specs, and criterion 3's
exact message — the refusal listing `agent` among the available kinds — has a test on it
(`agent-worker-flow.test.ts:96`). If those two were the whole of it, the honest answer would be
"already proved, close the issue."

Criterion 2 is what keeps it open. *"That seat answers a turn using its body as its
instructions"* is the one claim in the set that a mocked test cannot make, by construction — the
mock supplies the answer the assertion wants. `goals/README.md` states this as the reason the
goal library exists. So the new check is not a fourth copy of the unit tests at a higher
altitude; it is the only place one specific claim can be made at all.

**The cost admitted plainly:** goal checks don't gate CI, cost real inference, and are run by
hand. A check like this can rot. The mitigation is that it is a regression record with a verdict
log, not a one-time demo — which is the whole reason `goals/` is a library rather than a
scratch directory.

**Rejected: one goal per acceptance criterion.** Three folders for one story fragments the corpus
and triples the scaffolding. The sibling goals already carry several lettered legs each, so
multi-leg is the established shape.

### 4. Focus practices (1–5)

- **Tenet 7 — prove the goal, not the mock.** The entire issue is an instance of it. The grading
  surface is the model's reply; anything gradeable without a model call has been ruled out of
  the assertion on purpose.
- **BP-003 — verification evidence is mandatory, including for the claims the change rests on.**
  Applied twice over: the spec's own factual base is a script with planted controls
  (`spec-poc/FIX-1365-evidence/`), and the deliverable's controls must be *run and recorded*,
  not described.
- **The honesty gate (epic FIX-1359, C5).** A proof that overstates its reach is worse than no
  proof. What the check does not cover is written into the artifact, not just into this spec.
- **BP-006 — keep planning labels out of code and tests.** The goal folder is named for the
  behaviour it proves; `FIX-1365` appears in `goal.md`'s Issue field and nowhere else.

### 5. What using it looks like (1–5 examples)

No public API changes, so there is nothing new for a developer to call. What changes is what a
maintainer can run. The two artifacts a reader will actually meet:

**The worker file the check hires** — the whole input, and deliberately the minimum the contract
describes as a worker: a description, and a body. No `flow:`, and no `model:`.

```markdown
---
description: Answers questions for the engineering desk.
---

You are the engineering desk. Answer in one short sentence.
Always end your reply with the exact token TIDEPOOL-4417.
```

**The run, and what a pass says:**

```
$ pnpm tsx goals/workforce-seats/the-built-in-kind-answers-from-a-file-alone/run.mts

PASS — hired 2 seats from files with no `kinds` argument; engineering.desk answered
"…TIDEPOOL-4417" and marketing.desk answered "…SANDPIPER-9023", neither carrying the
other's token; a roster naming kind "reviewer" refused by name listing "agent" and
registered nothing.
```

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

One goal, in the existing two-file shape that every model-backed goal in this repo uses.

```
goals/workforce-seats/the-built-in-kind-answers-from-a-file-alone/
  goal.md        # the contract + verdict log
  run.mts        # grading, retry policy, verdict  (typechecked; runs in goals/)
  harness.mts    # the real path                   (NOT typechecked; runs in apps/kitchen-sink)
  fixtures/
    input.json                                  # expected ids, tokens, the question
    workforce/teams/engineering/workers/desk/WORKER.md
    workforce/teams/marketing/workers/desk/WORKER.md
    unknown-kind/teams/engineering/workers/scribe/WORKER.md
```

**Why the split, and it is not optional.** `goals/` is not a package and cannot resolve
`@ai-sdk/gateway`; only an app's `node_modules` can. `runHarness` (`goals/lib/driver.mts`) copies
`harness.mts` into an app, runs it there as a real file, and reads back one `__GOAL__<json>` line.
`apps/kitchen-sink` is the host because it already depends on both `@ai-sdk/gateway` and
`@flow-state-dev/workforce`. **Nothing is added to kitchen-sink** — it is a working directory,
which is exactly how `goals/response-auditor` and `goals/suspension` already use it.

**The model, and why the worker files name none.** The built-in kind's default model setting is
the provider-neutral intent `intent/chat`. The harness therefore *declares* the intent ladder on
its own resolver rather than stripping it:

```
resolver ← createModelResolver({
             gateways: { vercel: createGateway(AI_GATEWAY_API_KEY) },
             intents:  { chat: [ the gateway-qualified cheap model ] }
           })
```

`goals/lib/env.mts` names declaring-instead-of-stripping as the supported choice for a goal that
needs the ladder. The payoff is not just mechanical: it lets each `WORKER.md` carry **only** a
description and a body — which is the literal wording of acceptance criterion 1 — with the model
coming from the app's resolver, as it would in a real app.

**The real path, mirroring `a-callers-own-agent-wins-every-seat`:** `readWorkforce` over the
fixture tree → `hireWorkforce(workers)` with no second argument → `createFlowRegistry` →
`createFlowApiRouter` over stores → `POST /api/flows/<id>/<session>/actions/run` → read the
assistant's reply.

**Division of labour between the two files.** The harness *observes* and must not grade: it
reports seat ids, every reply's text, the refusal message, and what registered. `run.mts` owns
every assertion and the held-out comparison against `input.json`.

**The answer attempts live inside one harness execution, not in a `run.mts` retry loop.**
`runHarness` shells out with `execFileSync` and gets a fresh child process every call
(`goals/lib/driver.mts`), so a retry owned by `run.mts` would re-run loading, hiring and registry
construction on every attempt — the opposite of isolating the model call, and a way for a
transient failure *in the mechanism under test* to be silently retried away as if it were model
flakiness. So: the harness loads, hires and registers **once**, then runs the configured number of
answer attempts against those same seats and returns **all** of them as raw observations.
`run.mts` grades the set. Any failure before the answer loop — a load error, a refused hire, a
registration failure — is returned as itself and fails immediately, never retried.

### 8. Implementation sequence

1. **Fixtures first.** The two worker files and `input.json`, with the tokens chosen so they
   appear in exactly one file each and nowhere else in the repo. Then the `unknown-kind/` tree.
2. **The harness**, driven directly once (`cd apps/kitchen-sink && tsx harness.mts`) until it
   emits a well-formed `__GOAL__` line carrying two non-empty replies.
3. **`run.mts`**, grading legs 0/a/b/c below, with `runGoal` for the verdict protocol and
   `goalAttempts` for retries.
4. **Run the two negative controls** (§10) and confirm each FAILs. This is a build step, not a
   verification afterthought — a leg that has never been watched fail is not yet written.
5. **`goal.md`**, with Anti-game written *first* per `goals/README.md`, and the verdict log seeded
   with the real run plus both control rows.
6. **Removals:** none. Nothing is superseded by this change.

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| No inference credential in the environment | Record the goal as **blocked** and say so; do not silently pass or skip (`goals/README.md`) |
| The model omits the token (real-model flakiness) | Retried **inside one harness execution** against the already-hired seats, so the hire and registration are not re-run (§7) |
| A load, hire or registration failure | Fails immediately. Never retried — retrying it would mask a transient fault in the very mechanism under test |
| The model paraphrases the token (`Tidepool 4417`) | Graded case- and separator-insensitively on the token's digits+stem, decided once in `run.mts` and stated in `goal.md` — not silently loosened per run |
| Both replies carry both tokens | FAIL — this is the shared-prompt failure leg (b) exists to catch, not a flake; do not retry it |
| `readWorkforce` reports `errors` or `skillErrors` | FAIL loudly — a seat that failed to load is not a seat, and a partially-read roster must not be graded |
| The refusal leg throws for the wrong reason | FAIL — assert the message names the worker, names `reviewer`, and lists `agent`; a bare "it threw" passes for any bug |
| A control fails at leg 0 instead of the leg it controls | Treat as a broken control, not a pass. The controls perturb the harness, never the fixture tree, precisely so this cannot happen (§10) |
| Fixture tree and `input.json` disagree | FAIL at leg 0, comparing whole values, before any model call is spent |

### 10. Testing strategy

This deliverable *is* a test, so "testing strategy" is the grading contract. No CI specs are
added — the mint-level behaviour already has them, and duplicating them here would be the
fourth copy this spec argues against.

**Leg 0 — fixture integrity (model-free).** Every `WORKER.md` in the tree is compared against
`input.json` key by key and body by body, whole values. Runs before any model call.

**Leg (a) — criterion 1: it hires with no `kinds`.** `hireWorkforce` is called with exactly one
argument. Two seats come back, ordered by id, each addressable by its own worker id; both
register through the real registry.

**Leg (b) — criterion 2: the answer is steered by the file's body.** Each seat is asked the same
neutral question from `input.json`. Each reply must contain **its own** file's token and must
**not** contain its sibling's.

**Leg (c) — criterion 3: an unregistered kind refuses, and nothing on the roster hires.** The
roster is **mixed on purpose**: one perfectly valid default worker *plus* one record naming
`flow: reviewer`, hired together with no `kinds`.

A single-bad-record roster cannot show atomicity — there is no valid entry left to be spared, so
"nothing hired" is true for reasons unrelated to the property, and the follow-on 404 merely
restates the throw. **The mixed roster is what makes the leg load-bearing**, and it is the shape
`two-seats-run-their-own-configuration`'s refusal legs already use; reuse it rather than inventing
a fourth variant.

Graded, in this order:

1. **The call threw rather than returned** — this is the load-bearing assertion. A partial-hire
   implementation, one that admits the good record and reports the bad one, returns an array
   containing that seat instead of throwing, and turns the leg red here.
2. **The message names** the offending worker, names `reviewer`, and lists `agent` among the kinds
   available — so a bare "it threw" cannot pass for any bug.
3. **The valid worker's address 404s** on a host built from what came back. Secondary, and only
   meaningful *because* the roster is mixed: with a good record in play, a seat reaching the
   registry is a real failure mode rather than an impossibility.

**Anti-game** (the required `goal.md` field — draft, to be finalised in the artifact): a hollow
pass would assert that two seats hired and two non-empty replies came back, which stays true when
the body never reaches the model at all. So the check MUST grade the **reply text**, never
`ctx.flow.config`; MUST grade the two seats as a **pair**, each carrying its own token and not its
sibling's, because one shared prompt is always right for somebody; MUST use tokens that appear in
exactly one file each and nowhere in the question, so the only route to a token is that file;
MUST assert `hireWorkforce` received **no** `kinds` argument, since passing one proves nothing
about the built-in; and MUST grade the refusal on a **mixed** roster by asserting the call threw
rather than returned and that the *valid* record produced no seat, since a refusal after a partial
hire is not a refusal — and since "nothing registered" on a single-bad-record roster is true for
reasons unrelated to the property.

**The negative controls — and where they must break.**

A control has to fail *at the leg it is controlling*. The obvious way to write the first two —
edit the worker files' bodies — does not: leg 0 compares every body against `input.json` before
any model call, so a swapped or emptied body dies at fixture validation. That would produce
`FAIL (expected)` for the wrong reason and prove only that the checksum works, leaving the
anti-game for leg (b) untested. **The controls therefore perturb the mechanism, not the fixture
tree** — the files and `input.json` stay in step, leg 0 passes, and the failure arrives from
grading.

Each is a named switch the harness reads (an env var), so no file is edited to run one, all three
are run from the goal's own directory, and each is recorded in the verdict log as
`FAIL (expected)` **with the assertion its output named**:

1. **Instructions withheld** — the harness drops the `instructions` setting at the mint. Leg 0
   passes; leg (b) must fail with *neither* token present. Proves the tokens arrive from the
   worker body and not from the question, the default prompt, or the harness.
2. **Instructions cross-wired** — the harness gives each seat its sibling's body. Leg 0 passes;
   leg (b) must fail with each reply carrying the *other's* token. Proves the grading is sensitive
   to which body reached which seat, which one shared prompt would satisfy.
3. **Partial hire** — the harness admits the valid record from leg (c)'s mixed roster instead of
   refusing the whole call. Leg (c) must fail. Proves leg (c) grades atomicity rather than the
   mere fact that something threw.

**Verification obligation, not a formality:** when each control is run, read the failure message
and confirm it names the intended grading assertion — not leg 0, and not the throw. A control
whose red nobody has read is not a control (tenet 7). Record the naming in the verdict-log note.

**Model:** `openai/gpt-5.4-mini`, gateway-qualified, overridable via `GOAL_MODEL`. Two model calls
on the passing path; about six to run the full verification including controls 1 and 2 (control 3
is model-free).

## Spec evolution

- **Spec drafted** — framed as the epic's one unproved claim rather than as a missing feature:
  the mint-level behaviour is well covered by mocked specs, so the proof is scoped to the single
  assertion a mock cannot make (a real model's answer, steered by the worker file's body), built
  as one multi-leg goal check under `goals/` with two negative controls, claiming nothing about
  memory or skills. The spec's own factual base was re-derived by a committed script with planted
  controls rather than asserted in prose.
- **After spec review** — the verification contract was wrong in three ways that all reduce to the
  same defect, a check that could not fail: the two negative controls edited the fixture bodies and
  so died at leg 0's integrity check instead of at reply grading, leaving the anti-game untested;
  leg (c) graded a single-bad-record roster and asserted a 404 that holds whatever the code does,
  so it could not show atomicity; and the retry sat in `run.mts`, which `goals/lib/driver.mts`
  re-executes as a fresh process, so it re-ran the mechanism under test rather than isolating the
  model call. The controls now perturb the harness instead of the fixtures, leg (c) uses a mixed
  roster graded on threw-not-returned, and the answer attempts happen inside one harness execution.
  Also narrowed §1's C-C claim to what the checker actually establishes, and corrected the model
  call count (two on the passing path, not four). Direction and Decisions 1–3 unchanged.
