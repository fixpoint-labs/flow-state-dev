# FIX-1366: Teach the built-in worker kind — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

The built-in worker kind shipped. A team can now drop a file carrying a description and
some instructions into their workforce tree and get a working worker, with no code at all.
That is the promise this whole epic leads with.

**Nothing we publish says so.** Every workforce page still teaches the world as it was a
week ago: supplying a `kinds` map is mandatory, and the kind you must write yourself is
called `worker-agent` — a placeholder whose name reads exactly like a built-in. So a reader
arriving today is taught to hand-build the thing they no longer need, under a name that
suggests it came with the box.

Three consequences, in the order a user meets them:

- **The headline feature is invisible.** No page, table or example mentions that an absent
  `flow:` now resolves to a worker we ship.
- **The example teaches the wrong shape.** `overview.md` and `workers-on-disk.md` open with
  a `kinds` map as the required step. A reader copies it and writes a custom kind for a job
  the default already does.
- **The placeholder is indistinguishable from the real thing.** `worker-agent` sits in prose
  beside the genuine built-in id `agent`. The executable surface already renamed it to
  `custom-agent` so the two could not be confused; prose did not follow, so the confusion
  now lives only where users read.

Separately, `docs/atlas/workforce.html` — which is **served publicly**, as GitHub Pages
uploads `docs/atlas` as the site root — still describes `defineAgent` as an "invent-kill
candidate" that "may not need to exist." It was removed. The Atlas is also the one workforce
surface a markdown-only sweep misses, because it is rendered HTML.

**Why now:** the kind is on `main`. Every day the pages stay as they are, the epic's
headline promise is one a user cannot find, and the placeholder keeps being copied.

---

### 2. Solution in plain terms

One new page teaches the built-in worker: what you get without writing any code, what you
can change, and what it does not do. `overview.md` leads with that zero-code path and demotes
the `kinds` map to the door you open when the default is not enough.

The placeholder is renamed to `custom-agent` everywhere prose teaches it, matching the
executable surface, so a custom kind can never be read as the one we ship.

The Atlas gets a factual correction pass — the rows the shipped kind made false, and the
removed API it still describes as pending — not a rewrite.

The epic's contract document is renamed to match the locked vocabulary, with its two inbound
links moved in the same change.

---

### 6. Decisions & rules — the sign-off surface

1. **The built-in worker gets its own page; `overview.md` leads with the zero-code promise
   and links to it.**
   *Rejected:* folding all of it into `overview.md`. What an app can change about the
   built-in — the tool catalog it may reach, the skills it is seeded with, the default model,
   the per-worker `tools:` fence, the up-front skill-matching switch — is a reference table.
   Inside an overview it either crowds out the orientation the overview exists to give, or
   gets cut to a sentence that sends people to read our source.
   *Locks in:* the out-of-the-box worker becomes a **documented product surface** with a URL
   we keep. The options table is a public promise: narrowing it later reads as a removal to
   anyone who built on it, whatever the code says.

2. **The page publishes now, stating plainly that the built-in does not remember across
   turns — rather than waiting for memory to land.**
   *Rejected:* holding the page until the memory work ships, so the first published account
   of the built-in worker is not carrying a caveat.
   *Locks in:* the first thing a prospective user reads about our out-of-the-box worker
   names a limitation on it, in public, for as long as memory takes. The alternative is
   that the feature stays undiscoverable in the meantime — which costs us the launch, not
   just the caveat. Structurally the line is cheap to delete later; the expectation it sets
   is what we are actually signing.

3. **The Atlas gets a factual honesty pass, not a restructure.**
   *Rejected:* rebuilding the workforce Atlas around the now-shipped built-in.
   *Locks in:* the Atlas stays a planning record corrected per-epic rather than a maintained
   product doc. It will keep drifting between epics, and each epic pays a small correction
   toll instead of one owner carrying it continuously. If we ever want it to read as a
   product page, that is its own piece of work and it is not this one.

**Non-goals** — reconciling the two skills entry points (FIX-1362 owns it; this spec only
stops the guide implying the built-in uses the one it does not); teaching how an app composes
memory in (FIX-1364); renaming `createChannelFlow` / `channelFlow` (FIX-1386, explicitly
fenced off); any Collab or channel teach-ahead; and rewriting the Atlas's internal voice or
stripping its Linear links, which is a pre-existing condition noted in §12.

**Size:** Small–Medium — 1 new page · 5 edited surfaces · 1 rename + 2 inbound links ·
0 new test behaviours (documentation change; verification is the docs build + two greps) ·
1 PR.

---

### 3. Tradeoffs & alternatives

**The main alternative: no new page — teach the built-in inside `workers-on-disk.md`.**
That page already carries a short replacement section describing the factory, added as a
correction when the kind shipped. Growing it is the smallest possible change.

It loses on discoverability. `workers-on-disk.md` is a page about the file convention; a
reader asking "what do I get for free?" has no reason to open it, and the sidebar gives them
no hint. The built-in worker is a *concept*, not a detail of the directory format.

**The simpler approach considered, and why it is not enough:** a pure find-and-replace of
`worker-agent` → `custom-agent` with no new page. That fixes the misleading name and nothing
else — the reader is still taught that a `kinds` map is mandatory, just with a better-named
example. It repairs the wrong half of the problem.

**What this trades:** one more sidebar entry in a section that currently has three pages, and
the ongoing cost of keeping an options table honest as the factory grows.

---

### 4. Focus practices

1. **The outsider rule is the binding constraint** (`docs/contributing/user-docs.md`). The
   pages describe what the worker does — never what it used to be called, which issue
   introduced it, or that a placeholder was renamed. The rename history in §7 is sweep
   material for the implementer, not page material.
2. **No internal issue or PR numbers anywhere under `apps/docs/`** (BP-006 and the writing
   standard). The Atlas is a different artifact and keeps its Linear links — see §12.
3. **BP-034 — finish the move.** The contract rename updates the filename, the title, the
   provenance header in the source file that cites it, and the reference-table row. Not just
   the links.
4. **Do not write the user-facing prose while holding this spec.** Dispatch `docs-writer`
   with a surface brief, then `docs-editor`. See §8.

---

### 5. What using it looks like

**A reader who wants a worker and has written no code.** Opens Workforce → Overview. The
first example is a worker file with a description and a body, and a hire call with no
`kinds` argument. They get a worker that talks.

**A reader who needs their worker to call their own tools.** Follows the link to the
built-in worker page, finds the factory, registers their configured version under `agent`,
and learns in the same place that doing so replaces the default for every seat on the roster.

**A reader who needs something the built-in is not.** Opens the built-in worker page, reads
what it does not do — including that it does not remember across turns — and goes to the
file-convention page to register a kind of their own under a name that is now clearly an
example (`custom-agent`), not a shipped default.

#### 7.3 The new page and the overview's new shape

New page at `apps/docs/docs/workforce/built-in-worker.md`, third in the sidebar after
`overview` and before `workers-on-disk` (it is a concept, and it precedes the file format).

It answers three questions in this order:

1. **What you get without writing code.** A worker file with a body and no `flow:` key hires
   into the worker we ship. Its body becomes the worker's instructions. It talks, and it can
   reach the skills the app handed over.
2. **What you can change.** The factory's three options — the tool catalog, the skills to
   seed, a default model — and the fact that calling it with arguments *replaces* the default
   for every seat, because there is no second configuration door on the hire step. Plus the
   two per-worker controls a record itself declares: `instructions` and `tools`, where
   `tools:` is a hard fence (a worker may call exactly the catalog keys it names; an empty
   list means none).
3. **What it does not do.** It does not remember across turns (Decision 2). Skills reaching
   it are seeded per app, not per worker, today. Neither is written as a roadmap promise —
   state the behaviour, not the plan.

`overview.md` changes shape: its first hire example drops the `kinds` argument entirely and
shows the zero-code path, with a following paragraph introducing `kinds` as what you pass when
you want your own worker kind — linking to the new page and to `workers-on-disk.md`. The
`workerAgentFlow` identifier in its example becomes `customAgentFlow` under kind
`custom-agent`.

`workers-on-disk.md` keeps its shape. Only the placeholder renames, plus one framing sentence
so its `kinds` map no longer reads as mandatory.

#### 7.4 The Atlas pass (`docs/atlas/workforce.html`)

Rendered HTML, published at the Pages site root. Correct **only** the statements the shipped

- Line 577 — `worker-agent` named as a built-in. The built-in kind id is `agent`; a custom

- The `defineAgent` / `materializeAgent` rows that read as *pending* decisions ("invent-kill
  candidate", "may not need to exist", "kill it") — these are now **done**, and saying a

- The `origin/main` pin line (line 242) — re-pin to the commit this work lands against, with
  its date.
- Any row asserting a `kinds` map is required at hire.

Leave the fence, the sequence, the vocabulary and the voice alone. Entity-escaped HTML
(`&#8212;` etc.) is the file's existing convention — match it.

#### 7.5 The contract rename

`docs/architecture/workforce-agent-kind.md` → **`docs/architecture/workforce-default-worker-kind.md`**,
title `# The Default Workforce Agent Kind — Locked Contract` →
**`# The Default Workforce Worker Kind — Locked Contract`**.

Rationale: the locked vocabulary is *worker* as the product noun, with `agent` as one kind of
worker. "Agent kind" as a filename teaches the noun we moved away from; "worker kind" is the
phrase the vocabulary endorses, and the document is specifically about the **default** one.

Use `git mv` so history follows. Both inbound references move in the same commit:

- `docs/contributing/architecture-reference.md:42` — link target **and** link text
  ("Default Workforce Agent Kind" → "Default Workforce Worker Kind").
- `packages/workforce/src/agent-worker-flow.ts:15` — a provenance comment in the file header.
  This is the BP-034 one that a link checker will never catch.

**Do not** rewrite the contract's body. Its §C6 migration text (lines ~269–278) describes the
sweep this issue performs; leave it as the record of the split. It is an internal architecture
doc, not published surface.

### 12. Dependencies, open questions & follow-ups

**Dependencies:** none blocking. The kind is merged to `main` (commit `210e47679`), which is
this spec's base.

**Coordination seam worth watching — FIX-1364 and the memory line.** The contract splits
memory: FIX-1364 owns the composition-seam design and the teaching surface for *how* an app
composes memory in; this issue owns saying honestly that the built-in has none. Both write
about memory on the workforce teaching surface, and FIX-1364 is in flight in parallel. The
split is clean in principle — a statement of current behaviour here, a how-to there — but if
FIX-1364 lands its page first, the honest line in Decision 2 should link to it rather than
repeat it. Not a blocker; a merge-order note.

**Open question, deliberately not settled here — the Atlas's voice.** `docs/atlas/*.html` is
served publicly as the Pages site root, but is written as an internal planning record: Linear
issue links, commit pins, owner rulings, terse fence prose. Our writing standard says no
internal issue numbers in published prose. Either the Atlas is not really published surface
(and the Pages upload is the bug), or it is and its voice is wrong. **This spec assumes the
former and changes nothing about it** — Decision 3 keeps the pass factual. Worth an Architect
ruling and its own ticket; it is not this issue's to decide, and it would swallow it.

**Follow-up, already ticketed:** FIX-1386 renames `createChannelFlow` / `channelFlow`.
Explicitly fenced out of this issue.

**Follow-up worth filing:** the skills guide (`apps/docs/docs/skills/overview.md`) leads with
`createSkillsCapability` while `binding.md` already calls it "the older" path and the built-in
worker uses `createSkillsLibrary`. The contract flags correcting this as this issue's, but
reconciling the two entry points is FIX-1362's. This spec takes only the narrow half: the new
page must not imply the built-in uses the capability. Re-ordering the skills guide's emphasis
should wait for FIX-1362 and be its own change.

## Spec evolution

- **Spec drafted** — framed from the brief as four sweeps plus a rename. Research collapsed
  two of the four to zero-change findings (§7.2): the superseded factory names were already
  fully absorbed, and the "killed agent surface" on published pages turned out to document a
  live bring-your-own option surface correctly. What remained was the thing the brief listed
  last and the epic cares about most — **nothing teaches the built-in worker at all** — so the
  spec was re-centred on a new page, with the sweeps as supporting work rather than the point.
