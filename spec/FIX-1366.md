# FIX-1366: Teach the built-in worker kind — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

The built-in worker kind shipped, and — unlike what an earlier draft of this spec claimed —
**it was documented when it shipped.** `apps/docs/docs/workforce/workers-on-disk.md` carries a
section, "The worker you get without writing one" (line 258), that teaches the zero-code hire,
the body becoming instructions, the no-memory line, the shared-skills honesty line and the
factory replacement. It is good, accurate prose. `packages/workforce/README.md` covers the same
ground.

**The gap is not absence. It is that nobody finds it, and what they do find is incomplete or
misleading.** Three specific failures, in the order a reader meets them:

- **The front door never mentions it.** `overview.md` is where the Workforce section starts,
  and its "Hire a roster" example still leads with a `kinds` map as the required step. A
  reader whose question is *"what do I get without writing code?"* is answered on a different
  page, two-thirds of the way down, under a heading they have no reason to open — it sits at
  line 258 of a page about the **file format**.
- **The example teaches a name that reads like a shipped default.** Both pages and the README
  still demonstrate custom kinds under the placeholder `worker-agent`, sitting in prose beside
  the genuine built-in id `agent`. The executable surface renamed it to `custom-agent`
  precisely so the two could not be confused; prose did not follow, so the confusion now lives
  only where users read.
- **The reference is thin where being thin is wrong.** The section says the built-in's settings
  are "`instructions`, `model`, and `tools` — plus a switch." The shipped API has **five**
  app-level options and **four** worker settings. A reference that undercounts a public surface
  sends people to read our source.

Separately, `docs/atlas/workforce.html` — **served publicly**, as GitHub Pages uploads
`docs/atlas` as the site root — still describes `defineAgent` as an "invent-kill candidate"
that "may not need to exist." It was removed. The Atlas is also the one workforce surface a
markdown-only sweep misses, because it is rendered HTML.

**Why now:** the kind is on `main` and is the epic's headline. Every day the front door stays
as it is, the promise is one a reader has to go looking for, and the placeholder keeps being
copied.

---

### 2. Solution in plain terms

**Grow and promote what already exists — do not write a second copy of it.**

`overview.md` leads with the zero-code hire and links by anchor into the section that already
teaches it, so the front door answers the question it is asked. That section grows only where
its reference is genuinely thin: the complete inventory of what an app can configure and what
a worker declares. The placeholder renames to `custom-agent` everywhere prose teaches it, so a
custom kind can never be read as the one we ship.

The Atlas gets a bounded factual correction pass. The epic's contract document is renamed to
match the locked vocabulary, and a false statement in the shipped source's own module docstring
— found during this spec's review — is corrected alongside it.

### 6. Decisions & rules — the sign-off surface

1. **The built-in is taught where it already lives: `workers-on-disk.md`'s existing section
   grows, and `overview.md` promotes it by anchor. No new page.**
   *Rejected:* a new `apps/docs/docs/workforce/built-in-worker.md` as the canonical home — and
   also the thinner variant of it, a stub page that exists only to redirect. This spec argued
   for the new page in an earlier draft on the premise that nothing taught the built-in at all.
   That premise was false (§1), and with the content already written and good, a new page buys
   a URL and a sidebar entry while creating a second surface to keep in step.
   *Locks in:* the Workforce section keeps one page per concept, matching `channels.md`, which
   teaches what a channel is, how it is declared, how to register a kind of your own, and what
   it does not do yet — all in one place. Discoverability now depends on the overview's lead
   and the anchor link rather than on a sidebar entry, so if that promotion is weak the problem
   comes back as "still hard to find."

2. **The reference becomes complete: all five app options and all four worker settings, with
   the emphasis unchanged.**
   *Rejected:* publishing "three settings plus a switch" as though it were the whole surface.
   An acceptable alternative the Architect named: document the three core options and
   **explicitly** defer the two classifier-tuning knobs in one line. What is not acceptable is
   an inventory that reads as complete and is not.
   *Locks in:* `classifierModel`, `confidenceThreshold` and `skills.enableLlmClassifier` become
   documented public surface, so narrowing them later reads as a removal. The emphasis rule is
   part of the decision, not decoration: the LLM classifier is **opt-in and off by default**,
   the stock path is the default-active set plus `/skill-name`, and the prose must not leave a
   reader feeling they are expected to turn it on.

3. **The Atlas gets a bounded factual pass on `workforce.html`, not a restructure.**
   *Rejected:* rebuilding the workforce Atlas around the shipped built-in; and extending the
   pass to the three sibling atlas pages, which would make this issue a full Atlas hygiene
   sweep.
   *Locks in:* the Atlas stays a planning record corrected per-epic. Its sibling pages keep
   asserting a removed API exists until FIX-1387 picks them up (§12) — a known, recorded
   residue rather than a silent one.

**Acceptance criterion carried out of an earlier draft's Decision 2.** The no-memory disclosure
already ships at `workers-on-disk.md:270`, so there is no publish-now-or-hold fork. The
criterion is that **the reshaped overview and the grown section keep the no-memory statement at
least as prominent as it is today** — a reader who meets the built-in through the new front door
must meet its limits too, not only through the old path. It is stated as current behaviour, not
as a roadmap promise.

**Second acceptance criterion — the `tools:` fence is taught with its hole named.** Per an
Architect ruling (epic PR #1730), the hard-fence guarantee stands and core will be changed to
enforce it; a rebrand to "convention" was rejected. Until that lands, the page states the
guarantee *and* names the residue — capability-contributed tools are currently unioned onto a
block's declared `tools:` rather than intersected. Written as behaviour and a known limit, not a
roadmap promise. Mechanics in §7.3.2.

**Non-goals** — reconciling the two skills entry points (FIX-1362); teaching how an app composes
memory in (FIX-1364); renaming `createChannelFlow` / `channelFlow` (FIX-1386); the Atlas's voice
and publication question and its sibling pages (FIX-1387); **changing core's tool resolution**,
which has its own issue and migration story; any Collab or channel teach-ahead.

**Size:** Small — 0 new pages · 5 edited surfaces · 1 rename + 2 inbound refs · 1 source
docstring fix · 0 new test behaviours (verification is the docs build + two scoped greps) ·
1 PR.

### 3. Tradeoffs & alternatives

**The main alternative, and this spec's own earlier answer: a new `built-in-worker.md`.** It
was argued on discoverability — the built-in is a *product concept* while `workers-on-disk.md`
is the *file format*, and a reader asking "what do I get for free?" has no reason to open a
page about directory layout. That reasoning is still sound as far as it goes.

It loses on the evidence. Once you have read the existing section, the new page is not creating
teaching, it is relocating it, and a relocation buys discoverability only through the sidebar
entry — which an anchor link from the overview's lead example buys at no structural cost. The
duplicate-maintenance risk it introduces is real and the benefit is one URL.

**The thinner version is worse, not safer.** A stub page that only points at the real content
adds a URL and a sidebar row while teaching nothing, and it splits a reader's attention at the
exact moment they are trying to get oriented.

**What this trades:** discoverability now rests entirely on the overview's lead paragraph and
one anchor link. There is no sidebar entry reading "the built-in worker," so a reader browsing
the sidebar alone still will not see the concept named. If the promotion proves too quiet,
the fix is a sidebar label change or a page split — both cheap, and both better made once
someone has actually failed to find it.

### 5. What using it looks like

**A reader who wants a worker and has written no code.** Opens Workforce → Overview. The first
example is a worker file with a description and a body, and a hire call with no `kinds`
argument. One line tells them this is the built-in and links them straight to the section that
covers it.

**A reader who needs their worker to call their own tools.** Follows that link, finds the
complete options table, registers their configured flow under `agent`, and learns in the same
place that doing so replaces the default for every seat on the roster.

**A reader who needs something the built-in is not.** Reads, in the same section, what it does
not do — including that it does not remember across turns — and continues down the same page to
"When a worker needs more than settings," where the example kind is now clearly an example
(`custom-agent`) rather than a shipped default.

#### 7.3.1 The complete inventory

Verify against `packages/workforce/src/agent-worker-flow.ts` at implement time; these line
references are a snapshot.

**What the app supplies — `AgentWorkerFlowOptions`, five options** (`:77–102`):

| Option | What it is |
|---|---|
| `catalog` | The tools workers may name in `tools:`. Omitted, the built-in carries none |
| `skills` | Skills seeded into the library every seat of this kind reads |
| `model` | Default model for workers that name none |
| `classifierModel` | Model the up-front matcher's opt-in third tier uses |
| `confidenceThreshold` | Confidence that tier must reach |

**What one worker declares in its own file — four settings** (`:114–161`): `instructions`,
`model`, `tools`, and `skills.enableLlmClassifier` (**default `false`**).

**Why the last two app options are app-level and not per-worker** is worth one sentence,
because it is the kind's governing principle: the matcher is built once for the kind, so a
per-worker value could not be honoured — and a setting that is silently ignored is exactly the
failure this kind's tool handling exists to prevent.

**Emphasis rule — complete reference, unchanged emphasis.** Document the knobs truthfully; do
**not** let the prose promote the classifier as something to reach for. It is opt-in and off by
default so a zero-configuration worker never spends an extra model call per turn deciding
whether a skill applies. A reader should finish knowing the knob exists with no impression they
are expected to enable it. (§6's permitted alternative: document the three core options and
defer the two tuning knobs in an explicit one-liner. Not permitted: an inventory that reads as
complete and is not.)

#### 7.3.2 The `tools:` fence — teach the guarantee, name the hole

A worker's `tools:` is published as a **hard runtime fence**: a seat may call exactly the
catalog keys it names, and an empty list means none. **Teach that guarantee — it is the
intended contract and it is what core will enforce.** An Architect ruling settled this: the
fence stands, core will be changed to enforce it, and a rebrand to "convention" was explicitly
rejected because it would silently fork the published C1 contract and the owner-facing refusal
text.

**But it is not unconditionally true today, and the page must not claim it is.** Core currently
**unions** capability-contributed tools onto a block's declared `tools:` rather than
intersecting them — `packages/core/src/blocks/generator.ts` resolves to
`return [...base, ...staticTools, ...dynTools]`. So a capability mounted on the generator can
put a tool on it that the worker never named.

The stock built-in holds the line, which is why this is a hole and not a breach: it hands the
skills library the app's catalog with registration turned off
(`createSkillsLibrary({ catalog, registerCatalogTools: false })`), so the library never
registers a catalog tool itself, and the generator's own `tools: names → catalog[name]` mapping
stays the only stock registration path. The gap opens for an app that mounts a capability which
*does* contribute tools and has not opted out.

**How to write it:**

- State the guarantee plainly and first. It is the contract, not an aspiration.
- Then name the residue in one or two sentences: capability-contributed tools are currently
  unioned rather than intersected, so the guarantee holds for the stock worker and for
  capabilities that opt out, and core enforcement is coming.
- **Behaviour and a known limit, not a roadmap promise** — the same discipline the no-memory
  line already follows. No dates, no "soon".
- **The enforcement work is [FIX-1393](https://linear.app/fixpoint-labs/issue/FIX-1393)** ("Tools
  fence is a documented guarantee, not an enforced one — capability tools union onto declared
  `tools:`"). That id is for *this spec's* reader, not for the page: **no issue numbers go into
  `apps/docs` prose** (BP-006 and the writing standard). On the page the limitation is stated as
  behaviour, unattributed. The id is here so the implementer can check whether FIX-1393 has
  already landed — if it has, the residue sentence comes out and the guarantee is taught flat.

This is the epic's gap-honesty discipline applied once more: we publish a guarantee, and where
it does not yet fully hold we say so rather than letting the sentence quietly overstate.
