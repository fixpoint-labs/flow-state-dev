# FIX-150: Workspaces — the file-projection component and where a run's files live — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

An agent that works with files needs somewhere to put them, and the framework needs those
files back afterwards. That machinery exists once today, welded to the shell tool. Only an
agent that runs shell commands gets a workspace.

The coding-agent path has none of it. A coding run inherits whatever directory the FSD
server happens to be sitting in, reads and writes there, and nothing it produces comes back
as state. Nothing stops it writing anywhere else on the machine either.

**Why now.** This issue was filed with a gate on it — *validate that real usage requires
this abstraction before investing.* The Conductor epic (LAB-68) has cleared that gate. Its
layer-zero work established that a coding-harness run **is** an FSD session and that a run's
file writes are state the layers above have to read; LAB-134 delivered an *index* of those
writes and explicitly kept the file contents out of scope — "we keep an index into the
working tree, not a copy of it." The copy is this issue, and everything above L0 in that
epic reads it.

Two more things make the timing real. The one implementation we have carries a live
data-loss bug (FIX-998): two runs sharing a collection delete each other's files. And the
containment the coding path would inherit is not what anyone would choose — measured on a
real run, files we project into a workspace can silently reconfigure the agent that reads
them.

### 2. Solution in plain terms

Pull the workspace machinery out of the shell tool and make it a component in its own
right. It takes a set of resource collections, lays them out as files in a place, and later
reads that place back and works out what changed. The shell tool becomes one caller of it.
A plain directory that a coding agent is pointed at becomes another.

Two things travel with the move. The projection **remembers what it laid down**, so reading
back can tell "someone else changed this" from "nothing changed" instead of overwriting
either way — that is the data-loss bug, fixed at the point both callers pass through. And
because the second caller is a real coding harness with a real shell, **the framework states
that harness's containment** rather than inheriting it.

**Philosophy.** Tenet 5 (fix at the owning layer) — the same walk-and-diff exists in two
copies and the bug lives in both, so the fix belongs where they converge. Tenet 3 (earn
every addition) — this ships one component that replaces two, and does **not** build the
`workspaceRunner` block the issue names. Tenet 2 (composition over features) — a workspace
is a composition of collections and a place, not a new primitive.

**In tension with tenet 3:** it adds a package. The alternative — leaving the component in
the tools package — makes the coding-agent path depend on six sandbox adapters and a
shell-quoting library to obtain a file projector. The dependency weight is the reason, and
it is stated as a decision below rather than buried.

### 6. Decisions & rules — the sign-off surface

1. **We build a projection component, not the `workspaceRunner` block the issue names —
   and both existing copies of the machinery collapse into it in the same change.**
   *Rejected:* shipping the block as specified, and leaving today's two copies beside it.
   *Locks in:* the shell tool's file behaviour changes in the same release as the new
   capability, so there is one behaviour to document, teach and support instead of two that
   drift. The bill arrives now rather than later: anything written against today's exported
   sync class breaks in this release.

2. **The live data-loss bug rides this change.** The projection remembers the content it
   laid down, so reading back reports a conflict instead of silently overwriting or
   deleting. That memory is the fix, and it is the only thing riding here: the default
   workspace scope does not move (§7). FIX-998 closes when this lands.
   *Rejected:* fixing FIX-998 first, on the code this change deletes. Also rejected:
   flipping the default from a per-session directory to a per-run one under this decision.
   It is a separate behaviour change, it does not fix the bug, and `"run"` ships as an
   explicit scope instead.
   *Locks in:* the window in which two concurrent runs can destroy each other's files stays
   open until this ships rather than until a smaller fix ships. Reversible — the smaller fix
   is still available if that window turns out to bite someone first.

3. **The framework states the coding harness's containment, it covers every write-capable
   tool, and it fails closed.** A projected workspace never configures the agent reading it,
   the available tool list is stated rather than inherited, and OS-level write confinement
   is on by default — on a host that cannot provide it, a run refuses to start rather than
   running uncontained. The fence takes three mechanisms rather than one: OS confinement
   over sandboxed shell commands, the shell's unsandboxed escape disabled, and the approval
   seam checking the target path of every write-capable tool. Only the first was measured
   (§12), and a fence with holes that fails closed buys the deployment friction without
   buying the guarantee.
   *Rejected:* inheriting the harness's own defaults and documenting the risk; and fencing
   the shell alone, when a built-in file tool has already been seen writing to the
   filesystem root from inside a run.
   *Locks in:* an app deployed to a host without the sandbox dependencies will see
   coding-agent runs refuse until an operator installs them or explicitly opts out. We are
   choosing a deployment-visible failure over a silent one, and the opt-out is a config
   line, not a code change.

**Non-goals.** No content-addressed store — resources already hold content, and a CAS beside
them is a second store with its own retention question. No conflict *resolution*: the
projection reports a conflict and stops; who merges it is a separate design question
(FIX-998 draws the same line). No git: no worktree strategy, no GitResource — measured and
rejected, see §12. No change to the sandbox adapter set or to the `user` / `org` workspace
scopes. No filesystem watchers — hydrate and flush stay explicit calls. No distributed
locking across processes.

**Size:** Large — 13 production files · 14 test behaviours · 4 doc surfaces · 4 PRs.

---

### 3. Tradeoffs & alternatives

**Alternative: leave it in the tools package and have the coding path import it.** No new
package, and the code is already there. Rejected on dependency weight and layering: the
coding-agent package would pull in six sandbox adapters, a shell-quoting dependency and the
whole bash block surface to obtain a file projector. The projector's real dependency set is
the core resource types and a place to write.

**Alternative: build the `workspaceRunner` block the issue names.** Rejected. A block that
hydrates, runs, and flushes is a sequencer composition, and `createBashBlocks` already
expresses it. Adding a named block for it puts a second route to one job on the public
surface, which is the shape tenet 3 rejects.

**The simpler approach: add `cwd` to the coding-agent options and stop.** Genuinely
tempting, and one field. The POC confirms it works (§12). Insufficient because it hands the
run a directory with nothing in it and nothing coming back out: the files never become
state, which is exactly what the epic above this needs. It also ships the containment
defaults the POCs measured to be wrong, and it leaves the data-loss bug where it is.

**Where the complexity is:** not the walk. It is flush's three-way outcome — unchanged /
clean write / conflict — and the fact that a *delete* needs the same evidence as a write.
FIX-998's own notes record a first fix that closed the write path and left the delete path
open, which is the mistake to design against rather than rediscover.

### 4. Focus practices (1–5)

1. **BP-031 (never decide from caller-controllable input)** — a projected workspace is built
   from resource collections, which an application's users write. A POC measured that such a
   workspace's own settings file and instruction file are honoured by the agent reading it
   unless we say otherwise. The workspace is caller-controllable input; the agent's
   configuration must not come from it.
2. **Tenet 5 — one convergence point** — flush's write path and its delete path are two
   writers of one invariant ("never destroy evidence you do not have"). Both must pass the
   same check, and the producers include the orphan path and the read-only-mount path.
3. **Tenet 7 / BP-003 — the check must be able to fire** — a hydrate-then-flush round trip
   only fails when the mechanism is broken. The goal check has to fail in the world we are
   in today. §10 states it in those terms.

### 5. What using it looks like (1–5 examples)

**A shell-tool call site does not move** *(what this spec proposes; the behaviour underneath
changes, the code does not):*

```ts
const { bashCommand } = createBashBlocks({ provider: { type: "local" } });
// Same call, same auto-discovery of mounted collections. What changes: flush now
// reports a conflict instead of silently overwriting, and never deletes a path it
// did not lay down.
```

**A coding agent gets a projected workspace** *(new — today this call inherits the server's
directory, returns nothing to state, and takes no `uses` — §7 adds the slot):*

```ts
const coder = claudeCodeAgent({
  uses: [createWorkspaceCapability({ collections: ["artifacts"] })],
});
// The run starts in a directory containing artifacts/ laid out from the collection.
// On end of turn, what it wrote there is read back into the collection.
```

**What a conflict looks like from the caller's side (before / after):**

```
before  two runs flush over one collection
        → run A's new file is deleted by run B's flush; A's edit is overwritten by B's

after   two runs flush over one collection, each owning a disjoint path in it
        → both files survive, and neither run reports a conflict

        and when something outside the projection changed a path under us
        → that path is reported as a conflict carrying the base we laid down,
          their version, and ours — and is not written
```

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

A new package, `@flow-state-dev/workspace`, holds the projection. It depends on the core
resource types and nothing else. Two consumers today; a third (Conductor's L0) in sight.

```mermaid
flowchart TB
  subgraph collections["resource collections (the durable store)"]
    A[artifacts/**]
    S[skills/**]
  end

  P["@flow-state-dev/workspace<br/>mounts · hydrate · flush · baseline"]

  collections -->|hydrate| P
  P -->|flush: unchanged / write / conflict| collections

  P --> PL1[place: host directory]
  P --> PL2[place: bash sandbox]

  PL1 --> C["coding harness run<br/>cwd = the directory"]
  PL2 --> B[bash tool blocks]
```

- **`@flow-state-dev/workspace`** — owns mounts (a collection, its prefix, whether it is
  writable), whatever ownership state the overlap check ends up needing (a requirement with a
  named goal, not a settled mechanism — below), the hydrate/flush pair, the per-path **baseline** (recorded at hydrate, advanced on every
  clean write — full lifecycle below), and the routing rules. Exposes a narrow **place**
  interface: read one path, write one path, list the paths under a set of prefixes.
  Deliberately *not* `Sandbox` — the projection never executes a command.
- **`@flow-state-dev/tools`** — `createBashBlocks` and `createBashTool` both delegate to it;
  the `Sandbox` adapters are wrapped as a place. `file-sync.ts` is **deleted** and its export
  removed, along with the duplicate hydrate/flush inside `blocks.ts`.
- **`@flow-state-dev/claude-code`** — the SDK options interface gains the fields a projected
  workspace needs and a `uses` slot to install a capability at all (both below), plus a
  workspace capability that hydrates before the run, flushes at end of turn, and sets the
  containment.
- **Untouched:** the sandbox adapter set, the resource system, the item taxonomy, block kinds.

**The seam that composition needs does not exist yet, and it is two additions.** §5's
`claudeCodeAgent({ uses: [...] })` does not compile today: the factory takes
`ClaudeCodeAgentOptions` (`packages/claude-code/src/sdk/agent.ts:57`), which has no `uses`
field. Nor is there a generic before/after wrapper to reach for instead — a capability
contributes resources, state schemas, targets, `fns` and generator presets and nothing else
(`CapabilityConfig` and `PresetDef`, `packages/core/src/capability/types.ts`), a block's own
lifecycle hooks are `onCompleted` and `onErrored` only (`packages/core/src/types/block.ts:805`)
with no before-execute hook at all, and a capability cannot contribute even those two. So:

1. **`claudeCodeAgent` forwards a `uses` slot to its `handler()` call.** `handler` already
   accepts `uses` (`packages/core/src/blocks/handler.ts`); the factory simply never passes one.
   This is the `UsesSlot` forwarding convention the pattern factories already follow —
   `planAndExecute`, `supervisor`, `debate`, `roundRobin`, `routedSpecialists`.
2. **The agent block's own `execute` is the lifecycle seam, and it already exists.** It is the
   one place both ends are reachable: hydrate before `query()`, and flush from the harness's
   end-of-turn hook threaded into the query options (POC 3 measured that hook holding a real
   flush). The capability supplies both as `fns` — `ctx.cap.workspace.hydrate()` / `.flush()` —
   and `execute` calls them when the capability is installed.

Point 2 is a real coupling and is stated rather than hidden: the agent block has to know a
workspace capability may be present, because nothing in the capability system can wrap its
execution. Adding a general before/after wrapper to capabilities would be a core change
needing its own justification, and is deliberately not proposed here.

**Placement strategies behind the place interface — two, not three.** The bash sandbox and a
host directory pointed at by `cwd`. The SDK's own worktree machinery was evaluated as a
third and rejected on measurement (§12): it is git-only in its built-in form, and the
host-implementable form only ever fires when the *model* asks for it, so it is a mid-run
relocation seam rather than a placement the framework can choose. The projection therefore
does not build on it, and the containment defaults **omit the tools that trigger it** so a
run cannot relocate out from under a projection.

**Isolation unit: `run` becomes available, `session` stays the default.** Today a workspace
is per session, so N runs in one session share one mutable directory with no coordination —
which is FIX-998's blast radius. `WorkspaceScope` gains a fourth member, `"run"`: one
directory per run, chosen explicitly. The default does **not** move. We cannot tell from
outside whether real usage depends on a workspace surviving between turns in a session, and
an unknown of that shape argues against a default flip rather than for one — flipping is a
behaviour change nobody asked for, riding a change asked for on other grounds. Isolation is
not what fixes the bug in any case: it removes contention between our own concurrent runs,
and it does **not** replace the baseline check, because a collection can also be written by
an action block, another tool, or another session over a `user`/`org` scope.

**No path gets two writers without one of them being told — the goal, stated as a requirement
rather than a mechanism.** Flush is a read-compare-write, and nothing in the store layer can
make it atomic: `ContentStore.set(scopeType, scopeId, resourceKey, content)` takes no version
and overwrites unconditionally, and the `expectedVersion` machinery that does exist
(`resource-cas.ts`, `resource-state-predicate.ts`) guards resource **state**, not content. A
second writer therefore has to be caught above the store. What catching it has to achieve is
fixed here; how it is caught is not:

- **Both consumers get at least a basic overlap check** — the bash tool and the coding agent
  alike. Neither ships a projection that can double-write a path in silence.
- **Failing loudly satisfies the requirement.** A refused second writer that tells its caller
  to try again is a legitimate outcome: the caller learns its work cannot proceed as framed
  and gets to re-frame it or retry.
- **Silent double-writing does not satisfy it.** That is the whole bar, and it is the part
  that is not negotiable.

**The mechanism, the default and the granularity are the implementer's calls, made with the
code in front of them.** This is a deliberate demotion. The analysis below is the best
available and is kept in full, but it is now *evidence for those calls* rather than a design
to execute — the shape and its real cost are legible from inside the code and were being
guessed at from outside it.

**The unit that makes §10's first goal reachable is the projected path** — not the collection,
and not the mount. Two runs may share a collection, and share a mount inside it, so long as
the paths they touch are disjoint: one under `artifacts/spec/**` while another is under
`artifacts/src/**`. Both finish, both results land in the same collection, and neither
contests anything the other touched. A coarser unit rules that goal out rather than delivering
it, so whatever check is built must not fire on disjoint paths.

**Allocation by one actor is cheaper than negotiation between two.** If the owned paths come
from the single place that dispatches the runs — a coordinator that knows the split before it
starts anything — there is no distributed agreement to reach and nothing to acquire, and the
projection's own job is the cheap half: hold the owned prefixes and reject an overlap, using
the same longest-prefix comparison mounts are already matched by. That was the earlier
design's core and it remains the cheapest shape on the table.

**The implementer's decisions, and the evidence to make them from.** Each fact below was
checked against the code on this branch. Re-check anything you lean on.

*1 — The public API delta can credibly be zero.* Prefixes are already **derived**, not
configured: `discoverMounts` computes `const prefix = getPatternPrefix(value.pattern);`
(`packages/tools/src/bash/blocks.ts:286`). Both lifecycle seams already receive the block
context — `getOrCreate(ctx)` (`blocks.ts:715`) and `releaseBashSandbox(provider, ctx)`
(`blocks.ts:1025`) — and `BlockContext.request` (`packages/core/src/types/block.ts:215`) is a
`RequestScopeHandle` carrying `identity: ScopeIdentity` with an `id`
(`packages/core/src/types/scope.ts:130-135`). A claim-and-release can therefore live entirely
inside `blocks.ts` with nothing new on the surface. And if a field *is* added it is pure
widening: every option on `CreateBashToolOptions` (`packages/tools/src/bash/types.ts:315`),
`CreateBashBlocksOptions`
(`blocks.ts:62`) and `CreateBashCapabilityOptions` (`capability.ts:43`) is already optional,
and all three factories default their whole options bag (`create-bash-tool.ts:53`,
`blocks.ts:706`, `capability.ts:209`).

On `createBashTool` specifically: the out-of-flow call path the docs show
(`apps/docs/docs/tools/bash.md:208`) is **not** a constraint on this design. We call
`createBashTool` inside a flow. If it needs an owner token to participate in the check, assume
one is present. Do not build the design around preserving out-of-flow allocation — and do not
go the other way and propose deprecating that path either. It is simply not a case this
optimises for.

*2 — On-by-default versus opt-in is the real fork, and it is a behaviour decision with no
signature change.* Opt-in leaves every existing caller unguarded and makes the rule a config
knob rather than a guarantee. On-by-default makes the rule real, at the price that a second
same-session writer which today silently double-writes starts being refused. Nothing in this
repo does that today, so no in-repo caller changes behaviour either way.

*3 — Per-run versus per-session granularity, and what the second one costs.* The sandbox
registry (`blocks.ts:181`) is keyed by scope alone: `resolveScopeKey` (`blocks.ts:227-241`)
returns `session:<id>`, `user:<id>` or `org:<id>`, with **no request dimension** anywhere in
it. Two routes, and this table is a price list rather than a recommendation:

| Route | What it buys | What it costs |
|---|---|---|
| A claims field on `SandboxEntry` (`blocks.ts:158-165`), arbitrating inside the shared sandbox keyed by `ctx.request.identity.id` | Overlap arbitration between concurrent requests in one session. Cheap; nothing public moves; same-session sandbox sharing is unchanged | Not per-run isolation — one directory, two runs, arbitration layered on top |
| A request dimension added to the registry key | Correct per-run isolation, the same unit `"run"` scope names | Same-session concurrent requests stop sharing a sandbox. Every non-`local` provider is pinned to `session` scope in `getOrCreate`, so under MOAT this is one container per request instead of one per session — and a cold start there "takes a few seconds" (`apps/docs/docs/tools/bash.md:212`). A real cost and a real latency regression |

*4 — A constraint, not a suggestion: if the design keeps an allocation ledger as a resource,
declare it as a single `ResourceRef`, never a collection.* `discoverMounts`
(`blocks.ts:274-298`) walks `ctx.resources` and mounts **every** `ResourceCollectionRef` it
finds at its pattern prefix, defaulting to `writable: true`. A ledger declared as a collection
therefore becomes a writable directory inside the bash workspace — the projection would hand
the run the very record that governs it. A single `ResourceRef` fails the `isCollectionRef`
check and is never mounted.

*5 — If a ledger resource is declared, it belongs on the capability, not on the tool blocks.*
A generator is a leaf whose own declarations equal its bubble-up set
(`packages/core/src/blocks/generator.ts:2718-2720`), and `collectBlockResources` runs over the
action roots plus detached-worker runners (`packages/core/src/flow/defineFlow.ts:1058`, over
`declaringBlocks`) — **not** over `graph.toolRoots`, which feed only the workstream-binding
collector. A resource declared on `bashCommand` would never reach `flow.resources`. Adding
`resources` to the bash capability is fully additive: consumers declare nothing, because
block-declared resources bubble into the flow's resource map automatically (precedent:
`packages/memory/src/memory-capability.ts:275`). Note that it reverses a stated property —
`packages/tools/src/bash/capability.ts:10-15` says in as many words that the bash capability
installs no resources of its own — so that module docstring changes with it.

*6 — A test-fixture break TypeScript will not catch.* `buildCtx`
(`packages/tools/test/bash.test.ts:978`) returns `{ session, user, org, resources } as any`
with **no `request` field**, and `bash-moat.test.ts` builds `const ctx: any = { session,
resources }` the same way. Any allocator reading `ctx.request.identity.id` throws at runtime
across twelve call sites — ten `buildCtx()` calls in `bash.test.ts` and two inline contexts in
`bash-moat.test.ts` — and because both are cast `as any`, `tsc` stays silent about all of it.
Budget the fixture work; do not discover it.

*7 — Sizing, as an estimate and not a budget.* A full allocator across both consumers was
estimated at 290–385 production LOC plus 380–560 test LOC, of which roughly 200–285 is
net-new — the rest lands inside code this change already rewrites. A Claude-Agent-only version
is roughly half. That estimate was made before any of it was written, and is offered for
planning only.

Whatever mechanism is chosen, it is not a lock — and the reason matters, because it is **not**
that no cross-process primitive exists. One does. `StoreRegistry` requires a `LeaseStore`
(`packages/engine/src/stores/types.ts:1235`); its key is a bare `string` over a `request_id
TEXT PRIMARY KEY` column with no foreign key; the filesystem, SQLite and Postgres adapters
each implement it across processes (exclusive `open(…, "wx")`, a transactional upsert, and
`SELECT … FOR UPDATE`); and it already carries a non-request key in production — the
durability sweeper acquires `"__durability_sweeper__"` as a multi-host sentinel. A per-path
lease is reachable. Two things make it the wrong tool, and the first is disqualifying:

- **It is a lease, not a mutex.** `LeaseOptions.durationMs` bounds it and expiry is *silent*:
  `acquire` hands the key to the next caller once `expiresAt <= now`, and the holder is never
  told. Guarding a flush with one means re-checking before every write, re-acquiring on
  expiry, and treating expiry as an error — a flush that can fail partway through for timing
  reasons that have nothing to do with the data. That is a worse failure mode than the race it
  was bought to prevent.
- **Nothing on the resource-write path takes one.** Every consumer today is durability and
  resume machinery. It would have to be adopted there, not merely used.

The claim that holds, and the only one worth writing down: **no cross-process lock is taken on
the resource-write path.** Ownership was the earlier choice because it removes the concurrent
case structurally rather than detecting it, not because the primitive is missing. The same care applies to reaching for CAS underneath, if
anyone later does: even that is not uniform across adapters. The filesystem adapter's resource
CAS "compares under a per-key mutex held on the store **instance**, so it closes the
in-process race but does **not** protect two OS processes over one directory"
(`packages/engine/src/stores/types.ts:1032`, stated deliberately in the contract). Real CAS is
memory, SQLite and Postgres only.

**Whatever the check turns out to be, it reaches one case — and the hash comparison beside it
is narrower than it looks.** An overlap check addresses projection-versus-projection. Against
every other writer — an action block,
another tool, a different session — the hash comparison does something weaker: it **narrows**
the window rather than closing it. It cannot close it. `theirs` is read, then `writeContent()`
runs unconditionally, and a non-projection write landing between those two still gets
overwritten. What the check buys is the *size* of that window: hydrate-to-flush is an entire
agent run, read-to-write is a store round trip. Minutes down to milliseconds, not down to
zero.

**That residual is narrow, silent, and accepted** — and it is worth naming both halves of why.
Closing it needs the atomic conditional content write §6 declined: versioning `ContentStore`
writes across every store adapter, which is a larger change than the bug it would close here.
And the bar this design is held to is that **loss must be loud, not that it must be
impossible.** The overlap check makes the projection-versus-projection case loud or impossible
depending on what is built; the hash check makes the ordinary non-projection case loud; a non-projection writer landing inside a
millisecond window is neither, and that is the price being paid.

**When a path-level check stops being enough**, the expectation is a mechanism layered *on top* —
worktrees and a merge step, or something like it — **not** versioned content writes
underneath. That was considered and deliberately rejected, so `expectedVersion` on the
content store is the wrong door to reach for.

**Change detection: diff is the source of truth, hooks are an optimisation.** Measured
(§12): the harness's post-tool hook carries a file path for its own write tool and only an
opaque command string for a shell write, and the file-change hook never fires at all. So
hooks cannot decide what to persist. They are used to *narrow* the work (a turn whose tool
calls were all reads needs no walk) and to feed the run index LAB-134 built. One source of
truth, one optimisation on top of it.

**Flush boundary: the consumer's, not the component's.** The component exposes `flush()`;
each consumer picks when. The bash blocks keep flushing after each command. The coding-agent
capability flushes at **end of turn**, which was measured to block long enough for a real
flush. Session-end is not a candidate — it did not fire at all in the measured run.
Directory-change events turned out to be a non-issue: a shell `cd` does not persist between
tool calls, and the only thing that relocates a run is the worktree tool we are not offering.

**Containment defaults the framework sets** (measured except where the note below says
otherwise — §12):

| What | Default | Why |
|---|---|---|
| settings sources | **explicitly none** | Omitting the option loads the *workspace's own* settings and instruction files. The workspace is user-writable content (BP-031). |
| available tools | **stated list** | The permission allowlist does not restrict availability; the availability list does. Excludes the worktree tools. |
| working directory | the projected root | Placement, not containment — see the next row. |
| OS write confinement | **on, scoped to the projected root**, failing closed | A run without it writes anywhere on the host. Covers sandboxed shell commands. |
| the shell's unsandboxed escape | **disabled** | It defaults to *allowed*, and it lets one command opt out of the row above. |
| extra readable directories | **none** | Everything the run should see is a mount inside the root. |
| approval | the framework's existing approval seam, **checking the target path of every write-capable tool** | The blanket bypass mode is refused when the process runs as root, which is the shape of a server container. The built-in file tools are fenced here rather than by command sandboxing — and one was measured resolving a bare relative path to the filesystem root. |

Only the shell path is measured (POC 5, §12). The other two rows are read off the harness's
own contract — the unsandboxed escape defaults to allowed, and the built-in file tools
resolve through approval rather than through command sandboxing — so §10's containment goal
exercises each path separately instead of treating one measurement as covering all three.

**Sketch — pseudocode. Illustrative, not the contract. React to the shape.**

```
hydrate(mounts, place):
    for each mount, for each entry:
        write it at <mount prefix>/<entry key>
        remember baseline[path] = hash(content)          ← where the fix starts

flush(mounts, place, baseline):
    for each path the place now holds:
        route it to the mount whose prefix is the longest match
        no match and not scratch → orphan (reported, never guessed at)
        read-only mount          → skip

        now = hash(local content)          (this is "ours")
        base = baseline[path]              (absent = we never laid this down)
        theirs = hash(collection's current content)

        now == base                 → unchanged, do nothing
        base absent, theirs absent  → clean create
        theirs == base              → clean write
        now == theirs               → already what we would write; clean, nothing to do
        otherwise                   → CONFLICT (base, theirs, ours); write nothing

        after any clean outcome that leaves the collection holding `now`
        — create, write, and the `now == theirs` branch alike:
            baseline[path] = now                          ← or our own next flush
                                                             contests this one

    for each path we hold a baseline for and the place no longer holds:
        theirs == base ?  → delete it, and drop baseline[path]
        otherwise         → CONFLICT with ours = absent    ← the half that gets missed
    (a path we hold no baseline for is not ours to delete)
```

What this asks a reviewer: *should a delete that can't prove safety be a conflict, or just a
no-op?* A conflict makes the caller deal with it and is loud; a no-op is quiet and lets
deleted files accumulate in the collection forever. The sketch takes the first, and that is
the half FIX-998's notes record a first fix getting wrong — so it is the shape to argue with
if it is wrong.

**The baseline's lifecycle, end to end.** It is not a snapshot of hydrate. It tracks what the
projection last committed, and it changes at five points:

| When | What happens to `baseline[path]` |
|---|---|
| Hydrate lays a path down | **Recorded** — `hash(content)` as written |
| A clean write | **Advanced** to what we just wrote |
| A clean create | **Advanced** to what we just wrote |
| The `now == theirs` no-op | **Advanced** to `now` — the branch writes nothing, but the collection *already holds* what we would have written |
| A clean delete | **Dropped** |

The no-op row is the one that is easy to miss, and it is not cosmetic. That branch commits
nothing, so leaving `base` at what hydrate saw means the next local edit is compared against a
version the collection no longer holds, and reports a conflict that is not one.

**Holding a baseline is what makes a path ours — not having hydrated it.** A file this run
created and flushed was never hydrated, and it is still ours: we know exactly what we put
there. So the delete pass iterates **every path we currently hold a baseline for**, not the
hydrate-time set. Otherwise a run that creates a file in one command and deletes it in the
next leaves the collection holding a file that no longer exists in the workspace, forever, and
nothing ever reports it.

Both halves matter on the *happy path*, which is what makes them more damaging than the
concurrent case. The shell tool flushes after *every* command, so an ordinary two-command edit
would otherwise report a conflict against a write the same projection made, on one run with no
concurrency anywhere; and create-then-delete is two ordinary commands.

**The baseline is per-projection and discarded at teardown** — not persisted. A resumed
session that no longer holds one owns no paths at all: it writes only where the collection is
untouched, and deletes nothing. That degrades safely and is invisible to both consumers
today, since each hydrates at the start of a run and flushes within it.
Persisting it is additive if a workspace ever needs to outlive a run (§12 follow-ups).

**A runnable POC accompanies this spec.** Six throwaway probes on the spec PR under
`spec-poc/FIX-150-workspace-projection/`, each with a measured verdict. What they showed is
in §12; the containment table and the two-strategies call are theirs, not assumptions.

### 9. Edge cases & error handling

| Case | Expected |
|---|---|
| A path exists under two mount prefixes | Longest prefix wins; mounts are matched longest-first |
| A write lands under no writable mount | Orphan: reported as run-visible state, never guessed into a default collection, never silently dropped |
| A write lands in the scratch directory | Ignored, as today — that is what the directory means |
| The place is unreadable at flush time | Abort the flush; **never** run the delete pass on an empty listing |
| Collection metadata entries (leading `_`) | Never hydrated, never deleted by a flush |
| A path we hold no baseline for vanishes | Not ours; no delete, no conflict |
| A path this run created and flushed is then deleted and flushed again | Ours: we hold a baseline for it, so the delete is detected and applied under the same check. The delete pass walks every owned baseline path, not the hydrate-time set |
| A file is byte-identical to what we laid down | Unchanged; no write, no conflict, no timestamp churn |
| Two runs write the same path with the same content | Both clean; hashes agree, so there is nothing to contest |
| Two runs would write the same path | The overlap is detected and refused **loudly**: the second writer is stopped and told, with a message naming the contested path, so it can re-frame or retry. Never silently narrowed, never both admitted. Where the refusal lands — allocation, hydrate or flush — is the implementer's call (§7) |
| Two runs share a collection but write disjoint paths inside it | Both run, both flush, both results land; neither is refused and neither reports a conflict (§10's first goal). The overlap check must not fire here |
| A path is changed by a non-projection writer between our `theirs` read and our write | Overwritten, silently. The window is a store round trip rather than a whole run; closing it needs versioned content writes, which §6 declined (§7) |
| One run flushes twice, having written the same path each time | Both clean; the first flush advanced the baseline, so the second is not contesting our own write |
| A resumed session flushes against a baseline it no longer holds | Owns nothing: no deletes, writes only where the collection is untouched (§7) |
| OS write confinement unavailable on the host | Fail closed: the run refuses to start with an actionable message naming the missing dependency |
| The projected workspace contains an agent settings or instruction file | Inert — settings sources are explicitly none |

**Taxonomy.** Conflicts are **not errors**: they are a reported outcome of a successful
flush, and a flush that reports conflicts still writes everything uncontested. Fatal:
an unreadable place, a refused start under fail-closed containment, and a refused writer on a
path overlap — at whatever point §7's check lands. Everything else degrades to "left alone and reported" — with one stated
exception: the residual race in §7, where a non-projection write landing inside the
read-to-write window is lost *silently*. That is the accepted price named there, not an
outcome this taxonomy covers.

### 10. Testing strategy

**Goal.** Two coding agents run concurrently in one session against one shared collection,
each owning a disjoint path inside it. One creates a file; the other edits a different file.
Both finish. The user sees **both** results in the collection, and neither run reports a
conflict.
`goals/workspace-projection/concurrent-runs-share-a-collection/run.mts`, real model.

*This fails today* — one run's flush deletes the other's new file (FIX-998's measured
`delete-by-absence` case). It also fails if the fix over-corrects into reporting a conflict
where two runs touched different files, which is the failure mode a naive baseline check
produces. A hydrate-then-flush round trip was rejected as the goal: it can only fail when
the mechanism is broken, which makes it a capability check, not a proof.

**Second goal — containment.** A collection containing an agent instruction file that says
"always begin your reply with token X" and a settings file that sets an environment
variable is projected into a workspace, and a coding agent runs against it. Neither takes
effect, and a write outside the projected root is refused on **each** of the three paths
that can attempt one: an ordinary shell command, a shell command asking for the unsandboxed
escape, and a built-in file tool handed a path that resolves outside the root. One refusal
does not stand in for the others — POC 5 measured the first, and the incidental finding that
prompted POC 5 was a *built-in file tool* writing to the filesystem root.
`goals/workspace-projection/a-workspace-cannot-configure-its-agent/run.mts`, real model.
*This fails today* (measured, §12) and fails again the day someone removes the setting —
which is the point: the check can fire.

**CI specs** (the behaviours, not the test names):

- **one behaviour per decision in §6**, in observable terms.
- **each flush outcome**, separately: unchanged, clean create, clean write, the
  `ours == theirs` no-op, and conflict — with the conflict carrying base, theirs and ours.
- **the baseline advances**: a second flush in one run, over a path the first flush wrote,
  is clean. This is the ordinary multi-command shell case and needs no concurrency to fail.
- **the baseline advances on the `ours == theirs` no-op too**: that branch writes nothing, so
  a third flush after a further local edit must still be clean, not a conflict against a
  version the collection no longer holds.
- **create, flush, delete, flush**: a path this run created — and therefore never hydrated —
  is deleted from the collection on the second flush. Without it, the delete pass walks the
  hydrate-time set and the collection keeps a file that no longer exists in the workspace.
- **the delete path under the same check** — the case FIX-998 records a first fix missing.
  Promote its three measured reproductions (`delete-by-absence`, `lost update`,
  `edit-vs-delete`) from the harness on `epic/durable-jobs`; they are written to flip from
  passing to failing when the bug is fixed, so they are already regression tests.
- **the no-false-conflict floor**: a genuine no-op flush reports zero writes, zero conflicts,
  zero deletes. Without this the conflict check can pass by reporting everything.
- **what must not change**: the existing bash suite passes untouched, and a single-run
  workspace behaves exactly as today.
- **the second path (BP-035)**: every behaviour exercised on a *second* flush against a
  changed collection, not only a first flush against a fresh one.
- **the shell blind spot**: a file written through the shell is persisted, proving flush does
  not depend on tool observation.

**Discipline:** `tdd`. The seam is the projection component against an in-memory place —
no sandbox, no harness, no model, so every behaviour above is a tracer bullet.

## Spec evolution *(the change story, not an audit log)*

- **Spec drafted** — framed as a projection component rather than the block the issue names,
  because the machinery already exists twice and the gap is that it is welded to one caller;
  chose two placement strategies over three and framework-stated containment over inherited
  defaults, both settled by POC rather than argued; folded FIX-998 in, because the fix and
  the extraction touch the same code and the extraction deletes it.
- **After spec review** — pinned single-writer-per-mount as *ownership at assignment* rather
  than a lock, because the content store's writes cannot be versioned; made the baseline
  advance on every clean create,
  write and delete, because the shell flushes per command and a run was otherwise contesting
  itself on the happy path; widened containment to the shell's unsandboxed escape and the
  built-in file tools, because only the shell path had been measured; added an
  `ours == theirs` clean outcome, because the sketch reached CONFLICT where the edge-case
  table promised clean; and dropped the session→run default flip, keeping `"run"` as an
  explicit scope, because nothing establishes that no usage depends on a workspace surviving
  between turns.
- **After the second review round** — narrowed ownership from the mount to the projected
  **path** and named the coordinator as the actor that allocates it, because mount-scoped
  ownership ruled out §10's first goal and left "who enforces this across workers?"
  unanswered; corrected the claim that the hash check *handles* non-projection writers to what
  it actually does, which is narrow the window from a whole run to a store round trip and
  leave a residual that is narrow, silent and accepted; wrote the baseline's whole lifecycle in
  one place, including the two advances that were missing — after the `ours == theirs` no-op,
  and on a path this run created rather than hydrated — because what makes a path *ours* is
  holding a baseline for it, not having hydrated it; replaced the not-a-lock rationale, which
  had cited `pg_advisory_lock` to argue no cross-process primitive exists, with the accurate
  one (a `LeaseStore` is reachable and cross-process; it is the wrong tool because it is a
  time-bounded lease with silent expiry and nothing on the resource-write path takes one); and
  named the seam the coding-agent composition actually needs, because `ClaudeCodeAgentOptions`
  has no `uses` field and no capability lifecycle wrapper exists to substitute for one.
- **After the owner's call on ownership** — moved the one-writer-per-path rule from a settled
  mechanism to a **soft requirement**. The spec now states the goal — both consumers get at
  least a basic overlap check, a refusal that tells the agent to try again is an acceptable
  outcome, silent double-writing is not — and hands the mechanism, the default and the
  granularity to the implementer, because the real cost of each is legible from inside the
  code and was being decided from outside it. The reasoning is kept in full and demoted from
  decision to evidence, with the facts that make the choice cheap attached: the public API
  delta can credibly be zero, the sandbox registry has no request dimension and adding one
  buys per-run isolation at a MOAT container per request, a ledger declared as a *collection*
  would be mounted into the very workspace the agent can write to, a ledger declared on the
  tool blocks would never reach `flow.resources`, and twelve test fixtures build a context
  with no `request` field behind an `as any` that keeps `tsc` quiet. Added the §8 step that
  actually builds it, which the sequence had been missing while §7 read as settled; and
  dropped the out-of-flow `createBashTool` path as a constraint — we call it inside a flow, so
  an owner token can be assumed present where it matters.
