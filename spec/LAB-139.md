# LAB-139: A run that needs a decision can ask for one, and be answered — Implementation Spec

## Part I — The Case *(for the human)*

### 1. Problem — why it matters, why now

A background coding run that hits a real ambiguity has two options: guess, or stop. It cannot
ask anybody. The framework's durable pause holds the *asking* request open, and for a
background run that request is the run's own — so a run that pauses to ask pauses only
itself, and nobody is told a person is needed.

The common case is not a run that fails. It is a run that finishes a turn with a question.

**Why now** — this is the epic's Proof, and nothing else in the set tests it.

### 2. Solution in plain terms

When the run needs a decision it writes the question into an **inbox** — a shared list of open
questions — and puts its own job on hold. The board lets go and the run's request ends, so
nothing is held open while a person thinks. The operator answers the row and takes the job off
hold, which starts the run again on that answer.

Two things make it work. **The question is a durable row, not a paused request**, so an answer
arriving tomorrow morning still has somewhere to land. And **holding for a person is an
outcome of the run**, beside *done* and *that attempt failed*.

**Philosophy** — tenet 5 (*fix at the owning layer*): the hold, the board's exit and the
re-queue are the substrate's, consumed rather than rebuilt. Tenet 3 (*earn every addition*):
this adds nothing to the published framework.

### 6. Decisions & rules — the sign-off surface

1. **The answer travels on the question's own row, never on the channel that already carries
   why the last attempt failed.**
   *Rejected:* handing it back through the job's existing feedback field — the cheapest
   wiring, and the one that already means something else.
   *Locks in:* a run can never be told *"your last attempt stopped because: take the second
   option."* The manager reads two places on every start instead of one, forever.

2. **Answering a question costs the run one of its retries, and we ship that this cycle.**
   *Rejected:* conductor counting which restarts were answers — a second counter beside the
   board's, which is how two counts drift.
   *Locks in:* ask three questions of a run budgeted for three retries and it has none left
   for a real failure. Whoever files the job budgets for questions *plus* failures until the
   discount lands in the substrate, where it rides on FIX-1244.

3. **Ratify the scope cut: the operator gets one verb, *answer*.** Redirecting a run
   mid-flight and sending it on a side errand are not built, and cancelling needs one small
   piece: the board cancels the job, conductor withdraws the question (§7).
   *Rejected:* the four steering verbs this issue originally scoped in.
   *Locks in:* the only thing a person can do to a live run is answer what it asked; anything
   else waits for the run to finish or for a later issue. Not an engineering fork — the
   engineering is the same either way, and this is the over-scope call to keep or overturn.

**Non-goals** — the four consumed pieces (§12), the `awaiting_review → parked` rename, working
out which question a free-form reply addresses (an answer names its row), any inbox UI, and
more than one run at a time.

**Size:** Medium — 6 production files · 19 test behaviours · 1 doc surface · 1 PR. **No
framework change**: LAB-138 spent this epic's one on the run's working directory.

---

### 3. Tradeoffs & alternatives

**Alternative: pause the run's request and resume it when the answer arrives.** Closed by the
product owner (D-1). What is new is that the chosen path is no longer merely the safer one — it
now runs end to end on today's `main` (§12).

**The simpler approach: let the operator read what the run said and file a new job with more
context.** It needs nothing built, and it is a restart — which the epic says is not the Proof.
It also throws away everything the run had worked out.

**Where the complexity is:** not the round trip; that was the unknown, and it runs. It is the
two ends — getting the run to *ask* on a harness with no seam for a question to leave through,
and getting the answer back into the **same** coding conversation.

### 4. Focus practices (1–4)

1. **BP-031** — which run, which issue and which attempt a question belongs to is derived
   server-side. Only the question's words and the answer's words come from outside.
2. **One create-only convergence point for the ask** (tenet 5). That step commits no output
   and re-executes on recovery; one create-only path, or a replay erases an answer.
3. **Nothing carried between attempts is stale by default** (tenet 5). The checkout survives a
   retry, so bind what the last attempt left there to the attempt — §7.
4. **Tenet 7 — a check that cannot fire is not a check.** Answering a row nobody parked passes
   trivially, so §10 asserts after a real park.

### 5. What using it looks like

The inherited board gains one option — `onReview: "exit"` — and the operator gets one
zero-model action:

```ts
await conductor.answer({
  question: "FIX-1166/implement/1/a3f19c",   // the row, named explicitly
  answer: "Correct the path only. Leave the symlink alone.",
});
```

The observable change: a run that hit an ambiguity used to guess or stop with nothing useful
to show. Now a question row appears, the drain returns `parked-for-review`, and an answer
starts the run again holding it.

## Part II — The Build Plan *(for the implementing agent)*

### 7. Technical design

Everything here is conductor's own code in `labs/conductor/`. Nothing is added to the
published framework.

```mermaid
flowchart TB
  subgraph coord["coordinator session"]
    ANS["answer action (zero-model)"]
    ST["status action — board row + open questions"]
  end
  subgraph ws["the run's workstream (detached)"]
    MGR["the manager — LAB-138's, plus a third outcome"]
    AGENT["claudeCodeAgent in its own checkout"]
  end
  INBOX[("inbox/** — user-scoped, one row per question")]
  BOARD[("the board row — LAB-138's user-scoped ledger")]

  AGENT -->|writes its question to this attempt's marker path| MGR
  MGR -->|create-only write| INBOX
  MGR -->|awaitReview| BOARD
  MGR -.->|announce, Relay FIX-1230| coord
  INBOX --> ST
  ANS -->|patch row to answered| INBOX
  ANS -->|resumeFromReview re-queues the row| BOARD
  BOARD -->|the next drain claims and re-dispatches| MGR
  INBOX -->|answered rows fold into the prompt| MGR
```

**Two POCs on this branch measured the round trip before this design was drawn, and changed
it. Their measurements live in §12 and are not repeated here.** The one that reshaped the
document: since FIX-1234 landed, a detached worker's own park **survives** its normal return,
so nothing below is a workaround for the epic-spec's contrary table row.

#### The inbox

A plain `defineResourceCollection`, modelled on `labs/knowledge-hub/src/inbox.ts` — **not a
new capability** (LAB-68's standing rule; FIX-1075 gets the evidence).

- `pattern: "inbox/**"`, `scope: "user"`, `flowIsolation: false` (BP-027),
  `prefetchMode: "lazy"` so posting a question is a point lookup rather than a scan of every
  question the user has ever been asked (BP-033) — **true of the ask and only of the ask**; see
  the accessor split below.
- `llmWritable: false`, and `llmReadable` only if a phase's readable set needs it. Conductor's
  own blocks are the only writers: the question's *words* come from the run, its *identity*
  does not (BP-031).
- State: the question, who asked, when, `status` (`open` / `answered` / `withdrawn`), and the
  answer — the last `.nullable().default(null)` (BP-023).

**The key: bare topic `<issue>/<phase>/<attempt>/<fingerprint>`**, the fingerprint a hash of
the question's text. Issue-first so `list("<issue>/<phase>/")` reads as one contiguous range.
**Hash-keyed rather than counted**, because a counter needs committed state and the ask step
has none — a replay would number the same question twice. **The attempt segment keeps the hash
safe:** without it a later attempt asking the identical question would land on the
already-answered row, and the manager would fold a stale answer into the prompt instead of
asking.

**No epic segment — locked here, not deferred, and the reason has to be the right one.** D-4
partitioned the *board* because a board is a **claim pool**, where sharing storage lets one epic
claim or settle another's row. **An inbox row is never claimed.** What exempts it is **who reads
it**: an unfiltered `inbox/` listing spanning epics is *a person's inbox*, which is the product
rather than a boundary crossed. Every read this issue performs is prefixed by issue and phase.

**The rule this is one application of:** *a key that two boards write, whose reader is a **job**,
needs the board's discriminator; a key whose reader is a **person** does not.* The job-shaped
keys — `runs/**`, the checkout, the branch — are the other application, and they fold elsewhere.
Deriving the exemption from that rule is what keeps it from reading as a special case.

**What is *not* the reason: "issue ids are globally unique, so two epics cannot collide."** They
can. The key is **attempt-keyed**, and the attempt comes from *a board's* counter — two epics
driving the same issue-phase keep independent counters, so both can produce attempt 1 and land
on one key. Reachable on a mid-flight epic move with the old manager still running (§13). **The
discriminator still buys nothing a person's inbox wants**, which is what earns the lock — but
the collision argument does not, and anyone re-deriving the lock from it would be reasoning from
a false premise.

**The two accessors do not cost the same, and the spec should not claim they do.** Checked in
`packages/engine/src/context/resource-registry.ts`:

- **The ask is a genuine point lookup.** `get` / `upsert` go through `ensureInstance` →
  `getInstance(resolvedKey)`, so the create-only write loads one row. The lazy-prefetch
  justification holds here.
- **A prefixed `list` is not filtered at the source.** `list(prefix)` calls `ensurePrefix()` →
  `getByPrefix(collectionKeyPrefix)`, and that prefix is the **pattern's** (`inbox/`), not the
  caller's; the caller's prefix is applied in memory afterwards by `nsHandle.list(prefix)`. So
  the prompt fold and `status` load **the user's whole inbox across every epic**, then discard
  what does not match.

**Named, not designed around.** The key does not move to chase this — it is locked, and its
reader is a person (above). Issue-first keys still make the in-memory filter exact and the store
range contiguous, which is what they were for. But BP-033's *filter at the source* is **not**
available on this registry's list path, so the honest statement is that these reads are bounded
by the user's retained inbox rather than by the issue-phase. That is the §13 retention limit,
now with a hot-path cost attached rather than only a storage one.

**Key vocabulary is LAB-138's rule, inherited and not restated**: a string handed *to* the
collection carries no `inbox/` prefix, one that came *out* of it does, and the accessor is
`ref.path` (LAB-138 §7, "Two vocabularies").

#### The replay-safe write — this issue's own obligation

The step that posts a question commits no output, so it **re-executes on recovery**. An
unguarded write recreates the row or resets it, and the answer then lands on a row nobody is
reading — or is wiped by a replay of the step that created it.

**The rule: the ask is a create-only write, and nothing else ever writes an `open` row.**
`upsert(bareTopic, {}, { question, askedBy, askedAt, status: "open", answer: null })` — the
patch branch has nothing to apply, so a second execution is a read. Verified against an
already-answered row (§12).

The two other writers are narrow and neither can reopen a row: the **answer** patches
`status: "answered"` plus the body, and the **withdraw** patches `status: "withdrawn"`. Status
only ever moves forward. There is no `open` write outside the create branch — one convergence
point rather than a guard on each writer (tenet 5).

#### How the run surfaces a question, and why the marker is per-attempt

**The harness offers no seam for one, and this was checked rather than assumed.**
`claudeCodeAgent`'s options are `model`, `systemPrompt`, `allowedTools`, `disallowedTools`,
`permissionMode`, `agents`, `maxTurns`, `includePartialMessages`, `onToolApproval`, `detached`,
`recordWork` — plus the per-run working directory LAB-138 adds. There is **no MCP-server option
and no way to hand the run an FSD tool**, so a conductor-owned "ask" tool the model calls
cannot be built without widening the framework, which LAB-138's decision 3 rules out.

**So the question travels as a file in the run's own checkout**, at a path the implement prompt
names, written before the run opens the PR. This is why the ask is **forced** rather than
spontaneous — a property of the harness surface, not a shortcut, and the epic-spec already
states it as a limit on what the Proof shows.

**The marker path carries the attempt, and that is load-bearing rather than tidy.** A retry
inherits the previous attempt's checkout — that is decision 2's whole economics — so last
attempt's question file is still sitting there when the next attempt starts. A single fixed path
means an attempt that quietly did nothing looks exactly like an attempt that asked: the
manager reads the stale file, writes a **new** row under the new attempt's key, and parks
instead of taking the no-question failure path. The run stalls on a question nobody asked.

**So the path is derived from `attempts` on the worker input and sits at
`<checkout>/.fsdev/ask/<attempt>.md`** — inside the tree, on a **tracked-gitignore** path — and
the manager reads only the current attempt's path. The attempt number is server-derived, so
nothing the model writes decides which file is read (BP-031).

**Two constraints meet here, and the path is chosen to satisfy both without a step.** The marker
must be **writable**, and it must not **ride into the product PR**.

- *Writable.* Inside `cwd` is the only place it is. Measured, not assumed (§12): an out-of-tree
  Write is denied under exactly the config every call site uses today — no `permissionMode`, no
  `onToolApproval` — with `decision_reason_type: "workingDir"`, and the SDK's
  `additionalDirectories` is exposed nowhere in conductor's options. Reaching it would be a
  **framework change**, which LAB-138's decision 3 rules out and whose one allowance this epic
  already spent on the run's working directory.
- *Not committable.* `git add -A` does not stage a gitignored path, which is the whole thing an
  out-of-tree marker was reaching for.
- *No step per invocation.* `.gitignore`'s `**/.fsdev/**` is committed to `main`, so it is
  already there on every fresh clone and every worktree, with nothing to set up, remember or
  crash between. **That is the discriminator**, and it is why the same tenet-5 reasoning that
  rejected the alternatives now selects this one rather than only ruling things out: *rejected,
  a per-worktree `.git/info/exclude` entry* — itself a step, at worktree-prep time — and
  *rejected, clearing or archiving the marker before each invocation* — a step a crash can
  interrupt, leaving the stale-marker stall.

**`.fsdev/` rather than `.orchestration/`, checked rather than assumed.** `**/.fsdev/**` matches
at **any depth**, while `/.orchestration/` is root-anchored and would silently stop covering the
marker if the path ever nested. `.fsdev/` is also the framework's own namespace, and it does not
read as the coordinator's session memory, which is a different thing.

**The trade-off, stated rather than hidden: the guarantee is now coupled to that `.gitignore`
entry staying accurate.** Narrow the pattern or rename the directory without updating it and the
leak comes back silently. The coupling is low and already relied on everywhere else in this repo
— but it is a coupling, and this path is not free of one.

**The general shape, swept as asked: the key's attempt segment protects a *row* from
collision; it does not make anything else *fresh*.** Two other things cross attempts and both
were checked. The prompt fold reads `answered` rows across *all* attempts — deliberate, that is
the question history, not a freshness assumption. And LAB-138's `runs/**` row is keyed
`<issue>/<phase>` with no attempt segment at all, which is exactly why that spec makes the
opening upsert clear every attempt-scoped field explicitly. Nothing else leans on uniqueness to
imply freshness.

*The alternative channel is the run's final message* (`SdkAgentHandle.finalMessage`), parsed
for a marker. Not chosen: it is absent on a thrown exit and is the one field a summarising
model most likes to reword. Where the run wrote no marker for this attempt and the
done-condition is unmet, that is an ordinary failed attempt — not a question.

#### The park, and the manager's third outcome

LAB-138 leaves a two-outcome decide step and names the seam: *"Adding a parked-on-a-person
outcome is LAB-139's to define, on the substrate it consumes."* This is that definition.
**The row is created before the outcome is selected, not inside the park arm.** If this
attempt's marker holds a question, the create-only write happens first; the arms then decide what
becomes of it. Creating it inside arm 2 was a defect: a marker plus an **errored** verdict never
reaches arm 2, so arm 3 withdraws a row that was never created, and succeeded-and-done with a
marker has the same shape. **Behaviour 9 requires the failed question's row to be durably
`withdrawn`** — that is the question history a later attempt and a late answer both read — so the
row has to exist for a failure path to withdraw it.

**Three outcomes, in this order, and the order is the design:**

1. **The verdict succeeded AND the done-condition holds → return.** Unchanged. If a question
   is still open, the run answered it itself: **withdraw the row** and complete. A withdrawn
   row is never deleted, so a late answer against it is reported back rather than applied.
2. **The verdict did NOT fail AND this attempt's marker holds a question → park.**
   `awaitReview(taskId, <the question>)`, then **return normally**. The recorders leave the row
   alone, the workstream request ends, and the run costs nothing while a person thinks.
3. **Anything else → throw.** Unchanged. **Withdraw any open row first** — the attempt failed,
   so its question is moot, and leaving it open means an answer later lands against a row no
   attempt is waiting on.

**All three arms are conjunctions, and arm 2's second half is the one easy to drop.** A
question is only worth holding the board for if the run is still in a position to use the
answer. **A run that asked and then failed is not** — and the SDK reports its most common
failures by *returning*, not by throwing: a turn cap or an exhausted budget comes back as an
errored handle (LAB-138 decision 1's whole premise). So an arm gated on the marker alone
matches that run, parks it, and waits on a person for an attempt that is already dead. The row
never re-pends, the retry budget is never spent, and nothing reports it — a silent stall, which
is the mirror of the silent success LAB-138 exists to kill. **The failed-with-a-question run
must fall through to arm 3**, which withdraws the open row and throws.

**Why the park arm sits after completion and before failure.** A run that finished the job
should not be held for a question it no longer needs answered; a run that failed should not
hold the board for one either. Only the middle case is a genuine wait on a person — and with
arm 2 gated on the verdict, the arms now say that rather than only the prose beneath them.

*This is the second instance of one shape in this epic: **two signals matter, the prose states
both, the encoded condition names one.*** LAB-138 caught it at completion — the done-condition
alone would have completed a run that opened the PR and then exhausted its budget. Here it was
the park. Both re-admit the pathology the neighbouring decision exists to close, from the other
side.

#### The board delta

One option on the board LAB-138 builds: **`onReview: "exit"`.** Its three construction refusals
are all satisfied by LAB-138's board as specified, and the implementer should confirm each
rather than assume it: the ledger is a `defineTaskCollection()` (resource-backed — a
request-backed one is refused); `onIdle` is left at its default `complete-or-blocked` (both
`wait` and `complete` are refused, with reasons in `park-exit.ts`); and `initialTasks` must
carry stable ids — LAB-138 seeds through a `seed` action rather than `initialTasks`, so the
refusal does not fire, which is a fact to check rather than rely on.

**The drain that wakes a parked row must name the session.** `createExecutionContext` defaults
an absent `sessionId` to a fresh `ephemeral_…` value, which becomes the scope id for
session-scoped state — so a drain that omits it resolves a different ledger, finds an empty
board, and reports success having reached nothing. That is documented and tested upstream
(`task-board-park-exit-across-requests.test.ts`, the negative arm). LAB-138's board is
`user`-scoped so its ledger is not the exposure, but its `runs/**` record is session-scoped
with lineage sharing, and the failure looks like nothing happened either way. **State it as a
requirement on the `wake` action, not an assumption:** every drain conductor runs names the
coordinator session.

Nothing else about the board changes. Its scope, partition and lifetime are LAB-138's D-4 lock,
settled there precisely because this issue inherits them.

#### The wake — shipped verbs composed, and the seam where they collapse into one

**The `answer` action reads the board row first, and refuses unless the row is parked.**
Parked is the shipped `awaiting_review` — what D-1 calls `needs_input` in product terms, the
enum being what the guard compares against (BP-030). **Parked is the only proceed path, and
every other status refuses locally**: `pending` (a LAB-138 retry, and the *second* answer of a
duplicate pair, because the first already re-queued the row), `in_progress` (a claim — a live
run is not waiting on anybody), `completed`, `errored`, `cancelled`. *Held* would be exactly
the wrong word here: on this board a row is held when it is **claimed**, which is the one state
the answer path must not proceed from.

**And the guard is a pair, not a single check: the task parked AND the named inbox row still
`open`.** The task is shared across attempts; the row is per-attempt (the key's attempt segment).
Attempt 1 asks and fails, so its row is withdrawn; attempt 2 later parks on a question of its
own. An answer naming **attempt 1's** row finds the shared task at `awaiting_review`, passes a
task-only guard, flips a withdrawn row to `answered` and re-queues the run — **while attempt 2's
actual question is still open.** The run resumes holding an answer to a question nobody asked,
and the real one is never answered. So the row write is a **conditional `open → answered`
transition**, the same forward-only discipline the ask and the withdraw already use, and a row
that is not `open` refuses the whole action before anything is written. **That is also the
mechanism §9's withdrawn-row outcome always needed** — the outcome was specified, the path to it
was not.

**A refusal is a returned decline, not a throw** — the action's output carries the reason and
the row's current status, so an operator (and §10's assertions) can tell *refused* from *done*.
Three of §9's rows and behaviour 12 all rest on that one shape; it is the same stance the
substrate's own verbs took when FIX-976 made their declines reportable.

The substrate will not refuse for it: `resumeFromReview` passes no `requireFrom`, and every
remaining guard is behind `ifAllowed`, which this design does not adopt — so a row that was
never parked reports `recorded` and the answer lands on a run nobody is waiting on (§12). The
guard is **product-level, in conductor's own action**: no second primitive, no counter, no
status and no verb, and nothing in the substrate changes. It is what makes §10's behaviour 12 a
completion criterion rather than a wish, and it covers §9's terminal row and the racing-answers
row **on the common path** — read-then-refuse is not atomic, and §13 names the window it leaves.

On a parked task with an open row the action then does three things, and the third is the one
easy to leave out:
patch the inbox row to `answered`; `resumeFromReview(taskId)` **with no feedback** (which also
clears any stale failure reason, §12); and **run LAB-138's `wake` drain itself, naming the
coordinator session.**

**The drain belongs to the action, not to the operator's next step.** `resumeFromReview` only
leaves the row `pending`, and with `onReview: "exit"` the drain that observed the question has
already ended — so an `answer` that stops after two calls leaves the row waiting for whatever
happens to drain next, and §5's *"an answer starts the run again holding it"* is a promise the
design does not keep. The POC's re-dispatch came from a **separate** `drain` invocation after
the answer (`round-trip.mts`, M4), which is precisely the step §5 never shows the operator
making. **Third instance of one shape in this epic — the prose promises the whole round trip
and the encoded path stops one step short** (the park arm named one signal of two; §9's
completion row did the same). Worth naming as the recurring defect, not only fixing.

**The three calls are not atomic, and a crash between any two of them leaves a durable prefix.**
Patch, `resumeFromReview`, drain — each commits on its own. A request that dies between calls 1
and 2 leaves the row `answered` with the task **still parked**: the operator watched the answer
be accepted and nothing will ever run it. One that dies between 2 and 3 leaves the row
`answered` with the task `pending` and no drain in flight, because `onReview: "exit"` ended the
one that observed the question. **These are not two cases, they are one defect**: the sequence
has committed part of itself, and the proceed lock — parked **and** `open` — refuses to re-enter
a sequence whose first call already landed.

**First, what "this sequence" means, because the rule is only as tight as the state it ranges
over.** The condition is **the question the task is waiting on**, and it is read off the
questions themselves — **never off the counter**:

- **Proceed** names its question directly: the row must be `open`, which is what makes it the
  question the task parked on.
- **Recovery** names it by absence: the row must be `answered`, and **no row under
  `<issue>/<phase>/` may be `open`.** An open row means the task is waiting on a *different*
  question, and this answer is not the sequence to restart.

**No offset, no arithmetic, no `attempts` in the condition at all.** An earlier attempt's
retained `answered` row is still refused while a later question is open, which is the case the
correlation exists for. A stale `answered` row named when nothing is open falls into recovery and
**drains** — it writes nothing and applies no answer, so the worst it can do is what a drain
always does.

*Rejected: persisting the row's key on the task at park time.* It is the obvious identity
carrier and it is not available — this spec **designs no field on the task** (that is FIX-1179's
surface), and the one existing carrier, `feedback`, is **cleared by our own `resumeFromReview`**
(§12 measured it) precisely when recovery would need to read it. *Also rejected: widening the
offset to "N behind."* That keeps the counter in the condition and buys exactly one more failure.

**Why the counter cannot carry this, stated so it is not re-derived:** `applyClaimToTask`
advances `attempts` on **every** claim, and `isClaimable` admits a lease-lapsed row — so each
abandoned reclaim advances it again while the open question does not change. A condition written
as "one behind" survives exactly one abandoned hand-off; the second lapses the task to two ahead
and strands the recorded answer with no drain left to run it. **The counter measures how many
times the mechanism moved. The question is what the rule means.**

*Cost, named rather than hidden:* recovery reads the issue-phase listing to establish that
nothing is open, which pays §7's namespace-wide `list` (above). It is on the answer path, not on
the run's hot path, and it is the same read `status` already performs.

**Then recovery is one rule, not a list of admitted pairs: an `answered` row with nothing open
beside it means the patch is durable and this is the sequence to restart.** It never re-patches.
It reads the task to see how far the sequence got:

- task **parked** → `resumeFromReview`, then drain.
- task **`pending`** → drain only.
- task **`in_progress` whose lease has lapsed** — an abandoned claim — → drain only. The drain's
  own lease-lapse reclaim is the recovery; nothing here reaches inside it.
- **anything else** → decline: a **live** `in_progress` (a run holds it), or terminal.

**The live-vs-abandoned split is the whole third arm, so the observable is named rather than
assumed — and it was checked before the arm was written.** Status cannot make this distinction;
the lease can, and `answer` can see it:

- **Abandoned is `status === "in_progress"` with `leaseUntil` present and already past** — the
  substrate's own `leaseLapsed`, evaluated against **the same clock the claim wrote against**,
  not the action's wall clock.
- **`answer` genuinely has those fields.** It reads the row server-side, where the read hands
  back the whole persisted task; `claimedBy` is redacted only on the *client* emission path
  (`toEmittedTask`/`SERVER_ONLY_TASK_FIELDS`), which this action is not on.
- **An absent `leaseUntil` reads as LIVE and declines** (`== null`, BP-030: rows persisted before
  FIX-1005, rows never claimed). The conservative direction is the safe one and it is deliberate:
  a stranded answer is recoverable by any later wake, **a live run resumed underneath itself is
  not**, so the arm refuses whenever it cannot prove abandonment.

**Had that observable not existed, the arm would not ship** — the limit would be named here
instead. Draining every `in_progress` is not the fallback; it resumes a run that is still
working, which is a worse failure than the one the arm closes.

Idempotent by construction: a repeat of either branch is a drain that finds nothing left to
claim, and the row's body is never rewritten. Re-running is safe, not merely tolerated.

**The third arm exists because the drain is not atomic either, so the sequence has four commit
points and not three.** Patch, `resumeFromReview`, **claim**, hand off. The claim advances
`attempts` and takes the row `in_progress` before the hand-off is attempted, and a hand-off that
throws leaves the claim off the request's state — so nothing settles the row and nothing owns it;
it simply sits until its lease lapses. Without this arm the operator has answered, the answer is
durable, `attempts` has moved, and no drain remains to run it: the outcome this whole design
exists to prevent, arriving through the machinery built to prevent it. **Ownership rather than
status is what the arm reads**, because a live run and an abandoned claim are the same status.
The re-claim charges another attempt and records an abandonment — the board's own accounting for
a run that was claimed and never started, which this design does not adjust (decision 2).

**Without the correlation the rule resumes the wrong question, and answered rows never expire.**
Attempt 1 asks Q1 and it is answered; attempt 2 asks Q2 and parks. A delayed retry naming
**attempt 1's** row finds an `answered` row and a parked task, matches recovery, and resumes
attempt 2 **while Q2 is still open** — the run restarts holding an answer to a question it did
not ask, and the real one is never answered. The attempt segment is what refuses it.

**Stating it as one rule rather than a second admitted pair is deliberate.** The pair form is
what hid the `(answered, parked)` case to begin with — it enumerated the case the previous fold
had in front of it instead of naming the property the sequence has, and §9's audit found that
same failure mode in a table of enumerated outcomes. The rule reads off one fact, *is the patch
durable*, and then one more, *how far did the sequence get*.

**No body comparison, deliberately.** A second, different answer arriving on an already-answered
row resumes the run holding the **first** answer and drops its own body — the duplicate outcome
§12 records and accepts. Telling a genuine second answer from a replay is FIX-1244's, not this
rule's.

**A consumer-side stopgap with a known exit.** FIX-1244's atomic verb makes the recorded answer
and the new request one write, so **both** windows close and this rule leaves with the three
calls it exists to restart. Its three jobs are unchanged.

**Fourth instance of one shape in this epic, and the reason to name it rather than fix it
quietly:** *the prose promises the whole round trip and the encoded path has a hole in it* —
LAB-138's completion arm, this issue's park arm, the drain nobody owned, and now the gap between
two writes that each looked complete. **Three of the four were opened by a lock that was correct
in isolation.** That is the framing worth carrying to `distill-lessons` at epic wrap, because it
changes what the fix is: the defect does not arrive in the sloppy paragraph, **it arrives where
two careful ones meet** — so what needs fixing is not anyone's discipline but the fact that our
locks compose badly and **nothing in the process checks the seam between two of them.** Each
review round here checked the lock it was folding; none checked it against the lock folded the
round before, which is how a parked-only guard and an action-owned drain shipped a dormant run
between them.

**And the fifth instance is the recursive one — lead with it.** The recovery rule above was
itself added to close a seam between two locks, **and left a seam on its own other side**: it
admitted `(answered, pending)` and not `(answered, parked)`, because it was written as the pair
the previous fold needed rather than as the property the sequence has. A fix aimed at one seam,
shaped as an enumeration of the cases in front of it, **produces the next seam**. The counter is
the one this rule now uses: state the rule over the durable state, not over the cases.

**And the sixth instance is inside the rule written to fix the fifth, which is what sharpens the
lesson rather than repeating it.** The rule said *restart from the durable prefix* and then
under-specified the prefix: it read as *"an answered row exists"* when what was meant is
*"**this attempt's** answer sequence was interrupted."* An under-specified rule fails exactly the
way an enumeration does — both range over more states than the author had in mind. **So stating
a rule instead of a list is not the fix on its own**; the fix is pinning the state it ranges
over, and the check is to name a state that satisfies the rule and should not.

**Eighth instance, and the second one a fold created rather than uncovered — this time inside
the correlation written to fix the sixth.** The correlation was stated over the **counter**
(`attempts` equality) when what it means is *the question the task is sitting on*, and a claim
advances the counter without changing the question. A wake that claimed and then failed to hand
off landed in a state the correlation rejected and the recovery rule never named. **The pattern
is now explicit enough to state as a habit:** each of these came from writing the condition in
the vocabulary of the *mechanism in front of us* — a status, a pair, a counter — instead of the
vocabulary of the **thing being tracked**: is a run live, which question is open, did this
sequence commit. The seam appears wherever a mechanism changes state without changing meaning.

**Ninth instance, and it is the cheap half of the eighth: when the rule moved, three artifacts
kept teaching the condition it replaced.** §9's earlier-attempt row, this section's own sketch,
and §8's build step all still said *"the attempt segment equals `attempts`"* — the counter form —
after the rule had moved to the question. None of them was wrong when written; each was a
faithful copy of a rule that then changed underneath it. **So the habit has a second half:** when
a condition moves, sweep every artifact that states it rather than fixing the one that was
pointed at. The cost of missing one is not a defect today — it is the next reader deriving the
old condition from a document that still teaches it.

**The distinction that makes this a consumer rather than a second primitive:
`resumeFromReview` *re-queues* the row. It does not start a request.** The next drain — the one
`answer` runs — is what claims and dispatches, and that dispatch is a new workstream request. So
the shipped verbs composed are **today's effect of FIX-1244**, not a local wake — nothing here invents one, and nothing
here proposes a change to who owns it.

**FIX-1244 stays the owner of the honest primitive** — one verdict, a payload in, a new request
out. **The collapse seam is the `answer` action's three calls**: when FIX-1244 lands they
become one parked-only verb, and nothing else in this design moves. The retry-discount decision 2 names is a rider on
that same work, which is why **conductor grows no counter of its own**.

#### Relay carries the announcement; the row carries the question

D-1: the ask travels Relay. Precisely: **the inbox row is the durable carrier** — the epic-spec
says so in the same breath — and Relay's fire-and-forget send is the **announcement**, so the
coordinator session learns a question exists without polling. **The manager sends it after the park**, naming the row's key and nothing else — the order is a
requirement, not a detail of the writing: what is announced must already be answerable, or the
first subscriber fast enough to act on it is refused by the parked-only guard and then watches
the task park on the question it just tried to answer.

Nothing of FIX-1230 is in tree, so the send sits behind one seam whose default is a no-op.
**What that costs while it is absent:** the operator finds the question by reading rather than
being told — the `status` action below, and the `resource_change` events a collection mutation
already streams to a watching client. Everything else here is testable and shippable without
it.

**The answer's route in is never the public caller-addressed one** (epic theme 6). The `answer`
action is an ordinary action on the conductor flow, running in the coordinator's own session;
it re-queues a *board row* and never re-enters the detached dispatch. `WORKSTREAM_SOURCE` stays
in `NEVER_PUBLIC_REENTRY_SOURCES`, untouched. **An implementation that reaches for that
allow-list has taken a wrong turn**, not found a bug.

#### Reading the answer back, and the same coding session

**The manager folds every `answered` row under `<issue>/<phase>/` into the prompt, oldest
first.** No "consumed" flag and no fourth status: folding is idempotent, so a replay produces
the same prompt, and it is correct whether the coding session resumed or started cold.

**Continuing the same coding session is FIX-1246's, and this issue builds none of it.**
`claudeCodeAgent({ detached: true })` consults no session provider, so it passes no `resume` to
the SDK and a re-dispatched attempt is a cold start — which is why restart is not Proof. What
this issue does is have the id ready: LAB-138's `runs/**` row already carries the harness
session id as bookkeeping, and the manager hands it to whatever FIX-1246 ships. **This spec
designs no field on the task**, names no shape, and stands nothing in for the typed top-level
task field that is FIX-1179's.

#### The read surface

LAB-138's zero-model `status` action gains the open inbox rows for the issue-phase beside the
board row it already reports. That is how an operator sees a question with no UI built, and it
is what §10's behaviours assert against. **The board row stays the authority on the job's state
and the inbox row on the question's** — neither is inferred from the other.

**And `status` reconciles what it reads: an `open` row whose task is terminal is withdrawn
there.** The board's `cancel` writes the task row and nothing else — the manager never runs
again, so neither withdrawal arm fires — and the question is then unanswerable by construction,
because the guard above refuses a terminal task. Left alone it shows in `status` forever as a
question nobody can act on. **Reconciling at the read rather than wrapping the cancel verb is
deliberate:** an operator can cancel through the board's own verb, so a conductor `cancel`
wrapper is a step that can be bypassed, while the only surface that can *display* a stranded row
is the one that clears it. The `answer` guard's terminal refusal withdraws it on the same
terms. Both writes are the ordinary forward-only withdraw, so running either twice is a read.

**Solution sketch — pseudocode. Illustrative, not the contract. React to the shape.**

```

  on entry:

      → two channels, two meanings, and they never carry each other

  run the coding agent, in its checkout, under a wall-clock deadline,
  told to write any question to THIS ATTEMPT's marker path

  if THIS ATTEMPT's marker holds a question

      ↑ BEFORE the arms, not inside the park arm. TWO of the three arms
        WITHDRAW this row, and a marker with an errored verdict never
        reaches the park arm at all — creating it there means withdrawing
        a row that was never created, while behaviour 9 wants it durably
        `withdrawn`.

  read the verdict (LAB-138's), then decide — THREE outcomes:

      verdict succeeded AND done-condition holds

          → return                                   (row completes)

          → awaitReview(taskId, the question)
          → announce over relay                      (no-op until FIX-1230)
          ↑ ANNOUNCE AFTER THE PARK, never before. A fast subscriber that
            answers on the announcement would be refused by the parked-only
            guard, then watch the task park on the question it just tried to
            answer. What is announced is already answerable.
          → return normally                          (row STAYS parked —
                                                      the recorders refuse it)
          ↑ BOTH halves. A run that asked and then reported failure is
            NOT parked — the SDK returns its turn-cap and budget failures

            for an attempt that is already dead.

      anything else — INCLUDING a failed verdict with a question open
          → withdraw any open row (the attempt failed; its question is moot)
          → throw                                    (row re-pends, or errors
                                                      once the budget is spent)

the answer action, in the coordinator's own session, zero-model:

      read the board row AND the named inbox row
      FIRST: is this the question the task is waiting on?
             proceed  → the named row is `open`
             recovery → the named row is `answered` AND NO row under

             → otherwise decline, whatever the statuses say
          ↑ NO `attempts` in this condition, and no offset. Every claim
            advances the counter — including each lease-lapse reclaim —
            while the open question does not change, so any counter form
            ("equal", "one behind", "N behind") survives a bounded number
            of abandoned handoffs and then strands the answer.
          ↑ answered rows are retained forever. Without this, a delayed retry
            naming ATTEMPT 1's answered row matches recovery against a task
            parked on ATTEMPT 2 — and resumes it while Q2 is still open.

      proceed only on (task parked AND row `open`); anything else refuses
          ↑ the row half is NOT redundant. The task is shared across attempts,
            the row is per-attempt: a late answer naming attempt 1's WITHDRAWN

            attempt 2's real question is still open.
          ↑ RECOVERY is one rule, not a second pair: a named row already

          ↑ the substrate will not do this for us: resumeFromReview passes no
```

### 8. Implementation sequence

**One PR.** Every deliverable is conductor-local and none is separately shippable — there is no
framework change to review on its own, which is what made LAB-138 two.

1. **The inbox collection** — `labs/conductor/src/inbox.ts`: the definition, the key grammar
   and its helpers, and **the create-only write as the single ask path**. *Test:* §10's replay
   behaviours. *Depends on:* nothing.
2. **The ask** — the per-attempt marker path, reading it out of the checkout, and the withdraw.
   *Test:* §10's stale-marker and withdraw behaviours. *Depends on:* 1.
3. **The manager's third outcome** — the decide step's three arms in §7's order, the park, and
   the fold of answered rows into the prompt. *Test:* §10's three-arm and fold behaviours
   against a stubbed agent resolver. *Depends on:* 2, and LAB-138's manager.
4. **`onReview: "exit"` on the board**, having confirmed all three construction refusals, and
   the `wake` action naming the session. **Do this early** — a construction-time throw fails
   before anything else can run. *Depends on:* LAB-138's flow.
5. **The `answer` action**, zero-model: **the question condition first** (proceed: the named row
   is `open`; recovery: it is `answered` and **no** row under `<issue>/<phase>/` is `open` — no
   `attempts` anywhere in it), the **paired guard** (task
   `awaiting_review` **and** row `open`) and **the recovery rule** — an already-`answered` row means the patch is durable,
   so restart from that prefix, never re-patch, and branch on the task (parked → resume + drain;
   `pending` → drain; else decline) — the conditional `open → answered` row patch, `resumeFromReview` with no feedback, and **the
   `wake` drain the action runs itself**, naming the coordinator session. Plus the `status`
   action's inbox half **and its terminal-task reconciliation**. *Test:* §10's behaviours 12 and
   15–17 for the guard, the recovery and the cancel, and behaviour 7 **driven through `answer`
   alone** — a test that drains by hand passes with the missing drain in place.
   *Depends on:* 1, 4.
6. **The relay announcement seam**, defaulting to a no-op, and the implement prompt's forced
   ask against the per-attempt path. *Depends on:* 3.
7. **The goal check** (§10) — **written now, gated on FIX-1246.** Not a completion criterion
   for this PR.

**Removals.** None.

**Two cautions.**

- **Do not pass the answer as `resumeFromReview`'s feedback**, however convenient. That field
  is LAB-138's failure-reason carrier and decision 1 turns on the two staying separate.
- **Do not add a "consumed" status to the inbox.** The fold is idempotent by construction; a
  consumed flag reintroduces exactly the write-a-row-that-a-replay-can-reset problem this issue
  exists to close.

### 9. Edge cases & error handling

**Only the cases §10 does not already cover as a behaviour.** Everything else — the park, the
drain over a parked row, the replay, the fold, the three decide arms, the retry cost — is a
numbered behaviour there, and keeping two enumerations is where drift starts.

| Case | Expected |
|---|---|
| The same question is asked twice in one attempt | One row — the hash keys them together, which is correct: it is the same question |
| A question is asked and the attempt then **fails** | The row exists and reads `withdrawn` — it is created when the marker is read, **before** the outcome is selected, so both failure paths have something to withdraw (§7). The question history is what a later attempt and a late answer read |
| The run **succeeded**, opened the PR **and** left a question | Completed, and the row is **withdrawn** — the run answered itself. Both halves of arm 1: a run that opened the PR and *then* reported failure is a failed attempt (LAB-138 decision 1), and its question is withdrawn on the way out rather than parked |
| An answer arrives for a **withdrawn** row | The row is not deleted, so the answer is reported back and not applied. The task is untouched — **including when the task is parked on a later attempt's question**, which is what the guard's row half exists for (§7) |
| A **parked task is cancelled** while its question is open | The board's cancel writes the task row only, so the row survives it. `status` withdraws an `open` row whose task is terminal, and the `answer` guard does the same on its way to refusing (§7). The question is never answerable after the cancel, and never displayed as though it were |
| The wake **claims and then fails to hand off** | The row is `in_progress` with **a lapsed lease** — an abandoned claim — so the answer is durable and nothing is running it. Recovery's third arm drains; the substrate's lease-lapse reclaim does the rest (§7). Read the lease, not the status: **a live `in_progress` declines**, and an absent `leaseUntil` reads as live, because resuming a run that is still working is worse than leaving an answer for a later wake |
| The request dies **part way through the three calls** | Nothing is lost and nothing runs. The row is `answered` either way, so re-running `answer` restarts from that prefix: task still parked → `resumeFromReview` then drain; task `pending` → drain only (§7). Both windows close when FIX-1244's atomic verb makes the three calls one write |
| An answer names a row while a **different question is open** | Declined. The condition is read off the questions: recovery requires the named row `answered` **and no `open` row** under `<issue>/<phase>/` (§7). An earlier attempt's retained `answered` row is refused exactly while a later question waits, which is what it exists for |
| The wake's claim fails **repeatedly** | Recovered every time, not just the first. `attempts` advances on each lease-lapse reclaim while the open question does not change, so the condition names no counter and no offset (§7). Which arm applies still turns on **live vs abandoned**: a lapsed lease drains, a live `in_progress` declines, an absent `leaseUntil` reads as live |
| An answer arrives for a row whose task is terminal | The write is refused and the refusal is **reported**, never read as success. If the named row is still `open` the refusal **withdraws it on the way past** — the same read-site reconciliation `status` performs |
| Two answers race the same row | **The first always takes effect and the row is never overwritten** — the conditional `open → answered` refuses the second write (§7). The second is reported as refused **once the run is moving again** (task `in_progress`, or terminal). While the row is `answered` and the sequence is still mid-flight, recovery cannot tell a second answer from a replay of the first: it resumes the run holding the **first** answer and drops the second's body. **Telling them apart needs a body comparison, which is FIX-1244's** — the windows are its to remove, not this rule's to grow |
| Relay is absent | The announcement is a no-op. The question is still readable through `status` and still streams as a `resource_change` |
| A drain omits the coordinator session | Resolves an empty ledger and reports success having reached nothing (§7). Every drain conductor runs names the session |
| The hold status is renamed (`awaiting_review → parked`) | FIX-1245's, and **this design now has one thing in its path**: the guard compares a status enum, so the rename moves with it. The verbs `awaitReview` / `resumeFromReview` are still unchanged. Tolerate both spellings when it lands rather than anticipating it (BP-030) — one comparison, named here so it is not found by a failing guard |

> **Every row above names the code that produces it, and the table was audited row by row
> against the substrate rather than against its own prose.** That check exists because two rows
> — the refused answer and the withdrawn row — turned out to state an outcome nothing
> implemented: they were written as though `resumeFromReview` already refused, and it does not
> (§12). Both now have a path, and it is the same conductor-local one: **the paired guard**. The
> mechanism is no longer with the product owner. What remains genuinely open is not an outcome
> but a **window** — the racing-answers row above says exactly how wide it is, and FIX-1244
> closes it.

**Second path (BP-035).** The second path here is **the attempt that starts holding an
answer**: the prompt is built from two channels instead of one, the retry budget has already
been charged, the checkout carries the last attempt's leavings, and the coding session is (for
now) a cold start. A suite that only exercises a first attempt asking a question proves
nothing.

### 10. Testing strategy

**Goal — the epic's Proof.** One real Linear issue —
**[FIX-1166](https://linear.app/fixpoint-labs/issue/FIX-1166)**, one wrong path in `CLAUDE.md`
— driven from a conductor task row to an open PR, with the run posting a question to the inbox,
a person answering it without opening a terminal, and the run finishing on that answer.
Evidence: the inbox row and its answer, the `runs/*` row, the board row, and the PR. Lives at
`goals/conductor/asks-and-is-answered/`. **Write it now; it runs when FIX-1246 lands** (§12).

**What is actually net-new here, because it decides where the effort goes.** The park, the
drain's exit and the cross-request resume are pinned upstream for the **inline, session-scoped**
path by `packages/orchestration/test/task-board/task-board-park-exit-drain.test.ts` and
`packages/integration-tests/src/scenarios/task-board-park-exit-across-requests.test.ts`. The
surface nothing covers is **detached + user-scoped + cross-request**, and conductor's own
behaviour on top. So behaviours 1–3 and 6 **extend those existing tests** rather than starting
green-field, and the POC graduates into **one integration scenario plus conductor unit tests**
— not two permanent `pnpm tsx` scripts.

**CI specs** (19 behaviours, in observable terms — not test names):

1. **The park survives a normal return** — *detached* worker, *user*-scoped ledger. Calls
   `awaitReview` on its own row and returns; the row reads `awaiting_review`, not `completed`.
   *Extends the park-exit drain tests onto the detached path.*
2. **A drain over a parked row reports it and dispatches nothing** — `parked-for-review`, zero
   new dispatches. *Extends.*
3. **The negative arm of 2**: the same board without `onReview: "exit"` does **not** report
   `parked-for-review`. Without this, 2 passes on a board that never had the option set.
4. **The ask is replay-safe.** Run the ask step twice in one attempt: one row, identical state.
5. **A replay cannot erase an answer.** Answer the row, then re-run the ask step; it still
   reads `answered` with the body intact. **A test that only replays an `open` row passes with
   the bug in place.**
6. **The inbox crosses the session boundary.** A row written inside the workstream is read by
   the coordinator session, with no `sharedToWorkstream` declared anywhere. *Extends.*
7. **The answer reaches the next attempt.** After an answer, the manager's prompt carries the
   answer's body. Assert on the prompt the harness received. **No POC coverage — green-field.**
8. **The two channels never carry each other.** Stage a failed attempt (feedback = the error)
   *then* a question and an answer; assert the resumed prompt carries the answer as an answer
   and **not** the stale failure as this attempt's reason. Decision 1, and the behaviour that
   fails silently. **No POC coverage — green-field.**
9. **The three decide arms, and the fourth combination that is the actual trap.** Each
   asserted on the board row *and* the inbox row afterwards. Three are the arms as written:
   succeeded-and-done → row `completed`, question row `withdrawn`; not-failed-with-a-marker →
   row `awaiting_review`, question row `open`; no marker and not done → row `pending`, no
   question row. **The fourth is the one that can fail: a run that writes a marker AND returns
   an errored verdict** — a turn cap or an exhausted budget, which the SDK reports by returning
   rather than throwing — **must take the failure path**: row back to `pending` (or `errored`
   once the budget is spent), the question row **present and `withdrawn`**, and **the row never
   `awaiting_review`.** *Present* is half the assertion: this combination never reaches the park
   arm, so a design that created the row there leaves nothing to withdraw and an assertion that
   only checks "not `open`" passes against an absent row. Assert on all four, not three. **A suite that pairs marker-with-success
   and no-marker-with-failure passes with the bug in place**, because neither of those two
   combinations ever puts a marker and a failure on the same attempt — which is exactly the
   combination arm 2's verdict half exists to exclude. **No POC coverage — green-field.**
10. **A stale marker cannot fake a question.** A **second attempt in the same checkout** that
    writes no new marker takes the **no-question failure path**, and **no second open row
    appears**. The first attempt's marker file is still on disk, which is the point — a fixed
    path passes every other behaviour here and fails this one. **And the derived path is inside
    the checkout and gitignored**: assert both — inside, because outside is unwritable (§12), and
    ignored, because a staged marker ships the question text in the product PR. `git
    check-ignore` on the derived path is the assertion.
11. **A completed run withdraws rather than deletes**, and a late answer against a withdrawn
    row is reported and not applied.
12. **A decline is reported, never swallowed.** Answer a row that was never parked; the action
    surfaces the refusal. *(A silent decline is the defect class LAB-138 exists to remove,
    relocated.)*
13. **The retry budget is charged by an answer.** After one question and one answer, `attempts`
    has advanced and no abandonment discount applied. Pinning decision 2's cost so it cannot
    regress into a surprise.
14. **The same question in a later attempt is asked again**, not answered from the earlier
    attempt's row — what the key's attempt segment buys, and a key without it passes every
    other behaviour here.
15. **An answer against a stale row refuses, with the task parked.** Withdraw attempt 1's row,
    park the task on attempt 2's question, then answer **attempt 1's** row: refused, attempt 1's
    row still `withdrawn`, attempt 2's row still `open`, and **the task still
    `awaiting_review`** — not re-queued. A task-only guard passes this and strands the real
    question. **Second arm, and it is the one the recovery rule can fail:** answer attempt 1's
    question so its row reads `answered`, park the task on attempt 2's, then answer **attempt
    1's** row again — declined on the attempt correlation, attempt 2 still `open`, task still
    `awaiting_review`. A rule keyed on status alone resumes attempt 2 here.
16. **The half-finished answer recovers, from either prefix.** Two arms, and a suite with only
    the second passes with the worse bug in place. **Crash after the patch** — row `answered`,
    task still **parked** — and re-run `answer`: it resumes and drains, the run comes back
    holding the answer, and the row is not rewritten. **Crash after `resumeFromReview`** — row
    `answered`, task `pending` — and re-run: it drains only. **Crash after the claim** — row
    `answered`, task `in_progress` with a lapsed lease and `attempts` one beyond the row's — and
    re-run: it drains, the reclaim picks the row up, and the run comes back holding the answer.
    **Then fail the recovery drain at the same point and re-run again** — two consecutive
    claim-before-hand-off failures, so `attempts` is now **two** beyond the row's. It must still
    recover: a suite that stages one failure passes with an offset condition in place, which is
    the bug this behaviour exists to catch. **And the negative arm, which is the one that
    matters:** the same pair with the lease **still live** must **decline and dispatch nothing** — a suite without it passes with an action that
    drains every `in_progress` and resumes a run that is still working.
    Then run each once more: still one dispatch, nothing rewritten.
17. **A cancelled task does not strand its question.** Cancel a parked task with an open row,
    then call `status`: the row reads `withdrawn`, and a later answer against it is refused.
18. **What is announced is already answerable.** Assert the order at the seam: the announcement
    fires **after** `awaitReview`, and a caller answering the moment it fires is accepted, not
    refused. The seam is a no-op until FIX-1230, so the assertion is on the stub's call order —
    which is the point, because the defect only becomes visible once a real subscriber exists.
19. **The board still constructs** with `onReview: "exit"` alongside LAB-138's ledger, `onIdle`
    and seeding. The regression is a construction-time throw, so the assertion is that the
    board builds.

**Discipline.** `tdd`. Two seams, neither needing an HTTP server: the inbox write, key grammar
and marker path as plain unit tests, and one `runAction` scenario over a detached board with a
stubbed agent resolver for 1, 2, 3, 6, 7, 8, 9, 10, 13 and 15–18.

parked-only or atomic; those are different properties.

### 13. Review notes for the implementer

- **The POC scripts on this branch are a starting point, with one trap.** Their answer path is
  **not** the product seam: they deliver the answer through `resumeFromReview`'s feedback and
  the stub manager reads `input.feedback`, because that was the cheapest way to prove the board
  round trip. Production is inbox patch → prompt fold → `resumeFromReview` with **no** feedback
  (decision 1). Graduate the *substrate* measurements, never the answer path — and note that
  behaviours 7, 8 and 9 have no POC coverage at all.
- **The board's construction refusals fire before anything runs.** `onReview: "exit"` is
  refused on a request-backed collection, on `onIdle: "wait"`, on `onIdle: "complete"`, and on
  `initialTasks` without ids. Each message carries its own fix. Get this right first, not last.
- **A named limit, not a task: nothing bounds how long a question may stay open.** A parked row is
  deliberately outside the lease's governance, so a question nobody answers holds its row
  forever. Correct for a human wait, wrong for an abandoned one, and closing it needs a policy
  nobody has chosen. Do not invent one.
- **A named limit, not a task: `answer`'s refusal is right on the common path, not on the
  race.** The action reads the board row and then calls `resumeFromReview`, and the row can move
  between those two — a run settles, a sibling answer lands — so a refusal that should fire can
  be overtaken. Closing that window means the verb itself refuses a row that is not parked,
  atomically, which is the property FIX-1244 owns. Do not invent a lock, a compare-and-set or a
  conductor-side status to close it here. **The same window has one visible cost worth telling an
  operator about:** a second answer arriving on an already-`answered` row is indistinguishable
  from a replay, so it resumes the run holding the first answer and drops its own body (§9). Say so in the README's
  limits rather than papering over it in the action.
- **A stop rule, not a limit: the recovery rule has been extended four times, and a fifth window
  is FIX-1244's, not a fifth arm.** Each extension had the same cause — a condition that named a
  **mechanism** (a status pair, a counter, an offset) where it meant a **fact** (is the patch
  durable, which question is open, is a run live). The condition is now written entirely over
  facts, which is why this should be the last one. **If a fifth window appears anyway, do not add
  an arm.** It means the three-call sequence cannot be made restartable from outside, and the
  answer is the atomic verb FIX-1244 owns — one write, no prefix to recover from. Escalate it
  there rather than continuing to close windows by hand here.
- **A named limit, not a task: one issue, one live epic.** The inbox key carries the attempt, and
  the attempt is *a board's* counter, so two boards driving the same issue-phase can both issue
  attempt N — a **mid-flight epic move with the old manager still live** can clobber attempt N's
  row. The epic segment does not close it and is not being added (§7's reason); neither does a
  compare-and-swap or a conductor-side status. Do not invent one. Move an issue between epics
  with the old manager stopped.
- **Answered rows are never deleted and nothing prunes them, and the prefixed reads do not
  bound the load.** Expected volume this cycle is small — one run, one issue at a time, a handful
  of questions each — so no retention policy is specified. What changes the shape of this limit
  is the accessor split in §7: a prefixed `list` loads the whole `inbox/` namespace and filters
  in memory, so **every prompt fold and every `status` call pays for every question the user has
  ever been asked**, not just this issue-phase's. Retention is therefore a hot-path cost, not
  only a storage one. Still watch it rather than pre-solving it — the fix is a retention policy
  or a source-filtering list, and neither is this issue's. Do not move the key to chase it.
- **One run at a time is a property of the board, not of this design.** Nothing here assumes
  it, and nothing here is tested against two runs asking at once. The keys are already disjoint
  by issue; the untested part is the operator's read.

  a pause. Two throwaway POCs preceded the design and changed it: since FIX-1234 landed, a
  worker's own park survives its normal return, so no workaround for the epic-spec's contrary
  measurement appears anywhere here. Separated the two carriers — the board's `feedback` for
  why an attempt failed, the inbox row for an answer — after measuring that a re-queue clears
  feedback. Made the ask a create-only write with a hash-derived key, and verified it cannot
  erase an answer. Cut the four steering verbs to one. Named the retry a question costs rather
  than hiding it.
- **After review — two locks, one fold, and a trim.** Locked the inbox key with **no epic
  segment** and the reason that keeps it that way: D-4 partitioned the board because a board is
  a claim pool, and an inbox row is never claimed, so a discriminator buys nothing and costs a
  segment. Locked §7's wake as **settled rather than raised** — `resumeFromReview` re-queues and

  one step short of, and an Architect lock on the word that names the wait.** §10's behaviour 12

  does not adopt, so a never-parked row reports `recorded`. §9 was honest that the mechanism was

  is parked** — the shipped `awaiting_review`, `needs_input` in product terms — with `pending`,
  `in_progress` and every terminal status refusing locally. **Locked wording, because the first
  draft of this fold had it backwards:** *held* on this board means **claimed**, so a guard

  run. The second gap was the drain. §7 said the existing `wake` drain "does the rest" without
  ever saying who runs it — and with `onReview: "exit"` the drain that saw the question has

  the epic's recurring defect** — the prose promises the whole round trip, the encoded path has a

  promised the loser is always reported, but inside the recovery window the second answer is
  indistinguishable from a replay of the first: it reports a drain while its body is dropped.
  Restated as what actually happens, with the reason it stays that way — telling the two apart
  would put a body comparison inside the one admitted exception, and the window is FIX-1244's to
  remove rather than the guard's to grow. *The hold status is renamed* claimed nothing here
  anticipates the new name, which stopped being true the moment the guard began comparing a
  status enum; restated to name the one comparison FIX-1245 moves, tolerating both spellings
  (BP-030). §9's block quote — which still said the mechanism for those rows sat with the
  product owner — is now the audit note: the mechanism is the paired guard, and what remains
  open is a **window, not an outcome**. §7 also pins what *reported* means, a returned decline
  carrying the reason and the row's status rather than a throw, since three rows and a CI
  behaviour rest on that one shape.
- **The out-of-tree marker, folded and then reversed on measurement.** The concern was real —
  `.conductor/ask/<attempt>.md` sat in the run's own tree, where an agent that stages wholesale
  commits the question text into the product PR — and the first fix moved it outside the
  worktree, with a note that the run's permission to write there should be confirmed rather than
  assumed. A POC confirmed the opposite: under the config every call site uses today, an
  out-of-tree Write is **denied** (`decision_reason_type: "workingDir"`) while the run's
  `result.subtype` stays `"success"`, so the manager cannot tell a refused ask from an attempt
  that never asked — the park arm's silent stall, re-entered through the ask. The marker is back
  inside the checkout at **`<checkout>/.fsdev/ask/<attempt>.md`**, a **tracked-gitignore** path,
  which is writable (inside `cwd`), unstageable (`git add -A` skips ignored paths) and **costs no
  step per invocation**, because the `.gitignore` entry is already on `main`. That last property
  is the discriminator, and it turns the tenet-5 reasoning that had only rejected the
  alternatives — a per-worktree `.git/info/exclude`, clearing the marker each run — into the
  thing that selects this one. `.fsdev/` over `.orchestration/` because `**/.fsdev/**` matches at
  any depth while `/.orchestration/` is root-anchored. The attempt segment and all its reasoning
  are untouched. **The trade-off is named rather than hidden:** the guarantee is now coupled to
  that `.gitignore` entry staying accurate, and narrowing the pattern re-opens the leak silently.
- **The recovery pair became a rule, because the pair had a seam on its own other side.** The
  three calls `answer` makes are not atomic, and the pair form covered a crash between calls 2
  and 3 while leaving the crash between 1 and 2 — row `answered`, task **still parked** —
  matching neither proceed nor recovery. The retry refused and the task stayed parked forever
  holding an answer the operator had watched land, which fails the goal itself: a question asked
  *and answered*. Recovery now keys on one fact — **an already-`answered` row means the patch is
  durable** — and restarts the sequence from that prefix without ever re-patching, branching on
  the task (parked → resume then drain; `pending` → drain; anything else → decline). Proceed is
  untouched: parked **and** `open`, then all three calls. No body comparison, so a second
  different answer still resumes on the first and drops its own body — the duplicate outcome §12
  already accepts, and FIX-1244's to tell apart. Both windows close when FIX-1244 collapses the
  three calls into one write; its three jobs do not move.
  **This is the fifth instance of the epic's shape and the one to lead with, because it is
  recursive:** the recovery pair was added to close a seam between two locks and left a seam on
  its own other side — it enumerated the case the previous fold had in front of it instead of
  naming the property the sequence has. A fix aimed at one seam, shaped as an enumeration,
  produces the next seam. The counter is what the rule now does: state it over the durable state,
  not over the cases.
- **Third round — the rule's own state was looser than the thing it meant, and the sketch had
  drifted from the prose twice.** Recovery keyed on *"the named row is already `answered`"*, and
  answered rows are retained forever while the task is shared across attempts: a delayed retry
  naming attempt 1's answered row matched recovery against a task parked on **attempt 2** and
  resumed it with Q2 still open. The fix was already in the key — the named row's attempt segment
  must equal the task's `attempts` — so it costs no field and no body comparison, and it is now a
  precondition of **every** path rather than of recovery alone. Proceed had excluded the case
  only as a side effect of the withdrawal arms clearing earlier open rows; that made correctness
  a consequence of another arm rather than a property of this one. **Sixth instance, and it sits
  inside the rule written to fix the fifth**, which sharpens the lesson instead of repeating it:
  stating a rule rather than an enumeration is not the fix on its own, because an under-specified
  rule fails the same way — both range over more states than the author meant. Pin the state the
  rule ranges over, and check it by naming a state that satisfies the rule and should not. Two
  smaller drifts, both prose-vs-sketch, which is what §9's audit was about: the sketch announced
  over Relay **before** `awaitReview` while the prose said after — swapped, with the reason
  (a subscriber fast enough to answer an announcement would be refused by the parked-only guard,
  then watch the task park on the question it just tried to answer) promoted into the prose as a
  requirement and asserted in behaviour 18; and the sketch made every failed guard write nothing,
  while §7 and §9 both promise the `answer` guard withdraws an `open` row whose task is terminal.
  The prose was right and the sketch moved: that withdrawal is read-site reconciliation, the same
  thing `status` does, and not the `cancel` wrapper the lock rules out.
- **Architect lock on the inbox key's *reason*, with the key itself untouched.** The lock's
  second half — *"issue ids are globally unique, so two epics cannot collide"* — does not survive
  two boards: the key is attempt-keyed and the attempt is **a board's** claim-time counter, so
  two epics driving the same issue-phase keep independent counters, both can produce attempt 1,
  and both land on one key. The exemption is real but rests on something else, now stated:
  **the reader is a person**, and an unfiltered listing spanning epics is the product. Written as
  one application of the rule locked across both PRs — *a key two boards write whose reader is a
  **job** needs the board's discriminator; a key whose reader is a **person** does not* — so the
  inbox reads as derived rather than special-cased, with the job-shaped keys (`runs/**`, the
  checkout, the branch) as the other application. §13 names the residue as a limit: one issue,
  one live epic, and a mid-flight move with the old manager still live can clobber attempt N's
  row. No epic segment, no compare-and-swap, no conductor-side status.
  **Seventh instance of the epic's shape, and the cheapest one in the set** — a rule stated over
  the case in front of us, ranging over less than it needed to. Here the correction is to the
  *justification* rather than the behaviour: nothing was broken, the code was right, and the only
  casualty would have been the next person reasoning from a premise that is false. That is the
  clearest illustration of why the shape is worth chasing — most instances cost a defect, this
  one cost only a wrong reason, and it surfaced the same way: by checking the claim against a
  second case (`runs/**`) rather than the one it was written for.
- **Round four — two self-contradictions and the window the last fold opened.** The correlation
  folded a round earlier was stated over the **counter** (`attempts` equality) when what it means
  is *the question the task is sitting on*, and a claim advances the counter without changing the
  question. So a wake that claimed and then failed to hand off left the answer durable,
  `attempts` moved, the row `in_progress` owned by nobody, and the correlation rejecting the
  retry — the operator answered and nothing runs, arriving through the machinery built to prevent
  exactly that. Both halves moved: the correlation now reads the question (equal while parked or
  `pending`, one behind once this answer's own claim has advanced it — **an offset the entry
  below replaces, because every reclaim advances the counter**), and recovery gained a
  third arm for an `in_progress` row **nobody owns**, which drains and lets the substrate's
  lease-lapse reclaim do the rest. **The sequence has four commit points, not three** — patch,
  resume, claim, hand off — and the arm is written over *ownership* because a live run and an
  abandoned claim share a status. **Eighth instance, and the second created by a fold**, which is
  what finally makes the pattern statable as a habit: every one of these came from writing the
  condition in the vocabulary of the mechanism in front of us — a status, a pair, a counter —
  rather than the thing being tracked: is a run live, which question is open, did this sequence
  commit. The seam appears wherever a mechanism changes state without changing meaning.
  Second, the create-only write lived **inside the park arm**, so a marker with an errored
  verdict never created a row and the failure arm withdrew one that did not exist — while
  behaviour 9 requires it durably `withdrawn`. The row is now created when the marker is read,
  before the outcome is selected; §9, §10 and the sketch were made to agree, and behaviour 9
  asserts the row is **present** and `withdrawn`, since an assertion that only checks "not
  `open`" passes against an absent row. Third, §7's own performance justification was half false:
  `get`/`upsert` are genuine point lookups (`ensureInstance`), but `list(prefix)` loads the
  **pattern** prefix and filters in memory, so the prompt fold and `status` read the user's whole
  cross-epic inbox. The claim is corrected per accessor rather than the key being moved, and
  §13's retention limit now carries a hot-path cost rather than only a storage one.
- **The third arm shipped, on a named observable — and the sweep that followed it.** The owner's
  condition for the partial-wake arm was that `answer` must be able to tell an **abandoned** claim
  from a **live** run, since status alone cannot: draining every `in_progress` resumes a run that
  is still working, which is worse than the hole the arm closes. It can. Abandonment is
  `in_progress` with `leaseUntil` present and already past — the substrate's own `leaseLapsed` —
  and the action reads the row server-side, where the whole persisted task comes back;
  `claimedBy` is redacted only on the client emission path, which this is not. An **absent**
  `leaseUntil` reads as live and declines (BP-030), because the arm refuses whenever it cannot
  *prove* abandonment: a stranded answer survives to the next wake, a run resumed underneath
  itself does not. The observable is in §7 and in §9's rows, and behaviour 16 gained the negative
  arm — same pair, live lease, must decline and dispatch nothing — since a suite without it
  passes against an action that drains everything.
  **Ninth instance, and the cheap half of the eighth:** when the correlation moved from the
  counter to the question, **three** artifacts kept teaching the old condition — §9's
  earlier-attempt row, §7's sketch, and §8's build step. Only the first had been pointed at; the
  sweep found the other two. Each was a faithful copy of a rule that changed underneath it, which
  is the same family as a comment still describing a topic shape that moved. **The habit gains a
  second half:** when a condition moves, sweep every artifact that states it rather than fixing
  the one in front of you — the cost of missing one is not a defect today, it is the next reader
  deriving the replaced condition from a document that still teaches it.

**Tenth instance, and it is the lesson landing on the fix written to apply it.** The correlation
was moved *"from the counter to the question"* — in the prose. What was encoded was **"one
behind"**, which is a counter condition wearing the new vocabulary: it tracks how many times the
mechanism has moved, so it survived exactly one abandoned hand-off. `applyClaimToTask` advances
`attempts` on every claim and `isClaimable` admits lease-lapsed rows, so a second failure at the
same point put the row two behind and stranded the answer again. **The rename was not the fix.**
A condition is only over facts when the mechanism can move any number of times without changing
it — that is the test, and "one behind" fails it on the second move. The condition now reads
`open` / `answered`-with-nothing-open, which no number of reclaims disturbs.
- **The correlation stopped counting.** The previous round moved the correlation *"from the
  counter to the question"* in the prose while encoding **"one behind"**, which is a counter
  condition in the new vocabulary: `applyClaimToTask` advances `attempts` on **every** claim and
  `isClaimable` admits lease-lapsed rows, so a second claim-before-hand-off failure put the row
  two behind and stranded the recorded answer with no drain left to run it. The offset was not
  widened — widening buys one more failure and keeps the counter in the condition. The condition
  is now read off the questions themselves: **proceed** requires the named row `open`;
  **recovery** requires it `answered` **and no `open` row** under `<issue>/<phase>/`, because an

  arithmetic, and it holds for any number of reclaims. Persisting the row key on the task was the

  condition did not change it. The test that would have caught it is now written down: a
