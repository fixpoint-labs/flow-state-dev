**R1.** The page does not say. It uses "app" throughout, saying a flow is served by an app and a kit adds flows to an app, but never defines the term.

**R2.** A kit is an installable unit that adds flows to an app from one config object. It can also declare slots that other kits fill.

**R3.** A flow is a set of blocks and actions that an app serves.

**R4.** A block is one unit of code with typed input and output. A board worker is one example, since it is the block that runs a task.

**R5.**
- (a) The page does not say where a worker's instructions live. It only says a Workforce worker is a configuration a user owns, and it mentions a worker's "file" that can say `harness: codex`.
- (b) You add a kit, which installs flows into an app. For example, the harness kit adds the coding board view and a shared coding worker flow.
- (c) The nearest match is a block, a unit of code with typed input and output. The page never says outright that a single step in handling a request is a block.

**P2.1.**
- **The other two research tasks:** They are unaffected. A failure marks only that task failed and the board keeps going, which is the default behavior when a worker throws. If the failed task has retries left, it goes back to `pending` and is tried again first.
- **Compare:** Once the failed task ends in error with no retries left, compare is cancelled and labelled `skipped`, and its row names the task that caused it. Compare never runs, even if the other two research tasks completed.
- **How the run ends:** With nothing ready and no active worker, the board stops with the reason "blocked by failures", because a task is errored.

**P2.2.** Not necessarily. By default tasks live on the running request, so they do not outlive it. To survive across requests they need a durable collection, which is a stored resource declared with a name and a scope. A board that has already stopped also needs its drain run again before it picks up new work (the page says this for retries). The page does not say what triggers that new drain.

**P2.3.** Compare must list the three research tasks as dependencies. The framework gives a board worker the goal, input, context and, by flow policy, results of earlier tasks. The default policy shows a worker only the results of its own dependencies, so compare would see exactly those three results.
