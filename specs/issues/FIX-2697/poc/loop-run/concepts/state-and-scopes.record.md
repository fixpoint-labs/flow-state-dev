## 2 · Cold-read questions

Written by an agent that had seen no draft. Pass 9 got these unchanged.

1. Alice, a customer of the support desk, is on the Pro plan. Her plan should be there in every new conversation she opens with the desk, without the browser sending it each time. Which scope do you put `plan` in, and how do you read it in a handler?
   Answer: User state. Declare it with `defineFlow({ user: { stateSchema } })` and read it as `ctx.user.state.plan`. User state follows one user across all their sessions and flows in one organization (eng/src/stores/scope-keys.ts:156-164), so the field is there in a brand-new conversation. Session state would not work: a session is one conversation, and the next request sees it only if it names the same `sessionId`.
2. During one reply, a block writes `{ phase: "running" }` into request state. A second request arrives a moment later in the same session. Can it read `phase`? *(edge case)*
   Answer: No. Request state lives on that request's own record, keyed by its request id, and starts as `{}` (eng/src/context/initial-request-record.ts:49, 66-92). The second request has its own id and its own record. To carry a value from one request to the next in a conversation, put it in session state, which the next request with the same `sessionId` sees.
3. Alice and Bob both work in the organization `acme`, and each has two conversations open with the desk. Which records do they share, and which belong to one person? *(edge case)*
   Answer: They share one org record, keyed by the bare org id `acme`, which every user and session in the org reads and writes (scope-keys.ts:196-203). Each has their own user record (`alice:~org:acme`, `bob:~org:acme`) that the other never reads. Each of the four sessions has its own record. So if Bob changes org state, Alice's next request sees it. Nothing Bob writes to his user or session state reaches her.
4. Session state holds `escalationScore`, an internal number the agent uses to decide when to hand off to a human. The session also holds `ticketStatus`, which the browser should show. How do you keep the score from the browser?
   Answer: Leave `escalationScore` out of `expose` and list only the other field: `session: { stateSchema, client: { expose: ["ticketStatus"] } }`. State is private unless the flow names a field in that scope's `client.expose`, and a flow with no `client` sends an empty `state` (core/types/flow.ts:54-63, 372-375; eng/test/session-read-projection.test.ts:128-136). Adding a field to the schema does not send it to the browser. One exception: a field marked `.readonly()` is visible to the client even when it is not exposed, so do not mark the score readonly.
5. While editing the flow, someone renames the user field `plan` to `tier` in the schema but leaves `client: { expose: ["plan"] }` as it was. What happens? *(edge case)*
   Answer: `defineFlow` throws when the flow is defined: `Flow "<kind>" user.client.expose names key(s) not on user.stateSchema: ... Valid keys: ...` (core/flow/defineFlow.ts:105-120). `expose` names must be top-level keys of that scope's `stateSchema`. Nothing reaches the browser with a stale name.
6. Alice also belongs to a second organization, `globex`. A conversation she starts there reads `ctx.user.state.plan`. Does it see her `acme` plan, and can she move an existing `acme` conversation over to `globex`? *(edge case)*
   Answer: No to both. The user record is keyed by user and org (`alice:~org:acme`, `alice:~org:globex`), so each org keeps its own copy and there is no cross-org user state (eng/test/user-cell-keys.test.ts:47-52). In `globex`, the field reads as its schema default until something writes it. A session is bound to one user and one org when it is created. A later request on that session that names another org is rejected with `OrgBindingMismatchError` (eng/test/binding-immutability.test.ts:128-164).
